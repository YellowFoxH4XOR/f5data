K000161335: VELOS controller-manager pods disrupted after assigning slots to 'none' partition

Published

  • F5OS-C: 1.8.X, 1.8.2, 1.8.1, 1.8.0
Source

Description

The two controller-manager pods are observed to be disrupted and are not in a 1/1 Ready state after assigning blades to the none partition.

For example, in the output of oc get pods --all-namespaces, the pods are observed to be in CrashLoopBackOff state, similar to the following example:

[root@controller-2(VEL410):Active ~]# oc get pods --all-namespaces -o wide | grep controller-manager
kube-service-catalog   controller-manager-kb7th   0/1       CrashLoopBackOff   1         27s       100.76.0.29   controller-1.chassis.local
kube-service-catalog   controller-manager-4zp6r   0/1       CrashLoopBackOff   1         37s       100.77.0.30   controller-2.chassis.local

The controller-manager pods might also be observed in Error or Running state with 0/1 Ready containers.

The output of oc logs -n kube-service-catalog <pod name> will show an error similar to the following:

controller_manager.go:237] error running controllers: failed to get api versions from server: failed to get supported resources from server: unable to retrieve the complete list of server APIs: subresources.kubevirt.io/v1alpha3: the server is currently unable to handle the request

Environment

  • Slots were previously assigned to an enabled VELOS partition
  • Slots assigned to 'none' partition

Cause

  • Bug ID 2291469: Assigning slots to 'none' VELOS partition causes controller-manager pods to be disrupted and 0/1 Ready

Recommended Actions

Assign the slots to an enabled partition.

CLI prompt may indicate Cluster update in-progress for a brief period as playbooks run to add blades into the cluster.

If the controller-manager pods fail to become ready after 30 minutes or more, generate a qkview and open a case with F5 Support for further investigation.
