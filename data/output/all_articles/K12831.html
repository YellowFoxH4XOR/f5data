Known Issue

After configuring packet filters, you may notice that the BIG-IP system is incorrectly dropping the return packets of certain connections.

This issue occurs when all of the following conditions are met:

  • The BIG-IP platform and software version support Clustered Multiprocessing (CMP).
  • CMP is enabled globally.
  • CMP is enabled for the specific traffic-handling object.
  • Packet filtering is enabled with the Filter established connections option disabled (this is the default setting).

When the Filter established connections option is disabled, the packet filter filters only new connections. Packets for a connection that is already established, or is being established, are not filtered. Essentially, a different packet filter rule to explicitly allow the return packets is not needed.

However, if the client-side and server-side connections are handled by different Traffic Management Microkernel (TMM) instances, which may happen under certain circumstances, the packet filter drops legitimate return traffic that the BIG-IP system should pass.

This issue occurs because the packet filter that is running on the different TMM instance does not recognize the return packets as part of an existing connection.

Impact

The BIG-IP system incorrectly drops return packets, which may cause your applications to fail or work intermittently.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • Packet captures show that the BIG-IP system is receiving return traffic for one or more connections, but failing to forward those packets.
  • Some connections may fail. DNS traffic, or traffic with IP fragments, are more likely to fail due to how TMM handles connections.
  • If logging is enabled for the affected packet filter rule, many entries similar to the following example are logged to the /var/log/pktfilter file:

    local/tmm notice tmm[4835]: 01250004:5: test_pf_rule (56687): reject on external, len: 98
    [IPv4 84 192.168.1.1 -> 192.168.1.2 ICMP 0:0]

Workaround

To work around this issue, you can perform one of the following tasks:

  • Define additional packet filter rules that explicitly allow return traffic.
  • Disable CMP for the affected traffic-handling object.

    Note: If the affected traffic-handling object is one that does not allow CMP to be disabled (for example a SNAT), you can first replace this object with an equivalent virtual server.

    Note: For more information about how to disable CMP for a specific virtual server, refer to K7751: Overview of Clustered Multiprocessing (9.x - 10.x).
