Description

The cand process manages the CAN buses for multiple clients (over UDP/SLIP/PPP). It manages utility communication among all cards in the VIPRION chassis, fan trays, and the Annunciator panel. When not running, the impact is a loss of function and communication between devices in the CAN bus occur. 

You may experience logs in /var/log/ltm on VIPRION devices related to the cand daemon such as the ones below:

slot1/<hostname> err cand[8294]: 013d0004:3: CAN bus 2 DOWN: sync failed (retrying) CanPicDev: send failed (error code: 0x1)
slot3/<hostname> err cand[8278]: 013d0004:3: CanPicDev: send failed (error code: 0x4)
slot2/<hostname> err cand[8285]: 013d0004:3: CanPicDev: send failed (error code: 0x4)
slot2/<hostname> err cand[8158]: 013d0004:3: CanPicDev: send failed (error code: 0x4)

Environment

  • cand logging
  • VIPRION devices

Cause

CAN data packet error codes (briefly) explained:

Code 1: Packet errors: this can happen when the CAN data packet is corrupted, for example, the size of the CAN packet sent out differs from what is intended, or a received packet has wrong header or no data at all, etc

Code 4: Invalid sequence number: the host and CPLD is out of sync. The host and the PIC use a sequence number in the header to match up the requests and replies between them. If somehow the sequence number in the received packet is not expected, this PIC error will return. Upon seeing this error, the host wil try to recover by resyncing with the PIC to reset the sequence number.

These error messages indicated that there was a timed-out reply from the PIC to the host for the request of the CPLD sensor data via CAN bus on blade 3, and chmand later recovered from the failure. CPLD data is read every second on all blades, and such time-outs will happen occasionally, when there are bursts of CAN bus accesses.

Recommended Actions

None - These log entries can be safely ignored.
