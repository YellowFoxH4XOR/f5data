Topic

This article applies to BIG-IP 11.x. For information about other versions, refer to the following articles:

  • K29377715: Overview of the TCP profile (14.x)
  • K10711911: Overview of the TCP profile (13.x)
  • K70025261: Overview of the TCP profile (12.x)
  • K7559: Overview of the TCP profile (9.x - 10.x)

The TCP profile allows an administrator to specify how a BIG-IP virtual server processes TCP traffic. You can use the TCP profile alone, to manage traffic, or in conjunction with other profiles, such as the HTTP profile for processing Layer 7 (L7) traffic, or the SSL profile for processing Secure Sockets Layer (SSL) traffic.

The TCP profile is located in the Configuration utility, under Local Traffic > Profiles > Protocol > TCP.

Note: F5 recommends that you create a custom TCP profile instead of modifying the default TCP profile. Creating a custom TCP profile allows you to associate a custom profile, which contains specific settings, with individual or groups of virtual servers.

Settings and definitions in the TCP profile

Beginning in BIG-IP 11.6.0, the Configuration utility organizes the TCP profile in a manner that better indicates the purpose and impact of the available settings. Unless otherwise noted, the same settings and values are available in earlier BIG-IP 11.x versions, but may be displayed in a different order. This article is formatted to describe the settings and definitions of the TCP profile as they appear in the BIG-IP 11.6.0 Configuration utility.

Timer Management

SettingDefault ValueDescription
Close WaitSpecify : 5 secondsAvailable options:
  • Specify: User-specified amount of time (in seconds) that a TCP connection remains in the LAST/ACK state before quitting.
  • Immediate: Specifies that the TCP connection closes immediately after entering the LAST/ACK state.
  • Indefinite: Specifies that TCP connections in the LAST/ACK state do not close until they meet the maximum retransmission timeout (RTO).
Fin WaitSpecify : 5 secondsAvailable options:
  • Specify: User-specified amount of time (in seconds) that a TCP connection is in the FIN/WAIT or CLOSING state before closing.
  • Immediate: Specifies that the TCP connection closes immediately after entering the FIN/WAIT or CLOSING state.
  • Indefinite: Specifies that TCP connections in the FIN/WAIT or CLOSING state do not quit.

Note: This setting applies only to TCP connections in the FIN/WAIT-1 state. TCP connections in the FIN/WAIT-2 state are handled by the Idle Timeout setting.

Idle TimeoutSpecify : 300 secondsAvailable options:
  • Specify: User-specified amount of time (in seconds) that the connection can remain idle before the connection is eligible for deletion.
  • Indefinite: Specifies that the connection can remain idle indefinitely.

Note: Use caution when adjusting idle times, as each TCP connection requires resources to track and maintain. Allowing TCP connections for long periods of time uses more resources that can be better used for new connections.

Keep Alive IntervalSpecify : 1800 secondsAvailable options:
  • Specify: User-specified amount of time (in seconds) that determines the interval at which the system sends data over an idle connection to decide whether the connection is still valid.
  • Indefinite: Specifies that the system does not send Keep-Alive communications.
Minimum RTO
(11.4.0 and later)		0 millisecondsThis setting specifies the minimum length of time the system waits for acknowledgements of data sent before resending the data. The value must be equal to or less than 5000. The default value is 0 milliseconds, which means that the system uses the RFC-compliant value of 1 second. If the Packet Loss Ignore Rate and Packet Loss Ignore Burst settings contain values other than 0, this value drops to 203 ms. If MPTCP is enabled, the value drops to 200 ms.

Note: This setting is not available in the Configuration utility until BIG-IP 11.6.0. For previous versions, you can use the Traffic Management Shell (tmsh) for this setting.

Reset On TimeoutEnabledWhen the connection exceeds the Idle Timeout value, the system sends a reset (RST) and deletes the TCP connection. If disabled, the system deletes the TCP connection when the connection exceeds the Idle Timeout value, but does not send an RST to the client.

Note: If the Reset on Timeout setting is disabled, the client can assume that the connection is still valid long after it has been removed from the BIG-IP LTM system.

Time WaitSpecify : 2000 millisecondsAvailable options:
  • Specify: User-specified amount of time (in milliseconds) that a TCP connection remains in the TIME-WAIT state before the system closes it. Values range from 0 to 600000 milliseconds.
  • Immediate: Specifies that the system closes the connection immediately after the connection enters the TIME-WAIT state.
  • Indefinite: Specifies that TCP connections can remain in the TIME-WAIT state indefinitely.
Time Wait RecycleEnabledWhen a SYN packet is received in a TIME-WAIT state, the system recycles or reuses the connection. This option allows the system to better optimize system resources by reusing a connection in a TIME-WAIT state when a SYN packet is received, instead of creating a new connection.

Note: If disabled, the system establishes a new connection instead of reusing a connection that is in a TIME-WAIT state.

Zero Window TimeoutSpecify : 20000 millisecondsAvailable options:
  • Specify: User-specified amount of time (in milliseconds) that the TCP connection can receive zero-length window probes before the system closes the connection.

    Note: The timeout starts when the peer advertises a zero length TCP window or when enough data has been sent to fill the previously advertised window. The timer is cancelled when a non-zero length window is received.

    Note: The BIG-IP system honors timeout values in multiples of 5000 (for example: 5000 ms, 10000 ms, and 20000 ms). This behavior accounts for the minimal time required for CPU timers and Round Trip Time (RTT) of packets to ensure that when a zero window size update is received, the system allows the counter to start and TCP window probes are sent to query whether there is a window size change on the receiver. If you enter a value that is not a multiple of 5000, the system rounds the value up to the next multiple of 5000. For example, if a 0 is entered, the system rounds up to 5000 ms. If 7000 is entered, the system rounds up to 10000 ms.

  • Indefinite: Specifies that the system does not delete TCP connections based on a zero- length window.

Data Transfer

SettingDefault ValueDescription
Acknowledge on PushEnabledThis setting improves performance to Windows and Mac OS peers writing out on a small send buffer.
Delayed AcksEnabledThis setting allows the system to send fewer than one ACK (acknowledgment) segment, per data segment received. This is part of TCP congestion control, defined in RFC 1122: Requirements for Internet Host and RFC 2581: TCP Congestion Control.

Note: F5 recommends that you keep this setting enabled, as it allows the application to update the TCP window and send an immediate response if required. This setting also reduces the number of segments sent by the server.

Initial Receive Window Size0 MSS unitsThis setting specifies the initial receive window size for connections to this destination. Actual window size is this value multiplied by the MSS for the same connection. The default value is 0 (zero), meaning that the system uses the Slow Start value. Valid values range from 0 to 16.
Max Segment Size (MSS)
(11.5.0 and later)		1460 bytesThis setting specifies the largest amount of data that the system can receive in a single TCP segment, not including the TCP and IP headers. If the value is 0 (zero), the system calculates the value from the maximum transmission unit (MTU). The default value is 1460 bytes.
Nagle's AlgorithmDisabledWhen enabled, this setting specifies that the system applies Nagle's algorithm to reduce the number of short segments on the network. Detailed in RFC 896: Congestion Control in IP/TCP Internetworks, the Nagle Algorithm is a TCP optimization that makes the stack wait until all data is acknowledged on a connection before sending more data. This process, known as nagling, increases the efficiency of a network application system by decreasing the number of packets that must be sent.

Note: In some highly interactive client/server environments, the use of Nagle's Algorithm might cause undesired behavior and should be disabled.

Congestion Control

SettingDefault ValueDescription
Appropriate Byte Counting (RFC 3465)EnabledThis setting increases the congestion window by basing the increase amount on the number of previously-unacknowledged bytes that each ACK covers.
Congestion Metrics CacheEnabledThis setting specifies that the system uses a cache for storing congestion metrics.
Congestion ControlHigh SpeedThis setting specifies the congestion control mechanism that the BIG-IP system uses.

Available options:
  • None: No congestion control algorithm implemented.
  • High Speed: A more aggressive, loss-based algorithm.

    For more information, refer to RFC 3649: HighSpeed TCP for Large Congestion Windows.

  • New Reno: A modification to the Reno algorithm that responds to partial acknowledgments when selective acknowledgments (SACK) are unavailable.

    For more information, refer to RFC 2582: The NewReno Modification to TCP's Fast Recovery Algorithm.

  • Reno: An implementation of the TCP Fast Recovery algorithm, based on the implementation in the BSD Reno release.

    For more information, refer to RFC 2581: TCP Congestion Control.

  • Scalable: A TCP algorithm modification that adds a scalable, delay-based and loss-based component into the Reno algorithm. This option is used in conjunction with the Appropriate Byte Counting setting.
  • CUBIC (11.6.0 and later): Specifies that the system uses a TCP algorithm that is optimized for high bandwidth, high delay networks.
  • Westwood+ (11.6.0 and later): Specifies that the system uses a TCP algorithm based on a bandwidth estimation metric.
  • CAIA Delay Gradient (CDG) (11.5.0 and later): Specifies that the system uses a delay based TCP that senses onset of congestion by variations in round trip time (RTT).
  • CAIA Hamilton Delay (CHD) (11.5.0 and later): Specifies that the system uses a TCP algorithm that aims to keep network queuing delays below a particular threshold (queue_threshold) and decides to reduce the congestion window (cwnd) probabilistically based on its estimate of the network queuing delay.
  • Illinois (11.5.0 and later): Specifies that the system uses a TCP algorithm that is especially targeted at high-speed, long-distance networks.
  • Vegas (11.5.0 and later): Specifies that the system uses a TCP algorithm modification that adds a delay-based and loss-based component into the Reno algorithm.
  • Woodside (11.5.0 and later): Specifies that the system uses a TCP algorithm that is especially targeted at high-speed, long-distance networks with enhanced congestion recovery.
Delay Window ControlDisabledWhen enabled, this setting specifies that the system uses an estimate of queuing delay as a measure of congestion to control the amount of data sent (in addition to the normal loss-based control).
Explicit Congestion NotificationDisabledWhen enabled, this setting specifies that the system uses the TCP flags CWR (Congestion Window Reduced) and ECE (ECN-Echo, used to indicate that the TCP peer is Explicit Congestion Notification capable during the three-way handshake) to notify its peer of congestion and congestion counter-measures.

Note: When this setting is enabled, it is used only when two hosts signal that they want to use it. This setting allows a host to set the ECN bit within the IP header to notify the transmitter that the link is congested.

Initial Congestion Window Size0 MSS unitsThis setting specifies the initial congestion window size for connections to this destination. Actual window size is this value multiplied by the MSS for the same connection. The default value is 0 (zero), meaning that the system uses the values specified in RFC 2414. Valid values range from 0 to 16.
Packet Loss Ignore Burst0 packet countThis setting specifies the probability of performing congestion control when multiple packets are lost, even if the Packet Loss Ignore Rate value was not exceeded. Valid values range from 0 to 32. The default value is 0, meaning that the system performs congestion control if any packets are lost. Higher values decrease the chance of performing congestion control.
Packet Loss Ignore Rate0 packets lost per millionThis setting specifies the threshold of packets lost per million at which the system performs congestion control. Valid values range from 0 to 1,000,000. The default value is 0, meaning the system performs congestion control if any packet loss occurs. If you set the ignore rate to 10 and packet loss for a TCP connection is greater than 10 per million, congestion control occurs.
Rate Pace
(11.5.0 and later)		DisabledThe system paces the egress packets to avoid dropping packets, allowing for optimum goodput. This option mitigates bursty behavior in mobile networks.
Slow StartEnabledThis setting specifies that the system uses larger initial window sizes, as specified in RFC 3390: Increasing TCP's Initial Window, to help reduce round trip times. TCP slow-start congestion avoidance is a method of converging on the right amount of data to put on the link without overloading the link in order to prevent packets from being dropped.
Timestamps Extension for High Performance (RFC 1323)
(11.4.0 and later)		EnabledThis setting specifies that the system uses the timestamp extensions for TCP, as specified in RFC 1323, to enhance high-speed network performance. The timestamp option allows for accurate RTT measurement, in addition to simplifying window calculations for the sender.

Note: Beginning in BIG-IP 11.4.0, the window scale functionality is built into the TCP profile and cannot be manually disabled or enabled. The functionality will be negotiated if the send or receive buffer is larger than 65535 bytes. This option only controls the Timestamp functionality.

Loss Detection and Recovery

SettingDefault ValueDescription
D-SAC (RFC 2883)DisabledThis setting specifies the use of the Selective ACKs (SACK) option to acknowledge duplicate segments. RFC 2883 specifies an extension to Selective Acknowledgements, known as D-SACK. Using D-SACK blocks, a receiver can notify its peer when it receives multiple copies of data, thus warning the sender of in-band network replication of segments, or causing the peer to scale back in its re-sending speed.

Note: F5 recommends that you do not enable this option unless the peer device communicating with the BIG-IP system also supports D-SACK.

Early Retransmit
(11.6.0 and later)		DisabledWhen enabled, this setting specifies that the system uses early retransmit (as specified in RFC 5827) to reduce the recovery time for connections that are receive- buffer or user-data limited. By default, this setting is disabled. Enabling this setting allows TCP to assume a packet is lost after fewer than the standard number of duplicate ACKs, if there is no way to send new data and generate more duplicate ACKs.
Initial Retransmission Timeout Base Multiplier for SYN Retransmission0 millisecondsThis setting specifies the initial RTO base multiplier for SYN retransmissions. The default value is 0 (zero), which sets the initial base RTO for SYN retransmissions at three seconds. This value is modified by the exponential backoff table to select the interval for subsequent retransmissions.

For example, if the value of this setting is changed to 1000, then the initial base SYN RTO would be changed to one second, and the next RTO would be two seconds, and then the subsequent RTO would be four seconds, etc., based on the exponential backoff table.

Limited Transmit RecoveryEnabledThis setting specifies that the system uses limited transmit recovery revisions for fast retransmits, as specified in RFC 3042: Enhancing TCP's Loss Recovery Using Limited Transmit to reduce the recovery time for connections on a lossy network.
Maximum Segment Retransmissions8This setting specifies the maximum number of times the system resends data segments.
Maximum Syn Retransmissions3This setting specifies the maximum number of times the system resends a SYN when it does not receive a corresponding SYN/ACK.
Selective ACKsEnabledThis setting specifies that the system processes data using selective ACKs in order to improve system performance.

Note: F5 recommends that you do not disable this option. Selective ACKs (SACK) improves performance by explicitly listing which packets, messages, or segments in a stream are acknowledged. This lets the sender know specifically what information is missing, so that it only retransmits the missing information. For more information about SACK, refer to RFC 2018: TCP Selective Acknowledgment Options.

Selective NACKDisabledThe system processes data using a selective negative acknowledgment (SNACK) whenever possible, to improve system performance.
Tail Loss Probe
(11.6.0 and later)		DisabledWhen enabled, this setting specifies that the system uses Tail Loss Probe to reduce the number of RTOs. RTOs occur when TCP segments are lost from the tail of a transaction or a window of data/ACKs are lost. By default, this setting is disabled. Enabling this setting allows TCP to send a probe segment to trigger fast recovery instead of recovering a loss via an RTO.

Security and Quality of Service

SettingDefault ValueDescription
Hardware SYN Cookie ProtectionEnabledThis setting enables or disables hardware SYN cookie protection when PVA10 is present on the system. This feature is available on certain hardware platforms only, specifically, those on which PVA10 is present.
SYN Cookie White List
(11.6.0 and later)		DisabledThis setting specifies whether or not to use the SYN Cookie White List. This feature is primarily useful in environments configured for nPath routing (also known as asymmetric routing or multipath routing). In these environments, the BIG-IP system sees only the inbound traffic, and responses from the server go directly from the server to the client, bypassing the BIG-IP system. Because of how traffic processing works in nPath configurations, you cannot use SYN cookies, so the SYN Cookie White List option provides similar functionality. When enabled, the white list is populated by challenging clients with an RST packet. Clients that respond appropriately, by sending a retry, are included in the white list for the configured time (the default time is 30 seconds). The white list is not shared among blades, which means the client is challenged by each blade, and the client host may see multiple challenge/RST actions.

Note: F5 is working to eliminate exclusionary language in our products and documentation. For more information, refer to K34150231: Exclusionary language in F5 products and documentation.

MD5 SignatureDisabledWhen enabled, this setting specifies to use RFC 2385 TCP-MD5 signatures to protect TCP traffic against intermediate tampering.

Note: When the MD5 Signature and MD5 Signature Passphrase settings are enabled, they protect Border Gateway Protocol (BGP) sessions from being tampered with, as BGP utilizes TCP as its transport. MD5 Signature provides enhanced security between BGP endpoints.

MD5 Signature PassphraseBlankType the plain-text passphrase (from 1 to 80 characters in length) that is used in a shared-secret scheme to implement the spoof-prevention parts of RFC 2385.

Note: When the MD5 Signature and MD5 Signature Passphrase settings are enabled, they protect BGP sessions from being tampered with, as BGP utilizes TCP as its transport. MD5 Signature provides enhanced security between BGP endpoints.

IP ToSSpecify : 0This setting specifies the Layer 3 (L3) Type of Service (ToS) level that the system inserts in the TCP packets destined for clients.

Available options:

  • Specify: Specifies the IP ToS setting that the system inserts in the IP packet header. You can specify a number between 0 and 255.
  • Pass Through: Specifies that the IP ToS setting remains unchanged.
  • Mimic: Specifies that the system sets the ToS level of outgoing packets to the same ToS level of the most-recently received incoming packet. For example if the most-recently received packet had a ToS level of 3, the system sets the ToS level of the next outgoing packet to 3.

The IP ToS is part of the TCP/IP and is primarily used for ToS Application Routing, which is supported by Open Shortest Path First (OSPF) and Intermediate System-to-Intermediate System (IS-IS). This setting allows the administrator to specify the importance and routing preference the packet should be given on a supported network. For more information about ToS Precedence values and a description of ToS Application Routing, refer to the following RFCs:

  • RFC 791: INTERNET PROTOCOL
  • RFC 1583: OSPF Version 2
  • RFC 2474: Definition of the Differentiated Services Field (DS Field) in the IPv4 and IPv6 Headers
Link QoSSpecify : 0This setting specifies the Layer 2 (L2) Quality of Service (QoS) level that the system inserts in the TCP packets destined for clients.

The Link QoS is used to specify the QoS level that the system assigns to the TCP packets when sending to a client. These values are similar to IP ToS, but are applied to the link layer or L2. For more information about QoS, refer to the following RFCs:

  • RFC 2474: Definition of the Differentiated Services Field (DS Field) in the IPv4 and IPv6 Headers
  • RFC 2697: A Single Rate Three Color Marker
  • RFC 2597: Assured Forwarding PHB Group
  • RFC 2598: An Expedited Forwarding PHB

Note: F5 is working to eliminate exclusionary language in our products and documentation. For more information, refer to K34150231: Exclusionary language in F5 products and documentation.
