Improper assets management

Improper assets management vulnerabilities can occur when security best practices are not followed during the API development cycle, as described in the following bullets:

  • During the API design phase, security best practices should be an integral part of the design implementation. Failure to maintain documentation that describes how the API is designed and failure to follow security best practices in the design phase may lead to vulnerabilities such as old API versions, unpatched systems, and unnecessarily exposed API endpoints.
  • Using up-to-date API documentation is essential for the application and DevOps teams that are building the APIs; good documentation practices provide security benefits throughout the API lifecycle. For example, using the current version of the OpenAPI specification (OAS) to define the structure and syntax of your APIs may prevent well-known misconfigurations. Failure to use API documentation or using outdated documentation makes it more difficult to find and fix vulnerabilities in a timely manner.
  • Testing the API for security flaws throughout the API development lifecycle should be a priority. Failure to perform security testing may lead to well-known misconfigurations or vulnerabilities.
  • During the deployment phase, external protection measures such as API security firewalls should be implemented for all exposed versions of your APIs.
  • Inventory your APIs. Perform regular perimeter scans to discover and inventory your APIs so that you can manage them. Failure to manage existing APIs and de-commission old APIs may result in increased risk to your environment.

Improper assets management common weakness enumeration (CWE)

The following common weaknesses may increase the likelihood of attacks against your APIs:

  • CWE-1059: Incomplete Documentation
  • CWE-1053: Missing Documentation for Design

Improper assets management attack scenario

In the following scenario the attacker finds old, unpatched API endpoints that are still connected to the production database.

  1. The attacker uses an automated scanning tool to search production APIs on the target system.
  2. The scanning tool finds old, unprotected API resources.
  3. Since the old API is not running the latest code, the attacker uses injection attacks to compromise the production database.

Secure your APIs against improper assets management attacks with F5 products

To protect your APIs, best practices recommend that you implement a repeatable process that is audited for security when setting up and configuring your environment. Include, in your configurations, the F5 features listed in the following tables.

Use BIG-IP APM to mitigate improper assets management attacks

You should have a simple, clear, and repeatable process when updating to new API versions. This process makes it clear which environment the API is running, who has access to the production and test servers, which API version is running, and so on. BIG-IP APM addresses these concerns by implementing API Protection using a hierarchy of resources in a modular approach, as follows:

BIG-IP virtual server >> API Protection profile >> OpenAPI spec file 

An API protection profile is associated with a BIG-IP virtual server. The profile is created by importing an OAS file that specifies defining API endpoints, servers, and so on. This modular approach facilitates API versioning, testing, and change management. For example, to update to a new API version, complete the following steps:

  1. Specify new API specifications in an OAS file.
  2. Create a new API protection profile by importing the new spec file.
  3. Associate the new API protection profile to a new test virtual server, accessible only internally.
  4. To update to the new API version in production, simply de-associate the old API protection profile from the production virtual server and replace it with the new API protection profile. 

You can perform this change manually on the BIG-IP Configuration utility or with Guided Configuration.
