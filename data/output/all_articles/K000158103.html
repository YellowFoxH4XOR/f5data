Description

When switching to cookie encryption and using it through iRules or policies to persist via the URI, users may experience blank screens, unauthorized access errors, or find their sessions load balanced to different servers despite using the same browser session. Switching back to non-encrypted cookie persistence resolves the issue.

Environment

  • BIG-IP LTM

Cause

Enabling cookie encryption causes BIG-IP to use a single encrypted cookie name for all pools associated with the virtual server. When a single cookie encryption profile is applied to multiple pools, each pool encrypts the cookie value with its own encryption key. If traffic later reaches another pool, the encrypted value is rewritten using that pool’s key. As a result, BIG-IP may re-load balance the request, even if an iRule or policy had previously directed the request to a specific pool. This issue does not occur when encryption is disabled because BIG-IP automatically includes the pool name in the cookie when no encryption profile is applied.

Recommended Actions

When switching to encrypted cookie persistence, ensure that each pool requiring persistence is configured with a unique cookie name. This prevents pools from overwriting one another’s encrypted cookie values and allows them to persist traffic independently in the same way non-encrypted cookie persistence behaves.
