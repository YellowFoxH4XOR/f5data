Description

Understanding authorization policies

Authorization policies enable access control of workloads in the mesh. To define an authorization policy resource, we need to specify three fields in the spec section:

  • Selector: Defines what workloads this policy will apply to.
  • Action: If the rule matches the request define whether it is a deny or allow.
  • Rules: Defines a list of rules that will trigger this policy.

At the rules level we can optionally specify three fields:

  • From: Defines where the request is coming from, this could be ipblocks, namespaces, principals, notIpblocks, notnamespaces, etc.
  • To: Specifies the operation of a request, such as host or method.
  • When: It will define additional conditions of a request.

Istio Authorization Policy with XFCC condition

  • As explained before we can specify additional conditions using the field when we can use different keys and values. For information about the list of supported keys, refer to the Istio configuration guide: Authorization Policy Conditions.
  • The following example shows a Authorization Policy has been defined to allow communication from pods in test1-ns and test-ns2 to host httpbin.dummy1-ns.svc.cluster.local using XFCC headers as a matching condition, but does not work properly:

    Note: This condition intends to check sleep’s pod XFCC header and look for the DNS key using wildcards with unsupported format: *DNS=sleep.example.com*, after testing this policy, it didn’t work as expected and getting a RBAC: access denied message.

    apiVersion: security.istio.io/v1beta1
    kind: AuthorizationPolicy
    metadata:
      name: test-authz-policy
      namespace: dummy1-ns
    spec:
      action: ALLOW
      rules:
      - from:
        - source:
            namespaces: ["test1-ns", "test2-ns"]
        to:
        - operation:
            hosts: ["httpbin.dummy1-ns.svc.cluster.local"]
            paths: ["/headers"]
        when:
        - key: request.headers[X-Forwarded-Client-Cert]
          values: ["*DNS=sleep.example.com*"]

Environment

  • Kubernetes: 1.17x, 1.18.x, 1.19.x, 1.20.x
  • Aspen Mesh: 1.6.x, 1.9.x

Cause

Istio Authorization Policy rules only support Exact, Prefix, Suffix and Presence match:

  • Exact match: “abc” will match on value “abc”.
  • Prefix match: “abc*” will match on value “abc” and “abcd”.
  • Suffix match: “*abc” will match on value “abc” and “xabc”.
  • Presence match: “*” will match when value is not empty.
Important: Expressions like *string* are not currently supported.

Contents of XFCC header will be seen as a single string, even if it seems keys are separated by semi-colons. For example:

'x-forwarded-client-cert', 'By=spiffe://cluster.local/ns/dummy1-ns/sa/httpbin;Hash=ee902b419baac145c784692a2cb1dfa6c9c8bd34ffec55cae5878d5d5d50be65;Subject="";URI=spiffe://cluster.local/ns/test1-ns/sa/sleep;DNS=a.example.com;DNS=sleep.example.com'

Recommended Actions

Since the XFCC header value is seen as a single string if we want to use the DNS key from the XFCC header the following condition must be defined. For example:

    when:
    - key: request.headers[X-Forwarded-Client-Cert]
      values: ["*DNS=sleep.example.com"]

This condition is using a suffix for the string defined in the XFCC header, it will match everything that is before DNS=sleep.example.com.

Additional Information

For information about XFCC headers, refer to the Aspen Mesh operations guide: Configuring XFCC Headers.
