K000162391: [Azure ARM Templates] Inconsistent BIG-IP VE interface mapping due to Azure NIC index ordering

Type
Support Solution
Published
2026-08-07
Updated
2026-08-07
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000162391

Description

A three-NIC BIG-IP LTM VE deployment in Microsoft Azure can assign external and internal self IP addresses to the wrong interfaces. This occurs when Azure presents the NICs in an order that differs from the order expected by metadata lookups using NIC indexes.

The resulting error may include:

metadataProvider should NOT have additional properties

metadataProvider should have required property 'index'

metadataProvider should match "then" schema

Environment

  • BIG-IP LTM VE.
  • Microsoft Azure.
  • Three NICs per BIG-IP VE:
    • Management network.
    • External traffic network.
    • Internal traffic network.
  • HA deployment using f5-azure-arm-templates-v2.
  • Declarative Onboarding configuration.
  • External and internal IPv4 addresses resolved through Azure network metadata with index: 1 and index: 2.

Cause

Azure NIC attachment or presentation order is not deterministic across virtual machine deployments. Metadata lookups based on NIC indexes can therefore associate external and internal addresses with the wrong BIG-IP interfaces.

The template uses metadata definitions similar to the following:

- name: SELF_IP_EXTERNAL
type: metadata
metadataProvider:
type: network
environment: azure
field: ipv4
index: 1

- name: SELF_IP_INTERNAL
type: metadata
metadataProvider:
type: network
environment: azure
field: ipv4
index: 2

Replacing index with addressPrefix is not accepted by the runtime-init schema and causes declaration validation errors.

If the self IPs are changed to static values while the default and management gateways remain metadata-based, gateway discovery can select the wrong subnet gateway. This can cause incorrect routing and errors such as:

Unable to register device: connect EHOSTUNREACH <destination>:443

Recommended Actions

For fixed BIG-IP LTM VE HA deployments with pre-allocated IP addresses, use static values for both self IPs and gateways instead of Azure network metadata indexes.

  1. Replace the external and internal self IP metadata definitions with static definitions:

    - name: SELF_IP_EXTERNAL
    type: static
    value: '<external-self-IP>/24'

    - name: SELF_IP_INTERNAL
    type: static
    value: '<internal-self-IP>/24'

  2. Change the default and management gateway definitions to static values:

    - name: DEFAULT_GW
    type: static
    value: '<external-gateway-IP>'

    - name: MGMT_GW
    type: static
    value: '<management-gateway-IP>'

  3. Use the required value formats:
    • Self IP values must use CIDR notation, such as <external-self-IP>/24.
    • Gateway values must be bare IP addresses without a subnet mask.
    • Do not specify a gateway as <gateway-IP>/24.
  4. Ensure that the static values correspond to the intended networks:
    • SELF_IP_EXTERNAL must belong to the external subnet.
    • SELF_IP_INTERNAL must belong to the internal subnet.
    • DEFAULT_GW must be the gateway for the external traffic network.
    • MGMT_GW must be the gateway for the management network.
  5. Redeploy or onboard the affected BIG-IP VE using the modified YAML declaration.
  6. Verify that:
    • The external self IP is assigned to BIG-IP interface 1.1.
    • The internal self IP is assigned to BIG-IP interface 1.2.
    • The default route uses the external gateway.
    • The management route uses the management gateway.
    • Required F5 services are reachable over HTTPS.

Additional Information

  • The standard template uses metadata to support dynamic provisioning and generic deployment scenarios.
  • Metadata-based NIC indexes may be used where interface ordering is controlled and deterministic.
  • For fixed HA deployments with explicitly allocated IP addresses, static values avoid dependence on Azure NIC ordering and provide deterministic interface-to-address assignments.
  • Using static self IPs without also using static gateway values is not sufficient; all dependent network parameters must be aligned.
  • The addressPrefix modification should not be used with the affected runtime-init schema because it results in declaration validation failure.
