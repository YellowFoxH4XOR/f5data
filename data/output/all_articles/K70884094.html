Description

WebSocket is a protocol used for bidirectional communication between the client and the server. It is standardized by RFC 6455 and widely used by applications and API implementations. WebSocket is distinct from HTTP, but it uses HTTP Upgrade header to establish a connection between parties. Istio cannot recognize WebSocket protocol, but the WebSocket is supported by Istio Proxy sidecars out of the box and there is no need for additional configuration. In this article we will show the WebSocket application in action and check Envoy configuration configuring WebSocket protocol.

Envoy support for WebSocket is documented in the below links:

  • HTTP Upgrades
  • HTTP connection manager

Istio protocol selection and discovery is described in the linked article below:

  • Protocol Selection

Environment

  • Aspen Mesh: 1.6.x, 1.9.x

Recommended Actions

We will use WebSocket's Python library to deploy WebSocket applications in our cluster. WebSocket's documentation contains an example code and yaml manifest we can use to create a WebSocket application in our cluster. Please follow the steps from the Containerize application section in the linked article below to create a Python application and build an image we will use later:

Note: You may want to push your image to a public repository like dockerhub or quay so our Kubernetes cluster can pull the image from that remote repo. Use docker push <image> command to push the image if you use Docker to build the image.

  • Deploy to Kubernetes

We may want to modify the deployment configuration from the example above to run the WebSocket server in Istio mesh.

Below is the yaml file you can use to deploy:

apiVersion: v1
kind: Service
metadata:
  name: websockets-test
spec:
  type: ClusterIP
  ports:
    - port: 8001
      targetPort: 80
      name: http-websocket
  selector:
    app: websockets-test
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: websockets-test
spec:
  selector:
    matchLabels:
      app: websockets-test
  template:
    metadata:
      labels:
        app: websockets-test
    spec:
      containers:
      - name: websockets-test
        image: quay.io/<path to your repo>/websocket-server:latest
        livenessProbe:
          httpGet:
            path: /healthz
            port: 80
          periodSeconds: 1
        ports:
        - containerPort: 80

Having the server image and above deployment manifest we need to deploy the application to the namespace being a part of the Istio mesh (where Istio injects istio-proxy sidecar).

Now we will deploy Client WebSocket application we can use to open a WebSocket interactive echo communication.

We will use the same WebSockets Python library to test our application but we will need to build an image with a preinstalled library. You can use the below simple Dockerfile to create the image we will use:

FROM python:3.9-alpine
RUN pip install websocket

Use Docker to build and push the image. The below yaml manifest can be used to deploy the image to our cluster:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: websockets-client-sleep
spec:
  selector:
    matchLabels:
      app: websockets-client
  template:
    metadata:
      labels:
        app: websockets-client
    spec:
      containers:
      - name: websockets-client
        image: quay.io/<path-to-yourrepo>/websocket-client:latest
        command: ["sleep", "14d"]

Deploy above yaml file to the same namespace where you deployed WebSocket server application.

To test the application, we need to open a shell command to the client POD:

kubectl exec -it -n <namespace> websockets-client-sleep-<xxxx> -- sh

To open a WebSocket interactive echo connection to our server we can use the command from the below example: 

/ # python3 -m websockets ws://websockets-test.<namespace>.svc.cluster.local:8001
Connected to ws://websockets-test.ws.svc.cluster.local:8001.
> test
< test
>test2
<test2
Connection closed: 1000 (OK).
/ #

Below examples show how the WebSocket connection may appear in the istio-proxy access logs:

  • On client side

    ? kubectl logs websockets-client-sleep-68b894bd4-d9w8x -n ws -c istio-proxy | tail -2

  • On server side

    ? kubectl logs websockets-test-dbf7d79f4-62t78 -n ws -c istio-proxy | tail -1
    [2021-11-24T11:58:17.091Z] "GET / HTTP/1.1" 101 UC upstream_reset_after_response_started{connection_termination} - "-" 19 11 2931 - "-" "Python/3.9 websockets/10.1" "4e1f2a9e-bff2-4aa6-8acc-3353f8b476b0" "websockets-test.ws.svc.cluster.local:8001" "127.0.0.1:80" inbound|80|| 127.0.0.1:53064 192.0.2.4:80 192.0.2.184:34506 - default

As you can see above, we have only one Access Log entry for the WebSocket connection even though we sent two requests to the echo server (test and test2). Envoy will create that access log entry only after the connection is closed and we will not see any message for every tcp request. This is because Envoy sees a WebSocket connection as a TCP bytes flow and only HTTP Upgrade request/response is understood by the proxy.
