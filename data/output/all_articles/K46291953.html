Issue

Old Behavior

In versions prior to BIG-IP 13.0.0, when there is a virtual server configured with an HTTP profile that is expecting a body in a response, the BIG-IP system waits until it receives part of the body before sending HTTP headers smaller than 16 kilobytes (KB) in length. For example, a virtual server expects a body when the response has no Content-Length header.

By combining the headers and body into one packet before sending a response, the BIG-IP system can reduce the total number of packets it sends. However, when a response body is less than 16 KB in length and delays or fails to send because a server is misconfigured or non-compliant, the BIG-IP system waits until the connection closes before sending the response.

New Behavior

Beginning in BIG-IP 13.0.0, when a virtual server configured with an HTTP profile expects to receive a body with a response, the BIG-IP system immediately sends response headers that are less than 16 KB in length, without waiting to receive the body.

F5 Product Development tracked this change as ID 455560.

Impact

None

Recommended Actions

If your application experiences delays due to this behavior in BIG-IP versions prior to 13.0.0, consider the following:

  • You can use iRules to pad the response headers and increase the header length to larger than 16 KB so that the BIG-IP system egresses the response headers without waiting for the body.
  • If delays occur when requesting specific URLs, you can disable the HTTP profile for those URLs using iRules; however, this approach may not be suitable for all applications and can cause problems for subsequent requests over Keep-Alive connections.
  • If the server response contains no body and does not indicate there is no body, configure the server to indicate a body length of 0 KB by including a Content-Length: 0 HTTP header in the response or through the use of chunking.
