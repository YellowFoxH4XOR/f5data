Description

Customer encountered the error messages, "Failover initialization failed: undefined" in the suggested 3 CFE troubleshooting steps;

 

1) Dry-run on standby:

curl -su admin: -X POST -d '{"action":"dry-run"}' http://localhost:8100/mgmt/shared/cloud-failover/trigger | jq .

{

 "message": "Failover initialization failed: undefined"

 

2) Inspect on one instance to validate cloud resources:

curl -su admin: http://localhost:8100/mgmt/shared/cloud-failover/inspect | jq .

{

 "message": "Failover initialization failed: undefined"

 

3) Reset the state file:

curl -su admin: -X POST -d '{"resetStateFile":true}' http://localhost:8100/mgmt/shared/cloud-failover/reset | jq .

{

 "message": "Failover initialization failed: undefined"

 

 

Environment

BIG-IP LTM VE 15.1.10

CFE 2.1.2 in AWS

 

Cause

In the case of the scopingName rather than scopingTags configuration in AWS, the Bucket Name should be the "Access point of the S3 bucket" as stated in the "Accessing a bucket through S3 access points".

 

Recommended Actions

We can see the referenced error message, "Failover initialization failed: undefined undefined" as well as "scopingName" value in the /var/log/restnoded/restnoded.log below.

Here is the problem.

Error: "Hostname/IP doesn't match certificate's altnames: \"Host: aws-xxxxx-cfe-state.xxxxxxxxxxxx.f5.prod.cloud.example.com.s3.amazonaws.com. is not in the cert's altnames: DNS:*.s3.amazonaws.com, DNS:s3.amazonaws.com\""

 

The following configuration isn't correct.

 

"externalStorage": {

"scopingName": "aws-xxxxx-cfe-state.xxxxxxxxxxxx.f5.prod.cloud.example.com",

The scopingName should be the "Access point" of the S3 bucket rather than the "Bucket" name.

The access point doesn't allow a 'dot' within the name, therefore, the subjectAltName will not complain.

The customer may create a bucket named "s3bucket-test" and S3 will assign an alias name as the following.

s3bucket-test-8mm5fqauwiqdp8mownq86rrjua9yrusw2a-s3alias

 

Then the customer may have a quick test on their BIG-IP to confirm it using curl command;

 

curl -s -I https://s3bucket-test-8mm5fqauwiqdp8mownq86rrjua9yrusw2a-s3alias.s3.amazonaws.com

 

It will respond with HTTP 301 with the "x-amz-bucket-region" header. (This header is what we need)

 

[admin@ip-10-0-10-11:Standby:In Sync] aws # curl -s -I https://sebucket-test-8mm5fqauwiqdp8mownq86rrjua9yrusw2a-s3alias.s3.amazonaws.com

HTTP/1.1 301 Moved Permanently

x-amz-bucket-region: us-west-2

x-amz-request-id: VQV1B0D65TY60XRQ

x-amz-id-2: 8FaxvAV76x2gez+Sw3jaAXhj5zq7Q63XfBHHcttkOD4Nf0KdozNy6xqll39hywVFPmgZ1dLffn2p08kB2G/d/NRVMcKWQLvW

Content-Type: application/xml

Transfer-Encoding: chunked

Date: Tue, 15 Oct 2024 09:13:34 GMT

As a conclusion, the customer needs to put the "alias" name (with or without the s3.amazonaws.com is OK) as the value of the scopingName.
