Known Issue

The primary blade on a VIPRION chassis may fail to use the floating cluster/management IP address as the source for management traffic.

This issue occurs when all of the following conditions are met:

  • The VIPRION chassis is configured with a floating cluster/management IP address and cluster member IP addresses.
  • The VIPRION chassis is rebooted.

This issue is the result of a race condition that occurs when the VIPRION system reconfigures the floating cluster/management IP address as the global management IP address for the primary blade after a reboot.

Impact

Your management traffic may come from an incorrect source IP address.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The VIPRION system fails to assign the floating cluster/management IP address as its global management IP address but instead incorrectly assigns it as its global secondary management IP address. To verify this behavior, you can type the cluster shell (clsh) utility ip addr ls mgmt command at the command line.

    The following command-line output example shows the system incorrectly assigning the floating cluster/management IP address 192.168.248.164 as the global secondary mgmt IP address instead of the global mgmt address:

    6: mgmt: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue
        link/ether 00:01:d7:c7:28:c0 brd ff:ff:ff:ff:ff:ff
        inet 192.168.248.167/24 brd 10.255.248.255 scope global mgmt
        inet 192.168.248.164/24 brd 10.255.248.255 scope global secondary mgmt
        inet6 fe80::201:d7ff:fec7:28c0/64 scope link
           valid_lft forever preferred_lft forever

    The correct behavior is for the system to assign the floating cluster/management IP address 192.168.248.164 as the global mgmt IP address.

  • You observe that management traffic is coming from an incorrect source IP address.
