K000151087: How to safely update a Load Balancer or origin pool in F5 Distributed Cloud without causing disruption

Published
2025-04-29
Updated

Applies to

  • F5 Distributed Cloud
Source

Description

Updating a Load Balancer or Origin Pool configuration within the F5 Distributed Cloud (F5 XC) environment can potentially lead to short-term disruptions. By default, when modifications (via API or GUI) are made directly to an existing origin pool or load balancer object, the previous instance of this object may be deleted immediately. This removal causes the upstream endpoint previously managed by that configuration to become temporarily inaccessible for approximately five minutes, which is the maximum time frame required for a new configuration to propagate across regional edge nodes and restore endpoint accessibility. Consequently, users may experience brief disruptions or errors such as no_healthy_upstream .

To mitigate this potential issue and ensure continuous availability during configuration updates, the following best-practice process is recommended.

Environment

  • F5® Distributed Cloud
  • HTTP Load Balancer

Cause

When a load balancer or origin pool is updated directly, F5 XC replaces the existing configuration immediately. If the new configuration has not yet fully propagated and passed health checks, this can result in unreachable endpoints.

Answer/Recommended Actions

To ensure a smooth, uninterrupted update process, follow the steps below:

Step 1: Create a new origin pool with the updated configuration

Instead of editing the existing origin pool, create a new one with your updated settings—this may include:

  • New IP addresses
  • Modified DNS names
  • Updated health probe settings

Ensure this new origin pool closely mirrors the old one, but with the required adjustments tailored to the new configuration .

Step 2: Associate the new origin pool with the Load Balancer (Set priority to 0)

  • Add the newly created origin pool to the existing load balancer but configure its traffic priority as zero.
  • This prevents it from handling traffic immediately, giving F5 XC adequate time for endpoint health evaluations.

Step 3: Wait for endpoint health validation across all REs

  • F5 XC will check the health of the new origin pool’s endpoints.
  • Effective endpoint validation can take up to 5 minutes, due to factors such as DNS resolution, health checks, and synchronization across regional edge sites.
  • It is critical to monitor the health of the new origin pool using the F5 XC dashboard or API to confirm that all endpoints are marked as healthy before proceeding 
  • Only continue once all endpoints are marked healthy.

Step 4: Change priorities to activate the new origin pool

After confirming endpoint health:

  • Set the new origin pool’s priority to 1 to start routing traffic.
  • Set the old origin pool’s priority to 0 to stop routing traffic to it.

This ensures a smooth cutover without user impact.

Step 5: Validate configuration propagation across REs

Allow up to 30 seconds for the updated configuration to fully propagate across all edge locations.

During this time, monitor the load balancer to:

  • Confirm traffic is being routed to the new origin pool
  • Check logs or metrics to ensure normal operation

Step 6: Delete the old origin pool

Once you’re confident the new origin pool is fully operational and traffic is stable:
Delete the old origin pool to keep your configuration clean and maintain best practices.

Additional Information

Following this step-by-step process helps you avoid downtime, ensures endpoint readiness, and prevents routing errors such as no_healthy_upstream .
