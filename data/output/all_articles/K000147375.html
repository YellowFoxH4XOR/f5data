Answer/Recommended Actions

Ensure you have completed the initial setup configured to direct traffic to the F5 Distributed Cloud.

Setup Guide: Web App Security & Performance

The F5 Distributed Cloud WAF Managed Services will use a combination of techniques and sources to determine if traffic is malicious. Below is a sample list of the recommended configurations to start with protecting your application:

 

IP Reputation

This feature enables you to allow or deny IP addresses based on a threat category or a threat score. The IP Reputation Service includes a database of known malicious IP addresses. This database is updated continuously.

Setup Guide: Configure IP Reputation Service

 

Fast Access Control Lists (ACLs)

Using the F5® Distributed Cloud Console Fast ACLs, you can block traffic from specific sources, or apply a rate limit to the traffic from a specific source. You can also enhance protection by filtering traffic based on source address, source port, destination address, destination port, and protocol.

Setup Guide: Configure Fast ACLs

 

WAF Policy Management

WAF consists of technology that enables you to allow or block requests and responses based on the configuration.

Protecting your applications using WAF requires you to create a "WAF object" in F5 Distributed Cloud Console (Console) and enable it by attaching it to an HTTP/HTTPS load balancer that serves the application for which you want to protect (with the WAF).

Setup Guide: Configure Web Application Firewall

 

Malicious User Detection and Mitigation

Enabling this feature includes enabling the detection of malicious activities and associated mitigation steps. The mitigation steps include issuing JavaScript Challenge or Captcha Challenge or temporary blocking of the user.

Setup Guide: Malicious Users

 

L7 DDoS Auto Mitigation

Advanced L7 DDoS detection and auto-mitigation are enabled by default on all existing and new HTTP load balancers to provide default protection for all customer origins against large-scale volumetric L7 DDoS attacks. Users will have the option to choose a different mitigation action.

Setup Guide: DDoS Protection

The configurations above can be configured at a default level, this will depend on the nature of your application and security expectations. These main settings control the conditions for denying/allowing requests.

 

Service Policies

Service Policy set consists of many Services Policies and each Service Policy is comprised of many Rules. These Policies have two main concepts:

  1. Server and Client - Server here is from the point of view of the policy. Server is a set of domains for which the policy is being written for. Client is a set that is consuming this service and at the other end of the connection. For example, server can be a domain in virtual host. Client can be set of ip address, a specific IP address, or a subnet/prefix, service name, or an arbitrary set.
  2. Rules - Rules are applied to all requests to the Server from the Client. In the case of TCP Proxy with SNI, only server domain and Client can be matched. In case of HTTP and HTTPS proxies - domain, path, query parameters and HTTP headers can be matched. Requests can be allowed or denied based on this match.

Setup Guide: Configure Service Policy

When configuring a Service Policy, please take into consideration the following:

  1. You can assign a maximum of 4 IP Prefix Sets per service Policy. (How many IP Prefix Sets can I have for one Service Policy? )
  2. If the Service Policy is applied at the load balancer (LB), ensure it is configured correctly to avoid unintentionally denying traffic. (Why does my Service policy deny traffic source from a pod to load balancer?

The configuration will also depend on the nature of your application, however, we provide you with the following examples of recommended Service Policies that might be beneficial for use:

IP Geolocation 

It is used to block geographical regions where your company has no business operations. It can also help you control who gets access to your web application and can choose to filter depending on a visitor's location.

Allow/Block specific path

It is used to allow or block a specific path in which you can control who gets access to your web application. Eg: In case you require specific IPs to access a restricted path, you will need to create two rules:

    1. Rule to add the allowlist IPs
    2. Rule to define the restricted path
