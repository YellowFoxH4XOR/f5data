Description

This article describes the solution for DIAMETER handshake failure

  • When BIGIP trying to establish DIAMETER channel, it resets the connection after DIAMETER peer replies with CEA, (Capabilities Exchange Answer)  to the CER (Capabilities Exchange Request) message that the BIGIP sent.
  • In ltm log, the following error appears on DIAMETER channel establishment:
01230140:3: RST sent from 192.168.1.10:54286 to 192.168.1.5:3869, [0x2bd8143:1154] diameter peer state machine error
  • In traffic capture, there is a TCP reset sent by the BIGIP right after it receives and acknowledging a DIAMETER CEA message:

Environment
  • BIGIP PEM
  • DIAMETER peer

Cause

This is caused due to 2 conditions:

  1. PEM's tmm.diameter.application.enforce.capability.exchange.avps value set to 'all' (default ): 
    sys db tmm.diameter.application.enforce.capability.exchange.avps {
    default-value "all" <<<
    scf-config "true"
    value "all" <<<
    value-range "all auth none vendor"
}
    Possible values are:
    none:    gx will be allowed regardless of the existence of vendor-specific-application-id or auth-application-id
    vendor: gx will be allowed only if vendor-specific-application-id exist
    auth:     gx will be allowed only if auth-application-id exist
    all:         gx will be allowed only if both vendor-specific-application-id and auth-application-id exist (DEFAULT)
     
  2. DIAMETER peer is not sending BOTH AVPs of:
    1. vendor-specific-application-id
    2. auth-application-id

Recommended Actions
Option 1:
Make sure that DIAMETER peer will send both AVPs (vendor-specific-application-id and auth-application-id)

Option 2:
Update tmm.diameter.application.enforce.capability.exchange.avps value to match the scenario (none / vendor / auth / all)
