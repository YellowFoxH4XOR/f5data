K000162831: Unexpected failover in Oracle Cloud Infrastructure

Type
Support Solution
Published
2026-08-07
Updated
2026-08-26
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.3
Source
https://my.f5.com/manage/s/article/K000162831

Description

During failover communication loss and recovery, a BIG-IP LTM traffic-group callback may continue processing after the traffic group has transitioned to Standby. This can leave the OCI active Self-IP associated with the wrong device.

Environment

  • Product: BIG-IP LTM
  • Deployment: High-availability pair in Oracle Cloud Infrastructure
  • Failover callback scripts:
    • tgactive
    • tgstandby
    • tgrefresh
  • The OCI integration uses traffic-group state changes to manage the active Self-IP state.

Cause

The tgactive callback can continue executing after the traffic group transitions to Standby when failover and failback occur in rapid succession. If the tgstandby and tgrefresh callbacks do not handle these transitions, the state may not be synchronized correctly. This can result in an active/active condition or leave the OCI active Self-IP associated with a device that is no longer the preferred Active peer.

Recommended Actions

  1. Obtain the validated tgstandby and tgrefresh callback scripts from F5 Support.
  2. Install the scripts in the /config/failover directory.
  3. Verify that the scripts contain the required F5-provided content.
  4. Test failover and failback behavior in a controlled maintenance window.
  5. Confirm that:
    1. The device entering Standby stops Active-state processing.
    2. The preferred Active device owns the traffic group after communication is restored.
    3. The OCI active Self-IP is associated with the correct device.
  6. Review the failover timeout and failover network stability separately. Increasing the timeout may reduce failovers caused by brief communication interruptions, but it does not replace the callback-state handling provided by tgstandby and tgrefresh.

Additional Information

  • A communication interruption can legitimately trigger failover. The unexpected behavior occurs when callback execution does not follow the subsequent Active/Standby state transition.
