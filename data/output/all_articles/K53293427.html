Description

Heap Overflows (CWE-122) are a sub-class of the Buffer Overflow vulnerability (see K69961311) that can affect applications written in many programming languages, and the name describes any situation in which the software attempts to move data from one location in memory into a fixed-length buffer allocated on the heap, which is too small to hold the data.

Environment

Any software application.

Cause

  • Insufficient bounds checking when working with user-supplied data.

Recommended Actions

Since buffer overflows can affect such a vast array of applications it is impossible to give one-size-fits-all advice beyond ensuring that your application applies good bounds-checking when working with any user-supplied input. If we talk about web applications, specifically, however, it may be possible to mitigate buffer overflow attacks against a web application or web server using BIG-IP Advanced WAF, Silverline WAF etc to enforce length checks against user-supplied input (in the form of HTTP parameters, URIs, and headers). Specific instructions are outside of the scope of this document since any policy must be tailored to the web application in question.
 
If you are concerned about a known buffer overflow vulnerability in the BIG-IP Configuration Utility the best mitigation is to ensure your administrators:
  • Access the Configuration Utility from a dedicated management host, jump box or another controlled environment

Additional Information

To explain the anatomy of a Heap Overflow, we must first explain (in brief) how common architectures handle memory management within processes and, specifically, how they manage the stack.

Imagine the memory space of a typical process looks something like this:

0xffff ffff +-------------+
            |    Stack    |
            +-------------+
            |      v      |
            |             |
            |     free    |
            |             |
            |      A      |
            +-------------+
            |    Heap     |
            +-------------+
            |    data     |
            +-------------+
            |             |
            |    Text     |
            |             |
0x0000 0000 +-------------+

At the bottom of this diagram, we have the lowest memory address associated with the process (and at the top, the highest). Reading top-down we have the stack space, which grows downward through unallocated space toward the heap, which grows upward toward the stack. Next comes data (which we can ignore for the purposes of this explanation) and finally text which, despite the name, contains the immutable application code.

Heap Overflows, as the name implies, deal entirely with variables allocated on the heap, and heap management is an extremely complex topic; notably, how the heap is managed will vary greatly depending on the operating system being targeted and/or the language the application is written in. You can consider most heaps, however, to be made up of a set of ‘blocks’, each block containing the data the application wishes to store along with some meta data about the heap block itself (for example it’s size, whether or not the block is in use or free, and pointers to the block before and after this one in memory). A typical example might look something like this:

0xffff ffff +-------------+
            |    data     |
            +-------------+
            |   BACKPTR   |
            +-------------+
            |   FWDPTR    |
            +-------------+
            |    SIZE     |
            +-------------+
...
0x0000 0000

The heap itself will be made up of repeating – not necessarily contiguous – blocks like the above, e.g.:

0xffff ffff
...
            +-------------+
            |    data2    |
            +-------------+
            |    SIZE     |
            +-------------+
            |   BACKPTR   |
            +-------------+
            |   FWDPTR    |
0xaaaa aaaa +-------------+
            |    data1    |
            +-------------+
            |    SIZE     |
            +-------------+
            |   BACKPTR   |
            +-------------+
            |   FWDPTR    |
            +-------------+
...
0x0000 0000

Since data fills upward in this example, if there is insufficient bounds checking when moving data into data1, the first thing we will overwrite is actually the meta-data for data2. 

This may not seem initially a problem but, when data2 is subsequently freed and the memory management functions attempt to return it to the heap as free memory, the meta-data will contain garbage or malicious information leading to, at best, unpredictable results. At worst, an attacker may be able to overwrite the meta-data with information that will lead to the memory management functions subsequently tampering with areas of memory not contained within the stack – in this way it is possible for an attacker to use a heap overflow to overwrite arbitrary areas of memory and inject malicious code.

As noted above, explaining the complete mechanism is difficult in a general sense as it will vary depending on how the memory allocation is performed in any given environment; the related content section at the foot of this article contains a number of links describing specific scenarios in more detail.

Affected Environments

As we have seen above, almost all applications, web servers, and environments are potentially susceptible to buffer overflows. The exception to this rule comes in the form of interpreted languages such as Python; here, it is not the application itself which may be susceptible but the underlying interpreter – i.e., Python code is considered safe, but this does not preclude the possibility of a buffer overflow vulnerability in the Python run-time itself as this was written in a lower-level programming language.

Examples

Consider the following simple stack overflow example C code:

#include <stdlib.h>
#include <stdio.h>
#include <string.h>

#define BUFSIZE 10
int main(int argc, char **argv) {
        char *buf;
        buf = (char *)malloc(sizeof(char)*BUFSIZE);
        gets(buf);
}

The above snippet of C code allocates a fixed-size buffer on the heap with a call to ‘malloc’ of 10*charwidth bytes (if we assume that a character is 1-byte wide then this will be a 10-byte buffer) and then copies from STDIN into ‘buf’ using the gets() function call without any bounds checking, allowing the user to move an arbitrary amount of data into the heap.

Given this example we are unlikely to experience a crash or any other negative consequences, but the heap chunk will suffer an overflow if we move more than 10 bytes into it. A crash or further exploitation would, in most cases, require a more realistic application which not only allocates but also deallocates further heap variables.

There are many protection mechanisms built into current compilers and processors to try and prevent this attack from working as outlined above such as non-executable memory space, stack canaries and other compiler-based automatic bounds checking, and address space layout randomisation which makes predicting the address you need to jump to much more difficult.
 
Mitigations
 
If you wish to protect an application against buffer overflows attacks and cannot use Advanced WAF or a similar product to enforce bounds checking on input then you should build this functionality into the application itself:
  • Ensure that all input is subject to sufficient bounds checking
  • Ensure that any memory copy related code is subject to sufficient bounds checking, and do not rely on earlier checks on the original input length
  • Ensure that any application is compiled with all available compiler protections, e.g., stack canaries, NX-bit, ASLR/PIE etc
OWASP has additional advice for this in their Buffer Overflow cheat-sheet.
