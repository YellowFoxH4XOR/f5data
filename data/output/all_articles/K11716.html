Known Issue

This is the result of a known issue. If the VIPRION system elects a new primary blade, management traffic sourced from the newly elected primary blade will not use the cluster management IP address as the source IP address. Instead, the blade’s own management IP address will be used. This behavior is incorrect as management traffic sourced from the primary blade should always use the cluster management IP address as the source IP address. This behavior may disrupt services that use the management interface such as SNMP, syslog, and authentication services such as Radius.

Note: For more information, refer to K10778: Overview of the VIPRION system management IP address selection for outgoing connections.

F5 Product Development tracked this issue as ID 247789 (formerly CR133361) and it was fixed in BIG-IP 11.2.0. For information about upgrading, refer to the BIG-IP LTM, ASM, or PSM release notes.

Workaround

You should account for this issue when configuring access lists on a firewall or router that the VIPRION system will traverse with its management traffic. Likewise, any application performing source IP address filtering (for example, an Active Directory server used by the VIPRION system for remote authentication) should also account for this issue.

Note: For remote syslog traffic, you can configure the VIPRION system to always use the cluster IP address as the source by setting the syslog local-ip setting. To do so, navigate to the System › Logs › Configuration › Remote Logging page in the Configuration utility or use the following tmsh command syntax:

tmsh modify sys syslog remote-servers add { serv1 { host <remote syslog> local-ip <cluster IP> } }

For more information about the tmsh syslog component, refer to the Traffic Management Shell (tmsh) Reference Guide. For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.
