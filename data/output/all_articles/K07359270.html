Topic

Abstract

If you’re like most network security professionals, selecting, implementing, and using a web application firewall (WAF) are not easy tasks. You must assess your security needs, the protection offered by various WAFs, and the ongoing administrative effort that some WAF features require from your engineers.

If you are new to WAFs, F5 suggests you start small and learn as you go. The features that are the easiest to implement provide good protection, and not all applications require maximum security. As you gain experience with your WAF, you can add more sophisticated features where necessary.

To help you get started and progress with a WAF, this article provides a continuum of security features—from good protection that’s easiest to implement to maximum protection that requires the most WAF skill—so that you can start defending against attacks today and advance your web application security as you learn to operate your WAF.

Description

Web application security is complicated

To protect one or more web applications and their data against attack, web application firewalls use a security policy. Security policies consist of features that control access to web applications.

A security policy must ensure all genuine users have access to the application and the right data while prohibiting access to unauthorized users and malicious activity. While it sounds simple, security policies provide a deep selection of security features, some of which require complex configuration, monitoring, and adjustment. Often, there is also a delicate balance between implementing the appropriate level of security based on an application’s exposure to threat (sensitivity) and the possible aftereffect of disrupting its performance and users’ access.

Meanwhile, every web application in your organization needs a security policy, whether the application is accessible to the public or only employees. This requirement can be light work or a heavy lift, depending on several factors, including the size of your organization, the number of applications, and the sensitivity of your applications and data.

Start small, but most of all, start

If you’re new to WAFs, the most important thing to know is that you can and should start using one, now! You get the bulk of your WAF’s protections from the subset of security features that are the easiest to use, so start by implementing those and use them to get acquainted with WAF technology. Since you make marginal gains in protection as you add more complex security features to a policy, when you are starting out, avoid using all your WAF’s capabilities, even if your applications contain sensitive data that require maximum security.

The more you use a WAF, the easier it gets

The good news is that the more experience you gain configuring and maintaining security policies, the better you become at operating your WAF. With practice, you eventually progress to implementing more complex security features and varying levels of protection across individual security policies for multiple applications.

You also learn that, across the continuum of application security, there is a correlation between an increased level of protection and an increased level of associated administrative effort. Once you are familiar with the implications of this trade-off, you’ll be able to assess the appropriate approach for each new application you want to use with your WAF, including the following considerations:

  • Is the level of application security commensurate to the level of threat?
  • Is the level of application security proportional to the value of the application and its data?
  • Is the level of administrative effort required justified by the threat-level, application, and data?

The BIG-IP ASM system is designed to help

The BIG-IP ASM system provides tools that can shorten your time to WAF proficiency and reduce the risk of disruption to your applications as you learn.

Policy Builder

When you use BIG-IP ASM Policy Builder in Automatic learning mode, the system identifies legitimate application usage and begins to build your security policy based on a statistical analysis of your traffic and the intended behavior of your application. You direct Policy Builder to create a security policy that is looser or tighter by specifying how the policy learns which entities to block and allow, including file types, parameters, URLs, cookies, and redirection domains.

At one end of the security spectrum, there is a “negative” security approach, which excludes, or denylists, entities that you specify from the application. The policy identifies which entities to block using wildcards (pattern matching) and relaxes a wildcard when false positives occur, resulting in a security policy that is looser, but easier to manage.

At the other end is a “positive” approach, which uses accept lists to identify the entities that can access the application. This technique eliminates wildcards in favor of comprehensive accept lists of allowed entities, resulting in a large, granular configuration that provides strict security but is more cumbersome to manage.

There are, of course, learning options in the middle of this spectrum that combine the two approaches.

In the final stage, Policy Builder further refines the security policy until it is stable and ready to enforce the requisite security features.

When you use automatic learning mode, it’s tempting to delegate ongoing maintenance of your security policy to Policy Builder, but there is a risk that it may incorrectly interpret and block genuine traffic. Therefore, you should monitor the suggestions it makes for any corrections. This process is a great way to start using and learning about your WAF.

If you are an administrator with more experience, you can build your own policy using Policy Builder in manual learning mode, which evaluates traffic and provides “tuning” suggestions—additional security features—which you review for inclusion in your policy.

For more information about Policy Builder, refer to the following articles:

  • K79575295: Creating a security policy automatically (13.x)

Blocking and Transparent enforcement modes

A security policy’s enforcement mode specifies whether the system simply logs traffic that triggers a security policy violation or blocks it. In Transparent enforcement mode, violations do not block traffic, but in Blocking mode, they do.

It’s common for administrators to only move applications from Transparent to Blocking enforcement mode after a period spent monitoring the system’s security violation data and gaining confidence in the accuracy of the policy. In this way, the BIG-IP ASM system helps administrators lower the risk of blocking genuine traffic that triggers false positives.

By providing visibility into security violation data, Transparent enforcement mode also alerts administrators to application attacks that would otherwise go unnoticed without a WAF. This improved awareness helps administrators understand the threat profile their application faces and make informed decisions to protect it.

For more information about enforcement modes, refer to K39522452: Configuring the security policy enforcement mode.

Progressing with application security using the BIG-IP ASM system

As you gain experience with the WAF capabilities you currently use, you can extend your skills and increase your network’s protection by adding more advanced options to security policies that need it. To help you progress, F5 grouped BIG-IP ASM security features into the following levels of application protection:

  • Good
  • Elevated
  • High
  • Maximum

Each grade on the continuum corresponds to an increase in the following:

  • Application sensitivity—The application’s exposure to threat.
  • Data protection—How valuable the application’s data is.
  • Administrative effort—The resources and expense required to maintain the application’s level of security.

Good protection 

For those who are new to WAFs, this category is a good place to start. These security features constitute a high-level security policy, providing good protection from untargeted attacks, which you can deploy with minimal administrative effort, time, and risk of disruption to your application.

Attack signatures

Attack signatures are rules or patterns that identify attacks on web applications. Because they provide broad protection against attacks, they are a fundamental technology employed by WAFs to detect malicious traffic.

The F5 threat research and intelligence team develops and maintains the attack signatures used in the BIG-IP ASM system and adds new signatures when new vulnerabilities are discovered.

The BIG-IP ASM system applies attack signatures to each HTTP request and response, and uses request normalization processing, a method for reversing the encoding schemes that hackers use to evade signature-based intrusion detection systems.

Using the BIG-IP ASM system, you can easily:

  • Add attack signatures to a new or existing security policy.
  • Select the attack signatures you need using the accuracy, severity, and system information provided for each one.
  • Assess the impact of attack signatures on an application during an initial staging period.
  • Monitor and evaluate violations in production using reporting that includes the contexts in which violations occur, details about possible attack types, and a rating for each violation.

Administrative effort required

  • Enable attack signatures for a new or existing policy.
  • Review reporting during staging to monitor and evaluate any false positives on new policies.
  • Automatically update your system and existing policies with the most current attack signatures.

For more information about attack signatures, refer to the following articles:

  • K82512024: Managing BIG-IP ASM Live Updates (14.1.x and later)
  • K8217: Managing BIG-IP ASM attack signatures (11.5.x - 14.0.x)
  • K62525205: All attack signature updates for BIG-IP ASM, Advanced WAF, F5 Essential App Protect, and NGINX App Protect

Transparent enforcement mode

You can learn how WAFs improve your security posture by deploying a basic security policy in Transparent enforcement mode and observing the interaction among the BIG-IP ASM system, your application, and security threats. In this mode, the system logs violations but doesn’t perform blocking; the system allows all requests to pass through to the application. In the resulting BIG-IP ASM reporting, you can find details about each security violation and the specific components of the application under attack.

Similarly, Transparent enforcement mode is helpful for most any project that requires security monitoring without enforcement and without impact to applications, including:

  • Testing the security features in new policies by monitoring reported security violations.
  • Deploying new versions of applications and monitoring reported security violations.
  • Detecting patterns of malicious activity, such as attacks originating from particular geographic locations or targeting particular areas of an application.
  • Improving your awareness of application layer attacks on security policies that warrant only base-level security.

You can collect this data for one or multiple applications, and because each security policy has its own enforcement mode setting, you can transition between Transparent and Blocking modes for each application, when you need to.

Administrative effort required

  • Enable the Transparent enforcement mode and the Alarm setting for the desired violations.
  • Regularly monitor reporting to review policy violation data.

IP Intelligence

Organizations are exposed to a variety of attacks from rapidly changing IP addresses. F5 IP Intelligence blocks and provides reporting about malicious IP addresses using a data feed from a subscription-based database.

Information from this service also provides more context for reviewing other BIG-IP ASM violation data and analyzing application layer access patterns.

Administrative effort required

  • License the IP Intelligence feature on the BIG-IP system.
  • Enable the feature and the Alarm setting on IP intelligence categories of interest.
  • Ensure access to the data feed.

For more information about IP Intelligence, refer to K13875: Managing IP reputations and the IP Address Intelligence database.

Geolocation

The BIG-IP ASM system has an IP geolocation feature that identifies the origin of traffic at the country-level using a database of IPv4 and IPv6 addresses.

In addition to helping you interpret violation incidents and trends, with this data, you can block or allow access to an application based on the geographic origin of the traffic (denylisting and acceptlisting, respectively.) If your organization wants to deny access to a particular country of origin, this feature makes it simple.

Administrative effort required

  • Determine a regular schedule for uploading updated geolocation data, especially when using denylisting.
  • Periodically review violation data to ensure the feature is operating correctly.

For more information about the IP geolocation feature, refer to K79414542: Configuring geolocation enforcement using BIG-IP ASM security policy.

Protocol compliance

A common attack vector is confusing web servers, web applications, and security products using malicious content hidden in HTTP requests that web servers and simple HTTP proxies often fail to detect. Many HTTP servers and proxies don’t strictly enforce protocol conformance. Instead, they focus on successfully processing the request while ignoring HTTP request attributes that aren’t compliant.

BIG-IP ASM protocol compliance checks perform strict and detailed HTTP validation, which surpasses that of typical proxies—including the HTTP profile in the BIG-IP Local Traffic Manager (LTM) system—and detect, log, or block non-compliant and malicious traffic. If any of the 19 protocol enforcement checks trigger false positives with your application, you can easily remove them using Policy Builder.

Administrative effort required

  • After a representative sample of traffic passes through a newly deployed security policy, review protocol compliance learning suggestions for false positives.
  • When the system reports a high number of violations, remove checks that are causing false positives using Policy Builder.

For more information about protocol compliance, refer to K10280: Overview of BIG-IP ASM HTTP protocol compliance.

Protection from evasion techniques

HTTP permits several character encoding schemes, and hackers often leverage these schemes for attacks. However, most network security devices rely only on simple string matching validation and the input validation features that come with applications for detection. Similarly, hackers exploit common character sequences to bypass string matching validation, such as using ../ to navigate to a parent directory of interest.

To reduce the risk of false positives, most security devices bypass checking for these evasion techniques, because they are used in legitimate requests and aren’t overtly illegal or non-complaint.

However, most applications need protection from evasion techniques. Like HTTP protocol compliance checks, in the BIG-IP ASM system, you can enable checks for them, monitor reporting, and then disable any checks that cause false positives, with little risk to application performance.

Administrative effort required

  • After a representative sample of application traffic passes through a new security policy, the system evaluates HTTP requests against evasion technique violations, and either automatically enables or suggests that the administrator enable this feature.

For more information about protection from evasion techniques, refer to K7929: Working with Evasion technique detected violations.

Protection from parameter exploits—denylisting

When examining an HTTP request, parameter values are one of the most important components for careful review. At the heart of many vulnerabilities associated with parameters are some common misconceptions about them, including that:

  • Only the server sets parameters—false!
  • They are limited to a subset of server-controlled values, such as choices in an HTML form—false!
  • Client-side JavaScript evaluates and enforces parameters, such as text input from an HTML form—false!

In fact, many exploits manipulate, modify, or embed malicious content in parameter values bound for web applications.

The BIG-IP ASM system offers multiple methods to protect against these threats, including denylisting. In this approach, when the system parses parameters—both those in URIs and POST payloads—it validates the values against signature and metacharacter policies to identify known exploit patterns. Should you encounter a false positive, Policy Builder adds that value to your security policy to prevent future violations, effectively slightly relaxing the default policy settings.

Administrative effort required

  • Enable signature detection in your security policy.

For more information about protection from parameter exploits, refer to K79544554: Configuring attack signatures for a parameter.

Threat campaigns

One of the biggest challenges you face in assessing the threat landscape is differentiating between an attack and a false positive.

You can effectively block malicious requests using a WAF and vulnerability signatures, which evaluate web requests and server responses for indications of known attacks. However, this approach also flags innocuous requests that include these signatures, thereby requiring you to determine whether your system is actually under attack.

Part of the problem is that you are working from a single point of data. When you have more information, you can tell more easily whether your system is compromised.

When you have Advanced WAF, you can subscribe to Threat Campaigns, which is a feed that provides a set of data to evaluate whether incoming requests are malicious. F5 developed and maintains Threat Campaigns using active research, honey pots, and other monitoring tools to understand how a cybercriminal or organization weaponized a vulnerability. Threat Campaigns also knows how vulnerabilities are being used, such as the payload of the attack, where the attack originates, various data elements—including specific headers—and even the shell code of the attack.

You can also rate limit, block, or even honey pot an incoming request without adversely impacting the normal operation and traffic of the underlying web application.

F5 releases Threat Campaign updates as needed. F5 may post updates several times a week as it discovers new threats. You can schedule your system to download Threat Campaigns at the same time you download attack signature updates.

The system also flags Threat Campaigns in request logs, validating the threat and the efficacy of the protection.

For example, consider the case of CVE-2017-5638, which is a vulnerability in the Apache Struts 2 Jakarta Multipart parser. When this vulnerability arrives with a particular string and a few other data points, and sends an echo kiss, Threat Campaigns can definitively identify it as an attack.

Though Threat Campaigns is a powerful tool, it is complimentary to attack signatures. For example, the request log for an occurrence of the CVE-2017-5638 vulnerability shows that it triggered both Threat Campaigns and any valid signatures.

Administrative effort required

  • Subscribe to the service.
  • The BIG-IP system checks for updates every eight hours. Choose how you would like to download updates:
    • Automatically (Real Time).
    • You select the days and times (Scheduled).
    • You install them manually (Disabled).

For more information about implementing Threat Campaigns, see K82512024: Managing BIG-IP ASM Live Updates (14.1.x and later).

Elevated protection 

The security features at this level provide more protection than those in the previous category, while still requiring minimal effort. They do, however, necessitate some additional care to ensure they don’t impact application performance.

Bot defense

There is a significant increase in the use of automated scripts or programs—commonly known as bots—for a variety of malicious purposes, such as:

  • Denying legitimate users access to applications.
  • Extracting site information in ways unintended by application owners.
  • Seeking application vulnerabilities for exploitation.

At the same time, there are benign bots, of which you may be completely unaware, that have long automated essential internet tasks, such as crawling sites for search engines. Industry sources estimate bots comprise 50 percent of all internet traffic, 30 percent of which are malicious.

Identifying and classifying benign and malicious bot traffic is a delicate process requiring several tools. The BIG-IP ASM system has a bot detection engine, which uses a combination of known bot signatures, JavaScript, CAPTCHA, and rate limiting to disrupt programmatic access to applications by bots.

Analyzing bot traffic provides benefits beyond blocking attacks. Distinguishing bots early in the request process reduces the number of BIG-IP ASM alarms and false positives, improving application performance. You also reduce the amount of traffic that the application server must process. Lastly, BIG-IP ASM bot data aids administrators in creating and maintaining security policies.

Administrative effort required

  • Enable the Bot Defense profile (DoS Protection profile in versions 12.x - 13.x) for the virtual server; it requires little ongoing interaction, other than ensuring the signature database is updated.
  • When signatures fail to classify bots, use other methods to challenge the requestor.

For more information about bot protection, refer to K42323285: Overview of the unified Bot Defense profile.

Web scraping protection

Web scraping is the programmatic extraction of information from a web application in a manner not intended by, and often contrary to the interest of the application owner. This type of attack requires targeted mitigation strategies, as web scraping is unlikely to trigger violations in other components of security policies.

Organizations that suspect or encounter web scraping often respond with heightened application layer security, including the use of CAPTCHA or request rate limiting, which can adversely impact user experience.

Using The BIG-IP ASM system, you typically detect web scraping using bot management capabilities in the Layer 7 (L7) DoS profile. To mitigate an attack, you iteratively configure, or tune, six different web scraping protection features—possibly to Alarm mode.

Administrative effort required

  • Configure and tune several security features in your security policy.

For more information about bot protection, refer to the following articles:

  • K42323285: Overview of the unified Bot Defense profile
  • K15405450: Overview of web scraping detection

L7 DoS attack protection

You need a capable WAF to block DoS attacks that employ an L7 attack vector, because the attacks are not entirely susceptible to L2, L3, and L4 mitigation approaches.

Meanwhile, attackers quickly respond to new L7 DoS protection measures by adjusting their methods.

To address these problems, the BIG-IP ASM system uses a comprehensive set of tools, which you can simultaneously enable to detect and avert L7 DoS attacks.

Administrative effort required

  • Start simply by trying bot signature and detection features.
  • If you need an application layer approach, provide the details necessary to configure and apply an L7 DoS profile for detection and mitigation.

For more information about L7 DoS protection, refer to the following articles:

  • K13410341: Overview of L7 DDoS attack protection (14.x - 17.x)
  • K29359407: Overview of L7 DDoS attack protection (12.x - 13.x)

Disallowed file types

You can block HTTP requests based on a file extension used in a URL, such as .jsp. Because most web applications use a limited set of file types, creating a list of legal and illegal file types in your security policy is a simple exercise that reduces the application attack surface with a minimal chance of false positives.

Enabling disallowed file types alongside other security features constitutes a layered approach that decreases the risk of malicious requests reaching your applications.

Administrative effort required

  • Configure the lists of allowed and disallowed file types in your security policy.
  • Update the list, as needed.

For more information about disallowed file types, refer to K69153854: Configuring the BIG-IP ASM system to deny requests for certain file types.

External logging

BIG-IP ASM logs are a valuable resource for reviewing security policy violation incidents.

At the same time, many organizations use a centralized security information and event management (SIEM) system for comprehensive logging of security events generated by all network and application security solutions. For these organizations, it’s critical that WAFs share event data to keep administrators apprised of incidents and possible attacks, and for long term log storage.

The BIG-IP ASM system has highly flexible logging capabilities, which you can configure to send detailed event data for each application to multiple locations, both local and external.

Administrative effort required

  • Define logging profiles for each intended destination, such as a SIEM platform.
  • Carefully ensure the proper logging profile is enabled on each application.

CSRF protection

When an application has cross-site request forgery (CSRF) vulnerabilities, its authenticated users are exposed to fraudulent actions that can have serious consequences, such as money transfers, password changes, and unauthorized product purchases.

Fixing applications exposed to these attacks can require significant effort by developers. However, WAFs enable you to respond rapidly without application changes. With the BIG-IP ASM system, you can quickly protect applications using virtual patching until CSRF vulnerabilities can be fully addressed in application code.

Administrative effort required

  • Obtain the specific URLs that have vulnerabilities and add them to the URL list when configuring the CSRF protection feature.
  • Ensure the application functions properly after enabling the CSRF protection feature in your security policy.

For more information about CSRF, refer to K11930: Overview of the ASM CSRF protection feature.

HTTP redirection protection

An "open redirect" attack occurs when hackers discover an application vulnerability and use it to defraud users by surreptitiously redirecting them to another site. For example, attackers redirect users to a forged page on a site that deceptively appears like the one they just left. There, users are required to enter their credentials, which hackers then steal.

These vulnerabilities are generally the result of faulty application coding, which developers must address upon discovery.

However, in the BIG-IP ASM system, you can build an accept list of approved domains to which an application can redirect users. Then, should you experience an open redirect attack, the BIG-IP ASM system detects and blocks redirects to unauthorized sites. This feature is an additional layer of protection and may also catch new variants of redirect exploits that can’t be detected by application-oriented security.

Administrative effort required

  • In organizations that do not expect redirects to any external domains, replace the default setting, which allows redirects to any domain, with your own domain, such as F5.com and all subdomains.

Or,

  • In organizations with a finite number of domains, for example only subsidiaries and affiliated businesses, replace the default setting with those domains and subdomains.

Or,

  • In any organization, let BIG-IP ASM Policy Builder learn and suggest the best configuration for redirect domains.

For more information about HTTP redirection protection, refer to K04211103: Configuring HTTP redirection protection.

Cookie tampering protection

Cookies provide critical functions for web applications, including state persistence and identifying users. When developers utilize cookies to store data used by applications, they sometimes overlook including input validation to prevent tampering with that data.

In these cases, attackers misuse cookies and their values for the following purposes:

  • Storing and submitting values that influence application behavior
  • Manipulating cookie values
  • Introducing new cookies
  • Introducing application vulnerabilities
  • Hijacking user sessions

Cookies arrive in HTTP requests in cookie headers, which WAFs scan for string violations. However, only sophisticated WAFs provide extended cookie protection capabilities.

The BIG-IP ASM system employs two additional features to inhibit cookie tampering. The system can “enforce” cookies, which means it can detect when attackers manipulate values set by the server, and then optionally block the corresponding requests. You typically apply this feature to cookies that contain sensitive data and influence application behavior.

Also, when examining requests, the BIG-IP ASM system can reference a accept list of “allowed” cookies that are legitimate for the application. The system detects and optionally blocks cookies that aren’t in the accept list. This is not a frequently used feature, but it’s particularly helpful for internal applications with singular security requirements and concerns about cookies.

Administrative effort required

  • Before enforcing cookies, enable the system to automatically build a list of candidates by detecting cookies that the server sets and return unmodified by clients.

Or,

  • Before enforcing cookies, get a list of candidate cookies from your application development team, by completing a penetration test, or from an application security audit.
  • Provide the system with a accept list of allowed cookies (the BIG-IP ASM system does not automatically create it) and remove the default wildcard setting for allowed cookies.

For more information about cookie tampering protection, refer to K57420543: Configuring cookie tampering protection.

High protection 

For this level of protection, you tailor your security policy to protect your application from targeted attacks, such as using login pages that reinforce security.

Allowed URL list

Web applications are comprised of large numbers of objects with their own, unique URLs. These URLs can change rarely or very frequently, depending on how often an application is updated.

At the same time, there are also unpublished URLs, accessed by those who maintain applications, that are not intended to receive traffic from ordinary users. These URLs can pose a significant risk when hackers scan for or guess them.

To counter this threat, basic WAFs and proxy servers rely on a denylist of these and other “disallowed” URLs, and use other negative security measures, like attack signatures.

With the BIG-IP ASM system, you have the option to use a considerably more comprehensive approach: limiting user access to only a accept list of “allowed” URLs, or those URLs that the application’s developers expect ordinary users to use. There are two types of allowed URLs: explicit and wildcard. An explicit URL represents one file, such as /login.jsp, while a wildcard URL allows URLs that match a string pattern, such as /products/*.

The BIG-IP ASM system can use allowed URLs because it has the capacity to automatically learn an exhaustive accept list of them, even when an application has hundreds or thousands of allowed URLs. With this approach, when an attacker tries to access a URL that isn’t allowed, the security policy can be configured to block the request. Note that to enable this feature, you must remove the stand-alone wildcard entity (*) from the Allowed URL list, which otherwise allows access to any URL.

Before enabling Blocking mode for this feature, it’s essential that you include a validation period during which you test your configuration. Use Transparent enforcement mode—or for those who must remain in Blocking mode, disable the blocking of illegal URLs—and monitor your security policy for false positives.

Administrative effort required

  • Depending on which capabilities you want to use, do one or more of the following:
    • Provide the system with a deny list of disallowed explicit URLs, which you create.
    • Provide the system with a accept list of allowed URLs, which you create (explicit and/or wildcard) and remove the wildcard entity (*) from the Allowed URL list, if Policy Builder hasn’t already done so automatically.
    • Enable the system to automatically learn an accept list of allowed URLs (explicit and/or wildcard).
  • Before enabling Blocking mode on these features, validate your configuration for a period of time by monitoring your security policy for false positives in Transparent enforcement mode.
  • For significant application or content updates, transition back to Transparent enforcement mode and monitor for false positives from new URLs, so that you don’t block legitimate access to the application.

For more information about allowed URL lists, refer to K29418033: Configuring allowed or disallowed URL lists.

User session tracking

Typical user interactions with an application span many independent HTTP requests. Because HTTP is a stateless protocol, servers don’t retain information about browsers beyond the duration of each HTTP transaction. However, you can use a WAF to track all application traffic during a user session, allowing you to perform user validation and gather insights about users.

You don’t typically get session tracking from a basic WAF. These features require session tables and other data structures that consume WAF memory. For this reason, most WAFs don’t offer session state, instead operating on a request-by-request basis.

However, the BIG-IP ASM system employs very sophisticated methods for associating HTTP requests with the appropriate sessions, including the use of HTTP cookies and browser fingerprinting to create unique device IDs for a client's session. This is because the BIG-IP ASM system uses session tracking for the following purposes:

  • As a prerequisite for enforcing certain security policy violations, such as attempting to bypass a login page or execute a brute force attack against a login page
  • To improve violation log reporting by including application user name and a session ID, which identifies violations that occur during the same user session
  • To provide additional enforcement capabilities for sessions that produce violations, including more aggressive blocking and deferred blocking, which enables you to delay blocking users until a session produces multiple violations

Administrative effort required

  • Enable session tracking in your security policy.
  • Configure additional features required for your application, such as customized blocking, login page enforcement, and brute force login protection.
  • If you have a newer version of the BIG-IP ASM system, add your login pages to your security policy, which activates an automatic association between application user names and user sessions, and includes that data in violations logs.

For more information about user session tracking, refer to K02212345: Configuring user session tracking.

DataSafe

DataSafe protects data before users send it from their browser. This feature targets malware and credential theft that steals in-browser data, which is data that users enter into form input fields when they're interacting with a web application, such as a financial website. These types of attacks target passwords, account numbers, credit card numbers, social security numbers, and other valuable personal data.

Thieves use several kinds of attacks to steal this data, including keyboard logging programs (malware), POST data grabs, and adding fake input fields to returned webpages.

DataSafe uses several methods to counter these attacks, including:

  • Protecting the data users enter into form fields, using encryption, substitution, or obfuscation
  • Encrypting data in real-time, as you type it
  • Obfuscating input form field names
  • Blocking attackers from entering stolen credentials
  • Adding decoy input form fields, which confuses malware by adding and removing fields with varying names from a form

If you have Advanced WAF, you have the DataSafe feature. You don’t have to install it on clients; you enable it on the BIG-IP system.

Administrative effort required

  • Provision Fraud Protection Service (FPS) for BIG-IP DataSafe.
  • Create a BIG-IP DataSafe profile.
  • Create a virtual server.
  • Associate the profile with that virtual server.

For more information about implementing DataSafe, refer to Adding BIG-IP DataSafe to the BIG-IP System in BIG-IP DataSafe Configuration.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Session hijacking protection

In this type of attack, hackers hijack authenticated user sessions to perform transactions and access data under the guise of genuine users. They typically hijack sessions by obtaining the value of a session cookie using one of the following methods:

  • Using malware installed on users’ systems
  • Intercepting a cookie during transit that is passed in cleartext
  • Exploiting a weak, compromised, or otherwise unsecured encrypted path
  • Intercepting a cookie due to user error

The BIG-IP ASM system uses browser fingerprinting to defend against session hijacking. This technology enables the system to create a device ID, which it associates with a session and then stores for user session tracking.

When suspicious activity occurs, such as a new session or source IP address change during a session, the system can revalidate the fingerprint. In the event the BIG-IP ASM system receives requests for a new session with an inconsistent device ID, it can report or block the activity.

Particularly sensitive web applications sometimes obtain and store browser fingerprinting data when you log in for use in detecting these attacks. However, most WAFs and web applications outside of the banking and financial sector do not use browser fingerprinting at all.

Nevertheless, with the BIG-IP ASM system, you can readily enable this advanced technology to protect even common web applications against session hijacking and other attacks.

Administrative effort required

  • Enable session awareness in your security policy.
  • Enable session hijacking protection.
  • Before enabling Blocking mode, validate your configuration for a period of time by monitoring your security policy for false positives while the policy is in Transparent enforcement mode.

For more information about session hijacking protection, refer to K40120684: Configuring session hijacking protection.

Brute force attack protection

There is more than one kind of brute force attack. In the classic version, hackers attempt to log in to an application by repeatedly guessing users’ account credentials. Because of these attacks, most applications now lock an account when it encounters multiple unsuccessful authentication attempts, at least temporarily. However, this strategy only protects against attack on a single account.

In another version of this attack, commonly called “credential stuffing,” hackers make only one attempt to log in to users’ accounts. They obtain a collection of user name and password combinations from a compromised application and programmatically evaluate them against their target application, looking for accounts where users reused their compromised credentials. When they finish, the hackers know those accounts for which they have valid credentials on the target application.

Because hackers continually change their brute force attack strategies in response to detection and mitigation technology, the BIG-IP ASM team closely monitors these attacks and adds new protections, including significant upgrades in BIG-IP 13.x. The BIG-IP ASM system now detects these attacks based on:

  • User names that have multiple failed login attempts
  • User device IDs, captured through browser fingerprinting
  • User IP addresses

Administrative effort required

  • Add all login URLs to your security policy, using a minimum of one URL. In recent BIG-IP ASM releases, Policy Builder learns login pages automatically.
  • Enable brute force protection using the default settings or by creating a custom configuration.

    Important: The default settings use CAPTCHA pages that are displayed in both Transparent and Blocking enforcement modes.

  • Validate your configuration for a period of time by monitoring brute force event logs and attack data for false positives triggered by genuine traffic.
  • In the event of an attack, use the numerous capabilities in the BIG-IP ASM system to better understand the detected attack traffic.

For more information about brute force attack protection, refer to the following articles:

  • K18650749: Configuring brute force attack protection (13.1.0 and later)
  • K54335130: Configuring brute force attack protection (12.1.2 - 13.0.x)

Blocking mode override

Some types of specialized application testing and troubleshooting require unencumbered access to applications, including:

  • Testing a new revision
  • Penetration testing
  • Using automated scanning tools to identify and resolve vulnerabilities detected by the BIG-IP ASM system

The BIG-IP ASM system identifies this legitimate test traffic by a specific, unique hostname in the host header and then allows this traffic to bypass Blocking and be handled by Transparent enforcement mode. Continuing to validate this traffic in Transparent enforcement mode assists administrators by informing policy tuning and learning processes.

This feature marks a great improvement over traditional, riskier bypass and customization approaches.

That said, you must protect the hostname to ensure that malicious traffic from adversarial sources cannot exploit the Blocking enforcement override. Some strategies include:

  • Maintaining secrecy around the hostname
  • Ensuring regular rotation of the hostname
  • Restricting access to the hostname with an accept list set of IP addresses or subnets using controls in local traffic policies or iRules

Administrative effort required

  • Add explicitly defined override host headers for Transparent enforcement mode.
  • Configure hostnames for this feature and then enable the Override option.
  • Take measures to secure and restrict access to the hostnames.

For more information about Blocking mode override, refer to K67438310: Configuring BIG-IP ASM to operate in Transparent mode for certain host names.

Behavioral DDoS

The Behavioral DDoS feature mitigates DDoS attacks by analyzing traffic behavior and using machine learning and data analysis.

Working with other BIG-IP DDoS protections, Behavioral DDoS examines traffic flowing between clients and application servers to automatically establish the baseline traffic flow profiles for Layers 7 (HTTP), 3, and 4.

Using a customer feedback loop, Behavioral DDoS continuously monitors server health, loading, attacks, and mitigations. Any anomalies are put on watch, and the system applies mitigation as needed, such as slowing down a client, a CAPTCHA request, or blocking the request.

When a DDoS attack occurs and the server suddenly receives many requests all at once, Behavioral DoS slows traffic the least amount necessary to keep the server from slowing or crashing.

In summary, Behavioral DDoS works by doing the following:

  • Learns typical behavior of normal traffic
  • Detects an attack based on current conditions (server health)
  • Finds a behavior anomaly (what and who changed to cause congestion)
  • Mitigates by slowing down suspicious clients
  • Improves with experience

Administrative effort required

  • Enable and configure Behavioral DDoS in the Stress-based Detection section of a DoS protection profile.
  • Set the level of mitigation you want, ranging from No Mitigation (learning only) to Aggressive Protection (proactively performs all protection actions).

For more information about implementing Behavioral DDoS protection, see Preventing DoS Attacks on Applications in BIG-IP Application Security Manager: Implementations.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Maximum protection 

Maximum application protection from the BIG-IP ASM system uses specialized techniques that are designed to prevent advanced attacks.

Data Guard

The prevailing approach to network and application security is blocking malicious traffic in the inbound direction before it can reach its intended target. However, it may not be possible to detect every inbound attack, and there is also problematic outbound traffic. For example, when attackers place sensitive data in ordinary files on web servers for exfiltration, they bypass traditional detection because there is nothing suspicious about the request for the file.

The BIG-IP ASM system provides outbound protection using its Data Guard feature, which examines outbound traffic for patterns that match common sensitive data types, such as social security and credit card numbers, and then masks the data or blocks responses containing the data.

For applications that store sensitive data elsewhere in their infrastructure, Data Guard provides an additional layer of protection.

Data Guard is designed for customers who have unique concerns about leaking sensitive data and requires consideration before implementation. For example, because the BIG-IP ASM system doesn’t treat the data masking function as a blocking response, it works in Blocking and Transparent enforcement modes. Therefore, when you enable Data Guard in an inappropriate context, data masking can trigger false positives and application disruption.

Administrative effort required

  • Enable and configure in your security policy, bearing in mind that the default configuration masks data that matches credit card and US social security numbers.

For more information about Data Guard, refer to K34154012: Configuring Data Guard exception patterns (12.x - 17.x).

DAST integration

Many organizations identify application security vulnerabilities using automated, dynamic application scanning tools (DAST) and services from providers like WhiteHat Security, HP, ImmuniWeb, Qualys, Quotium, and Trustwave. Typically, security testing teams manually triage the output from these tools and assign high risk vulnerabilities to application development teams for resolution.

Common WAFs can detect and redress most vulnerabilities detected by a DAST. Nevertheless, the BIG-IP ASM system provides support for automated, closed-loop remediation of many vulnerabilities identified by these tools. When you use this feature, the system automatically customizes your security policy to resolve the vulnerability, or if it cannot, the system reports the liability so the administrator can do so.

Administrative effort required

  • Export the DAST results in a format compliant with the BIG-IP ASM system and then upload the results into the system.
  • Review the upload results.

Protection from parameter exploits—acceptlisting

As stated previously, many exploits manipulate, modify, or embed malicious content in parameter values bound for web applications. To increase restrictions on parameter values beyond a denylist of signature and metacharacter checks, you can use acceptlisting.

In this approach, the BIG-IP ASM system automatically builds a comprehensive list of explicit parameters used by the application and then “tightens” them by applying individual constraints to each one, such as the maximum length and data type for its value. These constraints can be automatically or manually added to the policy.

At the end of this “learning” process, you can prevent the application from using any parameter that hasn’t been specified, thereby restricting it from accepting requests with new parameters. However, in most cases this practice is not recommended, as it makes the policy especially sensitive to application changes and therefore requires greater administrative effort. Additionally, the incremental benefit associated with a strict accept list is insignificant.

You get the greatest benefit by using elements of both approaches: signature and metacharacter checks, and customized constraints on parameters added to the policy.

Additionally, parameters set by the server are particularly sensitive and often targets for hacking. To protect these, the BIG-IP ASM system first observes the parameter value being set by the server, and then it requires that it receives the same value from the user that was set by the server.

Administrative effort required

  • Enable signature detection in your security policy.
  • Enable Policy Builder to automatically identify parameters and apply them to your policy.

Allowed HTTP request methods

The default settings for the BIG-IP ASM system security policies allow application requests to use the following HTTP methods:

  • GET
  • POST
  • HEAD, which the system changes to GET

Requests that use other methods, such as OPTIONS, DELETE, and TRACE, trigger a violation. Since most web applications exclusively use the GET and POST methods, allowing only these two can significantly reduce your security risk.

You can "relax" the policy while you are evaluating it in Transparent enforcement mode to permit other HTTP methods that the application can use.

In recent releases of the BIG-IP ASM system, you can override the default allowed methods in the following special cases:

  • You can allow an additional method on URLs that require the use of a method other than GET or POST.
  • You can remove POST on URLs that should only receive GET requests.

These customizations allow you to tune your policy to your application’s specific requirements, thereby tightening security for it.

Administrative effort required

  • Define and refine your allowed HTTP methods list in your security policy.

Conclusion

A security policy must ensure all genuine users have access to the application and the right data while prohibiting access to unauthorized users and malicious activity. You must strike the right balance to implement the appropriate level of security based on an application’s attack surface.

F5’s advice: when you are new to web application security, start small. Create a plan (even simply identifying your top ten risks), take advantage of tools to ease the process (Policy Builder and enforcement modes), and choose the security features that best match your threats, administrative resources, and experience with a WAF.

Most importantly of all, start.
