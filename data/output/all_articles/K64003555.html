Introduction

SSL Orchestrator provides an all-in-one solution that supports policy-based management and steering of SSL/TLS encrypted traffic flows to existing security devices and centralizes the SSL decrypt/encrypt functions across the entire security infrastructure.

This chapter provides an overview of the compatibility issues specific to the SSL Orchestrator configuration as well as its high availability (HA) configuration that you should consider when planning for an update or upgrade.

Prerequisites

You must meet the following prerequisites to use this procedure:

  1. You have administrative access to the SSL Orchestrator systems.
  2. Your SSL Orchestrator system is running version 15.1.x-7.x or later.

Update or upgrade SSL Orchestrator

Before you upgrade, ensure the following:

  • Refer to K13845: Overview of supported BIG-IP upgrade paths and an upgrade planning reference for the supported upgrade paths.
  • When upgrading SSL Orchestrator systems in an HA configuration, you must upgrade systems in the HA pair together. Do not upgrade only one.

Pre-upgrade checklist

You should perform the following steps on your SSL Orchestrator systems in an HA configuration or standalone setup:

  • Verify SSL Orchestrator configuration readiness
  • Perform a UCS backup of all SSL Orchestrator systems
  • Verify HA state readiness

Verify SSL Orchestrator configuration readiness

SSL Orchestrator configuration is stored in an iAppLX block, which has a state value maintained by the BIG-IP system. You must verify that all deployed iAppLX applications have a state of UNBOUND. The UNBOUND state indicates that the configuration is stable with no reconfiguration pending and that no errors have occurred. To verify the state of all deployed iAppLX applications, perform the following steps:

  1. Log in to the Configuration utility.
  2. Go to iApps > Application Services > Applications LX.
  3. Observe the Status of the deployed iAppLX applications and note the following meanings:
    • Green dot indicates a BOUND state.
    • Circling dot indicates a BINDING state.
    • Red dot indicates an ERROR state.
    • Gray dot indicates an UNBOUND state.

      Note: Other iApps use this status to indicate UNDEPLOYED, an inactive status. SSL Orchestrator uses it as a nominal status.

    • Gray dot and iAppLX application starting with sslo_ob indicate a PENDING state.
  4. If any of the SSL Orchestrator-related iAppLX application is in the BOUND, BINDING, PENDING, or ERROR state, you must resolve the error prior to upgrading.

Perform a UCS backup of all SSL Orchestrator systems

After you verify that the SSL Orchestrator configuration is ready, perform a UCS backup of all SSL Orchestrator systems. For more information, refer to K13132: Backing up and restoring BIG-IP configuration files with a UCS archive.

Verify HA state readiness

If you are upgrading to 16.0.x-8.x and later, you should verify the status of the HA between peers and resolve any HA issues prior to performing the upgrade.

  • Check for a good gossip HA state. To do so, perform the steps in the Verifying gossip is working between the high availability device pair before installing the ISO section of the Setting up F5 Guided Configuration for SSL Orchestrator in High Availability chapter of the F5 Guided Configuration for SSL Orchestrator: Setup 16.0.x manual.
  • Use the ha-sync utility to resolve gossip or MCP HA problems. For information about the ha-sync utility, refer to the F5 Guided Configuration for SSL Orchestrator: High Availability Diagnostics and Sync-Repair Tool manual.
  • Ensure that the device group that includes both HA devices is the Sync-Failover group type and Manual with Incremental Sync sync type.
  • Ensure that the port lockdown setting for the self IP address of the HA VLAN for both devices is either Allow All or All Default. Both devices must be able to reach each other over the self IP address of the HA VLAN.
  • Ensure the NTP and DNS settings for each HA device are identical.

Upgrade procedure

Upgrade from 15.1.x-7.x

Starting from SSL Orchestrator 15.1.x-7.x, to upgrade, you must perform the following high-level steps in sequence:

  1. Manually remove references to SSLO MCP objects
  2. Upgrade the underlying BIG-IP software and boot to the newly upgraded software volume
  3. Verify the gossip protocol is working between the HA devices
  4. Verify log files related to the upgrade and HA status
  5. Update the SSL Orchestrator software and configuration

Important: You must not go to the SSL Orchestrator > Configuration page at any point during the upgrade process until the final step of updating the SSL Orchestrator software and configuration. Going to that page before then causes SSL Orchestrator to perform some configuration modification and may result in a failed upgrade.

1. Manually remove references to SSLO MCP objects

When upgrading to SSL Orchestrator 16.1.x-9.x, these versions contain stability improvements to the control plane, including a transition to the standard BIG-IP centralized management infrastructure (CMI) architecture for HA synchronization. This requires substantial reconfiguration that is handled automatically during the upgrade, with one exception. SSL Orchestrator creates MCP objects as part of the deployment process with names beginning with sslo. These sslo MCP objects can be referenced by other MCP objects outside of SSL Orchestrator; for example, attaching an sslo SSL profile to a standard LTM virtual server. Prior to an upgrade to SSL Orchestrator 16.1.x-9.x, you must manually remove all references to these sslo MCP objects from non-sslo BIG-IP configuration objects regardless of the HA status. This step is critical to ensure the configuration is deployed correctly after the SSL Orchestrator 16.1.x-9.x or 17.0.x-10.x upgrade. Failure to do so will result in an upgrade failure. To recover from the upgrade failure, you must reboot SSL Orchestrator to its previous version prior to the upgrade and remove all references of the sslo MCP objects from non-sslo BIG-IP configuration objects. After you have removed these references, you should then re-attempt to upgrade the SSL Orchestrator system to 16.1.x-9.x or 17.0.x-10.x.

The upgrade failure may produce an error message similar to the following example:

Unable to complete the cleanup. You must resolve the error (if any), delete the iApp blocks in error state (if any) from the iApps menu on the left hand side and perform CMI sync. Then resume the upgrade process: click Upgrade. : transaction failed:01070294:3: The profile (/Common/sslo-default-http) is a parent of one or more profiles, can't delete.

2. Upgrade the underlying BIG-IP software and boot to the newly upgraded software volume

Unlike earlier SSL Orchestrator versions, upgrading from SSL Orchestrator 15.1.x-7.x to later versions does not require you to remove the HA configuration prior to upgrading. If you are upgrading a pair of HA devices, ensure that you perform the following high-level steps:

  1. Perform the upgrade on the standby device.
  2. Force the standby device offline.
  3. Restart the forced-offline device and boot to the newly upgraded software volume.
  4. Perform the upgrade on the active device.
  5. Restart the active device and boot to the newly upgraded software volume.
  6. Release the forced-offline device and reactivate it to standby.

Refer to the following upgrade guides applicable to your environment to perform the upgrade:

  • Chapter 5: Update or upgrade a standalone BIG-IP VE system using the Configuration utility
  • Chapter 6: Update or upgrade a standalone BIG-IP VE system using the TMOS Shell
  • Chapter 7: Update or upgrade BIG-IP HA systems using the Configuration utility
  • Chapter 8: Update or upgrade BIG-IP HA systems using the TMOS shell
  • Chapter 9: Update or upgrade BIG-IP systems using BIG-IQ

3. Verify the gossip protocol is working between the HA devices

When both devices have booted to the newly upgraded software volume, you should verify that the gossip protocol is working between the HA device pair. To do so, perform the following procedure on both HA devices for comparison:

Note: In SSL Orchestrator 15.1.x-7.x and 16.0.x-8.x, the system automatically tests the gossip status by itself all the time. You should perform this procedure if the system reports an error. Otherwise, this procedure is optional for these SSL Orchestrator versions.

  1. Log in as the root user to the command line of the SSL Orchestrator device.
  2. Verify the status of the gossip protocol by entering the following command:

    restcurl -u admin: shared/gossip | grep status

    The status should report as ACTIVE.

  3. Verify the HA devices list by entering the following command:

    restcurl -u admin: tm/cm/device

    Both devices should report the same list of devices.

  4. Verify the ConfigSync IP address of each device by entering the following command:

    restcurl -u admin: tm/cm/device | jq '.items[] | {devicename: .name, ConfigSyncIP: .configsyncIp, UnicastAddress: .unicastAddress}'

    • Verify that the configsyncIp attribute for each device listed matches the self IP address of the HA VLAN of each corresponding device.
    • Verify both the management IP and the configsyncIp attribute are entries in the unicastAddress attribute.
  5. Verify the list of HA devices participating in the gossip protocol by entering the following command:

    restcurl -u admin: shared/resolver/device-groups/tm-shared-all-big-ips/devices

    • Verify both HA devices are in the list.
    • Verify the address attribute matches the corresponding HA device configsyncIp attribute obtained from earlier steps. Alternatively, you can use the following command to directly obtain the address attribute:

      restcurl -u admin: shared/resolver/device-groups/tm-shared-all-big-ips/devices | jq '.items[] | {Address: .address}'

  6. Verify the failover state of the HA devices by entering the following command:

    restcurl -u admin: tm/shared/bigip-failover-state

    • Verify the failoverState attribute is reported correctly for each HA device: active for the active device and standby for the standby device.
    • Verify that the networkFailoverDeviceGroup attribute matches their corresponding device group.

4. Verify log files related to the upgrade and HA status

You should verify the following:

Note: You should not check on the SSL Orchestrator configuration until you have performed the following verification.

  • Check /var/log/liveinstall.log on both HA devices for errors and ensure the ISO upgrade is successful.
  • Check that the services on both HA devices are functioning properly using the bigstart status command.
  • Check the /var/log/ltm on both HA devices for any sign of configuration load errors.
  • Check the BIG-IP configuration is in sync between the HA devices. If the Configuration utility or TMOS Shell (tmsh) reports Changes Pending status, ensure you perform a manual configuration synchronization (ConfigSync) between the HA devices.

5. Update the SSL Orchestrator software and configuration

After you have completed the verification, you can now check on the SSL Orchestrator configuration. To do so, perform the following procedure:

  1. Log in to the Configuration utility of the active SSL Orchestrator device.
  2. Go to SSL Orchestrator > Configuration. Doing so starts the SSL Orchestrator rpm upgrade automatically on the current device.
  3. Perform step 2 on the other HA peer device.

    When the SSL Orchestrator rpm upgrade completes on both devices, both devices automatically start the SSL Orchestrator configuration upgrade. The duration of this process depends on the number of configuration objects deployed. You must wait for the entire process to complete.

    The process is complete when the Configuration utility reports the HA status as Changes Pending and the system removes the SSL Orchestrator upgrade status message.

  4. Go to iApps > Application Services > Applications LX. Wait for all SSL Orchestrator apps change to the BINDING (grey dot) state.
  5. Perform a manual ConfigSync to synchronize the configuration between the HA devices. To do so, perform the following steps:
    1. Go to Device Management > Overview.
    2. Ensure the active device is selected in the Devices list and Push the selected device configuration to the group is selected in the Sync Options list for the sync-failover device group.
    3. Select Sync to perform a manual ConfigSync.
  6. Perform any post-upgrade validation or test for your deployment.

Common issues and error messages during upgrade

  • After the underlying base BIG-IP software upgrade, if the HA configuration and gossip protocol are not functioning properly and you go to SSL Orchestrator > Configuration, the system continues to upgrade the SSL Orchestrator rpm software but not the SSL Orchestrator configuration. The system prompts to correct the HA setup first before performing any further configuration.
  • Starting in SSL Orchestrator 16.0.x-8.x, when the HA configuration and gossip protocol start working, the SSL Orchestrator rpm upgrade automatically resumes. For versions prior to SSL Orchestrator 16.0.x-8.x, you must ensure the gossip protocol is working properly prior to going to SSL Orchestrator > Configuration on the active device.
  • In some cases, the HA configuration and gossip protocol may seem to be uncorrectable. To recover, you must break the HA pair, remove the HA configuration completely, and rebuild the HA configuration. When the device trust is reset, the now-standalone devices individually trigger and resume the SSL Orchestrator rpm upgrade.
  • If the restnoded or restjavad process restarts or the system restarts during deployment, it is possible that some of the deployments may be in error states, and, as a result, any configuration changes are disabled.
  • The system may take time to recover automatically from HA connectivity issues. When that happens, the SSL Orchestrator > Configuration page displays the error message with a red background, and any configuration changes are disabled.
  • SSL Orchestrator deployment may fail and time out due to high CPU usage on devices, hypervisors that are starved of resources. Large configurations may also be a contributing factor. When this happens, you must restart the restnoded and restjavad processes using the bigstart restart restjavad restnoded command. Alternatively, you can restart the entire system.

Upgrade procedure

  • Upgrade from 14.1.x-5.x/15.0.x-6.x to 15.1.x-7.x (Break HA)
  • Upgrade from 14.0.x-4.x or earlier (Forklift Config)

Upgrade from 14.1.x-5.x/15.0.x-6.x to 15.1.x-7.x (Break HA)

To upgrade from SSL Orchestrator 14.1.x-5.x/15.0.x-6.x to SSL Orchestrator 15.1.x-7.x, you must perform the following high-level steps in sequence:

  1. Break HA if the SSL Orchestrator application is deployed on HA devices
  2. Upgrade the underlying BIG-IP software and boot to the newly upgraded software volume
  3. Setup the HA configuration if the SSL Orchestrator application is to be deployed on HA devices
  4. Release the forced offline device
  5. Verify the gossip protocol is working between the HA devices
  6. Verify log files related to the upgrade and HA status
  7. Update the SSL Orchestrator software and configuration

Important: You must not go to the SSL Orchestrator > Configuration page at any point during the upgrade process until the final step of updating the SSL Orchestrator software and configuration. Going to that page before then causes SSL Orchestrator to perform some configuration modification and may result in a failed upgrade.

1. Break HA if the SSL Orchestrator application is deployed on HA devices

If your SSL Orchestrator is in an HA configuration and you are upgrading from 14.1.x-5.x/15.0.x-6.x to 15.1.x-7.x, you must first break the HA between the peers. To avoid the having both active and standby units become active at the same time, you should first force the standby unit offline before removing the HA configuration. To do so, perform the following procedure:

  1. Log in to the Configuration utility of the STANDBY device.
  2. Go to Device Management > Devices.
  3. Select the standby device; it should be indicated by its device name followed by (Self).
  4. Select Force Offline.
  5. Log in to the Configuration utility of the ACTIVE device.
  6. Go to Device Management > Device Groups.
  7. Select the device group that includes the standby device.
  8. Remove all devices from the device group by moving them from the Includes list to the Available list.
  9. Select Update.

    Note: If the system returns an error that it cannot delete the device from the device group as it is used by the HA order feature in a traffic group, refer to K31248425: 01071761:3: Cannot delete device (/Common/<Device Name>) from device group (/Common/ha-group) because it is used by HA order on traffic group (/Common/traffic-group-1) for details on the steps to rectify the error.

  10. Select Delete to remove the device group.
  11. Go to Device Management > Device Trust > Device Trust Members.
  12. Check the standby device and select Delete.
  13. Select Delete to confirm the deletion.
  14. You should observe the active and standby devices report their status as ONLINE (ACTIVE) Standalone and FORCED OFFLINE Standalone respectively.
  15. Repeat steps 6 through 12 on the standby device, as needed.

2. Upgrade the underlying BIG-IP software and boot to the newly upgraded software volume

After you are done breaking HA or if you are upgrading standalone SSL Orchestrator 14.1.x-5.x/15.0.x-6.x to 15.1.x-7.x, refer to the following upgrade chapters applicable to your environment to perform the upgrade on the forced offline device first followed by the active device:

  • Chapter 5: Update or upgrade a standalone BIG-IP VE system using the Configuration utility
  • Chapter 6: Update or upgrade a standalone BIG-IP VE system using the TMOS Shell
  • Chapter 9: Update or upgrade BIG-IP systems using BIG-IQ

3. Set up the HA configuration if the SSL Orchestrator application is to be deployed on HA devices

After you have completed the upgrading on both devices, you should boot the devices to their newly upgraded software volume. After the devices boot, wait at least ten minutes before performing any management functions, then set up the HA configuration as needed. Refer to the following procedure for setting up the HA configuration:

  1. Log in to the Configuration utility of the active device.
  2. Go to Device Management > Devices.
  3. Select the name of the active device.
  4. Select ConfigSync and verify that the ConfigSync IP address is intact.
  5. Select Failover Network and verify that the failover configuration is intact.
  6. Log in to the Configuration utility of the forced offline device.
  7. Go to Device Management > Devices.
  8. Select the name of the forced offline device.
  9. Repeat steps 4 and 5 for the forced offline device.
  10. Log back into the Configuration utility of the active device.
  11. Go to Device Management > Device Trust > Device Trust Members.
  12. Select Add.
  13. For Device Type, select Peer.
  14. For Device IP Address, enter the management IP address of the forced-offline device.
  15. Enter the Administrator Username and Administrator Password.
  16. Select Retrieve Device Information.
  17. Verify the device certificate information and select Device Certificate Matches.
  18. For Name, as needed, enter the forced-offline device hostname.
  19. Select Add Device to add the forced offline device to the device trust.
  20. Go to Device Management > Device Groups.
  21. Select Create to create a new sync-failover device group.
  22. For Name, enter your device group name.
  23. For Group Type, select Sync-Failover.
  24. For Members, move both devices from the Available list to the Includes list.
  25. For Sync Type, select Manual with Incremental Sync.
  26. Select Finished.
  27. Go to Device Management > Overview.
  28. For Devices, ensure that the active device is selected.
  29. For Sync Options, ensure Push the selected device configuration to the group is selected for the newly created sync-failover device group.
  30. Select Sync to perform a manual ConfigSync.

4. Release the forced offline device

You can now release the forced-offline device from offline status. To do so, perform the following procedure:

  1. Log in to the Configuration utility of the forced-offline device.
  2. Go to Device Management > Devices.
  3. Select the name of the forced-offline device (it should be indicated by a black diamond).
  4. Select Release Offline.
  5. Select OK to confirm and bring the device online.
  6. You should observe this device report its status as ONLINE (STANDBY) In Sync.

You should verify the following:

Upgrade from 14.0.x-4.x or earlier (Forklift Config)

To upgrade from SSL Orchestrator 14.0.x-4.x or earlier to SSL Orchestrator 14.1.x-5.x or 15.1.x-7.x, you must "forklift" the configuration. The forklift process consists of the following high-level steps in sequence:

  1. Break HA if the SSL Orchestrator application is deployed on HA devices
  2. Undeploy your existing SSL Orchestrator application

1. Break HA if the SSL Orchestrator application is deployed on HA devices

If your SSL Orchestrator devices are in an HA configuration, you must break the HA between the peers before performing the upgrade steps previously detailed. To avoid having both active and standby units become active at the same time, you should first force the standby device offline before removing the HA configuration. To do so, perform the following procedure:

  1. Log in to the Configuration utility of the STANDBY device.
  2. Go to Device Management > Devices.
  3. Select the standby device; it should be indicated by its device name followed by (Self).
  4. Select Force Offline.
  5. Log in to the Configuration utility of the ACTIVE device.
  6. Go to Device Management > Device Groups.
  7. Select the device group that includes the standby device.
  8. Remove all devices from the device group by moving them from the Includes list to the Available list.
  9. Select Update.

    Note: If the system returns an error that it cannot delete the device from the device group as it is used by the HA order feature in a traffic group, refer to K31248425: 01071761:3: Cannot delete device (/Common/<Device Name>) from device group (/Common/ha-group) because it is used by HA order on traffic group (/Common/traffic-group-1) for details on the steps to rectify the error.

  10. Select Delete to remove the device group.
  11. Go to Device Management > Device Trust > Device Trust Members.
  12. Check the standby device and select Delete.
  13. Select Delete to confirm the deletion.
  14. You should observe the active and standby devices report their status as ONLINE (ACTIVE) Standalone and FORCED OFFLINE Standalone respectively.
  15. Repeat steps 6 through 12 on the standby device as needed.

2. Undeploy your existing SSL Orchestrator application

Undeploy your existing deployed SSL Orchestrator application by performing the following steps:

  1. Log in to the SSL Orchestrator Configuration utility.
  2. Go to iApps > Application Services > Applications LX.
  3. Select all deployed SSL Orchestrator Apps and select Undeploy.
  4. Select the SSL Orchestrator Apps with the following templates:
    • f5-ssl-orchestrator-storage
    • f5-ssl-orchestrator-network
    • f5-ssl-orchestrator-policy
    • f5-ssl-orchestrator-service
    • f5-ssl-orchestrator-tls
    • f5-ssl-orchestrator
  5. Select Delete.

3. Uninstall the SSL Orchestrator software

Uninstall the SSL Orchestrator software by performing the following steps:

  1. Go to iApps > Package Management LX.
  2. Select the f5-iappslx-ssl-orchestrator package.
  3. Select Uninstall….
  4. Select Yes to confirm uninstalling the package.

4. Upgrade the underlying BIG-IP software and boot to the newly upgraded software volume

Upgrade the underlying BIG-IP software to BIG-IP 14.1.0 or later and boot to the new partition. Refer to the following upgrade guides applicable to your environment:

  • Chapter 5: Update or upgrade a standalone BIG-IP VE system using the Configuration utility
  • Chapter 6: Update or upgrade a standalone BIG-IP VE system using the TMOS Shell
  • Chapter 7: Update or upgrade BIG-IP HA systems the Configuration utility
  • Chapter 8: Update or upgrade BIG-IP HA systems using the TMOS Shell
  • Chapter 9: Update or upgrade BIG-IP systems using BIG-IQ

5. Set up the HA configuration if the SSL Orchestrator application is to be deployed on HA devices

When the devices boot, wait at least ten minutes before performing any management functions. Then set up the HA configuration as needed. Refer to the following procedure for setting up the HA configuration:

  1. Log in to the Configuration utility of the active device.
  2. Go to Device Management > Devices.
  3. Select the name of the active device.
  4. Select ConfigSync and verify that the ConfigSync IP address is intact.
  5. Select Failover Network and verify that the failover configuration is intact.
  6. Log in to the Configuration utility of the forced offline device.
  7. Go to Device Management > Devices.
  8. Select the name of the forced offline device.
  9. Repeat steps 4 and 5 for the forced offline device.
  10. Log back in to the Configuration utility of the active device.
  11. Go to Device Management > Device Trust > Device Trust Members.
  12. Select Add.
  13. For Device Type, select Peer.
  14. For Device IP Address, enter the management IP address of the forced-offline device.
  15. Enter the Administrator Username and Administrator Password.
  16. Select Retrieve Device Information.
  17. Verify the device certificate information and select Device Certificate Matches.
  18. For Name, enter the forced-offline device hostname as needed.
  19. Select Add Device to add the forced offline device to the device trust.
  20. Go to Device Management > Device Groups.
  21. Select Create to create a new sync-failover device group.
  22. For Name, enter your device group name.
  23. For Group Type, select Sync-Failover.
  24. For Members, move both devices from the Available list to the Includes list.
  25. For Sync Type, select Manual with Incremental Sync.
  26. Select Finished.
  27. Go to Device Management > Overview.
  28. For Devices, ensure the active device is selected in the list.
  29. For Sync Options, ensure Push the selected device configuration to the group is selected for the newly created sync-failover device group.
  30. Select Sync to perform a manual ConfigSync.

6. Provision and update the SSL Orchestrator software as needed

Provision the SSL Orchestrator on the System > Resource Provisioning page as needed. For information about provisioning resources for a module, refer to K12111: Provision licensed BIG-IP modules.

Update the SSL Orchestrator rpm as needed by performing the following steps:

  1. Ensure you have downloaded the latest SSL Orchestrator rpm package for your SSL Orchestrator version from F5 Downloads to your local workstation.
  2. Log in to the SSL Orchestrator configuration utility.
  3. Go to SSL Orchestrator > Configuration.
  4. At the top of the page, select Upgrade SSL Orchestrator.
  5. Select Choose File.
  6. Navigate to location of the SSL Orchestrator rpm package that you have downloaded at the beginning of this procedure and select Open.
  7. Select Upload and Install.

7. Configure your SSL Orchestrator application

Configure your SSL Orchestrator application using the SSL Orchestrator setup utility.

If your SSL Orchestrator experiences a failed upgrade and you need to recover your system, you must perform a series of manual steps to clean up the FDB nodes as well as the SSL Orchestrator application. For information about the manual steps, refer to the following documentation appropriate for your SSL Orchestrator version:

  • SSL Orchestrator 15.1.x-7.x

    The Overview: Upgrade from previous SSL Orchestrator versions using the recovery procedure section of the Setting up F5 Guided Configuration for SSL Orchestrator chapter of the F5 Guided Configuration for SSL Orchestrator: Setup 15.1.0-7.0 manual.

  • SSL Orchestrator 14.1.x-5.x

    The Upgrade from previous SSL Orchestrator versions using the recovery procedure section of the Installing and Upgrading SSL Orchestrator chapter of the F5 Guided Configuration for SSL Orchestrator: Setup 14.1.0-5.0 manual.
