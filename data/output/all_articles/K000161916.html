K000161916: Control plane CPU spike to 100% due to REST framework Gossip Loop

Type
Support Solution
Published
2026-06-29
Updated
2026-06-29
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000161916

Description

BIG-IP control plane CPU utilization spikes to 100% following a device rejoin to a device trust cluster. The java (restjavad) process is consistently at peak CPU usage.

Further check on the restjavad logs reveals that the REST framework gossip mechanism enters a loop, repeatedly issuing PUT requests for the same device UUID.

[I][3417742][<time-stamp>][ForwarderPassThroughWorker] {"user":"local/admin","method":"PUT", "uri":"http://localhost:8100/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices/<device-UUID>", "status":200,"from":"http://localhost:8100/shared/gossip"}

 

Environment

  • BIG IP LTM
  • Device trust cluster

 

Cause

A stale or inconsistent REST device object was introduced when the device was rejoined to the trust cluster. This triggered a gossip loop in the REST framework, causing repeated PUT operations for the same device UUID. The resulting load generated thousands of gossip-conflict records in REST framework storage, overwhelming the default restjavad heap memory allocation and causing frequent GC cycles and sustained high CPU usage by the java process.

 

Answer/Recommended Actions

Immediate Mitigation — Restart restjavad:

  1. On the standby device, restart the restjavad process: bigstart restart restjavad restnoded
  2. Monitor the analysis plane CPU utilization to confirm it drops to normal levels.
  3. Once the standby is stable, perform a controlled failover so the previously active device becomes standby.
  4. Repeat the restjavad restart on the new standby device: bigstart restart restjavad restnoded
  5. Confirm CPU utilization is within normal ranges on both devices.

 

If the issue persists after restarting restjavad:

  • Rebuild device trust and clear REST storage

 

Additional Information

The gossip loop can be confirmed by checking the number of gossip-conflict records in REST framework storage:

grep "shared/gossip-conflicts" storage_text_dump.txt | grep id | wc
