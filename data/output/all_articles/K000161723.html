Description

On VELOS chassis (CX1610 and CX410 platforms), persistent module:communication-error alarms may be reported for the fantray (vfc) and/or psu-controller (vpc) components, with system health showing unhealthy status and error severity. This condition persists even though physical hardware (fans, PSUs, voltages, and temperatures) continues to operate normally and individual sensor readings report OK. The alarms appear to be stale/stuck and do not self-clear.

Example alarm output:

show system alarms

ID RESOURCE SEVERITY TEXT TIME CREATED
------------------------------------------------------------------------------------------

12345 fan-controller-4 ERROR Module communication error detected 2026-02-05 01:23:45 UTC

Environment

  • F5OS-C on VELOS CX1610 or CX410 chassis platforms
  • Components affected: fantray (vfc) and/or psu-controller (vpc)
  • Physical hardware (fans, PSUs, voltages, temperatures) reporting OK
  • Alarms persist across controller failover and do not self-clear
  • BIG-IP LTM tenant running on VELOS (R100 blades)

Cause

ID1978041 — The module:communication-error state becomes latched/stuck in the diag-agent and is not automatically cleared, even when the underlying hardware is operating normally. A fix is available in F5OS-C.

Answer/Recommended Actions

To clear the stuck module:communication-error alarms, perform the following steps on both the active and standby system controllers. These commands should ideally be run during a maintenance window as a precaution, although no production traffic impact is expected from restarting the diag-agent service.

Option 1: Clear alarms individually using diag-agent

  1. To clear the alarm for fantray-4 (chassis/hardware/vfc4), run:

    docker exec -it diag-agent psf run PATCH:components/attributes component=chassis/hardware/vfc4 attribute=module:communication-error data.value=false eval=true

  2. To clear the alarm for psu-controller-3 (chassis/hardware/vpc3), run:

    docker exec -it diag-agent psf run PATCH:components/attributes component=chassis/hardware/vpc3 attribute=module:communication-error data.value=false eval=true

Option 2: Restart the diag-agent container

As an alternative to the individual PATCH commands above, restart the diag-agent container on both controllers:

docker container restart diag-agent

Verify the alarms are cleared

After applying either option, verify that the alarms have been resolved. Replace X and Y with the correct value:

show system health components component fantray-X

show system health components component psu-controller-Y

The module:communication-error attribute should now show health: ok and value: false.

Permanent fix: Upgrade to the fixed version of F5OS-C.

Additional Information

  • The diag-agent service performs diagnostic activities such as Power-On Self-Test (POST) and online/offline diagnostics. No production traffic impact is expected if the diag-agent container is restarted.
  • Despite the unhealthy / error status reported for the fantray and psu-controller components, individual hardware sensor readings (voltages, fan speeds, temperatures) continue to report as OK, confirming the physical hardware is functioning normally.
  • This issue has been observed across multiple VELOS CX1610 and CX410 chassis deployments, and consistently resolves with the diag-agent workaround described above.
  • The error state is latched in the diag-agent and does not self-clear; the alarms will reappear after the next diag-agent restart if the underlying trigger condition recurs on F5OS-C versions prior to the fix.
