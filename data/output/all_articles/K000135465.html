K000135465: Considerations when configuring UDP syslog (port 514) load-balancing

Type
Support Solution
Published
2024-07-24
Updated
2025-04-01
Applies to
  • BIG-IP
Source

Description

Consistently overloaded data-plane CPU utilization at 100% for any single tmm core may cause delayed traffic processing up to the point of failure or fail-over.

Environment

  • Virtual server utilizing the UDP protocol
  • Load-balancing syslog (UDP)

Cause

The BIG-IP system will normally distribute traffic among different tmms using clustered multi-processing (CMP). Traffic is distributed among the blades and tmms by the disaggregator (DAG). Clustered multi-processing is generally the best way to spread network traffic processing load between separate CPU cores by taking advantage of the fact that most network traffic have unique connection IP/port numbers for each connection. Processing network traffic on a per-connection basis saves CPU time from repeating certain processes, such as network address translation, route lookups, and arp lookups.

However, with the advent of SIEM systems, some log aggregators that use protocols like syslog UDP may combine the load of several different systems into one IP addresses. Other applications, such as snort, may send large amounts of UDP syslogs from a single UDP socket (connection).

When configuring load-balancing for UDP syslog, syslog traffic from a single source IP/port will be distributed by CMP to only one tmm CPU core on the BIG-IP system. This can lead to the single tmm CPU core to be overloaded, while other CPU cores are not being utilized at all.

 

Recommended Actions

There are several methods that can be used to achieve a more optimized traffic distribution among the available tmm data-plane CPUs.

The first option is to ensure that incoming traffic to BIG-IP virtual servers has enough entropy (randomness) based on large numbers of source IP addresses and TCP/UDP source ports.

For example, instead of aggregating all logs into one syslog stream, logs can be sent directly from different devices to BIG-IP before log aggregation. Or, the log aggregator can try to utilize multiple UDP streams using different connections/instances such that there are more sockets used to send traffic to BIG-IP's virtual server in parallel.

If this cannot be achieved, other features can be used to spread the load.

Some BIG-IP hardware appliances allow traffic acceleration and can use UDP round-robin to spread UDP traffic processing among different tmm data-plane CPUs regardless of the source/destination IP/port tuple.

Refer to the following resources to configure your BIG-IP system for UDP DAG round-robin:

Additional Information

Troubleshooting: 

You can observe the performance statistics of your BIG-IP system to identify if there is any single data-plane CPU that is consistently set at 100% CPU.  You may want to look at your BIG-IP system CPU performance graphs under "View Detailed Graph.."
You can also upload your system's QKview snapshot to ihealth2.f5.com  to examine which virtual servers are utilizing the most CPU in more detail.
