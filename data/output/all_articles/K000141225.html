Description

Client authentication fails via On-Demand Cert Auth on APM, but it works OK in LTM.
You may encounter these kind of logs

/var/log/ltm

---------

ltm:Sep 01 09:00:00 bigip.example.com err tmm1[23756]: 01230140:3: RST sent from 1.1.1.1:443 to 2.2.2.2:50581, [0x2feb9ec:4230] Access encountered an error (Unknown error)

/var/log/apm

---------
Invalid cert:

apm: info apmd[15293]: 01490006:6: /Common/ap_profile: Following rule 'fallback' from item 'Start' to item 'On-Demand Cert Auth'
apm: info apmd[15293]: 01490007:6: /Common/ap_profile:5fc5fc49: Session variable 'session.clientcert.ssl_rehandshake_pending' set to '2'
apm: info apmd[15293]: 01490007:6: /Common/ap_profile:5fc5fc49: Session variable 'session.ssl.cert.exist' set to '0'
apm: info apmd[15293]: 01490007:6: /Common/ap_profile:5fc5fc49: Session variable 'session.ssl.cert.valid' set to '1'

In packet captures you may see this TCP Reset log.

 

 TCP 255 OUT s1/tmm1 : https(443) → 50578 [RST, ACK] Seq=9311 Ack=5756 Win=0 Len=68 [F5RST: Access encountered an error (Unknown error)]

Environment

  • BIG-IP APM v15.x to 17.x
  • The openssl -verify command reports back: OK
  • The certificate exists in the Personal Certificate Repository, and Enhanced Key Usage contains Client Authentication.
  • The user is asked to select a Client Cert from list when access the APM VS through web browser.

 

Cause

Issuer field on Client Certificate is not populated with a valid value.
There are some validation requirements to make On-Demand works properly.
Here is a list of checks performed by BIG-IP to validate the certificates:

 

Certificate depth should not be more than the configured value

BIG-IP validates the certificate chain (root and intermediate certificate) based on the value specified in the Certificate Chain Traversal Depth field sent by the client or server. By default, the value is set to 9. If the certificate chain depth is more than the specified value, then certificate validation fails with the “certificate chain too long” error message

Certificate trusted chain BIG-IP validates the certificate chain of trust with the respective issuer for each certificate in the chain.

Certificate Revocation List (CRL) The CRL validates the certificates from the chain, statically or dynamically, based on the configurations.

Certificate extensions BIG-IP requires a CA certificate to have Basic Constrains and CA: True attributes.

Certificate duration validity The date and time mentioned in the Not Before and Not After fields for a valid certificate must be based on the current time.

Certificate’s common name BIG-IP verifies the common name of the certificate with the DNSName attributes subject alternative names (subjectAltName).

 

If any of the above checks ails, then the certificate is marked as invalid.

 

Recommended Actions

Create a new Client Certificate and make sure the Issuer field is populated and any other requirement listed here is fulfilled.
