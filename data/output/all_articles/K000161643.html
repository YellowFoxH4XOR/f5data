Topic

This article provides an overview of how certificates are renewed on the BIG-IP system with they keymgmtd daemon by describing the following:

  • Certificate auto-renewal starts 14 days prior to expiry with tiered retries that never give up.
  • BIG-IP only tries auto-renews CA-managed certificates. Manually imported certs are your responsibility.
  • The system performs key-matching verification and blocks installs when verification fails. The old certificate stays active if the new one does not match.
  • Only HA-active, primary (for clusters) and licensed devices run renewals. In the event of a failover, renewal resumes on the next timer cycle.

Description

After a certificate is created and bound to a virtual server's SSL profile, keymgmtd — the control-plane daemon — takes over the certificate lifecycle management. It subscribes to certificate, key, and Certificate Signing Request (CSR) objects in real time through the MCP message bus, and evaluates renewal eligibility on a weekly sweep.

The following two certificate categories exist:

  • CA-managed system native certificates in BIG-IP: auto-renewed by keymgmtd. There are certificate orders for these.1
  • Manually imported certificates: you must track and rotate these yourself. There are no certificate orders for these.1

1To show counts of successful, failure and pending orders, enter tmsh show sys crypto cert-order-manager.

Note: T14 refers to 14 days to expiry and so on.

T14: Weekly validity sweep detects the certificate is within the auto-renewal window. keymgmtd creates a certificate order and submits a CSR to the configured CA (e.g. Comodo/Sectigo, Symantec/DigiCert, GoDaddy, or ACME).
T14 to T7: Active polling. CA responses are mapped to one of the following:

  • Approved (install immediately)
  • Pending (poll again next cycle)
  • Rejected or Error (retry on next cycle)

T7 to T0: Escalation territory. If still unresolved, retries continue at longer intervals while alerts are logged into /var/log/ltm log file.
T0: Certificate expires. New TLS handshakes fail for most modern clients. While existing sessions may persist briefly, a service outage occurs.

Certificate and private key verification

Before installing any renewed certificate, keymgmtd verifies the new certificate matches the private key. If there's a mismatch, installation is refused, the temporary file is cleaned up, and the old certificate stays in place. When this occurs you may observe the following message in the /var/log/ltm log:
Failed to install certificate due to mismatch of the certificate with key

HA and Clustering requirement

The certificate order manager activates only when the device is HA-active for the default traffic group and the feature is licensed. For clustered devices, the device must be the primary device.

After a failover, the new active device picks up all pending orders on the next timer cycle. No orders are lost as they persist in configuration, and not in memory. 

Recommendations

Use the following command to troubleshoot issues:

  • Certificate expiry check
    tmsh list sys file ssl-cert /Common/mycert.crt all-properties
    openssl x509 -in /config/ssl/ssl.crt/mycert.crt -noout -dates -serial -subject

  • OCSP certificate validation stats 
    tmctl cert_validator_ocsp_stat
  • Client SSL profile stats (189 columns!) 
    tmctl profile_clientssl_stat
  • Server SSL profile stats (152 columns)
    tmctl profile_serverssl_stat
  • OCSP responder profile stats 
    tmctl profile_ocsp_responder_stat
  • Daemon health and logs
    bigstart status keymgmtd grep -i "keymgmtd\|cert.*order\|CertOrder" /var/log/ltm | tail -30
  • Enable debug logging
    tmsh modify sys db log.keymgmtd.level value debug
  • External handshake verification 
    echo | openssl s_client -connect :443 -servername 2>/dev/null \ | openssl x509 -noout -dates -serial -issuer
    Healthy: Verify return code: 0 (ok)
    Expired: Verify return code: 10 (certificate has expired)
