Security Advisory Description

An issue in NGINX resolver may allow an attacker who is able to forge UDP packets from the specified DNS server to cause a 1-byte memory overwrite, resulting in a worker process crash or other unspecified impact. (CVE-2021-23017)

Impact

A remote attacker can cause a worker process to stop responding, denying access to some users. This vulnerability is present only if one or more resolver directives have been configured. By default, no resolvers are configured.

NGINX Plus and Open Source

For more information about the resolver directive, refer to the following NGINX modules directive reference pages:

  • ngx_http_core_module
  • ngx_http_upstream_module
  • ngx_mail_core_module
  • ngx_stream_core_module
  • ngx_stream_upstream_module

NGINX Ingress Controller

Most commonly, the resolver is used with NGINX Plus to support ExternalName services as load balancing destinations, however other use cases are possible. For more information about use with ExternalName services, refer to the kubernetes-ingress page in GitHub.

Mitigation

To mitigate this vulnerability, F5 recommends that you configure DNS servers in a properly secured, trusted local network. Additionally, you can remove resolver statements from your configuration if business logic allows for this modification. To do so, perform one of the following procedures appropriate for your product:

  • NGINX Ingress Controller
  • NGINX Plus and Open Source

NGINX Ingress Controller

Impact of action: Removing resolvers can break NGINX features that rely on them, which may cause downtime for the applications exposed via NGINX Ingress Controller. Any modifications to the configuration should first be performed in a test environment to ensure compatibility. Modifications to your production environment should be implemented during a maintenance window to allow for time to roll back changes if necessary.

For NGINX Ingress Controller, removing resolvers from the configuration depends on how the resolvers were added. Resolvers can be configured by any of the following methods:

  • Directly via the resolver-addresses ConfigMap key. For more information, refer to the General Customization section of the ConfigMap Resource page.
  • Indirectly via configuration snippets, by adding a resolver directive via the following methods:
    • Using http-snippets, server-snippets, location-snippets, or stream-snippets in the ConfigMap. For more information, refer to the Snippets and Custom Templates section of the ConfigMap Resource page.
    • Using the nginx.org/server-snippets or nginx.org/location-snippets Ingress annotations. For more information, refer to the Snippets and Custom Templates section of the Advanced Configuration with Annotations page.
    • Using the http-snippets or server-snippets fields of VirtualServer resources or using the location-snippets fields of VirtualServer or VirtualServerRoute resources. For more information, refer to the Using Snippets section of the VirtualServer and VirtualServerRoute Resources page.
    • Using the serverSnippets field of TransportServer resources. For more information, refer to the Using Snippets section of the TransportServer Resource page.
  • Indirectly via custom configuration templates, by adding a resolver directive. For more information, refer to the Custom Templates page.
To determine if your NGINX Ingress Controller configuration is vulnerable, review each of the previously listed configuration sections and inspect the full generated NGINX configuration for any resolver directives. For more information about checking the full generated configuration, refer to the Checking the Generated Config section of the Troubleshooting page.

NGINX Plus and Open Source

For NGINX Plus or Open Source, the configuration can be split into multiple configuration files and is usually stored in /etc/nginx or in a subfolder of that directory. You must review each configuration file to determine whether a resolver directive has been set.

Impact of action: The business logic that your NGINX configuration implements may rely on an ability to resolve names in run-time; therefore, modifications to the resolver directive may cause unintended consequences. Any modifications to the configuration should first be performed in a test environment to ensure compatibility. Modifications to your production environment should be implemented during a maintenance window to allow for time to roll back changes if necessary.

  1. Log in to the command line of your NGINX host system, with administrative privileges.
  2. Go to your NGINX configuration directory, usually in /etc/nginx.

    Note: The configuration can be stubbed out to multiple files, so be sure to review all appropriate configuration sections.

  3. Using your preferred text editor, locate the configuration block containing the resolver directive and enter a number sign (#) at the beginning of the line to comment out the directive. For example:

    Note: If there are multiple resolver directives in your configuration, F5 recommends testing changes one at a time.

    upstream example {
        # resolver 192.0.2.1:1053;
        server example.net;}

  4. Save changes and exit the text editor.
  5. Test configuration changes by entering the following command:

    sudo nginx -t

  6. The output should appear similar to the following:

    nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
    nginx: configuration file /etc/nginx/nginx.conf test is successful

  7. Reload the NGINX configuration by entering the following command:

    sudo service nginx reload
