Description

In an NGINX Plus stream (Layer 4) configuration, you may see repeated errors such as:

upstream timed out (110: Connection timed out) while connecting to upstream,
client: X.X.X.X, server: VIP:443, upstream: "BACKEND:443",
bytes from/to client:0/0, bytes from/to upstream:0/0

These errors persist even after setting proxy_responses 0 and/or commenting out proxy_timeout. This article explains why: Direct Server Return (DSR) and the proxy_responses directive apply only to UDP. When they are applied to a TCP stream service, they have no effect, and a DSR-style return path breaks the TCP handshake. The correct method for preserving the client source IP on TCP is IP Transparency.

Symptoms

  • High volume of upstream timed out (110: Connection timed out) while connecting to upstream entries in the NGINX error log.
  • Log entries consistently show bytes from/to client:0/0 and bytes from/to upstream:0/0 (no data exchanged).
  • May be accompanied by upstream server temporarily disabled while connecting to upstream and no live upstreams.
  • Errors continue unchanged after setting proxy_responses 0 and/or removing proxy_timeout.

Environment

  • NGINX Plus (and NGINX Open Source built with --with-stream)
  • stream (Layer 4 TCP/UDP) proxying
  • proxy_bind ... transparent (IP transparency / transparent proxy) in use
  • A Direct Server Return (DSR) style network design (backend return traffic routed around NGINX toward the client)

Cause

1. Stream servers default to TCP

In the stream context, TCP is the default protocol. UDP requires the explicit udp parameter on the listen directive. A listener without udp is a TCP service:

server {
    listen VIP:443 ;      # no "udp" => TCP
    # ...
}

As a TCP reverse proxy, NGINX opens its own connection to the upstream and must complete the full TCP three-way handshake (SYN → SYN-ACK → ACK) before any data can flow. NGINX always requires the upstream's SYN-ACK to arrive back at its own socket. This is inherent to TCP proxying and cannot be disabled by any directive.

2. proxy_responses is UDP-only

Per the NGINX documentation, proxy_responses:

"Sets the number of datagrams expected from the proxied server in response to the client request if the UDP protocol is used."

It counts UDP datagrams. On a TCP connection it is a no-op, so changing it from 1 to 0 has no effect on a TCP service.

3. proxy_timeout does not govern the connect phase

The error text while connecting to upstream indicates the failure occurred in the TCP connect phase (establishing the connection), and 0/0 bytes confirms no data was exchanged. The connect phase is governed by proxy_connect_timeout (default 60s), not by proxy_timeout. Removing proxy_timeout therefore does not change this behavior.

4. DSR is UDP-only; it is not supported for TCP

The F5 blog IP Transparency and Direct Server Return with NGINX and NGINX Plus as Transparent Proxy states that DSR applies to UDP-based protocols only:

MethodSupported protocolsUDP required config
IP Transparency (Method 1)TCP-based and UDP-based (TCP: works by default)UDP: proxy_responses 1
DSR – Router NAT (Method 2a)UDP-based only (TCP: not supported)UDP: proxy_responses 0
DSR – Origin NAT (Method 2b)UDP-based only (TCP: not supported)UDP: proxy_responses 0

In a DSR design the backend's return traffic is intentionally routed around NGINX toward the client. For a TCP service this means the upstream's SYN-ACK never returns to NGINX, so connect() never completes and times out with 0/0 bytes exchanged. DSR fundamentally cannot work for TCP.

How to confirm

The symptom (110 / 0-0 bytes / "while connecting to upstream") is a TCP connect failure, but on its own it does not prove why the SYN-ACK is not returning. Three distinct causes produce an identical log line:

  1. A DSR-style return path routes the backend SYN-ACK around NGINX (design issue).
  2. A firewall/ACL between NGINX and the backend drops the SYN or the returning SYN-ACK.
  3. The backend is not listening on the port (this usually returns a RST / 111 ECONNREFUSED rather than 110, but confirm).

Take a simultaneous packet capture on both hosts while errors are occurring:

# On the NGINX host
sudo tcpdump -ni any host BACKEND_IP and tcp port 443 -w /tmp/nginx-443.pcap

# On the backend host
sudo tcpdump -ni any tcp port 443 -w /tmp/backend-443.pcap

Interpretation:

  • Backend sends a SYN-ACK but NGINX never sees it → return-path / DSR bypass.
  • Backend never receives the SYN → firewall/routing dropping outbound traffic.
  • Backend sends a RST → service not listening on that port.

Resolution

To preserve the client source IP on TCP services while keeping NGINX functional, use IP Transparency (Method 1), not DSR. In this model the backend return traffic is routed back through NGINX and intercepted at its local socket, so the TCP handshake completes normally. For TCP, the blog notes this "works by default" once the return routing and transparent intercept are in place.

  • Keep proxy_bind $remote_addr:$remote_port transparent; (client-IP spoofing on egress is correct).
  • Remove any DSR-style forwarding rules that send backend return traffic directly to the client.
  • Route the backends' return traffic back to the NGINX host (NGINX as the return path for that traffic).
  • Configure NGINX to intercept the returning traffic to its local socket (policy routing + transparent intercept, per the "IP Transparency" section of the blog).
  • Do not rely on proxy_responses / proxy_timeout for TCP — they are UDP-oriented and irrelevant here.

Note on port 443 in a stream block: this is SSL passthrough (Layer 4) and is fully supported. The backends terminate TLS. This is unrelated to the connect-timeout issue.

Directive quick reference

DirectiveApplies toNotes
proxy_responsesUDP onlyCounts expected UDP response datagrams. No effect on TCP.
proxy_timeoutTCP & UDPTimeout between two successive read/write operations on an established session. Does not govern the initial connect.
proxy_connect_timeoutTCP & UDPTimeout for establishing the connection to the upstream (default 60s). This is what expires in the "while connecting to upstream" error.
proxy_bind ... transparentTCP & UDPOriginate the upstream connection from the client's real IP. Requires kernel routing/intercept configuration.
