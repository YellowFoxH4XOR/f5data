Description

This article dicusses potential network performance degradation that may arise when there is incoming traffic matching an F5OS Layer 2 Forwarding Database (FDB) entry that was removed (and not yet re-learned), or was created (learned) on a different port.
This can happen in deployments matching the below conditions:
 
Condition 1 (Applies to r5k, r10k, r12k, and Multi-Blade VELOS systems):

Tenant being configured to send traffic via MAC address A (typically a virtual MAC), but the returning traffic coming via MAC address B (typically a physical MAC). One of known examples is Arista IP anycast technology, where tenant egresses traffic via a gateway that is resolved to virtual MAC address (due to IP anycast), but the returning traffic comes from real VLAN MAC address.

 
A F5OS FDB entry is created when the tenant issues an ARP request for gateway MAC, and Arista responds with a virtual MAC address. The F5OS FDB entry age expires due to returning traffic coming from real VLAN MAC address. When F5OS FDB entry is removed, and tenant keeps egressing the traffic via gateway, F5OS FPGA (packet processing component) will consider this traffic internally as DLF (Destination Lookup Failure).
 
Since F5OS 1.8.0, DLF traffic is rate-limited internally to a relatively low value. This in turn will cause most of the outgoing traffic towards the network to be dropped internally. These internal drops will naturally cause TCP retransmissions and eventually applications timeouts.
Condition 2 (Applies to r10, r12k and Multi-Blade VELOS systems):
rSeries:

LACP trunk (or static LAG) comprising interfaces from different FPGAs. This applies only to rSeries 10XXX/12XXX and does not apply to multi-blade Velos partition.

 
On rSeries, FPGA-1 handles ports 1.0 to 10.0, and FPGA-2 handles ports 11.0 to 20.0. On Velos, each blade has its own FPGA. 
The FDB entries are synchronized between the FPGAs. But aging events are processed only on FPGA that learned the entry first.

When LACP trunk (or static LAG) is, for example comprising interfaces 1.0 and 11.0, and certain MAC address is learned via port of FPGA-1, subsequent packets that are hashed to port of FPGA-2 will not refresh the aging of this MAC address entry in FDB table. 

The issue is tracked under ID1934005, and only affects rSeries 10k and 12k. After the fix, the aging events will be tracked on both FPGAs.

 

Multi-Blade Velos:

When LACP trunk (or static LAG) is, for example comprising interfaces from blade-1 and blade-2, and a certain MAC address is learned via port on blade-1, subsequent packets that are hashed to port on blade-2, will not refresh the aging of this MAC address entry in FDB table. This is expected since only owner blade updates the aging of the MAC address entry. If packets consistently hit a non-owner blade, the entry on the owner blade will age out.

Note: In most of the traffic patterns, this issue will not occur as MAC address entries aging will be updated due to packets consistent arrival to all the blades. It is only when the traffic is sent out periodically with high interval between the packets, in conjunction with load-balancing decision causing packets to stick to non-owner blade for a while, the problem will surface.

Environment

  • rSeries 5XXX (only condition 1), 10XXX, 12XXX
  • F5OS-C 1.6.x, 1.8.x
  • F5OS-A 1.5.x, 1.8.x
  • Infrequent traffic hitting F5OS from a certain MAC address

Cause

F5OS is infrequently receiving traffic from a certain MAC address.
When F5OS FDB entry ages out and traffic is coming to F5OS platform from a matching destination MAC address that was removed from the table and not yet re-learned, FPGA will consider this traffic internally as DLF (Destination Lookup Failure).
Since F5OS 1.8.0, DLF traffic is rate-limited internally to a relatively low value. This in turn will cause most of the outgoing traffic towards the network (traffic that came in from the client) to be dropped internally.

2) Consider the below steps when virtual MAC addresses are in use (for example due to Arista IP anycast technology) .

  • Add static FDB entry for aging-out MAC address via confd:
(config)# fdb mac-table entries entry <mac-address> <vlan-id> tag_type_vid interface interface-ref config interface <interface>
(config)# commit

Note: If an FDB entry is learned via a trunk interface, make sure you add an FDB entry for that trunk interface, not an interface being part of a trunk. The same command works on rSeries as well as on Velos partition.

  • Lower ARP cache timeout on tenant via 'arp.timeout' sys db.

CLI:

# tmsh modify sys db arp.timeout value 98
# tmsh save sys config

GUI:

Network ›› ARP : Options and change value of 'Dynamic Timeout' field.

The tenant will now send an ARP request every 98 seconds, before FDB expires on F5OS (300 seconds).

Note: A lower value generates more ARP traffic, but the impact of the extra ARP traffic should be negligible in most environments.

  • Configure LTM pool and add IP address resolved to virtual MAC. Assign ICMP health monitor to the pool. The pool does not need to be referenced by any object like virtual server or iRule. The health monitor will send ICMP echo requests and will wait for replies. If the IP address sends back ICMP echo reply, it will refresh timeout of ARP entry on the tenant as well as FDB entry on F5OS.

Note: This solution will work only when the IP address is able to respond to ICMP requests. If you choose this solution, make sure the interval in ICMP health monitor is lower than 300 seconds (default timeout of ARP and FDB entries).

3) Consider the below steps when using LACP trunk (or static LAG) comprising interfaces from different FPGAs.

  • Add static FDB entry for aging-out MAC address via confd:
(config)# fdb mac-table entries entry <mac-address> <vlan-id> tag_type_vid interface interface-ref config interface <interface>
(config)# commit

Note: If an FDB entry is learned via a trunk interface, make sure you add an FDB entry for that trunk interface, not an interface being part of a trunk. The same command works on rSeries as well as on Velos partition.

  • Contact F5 Support to get F5OS-A 1.8.0 Engineering Hotfix for ID1934005 or upgrade to the official fix in the next F5OS-A 1.8.x release for the condition 2 on rSeries 10k and 12k.
