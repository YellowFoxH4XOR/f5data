K35715602: BIG-IP AVR - There is no data in Analytics but displays error message

Type
Support Solution
Published
2021-05-18
Updated
2023-02-21
Applies to
  • BIG-IP
  • BIG-IP Analytics: 15.1.2
Source
https://my.f5.com/manage/s/article/K35715602

Description

This article addresses no data in Analystics.

When navigating to Statistics > Analytics > HTTP > Overview, you will see error message:
Failed to run a report: Could not retrieve AuthZ entity IDs: vips

When navigating to Statistics >  Analytics > CPU, you will see error message:
"There was a system error... Data could not be fetched" as well "Internal error

Environment
  • BIG-IP AVR
  • Several objects in Statistics > Analytics has no data
  • Errors can be seen in several objects as per Description

Cause

There is a possible database issue with AVR.

Recommended Actions

You will need reset the database to resolve the issue.
  1. Login to the Command Line.
  2. Run the following command:

    Impact of workaround: Restarting mysql service will make device offline and interrupts traffic processing. You should perform this action only during a maintenance window. If the system is configured as part of a high availability (HA) pair, the device may fail over.

    bigstart restart mysql
    touch /var/avr/init_avrdb
    bigstart restart monpd
If after resetting the database does not resolve the issue, you will need to check the permissions/contexts on the symbolic link.
  1. Login the Command Line.
  2. Run the following command to check the permission.
    ls --lcontext -d /tmp /var/tmp /shared/tmp /var/lib/mysql
    ls --lcontext /var/lib/mysql

    Below is an expected permissions/contexts on the symbolic link.
    # ls --lcontext -d /tmp /var/tmp /shared/tmp /var/lib/mysql
    drwxrwxrwt. 15 system_u:object_r:tmp_t:s0       root  root  4096 2021-01-01 10:10 /shared/tmp
    drwxrwxrwt.  5 system_u:object_r:tmp_t:s0       root  root  1024 2021-01-01 10:10 /tmp
    lrwxrwxrwx.  1 system_u:object_r:appdata_t:s0   mysql mysql   34 2021-01-01 10:10 /var/lib/mysql -> /appdata/mprov/local/HD1.1/mysqldb
    lrwxrwxrwx.  1 system_u:object_r:tmp_t:s0       root  root    13 2021-01-01 10:10 /var/tmp -> ../shared/tmp
    # ls --lcontext /var/lib/mysql
    lrwxrwxrwx. 1 system_u:object_r:appdata_t:s0   mysql mysql 34 2021-01-01 10:10 /var/lib/mysql -> /appdata/mprov/local/HD1.1/mysqldb

    Below is an example of a permissions/contexts on the symbolic link which is having an issue.
    # ls --lcontext -d /tmp /var/tmp /shared/tmp /var/lib/mysql
    drwxrwxrwt.  8 system_u:object_r:tmp_t:s0       root  root     12288 May  1 01:00 /shared/tmp
    drwxrwxrwt. 10 system_u:object_r:tmp_t:s0       root  root      6144 May 11 01:00 /tmp
    lrwxrwxrwx.  1 system_u:object_r:appdata_t:s0   mysql mysql       34 Apr 11 01:00 /var/lib/mysql -> /appdata/mprov/local/HD1.2/mysqldb
    drwxr-xr-x.  5 unconfined_u:object_r:tmp_t:s0   root  webusers  4096 May 11 01:00 /var/tmp
    # ls --lcontext /var/lib/mysql
    lrwxrwxrwx. 1 system_u:object_r:appdata_t:s0   mysql mysql 34 Apr 11 01:00 /var/lib/mysql -> /appdata/mprov/local/HD1.2/mysqldb
     
  3. Based on the on the problem above, the example shows an issue with /var/tmp. To resolve the issue with /var/tmp run the following command.
    mv /var/tmp /var/tmp.backup
    ln -s /shared/tmp /var/tmp
    reboot
  4. After the reboot, the issue should be resolved.
  5. Delete the temp file /var/tmp.backup with the following command:
    rm /var/tmp.backup
