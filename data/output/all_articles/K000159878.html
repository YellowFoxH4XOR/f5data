K000159878: Guided Configuration deployments missing or not visible in GUI on HA peer after upgrade

Type
Support Solution
Published
2026-02-04
Updated
2026-02-04
Applies to
  • BIG-IP
  • BIG-IP APM: 17.1.1
Source
https://my.f5.com/manage/s/article/K000159878

Description

After upgrading BIG-IP APM systems and Guided Configuration to newer versions, Guided Configuration deployments may become missing or inaccessible in the GUI on one device in an HA pair, while remaining visible on the other device.

Symptoms include:

  • "Not Found - The requested URL was not found on this server" error when accessing Access > Guided Configuration
  • Guided Configuration deployments visible in GUI on active device but not on standby device
  • Underlying configuration objects (virtual servers, access policies, pools, iRules) remain present and functional on both devices
  • Configuration sync shows devices are in sync at TMOS level
  • Error message during GC operations: "Config processor is not available: java.util.concurrent.TimeoutException: Unavailable"

Log messages:

info iAppsLX_save_pre[xxxxx]: Skipping f5-iappslx-access-framework iapp package that does not have iapp path: /var/config/rest/iapps/f5-iappslx-access-framework

Environment

  • BIG-IP APM version 17.1.1 or later
  • Platform: Any BIG-IP platform (including iSeries) running in HA configuration
  • Guided Configuration upgraded from version 3.0 to 10.0 (or other major version jumps skipping intermediate versions)
  • iAppLX packages (f5-iappslx-access-framework) installed
  • HA pair with sync-failover device group configured
  • Auto-sync or manual sync mode

Cause

The REST framework database, which stores Guided Configuration deployment metadata, does not automatically synchronize between HA devices through standard configuration sync. Upgrading Guided Configuration by skipping required intermediate versions (e.g., directly from 3.0 to 10.0) can result in loss of deployment visibility in the GUI, even though the underlying TMOS configuration objects remain intact and synchronized.

Recommended Actions

Follow Incremental Upgrade Path for Guided Configuration

Always upgrade Guided Configuration sequentially through supported intermediate versions to prevent deployment metadata loss:

  1. Identify your current GC version by navigating to Access > Guided Configuration
  2. Download required intermediate GC packages from F5 Downloads (https://my.f5.com/manage/s/downloads)
  3. Upgrade incrementally following the supported path: 3.0 → 5.0 → 7.0 → 9.0 → 10.0
  4. Do not skip major versions during upgrade

Important: You can only upgrade up to one or two major versions later than your current version.

Repair Missing Guided Configuration Deployments Using Package Reinstallation

If GC deployments are already missing after an improper upgrade, attempt package reinstallation:

On the affected device:

  1. Navigate to iApps > Package Management LX
  2. Uninstall all iAppLX packages (including f5-iappslx-access-framework)
  3. Do NOT manually reinstall packages
  4. Navigate to Access > Guided Configuration
  5. Allow the system to auto-install default packages for your BIG-IP version
  6. Verify if missing deployments become visible

If deployments remain missing, restart services:

tmsh restart sys service httpd tomcat restjavad restnoded

Synchronize REST Database Between HA Peers Using sslofix Tool

If GC deployments are visible on one device but not the peer after attempting package reinstallation, use the sslofix tool to manually synchronize the REST database:

Prerequisites:

  • Configure passwordless SSH access from local device to remote HA peer (refer to K13454)
  • Ensure the device with correct GC configuration is active
  • Verify devices are in sync at TMOS level before proceeding
  • Ensure you have the most recent configuration on the local device

Steps:

  1. Download the sslofix script from https://clouddocs.f5.com/sslo-troubleshooting-guide/sslofix.html
  2. Run diagnostic check using the management IP address of the peer:
  3. sslofix -D <device-group-name> -H <peer-management-ip> --diagnostic
  4. Review diagnostic output for any warnings or errors
  5. If diagnostics pass or show acceptable warnings, run the sync:
  6. sslofix -D <device-group-name> -H <peer-management-ip> --force
  7. The script will:
    • Stop restjavad on both devices
    • Remove REST Framework device certificates and conflicts
    • Generate new REST Framework device key-pairs
    • Restart restjavad and restnoded services
    • Initiate CMI sync operation

Verify GC deployments are now visible on peer device by navigating to Access > Guided Configuration

 

Important notes:

  • Use the management IP address (not self IP or floating IP) for the -H parameter
  • The script only affects the control plane; no production traffic impact expected
  • Some warnings during diagnostic checks may be acceptable; the script can still succeed

Additional Information

Troubleshooting sslofix Errors:

  • If you receive "Peer device must be a member of [device-group] device group!" error, verify you are using the management IP address (not self IP) for the -H parameter
  • If passwordless SSH is not configured, the script will fail; refer to K13454 for SSH configuration steps
