K000163376: F5 Distributed Cloud TLS Handshake Failures with Shared VIPs and Default Coalescing

Type
Support Solution
Published
2026-09-22
Updated
2026-09-22
Source

Description

Older Windows/.NET clients may receive TLS fatal handshake failures when multiple Distributed Cloud HTTPS Load Balancers share the same VIP and wildcard certificate, even when the configured cipher suites appear compatible.

Environment

  • F5 Distributed Cloud HTTPS Load Balancers.

  • Multiple virtual hosts using the same VIP, port, and wildcard certificate.

  • Load Balancers configured with different TLS security profiles and Default Coalescing.

  • Clients include older Windows/.NET systems, Java 8 clients, embedded systems, or appliance-based clients.

Cause

A shared Envoy listener combined virtual hosts using the same VIP and wildcard certificate. Default Coalescing allowed incompatible TLS parameters to be applied across Load Balancers, causing TLS handshake failures for older clients. CE logs reported “Security parameters mismatch between VirtualHosts.”

Answer/Recommended Actions

Do not assume a cipher-suite mismatch when command-line TLS tests succeed but the Windows/.NET application fails.

  • Confirm that the client can establish TLS 1.2 to the VIP and note the negotiated cipher.

  • Compare the command-line test results with the application or .NET handshake results.

  • Review CE logs for “Security parameters mismatch between VirtualHosts.”

  • For affected Load Balancers, change Coalescing from Default Coalescing to Strict Coalescing and retest the affected client.

  • Use Strict Coalescing individually for other Load Balancers accessed by older or compatibility-sensitive clients.

  • Use a dedicated VIP when Strict Coalescing is not suitable.

Additional Information

A successful TLS handshake followed by an HTTP 403 indicates that TLS negotiation completed and the 403 is an application or authorization response, not a TLS handshake failure.
