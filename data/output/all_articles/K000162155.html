K000162155: DNS Listener with Transparent Cache not forwarding queries for arpa zones to back end DNS pool members

Type
Support Solution
Published
2026-07-09
Updated
2026-07-15
Applies to
  • BIG-IP
  • BIG-IP DNS: 17.5.X, 17.5.1, 17.5.0, 17.1.3
Source
https://my.f5.com/manage/s/article/K000162155

Description

On BIG-IP DNS 17.1.3 and later, a DNS Transparent Cache configured with answer-default-zones no may still respond locally with NXDOMAIN to queries for _dns.resolver.arpa (and potentially service.arpa) instead of forwarding those queries to the configured back-end DNS pool members or local BIND, as expected.

This behavior persists across TMM restarts and is not resolved by restarting TMM.

Observed symptoms:

  • DNS queries for _dns.resolver.arpa (e.g., SVCB type queries per RFC 9462) sent to a listener backed by a Transparent Cache are answered locally by BIG-IP with NXDOMAIN.
  • The NXDOMAIN response includes an authority section referencing resolver.arpa. SOA localhost. nobody.invalid., indicating the response originates from Unbound's built-in local zone, not from the back-end pool.
  • The answer-default-zones no setting on the Transparent Cache profile has no effect on these zones.
  • The behavior is persistent — it is not triggered by a configuration change and is not resolved by restarting TMM.

Example of affected query/response

;; QUESTION SECTION:
;_dns.resolver.arpa.    IN SVCB

;; ANSWER SECTION:
(empty)

;; AUTHORITY SECTION:
resolver.arpa.  10800 IN SOA localhost. nobody.invalid. 1 3600 1200 604800 10800

;; status: NXDOMAIN

Environment

  • Product: BIG-IP DNS
  • Affected versions: 17.1.3, 17.1.3.1, 17.1.3.2, 17.5.x (Backlog)
  • Unaffected versions: 17.1.2 and earlier (Unbound 1.23.0 was not yet present)
  • Configuration: DNS Transparent Cache profile with answer-default-zones no
  • Query types affected: Any query type (SVCB, A, AAAA, NS, etc.) for zones resolver.arpa. and service.arpa., including subdomains such as _dns.resolver.arpa
  • Platform: All platforms running the affected BIG-IP DNS versions

Cause

Bug ID2377749

Answer/Recommended Actions

Apply an iRule to the DNS listener(s) to bypass the Transparent Cache for queries matching the affected zones. This allows those queries to be forwarded directly to the configured back-end pool members.

when DNS_REQUEST {
 if { [DNS::question name] ends_with "resolver.arpa" } {
 DNS::disable cache
 }
}

To also cover service.arpa or apply a broader scope to all .arpa queries:

when DNS_REQUEST {
 if { [DNS::question name] ends_with ".arpa" } {
 DNS::disable cache
 }
}

Considerations for the iRule workaround:

  • The Transparent Cache is completely bypassed for matched queries — every matching query is forwarded to the back-end pool on every request, even within the TTL validity period. There is no cache-hit benefit for these queries.
  • If a broad scope (ends_with ".arpa") is used, this includes all reverse PTR lookups (in-addr.arpa). In high-volume CGNAT environments, bypassing the cache for all reverse lookups may significantly increase back-end DNS pool member load. A narrower scope (ends_with "resolver.arpa") is recommended unless broader coverage is required.

Additional Information

This is a distinct issue from Bug ID1966405, which describes a triggered regression where PTR lookups for RFC1918 addresses return NXDOMAIN after a local zone configuration change, and which is resolved by a TMM restart. Bug ID2377749 is a persistent behavioral change that occurs regardless of any configuration change and is not resolved by TMM restart.
