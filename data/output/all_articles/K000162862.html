K000162862: TCP ZeroWindow Packets Sent by BIG-IP to a Pool Member

Type
Support Solution
Published
2026-08-11
Updated
2026-08-11
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000162862

Description

A packet capture shows a pool member packet labeled TCP Window Full, followed by a TCP ZeroWindow advertisement from BIG-IP on the server-side connection.

Environment

  • Product: BIG-IP LTM
  • Standard TCP profile used on client-side and server-side connections
  • BIG-IP operating as a full proxy between clients and pool members
  • Relevant TCP profile settings:
    • Auto-proxy-buffer-size: Disabled
    • Auto-receive-window-size: Disabled
    • Auto-send-buffer-size: Disabled
    • Proxy-buffer-high: 65535 bytes
    • Proxy-buffer-low: 32768 bytes
    • Send-buffer-size: 131072 bytes
    • Receive-window-size: 65535 bytes

Cause

The behavior is consistent with normal BIG-IP full-proxy content-spooling flow control.

When the server-side proxy buffer reaches the configured 'Proxy-buffer-high' threshold, BIG-IP stops advancing the receive window advertised to the pool member. If the pool member consumes the remaining advertised window, BIG-IP may advertise a TCP ZeroWindow until sufficient buffer space becomes available.

Possible contributing factors include:

  • A slower client-side connection or network path
  • Delayed client acknowledgments
  • Client-side packet loss or retransmissions
  • Different transfer rates between the server-side and client-side connections
  • TCP buffer or receive-window settings that are too small for the traffic pattern

TCP ZeroWindow packets alone do not indicate a BIG-IP failure. They indicate temporary server-side TCP backpressure while BIG-IP waits for buffered data to be forwarded through the client-side connection.

Answer/Recommended Actions

1- If application performance is normal and there are no delays, timeouts, or throughput problems, the TCP ZeroWindow packets can be treated as expected flow-control behavior.

2- If ZeroWindow events are frequent or prolonged, review the client-side connection for:

  • Delayed acknowledgments
  • Packet loss
  • Retransmissions
  • Reduced transfer rates
  • Client or network performance limitations

3- Create a custom server-side TCP profile based on the existing profile and evaluate appropriately larger values for:

  • proxy-buffer-high
  • proxy-buffer-low
  • receive-window-size

4- Alternatively, evaluate Automatic proxy-buffer and receive-window settings. These options dynamically calculate buffer-related values per connection based on network conditions.

5- Apply configuration changes to a test or limited-scope virtual server before broader deployment. Retain the existing TCP profile as a rollback option.

6- Monitor the following before and after changes:

  • TMM and system memory utilization
  • Concurrent connection count
  • Throughput
  • Response time
  • TCP ZeroWindow frequency and duration
  • Retransmissions
  • Application timeouts

7- Validate the results with a packet capture covering both client-side and server-side connections.

Note: Larger effective buffers can increase memory consumption per active connection. The impact depends on concurrent connections, traffic volume, burst rate, bandwidth, latency, and the amount of data being buffered. 

Additional Information

When the client-side connection drains data more slowly than the pool member sends it, BIG-IP buffers the data and applies backpressure to the pool member. The server-side receive window can reopen after the buffered data falls below the configured 'proxy-buffer-low' threshold.

Automatic buffer settings may help when network conditions vary, but they are not guaranteed to improve every traffic pattern. Manual tuning may be preferable for a stable and well-understood application.
