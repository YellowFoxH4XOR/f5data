Broken object level authorization

This is a security risk that occurs when authorization rules that dictate which object can be accessed by which users does not exist or are not applied properly. This allows users to manipulate API request parameters to access objects which they are not authorized to. Note that this is not related to authentication. You may be authenticating the API requests correctly but still be vulnerable to broken object level authorization. The most common cause for this is that server components do not track the client state and instead rely on object IDs in API requests, which can be easily manipulated.

This vulnerability can lead to data exfiltration enabling attackers to destroy or modify application data. In worst case scenarios, depending on the application, sensitive information such as account information, IDs, and passwords may be leaked, enabling attackers to take over accounts.

Broken object level authorization common weakness enumeration (CWE)

The following common weaknesses may increase the likelihood of attacks against your APIs:

  • CWE-284: Improper Access Control
  • CWE-285: Improper Authorization
  • CWE-639: Authorization Bypass Through User-Controlled Key

Broken object level authorization attack scenario

In the following attack scenario, the attacker manipulates the userid value in the URI path to retrieve user information from other users' account.

  1. The attacker uses a legitimate account and sends the following API request to retrieve their user information.

    GET https://api.example.com/v2/userid-1a-1234/userinfo
    Cookie: _userId=userid-1a-1234

  2. The attacker creates a second legitimate account, and using the userid, guesses and enumerates different userid values. They use a script or tool to send API requests, testing a range of userids, and receive sensitive information of other users.

    GET https://api.example.com/v2/userid-1a-1111/userinfo
    Cookie: _userId=userid-1a-1111
    GET https://api.example.com/v2/userid-zz-9999/userinfo
    Cookie: _userId=userid-zz-9999

  3. They expand the scope of the attack by manipulating the API request to delete users.

    DELETE https://api.example.com/v2/userid-1a-1111
    Cookie: _userId=userid-zz-9999

Secure your APIs against broken object level authorization attacks with F5 products

To protect your APIs, best practices recommend that you implement authorization mechanisms to check if the logged-in user has access to perform the requested action on the record in every function that uses an input from the client to access a record in the database.

Use BIG-IP APM to mitigate broken object level authorization attacks

Responsibility of preventing broken object level authorization tends to fall on the application server as it is closely related to the application code and logic. However, there are a lot of reasons to share, if not delegate, this responsibility to the API Gateway as well. The API Gateway sees all the parameters in the API request, can correlate object ID relationships, and most importantly, can manage user sessions.

To add a layer of protection for your APIs against broken object level authorization attacks, implement the following:

Note: For a specific example on how to configure the Per-request policy for this, refer to K11764434: Configure BIG-IP APM API protection session variables for secure API authorization

  • Authorization mechanisms to validate the API calls are authorized to perform what they are requesting for.

    The system processes API requests through Per-request policies. Through the Per-request policy flow, you can extract a range of information from the API request, assign them to subsession or perflow variables, and validate the values to ensure each request is authorized. To design and implement the authorization mechanism you want, use a combination of the following in Per-request policies based on your application logic:

    • Per-request policy branches
    • Subsession and perflow variables
    • Sub routine gating criteria

For example, you can enforce the following application logic to validate API calls:

An API request to read or modify an object, includes the azureID value in its path and this value must match the value in the JWT token included in the authorization header of the request.

  • User session tracking

    One of the biggest reasons for broken object level authorization attacks is the lack of user session tracking. On the same note, you can resolve many attacks by tracking user sessions. Use a combination of the following in Per-request policies based on your application logic to design and implement user session tracking:

    • BIG-IP APM subsession: This is a distinct ID created for each subsession for each distinct gating criteria value that you can use.
    • HTTP connector agent: This is used to communicate with external servers to make API calls or retrieve information.
    • iRules: These are used to manipulate data, headers, and so on.

For example, you can enforce the following application logic through tracking user sessions to secure against broken object level authorization:

In order to read or modify attributes of a purchase item, the user must have created the item in a previous API call. The API request must include a unique, non-guessable ID in the HTTP cookie or header that is made up of IDs such as the apm subsession ID combined with the ID of the object.
