K000134487: Identify the unknown DNS traffic generated by BIG-IP self-IP address

Type
Support Solution
Published
2023-05-05
Updated
2023-05-09
Applies to
  • BIG-IP
  • BIG-IP ASM: 16.1.2
Source
https://my.f5.com/manage/s/article/K000134487

Description

Steps to identify why your BIG-IP ASM/WAF may send DNS traffic to remote destinations in unexpected geo-locations.

Environment

  • security bot-defense signature
  • DNS traffic

Cause

Verify if the traffic could be related to nameservers of the domains listed under security bot-defense signature. If yes, then this traffic could be expected because the BIG-IP will have to perform reverse DNS lookups as part of bot-defense mechanism for the configured domains.

Note: In this example, Russia is the unexpected geolocation.

/config/bigip.conf:

security bot-defense signature /Common/Yandex {​

  category "/Common/Search Engine"

  domains {​ .yandex.com .yandex.net .yandex.ru }​

  factory-rule $M$V...

  risk na

  user-defined false

}​

security bot-defense signature /Common/YandexSearch {​

  category "/Common/Service Agent"

  factory-rule $M$t...

  risk na

  user-defined false

}​

​security dos bot-signature /Common/asm-hidden/ASM-search-engine-Yandex {​

  category /Common/asm-hidden/ASM-search-engines

  domains {​ .yandex.ru .yandex.net .yandex.com }​

  rule "headercontent:\"yandex\"; useragentonly; nocase;"

}

 

Run a packet capture and follow the traffic the DNS stream to the unknown destination IP(s). In below example 1.2.3.4 is the BIG-IP non-floating self-ip address and the destination IP is 87.250.250.1:

 

 1.2.3.4 → 87.250.250.1 84 61339 53 DNS OUT s1/tmm8 : Standard query 0x852f PTR 174.213.108.95.in-aDdr.aRpA OPT

 87.250.250.1 → 1.2.3.4 130 53 61339 DNS IN s1/tmm8 : Standard query response 0x852f PTR 174.213.108.95.in-addr.arpa PTR 95-108-213-174.spider.yandex.com OPT

 

Now perform a DNS lookup for the destination IP. You can do in by various means including dig utility.

 

$ dig -x 87.250.250.1

; <<>> DiG 9.11.3-1ubuntu1.18-Ubuntu <<>> -x 87.250.250.1

;; global options: +cmd

;; Got answer:

;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 56912

;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:

; EDNS: version: 0, flags:; udp: 4096

;; QUESTION SECTION:

;1.250.250.87.in-addr.arpa.    IN     PTR

;; ANSWER SECTION:

1.250.250.87.in-addr.arpa. 299 IN     PTR    ns3.yandex.ru.

 

And finally try a geo look-up for the returned ip-address which is the ip of one of the nameserver for 'yandex.ru' domain.

# geoip_lookup 87.250.250.1

Will attempt to lookup ip '87.250.250.1'

No database specified.

opening database in /usr/share/GeoIP/v2/F5GeoIP.dat

size of geoip database = 25559575, segments = 10061881, version = Copyright (c) F5 Networks Inc, All Rights Reserved GEOIP2 v1, 20220207

geoip_seek = 00b90125

geoip record ip = 87.250.250.1

country_code = RU

country_name = Russian Federation            <---

region_name = Moscow City

continent_code = AS

 

Please note, in above example, 'yandex' controls the location of its nameservers and no-one else including F5 can change this.

Recommended Actions

Check your bot defense logs as well as output of tmsh show net dns-resolver that exposes quite a lot of stats about these reverse lookups.
