Description

BIG-IP tenants running on F5OS appliances in an active/standby HA configuration experience complete loss of data plane connectivity when failed over from one host to another. The symptoms include:

  • All tenants function normally on one host but lose network connectivity when moved to the standby host
  • Interfaces show "up" status with no errors, but traffic does not pass
  • ICMP and other traffic to virtual servers, self-IPs, and pool members fail after failover
  • LAG (Link Aggregation Group) statistics show significant traffic differences between hosts (terabytes on working host vs. megabytes on non-working host)
  • ARP requests are visible on the F5OS layer but do not reach the peer device or upstream switch
  • ARP requests may be reflected back to the tenant (egress OUT s1/tmm1, immediately followed by ingress IN s1/tmm0)
  • After adding static ARP entries, traffic egresses the F5OS but no return traffic is received
  • Pool members remain down despite correct configuration
  • Qkview generation on the affected host is significantly slower than on the working host

Environment

  • Product: F5OS (R10600 appliances, C128)
  • F5OS version: 1.8.3
  • BIG-IP tenants: v17.5.1.3
  • Configuration: Active/Standby HA, each host running multiple BIG-IP tenants
  • Network: LAG (Link Aggregation Group) interfaces with LACP, multiple VLANs configured
  • Upstream Switch: Cisco with trunk/access ports and VLAN tagging
  • Recent actions: Tenant failover between hosts, VLAN configuration synchronization, interface troubleshooting, fiber reseating
  • Issue observed consistently when tenants are failed over to specific host

Cause

Misconfiguration on the upstream network switch. Packets egress the F5OS appliance correctly but are not received or processed by the switch, resulting in loss of data plane connectivity for tenants on the affected host.

Answer/Recommended Actions

Verify F5OS and Tenant Configuration

  1. Ensure all VLANs and interfaces are consistently configured across both F5OS hosts
  2. Remove any unnecessary VLAN assignments or interface configurations used during troubleshooting
  3. Verify tenant VLAN assignments match between hosts

Diagnose Network Path Issues

  1. Synchronize and compare counters:
    • On F5OS: Run reset counters all
    • On the switch: Reset interface counters for ports connected to the affected host
    • Compare egress counters on F5OS with ingress counters on the switch to identify silent drops
  2. Perform LACP member isolation:
    • Administratively down each LACP port member one at a time
    • Test if traffic flows correctly on remaining active links
    • This helps identify if the issue is isolated to a specific physical link
  3. Capture and analyze traffic:
    • Start packet captures on both F5OS hosts:

    system diagnostics tcpdump interface <VLAN_NAME> outfile <HOSTNAME>.pcap

    • Start packet captures on affected tenants:

    tcpdump -nni 0.0:nnn -s0 -w /shared/tmp/$(date +%Y%m%d_%H%M%S)_$HOSTNAME.pcap

    • Perform connectivity tests (ping virtual servers, self-IPs, pool members)
    • Review captures for ARP behavior and packet flow
  4. Test with static ARP entries (diagnostic only):
    • Add static ARP entries for pool members on affected tenants per K16221
    • Test if traffic can be forced through
    • This helps isolate whether the issue is ARP-related or deeper in the network path

Coordinate with Network Team

  1. Review and correct upstream switch configuration
  2. Check switch-side logs for:
    • Port flapping
    • LACP synchronization issues
    • CRC errors
    • Input/output drops
    • Error-disabled ports (e.g., UDLD empty echo)
  3. Verify switch ports are correctly configured for:
    • Trunk/access mode
    • VLAN tagging/untagging
    • LACP settings matching F5OS configuration
  4. Obtain switch-side packet captures to verify traffic ingress/egress

Physical Layer Verification

  1. Reseat SFPs and recertify fiber connections
  2. Verify cable integrity
  3. Confirm switch ports are not error-disabled

Resolution

Once the switch misconfiguration is identified and corrected, all tenants should regain data plane connectivity and HA functionality will be restored.

Additional Information

  • This issue was not related to F5OS or BIG-IP software bugs, but rather to upstream network infrastructure misconfiguration
  • The discrepancy between tenant MCPD reporting trunk DOWN while F5OS reports trunk UP is a key diagnostic indicator of network path issues
  • ARP requests being reflected back to the tenant (visible as OUT followed immediately by IN in the same capture) indicates a network path problem rather than an F5OS or BIG-IP issue
  • Significant differences in qkview generation time between hosts may indicate underlying system issues but were not the root cause in this scenario
  • Consistent configuration and close coordination between F5 and network teams is critical for troubleshooting HA environments
  • When troubleshooting, always collect diagnostics from both F5OS hosts and all affected tenants simultaneously to see the complete picture
