Description

  • Customers deploying CIS often raise a security concern: the BIG-IP credentials CIS uses are stored in a
    native Kubernetes `Secret`, which is only base64-encoded (not encrypted) at rest in etcd by default.
  • They ask whether CIS can instead source its BIG-IP credentials from an external secrets manager — For instance, from the **External Secrets Operator (ESO)** backed by **HashiCorp Vault**.
  • This article answers that question and provides the validated configuration.

Environment

  • F5 Container Ingress Services (CIS) (CRD mode)
  • F5 BIG-IP
  • External Secrets Operator (Hashicorp Vault, AWS Secrets Manager etc)

Cause

CIS is designed to consume native Kubernetes Secrets and does not interact directly with External Secrets Operators

Answer/Recommended Actions

  • CIS reads BIG-IP credentials from a native Kubernetes Secret (f5-bigip-ctlr-login). It does not interact directly with  any External Secret Store.
  • ESO is responsible for creating and continuously syncing the native Kubernetes Secret from the external provider (e.g., HashiCorp Vault). CIS consumes the secret transparently, regardless of how it was created or updated.
  • To implement this integration:
    • Deploy ESO and configure a ClusterSecretStore resource to connect to your external provider (e.g., HashiCorp Vault).
    • Create an ExternalSecret resource that references the ClusterSecretStore and targets the f5-bigip-ctlr-login Secret in the kube-system namespace.
    • Ensure the ServiceAccount used for Vault authentication is in the external-secrets namespace and that cross-namespace references are allowed by using a cluster-scoped ClusterSecretStore.
    • The BIG-IP user credentials (with Administrator role) must exist before CIS starts to avoid REST API lockouts due to failed logins.
    • Verify the integration by:
      • Checking the labels on the f5-bigip-ctlr-login Secret to confirm ESO management.
      • Reviewing ESO logs for successful reconciliation of the secret.
      • Decoding the secret data to confirm correct credential values.
      • Inspecting the external provider (e.g., Vault) to ensure the expected values are present.

Additional Information

  • CIS is agnostic to the source of the Kubernetes Secret; as long as the secret exists and is formatted correctly, CIS will function as expected
  • Using a cluster-scoped ClusterSecretStore is necessary for cross-namespace ServiceAccount references.
  • If the BIG-IP user does not exist or is misconfigured, repeated failed logins may trigger BIG-IP REST lockout.
