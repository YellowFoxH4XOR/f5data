Description

  • You want to use of "x-forward-host header" with your NGINX Ingress Controller.
  • When setting "x-forward-host header" using NGINX Custom resourec like virtualServer, the "x-forward-host header" value is not sent with the request to the upstream
  • On the other hand, you note, "x-forward-host header" value is set to the host in URL. 

Background

  Discussing "proxy_set_header" directive first

  • in Nginx-Plus and its derivative products like NGINX Ingress Controller, by default, "proxy_pass_request_headers" directive is turned on. 
    • this in turn mean, header fields of the original request are passed to the proxied server
  •  with the above directive enforced, proxy_set_header would then be used to redefine or append fields to the request header passed to the proxied server (upstream).
    • appended header is extracted from original client request.
    • in the event of this field being empty in the client's request header then nothing will be passed.
    • however, in such a case, Nginx Ingress Controller, by default appends/uses the $host variable 
    • the $host value equals the server name in the “Host” request header field or the primary server name if Host field is not present
  • you can find the same statement here.

Discussing proxy_set_header X-Forwarded-Host

  • as described above, proxy_set_header X-Forwarded-Host has the ingress controller set the value to $host
  • in addition, if one to 'exec' into Nginx controller pod and output the configuration, you find each location is appended with "proxy_set_header X-Forwarded-Host $host;" 
  • so, from the outset, "If x-forward-host header is NOT sent in request then, by default, it is set to the host in URL", summarize the above behavior

Important on X-Forwarded-Host and action.proxy.requestHeaders 

  • you can find the additional details here
    • If Ingress has been configured with action.proxy.requestHeaders this ensures that only ONE set of headers will be sent to the upstream server. 
    • In summary, by setting action.proxy.requestHeaders in the VirtualServer Custom Resource, NGINX Ingress will only send the specified headers that have been defined.
  • we also have a set of list that are configurable Headers       
  • here are the headers that can be set with Action.Proxy.RequestHeaders.Set.Header     

        $request_uri, $request_method, $request_body, $scheme, $http_, $args, $arg_, $cookie_, $host, $request_time, $request_length, $nginx_version, $pid, $connection, $remote_addr, $remote_port, $time_iso8601, $time_local, $server_addr, $server_port, $server_name, $server_protocol, $connections_active, $connections_reading, $connections_writing, $connections_waiting, $ssl_cipher, $ssl_ciphers, $ssl_client_cert, $ssl_client_escaped_cert, $ssl_client_fingerprint, $ssl_client_i_dn, $ssl_client_i_dn_legacy, $ssl_client_raw_cert, $ssl_client_s_dn, $ssl_client_s_dn_legacy, $ssl_client_serial, $ssl_client_v_end, $ssl_client_v_remain, $ssl_client_v_start, $ssl_client_verify, $ssl_curves, $ssl_early_data, $ssl_protocol, $ssl_server_name, $ssl_session_id, $ssl_session_reused, $jwt_claim_ (NGINX Plus only) and $jwt_header_ (NGINX Plus only).

Environment

  • NGINX Ingress Controller
  • x-forward-host header

Cause

  • None, Nginx works as designed

Recommended Actions

  • None, X-Forwarded-Host is NOT the list of configurable Headers, discussed above, and therefore can't be defined from within "action.proxy.requestHeaders" schema

With the above 

  • you can see below, we have two sets of proxy_set_header 'x-forwarded-host' entries
  • like
    • proxy_set_header 'x-forwarded-host' '$http_x_forwarded_host';
    • proxy_set_header X-Forwarded-Host $host;
  • but as discussed above, "only ONE set of headers will be sent to the upstream server"
  • and given we can't use "action.proxy.requestHeaders" to override proxy_set_header 'x-forwarded-host' as 'x-forwarded-host' is NOT one the allowed headers, we can't guarantee the use of location snippets also helps remove the limitation.
