Description

Bot Defense logs show that BIG-IP cannot confirm that the request came from a search engine.

Search Engine Verification Failed.
The system detected a bot that presented as a known search engine. Source IP Address reverse DNS checked failed.

 

A manual reverse lookup of the IP using nslookup or similar confirms that the bot is in fact a legitimate search engine bot.

Environment

  • Bot Defense

Cause

Search Engine Verification can fail under any of the following conditions:

  • No forward zone is configured in the DNS resolver.
  • The nameserver is not reachable through a TMM interface.
  • The DNS resolver is not configured for the route domain associated with incoming traffic or in the default route domain.

Recommended Actions

The DNS resolver object configured at Network > DNS Resolvers does not use the system's configured DNS servers. You must configure a forward zone in the resolver itself, and list your name server there.

For systems using multiple route domains, you can configure a DNS Resolver on the route domain associated with incoming traffic, or configure a DNS resolver on default route domain. Bot Defense selects the DNS resolver based on the incoming traffic route domain. If no resolver is configured for that route domain, Bot Defense attempts to use a resolver configured on the default route domain.

Here is an example of an incomplete DNS resolver configuration:

net dns-resolver /Common/scott-resolver {
    route-domain /Common/0
    randomize-query-name-case no
}

Now the forward zone is added:

tmsh modify net dns-resolver scott-resolver forward-zones replace-all-with { . { nameservers add { 9.9.9.9:53 } } }

The DNS resolver is now complete, and functional:

net dns-resolver /Common/scott-resolver {
    forward-zones {
        . {                             <---- Note the '.' name, this allows DNS queries for all names
            nameservers {
                9.9.9.9:53 { }          <---- This must be reachable via a TMM route
            }
        }
    }
    randomize-query-name-case no
    route-domain /Common/0
}

Verify the resolver conifguration

Run:

tmsh list net dns-resolver </Partition/dns-resolver_name>

After configuring the DNS resolver, you must ensure that the name server is accessed via a TMM route. It cannot use a management route.

Verify the route to the nameserver

For default route domain:

ip route get <name server ip>

For a non-default route domain, run the command in the specific route-domain context:

rdexec <route-domain id> ip route get <name server ip>

Verify DNS traffic

Ensure DNS Traffic is using a TMM route and not management interface. Run tcpdump from default route-domain to capture traffic from all configured VLANs and route-domains:

tcpdump -nni 0.0 host <name server ip>
tcpdump -nni eth0 host <name server ip>

Review dns-resolver statistics:

tmsh show net dns-resolver </Partition/dns-resolver_name>
 

You may need to add an explicit TMM route in order to correctly route the reverse lookup queries via a TMM route. For information about managing static routes, refer to:

  • K13833: Managing static routes in BIG-IP and BIG-IQ
