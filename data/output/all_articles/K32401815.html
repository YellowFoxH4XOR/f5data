Description

A standard virtual server access fails. When taken a tcpdump, it  shows BIGIP virtual server sends [RST, ACK] with reset cause as below : 

[F5RST: Policy action]

 Note: To be able to see the reset cause in tcpdump opened in Wireshark, please enable F5's ethernet trailer in Wireshark. Steps provided in article: K14812111: Configure Wireshark to read F5 Ethernet Trailers

Tcpdump opened in Wireshark will show a tcp flow similar to below between client IP address and virtual server IP:

Client  →  sends [FIN, ACK] to  →  virtual server 
virtual server → sends [ACK] to  →  Client 
virtual server → sends [FIN, ACK] to →  Client
Client → sends [ACK] to  →  virtual server
Client → sends  [TCP Dup ACK (previous ACK packet no from client)#1]  [ACK] to  →  virtual server
virtual server →  sends  [RST, ACK]  [F5RST: Policy action] to  →  Client 

Environment

  • Standard virtual server
  • Virtual server resets the connection with reset cause: [F5RST: Policy action]

Cause

After client and virtual server both sending FIN to initiate closing the connection, client acknowledged the FIN sent by BIG-IP virtual server,
Then no further communication is necessary at all, the conversation should have finished. Instead client sends another ACK [TCP Dup ACK] which is unexpected and confusing response to the BIGIP.  

In response BIGIP sends a RST to abort all further communication for this TCP session. If the client had continued to send packets in same TCP flow. the BIGIP would send an additional RST for each extra packet the client sends. In this situation, the behavior of the BIGIP is normal and expected. The issue : client is continuing to send data after the TCP close is completed.

Recommended Actions

  • Confirm above behavior by taking a packet capture on BIG-IP and take action accordingly. 
    K411: Overview of packet tracing with the tcpdump utility
  • Verify the configuration and network to determine if there are any abnormalities with the connection.
