K000161039: BIG-IP APM VPN with ACL packet logging, only "reject" ACL logs are generated and forwarded to syslog

Type
Support Solution
Published
2026-04-29
Updated
2026-04-29
Applies to
  • BIG-IP
  • F5 Distributed Cloud Services
  • BIG-IP APM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000161039

Description

When configuring BIG-IP APM VPN with ACL packet logging, only "reject" ACL logs are generated and forwarded to syslog (local or remote), while "allow" ACL logs are missing. This occurs even when the logging profile and log publisher are correctly configured, and packet logging is enabled on the ACL. The issue is typically seen in environments where layered (forwarding) virtual servers are present.

Symptoms:

  • "Reject" ACL logs appear as expected in /var/log/pktfilter and/or remote syslog.
  • "Allow" ACL logs are not present in /var/log/pktfilter or on the remote syslog server.
  • Packet logging is enabled on the ACL for both allow and reject actions.
  • Log publisher includes both remote HSL and local-syslog destinations.
  • No "allow" entries are found when searching logs for relevant session IDs.

Environment

  • BIG-IP APM
  • VPN Access Policy with ACLs configured for packet logging (both allow and reject)
  • Log publisher configured with both remote HSL and local-syslog destinations
  • Layered (forwarding) virtual servers present in the configuration
  • iRules in use on virtual servers

Cause

Layered forwarding virtual servers may intercept VPN traffic before it reaches the internal Network Access listeners responsible for ACL enforcement. As a result, ACLs are not evaluated for the traffic, and "allow" log entries are not generated or forwarded. This is expected behavior when traffic does not traverse the correct listener for ACL enforcement.

Answer/Recommended Actions

To ensure ACLs are evaluated and "allow" logs are generated and forwarded:

  1. Verify Logging Profile and Publisher:
    • Ensure the log publisher includes both remote HSL and local-syslog destinations.
    • Confirm the log level for apm-acl is set to info in the APM log setting.
  2. Check ACL and Access Profile Assignment:
    • Confirm the correct ACL is assigned to the Access Policy and that packet logging is enabled for both allow and reject actions.
  3. Force ACL Evaluation in Layered VS:
    • Add the following iRule to the affected layered (forwarding) virtual server(s):

    when CLIENT_ACCEPTED {
    ACL::eval
    }

    • This forces the ACL to be evaluated for each new connection, ensuring that both allow and reject actions are logged as expected.
  4. Monitor Logs:
    • After applying the iRule, monitor /var/log/pktfilter and /var/log/apm for allow log entries.
    • Confirm that allow logs are also forwarded to the remote syslog server.
  5. Reference Articles:
    • Review F5 KB articles for further details on ACL enforcement and logging behavior.

Additional Information

  • This behavior is expected when layered forwarding virtual servers are used and ACL evaluation is not explicitly triggered.
  • The same configuration may work on other platforms if the traffic flow differs and does not involve layered VSs.
  • Adding ACL::eval to the iRule ensures consistent ACL enforcement and logging regardless of the virtual server architecture.
