Description

F5 sending reset with F5RST: Policy action, without a policy applied.

This is observed in a packet capture, or in the /var/log/ltm log file when the tm.rstcause.log database variable is enabled.

Environment

  • Virtual server

Cause

This type of reset can occur under various conditions, not just when an LTM traffic policy is applied. Additional troubleshooting is required to determine the exact cause.

Recommended Actions

Investigate the configuration in full and review a packet capture to determine if there are any abnormalities with the connection.

Additional Information

Here is one example where this type of reset can occur, shortly after a four-way TCP connection termination:

10.10.10.25 → 10.10.20.34 TCP IN  s1/tmm1 : 55201 → 80 [FIN, ACK]
10.10.20.34 → 10.10.10.25 TCP OUT s1/tmm1 : 80 → 55201 [ACK]
10.10.20.34 → 10.10.10.25 TCP OUT s1/tmm1 : 80 → 55201 [FIN, ACK]
10.10.10.25 → 10.10.20.34 TCP IN  s1/tmm1 : 55201 → 80 [ACK]
10.10.10.25 → 10.10.20.34 TCP IN  s1/tmm1 : 55201 → 80 [ACK]
10.10.20.34 → 10.10.10.25 TCP OUT s1/tmm1 : 80 → 55201 [RST, ACK] [F5RST: Policy action]

In this example, the client 10.10.10.25:55201 initiated closing the connection with a FIN, ACK sent to the virtual server 10.10.20.34:80.

The BIG-IP acknowledges this with an ACK, then sends its own FIN, ACK.

The client then sends a final ACK, acknowledging the FIN sent from the BIG-IP.

At this point, the socket is expected to be in a CLOSED state on both sides of the connection.

However, the client sent an additional segment with the ACK flag set. The BIG-IP responded to this with a TCP reset, reset cause [F5RST: Policy action].
