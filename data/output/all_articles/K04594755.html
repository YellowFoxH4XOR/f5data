Issue

Description

GRE (Generic Routing Encapsulation) is a tunneling protocol that can encapsulate a wide variety of network layer protocols inside virtual point-to-point links over an IP network. Due to its nature, allowing huge payloads to be encapsulated and sent, adding processing overhead of IP defragmentation to impact a target, it is abused and used in GRE Flood attacks.

BIG-IP Local Traffic Manager (LTM) using the Packet Filter Feature can be configured to mitigate a GRE Flood by Source and Destination Address matching.

Environment

  • BIG-IP LTM Module is provisioned

Cause

GRE Flood traffic is suspected to be hitting the BIG-IP System

Recommended Actions

Determine the source of UDP flood traffic

The source of the GRE flood traffic can be determined using a couple of methods, which could be from an external source - a report from an external monitoring tool - or a packet capture are a few examples. During an actual GRE flood traffic event, a packet capture would be beneficial to understand the type of GRE traffic being flooded to the BIG-IP.

  1. Run a packet capture using the tcpdump utility from the BIG-IP Console or SSH session

    tcpdump -nni 0.0:nnn udp -s0 -w /var/tmp/gre_flood.pcap -C 5 -W 2 -vv

    Clarification from tcpdump man page (man tcpdump):

    • n, nn, or nnn
      Capture with increasing amounts of internal debugging information appended to the end of each packet.  Requires the use of -s0 to actually acquire and display the information.
    • -C    
      Before  writing  a  raw  packet to a savefile, check whether the file is currently larger than file_size and, if so, close the current savefile and open a new one.  Savefiles after the first savefile will have the name specified with the -w flag, with a number after it, starting at 1 and continuing upward.  The units of file_size are millions of bytes (1,000,000 bytes, not 1,048,576 bytes).
    • -W    
      Used  in  conjunction  with  the -C option, this will limit the number of files created to the specified number, and begin overwriting files from the beginning, thus creating a ’rotating’ buffer.  In addition, it will name the files with enough leading 0s to support the maximum number of files, allowing them to sort correctly.
    • -s
      Snarf snaplen bytes of data from each packet rather than the default of 65535 bytes. Setting snaplen to 0 sets it to the default of 65535, for backwards compatibility with recent older versions of tcpdump.

      A resulting filename of the packet capture file can be gre_flood.pcap0, gre_flood.pcap1, gre_flood.pcapx.
       
  2. Determine the top source IP/s sending the GRE traffic and from which vlan it was received using the tshark command

    tshark -nnnr /var/tmp/gre_flood.pcap1 -T fields -e ip.src -e vlan.id | sort -rn | uniq -c | sort -rnk 1

    Note: Wireshark can also be used to review the packet capture and determine the top source IP/s and vlan

Create a Packet Filter rule

Packet filters enhance network security by specifying whether a BIG-IP system interface should accept or reject certain packets based on criteria that you specify. Packet filters enforce an access policy on incoming traffic. They apply to incoming traffic only. This compliments the BIG-IP default deny nature, where an additional layer of protection to BIG-IP listeners are available.

Packet Filter rules require the Protocols, Source Hosts and Networks, Destination Hosts and Networks and Destination Port information in order to create the desired rule.

Impact of procedure: Configuring packet filter rules that are inappropriate for your environment may result in traffic disruption.

  1. From the BIG-IP Configuration utility (Web GUI), Navigate to Network  ››  Packet Filters : Rules  ››  New Packet Filter Rule..., on Enable Packet Filtering option, set it to Enabled

    Important: Changing the default value of the Unhandled Packet Action property can produce unwanted consequences. Before changing this value to Discard or Reject, make sure that any traffic that you want the BIG-IP system to accept meets the criteria specified in your packet filter rules.

  2. Provide the following information:

    Configuration

    Name - Provide a descriptive name for the packet filter rule    
    Order - Specifies the order in which the system applies the packet filter, if you configure more than one packet filter rule    
    Action - Specifies how the system should process a packet that matches the criteria specified in the packet filter rule. GRE flood needs to be prevented, thus, set this to discard         
    VLAN / Tunnel - from the previous procedure, #2 of Determine the source of udp flood traffic, select from the dropdown list the name of the vlan   Logging    - Enable logging for troubleshooting and verifying the action taken by the packet filter

    Filter Expression 

    Filter Expression Method - Use 'Build Expression' option    
    Protocols - select UDP from the list    
    Source Hosts and Networks - from the previous procedure, #2 of Determine the source of udp flood traffic, add the IP addresses or networks of udp flood traffic source     
    Destination Hosts and Networks - if you wish to deny access to certain destination or any destination, set the appropriate IP address or network address     
    Destination Port - set the destination port

    Note: K13383: Configuring CIDR Network Addresses for the BIG-IP packet filter states that if you need to configure packet filtering to block Classless Inter Domain Routing (CIDR) network block addresses, this should be done from the tmsh utility.

    Example packet filter using the tmsh command to define network addresses:

    create /net packet-filter block_gre order 1 action discard rule "( src net 1.1.1.1/32 ) and ( dst net 2.2.2.2/32 )"

    Note: Remember to save the changes using the save sys config command.

  3. If logging is enabled, you can review the packet filter generated logs from the following location:

    From the Configuration utility, navigate to System  ››  Logs : Packet Filter and then disable logging after you confirm the packet filter rule is blocking the UDP flood traffic as expected.
