K98432520: Native RDP resource connections are not using SNAT pool IP after upgrade to 15.1.x

Description

After upgrading to v15.1.x, the settings configured in the Route Domain and SNAT Selection agent in the access policy VPE are not getting applied for Native RDP resource connections.
Instead of using the SNAT pool IP, it uses the SNAT automap IP. Depending on how your environment is configured, this may or may not work.

The reason for that, is that starting with 15.1.0, ActiveX RDP are not supported anymore (its usage has been deprecated due to browsers moving away from it).

When ActiveX was supported, the RDP was established within the browser itself (no rdp file was downloaded) and the Access Policy Route Domain and SNAT Selection agent configuration was applied to the RDP connection.
Now, with Native RDP client, the RDP is launched independently from the browser that established the actual APM session, therefore the Route Domain and SNAT Selection agent configuration cannot be applied to the RDP connection.

Environment

  • BIG-IP APM Access Policy that has the Route Domain and SNAT Selection agent configured and assigned in the access policy

Cause

  • Bug ID 969097

Recommended Actions

There is no fix available for it.

However, there are two ways you can workaround this issue:

Solution A: Applying same SNAT pool for all users

By creating a layered VS for the affected RDP resource/s:

1. create a layered virtual, of type Forwarding (IP) with the same IP address as the RDP server and listening on port 3389.
example: 172.16.20.40:3389
2. leave other settings with default ones. Just assign the SNAT pool (the one that you have configured in the Route Domain and SNAT Selection agent in the VPE) on this layered VS
3. after creating the layered VS, navigate to Local Traffic  ››  Virtual Servers : Virtual Address List. select the VS IP for the layered VS you created previously (172.16.20.40) and uncheck ARP. Then click Update.

Solution B: Applying different SNAT pool for different population of users

By creating multiple APM VS:

1. create an individual Access HTTPS VS for each population of users and assign a different SNAT pool object directly on each VS
2. create an HTTPS LTM VS that would receive traffic for all and then send the traffic over to the different Access VS created in 1. based on the Host header value (site1.example.com, site2.example.com, etc.)
3. create an iRule (such as the one below) to route the traffic to the different Access HTTPS VS and attach it to the HTTPS LTM VS:

when HTTP_REQUEST {
  if { [HTTP::host] == "site1.example.com" } {
     virtual "/Common/VS_partners"
     return
  }
  if { [HTTP::host] == "site2.example.com" } {
     virtual "/Common/VS_internal"
     return
  }
}
