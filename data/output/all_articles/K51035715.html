Topic

This article covers how to create a certificate signed by your organization's certificate authority (CA) for the Configuration utility. To create your own local root CA to sign the certificate for the Configuration utility instead, refer to the following article:

  • K42531434: Replacing the Configuration utility's self-signed device certificate with a CA-signed device certificate

You should consider using this procedure under the following conditions:

  • You want to avoid SSL certificate alert messages when connecting to the Configuration utility.
  • You want to use a certificate singed by your organization's CA for the Configuration utility.

Description

The Configuration utility uses a self-signed SSL device certificate by default. When you access the Configuration utility, most web browsers generate an alert message and pause the connection until a web browser security exception is made. You can make a single security exception and access the Configuration utility without future alerts. The web browser security icon will continue to show the Configuration utility as an insecure site. However, if you prefer to not make a web browser security exception and have the web browser security icon indicate a secure site, you can do the following:

  • Replace the Configuration utility's self-signed device certificate with a CA-signed SSL certificate
  • Ensure the CA signing certificate from your organization exists in the client web browser's Trusted Root CA certificate store

Note: If your BIG-IP system is managed by a BIG-IQ system, replacing the BIG-IP Configuration utility's self-signed SSL certificate does not affect the trust between the managed BIG-IP system and the BIG-IQ system.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • Administrative access to the BIG-IP system to use the openssl command and to copy files
  • Access to submit the Certificate Signing Request (CSR) from the BIG-IP system to your organization's CA

Procedures

Create a device certificate signing request

In this procedure, optionally create a custom openssl.cnf file to add Subject Alternative Name (SAN) details to your certificate, and use the openssl command to create a certificate signing request (CSR). You submit the CSR to your organization's CA to sign.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP command line.
  2. To create a directory to store the certificate and accompanying files, enter the following command:

    mkdir /var/tmp/my_gui_cert

  3. Change to the new directory by entering the following command:

    Note: After this step, you can skip to step 7 if you do not want to add SAN or Extended Key Usage (EKU) extensions to the CSR.

    cd /var/tmp/my_gui_cert

  4. Copy the default openssl.cnf file to the new directory you created by entering the following command:

    cp /etc/pki/tls/openssl.cnf /var/tmp/my_gui_cert/custom_openssl.cnf

  5. To add SAN details to the CSR, edit the custom_openssl.cnf file by adding the sections below to the end of the file using the following command syntax:

    Important: Specify the fully-qualified domain name (FQDN) of your BIG-IP as the first name in the alt_names section then add your alternative names.

    [ req_ext ]
    subjectAltName = @alt_names

    [ alt_names ]
    DNS.1 = <FQDN 1>
    DNS.2 = <FQDN 2>
    DNS.3 = <FQDN 3>
    ...
    DNS.x = <FQDN x>
    ...
    IP.1 = <IP_addr 1>
    IP.1 = <IP_addr 2>
    IP.1 = <IP_addr 3>
    ...
    IP.x = <IP_addr x>

    For example:

    [ req_ext ]
    subjectAltName = @alt_names

    [ alt_names ]
    DNS.1 = www.example.com
    DNS.2 = test.example.com
    DNS.3 = mail.example.com
    IP.1 = 192.0.2.1
    IP.2 = 198.51.100.254
    IP.3 = 2001:DB8::1

  6. To include EKU extensions in your certificate request, edit the custom_openssl.cnf file by adding the section below to the end of the file using the following command syntax:

    Important: The CA that signs your request, determines the extensions to add and can choose not to copy your requested extensions into the signed certificate or the CA may already add desired extensions and including them in the request is not necessary. F5 recommends contacting your CA to confirm what will be included.

    [ req_ext ]
    extendedKeyUsage = <purposes>

    For example:

    [ req_ext ]
    extendedKeyUsage = serverAuth, clientAuth

    If you also included a subjectAltName, the added section appears similar to the following example:

    [ req_ext ]
    subjectAltName = @alt_names
    extendedKeyUsage = serverAuth, clientAuth

  7. Save the changes you made to custom_openssl.cnf.
  8. Within the current working directory /var/tmp/my_gui_cert, generate a CSR that uses the custom config file using the following command syntax:

    Note: Omit the last two command options, -config custom_openssl.cnf and -reqexts req_ext if you are not adding any request extensions.

    openssl req -new -sha256 -nodes -newkey rsa:<Key Size> -keyout <FQDN>.key -out <FQDN>.csr -config custom_openssl.cnf -reqexts req_ext

    For example, the following command generates a CSR with 2048-bit key size for the www.example.com domain (to generate a 4096-bit key, use rsa:4096):

    openssl req -new -sha256 -nodes -newkey rsa:2048 -keyout www.example.com.key -out www.example.com.csr -config custom_openssl.cnf -reqexts req_ext

  9. Respond to the prompts to fill in the details for the certificate.

    Note: Unless required by your organization, you can leave the CSR challenge password blank.

    Important: The Common Name must match the first name in the alt_names section and what you enter in the web browser's URL field when accessing the Configuration utility.

  10. Verify the content in the CSR before submitting it to the CA using the following command syntax:

    openssl req -noout -text -in <name of CSR file>

    For example:

    openssl req -noout -text -in www.example.com.csr

  11. If you made a mistake, delete the CSR and key files and repeat steps 8 through 10.
  12. Transfer the CSR file from the BIG-IP system. For more information, refer to: K175: Transferring files to or from an F5 system.
    a. If necessary for submission, to view and copy the raw content of the CSR file to your clipboard, use the following command syntax:

    cat <name of CSR file>

    For example:

    cat www.example.com.csr

  13. Submit the CSR to your organization's internal CA for signing. You should receive a certificate file and possibly a chain certificate file in return.

Replace the BIG-IP system self-signed device certificate

To back up and replace the BIG-IP system's self-signed device certificate with your CA-signed certificate, perform the following procedure.

If the target device is a BIG-IP DNS system, connectivity between remote BIG-IP systems will fail until the new signed certificate is exchanged. You should perform this procedure during a planned maintenance period. For more information about exchanging certificates, refer to the DNS sync group peer procedures in K16951115: Changing the BIG-IP DNS system device certificate using the Configuration utility.

Note: SSL certificates signed by a third-party CA must include both the client authentication (clientAuth) and server authentication (serverAuth) EKU extensions, to allow use by both server and client applications. For example, the big3d process operates as a server (serverAuth) while the gtmd process operates as a client (clientAuth). Contact your CA to confirm that the aforementioned purposes are added to signed certificates. For more information, refer to K7717: BIG-IP DNS and Link Controller support for third-party SSL certificates.

Impact of procedure: Communication with other BIG-IP devices will fail until the new certificate is exchanged. There will be no impact to high availability (HA) features, such as traffic groups and device groups.

  1. Log in to the BIG-IP command line.
  2. Transfer the CA-signed certificate you obtained to the /var/tmp/my_gui_cert directory you created on the BIG-IP system. If applicable, copy the chain certificate. For more information, refer to: K175: Transferring files to or from an F5 system.
  3. Verify that the CA-signed certificate matches the associated private key by comparing the MD5 output. To do so, use the following syntax:
    Important: Do not skip this step. When you replace the httpd certificate and key using bash in step 5, the system does not validate that the key and certificate match. If they don't match, httpd will not run after the restart in step 8 and you will lose Configuration utility access.

    openssl x509 -in /var/tmp/my_gui_cert/<CA-signed cert>.crt -pubkey -noout | md5sum; openssl rsa -in /var/tmp/my_gui_cert/<private key>.key -pubout | md5sum

    For example:

    openssl x509 -in /var/tmp/my_gui_cert/www.example.com.crt -pubkey -noout | md5sum; openssl rsa -in /var/tmp/my_gui_cert/www.example.com.key -pubout | md5sum

  4. Make backups of the existing self-signed certificates and keys of the target BIG-IP system by entering the following two commands:

    cp /config/httpd/conf/ssl.crt/server.crt /config/httpd/conf/ssl.crt/server.crt.orig
    cp /config/httpd/conf/ssl.key/server.key /config/httpd/conf/ssl.key/server.key.orig

  5. When replacing the device certificate in this step, you overwrite the default self-signed device certificate files, /config/httpd/conf/ssl.crt/server.crt and /config/httpd/conf/ssl.key/server.key. Overwriting the files ensures the system is compatible with iQuery and ensures there will be no ConfigSync conflicts. To overwrite the existing self-signed SSL certificate and key with the new CA-signed SSL certificate, key, and when applicable copy a chain certificate, on the BIG-IP system, use the following command syntax:

    cp /var/tmp/my_gui_cert/<CA-signed cert>.crt /config/httpd/conf/ssl.crt/server.crt
    cp /var/tmp/my_gui_cert/<private key>.key /config/httpd/conf/ssl.key/server.key
    cp /var/tmp/my_gui_cert/<chain cert>.crt /config/httpd/conf/ssl.crt/

    For example, to copy the new CA-signed SSL certificate and chain certificate named www.example.com.crt, www.example.com.key, and www.example.com-chain.crt to a BIG-IP system, enter the following command:

    cp /var/tmp/my_gui_cert/www.example.com.crt /config/httpd/conf/ssl.crt/server.crt
    cp /var/tmp/my_gui_cert/www.example.com.key /config/httpd/conf/ssl.key/server.key
    cp /var/tmp/my_gui_cert/www.example.com-chain.crt /config/httpd/conf/ssl.crt/

  6. If applicable, for proper iQuery communication you must append any chain or root certificates in the /config/httpd/conf/ssl.crt/server.crt file. To do so, use the following command syntax:

    cat /config/httpd/conf/ssl.crt/<chain cert>.crt >> /config/httpd/conf/ssl.crt/server.crt

    For example:

    cat /config/httpd/conf/ssl.crt/www.example.com-chain.crt >> /config/httpd/conf/ssl.crt/server.crt

  7. If applicable, configure httpd to use the new combined chain certificate file to secure the Configuration utility using the following command syntax:

    tmsh modify sys httpd ssl-certchainfile /config/httpd/conf/ssl.crt/<combined cert>.crt

    For example:

    tmsh modify sys httpd ssl-certchainfile /config/httpd/conf/ssl.crt/server.crt

  8. To load the new certificates into the running configuration, restart the httpd process using the following command syntax:

    tmsh restart sys service httpd

  9. In most situations your organization's root certificate should be pre-installed on organization workstations so that web browsers will trust the BIG-IP with the CA-signed certificate. However, if you need to install the root certificate to the web browser's trusted root CA certificate store, follow the Updating the web browser Trusted Root CA certificate store procedure in K42531434: Replacing the Configuration utility's self-signed device certificate with a CA-signed device certificate.
