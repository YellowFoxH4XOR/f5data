K000139100: Troubleshooting high mcpd CPU usage driven by SNMP polling

Description

High amounts of SNMP polling can cause the snmpd process to constantly pull data from statistic tables via mcpd, making the mcpd process very busy. A troubleshooting technique is shown which may help to see if SNMP polling is causing high mcpd CPU use.

When this is occurring snmpd CPU use may be 5-10 times lower than mcpd use so it may not be very obvious this is the cause of an issue with mcpd CPU use.

Note the issue may surface on one peer of a cluster and the other be fine. It may surface after a reboot or upgrade, simply due to that changing the polling patterns of the network management systems on the device polled. What matters is all the polling from whatever source within a short duration.

A straightforward and safe workaround, is to tune snmpd by increasing the number of cache slots to 16, as shown in the workaround section of Bug ID 1006449.

Environment

  • Any BIG-IP being polled via SNMP with risk factors shown below
  • Large configurations which leads to large statistics tables
  • Many network management systems polling system
  • Short polling intervals

Cause

If data is being polled from more than four tables within a short period of time by one or more SNMP clients, such as network management systems (NMS) this can make mcpd CPU very high especially if the tables are large in size.

Large configurations often have large stats tables for virtual servers, nodes, pools, pool members, monitors and so on.

This happens because snmpd maintains caches for four tables by default. If more than that are concurrently polled it will constantly be refilling these cache slots by pulling data from the source tables via mcpd.

Recommended Actions

A straightforward and safe workaround, is to tune snmpd by increasing the number of cache slots to 16, as shown in the workaround section of Bug ID 1006449.

You can use mcpd statistics to see if processing messages for snmpd is a major contributor to mcpd CPU use.

You can use statistics from the mcp_transaction_stat table to see if snmpd is one of the large users of mcpd. If it is it may well sort very near the top when sorted on total_transactions, but with a bit more processing with awk we can get a sense of the total transaction CPU use by multiplying that by the average time for a transaction. The units aren't very important, just the relative values. If you then sort on this use you can see if it's plausible snmpd could be driving mcpd use. It may still still be a factor though, even if not the most important. The technique is generally useful for troubleshooting mcpd CPU use, not just specific to that driven by snmpd.

Starting with the current values

The column titles will not show, but were added by hand for clarity. The fourth column below is created by awk and represents use, and this is also the sort key.
There's nothing magical about showing only top three, but probably if snmpd isn't fairly close to top it may not be driving mcpd CPU.

Change directory to where the stat files are kept (or on a BIG-IP use -d blade instead of -f mcp_stat_segment or use the full path -f /var/tmstat/blade/mcp_stat_segment)

cd /var/tmstat/blade

/var/tmstat/blade$ tmctl -q -f mcp_stat_segment mcp_transaction_stat -s user,total_transactions,process_time_mean | awk '{use=$2*$3; print $0"   "use}' | sort -k 4 -rn | head -3
user                            total_transactions process_time_mean
------------------------------- ------------------ -----------------

%snmpd                                   164897519                46   7585285874
%statsd                                     512773              5124   2627448852
%bigd.2                                    1975331               579   1143716649

Note: The user may be snmpd or %snmpd. If checking how it varies over time, as shown below, make sure to use the correct version in the user= query filter.

In this case it's very clear that snmpd and stats related activity are big users of mcpd CPU. Usually the use falls of very quickly as you show more rows so typically the first few rows account for nearly all mcpd CPU use.

For completeness, the command below would give a similar output sorted on total_transactions, showing top three, and this does show column titles:
/var/tmstat/blade$ tmctl -f mcp_stat_segment mcp_transaction_stat -s user,total_transactions,process_time_mean -OK total_transactions -L 3

Looking at snapshot data

You can also look at the snapshot data, and this is advisable because you can see what is happening recently. On a system with high uptime and a long mcpd process uptime conditions my change over time and total transactions over a long period may be misleading if they have. For instance new SNMP NMS may have been set up recently to poll BIG-IP and cause the overload described previously.

Change directory to /shared/tmstat/snapshots/blade0/public/3600 (or 86400). On a multi-blade capable system replace blade0 with the primary blade number, often 1.

cd /shared/tmstat/snapshots/blade0/public/3600

Pick a snapshot file and put in place of <blade0-public-3600-20XX-XX-XXTXX:00:00> placeholder below

/shared/tmstat/snapshots/blade0/public/3600$ tmctl -q -f  <blade0-public-3600-20XX-XX-XXTXX:00:00> mcp_transaction_stat -s user,total_transactions,process_time_mean -OK total_transactions | awk '{use=$2*$3; print $0"   "use}' | sort -k 4 -rn | head -3
snmpd                           160005038     85   13600428230
%statsd                           1048994   1752   1855357488
%cmi-mcpd-peer-/Common/ltm2        711704    816   580750464

This output is from a different system to the first set of output and shows user snmpd rather than %snmpd.
You can also see how this is increasing over time in the snapshot files:

Note:  You may need to change user=snmpd, to user=%snmpd

/shared/tmstat/snapshots/blade0/public/3600$ tmctl -D . mcp_transaction_stat -s time,user,total_transactions,process_time_mean user=snmpd | awk '/^2/{p3 ? delta=($3-p3)*$4 : delta=""; p3=$3; print $0"   "delta;next}{print $0}'

The last column here is a computation of use over the interval from previous row, so delta in total_transactions times current process_time_mean.

You can change the user= filter to pick out other mcpd users, for example %statsd and compare the use.
It can also be compared with the total current value divided by number of uptime hours or days to see if it has been roughly consistent.

If snmpd is large user of mcpd time then follow the tuning shown in workaround section of Bug ID 1006449 to see if that helps. It may be also a good idea to review how much polling is happening from where and whether so much data is needed, and whether intervals can be adjusted.
