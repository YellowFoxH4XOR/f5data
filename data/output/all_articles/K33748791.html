Issue

It is normal for the audit2allow executable to log a compile error message and subsequently create a Type Enforcement (TE) file containing only a module header when there are no denials present in an auditd log file.

It is helpful to always probe the system, before committing, to see if SELinux is the cause of any system or application issues. To determine this, ask the following questions:

  1. Is the problem there when I temporarily set SELinux mode to permissive?

    # sudo setenforce 0

  2. Is the problem there when Enforcing is on?

    # sudo setenforce 1

If the answer to 1) is Yes, then it’s unlikely to be an SELinux issue.

If the answer to 1) is No and the answer to 2) is Yes, then the issue is caused by SELinux. In this case, you need to go through the procedure again to find the corresponding denial and create a policy to allow it. Because of this, when starting, you should not modify auditd logs but rather leave them as they are because it is very easy to miss a denial event.

Furthermore, SELinux does not search for issues. Rather, it reacts to events and decides whether they should proceed. This means that you may have missed an earlier denial, possibly because the event had not occurred earlier, so there was no message logged from which a policy could be created. Therefore, it is important that you perform as much work in permissive mode as possible and only commit to the permanent change of enforcing when you are absolutely certain it is safe to do so because a mistake could permanently lock up your Linux host if, for example, SELinux is blocking a service like sshd from starting up and it may be your only access point in to the Linux host.

There are precautions that you can take to prevent the loss of the Linux host in case of a mistake.

As long as SELinux is in permissive mode or you've only temporarily set enforcing, the Linux host at worst needs only to be restarted to revert back to permissive mode to recover the system. However, when the change is made permanent by editing the file /etc/selinux/config, it is often best to take precautions to avoid the loss of the Linux host because mistakes may be made.

There are several ways to recover the Linux host, but the most straightforward is to boot into console (tty) mode, edit the /etc/selinux/config file, and restart again. Another option is to take a snapshot of your Linux host before you enable enforcing. If, however, you don't have access to console mode or can't take snapshots, the following method is a simple approach that you can adopt in your policy development lifecycle and will prevent loss of the Linux host. However, this approach does not cover all possible scenarios.

  1. Create the following script in your SElinux administrator’s home directory and call it check-selinux.sh. In this example, the directory is /home/ubuntu/bin.

    #!/bin/bash
    date_str=$(date)
    echo "Selinux restore service: ${date_str}" > /home/ubuntu/bin/selinux_restore_service.log
    CONF=/etc/selinux/config
    selinux_mode=$(sudo getenforce 2> /dev/null)
    if [ "${selinux_mode}" = "Enforcing" ] || [ "${selinux_mode}" = "Permissive" ]; then
                    sudo chmod -R a+w /etc/selinux/
                    sudo sed -e "s/^SELINUX=.*$/SELINUX=permissive/" < $CONF > $CONF.new
                    sudo mv $CONF.new $CONF
                    sudo chown root /etc/selinux/config
                    sudo chgrp root /etc/selinux/config
    fi

    while true
    do
            sleep 5
    done

  2. Make it executable:

    sudo chmod a+x check-selinux.sh

  3. Create a service file called /etc/systemd/system/check-selinux.service:

    [Unit]
    Description=Selinux Monitor service
    After=network.target
    StartLimitIntervalSec=0
    [Service]
    Type=simple
    Restart=always
    RestartSec=1
    User=ubuntu
    ExecStart=/home/ubuntu/bin/check-selinux.sh

    [Install]
    WantedBy=multi-user.target

  4. Install and start the new service

    sudo systemctl enable check-selinux
    sudo service check-selinux start

This service is simple and on each restart sets the SELinux mode to permissive in the /atc/selinux/config file. It does not take effect until the second restart. This allows you to continue working without risking the Linux host.

On Rhel7.x, there is a bug in the default docker which prevents etcd and Flannel resource directories from being labelled correctly for SELinux. This issue shows as a “permission denied” message in the startup logs of the corresponding docker containers.

For etcd, perform the following (-a option ensures the process is listed even if it has exited):

# docker ps -a | grep etcd
fc04cbf0ed40        2c4adeb21b4f            "etcd --advertise-..."   9 minutes ago        Up 9 minutes                                                                                       k8s_etcd_etcd-ip-192-0-2-2.us-west-2.compute.internal_kube-system_3208211c427f97d8806ebd529e98ea80_29
30825d5bd7ad        k8s.gcr.io/pause:3.1    "/pause"                 9 minutes ago       Exited (0) 10 minutes ago                                                                          k8s_POD_etcd-ip-192-0-2-2.us-west-2.compute.internal_kube-system_3208211c427f97d8806ebd529e98ea80_5

Next get the etcd container, here it is fc04cbf0ed40, and execute the following at the terminal:

docker logs fc04cbf0ed40
...
2021-06-15 11:10:32.849276 C | mvcc/backend: cannot open database at /var/lib/etcd/member/snap/db (stat /var/lib/etcd/member/snap/db: permission denied)
panic: cannot open database at /var/lib/etcd/member/snap/db (stat /var/lib/etcd/member/snap/db: permission denied)
...

If the logs contain the previously indicated message or similar, this is an indicator that the corresponding directory /var/lib/etcd has not been labelled correctly and that SELinux is blocking the docker container runtime from accessing it. The domain of the docker container runtime is container_t, so, in principle, the directory needs to have its SELinux context updated to allow docker to access it. You can do this by entering the following command:

sudo chcon -R -t container_file_t /var/lib/etcd

For Flannel, the process is very similar. In this case, the error message is similar to the following:

cp: can't create '/etc/cni/net.d/10-flannel.conflist': File exists

To fix the issue, enter the following command at the terminal:

sudo chcon -R -t container_file_t /etc/cni

On Ubuntu 18.04, there is a known bug in the default systemd process v236, which prevents SELinux and docker working together. The issue has been resolved in systemd v239+. In this case, the only solution is to upgrade systemd.
