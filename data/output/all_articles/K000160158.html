K000160158: LTM error using AWS CloudHSM -- only when doing secp384r1

Type
Support Solution
Published
2026-02-26
Updated
2026-02-26
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000160158

Description

When creating a Certificate Signing Request (CSR) or self-signed certificate on BIG-IP using AWS CloudHSM with ECDSA key type and the secp384r1 elliptic curve, the operation fails with the error:

Key management library returned bad status: -18, A vendor error has occurred.

The following errors appear in /var/log/ltm:

err iControlPortal.cgi[21743]: error: fips-codec109 Exceeded maximum DSA sign attempts.

err iControlPortal.cgi[21743]: error: fips-codec109 FIPS ECDSA sign error. FIPS 0xffffffff : Unknown

err iControlPortal.cgi[21743]: 01960023 fips_ecdsa_sign(): mod_err = 0xffffffff

err iControlPortal.cgi[21743]: 01960005 netHSM: Shared memory error [Failed to fetch result].

err pkcs11d[22777]: 01960111 C_Sign: pkcs11_rv=0x00000006, CKR_FUNCTION_FAILED.

Other ECDSA curves (prime256v1) and key types (RSA) work as expected. The command tmsh run sys crypto nethsm-test passes all tests including ECDSA_SECP384R1 tests.


Environment

  • BIG-IP version 17.5.1 or later (with AWS CloudHSM SDK5 support)
  • AWS CloudHSM Client version 5.16.1 (cloudhsm-pkcs11-5.16.1-1.el7.x86_64.rpm)
  • FIPS mode enabled
  • Certificate/CSR generation using:
    • Key type: ECDSA
    • Curve: secp384r1
    • Method: GUI (System › Certificate Management › Traffic Certificate Management › SSL Certificate List › Create)


Cause

BIG-IP uses SHA256 as the default signing algorithm for certificate signing and CSR generation. When using the secp384r1 elliptic curve in FIPS mode, NIST FIPS 186-4 compliance requirements mandate a minimum hash algorithm strength of SHA384 for this curve size (384 bits).

The mismatch between BIG-IP's default SHA256 and the FIPS-required SHA384 minimum causes the signing operation to fail in the FIPS cryptographic module when interfacing with AWS CloudHSM. The error occurs specifically during the fips_ecdsa_sign() operation, resulting in C_Sign: CKR_FUNCTION_FAILED from the PKCS#11 interface.

Note: This issue is specific to FIPS mode operations with AWS CloudHSM when using secp384r1. Other curves like prime256v1 (256-bit) work correctly because SHA256 meets the minimum requirement for that curve size.


Answer/Recommended Actions

Resolution:

A fix is available that corrects the signing algorithm selection logic to use appropriate SHA algorithms based on the elliptic curve being used in FIPS mode.

  1. Contact F5 Support to request the fix for your specific BIG-IP version against ID2220353
  2. After installing the fix, CSR and certificate generation with ECDSA secp384r1 will function correctly

Workaround (if fix cannot be immediately applied):

Use alternative key configurations that are compatible with the current implementation:

  • ECDSA with prime256v1 curve (256-bit)
  • RSA key types (2048-bit or 4096-bit)

These alternatives work correctly with AWS CloudHSM in FIPS mode.


Additional Information

Verification Steps:

Before opening a case, verify AWS CloudHSM connectivity and basic functionality:

# Test CloudHSM connectivity

tmsh run sys crypto nethsm-test


# Expected output should show PASS for all tests including:

# [ECDSA_PRIME256v1_SHA256]: Pass

# [ECDSA_SECP384R1_SHA256]: Pass (but CSR generation will still fail)

# [ECDSA_SECP384R1_SHA384]: Pass

Important Notes:

  • AWS CloudHSM SDK3 is no longer supported; use SDK5 (client version 5.16.1 or later)
  • The nethsm-test utility passing ECDSA_SECP384R1 tests does not indicate CSR generation will work, as it tests different cryptographic operations
  • This issue only affects certificate/CSR creation; existing secp384r1 certificates imported into CloudHSM can be used normally for SSL/TLS operations

Related Error Messages:

If you see these additional messages, they are also symptoms of this issue:
