K000163438: Traffic Interruption During F5 WAF for NGINX Policy-Bundle Swaps

Type
Support Solution
Published
2026-09-28
Updated
2026-09-28
Applies to
  • NGINX Products
  • F5 WAF for NGINX: 5.14.0
Source
https://my.f5.com/manage/s/article/K000163438

Description

Changing the active WAF policy bundle during continuous traffic can trigger an NGINX reload and WAF plugin reconnection. In-flight requests may be interrupted and return:

  • HTTP status 000
  • curl exit code 52 — Empty reply from server
  • In some cases, curl exit code 7 — Couldn't connect to server

Relevant log messages may include:

signal 1 (SIGHUP) received ... reconfiguring

APP_PROTECT ... "event": "configuration_load_start"

APP_PROTECT ... compilation status: successful

"GET / HTTP/1.1" 000 0

"GET / HTTP/1.1" 200 22

Environment

  • F5 WAF for NGINX
  • NGINX Ingress Controller
  • Continuous HTTP traffic to a WAF-protected backend
  • Active policy changed through spec.waf.apBundle
  • Target policy bundle already present on the filesystem

Cause

This behavior is associated with bug Bug ID WAFMC-15390.

During a policy-bundle swap and NGINX reload, the WAF enforcer can interrupt an in-flight transaction while workers reconnect to the WAF plugin. With the default enforcer action of drop, the affected transaction can be dropped, resulting in an empty response and HTTP status 000.

The behavior can depend on the policy-bundle content. The specific policy element responsible may not be isolated, and regenerating the policy bundle may prevent reproduction.

Recommended Actions

Install a F5 WAF for NGINX release containing the fix for Bug ID WAFMC-15390.

The fix requires the enforcer action to be set to pass in the NGINX http context:

http {
app_protect_enforcer_drop_action pass;
}

When using NGINX Ingress Controller, configure the directive through the HTTP snippets configuration:

http-snippets: |
app_protect_enforcer_drop_action pass;

Validate the resulting NGINX configuration and reload the deployment according to the normal NGINX Ingress Controller operating procedure.

Additional Information

  • Generate and validate a fresh policy bundle before switching the active bundle.
  • Avoid reusing a policy bundle that reproduces the interruption.
  • If the issue persists, compare the reproducing and non-reproducing policy configurations and their generation metadata.
  • Retain the default drop behavior when strict WAF enforcement is required, and investigate the policy configuration instead of enabling pass.

The pass setting is fail-open behavior. If an in-flight transaction is interrupted during a policy reload or WAF plugin reconnection, the transaction is released to the client instead of the connection being dropped. The affected transaction may therefore reach the client without completing WAF enforcement.

The default drop behavior prioritizes WAF enforcement but can produce empty replies during this transition.

A policy-bundle swap can trigger an NGINX SIGHUP, WAF configuration compilation, worker reconfiguration, and WAF plugin reconnection even when the bundle already exists on the filesystem.
