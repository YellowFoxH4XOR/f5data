Known Issue

Modifying the IP Encapsulation type within a pool configuration may cause the mcpd process to restart on secondary blades.

This issue occurs when all of the following conditions are met:

  • You have a multi-bladed VIPRION system.
  • You use the Configuration utility to modify the IP Encapsulation type within a pool configuration.

Impact

The VIPRION system temporarily fails to process traffic while the mcpd process restarts on all secondary blades.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The mcpd process restarts on all secondary blades and logs error messages to the /var/log/ltm file that appear similar to the following example:

    err mcpd[12345]: 01020036:3: The requested pool profile (49825) was not found.
    err mcpd[12345]: 01070734:3: Configuration error: Configuration from primary failed validation: 01020036:3: The requested pool profile (49825) was not found.

  • Restarting the mcpd process may cause the other daemons to restart; other daemons rely on the mcpd process to communicate with each other.

Workaround

To work around this issue, modify the IP Encapsulation type using the Traffic Management Shell (tmsh) instead of the Configuration utility. To do so, use the following procedure:

Impact of workaround: Modifying the Encapsulation type may impact the traffic through the tunnel, and F5 recommends testing any such changes during a maintenance window.

  1. Log in to the tmsh utility by typing the following command:

    tmsh

  2. Modify the IP Encapsulation type using the following command syntax:

    modify /ltm pool <pool_name> profiles replace-all-with {IP Encapsulation type}

    For example, you can use the following tmsh command to modify the IP Encapsulation type 'gre' profile to the 'ipip' type for the 'http-pool' pool:

    modify /ltm pool http-pool profiles replace-all-with { ipip }
