K000159551: Nessus Scans Detect Weak Ciphers on BIG-IP Despite TLS 1.2 Configuration

Type
Support Solution
Published
2026-01-14
Updated
2026-01-14
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000159551

1. Description

Nessus vulnerability scans report weak ciphers on BIG-IP systems even though the configuration shows only TLS 1.2 and above are enabled. When attempting to apply more restrictive SSL profiles with stronger cipher strings to virtual servers, application connectivity breaks. This issue occurs because:

  • Cached SSL sessions may cause scanners to detect previously negotiated weak ciphers
  • Cipher mismatches exist between BIG-IP Server SSL profiles and backend server capabilities
  • The cipher strings in Client SSL and Server SSL profiles may still include weak ciphers

2. Environment

  • BIG-IP LTM version 17.5.1 or similar
  • Client SSL and Server SSL profiles attached to virtual servers
  • SSL session caching enabled in SSL profiles (default configuration)
  • Backend servers supporting TLS 1.2
  • Nessus or similar vulnerability scanning tools

3. Cause

Weak cipher detection persists due to cached SSL sessions that retain information about previously negotiated cipher suites. Even after updating SSL profile configurations to exclude weak ciphers, scanners may continue to report vulnerabilities until the SSL session cache is cleared. Additionally, overly restrictive cipher strings in Server SSL profiles may not match the cipher capabilities of backend servers, causing application connectivity failures.

4. Recommended Actions

Clear SSL Session Cache

  1. Temporarily disable SSL session caching:
  2. tmsh modify ltm profile client-ssl <profile_name> cache-timeout 0
  3. tmsh modify ltm profile client-ssl <profile_name> cache-size 0
  4. Re-enable caching after clearing:
  5. tmsh modify ltm profile client-ssl <profile_name> cache-timeout 3600
  6. tmsh modify ltm profile client-ssl <profile_name> cache-size 262144
  7. Alternatively, perform a failover to clear the cache

Update Cipher Strings

  1. Use the following recommended cipher string for Client SSL profiles to exclude weak ciphers:
  2. DEFAULT:!SSLv3:!MD5:!EXPORT:!RC4:!DH:!DHE:ECDHE+AES:!CAMELLIA:!ECDHE-RSA-AES128-CBC-SHA:!ECDHE-RSA-AES256-CBC-SHA:!AES128-SHA
  3. Test the cipher string before applying to production:
  4. tmm --clientciphers 'DEFAULT:!SSLv3:!MD5:!EXPORT:!RC4:!DH:!DHE:ECDHE+AES:!CAMELLIA:!ECDHE-RSA-AES128-CBC-SHA:!ECDHE-RSA-AES256-CBC-SHA:!AES128-SHA'
  5. For Server SSL profiles, test cipher string compatibility:
  6. tmm --serverciphers '<cipher_string>'

Test Backend Server Cipher Support

  1. Identify which ciphers your backend servers support:
  2. openssl s_client -connect <backend_server_ip>:<port> -tls1_2 -cipher '<cipher_name>'
  3. Adjust the Server SSL profile cipher string to match backend server capabilities while maintaining strong ciphers in the Client SSL profile

Verify Protocol Configuration

  1. Confirm only TLS 1.2 and above are enabled:
  2. tmsh run util clientssl-ciphers TLSv1_2
  3. tmsh run util clientssl-ciphers TLSv1_3
  4. Check the cipher configuration on virtual servers:
  5. tmsh list ltm virtual <virtual_server_name> profiles

Validate Changes

  1. After making configuration changes and clearing the SSL session cache, test application connectivity
  2. Re-run Nessus or vulnerability scans to confirm weak ciphers are no longer detected

5. Additional Information

When using openssl s_client to test SSL/TLS connections, the output may show "New, TLSv1/SSLv3" which refers to the cipher suite family designation, not the actual negotiated protocol version. The actual protocol in use is displayed in the "SSL-Session" section under "Protocol". For example:

New, TLSv1/SSLv3, Cipher is ECDHE-ECDSA-AES256-GCM-SHA384

...

SSL-Session:

Protocol : TLSv1.2

Cipher : ECDHE-ECDSA-AES256-GCM-SHA384

In this example, TLS 1.2 is the negotiated protocol, despite the "TLSv1/SSLv3" label appearing earlier in the output.

The Client SSL profile controls encryption between clients and the BIG-IP, while the Server SSL profile controls encryption between the BIG-IP and backend servers. These profiles can have different cipher strings to accommodate different security requirements and backend server capabilities.
