Description
BIG-IP 11.5.0 introduced split planes (sometimes called HTSplit) functionality which uses separate logical cores for Data Plane and Control/Analysis Plane on the same physical core. As these hyperthreads share a common physical core, a watchdog prioritization process, Idle Enforcer, was also added to ensure the Data Plane under high usage is not adversely affected by Control/Analysis Plane usage at the same time.

When the Idle Enforcer starts, it writes a log message to /var/log/kern.log in the format:
info kernel: ltm driver: Idle enforcer starting - tid: <pid> cpu: <core ID X>/<core ID Y>
When the Idle Enforcer stops, it writes a similar log entry:
info kernel: ltm driver: Idle enforcer exiting - tid: <pid> cpu: <core ID Z>

An instance of the Idle Enforcer runs on each Control or Analysis Plane core on the BIG-IP. The first instance of the core ID ("core ID X") in the starting message is the core which Idle Enforcer should be activated on. The starting message also contains the second instance of core ID ("core ID Y") which is the current CPU, writing the log message and performing the action. The third instance of core ID ("core ID Z") found in the exiting message is the core which ran the Idle Enforcer. The starting and exiting messages both share the same tid (Process ID).

Besides having matching tid values, the cores in the starting and exiting message pairs should match. Either all three core IDs will be the same (for example 3/3 and 3) or the first and third will match (5/1 and 5). In most circumstances the two core IDs in the starting message will match, resulting in all three core IDs referencing the exact same odd-numbered core.

Environment

  • 11.5.0 or later
  • scheduler.splitplanes.ltm db key set to true (default)
  • Sufficient Data Plane CPU usage (default 80%) to trigger Idle Enforcer for long enough (default 100ms)
  • without heavy use of ASM module, as this suspends Idle Enforcer activity as its data plane runs across all cores

Cause
Once CPU usage on a the Data Plane hyperthread reaches 80% for at least 100ms, the Idle Enforcer is activated on the corresponding Control or Analysis plane hyperthread running on the same physical core. For example Data Plane hyperthead core 0 and Control Plane hyperthread core 1 are both on the first physical core. While active, the Idle Enforcer starts cycling between pausing the odd core hyperthread and running it for a shorter duration, thereby lowering contention with the peer even hyperthread core for use of the physical core. Typically the cycle is 4ms pause, 1ms run, and will cycle like this while the even core is above 80%, usually for periods substantially less than one second.

Pausing the Control/Analysis Plane hyperthread briefly does not typically impact functionality. Sufficient halting may result in reduced and insufficient capacity of the control plane to meet demand. 
 

Recommended Actions

  1. It's usually best to judge Idle Enforcer impact from detailed per core CPU graphs that show CPU mode. As it is implemented as a kernel activity, Idle Enforcer shows as extra system mode use on the odd numbered core. The proportion of time the even numbered core spends above 80% determines how much system mode use is added on the peer odd numbered core. When fully engaged on an even numbered core it will add up to 80% as system mode on the peer odd numbered core, when engaged half the time just an extra 40%. This system mode use isn't actual use, the core is halted, and normal system mode use will still be present. Even cores may spike above 80% for fractions of a second triggering idle enforcer activity, but the even core use may average out to less than 80% as the graph averages out over a longer time period such as 10s or more.
  2. Determine if the Idle Enforcer messages occur nearly continuously and for seconds or longer at a time or less frequently and for periods under a second.
  3. Determine if the duration between an Idle Enforcer's starting and exiting messages is sub-second or a longer period of time.
  • Less frequent Idle Enforcer messages can typically be ignored as a transient Data Plane usage spike.
  • Longer duration Idle Enforcer periods may be an indication the Data Plane is exceeding it's capacity and action needs to be taken more urgently. Additionally, the probability of Control/Analysis Plane process impact is higher if more or all control plane cores are limited at same time. It's important the control plane load fits within the capacity available after the maximum likely amount of idle enforcer is present. Take care to use long enough intervals for monitors, consider running https monitors in tmm if a hardware SSL offload device is available.
