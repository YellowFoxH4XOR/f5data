Known Issue

This is the result of a known issue. There is a discrepancy between the mechanism used by the BIG-IP system to reap idle connections and the idle time reported by command line utilities. Connections are made of both client-side and server-side flows, and are reaped when both flows have reached the configured idle timeout value. However, when listing active connections using the bigpipe utility or the tmsh shell, the idle time is reported for the client-side flow only.

Note: The idle timeout configured for the client-side connection may not always be the same as the one configured for server-side connection. This depends on the traffic management object handling the connection and its configuration. For example, a virtual server could be using different client and server protocol profiles, and each profile could have been configured with a different idle timeout value. For more information, refer to K7606: Overview of BIG-IP idle session timeouts.

Note: You can use the bigpipe conn show all command or the tmsh show sys connection all-properties command to list all active connections in a verbose format. The two commands display the same information, but the data is laid out differently. The examples included in this article were generated using the bigpipe utility. For more information, refer to the Bigpipe Utility Reference Guide and the Traffic Management Shell (tmsh) Reference Guide.

For example, the following command output, which represents one entry in the BIG-IP system connection table, only includes one idle time:

VIRTUAL 10.0.0.100:http <-> NODE 192.168.1.10:http TYPE any 1/1
CLIENTSIDE 10.0.0.22:57565 <-> 10.0.0.100:http
(pkts,bits) in = (29, 1679) out = (69, 102064)
SERVERSIDE 192.168.1.1:57565 <-> 192.168.1.10:http
(pkts,bits) in = (82, 118128) out = (44, 2463)
PROTOCOL tcp UNIT 1 IDLE 12 (300) LASTHOP internal 00:50:56:8e:60:8c

The IDLE value in the output indicates the number of seconds that the client-side connection has been idle, and the value immediately following in parentheses indicates the idle timeout configured for the client-side connection. The idle time and idle timeout values for the server-side connection are not displayed. For completeness of reporting, the output should include the idle time and idle timeout values for both the client-side connection and the server-side connection.

F5 Product Development tracked this issue as ID 341904, and it was fixed in BIG-IP 11.0.0 and Hotfix-BIGIP-10.2.4-817.0-HF7, issued for BIG-IP 10.2.4.

For information about upgrading, refer to the BIG-IP LTM, ASM, PSM, Link Controller, WebAccelerator, APM, WOM, or Edge Gateway release notes.

For information about installing a hotfix for version 10.x systems, refer to K10025: Managing BIG-IP product hotfixes (10.x).

Additional information

While this issue is cosmetic, it may lead to situations where connection table entries appear to have exceeded their configured idle timeout value. For example, the following output demonstrates a connection which appears to exceed its configured idle timeout value:

VIRTUAL 10.0.0.100:http <-> NODE 192.168.1.10:http TYPE any 1/1
CLIENTSIDE 10.0.0.22:48967 <-> 10.0.0.100:http
(pkts,bits) in = (4, 177) out = (3, 483)
SERVERSIDE 192.168.1.1:48967 <-> 192.168.1.10:http
(pkts,bits) in = (25, 1375) out = (25, 1029)
PROTOCOL tcp UNIT 1 IDLE 2484 (300)

LASTHOP internal 00:50:56:8e:60:8c

The idle timeout in the previous example appears to be set to 300 seconds, and the connection appears to have been idle for 2484 seconds. However, since these values represent only the client-side connection flow, we can infer that the server-side connection flow has not yet exceeded its configured idle timeout value. If both connection flows are configured with the same idle timeout value, this behavior usually occurs when the back-end server is configured to send TCP Keep-Alive packets, but the client is not sending any traffic. In this case, the connection is still active because the server-side flow never reaches the configured idle timeout value. This behavior is also evidenced by the higher pkts and bits counters on the server-side flow. This particular connection is reaped by the BIG-IP system only if the back-end server stops sending Keep-Alive packets and the server-side flow remains idle longer than the configured server-side idle timeout.

Note: There are other reasons why connections may exist after the idle timeout expires. For more information, refer to K5401: Connection reaping will occur within an 8.4 second window around the idle timeout.
