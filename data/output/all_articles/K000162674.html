Description

Due to the layers involved when tracking down potential ARP issues capturing ARP traffic may need to be done at multiple points. This is due to the varying capture planes and to the platform architecture.

Environment

The r5000/10000/12000 are fundamentally different from the r2000/4000 series and the Velos mutli-blade system. Because of this each of the three platform types are treated differently.

 

Cause

This article covers the FPGA-based forwarding architecture used by these higher-end rSeries platforms.

 

The key distinction is that the tenant does not have the same direct physical-interface visibility as an r2000/r4000 tenant. The differences are even greater with the Velos system.

 

Answer/Recommended Actions

Using an R5600 for an example, your would capture dataplane ARP at the F5OS-A host/appliance layer using the F5OS CLI—not by running tcpdump directly from the F5OS bash shell.

 

Note: To run these commands you will log in as admin, but that means from the ssh shell there is no access to root. It is often easier to login as root and then su admin from there (use quit to move back to root). That will allow you to move back and forth from bash to F5OS and back from one shell. That way it works very much like going back and forth on a classic BIG-IP between bash and TMOS.

 

  1. Log into the device as an administrator and run:system diagnostics tcpdump outfile <name of the capture>.pcap bpf "arp"
    For example:
    system diagnostics tcpdump outfile r5600-host-arp.pcap bpf "arp"
  2. Run it long enough to catch the traffic needed for review. It can be very verbose so be cognizant that and catch what you need.
  3. Once the traffic has been captured there are 2 ways to retrieve it.
    1. Via the GUI go to SYSTEM SETTINGS > File Utilities > Base Directory :: diags/shared :: tcpdump and download the file.
    2. Via the CLI
      1. Log in to the command line on the rSeries system as the admin user (or su admin if you have logged in as root already).
      2. To export the use the following syntax...file export protocol <https | scp | sftp> local-file diags/shared/<tcpdump_filename> remote-host <host_address> remote-file <path/to/remote_file> username <user>
        1. For example, to export the /var/shared/example_capture.pcap file to the /tmp/ directory of the remote host at 10.10.10.100 using scp protocol, enter the following command: file export protocol scp local-file diags/shared/example_capture.pcap remote-host 10.10.10.100 remote-file /tmp/example_capture.pcap username admin Note: To disable remote system identity verification, use the insecure option to the file command.
      3. Note: To disable remote system identity verification, use the insecure option to the file command.
      4. To check the status of the file transfer, enter the following command: file transfer-statusWhen complete, your output is similar to the following example:3    |Export file|SCP     |diags/shared/example_capture.pcap                         |10.10.10.100       |/tmp/example_capture.pcap                          |         Completed|

A capture can also be done on a specific front-panel interface or LAG:

  1. Use the actual F5OS interface name, such as a port/subport or LAG:system diagnostics tcpdump interface "10.0" outfile r5600-interface-10-arp.pcap bpf "arp"
    Or:
    system diagnostics tcpdump interface LAG1 outfile r5600-lag1-arp.pcap bpf "arp"
    1. The interface-specific form is preferred on busy systems. F5 warns that rSeries interfaces can operate at high rates, so filtering to arp and selecting the relevant interface helps avoid unnecessary packet drops. 
    2. outfile should appear before bpf; otherwise F5OS may report a filter syntax error. KB K80685750 documents the syntax and output location.

Getting one on the tenant is pretty standard to what would be done on any BIG-IP.

  1. From an SSH session using the bash shell the syntax would look something like this...tcpdump -s0 -nni 0.0:nnn -w /var/tmp/r5600-tenant-arp.pcap arp

Note: For troubleshooting traffic between two tenants or two appliances, start captures concurrently on the relevant F5OS hosts and tenants, reproduce the issue—for example, ping the peer or affected gateway—and run the capture for at least one minute.

 

Additional Information

There are a couple of important distinctions that should be considered:

•    F5OS host:
system diagnostics tcpdump ...
•    BIG-IP tenant:
tcpdump ... 0.0:nnn ...
Do not use a host-level 0.0 capture as a substitute for an interface capture when you need to verify packets actually entering or leaving the R5600 front-panel port. For ARP analysis in Wireshark, a useful display filter is:
arp
Or, for a specific IP address something like this should work:
arp.dst.proto_ipv4 == <IP-address> or arp.src.proto_ipv4 == <IP-address>
