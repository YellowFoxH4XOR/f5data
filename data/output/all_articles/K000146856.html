Description

You want to know how Host Header rewrites work.

Environment

  • F5® Distributed Cloud HTTP Load Balancer (LB)

Cause

The incoming Host header does not match any of the values configured under Domains or the CNAME record value for the virtual host, resulting in the request being rejected by the HTTP Load Balancer.

Answer/Recommended Actions

An incoming request to a HTTP LB will be rejected with an HTTP 404 error if the incoming Host header does not match any of:

  1. The values configured under Domains
  2. The CNAME record value for the virtual host, (e.g. ves-io-xxxx-....volterra.com)

Host rewrite is enabled by default, i.e. any incoming Host header will be stripped and replaced with a new Host header matching the FQDN of the configured origin pool.

 

Explanation

You have a LB with the domains listed as

   "domains": [
      "www.example.com",
      "*.gov-example.com"
    ],

Requests to the LB's CNAME with either the exact or wildcard domain names are allowed. Others will get an HTTP 404;

$ curl -LIS http://ves-io-123.volterra.us -H "www.example.com"
HTTP/1.1 200 OK

$ curl -LIS http://ves-io-123.volterra.us -H "Host:www.gov-example.com"
HTTP/1.1 200 OK

$ curl -LIS http://ves-io-123.volterra.us -H "Host:www.net-example.com"
HTTP/1.1 404 Not Found

 

Additional Information

Additional Questions

  • Q: Is the only way to disable Host Rewrite by configuring a simple route and disable it there?
    • A: Here are few options that illustrate how to use host rewrite:
      • In the origin pool, if you have configured a SNI to be used, the SNI becomes the host header.
      • In the origin pool, if you have configured use_host_header_as_sni, then the domain itself becomes the host header.
      • You can also use routes configuration instead of origin pool and enable host_rewrite.
  • Q: If the origin server is set to IP address, is Host Rewrite automatically disabled ?
    • A: It depends on the tls configuration of your origin pool, as explained above.
  • Q: What is the order of processing? If Service Policies operate on the Host header, are these operations done before the rewrite operation?
    • A: The short answer is service policies are evaluated on the original host header (before it is re-written). 
    • A: The long answer is that as soon as our proxy gets a request from the client, if security policy is applied on the HTTP LB, the proxy sends the Host Header to for service policy validation and the policy is evaluated on the request. If it passes, the request is sent back to the proxy. If host_header rewrite is present in the configuration, our proxy will then re-write the host header. Therefore, it is important to use the original host header for any evaluation in service policy.
  • Q: Are the Host header values seen in security event logs from before the rewrite occurs?
    • A: It is after the host_rewrite occurs. Therefore, the security event logs should have the rewritten host header in req_header field.
  • Q: What if there are a multiple Host headers, no Host header, malformed Host header or similar violations, but the Application firewall (FW) is either disabled or set to transparent mode? Does the rewrite still occur as usual?
    • A: host rewrite is the property of the proxy and therefore it gets re-written just before it is sent to the endpoint. (assuming that the question is for WAF)
  • Q: (Only applicable for Silverline customers) Can the default Host Rewrite behavior be toggled at a per-tenant level, or similar, so that it’s disabled by default on new LBs? (Most of the VIPs from Silverline do not have such a configuration, and we’ll have to ensure it doesn’t get introduced as it could break apps in unpredictable ways.)
    • A: This is done at the LB level.
