K000161353: Diagnosing 0-Byte Responses and Session Cookie Concerns When Using F5 Distributed Cloud (XC) with BIG-IP as Origin

Type
Support Solution
Published
2026-05-20
Updated
2026-05-20
Applies to
  • F5 Distributed Cloud Services
  • F5 Distributed Cloud WAF
Source
https://my.f5.com/manage/s/article/K000161353

Description

Requests routed through F5 Distributed Cloud (XC) to an on-premises BIG-IP virtual server as the origin return a 0-byte response for the application endpoint /path on example.com. The same requests work as expected when routed directly to BIG-IP or to an Azure Load Balancer origin. Analysis shows that the presence of the X-Forwarded-For (XFF) header in requests from XC to BIG-IP triggers the 0-byte response. There is no evidence that XC is removing the Session cookie.

Environment

  • Product: F5 Distributed Cloud (XC) with HTTP Load Balancer
  • Origin Servers:
    • On-premises BIG-IP virtual server
    • Azure Load Balancer
  • Application Domain: example.com
  • Endpoint: /path
  • XC adds the X-Forwarded-For header by default
  • BIG-IP is configured as the origin server for the application on XC

Cause

The 0-byte response is caused by the presence of the X-Forwarded-For (XFF) header in requests sent from XC to the BIG-IP origin. The BIG-IP configuration (potentially an iRule or security policy) is likely set to trigger on the presence of the XFF header, resulting in an empty response. There is no evidence that the Session cookie is being removed by XC.

Answer/Recommended Actions

  1. Review BIG-IP Configuration:
    • Check for any iRules, security policies, or configurations on the BIG-IP that act on the presence of the X-Forwarded-For header.
    • Adjust or remove any rules that block or alter responses when the XFF header is present.
  2. Modify XC HTTP Load Balancer or Route (if needed):
    • As a workaround, configure the XC HTTP Load Balancer or route to remove the X-Forwarded-For header before forwarding requests to BIG-IP.
    • Note: Removing the XFF header will prevent the origin from seeing the true client IP unless another header (e.g., x-envoy-external-address) is used.
  3. Validate Cookie Handling:
    • There is no evidence that XC is removing the ASP.NET_SessionId cookie. If session issues persist after resolving the 0-byte response, further investigation may be warranted.
  4. Testing:
    • After making configuration changes, test the application endpoint through XC to confirm that normal responses are restored.

Additional Information

  • The issue does not occur when using Azure Load Balancer as the origin.
  • The presence of the XFF header alone (regardless of its value) triggers the 0-byte response from BIG-IP.
  • The initial assumption regarding session cookie removal was not supported by packet captures or HAR file analysis.
  • Removing the XFF header at the XC layer is a valid workaround but may impact logging or client IP visibility on the origin.
