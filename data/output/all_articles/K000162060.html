K000162060: OAuth RS+AS receives 503 with an empty RST reason

Type
Support Solution
Published
2026-07-02
Updated
2026-07-02
Applies to
  • BIG-IP
  • BIG-IP APM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000162060

Description

OAuth2 authorization code exchange for browser-based clients fails. Mobile application authentication works, but browser access fails with "access deny" on the RS+Client policy. Error messages include:

  • Session variable 'session.oauth.client.last.errMsg' set to 'HTTP error 503, '
  • SSL Handshake failed for TCP ...OAuth Client: failed for server '/Common/name' using 'authorization_code' grant type, error: HTTP error 503

Environment

  • Device acts as both OAuth2 Authorization Server and Resource Server
  • Virtual servers for AS and RS+Client share the same IP address and port
  • LTM policy routes traffic based on Host header to internal virtual servers
  • DNS resolves both AS and RS FQDNs to the same IP address
  • IPv6 is enabled

Cause

When the Authorization Server (AS) and Resource Server (RS) virtual servers share the same IP address and port, the internal backchannel connection initiated by the APM OAuth client for token exchange cannot reliably select the correct virtual server. The LTM policy, which routes based on Host header, does not influence these internal TMM-initiated connections, resulting in failed SSL handshakes and HTTP 503 errors.

Answer/Recommended Actions

To resolve the issue:

  1. Assign unique IP addresses to the Authorization Server (AS) and Resource Server (RS) virtual servers.
  2. Update DNS and OAuth client/server configuration to reference the new, unique IP addresses as appropriate.
  3. Ensure that the LTM policy and APM objects are updated to reflect the new virtual server assignments.
  4. Test the OAuth2 authorization code flow for both mobile and browser clients to confirm successful token exchange.
