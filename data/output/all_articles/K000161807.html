K000161807: Licensing a BIG-IP Directly via iControl REST and the F5 Activation Service

Description


This article walks through the complete API sequence used to license a BIG-IP using only iControl REST calls to the device itself and the F5 Activation Service — generating a hardware dossier on the BIG-IP, submitting it to F5 for activation, and pushing the resulting license file back onto the device. No BIG-IQ is involved at any point in this process; the BIG-IP is licensed directly using its own registration key.

This is the same underlying mechanism used by the on-box SOAPLicenseClient utility and by F5's own automation tooling (including the Ansible bigip_device_license module). Understanding the raw API calls is useful for building custom automation, troubleshooting a failed activation, or validating what a higher-level tool is doing under the hood.

The example throughout this article uses a BIG-IP at 10.10.10.10. Substitute your own management IP, credentials, and registration key.

 

Environment


BIG-IP running TMOS 12.0 or later with iControl REST enabled

A valid registration key issued via the My F5 portal

Network access from the workstation running these commands to the BIG-IP's management interface (port 443)

Internet access from the same workstation to reach activate.f5.com (the BIG-IP itself does not need internet access for this workflow — only the machine issuing these REST calls does)

curl and python (used here for response parsing; any HTTP client and SOAP/XML parser will work equally well)

 

Cause


A newly deployed or re-licensed BIG-IP requires a signed license file before any module can be provisioned. Generating that license involves three distinct systems talking to one another: the BIG-IP itself (which must generate a dossier — a cryptographic statement of its own hardware identity), the F5 Activation Service (which validates the dossier against a registration key and signs a license), and the BIG-IP again (to receive and apply the signed license).

When this is done through the GUI or through BIG-IQ, these three steps are hidden behind a single workflow. This article exposes each step individually as a discrete REST or SOAP call, which is necessary when building automation, troubleshooting a failure at a specific stage, or working in an environment where BIG-IQ is not present.

 

Recommended Actions

Step 1 — Authenticate to the BIG-IP

iControl REST supports token-based authentication. Obtain a token before making further calls:

curl -sk -X POST https://10.10.10.10/mgmt/shared/authn/login -H "Content-Type: application/json" -d '{"username":"admin","password":"yourpassword","loginProviderName":"tmos"}'


The response contains a token under token.token. Extract it and include it as an X-F5-Auth-Token header on every subsequent call in this article:

TOKEN=$(curl -sk -X POST https://10.10.10.10/mgmt/shared/authn/login -H "Content-Type: application/json" -d '{"username":"admin","password":"yourpassword","loginProviderName":"tmos"}' | python -c "import json,sys; print(json.load(sys.stdin)['token']['token'])")


If token authentication is unavailable, HTTP Basic authentication (-u admin:yourpassword) works as a fallback on every call below.

Step 2 — Generate the dossier on the BIG-IP

The dossier is generated on-device using the get_dossier utility, invoked through the iControl REST bash endpoint. This requires your registration key as input:

curl -sk -X POST https://10.10.10.10/mgmt/tm/util/bash -H "X-F5-Auth-Token: $TOKEN" -H "Content-Type: application/json" -d '{"command": "run", "utilCmdArgs": "-c \"get_dossier -b XXXXX-XXXXX-XXXXX-XXXXX-XXXXXXX\""}'


The response's commandResult field contains the dossier — a long block of encoded text representing the device's hardware identity bound to the supplied registration key. Save this output; it is required for the next step.

Step 3 — Submit the dossier to the F5 Activation Service

The Activation Service uses SOAP. To ensure the request passes the Activation Service's Web Application Firewall (WAF) client reputation and protocol compliance checks, you must spoof a standard curl User-Agent and explicitly quote the SOAPAction header. The previous method of using getEULA and activate has been replaced by a unified, stripped-down getLicense call.

Submit the initial request using the dossier generated in Step 2:

curl -s -X POST https://activate.f5.com/license/services/urn:com.f5.license.v5b.ActivationService -H "Content-Type: text/xml; charset=utf-8" -H "User-Agent: curl/8.10.1" -H "SOAPAction: '"urn:com.f5.license.v5b.ActivationService#getLicense"'" -d '<soapenv:Envelope xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns:xsd="http://www.w3.org/2001/XMLSchema" xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/" xmlns:urn="urn:com.f5.license.v5b.ActivationService"><soapenv:Header/><soapenv:Body><urn:getLicense soapenv:encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"><dossier xsi:type="xsd:string">PASTE_DOSSIER_FROM_STEP_2_HERE</dossier><eula xsi:type="xsd:string"></eula></urn:getLicense></soapenv:Body></soapenv:Envelope>'


Handling EULA Acceptance: If the response returns a EULA_REQUIRED state along with the EULA text, you must accept it to proceed. To do this while bypassing WAF signature blocks, extract the EULA text, HTML-escape it (e.g., convert < to &lt;, ensuring you do not double-encode existing XML entities), and submit the exact same curl request again, but this time place the escaped EULA text inside the <eula xsi:type="xsd:string"></eula> tags. This escaping process accurately mimics the web portal's behavior.


On success, the response contains the signed license text within the <license> block. Common fault conditions returned at this stage include fault code 51089 (the supplied key is an internal/development key and cannot be activated on production) and fault code 51092 (the key is already activated on a different unit — contact licensingsupport@f5.com to release it). Save the returned license text; it is required for the final step.

Step 4 — Push the license file back to the BIG-IP

Write the signed license text to /config/bigip.license using the same bash utility endpoint used in Step 2. Because the license content contains characters that complicate shell quoting, base64-encoding it first and decoding on the BIG-IP side is the most reliable approach:

LICENSE_B64=$(echo -n "$LICENSE_TEXT" | base64 -w0)

curl -sk -X POST https://10.10.10.10/mgmt/tm/util/bash -H "X-F5-Auth-Token: $TOKEN" -H "Content-Type: application/json" -d "{\"command\": \"run\", \"utilCmdArgs\": \"-c \\\"echo $LICENSE_B64 | base64 -d > /config/bigip.license\\\"\"}"


Step 5 — Apply the license

Run reloadlic via the same endpoint to load the new license file into the running configuration:

curl -sk -X POST https://10.10.10.10/mgmt/tm/util/bash -H "X-F5-Auth-Token: $TOKEN" -H "Content-Type: application/json" -d '{"command": "run", "utilCmdArgs": "-c \"/usr/bin/reloadlic\""}'


Step 6 — Confirm the license is active

Read back the license state to confirm the registration key now matches what was activated:

curl -sk https://10.10.10.10/mgmt/tm/sys/license -H "X-F5-Auth-Token: $TOKEN"


The response's registrationKey field under entries should now show the activated key, along with license start/end dates and the licensed module list.
