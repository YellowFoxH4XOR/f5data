K8553: Using the least connections load balancing method with priority groups in a pool can cause TMM to crash

Known Issue

This is the result of a known issue. Using the least connections load balancing method in a pool with priority groups can cause the TMM process to crash. This issue can occur when a member in the highest priority group is marked down, and then up by a monitor or manually while the virtual server is processing connections.

For example, in the following pool configuration, when a pool member with a priority of 5 is marked down, and then up while the virtual server is processing connections, TMM can crash:

pool pool-A {
lb method member least conn
min active members 2
member 172.1.1.90:http priority 5
member 172.1.1.91:http priority 5
member 172.1.1.95:http priority 3
member 172.1.1.96:http priority 3
}

F5 Networks Product Development tracked this issue as CR91898 and it was fixed in BIG-IP LTM version 9.4.6. For information about upgrading, refer to the BIG-IP LTM Release Notes.

Addionally, this issue was fixed in Hotfix-BIG-IP-9.3.1-HF3 issued for BIG-IP version 9.3.1, and in Hotfix-BIG-IP-9.4.5-HF2 issued for BIG-IP version 9.4.5. You may download these hotfixes or later versions of the hotfixes from the F5 Networks Downloads site.

For information about the F5 Networks hotfix policy, refer to K4918: Overview of F5 Networks critical issue hotfix policy.

For information about how to manage F5 Networks product hotfixes, refer to K6845: Managing F5 Networks product hotfixes.

Workaround

To work around this issue, choose a method other than the least connections load balancing method for the pool.
