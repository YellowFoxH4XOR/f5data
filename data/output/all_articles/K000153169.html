K000153169: HA failover did not occur

Type

Published
2025-08-27
Updated
2025-08-27
Applies to
  • BIG-IP
Source

Description

A BIG-IP LTM high availability (HA) failover event may not occur as expected when both devices in the HA pair experience severe memory pressure and excessive swap usage. This condition is triggered by over-provisioning multiple modules (such as BIG-IP LTM, BIG-IP ASM, BIG-IP APM, BIG-IP Analytics) on hardware with sufficient RAM. When system load is high, swap memory usage increases, leading to critical processes (tmm, mcpd, bd) going offline on both devices. As a result, neither device is able to assume the Active role, and traffic is not processed. Log messages may include warnings such as "Failover status message received after [gap] second," "No failover status messages received," and "HA proc_running [daemon] fails action is go offline and down links," indicating that both devices are unable to participate in failover.

Environment

- BIG-IP LTM
- Multiple modules provisioned: BIG-IP LTM, BIG-IP ASM, BIG-IP APM, BIG-IP Analytics
- High system load and swap memory usage
- HA device group with two devices

Cause

Excessive module provisioning on hardware, even with sufficient RAM, can lead to high swap usage and memory exhaustion. When memory usage is critical, essential processes such as tmm, mcpd, and bd may go offline on both devices. This simultaneous failure prevents either device from assuming the Active role in the HA pair, resulting in loss of traffic and failure of the HA failover mechanism.

Recommended Actions

- Review and reduce the number of provisioned modules to only those essential for your environment.
- Deprovision any modules not actively in use to lower system resource consumption.
- Consider increasing system RAM if possible, especially when running multiple modules.
- Monitor system health and resource utilization proactively, focusing on swap usage and process status.
- Use commands such as tmsh show sys memory and review logs for sod, tmm, mcpd, and bd failures.
- Follow F5 best practices for module provisioning and resource allocation.
- In the event of simultaneous device failure, rebooting one device may allow the other to recover and assume the Active role, but this is not a recommended solution for ongoing operations.
- Implement regular configuration reviews and capacity planning to prevent future resource exhaustion scenarios.
