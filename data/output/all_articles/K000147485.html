Answer/Recommended Actions

Access control enforces policy such that users cannot act outside of their intended permissions. Failures typically lead to unauthorized information disclosure, modification, or destruction of all data or performing a business function outside the user's limits. For more information, please visit: A01:2021 – Broken Access Control

There are many ways to infiltrate application servers using broken access controls and we are going to focus on the following scenario below and how to mitigate it using a WAF/WAAP policy in Distributed Cloud (XC).

To configure the WAF policy enforcement in blocking mode:

  1. Make sure that you already have a LB configured as well as a WAF policy configured. The following articles should help you with this process: HTTP Load Balancer and Application Firewall
  2. Now, let's configure our WAF policy in our LB. To do that, navigate in your XC console to your LB by going to: Home >> Web App & API Protection >> select the namespace in which you configure your LB >> Manage >> Load Balancers >> HTTP Load Balancers
     

  3. Locate your LB and click on the 3-dot figure at the right of your screen and select "Manage Configuration"
     

  4. Click on the "Edit Configuration" button at the upper-right corner of the console, select "Web Application Firewall" from the "Edit" Menu, make sure that " Web Application Firewall (WAF)" is set to enable, then just below, select the WAF policy that you have configured in Step #1 and then click on the "Edit Configuration" option.
     

  5. Verify that all WAF policy setting are configured as "Default" and make sure that the "Enforcement Mode" is set to "Blocking"
     

  6. Click on the "Continue" button at the bottom-right of the console, and then click "Save and Exit" at the same location.

  7. To verify that the WAF policy is working as expected, we are running a test using the OWASP Juice Shop, which is a vulnerable application configured as backend. Check on the "Additional Information" for details on how we set this scenario.

    When trying to break the access control of this application using an SQL injection command, after clicking "Log In" you will see that, instead of logging in as admin, you are still in the same screen and the words [object Object] appear just above the Email box. If you open the browser's network analyzer and check the response tab, you will see that you were unable to login because the request was blocked by the WAF policy and a support ID was generated for this request.
     

  8. To verify the Support ID that you just received, go back to the XC console and navigate to Home >> Web App & API Protection >> select the namespace in which you configure your LB >> Overview >> Security, then scroll to the bottom of the console and select your LB:

     

  9. Once in that page, click on the "Security Analytics" tab where you will see the latest security violations
     

  10. Click in the "Add Filter" option and then select: "req_id >> in >> insert the Support ID that you received in the juice shop". 
     
    Please be aware that, by default, the time range for the violations is 5 minutes, but you can adjust that time range as needed.

  11. The result will display the violation details in which you will be able to see detailed information about the source, the request that was made, and below that you will see the detection type, which is "waf_sec_event", the action that was taken, which was a "block" and just below that you will be able to see the reason why that request was blocked, in this case because it triggered Signature ID 200015112:
     

 

Additional Information

In this scenario, we are using OWASP Juice Shop, which is an insecure web application designed for security training and other related purposes. For more information about the Juice Shop please visit: OWASP Juice Shop

Now consider that, instead of logging into the Juice Shop using valid credentials, an attacker uses SQL injection attacks to login as another standard or admin user. We can also say this is broken authentication, because an attacker authenticated to the system using an injection attack without providing valid credentials.

  1. Open a browser session and navigate to the LB you created with the Juice Shop and click on the login button:
