Issue

Description

Any of the following symptoms may be observed:

  • /var/log partition may show high disk utilization
  • Command line alerts similar to the following appear:

    emerg alert: 01100045:1 /var/log disk usage exceeds 95%. Reduce log disk space now

  • Log rotation and archiving of logs may not work as expected
  • Log entries span multiple days in a single file
  • Small amount of log files
  • Logs missing recent entries
  • Log files missing completely
  • Logs not archived into .gz file format
  • Large amount of log files

Environment

  • Local logging

Cause

Any of the following may cause this:

  • Files under /var/log may be consuming all available disk space.
  • The logrotate script may not be configured to run daily.
  • Processes may be logging at debug level.
  • Logs may not be configured to be archived or deleted.

Recommended Actions

Perform the following procedures to troubleshoot this issue:

  • Checking size and modification time of existing files under /var/log
  • Verifying if debug level logging is enabled
  • Verifying if monitor logging is enabled
  • Verifying if deleted monitor logging files are consuming disk space
  • Increasing the size of the /var/log partition
  • Verifying the logrotate maximum log age
  • Verifying if the system is configured to keep archives
  • Verifying the logrotate script

Checking size and modification time of existing files under /var/log

Check the size of existing files under /var/log and subdirectories, and delete any large files.

Execute this command to display the contents of /var/log recursively with the largest files at the top of the output:

ls -lhSR /var/log

Example output:

/var/log:
total 1.1G
-rw-r--r--. 1 root      root      1.0G 2019-03-07 16:23 troubleshooting_01.pcap
-rw-rw-rw-. 1 root      root      129K 2019-03-07 03:20 disk_statistics.log.1
-rw-r--r--. 1 root      root      110K 2019-03-07 03:19 disk_latency.log.1
-rw-r--r--. 1 root      root       97K 2019-03-01 21:37 dmesg

The example output indicates a 1GB .pcap file is consuming space under /var/log. This file type will not be deleted by the logrotate utility and will remain until manually deleted.

Important: /var/log should be used exclusively for log files

Verifying if debug level logging is enabled

Debug logging is verbose and can quickly fill /var/log.

Verify log levels by navigating to System > Logs > Configuration > Options in the GUI (Configuration Utility)

Refer to the following article for more information:

  • K15530: Debug logging and BIG-IP system resource utilization

Verifying if monitor logging is enabled

Monitor logging is verbose and can quickly fill the /var/log/monitors directory. Over a period of time, this will fill the /var/log partition.

Verify if monitor logging is enabled at the node or pool member level by reviewing the output of the following commands:

tmsh list ltm node all-properties | grep -iE 'node|logging enabled'

tmsh list ltm pool all-properties | grep -iE 'ltm pool|address|logging enabled'

The example output below indicates that monitor logging is enabled for the node 10.10.5.11:

ltm node 10.10.5.11 {
    logging enabled
ltm node 10.10.5.12 {
ltm node 10.10.5.13 {

Verifying if deleted monitor logging files are consuming disk space

Even if monitor logging is disabled, monitor log files can be left behind. Once deleted, these files may still be held open by the bigd process, which will not release the disk space.

Execute the following command to check for deleted files with open file handles:

lsof -ws | grep -i 'size\|deleted'

In this example output, there is a deleted file consuming a large amount of space under /var/log/monitors:

COMMAND     PID     USER   FD   TYPE             DEVICE        SIZE       NODE NAME
bigd       6121     root    5w   REG              253,1  2018573650     851970 /var/log/monitors/Common_icmp-fast-monitor.log.1 (deleted)

This file can be released by restarting the bigd process:

tmsh restart sys service bigd

Note: Health monitoring is not available while bigd restarts

Increasing the size of the /var/log partition

On BIG-IP VE, the size of the /var/log partition can be extended if there is a need for increased logging.

Refer to the following article to extend the /var/log partition:

  • K14952: Extending disk space on BIG-IP VE

Verifying the logrotate maximum log age

The logrotate.logage db key controls how many days of logs will be kept.

The default value is 8. The minimum value is 0, and the maximum value is 100.

Verify the current value with the following command:

tmsh list sys db logrotate.logage

Verifying if the system is configured to keep archives

The tmsh list sys log-rotate common-backlogs option specifies the maximum number of log files that the system retains for each log file.

The default value is 24. The minimum value is 0, and the maximum value is 100.

Verifying the logrotate script

Verify that the logrotate script resides in /etc/cron.daily/ with the following command:

ls -l /etc/cron.*y

Additional Information

For BIG-IP events, the system routes messages from the errdefs subsystem through syslog-ng to the local log files. For non-BIG-IP events, the system routes messages directly through syslog-ng to the local log files.

The logrotate script is run once per day, but it can be invoked manually and tested with the following command:

logrotate -f /etc/logrotate.conf
