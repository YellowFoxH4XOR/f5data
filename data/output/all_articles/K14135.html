Topic

This article applies to BIG-IP 11.x through 21.x. For information about other versions, refer to the following article:

  • K11736: Defining network resources for BIG-IP HA features (9.x - 10.x)

BIG-IP high availability (HA) features, such as connection mirroring, configuration synchronization (ConfigSync), and network failover, allow core system services to be available for a BIG-IP device group in the event that a particular device group member becomes unavailable. This article explains how to choose the appropriate network resources (IP addresses and VLAN) for BIG-IP HA features.

For an overview of HA groups, refer to the HA groups overview and Setting up HA groups videos in K42542000: Video: Using the HA group feature.

Description

When configuring the HA features for BIG-IP device groups, it is important to select the network resources that are appropriate for your environment. For example, certain HA features allow you to configure the management IP address to process the HA traffic, while other features prohibit the use of the management IP address.

The following section provides information for selecting appropriate network resources for the mirroring, ConfigSync, and failover features.

Mirroring

The connection and persistence mirroring features duplicate the connection and persistence information from the active unit to a peer system. In the event of a failover, the peer system can begin processing connections immediately, without interruption.

  • Before configuring connection and persistence mirroring, ensure the reliability and throughput of the intended network, consider the following recommendations:
    • Layer 7 (L7) mirroring over a low throughput HA link may not function as you want. 
    • Layer 4 (L4) mirroring over a high latency HA link may cause connection hangs. 
    • BIG-IP APM and ASM systems require frequent synchronization of session information between failover peers.

The following table summarizes the recommended network resources for mirroring.

Mirroring resourceAllowed resourceRecommendation
IP addressself IPConfigure both primary and secondary local mirror addresses.
VLANanyConfigure dedicated VLAN and interfaces to process mirror traffic.

Mirroring recommendations

  • Configure a dedicated VLAN and dedicated interfaces to process mirroring traffic.

    The BIG-IP state mirroring mechanism is managed by the Traffic Management Microkernel (TMM) process, and connection data is synchronized to the peer system with every packet or flow state update. In some environments, this behavior may generate a significant amount of traffic. Using a shared VLAN and shared interfaces for both mirroring and production traffic reduces the overall link capacity for either type of traffic. Due to high traffic volumes, production traffic may interfere with the mirroring traffic (and the other way around), potentially causing latency in mirrored connections or interrupting the network mirror connection between the two BIG-IP devices. If the network mirror connection is interrupted, it can cause loss of mirror information and interfere with the ability of the peer device to take over connections in the event of a failover.

    Note: While you can configure multiple self IP addresses on a VLAN that is dedicated to process mirroring traffic, you cannot specify which self IP address will be used as the peer's source address. Consequently, this configuration may result in errors when performing a ConfigSync. Therefore, F5 recommends that you configure one self IP address on the VLAN that is dedicated to process mirroring traffic.

  • Use the default Clustered Multiprocessing (CMP) hash setting for the VLAN in which mirroring is configured (BIG-IP 11.3.0 and later).

    The CMP hash setting for the VLAN specifies how the BIG-IP system disaggregates traffic for the VLAN. The default hash (Default) specifies that the system uses L4 ports when disaggregating traffic on the VLAN. Choosing a non-default hash, such as Source Address, may disrupt mirroring traffic between TMM instances.

  • Do not use a VLAN group for network mirroring traffic.

  • When the network mirror connection is established, it will traverse one of the child VLANs of the VLAN group. Because both BIG-IP systems are connected to all child VLANs, it is possible for normal Address Resolution Protocol (ARP) behavior to cause the network mirror traffic to move from one child VLAN to another. Movement of a connection from one child VLAN to another, in conjunction with VLAN-keyed connections, will result in the network mirror connection being reset. Loss of the network mirror connection, even briefly, may cause the loss of some mirroring state on the standby device, and interfere with its ability to take over connections in the event of a failover.

  • Configure both primary and alternate mirroring addresses.

    Especially when configured in conjunction with the previous recommendations (primary and alternate mirroring links each directly connected over a separate dedicated VLAN), an alternate mirroring path further ensures reliable mirroring in case of equipment or cable failure.

ConfigSync and device clustering

Starting in BIG-IP 11.x, the ConfigSync feature works in combination with the device service clustering (DSC) architecture. When the device clustering components (including the ConfigSync IP address) are properly defined, the device group members establish a communication channel (CMI channel) to accommodate device group communication and synchronization.

The following table summarizes the recommended network resources for ConfigSync.

ConfigSync resourceAllowed resourceRecommendation
IP addressself IP
mgmt (only with database variable)		Use a self IP address for ConfigSync.
VLANanyUse an internal or dedicated HA VLAN.

ConfigSync and device clustering recommendations

  • Configure the ConfigSync address to use a self IP address, the internal VLAN, or dedicated HA VLAN.
  • Make sure that each device in the HA group has the IP address of its management (mgmt) interface set to a value unique within the group. Some of the HA functionality is relying on the address of the interface for uniquely identifying the individual members.
  • Avoid using the management (mgmt) interface for ConfigSync/device service traffic.

    By default, the management address is unavailable for ConfigSync/device clustering communication. It is possible to configure the BIG-IP system to use the management IP address to accommodate device group communication and synchronization by enabling the configsync.allowmanagement database variable. You can do so using the tmsh modify /sys db configsync.allowmanagement value enable command. However, F5 recommends using the self IP address of the internal VLAN for ConfigSync traffic.

Network Failover

When BIG-IP device group members are configured to use network failover, the systems communicate over the configured failover addresses.

The following table summarizes the recommended network resources for network failover.

Network failover resourceAllowed resourceRecommendation
IP addressself IP
mgmt IP
multicast IP		Configure failover unicast and multicast addresses for each device group member.
VLANanyUse an internal or dedicated HA VLAN in addition to the management (MGMT) interface.

Network failover recommendations

  • To ensure the most stable network failover configuration, choose two channels for network failover communication. F5 considers it best practice to select both the management address and a TMM network address. This configuration avoids unexpected failover conditions, for example, while the BIG-IP system initializes and before the TMM network connectivity channels are fully established. To do this, you must configure a management and TMM failover unicast address.
  • Ensure that you have configured a reliable NTP server for the proper time synchronization among the members of the DSC group.
  • Before you deploy network failover, to ensure the reliability of the intended network, consider the following recommendations:
    • Ensure that you have access to and control over interim devices, and links between the BIG-IP systems.
    • Test the failover network between the BIG-IP systems to ensure low latency of under 100ms is provided by the network.

      Important: BIG-IP heartbeat messages that are dropped or delayed by a poor performing network can trigger an unexpected failover between BIG-IP peer systems.

  • To configure network failover for VIPRION systems, refer to the following articles:
    • K37361453: Configuring network failover for redundant VIPRION systems (13.x - 17.x)
    • K13915: Configuring network failover for redundant VIPRION systems (11.x - 12.x)
