K000160102: WebSocket connections fail intermittently when pool assignment is performed within the WS_REQUEST iRule event.

Type
Support Solution
Published
2026-02-20
Updated
2026-02-20
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000160102

Description

WebSocket connections fail intermittently when pool assignment is performed within the WS_REQUEST iRule event. Instead of receiving the expected HTTP 101 Switching Protocols response to complete the WebSocket handshake, clients receive a TCP RST from the BIG-IP system. This issue occurs when using the pool command in the WS_REQUEST event, even though the iRule syntax is valid. Typical symptoms include:

  • Approximately 1 in 5 WebSocket connection attempts fail with TCP RST
  • Client errors such as "recvAddress(..) failed with error(-104): Connection reset by peer" or "Failed to upgrade to websocket"
  • Incomplete WebSocket handshakes visible in packet captures (missing 101 response)
  • iRule logs show WS_REQUEST event firing but no subsequent WS_RESPONSE or WebSocket upgrade completion for failed sessions

Environment

  • BIG-IP LTM
  • Virtual Server with WebSocket profile configured
  • MQTT over WebSocket or similar WebSocket-based application protocols
  • iRule using pool command within WS_REQUEST event
  • HTTP profile applied to Virtual Server

Cause

The BIG-IP system requires pool selection to occur before the WebSocket upgrade process begins. When the pool command is executed within the WS_REQUEST event, it occurs too late in the connection processing flow. The WS_REQUEST event fires after the HTTP Upgrade headers are detected but before the 101 response is generated. Attempting to change pool assignment at this stage causes inconsistent behavior where the system cannot reliably complete the WebSocket handshake, resulting in TCP RST packets being sent instead of the 101 Switching Protocols response.

Recommended Actions

Separate pool assignment from WebSocket processing by performing pool selection in the HTTP_REQUEST event and enabling WebSocket-specific features in the WS_REQUEST event.

Incorrect iRule pattern (causes intermittent failures):

when WS_REQUEST {
if { ($host equals "example.com") and ([HTTP::path] starts_with "/mqtt") } {
WS::payload_processing enable
pool $mqtt_websocket_pool
}
}

Correct iRule pattern (separate concerns):

when HTTP_REQUEST {
if { ($host equals "example.com") and ([HTTP::path] starts_with "/mqtt") } {
pool $mqtt_websocket_pool
}
}

when WS_REQUEST {
if { ($host equals "example.com") and ([HTTP::path] starts_with "/mqtt") } {
WS::payload_processing enable
}
}

This approach ensures pool selection occurs during normal HTTP request processing, before WebSocket upgrade negotiation begins, while WebSocket-specific configuration is applied at the appropriate event.

Additional Information

  • The WS_REQUEST event is triggered when WebSocket upgrade headers (Upgrade: websocket, Connection: Upgrade, Sec-WebSocket-Key) are present in the client request
  • Pool assignment should always be completed before WebSocket protocol switching occurs
  • Other iRule commands that affect connection routing (such as node or pool member) should also be executed in HTTP_REQUEST rather than WS_REQUEST
  • The WS::payload_processing command and other WebSocket-specific operations are appropriate for the WS_REQUEST event
