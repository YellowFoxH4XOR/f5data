Topic

HTTP/2 supports all of the core features of HTTP/1.1 but improves efficiency in several ways. HTTP/2 enables a more efficient use of network resources and a reduced perception of latency by introducing header-field compression and allowing multiple concurrent exchanges on the same connection. HTTP/2 is introduced in BIG-IP 11.6.0 more features are added. The following summarizes the features added in various BIG-IP versions:

BIG-IP 11.6.0

  • Introduction of HTTP/2 protocol support as defined in RFC 7540 for processing client-side HTTP/2 traffic.

BIG-IP 14.1.0

  • Introduction of support for server-side HTTP/2 traffic processing, iRules support, PUSH_PROMISE, and dynamic fallback to HTTP/1.
  • Support provided for PUSH_PROMISE, in which the BIG-IP system responds to server-initiated PUSH_PROMISE and forwards pushes to the client.
  • For persistence, only cookie persistence is supported.

BIG-IP 15.0.0

  • Introduction of support for the webacceleration profile in HTTP/2 full-proxy mode.
  • Following cookie persistence support, support provided for the following persistence attributes: simple, source addr, sticky, dest addr, cookie, uie.

BIG-IP 15.1.0

  • Introduction of support for BIG-IP HTTP/2 monitors.

Description

Beginning in BIG-IP 15.1.0, you can configure HTTP/2 monitors to monitor the health of the HTTP/2 service of your server pools. The available monitors types are http2 and http2_head_f5.

In-TMM monitoring

HTTP/2 monitors use In-Traffic Management Microkernel (TMM) monitoring, which is introduced in BIG-IP 13.1.0. In-TMM monitoring lets you select an SSL profile from an available list of all server SSL profiles in the BIG-IP system. When selecting an SSL profile, the BIG-IP system's data plane processes directly handle the HTTPS connections (TMM). This improves HTTPS monitor scaling on systems with four or more CPU cores and allows the HTTPS health monitor to use SSL acceleration hardware, including the use of SNI (Server Name Indication) without in-TMM monitoring enabled.

Note: The HTTP/2 RFC recommends using TLS end-to-end as a best practice. On the BIG-IP system, in the HTTP/2 profile, the Enforce TLS Requirements must be enabled, and you must select a Server SSL profile for your HTTP/2 monitor.

In-TMM monitoring is controlled by the database variable bigd.tmm in accordance with K11323537: Configuring In-TMM monitoring. However, this database variable is ignored for the HTTP/2 monitor types, and you do not need to enable it to use HTTP/2 monitors. Similar to HTTP/1.1, the bigd monitoring daemon has overall control of the monitoring and communicates with the Master Control Program (MCP) and TMM modules. bigd uses the TMM module to communicate with the back-end servers, receives feedback, and updates the health status of the nodes.

HTTP/2 PUSH events

Because HTTP/2 monitors use the TMM module to communicate with the pool members, TMM and the HTTP/2 monitors respond to PUSH events, as defined in HTTP/2. In a server PUSH event, the back-end server push lets the server preemptively push website assets to the client without the client having explicitly requested them. For example, if you configure your HTTP/2 monitor to send a query string /example to the pool member and the pool member replies with a 200 OK message but also pushes 20 MB of data from /example, 20 MB of data traverses the network at every monitor interval from every single pool member. Therefore, when configuring the Send String in your HTTP/2 monitor, you should ensure that it does not result in a similarly large response from the server. 

Configuration

To configure HTTP/2 monitoring, you need to create a HTTP/2 monitor and then associate it to your pool. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Monitors.
  3. Select Create.
  4. Enter an appropriate name for your monitor.
  5. For Type, select HTTP/2.
  6. For Parent Monitor, select a monitor type. The built-in options are http2 or http2_head_f5. 

    Note: http2_head_f5 is similar to the http_head_f5 and https_head_f5 monitor types in that they send HEAD requests instead of GET requests and expect to receive a Server string in return.

  7. For Configuration, select Advanced.
  8. For SSL Profile, select an appropriate Server SSL profile.
  9. Select Finished.
  10. Go to Local Traffic > Pools > Pool List and select the appropriate pool.
  11. For Health Monitors, in the Available list, select the new HTTP/2 monitor and move it to the Active list.
  12. Select Update.

Troubleshooting

Logging

The BIG-IP system logs messages related to health monitors to the /var/log/ltm file. Logging is performed by the bigd and In-TMM modules. Similar to troubleshooting other modules, for the bigd module, troubleshoot by referring to K12531: Troubleshooting health monitors.

To enable debug for the TMM monitor agent, you can modify the log.tma.level database variable. For example, to enable debug logging, enter the following tmsh command:

tmsh modify sys db log.tma.level value debug

To revert to the original default value, enter the following tmsh command:

tmsh modify sys db log.tma.level value notice

Tools

Curl

When a HTTP/2 monitor is down, you should use a command line tool to determine the health of the back-end server. Beginning in BIG-IP 14.1.0, you can use curl with the --http2 switch on the BIG-IP system to verify the HTTP/2 health of your pool members. To do so, use the following command syntax:

curl --http2 -Ik https://<server_IP_address>

To add verbosity to the output, use the following command syntax:

curl --http2 -Ivk https://<server_IP_address>

When your pool member is able to provide HTTP/2 service, you may observe an output similar to the following truncated example:

* ALPN, server accepted to use h2
[...]
* Using HTTP2, server supports multi-use
* Connection state changed (HTTP/2 confirmed)
[...]

nghttp

Beginning in BIG-IP 14.1.0, you can also use nghttp to verify the health of the back-end server. To do so, use the following command syntax:

nghttp -nv https://<server_IP_address>

You may observe an output similar to the following truncated example:

[  0.202] Connected
The negotiated protocol: h2
[...]
