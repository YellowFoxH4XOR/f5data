Known Issue

Excessive GC (Allocation Failure) logs on active and standby BIG-IP systems.

This issue occurs when all of the following conditions are met:

  • You are running BIG-IP systems in a standalone or high availability (HA) deployment.
  • The Java Virtual Machine (JVM) triggers a Garbage Collection cycle to free memory.

The JVM manages memory to ensure free space is available. If a new object allocation request arrives that cannot fit into the current free space in the JVM heap’s young generation (or the relevant memory pool), JVM triggers a Garbage Collection cycle. 

Impact

This log entry alone is benign and indicates normal JVM memory management. Only if the messages appear very frequently, such as many messages per second, and pause times grow longer, such as hundreds of milliseconds or seconds, or if post-GC usage remains consistently high above 80% of heap, would it start to have an operational impact.

If the system was encountering an actual out-of-memory condition, the system would log a message similar to the following example:

OutofMemoryError: Java heap space error

Symptoms

As a result of this issue, you may encounter the following symptom:

  • Messages similar to the following example appear in the /var/log/restjavad-gc.log .0.current file:

    2024-05-23T11:06:56.410+0900: 368.168: [GC (Allocation Failure) 108438K->56007K(190080K), 0.0031826 secs]
    2024-05-23T11:07:00.535+0900: 372.294: [GC (Allocation Failure) 108487K->56021K(190080K), 0.0048274 secs]
    2024-05-23T11:07:04.619+0900: 376.378: [GC (Allocation Failure) 108501K->56052K(190080K), 0.0135200 secs]
    2024-05-23T11:07:08.828+0900: 380.586: [GC (Allocation Failure) 108532K->56041K(190080K), 0.0062813 secs]
