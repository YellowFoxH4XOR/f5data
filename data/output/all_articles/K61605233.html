Description
Audit logging of failed/malicious SNMPv2c requests is desired for improved network security.

Environment

  • BIG-IP
  • SNMPv2c Agent functionality configured on BIG-IP

Cause
SNMPv2c was not designed with robust security in mind and does not have audit logging similar to traditional AAA protocols like TACACS+ or RADIUS. The BIG-IP uses the industry standard net-snmp without any additional audit logging customization. There are four OIDs on an SNMPv2c Agent like the BIG-IP which can be polled by a Manager to gather some audit logging functionality. The OIDs are part of the "SNMP" group in the "SNMPv2-MIB" from RFC1213. They are:

MIB_OBJECT        OBJECT_ID: 1.3.6.1.2.1.11+ DESCRIPTION
snmpInBadVersions             .3             Total number of SNMP messages delivered to
                                             the SNMP entity for an unsupported SNMP version.

snmpInBadCommunityNames       .4             Total number of SNMP messages delivered
                                             to the SNMP entity which used a SNMP
                                             community name not known to said entity.

snmpInBadCommunityUses        .5             Total number of SNMP messages delivered
                                             to the SNMP entity which represented an SNMP
                                             operation which was not allowed by the SNMP
                                             community named in the message.

snmpInBadValues               .10            The total number of SNMP messages which
                                             were delivered to the SNMP protocol entity
                                             and for which the value of the error-status
                                             field was "badValue".

While these OIDs are considered obsolete, they are present in BIG-IP software and usable.

Recommended Actions

The above OIDs can be queried by a SNMP Manager with thresholds and analysis as deemed necessary by your internal security protocols.
 

Additional Information
Here are simple examples of querying these locally on a BIG-IP test system (where "public" is the community name):
[root@bigip01:Active:In Sync] config # snmpwalk -v2c -c public localhost .1.3.6.1.2.1.11.3
SNMPv2-MIB::snmpInBadVersions.0 = Counter32: 0

[root@bigip01:Active:In Sync] config # snmpwalk -v2c -c public localhost .1.3.6.1.2.1.11.4
SNMPv2-MIB::snmpInBadCommunityNames.0 = Counter32: 0

[root@bigip01:Active:In Sync] config # snmpwalk -v2c -c public localhost .1.3.6.1.2.1.11.5
SNMPv2-MIB::snmpInBadCommunityUses.0 = Counter32: 0

[root@bigip01:Active:In Sync] config # snmpwalk -v2c -c public localhost .1.3.6.1.2.1.11.10
SNMPv2-MIB::snmpInBadValues.0 = Counter32: 0

The OID names can be translated like this:
[root@bigip01:Active:In Sync] config # snmptranslate -On SNMPv2-MIB::snmpInBadCommunityNames.0
.1.3.6.1.2.1.11.4.0

The following shows the increase of value, if an incorrect community name is attempted:
[root@bigip01:Active:In Sync] config # snmpwalk -v2c -c "bad-name" localhost .1.3.6.1.2.1.11.4
Timeout: No Response from localhost

[root@bigip01:Active:In Sync] config # snmpwalk -v2c -c public localhost .1.3.6.1.2.1.11.4
SNMPv2-MIB::snmpInBadCommunityNames.0 = Counter32: 6

Note that the value has changed from "0" to "6" because of the attempted walking of several OID levels via the snmpwalk. If only an snmpget had been used the counter would have incremented a single time from "0" to "1".
