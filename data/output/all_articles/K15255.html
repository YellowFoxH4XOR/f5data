Known Issue

The bigd process on the secondary blade of a Clustered Multiprocessing (CMP) system may not receive the configuration for built-in monitors, causing the bigd process to log failures and misidentify which monitors should run.

This issue occurs when all of the following conditions are met:

  • The mcpd process restarts on a VIPRION blade in a clustered system.
  • The system uses internal monitors to monitor pool members.

Impact

Some pool members may not be properly monitored.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • Errors similar to the following example appear in the /var/log/ltm file:

    err bigd[<pid>]: 01060129:3: Template /Common/postgresql is not initialized.
    err bigd[<pid>]: 01060129:3: Template /Common/tcp is not initialized.
    err bigd[<pid>]: 01060129:3: Template /Common/snmp_dca is not initialized.
    err bigd[<pid>]: 01060129:3: Template /Common/wap is not initialized.
    err bigd[<pid>]: 01060129:3: Template /Common/real_server is not initialized.
    err bigd[<pid>]: 01060129:3: Per-invocation log rate exceeded; throttling.

  • Affected pool members are incorrectly marked down, or not marked down when offline.

Workaround

To work around this issue, you can manually restart the bigd process on the affected blade. To do so, perform the following procedure:

Impact of workaround: Nodes on affected blades may temporarily be marked down as the bigd process restarts.

  1. Log in to the Traffic Management Shell (tmsh) by typing the following command:

    tmsh

  2. Restart the bigd process by typing the following command:

    restart sys service bigd

  3. Save the change by typing the following command:

    save /sys config
