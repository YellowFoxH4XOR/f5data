Description
The fix for ID919317 results in the BIG-IP no longer dropping all routes advertised by a BGP neighbor which are reached recursively. The BGP RFC 4271 does not specify if such routes must or must not be dropped so the BIG-IP behavior before and after the change is permissible. This can result in unanticipated behavior when upgrading to a software version containing the fix for ID919317 if the administrator is unaware of the change.

Environment

  • BGP configured
  • One or more BGP neighbors providing BIG-IP with routes reached recursively
  • Upgrade from version without ID919317 to version containing the fix (only 16.1.0 currently)

Cause
In versions without the fix for ID919317, when the BIG-IP receives routes which are reached recursively, they will be discarded. The /var/log/ltm log may contain messages like below:
Aug 17 10:57:17 bigip err tmm[18025]: 01010036:3: Route 198.51.100.1%0/32 loops back to itself
Aug 17 10:57:17 bigip err tmm[18025]: 01010037:3: Route 192.0.2.0%0/24 is unreachable
Aug 17 10:57:17 bigip err tmm[18025]: 01010036:3: Route 198.51.100.1%0/32 loops back to itself
Aug 17 10:57:17 bigip err tmm[18025]: 01010037:3: Route 203.0.113.0%0/24 is unreachable
In this example there is a BGP peer of the BIG-IP advertising route for 198.51.100.1/32 where the next hop is 198.51.100.1, which is recursive. 198.51.100.1 is also the next hop for two other routes that peer is advertising, 192.0.2.0/24 and 203.0.113.0/24 which are both reported as unreachable.

Reviewing the ZebOS "show ip route" in versions without the ID919317 fix will show the absence of the routes which are reached recursively. In versions with the fix for ID919317 however, those routes are no longer discarded and are visible with the notation 'recursive via [IP Address]' as seen below:
C       198.51.100.0/24 is directly connected, Internal-VLAN
B       198.51.100.1/32 [200/0] via 198.51.100.1, Internal-VLAN, 00:00:54
B       192.0.2.0/24 [200/0] via 198.51.100.1 (recursive via 198.51.100.1), 00:11:27
B       203.0.113.0/24 [200/0] via 198.51.100.1 (recursive via 198.51.100.1), 00:11:27
C       127.0.0.1/32 is directly connected, lo
C       127.1.1.254/32 is directly connected, tmm
The two routes which are reached recursively are noted in the output and traffic can still be routed to them.

Recommended Actions
Review BGP configuration on BGP neighbor(s) of BIG-IP and verify all configured routes are required as recursive routing is rarely intentional. In the above example, there is likely no value in the BIG-IP's BGP neighbor advertising a /32 route that matches the interface it uses to communicate with BGP peers. In this example, removing the /32 route from the BGP neighbor will have no adverse impact and improve the BGP routing and advertisement.
