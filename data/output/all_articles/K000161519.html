Description

One BIG-IP device in an HA pair may show its peer as down (red) while the peer device shows both devices as up (green). Rebuilding device trust does not resolve the issue. This can occur when failover heartbeat traffic is blocked on the Internal Self IP. In the observed case, the affected unit had the Internal Self IP configured with allow-service none, which prevented UDP 1026 failover heartbeat communication.

Environment

  • BIG-IP LTM in an HA pair
  • version 17.5.1.3
  • device failover / sync configuration
  • Internal Self IP used for HA communication
  • one device configured with Internal Self IP port lockdown allow-service none while the peer uses allow-service default

Cause

Internal Self IP port lockdown configured as allow-service none on one device, blocking required HA failover heartbeat traffic on UDP 1026

Recommended Actions

Verify the Internal Self IP port lockdown setting on both devices. If one device is configured with allow-service none, update it to allow the required heartbeat traffic. Example:
tmsh modify net self /Common/Internal_SelfIP allow-service default
tmsh save sys config

After applying the change, verify HA recovery with:
tmsh show cm failover-status
tmsh show cm sync-status

If needed, compare the Internal Self IP configuration on both peers to confirm they are aligned. Trust reset is not expected to resolve this issue when heartbeat traffic is blocked by port lockdown.

Additional Information

This issue can present asymmetrically. The device with the restrictive Internal Self IP setting may report the peer as down because it cannot receive heartbeat packets, while the peer may still report both devices as up if its own Internal Self IP allows the required traffic. Updating the port lockdown setting does not require a reboot and should not interrupt traffic.
