Description

When accessing Google web applications, such as Google Drive or Gmail, through BIG‑IP SSLO, certain actions (including download, rename, and share operations for files or mail attachments) fail to function.

Bypassing Google services in the SSLO security policy immediately resolves the issue.

Browser developer tools report: net::ERR_SSL_VERSION_OR_CIPHER_MISMATCH for specific Google application subdomains.

With TCP RST cause logging enabled, logs show certificate signing and handshake‑related failures similar to the following in /var/log/ltm:

warning tmm1[17479]: 01260009:4: <source_ip>:<source_port> -> <dest_ip>:443: Connection error: ssl_hs_fwdp_vfy_sign_cert:15588: alert(80) fwdp sign cert error
tmm1[17479]: 01260013:4: SSL Handshake failed for TCP <source_ip>:<source_port> -> <dest_ip>:443
tmm1[17479]: 01230140:3: RST sent from <source_ip>:<source_port> -> <dest_ip>:443, [0x316fa5a:662] cl side error (No error)

Packet captures show that SSLO completes the server‑side TLS handshake, during which the upstream server presents an ECDSA certificate. Immediately afterward, SSLO sends a fatal handshake failure alert to the client and resets the connection with cause: [F5RST: cl side error (No error)]

Environment

  • BIG-IP SSL Orchestrator (SSLO)
  • Layer 3 Transparent Forward Proxy Topology
  • SSL profile configured with only an RSA CA certificate/key 

Cause

The SSLO Client SSL profile is configured only with an RSA CA certificate/key pair, which prevents SSLO from forging an ECDSA certificate when the upstream server negotiates ECDSA during the TLS handshake.

Answer/Recommended Actions

Update the SSLO SSL configuration to include both the EC CA and template certificate/key pair.
