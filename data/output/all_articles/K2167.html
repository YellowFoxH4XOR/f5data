BIG-IP HTTP and HTTPS application health monitors are used to verify the health of the server by checking whether the expected response is returned in response to a specific request. The following information is intended to help you construct an appropriate request to verify the health of your HTTP servers.

Note: F5 recommends that you consult the documentation from your HTTP server vendor for the specific HTTP request string necessary (if any) to verify the health of your HTTP servers.

HTTP request formats

The BIG-IP system, by default, uses HTTP 0.9 when sending monitor requests. An HTTP 0.9 request consists of only a request line, which must be terminated by a line feed (LF) character. The request line consists of a single line containing the HTTP request method, a space, and the name of the object requested (including the path, if necessary). No version is specified. No headers or request body are supported in HTTP 0.9.

Note: The official HTTP 0.9 specification included only one request method: GET.

Note: Since HTTP 1.0 or higher is required to support the use of authentication headers, the BIG-IP system uses HTTP 1.0, by default, to send requests when basic authentication is enabled. Basic authentication is enabled by configuring a User Name and Password in the monitor definition. Basic authentication sends password information unencrypted, using Base64 encoding. If Basic Authentication fails, the BIG-IP system tries NTLM authentication.

By specifying the HTTP version in the Send String, you can force the BIG-IP monitor to send an HTTP 1.0 or 1.1 request that accommodates a wider range of request options. An HTTP 1.0 or 1.1 request begins with a request line that consists of a single line containing the HTTP request method, a space, the name of the object requested (including the path, if necessary), a space, and the HTTP version of the request. The request line may be followed by a list of headers. The request line and each header line in an HTTP 1.0 or 1.1 request must be terminated with a single carriage return/line feed (CR/LF) sequence, and the end of the request headers is indicated by a terminating double carriage return/line feed sequence (CR/LF/CR/LF). For some request methods, the header list may be followed by a request body.

The header and body requirements vary depending on the request version and the request method, so the appearance of HTTP requests differ widely. For example, in an HTTP 1.0 request, no headers are required. However, in an HTTP 1.1 request, the Host header is required, although it may contain a null value. The Connection header was also added in HTTP 1.1, allowing management of Keep-Alive connections intended to serve multiple requests. While this header was not officially part of the HTTP 1.0 specification, many HTTP 1.0 implementations implicitly support or expect Keep-Alive behavior based on this header.

Note: The official HTTP 1.0 specification included the following case-sensitive request methods: GET, HEAD, and POST. The official HTTP 1.1 specification included the following case-sensitive request methods: GET, HEAD, POST, PUT, DELETE, TRACE, and CONNECT. Extensions to the originally specified request methods in each version may be supported by some implementations. You can specify any request method supported by your server when constructing the Send String for an HTTP or HTTPS application health monitor.

For detailed specifications for each HTTP version, refer to the following locations:

  • For more information about HTTP 0.9, refer to the original W3C HTTP specification.
  • For more information about HTTP 1.0, refer to RFC1945.
  • For more information about HTTP 1.1, refer to RFC2616.

An HTTP 0.9 GET request appears similar to the following example:

GET /index.html

An HTTP 1.0 GET request that includes two optional headers appears similar to the following example:

GET /index.html HTTP/1.0
Referer: http://www.example.com/login.cgi
User-Agent: Mozilla/3.0Gold

An example of an HTTP 1.1 POST request that includes the required Host header, several optional headers, a double CR/LF terminating the header list, and a request body containing the POST data, appears similar to the following example:

POST /form.cgi HTTP/1.1
Accept: *.*
Accept-Language: en-us
Accept-Encoding: gzip, deflate
User-Agent: Mozilla/4.0 (Compatible; MSIE 6.0; Windows NT 5.0; T312461)
Host: host.example.com
Connection: Keepalive
Referer: http://www.example.com/index.html

First=Joe&Last=Cool&userID=123456789

Representation and interpretation of line termination characters 

The CR and LF line termination characters are key to the accurate construction and parsing of HTTP requests, regardless of the HTTP version. Depending on the tool used to examine or construct the request, the CR and LF characters may be represented by the characters in the following table.

CharacterText
(used to construct monitor Send Strings)		HEX
(displayed in tcpdump traces)
Carriage Return (CR)\r0x0d
Line Feed (LF)\n0x0a

The BIG-IP system does the following when formatting a Send String in an HTTP health monitor:

  • Translates each instance of \r to a CR character (0x0d).
  • Translates each instance of \n to a LF character (0x0a).
  • Appends a double CR/LF sequence to the end of the Send String if there are insufficient CR/LF to terminate the headers.
  • When basic authentication or NTLM / NTLMv2 authentication is enabled by configuring a User Name and Password in the monitor definition,  inserts the Authorization header and a terminating double CR/LF sequence (0x0d 0x0a 0x0d 0x0a) after the last character in the Send String.  

Construct an appropriate HTTP/HTTPS monitor Send String

Refer to the following sections to assist you in constructing an appropriate monitor Send String:

  • Send String without basic authentication
  • Send String with basic authentication
  • Send String with NTLM / NTLMv2 authentication

Send String without basic authentication

  1. Enter the request line, including the HTTP method, the path to the requested object, and the HTTP version (optional) followed by a single \r\n sequence.
  2. Enter any headers you want or need, following all but the last header with a single \r\n sequence.
  3. Terminate the Send String with a double \r\n sequence.
  4. (Optional) Add a request body.

    Note: You must add a double \r\n sequence to separate the last header from the request body. No terminating sequence is required at the end of the request body.

    HTTP 1.1 examples

    GET /index.html HTTP/1.1\r\nHost: host.example.com\r\nConnection: Close\r\n\r\n

    POST /form.cgi HTTP/1.1\r\nHost: host.example.com\r\nConnection: Close\r\n\r\nFirst=Joe&Last=Cool

    HTTP 1.0 examples

    GET /index.html HTTP/1.0\r\n\r\n

    GET /index.html HTTP/1.0\r\nUser-agent: Mozilla/3.0Gold\r\nReferer: http://host.example.com/login.cgi\r\n\r\n

    POST /form.cgi HTTP/1.0\r\n\r\nFirst=Joe&Last=Cool

Send String with basic authentication

Important: If your health check must use basic authentication to send a request which also contains a message body, such as a POST request, you must instead configure a custom external monitor or use the workaround outlined in K1033: Configuring an HTTP application health monitor to send a POST request. When basic authentication is enabled by adding a User name and Password to the monitor configuration, the BIG-IP system erroneously appends the Authorization header and a double CR/LF sequence after the last character in the Send String (after the message body), resulting in a malformed request. For more information about creating external monitors, refer to the HTTP Monitor cURL Basic POST article on DevCentral.

  1. Ensure you have a User Name and Password configured for the monitor.
  2. Enter the request line, including the HTTP method, the path to the requested object, and the HTTP version followed by a single \r\n sequence.

    Important: If the request includes headers other than the Authorization header that is inserted by the system, you must specify HTTP 1.0 or higher in the Send string.

  3. Enter any headers you want or need, following all but the last header with a single \r\n sequence.
  4. No terminating sequence is required, regardless of whether the request contains any headers.

    HTTP 1.1 examples

    GET /index.html HTTP/1.1\r\nHost: host.example.com\r\nConnection: Close

    HTTP 1.0 examples

    GET /index.html HTTP/1.0\r\n

    GET /index.html HTTP/1.0\r\nUser-agent: Mozilla/3.0Gold\r\nReferer: http://host.example.com/login.cgi

Send String with NTLM / NTLMv2 Authentication

Important: If your health check must use NTLM / NTLMv2 to send a request which also contains a message body, such as a POST request, you must instead configure a custom external monitor. When NTLM/NTLMv2 is enabled by adding a User Name and Password to the monitor configuration, the BIG-IP system erroneously appends the Authorization header and a double CR/LF sequence after the last character in the Send String (after the message body), resulting in a malformed request. For more information about creating external monitors, refer to K71282813: Overview of BIG-IP EAV external monitors.

For an HTTP/HTTPS monitor to successfully use NTLM or NTLMv2 authentication, a monitor must meet the following configuration requirements:

  • The monitor must have a send string. Because it is necessary to use HTTP 1.1, at a minimum the send string should use a format similar to the following example:

    GET /<filename/path> HTTP/1.1\r\nHost: <hostname>

  • The monitor must have a Receive String.
  • The monitor cannot be a Reverse monitor.
  • The monitor must have the User Name setting configured. The acceptable username format may vary depending on your server implementation. Common username formats are as follows:
    • Simple username. For example, UserName
    • User principal name (UPN). For example, UserName@domain.local
    • Down-level logon name. For example, DOMAIN\UserName
  • The monitor must have the Password setting configured.

After this monitor is associated with a pool or pool member, it only enacts NTLM if the request with basic authentication gets a 401 response with a WWW-Authenticate header set to NTLM. At this point the NTLM handshake should start.

Example send string

GET /index.html HTTP/1.1\r\nHost: host.example.com
