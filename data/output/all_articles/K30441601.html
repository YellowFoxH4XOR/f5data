Description

When EAV external monitor takes execution time longer than the monitor interval time, an error message is logged as shown below. 

<Month Date Time> <BIGIP Hostname> err logger: EAV exceeded runtime needed to kill <FQDN or or domain>:<port>:<pool member IP>

For example: 
ltm monitor external /Common/example-external-monitor {
    defaults-from /Common/external
    destination *:*
    interval 30
    run /Common/example-external-monitor
    time-until-up 0
    timeout 91
    user-defined HOST example.com
    user-defined RECV "HTTP/1.1 200"
    user-defined URI /example/URI.xml
}
In the above monitor configuration, the script /Common/example-external-monitor is executed to verify the health of the pool member. The monitor verifies the connection to pool members at a set interval. If the monitor connection is failed within the timeout value, the pool member is marked as down. 

Environment

  • EAV External Health Monitors

Cause

The error message triggers when the previous monitor instance is hung or takes longer than the monitor interval value. 
Sample External monitor script: 
 

#!/bin/sh
NODE=`echo ${1} | sed 's/::ffff://'`
if [[ $NODE =~ ^[0-9]{1,3}.[0-9]{1,3}.[0-9]{1,3}.[0-9]{1,3}$ ]]; then
    # node is v4
    NODE=${NODE}
else
    # node is v6
    NODE=[${NODE}]
fi
PORT=${2}
##FOLDER="INBOX"
PIDFILE="/var/run/`basename ${0}`.${IP}_${PORT}.pid"
RECV='250'

# kill of the last instance of this monitor if hung and log current pid
if [ -f $PIDFILE ]
then
   echo "EAV exceeded runtime needed to kill ${NODE}:${PORT}" | logger -p local0.error 

Note: The above script looks for the PIDFILE exist, and kill the PIDFILE. 

   kill -9 'cat $PIDFILE' > /dev/null 2>&1
fi
echo "$$" > $PIDFILE
/usr/bin/curl-apd -k -v smtp://${NODE}:${PORT} 2>&1 | grep "${RECV}" > /dev/null
STATUS=$?
rm -f $PIDFILE
if [ $STATUS -eq 0 ]
then
    echo "UP"
fi
exit

Recommended Actions

To work around the issue you may follow any of the below-mentioned procedure. 

  1. If you are observing the logs very often, this could be due to monitor taking a long time to execute than the specified timeout. To work around the issue, increase the monitor interval at Local Traffic >> Monitor >> (monitor_name). 
    Note:  for the monitor to operate properly, the Interval and Timeout should be set correctly.  Please see K350: Recommended health monitor frequency and timeout values 
     
  2. If the issue triggers occasionally, this is probably the monitor script hung or took longer than expected, which is corrected by the script by deleting the hung process. 
     
  3. If the monitor using curl-apd command to verify the health of the pool member, you may either configure the timeout or maxtime for the curl command to wait for a response. 
    Example: 
    curl-apd -k -i --resolve $HOST:$PORT:$NODE https://$HOST$URI | grep -i "${RECV}" > /dev/null 2>&1 

    Add the timeout value to the command:
    curl-apd -k -i --connect-timeout 29 --resolve $HOST:$PORT:$NODE https://$HOST$URI |grep -i "${RECV}" > /dev/null 2>&1 
    (or)
    Add the maxtime value to the curl command. 
    curl-apd -k -i --maxtime 15 --resolve $HOST:$PORT:$NODE https://$HOST$URI | grep -i "${RECV}" >     /dev/null 2>&1

Additional Information

The default behavior for curl is to wait for the response endlessly, adding maxtime or timeout to curl-apd command will end the previous open monitor instance.
