Description

After upgrading F5 VELOS Chassis from F5OS-C version 1.6.2 to 1.8.1, customers may encounter a situation where all tenants within a newly created or existing partition fail to deploy and remain in an INOPERATIVE state. Attempts to create or redeploy tenants result in errors such as "Tenant deployment failed - Server is not responding." Log files may show repeated messages like "Key header check failed" from the api-svc-gateway process. Additionally, controller-manager pods in the kube-service-catalog namespace may enter a CrashLoopBackOff state due to expired Service Catalog API Server certificates, resulting in further deployment failures.

Environment

  • F5 VELOS Chassis (e.g., F5-VEL-CX410-AC, F101)
  • F5OS-C software upgrade from version 1.6.2 to 1.8.1
  • System configuration with two system controllers and multiple blades
  • Partitions with ID=1 (not limited to those named "default")
  • Tenants deployed within affected partitions
  • OpenShift/Kubernetes environment with Service Catalog API Server
  • Service Catalog API Server certificate present and potentially expired
  • Actions: Upgrade, partition recreation, tenant deployment, certificate renewal

Cause

Bug ID 1642081 (partition key corruption for partitions with ID=1 during upgrade from affected versions).
Bug ID 1962261 (expired Service Catalog API Server certificate causing controller-manager CrashLoopBackOff).

Recommended Actions

  • If tenants are INOPERATIVE and "Key header check failed" errors are present after upgrade, delete and recreate the affected partition from scratch.
  • If tenant deployment fails with "Server is not responding" and controller-manager pods are in CrashLoopBackOff, regenerate the Service Catalog API Server certificate by running the following command inside the orchestration_manager container:
    docker exec -it orchestration_manager ansible-playbook -v -i <inventory_path> playbooks/openshift-service-catalog/config.yml
  • Proactively renew the Service Catalog API Server certificate before expiration to prevent related deployment issues.
  • For HA environments, perform upgrades in a staggered manner and fail over tenants to the standby chassis to minimize downtime if partition recreation is required.
  • Once running F5OS-C 1.8.0 or higher, the partition key corruption issue is resolved for future upgrades, but existing corruption must be addressed as above.

Additional Information

  • The partition key corruption issue can affect any partition with ID=1, regardless of its name.
  • The upgrade to a fixed version (1.8.0 or higher) does not repair existing partition corruption; the partition must be recreated if already affected.
  • The Service Catalog API Server certificate expiration is a separate issue but can prevent tenant deployment if not renewed.
  • Running the certificate renewal playbook does not cause downtime for currently deployed tenants.
