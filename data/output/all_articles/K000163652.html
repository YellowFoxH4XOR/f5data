K000163652: Device trust fails with "This device is not found" when you click on 'Device Certificate Matches' button in Step 2

Type
Support Solution
Published
2026-11-03
Updated
2026-11-03
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000163652

Description

  • When trying to build Device Trust, you get below error in Step 2 - when you click on 'Device Certificate Matches' button. Step 1, there is no issue.
    This device is not found

Symptoms:

  • The initial HTTPS connection to the peer on TCP 443 succeeds, and the peer certificate is displayed.
  • Trust establishment fails when additional HTTPS connections are opened to the peer.
  • Logs on both devices show no explicit error.
  • Packet captures show large TCP segments with the Don't Fragment (DF) bit set that never reach the peer. The sender retransmits them repeatedly, and no ICMP "fragmentation needed" messages are returned.

Environment

  • You are building device trust between two different plaforms. For example vCMP guest on iSeries and Tenant on rSeries. Issue is not explicit with building trust between different platforms.
  • Devices in different management subnets, with at least one intermediate Layer 3 device on the path
  • icontrol.basic_auth set to enable (default) on both devices
  • tmsh list /sys icontrol-soap returns an empty configuration, httpd allow is All, and sshd allow is ALL
  • A device in the Forced Offline state is being added to or joined to a trust domain

Cause

  • Network MTU mismatch (packet drops for large packets) on the path between the management IPs. You will see packet drops. Not all packets reach the peer device. For example a 1527-byte TCP segment was split by TCP Segmentation Offload into 1448-byte and 79-byte segments. The 1448-byte segment never reached the peer, and its retransmissions were never received. The segments were within the MSS (1460 bytes) and had DF set, but no ICMP unreachable messages appeared in the captures, so they were either not generated or were dropped.
  • The root cause is in your network infrastructure limitation, not in BIG-IP.

Answer/Recommended Actions

  1. Verify basic reachability and allow lists on both peers.
    • Confirm ICMP, TCP 22, and TCP 443 connectivity between the management IPs.
    • Run tmsh list sys httpd allow and tmsh list sys sshd allow. Both must permit the peer.
    • Run tmsh list /sys icontrol-soap. An empty configuration means no restrictions are configured.
  2. Confirm the path MTU between the peers. Run the following from each device, replacing the placeholder with the peer's management IP:
    • tracepath -n <peer-mgmt-ip>
    • ping -M do -s 1472 <peer-mgmt-ip> -c3
    • Start with an ICMP payload of 1472 bytes. This corresponds to a 1500-byte IP packet (1472 + 8-byte ICMP header + 20-byte IP header).
    • Repeat from the other device to the first device.
    • If the 1472-byte ping fails with DF set and a smaller size succeeds, the path MTU is smaller than 1500.
  3. Correct the MTU on the network path. Check whether the smaller MTU is expected, for example because of a tunnel. If it is not expected, fix the misconfigured link or device so that the path supports 1500-byte packets, and ensure ICMP "fragmentation needed" messages are not blocked.
  4. Temporary workaround (not persistent). You can lower the MTU of the management interface to allow trust establishment. This change does not persist across reboots and is not a long-term fix: ip link set eth0 mtu <value>
  5. Alternative: establish the trust using a self IP address. Add the peer by its ConfigSync or self IP address instead of its management IP. Ensure that TCP 4353 (ConfigSync) is reachable between the peers.
  6. Peer state requirement. A device in the Forced Offline state cannot be added to a device trust. Bring the device online before adding it.
  7. If the issue persists after the above steps, collect data for F5 Support:
    • Run tcpdump -nni eth0 -s0 'host <peer-1-ip> or host <peer-2-ip> or arp or icmp' -w /var/tmp/${HOSTNAME%%.*}-eth0.pcap on both devices while reproducing the failure. Wait about 30 seconds between attempts.
    • Run iptables-save -c &>> /var/tmp/${HOSTNAME%%.*}-iptables.out on both devices before, during, and after testing.
    • Generate a qkview on both devices after testing (see K12878).
