Description

vCMP guest is not receiving traffic (for example, SYN packets) seen in interface level captures on the vCMP host, and span port captures on the connected switch.

Packets in question appear valid, with no bit flips or similar issues.

Problem appears to affect virtual servers reachable via specific VLANs only.

Environment

  • vCMP guest running on a single slot:

    vcmp guest ltm-guest-1 {
        <...>
        assigned-slots { 1 }
        <...>
        vlans {
            /Common/vlan100
            /Common/vlan200
            /Common/vlan300
        }
    }

  • With trunk members on multiple slots:

    net vlan /Common/vlan300 {
        interfaces {
            repro_trunk {
                tagged
            }
        }
        tag 300
    }

    net trunk External {
        interfaces {
            1/1.1
            3/1.1
        }
        lacp enabled
    }

  • MAC Masquerade configured on vCMP guest:

    cm traffic-group /Common/traffic-group-1 {
        mac 01:23:e9:bc:50:00
    }

Cause

Host's FDB entry is invalid on the slot where guest doesn't run, and maps the guest's MAC address as reachable via an external trunk.

tmsh show net fdb vlan all-records -hidden
----------------------------------------------------------------------
Net::FDB
VLAN                      Mac Address        Member            Dynamic
----------------------------------------------------------------------
vlan100                   01:23:e9:bc:50:00  trunk:32          yes
vlan200                   01:23:e9:bc:50:00  trunk:32          yes
vlan300                   01:23:e9:bc:50:00  trunk:External    yes

Continuing with the example described in the Environment, slot 3's FDB entry shows the guest's MAC masquerade address 01:23:e9:bc:50:00 as reachable out of trunk External for vlan300.
trunk:32 is the correct, expected value, since this is the virtual trunk mapped to the guest.

The mapping to External is invalid, and will lead to packets destined for that MAC address being dropped at the host level on slot 3.

The root cause of this issue is that the BIG-IP received a frame from the guest's MAC address via the External trunk. This should not happen unless there is a MAC address conflict with another device, or ARP spoofing is taking place in the network.

Recommended Actions

FDB entries on the host are updated when a unicast frame leaves the guest and egresses via a trunk member.
However, in the case of a guest running on a single slot, with trunk members on multiple slots, unicast egress frames will only leave via the slot where the guest is running. This is due to the default optimized value of sys db trunk.cluster.distribution.
FDB entries will also be updated when a broadcast frame is sent from the guest.

Clearing the issue

To clear the errant FDB entry, disable and re-enable ARP for an affected virtual address. For example:

tmsh modify ltm virtual-address /Common/10.10.10.1 arp disabled
tmsh modify ltm virtual-address /Common/10.10.10.1 arp enabled

This should trigger a series of GARPs (i.e. broadcast frames), updating the FDB on the affected slot.

Review the output of show net fdb vlan all-records -hidden on the vCMP host to confirm that the issue is cleared.

Preventing the issue

Investigate other network devices in the same layer 2 environment to determine if there is a MAC address conflict or misbehaving system.

Re-configuring the vCMP guest to run on all slots where trunk members reside will avoid the issue. This will cause unicast frames to leave via both slots, which would clear any errant FDB entries much faster.

Modifying sys db trunk.cluster.distribution to balanced on the vCMP guest will also avoid the issue, since unicast frames will leave via all trunk members.

tmsh modify sys db trunk.cluster.distribution value balanced

However, it should be noted that this increases backplane utilization, which can have performance implications in high traffic scenarios. This option is therefore discouraged

Additional Information

Packets can be dropped due to a large number of possible reasons. This issue is unlikely to occur in the vast majority of vCMP environments.
