Description

FQDN pool went offline even when the BIG-IP is able to resolve DNS and reach to the FQDN via TCP port 443 tested using curl command.

Environment

  • BIG-IP
  • LTM
  • FQDN Pool
  • Monitor failed
  • GUI
  • CLI

Cause

The BIG-IP has the "node default monitor" changed from default "none" to any "icmp ping" and this will applied to all the nodes even if the individual node doesn't has any monitor HC configured.

If the configured FQDN Pool doesn't allow ICMP ping, then the "default-node-monitor" configuration will cause the FQDN pool goes down (red)

example:
list ltm default-node-monitor 
ltm default-node-monitor {
    rule /Common/icmp
}

 

Recommended Actions

There are 3 options as listed below that can resolve this issue:

  • Restore the "default-node-monitor" to "none"
tmsh modify /ltm default-node-monitor rule none
tmsh save /sys config

  • Add another default monitor "https_443" with at least 1 healthy
tmsh modify /ltm default-node-monitor rule min 1 of { icmp https_443}
tmsh save /sys config

  • Alternatively, change the node FQDN Pool to have it own health check monitor (e.g. default monitor "https_443").
tmsh modify /ltm node removemeFQDN monitor https_443
tmsh save /sys config

Additional Information

If the issue impacts all FQDN pool members on one BIG-IP but not the HA peer, then it's possible that the dynconfd daemon responsible for resolving FQDN pool members is no longer working.

Check for logged messages in /var/log/dynconfd.log

If it has been some time since last logged message, this could indicate a problem even if the process is showing as UP.

Restart the daemon to restore operation:

tmsh restart sys service dynconfd

Note: Restart of dynconfd temporarily interrupts queries for FQDN name resolution and updates (deletion/creation) of ephemeral nodes/pool members in response to FQDN resolution changes. This should have no impact to traffic.
