Description

When using priority group activation in a pool configuration, traffic does not automatically shift back to the primary pool member after it becomes available.
This behavior persists even when session persistence is removed and session timeout values are adjusted.
Additionally, there may be a delay in new sessions being created with the primary pool member once it comes back online.

Traffic not load balancing back to original pool member after becoming available again.
We have set up a primary and standby pool member and configured the priority on the pool member but when the primary goes down, user sessions correctly connect to the standby.
But when the primary comes back up, user sessions remain on standby, causing issues due to backend server settings.

Environment

  • BIG-IP
  • Pool configured with priority group activation (priority-group values set for members).
  • min-active-members set to 1.
  • slow-ramp-time configured (default: 10 seconds).
  • Source address persistence profile applied.

 

Cause

The issue arises due to the following factors:

  1. Persistence Profile Conflict: A source address persistence profile was applied to the virtual server, which overrides priority group activation settings. This prevents traffic from shifting back to the primary pool member as expected when it becomes available again.
  2. Slow Ramp Time Configuration: The slow-ramp-time setting delays the full activation of a pool member for a specified duration (default: 10 seconds). This can cause a delay in new connections being directed to the primary pool member after it comes back online.
  3. Residual Connections: Existing active connections established before changes were made may continue until they expire, leading to unbalanced traffic distribution temporarily.

 

Recommended Actions

To resolve this issue and ensure proper failover behavior:

  1. Remove Persistence Profile: If using priority group activation, avoid applying any persistence profiles (e.g., source address persistence) on the virtual server as they override priority grouping logic.
  2. Adjust Slow Ramp Time Setting: Consider reducing the slow-ramp-time value from its default of 300 seconds (5 minutes) to a lower value such as 10 seconds unless there is a specific requirement for keeping it higher. Alternatively, avoid using slow ramp time entirely when combined with priority grouping configurations.

Example configuration snippet:

ltm pool <pool_name> {
...
slow-ramp-time 10
...
}

 

3. Reset Statistics After Changes: After making changes to configurations like removing persistence or adjusting ramp time, reset statistics on the pool members and monitor traffic distribution over time to confirm that new connections are correctly routed based on updated settings.

4. Avoid Combining Slow Ramp Time with Priority Grouping: As per best practices outlined in F5 documentation, avoid combining these two features since they can conflict and lead to unexpected behavior.
