K000141274: Client browsers are unable to access website with self-signed cert when SSLO interception is enabled, browser continually asks user to trust new forged cert

Type
Support Solution
Published
2024-09-30
Updated
2024-09-30
Applies to
  • F5 App Protect
  • F5 SSL Orchestrator
Source
https://my.f5.com/manage/s/article/K000141274

Description

When a website with a self-signed cert which is untrusted by SSLO is accessed via SSLO with 'Untrusted Certificate Authority' set to 'ignore' (so SSLO does not have the self-signed cert's issuer in its trusted cert authorities list), SSLO is seen to intercept the connection normally and give the client a forged certificate as usual, however when the user clicks "accept cert and continue" in their browser, they are just presented with another prompt about an untrusted server certificate, asking them to "accept cert and continue" again. They never actually get through to the actual website.

This only happens if the SSLO's signing cert is not already in the client browser's trusted CAs list.

 

Environment

BIG-IP SSLO

 

Cause

Our design is explicitly to not cache forged certs for self-signed webservers if the signing cert is untrusted.

This can result in the clients browser effectively "blocking" the site since the client doesn't implicitly trust the cert, but it's important to note that it's not the SSLO which blocks the website. If the client implicitly trusted the cert, or added it to it's trusted store, then the website would work fine.

 

Recommended Actions

Add the self-signed certificate from the webserver to the SSLO's trusted CA list, so that SSLO now trusts the server certificate and will cache its forged certificate for the client.

Alternatively, add the SSLO's signing cert to the trusted CAs list in the clients browser, so the user never gets a prompt to trust the incoming forged cert since it is signed by SSLO.
