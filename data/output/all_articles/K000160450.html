K000160450: Troubleshooting F5 Distributed Cloud Load Balancer to Kubernetes NodePort Service: Origin Pool Endpoint Discovery and Port Selection

Type
Support Solution
Published
2026-03-24
Updated
2026-06-12
Applies to
  • F5 Distributed Cloud Services
  • F5 Distributed Cloud WAF
Source
https://my.f5.com/manage/s/article/K000160450

Description

F5 Distributed Cloud Load Balancer configured with a Kubernetes NodePort service as an origin pool via service discovery fails with ClientError or UpstreamError. No origin pool endpoints are displayed in the LB performance tab, or endpoints intermittently disappear.

Environment

  • Product: F5 Distributed Cloud WAF / Multi-Cloud App Connect
  • Feature: TCP Load Balancer, Kubernetes Service Discovery
  • Backend: Kubernetes NodePort service (example manifest below)
  • Example service manifest:

    apiVersion: v1

    kind: Service

    metadata:

     name: service

    labels:

     app: service-app

    spec:

    type: NodePort

    selector:

    app: service-app

    ports:

     - name: web

    port: 443

    targetPort: 2222

  • Origin pool configured with discovered service name (e.g., service.service-discovery-name)
  • NodePort and Pod listen ports involved (e.g., NodePort 30998, Pod port 2222, Service port 443)
  • Environment may include VMware Kubernetes Service (VKS) or other K8s clusters
  • Distributed Cloud Customer Edge (CE) nodes as source/destination
  • Possible CE instability (pod crashes, tunnel flaps, memory alarms) noted in some cases

Cause

Misunderstanding of which port to specify in the origin pool definition for a Kubernetes NodePort service.
- The port required is the Pod Listen Port (the port field in the K8s service manifest), not the NodePort or container port.
- Service discovery for Kubernetes does not support automatic port selection; the port must be specified manually.
- If the port is not correctly specified, origin endpoints may not be discovered, resulting in ClientError.
- If the backend is unreachable (e.g., firewall, pod not ready), UpstreamError will be seen after endpoints are discovered.

Answer/Recommended Actions

  1. Verify Service Discovery Configuration
    • Ensure the correct service name is used (as suggested by the service discovery autocomplete).
    • Do not append cluster-id unless required by your environment.
  2. Specify the Correct Port in Origin Pool
    • For Kubernetes NodePort services, specify the Pod Listen Port (the port field in the service manifest, e.g., 443).
    • Do not use the NodePort value (e.g., 30998) or the container port (e.g., 2222).
  3. Validate Backend Health and Connectivity
    • Confirm that the backend pod is running, ready, and accepting connections on the specified port.
    • Ensure there are no firewall or network blocks between the CE and the NodePort service.
  4. Troubleshooting Steps
    • Use kubectl describe service <service-name> -n <namespace> to confirm service and port details.
    • Use kubectl get endpoints <service-name> -n <namespace> to verify endpoint population.
    • Use kubectl logs <pod-name> -n <namespace> to check for application-level errors.
    • If endpoints are not discovered, review service discovery configuration and port selection.
    • If UpstreamError occurs, check network path and pod readiness.
  5. Documentation and UI Notes
    • The "Automatic" port selection option is only available for Consul and Classic BIG-IP service discovery, not for Kubernetes.
    • If multiple ports are exposed by the service, auto-selection is not supported to avoid ambiguity.

Additional Information

  • When using NodePort services, the Node IPs are discovered automatically, but the port must match the Pod Listen Port as defined in the service manifest.
  • If the origin pool is misconfigured, endpoints will not be discovered and traffic will fail with ClientError.
  • If endpoints are discovered but backend is unreachable, traffic will fail with UpstreamError.
  • This behavior is expected and by design for F5 Distributed Cloud.
