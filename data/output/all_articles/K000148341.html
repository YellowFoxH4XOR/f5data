Description

Pool members are flapping frequently in Azure. This can affect multiple pool members and can occur inconsistently between multiple devices. The same pool member added to a High Availability pair may show as up on one device, while flapping on another.

Environment

  • BIG-IP Virtual Edition (VE)
  • Azure cloud
  • BIG-IP using the 'sock' network driver
  • BIG-IP sends a TCP SYN followed immediately by RST to pool members.
  • The 'provision.1nic' DB key is set to 'forced_enable'. This is common in BIG-IP VE configurations running on Azure. 
         Note: It was also observed that this issue can occur rarely on devices not matching this 'forced_enable' condition. In these instances, it is advised to verify if workaround solves the issue even if this condition is not matched.

Cause

This issue can occur due to known bug:

Bug ID 1013793: Pool members may flap on BIG-IP VE with provision.1nic set to forced_enable: https://cdn.f5.com/product/bugtracker/ID1013793.html

Recommended Actions

When you investigate this possible bug issue, you should first verify that the bug conditions are met for your environment. 

-- In a BIG-IP Virtual Edition (VE) System using the 'sock' network driver, as can be determined by reviewing “driver_in_use” column in the output of the following command:

 tmctl -d blade tmm/device_probed

-- The 'provision.1nic' DB key is set to 'forced_enable'. This is common in BIG-IP VE configurations running on Azure. Run the following command to verify:

tmsh list sys db provision.1nic

-- Use a packet capture to verify that the BIG-IP sends a TCP SYN followed immediately by RST to pool members.

 

The work around commands below will take effect on traffic as soon as they are executed, any incoming IPv4 or IPv6 packets on interfaces matching "eth+" will be dropped immediately. This rule is applied to the raw PREROUTING chain, which processes packets at a very early stage, so the traffic is impacted right away.

Note: If there are concerns about any negative impact to traffic when applying this workaround, it is highly recommended to generate a UCS backup and save it off the BIG-IP, then complete these changes during a maintenance window.

 

1) Use the following commands to work around this on a running system (the word 'command' is a required part of what should be typed in):

    command iptables  -t raw -I PREROUTING 1 -i eth+ -j DROP

    command ip6tables -t raw -I PREROUTING 1 -i eth+ -j DROP

 

2) In addition to that, to ensure the workaround persists after TMM restarts or system reboots, add the following to /config/user_alert.conf:

alert tmm_id1013793_workaround "HA reports tmm ready" {

        exec command="iptables  -t raw -D PREROUTING -i eth+ -j DROP";

        exec command="ip6tables -t raw -D PREROUTING -i eth+ -j DROP";

        exec command="iptables  -t raw -I PREROUTING 1 -i eth+ -j DROP";

        exec command="ip6tables -t raw -I PREROUTING 1 -i eth+ -j DROP";

}

 

3) Then restart alertd by running:

tmsh restart sys service alertd

 

Once you have completed these steps, please test to ensure everything is working as expected.
