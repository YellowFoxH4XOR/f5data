Description

The following article provides a checklist for when an IPsec tunnel establishes correctly but packets fail to be forwarded over the tunnel.

Environment

  • IPsec (IKEv1 or IKEv2) tunnel configured and established on a BIG-IP device.
  • Packets that are expected to be tunneled do not arrive at the endpoint.
This article sometimes makes a distinction between tunnel mode and interface mode. The mode is configured on the ipsec-policy object. Whenever the IPsec mode is being referenced, the mode type will be in italics.

Verifying established Security Associations (SAs) on the BIG-IP

This article does not cover troubleshooting IPsec tunnel establishment or troubleshooting IPsec SAs. To verify that the tunnel established correctly, on both IPsec peers verify that the IKE SAs and IPsec SAs are in an established state and have the same SPI numbers.

To view the established SAs, use the following command and pay attention to the "in" and "out" direction as well as the SPI.

Cause

In the majority of cases, problems with an IPsec tunnel are related to missing or incorrect configuration items.

Recommended Actions

The following items pertain only to troubleshooting the BIG-IP.

Check whether ESP packets are sent or received

ESP packets are the encrypted private network packets and are not part of the ISAKMP tunnel negotiation. In the example above from the tmsh show net ipsec ipsec-sa all-properties command, the SPI numbers are highlighted.The SPI number is always unencrypted in the ESP payload.

Use tcpdump to verify the following things:

  • Whether ESP packets are seen at all.
  • Whether ESP packets inbound and outbound match the SPI numbers in the IPsec SA.
  • Whether ESP packets are seen in only one direction.
The following tcpdump syntax may be useful:
 
tcpdump -s 0 -i 0.0:nnn -w /shared/tmp/esp.pcap 'esp or port 500 or port 4500'

The command above catches:
  • All ISAKMP with port 500, which should not strictly be necessary if the tunnel is healthy.
  • All raw ESP.
  • All ESP encapsulated in port 4500 due to NAT Detection.
Verify whether a packet generated from a network local to the BIG-IP, which should be tunneled, results in an outbound ESP packet:
 
tcpdump -s 0 -i 0.0:nnn -w /shared/tmp/esp.pcap 'esp or (net <selector source IP> and net <selector destination IP>)'
 
Example:
 
tcpdump -s 0 -i 0.0:nnn -w /shared/tmp/esp.pcap 'esp or (net 10.1.1.0/24 and net 10.2.1.0/24)'

The selector IPs are used as part of the filter. If you see no packets matching the selector source and destination, this would explain why packets are not traversing the tunnel.
 
Look for ICMP packets

ICMP packets can provide valuable clues. Unreachable messages are often overlooked during troubleshooting.
  • Protocol unreachable packets can indicate that the ICMP source is not listening for ISAKMP or ESP packets.
  • Network unreachable packets can indicate that the ICMP source has no route for the intended network.
  • If the BIG-IP generates ICMP network unreachable packets for the private networks, this could indicate the absence of a route or Virtual Server.
  • If the BIG-IP generates protocol unreachables for ESP, this may indicate a missing self IP. It may also indicate that the sys db ipsec.lookupip, ipsec.lookupspi or ipsec.passesp have been changed from the default values.


Verify the local IP

A self IP must be configured on the BIG-IP to use as the local address of the tunnel. A floating self IP is permitted.

  1. If the local IP used in the ipsec-policy (for tunnel mode) or the tunnels object (for interface mode) does not exist as a self IP, then the tunnel can establish but ESP packets will be rejected.
  2. The local IP cannot be a Virtual Address that does not have self IP.
  3. It is bad practice to use a Virtual Address even when it exists as a self IP.
  4. The local IP should be attached to the VLAN of the next hop to the remote peer address.


Verify the route to the remote network

A specific or default route must exist to the remote private network. In order for the BIG-IP to know that it has somewhere to forward the packet a route of some kind must exist.

  • In interface mode the route must be an interface route that points to the correct IPsec interface.
  • Interface mode can utiliize a gateway route only if the route is dynamically learned via a routing protocol such as BGP over the established tunnel.
  • In tunnel mode a normal gateway route is used.
  • While a gateway route may point to an external (Internet facing) IP, the packet will not be accidentally forwarded to the default gateway device as long as the selector exists.
Example tunnel mode route:
net route to-remote-private {
    gw 172.16.1.254
    network 10.1.1.0/24
}

Example interface mode route:
net route to-remote-private {
    interface /Common/ipsec_tunnel
    network 10.1.1.0/24
}
 

Verify the Virtual Servers

A Virtual Server must exist to catch the private network packets. A wildcard forwarding Virtual Server will suffice, but is undesirable to have a wildcard Virtual Server listening on an external interface.

For connections that establish from the BIG-IP side, create a Virtual Server that has

  • a "destination" of the network configured in the "destination-address" of the traffic-selector and
  • a "source" matching the "source-address" of the traffic-selector and
  • is listening only on the internal VLAN(s) that new connections arrive.
Virtual Servers are stateful, meaning that traffic returning to the aforementioned Virtual Server will be returned to the intended destination. However, if the remote IPsec endpoint is sending new connections to the BIG-IP then a reverse Virtual Server is required. Create a Virtual Server that has
  • a "source" of the network configured in the "destination-address" of the traffic-selector and
  • a "destination" matching the "source-address" of the traffic-selector and
  • is listening only on the external VLAN that the IPsec tunnel is using.
Interface mode is slightly different. Instead of the Virtual Server listening on the external VLAN, the IPsec interface must be in the "vlans" list, not the external VLAN.

 

Additional Information

There are a number of articles that explain how to change some IPsec sys db values for specific scenarios. The sys db values must never be altered for the purpose of troubleshooting. For a normal site-to-site tunnel, if the sys db ipsec.* values are altered from defaults then problems are compounded, not solved.
