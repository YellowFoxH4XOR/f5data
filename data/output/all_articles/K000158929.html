K000158929: Effects of packet loss on serverside of SSLO seem to be greatly magnified when service is set to intercept instead of bypass

Type
Support Solution
Published
2025-12-29
Updated
2025-12-29
Applies to
  • F5 App Protect
  • BIG-IP SSL Orchestrator: 17.5.0
Source
https://my.f5.com/manage/s/article/K000158929

Description

The effects of packet loss on serverside of SSLO can be greatly magnified when service is set to intercept instead of bypass - leading to final page load times of (for example) 30-45 seconds instead of 5-10 seconds in an example case.

 

Environment

Big-IP SSLO


Cause

When decryption is enabled on the service (ie. service action is set to "intercept"), the SSLO has to wait for the entire TLS record to be received from the server before it decrypts it and forwards it on to the "intercept" service. 

 

Recommended Actions

None.


Additional Information

When decryption is disabled on the service (ie. service action is set to "bypass" instead of "intercept"), this decryption is not required and the TCP segment is just passed on directly to the service, and thus can go all the way back to the client, and the overall TCP throughput achieved is much higher when packet loss is a consideration, especially if Selective Acknowledgements (SACK) are enabled in the TCP connection and out of order segments do not need to be re-transmitted.

Basically when decryption at the service is enabled on SSLO, it is going to have a similar effect to disabling SACK on the TCP connection, since each TLS record has to be completely received by the SSLO from the server before it can be decrypted by SSLO and sent to the service.

This is a design level issue - the serverside connection is expected to have very little packet loss if a decryption service is being used, as the entire TLS record needs to be present to be decrypted by SSLO before it can pass the decrypted data on to the service.
