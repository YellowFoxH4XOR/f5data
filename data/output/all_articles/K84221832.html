Topic

This article covers Port Block Allocation (PBA) mode for Large Scale NAT (LSN) pool configuration.

PBA is a translation mode option that reduces CGNAT logging overhead by creating a log entry only when a subscriber first establishes a network connection, assigning a port block, and when the system releases the block when no more connections are using it.

There isn't a single correct solution to adequately configure PBA because each customer environment is different. The following information helps you understand the issues involved and outlines some of the tools available. If you require further assistance deploying PBA in your environment, contact F5 Technical Support .

Understanding and configuring PBA sizing options

CGNAT PBA works allocates a contiguous set of source translation endpoints called port blocks. These port blocks are associated to a client by one IP address and a block of ports. Port blocks are allocated on-demand and have a fixed size.

LSN pool configuration settings are closely interrelated and determine how the blocks are allocated to the clients. Choose these settings carefully to adequately and efficiently service clients that may require a different number of simultaneous connections. Careful analysis and testing is required to find optimal values.

The following LSN pool configuration settings are covered in this article:

  • Member List: Specifies the set of translation IP addresses available in the pool as a collection of IP prefixes with their prefix lengths.  All public-side addresses come from the subnets entered in this property in CIDR format.
  • Port Block Allocation: Configures the port block settings for PBA mode, which include:
    • Block Size: The number of ports allocated in a block. The default value is 64.
    • Client Block Limit: The maximum number of blocks assigned to a single subscriber. The default is 1.
  • Port Range Low: Specifies the lowest range port number available for use with translation IP addresses. The default value is 1025.
  • Port Range High: Specifies the highest range port number available for use with translation IP addresses. The default value is 65535.
  • Inbound Connections: Specifies the inbound-connection mode for incoming connections to translation endpoints.

Choosing the optimum block size

You can estimate the number of total available blocks on a BIG-IP system configured with CGNAT PBA with the following formula:

(port-range * IP Pool Size) / block-size

For example, you use the following settings:

Port Range Low: 1025
Port Range High: 65535   
Member List:  10.1.1.0/21
Block Size: 128

This example provides 64510 ports per IP address, 2046 usable IP addresses, and 128 ports per IP. A total of (64510 * 2046) / 128 = 1031152 blocks are available for allocation to clients.

In an ideal configuration, the majority of clients will use only one port block. To accommodate clients who require more ports, you must increase the Client Block Limit from the default value of 1 to a greater value. Increasing the Client Block Limit and allowing clients to use more than one block is preferable to choosing a larger block size, which may result in a large number of ports in a block to remain unused. Unused ports will not be available to other clients because you can only allocate a port block to one client at a time.

Choosing the optimum block size is a trade-off based on balancing operational priorities.

When you increase the block size, you may encounter the following behaviors:

  • Less processing is required.
  • Less logging is required.
  • Blocks are allocated less efficiently.  A subscriber who cannot make use of all the ports in a block will waste ports that are unused because you cannot share them with other subscribers.
  • The blocks may be distributed unevenly across the different Traffic Management Microkernels (TMMs), resulting in prematurely exhausted address space.

When you reduce the block size, you may encounter the following behaviors:

  • More processing is required.
  • More logging is required.
  • Blocks are allocated more efficiently.
  • Performance may be impaired.
  • Can interfere with some applications, such as peer-to-peer, as the IP translation address changes more frequently. You can mitigate this issue by enabling the PBA persistence option.
  • Setting the block size to a value significantly less than the default value of 64 will reduce the maximum achievable connection rate and number of concurrent connections

Other block size considerations

Blocks at the end of the port range that are smaller than the block size will be unused. 

Note: Selecting a port block size that is not evenly divisible by the number of translation ports available will cause the BIG-IP Configuration utility to produce a warning message.

For example:

Port Range Low: 1025
Port Range High: 65535  
Block Size: 64

A total of 64510 translation ports available. Therefore, 1007 port blocks are available per member list IP, and 62 ports are unused. 

Inbound connections

By default, the Inbound Connections setting is set to disabled. When disabled, the number of potential connections available per client and per block increase because you can reuse the same translation endpoint for concurrent connections from the same subscriber to multiple destinations. This option allows you to use port blocks efficiently.

For example:

Reusing the same translation endpoint when disabled:

CLIENT (internal address:port)          CLIENT (external address:port)               SERVER (host endpoint)
10.50.0.1:2001                 <->      40.0.0.100:1026                  <->         60.0.0.10:80
10.50.0.1:2002                 <->      40.0.0.100:1026                  <->         70.0.0.20:80

If the Inbound Connections option is set to Automatic, a translation endpoint within a given block has a unique map to each server host endpoint and may not be shared. The Automatic setting uses port blocks less efficiently, but may be required for SIP or peer-to-peer protocols.

A new translation endpoint in use when set to Automatic:

CLIENT (internal address:port)           CLIENT (external address:port)        SERVER (host endpoint)
10.50.0.1:2001                    <->    40.0.0.100:1026                 <->   60.0.0.10:80
10.50.0.1:2002                    <->    40.0.0.100:

    1051                 <->   70.0.0.20:80

    Block Lifetime and Block Idle Timeout options

    The Block Lifetime option sets the time that a client may use a block, even if there are existing connections. The default setting for this option is zero, which is the equivalent to an infinite time out. Therefore, a client uses the same block until the Block Idle Timeout option times out all of their connections.  A block idle timeout value of zero results in less logging, but clients may reuse the same set of ports indefinitely, which RFC6056 states can make attacks based on guessing ephemeral ports easier to mount. Alternatively, you can specify a finite (non-zero) block lifetime value, which helps randomize port allocation and a useful way to recycle a few small blocks.

    For example:

    Block Lifetime: 0
    Block Idle Timeout: 3600

    Clients will use the same port block until all of their connections are idle for 3600 seconds (1 hour), after which the block is released into the pool for other clients.

    Block Lifetime: 3600
    Block Idle Timeout: 3600

    In the previous example, after a client uses a port block for 3600 seconds and requests a new outbound connection, the client is assigned a new block. Existing connections continue to use the originally assigned block, and all new connections use the newly assigned block. The newly assigned block is now the active block, and the original block is designated as a zombie block.

    Zombie blocks

    A port block becomes a zombie block when new subscribers can no longer use the block because its block lifetime expired and it still has active connections. One or more zombie blocks may accumulate under the following conditions:

    1. You set the Block Lifetime option to a non-zero value.
    2. Subscriber connections are long-lived.
    3. You make a configuration change that invalidates a block and turns it into a zombie.

    To help control zombie blocks, you can set a non-zero zombie timeout value. When this timer expires, the associated long-lived zombie block connections are killed, but the persistence records are not deleted until the persistence timeout expires. If the application reconnects before the persistence records expire, PBA will attempt to reallocate the same block. However, this action may not be possible if the subscriber has reached their block limit or another subscriber is using that block. 

    Note: Zombie blocks do not count towards the client block limit.

    For more information about CGNAT persistence, refer to K14823: Overview of CGNAT Persistence.

    Troubleshooting tools for fine-tuning PBA deployments

    You can monitor the CGNAT port block usage several different ways. The following tools may assist you in fine-tuning PBA configurations.

    Viewing CGNAT port block usage using the TMOS Shell (tmsh)

    You can use the show ltm lsn-pool <LSN-POOL-NAME> raw command syntax to view the following information:

    • Active, requested, and failed translation mappings
    • Persistence request failures
    • Active port blocks (currently allocated)
    • Clients using max port blocks
    • Total port block allocations, failures and freed
    • Total failed client connections caused by block limit reached
    • Active zombie port blocks
    • Total zombie port blocks created and deleted

    The lsndb command

    Important: This command may add some resource usage stress to a system already under significant traffic load. Use with caution.

    • lsndb list client: Displays the number of ports that are used out of the allocated block, per client. You can determine how efficiently clients are using port blocks.

      The lsndb list client command output appears similar to the following example:

      LSN Client Connections
      Client                                              Connections
      -------------------------------------------------------------------
      100.97.31.204                                       1
      100.96.56.36                                       62
      100.27.76.133                                      28
      100.7.76.139                                        0
      100.27.4.42                                        10
      100.17.47.38                                        0

    • lsndb list pba: Displays the list of allocated port blocks. You can determine how many clients have more than one allocated port block.
    • lsndb list persistence: Displays the list of all persistence entries per client.
    • lsndb list endpoint:  Displays reserved endpoints.
    • lsndb list inbound: Displays only the inbound mappings.

    Monitoring CGNAT errors

    When the BIG-IP platform cannot find the translation endpoint for a subscriber, PBA logs a message similar to the following in the /var/log/ltm file:

    info tmm[25077]: 1 "Apr 29 2019 14:38:39 PDT","192.168.1.1","test.example.com","LSN_ERR","PBA - Translation failed","10.10.1.1","2982","0","UDP","::","0","0"

    A timeout triggers this log message when the BIG-IP system looks for a new port block for a client, but can't find it due to a shortage of available blocks, or the systems takes too long to find an available port block.

    An insufficient number of available blocks may cause a sudden increase in the number of these log messages, which indicates that you need to change the block allocation configuration.
