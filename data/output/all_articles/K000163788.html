K000163788: Repeated “Flow expired (sweeper) (idle timeout)” Messages for BIG-IP HTTP/HTTPS Health Monitors

2026-10-20
Applies to

Source

Description

BIG-IP logs repeated messages such as below sample logs under "/var/log/ltm":

<Date & Time> <Hostname> err tmm5[5090]: 01230140:3: RST sent from <Source-IP:PORT> to <Destination-IP:PORT>, [0x322bdb7:733] {peer} Flow expired (sweeper) (idle timeout)

The messages could be associated with either 'HTTP' or 'HTTPS' health-monitor probes to a backend pool member. The available evidence did not necessarily confirm any memory exhaustion or termination of active application sessions.

Environment

  • BIG-IP LTM
  • An HTTP or HTTPS health monitor assigned to a backend pool
  • Health-monitor probes originate from a Non-floating Self-IP

Cause

The exact cause may vary. The messages can occur when an HTTP or HTTPS health-monitor connection remains Idle or does not complete before the configured timeout.

Possible contributing conditions include:

  • The monitor request uses an incorrect application path.
  • The backend requires a specific Host header.
  • The configured Receive String does not match the backend response.
  • The HTTP transaction remains incomplete or idle.
  • The backend does not close the connection after returning the response.
  • The monitor timeout is reached before the expected response is received.

The available evidence should not necessarily establish TMM Exhaustion, critical Host-memory pressure, CPU saturation, or Memory-triggered aggressive sweeping as the cause.

Answer/Recommended Actions

1) Review the HTTP / HTTPS monitor configuration:

  • Confirm the monitor assigned to the affected pool.
  • Verify that the request path is a valid health-check endpoint.
  • Confirm the HTTP version and required headers.
  • Verify that the Receive String matches a reliable backend response.
  • Review the monitor interval, timeout, and send/receive settings.

2) Create a dedicated HTTP / HTTPS monitor:

  • Use an endpoint that reliably returns a healthy response.
  • Include the required Host header if the backend uses virtual hosting.
  • Consider including Connection: Close so the backend is requested to close the connection after sending its response.
  • Use a Send String that matches the confirmed backend response. Below is an Example format:
GET /health HTTP/1.1\r\nHost: Web.Example.Com\r\nConnection: Close\r\n

Replace the path, hostname, and Receive String with values appropriate for the backend application.

3) Validate the backend response:

  • Confirm that the backend accepts connections from the self IP used by the monitor.
  • Verify that the backend responds promptly to the configured request.
  • Confirm that TLS negotiation and required HTTP headers succeed.
  • Check backend logs for rejected, delayed, incomplete, or persistent monitor connections.

4) Test changes during a Maintenance window:

  • Apply the dedicated monitor during a planned maintenance period.
  • Compare monitor results and system logs before and after the change.
  • If appropriate, compare the existing monitor with the dedicated monitor to determine whether request or response behavior contributes to the idle flows.

5) Correlate future events:

  • Compare each sweeper message with monitor execution and backend-server logs.
  • Confirm whether the affected flow is monitor traffic or application traffic.
  • Collect the monitor configuration, backend response behavior, and relevant BIG-IP logs if the messages continue.

6) Continue resource monitoring:

  • Review TMM memory, host memory, CPU, swap usage, and aggressive-mode sweeper events.
  • Do not attribute the messages to memory pressure unless resource statistics overlap the event period and show a corresponding exhaustion condition. 

Additional Information

  • A Flow expired (sweeper) (idle timeout) message indicates that BIG-IP expired an idle flow and sent a TCP reset for that flow.
  • When the flow belongs to an HTTP / HTTPS health monitor, the event may affect the monitor transaction or pool-member health evaluation rather than active user sessions.
  • Receiving an HTTP response does not necessarily mean that the monitor transaction closes immediately. The transaction may remain open until the Receive String is matched, the connection is closed, or the monitor timeouts reached.
  • Monitor interval and timeout values should not be changed without first validating the backend request path, Host header, response content, connection behavior, and application-side logs.
