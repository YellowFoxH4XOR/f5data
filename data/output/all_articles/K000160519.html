K000160519: Pool member flapping due to delayed HTTPS responses

Description

Pool members intermittently flap (transition between UP and DOWN states) on BIG-IP. Pool members are marked down by HTTPS health monitors despite backend servers appearing healthy. Log messages may misleadingly show "Response Code: 200 (200)" as the last error, but the actual cause is delayed or missing responses to health checks exceeding the configured monitor timeout.


Environment

  • BIGIP LTM
  • HTTPS monitor with interval 5 seconds, timeout 16 seconds, custom send string, expecting "HTTP/1.1 (200)" in response
  • Multiple pool members are experiencing flapping

Cause

Backend server slowness in responding to HTTPS health checks, specifically delays in the TLS handshake (e.g., 17 seconds to reply with "server hello"), which exceeds the configured monitor timeout (16 seconds). This results in the BIG-IP marking the server as down, causing pool member flapping. Packet captures confirm the delayed server response during the monitor interval.


Answer/Recommended Actions

  • Engage backend server administrators to investigate and resolve the cause of delayed TLS handshake responses.
  • As a workaround, increase the HTTPS monitor interval and timeout, for example:
    • Set interval to 10 seconds
    • Set timeout to 31 seconds (recommended formula: timeout = (3 x interval) + 1)
  • Review and adjust monitor settings to balance timely failure detection with tolerance for backend latency.


Additional Information

The misleading "Response Code: 200 (200)" in logs refers to the last successful response, not the current failure.

Delayed TLS handshakes or slow HTTP responses from backend servers are common causes of monitor flapping.

Increasing monitor timeout values is a mitigation, not a root cause fix; backend performance should be addressed.
