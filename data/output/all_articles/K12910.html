Known Issue

iRules using the IP::addr iRule command with a netmask in dotted-decimal notation may produce incorrect results. This occurs because F5 inadvertently removed the ability to use the IP::addr iRule command with dotted-decimal netmasks from the product in BIG-IP version 10.0.0. iRules using the IP::addr iRule command with a netmask in slash notation work as expected.

For example, in the following iRule, the log #1 statement uses the IP::addr iRule command with a netmask in dotted-decimal notation, and the log #2 statement uses the IP::addr iRule command with a netmask in slash notation:

when CLIENT_ACCEPTED {
log "#1 - 10.1.1.1/255.255.0.0 = [IP::addr 10.1.1.1/255.255.0.0 equals 10.1.0.0]"
log "#2 - 10.1.1.1/16 = [IP::addr 10.1.1.1/16 equals 10.1.0.0]"
}

The BIG-IP system properly loads the above iRule. However, the iRule returns incorrect results; both commands should produce a positive match, but the log #1 statement returns 0 (does not match), and log #2 returns 1 (matches).

This issue occurs when the following condition is met:

  • The IP::addr iRule command uses a netmask in dotted-decimal notation.

Impact

The IP::addr iRule command returns incorrect values.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • The IP::addr iRule command performs an incorrect comparison of IP address/subnet/supernet to IP address/subnet/supernet.

Workaround

To work around this issue, you can change the iRule syntax so that the netmask is in slash notation.

Impact of workaround: None.

For example, the following iRule uses the IP::addr command with a dotted-decimal netmask:

when CLIENT_ACCEPTED {
log "10.1.1.1/255.255.0.0 = [IP::addr 10.1.1.1/255.255.0.0 equals 10.1.0.0]"
}

You can work around the issue by changing the IP::addr command to specify the netmask in slash notation as displayed in the following example:

>when CLIENT_ACCEPTED {
log "10.1.1.1/16 = [IP::addr 10.1.1.1/16 equals 10.1.0.0]"
}
