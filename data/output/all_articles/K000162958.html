K000162958: NGINX Ingress Controller Reload Failures Caused by NGINX App Protect WAF Zombie Processes

Type
Support Solution
Published
2026-08-17
Updated
2026-08-17
Applies to
  • NGINX Products
  • NGINX Ingress Controller: 5.3.0
Source
https://my.f5.com/manage/s/article/K000162958

Description

NGINX Ingress Controller reloads can fail with sh: 1: Cannot fork when zombie cp processes generated by NGINX App Protect WAF exhaust the controller pod’s PID limit. This can cause stale upstream configuration, endpoint update failures, API 503 responses, and client connection failures.

Example error:

nginx reload failed: command /usr/sbin/nginx -s reload -e stderr

stderr: "sh: 1: Cannot fork"

finished with error: exit status 2

Environment

  • NGINX Ingress Controller
  • Kubernetes
  • NGINX App Protect WAF enabled
  • NGINX configuration managed through Kubernetes Ingress resources
  • Controller pod configured with a cgroup PID limit

Cause

This issue is associated with a known NGINX Ingress Controller defect tracked as NIC Bug 10421.

During NGINX reloads, NGINX App Protect WAF can generate helper cp processes that are not properly reaped. These processes remain as zombies and accumulate until the controller pod reaches its configured PID limit. Once the limit is reached, the shell cannot create a new process and NGINX reloads fail with Cannot fork.

The issue may also produce:

  • Failed EndpointSlice or endpoint updates
  • HTTP 503 responses from the controller API
  • Stale upstream server configuration
  • Client connection failures
  • Increased nginx_ingress_controller_nginx_reload_errors_total metrics
  • Large numbers of zombie cp processes

The -enable-config-safety feature does not resolve this issue because the failure is caused by PID exhaustion during NGINX App Protect WAF processing rather than invalid NGINX configuration.

Recommended Actions

  1. Upgrade NGINX App Protect WAF to a release containing the fix.
  2. Until the upgrade is completed, periodically restart the NGINX Ingress Controller deployment before the PID limit is reached:
    kubectl rollout restart -n <namespace> deployment/<nginx-ingress-deployment-name>
  3. If required, automate the restart with a Kubernetes CronJob. Adjust the schedule according to the observed rate of zombie-proces s accumulation:

    apiVersion: batch/v1
    kind: CronJob
    metadata:
    name: nginx-ingress-pod-refresher
    namespace: <namespace>
    spec:
    schedule: "0 0 * * 0"
    jobTemplate:
    spec:
    template:
    spec:
    serviceAccountName: <<sCRub_LICENSEKEY_bPkYG6Hi8UKNCCxDnDLXG>-name>
    containers:
    - name: kubectl
    image: bitnami/kubectl:latest
    command:
    - /bin/sh
    - -c
    - kubectl rollout restart deployment/<nginx-ingress-deployment-name> -n <namespace>
    restartPolicy: OnFailure

    The CronJob is an example workaround and must be adapted to the deployment names, permissions, security requirements, and maintenance procedures of the environment.

  4. Monitor PID usage in the controller pod:
    read -r CUR < /sys/fs/cgroup/pids.current; echo "$CUR"
    read -r MAX < /sys/fs/cgroup/pids.max; echo "$MAX"
  5. Monitor the following indicators:
    • pids.current compared with pids.max
    • Number of zombie processes
    • nginx_ingress_controller_nginx_reload_errors_total
    • Endpoint update errors
    • NGINX reload failures containing Cannot fork
  6. Confirm that a deployment restart removes the accumulated zombie processes and restores successful NGINX reloads.

Additional Information

  • The rolling restart is a temporary workaround and does not correct the underlying NGINX App Protect WAF defect.
  • The workaround interval should be based on the observed reload frequency and PID consumption rate.
  • Do not rely on -enable-config-safety as a mitigation for PID exhaustion caused by NGINX App Protect WAF processing.
