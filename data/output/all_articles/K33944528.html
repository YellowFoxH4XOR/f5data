Description

In the following example, there are 2 namespaces. One is with label istio-injection=enabled, which injects a sidecar for pod spun in that namespace and another one is without any label. Below are the high-level information on cert generation and accessibility for above mentioned namespaces:

$ kubectl get namespace –show-labels
with-sidecar-injection      Active   138d   istio-injection=enabled
without-sidecar-injection   Active   138d   ca.istio.io/override=true

$ kubectl get pods -n without-sidecar-injection
NAME         READY    STATUS      RESTARTS     AGE
sleep-5f5f494757-vmvzk  1/1    Running   0       39m 

$ kubectl get secrets -n without-sidecar-injection
NAME                      TYPE                        DATA AGE
default-token-9s8qn   kubernetes.io/service-account-token   3   8d
istio.default       istio.io/key-and-cert               6   7d23h
istio.sleep         istio.io/key-and-cert               6   7d23h
sleep-token-wfv68   kubernetes.io/service-account-token   3   8d

$ kubectl get sa -n without-sidecar-injection
NAME   SECRETS   AGE
default   1     10d
sleep     1     10d

As you can see in the output above, we do create a istio.io/key-and-cert type secret for pods without a side car which consists of CA cert, Root cert, Chain-cert and Key. This is only accessible by the respective service account created in the namespace and is created by the citadel agent. For legacy applications, Aspen Mesh generates the Secrets with TLS credentials and automatically manages the licycle of these credentials by either mounting them as volume or by directly from the Kubernetes API server. For more information, please consult this. 

$ kubectl get pods -n with-sidecar-injection
NAME                   READY    STATUS    RESTARTS    AGE
httpbin-74fb669cc6-wn2ch  2/2     Running     0       7d22h

$ kubectl get secrets -n with-sidecar-injection
NAME                    TYPE                           DATA  AGE
default-token-46g4r   kubernetes.io/service-account-token   3   11d
httpbin-token-qx2n2   kubernetes.io/service-account-token   3   11d

$ kubectl get sa -n with-sidecar-injection
NAME    SECRETS   AGE
default    1      11d
httpbin    1      11d

Whereas in the with-sidecar-injection, we create a kubernetes.io/service-account-token secret for the pod as the certificates are generated automatically by the SDS (Secret Discovery Service) generation process which is default in Aspen Mesh. The certificate is only accessible by the istio-proxy of the application pod and since it lives in memory, the private key never leaves the node. Please read this for more information. You can check the certificate at:

$ istioctl proxy-config secret httpbin-74fb669cc6-wn2ch.with-sidecar-injection -o json | jq '.dynamicActiveSecrets[0].secret.tlsCertificate.certificateChain.inlineBytes' | sed 's/"//g' | base64 --decode | openssl x509 -noout -text

For SDS mode, all the certs and Keys live in memory of istio-proxy. To view that you can port-forward the httpbin pod with sidecar and check for secretsconfigdump at http://localhost:15000/config_dump in configdump of envoy proxy. For example:

Additional Information

With the citadel case, the private key is created in the secret (which is a namespace wide object). It is better to define the necessary RBAC rules and Authorization in such a way that only authorized user gets to the pod. With SDS, Since the key is only retrieved by localhost via querying on envoy proxy on port 15000 and not via external host. Here is the basic workflow of CSR and Cert generation: The exchange of key and certs are done via communication between SDS and envoy which happens through unix socket and are done in memory. Therefore this should suffice for integrity and confidentiality. With 1.6 and above, we have distroless istio-proxy so we cannot have a shell to look inside but if you have an old 1.5 environment, you can see that the directory /etc/istio/proxy/sds has all the files open by pilot-agent over unix socket.
