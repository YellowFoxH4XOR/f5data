Known Issue

Synchronizing BIG-IP APM access policies among Virtual Clustered Multiprocessing (vCMP) guests may cause the target guest's secondary blade to reboot.

This issue occurs when all of the following conditions are met:

  • You deploy the vCMP guests on a chassis system with multiple blades installed.
  • The target vCMP guests reside on more than one slot in the cluster.

Impact

Configuration validation may fail, causing the mcpd process to reboot the blade.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

    slot2/<hostname> err mcpd[<PID>]: 01070734:3: Configuration error: Configuration from primary failed validation:
    01020036:3: The requested Access Profile (/Common/ap_access) was not found.... failed validation with error 16908342.
    slot2/<hostname> notice promptstatusd[<PID>]: 01460006:5: semaphore mcpd.running(1) held
    slot2/<hostname> warning promptstatusd[<PID>]: 01460005:4: mcpd.running(1) held, wait for mcpd
    slot2/<hostname> err clusterd[<PID>]: 013a0004:3: IO error on recv from mcpd - connection lost

  • Blades in the cluster reboot after you attempt to synchronize BIG-IP APM access policies.

Workaround

There is no workaround for this issue. However, you can mitigate this issue by configuring the vCMP guests participating in policy synchronization to span only a single slot. For more information about configuring vCMP guests, refer to the vCMP for VIPRION Systems: Administration guide.
