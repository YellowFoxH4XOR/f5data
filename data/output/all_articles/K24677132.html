Description

Pool members on a standby BIG-IP may intermittently flap its monitor status up and down, if there is a SNAT pool IP address which is the same as a non-floating BIG-IP self-IP in the same traffic-group.

Symptoms

  • ARP cache of another device/router/server on the same IP subnet shows standby's self IP is resolved to active unit's mac address
  • Traffic using the standby BIG-IP self-IP may intermittently fail.
    Example:
    ping requests sent from the standby BIG-IP to another device/router/server on the same IP subnet will generate responses that are sent to the active BIG-IP

Environment

  • BIG-IPs in an HA cluster
  • SNAT pool member shares an IP address with a non-floating BIG-IP self-IP

Cause

When a SNAT pool member shares the same IP address as a non-floating BIG-IP self-IP, this creates an IP conflict on the VLAN because now both the SNAT pool IP is used for production traffic, and the standby non-floating BIG-IP self-IP is used for control-plane traffic such as monitors.
Note: Having a SNAT pool member sharing a floating IP addresses does not cause an IP conflict, but the IP will share production traffic with control-plane traffic.

All SNAT pool IP addresses generate GARPs when a BIG-IP becomes active, this causes other devices on the same broadcast domain to learn that the self-IP address of the standby BIG-IP should go to the newly active BIG-IP. The devices will then subsequently learn the mac address of either BIG-IP, which causes intermittent production traffic failures and intermittent monitor failures on the standby unit.

This example shows the non-floating self-IP address 10.10.10.138 conflicts with a SNAT pool member:

ltm snatpool my_conflicting_snatpool {
    members {
        10.10.10.138
        10.10.10.139
    }
}
net self 10.10.10.138 {
    address 10.10.10.138/24
    traffic-group traffic-group-local-only
    vlan external
}
 

Recommended Actions

To resolve this issue, remove any non-floating self IP addresses from the SNAT pool.

To correct the misconfiguration, perform the following procedure:
Impact: Performing the following procedure will disrupt existing production traffic using the conflicted IP addresses.
  1. On the active unit, log in to the BIG-IP via the configuration Utility
  2. Browse to Local Traffic > Address Translation > SNAT Pool List
  3. Click on the SNAT pool list in which the self IPs are configured
  4. Remove SNAT pool member IP addresses that conflict with any non-floating BIG-IP self-IP
  5. Update
  6. Perform ConfigSync from active to standby
  7. For each conflicted IP address removed in step 4, run the following command to delete active connections using them:
    tmsh delete sys conn ss-client-addr <conflicting IP address>
    Example:
    tmsh delete sys conn ss-client-addr 10.10.10.138
     
  8. Clear the arp cache on any affected devices/routers/servers in the broadcast domain (including the active BIG-IP)
    arp -d <conflicting IP address>
    Example:
    arp -d 10.10.10.138

If the above does not resolve the problem, then you may have to restart mcpd/tmm on both systems using the following procedure:
Impact: Performing the following procedure will disrupt existing production traffic.
  1. Perform the procedure outlined in K13030: Forcing the mcpd process to reload the BIG-IP configuration on the standby unit.
  2. Repeat the procedure outlined in K13030: Forcing the mcpd process to reload the BIG-IP configuration on the active unit
