Description

When attempting to add SOA records for domains that are already configured as WideIPs in BIG-IP DNS, the ZoneRunner GUI may display errors when opening the records. Additionally, running a dig command may return an NXDOMAIN response status. This behavior occurs due to conflicts between the sub-domain record created by WideIP and the zone configuration.

Environment

  • Product: BIG-IP DNS
  • Configuration includes multiple WideIPs and attempts to create SOA records for delegated zones within the same top domain.

Cause

When a WideIP is created, it automatically generates an A record as a sub-domain using $ORIGIN within the top domain's zone file. If a new zone is created for this sub-domain (e.g., subdomain.example.com), it does not include the pre-existing A record from the top domain's zone file. As a result, ZoneRunner returns NXDOMAIN because it cannot find the expected A record in the newly created sub-domain's zone file.

Additionally, if fallback methods like "Return to DNS" are configured for WideIPs but their associated virtual servers go down, queries may fail to resolve correctly due to delegation issues between zones.

Recommended Actions

  1. Modify Zone Files Directly
    • Move all relevant records from the top domain's zone file (e.g., example.com) into the newly created sub-domain's zone file (e.g., subdomain.example.com).
    • Update $ORIGIN directives accordingly.
    • Refer to K7032 for instructions on modifying BIND zone files.

  2. Delegate Zones Properly
    • Ensure that delegated zones have their own SOA records and contain all necessary resource records (e.g., A or AAAA) required for resolution.
    • Avoid leaving resource records only in the parent domain’s zone file if they belong to a delegated sub-domain.

  3. DNS Express Configuration
    • If NXDOMAIN errors persist after creating SOA records for delegated zones, consider enabling DNS Express for those zones.
    • This can improve query handling and prevent unexpected resolution failures.

  4. Fallback Method Behavior with Delegated Zones
    • When configuring fallback methods like "Return to DNS," ensure that resource records exist in both parent and delegated zones if needed.
    • Verify that delegation settings align with your environment’s requirements and test thoroughly before deploying changes in production.

  5. Testing & Troubleshooting
    • Perform tests using tools like dig from different locations (local GTM vs remote devices) to identify discrepancies caused by caching or network configurations.
    • Collect logs, Qkviews, and packet captures during testing scenarios where GTMs are taken offline or access is restricted via firewalls.

  6. Revisit Environment Design
    • Evaluate whether having separate SOAs for top domains and delegated sub-domains aligns with operational requirements.
    • Consider consolidating or restructuring configurations if SERVFAIL or NXDOMAIN errors arise frequently due to design limitations.
