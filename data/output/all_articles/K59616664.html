Topic

You should consider using this procedure under the following condition:

  • You want to receive email alerts when the availability status of a pool member, pool, or virtual server changes.

Description

Virtual servers and load-balancing pools are the most important BIG-IP traffic management objects. Pools represent your internal application servers and your system should have health monitors assigned to check the availability of the application or service. When a health monitor check fails, the availability status of one or more pool members changes and the BIG-IP system logs a pool member status change message to the /var/log/ltm file. Health monitor checks for all pool members in a pool may fail on rare occasions, and if that happens, the BIG-IP system logs status change messages indicating that both the pool and virtual server are unavailable to process traffic.

To help you monitor and better respond to status changes, you can configure the BIG-IP system to send email alerts when the availability status of pools, virtual servers, or pool members changes. Because these changes indicate different levels of impact to your service, it is important that you understand what the different log messages are, what they mean, and how they may impact your service.

Pool and virtual server status

The highest level of impact occurs when status changes indicate that there are no available pool members, which causes both the pool and virtual server to become unavailable. For example, the following messages indicate that there are no available pool members in the pool_one pool and that the vip_one virtual server is unavailable to process application traffic:

01071682:5: SNMP_TRAP: Virtual /Common/vip_one has become unavailable
01010028:3: No members available for pool /Common/pool_one

Pool member status

The impact of a pool member status change varies depending on the number of pool members that change and the duration of that change. Status change events that occur for a single pool member and for a short period of time represent very low or no noticeable impact to service. For example, the following messages indicate that a single pool member in the pool_one pool was unavailable for 10 seconds:

01070638:5: Pool /Common/pool_one member /Common/192.168.10.1:80 monitor status down. [ /Common/http: down; Connection refused. @2017/12/01 12:00:00.  ] 
01070727:5: Pool /Common/pool_one member /Common/192.168.10.1:80 monitor status up. [ /Common/http: up ]  [ was down for 0hr:0min:10sec ]

Status changes involving a greater number of pool members being down for longer periods of time represent a more significant and likely noticeable impact to service. For example, the following messages indicate that three pool members in the pool_one pool were unavailable for approximately three and a half minutes.

01070638:5: Pool /Common/pool_one member /Common/192.168.10.1:80 monitor status down. [ /Common/http: down; Connection refused. @2017/12/01 12:00:00.  ] 
01070638:5: Pool /Common/pool_one member /Common/192.168.10.2:80 monitor status down. [ /Common/http: down; Connection refused. @2017/12/01 12:00:01.  ] 
01070638:5: Pool /Common/pool_one member /Common/192.168.10.3:80 monitor status down. [ /Common/http: down; Connection refused. @2017/12/01 12:00:02.  ] 
01070727:5: Pool /Common/pool_one member /Common/192.168.10.1:80 monitor status up. [ /Common/http: up ]  [ was down for 0hr:3min:30sec ]
01070727:5: Pool /Common/pool_one member /Common/192.168.10.2:80 monitor status up. [ /Common/http: up ]  [ was down for 0hr:3min:31sec ]
01070727:5: Pool /Common/pool_one member /Common/192.168.10.3:80 monitor status up. [ /Common/http: up ]  [ was down for 0hr:3min:32sec ]

Considerations for large configurations

If your configuration includes a large number of pool members, you may receive a high volume of email alerts, which increases network traffic and the amount information you need to analyze and understand. To avoid this, consider configuring email alerts to trigger only when an entire pool or virtual server status changes. Also consider using Simple Network Management Protocol (SNMP) to deliver individual pool member status change messages using SNMP trap alerts. The BIG-IP system configures SNMP trap alerts for pool members' status by default, so you only need to configure an SNMP trap destination. For more information on configuring an SNMP trap destination, refer to the following article K77406702: Configuring an SNMP trap destination using tmsh.

After you decide which status change message are most important, you can use the following procedures to configure and test email alerts based on pool member, pool, or virtual server status changes.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have Advanced shell (bash) and TMOS Shell (tmsh) access to the BIG-IP system.
  • You have an SMTP mailhub (mail server) and a DNS name server.

Procedures

  • Configuring the SMTP mailhub and DNS name server
  • Configuring email alerts for pool and virtual server status changes
  • Configuring email alerts for pool member status changes
  • Testing email delivery
  • Resolving syntax errors (alertd restarts)

Configuring the SMTP mailhub and DNS name server

You must first configure the SMTP mailhub, or mail server, to receive and deliver BIG-IP system email alerts. You must also configure the DNS name server if you intend to resolve fully qualified domain names (FQDN). Perform the following procedure to configure the SMTP mailhub and DNS name server:

Note: If you are running BIG-IP 13.0.0, you must follow the Workaround procedure in the following article: K15188934: Emails generated by the BIG-IP system may fail after upgrading to 13.0.0.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to tmsh by typing the following command:

    tmsh

  2. To configure a DNS name server, use the following command syntax:

    modify sys dns name-servers add { <IP address> }

    For example, to configure the system to use a DNS name server with the IP address 192.168.10.200, type the following command:

    modify sys dns name-servers add { 192.168.10.200 }

  3. To configure the system to send locally generated email messages, use the following command syntax:

    modify sys outbound-smtp mailhub <mail_server>:<port>

    For example, to configure the system to send locally generated email messages to host mail.example.com using TCP service port 587, type the following command:

    modify sys outbound-smtp mailhub mail.example.com:587

  4. To save the configuration, type the following command:

    save /sys config

Configuring email alerts for pool and virtual status changes

To receive an email alert when a pool or virtual server status changes, you must modify the /config/user_alert.conf file and define custom email alerts based on availability status changes for both pools and virtual servers.

Note: Because the /config/user_alert.conf file overrides the BIG-IP system /etc/alertd/alert.conf SNMP trap file, you will notice an SNMP Object Identifier (OID) included in the email alert example for the virtual server. If you are not using SNMP traps, you can remove the snmptrap entry. However, if you do this, the BIG-IP system no longer sends SNMP traps for virtual server status changes.

Perform the following procedure to create the custom email alerts for pool and virtual server status changes:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the bash shell.
  2. Using a text editor, open the /config/user_alert.conf file.
  3. Use the following alert syntax to send an email notification when a pool has no available pool members:

    Note: The email Subject is the exact message logged to the /var/log/ltm file and you cannot modify it.

    Note: The toaddress requires the full email address. However, the fromaddress appends @<BIG-IP hostname>.

    alert BIGIP_TMM_TMMERR_LAST_PMBR_DOWN {
    email toaddress="<email address>"
    fromaddress="<bigip user>"
    body="<text message>"
    }

    For example, the following alert sends an email notification to the root and admin users at example.com with the message Pool has no available pool members.:

    alert BIGIP_TMM_TMMERR_LAST_PMBR_DOWN {
    email toaddress="root@example.com,admin@example.com"
    fromaddress="root"
    body="Pool has no available pool members."
    }

  4. Use the following alert syntax to send an email notification when a pool has recovered and there are again available pool members:

    alert BIGIP_TMM_TMMERR_PMBR_BACK_UP {
    email toaddress="<email address>"
    fromaddress="<bigip user>"
    body="<text message>"
    }

    For example, the following alert sends an email notification to the root and admin users at example.com from root@ltm1.example.com with the message Pool now has available pool members.:

    alert BIGIP_TMM_TMMERR_PMBR_BACK_UP {
    email toaddress="root@example.com,admin@example.com"
    fromaddress="root"
    body="Pool now has available pool members."
    }

  5. Use the following alert syntax to send an email notification when a virtual server has become unavailable and has stopped processing traffic:

    alert BIGIP_MCPD_MCPDERR_VIRTUAL_UNAVAIL {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.136";
    email toaddress="<email address>"
    fromaddress="<bigip user>"
    body="<text message>"
    }

    For example, the following alert sends an email notification to the root and admin users at example.com from root@ltm1.example.com with the message A virtual server has stopped processing traffic.:

    alert BIGIP_MCPD_MCPDERR_VIRTUAL_UNAVAIL {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.136";
    email toaddress="root@example.com,admin@example.com"
    fromaddress="root"
    body="A virtual server has stopped processing traffic."
    }

  6. Use the following alert syntax to send an email notification when a virtual server has become available:

    alert BIGIP_MCPD_MCPDERR_VIRTUAL_AVAIL {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.135";
    email toaddress="<email address>"
    fromaddress="<bigip user>"
    body="<text message>"
    }

    For example, the following alert sends an email notification to the root and admin users at example.com from root@ltm1.example.com with the message A virtual server has resumed processing traffic.:

    alert BIGIP_MCPD_MCPDERR_VIRTUAL_AVAIL {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.135";
    email toaddress="root@example.com,admin@example.com"
    fromaddress="root"
    body="A virtual server has resumed processing traffic."
    }

  7. Save and exit the file.
  8. To restart the alertd process, type the following command:

    tmsh restart sys service alertd

Configuring email alerts for pool member status change

To receive an email alert when a pool member status changes, you must modify the /config/user_alert.conf file and define custom email alerts based on the following health check events:

  • A pool member has failed a health check.
  • A pool member has recovered from a failed health check.

Note: Because the /config/user_alert.conf file overrides the BIG-IP system /etc/alertd/alert.conf SNMP trap file, you will notice an SNMP OID included in the email alert example. If you are not using SNMP traps, you can remove the snmptrap entry. However, if you do this, the BIG-IP system no longer sends SNMP traps for this status change.

Perform the following procedure to create custom email alerts for pool member status changes:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the bash shell.
  2. Using a text editor, open the /config/user_alert.conf file.
  3. Use the following alert syntax to send an email notification when a pool member fails a health check and is marked down:

    Note: The email Subject is the exact message logged to the /var/log/ltm file and you cannot modify it.

    Note: The toaddress requires the full email address. However, the fromaddress appends @<BIG-IP hostname>.

    alert BIGIP_MCPD_MCPDERR_POOL_MEMBER_MON_STATUS {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.10";
    email toaddress="<email address>"
    fromaddress="<bigip user>"
    body="<text message>"
    }

    For example, the following alert sends an email notification to the root and admin users at example.com from root@ltm1.example.com with the message A pool member health check has failed.:

    alert BIGIP_MCPD_MCPDERR_POOL_MEMBER_MON_STATUS {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.10";
    email toaddress="root@example.com,admin@example.com"
    fromaddress="root"
    body="A pool member health check has failed."
    }

  4. Use the following alert syntax to send an email notification when a pool member recovers from a failed health check and has been marked up:

    alert BIGIP_MCPD_MCPDERR_POOL_MEMBER_MON_STATUS_UP {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.11";
    email toaddress="<email address>"
    fromaddress="<bigip user>"
    body="<text message>"
    }

    For example, the following alert sends an email notification to the root and admin users at example.com from root@ltm1.example.com with the message A pool member has recovered from a failed health check.:

    alert BIGIP_MCPD_MCPDERR_POOL_MEMBER_MON_STATUS_UP {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.11";
    email toaddress="root@example.com,admin@example.com"
    fromaddress="root"
    body="A pool member has recovered from a failed health check."
    }

  5. To restart the alertd process, type the following command:

    tmsh restart sys service alertd

Testing email delivery

The most effective way to verify health checking and email delivery is to shut off the service on the application server or block network access between the BIG-IP system and the application server. After the pool monitor's timeout period expires, you should receive emails indicating down status. Turn the service back on or restore network connectivity between the BIG-IP system and the application server and you should receive emails indicating up status. If impacting service this way is not possible, you can perform the following procedure to generate log messages that trigger alert emails without impacting service:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the bash shell.
  2. Use the following command syntax to generate a log message in the /var/log/ltm file to trigger an alert email:

    logger -p local0.notice "<logged error message>"

    For example, you can copy and paste the following commands to test all of the email alerts configured in this article:

    Note: You can copy and paste the commands all at one time. You do not need to modify these commands to test email delivery.


    logger -p local0.notice "01070638:5: Pool /Common/pool_one member /Common/192.168.10.1:80 monitor status down."
    logger -p local0.notice "01071682:5: SNMP_TRAP: Virtual /Common/vip_one has become unavailable"
    logger -p local0.notice "01010028:3: No members available for pool /Common/pool_one"
    logger -p local0.notice "01070727:5: Pool /Common/me member /Common/192.168.10.1:80 monitor status up."
    logger -p local0.notice "01071681:5: SNMP_TRAP: Virtual /Common/vip_one has become available"
    logger -p local0.notice "01010221:3: Pool /Common/pool_one now has available members"

  3. You should receive emails from the BIG-IP system on your remote device or workstation.

Resolving syntax errors (alertd restarts)

If syntax errors occur in the /config/user_alert.conf file, the alertd process continually restarts until you fix the syntax error. If the alertd process enters a restart loop, perform the following procedure to resolve the issue:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the bash shell.
  2. To stop the alertd process, type the following command:

    tmsh stop sys service alertd

  3. Open the user_alert.conf file for editing and compare the newly configured alerts with the examples in the previous procedures. After you fix any typographical errors, proceed to the next step.
  4. To start the alertd process, type the following command:

    tmsh start sys service alertd
