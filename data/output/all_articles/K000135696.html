Server-side request forgery

Server-side request forgery (SSRF) flaws occur whenever an API fetches a remote resource without validating the user-supplied URL. This flaw allows an attacker to force the application to send crafted requests to unintended resources or destinations, bypassing security controls such as a firewall or a VPN. Most modern application development concepts encourage developers to access an external resource or destination based on user input, for example webhooks, file fetching from URLs, custom single sign on (SSO), and URL previews. However, technologies like public cloud and pods and containers (such as Kubernetes and Docker) expose management and control channels over HTTP on predictable, well-known paths, thus making them easy targets for an SSRF attack.

Successful SSRF attacks can result in the following:

  • Exposure and theft of data that may include sensitive personal or corporate information
  • Unauthorized manipulation of sensitive data
  • Hijack of a vulnerable system to use its trust relationship with other systems to launch further attacks

Server-side request forgery attack scenario

In the following attack scenario, an attacker exploits an API that makes calls to an internal resource on the same network.

  1. The attacker identifies an API that is vulnerable to SSRF attacks.
  2. The attacker sends a forged request to the vulnerable API and targets the internal resource that resides on the same network. For example, the following forged request targets 192.168.169.254, which resides on the internal network: 
    POST /graphql

[
  {
    "variables": {},
    "query": "mutation {
      createNotificationChannel(input: {
        channelName: \"ch_piney\",
        notificationChannelConfig: {
          customWebhookChannelConfigs: [
            {
              url: \"http://192.168.269.254/myadmin\",
              send_test_req: true
            }
          ]
          }
      }){
        channelId
    }
    }"
  }
]
  3. The API sends the forged request to the internal resource and receives a response with the requested data.
  4. The API sends the response data back to the attacker, bypassing detection.

Secure your APIs against server-side request forgery attacks with F5 products

To protect your APIs against server-side request forgery attacks, you should consider the following recommended best practices:

  • Isolate the resource fetching mechanism in your network. Typically resource fetching mechanism should not involve internal resource/destination.
  • Ensure all client-supplied input are validated and sanitized.
  • Disable HTTP redirections if possible.
  • Use an accept list, if possible, to limit the following:
    • The location from which remote users are expected to download and access resources
    • URL schemes and ports
    • Accepted media types for a functionality
  • Use a well-tested and maintained URL parser to avoid issues caused by URL parsing inconsistencies.
  • Avoid sending raw responses to client.

In addition, use the following controls in F5 products to secure your APIs:

  • Use BIG-IP Advanced WAF/BIG-IP ASM to mitigate SSRF
  • Use NGINX App Protect to mitigate SSRF
  • Use F5 Distributed Cloud Service to mitigate SSRF

Use BIG-IP Advanced WAF/BIG-IP ASM to mitigate SSRF

In BIG-IP Advanced WAF/BIG-IP ASM 16.1.0 and later, you can use the SSRF protection feature to protect your APIs against SSRF attacks. You should identify parameters of data type URI that are subjected to SSRF attacks and explicitly define the URI parameters in your security policy. Alternatively, you can use the Auto-detect Parameter Value Type feature to automatically detect URI parameters in your APIs. With these parameters, you should identify the specific hosts to which you want to disallow access, and in your security policy under Advanced Protection > SSRF Protection, add these specific hosts (IP addresses or host names) to the SSRF Hosts list. For more information about the SSRF Protection feature, refer to the following resources:

  • The Mitigating Server-Side Request Forgery chapter of the BIG-IP Application Security Manager: Implementations guide.
  • K79011367: Using the ‘Auto detect’ option for a parameter to reduce false positive violations.

Additionally, you can enable SSRF attempt attack signatures for your security policy. For more information, refer to the Assigning Attack Signatures to Security Policies chapter of the BIG-IP Application Security Manager: Attack and Bot Signatures guide.

Use NGINX App Protect to mitigate SSRF

You can use the parameter parsing security feature in NGINX App Protect to protect your APIs against SSRF attacks. You should define the URI parameters in your application or allow them to be automatically detected. For more information, refer to the Parameters section of the NGINX App Protect WAF Configuration Guide. Additionally, you can configure SSRF attack signatures in your security policy. For more information, refer to the Signature Sets section of the NGINX App Protect WAF Configuration Guide.

Use F5 Distributed Cloud Service to mitigate SSRF

The F5 Distributed Cloud Service provides updated SSRF attempt attack signatures to protect your APIs against SSRF attacks when you configure a HTTP load balancer with WAF enabled for your application service. For more information about how to protect your APIs, refer to the demonstration illustrated in Mitigating OWASP Web Application Risk: SSRF Attack using F5 XC Platform. For detailed steps on configuring a Web Application Firewall in F5 Distributed Cloud Service, refer to the Application Firewall documentation on F5 Distributed Cloud Service.
