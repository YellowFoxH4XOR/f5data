Description

Cross-site Request Forgery (moving forward, CSRF) is a security vulnerability usually found in web applications. An application vulnerable to CSRF allows an attacker to force a victim user to execute unwanted actions in a web application to which they are currently authenticated.

Environment

A web application being delivered to a web browser on a client device (e.g., Chrome, Edge, Firefox etc)

Cause

  • A web application which does not use a secondary mechanism (e.g. prompt, 2nd factor, one-time tokens) to authorize requested actions

Recommended Actions

It is possible to mitigate CSRF attacks against a web application using BIG-IP Advanced WAF, Silverline WAF etc to insert a CSRF token into responses and then validate that token in subsequent requests. Specific instructions are outside of the scope of this document since any policy must be tailored to the web application in question.
 
If you are concerned about a known CSRF vulnerability in the BIG-IP Configuration Utility the best mitigation is to ensure your administrators:
  • Access the Configuration Utility from a dedicated management host, jump box or another controlled environment

Additional Information

Cross-site Request Forgery attacks may also be referred to as CSRF, XSRF, “Sea Surf” or, less commonly, Session Riding or One-Click attacks.

Cross-site Request Forgery
 
All of the names above refer to the same basic problem, that is, a web application which implicitly trusts any request from an authenticated user without some second factor to authorize the intent of the request.
 
To exploit a vulnerable web application, an attacker must trick the victim into submitting a malicious request while already authenticated to the application. In this way, the attacker inherits the identity and privileges of the victim and is able to perform an undesired action as though the attacker were the victim.
 
Despite the name “One-Click Attack”, this does not always require the victim user to click on a malicious link. An attacker can deliver their payload in a variety of ways:
  • The attacker may use social engineering (e.g., phishing) to trick the victim into clicking on a specifically constructed malicious link directly to the target application
  • The attacker may embed the malicious link inside an IMG or IFRAME tag within an innocent looking web page or email such that the link will be automatically requested by the victim user’s browser or email client, executing the attack silently without user interaction
  • Embedding the attack as malicious HTML or JavaScript in an innocent, legitimate website vulnerable to Stored Cross-site Scripting (see K33001652)
  • In some cases, by storing the attack in the target application itself (see “Stored CSRF” below)
 
Example
 
Imagine an online banking application which uses only GET requests; the request issued to transfer money between accounts might look something like this:
GET http://evilbank.com/transfer.php?to=7654321&amount=100 HTTP/1.1
 
An attacker, Bob, wishes to perform a CSRF attack against a victim user, Jane, when she is logged in to the vulnerable banking application. Bob must first construct a malicious link which, in this case, is simple since the URL is predictable and has no additional layers of security such as a server-generated one-time token that is validated in subsequent requests. If Bob wishes to transfer $1000 from Jane to himself, he must only construct a link with the destination account number and amount:
http://evilbank.com/transfer.php?to=9999999&amount=1000
 
Bob must now engineer a situation in which Jane’s browser will make the malicious request while she is logged into the banking application. He could do this in a number of ways, often as simple as:
  • Sending an unsolicited email or instant message with HTML content
  • Inserting the exploit URL or script into pages that the victim might browse while they are carrying out online banking tasks
 
Bob can make the malicious link look innocuous by including it in an email as a normal link with innocent looking text, or by using a 0-pixel image. Using the latter approach the victim, on viewing the email, would not see any content at all however the rendering engine would still submit the request to the banking application (this is predicated on the email rendering engine and browser sharing state and session cookies – this is the case when using webmail, for example)
 
Similar approaches can be taken to exploit applications which rely on POST requests for state-changing actions (and, therefore, POST requests alone are not sufficient to mitigate CSRF attacks), or applications which rely heavily on JSON to pass parameters. The OWASP Cross-Site Request Forgery page has additional detail.
 
Stored CSRF
 
As noted above, a Cross-site request forgery attack can be carried out by embedding an IMG or IFRAME tag or other client-side script (such as JavaScript) that will cause the victim browser to execute the malicious request against the target, vulnerable application. If the target application also allows the attacker to store HTML that will be subsequently rendered by the victim while performing legitimate actions, this may allow the attacker to carry out a Stored CSRF attack.
 
The easiest example here is to imagine an online discussion forum that allows HTML to be included in forum posts, if the attacker makes a post containing the malicious HTML or JavaScript then the browser of any visitor who views that post will attempt to render the malicious HTML – if the visitor viewing the post is the target victim then the victim’s browser will execute a CSRF attack against the forum using the credentials of the victim user.
 
Mitigations
 
If you wish to protect an application against CSRF attacks and cannot use Advanced WAF or a similar product to insert one-time tokens then you should build this functionality into the application itself:
  • Ensure all requests that cause a state change include tokens validated by the target application on the server side.
  • Consider using the SameSite Cookie attribute for any session or authorization cookies
  • Consider validating the request origin (e.g. Origin and Referrer headers) server-side in the target application
  • Avoid using GET requests for state-change operations
 
OWASP has additional advice for this in their Cross-Site Request Forgery Prevention cheat-sheet.
