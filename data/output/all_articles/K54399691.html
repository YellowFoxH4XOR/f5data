Description

BIG-IP LTM+APM processes POST method HTTP requests as follows:

1. BIG-IP APM stores Initial POST method HTTP requests in the session database
2. After Access Policy completes successfully BIG-IP APM sends javascript that instructs the user-agent to send a POST method HTTP request to the BIG-IP APM with data "dummy=<blob>"
3. BIG-IP APM uses the dummy <blob> value to retrieve the initial POST request (see step 1) and sends it to the backend resource

When a BIG-IP LTM+APM environment is configured to set and implement variable values into backend requests after Access Policy receives the initial POST request and before BIG-IP APM sends the backend request then the variable values will not be implemented in the backend POST requests.

Environment

  • BIG-IP LTM+APM protected resources
  • Variable values set and implemented into backend requests after Access Policy receives the initial POST request and before BIG-IP APM sends the backend request

Cause

This is expected behavior.

Recommended Actions

Set and implement variable values into backend requests before Access Policy receives the initial POST request if possible or when APM sends the backend POST request.

Additional Information

An example of this behavior is an Access Policy iRule event that triggers an iRule that sets variable values that are implemented for header insert values, such as 'HTTP::header insert "Header" $variable', within an HTTP_REQUEST event. Since the BIG-IP APM receives the dummy <blob> value after the HTTP_REQUEST event and the variable value is set after the Access Policy receives the initial POST request then the backend request will contain "Header" without a value. An example workaround for this example use case is to implement the header insert commands within the ACCESS_ACL_ALLOWED event.

Note: F5 Support does not design nor configure iRules.  If you are in need of any assistance configuring an iRule to best work for your environment, F5 Professional Services can assist.
