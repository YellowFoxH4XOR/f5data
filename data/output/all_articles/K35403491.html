Description
Domain name monitor is marked “offline” but the webpage can be accessed.
Https Monitor is marked down with reason: connect: protocol mismatch search result false when you check with tmsh command as below:

tmsh show /gtm pool members

 -----------------------------------------------------
  | Gtm::Pool Member: /Common/pool_443 vs_443:/Common/test
  -----------------------------------------------------
  | Status
  |   Availability : offline
  |   State        : enabled
  |   Reason       :  Monitor /Common/monitor_https_example_com from 10.0.0.1 : connect: protocol mismatch search result false

  • You may also notice an ssl handshake failure message as one of the following
    err big3d[8235]: 01333001:3: SSLConnect: SSL error:14094410:SSL routines:SSL3_READ_BYTES:sslv3 alert handshake failure
    err big3d[6071]: 01333001:3: SSLConnect: SSL error:140770FC:SSL routines:SSL23_GET_SERVER_HELLO:unknown protocol
  • You may see alerts in /var/log/gtm
    alert gtmd[14124]: 011ae0f2:1: Monitor instance /Common/monitor_https 10.0.0.1:443 UNKNOWN_MONITOR_STATE --> DOWN from 1.1.1.1 (connect: protocol mismatch search result false)

Environment

  • BIG-IP GTM
  • BIG-IP DNS
  • Pool members as Generic Host
  • HTTP[S] monitors

Cause
These messages are coming from our 'big3d' process which is responsible for (among other things) doing the health checks on monitored servers. The error message comes directly from the ssl library that big3d uses. The most common reason for this is you are attempting to use an https monitor for an http resource. This is not specific to BIG-IP, for example you can see the same in curl when trying to use the https protocol on a port-80 http server:

$ curl -k https://1.1.1.1:80
curl: (35) error:140770FC:SSL routines:SSL23_GET_SERVER_HELLO:unknown protocol
Recommended Actions
The appropriate action is to change the monitor type to suit the pool member. Do not apply https monitors to http pool members. Because the member isn't listed in the log message, it is challenging to determine which pool member is the cause of the log message. The best action is to review the members which are in a down state by monitor, and audit to ensure that it's appropriate for an https monitor to be applied to that member.

    Additional Information
    You can use the following to get a listing of the pool members down with protocol mismatch. From there, you can review which of them is inappropriate for https monitor. 

    tmsh show gtm pool [type] members | grep -B 6 'protocol' 
    Note: You must utilize the correct "type" as one of the supported types: a aaaa cname mx naptr srv

    Example

    # tmsh show gtm pool a members | grep -B 6 'protocol'
    ..
      --------------------------------------------------------------
      | Gtm::Pool Member: pool_mobile:A 10_35_20_21_80:server_mobile
      --------------------------------------------------------------
      | Status
      |   Availability : offline
      |   State        : enabled
      |   Reason       :  Monitor /Common/https_head_f5 from 10.35.13.1 : connect: protocol mismatch search result false
    ..

    You may instead utilize tcpdump to capture monitor traffic to identify if https monitors are inappropriately applied.

    1. Perform TCP dump to investigate the cause of monitor. 
      Refer to K411: Overview of packet tracing with the tcpdump utility
       
    2. If there is no issue for ssl handshake, you should check the https monitor is correctly configured ,especially the http request formatting.
      Refer to K13397: Overview of HTTP health monitor request formatting for the BIG-IP DNS system
