Topic

The BIG-IP LTM HTTP profile allows some compression settings to overlap, where other HTTP settings will disable or prevent compression from occurring.

The HTTP setting options are as follows:

  • Disable - This setting turns off the Compression module. Content that uses this HTTP Profile will not be compressed. This is the default setting.
  • Enable - This setting enables the Compression module.
  • Selective - This setting enables compression when an iRule specifies the HTTP::compress command.

Note: For information about using iRules when the Selective option for HTTP Compression is enabled, visit http://devcentral.f5.com. Additional information and examples of the iRule syntax are available in the iRule Wiki.

If the Compression option is enabled but no URI or content compression is specified, all responses from the server are compressed, as long as the client specifies gzip or deflate in the Accept-Encoding header.

By default, the profile automatically has content compression configured when the Compression option is enabled, with the following content types specified in the Include list:

Include
text/
application/(xml|x-javascript)

This default list specifies that all text and JavaScript content will be compressed. Content not matching these specifications will not be compressed.

Order of precedence for URI Compression or Content List

Two options specify what is compressed when HTTP compression is enabled in the HTTP profile: URI Compression, and Content List.

The URI Compression option specifies whether the system compresses URI responses specified in the header of the client request. This option contains an Include and Exclude list.

The Content List option specifies whether the system compresses the content contained in the Content-Type header of a response. This option also contains an Include and Exclude list.

In order for compression to occur, a match must be made in the Include list and not in the Exclude list. If you specify something specific in the Include list but specify something that is general in the Exclude list that is already included in the Include list, the Exclude list takes precedence. Any match found in the Exclude list has priority over any match in the Include list.

The following example demonstrates how a general content match can override a very specific content match. If the site compresses large text files, but does not compress smaller sized text/html files or regular HTML pages, the following lists are composed:

Include list:
text/plain
application/(xml|x-javascript)

Exclude List:
text/

Because text/ is considered a wild card in the Exclude list in the example above, only JavaScript is compressed, while none of the plain text is compressed. Due to the fact that any match found in the Exclude list has priority over any match in the Include list, the wild card text/ takes precedence over the items in the Include list, even though the items in the Include list are more specific.

Keep Accept Encoding and Browser Workarounds options

Two additional options are available in the Compression section of the HTTP profile: Keep Accept Encoding and Browser Workarounds.

Keep Accept Encoding

The Keep Accept Encoding setting is disabled by default. When this option is disabled, the BIG-IP LTM will remove the Accept-Encoding: gzip,deflate header before sending the request back to the server. This prevents the server from compressing the content if it is configured to compress the content. The compression module will not compress data that has already been compressed.

The Keep Accept Encoding option should only be enabled in situations when you want the server, rather than the BIG-IP LTM, to handle compression. In order for the BIG-IP LTM to recognize the compressed content when the Keep Accept Encoding option is enabled, it is important to specify which content the BIG-IP LTM should compress, and ensure the content does not overlap the content that the server is compressing.

Browser Workarounds

The Browser Workarounds option is disabled by default and only needs to be enabled in situations where you are using Netscape 4.0x and Internet Explorer 6 SP1 browsers.

Some early versions of the Netscape 4.0x and Internet Explorer 4.x through 6 SP1 browsers (KB328498) advertised the Accept-Encoding header, but were unable to properly handle compressed data. The Browser Workarounds option identifies the Netscape 4.0x and Internet Explorer 4.x through 6.x browsers by the information contained in the User-Agent header, and disables compression for requests made by these browsers.

The following behavior occurs when the Browser Workarounds option is enabled in the HTTP Profile:

  • Responses for Netscape 4.x browsers will not be compressed
  • Responses for Netscape 4.x browsers that are not HTML or plain text will not be compressed
  • Responses for IE browsers that are JavaScript or CSS files through SSL will not be compressed
  • Responses for IE browsers that are JavaScript or CSS files with Cache-Control: no-cache will not be compressed
  • User-Agent will be added to the Vary header if the response is not HTML or plain text
