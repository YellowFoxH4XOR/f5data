Topic

This article specifies best practices for making a traffic-impacting change to the BIG-IP system during a maintenance window. You should follow these best practices to receive the best possible assistance from F5 Technical Support, in case you encounter an issue.

Note: You should make all traffic-impacting changes during a maintenance window. If possible, you should first stage the change in a test environment.

Note: If the change is large in scope, F5 recommends that you open a proactive case. For more information, refer to K16022: Opening a proactive service request with F5 Technical Support.

Before making a traffic-impacting change to the BIG-IP system

Gather the following data, which F5 Technical Support will use to establish a baseline of your configuration and network traffic before the change:

  • Create a user configuration set (UCS) archive. If the BIG-IP system is a member of a high-availability pair, create a UCS archive of each unit.

    Note: For more information, refer to K4423: Overview of UCS archives, K13132: Backing up and restoring BIG-IP configuration files (11.x - 12.x), K11318: Backing up and restoring BIG-IP configuration files (10.x), or K3499: Backing up and restoring BIG-IP 9.x configuration files.

  • Create a qkview file. If the BIG-IP system is a member of a high-availability pair, create a qkview file of each unit.

    Note: For more information, refer to K1858: Overview of the qkview utility (9.x) and K12878: Generating BIG-IP diagnostic data using the qkview utility.

  • If possible, draw a network diagram. A network diagram is an important diagnostic resource that helps F5 Technical Support quickly become familiar with an unknown network.
  • Collect tcpdumps and/or ssldumps relevant to the application that will be directly affected by the change. Ensure that captures are written out to a binary file (text output is generally insufficient).

    Note: Captures taken exclusively on the BIG-IP system may often not be sufficient to represent your traffic (especially if the BIG-IP system is the device suspected of introducing the issue). F5 recommends that you supplement any captures taken on the BIG-IP system with independent captures (either taken from mirrored ports, or on the client and server end point devices).

    Customer configurations and environments vary; therefore, you must determine the best options to pass to the tcpdump utility. Example network captures are as follows:

    • Wide open capture

      Objective: catch a small sample of full L2-L7 traffic. Use the packet count option to limit the capture size.

      tcpdump -ni 0.0:nnn -s0 -c 100000 host <virtual_server_ip> or <pool_member_ip> or <pool_member_ip> or <pool_member_ip> -w /var/tmp/L2-L7-<working|non-working>.pcap

      For example:

      tcpdump -ni 0.0:nnn -s0 -c 100000 host 192.168.1.100 or 10.0.0.1 or 10.0.0.2 or 10.0.0.3 -w /var/tmp/L2-L7-working.pcap

    • Targeted capture

      Objective: catch a small sample of targeted L4-L7 traffic. Use the packet count option to limit the capture size.

      tcpdump -ni 0.0:nnn -s0 -c 100000 '(port <virtual_server_port> and host <virtual_server_ip>) or (port <pool_member_port> and host <pool_member_ip> or <pool_member_ip> or <pool_member_ip>)' -w /var/tmp/L4-L7-<working|non-working>.pcap

      For example:

      tcpdump -ni 0.0:nnn -s0 -c 100000 '(port 443 and host 192.168.1.100) or (port 80 and host 10.0.0.1 or 10.0.0.2 or 10.0.0.3)' -w /var/tmp/L4-L7-working.pcap

      Beginning in BIG-IP 11.2.0, you can use the 'p' interface modifier to capture for a specific flow and its related peer flow. This modifier allows you to capture a specific traffic flow through the BIG-IP system from end to end, even when the configuration uses a Secure Network Address Translation (SNAT) or OneConnect. For example, the following command searches for traffic to or from client 10.0.0.1 on interface 0.0:

      tcpdump -ni 0.0:nnnp -s0 -c 100000 -w /var/tmp/capture.dmp host 10.0.0.1

      Once tcpdump identifies a related flow, the flow is marked in the Traffic Management Microkernel (TMM), and every subsequent packet in the flow (on both sides of the BIG-IP system) is written to the capture file.

      Important: The :p modifier produces large amounts of data and can cause significant resource utilization. This additional resource demand may cause poor performance or a system failure if the BIG-IP system is at high resource utilization. Use this modifier only with very specific filters.

      Note: The :p modifier will continue to produce flow information for the life of the connection. Subsequent tcpdump captures will reveal flow information from previous tcpdump captures using the :p modifier if the connection is still active. To clear flow information from previous use, run the tcpdump command without the :p modifier, using a filter that matches no information in the flow, and ensure that some traffic has been received by the BIG-IP system for the flow.

    • Targeted capture with a test client

      Objective: if a test client is available, capture all traffic from this client. If L2 issues have been ruled out, this set of captures tends to provide the most value. If the application uses Secure Sockets Layer (SSL), it is especially important that you capture the initial SSL handshake. If a network device before the BIG-IP system performs a NAT on traffic or aggregates connections, do not take these captures, as filtering on the client IP address will not record any traffic.

      Virtual server with no SNAT

      Note: If no SNAT is present, there is typically less need to limit capture sizes as the scope is sufficiently specific. Simply terminate the capture by pressing Ctrl+c after you have reproduced the behavior on the test client.

      tcpdump -ni 0.0:nnn -s0 host <client_ip> -w /var/tmp/client-only-<working|non-working>.pcap

      For example:

      tcpdump -ni 0.0:nnn -s0 host 192.168.1.5 -w /var/tmp/client-only-working.pcap

      Virtual server with SNAT

      Note: If the virtual server has a dedicated secure network address translation (SNAT) pool, you can typically replace the pool member IPs with the SNAT pool IPs, which may be easier if the number of pool members is large. If the SNAT pool is shared with other virtual servers or if the virtual server is using SNAT Auto Map, this will capture non-related traffic.

      tcpdump -ni 0.0:nnn -s0 -c 100000 '(host <client_ip>) or (port <pool_member_port> and host <pool_member_ip> or <pool_member_ip> or <pool_member_ip>)' -w /var/tmp/client-and-pool-members-<working|non-working>.pcap

      For example:

      tcpdump -ni 0.0:nnn -s0 -c 100000 '(host 192.168.1.5) or (port 8080 and host 10.0.0.1 or 10.0.0.2 or 10.0.0.3)' -w /var/tmp/client-and-pool-members-working.pcap

After making a traffic-impacting change to the BIG-IP system

If an issue arises after the change, gather the following data while the event is still occurring (before you roll back). Then, submit the data you collected before and after the change to F5 Technical Support. Also include detailed information about why you implemented the change, the behavior that you expected after the change, and the issue that arose after the change.

  • Create a qkview. If the BIG-IP system is the member of a high-availability pair, create a qkview of each unit.

    Note: For more information, refer to K1858: Overview of the qkview utility (9.x) and K12878: Generating BIG-IP diagnostic data using the qkview utility.

  • If a specialized qkview output is present in the /var/tmp directory, include this file in the data you will be sending to F5 Technical Support.

    Note: For more information, refer to K8483: A specialized qkview snapshot is captured after a TMM core.

  • Create a tarball of the Host logs by running the following command:

    tar zcvf /var/tmp/$HOSTNAME-logs.tar.gz /var/log/*

    If the BIG-IP system is the member of a high-availability pair, collect the logs of each unit.

    Note: You can skip this step in BIG-IP 10.x or later, as the qkview of BIG-IP 10.x or later collects data that includes these logs.

  • Create a tarball of the RRD data (the performance graphs) by running the following command:

    tar zcvf /var/tmp/$HOSTNAME-rrd.tar.gz /var/rrd/*

    If the BIG-IP system is the member of a high-availability pair, collect the RRD files of each unit.

    Note: You can skip this step in BIG-IP 10.x or later, as the qkview of BIG-IP 10.x or later collects data that includes this data.

  • Create a tarball of the Switch Card Control Processor (SCCP) logs by running the following command:

    ssh sccp "tar czvf - /var/log/" > /var/tmp/$HOSTNAME-sccp-logs.tar.gz

    If the BIG-IP system is the member of a high-availability pair, collect the SCCP logs of each unit.

    Note: You can skip this step in BIG-IP 10.x or later, as the qkview of BIG-IP 10.x or later collects data that includes these logs.

    Note: This step only applies to BIG-IP platforms that include the SCCP subsystem, namely the 1500, 3400, 3410, 4100, 6400, 6800, 8400, and 8800 platforms.

  • Gather new sets of tcpdumps and/or ssldumps; you should perform the same captures that you performed before the change.

    Important: Ensure that you modify the output file names, so you do not overwrite the original baseline captures.

  • Gather any other data that would be relevant (server logs, client logs, etc.).
  • If you roll back the change, gather a post rollback qkview (for each unit).
