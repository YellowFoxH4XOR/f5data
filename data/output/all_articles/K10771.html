Known Issue

This is the result of a known issue. The BIG-IP system may fail to reset the pool selection after each HTTP request, and may send server-side HTTP requests to the wrong pool, when an HTTP virtual server is configured to use the following:

  • A default pool
  • A selective HTTP class that points to a pool other than the default pool associated with the virtual server
  • OneConnect
  • WebAcceleration profile with appropriate HTTP cache settings to cache the requested object (referred to as RAM Cache in BIG-IP versions prior to 11.0.0)

When all of the above conditions are met, if the BIG-IP system serves a cacheable object from the pool specified in the HTTP class, all subsequent requests will also be served from the pool specified in the HTTP class, even if the requests did not match the class. The expected behavior is for the BIG-IP system to process each HTTP request independently and serve the request from the pool specified in the HTTP class only if the request matched the HTTP class. All HTTP requests that do not match the HTTP class should be served from the default pool attached to the virtual server.

F5 Product Development tracked this issue as ID 222806 (formerly CR124626). This ID was not fixed; however, the issue no longer applies to BIG-IP 11.4.0 or later.

Workaround

You can work around this issue by applying one of the following workarounds:

  • Using a catch-all HTTP Class
  • Using an iRule

Important: Regardless of the workaround you chose, existing TCP connections will continue to be served by the wrong pool. If you want to terminate these connections, you may use the bigpipe conn (<conn key list> | all) delete command to either delete all connections or single connections.

Using a catch-all HTTP Class

You can prevent this issue from occurring by assigning the following to the affected virtual server: a catch-all HTTP class with no selection criteria pointing to the default pool attached to the virtual server. This will ensure that all requests are handled by either HTTP class and that the virtual server load balancing algorithm will never choose the default pool. Even though it is not necessary, the virtual server may continue to have a default pool; the only purpose of the default pool will be marking the virtual server as up or down.

  1. Log in to the Configuration utility.
  2. Expand the Local Traffic section.
  3. Click Profiles.
  4. Under the Protocol tab, click HTTP Class.
  5. Click Create.
  6. Enter catch-all-SOL10771 as the name of the new HTTP Class profile.
  7. Select the custom box corresponding to the Send To action.
  8. In the Send to drop-down menu, select Pool.
  9. From the Pool drop-down menu, select the default pool attached to the affected virtual server.
  10. If required, you may enable ASM or WebAccelerator in this HTTP Class.
  11. Click Finished.
  12. Click Virtual Servers.
  13. Click the virtual server affected by this issue.
  14. Click Resources.
  15. Next to HTTP Class Profiles, click Manage.
  16. Move the catch-all-SOL10771 HTTP Class from Available to Enabled.

    Important: The catch-all-SOL10771 HTTP Class must be at the bottom of the list.
  17. Click Finished.

Note: If additional virtual servers are affected by this issue, you need to repeat this procedure in its entirety for each virtual server. Also note that you have to use different names for the additional catch-all HTTP Classes.

Using an iRule

You can work around this issue by creating an iRule and attaching it to the virtual server that presents the issue described in this Solution. To do so, perform the following procedure:

Note: F5 may recommend this workaround if you have more affected virtual servers, since you do not need to create a specific new object for every affected virtual server.

  1. Log in to the BIG-IP System Configuration utility.
  2. Expand Local Traffic.
  3. Click iRules.
  4. Click Create.
  5. Enter workaround-SOL10771 as the name of the new iRule.
  6. Paste the following iRule in the Definition text box:

    Note: The priorities are set in the following iRule to ensure that the CLIENT_ACCEPTED event fires after any other iRule CLIENT_ACCEPTED events with the default priority (500), and that the HTTP_CLASS_FAILED event fires before any other iRule events. If you have existing iRules with priorities set on these events, you should ensure that the priority of the following iRule will still fire in the desired order.

    when CLIENT_ACCEPTED priority 900 {
    set default_pool [LB::server pool]
    }
    when HTTP_CLASS_FAILED priority 100 {
    pool $default_pool
    }
  7. Click Finished.
  8. Click Virtual Servers.
  9. Click the virtual server affected by this issue.
  10. Click the Resources tab.
  11. Next to iRules, click Manage.
  12. Move the workaround-SOL10771 iRule from Available to Enabled.
  13. Click Finished.

Note: Repeat steps 7 through 12 for any additional virtual servers affected by this issue.
