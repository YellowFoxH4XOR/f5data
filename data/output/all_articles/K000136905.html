Description

It is possible to observe resource constraints on a BIG-IP system when it is being managed with automation tasks through either REST, Ansible, AS3, AppViewX or any other automation technologies. This article covers the possible side effects of it and subsequent considerations that can be undertaken to address those issues.

Environment

Managing BIG-IP systems with automation tasks via REST, Ansible, AS3, AppViewX and other technologies. 

Cause

  • CPU utilization
  • Memory utilization

CPU utilization
One of the most common scenarios that can lead to icrd_child & mcpd processes enduring high CPU utilization is when they're inundated by the sheer volume of the API calls that are directed towards the system. In checking the top -cb output, you can observe multiple instances of icrd_child process being spawned up by restjavad process (which is the parent process for icrd_child). When multiple instances of icrd_child process exists, that typically indicates that there is high load on the system that cannot be handled by a single icrd_child instance.

When an API call is issued to the device, the REST framework (restjavad process) spawns up icrd_child process which then subsequently sends a query to mcpd process in order to retrieve the dataset being requested (for e.g. retrieving GTM pool, WideIP, LTM pool or virtual server objects or performing modifications such as enabling/disabling any object's status). The mcpd process is single-threaded, which results in these API requests queued up as mcpd processes them one request at a time. This can drive up the CPU usage and can contribute to latency issue observed if enormous amount of API calls are issued to the device.

When restjavad process is busy, it can eventually lead to failures in processing multiple requests and the system returning a HTTP 400 Bad Request status code in response. Certain automation systems can automatically re-issue the request if a 400 Bad Request response is received and that can lead to exacerbating the situation furthermore.

Memory utilization
It is quite possible to see memory constraints with restjavad process if there are enormous amount of API calls issued to the BIG-IP system. If restjavad process itself runs out of all of it's allocated memory, then it could result in restjavad process being restarted in a frequent manner. It could subsequently lead to the device control plane running out of memory and result in the Linux Kernel invoking the Out of Memory (OOM) killer process in order to reclaim some of the memory back, which could result in a more devastating impact on the system depending on which process is killed by the kernel. Lack of sufficient memory can increase spooling requirements and sometimes affect CPU as well.

There are options such as increasing allocation for control plane with the provision.extramb db variable along with increasing memory allocation for restjavad via provision.restjavad.extramb db variable but this may not be a long-term resolution. This is described within the following two articles:

  • K26427018: Overview of Management provisioning 
  • K000092380: Restjavad restarting after upgrade with restjavad.useextramb set to true

Recommended Actions

The recommendation from F5 is to reduce the number of API calls that are issued to the device to prevent icrd_child instances and the single-threaded mcpd process to backup requests, which can lead to latency, drive up CPU utilization and potentially even cause requests to get timed out. To avoid hitting that scenario, reducing the volume of API calls being issued to the device either by increasing the interval time and ensuring the automation system has a proper grace period in-between requests or taking any other necessary measures would help alleviate the control plane pressure being witnessed.

Additional Information

It is worth noting that changes to the number of objects configured on the device can play a part in contributing to some of the concerns covered in this article. For example, the impact of repeated API calls, especially when it is issued at a certain interval, goes up when the number of queried object count increases. Multiple concurrent queries for hundreds or even thousands of objects can result in increased latency and resource consumption than when issuing these concurrent queries for tens of object each at a time. Scaling the queries with higher number of objects at a time can result in increased resource consumption and performance degradation.
