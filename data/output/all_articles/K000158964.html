K000158964: VELOS tenant unable to receive traffic due to backplane VOQ synchronization failure between blades

Type
Support Solution
Published
2025-12-31
Updated
2025-12-31
Source
https://my.f5.com/manage/s/article/K000158964

Description

On F5OS VELOS systems, a tenant deployed on a specific blade may be unable to receive ingress traffic when active network interfaces are on a different blade. Traffic arrives at the blade with active interfaces, but is not forwarded across the backplane to the blade hosting the tenant, while inter-tenant communication between blades continues to function normally.

The issue so far occurs after system upgrade to 1.8.2.

Symptoms include:

  • Tenant self-IP is not reachable from external networks
  • Traffic is seen on partition level, but tenant does not receive packets
  • Other tenants on different blades can receive traffic
  • Direct inter-blade communication between tenants is working (direct blade-to-blade traffic)

Error messages in logs:

fpgamgr[12]: priority="Err" msg="Failed to delete CDB component" ERROR="locked" LASTERR="Could not acquire lock"

or

fpgamgr[13]: priority="Err" msg="Failed to create CDB component" COMPONENT="/voq-states/voq-state{%d %d}" ERROR="locked" LASTERR="Could not acquire lock" ERRNO=10. 

Diagnostic indicators:

  • show voq-states command shows missing VOQ entries from the blade with active interfaces to the affected blade (that doesn't have active interfaces)
  • vqf_voq table shows imm_enabled set to 0 for queues from the ingress blade to the affected blade
  • Packet captures on the partition show traffic arriving but not being forwarded to the tenant blade

Note: there is a bug with a bit similar symptoms ID1696325: https://cdn.f5.com/product/bugtracker/ID1696325.html, but it was resolved in F5OS-C 1.8.1, so it's not applicable here.

Environment

  • Platform: VELOS chassis platforms (F5-VEL-BTA-CX410-AC, F101, etc.)
  • Affected Versions: F5OS-C 1.8.2

Cause

The issue is a result of a known Bug ID2140617 - race condition occurs during blade initialization where the blade fails to write to the Configuration Database (CDB) after enabling its Egress Memory Manager (EMM) registers.

This results in the Ingress Memory Manager (IMM) on other blades not being properly enabled for queues destined to the affected blade, preventing traffic from being forwarded across the backplane from the blade receving ingress traffic to the tenant blade.

Recommended Actions

Immediate workaround:

  1. Reboot the affected blade (the blade hosting the non-working tenant) using partition CLI:
    cluster nodes node blade-<X> reboot
    Note: Replace <X> with the blade number hosting the non-working tenant.
  2. Verify VOQ states are properly synchronized after reboot:
    show voq-states - confirm that all blade-to-blade entries show enabled VOQs (for example, if interfaces 1.0 and 2.0 are used on a blade, it should result in [ 4 9 15 ] VOQ numbers in show voq-states output)
  3. Check velos.log on a partition to confirm there are no voq-related CDB errors for fpgamgr.
  4. Test connectivity from the tenant to verify traffic flow is restored.

 

Permanent Resolution:

  • Upgrade to F5OS-C version 1.8.3 or later when available
  • Contact F5 Support to request an Engineering Hotfix (EHF) for version 1.8.2 if immediate resolution is required
