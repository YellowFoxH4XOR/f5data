Description

Users intermittently experience authentication failures ("User not authenticated") when accessing an application behind BIG-IP LTM. The issue occurs when Cookie Insert persistence is configured on two HTTPS virtual servers sharing the same VIP on different ports (e.g., 443 and 9443), both backed by the same pool. Subsequent requests during an active session are routed to a different backend pool member than the one that handled the initial login, causing the application's authentication token to be missing on the alternate server.

  • "User not authenticated" errors during an active user session
  • Application session tokens (e.g., ASP.NET Session IDs) not found on the receiving pool member
  • Issue does not occur when only a single pool member is active
  • Issue does not occur when the application is accessed without a load balancer

Environment

  • Product: BIG-IP LTM
  • Version: 17.1.x
  • Persistence type: Cookie Insert
  • Setting attempted: Match Across Services / Match Across Virtual Servers enabled
  • Two HTTPS virtual servers sharing the same VIP on different ports (e.g., 443 and 9443)
  • Both virtual servers backed by the same two-member pool
  • Application flow: initial login request lands on the first virtual server (port 443); application subsequently redirects users to the second virtual server (port 9443)
  • Backend application uses session-based token authentication (e.g., ASP.NET Session IDs); session state is not shared between pool members
  • A firewall performing DNAT sits in front of BIG-IP, translating the public IP to the VIP

Cause

Cookie Insert persistence is architecturally incompatible with the Match Across Services/Virtual Servers setting when traffic for a single user session spans two virtual servers on different ports sharing the same pool. BIG-IP does not maintain session affinity across virtual servers in this configuration, causing requests to be routed to a different pool member than the one that handled the initial login.

Answer/Recommended Actions

Option 1 (Recommended Production Approach): Use Cookie Hash Persistence with Match Across Virtual Servers

  1. Remove the Cookie Insert persistence profiles from both virtual servers.
  2. Remove the Match Across Services/Virtual Servers settings from both virtual servers.
  3. Configure Cookie Hash persistence on both virtual servers.
  4. Enable Match Across Virtual Servers with Cookie Hash persistence — this is a supported combination for maintaining session affinity across multiple virtual servers sharing the same pool.

Option 2 (iRule-Based Workaround): Enforce Consistent Pool Member Routing via Custom Cookie

  1. Remove the Cookie Insert persistence profiles and Match Across settings from both virtual servers.
  2. Apply the following iRule to both virtual servers:

when SERVER_CONNECTED {
set lbserver [IP::server_addr]
}
when HTTP_RESPONSE {
HTTP::cookie insert name "LB-Across" value "$lbserver" path "/"
}
when HTTP_REQUEST {
if { [HTTP::cookie exists "LB-Across"] } {
node [HTTP::cookie "LB-Across"] 80
}
}

  1. Test thoroughly in a non-production environment before deploying to production.And the above example is when backend pools are listening on port 80

Important: This iRule stores the backend server address in plaintext within the cookie. This is a conceptual workaround only. For production use, implement cookie value encryption or obfuscation before deployment.Please enage Professional services if further assistance with irule creation is required based on the requirements

Additional Troubleshooting Step:

  • If authentication errors persist after addressing persistence configuration, engage the application team to investigate whether individual pool members have independent application-side issues (e.g., token or session errors occurring even in single-member testing scenarios).

Additional Information

  • Cookie Insert + Match Across Services/Virtual Servers is not a supported combination on BIG-IP for cross-virtual-server session affinity. This behavior is by design and is not a bug.
  • Source Address Affinity persistence with Match Across may also fail to maintain per-user session affinity in environments where multiple users share the same source IP address (e.g., behind a NAT or firewall performing DNAT), as BIG-IP cannot distinguish individual users by source IP alone in such scenarios.
  • If errors are observed when only a specific pool member is active (independent of persistence configuration), this may indicate a concurrent application-side issue on that member, which should be investigated separately by the application team.
