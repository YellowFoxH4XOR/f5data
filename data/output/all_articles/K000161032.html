K000161032: SCTP Peer Server Does Not Respond to INIT After BIG-IP Upgrade from v14 to v17.1.2

Type
Support Solution
Published
2026-04-29
Updated
2026-04-29
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.2
Source
https://my.f5.com/manage/s/article/K000161032

Description

After upgrading BIG-IP LTM from version 14 to 17.1.2, SCTP peer servers do not respond to SCTP INIT messages. Packet captures show repeated SCTP INITs sent from BIG-IP, but no responses from the peer server. Rolling back to version 14 restores normal SCTP handshake and Diameter communication. This issue occurs when using MRF Diameter transport-config with a defined source-port.

Environment

  • Product: BIG-IP LTM
  • Software Versions: v14 (working), v17.1.2 (issue observed)
  • Features: MRF Diameter, SCTP transport
  • Configuration:
    • Diameter peers and transport-config objects with SCTP and explicit source-port set (e.g., source-port 13868)
    • Source-address-translation (SNAT) enabled in transport-config
  • Recent Change: Upgrade from BIG-IP v14 to v17.1.2

Cause

A behavior change introduced in BIG-IP v16.0.0 (see Bug ID836205)
When a non-zero source-port is defined in MRF transport-config, the default source-port-mode changes to 'change' instead of 'preserve-strict'. This can cause SCTP INIT packets to use unexpected source ports, leading to peer servers not responding.

Answer/Recommended Actions

To resolve SCTP peer connectivity issues after upgrading to BIG-IP v16.0.0 or later:

  1. Identify all MRF Diameter transport-config objects with a non-zero source-port defined.
  2. Explicitly set the source-port-mode to preserve-strict for each affected transport-config. For example:

    modify ltm diameter transport-config <name> source-port-mode preserve-strict

    save sys config

  3. Save the configuration.
  4. Verify SCTP connectivity and that peer servers respond to INIT messages as expected.

Additional Information

  • In BIG-IP versions prior to 16.0.0, the default behavior for source-port-mode was 'preserve-strict' when a source-port was set.
  • After the upgrade, if source-port-mode is not explicitly set, it defaults to 'change', which may break SCTP handshakes with peers expecting a fixed source port.
  • This behavior change is documented in Bug ID836205.
