Description

When having HA F5OS VELOS system or rSeries r5/r10/r12k appliance connected to the same set of Cisco ACI switch, when you failover the traffic group from one tenant on one F5OS system to the other one, you observed that the switch raises alert related to either "Endpoint Retention Policy" , "Rogue EP Control", or "Disabling learnig in vlan xxx for xxxs due to too many mac moves.". This kind of alert usually indicate one mac address shows in multiple interfaces in a short time(e.g. within less than 1 second). When such alert is raised, the swich could suspend L2 MAC/ARP/NDP learning for some time given the configurations on the switch and further affecting the overall traffic processing.

For example:

Learning is disabled on BD <BD_NAME> on node with id <id> with name <name> from pod <x> of fabric <FABRIC_NAME> because of BD Move frequency

OR

<faultRecord ack="no" affected="xxxx" cause="ep-mac-is-rogue" changeSet="addr:xxx" childAction="" code="xxxx" created="xxxx" delegated="no" delegatedFrom="" descr="EP MAC xxxx is rogue on interface pox of Node xxxx, Pod x, moving from interface port-channelx (0xxxxxxx)" dn="xxxx" domain="access" highestSeverity="warning" id="xxxxxx" ind="modification" lc="raised" modTs="never" occur="1" origSeverity="warning" prevSeverity="warning" rule="epm-rogue-mac-ep-epmacrogue" severity="warning" status="" subject="oper-state-change" type="operational"/>

 

On some other Cisco switch, it could be observed having the below logs:

L2FM-2-L2FM_MAC_FLAP_DISABLE_LEARN: Disabling learnig in vlan xxx for 120s due to too many mac moves.

L2FM-2-L2FM_MAC_FLAP_RE_ENABLE_LEARN: Re-enabling learning in vlan xxx

Environment

  • F5OS VELOS or r5k/r10k/r12k appliances that have FPGA chips
  • Mac Masqurade is configured
  • Failover event
  • Cisco ACI switch
  • FastL4 profile

Cause

On F5OS platforms, the tenant runs like a VE on a hypervisor system. For FPGA platforms, it takes time to send signals to FPGA chip to clear/sync the FPGA states when failover is triggered from the guest tenant to the F5OS platform OS layer and subsequently the underlayer FPGA chip. Thus, there is chance to meet a race condition that the old active device could still forward a small amount traffic at nano-seconds(e.g. 0.0001 seconds) level.

Additionally, if IPv6 traffic is involved, BUG 2016349 could magnificate the impact because of missing NDP NA. NDP NA is used for moving traffic from one device to the other like the ARP in IPv4, when it get missed, the NDP entry on upstream network devices could miss so it might still send traffic to old Active F5OS system. Thus, it magnificate the impact given the aforementioned signaling mechanism.

Recommended Actions

To mitigate this issue, there could be multiple directions.

The main two solutions are:

  1. Adjust the Cisco ACI Switch configuration to be more tolerable. Typically, there are configuration options such as "Move Frequncy" or "Rougue Control" those controls the sensitivity of the trigger, adjusting those options to a more tolerant value could be recommended to have better compability.
  2. Adjust the db key "pva.standby.flush" to value 1, so the VELOS FPGA flush process could be faster. This is only appliacable for BIG-IP Tenant versions >=17.1.1.2 and F5OS dma-agent >=11.3(F5OS-A/C >=1.8). To do so, you could use the below command and restart the tenant to let the BIG-IP to pick up the change.
    Important: Restarting would impact traffic processing, please arrange maintenance window for this operation.     
    tmsh modify sys db pva.standby.flush value 1
tmsh save sys config
