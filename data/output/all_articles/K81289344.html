Description

Beginning in BIG-IP 14.0.0, RFC4291 IPv4-Mapped IPv6 self IP Addresses are automatically converted and created as IPv4 self IP addresses.

  • Attempting to configure an IPv4-Mapped IPv6 self IP address on earlier versions fails with the following error message:
    Error: Invalid IP or Hostname
  • After upgrading to 14.x or later, configuring an RFC4291 IPv4-Mapped IPv6 self IP address, results in the self IP address being created as the respective IPv4 IP address.

    For example, if you try to add self IP IPv6 ::ffff:a16:c05/96 via the GUI interface, it will auto-convert it back to an IPv4 self IP address

    net self v15GUI {
        address 10.22.12.5/22
        traffic-group traffic-group-local-only
        vlan myVlan
    }

    Viewing it via GUI shows the same;
    v15GUI          10.22.12.5        255.255.252.0   myVlan        traffic-group-local-only Common

Note: if attempting to create IPv4-Mapped IPv6 address using TMOS CLI may result in a TMM restart loop. for information refer to Bug Tracker article: Bug ID 858309: Setting a self IP with an IPv6 Address with an embedded IPv4 address causes tmm to continually restart

Environment

  • BIG-IP with IPv6 configuration (RFC4291 IPv4-Mapped IPv6 addresses)
  • Versions 14.x or greater
 

Cause

None. This is an expected change in behavior to address threats with IPv4 Mapped IPv6 addresses, listed and discussed further in the Additional Information section below.
 

Recommended Actions

Avoid using IPv4-Mapped IPv6 addresses. Use IPv4, or alternative IPv6 addresses.
 

Additional Information

For more details about IPv4-Mapped IPv6 addresses, and possible related threats, refer to the following information:

  • IPv4-Mapped Addresses on the Wire Considered Harmful
  • RFC4291 #section-2.5.5.2 - IPv4-Mapped IPv6 address

Some key points include from those articles:

2.  Threats due to the use of IPv4-mapped address on wire

When an application using the AF_INET6 API receives an IPv4-mapped
addresses (for example, returned by getpeername(2) or recvfrom(2)), it
cannot detect if the packet received by the node actually used IPv4
(basic API behavior) or IPv6 (SIIT behavior).

This ambiguity creates an opportunity that a malicious party can exploit
in order to deceive victim nodes.  For example:

o If an attacker transmits an IPv6 packet with ::ffff:127.0.0.1 in the
  IPv6 source address field, he might be able to bypass a node's access
  controls by deceiving applications into believing that the packet is
  from the node itself (e.g., the IPv4 loopback address, 127.0.0.1).
  The same attack might be performed using the node's IPv4 interface
  address instead.

o If an attacker transmits an IPv6 packet with IPv4-mapped addresses in
  the IPv6 destination address field corresponding to IPv4 addresses
  inside a site's security perimeter (e.g., ::ffff:10.1.1.1), he might
  be able to bypass IPv4 packet filtering rules and traverse a site's
  firewall.

o If an attacker transmits an IPv6 packet with IPv4-mapped addresses in
  the IPv6 source and destination fields to a protocol that swaps IPv6
  source and destination addresses, he might be able to use a node as a
  proxy for certain types of attacks.  For example, this might be used
  to construct broadcast multiplication and proxy TCP port scan attacks.
