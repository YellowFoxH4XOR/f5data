K000153190: BIG-IP LTM iRule STREAM::expression HTTP-to-HTTPS Rewriting Fails Due to Incorrect Delimiter Syntax

Type
Support Solution
Published
2025-09-17
Updated
2026-05-21
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.2
Source
https://my.f5.com/manage/s/article/K000153190

Description

When using a BIG-IP LTM iRule with STREAM::expression to rewrite HTTP references to HTTPS in HTTP responses, a syntax error in the iRule can cause the website to fail to render correctly.

Symptoms:

  • Website fails to load properly (broken page rendering) when the STREAM::expression iRule is applied.
  • Removing the @http:@https:@ expression from the iRule allows the page to load, but results in mixed content warnings in the browser.
  • HTTP references in response body content (such as JavaScript URLs) are not being rewritten to HTTPS as expected.

Environment

  • Product: BIG-IP LTM
  • Version: 17.1.2
  • Feature: iRule with STREAM::expression for HTTP-to-HTTPS response body rewriting
  • Backend application: WordPress (recently patched/upgraded)
  • Virtual server configuration:
    • HTTPS frontend (port 443) with SSL offload
    • HTTP backend (port 80)
    • Stream profile attached
    • Accept-Encoding header removed in HTTP_REQUEST event
  • iRule events used: HTTP_REQUEST, HTTP_RESPONSE

Cause

Incorrect delimiter syntax in STREAM::expression within the iRule. Specifically, a space was present between the opening brace  {  and the first delimiter character @. According to F5 documentation, this space causes STREAM::expression to not function as intended, preventing proper HTTP-to-HTTPS rewriting of response body content.

Answer/Recommended Actions

Per the STREAM::expression iRules documentation, there must be no space between the opening brace  {  and the first delimiter in the expression.

Incorrect syntax (will NOT work):

STREAM::expression { @http:@https:@ @Windows@Linux@ }

Please take note on the space between  {  and the first @)

Correct syntax (will work):

STREAM::expression {@http:@https:@ @Windows@Linux@}

  1. Locate the iRule applied to the affected virtual server that contains the STREAM::expression command.
  2. In the HTTP_RESPONSE event, verify the STREAM::expression block does not have a space between the opening brace  {  and the first delimiter.
  3. Update the iRule to use the correct syntax. Example of a corrected iRule for HTTP-to-HTTPS rewriting: 
    when HTTP_REQUEST {
    STREAM::disable
    HTTP::header remove "Accept-Encoding"
}
when HTTP_RESPONSE {
    STREAM::disable
    if { [HTTP::header exists "Location"] } {
        HTTP::header replace Location [string map {"http://" "https://"} [HTTP::header Location]]
}
    if { [HTTP::header "Content-Type"] starts_with "text/html" } {
        STREAM::expression {@http:@https:@ @http://@https://@ @http:\/\/@https:\/\/@}
        STREAM::enable
    }
}
  1. Apply the updated iRule to the virtual server.
  2. Test the website to confirm that HTTP references in the response body are correctly rewritten to HTTPS and that no mixed content warnings appear.

Additional Information

  • The incorrect syntax issue may not have been apparent prior to the backend WordPress upgrade if the previous WordPress version generated response content that did not trigger the problematic code path in the same way.
  • When STREAM::expression fails silently due to the syntax error, HTTP references in the response body are not rewritten, causing browsers to report mixed content warnings or fail to load resources.
  • The Accept-Encoding header should be removed in the HTTP_REQUEST event (as shown above) to prevent the backend from sending compressed responses, which would interfere with stream-based content rewriting.
  • Ensure the Stream profile is attached to the virtual server for STREAM::expression and STREAM::enable to function correctly.
  • The Content-Type condition (starts_with "text/html" or contains "text") controls which responses are subject to stream rewriting. Using contains "text" is broader and may affect additional content types such as JavaScript files.
