Enabling logging with the Common.Bigip.Failover.DbgFile bigdb key

To enable logging with the Common.Bigip.Failover.DbgFile bigdb key, perform the following procedure:

  1. Log in to the command line.
  2. Enable the failover log by typing the following command:

    bigpipe db set Common.Bigip.Failover.DbgFile = /var/log/failover.log
  3. Reinitialize the switch over daemon to begin logging by typing the following command:

    bigstart reinit sod

    The information is now logged to the /var/log/failover.log file.

Disabling the failover.log file

To disable the failover.log file, perform the following procedure:
 

  1. Log in to the command line.
  2. Disable the failover.log file by typing the following command:

    bigpipe db unset Common.Bigip.Failover.DbgFile
  3. Reinitialize the switch over daemon to disable logging by typing the following command:

    bigstart reinit sod

The failover.log file entries are defined as follows:

Network Failover Settings

The first section (starting with UnitNumber and ending with failover_loop) logs the settings for network failover. This section includes the timeouts allowed for peer response and retry before failover occurs.

State Table

The rest of the log is the State Table. The State Table defines the state mask for the unit and its peer. The columns for this table are defined as follows:

The first column of the State Table contains the logged events. The event types are:

  • test
  • startup
  • standby
  • active

The unit_m (second) column of the State Table contains the mask of the unit ID number. For example, an active-active unit would have a value of 1 or 2, a standby unit would have a value of 0, and an active-standby pair would have a value of 3.

Unit StatusValue
Standby0
Active (Unit ID 1) - only in active-active1
Active (Unit ID 2) - only in active-active2
Active (Unit ID 1 and 2)3

 

The peer_m (third) column of the State Table displays the status of the peer. The logic is the same as the unit_m column, with the addition of the value -1. This value means that the status of the peer is undetermined.

Unit StatusValue
Standby0
Active (Unit ID 1) - only in active-active1
Active (Unit ID 2) - only in active-active2
Active (Unit ID 1 and 2)3
Unable to determine peer status-1

 

The fourth column is the state field. During a failover, the state field is ignored. In a test_event, the state field reflects the value retrieved from the serial line. Any change in value would indicate an issue with the serial line.

State Mirroring and Stateful Failover Error Messages

BIG-IP address initialization errors

Error messagesDescription
  • exiting, no peer IP addr specified in bigdb
  • must specify BIG-IP's IP addr in bigdb
  • must specify peer ip addr
  • BIG-IP's local internal IP address not in bigdb
For each of these errors there is an exit, and a failure. To fix these errors, rerun the config command and set the IP addresses for the local BIG-IP and its peer.

Error Recovery

Error messagesDescription
  • make_msg_consistant fails: zero len msg
  • make_msg_consistant fails: can't read last msg
These are fatal errors and should be escalated to Engineering Services immediately.

Initialization Errors

Error messagesDescription
  • fopen fails: <error string>
  • log file open fails: <error string>
  • debug level specific without log file
  • child log file open fails: <error message>
These errors occur when sfd is invoked with debug logging. Be sure to specify a log file in a valid path.
  • write_pid_file: open: <error string>
  • cannot execute /bin/ps
  • kill: <error string>
  • kill_via_pid: kill: <error string>
These errors indicate that sfd did not stop correctly when restarted.

Out of memory error

Error messageDescription
out of memory, aborting.This error should only occur if the BIG-IP global memory_reboot_percentage is set to 0. If you receive this error, reset the global memory_reboot_percentage to 95 so the BIG-IP will reboot when it runs out of memory.
