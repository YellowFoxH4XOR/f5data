Known Issue

Requests may trigger a Modified ASM cookie violation after you upgrade the system.

This issue occurs when all of the following conditions are met:

  • You have configured your BIG-IP ASM security policy to alarm or block on Modified ASM cookie violations.
  • The security policy processes user requests.
  • You upgrade to a listed release.
  • Existing users attempt to request additional content.

Impact

Existing users receive a false positive Modified ASM cookie violation and the system may block the users.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • When a user requests content through the security policy presenting a BIG-IP ASM cookie from the pre-upgrade session, the BIG-IP ASM triggers a Modified ASM cookie violation.
  • When a user requests content through the security policy that did not have a pre-upgrade session (no BIG-IP ASM cookie) the Modified ASM cookie violation is not triggered.
  • When you compare the post-upgrade BIG-IP ASM cookie with the pre-upgrade BIG-IP ASM cookie, the post-upgrade cookie is larger by several bytes.

Workaround

To work around this issue, you can temporarily implement one of the following methods to remove or ignore pre-upgrade BIG-IP ASM cookies. To do so, perform the following procedures:

  • Remove the Block setting for the Modified ASM cookie of the affected security policy
  • Configure the affected security policy blocking page with the Response Type of Erase cookies
  • Create and apply an iRule to the affected virtual server

Remove the Block setting for the Modified ASM cookie of the affected security policy

Impact of workaround:  By performing the following procedure, you configure the security policy to no longer block requests that have a Modified ASM cookie.

You can work around the Modified ASM cookie violation blocking by removing the block setting for this violation.

To do so, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Navigate to Security > Application Security > Policy Building > Learning and Blocking Settings.
  3. Set Current edited policy to the name of the affected policy.
  4. Click the Blocking Settings button.
  5. Clear the Block box for Modified ASM cookie.
  6. Click Change.
  7. Click Apply Policy.

Configure the affected security policy blocking page with the Response Type of Erase cookies

Impact of workaround:  Performing the following procedure will initially block user requests that have a Modified ASM cookie; however, subsequent requests will be handled normally.

You can work around the Modified ASM cookie violation triggered by pre-upgrade ASM cookies by having the BIG-IP ASM system remove the old cookie on the first blocking violation.

To do so, perform the following procedure:

  1. Navigate to Security > Application Security > Policy.
  2. Click the name of the affected policy.
  3. Click the Response Pages tab.
  4. In the Default Response Page section, from the menu, change the Response Type to Erase Cookies.
  5. Click Save.
  6. Click Apply Policy.

Create and apply an iRule to the affected virtual server

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

You can create and implement an iRule that will remove the user request old cookie and assign the user request an updated cookie.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules.
  3. Click Create.
  4. In the Name box, type a name for the iRule.
  5. In the Definition box, enter the following text:

    when ASM_REQUEST_DONE {
    if {[ASM::violation names] contains "VIOLATION_MOD_ASM_COOKIE"} { 
    log local0. "remove TS01d2cce8 cookie" 
    HTTP::respond 302 Location "http://<absolute uri>?[ASM::support_id]" "Set-Cookie" "TS01d2cce8=deleteOldTSCookie;expires=Thu, 01 Jan 1970 00:00:01 GMT"
          }
    }

    Note: For the security policy protected resource, replace <absolute uri> with the destination URI of the initial access.

    For example:

    http://www.example.com/index.html

  6. Click Finished.
  7. Navigate to Local Traffic > Virtual Servers.
  8. Click the name of the virtual server that is affected by this issue.
  9. Click the Resources tab.
  10. In the iRules section, click Manage.
  11. From the Available column, select the new iRule.
  12. To move the iRule to the Enabled column, click the << button.
  13. Click Finished.
