K25255894: EXT4-fs error (device dm-3): ext4_ext_find_extent

Description

Error messages similar to the following are being logged in /var/log/kern.log

May 13 11:28:03 host.example.com crit kernel: EXT4-fs error (device dm-3): ext4_ext_find_extent:880: inode #75: comm java: pblk 33813 bad header/extent: invalid magic - magic 0, entries 0, max 0(0), depth 0(0)
May 13 11:28:03 host.example.com warning kernel: JBD2: Spotted dirty metadata buffer (dev = dm-3, blocknr = 0). There's a risk of filesystem corruption in case of system crash.
May 13 11:28:03 host.example.com crit kernel: EXT4-fs error (device dm-3): ext4_ext_find_extent:880: inode #75: comm java: pblk 33813 bad header/extent: invalid magic - magic 0, entries 0, max 0(0), depth 0(0)
May 13 11:28:03 host.example.com crit kernel: EXT4-fs error (device dm-3): ext4_ext_remove_space:2971: inode #75: comm java: pblk 33813 bad header/extent: invalid magic - magic 0, entries 0, max 0(0), depth 0(0)
May 13 11:28:03 host.example.com crit kernel: EXT4-fs error (device dm-3) in ext4_ext_truncate:4683: IO failure

Environment

BIG-IP 

Cause

Unknown at this time

Recommended Actions

1.  The first thing to try is a forcing a file system check on restart:

K73827442: Forcing a file system check on the next system restart (12.x - 16.x)
https://my.f5.com/manage/s/article/K73827442

2.  If this does not resolve the issue you will need to try this more detailed check:

1. Find which logical volume corresponds to "dm-3" (which is pointed out in the "EXT4-fs error" logs) by running the following command:

#lsblk --output NAME,KNAME,TYPE,SIZE,MOUNTPOINT

Example output:

NAME                          KNAME TYPE   SIZE MOUNTPOINT
sda                           sda   disk   126G
|-sda1                        sda1  part   200M
|-sda2                        sda2  part    16M
`-sda3                        sda3  part 125.8G
  |-vg--db--vda-dat.maint.1   dm-0  lvm    300M
  |-vg--db--vda-dat.share     dm-1  lvm     15G /shared
  |-vg--db--vda-dat.appdata   dm-2  lvm   66.7G /appdata
  |-vg--db--vda-dat.log       dm-3  lvm      3G /var/log	<---------
  |-vg--db--vda-dat.swapvol   dm-4  lvm   1000M [SWAP]
  |-vg--db--vda-set.1.root    dm-5  lvm    440M /
  |-vg--db--vda-set.1._usr    dm-6  lvm    5.2G /usr
  |-vg--db--vda-set.1._config dm-7  lvm    2.2G /config
  |-vg--db--vda-set.1._var    dm-8  lvm      3G /var
  |-vg--db--vda-set.2.root    dm-9  lvm    440M
  |-vg--db--vda-set.2._usr    dm-10 lvm    5.2G
  |-vg--db--vda-set.2._config dm-11 lvm    2.2G
  `-vg--db--vda-set.2._var    dm-12 lvm      3G

Save this output in a text file before the next step as you will be restarting the unit.

2. Using the VMWare console, restart the BIG-IP.  While the BIG-IP is restarting, you have a short time (by default, only a few seconds) to press a keyboard key to interrupt auto-boot. After the GNU GRUB menu appears, immediately press the down arrow key. Select TMOS maintenance. Press Enter.

3. Run command "e2fsck -y /dev/mapper/<dm-3-vg-name>" pointing to the logical volume which corresponds to dm-3.

Taking the example from above, it would be:

#e2fsck -y /dev/mapper/vg--db--vda-dat.log

4. This should show some output recovering the errors.

5. Run the command "reboot" after the recovery is complete.

You may need to repeat these steps if after rebooting a new logical volume presents similar error message
