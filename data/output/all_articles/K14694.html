Known Issue

The active_members iRule command does not account for priority groups.

This issue occurs when all of the following conditions are met:

  • You use the active_members iRule command for a pool that is configured with minimum active members (min-active-members).
  • You configure the pool members with priority groups (priority-group).

The active_members iRule command does not restrict available pool member results to only be members of the priority groups currently in use. The active_members iRule command incorrectly returns the number of pool members that are available across all priority groups, even if the highest-priority group has enough active members to preclude load-balancing to a lower priority group's pool members.

Impact

The affected iRule may inaccurately calculate the number of active pool members that are eligible for a load balancing decision.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • BIG-IP iHealth lists Heuristic H430123 on the Diagnostics > Identified > Medium screen.
  • An affected iRule may not function as expected.
  • The active_members <pool> command returns an unexpected result.

Workaround

Impact of workaround: Performing the following workaround should not have a negative impact on your system. However, you should validate any iRule changes before introducing the changes to a production environment.

To work around this issue, you can use the -list argument with the active_members iRule command.

For example, you could use the -list argument with the active_members command:

when CLIENT_ACCEPTED {
      if { [active_members -list http_pool] >= 2 } {
        pool http_pool
      }
    }
