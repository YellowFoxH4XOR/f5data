Description

When the Microsoft Exchange Extended Protection mitigation for vulnerability CVE-2024-21410 is applied on the Exchange servers, it can break the connection between Outlook and the exchange server.

NOTE: This article applies to BIG-IP devices that do not have APM provisioned. For devices with APM provisioned, please refer to article K000139336

Environment

  • Channel Binding
  • LTM-only setup (No APM provisioned - Other modules can be provisioned)

Cause

Windows Extended Protection enhances the existing authentication in Windows Server and mitigates authentication relay or man-in-the-middle (MitM) attacks. This mitigation is accomplished by using security information that is implemented through channel-binding information specified through a Channel Binding Token (CBT) which is primarily used for TLS connections.

This is causes any proxies (in our case, a BIG-IP) between Outlook and the Exchange server, to be affected.

If the device has only LTM provisioned (no APM), this will have an impact to the SSL configuration of the VIP.

Recommended Actions

Deploying this mitigation can prevent Exchange from working, depending on how the VIP (SSL offload vs. SSL bridging as mentioned above) is configured and the certificates. This is not a direct issue with the BIG-IP, it's just that this deployment causes issues with any proxies located between Outlook and the Exchange servers. This has to be discussed internally first with architects within the organisation on how it should be deployed. Since deploying this is likely to break any proxy-based architecture it will have to be decided whether the network setup will remain with the proxy or with Channel Binding. If the choice is to go with both, then the client SSL profile will need to be reconfigured with the certificate and key from the internal Exchange server.

SSL Offloading scenarios
Extended Protection isn't supported in environments that use SSL Offloading. SSL termination during SSL Offloading causes Extended Protection to fail. To enable Extended Protection in your Exchange environment, you must not be using SSL offloading with your Load Balancers.

SSL Bridging scenarios
Extended Protection is supported in environments that use SSL Bridging under certain conditions. To enable Extended Protection in your Exchange environment using SSL Bridging, you must use the same SSL certificate on Exchange and your Load Balancers. Using different certificates cause Extended Protection Channel Binding Token check to fail and as a result, prevent clients from connecting to the Exchange server.
