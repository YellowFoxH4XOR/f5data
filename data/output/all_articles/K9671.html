Known Issue

This is the result of a known issue. The BIG-IP WebAccelerator inserts the HTTP Cache-Control: no-cache header into a response. This behavior occurs when the requested object matches an acceleration policy node with client cache settings configured with the Do not change option selected, and the response from the origin web server (OWS) does not have an existing HTTP Cache-Control header.

Note: The BIG-IP WebAccelerator inserts the HTTP Cache-Control: no-cache header into a response regardless of whether the Always proxy request for this node option is selected.

When the HTTP Cache-Control: no-cache header is inserted by the BIG-IP WebAccelerator, Internet Explorer 6 browser clients may be unable to display objects with an external application.

Note: For information about this issue, refer to K9603: Microsoft Office documents may not open or save properly when accessed through a BIG-IP WebAccelerator using Internet Explorer 6.

Note: This behavior was introduced in Hotfix-BIG-IP-9.4.5-HF2 for BIG-IP WebAccelerator version 9.4.5 to address caching issues with downstream caches.

Starting in BIG-IP WebAccelerator version 9.4.5-HF2, when the Configure and use Proxy Rules for this node option is selected, the BIG-IP WebAccelerator will insert a Cache-Control: private directive. In version 10.0.x, the BIG-IP WebAccelerator will insert a Cache-Control: public directive.

The client-side Cache-Control header is not altered by proxy rules and proxy override rules that otherwise change the BIG-IP WebAccelerator proxy behavior.

F5 Product Development tracked this issue as CR114311 and it was fixed in BIG-IP WebAccelerator version 10.1.0. For information about upgrading, refer to the BIG-IP WebAccelerator release notes.

Additionally, this issue was fixed in BIGIP-10.0.1-378.0-HF3, which has been issued for BIG-IP WebAccelerator version 10.0.1, for the 10.0 software branch. You may download this hotfix or later versions of the cumulative hotfix from the F5 Downloads site.

To view a list of the latest available hotfixes, refer to K9502: BIG-IP hotfix matrix.

Workaround

You can work around this issue by configuring the BIG-IP WebAccelerator to insert an HTTP Cache-Control: max-age=10 header instead of the HTTP Cache-Control: no-cache header. To do so, perform the following procedure:

  1. Identify the node in the acceleration policy that is being matched.

    Note: For information about using the C code in an X-PvInfo header to identify the acceleration policy node matched for a request, refer to K9541: Determining the X-PvInfo header C code for a BIG-IP WebAccelerator application.

    Note: For information about the X-PvInfo header information, refer to the Viewing X-PvInfo response headers section of the Using HTTP Headers chapter in the BIG-IP WebAccelerator Policy Management Guide.

    Requests for unclassified object types will use the unclassified node in an acceleration policy. The Unclassified node by default is configured to use the Do not change option for the client cache settings. However, you should not modify the unclassified node for an acceleration policy unless you are sure that you want the changes applied to all unclassified requests.

    If the node being matched is the unclassified node, you should add a custom object type and and create a node in the acceleration policy that matches the custom object type. For example, CSV and iCalendar files are unclassified object types by default.

    Note: For information about adding an object type for CSV files to the globalframent.xml file, refer to K9461: Configuring the BIG-IP WebAccelerator to recognize the CSV file type.

    Note: For information about adding an object type for iCalendar files to the globalframent.xml file, refer to     K9660: Configuring the BIG-IP WebAccelerator to recognize iCalendar files.
  2. Log in to the Configuration utility.
  3. Click WebAccelerator.
  4. Click Policies.

    A new Policies configuration page opens.

    Note    : You cannot edit predefined acceleration policies. If you are using a predefined acceleration policy, you must copy the policy and edit the new user-defined acceleration policy.     
  5. Select the user-defined acceleration policy to edit.
  6. Expand the branches in the Policy Tree and select the policy node to edit.
  7. Select Acceleration Rules from the Policy drop-down menu.
  8. Click on the Lifetime menu tab.
  9. Click on the Maximum Age radio option button.

    A new Maximum Age field and drop-down menu are displayed.
  10. Type 10 in the Maximum Age field.
  11. Select Seconds from the Maximum Age drop-down menu.
  12. Click Save.
  13. Click Publish.
  14. Click Publish Now.

Note: If you had to copy a predefined acceleration policy and create a new user-defined acceleration policy, you must also associate the new user-defined policy with your BIG-IP WebAccelerator application.

The BIG-IP WebAccelerator will now insert an HTTP Cache-Control: max-age=10 header instead of the HTTP Cache-Control: no-cache header for requests matching the acceleration policy node.

Additional workarounds

You can also work around this issue by performing one of the following additional workarounds:

  • Create a custom node in the WebAccelerator policy to match affected pages and set the appropriate caching level.
  • Use an iRule to strip out the Cache-Control header for affected pages.
