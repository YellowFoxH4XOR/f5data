Description

This article provides an example showing the details about how an external HTTP client communicates with pods within the mesh cluster. The below example contains two deployments named sleep (one with sidecar and one without) and the purpose is to simulate HTTP client inside and outside the mesh. It also includes another httpbin deployment with sidecar with the purpose of simulating a HTTP server inside a mesh, with a sleep additional service account which is mounted to the sleep pod without a sidecar to add the necessary client certificates. You can verify this by opening a shell into the sleep pod without a sidecar and verifying the certificate at volume mount location (/etc/sleep/tls).

Protected by mTLS: Yes (as the default PeerAuthentication is in Strict Mode).

This is a motivating case for this example. How does a non-mesh client talk to a service in the mesh? There are three possible approaches: 

  1. Use a Gateway, a special resource implemented in ingress gateway pods specifically designed to forward communication from external clients that cannot do mTLS onto the mesh. 
  2. Disable mTLS for a particular service using an authentication Policy. This is less secure. It also generally requires an equivalent DestinationRule so that mesh clients know to not use mTLS. It's possible to make mTLS optional but this may be worse from a security standpoint as traffic may look secured until a client asks for insecure. 
  3. Teach the client how to do mutual TLS and give it a certificate and key so that it is accepted by server sidecars that are in the mesh. This example covers the last approach. First, you must give the client application a certificate and key to use that will be trusted by the mesh. You can see in the example that we created an extra service account (sleep-additional). 

After deploying all the above yaml files, Now we must use it when calling a service that is protected by an mTLS-enforcing sidecar, like httpbin-sidecar:

You can see that the sidecar trusted the sleep client based on the SPIFFE identity spiffe://cluster.local/ns/nosidecar-mtls/sa/sleep-additional which is from the sleep-additional service account (not the primary sleep service account). This depicts that when we configured the external client with correct certificate, we can achieve a mTLS communication between two endpoints. 

Environment

  • Aspen Mesh: 1.9.x

Cause

None

Recommended Actions

None

Additional Information

Note that the client curl cannot validate the server (the -k option was passed to curl). Service mesh certificates do not have DNS SANs or CNAMEs by default and by design. So, while curl can validate the cert is signed by the proper web-of-trust, it cannot confirm that it is a valid cert for the service that the user asked it to connect to (httpbin-sidecar). Curl does not have an option to validate the SPIFFE URI SAN instead.
