Topic

You can use an iRule to load balance HTTP requests to different pools, depending on the attributes of the traffic. For example, you can load balance individual HTTP requests to different pools based on the URI path, content type, request parameters, user agent, or other request attributes. However, in order to support proper pool reselection mid-connection, such as supporting multiple HTTP requests arriving on the same Keep-Alive connection, the existing server-side connection must first be detached. If no conditions resulting in pool selection match the request, failure to detach from the existing server-side connection may result in an unexpected choice for the default pool. You can ensure that the existing server-side connection is detached by following one of the following two recommendations:

  • Applying a OneConnect profile to the virtual server
  • Explicitly coding the iRule to select a pool under every possible condition

Note: You may also use the LB::detach iRules command to detach the server-side connection when a pool change is detected. However, the previous recommendations result in a simpler, more efficient iRule. For more information, refer to LB::detach command on F5 Cloud Docs.

Note: The pool selection behavior temporarily changed in BIG-IP 11.5.3 HF2, and 12.0.0 through 12.0.0 HF3. For more information, refer to K00725997: The OneConnect virtual server may preserve the pool selection across multiple HTTP requests. However, that behavior change was reverted in BIG-IP 11.5.4 and 12.1.0.

Default pool selection for virtual servers using OneConnect

With a OneConnect profile applied, the server-side connection is always detached upon completion of the server response, and the default pool selection is reset for each request to match the default pool configured on the virtual server. As a result, pool reselection using an iRule applied to a OneConnect virtual server operates as expected:

  • Requests matching the pool selection conditions coded in the iRule are always sent to the indicated pool.
  • Requests not matching any pool selection condition in the iRule are always sent to the default pool configured on the virtual server, regardless of whether a pool was already selected for a previous request on the same connection.

When a client connects to a OneConnect virtual server that uses an iRule for pool selection, a pool is selected based on the attributes of each request and the coded iRule conditions. If a condition resulting in pool selection matches the request, the request is sent to the selected pool. If multiple conditions resulting in pool selections match the request, the request is sent to the pool selected in the last matching condition. If no iRules condition resulting in a pool selection matches the request, the request is sent to the default pool that is configured on the virtual server.

For example, using the following iRule, requests for /foo/bar/index.html is always be sent to the pool foo, while requests for /login will always be sent to the default pool configured on the virtual server:

when HTTP_REQUEST {
if { [HTTP::uri] starts_with "/foo" } {
pool foo
}
}

Default pool selection for virtual servers not using OneConnect

Without a OneConnect profile applied, the server-side connection is only detached if a new pool is explicitly selected. The default pool selection is not reset to match the default pool configured on the virtual server for subsequent requests on the same connection. Therefore, the default pool defined on the virtual server is only used as the default selection for initial requests that do not match any of the pool selection conditions (never for subsequent requests). As a result, pool reselection using an iRule applied to a non-OneConnect virtual server does not always operate as expected:

  • Initial and subsequent requests matching the pool selection conditions coded in the iRule are always sent to the indicated pool.
  • Initial requests not matching any pool selection condition in the iRule are always sent to the default pool configured on the virtual server.
  • Subsequent requests not matching any pool selection condition in the iRule are always sent to the last pool selected for this connection.

Initial pool selection

Initial pool selection for new connections to a non-OneConnect virtual server is the same as that for a OneConnect virtual server. When a client connects to a non-OneConnect virtual server that uses an iRule for pool selection, a pool is selected based on the attributes of the first request and the coded iRule conditions. If a condition resulting in pool selection matches the request, the request is sent to the selected pool. If multiple conditions resulting in pool selections match the request, the request is sent to the pool selected in the last matching condition. If no iRule condition resulting in a pool selection matches the request, the request is sent to the default pool that is configured on the virtual server.

For example, using the previous iRule example, a new connection containing a request for /foo/bar/index.html will always be sent to the pool foo, while a new connection containing a request for /login will always be sent to the default pool configured on the virtual server.

Subsequent pool selection

Pool selection for subsequent requests on a Keep-Alive connection to a non-OneConnect virtual server is different from that for a OneConnect virtual server. When a subsequent request arrives on a client connection for which a pool has already been chosen, a new pool may be selected based on the attributes of the subsequent request and the coded iRule conditions. As with the initial request, if a condition resulting in pool selection matches the request, the request is sent to the newly selected pool. If multiple conditions resulting in pool selections match the request, the connection is sent to the pool selected in the last matching condition. However, if no iRule condition resulting in a pool selection matches the request, the request is not sent to the default pool that is configured on the virtual server. Instead, the request is sent to the pool that was selected for the last request on the same connection.

For example, using the iRule example, a new connection containing a request for /foo/bar/index.html on a Keep-Alive connection will be sent to the pool foo, and a subsequent request for /profile.php on the same connection will also be sent to the pool foo, even though the attributes of the requests do not match the condition choosing the pool foo.

To ensure that subsequent requests are sent to the expected pool on a non-OneConnect virtual server, the iRule must explicitly select a pool under all conditions.

For example, the previous iRule example may be modified as follows to be compatible with a non-OneConnect virtual server:

when HTTP_REQUEST {
if { [HTTP::uri] starts_with "/foo" } {
pool foo
} else {
pool bar
}
}

When this iRule is applied to a non-OneConnect virtual server, a new connection that contains a request for /foo/bar/index.html on a Keep-Alive connection will be sent to the pool foo, and a subsequent request for /profile.php on the same connection will be sent to the pool bar.

Alternatively, you can use the LB::server pool command in the CLIENT_ACCEPTED event as shown in the example below to dynamically set the default pool in the iRule to the value of the default pool applied to the virtual server. This step is useful when applying the same iRule to virtual servers using different default pool names.

For example:

when CLIENT_ACCEPTED {
#When used in the CLIENT_ACCEPTED event, [LB::server pool] returns
#the name of the default pool configured on the virtual server 
#because no LB decision has been made for the brand new connection
set def_pool [LB::server pool]
}
when HTTP_REQUEST {
if { [HTTP::uri] starts_with "/foo" } {
pool foo
} else {
pool $def_pool
}
}

When this iRule is applied to a non-OneConnect virtual server, a new connection that contains a request for /foo/bar/index.html on a Keep-Alive connection is sent to the pool foo, and a subsequent request for /profile.php on the same connection is sent to the default pool configured on the virtual server.

Note: The same issue arises when the system persists requests to different destinations within the same Keep-Alive connection. For more information, refer to K7964: The BIG-IP system may appear to ignore persistence information for Keep-Alive connections.
