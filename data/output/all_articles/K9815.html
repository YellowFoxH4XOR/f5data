Topic

If a virtual server references a cookie persistence profile with a non-default cookie name and an iRule that chooses among multiple pools with different members, persistence is maintained for only the most recently selected pool. Since the cookie name is shared, once a new pool is chosen, the persistence information referencing the member in the original pool is overwritten with the new information referencing the member in the new pool. As a result, persistence within the original pool may fail.

For example, assume a virtual server uses a cookie persistence profile specifying the custom cookie name PersistCookie. The virtual server also references an iRule that selects between two pools (Pool_1 and Pool_2), depending on the request URI. When the first request arrives, the BIG-IP system selects a member from Pool_1 and inserts PersistCookie into the response that references the selected pool member. Subsequent requests from that client session include that cookie, which the BIG-IP uses to persist to the indicated pool member. When the client makes a request that causes the BIG-IP to select Pool_2, the BIG-IP system selects a member from Pool_2 and again inserts PersistCookie into the response that references the selected pool member. When the client receives the cookie, it overwrites the previously stored value with the new value. When the client again makes a request for which the BIG-IP selects Pool_1, the persistence cookie is submitted, but it now contains the persistence information referring to a member of Pool_2. Since the pool member referenced by the persistence cookie is not a member of the selected pool, the BIG-IP system cannot choose it. With no valid persistence information available, the BIG-IP system must make a new load balancing decision. This sequence of events is repeated each time the iRule selects a new pool.

Note: This issue does not occur if all pools contain an identical set of pool members. In addition, if a subsequently-chosen pool has an identical member to that encoded in the persistence token by a previous pool selection, the request will be persisted as expected.

You can avoid this issue by using one of the following techniques:

  • Configuring the cookie persistence profile to use the default persistence cookie name
  • Specifying in the iRule a unique custom persistence cookie name for each pool
  • Load-balancing connections to virtual servers referencing single pools and unique persistence profiles

Configuring the cookie persistence profile to use the default persistence cookie name

The easiest way to avoid this issue is to not configure a custom cookie name.

By default, when using HTTP cookie insert persistence, the BIG-IP system inserts a cookie with a unique name referencing the selected pool. The cookie name takes the following format:

BIGipServer<pool_name>

Using a unique cookie name for each pool requiring persistence ensures that the persistence information for each pool is retained across pool selections.

Note: One drawback of this approach is that the cookie name exposes the fact that the BIG-IP system is in use, which may be considered a security breach.

Specifying in the iRule a unique custom persistence cookie name for each pool

The preferred solution is to modify the iRule to specify a unique custom persistence cookie name for each pool selected by the iRule.

For example, the following iRule does not specify the cookie name to be used:

rule SelectPoolbyURI_sharedCookie {
when HTTP_REQUEST {
if { [string tolower [HTTP::path]] starts_with "/xyz/" } {
pool Pool_1
persist cookie insert
} else {
pool Pool_2
persist cookie insert
}
}
}

If a custom cookie name is configured for the cookie persistence profile, the persistence failure described above will occur.

The iRule may be modified to avoid this issue by specifying a unique cookie name, depending on the pool chosen.

For example, using the following iRule, a separate persistence cookie is maintained for each pool:

rule SelectPoolbyURI_uniqueCookie {
when HTTP_REQUEST {
if { [string tolower [HTTP::path]] starts_with "/xyz/" } {
pool Pool_1
persist cookie insert "Pool_1"
} else {
pool Pool_2
persist cookie insert "Pool_2" }
}
}

Note: In both cases, a cookie persistence profile including any other desired options must still be applied to the virtual server.

Note: The iRule should explicitly define a pool selection and the corresponding unique cookie name for every possible condition resulting in a pool selection. Any condition for which a pool is not explicitly assigned along with a corresponding unique cookie name may result in selection of the default pool, and the insertion of a cookie named according to the applied cookie persistence profile configuration.

Load-balancing connections to virtual servers referencing single pools and unique persistence profiles

Coding custom persistence cookie names in an iRule instead of using the cookie name defined in the persistence profile adds a layer of abstraction that may not be obvious, since information about the virtual server’s resources is now distributed among the virtual server definition, the profile definition, and within the iRule. In versions 9.4 and later, you can use the virtual iRule command instead of the pool iRule command to load-balance requests to other virtual servers instead of pools. This behavior allows configuration of a master virtual server that distributes requests to other more specifically configured virtual servers. For example, each of those virtual servers can reference a single default pool, along with a custom cookie persistence profile using a unique custom cookie name, which allows each of the virtual servers to independently maintain persistence for its default pool.

To insert custom cookies with unique names per pool using this approach, you must configure a separate virtual server for each pool the iRule will select. Each virtual server references a unique default pool and a corresponding cookie insert profile that specifies a unique cookie name.

Once you have configured the virtual servers fronting each pool, modify the iRule to select the virtual server corresponding to each pool it originally selected. For example, modifying the example from the Specifying in the iRule a unique custom persistence cookie name for each pool section results in the following iRule:

rule SelectVSbyURI {
when HTTP_REQUEST {
if { [string tolower [HTTP::path]] starts_with "/xyz/" } {
virtual Virtual_Pool_1
} else {
virtual Virtual_Pool_2
}
}

Finally, remove the persistence profiles from the original virtual server, and apply the new iRule as its resource. The resulting configuration includes the following references:

virtual MainVirtual {
rules SelectVSbyURI
}

rule SelectVSbyURI {
when HTTP_REQUEST {
if { [string tolower [HTTP::path]] starts_with "/xyz/" } {
virtual Virtual_Pool_1
} else {
virtual Virtual_Pool_2
}
}
}

virtual Virtual_Pool_1 {
pool Pool_1
persist Pool_1
}

profile persist Pool_1 {
cookie name Pool_1
}

virtual Virtual_Pool_2 {
pool Pool_2
persist Pool_2
}

profile persist Pool_2 {
cookie name Pool_2
}

While this configuration may appear more complex than the Specifying in the iRule a unique custom persistence cookie name for each pool technique, it does provide a more clear association between the target pools and their persistence profiles.
