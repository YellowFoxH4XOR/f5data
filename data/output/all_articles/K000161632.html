K000161632: BIG-IP Module Provisioning Changes Cause Temporary Interface and Trunk Disruption

Type
Support Solution
Published
2026-06-08
Updated
2026-06-08
Applies to
  • BIG-IP
  • BIG-IP APM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000161632

Description

Enabling or disabling (provisioning or deprovisioning) a BIG-IP module such as APM, ASM, or AVR causes the TMM (Traffic Management Microkernel) process to restart. During this restart, all network interfaces and trunks managed by TMM temporarily go down and then recover once TMM reinitializes. This behavior is expected and may trigger HA failover events and generate log messages such as:

  • HA proc_running tmm fails action is go offline and down links
  • Initiating TMM shutdown.
  • Trunk: <trunk_name> is DOWN
  • Link: <interface> is DOWN
  • sod[xxxx]: Leaving Standby for Offline for ha table offline_cond

Environment

  • BIG-IP (any version)
  • High Availability (HA) pair configuration
  • One or more BIG-IP modules (e.g., APM, ASM, AVR) being provisioned or deprovisioned
  • Trunks and/or aggregated interfaces (LACP) configured

Cause

When a BIG-IP module is enabled or disabled, the system must restart the TMM process to allocate or release the resources required by the module change. This TMM restart is the direct cause of the temporary interface and trunk disruption.

Answer/Recommended Actions

This is expected behavior. To minimize traffic impact when making module provisioning changes in an HA environment, follow these best practices:

  1. Verify HA health on both devices before making any changes:
  • tmsh show sys ha-status all-properties
  • tmsh show sys failover
  • tmsh show cm sync-status
  1. Perform the provisioning change on the Standby device first to avoid triggering a failover from the Active unit.
  2. Schedule the change during a maintenance window, as interfaces and trunks will be temporarily down during the TMM restart.
  3. Wait for the Standby device to complete its TMM restart and return to Standby state.
  4. Force a controlled failover to the updated device:
  • tmsh run sys failover standby
  1. Verify HA health again on both devices.
  2. Repeat the provisioning change on the now-Standby peer.
  3. Verify HA health a final time after both devices have completed the change.

Note for APM specifically: Both provisioning and deprovisioning APM require a system reboot. Ensure the peer device is healthy and Active before proceeding.

Additional Information

  • The sod log message HA proc_running tmm fails action is go offline and down links is normal TMOS logging during a TMM restart cycle and does not indicate a fault or crash on its own.
  • A controlled TMM shutdown (as opposed to a crash) will produce the log entry Initiating TMM shutdown. followed by orderly detachment of HSB/ePVA hardware. In this case, no core file will be generated, which is expected.
  • Interface and trunk disruption during module provisioning is driven entirely by the BIG-IP HA failover logic (sod, pfmand, lacpd) — it is not triggered by any module-specific policy or configuration (e.g., APM access policies do not cause interface state changes).
