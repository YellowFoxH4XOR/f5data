Answer/Recommended Actions

Misconfiguration vulnerabilities make your application susceptible to attacks that target any part of the application stack. For example, the following attack types may target misconfiguration vulnerabilities:

  • Brute force/credential stuffing
  • Code injection
  • Buffer overflow
  • Command injection
  • Cross-site scripting (XSS)
  • Forceful browsing

The application might be vulnerable if the application is:

  • Security headers and directives are either not sent by the server or are not configured with secure values.
  • Error handling exposes users to stack traces and other too detailed error messages.

 

To Configure Content Security Policy Header:

Proper set-up can be consulted in this KB article: How to configure Content Security Policy to HTTP Response

 

To configure Domains and LB Type: 

1.  From the Distributed Cloud console homepage, select WAAP service.
2. Go to Load Balancers.
3. Select your Load Balancer and go to Manage Configuration.
4. From the sidebar navigate to Domains and LB Type. 
5. Navigate to the top right corner and select Edit Configuration. 

You will be met with the following interface: 

Configuration Guide: 

Load Balancer Type: Use HTTPS/TLS for all communications, and disable outdated or insecure protocols (e.g., SSLv3).
HTTP with Automatic Certificate - We recommend using HTTP with a certificate either a manual or automatic one.
HTTP Redirect to HTTPS - HTTPS encrypts data between the client and server using TLS (Transport Layer Security). This ensures that sensitive information like login credentials, personal data, and payment details are protected from eavesdropping and interception.
HTTP Listening Port: 443 by default.
TLS Security Level: High.
HTTP Protocol Configuration: Unless we are using legacy systems we can set this to HTTP/2, otherwise we can use HTTP 1.1 & HTTP/2 with a Certificate. 

 

To configure the WAF (Web Application Firewall): 

1. From the Distributed Cloud console homepage, select WAAP service.
2. Select HTTP Load Balancer under Manage->Load Balancers.
3. Select your Load Balancer and go to Manage Configuration, and then click Edit Configuration.
4. Go to Web Application Firewall, enable it and select Add Item.

5. Select the constructed app firewall and scroll down to Security Configuration, where you may Enable WAF (Web Application Firewall). Press Save & Exit.

You will see the following interface for the configuration: 

Enforcement Mode: We should set this to blocking after 1 week of grace period of monitoring mode of the WAF this is for the ML model to observe regular baseline traffic, the change of enforcement must be done manually after the grace period. 

Security Policy: We recommend leaving this as default, it will perform automatic Attack Signature tuning. Threat campaign and Violations are by default enabled.

Note: If we require granular tuning we can change to custom and specify: High, Medium & Low attack signatures, but this can trigger some false positives due to low accuracy signatures and is generally not recommended. 

Signature-Based Bot protection: We recommend leaving this at default, malicious bots will be automatically blocked while suspicious bots will be reported for manual review.

Allowed Response Status Codes: We recommend leaving these at default (What are default response codes allowed on Web Application Firewall layer ?).

Mask Sensitive parameters in Logs: Sensitive parameters such as Passwords, and relating to credit-cards are automatically configured however if your application uses custom parameter for these fields this section must be set to custom and you must specify the parameters that pertain to sensitive personal information. 

Blocking Response Page: This can be left at default. 

 

6. To validate the WAF is working as expected we have launched a POC on a XXE XML External Entity Attack, once you have received the Support ID, go back to the XC console and navigate to Home >> Web App & API Protection >> select the namespace in which you configure your LB >> Overview >> Security, then scroll to the bottom of the console and select your LB.

 

7. Go to the Security Analytics Tab and see it generated a trigger of XML External Entity (XXE) injection on 4 different signatures and it was blocked. 

 

As you can see from the demonstration, the F5 Distributed Cloud WAF engine was able to successfully detect and restrict the attempt to exploit the XXE vulnerability.

 

Additional Information

Will the above configuration help us mitigate XXE Injections Attacks? In short, Yes - XML parsers are involved in a security misconfiguration known as "XML eXternal Entities" (XXE) vulnerability class. There are ways to refer to "entities" in the XML standard, including files and URLs. 

Parsers frequently completely resolve foreign entities by default, which means that XML documents may expose files and other private data to possible attackers. A4:2017-XML External Entities (XXE), which was previously a separate category of risk, is now a part of security misconfiguration.

 

XML External Entities - Proof-of-Concept:

Step 1: Identify and exploit the XXE vulnerability in the application, such as a file upload section that is not properly sanitized.

Note: Among various types of XXE attacks, we have chosen one to retrieve the contents of a file (/etc/passwd) containing information related to the users on the system like username, user id etc. from the server’s file system. 

Crafted.xml - XXE Payload we used for this test: 

<?xml version="1.0" encoding="ISO-8859-1"?> <!DOCTYPE foo [ <!ELEMENT foo ANY > <!ENTITY xxe SYSTEM "file:///etc/passwd" >]> <foo>&xxe;</foo>

Perhaps in this POC it did not parse back the XML result with the details yet the attempt was completely valid. Should this application have been vulnerable to retrieving the output it would have disclosed critical confidential information.

If we place this application behind XC WAF, it would generate the block as seen in step 7 of this article. 

 

 

What kind of attacks will a Content Security Policy help me mitigate? 

  1. Prevents Cross-Site Scripting (XSS): Unauthorized scripts are blocked by Content Security Policy (CSP) headers, preventing XSS attacks.

  2. Mitigates Clickjacking: Clickjacking is avoided when attackers are unable to embed your website in an iframe thanks to X-Frame-Options headers.

  3. Stops MIME Type Sniffing Attacks: X-Content-Type-Options headers prevent browsers from incorrectly interpreting file types, this will help avoid MIME type sniffing attacks.

  4. Blocks Man-in-the-Middle Attacks: Strict-Transport-Security (HSTS) headers enforce HTTPS, reducing the risk of man-in-the-middle attacks.

  5. Reflected XSS: X-XSS-Protection headers enhance browser security to stop reflected XSS attacks.

  6. Prevention against Mixed Content Vulnerabilities: CSP headers block the loading of insecure HTTP content on HTTPS sites, avoiding mixed content attacks.

  7. Protection against Sensitive Data Leaks: Referrer-Policy headers control the amount of referrer information shared, preventing sensitive data leaks.

  8. Helps reduce Remote Code Execution Risks: Proper CSP configuration can prevent the execution of unauthorized scripts, mitigating remote code execution attacks.

  9. Blocks Drive-By Download Attacks: CSP and X-Content-Type-Options headers can prevent the execution of malicious content, stopping drive-by downloads.

  10. Mitigates Cross-Site Request Forgery (CSRF): Certain headers, like CSP and HSTS, can indirectly help in reducing the risk of CSRF attacks by ensuring secure and restricted content delivery.

Is HTTP/1.1 Secure?

When used with HTTPS (TLS), HTTP/1.1 can be secure, as the data transmitted is encrypted and the integrity of the communication is protected. However, when used without HTTPS, HTTP/1.1 lacks encryption, it is open to manipulation and interception, rendering it insecure.

Compatibility considerations: 

  • Legacy: Some older web browsers, applications, and devices might only support HTTP/1.1 or earlier versions (like HTTP/1.0). Disabling HTTP/1.1 would block these clients from accessing your server, leading to compatibility issues.
  • Modern Clients: Most modern web browsers and applications support HTTP/2 and even HTTP/3. If your server supports these newer protocols, most users would not be affected if HTTP/1.1 is disabled.
