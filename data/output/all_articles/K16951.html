Topic

You can configure the BIG-IP system to proactively monitor the Secure Sockets Layer (SSL) hardware accelerator and take a specified action if a failure is detected. This applies to platforms with a Cavium Nitrox, Cave Creek, or Coleto Creek SSL hardware accelerator.

Description

BIG-IP 11.4.0 introduced the following two database variables (or keys), which allow the BIG-IP system to both monitor and respond when the SSL hardware accelerator fails:

  • crypto.ha

    Enables or disables monitoring the SSL hardware accelerator card. The available crypto.ha options include the following:

    • enable - Enables monitoring of the SSL hardware accelerator card (default value)
    • disable - Disables monitoring of the SSL hardware accelerator card
  • crypto.ha.action

    Configures what action the BIG-IP system takes once a failure is detected. The available crypto.ha.action options include the following:

    • go-offline-downlinks - The system goes offline and brings down all links (default value beginning in 13.x)(introduced in 13.0.0)
      For a multi-bladed chassis, this option does not trigger a failover to the standby chassis, it leaves the active chassis running with one fewer active blade. However, for appliances or chassis with only one blade, this action triggers a failover.
    • go-offline-downlinks-restart - The system goes offline, brings down all links, and restarts the service (introduced in 13.0.0)
    • failover - Fail over to a peer device (default beginning in 12.x)
    • none - No action (default value for 11.x)
    • reboot - Reboot the BIG-IP system
    • restart-all - Restart all BIG-IP system daemons

Depending on the crypto.ha.action option selected, your BIG-IP system may not recover automatically and will require manual intervention to recover from the crypto card failure. Depending on the failure encountered, you may be required to reboot the BIG-IP system or restart BIG-IP system daemons after a failure.

F5 has purposely selected default crypto.ha.action actions that require manual intervention rather than recovering automatically by rebooting the system or restarting system daemons.  Having a crypto.ha.action setting that does not reboot or restart system daemons provides the following benefits:

  • Allows you to run the nitrox_diag diagnostic utility on the failed system. The nitrox_diag diagnostic utility is designed to diagnose hardware errors associated with Cavium Nitrox SSL hardware accelerator cards. However, a reboot or restart of system daemons will most often prevent the diagnostic utility from determining the failure that triggered the action. For more information about the nitrox_diag utility, refer to K95944198: Overview of the nitrox_diag diagnostic utility.
  • For multi-bladed chassis systems, the default action in 13.x (go-offline-downlinks) allows the system to keep functioning on the original chassis, and only bring the affected blade offline. This provides the least impact or unplanned downtime.

To configure the system to automatically recover, and avoid manual intervention, you can configure the crypto.ha.action setting to reboot. F5 recommends this for BIG-IP systems that are not configured in a high availability (HA) configuration.

Modifying the database keys

To modify the database keys, perform the following procedures:

Modifying the crypto.ha database key

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP command line.
  2. To modify the crypto.ha database key, use the following command syntax:

    tmsh modify sys db crypto.ha value < enable | disable >

    For example, to disable crypto.ha, type the following command:

    tmsh modify sys db crypto.ha value disable

Modifying the crypto.ha.action database key

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP command line.
  2. To modify the crypto.ha.action database key, use the following command syntax:

    tmsh modify sys db crypto.ha.action value < failover | none | reboot | restart-all | go-offline-downlinks | go-offline-downlinks-restart >

    For example, to configure the BIG-IP system to fail over when the SSL accelerator fails, type the following command:

    tmsh modify sys db crypto.ha.action value failover

Recommendations

  • To configure the system to automatically recover, and avoid manual intervention, you can configure the crypto.ha.action setting to reboot. F5 recommends this for BIG-IP systems that are not configured in a high availability (HA) configuration. 
  • In BIG-IP 12.0.0 and later, you can configure the system to mirror SSL connections that are terminated by the BIG-IP system. In BIG-IP versions prior to 12.0.0, the BIG-IP system does not support mirroring SSL connections. If a failover event occurs, all current SSL connections will terminate and clients must re-establish new SSL connections on the newly active BIG-IP system.
  • You can configure custom SNMP traps based on unique error messages logged when the SSL hardware accelerator fails. When the SSL accelerator fails, the following error messages appear in the /var/log/ltm file:

    crit tmm[6789]: 01010025:2: Device error: cn0 device requires hard reset; trying soft reset
    crit tmm2[6789]: 01010025:2: Device error: cn2 PCI write master retry timeout

    For information about creating custom SNMP traps, refer to K3727: Configuring custom SNMP traps.

  • The BIG-IP system will take no fail-safe action when you set the crypto.ha database key to enabled and the crypto.ha.action to none. You do not need to disable the crytpo.ha database key when the crypto.ha.action database key is set to none.
