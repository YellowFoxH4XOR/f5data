Known Issue

If you delete and re-create a file on a BIG-IP system, that file may not synchronize to peer systems during a configsync to or from the Device Group.

This issue occurs when all of the following conditions are met:

  • The BIG-IP systems are configured as part of a Device Group.
  • You delete and re-create (or import) a file with the same destination filename as the file that was deleted.
  • A synchronization to or from the Device Group is run on any system in the Device Group.

The BIG-IP system acts as though a file that has the same filename as the previously-deleted file is the same file. The system does not synchronize files in this situation, and does not update the file on the peer system that has the same destination name.

Impact

  • The BIG-IP Device Group information is not fully synchronized, even though the BIG-IP system indicates that the members of the Device Group are synchronized. Systems in the Device Group that do not share identical synchronization information can behave unexpectedly in a failover event.
  • BIG-IP APM-specific configurations that use SecurID as a policy authentication method, and that experience a failover event, may prevent clients from accessing BIG-IP APM-configured resources.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • File synchronization for files that you have deleted and replaced, which have the same file names, is not successful across peer systems of a Sync-Failover Device Group.
  • In a failover event, services that depend on data that is contained in the unsynchronized files may not function as expected.
  • BIG-IP APM policies that are configured with SecurID authentication clients may be unable to access BIG-IP APM-configured resources after a failover, if SecurID files for the Active BIG-IP APM have been modified as detailed in this article.

Workaround

The workaround for this issue varies, depending on what problem you are experiencing.

To work around general file synchronization issues that are related to this known issue, refer to the following information:

  • Ensuring that synchronization for the Device Group includes file changes

If the system is licensed for BIG-IP APM, and you are attempting to recover SecurID functionality, refer to the following information:

  • Recovering SecurID functionality in the event of a failover between BIG-IP APM members of an unsynchronized Device Group

Ensuring that synchronization for the Device Group includes file changes

Impact of workaround: You may need to update objects that reference specific file names to reference the new file name.

When deleting and replacing files using the Configuration utility, remember to do the following:

  • Choose a different name when re-creating or re-importing a previously-deleted file.
  • When re-importing the file object, choose the Overwrite Existing option instead of Create New.

Recovering SecurID functionality in the event of a failover between BIG-IP APM members of an unsynchronized Device Group

Impact of workaround: You may need to update objects that reference specific file names to reference the new file name.

If the following events occurred with your BIG-IP APM configuration, the following workaround would help you recover access for clients authenticated with SecurID.

  • You have modified a SecurID file on the active BIG-IP APM member, as described in this article.
  • A failover occurred between BIG-IP APM Device Group members, causing the alternate member to become the active BIG-IP APM system.
  • After the failover event, clients authenticated with SecurID are unable to access configured resources.

You can update the newly-active BIG-IP APM system with the previously-known SecurID information by manually copying the file from the previously-active BIG-IP APM system to the now-active BIG-IP APM system. To do so, complete the following procedure:

  1. Log in to the command line of the Standby BIG-IP APM system.
  2. Change directories by typing the following command:

    cd /config/filestore/files_d/Common_d/Securid_server_config_file_d

  3. Check for the file ending in ::Securid_1.

    For example:

    ls -l *::SecurID_1

    -rw-r--r-- 1 root root 512 Jun 21 15:46 :Common:rsaAAA::SecurID_1

  4. To securely copy the Securid_1 file to the active BIG-IP APM system, type the following command:

    scp ./\:Common:rsaAAA\:\:Securid_1 peer_management-ip-address-active-APM:/config/filestore/files_d/Common_d/Securid_server_config_file_d/

Important: You must use the backslash in front of each of the colons in the filename to secure copy the file to the peer system.
