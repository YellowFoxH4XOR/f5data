Known Issue

This is the result of a known issue. After rebooting or restarting services on the secondary VIPRION blade, the blade may receive incorrect profile settings from the mcpd process running on the primary blade. As a result, core BIG-IP services, such as the mcpd and tmm processes, continually restart as they attempt to load the configuration.

When this issue occurs, the secondary blade logs error messages to the /var/log/ltm file that appear similar to the following example:

err mcpd[13662]: 01070734:3: Configuration error: Configuration from primary failed validation: 01070281:3: Invalid "http lws width" value for profile http-wan-optimized-compression. Value must be greater than 0."

Note: The actual profile names in the error message will vary and depend on the system's configuration.

In addition, the console generates error messages that appear similar to the following example:

emerg logger: Re-starting mcpd
emerg logger: Re-starting stpd
emerg logger: Re-starting tmm
emerg logger: Re-starting tmm1
emerg logger: Re-starting tmm2
emerg logger: Re-starting tmm3
emerg logger: Re-starting cssd
emerg logger: Re-starting bigd
emerg logger: Re-starting named

Note: The primary VIPRION blade is not affected by this issue and continues to operate as expected.

F5 Product Development tracked this issue as ID 338677 and it was fixed in BIG-IP version 10.2.1. For information about upgrading, refer to the BIG-IP LTM, ASM, GTM, PSM, Link Controller, WebAccelerator, APM, WOM, or Edge Gateway release notes.

Workaround

You can work around this issue by correctly loading the profile(s) and starting the services on the secondary blade(s). To do so, perform the following procedure:

Important: This procedure will disrupt traffic if performed on the active BIG-IP unit. F5 recommends that you perform these steps during a maintenance window.

  1. Log in to the command line by connecting to the Management IP address.
  2. Determine the blade number(s) for the affected secondary blade(s) by using the following command syntax:

    bigpipe cluster show

    For example, the following command output indicates that the primary blade is slot 1, and the secondary is slot 2:

    CLUSTER default Primary slot: 1 172.24.21.35/24
    +-> CLUSTER MBR default/1 enabled
    | | 172.24.21.34 not priming licensed
    | | HA: active green (reason: Run)
    +-> CLUSTER MBR default/2 enabled
    | | 172.24.21.33 not priming licensed
    | | HA: active green (reason: Run)
    +-> CLUSTER MBR default/3 disabled
    | | default inet6 not priming not licensed
    | | HA: unknown blue (reason: Slot state unknown, manually disabled)
    +-> CLUSTER MBR default/4 disabled
    | default inet6 not priming not licensed
    | HA: unknown blue (reason: Slot state unknown, manually disabled)

  3. Disable the primary blade by using the following command syntax:

    Note: If you are connected to the VIPRION using the Management IP address, the following command will terminate the ssh connection.

    bigpipe cluster default member <primary_blade> disable

    For example, the following command disables blade number 1:

    bigpipe cluster default member 1 disable

    The secondary blade now makes itself primary and loads the correct configuration.
  4. Log in to the command line of the newly-active blade by connecting to the Management IP address.
  5. Re-enable the formerly-active blade by using the following command syntax:

    bigpipe cluster default member <formerly_active> enable

    For example, if blade 1 was the formerly-active blade, enter the following command:

    bigpipe cluster default member 1 enable

  6. Repeat these steps on any additional blades, as required.
