Topic

This article applies to BIG-IP ASM 14.1.0 and later. For information about other versions, refer to the following articles:

  • K00736342: Configuring bot protection
  • K15405450: Overview of web scraping detection

You can quickly and easily protect your application against bots using features and settings in the Bot Defense profile.

Description

Starting in BIG-IP ASM 14.1.0, a new Bot Defense profile is available for configuration. The Bot Defense profile replaces and includes the original functionality of the DoS profile bot signatures and proactive bot defense, as well as Web Scraping. Device ID is now located in the Browser Verification sections of the Bot Defense profile. In addition to merging these configuration areas to a single Bot Defense profile, the new profile contains additional mitigation actions, unified logging, and full transparent mode, which allows for bot detection reporting without blocking.

Bot defense is implemented by identifying clients by type of clients (client classification), through identification of browser types (classes), based on the browser (all known browsers), or mobile application (with or without the F5 anti-bot SDK). Trusted bot traffic is passed without anomaly detection whereas untrusted bot (suspicious browser, malicious bot, and unknown bot) activity is monitored for activity that indicate threat patterns (benign bot signatures). When a threat pattern is identified from a client that is identified as a bot, the configured mitigations (class, category, signature, and anomaly level) are applied to the bot request, and this information is logged along with a recommended mitigation (when configured in enforcement mode transparent) that you can use for reporting. When multiple mitigation actions are identified based on bot activity, the most strict mitigation action configured is utilized.

The following features are combined into one profile called the Bot Defense profile:

  • Proactive Bot Defense
  • Bot Signature features in the DoS profile
  • Web Scraping in the BIG-IP ASM security policy

Learn more about Proactive Bot Defense in the following sections:

  • How it works
  • Configuring Proactive Bot Defense
  • Recommendations

How it works

The Bot Defense profile does the following to process client traffic:

  • Classifies and verifies
  • Performs anomaly detection
  • Applies the mitigation actions that you configured
  • Logs and reports with a Bot Defense logging profile. For more information refer to K11412315: Configuring Bot Defense logging.

When a client triggers more than one bot signature or anomaly, the system performs the most strict mitigation action that you configured.

During the classification, verification, and anomaly detection stages, the Bot Defense profile classifies client traffic as described in the following table.

Bot class Description

Browser: A client that successfully passes a series of browser verification and validation tests

Mobile App:

  • An Anti-Bot Mobile SDK client that successfully passes the Anti-Bot Mobile SDK verification
  • Mobile app clients that the system identifies through other verification methods because they do not use the Anti-Bot Mobile App SDK

Trusted Bot: A client that exhibits known search engine behaviors/signatures

Untrusted Bot: A client that exhibits non-malicious tools/bots behaviors/signatures:

  • Tools—Site crawlers, monitors, spiders, and web downloaders
  • Bots—Search bots and social media agents

Suspicious Browser: A client that fails specific browser verification tests

Malicious Bot: A client that the system detects using a combination of bot signatures, browser verification tests, and anomaly detection heuristics, including DoS tools, known exploit tools, and vulnerability scanners

Unknown: A client that the system is unable to identify using various means, such as non-browser clients

Configuring Proactive Bot Defense

To configure the Bot Defense profile, do the following:

  1. Go to Security > Bot Defense > Bot Defense Profiles.
  2. Select the name of the profile you want.
  3. Under Bot Profile Configuration, select each of the following to configure the profile settings:
    • General Settings
    • Mitigation Settings
    • Microservice Protection
    • Browser Verification
    • Mobile Applications
    • Signature Enforcement
    • Whitelist

General Settings

SettingDescription
Profile NameName of the profile. This setting is required.
DescriptionDescription of the profile.
Enforcement ModeSelect one of the following modes, depending on the readiness of your application environment and requirements:
  • Transparent—The system logs traffic mitigation and verification actions, according to your logging profile settings, but does not provide the following:
    • JavaScript-based verification.
    • Device ID collection.
    • CAPTCHA challenge.
  • Blocking—The system performs traffic mitigation and verification, and logs them according to your logging profile settings.
Profile Template

The template you select determines the default values for mitigation and verification settings. However, you can customize these settings to meet your application security requirements.

After the system saves the profile, you can't change this setting.

The following list contains descriptions of the available templates:

  • Relaxed—Performs basic verification of browsers and blocks malicious bots based on bot signatures.
  • Balanced—This is the default selection. Performs advanced verification of browsers, including:
    • CAPTCHA challenges for suspicious browsers.
    • Anomaly detection algorithms and bot signatures to detect and block malicious bots.
    • Limiting the total request rate for unknown bots.
  • Strict—This is the strictest policy; it has settings that:
    • Only allow browsers access if they pass proactive verification.
    • Block all bots except trusted ones.
Signature Staging upon Update1When the system receives a signature update, either via a version update or custom signatures, it places newly created or modified signatures in staging. The system does not block requests, but it logs them.

The default selection is Disabled. When the setting is disabled, the system enforces the mitigation action defined for the signature in Mitigation Settings.

Enforcement Readiness Period1Defines the period of time since the last change that the Bot Defense profile remains in Staging mode before the system suggests enforcing the profile. The default value is 7 days.
Redirect to Pool(15.x and later)The pool to redirect suspected bot traffic to.
First CAPTCHA Response1, 2When the system suspects that the end client is a bot, this setting determines whether the system sends the default response page or a custom response page to the first CAPTCHA challenge. You customize the response page by selecting Custom and editing the HTML code.
Failure CAPTCHA Response1, 2Determines whether the system sends the default response page or a custom response page to a failed CAPTCHA challenge. You can customize the response page by selecting Custom and editing the HTML code.
Blocking Page Response1, 2You can customize the blocking page by selecting Custom and editing the HTML code.
Honeypot Response Page (15.x and later)The system sends the Honeypot Response Page when a client fails the login.
  • Default specifies that the system displays the system’s default response after the user fails a login.
  • Custom specifies that you want to write a custom response for the system to display after a user fails a login.

1For BIG-IP 14.x, to view the advanced settings, select Advanced.

2For BIG-IP 15.x and later, the settings are under the Response and Blocking Pages.

Bot Mitigation settings (Mitigation settings in BIG-IP 14.x)

Under Mitigation Settings, you can select the mitigation action you want the system to perform for each of the following bots:

  • Trusted bot
  • Untrusted bot
  • Suspicious browser
  • Malicious bot
  • Unknown

The template you selected for Profile Template determines the default value for each mitigation action. F5 recommends you use the default values unless you have specific application requirements. The mitigation actions are defined in the following table.

Mitigation actionBotDescription
None
  • Trusted
  • Untrusted
  • Suspicious browser
  • Malicious 
The system disables and does not check bot signatures.
  • Suspicious browser
  • Malicious 
The system disables and does not check anomaly detection algorithms.
UnknownThe system does nothing.
AlarmAllThe system detects bot threats and logs them according to the logging profile settings.
CAPTCHAAllThe system sends a CAPTCHA challenge to the client.
BlockAllThe system stops the client's access and sends a blocking page to the client.
TCP ResetAllThe system terminates the client's connection.
Rate LimitUnknownThis action is only applicable to the Unknown bot type. The system processes the configured number of transactions per second and terminates any Unknown bot type connections when it reaches the threshold. The default value is 30 transactions per second.
Honeypot PageAllThe system sends the Honeypot Response Page to the client.
Redirect to PoolAllThe system forwards the traffic to the selected pool.

Under Strict Mitigation Enforcement Cases, you can provide additional mitigation and verification modes under the circumstances listed in the following table.

ModeSettings
DoS Attack Mitigation ModeWhen enabled, the system uses the following mitigation and verification settings during a DoS attack:
  • Browser Verification: Verify Before Access
  • Trusted Bots: Alarm
  • Untrusted Bots: Block
  • Suspicious Browsers: Block
  • Malicious Bots: Block
  • Unknown: Block

Enabling the DoS Attack Mitigation Mode requires that you assign a DoS profile to the virtual server.

API Access for Browsers and Mobile ApplicationsIf enabled, the system uses the following mitigation and verification settings during a client's access to API endpoints/URLs:
  • Browser Verification: Verify Before Access
  • Trusted Bots: Block
  • Untrusted Bots: Block
  • Suspiciuos Browsers: Block
  • Malicious Bots: Block
  • Unknown: Block
A URL is considered an API URL in the following cases:
  • Content-Type request header matches *json*, *xml*
  • Content-Type response header with values *json*, *xml*
  • Request has X-Security-Request header and the Single Page Application option is enabled.
  • Request is already AJAX-qualified.

Under Mitigation Settings Exceptions, you can:

  • Configure exceptions for a specific bot or bot type.
  • Define the mitigation action for the system to perform on that specific bot or bot type.

For example, if you configure your Bot Defense profile to use the Strict template, and you want to allow the Curl command to be able to access your application, you can do the following:

  1. Select Add Exceptions.
  2. Select Untrusted Bot.
  3. Select HTTP Library.
  4. Select curl.
  5. Select Add.

Microservice Protection

Use the following settings to define the mitigation and verification actions you want the system to take on a microservice, based on specific hostname and URL (order of URLs is important). You can provide the protection types listed in the following table based on OWASP Automated Threats.

Threat protectionDescription
Login ProtectionThe system detects and protects attempts to automate user account login using attack methodologies such as credential cracking (OAT-007) and/or stuffing (OAT-008). The system reports this threat as Login Transactions Anomaly.
Signup ProtectionThe system detects and protects attempts to create multiple accounts for subsequent misuse such as generating spam and spreading malware. The system reports this threat as Signup Transactions Anomaly.
Search ProtectionThe system detects and protects attempts to collect application content, such as Web Scraping (OAT-011), or create computationally expensive search queries resulting in DoS (OAT-015). The system reports this threat as Search Transactions Anomaly.
Shopping Cart ProtectionThe system detects and protects attempts to automate the product addition to cart operation. These attempts are typically used to carry out the following attacks:
  • Card Cracking (OAT-010)—Identify missing start/expiry dates and security codes for stolen payment card data by trying different values.
  • Cashing Out (OAT-012)—Buy goods or obtain cash utilizing validated stolen payment card or other user account data.
  • Denial of Inventory (OAT-021)—Deplete goods or services stock without ever completing the purchase or committing to the transaction.

The system reports this threat as Shopping Cart Transactions Anomaly.

Checkout ProtectionThe system detects and protects attempts to automate checkout as part of a product purchase operation. These attempts are typically used to carry out the following attacks:
  • Card Cracking (OAT-010)—Identify missing start/expiry dates and security codes for stolen payment card data by trying different values.
  • Cashing Out (OAT-012)—Buy goods or obtain cash utilizing validated stolen payment card or other user account data.
  • Denial of Inventory (OAT-021)—Deplete goods or services stock without ever completing the purchase or committing to the transaction.

The system reports this threat as Checkout Transactions Anomaly.

Automated Form SubmissionThe system detects and protects attempts to automate form submission in an application. These attempts are typically used to carry out the following automated attacks:
  • Expediting (OAT-006)—Perform actions to hasten progress of usually slow, tedious, or time-consuming actions.
  • Scalping (OAT-005)—Obtain limited-availability and/or preferred goods/services by unfair methods, such as ticket taking bots.
  • Skewing (OAT-016)—Repeated link clicks, page requests or form submissions intended to alter some metric.
  • Sniping (OAT-013)—Last minute bid or offer for goods or services.

The system reports this threat as Automated Form Submission.

Intellectual Property HarvestingThe system detects and protects attempts to collect data that constitutes Intellectual Property. The web scraping may occur in real time or periodically. The system reports this threat as Intellectual Property Harvesting anomaly.
Web ScrapingThe system detects and protects attempts to collect application content and/or other data for use elsewhere. The web scraping may occur in real time or periodically. Some web scraping may be used for cryptanalysis, reverse engineering, or session analysis. The system reports this threat as Web Scraping anomaly.
Custom Microservice ProtectionThe system detects and protects attempts to automate access to a microservice. The system reports this threat as Automated Attack on Microservice.

Browsers (Browser Verification in BIG-IP 14.x)

Use the following settings to customize browser challenge settings to fit your application environment. The default values for each setting are determined by your selection in Profile Template (under General Settings). F5 recommends you use the default values set by the profile template you selected unless you have specific application requirements.

SettingDescription
Browser Access(BIG-IP 15.x and later)Many server applications are mobile application specific and not for browser access. Therefore, browsers that do access these mobile applications are typically driven by attackers and should be blocked. The default value is Allow.
Browser VerificationSpecifies what and when the system sends challenges.
  • None—The system does not perform JavaScript and header-based verifications. However, some anomaly detection (such as Session Opening) still occurs.
  • Challenge-Free Verification—The default value when Profile Template is set to Relaxed. The system performs header-based verification but does not perform JavaScript verification.
  • Verify Before Access—The default value when Profile Template is set to Strict. The system sends a white page with JavaScript to challenge the client. If the client fails the challenge, the system performs the configured mitigation action and reports the anomaly. If the client passes the challenge, the system forwards the request to the server.
  • Verify After Access (Blocking)—The default value when Profile Template is set to Balanced. The system injects a JavaScript challenge in the server response prior to sending the response to the client. If the client fails the challenge, the system  performs the configured mitigation action and reports the anomaly. If the client passes the challenge, the system forwards the request to the server.
  • Verify After Access (Detection Only)—The system injects JavaScript challenge in the server response prior to sending the response to the client. If the client fails the challenge, the system only reports the anomaly but does not perform any mitigation action. If the client passes the challenge, the system forwards the request to the server.
Device ID ModeA unique identifier that BIG-IP ASM creates by sending JavaScript to get information about the client device. The default value for this setting is determined by your selection in Profile Template (under General Settings). F5 recommends you use the default values set by the Profile Template you selected unless you have specific application requirements.
  • None—The default value when Profile Template is set to Relaxed. The system does not send JavaScript to collect the device ID.
  • Generate After Access—The default value when Profile Template is set to Balanced. The system injects the JavaScript in the server response before forwarding to the client. This is less intrusive and has less of a latency impact.
  • Generate Before Access—The default value when Profile Template is set to Strict. The system sends the JavaScript challenge to the client before forwarding the client request to the server. This guarantees that every request that reaches the server has a device ID. This has more of a latency impact compared to the previous option. The system blocks bots that attempt to present themselves as browsers but are unable to execute the JavaScript challenge.
Verification and Device-ID Challenges in Transparent ModeThe default is Disabled. When enabled, the system sends JavaScript challenges and verification tests to the client, even though Enforcement Mode (under General Settings) is set to Transparent.
Single Page ApplicationWhen your web application loads new content without triggering a full page-reload, it is considered a Single Page Application (SPA). When enabled, the system injects JavaScript challenges to every response, thus sending various challenges (such as browser verification, Device ID, and CAPTCHA) without requiring a page reload. The default is Disabled.
Cross Domain RequestsConfigures how the system should respond when it receives a request for non-HTML resources (such as images, CSS, XML, JavaScript, and Flash) without a valid cookie and has a referer header with a different domain.
  • Allow all requests—Allows requests for non-HTML resources after they pass the system's redirect-cookie challenge. This is the default value.
  • Allow configured domains; validate in bulk—Allows requests for non-HTML resources if the domain in the referer header matches a domain configured in the Related Site Domains or Related External Domains setting. The system fetches the cookies from the domains configured in the Related Site Domains setting in advance. F5 recommends this option if your application has many cross-domain resources.
  • Allow configured domains; validate upon request—Allows requests for non-HTML resources if the domain in the referer header matches a domain configured in the Related Site Domains or Related External Domains setting. The system fetches the cookies from the domains configured in the Related Site Domains setting in real time when they are requested. F5 recommends this option if your application does not have many cross-domain resources.

Mobile Applications

Use these settings to configure your system for mobile app clients. For systems that are licensed with the Anti-Bot Mobile SDK, you can enable the Applications with Anti-Bot Mobile SDK section and configure the necessary settings for your mobile app clients that use the Anti-Bot Mobile SDK.

If the mobile app client does not use the Anti-Bot Mobile SDK, you can define a custom bot signature for the system to identify the mobile app client. For information about creating a custom bot signature, refer to the Writing Custom Bot Signatures in BIG-IP Application Security Manager: Attack and Bot Signatures.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Signature Enforcement

This page displays the list of bot signatures. You can select one or more signatures from the list and change their enforcement settings to either Enforce or Stage. You put bot signatures in staging to evaluate the signature and log the requests. Only stage a bot signature when you have a concern on potential false positives. Bot signature staging is disabled by default.

Whitelist

On this page, you can define a specific IP address, geolocation, and/or URL for which you want to enable or disable Mitigation Action, Browser Verification, and Device ID Challenges. The system applies allowlisted items in order.

Note: F5 is working to eliminate exclusionary language in products and documentation. For more information, refer to K34150231: Exclusionary language in F5 products and documentation.

Recommendations

None. However, you must configure a DNS server and a DNS resolver before configuring a Bot Defense profile, as the profile requires these two items to work.

You configure a DNS server at the following location:

  • System > Configuration > Device > DNS

You configure a DNS resolver at the following location:

  • Network > DNS Resolver > DNS Resolver List
