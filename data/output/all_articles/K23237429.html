Description

Starting in version 14.1.0 the following log line may appear:

01220001:3: TCL error: /Common/<iRule_name> <HTTP_REQUEST> - ERR_NOT_SUPPORTED (line 1)     invoked from within "HTTP::host"
  • Where <iRule_name> is the name of the iRule that generated the log message.

This will happen if one of the following iRule commands:

  • HTTP::respond
  • HTTP::redirect
  • HTTP::retry

Is used. Or if a policy or http profile is used to redirect or respond to HTTP requests.  Then, in either another iRule on the same connection or AFTER that command is called, you attempt to use one of the following iRule commands:

  • HTTP::collect
  • HTTP::close
  • HTTP::cookie names
  • HTTP::header names
  • HTTP::host
  • HTTP::is_keepalive
  • HTTP::is_redirect
  • HTTP::method
  • HTTP::path
  • HTTP::query
  • HTTP::request
  • HTTP::uri
  • HTTP::version

For example the following iRule will fail:

when HTTP_REQUEST {
  if { [HTTP::uri] equals "/"} {
        HTTP::redirect "https://10.10.10.1/"
   }
  log local0. "Host [HTTP::host]"
}

In the above example, the iRule command HTTP::host will fail and the system logs this message because HTTP::host is being used after the iRule command HTTP::redirect.

Environment

  • BIG-IP 14.1.x and later
  • Upgrading from previous version
  • iRule with any of the following commands:
    • HTTP::respond
    • HTTP::redirect
    • HTTP::retry
  • iApp using any of the previous iRule commands

Cause

  • Change in behavior due to enhancement ID 737252.
    • HTTP iRule commands that inspect HTTP state after the commands HTTP::respond, HTTP::redirect and HTTP::retry will now return errors instead of returning corrupt data. This affects the commands in their respective valid iRule events; for example this affects HTTP::retry in both HTTP_RESPONSE and HTTP_RESPONSE_DATA events since it is valid in both events.
  • This is a new log message added to inform the administrator that the iRule is trying to utilize HTTP context commands after already sending an HTTP response or redirect.
    Note: Previously, this condition could have failed silently, without logging any related errors or warnings.

Recommended Actions

To avoid this condition, you must prevent further iRule processing after every HTTP::respond, HTTP::redirect and HTTP::retry command. This can be accomplished by using the return or event disable commands.
In addition, you can check to see if the LTM has already issued an HTTP::respond, HTTP::redirect or HTTP::retry by using the HTTP::has_responded command.

Important: In the case of multiple iRules, the event disable or return will not be sufficient since it ends execution for a single iRule in a Virtual Server; additional/subsequent iRules in the same Virtual Server may continue to be processed. If you are trying to end all iRules execution then use either event disable all, or check for HTTP::has_responded. Please review iRule event reference for more information on which one to use.

For example, the following iRule will trigger the log:

ltm rule otters {
  when HTTP_REQUEST {
    HTTP::respond 200 content "splash\n";  # HTTP::respond issued.
    log local0.debug "[HTTP::uri]";        # This data is no longer available. This will generate a TCL error.
  }
}

One way to fix this iRule is to change the order. For example, the following iRule will not trigger the log:

ltm rule otters {
  when HTTP_REQUEST {
    log local0.debug "[HTTP::uri]";        # The uri data is still available.
    HTTP::respond 200 content "splash\n";  # HTTP::respond issued.
  }
}

The other workarounds:

  • Modify iRules to use HTTP::has_responded, which checks if the HTTP context is still available.

  • Add return after every HTTP::respond, HTTP::redirect, and HTTP::retry command, as appropriate. This may require other changes to the iRules. For instance, in the original iRule above, putting a "return" immediately after the HTTP::respond means that the "log" command will not be executed. Instead, the code needs to be reordered:
    ltm rule otters {
        when HTTP_REQUEST {
            if { [HTTP::has_responded] } { return };    # Exit if there was a previous HTTP::(respond|redirect|retry)
            log local0.debug "[HTTP::uri]";             # Log the URI
            HTTP::respond 200 content "splash\n";       # Perform the respond
            return;                                     # Explicitly exit further iRule processing.
        }
    }

Additional Information

  • Each time this message is logged, a TCP RST is sent to the client and the connection is forcibly closed.
    Note: In BIG-IP APM versions prior to 14.1.0, the BIG-IP APM iRule would encounter a TCL error and would not automatically trigger a TCP reset.
  • The message was added in version 14.1 and is considered the desired behavior to notify the user about a potential problem.
  • If there are multiple iRules assigned to a virtual server, and a preceding iRule for this connection has already sent a response, then this error will also occur if subsequent iRules either try to amend the response, or send another response. Changing the order of the iRules can also prevent this log.
  • In versions prior to 14.1 you could find similar error log such as the following:

    tmm[16525]: 01220001:3: TCL error: /Common/IRULE_NAME <HTTP_REQUEST> - Can't call after responding - Operation not supported (line 1) invoked from within "HTTP::collect $content_length".

    This error represents the same issue described in the article, where we are trying to use HTTP::collect while another iRule has already closed the HTTP context with HTTP::respond. The solution in versions earlier than 14.1 is to use the event disable all command if multiple iRules are configured, or the event disable command if single iRule is in play. Just be aware that if you disable all events and a subsequent request is made on that same tcp connection it may be passed through without any irule processing and have unintended consequences such as allowing traffic where the irule should have rejected it.

The following iRule commands are valid after HTTP::(redirect|respond|retry):
  • HTTP::has_responded
  • HTTP::fallback
  • HTTP::hsts
  • HTTP::passthrough_reason
  • HTTP::password
  • HTTP::username
  • HTTP::request_num
The following iRule commands are invalid after HTTP::(redirect|respond|retry):
  • HTTP::collect
  • HTTP::close
  • HTTP::cookie names
  • HTTP::header names
  • HTTP::host
  • HTTP::is_keepalive
  • HTTP::is_redirect
  • HTTP::method
  • HTTP::path
  • HTTP::query
  • HTTP::request
  • HTTP::uri
  • HTTP::version
