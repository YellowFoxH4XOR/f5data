Known Issue

The Secure Socket Layer (SSL) session handshake may fail when the server uses a self-signed certificate for authentication.

This issue occurs when all of the following conditions are met:

  • The server SSL profile's Server Certificate option is set to require.
  • The pool members are Netty based SSL servers.

Impact

The SSL handshake fails during SSL verification and stops responding until the session timeout.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The BIG-IP system logs error messages to the /var/log/ltm file that may appear similar to the following example:

    info tmm[15051]: 01260013:6: SSL Handshake failed for TCP 10.10.6.100:8443 -> 10.10.1.4:40529
    err tmm[15051]: 01230140:3: RST sent from 10.10.1.4:40529 to 10.10.6.100:8443, [0x1f9b411:1440] SSL handshake timeout exceeded
  • You may observe error messages on your Netty server that appear similar to the following example:

    INFO com.f5.ecm.transportMgr.PublicConnection.PublicConnectionInitializer - Public SSL: using /root/netty/netty.crt and /root/netty/netty.key
    ERROR com.f5.ecm.transportMgr.PublicConnection.PublicHandler - General Exception: Connection reset by peer

Workaround

To work around this issue, you can configure the back-end Netty based SSL servers to use a Certificate Authority (CA) signed certificate.

Impact of workaround: Performing the suggested workaround should not have a negative impact on your system.
