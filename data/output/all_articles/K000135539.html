Description

This article provides information with example configuration about how to route traffic between namespaces through external gateway; i.e. if routing traffic via external gateway between namespaces is needed then this article provides an example. 

Environment

AspenMesh 1.11.x , 1.14.x

Cause

None

Recommended Actions

Example, using custom domain name without ".svc.cluster.local", you would need to make sure that name can be resolved to the correct service within the cluster. This typically involves updating your cluster's DNS settings. However, keep in mind that any custom DNS settings would need to be maintained separately from the rest of the Kubernetes configuration, which might complicate things.

Here's an example of how you might configure this scenario using Istio resources. Note that it is assumed the services are HTTP-based. If not, you would need to adjust these configurations accordingly. 

First, you would create a Gateway and VirtualService for the external access: 

apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: external-gateway
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "example.com"
---
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: appx-route
spec:
  hosts:
  - "example.com"
  gateways:
  - external-gateway
  http:
  - match:
    - uri:
        prefix: /path1
    route:
    - destination:
        host: appx1.default.svc.cluster.local
  - match:
    - uri:
        prefix: /path2
    route:
    - destination:
        host: appx2.default.svc.cluster.local

This configuration would route http://example.com/path1 to appx1 and http://example.com/path2 to appx2.

To route internal traffic in the same way, you would create another VirtualService without a gateway. This VirtualService applies to traffic within the mesh:

apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: appx-internal-route
spec:
  hosts:
  - "appx.default.svc.cluster.local"
  http:
  - match:
    - uri:
        prefix: /path1
    route:
    - destination:
        host: appx1.default.svc.cluster.local
  - match:
    - uri:
        prefix: /path2
    route:
    - destination:
        host: appx2.default.svc.cluster.local

This configuration would route http://appx.default.svc.cluster.local/path1 to appx1 and http://appx.default.svc.cluster.local/path2 to appx2. Any pod within the cluster could access appx this way, and it would be routed based on the path in the same way as external traffic. 

Note this is just a reference configuration require testing. You would need to adjust it to fit your environment and requirements. Specifically, you might need to change the names of the hosts, services, and paths. You may also need to adjust the namespace if your services are not in the default namespace. Lastly, if your services use a protocol other than HTTP, you would need to adjust the VirtualService configurations accordingly.
 

Additional Information

Let's start first by discussing how hostname resolved within the Kubernetes cluster. The hostname should be resolvable within the Kubernetes cluster. By convention, it usually follows the <service-name>.<namespace-name>.svc.cluster.local pattern. However, the domain name itself doesn't strictly have to follow this pattern. You could use a custom domain name such as "app1.int-endpoint.svc.cluster.local" as long as it can be resolved to the correct service within the cluster.  

There is no strict constraint on internal hostnames apart from being DNS-resolvable within the cluster. You can define a common name for internal hosts across namespaces as long as the common name can be correctly resolved to the appropriate service in each namespace.

Keep in mind, however, that defining the same hostname for services in different namespaces might be confusing, and could potentially lead to naming conflicts or unexpected routing behavior. It would be more conventional to include the namespace in the hostname to keep things clear and avoid conflicts.
