K000160126: SSLO Traffic hits incorrect Virtual Server when sys db connection.vlankeyed is disabled

Type
Support Solution
Published
2026-02-24
Updated
2026-02-24
Applies to
  • F5 App Protect
  • BIG-IP SSL Orchestrator: 17.5.0
Source
https://my.f5.com/manage/s/article/K000160126

Description

In a BIG-IP SSL Orchestrator (SSLO) deployment with an inline Layer 3 service, return traffic from the Layer 3 firewall may hit an incorrect virtual server on the SSLO device when the system database variable connection.vlankeyed is set to "disable". This results in failed SSLO traffic flows as packets are not processed by the expected service virtual server.

Symptoms include:

  • SYN packet retransmissions observed in packet captures
  • Return traffic from Layer 3 services matching the wrong virtual server
  • Traffic failing to complete the service chain properly
  • Packet captures showing "tcp port numbers reused" and "tcp retransmission" messages in analysis tools

Error/Log Messages:

  • F5 Ethernet Trailer in packet captures shows traffic hitting an unexpected virtual server
  • Connection failures through the SSLO topology

Environment

  • Product: BIG-IP SSL Orchestrator (SSLO)
  • Version: 17.5.0 (affects all versions)
  • Platform: F5-BIG-R4800, C131, and other platforms
  • Configuration:
    • SSLO topology with inline Layer 3 service
    • Multiple VLANs: client-side VLANs and service-side VLANs (to-service and from-service)
    • BGP routing or other configurations requiring sys db connection.vlankeyed set to "disable"
    • Service virtual server source port setting configured as "preserve" (default)
  • Conditions:
    • sys db connection.vlankeyed is set to "disable" (non-default setting)
    • Same TCP 4-tuple (source IP, source port, destination IP, destination port) appears on multiple VLANs

Cause

When sys db connection.vlankeyed is set to "disable", BIG-IP matches connections based solely on the TCP 4-tuple (source IP, source port, destination IP, destination port), ignoring VLAN context. By default, this setting is "enable", which includes VLAN ID as part of the connection key.

In SSLO deployments with inline Layer 3 services, the same TCP connection traverses multiple VLANs:

  1. Client-side VLAN → SSLO
  2. SSLO → to-service VLAN → Layer 3 firewall
  3. Layer 3 firewall → from-service VLAN → SSLO
  4. SSLO → Client-side VLAN

When return traffic from the Layer 3 service arrives on the from-service VLAN with the same 4-tuple, BIG-IP incorrectly associates it with the original client-side connection instead of the service virtual server, causing the traffic to hit the wrong virtual server and fail.

Answer/Recommended Actions

Primary Solution:

Modify the SSLO service virtual server configuration to change the source port behavior from "preserve" to "change". This ensures unique 4-tuples across VLANs and prevents connection collisions.

Configuration Steps:

  1. Navigate to Local Traffic > Virtual Servers
  2. Locate the SSLO service virtual servers (typically named ssloS_<service-name>-t-<number> and ssloS_<service-name>-u-<number>)
  3. For each service virtual server:
    • Edit the virtual server configuration
    • Change the Source Port setting from "Preserve" to "Change"
    • Save the configuration
  1. Test traffic flow through the SSLO topology

Alternative Solution (if applicable):

If your environment does not require connection.vlankeyed to be disabled:

  1. Enable VLAN-keyed connections:
  2. tmsh modify sys db connection.vlankeyed value enable
  3. tmsh save sys config
  4. This restores the default behavior where BIG-IP includes VLAN context in connection matching

Verification:

  • Capture traffic using: tcpdump -s0 -i 0.0:nnn -w /var/tmp/capture.pcap --f5 ssl
  • Verify that return traffic from Layer 3 services hits the correct service virtual server
  • Confirm no SYN retransmissions or connection failures

Additional Information

Understanding connection.vlankeyed:

  • Default value: "enable" - BIG-IP includes VLAN ID as part of the connection key, allowing the same 4-tuple on different VLANs to be treated as separate connections
  • When disabled: BIG-IP matches connections only by 4-tuple, which can cause issues in multi-VLAN architectures like SSLO

Why this setting might be disabled:

  • BGP routing configurations where traffic may arrive from different VLANs
  • Advanced routing scenarios requiring VLAN-agnostic connection handling
  • Legacy configurations or specific architectural requirements

SSLO-specific considerations:

  • SSLO requires multiple independent connections on different VLANs to function properly
  • Inline Layer 3 services are most affected by this issue
  • Service types using SNAT may not experience this issue as the 4-tuple is modified
  • Ensure adequate memory allocation for restjavad/restnoded processes:
  • tmsh modify sys db provision.extramb value 4000
  • tmsh modify sys db provision.restjavad.extramb value 2227
  • tmsh modify sys db provision.tomcat.extramb value 300
  • tmsh modify sys db restnoded.timeout value 600
  • tmsh modify sys db restjavad.timeout value 600
  • tmsh modify sys db icrd.timeout value 600

Expected behavior:

  • With connection.vlankeyed enabled (default), traffic flows correctly through SSLO service chains
  • With the workaround applied (source port set to "change"), unique 4-tuples prevent connection collisions even when connection.vlankeyed is disabled
