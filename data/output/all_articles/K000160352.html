K000160352: BIG-IP LTM VE Standby Device Offline and HA Failover Communication Failure on VMware ESXi

Type
Support Solution
Published
2026-03-15
Updated
2026-03-15
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.3
Source
https://my.f5.com/manage/s/article/K000160352

Description

A BIG-IP LTM VE device in a high-availability (HA) pair became offline and disconnected from its peer. The device was unable to communicate over the dedicated failover VLAN, resulting in loss of HA sync and all virtual servers and pool members going offline. Key symptoms included:

  • Device status: OFFLINE/INOPERATIVE
  • Unable to ping peer's failover unicast address (Destination Host Unreachable)
  • tmsh show /cm failover-status: No failover updates received from peer, status "Error"
  • Log messages:
    • MCPD query response exceeding 30 seconds  
      warning snmpd[7201]: 010e0004:4: MCPD query response exceeding 30 seconds.
    • scriptd exceeded time to live, terminating script  
      err scriptd[4878]: 014f0004:3: script has exceeded its time to live, terminating the script
    • SOD killing mcpd due to failed heartbeat  
      notice sod[6778]: 01140041:5: Killing /usr/bin/mcpd pid 4970.
warning sod[6778]: 01140029:4: HA daemon_heartbeat mcpd fails action is restart.
    • Overdog scheduling exceeded timeout (up to 14 seconds)  
      warning sod[6778]: 010c0083:4: No failover status messages received for 15.200 seconds, from device ...
    • Core files generated for mcpd, scriptd, tmm
  • Management IPs remained accessible, but failover and self IPs were not
  • After rebooting the affected VE, the device returned to normal operation, and HA sync was restored.

Environment

  • Product: BIG-IP LTM VE
  • Version: 17.1.3
  • Platform: VMware ESXi
  • HA pair configuration with failover VLAN
  • Port group security settings: Promiscuous Mode, MAC Address Changes, and Forged Transmits set to "Reject" (VMware default)
  • No recent changes to ESXi host, VM settings, or network configuration
  • High memory usage and swap utilization were observed on the affected device
  • NTP servers are configured but not responding on the affected device

 

Cause

The hypervisor (VMware ESXi) failed to provide sufficient CPU resources to the BIG-IP VE for an extended period (over 14 seconds), resulting in SOD killing critical daemons (mcpd, tmm, scriptd) and the device going offline. This resource starvation led to system instability and loss of HA failover communication.

 

Answer/Recommended Actions

  1. Review and ensure the BIG-IP VE is configured with dedicated CPU and RAM resources on the hypervisor; avoid overcommitment.
  2. Monitor hypervisor health and resource allocation to prevent descheduling.
  3. If the device becomes unresponsive due to resource starvation, reboot the affected VE to restore services.
  4. For HA reliability, consider adding management IPs as secondary failover unicast addresses.
  5. If HA traffic is blocked, review ESXi port group security settings (Promiscuous Mode, Forged Transmits, MAC Address Changes) and set to "Accept" if required for HA communication.
  6. Verify NTP server accessibility and configuration.

 

Additional Information

  • The issue was resolved by rebooting the affected VE, which restored normal resource allocation and HA sync.
  • Other VEs with identical resource allocation may not exhibit the issue if hypervisor resources are not overcommitted or descheduled.
  • SOD (System Overdog Daemon) will kill daemons if the hypervisor fails to provide resources for extended periods, as indicated by overdog logs.
