Issue

Beginning with BIG-IP version 10.2.1, the default file creation mask of the shell process is u=rwx,g=,o= (or octal 077) for all users.

In previous BIG-IP versions, the default file creation mask of the shell process is u=rwx,g=rx,o=rx (or octal 022) for the root user and u=rwx,g=rwx,o=rx (or octal 002) for any other user.

F5 changed this setting, which is also inherited by all processes subsequently started from the shell, in order to allow for greater security. With a default file creation mask of 077, files and directories created by a user will not be readable by any other user on the BIG-IP system.

For example, if an attacker gained control of a process that runs on the BIG-IP system without root privileges, the attacker would not be able to use that process to access files created by the root user.

The file creation mask is also often referred to as user mask, or simply umask.

F5 Product Development tracked this change in behavior as ID 225251 (formerly CR138898).

Brief overview of the user mask

The user mask limits the permission modes for files and directories created by a process. It is important to note that the user mask does not set extra permissions beyond what is originally specified by the process that creates the file or directory.

Example 1

When programs create files, they usually specify read and write permissions for all users, and no execute permissions (rw-rw-rw- or 666).

However, a user mask of 077 will change the permissions so that the owner of the file has read and write access, and everybody else has no access at all (rw------- or 600).

It should be noted that no one has execute permissions, not even the owner of the file, which the user mask would have allowed. This is because execute permissions were not set for anyone by the process that created the file.

Example 2

When programs create directories, they usually specify read, write, and execute permissions for all users (rwxrwxrwx or 777).

However, a user mask of 077 will change the permissions so that the owner of the directory has read, write, and execute permissions, and everybody else has no access (rwx------ or 700).

In this case, the owner of the directory has execute permissions because they were set by the process that created the directory.

Octal user masks

The following table explains the meaning of the digits that can be used to define octal user masks:

Digit Permissions masked to processes Permissions available to processes
0noneread, write, and execute
1executeread and write
2writeread and execute
3write and executeread
4readwrite and execute
5read and executewrite
6read and writeexecute
7read, write, and executenone

Octal user masks are represented using three digits. The first digit masks permissions for the user who owns the file, the second digits masks permissions for the file’s group, and the third digit masks permissions for other users not in the file’s group.

Displaying the current user mask

You can display your current user mask by typing the umask command. For example:

# umask
0077

If the -S option is supplied, the command displays your user mask in its symbolic form. For example:

# umask -S
u=rwx,g=,o=

Modifying the current user mask

If you need to create several files or directories that require special permissions, you may find it convenient to temporarily change your default user mask. To do so, type the umask command followed by the new mode. If the new mode begins with a digit, it is interpreted as an octal number; otherwise it is interpreted as a symbolic mode mask. For example, the following two commands are equivalent:

# umask 022

# umask u=rwx,g=rx,o=rx

F5 recommends changing your user mask back to its default value of 077 once you have completed your task. Alternatively, simply exit the shell, as the change is only valid for the current session.

Implications of this change in behavior

Because of this change in behavior, extra care must be taken when using the command line to manually handle files or directories on the BIG-IP system. Operations that were legitimate in previous BIG-IP versions may cause issues in version 10.2.1 or later. Specifically, you should always consider which users or processes will require accessing the files and directories you create.

Example 1

In BIG-IP version 10.2.1, a UCS archive created from the command line cannot be restored or downloaded via the Configuration utility. This issue occurs because the Configuration utility does not run with root privileges and therefore cannot access the archive.

Note: For more information on this issue, refer to K12600: A UCS archive created from the command line cannot be restored or downloaded from the Configuration utility.

Note: F5 Product Development is treating this inadvertent effect of the change in behavior as a known issue.

Example 2

When configuring the radvd service, the manuals have you copy the /etc/radvd.conf.example file to a new file named /etc/radvd.conf. While the permissions of the example file are correctly set to rw-r--r-- (644), in BIG-IP version 10.2.1 or later the permissions of the new file will be set to rw------- (600). This is not the case in previous BIG-IP versions, where the permissions of the new file will be identical to those of the example file. This difference in permissions is another effect of the change in behavior discussed in this Solution.

As a result, because the radvd service is started by the radvd user, the process will not be able to access the /etc/radvd.conf file and will continuously restart. If the /var/log/daemon.log file is inspected, you will see the following error message:

err radvd[31921]: can't open /etc/radvd.conf: Permission denied

You can resolve this situation by manually fixing the permissions of the /etc/radvd.conf file. To do so, type the following command:

chmod 644 /etc/radvd.conf

Note: The radvd service will continue to restart even after the permissions have been fixed if the /etc/radvd.conf file does not contain a valid configuration. If necessary, review the /var/log/daemon.log file to determine why the radvd service is restarting.
