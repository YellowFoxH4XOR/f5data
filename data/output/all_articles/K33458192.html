Known Issue

TCP time stamps sent by the VIPRION system may be inconsistent between blades.

This issue occurs when all of the following conditions are met:

  • You have a VIPRION system with multiple blades installed.
  • You have a server with the tcp_tw_recycle parameter enabled.

    Note: This TCP/IP parameter enables fast recycling of TIME_WAIT sockets. The default value is 0 (disabled).

  • The BIG-IP system communicates with the server using one or both of the following methods:
     
    • Using a virtual server with Secure Network Address Translation (SNAT) enabled.
    • Monitoring the server as a pool member.

Impact

Client connections or monitors may fail because the system sends TCP SYN packets with differing time stamps.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • Client connections and monitors fail intermittently after you enable tcp_tw_recycle on a server.

Resolution

Status

F5 Product Development has assigned ID 542104 to this issue. F5 has confirmed that this issue exists in the products listed in the Applies to (see versions) box, located in the upper-right corner of this article. Workaround

To work around this issue, you can either disable tcp_tw_recycle on the remote server or reboot the VIPRION system. To reboot the VIPRION system, perform the following procedure:

Impact of workaround: Performing the following procedure halts all traffic processing and you should perform the procedure only during scheduled maintenance.

  1. Log in to the Advanced Shell (bash) of the BIG-IP system.
  2. To ensure the blade's times are synchronized, type the following command:

    clsh ntpq -pn

  3. If the blade's times are significantly out of sync, ensure that you have an NTP server configured in the Configuration utility by navigating to System > Configuration > Device > NTP.
  4. To reboot the VIPRION system, type the following command:

    clsh reboot
