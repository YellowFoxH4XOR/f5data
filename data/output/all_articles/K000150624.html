Description

After an upgrade, CPU utilization from control-plane processes may increase.

 

Environment

A BIG-IP with many recurring processes on the control plane that uses libcrypto.  This includes frequently executed periodic external monitors or icall scripts that call external executables that loads the libcrypto library, even if it does not use encryption.  For example:

  • snmpget
  • LDAP monitor
  • dig

 

From system profiling (oprofile) results, we may see control-plane CPU (ie. odd-numbered CPUs in hyperthreaded systems) to spend a lot of time calling libcrypto:

 

Sorted by CPU 1:
 
[Start code block]
samples	%	samples	%	samples	%	samples	%	image	name	app
0	0	2169	62.256	0	0	1924	56.1097	libcrypto.so.1.0.2za	snmpget	/usr/lib64/libcrypto.so.1.0.2za

 

Cause

From BIG-IP 16.1.2.2, F5 is utilizing a new version of jitterentropy to generate random number seeds.

The issue is described in Bug ID 1579533: Jitterentropy read is restricted to FIPS mode or TMM usage only, for performance reasons

When executables like snmpget initializes, it may start an ssl library even if it does not use ssl, which will in turn try to get a random number seed from the operating system.  TMOS updated the random number seed generator that uses CPU jitter, and this causes more CPU utilization to produce a random seed.  Normally this isn't a problem when a control-plane process starts up and remains alive for a long time since the extra CPU to generate the random seed is only run at the beginning of the process when the random seed is requested.  However, when many new processes are started (and stopped) periodically, such as external monitors, then the number of CPU required to generate the random seed adds up until overall control-plane CPU utilization greatly exceeds BIG-IP versions that uses the previous random number seed generator.

 

Recommended Actions

  • Find alternative processes that does not use random number seeds.  For example, instead of using snmpget in a periodic script or external monitor, use tcp monitors instead.
  • Or, run processes less frequently.  For example, instead of running external monitors every 5 seconds, try running them every 30 seconds instead.

 

To check if your recurring process uses libcrypto, try running your process using strace.  For example:

# strace snmpget -c public localhost sysSystemUptime.0 2>&1 | grep -i libcrypto
open("/usr/lib64/tls/libcrypto.so.10", O_RDONLY|O_CLOEXEC) = -1 ENOENT (No such file or directory)
open("/usr/lib64/libcrypto.so.10", O_RDONLY|O_CLOEXEC) = 3
