K000149855: BIG-IP LTM Cookie Persistence may fail for upstream requests from F5 Distributed Cloud

Type
Support Solution
Published
2025-02-18
Updated
2026-05-11
Source
https://my.f5.com/manage/s/article/K000149855

Description

    An incompatibility exists between connection reuse (enabled by default on XC Origin Pools) and cookie-based session persistence applied on an upstream BIG-IP LTM system.  The incompatibility may result in broken session persistence, and users might encounter problems such as failing login sessions or inconsistency in reaching the same application server, leading to broken workflows.

    When accessing an application through F5 Distributed Cloud (XC), users may experience intermittent session timeouts and HTTP 404 errors via upstream. The issue presents as users being logged out mid-session and redirected to a session timeout page after receiving a 404 response from the backend application. This behavior is observed only when traffic passes through XC; direct (intranet) access does not exhibit the problem. Logs show rsp_code_details = via_upstream, indicating the 404 is generated by the backend application, not XC. The issue is intermittent and not tied to a specific user or time.

    BIG-IP LTM is configured as the XC origin with a cookie persistence profile and multiple pool members in its backend pool. 

    Environment

    • F5® Distributed Cloud (XC) HTTP Load Balancer and Origin Pool
    • F5 BIG-IP LTM as origin endpoint
    • Connection Reuse
    • Cookie Persistence

    Cause

    This issue occurs due to how TCP connections are handled between the XC Origin Pool and the F5 LTM:

    1. By default, XC Origin Pool performs connection reuse, carrying multiple requests over a single shared TCP connections.
    2. The origin pool on F5 LTM is configured for cookie persistence.  Cookie persistence inserts a cookie into HTTP response containing encoded (and optionally encrypted) value indicating the backend pool member the session should remain bound to.  When the cookie is returned by the client in a subsequent request, F5 BIG-IP LTM makes a forwarding decision based on the cookie value, overriding normal load balancing logic.
    3. However, F5 LTM by default asserts a load balancing decision per connection, not per request.  When HTTP requests received by F5 LTM are multiplexed on a shared connection, such as with HTTP/1.1 connection reuse or HTTP/2, the LB decision made for the first request is inherited by all subsequent ones. As a result:
      • Persistence cookies may not be honored.
      • All requests on the shared connection are directed to the same backend pool member as the first.
      • Misdirected requests result in broken session state, often manifested as user experience of 'random logout', 'session timeout', 'redirected to login page', etc.
    4. See K7964: The BIG-IP system may appear to ignore persistence information for Keep-Alive connections for further details of this incompatibility.

    Recommended Actions

    There are three options to address the incompatibility of connection reuse with upstream cookie persistence:

    1. [on the BIG-IP] Use OneConnect to detach the server side after each request :

      • In the BIG-IP LTM configuration, apply the OneConnect profile to the virtual server that serves the XC origin pool.
      • OneConnect ensures that individual HTTP requests will create new server-side connections, thereby honoring the persistence cookies.
    2. [on the BIG-IP] Use an iRule to detach the server side after each request
      • Apply an iRule to effectuate the same server-side detachment logic as OneConnect
      • The iRule approach allows for customization.
      • Refer to K7964 for details.
    3. [on XC] Disable Connection Reuse on the XC Origin Pool
      • As disablement of Connection Reuse will increase the count of active upstream connections, ensure the XC origin pool and the origin endpoint are appropriately configured to handle the changed traffic shape (for instance, connection limits may need to be raised).
      • An incremental performance penalty may be incurred as a result of the increased TCP overhead.

    Validation steps after configuration :

        • Ensure no additional latency or connection-related errors arise due to this change.
        • Test key workflows, particularly login sessions and other session-based transactions, to confirm consistent behavior.

    Additional Information

    • The issue is not caused by WAF or security policy blocks.
    • Increasing backend timeout values does not resolve the problem.
    • The root cause is session stickiness loss due to connection reuse, not a timeout or application bug.
    • Disabling Connection Reuse on the XC Origin Pool immediately resolves the session drop and 404 behavior.
