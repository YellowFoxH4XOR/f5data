Description

The external monitor type, sometimes referred to as an EAV (Extended Application Verification), applicable to both LTM and DNS (previously known as GTM) monitors, allows the use of arbitrary scripts for monitoring application service. Typically these are script that run under the bash, perl, or python shells. When the script runs, and produces any output, the monitor is considered successful, and the target is marked up.

 

In a unix environment, the first line of an executable script can optionally start with the special sequence "#!", which is known as a "she-bang", followed by the full path and filename of the shell that should be used to execute the commands in the script. This allows the script itself to specify the interpreter that it should run under. The she-bang line is optional, and if omitted, the script will run under the default shell (/bin/sh).

 

Plain text files, such as shell scripts, consist of lines ASCII characters which are each terminated by line breaks sequences. In a unix environment, the line break sequence is a single character, 0x0A (linefeed), but in a windows environment, for example files saved using notepad.exe, the line break sequence is two characters - 0x0D 0x0A, which is a carriage return, followed by a line feed. If a text file created in a windows environment has been copied to a BIG-IP using a binary-intact method, the line break sequences will be incompatible, and unix will see an unwanted additional 0x0D carriage return character at the end of every line.

 

This additional character can cause scripts containing a she-bang line to fail to execute, because the operating system tries to execute an interpreter with a trailing carriage return in the name, which not only does not exist, but is also not an allowed shell (not present in the file /etc/shells), so the execution of the script fail, with the error "No such file or directory", which can be misleading, because the script file does exist.

 

Symptoms

  • If the script has been created as described above, and contains windows line termination sequences, causing the script to fail to execute, then the monitored target will be marked down, with a cause of "Pool member has been marked down by a monitor".
  • If a tcpdump packet capture is performed, none of the expected monitor traffic (assuming the monitor sends traffic), will be seen towards the monitored target,
  • For LTM monitors, the db variable "bigd.debug" can be set to 'enabled' (tmsh modify sys db bigd.debug value enabled), and the message "(spawn_external_pinger): EAV execve: No such file or directory" will be seen in /var/log/bigdlog when the external monitor script is executed.
  • For DNS (GTM) monitors, which could be executed by any permitted big3d agent in the GTM (DNS) Sync Group, there is no ability to enable debug logging in big3d for external script execution

 

Troubleshooting

To troubleshoot and confirm the problem, it is first necessary to identify the filename associated with the external monitor script.

  1. Identify the name of the external monitor's program (Local Traffic >> Monitors >> [external monitor name] >> External Program)
  2. Identify the filestore cache file associated with the external monitor
  3. Use the "file" utility to identify the monitor script's file type - for windows files, the command will note "with CRLF line terminators"

For example:

[root@bigip1:Standalone:Active] config # grep -A1 "My_external_monitor" /config bigip.conf | grep cache-path

cache-path /config/filestore/files_d/Common_d/external_monitor_d/:Common:My_external_monitor_89804_3

 

[root@bigip1:Standalone:Active] config # file -b /config/filestore/files_d/Common_d/external_monitor_d/:Common:My_external_monitor_89804_3

Bourne-Again shell script, ASCII text executable, with CRLF line terminators

 

If the file has unix line terminators, the output of the file command will not include the "with CRLF line terminators" phrase.

 

Environment

  • BIG-IP with external monitors (either LTM or DNS)
  • The external monitor script has been created in a Microsoft Windows environment, for example with notepad.exe
  • The external monitor script contains a she-bang (#!) sequence, for example "#!/bin/bash" on the first line
  • The external monitor has been copied to the BIG-IP using a binary-intact file transfer method, for example WinSCP


Cause

Script files created in a Microsoft Windows environment, copied to a BIG-IP device using a binary-intact file transfer method

 

Recommended Actions

The simplest method to convert the file to have unix line terminators is to simply open the script in the BIG-IP GUI, and hit update - this will re-save the file with unix line terminators.

System >> File Management >> External Monitor Program File List >> (select the monitor) >> Update

 

Alternatively, after identifying the filestore cache path, per the troubleshooting steps noted above, the script can be edited using vim, and re-saved in unix format.

  1. vim <cache-file>
  2. :set ff=unix
  3. :wq

To avoid this problem occurring in the first place, use the BIG-IP GUI to create external monitor scripts, and paste the script into the definition area. Alternatively, if the script has been created in a windows environment, and then copied to a BIG-IP, set the file transfer program (for example winscp) to ASCII mode when transferring the files, or configure it to specifically for unix style line terminators. The exact method to do this varies depending on the file transfer program and falls outside the scope of this article.
