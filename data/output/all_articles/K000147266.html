Answer/Recommended Actions

SSRF flaws occur whenever a web application is fetching a remote resource without validating the user-supplied URL. It allows an attacker to coerce the application to send a crafted request to an unexpected destination, even when protected by a firewall, VPN, or another type of network access control list (ACL).

As modern web applications provide end-users with convenient features, fetching a URL becomes a common scenario. As a result, the incidence of SSRF is increasing. Also, the severity of SSRF is becoming higher due to cloud services and the complexity of architectures.

For more information, please visit: A10:2021 -Server-Side Request Forgery

There are many ways to infiltrate application servers using broken access controls and we are going to focus on the following scenario below and how to mitigate it using a WAF/WAAP policy in Distributed Cloud (XC).

To configure the WAF policy enforcement in blocking mode:

  1. Make sure that you already have a LB configured as well as a WAF policy configured. The following articles should help you with this process: HTTP Load Balancer and Application Firewall
  2. Now, let's configure our WAF policy in our LB. To do that, navigate in your XC console to your LB by going to: Home >> Web App & API Protection >> select the namespace in which you configure your LB >> Manage >> Load Balancers >> HTTP Load Balancers
     

  3. Locate your LB and click on the 3-dot figure at the right of your screen and select "Manage Configuration"
     

  4. Click on the "Edit Configuration" button at the upper-right corner of the console, select "Web Application Firewall" from the "Edit" Menu, make sure that " Web Application Firewall (WAF)" is set to enable, then just below, select the WAF policy that you have configured in Step #1 and then click on the "Edit Configuration" option.
     

  5. Verify that all WAF policy settings are configured as "Default" and make sure that the "Enforcement Mode" is set to "Blocking"
     

  6. Click on the "Continue" button at the bottom-right of the console, and then click "Save and Exit" at the same location.

  7. To verify that the WAF policy is working as expected, we are running a test using the OWASP Juice Shop, which is a vulnerable application configured as a backend. Check on the "Additional Information" for details on how we set this scenario.

    We can notice that this application is vulnerable to SSRF attacks when we type any URL into the Image URL field, when we choose any URL this value will be stored in the imageURL parameter, and we will find that no requests to get the image were made by our web browser, therefore, the image was downloaded by the Juice Shop server,

    However, these kind of requests are blocked by the WAF policy before they reach the server
     
  8. To verify the Support ID that you just received, go back to the XC console and navigate to Home >> Web App & API Protection >> select the namespace in which you configure your LB >> Overview >> Security, then scroll to the bottom of the console and select your LB:

     

  9. Once in that page, click on the "Security Analytics" tab where you will see the latest security violations
     

  10. Click in the "Add Filter" option and then select: "req_id >> in >> insert the Support ID that you received in the juice shop". 
     
    Please be aware that, by default, the time range for the violations is 5 minutes, but you can adjust that time range as needed.

Additional Information

In this scenario, we are using OWASP Juice Shop, which is an insecure web application designed for security training and other related purposes. For more information about the Juice Shop please visit: OWASP Juice Shop

The only promising input field for an SSRF attack is the following field "Image URL", used to import an image using the URL. Open your browser's DevTools and watch the Network tab.

Use the following link "https://placekitten.com/100/100" into "Image URL" and click "link Image". You will realize a request http://xxxxxxxxxxx/profile/image/url with the chosen https://placekitten.com/100/100 as parameter imageUrl.

You will find no HTTP request to https://placekitten.com/100/100 going out from your browser, though. As the image was retrieved and associated with your profile, it must have been downloaded by the Juice Shop server.
