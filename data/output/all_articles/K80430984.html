Description

When using the REST API to manage F5 BIG-IP platforms, an admin may want to know the maximum TPS (transactions per second) they can send to the REST API on their platform.

Environment

  • BIG-IP managed or monitored using REST API
  • Performance

Cause

None

Recommended Actions

F5 do not provide this type of metric for the REST API on a BIG-IP because it varies greatly with the nature of the API requests we send to the device, as well as the device config objects present which may be being polled to return the values required for the API response, etc. A simple measure of "how many GET requests for a specific command can a given platform take" also has too many variables which would greatly affect the answer, such as:

  • Size of the configuration
  • Exact API command being run
  • Other processes running on the system
  • Whether AVR or similar items that use the mgmt CPU are provisioned
  • etc.

The admin can try to find a value for the specific commands in a poll for their platform and config themselves (if they just want to know a "max TPS" they can send to the API safely). The admin would need to configure the box as they want it, and then test how many API transactions of the types they want they can run against the box before the system CPU starts to run at 50% or so. At that point, they should treat that as the ceiling "absolute max TPS" (for their chosen commands, and on their particular config), because if there is a spike of traffic, then TMM could trigger the idle-enforcer on the system CPU which would result in the API calls failing at that point if they needed more CPU.

Once they have determined a ceiling "absolute maximum TPS" for their system, they should ensure they don't use more than about 50% (or less) of that in the real world. This is because the system management (REST API) is not the primary function of the device, and there are other processes that also run on the mgmt CPU of the box which are important and we need to make sure they are not starved by the REST API calls.
