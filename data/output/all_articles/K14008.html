Known Issue

Configuring a pool as the next hop route (the default gateway pool) may cause iQuery traffic to fail.

This issue occurs when the following conditions are met:

  • BIG-IP device group members, or BIG-IP GTM sync group members, reside on different networks.
  • The affected devices are configured to communicate with peer devices using a pool as the next hop route.

The device service clustering (DSC) and BIG-IP GTM synchronization technologies both use TCP port 4353 to facilitate communication between peer devices. When a pool is configured as the next hop route, the BIG-IP system defines an internal listener object that rejects the outbound iQuery traffic. As a result, BIG-IP DSC and BIG-IP GTM synchronization may fail.

Impact

  • BIG-IP device group communication may fail.
  • High-availability features, such as synchronization, failover, and mirroring fail to operate.
  • BIG-IP GTM synchronization and iQuery communication may fail.

Symptoms

As a result of this issue, the BIG-IP device group members may encounter one or more of the following symptoms:

  • BIG-IP iHealth lists Heuristic H395608 on the Diagnostics > Identified > Medium screen.
  • The Device Management screen in the Configuration utility indicates that the peer device is offline (red).
  • The system logs error messages to the /var/log/ltm file indicating that the peer device is unreachable. The error messages appear similar to the following example:

    err mcpd[5198]: 0107142f:3: Can't connect to CMI peer 10.12.16.213, port:6699, Transport endpoint is not connected

  • The tmsh show /cm sync-status command indicates that the sync status is disconnected.

    For example:

    tmsh show /cm sync-status

    ------------------------------------------------------------------------------
    CM::Sync Status
    ------------------------------------------------------------------------------
    Color red
    Status Disconnected
    Summary
    Details

In addition, the BIG-IP GTM sync group members may encounter one or more of the following symptoms:

  • The Servers screen in the Configuration utility indicates that the sync group peer is offline (red).
  • The system logs error messages to the /var/log/gtm file indicating that the sync group peer is unreachable. The error messages appear similar to the following example:

    alert gtmd[16813]: 011a500c:1: SNMP_TRAP: Box 10.12.16.213 state change green --> red (Box 10.12.16.213 on Unavailable)
    alert gtmd[16813]: 011a5004:1: SNMP_TRAP: Server /Common/B3900-R14-S13 (ip=10.12.16.213) state change green --> red (No communication)
    notice gtmd[16813]: 011ae020:5: Connection in progress to 10.12.16.213
    notice gtmd[16813]: 011ae020:5: Connection in progress to 10.12.16.213
    notice gtmd[16813]: 011ae020:5: Connection in progress to 10.12.16.213
    alert gtmd[16813]: 011a5009:1: SNMP_TRAP: BIG-IP GTM /Common/B3900-R14-S13 (10.12.16.213) left sync group default
  • The tmsh show /gtm iquery command indicates that the iQuery state is not connected.

    For example:

    ---------------------------------------
    Gtm::IQuery: 10.12.16.213
    ---------------------------------------
    Server B3900-R14-S13

  • The iqdump utility indicates the iQuery connection to the peer system failed.

    For example:

    iqdump 10.20.23.19
    Connection to ::ffff:10.20.23.19:4353 failed: Connection refused

Workaround

To work around this issue, change the next hop route to use a gateway IP address instead of a pool. To do so, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Network > Routes.
  3. Click the route that is associated with the iQuery traffic.
  4. Change Resource to Use Gateway.
  5. In the Gateway Address box, enter the gateway IP address.
  6. Click Update.
