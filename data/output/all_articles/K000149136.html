K000149136: SSLO does not allow re-use of a single client connection after serverside is closed

Type
Support Solution
Published
2024-12-30
Updated
2024-12-30
Applies to
  • F5 App Protect
  • F5 SSL Orchestrator: 17.X.X, 17.1.X, 17.1.1, 17.1.0, 17.0.X, 17.0.0
Source
https://my.f5.com/manage/s/article/K000149136

Description

SSLO does not allow re-use of the same client TCP connection after the server side is closed. 

This behaviour only really becomes apparent in the particular case when a client specifically sends 2 separate HTTP CONNECT cmds over the same TCP stream to an SSLO explicit proxy deployment. 

 

Environment

BIG-IP SSLO

 

Cause

This is by design on SSLO at present, basically the same client connection (on SSLO) cannot form 2 separate usable server connections.

 

Recommended Actions

A workaround could be to disable connection reuse (disable "Connection: keep-alive", aka send "Connection: close" in the HTTP response) in the clientside HTTP profile attached to the SSLO VS.

This workaround however would have the secondary effect of only allowing one http request/response per TCP connection.

 

Additional Information  

"The CONNECT method converts the request connection to a transparent TCP/IP tunnel", so when the serverside connection is closed, a normal HTTP proxy will also close the clientside connection, so there is no possibility of a second HTTP command (eg. 2nd CONNECT) being sent out on the same original TCP connection after the serverside connection is closed.

SSLO (in xp mode) used to behave like an ordinary HTTP proxy in the past, but this was changed as part of ID 755447 to handle the situation when a service sends a RST on the server side, and sends back content on the client side, so basically now the SSLO does not automatically close the clientside connection as soon as the serverside connection is closed, in case there is a service present which wants to send something else to the client.

Some client programs or scripts might expect the normal http proxy behaviour and thus might not expect the clientside TCP connection to be kept open in that situation, and may send a second CONNECT command without explicitly closing the clientside connection and opening a new one, as they would expect their OS or underlying subsystem to open a new TCP connection and send the second CONNECT command. However this will fail if a new connection is not used as it does not make sense to send a second HTTP command on a connection if it has already been converted (via an older CONNECT command) to a TCP connection.
