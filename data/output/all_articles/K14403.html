Topic

This article applies to BIG-IP 11.x and later. For information about previous versions, refer to the following article:

  • K12263: Maintaining disk space on the BIG-IP system (9.x - 10.x)

Monitoring the hard disk capacity on a BIG-IP unit is critical to maintaining a healthy system. If a BIG-IP system is running low on disk space, you may experience performance-related issues, such as the inability to perform upgrades, run configuration synchronization (ConfigSync) operations, or save user configuration set (UCS) files. F5 recommends that you periodically check disk space usage and use industry best practices for keeping disk usage to a minimum.

Description

Overview of the LVM disk-formatting scheme

The BIG-IP system uses the logical volume management (LVM) disk-formatting scheme. LVM is an enhanced software image manager used for deploying logical rather than physical storage. With the LVM disk-formatting scheme, logical volumes may span across one or more physical hard drives and can be resized without interrupting service.

The BIG-IP system's LVM volume sets are formatted such that every product module includes a description of the file systems it needs, including a mount point and size for each volume. During installation, the BIG-IP system automatically allocates an appropriate amount of disk space when creating a volume set. For example, on a BIG-IP 2000 series platform provisioned for BIG-IP LTM and BIG-IP ASM, you can use the lvs command to review the system allocates disk space for each volume set, and the output may appear similar to the following example:

  LV                       VG        Attr      LSize   Pool Origin Data%  Move Log Cpy%Sync Convert
  app.ASWADB.set.1.mysqldb vg-db-sda -wi-ao---  12.00g                                            
  set.1._config            vg-db-sda -wi-ao---   3.17g                                            
  set.1._usr               vg-db-sda -wi-ao---   3.29g                                            
  set.1._var               vg-db-sda -wi-ao---   3.00g                                            
  set.1.root               vg-db-sda -wi-ao--- 440.00m

Additionally, the system allocates a certain amount of disk space for the shared volume, and the log volume. For example, a BIG-IP 2000 series platform allocates disk space for the shared and log volumes that appear similar to the following example:

  LV                       VG        Attr      LSize   Pool Origin Data%  Move Log Cpy%Sync Convert
  dat.log.1                vg-db-sda -wi-ao---   7.00g                                            
  dat.share.1              vg-db-sda -wi-ao---  30.00g

Symptoms of a full or near full disk

When the BIG-IP file systems become full, undesirable or unpredictable behavior may result. Symptoms may include the following:

  • The diskmonitor utility generates warning messages or traps. The diskmonitor utility is a script that runs periodically on the BIG-IP system and alerts you if the partition space or volumes reach a defined threshold. If one or more of these thresholds are reached, a log message is logged to the /var/log/ltm file.

    For example, the following message indicates that the /shared partition has less than 30 percent free space available:

    diskmonitor: 011d005: Disk partition shared has less than 30% free

    The following message indicates that the /shared partition has zero percent free space available:

    diskmonitor: 011d004: Disk partition shared has only 0% free

    Additionally, the BIG-IP system sends the following SNMP trap alerts when the partition space reaches a defined threshold:

    alert BIGIP_DMON_ERR_DMON_ALERT {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.25"
    }
    alert BIGIP_DMON_ERR_DMON_WARN {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.25"
    }
    alert BIGIP_DMON_ERR_DMON_GROWTH {
    snmptrap OID=".1.3.6.1.4.1.3375.2.4.0.26"

  • Upgrades, hotfix installations, or point release installations fail to proceed.
  • Daemon log messages appear similar to the following examples:

    Couldn't write to <file> / <partition>
    Failed to open file

  • The system performance degrades, such as slow or failed disk writes.

Recommendations

To help prevent disk usage issues, F5 recommends that you use the following guidelines to maintain adequate disk space on the system:

  • Delete imported software images that are no longer needed. For more information, refer to K34745165: Managing software images on the BIG-IP system.
  • Delete unnecessary OPSWAT EPSEC packages.  For more information, refer to K21175584: Removing unnecessary OPSWAT EPSEC packages from the BIG-IP APM system.
  • Delete unused boot location volumes that are no longer needed. For more information, refer to K33265170: Deleting a boot location file system to free up disk space.
  • When you plan to add more BIG-IP modules to the system, you should also consider if additional disk space is required for the module's application volumes. Each module provisioned and installed on a different software volume may have its own set of the application volume disks. For more information, refer to K17477: Disk usage by the BIG-IP modules with application volumes.
  • Store maintenance-related files in the /shared/tmp directory. Maintenance-related files are those files that an administrator may create while performing maintenance or troubleshooting-related tasks on the system. For example, tcpdump files, UCS archives, or QKView files should be stored in the /shared/tmp directory. Using the /shared/tmp directory for maintenance-related files is recommended for the following reasons:
    • The BIG-IP installer allocates a large amount of disk space to the /shared partition.
    • The /shared/tmp directory is shared between all installed images on a system. For example, if you save a tcpdump file to the /shared/tmp directory, each installation image or volume set has access to the tcpdump file.
  • Store long-term maintenance files on a network share. If you create files that are suitable for longer-term storage, such as UCS archives or single configuration file (SCF) files, F5 recommends that you move them to a network share.
  • When creating or generating a file on the BIG-IP system, provide the full path location so that the file is saved to the intended location and not the current working directory. For example, the following tcpdump command saves the capture file to the /shared/tmp directory:

    tcpdump -ni 1.1 -w /shared/tmp/example-tcpdump.pcap

    The following qkview commands save the corresponding support file to the /var/tmp directory:

    qkview -f /var/tmp/example-qkview.tar.gz

    The following TMOS Shell (tmsh) command saves the corresponding UCS file to the /var/tmp directory:

    tmsh save /sys ucs /var/tmp/example-config.ucs no-private-key

    Note: By default, UCS files are saved in their image-specific partitions, which are not visible to all installed images. If you plan to create an archive that to use for production (using either the Configuration utility or command line), no path name is needed and the UCS archive is saved to the default location of /var/local/ucs/.

  • Avoid storing files in directories that reside on the root file system. The BIG-IP system has a relatively small root file system and separate partitions for file systems, such as /config, /usr, and /shared. Directories, such as /home reside on the root file system and should not be used for file storage.
  • Store image files in /shared/images directory. If you upload installation images to the BIG-IP system using the command line, you should store them in the /shared/images directory.
  • Periodically check the available disk space on the BIG-IP system.
  • To check available disk space, you can use the df -h command.

    Note: On a multi-blade VIPRION system, you should run the commands from each blade. To connect to the terminal of a blade from another blade, use the ssh slot<slot number> command syntax.

    For example, the df -h command may produce the following output, which indicates that the root file system is at 100 percent usage:

    Filesystem      Size  Used Avail Use% Mounted on
    /dev/md4        427M  427M     0 100% /
    none             24G  2.2M   24G   1% /dev/shm
    /dev/md6        3.2G   76M  2.9G   3% /config

  • Check for deleted files still using disk space.

    Unix-based operating systems allow files to be deleted while they are still open by other processes. When this occurs, the release of occupied disk space is deferred until all open handles on the relevant file are closed. This deferred deletion can cause the amount of reported space used by files on a mount point appear inconsistent with the total disk space used.  You can check how much space used by deleted files by entering the following command. 

    Note: It is important to consider where these files are mounted in the file system because not all mount points exists on disk. Some are in memory, such as /var/tmstat, and some are virtual, such as /proc.  Specifically, the tmpfs and hugetlbfs file systems are stored entirely in memory (also known as a ram-drive) and do not occupy any physical disk space.

        lsof -ws | grep -i 'size\|deleted'

    Example output:

    In the previous output, it appears that 10 MB (10,485,760 bytes) of space is being used by a deleted file on /dev/mprov/tmm, this file is actually mounted on the hugetlbfs file system, so it is not actually contributing to physical disk usage. To determine the file system type, first identify where the mount point is located, using the df (disk free) command on the folder in which the deleted file is located:

          df /dev/mprov/tmm/

        none                   0     0         0    - /dev/mprov/tmm

    Then grep the output of the mount command for that mount point to identify the file system type:

       mount | grep /dev/mprov/tmm
       none on /dev/mprov/tmm type hugetlbfs (rw,pagesize=2M)

    Similarly, the deleted file in /var/tmstat is on a tmpfs file system and also not contribute towards physical disk space usage.

    For files stored on the physical disk/ssd, the file system is typically ext3 or ext4. For example /shared

        mount | grep 'on /shared '
        /dev/mapper/vg--db--vda-dat.share on /shared type ext3 (rw,noatime)


    If you are sure that the deleted file is stored on a physical disk, check the SIZE column (displayed in bytes) to see if there are any large files that have not been released. The NAME column displays the file's location. In the previous example, the bigd process is keeping a file open in /var/log/monitors, which is 2,018,573,650 bytes (roughly 2 GB). For the disk space to be released, either the bigd process must release the file or it releases when you restart the bigd service.
