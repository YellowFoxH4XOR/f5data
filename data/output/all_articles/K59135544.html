Known Issue

After an upgrade, the BIG-IP ASM system stays in the not ready state.

This issue occurs when all of the following conditions are met:

  • Your BIG-IP ASM configuration uses a security policy without a policy name.
  • You upgrade the BIG-IP ASM system to an affected release.

Impact

The BIG-IP ASM system stays in the not ready state.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • After upgrading the system, you observe log messages in the /var/log/ts/ts_configsync.log file similar to the following example:

    asm_start|INFO|<date and time>|18295|F5::ASM::COAPI::SaveAll,,MCP state was persisted
    asm_start|INFO|<date and time>|18295|F5::LockFactory::Base::unlock,,F5::ConfigSync Line 299 has unlocked /ts/lock/ts_db.lock. (Lock count: 0)
    emerg logger: Re-starting asm

  • After upgrading the system, you observe log messages in the /var/log/asm file similar to the following example:

    info perl[<pid>]: 01310053:6: ASMConfig change:   [delete] { audit: component = tsconfd }
    info perl[<pid>]: 01310053:6: ASMConfig change:   [delete] { audit: component = tsconfd }
    info perl[<pid>]: 01310053:6: ASMConfig change:   [delete] { audit: component = tsconfd }
    info perl[<pid>]: 01310053:6: ASMConfig change:   [delete] { audit: component = tsconfd }
    info perl[<pid>]: 01310053:6: ASMConfig change:   [delete] { audit: component = tsconfd }
    info perl[<pid>]: 01310053:6: Per-invocation log rate exceeded; throttling.

  • When you attempt to execute a configuration synchronization (ConfigSync), the synchronization fails.

Workaround

To work around this issue, you can manually review the BIG-IP ASM Security Policy list and remove any policies that are configured without a policy name. Alternatively, you can execute a MySQL command to locate the policy ID number of security policies that are configured without a policy name. To do so, perform the following procedure:

Impact of workaround:  Performing the following procedure should not have a negative impact on your system.

  1. Log in to the command line of the affected BIG-IP ASM system.
  2. Query the MySQL database for security policies that are configured without a policy name by typing the following command:

    mysql -uroot -p`perl -MF5::DbUtils -e 'print F5::DbUtils::get_mysql_password(user => qw{root})'` -e 'SELECT * FROM PLC.PL_POLICIES WHERE name = ""\G'  | awk '{print $1,$2,$3}'

  3. In the MySQL output, note the policy ID number for any listed security policies (typically the first numeric value of the policy data).

    MySQL output appears similar to the following example:

    id account_id name

    21    2     

  4. Log in to the Configuration utility.
  5. Navigate to Security > Application Security > Security Policies.
  6. Locate the policy ID numbers noted in the step 3 output by counting the line items.

    For example, if the MySQL query returns the policy ID number of 21, you should check the Security Policies list for the 21st line item in both the Active and Inactive lists, and verify that the policies are configured without a policy name.

  7. For unnamed security policies that are in the active state:
    1. Select the affected security policy.
    2. Click Deactivate.
    3. Click Inactive Policies.
    4. Select the check box of the deactivated security policy.
    5. Click Delete.
  8. For unnamed security policies that are in the inactive state:
    1. Click Inactive Policies.
    2. Select the check box of the deactivated security policy.
    3. Click Delete.
  9. Repeat steps 7 and 8 for each unnamed security policy.
  10. Reboot the BIG-IP ASM device by navigating to System > Configuration Device, and then clicking Operations > Reboot.
