K000150818: SNMP authentication may not work upon restoring F5OS backup

Type
Support Solution
Published
2025-04-11
Updated
2025-04-11
Applies to
  • F5OS
  • F5OS-A: 1.8.0, 1.7.0, 1.5.0, 1.5.1, 1.5.2, 1.5.3
  • F5OS-C: 1.8.0, 1.6.0, 1.6.1, 1.6.2
Source
https://my.f5.com/manage/s/article/K000150818

Description

Restoring a backup with an SNMP user on a system with a different SNMP engine ID will duplicate the SNMP user but without authentication and privacy keys. However, this is only seen when the database is later backed up. Here is an example upon examining the XML database backup:

<usmUserTable>
<usmUserEntry>
<usmUserEngineID>80:00:2f:f4:03:14:a9:d0:67:eb:02</usmUserEngineID>
<usmUserName>rcard</usmUserName>
<usmUserSecurityName>rcard</usmUserSecurityName>
<usmUserAuthProtocol>1.3.6.1.6.3.10.1.1.3</usmUserAuthProtocol>
<usmUserPrivProtocol>1.3.6.1.6.3.10.1.2.4</usmUserPrivProtocol>
</usmUserEntry>
<usmUserEntry>
<usmUserEngineID>80:00:2f:f4:03:14:a9:d0:77:c9:82</usmUserEngineID>
<usmUserName>rcard</usmUserName>
<usmUserSecurityName>rcard</usmUserSecurityName>
<usmUserAuthProtocol>1.3.6.1.6.3.10.1.1.3</usmUserAuthProtocol>
<usmUserPrivProtocol>1.3.6.1.6.3.10.1.2.4</usmUserPrivProtocol>
<usmUserAuthKey>2d:5d:05:86:c4:9f:78:78:dd:9a:7d:d1:45:3f:16:91:54:1d:e6:29</usmUserAuthKey>
<usmUserPrivKey>2d:5d:05:86:c4:9f:78:78:dd:9a:7d:d1:45:3f:16:91</usmUserPrivKey>
</usmUserEntry>
</usmUserTable>

This is the crucial part:

<usmUserEntry>
<usmUserEngineID>80:00:2f:f4:03:14:a9:d0:67:eb:02</usmUserEngineID>
<usmUserName>rcard</usmUserName>
<usmUserSecurityName>rcard</usmUserSecurityName>
<usmUserAuthProtocol>1.3.6.1.6.3.10.1.1.3</usmUserAuthProtocol>
<usmUserPrivProtocol>1.3.6.1.6.3.10.1.2.4</usmUserPrivProtocol>
</usmUserEntry>

No usmUserAuthKey and usmUserPrivKey.

Furthermore, /var/F5/system/log/snmp.log on F5OS does not indicate there is something wrong with SNMP user keys, even when receiving SNMP requests. The problem can be seen on the SNMP client, which report authentication failure.

root@snmp-client:~# date; snmpwalk -v3 -u snmp-client -l authPriv -a SHA -A test1234 -x AES -X test1234 10.154.84.35 .1.3.6.1.4.1.12276.1.3.1.2
Thu Apr 10 13:43:11 UTC 2025
snmpwalk: Authentication failure (incorrect password, community or key)

[root@appliance-1(R10900-R84-S35):Active] ~ # tail -f /var/F5/system/log/snmp.log
<...>
<INFO> 10-Apr-2025::13:43:11.855 R10900-R84-S35 confd[158]: snmp get-request reqid=1946931591 10.155.104.147:41112
<INFO> 10-Apr-2025::13:43:11.855 R10900-R84-S35 confd[158]: snmp report reqid=1946931591 10.155.104.147:41112 (1.3.6.1.6.3.15.1.1.4.0=0)
<INFO> 10-Apr-2025::13:43:11.866 R10900-R84-S35 confd[158]: snmp report reqid=0 10.155.104.147:41112 (1.3.6.1.6.3.15.1.1.5.0=2)

Environment

  • Restoring a database backup that contains an SNMP user.
  • Doing the restore on a system with a different SNMP Engine ID.

Cause

ID1812497.

Recommended Actions

  1. Once backup is restored, enter SNMP user passwords manually via F5OS GUI or CLI.
  2. Change SNMP engine ID on the target device:

    appliance-1(config)# system snmp engine-id config value
    Possible completions:
    <string, min: 5 chars, max: 27 chars> ipv4 ipv6 mac

    Note: this would require an administrator to compare SNMP engine ID in confd and in the backup, before loading the backup.
