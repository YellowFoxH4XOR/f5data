K000137129: The designated standby BIG-IP Next instance is removed from BIG-IP Next Central Manager when the attempt to create HA fails

Description

When you attempt to setup High Availability (HA) between two BIG-IP Next instances in the BIG-IP Next Central Manager UI and the HA setup fails, the designated standby BIG-IP Next instance is removed from the BIG-IP Next Central Manager.

Environment

  • BIG-IP Next instances
  • BIG-IP Next Central Manager

Cause

During the HA setup, the BIG-IP Next Central Manager resets the designated standby BIG-IP Next configuration to factory defaults including the admin password. This effectively removes the designated standby BIG-IP Next instance from the BIG-IP Next Central Manager.

Recommended Actions

To add the removed BIG-IP Next instance back to the BIG-IP Next Central Manager, you must first set a new password for the admin user of the BIG-IP Next instance before adding it back to the BIG-IP Next Central Manager.

To set a new password for the admin user of the BIG-IP Next instance, you can use the following curl command to the BIG-IP Next REST API on a workstation with curl utility:

curl -sku admin:admin -H "Content-Type: application/json" -X PUT https://<BIG-IP Next management IP>:5443/api/v1/me -d '{ "currentPassword": "admin", "newPassword": "<your new admin user password>" }'

For example,

curl -sku admin:admin -H "Content-Type: application/json" -X PUT https://192.168.86.52:5443/api/v1/me -d '{ "currentPassword": "admin", "newPassword": "myNewPassword" }'

After you have set a new password for the admin user successfully, you can then proceed to the BIG-IP Next Central Manager to add the BIG-IP Next instance. You can either use the BIG-IP Next Central Manager UI or the BIG-IP Next Central Manager REST API to add the BIG-IP Next instance.

To use the BIG-IP Next Central Manager REST API to add the BIG-IP Next instance, perform the following procedure on a workstation with curl and jq utilities:

  1. Login to the BIG-IP Next Central Manager REST API using the following command syntax:

    curl -sk -H "Content-Type: application/json" -X POST https://<Central Manager management IP>/api/login -d '{ "username": "admin", "password": "<Central Manager admin user password>" }' | jq -M .

    For example:

    curl -sk -H "Content-Type: application/json" -X POST https://192.168.1.181/api/login -d '{ "username": "admin", "password": "MyPassword" }' | jq -M .

  2. The command should return a response containing the access token. You will need to extract the access token for the next step.
  3. Add the BIG-IP Next instance to the BIG-IP Next Central Manager using the following command syntax:

    curl -sk -H "Content-Type: application/json" -H "Authorization: Bearer <access token from previous step>" -X POST https://<Central Manager management IP>/api/device/v1/inventory -d '{ "address": "<BIG-IP Next instance management IP>", "port": 5443, "device_user": "admin", "device_password": "<BIG-IP Next instance admin user password>", "management_user": "admin-cm", "management_password": "<management user password>" }' | jq -M .

    For example:

    curl -sk -H "Content-Type: application/json" -H "Authorization: Bearer YRMBb<truncated for brevity>R8A==" -X POST https://192.168.1.181/api/device/v1/inventory -d '{ "address": "192.168.86.52", "port": 5443, "device_user": "admin", "device_password": "MyNewPassword", "management_user": "admin-cm", "management_password": "MyMgmtPassword" }' | jq -M .

    The command should return an output containing the task ID similar to the following example:

    {
      "_links": {
        "self":{
          "href":"/v1/discovery-tasks/0a7dfe7b-c75b-486f-af81-c92e582377dd"
        }
      },
      "path":"/v1/discovery-tasks/0a7dfe7b-c75b-486f-af81-c92e582377dd"
    }

  4. To query the status of the task, enter the following command syntax:

    curl -sk -H "Content-Type: application/json" -H "Authorization: Bearer <access token from previous step>" https://<Central Manager management IP>/api/v1/system/tasks/<task ID> | jq -M .

    For example:

    curl -sk -H "Content-Type: application/json" -H "Authorization: Bearer YRMBb<truncated for brevity>R8A==" https://192.168.1.181/api/v1/system/tasks/0a7dfe7b-c75b-486f-af81-c92e582377dd | jq -M .

    If the task completes successfully, the command should return an output reporting the state of the task as discoveryDone and the status of the task as completed similar to the following example:

    {
      "_links": {
        "self": {
          "href": "/api/v1/system/tasks/0a7dfe7b-c75b-486f-af81-c92e582377dd"
        }
      },
      "created": "2023-10-03T08:41:07.121264Z",
      "duration_ms": 0,
      "failure_reason": "",
      "id": "0a7dfe7b-c75b-486f-af81-c92e582377dd",
      "name": "discover 192.168.86.52",
      "state": "discoveryDone",
      "status": "completed",
      "updated": "2023-10-03T08:41:16.093049Z"
    }

    If the task is pending your verification and acceptance of the new instance certificate, the command should return an output reporting the state as discoveryWaitForUserInput similar to the following example:

    Note: Starting in BIG-IP Next Central Manager 20.2.0, the system now requires that you verify and accept the certificate of the instance you are attempting to discover and bring under management.

    {
        "_links": {
            "self": {
                "href": "/api/v1/system/tasks/ef23bca9-83ba-448a-84b7-4000f47a1631"
            }
        },
        "created": "2024-04-17T08:12:46.482905Z",
        "duration_ms": 0,
        "id": "ef23bca9-83ba-448a-84b7-4000f47a1631",
        "name": "discover 10.201.61.134",
        "state": "discoveryWaitForUserInput",
        "status": "running",
        "updated": "2024-04-17T08:12:46.550763Z"
    }

    If you see this state, you must perform the next step.

  5. If the state of the task is discoveryWaitForUserInput, you must enter the following command syntax to accept the certificate of the new instance:

    curl -sk -H "Content-Type: application/json" -H "Authorization: Bearer <access token from previous step>" -X PATCH https://<Central Manager management IP>/api/v1/discovery-tasks/<task ID> -d '{ "is_user_accepted_untrusted_cert": true }'

    For example:

    curl -sk -H "Content-Type: application/json" -H "Authorization: Bearer YRMBb<truncated for brevity>R8A==" -X PATCH https://192.168.1.181/api/v1/discovery-tasks/ef23bca9-83ba-448a-84b7-4000f47a1631 -d '{ "is_user_accepted_untrusted_cert": true }'

    The command should return the HTTP status code of 204 with No Content. If you perform step 4 to query the status of the task, you should now see that the discovery process proceeds to other stages and finally report the state of the task as discoveryDone and the status of the task as completed.
