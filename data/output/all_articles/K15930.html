Topic

This is an overview of general Virtual Clustered Multiprocessing (vCMP) configuration considerations; it is intended as a starting point for gathering vCMP information. However, because each environment introduces its own set of variables, consider the article as informational suggestions or recommendations, unless specifically indicated as a requirement. F5 recommends that you evaluate the information as it applies to your configuration and environment.

Description

The following statements describe vCMP hosts and guests:

  • vCMP hosts are the system-wide hypervisors that enable users to create, view, and manage all vCMP guests on the system. A vCMP host allocates system resources to vCMP guests as needed.
  • vCMP guests are objects that users create on vCMP host systems, to run one or more BIG-IP modules. A vCMP guest consists of a TMOS instance, and one or more BIG-IP modules. Each vCMP guest has its own share of hardware resources that the vCMP host allocates to it, allowing each vCMP guest to function like a separate BIG-IP device.

Recommendations

During configuration, vCMP guests should generally be treated as miniature implementations of the type of platform they are on. For example, a vCMP guest on an appliance platform should be configured as a small-scale appliance platform. Likewise, vCMP guests on a VIPRION platform should be configured as small-scale VIPRION platforms.

License considerations

Each guest inherits the license of the vCMP host, and the host license must include all BIG-IP modules that you plan to provision on vCMP guest instances.

Disk management

When planning disk management for a vCMP host, if you plan to install multiple software versions on different slots, you should ensure that you allocate enough disk space for the vCMP host volumes to support the installation of the additional slots. Normally, the default values allocated are sufficient. However, if required, additional disk space must be reserved before the host system is provisioned for the vCMP feature. Attempting to resize disks later can produce unexpected results. If you must specify additional disk space to be reserved for accommodating expanding volume sizes, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Go to System > Disk Management.
  3. Select the logical disk name you wish to modify (for example, HD1).
  4. Change the Reserved (MB) value to the new value.
  5. Select Update.

Provisioning

When provisioning for vCMP, the vCMP host system is provisioned for only vCMP (Dedicated). You must provision individual product modules within the vCMP guest.

Important: Prior to provisioning vCMP, any previously created BIG-IP module configuration elements, such as any BIG-IP LTM virtual servers, pools, or profiles, should be deleted from the configuration. BIG-IP module configuration elements left in place on the vCMP host could disrupt communication with configurations created within a vCMP guest.

VLAN considerations

When configuring VLANs for vCMP systems, take note of the following considerations:

  • VLANs and interfaces are configured on the vCMP host (hypervisor) system. The configured VLANs are then available for selection on the vCMP guest system as needed.
  • Guests inherit the VLAN name and VLAN tag ID. Custom settings for other VLAN options, such as maximum transmission unit (MTU), Auto Last Hop, sFlow Polling interval made on the vCMP host, will not be inherited by the vCMP guest and must be configured on the vCMP guest system.
  • vCMP host VLANs that reside in a partition other than Common or a non-default route domain will not be inherited by the vCMP guest and must be created on the vCMP guest system manually.

    Note: Each guest's traffic is separate from other guests; it is very rare that a route domain would be required or add any functionality. For information, refer to K15336: Moving an inherited VLAN to an alternate partition in a vCMP guest.

  • If multiple guests each use a VLAN group, verify that the VLAN group for each guest does not bridge the same two VLANs.
  • When using the same VLAN across multiple blades, in order to avoid Spanning Tree Protocol (STP) issues or other potential routing loop issues, you should configure the blade interfaces into a trunk and assign the trunk to the VLAN. You can then select the VLAN on the vCMP guest system.
  • If a VLAN is created within a given single vCMP guest, it will only be visible and accessible via that specific vCMP guest. Any other vCMP guests, and the vCMP host, will not be able to see or access that guest's VLAN. 

Management IP addresses

In addition to the cluster IP address, each blade should have its own unique cluster member IP address; this is recommended for both the host and guest systems. For example, if you have two guests that span four blades, you should have a cluster IP address for the host and also a cluster member IP address for each individual blade on the host. Then, within the guest, you should have a cluster IP address and a unique cluster member IP address for each blade in the guest. This configuration improves failover capabilities and communication within the chassis/blades.

VIPRION chassis master key considerations

If a user configuration set (UCS) archive file is originally taken from a vCMP guest running on a blade, and is reinstalled to the same vCMP guest running on the same blade, but the blade has been inserted into a different chassis, the vCMP guest will fail to load its configuration and also reports an error message to the /var/log/ltm file, similar to the following example:

mcpd[19819]: 01071027:5: Master key OpenSSL error: 19819:error:06065064:digital envelope routines:EVP_DecryptFinal_ex:bad decrypt:evp_enc.c:330:

Note: If the device is in appliance mode then you can configure the basic self IP, network information, setup device group and synchronize from the other device in the pair.

To avoid this situation, you can specify the master key for your system to use. Then, in the event of a Return Materials Authorization (RMA), you can specify the same master key on the new chassis. However, you must create the master key before creating any vCMP guests. To create the master key, perform the following procedure:

  1. Log in to the TMOS Shell (tmsh) by entering the following command:

    tmsh

  2. Enter the following command:

    modify sys crypto master-key prompt-for-password

  3. At the Enter password: prompt, enter the desired password.
  4. Confirm the password.

Important: If your configuration contains DNSSEC keys and you are using a software version earlier than BIG-IP 16.0.0, do not use tmsh modify sys crypto master-key prompt-for-password. Instead use the workaround provided in BUG ID 639606.

If a chassis RMA is ever required, you must perform the procedure using the same password on the new chassis. Afterwards, UCS files created on the original chassis should install properly.

High availability considerations

When configuring high availability (HA) features for vCMP systems, take note of the following considerations:

  • You should not configure vCMP hypervisor hosts for HA or failover. In addition, you should not configure VLAN fail-safe and other HA features on the host system.
  • If you configure more than one guest on a vCMP host to use the same VLAN, you should avoid using the VLAN fail-safe feature for the guest instances; when a vCMP guest detects a loss of network traffic on the VLAN and attempts to generate VLAN fail-safe traffic, the other guests configured on the same VLAN may respond to the fail-safe requests, which prevents a failover event from occurring.
  • HA device groups are configured on the vCMP guests. Members of a Sync-Failover device group should each run on a separate chassis, and each peer in the device group should have the same number of slots on each chassis. The maximum supported size of a Sync-Failover device group is eight members.
  • Multi-bladed guests require the same failover configuration, similar to a physical VIPRION system. For information, refer to K13915: Configuring network failover for redundant VIPRION systems (11.x - 12.x) or K37361453: Configuring network failover for redundant VIPRION systems (13.x - 15.x).
  • The self IP addresses that you specify per vCMP guest, for configuration synchronization (ConfigSync) and failover, should be the self IP addresses configured on the vCMP guest (not the vCMP host). Similarly, the management IP address that you specify per vCMP guest, for device trust and failover, should be the cluster IP address of the vCMP guest.

Guest virtual console

From the vCMP host, you can use the vconsole command to gain console access to a specific guest by using the following command syntax:

vconsole <Guest Name> <Slot #>

For example, to access a guest named LTM_Guest on slot 1, enter the following command:

vconsole LTM_Guest 1

From within a guest, if you need to switch blades, you can use the ssh command to switch to different slots by using the following command syntax:

ssh <slot name>

For example, to switch from slot 1 to slot 2, enter the following command:

ssh slot2

For more information, refer to K15372: Overview of the vconsole utility.

Local traffic configuration

Local traffic features (such as virtual servers, pools, profiles, etc.) are not configured on the vCMP host, and the Configuration utility on a vCMP host system does not provide for configuration of local traffic features. However, even though tmsh on the vCMP host does not restrict configuration of local traffic features, you should not attempt to do so. To configure local traffic features, you must be logged in to a vCMP guest provisioned with the BIG-IP LTM module.

When making local traffic configuration changes, you should ensure that you are connected to the vCMP guests system's cluster IP address and not directly to an individual cluster member.

Retaining initial guest images

Guest initial image .iso files should be retained on the host system. When loading a UCS file on the host, if the initial image .iso file has been removed, the UCS will fail to load and will indicate that it is waiting for the initial image.

Boot times

A fully bladed VIPRION chassis, with guests, can take up to 20 minutes to completely finish the boot process. You should allow the system ample time to boot and become available before assuming that the system is failing.

Starting and shutting down guests

Before restarting or upgrading a host system, you should perform a graceful shutdown of all guest systems running on the host. To do so, perform the following procedure:

  1. Log in to the host system's Configuration utility.
  2. Go to vCMP > Guest List.
  3. Select the name of the guest system you want to shut down.
  4. For Requested State, select Configured.
  5. Select Update.

RAM allocation

When you create a guest, the guest will provision RAM based on the number of cores you are assigning to the guest.

RAM per core is calculated based on the following:

(total blade memory - management overhead (normally 4-8 GB))/# of cores = RAM per allocated core.

If you need more RAM for the guest, you must add more cores.

For general guidelines about module combination and memory considerations for BIG-IP 11.4.x and later, refer to the release notes for your software version. For information about how to locate F5 product documentation, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Note: In BIG-IP 11.3.0 through 11.5.1, and BIG-IP 11.6.0 through 11.6.0 HF4, vCMP guests with less than 6.5 GB of memory support provisioning for a maximum of two software modules. For more information, refer to K14210: vCMP guests with less than 6.5 GB of memory support a maximum of two provisioned modules for some versions. For information about other versions, refer to K95553400: vCMP guests with more than 4 GB and less than 8 GB of RAM can now provision more than two modules.

vCMP guest disk management

When vCMP guests are deleted, the guest's virtual disk remains on the system. To prevent these unattached virtual disks from consuming disk space over time, you should routinely delete any unwanted virtual disks from the system.

You can delete an unattached virtual disk from the BIG-IP system by performing the following procedure:

  1. Log in to the vCMP host's Configuration utility.
  2. Go to vCMP > Virtual Disk List.
  3. Select the check box next to the virtual disk name you want to delete.
  4. Select Delete.
  5. Select Delete again.

Backing up vCMP host and guests

When backing up vCMP systems, you should create UCS archives on the vCMP host and each of the vCMP guests. The UCS archive files should be saved to a remote location, in addition to the BIG-IP system.

Analyzing vCMP guest performance

Beginning in BIG-IP 11.6.0, the vCMP host can view detailed guest performance statistics such as disk usage, CPU usage, and network throughput using BIG-IP Analytics. The performance statistics on the VCMP host and guest may differ because the host statistics reflect additional overhead to manage the guests. You can use BIG-IP Analytics to view current and trending data regarding vCMP guest resource and network utilization. For procedures and more information, refer to K15684: vCMP hypervisor can use Analytics to analyze vCMP guest performance.

Upgrade considerations

When upgrading vCMP systems, take note of the following considerations:

  • Before upgrading a guest, ensure that the new version supports the hardware and is supported by the vCMP host version. For information, refer to K14088: vCMP host and compatible guest version matrix.
  • Before performing an upgrade, you should reactivate the license on the vCMP host system. The vCMP guests retrieve their license from the host, so you do not need to reactivate the guest licenses.

    Important: Reactivating the vCMP host license will result in a temporary traffic interruption on the guest systems while the license is reactivated on the host system.

  • Before upgrading a host system, you should gracefully shut down the guests by setting the requested state to Configured. You should gracefully shut down one guest at a time.
  • Guests on separate slots can be upgraded at the same time. However, you should ensure that only one upgrade at a time is performed on any one slot. Attempting to upgrade multiple guests on the same slot may cause high CPU utilization and result in watchdog reboots.

Common upgrade questions

Q: Which should I upgrade first, the guests or the hypervisor host?

A: Plan the order for vCMP host/guest upgrades according to the following guidance:

  • To determine host/guest compatibility for your platform, refer to K14088: vCMP host and compatible guest version matrix.
  • If you are upgrading the vCMP system to a version that would temporarily result in the vCMP host and guest running incompatible versions, F5 recommends that you upgrade the guest instance first and then activate the boot location for the newly upgraded guest. Next, on the vCMP host, set the upgraded guest to the Provisioned state. You can then safely upgrade the vCMP host to the new, compatible version. Once you have rebooted the host to the new version, set the vCMP guest to Deployed.
  • For other cases, F5 recommends that you upgrade the host first.

Q: Can I update all of my guests at once?

A: While the system will allow you to upgrade multiple guests at the same time, F5 recommends that you only upgrade one guest, per slot, at a time. If you have multiple guests on separate slots, you can upgrade them at the same time. However, if you have two guests that use blade 1, then upgrade the guests one at a time. This rule also applies to guests that span multiple blades; if there is any overlap, then F5 recommends that you upgrade the guests one at a time.

Q: Are there any requirements for chassis, host, and guest versions?

A: The only requirements are based on the host and guest versions supported by your hardware. For information, refer to K14088: vCMP host and compatible guest version matrix.

Q: If I only plan to upgrade some vCMP guests, and not the host, is it required/suggested to re-activate the license on the host first?

A: While F5 recommends that you always re-activate the host license before performing an upgrade, it is possible to verify the license's service check date to see if re-activation is required. If the service check date is older than the license check date, required by the version that you want to upgrade to, then you must re-activate the license first.

You can view the service check date for a host system's license file by entering the following command (from the host system's command line):

grep -i "service check date" /config/bigip.license

Output appears similar to the following example:

Service check date: 20121010

The format for the service check date is (Year)(Month)(Day). In this example, the service check date is 2012-10-10 or October 10, 2012.

If you tried to upgrade the example system to BIG-IP 11.3.0, which has a license check date of 2012-10-25, the attempts to upgrade would fail until the license is re-activated.

To view the date required by released versions, refer to the License Check Date table in K7727: License activation may be required prior to software upgrade for the BIG-IP or Enterprise Manager system.

Recommended versions

As a general rule, F5 recommends running the most current supported versions. This recommendation is suggested for vCMP configurations as well. Additionally, due to some significant issues that could affect vCMP installations, it is highly recommended that vCMP systems run a minimum of BIG-IP 11.4.0, 11.3.0 HF1, or 11.2.1 HF3 or later. For information, refer to K14330: vCMP hosts with high disk I/O may experience instability.

For a list of supported vCMP host and guest versions by platform, refer to K14088: vCMP host and compatible guest version matrix.

vCMP functionality has expanded with the releases of new versions. You should refer to the release notes for each version for a full list of added functionality. However, the following are significant enhancements by version:

  • BIG-IP 11.2.1 introduces support for B4300 guest access to hardware SSL and compression resources.
  • BIG-IP 11.3.0 introduces the ability to assign guests to specific blades.
  • BIG-IP 11.4.0 introduces a new trunk monitor feature to provide for sub-second failover. Also, support for the VIPRION 4800 platform was added.
  • BIG-IP 11.5.0 introduces support for the VIPRION 2200 platform.
  • BIG-IP 11.6.0 introduces support for traffic being prioritized and dropped selectively using Differentiated Services Code Point, as well as 802.1QinQ support. This version also introduced vCMP virtual disk templates and vCMP guest access to hypervisor ISO images.
  • BIG-IP 12.0.0 introduces support for per-guest SSL rate limiting for certain BIG-IP platforms as well as network rate limiting.
