Description

A pool member can appear disproportionately busy in BIG-IP least-connections selection when cookie persistence keeps many long-lived, mostly idle client connections associated with that member. Backend application counters may show few active requests at the same time because BIG-IP is accounting for open TCP connections, not only current application work.

Environment

  • BIG-IP LTM

Cause

BIG-IP generally load balances connections. With cookie persistence, related client traffic can remain pinned to one pool member, and least-connections-member selection considers existing connection counts when choosing a target for new non-persisted traffic. If clients keep idle sockets open and send periodic TCP keepalives, those flows can remain in the BIG-IP connection table for an extended period.

  • The BIG-IP connection count can stay high while the backend application reports a lower active-request count.
  • Client-side keepalive traffic can refresh idle state and delay connection cleanup.
  • Server-side keepalive probes may help backend socket-liveness checks, but they do not remove the client-side connection concentration that affects least-connections selection.

Recommended Actions

  1. Verify the load-balancing and persistence settings:
    tmsh list ltm virtual <VIRTUAL-SERVER> persist profiles pool
    tmsh list ltm pool <POOL-NAME> load-balancing-mode
    tmsh list ltm profile tcp <TCP-PROFILE> idle-timeout keep-alive-interval
    Confirm whether cookie persistence, least-connections selection, and TCP idle settings match the observed distribution pattern.
  2. Measure connection concentration:
    tmsh show ltm pool <POOL-NAME> members
    tmsh show sys connection ss-server-addr <POOL-MEMBER-ADDRESS> ss-server-port <PORT NUMBER> all-properties
    Look for many idle or long-lived connections concentrated on the same member, especially from a small client population.
  3. Align idle cleanup with client behavior:
    If application requirements allow it, set the effective TCP idle timeout so stale idle sockets close before recurring client keepalives keep them alive indefinitely. Review the persistence timeout and scope at the same time.
  4. Evaluate request-level reuse where safe:
    For HTTP applications that support it, consider a OneConnect profile so BIG-IP can detach server-side connections and make more granular request-level choices. Validate session affinity and application behavior before enabling this change.
  5. Compare counters from the same interval:
    During a controlled test, compare BIG-IP pool member connections with backend socket and request counters from the same time window. If source address translation is used, group backend sockets by the BIG-IP server-side source address.
