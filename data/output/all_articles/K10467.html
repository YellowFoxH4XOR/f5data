K10467: Userland applications on a BIG-IP system cannot connect to hosts in non-default route domains

Topic

Important: Beginning in BIG-IP version 11.1.0, the behavior described in this article no longer applies due to an architectural change in the route domain feature. For more information, refer to K13472: Change in Behavior: Userland applications on a BIG-IP system can now connect to hosts in non-default route domains.

A BIG-IP administrator may be required to run userland diagnostic utilities (such as ping, telnet, ssh, ftp, and curl) against a node or pool member that was added to the BIG-IP system. An issue arises when you try to diagnose a node or pool member that does not reside in the default route domain of the BIG-IP system, as most userland applications are not designed to handle the IP%ID syntax. For example, assuming 10.0.0.2%10 is a node that was added to the BIG-IP system, an administrator is able to use the ping utility against that node, but they are not able to use telnet or SSH to access the node. These applications mistake the IP%ID notation for a hostname, which clearly does not exist and fails to be resolved.

For example:

# ping 10.0.0.2%10
PING 10.0.0.2%10(10.0.0.2%10) 56 data bytes
64 bytes from 10.0.0.2%10: icmp_seq=0 ttl=64 time=2.67 ms
64 bytes from 10.0.0.2%10: icmp_seq=1 ttl=64 time=0.993 ms

# telnet 10.0.0.2%10
telnet: 10.0.0.2%10: Name or service not known
10.0.0.2%10: No address associated with name

Note: You can successfully ping a node in a non-default route domain, because when you enter the ping command on a BIG-IP system, you are actually running a wrapper script. In this case, a Perl script detects the route domain IP%ID notation, translates it to an equivalent IPv6 address, and then feeds it to the ping6 utility.

Workaround

Note: This workaround works only with utilities that support IPv6 addresses.

You can work around this issue by converting the IP%ID notation to an equivalent IPv6 address that can be used by userland applications on a BIG-IP system.

Due to a known issue, the syntax for the IPv6 address is version-specific, as follows:

Important: BIG-IP versions prior to 10.1.0 use the wrong IPv6 address range for the Route Domain feature. For more information, refer to K10511: The BIG-IP system uses the wrong IPv6 address range for the Route Domain feature.

BIG-IP versions prior to 10.1.0

2610:0000:0C10:F501:0000:<Route Domain ID>:<IPv4 IP upper 2 bytes>:<IPv4 IP lower 2 bytes>

BIG-IP versions 10.1.0 through 11.0.0

2620:0000:0C10:F501:0000:<Route Domain ID>:<IPv4 IP upper 2 bytes>:<IPv4 IP lower 2 bytes>

In the example IPv6 address, the <Route Domain ID> entry is the hexadecimal equivalent to the Route Domain ID, and the <IPv4 IP upper 2 bytes> and <IPv4 IP lower 2 bytes> entries are the hexadecimal equivalent to the IPv4 IP address.

For example, with an IP%ID notation of 10.0.0.2%10, the equivalent IPv6 address will be as follows:

BIG-IP versions prior to 10.1.0

2610:0000:0C10:F501:0000:000A:0A00:0002

BIG-IP versions 10.1.0 through 11.0.0

2620:0000:0C10:F501:0000:000A:0A00:0002

The hexadecimal equivalent to the Route Domain ID of 10 is the 000A portion of the address. The hexadecimal equivalent to the IPv4 IP address of 10.0.0.2 is the 0A00:0002 portion of the address (10.0.0.2 = 0A 00 00 02 hexadecimal).

This IPv6 address can now be used with IPv6 compatible utilities, as shown in the following example:

# telnet 2620:0000:0C10:F501:0000:000A:0A00:0002 80
Trying 2620:0:c10:f501:0:a:a00:2...
Connected to 2620:0000:0C10:F501:0000:000A:0A00:0002 (2620:0:c10:f501:0:a:a00:2).
Escape character is '^]'.

Note: For added simplicity, the equivalent IPv6 address can also be represented using the mixed notation. In this case, the last 32 bits of the IPv6 address are filled with the original IPv4 address. The advantage is that only the Route Domain ID needs to be converted to HEX. For example, in BIG-IP versions 10.1.0 and later, 10.0.0.2%10 can also be written as follows:

2620:0000:0C10:F501:0000:000A:10.0.0.2

Important: The main intent of the Route Domain feature is to allow large organizations to deploy identical solutions, featuring overlapping IP addresses, to their customers.

F5 recommends that those services defined globally on the BIG-IP system (such as DNS, NTP, SMTP, SNMP and SYSLOG) use servers that reside either on the management network or Route Domain 0 of the BIG-IP system. These services are userland applications and may not understand the IP%ID notation or be IPv6 compatible to permit the use of the suggested workaround. An example of such a service is the SNMP service. For more information, refer to K12761: BIG-IP snmpd does not respond to SNMP queries or send SNMP traps using an IPv6 address or an address in a route domain other than 0.

F5 also recommends that you configure features such as ConfigSync, Network Failover, and Network Mirroring with IP addresses in Route Domain 0. These high-availability features are also userland processes and do not recognize the Route Domain IP%ID notation.
