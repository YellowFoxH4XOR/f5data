Description

Deploying F5 Distributed Cloud Customer Edge (CE) nodes on AWS manually introduces configuration overhead, inconsistency risks, and scaling challenges. A Terraform-based Infrastructure as Code solution enables teams to deploy CE nodes on AWS in a consistent, automated, and scalable way — from single-node proof-of-concepts to multi-node production deployments — using a dual-layer load balancing strategy combining AWS Network Load Balancers (NLB) and F5 Distributed Cloud Virtual Sites.

  • How can F5 Distributed Cloud Customer Edge nodes be deployed on AWS using Terraform automation?
  • How does the dual-layer load balancing strategy using AWS NLB and F5 Distributed Cloud Virtual Sites work?
  • What AWS infrastructure prerequisites are required before deploying F5 XC CE nodes with Terraform?
  • How is the number of CE nodes scaled up or down using this Terraform solution?
  • Why are Virtual Sites used in this architecture and how do they provide abstraction across multiple CE nodes?

Environment

  • Single-node to multi-node CE deployments (1–10 nodes supported)

Architecture Overview

This solution implements a dual-layer load balancing strategy:

  • Layer 1 — AWS NLB: Provides cloud-native Layer 4 distribution across CE nodes, AWS-native health checking, cross-zone load balancing, and AWS Shield Standard DDoS protection. CE nodes are not directly exposed to the internet.
  • Layer 2 — F5 XC CE + Virtual Sites: Provides application-layer security (WAF, Bot Defense, API Protection, Rate Limiting), advanced traffic management (A/B testing, canary deployments, application load balancing), and multi-cloud connectivity. Virtual Sites provide unified configuration and policy enforcement across all CE nodes regardless of physical location or count.

Prerequisites: AWS Infrastructure Setup

This Terraform solution follows a bring-your-own-infrastructure model. The following AWS components must exist before deployment:

  1. VPC with DNS support: 
    aws ec2 create-vpc \
  --cidr-block 10.0.0.0/16 \
  --enable-dns-hostnames \
  --enable-dns-support \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=my-vpc}]'
  2. Three-tier subnet architecture:
    • Public Subnet: Hosts the NAT Gateway and optionally the NLB.
    • Outside Subnet (Private): Connects CE SLO interfaces with NAT Gateway routing for internet access.
    • Inside Subnet (Private): Handles internal workload traffic via CE SLI interfaces.
  3. NAT Gateway for CE outbound access: 
    aws ec2 allocate-address --domain vpc
aws ec2 create-nat-gateway \
  --subnet-id subnet-public-xxxxxxxxx \
  --allocation-id eipalloc-xxxxxxxxx
  4. Route Table Configuration:
    SubnetDestinationTargetPurpose
    Public0.0.0.0/0IGWInternet access
    Outside0.0.0.0/0NAT GatewayCE outgoing internet access
    Inside10.0.0.0/16LocalVPC internal traffic

Prerequisites: F5 Distributed Cloud

  1. Generate an API Certificate (P12) from the F5 XC Console following the official documentation.
  2. Locate the latest F5 XC CE AMI for the target AWS region: 
    aws ec2 describe-images \
  --region your-region \
  --filters "Name=name,Values=*f5xc-ce*" \
  --query "reverse(sort_by(Images, &CreationDate))[0].ImageId" \
  --output text

Step 1: Clone the Repository

git clone https://github.com/veysph/Prod-TF.git
cd Prod-TF/Virtual\ Site/f5xc-ce-aws
cp terraform.tfvars.example terraform.tfvars

Step 2: Configure terraform.tfvars

Edit terraform.tfvars with values specific to your AWS environment and F5 XC tenant:

# AWS Infrastructure References
vpc_name                = "your-vpc-name"
outside_subnet_name     = "your-outside-subnet-name"   # Private subnet with NAT route
inside_subnet_name      = "your-inside-subnet-name"    # Private subnet for workloads
nlb_public_subnet_name  = "your-public-subnet-name"    # Public subnet for NLB
aws_region              = "your-aws-region"
aws_ssh_key             = "your-ssh-key-name"
aws_f5xc_ami            = "ami-xxxxxxxxxxxxxxxxx"

# F5 XC Configuration
f5xc_ce_site_name       = "your-site-name"
f5xc_api_url            = "https://your-tenant.console.ves.volterra.io/api"
f5xc_api_p12_file       = "/path/to/your/api-creds.p12"

# Scaling and Features
num_ce_nodes            = 1     # Deploy 1-10 nodes
deploy_nlb              = true
create_f5xc_virtual_site = true
create_f5xc_loadbalancer = true

Step 3: Execute Deployment

terraform init
terraform plan
terraform apply

Scaling CE Nodes

To scale the number of CE nodes after initial deployment, update the num_ce_nodes variable in terraform.tfvars and re-apply:

terraform apply

New CE nodes automatically join the Virtual Site based on label matching and begin receiving traffic through the NLB without any DNS changes or manual configuration.

Additional Information

Understanding Virtual Sites in this Architecture

A Virtual Site in F5 Distributed Cloud is a logical abstraction that groups multiple CE sites together, creating a unified distributed application delivery fabric. In this deployment:

  • Location Abstraction: Configuration is pushed uniformly to all CE nodes regardless of their physical location or count. You do not need to update individual CE configurations as nodes are added or removed.
  • Label-Based Membership: CE sites automatically join the Virtual Site based on label matching. For example, any CE site with the label environment=production automatically joins the production Virtual Site: 
    f5xc_vsite_key       = "environment"
f5xc_vsite_key_label = "production"
  • Multi-Region and Multi-Cloud: A single Virtual Site can span CE nodes across AWS US-East, AWS US-West, AWS EU-Central, Azure, and on-premises data centers simultaneously, while maintaining a single configuration interface.

Why AWS NLB and F5 XC CE Together?

Each layer addresses different responsibilities:

  • AWS NLB: Ultra-low latency Layer 4 distribution, cross-zone load balancing, AWS Shield Standard DDoS protection, CloudWatch integration, and CE health checking at Layer 4. CE nodes are not directly exposed to the internet.
  • F5 XC CE: Application-layer security (WAF, Bot Defense, API Discovery, API Protection, Rate Limiting), advanced L7 traffic management (A/B testing, canary deployments, path-based routing), and multi-cloud networking connectivity.
