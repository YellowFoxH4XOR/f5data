Description
Upon upgrading from an earlier version to 13.1.5, 14.1.4.6, 15.1.5.1, 16.1.2.2 and 17.0.0 (or later version in respective branches), you can see iControl REST returning 401 Unauthorized response for every API call originating from behind a proxy. These are the versions consisting of a fix for K55580033: iControl REST vulnerability CVE-2022-35728. As part of enhancing security protections on the product, a new database variable httpd.matchclient was introduced in these versions and this enforcement can result in API calls coming through a proxy can be rejected in an undesired manner. This article covers what causes that and how to overcome it.

Environment

  • Remote users issuing API calls through a proxy to the BIG-IP
  • sys db httpd.matchclient configured as true (default)
  • Upgrading from a previous version to one of these (or later) versions: 13.1.5, 14.1.4.6, 15.1.5.1, 16.1.2.2 and 17.0.0

Cause

The API calls originating through a proxy fail with 401 Unauthorized response. F5 Product Engineering is tracking this as a known issue at ID1110893. You can enable httpd debugging with the following commands:
tmsh modify /sys syslog local6-from debug
tmsh modify /sys httpd log-level debug
tmsh restart sys service httpd
tmsh restart sys service syslog-ng

When the failure occurs, the following messages would be logged within /var/log/httpd/httpd_errors log file:
Jul 12 12:03:39 bigip debug httpd[23262]: [auth_pam:debug] [pid 23262] mod_auth_pam.c(2462): [client 198.51.100.58:7999] AUTHCACHE Token client (10.10.10.10, 10.154.100.26) and current client mismatch (10.10.10.10)
Jul 12 12:03:39 bigip debug httpd[23262]: [auth_pam:debug] [pid 23262] mod_auth_pam.c(2462): [client 198.51.100.58:7999] AUTHCACHE Token client (10.10.10.10, 10.154.100.26) and current client mismatch (10.10.10.10)

The token gets created by accounting for both the original client (10.154.100.26) and proxy address (10.10.10.10). When the client returns by utilizing the provided token, the original client IP isn't accounted for and that results in a mismatch, which subsequently ends in the API calls being rejected due to this bug.

You can disable httpd debugging with the following commands:
tmsh modify /sys httpd log-level warn
tmsh modify /sys syslog local6-from notice
tmsh restart sys service httpd
tmsh restart sys service syslog-ng

Recommended Actions
The workaround is to disable the httpd.matchclient db variable, which would revert the behavior back to how things worked in versions prior to 13.1.5, 14.1.4.6, 15.1.5.1, 16.1.2.2 and 17.0.0 in respective branches, until a fix can be introduced for ID1110893. If there is interested in obtaining a fix through an Engineering Hotfix before it can be fixed in a GA release code, please open a service request with F5 Support.
