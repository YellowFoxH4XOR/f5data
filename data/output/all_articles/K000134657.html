K000134657: Aspen Mesh Metrics Collector POD in OOMKilled crash loop during startup

Type
Support Solution
Published
2023-05-25
Updated
2023-07-19
Applies to
  • Aspen Mesh: 1.9, 1.11, 1.14
Source
https://my.f5.com/manage/s/article/K000134657

Description

The aspen-mesh-metrics-collector POD is being OOM killed by the cluster and "metrics-collector" container stays in not-healthy status. This behavior could indicate that Prometheus cannot allocate enough memory to repeat WAL files.

> kubectl get pods --selector app=aspen-mesh-metrics-collector -n istio-system
NAME                                            READY   STATUS    RESTARTS   AGE
aspen-mesh-metrics-collector-6cd99f6857-rs674   2/3     Running   0          6d21h


Environment

Aspen Mesh 1.9.x, 1.11.x, 1.14.x,


Cause

In busy clusters, with many prometheus targets, the size and number of WAL files may consume gigabytes of data. Aspen Mesh Metrics Collector does not set any limit for size of WAL files.
WAL files are stored in metrics-collector on persistent volume mounted to the POD via persistent-volume-claim.
The filesystem is not cleaned up in case the POD is being restarted. Prometheus tries to repeat all existing WAL files, and load them into memory, during the startup to prevent data loss.
As a result of this process, the memory consumption of the POD might increase drastically, even to gigabytes in busy clusters, and this might result of reaching the memory limit for the POD.


Recommended Actions

The possible workarounds for the problem are:

  1. Assign more memory to the POD
  2. Remove existing WAL files from the persistent volume mounted to aspen-mesh-metrics-collector POD.
NOTE: Removing WAL files will result in losing data from maximum 2 hours (by default, unless modified).

Depending on the number of metrics scraped by Prometheus and the number of PODs in Aspen Mesh, Prometheus might need even 10-20 GBs of memory assigned to the POD.

To remove existing WAL files from the storage the user may use a temporary toolbox POD with shell access to the container.
Below is an example POD spec that can be used for this purpose:

apiVersion: v1
kind: Pod
metadata:
  name: test-pod
  namespace: istio-system
  annotations:
    sidecar.istio.io/inject: "false"
spec:
  containers:
  - image: busybox:1.28
    command:
      - sleep
      - "3600"
    imagePullPolicy: IfNotPresent
    name: multitool
    volumeMounts:
    - mountPath: /metrics-collector/tsdb
      name: datastore
  restartPolicy: Always
  volumes:
  - name: datastore
    persistentVolumeClaim:
      claimName: aspen-mesh-metrics-collector


The aspen-mesh-metrics-collector deployment has to be scaled to 0 instances before creating the toolbox POD because a persistent volume cannot be mounted to multiple PODs running at the same time.

> kubectl scale deployment -n istio-system aspen-mesh-metrics-collector --replicas 0
deployment.apps/aspen-mesh-metrics-collector scaled


The persistent volume is mounted under "/metrics-collector/tsdb" directory.
Once the POD is up and running the user can exec to the POD shell and remove WAL files from "/metrics-collector/tsdb/wal" directory.

All files need to be removed from the directory:

/multitool $cd /metrics-collector/tsdb/wal
/multitool $ ls -ls /metrics-collector/tsdb/wal
total 54008
 26976 -rw-r--r--    1 nobody   nogroup   27623424 Feb  6 11:00 00000551
 26976 -rw-r--r--    1 nobody   nogroup   27623424 Feb  6 13:00 00000552
    52 -rw-r--r--    1 nobody   nogroup      49301 Feb  6 13:00 00000553
     4 drwxr-sr-x    2 nobody   nogroup       4096 Feb  6 13:00 checkpoint.00000550
 
/multitool $rm -f ./*


Once the WAL files are removed we can remove test-pod and scale metrics-collector deployment back to 1:

> kubectl delete pod test-pod -n istio-system
> kubectl scale deployment -n istio-system aspen-mesh-metrics-collector --replicas 1
deployment.apps/aspen-mesh-metrics-collector scaled


All containers should be healthy now:

> kubectl get pods --selector app=aspen-mesh-metrics-collector -n istio-system
NAME                                            READY   STATUS    RESTARTS   AGE
aspen-mesh-metrics-collector-6cd99f6857-rs674   3/3     Running   0          6d21h


Additional Information

The amount of data scraped and stored by aspen-mesh-metrics-collector (prometheus instance) might be significant for big clusters with many meshed workloads.
Aspen-mesh-metrics-collector is based on Prometheus 2.23.0 release.
"--storage.tsdb.retention.size" flag limiting the total size of storage is considered experimental in Prometheus 2.23.0.
Prometheus keeps the current block of incoming samples in memory and stores them in write-ahead log files, called WAL files, to protect data from loss in case of a crash or restart.
Write-ahead log files are stored in the 'wal' directory in 128MB data segments. WAL files contain raw data that has not yet been compacted.
Wal directory is mounted in aspen-mesh-metrics-collector to "/metrics-collector/tsdb/wal" location.
Prometheus will retain a minimum of three write-ahead log file, or more, in order to keep at least two hours of raw data.
More information about WAL files can be found on Prometheus documentation.
