Description

This article offers explanations to some peculiar questions around Disk Storage, Tenant Disk Allocation, and Resource Limits on F5OS systems.

Environment

  • Tenants deployed on F5OS systems

Cause

N/A.

Recommended Actions

1. Why does the "Available Storage" field display a smaller value (e.g., 455 GB) than the physical SSD capacity (e.g., 1 TB on r10900/r5900) when no tenants have been created? Shouldn't it reflect the total disk size?
The discrepancy arises because F5OS reserves part of the SSD for essential system operations and over-provisions the disk to enhance performance and reliability. The Available Storage value represents the remaining usable capacity after these allocations. This behavior is governed by design and is documented in K000135513: F5OS platform (rSeries/VELOS) shows different disk size compared to platform data sheet.

2. Does the "Available Storage" field serve any purpose if it cannot accurately reflect the actual storage capacity due to thin provisioning?
Despite not being an absolute limit, the Available Storage field provides a useful guideline for administrators. Thin provisioning allows virtual space to be over-allocated, meaning tenants can be created even when the GUI reports "0 GB" of available storage, as actual disk utilization increases only when tenants consume physical resources. Monitoring disk usage is essential to avoid over-commitment. This is documented within K000140343: What are the minimum and maximum values for Virtual Disk Size when creating and configuring BIG-IP tenants on rSeries?

Furthermore, this is being tracked as bug ID2050173 by Product Engineering to address the misleading display of "0 GB" under certain conditions.

3. Why does the GUI always show a fixed disk size (e.g., 142 GB for T4 tenants) under Tenant Deployments, regardless of vCPU allocation, even though the actual disk usage is dynamically determined by vCPU count via thin provisioning?
The value displayed in the GUI reflects the configured, or requested, virtual disk size set at deployment. This is a predefined quota based on the image type and is not adjusted in real-time by vCPU allocation. The fixed value is intentional to establish clear administrative boundaries and simplify resource management.

4. How were the maximum tenant limits per appliance (outlined in F5 article K45191957) determined, given that more tenants can technically be created with thin provisioning?
The maximum tenant limit is determined by the minimum resource requirements (vCPU, memory, and disk) for each tenant image type, as well as the total available system resources and validated configurations. The figures detailed in K45191957: Overview of the BIG-IP tenant image types reflect supported, tested, and recommended deployments to ensure reliable operational performance in production environments.

5. What is the role of the "Minimum virtual disk size" field in deployment documentation, given that deployments below this size are blocked and thin provisioning dynamically allocates disk space based on vCPU allocation?
The "Minimum virtual disk size" serves as a safeguard to guarantee tenants have sufficient space to function effectively based on the requirements of the chosen image type. This lower limit ensures proper operation and prevents misconfiguration that could lead to tenant failures. It is independent of disk allocation based on vCPU count.
