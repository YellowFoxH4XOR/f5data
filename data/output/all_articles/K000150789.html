Description

A web application with legitimate file upload functionality experiences constant blocking from F5® Distributed Cloud (XC) WAF, often from different signature IDs.  How can XC WAF be configured to reliably permit these file uploads?

Environment

  • F5® Distributed Cloud (XC) WAF
  • F5 XC Service Policies

Cause

File upload content contains binary data patterns that match WAF signature IDs for potential attacks, causing false positive detections and blocks

Recommended Actions

Context

  • As a WAF is designed to process HTTP, a textual protocol, data types that cannot be parsed as text are prone to unpredictable parsing results which can incur False Positives (FPs). 
  • Files such as PDFs, Word/Excel documents, images and other documents that must be opened in a specific application are binary data, which cannot be parsed as text and therefore cannot be reliably inspected by a WAF.
  • An approximate visualization of the WAF's interpretation of a binary file can be seen by opening such a file in a text editor:

Example of PDF document opened in Notepad++:

 

 

Some of these unreadable character sequences may constitute patterns that match WAF signatures.  A WAF blocking message that triggered on binary POST body content is characterized by:

  1. context: body
  2. non-ASCII characters in the signature matching_info field

Remediation of the FPs isn't as simple as excluding one signature: different binary documents may trigger different signatures in a non-deterministic fashion.

Instead, an exclusion rule is required to skip signature matching on the specific data type.  It would be imprudent to expose the application to file upload attack vectors, it's most important to ensure this exclusion rule is as narrowly targeted as possible.

NOTE: F5 XC support analysts are available to assist with this procedure if you are unsure.

 

Step 1: Collect Required Information

The first step is to collect the information required to define match conditions for the exclusion rule.  As mentioned, it is strongly recommended to ensure these match conditions are as narrow as possible, ideally only applying to the exact file upload location.

The recommended approach is to define the exclusion rule with three match conditions that must all evaluate as TRUE for the exclusion to be enacted.  Those are:

  1. Method
  2. Exact path (or tightly defined regex)
  3. Content-Type header value

The appropriate values for these conditions can be obtained from the security event log.  The first two are presented in the standard view:

 

The Content-Type header value can be found in the JSON view.  Hit the JSON tab on the log record and locate the field:

Common POST methods specified in the Content-Type header for binary file uploads include:

  • multipart/form-data; boundary=---...
  • image/jpeg, image/png, video/mp4, application/pdf and other specific MIME types
  • application/octet-stream

 

The most common of these is Multipart and we'll continue to use it as the demonstrative example.  Because multipart specification in Content-Type header will also contain a random character sequence to define the multipart boundary, matching must be done by regex.

 

Using the screenshots above as example, the exclusion rule match conditions will therefore be:

ElementMatch TypeValue
methodExactPOST
pathExact/repo/upload/uploadFile.php
header Content-Typeregex.*multipart/form-data.*

 

 

Step 2: Create the Service Policy

This type of exclusion requires a Service Policy (SP).  That is because WAF Exclusion Rules on the LB do not support header matching.

To create the SP, from the Web App & API Protection tile navigate to Manage -> Service Policies -> Service Policies and hit Add Service Policies.

Give the SP a name. then click Configure under Rules (Custom Rule List).

Click Add Item to create a Service Policy Rule.

Give the rule an informative name.

Specify Actions.  You will need to hit the Show Advanced Fields slider:

  • Action: Next Policy
  • Select App Firewall Action Type: App Firewall Detection Control

 

When you select App Firewall Detection Control, the frame will expand to present additional WAF exclusion config options.

Specify WAF Exclusion Actions:

  • SignatureID: 0  (this means "all signatures")
  • Context: Body
  • Context Name: leave blank

 

Now, scroll down the page to the Request Match section.  This is where the match conditions are defined.

Specify the Method as POST.

Hit Configure under HTTP Path.

On the resultant screen, enter the upload URL path under Exact Values match.  Optionally, apply Transformers to account for variations in case, encoding, etc.

 

Hit Apply to return to the previous page, which should now look like:

 

Now, configure matching on the Content-Type header.  Hit Add Item under HTTP Headers.

Specify the Header Name as Content-Type (it's case insensitive), leave Match Options as Match Values and enter the regex pattern under Regex Values.

.*multipart/form-data.*

For POST methods other than multipart, adjust the Header match conditions accordingly.

 

Hit Apply several times and Add Service Policy to save it.

 

 

Step 3: Apply the Service Policy to the HTTP LB

Edit Configuration on the HTTP Load Balancer go to Common Security Controls -> Service Policies  and select Apply Specified Service Policies

 

Hit Configure.

NOTE: exact steps will vary if the LB has existing SPs applied.

  • We will need to add two Service Policies to an LB with none already applied. 
  • Adjust accordingly if the LB already has Service Policies applied; the order in which this one is assigned is largely inconsequential provided it's above any Allow action that matches legitimate traffic. 
  • Best practice is to assign WAF exclusion SPs below any enforcing controls.
  • The below assumes an LB with no existing SPs.

 

Hit Add Item so that there are two objects in the list.

For the first SP, select the one we created in the previous step from the drop-down.

For the second SP, select an existing allow-all SP, or use ves-io-shared/ves-io-allow-all if one doesn't exist.

  • Assigning the allow-all SP is necessary because a SP ruleset has a default Deny action if an allow is not matched.
  • 'allow all' does not mean the request is forwarded to the origin without further inspection, it means only that it's allowed by Service Policies, and will be passed to the next module (WAF) for further inspection.

Hit Apply, the Save HTTP Load Balancer.

 

    File Uploads at the specified path should now no longer be blocked by WAF.

     

    Additional Information

    What is Content-Type: multipart/form-data header ?

    The Content-Type: multipart/form-data header is used in HTTP requests to indicate that the request body contains multiple parts, each with its own set of headers. This content type is commonly used for submitting forms that include files and other data, especially in scenarios like file uploads.

    What is the "boundary string" that follow that header?

    • The boundary string is specified in the Content-Type header and is used to delineate the different parts of the request body. For example: 
      Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW
    • Each part of the body is preceded by --boundary, and the final boundary is --boundary--.

     

    See also: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods/POST
