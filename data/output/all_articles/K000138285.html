Description

ICAP not working.

Virtual server is set up for request adaptation. When adapted request returns from ICAP server, an iRule serves an HTTP response to the client via HTTP::respond in ADAPT_REQUEST_RESULT:

when ADAPT_REQUEST_RESULT {
    HTTP::respond 200 content {OK}
}

This results in a connection reset, with a message similar to the following logged to /var/log/ltm:

011f0007:3: http_process_state_prepend - Invalid action:0x107041 clientside (10.1.1.1:59519 -> 172.16.1.1:80) ((null connflow)) (Client side: vip=/Common/http-vs profile=http addr=172.16.1.1 port=80 rtdom_id=0 client_ip=10.1.1.1)

Environment

  • ICAP
  • Content Adaptation

Cause

HTTP::respond in ADAPT_REQUEST_RESULT is not supported. The reset is expected.

Recommended Actions

To avoid this issue, you will need to re-evaluate the virtual server configuration.

An alternative approach is to forward the connection to another virtual server on ADAPT_REQUEST_RESULT:

## iRule on the client VS (not shown) with request-adapt

when ADAPT_REQUEST_RESULT {
    virtual /Common/respond_icap
}

## Responding VS

ltm virtual respond_icap {
    destination 1.2.3.4:http
    ip-protocol tcp
    mask 255.255.255.255
    profiles {
        http { }
        tcp { }
    }
    rules {
        respond_icap
    }
    serverssl-use-sni disabled
    source 0.0.0.0/0
    translate-address enabled
    translate-port enabled
    vs-index 4
}
 
ltm rule respond_icap {
when HTTP_REQUEST {
    HTTP::respond 200 content {OK}
    }
}

Note: This must be tested, and may not work in all deployments.
