K53534549: certificateCustomFields validation for Aspen Mesh upgrade from 1.9.x to 1.11.x

Applies to

Source

Description

This article describes the upgrade procedure and validation steps to confirm Aspen Mesh has been upgraded successfully, as well as the .global.certificateCustomFields field value has been propagated to the newer version.

Environment

  • Aspen Mesh: 1.9.x - 1.11.x
  • Kubernetes: 1.17x - 1.22.x

Cause

None

Recommended Actions

By default, Istio does not populate the Subject field for certificates and this might cause issues since some applications expect to receive either the Subject field or the SAN DNS name extension.

Aspen Mesh developed a solution for this, certificateCustomFields. This feature generates certificates with SAN DNS extensions for workloads based on annotations with the associated service account. This is especially useful for legacy VMs connecting to pods inside the mesh.

This article assumes certificateCustomFields is already in use. For information about how to enable this feature, refer to the Aspen Mesh article Mesh Workload Certificates with DNS and URI SAN entries.

Aspen Mesh version aspenmesh-carrier-grade-1.9.8-am1 is used in the below example, and a demo of working with the sleep application. This application can be found in the Aspen Mesh release folder ../aspenmesh-carrier-grade-1.9.8-am1/samples/sleep/sleep.yaml.

The sleep service account has been modified with the following annotations:

apiVersion: v1
kind: ServiceAccount
metadata:
  name: sleep
  annotations:
   "certificate.aspenmesh.io/customFields": '{ "SAN": { "DNS": [ "test-sleep.example.com", "sleep.example.com" ], "URI": [ "com.example.uuid:cc1bf660-9e35-4169-9bbf-2a893ea2fa5d" ] } }'

To confirm custom DNS and URIs have been added, run the following commands:

$ export SLEEP_POD=$(kubectl get pod -l app=sleep -o jsonpath='{.items[0].metadata.name}')
$ istioctl proxy-config secret $SLEEP_POD -o json | jq '.dynamicActiveSecrets[0].secret.tlsCertificate.certificateChain.inlineBytes' -r | base64 -d | openssl x509 -noout -text

The output of the previous command should show the same values you specified in the service account:

…
X509v3 Subject Alternative Name: critical
DNS:sleep.example.com, URI:spiffe://cluster.local/ns/default/sa/sleep, DNS:test-sleep.example.com, URI:com.example.uuid:cc1bf660-9e35-4169-9bbf-2a893ea2fa5d 
…

Another way to confirm it is working as expected is to run a curl command:

kubectl exec sleep-557747455f-xsxz2 -c sleep -- curl  http://httpbin:8000/headers

…
"X-Forwarded-Client-Cert": "By=spiffe://cluster.local/ns/default/sa/httpbin;Hash=d162c31ef3c438d95ca0b10b85c1f1d0d24d2cd1955ea52fd732559fb7422ee5;Subject=\"\";URI=spiffe://cluster.local/ns/default/sa/sleep;DNS=sleep.example.com;DNS=test-sleep.example.com"
…

This confirms CertificateCustomFields is working as expected.

Upgrade instructions

Prior to following the Aspen Mesh upgrade instruction, it is assumed that you’ve downloaded the desired version, and your working directory is the Aspen Mesh release directory. For information about downloading a release, refer to the Aspen Mesh article Downloading Releases.

The release version is aspenmesh-carrier-grade-1.11.8-am2 in the following example.

Post-upgrade Tasks

To show the upgraded version using Helm, run the command below: 

helm ls -A

The output appears similar to the following example (some of the contents have been omitted):

~/ ? helm ls -A                                                           
NAME            NAMESPACE     ...  STATUS      CHART                       

istio-base      istio-system  ...  deployed    base-1.11.8-am2
istio-cni       kube-system   ...  deployed    istio-cni-1.11.8-am2
istio-ingress   istio-system  ...  deployed    istio-ingress-1.11.8-am2
istiod          istio-system  ...  deployed    istio-discovery-1.11.8-am2

After upgrading, some applications will still be using an older sidecar. It is very important to upgrade sidecars immediately after upgrading.

In this example the sleep deployment will be restarted by entering the following command:

kubectl rollout restart deployment sleep

To confirm that the CertificateCustomFields feature has been propagated correctly, enter the same commands we ran prior to the upgrade:

$ export SLEEP_POD=$(kubectl get pod -l app=sleep -o jsonpath='{.items[0].metadata.name}')

$ istioctl proxy-config secret $SLEEP_POD -o json | jq '.dynamicActiveSecrets[0].secret.tlsCertificate.certificateChain.inlineBytes' -r | base64 -d | openssl x509 -noout -text

Example output:

…
X509v3 Subject Alternative Name: critical
DNS:sleep.example.com, URI:spiffe://cluster.local/ns/default/sa/sleep, DNS:test-sleep.example.com, URI:com.example.uuid:cc1bf660-9e35-4169-9bbf-2a893ea2fa5d 
…

And finally, a curl test:

kubectl exec sleep-557747455f-xsxz2 -c sleep -- curl  http://httpbin:8000/headers

…
"X-Forwarded-Client-Cert": "By=spiffe://cluster.local/ns/default/sa/httpbin;Hash=d162c31ef3c438d95ca0b10b85c1f1d0d24d2cd1955ea52fd732559fb7422ee5;Subject=\"\";URI=spiffe://cluster.local/ns/default/sa/sleep;DNS=sleep.example.com;DNS=test-sleep.example.com"
…

The curl output confirms certificateCustomFields is working as expected after the upgrade.
