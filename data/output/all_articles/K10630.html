Topic

When the BIG-IP system is configured to use the HTTPS monitor to monitor a pool member, and the pool member uses a TCP close handshake rather than the expected SSL close_notify alert to terminate the monitor requests, each SSL monitor instance will remain in the BIG-IP memory approximately 15 seconds longer than required. As a result, when using the HTTPS monitor to monitor a large number of HTTPS pool members that respond in this fashion, the bigd monitor daemon will consume more than the expected amount of memory.

This behavior is expected. The bigd monitor daemon expects the server to properly shut down the SSL session by sending an SSL close_notify alert before closing the TCP connection, in compliance with RFC2246: The TLS Protocol. When the close_notify alert is not seen before the TCP close handshake begins, the BIG-IP system delays its closure of the connection until approximately 15 seconds after the TCP FIN is seen from the server.

Note: Up to 512 connections are maintained on the BIG-IP system in this deferred state. Connections over this limit will be closed immediately.

Note: This issue is not a memory leak. Each additional HTTPS monitor in this deferred state will use additional memory, but once the connection is fully closed, all resources associated with the monitor instance are available to the BIG-IP system.
