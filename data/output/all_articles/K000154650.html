Description

This article provides guidance on common operational and monitoring queries for NGINX Plus managed via NGINX Instance Manager (NIM).

It covers: -

  • Procedures for manually reloading or restarting NGINX Plus instances.
  • Discusses the possibilities and limitations of automated/self-healing reloads using external tools.
  • Clarifies alert notification capabilities within the NIM dashboard.
  • Explains how to configure log forwarding from NGINX Plus to syslog servers for enhanced visibility, including where to place configuration directives in nginx.conf.
  • Options available in NIM for consolidated views across multiple backend instances and describes how users can export aggregated data using the Metrics API.

 

Environment

Product: NGINX Plus

Version: R34

Management Platform: NGINX Instance Manager (NIM)

Operating System: General Linux/Unix environments

 

Cause

  • Automated or self-healing reload/restart is not a native feature of NGINX Plus.
  • The NIM dashboard does not provide built-in mechanisms for alert notifications.
  • Log retention and visibility are not handled within the NIM dashboard; these are managed at the OS level or via external syslog servers.
  • Consolidated data views in NIM are limited to NGINX Plus instance information.

 

Recommended Actions

  1. NGINX Reload/Restart Procedures:
    • Manuals reload is recommended using:  
      sudo nginx -t && sudo service nginx reload
    • Automated/self-healing reloads are not a native feature. Use external tools such as systemd, Kubernetes, or custom scripts to monitor and manage automatic restarts/reloads based on health checks.
  2. Alert Notifications from NIM Dashboard:
    • The NIM dashboard does not have built-in mechanisms for sending alerts or notifications.
    • Consider integrating with third-party monitoring or SIEM solutions for alerting requirements.
  3. NGINX Log Visibility & Retention:
    • Raw access and error logs are not displayed directly in the NIM dashboard.
    • Logs are best managed by configuring NGINX to send them to a syslog server for centralized storage and retention. Example configuration, please consider placing the configuration as the error_log and access_log supported context:  
      error_log syslog:server=unix:/var/log/nginx.sock debug; 
access_log syslog:server=[IP_ADDRESS]:1234,facility=local7,tag=nginx,severity=info;
    • error_log context:  
      Syntax:	error_log file [level];
Default: error_log logs/error.log error;
Context: main, http, mail, stream, server, location
    • access_log context: 
      Syntax:	access_log path [format [buffer=size] [gzip[=level]] [flush=time] [if=condition]];
access_log off;
Default: access_log logs/access.log combined;
Context: http, server, location, if in location, limit_except
    • Refer to official documentation for details: NGINX Logging to Syslog
  4. Consolidated Data Views in NIM:
    1. The NIM dashboard provides consolidated status, health, configuration, and certificate views across all registered NGINX Plus instances.
    2. To export or aggregate this data programmatically, use the NIM Metrics API.
