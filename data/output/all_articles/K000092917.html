Description

Snmpwalk requests that result in large (larger than network MTU) response from BIG-IP may not work over network.

Examples of such requests include virtual server or pool statistics.

In packet capture the traffic can look similar to:

<source IP> <source port> <destination IP> 161 SNMP 94 getBulkRequest <OID>

<destination IP> <source IP> IPv4 1242 Fragmented IP protocol (proto=UDP 17, off=4440, ID=83de)

 

Environment

  • BIG-IP LTM
  • BIG-IP DNS
  • SNMP Walk
  • Virtual server statistics

 

Cause

When the SNMP request arrives (UDP packet) DAG uses UDP ports (default CMP hashing) to create a flow and send the packet to a TMM. Packet is then forwarded to Linux Host.

If the response is then larger than MTU, Linux host replies with a fragment first (MF flag).

Fragment has no ports, so hashing is done by ip only. If the fragment happens to hash to a different TMM (than the original one, from client-side UDP packet) a new flow is then created (instead of the initial flow being used). Which means initial settings (first UDP packet from SNMP request, from client, with client details) are lost.

This behaviour is described by ID948065.

 

Recommended Actions

It is recommended to upgrade to version 17.0 or later.
