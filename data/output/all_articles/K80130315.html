Description

Security policy blocks a JSON request which appears to be well-formed, and shows JSON profile N/A in the request logs.

Messages similar to the following are observed in /var/log/asm:

emerg perl[6640]: 01310003:0: ASM out of memory error: event code X242 Exceeded maximum memory assigned for XML/JSON processing

Furthermore, messages similar to the following are observed in /var/log/ts/bd.log:

Cannot allocate 8192 more bytes for XML parser

Environment

  • JSON
  • Security policy
  • Violations

Cause

This occurs when the XML/JSON parser is out of memory.

Recommended Actions

Increase the amount of memory allocated to the BIG-IP ASM XML processing engine.

  • K10803: Customizing the amount of memory allocated to the BIG-IP ASM XML processing engine

Additional Information

This issue can happen if there are many requests, or large requests that utilize a lot of memory in the XML/JSON parser.
 

1. Usage of the XML memory

XML memory usage will grow until the system has enough buffers allocated to handle peak traffic flow, and then memory usage plateaus. There is no release of the memory that it allocates, outside of a restart of ASM processes. In a normal use case, this never gets out of hand as a correct configuration would only grow with appropriately scanned files, and would \"balance\" over time. The bd daemon will not release memory back to the system until it is restarted. After the failover XML memory usage on the new standby would be still high and only after the bd restart XML memory usage will be released.

2. Usage of XML memory when ASM policy is applied

XML memory usage increasing (or decreasing) after performing changes to security policies is considered to be expected behavior.
If you modify an existing XML/JSON profile of an existing ASM policy, a set of data associated to the profile object will be purged and a new profile object will be created. Parsers belonging to these content profile objects, if it was handling traffic, could most likely have increased associated buffers depending on observed request data size. As the parser gets purged, the associated memory gets freed. The associated buffer of the newly created parser will be the default size.

Multiple XML/JSON profiles (even across different ASM policies) can be unified internally and it can be a single object internally when configuration and schema are identical. In that case, a single XML/JSON profile object is referred by multiple profiles (such as, for example, the Default XML/JSON profiles on each policy), and deleting one of the multiple profiles won't trigger purging the profile object as there are other profiles referring it. Now, whenever one of those XML/JSON profiles is modified, that profile is no longer one of the multiple profiles that have the identical configuration/schema as others, so certain changes are made within the database and in-memory by ASM, and a new profile object will get created unless there is other existing profile that has identical configuration/schema to the configuration of after the change. You would see a slight increase in overall xml memory usage, then depending on traffic this leads to more increase.
