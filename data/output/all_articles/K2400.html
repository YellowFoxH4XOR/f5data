Issue

In a redundant pair of BIG-IP units, you can mirror connections and persistence information from the active unit to the standby unit, so that the standby system is aware of open connections and can resume handling them in the event of a failover. This mirrored information is maintained and communicated by the stateful failover daemon (sfd). On each BIG-IP, the sfd process communicates with the peer unit through the TCP port 1028 on the internal interface of the BIG-IP system.

For more information, refer to K1552: Enabling stateful failover logging.

Troubleshooting

  • Verifying that sfd is running
  • Examining the sfd log files for errors
  • Verifying the sfd connection
  • Verifying sfd communication
  • Verifying user.db values
  • Verifying communication between the active and standby systems
  • Verifying bigdb keys
  • Verifying communication between the active and standby systems

Verifying redundant pair configuration

Verify that both BIG-IPs in the redundant pair have the same configuration.


Verifying that sfd is running

To verify that the sfd process is running, type the following command:

ps -ax | grep sfd

If you do not receive output from this command, the sfd process is not running. If the sfd process is not running, you must restart the sfd process by rebooting the BIG-IP system.


Examining the sfd log files for errors

To view the the sfd log file for errors, type the following command, where <number value> is the number of lines you want displayed:

tail -<number value> /var/log/bigd

For example, to show the last 30 lines in the file, you would type the following command:

tail -30 /var/log/bigd

Verifying the sfd connection

To verify that the sfd process is connected and mirroring on a global basis, type the following command:

b virtual <ipddress:service> mirror show

Two sfd processes should be running on the standby BIG-IP.

Note: The standby unit always has two sfd processes running, but in BIG-IP version 3.0, two sfd processes will also be running on the active BIG-IP system when it is in active-active mode. To determine if the sfd process is running on BIG-IP version 3.0, use the b unit peer show command.

Verifying sfd communication

To verify that the sfd process is sending packets from the active to the standby system through TCP port 1028, type the following command:

tcpdump -ni exp1 port 1028

The sfd process always communicates over the internal interface, which is exp1 in this example.


Verifying the bigdb keys

Using the bigpipe db commands, verify the following keys and their settings:

  • bigpipe db get Common.Bigip.StateMirror.Username

    Should return with admin as the username.
  • bigpipe db get Common.Bigip.StateMirror.PeerListenPort

    The default port is 1028.
  • bigpipe db get Local.Bigip.StateMirror.Ipaddr

    The IP address of this BIG-IP system.
  • bigpipe db get Local.Bigip.StateMirror.PeerIpaddr

    The IP address of the BIG-IP peer unit.

Note: The sfd process defaults to port 1028. If you find it necessary to change this setting for security reasons, change the Bigip.StateMirror.PeerListenPort key value to the port number desired on both systems by typing the following command:

bigpipe db set Bigip.StateMirror.PeerListenPort <IP Port>

Note: Since the sfd process attempts to determine its own internal IP interface address, it is possible that, if the system has multiple network interface cards (NICs), the sfd process has defined the wrong address to use to communicate with its peer. If the internal IP interface address is incorrect, correct it by typing the following command:

bigpipe db set Local.Bigip.StateMirror.Ipaddr <IP address>

Important: Changing any of the values listed above requires a reinitialization of the sfd process. To do so, type the following command:

bigstart reinit sfd

Verifying communication between the active and standby systems

Verify that there is activity between the active and standby system by typing the following command:

b sfstats dump

You can perform the following two procedures to get more information about what one system is sending the other (and to debug):

Method 1: Enabling logging (simplest method)

  1. Use the bigpipe db set command to set a Bigip.StateMirror.StandbyFile key to the path of the desired log file. This behavior will cause the standby sfd process to log the messages it receives to the specified log file.

    Note: For specific instructions about how to set the state mirroring keys, refer to the BIG-IP Reference Guide.
  2. The log file contains raw a data file. To read it, use the BIG-IP /sbin/sfread utility.

    Note: The log file is truncated each time the sfd process starts, usually when the system is booted.

Method 2: Enabling the debug file

  1. Use the bigpipe db set command to set the Common.Bigip.StateMirror.DbgFile key for the debug file path. If you use a relative name, the file is saved in the /var/run directory.

    Note    : For specific instructions about how to set the state mirroring keys, refer to the BIG-IP Reference Guide.
  2. The Bigip.StateMirror.DbgLevel key value contains several bits that can be run together using OR statements. The values of the different bits include the following:
  • Log the number of bytes read and written with each sfd message (noisy)
  • Log connection attempts and results (useful)
  • Log state changes (for example, going from active to standby)
  • Open log files in append mode, the default is to truncate the files when opening.

Note: Running these daemons in debugging mode can cause your disk to fill up quickly. F5 Networks recommends that you monitor the disk space closely, and only to run these commands as long as needed to gather the necessary information.
