Description

SSLO - IP address-based bypass rules may appear not to work for some sites, resulting in a failed handshake seen in pcaps.
 

Environment

SSLO 6.x, 7.x
 

Cause

There are a few different types of bypass in SSLO - eg. SSL-based and IP-based.

Admins need to take care to position (move up/move down by using the drag area beside the rule) any IP-based rules above the default SSL-based "pinners" rule (and any other SSL-based rules they may have created), if they want IP address-based bypass rules to work as expected by looking at the OSI model, ie. that IP address bypasses (OSI layer 3) should be processed before SSL (OSI layer 5/6).

Due to the following reasons an SSL-based rule occurs before an IP-based rule the IP based bypass may fail for some websites:
  • For an SSL-based rule, a bigip-generated TLS client hello is used to collect the server's cert, then if that passes certain checks, the actual client hello from the client (due to bypass) is sent in another tcp stream
  • If the web server won't accept a "standard" bigip-generated client hello for any reason (eg. client cert required, or some specific cipher or other setting required) then this first connection would fail, and the entire connection would be aborted by SSLO.
IP-based bypass normally only checks the client's client hello for very basic things and forwards it on - it doesn't even check for ciphers after the fix for ID774913 - however if the SSL-based rule is before the IP-based rule in the processing order, then the server-cert-collection connection (triggered by the SSL-based rule) needs to succeed before the IP-address based bypass kicks in.
 

Recommended Actions

Ensure that any IP-address-based bypass rules are above the default SSL-based "pinners" rule (and any other SSL-based rules).
