K000161134: APM oAuth Discovery task may not work normally after migration

Description

On BIG-IP APM systems, the OAuth Discovery task for a provider may stop running automatically after a UCS restore or device re-licensing. The task status in the GUI remains "STARTED," but the last run time does not update, and the discovery process does not execute as scheduled. Manual execution of the discovery task allows APM VPN logins to proceed normally. This issue typically affects only the impacted node, while other nodes continue to function as expected.

Environment

  • Product: BIG-IP APM
  • OAuth provider configuration
  • Discovery interval: x minutes
  • Recent actions: UCS restore or device re-licensing, resulting in a change of the device's machine ID
  • No relevant OIDCDiscoverTaskCollectionWorker logs found for the affected period

Cause

A mismatch between the ownerMachineId stored in the OAuth Discovery task’s REST storage and the current device’s machine ID. This mismatch occurs after a UCS restore or re-licensing event, causing the OIDCDiscoverTaskCollectionWorker to silently skip the task during restjavad startup.

Answer/Recommended Actions

To resolve the issue and restore automatic execution of the OAuth Discovery task:

  1. Identify the Task ID for the Affected Provider
    restcurl /tm/access/oidc/discover | python3 -m json.tool | grep -E "id|providerName|ownerMachineId"
  2. Update the Task’s ownerMachineId
    Replace PATCH /tm/access/oidc/discover/<task-id> with the correct HTTP path and use the task ID from the previous step:
    restcurl -X` PATCH /tm/access/oidc/discover/ -d '{"forceRestart":true}'
  3. Verify Task Execution
    Within 5 minutes, check the logs to confirm the discovery task is running:
    grep "OIDCDiscover.*MFA_Azure_Coscon" /var/log/restjavad.0.log
  4. Alternative Solution
    If updating the ownerMachineId does not resolve the issue, recreate the OAuth provider configuration.

Additional Information

  • This issue is specific to scenarios where the device’s machine ID changes (such as after UCS restore or re-licensing).
  • Creating a new provider with the same settings typically results in normal discovery task operation.
  • No error is logged when the task is skipped due to a machine ID mismatch.
