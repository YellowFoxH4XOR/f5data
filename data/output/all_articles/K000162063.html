K000162063: CIS 2.20.4: Pool Members Created in Route Domain 0 Instead of Specified Route Domain

Type
Support Solution
Published
2026-07-03
Updated
2026-07-03
Source

Description

When using F5 Container Ingress Services (CIS) version 2.20.4 with NodePort mode and strict route domain isolation, pool members and node objects may be created in Route Domain 0 (%0) instead of the intended non-default route domain specified for the virtual server (VIP). This results in ingress traffic failing, as strict isolation prevents communication between route domains. The issue is observed after upgrading from CIS 2.20.3 to 2.20.4. Rolling back to CIS 2.20.3 restores correct behavior. No specific error messages are generated, but traffic fails to reach pool members due to route domain mismatch.

Environment

  • F5 Container Ingress Services (CIS) v2.20.4 (Red Hat Operator-deployed)
  • AS3 version 3.54.2
  • BIG-IP platform: F5-BIG-BR-R12600-DS, C138
  • OpenShift clusters using NodePort mode with strict route domain isolation
  • Virtual servers configured with non-default route domains via bigipRouteDomain in the VirtualServer CRD
  • Pool members and node objects expected in the same non-default route domain as the VIP
  • Recent action: Upgrade from CIS 2.20.3 to 2.20.4

Cause

Bug ID CONTCNTR-6573

Answer/Recommended Actions

  • Continue using CIS version 2.20.3 as a workaround until a fix is released in CIS 2.20.5.
  • Avoid restarting or reconciling unaffected clusters running CIS 2.20.4, as this may trigger the same issue.
  • Monitor for the release of CIS 2.20.5 and plan to upgrade once available to resolve the route domain assignment problem.

Additional Information

  • In NodePort mode, CIS creates node objects in the /Common partition, which defaults to Route Domain 0. There is currently no supported mechanism to place node objects in a custom partition or non-zero route domain in NodePort mode.
  • The bigipRouteDomain field in the VirtualServer CRD only affects the VIP destination, not pool members or node objects.
  • This issue does not occur in CIS 2.20.3, and rolling back to this version restores expected behavior.
