Description

Applying logging profiles for Telemetry Streaming to a large number of virtual servers on BIG-IP LTM, especially with ASM enabled, can result in excessive log generation and resource exhaustion. The "bulk" API endpoint for logging profile assignment is only available for the ASM module, not for LTM. Custom scripts used for bulk configuration may cause high CPU utilization.

Environment

  • BIG-IP LTM
  • BIG-IP ASM/AFM
  • A large number of virtual servers requiring logging profile configuration for Telemetry Streaming
  • ASM module present on some or all virtual servers
  • Telemetry Streaming feature enabled

Cause

To properly evaluate platform constraints during high-volume AFM/ASM event generation, we must decouple the transport-layer logging architecture from the control-plane automation framework. These are distinct operational vectors that often get conflated.

1. Data-Plane Logging vs. Control-Plane Middleware

  • High-Speed Logging (HSL): Operates entirely within the TMM data plane. By bypassing the legacy Linux syslog daemon, HSL generates and streams log micro-batches directly from the microkernel traffic engine to external collectors, maximizing throughput and minimizing CPU context switching.
  • Telemetry Streaming Compatibility: HSL and TS are not mutually exclusive; the architecture supports utilizing HSL to push logs into the TS Event Listener endpoint. However, because TS executes via the restnoded daemon, it is strictly bound by the single-threaded CPU and memory allocations inherent to the iApps LX framework. The compatibility of using HSL to send logs to the Event Listener is documented here. 

2. Root Cause Analysis of the Node.js Processing Failure

Telemetry data indicates that the primary constraint is a fundamental product limitation within the Node.js (restnoded) execution environment, rather than management plane resource starvation.

Telemetry Streaming’s Node.js-based architecture is fundamentally unsuited for the sustained, high-velocity event rates generated by ASM/AFM security and request logs in large-scale environments. Under heavy load, the framework experiences severe degradation:

  • Unbounded Memory Retention: The internal event-loop queues accumulate data faster than Node.js can process it, leading to memory exhaustion.
  • Stream Degradation: As memory pressure peaks, the system induces throttling, resulting in dropped log packets and truncated, incomplete JSON payloads.
  • Consumer Concurrency Strain: This processing bottleneck is severely compounded when handling simultaneous push (e.g., Splunk) and pull (e.g., Prometheus) consumers, which forces the single-threaded runtime to duplicate serialization and buffering efforts.
  • Architectural Impact: Migrating the logging source to HSL while retaining TS as the consumer offloads processing overhead from the management plane (systemd-journald/syslogd). However, it fails to remediate the underlying choke point because restnoded remains in the serialization path. To resolve these stability and data integrity issues under high AFM/ASM volumes, Node.js must be bypassed by routing HSL payloads directly to your remote analytics tier.

Answer/Recommended Actions

  • Avoid using ASM Telemetry Streaming logging profiles on a large number of virtual servers due to risk of excessive log generation and resource exhaustion.
  • The "bulk" API endpoint for logging profile assignment is only available for the ASM module, not for LTM.
  • Custom scripts for bulk configuration may cause high CPU utilization and are not recommended for production environments.
  • Consider configuring High Speed Logging (HSL) as a scalable alternative for logging needs.
