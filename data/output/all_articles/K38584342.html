K38584342: How does the EPSEC AV endpoint check, ''last update'' agent calculate dates since last update

Type
Support Solution
Published
2021-05-14
Updated
2025-04-02
Applies to
  • BIG-IP
Source

Description

BIG-IP APM provides a feature to do Endpoint Inspection (EPSEC) of the devices connecting to the APM using libraries from OPSWAT OESIS SDK.

One of those Endpoint checks is for Anti-Virus/Antimalware. In this check, the Virus definition age can be checked by setting the number of 'days' allowed. A device will need to pass this test before being able to connect to the APM. The terms Anti-Virus and Anti-Malware are considered as the same below.

The end devices may start to fail the Endpoint Inspection and be blocked from connecting, then sometime later they will start working again.

Environment

This unexpected behaviour happens when: 

  • Access Policy configured for Network Access, Portal Access or LTM+APM mode.
  • Endpoint Inspection is configured as part of the Access Policy.
  • "DB Age Not Older Than(days)" is set (aka db-age).
  • db-age is set to a small value.
  • This applies to all current BIG-IP versions, all APMClient release, and all Opswat EPSEC releases.

Cause

The failure occurs because of the DB Age Not Older Than(days) test:
  • The frequency of each Vendor issuing updates, and the client successfully downloading those updates, is unpredictable.
  • The times each vendor products check for updates are unpredictable. Some products allow configuring update checks and frequency, some products allow you to schedule a scan, updating the databased before the scan.
  • Some vendors AV products do not report a time, only a date, This is then interpreted as the start of that day  (00:00:00 UTC).
  • AV vendors often display update time in local time zone for users to see.
  • The timestamp reported by a particular vendor and passed to APM does not contain TimeZone information. It is formatted as a Unix Timestamp (number of seconds since 00:00:00 UTC on 1 January 1970).  This is inherently UTC based.

Recommended Actions

Because the variability of the reporting above, the dates reported by clients can be out by over a day, F5 recommends:

  • The db-age test in an Access Policy should not be set to less than 3.
  • A db-age of 7 or 14 is the most common values used.
  • This value may need to be adjusted depending on your experience with a particular vendor updates.
  • Setting db-age as 0 is the default and results in no age checking taking place.
In the TMUI (GUI) help text this is described as

  DB Age Not Older Than(days)
      To check the age of the database, type the number of days.

In the TMSH (CLI) configuration it is set as db-age <number-of-days>

(cfg-sync Standalone)(Active)(/Common)(tmos)#
     modify apm policy agent endpoint-check-software myAP_act_av_software_check_ag items modify { 0 { db-age 7 } } 

apm policy agent endpoint-check-software myAP_act_av_software_check_ag {
    items {
        0 {
            db-age 7
            state enabled
        }
    }
}

 Software Check Agents normally end with the string "_act_av_software_check_ag" preceded by the policy name.
The "state enabled" is the default test that checks that the Anti Malware software is actually running. 
 

Additional Information

The public documentation for all the OPSWAT OESIS SDK methods can be found here: http://software.opswat.com/OESIS_V4/html/c_method.html
In this case we are interested in the values returned by "GetDefinitionState" method and specifically the parameters "source_time" and "last_update". These are found by clicking the "Manageability" tab on the website above.

The "last_update" field is the value when the Antimalware Product successfully performed the last virus/malware definitions update check. If the endpoint reports that it was able to complete the update check successfully (whether that resulted in any updated information, or just a response that "you are up-to-date") then this date is updated.

The “source_time” field is the time when the definitions were made available by the product/vendor. This may be just a date (with the Time value 00:00:00) or a full timestamp. This is the value that F5 checks for db-age.

For both fields, the time is returned in Unix time format and may be displayed as the local time on the machine where the method was run. For both these values, the actual method of checking of these values varies with different products, and some may need privilege escalation.

The SDK also returns an "is_recent" value, that is not currently used by F5. This is hard coded in the library as true for "last_update" if less than 3 days prior. This is used by other users of the SDK.

Converting

$ date  -r 1620336504 ==> Fri  7 May 2021 09:28:24 NZST
$ date -ur 1620336504 ==> Thu  6 May 2021 21:28:24 UTC

So the v3v4 libraries report a date time, and do not record a timezone.
The WaDiagnose only reports a number, "1620336504" but that matches the NZST, showing that the v3v4 libraries are actually returning a local time/date.

When that Windows device connects to a 13.1 APM (which uses the v3v4 bridge)
The value returned as session.check_software.last.av.item_1.db_time is "1620336504".

This confirms the F5 code is not performing any conversion in the reported UTC Time values.

Looking at in identical Windows device running in an India timezone, confirms the data file is being reported as local time (India UTC +5.5 is 6 hours 30 minutes different from New Zealand (UTC +12)

GetDataFileTime, (0 ms) Result: OK Value: 2021/5/7 2:58:24

When that connects to the same APM running 13.1 it reports the same Unix timestamp "1620336504"

To implement the Access Check, the db-age value (number of days) is multiplied by the number of seconds in a day, is added to the reported db_time from the client device (in UTC) and is compared with the current time (in UTC). The check fails if the current time is larger than: 
          db_time + ( db-age * 24 * 60 * 60 ) 

Troubleshooting

When checking the reported db dates, one should also check that the db version is the same as expected. For a given db version, you should always see the same db time.

The article K11643 linked below, details how to obtain, extract and use the OPSWAT diagnosis tools. Checking the output of these tools shows the information that the client side libraries provide directly, before the F5 code passes this to the APM for checking.

When looking in the APM logs these are the variables of interest
session.check_software.last.av.item_1.db_time  
session.check_software.last.av.item_1.db_version
session.check_software.last.av.result

To display these variables in a client session window, insert the following snippet in a message box after the AV test 

Session ID is: %{session.user.sessionid} <br>
db_time is %{session.check_software.last.av.item_1.db_time} <br>
db_version is %{session.check_software.last.av.item_1.db_version} <br>
Result (1 is pass, 0 is Fail) is %{session.check_software.last.av.result} <br>

Warning, be careful if you try to convert from unix time to a user friendly date in the session window, using javascript will run in the browser, and default to client local time. Using TCL to convert for logging, will default to a representation in the APM's local time. Ensure any translation is always maintaining UTC time.

When reporting problem issues with endpoint inspection, it is best to include a screenshot of the product, showing when it says it was last updated, the output of the appropriate OesisDiagnose/WaDiagnose, and the APM log file taken after the product connects (noting the problem sessionID if possible)
