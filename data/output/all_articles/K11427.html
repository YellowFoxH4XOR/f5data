Known Issue

This is the result of a known issue. It is possible to create and apply an iRule which contains an escaped newline character following a suspended command within an if clause. However, when the suspended command is resumed, the escaped newline character causes TMM to miscalculate the memory position from which iRule processing should resume. As a result, the TMM process terminates with SIGFPE, dumps a core file, and logs the following assertion:

notice panic: Invalid saved PC:

Note: For more information about suspended iRules commands, refer to K12962: Some iRules commands may temporarily suspend iRule processing.

In the following example, an escaped newline character was inserted into the log command to make the code easier to read:

when HTTP_REQUEST {
if {[HTTP::cookie "JSESSIONID"] != ""} {
log local0. "Used persistence record from cookie. Existing key? \
[persist lookup uie [string tolower [HTTP::cookie "JSESSIONID"]]]"
}
}

The backslash at the end of the first line escapes the newline character immediately following it, and the interpreter processes both lines together as a single iRule statement. However, since the escaped newline character is followed by the persist command, which suspends iRules processing, and both are wrapped within the conditional 'if' construct, any HTTP request that contains a non-blank JSESSIONID cookie will cause TMM to become unresponsive.

F5 Product Development tracked this issue as ID 224391 (formerly CR135937), and it was fixed in BIG-IP version 10.2.1. For information about upgrading, refer to the BIG-IP release notes.

Workaround

Since newline characters are typically escaped for cosmetic purposes only (to enhance readability of the iRule code), you can work around this issue by editing the iRule to remove all escaped newline characters that precede suspended commands.
