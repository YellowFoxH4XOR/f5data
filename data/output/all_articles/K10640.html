Topic

On a BIG-IP system, in the event that a pool member fails, the default behavior is for connection attempts to that pool member to continue until the pool member is marked down by its assigned monitors. This behavior may cause the BIG-IP system to load balance new connections to a pool member that has just failed, but whose monitor has not yet timed out.

Refer to the following example scenario, in which a BIG-IP system is configured with the http_servers pool:

pool http_servers {
   monitor all http
   members {
      192.168.1.10:http {}
      192.168.1.11:http {}
   }
}

  • The http_servers pool uses the default HTTP monitor, which has an interval of five seconds and a timeout of 16 seconds.

    Note: F5 recommends setting the timeout of custom monitors to three times the chosen interval time, plus one. This particular ratio ensures that more than one health check must fail in order for a pool member to be marked down. For example, with an interval of five seconds and a timeout of 16 seconds, the BIG-IP system must not receive any valid response from a pool member for 16 seconds before it can mark the pool member down. Because in 16 seconds the BIG-IP system runs four health checks against the pool member, all four health checks must fail for the system to consider the pool member down. Ultimately, this configuration prevents the status of a pool member from flapping unnecessarily.

  • The 192.168.1.11:http pool member, last checked by the HTTP monitor at 21:10:00 (HH:MM:SS), is marked up. The 192.168.1.11:http pool member's next health check is not due until 21:10:05.
  • At 21:10:02, the 192.168.1.11:http pool member suffers a failure and becomes unresponsive.
  • At 21:10:03, a new connection arrives to the virtual server using the http_servers pool. The system makes a load balancing decision and load balances the client to the 192.168.1.11:http pool member. This behavior is a valid load balancing decision because the BIG-IP system does not yet recognize that the pool member has failed.
  • The BIG-IP system attempts to establish a TCP connection to the pool member. When this server-side connection fails, the system resets the client's connection.
  • Additionally, the BIG-IP system may also load balance further connections to the 192.168.1.11:http pool member before the HTTP monitor marks it down, which occurs 16 seconds after the BIG-IP system receives the last successful response. The system also resets client connections.

You can change the behavior outlined in the previous example by performing the following actions:

  • Select a new pool member as soon as the BIG-IP system detects that the pool member to which it is attempting to connect has become unresponsive.
  • Immediately mark the unresponsive pool member down to avoid further connections being load balanced to that pool member.

To perform these actions, you can either write an iRule, or, beginning in BIG-IP 10.0.0, you can use features readily available within the Configuration utility.

Changing the default behavior using an iRule

You can change the default behavior with an iRule similar to the following example:

when LB_FAILED {
   if { [active_members [LB::server pool]] > 0 } {
      catch { LB::down }
      LB::mode rr
      LB::reselect
   }
}

This iRule allows a client-side connection to remain open after a pool member has become unresponsive. For example, if the pool member failed to complete a TCP handshake or respond to an ARP request.

Using the LB::reselect iRules command, the client request is then load balanced to a different pool member, or even to a different pool, once the LB_FAILED event fires. The time between the initial connection attempt and LB_FAILED is dependent on profile parameters. For example, in regards to TCP, the profile parameters that affect SYN retransmission.

The LB::down iRules command causes the pool member to be marked down upon the LB_FAILED event rather than wait for its monitors to time out and limit the number of client connections affected. You can write more complex iRules to defer LB::down until a number of failures have occurred to allow a margin of error.

When an iRule marks a pool member down, the BIG-IP system logs a message to the /var/log/ltm file that appears similar to the following example:

  • BIG-IP 11.x and later

    01070638:5: Pool /Common/http_servers member /Common/192.168.1.11:80 monitor status iRule down. [ was up for 0hr:3min:24sec ]

  • BIG-IP 9.x through 10.x

    01070638:5: Pool member 192.168.1.11:http monitor status iRule down.

Note: When the pool member becomes responsive again, the health monitors associated with the pool marks the pool member up.

Changing the default behavior using the Inband monitor feature (10.x or later)

Beginning in BIG-IP 10.x, the Inband monitor type is introduced. The Inband monitor determines the availability of a pool member based on a specified number of failed connection attempts or data request attempts within a specified time interval. This monitor works in parallel with regular monitors, and you can use it instead of the LB::down iRules command.

Note: For more information about the Inband monitor, refer to the Configuration Guide for BIG-IP Local Traffic Management.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

The Inband monitor provides no error handling for in-progress connections. Therefore, it does not replace the LB::reselect functionality. However, beginning in BIG-IP 10.x, you can cause a reselection by using the Reselect Tries advanced pool feature. This feature is equivalent to the LB::reselect iRules command. After the BIG-IP system considers a connection attempt to a pool member as failed (equivalent to the LB_FAILED iRules event), the system selects a new pool member using the load balancing settings of that pool. If that pool member also fails, the system repeats the reselection until it reaches the limit configured for this option. Only at this point does the system reset the client connection.

Note: Do not confuse this feature with the Reselect option under the Action on Service Down advanced pool feature, which manages established client connections by moving them to an alternative pool member when monitors mark the original pool member down. For more information about Action on Service Down, refer to K15095: Overview of the Action On Service Down feature.

As a result, in BIG-IP 10.x and later, you can avoid many failure situations without the need for an iRule since you can use the combination of Inband monitors and the Reselect Tries feature instead of the LB::down iRules command and the LB::reselect iRules command. iRules continue to offer greater flexibility, and you can still use them in combination with these features where a particular behavior is required.
