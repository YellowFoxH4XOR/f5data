K000151484: Failed to upgrade to websocket with 302 Found or 200 OK response instead of 101 Switching Protocols

Type
Support Solution
Published
2025-06-11
Updated
2025-06-11
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.1
Source
https://my.f5.com/manage/s/article/K000151484

Description

After setting up WebSocket pool member on port 443 and tried establishing WebSocket connections through a virtual server, It's not working as expected the connection is failing with errors such as:

org.eclipse.jetty.websocket.api.UpgradeException: Failed to upgrade to websocket: Unexpected HTTP Response Status Code: 200 OK

or

Failed to upgrade to websocket: Unexpected HTTP Response Status Code: 302 Found

 The iRule use a pattern like *.example.com for matching Host Header, but incoming requests included the port in the Host header (e.g.,VIP-TEST.example.com:443). This mismatch caused traffic to be routed to an incorrect pool, resulting in unexpected backend responses (HTTP 200/302 instead of 101). The backend application returned HTTP 404 or 302 responses when it did not recognize the requested path or was not configured for WebSocket upgrades on that path.

 

Environment

  • LTM
  • Web Socket Upgrade
  • VIP on port 443
  • iRule used for pool selection based on Host header
  • Backend application expected to support WebSocket upgrades

 

Cause

Backend application expected to support WebSocket upgrades.

 

Recommendations

  • Update iRule for Proper Host Header Matching:
    • Modify the iRule so it matches both hostnames with and without port numbers:
    • This ensures correct routing of requests regardless of whether ":443" is present in the Host header.
when HTTP_REQUEST {

  switch -glob [HTTP::host] {

    "*.example.com*" {

      pool <Pool_name>

      set FINISHED 1

      return

    }

    default {

      pool <Pool_name>

      set FINISHED 1

      return

    }

  }

}

Note: The iRule used above is an example.

  • Set Response Chunking to Unchunk in HTTP Profile:
    • This prevents addition of a Transfer-Encoding: chunked header, which can interfere with WebSocket handshakes.
  • Verify Backend Application Configuration:
    • Ensure your backend application supports and properly handles WebSocket upgrade requests on all required paths.
    • Test direct access from client to backend (bypassing BIG-IP) and confirm receipt of 101 Switching Protocols.
  • Test Incrementally With Minimal Configuration:
    • Temporarily remove custom iRules and use default profiles.
    • Gradually reintroduce customizations while testing after each change.
  • Use Decrypted Packet Captures for Troubleshooting:
    • Capture decrypted traffic between client, BIG-IP, and backend.
    • Confirm that upgrade requests are routed correctly and that backends respond appropriately (101 Switching Protocols).
