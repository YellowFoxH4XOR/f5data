Description

Installing or upgrading to BIG-IP v17.5.1.6 may fail or leave the new boot location unusable because the /usr logical volume created by the v17.5.1.6 base image can be too small for the installed packages.

This issue can affect physical appliances, VIPRION blades, F5OS tenants, vCMP guests, and BIG-IP Virtual Edition systems. The symptom you observe depends on your platform.

On iSeries appliances with an onboard FIPS HSM (e.g. i5820-DF, i7820-DF, and i15820-DF)

Installation of BIG-IP v17.5.1.6 fails, and the new boot location cannot be activated. The installation status reported by tmsh show sys software status appears as failed (Failed to install.).

/var/log/liveinstall.log log file may contain:
info: RPM: depmod: ERROR: Could not create index 'modules.dep'. Output is truncated: No space left on device
error: rpm transaction failed; 65024
info: Remaining total space is 7266434 KiB
info: 0 KiB free in cpmirror.set.2./usr
info: 324898 KiB free in cpmirror.set.2./
info: 3025516 KiB free in cpmirror.set.2./config
info: 3916020 KiB free in cpmirror.set.2./var
error: Disk full (filesystem volumes). See SOL#10636
error: Package installation failed.

 

On other iSeries appliances (except for i850/i2000/i4000-series)

Installation appears to succeed, but after rebooting into the new boot location, the system is unreachable via SSH. The /usr filesystem has no free blocks.

There will be errors printed on the console along the lines of:
perl: warning: Falling back to the standard locale ("C").
/sbin/setfiles set context /usr->system_u:object_r:usr_t:s0 failed:'No space left on device'

 
i850/i2000/i4000-series appliances do not appear to encounter this problem. These platforms have a smaller footprint, leaving sufficient space in /usr. Even without the issue, these products still belong to the product group below, and the same recommended actions apply.
 

On other platforms (VIPRION blades, F5OS tenants, vCMP guests, and BIG-IP Virtual Edition systems)

The /usr volume shows 100% used, with 0 free space available. The status may not immediately cause issues, but it may lead to other operations failing, such as installing an engineering hotfix or updating any components that would require available space in the /usr volume.

Environment

  • BIG-IP v17.5.1.6 specifically
  • Any BIG-IP platform installing or upgrading to v17.5.1.6, including iSeries appliances, VIPRION blades, F5OS tenants, vCMP guests, and BIG-IP Virtual Edition systems.

Cause

The issue relates to an increased size of the apmclients ISO image bundled with BIG-IP 17.5.1.6 and was fixed in 17.5.1.8 via ID2301585.

Note: BIG-IP 17.5.1.7 was not released to MyF5 downloads because the version remained in Limited Availability (LA). For more information, please refer to K000162273.

Customers are always encouraged to upgrade and run the latest release within their current branch.

Answer/Recommended Actions

Follow one of the options below.

  • Option A: Upgrading to 17.5.1.8 or later
  • Option B: Installing the Engineering Hotfix (EHF)
  • Option C: Obtaining and Installing an Engineering Hotfix for ID2298081

Option A: Upgrading to 17.5.1.8 or later

BIG-IP 17.5.1.8 includes a fix for ID2301585, which has an increased size of /usr.

Customers are always encouraged to upgrade and run the latest release within their current branch.

Note: This option creates the /usr filesystem in the target boot location at 8264 MB. This requires free space in the volume group (VG). See K000148391: Verifying free disk space for software upgrade.

Option B: Manual workaround (required for FIPS HSM platforms for v17.5.1.6 install)

On iSeries appliances with an onboard FIPS HSM (e.g., i5820-DF, i7820-DF, i15820-DF), the base image installation of 17.5.1.6 fails, so the subsequent EHF install will not be started. These platforms must use the manual workaround:

Note: This option extends the /usr filesystem in the target boot location to ensure it is at least 7240 MB. This requires free space in the volume group (VG). See K000148391: Verifying free disk space for software upgrade.

  1. Install the software version you are currently running (or any non-17.5.1.6 version) to another boot location.

    Important: Install any version other than 17.5.1.6, as the workaround will fail due to the reason explained above.

  2. Scan the logical volume to find out the logical volume (LV) for /usr of the newly installed volume.
    lvscan | grep usr
    For example, the output includes lines like below.  This is the /usr filesystem for HD1.2.
      ACTIVE            '/dev/vg-db-vda/set.2._usr' [6.58 GiB] inherit

  3. Check whether the /usr LV is less than 7240 MB and needs to be extended:
    lvs --noheadings -o lv_size --units m <output in lvscan for the /usr>For example:
    lvs --noheadings -o lv_size --units m /dev/vg-db-vda/set.2._usr

  4. If the reported size is less than 7240M, extend it to 7240M:
    lvresize -L 7240M -r <output in lvscan for the /usr>
    For example:
    lvresize -L 7240M -r /dev/vg-db-vda/set.2._usr

    If the size is already 7240M or larger, skip this step.

  5. Install the intended image (17.5.1.6) to the same boot location in steps 1-4.  It is important not to delete the boot location after extending its size in step 4.

Option C: Obtaining and Installing an Engineering Hotfix for ID2298081

On platforms other than iSeries appliances with an onboard FIPS HSM, there is an option to install an EHF for ID2298081.

Note: The EHF image Hotfix-BIGIP-17.5.1.6.0.67.25-ENG.iso, which is currently available in MyF5 Downloads does not include the fix for ID2298081. Open a support case to obtain an EHF. See K13123: Managing BIG-IP product hotfixes (15.x - 21.x).

Note: This option extends the /usr filesystem in the target boot location to 7764 MB. This requires free space in the volume group (VG). See K000148391: Verifying free disk space for software upgrade.

After the installation completes, verify the new boot location. See Detecting a problem prior to booting to a new boot location below.

Detecting a problem prior to booting to a new boot location

After installing BIG-IP v17.5.1.6, verify the target boot location before rebooting.  Check whether the /usr filesystem of the target boot location is completely full, and whether critical "shared.mount" and "var-log.mount" files are present and have contents.

  1. Identify the /usr logical volume for the target boot location.
    lvscan | grep usr
  2. Mount it and check utilization
    TARGET=$(mktemp -d)
    mount -o ro /dev/vg-db-sda/set.3._usr "$TARGET"
    echo "=== stat (Free Blocks should be non-zero) ==="
    stat -f "$TARGET"
    echo "=== systemd mount unit sizes (must be non-zero) ==="
    stat -c '%s bytes: %n' "$TARGET"/lib/systemd/system/shared.mount "$TARGET"/lib/systemd/system/var-log.mount
    umount "$TARGET" && rmdir "$TARGET"    Note: The volume group name varies by platform (e.g., vg-db-sda, vg-db-cpmirror). Use the path shown in the lvscan output. Adjust the volume set number (e.g., set.3) to match your target boot location.
  3. If the usr filesystem has zero free blocks, or if shared.mount or var-log.mount are zero bytes, do not reboot into this boot location. Apply the workaround option B above.
