Description

The BIG-IP Edge Client or web browser VPN plug-in may remain in the Reconnecting state while trying to establish or re-establish network access with the BIG-IP APM system. At the Windows system tray the following message may be observed:

Connection to /Common/NetworkAccess_example_name has been lost. BIG-IP Edge Client will restore the connection when possible.

When this happens, the BIG-IP Edge Client log file %temp%/f5TunnelServer.log, may log an entry similar to the following example:

Error 2019-03-12 21:33:26:101 \UTunnel.cpp, UTunnel::RunObjectProc, Heartbeat from server was not received. (timeout in msec, time passed in msec), 65000, 65109

Environment

  • BIG-IP APM network access DTLS is in full or split tunnel mode
  • The BIG-IP Edge Client on Windows
  • Web browser client on Windows

Cause

Network access VPN reconnect events can occur due to intermittent network issues that disrupt the communication between the BIG-IP Edge Client and the BIG-IP APM system. When the network access tunnel is in DTLS mode over User Datagram Protocol (UDP)  the client incrementally monitors incoming traffic. UDP is a connection-less protocol, which does not track the send or receive status of the packet stream. To detect and recover from network events that happen due to packet drops, loss, or resets, the DTLS network access client is set to monitor incoming traffic based on a fixed 65 second timer.  If no traffic is detected within this time, the BIG-IP Edge Client attempts to recover by attempting to reconnect. The BIG-IP APM system and client incrementally send each other keep-alive probes (PPP/LCP and Control Channel Probes) and a continuing reconnect state indicates that the client is not receiving those packet events. 

Overall, this is an indication that traffic is being dropped on the network between the BIG-IP APM system and the client, or on the client's networking stack itself.  The BIG-IP Edge Client and web browser VPN plug-in client will enter a reconnect loop and attempt to transparently reconnect the user.

Recommended Actions

  • Perform a network packet capture on both the BIG-IP system and the client to determine if they are sending or receiving the keep-alive probe packets.
  • Enable TCP reset logging on the BIG-IP system to determine the cause of the TCP reset. For more information on enabling TCP reset logging, refer to K13223: Configuring the BIG-IP system to log TCP RST packets.
  • Verify the health of the BIG-IP system by looking into the CPU and memory usages. For example, a system under memory pressure may drop packets. Refer to K16562: Overview of the tm.tcpmemorypressure database keys.
