Description

Memory growth on BIG-IP LTM systems due to dentry (directory entry) cache accumulation in unreclaimable slab memory. The dentry cache stores information about inodes for files and directories, including negative lookups (non-existent files/directories). When processes perform large numbers of file or directory operations on file objects with novel names or paths, such as temporary files with random components to their name, or file or directory existence checks for file objects that do not exist, the dentry cache can grow significantly, consuming host (4KB page) memory.

Environment

  • Product: BIG-IP (all modules), BIG-IQ
  • Linux kernel memory management (dentry/inode cache behavior), Centos 6.x/7.x kernels
  • Custom scripts or processes performing large numbers of file handling or existence checks on novelly named files or directories (for example external monitors that create a temp file with random component to name)
  • vm.vfs_cache_pressure kernel parameter (default 100, tested with 500)

Cause

Dentry cache growth due to tracking inodes for files and directory paths, including for non-existent files or directories, leads to increased unreclaimable slab memory usage. The Linux kernel does not automatically trim dentry cache entries unless memory pressure is detected, which can result in significant host (4KB page) memory consumption over time. A dentry cache entry size is typically 192 bytes.

Answer/Recommended Actions

To manage dentry cache growth and reclaim memory:

  1. Monitor dentry cache usage:
    • Use slabtop --once | grep dentry to check current dentry cache size.
    • Review /proc/meminfo for MemAvailable, Slab, SReclaimable, and SUnreclaim values.
  2. Manually drop dentry and inode caches:
    • Create, and make executable, a script in /etc/cron.monthly, or for faster dentry growth /etc/cron.weekly, with the following content:

    #!/bin/bash
    sync && echo 2 > /proc/sys/vm/drop_caches

    • This command safely frees reclaimable slab objects, including dentries and inodes, without affecting page cache. The cache will quickly repopulate with actively used directory and file object locations.
  3. Adjust kernel cache pressure (optional):
    • The vm.vfs_cache_pressure parameter controls how aggressively the kernel reclaims dentry and inode caches.
    • Increasing the value (e.g., to 500) may help keep dentry cache growth in check under memory pressure, but does not prevent growth during normal operation.
    • Example: sysctl -w vm.vfs_cache_pressure=500
    • Note: Excessively high values may impact performance. Releasing dentry by drop_caches is expected be more useful.

Additional Information

  • Dentry cache growth is a known behavior of the Linux kernel and is not specific to BIG-IP software.
  • The kernel will typically reclaim dentry cache when real memory pressure occurs, but proactive cache drops can help maintain predictable memory usage.
  • Regular cache drops are generally harmless for BIG-IP systems, as performance is not typically disk latency bound.
  • The vm.vfs_cache_pressure setting mainly affects behavior under memory pressure and does not prevent dentry cache from growing during normal operation.
  • Monitoring tools such as slabtop and /proc/meminfo are useful for tracking memory usage trends.
