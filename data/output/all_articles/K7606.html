Topic

When the BIG-IP system receives a request that matches a configuration object, such as a virtual server or a secure network address translation (SNAT), the BIG-IP system processes the request and then tracks the connection flow by adding an entry to the connection table. If the connection flow becomes idle, the BIG-IP system starts an idle connection timer to determine when the system will delete the connection from the connection table. After the connection reaches the idle session timeout, the BIG-IP system can delete it.

Protocol profiles or SNATs associated with the virtual server handling the connection can time out idle connections. The system can time out connections that a virtual server does not manage based on SNAT automap or VLAN group settings. The shortest timeout value that applies to a connection is the value that always takes effect. In some cases, however, you may want to change this behavior.

For example, you may have configured a forwarding virtual server that is intended to carry long-standing connections, and these connections (such as SSH sessions) may become idle for long periods of time. In this case, you can configure a long idle timeout value on the related protocol profile (in this case, TCP).

Note: For information about the BIG-IP system connection reaper, refer to K5401: Connection reaping will occur within an 7.4 second window around the idle timeout.

Default timeout values

The following BIG-IP objects have idle timeout values:

  • Protocol profiles
  • OneConnect profile
  • SNATs
  • NATs

Protocol profiles

A protocol profile is associated with a virtual server and tells the virtual server how to process incoming traffic, based on the profile configuration. Protocol profiles have an idle timeout setting which specifies the number of seconds that a connection is idle before it is eligible for deletion.

The following list includes the default protocol profile timeout values:

  • FastL4 profile

    The default idle timeout is 300 seconds.

    Note: The default idle timeout is six seconds for FastL4 connections on a standby BIG-IP system. For more information, refer to K14858: The mirrored FastL4 connection idle timeout value on the standby system is six seconds.

  • Fast HTTP profile

    The default idle timeout is 300 seconds.

  • SCTP profile

    The default idle timeout is 300 seconds.

  • TCP profile

    The default idle timeout is 300 seconds.

    Where the idle timeout values of the client and server TCP profiles differ, the shorter timeout determines when a connection is eligible for deletion.

  • UDP profile

    The default idle timeout is 60 seconds.

For each timeout value setting, you can specify a value in seconds or use the keywords Immediate or Indefinite. For information about configuring the idle timeout for a protocol profile, refer to K7166: Changing the idle timeout for a protocol profile.

Important: Specifying an indefinite idle timeout for connectionless protocols, such as User Datagram Protocol (UDP), can lead to stalled connections and resource exhaustion. Specifying an indefinite idle timeout for connection-oriented protocols, such as TCP, can lead to resource exhaustion if connections are not shut down gracefully. In most cases, F5 recommends that you set the idle timeout to a small-as-possible finite value.

Note: Changing the idle timeout value for an existing protocol profile does not alter the timeout the BIG-IP system uses for existing virtual server connections. Existing connections continue to use the previous idle timeout value. To force an existing connection to use the new timeout value, you must manually remove the existing connection from the connection table using the tmsh delete sys connection command.

OneConnect profile

The OneConnect profile allows the BIG-IP system to minimize the number of server-side TCP connections by making existing connections available for reuse by other clients. The Idle Timeout Override setting specifies the number of seconds that a connection remains idle before the connection flow is eligible for deletion. You can use this setting to override the protocol profile timeout and increase the timeout value for connections once they are pooled for reuse.

The default OneConnect Idle Timeout Override setting is Disabled.

SNATs

A SNAT is an object that maps an original client IP address to a translation IP address defined on the BIG-IP system. When you configure an IP address SNAT or SNAT pool on the BIG-IP system, the system creates a corresponding SNAT translation IP address object. You can define a protocol timeout value for the corresponding SNAT translation IP address object.

The following list includes the default SNAT timeout values:

  • IP address SNAT translation object

    The default idle timeout is Indefinite.

  • SNAT pool translation object

    The default idle timeout is Indefinite.

  • SNAT automap

    The idle timeout is Indefinite.

Note: With the idle timeout set to Indefinite, the BIG-IP system internally limits UDP and IP SNAT translation idle timeout periods to a maximum of 300 seconds. The system sets TCP SNAT translation idle timeout periods to 2^32 or 4294967296 seconds (49710 days/136 years).

Important: Using an indefinite idle timeout can lead to resource exhaustion if connections are not shut down gracefully. This is especially true for TCP-based communication. In most cases, F5 recommends that you set the idle timeout to a small-as-possible finite value.

SNAT automap objects have a non-configurable idle timeout value. If you need to implement a SNAT with a configurable idle timeout, create a SNAT with a defined translation IP address or a SNAT pool, and then set the required idle timeout for the translation addresses. You can specify a timeout value in seconds or use the keywords Immediate or Indefinite. For more information, refer to K6017: The BIG-IP SNAT automap idle timeout value is not configurable.

Note: Changing the idle timeout value for a SNAT does not affect existing connections. Existing connections continue to use the previous idle timeout value. To force an existing connection to use the new timeout value, you must manually remove the existing connection from the connection table using the tmsh delete sys connection command.

NATs

A Network address translation (NAT) is an object that allows two hosts in different networks to connect directly to each other. More specifically, a NAT is an address translation object which tells the BIG-IP system to translate one IP address in a packet header to another IP address. A NAT consists of a one-to-one mapping of a public IP address to an internal private class IP address.

A NAT has a non-configurable idle timeout of 300 seconds.

Depending on your specific configuration, a connection on the BIG-IP system that a NAT object handles may or may not continue to work after the connection exceeds the 300 second idle timeout.

NAT connection examples

  • Connecting with NAT

    A client opens an SSH connection to the NAT address on the BIG-IP system, and the BIG-IP system proxies the connection to the NAT origin address. After 300 seconds, the BIG-IP system removes the connection from its connection table. Because the BIG-IP system does not track the status of NAT connections, it does not send out TCP reset (RST) packets after removing the entry from the connection table. If the client then sends new data on the open connection, the BIG-IP system creates a new entry in the connection table and sends the data to the server. The fact that the BIG-IP system removes the initial entry from the connection table is transparent to both the client and the server.

    Note: The BIG-IP 2000 and 4000 series platforms may fail to preserve the source port for NAT for some versions. For more information, refer to K55242686: The BIG-IP system modifies source ports on NAT connections instead of preserving them.

  • Connecting with NAT and a wildcard forwarding virtual server

    A client opens an SSH connection to the NAT address on the BIG-IP system, and the BIG-IP system proxies the connection to the NAT origin address. After 300 seconds, the BIG-IP system removes the connection from its connection table. Because the BIG-IP system does not track the status of NAT connections, the BIG-IP system does not send out RST packets after removing the entry from the connection table. If the server then sends new data on the open connection, the BIG-IP system forwards that data by way of the forwarding virtual server, which takes precedence over the NAT. Because this IP packet takes a different route and the system translates it differently, the client system rejects it, and the SSH connection abruptly terminates. For more information, refer to K9038: The order of precedence for local traffic object listeners.
