Description
 

Environment

  • Big-IP
  • iRules or Topology loadbalancing
  •  

Cause
If the selinux permissions become corrupted on the geolcation database files then TMM may load the older default files that ship originally with the system.  When this happens you may observer that there is a difference between the results of an ltm irule and the results of geoip_lookup.  Results below are fictional IP's for demonstration purposes. These results are not reproducible using these IP's:

If you create a DNS processing virtual server and apply this irule:
when DNS_REQUEST { 
 set edns [DNS::edns0 subnet address]
      log local0. "EDNS: $edns - EDNS-LOCATION: [whereis [string tolower $edns]] - LDNS: [IP::remote_addr] - LOCATION: [whereis [IP::remote_addr]] - QUESTION: [DNS::question name], [DNS::question type] - ANSWER: [DNS::answer]"

}

Then hit that irule with a source IP of 123.124.125.1 and an EDNS0 subnet of 185.12.14.1 it may log something like this:
 

Mar 29 10:43:46 bigip.dnstest info tmm[11188]: Rule /Common/dns_logging <DNS_RESPONSE>: EDNS: 185.12.14.1 - EDNS-LOCATION: EU EU {} {} - LDNS: 123.124.125.1 - LOCATION:  - QUESTION: dns.request.example.com, A - ANSWER: {dns.request.example.com. 30      IN      A       10.90.12.11}

Running geoip_lookup against that same EDNS0 IP yields results that are quite different like this:


[root@bigip:Active:Standalone] auditd # geoip_lookup 185.12.14.1
Will attempt to lookup ip '185.12.14.1'
No database specified.
opening database in /shared/GeoIP/v2/F5GeoIP.dat
size of geoip database = 25608919, segments = 10157420, version = Copyright (c) F5 Networks Inc, All Rights Reserved GEOIP2 v1, 20220321
geoip_seek = 00670146
geoip record ip = 185.12.14.1
country_code = IN
country_name = India
region_name = Karnataka
continent_code = AS
Scope = 23

This happens because the selinux permissions on the geoip files are incorrect. The most common reason for this is the use of the mv command vs cp command to move the files from a location where the selinux permissions are different.  Avoid using the mv command and make sure to upload the files to the proper location.



[root@bigip:Active:Standalone] v2 # ls -lZ
...snip...
-rw-r--r--. root root system_u:object_r:shared_geoip_t:s0 F5GeoIPOrgv2.dat  <----- This file type is configured correctly with shared_geoip_t
-rw-r--r--. root root system_u:object_r:default_t:s0   F5GeoIPRegion2v2.dat  <---- This file is configured improperly with default_t and this causes issues

Recommended Actions
 

The easiest solution is to allow the system to reboot and correct the files automatically to do so:
Force Security-Enhanced Linux (SELinux) to re-label the file system on the next boot by entering the following commands (note this will reboot the device and disrupt traffic if it is processing it):

[root@bigip:Active:Standalone] v2 # touch /.autorelabel
[root@bigip:Active:Standalone] v2 # full_box_reboot

If that doesn't work or you are unable to reboot the device you can try manually correcting the file type with this command (Note: Every improper geolocation file must be manually corrected):
[root@bigip:Active:Standalone] v2 #  cd /shared/GeoIP/v2/
[root@bigip:Active:Standalone] v2 # ls -lZ  (this output will show many files, some are symlinks, focus on correcting ALL that are wrong. This is just one example below) 
-rw-r--r--. root root system_u:object_r:default_t:s0   F5GeoIPRegion2v2.dat  <--- Here type is shown as default_t but should be shared_geoip_t
[root@bigip:Active:Standalone] v2 # chcon -h -t shared_geoip_t F5GeoIPRegion2v2.dat

Now you need to restart tmm (this will disrupt traffic if it is processing any) to get it to pickup the new file permissions.
[root@bigip:Active:Standalone] v2 # bigstart restart tmm
