Description

By default, Aspen Mesh comes with Mutual Transport Layer Security (mTLS) policy set to strict, which means both client and server expect a two-way mTLS handshake. Sidecar to sidecar mTLS is an uncomplicated use case, where the sidecar at the client side communicates to a sidecar at the server side by exchanging certs, resulting in a successful two-way mTLS communication.

Environment

The following example diagram illustrates two different Kubernetes (k8s) clusters with mTLS policy set to strict. Both the client and server will present their certificates at the time of TLS negotiation, which allows a successful mTLS connection. This allows the SLEEP pod on the client side to communicate with the HTTPBN pod on the server side, using the associated sidecar (abbreviated SC in the diagram) on each side.

Components used in this example:

  • BIG-IP version 15.1.0.4 with a layer 4 service proxy configuration
  • Red Hat OpenShift version 4.6.x
  • Kubernetes version 1.19 and later
  • Aspen Mesh version 1.6.x - 1.9.x

Recommended Actions

Client side configuration considerations

  • Create a Service Entry policy to enable cluster to cluster communication. For more information, refer to Service Entry.

    Note: This link takes you to a resource outside of AskF5. The third party could remove the document without our knowledge.

  • Configure TLS Mode using ISTIO_MUTUAL, in order to ensure that mTLS is enabled.
  • Configure Istio/Aspen Mesh control plane managed certificates.

Server side configuration considerations

  • Create a PeerAuthentication policy to define sidecar traffic configuration. For more information, refer to PeerAuthentication.

    Note: This link takes you to a resource outside of AskF5. The third party could remove the document without our knowledge.

  • Configure either Istio/Aspen Mesh control plane managed certificates (recommended) or provide your own certificates.
