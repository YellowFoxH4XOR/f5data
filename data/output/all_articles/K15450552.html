Known Issue

Authentication fails for Microsoft Exchange ActiveSync users when the password contains special UTF-8 characters.

This issue occurs when any of the following conditions are met:

  • BIG-IP APM users authenticate to the BIG-IP system with passwords containing special UTF-8 characters, such as Ä or ê.
  • You configure an iRule that uses the HTTP::header insert <Client-IP> command to insert an object where <Client-IP> is a string representation of an IP address.
  • You configure an iRule that processes other input containing IP addresses, such as IP::addr, UTF-8 characters, or other objects that are handled as byte arrays.

This issue may occur when low-level Tool Command Language (Tcl) functions servicing iRules APIs parse UTF-8 characters into strings. The Tcl marshalling routines used by some iRules functions (including HTTP::header insert) coerce some arguments into the bytearray type. The bytearray type receives special treatment when coerced into other objects, such as IP addresses, where the binary IP address is expected in the bytearray instead of a string representation. Under certain conditions, when a string is coerced into a bytearray, the coercion fails produces an error.

BIG-IP APM user authentication is implemented using iRules. Therefore, the handling of UTF-8 characters in iRules affects BIG-IP APM user authentication when the user password contains UTF-8 characters.

For more information about data type coercion, refer to the following DevCentral article: Polymorphism - Making TCL operators work for you.

Impact

Affected iRules may not function, and application functionality dependent on the iRules is impaired. For example, BIG-IP APM authentication service may be unavailable.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • When you have special UTF-8 characters in your password, you are unable to authenticate to the BIG-IP APM system.
  • Multiple users are unable to authenticate after upgrading to BIG-IP APM 13.0.0 or later.
  • When using the HTTP::header insert command in an iRule, the system logs an error message in the /var/log/ltm file that appears similar to the following example:

    err tmm[17094]: 01220001:3: TCL error: /Common/example_irule <HTTP_REQUEST> - bad IP address format (line 1)     invoked from within "..."

Workaround

Depending on your specific issue and symptom, you can perform one of the following workarounds:

  • Modifying your BIG-IP APM access policy
  • Modifying your affected iRule

Modifying your BIG-IP APM access policy

If you are experiencing BIG-IP APM user authentication failures that include UTF-8 characters in passwords, you can add a Variable Assign policy item after the Logon Page policy item in the access policy. To do so, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Access > Profiles / Policies.
  3. For the access profile you want to use, click Edit.
  4. In the visual policy editor (VPE), on the fallback branch for the Logon Page policy item , click the Add icon (+).
  5. On the Assignment tab, click Variable Assign, and then click Add Item.
  6. Click Add new entry and click Change to edit the variable assignment.
  7. Click Custom Variable, Secure, and Custom Expression.
  8. In the Custom Variable box, type the following:

    session.logon.last.password

  9. In Custom Expression box, type the following:

    set pass [mcget -secure session.logon.last.passwor
    d]; binary scan $pass c* chars; set newpass ""; foreach {ch} $chars { append newpass [format %c [expr $ch & 0xFF]] }; return $newpass

  10. Click Finished.
  11. Click Save.
  12. Click Apply Access Policy.
  13. To close the visual policy editor, click Close.

Modifying your affected iRule

If your iRule processes IP addresses, UTF-8 characters, or other objects that are handled as bytearray types, you may be able to work around this issue by troubleshooting the iRule to determine the source of the error, and modifying the iRule. For example, if you use the HTTP::header insert command to process a string variable as IP address, you may encounter the following error message in the /var/log/ltm logs:

TCL error: /Common/example_irule <HTTP_REQUEST> - bad IP address format (line 1)     invoked from within "whereis $IP__client_addr country"

You can work around this issue by converting the string to an IP address with IP::addr before inserting it as a header.

For example, the following iRule produces the previous error message:

when HTTP_REQUEST {
    set exampleIP "192.0.0.2"   
   
    HTTP::header insert X-Forwarded-For $exampleIP

    log local0. "Where is myip1: [whereis $exampleIP country]"
}

To work around the issue, you can replace the previous iRule with the following iRule:

when HTTP_REQUEST {

    set exampleIP "192.0.0.2"   
   
     HTTP::header insert X-Forwarded-For [IP::addr $exampleIP mask "255.255.255.255"]

   log local0. "Where is exampleIP: [whereis $exampleIP country]"
}
