K000148668: Troubleshooting connection to upstream timeout issues: [error] 8#8: *1111 upstream timed out (110: Connection timed out) while connecting to upstream

Description

Nginx error:

  • The error message "upstream timed out (110: Connection timed out) while connecting to upstream, " means that nginx wasn’t able to establish connection with proxied server during the value of “proxy_connect_timeout”

Status code recorded and returned to client:

  • 504

Environment

Nginx LB, the basic setup is

 <Client> <-> <Nginx LB> <Upstream group>

Cause

There are several possible reasons caused this error:

Cause 1. Network issues 

Cause 2. Upstream servers are cloud instances, their IP addresses are changed from time to time but nginx is configured to resolve upstream fqdns statically, without "resolver" directive and “resolve” upstream server parameter

Cause 3. The default "proxy_connect_timeout" value is 60 sec, or explicitely configured. Upstream servers are overloaded, respond slowly and it takes more than "proxy_connect_timeout" value

Answer/Recommended Actions

Cause 1. Nginx dashboard displays the upstream IPs in case of they are configured as domain names and nginx resolves them. Direct requesting the upstream app from nginx instance via “curl -v http://<upstream_addr>/<request_uri>” command will represent connection issue if it is permanent.

 

Cause 2. Static resolving means that nginx resolves upstreams domain names into IP only while reload/restart. It uses system resolver or external DNS if it is configured by “resolver” directive. To get dynamic resolving, via external DNS and valid for TTL from response, the configuration should contain both of:

  • “resolver” directive
  • “upstream” group with “resolve” parameter for the servers and proxy_pass to this upstream group

    ——— configuration example ——— 
http {
    resolver 10.0.0.1 valid=300s ipv6=off;
    # ...
    server {
        location / {
            proxy_pass http://backend;
        }
    }
    upstream backend {
        zone backend 32k;
        least_conn;
        # ...
        server backend1.example.com resolve;
        server backend2.example.com resolve;
    }
}

Cause 3. If the test for Cause #1 represents intermittent connection issue and nginx access_log contains both successful (2xx/3xx) records and 504 for the same Uris, there may be the chance that “proxy_connect_timeout” is not enough and increasing this value can mitigate the issue, or at least reduce the number of such failures. Please note that the value should be reasonable. One of the way to understand this is to run the test with the access log extension uct=$upstream_connect_time, trace the statistics and get the optimal value. From our best practice the default 60 sec is pretty large.

Additional Information

Though the recommendations relate to "http" context directives and variables, the troubleshooting logic may be used for "stream" context also. For this case the directives and variables should be available in nginx stream modules
