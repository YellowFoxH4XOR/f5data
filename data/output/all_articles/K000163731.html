K000163731: Reclaiming Disk Space Used by ClickHouse Logs in NGINX Instance Manager Description

Type
Support Solution
Published
2026-10-15
Updated
2026-10-15
Applies to
  • NGINX Products
  • NGINX Instance Manager: 2.22.0
Source
https://my.f5.com/manage/s/article/K000163731

Description

The /var filesystem in NGINX Instance Manager can reach high utilization when ClickHouse retains excessive trace and text log data under /var/lib/clickhouse. Direct deletion of individual ClickHouse .bin files is unsafe and can corrupt table parts.

Environment

  • NGINX Instance Manager
  • ClickHouse data stored under /var/lib/clickhouse
  • ClickHouse system log tables:
    • system.trace_log
    • system.text_log
    • system.metric_log
    • system.asynchronous_metric_log
    • system.query_log

Cause

ClickHouse trace-level and text-level logging can generate a large volume of diagnostic data. Without restrictive TTL settings, the following tables can grow significantly:

  • system.trace_log
  • system.text_log

Recommended Actions

  1. Back up NGINX Instance Manager

    Create and verify an NGINX Instance Manager backup before modifying ClickHouse configuration or retention settings.

  2. Review ClickHouse table usage

    Run the following query using clickhouse-client:

    SELECT
    database,
    `table`,
    formatReadableSize(sum(bytes_on_disk)) AS size
    FROM system.parts
    WHERE active
    GROUP BY database, `table`
    ORDER BY sum(bytes_on_disk) DESC;

  3. Do not delete ClickHouse files directly

    Do not use rm to delete individual files under /var/lib/clickhouse. ClickHouse manages table-part files and metadata as a unit. Removing a single column file can make the table part inconsistent.

  4. Configure retention for trace and text logs

    Apply a suitable TTL to the affected system tables. For example:

    ALTER TABLE system.trace_log
    MODIFY TTL event_time + INTERVAL 3 DAY;

    ALTER TABLE system.text_log
    MODIFY TTL event_time + INTERVAL 3 DAY;

    Select a retention period that meets operational and troubleshooting requirements.

  5. Reduce ClickHouse logging verbosity

    Change the ClickHouse server logging level from trace to error in the ClickHouse server configuration. This reduces the amount of diagnostic data generated.

  6. Restart ClickHouse when required

    After changing the ClickHouse configuration, check and restart the service according to the approved maintenance procedure:

    sudo systemctl status clickhouse-server
    sudo systemctl restart clickhouse-server
  7. Verify cleanup

    Recheck filesystem usage:

    df -h /var

    Review active mutations if required:

    SELECT
    database,
    table,
    mutation_id,
    command,
    is_done,
    latest_fail_reason
    FROM system.mutations
    ORDER BY create_time DESC;

    TTL processing and physical disk-space reclamation may not occur immediately after the ALTER TABLE command completes.

Additional Information

  • Do not remove individual .bin files from ClickHouse data directories.
  • Use ClickHouse TTL settings or other ClickHouse-native data-management commands.
  • Confirm that the selected retention period satisfies diagnostic and operational requirements.
  • Keep a verified backup before changing ClickHouse retention or logging configuration.
  • Perform service restarts during an approved maintenance window.
  • NGINX Instance Manager does not provide a dedicated cleanup script for this purpose.
