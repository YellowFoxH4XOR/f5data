Description

After implementing HTTP2 on the BIG IP, found by a packet capture taken on the VIP, that the connection was reset with GOAWAY message, and without a clear indication why this GOAWAY appeared.

In that capture, Additional Debug Data is in the GOAWAY packet as the following:
 

Frame 26241: 268 bytes on wire (2144 bits), 268 bytes captured (2144 bits)
   Ethernet II, Src: 00:00:5E:00:53:00, Dst: 01:00:5E:90:10:00
   802.1Q Virtual LAN, PRI: 0, DEI: 0, ID: 1022
   Internet Protocol Version 4, Src:10.10.1.1 , Dst:192.168.1.1
   Transmission Control Protocol, Src Port: 443, Dst Port: 55075, Seq: 4218590041, Ack: 176995330, Len: 46
   Transport Layer Security
   HyperText Transfer Protocol 2
       Stream: GOAWAY, Stream ID: 0, Length 15
           Length: 15
           Type: GOAWAY (7)
           Flags: 0x00
               0000 0000 = Unused: 0x00
           0... .... .... .... .... .... .... .... = Reserved: 0x0
           .000 0000 0000 0000 0000 0000 0000 0000 = Stream Identifier: 0
           0... .... .... .... .... .... .... .... = Reserved: 0x0
           .000 0000 0000 0000 0000 0000 0110 1111 = Last-Stream-ID: 111
           Error: NO_ERROR (0)
           Additional Debug Data: 74696d656f7574                              <--- The reason before decoding


If we decode the Additional Debug Data portion, we can see that the GOAWAY reason is due to timeout.

   $ echo '74696d656f7574' | xxd -r -p
   timeout

 

Environment

  • BIG IP
  • HTTP/2

Cause

The GOAWAY messages from the server is likely due to a 5-second idle timeout configured on the server (possibly KeepAliveTimeout in the Apache config).
From the pcap, we can see that once the server has responded and the BIG-IP sends the ACK, the server waits for 5 seconds, then initiates a shutdown via the GOAWAY (NO_ERROR, timeout) packet when it doesn't see any further transactions.

Recommended Actions

Change the web server idle timeout from 5 sec to 300 sec
