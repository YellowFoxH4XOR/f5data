Description

After upgrade, some Virtual Servers with redirect policies are not redirecting correctly and showing a web error on the browser, similar to:

PR_CONNECT_RESET_ERROR

If a traffic capture has been taken with RST cause enabled, you can see:

[F5RST: iRule execution error]

You can also find similar logs on /var/log/ltm every time the redirection tries to take place:

err tmm[<PID>]: 01220001:3: TCL error: /Common/<iRule name> <HTTP_REQUEST> - Can't call after responding - ERR_NOT_SUPPORTED (line 1) invoked from within "HTTP::uri"
err tmm[<PID>]: 01220001:3: TCL error: /Common/<iRule name> <HTTP_RESPONSE> - Can't call after responding - ERR_NOT_SUPPORTED (line 1)     invoked from within "HTTP::header insert Cache-Control "no-store, no-cache""

Note: You might not see these logs if the db variable log.rules.level has been modified from its default value.

Environment

  • Virtual Server with LTM Policies and iRules attached
  • After upgrade to 14.1.x or above

Cause

Due to a change in behaviour explained on K23237429: TCL error: ERR_NOT_SUPPORTED after upgrade to version 14.1.0 or later, when the iRule runs after the policy has already responded, it generates a TCL error and resets the connection with RST cause: RST cause: [274ac96:1863] {peer} iRule execution error.

Recommended Actions

Apply the workaround on K23237429 to add: if {[HTTP::has_responded]}{return} at the beginning of the iRule, so that it exits immediately if HTTP has already responded with the LTM policy.

Additional Information

Depending on the specific iRule syntax, you might also need to add the workaround on each HTTP::redirect, HTTP::respond and HTTP::retry, before and after as shown on this example:

if {[HTTP::has_responded]}{return}    → add line
HTTP::redirect "http://www.example.com."
return                                → add line
