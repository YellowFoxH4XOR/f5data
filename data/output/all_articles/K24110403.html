K24110403: After Windows 20H1/20H2/21H1 upgrade users are unable to resolve DNS after disconnecting the F5 APM Edge Client

Description
After the Windows 10 20H1, 20H2 or 21H2 in-place upgrades, users may experience a loss of DNS Resolution after using the F5 Edge Client. 
The symptoms of this issue are failures to resolve all DNS queries using ping, nslookup, or while using a web browser. 
Users may experience browser errors relating to DNS:

  • Microsoft Edge -  Hmmm...can't reach this page
  • Google Chrome -  DNS_PROBE_FINISHED_NO_INTERNET
  • Mozilla Firefox - Hmm. We're having trouble finding that site

Environment

All the following conditions must be met to be affected by the issues mentioned in this article.

  • Windows 10, version 19041 (20H1), Windows 10, version 19042 (20H2) or Windows 10, version 19043 (21H1)
  • Appending DNS Suffixes in the Advanced TCP/IP Settings on the workstation
  • SearchList registry key type is not a REG_SZ
  • F5 APM Edge Client
  • F5 DNS Relay Proxy Service
  • Network Access List DNS Suffixes 
  • Network Access List Enforce DNS search order enabled
  • Split Tunnel

Cause
When the Access Policy is configured to append DNS Suffixes, the F5 Edge Client creates the SearchList_F5_BACKUP_VALUE registry key which contains the original SearchList registry key type and existing DNS Suffixes. 
In certain instances, the SearchList value can can be restored as a non-REG_SZ value, causing all DNS queries to fail after disconnecting the F5 Edge Client.This issue is being tracked under bug ID1023621.


Recommended Actions

To fix this issue, you can upgrade or update to APM Clients 7.2.1.4 or a later version. For more information on updating your APM Clients refer to K23159056: Upgrade the BIG-IP Edge Client | BIG-IP update and upgrade guide.

To work around this issue, an Administrator can modify the Windows Registry with the Registry Editor, Command Prompt or Logon Scripts. 

Note: The workaround addresses one of the conditions in the Environment section so that the Windows client does not hit the issue.

To use the Windows Registry Editor:
  1. Log in to the affected Windows system using an account with privileges to edit the registry for the users on the system.
  2. Click Start.
  3. Select Run.
  4. In the Open box, type the following:
    regedit
  5. Click OK.
  6. Navigate to HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters folder.
  7. Delete the SearchList REG_BINARY value.
  8. Click Edit, then New , then String Value.
  9. For String Value, type SearchList
  10. Click File and then click Exit.
  To use Windows Command Prompt run the following commands:
  1. reg delete HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\ /v SearchList /f
  2. reg add HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters /t REG_SZ /v SearchList /f
 
A logon script deployed through Group Policy Objects(GPO) or other Endpoint Management Systems can be used to work around this issue:
Note: This script was provided to F5 by the Microsoft Windows Support Team. Please test the functionality of this script prior to deploying to end user devices
 

#Requires -RunAsAdministrator

<#

    Workaround script for customers impacted by:

    Microsoft Safeguard:33324334

    F5 BugID: ID1023621


    How to use:

    1. Set the PowerShell execution policy to that of Unrestricted (Set-ExecutionPolicy -ExecutionPolicy Unrestricted)

    2. Run script at logon of the user directly prior to performing upgrade

#>

#Easy test if the value exists

function Test-RegistryValue {

    param (

     [parameter(Mandatory=$true)]

     [ValidateNotNullOrEmpty()]$Path,

     [parameter(Mandatory=$true)]

     [ValidateNotNullOrEmpty()]$Value

    )

    try

    {

        Get-ItemProperty -Path $Path | Select-Object -ExpandProperty $Value -ErrorAction Stop | Out-Null

        return $true

    }

    catch

    {

        return $false

    }

}

#Set the path of the reg key

$fullPath = "HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters"

$shortPath = "\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters"

#The property we care about in this situation

$prop = "SearchList"

#The expected type is that of string

$expectedType = "string"

#List of all other types that we do not expected

$unexpectedTypes = @("binary",

                      "expandstring",

                      "multistring",

                      "dword",

                      "qword",

                      "-")

#First check if it exists, if it doesn't exist, simply create an empty string and return

$exists = Test-RegistryValue -Path HKLM:\$shortPath -Value $prop

if(!$exists)

{

    New-ItemProperty -Path HKLM:\$shortPath -PropertyType String -Name "SearchList" -Force | Out-Null

    return

}

#Grab the type as this is the primary trigger

$type = (Get-Item -Path Registry::$fullPath).GetValueKind("$prop")

#If we're of type $expectedType, we're probably good but, we need to nesure the null terminator is present no matter the contents

if($type -eq $expectedType)

{

    #Our key is the correct type, now we need to ensure it is null terminated

    $length = (Get-ItemPropertyValue -Path Registry::$fullPath -Name $prop).Length

    if($length -eq 0)

    {

        #Since we're here the key is empty, overwrite as empty to enforce the null-terminator

        Set-ItemProperty -Path Registry::$fullPath -Name $prop -Value "" -Force

    }

    else

    {

        #The key is a REG_SZ and has values, enforce the null-terminator, no harm in just overwriting with same values as Set-ItemProperty enforces the null terminator

        #Populate the current value

        $popValue = (Get-ItemPropertyValue -Path Registry::$fullPath -Name $prop)

        #Enforce the null-terminator

        Set-ItemProperty -Path Registry::$fullPath -Name $prop -Value "$popValue" -Force

    }

}

else

{

    #The key both exists AND is an unexpected type (NOT REG_SZ), we need to recover from that

    if(($type -eq $unexpectedTypes[1]) -or ($type -eq $unexpectedTypes[3]) -or ($type -eq $unexpectedTypes[4]) -or ($type -eq $unexpectedTypes[5]))

    {

        #The only data types we can recover the list from are REG_MULTI_SZ and REG_BINARY so just delete and recreate if REG_DWORD, REG_QWORD, REG_EXPAND_SZ, or UNKNOWN

        Remove-ItemProperty -Path Registry::$fullPath -Name $prop -Force

        Set-ItemProperty -Path Registry::$fullPath -Name $prop -Value "" -Type String -Force

    }

    else

    {

        #Handle REG_BINARY

        if($type -eq $unexpectedTypes[0])

        {

            #Grab the binary data

            $popValue = (Get-ItemPropertyValue -Path Registry::$fullPath -Name $prop)

            #Convert the binary data to a string

            $newValue = [System.Text.Encoding]::Default.GetString($popValue)

            #Delete the binary value

            Remove-ItemProperty -Path Registry::$fullPath -Name $prop -Force

            #Set as REG_SZ with values from REG_BINARY data

            Set-ItemProperty -Path Registry::$fullPath -Name $prop -Value "$newValue" -Type String -Force

        }

        #Handle REG_MULTI_SZ

        if($type -eq $unexpectedTypes[2])

        {

            #Populate the values in the REG_MULTI_SZ

            #Grab the REG_MULTI_SZ data

            $popValue = (Get-ItemPropertyValue -Path Registry::$fullPath -Name $prop)

            #Join the values of the REG_MULTI_SZ into a single string delimited by a ,

            $separator = ","

            $newValue = [string]::Join($separator,$popValue)

            #Set as REG_SZ with values from REG_BINARY data

            Remove-ItemProperty -Path Registry::$fullPath -Name $prop -Force

            Set-ItemProperty -Path Registry::$fullPath -Name $prop -Value "$newValue" -Type String -Force

        }

    }

}
