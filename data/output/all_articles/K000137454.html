Can you tell me about the mitigation for this vulnerability?

For BIG-IP versions 14.1.0 and later, you can run the mitigation script noted in the security advisory article. F5 recommends downloading the script (as opposed to using copy / paste). The mitigation script works as follows:

  • Saves a backup of the /config/httpd/conf.d/proxy_ajp.conf and /etc/tomcat/server.xml files
  • Creates a random secret that is used between Apache and Tomcat processes internally, then places this secret within the configuration files and restarts httpd and tomcat.
  • If you run the script once, the mitigation persists through reboots but does not persist through upgrades and is not carried over by UCS installation (for example, after an RMA or clean installation).
  • To reverse the changes, you can run the command mentioned the security advisory using the -u flag.

  • K000137322: BIG-IP iRule or LTM policy may generate multiple HTTP redirect responses
What is HTTP request smuggling?A request smuggling attack exploits differences in the way that two HTTP devices parse HTTP requests. For example, a request smuggling attack often involves a front-end device that performs authentication and authorization tasks and a back-end device that services the requests. To initiate request smuggling, the attacker often manipulates the Transfer-Encoding header and the Content-Length header in such a way that causes either the front-end device or the back-end server to incorrectly interpret the request and pass through a malicious HTTP query.
In the security exposure scenario, an attacker may be able to perform HTTP request smuggling leading to HTTP cache poisoning. In this scenario, the cache or CDN acts as the front-end system and the BIG-IP acts as the back-end system. When the BIG-IP system is configured with a vulnerable redirect iRule or local traffic policy as defined in the security exposure, the attacker may be able to prompt a malicious redirect response from the BIG-IP system that is cached by the front-end CDN or cache system.
  • HTTP Request Smuggling, what it is, how to find it and how to stop it
Is there a way to see if this exposure is being exploited?In theory you could run a packet capture and look for requests and responses that indicate a request smuggling attack. However, F5 does not recommended performing real time, continuous packet captures on the BIG-IP system due to the impact on device performance. In addition, you may be able to see certain variants of this type of exposure via iRules and logging, however F5 recommends using the iRule mitigation instead.
