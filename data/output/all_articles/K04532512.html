Can you briefly explain my risk assessment?

Your system is exposed to at least one critical vulnerability (CVSS 9.8) on your management port if your system is running the one or both of the following:

  • BIG-IP 12.x and later
  • Any BIG-IQ version regardless of configuration

Your system has an additional critical vulnerability (CVSS 9.0) on your data plane (CVE-2021-22991) if any of the following scenarios apply to you:

  • You are running BIG-IP 12.1.x or later using BIG-IP APM in any configuration.
  • Your system is using a specific function in iRules or LTM policies or both.
  • You are using the URL categorization feature in either BIG-IP PEM or Secure Web Gateway.
  • You are using Advanced WAF Risk Engine (Early Access customers only).

Your system has an additional critical vulnerability (CVSS 9.0) on your data plane (CVE-2021-22992) if you are running BIG-IP 11.6.0 or later using Advanced WAF or BIG-IP ASM with a specific configuration related to login pages.

You may be exposed to up to two critical vulnerabilities on your management port and two critical vulnerabilities on your data plane (traffic flowing through virtual servers).

Note: For more information about the data plane, refer to What is the difference between the control plane and the data plane? in this article.

What’s the best way to resolve these vulnerabilities?

F5 recommends installing a fixed version as soon as possible to eliminate the risk posed by these vulnerabilities. In the interim, you can apply the mitigations documented in the individual security advisories listed in this article.

Which software version I need to install to fix these vulnerabilities?

For BIG-IP products, these vulnerabilities are fixed in BIG-IP 11.6.5.3, 12.1.5.3, 13.1.3.6, 14.1.4, 15.1.2.1, and 16.0.1.1.

For BIG-IQ products, CVE-2021-22986 is fixed in BIG-IQ 7.0.0.2, 7.1.0.3, and 8.0.0.

Note: CVE-2021-22987 through CVE-2021-22990 do not affect BIG-IQ.

Note: According to commitments listed in K4602: Overview of the F5 security vulnerability response policy, F5 has not evaluated End of Technical Support (EoTS) versions.

What is the difference between the control plane and the data plane?

Control plane refers to management-related services and traffic flowing to them, such as the Configuration utility (TMUI), iControl REST, and SSH, either through the management IP address or a self IP address exposing the HTTPS or SSH ports (443 or 22). Data plane refers to any traffic handled by a virtual server, SNAT, NAT, or other non-control-plane-traffic handler.

Are you aware of any of these issues being publicly exploited?

No. At the time of publication, F5 is not aware of any public exploitation of these issues.

Is there a way to determine whether any of these vulnerabilities have been exploited on my BIG-IP system?

F5 is not aware of any specific indicators of compromise associated with these vulnerabilities, however, F5 iHealth contains several heuristic tests designed to look for possible evidence of malicious activity within an uploaded QKView file, for example unknown processes or logins from public IP addresses.

What steps should I take if I suspect a compromised BIG-IP system?

You should follow the guidance outlined in K11438344: Considerations and guidance when you suspect a security compromise on a BIG-IP system.

What should I do if I am running an older platform, such as BIG-IP 6900, which is not compatible with the fixed software versions?

Most older platforms currently in use are in extended support, defined in K4309: F5 platform lifecycle support policy. If you are using such a platform, or one completely out of support, you should consider upgrading to a fully supported hardware platform.

F5 will not release engineering hotfixes on maintenance or point releases that were current when a platform passed platform End of Service Date (EoSD) and entered extended support. However, since you are already running a platform that is not fully supported, you may consider updating to a software release with the fixes. F5 does not take steps to break updates for platforms in extended support. So, in general, F5 expects that later maintenance and point releases issued after the platform entered extended support should work normally . For example, a system that was running BIG-IP 12.1.3 when it entered extended support will likely run 12.1.5.3 without issue, and updating will not change the support status. In the meantime, you can immediately apply the mitigations provided in the appropriate security advisory.

What is iControl REST?

iControl REST is the web services-based API that the BIG-IP system uses to allow complete, dynamic, programmatic control of F5 configuration objects. It enables applications to work in concert with the underlying network based on true software integration.

iControl REST uses modern web standards in the form of Representational State Transfer (REST) and JavaScript Object Notation (JSON). iControl REST is used in BIG-IP 11.4 and later. Its API is based on the TMOS Shell (tmsh), sharing the same overall layout and structure. It is essentially a JSON version of tmsh that adheres to REST standards. iControl REST complies with modern web-based programming paradigms and is easier to use and implement than iControl SOAP.

I don’t use iControl REST. Can I disable it?

No, the Configuration utility (TMUI) requires iControl REST for its operation; therefore, disabling iControl REST is not possible.

What is the difference between the Configuration utility (TMUI) and iControl REST access?

The Configuration utility is the BIG-IP GUI in which you can make configuration changes. iControl REST is designed for machine automation. While both the Configuration utility and iControl REST are accessible on the same IP and port, they are different interfaces and there are different ways to restrict access to them.

As part of mitigating CVE-2020-5902, I restricted access to the Configuration utility (TMUI) using an HTTPD configuration. Is that sufficient to block access to iControl REST?

No. That mitigation enforces access to the Configuration utility but not iControl REST, which is the vulnerable interface.

My configuration already restricts access to the Configuration utility (TMUI) using an HTTPD configuration. Is that sufficient for blocking access to iControl REST?

No. That mitigation enforces access to the Configuration utility but not iControl REST, which is the vulnerable interface.

As part of mitigating CVE-2020-5902, I blocked access to the Configuration utility on my self-IP address. Is that sufficient to block access to iControl REST?

Yes. Blocking access to TCP port 443 on self-IP addresses through the port lockdown configuration prevents access to both the Configuration Utility and iControl REST. This is sufficient to block access to iControl REST.

If you require access to iControl REST through the self-IP address (for example, if the BIG-IP system is managed by BIG-IQ or other tools that use iControl REST), then you must use another mechanism such as an external firewall or the BIG-IP AFM network firewall policy on the self-IP address to limit access to port 443 to only trusted hosts.

My configuration already restricts access to the Configuration utility on my self-IP address. Is that sufficient for blocking access to iControl REST?

Yes. Blocking access to TCP port 443 on self-IP addresses through the port lockdown configuration prevents access to both the Configuration Utility and iControl REST. This is sufficient to block access to iControl REST.

If you require access to iControl REST through the self-IP address (for example, if the BIG-IP system is managed by BIG-IQ or other tools that use iControl REST), then you must use another mechanism, such as an external firewall or the BIG-IP AFM network firewall policy on the self-IP address, to limit access to port 443 to only trusted hosts.

Can I mitigate these vulnerabilities using iptables or the management port firewall (BIG-IP 14.1.0 and later)?

You may restrict access to the iControl REST management interface to trusted hosts using either iptables (as described in K69354049: Restricting access to the BIG-IP management interface for Configuration Utility and iControl REST services using iptables) or the management port firewall in BIG-IP 14.1.0 and later (as described in K94615110: Configuring firewall rules on the BIG-IP management port without additional license).

How do I know if my BIG-IP system is using appliance mode?

You can verify that your system is running in appliance mode from the License page in the Configuration utility. A line similar to the following example displays under Active Modules: Appliance Mode (TMSH Only, No Root or Bash Access).

Appliance mode is a non-default license option which you must be explicitly request from F5. Very few customers use it. For more information about Appliance mode, refer to K12815: Overview of Appliance mode.

How can I determine whether the iControl REST interface or Configuration utility for my system is accessible from the Internet?

The Diagnostics tab within F5 iHealth has heuristic tests designed to look for several different pieces of evidence which suggest there are interfaces exposed to the public Internet, but it may not be able to identify all cases.

Alternatively, having a public (that is, a routable non-RFC1918) IP address associated with the management port or self IP addresses is a strong indication that these interfaces may be accessible through the Internet. You can test this by attempting to connect back to the BIG-IP system on port 443 or 22 from a remote device. If these interfaces have RFC1918 addresses associated, then you must check upstream NAT devices to determine if there is any inbound connectivity from the Internet (such as through port forwarding).

Have I mitigated these risks if I am restricting access to iControl REST to internal users?

There is still a risk of lateral attacks from internal hosts and malicious insider threats.

How does ‘Allow None’ port lockdown on a self IP address affect high availability (HA) configurations?

Allow None may break or degrade HA configurations by blocking required traffic. You can use Allow Custom with port 1026 allowed. For more information, refer to the security advisories which have links to additional documentation on port lockdown.

On the configured Config Sync IP, Allow None may break or degrade some ConfigSync operations such as SSL Orchestrator and Access Guided Configuration (AGC) and impact the ability to establish device trust within a sync group.

Are there any necessary special considerations when installing a fixed version on a device with BIG-IP APM licensed and provisioned?

When upgrading the BIG-IP system, the version of the APM Clients ISO file that is shipped with the BIG-IP software ISO file automatically becomes the active APM Clients version.

For example, when you upgrade a system running BIG-IP 15.1.1 with APM Clients 7.2.1 active to BIG-IP 15.1.2, the active APM Clients version after the upgrade automatically becomes 7.1.8.4, the version that is shipped with BIG-IP 15.1.2. You should verify the active APM Clients version after a BIG-IP software upgrade and update your APM Clients version as appropriate.

For more information on BIG-IP and APM Clients version, refer to K13757: BIG-IP Edge Client version matrix. You may also want to review K15302: Understanding BIG-IP Edge Client Component Update behavior for Windows, macOS, and Linux CLI, and K52547540: Updating BIG-IP Edge Client for the BIG-IP APM system.

Does CVE-2021-22986 impact iControl SOAP?

While iControl SOAP is not impacted by the vulnerability, it is still recommended to update to protect against CVE-2021-22986 for iControl REST.

Is the VCMP host vulnerable to CVE-2021-22986, CVE-2021-22987, CVE-2021-22988, CVE-2021-22989, and CVE-2021-22990?

The VCMP host is vulnerable to CVE-2021-22986, and CVE-2021-22987 (running in appliance mode) or CVE-2021-22988 (running in non-appliance mode).
The VCMP host is not vulnerable to CVE-2021-22989 and CVE-2021-22990 because CVE-2021-22989 and CVE-2021-22990 are specific for Advanced WAF or BIG-IP ASM, and the VCMP host does not have Advanced WAF or BIG-IP ASM module provisioned on it.

If ASM is Provisioned but not configured, am I at risk for CVE-2021-22990?

With ASM provisioned a malicious privileged user can gain access to the ASM UI. So CVE-2021-22990 is still a risk.
