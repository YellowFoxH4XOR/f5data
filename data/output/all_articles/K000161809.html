Description

This article is written for engineers who previously relied on BIG-IQ to handle BIG-IP licensing and now need to bring that licensing step into their existing automation directly, without a BIG-IQ in the loop. It covers two approaches — F5 Declarative Onboarding (DO) and Ansible — with complete worked examples that can be adapted into an existing pipeline rather than built from scratch.

Both approaches talk directly to the target BIG-IP and to the F5 Activation Service: generating a dossier on-device, submitting it for activation, and applying the signed license, driven by a single declaration or playbook task rather than a manual sequence of commands.

Worked examples throughout use a BIG-IP at 10.10.10.10. Substitute your own management IP, credentials, and registration key.

Environment

  • BIG-IP running TMOS 13.1 or later with iControl REST enabled.

  • A valid registration key issued via the My F5 portal.

  • Network access from the host issuing the declaration or playbook to the BIG-IP's management interface, and internet access from whichever side performs activation to reach the F5 Activation Service.

  • For Declarative Onboarding: the DO extension package installed on the target BIG-IP.

  • For Ansible: the f5networks.f5_modules collection installed on the control node.

Cause

Manually licensing a BIG-IP one command at a time does not scale once deployment is automated, and licensing is typically the first action needed before any further configuration is meaningful. With BIG-IQ removed as the licensing broker, that step needs to move into whichever automation tool is already managing the rest of the device lifecycle. This article documents both options so the right one can be chosen depending on whether licensing is one step in a larger first-boot declaration, or a standalone, repeatable task within an existing Ansible playbook.

Answer/Recommended Actions

Declarative Onboarding — worked example

Declarative Onboarding expresses licensing as a License class within a larger declaration, alongside other first-boot settings such as hostname, NTP, and VLANs. The declaration is sent as a single HTTPS POST directly to the BIG-IP being licensed.

The full declaration:

{
  "class": "Device",
  "schemaVersion": "1.30.0",
  "async": true,
  "Common": {
    "class": "Tenant",
    "myLicense": {
      "class": "License",
      "licenseType": "regKey",
      "regKey": "XXXXX-XXXXX-XXXXX-XXXXX-XXXXXXX"
    },
    "hostname": "bigip1.example.com"
  }
}

Send it to the device:

curl -sk -u admin:yourpassword -X POST \
  https://10.10.10.10/mgmt/shared/declarative-onboarding \
  -H "Content-Type: application/json" \
  -d @declaration.json

Because async is set to true, the POST returns immediately with a task ID. Poll the same endpoint with GET to check progress:

curl -sk -u admin:yourpassword \
  https://10.10.10.10/mgmt/shared/declarative-onboarding

The response includes a result.code of 200 and result.message of "success" once licensing and any other classes in the declaration have completed. DO generates the dossier on the device, submits it to the Activation Service, accepts the EULA, and applies the resulting license internally — none of that is visible as separate steps, only the final declaration status.

In practice this License class is combined with the rest of a first-boot declaration — NTP servers, VLANs, self IPs, module provisioning — so a single declaration brings a freshly deployed BIG-IP from unconfigured and unlicensed to fully onboarded in one pass. Adding licensing to an existing DO declaration is simply a matter of adding the License block shown above alongside whatever other classes are already present.

Ansible — worked example

The f5networks.f5_modules collection provides a dedicated module, bigip_device_license, for licensing a single device as a standalone task. This fits naturally as an early task in an existing playbook, run before any configuration tasks that depend on the device being licensed.

Install the collection if not already present:

ansible-galaxy collection install f5networks.f5_modules

A complete playbook:

---
- name: License BIG-IP
  hosts: localhost
  connection: local
  gather_facts: false

  vars:
    bigip_host: "10.10.10.10"
    bigip_user: "admin"
    bigip_password: "{{ vault_bigip_password }}"
    bigip_regkey: "XXXXX-XXXXX-XXXXX-XXXXX-XXXXXXX"

  tasks:
    - name: Activate and install license
      f5networks.f5_modules.bigip_device_license:
        license_key: "{{ bigip_regkey }}"
        provider:
          server: "{{ bigip_host }}"
          user: "{{ bigip_user }}"
          password: "{{ bigip_password }}"
          server_port: 443
          validate_certs: false
      register: license_result

    - name: Show result
      debug:
        var: license_result

Store the BIG-IP password in Ansible Vault rather than inline in the playbook:

ansible-vault create group_vars/local/vault.yml

with contents:

vault_bigip_password: "your-bigip-password"

Run it:

ansible-playbook license_bigip.yml --ask-vault-pass

On success license_result reports changed: true. Re-running the same playbook against an already-licensed device with the same key reports changed: false, since the module checks the device's current license before attempting activation — safe to leave in place as a recurring task in a playbook that is applied repeatedly.

To remove a license from a device, for example as part of decommissioning, the same module is used with state: absent and license_key omitted:

    - name: Remove license
      f5networks.f5_modules.bigip_device_license:
        state: absent
        provider:
          server: "{{ bigip_host }}"
          user: "{{ bigip_user }}"
          password: "{{ bigip_password }}"
          server_port: 443
          validate_certs: false

Additional Information

  • Where activation actually happens differs between the two approaches. With Declarative Onboarding, the entire process including the call to the Activation Service happens from the BIG-IP itself, so the BIG-IP needs internet access to reach the Activation Service directly. With the Ansible module, the dossier is generated on the BIG-IP but the call to the Activation Service is made from the Ansible control node, so only the control node needs internet access — useful where BIG-IP devices are deliberately kept off the internet.

  • Verify the license took effect on either path by querying the device directly:

    curl -sk -u admin:yourpassword \
  https://10.10.10.10/mgmt/tm/sys/license

    The registrationKey field under entries should match the key supplied.

  • For environments with no internet access anywhere in the automation chain, the dossier can be generated and submitted for offline activation through the My F5 portal manually, with the resulting license file applied to the device separately — for example by writing it to /config/bigip.license via /mgmt/tm/util/bash and running reloadlic — rather than relying on either tool's built-in online activation.

  • Common activation failures are the same regardless of which tool drives them, since both ultimately call the same F5 Activation Service. A failure indicating the key is already active on a different unit means the key needs to be released before reassignment — contact licensingsupport@f5.com with the registration key and chassis serial number. A failure indicating an invalid or internal key means the key supplied is not eligible for production activation; re-confirm the correct key from the My F5 portal.

  • Related resources: the F5 Declarative Onboarding documentation covers the full schema for the License class and how it combines with other onboarding classes in a single declaration. The F5 Ansible collection documentation covers the full parameter set for bigip_device_license, including offline activation options. K2595 and K7752 in the F5 knowledge base cover the underlying activation process in more detail for troubleshooting.
