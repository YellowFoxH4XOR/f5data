Description

When you configure a vlan_group it will bridge traffic not matching a configured listener with the internal listener _vlangroup. This can cause a number of issues in an environment  with HA.

Environment

  • Transparent vlan-group in a HA setup

Cause

First issue is with failsafe. Failsafe works by sending packets out onto the vlan sourced by the vlan-group self-ip and mac-address to multicast address 224.0.0.1 and an appropriate multicast mac-address. The adjacent switch will normally return a copy of the packet to the sender allowing BIG-IP to determine that the vlan is operational. However, in a HA setup the multicast packet is also bridged by _vlangroup. With transparent bridging, the end result is that the active BIP-IP sources a packet with the self-ip and mac-address of the standby. The end result is that local switches get 2 copies of the same frame on different ports and depending which one it gets last, it will update its mac-address table accordingly. The end result can be that the switch is sending packets destined to the standby (eg: monitor) to the active instead.

Second issue relates to the standby learning about the presence of mac-address on the wrong side of the vlan-group. This occurs when various frames are bridged by the active causing the standby to learn about certain mac-address on the wrong side of the vlan-group. This can cause monitor probes to go out on the wrong vlan and fails. The following are possible:

  • Gratuitous arp (GARP) request received in standby. GARP can be sent either either request or reply opcode set. GARP replies are not bridged by design.
  • If two IP addresses have the same source mac address (eg: coming through a NAT gateway), then the standby might incorrectly update the location of one IP by receipt of a bridged arp request sourced by the other.

Recommended Actions

For the first issue any of the following will resolve:

  • Disable failsafe
  • Disable multicast bridging (needs to be done via CLI)
  • Change the vlan-group to either translucent (Default) or opaque mode

For the second issue, both possibilities are resolved by changing the vlan-group to use either translucent (default) or opaque mode.

Additional Information

Transparent mode uses the client source mac-address to learn the address of devices on the serverside. 

Both translucent and opaque mode use a different source mac-addresses when learning the address of the serverside devices.
  • Translucent mode will modify the client source mac-address by setting the  locally-administered bit to 1.
  • Opaque mode will use the BIG-IP vlan mac-address as source.
