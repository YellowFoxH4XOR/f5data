Topic

When troubleshooting issues with restjavad, start from this article. 

Description

restjavad implements iControlREST and together with restnoded and icrd, they form the REST framework. Use the following sections to troubleshoot restjavad memory issues:

  • Services that depend on restjavad
  • restjavad log files
  • Impact of restarting restjavad
  • Troubleshooting restjavad memory issues

Services that depend on restjavad

Services that rely on restjavad include the following: 

  • REST API calls
  • BIG-IQ communications
  • BIG-IP configuration utility, in particular when loading or deploying
    • SSL Orchestrator
    • Access and Advanced/WAF Guided Configuration
    • iApps LX pages and configurations. 
  • Device statistics collection with AVR provisioning
  • Automation toolchain (Application Services 3 (AS3), Declarative Onboarding (DO), Telemetry Streaming (TS))
  • Any automation, scripts that you may have configured using the services listed above.

restjavad log files

Refer to the following log files when troubleshooting issues:

  • /var/log/restjavad.x.log: Refer to this file first and foremost
  • /var/log/restjavad-gc.log.x: garbage collection logs
  • /var/log/restjavad-api-usage.json: keeps statistics on iControl REST transactions. The default size is 100-200K. When it gets too large (around > 3MB), issues may arise.
  • /var/log/restjavad-audit.0.log: Audit log file for API calls.

In certain situations where more information is needed, F5 Support may request that you increase restjavad logging. To do so, refer to K15436: Configuring the verbosity for restjavad logs on the BIG-IP system.

Impact of restarting restjavad

Restarting restjavad or restnoded affects the control plane and the services (listed above) that depend on it. While the data plane is not impacted, in rare situations where system resources (CPU, memory) are exhausted, the system may experience service restarts or even reboot and unable to process traffic.

In most environments, the daemons can typically be restarted with momentary impact on the services listed and does not have an impact on production traffic. In limited cases, depending on your environment, when automation is a critical part, you may want to restart restjavad in a scheduled maintenance window.

In addition, note that REST API calls are not limited to communications with external devices (e.g. management devices), internal API calls that load the Configuration utility and configurations also rely on restjavad and restnoded daemons.

Troubleshooting restjavad memory issues

restjavad memory issues can be grouped into the following 3 categories. If unable to identify the exact root cause, you can perform the recommended action progressively.

Note: As part of initial troubleshooting, you should first verify any core files generated in /shared/core. You can contact F5 Support to have the core file analyzed.

  • Timing issues on startup

    DescriptionSymptomsRecommended action*
    When restjavad timing issues occur occasionally on startup, usually after a reboot or upgrade.

    This most commonly results in the following error messages:

    • On the Configuration utility
      Error getting auth token from login provider
    • /var/log/restjavad.0.log
      [RestWorkerHost] Failed to load all the workers. Exceeded waiting time

    This can be resolved most of the time by restarting the restjavad and restnoded processes. For more information, refer to K000150645: Overview of troubleshooting 'Error getting auth token from login provider'.

    *Beginning from BIG-IP 16.1.5 and 17.1.2, a significant number of restjavad known issues (including ID1025261, ID1153865/ID1153853) have been resolved. F5 recommends updating your system first and foremost to the latest BIG-IP versions before attempting to perform the workarounds. Refer to K2200: Most recent versions of F5 software.

  • Timeout errors

    DescriptionSymptomsRecommended action*
    When restjavad regularly or occasionally times out.

    /var/log/restjavad.0.log
    Exception:java.util.concurrent.TimeoutException

    /var/log/restnoded/restnoded.log
    severe: [Auditor] Failed to run audit cycle [RestOperationNetworkHandler] request timeout.

    When restjavad regularly times out, in most cases, you can increase the timeout values of restjavad, restnoded and icrd to resolve the issue. For more information, refer to K94602685: REST API occasionally times out.

    *Beginning from BIG-IP 16.1.5 and 17.1.2, a significant number of restjavad known issues (including ID1025261, ID1153865/ID1153853) have been resolved. F5 recommends updating your system first and foremost to the latest BIG-IP versions before attempting to perform the workarounds. Refer to K2200: Most recent versions of F5 software.

  • Insufficient restjavad memory

    DescriptionSymptomsRecommended action
    In the worst case of the three, restjavad runs out of memory where you may observe the process restarting. In extreme cases where restjavad keeps restarting, you may observe CPU spikes leading to system degradation.

    /var/log/restjavad.0.log
    java.lang.OutOfMemoryError: Java heap space

    /var/log/daemon.log
    emerg logger[6270]: Re-starting restjavad

    /var/log/restjavad-gc.log.0.current
    [Full GC xxxxK->yyyyyK), x secs]

    Perform the following procedure to increase restjavad memory:

    1. Upgrade your system to the latest BIG-IP version that contains the fix for ID1153865. 
      Note: Beginning in BIG-IP 15.1.9, 16.1.4, 17.1.0, you use provision.restjavad.extramb to provision more memory for restjavad.

    2. Beginning from the existing values on your system, increase DB variable provision.extramb as necessary (heed warning beneath) to provide extra host (4KB page) memory. To avoid capping restjavad memory, it needs to be at least the value of provision.restjavad.extramb - 384.
      To provide flexibility, and extra host memory for other components, it often  makes sense to set it higher. That may also avoid extra unnecessary service restarts.
      Impact of procedure: Modifying provision.extramb restarts TMM and other daemons impacting traffic. F5 recommends performing this during a scheduled maintenance window.  It needs to be set on each peer one at a time.
    3. Check for available host (4KB  page memory) with MemAvailable in cat /proc/meminfo,  to see that it will cover the increase in provision.restjavad.extramb (**default is 384MB)
    4. increase provision.restjavad.extramb incrementally, and restart the daemon to increase restjavad memory. 200MB increments may be suitable. 
    5.  Check ltm log after the restjavad restart as it will log its heap size on start, and re-check MemAvailable.

      For example:
      1. tmsh modify sys db provision.extramb value < 500 or 1000 or 2000 >
      2. tmsh modify sys db provision.restjavad.extramb value < 600 or 1000 or 2000>
      3. tmsh restart sys service restjavad

      In the above examples, the value of provision.restjavad.extramb  is not greater than 384MB  more  than provision.extramb. It can be, but provision.extramb will cap the restjavad. memory.
      To set back to **default use:
      tmsh modify sys db <name> reset-to-default
       For more information selecting the memory for your system, refer to K000133258: Provisioning restjavad memory with provision.restjavad.extramb.

      Also refer to the examples in K00505373: Automation Toolchain restjavad extra memory allocation guidance, when your system uses Automatic toolchain (AS3, DO, TS).
    *In some situations, depending on your environment, F5 Support may advise you to clear the REST storage. For more information, refer to K67220984: Clear-rest-storage. What does it do?.
    Important:
    - Do not clear REST storage on devices that have BIG-IP SSL Orchestrator provisioned and configured as it removes the configuration.
    - If the BIG-IP is managed by a BIG-IQ, clear-rest-storage disconnects the BIG-IP from BIG-IQ management. You'll need to remove the device from the BIG-IQ and rediscover it

    **To display the default value for a DB variable enter printdb -n <DB variable>.

Additional Information

If the issue persists, depending on the memory requirements of your BIG-IP system, you may need to provision more memory to the system.
