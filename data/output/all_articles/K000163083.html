K000163083: BIGIP DNS/GTM marked prober pool down causing "no route" errors

Type
Support Solution
Published
2026-08-25
Updated
2026-08-25
Applies to
  • BIG-IP
  • BIG-IP DNS
Source
https://my.f5.com/manage/s/article/K000163083

Description

BIG-IP DNS may temporarily select an LTM outside the configured prober pool to perform health-monitoring probes after maintenance or iQuery reconnection. If the LTM cannot route to the monitored targets, probes may fail with “no route” errors and monitored resources may be marked DOWN.

Example log messages:

Prober Pool ... state change green --> yellow (Establishing communication)

Prober Pool ... state change yellow --> red (No communication)

Monitor instance ... UP --> DOWN ... (no route)

Prober Pool ... state change yellow --> green

Environment

  • BIG-IP DNS systems are members of a sync group.
  • A specific prober pool is configured.
  • The prober fallback setting is any-available.
  • An LTM or other BIG-IP system is associated with the BIG-IP DNS configuration.
  • The potential fallback device does not have routing to the monitored targets.
  • Maintenance includes one or more of the following:
    • Entering or leaving maintenance mode.
    • Disabling and re-enabling a data-plane interface.
    • Refreshing a license.
    • Reloading the configuration.
    • Reinitializing platform services.
    • Transitioning a traffic group.
  • iQuery connections are interrupted and re-established.

Cause

Maintenance mode does not remove a BIG-IP DNS system from its sync group or configured prober-pool configuration.

When iQuery connections are re-established, connections to peer systems may be established sequentially. During this period, the BIG-IP DNS system may reconnect to an associated LTM before reconnecting to any member of the configured prober pool.

If the prober fallback setting is any-available, the available LTM can be selected as a fallback prober. When the LTM does not have a route to the monitored target, the probe fails with a no route error and the monitored resource may temporarily change to DOWN.

The resource can recover automatically after connectivity to the configured prober-pool members is restored.

Removing a BIG-IP DNS system from the preferred prober pool alone is not sufficient when fallback behavior still permits another available device to perform probing.

Recommended Actions

  • Disable fallback probing
    If unrelated BIG-IP systems must not perform health monitoring, configure the relevant GTM server objects with a prober fallback setting of none:
    tmsh modify gtm server <server-name> prober-fallback none
    tmsh save sys config gtm-only
    Apply the setting to the appropriate server objects.
    Impact of workaround: If all configured prober-pool members are unavailable, probe tasks pause instead of being delegated to another available device. This prevents invalid probe sources but removes the use of an external fallback prober.
  • Prevent specific devices from performing service checks
    For devices that must not be selected as backup probers, set:
    tmsh modify sys db iq-allow-service-checks value no
    This prevents those devices from being selected as probers during normal operation and fallback operation.
  • Consider Ignore Down Response
    For suitable monitors, enable Ignore Down Response to prevent a single transient no route response from immediately marking a resource down when a successful response is received within the configured timeout.
    Impact of workaround: This setting may delay detection of resources that are genuinely unavailable.
  • Validate the maintenance procedure
    • Before maintenance:
      1. Review the configured prober pool and fallback behavior.
      2. Identify every BIG-IP system that could be selected to perform probing.
      3. Verify that each eligible prober has routing to the monitored targets.
      4. Confirm iQuery connectivity between the BIG-IP DNS systems.
      5. Consider setting prober fallback to none when fallback devices do not have equivalent routing.
      6. Do not rely on removing the maintenance device from the preferred prober pool as the only mitigation.
    • After maintenance:
      1. Verify that the configured prober-pool members have returned to a healthy state.
      2. Confirm that monitored resources are not receiving probes from an improperly routed device.
      3. Review /var/log/gtm for prober-pool state changes and no route errors.
      4. If necessary, enable debug probe logging to identify the device originating the probe:
        tmsh modify sys db gtm.debugprobelogging value enable
      5. After troubleshooting, disable debug probe logging:
        tmsh modify sys db gtm.debugprobelogging value disable

Additional Information

  • The default prober fallback behavior is Any Available.
  • A configured prober pool controls preferred probing devices; fallback settings determine what happens when those devices are unavailable.
  • An LTM can be selected as a fallback prober if it is available through iQuery and fallback behavior permits any available device.
  • The selected prober must have network reachability to the monitored targets.
  • Temporary resource state changes can occur when a fallback prober has incomplete or incorrect routing.
  • No software defect was identified for this behavior.
