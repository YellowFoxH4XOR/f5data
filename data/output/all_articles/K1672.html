Topic

This is not a problem with BIG-IP or the load balancing configuration. This issue is caused by the way that the Internet Explorer browser interacts with the web server configuration.

SSL proxy and HTTP keep-alives process description

The client requests data from the SSL secured portion of a web site, which is an SSL proxy on BIG-IP. In this request, the client also requests that keep-alives are enabled. The SSL proxy on BIG-IP receives the request, decrypts the data, and forwards the traffic to the virtual server, which is also on BIG-IP. The virtual server forwards this traffic to the server that to which the connection is load balanced.

The server supplies the requested data to the virtual server with the following header settings:

Keep-Alive: timeout=15, max=8

The virtual server passes the data to the SSL proxy on BIG-IP and the SSL proxy re-encrypts the data and sends it back to the client.

The timeout value in the header defines the amount of idle time that the server will wait to accept HTTP sessions from the client over the same TCP connection. The max value defines the maximum number of HTTP sessions that the server will accept over the same TCP connection.

The purpose of the timeout value for keep-alives is to prevent TCP connections from being open for unlimited periods of time and consuming server resources. The purpose of the max value is to prevent a client from monopolizing server resources.

Note: Additional information about keep-alive values, as well as information about Microsoft Internet Explorer compatibility issues with keep-alives, is provided on the apache.org web site at http://httpd.apache.org/docs/keepalive.html

In this example, a user is buying something on a site and they are prompted to fill out a form so they can check out. When the user takes more than 15 seconds to fill out the form, the server closes the connection.

As per RFC standards, the following occurs:

When the server closes the TCP connection, it sends a FIN message to the client. This FIN message is passed to the virtual server, the virtual server passes the FIN message to the SSL Proxy, and the SSL Proxy sends an ACK message to acknowledge the server's FIN message. The SSL proxy then sends a FIN message to the server and the server acknowledges it with an ACK message. At this point, the connection between the server and the BIG-IP SSL proxy is considered closed.

At the same time as the SSL proxy and server are properly closing their session, the SSL proxy sends a standard SSL Encryption Alert to the client that informs the client to tear down the SSL session. The SSL proxy also sends a FIN message to the client and the client responds with an ACK message; however, Internet Explorer never sends a FIN message to the SSL proxy so that it finishes tearing down the session so the client browser does not recognize that the connection has closed.

After the user completes the form and submits it, the server sends an HTTP POST to the SSL Proxy over the TCP connection that has closed. In response, the BIG-IP's SSL proxy provides the standard Reset packet to the client. The client browser then recognizes the connection has closed and displays an ambiguous HTTP error, such as Page cannot be displayed, to the user. Internet Explorer does not attempt to resend the request to the server/SSL proxy.

Solution

You can eliminate this issue by removing or increasing the HTTP keep-alive timeout on the server configuration. For specific configuration options, refer to http://httpd.apache.org/docs/keepalive.html

Common questions

  • Why doesn't this issue occur when I wait a minimum of 16 seconds before loading each page?

    Eventually, the client will close out the HTTP session. When it does, Internet Explorer uses a new HTTP session and, therefore, a new TCP connection to send the HTTP POST for the form. The amount of time that Internet Explorer waits to do this varies.

  • Why doesn't this issue occur when I complete the form within 15 seconds?

    15 seconds is the timeout value, so the TCP and HTTP sessions to the server are still considered open and ready to accept HTTP requests (such as GET or POST) if the form is submitted within this timeout limit.

  • Why doesn't this issue occur when I resubmit the form (after the error page) or use the Back button, then use the Forward button?

    It works under these circumstances, because Internet Explorer considered the old TCP/HTTP session closed after it received the Reset packet from the BIG-IP's SSL proxy and submitted the POST on a new TCP/HTTP session.

  • Why doesn't this issue occur when I terminate SSL on the server?

    Since Internet Explorer never finishes closing the connection with the server when the server requests that it is closed, the server still allows the client to continue to send data to it through the same TCP connection. When the server sends the FIN message, to which Internet Explorer responds with an ACK message, the server enters a TCP half closed state and advises the client that it is finished transmitting; however, the client has not advised the server that the client is finished. If the client had sent both an ACK and a FIN/ACK packet, the connection would have been closed properly.
