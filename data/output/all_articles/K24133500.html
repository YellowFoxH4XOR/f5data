Known Issue

A VIPRION blade may erroneously re-enable itself when you attempt to disable it.

This issue may occasionally occur when all of the following conditions are met:

  • You have a pair of VIPRIONs configured in a high availability (HA) configuration.
  • You configure the VIPRIONs to perform HA failover based on the min-up-members option.

    For example, if both of the VIPRIONs are running with two blades and have HA configured with min-up-members set to 2, a disabled blade on the active HA member will trigger a failover to the standby unit.

  • You attempt to manually disable the primary blade of the active HA member.

    Note: Subsequent attempts to disable the blade may work.

Impact

You may be unable to manually disable a VIPRION blade.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • The VIPRION blade re-enables itself immediately after you attempt to disable it.

Workaround

There is no work around. However, you can mitigate the issue by setting the HA min-up-members to a lower value, so that the VIPRION is less likely to trigger an HA failover when a single blade is disabled. To do so, you can perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the TMOS Shell (tmsh) of the VIPRION system by typing the following command:

    tmsh

  2. To reconfigure the min-up-members setting to a lower value on the VIPRION system, use the following command syntax:

    modify /sys cluster default min-up-members <value>

    For example, if the min-up-members setting is set to 2, you can lower the min-up-members setting to 1 by typing the following command:

    modify /sys cluster default min-up-members 1

  3. Save the configuration by typing the following command:

    save /sys config

  4. Repeat steps 1 to 3 on the peer VIPRION system.
