Topic

NGINX Controller is compatible with SELinux running on the following supported Linux distributions: CentOs 7.x, RedHat EL 7.x (Rhel7.x), Ubuntu 18.04, or Ubuntu 20.04.

SELinux is installed and fully provisioned but disabled by default on CentOS 7.x and RedHat EL 7.x. To have NGINX Controller and its associated agents running in an SELinux-protected CentOs 7.x or Rhel7.x environment, you must first perform a few additional procedures. For more information, read the following sections of this article.

On Ubuntu, by default, the Linux SE of choice is AppArmor, which means that you before you can install NGINX Controller or one of its agents, you must first install SELinux and have its security policies provisioned in a manner which allows the host to run properly.

Description

SELinux preparation

The following approach acts as a guide when configuring SELinux on Linux hosts intended for an instance of NGINX Controller or one of its agents. For a more in-depth discussion of SELinux, you can find a wealth of helpful articles and books on the subject by searching online.

The following approach assumes that the SELinux administrator has sudo privileges and that SELinux is installed and is either disabled or in Permissive mode. It also assumes the use of targeted as the SELinux security policy type.

You can configure SELinux to implement either a targeted policy or a multilevel security (MLS) policy. A targeted policy applies access controls to a limited number of processes on the system that attackers are most likely to target.

On CentOs7.x and Rhel7.x, the default active security policy type is targeted, whereas on Ubuntu it is default. To check the state of your SELinux installation, at the terminal, enter the following command:

sudo sestatus

If your system is configured for the targeted security policy type and is currently active but not enforcing the installed security policies, output should appear similar to the following. This is referred to as being in permissive mode:

# sudo sestatus
SELinux status:                 enabled
SELinuxfs mount:                /sys/fs/selinux
SELinux root directory:         /etc/selinux
Loaded policy name:             targeted
Current mode:                   permissive
Mode from config file:          permissive
Policy MLS status:              enabled
Policy deny_unknown status:     allowed
Max kernel policy version:      28

or

SELinux status:                 disabled

The configuration for your SELinux system is predominantly expressed by the high-level configuration file /etc/selinux/config and the active policy modules found in the /etc/selinux/targeted/active/modules file.

Important: Unless you are sure your policies are correct, never set the operational mode to enforcing in the /etc/selinux/config file and restart. Doing so prematurely may cause the loss of the Linux host.

Change to permissive mode
To change from disabled to permissive mode, perform the following actions:

CentOs 7.x and Rhel7.x

  1. At the terminal, enter the following commands:

    sudo reboot
    sudo touch /.autorelabel

  2. Save the changes
  3. Change the line SELINUX=disabled to SELINUX=permissive.
  4. Enter the following command:

    sudo vi /etc/selinux/config

Ubuntu 18.04 and 20.04

  • Enter the following commands:

    sudo selinux-activate

    reboot

Note: If you are restarting for the first time, the Linux host may take some time to respond. This is normal as during startup because SELinux needs to appropriately label every file to serve its purpose, and, depending on the number files it needs to label, this may take some time. Furthermore, if your SELinux was disabled for an extended period, F5 recommends that you refresh the SELinux labels. You can accomplish this using the previously described steps.

For testing purposes, you can temporarily change the SELinux operational mode by entering the following command syntax:

sudo setenforce <0/1>

The following examples demonstrate using this syntax to set the mode to permissive and enforcing, respectively:

# sudo setenforce 0 
  (permissive)
# sudo setenforce 1 
  (enforcing)

Restarting the host restores the mode defined in /etc/selinux/config.

To quickly discover which mode is currently active, at the terminal, enter the following command:

sudo getenforce

The output appears similar to the following example:

# sudo getenforce
Permissive

To install auditd on Ubuntu 20.04, at the terminal, enter the following commands:

sudo apt-get update -y
sudo apt-get install -y auditd

From this point on, this approach assumes your SElinux system is in permissive mode and is set to targeted. The following process uses tools provided by default with your SELinux installation and the logs of the auditd service, which are in the /var/log/audit/auditd.log file.

Manually rotate auditd logs

The auditd service automatically rotates its logs periodically. If you need to rotate them on demand, you can use the following procedure.

  • At the terminal, enter the following commands:

sudo mv /var/log/audit/audit.log /var/log/audit/audit.log.ondemand.1
sudo touch /var/log/audit/audit.log
sudo chmod 0600 /var/log/audit/audit.log
sudo service auditd restart

Note: The name audit.log.ondemand.1 is used to avoid collisions because the auditd default naming policy uses audit.log.n.

SELinux policy development

Background information

After SELinux is running and set to permissive mode and the with filesystem labelling is completed, you should restart the system again and allow it to run for approximately a day to ensure that SE Linux has a chance to vet the majority of the Linux services and subsystems and logs any corresponding denials to the auditd logs.

The SELinux vetting process produces many types of entries in the auditd logs. These appear similar to the following example:

type=SERVICE_START msg=audit(1619547788.116:43): pid=1 uid=0 auid=4294967295 ses=4294967295 subj=system_u:system_r:init_t:s0 msg='unit=getty@tty1 comm="systemd" exe="/usr/lib/systemd/systemd" hostname=? addr=? terminal=? res=success'

When traversing logs, focus your interest on entries containing the text denied because these entries require the creation of a policy to succeed and for the corresponding application to correctly function. This functionality can include port bindings and file I/O.

An example of such an entry appears as follows:

type=AVC msg=audit(1622807492.524:70): avc:  denied  { execmem } for  pid=740 comm="none" scontext=system_u:system_r:kernel_t:s0 tcontext=system_u:system_r:kernel_t:s0 tclass=process permissive=1

At its core, SELinux is a labelling system. Processes and users have labels (or domains) and only resources with labels that match the processes domain may be used, consumed, modified, deleted, created, and so on. If an application tries to perform an action that SELinux does not approve of, in permissive mode, SELinix logs a denied message to auditd before the action is allowed to continue. If the system is in enforcing mode, SELinux logs the denial, and the action is blocked.

SELinux works on the principle of least permissions. In a bare system, a process or user starts with no or limited permissions. The system must write, compile, and load a security policy into the Linux kernel to give it more permissions. Allowing the system to run for a set period before beginning provides time for any denials of Linux system processes or allowed services to be captured in the auditd logs before any work is done for NGINX Controller or its agents. The msg=(1622807492.524:70) ID is unique to each message and can be used to locate denials or as a checkpoint in large auditd log files. The details of multilevel or multicategory security is beyond the scope of this document, but, in general, these levels allow for even more fine-grained approach to the SELinux security configuration.

Policy development process

The process to identify and process any denials is same whether the Linux host is set up for NGINX Controller or its agent or the NGINX Controller or its agent is being installed or is running.

In practice, allowing the auditd log to grow and process rather than breaking it up is more convenient and less error-prone.

  1. Locate and record the ID of the last message in the /var/log/audit/audit.log file. This allows quick identification of any new denials.
  2. Ensure SELinux is in permissive mode by entering the following command:

    sudo vi /etc/selinux/config

  3. Set SELINUX=permissive.
  4. Save the changes.
  5. Restart the Linux host.
  6. Install NGINX Controller Agent on all intended Linux hosts.
  7. Install the required licenses.
  8. Run a test of NGINX Controller to exercise its functionality and trigger any SELinux denials that need to be included in the policy to be developed. As a baseline, the shakedown test should include the following steps:
    1. Stop or start the Kubelet service by entering the appropriate command, respectively:

      sudo systemctl stop kubelet

      sudo systemctl start kubelet

    2. Stop/Start the Docker service by entering the appropriate command, respectively:

      sudo systemctl stop docker

      sudo systemctl start docker

    3. Stop or start NGINX Controller Agent by entering the appropriate command, respectively:

      /opt/nginx-controller/helper.sh controller start

      /opt/nginx-controller/helper.sh controller stop

      sudo systemctl stop controller-agent

      sudo systemctl start controller-agent

    4. Trigger internal NGINX Controller reconciliation by entering the following command:

      /opt/nginx-controller/helper.sh controller reconcile

    5. In the NGINX Controller user interface, create the necessary objects to monitor and configure the intended target NGINX Plus instances.
    6. For Analytics confirm that the NGINX Plus instances are sending data back to the controller.
    7. Create a support package by entering the following command:

      /opt/nginx-controller/helper.sh supportpkg -o ./supportpkg.tar

    8. Create a cluster-config backup by entering the following command:

      /opt/nginx-controller/helper.sh cluster-config save

    9. Restart all Linux hosts
  9. If the embedded database option is being used for a controller, allow your system to run until at least one database rollup job and one backup of the configuration database (postgres) is created.
  10. F5 recommends now allowing the system to run for another five days and allow administrators to further exercise the system. F5 does not recommend allowing other users onto the system at this stage.
  11. You can now develop polices, repeating the following steps on each Linux host. Create a type enforcement (.te) file from the auditd logs, which is essentially a human-readable policy source file. Compile the type enforcement file into a loadable policy package (pp) file by entering the following commands:

    mkdir workarea
    cd workarea
    sudo cat /var/log/audit/audit.log | audit2allow -M
    combined_denied_<hostname>

  12. Load the policy into the running kernel by entering the following command:

    sudo semodule -i combined_denied_<hostname>.pp

  13. Check that the policy module is loaded by entering one of the following commands:

    sudo semodule -l | grep combined_denied

    or

    sudo ls -al /etc/selinux/targeted/active/modules | grep combined_denied

  14. To delete a policy, use the following command syntax:

    sudo semodule -r combined_denied_<hostname>

  15. Restart each Linux host
  16. It is now appropriate to temporarily set each of your hosts to enforcing to test your system. Note that you should do this taking in account previously listed precautions and after reading the following troubleshooting section. If any further issues occur, you should reset the system to permissive mode and inspect the audit and any failing component logs for any actions blocked by SELinux.

    sudo setenforce 1

  17. Repeat the test detailed earlier.
  18. Permanently set SELinux on each host to enforcing and restart by performing the following steps. F5 recommends you do this one host at a time:
    1. Enter the following command:

      sudo vi /etc/selinux/config

    2. Set SELINUX=enforcing
    3. Save the changes.
    4. Restart the Linux host.

Note: The combined_denied_<hostname> is only used for tracking purposes. You can use any module name as long as it follows the appropriate naming convention. Additionally, the type enforcement and policy package file names and module name must match exactly.

SELinux policy refinement

You can leave policy refinement until a full set of policy modules that achieve the result you want are created. At this point, you can review the complete set of type enforcement source files to remove any redundancies. F5 recommends that an experienced SELinux administrator conduct this review.
