K000138404: rSeries configuration backup failed to restore: "Error: access denied"

Type
Support Solution
Published
2024-01-30
Updated
2024-02-29
Applies to
  • rSeries Platforms
  • F5OS
  • F5OS-A: 1.5.1, 1.5.0, 1.4.X, 1.3.X, 1.2.X, 1.4.0, 1.3.2, 1.3.1, 1.3.0, 1.2.0
Source
https://my.f5.com/manage/s/article/K000138404

Description

Attempted to restore a configuration backup file to an rSeries system with minimal configuration (e.g. RMA replacement, or after clean install).

Backup restoration failed:

appliance-1(config)# system database config-restore name f5os-a-1-5-0-backup.xml
A clean configuration is required before restoring to a previous configuration.
Please perform a reset-to-default operation if you have not done so already.
Proceed? [yes/no]: yes
Error: access denied
Database config-restore failed.

Environment

  • rSeries
  • Configuration backup and restore

Cause

Bug ID 1284269: Config restore fails if it contains an SNMP user

Recommended Actions

There are two known workarounds to this problem.

Add an SNMP user to the configuration, then remove it

One workaround is to add an SNMP user to the configuration, remove it, then load the original configuration backup once more.

conf
system snmp users user dummy_user config authentication-protocol sha privacy-protocol aes
commit
no system snmp users user dummy_user
commit

Attempts to load the configuration backup again should succeed at this point.

Edit the configuration backup

An alternative workaround is to edit the backup file, removing the configuration in question.

Adding an SNMP user to the configuration creates several type of configuration object. These must all be removed.

For example, remove these lines for a user created with the username myuser:

>      <SNMP-USER-BASED-SM-MIB xmlns="http://tail-f.com/ns/mibs/SNMP-USER-BASED-SM-MIB/200210160000Z"
>        <usmUserTable>
>          <usmUserEntry>
>            <usmUserEngineID>80:00:2f:f4:03:14:a9:d0:1f:3d:02</usmUserEngineID>
>            <usmUserName>myuser</usmUserName>
>            <usmUserSecurityName>myuser</usmUserSecurityName>
>            <usmUserAuthProtocol>1.3.6.1.6.3.10.1.1.3</usmUserAuthProtocol>
>            <usmUserPrivProtocol>1.3.6.1.6.3.10.1.2.4</usmUserPrivProtocol>
>          </usmUserEntry>
>        </usmUserTable>
>      </SNMP-USER-BASED-SM-MIB>

>        <vacmSecurityToGroupTable>
>          <vacmSecurityToGroupEntry>
>            <vacmSecurityModel>3</vacmSecurityModel>
>            <vacmSecurityName>myuser</vacmSecurityName>
>            <vacmGroupName>authPriv</vacmGroupName>
>          </vacmSecurityToGroupEntry>
>        </vacmSecurityToGroupTable>

>          <vacmAccessEntry>
>            <vacmGroupName>authPriv</vacmGroupName>
>            <vacmAccessContextPrefix></vacmAccessContextPrefix>
>            <vacmAccessSecurityModel>3</vacmAccessSecurityModel>
>            <vacmAccessSecurityLevel>authPriv</vacmAccessSecurityLevel>
>            <vacmAccessContextMatch>exact</vacmAccessContextMatch>
>            <vacmAccessReadViewName>internet</vacmAccessReadViewName>
>            <vacmAccessNotifyViewName>internet</vacmAccessNotifyViewName>
>          </vacmAccessEntry>

>          <users>
>            <user>
>              <name>myuser</name>
>              <config>
>                <name>myuser</name>
>                <authentication-protocol>sha</authentication-protocol>
>                <privacy-protocol>aes</privacy-protocol>
>              </config>
>            </user>
>          </users>

Note: Save a copy of the original backup file to revert to if mistakes are made.

Additional Information

Configuration load failure can have a variety of different root causes. If you do not have SNMP users defined in the backup or are not running one of the versions affected by ID1284269, your system is not affected by this issue.
