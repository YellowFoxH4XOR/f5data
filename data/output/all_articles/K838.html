Introduction

DCOM is a Microsoft protocol analogous to CORBA/IIOP. The design of DCOM makes use with address translation impossible, causing severe challenges to load balancing. This document outlines some strategies for load balancing DCOM.

Issues and solutions

DCOM Presents four main problems that must be solved or worked around for effective load balancing.

Source address in data payload

Issue #1

A common problem in applications using address translation is a source address located in the data payload of a packet. This occurs because the DCOM servers embed the source address deep in the packet in a non-specific location so it is not possible to translate the address. Because clients respond to this source address, they attempt to respond directly to nodes, rather than to virtual servers (VIPs).

Solution

The only way to address this problem is to allow it to function as intended. With the BIG-IP Controller, this means using routable addresses on the nodes and making use of IP forwarding on the BIG-IP Controller. In this configuration, clients will have the ability to communicate directly with the nodes after the initial connection is load balanced.

Dynamically assigned ports

Issue #2

DCOM makes use of dynamically assigned ports, rather than fixed ports, for object servers. In a default configuration, DCOM can make use of any port from 1024 to 65535 for object servers. Clients learn the port for the object server they need from the DCOM Service Control Manager (SCM) on port 135. Due to the wide range of possible ports, it is very difficult to assign specific VIPs.

Solution

The biggest concern of dynamically assigned ports is security. IP filters can be used to tighten security on the BIG-IP if the range of ports used by DCOM is limited. You can change this range by manipulating some of the registry settings on the DCOM server.

Follow the steps below to change the port range for Windows NT 4.0:

  1. If it does not already exist, create the following key (classless):

    HKEY_LOCAL_MACHINE\Software\Microsoft\Rpc\Internet

  2. Create the value Ports:

    Type: REG_MULTI_SZ
    Value: port-range (i.e. 5000-6000)

  3. Create the value PortsInternetAvailable:

    Type: REG_SZ
    Value: "Y"

  4. Create the value UseInternetPorts:

    Type: REG_SZ
    Value: "Y" or "N"

    (Y indicates you want to use only the ports you indicated in Ports; N indicates that you wish to use any ports other than those you listed.)

DCOM communicates on both TCP and UDP

Issue #3

DCOM always attempts to connect with UDP first, then with TCP if UDP fails. UDP is only successful when both the client and the server are Windows NT 4.0. There is a 30-second timeout before UDP communications are determined to be unsuccessful. Because this UDP communication can take place on a wide range of ports, it is generally not desired in situations where security is a concern.

Solution

The easiest way to configure DCOM is to use TCP as its primary mode of communication rather than to allow the wide range of UDP ports it may use. To set DCOM to use TCP-only communication, modify the HKEY_LOCAL_MACHINE\Software\Microsoft\Rpc registry key so that NCACN_IP_TCP is the first listed value.

Call-backs

Issue #4

DCOM can employ call-backs, where the server initiates a connection outbound to the client. This requires the ability to allow outbound connections through the BIG-IP Controller.

Solution

The solution for call-backs is the same as the solution outlined in the Source address in data payload section. IP forwarding in combination with internet-routable addresses eliminates this problem.

Scenarios

DCOM server internal to the BIG-IP Controller and clients are external

In this scenario, clients on the internet need to connect to a group of DCOM servers behind a BIG-IP Controller. The goal in this case, is to load balance the initial connections to the servers and then allow them to finish the sessions directly. Following the steps below to create this configuration:

  1. Create a VIP using TCP port 135 (DCOM Service Control Manager) that load balances to port 135 on the DCOM servers.

    For instructions specific to the version of the BIG-IP Controller you are using, refer to the BIG-IP manual:

  2. Enable IP forwarding on the BIG-IP Controller.

    For instructions specific to the version of the BIG-IP Controller you are using, refer to the BIG-IP manual:

  3. Set the treaper for port 135 to a very low value (such as 1 second).

    For information on the treaper command and how to use it, see K397: Configuring BIG-IP to close idle connections.

  4. Configure the DCOM server to use only TCP (see the DCOM communicates on both TCP and UDP section above).

DCOM Server and Clients Internal to BIG-IP

In this scenario, both clients and server are internal to the BIG-IP Controller. The goal is to load balance the initial connections using VIP bounceback. Following the steps below to create this configuration:

  1. Create a VIP using TCP port 135 (DCOM Service Control Manager) that load balances to port 135 on the DCOM servers.

    For instructions specific to the version of the BIG-IP Controller you are using, refer to the BIG-IP manual:

  2. Create either a default SNAT or a SNAT that includes all clients that will use DCOM.

    For instructions specific to the version of the BIG-IP Controller you are using, refer to the BIG-IP manual:

  3. Enable IP forwarding on the BIG-IP Controller.

    For instructions specific to the version of the BIG-IP Controller you are using, refer to the BIG-IP manual:

  4. Set the treaper for port 135 to a very low value (such as 1 second).

    For information on the treaper command and how to use it, see K397: Configuring BIG-IP to close idle connections.

  5. Configure the DCOM server to use only TCP (see the DCOM communicates on both TCP and UDP section above).
