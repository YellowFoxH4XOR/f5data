Description

Aspen Mesh envoy sidecars has many options on how it will resolve DNS depending on the cluster type.

An envoy cluster is a group of logically similar upstream hosts that Envoy connects to. Envoy discovers the members of a cluster via service discovery.

There are 5 types of clusters: STATIC, Strict DNS, Logical DNS, Original destination (DST) and EDS (endpoints discovery service).

There are also many difference in the configuration in each cluster you can found more information here.

We will mainly focus on Strict DNS which is the preferred cluster type in Istio and Aspen Mesh when we create a Service Entry with resolution type: DNS.

Environment

  • RedHat Openshift: 4.6.x, 4.7.x 4.8.x, 4.9.x, 4.10.x
  • Kuberntes: 1.17x, 1.18.x, 1.19.x, 1.20.x, 1.21.x, 1.22.x, 1.23.x
  • Aspen Mesh: 1.6.x, 1.9.x , 1.11.x, 1.14.x

Cause

Service Entry is a definition for our sidecars to establish a connection with external services. If you want to know more about Service Entry best practices refer to the following article:
K00612159: Aspen Mesh Service Entry best practices

A Service Entry could have three different resolution types: NONE, STATIC (which will be translated to a STATIC cluster), and DNS (this is the Strict DNS cluster).

The difference between the last two is:

  • STATIC you need to provide endpoints to resolve an FQDN, we are assuming those IP endpoints will resolve our host and won’t change, then allow the communication with the external service.
  • When the type is DNS, no endpoints are provided, but each sidecar will query our local DNS server to retrieve those IP addresses.

Imagine a scenario where we have more than 10 Service Entries and more than 50 sidecars running in a cluster, each sidecar will query those 10 external services that can be translated into a hundred or thousand queries.

The behavior of envoy is to refresh the DNS endpoints every 5 seconds (5s is the default refresh rate) on a small cluster configuration this will not represent an issue, but as soon as your cluster grows maybe you will start seeing more and more queries. If this is the case, then you should think on increase the refresh rate.

Recommended Actions

  1. Increase the dnsRefreshRate
  2. About dnsRefreshRate and respect_dns_ttl

Increase the dnsRefreshRate

  1. To increase the dnsRefreshRate, we need to update our override values file as follows:

    meshConfig:
      dnsRefreshRate: 60s

  2. Upgrade your Aspen Mesh installation:

    helm upgrade -i istiod manifest/charts/istio-control/istio-discovery -n istio-system –values aspen-mesh-values.yaml

  3. After upgrade the installation, there is no need to bounce your application/sidecars automatically will receive the new configuration. You can verify the change with the following command:

    istioctl pc clusters <your-pod> --port 443 -o json

About dnsRefreshRate and respect_dns_ttl

In our example above we increase the refreshRate but there is another field called respectDnsTtl.

If respect_dns_ttl is enabled (this is default in Aspen Mesh), DNS record TTLs and dns_refresh_rate are used to control DNS refresh rate. 

For Strict DNS cluster, if the minimum of all record TTLs is 0, dns_refresh_rate will be used as the cluster’s DNS refresh rate. Otherwise, the sidecar will use the dns_ttl as refreshRate and will ignore the dnsRefreshRate configured.
