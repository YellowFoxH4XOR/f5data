Topic

This article applies to BIG-IP 9.x - 11.3.x. For information about other versions, refer to the following article:

  • K14813: Detecting and mitigating DoS/DDoS attacks (11.4.x - 16.x)

The BIG-IP system default configuration is secure; the system denies all traffic except for traffic types that you specifically configure the system to accept. Although the deny-by-default approach protects against attacks on unused addresses and services, remote attackers may initiate denial-of-service (DoS) attacks, which attempt to prevent legitimate users from accessing configured addresses and services. The BIG-IP system includes configuration options which can help to mitigate the effects of such attacks.

Global Settings

Global settings that can mitigate denial-of-service attacks include the following:

  • Adaptive connection reaping
  • SYN flood protection
  • BigDB settings

Adaptive connection reaping

Adaptive reaping is a global setting that allows the BIG-IP system to remove connections from its connection table when the connection load surpasses a defined percentage of memory usage.

To mitigate DoS attacks, you can configure low-water mark and high-water mark thresholds, as follows:

  • The low-water mark threshold determines the percentage of memory usage at which the system silently purges stale connections from the connection table. When the memory usage remains above the low-water mark, adaptive reaping becomes more aggressive and active connections closest to their service timeout are purged by the BIG-IP system.
  • The high-water mark threshold determines the percentage of memory usage at which the system prevents new connections from being established. When the memory usage exceeds the high-water mark, the BIG-IP system does not accept new connections until the memory usage drops below the low-water mark threshold.

To configure adaptive connection reaping on the BIG-IP system, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Select System.
  3. Select General Properties for 9.x, or Configuration for 10.x - 11.x.
  4. From the Local Traffic menu, select General.
  5. In the Properties section, set the Reaper High-water Mark and Reaper Low-water Mark settings.

    Note: To disable adaptive connection reaping, set both values to 100.

  6. Select Update.

Adaptive connection reaping events, similar to the following examples, log to the /var/log/ltm file:

tmm tmm[714]: 011e0002:4: sweeper_update: aggressive mode activated. (117504/138240 pages)
tmm tmm[714]: 011e0002:4: sweeper_update: aggressive mode deactivated. (117503/138240 pages)

SYN flood protection

The BIG-IP system includes a feature known as SYN Check, which helps prevent the BIG-IP SYN queue from becoming full during a SYN flood attack. The SYN Check Activation Threshold setting indicates the number of new TCP connections that can be established before the BIG-IP LTM activates the SYN Cookies authentication method for subsequent TCP connections. When the BIG-IP LTM system activates the SYN Cookies authentication method, the system does not need to keep the SYN-RECEIVED state that is normally stored in the connection table for the initiated session. Because the SYN-RECEIVED state is not kept for a connection, the SYN queue cannot be exhausted, and normal TCP communication can continue.

Note: For more information about BIG-IP SYN cookie protection, refer to K7847: Overview of BIG-IP SYN cookie protection (9.x - 11.2.x).

The default value for the SYN Check Activation Threshold setting is 16,384 connections. To adjust the SYN Check Activation Threshold, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Select System.
  3. Select General Properties for 9.x, or select Configuration for 10.x - 11.x.
  4. From the Local Traffic menu, select General.
  5. Enter a value in the SYN Check Activation Threshold box.
  6. Select Update.

BigDB settings

  • The TM.MaxRejectRate BigDB key can reduce the effects of a DoS attack by allowing you to limit the number of TCP RSTs or Internet Control Message Protocol (ICMP) unreachable packets that the BIG-IP system sends in response to incoming connections that cannot be matched with virtual server connections.

    Note: For more information, refer to K9259: Configuring the rate at which the BIG-IP system issues TCP RSTs or ICMP unreachable packets (9.x - 10.x).

  • The TM.MaxICMPRate BigDB key can reduce the effects of a DoS attack by allowing you to limit the number of responses the BIG-IP LTM system will send for ICMP errors and ICMP unreachable events.

    Note: For more information, refer to K7113: Limiting responses from the BIG-IP LTM system for ICMP errors and ICMP unreachable events.

BIG-IP object settings

You can make the following configuration adjustments to specific objects to minimize the potential of a successful denial-of-service attack:

  • Protocol profile Idle Timeouts
  • TCP profile settings
  • IP rate classes
  • Virtual server connection limits
  • iRules

Protocol profile Idle Timeouts

Stale connection table entries can cause the BIG-IP system's memory utilization to increase, leaving fewer system resources available for legitimate connections. Lowering the Idle Timeout in the protocol profiles that are assigned to active virtual servers allows the BIG-IP system to remove stale connections from the connection table earlier, freeing up system resources.

To adjust the Idle Timeout in a protocol profile, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Select Local Traffic.
  3. Select Profiles.
  4. From the Protocol menu, select the type of profile to modify (such as TCP).
  5. Select the name of the profile to modify.
  6. In the Settings section, select Specify from the Idle Timeout list.
  7. Type the new timeout value in the field.

    For example, to lower the TCP Idle Timeout from the default value of 300 seconds to a new value of 60 seconds, type 60.

  8. Select Update.

TCP profile settings

TCP profile settings include Maximum Segment Retransmissions or Deferred Accept.

Maximum Segment Retransmissions

The Maximum Segment Retransmissions setting specifies the maximum number of data segment retransmissions that the BIG-IP system allows. The default is eight retransmissions. When the default number of retransmissions is exceeded, the Traffic Management Microkernel (TMM) resets the TCP connection to avoid resource starvation during a potential DoS attack.

The Maximum Syn Retransmissions setting specifies the maximum number of times that the BIG-IP system retransmits a SYN packet when it does not receive a corresponding SYN-ACK. The default is four retransmissions.

To change either the Maximum Segment Retransmission setting or the Maximum Syn Retransmissions setting, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Select Local Traffic.
  3. Select Profiles.
  4. From the Protocols menu, select TCP.
  5. Select the relevant TCP profile.
  6. Change the Maximum Segment Retransmission setting or the Maximum Syn Retransmissions setting.
  7. Select Update.

Deferred Accept

The Deferred Accept option specifies that the BIG-IP system does not dedicate resources to the connection until the system receives the data packet from the client. This setting is useful when negotiating three-way handshake DoS attacks.

By default, the Deferred Accept option is disabled on the BIG-IP LTM.

To enable the Deferred Accept setting, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Select Local Traffic.
  3. Select Profiles.
  4. From the Protocols menu, select TCP.
  5. Select the relevant TCP profile.
  6. Select the Deferred Accept box.
  7. Select Update.

Note: The Deferred Accept option is not compatible with some applications. For more information, refer to K4654: The Deferred Accept TCP Profile option may not be compatible with some applications.

IP rate class

A rate class is a rate-shaping policy that allows you to enforce a throughput restriction on incoming traffic. To implement a rate-shaping policy, you must create a rate class, and then apply the rate class to the virtual server. For example, you can create an IP rate class of 30 Mbps, with a maximum queue size of 2 Mbps.

Note: The rate class module does not require an add-on license key for hardware manufactured after 04-May-2010.

To create a rate class, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Select Local Traffic (select Network in 10.x).
  3. Select Rate Shaping.
  4. Select Create.
  5. Type a name for the Rate Class.
  6. In the Base Rate box, type 2000000 (2 Mbps).
  7. In the Ceiling Rate box, type 30000000 (30 Mbps).
  8. In the Burst Size box, type 500 and select Megabytes from the list.
  9. From the Direction list, select Any.
  10. From the Queue Discipline list, select Stochastic Fair Queue.
  11. Select Finished.

You must now associate the rate class with the virtual server.

Virtual server connection limits

You can configure connection limits for the virtual server. The connection limits determine the maximum number of concurrent connections allowed for a virtual server.

Note: The BIG-IP system sends a TCP reset in response to connection attempts to a virtual server for which the connection limit is reached.

To configure connection limits for the virtual server, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Select Local Traffic.
  3. Select Virtual Servers.
  4. Select the virtual server for which you want to configure the connection limit.
  5. From the Configuration menu, select Advanced.
  6. Type a Connection Limit for the virtual server.
  7. Select Update.

iRules

You can create an iRule that blocks or limits the number of requests that match a specific profile to filter out a specific connection-based DoS attack. If you can profile the requests that result from a particular DoS attack, then you can write an iRule that discards requests based on those specific criteria, such as source IP address or request pattern.

For example, using an iRule, the BIG-IP system can mitigate the effects of the Slowloris denial-of-service attack as detailed in K10260: Mitigating Slowloris DoS attacks with the BIG-IP system
