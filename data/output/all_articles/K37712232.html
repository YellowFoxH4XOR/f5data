Introduction

Shape Enterprise Defense

Shape’s Enterprise Defense solution protects web and mobile applications from simple to sophisticated automation attacks that would otherwise result in large-scale fraud.

Every day, web and mobile applications face an onslaught of sophisticated attacks with one commonality: instead of exploiting application vulnerabilities, attackers abuse an application’s originally designed functionality. These imitation attacks—delivered by bots and other forms of automation—simulate human behavior using highly sophisticated automated tools, with the goal of conducting crime or disrupting business.

Shape Defense provides all-in-one security to protect your applications from bots, fake users, and unauthorized transactions.

Behind the scenes, Shape solution leverages artificial intelligence and machine learning, among other technologies, to accurately determine in real-time if an application request is from a fraudulent source, and, if so, effectively mitigate. As soon as new countermeasures are deployed, 5-10% of attackers typically attempt to retool and start a new attack. Shape solution adapts and maintains full efficacy even as attackers evolve.

By defending the world’s largest companies, Shape has developed expertise in not just knowing whether a request is coming from a bot or human but whether the request was made with malicious or benign intent. This ability allows Shape to prevent fraud in real-time, manage aggregator and partner access to your applications, and provide new data for customer and business insights.

Understanding the traffic flow

Note: This section describes the request flow for POST and GET XHR endpoints.

To understand how Shape protects GET endpoints against unwanted “scraping,” contact your Shape Security TAM.

Shape uses JavaScript based signal detection countermeasures to detect automation. In this type of countermeasure integration, the Shape JavaScript is injected into the web pages (referred to as “entry pages”) from where the request to a protected POST or GET XHR “endpoint” can be made.

The JavaScript code executes and collects telemetry consisting of user behavior and browser environment and attaches this information to the protected endpoint request. Based on the attached token and telemetry information, Shape determines whether it is human or automated activity.

  • Client browser makes a request for a page that has been defined as an “entry point” to a protected POST or GET XHR “endpoint”. The “entry page” when parsed by the browser triggers a request to Shape JavaScript.
  • The request for Shape JavaScript is routed to Shape clusters per the rules configured on the BIG-IP system.
  • Shape serves the JavaScript bundle. The JavaScript when executed by the browser collects the telemetry.
  • The requests to a protected endpoint are routed back through the active Shape Cluster, where the acquired signals are analyzed, and the traffic is either allowed through or mitigated. The Shape decoration (telemetry) is removed from the HTTP request before forwarding it to F5 on the second leg.

In order to integrate with Shape Enterprise Defense, you need to configure the BIG-IP system for two functions: JavaScript injection and traffic steering.

Integration architecture

Figure: Integration architecture

JavaScript injection

This solution leverages the BIG-IP system to inject Shape JavaScript tags into the targeted entry pages. HTML content profiles provide a mechanism for selective modification of HTTP response data for JavaScript injection.

Traffic steering

F5 iRules are used to steer appropriate HTTP traffic to the Shape clusters for analysis. The administrator creates data groups that match the URI paths to be protected.

BIG-IP configuration for Shape Defense

Note: Review and understand the prerequisite information provided by your Shape Security TAM before proceeding with the integration.

While configuring the BIG-IP system, substitute the strings highlighted in blue with the information provided to you by Shape.

Prerequisite data

During the discovery phase, your TAM engages with you to analyze the applications and identify digital properties, flows, and endpoints that should be protected with Shape Enterprise Defense solution.

After the initial phase is complete, your TAM works with you in determining prerequisite data tailored to your web application(s) and deployment model. This information is a must to configure JavaScript injection and traffic steering rules at the F5 layer.

  • Digital Properties to be Protected (example: www.site.com)
  • Shape Cluster IPs
  • Shape JavaScript URI
  • Shape Outbound IPs
  • Sensitive URI paths to be routed to Shape Clusters (GET and/or POST URI list)
  • Custom header name to identify Shape processed traffic

HTML content profile rule—“ShapeJSAppend”

Substitute ShapeProvidedJSPath with the Shape JavaScript path unique to your deployment.

create ltm html-rule tag-append-html /Common/ShapeJSAppend { action { text "<script type=\"text/javascript\" src=\"ShapeProvidedJSPath\?cache\"></script> <script type=\"text/javascript\" src=\"/ShapeProvidedJSPath\?async\" async></script>" } match { tag-name /title } }

This rule:

  • Matches the tag.
  • Appends the shape JavaScript into the HTTP response after the matched tag.

HTML content profile – “ShapeInject”

create ltm profile html /Common/ShapeInject { app-service none content-detection disabled content-selection add { text/html text/xhtml } defaults-from /Common/html description none rules add { /Common/ShapeJSAppend } }

This rule:

  • Matches HTTP response where the mime type is text/html or text/xhtml.
  • Transforms the matched HTTP response with the ShapeJSAppend rule previously described.

Data groups

Create the following data groups:

ShapeDataGroup

A list of IP addresses from where Shape Security sources protected content.

Substitute x.x.x.x with the Shape Outbound IP addresses provided by your Shape TAM.

create ltm data-group internal /Common/ShapeDataGroup { records replace-all-with { x.x.x.x/32 { } x.x.x.x/32 { } } type ip }

ShapeGETEndpoints

A list of paths to be routed to Shape Security for the GET or GET XHR methods.

Substitute /path1/ and /path2/ with the sensitive URI paths in lowercase for the GET method provided by your Shape TAM.

create ltm data-group internal /Common/ShapeGETEndpoints { records replace-all-with { /path1/ { } /path2/ { } } type string }}

ShapePOSTEndpoints

A list of paths to be routed to Shape Security for the POST method.

Substitute /path/1 and /path/2 with the sensitive URI paths in lowercase for the GET method provided by your Shape TAM.

create ltm data-group internal /Common/ShapePOSTEndpoints { records replace-all-with { /path/1 { } /path/2 { } } type string }

ShapeJS

Contains the Shape JavaScript path.

Substitute /js/my.js with the JavaScript path in lowercase provided by your Shape TAM.

create ltm data-group internal /Common/ShapeJs { records replace-all-with { /js/my.js { } } type string }

Server SSL profile

Traffic between the BIG-IP system and the Shape Clusters needs to be TLS encrypted. Encryption is selectively disabled by the iRule for traffic destined to pool members on port 80 (for SSL offload use cases).

Create the following Server SSL profile:

create ltm profile server-ssl /Common/serverssl-shape { app-service none defaults-from serverssl }

Health monitor

The BIG-IP system monitors the health and availability of the Shape cluster.

Create the following health monitor:

create ltm monitor tcp /Common/ShapeMonitor { adaptive disabled defaults-from /Common/tcp destination *:80 interval 5 recv 200 recv-disable none send "GET /sedcloudapi/health HTTP/1.1\r\nHost: fastcache.net\r\nConnection: Close\r\n\r\n" time-until-up 0 timeout 16 }

Shape cluster pool

The Shape cluster pool is the pool of IP addresses of the Shape clusters.

Substitute x.x.x.x and y.y.y.y with the IP addresses of the Shape clusters provided by your Shape TAM.

create ltm pool /Common/ShapeProdPool { members replace-all-with { /Common/x.x.x.x:443 { address x.x.x.x } /Common/y.y.y.y:443 { address y.y.y.y } } monitor /Common/ShapeMonitor }

Shape integration iRule

Create the following iRule using: create ltm rule /Common/Shape-iRule

Important: This iRule provides guidance on integrating Shape with your BIG-IP virtual server. Before implementation, you should evaluate the security of the iRule in accordance with your corporate security policy and specific requirements of your network environment and make the necessary modifications.

In the iRule, you need to substitute CustomHeader with the header supplied by your Shape technical account manager.

when RULE_INIT {

	# Log debug messages (1=yes, 0=no)
	# Set to 0 when not debugging this iRule
	set static::shape_debug 0

	# Webserver pool
	set static::shape_web_pool "webserver-http-pool"

	# Shape pool
	set static::shape_service_pool "ShapeProdPool"

	# List of IP addresses from where Shape Security will source protected content
	set static::shape_ip_dg "ShapeDataGroup"

}
when HTTP_REQUEST {
 
	# Insert XFF header
	HTTP::header insert X-Forwarded-For [IP::client_addr]

	# If this client IP is one of Shape outbound IPs and where the supplied shape custom header name is present
    # NOTE: Replace CustomHeader with the header name supplied by your Shape technical account manager
	#   this is a return flow from Shape and it needs to go to Origin server pool
	if { [class match [IP::client_addr] equals $static::shape_ip_dg] and [HTTP::header exists {CustomHeader}] } {

		if { $static::shape_debug }{ log local0. "[IP::client_addr][TCP::client_port]: Bypass" }
        # Do not inject JS
		HTML::disable
        # Disable ASM if it's enabled. Use catch to handle error if ASM is not enabled on the virtual server
		set asm_disable_cmd "catch {ASM::disable}"
		eval $asm_disable_cmd

		pool $static::shape_web_pool
	
    } elseif { [class match [string tolower [HTTP::path -normalized]] equals ShapeJs] }{

		# If request is for Shape JS, route it to Shape

		if { $static::shape_debug }{ log local0. "[IP::client_addr][TCP::client_port]: Matched ShapeJS datagroup" }

		# Test if the pool has active members before sending traffic
		if  { [active_members $static::shape_service_pool] >= 1 } {
			snat automap
			pool $static::shape_service_pool
			if { $static::shape_debug }{ log local0. "[IP::client_addr][TCP::client_port]: ShapeJS URI, sent to shapeshifter [HTTP::uri]"}

		} else {
			# If the ShapeShifter pool is not available, then no need to forward this to origin, send back an empty 200 OK
			# Can also put an empty file at Origin for the Shape js request for occasions when the iRule is disabled.
			if { $static::shape_debug }{ log local0. "[IP::client_addr][TCP::client_port]: ShapeJS URI, but $static::shape_service_pool pool down! Sent HTTP 200 response"}
			HTTP::respond 200
			return
		}

    } elseif { [HTTP::method] equals "POST" and [class match [string tolower [HTTP::uri -normalized]] starts_with ShapePOSTEndpoints] } {
		# Protected POST Endpoints to be routed to Shape

		# Test if the pool has active members before sending traffic
		if  { [active_members $static::shape_service_pool] >= 1 } {
			if { $static::shape_debug }{ log local0. "[IP::client_addr][TCP::client_port]: Shape POST sent to shapeshifter [HTTP::uri]"}
			snat automap
			pool $static::shape_service_pool
		} else {
			# If the ShapeShifter pool is not available, send traffic to the default pool
			if { $static::shape_debug }{ log local0. "[IP::client_addr][TCP::client_port]: Shape POST, but $static::shape_service_pool pool down! Sent to default pool [HTTP::uri]"}
			    pool $static::shape_web_pool
		}
    } elseif { [HTTP::method] equals "GET" and [class match [string tolower [HTTP::uri -normalized]] starts_with ShapeGETEndpoints] } {
		# Protected GET Endpoints to be routed to Shape

		# Test if the pool has active members before sending traffic
		if  { [active_members $static::shape_service_pool] >= 1 } {
			if { $static::shape_debug }{ log local0. "[IP::client_addr][TCP::client_port]: Sent to shapeshifter [HTTP::uri]"}
			snat automap
			pool $static::shape_service_pool
		} else {
			# if the ShapeShifter pool is not available, send traffic to the default pool
			if { $static::shape_debug }{ log local0. "[IP::client_addr][TCP::client_port]: Shape GET, but $static::shape_service_pool pool down! Sent to default pool [HTTP::uri]"}
				HTML::disable
			    pool $static::shape_web_pool
		}
	}
}

when SERVER_CONNECTED {
	# Disable SSL serverside profile for SSL offload use cases
	if {[LB::server port] != 443 } {
		SSL::disable
	}
}


when HTTP_RESPONSE {
	# Do not inject javascript for Shape interstitials
	if { [HTTP::header exists "ISTL-RESPONSE"] } {
		HTML::disable
	}
}

This rule:

  • Injects an X-Forwarded-For header for identification of original client IP addresses in SNAT environment.
  • Bypasses rule processing for traffic already processed by Shape and directs it to the origin web server.
  • Routes requests for Shape JavaScript to Shape devices; if Shape is down or unavailable, the rule returns HTTP 200 OK to the end user.
  • Routes requests for sensitive GET and POST paths to Shape clusters falling back to origin if Shape is not available.
  • Disables JavaScript injection for Shape Interstitial response. This snippet is required if you are protecting GET endpoints with Shape Enterprise Defense solution.
  • Disables Server SSL profile for SSL offload scenarios.

Bringing it all together— virtual server elements

Substitute https-virtual with the name of the existing virtual server that hosts the application to be protected. The virtual server must have an HTTP profile attached.

modify ltm virtual /Common/https-virtual { profiles add { /Common/ShapeInject { } /Common/serverssl-shape { context serverside } /Common/oneconnect { } } rules { /Common/Shape-iRule } }

Running the previous TMOS Shell (tmsh) command:

  • Associates the serverssl-shape profile with the Shape protected virtual server.

    Note: If performing SSL offload, the iRule selectively disables the Server SSL profile for traffic destined to nodes on port 80.

    Note: OneConnect is needed to cover HTTP 1.1 pipeline requests. Without the OneConnect profile, the previously described iRule examines the first HTTP 1.1 pipelined request and sends it to the back-end pool member. Any subsequent pieplined request bypasses the iRule logic and sends to the same back-end pool member as the initial request on this connection. For more information about the OneConnect behavior, refer to K7208: Overview of the OneConnect profile.

  • Associates the ShapeInject HTML content profile with the shape protected virtual server for injection of the Shape JavaScript tags into HTTP responses.
  • Associates the shape-iRule with the shape protected virtual server.

Note: Virtual servers which leverage persistence may require further tailoring. Work with your Shape TAM.
