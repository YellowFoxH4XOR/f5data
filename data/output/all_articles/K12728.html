Known Issue

This is the result of a known issue. If you migrate a virtual server from one BIG-IP GTM server object to another, the old monitor assigned to the first server object may remain in operation and continue to attempt to monitor the migrated virtual server. In addition, any monitors assigned to the newly-associated server object may not function as expected. This issue may result in the BIG-IP GTM system marking the virtual server status as unknown or down. Additionally, other members of the BIG-IP GTM sync group will likely have a different status for the same migrated object.

In the following example, the host1 server object is configured with a virtual server (10.24.0.1:80) and an HTTP monitor. If the virtual server is migrated from host1 to host2, the HTTP monitor configured for host1 may continue monitoring the virtual server. As a result, the BIG-IP GTM system may mark the migrated virtual server status as unknown or down:

server { // datacenter=DC1, #VS=1
name "host1"
type generic
box {
address 10.24.0.1
unit_id 1
}
monitor "http"
vs {
name "vip1"
address 10.24.0.1:80 // http
}
}

server { // datacenter=DC1, #VS=0
name "host2"
type generic
box {
address 10.24.0.2
unit_id 1
}
monitor "gateway_icmp"
}

When this issue occurs, an error indicating that the system could not find the monitor object is logged, appearing similar to the following example:

gtmd[14589]: 011ae00b:3: Could not find monitor object 10.24.0.1:80

Note: This issue occurs whether you use the Configuration utility or the command line to migrate the virtual server to the new server object.

F5 Product Development tracked this issue as ID 351579 and it was fixed in BIG-IP GTM 10.2.2.

For information about upgrading, refer to the BIG-IP GTM release notes.

This issue has been fixed in cumulative hotfix Hotfix-BIGIP-10.2.1-496.0-HF2, which has been issued for BIG-IP GTM version 10.2.1. You may download this hotfix or later versions of the cumulative hotfix from the F5 Downloads site.

For information about installing a hotfix for version 10.x systems, refer to K10025: Managing BIG-IP product hotfixes (10.x).

Workaround

You can work around this issue by deleting the virtual server object(s) from the BIG-IP GTM system and re-creating and associating the objects with the new server. To do so, perform the following steps:

  1. Remove the BIG-IP GTM pool member(s) you intend to migrate from the associated pool.
  2. Verify that each BIG-IP GTM system in the sync group reflects the changes from the previous step.
  3. Delete the virtual server object(s) you intend to migrate (the virtual servers should match the pool members removed in Step 1).
  4. Verify that each BIG-IP GTM system in the sync group reflects the changes from the previous step.
  5. Add the virtual server object(s) to the new server object(s) .
  6. Add the virtual server(s) as pool members to the appropriate pools.
  7. Verify that each BIG-IP GTM system in the sync group reflects the changes from the previous step.
  8. Confirm object status is either up (green) or down (red).
