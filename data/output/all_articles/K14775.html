Topic

You should consider using this procedure under the following condition:

  • In HTTP redirect responses from a pool member that is behind a virtual server with SSL Client profile enabled you want the redirects to http:// URL presented to the client as redirects to https://

The procedure do not apply to conditions when the http:// URL is included inside the body of the of HTML document, rather than in HTTP response header

Description

A virtual server that has a Client SSL profile applied accepts HTTPS connections from clients, decrypts the SSL sessions, and sends the HTTP requests to the web server. If the BIG-IP system is not re-encrypting requests with a Server SSL profile, the web server listens and responds to all requests using HTTP. As a result, self-referencing Location headers in redirect responses specify the HTTP protocol instead of the HTTPS protocol that the client originally requested. The BIG-IP Client SSL profile encrypts the response and returns it to the client, but the Location header value is not modified by default. The client follows the HTTP redirect, and the request fails in one of the following ways:

  • If no HTTP virtual server was configured for the same virtual address on the BIG-IP system, the connection fails and the system no longer uses the SSL session.
  • If an HTTP virtual server is configured on the same virtual address and sends traffic to the same web servers, the request may unintentionally succeed, but not be encrypted, because the system used the HTTP protocol instead of the HTTPS protocol.
  • If an HTTP virtual server is configured on the same virtual address and uses an iRule or Fallback Host to redirect an HTTP response to HTTPS, the system may repeatedly redirect the request between the two locations until the browser reaches its maximum redirect limit and reports an error.

Many applications rely on the use of redirects. When these redirects fail, the SSL session is disrupted, and in most cases the website is unusable.

Special case: Trailing slash redirects

When a requested URI does not include a trailing forward slash ( / ) at the end of the URI, some web servers generate a courtesy redirect using the following algorithm:

  • When a request arrives specifying a resource name that does not end with a slash, the web server first searches for a file with a name that matches the last section of the URI.
  • If the web server cannot find a matching file, it looks for a directory with a name that matches the last section of the URI.
  • If the web server finds a matching directory, it sends an HTTP 302 redirect response back to the client with the Location value, specifying the protocol over which the request was received, the originally-requested resource, and a trailing slash.

The following is an example of a trailing slash HTTP 302 redirect response scenario for a BIG-IP virtual server that has a Client SSL profile configured, and does not have a Server SSL profile configured:

  1. A user types https://www.f5.com/stuff without a trailing slash, intending to browse the stuff directory.
  2. The client browser sends an SSL request to the Client SSL virtual server, which resides on the BIG-IP LTM system.
  3. The BIG-IP LTM system decrypts the request and sends a GET /stuff command to the web server using the HTTP protocol.
  4. Because a file named stuff does not exist in the root directory of the web server, but a directory named stuff exists, the web server sends an HTTP 302 redirect response for the same resource name over the same protocol, appending a trailing slash. Since the request was sent using the HTTP protocol, when the web server sends the HTTP 302 redirect response, it specifies HTTP (not HTTPS), and the resulting redirect header is Location: http://www.f5.com/stuff/.
  5. When the client receives the HTTP 302 redirect response, it sends a new request to the BIG-IP LTM virtual server requesting http://www.f5.com/stuff/.
  6. Since the request uses HTTP, rather than HTTPS, the SSL session fails in one of the ways previously described.

Trailing slash redirects are matched by the Matching http-rewrite option, ignoring the trailing slash.

Important: In versions prior to BIG-IP 12.1.0, the system does not rewrite redirects from web servers that use the HTTPS protocol. Typically, this is not an issue if the backend HTTPS server is running on the same port as the virtual server. The redirect works because the port the server is listening on is the same as the virtual server. However, if the backend HTTPS server is running on a different port than that of the virtual server, the redirect fails. Beginning in BIG-IP 12.1.0, the system also rewrites redirects from web servers that use HTTPS protocol. If the redirect URI already uses https://, only the IP address and port are updated, as needed.

Note:  In some cases you might want to rewrite HTML content to match the redirect URI, or you want to redirect to different server URI than the original one, in this case we can use rewrite profile instead of relying on HTTP rewrite feature. Keep in mind that the rewrite of content is dependent on tags and attributes of the content body, but this will guarantee that scripts and style files with attributes such as src, href, or link within the HTML page will match the redirected URL.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You have the Client SSL profile configured on a virtual server.

Procedures

Configuring HTTP rewrites using the BIG-IP Configuration utility

The following procedure enables HTTP rewrites using the BIG-IP Configuration utility.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Select Local Traffic > Profiles > Services > HTTP.
  3. To create a new HTTP profile, select Create. Alternatively, you can select an existing profile to modify.
  4. If you are creating a new profile, enter a name for the profile, for Parent Profile, select http.
  5. Under Settings, set Redirect Rewrite to All, Matching, or Nodes, depending upon your configuration:
    • Choose Matching to rewrite redirects when the path and query URI components of the request and the redirect are identical (except for the trailing slash). This option is useful if the redirect references the same object, changing only the protocol or host name, while the path and name of the requested object remains the same. This setting is useful when addressing the trailing slash redirect special case issue previously discussed.
    • Choose Nodes to rewrite redirects when the redirect URI contains a node IP address instead of a host name, and you want the system to change it to the virtual server address.
    • Choose All to rewrite all HTTP 301, 302, 303, 305, or 307 redirects to HTTPS, whether or not they match the virtual server.
    • Choose None to disable HTTP rewrites.
  6. Select Finished.

    Note: If you created a new profile, you must now associate it with the virtual server. If you modified an existing profile, you can skip the remaining steps.

  7. Go to Local Traffic > Virtual Servers.
  8. Select the virtual server for which redirect URLs should be rewritten.
  9. Under Configuration, for HTTP profile, select the new HTTP profile.
  10. Select Update.

Configuring HTTP rewrites using tmsh 

The following procedure enables HTTP re-writes using the TMOS Shell (tmsh).

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

Note: If you created a new HTTP profile, you must now associate it with the virtual server. If you modified an existing profile already associated with a virtual server, you can skip the next step.

  1. Log in to tmsh by entering the following command:

  2. tmsh

  3. The following command syntax creates a new HTTP profile with redirect-rewrite turned on:

    tmsh create /ltm profile http <profile_name> defaults-from http redirect-rewrite <rewrite_type>

    In the previous command syntax, note the following:
    • <profile_name> is the name of the new HTTP profile you want to create.
    • <rewrite_type> is one of the following rewrite types depending on your configuration:
      • Choose Matching to rewrite redirects when the path and query URI components of the request and the redirect are identical (except for the trailing slash). This option is useful if the redirect references the same object, changing only the protocol or host name, while the path and name of the requested object remains the same. This setting is useful when addressing the trailing slash redirect special case issue previously discussed.
      • Choose Nodes to rewrite redirects when the redirect URI contains a node IP address instead of a host name, and you want the system to change it to the virtual server address.
      • Choose All to rewrite all HTTP 301, 302, 303, 305, or 307 redirects to HTTPS, whether or not they match the virtual server.
      • Choose None to disable HTTP rewrites.
  4. To modify an existing http profile, use the following command syntax:

    modify /ltm profile http <existing_profile_name> redirect-rewrite <rewrite_type>

    In the previous command syntax, note the following:
    • <existing_profile_name> is the name of the existing HTTP profile you want to modify.
    • <rewrite_type> is one of the rewrite types listed in step 2.
  5. To associate an http profile with a virtual server, use the following command syntax:

    modify /ltm virtual <virtual_server> profiles add { <http_profile> }

    In the previous command syntax, note the following:
    • <virtual_server> is the name of the virtual server you want to modify.
    • <http_profile> is the name of the newly created HTTP profile you want to associate with this virtual server.
  6. Save the change by entering the following command:

    save /sys config
