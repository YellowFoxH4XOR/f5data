Description

This article will be used in environments where BIG-IP DNS or BIG-IP GTM are NOT Provisioned and the daemon named is continuously restarting after reboot of a Viprion chassis.

  • You will see the following message scrolling upon reboot:
     

    logger[21969]: Re-starting named

  • When reviewing /var/log/daemon.log you will also see the following:
     

    err named[<PID>]: /config/named.conf:40: change directory to '/config/namedb' failed: file not found
    err named[<PID>]: /config/named.conf:40: parsing failed: file not found
    crit named[<PID>]: loading configuration: file not found
    crit named[<PID>]: exiting (due to fatal error)

     

Environment

NOTE: All of these symptoms need to be present in order for this article to apply:

  • BIG-IP DNS or BIG-IP GTM are NOT Provisioned
  • The daemon named is continuously restarting after reboot of a multi-bladed Viprion chassis.
  • You continuously see: logger[<PID>]: Re-starting named on your command prompt
  • You review the log var/log/daemon.log and you see the named errors documented in the Description above
     

Cause

When the configuration is trying to load it is referencing the directory '/config/namedb' which is not present in a non DNS/GTM provisioned environment so parsing fails and then the configuration fails to load. This then creates a loop where named is continuously restarting. 

Ultimately this issue is caused by the following bug: 
Bug ID 1004317: Csyncd removes files and directories under /config/zebos, /var/named/config/namedb, etc.

Recommended Actions

If all of the above matches you can perform the following commands to resolve this issue: 

The following steps should be performed on the Primary slot:

  # clsh bigstart stop csyncd named zrd
  # mkdir -p /var/named/config/namedb
  # chown named.named /var/named/config/namedb
  # restorecon -R /var/named
  # clsh bigstart start csyncd named zrd

When the csyncd starts again at the end it should sync the directory back to the others and this issue should be resolved. Please note this absolutely needs to be done on the Primary slot.
 

Additional Information

csyncd - For all platforms, the csyncd process populates the software image table. In addition, on VIPRION systems, the csyncd process replicates portions of the file system among cluster members. If it is not running or goes down - For all platforms, the software image table is not updated, and users cannot view or manage the latest software image list using the Configuration utility. In addition, on VIPRION systems, no synchronization among cluster members.

The csyncd process will only be down while you are going through these steps.
