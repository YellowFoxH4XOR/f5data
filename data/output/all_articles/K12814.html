Topic

This article describes a specific behavior of the bigip monitor, which you should consider when you configure the BIG-IP GTM system.

When you define a BIG-IP system as a server object on a BIG-IP GTM system, you generally assign the bigip monitor to the BIG-IP server object. The bigip monitor gathers metrics and statistics information that the remote BIG-IP system acquires through local monitoring of its own resources. For example, the bigip monitor can automatically discover and periodically update the status of virtual servers and links that are configured on the monitored BIG-IP server object, thus greatly reducing the administrative overhead on the BIG-IP GTM system.

However, if you assign the bigip monitor to a BIG-IP server object, but you also assign a monitor to one of its child virtual servers, the bigip monitor that is applied to the BIG-IP server object does not collect or display metrics and statistics for that virtual server object. Effectively, any BIG-IP GTM monitor that you assign to a virtual server object overrides (for that virtual server only) the monitor assigned to its parent server. This behavior is intended.

Note: For more information about configuring and monitoring resources on the BIG-IP GTM system, refer to the Configuration Guide for BIG-IP Global Traffic Manager and BIG-IP Global Traffic Manager: Implementations manuals.

Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

In the following configuration, the BIG-IP GTM system does not collect metrics and statistics for the my_vs_three virtual server:

SERVER Seattle_LTM
| Product: BIG-IP System (Single)
| Health Monitors: bigip
+-> VIRTUAL SERVER my_vs_one
| | Health Monitors: None
+-> VIRTUAL SERVER my_vs_two
| | Health Monitors: None
+-> VIRTUAL SERVER my_vs_three
| Health Monitors: my_http_monitor

Note: You are more likely to notice that the BIG-IP GTM system is not collecting metrics and statistics for a virtual server if you use dynamic load balancing modes. All dynamic load balancing modes make load balancing decisions based on the metrics collected by the big3d agents or by using Simple Network Management Protocol (SNMP). If no metrics are available for a virtual server, then dynamic load balancing modes do not work as expected.

Note: When a virtual server is hosted on a server of the BIG-IP system type, you generally do not have to assign additional monitors to the virtual server. F5 recommends that you assign all the appropriate monitors to the resource through the remote BIG-IP system, and then assign only the bigip monitor to the BIG-IP system through the BIG-IP GTM system.

If you determine that you require an additional monitor at the virtual server level, and also that you want to collect metrics and statistics for the virtual server, you can assign the bigip monitor to both the server and the virtual server objects.

For example, modify the configuration previously discussed in this article, as follows:

SERVER Seattle_LTM
| Product: BIG-IP System (Single)
| Health Monitors: bigip
+-> VIRTUAL SERVER my_vs_one
| | Health Monitors: None
+-> VIRTUAL SERVER my_vs_two
| | Health Monitors: None
+-> VIRTUAL SERVER my_vs_three
| Health Monitors: bigip, my_http_monitor

According to this example, you have assigned the bigip monitor to the virtual server on which you had assigned a monitor. This configuration ensures that the BIG-IP GTM system collects metrics and statistics for that virtual server as well.
