Topic

This article describes split DNS, deployment scenarios, and how to obtain split DNS behavior with the BIG-IP DNS system through wide IPs and topology load balancing.

Description

Split DNS refers to setting up different DNS views for the same domain. This configuration involves creating one zone to resolve names for the internal network and another zone to resolve names for the external network.

Note: For more information about resolving names for internal networks, refer to the Internet Engineering Task Force (RFC 1918). This link takes you to a resource outside of AskF5, and it is possible that the document may be removed without our knowledge.

Split DNS implementation using standard DNS servers

Split DNS is a configuration in which the resolution IP address of a name is dependent on the location of the requesting client, or the Local Domain Name System (LDNS) is being requested on behalf of a client. For example, a site may have several web applications that have both internal network addresses and external addresses. Clients on the internal network may have access to both sets of applications. The external applications are accessible using a Network Address Translation (NAT). The intent of split DNS is to have internal clients resolve fully-qualified domain names (FQDN) for the applications to internal addresses on the corporate LAN, rather than accessing the resource through the advertised public address for that resource. Split DNS also ensures that external requests for the resource resolve to the public Internet addresses.

In some cases, accomplishing split view DNS resolution using standard DNS servers (non-BIG-IP GTM), may involve configuring two DNS servers: an internal DNS server for the private class IP address networks, and an external DNS server for both the internal and external clients for DNS. The internal DNS server is configured to send queries to the external DNS server, excluding the FQDNs intended to resolve to the local RFC 1918 addresses. The FQDNs for internal resolution are configured on the internal DNS server. Only internal clients can query the internal DNS server, while both internal and external clients can query the external DNS server. The external-facing DNS server is configured to resolve all queries to public Internet IP addresses. This configuration allows the internal DNS server to resolve queries from internal clients with local RFC 1918 network addresses. The internal DNS server will forward any queries that it cannot resolve to the external DNS server.

With tiered DNS servers, internal clients querying for DNS resolution:

  • Resolve queries for FQDNs that reside on both the RFC 1918 and external networks.
  • Resolve queries for configured internal FQDNs to local private network RFC 1918 addresses.
  • Resolve queries for FQDNs that are not configured on the internal DNS, with RFC 1918 addresses with external public (Internet) addresses.

External DNS queries:

  • Resolve FQDNs to public (Internet) addresses only, and are unaware of the RFC 1918 addressing used by internal DNS and clients

Split DNS implementation using BIG-IP GTM wide IPs

Using BIG-IP GTM wide IPs to implement split DNS is similar to using standard DNS. To do so, you can allow DNS queries for wide IP domain names to resolve differently depending on the topological placement of the requesting LDNS. For example, internal DNS queries will resolve to internal IP addresses, while external queries will resolve to external IP addresses when querying the same FQDN. Deploying split DNS using BIG-IP GTM wide IPs has the following benefits:

  • The BIG-IP GTM wide IP DNS resolution differentiates between internal/RFC 1918 and external LDNS requests.
  • Optimized internal access to resources and enhanced security for internal clients accessing DNS resources with their public FQDN.
  • Ensured resource availability for DNS resolutions.

Split DNS deployment scenarios using wide IPs

Given the combination of internal/RFC 1918 (local private network) and external Internet addressing configuring the BIG-IP GTM system's virtual server references is a manual process. A single RFC 1918 address is represented in the BIG-IP GTM configuration as two separate virtual servers. The first virtual server references the RFC 1918 (local private network) address directly as the virtual address. The second virtual server is configured with the same RFC 1918 (local private network) address as the translation-address for the virtual server and the address of the virtual server is configured with a public Internet address.

Wide IP split DNS for multiple pools with multiple virtual servers

Create individual wide IPs for split DNS responses. Wide IP resolution addresses are obtained from two separate pools of virtual servers. When creating two BIG-IP GTM pools of virtual servers, each pool includes virtual server addresses in the range to fulfill resolution based on the IP address of the requesting LDNS. For example, a pool that will fulfill resolutions for clients for local RFC 1918 networks will have virtual server addresses that are on the same local RFC 1918 network ranges. A pool that is created for external resolutions will contain virtual servers with IP addresses that are Internet routable and accessible by external clients.

Each pool represents the virtual server addresses for resolution based on the topology placement of the requesting LDNS. Topology should be configured to map out all local RFC 1918 network ranges. When a client request matches any of these predefined internal/local private network ranges, topology will select the resolution address from the assigned pool for internal RFC 1918 virtual servers. Queries that do not reside in the mapped local private networks are considered external network requests. Topology will then select a resolution address from the second pool of virtual server addresses configured specifically for use when sending external responses.

Note: For multiple RFC 1918 network ranges, you can create a Topology Region to contain all of these networks.

Configure the following objects on a BIG-IP GTM system that has already been populated with servers and virtual servers for both public and private class networks.

  1. Create an external facing (Internet) BIG-IP GTM pool of publicly accessible network virtual addresses, selecting a desired load balancing algorithm.
  2. Create an internal (RFC 1918) BIG-IP GTM pool of local private network virtual addresses used for resolution, selecting a desired load balancing algorithm.
  3. If you want a fallback IP address, F5 recommends that you use the public Internet IP address.
  4. Create a new Topology record where Request Source IP Subnet (is) <ip addresses range of your local private network> and Destination is the pool of RFC 1918 (local private network) addresses that you created in step 2.
  5. Repeat the previous step if there are multiple internal/local private network ranges that cannot be spanned by widening the network subnet mask.
  6. Create a new Topology record where Request Source IP Subnet (is not) <ip addresses range of your local private network> and Destination is the pool of non-RFC 1918 (local private network) addresses that you created in step 1.
  7. Repeat the previous step if there are multiple non-internal/local private network ranges that cannot be spanned by widening the network subnet mask.
  8. Create a wide IP that references both pools, setting the Load Balancing Method pool to Topology.
  9. Repeat these steps for each wide IP that you want to have Topology select the destination pool based on the LDNS network.

Wide IP split DNS single pool with one virtual server per view

To create a global BIG-IP GTM topology that implements split DNS across multiple wide IPs with each using a single pool configuration, perform the following steps:

  1. Create Topology records that are specific to local RFC 1918 networks:

    Request Source = IP Subnet is <your local private network ip address range> and Destination = IP Subnet is <local private network RFC 1918 address range>.

  2. Repeat the previous step if there are multiple local private network ranges that cannot be spanned by widening the network subnet mask.
  3. Create a Topology record that negates use of the local private network for address resolution when the source DNS is not of a local private network:

    Request Source = IP Subnet is not <your local private network ip address range> and Destination = IP Subnet is not <local private network RFC 1918 address range>.

  4. Repeat the previous step if there are multiple local private network ranges that cannot be spanned by widening the network subnet mask.
  5. Create a BIG-IP GTM pool that contains only one local private network virtual address and only one public facing virtual address that support the same application, setting the Load Balancing Method to Topology.
  6. If you want a fallback IP address, F5 recommends that you use the public Internet IP address.
  7. Create a wide IP that references the newly created pool.
  8. Repeat these steps for each wide IP for which you want Topology to select the destination pool member based on the LDNS network.

Recommendations

When configuring the BIG-IP GTM wide IP for split DNS resolution, you should consider the following:

  • You need administrative access to the BIG-IP GTM system.
  • You must be familiar with configuring BIG-IP GTM wide IPs to aid in building out wide IPs with topology.
  • You must configure the BIG-IP GTM system with servers that represent the same resource as a virtual server for both public Internet and private RFC 1918 addresses.
  • You must configure the BIG-IP GTM system with access to the required network resources. The BIG-IP GTM system ensures availability of a configured resource (virtual server) by probing that resource. Typically, a firewall NAT translates an external request to the internal RFC 1918 address of a public resource. Therefore, the BIG-IP GTM system must be able to access that resource on both the RFC 1918 and the firewall NAT public address. For additional details regarding BIG-IP GTM and BIG-IP configurations with firewall NAT rules, refer to K14707: Configuring BIG-IP DNS server objects for BIG-IP devices that reside behind a firewall NAT.
