Topic

NT LAN Manager (NTLM) is a technology that uses an encrypted challenge/response protocol to authenticate users over the network. The system requesting authentication performs a calculation to prove that it has access to the secured NTLM credentials. The proof is in the form of an encrypted version of the user's password and is supplied as a header in the HTTP request. NTLM credentials are based on data, such as the domain name and user name, obtained during the interactive logon process.

Description

Details related to NTLM authentication and how the BIG-IP system optimizes the NTLM authentication process for HTTP are discussed in the following sections:

  • NTLM authentication process for HTTP
  • Potential challenges associated with optimizing NTLM traffic
  • Using the NTLM profile to optimize NTLM traffic

Note: The terms "client-side flow" and "server-side flow" refer to the BIG-IP system's full proxy architecture. A client-server connection is formed when the BIG-IP system attaches a client-side flow with a server-side flow. For more information, refer to K8082: Overview of TCP connection setup for BIG-IP LTM virtual server types.

NTLM authentication process for HTTP

The NTLM challenge-response authentication process can be summarized as follows:

  • The client initiates a connection to the server and sends an HTTP request.
  • The server indicates that NTLM authentication is required by sending an HTTP 401 Unauthorized HTTP response message that contains the WWW-Authenticate: NTLM response header.
  • The client sends the HTTP request again, adding an Authorization HTTP header, indicating its willingness to authenticate itself with a server using the NTLM protocol. This is an NTLM type 1 message.
  • The server responds with another HTTP 401 Unauthorized message, providing a password challenge to the client. The message may also contain information about the authentication target. This is an NTLM type 2 message.
  • The client performs a calculation that proves it has access to the secured NTLM credentials, and sends the HTTP request again along with the authentication target (domain name/server name), user name, and client workstation name. This is an NTLM type 3 message.
  • The server performs the same calculation on the password it holds for the user (this involves a server-Domain Controller dialogue for non-local accounts). If the password is correct, the server sends a standard HTTP response, such as a 200 OK.
  • The server accepts further requests from the client on the same TCP connection without additional authentication. This is because NTLM is a connection-oriented protocol rather than a request-oriented protocol; the connection is considered authenticated until it closes.

Note: The NTLM authentication process requires that the request is sent three times to the same server and that the server allows Keep-Alive connections.

Potential challenges associated with optimizing NTLM traffic

The nature of NTLM authentication poses several challenges with respect to the OneConnect feature.

The BIG-IP OneConnect feature enhances HTTP connections by efficiently managing connections created between the BIG-IP system and back-end pool members. The OneConnect feature works with HTTP Keep-Alives to allow the BIG-IP system to minimize the number of server-side TCP connections by making existing connections available for reuse by other clients. OneConnect also allows the BIG-IP system to process and load-balance each HTTP request individually.

Note: For more information about the OneConnect profile, refer to K7208: Overview of the OneConnect profile.

Prior to BIG-IP 9.2.0, NTLM and OneConnect were mostly incompatible. For example, with a OneConnect profile associated with a virtual server, it is possible that the NTLM type 1 and type 3 messages are sent to different servers, causing authentication to fail. To overcome this issue, persistence was required, limiting the benefit of OneConnect.

In BIG-IP 9.2.0 through 9.4.x, the BIG-IP system handles the NTLM handshake differently and does not detach the server-side flow after sending the HTTP 401 Unauthorized response to the client. This allows the initial client request and the subsequent NTLM type 1 and type 3 messages to follow the same server-side flow. As a result, the NTLM handshake is able to complete successfully. This behavior was possible prior to BIG-IP 9.2.0 through the ONECONNECT::detach disable iRules command.

However, since NTLM is connection-oriented and allows multiple requests on the same connection without re-authentication, issues can occur after the initial handshake when the OneConnect feature adds NTLM-authenticated requests to the connection pool to potentially be reused by unauthenticated clients. Prior to BIG-IP 10.0.0, this issue could be mitigated or avoided only by using special techniques such as:

  • Configuring the OneConnect source mask feature to limit server-side flows by subnet or to the original client IP address
  • Configuring an iRule to disable the OneConnect profile for NTLM, or to provide special handling for NTLM

In general, there is a trade off with such solutions; the less complex solution offers reduced OneConnect effectiveness for non-NTLM traffic, and the more complex solution offers a greater impact on BIG-IP resources and (iRules) supportability.

Using the NTLM profile to optimize NTLM traffic

Starting in BIG-IP 10.0.0 and later, you can use the NTLM profile to optimize NTLM traffic by navigating to Local Traffic > Profiles > Other > NTLM in the Configuration utility.

Note: The NTLM profile does not support the NTLM Negotiate security header. For more information, refer to K11110: The BIG-IP NTLM profile does not support IIS authentication negotiation using the WWW-Authenticate: Negotiate header.

Note: Before you can enable the NTLM profile for a virtual server, you must first enable OneConnect and HTTP profiles for the virtual server.

The NTLM profile is used to key the OneConnect managed server-side connections to existing NTLM credentials ensuring that server-side connections are only re-used by the previously NTLM authenticated client. When the NTLM profile is associated with a virtual server and the server replies with the HTTP 401 Unauthorized HTTP response message, the NTLM profile inserts a cookie, along with additional profile options, into the HTTP response. The information is encrypted with a user-supplied passphrase and associated with the server-side flow. Further client requests are allowed to reuse this flow only if they present the NTLMConnPool cookie that contains the matching information. By using a cookie in the NTLM profile, the BIG-IP system does not need to act as an NTLM proxy, and returning clients do not need to be re-authenticated.

The NTLM profile works by parsing the HTTP request containing the NTLM type 3 message and securely storing the following pieces of information (aside from those which are disabled in the profile):

  • User name
  • Workstation name
  • Target server name
  • Domain name
  • Cookie previously set (cookie name supplied in the profile)
  • Source IP address

With the information safely stored, the BIG-IP system can then use the data as a key when determining which client-side requests to associate with a particular server-side flow. You can configure this using the NTLM profile options. For example, if a server's resources can be openly shared by all users in that server's domain, then you can enable the Key By NTLM Domain setting, and all server-side flows from the users of the same domain can be pooled for connection reuse without further authentication. Or, if a server's resources can be openly shared by all users originating from a particular IP address, then you can enable the Key By Client IP Address setting and all server-side flows from the same source IP address can be pooled for connection reuse.

Note: Although the information is used for persistence purposes, for security reasons, it is not visible to the BIG-IP administrator, nor is it stored in the BIG-IP persistence table. The NTLM profile uses the concept of persistence at a more granular level than session persistence. The persistence key indicates the pool member to which the request is sent, as well as the particular (NTLM-authenticated) server-side flow. Because the client presents the NTLMConnPool cookie for each request, the profile not only provides security without compromising OneConnect efficiency, but it also makes NTLM become request-oriented and effectively provides single sign-on capability since the need to re-authenticate each new client connection is removed.
