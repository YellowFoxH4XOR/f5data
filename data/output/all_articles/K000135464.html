Description

A pool may be created that includes static IP pool members and (fully-qualified domain name) FQDN nodes.

Upon creating a new FQDN node, the BIG-IP system will automatically query its configured DNS resolver for both its A and AAAA records. It will collect IPv4 and IPv6 addresses that are recursively queried by the DNS resolver.

For example, the following shows a query for www.f5.com retuns 2 IPv4 addresses and 2 IPv6 addresses.

# dig www.f5.com A
www.f5.com.       8    IN   CNAME  dwbfwz8xncgmg.cloudfront.net.
dwbfwz8xncgmg.cloudfront.net. 38 IN   A    108.156.91.78
dwbfwz8xncgmg.cloudfront.net. 38 IN   A    108.156.91.96
dwbfwz8xncgmg.cloudfront.net. 48 IN   AAAA  2600:9000:2351:9200:14:232e:8a00:93a1
dwbfwz8xncgmg.cloudfront.net. 48 IN   AAAA  2600:9000:2351:7c00:14:232e:8a00:93a1

The BIG-IP system will then proceed to automatically create nodes and pool members consisting of all the returned DNS A and AAAA IP address records. These are dynamically created and removed based on the DNS serevr response. These automatically created nodes and pool members are also referred to as ephemeral nodes or ephemeral pool members.

For example, the following pool has two static pool members and one FQDN node.

# tmsh list ltm pool my_http_pool
ltm pool my_http_pool {
  members {
    10.11.65.100:http {
      address 10.11.65.100
      ratio 5
      session monitor-enabled
      state down
    }
    10.11.65.101:http {
      address 10.11.65.101
      ratio 3
      session monitor-enabled
      state up
    }
    www.f5.com:http {
      fqdn {
        autopopulate enabled
        name www.f5.com
      }
      ratio 2
      state fqdn-up
    }
    _auto_108.156.91.54:http {
      address 108.156.91.54
      ephemeral true
      ratio 2
      session monitor-enabled
      state up
      fqdn {
        autopopulate enabled
        name www.f5.com
      }
    }
    _auto_108.156.91.66:http {
      address 108.156.91.66
      ephemeral true
      ratio 2
      session monitor-enabled
      state up
      fqdn {
        autopopulate enabled
        name www.f5.com
      }
    }
    _auto_2600.9000.2351.1000.14.232e.8a00.93a1:http {
      address 2600:9000:2351:1000:14:232e:8a00:93a1
      ephemeral true
      ratio 2
      session monitor-enabled
      state checking
      fqdn {
        autopopulate enabled
        name www.f5.com
      }
    }
    _auto_2600.9000.2351.5600.14.232e.8a00.93a1:http {
      address 2600:9000:2351:5600:14:232e:8a00:93a1
      ephemeral true
      ratio 2
      session monitor-enabled
      state checking
      fqdn {
        autopopulate enabled
        name www.f5.com
      }
    }
  }
}

Considerations

There are some considerations when using FQDN pool members compared to using static pool members.

  • Creating an FQDN node causes the BIG-IP system to create an undetermined number of nodes and pool members based on the DNS server answer.
  • Any Ratio, Priority Group Activation, and connection limit values for ephemeral (automatically created) members are set to the same value that was specified on the FQDN node.
  • Any Ratio, Priority Group Activation, and connection limit value on each ephemeral node or pool member are note permitted be configured separately.

Consequently, mixing static and FQDN pool members in the same pool may produce unexpected results.

Let's say we have these members in a pool:

a.com 10.0.1.1 ratio 1
a.com 10.0.1.2 ratio 1
a.com 10.0.1.3 ratio 1
b.com 10.0.2.1 ratio 2
b.com 10.0.2.2 ratio 2
static 10.0.3.1 ratio 5

We can see a.com will have a total ratio of 1+1+1 = 3, while b.com will get a total ratio of 2+2 = 4, while the static pool member has a ratio of 5

To acheive a 1:1:1 ratio balance between a.com, b.com, and the static pool member, we will need to consider the number of ephemeral pool members returned by the DNS server.

For example:

a.com 10.0.1.1 ratio 2
a.com 10.0.1.2 ratio 2
a.com 10.0.1.3 ratio 2
b.com 10.0.2.1 ratio 3
b.com 10.0.2.2 ratio 3
static 10.0.3.1 ratio 6

This gives us a 2+2+2=6, 3+3=6, and 6 ratio values, which translates to a 1:1:1 load-balancing weight between a.com, b.com and the static pool member.

Other Use Cases

What if the DNS server returns an undetermined and dynamically changing number of IP addresses?

For example, at one point, a.com can contain 3 members.

a.com 10.0.1.1 ratio 1
a.com 10.0.1.2 ratio 1
a.com 10.0.1.3 ratio 1

Two weeks later, the FQDN provider unpredictably changes its hosts and provides only two with one ipv6 address:

a.com 10.0.1.1 ratio 1
a.com 10.0.1.2 ratio 1
a.com ::100 ratio 1

Option 1: On the DNS server level, consider using the F5 BIG-IP DNS to optimize and control the provisioning of IP addresses to clients. The F5 BIG-IP DNS can provide IP addresses based on the client's LDNS proximity, topology, round-trip-time, hops, and other metrics, as well as a server's measured load, traffic, and many other dynamic and static load-balancing methods.

(See the F5 technical documentation for your version of F5 BIG-IP DNS more information: BIG-IP DNS: Load Balancing )

Option 2: You can create different pools and load-balance among those pools. You can then use iRules to control the distribution of connections between the pool members. For example:

Pool A contains a.com
Pool B contains b.com
Pool C contains all static pool members

We can then use an irule on the virtual server to distribute connections between the pools evenly or in any desired ratio:

when CLIENT_ACCEPTED {
  set x [expr rand()]
  if {$x < 0.33333} { 
    log local0. "pool A"
    pool pool_a
  } elseif {$x < 0.66666} {
    log local0. "pool B"
    pool pool_b
  } else {
    log local0. "pool static"
    pool pool_static
  }
}
