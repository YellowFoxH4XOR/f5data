Description

The article addresses the issue on BIG-IP where connections are persistently established and do not close. These connections can be viewed using the "tmsh show sys connection" command, where we continually see these entries even when the client is not utilizing the given connection. This can lead to a slight increase in resource usage on the device when there is a vast number of such connections.

 

Environment

  • BIG-IP
  • Virtual Server
  • TCP profile

 

Cause

The root cause of this behavior might be an improperly configured TCP profile attached to the Virtual server. The most common reason might be the intent to set up a proxy, but improperly selected settings result in these connections never closing.

 

 Recommended Actions

The actions or steps required to address the topic covered in the description. You can easily check if this issue affects you:

 

1. Ensure the connection is definitely terminated by either enforcing it on the client or by deleting it using the command: 

tmsh delete /sys connection cs-client-addr <client_ip> cs-server-addr <vs_ip> cs-server-port <vs_port>

 

2. After removal or termination, verify if it still appears in the connection table using: 

tmsh show /sys connection cs-client-addr <client_ip> cs-server-addr <vs_ip> cs-server-port <vs_port>

 

3. If the connection still appears, but with a reduced age, this indicates that the issue might affect you.

 

Here is the part of the configuration that makes connections to be proxied:

 

ltm profile tcp /Common/custom-tcp-proxy {

fin-wait-timeout 5

keep-alive-interval 180 <---

idle-timeout 300 <---

}

 

But there needs to be specified one more value: fin-wait-2-timeout.

 

This is the reason why the connections are not terminated from the F5 side. If one of the devices on the Server or Client side does not answer for FIN flag, the connection will be still established and exist as a loop. Therefore if you would like to avoid this you can specify the fin-wait-2-timeout on your tcp profile. This FIN-wait-2 flag status is enabled when one of the devices sends the FIN flag without any answer then a second fin will be sent to terminate the connection. To do so, you need to specify fin-wait-2-timeout and it needs to be smaller than keep-alive to avoid further loops.
