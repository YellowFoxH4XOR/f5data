Description
This article applies to BIG-IP 11.x through 14.x when FIPS-mode is not enabled. For information about later versions, refer to the following article:

  • K24290241: Overview of the BIG-IP core file retention policy
When a process (like TMM) crashes on the BIG-IP, it will write it's current state to a core file which is then saved in the /var/core directory. This data can be helpful to F5 in determining the root cause of the crash. By default, each process will write only a single core file, overwriting any previous core file it generated. If a process's initial crash resulted in subsequent crash(es), the data from the initial precipitating crash will be overwritten. This will complicate further investigation which relies on that initial crash's core file.

This details how to change default behavior to save the initial core file generated by a process in addition to the latest (if multiple core files are generated).

Environment

  • BIG-IP 11.x to 14.x.
  • FIPS-mode disabled

Cause
None

Recommended Actions
Note: Saving the initial core file generated in addition to the latest core file will increase the potential disk space usage in /var/core by double at most. Only in rare circumstances will this have adverse impact on the BIG-IP. Periodic review of disk usage on the BIG-IP is recommended.

Warning: FIPS-mode does not allow modification of core files like the /usr/bin/corehelper script. Altering core files while in FIPS-mode will result in system integrity check failure and prevent boot up. Do not use this procedure when FIPS-mode is enabled. When FIPS-mode is needed, upgrade to version 15.0 or later for the desired core file saving functionality. 

Note: This customization will not persist through upgrade and will need to be re-added after upgrade. The configuration is not needed if upgrading to version 15.0 later where this functionality is controlled via config settings.

The process describes how to alter default behavior to save the initial core file a process generates in addition to any subsequent core files it generates. This is done by expanding the /usr/bin/corehelper script.

  1. Access bash shell on BIG-IP (via console or SSH)
  2. Remount /usr as read-write filesystem
    mount -o remount, rw /usr
  3. Back up the original "corehelper" script
    cp /usr/bin/corehelper /usr/bin/corehelper.original
  4. Edit the script
    vi /usr/bin/corehelper
  5. Paste in the following information at the very end of the file
    # Added per KXXXXXXX
    SAVF="${OUTF}.initial"
    if [ -f "$SAVF" ]; then
        $LOGCMD "Initial core file: $SAVF"
    else
        $LOGCMD "Saved initial core file $OUTF as $SAVF"
        mv $OUTF $SAVF
    fi
  6. Save and quit the file
  7. Remount /usr as read-only filesystem
    mount -o remount, ro /usr
The next time the script is executed by the system processes it will utilize the additional code. No restart of processes or reboot is required.

To rollback these changes, perform the following procedure:
  1. Access bash shell on BIG-IP (via console or SSH)
  2. Remount /usr as read-write filesystem
    mount -o remount, rw /usr
  3. Replace the altered script with the original
    mv /usr/bin/corehelper.original /usr/bin/corehelper
  4. Remount /usr as read-only filesystem
    mount -o remount, ro /usr
Once again these changes will take place immediately, for the next core file write which occurs.

Additional Information
In default behavior, the system will generate a core file with a name specific to the process, like "tmm.bld0.0.1.core.gz". Any subsequent crash of the process will overwrite that file with a new file of the same name, only leaving the most recent core file. The expanded script continues the same behavior andwever after the file is saved, the script now looks for a file with the name of the core file but with ".initial" appended to it, like "tmm.bld0.0.1.core.gz.initial". If that file does not exist, the core file is renamed with that extension, becoming the preserved initial core file. This action will be taken only once for each process. Any subsequent crashes of the same process generate cores without the .initial name, ensuring that initial file is never overwritten.

When gathering core file(s) from a system which has implemented this expanded functionality, the ".initial" core file will be of most importance while the standard core file should also be provided to F5 as it still may have value.

Finally, this expanded script adds several additional log messages related to core file generation to /var/log/user.log similar to what currently exists.

Here are the log messages (new message highlighted) when the first core file for a specific process is generated:

Jan 14 09:58:42 bigip1 notice logger: Finished writing 63040844 bytes for core file: /var/core/tmm.bld0.0.1.core.gz for PID 5903
Jan 14 09:58:42 bigip1 notice logger: Saved initial core file /var/core/tmm.bld0.0.1.core.gz as /var/core/tmm.bld0.0.1.core.gz.initial
