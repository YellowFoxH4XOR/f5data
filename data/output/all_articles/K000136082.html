Description

However, the "df -h" command did not reflect the correct partition size even though the /var volume size is allocated with the 131 GB in the lvscan command below.

Environment

BIG-IQ VE 8.0.0

BIG-IQ DCD

 

Cause

It should be a Hypervisor disk issue which needs filesystem fsck to fix it.

 

Recommended Actions

Please double-check the actual size and allocated size for each issued /shared, /var/log, /var filesystem with the following commands below;

# df -h

Filesystem Size Used Avail Use% Mounted on



/dev/mapper/vg--db--vda-dat.share.1 30G 7.0G 22G 25% /shared

/dev/mapper/vg--db--vda-dat.log.1 6.7G 991M 5.3G 16% /var/log

/dev/mapper/vg--db--vda-set.2._var 74G 16G 55G 23% /var <====== Same /var filesystem issue

 

 

 

 

# lvscan



NAME AJ:MIN RM SIZE RO TYPE MOUNTPOINT

-vg--db--vda-dat.share.1 253:1 0 100G 0 lvm /shared

-vg--db--vda-dat.log.1 253:2 0 100G 0 lvm /var/log

-vg--db--vda-set.2._var 253:11 0 300G 0 lvm /var

 

 

 

 

And then, please follow up the suggested steps because the filesystem check for each issued /shared, /var/log, /var filesystem to be unmounted and then resized in the maintenance operating system (MOS) mode as stated in K1424;

 

1. Reboot the BIG-IQ system into MOS

2. Most of the file systems will be unmounted. If the /shared, /var/log & /var is mounted, then please unmount them.

3. Execute the command for all the filesystems which you are noticing the difference.

 

 

#umount /var          =====> Run this command only if the partition is mounted.

 

 

 

 

For example of /var filesystem;

 

#e2fsck -yf /dev/mapper/vg--db--vda-set.2._var



#resize2fs /dev/mapper/vg--db--vda-set.2._var



#mount /dev/mapper/vg--db--vda-set.2._var /var



#df -h

 

 

 

 

Restart the system using the following command:

 

 

#reboot

 

 

 

 

Once the system is booted back, check the partition size.

 

Note: To scan all disks for logical volumes, type the "lvscan" command and then determine which logical volume contains the files that you want to retrieve
