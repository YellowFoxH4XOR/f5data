Description

Injection attacks are a class of attacks against any application which accepts and interprets user supplied input without properly validating, filtering or sanitizing that input, and where that input is subsequently used to query an underlying data provider such as a SQL database or LDAP server. The most commonly known attack is a SQL injection attack against a web application, which allows an attacker to inject arbitrary SQL into an otherwise legitimate query with the aim of retrieving or modifying information to which a legitimate user should not have access.

Environment

A web application being delivered to a web browser on a client device (e.g., Chrome, Edge, Firefox etc)

Cause

  • A web application which does not properly validate, filter or sanitize user input

Recommended Actions

It is possible to mitigate most injection attacks against web applications using BIG-IP Advanced WAF, NGINX App Protect, Silverline WAF etc to block potentially malicious user input from being ingested and interpreted by the web application. Specific instructions are outside of the scope of this document as any policy must be tailored to the web application in question.
 
If you are concerned about a known injection vulnerability in the BIG-IP Configuration Utility (e.g., an SQL injection vulnerability) the best mitigation is to ensure your administrators:
  • Access the Configuration Utility from a dedicated management host, jump box or another controlled environment
  • Do not click on links to access the Configuration Utility but rather enter the address manually or use a bookmark

Additional Information

The term “injection attack” refers to any of a class of attacks where malicious user input is provided to the web application and is later used within a query or other operation where the input was assumed safe; most commonly this refers to a SQL injection attack where a malicious actor injects arbitrary SQL commands into user input and the web application subsequently executes the injected SQL to perform malicious actions such as defacement, deletion of data or extraction of data the user would not ordinarily have access to.

The term can also commonly refer to injection of operating system commands, NoSQL queries or LDAP queries amongst others.

Since the most common injection attack is arguably SQL injection, we will concentrate on that here. Imagine a web application which uses untrusted user input to construct a SQL call, similar to the following pseudocode:

user = $_COOKIES['user']
query = "SELECT * FROM users WHERE user='" + $user + "'";

Assuming a legitimate user’s name is stored in the ‘user’ cookie, the query might look like the following prior to execution:

SELECT * FROM users WHERE user='bob';

If an attacker modifies the cookie value, however, to contain ' or '1'='1, then the query constructed would look as follows:

SELECT * FROM users WHERE user='' or '1'='1';

This changes the meaning of the query significantly and, rather than returning the single record pertaining to the user, would return all the records from the ‘users’ table since the injected SQL causes the WHERE clause to always return ‘true’. In a similar manner an attacker may be able to cause the web application to construct a query that would result in modification of data, deletion of data or the execution of stored procedures that would not normally be accessible to users. 

 
Mitigations
 
Application-side mitigations for injection attacks are:
  • Use a “safe” API which provides a parameterized interface to the target data (e.g., SQL)
    • For SQL, use prepared statements and parameterized queries
  • Ensure that any dynamic queries use the appropriate character escaping mechanisms, specific to the target data
  • If user input is used for column names or similar (e.g., in SQL queries), map the provided user input to a fixed list rather than using the user input directly
  • Use an allow-list approach for valid characters in user input fields

Deny lists of invalid characters, specifically, may not provide adequate protection as some targets (e.g., SQL server) may interpret Unicode characters as ASCII equivalents, leading to a large and unpredictable range of characters requiring black-listing. This is called a Unicode Homoglyph attack or Unicode Smuggling.

You can also use a Web Application Firewall such as Advanced WAF, ASM, NGINX App Protect etc to:
  • Check user inputs against signatures of known injection attacks
  • Check user inputs against signatures of known vulnerabilities in web frameworks & applications
  • Block inputs containing deny-listed characters or allow only allow-listed characters
 
A combination of both methods for a Defence-in-Depth posture is highly recommended.
