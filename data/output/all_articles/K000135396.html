Description

GTM sync and RFS sync stops working after out of memory condition

The following logs can be seen in /var/log/ltm:

warning tmm[29754]: 011e0002:4: sweeper_segment_cb_any: Aggressive mode /Common/default-eviction-policy activated (0) (global memory). (3564153/4192768 pages)

warning tmm[29754]: 01010290:4: TCP: Memory pressure activated

err tmm[29754]: 011e0003:3: Aggressive mode sweeper: /Common/default-eviction-policy (0) (global memory) 422 Connections killed

 

Environment

  • BIG-IP DNS versions 12.x.x to 17.x.x
  • DNSSEC
  • nShield netHSM

Cause

Bug ID 966461

Recommended Actions

Upgrade to fixed version and set dnssec.fipswaitingqueuecap to an appropriate value

Additional Information

Here is some guidance for setting an appropriate value for dnssec.fipswaitingqueuecap:

Use the following command to view the sig_queued stats during peak times:

tmctl -d /var/tmstat/blade/ dnssec_stat

Based on the TMM memory available, a value for dnssec.fipswaitingqueuecap can be determined per TMM (sig_queued value is for all TMM's).

The chosen value must be specifically tuned for each environment.

Start by identifying a peak sig_queued of X, and you could cap the queue at twice this value 2X for example.

dnssec.fipswaitingqueuecap =  2X / Number of TMM's

In order to account for seasonality (periods of expected increased traffic) and TMM has sufficient memory, you may decide 3X or 4X is more appropriate for your environment. It is important that TMM doesn't run out of memory if the value is too high.

For a single crypto request, dnssec_rrsig holds 4.1K bytes of memory out of which the buffer allocated for signature creation takes most of the memory. The higher the value set for dnssec.fipswaitingqueuecap, the higher the potential TMM memory utilised.
