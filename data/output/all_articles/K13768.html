Topic

You should consider using this procedure under the following condition:

  • You have a BIG-IP LTM or BIG-IP GTM system.
  • Your BIG-IP system has a large number of pool members monitored by an HTTPS type monitor.
  • You need to identify a specific pool member that is marked down by the monitor.

Description

The BIG-IP system's HTTPS type monitor uses SSL/Transport Layer Security (TLS) to send and receive content from secure web servers to verify the availability status. When an HTTPS monitor experiences SSL/TLS related failures, error messages similar to the following example are logged to the /var/log/ltm file for LTM based monitors or /var/log/gtm file for GTM base monitors:

err bigd[12345]: 01060111:3: Open SSL error - error:140790E5:SSL routines:SSL23_WRITE:ssl handshake failure.

The error message itself does not indicate specifically which pool member is failing. To identify specifically which HTTPs monitored pool member by IP address is failing, use one of the following procedures.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • Command line access to the BIG-IP system.

Procedures

  • BIG-IP LTM: Identifying which HTTPS monitored pool members are failing
  • BIG-IP GTM: Identifying which HTTPS monitored pool members are failing

BIG-IP LTM: Identifying which HTTPS monitored pool members are failing

The BIG-IP LTM system can log failure messages for a specific pool member by setting the bigd process logging level to debug. When set to debug, the bigd process will log error messages for specific pool members to the /var/log/bigdlog file.

Impact of procedure: Performing the following procedure may have a negative impact on your system. When enabling debug logging on a busy system for an extended period of time may result in disk space exhaustion and a possible fail over event.

  1. Log in to the BIG-IP command line.
  2. To enable debug logging for the bigd process, type the following command:

    tmsh modify sys db bigd.debug { value enable }

  3. To monitor the /var/log/bigdlog file, type the following command:

    tail -f /var/log/bigdlog |grep 'return ssl false'

    In the following example output, you can identify the node that fails an SSL handshake by the return ssl false message:

    ID 40 :(_ssl_shutdown_service): shutting down, return ssl false [ addr=::ffff:10.12.23.27:80 srcaddr=::ffff:10.12.23.139%0:52845 mon=/Common/https fd=9 ]

  4. After you identify the specific pool member by IP address, return to the command line by pressing the CTRL+C keys.
  5. To disable debug logging for the bigd process, type the following command:

    tmsh modify sys db bigd.debug { value disable }

  6. To verify that the debug has been disabled for the bigd process, type the following command:

    tmsh list sys db bigd.debug

BIG-IP GTM: Identifying which HTTPS monitored pool members are failing

The BIG-IP GTM system can log failure messages for a specific pool member by enabling the gtm.debugprobelogging database variable. When gtm.debugprobelogging is set to enable, the gtmd process will log error messages for specific pool members to the /var/log/gtm file.

Impact of procedure: Performing the following procedure may have a negative impact on your system. When enabling debug logging on a busy system for an extended period of time may result in disk space exhaustion and a possible fail over event.

  1. Log in to the BIG-IP command line.
  2. To enable debug logging for the gtmd process, type the following command:

    tmsh modify sys db gtm.debugprobelogging { value enable }

  3. To monitor the /var/log/gtm file, type the following command:

    tail -f /var/log/gtm |grep 'protocol mismatch'

    In the following example output, you can identify the node that fails an SSL handshake by the state: protocol mismatch message:

    notice gtmd[16622]: 011ae03d:5: Probe from 10.11.23.139: buffer = <monitor> <name>/Common/https</name> <addr>::ffff:10.12.23.127</addr> <port>80</port> <trans_addr>::ffff:10.12.23.127</trans_addr> <trans_port>80</trans_port> <server_name><![CDATA[/Common/lc1.example.com]]></server_name> <vs_name><![CDATA[/Common/vip_two]]></vs_name> <monitor_state>6</monitor_state> <node_type>3</node_type> <monitor_type>5</monitor_type> <vs_score>0</vs_score> <why>state: protocol mismatch</why> <probe_time>1860</probe_time> </monitor>

  4. After you identify the pool member by IP address, return to the command line by pressing the CTRL+C keys.
  5. To disable debug logging for the gtmd process, type the following command:

    tmsh modify sys db gtm.debugprobelogging { value disable }

  6. To verify that the debug has been disabled for the gtmd process, type the following command:

    tmsh list sys db gtm.debugprobelogging

Recommended Actions

  • Common reasons for monitor failures include:
    • An HTTPs monitor is applied to a non HTTPS pool member. In this case, an HTTP monitor may mark the pool member status as available.
    • The pool member does not support the same SSL/TLS properties as the HTTPs monitor. For example, the pool member does not support any version of TLS. For additional information on troubleshooting SSL/TLS issues, refer to K15292: Troubleshooting SSL/TLS handshake failures
  • If additional diagnostic information must be obtained to further troubleshoot a connection issue, you can use the tcpdump utility and filter based on the the pool member's IP address. For additional information on using the tcpdump utility, refer to K411: Overview of packet tracing with the tcpdump utility
