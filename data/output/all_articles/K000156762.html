K000156762: Dropping DNS Traffic From a Specific Region

Type
Support Solution
Published
2025-12-22
Updated
2025-12-22
Applies to
  • BIG-IP
  • BIG-IP DNS: 17.5.0
Source
https://my.f5.com/manage/s/article/K000156762

Description

DNS traffic response discrepancies can occur in BIG-IP DNS (GTM) deployments when WideIP pools are configured with no available members (pool status "red") and the fallback action is set to "Return to DNS." In this configuration, DNS queries may continue to receive responses despite the absence of pool members, which can lead to confusion regarding traffic statistics and handling. Additionally, topology rules that route traffic based on client country with a fallback of "Drop Packet" will silently drop packets without notifying the DNS client. Attempts to use iRules for custom DNS responses or error codes are limited by command availability within the DNS context.

Environment

  • Product: BIG-IP DNS (GTM)
  • Version: 17.5.0
  • Configuration details:
    • WideIP pools with no available members ("red" status)
    • Pool fallback actions set as "Return to DNS" or "Drop Packet"
    • Topology rules based on client country
    • iRules attached either at WideIP or Listener level

Cause

  • With pool fallback set to "Return to DNS," queries for WideIPs with no available pool members are returned to the resolver, resulting in continued traffic and responses.
  • Setting fallback to "Drop Packet" causes silent drops; clients do not receive feedback.

Recommended Actions

  1. Pool Fallback Action:
    Change pool fallback from "Return to DNS" to "Drop Packet" for WideIPs with no available members if you want all such queries dropped silently.
    If explicit feedback is required for dropped queries (such as sending RCODE REFUSED), attach an iRule at the Listener level using LTM syntax:

    when DNS_REQUEST {
        if { [DNS::is_wideip [DNS::question name]] } {
            set client_ip [IP::client_addr]
            set country [whereis $client_ip country]
            if { $country eq "IN" } {
            DNS::header rcode REFUSED
            DNS::return
    }
    }
    }

    This example sends an RCODE REFUSED for requests originating from India targeting WideIP hostnames; adapt logic as needed.
  2. Limitations:
    Custom content such as HTML cannot be sent in a DNS response using GTM/DNS iRules.
    Always test new or modified iRules during a maintenance window due to their impact on all requests processed by the Listener.
    Support for custom iRules is limited; ensure thorough validation and testing before production deployment.
  3. Monitoring:
    After making changes, review relevant statistics and logs to confirm expected behavior—such as dropped queries or specific RCODE responses.
