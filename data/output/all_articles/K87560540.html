Description

Aspen Mesh Packet Inspector (Pcapper) captures the HTTP/2 traffic flowing through the service mesh internally before it is converted from plaintext to mTLS. It generates the plaintext representation of that traffic and forwards it to a packet broker. This traffic is encrypted between Pcapper and the packet broker via outer TLS wrapper using keys and certs that identify both ends. 

One on-the-wire TCP session may contain a mix of many different requests/responses (conflating multiple transactions, call flow, etc.). The virtual representation contains only one request/response per virtual TCP flow. It is then delivered to the packet broker via HTTP POSTs containing the metadata (which pod this came from, what OpenTracing trace ID is associated with it, etc.) and pcaps (the most generic format for recording packet captures). 

The simplest mode for Aspen Mesh Packet Inspector is where all the packets for a small transaction are sent and received in a short window of time. In this case, the entire request and response can be delivered in one HTTP POST to the packet broker which contains metadata and a pcap (approximately 8 packets).

Aspen Mesh will split a single transaction across multiple HTTP POST to packet broker under following cases:

  1. The transaction takes longer than tapfilterTimeout to complete. This case is designed to deliver a partial packet capture to tools (i.e. packet broker) to diagnose hung transactions – if we always wait until a transaction is entirely complete, then tools have no chance to operate on a transaction where, for instance, the request has been sent but the server is taking a long time to generate a response.

    Behavior: We buffer and group packets until tapfilterTimeout elapses, then we send a new capture to GCB with we have so far, delete our in-memory copies of what was delivered, and restart tapfilterTimeout.

  2. The transaction takes more than tapfilterBufferSize to complete. This case is designed to deliver very large transactions in small pieces to relieve memory pressure on Aspen Mesh and other components. Imagine a 1GB file transfer – without this behavior, Aspen Mesh would have to buffer approximately 1GB of data in memory, then send an enormous 1GB HTTP POST to GCB, and so on.

    Behavior: We buffer and group packets until we have used tapfilterBufferSize for our internal storage for this transaction, then we send a new capture to GCB with what we have so far, delete our in-memory copies of what was delivered, and restart counting towards tapfilterBufferSize.

Environment

  • Aspen Mesh: 1.6.14 and later
  • Kuberntes: 1.18 and later 

Cause

In cases where you look at the single transaction pcap file and if these packet captures (which included the whole 3 way handshake, request and response) are larger than the Buffer Size configured, Pcapper went break these single transaction into multiple POST before sending it to the packet broker. In a comparable manner, if your single transaction is taking longer than filter timeout configured, it will break it into multiple POST before sending it to packet broker. Here is the documentation on how to configure the pcapper configuration.

So if the Buffer Size is configured less than 10954 kb, pcapper will send this transaction into multiple HTTP POST response to the packet broker.
