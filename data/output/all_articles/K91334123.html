K91334123: After upgrade REST API calls fail with ''401 Authentication Failed''

Type
Support Solution
Published
2022-05-25
Updated
2025-05-01
Applies to
  • BIG-IP
Source
https://my.f5.com/manage/s/article/K91334123

Description

Since upgrading to BIG-IP versions (17.0.0, 16.1.2.2, 15.1.5.1, 14.1.4.6, 13.1.5), periodically getting 401 errors with REST calls with token-based authentication.

This issue may occur intermittently.

Environment

  • BIG-IP version 17.0.0, 16.1.2.2, 15.1.5.1, 14.1.4.6, 13.1.5
  • REST API calls with token-based authentication (such as using curl with a token in a script)
  • AS3 deployments
  • Ansible
  • Python programs that rely on token authentication

Cause

There are a few potential causes for this issue and workarounds depending on how you are encountering the issue.  Two of which are:

  • Token generation issues on 13.1.5 and 14.1.4.6 are generally due to ID877145. 
    1. In some instances a token may fail to generate as a result of ID877145 on version 14.1.4.6 or 13.1.5. If that happens and your script does not test for the existence of a token and attempts to make a call with a null token value (due to failed generation) you can encounter a 401 error.
  • Use of that token failing to authenticate are due to ID1108181.
  1. A common issue inside of scripts is when tokenrefresh is called this is primarily used inside of the F5 modules with python. This refresh often fails. If you can modify your code to either generate a new token or continue to use the old one it will limit the instances of this 401 issue.
  2. The third common issue where this is seen is when your script generates a token and then attempts to use it rapidly (typically in less than 1 second of generation).  If you simply introduce a delay of 1 second between token generation and use then it can remediate this issue.
  3. Ansible playbooks and AS3 deployments will frequently encounter this - a workaround does not exist for those.
  • REST Requests return 401 Unauthorized when using Basic Auth due to ID1035661
  1. Triggered when a REST request comes in using Basic Auth while an asynchronous task is executing on the BIG-IP. An example of an asynchronous task is the BIG-IP processing an AS3 declaration.  
  • Basic authentication for REST admin account failing due to ID1146373
  1. If you view the restjavad.audit log you may see a username of local/null on the line showing the 401 for the rest call that was tried.
  2. [I][1223][05 Jan 2022 17:21:19 UTC][ForwarderPassThroughWorker] {"user":"local/null","method":"GET","uri":"http://localhost:8100/mgmt/tm/ltm/node","status":401,"from":"X.X.XX.X"}

Note: The behavior of local/null is normal if the username and password are sent in the body of the JSON. If local/null is seen using a curl -u request, then this is an indicator that you are hitting ID1146373.
 

  • Bug ID 1025513: PAM Authenticator can cause authorization failure if it fails to lock /var/log/tallylog
  1. This is a similar issue with an identical log message as the previous symptom. Clients see the following message:
  2. {"code":401,"message":"Authorization failed: no user authentication header or token detected. Uri:http://localhost:8100/mgmt/tm/ltm/pool/?expandSubcollections=true Referrer:<ip_address> Sender:<ip_address>,"referer":<ip_address>,"restOperationId":12338804,"kind":":resterrorresponse"}

Recommended Actions

Token generation issues on 13.1.5 and 14.1.4.6 are generally due to ID877145. 

  1. Review the /var/log/restjavad.0.log logs for the following:
    [SEVERE][8100/shared/authn/login AuthnWorker] Error as the maximum time to wait exceeded while getting value of loginProviderName
    [SEVERE][8100/shared/authn/login AuthnWorker] Error while setting value to loginProviderName when no loginReference and no loginProviderName were given
  2. Upon confirmation of hitting this an engineering hotfix can be requested from support.

Use of that token failing to authenticate are due to ID1108181.

If you are on an affected version and suspect you are encountering ID1108181 when using a rest token, AS3, or ansible then you can enable http debugging then restart httpd/syslog and you will see this log message within /var/log/httpd/httpd_errors after you encounter it:

  1. To enable debug logging for http:
    1. tmsh modify /sys httpd log-level debug
    2. tmsh modify /sys syslog local6-from debug
  2. To restart the relevant daemons:
    1. bigstart restart httpd
    2. bigstart restart syslog-ng
  3. Review /var/log/httpd/httpd_errors logs for the following:
    bigip.device.com debug httpd[30629]: [auth_pam:debug] [pid 30629] mod_auth_pam.c(2495): [client 10.5.1.193:47110] AUTHCACHE failed to open file Permission denied
  4. To reset these values and the daemons back to default run:
    1. tmsh modify /sys httpd log-level warn
    2. tmsh modify /sys syslog local6-from notice
    3. bigstart restart httpd
    4. bigstart restart syslog-ng
  5. Upon confirmation of hitting this we recommend upgrading to a version that has a fix for Bug ID 1108181
