Known Issue

TCP retransmissions that are sent by the BIG-IP system from a Virtual Local Area Network (VLAN) group may not have the media access control (MAC) address set correctly.

This issue occurs when all of the following conditions are met:

  • A standard virtual server, enabled on a VLAN group, is configured without a secure network address translation (SNAT).
  • The VLAN group Transparency Mode option is set to Translucent.
  • Packet loss occurs and causes the BIG-IP system to send TCP retransmissions.

The Transparency Mode setting, within the VLAN group configuration, specifies the level of exposure of remote MAC addresses. The default option is Translucent, which forwards the MAC address with the locally administered bit set. For more information, refer to the VLANs and VLAN Groups chapter of the BIG-IP TMOS: Concepts guide for your version of the BIG-IP system.

Impact

Traffic egressing the BIG-IP system with the source MAC address of another host may result in traffic loops.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • Some TCP retransmissions are forwarded to the backend server with the client's source MAC address.

    For example, refer to the following diagram and scenario:


     

    In this diagram, the BIG-IP system is configured with two VLANs named External and Internal. Both VLANs are assigned to the vg1 VLAN group, which is configured for Translucent mode.

    The host named Client resides on the External VLAN, and the host named Server resides on the Internal VLAN. Their respective IP addresses are 10.1.0.1 and 10.1.0.10.

    The following pool is created on the BIG-IP system:

    ltm pool /Common/pool_ssh {
    members {
    /Common/10.1.0.10:22 {
    address 10.1.0.10
    }
    }
    monitor /Common/tcp
    }

    The following virtual server is created on the BIG-IP system:

    ltm virtual /Common/vs_ssh {
    destination /Common/10.1.0.20:22
    ip-protocol tcp
    mask 255.255.255.255
    pool /Common/pool_ssh
    profiles {
    /Common/tcp { }
    }
    source 0.0.0.0/0
    translate-address enabled
    translate-port enabled
    }

    A request that originates from the Client host, destined for the vs_ssh virtual server, would have the source IP address as 10.1.0.1 and the source MAC address as 00:50:56:92:1e:87. Under normal circumstances, when the BIG-IP system load balances the request from the Client, to the Server, the source MAC address from the Client is applied, with the locally administered bit set, or 02:50:56:92:1e:87.

    Occasionally, TCP retransmissions sent from the BIG-IP system to the Server will incorrectly include the original Client MAC address: 00:50:56:92:1e:87, without setting the locally administered bit (02).

Workaround

To work around this issue, you can enable a SNAT on the affected virtual server. To do so, perform the following procedure:

Impact of workaround: Depending on your application environment, you may need to add the SNAT address to the allowed lists for various devices.

  1. Log in to the Configuration utility.
  2. Click Local Traffic.

    Note: If you want to create a pool of SNAT addresses, perform steps 3 through 9. Otherwise, skip to step 10.
  3. Click Address Translation.
  4. Click SNAT Pool List.
  5. Click Create.
  6. Type a name for the SNAT pool.
  7. In the IP Address box, type a SNAT IP address and then click Add.
  8. Repeat the previous steps for the remaining SNAT IP addresses.
  9. To save the changes, click Finished.

    Note: To enable the SNAT configuration on the affected virtual server, perform steps 10 through 14.
  10. Click Virtual Servers.
  11. Click Virtual Server List.
  12. Select the name of the affected virtual server.
  13. From the Source Address Translation list, select the desired option.

    Note: Selecting the SNAT option from the Source Address Translation list enables the SNAT Pool list. You can choose your SNAT pool from this list.
  14. Click Update.
