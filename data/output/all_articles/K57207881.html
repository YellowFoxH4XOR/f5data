Description

Attempting to secure http headers with some or all of the recommended security practices securityheaders.com

Environment

  • BIG-IP
  • Virtual server
  • HTTP profile

Cause
None

Recommended Actions

  1. Firstly we must create the action where we place the code to adjust the headers:
    when HTTP_RESPONSE_RELEASE {
        ...
    }
  2. Inside the response action we can determine which security measures to implement
    1. For Strict Transport Security there are three possible values to include in the header. Max Age which is required, as well as includeSubdomains and preload which are optional.
      if {!([HTTP::header exists "Strict-Transport-Security"])} {
          HTTP::header insert Strict-Transport-Security "max-age=31536000; includeSubdomains; preload"
      }
    2. For Content Security Policy there are a significant number of configuration parameters, which don't allow for a full account in this article.  However, the specification while maintained by W3.org is extremely well documented by Mozilla:
      Content Security Policy (CSP)

      This is a reasonable example for general use:
      if {!([HTTP::header exists "Content-Security-Policy"])} {
          HTTP::header insert Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self'; font-src 'self'; img-src 'self'; frame-src 'self'; upgrade-insecure-requests"
      }
    3. For Referrer Policy it supports only one value, but there is a range of options.  The options available are as follows: no-referrer, no-referrer-when-downgrade, origin, origin-when-cross-origin, same-origin, strict-origin, strict-origin-when-cross-origin, unsafe-url
      These do have specific use cases and are also well documented at Mozilla:
      Referrer-Policy

      This is a reasonable example for general use:
      if {!([HTTP::header exists "Referrer-Policy"])} {
          HTTP::header insert Referrer-Policy "strict-origin"
      }
    4. Permissions Policy is relatively new as it resulted from an update and rename of the Feature Policy header.  Its purpose is to allow a site to turn on or disable some browser properties and API.  The configuration options are still being updated, but preliminary capability would be similar to Feature Policy.  The current Mozilla reference has yet to be updated, but it is flagged for update:
      Feature-Policy
      Here is a basic example, but it will need to be adjusted based on your application needs:

      if {!([HTTP::header exists "Permissions-Policy"])} {
          HTTP::header insert Permissions-Policy "geolocation=(self \"https://example.com\"), microphone=()"
      }

    5. The X-Frame-Options header allows for controlling the ability of certain objects to be rendered in a browser to limit click jacking possibilities.  There are two possible values deny and sameorigin.  Details are again documented well at Mozilla:
      X-Frame-Options

      Here is a common example:
      if {!([HTTP::header exists "X-Frame-Options"])} {
          HTTP::header insert X-Frame-Options "DENY"
      }

    6. Last on our list for the check against secureheaders.com is the X-Content-Type-Options.  There is only a single value which is nosniff.  Here is the Mozilla documentation:
      X-Content-Type-Options
      if {!([HTTP::header exists "X-Content-Type-Options"])} {
          HTTP::header insert X-Content-Type-Options "nosniff"
      }

 

Here is an example of the full iRule put together:

when HTTP_RESPONSE_RELEASE {
   if {!([HTTP::header exists "Strict-Transport-Security"])} {
       HTTP::header insert Strict-Transport-Security "max-age=31536000; includeSubdomains; preload"
   }
   if {!([HTTP::header exists "Content-Security-Policy"])} {
       HTTP::header insert Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self'; font-src 'self'; img-src 'self'; frame-src 'self'; upgrade-insecure-requests"
   }
   if {!([HTTP::header exists "Referrer-Policy"])} {
       HTTP::header insert Referrer-Policy "strict-origin"
   }
   if {!([HTTP::header exists "Permissions-Policy"])} {
       HTTP::header insert Permissions-Policy "geolocation=(self \"https://example.com\"), microphone=()"
   }
   if {!([HTTP::header exists "X-Frame-Options"])} {
       HTTP::header insert X-Frame-Options "DENY"
   }
   if {!([HTTP::header exists "X-Content-Type-Options"])} {
       HTTP::header insert X-Content-Type-Options "nosniff"
   }
}

Additional Information
This article is applicable when BIG-IP forward the HTTP data between client and pool member.
Please verify the client is compatible with the HTTP headers, the new header will not cause the application abnormal.

In some cases additional adjustment may be required.  Specifically APM has an additional event call to allow iRule processing:
