K14184: Troubleshooting BIG-IP APM Portal Access applications

Type
Knowledge
Published
2013-02-13
Updated
2026-10-30
Applies to

  • BIG-IP APM
Source

Description

You should consider using this procedure under the following condition:

  • Users have issues accessing applications through BIG-IP APM Portal Access.

Symptoms

You may observe one or more of the following symptoms:

  • The web page, or items on it, does not display.

  • Links do not open, or forms are not submitted correctly.

  • The browser developer console shows JavaScript errors.

Environment

  • BIG-IP APM 17.1.x, 17.5.x, or 21.1.x

  • Portal Access resource configured

Cause

Portal Access rewrites HTML, CSS, and JavaScript so that the application can be accessed through the BIG-IP APM virtual server. When content is not rewritten correctly, the application does not work as expected. The issue can also be in the application, the browser, or the BIG-IP APM configuration.

Answer/Recommended Actions

Use the following procedures to find the cause:

  • Accessing the web application directly

  • Accessing the web application with a different browser or client system

  • Checking the BIG-IP APM configuration

  • Checking JavaScript rewriting

  • Collect HTTPWatch or HAR files for support

Accessing the web application directly

Access the web application directly from the client system, without BIG-IP APM. If the issue also occurs, investigate the application or the browser first, before you troubleshoot Portal Access.

Accessing the web application with a different browser or client system

  1. Access the application through Portal Access with another supported browser. For supported browsers, refer to K14047: Supported operating systems and web browsers for the BIG-IP APM system.

  2. Access the application through Portal Access from another client system.

If the issue does not occur, compare the browser versions, browser extensions, and proxy settings of the two systems.

Checking the BIG-IP APM configuration

  1. Check the configuration of the virtual server, access policy, Portal Access resource, connectivity profile, and rewrite profile. If the Portal Access resource uses HTTPS, the virtual server needs a Server SSL profile. If the back-end application uses a non-standard port, include the port in the Application URI of the Portal Access resource, for example https://application.example.com:8443.

    Note: Adding a Server SSL profile should not affect other HTTP Portal Access resources. If the webtop has other resources, make this change during a scheduled maintenance window.

  2. Check name resolution and access errors:

    • If the Portal Access resource uses a fully qualified domain name (FQDN), make sure that the BIG-IP system can resolve it with the DNS servers in System > Configuration > Device > DNS. Portal Access does not use static host entries in the /etc/hosts file.

    • If the browser is redirected to /vdesk/my.acl.php3?errorcode=3016, the BIG-IP system could not resolve a host name in the request. The APM log (/var/log/apm) shows a message similar to 01490504:5: ... <host_name> can not be resolved.

    • If the browser is redirected to /vdesk/my.acl.php3?errorcode=17, an access control list (ACL) may have denied the request. Check the APM log to confirm the cause.

    • If the APM log shows Access to <resource> rejected because it points to reserved address, check whether the application links to a loopback or client-local address, for example http://127.0.0.1. If it does, add that address (for example *://127.0.0.1*) to the Bypass List of the rewrite profile, and keep a Rewrite List entry such as *://* so that other links are still rewritten. The Bypass List and Rewrite List are shown only when split tunneling is enabled. For more information, refer to K000130439.

  3. If the virtual server has a Compression profile or a Web Acceleration profile, consider removing them while you troubleshoot, to reduce complexity and unexpected results.

  4. Check that the application does not use a feature that Portal Access does not support. The Portal Access section of the BIG-IP APM Client Compatibility Matrix lists the limitations, for example:

    • The HTTP/2 protocol.

    • Identity federation (OAuth, SAML, Microsoft Entra ID) with token forwarding. A back-end SAML service provider cannot be a Portal Access resource; configure it as a pool instead.

    • JavaScript Web Workers or Service Workers. For Oracle PeopleSoft, refer to K000157040.

    If the application requires HTTP/2, publish it with Web Access Management (LTM+APM) instead of Portal Access. For more information, refer to K14079: Converting an access policy to LTM+APM mode.

Checking JavaScript rewriting

  1. In the browser developer console (F12), check for JavaScript errors when the application is accessed through Portal Access.

  2. On the BIG-IP system, check the rewrite logs (/var/log/rewrite*) for JavaScript parse errors, for example messages that include MODERN failed to parse.

  3. Check that the application's JavaScript is supported by the rewriting mode and the BIG-IP version. For more information, refer to K15142093: BIG-IP APM Portal Access - JavaScript compatibility.

  4. If the application uses ES6 or later JavaScript, make sure that it is rewritten in Modern mode. For more information, refer to K000130439.

  5. If the application is rewritten in Modern mode and still does not work, try the latest browser-side rewriter file in K000148786: Latest cache-fm-Modern.js file for Portal Access.

  6. If requests reach the virtual server without the Portal Access prefix (/f5-w-<hex>$$), refer to K13500329.

  7. If /f5-h-$$/ is added to the URL path again on each page refresh, the application may have a <base href> tag in its home page. For more information and a workaround, refer to Bug ID 1586405.

  8. If the browser console shows an error from the Portal Access rewriter file, such as Failed to read the 'localStorage' property from 'Window': The document is sandboxed and lacks the 'allow-same-origin' flag, the page is in an iframe whose sandbox attribute does not include allow-same-origin. Portal Access does not support this case (Bug ID 840257). Open a support case.

Collect HTTPWatch or HAR files for support

Before you open a support case for an application in Portal Access, collect the following data:

  1. An HTTPWatch or HAR file of the application accessed directly, without BIG-IP APM.

  2. An HTTPWatch or HAR file of the application accessed through Portal Access.

  3. The output of the browser developer console (F12).

  4. Screenshots or videos of the issue.

  5. A QKView file of the BIG-IP system.

  6. The names of the virtual server, access policy, and Portal Access resource, and a test user name and session ID.

When you record the HTTPWatch or HAR files:

  • Clear the browser cache and cookies before each recording. With HTTPWatch, select Tools > Clear Cache and All Cookies.

  • Perform the same steps in the direct recording and in the recording through Portal Access, so that the two recordings can be compared.

  • HTTPWatch: save the capture in .hwl format. You can use the free Basic edition to record and send it to F5 Support, and F5 Support can read the full file. This is the preferred method.

  • Browser developer tools: enable Preserve log (Google Chrome, Microsoft Edge) or Persist Logs (Mozilla Firefox), and save the HAR file with content.

  • Open the browser, start the recording, and then access the application. If the application opens in a new tab, make sure that the new tab is recorded, and refresh the page so that the page load is in the capture.

    Note: The first requests of a new tab may not be recorded. To record them, start an access session, open a new tab, start the recording for that tab, and enter the Portal Access URL of the application: https://<virtual_server_host_name>/f5-w-<hex_value>$$/<path>. The hexadecimal value is the encoding of the back-end scheme and host (and port, if it is not the default). For example, https://application.example.com is 68747470733a2f2f6170706c69636174696f6e2e6578616d706c652e636f6d. For more information, refer to K13500329.

A packet capture is needed only when F5 Support asks for it, for example to verify what the back-end application sends to the BIG-IP system, or what the BIG-IP system sends to the back-end server. For more information, refer to K1893: Packet trace analysis.

Open a support case and provide the data. F5 Support will ask for more information if needed.
