Resolution/Answer

Environmental or configuration issues can sometimes cause the XC to malfunction. This article outlines common XC errors and provides guidance on how to identify their root causes.

Terminology:

Terminology:DownstreamConnection from client to our Load Balancer
UpstreamConnection from Load Balancer to the origin server endpoint

  1. Always obtain an access log for the failed 5xx/4xx error and analyze the data for any potential clues.

  2. Check the rsp_code_details in your request logs for further insights.

403

csrf_origin_mismatch
If CSRF is enabled we compare the value of origin header against a list of allowed domains. If
origin is not there WAF blocks the request. Check how the POST or PUT requests are being sent.

  • Is the Origin or Referer header set? Else a CSRF violation would be set.

    • Ref: https://community.f5.com/t5/technical-articles/how-to-protect-your-applications-from-cross-site-request-forgery/ta-p/309117

403

ext_authz_denied
Blocked by Service Policy

404

route_not_found
XC does not find a route or domain that matches current config.
It is possible that there is no route match (misconfiguration).

  • SNI at Origin Server config is wrong.

  • The request fails because authority does not route match.

  • There is no match for host header. i.e www.example.com (wildcard domains are allowed)

  • There is no match condition in any of the route objects.

  • Request to a HTTP LB will be rejected (404) with a req_id if the incoming Host header:

    • Does not match any of the values configured under domains

    • Does not match the CNAME value for the virtual host (ex:ves-io-<random-string>.ac.vh.volterra.us)

  • The wildcard HTTP Load Balancer (ie: *.example.com) does not have a Simple Route for subdomain.example.com. At the same time, another HTTP Load Balancer is configured with a specific domain match for subdomain.example.com. Both load balancers are advertised on the same virtual IP address.
    • 1. Fix configuration by ensuring that subdomain.example.com is routed exclusively to the appropriate HTTP load balancer or
    • 2. By removing the conflicting wildcard/domain overlap on the shared VIP or set other VIP.

  • Healthcheck may have failed for all origin servers. If Retract Cluster is enabled (default behavior), this will remove the listener, causing HTTP requests to return 404 and HTTPS requests to fail to connect.

  • The Load Balancer configuration with multiple certificates (for *.example.com and *.myotherdomain.com) and default HTTPS Load Balancer is enabled; then XC selects the fallback TLS/virtual host based on the first configured domain. As a result, requests for that domain succeed, while requests for other domains may return 404 route_not_found . Mitigation include: 
    1. Ensure clients send the correct SNI value during the TLS handshake.
    2. Use a single multi‑SAN certificate when multiple wildcard domains are involved to support non‑SNI clients.
    3. Deploy separate HTTPS Load Balancers (VIPs) per domain to avoid fallback routing ambiguity for non-SNI clients.

Check if there is slow_ddos_mitigation with request_timeout configured.

Two options:
a. Input the Max Request Bytes limit (up to a maximum 10485760 bytes)
b. Check the box to disable the Buffer Policy

421

misdirected_request
  • Issue with Wildcard Certificates, HTTP/2, and 421 Status Code in Safari
    • When using wildcard certificates and HTTP/2, our gateway may respond with a 421 status code when proxying different sites. This occurs due to the nature of HTTP/2 request coalescing, where requests for multiple domains (e.g., authenticate.x.y.z, verify.x.y.z, httpbin.x.y.z) share the same connection. To handle this, our gateway sends a 421 response, instructing the browser to reset the connection when the domain (authority) changes.
    • However, the Safari browser does not correctly handle the 421 status code and fails silently instead of resetting the connection, causing issues with the proxy.
  • TLS Coalescing and Load Balancer Configuration
    • When configuring multiple load balancers with the same wildcard or TLS certificate for different domains (e.g., example.com in LB-1 and www.example.com in LB-2), Safari using HTTP/2 will reuse the same connection across hosts. This results in multiple requests being sent over the same TLS connection.
    • Because the HTTP/2 standard forbids renegotiation on an already established connection, this behavior makes renegotiation impossible, leading to errors in proxying different domains using the same certificate.

Resolution Options for Wildcard Certificate, HTTP/2, and 421 Status Code Issues

To resolve issues related to wildcard certificates, HTTP/2, and the 421 status code (especially in Safari), you can try one of the following solutions, with option #1 being the easiest and least disruptive:

 

1. Ensure Consistent SSL Configuration Across Load Balancers:

• If you are using the same TLS certificate across multiple load balancers (LBs) with HTTP/2, make sure that all LBs have identical SSL configurations. This includes the same protocols, ciphers, and client verification settings.

• Merge all routes into one load balancer, combining all the affected domains into a single configuration.

2. Use Separate TLS Certificates for Each Load Balancer:

• Assign different TLS certificates to each load balancer that shares the same IP address. This avoids conflicts with connection reuse.

3. Assign Unique IP Addresses for Each Load Balancer:

• If multiple LBs are using the same TLS certificate, assign a unique public IP address for each LB. This ensures that connections do not overlap and prevents renegotiation errors.

4. Alternative Browser Recommendations:

• If feasible, avoid using Safari at the customer end, as Safari does not handle 421 redirects well, unlike Chrome and Firefox.

5. Disable HTTP/2:

• Disable HTTP/2 via the XC Console. Keep in mind that while this resolves the issue, it may reduce performance due to the absence of HTTP/2 optimizations.

For TCP Load Balancers:

• Use Non-Wildcard Certificates: Create individual non-wildcard certificates for each load balancer and update their configurations accordingly.

• Advertise TCP Proxy on Different VIPs or Ports: Ensure that each load balancer is using a different virtual IP or port to avoid conflicts.

Additional Information:

When using a wildcard certificate, browsers attempt to reuse the same session via HTTP/2 coalescing, and in response, the gateway sends a 421 status code, requesting the client to reconnect with the proper SNI.

• Chrome and Firefox handle the 421 redirect correctly, resetting the connection and continuing the session as expected.

• Safari and iOS browsers struggle with this process, often failing silently and not resetting the connection properly.

503

cluster_not_found
XC did not find an endpoint to send upstream.

  • If using a k8s service as upstream, it's possible the service name is wrong.

  • Ensure the OriginPool has LB_Override set instead of a specific load balancing algorithm until the issue is resolved.

  • Try with Endpoint Selection as: Local Endpoints Preferred
  • Check if Quad-A record is returning NOERROR response and not NXDOMAIN or SERVFAIL
  • Verify the cluster status from the origin child object on each RE and confirm that the cluster is installed and passing health checks.
  • Check the log details and find whether the vh_name is empty

Verify your Origin Pool configuration and ensure you have used the appropriate settings for your pool or virtual site.

503
upstream_reset_before_response_started{connection_failure, TLS_error, OPENSSL_internal::CERTIFICATE_VERIFY_FAILED}
 
The certificate offered by the server was validated, and that validation failed.

  • In the Origin pool TLS config, skip the verification.

  • In the Origin pool TLS config, use a custom CA list.

503
upstream_reset_before_response_started{connection termination} OPENSSL_internal::CERTIFICATE_VERIFY_FAILED}
The upstream server is closing the connection. It is possible that the upstream server :

  • Is overloaded by the requests and unable to handle it. Check response time value.

  • Has a http idle timeout can be lesser than the idle-timeout on the origin-pool.

The origin-pool idle-timeout must be configured to be less than that on the server.

503
upstream_reset_before_response_started{protocol_error}
Check if the http response headers from the origin-server have any invalid field names. Query the the origin-server directly via cURL or something equivalent. Usually indicates that XC is seeing an
error in one of the http-headers of the response from the server. We would need to see the http
headers that the origin-server is responding with to identify the issue.
 
In one of the scenarios, it was seen that the origin-server may have a total of more than 100 headers
(mostly duplicate headers), which XC will treat as failure parsing the response.

503
upstream_reset_before_response_started{connection_failure, delayed_connect_error:_111}
No TCP SYN-ACKs seen for the TCP connection attempts to the endpoints.
The time_to_last_downstream_tx_byte would usually show some x seconds, and the other time_to_last_
fields would be 0 in this case.

503
upstream_reset_before_response_started{connection_termination}

This error occurs when the origin server closes the connection while the connection pool on the XC platform is still active.

1. Align Idle Timeout Settings. Ensure the connection idle timeout settings are aligned between the XC origin pool and the origin server.
Tip: Set the idle timeout on the XC origin pool a few seconds shorter than the server’s idle timeout to avoid premature connection closure.
2. Configure Retry Policy. Apply a retry policy for HTTP 5xx errors to improve resilience in case of transient server issues.
3. Further Troubleshooting. If the issue persists after applying the above changes:
• Perform a packet capture for deeper analysis.
• Verify if TLS is enabled on the origin server’s configuration.

503
upstream_reset_before_response_started{remote_refused_stream_reset}
The error message "remote_refused_stream_reset" means that the remote server (the upstream server) has refused to accept or process the HTTP/2 stream initiated by XC.
  • Common reason is related to HTTP/2’s maximum concurrent streams setting. If a single connection exceeds the SETTINGS_MAX_CONCURRENT_STREAMS value, the endpoint will reset the stream, and XC logs the error remote_refused_stream_reset.

    Ideally, the number of streams generated should not exceed the SETTINGS_INITIAL_WINDOW_SIZE value provided by the endpoint. Exceeding this limit could indicate a boundary value issue, or it may mean that the client is not properly honoring the server’s configuration.

    To verify the settings on the Origin Server, you can use a tool called nghttp to inspect the SETTINGS_MAX_CONCURRENT_STREAMS value. In case a single connection carries more streams than the settingSETTINGS_MAX_CONCURRENT_STREAMS, the endpoint will reset the stream and envoy may report 503 with remote_refused_stream_reset

503
response_payload_too_large
 
This error message could be observed on receiving a response of size greater than 64KB from the OriginServer and the OriginServer might be using HTTP1.1 alone as well as DataGuard is configured on the HTTP LB for the corresponding path.
  • Check if the Origin Server can be modified to support HTTP2
  • Add a Skip DataGuard rule to skip the req_path with could return 64Kb as the first entry.

504
stream_idle_timeout
 
The origin server took more than the idle timeout configured to respond to the request.
  • Increase the idle timeout on the HTTP LB.
  • Check how long the origin server will spend processing the request with the customer
  • Increase the timeout in the miscellaneous options of the route (default 30 seconds)

 

504
upstream_response_timeout
 
Origin server took more time than the timeout configured on the route in the load balancer.
  • Increase the timeout in the miscellaneous options of the route (default 30 seconds).
504
This response code may occur due to a TCP connection timeout to the upstream. It happens when the route timeout is set lower than the connection timeout on the upstream Origin Pool.
  • Slow responses by Region Edges (REs):

a. Check the src_site and dst_site on access logs - If they are different then check if OriginPool has LocalEndpointsPreferred set for Endpoint Selection
b. Check if duration_with_data_tx_delay is not the same as observed by the end user. If not, then "Connection Idle Timeout" may need to set in HTTPS lb types advanced option.
c. Check the five time_to_* fields in the access logs to analyze where the delay is . Those 5 values give an indication of where the delay could be

    • It is a very good practise to have the server support HTTP2 . By default, origin-pool is configured to use "Automatic" HTTP protocol negotiation(i.e use ALPN to negotiate HTTP 1.1 or HTTP/2). 
    • This not only reduces the load on the server (by reusing the same TCP(or TLS) connection, but also does the same on the RE/CE site.
    • If in the worst case scenario, there is a remote chance of a 5xx generated, but we are unable to root-cause it, if you are willing, a Retry option can be added to the route.

    • {"UpstreamConnectionFailure":"true","UpstreamOverflow":"true"} flag. This usually indicates that the limit established by the default Circuit Breaker configuration could be causing these 503 errors.

  • If you see {"UpstreamConnectionFailure":"true"} flag in req details and response_code_class: Upstream Error
