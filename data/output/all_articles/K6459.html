Topic

This article applies to BIG-IP 9.x through 11.2.1. For information about other versions, refer to the following article:

  • K14800: Order of precedence for virtual server matching (11.3.0 and later)

When determining the order of precedence applied to new inbound connections, the BIG-IP system uses an algorithm that places a higher precedence on the address netmask and a lesser emphasis on the port. The BIG-IP LTM system sets virtual server precedence according to the following criteria:

  • The first precedent of the algorithm chooses the virtual server that has the longest subnet match for the incoming connection.
  • If the number of bits in the subnet mask match, the algorithm chooses the virtual server that has a port match.
  • If no port match is found, the algorithm uses the wildcard server (if a wildcard virtual server is defined).
  • A wildcard address has a netmask length of zero; thus, it has a lower precedence than any matching virtual server with a defined address.

Note: Neither the numerical order of virtual server IP addresses nor the order in which they are listed in the configuration affect BIG-IP performance.

This algorithm results in the following order of precedence:

<address>:<port>
<address>:*
<network>:<port>
<network>:*
*:<port>
*:*

Example of VIP precedence behavior

For example, take a BIG-IP system with the following VIPs configured on the inbound VLAN:

10.0.0.0/8:80
10.10.0.0/16:80
10.10.10.10/32:80
20.0.0.0/8:*
20.0.0.0/8:80
*:80 (alternatively noted as 0.0.0.0/0:80)
*:* (alternatively noted as any:any, 0.0.0.0/0:any)

The following table illustrates how inbound destination addresses map to the configured VIPs:

Supplemental Information

  • Beginning with BIG-IP LTM 9.4.0, the bigpipe db TM.ContinueMatching variable is set to false, which negates the precedence order and causes BIG-IP LTM to reject the packet if the requested virtual server is unavailable. For more information, refer to K8009: Overview of the 'TM.ContinueMatching' db variable.
