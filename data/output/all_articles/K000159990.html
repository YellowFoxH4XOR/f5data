Description

In F5 SPK (Service Proxy for Kubernetes) environments, TMM pods may fail to start with errors similar to the following:

 

Failed to create pod sandbox: rpc error: code = Unknown desc = failed to create pod network sandbox ... error adding container to network "net0-spk-core-dns": unsupported CNI result version "1.0.0"

 

Symptoms:

 

  • TMM pods remain in a crash-loop or fail to start
  • Pod events show FailedCreatePodSandBox errors
  • NetworkAttachmentDefinition (NAD) configuration shows cniVersion: "1.0.0"
  • Manual attempts to update the NAD to cniVersion: "0.3.1" are automatically reverted to "1.0.0"
  • The issue affects all SPK-related NADs but not other network attachment definitions in the cluster

 

Environment

  • F5 SPK (Service Proxy for Kubernetes) version 1.7.14 or similar releases
  • BIG-IP Product Group
  • OpenShift Container Platform with OVN-Kubernetes CNI
  • SR-IOV Network Operator version 4.18 (upgraded from version 4.12 or earlier)
  • NetworkAttachmentDefinitions with annotations:
    • k8s.v1.cni.cncf.io/resourceName: openshift.io/internalNetPolicy
    • k8s.v1.cni.cncf.io/resourceName: openshift.io/externalNetPolicy
  • Multus CNI configuration file: /etc/kubernetes/cni/net.d/00-multus.conf`
  • SriovNetwork custom resources managing NADs

 

Cause

SR-IOV Network Operator version 4.18 automatically overwrites the cniVersion field in NetworkAttachmentDefinitions to "1.0.0" when managing SR-IOV networks. This version is incompatible with F5 SPK releases, which require cniVersion: "0.3.1" for successful TMM pod network attachment and operation.

The SR-IOV operator manages NADs through SriovNetwork custom resources, and any manual edits to the NAD are overwritten by the operator's reconciliation process, making it impossible to persist the correct CNI version while the 4.18 operator is active.

 

Answer/Recommended Actions

To resolve this issue and allow TMM pods to start successfully:

  1. Downgrade the SR-IOV Network Operator:
    • Follow your platform vendor's documented procedure to downgrade the SR-IOV Network Operator from version 4.18 to version 4.12
    • For Red Hat OpenShift, consult Red Hat documentation for the downgrade procedure
  2. Reinstall or Reapply SPK Application:
    • After downgrading the SR-IOV operator, reinstall the SPK application or reapply the TMM deployment:

    helm uninstall <release-name> -n <namespace>

    helm install <release-name> tar/f5ingress-<version>.tgz -f <values>.yaml

  3. Verify NAD Configuration:
    • Confirm that NetworkAttachmentDefinitions now show the correct CNI version:

    oc get network-attachment-definitions -n <namespace> -o yaml | grep cniVersion

    • Expected output should show: "cniVersion": "0.3.1"
  4. Verify SriovNetwork Resources:
    • Check that SriovNetwork custom resources are properly configured:

    oc get sriovnetwork -A

    oc get sriovnetwork -n openshift-sriov-network-operator <name> -o yaml

  5. Restart TMM Pods:
    • Delete existing TMM pods to allow recreation with correct network configuration:

    oc delete pod -n <spk-namespace> -l app=f5-tmm

  6. Monitor Pod Startup:
    • Verify TMM pods start successfully and attach to the network:

    oc get pods -n <spk-namespace>

    oc describe pod -n <spk-namespace> <tmm-pod-name>

Important: Do not attempt to manually edit the NAD or SriovNetwork resources to change the CNI version while SR-IOV Operator 4.18 is installed, as changes will be automatically reverted.

Note: Ensure the Multus CNI configuration on worker nodes shows "cniVersion": "0.3.1" by checking: cat /etc/kubernetes/cni/net.d/00-multus.conf`

Additional Information

 

Compatibility Information:

 

  • Current SPK releases (including 1.7.14) require CNI version 0.3.1 for successful operation
  • SR-IOV Network Operator version 4.12 is compatible with SPK and uses CNI version 0.3.1
  • SR-IOV Network Operator version 4.18 enforces CNI version 1.0.0, which is incompatible with current SPK releases

 

Future Support:

 

  • F5 Engineering is working on compatibility with SR-IOV Operator 4.18+ in future SPK releases
  • A bug has been filed to track this incompatibility
  • F5 documentation will be updated to include:
    • Warning that SR-IOV Operator 4.18+ is not compatible with current SPK releases
    • Specification that CNI version 0.3.1 is required for successful TMM pod operation
    • Updated compatibility matrix showing supported SR-IOV operator versions

 

Verification Steps:

To confirm your environment is affected by this issue, check:

 

  1. SR-IOV operator version: oc get csv -n openshift-sriov-network-operator
  2. NAD CNI version: oc get net-attach-def -A -o yaml | grep cniVersion
  3. TMM pod events: oc describe pod -n <namespace> <tmm-pod-name>
