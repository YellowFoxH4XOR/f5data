K000163368: CDN Proxy Integration with BIG-IP LTM: Client IP, Session Affinity, and Geolocation

Applies to

Description

A CDN proxy in front of a BIG-IP LTM virtual server can replace the original client source IP with a proxy address and provide the original address in an HTTP header. This may cause repeated HTTP 302 redirects, missing CSS, JavaScript, and icon resources, unexpected application logouts, inconsistent pool-member selection, and incorrect geolocation or WAF decisions. 

Environment

  • BIG-IP LTM virtual server.
  • High-availability portal with two application servers.
  • Round-robin load balancing.
  • Traffic flow: client → CDN proxy → BIG-IP virtual server → Application-server pool.
  • The proxy may:
    • Replace the original client source IP at Layer 3.
    • Provide the original client IP in CF-Connecting-IP, True-Client-IP, or another configured header.
    • Reuse a TCP connection for requests from different clients.
  • BIG-IP features associated with the virtual server may include:
    • HTTP profile.
    • ASM/AWAF security policy.
    • Application DoS profile.
    • Bot Defense profile.
    • Persistence profile.
    • Geolocation enforcement.

Cause

Proxy source-IP translation and TCP connection reuse can prevent BIG-IP from consistently applying the original client identity for persistence and security processing. If BIG-IP receives only proxy source addresses, Source Address persistence cannot provide per-client affinity. If requests from different clients share a TCP connection, BIG-IP may make the load-balancing decision when the connection is established, and subsequent persistence information may not be evaluated as expected. 

Answer/Recommended Actions

1) Confirm the client-IP header:

Confirm the following with the CDN provider:

  • Whether source-IP translation occurs before connecting to BIG-IP.
  • Which HTTP header contains the original client IP.
  • Whether the header is CF-Connecting-IP, True-Client-IP, or another header.
  • Whether TCP connections are reused for requests from different clients.

Do not configure BIG-IP to trust a header until its name, format, and source are confirmed.

2) Configure the BIG-IP HTTP profile:

On the HTTP profile associated with the virtual server:

  • Enable Accept XFF.
  • Configure the verified client-IP header when it is not the default X-Forwarded-For header.
  • Ensure the header is accepted only from the intended trusted proxy path.

3) Configure ASM/AWAF geolocation processing:

For the ASM/AWAF security policy associated with the virtual server:

  • Enable Trust XFF Header.
  • Configure the same verified client-IP header used by the proxy.
  • Confirm that geolocation decisions use the intended client-IP information.

4) Configure Application DoS and Bot Defense client-IP processing:

Application DoS and Bot Defense profiles use the HTTP profile’s Accept XFF configuration for client-IP identification. They do not use the ASM policy’s Trust XFF Header setting for this purpose.

Verify the HTTP profile configuration when Application DoS or Bot Defense is enabled.

5) Review session-affinity design:

Source Address persistence uses the Layer 3 source IP address received by BIG-IP. It cannot use the original client IP when BIG-IP receives only proxy source addresses.

If the original client IP is available only in an HTTP header:

  • Use a carefully validated universal-persistence design that extracts the verified client-IP header.
  • Use the extracted client IP as the persistence key.
  • Validate the behavior with one application server enabled and then with both servers enabled.
  • Confirm that requests from the same client consistently use the expected persistence key and pool member.

Custom iRules and universal persistence require design and implementation validation. Professional Services may be required for this activity. You may contact with your F5 Account Team.

6) Review connection handling:

If the proxy sends requests from different clients over the same TCP connection, review BIG-IP connection and persistence behavior. Evaluate OneConnect or an appropriate iRule-based design according to the application requirements.

7) Validate the complete path:

Compare CDN, BIG-IP, and application logs or HTTP traces to verify:

  • The expected client-IP header is present.
  • The header contains the correct original client address.
  • BIG-IP trusts the header only from the intended proxy.
  • The persistence key remains consistent for the same client.
  • Requests are sent to the expected application server.
  • HTTP 302 redirects do not repeat unexpectedly.
  • CSS, JavaScript, and icon resources load successfully.
  • Application sessions remain active.
  • Geolocation decisions use the intended client address.

8) Validate geolocation data:

BIG-IP does not automatically use a CDN country header for its own geolocation decisions. BIG-IP must first identify the original client IP from a trusted HTTP header and then map that address to a country using its local geolocation database.

Ensure that the Geolocation database is current. In an HA deployment, update each BIG-IP system because geolocation database updates are not synchronized through the Configuration utility. 

Additional Information

  • The client-IP header and country header serve different purposes. Configuring a country header alone does not cause BIG-IP to use the original client IP for geolocation.
  • Enabling Accept XFF in the HTTP profile is important for client-IP processing by features that rely on the HTTP profile, including Application DoS and Bot Defense.
  • Enabling Trust XFF Header in the ASM security policy is relevant to ASM/AWAF processing, including geolocation enforcement.
  • A custom iRule that copies CF-Connecting-IP or True-Client-IP into X-Forwarded-For does not by itself prove that persistence, ASM, Bot Defense, Application DoS, and application-session behavior are correctly implemented.
  • A fix is available for the documented connection and persistence behavior. Complete design, implementation, and validation assistance may require Professional Services.
