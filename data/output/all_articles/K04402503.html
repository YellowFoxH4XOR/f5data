Topic

You should consider using this procedure under the following conditions:

  • You license and provision BIG-IP APM on the BIG-IP system.
  • You configure BIG-IP APM to allow mobile users to connect to your resources.
  • Mobile Android users do not authenticate successfully to the BIG-IP APM system after initial setup.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have administrative access to the BIG-IP APM Configuration utility and command line.
  • You have access to the Android client device.

Procedures

This article provides data gathering tools to identify potential issues when connecting to the BIG-IP APM system using the F5 Access for Android. To gather the diagnostic data from the BIG-IP APM system and the Android client, perform the following procedures:

Note: Before attempting to reproduce the issue, close all existing connections from the Android client to BIG-IP APM, including any clientless connections, such as Outlook Anywhere, Autodiscover, and Outlook Web Access (OWA).

  • Enabling and disabling access policy debug logging
  • Generating packet captures and session ID on the BIG-IP APM system
  • Decrypting packet captures
  • Gathering F5 Access logs from the Android device
  • Gathering F5 Access logs from iOS device
  • Gathering the diagnostic data

Enabling and disabling access policy debug logging

Impact of procedure: Setting the log level to Debug increases the log level for access policy logging. You should only perform this procedure when troubleshooting.

  1. Log in to the BIG-IP Configuration utility.
  2. Navigate to System > Logs > Configuration > Options > Access Policy.
  3. Under Access Policy Logging, for Access Policy, click Debug to enable debug level logging or Notice to select the default logging level. You should disable debug level logging once troubleshooting is complete.
  4. Click Update. 

Generating packet captures and session ID on the BIG-IP APM system

Impact of procedure: Performing the following procedure should not have a negative impact on the system.

  1. Log in to the BIG-IP command line.
  2. To capture traffic between the Android Client and virtual server, specify the 0.0 interface using the following syntax:

    If your BIG-IP is v15.0.0 and later:
    tmsh modify sys db tcpdump.sslprovider value enable
    tcpdump -s0 -ni 0.0:nnnp -w /var/tmp/"$HOSTNAME"_"$(date +%d-%m-%y)".pcap --f5 ssl -vv host <client_public_IP>
    NOTE: The client_public_IP is IP seen by the BIG-IP when establishing session)

    If your BIG-IP is older than v15.0.0:
    tcpdump -ni 0.0:nnn -s0 host <android_client_IP> -w /path/to/capture_file

    For example, if the Android's IP address is 206.20.80.107 and you want to send the output to the /var/tmp/AndroidClient.pcap file, type the following command:

    tcpdump -ni 0.0:nnn -s0 host 206.20.80.107 -w /var/tmp/AndroidClient.pcap

  3. Log in to the client system and reproduce the issue by attempting to access the virtual server from the Android device. 
  4. .Connect from the client device and take note of the APM session ID associated with the failed attempt and find the Session ID:
       Navigate to: Access → Overview → Access Reports. (you can find it by client IP)
  5. Close all browsers first to prevent capturing resumed SSL sessions.
  6. Once you have reproduced the issue, stop the tcpdump command by typing Ctrl+C at the BIG-IP command line. The tcpdump command output will be sent to the /var/tmp/<filename>.pcap file. 

 

Decrypting packet captures

If your BIGIP is v15.0.0 or later, follow:

K31793632: Creating a decrypted tcpdump capture without using an iRule

If youre BIGIP is older than v15.0.0 follow:
Note: You should store private SSL keys securely. Do not gather private keys when collecting diagnostic data for troubleshooting.

Impact of procedure: Performing the following procedure should not have a negative impact on the system.

    1. Log in to the BIG-IP APM Configuration utility.
    2. Navigate to Local Traffic > Virtual Servers > Virtual Server List and click the virtual server.
    3. Identify the Client SSL profile in use. Navigate to Local Traffic > Profiles > SSL > Client and click that profile.
    4. Note the value for the Key setting in the profile. You will match this to the respective key file in the next steps.
    5. Log in to the BIG-IP command line and navigate to the /config/filestore/files_d/Common_d/certificate_key_d/ directory by typing the following command:

      cd /config/filestore/files_d/Common_d/certificate_key_d/

    6. Make note of the key file name associated with the value for the Key setting from the previous step. For this example, assume the key file name is test.org.key_1.
    7. Decrypt the tcpdump capture file using the following syntax:

      ssldump -AdenN -r /path/to/tcpdump_catpure_file -k /path/to/private_key > /path/to/output_file

      For example

      ssldump -AdenN -r /var/tmp/AndroidClient.pcap -k /config/filestore/files_d/Common_d/certificate_key_d/\:Common\:www.site.com.key_1 > /var/tmp/AndroidClient.txt

    8. The resulting AndroidClient.txt file will contain the decrypted traffic that you can analyze to determine the cause of the issue.

 

Gathering F5 Access logs from the Android device

Impact of procedure: Performing the following procedure should not negatively affect the Android client device.

  1. Log in to the Android client device.
  2. Open the F5 Access application.
  3. Select Diagnostics in the drop-down menu.
  4. Select the bug icon in the banner to begin the data collection process. The resulting logs are placed in the EdgeClientLog.zip file, which you can then transfer using one of the available options on the Android device.

 

Gathering F5 Access logs from the iOS device
        Follow K29591125: Collecting diagnostic data when using F5 Access for iOS

 

Gathering the diagnostic data

Impact of procedure: Performing the following procedure should not have a negative impact on the system.

Once you are able to reproduce the issue and generate packet captures, you can gather the diagnostic data in one place for future analysis. To do so, perform the following procedure:

  1. Log in to the BIG-IP command line.
  2. Create a new directory for the diagnostic files and change to the new directory by typing the following command:

    mkdir /var/tmp/diag_files

  3. Copy the packet capture files to the new directory by typing the following command:

    cp /var/tmp/AndroidClient.pcap  /var/tmp/AndroidClient.txt /var/tmp/diag_files/

  4. Generate a tarball of the log files by typing the following command:

    Note: This command will create a file named logfiles.tar.gz and place it in the newly created directory.

    tar -czvf /var/tmp/diag_files/logfiles.tar.gz /var/log/*

  5. Generate a tech.out diagnostic file by typing qkview at the command line. Output is placed in the /var/tmp/ directory. Move it to the newly created directory using the following syntax:

    mv /var/tmp/<hostname>.qkview /var/tmp/diag_files

    For example:

    mv /var/tmp/bigip.example.com.qkview /var/tmp/diag_files
