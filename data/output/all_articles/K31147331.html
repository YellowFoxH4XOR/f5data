Description

You can configure a BIG-IP system with nodes and pool members that are identified with fully-qualified domain names (FQDNs). When you configure pool members with FQDN, addresses will dynamically follow DNS changes. Fully dynamic DNS-managed pools may even be created

This article discusses the behavior of the DNS component ( resolver) of the FQDN monitor whenever the configured DNS server/s is not available and is NOT replying with ICMP dest port unreachable

Environment
  • FQDN Nodes

Cause

This behavior is by design.

Recommended Actions

None

    Additional Information

    When LTM is configured to use the FQDN nodes/pool members it needs to resolve the FQDN of the node to IP Address.

    This is done by sending a DNS query to the DNS configured sys dns server.

    For example:

    sys dns {
        name-servers { 1.1.1.1 2.2.2.2 }
    }

    The LTM will send a DNS query containing the FQDN name of the node, and record the response with the resolved IP address.

    Under certain conditions, the response might not arrive to LTM, forcing it to retransmit the request.

    Condition 1: Server responds with ICMP unreachable

    When the DNS server is alive and reachable, but the DNS service is not running, LTM will receive ICMP message with Destination port unreachable.

    Upon receiving the message LTM will try resolving the FQDN on the next DNS server configured in the “sys dns” section ( 2.2.2.2) in our example .

    Before moving to the next DNS server, LTM will wait 5 seconds. That is the timeout when moving from one DNS server in the list to another.

    Condition 2: Server is down /does not exist / ICMP message are drop by device in the middle

    When a DNS server is down and not responding with ICMP unreachable and/or the ICMP messages being dropped on the network before reaching LTM, the LTM will first try retransmitting the DNS query to the same server, and only after (Timeout * Retires) time it will try sending the query to the next DNS server on the list ( configured in sys dns)

    The retransmit delay period is 5 seconds and number of retries is 3 are coming from the system resolver library.

    The retransmit delay is how long the lower-level code waits for a response from the DNS server before timing out and retrying.

    These values are not user-visible or configurable.

    Effectively, these values are fixed at 5 seconds and 3 retries.

    The number of retries determines how many additional queries (with retransmit delays) the lower-level code issues before moving to the next DNS server in the resolver list.

    The Resolver will move to the next server after (3+1) * 5 seconds.

    When LTM has reached the (3+1)*5 seconds, for the last Resolver in sys dns list, it will wait additional 5 seconds and then start over from the top of the list in sys dns.
