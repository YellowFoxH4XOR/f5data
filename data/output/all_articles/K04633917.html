K04633917: How does pmtud and cmetrics timeout work, why aren't entries deleted after 600 seconds ?

Description

The basics of path mtu discovery (pmtud) are that devices (normally on different subnets) will send packets up to the size specified in the mss tcp option of the 3whs. Most packets with a tcp payload are sent with the df (don't fragment) bit set. If an intervening device receives a packet on an ingress interface that is too large to fit on the egress interface and the df bit is set, then it will send an icmp unreachable back to the sender indicating that fragmentation is required and that the df is set. It will inform the sender of the new maximum mss for that connection. The sender will segment (not fragment) and resend the "too big" payload into two or more smaller packets (still with the df bit set).

BIG-IP with a standard VS will sit as full proxy between client and server. If it see's a icmp unreachable fragmentation required but df bit set, then it will cache that entry, noting the IP address and mss. It will then use that entry to reduce the packet size accordingly on packets sent to the IP specified as the source of the icmp unreachable. BIG-IP shows the entry in the cmetrics table.

Here is a typical cmetrics entry. You can see the IP address of the device and the MSS (MTU) advertised by the intervening device (the one sending the icmp unreachable).

Output is from the command "tmsh show net cmetrics"

Net::RouteMetric
Destination IP   HWaddress         TMM  rtt       rttvar    ssthresh  bandwidth  MTU
172.18.128.11    b4:c:25:e0:40:10  0    487763    535156    0         996        577

The default timeout for the cmetrics entry is 600s (10 minutes). There is a sys db to control this, others to control the use of cmetrics cache and maximum number of cacheable entries.

[root@LTM1.example.com:/S1-green-P::Active:In Sync] config # tmsh list sys db route.metrics*
sys db route.metrics.maxentries {
    value "0"
}
sys db route.metrics.mtu {
    value "enable"
}
sys db route.metrics.timeout {
    value "600"
}

The cmetrics timeout is effective and will remove the entry from the table 600 seconds after creation so long as the entry is not refreshed.

A cmetrics entry will be refreshed either of the following from a single connection:-
- With Timestamps enabled, 4 TCP payloads and 4 ACKs are needed.
- With Timestamps disabled, 4 ACKs from different round-trips are needed.

So, if during the 600s after the cmetrics entry was either created or refreshed, a single tcp connection sending 4 payloads with ack will refresh the timeout back to 600s.
This is working as designed.

However, if you are not aware of the refresh process, it can give the impression that the entry is never deleted.

Cause

Recommended Actions

There are a couple of options to work around the issue:-

1: If the cmetrics entry is caused by a network error, then you can manually delete the entry via "tmsh delete net cmetrics" once the issue causing the smaller mss has been resolved.

2: Use crontab to periodically delete cmetrics entries.

The following should delete any cmetrics entries < 1460 bytes every 10 minutes. This would be reguardless of how long the entry had been present. However, if a client generates the cmetrics entry on every connection, then it will behave as expected.

10 * * * * for i in `tmsh show net cmetrics | grep  -v ' 0$' | grep -v 'MTU$' | grep '^[1-9]' | awk '{if ($8<1460) print $1;}'`; do echo `date` :: "tmsh delete net cmetrics dest-addr $i" >> /var/log/mtu.log; tmsh delete net cmetrics dest-addr $i; done

You might want to adjust either the size or frequency of the deletion.

3: The following irule will do the same. The difference between this option and #2 above is that the first deletion of the cmetrics entry will occur 10 minutes after the first creation of the entry.

when CLIENT_CLOSED {
  set client [IP::client_addr]
  set port [TCP::client_port]
  if { [TCP::mss] <= 536 } {
    log local0. "Small TCP mss: [TCP::mss]. Client: $client Port $port lifetime: [table lifetime -remaining smtu_$client]"
# If permanent table entry doesn't exist, create permanent and temporary entries
    if { [table lookup -notouch perm_$client] == "" } {
      table set perm_$client 1 indefinite indefinite
      table set smtu_$client 1 600 600
    }
  }
# If permanent entry exist but temporary has timed out, then delete permanent entry and clear cmetrics
  if {[table lookup -notouch perm_$client] == 1 && [table lookup -notouch smtu_$client] == "" } {
    log local0. "Deleting MTU entry for $client:$port"
# Note that the command "[TCP::rt_metrics_timeout 1]" throws an error (hence the "catch")
# Note that the command "[TCP::rt_metrics_timeout 0]" doesn't actually do anything
    catch { [TCP::rt_metrics_timeout 1] }
    table delete perm_$client
  }
}

Note that this effectively ensures that a cmetrics entry for mss < 536 bytes will be deleted after 10 minutes and might need to be adjusted depending on requirements.
