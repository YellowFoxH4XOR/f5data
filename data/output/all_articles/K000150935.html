Description

On F5OS systems, the BIG-IP tenant deployment may fail with the error:

Not ready: containers with unready status: [compute]

This is often due to an expired Kubernetes (K3s) service account token used by the Multus CNI plugin, as described in F5 Bug ID1694481. To avoid this issue, it is recommended to proactively check the expiry date of the token before redeploying the tenant.

Environment

  • F5OS-A
  • Tenant deployment
  • Service Account Token
  • Multus Token

Cause

When a tenant is transitioned from "Deployed" to "Configured" and then redeployed, the Multus CNI plugin may use an expired service account token, causing the compute container to fail to start. This results in the tenant being stuck in a "Provisioned" or "Unavailable" state.

Recommended Actions

To avoid tenant deployment issues, verify the expiry date of the Multus service account token before redeploying

Step 1: Find the Pod Name for Multus

  1. Use the following command to find the Multus pod name:

kubectl get pods --all-namespaces | grep multus

  1. Identify the pod name from the output. For example, you might see:

kube-system   kube-multus-ds-amd64-5qvjj   1/1     Running   17      12

The pod name in this example is kube-multus-ds-amd64-5qvjj.

Step 2: Access the Multus Pod

  1. Use the following command to enter the Multus pod. Replace the pod name with the one found in Step 1:   

kubectl exec -it kube-multus-ds-amd64-5qvjj -n kube-system bash

  1.   Verify that you've successfully entered the pod. Your command prompt should now reflect the shell inside the pod.

Step 3: Check the Service Account Token and Multus Token

  1. Run the following command to check the service account token inside the pod:

cat /var/run/secrets/kubernetes.io/serviceaccount/token

  1. Run the following command to check the Multus token:

cat /host/etc/cni/net.d/multus.d/multus.kubeconfig

Copy the tokens displayed for reference.

  1. Compare both tokens:

  • If the service account token and the Multus token are the same, no further action is required.
  • If they are different, proceed to Step 4 to check the expiry date of the Multus token.

Step 4: Decode the Multus Token (On Linux-System Bash, Not Pod Bash)

  1. Exit the pod by typing:

exit

  1. On the Linux-system bash, locate the payload part of the Multus token. A token typically consists of three parts, separated by dots (.):<Header.Payload.Signature>

  2. The payload is the middle section of the token.

  3. Use the following command to decode the payload on the Linux-system bash:

echo '<token_Payload>' | base64 -d | jq

Replace <token_Payload> with the actual payload part of the Multus token.

Step 5: Decode the "exp" Field

  1. Locate the "exp" field in the decoded payload. For example:

<"exp": 1774368207>

  1. Convert the exp timestamp into a human-readable date using the following command:

date -d @1774368207

  1. The output will give you the expiry date. For example:

Fri Oct 16 13:10:07 UTC 2026

Step 6: Handling Expired or Near-Expiry Dates

  1. If the token is expired or approaching the expiry date, you can resolve the issue by restarting the Multus pod. Use the following command to delete the Multus pod:

kubectl delete pod <multus-pod-name> -n kube-system

Replace <multus-pod-name> with the actual name of the Multus pod (e.g., kube-multus-ds-amd64-5qvjj).

  1. When you delete the Multus pod, Kubernetes will automatically recreate it, and the system will generate a new token. 

  2. After the pod is recreated, repeat Steps 1–5 to confirm the new token and its expiry date.
