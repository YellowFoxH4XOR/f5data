K000160026: LACP Interface Stuck in LACP_DOWN/OUT_OF_SYNC State After F5OS-C Upgrade on VELOS CX410 after upgrade from 1.8.0 to 1.8.2

Type
Support Solution
Published
2026-02-16
Updated
2026-08-17
Applies to
  • F5OS Products
  • F5OS-C: 1.8.2
Source
https://my.f5.com/manage/s/article/K000160026

Description

  • After upgrading F5OS-C software on a VELOS CX410 chassis from version 1.8.0 to 1.8.2, an interface may remain in a LACP_DOWN and OUT_OF_SYNC state, resulting in traffic loss for tenants on the affected blade. The issue is characterized by:
  • Interface stuck in LACP_DOWN, OUT_OF_SYNC state post-upgrade
  • LACP partner system showing as null/defaulted in packet captures
  • Interface bounce (administratively disabling/enabling) does not resolve the issue
  • Interface recovers only after rebooting the affected blade
  • ATSE register values showing 0xebade001 in diagnostic register dumps (reg_dump files)
  • Log messages such as:

    cdb_set_values failed for interface INTERFACE="X/X.0" ERRNOSTR="locked" LASTERR="Could not acquire lock"

Environment

  • F5OS-C version 1.8.2 (upgraded from 1.8.0)
  • VELOS CX410 chassis (F5-VEL-CX410-AC, F101 platform)
  • BX110 blade
  • LACP bundle configured across multiple blades
  • One or more front panel interfaces disabled (not in use)
  • Recent upgrade action performed

Cause

Bug ID 2152957

Answer/Recommended Actions

Upgrade to a fixed version. F5 introduced a fix for this issue in F5OS-C 1.8.2-HR1 and F5OS 2.0.0. Alternatively, perform the following workaround.

Workaround:

  1. Enable all front panel ports on the affected blade, including those not currently in use:

    interfaces interface <interface_name>

    config enabled

  2. Verify there are no port mode mismatches by ensuring installed optics match the configured port speeds in the portgroup configuration.
  3. Monitor interface status after enabling all ports. If the LACP interface recovers and joins the bundle successfully, the workaround is effective.
  4. If the issue persists or recurs, reboot the affected blade as a temporary recovery measure:
    • Identify the affected blade from logs or interface status
    • Reboot the blade (note: this will disrupt tenant traffic on that blade)
    • Verify interface status after blade reboot
