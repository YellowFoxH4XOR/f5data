Topic

The Secure Vault feature provides an additional layer of security to the BIG-IP system by encrypting passwords and passphrases, which the system stores in its configuration files. This article discusses how the Secure Vault feature works and demonstrates some of the necessary Secure Vault management commands.

For information on how F5OS systems use a primary key to encrypt highly sensitive passwords/passphrases, refer to

  • VELOS: Securing / Hardening F5OS on VELOS.
  • rSeries: Securing / Hardening F5OS on rSeries

Description

The BIG-IP system configuration may contain objects that require a password or passphrase. For example, a password or passphrase may protect an imported SSL key, or a health monitor may be configured to authenticate a remote service using a password or passphrase. BIG-IP system configuration files end with the .conf file extension and the system stores them in its /config directory. The BIG-IP system secures access to configuration files through user authentication, and the Secure Vault feature provides an additional layer of security by encrypting passwords and passphrases contained in BIG-IP system configuration files.

Passwords and passphrases that Secure Vault encrypts appear in the BIG-IP system configuration files and begin with a $M$ prefix. For example:

passphrase $M$g2$UEOTKSvSN/7kasHTLIBsEw==
password $M$Sx$z5wBus7I+VhvLCndYNz+Mg==

The following sections offer additional details about the BIG-IP system's Secure Vault feature:

  • Unit and master keys
  • High availability (HA)
  • Event logging
  • Resetting the master key

Unit and master keys

The Secure Vault feature provides security through the use of two cryptographic keys: the unit key and the master key. The BIG-IP system securely stores the unit key in the system EEPROM hardware and uses it to encrypt and decrypt the master key. The BIG-IP system stores the master key in its file system and the mcpd process uses it to encrypt and decrypt passwords and passphrases when loading BIG-IP system configuration files. The following table shows the important properties for each key type.

Unit keyMaster key
Performs master key encryption and decryptionPerforms password and passphrase encryption and decryption
Is unique to each BIG-IP systemIs shared between all high-availability (HA) BIG-IP systems configured in a Device Service Cluster (DSC)1
Is a symmetric AES256 keyIs a symmetric AES128 key
Is stored in EEPROM2Is stored in the master file in /config/bigip/kstore on the BIG-IP file system

1BIG-IP DNS (formerly known as BIG-IP GTM) systems are not inherently configured in a DSC. To synchronize the master key with BIG-IP DNS systems, you can use the gtm_add utility or follow the guidance in Resetting the master key.

2If no EEPROM is available, for example in the case of BIG-IP Virtual Edition (VE), the system stores the unit key as a hidden file named .unitkey in the /config/bigip/kstore file. The system generates and stores Virtual Clustered Multiprocessing (vCMP) guest unit keys on the vCMP host, and the host unit key, stored in hardware, protects the host master key.

When the BIG-IP system starts, the mcpd process reads and validates configuration files prior to loading them into running memory and performs the following decryption tasks:

  1. Retrieves the unit key from (S)EEPROM.
  2. Decrypts the master key using the unit key.
  3. Decrypts all passwords and passphrases in system configuration files.
  4. Passes decrypted passwords and passphrases to system processes such as the Traffic Management Microkernel (TMM) or the bigd monitor process.

High availability (HA)

When your BIG-IP systems are in an HA configuration, all of the HA peer systems must have the same master key. To ensure all HA peers have the same master key, the DSC architecture acts in the following ways:

  • When an HA peer BIG-IP system modifies the master key, the updated master key synchronizes to all HA peer systems in the trust domain.
  • When a new BIG-IP system joins the local trust domain, the system receives a copy of the current master key, which HA peer systems use in the trust domain.
  • For most shared objects, the unit that pushes the initial configuration is the one that controls the shared objects.  It's the same here, but in this case the "push" is cryptographic data to allow communication over the device trust.
  • Encrypted passwords and passphrases may appear differently when comparing the configuration files from different HA peer systems. Each HA peer's instance of the mcpd process uses a different salt, or random data, to encrypt and decrypt passwords and passphrases. This does not affect configuration synchronization (ConfigSync) in any way.

Event logging

The Secure Vault feature logs information to the /var/log/secure file. You can enable debug logging by typing the following TMOS Shell (tmsh) command:

tmsh modify sys syslog auth-priv-from debug

To return Secure Vault logging to the default setting, enter the following command:

tmsh modify sys syslog auth-priv-from notice

Recommendations

  • For vCMP systems: whenever you reset the master key on a vCMP host, you must reboot the host and guest systems immediately afterwards and then reset the master key for each vCMP guest. Otherwise, the host loses each guest's unit key and causes an issue with each guest's master key. Resetting the master key on a vCMP guest or vCMP guests configured in a HA device group is the same as non-vCMP standalone or HA systems.
  • When you initially set up a new BIG-IP system, choose a secure password or passphrase and reset the BIG-IP system master key. You can then subsequently use the password or passphrase each time you want to generate the same master key. Having control over the master key in this way allows you to restore user configuration set (UCS) files on different BIG-IP hardware platforms. For example, you may need to do this when you migrate multiple BIG-IP platforms or replace BIG-IP systems that are not part of an HA configuration. For more information, refer to K9420: Installing UCS files containing encrypted passwords or passphrases.
  • You can reset the BIG-IP system's master key using tmsh and a strong password or passphrase. When resetting the master key, the Secure Vault feature prompts you for a password or passphrase. Choose a strong password or passphrase and store it in a secure location for future use. Review the following list of recommended criteria that a strong password or passphrase should contain:
    • 10 or more characters for BIG-IP, 16 or more characters for BIG-IQ
    • One or more capital letters
    • One or more lowercase letters
    • One or more numbers
    • One or more special, non-null characters
  • Encrypted passwords or passphrases can only be decrypted by the same master key that encrypted them. The Secure Vault feature always generates the same master key when using the same secure password or passphrase to reset the master key. This can be helpful when restoring a UCS file containing encrypted passwords and passphrases on a BIG-IP system with a different master key.  Especially for RMA of standalone devices, F5 recommends setting the device master key during initial configuration in order to use a known master key in case a UCS restore is necessary. Whenever possible, you should use the documented tmsh commands for master and unit key manipulation. Only use the f5mku command with assistance from F5 Support when no tmsh commands exist to perform the task you want.

Resetting the master key

To reset the Secure Vault's master key, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to tmsh by entering the following command:

    tmsh

  2. To view the BIG-IP system's current master key, enter the following command:

    show sys crypto master-key

    The command output appears similar to the following:

    ------------------------------------------------------------------------------------------------------------
    Sys::Master-Key
    ------------------------------------------------------------------------------------------------------------
    master-key hash <peG9W+X/fittfJA65hlDGpiGbYOp+GlvnOmHE0puZEbKY107MVZpaBKwbOOO+8BItsk99BXUXNN/anDSTZnTbA==>
    previous hash <>

  3. To reset the BIG-IP system's current master key, enter the following command:

    Important: If your configuration contains DNSSEC keys and you are running a version prior to BIG-IP 16.0, do not use tmsh modify sys crypto master-key. Instead use the workaround provided in ID 639606.

    modify sys crypto master-key prompt-for-password

    The command twice prompts you to enter the password:

    enter password:

  4. To save the re-encrypted configuration objects in memory to disk, enter the following command:

    save sys config

  5. If the BIG-IP system is in an HA configuration, you can run ConfigSync by using the following command syntax:

    run cm config-sync to-group <name>

    For example, to synchronize the device group named example_dg, enter the following command:

    run cm config-sync to-group example_dg

  6. To view the BIG-IP system's new master key, enter the following command:

    show sys crypto master-key

    The command output appears similar to the following:

    -----------------------------------------------------------------------------------------------------------
    Sys::Master-Key
    -----------------------------------------------------------------------------------------------------------
    master-key hash <4X2mgPNwBG2EJv7Sm4QA9SyXTXehiaSgUzIYuG8+WhrgsOTRf8RlWyEUuXFaqfvxs5uib5UzXrLwxfAr/3KExg==>
    previous hash <peG9W+X/fittfJA65hlDGpiGbYOp+GlvnOmHE0puZEbKY107MVZpaBKwbOOO+8BItsk99BXUXNN/anDSTZnTbA==>

Backing up the BIG-IP configuration

Make sure that you regularly back up the BIG-IP system configuration and maintain the backup UCS files in a secure manner. For more information about creating and restoring UCS files, refer to K13132: Backing up and restoring BIG-IP configuration files with a UCS archive.
