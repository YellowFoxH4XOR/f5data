Topic

This article applies to BIG-IP 9.x through 15.0.x. For information about other versions, refer to the following article:

  • K56163641: BIG-IP DNS HTTP health monitor behavior when processing a server response (15.1.x - 16.x)

You can use the BIG-IP DNS (formerly BIG-IP GTM) HTTP and HTTPS health monitors to verify the health of the server by checking whether the expected response is returned after a specific request. The following information provides insight into how the BIG-IP DNS HTTP and HTTPS health monitors behave upon receiving different responses from a server.

Description

By default, the BIG-IP DNS system uses HTTP version 0.9 when sending monitor requests, unless the HTTP version-specific information is configured in the Send String. When the BIG-IP DNS system is configured to send HTTP version 0.9 monitor requests, the BIG-IP DNS system marks the server up as long as the server returns a response.

When the BIG-IP DNS HTTP health monitor is configured to send either HTTP version 1.0 or 1.1 in its Send String, the BIG-IP DNS system expects an HTTP 200 OK response status from the server before proceeding to search for the Receive String in the server response payload, if configured. When the Receive String is successfully found in the server response payload, the BIG-IP DNS system marks the server as up. This behavior is by design.

When the response from the server is not HTTP 200 OK, the BIG-IP DNS system marks the server as down, regardless of whether the Receive String is found in the server response and reports the response status in the /var/log/gtm file. The purpose of the behavior is to ensure that the response received is the correct HTTP resource requested by the HTTP health monitor. For example, assume that the BIG-IP DNS system is configured to send the following monitor request with a Receive String of iamalive:

GET /index.html HTTP/1.1\r\nHost: host.domain.com\r\nConnection: Close\r\n

  • The BIG-IP DNS system marks the server as up if the server returns the following response:

    HTTP/1.1 200 OK
    Content-Type: text/html

    <HTML>
    <BODY>iamalive</BODY>
    </HTML>

  • The BIG-IP DNS system logs a message that appears similar to the following example to the /var/log/gtm file:

    011ae0f2:1: Monitor instance /Common/gtm-test-monitor 10.100.1.101:80 DOWN --> UP from 10.100.1.100 (connect: success search result true)

     
  • The BIG-IP DNS system marks the server as down if the server returns the following response status:

    HTTP/1.1 302 Moved Temporarily
    Location: http://www.yoursite.com/new/location.html
     

  • The BIG-IP DNS system logs a message that appears similar to the following example into the /var/log/gtm file:

    011a4003:1: SNMP_TRAP: Pool /Common/default.http member /Common/gtm_vip (ip:port=10.100.1.101:80) state change green --> red ( Monitor /Common/gtm.test.monitor from 10.100.1.100 : state: redirected)

    Note: If the server response includes a meta refresh tag in the HTML content, it has the same effect as an HTTP 302 Found response status code. The following example shows a meta refresh tag:

    <meta http-equiv="refresh" content="1;url=http://www.yoursite.com/new/location.html">

  • The BIG-IP DNS system marks the server as down if the server returns the following response status:

    HTTP/1.1 404 Not Found

  • The BIG-IP DNS system logs a message that appears similar to the following example into the /var/log/gtm file:

    011a4003:1: SNMP_TRAP: Pool /Common/default.http member /Common/gtm_vip (ip:port=10.100.1.101:80) state change green --> red ( Monitor /Common/gtm.test.monitor from 10.100.1.100 : state: server error)

The big3d process is responsible for issuing probe requests and broadcasts the response to all listening gtmd processes. Typically, the default interval for BIG-IP DNS monitors is longer than the BIG-IP LTM monitors, and by default the BIG-IP DNS system marks objects as unavailable more aggressively than the BIG-IP LTM system does.

Note: The terminology search result will be in the log message only if the monitor is configured with a Receive string.

For example:

  • When a probe receives a response within the Probe Timeout period (5 seconds, by default), and does not have a Receive string configured, the BIG-IP DNS system logs a message that appears similar to the following example to the /var/log/gtm file:

    011ae0f2:1: Monitor instance /Common/https 10.10.7.0:443 CHECKING --> UP from 10.10.0.1 (state: success)

  • When a probe does not receive a response within the Probe Timeout period (5 seconds, by default), and is configured with a Receive string, the BIG-IP DNS system logs a message that appears similar to the following example to the /var/log/gtm file:

    011ae0f2:1: Monitor instance /Common/http_short 10.10.7.70:80 CHECKING --> DOWN from 10.10.0.1 (connect: timeout search result false)

  • When the response from the server is not HTTP 200 OK, the BIG-IP DNS logs a message that appears similar to the following example to the /var/log/gtm file:

    011ae0f2:1: Monitor instance /Common/http 10.10.7.70:80 UP --> DOWN from 10.10.0.1 (state: server error)

  • When a proper response is received from the server but does not match the configured Receive string, the BIG-IP DNS system logs a message that appears similar to the following example to the /var/log/gtm file:

    011ae0f2:1: Monitor instance /Common/http 10.10.7.70:80 UP --> DOWN from 10.10.0.1 (connect: success search result false)

  • When the response from the server is not HTTP 200 OK, the monitor is configured with a Receive string, and the string is matched, the BIG-IP DNS system logs a message that appears similar to the following example to the /var/log/gtm file:

    011ae0f2:1: Monitor instance /Common/http_short 10.10.7.70:80 CHECKING --> DOWN from 10.10.0.1 (connect: server error search result true)

  • When the server responds with a protocol that does not match the applied monitor, the BIG-IP DNS system logs a message that appears similar to the following example to the /var/log/gtm file:

    011ae0f2:1: Monitor instance /Common/udp 10.10.7.70:53 UP --> DOWN from 10.10.0.1 (state: protocol mismatch)

For more information on BIG-IP DNS health monitors, refer to K8170: Understanding differences between BIG-IP LTM and BIG-IP DNS monitors.

Recommendations

Before deploying a BIG-IP DNS HTTP and HTTPS health monitor, use the command line to send a test request to the server and ensure that an HTTP 200 OK response status is received from the server. If the server is not returning an HTTP 200 OK response status, make the appropriate modifications to the send string so the system sends the request to the correct resource.
