K000157199: ASM policy delays HTTP request with “Pending DNS Requests Exceeded” violation

Type
Support Solution
Published
2025-10-29
Updated
2026-08-19
Applies to
  • BIG-IP
  • BIG-IP ASM: 17.0.0, 17.1.0, 17.0.X, 17.X.X, 17.5.X, 17.5.1, 17.5.0, 17.1.X, 17.1.3, 17.1.2, 17.1.1
Source
https://my.f5.com/manage/s/article/K000157199

Description

Users may experience significant application slowness or delays when an ASM security policy is configured on the virtual server. 

ASM event logs may show requests with the violation “Pending DNS Requests Exceeded”. This indicates that DNS resolution requests are being queued and not completed in time, resulting in delayed or blocked transactions. This behavior can occur even if the security policy is in transparent mode or the requests are not blocked by ASM.

Environment

  • AWAF/ASM version 17.0 or later
  • Server-Side Request Forgery (SSRF) Protection is enabled, with an SSRF Host property configured using a wildcard hostname
  • HTTP requests contain a parameter value that resembles a URI

Cause

Upon reviewing the HTTP requests in the event logs or a packet capture, you may find a parameter value that resembles a URI. 

This value may appear in:

A key-value parameter in the request URI
A key-value parameter in the request payload
A field in a JSON request body

For example:

GET https://www.test.com/app.php?addr=http://internal.test.com/&action=ping

or

POST https://www.test.com/order

{"id":100,"target":"https://order.test.com/neworder"}

The SSRF protection feature inspects parameter values that appear to contain URIs and attempts to resolve hostnames that are not explicitly allowed or denied in the SSRF Hosts list.

If DNS resolution does not complete and the pending DNS request queue reaches its limit, the system generates the “Pending DNS Requests Exceeded” violation. This can delay request processing and may cause the request to be blocked, depending on the security policy configuration.

Recommended Actions

  • If SSRF protection is required for request inspection, ensure that DNS resolution works properly on the BIG-IP system. Configure a DNS server that can respond to resolution requests without delay. If a DNS server is already configured but responses remain slow, capture DNS traffic, for example on port 53, for further troubleshooting.
  • If a URI-like parameter value in the request is confirmed to be legitimate, add the hostname, such as "internal.test.com", to the SSRF Hosts list and set its action to "Allow". This prevents further DNS evaluation of that hostname by the SSRF protection feature.
  • If the entire parameter is considered safe and cannot be used to trigger an SSRF attack in the application (confirm this with the application security team). You can then change the parameter’s "Data Type" from "Auto-detect" to a value other than "URI" (e.g. "Alpha-Numeric") in the security policy to prevent URI detection and DNS lookup for the value of that parameter.
  • If SSRF protection is not required in the environment (again, discuss this with the application security team), disable the Learn, Alarm, and Block settings for the "Server-side access to disallowed host" violation in the security policy.

Additional Information

The SSRF protection feature helps prevent server-side request forgery attacks by inspecting user-supplied parameter values and controlling access to internal resources.

When the action for a hostname is set to Resolve, the system attempts to resolve the hostname through DNS. This can delay request processing if DNS resolution is slow or the domain is unreachable.
