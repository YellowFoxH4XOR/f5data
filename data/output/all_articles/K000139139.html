K000139139: Azure Load Balancer Health Probes to NGINX Deployment Show error "client closed connection while SSL handshaking, client: 168.63.129.16, server: 0.0.0.0:443"

Type
Support Solution
Published
2024-04-01
Updated
2024-04-01
Source
https://my.f5.com/manage/s/article/K000139139

Description

  • You successfully provisioned NGINXaaS for Azure 
  • You updated your configuration and successfully proxying request through NGINX
  • However, you noticed NGINX error logs being filled up with errors from the Azure Load Balancer IP Address (168.63.129.16) like the ones below. 
    2024/02/23 22:41:06 [info] 848484#848484: *463272 client closed connection while SSL handshaking, client: 168.63.129.16, server: 0.0.0.0:443
    2024/02/23 22:41:07 [info] 848484#848484: *463274 client closed connection while waiting for request, client: 168.63.129.16, server: 0.0.0.0:80

Environment

  • NGINX as a Service for Azure
  • Azure
  • SSL

Cause

  • An Azure service health probe checks for status via a TCP connection for each port in the NGINX configuration,

Recommended Actions

  • Nginx, as a proxy, cannot control who is trying to connect to it,
  • With that said, it is possible to filter these logs out if they are causing concern by reducing the error.log level to "error" .
  • Alternatively, one can leverage Azure Monitor as it provides additional destinations as well as tools for querying, filtering, and transforming logs. There is also suggestion around Azure Monitor + Logs Analytics as alternative avenue with which you may be able to filter logs better.
  • To confirm at this current time and at a time of this article publication, it is not directly possible to eliminate these logs from 168.63.129.16 due to the way in which this traffics are generated and the way in which the error log works.

Additional Information

  • By default, an Azure service health probe checks for status via a TCP connection for each port in the NGINX configuration, incrementing the connection count for each port. 
  • This means, for Azure Load Balancer's health probe to mark up NGINX instance, one must allow 168.63.129.16 IP address in any Azure network security groups and local firewall policies.
  • However, this contributes to minimal traffic and should not affect metrics on the NGINX, significantly.
  • As a workaround, we are considering a plan for internal configuration that can eliminate error log output from source IP 168.63.129.16. But, doing so, does not eliminate traffic from metrics, which in turn could lead to other confusion.
