K000163954: Velos Partition management IP suddenly became inaccessible

Type
Support Solution
Published
2026-10-26
Updated
2026-10-26
Applies to
  • F5OS Products
  • F5OS-C: 1.8.X, 1.8.2, 1.8.1, 1.8.0
Source
https://my.f5.com/manage/s/article/K000163954

Description

A VELOS partition management IP suddenly becomes unreachable from one or more source host IPs even when the sources are allowed in partition configuration.

  • Sometimes HTTPS may fail while SSH continuing to work when both are allowed or vice versa from the same IP.
  • Sometimes entire source subnets may not work.
  • tcpdump shows "ICMP Destination Unreachable (Port Unreachable)" responses to TCP SYN packets from allowed source IPs.
  • The running configuration lists the source subnet in allowed-ips.
  • Sometimes other source IPs or subnets may work without issues.
  • Sometimes this may happen only on one controller (active or standby)

Environment

  • VELOS Chassis with F5OS-C v1.8.2
  • Velos Partition whitelisted source IPs or networks.
  • Management access for ports HTTPS (22, 80, 443, 7001:7008, 8888) and SNMP (UDP 161) are permitted through the partition firewall manager

Cause

This can happen if iptables chain is out of sync with the running configuration. This issue is internally tracked under ID2695953.

Due to this bug, even when running configuration has allow entries for source subnets, the iptables chain in firewall-manager container for that partition, may not have all the corresponding allow entries for those source subnets.

Recommended Actions

Follow the workaround to fix the impact of the bug:

  1. Log in to the Partition GUI as an administrator.
  2. Navigate to System Settings > System Security and remove the affected allowed-ips entry.
  3. Re-add the same entry with the same subnet and prefix length.
  4. Test HTTPS and SSH access to the partition management IP from the affected source and it should start working again.

Additional Information

To verify the iptables state of a partition, follow the steps below:

  1. Log in to the affected controller as root.
  2. Run the command below:
    # docker exec partition<ID>_firewall-manager iptables -t filter --modprobe=/bin/true --list -v -nNote: Replace <ID> with the partition ID.
  3. Confirm that the ANYPORT_ALLOW_RULES chain contains a TCP ACCEPT entry for the source subnet with dports 22,80,443,7001:7008,8888.
    If required, compare the output between the active and standby controllers.
