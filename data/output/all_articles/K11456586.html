Description

Some iSeries platforms and VIPRION B4450 blades can potentially experience unbalanced TMM (Traffic Management Microkernel) connection counts, viewable using the command tmsh show sys tmm-traffic. Even-numbered (data-plane) CPU cores show skewed utilization across cores.

Environment

  • iSeries platforms (i5000/i7000/i10000/i11000/i15000 series)
  • VIPRION B4450 blade

Cause

Linux kernel 2.4+ and potentially other operating systems, can favor the use of even numbered ephemeral ports. If these clients cycle through connections quickly enough or client side IP diversity is small, the disaggregator (DAG) could prefer certain tmm's over others causing unbalanced tmm connection loading. Using the command tmsh show sys tmm-traffic, the BIG-IP system might report connection that are substantially unbalanced as show in the example below.

Recommended Actions

Alter db variable to change DAG hashing algorithm

With the fix of ID 913829, a new db variable dagv2.pu.table.size.multiplier was introduced. The db variable changes the normal DAG hashing algorithm to compensate for the port striding use from client system. Valid db values are 1 (default), 2, or 3 and altering requires a tmm restart. F5 has found the value 2 to be the most effective setting for dagv2.pu.table.size.multiplier for the most common situation where this occurs.

Impact of workaround: Restarting TMM will disrupt service traffic. F5 recommends to perform this action while the device is in Standby or in a maintenance window.

  1. Alter the db variable.
    tmsh modify sys db dagv2.pu.table.size.multiplier value 2
  1. Restart tmm. This will cause traffic groups to failover within HA pair, or disrupt service traffic in case of a standalone device.
    bigstart restart tmm

Monitor the BIG-IP, validating traffic is balanced. If the value 2 does not produce the desired balance pattern, try using the value 3.

Programmatically determining which setting provides proper balancing

Using source and destination ports from a packet in the client side VLAN, run the command on the platform that has the unbalanced traffic using the command:
# cmp_dest --command resolve --pu_table_size_multiplier <dag db variable> --remote_port <source_port> --local_port <dest_port>
Note: Option --command resolve, queries the local hardware for number of tmm and various other options. Hence, it is critical to run on exact same hardware as device experiencing unbalanced connections.
Note: Option --pu_table_size_multiplier, is db variable dagv2.pu.table.size.multiplier values can be 1, 2, or 3 overriding the setting it gets from--command resolve option.

Likewise, if you would like to test with even numbered 200 (COUNT) ephemeral ports starting from the source port 10000 (START), you can run the following command:

START=10000; COUNT=200; for i in $(seq 0 $((COUNT-1))); do rp=$((START+i*2)); printf $rp:
cmp_dest --command resolve --pu_table_size_multiplier 2 --remote_port $rp --local_port 80
done |awk -F '/' '{print $3}' |sort |uniq -c

Sample output would be like:

     32 tmm0
     34 tmm1
     32 tmm2
     34 tmm3
     34 tmm4
     34 tmm5

Using this information, you should be able to determine the appropriate dagv2.pu.table.size.multiplier value.
