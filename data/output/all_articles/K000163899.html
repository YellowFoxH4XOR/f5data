K000163899: Portal Access connections are reset with the error "Fetching cookie failed"

Type
Support Solution
Published
2026-10-26
Updated
2026-10-29
Applies to
  • BIG-IP
  • BIG-IP APM: 21.1.0
Source
https://my.f5.com/manage/s/article/K000163899

Description

After you open several Portal Access applications in one access session, the browser shows an error instead of the application:

  • Google Chrome: ERR_EMPTY_RESPONSE or ERR_CONNECTION_RESET

  • Mozilla Firefox: PR_END_OF_FILE_ERROR

The failure can get worse over time: affected users can fail on the first application, not only after several applications. The access session stays active. Access reports show no session end or timeout.

When you troubleshoot this issue, you may observe the following log messages (examples; the addresses and process IDs vary):

  • In the /var/log/ltm file:

    err tmm1[<pid>]: 01230140:3: RST sent from <virtual_server_address>:443 to <client_address>:<port>, [<id>] Internal error (APM::REWRITE requested abort (ERROR Fetching cookie failed.))

  • In the /var/log/rewrite file:

    error rewrite - RewritePlugin.cpp:3290 (<address>): ERROR: Fetching cookie failed.

Environment

  • BIG-IP APM 17.1.3, 17.5.1, or 21.1.0, before the fixed releases listed in Recommended Actions

  • Portal Access resource and rewrite profile

  • Back-end applications, or other BIG-IP features on the virtual server, that set large cookies. For example, large authentication cookies, BIG-IP ASM or bot defense cookies, or the session cookie that the HTTP Analytics profile adds when User Sessions is enabled.

Cause

Portal Access keeps the cookies of the back-end applications in the access session. When the total cookie data reaches the cookie data size limit, Portal Access cannot fetch the cookies and resets the connection. The cookie data grows as you open more applications in the same session. This issue is tracked as Bug ID 2359001.

Answer/Recommended Actions

  1. Upgrade to a release that includes the fix: 17.1.3.6, 17.5.1.10, 21.1.0.3, or later. If you need an engineering hotfix, refer to K4918: Overview of the F5 critical issue hotfix policy.

  2. After the upgrade, verify that the database variable for the rewrite buffer exists:

    tmsh list sys db access.http.buffersize

    The default value is 16 (KB). If the command returns 01020036:3: The requested database variable (access.http.buffersize) was not found., do not try to change it. Open a support case to confirm the release or hotfix that you need.

  3. Increase the rewrite buffer size:

    Impact of procedure: F5 recommends performing this procedure during a scheduled maintenance window.

    tmsh modify sys db access.http.buffersize value 32

    If the issue persists, increase the value in steps, up to 128 (the valid range is 4 to 128). Test after each change.

  4. Test the change:

    1. Start a new access session.

    2. Open the same number of Portal Access applications that failed before.

    3. Check that the browser loads all applications, and that /var/log/ltm has no new messages that include Fetching cookie failed.

Workaround

If you cannot upgrade, and the virtual server has an HTTP Analytics profile, you can reduce the cookie data: in the HTTP Analytics profile, in Collected Metrics, clear User Sessions. This may resolve the symptoms, but it does not raise the cookie data size limit. Larger back-end cookies can still cause the issue. After you upgrade and test, you can select User Sessions again.

Impact of workaround: HTTP Analytics does not collect user session metrics for the virtual server.

Note: Change one setting at a time, so that you can see which change has an effect.

If the issue persists, open a support case and provide the data listed in the Collect HTTPWatch or HAR files for support section of K14184: Troubleshooting BIG-IP APM Portal Access applications. Also include the following:

  • The output of tmsh show sys version and tmsh list sys db access.http.buffersize

  • The /var/log/rewrite file, or a packet capture that shows the reset message
