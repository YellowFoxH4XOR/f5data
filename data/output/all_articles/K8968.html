Topic

When you configure a persistence profile for a virtual server, the BIG-IP LTM system tracks and stores session data, such as the pool member that serviced a client request. Persistence allows returning clients to bypass load balancing and connect directly to the server to which they last connected.

Note: When a cookie persistence profile is configured for a virtual server, the BIG-IP system does not store the session data locally in the persistence table; the BIG-IP system stores the session data in the cookie.

Based on the following example configuration, when client 100.0.0.1 connects to the my_virtual virtual server, the BIG-IP LTM system load balances the connection to one of the pool members in my_pool, and creates a persistence entry in the persistence table. When the client returns to the virtual server and the persistence entry has not expired, the BIG-IP LTM system bypasses load balancing and sends the connection directly to the server to which it last connected.

ltm virtual my_virtual {
    destination 10.0.0.1:http
    ip-protocol tcp
    mask 255.255.255.255
    persist {
        my_persist {
            default yes
        }
    }
    pool my_pool
    profiles {
        http { }
        tcp { }
    }
    source 0.0.0.0/0
    translate-address enabled
    translate-port enabled
}
ltm persistence source-addr my_persist {
    app-service none
    defaults-from source_addr
}
ltm pool my_pool {
    load-balancing-mode fastest-node
    members {
        10.12.10.6:http {
            address 10.12.10.6
        }
        10.12.10.7:http {
            address 10.12.10.7
        }
        10.12.10.8:http {
            address 10.12.10.8
        }
    }
    min-active-members 1
    monitor mon_http
}

If a monitored pool member becomes unavailable, persistence table entries that reference that pool member remain in the persistence table in case the pool member becomes available again. The entries will remain for the duration of the configured timeout value on the persistence profile.

Important: If a new connection matches an entry in the persistence table during the period of time the pool member is unavailable, that entry will be ignored and the new connection will be load balanced. The existing persistence table entry will be removed and a new persistence entry will be created. For example, if the BIG-IP LTM system receives a new connection with a Secure Sockets Layer (SSL) session ID matching an existing SSL persistence table entry, the new connection will be load balanced to a pool member and a new persistence table entry will be created in place of the existing persistence table entry.

Using persistence with priority group activation

The priority group feature allows each member in the load balancing pool to be assigned a priority. While all the members of the highest priority group are available, traffic is load balanced to that priority group. If the number of available members in the highest priority group drops below a configured number, the BIG-IP LTM system activates the next highest priority group and sends traffic to those pool members.

When a virtual server references a priority group pool, persistence may cause traffic to persist to a node in a lower priority group even after a higher priority group is reactivated.

Based on the following example configuration, if both priority 3 members of the my_pool pool are marked down, the priority 2 member 10.12.10.6, begins taking connections. When a client connects to the my_virtual virtual server, the BIG-IP LTM system load balances the connection to the 10.12.10.6 pool member, and creates a persistence entry in its persistence table. When the client returns to the virtual server and the persistence entry has not expired, the BIG-IP LTM system bypasses load balancing and sends the connection directly to the server to priority 2 member 10.12.10.6, regardless of whether a higher priority pool member has returned to service.

ltm virtual my_virtual {
    destination 10.0.0.1:http
    ip-protocol tcp
    mask 255.255.255.255
    persist {
        my_persist {
            default yes
        }
    }
    pool my_pool
    profiles {
        http { }
        tcp { }
    }
    source 0.0.0.0/0
    translate-address enabled
    translate-port enabled
}
ltm persistence source-addr my_persist {
    app-service none
    defaults-from source_addr
}
ltm pool my_pool {
    load-balancing-mode fastest-node
    members {
        10.12.10.6:http {
            address 10.12.10.6
            priority-group 2
        }
        10.12.10.7:http {
            address 10.12.10.7
            priority-group 3
        }
        10.12.10.8:http {
            address 10.12.10.8
            priority-group 3
        }
    }
    min-active-members 1
    monitor http
}

If connections are persisted to a lower numbered priority pool member you can clear the persistence entries for the pool member using the following command syntax:

tmsh delete ltm persistence persist-records pool <pool_name> node-addr <node_IP> node-port <node_port>

For example, if connections are persisted to pool member 10.12.10.6:80, you can clear the persistence entries for the pool member by typing the following command:

tmsh delete ltm persistence persist-records pool my_pool node-addr 10.12.10.6 node-port 80
