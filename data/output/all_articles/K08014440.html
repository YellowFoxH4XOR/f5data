Description

BIG-IP does not forward IP fragments until all fragments of an incoming packet arrives. In some cases, the size of IP fragments may change when BIG-IP forwards IP fragments.

Environment

  • BIG-IP fastL4 virtual server (VS) configured with ''Reassemble IP Fragments'' disabled
  • Client or server sending IP fragments to BIG-IP

Cause

Working as designed.

Recommended Actions

None

Additional Information

A standard (full-proxy) virtual server will re-assemble inbound IP fragments and (if necessary) re-fragment outbound IP payloads.

Article K9012 explains how reassembly of IP fragments is handled with fastL4 profiles. The default setting of the "Reassemble IP Fragments" option in the fastL4 profile is "disabled". This might give the perception that a fastL4 virtual server, with "Reassemble IP Fragments" set to disabled, will forward IP fragments from ingress to egress without first gathering all fragments. ie: that each fragment will be simply forwarded whether the complete set of fragments arrive or not.

BIG-IP is neither a router or a bridge and will always wait for all fragments before forwarding anything on to the egress vlan. This relates to the tmm CMP architecture. For the non-first fragments, the DAG does not know which tmm to send the fragments to. Therefore, it gathers up all fragments and then forwards them when the fragment chain is complete to a tmm based on the information in the first fragment. This behaviour cannot be overridden.

The purpose of "Reassemble IP Fragments" is to determine how the fragments will be processed leaving the fastL4 virtual server. If the default of disabled is used, then each fragment is sent processed outbound as they are received. If "Reassemble IP Fragments" is set to enabled, then the whole payload will be re-assembled and then, if required, it will be re-fragmented on the egress vlan.

For example, if you have somewhere on the ingress side of the fastL4 virtual server there is a segment with IP MTU of 1000 bytes and the egress IP MTU is 1480 bytes.

If the client sends a payload of 1400 bytes (with the ip don't fragment bit not set), then it will arrive as two fragments of 1000 and 400 bytes. With "Reassemble IP Fragments" disabled, the fastL4 virtual server will output this again as two fragments of 1000 and 400 bytes. If "Reassemble IP Fragments" enabled, the fastL4 virtual server will output this again as a single fragment of 1400 bytes.

If the scenario is changed slightly such that the egress IP MTU is 800 bytes.

Now, if the client again sends the same payload, then it will still arrive as two fragments of 1000 and 400 bytes. However, now with "Reassemble IP Fragments" disabled, the fastL4 virtual server will output this as three fragments of 800, 200 and then 400 bytes. If "Reassemble IP Fragments" is enabled, the fastL4 virtual server will output this as a two fragments of 800 and 600 bytes.
