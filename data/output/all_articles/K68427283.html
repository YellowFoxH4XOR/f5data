Description

The BIG-IP system is in an Offline state, and the CLI prompt shows datasyncd down.

The following message is seen in /var/log/ltm:

warning sod[8866]: 01140029:4: HA proc_running datasyncd fails action is go offline and down links.

Furthermore, messages similar to the following can be seen in /var/log/datasync/datasyncd.log:

DATASYNCD|NOTICE|Aug 20 12:05:11.162|10753|datasyncd_main.c:5192|untar_update_files: executing command "tar -xvf /var/datasync/loaded_updates/clntcap_update_v12.1.2__20208903_1324844__202012812_022631__3ac9502cf1f6e3bb87a267e0fa1234c8 -C /var/datasync/cs/ --strip-components=1 format00"
tar: This does not look like a tar archive
tar: format00: Not found in archive
tar: Exiting with failure status due to previous errors

Environment

  • ASM or FPS provisioned

Cause

/var partition is full, leading to a corrupted datasync update-file.

Recommended Actions

To recover from this issue, free disk space under /var, delete the corrupted file, and sync the datasync-global-dg device group from the peer.

Freeing disk space

You must first free disk space on the /var partition. Refer to the following article for guidance:

  • K14403: Maintaining disk space on the BIG-IP system

Recovering datasyncd

Review the log messages in /var/log/datasync/datasyncd.log to determine which file is corrupted.

In the example given in the description of this article, the corrupted file is:

/var/datasync/loaded_updates/clntcap_update_v12.1.2__20208903_1324844__202012812_022631__3ac9502cf1f6e3bb87a267e0fa1234c8

Next, review /config/bigip_base.conf to determine which security datasync update-file references this file.

Continuing with our example above, this would be:

security datasync update-file /Common/datasync-global/update-file-clntcap_update_v12.1.2__20208903_1324844__202012812_022631__3ac9502cf1f6e3bb87a267e0fa1234c8 {
    cache-path /config/filestore/files_d/Common_d/datasync_update_file_d/:Common:datasync-global:update-file-clntcap_update_v12.1.2__20208903_1324844__202012812_022631__3ac9502cf1f6e3bb87a267e0fa1234c8_82280_1
    original-create-comment "installed update"
    original-create-device "asm1.example.com / asm1.example.com #1"
    original-create-time 2020-08-14:03:48:44
    revision 1
    source-path /var/datasync/updates/clntcap_update_v12.1.2__20200813_174754__20200812_022631___3ac9502cf1f6e3bb87a267e0fa1234c8
}

Delete the configuration reference to this file:

tmsh delete security datasync update-file <file>

To delete the file in our example above, the command would be:

tmsh delete security datasync update-file /Common/datasync-global/update-file-clntcap_update_v12.1.2__20208903_1324844__202012812_022631__3ac9502cf1f6e3bb87a267e0fa1234c8

Save the configuration:

tmsh save /sys config

Restart datasyncd:

tmsh restart /sys service datasyncd

The system should come back online at this point. If it does not, review the output of the HA table for any other failures:

tmsh show /sys ha-status

Finally, on the peer system, sync the datasync-global-dg device group to the group:

tmsh run cm config-sync to-group datasync-global-dg force-full-load-push

Additional Information

Take care not to allow the /var partition to get filled, as many processes rely on this partition for temporary storage.

Automatic UCS backup tasks are a common culprit of an over-utilized /var partition.
