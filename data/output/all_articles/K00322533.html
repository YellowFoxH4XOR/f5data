Topic

The BIG-IP AFM has an intrusion detection and intrusion prevention feature called Protocol Inspection, which includes a signature matching engine that supports using custom signatures. This allows the user to craft their own signatures to mitigate emerging threats.

Description

Protocol Inspection signatures in relation to Snort

Protocol Inspection signatures use Snort syntax for content matching but are otherwise different. Structurally, each Snort signature is a one-line, self-contained entity.

Signature components

Protocol Inspection custom signatures contain several signature fields:

Name

A Protocol Inspection signature is an object in TMOS and requires a unique name. Unlike most TMOS objects, a Protocol Inspection signature name can begin with or consist solely of numerals. Signatures imported from a file have names generated from the service and description.

Description

This is a required field. It provides a summary or descriptive title for the signature. The system uses it in combination with service to generate signature names for signatures imported from files. The description displays prominently in the Inspection Profile and in the Inspection pages, so F5 recommends that you use a usefully description while keeping the character count under 40 characters to fit in the allotted column space in the displays.

Signature definition

The signature definition (sig) is where you write the matching patterns to specify the detection logic. The signature definition follows Snort rules syntax. You cannot save the signature without a definition, but you can currently create signatures in the TMOS Shell (tmsh) or import them from file without a definition. The following are the keywords for the signature definition:

  • content is the primary way to specify a pattern you want to alert for. Place the pattern in quotes. Escape the quotes with a backslash (\).

    For example:

    content: \"example\";

    • hexadecimal content

      Place hex characters inside pipe character ( | ) 

      For example,

      content: \"|FF|\";)

      For characters that are part of the Snort rules syntax, use their hexadecimal representation, as shown in the following table.

      CharacterHexadecimal
      "22
      ;3B
      :3A
      |7C

      For example,

      content: \"http|3A|//www.someurl.com/uri.html \"

  • nocase modifies the preceding content check and ignores case sensitivity.

    For example, the following matches "EXAMPLE" and "example" and permutations thereof.

  • offset specifies the number of bytes to skip from the beginning of the payload before searching for a pattern. offset 0; is the default and can be unspecified. Often paired with the depth keyword (see next).
  • depth specifies the distance in bytes to search for a pattern. The entire pattern must be contained within the depth value to match. If an offset value is specified, the depth value starts at the offset.

    For example, the following start looking for "example" in four bytes starting 16 bytes in from the beginning of the payload.

    (content:"example"; depth:4; offset:16;)

  • distance

    Specifies the distance in bytes to skip from the previous match to search for the next content match. Similar in concept to offset except it starts from the end of the previous content match rather than the beginning of the payload. This keyword is often paired with the within keyword (see next).

    For example, the following matches if "EXAMPLE" is found and "EXAMPLE2" is found somewhere after 1 byte from " EXAMPLE".

    (content:"EXAMPLE"; content:"EXAMPLE2"; distance:1;)

  • within specifies the distance in bytes to search. The entire pattern must be contained within the within value to match. It is similar to depth, except it starts from the end of the previous content match rather than the beginning of the payload.

    For example, the following matches if "EXAMPLE" is found and if "EXAMPLE2" is found entirely within 8 bytes of the end of "EXAMPLE".

    (content:"EXAMPLE"; content:"EXAMPLE2"; within:8;)

    The content check modified by the within keyword must fit in the within keyword value. In the previous signature example, this matches because the end of the string "EXAMPLE2" is within 8 bytes of the end of the previous match:

    GET /EXAMPLEABCEXAMPLE2

    The following example does not match:

    GET / EXAMPLEabcdEXAMPLE2

    The within keyword starts counting from 1.

    • distance + within

      When using distance + within keywords, the within keyword value starts at the end of the distance keyword value.

      (content: \"ABC\";content:\"KLM\"; distance: 5;within:5;)

      After matching "ABC", move 5 bytes forward into the payload, then start looking for "KLM" which must be found entirely within the next 5 bytes.

      The following example matches:

      • "ABC01234KLMXXXX"

        "KLM" starts at least 5 bytes (actually exactly 5 bytes) after "ABC" and is contained within no more than 5 bytes after ABC + distance value = 5 + 5 = 10"ABC")

      • "ABCDEFGHIJKLMXXXX"

        "KLM" starts at least 5 bytes after ABC (actually 7 bytes) and must be contained no more than 5 bytes after the distance interval of 5. ("KLM" is actually found contained within exactly 5 bytes of the end of the distance value of 5)

      The following example does not match:

      • "ABCXXDEFGHIJKLMXXXX"

        "KLM" is found at least 5 bytes from the end of "ABC" (actually 9 bytes) but does not fit within 5 bytes of the end of the distance value. The beginning of the content string "K" is within 5 bytes from the end of the distance value from the previous match, but the entire string must be found inside the within value. "LM" is at byte 14-15, which is outside the within value.

  • http_client_body restricts the content search to the body of an HTTP client request.
  • http_cookie restricts the content search to the cookie header field of an HTTP client request or HTTP server response.
  • http_header restricts the content search to the HTTP header.
  • http_method restricts the content search to the HTTP method specified in the client request.
  • http_uri restricts the content search to the URI specified in the client request.
  • byte_jump and byte test make it relatively easy to write rules for length-encoded protocols. The bye_jump keyword allows the user to read a value from a specified location in the packet and skip forward the number of bytes in that value. This is useful for several protocols like RPC that have variable length fields with headers defining the length of those fields.

    byte_jump: <number of bytes to extract the jump value from>, <offset>

    byte_jump: <bytes_to_convert>, <offset>[,relative], [,big] [,little][,string][,hex] [,dec] [,oct] [,align] [,from_beginning];

    • offset

    • relative (modifies an offset to be used relative to the previous content match)

    • big

    • little

    • value types

      • string

      • hex

      • dec

      • oct

    • align

    The byte_test keyword compares a protocol field against a given value.

    Syntax of the keyword is as follows:

    byte_test:<bytestoconvert>,[!]<operator>,<value>,<offset>[,relative][,<endian>][,<numbertype>,string];

    Comparisons available are as follows:

    • < Less than
    • > Greater than
    • = Equals

    For example, the following syntax find bytes 16 03 00, read the next two bytes and take their value as the number of bytes to jump forward. Look for bytes 18 03 00 within 3 bytes of where you landed. Then take the next two bytes and see if their value is greater than 128.

    (content:"|16 03 00|"; byte_jump:2,0,relative; content:"|18 03 00|"; within:3; byte_test:2,>,128,0,relative; metadata: service ssl; )

    • 3.9 Writing Good Rulesin the Snort Users Manual 2.9.16 includes a useful real-world example.

  • fast_pattern in Snort is a very efficient pattern matching engine that is used like a pre-processor to determine whether the most specific (longest) content string is present in the packet. If the content string is not present, there is no point in applying the signature to the packet with the more comprehensive (slower) main matching engine. You can also use fast_pattern as a standalone high-performance matching engine for simple pattern tests.

    The BIG-IP AFM signature matching engine has a different architecture with regard to the fast_pattern keyword; it allows the fast_pattern keyword for compatibility reasons but ignores it.

  • pcre (Perl Compatible Regular Expression) provides the ability to match against complex or variable patterns. Protocol Inspection uses the Hyperscan regular expression library.

    For example, at the start of the packet, look for xpn followed by one or more spaces, followed by *@.

    (pcre:"/^expn\s+\*@/smi"; metadata: service;)

    You may want to use the following reference tool when writing a signature definition using PCRE: regex101.com/
