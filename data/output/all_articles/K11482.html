K11482: The BIG-IP system automatically caches SSL client certificates

Source

Issue

In BIG-IP versions prior to 10.1.0, when a Secure Sockets Layer (SSL) virtual server is configured to request or require clients to present a valid certificate, the BIG-IP system does not cache the certificates that the clients present. This causes the SSL::cert iRule command to return data about a client's certificate only during the TCP connection in which the certificate is presented. If a client resumes a previously-established SSL session, the SSL::cert iRule command does not return any data.

A common workaround to this limitation is to manually store the client's certificate in the session table for retrieval during subsequent requests. This is accomplished by using the session iRule command, which utilizes the session table to store arbitrary information based on the same keys as persistence.

Note: For more information about this technique, refer to the session command documentation on DevCentral. A separate DevCentral login is required to access this content.

Beginning with BIG-IP 10.1.0, the BIG-IP system automatically caches SSL client certificates. This allows the SSL::cert iRule command to retrieve a client's certificate even after an SSL session was resumed. Therefore, iRules no longer require the previously-mentioned workaround after a BIG-IP system is upgraded to version 10.1.0.

Additionally, the following SSL::cert subcommands are also cached for the duration of the SSL session:

SSL::cert <index> #GET_PEER_CERT

SSL::cert issuer <index> #GET_PEERCERTISSUER

SSL::cert count # GET_PEER_CERTCOUNT

F5 Product Development tracked these changes in behavior as ID 213376, ID 213375, and ID 291400 (formerly CR47519 and CR116806).
