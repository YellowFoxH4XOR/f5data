Topic

Virtual servers referencing multiple pools by using iRules, HTTP classes, or local traffic policies may not reflect the expected status since the virtual server status must be derived from the status of multiple resources.

Virtual servers using HTTP classes or local traffic policies always reflect the status of the default pool. If no default pool is assigned, the virtual server status is Unknown.

The status of a virtual server using iRules that reference pools is derived as follows:

  • The status of the default pool and each pool referenced within an iRule is considered when determining the status of the virtual server.
  • When multiple pools are referenced from within a single iRule, the highest precedence status reflected by any pool is reflected as the virtual server's status. In order of precedence, the possible statuses are: Available, Offline, and Unknown.
  • Only direct iRules pool references are taken into account when determining the status of a virtual server. Anything that requires an iRule to execute in order to determine the pool does not affect the status of the virtual server. For example, the following iRules pool reference does not contribute to the status of the virtual server because the pool is referenced as a variable:

    set pool test.pool
    pool $pool

Since the BIG-IP GTM uses the virtual server status as reported by the BIG-IP hosting the virtual server, wide area load balancing decisions may be affected by the reported virtual server status.

You may be able to include logic in a BIG-IP LTM iRule to handle likely failure scenarios rather than relying solely on the virtual server's reported status.
