Topic

Introduced in BIG-IP 10.0.0, the inband monitor passively monitors a configured pool member to determine its health status. You can use an inband monitor when you don't want health traffic running directly between the BIG-IP and a pool member.

Description

You can apply the inband monitor to Standard and FastL4 virtual servers.

The inband monitor is passive because it inspects Layer 4 (L4) TCP traffic running to and from a pool member to determine that pool member's health, instead of initiating health monitoring traffic.

The monitor reports a pool member as down when either of the following two events occur:

  • There are TCP resets (RSTs) from the pool member.
  • Response packets from the pool member are overly delayed.

The inband monitor has the following configurable settings.

Inband monitor settings
SettingDefinition
FailuresThe number of failures (TCP RSTs or delayed responses) in a Failure Interval that trigger a down state. Note the value is per Traffic Management Microkernel (TMM) rather than per pool member. The default value is 3, which means that the system marks the pool member unavailable at the fourth failure. The multiple tmm processes use a per-process number to calculate failures, depending on the specified load. For example, for the Round Robin load balancing method, if there are N tmm processes and M pool members, and the Failures setting is set to L, then up to N*M*L+1 failures can occur before the system marks the node as down.
Failure IntervalThe period in which the allowed number of failures must occur to trigger a down state. The default value is 30 seconds.
Response TimeThe period in which the pool member must respond to a packet from the BIG-IP system before the system considers the packet delayed and a failure. The default value is 10 seconds.
Retry TimeThe period of time before the BIG-IP system attempts to reconnect to the pool member for load balancing, when the pool member is in a down state. When the attempt is unsuccessful, the inband monitor waits the same period before it attempts again. The default value is 300 seconds (five minutes).

Inband monitor example

This example illustrates the operation of the inband monitor; it uses the following setup:

  • A pool with two members.
  • The Round Robin load balancing algorithm.
  • The pool has an inband monitor and the the two pool members inherit it.
  • The BIG-IP has one TMM (multiple tmm processes use a per-process number to calculate failures. See the Failures description for details).

As long as both pool members do the following, the inband monitor keeps both pool members available:

  • Send two or less TCP RSTs within a 30 second period
  • Respond to a packet within a 10 second period

A pool member is marked down by the inband monitor when one or both of the following occur:

  • Three or more TCP RSTs within a 30 second period
  • Response to a packet that exceeds a 10 second period

After the system marks the pool member down, it is no longer eligible as a load balancing destination and does not receive new traffic.

After 300 seconds without new traffic, the system makes the pool member eligible again, and the pool sends a new connection for load balancing to it. 

If that connection is successful, the inband monitor marks the pool member active. If the connection is not successful, the monitor waits another 300 seconds, and then marks the pool member as eligible for load balancing again.
