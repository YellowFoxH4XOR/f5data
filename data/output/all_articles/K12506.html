Known Issue

This is the result of a known issue. In BIG-IP version 10.2.0, when URI::decode is called on an array object that is converted to a string object, an incorrect decoding may result in a recursive call that eventually may cause TMM to exhaust memory, and to dump core. This behavior occurs when URI::decode is called on an object, and then called again on the decoded version of that object.

For example, the following code block will result in URI::decode being called on the decoded version of a previously decoded object:

when HTTP_REQUEST {
# decode original URI.
set tmpUri [string tolower [HTTP::uri]]
set tmpUri2 [URI::decode $tmpUri]

# repeat decoding until the decoded version equals the previous value.
while { $tmpUri2 ne $tmpUri } {
set tmpUri $tmpUri2
set tmpUri2 [URI::decode $tmpUri]
}

When this recursive decoding occurs, TMM may core with the following SIGFPE panic:

panic: unable to alloc 4194372 bytes

F5 Product Development tracked this issue as ID 337562 and it was fixed in BIG-IP versions 10.2.2 and 11.0.0. For information about upgrading, refer to the BIG-IP LTM, ASM, GTM, PSM, Link Controller, WebAccelerator, APM, WOM, or Edge Gatway release notes.

Additionally, this issue has been fixed in cumulative hotfix Hotfix-BIGIP-10.2.1-473.0-HF1, which has been issued for BIG-IP version 10.2.1. You may download this hotfix or later versions of the cumulative hotfix from the F5 Downloads site.
