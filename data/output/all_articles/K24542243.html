Description

SNMP OIDs have two components - the index and value, for example sysUpTime.0 is an index, and the value could be 12345678. The MIB definition can express some parts of the index as a string of variable length, for example, myobjects."myexampleobjectname".value = 10, where "myexampleobjectname" is encoded in an OID as a sequence of bytes prefixed by the length of that sequence.  

xx."apple".yy would be encoded as xx.5.97.112.112.108.101.yy, with the 5 indicating the length of the following string sequence, "a" = 97 ASCII, p = 112, and so on.


BIG-IP uses this technique with a number of objects, such as ltm pools, node names, gtm wide ips, and so on to provide unique index OIDs for each  object. However, the SNMP standard imposes a maximum length of 128 bytes in an OID index, forcing BIG-IP to have to truncate the object name to fit within that limit.  

The solution implemented since since 11.5.4 HF2, 11.4.1 HF10, and other versions released around the same time, is to truncate the variable length component of the index to a maximum of 100 bytes, by replacing the final 8 bytes with a 32 bit checksum of the original variable component.  This ensures that the index OID is consistently named, and also unique.  It does not result in a loss of data - only the index OID is truncated - the value of that OID is not, and the name of the object is typically available under the '...Name' OID, for example " "x.x.x.xx.x.x.ltmPoolName.<variable length component> = <untruncated object name>"

Although this behaviour is necessary to comply with SNMP standards, it can cause confusion to SNMP monitoring software that incorrectly expects to find an object's untruncated name as part of the index OID.    To avoid this, customers can limit the size of their index OIDs by keeping the length of the component objects small enough so as not to trigger the truncation.

To do this effectively, the following must be understood

  • Each string component requires one additional byte to express the length
  • Truncation occurs when the total length of the variable length section reaches 100 bytes.
  • Some OIDs contain multiple strings in the index
  • Some objects contain additional metadata outside of the string piece - for example, In BIG-IP DNS 13.0.0 and later, gtm wideip and gtm pool objects are both prefixed with their rrtype (eg, A, AAAA, CNAME, etc). This counts towards the size of the variable length component.
  • The partition name and the backslashes count towards the total length, for example "/Common/myltmpool" is 17 bytes long. Objects created using iApps can have unusually long names due to the include of the name of the iApp's name within the object's name.
Examples 
F5-BIGIP-LOCAL-MIB::ltmPoolName.<variable length component>.name = "/ParitionName/<ltm pool name>"
The BIG-IP LTM pool Name OID contains the name of the pool.  Truncation occurs at 100 bytes, and 99 bytes are required to store a 98 byte string, so pool names of 98 characters or less will not be truncated.
 
F5-BIGIP-GLOBAL-MIB::gtmWideipPoolPoolName.<rrtype>.<wipname>.<rrtype>.<poolname> = "gtm-wideip-pool-entry-name"
This OID contains the name of a pool that has been assigned to a wideip.  Truncation still occurs at 100 bytes, but the way that is counted is more complicated:
 
rrtype = 1 byte
wipname = length of string + 1 (including '/Common/')
rrtype = 1 byte
poolname = length of string + 1 (including '/Common/')

For this type of object, the total of the two variable length strings can be up to 95 bytes each before truncation occurs. 
 

Environment

  • BIG-IP GTM / BIG-IP DNS
