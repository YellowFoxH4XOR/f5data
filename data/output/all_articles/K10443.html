Known Issue

This is the result of a known issue. If a reverse monitor request results in a response from the server that is smaller than 5120 bytes and does not match the recv string, and a subsequent monitor request results in a response that matches the recv string, the BIG-IP system will correctly mark the pool member or node unavailable as a result of the second response, but may not observe the configured monitor timeout. In some cases, the pool member or node may be marked unavailable immediately, while in other cases, the pool member or node may not be marked unavailable until some time after the timeout has expired.

Note: This behavior is observed only when the requested object is smaller than 5120 bytes. The size of the matching response that results in the unavailable status is not relevant.

Note: For more information about reverse monitors, refer to the Configuration Guide for BIG-IP Local Traffic Management or the Configuration Guide for BIG-IP Application Security Management for your version.

F5 Product Development tracked this issue as CR124241 and it was fixed in BIG-IP 10.1.0. For information about upgrading, refer to the BIG-IP LTM or ASM Release Notes.

Workaround

You can work around this issue by ensuring that the object requested by a reverse monitor is larger than 5120 bytes. For example, if you have configured a reverse HTTP monitor to request /monitor.html with a recv string of HTTP/1.1 404, the monitor.html page (including the headers and the body) must be larger than 5120 bytes.
