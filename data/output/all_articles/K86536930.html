Known Issue

The Linux host on a secondary blade may lose dynamic routes previously learned from a dynamic routing protocol.

This issue occurs when all of the following conditions are met:

  • Your VIPRION system is licensed with the BIG-IP Advanced Routing Module (BIG-IP ARM).
  • Your VIPRION chassis or Virtual Clustered Multiprocessing (vCMP) guest is multi-bladed.
  • The Linux host has learned routes by way of dynamic routing.
  • A restart of services or reboot occurs on the secondary blade.

Impact

Routes on the Linux host of a secondary blade are lost. This may affect host traffic, such as monitoring, remote logging, Simple Network Management Protocol (SNMP) , or network time protocol (NTP), due to the lack of routing information.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • Your VIPRION system sends local process traffic originating from the Linux host out the wrong interface, sends traffic using an incorrect route, or fails to send traffic altogether.
  • Monitor traffic fails, causing the BIG-IP system to incorrectly mark resources as unavailable.

Workaround

To work around this issue, you can modify the BIG-IP ARM maximum-paths setting on the primary blade to trigger a route update to the secondary blades. To do so, perform one of the following procedures:

Manually modify the BIG-IP ARM maximum-paths setting on the primary blade

Impact of workaround: The impact of the suggested workaround depends on the specific environment. F5 recommends that you test any such changes during a maintenance window and consider the possible impact on your specific environment.

  1. Log in to the primary blade command line.
  2. Open the imish shell by typing the following command:

    imish

  3. To enter Enable mode, type the following command:

    enable

  4. To enter Configuration mode, type the following command:

    configure terminal

  5. Modify the maximum-paths setting and revert it back to the original value (note the original value before doing so) using the following command sequence syntax:

    maximum-paths <1-64>
    maximum-paths <1-64>

    For example:

    maximum-paths 5
    maximum-paths 4

  6. Exit the interface configuration mode by typing the following command:

    exit

  7. Exit the imish shell by typing the following command:

    quit

Automatically modify the BIG-IP ARM maximum-paths setting on the primary blade when a blade joins the cluster (BIG-IP 11.4.x - 11.5.x)

Impact of workaround: The impact of the suggested workaround depends on the specific environment. F5 recommends that you test any such changes during a maintenance window and consider the possible impact on your specific environment.

  1. Log in to the primary blade command line.
  2. Back up the user_alert.conf file by typing the following command:

    cp /config/user_alert.conf /config/user_alert.conf.K86536930

  3. Use a text editor to edit the /config/user_alert.conf file.
  4. Add the stanza to the file:

    /* Workaround for ID589338 */
    alert BLADE_JOINED_CLUSTER "010719fc:5: Mate cluster member (.*) turned Green." {
        exec command="/usr/sbin/zebos -a cmd 'enable,conf t,maximum-paths 5,maximum-paths 4,exit,exit'"
    }

  5. Save the file and then exit the editor.
  6. For information about how to test the alert, refer to K14397: Running a command or custom script based on a syslog message

Note: Since the Mate cluster member log message is not present in BIG-IP 11.6.x, this procedure works on only BIG-IP 11.4.x - 11.5.x.
