Topic

When configuring Kerberos Single Sign-On (SSO), the BIG-IP APM supports either the KRB5 Kerberos 5 or SPNEGO mechanisms for sending the Kerberos Generic Security Service Application Program Interface (GSS-API) authorization to a back-end server.

Description

BIG-IP APM SSO inserts a base64 encoded GSS-API token containing the Kerberos ticket into the header of the HTTP request sent to the applicable back-end web server. The Kerberos SSO Send Authorization configuration option dictates when the token will be inserted and which mechanism (KRB5 Kerberos 5 or SPNEGO) will be used. The Send Authorization configuration includes the following options:

  • Always (default)

    The Always option sends a KRB5 Kerberos 5 mechanism type (OID 1.2.840.113554.1.2.2) as the authorization request. The Authorization header with a Kerberos ticket is inserted into every HTTP request, regardless of whether the request requires authentication.
  • On 401 Status Code

    The On 401 Status Code option sends an SPNEGO mechanism type (OID 1.3.6.1.5.5.2) as the authorization request. The BIG-IP system first forwards the user's HTTP request to the web server without inserting a new Authorization header, but any browser's Authorization header will be deleted. If the server requests authentication by responding with a 401 status code, the BIG-IP system retries the request with the Authorization header.

Most web servers are able to retrieve the Kerberos ticket from either type of authorization mechanism, but some web servers may require a specific type of authorization. In case of a mismatch, Kerberos SSO will fail even though the BIG-IP APM system is sending the correct Kerberos ticket to the back-end server. You may observe OID type errors in the authentication log files of the web server.
