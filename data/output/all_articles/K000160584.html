K000160584: Packets are intermittently dropped when using immediate timeout with firewall nat policy

Type
Support Solution
Published
2026-04-02
Updated
2026-04-08
Applies to
  • BIG-IP
  • BIG-IP AFM
Source
https://my.f5.com/manage/s/article/K000160584

Description

Packets received by BIG-IP are intermittently dropped and fails to create a new connection to be forwarded when the virtual server uses a connection profile with immediate timeout and a firewall nat policy is applied.

This may appear as lowered call quality in VoIP applications, missing UDP packets, or ICMP unreachables from the BIG-IP.

 

Environment

This can happen on a BIG-IP with the following configuration:

  • The virtual server uses a connection profile with immediate timeout
  • The virtual server uses a firewall nat policy

An example of a connection profile with immediate timeout:

ltm profile fastl4 /Common/myfastl4-timeout_immediate {
    app-service none
    defaults-from /Common/fastL4
    idle-timeout immediate
}

An example of a firewall nat policy:

security nat policy /Common/outbound_policy { rules { snat-rtp-policy { ip-protocol any translation { destination /Common/snat_rtp source none } } } } security nat destination-translation /Common/snat_rtp { addresses { 192.168.1.100 { } } type static-nat }

 

Cause

When using immediate timeout, each new packet creates a new connection. These connections are queued and flagged to not be matched to any subsequent new incoming packets. When packets are sent in quick succession, there is a fair chance previous immediately timed out connections may still exist in tmm, and therefore the firewall nat will reject to create a new nat, causing the connection to be rejected and the new packet dropped. This is unique to the firewall nat implementation, which is different from the regular LTM nat implementation that does not exhibit this issue.

F5's reference identification of this known behavior is ID 2261017.

Recommended Actions

The general recommendation is to increase the connection immediate timeout to one second or higher. Increasing the timeout, even to one second, will significantly avoid these race conditions and will allow tmm to much more efficiently process network traffic.

The reason is that tmm is designed from the ground up to be a distributed, parralel processing, full-proxy, connection-based architecture, which means tmm accelerates network processing by distributing the computation of network traffic resources among multiple CPUs that is keyed to its connection (generally a unique IP/port tuple). Configuring immediate timeout to unecessarily process network traffic packet by packet will significantly increase the processing overhead, causing each packet to be searched, matched, and processed as spearate full-proxied connections that are immediately deleted, instead of the system accelerating network processing by treating each packet using the existing pre-processing of connections.

Immediate timeout do have some use cases, such as DNS request/responses, in which the Datagram LB option can be used instead. However, most other protocols with UDP streams, such as VPN and VoIP protocols, use a unique IP/port tuple which greatly benefits from BIG-IP full-proxy connections.

Even when the use case is to allow packets in and out bidirectionally, connection flows already handle bidirectional packets because each connection flow consists of two flows: a clientside connection and a serverside connection, each that have its own bidirectional unique IP/port tuple. Depending on where the packet hits the virtual server, the clientside is created first, followed by the serverside connection.

For example:

client <=> < src ip:port <-> dst ip:port > clientside connection <---> tmm proxy <---> serverside connection < src ip2:port2 <-> dst ip2:port2 > <=> server

Therefore, as long as there are packets belonging to the IP/port tuple in both directions, both connections are kept alive and return packets are processed and returned to the client.

ltm profile fastl4 /Common/myfastl4-timeout_15s {   app-service none   defaults-from /Common/fastL4
  idle-timeout 15}
