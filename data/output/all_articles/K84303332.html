Topic

This article applies to BIG-IP 13.x through 21.x. For information about other versions, refer to the following articles:

  • K13478: Overview of connection and persistence mirroring (11.x - 12.x)
  • K7222: Overview of connection and persistence mirroring (9.x - 10.x)

The connection and persistence mirroring feature allows you to configure BIG-IP systems in a high availability (HA) configuration to duplicate connection and persistence information to peer members of the BIG-IP device group. This feature provides higher reliability but may affect system performance.

Note: For information about connection and persistence mirroring for VIPRION systems, refer to the High Availability Configuration chapter of the VIPRION Systems: Configuration manual (13.x). For information about how to locate F5 product manuals, refer to K98133564: Tips for searching MyF5 and finding product documentation.

Description

The BIG-IP device service clustering (DSC) architecture allows you to create a redundant system configuration for multiple BIG-IP devices on a network. System redundancy includes the ability to mirror connection and persistence information to a peer device to prevent service interruptions during failover. The Traffic Management Microkernel (TMM) manages the state mirroring mechanism, and connection and persistence data is synchronized to the standby unit with every packet or flow state update. The standby unit decapsulates the packets and adds them to the connection table.

The BIG-IP system maintains a separate mirroring channel for each traffic group. The active BIG-IP system in an HA device group dynamically establishes a mirroring connection to the standby system with a status of Next Active for a given traffic group. The port range for each connection channel begins at TCP 1029 and increments by one for each new traffic group and channel created. For more information, refer to K14894: The BIG-IP system establishes a separate mirroring channel for each traffic group.

You can configure the system to mirror SSL connections that are terminated by the BIG-IP system to peer device group members. For more information, refer to K17391: Configuring SSL connection mirroring.

You can use the Configuration utility or TMOS Shell (tmsh) to configure mirror addresses, configure connection mirroring for virtual servers and Secure Network Address Translations (SNATs), and configure persistence mirroring. You can also view mirroring data on the active and standby BIG-IP systems using tmsh. To do so, refer to the following sections:

  • Determine the active mirroring channel
  • Enable connection mirroring for a virtual server
  • Enable connection mirroring for a SNAT

Configure local mirror addresses

The connection and persistence mirroring feature requires you to specify which self IP addresses and VLANs each member of the BIG-IP device group uses for mirroring. For each member of a BIG-IP device group, you configure the Primary Local Mirror Address setting to assign the preferred self IP address that the system uses to establish mirroring channels. Additionally, you can configure the Secondary Local Mirror Address setting for each member of the device group. The Secondary Local Mirror Address setting assigns the self IP address and VLAN that the system uses to establish the mirroring channels when the channel cannot be established or fails using the primary address.

Important: When primary and secondary local mirror addresses are configured, the BIG-IP system uses only one of the addresses for the mirroring link and prefers the primary. If the active mirroring link fails, the standby BIG-IP system closes all currently mirrored connections and begins mirroring new connections using the other mirroring link.

If the BIG-IP system mirrors a high volume of connection and persistence information, F5 recommends using IP addresses that are configured to use a VLAN and interface dedicated to processing mirroring traffic. For information about the network resources used for BIG-IP HA features, refer to K14135: Defining network resources for BIG-IP HA features (11.x - 16.x).

To specify the primary and secondary mirror addresses, perform one of the following procedures:

Use the Configuration utility to specify mirror addresses

  1. Log in to the Configuration utility.
  2. Go to Device Management > Devices.
  3. Select the local device indicated with (Self).
  4. Select the Mirroring tab.
  5. For Primary Local Mirror Address, select the appropriate IP address and VLAN to be used as the primary option for mirroring.
  6. Optional: For Secondary Local Mirror Address, select the appropriate IP address and VLAN to be used as the secondary option for mirroring.

    Note: F5 recommends configuring this setting.

  7. Select Update.

Use tmsh to specify mirror addresses

  1. Log in to tmsh by entering the following command:

    tmsh

  2. Configure the mirror addresses by using the following command syntax:

    modify /cm device <device_name> mirror-ip <IP_address> mirror-secondary-ip <IP_address>

    For example, to configure mirroring for a device named example.com using a primary mirror IP address of 192.0.2.100 and a secondary mirror IP address of 192.0.2.101, enter the following command:

    modify /cm device example.com mirror-ip 192.0.2.100 mirror-secondary-ip 192.0.2.101

  3. Save the change by entering the following command:

    save /sys config

  2. To view the active mirroring channel, enter the following command:

    tmctl ha_stat | head -20

Enable connection mirroring for a virtual server

The BIG-IP system can mirror TCP or User Datagram Protocol (UDP) connections for virtual servers. To configure the BIG-IP system to mirror connection information for virtual servers, you must enable the Connection Mirroring setting on each virtual server that you want the system to mirror connections for. To enable connection mirroring for a virtual server, perform one of the following procedures:

Using the Configuration utility to enable connection mirroring for a virtual server

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Virtual Servers > Virtual Server List.
  3. Select the virtual server for which you want to enable connection mirroring.
  4. In the Configuration list, select Advanced.
  5. Select the Connection Mirroring check box.
  6. Select Update.

Use tmsh to enable connection mirroring for a virtual server

  1. Log in to tmsh by entering the following command:

    tmsh

  2. To enable connection mirroring for the virtual server, use the following command syntax:

    modify /ltm virtual <virtual_server> mirror enabled

  3. Save the change by entering the following command:

    save /sys config

Enable connection mirroring for a SNAT

The BIG-IP system can mirror TCP or UDP connection information for connections processed by a SNAT. To configure the BIG-IP system to mirror connection information for SNATs, you must enable the Stateful Failover Mirror setting on each SNAT that you want the system to mirror connections for. To enable connection mirroring for a SNAT, perform one of the following procedures:

Using the Configuration utility to enable connection mirroring for a SNAT

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Address Translation > SNAT List.
  3. Select the SNAT for which you want to enable connection mirroring.
  4. Select the Stateful Failover Mirror check box.
  5. Select Update.

Use tmsh to enable connection mirroring for a SNAT

  1. Log in to tmsh by entering the following command:

    tmsh

  2. To enable connection mirroring for a SNAT, use the following command syntax:

    modify /ltm snat <snat> mirror enabled

  3. Save the change by entering the following command:

    save /sys config

Enable persistence information mirroring

In addition to connection information, the BIG-IP system can also mirror some types of persistence information between peer members of a BIG-IP device group. To configure the BIG-IP system to mirror persistence information, you must enable the Mirror Persistence setting in each persistence profile you want to enable mirroring for. The BIG-IP system can mirror persistence information between peers for the following persistence profiles:

  • Destination address affinity
  • Hash
  • Host
  • Microsoft Remote Desktop
  • SIP
  • Source address affinity
  • SSL
  • Universal

To enable connection mirroring for a persistence profile, perform one of the following procedures:

Note: Instead of modifying a default profile, F5 recommends that you create a custom profile using the default profile as the parent profile. You can then modify some or all of the values defined in the custom profile, while leaving the parent profile settings at their default value. For information, refer to K14488: Working with profiles.

Use the Configuration utility to enable connection mirroring for a persistence profile

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Profiles > Persistence.
  3. Select the persistence profile for which you want to enable persistence mirroring.
  4. Select the Mirror Persistence check box.
  5. Select Update.

Use tmsh to enable connection mirroring for a persistence profile

  1. Log in to tmsh by entering the following command:

    tmsh

  2. To enable persistence mirroring for a persistence profile, use the following command syntax:

    modify /ltm persistence <profile_type> <profile_name> mirror enabled

    For example, to enable mirroring for a hash persistence profile named HashPersist1, enter the following command:

    modify /ltm persistence hash HashPersist1 mirror enabled

  3. Save the change by entering the following command:

    save /sys config

View mirrored connection data

You can use tmsh to view the connection information that has been mirrored to a BIG-IP device group member. To do so, use the tmsh show /sys connection type mirror command.

If you want to view additional details, you can use the tmsh show /sys connection type mirror all-properties command.

View mirrored persistence data 

You can use tmsh to view the persistence information that has been mirrored to a BIG-IP device group member. To do so, use the tmsh show /ltm persistence persist-records command.

If you want to view additional details, you can use the tmsh show /ltm persistence persist-records all-properties command.

Recommendations

When configuring mirroring on the BIG-IP system, F5 recommends that you consider the following suggestions:

Note: After a failover event, the BIG-IP system re-mirrors only Performance L4 and SNAT connections to the newly standby device. For more information refer to K000132338: Is it possible to synchronize connection mirroring information after a reboot or TMM restart?

  • Enable connection and persistence mirroring when a BIG-IP failover would cause the user's session to be lost or significantly disrupted

    For example, where long-term connections, such as File Transfer Protocol (FTP) and Telnet, are good candidates for mirroring, mirroring short-term connections, such as HTTP and UDP, is not recommended as this causes a decrease in system performance. In addition, mirroring HTTP and UDP connections is typically unnecessary, as those protocols allow for failure of individual requests without loss of the entire session.

  • Configure a dedicated VLAN and dedicated interfaces to process mirroring traffic

    The TMM process manages the BIG-IP LTM state mirroring mechanism, and connection data is synchronized to the standby unit with every packet or flow state update. In some mirroring configurations, this behavior may generate a significant amount of traffic. Using a shared VLAN and shared interfaces for both mirroring and production traffic reduces the overall link capacity for either type of traffic. Due to high traffic volumes, production traffic and mirroring traffic may interfere, potentially causing latency in mirrored connections or interrupting the network mirror connection between the two BIG-IP devices. If the network mirror connection is interrupted, it can cause loss of mirror information and interfere with the ability of the peer device to take over connections in the event of a failover.

  • Use direct cables for network mirroring interfaces

    You can use direct cables for network mirroring interfaces on the BIG-IP systems in the failover pair, and F5 highly recommends that you do this when configuring a dedicated VLAN for mirroring. Configuring the pair in this way removes the need to allocate additional ports on surrounding switches and removes the possibility of switch failure and switch-induced latency. Interfaces used for mirroring should be dedicated to the mirroring VLAN. Tagged interfaces shared with other VLANs could become saturated by traffic on other VLANs.

  • Configure both primary and secondary mirror addresses

    This allows an alternate mirroring path and ensures reliable mirroring in the event of equipment or cable failure.

  • Use a virtual server to process FTP traffic

    When using SNATs to process FTP connections, the BIG-IP system may modify the FTP control channel's TCP payload, for example, when rewriting the IP address in the FTP PORT command request packet sent from the client to the FTP server. The modification to the TCP payload size in the FTP PORT command packet may cause a difference between the TCP sequence and TCP acknowledgment numbers on both the client- and server-side connection flows. During an HA failover event, FTP control connections can fail because SNAT mirroring does not synchronize TCP sequence and TCP acknowledgement numbers between all of the BIG-IP systems in the HA configuration. To avoid this, process FTP connections using a standard virtual server with an associated FTP profile and mirroring enabled. For more information, refer to K93017176: Overview of the Standard virtual server.

  • Note that the standby system's connection table may contain entries that have been cleared from the active system's connection table

    When a connection is closed and cleared from the connection table of the active BIG-IP system, that connection is not cleared from the standby BIG-IP system's connection table at the same time. By default, the connection remains in the standby system's connection table until the system reaches the connection's idle timeout value. If you require the standby system's connection table to be synchronized with the active system, you can enable the statemirror.verify database variable (disabled by default) on the active and standby systems. Enabling the statemirror.verify database variable causes the system to mirror connections from the active system to the standby system, and back to the active system before they are processed. Enabling the statemirror.verify database variable may significantly decrease performance. The amount of performance loss depends on the specific environment. F5 recommends that you test any such changes during a maintenance window and consider the possible impact on your specific environment.
