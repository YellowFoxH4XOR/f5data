Topic

You should consider using these procedures under the following condition:

  • You want to run tasks in an Ansible playbook to replace the Configuration utility's self-signed certificate with a CA-signed certificate

Description

The Configuration utility uses a self-signed SSL certificate, known as a device certificate, that is valid for 10 years by default. In some cases, you may want to replace the BIG-IP system's default device certificate with a CA-signed one. You can automate the steps to complete this on a single BIG-IP system or numerous BIG-IP systems using Ansible, which is a tool that automates and manages multi-machine configuration and deployment.

Example playbook

The following is an example of a playbook that creates a CSR, signs it with a CA, and deploys it on the BIG-IP system. Use the procedures in this article to create a similar playbook:

---
- name: Update BIG-IP device certificate
  hosts: bigip_15_dg
  gather_facts: False
  vars:
    key_path: "/config/httpd/conf/ssl.key/"
    csr_path: "/config/httpd/conf/ssl.csr/"
    crt_path: "/config/httpd/conf/ssl.crt/"

  tasks:

    - name: Backup original server.crt and server.key files
      shell: >
        cp -p "{{ crt_path + 'server.crt'}}" "{{ crt_path + 'server.crt.'}}"$(date +%s);
        cp -p "{{ key_path + 'server.key'}}" "{{ key_path + 'server.key.'}}"$(date +%s)

    - name: Create CSR and private key on BIG-IP
      command: >
        openssl req -new -sha256 -nodes -newkey rsa:2048
        -keyout "{{ key_path + 'server.key' }}"
        -out "{{ csr_path + inventory_hostname + '_server.csr' }}"
        -subj "{{ '/C=US/ST=WA/L=Seattle/O=MyCompany/CN=' + inventory_hostname }}"

    - name: Fetch CSR from BIG-IP
      fetch:
        src: "{{ csr_path + inventory_hostname + '_server.csr' }}"
        dest: files/
        flat: yes

    - name: Sign CSR on localhost
      command: >
        openssl x509 -req -in "{{ 'files/' + inventory_hostname + '_server.csr' }}"
        -CA /root/servitor_CA.pem -CAkey /root/servitor_CA.key
        -CAcreateserial -out "{{ 'files/' + inventory_hostname + '_server.crt' }}" -days 365
      delegate_to: localhost

    - name: Output signed cert and CA to var
      shell: cat "{{ 'files/' + inventory_hostname + '_server.crt' }}" /root/servitor_CA.pem
      register: certificates
      delegate_to: localhost

    - name: Overwrite BIG-IP server.crt with new signed cert and CA cert
      shell: cat > "{{ crt_path + 'server.crt' }}"
      args:
        stdin: "{{ certificates.stdout }}"

    - name: Restart httpd
      command: tmsh restart sys service httpd
      register: restart_out

    - debug: msg="{{ restart_out.stdout_lines }}"

    - name: Append new certs to own /config/big3d/client.crt and /config/gtm/server.crt
      shell: >
        cat "{{ crt_path + 'server.crt' }}" |
        tee -a /config/big3d/client.crt >>
        /config/gtm/server.crt

Prerequisites

You must meet the following prerequisites to use these procedures:

  • You have Ansible 2.7 or later installed on the control machine.
  • You have BIG-IP 12.x or later installed on the devices in the environment.
  • The OpenSSL package is installed on the control machine.
  • You have a Certificate Authority (CA) certificate and key on the control machine you can use to sign a Certificate Signing Request (CSR).
  • The certificate you sign with the CA includes both the client authentication (clientAuth) and server authentication (serverAuth) extended key usage (EKU) extensions. For more information refer to K7717: BIG-IP DNS and Link Controller support for third-party SSL device certificates.

    Note: For information about the deprecation of clientAuth EKU for public certificates generated by Public Key Infrastructure (PKI) certificate authorities (CA) and what you can do to prepare, you may want to refer to the F5 DevCentral article: The End of ClientAuth EKU…Oh Mercy…What to do?.

  • The Python packages required for each module you want to use on the control machine are installed. For more information, refer to Module Index in the Ansible User Guide.

    Note: This link takes you to a resource outside of AskF5. The third-party could remove the document without our knowledge.

Defining play settings

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to your control machine.
  2. Create a playbook file called update_bigip_device_certificate.yml.
  3. Start composing your playbook YML file and set the hosts to the group of BIG-IP devices you want to configure with a new device certificate, such as bigip_15_dg in the previous example. Gathering system facts is not necessary for this playbook.
  4. In the var parameter, define the file system paths to the device certificates and keys with a variable, such as key_path from the previous example, and so on.

The following is the play settings section from the example playbook showing all the elements described in this procedure:

---
- name: Update BIG-IP Device Certificate
  hosts: bigip_15_dg
  gather_facts: False
  vars:
    key_path: "/etc/httpd/conf/ssl.key/"
    csr_path: "/etc/httpd/conf/ssl.csr/"
    crt_path: "/etc/httpd/conf/ssl.crt/"

Creating a task that backs up the self-signed device certificate files

When replacing the device certificate you overwrite the default self-signed device certificate files, /config/httpd/conf/ssl.crt/server.crt and /config/httpd/conf/ssl.key/server.key. This is the preferred method for compatibility with iQuery communication. If the BIG-IP system is in a BIG-IP DNS environment, or you plan to ever incorporate the BIG-IP into an environment with BIG-IP DNS systems, use the bigip_add script to set up iQuery communication. This utility only looks for the /config/httpd/conf/ssl.crt/server.crt file and ignores any other files. Overwriting the files ensures the utility works as expected. For more information on exchanging certificates refer to the Re-establishing iQuery communication procedure.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Start your list of tasks with the tasks statement.
  2. Create a task that uses the shell module. The example makes use of the Folded Block Scalar, (>) to break up long command lines into multiple lines which makes the playbook easier to read.
  3. Enter a command string that combines two commands with the semicolon (;) to make a copy of both the self-signed device certificate and device key. Using command substitution you can append the Unix epoch time to create a uniquely named file for the original self-signed certificate that won't be overwritten. You can create variables that concatenate the device certificate and key paths variable with the name of the device certificate and key. From the example playbook the source file "{{ crt_path + 'server.crt'}}" becomes /etc/httpd/conf/ssl.crt/server.crt and the copy "{{ crt_path + 'server.crt.'}}"$(date +%s) becomes a file named similar to /etc/httpd/conf/ssl.crt/server.crt.1565637242.

    Note: While the Ansible copy module is idempotent (unchanged in value when multiplied or otherwise operated on by itself), it is not used here because you change the server.crt and server.key files later in the play; therefore, if the playbook is run again, you overwrite the original self-signed certificate.

The following tasks from the example playbook show the elements described in this procedure:

  tasks:

  - name: Backup original server.crt and server.key files
      shell: >
        cp -p "{{ crt_path + 'server.crt'}}" "{{ crt_path + 'server.crt.'}}"$(date +%s);
        cp -p "{{ key_path + 'server.key'}}" "{{ key_path + 'server.key.'}}"$(date +%s)

Creating tasks that generates a CSR and copy it to the control machine

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Create a task that uses the command module with the Folded Block Scalar (>).
  2. Use the OpenSSL command to generate a CSR and private key on the remote BIG-IP. 
    1. For the values of the filename command options, -keyout and -out you can create variables that concatenate the device certificate and key paths with the key name and in the case of the CSR the inventory_hostname variable and the CSR file name. From the example playbook "{{ csr_path + inventory_hostname + '_server.csr' }}" becomes /etc/httpd/conf/ssl.csr/bigip1.example.com_server.csr.
      Note: The Configuration utility does not support an encrypted private key.
    2. For the -subj command option you include all the desired details to make up the distinguished name (DN). Leave the common name (CN) at the end to concatenate with inventory_hostname. The CN should the a fully qualified domain name (FQDN) of the BIG-IP system. You can append the domain name to the end using the concatenation technique if your inventory_hostname does not use FQDNs. From the example playbook "{{ '/C=US/ST=WA/L=Seattle/O=MyCompany/CN=' + inventory_hostname }}" becomes 
      /C=US/ST=WA/L=Seattle/O=MyCompany/CN=bigip1.example.com
      Note: The example omits some details such as email address and organizational unit from the DN.
  3. Create a task that uses the fetch module to retrieve the CSR from the BIG-IP system.
  4. The src can use the same concatenation technique described previously to reference the CSR file on the BIG-IP system while dest is a location on the control machine's file system. In the example we use the files directory that typically resides in an Ansible playbook directory. Include flat: yes to prevent the module from appending the hostname and path to the file name.

The following tasks from the example playbook show the elements described in this procedure:

    - name: Create CSR and private key on BIG-IP
      command: >
        openssl req -new -sha256 -nodes -newkey rsa:2048
        -keyout "{{ key_path + 'server.key' }}"
        -out "{{ csr_path + inventory_hostname + '_server.csr' }}"
        -subj "{{ '/C=US/ST=WA/L=Seattle/O=MyCompany/CN=' + inventory_hostname }}"

    - name: Fetch CSR from BIG-IP
      fetch:
        src: "{{ csr_path + inventory_hostname + '_server.csr' }}"
        dest: files/
        flat: yes

Creating tasks that use a CA to sign the CSR and copy the signed certificate to the BIG-IP system

If you use iQuery in your environment, placing both the new device certificate with the root CA certificate in the /config/httpd/conf/ssl.crt/server.crt file will allow the big3d and gtmd processes to establish a chain of trust when initializing iQuery connectivity.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Create a task that uses the command module with the Folded Block Scalar, (>).
  2. Use the OpenSSL command to sign the CSR obtained from the BIG-IP with the CA certificate and key stored on the control machine. 
    1. For the filename command options, -in and -out you can create a variable using the concatenation method as shown previously.
    2. For the -days option choose the validity period in days for the certificate.
  3. Add delegate_to: localhost so the task is performed on the control machine itself where the CA certificate and key are stored.
  4. Create a task that uses the shell module.
  5. Configure the module to execute the cat utility to output the newly signed device certificate and the CA certificate.
  6. Include register: certificates to store the output from the shell command to a variable called certificates.
  7. Add delegate_to: localhost so the task is performed on the control machine itself where the certificates and are stored.
  8. Create another task that uses the shell module.
  9. Configure the module to execute the cat utility and direct output to the /config/httpd/conf/ssl.crt/server.crt file on the remote BIG-IP system. Use the concatenation technique described previously to reference the CSR file.
  10. Under args, configure the stdin parameter with the contents of the certificates variable you created in the previous task. This will place the contents of the new device certificate and CA certificate to the standard input of the cat utility.

The following tasks from the example playbook show the elements described in this procedure:

    - name: Sign CSR on localhost
      command: >
        openssl x509 -req -in "{{ 'files/' + inventory_hostname + '_server.csr' }}"
        -CA /root/servitor_CA.pem -CAkey /root/servitor_CA.key
        -CAcreateserial -out "{{ 'files/' + inventory_hostname + '_server.crt' }}" -days 365
      delegate_to: localhost

    - name: Output signed cert and CA to var
      shell: cat "{{ 'files/' + inventory_hostname + '_server.crt' }}" /root/servitor_CA.pem
      register: certificates
      delegate_to: localhost

    - name: Overwrite BIG-IP server.crt with new signed cert and CA cert
      shell: cat > "{{ crt_path + 'server.crt' }}"
      args:
        stdin: "{{ certificates.stdout }}"

Creating tasks that restart the httpd process and update the local BIG-IP system trusted certificate store

You restart the BIG-IP system's httpd process so the Configuration utility starts using the new CA-signed certificate. Additionally, it is best practice to add the new certificate and CA certificate to the BIG-IP system's own trusted certificate stores in /config/big3d/client.crt and /config/gtm/server.crt.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Create a task with the command module to restart the BIG-IP system's httpd process with the TMOS shell (tmsh) so the Configuration utility will start using the new CA-signed certificate.
  2. (Optional) Include register: restart_out in the restart task to capture the output of the tmsh restart command.
  3. (Optional) Create a task with the debug module to print restart_out in order to verify that the httpd process was restarted successfully.
  4. Create a task that uses the shell module with the Folded Block Scalar, (>).
  5. Configure the module to execute the cat utility to append the contents of the /config/httpd/conf/ssl.crt/server.crt file to both the /config/big3d/client.crt and /config/gtm/server.crt files using a pipe (|) operator and the tee utility. Use the concatenation technique described previously to reference the certificate file.

The following tasks from the example playbook show the elements described in this procedure:

    - name: Restart httpd
      command: tmsh restart sys service httpd
      register: restart_out

    - debug: msg="{{ restart_out.stdout_lines }}"

    - name: Append new certs to own /config/big3d/client.crt and /config/gtm/server.crt
      shell: >
        cat "{{ crt_path + 'server.crt' }}" |
        tee -a /config/big3d/client.crt >>
        /config/gtm/server.crt

Running the playbook

You can now run the playbook from your control machine to make configuration changes to the BIG-IP devices in the play.

Impact of procedure: Default device certificates are backed up and overwritten. Unless the new device certificates are exchanged, iQuery connectivity between the BIG-IP systems fails upon a reconnect of the long-lived iQuery connection. There is no impact to device services clustering (DSC) features such as traffic groups and device groups. Restarting httpd causes the Configuration utility to temporary become unresponsive. F5 recommends that you perform this procedure during a scheduled maintenance window.

  1. Log in to your control machine.
  2. Change the working directory to the one with your playbooks.
  3. To run the playbook from the command line of your control machine, type the following command:

    ansible-playbook update_bigip_device_certificate.yml

    The output from the command appears similar to the Example playbook output section of this article.

Re-establishing iQuery communication

If you replaced the device certificates on a BIG-IP LTM system that is monitored by a BIG-IP DNS system with iQuery or you have replaced device certificates of BIG-IP DNS systems that are sync group peers, iQuery connectivity between the BIG-IP systems fails upon a reconnect of the long-lived connection. This is due to the new certificate being untrusted; therefore, you must complete the procedures that follow to re-establish iQuery communication with the new certificates in the following order. Otherwise you can skip this procedure.

  • Exchanging device certificates
  • Reinitializing iQuery
  • Verifying iQuery

Exchanging device certificates

You need to use the bigip_add script to exchange the new device certificates between the local system you run the script on and the remote system. The script appends the remote device certificate to the local /config/gtm/server.crt. The local system appends its own device certificate to the remote system's /config/big3d/client.crt file, which may result in a duplicate listing of the certificate if the local system did not have its own device certificates replaced. For more information about bigip_add, refer to ????K13312: Overview of the BIG-IP DNS big3d_install, bigip_add, and gtm_add utilities (11.x - 15.x).

Note: A duplicate certificate does not affect iQuery communication. If you remove a duplicate certificate from the Configuration utility it removes all instances of that certificate and need to be re-installed.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the command line of the BIG-IP system where you want to exchange certificates.
  2. Run bigip_add using the following syntax:

    bigip_add <IP address of remote BIG-IP you want to exchange device certificates with>

    Or

    bigip_add <username>@<IP address of remote BIG-IP you want to exchange device certificates with>

    In the previous syntax, note the following:

     - <username> is a user on the remote BIG-IP system with either the resource administrator or administrator role and has tmsh access enabled. For more information, refer to K14495: The bigip_add and gtm_add scripts now accept a username.

  3. Repeat on any other BIG-IP systems that need to exchange new device certificates.
