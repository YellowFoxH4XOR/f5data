Issue

Note: It is recommended to view the knowledge article shown below as it goes into more depth about VE throughput rate shaping:

          K15831: How the BIG-IP VE system enforces the licensed throughput rate 

Error Message

notice tmm[<PID>]: 01010045:5: Bandwidth utilization is <rate> Mbps, exceeded <percent>% of Licensed <limit> Mbps

In this error message, note the following:

  • <PID> is the process ID for the tmm process.
  • <rate> is the throughput rate in megabits per second that triggered the message generation.
  • <percent> is the percentage of the licensed limit that was exceeded.
  • <limit> is the licensed throughput limit for the system in megabits per second.

For example:

notice tmm[15234]: 01010045:5: Bandwidth utilization is 780 Mbps, exceeded 75% of Licensed 1000 Mbps

Message Location

You may encounter this message in the following location:

  • The /var/log/ltm file

Description

This message is actually a notice, rather an error.  It occurs when ingress traffic throughput rate, averaged over the preceding half second, exceeds a configurable percentage of the maximum licensed throughput rate on the BIG-IP system. The messages of this type complement the throughput graphs that have coarser time resolutions. 

 Note: The threshold percentage for alerting is configurable via sys db log.alertbwthreshold which defaults to 75%. It can be disabled by setting it to 0.  The solution shown below provides guidance on how to modify the value.

         K15377: Configuring the BIG-IP VE system to log a notification when the throughput rate exceeds a configured threshold

Impact

Generally this should be no or low impact - the traffic is shaped to the licensed bandwidth rate usually with no or limited drops.  

It can even occur during a single or low number of concurrent data transfers if they are large enough, even when minute by minute average throughput is low, particularly where the licensed bandwidth is the bottleneck bandwidth on the connection path. TCP will ramp up to use all bandwidth available until it reaches a bottleneck, so this will be seen more on lower tiers of licensed bandwidth such as 25 and 200 Mbps.

There is a trade-off in buffer size between avoiding packet loss in small excess bursts and avoiding excessive latency due to buffering large excess bursts. If traffic arrives at a higher rate than the licensed bandwidth it will be held in buffers, and will be played out from them at the licensed rate. If the situation persists the buffers will build in size, and RED mode will engage to drop some packets to signal congestion to TCP senders. If the situation still persists the buffers will build further, adding to latency and there will eventually be tail drops that will be more impactful.

Recommended Actions

Typically it's more useful to judge bandwidth required from throughput graphs than from these logs. The F5 graphs typically average over longer time periods than the logs, so half second peaks will be smoothed out to a lower value over a longer period of time. The logs can give useful information when read collectively though, and where there is great sensitivity to latency it may be worth considering a higher tier of bandwidth license.
