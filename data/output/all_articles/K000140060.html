K000140060: Connection max limit setting on pool members is being exceeded.

Type
Support Solution
Published
2024-06-20
Updated
2025-02-07
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000140060

Description

A connection limit is configured in a pool where the limit for each server is X amount of connections and it is observed in statistics that this limit is exceeded.

Environment

  • BIG-IP with Clustered Multiprocessing (CMP) enabled
  • Pool and Pool members
  • Connection Limit is configured and this connection limit is less than the available TMMs

Cause

The BIG-IP system divides the configured connection limit by the number of Traffic Management Microkernels (TMMs) that are running on the system and forces the calculated limit to round down to the nearest whole number, per TMM. If the connection limit is not evenly divisible by the number of running TMMs, the remainder (<connection limit> % <number of TMMs>) is distributed, one per TMM, to the lower ordered TMMs.

The problem here is not that TMM is failing to honor the connection limits. Using as example a system with two TMMs present and a connection limit of one connection per node:

1. The BIG-IP system divides the configured connection limit by the number of Traffic Management Microkernels (TMMs), which in this case the result is 0.5.

2. There is no such thing as .5 of a connection, so it gets rounded up to 1. Each TMM is limiting the nodes to a maximum of one connection, so in this case, two connections are allowed instead of the required one.

3. This is why it is generally recommended NOT to have a connection maximum less than the active number of TMM instances. This can lead to unexpected issues if for some reason the disaggregator (DAG) has an uneven connection distribution. For more information, please refer to K8457: Connection limits for a CMP system are enforced per TMM instance (f5.com)

Recommended Actions

Option 1: Pin the Virtual Server to a Single Core with an iRule

This option requires no system changes at all, just a simple iRule using a global variable, as they are not CPM compatible and thus will demote any virtual server to a single TMM, effectively pinning it and solving the problem. The iRule could look something like this:

when RULE_INIT {
 set ::global_pin_tmm
}

Option 2: Pin the Virtual Server to a Single Core with a TMSH Command

Use a TMSH command to pin the virtual server. It’s an option on the virtual server (not available in the GUI) to disable CMP:

tmsh modify ltm virtual <virtual server> cap-enabled no
