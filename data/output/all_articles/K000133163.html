K000133163: istio-proxy logs show "400 DPE http1.codec_error" when using a tool to test TCP connectivity

Type
Support Solution
Published
2023-03-27
Updated
2023-03-27
Applies to
  • Aspen Mesh: 1.14, 1.11, 1.9
Source
https://my.f5.com/manage/s/article/K000133163

Description

Disabling automatic protocol selection or protocol sniffing might cause Istio Sidecar proxy to reject the connection in case the packet payload cannot be decoded according to the protocol configured on Envoy.
The Sidecar will log 400 Error code (400 DPE http1.codec_error) in access logs in such case, Example:

# istio-proxy client logs
[2023-02-07T13:07:16.741Z] "- - HTTP/1.1" 400 DPE http1.codec_error - "-" 0 11 0 - "-" "-" "-" "-" "-" - - 11.21.69.105:9000 11.11.2.4:57032 - -


This can be reproduced by setting HTTP protocol on the Service port name and by sending TCP connection using telnet.

# Service snipped
apiVersion: v1
kind: Service
...
  ports:
  - name: http-svc1
    port: 9000
    protocol: TCP
    targetPort: 9000
bash-5.2# telnet tcp-echo 9000


The proxy Listener times out after some time and logs "400 DPE http1.codec_error" to istio-proxy logs.
 


Environment

  • Aspen Mesh 1.6.x, 1.9.x, 1.11.x
  • Red Hat OpenShift 4.6.x - 4.7.x
  • Kubernetes 1.17.x - 1.20.x



Cause

Packet payload cannot be decoded according to the protocol configured.

 


Recommended Actions

Enable automatic protocol selection by adding the following configuration to the global override values.yaml file and upgrading the istiod Helm chart.:

pilot:
  enableProtocolSniffingForOutbound: true
  enableProtocolSniffingForInbound: true


To upgrade istiod chart please run:

helm upgrade istiod manifests/charts/istio-control/istio-discovery -n istio-system --values <values-file>


When protocol sniffing is enabled we should see additional "default" filterChainMatch in every Listener configuration:

Protocol sniffing enabled

❯ istioctl pc listener -f config_dump_sleep.json --port 443
ADDRESS        PORT MATCH DESTINATION
0.0.0.0        443  Trans: raw_buffer; App: http/1.1,h2c Route: 443
0.0.0.0        443  ALL                                  PassthroughCluster


Protocol sniffing disabled

❯ istioctl pc listener -f config_dump_sleep.json --port 443
ADDRESS        PORT MATCH DESTINATION
0.0.0.0        443  ALL   Route: 443


In case automatic protocol detection is enabled and the protocol cannot be decoded (filter parsing times out) then Envoy will accept that connection with the default filterChainMatch.



Additional Information

Istio sidecars can proxy many different TCP based protocols, including HTTP, HTTPs, gRPC and raw TCP. The full list of all protocols is documented on Istio documentation.
Protocol type can be specified explicitly by specifying the protocol name in Service port name (name: <protocol>-[-<any-suffix>]) or by using appProtocol field (Kubernetes 1.20+).

In case the protocol is not specified, Istio can automatically detect HTTP or TLS protocols; if the protocol cannot be automatically determined then it will be treated as raw TCP.

In Aspen Mesh, due to security reasons, we decided to disable automatic protocol selection or protocol sniffing by default.
Protocol sniffing lessens the configuration burden to get started with Istio, but creates uncertainty about behaviors. Because this uncertainty can't be controlled by the client, it can be surprising or potentially hazardous.

In production we recommend to tell the proxy everything we know about the service and have the proxy reject everything that doesn’t look as expected.
All service ports should be declared with a name that specifies the protocol (things like “http-app” or “tcp-custom”).

Protocol detection should be enabled during mesh evaluation, tests or in very specific use cases.

The protocol sniffing is implemented by TLS and HTTP Inspector Envoy Listener filters.
