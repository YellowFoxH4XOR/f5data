Known Issue

This is the result of a known issue. When a response from an origin web server (OWS) does not contain the Content-Length HTTP header, and the total object size is larger than the maxResponseDataSize parameter, memory usage increases in both the BIG-IP WebAccelerator and TMM until the response is sent to the client. If the BIG-IP WebAccelerator system must process numerous chunked responses for large files, this can result in performance degradation and terminated connections.

The maxResponseDataSize parameter defined in the /config/wa/pvsystem.conf file defines the maximum response size that the BIG-IP WebAccelerator system will process. By default, the value of the maxResponseDataSize parameter is 64MB. When a response from an OWS contains a Content-Length header exceeding the value of maxResponseDataSize, the BIG-IP WebAccelerator system immediately bypasses the pvac process. When a response does not contain a Content-Length header, for example if the OWS responds using chunked transfer encoding, the BIG-IP WebAccelerator buffers the response data in memory. If the size of the response data eventually exceeds the value of the maxResponseDataSize parameter, the BIG-IP WebAccelerator hands off the response to TMM. TMM buffers the remaining response data in memory before serving the object to the client, which can consume considerable memory for large files. The memory buffered by the BIG-IP WebAccelerator and TMM is not released until the full object is served to the client. If this scenario occurs simultaneously for numerous large files, the BIG-IP WebAccelerator performance may degrade due to allocated memory being held while TMM buffers the remaining response.

Additionally, if TMM requires substantial memory to buffer the large files, the adaptive connection reaping feature may activate, which causes the BIG-IP system to terminate connections. When this occurs, log messages similar to the following example appear in the /var/log/ltm file:

local/tmm1 warning tmm1[6241]: 011e0002:4: sweeper_update: aggressive mode activated. (153313/180224 pages   )

Note: For more information about the adaptive connection reaping feature, refer to K5670: Overview of adaptive connection reaping (11.5.3 and earlier).

F5 Product Development is tracking this issue as ID 340417.

Workaround

You can work around this issue by configuring an additional HTTP class to bypass the BIG-IP WebAccelerator for specific content types.
