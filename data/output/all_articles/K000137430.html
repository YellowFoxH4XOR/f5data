K000137430: TLSv1.3 connection is reset by BIG-IP when iRule [SSL::sessionid] is invoked

Type
Support Solution
Published
2023-11-16
Updated
2024-07-03
Source
https://my.f5.com/manage/s/article/K000137430

Description

TLSv1.3 connection is reset by BIG-IP when iRule [SSL::sessionid] is invoked.

TCL error is logged in /var/log/ltm

 

BIGIP.example.com err tmm[18006]: 01220001:3: TCL error: /Common/decrypt-irule <CLIENTSSL_HANDSHAKE> - SSL hudfilter not reached or not in chain (line 1)     invoked from within "SSL::sessionid"

 

Or when iRule uses commands that require [SSL::sessionid] to return a value, a more complex error might be thrown.

For example:
 

BIGIP.example.com. err -c[18030]: 01220001:3: TCL error: /Common/clientssl_example <CLIENTSSL_CLIENTCERT> - wrong # args: should be "session add ssl <key>" while executing "session add ssl [SSL::sessionid] [list [SSL::verify_result] [b64encode [SSL::cert 0]] [X509::serial_number [SSL::cert 0]] ] 7200" invoked from within "if {[SSL::cert count] > 0 } { set cert 1 # Insert the following fields in the session table with a timeout of 7200 seconds: #..."

 

Environment

  • SSL::sessionid in iRule events
  • 15.1.9.1 or above
  • TLS1.3 in requests from client

Cause

ID 1389033

Recommended Actions

You should consider applying one of the following.
 

a) Rewrite the iRule to exclude the use of SSL::sessionid as a key for TLSv1.3 handshakes

b) Disable the use of TLSv1.3.

Additional Information

Despite of ID1389033, it does not remove the necessity to move away from using SSL::sessionid for TLS1.3 connections - the legacy SSL::sessionid returned for TLS1.3 connections is not consistent in the way that it is for earlier versions of TLS.

As per RFC8446: "In TLS 1.2 and below, this functionality was provided by "session IDs" and "session tickets" [RFC5077]. Both mechanisms are obsoleted in TLS 1.3."
