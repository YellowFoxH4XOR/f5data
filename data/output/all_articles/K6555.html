Known Issue

This is the result of a known issue. All FirePass Network Access clients require a DNS name resolution of the FirePass hostname or fully qualified domain name (FQDN) used to log in to the FirePass controller.

In addition to the initial DNS name resolution, one or more DNS name resolutions are required when Network Access is activated. If the IP address returned by the first name resolution belongs to a different FirePass controller than the IP addresses returned in subsequent resolutions, the Network Access connection fails, and produces an Invalid Session ID error.

This error indicates the Network Access client is attempting to connect to a different FirePass than the one which serviced the user's logon. The Network Access client presents session ID credentials that were generated by, and only valid for, the first FirePass controller, to the second FirePass controller. The second FirePass controller rejects the credentials and the connection fails.

When this failure occurs, the BIG-IP GTM has given the Network Access client different answers to its DNS name resolution queries for the FirePass FQDN. By default, BIG-IP GTM performs load balancing by returning different answers (IP addresses) to name resolution queries for the FirePass FQDN (the wide IP in the BIG-IP GTM configuration). Additional configuration for the BIG-IP GTM load balancing algorithm is necessary to ensure that only one IP address is given to the Network Access client in answer to queries for the wide IP.

Note: Some clients may experience this issue while others may not. Many factors may affect the result of the DNS lookup, such as DNS caching by the client operating system, or DNS caching at intermediate devices such as local DNS servers (LDNS) and proxy servers. These caches may prevent all DNS lookups or more than one lookup from reaching the BIG-IP GTM. Therefore, the client will not receive multiple IP addresses for the one FQDN.

F5 Product Development tracked this issue as CR65060 and it was fixed in FirePass version 6.1.0. For information about upgrading, refer to the FirePass release notes.

Additionally, this issue was fixed in cumulative hotfix HF-603-2, issued for FirePass version 6.0.3. You may download this hotfix or later versions of the cumulative hotfix from the F5 Downloads site.

Workaround

To work around this issue, you can perform one of the following procedures, depending upon your system environment:

  • Assign a unique DNS name to the HTTPS Web Service
  • Use BIG-IP GTM persistence records to allow the BIG-IP GTM to return the same IP address over multiple DNS responses
  • Use topology-based load balancing to allow the BIG-IP GTM to return the same IP address over multiple DNS responses

Assigning a unique DNS name to the HTTPS Web Service

For each FirePass controller in the global pool, you can configure the HTTPS Web Service with a unique DNS name, instead of the same DNS name that is configured in the BIG-IP GTM as the wide IP. The BIG-IP GTM uses the same name for DNS and the wide IP. Each HTTP Web Service can use the wide IP name, but the HTTPS URL to redirect to field and Hostname field will be configured using the HTTPS Web Service's unique name.

Clients attempting to log on to the FirePass controllers in the pool will use the wide IP name, connect to the HTTP Web Service, and be redirected to the HTTPS web service's URL, which does not use the wide IP name. Because the HTTPS Web Service has a DNS name that maps to only one IP address in the BIG-IP GTM DNS database, multiple name resolution requests will always receive the same IP address.

Note: If each FirePass controller's SSL server certificate has been generated with the wide IP name, then this method will result in a certificate warning pop-up window in the clients' browsers, due to the difference between the name used in the URL and the certificate name.

To assign a unique DNS name to the HTTPS Web Service, perform the following procedure:

  1. Log in to the FirePass Web Admin UI.
  2. From the menu, click Device Management.
  3. From the submenu, click Configuration.
  4. From the submenu, click Network Configuration.
  5. Click the Web Services tab.
  6. In the Add new service section, configure the following fields:
    • IP - Enter the IP address to which the BIG-IP GTM wide IP maps in the GTM DNS database.
    • Port - Enter the port number on which you run the HTTP (unencrypted) web service (usually port 80).
    • Name - Enter the FQDN used by the BIG-IP GTM wide IP (for example, fp.mycompany.com).
  7. Click the Add New button.
  8. On the Web Service Configuration menu, configure or change the following fields:
    • HTTPS URL to redirect to - Enter an HTTPS URL with the unique FQDN (for example, https://fp1.mycompany.com)
    • User Logon - Select the User Logon check box.
  9. Click the Update button.
  10. Click the Web Services tab.
  11. In the Add new service section, configure the following fields:
    • IP - Enter the same IP address used in configuring the IP field in Step 6.
    • Port - Enter the port number on which you typically run the HTTPS (encrypted) web service (usually port 443).
    • Name - Enter the unique FQDN used in the HTTPS URL to redirect to field, above (for example, fp1.mycompany.com).
    • SSL - Select the SSL check box.
  12. Click the Add New button.
  13. On the Web Service Configuration menu, configure or change the following fields:
    • Certificate - Use the links below this field to add or generate a certificate whose Common Name corresponds to the unique FQDN, if possible. Refer to the Note regarding SSL server certificates, above.
    • User Logon - Select the User Logon check box.
    • Admin Logon - Select the Admin Logon box if you require Admin logons on this Web Service.
  14. Click the Update button.
  15. Click the Web Services tab.
  16. Delete any previous Web Services that the two newly-created Web Services are replacing.
  17. Click the Finalize tab.
  18. Click the Finalize Changes button.
  19. Click the Apply Changes and Restart button.

Repeat this procedure for each FirePass in the load-balanced pool serviced by the wide IP.

Using BIG-IP GTM persistence records

Persistence records use the IP address of the local DNS server that queries the BIG-IP GTM to allow the BIG-IP GTM to return the same IP address over multiple DNS responses. This ensures that the client uses the same server in the global pool.

Note: To configure persistence records for your wide IP, refer to the Configuration Guide for BIG-IP Global Traffic Management.

Note: Persistence records may still fail to solve this issue if the client using Network Access has more than one local DNS server. If the client's DNS requests are sent to different local DNS servers, those DNS requests are then relayed to the BIG-IP GTM with different source IP addresses. The persistence records will be ineffective in the case of different LDNS IP addresses, and the BIG-IP GTM can then return different FirePass controller IP addresses in the DNS response, causing the Network Access client to fail.

Using topology-based load balancing

Topology-based load balancing uses a topology characteristic such as country of origin, top-level domain, or CIDR block of the local DNS server that queries the BIG-IP GTM to allow the BIG-IP GTM to return the same IP address over multiple DNS responses. This ensures that the client uses the same server in the global pool.

If the client's DNS requests are sent to different local DNS servers, then selecting a topology characteristic broad enough to ensure that all of a client's LDNS servers are within that topology will allow the BIG-IP GTM to return the same FirePass controller IP address in its DNS responses.

Note: To configure topology-based load balancing, refer to the Configuration Guide for BIG-IP Global Traffic Manager.
