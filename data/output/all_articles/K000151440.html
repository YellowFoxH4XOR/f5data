Description

When processing HTTP requests with the Content-Type multipart/mixed (commonly used for OData batch requests), BIG-IP ASM may exhibit high CPU consumption, ASM congestion, and violations such as "HTTP Request Body Unparsed Payload" and "Bad multipart parameters parsing." Attack signatures may be triggered in unexpected contexts, and positive security checks (such as allowed/disallowed URLs, methods, or content profiles) may not be enforced on individual sub-requests within the batch. Nested batch requests (e.g., changesets within multipart) are not parsed as separate requests, leading to inefficient processing and potential performance impact.

Environment

  • ASM
  • ODATA Batched Requests

Cause

BIG-IP ASM provides partial support for HTTP multipart batch (OData) requests by parsing boundaries and applying attack signatures to individual sections. However:

  • Positive security checks (such as allowed/disallowed URLs, methods, or content profiles) are only applied to the parent request—not to individual sub-requests inside the multipart batch.
  • Nested batch requests (e.g., changesets within multipart) are processed as a single payload chunk; value signatures are applied to the whole payload rather than parsed per sub-request. This can result in excessive signature processing, high CPU usage, false positives/negatives in detection logic, and overall ASM congestion. This is a product limitation.

Recommended Actions

To avoid performance issues or false positives:

  • In your ASM policy, create a header-based content profile or allowed URL entry for affected endpoints.
  • Match on Content-Type: multipart-mixed* and set Body Handling to "Do nothing" for these specific requests.
