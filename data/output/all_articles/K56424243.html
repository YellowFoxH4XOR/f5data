K56424243: Missing End of Header and End of Stream flag fields in Aspen Mesh Packet Inspector captured transactions

Description

End Headers

End Headers should be set in whichever HTTP/2 frame contains the end of the headers. Typically, there will be only one HEADERS frame from client to server (and it should have End Headers set), and one HEADERS frame from server to client. So, there should be:

  • One End Headers marker on the last (or only) HEADERS frame from the client to server (containing request headers).
  • One End Headers marker on the last (or only) HEADERS frame from the server to the client (containing response headers).

End Stream

End Stream should be set in whichever HTTP/2 frame is the end of the stream direction (request or response). There is:

  • One End Stream marker to end the stream from client to server (containing the request). 
  • One End Stream marker to end the stream from server to client (containing the response).

For information about HTTP/2 specification, refer to rfc7540 (ietf.org).

Typical examples

  • A GET request does not have a body, so the HEADERS frame from the client to server (request headers) should have the End Stream marker.
  • POST, PUT, PATCH and other requests with bodies have a HEADERS frame followed by one or more DATA frames. The last DATA frame (indicating that the request body has been completed) should have the End Stream marker. 
  • Most responses will have bodies (even in error like 502, typically there is a body returned that is the error message), so we would expect a HEADERS frame with End Headers set, and then one or more DATA frames, and the last DATA frame would have End Stream set.
  • Some responses do not have bodies (often 201 Created or 301 Moved Permanently), if we are handling a response without a body, we would expect a HEADERS frame with End Headers and End Stream set.

Environment

This was fixed in Aspen Mesh 1.9.5-am2 and Aspen Mesh 1.6.14-am7 releases. Releases before that were missing these flags in some of the transactions.

Cause

HTTP2 Packets received from the Aspen Mesh Packet Inspector (Pcapper) service of Aspen Mesh do not include the end header flag to indicate the completion of HTTP transaction. This is causing the packet broker tool to mark all transactions received as incomplete packets and drop them without properly processing the performance metrics for it. This is a highly impactful issue for the visibility need of cluster on which the Service Mesh is running.

Using tshark to look at one of the client side transactions. I.e. consumer pcap captured from the Aspen Mesh environment which shows the flag for End header was not set:

tshark -r PCAPPER.pcap -d tcp.port==49663,http2 -Y "frame.number==4" -VP
 Stream: HEADERS, Stream ID: 1, Length 376, POST /<URI>
        Length: 376
        Type: HEADERS (1)
        Flags: 0x00
            00.0 ..0. = Unused: 0x00
            ..0. .... = Priority: False
            .... 0... = Padded: False
            .... .0.. = End Headers: False
            .... ...0 = End Stream: False
        0... .... .... .... .... .... .... .... = Reserved: 0x0

We can see that the End Headers flag was missing in the HEADERS stream. In an analogous manner to the above, if we look at the DATA stream for the HTTP2, you will see that the End Stream flag is not set. This flag is required to indicate the end of a stream for an HTTP transaction.
