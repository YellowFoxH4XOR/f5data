Topic

The NGINX App Protect declarative policy gives you granular control when configuring attack signatures to reduce false positives. Since you can configure attack signature settings at different locations in the security policy, this article describes some of the settings you can use to create policies targeted for your application environment to reduce false positives.

Description

Configuring and optimizing attack signature protection in your App Protect security policy is an administrative task that extends beyond post implementation. The following sections describe the different controls and tools available to assist you to do so:

  • Including and excluding attack signatures
  • Signature settings
  • Overriding attack signatures based on content
  • Using the attack signature report tool

Including and excluding attack signatures

You can include or exclude attack signatures from your security policy in the following settings in the security policy file.

NameDescription
Violations and Threat campaignsAttack signatures can be included when you enable violations. For example, threat campaign violations are contextual information about active attack campaigns that contain high accuracy attack signatures. Due to the specific context of threat campaigns, the probability of false positives is low.
Signature setsAs the name implies, these are sets of attack signatures that you can include. For example: All Signatures, High Accuracy Signatures, Generic Detection Signatures, Generic Detection Signatures (High Accuracy). For a list of signature sets, refer to Signature sets in the NGINX App Protect Configuration Guide.
Server TechnologiesSpecific sets of attack signatures that are relevant to attacks targeted to a specific operating system, application, or server type. For a list of Server Technologies, refer to Available Server Technologies in the NGINX App Protect Configuration Guide.
Individual signaturesAllows you to include or exclude individual signatures granularly based on the signature ID. You can log the ID of a signature by adding the %sig_ids% variable when defining the log format in the app_protect_security_log JSON file.
User defined signaturesAllows you to define your own attack signature sets and signatures specific to your application environment. For more information about creating user-defined signatures, refer to User-defined Signatures in the NGINX App Protect Configuration Guide.

The following example policy includes attack signatures from the threat campaign violation, the high accuracy signature set, a user-defined signature set related to MongoDB, the Python,and Django server technologies, and excludes a specific signature by ID configuration.

Note: For the following user-defined signature set, create a separate JSON file to define your set of signatures and reference it from the nginx.conf file. For more information about creating user-defined signatures, refer to User-defined Signatures in the NGINX App Protect Configuration Guide.

{
   "policy": {
       "name": "policy_name",
       "template": { "name": "POLICY_TEMPLATE_NGINX_BASE" },
       "applicationLanguage": "utf-8",
       "enforcementMode": "blocking",
       "blocking-settings": {
           "violations": [
               {
                   "name": "VIOL_THREAT_CAMPAIGN",
                   "alarm": true,
                   "block": true
               }
           ]
       },

            {
                "name": "High Accuracy Signatures",

            },
            {
                "name": "example_mongodb_signature_set",
                "block": true,
                "alarm": true,

Signature settings

The signature-sets setting currently provides the minimumAccuracyForAutoAddedSignatures attribute to further tune your security policy.

NameValueDescription
Auto-Added signature accuracy (minimumAccuracyForAutoAddedSignatures)
  • Low: Low Accuracy. Also includes medium and high accuracy signatures.
  • Medium: Medium Accuracy. Also includes high accuracy signatures.
  • High: Includes only high accuracy signatures.
This relates to the inclusion of signatures implied as a result of adding Server Technologies to the policy. Including only High Accuracy signatures results in fewer false positives. The value in the default policy is medium.

Overriding attack signatures based on content

For the JSON, XML, gRPC profiles and URL, wildcard parameter, wildcard cookies entities, the attackSignaturesCheck attribute allows you to enable or disable attack signature checking based on content for further granular control. The value of attackSignaturesCheck in the default security policy is true. For more information about the support and use of the attributes for each profile/entity, refer to the NGINX App Protect WAF Declarative Policy.

For example, the following policy sets attackSignaturesCheck to true so that attack signatures and threat campaigns are detected on the specific user-defined URL /marketing and also overriding the security policy settings to enable a specific signature.

{
    "policy": {
            [...]
        },
        "urls": [
            {
                "method": "*",
                "name": "/marketing*",
                "protocol": "http",
                "type": "wildcard",
                "wildcardOrder": 1,
                "attackSignaturesCheck": true,
                "signatureOverrides": [
                    {
                        "enabled": true,
                        "signatureId": 200010008
                    }
                ]
            }
        ]
    }
}

Using the attack signature report tool

Beginning in App Protect 2.3.0, the attack signature report tool enables you to generate reports of attack signatures (default signatures included in the installation package and signatures included in a signature update package). The report is a JSON report file that includes information, such as the risk, accuracy, signature type, and other details of each signature ID that you can use to evaluate whether a signature is a false positive. For more information about the tool, refer to Attack Signature Report Tool in the NGINX App Protect Configuration Guide.

To generate a report named signature-report.json, enter the following command:

/opt/app_protect/bin/get-signatures -o signature-report.json | jq

The command pipes the output to the JSON processor jq, a powerful JSON filter and formatting tool.

Optional jq usage

  • To print the entire report with no filters, use the following command syntax:

jq '.' <report name>.json

To use jq with filters, you may need to edit the JSON report by removing {"signatures": at the beginning of the report and ,"revisionDatetime":"20XX-XX-XXTXX:XX:XXZ"} at the end using a test editor like vi or notepad.

For example:

{"signatures":[{"signatureType":"request","hasCve":false,   [...]   "signatureId":200000001,"isUserDefined":false}],"revisionDatetime":"2019-07-16T04:21:31Z"}

  • To run jq with filters, such as printing only information on the first signature ID or element in the array, use the following command syntax:

jq '.[0]' <report name>.json

For more information about using jq and its installation, refer to the jq documentation.

Recommendations

When configuring attack signatures in App Protect to reduce false positives, you should consider the following factors:

  • Have a good understanding of how attack signatures are added to the security policy, which enables you to implement targeted attack signature protection in your application environment. You should make use of the granular controls that App Protect provides as described in this article.

  • Include only attack signatures required by your applications. Including signatures that are not required consumes resources. For example, if your applications do not run SharePoint or Apache HTTP web server, you should not include them as Server Technologies. However, when in doubt about a signature set, you should include it in the policy.

  • Keep your App Protect attack signature package updated at all times. For more information, refer to Updating App Protect Attack Signatures in the NGINX App Protect Administration Guide.
