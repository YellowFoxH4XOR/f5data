Topic



It has been reported to F5 Networks that various versions of security scanning software may falsely report that the FirePass session ID is not random.

The following sites reference the types of attacks for which the security scans are testing and some of the associated consequences:

http://news.netcraft.com/archives/2003/01/01/security_advisory_2001011_predictable_session_ids.html

http://cookies.lcs.mit.edu/seq_sessionid.html

http://online.securityfocus.com/data/library/SessionIDs.pdf

F5 Networks Product Development has reviewed these concerns and verified that these are false-positive reports.

Ensuring the session is secure

The FirePass controller will set two HTTP cookies during the initial client connection to the FirePass. The cookie names and their values are as follows:

Cookie NameValue
VHOSTstandard
uRoamTestCookieTEST

Some security scanning software will detect these HTTP cookies, and falsely report that the FirePass session ID is not random.

The HTTP cookies VHOST and uRoamTestCookie are not used for session tracking, and actually have the same static contents for all FirePass users.

F5 Networks believes that the current mechanisms in place on the FirePass controller provide sufficient safeguards for securing the session.

Generation of session IDs

The FirePass controller does not actually set a session ID until after the user has been authenticated. As such, unless the security scanner logged into the FirePass controller, the security scanner will not receive a session ID to analyze.

The FirePass controller will provide a session ID to the client browser only after the user has been authenticated.

The FirePass controller uses an HTTP cookie, MRHSession, for session management.

Cookie NameValue
MRHSession<random value>

The session ID value is generated in a proprietary, secure manner. The algorithm that creates the session ID value is not reversible and provides a unique session ID per client. The amount of entropy incorporated into generating a session ID ensures that the same session is not created more than once, and it also ensures that the current and next ID generated will not be predictable.F5 Networks considers the detail of this generation algorithm to be intellectual property and not disclosed.

Other design considerations

In addition to the method used to randomly generate the session ID, other design considerations were included to ensure only the FirePass controller and client will see the MRHSession cookie session ID. The following safeguards ensure a third party will not have access to any of the session IDs in use:

  • The MRHSession cookie is only set after the SSL handshake has been completed, so the session ID is protected from interception with SSL encryption.

  • To ensure the client browser will not send the MRHSession cookie unencrypted, the HTTP header used by the Firepass to set the MRHSession cookie is sent with the secure option, as shown in the following example:

    Set-Cookie: MRHSession=027ae6171a1c134e16a8043adeac2342; path=/; secure

  • The MRHSession cookie is a session cookie which has inherent security properties.

    • Session cookies will expire when the browser session is closed.

    • Session cookies are stored in the client memory and not written to disk, accessing this data would require access to the memory space used by client's account on the host system.

  • Each login to the FirePass will cause a new MRHSession cookie to be created and the new session ID will not be related to the previous session ID.

In order to hijack a session, a malicious party would require access to the MRHSession cookie in the client memory during an active session, at which point the client has already been fully compromised. Subsequent login attempts to the FirePass controller would invalidate the session in memory, rendering the FirePass unusable.
