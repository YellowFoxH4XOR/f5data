Known Issue

The Web Scraping Detection feature may cause connections to be incorrectly reset, or in some cases generate TCL error messages. These issues are described in the following sections:

Web Scraping Detection with standard (non-iRule based) load balancing:

This issue occurs when all of the following conditions are met:

  • Web Scraping Detection is enabled.
  • The Web Scraping Detected violation is set to Block in the security policy Blocking Settings.

When Web Scraping is enabled, the BIG-IP ASM system replies to client requests with an HTTP response that is generated directly by the BIG-IP ASM system and is not a response from the origin web server (OWS). This response generates a second request from the client (an HTTP POST), which is normally then passed to the OWS if it otherwise meets the criteria defined in the security policy. The BIG-IP ASM system may incorrectly terminate this second HTTP request with a TCP reset.

Web Scraping Detection with iRule based load balancing:

Under a separate set of conditions, this issue may cause TCL error messages, but the connection may not be reset. This behavior occurs when all of the following conditions are met:

  • Web Scraping Detection is enabled.
  • The Web Scraping Detected violation is set to Block in the security policy Blocking Settings.
  • A load balancing pool member is selected by an iRule using the HTTP_REQUEST event.

For example, the following iRule makes the load balancing decision in the HTTP_REQUEST event, and would be susceptible to this issue:

when HTTP_REQUEST {
    if { [HTTP::uri] starts_with "/somepath" } {
        pool MyPool member 10.0.0.10 80
    } else {
        pool MyPool member 10.0.0.11 80
    }
}

Impact

Client connections may be reset.

Symptoms

As a result of this issue occurring due to the first set of conditions, you may encounter the following symptoms:

  • After an HTTP GET request has received a response, a subsequent HTTP POST request are terminated by the BIG-IP ASM system with a TCP RST.

As a result of this issue occurring due to the second set of conditions, you may encounter the following symptoms:

  • After an HTTP GET request has received a response, a subsequent HTTP POST request will cause error messages in the /var/log/ltm file that appear similar to the following example:

    01220001:3: TCL error: /Common/MyASM <HTTP_REQUEST> - Address in use (line 5) (line 5) invoked from within "pool MyPool member 10.0.0.11 80"

Workaround

To work around this issue, you can disable Web Scraping Detection Blocking, or redesign the iRule using the LB:detach command, depending on the conditions under which you experience the issue.

Impact of workaround: Web Scraping Detection violations will no longer be blocked. Ensure this is an acceptable change to the security policy for your environment.

Disable Web Scraping Detection Blocking

  1. Log in to the Configuration utility.
  2. Navigate to Application Security > Policy > Policy Properties for the active security policy you want to modify.
  3. From the Blocking menu, select Settings.
  4. Set the blocking mask for the Web Scraping Detection violation to Alarm.
  5. Click Save.
  6. Click Apply Policy.

Using LB:detach in an iRule

Use this workaround if you are using the Web Scraping Detection feature with iRules-based load balancing.

The example iRule shown above can be modified to detach the connection flow before the pool member selection occurs. For example:

when HTTP_REQUEST {
    if { [HTTP::uri] starts_with "/somepath" } {
        LB::detach
        pool MyPool member 10.0.0.10 80
    } else {
        LB::detach
        pool MyPool member 10.0.0.11 80
    }
}
