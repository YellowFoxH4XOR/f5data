K000160654: Terraform Apply Fails with HTTP 400 When Managing F5 Distributed Cloud Resources Due to TLS Inspection

Type
Support Solution
Published
2026-04-07
Updated
2026-06-12
Applies to
  • F5 Distributed Cloud Services
  • F5 Distributed Cloud
Source
https://my.f5.com/manage/s/article/K000160654

Description

When using Terraform (or OpenTofu) with the Volterra provider to manage F5 Distributed Cloud resources, terraform apply fails with an HTTP 400 (Bad Request) error, while terraform plan completes successfully. This occurs regardless of resource type or namespace (shared, default, system). The error persists even with correct permissions and service account configuration. Certificate and password errors produce distinct error messages, confirming authentication credentials are valid.

Environment

  • F5 Distributed Cloud (XC) platform
  • Terraform or OpenTofu
  • Volterra Terraform provider (volterraedge/volterra)
  • API certificate authentication (P12 file)
  • Multiple namespaces tested (shared, default, system)
  • TLS Inspection (SSL interception) present in the network path
  • Direct connection without intermediaries works as expected

Cause

TLS Inspection (SSL interception) on the network path between the Terraform client and the F5 Distributed Cloud API endpoint interferes with certificate-based authentication, resulting in HTTP 400 errors during resource creation.

Answer/Recommended Actions

  1. Identify TLS Inspection:
    Determine if your network path to the F5 Distributed Cloud API endpoint is subject to TLS Inspection or SSL interception by a proxy or security device.
  2. Bypass TLS Inspection for API Traffic:
    Create a bypass rule in your TLS Inspection or proxy device to exclude the F5 Distributed Cloud API endpoint (e.g., https://example.console.ves.volterra.io/api) from inspection.
  3. Test Connectivity:
    After implementing the bypass, re-run terraform apply to confirm that resource creation now succeeds.
  4. Certificate Handling:
    Ensure that the API certificate and password are correct. Incorrect values will produce authentication errors distinct from the HTTP 400 error described here.
  5. Namespace Permissions:
    Confirm that the service account used has the necessary permissions for the target namespace, though this is not the root cause in this scenario.

Additional Information

  • A 302 redirect observed in network logs may indicate the presence of a proxy or TLS Inspection device interfering with the connection.
  • When using a direct connection (no proxy or TLS Inspection), resource creation via Terraform works as expected.
  • This issue is not specific to a particular resource type or namespace; it affects all resource creation attempts via the Volterra provider when TLS Inspection is present.
  • Successful requests (with correct permissions and no TLS Inspection) return HTTP 200.
  • Requests with insufficient permissions (e.g., wrong namespace or missing admin rights) return HTTP 403 (Forbidden).
  • Example Terraform configuration: 
    terraform {
  required_providers {
    volterra = {
      source  = "volterraedge/volterra"
      version = "0.11.48"
    }
  }
}

  api_p12_file = "cert.p12"
  url          = "https://example.console.ves.volterra.io/api"

    rate  = 30.0

  }
