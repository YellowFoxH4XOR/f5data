Description

After changing the management IP address of a tenant hosted on rSeries, failover does not work.

A rebuild of device trust is performed but still, failover does not work.

In /var/log/ltm log, it is showing high availability heartbeat is lost after the tenant management IP address change. For example,

Jul 10 00:00:53 example.tenant notice mcpd[0000]: 010713bc:5: Propose change to management IP address (192.168.1.1/255.255.255.0).
Jul 10 00:00:53 example.tenant notice chmand[0000]: 012a0005:5: mgmtIpDel: deleting IP (192.168.9.9/25), interface (mgmt)
Jul 10 00:00:53 example.tenant notice chmand[0000]: 012a0005:5: mgmtIpAdd: adding IP (192.168.1.1/24), interface (mgmt)
Jul 10 00:00:14 example.tenant warning sod[0000]: 010c0083:4: No failover status messages received for 3.100 seconds, from device example.tenant (192.168.1.1) (unicast: -> 192.168.9.9).
Jul 10 00:00:30 Jul 10 00:00:14 err sod[0000]: 010c003b:3: bind fails on recv_sock_fd addr 192.168.9.9 port 1026 error Cannot assign requested address.

The old IP address is still present after changing the management IP address on a tenant and failover is not working. You may observe Active/Active situation for the same traffic group on different devices.

Environment

  • BIG-IP HA
  • Management IP addresses of tenants are changed
  • rSeries

Cause

The sod (failover) process still holds onto the old management IP address thus causing failover not to work.

Recommended Actions

To identify whether an outdated management-ip address is used, you can find the information by following one or more steps below:

Run the below 'netstat' command from cli and verify if the sod process holds the correct management IP address.

netstat -pan | grep '1026'

The sodlog under the /var/log/sodlog could also indicate the management IP address used when the sod started up, for example:

-- Mgmt --
IP: 192.168.1.2 slot_id: 0 self dev: true
-- Unicast Recv --
L fd=5 on 1.1.1.1:1026
open_fail: 0 udp_ready: true recv_ts: 0

In addition, you may also take traffic capture of the unicast IP address to inspect which management-ip address is used for the HA heartbeat. You may follow the tcpdump similar to the below one:

tcpdump -s0 -ni 0.0:nnn -vw /shared/tmp/place-to-store-the-packet.pcap host <unicast-ip-1> or <unicast-ip-2>

The management IP in the heartbeat packet can be found in the section below:

Frame 000: 334 bytes on wire (2672 bits), 334 bytes captured (2672 bits)
Ethernet II, Src: F5Networ_12:34:56 (14:a9:d0:12:34:56), Dst: F5Networ_54:32:01 (14:a9:d0:54:32:01)
802.1Q Virtual LAN, PRI: 0, DEI: 0, ID: 4094
Internet Protocol Version 4, Src: 192.168.1.1, Dst: 192.168.1.2
User Datagram Protocol, Src Port: 12340, Dst Port: 1026
F5 HA Heartbeat
    Message length: 203 (0x000000cb)
    Sequence number: 54321 (0x0000xxxx)
    Message request ID: 0 (0x00000000)
    Message flags: 0 (0x00000000)
    HA message
        Management address: ::ffff:192.168.9.9
        Management address: 192.168.9.9
        Slot ID: 0x0000
--snipped--

If an old management IP address is seen, restart the sod daemon by:

via TMSH:

tmsh restart sys service sod

or via the Bash shell:

bigstart restart sod
