Topic

The BIG-IP APM logging system has changed between versions. Event logs can be directed to syslog, the internal database, or a log publisher depending on version.

Description

BIG-IP APM 12.0.0 and later

Beginning in BIG-IP APM 12.0.0, log destinations are specified using a log publisher, which can then be associated with multiple access profiles. The default log setting configuration sends BIG-IP APM log events to both the internal database and to syslog by default and is applied automatically when creating an access profile. You can view BIG-IP APM log messages in the /var/log/apm file or by going to System > Logs > Access Policy in the Configuration utility. You can generate reports based on BIG-IP APM session information by going to Access > Overview > Access Reports (13.x and later) or Access Policy > Event Logs (12.x) in the Configuration utility.

BIG-IP APM 11.2.0 through 11.6.x

Starting in BIG-IP APM 11.2.0, the system sends BIG-IP APM log events to both the internal database and to syslog, by default. Additionally, the log.access.syslog database variable is enabled, by default. You can view BIG-IP APM log messages in the Configuration utility, by going to the Reports page (Access Policy > Reports), or in the /var/log/apm file.

BIG-IP APM 11.1.0

Starting in BIG-IP APM 11.1.0, the system directs BIG-IP APM logging events to an internal database. You can no longer view events in the /var/log/apm file or to syslog. You can view BIG-IP APM log messages by going to the Reports screen (Access Policy > Reports) in the Configuration utility.

You can configure the system to send BIG-IP APM log events to syslog so that you can view them in the /var/log/apm file. To do so, you can enable the log.access.syslog database variable by entering the following command:

tmsh modify /sys db log.access.syslog value enable

BIG-IP APM 10.1.0 through 11.0.0

Starting in BIG-IP APM 10.1.0, the system logs BIG-IP APM events to syslog, by default. Syslog logs the events in the /var/log/apm file and (if configured) forward them to remote syslog server destinations.
