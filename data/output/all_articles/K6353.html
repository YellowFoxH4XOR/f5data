Topic

You should consider using this procedure under the following condition:

  • You want to renew the self-signed device certificate on the BIG-IP system

Note: For information about creating a new SSL device certificate and key pair, refer to K9114: Creating a new SSL device certificate and key pair.

Note: For information about installing third party or wildcard certificates, refer to K7717: BIG-IP DNS and Link Controller support for third-party SSL device certificates.

Note: For information about the deprecation of clientAuth EKU for public certificates generated by Public Key Infrastructure (PKI) certificate authorities (CA) and what you can do to prepare, you may want to refer to the F5 DevCentral article: The End of ClientAuth EKU…Oh Mercy…What to do?.

Description

The BIG-IP system uses the device certificate to authenticate access to the Configuration utility and to accommodate device-to-device communication processes, such as configuration synchronization (ConfigSync), big3d, and gtmd.

Note: Starting in BIG-IP 10.2.4 and 11.2.0, the device certificate that ships with the BIG-IP system is valid for 10 years.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You must have access to the Configuration utility or command line of the BIG-IP system.

Procedures

  • Renewing the self-signed device certificate using the Configuration utility

    To watch a video demo of this procedure, go to Renew a self-signed SSL device certificate on the BIG-IP system using the Configuration utility.

  • Renewing the self-signed device certificate using the command line
  • Exchanging the new device certificate (BIG-IP DNS systems in sync groups)

To renew the self-signed device certificate on the BIG-IP system, perform one of the following procedures:

Note: Each F5 device has a unique x509 device certificate that you need to renew independently. This policy applies to standalone systems and redundant pair members.

Renewing the self-signed device certificate using the Configuration utility

Impact of procedure: Renewing the device certificate requires you to reauthenticate if you are using the Configuration utility.

  1. Log in to the Configuration utility.
  2. Go to: System > Certificate Management > Device Certificate Management > Device Certificate.

    Note: In BIG-IP 12.1.2 and earlier, go to System > Device Certificate > Device Certificate.

  3. Select Renew.
  4. For Issuer box, select Self.
  5. For Country, select the appropriate country.

    Important: F5 recommends that you configure a unique Common Name for each BIG-IP DNS synchronization group member. If this is not possible, you must have at least one other field (typically Division) with a unique value for each BIG-IP DNS system in a synchronization group to prevent synchronization issues.

  6. Select Finished.

Renewing the self-signed device certificate using the command line

Impact of procedure: Renewing the device certificate requires you to re-authenticate if you are using the Configuration utility.

Important:  When using the TMOS Shell (tmsh) to update the device certificate and key of a unit that is configured as part of sync-failover device group, make sure that certificate and key names are identical on all the members of sync-failover device group. Mismatched certificate and key names across the sync-failover device group may trigger a config-sync failure event with an error message similar to the following logged to /var/log/ltm on the high availability (HA) peer device after config-sync attempt: SSLCertificateFile: file '/config/httpd/conf/ssl.crt/<certificate_name>.crt' does not exist or is empty.

  1. Log in to the command line.
  2. To change directories to the /config/httpd/conf/ssl.crt directory, type the following command:

    cd /config/httpd/conf/ssl.crt

  3. To convert the server.crt certificate to a certificate signing request .csr, type the following command:

    openssl x509 -x509toreq -in server.crt -out ../ssl.csr/server.csr -signkey ../ssl.key/server.key

    Important: F5 recommends that you configure a unique common name for each BIG-IP DNS system in a synchronization group. If this is not possible, you must have at least one other setting (typically Division) with a unique value for each BIG-IP DNS system in a synchronization group to prevent synchronization issues.

    Alternatively, to configure a unique common name without using the existing server.crt to convert into a certificate signing request, you can use the following command syntax to generate a new server.crt file:

    openssl req -new -x509 -key ../ssl.key/server.key -days <# of days> -out server.crt

    For example, if you want to make the certificate valid for three years, type the following command:

    openssl req -new -x509 -key ../ssl.key/server.key -days 1095 -out server.crt

    The previous command is in interactive mode, and you have to fill in the required fields to generate a new server.crt file. If you have used this method, you can skip step 4 and proceed to step 5.

  4. Using the certificate signing request, specify the number of days for which the new certificate should be valid by using the following syntax:

    openssl x509 -req -in ../ssl.csr/server.csr -signkey ../ssl.key/server.key -days <# of days> -out server.crt

    Replace <# of days> with the number of days in year increments for which you want the certificate to be valid.

    For example, if you want to make the certificate valid for three years, type the following command:

    openssl x509 -req -in ../ssl.csr/server.csr -signkey ../ssl.key/server.key -days 1095 -out server.crt

  5. To restart the web server daemon, type the following command:

    tmsh restart /sys service httpd

  6. To copy the new self-signed certificate to the trusted client and server certificate files, type the following commands:

    cat /config/httpd/conf/ssl.crt/server.crt >> /config/big3d/client.crt
    cat /config/httpd/conf/ssl.crt/server.crt >> /config/gtm/server.crt

    Note: Alternatively, you can add the new certificate to the trusted device certificate file and remove all old certificates by typing the following command:

    cat /config/httpd/conf/ssl.crt/server.crt > /config/big3d/client.crt
    cat /config/httpd/conf/ssl.crt/server.crt > /config/gtm/server.crt

Exchanging the new device certificate (BIG-IP DNS systems in sync groups)

After you renew the BIG-IP device certificate on a BIG-IP system that is monitored using iQuery by BIG-IP DNS or a BIG-IP system that is part of a sync-group, you must make sure that the new certificate is copied to the trusted device certificate store on remote BIG-IP DNS system(s) in the iQuery sync-group. 

For more information about the exchange of certificates with a BIG-IP DNS system, refer to:

  • K43300744: Adding BIG-IP LTM to a network with BIG-IP DNS (13.x - 17.x)

Using the bigip_add command, exchange the new certificate with the other BIG-IP systems in the iQuery mesh. This ensures all devices have updated the certificate in the remote Trusted Server Certificate Store. To do so, perform the following procedure: 

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

Note: Refer to K13312: Overview of the BIG-IP DNS big3d_install, bigip_add, and gtm_add utilities for details regarding the bigip_add command.

  1. Log in, as root user, to the command line of the BIG-IP DNS system that monitors the BIG-IP system you updated the device on.
     
  2. To run the bigip_add script, use the following command syntax:
    bigip_add <BIG-IP_IP_address of the system you updated the device certificate>
  3. You can confirm iQuery has established by entering the following command:
    tmsh show gtm iquery
  4. If the iQuery result continues to display the old certificate, you may have to restart big3d on the remote system and/or gtmd on the local system. 

    Note: Be aware that restarting big3d and/or gtmd causes the iQuery connection to be torn down and re-established and causes iQuery to fail to connect.

    tmsh restart sys service gtmd
    tmsh restart sys service big3d
