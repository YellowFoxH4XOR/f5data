Description

Traffic on one or two interfaces stops responding intermittently, and no increment in drop counters at affected interfaces. Packet captures show only ARP packets are getting processed and other traffic is silently dropped at BIG-IP. Disabling and enabling interface will intermittently fix the issue.

Environment

  • BIG-IP Virtual Edition
  • Interface
  • IP Conflict
  • ARP request and response
  • MAC address

Cause
If more than one device using the same IP address, IP conflict happens. In general, this issue happens when user trying to test the configuration in test environment by replicating the production configuration. 

For example: Testing BIG-IP configuration on physical appliance in VMware test environment which has the same IP-address. 

Recommended Actions

  1. Take captures in non-working device and validate the destination MAC.
     
  2. To take captures on all interfaces by filtering affected interface IP
    # tcpdump -vvv -nnni 0.0:nnnp host <Interface IP address -s0 -w /var/tmp/<filename>.pcap 

    To take captures only on affected interface
    # tcpdump -vvv -nnni <interace>:nnnp -s0 host -w /var/tmp/<filename>.pcap 
     
  3. To check interface MAC address on BIG-IP, run below command, which will also shows the interface statistics like Pkts in, Pkts out, Drops-in, Drops-out and few more.
    # show /net interface all-properties -hidden
     
  4. Verify the MAC address in the packet capture and the interface on affected BIG-IP are same. If the MAC address is different than the BIG-IP interface, this indicates an IP conflict occured. 

Additional Information

The processed ARP request packet in this case will be a unicast packet with Target IP as affected interface IP and Target MAC address will be a different MAC. We expect to see unicast ARP in an attempt to refresh an expired, or expiring, ARP entry, many Client OS's will issue a "targeted" ARP query to the MAC address they already expect. Most of the time, this prompts a response from the intended target and allows the entry to be refreshed without sending a broadcast to the entire network.

RFC 1122 describes this behavior under section "ARP Cache Validation"
An implementation of the Address Resolution Protocol (ARP)[LINK:2] MUST provide a mechanism to flush out-of-date cache entries. If this mechanism involves a timeout, it should be possible to configure the timeout value.

A mechanism to prevent ARP flooding (repeatedly sending an ARP Request for the same IP address, at a high rate) must be included.  The recommended maximum rate is 1 per second per
"Unicast Poll" -- Actively poll the remote host by periodically sending a point-to-point ARP Request to it, and delete the entry if no ARP Reply is received from N successive polls.  Again, the timeout should be on the order of a minute, and typically N is 2.

However, if the other packets comes with a different destination MAC address that will be silently dropped without processing it.
