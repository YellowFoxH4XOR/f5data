Description

If you are using BIG-IQ with more than 1 DCD and you are getting the following message from the DCD:

  • Alert logs are currently not being replicated to other devices. This may be due to having only a single device configured or issues with other devices. To resume replication, either add additional devices or resolve any issues that exist on existing devices.

Environment

  • BIG-IQ CM
  • More than one BIG-IQ DCD 

Cause

You might have unassigned replica(s) shard.

Recommended Actions

Force elasticsearch to retry the allocation of that shard.

  1. Check the elasticsearch status and if there is any unassigned shard from CM, run the following commands:

     curl -s -u admin:admin --insecure https://localhost:9200/_cluster/health?pretty 
    {
      "cluster_name" : "7d7c2bdf-3fda-402f-ac07-d12edfed0012",
      "status" : "yellow",
      "timed_out" : false,
      "number_of_nodes" : 5,
      "number_of_data_nodes" : 4,
      "active_primary_shards" : 1662,
      "active_shards" : 3325,
      "relocating_shards" : 0,
      "initializing_shards" : 0,
      "unassigned_shards" : 1,
      "delayed_unassigned_shards" : 0,
      "number_of_pending_tasks" : 0,
      "number_of_in_flight_fetch" : 0,
      "task_max_waiting_in_queue_millis" : 0,
      "active_shards_percent_as_number" : 99.96993385447985
    }

    curl -s -u admin:admin --insecure https://localhost:9200/_cat/shards?v  |  grep 'UNASSIGNED'
    access-event-logs_2022-02-22t00-00-00-0600          2     p      STARTED         0    261b 10.252.61.33  b92e3d94-f6b7-4d2c-ae51-e4bf248d36e4
    access-event-logs_2022-02-22t00-00-00-0600          1     p      STARTED         0    261b 10.252.61.33  b92e3d94-f6b7-4d2c-ae51-e4bf248d36e4
    access-event-logs_2022-02-22t00-00-00-0600          1     r      UNASSIGNED                              
    access-event-logs_2022-02-22t00-00-00-0600          3     r      STARTED         0    261b 10.252.61.32  966e8491-2107-41b9-a6a5-bd23dfc86743
    access-event-logs_2022-02-22t00-00-00-0600          3     p      STARTED         0    261b 10.252.61.33  b92e3d94-f6b7-4d2c-ae51-e4bf248d36e4
     
  2. Force elasticsearch to retry the allocation of that shard:

    curl -skX POST https://localhost:9200/_cluster/reroute?retry_failed=true
     
  3. If that doesn't resolve this, use the following command to get more information (use /var/tmp/bigiqdiags/bigiq_diagnostics.txt to find the UNASSIGNED shard):

    curl -skX GET https://localhost:9200/_cluster/allocation/explain?pretty -d '{"index":"access-event-logs_2022-02-22t00-00-00-0600", "shard":1, "primary":false}'
     
  4. Worst case scenario is we tell elasticsearch to remove the replicas for that index and create them again:

    curl -skX PUT https://localhost:9200/access-event-logs_2022-02-22t00-00-00-0600/_settings -d '{"index":{"number_of_replicas":0}}'

    curl -skX PUT https://localhost:9200/access-event-logs_2022-02-22t00-00-00-0600/_settings -d '{"index":{"number_of_replicas":1}}'
