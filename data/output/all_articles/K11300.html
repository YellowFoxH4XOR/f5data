Known Issue

This is the result of a known issue. TMM does not update connection table entries on route changes.

When a new connection arrives for the BIG-IP system to process, TMM adds an entry into the connection table. Each entry in the connection table records several information, including but not limited to:

  • The clientside source IP address and port
  • The clientside destination IP address and port
  • The serverside source IP address and port
  • The serverside destination IP address and port
  • The protocol used by the connection (ICMP, TCP, UDP, etc.)
  • How long the connection has been idle and the idle timeout
  • The lasthop VLAN and MAC address

Once an entry is in the connection table, TMM matches any additional traffic from the client with the entry in the connection table and sends the traffic to the already selected pool member.

The issue described in this Solution causes connection table entries not to be re-evaluated and updated in the event of a change in the BIG-IP system routing table. As a result, it is possible for TMM to continue to send traffic to a destination which is now incorrect based on old information in the connection table.

Consider the following example:

  • A BIG-IP system is configured with a VLAN, a default gateway, and a forwarding virtual server.
  • A monitoring station is installed on the same VLAN as the BIG-IP system.
  • The monitoring station is configured to reach a server in a different subnet through the BIG-IP system.
  • The monitoring station begins to check the availability of the server and the monitoring traffic reaches the BIG-IP system.
  • Because the BIG-IP system is not directly connected to the subnet that the monitoring station is trying to reach, the BIG-IP system forwards the traffic to its default gateway. At this time, an entry is also added to the connection table.
  • For the purpose of this example we will suppose that the BIG-IP system’s default gateway cannot reach that particular subnet either, therefore the monitoring station marks the server as down.
  • The monitoring station continues to send monitoring traffic on a periodic basis such that the connection table entry never reaches its idle timeout.
  • At this point the BIG-IP system is configured with a second VLAN, which allows it to reach the monitored server directly. This action results in a new entry in the BIG-IP system routing table.
  • However, TMM does not update the existing entries in the connection table, therefore the traffic continues to be sent to default gateway rather than to the local network. This causes the monitoring station to continue to mark the server as down even though the BIG-IP system is now configured correctly and is able to reach the monitored server.

F5 Product Development tracked this issue as CR75149 and it was fixed in BIG-IP version 9.4.0. For information about upgrading, refer to the BIG-IP LTM, ASM, or Link Controller release notes.

Workaround

In order to resolve this issue, you must delete the connection table entry which has become invalid.

If the BIG-IP system is not in production or you are in a maintenance window, you can simply delete all entries from the connection table by running the following command:

bigpipe conn all delete

Otherwise, you can delete all connection table entries between two specific hosts by running the following command:

bigpipe conn client <client IP> server <server IP> delete

For example:

bigpipe conn client 192.168.1.1 server 10.0.0.100 delete
