K000162086: ASM Blocked Streaming API (SSE) Connections with Reset, Due to Incomplete Chunked Response

Type
Support Solution
Published
2026-07-06
Updated
2026-09-30
Applies to
  • BIG-IP
  • BIG-IP ASM: 17.0.0, 17.1.0, 17.0.X, 17.X.X, 17.5.X, 17.5.1, 17.5.0, 17.1.X, 17.1.3, 17.1.2, 17.1.1
Source
https://my.f5.com/manage/s/article/K000162086

Description

When using BIG-IP ASM (Application Security Manager) in front of a streaming API endpoint that utilizes Server-Sent Events (SSE), with 'Content-Type: text/event-stream', connections may be reset by ASM with the message "Incomplete chunked response". This occurs even though no ASM violations or blocking events are logged. The issue is observed when the backend server sends chunked HTTP responses without the required terminating chunk (0\r\n\r\n), which is standard behavior for SSE streams designed to keep connections open for real-time data delivery.

Environment

  • Product: BIG-IP ASM (Application Security Manager)
  • ASM policy in blocking mode attached to the affected virtual server
  • Streaming API endpoint using SSE (Content-Type: text/event-stream)
  • Backend server sends chunked responses without a terminating chunk
  • ASM response inspection features (e.g., Server Technologies, Attack Signatures in Response) may be enabled

Cause

The incompatibility between BIG-IP ASM response inspection features and the SSE protocol. ASM expects a normal terminating chunk (0\r\n\r\n) in HTTP chunked responses to complete inspection, but SSE streams intentionally omit this to keep the connection open. This causes ASM to reset the connection, interrupting the stream. 

Answer/Recommended Actions

To address this issue, consider the following options in order of lowest to highest risk:

Important: It's always recommended to perform this activity and test the results under a planned MW to avoid any unexpected service disruption.

 

1- Modify Backend Server Response Behavior (Lowest Risk):

Adjust the backend server to send the required HTTP chunked terminator (0\r\n\r\n) for streaming/SSE responses. This allows ASM to fully inspect and protect the traffic, maintaining all security features.

Note: This may not be feasible for SSE, as the protocol is designed to keep the connection open. As a side note, changing / replacing 'SSE' to 'WSS' would also revolve the Issue.

 

2- Use a Separate ASM Policy for Streaming API (Low Risk):

Create a dedicated ASM policy for the streaming/SSE endpoint with all response inspection features (such as Server Technologies, Attack Signatures in Response, Data Guard, etc.) disabled. Assign this policy only to the streaming API using a Local Traffic Policy or iRule.

This approach keeps full protection for other URLs. Below is an Example iRule for your reference, you need to modify based on your desired SSE endpoint URL:

when HTTP_REQUEST {
  if { [HTTP::uri] starts_with "/your_streaming_api_path" } {
    ASM::policy "/StreamingAPI-Policy"
  } else {
    ASM::policy "/Default-ASM-Policy"
  }
}

 

3- Disable ASM Response Inspection Features for All Traffic (Moderate Risk):

Globally disable response inspection features in the ASM policy. This increases the risk surface for all traffic. Below is the list of ASM's response inspection features which can lead to this conflict, as per K19905853:

  • Learn from Responses
  • Data Guard
  • Response Attack Signatures
  • Dynamic Parameter Extractions
  • Login Page Detection
  • Server Technologies
  • Dynamic Session ID in URL

 

4- Use an iRule to Selectively Bypass ASM for Streaming/SSE API (Highest Risk):

Apply an iRule to the virtual server to disable ASM for requests matching the streaming/SSE API URL. Below is a sample iRule script for your reference, which you need to revise as desired in your scenario: 

when HTTP_REQUEST {
  if { [HTTP::uri] starts_with "/your_streaming_api_path" } {
    ASM::disable
  }
}

Important: This removes all WAF protection for the streaming API endpoint, and you need to be cautious using this option.
Note: Disabling HTTP response buffering or applying an SSE profile at the LTM layer does not resolve this issue if ASM response inspection features are enabled, as ASM will still require full response buffering.

Additional Information

  • This is expected behavior due to the design of ASM response inspection features and the SSE protocol.
  • Version 21.1.0 introduced SSE support for ASM/AWAF. 
  • The recommended approach is to either adjust the backend to send the required terminator (if possible), disable response inspection features for the streaming endpoint, or bypass ASM for that endpoint.
  • Simply disabling HTTP buffering or using an SSE profile at the LTM layer will not resolve the issue if ASM response inspection is active.
