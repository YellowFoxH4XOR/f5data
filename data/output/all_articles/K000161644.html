K000161644: APM: OCSP Auth agent: Failure status 'Cert serial number 18446744073709551615 status is unknown'

Description

When using a BIG-IP APM access policy that includes Client Certificate Inspection followed by an OCSP Auth agent, some connections intermittently fail with the following error, even though the same certificate succeeds on other attempts:

  • Error message:

    OCSP Auth agent: Failure status 'Cert serial number 18446744073709551615 status is unknown'

Key observations:

  • APM logs show the correct certificate serial number at the Client Certificate Inspection stage for both successful and failed sessions.
  • Packet captures of OCSP requests sent from the BIG-IP confirm the correct certificate serial number is being used in the OCSP request — the corrupted serial does not appear in the wire traffic.
  • The OCSP responder itself returns a certStatus: unknown (2) response for the failing attempts, which is the direct source of the APM failure log entry.
  • Successful attempts return certStatus: good (0) from a different OCSP responder (identifiable by a different responderID / commonName in the response).

Environment

  • Product: BIG-IP APM
  • Version: 17.5.1
  • APM Policy components:
    • Client Certificate Inspection agent
    • OCSP Auth agent
  • OCSP configuration:

    apm aaa ocsp /Common/test {

        ca-file /Common/test.crt

        chain false

        ignore-aia true

        url http://X.X.X.X:YYYY/test/ocsp

        verify false

        verify-cert false

    }

  • The OCSP URL (http://x.x.x.x:yyyy/test/ocsp) configured in the APM OCSP object points to a Virtual Server (VS) on another BIG-IP, which load-balances requests across multiple backend OCSP responders.
  • The backend OCSP responders behind the VS are not identical — they return different responderID values and different certificate statuses for the same certificate serial number.

Cause

The root cause is not within BIG-IP APM itself. The intermittent failures are caused by the OCSP Virtual Server (acting as a load balancer for OCSP responders) routing requests to a backend OCSP responder that returns a certStatus: unknown response for the certificate in question.

  • Different backend OCSP responders behind the load-balancing VS have inconsistent certificate status data — one returns good, another returns unknown for the same certificate serial number.
  • The intermittent nature of the failures is explained by load balancing decisions directing some requests to the misbehaving OCSP responder.

Answer/Recommended Actions

  1. Identify the inconsistent OCSP responder by examining the responderID field (specifically the commonName) in OCSP responses captured via packet capture:
    • Failing responses will show a different commonName in the responderID than successful responses.
    • Compare the BasicOCSPResponse > tbsResponseData > responderID > byName field across failing and successful OCSP responses.
  2. Investigate the backend OCSP servers behind the load-balancing Virtual Server to determine why one or more responders are returning certStatus: unknown for valid certificates.
  3. Verify certificate status consistency across all backend OCSP responders — ensure all responders have up-to-date and consistent certificate revocation data.
  4. Review load balancing configuration on the OCSP Virtual Server to consider temporarily removing or isolating the misbehaving OCSP responder while the inconsistency is investigated.
  5. Confirm resolution by re-running packet captures and verifying that all OCSP responses return certStatus: good (0) for valid client certificates.
