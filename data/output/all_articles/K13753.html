Topic

This article applies to BIG-IP 9.4.x through 11.3.0. For information about other versions, refer to the following article:

  • K15097: Using the Local Traffic Policies feature to load balance HTTP requests to multiple pools

You can associate multiple HTTP class profiles with a virtual server to load balance HTTP requests to different pools, depending on the attributes of the traffic. For example, you can load balance individual HTTP requests to different pools based on the URI path, HTTP headers, cookies, or other request attributes. However, the existing server-side connection must first be detached in order to support proper pool reselection mid-connection, such as supporting multiple HTTP requests arriving on the same Keep-Alive connection. If no conditions resulting in pool selection match the request, failure to detach from the existing server-side connection may result in an unexpected choice for the default pool. You can ensure that the existing server-side connection is detached by following one of the following two recommendations:

  • Applying a OneConnect profile to the virtual server
  • Creating a catch-all HTTP class profile with the default pool of the virtual server

    With a selective HTTP class profile in place, specified criteria is matched and those requests are sent to the pool specified by the HTTP class profile. All other requests are matched by the catch-all HTTP class profile, which forwards the requests to the virtual server default pool and forces the new load balancing decision in this scenario.

Note: For information about using iRules to load balance to multiple pools for virtual servers not using OneConnect, refer to K9800: Using an iRule to load balance HTTP requests to multiple pools.

Default pool selection for virtual servers using OneConnect

With a OneConnect profile applied, the server-side connection is always detached upon completion of the server response, and the default pool selection is reset for each request to match the default pool configured on the virtual server. As a result, pool reselection using an HTTP class applied to a OneConnect virtual server operates as expected:

  • Requests matching the pool selection conditions coded in an HTTP class are always sent to the indicated pool.
  • Requests not matching any pool selection condition in an HTTP class are always sent to the default pool configured on the virtual server, regardless of whether a pool was already selected for a previous request on the same connection.

Note: If your application relies on the actual client IP address to provide functionality, you may need to configure a custom OneConnect profile using a Source Mask of 255.255.255.255. For more information, refer to K7208: Overview of the OneConnect profile.

When a client connects to a OneConnect virtual server that uses HTTP classes for pool selection, a pool is selected based on the attributes of each request and the coded HTTP class conditions. If a condition resulting in pool selection matches the request, the request is sent to the selected pool. If multiple conditions resulting in pool selections match the request, the request is sent to the pool selected in the last matching condition. If no HTTP class condition resulting in a pool selection matches the request, the request is sent to the default pool that is configured on the virtual server.

For example, using the following HTTP class, requests for /foo/bar/index.html will always be sent to the pool foo_pool, while requests for /login will always be sent to the default pool configured on the virtual server:

ltm profile httpclass foo {
app-service none
defaults-from httpclass
paths { glob:/foo* }
pool foo_pool
redirect none
}

Default pool selection for virtual servers not using OneConnect

Without a OneConnect profile applied, the server-side connection is only detached if a new pool is explicitly selected. The default pool selection is not reset to match the default pool configured on the virtual server for subsequent requests on the same connection. Therefore, the default pool defined on the virtual server is only used as the default selection for initial requests that do not match any of the pool selection conditions (never for subsequent requests). As a result, pool reselection using an HTTP class applied to a non-OneConnect virtual server does not always operate as expected:

  • Initial and subsequent requests matching the pool selection conditions coded in an HTTP class are always sent to the indicated pool.
  • Initial requests not matching any pool selection condition in an HTTP class are always sent to the default pool configured on the virtual server.
  • Subsequent requests not matching any pool selection condition in an HTTP class are always sent to the last pool selected for this connection.

Initial pool selection

Initial pool selection for new connections to a non-OneConnect virtual server is the same as that for a OneConnect virtual server. When a client connects to a non-OneConnect virtual server that uses an HTTP class for pool selection, a pool is selected based on the attributes of the first request and the coded HTTP class conditions. If a condition resulting in pool selection matches the request, the request will be sent to the selected pool. If multiple conditions resulting in pool selections match the request, the request will be sent to the pool selected in the first matching condition. If no HTTP class condition resulting in a pool selection matches the request, the request will be sent to the default pool that is configured on the virtual server.

For example, using the above HTTP class example, a new connection containing a request for /foo/bar/index.html will always be sent to the pool foo_pool, while a new connection containing a request for /login will always be sent to the default pool configured on the virtual server.

Subsequent pool selection

Pool selection for subsequent requests on a Keep-Alive connection to a non-OneConnect virtual server is different from that for a OneConnect virtual server. When a subsequent request arrives on a client connection for which a pool has already been chosen, a new pool may be selected based on the attributes of the subsequent request and an HTTP class condition. As with the initial request, if a condition resulting in pool selection matches the request, the request is sent to the newly selected pool. If multiple conditions resulting in pool selections match the request, the connection is sent to the pool selected in the first matching condition. However, if no HTTP class condition resulting in a pool selection matches the request, the request is not sent to the default pool that is configured on the virtual server. Instead, the request is sent to the pool that was selected for the previous request on the same connection.

For example, using the HTTP class example, a new connection containing a request for /foo/bar/index.html on a Keep-Alive connection will be sent to the pool foo_pool, and a subsequent request for /profile.php on the same connection will also be sent to the pool foo_pool, even though the attributes of the requests do not match the condition choosing the pool foo_pool.

To ensure that subsequent requests are sent to the expected pool on a non-OneConnect virtual server, a catch-all HTTP class profile needs to be configured. All requests not matching a prior HTTP class are matched by the catch-all HTTP class profile, which forwards the requests to the virtual server default pool.

For example, using the following HTTP classes and virtual server HTTP class order, any requests not matching the foo HTTP class will match the catch_all HTTP class and be sent to the default_pool as expected for the virtual server. As a result, pool reselection using the catch-all HTTP class applied to a non-OneConnect virtual server will operate as expected:

ltm profile httpclass foo {

app-service none
defaults-from httpclass
paths { glob:/foo* }
pool foo_pool
redirect none
}

ltm profile httpclass catch_all {
app-service none
defaults-from httpclass
paths none
pool default_pool
redirect none
}

ltm virtual http_vs {
destination 10.11.10.212:http
http-class {
httpclass1
catch_all
}
ip-protocol tcp
mask 255.255.255.255
pool http_pool
profiles {
http { }
tcp { }
}
snat automap
vlans-disabled
}

When the catch-all HTTP class profile is applied to a non-OneConnect virtual server, a new connection that contains a request for /foo/bar/index.html on a Keep-Alive connection is sent to the pool foo_pool, and a subsequent request for /profile.php on the same connection is sent to the pool default_pool.
