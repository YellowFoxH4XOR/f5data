K000162385: F5 CIS Operator v1.23.0 on OpenShift Applies Hardcoded securityContext Values Despite Empty F5BigIpCtlr CR

Support Solution
Published
2026-07-23

2026-07-23
Applies to

Description

When using F5 Container Ingress Services (CIS) operator bundle v1.23.0 installed via Red Hat OperatorHub on OpenShift, the CIS controller deployment managed by the `F5BigIpCtlr` CRD always applies hardcoded security context values even when `spec.securityContext` is left empty, set to `{}`, or set to `null` in the `F5BigIpCtlr` resource:

oc -n <namespace> get deploy/<deployment-name> -o jsonpath='{.spec.template.spec.securityContext}' | jq .

{

 "fsGroup": 1000,

 "runAsGroup": 1000,

 "runAsUser": 1000

}

The expected behavior is for the deployment to have no hardcoded security context, allowing OpenShift's Security Context Constraints (SCC) to assign the pod identity automatically — which was the behavior in previous operator versions.

Environment

- Red Hat OpenShift

- F5 Container Ingress Services (CIS) version 2.20.4

- F5 CIS operator bundle v1.23.0 installed via OperatorHub (fresh install or upgrade)

- `F5BigIpCtlr` CR with `spec.securityContext` empty, null, or not defined

Cause

The CIS operator Helm chart (`f5-bigip-ctlr-deploy.yaml`) uses the presence of a marker file `oscp-operator.txt` to detect whether it is running on OpenShift:

{{- $oscpOperator := .Files.Glob "oscp-operator.txt" }}

{{- if $securityContext.runAsUser }}

 runAsUser: {{ $securityContext.runAsUser }}

{{- else if (not $oscpOperator) }}

 runAsUser: 1000

{{- end }}

 

The same logic applies to `runAsGroup` and `fsGroup`. When the file is present, the chart skips the hardcoded values and allows OpenShift SCC to assign the pod identity. When the file is absent, the chart falls back to `1000` for all three fields.

The file `oscp-operator.txt` was omitted from the published operator bundle v1.23.0 due to a packaging defect. This caused the OpenShift detection logic to fail, resulting in hardcoded security context values being applied regardless of the `F5BigIpCtlr` CR configuration.

You can confirm the issue by checking the contents of the Helm chart directory inside the operator controller pod:

Affected (v1.23.0) — file missing:

oc -n openshift-operators exec -it <operator-controller-manager-pod> -- ls helm-charts/f5-bigip-ctlr

Chart.yaml README.md templates values.yaml

Fixed (v1.23.1) — file present:

oc -n openshift-operators exec -it <operator-controller-manager-pod> -- ls helm-charts/f5-bigip-ctlr

Chart.yaml README.md oscp-operator.txt templates values.yaml

Answer/Recommended Actions

Upgrade the F5 CIS operator bundle from v1.23.0 to v1.23.1, which restores `oscp-operator.txt` and resolves the issue.

 

Important: The direct upgrade to v1.23.1 may not trigger automatically via OperatorHub. This is because OpenShift OLM follows a strict upgrade graph — if a valid upgrade path between the installed version and v1.23.1 is not defined in the catalog, OLM will not generate a new InstallPlan even with Automatic approval and a Healthy CatalogSource. Use the following manual procedure:

 

⚠️ Perform during a maintenance window. The operator pod will restart. Existing BIG-IP objects and `F5BigIpCtlr` custom resources will not be affected.

 

Step 1 — Note the current CSV name:

oc get csv -n openshift-operators | grep f5

Step 2 — Backup the existing subscription:

oc get subscription f5-bigip-ctlr-operator -n openshift-operators -o yaml > f5-operator-subscription-backup.yaml

Step 3 — Delete the Subscription:

oc delete subscription f5-bigip-ctlr-operator -n openshift-operators

Step 4 — Delete the old CSV (use the name from Step 1):

oc delete csv f5-bigip-ctlr-operator.v1.23.0 -n openshift-operators

Step 5 — Wait ~30 seconds** to allow OLM controllers to fully process the deletion.

Step 6 — Recreate the Subscription targeting v1.23.1:

cat <<EOF | oc apply -f -

apiVersion: operators.coreos.com/v1alpha1

kind: Subscription

metadata:

 name: f5-bigip-ctlr-operator

 namespace: openshift-operators

spec:

 channel: stable

 name: f5-bigip-ctlr-operator

 source: certified-operators

 sourceNamespace: openshift-marketplace

 startingCSV: f5-bigip-ctlr-operator.v1.23.1

 installPlanApproval: Manual

EOF

Step 7 — Approve the generated InstallPlan:

oc get installplan -n openshift-operators

oc patch installplan <installplan-name> -n openshift-operators --type merge --patch '{"spec":{"approved":true}}'

Step 8 — Verify the fix:

# Confirm new CSV reached Succeeded

oc get csv -n openshift-operators | grep f5

# Confirm oscp-operator.txt is present

oc -n openshift-operators exec -it $(oc -n openshift-operators get pod -l name=f5-bigip-ctlr-operator -o jsonpath='{.items[0].metadata.name}') -- ls helm-charts/f5-bigip-ctlr

# Confirm securityContext is no longer hardcoded

oc -n <cis-namespace> get deploy/<cis-deployment-name> -o jsonpath='{.spec.template.spec.securityContext}' | jq .

 

The last command should return `{}` when no `securityContext` is defined in the `F5BigIpCtlr` CR, confirming OpenShift SCC is now managing the pod identity.

Additional Information

- This issue affects fresh installations of operator bundle v1.23.0 as well as upgrades to v1.23.0.

- Operator bundle versioning is independent of CIS versioning. CIS 2.20.4 is paired with operator bundle v1.21.0 at GA; v1.23.x bundles are subsequent operator releases.

- The `F5BigIpCtlr` custom resources are not deleted when recreating the OLM subscription — the operator reconciles them automatically after reinstallation.

- If your SCC policy permits `runAsUser/runAsGroup/fsGroup: 1000`, an interim workaround is to explicitly set these values in the `F5BigIpCtlr` CR to prevent reconciliation conflicts while awaiting the upgrade.
