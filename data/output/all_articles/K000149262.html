Description

Symptoms

  1. /var space exhaustion
  2. Slow or inconsistent runtimes for tasks such as "Importing" or "Applying" policies
  3. Prolonged upgrade time

Potential Results

  1. May result in configuration corruption in bd memory causes include but not limited to; false positives, inaccurate or unexpected blocking behavior
  2. asm_config_server core events
  3. asm_config_server rpc handler processes may cycle quickly
  4. Other processes may be unable to write to /var resulting in other unexpected behavior

Cause

Prior to BIG-IP 17.x, the process of updating the configuration in bd relied on the bd_agent process. To align with other bd dependent products BIG-IP 17.x has moved to using the manifest generation process. The manifest generation process compiles the configuration and writes the results to an incrementing manifest generation version folder under "/ts/files/site_{site_id}/config/", where site_id is often "1" unless configured otherwise. The manifest generation to the incrementing version folder can consume /var during heavy change times such as automated configuration changes or on devices with larger configurations. A large configuration is not simply the number of policies. Policies with large numbers of objects can contribute to the size of a manifest generation version.

Under the manifest generation method the asm_config_sync_rpc_handler processes require significantly more memory to fully process an update from the generation. Currently there is a max memory limit for asm_config_server_rpc_handler processes, 200,000,000 bytes (~191MB) which causes the process to write out the current state of unprocessed memory and any outstanding calls to disk. Then start a new process, which reads in the prior state and outstanding calls. With large configurations this process can cause the asm_config_sync_rpc_handler processes to perform the shutdown/spawn cycle frequently. At times this can introduce significant time into task completion as the task must wait for these processes to perform the shutdown/spawn cycle before continuing. Potentially multiple times during the manifest generation update process for larger configurations.

Recommended Actions

Workarounds

Space exhaustion prevention for /var volume:

Bug 1694693 "Var exhaustion due to the files in /var/ts/files/site_1/config"

    • Reduces runtime of internal tasks and the number of previous versions filling /var during manifest generation.

Extending the /var volume prior to boot into new volume can also help mitigate space concerns.

 

Task runtime improvement - reduce asm_config_server_rpc_handler cycling.

  1. Edit /etc/ts/tools/asm_config_server.cfg
    vim /etc/ts/tools/asm_config_server.cfg

  2. Add a line to increase the "AsyncMaxMemorySize" threshold
    Example sets the limit to 500MB:
                   AsyncMaxMemorySize=524288000
        *To ensure a single process handles a manifest generation update the limit may require a much larger size. Ensure there is enough host memory resources before increasing the variable and monitor the device memory following the change.

  3. Save and exit
    :wq!

  4. Restart the asm_config_server processes
    pkill -f asm_config_serv

  5. Monitor the host memory as increasing the limit allows a single process to consume more memory. The following articles provide an overview of the different types of memory on the BIG-IP system as well as how to interpret the results from the top command:
    • K16419: Overview of BIG-IP memory usage
    • K16739: Understanding 'top' output on the BIG-IP system

Important: Changes to this file do not survive upgrade

Changes to flat files such as /etc/ts/tools/asm_config_server.cfg can be copied forward to the destination volume prior to upgrade.

  1. Make a directory to mount the target volume to
    mkdir /var/tmp/mnt

  2. Mount the target volume read-write
    mount -o rw /var/vg-bd-sda/set.N.root /var/tmp/mnt #where N is the target volume. Example: HD1.3 = 3

  3. Copy the flat file to the target location
    cp /etc/ts/tools/asm_config_server.cfg /var/tmp/mnt/etc/ts/tools/asm_config_server.cfg

  4. Unmount the target volume
    umount /var/tmp/mnt
