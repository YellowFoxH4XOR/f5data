Known Issue

This is the result of a known issue. Modifying a NAT object may cause the configsync operation to fail.

Note: To modify a NAT object, you must first delete the existing NAT and then redefine it with the appropriate changes using the bigpipe command or the Configuration utility.

For example, you might want to modify a NAT object that appears similar to the following example:

nat 172.16.65.33 to 172.16.65.145 {
}

To modify a NAT you must first delete the NAT object and then redefine it. For example, the following bigpipe command deletes the above NAT configuration:

bigpipe nat 172.16.65.33 to 172.16.65.145 delete

Once you have deleted the NAT object, you can redefine it with the appropriate changes. For example, the following bigpipe command redefines the NAT with an alternate IP address:

bigpipe nat 172.16.65.33 to 172.16.60.100 { }

After you have performed the above operations to modify the NAT on one of the systems in a redundant pair and then attempt to synchronize the changes to the peer system by running the bigpipe config sync command, the configsync operation will fail.

If you are running BIG-IP version 9.4.x, the configsync operation generates an error message that appears similar to the following example:

BIGpipe NAT creation error:
01030013:3: eXtremeDB - attempted to create an object with a duplicate index

If you are running BIG-IP versions 10.0.0 through 10.0.1, the configsync operation generates an error message that appears similar to the following example:

BIGpipe NAT creation error:
01070710:3: Database error (13), Can't save/checkpoint DB object, class:nat s tatus:13 - EdbCfgObj.cpp, line 126.

This issue occurs because the original NAT object still exists on the peer system when the configsync operation is performed.

Note: This issue would not occur if you performed the configsync operation after deleting the existing NAT, and then performed configsync after redefining the NAT.

F5 Product Development tracked this issue as CR98657, and it was fixed in BIG-IP version 10.1.0. For information about upgrading, refer to the BIG-IP LTM release notes.

Workaround

If you have redefined a NAT object and attempted the configsync operation, you can work around this issue by performing the following procedure:

  1. Log in to the receiving configsync unit.
  2. Delete the original NAT object by using the following bigpipe syntax:

    bigpipe nat x.x.x.x to x.x.x.x delete
  3. Load the configuration by using the following command:

    bigpipe load

Note: The modified NAT object now exists on both BIG-IP systems.
