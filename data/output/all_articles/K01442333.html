Description

Getting errors with iRules having redirects on its code instructions, but issue is observed only when using Google Chrome to access a VIP

  • Symptoms are seen with log messages like this on LTM logs:
           01220001:3: TCL error: /Common/<iRule_name> <HTTP_REQUEST> - ERR_NOT_SUPPORTED (line 1)     invoked from within "HTTP::host"
  • And causes that you are not able to being redirect as expected.  

Environment

  • BIGIP LTM
  • iRules with 
  • This was observed when accessing to a VIP(s) content with google Chrome.

Cause

  • Conditions are the same described on KB article:  K23237429, recently upgrade from previous version to a 14.1.x, and having iRules that are using any of the following:  HTTP::respond , HTTP::redirect , HTTP::retry
  • But in addition to that article, this could be observed only with Chrome browser
  • Consider this article as an extension to previous article and shows another example of iRule code modification with the workarounds suggested.

Recommended Actions

  1. The recommended actions are the same as described on  K23237429
  2. In here 2 examples of iRules that caused the issue, and after that, the modified code with the workarounds:
  3. The First iRule example uses the workaround of putting the "return" command after every redirect.
  4. Second iRule example uses the workaround of putting the HTTP::has_responded instruction.

Here the example of an iRule Before and After the workaround applied (in this case the workaround was adding a 'return' instruction after every redirect):

BEFORE:
when HTTP_REQUEST {
    if { [HTTP::host] contains "mysite.abc.com"} {
          HTTP::redirect "https://example.com/home/resourceV"
    }
    if { [HTTP::host] equals "mysite.def.com"} {
          HTTP::redirect "https://example.com/home/resourceX"
    }
    if { [HTTP::host] equals "mysite.ghi.com"} {
          HTTP::redirect "https://example.com/home/resourceY"
    }
    if { [HTTP::host] equals "myusite.jkl.com"} {
          HTTP::redirect "https://example.com/home/resourceZ"
    }
}

AFTER:
when HTTP_REQUEST {
    if { [HTTP::host] contains "mysite.abc.com"} {
          HTTP::redirect "https://example.com/home/resourceV"
          return
    }
    if { [HTTP::host] equals "mysite.def.com"} {
          HTTP::redirect "https://example.com/home/resourceX"
          return
    }
    if { [HTTP::host] equals "mysite.geh.com"} {
          HTTP::redirect "https://example.com/home/resourceY"
          return
    }
    if { [HTTP::host] equals "myusite.ijk.com"} {
          HTTP::redirect "https://example.com/home/resourceZ"
          return
    }
}


Here a second example of an iRule Before and After the workaround applied (in this case, the workaround was applied with the 'HTTP::has_responded' instruction): 

BEFORE:
when HTTP_REQUEST {
    if { [HTTP::host] equals "mysite.abc.com"} {
        HTTP::redirect "https://example.com/home/resourceV1"
    }
    if { [HTTP::host] equals "mysite.def.com"} {
        HTTP::redirect "https://example.com/home/resourceX1"
    }
    if { [HTTP::host] equals "mysite.ghi.com"} {
        HTTP::redirect "https://example.com/home/resourceY1"
    }
    if { [HTTP::host] equals "mysite.ghi.com"} {
    HTTP::redirect "https://example.com/home/resourceZ1"
    }
}

AFTER:
when HTTP_REQUEST {
if {[HTTP::has_responded]} {
    return
}else {
       if { [HTTP::host] equals "mysite.abc.com"} {
             HTTP::redirect "https://example.com/home/resourceV1"
      }
       if { [HTTP::host] equals "mysite.def.com"} {
             HTTP::redirect "https://example.com/home/resourceX1"
      }
       if { [HTTP::host] equals "mysite.ghi.com"} {
             HTTP::redirect "https://example.com/home/resourceY1"
      }
       if { [HTTP::host] equals "mysite.ghi.com"} {
             HTTP::redirect "https://example.com/home/resourceZ1"
      }
    return
  }
}

Note: in some cases the virtual server can be assigned with multiple iRules that uses code that can cause the error such as HTTP::redirect or HTTP::host. In that case we can use event rule, event can be used to stop all subsequent actions in all the attached iRules you can use:
"event disable all" or just "event disable" to stop propagation for a single iRule.
