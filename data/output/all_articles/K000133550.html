K000133550: TCP::collect and TCP::payload commands does not work in conjunction with VDI Profile

Type
Support Solution
Published
2023-04-20
Updated
2023-04-20
Applies to
  • BIG-IP
  • BIG-IP APM: 15.1.8
Source
https://my.f5.com/manage/s/article/K000133550

Description

The iRule commands TCP::collect and TCP::payload configured in an user defined irule do not work when there is a VDI Profile associated on the Virtual Server.

 

When the vdi profile is on the Virtual Server, the TCP::payload is empty. 
 

A simple irule (as shown below) and vdi profile on the Virtual Server will show the issue:

 

when CLIENT_ACCEPTED {

TCP::collect 100

}

when CLIENT_DATA {

log local0. "The irule1 scan is: [TCP::payload 0 100]"

TCP::release

}
 

/var/log/ltm shows empty payload as below:

Apr 3 06:38:54 APM-example.net info tmm1[31524]: Rule /Common/tcp_irule <CLIENT_DATA>: The scan is:

 

Environment

BIG-IP APM Virtual Sever
VDI profile on the Virtual Server
 

User defined irule on the Virtual Server:
 

when CLIENT_ACCEPTED {

TCP::collect 100

}

when CLIENT_DATA {

log local0. "The scan is: [TCP::payload 0 100]"

TCP::release

}

Cause

 

The TCP::collect collects the payload but the priority of the CLIENT_DATA event determines which iRule has a chance to act on the collected data first. Lower number means higher-priority. When the higher priority CLIENT_DATA event irule releases the collected payload, there will be nothing for the lower-priority CLIENT_DATA events to examine.

 

So with vdi profile associated on the Virtual Server, one of the internal irule /Common/_sys_APM_RDG_Redirect has a CLIENT_DATA event priority of 3 and so it gets to handle the collected TCP::payload. After acting on the data, it releases the payload. Hence the user defined irule does not have a chance to examine it which results in those empty payload logs under /var/log/ltm.

 

Recommended Actions

1. To configure the user defined iRule with commands TCP::collect and TCP::payload and VDI profile (for VDI resources) on separate Virtual Servers.

2. To change the priority of the event CLIENT_DATA to 2 on the user defined irule

Note: The below workaround can have unexpected results with vdi resources.
 

If we set the CLIENT_DATA to priority 2 on the user defined irule, it allows it to examine the data first (when vdi profile is assigned to the Virtual Server):

 

when CLIENT_ACCEPTED {

TCP::collect 100

}

when CLIENT_DATA priority 2 {

log local0. "The scan is: [TCP::payload 0 100]"

TCP::release

}

For the other iRules to function properly, the above user defined irule probably should not release the data (TCP::release), so the other CLIENT_DATA (internal iRules under vdi profile) has a chance to act as well.
