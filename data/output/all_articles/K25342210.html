Issue

You should consider using this procedure under the following condition:

  • Your system is experiencing NGINX Controller Agent installation or metrics collection issues.

Symptoms

As a result of Controller installation or metrics collection issues, you may encounter the following symptoms:

  • The system prompts you for a password when you're installing NGINX Controller Agent.
  • The Controller Agent does not report metrics after the installation.

Recommended Actions

  • Troubleshooting password prompt when installing the Controller Agent
  • Troubleshooting the Controller Agent's failure to report metrics after installation

Troubleshooting password prompt when installing the Controller Agent

If the system asks you to provide a password when you're installing the Controller Agent, the cause may be that you are starting the install script from a non-root account. If so, you need sudo rights. Depending on your system configuration, sudo may ask you for a password if you're using a non-root account.

Troubleshooting the Controller Agent's failure to report metrics after installation

After you install and start the Controller Agent, it should start reporting right away, pushing aggregated data to the Controller Server at regular one-minute intervals. It takes about one minute for a new system to appear in the Controller user interface.

If you don’t see the new system in the user interface or the Controller Agent isn't collecting metrics, make sure of the following:

  1. The Controller Agent package is successfully installed and no warnings displayed during the installation.
  2. The controller-agent process is running and updating its log file.

    Note: For troubleshooting purposes, you can turn on Controller Agent debug logging by editing the agent.conf file. For more information, refer to K64001240: Enabling NGINX Controller Agent debug logging.

  3. The Controller Agent is running under the same user as your NGINX worker processes.
  4. The NGINX instance is started with an absolute path. The Controller Agent cannot detect NGINX instances launched with a relative path. For example: ./nginx.
  5. The user ID the Controller Agent is using and the NGINX instance can run the ps command to see all system processes. If the ps command is restricted for non-privileged users, the Controller Agent won’t be able to find or properly detect the NGINX master process.
  6. The system time is set correctly. If the time on the system on which the Controller Agent is running is ahead or behind the Controller Server’s clock, you won’t be able to see graphs. Make sure that the Controller Server and NGINX hosts have their time synchronized using NTP.
  7. stub_status is configured, and the stub_status module is included in the NGINX build. To check, use the nginx -V command.
  8. The nginx user (or the user set in NGINX config) has permission to read the NGINX access.log and error.log files.
  9. All NGINX configuration files are readable by the Controller Agent user ID. Check owner, group, and permissions.
  10. Extra configuration steps are performed as required for the additional metrics to be collected.
  11. The system DNS resolver is correctly configured, and the Controller Server’s fully qualified domain name (FQDN) can be resolved.
  12. Outbound TLS/SSL traffic from the system to the Controller Server’s FQDN is not restricted. You can check this by using the curl command. Configure a proxy server for the Controller Agent if required.
  13. selinux, apparmor, or other third-party OS security tools are not interfering with the metrics collection. For example, for selinux, check /etc/selinux/config and try setenforce 0 temporarily to see if it improves the situation for certain metrics.
  14. The virtual private server (VPS) provider has not used hardened Linux kernels that may restrict non-root users from accessing /proc and /sys. Metrics describing the system and NGINX disk I/O are usually affected. There is no easy workaround for this except to allow the Controller Agent to run as root. Fixing permissions for /proc and /sys/block may also help.
