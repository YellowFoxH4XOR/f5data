Topic

This article discusses the limitation of sending gratuitous Address Resolution Protocol (GARP) requests when a BIG-IP object is configured on a different subnet than the self IP address, or when a BIG-IP object is associated with a VLAN that has no self IP addresses configured.

Description

The BIG-IP system allows you to configure IP addresses for BIG-IP local traffic objects that do not match the subnet of the self IP address on the associated VLAN. Additionally, the BIG-IP system allows you to configure objects associated with VLANs that have no self IP addresses. For example, virtual servers, network address translations (NATs), or secure network address translations (SNATs) are local traffic objects.

Note: To accommodate the routing for this configuration, the upstream devices must be configured to route the traffic destined for the BIG-IP local traffic object's IP address or subnet to the BIG-IP system's floating self IP address on the associated VLAN.

For example, the following self IP address is associated with vlan21, which means the VLAN is assigned to the 172.28.21.0/24 network:

self 172.28.21.33 {
netmask 255.255.255.0
vlan vlan21
allow all
}

In addition, a virtual server can be defined on this same VLAN with a different IP subnet.

For example:

virtual http-vs {
pool http-pool-all
destination 192.168.1.100:http
ip protocol tcp
profiles {
http {}
tcp {}
}
vlans vlan21 enable
}

Note: The only restriction for the virtual server address is using a loopback IP addresses. For information about loopback IP addresses restriction, refer to K11650: Support for loopback and link-local addresses on BIG-IP systems.

For BIG-IP redundant systems during a failover, the system taking over as the active unit does not advertise GARP requests for BIG-IP local traffic objects that are configured in this manner. This behavior is by design because the BIG-IP system does not have the information for which VLAN to advertise the GARP, since the system is unable to match the virtual address to any VLAN subnet. When the BIG-IP system does not advertise GARP requests for a virtual address, the neighboring network devices may continue to send traffic to the previously active unit. As a result, traffic may be disrupted.

Recommendations

When you configure a BIG-IP local traffic object that does not match the subnet of the self IP address on BIG-IP systems in a highly available configuration, you should consider the following recommendations:

  • Consider adding a self IP address that belongs to the subnet of the affected BIG-IP local traffic object on the VLAN that is receiving traffic for this object. This will allow BIG-IP system to send gratuitous ARP announcement on failover. For information about adding a self IP address, refer to the BIG-IP TMOS: Routing Administration manual (11.6.x and later) and the BIG-IP TMOS: Concepts manual (11.5.x).

    Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

  • If adding a self IP address is not desirable, consider configuring MAC masquerade for the traffic group that contains the BIG-IP local traffic object. Associating the MAC masquerade address to the traffic group allows the BIG-IP redundant systems to fail over without having to advertise GARP requests each time. This helps to ensure that the system continues to process application traffic with minimal interruption in service. For information about configuring MAC masquerade, refer to K13502: Configuring MAC masquerade (11.x - 17.x).

    Note: The MAC masquerade address will be effective only when there is traffic hitting configuration objects that are assigned to the traffic group. The virtual addresses gratuitous ARP announcements are sent out only on VLANs that have directly connected self-IP (floating or local-only). When virtual address has no self-IP, no gratuitous ARP will be sent on failover.
