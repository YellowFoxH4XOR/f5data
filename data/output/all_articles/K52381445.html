Description

A BIG-IP DNS monitor shows a status of "no reply from big3d: timed out"

Environment

  • DNS (GTM) sync-group
  • iQuery mesh
  • DNS Monitor
    • gtmd

Cause

BIG-IP DNS monitoring is a distributed function spread out across all members of the DNS (GTM) sync-group. Each BIG-IP DNS unit runs a process called gtmd (responsible for scheduling probes), and each BIG-IP system defined as a 'gtm server' object runs a process called big3d (responsible for actually carrying out the probe)

The monitoring process is as follows. It is assumed that a full iQuery mesh already exists between all gtmd and big3d processes.

  1. One gtmd process is made responsible for each monitor instance, using a simple hash mechanism. This distributes the monitor instances evenly across all the gtmd processes in the sync group. The managing gtmd is responsible for identifying a big3d agent to execute the probe, and for scheduling the firing of the probes requests.

    You can identify which gtmd is responsible by looking for specific messages in the gtm log (log.gtm.level must be set to 'debug' for this message to appear). Each gtmd in the sync group will log "Will probe" if it is the managing gtmd, and "Will not probe ...." (with the details of the managing gtmd) if it is not.

    Aug 23 13:54:32 gtm-13112-2-177 debug gtmd[12930]: 011ae03b:7: Will probe 5.1.0.12:0 in DC /Common/dc1

    or

    Aug 23 13:54:34 gtm-13112-2-178 debug gtmd[21783]: 011ae03a:7: Will not probe 5.1.0.12:0 in DC /Common/dc1 because will be done by other GTM (/Common/gtm-177:5.0.0.177)

    NOTE: If you are using v16.1.* and over, please refer: K000137833: gtmd does not log "Will probe" / "Will not probe" with debug mode in /var/log/gtm

  2. The managing gtmd selects a big3d agent that will be used to carry out the probe.
    Note: This selection is dynamic and is influenced by the CPU load reported by each big3d, so can change over time.

    1. If the monitor probe type is "bigip" (which simply reads vip status from mcpd), then there is only one big3d that can do this, which is the big3d running on the target device.  For this type of monitor, prober-pools are not used, even if configured.

    2. For all other types of monitor, a big3d agent is selected with a bias towards those in the same data center as the target (but this is not guaranteed), limited by the members listed in any prober-pool that may be configured. In the case that no prober-pool members are available, gtmd will fall-back to the default selection method and any big3d agent can be selected.

  3. Every $interval seconds (the 'interval' value for the monitor instance), the managing gtmd sends a probe request over the iquery channel to the selected big3d agent, passing it the type of monitor to run and the target IP address/port. The probe can be seen at the gtmd end as a "Probe to ...", and at the big3d end as a "Probe from" if GTM.DebugProbeLogging is set to 'enable')

    Aug 23 13:54:32 gtm-13112-2-177 notice gtmd[12930]: 011ae03d:5: Probe to 5.0.0.178: buffer = <monitor>    <name>/Common/gateway_icmp</name>    <addr>::ffff:5.1.0.12</addr>    <port>0</port>    <trans_addr>::ffff:5.1.0.12</trans_addr>    <trans_port>0</trans_port>    <server_name><![CDATA[]]></server_name>    <vs_name><![CDATA[/Common/link-external]]></vs_name>    <router>::</router>    <timeout>120</timeout>    <probe_interval>1</probe_interval>    <probe_timeout>5</probe_timeout>    <probe_num_probes>3</probe_num_probes>    <probe_num_successes>0</probe_num_successes>    <reverse>0</reverse>    <transparent>0</transparent>    <node_type>5</node_type>    <monitor_type>26</monitor_type> </monitor>

  4. All gtmd processes in the sync group start a timer for that monitor instance, for $timeout seconds.

  5. The big3d agent runs the monitor, waiting for up to $probe-timeout seconds for it to complete. Depending on the type of monitor, and the probe-timeout value, big3d may send the probe multiple times. The exact behaviour here depends on the monitor type.

  6. If the monitor was successful, or if it definitively failed (unless 'ignore-down-response' is set), big3d sends a probe reply to

      all connected gtmds over the existing iquery connections. It is important to understand that big3d is responsible for sending the monitor status to all gtmd processes - not just to the one that triggered it. If 'ignore-down-response' is enabled, big3d will hold off sending anything to gtmd until $probe-timeout, and only then inform gtmd of the status (potentially the status may have changed to 'up' by that point)

    • Upon receiving a probe reply, gtmd processes the reply, matches it to a monitor instance, and clears the timer created for that monitor instance back in step 4.

    • Any gtmd that has the timer reach zero marks the target down with a cause of "big3d: timed out". A common misconception is that the monitor status is then replicated to the other gtmd processes - this is not correct - gtmd only updates monitor status when it receives an update from a big3d agent, or when $timeout occurs and it marks it down itself (regardless and independently of what the other gtmd processes may be doing). 
      Note: This message indicates that the state change came from the monitor instance's managing gtmd, even though it was actually the gtmd that timed out which set the state, and this can lead to confusion as to why a device not listed in the prober pool logged a state change.

      Aug 23 13:55:45 gtm-13112-2-178 alert gtmd[21783]: 011a6006:1: SNMP_TRAP: VS /Common/vs2 (ip:port=1.1.1.2:80) (Server /Common/ltm-212) state change blue --> red ( Monitor /Common/bigip from /Common/gtm-178 : no reply from big3d: timed out)

    With that in mind, it should be clear that the "big3d: timed out" state indicates that one or more gtmd processes did not not hear (or recognise) a probe reply from big3d. The most common causes for this scenario are:
    • Network issues that delay or drop the iQuery messages for sufficiently long that they don't reach one or more gtmd processes before $timeout occurs.(particularly likely if the timed out status is intermittent or flapping)
    • An incomplete iQuery mesh, where a particular big3d agent is missing an iquery connection to one or more gtmd processes, and is therefore unable to send probe replies to those gtmd processes. This scenario can occur even without configuration changes, for example if there's always been a hole in the mesh, and gtmd decides to move the queries to a different big3d agent to help even out CPU load.
    • All members in the iQuery group (including the BIG-IP running gtmd) are configured as generic hosts. gtmd is unaware of any big3d available for the monitoring
    • The use of a "bigip" type monitor with a virtual server that does not actually exist on the LTM in question (in this case, big3d receives the probe, asks the local mcpd for the status of the object, mcpd returns 'no such object', and big3d returns no response to gtmd at all).
    • Where a prober-pool is configured with single BIG-IP monitoring generic hosts (load balancing with Global Availability), the BIG-IP may become overworked.
    There are two other scenarios that can result in 'big3d: timed out':
    • Monitoring an ltm virtual server, with the bigip monitor, with a virtual-server name that does not exist on the LTM.   This can be resolved either by renaming the virtual server on the GTM, or by using the ltm-name field (only configurable via tmsh) to specify the virtual server's true name - see the section on 'ltm-name', below, for more information
       
    • Monitoring an ltm virtual server with both bigip and non-bigip monitors under the following specific conditions. 
      • The big3d performing the monitoring is running on the LTM that hosts the virtual server
      • The gtm server object is type bigip (and therefore there is a bigip monitor applied to the virtual server)
      • The big3d is on an LTM that is configured as a redundant pair (the gtm server object has more than one device configured)
      • The monitor response received by gtmd is 'DOWN' (monitor_state=6)
    To effectively monitor such a target, the following alternatives are recommended:
    • Perform the monitoring at the LTM using ltm monitors, and remove the  non-bigip monitors from the gtm
    • Create a prober pool to ensure that the LTM that hosts the virtual server is never selected to run the non-bigip probe
    • Create a gtm server object of type Generic Host, and configure the virtual-server there - this will mean there is no bigip monitor, and the non-bigip monitor will work normally
     

    Recommended Actions

    1. Determine which gtmd process(es) show the target as being down with the state of "no reply from big3d: timed out".
    2. Verify which gtmd is the managing gtmd (Identified in the "Will probe" / "Will not probe", and also in the "Monitor /Common/bigip from /Common/gtm-178 : no reply from big3d: timed out" messages), and which big3d was selected for running the probe ("gtmd [xxx]: Probe to x.x.x.x" or "big3d[xxx]: Probe from x.x.x.x") for the appropriate ip:port.
    3. Verify that iQuery (tcp/4353) is established and able to pass data between those gtm(s) and the big3d agent that was selected ("tmsh show gtm iquery" or "iqdump x.x.x.x")
    4. Determine what type of monitor is being used. If it is "bigip", then
      1. Enable probe logging (tmsh modify /sys db gtm.debugprobelogging {value "enable"}), and verify that a virtual server with the exact IP and port as seen in the probe request actually exists on the LTM. If the probe is being executed by a big3d agent in the same data center as the target device, you should ensure the translation address (if configured) matches.
      2. If there are multiple virtual servers with the same ip:port (but with different IP protocols) present, big3d may be sending back state for both, but the reply is only matching the first at the gtmd end. In this case, make use of the ltm-name setting (see Additional Information, below)
      3. Verify that the virtual-server is not using a port-list or address-list. These type of virtuals are not supported by big3d, and can not be monitored.
      4. If the LTM is part of an HA pair, verify that only two LTM devices are in the device-group (no longer a requirement since BIG-IP DNS 14.0.0. which supports more than 2 devices), and that all the members of the HA pair are defined in the gtm server object. The reason for this is that mcpd will only return status for a virtual server if it is currently active for the related traffic-group, so gtmd sends the probe request to all devices in the HA pair, as it doesn't know which one is currently active, expecting the big3d on the active to respond, and the rest to remain silent.
      5. If the device is running a version older than 13.x, then another possible cause is ID480795 (K40120584), which is where the IP addresses of the active/standby units have been moved between boxes using the BIG-IP GUI. This causes gtmd to only send the probe requests to one of the members of the HA pair, and if that's the standby, then it won't respond.
    5. Where prober-pools are configured, add additional BIG-IP's to the prober-pool configuration to distribute monitoring activity between multiple devices.  Use a load balancing method other than Global Availability to distribute the load.
    Additional Information

    ltm-name

    • The "ltm-name" setting can be configured per-virtual server on the BIG-IP DNS (only via tmsh, there is no GUI interface for this), and provides a way to tell the "bigip" monitor which virtual server it should be matching when there is ambiguity, for example two virtuals on the same IP:port, but one is UDP and one is TCP.    If configured, this value is passed in the probe request, and big3d passes it to mcpd.  
      Note: ltm-name  is also used for optimization reasons - if you have GTM.DebugProbeLogging enabled and are watching the probe requests, you'll see that the first time the probe is sent, <ltm_name> is unpopulated - "<ltm_name><![CDATA[]]></ltm_name>", and this causes big3d to have to find the virtual server by matching ip:port. Once located, big3d sends back the name of the object in the probe reply. - eg " <ltm_name><![CDATA[/Common/vs_test]]></ltm_name>".    gtmd then remembers this value (in memory only), and passes it in subsequent probe requests to optimize lookup speed. gtmd does not update the gtm configuration with this learned value - you should not expect to see it in the ltm-name attribute of the monitor instance, and if gtmd is restarted, it will revert to blank (or whatever ltm-name was set to in the configuration) until big3d has updated it.

    iqdump

    • The iqdump utility can be used to verify that iQuery can be established between two points. It does not 'sniff' an existing iquery connection, but establishes a new iquery connection  over tcp/4353 to the specified device, and subscribes to the specified sync-group-name (or 'default', if not specified with -s).   When troubleshooting holes in an iquery mesh, it can be a useful tool to verify that the certificates are still valid, and that there are no network layer issues preventing iquery from standing up.
