Topic

You should consider using this procedure under the following condition:

  • You want to secure your applications against Apache Log4j2 vulnerability (CVE-2021-44228) with NGINX Application Security products

Description

NGINX App Protect WAF blocks exploitation attempts using signatures specific to this Java Naming and Directory Interface (JNDI) Injection (200104768 and 200104769) and generic JNDI Injection signatures (200004450, 200004451, 200004474, 200104770, 200104771, 200104772, and 200104773).

Important: If you log the full contents of requests (for example, full HTTP request logging) to a remote logging system which is vulnerable to CVE-2021-44228, and that system parses the request body as sent, the remote logging system may still be vulnerable to exploitation.

Note: As stated in the following security advisory, NGINX is not vulnerable to the Apache Log4j2 RCE vulnerability:

  • K19026212: Apache Log4j2 Remote Code Execution vulnerability CVE-2021-44228

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You are using one or more of the following NGINX Application Security products:
    • NGINX App Protect WAF
    • NGINX Controller App Security
    • NGINX Controller API-Management with Advanced Security

Procedures

Find specific guidance for your product in one the following sections:

  • Mitigating the Apache Log4j2 vulnerability with NGINX App Protect WAF
  • Mitigating the Apache Log4j2 vulnerability with NGINX Controller App Security and NGINX Controller API-Management with Advanced Security

Mitigating the Apache Log4j2 vulnerability with NGINX App Protect WAF

To mitigate the Apache Log4j2 vulnerability with NGINX App Protect WAF, perform the following procedures:

Download and apply the latest signature updates

  • Download and apply the latest signature updates for NGINX App Protect WAF to ensure that all of the signatures you need are available.

    For information about downloading and updating signatures, refer to Updating App Protect Attack Signatures in the NGINX App Protect WAF Configuration Guide.

Note: F5 advises that you regularly update attack signatures for NGINX App Protect WAF. To be notified of attack signature updates, refer to K9970: Subscribe to email notifications regarding F5 products and security announcements.

Ensure you enabled the Server Side Code Injection Signature Set in your policy file

Ensure that you included and enabled ("block": true) the Server Side Code Injection Signature Set, which includes the nine JNDI injection attack signature IDs, in your NGINX App Protect JSON policy file.

  1. If you are using the original, pre-installed JSON policy files—such as NginxDefaultPolicy.json, NginxStrictPolicy.json or NginxApiSecurityPolicy.json—you already have this signature set. 
  2. Set the signature set to block, as in the following JSON policy example:

{
    "policy": {
        "name": "block_ssci_policy",
        "template": { "name": "POLICY_TEMPLATE_NGINX_BASE" },
        "signature-sets": [
            {
                 "name": "Server Side Code Injection Signature Set",
                 "block": true,
                 "alarm": true
            }
        ]
    }
}

Notes:

  • After updating attack signatures or making configuration changes to a policy, you must reload NGINX Plus to make the changes effective.
  • F5 recommends that you perform adequate testing to ensure that application functionality isn’t impeded as a result of configuration changes. For more information, refer to the NGINX App Protect WAF Configuration Guide.

Mitigating the Apache Log4j2 vulnerability with NGINX Controller App Security and NGINX Controller API-Management with Advanced Security

Note: NGINX Controller does not manage signature updates on NGINX instances. Therefore, you must perform the signature update process in Mitigating the Apache Log4j2 vulnerability with NGINX App Protect WAF on each NGINX instance on which you installed NGINX App Protect WAF.

NGINX Controller App Security enables the JNDI injection signatures in the Server Side Code Injection Signature Set by default. In addition, updating to the latest signature package provides greater mitigation against the vulnerability compared to any previous signature packages.

The JNDI injection signatures are also included in NGINX Controller API-Management with Advanced Security with the same default behavior.

To enable a higher level of mitigation efficacy, the Server Side Code Injection Signature Set can be set to Always Blocking mode using the Bring Your Own (BYO) NGINX App Protect Policy feature, available on NGINX Controller ADC version 3.20 and later. Using this feature, the policy can be set to always block when these signatures are triggered. Be aware that this setting change may cause false positives.

To enable blocking mode in addition to the NGINX Controller ADC default policy, do the following:

  • F5 recommends using the following custom NGINX App Protect JSON policy:

    {
        "policy": {
            "name": "block_ssci_policy",
            "template": {
                "name": "POLICY_TEMPLATE_NGINX_BASE"        },
            "applicationLanguage": "utf-8",
            "enforcementMode": "blocking",
            "signatures": [],
            "signature-sets": [
                {
                    "name": "Server Side Code Injection Signature Set",
                    "block": true,
                    "alarm": true            }
            ],
            "bot-defense": {
                "settings": {
                    "isEnabled": false            }
            },
            "headers": [
                {
                    "name": "*",
                    "type": "wildcard",
                    "decodeValueAsBase64": "disabled"            },
                {
                    "name": "*-bin",
                    "type": "wildcard",
                    "decodeValueAsBase64": "required"            },
                {
                    "name": "Referer",
                    "type": "explicit",
                    "decodeValueAsBase64": "disabled"            },
                {
                    "name": "Authorization",
                    "type": "explicit",
                    "decodeValueAsBase64": "disabled"            },
                {
                    "name": "Transfer-Encoding",
                    "type": "explicit",
                    "decodeValueAsBase64": "disabled"            }
            ],
            "cookies": [
                {
                    "name": "*",
                    "type": "wildcard",
                    "decodeValueAsBase64": "disabled"            }
            ],
            "parameters": [
                {
                    "name": "*",
                    "type": "wildcard",
                    "decodeValueAsBase64": "disabled"            }
            ]
        }
    }
