Description

  • Different pool configurations, virtual server profile options, and desired functionality may require different SSL profiles to be attached to a virtual server.
  • Trying to configure the virtual server may fail with an error.
  • The connection may not reach the pool member or be reset by the pool member.

Environment

  • BIG-IP virtual server
  • SSL profiles

Cause

  • Configuring a virtual server to inspect application-layer traffic without applying a Client SSL profile
  • Configuring a virtual server to connect to pool members listening for SSL without applying a Server SSL profile

Recommended Action
Confirm SSL requirements for pool members:

  • Consider well-known ports (80 for plaintext HTTP, 443 for HTTPS)
  • Consult server team to confirm requirements

Additional Info
The BIG-IP system offers three possible setups for handling SSL:

  1. SSL pass-through
    • The BIG-IP system doesn't participate in encryption at all.
    • Encrypted SSL payload is passed directly to the pool member.
    • Prevents BIG-IP from using application-layer features (HTTP profile, most iRules, and so on).
    • Used with neither Client SSL nor Server SSL profiles on the virtual server.
       
  2. SSL offload
    • The BIG-IP system accepts an encrypted connection from the client, decrypts it, and passes the plain text application data to the pool member.
    • Front-end is encrypted.
    • Back-end is plain text.
    • Allows the use of application-layer features.
    • Used by having a Client SSL profile but no server SSL profile.
       
  3. SSL re-encryption
    • The BIG-IP accepts an encrypted connection, decrypts it, then forms a new encrypted connection to the pool member.
    • Front-end is encrypted.
    • Back-end is re-encrypted.
    • Allows the use of BIG-IP application-layer features.
    • Used by having both a Client SSL profile and a server SSL profile.
