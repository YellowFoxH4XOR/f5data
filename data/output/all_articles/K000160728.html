Description

Standard HTTPS monitors in BIG-IP LTM may fail to mark pool members as '(Available) UP' when monitoring a physical backend server hosting Multiple SNI-based Applications. This is due to the monitor not sending a Server Name Indication (SNI) extension in the SSL handshake, resulting in TLS handshake failures and the error: "The children pool member(s) are down." To monitor multiple SNI hostnames on the same server, specific configuration steps are required. 

Environment

  • BIG-IP LTM
  • Individual backend server hosting multiple SNI-based applications
  • Standard HTTPS monitors configured at the pool level
  • Default 'serverssl' profile used for SSL re-encryption and monitoring
  • Requirement to monitor both SNI and Non-SNI applications

Cause

The standard HTTPS monitor does not include an SNI extension in its SSL handshake, which is required by the backend server to differentiate between multiple SNI-based applications. Without SNI, the server cannot present the correct certificate, causing the health check to fail and pool members to be marked down. Enabling In-TMM monitoring and configuring custom server SSL profiles with the appropriate SNI values resolves this limitation. 

Answer/Recommended Actions

1. Enable In-TMM Monitoring Globally: [K11323537]

Run the following commands:

tmsh modify sys db bigd.tmm value enable
tmsh save sys config

Note: This is a global change affecting all monitors. Plan for a maintenance window, as pool member status may briefly show as 'Unknown' during the transition.

2. Configure Monitors for SNI-Based Applications: [K000160569]

For each SNI-based application:

  • Create a custom server SSL profile with the server-name field set to the required SNI hostname.
  • Create a dedicated HTTPS monitor for each SNI, assigning the corresponding custom server SSL profile.
  • Assign SNI-specific monitors at the pool member level.

3. Configure Monitors for Non-SNI Applications:

Explicitly assign the default 'serverssl' profile (/Common/serverssl) to each HTTPS monitor. No custom profile is needed for non-SNI applications.

4. Update Monitor Send Strings: [K16343688]

Ensure all HTTPS monitor send strings include the HTTP version and correct headers followed by the expected CR/LF (\r\n\r\n). The Host header must match the application's hostname. Example:

GET / HTTP/1.1\r\nHost: example.com\r\nConnection: Close\r\n\r\n

5. Monitor TMM Resource Usage:

After enabling In-TMM monitoring, monitor TMM resource usage to make sure the Device resource utilization is still under desired state:

tmsh show sys memory
tmsh show sys tmm-info

Note: TMM resource usage may increase proportional to the number of monitors.

Additional Information

  • iRules cannot be used to influence SNI in health monitors; SNI must be set via server SSL profiles.
  • The difference between https and https_443 monitors is only the default port assignment; functionally, they are identical.
  • Enabling In-TMM Monitoring is stricter about HTTP compliance; monitors without an explicit HTTP version or Host header will fail.
  • During the transition to In-TMM Monitoring, pool members may briefly flap or show Unknown status; this is temporary and expected.
  • Only SNI-specific applications require custom server SSL profiles; non-SNI applications can use the default serverssl profile if explicitly assigned.
  • The 'bigd.tmm' enable command itself is lightweight, but ongoing TMM resource usage depends on monitor count and system resources.
