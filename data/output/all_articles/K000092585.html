K000092585: Tenant failing to start after controller upgrade from 1.3 to 1.5

Type
Support Solution
Published
2022-11-10
Updated
2022-11-18
Source
https://my.f5.com/manage/s/article/K000092585

Description


Tenant fail to start after a controller upgrade from 1.3 to 1.5, while all controllers, blades, and system redundancy are in a ready state and operating.


An error is displayed in the tenants output 
# show tenants

<snip>
                                INSTANCE                                                                                      CREATION  READY          MGMT
NODE  POD NAME                  ID        PHASE                                                                               TIME      TIME   STATUS  MAC
-------------------------------------------------------------------------------------------------------------------------------------------------------------
1     my-example-tenant  1         Error starting VirtualMachine the server is currently unable to handle the request                           -


 

Environment

  • F5OS version 1.3 upgraded to version 1.5
  • Existing tenants deployed
 

Cause


After a controller upgrade, it is possible that some of the Kubevirt pods from the previous software version to remain in an Unknown state. With these leftover pods, the Kubevirt install script will fail to install the newer Kubevirt pods.

A healthy kubevirt status may look as such: 
[root@controller-1() ~]# oc get pods -n kubevirt
NAME                              READY     STATUS    RESTARTS   AGE
virt-api-5675d6bb6d-hbm49         1/1       Running   0          42d
virt-api-5675d6bb6d-hlskq         1/1       Running   0          42d
virt-controller-587f46dc5-qzsfx   1/1       Running   2          42d
virt-controller-587f46dc5-w2v8r   1/1       Running   0          42d
virt-handler-lm98v                1/1       Running   0          42d
virt-handler-r2k4f                1/1       Running   0          42d
However, if the status is showing as Unknown, then you may be affected by this issue. 
NAME                              READY     STATUS    RESTARTS   AGE
virt-api-5675d6bb6d-hbm49         1/1       Unknown   0          42d
virt-api-5675d6bb6d-hlskq         1/1       Unknown   0          42d
virt-controller-587f46dc5-qzsfx   1/1       Unknown   2          42d
virt-controller-587f46dc5-w2v8r   1/1       Unknown   0          42d
virt-handler-lm98v                1/1       Unknown   0          42d
virt-handler-r2k4f                1/1       Unknown   0          42d

F5 is tracking this known issue via ID1154089. After a controller upgrade, it is possible that some of the Kubevirt pods from the previous software version can remain in an Unknown state. With these leftover pods, the Kubevirt install script will fail to install the newer Kubevirt pods.

 

Recommended Action


1. Get the list of pods that are in an Unknown state 
# oc get pods -n kubevirt | grep -i unknown
2. Manually delete all the kubevirt pods that are in the Unknown state.
# oc delete pod <pod-name> -n kubevirt
Note: You need to do this for each pod in a separate linux shell since the delete will hang the current shell you're on.

3. Modify kubevirt install script
  • Copy the shell script to /tmp
# cp /usr/share/omd/kubevirt/omd-kubevirt-velos-install.sh /tmp
# cd /tmp
# vi omd-kubevirt-velos-install.sh
  • On or about line 128 of that script look for this line:
kubepods=$(oc get pods -n kubevirt | grep -c virt-)
Right after that line insert this line:
kubepods=0
  • On or about line 272 of that script look for this line: 
kubepods=$(oc get pods -n kubevirt | grep -c virt-)
Right after that line insert this line:
kubepods=0
  • Save and exit the file

4. Rerun the kubevirt install script 
# /tmp/omd-kubevirt-velos-install.sh /usr/share/omd/kubevirt/

5. Check kubevirt pods status  - they should all be in the running state. 
# oc get pods -n kubevirt


 

Additional Info


The fix for ID1154089 will address this problem as a permanent solution.
