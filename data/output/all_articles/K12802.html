Known Issue

Description

When the BIG-IP WebAccelerator system proxies a request because the content has expired (X-PvInfo code S10202), if the origin web server (OWS) sends back an HTTP 304 Not Modified response, that object may incorrectly be promoted to Hot Cache. This issue may occur even when the BIG-IP WebAccelerator Maximum Age cache setting is set to 0.

Consider the following example:

  • A virtual server is configured with a BIG-IP WebAccelerator-enabled HTTP class and with the pre-defined http-acceleration HTTP profile
  • A WebAccelerator Application is created for the aforementioned virtual server; the Application uses the pre-defined Level 2 Delivery acceleration policy
  • The Pages node of this policy is configured to cache documents, but uses a WebAccelerator Maximum Age Cache Setting of 0; therefore, the system should never serve content that matches this node from cache without first revalidating the content with the OWS
  • Multiple requests for an object that matches the Pages node (for example /index.html) are sent to the virtual server, resulting in the following behavior:

    • The first request is proxied to the OWS because it is a new request. The BIG-IP WebAccelerator inserts the S10201 X-PvInfo code in its reply to the client.
    • The second request is also proxied to the OWS. The object is already in the BIG-IP WebAccelerator system's cache, but the BIG-IP WebAccelerator considers the content as expired. The BIG-IP WebAccelerator inserts the S10202 X-PvInfo code in its reply to the client. This is the expected behavior and is also how the BIG-IP WebAccelerator should behave for any ensuing requests for this object.
    • For the sake of this example, suppose the OWS replied to the previous request with an HTTP 304 Not Modified response. This caused the BIG-IP WebAccelerator to incorrectly promote the object to Hot Cache.
    • The third request (and any ensuing requests until the Hot Cache entry expires) is served from Hot Cache. The BIG-IP WebAccelerator inserts the S11101 X-PvInfo code in its reply to the client.

Effectively, the system does not observe the WebAccelerator Maximum Age cache setting and incorrectly promotes objects to Hot Cache. The objects remain there until they expire, which depends on the RAM Cache Maximum Age setting in the HTTP profile. If during this time the objects are modified on the OWS, the BIG-IP WebAccelerator system will serve stale content.

Note: For simplicity, the above example assumes that all the requests are handled by the same TMM instance. In the real world, if a BIG-IP system is running multiple TMM instances, and if the virtual server is CMP-enabled, the requests would be divided amongst all available TMM instances, and you would see more S10202 responses before beginning to see S11101 responses. However, this issue equally applies to both CMP-enabled and CMP-disabled virtual servers. After an appropriate number of client requests, all TMM instances will incorrectly promote the content to Hot Cache.

Impact

The BIG-IP WebAccelerator may serve stale content; as a result, your website or your application may not work as expected.

Symptoms

As a result of this issue, the BIG-IP WebAccelerator system may experience the following symptoms:

  • The BIG-IP WebAccelerator may serve stale content
  • The BIG-IP WebAccelerator incorectly promotes objects to Hot Cache

Status

F5 has confirmed that this issue exists in the products listed in the Applies To box. ID 208210 (formerly CR121824) has been assigned to this issue.
