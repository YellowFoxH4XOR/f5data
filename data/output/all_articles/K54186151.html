Description

BIG-IP Virtual Edition (VE) hits 100% CPU with increasing traffic load

  • TMM traffic can be impacted, service interruption might occur
  • The tmctl virtio_tx_stats table indicates a q_full non 0 value, similar to the following: 
    tmm/virtio_tx_stats
pci    txq    q_full pkt_too_big
------ --- --------- -----------
0:4.0    0         0           0
0:5.0    0         0           0
0:6.0    0 635926690           0
0:7.0    0     30048           0
0:8.0    0         0           0
0:9.0    0     13036           0
0:10.0   0     19231           0
  • The tmctl ndal_tx_stats table indicates blocking is occuring, similar to the following:
    tmm/ndal_tx_stats
    iface tmm   blocked
    ----- --- ---------
    tap     0         0
    1.1     0         0
    1.2     0 214115969
    1.3     0 283096599
    1.4     0         0
    1.5     0         0
     
  • The /var/log/tmm file and the virtio logs have messages similar to the following:
    notice virtio[0:4.0]: cso: 1 tso: 1 lro: 1 mrg: 1 event: 1 indir: 1 mq: 0 s: 1
    In the example above mq: 0 and s: 1 shows the device is using a single queue (s: 1) and no multi queue (mq: 0)

Environment

  • BIG-IP VE deployed in KVM/Openstack environment
  • VirtIO device/driver is in use
  • OVS is deployed with default single queue (if using OVS without DPDK, a setup which does not allow for multi-queue in the first place.)

Cause

With the default deployment using a single queue on the OVS the TX queue can become full causing TMM to resend the data adding extra CPU load on the VE.

Recommended Actions

Ensure the KVM/Openstack environment support Multi-queue mode (please see your relevant KVM documentation or engage your Hypervisors Team) or consider using SR-IOV instead of OVS

Also see K17160 Achieving consistent high-performance on BIG-IP VE
