Known Issue

The BIG-IP system may select an unexpected Client SSL profile for a virtual server connection.

This issue occurs when all of the following conditions are met:

  • An SSL virtual server is configured with multiple associated Client SSL profiles.
  • The virtual server receives a ClientHello that includes a TLS Server Name Indication (SNI) extension to request a specific host name.
  • The requested host name does not match any of the Server Name values configured in any of the Client SSL profiles associated with the virtual server.
  • The requested host name matches a Subject Alternative Name (SAN) configured in an SSL certificate used by one of the Client SSL profiles.

    Note: SANs are an optional configuration option for SSL certificates.

The BIG-IP system may prematurely select a Client SSL profile that matches a Common Name even though a different Client SSL profile should have been selected based on a better matching SAN.

When a virtual server is configured with multiple Client SSL profiles, the BIG-IP system can select a Client SSL profile for a connection based on the host name requested by the client. The BIG-IP system matches the host name using the following order of precedence:

  • The system first tries to match the host name with a Server Name configured in the Client SSL profiles.
  • If there is no match, then the system tries to match a Common Name of an SSL certificate used by the Client SSL profiles.
  • If there is no match, then the system tries to match a SAN of an SSL certificate used by the Client SSL profile.

For example, if you have a virtual server with two Client SSL profiles applied, the following is true:

  • ClientSSL_Profile1 uses an SSL certificate with a Common Name of *.domain.com.
  • ClientSSL_Profile2 uses an SSL certificate with a Common Name of foo.domain.com and a SAN of secure.domain.com. 

If the virtual server receives a request for secure.domain.com, the ClientSSL_Profile1 is matched first (Common Name of *.domain.com) even though ClientSSL_Profile2 has a certificate with a better match in the SAN field (secure.domain.com).

However, this order of precedence is not in accordance with Internet Engineering Task Force (RFC 6125), which states that the Common Name should be used as a last resort. Therefore, the BIG-IP system should try and match a SAN before trying to match the Common Name.

Impact

The virtual server may select a Client SSL profile that is not the preferred profile.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • Your BIG-IP system prematurely selects a Client SSL profile that matches a Common Name even though a different Client SSL profile should have been selected based on matching a SAN.
  • Client connections to the affected virtual server are not processed according to the expected Client SSL profile.

Workaround

There is no workaround for this issue. However, you may be able to mitigate this issue by configuring your Client SSL profiles with the understanding of what order of precedence the system will use to select a profile. For example, ensure that you have a Client SSL profile configured with a Server Name field that matches the requested host name, and configure any other options you want.

Impact of workaround: The impact of the suggested mitigation depends on the specific environment. F5 recommends that you test any such changes during a maintenance window and consider the possible impact on your specific environment.
