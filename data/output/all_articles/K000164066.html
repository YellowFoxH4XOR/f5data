K000164066: F5 LDAPS authentication issue - typos or white spaces in server names

Published

Updated
2026-10-30
Applies to

Source

Description

Remote LDAP/LDAPS authentication to a BIG-IP LTM fails with the message "Remote authentication server unreachable; local authentication failed." The nslcd log reports that the configured server entries are rejected:

nslcd: AD_1.example.com:636 doesn't start with ldaps:// and "ssl on" is specified

ldap_initialize(AD_1.example.com:636) failed: Bad parameter to an ldap routine

Environment

  • BIG-IP LTM 17.5.1
  • Remote LDAP authentication with SSL enabled (ssl on), using the system-auth LDAP object
  • The servers list in auth ldap system-auth contains malformed entries

Cause

The servers list in the auth ldap system-auth object was malformed. For example the affected node stored two FQDNs as one quoted, comma-joined string with a typo (AD_1.example.com, AD_2.example.com, where the second name was misspelled), or the entry had a leading space (" AD_2.example.com"). nslcd rejected these entries, which caused the LDAPS authentication failure.

Answer/Recommended Actions

  1. Check the configured server list:
    tmsh list auth ldap servers
    Review each entry. Look for comma-joined values in a single quoted string, typos in FQDNs, and leading or trailing spaces.
  2. Back up the current BIG-IP configuration.
  3. Replace the server list with the correct FQDNs:
    tmsh modify auth ldap system-auth servers replace-all-with { AD_1.example.com AD_2.example.com }
  4. Save the configuration:
    tmsh save sys config
  5. Test LDAPS authentication. If needed, test with one valid FQDN first and add the second one afterward.

Additional Information

  • Correcting the malformed server list required the CLI command above. Editing the server list in the GUI did not correct the entries.
  • The nslcd errors indicate a configuration problem. This differs from a zombie nslcd process, which is covered in K000136041: LDAP login fail if nslcd works abnormally. In this scenario, nslcd was running and accepting connections.
  • A wrong bind password and missing management routes to DNS servers on a peer device were also identified during troubleshooting. These were not isolated as separate causes of this issue.
  • Name resolution or routing may contribute to a delay before LDAPS traffic starts. This was not confirmed as resolved and is not covered by this article.
