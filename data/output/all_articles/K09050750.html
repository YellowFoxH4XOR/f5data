Issue

Description

  • How to determine recent config changes on the BIG-IP system, who made them, and the method used to make them.
  • Both BIG-IP HA devices show changes pending and have new commit ID times that are close to each other, but neither is close to the time of the last ConfigSync.

Environment

  • BIG-IP systems are members of a device group
  • ConfigSync
  • /var/log/audit log files

Cause

Unknown changes are made to the configuration. In some cases, automated systems may make changes. For example, HP Network Automation or Ansible can remotely change the BIG-IP configuration and may cause devices to go out of sync.

Recommended Actions

To find recent config changes, perform the following procedures:

  • Identifying time of most recent configuration change
  • Checking the /var/log/audit file for events recorded after the last known sync time and the time of the current commit id
  • Searching the /var/log/audit file for the 'cmd_data=' value to identify the configuration changes

Identifying time of most recent configuration change

  1. Log in to the TMOS Shell (tmsh).
  2. To identify the time of the last known change, determine the time when the devices were last in sync. To do so, use the following command syntax:

    show cm device-group <device_group>

    For example:

    show cm device-group Config-Sync

    Output appears similar to the following example:

    ------------------------------------------------------------------
    CM::Device-Group
    ------------------------------------------------------------------
    Group Name                       Config-Sync
    Member Name                      LTM1.example.com
    Time Since Last Sync (HH:MM:SS)  00:34:37
    Last Sync Type                   full-load-manual-sync
    CID Originator                   /Common/LTM1.example.com
    CID Time (UTC)                   2019-Mar-27 10:07:21   
    LSS Originator                   /Common/LTM1.example.com
    LSS Time (UTC)                   2019-Mar-27 09:30:41

  3. Note the time of the most recent configuration change. For example, the most recent configuration change in the previous output displays as follows:

    CID Time (UTC)                   2019-Mar-27 10:07:21

  4. Note the time of the last successful ConfigSync between the HA pair systems. For example, the time of the last successful ConfigSync between the HA pair in the previous output displays as follows:

    LSS Time (UTC)                   2019-Mar-27 09:30:41

Checking the /var/log/audit log file for events recorded after the last known sync time and the time of the current commit id

Note: The following procedure is performed using the Advanced Shell (bash). From tmsh, you can switch to bash by entering the run util bash command.

After you identify the time of the most recent configuration change, you can search the /var/log/audit log file for events recorded after the last known sync time and the time of the current commit id.

For example, using the output from the previous procedure, search the log file for changes that occurred between 09:30:41 and 10:07:21 on March 27 2019. If the device is a standalone and not part of a pair and you know the time of the last approved change, then use that time.

  1. Log in to the BIG-IP command line.
  2. Search the /var/log/audit log file for events recorded after the last known sync time and the time of the current commit id. To do so, use the following command syntax:

    cat /var/log/audit | sed -n -e '/<month day hour:minute>/,$p' | less

    For example:

    cat /var/log/audit | sed -n -e '/Mar 27 10:01:02/,$p'

    Output appears similar to the following example:

    Mar 27 10:01:02 LTM1.example.com notice tmsh[10433]: 01420002:5: AUDIT - pid=10433 user=root folder=/Common module=(tmos)# status=[Command OK] cmd_data=show sys mcp-state field-fmt
    Mar 27 10:01:02 LTM1.example.com notice tmsh[10438]: 01420002:5: AUDIT - pid=10438 user=root folder=/Common module=(tmos)# status=[Command OK] cmd_data=list sys db
    Mar 27 10:05:04 LTM1.example.com notice tmsh[10734]: 01420002:5: AUDIT - pid=10734 user=root folder=/Common module=(tmos)# status=[Command OK] cmd_data=list ltm pool test_pool
    Mar 27 10:07:21 LTM1.example.com notice mcpd[6140]: 01070417:5: AUDIT - client tmsh, tmsh-pid-10734, user root - transaction #10941977-2 - object 0 - create { pool { pool_name "/Common/another_pool" pool_monitor_rule "http" } } [Status=Command OK]
    Mar 27 10:07:21 LTM1.example.com notice mcpd[6140]: 01070417:5: AUDIT - client tmsh, tmsh-pid-10734, user root - transaction #10941977-3 - object 0 - create { pool_member { pool_member_pool_name "/Common/another_pool" pool_member_node_name "/Common/10.0.0.3" pool_member_port 80 pool_member_addr 10.0.0.3 } } [Status=Command OK]
    Mar 27 10:07:21 LTM1.example.com notice tmsh[10734]: 01420002:5: AUDIT - pid=10734 user=root folder=/Common module=(tmos)# status=[Command OK] cmd_data=create ltm pool another_pool { members add { 10.0.0.3:80 { address 10.0.0.3 } } monitor http }

Searching the log output for the 'cmd_data=' value to identify the configuration changes

Search the log output for the cmd_data= value to identify the executed commands and the user ID that executed them.

For example, using the output from the previous procedure, you can determine the time of the configuration changes, which user ID made them, and the method used to make the change:

  • Using the output from the previous example, you can see that a pool was created and the config was saved (09:30:41 and 09:30:44). Further down, at 09:38:51 and 09:38:54, a pool member 10.1.0.2 was created for the /Common/test_pool pool by the admin user ID:

    AUDIT - client tmui, user admin - transaction #10908049-3 - object 0 - create { pool_member { pool_member_pool_name "/Common/test_pool" pool_member_node_name "/Common/10.1.0.2" pool_member_port 80 pool_member_description "" pool_member_conn_limit 0 pool_member_ratio 1 pool_member_priority 0 pool_member_rate_limit 0 pool_member_update_status 1 pool_member_inherit_profile 1 } } [Status=Command OK]

  • You can also see the save (but not sync) at 09:38:54, which is done automatically because the config change was performed using the Configuration utility (which appears as tmui).

    AUDIT - pid=9847 user=root folder=/Common module=(tmos)# status=[Command OK] cmd_data=save / sys config partitions all

  • You can see that later, at 09:40:56, another pool member 10.0.0.2 was created for the pool /Common/test_pool by the admin user ID.

    AUDIT - client tmui, user admin - transaction #10918651-3 - object 0 - create { pool_member { pool_member_pool_name "/Common/test_pool" pool_member_node_name "/Common/10.0.0.2" pool_member_port 80 pool_member_description "" pool_member_conn_limit 0 pool_member_ratio 1 pool_member_priority 0 pool_member_rate_limit 0 pool_member_update_status 1 pool_member_inherit_profile 1 } } [Status=Command OK]

  • You can see another save at 09:40:59.

    AUDIT - pid=9957 user=root folder=/Common module=(tmos)# status=[Command OK] cmd_data=save / sys config partitions all

  • Later. again at 09:41:08, the pool member 10.1.0.2 was removed (deleted) from the pool /Common/test_pool by the admin user ID.

    AUDIT - client tmui, user admin - transaction #10923331-2 - object 0 - obj_delete { pool_member { pool_member_pool_name "/Common/test_pool" pool_member_node_name "/Common/10.1.0.2" pool_member_port 80 pool_member_update_status 1 } } [Status=Command OK]

  • You can see another save:

    AUDIT - pid=10045 user=root folder=/Common module=(tmos)# status=[Command OK] cmd_data=save / sys config partitions all

  • About 26 minutes later, at 10:07:21, a new pool named /Common/another_pool was created and a pool member 10.0.0.3 was added listening on port 80 by the root user ID. This appears in the first two lines, with the timestamp 10:07:21:

    AUDIT - client tmsh, tmsh-pid-10734, user root - transaction #10941977-2 - object 0 - create { pool { pool_name "/Common/another_pool" pool_monitor_rule "http" } } [Status=Command OK]
    AUDIT - client tmsh, tmsh-pid-10734, user root - transaction #10941977-3 - object 0 - create { pool_member { pool_member_pool_name "/Common/another_pool" pool_member_node_name "/Common/10.0.0.3" pool_member_port 80 pool_member_addr 10.0.0.3 } } [Status=Command OK]

  • Because the previous change was performed using tmsh and not the Configuration utility, the third line shows the actual command entered:

    cmd_data=create ltm pool another_pool { members add { 10.0.0.3:80 { address 10.0.0.3 } } monitor http }

  • From the output, you can see that the following occurred since the last ConfigSync:
    • The user ID admin created pool member 10.1.0.2 was added to pool /Common/test_pool using the Configuration utility.
    • The user ID admin created pool member 10.0.0.2 was added to pool /Common/test_pool using the Configuration utility.
    • The user ID admin removed pool member 10.1.0.2 removed from pool /Common/test_pool by admin using the Configuration utility.
    • The user ID root created a new pool using tmsh.
  • Events occurring on the day that match the day the logs are reviewed appear in the audit log. Events from the previous day appear in audit.1 and the events from the day before that appear in audit.2.gz, and so on. You should amend the previous command to use the correct log file. Note that log files more than two days old are compressed to a GZ format file, so replace cat with zcat. For example: zcat audit.4.gz | sed -n -e '/Mar 23 12:45/,$p' | less
