Known Issue

This is the result of a known issue. On a full-proxy connection, a BIG-IP TCP zero-window advertisement followed by a client FIN packet may result in a FIN / ACK storm on the server-side connection.

The following sequence of events describes how the FIN / ACK storm may occur:

  • A client opens a connection to a full-proxy virtual server and sends a request

    Note: An example of a full-proxy virtual server is one in which a TCP profile is associated.
  • The BIG-IP system opens a connection to the server and proxies the client's request
  • The pool member starts sending the response
  • The client is either slow to respond, or the link to the client is lossy. Therefore, the BIG-IP TCP proxy buffer fills up, and the BIG-IP sends a TCP zero-window advertisement to the server
  • The server starts sending zero-window probes and the BIG-IP responds with zero-window ACKs
  • The server sends a FIN packet and the BIG-IP ACKs the server's FIN
  • The client sends a FIN. As a result, the BIG-IP sends a FIN to the server
  • The server correctly ACKs the FIN and goes to a TIME_WAIT state
  • The BIG-IP system resends the FIN to the server

The last 2 bulleted items repeat as long as the server continues to send an ACK in response to the BIG-IP FIN.

Note: Even if the client closes the connection by sending a TCP RST, the server-side loop persists.

F5 Product Development tracked this issue as CR115944 and it was fixed in BIG-IP versions 9.4.7 and 10.1.0. For information about upgrading, refer to the BIG-IP LTM, ASM, Link Controller, or WebAccelerator release notes.

This issue has been fixed in Hotfix-BIGIP-9.3.1-69.0-HF6 issued for BIG-IP version 9.3.1, and in Hotfix-BIGIP-10.0.1-402.7-HF4 issued for BIG-IP version 10.0.1. You may download this hotfix or later versions of the hotfix from the F5 Downloads site.
