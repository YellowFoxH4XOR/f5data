Description

Modern application deployments rely on multi-datacenter redundancy and load balancing to assure fast and scalable access. Global Server Load Balancing (GSLB) and Disaster Recovery (DR) techniques are commonly used to direct web users to apps that are hosted in multiple locations, while providing various mechanisms to stick users to specific backend servers to preserve server-side session state. These functions are often performed by intelligent DNS services such as BIG-IP DNS. 

BIG-IP Edge Client is more complex than a standard web browser and has multiple asynchronous components that simultaneously rely on DNS resolution provided by both OS DNS libraries and built-in DNS clients, both for initial connections and for reconnections that may occur much later. Deployments using dynamic DNS for VPN services accessed by BIG-IP Edge Client (or F5 Access VPN client) must be carefully considered.

BIG-IP DNS (Previous known as BIG-IP GTM, and before that 3DNS) can be used in front of BIG-IP APM in order to provided global server load balancing (GSLB) based on DNS.
The deployment guide is the solution that was developed after in-depth consultation with Product Development (PD).

Note: Even though the last revision of the deployment guide Deploying BIG-IP GTM with APM for Global Remote Access was in November 2014 - The general concepts remain the same and it is still considered the recommended and supported setup. 

Environment

  • GTM/DNS configured to provide secure remote access to corporate resources via multiple APM's
  • Multiple APM's configured to allow remote users access to internal resources

Cause

At times customers try to come up with their own solutions to GSLB BIG-IP APM or it is misconfigured.

Common Network layouts we see in the field that can cause issues:

  1. A solution may be deployed to only use a single name FQDN such as vpn.apmsupport.local eliminating the need for the redirects to the unique name the redirects to the unique names west.vpn.apmsupport.local
  2. Multiple APM members in the GTM pool.

This can lead to client issues in the field that are difficult to troubleshoot, most align with user experiences such as: 

  • The user cannot get connected intermittently
  • The Edge Client Authenticates (ie: user logs on) and then reconnects.
  • The Edge Client remains in an Initializing state
  • Browser may be slow and present session error messages.

DNS requirements in a nutshell

The Edge Client must follow this sequence to provide successful authentication, re-authentication, and re-connect functions to end users.

  1. VPN client resolves a wide hostname (ex vpn.example.com). 
  2. GSLB DNS resolves the wide hostname to the appropriate IP address of a BIG-IP virtual server. This IP should be dynamic based on availability or geolocation.
  3. VPN client connects to the target BIG-IP APM using the wide hostname. 
  4. BIG-IP APM’s iRule fires to return a 302 redirect to the narrow hostname.
  5. DNS resolves the narrow hostname. This IP should be static. This should be a separate virtual server with the correct access policy. 
  6. The VPN client connects to the narrow hostname, performs authentication, and connects to the VPN service.
  7. Any reconnects or re-authentication is performed to the narrow hostname unless the login session completely expires and returns to the wide hostname.

Deployment Options
GSLB for APM can be applied in two broad categories. In each, the BIG-IPs have virtual servers and SSL configurations to service both the wide hostname and narrow hostname. The virtual server servicing the wide hostname should be an LTM virtual server since it only redirects to the APM virtual server servicing the narrow hostname.

  • High availability configuration
    BIG-IPs share IP address in a traffic group to provide redundancy
    • Pro: Users will auto-reconnect upon a BIG-IP failure.
    • Con: Half of BIG-IP capacity remains in an unused standby state.
  • Topology configuration
    Each BIG-IP has unique IP addresses, HA pairs are not used
    • Pro: All BIG-IP capacity is used.
    • Con: Any BIG-IP failure will kick off some users, prompting the Edge Client to automatically re-establish the login session. This may result in authentication prompts to users depending on the configuration.

Configuring the BIG-IP APM iRules
Important: You must assign one of the following iRules to the wide-IP virtual server so the client can be redirected to the narrow hostname. 

For Example: vpn.apmsupport.local would be the wide-IP virtual server where this iRule is applied - redirecting to the unique name west.vpn.apmsupport.local

when HTTP_REQUEST {
    HTTP::respond 302 Location https://<FQDN of the local narrow hostname of the APM instance>[HTTP::uri]
}


For Example:

when HTTP_REQUEST {
    HTTP::respond 302 Location https://west.vpn.apmsupport.local[HTTP::uri]
}


If it is not possible to have two separate virtual servers to service the wide and the narrow hostnames, the forwarding in the iRules has to be conditional and hidden APM events may need to be enabled.

when HTTP_REQUEST {
   if { [HTTP::host] ne "<FQDN of the local narrow hostname of the APM instance>" } {
      HTTP::respond 302 Location https://<FQDN of the local narrow hostname of the APM instance>[HTTP::uri]
   }
}
when CLIENT_ACCEPTED {
    ACCESS::restrict_irule_events disable
}
 

For Example:

when HTTP_REQUEST {
   if { [HTTP::host] ne "west.vpn.apmsupport.local" } {
      HTTP::respond 302 Location https://west.vpn.apmsupport.local[HTTP::uri]
   }
}
when CLIENT_ACCEPTED {
    ACCESS::restrict_irule_events disable
}
