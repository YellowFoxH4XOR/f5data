Topic

Monitoring login attempts is an important part of network security. Successful and failed login attempts are recorded in the BIG-IP system audit log and the system secure log, depending on the type of access.

Description

You can view BIG-IP system login attempts in the Configuration utility and from the command line. Use the following procedures, and for more information and instructional videos, refer to K16197: Reviewing BIG-IP log files.

Important: The /var/log/audit file records successful and failed login attempts for the Configuration utility and successful login attempts for the command line, but it does not record failed login attempts for the command line. View the /var/log/audit file in the Configuration utility by following the procedures below. The /var/log/secure file records successful and failed attempts for both the Configuration utility and for the command line. View the /var/log/secure and /var/log/audit files at the command line by following the procedures below.

Procedures

Configuration utility

  • View Configuration utility login attempts from Audit List
  • View Configuration utility login attempts from the Logins dashboard

Command line

You can view the secure log from the command line in the /var/log/secure file.

  • Review current (unarchived) log files
  • Review archived log files

Impact of procedure: Performing the following procedures should not have a negative impact on your system.

To watch a video demo of this procedure, go to  Monitor login attempts on your BIG-IP system.

View Configuration utility login attempts from Audit List

  1. Log in to the Configuration utility.
  2. Go to System > Logs > Audit > List.

View Configuration utility login attempts from the Logins dashboard

In BIG-IP 13.1.x and later, to view login attempts from the Configuration utility Logins dashboard, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Go to System > Logins.

    The Summary page is displayed.

  3. To display a table of previous logins, go to System > Logins > History or you can select the History tab from within the Summary page.

Review current (unarchived) log files

  1. Log in to the BIG-IP command line.
  2. To change to the /var/log directory, enter the following command:

    cd /var/log

  3. Use a Linux utility such as cat, less, or more to review the log file.

    For example, to view the secure log file, enter the following command:

    cat secure

Review archived log files

By default, the BIG-IP system compresses log files on a daily basis and deletes archived copies that are older than eight days. Archived log files are stored in the /var/log directory and can be viewed by performing the following steps:

  1. Log in to the BIG-IP command line.
  2. To change to the /var/log directory, enter the following command:

    cd /var/log

  3. Use a Linux utility such as zcat, zless, or zmore to review the log file.

    For example, to view the audit.2.gz log file, enter the following command:

    zcat audit.2.gz

Interpret the audit log

Successful command-line login attempts appear similar to the following example:

Sep 18 14:32:08 LTM1.example.com info sshd(pam_audit)[29817]: user=root(root) partition=[All] level=Administrator tty=ssh host=172.16.0.2 attempts=1 start="Thu Sep 18 14:32:08 2025".

When the user logs out, the system reports information that appears similar to the following example:

Sep 18 14:43:02 LTM1.example.com info sshd(pam_audit)[29817]: user=root(root) partition=[All] level=Administrator tty=ssh host=172.16.0.2 attempts=1 start="Thu Sep 18 14:32:08 2025" end="Thu Sep 18 14:43:02 2025".

Unsuccessful command line login attempts generate different messages, depending on whether the failure was due to incorrect password or unknown user:

  • Incorrect password:

    Sep 18 14:46:12 LTM1.example.com notice unix_chkpwd[31514]: password check failed for user (root)
    Sep 18 14:46:12 LTM1.example.com notice sshd[31510]: pam_unix(sshd:auth): authentication failure; logname= uid=0 euid=0 tty=ssh ruser= rhost=172.16.0.2 user=root
    Sep 18 14:46:15 LTM1.example.com err sshd[31469]: error: PAM: Authentication failure for root from 172.16.0.2

  • Unknown user:

    Sep 18 14:48:11 LTM1.example.com err sshd[31722]: pam_tally2(sshd:auth): pam_get_uid; no such user
    Sep 18 14:48:15 LTM1.example.com warning sshd[31722]: pam_unix(sshd:auth): check pass; user unknown
    Sep 18 14:48:15 LTM1.example.com notice sshd[31722]: pam_unix(sshd:auth): authentication failure; logname= uid=0 euid=0 tty=ssh ruser= rhost=172.16.0.2
    Sep 18 14:48:17 LTM1.example.com err sshd[31710]: error: PAM: User not known to the underlying authentication module for bob from 172.16.0.2

Successful Configuration utility login attempts appear similar to the following example:

Thu Sep 18 15:03:59 PDT 2025 admin 0-0 httpd(pam_audit): user=admin(admin) partition=[All] level=Administrator tty=(unknown) host=172.16.0.2 attempts=1 start="Thu Sep 18 15:03:59 2025" end="Thu Sep 18 15:03:59 2025".:

Unsuccessful Configuration utility login attempts appear similar to the following example:

Thu Sep 18 15:09:54 PDT 2025 bob 0-0 httpd(pam_audit): User=bob tty=(unknown) host=172.16.0.2 failed to login after 1 attempts (start="Thu Sep 18 15:09:53 2025" end="Thu Sep 18 15:09:54 2025").:

To determine why a Configuration utility login attempt failed, log in at the command line and examine the /var/log/secure file for a corresponding log entry, similar to the following example:

Sep 18 15:09:54 LTM1.example.com err httpd[26726]: [auth_pam:error] [pid 26726] [client 172.16.0.2:52054] AUTHCACHE PAM: user 'bob' (fallback: false) - not authenticated: User not known to the underlying authentication module, referer: https://192.168.0.1/tmui/login.jsp?msgcode=1&

The previous log entry indicates that a user bob attempted to log in from 172.16.0.2, but that is an unknown user.

Recommendations

In addition to maintaining strong authentication and password standards, monitoring login attempts can assist in tracking both authorized and unauthorized attempts to access a BIG-IP system, giving administrators vital information for formulating a security policy and reacting to threats.
