K000132912: Restrict access by Source IP address to the Virtual if the client IP address is inserted by the proxy as HTTP Header "X-Forwarded-For"

Description

If you have a Proxy in front of the BIG-IP and all the client IP are source Natted, You can still restrict access to the virtual server if the client IP address is inserted by the proxy as HTTP Header X-Forwarded-For.

Environment

  • iRule
  • LTM

Cause

Unable to restrict access to a virtual server when connections are proxied.

Recommended Actions

You can use an iRule with datagroup to restrict access to a virtual server when the client IP address is inserted in the HTTP header "X-Forwarded-For."

For example, if the client connection is coming through a proxy that inserts the "X-Forwarded-For" header with a range of IP addresses, you can create a datagroup on the BIG-IP system that contains the IP addresses appearing in the "X-Forwarded-For" header. The example datagroup is displayed below:
 

ltm data-group internal clients_dg {
    records {
        192.0.2.14/32 { }
        192.0.2.19/32 { }
        192.0.2.1/32 { }
    }
    type ip
}

You can then associate the datagroup with an iRule that blocks the IP addresses listed in the datagroup. For example:

when HTTP_REQUEST {
if { [class match [HTTP::header "X-Forwarded-For"] equals clients_dg] } {
   set xffHeader "[HTTP::header X-Forwarded-For]"
   log local0. "X-Forwarded-For IP dropped $xffHeader"
drop
}
}

Using the above iRule and datagroup examples, when the BIG-IP system processes a request that matches an IP addresses in the datagroup, the system will block the request and log a message on the /var/log/ltm file as below:

info tmm3[12003]: Rule /Common/xff-drop <HTTP_REQUEST>: X-Forwarded-For IP dropped 192.0.2.1
