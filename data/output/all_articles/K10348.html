Known Issue

This is the result of a known issue. The initial TCP packet received on the server side (sent from the server to the BIG-IP system) will be re-segmented into two or more TCP packets on the client side (sent from the BIG-IP system to the client) when all of the following four conditions are true:

  • The client requests TCP window scaling when establishing the connection
  • The client's windows scaling factor is large enough that the unscaled TCP window size is smaller than the Maximum Segment Size (MSS)
  • The server sends data before the client (i.e., protocols such as SSH or SMTP)
  • The server's initial response includes a payload larger than the unscaled TCP window size

When this occurs, the BIG-IP system re-segments the first server-side response packet into two or more client-side packets as follows:

  • The first client-side packet contains a TCP segment equal in size to the client's unscaled window size
  • The second and subsequent client-side packets contain the remainder of the data that was contained in the first server-side packet, using the largest TCP segments allowed by the MSS value

In most cases, re-segmenting the original TCP packet does not cause any issues, since TCP typically reassembles the segments from the packet stream into a byte stream before the data is visible to the higher layer application. However, some applications expect the server's original segment to arrive intact within a single TCP packet. Re-segmenting the server’s original response can confuse such applications.

Workaround

You may be able to work around this issue by disabling TCP window scaling or by configuring a sufficiently small TCP window scale factor on the client.
