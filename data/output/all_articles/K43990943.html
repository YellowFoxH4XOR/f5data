Known Issue

VIPRION systems configured for high availability (HA) may become active-active during the upgrade process.

This issue occurs when all of the following conditions are met:

  • The VIPRION systems are configured with one or more Virtual Clustered Multiprocessing (vCMP) guests.
  • You configure the vCMP guests in a Sync-Failover device group with the Automatic Sync feature enabled.
  • You upgrade a guest running one of the affected versions listed in the Applies to box to a newer maintenance release and reboot to the newly installed version.

For example, when you upgrade the standby BIG-IP system in an HA pair from 12.1.0 to 12.1.1 or later, and restart as expected, the management IP address used for failover communication is set to an incorrect value of 127.0.0.1, which is then propagated to the active system as part of the ConfigSync process. This results in a loss of communication and a traffic-impacting active-active condition.

This issue does not affect upgrades to cumulative or engineering hotfix releases within the same maintenance release. In this situation, the BIG-IP system is able to recover and synchronize the correct management IP address, correcting the previously synchronized address. For example, upgrading from BIG-IP 12.1.0 to 12.1.0 HF1 will not trigger this issue, while upgrading directly from 12.1.0 to 12.1.1 HF1 will trigger this issue.

Impact

Multiple vCMP devices in the traffic group become active simultaneously, resulting in a traffic disruption.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • BIG-IP iHealth may list Heuristic H637289 on the Diagnostics > Identified > High screen. 
  • After you upgrade and reboot a vCMP guest configured for HA on a VIPRION system, multiple BIG-IP systems become active at the same time.
  • One or more systems in the DSC group shows 127.0.0.1 or None as the management IP address for the upgraded device.

    For example, output from the tmsh show /cm device all command shows a management IP address of None:

    --------------------------------------------------
    CentMgmt::Device: guest1.vpr1.example.com
    --------------------------------------------------
    Mgmt Ip               None
    Configsync Ip         10.10.10.12
    Hostname              guest1.vpr1.example.com

    Output from the tmsh list /cm device command shows a management IP address of 127.0.0.1:

        hostname guest1.vpr1.example.com
        management-ip 127.0.0.1

Mitigation

To prevent an active-active condition during the upgrade process, you can disable the ConfigSync process before you attempt the upgrade process, or you can obtain an engineering hotfix containing a fix for the issue:

  • Disabling the ConfigSync process before upgrading the system
  • Obtaining an engineering hotfix with a fix for this issue

Disabling the ConfigSync process before upgrading the system

To mitigate this issue, you can disable the ConfigSync process by setting the ConfigSync IP address to none.  To do so, perform the following procedure:

Impact of workaround: Performing the following procedure prevents this system from synchronizing the configuration until the IP address is changed back to the original value.

  1. Log in to the BIG-IP command line.
  2. Use the following syntax to list the ConfigSync IP address, and make note of the current value:

    tmsh list /cm device <device_name> configsync-ip

    For example:

    tmsh list /cm device guest1.vpr1.example.com configsync-ip

  3. Set the ConfigSync IP address to none using the following syntax:

    tmsh modify /cm device <device_name> configsync-ip none

    For example:

    tmsh modify /cm device guest1.vpr1.example.com configsync-ip none

  4. Complete the upgrade process and reboot to the newly installed version.
  5. Once the device is fully up and running, use the following syntax to change the ConfigSync IP address back to the original value and re-enable the ConfigSync process:

    tmsh modify /cm device <device_name> configsync-ip <original_IP_address>

    For example:

    tmsh modify /cm device guest1.vpr1.example.com configsync-ip 10.10.10.10

Workaround

To work around this issue, you can perform one of the following procedures:

  • Reverting the upgraded system
  • Upgrading another system in the device group to the new software version

Reverting the upgraded system

To work around this issue by rebooting the upgraded system back to the original software volume and synchronizing the correct management IP address to the device group, perform the following procedure:

Impact of workaround: The upgraded system will be forced offline and rebooted to avoid an active-active condition.

  1. Log in to the BIG-IP command line.
  2. Force the upgraded system offline by typing the following command:

    tmsh run /sys failover offline

  3. Boot the system back to the original boot location using the following command syntax:

    tmsh reboot volume <original_volume>

    For example, if you were originally in volume HD1.1 and upgraded to HD1.2, type the following command to boot back to HD1.1:

    tmsh reboot volume HD1.1

  4. After the system has rebooted and is up and running, verify that the ConfigSync process is working by typing the following command:

    tmsh show cm sync-status

    Output should show a Status of In Sync:

    ----------------------------------------------------------------------------------
    CM::Sync Status
    ----------------------------------------------------------------------------------
    Color    green
    Status   In Sync
    Mode     high-availability
    Summary  All devices in the device group are in sync

    Once the systems in the device group are able to ConfigSync, the correct management IP address will be synchronized to the other devices, overwriting the incorrect IP address.

  5. If the system is in a forced offline status, release the forced offline status by typing the following command:

    tmsh run /sys failover online

  6. Verify that the DSC cluster is up and running correctly by typing the following command:

    tmsh show cm traffic-group

    Output should appear similar to the following example:

    ---------------------------------------------------------------------------------------
    CM::Traffic-Group
    Name                      Device              Status      Next
                                                              Active
    ---------------------------------------------------------------------------------------
    traffic-group-1           guest1.vpr1.example.com  active      false
    traffic-group-1          guest1.vpr2.example.com  standby     true

  7. You can now mitigate the issue using one of the previously shown options.

Upgrading another system in the device group to the new version

To work around this issue by upgrading the other systems in the device group, perform the following procedure:

Note: If you have more than two devices in the device group, in step 2 you will need to force offline all the devices that have not been upgraded. Then perform steps 3 to 7 for each device you forced offline in step 2.

Impact of workaround: The systems that have not been upgraded will be forced offline and rebooted to avoid an active-active condition.

  1. Log in to the BIG-IP command line of the system that has not yet been upgraded.
  2. To alleviate the active-active condition, force the system offline by typing the following command:

    tmsh run /sys failover offline

  3. Verify that the system is forced offline and that the other system is active.
  4. Upgrade the system to the same version as the previously upgraded system and reboot to the newly installed version.
  5. When the system is up and running, verify that the ConfigSync process is working by typing the following command:

    tmsh show cm sync-status

    Output should show a Status of In Sync:

    ----------------------------------------------------------------------------------
    CM::Sync Status
    ----------------------------------------------------------------------------------
    Color    green
    Status   In Sync
    Mode     high-availability
    Summary  All devices in the device group are in sync

    Once the systems in the device group are able to ConfigSync, the correct management IP address will be synchronized to the other devices, overwriting the incorrect IP address.

  6. If the system is in a forced offline status, release the forced offline status by typing the following command:

    tmsh run /sys failover online

  7. Verify that the DSC cluster is up and running correctly by typing the following command:

    tmsh show cm traffic-group

    Output should appear similar to the following example:

    ---------------------------------------------------------------------------------------
    CM::Traffic-Group
    Name                      Device              Status      Next
                                                              Active
    ---------------------------------------------------------------------------------------
    traffic-group-1           guest1.vpr1.example.com  active      false
    traffic-group-1          guest1.vpr2.example.com  standby     true
