K000152794: F5® Distributed Cloud GLR HTTP Endpoint Log Delivery Troubleshooting

Applies to

  • F5 Distributed Cloud WAF
Source

Description

When configuring F5 Distributed Cloud Global Log Receiver (GLR) with an HTTP endpoint, log delivery may fail with errors such as:

  • Http status: 400 Bad Request
  • Http failure response: 500 Server Error
  • Service call failed. No retries or retries exhausted.
  • SSL/TLS handshake issues, including failures when using TLS 1.2 but success with TLS 1.3.
  • Endpoint requests for client certificates (mTLS) may also be observed.

Environment

  • Product:  F5® Distributed Cloud (XC) WAF
  • Feature: Global Log Receiver (GLR)
  • Destination: Cloud-based SIEM or HTTP endpoint, potentially requiring mTLS
  • TLS versions: 1.2 and 1.3
  • Ciphers: Various ECDHE/ECDSA and ECDHE/RSA options
  • Public CA certificates used on the forwarder

Cause

  • The HTTP endpoint may require mutual TLS (mTLS) and/or specific cipher suites for successful SSL/TLS negotiation.
  • GLR may not support all cipher suites, especially some ECDHE/RSA ciphers with TLS 1.2.
  • If the endpoint is configured to require a client certificate, but the GLR is not configured to present one, the connection will fail.
  • Firewall or network restrictions may block traffic from GLR public IPs, but in this scenario, the endpoint was accessible.

Answer/Recommended Actions

  1. mTLS Configuration:
    - If the HTTP endpoint requires a client certificate, ensure the GLR is configured to present the appropriate client certificate.
    - Configure the client certificate in the GLR settings as required by the endpoint.
     
  2. TLS Version and Cipher Suite Compatibility:
    - Prefer using TLS 1.3, as it is supported and works reliably with GLR.
    - If TLS 1.2 must be used, ensure the endpoint supports one of these ciphers compatible with GLR:

    TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256

    TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384

    TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305_SHA256

    - Avoid using ECDHE/RSA ciphers with TLS 1.2, as these are not supported by GLR.

  3. Network Access:
    - Ensure the endpoint is accessible from the GLR public IP ranges.
    - Reference F5 public IP documentation to verify allowed IPs if network restrictions are in place.

  4. Log Format:
    - Logs are sent as HTTP POST requests with Content-Type: application/x-ndjson. Ensure your endpoint accepts this format.

  5. Troubleshooting:
    - Use tools like openssl s_client to verify endpoint requirements for client certificates and supported ciphers.
    - Review both endpoint and GLR configurations for handshake or authentication errors.

Additional Information

Mutual TLS (mTLS) is a security protocol that extends the standard TLS (Transport Layer Security) handshake by requiring both the client and the server to present and validate each other's digital certificates. In a typical TLS connection, only the server presents a certificate to prove its identity to the client. With mTLS, the client must also present its own certificate, allowing the server to authenticate the client as well. This two-way authentication ensures that both parties are who they claim to be, providing an additional layer of security for sensitive communications, such as log delivery between systems. In the context of this article enabling mTLS means the Global Log Receiver (GLR) must be configured to present a valid client certificate when connecting to the HTTP endpoint, and the endpoint must be set up to trust and verify that certificate.
