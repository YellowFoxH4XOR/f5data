Description

  • What are these files?
  • Why are there so many of them?
  • Is it safe to delete them?

Environment

  • rSeries filesystem
  • Kubernetes

Cause

The files under /var/lib/kubelet/pods/*/containers/* are the termination log for each pod's container, and are created each time a container starts up.

The files are cleaned up when a pod is evicted, but they are not cleaned up on container restart.

If there are numerous pods with restarting containers (for example, pods in CrashLoopBackOff state), these files can build up over time, and in extreme cases may even exhaust all available inodes on the /sysroot filesystem.

In the example given in this article's description, a single virt-operator pod is in CrashLoopBackOff state:

[root@appliance-1(R2600-R84-S12) ~]# kubectl get pod -n kubevirt virt-operator-6cc8df4cbf-xrdkj
NAME                             READY   STATUS             RESTARTS   AGE
virt-operator-6cc8df4cbf-xrdkj   0/1     CrashLoopBackOff   244        20h

[root@appliance-1(R2600-R84-S12) ~]# find /var/lib/kubelet/pods/*/containers/virt-operator -type f | wc -l
247

This is a Kubernetes issue that F5 is tracking as bug ID 1591181. This issue is not fixed by F5 or Kubernetes at the time of this article's publication.

There is further discussion about this issue on GitHub:

  • https://github.com/kubernetes/kubernetes/issues/104592
  • https://github.com/kubernetes/kubernetes/pull/111765
  • https://github.com/kubernetes/kubernetes/pull/121181

Recommended Actions

In the vast majority of cases this issue should not be cause for concern.

You can review available inodes and the number of files at /var/lib/kubelet/pods/*/containers/* with the following commands:

df -i /sysroot
find /var/lib/kubelet/pods/*/containers/* -type f | wc -l

Under normal operating conditions there should be no more than ~40 files, often fewer.

If there are hundreds or thousands of files, it's possible one or more pods on the system has a restarting container.

To determine if the pods are healthy, review the output of:

kubectl get pods --all-namespaces

If there are pods in a problematic state (CrashLoopBackOff, Unknown, etc.), then that is the immediate issue that should be investigated and addressed. Open a support case with F5 for further assistance.

Additional Information

It's safe to delete the extraneous 0 byte files with 8 character names, if desired. They are also safe to ignore, as long as there are available inodes, and you identify and address any issues with pods on the system.
