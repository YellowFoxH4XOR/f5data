Known Issue

Description

Following a failover event, the newly active BIG-IP system may take several minutes to reset all of the TCP connections that were established before the failover.

This issue occurs when all of the following conditions are met:

  • You have a high-availability redundant BIG-IP system (10.x high-availability pair or 11.x Sync-Failover device group)
  • Connection mirroring is not configured for the affected virtual servers.
  • You have a high number (more than one million) of active connections to the affected virtual servers.

When mirroring is not enabled for a virtual server, and a failover occurs, the newly active BIG-IP system resets any connections that were established prior to the failover. This situation occurs because the connection information does not mirror to the peer system. However, the rate at which the BIG-IP system resets these connections is limited. When the maximum reject rate threshold is reached, the BIG-IP system silently drops the packet. As a result, the dropped packet must be retransmitted until the number of reset packets drops below the maximum reject rate threshold, or the client times out the connection.

The maximum reject rate limit is primarily in place as a denial-of-service (DoS) prevention measure. The tm.maxrejectrate database key allows you to adjust the number of resets that the BIG-IP system sends per second. The default value for the tm.maxrejectrate database key is 250 per second. The maximum value allowed is 1000. However, for a BIG-IP system that services a high number of unmirrored connections, even if the tm.maxrejectrate database value is set to the maximum of 1000, it may take the newly-active BIG-IP system several minutes to reset all of the TCP connections that were established before the failover.

Impact

Following a failover, connections may become unresponsive for several minutes, or eventually time out.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • Following a failover, the BIG-IP system repeatedly logs messages to the /var/log/ltm file that appear similar to the following example:

    slot1/LTM-1 warning tmm14[12693]: 011e0001:4: Limiting open port RST response from 251 to 250 packets/sec

  • Following a failover, client connections may stop responding or eventually time out.
  • Following a failover, applications may malfunction, become unresponsive, or report that connections have timed out.

Workaround

To work around this issue, you may be able to minimize or eliminate the issue in your environment using one or more of the following options:

Increasing the maximum reject rate

Enabling Connection Mirroring

Enabling Loose Initiation for virtual servers using a FastL4 profile

Increasing the maximum reject rate

Increasing the tm.maxrejectrate database key value from the default of 250 to the maximum of 1000 may be sufficient for most environments.

Impact of workaround: Increasing the tm.maxrejectrate threshold may cause the BIG-IP system to use more system resources when experiencing a DoS attack.

For information about increasing the maximum reject rate, refer to the following articles:

  • K13151: Configuring the rate at which the BIG-IP system issues TCP RSTs or ICMP unreachable packets (11.x - 12.x)
  • K9259: Configuring the rate at which the BIG-IP system issues TCP RSTs or ICMP unreachable packets (9.x - 10.x)

Enabling connection mirroring

Enabling connection mirroring ensures that the standby BIG-IP system in a redundant configuration is aware of the existing connection flows in the event of a failover event.

Impact of workaround: Enabling connection mirroring may degrade performance (especially on highly utilized systems). Additionally, connection mirroring is not available for device groups with three or more devices. For information, refer to K13217: Mirroring fails for device groups with more than two members.

For information about enabling connection mirroring, refer to the following articles:

  • K7222: Overview of connection and persistence mirroring (9.x - 10.x)
  • K13478: Overview of connection and persistence mirroring (11.x - 12.x)

Enabling Loose Initiation for virtual servers using a FastL4 profile

For virtual servers that use a FastL4 profile, you can enable the Loose Initiation option. Enabling Loose Initiation allows the system to initialize a connection when it receives any TCP packet, rather than requiring a SYN packet for connection initiation. It also provides a good alternative to the high overhead of connection mirroring. In the event of a failover, with Loose Initiation enabled, the standby BIG-IP system accepts connections mid-flow and forwards as expected.

Impact of workaround: Enabling Loose Initiation may permit stray packets to pass through the system. This behavior may pose a security risk and reduce system performance. Additionally, enabling Loose Initiation may not work or can produce unexpected results with certain advanced configurations.

For more information about the Loose Initiation feature, and the virtual servers that use the FastL4 profile, refer to the following articles:

  • K7595: Overview of IP forwarding virtual servers
  • K12272: Overview of BIG-IP virtual server types (10.x)
  • K14163: Overview of BIG-IP virtual server types (11.x)
