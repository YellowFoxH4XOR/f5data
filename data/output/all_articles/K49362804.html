Description

Even though the client is sending a HTTP POST, in the ASM logs, it's shows that request as HTTP GET to the same URL.

  • HTTP POST method is being sent to BIG-IP VIP.
  • The event logs show that BIG-IP received a HTTP GET instead of a HTTP POST.
  • The the same HTTP GET is being forwarded to the backend as well.

Environment

  • BIG-IP ASM/LTM
  • A redirect is configured via an iRule

Cause

This happens because clients sometimes incorrectly convert a HTTP POST to HTTP GET. Even though as per HTTP RFC 1945 and RFC 2068, the clients should not change the HTTP method, some client implementations do change if they get a HTTP 301/HTTP 302. Although it may look like the BIG-IP is changing the HTTP POST to HTTP GET, it's the client which is changing the HTTP POST to HTTP GET. The BIG-IP merely logs it and forwards to the backend as received.

Recommended Actions

Follow any one of the steps to resolve the issue.

  1. This ideally should be fixed in the client to re-send request to the redirected URL without changing the HTTP method (i.e., HTTP POST should re-tried as HTTP POST).
  2. If that can't be done, there has to be logic in the application so that before sending a HTTP POST, the client must make sure that POST URL should not get a HTTP 3xx response.
  3. Alternatively if the iRule to redirect can be modified to send a HTTP 307 instead of a HTTP 301/302. This can be achieved by modifying the iRule for redirection as below:
    HTTP::respond 307 Location https://redirected-URL.
    Note: The server can only issue a HTTP 307 to instruct the client not to change the HTTP method. Ultimately it's up to the client follow this or not. If this is not working, please try Option 1 or Option 2.
