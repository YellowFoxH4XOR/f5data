Topic

The VELOS system provides multiple levels of high availability (HA) within a chassis, from the system controllers to the partitions.

Note: Currently, the VELOS system does not support HA between chassis.

Description

System controllers HA

You must install a VELOS chassis with a pair of system controllers for high availability (HA). Centralized functions, such as hosting the floating management IP address, providing the access point to the webUI, command-line interface (CLI), and representational state transfer (REST) API interfaces for configuration and management of the entire system is hosted on the system controller that is elected as the active controller. While the non-floating management IP address for each controller can be assigned by a Dynamic Host Configuration Protocol (DHCP) server, you must manually configure the floating management IP address and it should always be used as the primary management address for the chassis. If a failover occurs between system controllers, any existing connections to the webUI, CLI, and REST API interfaces on the previously active controller will be terminated, and you will need to reestablish a new connection to the newly promoted active controller.

By default, the VELOS chassis is configured with auto redundancy state. Controller 1 is elected as active if both controllers are present and controller 1 is available or healthy. If controller 1 is unavailable or unhealthy, controller 2 is elected as active. If controller 1 becomes available or healthy at a later time, no failover occurs and controller 2 remains as active. If controller 2 becomes unavailable or unhealthy and controller 1 becomes available or healthy, then a failover occurs and controller 1 becomes the active controller. The other options for the system redundancy state setting include the prefer-1 and prefer-2 options. The prefer-1 option indicates that controller 1 is preferred as the active controller, while the prefer-2 option indicates that controller 2 is preferred as the active controller. When the system redundancy state is set to either of these two options, the respective controller becomes the active controller, regardless of its health. If the preferred controller is not present, the non-preferred controller will be active. If the preferred controller becomes available or healthy at a later time, a failover occurs, and the preferred controller takes over as the active controller.

In addition to the system redundancy state setting, the controllers exchange relevant information, such as presence, health, and current role as part of their HA election process. Each controller then uses this local and peer information, applies a series of tests, and assigns a result to each of these tests. The results can be either be-active, be-standby, or indeterminate. If the result is indeterminate, the controller applies the next test in ascending order. If the result is either be-active or be-standby, the controller attempts to fulfill that result and skips all subsequent tests by setting the results to not-applicable. If the test results conflict between the controllers, the status of the redundancy state provides the tiebreaker.

All logs related to HA events for the system controllers are logged to the /var/log_controller/cc-confd file. Typically a failover event is indicated by a role change log message logged at the INFO log level.

For example:

role change detected 2 -> 1

If necessary, you can enable the debug log level by setting the ha-state-machine database variable for the confd process to true.

For information about the commands to view or configure the redundancy state, refer to K21130014: Managing high availability for the VELOS system controllers.

Partitions HA

The Partitions HA feature requires both system controllers to be present. Each partition independently determines its own active controller. Therefore, a partition may elect a system controller that is standby at the chassis level to be its active controller, and its active controller may be different from another partition.

Similar to the chassis level redundancy state, a partition has its own redundancy mode, the system redundancy config mode setting, with four different values:

  • auto: There is no preference to which system controller should be active; the system decides based on policy or history. This is the default value.
  • prefer-1: This value states preference for controller 1 as the partition’s active controller.
  • prefer-2: This value states preference for controller 2 as the partition’s active controller.
  • active-controller: This value states preference for the partition’s active controller is the same as the active controller at the chassis level.

The partition does not immediately initiate a failover when the redundancy mode setting is changed. The hardware health of the system controllers takes precedence over the preference. A failover only occurs when the system determines that the currently active controller is not healthy or unavailable, or a manual failover is triggered.

In addition to the partition redundancy mode, a partition administrator can set a preference for the partition to fail back to the preferred controller when the preferred controller becomes available. This system redundancy config auto-failback setting controls this action. By default, this setting is set to disabled; the partition does not auto-fail back to the preferred controller. A partition administrator can also indicate the amount of time in seconds the partition should wait after the preferred controller becomes ready before initiating a fail back, which is controlled by the system redundancy config auto-failback failback-delay setting. By default, the delay is set to 30 seconds.

A partition requires you to configure only a floating management IP address, which is hosted on its active controller. This floating management IP address serves as the access point to the webUI, CLI (using SSH), and SNMP interfaces for configuring and managing the partition. When a controller failover occurs for the partition, the newly promoted active controller takes over hosting of the floating management IP address and the ethernet MAC address. All connections to the floating management IP address prior to the failover will be terminated, and you must reestablish a new connection to the floating management IP address after the failover completes.

A partition has a private datastore residing on both system controllers. You can only perform all configuration changes on the partition’s active controller and are actively replicated to the standby controller automatically. If the standby controller is unavailable when a configuration change is made, the system ensures that the changes are automatically replicated as soon as the standby controller is available. In the event that the active controller fails prior to synchronizing the configuration changes to the standby controller, configuration changes may be lost. The data replication includes the configuration database and files that are necessary for continued operation in the event of a controller failure, such as tenant images, cryptographic keys, and certificates. Data, such as core files, QKView files, or similar diagnostic information, and system logs are not replicated between the controllers. For logging, each controller separately aggregates the logs from all partition nodes so that all logs are always available from either controllers.  

For more information about the commands to manage HA for a partition, refer to K58515297: Managing high availability for the VELOS partition.
