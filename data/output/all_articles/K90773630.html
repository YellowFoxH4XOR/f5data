Description

Will Root certificate for Addtrust have any impact after May 30th as it is expiring?
????How is BIG-IP behaving if the Root cert from the CABundle that is configured for each VIP profile (CLIENT/SERVER) expires?
Will BIG-IP display errors in the logs?
Will BIG-IP ignore the expiration?

Environment

  • Old Client's browsers 
  • Certificate Authority certificate is expiring or has expired

Cause

There will be no impact on the connection on the part of the BIG-IP.

The AddTrust cross-signing was originally done to account for older devices that did not include the USERTrust root.
If the USERTrust root is present (as it is in 100% of modern browsers, operating systems, and mobile devices), the software will simply choose a trust path that leads to USERTrust and ignores AddTrust.
Due to the USERTrust root’s ubiquity, only a vanishingly small number of legacy devices can be expected to experience trust issues when AddTrust expires.

Both new "USERTrust RSA Certification Authority" certificate (which expires on 2038-01-19) and old one expiring on 30th May 2020 have same 'Subject key identifier' so that Client connecting to server should be automatically able to 'chain back' to new "USERTrust RSA Certification Authority" in case if it's present in trust stores on Client end.

Recommended Actions

As a best practice it's always advised to provide full trust chain along with server certificate during SSL negotiation (when client is connecting to BIG-IP VIP) by setting up correct chain in clientssl profile on BIG-IP.  K14783: Overview of the Client SSL profile (11.x - 15.x)

Additional Information

Any expired certificate will not permit an SSL transaction, the best way is to replace it wherever necessary.

BIG-IP will continue to serve expired Root/CABundle configured in client/server ssl profiles to the clients connecting with VIP.

Basically it's up to the client to validate the certificate along with supplied CABundle.
On the part of the BIG-IP there is check-cert command that automatically runs on a weekly schedule, the system calls the command from the /etc/cron.weekly/5checkcert file.
The check-cert command checks for SSL certificates stored on the BIG-IP system (including CA bundles) that have expired or will expire within 30 days.
The system prints expiration information to the GUI and logs it to the /var/log/ltm file, for up to five expired certificates.
You can also manually run tmsh run sys crypto check-cert command at the BIG-IP CLI.
