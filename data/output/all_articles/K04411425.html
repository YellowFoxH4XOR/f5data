K04411425: Aspen-mesh-metrics-collector pod is in CrashLoopBackOff status with an exit code of 1

Type
Support Solution
Published
2022-02-08
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K04411425

Description

Aspen-mesh-metrics-collector pod is in CrashLoopBackOff status with an exit code of 1. The errors messages may appear similar to the following examples:

Event logs error message: Warning BackOff xmxxs (xxxx over xxh) kubelet, k8s-node-x.example.com Back-off restarting failed container 

Pods logs error message: level=error ts=xxxx-xx-xxTxx:xx:xx.xxxx caller = main.go:808 err="opening storage failed: open /metrics-collector/tsdb/wal/0000xxxx: no space left on device"

Environment

  • OpenShift container platform: 3.x, 4.x
  • Aspen Mesh: 1.6.x, 1.9.x

Cause

This is a known Prometheus issue causing the Prometheus server to restart due to prom. server storage ran out of space or PVC getting filled up to 100% capacity. 

Recommended Actions

  • As it’s going to handle (Extending storage) via underneath storage provisioners or providers, hence you may need to get this done by involving the related resources (Team/person handling container storage solution for your environment).
  • From the Kubernetes platform perspective, you can resolve the issue by expanding PVC. For more information, refer to the Kubernetes Article. 
  • You can extend Prometheus storage without deleting data for Aspen Mesh Metrics Collector by following the article K13444958: Extending Prometheus storage without deleting data for Aspen Mesh Metrics Collector.
  • Additionally, modifying the retention period could be helpful. To do so, refer to K40115984: Modify the retention time for the Prometheus DB in Aspen Mesh.

Additional Information

For more information about the known issue, refer to the GitHub page: Prometheus server going to CrashLoopBackOff due to disk fill event.
