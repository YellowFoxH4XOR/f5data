Topic

When changes are made to most BIG-IP configuration object options, the new parameters or options defined by the configuration change only apply to new connections that are established to the BIG-IP system after the change is made. Existing connections continues to use the configuration options that were defined at the time the connection was established.

Important: The information in this article pertains to modification of local traffic configuration object options, such as iRules, monitors, and profiles. In BIG-IP 9.x and earlier, deleting a local traffic object, such as a virtual server or pool, results in immediate impact to existing connections. In BIG-IP 10.x and later, deleting virtual servers or pools does not normally have an effect on existing connections. Additionally, other configuration changes, such as BigDB key modifications, or changes to network objects, such as interfaces of VLANs, may have an effect on existing connections.

Description

Connections that traverse a common virtual server, profile, or other configuration object may exhibit different behavior or characteristics depending on the configuration options that were set at the time the connection was established. This design ensures that existing connections are not interrupted or otherwise modified and are allowed to transfer data and eventually terminate following the same conditions and criteria under which they were established.

Persistence profile

If a source address affinity persistence profile Timeout option is set to a decreased value, the persistence records for subsequent connections may be removed from the persistence table before other persistence records created under the previous configuration. Additionally, such a configuration may lead to a disparity in the number of connections established to a virtual server and the number of persistence records stored for those same connections.

iRules

When a local traffic configuration object or behavior is modified by an iRule, changes to that iRule only apply to new connections. In these situations, existing connections are subject to the conditions defined in the iRule at the time the connection was first associated with the iRule.

Note: iRules modification may have broader effects beyond load balancing configuration options, depending on the complexity of a given iRule. For more information about the ramifications of modifying iRules, refer to iRules Home on F5 Cloud Docs.

In the following example iRule, a load balancing decision is made depending on the URI of the HTTP request:

when HTTP_REQUEST {
if { [HTTP::uri] starts_with "/baduri" } {
HTTP::respond 200 content {
<html>
<head>
<title>404</title>
</head>
<body>
This Page is not available.
</body>
</html>}
} else {
pool MyPool1
}
}

Recommendations

It is important to be familiar with how the BIG-IP system handles configuration changes with regard to new and existing connections. If you require that a minimum number of connections be established with an older set of configuration parameters, you may need to plan your changes to take place during low traffic hours, or make configuration changes to manually bleed connections off of a particular configuration object before committing new changes. Additionally, when troubleshooting or verifying a configuration change, take care to ensure that new connections are being established to test the configuration changes, and preexisting connections are not being mistaken for a failure of a configuration change to be applied to a specific class of traffic.

If you want to verify a configuration change from a client that has existing connections to a particular configuration object (for example, virtual server), you can delete these connections by using the following command syntax:

tmsh delete /sys connection cs-client-addr <client IP address> cs-server-addr <virtual server address> cs-server-port <virtual server port>

For example, the following command deletes all connections from client 10.1.1.20 to virtual server 10.1.1.2:80:

tmsh delete /sys connection cs-client-addr 10.1.1.20 cs-server-addr 10.1.1.2 cs-server-port 80

If you want to delete a specific connection on the client based on the client’s outgoing port, you can delete this specific connection by using the following command syntax:

tmsh delete /sys connection cs-client-addr <client IP address> cs-client-port <client outgoing port> cs-server-addr <virtual server address> cs-server-port <virtual server port>

For example, the following command deletes the specific connection from client 10.1.1.20 port 1076 to virtual server 10.1.1.2:80:

tmsh delete /sys connection cs-client-addr 10.1.1.20 cs-client-port 1076 cs-server-addr 10.1.1.2 cs-server-port 80
