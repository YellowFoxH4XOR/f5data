Description

After configuring the BIG-IP to use in-tmm monitoring as explained on: K11323537: Configuring In-TMM monitoring, some HTTP monitors fail to come up.

These monitors were working fine while bigd monitoring was enabled.

Example monitor config:

ltm monitor http /Common/<Monitor_Name>
    adaptive disabled
    defaults-from /Common/http
    destination *:*
    interval 5
    recv 200 OK
    recv-disable none
    send "GET /examplestring \r\n\r\n"
    time-until-up 0
    timeout 16
}

Environment

  • After changing to in-tmm monitoring
  • HTTP Health Monitors

Cause

TMM as the core component of the data plane, is more strict in its compliance to the HTTP specifications than bigd. By default the BIG-IP will generate HTTP 0.9 requests for HTTP monitor probes unless, an HTTP version is explicitly specified in the receive string of the monitor.

According to the specifications, HTTP 0.9 requests consist of a single line terminated by a CR/LF (\r\n) character sequence. This is the reason why the second CR/LF character is ignored when in-tmm is enabled, marking the monitor down. All characters after the first CR/LF in the monitor send string are ignored by TMM whereas bigd will send any string entered in the send string even if it is not a valid HTTP message.

By specifying HTTP 1.0 or higher in the monitor send string, it will allow the double CR/LF sequence to be sent while in-tmm monitoring is enabled.

Recommended Actions

Change the send string on the monitor to add the HTTP version explicitly, as recommended on: K2167: Constructing HTTP requests for use with the HTTP or HTTPS application health monitor. This is how it should look:

Before:

"GET /examplestring \r\n\r\n"

After:

"GET /examplestring HTTP/1.0\r\n\r\n"

Additional Information

This can also happen to HTTPs monitors.
