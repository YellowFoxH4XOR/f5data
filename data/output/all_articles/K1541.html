Topic

In some configurations, it may be desirable to have multiple VLAN groups. For example, you could deploy a BIG-IP at an ISP to do load balancing, while still providing a transparent L2-functioning solution for non-load balanced traffic. Whether traffic is headed for another network or to the Internet, for security reasons it is important to pass the traffic through a firewall.

Consider the following diagram:

In the preceding configuration example, each customer (C1 and C2) has a VLAN group and above each of these VLAN groups is a firewall. There are several complications associated with this configuration.

If you set up the two VLAN groups without any virtual servers, C1 can reach the Internet, as can C2. However, C1 cannot securely or properly reach C2 for the following reasons:

  • BIG-IP versions 4.0 PTF-01 through 4.1.1PTF-03 pass traffic between VLAN groups without going through the firewall. That means that in this configuration example, BIG-IP will route packets straight from C1 to C2, completely bypassing the firewall.
  • BIG-IP versions 4.1.1 PTF-03 and later do not route between VLAN groups unless IP forwarding is enabled. If IP forwarding is not enabled, BIG-IP drops the packet.

Ideally, BIG-IP should send any packets not destined for the BIG-IP itself, or for virtual servers on the BIG-IP, through the firewall—a hybrid of transparency at L2 and routing at L3.

In the original implementation of proxy ARP (the mechanism that causes BIG-IP to respond to ARPs on behalf of other hosts), BIG-IP proxies for ARPs using the MAC address of the VLAN group and all ARP replies show the VLAN group's MAC address.

This implementation works fine when there is only one VLAN group, but if BIG-IP receives a packet from C1 destined for BIG-IP's own MAC address with the destination IP of C2, BIG-IP has no reason to send the traffic through the firewall. If the MAC address has the destination of the BIG-IP, BIG-IP is the next hop and, therefore, that BIG-IP makes the next routing decision. According to BIG-IP system's routing table it can reach this network directly (because it is routing/bridging for both networks), and as we see above in the diagram, this would mean the firewall is bypassed.

In the new implementation of proxy ARP with transparent_vlangroups=1, BIG-IP does not use the MAC address of the VLAN group in its ARP replies; it uses the real MAC address of the host that is being requested with a locally unique bit toggled. Because of this, when a client on C1 makes a request for C2, the client ARPs for the default gateway (that is, the firewall), and BIG-IP responds with the firewall's MAC address, which has the locally unique bit toggled. When the client uses this MAC address to make a connection, BIG-IP recognizes that the MAC address needs to be sent to the firewall, and sends the packet out through the correct firewall-facing interface.

The flow is as follows:

C1 requests a connection to C2

  1. C1 sends an ARP for the default gateway (the firewall).
  2. BIG-IP sees this request, proxies a response for the firewall, and toggles a bit to make it unique so that the same MAC does not exist in multiple places on the network.
  3. The client receives this ARP entry and updates the ARP table.
  4. The client then tries to open a connection to C2, using the firewall MAC address assigned by BIG-IP as the next hop.
  5. BIG-IP receives this request and, since the MAC address is the same as the firewall, it sends the packet to that MAC address.

Steps 1 through 5 are then repeated with the firewall doing the ARP request.

Theoretically, it would appear that you could use virtual servers to bypass OS routing, but there is another complication. Consider the previous example where C1 is trying to connect to C2, except in this case we have a virtual server pointing at the firewall for both networks (on each VLAN group).

The flow is as follows:

  1. C1 sends an ARP for the default gateway.
  2. C1 receives the MAC address of the BIG-IP.
  3. C1 attempts to open a connection using the BIG-IP's MAC address as the next hop.
  4. BIG-IP receives the packet (on VC1) with its own address as the next hop, destined for C2, for which it has a VIP.
  5. The packet is sent to the firewall and creates a connection in the connection table.
  6. The firewall sends an ARP for C2 and gets the BIG-IP MAC address as the next hop.
  7. The firewall sends the packet to BIG-IP (on VE2).
  8. BIG-IP receives the packet, and looks up the connection to see if the VIP on which it was created is enabled on this VLAN.
  9. BIG-IP finds a connection (because it has the same source and destination as when it was first received on VC1), and sends the packet to the correct host (the firewall), as defined in the connection table.
  10. This cycle is repeated 127 times as the TTL gets decremented, and then the packet is dropped (routing loop).

If the firewall translated the source address, this configuration will work because it would appear as a new connection, enabling the traffic to be securely sent. This configuration only works if the firewall translates the address, and is no longer necessary with the new implementation of proxy ARP, but can also be resolved by making BIG-IP VLAN-aware. VLAN awareness allows BIG-IP to know on what VLAN a request is received so it can differentiate where (what VLAN) the request came from—this would also resolve the issue described in this example.

To enable VLAN awareness, set the honor_vlans internal variable to 1—this internal variable is available on BIG-IP version 4.1.1 PTF-04 and 4.1.1 PTF-05, and is enabled by default on BIG-IP 4.2 PTF-02 and greater. The following section demonstrates how to set up this configuration.

Configuring the new proxy ARP implementation

BIG-IP version 4.5 through 4.6.4

As of BIG-IP version 4.5, the internal transparent_vlangroups is the global setting: vlangroups opaque | translucent | transparent. The transparent setting corresponds to the internal setting.

To enable this through the command line, type the following command:

b global vlangroups transparent

The honor_vlans internal variable has been converted to the global variable, vlans lookup enable | disable. This global variable is enabled by default.


BIG-IP versions 4.1.1 PTF-04 through 4.1.1 PTF-05 and 4.2 PTF-02 through 4.2 PTF-10

By default, BIG-IP version 4.0 through 4.1.1 PTF-03 uses the original proxy ARP implementation, which sends out the VLAN group MAC address in all proxied ARPs.

To toggle this on BIG-IP version 4.1.1 PTF-04, 4.1.1 PTF-05, and 4.2 PTF-02 and greater, set the transparent_vlangroups internal variable by typing the following command:

b internal set transparent_vlangroups = 1

Where the possible values are:

0Use VLAN group MAC
1Use the real MAC address of the requested host with the locally unique bit toggled
2Use the real MAC address of the requested host
