K95558398: A BIG-IP ASM restoration from the UCS archive fails after a system upgrade

Type
Known Issue
Published
2017-07-29
Updated

  • BIG-IP ASM: 13.0.0, 12.1.3, 12.1.2, 12.1.1
Source

Known Issue

You are unable to restore a BIG-IP ASM configuration from a user configuration set (UCS) archive after you upgrade the system.

This issue occurs when all of the following conditions are met:

  • Your BIG-IP ASM system is running 12.1.0.
  • You have configured your BIG-IP ASM system with security policies.
  • You create a UCS archive that contains a security policy history file (/var/ts/dms/policy/policy_versions/ plc file) of zero length.
  • You upgrade your BIG-IP ASM system to an affected version.
  • You attempt to restore the BIG-IP ASM configuration using the UCS archive.

Impact

The configuration fails to load.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • When you attempt to load the UCS configuration from the command line, the system displays an error message similar to the following example:

    emerg load_config_files: "/usr/bin/tmsh -n -g load sys config partitions all " - failed. -- 01070710:3: Cannot update_indexes/checkpoint DB object, class:fw_log_profile status:13 - EdbCfgObj.cpp, line 127 Unexpected Error: Loading configuration process failed.

  • When you attempt to restore the UCS archive, the system logs error messages to the /var/log/ts/ts_configsync.log file that appear similar to the following example:

    y.log:273:ts_configsync.plcCRIT|<date time>|32029|F5::ImportExportPolicy::Base::fatal_error,,failed to fd_retrieve from gzip pipe (Magic number checking on storable file failed at /usr/lib/perl5/vendor_perl/Storable.pm line 401, at /usr/local/share/perl5/F5/ImportExportPolicy/Binary.pm line 1802 import_export_poli

    CRIT|<date time>|32029|F5::ImportExportPolicy::Base::fatal_error,,Cannot read from input file.

Workaround

To work around this issue, you can correct the corrupted PLC version files before you create the UCS archive and upgrade the system. To do so, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the command line of the affected system using administrator privileges.
  2. To locate the corrupted PLC version files with a zero-byte value, type the following command.

    find /var/ts/dms/policy/policy_versions/ -size 0

    Output appears similar to the following example:

    /var/ts/dms/policy/policy_versions/1/14.plc

  3. Change directories to the file location of the zero-byte PLC version file.

    For example:

    cd /var/ts/dms/policy/policy_versions/1/

  4. Copy the previous non-zero-byte PLC version file, overwriting the zero-byte PLC version file.

    For example:

    cp -f 13.plc 14.plc

  5. To verify that the PLC version file has the same byte size as the PLC version file that was copied, type the following command:

    ls -l

    Output appears similar to the following example:

    -rw-r--r--. 1 apache apache 111232 2017-01-28 12:03 13.plc
    -rw-r--r--. 1 root   root   111232 2017-07-22 11:44 14.plc

    Note: Output of the ls -l command is truncated for display purposes.

  6. To create a UCS archive of the BIG-IP ASM 12.1.0 system, use the following command syntax:

    tmsh save /sys ucs /var/tmp/<filename>.ucs

  7. Save the UCS archive file from the BIG-IP ASM system.
  8. Upgrade the BIG-IP ASM system.
  9. Use the UCS archive file created in step 6 to restore the configuration.
