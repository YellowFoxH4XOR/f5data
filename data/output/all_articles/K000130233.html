K000130233: Disk partition /shared/vmdisks has less than 40% free

Support Solution
Published

  • VIPRION Platforms

Source

Description

The vCMP Host logs report that the /shared/vmdisks partition is low on disk space. The vCMP Guests vmdisks need to be reduced in size. Rebuilding the vdisk then applying the backup file is a very efficient way to reduce disk space.

Environment

  • vCMP Host and Guests

Cause

vCMP Guest virtual disk are large and need to be reduced in size.

 Recommended Actions

Build a new vmdisk and apply the backup file to reduce disk space. In some cases, this can reduce a 40GB vdisk to 5GB.


Note: This procedure will delete all the existing partitions in the vCMP guest, and recreate only the running partition, making it impossible to boot in a different version, in case it is needed for any reason. 
 

  1. Delete any unnecessary backup files (/var/local/ucs/*.ucs), images (shared/images/*.iso) and qkview (/var/tmp/*.qkview) files from the vCMP Guests.

  2. Create a UCS archive (backup) file for the vCMP Guest system & save it off the device. Note: If you don't save this off the vCMP Guest, you won't be able to restore the image after rebuilding the vmdisk. 

    tmsh save /sys ucs /var/tmp/$HOSTNAME-description-mmdd

    • The .ucs extension is automatically added

  3. Copy the Master Key 

    f5mku -K

  4. Turn off the vCMP Guest

    • From the vCMP Host, in the WebUI, set this Guest to the "Configured" status.

  5. Remove the vmdisk from the Guest.

    • From the vCMP Host, access the Guest's settings

      • vCMP > Guest List > guest-name-here

    • Change Basic to Advanced

    • Set virtual disk to 'None;, using the drop-down menu

    • Check the Initial Image version, to ensure the BIG-IP version is the current and correct ISO selected on the drop-down option. This will avoid running into issues or the need to downgrade/upgrade the initial image version deployed.

    • Leave all other settings as-is

    • Click 'Update', to save.

  6. Delete this vdisk. Confirm that its backup file (*.ucs from step 2) and Master Key (from step 3) are saved off of the Guest. Note: If this is a bladed system (Viprion) there can be multiple vdisks; one for each blade. This is noted by the /<#> after the image name.

    • In the WebUI: vCMP > Virtual Disk List > Virtual Disk List > .img > check > delete

    • From the CLI:

      tmsh delete vcmp virtual-disk vmcp-guest1.img/<# of blade>

    • Delete the disk from each blade

  7. Deploy/Turn on the vCMP Guest. This is where new vdisks are created. They're usually much smaller than the original size. 

  8. Be patient. The disk build takes time. Note: Only perform this maintenance on one guest at a time otherwise the disk resources are consumed and will slow this maintenance.

    • To watch the disk build from the host:

      watch tmsh show vcmp virtual-disk

  9. Access the vCMP Guests by logging in to the GUI. Since this is a new build, use default credentials to log on.

  10. Provision the modules. If the necessary modules aren't provisioned, the backup file may fail to load so be sure all modules are provisioned before applying the ucs backup file.

    • Refer to the active vcmp guest: System > Resource Provisioning

    • Check/enable any necessary modules

  11. Apply the master key.

    • From the command line (CLI):

      f5mku -r <master key value from step 3>

  12. Load the backup UCS file.

    • Upload the UCS that was backed up in step 2 to /var/tmp using winscp

    • From the CLI:

      tmsh load sys ucs /var/tmp/$HOSTNAME-description-mmdd.ucs

  13. Check Image disk size and compare from the pre-step size captured.

    • From the vcmp host:

      tmsh show vcmp virtual-disk

Once the standby Guest is fully restored and functional, fail-over the traffic from the Active vCMP Guest, to the Standby vCMP Guest. Confirm that traffic is working. Then perform these same steps on the now-standby vCMP Guest, on the other vCMP Host.
