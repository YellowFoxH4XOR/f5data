K000161398: BIG-IP Tenant Management Traffic Routed Out TMM Data-Plane Interface Instead of Management Interface on F5OS-A rSeries

Source

Description

On F5OS-A rSeries appliances hosting BIG-IP tenants, management traffic (such as SSH and ICMP) to a tenant may be unreachable from a remote host, even though the tenant is in a Running state and appears healthy. Packet captures show that inbound SSH and ICMP requests arrive at the tenant's management interface, but reply traffic (SYN-ACK, ICMP echo reply) is sent out a TMM data-plane interface instead of the management interface. This results in failed SSH and ICMP connectivity to the tenant management IP.


Environment

  • F5OS-A rSeries appliances (e.g., r2600)
  • BIG-IP tenant deployed and in Running state
  • HA pair configuration (active/standby tenants on separate physical appliances)
  • Local-only self-IP configured on a VLAN within the BIG-IP tenant whose subnet overlaps with the management subnet of a remote host (e.g., TFTP server, jump host)
  • Remote management access attempted via SSH or ICMP from a host on the overlapping subnet


 Cause

The BIG-IP tenant maintains two separate routing tables: a Linux management routing table and a TMM routing table. If a TMM self-IP subnet (local-only or otherwise) overlaps with the subnet of the remote management host, TMM routes take precedence over Linux management routes. As a result, reply traffic is routed out the TMM data-plane interface instead of the management interface, and never reaches the remote host.

This behavior is documented in:

K99422936: Management traffic routed out TMM interface instead of mgmt interface

Answer/Recommended Actions

To verify and resolve the routing override:

  • Access the tenant via console:
  • virtctl console <tenant_name>-1
  • Check how the Linux kernel routes traffic to the remote host:
  • ip route get <remote-host-IP>
    • If the output shows a TMM self-IP interface (e.g., a VLAN interface) instead of mgmt, the TMM route is overriding the management route.
  • Review the TMM routing table and self-IPs:
  • tmsh show net route
  • tmsh list net self
    • Identify any self-IP subnet that overlaps with the remote host's subnet.
  • Verify the management route configuration:
  • tmsh list sys management-route
    • Confirm a default management route exists pointing to the correct gateway via the management interface.
  • Add a specific management route for the affected subnet:
  • tmsh create sys management-route <route-name> gateway <mgmt-gateway-IP> network <remote-subnet/mask>
  • tmsh save sys config
  • Verify the fix:
  • ip route get <remote-host-IP>
    • The output should now show routing via mgmt instead of the TMM interface.
  • Confirm SSH and ICMP connectivity from the remote host to the tenant management IP.

Additional Information

  • This issue is more likely to occur on the standby unit of an HA pair, as the active unit may have floating self-IPs active that result in a different effective TMM routing table.
  • The active and standby tenants reside on separate physical appliances with independent network paths; a routing discrepancy on one appliance does not affect the other.
  • Console access to the tenant via virtctl is unaffected by this issue and can be used for troubleshooting.
  • If SSH console access via the rSeries host (port 7001) is needed, ensure the tenant-console user is unlocked:

config system aaa authentication users user <tenant-console-user> config set-password

config system aaa authentication users user <tenant-console-user> config expiry-status enabled
