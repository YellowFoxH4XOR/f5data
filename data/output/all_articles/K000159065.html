K000159065: Understanding Why DNS CNAME Redirection Does Not Change Website Content

Description

When using DNS CNAME records to redirect traffic, you may observe that while DNS queries return the expected CNAME response, end-user browsers still display the original website content instead of the redirected destination. This occurs because DNS-based redirection (CNAME) does not modify the HTTP Host header or TLS SNI sent by the browser.

For example, if you own a domain called bob.com and normally serve your website as www.bob.com, users typing just bob.com in their browser may not see the expected content even when a CNAME record points bob.com to www.bob.com.

Environment

  • BIG-IP DNS (GTM)
  • DNS CNAME records
  • Virtual hosting environments
  • Modern web browsers
  • HTTP/HTTPS virtual servers

Cause

A CNAME record only affects DNS resolution and tells the browser which IP address to connect to. It does not change the HTTP Host header or TLS SNI (Server Name Indication) that the browser sends to the web server.

Example DNS resolution flow:

When a user types bob.com with the following DNS configuration:

bob.com      → www.bob.com (CNAME)
www.bob.com  → 192.0.2.10 (A record)

What actually happens:

  1. DNS asks for bob.com
  2. DNS returns a CNAME to www.bob.com
  3. DNS asks for www.bob.com
  4. DNS returns 192.0.2.10

DNS resolution is now complete. The browser connects to 192.0.2.10, but it still sends:

Host: bob.com
SNI: bob.com

because that is what the user typed in the URL bar

The web server sees at 192.0.2.10 a request for bob.com, not www.bob.com, and serves whatever virtual host is configured for bob.com. This is why a DNS CNAME does not behave like an HTTP redirect, it only changes how the IP address is found, not which site is requested by the browser.

Web platforms such as BIG-IP route traffic using the HTTP Host header and TLS SNI, not based on how DNS was resolved.

Recommended Actions

Choose one canonical hostname for your site (either www.bob.com or bob.com) and configure both DNS and HTTP appropriately.

If you want all traffic to use www.bob.com:

  1. Configure bob.com as an A record pointing to your BIG-IP virtual server IP address
  2. Configure www.bob.com as a CNAME pointing to your application hostname (or as an A record)
  3. Configure an HTTP virtual server on BIG-IP to send an HTTP 301 or 302 redirect from bob.com to www.bob.com
  4. Ensure your TLS certificate includes both bob.com and www.bob.com (or use a wildcard certificate)

If you want all traffic to use bob.com:

  1. Configure bob.com as an A record pointing to your BIG-IP virtual server IP address
  2. Configure www.bob.com as either:
    • A CNAME pointing to bob.com, OR
    • An HTTP redirect to bob.com (requires separate virtual server configuration)
  3. Ensure your TLS certificate includes both bob.com and www.bob.com (or use a wildcard certificate)

Note: DNS alone cannot change the hostname a browser sends. Only an HTTP redirect can modify the requested URL.

Additional Information

Glossary:

  • CNAME record – DNS record that points one name to another
  • A record – DNS record that maps a name to an IP address
  • DNS zone – Administrative domain, for example bob.com
  • FQDN – Fully qualified domain name
  • 301 / 302 – HTTP redirect status codes (301 = permanent, 302 = temporary)
  • Host header – HTTP header containing the requested hostname
  • SNI – TLS Server Name Indication field used to select the correct virtual host

Why CNAMEs are commonly used:

CNAMEs allow applications to point to provider-controlled hostnames that can move between IP addresses without customers needing to change their DNS records.

Example:

www.bob.com          → app-host.example.net (CNAME)
app-host.example.net → 159.60.132.149 (A record) (A record)

The provider controls app-host.example.net and can change IP addresses as needed while www.bob.com remains stable.

Best practice: Allowing both bob.com and www.bob.com to serve different content usually causes confusion with links, cookies, and redirects. Choose one name as the canonical site and redirect the other to it.
