Description

When accessing a virtual server, pages are returned but images do not load.

Environment

  • HTTPS virtual server performing SSL Offload
  • HTTP pool members

Cause

Links to images are returned as http:// rather than https://, causing clients to attempt establishing a non-SSL connection, which will typically be on port 80. The BIG-IP virtual server is listening on port 443 and expecting an SSL connection, so the connection to port 80 will fail unless a listener is also configured on that address and port.

Recommended Actions

Use a Stream profile and iRule to rewrite http:// content links to https:// in HTTP responses returned from pool members.

Important: F5 recommends you perform traffic impacting activities inside of a maintenance window.

Perform the following procedures to implement this solution:

  1. Create the following iRule:

    when HTTP_REQUEST {
        STREAM::disable
        HTTP::header remove "Accept-Encoding"
    }
    when HTTP_RESPONSE {
        if { [HTTP::header value Content-Type] contains "text"} {
           STREAM::expression {@http://@https://@}
           STREAM::enable
       }
    }

    Important: The iRule matching conditions may not match all use cases. See the Additional Information section for further details.

  2. Apply a Stream profile to the virtual server by navigating to Local Traffic > Virtual Servers > <Virtual Server> > Stream Profile, selecting a Stream profile, then clicking Update.

    Note: The default Stream profile is sufficient for this solution.

  3. Apply the newly created iRule to the virtual server under the Resources tab, by moving the iRule to the Enabled column, and clicking Finished.

Additional Information

Applying the Stream profile and iRule will cause clients to request the images in a connection to port 443.

HTTP responses typically contain a Content-Type header which indicates to browsers the type of media they contain.

The iRule will only perform the replacement for responses where the header Content-Type value contains text. This is relevant to most scenarios. If there are responses which do not match the iRule, inspect the HTTP headers in the response using browser Developer Tools to determine the Content-Type value that is returned, then modify the iRule as appropriate.
