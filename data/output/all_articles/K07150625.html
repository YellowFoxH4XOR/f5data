Topic

You should consider using this procedure under the following conditions:
  • Your BIG-IP system is experiencing User Datagram Protocol (UDP) flood attacks.
  • You want to to use a rate limiting iRule to prevent UDP flood attacks.

Description

UDP is a standard protocol for communication across IP networks, but since UDP packets are stateless, they require less error checking and validation, in contrast to TCP. A UDP flood attack attempts to overload a server with requests by saturating the connection tables on every accessible port on a server. Filling the connection table with these requests prevents valid requests from being served, and the server can become inaccessible to valid clients.

The BIG-IP system has the very flexible iRules feature to prevent traffic from impacting a virtual server (in this case, a UDP flood attack). A sample iRule similar to the following example rate limits connections on a UDP based virtual server based on a maximum connection rate allowed per second per client IP address. This iRule also has an allow-list function to bypass the rate limiting checks for IP addresses or subnet addresses that you want to allow.

Important: If you are planning to use the following sample iRule, you must set an appropriate value for the static::maxRate variable that is suitable for your environment because this value determines how many requests a single client IP address can send. If you set this value too low, the iRule limits the requests of a single client IP address unnecessarily. If you set it too high, the iRule allows all client IP address to send the same number of requests, which may overwhelm the application or service behind the virtual server.

when RULE_INIT {
  # Default rate to limit requests
  set static::maxRate 5
  # Default rate to
  set static::warnRate 3
  # During this many seconds
  set static::timeout 1
  #logging control
  set static::debuglevel 3
}
when CLIENT_ACCEPTED {
  if { ([class match [IP::client_addr] equals allowed_networks]) } {
  if { $static::debuglevel >= 3 } {
            log local0. "Returning from irule---allow-list match IP [IP::client_addr]"
        }
        return
  }        
      # Increment and Get the current request count bucket
      set epoch [clock seconds]
      set currentCount [table incr -mustexist "Count_[IP::client_addr]_${epoch}"]
      if { $currentCount eq "" } then {
          # Initialize a new request count bucket
          table set "Count_[IP::client_addr]_${epoch}" 1 indef $static::timeout
          set currentCount 1
      }

      # Actually check for being over limit
      if { $currentCount > $static::maxRate } then {
      if { $static::debuglevel >= 2 } {
            log local0. "ERROR: IP:[IP::client_addr] exceeded ${static::maxRate} requests per second. Rejecting request. Current requests: ${currentCount}."
        }
          event disable all
          drop
      }
      elseif { $currentCount > $static::warnRate } then {
      if { $static::debuglevel >= 2 } {
            log local0. "WARNING: IP:[IP::client_addr] exceeded ${static::warnRate} requests per second. Will reject at ${static::maxRate}. Current requests: ${currentCount}."
        }         
      }
      if { $static::debuglevel >= 3 } {
            log local0. "IP:[IP::client_addr]: currentCount: ${currentCount}"
        } 
}

Prerequisites

You must meet the following prerequisites to use this procedure:
  • You have access to the BIG-IP Configuration utility.
  • You have console or ssh access to the BIG-IP system.
  • You have administrator access to the BIG-IP system.

Procedures

  • Create the rate limiting iRule
  • Create the IP allow-list data group
  • Apply the rate limiting iRule to the virtual server
  • Monitor the log file for the iRule generated log

Create the rate limiting iRule

Impact of procedure: Performing this procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic  >  iRules > iRule List.
  3. Select Create.
  4. Enter a name for the iRule.
  5. For Definition, enter the rate limiting iRule syntax. You may copy the previous sample iRule and modify it according to the your application environment.
  6. Select Finished.

Create the IP allow-list data group

To create a allow-list for the IP addresses you want to bypass the rate limiting checks by the iRule, perform the following procedure:

Impact of procedure: Performing this procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility
  2. Go to Local Traffic  >  iRules  > Data Group List.
  3. Select Create.
  4. Enter a name for the data group.
  5. For Type, select Address.
  6. Under Address Records, for Address, add an IP address or a subnet address.
  7. Select Add.
  8. Select Finished.
Note: You do not need to apply the IP allow-list data group to any BIG-IP LTM configuration. Its purpose is to contain the IP addresses that the rate limiting iRule checks against for allowing.

Apply the rate limiting iRule to the virtual server

Impact of procedure: Performing this procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic  >  Virtual Servers > Virtual Server List.
  3. Select the name of the virtual server to which you want to apply the iRule.
  4. On the Resources tab, under iRules, select Manage.
  5. In the Available list, select the rate limiting iRule that you created in the first procedure from the and move it to the Enabled list.
  6. Select Finished.
