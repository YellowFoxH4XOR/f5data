K11535: BIG-IP WebAccelerator may ignore or corrupt cache expiration headers

Type
Known Issue
Published
2010-05-18
Updated
2023-02-21
Status
Legacy Content
Applies to
  • Legacy Products
  • BIG-IP WebAccelerator: 10.1.0
Source

Known Issue

This is the result of a known issue. The BIG-IP WebAccelerator may ignore or corrupt cache expiration headers sent by the origin web server (OWS).

This behavior occurs when the Ignore no-cache HTTP headers in the response option is selected or cleared. The following behaviors that occur are based upon whether the Ignore no-cache HTTP headers in the response option is selected or cleared, and the directive sent by the OWS:

  • The OWS sends a Pragma: no-cache directive, and the Ignore no-cache HTTP headers in the response option is cleared
  • The OWS sends an Expires 0/-1 directive, and the Ignore no-cache HTTP headers in the response option is selected
  • The OWS sends all three methods of cache control: Cache-Control: no-cache, Expires: 0/-1, and Pragma: no-cache, and the BIG-IP WebAccelerator Ignore no-cache HTTP headers in the response option is cleared.

The OWS sends a Pragma: no-cache directive, and the Ignore no-cache HTTP headers in the response option is cleared

The BIG-IP WebAccelerator corrupts the response from the OWS by adding an extra colon after the Pragma: no-cache directive.

For example:

GET http://test.example.com/image1.jpeg --> 200 OK
Connection: Close
Date: Mon, 07 Dec 2009 18:46:39 GMT
Pragma: no-cache:   <---------------- Notice the extra : on the pragma: no-cache. 
Accept-Ranges: bytes
ETag: "pv7487a567c700a34eca20ca4af54aa0f3"
Server: Apache/2.2.11 (Ubuntu) mod_python/3.3.1 Python/2.6.2 mod_ssl/2.2.11 OpenSSL/0.9.8g mod_perl/2.0.4 Perl/v5.10.0
Content-Length: 218470
Content-Type: image/jpeg
Last-Modified: Sat, 14 Nov 2009 20:18:02 GMT
Client-Date: Mon, 07 Dec 2009 18:46:41 GMT
Client-Peer: 10.10.10.51:80
Client-Response-Num: 1
X-PvInfo: [S10102.C9651.A2008.RA0.G1816.UC6334DFF].[OT/images.OG/images]

The OWS sends an Expires 0/-1 directive, and the Ignore no-cache HTTP headers in the response option is selected

The BIG-IP WebAccelerator correctly preserves the Expires header, but treats the content as expired.

For example:

GET http://test.example.com/image1.jpeg --> 200 OK
Connection: close
Date: Mon, 07 Dec 2009 18:55:36 GMT
Accept-Ranges: bytes
ETag: "pv7487a567c700a34eca20ca4af54aa0f3"
Server: Apache/2.2.11 (Ubuntu) mod_python/3.3.1 Python/2.6.2 mod_ssl/2.2.11 OpenSSL/0.9.8g mod_perl/2.0.4 Perl/v5.10.0
Content-Length: 218470
Content-Type: image/jpeg
Expires: -1  <-------Properly preserved Expires header
Last-Modified: Sat, 14 Nov 2009 20:18:02 GMT
Client-Date: Mon, 07 Dec 2009 18:55:38 GMT
Client-Peer: 10.10.10.51:80
Client-Response-Num: 1
X-PvInfo: [S10232.C9651.A2008.RA0.G1816.UC6334DFF].[OT/images.OG/images]   <---- WebAccelerator treating the content as expired.

The BIG-IP WebAccelerator should only treat the content as expired if the Ignore no-cache HTTP headers in the response option is cleared.

The OWS sends all three methods of cache control: Cache-Control: no-cache, Expires: 0/-1, Pragma: no-cache, and the BIG-IP WebAccelerator Ignore no-cache HTTP headers in the response option is unchecked

Note: Some .NET platforms send all three methods in response to support all versions of HTTP, as well as to support older versions of Microsoft Internet Explorer.

In this situation, the BIG-IP WebAccelerator may corrupt the Pragma: no-cache header in two different ways.

For example:

GET http://test.example.com/image1.jpeg --> 200 OK
Cache-Control: no-cache
Connection: close
Date: Mon, 07 Dec 2009 19:32:54 GMT
Pragma: no-cache: no-cache   <-----  Notice now that no-cache is listed twice.
Accept-Ranges: bytes
ETag: "pvc12fdfbe7b04f5306cb05b03f5f7cf4d"
Server: Apache/2.2.11 (Ubuntu) mod_python/3.3.1 Python/2.6.2 mod_ssl/2.2.11 OpenSSL/0.9.8g mod_perl/2.0.4 Perl/v5.10.0
Content-Length: 218470
Content-Type: image/jpeg
Expires: -1
Last-Modified: Sat, 14 Nov 2009 20:18:02 GMT
Client-Date: Mon, 07 Dec 2009 19:32:57 GMT
Client-Peer: 10.10.10.51:80
Client-Response-Num: 1
X-PvInfo: [S10232.C9651.A2008.RA0.G1816.UC6334DFF].[OT/images.OG/images]


GET http://test.example.com/image1.jpeg --> 200 OK
Cache-Control: public, s-maxage=4444, max-age=3333
Connection: close
Date: Mon, 07 Dec 2009 19:38:49 GMT
Pragma: no-cache: public, s-maxage=4444, max-age=3333  <------- Max-age information is inserted into the header.
Accept-Ranges: bytes
ETag: "pv6bc2cb7e4035cde5f46b649021ab45a0"
Server: Apache/2.2.11 (Ubuntu) mod_python/3.3.1 Python/2.6.2 mod_ssl/2.2.11 OpenSSL/0.9.8g mod_perl/2.0.4 Perl/v5.10.0
Content-Length: 218470
Content-Type: image/jpeg
Expires: -1
Last-Modified: Sat, 14 Nov 2009 20:18:02 GMT
Client-Date: Mon, 07 Dec 2009 19:38:51 GMT
Client-Peer: 10.10.10.51:80
Client-Response-Num: 1
X-PvInfo: [S10201.C9651.A2008.RA0.G1816.UC6334DFF].[OT/images.OG/images]

F5 Product Development tracked this issue as CR132526 and it was fixed in BIG-IP version 10.2.0. For information about upgrading, refer to the BIG-IP WebAccelerator release notes.
