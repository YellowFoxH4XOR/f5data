Description

When F5 Container Ingress Services (CIS) is configured to manage BIG-IP DNS (GTM) wideIPs through ExternalDNS custom resources, GTM provisioning can stop working and the controller log repeats the same error roughly every 128 seconds.

New ExternalDNS resources no longer deploy as wideIPs, and the condition does not clear on its own.

  • GTM/ExternalDNS provisioning halts; newly created or updated ExternalDNS resources never appear as wideIPs on the BIG-IP.
  • The CIS controller log repeats the same error on a backoff interval that grows to and then stays at 128 seconds
  • Restarting the CIS pod temporarily restores GTM provisioning, but the error returns while the offending resource still exists
  • On the BIG-IP, one or more wideIPs are left with no pool (a "pool-less" wideIP)
  • At the default INFO log level (no traceback is shown, and the triggering resource is not named):

[__main__ ERROR] Unexpected error: list index out of range
[__main__ ERROR] Error applying config, will try again in 128 seconds

  • At --log-level=DEBUG, the full Python traceback is visible:

[__main__ ERROR] Unexpected error: list index out of range
Traceback (most recent call last):
  File "/usr/local/bin/bigipconfigdriver.py", line 396, in _do_reset
    gtmIncomplete=self._update_gtm(config)
  File "/usr/local/bin/bigipconfigdriver.py", line 477, in _update_gtm
    mgr._gtm.delete_update_gtm(
  File "/usr/local/bin/bigipconfigdriver.py", line 792, in delete_update_gtm
    self.handle_operation_create(gtm,partition,gtmConfig,opr_config[opr],opr)
  File "/usr/local/bin/bigipconfigdriver.py", line 866, in handle_operation_create
    self._gtm_config[partition]['wideIPs'][index]["pools"][...]
IndexError: list index out of range

Environment

  • F5 Container Ingress Services (CIS / k8s-bigip-ctlr)
  • BIG-IP DNS (GTM) provisioning via CIS
  • ExternalDNS custom resource (CRD mode)

Cause

  • This is a defect in the CIS GTM/ExternalDNS agent (bigipconfigdriver.py), tracked as Bug ID 2564737
  • During each reconcile, the CIS GTM agent rebuilds its desired GTM configuration from the ExternalDNS resources, compares it against an in-memory cache (self._gtm_config), and pushes only the differences to BIG-IP DNS.
  • When a wideIP loses its last pool, the delete path removes the pool from the cached wideIP entry but does not remove the wideIP itself. This leaves a cache entry for a wideIP with an empty pool list (pools: []) — effectively a DNS name that points to nothing.
  • Later in that same reconcile pass, the create/update path walks the cache and indexes into that wideIP's pool list (...['wideIPs'][index]["pools"][...]). Because the list is now empty, the code reaches for an element that does not exist and raises IndexError: list index out of range.
  • That exception aborts the reconcile before the cache can be refreshed, so the bad entry is never cleaned up. Every subsequent reconcile pass (approximately every 128 seconds) trips over the same "poisoned" wideIP and fails again. The result is that all GTM provisioning stays stuck, and a restart alone does not permanently resolve it — if the offending resource still exists, the freshly rebuilt cache is re-poisoned on the next pass.

Answer/Recommended Actions

  • Upgrade CIS to 2.20.5 or later, which contains the fix for Bug ID 2564737.
  • In the fixed version, the GTM reconcile no longer fails when a wideIP's pool list becomes empty; the pool-removal event is followed by a successful, continued reconcile instead of the IndexError, and no pool-less wideIP "poison" is created.

Additional Information

Bug ID: 2564737 (fixed in CIS 2.20.5)
