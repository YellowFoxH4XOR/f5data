K000163125: IPsec VPN Fails to Establish Through Routed DDoS When IKE_AUTH Is Fragmented at the IPv4 Layer

Published
2026-09-30

Applies to

Source

Description

An IKEv2 VPN connection might fail during authentication when an IKE_AUTH message exceeds the effective path MTU and is fragmented at the IPv4 layer while traversing an F5 Distributed Cloud Routed DDoS GRE tunnel.

This issue only affects IKE traffic that relies on IPv4 UDP fragmentation. It does not occur if the packet remains below the effective path MTU and is transmitted without fragmentation, or if RFC 7383 IKEv2 fragmentation is correctly negotiated and used to split the IKE message into smaller packets before IP transmission.

Environment

  • F5 Distributed Cloud
    • Routed DDoS 
      • GRE Tunnels

Cause

The IKE initiator generates an IKE_AUTH message that results in a UDP datagram larger than the effective path MTU.

If IKEv2 fragmentation is not negotiated, the oversized UDP datagram is fragmented at the IPv4 layer. F5 Distributed Cloud Routed DDoS default security policies block fragmented UDP traffic as part of their fragment-handling protections.

If any fragment is blocked, the VPN concentrator cannot reassemble and process the complete request, so the initiator retransmits it and the VPN connection does not complete.

This issue does not occur when either:

  • IKE_AUTH remains below the effective path MTU and does not require IPv4 fragmentation; or
  • RFC 7383 IKEv2 fragmentation is correctly negotiated and used to divide a large IKE message into smaller IKE messages before IP transmission, avoiding IPv4 UDP fragmentation.

During troubleshooting a packet capture might show:

  • Successful completion of IKE_SA_INIT.
  • A large IKE_AUTH request over UDP/4500.
  • Multiple IPv4 fragments carrying the request.
  • Repeated IKE_AUTH retransmissions.
  • No corresponding IKE_AUTH response.
  • ICMP Type 3 Code 13 (Communication Administratively Filtered).

Answer / Recommended Actions

  1. Enable RFC 7383 IKEv2 fragmentation on the VPN concentrator and supported VPN clients.
  2. Confirm that both IKEv2 peers support and negotiate fragmentation. Configuring only a fragmentation size or threshold does not guarantee that RFC 7383 IKEv2 fragmentation is being used.
  3. Review the IKE-specific logs and packet captures for the following notification during IKE_SA_INIT:
    IKEV2_FRAGMENTATION_SUPPORTED
  4. Confirm that large IKE_AUTH exchanges are transmitted as multiple IKEv2 encrypted fragment messages rather than as fragments of a single IPv4 UDP datagram.
  5. Do not rely on TCP MSS adjustment to resolve the issue. TCP MSS settings do not affect IKE traffic, which uses UDP/500 or UDP/4500.
  6. Collect simultaneous packet captures from the VPN client and concentrator during the same failed connection attempt.
  7. After enabling IKEv2 fragmentation, verify that:
    • IKE_SA_INIT completes.
    • Both peers advertise IKEv2 fragmentation support.
    • IKE_AUTH uses IKEv2 encrypted fragments.
    • The packets remain below the effective path MTU.
    • IPv4 fragmentation is no longer required.
    • The IKE_SA remains established.

Additional Information

IKEv2 fragmentation versus IPv4 fragmentation

These are separate mechanisms:

  • IPv4 fragmentation divides one oversized IP datagram into multiple IP fragments.
  • IKEv2 fragmentation divides a large IKE message into smaller IKE protocol messages before they are transmitted by IP.

RFC 7383 IKEv2 fragmentation is preferred because it avoids relying on network devices to forward and reassemble IPv4 fragments.

MTU considerations

Reducing a VPN data tunnel MTU alone might not resolve this issue. The MTU setting for encrypted VPN data might not control the size of IKE control plane messages.
