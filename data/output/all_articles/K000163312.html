K000163312: An IPsec IKEv1 tunnel may fail to establish when an IKEv2 peer uses the same local IP address

Type
Support Solution
Published
2026-10-29
Updated
2026-10-29
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000163312

Description

An IPsec IKEv1 tunnel may fail to establish when an IKEv2 peer uses the same local IP address, even when the IKEv2 peer is disabled.
Symptoms include incomplete Phase 1 or Phase 2 negotiation and log messages such as:

  • Peer not responding

  • Phase 2 deleted

  • phase1 negotiation failed due to time up

  • Can't find ike peer config

  • Aborting isakmp

Environment

  • BIG-IP LTM system terminating IPsec tunnels.
  • IKEv1 and IKEv2 peers configured on the same BIG-IP system.
  • NAT traversal enabled.
  • An IKEv1 peer and an IKEv2 peer configured with the same local IP address.
  • The IKEv2 peer may be disabled.
  • The affected tunnel uses UDP/500 and UDP/4500.

Cause

The BIG-IP system uses listeners to process IKE traffic, and the listeners cannot reliably distinguish IKEv1 and IKEv2 when both versions use the same local IP address. Incoming NAT-T traffic may be directed to the IKEv2 listener, which cannot find a matching active IKEv2 peer configuration and aborts the flow. This prevents the intended IKEv1 tunnel from completing negotiation.

IKEv1 and IKEv2 tunnels must use separate local IP addresses. Multiple tunnels using the same IKE version may reuse a local IP address, but an IKEv1 tunnel and an IKEv2 tunnel must not share one.

Recommended Actions

  1. Review the local IP address configured for each IKEv1 and IKEv2 peer.
  2. Identify any IKEv1 and IKEv2 peers that share the same local IP address.
  3. If the IKEv2 peer is not required, remove it from the configuration.
  4. If the IKEv2 peer is required, assign it a unique local IP address that does not overlap with any IKEv1 peer.
  5. Ensure that the local IP addresses are existing BIG-IP self IP addresses. Floating self IP addresses may be used; virtual addresses must not be used.
  6. Re-establish the affected IPsec tunnel.
  7. Verify that Phase 1 and Phase 2 security associations become established and remain stable.
  8. If necessary, delete and recreate only the affected IPsec security association, or disable and re-enable the affected IKE peer during a controlled maintenance window.
  9. Avoid restarting TMM unless correcting the peer configuration and re-establishing the affected tunnel do not resolve the issue, because restarting TMM can affect other active traffic and tunnels.

Additional Information

  • UDP/500 traffic confirms that IKE packets are present, but does not confirm successful Phase 1 negotiation or establishment of the IPsec tunnel.
  • A disabled IKEv2 peer can remain relevant when it shares a local IP address with an active IKEv1 peer because traffic may still be processed by the IKEv2 listener.
  • If the configuration uses IPsec tunnel mode, configure different tunnel-local-address values for IKEv1 and IKEv2.
  • If the configuration uses IPsec interface mode, configure different local-address values for IKEv1 and IKEv2.
