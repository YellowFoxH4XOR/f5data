Description

Clock advanced logs can occur when using stream profile with ASM policy on a virtual server to scan large amounts of data


Environment

Configuration on affected virtual server should include:


Stream profile

ASM functionality - policy and web-security profile.


Cause

The data to be scanned by the stream profile is large and has been buffered and released in one go.


Recommended Actions

Try activating chunking in the stream profile. It is recommended to modify the setting in a custom stream profile and change virtual server to use that. This is not the same chunking as the HTTP Profile provides, though the stream profile does use and require that as well. Normally the default size of 4KB chunks in the stream profile is sufficient.


From command line (here str-ch is the custom profile name):

  tmsh create ltm profile stream str-ch defaults-from stream chunking enabled

tmsh save sys config

Use the custom stream profile in place of default on relevant virtual servers.


Alternatively, create, modify a custom stream profile, and then apply it in web user interface, with relevant section found at:

Local Traffic > Profiles > Other > Stream


Additional Information

There are many possible causes of tmm logging 'Clock advanced' logs, but they fall into two categories. The first is when tmm is actually solidly busy on one task during that period, and the other type is that the the tmm thread has not been scheduled to run in this period. The latter is more often seen on Virtual Edition systems where the hypervisor may not have scheduled the vCPU the tmm thread runs on appropriately.


The clock advanced logs should correlate with data passing through the virtual server with stream profile, which probably will appear busy in virtual_server_cpu_stat table. If the stream profile is the cause then the tmm thread handling the data examined will be busy at that time. Even if very busy, idle enforcer activity may not be evident in kern logs as ASM activity can suppress activation of the idle enforcer.


It makes sense to rule out irule execution being the cause if possible. It is though extremely rare to see irules run for 0.1s or more at a time.


The system db variable tmm.tcl.executionlimit may be used to help diagnose if irule is causing the clock advanced. It defaults to 500, which is too high to be useful normally. Reduce the value to 100, or at least below the ticks shown on a typical clock advanced log. If, when a long enough clock advance happens, no accompanying log shows which irule was running, then an irule isn't likely to be to blame. The stream profile uses TCL but isn't an irule, though can be controlled by them.
