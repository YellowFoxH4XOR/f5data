Known Issue

If the BIG-IP system executes a suspending iRules command within the Tcl catch command, the system does not suspend iRule processing as expected. When this occurs, the iRule does not function as expected and TMM may crash.

This issue occurs when the following condition is met:

  • An iRule executes a suspending iRules command within the Tcl catch command

The expected behavior is that the BIG-IP system suspends iRule processing on the connection when the suspending command is executed; then once the suspending command has completed, the BIG-IP system resumes iRule processing on the connection, beginning with the evaluation of the catch command that encloses the suspended command.

The Tcl catch command is intended to evaluate the code block provided to it, and trap runtime errors and exceptions within the code block that would abnormally terminate execution. It can be useful for debugging iRule logic that is based on information that is extracted or derived from the traffic streams processed by the BIG-IP system or other dynamic data. For example, the following iRule is intended to log one comment or the other, then either select a pool or discard the connection, based upon the success of the RESOLV::lookup command:

when HTTP_REQUEST {

if { catch {[RESOLV::lookup @10.1.1.74 [HTTP::host]} err] }{
log local0. "Error resolving requested host [HTTP::host]: $err"

discard
} else {
log local0. "[HTTP::host] resolved successfully"
pool myPoolA
}
}

However, on BIG-IP versions affected by this issue, the iRule will not suspend iRule processing, and connections may be processed incorrectly as follows:

  • The RESOLV::lookup command begins to execute
  • Since iRule processing is not suspended, the catch command is executed immediately, without waiting for the resolution results, and returns a value of 0 OK.
  • The if statement is evaluated as true, causing the first clause of the if statement to be evaluated.
  • The comment is logged, the connection is discarded, and the flow is removed from the connection table.
  • The RESOLV::lookup command completes successfully
  • iRule processing for the connection is resumed with the evaluation of the catch command, as if iRules processing had been suspended.
  • TMM crashes when iRules processing resumes because the connection no longer exists in the connection table.

Note: If the connection had not yet closed, and the catch command returned the expected value, the if statement would evaluate this time as false, causing the second clause of the if statement to be evaluated, the comment to be logged, and the pool to be selected.

Impact

iRules affected by this issue may not process traffic as expected. In addition, traffic processing may be briefly interruped each time TMM crashes.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • BIG-IP iHealth lists Heuristic H380423 on the Diagnostics > Identified > High screen.
  • Code blocks that are conditioned on a catch statement may be executed outside the expected conditions.
  • iRule logic following a catch statement may be executed twice with different results.
  • TMM may crash repeatedly with a SIGSEGV fault and produce a stack trace in the /var/log/tmm file.

Workaround

To work around this issue, you can remove the catch command from any affected iRules.

Impact of workaround: Removing the catch command may result in connections being reset when runtime errors occur.

  1. Log in to the Configuration utility.
  2. Click Local Traffic.
  3. Click iRules.
  4. Click on the name of the affected iRule.
  5. Edit the iRule to remove the offending command.
  6. Click Update.
