Broken function level authorization

Broken function level authorization is similar to Broken object level authorization | APIs and the OWASP Top 10 guide. Both relate to attackers accessing API endpoints that they are not authorized to, due to inadequate or improper authorization mechanisms to validate user requests. Broken function level authorization differs in that the target is API functions as opposed to objects. The main cause is when roles, groups, or user functions are not clearly defined or are too complex, and, as a result, authorization checks are not completely implemented based on clear user group and roles.

Attackers can exploit this vulnerability to gain access to unauthorized resources, take over another user's account, or escalate privileges to run administrative functions.

Broken function level authorization attack scenario

In the following attack scenario, the attacker manipulates the directory in the URI path and HTTP method to perform administrative functions.

  1. The attacker uses a legitimate account and sends the following API request to retrieve the user information:

    GET https://api.example.com/v2/userid-1a-1234/userinfo

  2. The attacker uses a script or tool to manipulate the request, enumerating a range of URLs and receives a valid response for the URL /all_userinfo. This is an unprotected administrative function that returns information for all users:

    GET https://api.example.com/v2/userid-1a-1234/all_userinfo

  3. The attacker expands the scope of his attack by manipulating the HTTP method of the API request to delete users, as follows:

    DELETE https://api.example.com/v2/userid-1a-2222

Secure your APIs against broken function level authorization attacks with F5 products

To protect your APIs, best practices recommend that you first plan and have a good overall view of the user and group hierarchy of your organization so that you can review and secure all API endpoints and authorization flows and deny all access, by default, requiring explicit grants to specific roles for access to every function.

Use BIG-IP APM to mitigate broken function level authorization attacks

BIG-IP APM as an API gateway proxy is your first line of defense and is well positioned to examine API requests' URI paths, HTTP content, and JWT tokens, and it communicates with other application servers for you to implement a set of complete authorization checks to secure your APIs.

To secure your APIs against broken function level authorization attacks, implement the following:

  • Authorization mechanisms to validate that the API calls are authorized to perform what they are requesting for.

    The system processes API requests through Per-request policies. Through the per-request policy flow, you can extract a range of information from the API request, assign them to subsession or per-flow variables and validate the values to ensure each request is authorized. Use a combination of the following in per-request policies based on your application logic to design and implement the authorization mechanism you want:

    • Per-request policy branches
    • Subsession and per-flow variables
    • Subroutine gating criteria

For example, you can enforce the following application logic to validate API calls:

For a user to make a POST request to a specific API endpoint (for example, /api/v1/users/export_all), they must be a member of the administrators group. To implement this, you create a branch rule in the per-request policy that examines the value of a session variable and scope value extracted from a JWT token.
