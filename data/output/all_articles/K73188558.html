Description

When a file is deleted from a unix filesystem, the contents of the file are not actually removed until all open file handles on that file are closed.  This means that a file can be in-use by a process, and still deleted (eg,, using the "rm" command), but as far as that process is concerned, the file is still there, and once the process ends, or otherwise closes the file, the kernel makes the disk space it was using available.

This can lead to a situation where a hung or unresponsive process has a file open which is occupying a lot of disk space, and in extreme situations, this could cause a mount point to run out of free space, with no available files to delete.

It is possible to 'truncate' a deleted file, freeing up the space it was using, even though it is still held open. This procedure should be carried out carefully, with the risks fully assessed before proceeding, as many processes will react badly or in unexpected ways if their data files are altered or truncated while they're still using them.  Care should be taken to determine why the owning process has hung, and what  it would likely do if one of the files it has open was truncated.  In most cases, it's better and safer to kill and restart the processes that own the file, so that it is cleanly closed, but there are exceptions - for example, truncating the file /var/tmp/mcpd.out is generally considered a safe procedure (see K09512955 ) because we know that this file only contains debug-level log output, that mcpd never reads from it, and restarting the mcpd process is service-impacting.   

Secondly, it's important to understand the difference between filesystems that occupy physical disk space and those that do not.   The unix directory structure consists of a tree of mount points where various filesystems are connected. Some cases these will be backed by physical storage devices such as hard drives and SSDs, but others will be memory based, or virtual filesystems that have no underlying storage at all.

For example, the /dev filesystem provides an I/O interface to system drivers and devices, but occupies no space. Similarly the /proc filesystem allows for information about processes to be presented in what appears to be files and folders, but also occupies no space.  The tmpfs and hugetlbfs type of filesystems are also memory based and while they do provide storage, it's all in RAM.  Furthermore, some processes have been intentionally designed (tmm does this, for example) to open and then immediately delete their temporary memory-based files, even though those files are still  being actively used, to ensure that they're never left behind if the process was to exit uncleanly. It is therefore normal to see "(deleted)" files showing up in the output of the 'lsof' command, and this does not, by itself, indicate a problem with the BIG-IP system.

For the types of filesystems that do utilise physical storage (hdd / ssd) systems, the unix directory structure consists of mount points where those filesystems are attached, and each of those 'mount points' can independently run out of space, so in order to address low disk space concerns, you must first identify which mount point(s) the issue is present on, and then focus on only the files that are stored  under that mount point.  In other words if there is insufficient disk space to write a file to /var/log/, deleting files from /shared or /home will not help, as they are on different mount points.


Environment

  • Critically low disk space on one or more mount points.


Cause

None


Recommended Actions

With that in mind, if, after careful consideration, or direction by F5 Support staff, it is determined that a deleted file needs to be truncated to free up physical disk space, the instructions below can be followed.

The 'lsof' command can be used to list deleted files that are still held open. For example, if I create a new file in /var/log, and while leaving it open, delete it in another terminal, then run lsof, I see it showing as (deleted):

(session-1):# (ls ; cat ) >  /var/log/test 

(session-2):# rm /var/log/test
(session-2):# lsof 2>/dev/null | grep deleted | grep test 
bash      28996            root    1w      REG              253,3        730        184 /var/log/test (deleted)
cat        28998            root    1w      REG              253,3        730        184 /var/log/test (deleted)



The output of lsof contains a number of columns, but the most  useful are the process name, pid, filehandle, and size of the file.   In this case, the size is 730 bytes, and there are  two filehandles attached to /var/log/test, one from bash (pid 28996, filehandle 1), and the other from cat (pid 28998, filehandle 1).  The process's filehandle is the 4th column in the lsof output.

The cleanest and safest way to recover disk space occupied by deleted files is to terminate all the processes that have the file held open. 

[root@gtm-17002-2-121:Active:Standalone] config #  kill 28996 28998


If the process(es) do not respond to kill signals, or if they can not be terminated because of to an undesirable service impact, and it is known that the contents of the deleted file in question is safe to remove, then the file can be truncated by referencing it through the proc filesystem.   All files held open by a process are visible under /proc/<pid>/fd, for example:

[root@gtm-17002-2-121:Active:Standalone] config # ls -l /proc/28996/fd/
total 0
lrwx------. 1 root root 64 May 18 12:01 0 -> /dev/pts/5
l-wx------. 1 root root 64 May 18 12:01 1 -> /var/log/test (deleted)
lrwx------. 1 root root 64 May 18 12:01 2 -> /dev/pts/5
lrwx------. 1 root root 64 May 18 12:01 255 -> /dev/pts/5

[root@gtm-17002-2-121:Active:Standalone] config # ls -l /proc/28998/fd/
total 0
lrwx------. 1 root root 64 May 18 12:01 0 -> /dev/pts/5
l-wx------. 1 root root 64 May 18 12:01 1 -> /var/log/test (deleted)
lrwx------. 1 root root 64 May 18 12:01 2 -> /dev/pts/5


If necessary, the content of the deleted file can be viewed by simply using the cat command - in this case, the content of the file is the output of the ls command that was run earlier when we created that file:

[root@gtm-17002-2-121:Active:Standalone] config # cat /proc/28998/fd/1 |head -5
aaa
api_settings
big3d
BigDB.dat
bigip


The disk space occupied by this file can be recovered by truncating the file to zero bytes:

[root@gtm-17002-2-121:Active:Standalone] config # truncate -s0 /proc/28998/fd/1
[root@gtm-17002-2-121:Active:Standalone] config # cat /proc/28998/fd/1 

# (no output - the deleted file is now empty, and the disk space it was using is available)


Another way to truncate a file is to redirect "nothing" into that file, using shell redirection syntax:

[root@gtm-17002-2-121:Active:Standalone] config #  > /proc/28998/fd/1

 

    Additional Information

    The recommended and safest way to recover disk space occupied by a deleted file will always be to terminate the process(es) that have open file handles on that file.  This could mean rebooting the BIG-IP device, to ensure that any dependencies are also restarted correctly. 

    Manual truncation of a deleted file must always be carried out with due care and knowledge of what the expected result is.  Typically this would be an action only be only be carried out at the request of an F5 Support Engineer.

    The presence of deleted files in a running BIG-IP system is both normal and not a direct indication of a problem.
