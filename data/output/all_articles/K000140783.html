K000140783: How to provide a blank/empty CRL signed by the CA for SSL Orchestrator (SSLO)

Description

The issue we are trying to resolve is how to provide a blank CRL signed by the CA. The key is stored in the hardware HSM on the device. The current sticking point is how do we interact with the key in the HSM to sign the CRL.

Environment

Relevant environmental factors specific to the topic

  • Configuration objects and settings Certificate Authority (CA), Hardware Security Modules (HSM), Certificate Revocation List (CRL)
  • SSL Orchestrator (SSLO)

Cause

The openssl binaries on cBIP are compiled with HSM support. This basically means you can point openssl at the “stub” key in the file system and that will engage the real key in the HSM.”

Recommended Actions

1) Create a blank CRL:

openssl ca -config ca.conf -gencrl -keyfile <path to CA key> -cert <path to CA cert> -out testcrl.crl

Note; An assumption is made here that you not running appliance mode and have access to shell.

2) Paths to CA key and certificate are their respective paths in the file store (disk).

Example:

3) Get the paths to the files stored on disk:

ls /config/filestore/files_d/Common_d/certificate_key_d/

…

/config/filestore/files_d/Common_d/certificate_key_d/:Common:testca_143018_1

 

ls /config/filestore/files_d/Common_d/certificate_d/

…

4) Generate the CRL:

openssl ca -config ./etc/pki/tls/openssl.cnf -gencrl \

-keyfile "/config/filestore/files_d/Common_d/certificate_key_d/:Common:testca_143018_1" \

-cert "/config/filestore/files_d/Common_d/certificate_d/:Common:testca_143020_1" \

-out testcrl.crl

5) So, then the way it would work:

  1. Generate your CRL from the forging CA. Assuming the CRL lasts for a few days/weeks, you’ll probably want some sort of automated process to update this.
  2. Base64 the CRL or dump directly into an iFile.
  3. Add an iRule to the SSLO topology VIP that inserts the CRLDP extension on the outgoing forged cert:

SSL::forward_proxy extension CRLDP "http://something.com/forgingca.crl"

6) Create a separate HTTP VIP listening on the client side that resolves to the name used in the above CRLDP value, then add an iRule that simply returns the CRL data on HTTP request.
