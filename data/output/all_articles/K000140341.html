Description

Dynamic CRL checking for client certificate authentication generally works with following order.

  1. BIG-IP first request client to provide its certificate for certificate authentication.
  2. Once client certificate is received by BIG-IP, BIG-IP checks the "X509v3 CRL Distribution Points" extension inside client certificate.
  3. Then, BIG-IP tries to resolve the FQDN of the "X509v3 CRL Distribution Points" URL and sends DNS request via DNS resolver, so that BIG-IP can download CRL from the specified "X509v3 CRL Distribution Points" URL.
  4. After BIG-IP successfully resolves the IP address of CRLDP FQDN. BIG-IP tries to download CRL from the specified "X509v3 CRL Distribution Points" URL.
  5. Once CRL is successfully downloaded, BIG-IP caches it and checks client certificate against CRL to see if client certificate is revoked or not.
  6. If client certificate is revoked, client side SSL connection is torn down. If client certificate is valid, client is allowed to access to resource (e.g., access to pool member, access to APM resources...etc).

Here is packet flow of normal/working case (once CRL file is successfully downloaded and cached, further DNS or HTTP CRL download traffic may not be captured, as BIG-IP uses locally cached one).

Figure: Dynamic CRL working case

 

Under specific configuration, DNS name resolution may not happen and client side SSL connection may be torn down with "alert(46) unknown certificate error" error message as follows.

Jul 16 13:02:15 bigip.local warning tmm4[11974]: 01260009:4: 10.1.1.50:52492 -> 10.1.1.176:443: Connection error: ssl_hs_do_crl_validation:6335: alert(46) unknown certificate error
Jul 16 13:02:15 bigip.local warning tmm4[11974]: 01260013:4: SSL Handshake failed for TCP 10.1.1.50:52492 -> 10.1.1.176:443

Here is packet flow of non-working case. Neither DNS traffic (of CRLDP FQDN name resolution) nor CRL download (HTTP) traffic is captured.

Figure: Dynamic CRL non-working case

 

Environment

  • Dynamic CRL checking for client certificate authentication
  • Net DNS resolver "Forward Zone" configuration does not match to the CRLDP FQDN inside client certificate

 

Cause

The error message can be seen at the time when DNS resolver "Forward Zone" configuration does not match to the client certificate CRLDP FQDN.

Here is example of non-working case. Client certificate's CRLDP FQDN is "ubuntu2204server1.f5ss.local". However, DNS resolver forward zone is specified as "invalid.local". Hence, DNS resolver does not try to resolve "ubuntu2204server1.f5ss.local" and CRL download process does not fire.

### client certificate CRLDP ###
root@ubuntu2204client1:~/f5ss.local.cert# openssl x509 -in testuser101.crt -text -noout | grep CRL -A 2
            X509v3 CRL Distribution Points:
                Full Name:
                  URI:http://ubuntu2204server1.f5ss.local/mycrl.crl
root@ubuntu2204client1:~/f5ss.local.cert#

Recommended Actions

Make sure DNS resolver forward zone is correctly covering FQDN of client certificate CRLDP FQDN.


For example, forward zone name "f5ss.local" can cover CRLDP FQDN "ubuntu2204server1.f5ss.local".

Figure: DNS resolver with specific zone name

net dns-resolver /Common/my_dnsresolver {
    forward-zones {
        f5ss.local {
            nameservers {
                192.168.10.201:53 { }
            }
        }
    }
    route-domain /Common/0
}

 

Or alternatively, forward zone "." (dot) may be the easiest way to see if name resolution correctly fire.

Figure: DNS resolver with "." (dot) zone

net dns-resolver /Common/my_dnsresolver {
    forward-zones {
        . {
            nameservers {
                192.168.10.201:53 { }
            }
        }
    }
    route-domain /Common/0
}

 

Additional Information

Once CRLDP FQDN is successfully resolved and CRL file is successfully downloaded and cached, you will find binary CRL file under "/config/filestore/crl_file_cache_d/" directory. The cached binary CRL file is neither PEM nor DER format.

[root@bigip:Active:Standalone] config # ls -l /config/filestore/crl_file_cache_d/
total 8
-rwx------. 1 root root 5304 Jul 16 13:04 http___ubuntu2204server1_f5ss_local_mycrl_crl.1
[root@bigip:Active:Standalone] config #

 

If CRL file is not saved under "/config/filestore/crl_file_cache_d/", CRL download might have failed due to any reason. At such time, it is better to check CRL file download traffic by tcpdump first.

Depending on CRLDP server IP address and BIG-IP routing configuration, CRL download traffic may traverse either management interface or TMM interface. On the following example, assuming CRLDP is HTTP URI (80/TCP).

[case-1) : CRLDP server is reachable via management interface]

# tcpdump -nni eth0 -s0 host [CRLDP server IP address] and port 80

[case-2) : CRLDP server is reachable via TMM interface]

# tcpdump -nni 0.0:nnn -s0 host [CRLDP server IP address] and port 80

 

Cache Timeout

The Dynamic CRL compares the current time and the CRL "Next Update" property,

BIG-IP checks every 10 minutes to see if it has expired. If CRL has expired, BIG-IP will fetch the latest CRL file from CRLDP.

Use the following command to check Next update timestamp in the crl file:

openssl crl -inform der -in test.crl -text

...

Last Update: Nov 19 02:52:29 2024 GMT

Next Update: Nov 26 15:12:29 2024 GMT

 

To manually delete Dynamic CRL cache, use the following steps.

1. Delete crl cache file in /config/filestore/crl_file_cache_d/

Example: 

rm http___www_f5_com_crl_crl.1

 

2. Restart keymgmtd process to reload cache:

tmsh restart sys service keymgmtd
