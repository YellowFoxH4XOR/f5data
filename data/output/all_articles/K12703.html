K12703: A virtual server may fail to forward traffic when using both a VLAN group and a one-armed configuration

Known Issue

This is the result of a known issue. By design, the BIG-IP system ensures that traffic cannot ingress a VLAN group on one VLAN and egress the VLAN group on the same VLAN, as this would be an illegitimate traffic pattern. However, if a listener other than the VLAN group is handling the traffic (for example a virtual server), traffic may legitimately ingress and egress the VLAN group through the same VLAN. This behavior is expected of the BIG-IP system. However, due to changes introduced in BIG-IP version 10.2.0, the BIG-IP system does not correctly handle traffic that ingresses a VLAN group and matches a FastL4 virtual server that would send the traffic back out of the same VLAN.

Consider the following diagram and the ensuing example:

 

 

  • The BIG-IP system in the image above is configured with the external and internal VLANs.
  • Both VLANs are assigned to the vg1 VLAN group.
  • A self IP address of 192.168.1.100 with a netmask of 255.255.255.0 is associated with the vg1 VLAN group.
  • Two hosts, that we will call client and server, reside on the external VLAN. Their respective IP addresses are 192.168.1.50 and 192.168.1.60, with a netmask of 255.255.255.0.
  • The following pool is created on the BIG-IP system:

    pool test_pool {
    monitor all http
    members 192.168.1.60:http {}
    }
  • The following virtual server is created on the BIG-IP system:

    virtual test_vs {
    snat automap
    pool test_pool
    destination 192.168.1.120:http
    ip protocol tcp
    profiles fastL4 {}
    }
  • The client attempts to connect to the virtual server; however, TMM silently drops its traffic. This is because the traffic would ingress and egress the VLAN group on the same VLAN, the external VLAN. This is not how the BIG-IP system is expected to behave; the fact that the traffic is handled by a virtual server ensures the validity of the traffic pattern. Therefore, the traffic should be forwarded.

Note: This issue does not occur in BIG-IP versions prior to 10.2.0.

Note: This issue does not occur when the virtual server uses a protocol profile other than FastL4. For example, standard virtual servers are not affected by this issue.

Note: This issue would not occur if the client and the server resided in different VLANs. For example, if the server resided in the internal VLAN, the traffic would ingress and egress the VLAN group on different VLANs, and as such would not be dropped by TMM.

F5 Product Development tracked this issue as ID 346107 and it was fixed in BIG-IP version 10.2.2. For information about upgrading, refer to the BIG-IP LTM release notes.

Workaround

If your specific requirements allow it, you can work around this issue by re-configuring the affected virtual server(s) to not use the FastL4 profile. For example, the virtual server in the example above could be converted to a standard virtual server.
