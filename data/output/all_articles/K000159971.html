1. Description

This article provides guidance on configuring vCMP guests to span multiple slots on VIPRION platforms, specifically for BIG-IP DNS deployments handling primarily UDP DNS traffic. It addresses questions about:

  • Multi-slot versus single-slot vCMP guest configurations
  • Expected performance and functionality impacts when spanning multiple blades
  • Behavior during blade failure scenarios
  • High availability (HA) configuration requirements
  • Session and state synchronization behavior for BIG-IP DNS

2. Environment

  • Product: BIG-IP DNS
  • Version: 17.1.3 and later
  • Platform: VIPRION chassis with multiple blades (e.g., B4450N, B4340N, B2250)
  • Configuration: vCMP guests with multi-slot allocation
  • Traffic type: Primarily UDP DNS (DNS recursion)
  • Deployment scenarios: Standalone, Active/Standby HA, or Active/Active DNS

3. Cause

None

4. Answer/Recommended Actions

Multi-Slot Configuration Recommendation

F5 strongly recommends configuring vCMP guests to span as many slots as possible. This approach provides:

  • Better redundancy and resource distribution
  • Improved resilience in case of blade failure
  • Fully supported configuration for BIG-IP DNS

Performance and Functionality Impact

  • No negative impact is expected when expanding a vCMP guest across multiple slots
  • Multi-slot configurations are fully supported and recommended
  • DNS functionality, latency, and overall performance remain unaffected
  • Known issues affecting multi-slot vCMP guests on older platforms or software versions have been resolved in BIG-IP 17.1.3

Blade Failure Behavior

When one blade becomes unavailable and the guest continues running on a single slot (Min Number of Slots = 1):

  • The guest will continue to run on the remaining slot with reduced resources
  • DNS features remain functional
  • Performance may degrade due to increased load on the remaining blade
  • Traffic will be redistributed and memory usage per blade will increase

High Availability Configuration Requirements

For HA deployments (Active/Standby or Active/Active DNS):

  • Both vCMP guests in the HA pair must be configured identically
  • The number of cores per slot, number of slots, and slot numbers must match on both guests
  • This ensures proper operation of connection mirroring and failover
  • The multi-slot recommendation applies to both standalone and HA setups
  • Device group members should be vCMP guests, not vCMP hosts

Session and State Synchronization

For BIG-IP DNS handling primarily stateless UDP traffic:

  • Session/state synchronization is largely independent of vCMP slot distribution
  • Any state synchronization (such as connection mirroring) occurs between HA pair members (between chassis), not between slots within the same guest
  • DNS behavior is independent of vCMP slot distribution

Configuration Steps

  1. Configure the vCMP guest with the desired cores per slot and number of slots
    • Example: 8 cores per slot × 2 slots (total 16 vCPU)
    • Set Min Number of Slots: 1
  1. For HA deployments, ensure both guests are configured identically
  2. Monitor performance after the change, especially during blade failure scenarios
  3. Consider increasing cores per slot if significant traffic growth is anticipated

5. Additional Information

  • Multi-slot vCMP guest configuration is recommended for improved resilience and load distribution
  • Memory does not aggregate across slots; the total memory available to a guest is only as much as the host has allocated to each slot
  • To increase memory and CPU resources, increase the number of cores per slot rather than adding more slots
  • For HA with connection mirroring, both devices must have identical hardware platforms (chassis and blades), and each chassis must contain the same number of blades in the same slot numbers
