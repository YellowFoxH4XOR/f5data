Description

To monitor availability and health of Applications running on Kubernetes Clusters we use Liveness, Readiness and Startup Probes. You can find documentation explaining what probes are on the official Kubernetes documentation are here:

When probes are configured for the POD, kubelet performs actions (e.g. by opening TCP connection or making HTTP request) to check whether the application running within the POD is ready (status is then changed from PodInitializing to Running or healthy.

To integrate applications using Probes with early releases of Aspen Mesh and Istio Service Mesh, you have to apply changes to the configuration. Istio and Aspen Mesh do not have built-in functionality for fixing and translating Kubernetes Probes. This problem and possible solutions can be found in Liveness or Readiness Probe Incompatible with mTLS in the Aspen Mesh documentation.

There are 3 possible solutions when you want to integrate applications using HTTP Liveness Probes with Aspen Mesh and mTLS:
  1. Disable mTLS for the health probe port.
  2. Use a Liveness Command Instead.
  3. Disable liveness probes.

Istio 1.2 introduced a new solution to Kubernetes Probes - added Kubernetes health check prober rewrite per deployment via sidecar.istio.io/rewriteAppHTTPProbers: "true" in the PodSpec annotation. Probes rewrite can also be enabled globally by setting the sidecarInjectorWebhook.rewriteAppHTTPProbe=true option in the values.yaml file.

Aspen Mesh is enabling the rewriteAppHTTPProbe feature by default and the sidecarInjectorWebhook.rewriteAppHTTPProbe option is set to true by default in the Helm values.yaml file. You can disable the Probes rewrite feature by applying the rewriteAppHTTPProbers: “false“ annotations

Environment

  • Kubernetes 1.17x,1.18.x,1.19.x,1.20.x  
  • Aspen Mesh 1.6.x, 1.9.x  

Cause

None

Recommended Actions

HTTP Liveness and Ready Probes configured for the POD are modified by Istio after deployment. kubelet is responsible for executing Probes and checking POD health or readiness. Kubelet probes request will be rejected if the istio proxy sidecar is injected into the POD and mTLS is enabled because kubelet is not part of the service mesh and does not have a TLS certificate accepted by istio proxy.

The following example describes what changes are made to HTTP probes to allow polling PODs health and readiness. Create the POD yaml manifest with HTTP livenessProbe configured to the namespace with istio proxy injection enabled:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: liveness-http
spec:
  selector:
    matchLabels:
      app: liveness-http
      version: v1
  template:
    metadata:
      labels:
        app: liveness-http
        version: v1
    spec:
      containers:
      - name: liveness-http
        image: docker.io/istio/health:example
        ports:
        - containerPort: 8001
        livenessProbe:
          httpGet:
            path: /examplepath
            port: 8001

After applying the above configuration, you observe that the livenessProbe is modified:

kubectl get pod liveness-http-<xxx>-<yyy> -o yaml
…
spec:
  containers:
    name: liveness-http
    livenessProbe:
      failureThreshold: 3
      httpGet:
        path: /app-health/liveness-http/livez
        port: 15020
        scheme: HTTP
      periodSeconds: 10
      successThreshold: 1
      timeoutSeconds: 1
    name: liveness-http
…

You observe that the port was changed from 8001 to 15020 and path was modified from /examplepath to /app-health/liveness-http/livez.

How is this implemented by Istio and Aspenmesh?
Liveness and Readiness probes ports are always changed to port 15020. Port 15020 is a special port used by Istio for Applications telemetry. This port is not intercepted by the iptables rules. You can confirm this by checking the iptables rules on the POD network namespace by running the iptables –S command on the Kubernetes node shell:  

nsenter -t <PIID> -n iptables -t nat –S
...
-A ISTIO_INBOUND -p tcp -m tcp --dport 15020 -j RETURN

The pilot-agent application, running along with the Envoy proxy inside the istio-proxy container, is listening on port 15020 and taking HTTP requests to the /app-health URI from kubelet.

The Istio injection webhook adds environment variable with original probes configuration to the istio-proxy container:

- name: ISTIO_KUBE_APP_PROBERS
      value: '{"/app-health/liveness-http/livez":{"httpGet":{"path":"/examplepath","port":8001,"scheme":"HTTP"},"timeoutSeconds":1}}'

The pilot-agent unmarshals the JSON object from the ISTIO_KUBE_APP_PROBERS variable to go struct called Prober.

type Prober struct {
        HTTPGet        *apimirror.HTTPGetAction `json:"httpGet"`
        TimeoutSeconds int32                    `json:"timeoutSeconds,omitempty"`
}

pilot-agent receives the request to the /app-health/liveness-http/livez URI and it then sends the request to the original probe URI, configured by the ISTIO_KUBE_APP_PROBERS variable, to the application using the localhost IP address. The application container and the istio-proxy container are running in the same POD and share the same network namespace. This is why the pilot-agent running inside a different container can reach the application, running in another container, using localhost as IP address.

if prober.HTTPGet.Scheme == apimirror.URISchemeHTTPS {
                        url = fmt.Sprintf("https://localhost:%v%s", prober.HTTPGet.Port.IntValue(), proberPath)
            } else {
                        url = fmt.Sprintf("http://localhost:%v%s", prober.HTTPGet.Port.IntValue(), proberPath)
}

At the end of the flow pilot-agent returns the HTTP response code received from the application to kubelet. Only the response code is returned by the pilot-agent. All headers or response body is skipped by pilot-agent.

Additional Information

In Istio 1.10 the IP address used by pilot-agent was changed to the POD IP address (instead of localhost).

The change was required to address Envoy proxy behavior changes documented in the following Istio blog post and GitHub issue:
  • Upcoming networking changes in Istio 1.10 Istio blog.
  • Rewrite app probe sends requests to the wrong endpoint, breaking pod IP listeners issue in Istio GitHub.
  • Match inbound cluster logic in prober issue in Istio GitHub.
  • The Istio design documentation.
