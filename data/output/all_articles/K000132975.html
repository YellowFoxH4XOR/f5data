K000132975: iRules using HTTP::host to populate the FQDN part of a website may occasionally evaluate unexpected values, or a null value

Type
Support Solution
Published
2023-03-14
Updated
2025-02-07
Applies to
  • BIG-IP
Source
https://my.f5.com/manage/s/article/K000132975

Description


iRules using HTTP::host to populate the FQDN part of a website may occasionally evaluate unexpected values, or even a null value. 

This can cause problems if the iRule later tries to use HTTP::host to check an FQDN against a data group to base a load balancing or content switching decision on, and especially if it returns a null value which can cause a TCL error in the iRule.



Environment


BIG-IP, iRule using HTTP::host



Cause


This is because HTTP::host in an iRule merely returns the value of the Host header from the client's HTTP request, and not the actual hostname which was sent in a DNS request to get the IP address of a website. 

The client has full control over what is sent within the Host header of its HTTP request, and for HTTP 1.0 requests, a Host header will likely not even be present in the request, resulting in a null value returned by HTTP::host for those requests.



Recommended Actions


Admins using HTTP::host in an iRule to populate the FQDN of the request for logging or internal decisions within the irule should ensure to keep in mind while developing the iRule that this merely returns the value of the Host header in the HTTP request, and not the actual FQDN used for the DNS query or corresponding to anything within the DNS system as such.


The HTTP::host could be replaced with something like URI::host , but URI::host will only work for requests that have the full host in the URI (ie. proxy requests).



Additional Information


https://clouddocs.f5.com/api/irules/HTTP__proxy.html contains examples of similar commands which can be used in iRules to return values related to HTTP proxy requests, which may be useful if attempting to reduce the reliance on the request's Host header.
