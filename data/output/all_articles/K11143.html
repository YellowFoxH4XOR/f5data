Known Issue

Using the HTTP::respond command or the HTTP::redirect command in a server-side iRule event may cause the BIG-IP ASM or BIG-IP WebAccelerator to abort the connection by sending a TCP RST to the client system instead of forwarding the expected response. In addition, this issue may cause the TMM process to dump core with a SIGABRT.

For example, using the following iRule with an BIG-IP ASM or BIG-IP WebAccelerator-enabled virtual server causes the BIG-IP ASM or BIG-IP WebAccelerator system to abort the connection by sending a TCP RST to the client, and may cause TMM to crash:

when HTTP_RESPONSE {
  if { [HTTP::status] == 200 } {
    HTTP::respond 302 Location "http://www.example.com/"
  }
}

F5 Product Development tracked this issue as ID 221949 (formerly CR103446) and it was fixed in version 11.0.0. For information about upgrading, refer to the BIG-IP ASM or WebAccelerator release notes.

Workaround

You can work around this issue by performing one of the following procedures:

  • Using the HTTP::header replace command instead of the HTTP::respond command
  • Disabling BIG-IP ASM or BIG-IP WebAccelerator processing in the iRule event before the HTTP::respond or HTTP::redirect command
Using the HTTP::header replace command instead of HTTP::respond

You may also be able to work around this issue by using the HTTP::header replace command instead of the HTTP::respond command.

For example:

when HTTP_RESPONSE {
    if { [HTTP::status] == <XXX> } {
        HTTP::header replace "Location" ...
    }
}

Disabling BIG-IP ASM or BIG-IP WebAccelerator processing in the iRule event before the HTTP::respond or HTTP::redirect command

Perform one of the following three procedures, depending on your product and version:

BIG-IP ASM 10.x

You can use the ASM::enable and ASM::disable iRules command to control BIG-IP ASM processing. To enable for all requests, but disable it prior to the affected commands in versions 10.x, use an iRule similar to the following example:

when HTTP_RESPONSE {
  ASM::enable
  if { [HTTP::status] == 200 } {
    ASM::disable
    HTTP::respond 302 Location "http://www.example.com/"
  }
}

Note: When you use the ASM::disable command to bypass the BIG-IP ASM for one request, you should always re-enable BIG-IP ASM processing for subsequent connections by using the ASM::enable command at the beginning of the iRule event.

BIG-IP WebAccelerator version 10.x

You can use the WAM::disable iRule command to disable WebAccelerator processing. To disable WebAccelerator prior to the affected commands, use an iRule similar to the following example:

when HTTP_RESPONSE {
  if { [HTTP::status] == 200 } {
    WAM::disable
    HTTP::close
    HTTP::respond 302 Location "http://www.example.com/"
  }
}

Note: The HTTP::close command prevents the issue described in K12271: Using the WAM::disable or PLUGIN::disable WAM command in an HTTP_RESPONSE event may cause a pvac transaction leak.

BIG-IP ASM 9.x

You can use the PLUGIN::enable and PLUGIN::disable iRules command to control BIG-IP ASM processing. To enable for all requests, but disable it prior to the affected commands in versions 10.x, use an iRule similar to the following example:

when HTTP_RESPONSE {
  PLUGIN::enable ASM
  if { [HTTP::status] == 200 } {
    clientside { PLUGIN::disable ASM }
    HTTP::respond 302 Location "http://www.example.com/"
  }
}

Note: When you use the PLUGIN::disable command to bypass the BIG-IP ASM for one request, you should always re-enable BIG-IP ASM processing for subsequent connections by using the PLUGIN::enable command at the beginning of the iRule event.
