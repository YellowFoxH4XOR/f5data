K000130542: After upgrade, F5 VELOS Controller is "In Progress" status for a long time

Type
Support Solution
Published
2023-02-09
Updated
2026-02-21
Applies to

  • F5OS-C: 1.5.1, 1.5.0
Source

Description

  • The /var/log_controller/velos.log file shows the upgrade was completed on one of the controller. You may observe logs similar to the following on the working controller. On the affected controller however, you may observe the same logs, but without the BOOT MARKER entry indicating there are issues preventing it from rebooting and completing the upgrade.

    <date_timestamp> controller-1 /usr/libexec/sw-mgmt/sw-util.sh switch_agnostic_os 1.5.1-14085: priority=Info msgid=0x3501000000000027 msg=Update complete. Reboot required for changes to take effect.
    <date_timestamp> controller-1 /usr/libexec/sw-mgmt/sw-util.sh switch_agnostic_services 1.5.1-14085 no_restart: priority=Info msgid=0x3501000000000026 msg=Update of controller platform services to version 1.5.1-14085 in progress.
    <date_timestamp> controller-1 /usr/libexec/sw-mgmt/sw-util.sh switch_agnostic_services 1.5.1-14085 no_restart: priority=Info msgid=0x3501000000000028 msg=Update complete.
    <date_timestamp> controller-1.chassis.local notice boot_marker: ---===[ BOOT-MARKER ]===---

  • Based on the GUI, the upgrade was successful only on one of the system controllers (Active Controller)
  • The second controller (Standby) keeps "In Progress" status for a long (undetermined) time.
  • You observe logs similar to the following in /var/log/sw-mgmt.debug:

    <date_timestamp> - ERROR: sw-mgmt: priority=error msgid=0x3501000000000102 msg=controller registry 2001 creation error: 409 Client Error: Conflict ("You cannot remove a running container [...]. Stop the container before attempting removal or use -f")

Environment

  • Upgrade F5OS-C on VELOS Platform (system controller)
  • Most of the needed docker containers are not running on the (not-working) controller. To determine this, do both of the following:
    • Run docker ps to list running containers on both controllers and compare the output.
    • Query /var/log/journal for any errors with platform-services-deployment using the following command:
      journalctl -D /var/log/journal -b -u platform-services-deployment --no-pager

      You may observe an output similar to the following indicating issues with platform-services-deployment when triggering docker-compose to start F5OS services.

      <date_timestamp> controller-2.chassis.local platform-deployment[13254]: Unexpected error encountered while starting platform services via docker-compose.
      <date_timestamp> controller-2.chassis.local platform-deployment[13254]: Unable to successfully launch platform services after 3 attempts. Giving up.
      <date_timestamp> controller-2.chassis.local platform-deployment[13254]: Try checking the active config under /var/docker/config for errors and rebooting?

  • reboot" or "shutdown -r now" commands failed to run. For example:

    # systemctl reboot
    Failed to start reboot.target: Connection timed out
    See system logs and 'systemctl status reboot.target' for details.

  • Upgrade the F5OS-C (controller-level) to newer version (from 'v1.5.0' to 'v1.5.1')

Cause

Some previously not-stopped containers prevented essential containers from starting properly on system controller, after upgrade to the newer version.

Recommended Actions

Perform force Reboot on the (Standby) controller that's not working. Follow below steps:

  1. Login as "root" to the working (Active) controller
  2. Use "SSH" command to login to the other controller, using the 'ccpeer' link. The default IP address for 'ccpeer' link for system controller-1 is "100.65.7.51", and for system controller-2 is "100.65.7.52". In our example, we consider that the controller-1 is Active and working fine, and the controller-2 is Standby and has the issue. So, establish SSH connection from controller-1 to controller-2, as below.

    # ssh 100.65.7.52
  3. Since the normal reboot command might not work in such cases, force reboot using the "sysrq" command. Run the three below commands, in the same sequence and note that the third command performs the reboot.
    Tip: Make sure you are on the correct controller that has the issue, when running these commands. 
    1. Sync all mounted filesystems: 

      # echo s > /proc/sysrq-trigger
    2. Remount all mounted filesystems in read-only mode: 

      # echo u > /proc/sysrq-trigger
    3. Immediately reboot the system: 

      # echo b > /proc/sysrq-trigger
  4. After "10 Minutes", the controller is supposed to be up and running and upgraded to the newer version.
