Known Issue

This is the result of a known issue. Normally, a TCP connection as a whole is not considered terminated until both sides have finished the shutdown procedure by sending a FIN and receiving an ACK. If a device withholds sending the final ACK to the BIG-IP system, the TCP connection that was being terminated may become a zombie connection and cause TMM to leak memory. This issue occurs because once a TCP connection has transitioned to a CLOSE-WAIT state, it cannot be removed from the BIG-IP system connection table unless the final ACK is received. At this point, no timeouts or other mechanism exists to remove the connection from the connection table.

Note: This issue affects standard TCP virtual servers only.

You can observe the following behavior on a unit affected by this issue:

  • The performance graphs display a constant growth in the amount of memory utilized by TMM
  • The bigpipe memory show command reveals a constant growth in the amount of memory allocated to the xfrag subsystem. The following example displays that the xfrag subsystem has grown to 1.3GB:

    MEMORY STATISTICS --
    | (Host) Total = 371.7MB Used = 190.5MB
    | (TMM) Total = 3.636GB Used = 1.569GB
    | SUBSYSTEM Alloc Max Obj size
    | connflow 15.23M 16.14M 192
    | laddr 1344 1344 56
    | listener 22784 23808 256
    | xfrag 1.351G 1.355G 2048
  • The bigpipe tcp show command displays a large number of connections in the CLOSE-WAIT state.

    For example:

    GLOBAL TCP STATISTICS
    | Conn (open, CLOSE-WAIT) = (3601, 62398)
    | Conn (FIN-WAIT, TIME_WAIT) = (2709, 381)
    | Conn (accept, not accept) = (81.99M, 0) (estab, fail) = (81.75M, 1928)
    | Conn (abandon, expire) = (199542, 1.076M) Resets = 5.173M Bad cksm = 4
    | (rxbadseg, rxooseg, txrexmits) = (0, 405247, 8.420M)
    | SYN cache overflow = 0 (rxcookie, rxbadcookie) = (0, 0)

    Note: You can determine which particular TCP profile has a large number of connections in the CLOSE-WAIT state by running the bigpipe profile tcp show command.
