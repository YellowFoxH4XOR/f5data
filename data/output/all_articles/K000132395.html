K000132395: NGINX subrequest Auth fails with log error "auth request unexpected status"

Type
Support Solution
Published
2023-02-02
Updated
2025-04-02
Applies to
  • NGINX Products
  • NGINX Plus: R24
Source
https://my.f5.com/manage/s/article/K000132395

Description

  • You have Nginx Plus configured to authenticate users prior to serving a request
  • Users are prompted and provided correct credential but they fail to access resource with Nginx logging error "upstream timed out (110: Connection timed out) while reading response header from upstream" along with "auth request unexpected status code" of value like 302
2024/12/01 18:34:56 [error] 92929#92929: *67 upstream timed out (110: Connection timed out) while reading response header from upstream, 
       client: 192.168.1.2, server: , 
       request: "GET /example.html HTTP/1.1", 
       subrequest: "/auth-proxy", upstream: "http://localhost:1234/auth-proxy",
       host: "10.10.1.2:8181"
2024/12/01 18:34:56 [error] 92929#92929: *67 auth request unexpected status: 504 while sending to client, 
       client: 192.168.1.2, server: ,
       request: "GET /example.html HTTP/1.1", 
       host: "10.10.1.2:8181"
 

Environment

  • Nginx
  • LDAP
  • Authorization Server

Cause

  • The cause and source of the issue, usually relates to the authorization server being misconfigured or having missing attributes.

Recommended Actions

  • ngx_http_auth_request_module implements client authorization based on the result of a subrequest and thereby dependent on the value of "$upstream_status"
  • Status code can only be 2xx or 401/403.
  • Any other status code requires further analysis of the authorization server configuration or attributes in order to determine its response with status code like 504/302 as opposed to 2xx or 401.

Additional Information

In general

  • If the subrequest returns a 2xx response code, access is allowed.
  • If subrequest returns 401 or 403, access is denied with the corresponding error code.
  • Any other response code returned by a subrequest is considered an ERROR.
  • A response status code like 302, 504 and so on from the authorizing server results in Nginx logging an error as it falls within any other code
  • This is the default behavior of Nginx
