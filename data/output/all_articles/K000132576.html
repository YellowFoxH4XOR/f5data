Description

A Hardware Security Module (HSM) enables the BIG-IP to store and protect PKI private keys. Specifically, an HSM not only stores private keys, but also performs all of the cryptography operations that require these keys (ex. digital signature creation). 

HSMs come in two varieties – onboard and network-based. Specific appliances support onboard Marvell HSMs, while a network HSM (NetHSM) can be deployed on any appliance and chassis. The following are the current list of supported NetHSM vendors:

  • nCipher / Entrust (XC):Originally Thales, spun off to nCipher, and eventually to Entrust Datacard, and then just Entrust.

    Reference: Interoperability Matrix for BIG-IP TMOS with nCipher Clients and HSM

  • Safenet - Acquired by Gemalto, then acquired by Thales.

    Reference: Interoperability Matrix for BIG-IP TMOS with SafeNet Clients and HSM

  • Safenet Data Protection on Demand

    Reference: Interoperability Matrix for BIG-IP TMOS with SafeNet Data Protection on Demand (DPoD) HSM

  • Atos (Bull Trustway Proteccio)

    Reference: Interoperability Matrix for BIG-IP TMOS with Atos (Bull Trustway Proteccio) HSM

  • Equinix SmartKey – Fortanix

    Reference: Interoperability Matrix for BIG-IP TMOS with Equinix SmartKey Clients and HSM

  • Azure Managed HSM

    Reference: Interoperability Matrix for BIG-IP TMOS with Azure Managed HSM

  • Amazon CloudHSM - Liquid Security

    Reference: Interoperability Matrix for BIG-IP TMOS with Amazon CloudHSM

The security of cryptographic keys and ciphers can be further confirmed by validation against the Federal Information Processing Standard (FIPS) 140-2/3. Each vendor is responsible for validating their product against this standard.

Note that although onboard HSMs and NetHSMs can be validated by the vendor at FIPS 140-2 or FIPS 140-3 Level 3, this does not mean BIG-IP systems using FIPS-validated HSMs are 140-2 or FIPS 140-3 Level 3 validated.
