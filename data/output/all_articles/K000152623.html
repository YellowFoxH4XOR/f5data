K000152623: Sync showing "In Sync" while one peer shows as Disconnected after migration.

Support Solution

Applies to

  • BIG-IP LTM: 17.0.0, 17.1.0, 17.0.X, 17.X.X, 17.5.X, 17.5.1, 17.5.0, 17.1.X, 17.1.2, 17.1.1
Source
https://my.f5.com/manage/s/article/K000152623

Description

On BIG-IP LTM systems, device group synchronization may fail or show intermittent connectivity issues between peers. The Device Management Overview may display one or more devices as "Disconnected" while the sync status appears "In Sync." System logs may show frequent entries such as:

01010201:2: Inet port exhaustion on <ip_address> to <ip_address:port> (proto <protocol>)

iControl connection to <ip_address> failed

This can result in repeated device trust or sync failures, and persistent port exhaustion warnings on self-IPs used for HA/sync.

Environment

  • Configuration:
    • Device Service Clustering (DSC) with device trust and sync-failover groups
    • Direct fiber or routed connections for HA/sync
    • Use of self-IPs for HA/sync
    • Source address persistence with mirroring enabled (in some cases)
    • Possible configuration migration from other platforms (e.g., UCS archive)

Cause

The root cause is the non-default setting of the database variable scheduler.splitplanes.ltm to false. This configuration causes TMM (Traffic Management Microkernel) to start without split planes, resulting in double the number of TMMs per slot. As a result, not all TMMs go "ready for world," leading to intermittent client traffic issues, sync instability, and port exhaustion on self-IPs used for HA/sync. This behavior is associated with ID 1975777 db variable scheduler.splitplanes.ltm was set to false (non-default).

Recommended Actions

  1. Check the value of the scheduler.splitplanes.ltm db variable:
    tmsh list sys db scheduler.splitplanes.ltm
    If the value is false, proceed to the next step.
  2. Reset the variable to its default value (true):
    tmsh modify sys db scheduler.splitplanes.ltm value true
    or
    tmsh modify sys db scheduler.splitplanes.ltm reset-to-default
  3. Reboot the affected tenants after making the change.
  4. Verify device trust and sync status after reboot:
    Ensure that Device Management Overview shows all devices as "Connected" and that sync status remains stable.
  5. Additional Considerations:
    • If source address persistence mirroring is enabled and not required, consider disabling mirroring to reduce port exhaustion risk.
      •  K38984252: GossipResourceUpdateSender Failed to send update to peer
    • Ensure only F5-qualified SFP modules are used for physical connections.
    • If persistent port exhaustion is observed on self-IPs, review services/monitors using those IPs; consider distributing traffic across additional self-IPs/subnets if needed.
