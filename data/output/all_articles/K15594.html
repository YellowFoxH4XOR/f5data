Topic

BIG-IP DNS persistence ensures that when a local DNS makes repetitive requests on behalf of a client, the BIG-IP system reconnects the client to the same resource as previous requests.

Description

Most load balancing methods divide DNS name resolution requests among available pools or virtual servers. Each time the BIG-IP DNS system receives a request, it sends that request to the most appropriate resource based on the configuration of your network. For example, when you visit a website, multiple DNS name resolution requests are generated as you move from page to page. Depending on the load balancing method configured, the BIG-IP DNS system can send each request to a different server, virtual server, or data center. However, in certain circumstances, you may want to ensure that a given set of resources remains throughout the session. For example, if you're attempting to conduct an online banking transaction, the same set of resources must remain to ensure that the transaction is completed successfully.

When BIG-IP DNS persistence is enabled for a wide IP, the BIG-IP DNS system ensures that, after a response to a DNS name resolution request is sent to a local DNS, subsequent requests from the same local DNS are provided the same resource until the current session is completed.

When BIG-IP DNS persistence is enabled on a wide IP, the following order of operation behavior occurs:

  1. A new local DNS (LDNS) makes a request for a wide IP that has persistence enabled.
  2. The BIG-IP DNS system servicing the query makes a load balancing decision and generates a persistence record.
  3. The BIG-IP DNS system servicing the query forwards the new persistence record to the peers in the sync group, usually within 7 seconds.
  4. Upon subsequent requests from the same LDNS for the same wide IP, the BIG-IP DNS system servicing the request updates the expiration of its persistence record.  This BIG-IP DNS system does not send an update to sync group peers.
  5. At 75% of the persistence TTL value, the BIG-IP DNS sends an updated record to sync group peers to avoid premature time out of the persistence record. 

BIG-IP DNS persistence settings

BIG-IP DNS persistence is enabled within the pool section of a wide IP's properties. When persistence is enabled, the following additional configuration elements are then exposed:

  • Persistence TTL: Persistence TTL specifies, in seconds, the length of time for which the persistence entry is valid. The default is 3600.
  • Persist CIDR (IPv4): Persist CIDR (IPv4) specifies the number of bits the system uses to identify IPv4 addresses when persistence is enabled. The default is 32.
  • Persist CIDR (IPv6): Persist CIDR (IPv6) specifies the number of bits the system uses to identify IPv6 addresses when persistence is enabled. The default is 128.

Note: Configuring Persist CIDR to a value of zero (0) may result in persistence records created with 32 (IPv4) or 128 (IPv6) bits instead of 0.0.0.0/0. For more information, refer to Bug ID 75560.

Drain Persistent Requests

Drain Persistent Requests is an additional global configuration that affects persistence behavior for all wide IPs with persistence enabled. Enabled by default, this setting specifies that when you disable a pool or data center, load-balanced persistent requests continues until the time-to-live (TTL) interval expires.

The Drain Persistent Requests setting is located in the Configuration utility at:

  • DNS > Settings > GSLB > General (BIG-IP 11.5.0 and later).
  • System > Configuration > Global Traffic > General (BIG-IP 11.4.1 and earlier).

BIG-IP DNS persistence within a BIG-IP DNS synchronization group

A BIG-IP DNS synchronization group is a collection of multiple BIG-IP DNS systems that share and synchronize configuration settings, including persistence information.

BIG-IP DNS persistence information is synchronized to each member of the BIG-IP DNS synchronization group by the gtmd process using the iQuery protocol. A BIG-IP DNS system's gtmd process sends persistence updates to the remote big3d process of another sync group member. When the remote big3d receives persistence information, it forwards the persistence update to its local gtmd process. The receiving gtmd then creates the appropriate persistence entry in memory and eventually the ldns.gz file.

The gtm.maxpersistsyncspersecond database variable

You can use the gtm.maxpersistsyncspersecond database variable to control the rate at which gtmd sends BIG-IP DNS persistence updates to big3d. The default is 800 per second.

This setting is based on two BIG-IP DNS systems in a sync group. An additional factor to the gtm.maxpersistsyncspersecond value is the number of BIG-IP DNS systems in the sync group. If there are more than two gtmd processes, the bandwidth allocated is automatically divided by N-1 (number of BIG-IP DNS systems in the sync group, minus one). For example, with three gtmd processes in a sync group, any one gtmd is allowed to send 400 persist updates per second (800 per second divided by 2 (3 members - 1) = 400 per second).

Monitoring Persistence records

A listing of persistence records can be obtained using the following tmsh command:

tmsh show gtm persist

You can capture persistence records over time for later analysis with the help of the following bash script:

Note: The following example collects an output of tmsh show gtm persist every 300 seconds (5 minutes) 24 times (2 hours) to the /var/tmp/gtm-persist.log file.

for i in {1..24};
do
date >> /var/tmp/gtm-persist.log;
tmsh show gtm persist >> /var/tmp/gtm-persist.log;
sleep 300;
done;
