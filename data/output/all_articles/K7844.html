K7844: The iRule global command active_members always returns a value of 1 when no pool members are available

Known Issue

This is the result of a known issue. The active_members iRule global command returns a value of 1 when no pool members are available. As a result, the system forwards traffic to unavailable pool members. This issue only occurs when limits are set on pool members and the limit has been reached. BIG-IP LTM disables connections to the member whose limit has been reached, but the member is still active.

For example:

pool My_Pool {   monitor all http   member 10.10.1.10:http limit 1}

The following iRule will evaluate each HTTP request:

when HTTP_REQUEST {log "[active_membersMy_Pool]" if { [active_members My_Pool] < 1} {   HTTP::respond 200 content "<html><head><title>Apology</title></head>   <body>Sorry, UNAVAILABLE </body></html>"   }

When the member in My_Pool reaches the defined limit, BIG-IP LTM will not allow any additional connections to members until the number of connections handled by the pool member falls below one.

In the previous example, the active_members iRule global command will always report 1 and the iRule will not be invoked. If the iRule was invoked, it would cause a reset of the connection since BIG-IP LTM will not allow any connections to pool member as the limit has been reached.

When this issue occurs, the following line is reported in /var/log/ltm:

tmm tmm[763]: 01220002:6: Rule My_Pool <HTTP_REQUEST>: 1

F5 Product Development tracked this issue as CR85057 and it was fixed in BIG-IP LTM 9.3.1. For information about upgrading, refer to the BIG-IP LTM release notes.

Workaround

To work around this issue, use the following LB_FAILED event. This event will properly trigger since BIG-IP LTM will report that no members are available to accept connections:

when LB_FAILED {HTTP::respond 200 content "<html><head><title>Apology Page</title></head><body>UNAVAILABLE</body></html>"}
