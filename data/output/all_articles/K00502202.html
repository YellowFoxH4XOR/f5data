Known Issue

The big3d process may end up in a restart loop on secondary blades of a chassis system.

This issue occurs when all of the following conditions are met:

  • The big3d_install utility is used against a target system.
  • The target system is a multi-blade chassis.
  • The big3d_install utility picks the iQuery installation method (and not the secure shell [SSH] method).
  • The big3d_install utility incorrectly determines that the system should copy the local version of the big3d process to the remote system.

Impact

If the cluster elects a new primary blade, and the big3d process is still restarting on that blade, iQuery communication could fail between that system and remote BIG-IP systems.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • After the big3d_install utility is run against a target system, and the target system is a multi-blade chassis, the big3d process may begin restarting in a loop on all secondary blades of the target system. The primary blade is not affected, as the big3d process continues to run in a stable fashion.

Workaround

To work around this issue, you can restart the big3d process on the secondary blade. To do so, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the command line of the primary blade.
  2. Restart the big3d process on the primary blade by typing the following command:

    bigstart restart big3d

    This, in turn, re-establishes communication with the big3d processes on the other blades, and stops them from restarting.

To prevent this issue from occurring after installation, you can use the following command syntax to run the big3d_install utility and specify that the system use the SSH installation method:

 big3d_install -use_ssh <target IP>
