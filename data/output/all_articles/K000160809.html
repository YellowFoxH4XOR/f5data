Description

When deploying Load Balancer objects in F5 Distributed Cloud, it may not be immediately clear how incoming client traffic is matched to a specific Load Balancer configuration. Understanding how the platform listens for and picks up traffic is essential for correctly designing application delivery and security services across Regional Edges (RE) and Customer Edges (CE).

 

  • How does F5 Distributed Cloud determine which Load Balancer object picks up client-side traffic?
  • What is an Advertise Policy and how does it relate to listener logic?
  • How are HTTP and TCP Load Balancers differentiated when multiple Load Balancer objects share the same IP and Port?
  • What is the role of SNI and host headers in Load Balancer selection?
  • What is a Default Load Balancer and when is it used?
  • How can additional IP addresses be used to differentiate Load Balancer objects on a Regional Edge?

Environment

  • F5 Distributed Cloud (SaaS)
  • Regional Edge (RE) data plane
  • Customer Edge (CE) data plane
  • HTTP and/or HTTPS Load Balancer objects
  • TCP (Layer 4) Load Balancer objects
  • Advertise Policy configured on Load Balancer objects
  • Default Tenant IP, Additional Tenant IP, or BYO-IP in use for VIP Advertisement
  • Virtual Sites (optional, used to scope Regional Edge advertisement)

Cause

None

Answer/Recommended Actions

F5 Distributed Cloud uses an Advertise Policy as its listener logic mechanism. An Advertise Policy is the combination of an IP Address and Port, along with optional L7 matching criteria (domain, SNI, or host header), to determine which Load Balancer (LB) object picks up incoming client traffic.

Advertise Policy Matching Logic

Similar to BIG-IP Virtual Servers, F5 Distributed Cloud selects the most specific match from the list of Load Balancer objects sharing the same Advertise Policy (IP + Port). The matching criteria differ by Load Balancer type:

  • HTTP Load Balancer (L7):
    • Matches on IP + Port, plus a domain (specific or wildcard).
    • For HTTPS, the domain is matched using the Server Name Indication (SNI) value of the TLS handshake.
    • For HTTP, the domain is matched using the host header of the request.
    • A specific domain (e.g., app.domain.com) takes precedence over a wildcard domain (e.g., *.domain.com).
    • A Default Load Balancer can be configured on an HTTPS LB to catch any traffic that does not match a more specific domain. Only one LB object per Advertise Policy (IP + Port) can be designated as the Default Load Balancer.
    • Note: A Default Load Balancer is not supported on HTTP port 80 listeners at the time of this publication. A feature request is in progress to address this limitation.
  • TCP Load Balancer (L4):
    • Matches primarily on IP + Port.
    • If the service supports SNI, a domain can also be configured for SNI-based matching.
    • A TCP LB without an SNI domain behaves as the default for any traffic matching the IP and Port.
    • There is no explicit Default Load Balancer concept for TCP LBs.

IP Address Options for Regional Edge Advertisement

On a Customer Edge (CE), customers can configure custom IP addresses directly under the VIP advertisement. On a Regional Edge (RE), F5 manages the infrastructure, so IP addressing is handled through the following tenant IP types:

  • Default Tenant IP: Provided automatically when a customer signs up. Attached to a global Virtual Site and advertised out of all Regional Edges. To use this IP, select "Advertise to Internet" under VIP Advertisement when configuring the Load Balancer.
  • Additional Tenant IP (/32): Additional IP addresses provided by F5 from their IP pool, available for purchase. Each additional IP address incurs a cost. These can be added to an LB object under VIP Advertisement as "Internet (Specified VIP)".
  • BYO-IP (Bring Your Own IP): Customers can bring their own IP space (minimum /24) to the F5 platform. Charges apply per /24 block. The IP space is advertised out of F5's global network. These IPs can also be used under VIP Advertisement as "Internet (Specified VIP)".

For both Additional Tenant IPs and BYO-IPs, Virtual Sites can be attached to the Specified VIP to limit which Regional Edge locations are used for traffic advertisement.

Common Listener Logic Use Cases

  1. Basic Listener Logic: A client requests app-b.domain.com over HTTPS. DNS resolves to the tenant IP. The RE matches on IP + Port 443, then finds the most specific domain match (app-b.domain.com) and proxies traffic to the associated origin pool.
  2. HTTP-to-HTTPS Redirect:
    • Option 1: Enable the built-in HTTP-to-HTTPS redirect checkbox on the HTTPS Load Balancer. This automatically creates a companion HTTP port 80 LB object with a redirect route.
    • Option 2: Manually create an HTTP Load Balancer with a wildcard domain and configure a route to always redirect HTTP to HTTPS. This is useful to avoid doubling LB object counts and to handle redirects across multiple domains with a single LB.
  3. Unused Domains & Direct Response Routes: For abandoned, vanity, or legacy domains, instead of issuing a 3xx redirect (which can generate unintended automated traffic), configure a Direct Response Route on the LB. This returns a custom response message directly from F5 Distributed Cloud, requiring a human action to navigate further rather than an automatic browser redirect.

Platform Caveats

  • A Default Load Balancer is not supported on HTTP (port 80) Load Balancers. A feature request is in progress for this capability. It is also not recommended to use unencrypted HTTP in production environments; however, HTTP port 80 listeners can be useful for redirect services.
  • A Customer Edge (CE) does not support Advertise Policies that use certain platform-reserved ports. These ports are specific to the CE platform and cannot be used for Load Balancer Advertise Policies.

Additional Information

F5 Distributed Cloud operates two distinct data plane types relevant to listener logic:

  • Regional Edge (RE): A SaaS-managed data plane hosted in F5 regional locations. Customers consume services without managing hardware, software, or scale. IP addressing on the RE is owned and managed by F5, which is why tenant IP types (Default, Additional, BYO-IP) exist to give customers flexibility in how their services are advertised.
  • Customer Edge (CE): A software data plane owned and managed by the customer, deployable on-premises (hypervisor or baremetal), in a public cloud/hyperscaler, or within Kubernetes (k8s) clusters. Since the customer owns the infrastructure, IP addressing is straightforward and configurable directly.

The concept of listener logic in F5 Distributed Cloud is analogous to Virtual Servers in BIG-IP, where the most specific combination of source, destination, and port matching the request determines which object processes the traffic flow. In F5 Distributed Cloud, this specificity is extended to include domain matching via SNI or host headers for L7 Load Balancers.

When using a wildcard certificate (e.g., *.domain.com) with a Default Load Balancer, any traffic arriving at the associated IP + Port that does not match a more specific domain-based LB object will be handled by the Default LB. L7 routes can then be used within the Default LB to take appropriate action on that traffic.

When planning IP address strategy for Regional Edge advertisement, consider the following:

  • For most HTTP/HTTPS deployments, a single IP (Default Tenant IP) is sufficient since domain-based matching differentiates LB objects.
  • Additional IPs may be needed when multiple Default Load Balancers are required, or for operational segmentation (e.g., separating production and non-production traffic).
  • BYO-IP is charged per /24 block. A contiguous /22 brought to the platform is billed as 4x /24 blocks.
