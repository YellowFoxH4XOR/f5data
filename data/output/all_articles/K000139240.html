K000139240: Virtual Server with Radius profile always set the DF flag in UDP packets

Type
Support Solution
Published
2024-04-10
Updated
2024-04-10
Applies to
  • BIG-IP
  • BIG-IP LTM: 15.1.10
Source
https://my.f5.com/manage/s/article/K000139240

Description

After applying Radius profile to the virtual server, Don't Fragment flag is set to 1. The outgoing packets in Wireshark do not have server-side connection ID information. This behavior lines up with Datagram LB from UDP profile.

K7535: Overview of the UDP profile
https://my.f5.com/manage/s/article/K7535

Datagram LBDisabled (Not Selected)The Datagram LB option, which is disabled by default, specifies that the system load balances UDP traffic packet-by-packet and does not treat UDP packets from the same source and port as part of a connection. This setting overrides the default behavior of the UDP profile.

Without setting DF flag under the hood, there might be a situation where one IP fragment would go to pool member 1, the other one may go to pool member 2. This would cause a complete packet loss.

This behavior also allows Radius persistence to work, as BIG-IP must have the whole Radius packet to check the persistence records.

Environment

  • BIG-IP
  • Virtual server with Radius profile

Cause

Expected behavior.

Recommended Actions

None, if network is capable of handling the whole Radius packets. If not, consider disabling Don't Fragment flag in UDP profile.

Additional Information

If the virtual server receives IP fragments, it will wait for all the fragments to come to reassemble them and send a single packet to the backend Radius server. But the IP fragments must match the minimum size. As per https://my.f5.com/manage/s/article/K17102, the default value is 552 bytes of payload length of an IP packet only and does not include IP header size.
