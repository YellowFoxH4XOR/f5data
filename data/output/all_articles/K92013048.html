K92013048: Aggressive reaping can happen when memory usage is low.

Type
Support Solution
Published
2022-03-03
Updated
2025-02-07
Applies to
  • BIG-IP
  • F5 App Protect
  • F5 SSL Orchestrator
  • F5 DDoS Hybrid Defender
Source
https://my.f5.com/manage/s/article/K92013048

Description

Traffic is being reset due to 'TCP: Memory pressure activated' with below warning messages, even though TMM memory doesn't appear to be running out.
Warning messages similar to the following are logged to /var/log/ltm:
Jun  6 09:48:58 slot4/<hostname> warning tmm1[3793]: 011e0002:4: sweeper_segment_cb_any: Aggressive mode /Common/default-eviction-policy activated (301000000000000) (global memory). (5197168/6114304 pages)
Jun  6 09:48:58 slot4/<hostname> warning tmm2[3793]: 01010290:4: TCP: Memory pressure activated 
Jun  6 09:48:59 slot4/<hostname> warning tmm[3793]: 011e0003:4: Aggressive mode sweeper: /Common/default-eviction-policy (300000000000000) (global memory) 3977 Connections killed 
Jun  6 09:53:18 slot4/<hostname> warning tmm2[3793]: 011e0002:4: sweeper_policy_bind_deactivation_update: Aggressive mode /Common/default-eviction-policy deactivated (30200000000000e) (global memory). (5194674/6114304 pages)

Environment

  • BIG-IP
  • High traffic volume
  • Throughput spikes

Cause

When throughput is high and there is a sudden jump in throughput, TMM can be led to believe it is out of memory. TMM invokes aggressive reaping when this happens in order for it to maintain established connections.

Recommended Actions

  1. Review the qkview graphs for throughput and look for sudden jumps in bits per second to determine when this lines up with a jump in memory.
    Note: This will only work if the jump lasts more than 10 seconds due to the snapshot nature of the qkview. Traffic bursts can be very short-lived and therefore difficult to identify.
     
  2. Run this command to view current memory usage on the BIG-IP

    tmctl -s name,allocated,max_allocated -K max_allocated -O memory_usage_stat | head
     
    Example output:
    name                              allocated max_allocated
    ------------------------------- ----------- -------------
    umem                            10693275912   16151536648
    xdata                             381407232   16746409984
    filter                            703221552    2145679768
    dns cache resolver               1877109992    1985426192
    session cache                     587496192    1822185088
    session                           664501432    1600563640
    string cache                      407371208    1248019296

Additional Information

While running the command suggested in step 2 above, you may see xdata momentarily reach a very high percentage of the max allocated amount.
This is often related to a sudden increase in the use of TCP buffers.
