Description

When using BIG-IP ASM Brute Force Protection, the system may allow more failed login attempts than the configured threshold for IP-based brute force detection. Additionally, for username-based brute force protection, enforcement actions may be inconsistent: sometimes a blocking page is presented instead of a client-side integrity challenge, even when "Alarm and Client Side Integrity" is configured. Event logs typically show "Brute Force: Maximum login attempts are exceeded," but the actual enforcement action may not always match the policy configuration.

Environment

  • Product: BIG-IP ASM
  • Configuration details:
    • Depending on configuration there could be two or more standalone BIG-IP devices deployed behind a cloud load balancer
    • Brute Force Protection enabled for both IP and username sources
    • Username-based enforcement set to "Alarm and Client Side Integrity"
    • IP-based enforcement set to "Alarm and Blocking"
    • Login URL defined (may be a generic path such as "/")
    • No explicit login page qualification performed

Cause

  1. Distributed Enforcement with Multiple Devices:
    In environments where multiple standalone BIG-IP devices are deployed behind a load balancer, each device tracks brute force attempts independently. The configured threshold is enforced per device rather than globally across all devices. This can result in more total failed attempts being observed before any single device enforces the block.
  2. URL Qualification for JavaScript Injection:
    For client-side integrity challenges (such as CAPTCHA or JavaScript injection) to function, the login URL must be “qualified.” A URL is qualified if it receives at least 10 consecutive HTML responses within five minutes. If this condition is not met, ASM cannot inject JavaScript into responses and will fall back to the default enforcement action for "Brute Force: Maximum login attempts are exceeded," which may be set to block access instead of issuing a challenge.

Recommended Actions

  • Centralized Enforcement:
    To achieve global brute force protection thresholds across all devices, consider deploying in a way that allows centralized or synchronized tracking of failed attempts (for example, using an HA pair with state synchronization).
  • Ensure URL Qualification:
    To ensure client-side integrity challenges are consistently presented:
    • Confirm that your login URL returns HTML content with appropriate content-type headers (e.g., text/html).
    • Ensure that at least 10 consecutive HTML responses are served from the login URL within five minutes.
    • Manually qualify your login URL using:
      tmsh modify sys db asm.cs_qualified_urls value <URL>
    • Explicitly define your login page in the ASM policy; avoid using overly generic paths unless necessary.
  • Review Enforcement Actions:
    The "Alarm and Blocking" action is only available for IP-based brute force protection.
    For username-based protection using "Alarm and Client Side Integrity," verify that related bypass mitigation settings are correctly configured.
  • Troubleshooting Steps if Issue Persists:
    • Collect fresh event logs showing current enforcement behavior.
    • Capture HAR files from browser sessions reproducing the issue.
    • Enable bd debug logging for BRUTE_FORCE_ENFORCER module during reproduction.
    • Generate asmqkview files via CLI to include required ASM MySQL database information.
