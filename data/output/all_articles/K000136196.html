Description

This technical article addresses the issue of pod initialization failures in a Kubernetes environment due to Envoy proxy timeouts. Specifically, the sidecar logs display the error message "Envoy proxy is NOT ready." The article identifies the potential causes and recommends corrective actions.

Environment

Aspen Mesh 1.11.x
 

Cause

  • Careful attention to EnvoyFilter configurations (example entry duplicate problem) or overlap settings for the same services.
  • Syntax errors (lowercase and uppercase issue) can help resolve such issues. 

Recommended Actions

This article provides an overview of the common causes behind Envoy proxy timeout issues during pod initialization.
 

Conflicting EnvoyFilters: EnvoyFilters configured to modify the services with LOGICAL_DNS settings may conflict and overlap in their logic like the same service is been mentioned more than once (duplicate). Below is an example: 

applyTo: CLUSTER 
match:
 cluster:
  service: example.svc.cluster.local
patch:
 operation: MERGE
 value:
  type: LOGICAL_DNS


Syntax Errors: Pay close attention to formatting. For instance, the word "CLUSTER" in uppercase in the configuration file is incorrect; it should be in lowercase. An incorrect and corrected example is shown below:

Incorrect:

match:
 CLUSTER: 

Correct:

match:
 cluster: 


Additional Information

Note that the DNS_ROUND_ROBIN resolution in Istio is equivalent to the LOGICAL_DNS resolution in Envoy.
