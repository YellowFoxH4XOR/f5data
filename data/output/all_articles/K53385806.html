Topic

Introduced in BIG-IP 14.1.0, the LB::enable_decsionlog iRules command allows you to enable BIG-IP LTM decision logging.

Description

You can use the LB::enable_decisionlog command with the CLIENT_ACCEPTED and HTTP_REQUEST iRules events to enable debug logging for load balancing events.

Note: The added logging generated by the LB::enable_decisionlog command could lead to performance issues and you should use it only during troubleshooting. You should disable LB::enable_decisionlog once troubleshooting is complete.

When the LB::enable_decisionlog command is called in an iRule, information about the load balancing decision is accumulated and logged to the /var/log/ltm file. The information captured includes the following:

  • Client and virtual server IP addresses and ports
  • The pool and selected pool member
  • The load balancing algorithm
  • The proxy connection status

For example, after the load balancing decision is made and the connection to the pool member is established, the Traffic Management Microkernel (TMM) generates a message similar to the following example and logs it to the /var/log/ltm file:

notice tmm1[8910]: 01010346:5: [LTM LB][10.10.10.10:49422 -> 10.10.10.100:80][Proxy: Picked 10.10.11.100%0:80 from pool /Common/pool_http using LB mode Round Robin][Proxy: Connecting][Proxy: Connected]

Notice that the proxy connection status information is collected as the events occur and the message is logged once all the information is available.  If the connection to the selected pool member stalls for some reason, message logging is delayed until the connection status is known. For example, if the BIG-IP system is unaware a pool member is down and selects it during a load balancing decision, message logging is delayed until the connection expires, at which time TMM logs a message similar to the following example:

notice tmm[8910]: 01010346:5: [LTM LB][10.10.10.10:49423 -> 10.10.10.100:80][Proxy: Picked 10.10.11.100%0:80 from pool /Common/pool_http using LB mode Round Robin][Proxy: Connecting][Proxy: Server connection expired][Flow: Destroying connflow]

Recommendations

When using the LB::enable_decisionlog iRules command to troubleshoot load balancing on the BIG-IP system, you should consider the following factors:

Due to the amount of logging generated by the LB::enable_decisionlog command and potential performance impacts, F5 recommends that you use the LB::enable_decisionlog command only to troubleshoot load balancing issues at the direction of F5 Support. You should disable the LB::enable_decisionlog command once troubleshooting is complete.

 

Example IRule:

This is a very basic iRule that will enable logging on a virtual server for all traffic passing thru the iRule.    Note that you will need to edit the irule based on the event that triggers the log.   please use only 1 of the event options (CLIENT_ACCEPTED or HTTP_REQUEST)    do not use both, as it'll  log the same decision 2 times.     

IMPORTANT:   Be aware of the traffic load, and potential impact to logging  when the Virtual server is a high volume destination.   Consider creating advanced irule conditional controls like "if statements" to manage the impact of logging in such situations.

#----------------------------------------------
#  LB::enable_decisionlog is used to log load balancing decisions to the LTM log
#  see https://my.f5.com/manage/s/article/K53385806 for details
#  use ONE of the two options below to log the selected event.    Do not use both. 
#  use "#" to comment out the unused section of this iRule  (example below)
#  It's recommended to only use this for diagnostic purposes.
#----------------------------------------------

when CLIENT_ACCEPTED {
    LB::enable_decisionlog
    return 
 }
