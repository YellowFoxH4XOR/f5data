K000160520: Slot Offline After BIG-IP AFM Module Provisioning on Multi-Slot VELOS Tenants

Type
Support Solution
Published
2026-03-30
Updated
2026-03-30
Applies to
  • BIG-IP
  • BIG-IP AFM: 17.1.3
Source
https://my.f5.com/manage/s/article/K000160520

Description

When provisioning the BIG-IP AFM module on multi-slot BIG-IP tenants running on VELOS, slot 2 may go offline and fail to rejoin the cluster. Cluster member status shows slot 2 as unavailable, and the slot does not recover until the tenant is rebooted.

Environment

  • BIG-IP version 17.1.3 deployed on F5 VELOS CX410-AC hardware
  • Multi-slot tenant configuration (slots 1 and 2 active per tenant)
  • Modules: BIG-IP AFM and BIG-IP GTM provisioned
  • Issue observed across multiple tenants and chassis/partitions
  • BIG-IP AFM module provisioned on running tenants
  • Cluster member IP addresses may not be explicitly configured
  • /usr partition disk utilization noted at 88%

Cause

Timing sensitivity during live BIG-IP AFM module provisioning on multi-slot tenants. When BIG-IP AFM is provisioned, all slots undergo a TMM restart; secondary slots (slot 2) are more susceptible to delays during the cluster rejoin process. If the secondary slot does not rejoin within the expected timeframe, it appears offline. Rebooting the tenant reinitializes all slots and restores cluster synchronization.

Answer/Recommended Actions

  • For future module provisioning changes, use the following steps:
  1. Set the tenant to "provisioned" state and wait for full shutdown.
  2. Set the tenant back to "deployed" state to ensure all slots start cleanly.
  • Verify that cluster member IP addresses are explicitly configured for all slots in each multi-slot tenant:
    • Run tmsh show sys cluster all-properties and confirm Address fields are populated for each slot.
  • If Address fields are empty, configure them:
  • tmsh modify sys cluster default members { 1 { address <slot1_mgmt_ip> } 2 { address <slot2_mgmt_ip> } }
    • tmsh save sys config
  • Monitor disk space utilization, especially the /usr partition, to prevent resource exhaustion during future provisioning.
  • Confirm cluster health after any module changes using:
    • tmsh show sys cluster
    • tmsh show sys mcp-state
    • tmsh show sys provision

Additional Information

The issue is not indicative of a hardware or software defect. The cluster is healthy after reboot, and no residual errors or bug matches were found in the reviewed environment.
