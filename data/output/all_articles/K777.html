Topic

Hash cookie persistence mode is an option that allows you to easily set persistence using a node's existing cookie. These hash cookies provide you with confirmation that, after initially being load balanced by the BIG-IP Controller, a client is returning consistently to the same node.

When using hash cookie persistence mode, BIG-IP performs the following processes:

  • Accepts a connection from a client and parses the HTTP request looking for a cookie.
  • If the cookie is found, performs a hash on the cookie and uses the result to determine to which node to load balance.
  • If the cookie is not found, BIG-IP uses its default load balancing mode to choose a node.

Note: BIG-IP does not necessarily direct the client to the same server on which it was initially load balanced. Instead, BIG-IP uses the cookie that the initial node sets to calculate the hash. On return, the client is sent to a node based on the hash value (this process is described in the Cookie hash example section).

Configuration

You can configure hash mode cookie persistence through the Configuration utility or the command line. Configuration through the Configuration utility is done through either the VIP or Pool Persistence screens.

For specific instructions about configuring through the Configuration utility, refer to the BIG-IP manual.

To configure hash cookie mode persistence through the command line, use the following version specific commands:

BIG-IP version 3.2 through 4.6

b pool <pool_name> modify { persist_mode cookie cookie_mode hash cookie_name <cookie name> [cookie_hash_offset] <offset in characters> cookie_hash_length <length in characters> }

BIG-IP version 3.0 through 3.1.1

bigpipe vip <ip addr:port> define <ip addr:port...> special cookie hash <cookie name> <offset in characters> <length in characters>

The options contained in these commands are defined as follows:

OptionDefinition
<cookie name>The name of any existing cookie set by the web server.
<offset in characters>Sets the number of characters in the cookie to skip before calculating the hash value. The ASCII value of each character is a byte in length.
<length in characters>The number of characters to use in when calculating the hash value.
<number of nodes>The number of nodes in this pool. (Persistence is on a per pool basis)

With these options, you can use a portion of a cookie you have already created to provide persistence.

Note: The portion of the cookie you use must contain a value unique to each server you are using.

Cookie hash example

For this example, there are three web servers and each server sets MYCOOKIE as follows:

node #1   MYCOOKIE=98765ABC12345
node #2   MYCOOKIE=98765DBG12345
node #3   MYCOOKIE=98765AYZ12345

Comparing the values of these cookies, only the eighth character is unique. To use this character, set the <offset in characters> value to 7. The eighth character is not the end of the cookie, so this means that the last six characters are used in calculating the hash value. Since the last five characters are not unique, you can set the <length in characters> value to 1 and isolate the unique character in this cookie value.

The portion of the cookie specified by <length in characters> and <offset in characters>) determines to which node BIG-IP will load balance traffic. BIG-IP will perform a hash function on the specified cookie portion, which will return an integer value in the range of 0 to nodes - 1, where nodes equals the number of nodes in the pool that are eligible to load balance traffic.

If a pool is configured with three nodes of equal priority with one considered unavailable, then nodes = 2 and the hash function will return either 0 or 1. If the hash function returns a 0, then BIG-IP will send traffic to the last defined node in the pool. The highest possible hash return value is mapped to the first node (which are numbered in order of definition) in the pool.

Following is a description of the hash algorithm:

             hash_value = 0
             for every character (CHAR) in cookie_portion
                     hash_value = hash_value * 7 + CHAR
             end for
             
             hash_value = hash_value % <# of eligible nodes>


In this example, if BIG-IP hashes a cookie that looks like ABC, the result of the algorithm performed on the cookie is equivalent to ((0 * 7 + A) * 7 + B) * 7 + C) % <# eligible nodes>.


The numeric values for the characters A - Z, as defined by ASCII (and used by BIG-IP), are 65 -90; therefore, the cookie string ABC will hash to ((0 * 7 + 65) * 7 + 66) * 7 + 67 == 3714. In a pool of 3 eligible nodes, 3714 % 3 == 0. In this instance, BIG-IP will send traffic to the third node.


If this result is 0, the last node in the pool would be chosen. If the result is <# eligible nodes> - 1, BIG-IP will send traffic to the first node.


With the same example, but now using an <offset in characters> of 6 and a <length in characters> of 3, the result is:


NodePortionSum
node #1ABC= ((0 * 7 + 65) * 7 + 66) * 7 + 67 == 3714
node #2DBG= ((0 * 7 + 68) * 7 + 66) * 7 + 71 == 3865
node #3AYZ= ((0 * 7 + 65) * 7 + 89) * 7 + 90 == 3898


BIG-IP would manage the traffic with these cookies as follows:


ABC == 3714 mod 3 = 0  BIG-IP will send traffic to node #3
DBG == 3865 mod 3 = 1 BIG-IP will send traffic to node #2
AYZ == 3898 mod 3 = 1 BIG-IP will send traffic to node #2


Note: Node #1 sends a cookie to the client that will direct BIG-IP to load balance subsequent client connections to node #3, and node #3 sends a cookie to the client that directs connections to node #2, which is usually undesirable. This emphasizes the care required when setting cookies on the backend servers using hash cookie persistence.


When using hash cookie persistence, it is important to remember that the hash value is mapped to a particular node list of nodes defined within the given pool; therefore, removing a node causes a shift in the assignment of cookies to nodes. If a node is removed from a virtual server, this could cause cookie persistence to fail.
