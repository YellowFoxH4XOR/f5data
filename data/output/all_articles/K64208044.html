Topic

You should consider using this procedure under the following condition:

  • You want the BIG-IP ASM system to enforce URL flows for HTTP and HTTPS URLs. 
  • Your web application does not use multiple frames.

    Note: The use of frames is not discussed in this article.

Description

URL flows

Some web applications require that web pages be accessed in a predefined order, which is called flow in the context of the BIG-IP ASM system. More specifically, a flow is the path leading from one explicit URL, called the referrer, to another URL, called the target.

Enforcing URL flows protects the web application from forceful browsing. You can configure the BIG-IP ASM system to check flows to URLs in the system security policy to enforce the predefined order. If a user accesses a page out of order, the system triggers an Illegal flow to URL violation.

For example, you want to users to access the pages of a web application in the following order:

  1. /myapp/login.php
  2. /myapp/home.php
  3. /myapp/pictures.php
  4. /myapp/cart.php

In checking the URL flow in this example, you allow the explicit URL /myapp/login.php in the security policy as an entry point so that users can start the flow on this page. Next, you allow /myapp/home.php as a target and allow flows to it from the referrer, /myapp/login.php. Next, you allow /myapp/pictures.php as a target for the referrer /myapp/home.php, and so on. In this example, because /myapp/cart.php comes last, it is only a target and not a referrer.

Flow parameters

You can configure the BIG-IP ASM system to enforce mandatory flow parameters. Continuing with the example flow from the previous section, if you configure the mandatory flow parameter user_info, for example, when the user browses from /myapp/home.php to /myapp/pictures.php, if the flow parameter user_info is not present in the query string or request body, the system triggers the Illegal number of mandatory parameters violation.

Browse URLs not present in the URL flow

A user can divert from the web application flow and browse to other allowed URLs without triggering a violation, as long as the user afterward returns to the flow and browses to the next page in the flow order. Continuing with the previous example, a user starts at /myapp/login.php, proceeds to /myapp/home.php, and then browses to the allowed URL /myapp/calendar.php, which is not part of the flow. To return to the flow without triggering a violation, the user must then browse to /myapp/pictures.php, which is the next page in the flow after /myapp/home.php. If the user browses out-of-flow order and goes back to /myapp/home.php or skips ahead to /myapp/cart.php, the system triggers the Illegal flow to URL violation.

Note: If the user diverts from the flow to browse to an illegal, blocked URL instead of an allowed URL, the user cannot access the blocked URL. As with allowed URLs, to return to the flow, the user must then browse to the next URL in the flow order. The user cannot go back or skip ahead without triggering the Illegal flow to URL violation.

Enforcing mandatory flow parameters can prevent users from browsing URLs out of flow order. Continuing with an earlier example, the user diverts from the flow and browses to the allowed URL /myapp/calendar.php. If the user then attempts to access /myapp/pictures.php but the request does not supply the mandatory parameter user_info, the user cannot rejoin the flow and must return to /myapp/login.php to start over.

Even if you don't enforce mandatory flow parameters, you can still allow browsing of allowed URLs and meanwhile prevent out-of-flow order browsing. To do this, you configure each allowed URL as an entry point for a new flow leading only to a logout URL in the security policy. You can do this even if your application doesn't have an actual logout page. For example, you can configure the allowed URL /myapp/calendar.php as an entry point and as a referrer only for the target URL /myapp/logout.php. After browsing to /myapp/calendar.php, the user cannot return to the original flow but instead must continue to the /myapp/logout.php URL, which sends the user back to /myapp/login.php to restart the flow.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have administrative access to the Configuration utility.
  • You have access to the web application on which you want to enforce URL flows.
  • You have an existing, editable security policy associated with a virtual server.

Procedures

  • Allow URLs in the security policy
  • Remove wildcards that match all URLs
  • Configure flows to URLs
  • Allow parameters in the security policy (optional)
  • Verify violations and configure the BIG-IP ASM to block illegal requests

Allow URLs in the security policy

To enforce URL flows, you must configure your security policy to explicitly allow all of the possible URLs for your web application. You can have the BIG-IP ASM system learn allowed URLs as clients browse the application, you can manually allow URLs, or you can do a combination of both. Only URLs in the Allowed URLs list are accessible to clients through the BIG-IP ASM system. All others URLs trigger an Illegal URL violation and are blocked if your policy is in blocking mode.

  • Configuring the BIG-IP ASM system to learn allowed URLs
  • Manually allow URLs in the security policy

Configure the BIG-IP ASM system to learn allowed URLs

To determine all URLs involved in your web application you can configure the system to learn new HTTP and HTTPs URLs, and then you can browse the application and accept the URLs from the learning suggestions. The system may suggest specific wildcards, for example *.[Cc][Ss][Ss] and *.[Jj][Pp][Gg]. Since these are page elements that are not part of the flow, you can include these in the security policy.

Impact of procedure: Adding URLs to the policy allows access to the URLs through the BIG-IP ASM system.

First, configure the BIG-IP ASM system to learn new URLs:

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Policy Building > Learning and Blocking Settings.
  3. Select the name of the policy you want to edit from the list near the top of the page.
  4. (BIG-IP 14.1 and earlier) Set the properties view to Advanced to show Policy Building Settings.
  5. Expand URLs.
  6. For Learn New HTTP URLs select Always.
  7. Select the Learn and Alarm check boxes for the Illegal URL and Illegal flow to URL violations.
  8. For File types for which wildcard HTTP URLs will be configured (e.g. *.jpg), make sure that the list contains all the file types you need for your web application's page elements. For example, if your web application uses cascading style sheets, you need to add the .css file type.
  9. Select Save.
  10. Select Apply Policy.

Next, browse your application and then review and accept the appropriate learning suggestions:

  1. In your web application, browse to all the URLs that you want to allow in the security policy.
  2. Go to Security > Application Security > Policy Building > Traffic Learning.
  3. Review the list of triggered traffic learning suggestions and select the check box for each Illegal URL suggestion triggered by a URL that you want to allow.
  4. Select Accept Suggestions and then select Accept Suggestions.
  5. Go to Security > Application Security > URLs > Allowed URLs > Allowed HTTP URLs.
  6. You should now see the URLs you accepted in the previous step in the Allowed URLs List.
  7. Select Apply Policy.

Manually allow URLs in the security policy

Using the Allowed HTTP URLs page, you can bypass learning and manually add all or some of the URLs to the security policy.

Impact of procedure: Adding URLs to the security policy allows access to the URLs through the BIG-IP ASM system.

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > URLs > Allowed URLs > Allowed HTTP URLs.
  3. Select the name of the policy you want to edit from the list near the top of the page.
  4. Select Create.
  5. Set the properties view to Advanced.
  6. For URL select Explicit, select HTTP or HTTPS as appropriate and enter the path portion of the allowed URL. For example:

    /myapp/login.php

  7. For Perform Staging, clear the Enabled check box.
  8. Select Create.
  9. Repeat steps 4 through 7 for each URL you want to include in the flow. Be sure to add specific wildcard URLs for page elements. For example, *.[Cc][Ss][Ss].
  10. When you're finished adding URLs, select Apply Policy.

Remove wildcards that match all URLs

To enforce URL flow, after you add all of the explicitly allowed URLs to your security policy, you must remove the * (match all URLs) wildcards for HTTP and HTTPS.

Impact of procedure: Removing the * (match all URLs) wildcards restricts application access to only the explicit URLs you allow in the security policy and more specific wildcards.

  1. Go to Security > Application Security > URLs > Allowed URLs > Allowed HTTP URLs.
  2. Select the name of the policy you want to edit from the list near the top of the page.
  3. Select the check boxes for [HTTP] and [HTTPS] protocols with the * wildcard in the URL column.
  4. Select Delete.
  5. Select Delete to confirm deletion.
  6. Select Apply Policy.

Configure flows to URLs

After you allow your web application URLs in the security policy, you can configure the BIG-IP ASM system to check URL flows for explicit URLs.

Impact of procedure: After you configure URL flow checking, users can only access URLs in the flow in a predefined order.

First, set up your web application entry point(s):

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > URLs > Allowed URLs > Allowed HTTP URLs.
  3. Select the name of the policy you want to edit from the list near the top of the page.
  4. In the Allowed URLs List, select the URL that is the start of your web application flow to open its URL Properties page. Using the example URLs previously listed in the Description section of this article, you would select /myapp/login.php.
  5. Set the properties view to Advanced.
  6. Under Allowed URL Properties, for Check Flows to this URL, URL is Entry Point, and URL is Referrer, select the Enabled check boxes.
  7. Select Update.
  8. Repeat steps 4 through 7 for each URL you want to configure as an entry point for the flow.

Next, configure the flow settings for the URL(s) that come next in your web application flow.

  1. On the Allowed URLs page, select the URL that comes next in the flow. Using the example URLs previously listed in the Description section of this article, you would select /myapp/home.php.
  2. Select the Flows to URL tab.
  3. Select Create.
  4. The Create A New Flow dialog box opens.
  5. For Referrer URL, select URL Path and enter the referrer URL that uses the selected URL as its target. For example /myapp/login.php.
  6. In the Protocol list, select HTTP or HTTPS, as appropriate.
  7. In the Method list, select the expected HTTP method with which users will access the URL. The options are GET or POST.
  8. For Frame Target, enter 1 for no frames.

    Note: The use of frames is not discussed in this article.

  9. If this flow can contain a query string or POST data, select the Allow QS/PD check box.
  10. If you want the system to verify query strings or POST data for this flow, select the Check QS/PD check box.

    Note: You also need to configure learning and blocking settings for Illegal query string or POST data to enforce this check.

  11. Select OK to close the dialog box.

    The URLs from which users can access the selected URL display in the Flows to URL list.

  12. Select the URL Properties tab.
  13. Set the properties view to Advanced.
  14. Under Allowed URL Properties, for Check Flows to this URL ensure that the Enabled check box is automatically selected by the BIG-IP system.
  15. For URL is Referrer, select the Enabled check box.

    Note: Do not select the Enabled check box if the URL is last in the flow.

  16. Select Update.
  17. Repeat steps the steps in this procedure for each subsequent URL in your web application flow that is not an entry point.
  18. Select Apply Policy.

To view the entire web application flow, go to Security > Application Security > URLs > Flows List.

Allow parameters in the security policy (optional)

For an added level of enforcement on your URL flows, you can configure the BIG-IP ASM system to enforce mandatory flow parameters. You can have the BIG-IP ASM system learn which parameters to allow as users browse the application, you can manually allow parameters, or you can do a combination of both. If a flow parameter is not present, the Illegal number of mandatory parameters violation is triggered.

  • Configuring the BIG-IP ASM system to learn which parameters to enforce in your URL flows
  • Manually add parameters to enforce in your URL flows

Configure the BIG-IP ASM system to learn which parameters to enforce in your URL flows

To determine all of the parameters your web application uses, you can configure the system to learn new parameters, then you can , browse the application and accept the parameters from the learning suggestions.

Impact of procedure: After mandatory flow parameters are configured, users can only access URLs in the flow if the request contains the parameters in the query string or request body.

First, configure the BIG-IP ASM system to learn new parameters:

  1. Go to Security > Application Security > Policy Building > Learning and Blocking Settings.
  2. Select the name of the policy you want to edit from the list near the top of the page.
  3. (BIG-IP 14.x and earlier) Set the properties view to Advanced to show Policy Building Settings.
  4. Expand URLs.
  5. Select the Learn and Alarm check boxes for the Illegal number of mandatory parameters violation.
  6. Expand Parameters .
  7. For Learn New Parameters select Always.
  8. For Parameter Level, select URL.
  9. Select Save.
  10. Select Apply Policy.

Next, browse your application and then review and accept the appropriate learning suggestions:

  1. In your web application, browse to all the URLs that supply parameters.
  2. Go to Security > Application Security > Policy Building > Traffic Learning.
  3. Review the list of traffic learning suggestions and select the check box for each Illegal parameter violation. Each learning suggestions indicates the parameter with which each URL is associated. For example:

    user_info on [HTTPS] /myapp/login.php
    user_info on [HTTPS] /myapp/home.php

  4. Select Accept Suggestions and then select Accept Suggestions.

Next, configure the flow settings for the parameters in your web application flow:

  1. Go to Security > Application Security > Parameters > Parameters List.
  2. Select a parameter name to open its Parameter Properties page.
  3. For Parameter Level select Flow.
  4. For From URL, select URL Path and then select in the URL Path box. A list of URLs appear. Select the appropriate URL for the parameter. For example, /myapp/login.php.
  5. For Method, select the expected HTTP method with which users will access the URL. The options are GET or POST.
  6. For To URL, select the box. A list of URLs appear. Select the appropriate URL for the parameter. For example, /myapp/home.php.
  7. For Perform Staging, clear the Enabled check box.
  8. For Is Mandatory Parameter, select the Enabled check box.
  9. Select Update.

    The Flow Parameters page opens.

  10. (Optional) Go to Security > Application Security > URLs > Flows List.
  11. (Optional) Expand the flow for which you just added the flow parameter and select the URL name to open the Flow Properties page. The Number of Mandatory Parameters value should reflect the number of parameters you added.
  12. Repeat the steps in this procedure for remaining learned parameters.
  13. Select Apply Policy.

Manually add parameters to enforce in your URL Flows

Using the Parameters List page, you can bypass learning and manually add all or some of the parameters to the security policy.

Impact of procedure: After you configure mandatory flow parameters, users can only access URLs in the flow if the request contains the parameters in the query string or request body.

  1. Go to Security > Application Security > Parameters > Parameters List.
  2. Select the name of the policy you want to edit from the list near the top of the page.
  3. Select Create.
  4. For Parameter Name, select Explicit and enter the parameter name.
  5. In the Parameter Level list, select Flow.
  6. For From URL, select URL Path and then select in the URL Path box. A list of URLs appear. Select the appropriate URL for the parameter. For example, /myapp/login.php.
  7. For Method, select the expected HTTP method with which users will access the URL. The options are GET or POST.
  8. For To URL, select the box. A list of URLs appear. Select the appropriate URL for the parameter. For example, /myapp/home.php.
  9. For Perform Staging, clear the Enabled check box.
  10. For Is Mandatory Parameter, select the Enabled check box.
  11. Select Create.
  12. (Optional) Go to Security > Application Security > URLs > Flows List.
  13. (Optional) Expand the flow for which you added the flow parameter and select the URL to open the Flow Properties page. The Number of Mandatory Parameters value should reflect the number of parameters you added.
  14. Repeat the steps in this procedure to create other flow parameters.
  15. Select Apply Policy.

Verify violations and configure the BIG-IP ASM to block illegal requests

To verify the URL flows and optionally verify flow parameters you are going to enforce, browse your web application to ensure violations are triggered as expected.

Impact of procedure: When you set the enforcement mode to Blocking for the security policy, the system blocks requests that both cause violations and are designated for blocking.

  1. In your web application, start browsing at the URL you configured as the entry point, for example /myapp/login.php, and then browse to each URL in your flow. When you reach the last page in the flow, for example /myapp/cart.php, stop and leave the application open.
  2. Log in to the BIG-IP ASM Configuration utility.
  3. Go to Security > Event Logs > Application > Requests.
  4. Make sure you do not see any violations for your browsing activity from step 1. Also ensure that the logs are not filtering out illegal requests.
  5. Return to your web application and, from the last page in the flow, browse to a URL in the middle of the flow.
  6. Check the Configuration utility Requests page again. You should now see an Illegal flow to URL violation for the activity in step 5.

    Note: You can divert from the flow and browse to other allowed URLs and as long as you browse to the next URL in the flow after diverting, you should not see an Illegal flow to URL violation. For information on how to prevent out-of-flow browsing, see the Description section in this article.

  7. Return to your web application and browse to a URL that is not in the Allowed URLs List.

    Note: If you configured mandatory flow parameters, access a URL in the flow without the mandatory parameter (use a tool such as curl or fiddler to create a custom request without the parameter if necessary) or access an out-of-flow URL that removes the mandatory parameter when browsing to the next URL in the flow.

  8. Check the Configuration utility Requests page again, and you should see Illegal flow to URL violations, Illegal URL violations, and, if you chose to configure mandatory flow parameters, Illegal number of mandatory parameters violations.
  9. After you are satisfied with the URL flow and flow parameter checking functionality and you do not have any other configuration modifications to make to the security policy, go to Security > Application Security > Policy Building > Learning and Blocking Settings.
  10. Under General Settings, in the Enforcement Mode list, select Blocking.
  11. Set the properties view to Advanced to show Policy Building Settings.
  12. Expand URLs.
  13. For Illegal URL, Illegal flow to URL, and, if applicable, Illegal number of mandatory parameters violations, select the Block check box.
  14. Select Save.
  15. Select Apply Policy.
