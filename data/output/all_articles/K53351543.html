Description

The purpose of this article is to overview the SSLO Health Dashboard statuses, their values and their underlying functionality.

Environment

  • SSLO

Cause

None

Recommended Actions

None

Additional Information

SSLO Health Dashboard includes the following fields:

  • Echo Verification
  • Gossip State
  • CMI Sync Status
  • Device Group Failover Status
  • Peer HA Verification Response
  • Overall Status

Echo Verification

Echo verification is exchanging timestamps between two boxes if exchange is invalid or not happening status is becoming bad.

Gossip State

The following table describes the possible gossip states.

StatusDescription
UNINITIALIZEDThis is the state of gossip right after the worker has been started - it essentially means check back after startup has completed.
UNPAIREDNot currently clustered with other peers.
SYNCHRONIZINGReceived a POST from peer requesting transition from UNPAIRED to ACTIVE so the initial full state replacement is in flight.
ACTIVEInitial state sync has completed. Gossip is actively subscribing to worker writes that require replication and performing that replication to all peers in an eventually consistent fashion.
OFFLINEThis appears to be relevant only to active/standby configurations of BIG-IQ CM (not iWorkflow) when a failover would perform a full restoration of a full state snapshot.

CMI Sync Status

CMI sync status values

  • High-Availability
  • Trust-Only

Device Group Failover Status

Device Group Failover Status values

  • Standby
  • Active
  • Standalone
  • Failure
  • Offline

Can be polled via following REST path: /mgmt/shared/iapp/f5-iappslx-ssl-orchestrator/cmiSyncStatusWorker

Peer HA Verification Response

HA Peer Verification Status values:

  • Good
  • Bad

HA verification worker performs the following actions (not necessarily in this order):

  1. Checking Gossip State and devices via /shared/gossip?$select=gossipPeerDevices for all the HA devices.

    • Verifying that the status is ACTIVE

  2. Checking /mgmt/tm/cm/device for all the HA devices.

    • Verifying that items count returned on both the devices are same.

    • Verifying that attribute configsyncIp is there for all the devices and  it should match with HA VLAN IP of the corresponding device

    • Verifying for each device that unicastAddress is present, and the configsyncIp value is an entry of unicastAddress. Usually the management IP should also be an entry of "unicastAddress".

  3. Verifying EchoContent - restcurl /shared/echo

  4. Checking /mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices for all the HA devices.

    • Validating the returned result that all the devices are there, same as the result of step 1.

    • Specifically validating that attribute address is there and it is matching with corresponding device HA configsyncIp.

    • Verifying Port Lockdown settings on all the HA devices  -> Must be either Allow All or Allow Default

  5. Checking /mgmt/tm/shared/bigip-failover-state for all the HA devices.

    • Verifying that attribute failoverState is active for active device and standby for the standby device.

    • Verifying that attribute networkFailoverDeviceGroup is matching on the corresponding HA Box.

  6. Checking HA sync failover group settings

    • Verifying that device-group is of Sync-Failover type, that all HA devices are part of it and the sync type is Manual with Incremental Sync

  7. Additional checks that are being done:

    • Check whether currently installed .iso and .rpm versions of each devices are matching

    • Check NTP, DNS settings of each device are matching.

  8. Checking verification status restcurl /shared/iapp/f5-iappslx-ssl-orchestrator/ha-verification?getpeer=1

Overall Status

Overall Status values:

  • Good
  • Bad

The overall status is dependent on Echo Verification, Gossip State, CMI Sync Status, Device Group Failover Status and Peer HA Verification Response being in a Good state.
