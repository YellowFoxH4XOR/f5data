Topic

Following is a summary of guidelines to use when determining how BIG-IP is using its resources:

  • Memory
    Use a baseline of 1 million TCP connections for one gigabyte of RAM. Only mirror long-lived, connections when necessary.

  • Delayed Binding
    The efficiency of BIG-IP in establishing new connections is directly related to the operations of delayed binding.

  • SSL acceleration and proxyd
    All available CPU for bulk encryption is used by SSL acceleration (proxyd).

Memory

Available memory is a vital consideration when trying to maximize the efficiency and speed in which the BIG-IP loads a configuration. The larger and more complex the BIG-IP configuration is, the more memory it will use, which, in turn, leaves fewer memory resources devoted to connections.

To determine how many raw throughput connections BIG-IP can handle, use a baseline of 1 million TCP connections per gigabyte of RAM. Connection mirroring will decrease this number, because memory allocation is used to mirror the connection as well as the connection space itself; however, mirroring short-lived connections that are generally easy to recover after a failover uses more memory and CPU cycles than it is worth.

Recommendations: Mirror only long-lived connections that do not gracefully recover, such as FTP transfers. Do not mirror short-lived, rapid connections such as HTTP or HTTPS.

Note: BIG-IP's baseline for connections/memory is 1 million connections to one gigabyte of RAM; however, due to operating system limitations, adding an additional gigabyte of RAM (for a total of 2 gigabytes of RAM) will only scale to roughly 1,250,000 connections.

Delayed Binding

Connections that utilize delayed binding features (such as rules, cookie persistence, and SSL acceleration) take up more CPU and memory resources than other connections because of the additional actions required when establishing delayed binding connections. These additional actions include inserting or evaluating cookies, evaluating a connection against a rule, encrypting and decrypting packets and, in some cases where an SSL proxy is used in conjunction with cookie persistence and a rule, all of these actions simultaneously.

Recommendation: Use delayed binding features when necessary, but because of the impact on performance consider writing simple and efficient rules, and use session cookies that expire when the client browser is closed.

SSL Proxy Connections Overview

Unlike most other BIG-IP traffic management features, which are processed directly by the kernel, BIG-IP processes SSL proxy connections outside of kernel space in proxyd. Features, such as proxyd, that are processed outside of the kernel are performed in user space.

Functions that are processed in user space are common on UNIX-based platforms and can be monitored by several UNIX tools that are bundled with the BIG-IP software. Some popular UNIX monitoring tools are covered in the Using UNIX tools to monitor system resources section later in this solution. 

SSL Acceleration and proxyd

The process of SSL acceleration is split into two parts:

  • Initial cipher establishment and key exchange
  • Bulk encryption of data

Cipher establishment and key exchange

Cipher establishment and key exchange are the most mathematical and resource-intensive parts of the process and, therefore, these processes are offloaded to the SSL acceleration hardware.

Because the SSL acceleration takes place outside of the kernel, in user space, the memory that it uses while processing HTTPS requests cannot be used to trigger BIG-IP's memory reboot percentage, which is activated when kernel space memory reaches a configured threshold.

Bulk encryption of data

Bulk encryption of data is much less intensive and is performed by the BIG-IP CPU(s); however, the proxyd process will usurp all available CPU it needs to perform the bulk encryption duties.

When CPU utilization reaches 90%, connections handled by the SSL proxy will begin to slow. If the CPU consumption continues to the 99 - 100% level, the BIG-IP's packet processing capabilities diminish for all connections. In this event, the non-SSL proxy connections get processing precedence over connections maintained by an SSL proxy.

It is important to point out that it is not out of the ordinary or detrimental for a process to occasionally consume CPU resources in the 90% range for a short period of time, as long as the proxyd or offending daemon releases the CPU resources when it no longer needs them; however, if proxyd takes up a significant allocation of CPU resources (into the 90% range) during peak hours of usage on a regular basis, consider upgrading the hardware platform or adding additional e-Commerce Controllers to appropriately scale for usage and traffic demands.

The general rule for TCP connections is 1 million connections per gigabyte of memory, although this does not apply to SSL proxy connections. SSL proxy connections through the SSL accelerator can only scale to 8,000 concurrent connections. To verify whether a BIG-IP system has reached this limit, you can view the proxy statistics in the BIG-IP Configuration utility and add up the values for current connections on all configured proxies. If you determine that a BIG-IP system has reached 8,000 concurrent SSL proxy connections, consider employing an e-Commerce Controller cluster, which can scale to meet current and future SSL demands. 

Recommendation: Use only the SSL proxy for content that needs to be encrypted to keep resources free for other connections. In addition, be aware that using SSL re-encryption configurations will exhaust resources twice as quickly.

Using UNIX tools to monitor system resources

There are several UNIX tools available to monitor system resources. These UNIX tools are good for looking at the data provided by BIG-IP tools such as bigtop, bigpipe conn dump, bigpipe summary, and object statistics, but they display data in a different manner in order to provide a better representation of resource usage. The following UNIX monitoring tools are the most common:

  • vmstat
  • top
  • netstat
  • df

vmstat

Command:    vmstat
Function:      Process, memory, paging, trap/interrupt (faults), and CPU statistics
Focus:          Memory utilization and paging
Information: Refer to the vmstat man page: man vmstat
Syntax:         vmstat <interval in seconds> <count>

Example:

The vmstat tool is good for evaluating memory usage. It also displays CPU utilization statistics, but unlike the top tool, it does not display which processes have consumed the most memory and CPU resources.

Note: A similar diagnostic tool bundled with BIG-IP is iostat. Refer to the iostat man page for usage guidelines.

The top tool is the most user-friendly UNIX statistics tool and is good for monitoring proxyd during peak hours. When proxyd is climbing toward 90%+ CPU utilization, the administrator should view the proxy statistics using the top utility as a starting point for checking BIG-IP load, CPU utilization, and available memory.

Note: A similar diagnostic tool bundled with BIG-IP is systat. Refer to the systat man page for usage guidelines.

netstat

Command:     netstat
Function:       Network, socket, and interface statistics.
Information: Refer to the netstat man page: man netstat

Example:

netstat -na: displays connections status, and localhost listeners
 netstat -nr: displays static routing table
 netstat -nisv: displays active interface statistical summary

The netstat syntax examples provided show only a few ways it can be used. The netstat command is capable of displaying a multitude of network related data and statistics. It is a good tool to use if you would like to see if a particular static route is being used, to see if the BIG-IP Configuration utility is listening on a specified address:port, and to evaluate interface statistics, such as dropped packets and collisions.

df

Command:    df
Function:      Displays disk utilization, and free space
Information: Refer to the df man page: man df
Syntax:          df

Example:

# df

The df tool displays free disk space on a per-partition basis. This is useful in ensuring that BIG-IP or 3-DNS have sufficient disk resources when installing upgrades and PTFs, or for running debug logging.
