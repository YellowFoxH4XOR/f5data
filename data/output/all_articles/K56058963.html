K56058963: How to distribute balance across istio-proxy workers threads in Aspen Mesh

Type
Support Solution
Published
2021-11-22
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K56058963

Description

You observed that there is an uneven distribution of connections to istio-proxy worker threads. How can you configure istio-proxy to balance the connections?

Environment

  • Kubernetes: 1.17x, 1.18.x, 1.19.x, 1.20.x
  • Aspen Mesh: 1.6.x, 1.9.x

Cause

By default, there is no coordination between worker threads. This means that all worker threads independently attempt to accept connections on each listener and rely on the kernel to perform adequate balancing between threads.

Recommended Actions

You can override the default behavior of istio-proxy and forcibly balance the connections with the following procedures:

  • Configure envoy filter to implement exact_balance
  • Verify and test the connections

Configure envoy filter to implement exact_balance

  1. Below you can find two EnvoyFilters one for the server-side and the other is client-side, change the namespace and workload selector to your app labels configuration, this is important as you don't want to apply this to every listener.

    #Server side
    ---
    apiVersion: networking.istio.io/v1alpha3
    kind: EnvoyFilter
    metadata:
      name: fortio-server-listener-balance
      namespace: perf-sidecar
    spec:
      workloadSelector:
        labels:
          app: fortio-server
      configPatches:
        - applyTo: LISTENER
          match:
            context: SIDECAR_INBOUND
            listener:
              portNumber: 15006 #do not change this port on server
          patch:
            operation: MERGE
            value:
              connection_balance_config:
                exact_balance: {}
     
    #Client side
    ---
    apiVersion: networking.istio.io/v1alpha3
    kind: EnvoyFilter
    metadata:
      name: fortio-client-listener-balance
      namespace: perf-sidecar
    spec:
      workloadSelector:
        labels:
          app: fortio-client
      configPatches:
        - applyTo: LISTENER
          match:
            context: SIDECAR_OUTBOUND
            listener:
              portNumber: 8080 #This can be changed to your client port listener
          patch:
            operation: MERGE
            value:
              connection_balance_config:
                exact_balance: {}

  2. After applying the EnvoyFilter you may want to restart the applications with the istio-proxy sidecar injected.
  3. You may notice the server-side port is different from the application you are running with istio-proxy sidecar injected, this is because of the proxy behavior of capturing all traffic inbound and redirecting to the application container. The port 15006 is the inbound istio-proxy port that will do the redirection. On the other hand, the outbound from the client uses the port definition which could be anything your application uses.

    Note: In the current version of Aspen Mesh 1.9.x, only the server-side is balanced, client-side configuration is not working properly, the fix could be merged on a future release.

Verify and test the connections

  1. To verify the connections are being distributed evenly, you need to annotate your sidecar to get access to specific metrics. If you don’t know how to annotate your deployment, check out the Annotate your deployment definition procedure in K12253321: Holding up application until proxy starts in Aspen Mesh
  2. Include the following stats in your annotation:

    annotations:
      proxy.istio.io/config: |-
        proxyStatsMatcher:
          inclusionRegexps:
            - "cluster.*.upstream_cx_total"
            - "cluster.*.upstream_cx_active"
            - "listener.*.downstream_cx_total"
            - "listener.*.downstream_cx_active"

  3. You can do the annotation before the restart of the application in point 2 or even after applying the EnvoyFilter in the section above.
  4. Once you have applied the EnvoyFilter and the new stats metrics available, you can monitor your connection balance with the following commands:

    kubectl port-forward <pod-name> -n <namespace> 15000:15000

    On another terminal, enter:

    curl -s localhost:15000/stats | grep listener.0.0.0.0_15006.worker

    The output should be something like this:

    listener.0.0.0.0_15006.worker_0.downstream_cx_active: 1 listener.0.0.0.0_15006.worker_0.downstream_cx_total: 13 listener.0.0.0.0_15006.worker_1.downstream_cx_active: 1 listener.0.0.0.0_15006.worker_1.downstream_cx_total: 13

    Observe the perfectly balanced connections.

  5. If you found it tricky running these commands in parallel, you can integrate the Aspen Mesh metrics with a Grafana dashboard for easy access; follow K11884926: Integrating Grafana with Aspen Mesh Metrics Collector for monitoring mesh metrics
