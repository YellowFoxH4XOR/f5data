K000162311: BIG-IP LTM: HA Failover and Core Dumps Caused by Full /var Partition

Type
Support Solution
Published
2026-07-17
Updated
2026-10-05
Applies to
  • BIG-IP
Source
https://my.f5.com/manage/s/article/K000162311

Description

A BIG-IP LTM system may experience repeated PostgreSQL connection errors, mcpd database errors, snmpd core dumps, TMM termination, and an unexpected HA failover when the /var filesystem becomes full. Typical log messages include:

  • 01070710:3: Database error (0), Unable to connect to PostgreSQL database.
  • 01071aea:4: CMI heartbeat timer expired
  • 01070920:3: Application error for confpp: snmpd: no process found
  • 01140029:4: HA daemon_heartbeat tmm fails action is go offline down links and restart
  • 011d0004:3: Disk partition /var (slot 1) has only 0% free

Core files may be generated for snmpd and tmm.0.

Environment

  • BIG-IP LTM 17.1.3 on a vCMP Guest
  • Modules provisioned: BIG-IP LTM, BIG-IP AFM, BIG-IP APM, BIG-IP ASM, BIG-IP APML
  • HA was configured

Cause

Prolonged exhaustion of the /var filesystem caused PostgreSQL to fail, preventing mcpd from connecting to the database. This led to repeated snmpd failures/core generation and a sod heartbeat timeout, which caused TMM to be killed/cored and triggered HA failover.

Answer/Recommended Actions

  1. Review diskmonitor and related logs for messages indicating /var was full (e.g., 011d0004:3: Disk partition /var (slot 1) has only 0% free).
  2. Check for UCS save/export activity to /var/local/ucs/ around the onset of the issue.
  3. Review /var/log/ltm, /var/log/messages, and audit logs for indicators such as:
    • 01070710:3: Database error (0), Unable to connect to PostgreSQL database.
    • 01071aea:4: CMI heartbeat timer expired
    • 01070920:3: Application error for confpp: snmpd: no process found
    • Core file generation for snmpd and tmm.0
  4. Free space on /var by removing or relocating unnecessary files, especially large UCS files or other transient data.
  5. After restoring adequate /var free space, confirm PostgreSQL and dependent services are healthy and monitor for recurrence of mcpd database errors, snmpd restarts, and HA instability.
  6. As a preventive measure, monitor /var capacity during UCS save/export operations and avoid allowing /var to remain exhausted for prolonged periods.

Additional Information

In this failure chain, /var reached 0% free during a UCS save/export and remained full for an extended period. PostgreSQL failure occurred later, followed by repeated mcpd database connection errors, snmpd instability, TMM termination, and unplanned HA failover. CPU and memory were not significant contributors.
