K000140349: Istio-Proxy container going into CrashLoopBackOff Due to Duplicated ServiceEntries

Type
Support Solution
Published
2025-03-31
Updated
2025-03-31
Applies to
  • Aspen Mesh: 1.14, 1.11
Source
https://my.f5.com/manage/s/article/K000140349

Description

On Aspen Mesh, the istio-proxy container within a pod may enter a CrashLoopBackOff state due to configuration issues. This issue can happen when multiple ServiceEntry objects define the same host and port number with DNS_ROUND_ROBIN resolution. This results in Envoy rejecting the configuration and causing the proxy to crash.

When this issue occurs, the istio-proxy logs display the following error message:

warning envoy config    gRPC config for type.googleapis.com/envoy.config.cluster.v3.Cluster rejected: Error adding/updating cluster(s) outbound|8081||example-svc.example.com: LOGICAL_DNS clusters must have a single locality_lb_endpoint and a single lb_endpoint

 

Environment

  • Aspen Mesh 1.11.X 1.14.X
  • Istio Service Entry
  • Istio Sidecar
  • Envoy

Cause

Envoy enforces a rule that LOGICAL_DNS clusters must have a single locality_lb_endpoint and a single lb_endpoint. When multiple ServiceEntry objects define the same host and port with DNS_ROUND_ROBIN resolution, Envoy rejects the configuration, causing the istio-proxy to crash.

Recommended Actions

To resolve this issue, identify and remove duplicate ServiceEntry objects with the same host and port number.

Step 1: Identify Duplicate ServiceEntries

 Check the configured ServiceEntry objects in your cluster:

kubectl get serviceentries
NAME              HOSTS                                   LOCATION        RESOLUTION        AGE
examplese1        ["example-svc.example.com"]             MESH_EXTERNAL   DNS_ROUND_ROBIN   14d
examplese2        ["example-svc.example.com"]             MESH_EXTERNAL   DNS_ROUND_ROBIN   19d

Step 2: Remove One of the Duplicate ServiceEntries

  Example of conflicting ServiceEntry objects:

apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: examplese1
  namespace: default
spec:
  hosts:
  - example-svc.example.com
  location: MESH_EXTERNAL
  ports:
  - name: http2-8081
    number: 8081
    protocol: HTTP2
  resolution: DNS_ROUND_ROBIN

apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: examplese2
  namespace: default
spec:
  hosts:
  - example-svc.example.com
  location: MESH_EXTERNAL
  ports:
  - name: http2-8081
    number: 8081
    protocol: HTTP2
  resolution: DNS_ROUND_ROBIN

Delete one of the duplicate ServiceEntry objects:

kubectl delete serviceentries examplese2 -n default

Additional Information

Once the duplicate entry is removed, the istio-proxy container of the pod affected will start properly

This issue has been fixed in Istio 1.21, where improvements were made to allow to create two or more Service Entry with DNS Round Robin resolution pointing at the same host without crashing the istio-proxy container.
