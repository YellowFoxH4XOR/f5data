Known Issue

This is the result of a known issue. When you change a setting for a node in a non-common partition that has an associated monitor, the mcpd process leaks a small amount of memory. For example, this issue would occur if a node referencing an ICMP monitor exists in a partition other than the common partition, and you change the dynamic ratio weight for the node.

Note: This issue is more likely to manifest and cause possible mcpd crashes if you use an automated process, such as a script, to make a large number of node configuration changes. To monitor the memory utilization for the mcpd process, use the following command:

top -p `pidof mcpd`

F5 Product Development tracked this issue as ID 338708, and it was fixed in BIG-IP version 10.2.1.

For information about upgrading, refer to the BIG-IP release notes.

In addition, this issue has been fixed in Hotfix-BIGIP-10.2.0-1789.0-HF2 issued for BIG-IP version 10.2.0. You may download this hotfix or later versions of the hotfix from the F5 Downloads site.

To view a list of the latest available hotfixes, refer to K9502: BIG-IP hotfix matrix.

For information about installing a hotfix, refer to K10025: Managing F5 product hotfixes for BIG-IP version 10.x systems.

For information about the F5 hotfix policy, refer to K4918: Overview of F5 critical issue hotfix policy.

Workaround

Important: This workaround involves restarting the mcpd process and should be performed on the standby system or during a maintenance window. The mcpd process is the messaging component of the BIG-IP system; other daemons rely on the mcpd process to communicate with each other.

You can temporarily work around this issue by restarting the mcpd process. To do so, type the following command:

bigstart restart mcpd
