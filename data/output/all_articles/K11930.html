Topic

Cross-site request forgery (CSRF) is an attack method that exploits a pre-existing relationship of trust, and forces a user to run unwanted actions on a web application that the user is currently authenticated.

Description

CSRF protection / CSRT injection

When you enable the CSRF protection feature, the system inserts custom JavaScript into the response pages of protected web applications.

The inserted JavaScript rewrites the URIs, adding the BIG-IP ASM cross-site response token (CSRT) to each URI. For example, an HTML response page contains the following URI reference:

<a href="https://host.domain.com/default.aspx">

After you enable the CSRF protection feature, the BIG-IP ASM system rewrites the URI reference so that it is similar to the following example:

<a href="https://host.domain.com/default.aspx?CSRT=17017154763700437104">

In an HTML form, the inserted JavaScript appends the CSRT as a hidden form variable. Then, when the browser requests an embedded URL that has a CSRT, the BIG-IP ASM system uses the CSRT to manage the request.

Note: The BIG-IP ASM system uses inserted JavaScript for both CSRF and JSON/AJAX protection. These configurations use independent and common JavaScript. To differentiate, look for the following keywords within the JavaScript.

  • CSRF JavaScript includes the _csrf_ = keyword.
  • JSON/AJAX JavaScript has the AJAX keyword in the body of the script.
  • CSRF and JSON/AJAX use common JavaScript, which you can identify by the typeof _csrf_== keyword.

Important: When the system modifies embedded URIs, there may be unintended side effects. If this behavior is incompatible with your application, disable CSRF protection.

CSRF violations

When the system detects a CSRF attack on a protected page, such as a request for a URL that does not include the appropriate token, the system issues a CSRF attack detected violation. 

To prevent token hijacking, the system also supports token aging. If the token is expired, the system issues a CSRF authentication expired violation.

Requirements for CSRF protection

For the system to protect embedded links in an HTTP response using the CSRT, the page must meet the following requirements:

  • The response must contain an HTML tag in the first packet.
  • The system cannot compress the response.
  • You cannot set Response Chunking to Preserve in the HTTP profile associated with the virtual server.
  • In versions prior 13.1.x, POST requests should contain at least one parameter.

    For example:

    POST /modify.php?param1=value1

    Note: In 13.1.0 and later, you can configure whether parameters are required in the URL.

Configure CSRF protection (16.1.0 and later)

For ASM version 16.1.0 and later, you can configure a security policy to protect against CSRF attacks, including specifying which URLs you want the system to examine, by performing the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Security Policies > Policies List.
  3. Select the name of the security policy.
  4. Select Advanced Protection.
  5. Select CSRF Protection.
  6. Select On.
  7. For Protected URLs Type, select the SSL Only to protect SSL requests only. Otherwise, select All URLs to protect the entire web application.
  8. For CSRF Token Expiration Time, select After to enable a token expiration time (default 600 seconds), or select No Limit to disable token expiration.
  9. For URLs List (Wildcards supported), select Add URL and define the CSRF URL properties as follows:
    • For Method and URL, select the URL method and enter the URL to be protected.
      Note: Type the URL in the format: /index.html, /*/index.php, or /index.?html.
    • For Required Parameters, select one of the following options:
      • Ignore: Ignore parameters when checking if the URL entry matches the request. This option should be used if a request to a URL is considered state-changing when it does not have parameters.
      • At Least One: Verify that there is at least one parameter in a request when checking if the URL entry matches the request. This option should be used if a request to a URL is considered state-changing when it contains at least one parameter.
      • Specify: Verify that one of the specified parameters is present in a request when checking if the URL entry matches the request. This is an OR operation. This option should be used if a request to a URL is considered state-changing when it contains one specific parameter.
    • Enforcement Action: This is the action you want to the system to take. The system goes through the list to find the first match for the method + URL combination. When the match is found the parameter condition is checked. List traversal stops after the first match of method and URL. If a matching entry in the list is found, the configured action will be performed. Possible actions are:
      • None: Do nothing. This option should be used to whitelist URLs.
      • Verify CSRF Token: Verify the CSRF token.
      • Verify Origin: Verify the header origin. Only use this for AJAX requests.
  10. Select Add to add the CSRF URL properties.
  11. Select Save.
  12. Select Apply Policy.

Configure CSRF protection (11.x - 16.0.x)

You can configure a security policy to protect against CSRF attacks, including specifying which URLs you want the system to examine, by performing the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > CSRF Protection.
  3. For Current edited policy, verify that the edited security policy is the one you want to work on.
  4. Select the CSRF Protection check box.
  5. To protect SSL requests only, select the SSL Only check box. Otherwise, to protect the entire web application, leave the SSL Only check box cleared.
  6. To enable the CSRT to expire, set Expiration Time to Enabled.
  7. Enter the URL to protect as follows:

    Note: Type the URL in the format: /index.html, /*/index.php, or /index.?html.

    • BIG-IP 14.x and later

      Enter the URL to protect and click Add. If you selected Advanced Edit Mode, you can select the appropriate HTTP method.

    • Versions prior to BIG-IP 14.x

      In the URLs List, click the URLs you want the system to examine. Add at least one URL to the list. The system considers all URLs that are not in the list to be safe, unless it discovers another problem.

  8. Select Add.
  9. Select Save.
  10. Select Apply Policy.

Configure CSRF protection blocking settings 

You can configure the appropriate blocking settings for CSRF protection by performing one of the following procedures:

Impact of procedure: Performing the following procedures should not have a negative impact on your system.

BIG-IP 12.x and later

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Policy Building > Learning and Blocking Settings.
  3. Under Advanced settings, in the Policy Building Settings section, expand CSRF Protection, and then select the appropriate Learn, Alarm, or Block setting for the two CSRF violations.
  4. Select Save.
  5. Select Apply Policy.

BIG-IP 11.x and earlier

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Blocking > Settings.
  3. For Violations List, select the appropriate Learn, Alarm, or Block setting for the two CSRF violations.
  4. Select Save.
  5. Select Apply Policy.
