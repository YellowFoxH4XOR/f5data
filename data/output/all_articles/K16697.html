Known Issue

Rebooting a cluster member may cause the Master Control Program Daemon (mcpd) process on secondary blades of other group members to restart.

This issue occurs when all of the following conditions are met:

  • At least two multi-blade (cluster) BIG-IP systems are configured as part of a trust domain. This may include a physical chassis or vCMP guests with at least two blades each configured.
  • Cluster members of the trust domain are provisioned with either the BIG-IP ASM or Fraud Protection Service (FPS) module.
  • One of the cluster members of the trust domain is rebooted.

The mcpd process restart may occur within a time frame of between a few minutes up to 24 hours after the cluster member reboot occurs. The mcpd restart should occur only once, and not repeat until the next time a device in the trust domain is rebooted.

The mcpd restart is caused by an inconsistency between the primary and secondary blades after a reboot, and does not occur if only a single blade is rebooted. Checking and fixing the inconsistency after a reboot may prevent this issue from occurring.

Impact

During the restart of the mcpd process on the secondary blade, that blade is offline and not handling traffic. There is no impact to traffic handled by the primary blade.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • When the mcpd process fails on the secondary blade, messages are logged to the /var/log/ltm file that appear similar to the following example:

    err mcpd[5958]: 01020036:3: The requested Datasync Device Table Stats (/Common/vcmp2.example.com cs-asm-dosl7) was not found.

    err mcpd[5958]: 01070734:3: Configuration error: Configuration from primary failed validation: 01020036:3: The requested Datasync Device Table Stats (/Common/vcmp2.example.com cs-asm-dosl7) was not found.... failed validation with error 16908342.

    err mcpd[5958]: 01020036:3: The requested Datasync Device Table Stats (/Common/vcmp2.example.com crypt-asm-dosl7) was not found.
    err mcpd[5958]: 01020036:3: The requested Datasync Device Table Stats (/Common/vcmp2.example.com crypt-fpm) was not found.
    err mcpd[5958]: 01020036:3: The requested Datasync Device Table Stats (/Common/vcmp2.example.com cs-asm-dosl7) was not found.
    err mcpd[5958]: 01020036:3: The requested Datasync Device Table Stats (/Common/vcmp2.example.com cs-fpm) was not found.
    err mcpd[5958]: 01020036:3: The requested Datasync Device Table Stats (/Common/vcmp2.example.com rsa) was not found.

Workaround

To work around this issue, you can check and fix inconsistencies between the primary and secondary blades after a reboot. To do so, perform the following procedures:

Important: You should repeat these procedures each time you reboot a device in the trust domain.

Checking for inconsistencies

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Traffic Management Shell (tmsh) by typing the following command:

    tmsh

  2. Check for inconsistencies by typing the following command on each blade of each cluster in the trust domain:

    list security datasync device-stats /Common/datasync-device-*/*cs-asm-dosl7* table

    You should view an object for each of the devices (clusters) in the trust domain. For example, if two multi-blade devices are joined in a trust domain, vcmp1.example.com and vcmp2.example.com (and both devices contain two blades), you will view output that appears similar to the following example:

    security datasync device-stats datasync-device-vcmp1.example.com/datasync-device-vcmp1.example.com-cs-asm-dosl7-stats {
        table cs-asm-dosl7
    }
    security datasync device-stats datasync-device-vcmp2.example.com/datasync-device-vcmp2.example.com-cs-asm-dosl7-stats {
        table cs-asm-dosl7
    }

    The previous example displays the object references for both vcmp1.example.com and vcmp2.example.com; therefore, the state is good. No further action is required on this device.

    However, in a faulty state, the secondary blade of vcmp2.example.com will display output that appears similar to the following example:

    security datasync device-stats datasync-device-vcmp1.example.com/datasync-device-vcmp1.example.com-cs-asm-dosl7-stats {
        table cs-asm-dosl7
    }

    Notice that the object reference for vcmp2.example.com device is missing. This indicates that the state is inconsistent and an mcpd restart may occur sometime within 24 hours. If the state is inconsistent, perform the following Fixing an inconsistency (if needed) procedure.

Fixing an inconsistency (if needed)

To fix an inconsistent state, you can force a synchronization of the datasync device groups to the device with the inconsistent state. For example, if two multi-blade devices are joined in a trust domain, vcmp1.example.com and vcmp2.example.com (both devices contain two blades), and if the vcmp2.example.com device had the inconsistent state, force a synchronization from vcmp1.example.com to vcmp2.example.com. For the purpose of this example, the vcmp2.example.com device is in an inconsistent state, and you are forcing a synchronization from vcmp1.example.com to vcmp2.example.com.

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Traffic Management Shell (tmsh) on vcmp1.example.com by typing the following command:

    tmsh

  2. Set the sync leader setting to vcmp1.example.com for the global device group by typing the following command:

    modify cm device-group datasync-global-dg devices modify { vcmp1.example.com { set-sync-leader } }

    Note: Wait a few seconds before performing Step 3.

  3. Set the sync leader setting to vcmp1.example.com for the vcmp1.example.com device group object by typing the following command:

    modify cm device-group datasync-device-vcmp1.example.com-dg devices modify { vcmp1.example.com { set-sync-leader } }

  4. Set the sync leader setting to vcmp1.example.com for the vcmp2.example.com device group object by typing the following command:

    modify cm device-group datasync-device-vcmp2.example.com-dg devices modify { vcmp1.example.com { set-sync-leader } }

    Note: Wait a few seconds, then recheck the state by performing the Checking for inconsistencies procedure. At this point, the blades should be synchronized.
