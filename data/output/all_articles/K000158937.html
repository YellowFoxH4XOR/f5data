Description

The BIG-IP may sometimes log the following messages in /var/log/tmm*

<big-ip hostname> notice Oops @ <source code file number>:<source code line number>:<message>

 

For example:

<13> Nov 27 18:20:13 mybigip.local.org notice Oops @ 0x30cd0e0:216: maximum pages

 

Environment

Any F5 BIG-IP product running tmm that generates Oops logs into /var/log/tmm*

While there may be other log messages with the word "oops," such as linux kernel drivers, ie. in other log files, this article specifically addresses only those that are generated from tmm in /var/log/tmm*.

 

Cause

The error message is generated when tmm code recognizes an Out Of Place Situation (OOPS), in other words, an unexpected condition.

 

For example, the following signifies that the tmm memory allocator failed to allocate memory:

<13> Nov 27 18:20:13 mybigip.local.org notice Oops @ 0x30cd0e0:216: maximum pages

 

Other examples:

The following signifies a problem while processing an iRule:

Oct 17 03:16:14 mybigip.local.org crit tmm[15415]: 01010289:2: Oops @ 0x29fda69:2759: Cannot continue a rule that is not suspended.

 

The following are just benign messages from a code quality tool (K51513933):

Dec 19 10:45:04 mybigip.local.org crit tmm[14165]: 01010289:2: Oops @ 0x2b13900:1348: invalid tp

 

 

Recommended Actions

Ideally, you want a clean bill of health for your system without tmm reporting any Oops messages by narrowing down the root cause of the message.

 

With benign messages, you might even try suppressing the logs, if they occur too frequently.

 

Fortunately, some Oops log messages are accompanied with a stack trace.

For example:

 

<13> Nov 27 18:20:10 localhost notice pgo_use x86_64 vadc TMM Version 17.1.3.0.0.11
<13> Nov 27 18:20:10 localhost notice Called from 0x15df736
<13> Nov 27 18:20:10 localhost notice Called from 0x8248df
<13> Nov 27 18:20:10 localhost notice Called from 0x82bc5e
<13> Nov 27 18:20:10 localhost notice Called from 0x82becc
<13> Nov 27 18:20:10 localhost notice Called from 0x2570f40
<13> Nov 27 18:20:10 localhost notice Oops @ 0x30cd0e0:216: maximum pages

 

A stack trace will help F5 support determine which part of the code leads to the OOPS condition. For example, after processing by F5 support, the following stack trace above suggests the root cause for this "maximum pages" error message is a failure in TCL (iRules) allocating memory for its variables.

 

#0 0x15df736 in tmm_oops at ../lib/stdio.c:1435
#1 0x8248df in page_alloc at ../kern/page_alloc.c:217
#2 0x82b0a1 in umem_page_alloc at ../kern/umem.c:2273
#3 0x82bc5e in umalloc at ../kern/umem.c:3234
#4 0x82becc in urealloc at ../kern/umem.c:2974
#5 0x2570f40 in Tcl_AttemptSetObjLength at ../generic/tclStringObj.c:884

For a more detailed analysis, you may upload your qkview and request a stack trace analysis to F5 support for further information.

 

You can modify how tmm handles caught unexpected conditions by modifying the db key tmm.oops, which can be set to silent,log, or panic.

 

The default behavior is to just log any unexpected conditions and try to resume traffic processing:

 

# tmsh list sys db tmm.oops
sys db tmm.oops {
  value "log"
}


If there are too many Oops log messages, you may try to suppress them by setting tmm.oops to silent.

 

# tmsh modify sys db tmm.oops value silent

 

In more difficult to diagnose cases, you may try to force an tmm core for an even deeper analysis.

You can configure the OOPS condition to panic and dump core instead of just logging a message, if tmm did not already produce a core. See: K10062: Overview of managing BIG-IP core files

If you want tmm to dump core for deep analysis, you can set tmm.oops to panic.

 

 # tmsh modify sys db tmm.oops value panic

 

Note: If you set tmm.oops to panic, tmm will stop, produce a core, and restart every time it encounters the unexpected condition. Please be careful to do this on only one of your active-standby pair, or expect some traffic impacting downtime. Configuring tmm.oops to panic on both active and standby units or blades may cause tmm to constantly core.

Note: If you expect the unexpected condition to repeat over and over, consider configuring the tmm core retention to 2 to 3 cores without rotation. See: K24290241: Overview of the BIG-IP core file retention policy
