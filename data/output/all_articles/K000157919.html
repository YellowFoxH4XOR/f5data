K000157919: BIG-IP Controller Ingress Services Shows External-IP Pending

Type
Support Solution
Published
2025-11-20
Updated
2025-11-20
Source
https://my.f5.com/manage/s/article/K000157919

Description

When using F5 BIG-IP Container Ingress Services (CIS) and F5 IPAM Controller in Kubernetes environments, users may encounter an issue where Kubernetes LoadBalancer services display their external IPs as "Pending" after upgrading Kubernetes (for example, from v1.29.x to v1.30.x). Key symptoms include:

 

  • The EXTERNAL-IP field for LoadBalancer services remains in the "Pending" state.
  • The problem is observed after a Kubernetes upgrade, but not on freshly deployed clusters with identical configuration.
  • Log messages show successful processing of services by CIS, but the assigned external IP does not persist or reverts to "Pending."
  • No direct errors are seen in CIS or IPAM logs related to this failure.

Environment

  • Kubernetes clusters (v1.29.x and v1.30.x), both upgraded and newly created
  • F5 BIG-IP Container Ingress Services (CIS) v2.20.1 (and earlier versions tested)
  • F5 IPAM Controller v0.1.12
  • MetalLB controller present in the environment
  • vSphere infrastructure using vsphere-cloud-controller-manager and cluster API (capv-controller-manager)
  • LoadBalancer services managed by both F5 CIS and MetalLB
  • Some services use TransportServer CRDs; others are standard LoadBalancer services
  • Issue occurs only in upgraded clusters, not fresh deployments with same configuration

Cause

The root cause is a conflict between F5 CIS and MetalLB controllers, where both attempt to manage the same Kubernetes LoadBalancer services. This results in the external IP being assigned and then reverted to "Pending" as each controller overwrites the other's changes.

Recommended Actions

To resolve this conflict and ensure that only F5 CIS manages relevant LoadBalancer services:

 

  1. If MetalLB is not required:
    Disable or remove the MetalLB controller from your cluster.
  2. If MetalLB is required for other workloads:
    Use the loadBalancerClass feature:
    • Add to your service manifests managed by CIS:

      spec:
        loadBalancerClass: f5

    • Update your CIS deployment arguments:

      --load-balancer-class=f5

      --manage-load-balancer-class-only=true 
    • Restart the CIS controller after making these changes.
    • Ensure only services with loadBalancerClass: f5 are managed by CIS; others can be managed by MetalLB or another controller as needed.
  3. Verify Resolution:
    Confirm that affected LoadBalancer services now have their EXTERNAL-IP correctly populated instead of showing "Pending."

Additional Information

  • This issue does not occur on freshly deployed clusters with identical configuration—indicating it is specific to environments where both controllers are active.
  • The ipMode field seen in service status is informational only; it cannot be configured directly.
  • Updating CRDs to latest versions helps avoid unrelated schema validation errors but does not resolve this particular issue.
  • Using loadBalancerClass is supported in recent versions of Kubernetes and CIS, providing a clean method for avoiding multi-controller conflicts.
