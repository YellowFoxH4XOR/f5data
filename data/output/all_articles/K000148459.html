Description

This article explains the scenarios where the Message Routing Framework (MRF) is needed for HTTP2 deployments. Specifically, it details when MRF is required and when it is not. MRF is an essential feature for routing HTTP2 traffic in certain configurations to ensure proper communication between the client and the pool member(s).

Environment

  • HTTP2 full proxy deployments
  • HTTP2 Gateway configurations
  • Client connections using HTTP2
  • Pool member(s) using HTTP1.1, HTTPS, or HTTP2
  • HTTP::respond iRule
  • HTTP redirects

Cause

None

Recommended Actions

The need for MRF in HTTP2 deployments depends on the specific configuration and the type of pool member connection. The following scenarios explain when MRF is needed or not:

Client (HTTP2) -> BIG-IP -> Web Server Pool (HTTP1.1): No MRF required
Client (HTTP2) -> BIG-IP -> Web Server Pool (HTTPS): No MRF required
Client (HTTP2) -> BIG-IP -> Web Server Pool (HTTPS with HTTP2): MRF required for HTTP2 to backend, otherwise HTTP1.1 is used
Client (HTTP2) -> BIG-IP -> Local HTTP::respond iRule: Works with and without MRF
Client (HTTP2) -> BIG-IP -> Internal Redirect -> Local HTTP::respond iRule: Fails without MRF, works with MRF
Client (HTTP2) -> BIG-IP -> Internal Redirect -> Web Server Pool (HTTP1.1): Fails without MRF, works with MRF
Client (HTTP2) -> BIG-IP -> Internal Redirect -> Web Server Pool (HTTPS): Fails without MRF, works with MRF
Client (HTTP2) -> BIG-IP -> Internal Redirect -> Web Server Pool (HTTP2): Fails without MRF, works with MRF

Additional Information

When using the HTTP::respond iRule, MRF is able to handle the responses and redirects properly, ensuring that the client receives the intended response through the BIG-IP Virtual Server. Without MRF, the system may not correctly process the HTTP2 protocol, leading to failures in redirection and response handling. This is particularly important for maintaining protocol consistency and ensuring seamless client-server communication in more complex routing scenarios.
