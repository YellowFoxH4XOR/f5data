Description
Microsoft Sharepoint provides the ability to integrate with native Microsoft Office applications running on the client. This feature can fail to function when using Big-IP APM since the cookies used by APM to track the user's session may fail to share between the browser displaying Sharepoint and the Office application trying to load the document, as outlined in K94430306. This can be addressed by either adding the relevant paths to the client's trusted paths or by configuring the APM to work with Microsoft's Office Forms-Based Authentication protocol (MS-OFBA). This article provides details on APM's MS-OFBA configuration and functionality.

Environment

  • Big-IP APM
  • Sharepoint
  • Microsoft Office
  • OFBA

Cause
Configuring OFBA will allow the Office application to authenticate with APM so that users can access Sharepoint documents, or allow Office to send a separate persistent cookie to re-use the user's existing APM Session.

Recommended Actions

  1. Configure the access policy handling sharepoint authentication to authenticate OFBA-compliant clients
  2. Attach the iRule /Common/_sys_APM_MS_Office_OFBA_Support to the APM virtual server handling Sharepoint authentication
  3. Review the settings in the /Common/sys_APM_MS_Office_OFBA_DG datagroup

Additional Information
There are two factors to be considered in this configuration. The first is whether Office should reuse the user's existing APM session or negotiate a new one. Reusing the existing session allows users to avoid logging in again but requires setting a persistent cookie on the user's machine that isn't tied directly to the browser session used for Sharepoint, which can present a security vulnerability. To allow this, enable the "ie_sp_session_sharing_enabled" variable (value 1) in the /Common/sys_APM_MS_Office_OFBA_DG datagroup. When this setting is enabled, the APM will send an additional cookie in addition to the MRHSession cookie with the same value, named "MRHSOffice." This cookie will be appended to each request coming from a web browser. When a request is received from an OFBA-compliant client (an Office application), the iRule checks whether that session ID matches an existing allowed session and if so rewrites or adds an MRHSession cookie with that value.

If the ie_sp_session_sharing_enabled value is set to 0 or a request is received from an OFBA-compliant client that does not include an MRHSOffice or MRHSession cookie, the APM will reply with either an HTTP 302 or HTTP 403  response to initiate the OFBA protocol. For more information on this protocol, please review Microsoft's documentation here.

[MS-OFBA]: Office Forms Based Authentication Protocol Note: This link points to a resource not controlled by F5. Its owners may update or remove the document without notice. 

As the MS-OFBA protocol relies on the browser presentation in the Office client itself, the system may interact in unexpected ways with more complex access policy configurations. Additionally,  iRules that modify ACCESS::restrict_irule_events property for the connection flow will cause the OFBA irule to fail. This includes the system default VDI profile. As such, a virtual server cannot be configured to simultaneously support VDI and OFBA.
