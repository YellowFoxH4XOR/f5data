K000149070: ASM IP Address Exception Overlap

Applies to

Description

In some cases when implementing IP Address Exceptions, and using IP subnets for the exception, you may run into an issue. That issue can come about when within that same subnet you have to add additional exceptions that are more specific. So that brings up the question... How will ASM deal with this overlap?

Environment

IP Exceptions needed to either block or allow IPs

Cause

The underlying issue is the question of specificity. What will ASM do when there is this overlap?

How the system responds to blocking requests sent from an IP address.

  • Policy Default: The Security >> Application Security : Policy Building : Learning and Blocking Settings will be used for requests from this IP address.
  • Never Block: The system does not block requests sent from this IP address, even if your security policy is configured to block all traffic.
  • Always Block: The system blocks requests sent from this IP address on condition that IP is blacklisted is set to Block under Policy Building Settings.

So it really depends on how you configure it.

For example:

  1. You have a subnet set to "Trust IP" (for example 10.0.0.0/255.0.0.0). 
  2. A more specific IP needs to be blacklisted within that subnet (for example 10.10.10.10/255.255.255.255) and is set to "Don't Trust IP".
  3. The Blacklist setting of "Block this IP Address" is set to "Policy Default".
  4. In Security ›› Application Security : Policy Building : Learning and Blocking Settings :: IP Address and Geolocation :: IP is blacklisted for the policy in question is set to Block.
  5. Then it will block it regardless of what is set for the greater subnet (in example 10.0.0.0/255.0.0.0).

Recommended Actions

What it comes down is to configure an "order of precedence" using the settings within the policy.

A couple of things to consider is how this will effect other portions of the policy.

  • For instance if it is set to Never Block the ASM Policy will act as if the IP does not even exist. It will not log, learn, or anything else with that subnet/IP.
  • If it is set to Always Block and IP is blacklisted is set to Block under Policy Building Settings it will always block that IP/subnet regardless of anything else. So how you set this up is very important.
    • Testing should be done because if it is set to Block it has no staging and starts immediately. If at all possible set IP is blacklisted to Alarm and check the results first and then adjust the policy as needed to get the results you need.
