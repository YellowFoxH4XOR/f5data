K000161453: BIG-IP APM resets requests with "Access encountered an error (Operation not supported)" when the URI contains unencoded characters

Type
Support Solution
Published
2026-05-27
Updated
2026-11-02
Applies to
  • BIG-IP
  • BIG-IP APM: 17.1.0, 17.1.2, 17.1.1, 17.5.1, 17.5.0, 17.1.3
Source
https://my.f5.com/manage/s/article/K000161453

Description

After you upgrade the BIG-IP system, requests to an application behind a virtual server with an access profile fail. The BIG-IP system resets the connection with the following reset cause:

Access encountered an error (Operation not supported)

In a packet capture, the reset cause appears as F5RST: Access encountered an error (Operation not supported).

The issue occurs only for requests whose URI contains unencoded characters such as {, }, |, \, or ^. For example, Microsoft SharePoint edits or updates fail, because some browsers send curly braces without encoding them. The issue does not occur when the access profile is removed from the virtual server.

Environment

  • BIG-IP APM 17.1.x, 17.5.x, or 21.1.x, before the fixed releases listed in Recommended Actions

  • Virtual server with an access profile

  • Application that sends URIs with unencoded characters such as {, }, |, ", \, or ^

Cause

BIG-IP APM validates the request URI more strictly, and it rejects requests that contain characters that RFC 3986 does not allow without encoding. This issue is tracked as the following bugs:

  • Bug ID 2298245: Access Profile rejects HTTP requests containing unencoded characters in the URI ({, }, |, ", \). Known affected versions include 17.1.3.2, 17.5.1.6, 21.0.0, and 21.1.0.

  • Bug ID 2448513: Access Profile rejects HTTP requests containing ^ in the URI. It occurs after an upgrade to 17.5.1.8.

Answer/Recommended Actions

Upgrade

Upgrade to a release that includes both fixes:

BranchBug ID 2298245 fixed inBug ID 2448513 fixed in
17.1.x17.1.3.417.1.3.6
17.5.x17.5.1.817.5.1.10
21.1.x21.1.0.1Not yet released at the time of writing. Check Bug ID 2448513.

Workaround: iRule

You can add the following iRule to the virtual server. It encodes the affected characters in the query string before BIG-IP APM processes the request. The issue affects only query string parameters.

Impact of procedure: F5 recommends performing this procedure during a scheduled maintenance window.

when HTTP_REQUEST priority 100 {
    if { [HTTP::has_responded] } { return }
    set my_query [HTTP::query]
    if { ($my_query contains "{") or
         ($my_query contains "}") or
         ($my_query contains "|") or
         ($my_query contains "\"") or
         ($my_query contains "\\") or
         ($my_query contains "^")
     } {
        HTTP::query [string map {"{" "%7B" "}" "%7D" "|" "%7C" "\"" "%22" "\\" "%5C" "^" "%5E"} $my_query]
    }
}

To back out of this procedure, remove the iRule from the virtual server.

You can also ask the application owner to encode URIs as RFC 3986 requires, so that the application does not send these characters unencoded.
