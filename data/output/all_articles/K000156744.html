K000156744: Velos : etcd and openshift high CPU intermediately

2025-10-01

Description

Permanent or intermittent high CPU usage may be observed on the controller board of F5 VELOS CX410 systems running F5OS-Chassis v1.6.1 or v1.6.2. This issue is characterized by periodic CPU spikes, sometimes exceeding 70–80% utilization for short durations. The processes most commonly involved are etcd and openshift, as seen in system logs and top output:

PID USER %CPU COMMAND

2358 root 32.1 etcd

62777 root 96.4 oc describe pod -n kubevirt virt-handler-gskq8

...

82263 root 109.3 openshift

These spikes typically do not result in end-user impact or system slowness, but monitoring tools may trigger alerts due to the transient high CPU usage.

Environment

  • Product: F5OS - Chassis (VELOS CX410)
  • Software Version: v1.6.1, v1.6.2
  • Platform: F5-VEL-LTM-CX410-AC, F101
  • Configuration: Controller board running infrastructure and master roles; OpenShift/etcd cluster present.
  • Typical setup: Multiple blades; tenants may or may not be processing traffic.

Cause

  • A software issue (ID 1624853) causes the etcd process to consume excessive CPU resources due to inefficiencies in its operation under certain conditions.
  • Periodic spikes are also caused by internal OpenShift/etcd/OMD operations.
  • Additional contributing factors can include physical network interface errors (such as high FCS error counts on management ports) and hardware faults (such as PSU errors).
  • The versions of OpenShift and etcd used in F5OS-C v1.x are relatively old, which can contribute to performance issues.

Recommended Actions

  1. Software Upgrade
    Upgrade to F5OS-C v1.8.1 or later, where ID 1624853 is resolved and additional interface-related bugs are fixed.
  2. Workaround for Older Versions
    Limit etcd CPU affinity using the taskset -cp <CPU_LIST> <ETCD_PID>
    Replace <CPU_LIST> (e.g., 4-7) with your desired CPUs and <ETCD_PID> with the actual process ID of etcd.
    Example:

    taskset -cp <CPU_LIST> <ETCD_PID>

  3. Cluster Maintenance
    Rebuild the OpenShift cluster to refresh etcd data and reinstall the cluster if persistent spikes remain after other steps.
    • This does not affect confd configuration, partitions, or tenants.
    • No rollback is available; a maintenance window of up to 2 hours is recommended.
    • Reference procedure: K64001020#workaround procedure for rebuilding OpenShift cluster on VELOS/F5OS-Chassis systems
  4. Hardware and Network Health
    Investigate and resolve physical network issues—especially high FCS error counts on management interfaces.
    Address any PSU faults by raising an RMA if necessary.
  5. Monitoring Recommendations
    Use the metric coreTotal1minAvg   for alerting, with a recommended threshold of 75%  to avoid false positives from brief spikes.
  6. Expected Behavior
    Brief CPU spikes caused by OpenShift or etcd are considered normal and do not impact cluster health or tenant workloads under typical circumstances.
    If sustained high CPU usage is observed, further investigation should be performed.
