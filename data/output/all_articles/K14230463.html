Topic

You should consider using this procedure under the following condition:

  • You want to reduce the number false positive violations generated in NGINX App Protect WAF.

Description

False positives occur when the system reports and blocks legitimate requests. This article describes some of the steps you can take to tune your NGINX App Protect WAF security policy to reduce the number of false positives.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You have administrative access to manage NGINX on the system.

Procedures

Perform the following procedures to reduce the number of false positives:

  • Add IP address exceptions
  • Review potential false positive violations
  • Configure security violation logging
  • Use transparent enforcement mode

Add IP address exceptions

NGINX App Protect WAF lets you add IP addresses or a range of IP addresses that come from trusted sources to an exception list to overwrite configuration settings from other parts of the security policy. You can configure specific rules, such as one to reduce false positives by not blocking requests from IP addresses in the list. To do so, you use the whitelist-ips entity in the security policy. The blockRequests attribute lets you configure the associated action with the following allowed values:

Note: F5 is working to eliminate exclusionary language in our products and documentation. For more information, refer to K34150231: Exclusionary language in F5 products and documentation.

  • policy-default specifies that the policy's blocking-settings configuration is used for requests from this IP address.
  • never specifies that the system does not block requests sent from this IP address, even if your security policy is configured to block all traffic.
  • always specifies that the system blocks requests sent from this IP address.

The following example rule defines IP addresses in the range 10.10.0.0/16 as trusted and prevents the system from blocking requests originating from them, despite the violation blocking settings:

{
    "name": "security_policy",
    "template": {
        "name": "POLICY_TEMPLATE_NGINX_BASE"
    },

    [...]

    "blocking-settings": {
        "violations": [
            {
                "name": "VIOL_RATING_THREAT",
                "alarm": true,
                "block": true
            }
        ]
    },
    "whitelist-ips": [
            {
                "blockRequests": "never",
                "neverLogRequests": false,
                "ipAddress": "10.10.0.0",
                "ipMask": "255.255.0.0"
            }
    ]
}

Review potential false positive violations

Investigating application traffic trends and statistics in your environment to determine false positives is an ongoing and integral part of security policy tuning. In particular, you should review the violation ratings of illegal requests in the security logs. NGINX App Protect WAF algorithms rate its violations to help distinguish between attacks and potential false positive alerts. Requests with a low violation rating (1 to 2) are more likely to be false positives, and an administrator should review and appropriately tune these.

Violation ratingAction
4 - 5The request is most likely a threat and unlikely to be a false positive.
3The request requires examination before classifying it as a false positive.
2The request looks like a false positive and requires examination before you appropriately tune your security policy.
1The request is most likely a false positive, and you should review and appropriately tune your security policy.
0There is no violation.

In the default security policy, the system logs and blocks violations with rating 4 or 5, but does not log or block violations with rating 3. When troubleshooting, you can override these settings using the VIOL_RATING_THREAT and VIOL_RATING_NEED_EXAMINATION settings, respectively. For example in the following configuration example, the /etc/nginx/NginxStrictPolicy.json strict policy causes the system to block requests that have a Violation Rating of 3, Needs examination rating.

[...]
      "blocking-settings" : {
         "violations" : [
     [...]
            {
               "block" : true,
               "description" : "Violation Rating Need Examination detected",
               "name" : "VIOL_RATING_NEED_EXAMINATION"
            }
         ]
      },
[...]

Configure security violation logging

To review the violation ratings of the application traffic in your environment, you need to log the appropriate information in the security log file. To log security violations with the appropriate details, perform the following procedures:

  • Define the security log directive file
  • Declare the log directive file with a log destination
  • Restart NGINX

Define the security log directive file

You define the filter and content format in the NGINX App Protect WAF security log directive file. The default NGINX App Protect WAF security log directive file is /etc/app_protect/conf/log_default.json. Using an editor, create a second file /etc/app_protect/conf/illegal_violations.json and save the following:

Note: The request_type in the filter can use any of the following values: all, illegal, or blocked. The format attribute in the content entity can be splunk, arcsight, default , or user-defined. For the full list of filter, content format, and other entity values, refer to Security Log Configuration File in the NGINX documentation.

{
    "filter": {
        "request_type": "illegal"
    },

    "content": {
        "format": "user-defined",
        "format_string": "Request ID %support_id%: %method% %uri% received on %date_time% from IP %ip_client% had the following violations: %violations%. attack_type=%attack_type% sub_violations=%sub_violations% severity=%severity% threat_campaign_names=%threat_campaign_names% violation_rating=%violation_rating% outcome=%outcome% outcome_reason=%outcome_reason% violation_details=%violation_details% request=%request%" request_status=%request_status%,
        "max_request_size": "any",
        "max_message_size": "5k"
    }
}

In the previous example, the system only logs illegal requests, and each log entry contains a user defined format that includes useful information to determine whether a violation is a false positive. In particular, it includes the violation rating %violation_rating%.

Declare the log directive file with a log destination

To use the security log directive file created in the previous procedure, define the app_protect_security_log_enable and app_protect_security_log directives in the nginx.conf file, as well as the log destination. You can configure targeted logging by setting the directives at any of the following contexts: http, server , or location. The following example configures logging at the http context and logs security information in /var/log/app_protect/class_illegal_security.log:

Note: For more information on configuring NGINX logging, refer to Directives in nginx.conf in the NGINX documentation.

http {
    include       /etc/nginx/mime.types;
    app_protect_enable on;
    app_protect_policy_file "/etc/nginx/nap.d/local-policy.json";

    app_protect_security_log_enable on;
    app_protect_security_log "/etc/app_protect/conf/illegal_violations.json" /var/log/app_protect/class_illegal_security.log;
    [...]
} 

Restart NGINX

Restart the nginx process by entering one of the following commands, as appropriate for your initial NGINX installation method and operating system:

  • nginx -s reload
  • systemctl restart nginx

Enter the following command to follow the security logs and review illegal requests with violations:

tail -f /var/log/app_protect/class_illegal_security.log

Use transparent enforcement mode

The Enforcement Mode setting allows you to introduce a security policy to your application environment in stages. When set to Transparent, the system does not block any requests. You can configure multiple security policies at different contexts (http, server, or location) in the nginx.conf file, which is useful when you want to observe traffic patterns for a virtual server, URI, or path for an application or gather statistics and trends to determine false positives before actual implementation. The following values are available for Enforcement Mode:

  • Blocking: The system blocks and logs illegal or suspicious requests, depending on configurations in the rest of the security policy.
  • Transparent: The system does not block any illegal or suspicious requests. Logging depends on other settings in the security policy.

When configuring Enforcement Mode, you should enable appropriate logging, as described in the Configure security violation logging procedure in this article, to review potential false positives.
