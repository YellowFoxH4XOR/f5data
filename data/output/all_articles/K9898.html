Topic

When ARX systems are configured for redundancy and failover, the active ARX system will synchronize state and configuration information to the peer (standby) ARX system.

A redundant ARX cluster provides the following methods of protection from an outage:

  • Service Manager

    Critical ARX daemons are monitored and restarted automatically, if needed. A failover can be triggered when a critical daemon fails or experiences a repeated failure.
     
  • Redundant Processors

    Each fastpath processor will mirror state information with a redundant processor. If the processor fails, the redundant processor takes over. Failure of both processors will trigger a failover.
     
  • Battery-backed NVRAM

    Non-volatile RAM used to store critical transaction information is battery backed to ensure that critical transaction information is not lost in the event of a power failure.
     
  • Quorum disk

    The redundant ARX cluster uses a quorum disk to ensure that the ARX with the most current state is active.
     
  • Critical Services

    The ARX administrator may designate external services as criteria for failover.
     
  • Reboot Cycle Protection

    A reboot limiter ensures switches do not infinitely transition.
     
  • Synchronization

    The ARX does not store any user data on the switches. In the event of a failover, transaction information is used to ensure that transactions are applied in the order they were received on the VIP. NFS Transaction IDs stored in the DRC ensure that duplicate requests for non-idempotent NFS transactions are not allowed to proceed. The active ARX system synchronizes the following state information to the standby ARX system:

    • In-Flight Transactions
    • Duplicate Request Cache (DRC)
    • Network Lock Manager clients (NLM)
    • Global configuration

The redundant ARX cluster employs a negotiated failover. The active ARX will only fail over if the peer ARX has a better view of the resources. Both systems must be able to reach the network for failover to occur. 

When a failover occurs, the following takes place:

  • The newly-promoted ARX system will:

    • Start services
    • Advertise the VIP and VMAC
    • Send gratuitous ARPs to update ARP tables
    • Establish connections with back-end resources and resume transaction in the order received
       
  • NFS Clients will pend their transactions until the VIP is active on the newly-promoted ARX system.
     
  • CIFS Clients will disconnect and automatically reconnect in the following situations:

    • If a user has an Explorer window open, and the window closes.
    • Lock state is preserved.


A small namespace (one volume less than 16 shares) will typically resume on the peer ARX system about 45 seconds after a failover. However, a large configuration may take longer than two minutes.

Note: Failover time is calculated from failover until shares are viewable on the newly-promoted ARX, not when the client resumes, because clients have back-off algorithms when a server is down.
