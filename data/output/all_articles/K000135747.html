K000135747: Understanding how CPU cores and memory are handled on a vCMP guest.

Description

You add a specific amount of cores to create and operate a vCMP guest. It is often assumed that both the CPUs and the memory from all the spanned blades acts in totality. However, that is only partially true.

You may ask yourself "Why are we seeing high CPU on this guest when we have allocated 20 CPU cores and it spans 2 blades (it can be more than 2). That is a total of 40 cores?".

To understand this we have to separate CPUs and memory because what happens when it is allocated is different for both.

Lets look at CPU cores first.

  • In the scenario described above the Data Plane is effectively 40 cores. However, for the Control/Analysis Plane due to the creation of a disk image for each blade (where the Linux host for each blade resides) it effectively only works with the 20 cores on each blade that has been allocated. This has to do with how the Linux operates within the confines of the Control/Analysis Plane. When you configure a guest a virtual disk is created and the portion of the disk space on a blade that you have allocated to a guest Virtual Machine (VM) is set.
    • For example, if a guest spans three blades, the system creates three virtual images for that guest. One on each blade on which the guest is residing. Each virtual disk is implemented as an image file with an .img extension, such as guest_A.img. Thus there are in effect 3 Linux OSs running and Linux cannot span the blades.
  • Memory on the other hand works a differently. It does not span but resides only on the one blade it is installed upon.
    • With vCMP memory cannot be allocated separately. It is divided up between the total number of cores and when you allocate a core that amount of memory goes along with it.
      • For Example if the system divides up the memory so each core has 2GB and you assign 4 cores the total memory is 8GB. If that guest spans 3 blades that does not make total memory 24GB. It will still only be 8GB per blade.

Using the restjavad process as an example it is now running on all blades individually and taking memory on each because it runs on the Control/Analysis Plane. Whereas tmm, where traffic is run, resides on the Data Plane and it is able to access the CPU cores across the blades but only has access to the memory on each blade.

The following article will help understand the Data and Control/Analysis Planes: K15003: Data and control plane tasks use separate logical cores when the BIG-IP system CPU uses Intel Hyper-Threading Technology

Environment

  • A network in which Viprion chassis are in use with multiple blades and the guests that reside on the Viprion span (are configured to use more than one blade) the blades.
  • Virtual Clustered Multiprocessing™ (vCMP®) This is the F5 Virtual Hypervisor.
  • vCMP Host, vCMP Guest, the various F5 Modules

Cause

By design a BIG-IP on a Viprion chassis provides many benefits. But depending on how the vCMP Guest has resources allocated and understanding how that alocation works can bring about both good and bad results. So the question is why the high CPU and/or the high memory?

Recommended Actions

  1. Review the needs of the system based on the modules and traffic (amount and type) to try and ensure a proper balance of resources is allocated to the guest. Some things such as ASM Aggregation will greatly influence how many cores should be allocated to the guest.
