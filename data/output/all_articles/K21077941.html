Topic

This article covers the basic usage examples,  calculations, and metrics utilization of the BIG-IP TMOS Shell (tmsh) cmetrics component. For information about tmsh cmetrics commands, refer to the following article:

  • CloudDocs TMSH Reference for net cmetrics

Description

The tmsh cmetrics component displays entries in the route metrics table on the BIG-IP system. Additionally, you can delete a specified route metric entry from the table. When using the cmetrics component or commands, you should consider the following information:

  • Display route metrics table
  • Delete a cmetrics entry
  • Display options
  • How cmetrics statistics are calculated
  • Potential impacts from how entries are stored and removed
  • Additional information

Display route metrics table

To display all the entries in the route metrics table, enter the following command from the BIG-IP command line:

tmsh show net cmetrics

The output appears similar to the following example:

Delete a cmetrics entry

To delete an entry of a specific destination IP address, use the following command syntax:

tmsh delete net cmetrics dest-addr <IP_Address>

For example, to delete the entry with destination IP address 10.10.1.11 from the route metrics table. enter the following command:

tmsh delete net cmetrics dest-addr 10.10.1.11

Note: You can delete only entries that have no connection references.

How cmetrics statistics are calculated

The BIG-IP system updates the cmetrics table MTU value IP by looking at incoming ICMP Fragmentation Needed (Type 3 Code 4) messages. It does not take info from the dynamic routing protocols, such as OSPF.  The MTU field in the cmetrics table for a destination is only updated through ICMP fragmentation needed (Type 3 Code 4) and ICMPv6 Packet Too Big messages received from that network device. It then caches the value in a cmetrics table. When MTU value is updated from ICMP packets, other stats are reset to zero.

The BIG-IP system also monitors different stats of a TCP connection and update other stats (rtt, rttvar, ssthresh, and bandwidth) when a TCP connection is closed. Subsequence new TCP connection from the same client refers to these states so that last channel estimates can be used in these new TCP connections.

The system uses a timer with a default value of 600 seconds for the cmetrics table. This timer restarts at the configured value when a new connection is made to the destination. You can modify this value by using the following command syntax:

tmsh modify sys db route.metrics.timeout value <number of seconds>

For example, to set the timer value to 800 seconds, enter the following command:

tmsh modify sys db route.metrics.timeout value 800

To display the current timeout value, enter the following tmsh command:

tmsh list sys db route.metrics.timeout

The output appears similar to the following example:

sys db route.metrics.timeout {
value "600"
}

In case of an increase of the path MTU for a particular destination, the metrics are updated when the timeout is reached and the particular entry is deleted from the table.

The following scenario explains the process of MTU discovery with an example:

BIG-IP 10.0.0.2/24 <----mtu 1500---> 10.0.0.1/24 Router 10.0.1.1/24 <----mtu 1450----> 10.0.1.2/24 Server

  • The BIG-IP system (10.0.0.2) sends a packet with DF (Don’t fragment ) flag enabled with size 1500 out to the server with IP 10.0.1.2.
  • The router does not forward this packet because it cannot fragment it and sends an ICMP Fragmentation Needed message (Type 3 Code 4) back to the BIG-IP system (10.0.0.1 ---> 10.0.0.2) with MTU 1450.
  • The system stores this to table cmetrics and keeps it for 600 seconds by default. During that time on the client side sends an ICMP Fragmentation Needed message (Type 3 Code 4) with MTU 1450 if the system receives a packet bigger than 1500 to instruct the client to use 1450 this as maximum IP packet size.

If the MTU path changes from 1450 to 1480:

  1. After 600 seconds of inactivity the value on the cmetrics table expires.
  2. When the BIG-IP system again sends a packet with 1500, there is an ICMP Fragmentation Needed message (Type 3 Code 4) back to the BIG-IP system (10.0.0.1 ---> 10.0.0.2) with MTU 1480
  3. The value of 1480 is added to the cmetrics table.

Potential impacts from how entries are stored and removed

When temporary reductions in path MTU occur on destinations that are in constant use, non-default MTU values may appear "stuck" in the cmetrics table.

Once an ICMP Fragmentation Needed packet is received, the BIG-IP caches the non-default MTU value for the related destination in the cmetrics table and then begins a 600 second countdown timer for the entry. This timer is reset back to 600 seconds on every connection and will count down only while no new connections are being sent to the node. When the timer reaches 0, the entry is removed from the table. Nodes that are continuously in use may rarely maintain 10 minutes with no activity. As a result, brief changes in MTU may appear "stuck" in the table and would need to be manually removed.

Additional information

  • If the BIG-IP system does not receive ICMP fragmentation needed messages, then you can only manually update the cmetrics table or at the close and teardown of a traffic TCP connection.
  • The command tmsh show net cmetric shows MTU as 0 until the first ICMP Fragmentation Needed message (ICMP Type 3 Code 4) is received. F5 Product Development has assigned ID 593292 to this issue. For more information, refer to the BugTracker article: Bug ID 593292.

Recommendations

To prevent the BIG-IP system from obtaining MTU information from route metrics, enter the following command:

tmsh modify sys db route.metrics.mtu value disable

This command is useful for routers that use NATs for multiple connections. Disabling route metrics prevents the BIG-IP system from assigning the same, or lower, MTU to all of the connections coming from the address that uses NAT, even though all of the connections through NAT can have various MTUs. The BIG-IP system can separately negotiate MTU requirements of each connection.

Note: If the system prevents ICMP messages from reaching the offending host by not forwarding ICMP Fragmentation Needed messages, client or server application failures may occur.

To disable PMTUD (that is, stop setting the Don't Fragment bit so that the system no longer receives Fragmentation Needed messages and hence stops populating the cmetrics table), enter the following command:

tmsh modify sys db tm.pathmtudiscovery value disable
