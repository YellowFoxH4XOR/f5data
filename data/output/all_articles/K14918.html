Known Issue

In rare circumstances, persistence records may become inconsistent across Traffic Management Microkernel (TMM) processes.

This issue occurs when all of the following conditions are met:

  • The system associates a persistence profile with a virtual server.
  • The system creates a persistence table record for a connection.
  • The system marks the client-persisted node down and up, in quick succession, within a 7-second window.
  • The system establishes a new connection within the 7-second window before the server is marked up again.

Impact

The system persists individual client sessions across multiple nodes, depending on which TMM processes the connection.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • TMM inconsistently processes persistence records.

Workaround

To work around this issue, you can associate an iRule with the virtual server.

Impact of workaround: iRules may increase processing overhead and require more system resources, per connection.

In the following iRules example, the system deletes persistence entries when a PERSIST_DOWN event is triggered.

when PERSIST_DOWN {
persist delete source_addr [IP::client_addr] }

For information about the PERSIST_DOWN iRules event, refer to PERSIST_DOWN on F5 Cloud Docs.
