Topic

You should consider using this procedure under the following condition:
  • You think you are receiving an HTTP POST flood attack.

Description

HTTP POST floods attempt to exhaust system resources on the target by sending a high volume of HTTP POST requests to the target server. If successful, the target server exhausts all available resources serving the malicious requests, leaving no resources remaining to serve legitimate HTTP requests, and thus denying service to legitimate consumers. HTTP POST flood traffic is often sourced from a distributed group of computers that form part of a malicious bot-net.

This article describes several mechanisms that you can consider when you need to mitigate an HTTP POST flood that has saturated either the capacity of the target web servers or the capacity of the BIG-IP system.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have BIG-IP LTM or BIG-IP Advanced WAF/ASM licensed and provisioned on your system.
  • Your ingress WAN link is not saturated. If your ingress link is saturated, blocking traffic upstream using a cloud scrubbing service such as F5 Silverline is preferable to attempting to mitigate using the BIG-IP system.

Procedures

  • Determine the nature of the attack
  • Use iRules to mitigate attacks
  • Use BIG-IP Advanced WAF/ASM layer 7 Denial of Service protection
  • Use BIG-IP Advanced WAF/ASM Universal Bot Defense / Proactive Bot Defense

Determine the nature of the attack

The first step is to try to determine the nature of the attack by inspecting the HTTP traffic and then to look for any commonality between requests that can be identified or are suspected of being malicious. Depending on the configuration already in place, you can do this using the tcpdump command (if the traffic is encrypted, you need to decrypt the traffic capture to see application traffic), using logs from the web server, or using BIG-IP Advanced WAF/ASM request logging.

For more information on using tcpdump to capture traffic, refer to the following articles:

  • K411: Overview of packet tracing with the tcpdump utility
  • K6546: Recommended methods and limitations for running tcpdump on a BIG-IP system
  • K13637: Capturing internal TMM information with tcpdump

For more information on decrypting SSL encrypted traffic, refer to the following articles:

  • K16700: Decrypting SSL traffic using the SSL::sessionsecret iRules command
  • K19310681: Decrypting SSL/TLS traffic using Wireshark and private keys

For more information on configuring BIG-IP Advanced WAF/ASM request logging, refer to the Logging Application Specific Events chapter of the BIG-IP Application Security Manager: Implementations manual.

Use iRules to mitigate attacks

You can write simple iRules designed to drop POST requests based on almost anything that can be read within the payload, either at the TCP layer using TCP::collect commands or, more simply, at the HTTP layer using the various HTTP commands. This article includes two examples for ease of reference. The first drops traffic based on the User-Agent header, and the second drops traffic based on geolocation. However, F5 recommends that you write iRules specific to your scenario and with conditions that match patterns in the traffic you identified using the techniques previously discussed.

Note: Any actions you take based on HTTP headers are often effective only for a limited amount of time before the attacker modifies their approach. Therefore, a dynamic blocking approach using BIG-IP ASM is usually the best option where available.

Drop traffic based on User-Agent headers

The following example iRule drops the request if the User-Agent header value equals mozilla/4.0. To drop traffic based on the User-Agent header, perform the following procedure:

Impact of procedure: All requests with a matching User-Agent are dropped and a log entry us created in the /var/log/ltm file. Logging all dropped requests on a production system is not recommended as the amount of logging may cause an excessive load on the BIG-IP system and result in instability; you should remove the log line after testing is complete. Since attacks often change, it is most effective to use a data group to store the patterns which you want to drop, and then compare against the data group using the class operators.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > iRules.
  3. Select Create.
  4. For Definition, enter an iRule similar to the following:

    when HTTP_REQUEST {
        if  {([string tolower [HTTP::method]] eq "post") && ( [string tolower [HTTP::header "User-Agent"]] == "mozilla/4.0") } {
            drop
            log local0. "Rejected [HTTP::method] request from [IP::remote_addr] with User-Agent [HTTP::header "User-Agent"], request for [HTTP::host][HTTP::uri]"
        }
    }

  5. Select Finished.
  6. Go to Local Traffic > Virtual Servers.
  7. Next to the virtual server under attack, select Edit.
  8. Next to iRules, select Manage.
  9. Select the name of the iRule in the Available list and move it to the Enabled list.
  10. Select Finished.

Drop traffic based on GeoLocation

The following example uses a Data Group and an iRule to drop the request if the country_code is CN or RU. To drop traffic based on geolocation, perform the following procedure:

Impact of procedure: Take care not to overwhelm the BIG-IP system with logging, and logging should be reserved for testing. The iRule shown in the previous procedure blocks on the Layer-3 IP address presented by the client, but you can instead take the same actions with some modifications in the HTTP_REQUEST event and headers, such as X-Forwarded-For or X-True-Client-IP. If BIG-IP Advanced WAF/ASM is available, it can handle geolocation enforcement more efficiently. For more information, refer to K79414542: Configuring geolocation enforcement.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > iRules > Data Group List.
  3. Select Create.
  4. Enter a name for the data group.
  5. For Type, select String.
  6. For String Records, enter the country_code for the countries you want to drop traffic, then select Add.

    For example, the following data group that contains the CN and RU country_codes:

    ltm data-group blocked_country {
     records { 
       CN {}
       RU {}
     }
     enter string
    }

  7. Select Finished.
  8. Go to Local Traffic > iRules > iRules List.
  9. Select Create.
  10. Enter a name for the iRule.
  11. For Definition, enter an iRule referencing the data group similar to the following example:

     when CLIENT_ACCEPTED { 
       if { [class match [whereis [IP::client_addr] country ] eq blocked_country]} {
          drop
          log local0.info "Blocked [IP::client_addr] from $country" 
       } 
     }

  12. Go to Local Traffic > Virtual Servers.
  13. Select the name of the virtual server to which you want to apply the iRule.
  14. Select the Resources tab.
  15. For iRules, select Manage.
  16. In the Available list, select the iRule you just created and move it to the Enabled list.
  17. Select Finished.

Use BIG-IP Advanced WAF/ASM Layer 7 Denial of Service protection

Current versions of BIG-IP Advanced WAF/ASM include advanced Denial of Service (DoS) protection mechanisms that can be configured in a wide variety of ways to effectively mitigate a GET flood. Using BIG-IP Advanced WAF/ASM to provide these protections offers significant advantages over an iRule, both from a flexibility and from a performance standpoint. For platforms that support mitigation in hardware, BIG-IP Advanced WAF/ASM can automatically add IP addresses that are consistently generating bad requests to a hardware-enforced shun list, greatly reducing the load on Traffic Management Microkernel (TMM) and the data plane.

The following procedure applies to BIG-IP 14.1.0 and later. For other versions, refer to the appropriate manual chapters for your version:

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Note: CAPTCHA challenges are not integrated into the target website but are served as an interstitial page to any attacker detected by the thresholds and, as such, do not carry any customer branding. This is a consideration if maintaining a seamless user experience in the face of a false positive detection is important. If so, you should use client-side integrity defense instead.

Impact of procedure: If an attack is already ongoing, you are unable to use any of the automatic threshold features or calculated throughput-increase values as the system learns the current traffic levels as the baseline; for immediate mitigation you must use the manual thresholds.

  1. Log in to the Configuration utility.
  2. Go to Security > DoS Protection > Protection Profiles.
  3. Select Create.
  4. Configure the profile with appropriate thresholds.
  5. Select either TPS-based Detection or Behaviorial & Stress-based Detection; on the Detection page for your preferred detection mechanism, configure the following settings:
    • Set Operation Mode to Blocking.
    • Set Thresholds Mode to Manual.
    • Set appropriate absolute TPS thresholds for the mitigation mechanism you want.

      For example, if you want to protect your application based on URL, for By URL, select Edit , set the appropriate thresholds (Relative or Absolute) for your application and select Request Blocking (Rate Limit). If the requests for URLs meet the conditions you have configured in these settings, the BIG-IP Advanced WAF/ASM prevents further attacks by limiting the number of requests per second.

  6. Select Finished.
  7. Go to Local Traffic > Virtual Servers.
  8. Select the name of the virtual server under attack.
  9. Select the Security tab and select Policies.
  10. For DoS Protection Profile, select Enabled, then for the profile setting, select the name of the new profile.
  11. Select Update.

Use BIG-IP Advanced WAF/ASM Universal Bot Defense / Proactive Bot Defense

Because high volume attacks are usually carried out by networks of automated computers (bots), BIG-IP Advanced WAF/ASM’s Universal Bot Defense (BIG-IP 14.1.0 and later) and Proactive Bot Defense (versions earlier than BIG-IP 14.1.0) are excellent mitigation options for volumetric attacks. Using BIG-IP Advanced WAF/ASM to provide these protections offers significant advantages over an iRule, both from a flexibility and from a performance standpoint. For platforms that support mitigation in hardware, BIG-IP Advanced WAF/ASM can automatically add IP addresses that are consistently generating bad requests to a hardware-enforced shun list, greatly reducing the load on TMM and the data plane.

The following procedure applies to BIG-IP 14.1.0 and later. For other versions, see the appropriate manual chapters for your version:

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Impact of Procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Security > Bot Defense > Bot Defense Profiles.
  3. Select Create.
  4. Configure the profile with appropriate thresholds.
  5. For Enforcement Mode on the General Settings page, select Blocking.
  6. Select Save.
  7. Go to Local Traffic > Virtual Servers.
  8. Select the name of the virtual server under attack.
  9. Select the Security tab and select Policies.
  10. For Bot Defense Profile, select Enabled, then for the profile setting, select the name of the new profile.
  11. Select Update.
