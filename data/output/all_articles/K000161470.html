K000161470: HTTP max header count exceeded on virtual server on certain browsers even with max-header-count increased on HTTP profile

Type
Support Solution
Published
2026-05-28
Updated
2026-05-28
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000161470

Description

BIG-IP LTM may reset connections for HTTP traffic traversing multiple virtual servers when an upstream or layer 1 virtual server enforces its own HTTP profile header limits independently of downstream virtual servers. In this scenario, Chromium-based browsers failed to access an application because the server response contained 65+ headers while the HTTP profile on the upstream virtual server used the default max-header-count of 64.

This may result in log messages like the following in /var/log/ltm:

011f0011:3: HTTP header count exceeded maximum allowed count of 64 and packet reset cause [F5RST: HTTP header count exceeded by server].

Some applications may attach more HTTP headers to packets depending on the User Agent (Browser) which can cause requests to fail when using some browsers, but not others. This behavior can be confirmed by collecting decrypted packet captures by using this procedure: Creating a decrypted tcpdump capture without using an iRule

Environment

  • BIG-IP LTM

  • HTTP traffic forwarded through multiple VIPs

  • Traffic forwarded from one virtual server to another by traffic policy or iRule

  • Upstream virtual server with HTTP profile using default (64) or lower max-header-count

Cause

The upstream virtual server will enforce the header limits configured in its attached HTTP profile independently of downstream virtual servers. The HTTP profile will retain the default max-header-count value of 64 if not modified, and if the backend server response contains 65+ headers BIG-IP will reject the response and send a TCP reset.

Answer/Recommended Actions

  • Review all virtual servers and HTTP profiles in the full traffic path when traffic is forwarded between VIPs by traffic policy or iRule.

  • Verify whether any upstream or layer 1 VIP has a lower max-header-count than required for the application response.

  • Check for these indicators during troubleshooting:

    • /var/log/ltm entries such as 011f0011:3: HTTP header count exceeded maximum allowed count of 64

    • Packet captures showing reset cause [F5RST: HTTP header count exceeded by server]

  • If needed, enable TCP reset cause tagging for troubleshooting:

    • tmsh modify /sys db tm.rstcause.pkt value enable

  • If TLS decryption is required for packet capture analysis, enable the SSL provider trailer and collect a capture:

    • tmsh modify sys db tcpdump.sslprovider value enable

    • tcpdump -s0 -nni 0.0:nnn --f5 ssl host 10.0.0.0 port 443 -vw /var/tmp/decrypt.pcap

  • Resolve the issue by using one or both of the following approaches:

    • Reduce the number of headers returned by the backend server

    • Increase max-header-count on all relevant HTTP profiles throughout the VIP chain, especially on the upstream VIP that first enforces the limit

  • Also validate whether max-header-size is appropriate for the expected traffic.

  • If browser-specific behavior is suspected, compare requests by User-Agent and log the response header count to determine whether different clients trigger different server responses. For example, attach an iRule that records User-Agent and [HTTP::header count] for the affected virtual server.

Additional Information

  • Header-limit settings are not inherited across chained virtual servers. Each virtual server processes traffic according to its own attached configuration and profiles.

  • Changing excess-server-headers handling on a downstream HTTP profile may not resolve the issue if an upstream VIP still enforces a lower header-count limit.
