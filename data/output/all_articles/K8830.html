K8830: BIG-IP active-active configuration may report address conflicts

Topic

A BIG-IP LTM system, configured as an active-active high availability (HA) pair, may report address conflicts if one unit is rebooted. This behavior can occur if the BIG-IP LTM is using hardware failover only, network failover, or a combination of both.

Note: For information regarding CR88337 in Hotfix-BIG-IP-9.3.1-HF1, which addresses the combined use of hardware and network failover, refer to K8300: Using network failover and serial cable failover with an active-active configuration may result in address conflicts.

This behavior occurs due to the amount of information required in an active-active configuration that must be communicated to each system. An active-active configuration can still function using only hardware failover, but address conflicts may occur.

In BIG-IP 9.3.1, the sod process network failover information was changed to use the Traffic Management Microkernel’s (TMM) statemirroring connection This behavior allows the information required by sod to be transmitted to either unit, even when the network failover option is not configured.

Note: Statemirroring is the configuration used to mirror state or connection information between units for connection setup, status, and tear down in the event a failover occurs. If so, the secondary unit in the HA configuration will be able to take over and handle the client communication.

When an address conflict is reported, the following message is reported to the /var/log/ltm file:

tmm tmm 01190004:4: address conflict detected for <IP Address> <MAC Address> on vlan <VLAN Number>

Common causes for this behavior include the following:

  • When poor network communication between the two systems occurs, sod uses the statemirroring configuration to send sod network failover messages and communication, even if network failover is not configured.
  • Sod started and is now attempting to move forward, but TMM has not established all of its necessary communication channels to various system daemons. This behavior can occur for large or complex configurations, in which some daemons are still parsing the configuration or are in the process of establishing communication to other daemons to provide status.

To prevent this behavior from occurring, you can adjust the Failover.TmmStartDelay bigpipe db variable to allow time for sod to establish a connection before TMM starts.

Introduced in BIG-IP version 9.3 under CR62536, Failover.TmmStartDelay provides the administrator the ability to configure sod to wait a specific amount of time after TMM has started, before determining whether to initiate failover.

The default value for Failover.TmmStartDelay is 30 seconds.

To configure sod to wait 60 seconds after TMM has started before initiating failover, type the following command from the command line:

bigpipe db Failover.TmmStartDelay 60
