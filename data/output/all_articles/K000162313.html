K000162313: Resolving CIS AS3 Declaration Failures Caused by Path-Length and Stale Node Conflicts

Type
Support Solution
Published
2026-07-17
Updated
2026-07-17
Applies to
  • F5 Automation and Orchestration
  • F5 BIG-IP Container Ingress Services
Source
https://my.f5.com/manage/s/article/K000162313

Description

F5 Container Ingress Services (CIS) can fail to apply AS3 declarations when:

  • An AS3 object path exceeds the 195-character limit.
  • A stale BIG-IP node object uses the same IP address as a current AS3 pool member.
  • A large declaration takes longer than the BIG-IP processing timeout.
  • A single declaration contains resources from multiple partitions and one resource fails validation.

Typical messages include:

unable to digest declaration. Error: Path ... is longer than 195 characters

declaration is invalid

pool member ... static address ... conflicts with bigip node ...

CIS may report HTTP 422 responses, and multiple VirtualServer resources can remain in an ERROR state until the invalid or stale configuration is removed.

Environment

  • F5 Container Ingress Services (CIS) 2.20.1.
  • BIG-IP with AS3 managing multiple partitions.
  • CIS deployed in custom-resource mode, including VirtualServer and related CRDs.
  • A large Kubernetes environment containing more than 185 namespaces.
  • Kubernetes pod IP addresses that can change when pods are restarted or recreated.
  • CIS configuration containing resources distributed across multiple BIG-IP partitions.
  • AS3 declarations submitted to the BIG-IP AS3 endpoint.
  • Optional CIS settings relevant to this issue:
    • --filter-tenants
    • --custom-resource-mode
    • --share-nodes
    • --as3-validation

Cause

The following causes were identified:

  • AS3 path-length violation: AS3 requires the combined /Tenant/Application/Object path to be no longer than 195 characters, including slashes.
  • Declaration fate sharing: When CIS submits a unified declaration, an invalid object can cause the complete declaration to be rejected. Consequently, updates for otherwise valid resources may also fail.
  • Stale BIG-IP node objects: A previous pod IP remained configured as a BIG-IP node while the same address was submitted as a pool-member address in a new AS3 declaration. AS3 rejected the declaration because of the address conflict.
  • Large declaration processing time: A CIS instance managing a large number of namespaces can generate a declaration that takes longer than the BIG-IP processing timeout.
  • Tenant-filtering scope: --filter-tenants=true is intended for AS3 ConfigMap processing. It does not provide the expected per-tenant isolation for deployments using custom-resource-based resources such as VirtualServer or TransportServer.

Answer/Recommended Actions

Resolve an AS3 path-length violation

  1. Identify the object reported in the AS3 warning.
  2. Shorten the tenant, application, or object names so the complete AS3 path is 195 characters or fewer.
  3. Resubmit the affected Kubernetes resource.
  4. Confirm that CIS receives a successful AS3 response and that the related resources leave the ERROR state.

The limit cannot be disabled through CIS configuration.

Resolve stale node and pool-member conflicts

Complete the following steps during a controlled maintenance period:

 

  1. Back up the BIG-IP configuration on both HA nodes:

tmsh save sys ucs /var/tmp/<backup-name>

 

  1. Export the current AS3 declaration for reference:

curl -sk -u admin:<password> \

https://<bigip-management-address>/mgmt/shared/appsvcs/declare

 

  1. Check for manually created objects in the partitions managed by CIS. Back up or document any objects that CIS does not own, because deleting AS3 declarations may remove AS3-managed configuration and will not recreate manually managed objects.
  2. Stop the CIS deployment before removing stale AS3 configuration:

kubectl scale deployment f5-cis -n f5-cis --replicas=0

 

  1. Delete the affected AS3 declaration or tenant declaration from BIG-IP. If deleting the complete declaration, use the AS3 declaration endpoint:

curl -sk -u admin:<password> \

-X DELETE \

https://<bigip-management-address>/mgmt/shared/appsvcs/declare

A tenant-specific deletion may be used when a narrower cleanup is required:

curl -sk -u admin:<password> \

-X DELETE \

https://<bigip-management-address>/mgmt/shared/appsvcs/declare/<tenant>

 

  1. Verify that obsolete BIG-IP node objects have been removed from the affected partitions:

tmsh list ltm node partition <partition>

 

  1. If stale nodes remain, remove only the confirmed obsolete node objects and save the configuration:

tmsh delete ltm node /<partition>/<node-name>

tmsh save sys config

 

  1. Configure CIS with shared nodes where appropriate:

--share-nodes=true

This places shared node objects in /Common and helps prevent duplicate node definitions across partitions.

 

  1. Restart CIS:

kubectl scale deployment f5-cis -n f5-cis --replicas=1

 

  1. Monitor CIS logs and verify successful AS3 processing:

kubectl logs -n f5-cis -f deployment/f5-cis

 

  1. Confirm that VirtualServer resources no longer report ERROR:

kubectl get virtualserver --all-namespaces

Reduce declaration size and cross-partition impact

  • Divide namespaces across multiple CIS instances.
  • Scope each CIS instance to an appropriate namespace or namespace group.
  • Assign each CIS instance only the BIG-IP partition or partitions it is intended to manage.
  • Avoid using a single CIS instance to generate one very large declaration for the entire Kubernetes cluster.
  • For AS3 ConfigMap deployments, enable tenant filtering where supported:

--filter-tenants=true

  • Do not rely on --filter-tenants=true to isolate VirtualServer, TransportServer, or other custom-resource-based declarations.

Validate the --as3-validation setting

  • --as3-validation=true causes CIS to validate an AS3 declaration before deploying it to BIG-IP.
  • The setting defaults to true when it is not specified.
  • Disabling validation does not resolve an AS3 declaration that BIG-IP itself rejects because of a path-length violation, duplicate node, or other declaration conflict.

Investigate large-declaration timeout symptoms

If CIS reports an HTML response or an AS3 response parsing error such as:

Response body unmarshal failed: invalid character '<' looking for beginning of value

collect the CIS and BIG-IP REST/AS3 logs around the failure and review the declaration size and processing duration. Splitting the CIS workload into smaller instances is the recommended long-term approach. Increasing BIG-IP timeout values may reduce timeout frequency but does not correct invalid declarations or stale configuration.

Additional Information

  • A single invalid object in a unified AS3 declaration can prevent other updates in that declaration from being accepted.
  • Removing stale AS3 configuration and allowing CIS to repopulate the current Kubernetes state can restore synchronization.
  • Before deleting AS3 declarations, verify whether manually created BIG-IP objects exist in CIS-managed partitions.
  • A successful CIS restart does not by itself prove that all resources have recovered; verify AS3 responses and Kubernetes resource status.
  • If GTM or ExternalDNS resources reference LTM virtual servers managed by another CIS instance, ensure that the referenced virtual server exists and is visible to the CIS instance managing the GTM resource.
