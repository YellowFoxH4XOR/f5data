Topic

F5 iWorkflow clusters are a mesh of three fully active iWorkflow peer virtual machines. The iWorkflow cluster helps to prevent administrative access outages and data loss by providing fault tolerance within the cluster.

You should consider using this procedure under the following conditions:

  • You want to migrate from a standalone iWorkflow instance to a cluster.
  • You are upgrading an existing iWorkflow cluster.
  • You intend to restore a UCS archive to an existing iWorkflow cluster.

Description

iWorkflow clusters are a collection of three nodes. The cluster uses an eventual consistency model when replicating configuration updates from the lead peer virtual sever to the sibling peers in the cluster. Select one of the cluster nodes as the lead peer. Then continue to use this lead peer for all interactions, unless it becomes unavailable or is inconvenient. Select different iWorkflow cluster members as the lead as long as you are not working on the same resources on different peers.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • Have administrative rights to the iWorkflow peers
  • Manage more than one iWorkflow instance
  • Have created a recent UCS archive and stored it on a remote secure storage server
  • Confirmed that all managed devices are healthy
  • Confirmed that the iWorkflow instance and any existing cluster members are healthy
  • Are familiar with the vi text editor

Procedures

You can manage the iWorkflow clusters using the following procedures:

  • Creating an iWorkflow cluster
  • Breaking an iWorkflow cluster

Creating an iWorkflow cluster

You can create a cluster from any iWorkflow instance; however, ensure that the peers that join the cluster are clean builds. You cannot import existing configurations from an existing iWorkflow instance. You can create an iWorkflow cluster using either the iWorkflow user interface, or the command line with the iControl REST requests.

Using the iWorkflow administrative user interface

Impact of procedure: When a peer joins the cluster, all existing data stored on the iWorkflow node is lost. Only the configuration information stored on the lead or initiating iWorkflow instance remains.

  1. Log in to the iWorkflow administrative user interface with your administrator username and password.

    For example:

    https://192.168.5.21/ui/login

  2. From the top navigation menu, select the System module.
  3. Click the + icon located in the iWorkflow Cluster header.
  4. In the New iWorkflow Cluster Member panel that opens, type the peer IP address, Admin username, and Admin password.
  5. Acknowledge the warning message that indicates that the system will overwrite data on the peer.
  6. Repeat steps 3 through 5 for the third iWorkflow member in the cluster.

Using iControl REST

You can create the iWorkflow cluster using REST requests and a simple JSON payload (text file), detailing the cluster member to add. The cluster member that receives the request to add another member is treated as the cluster leader. The configuration from the leader will be replicated to the new peer.

Following is an example of the JSON file: 

{
    "address": "10.10.99.6",
    "userName": "admin",
    "password": "admin",
    "properties": {
        "highAvailabilityMode": "active-active"
    }
}

The content of the JSON file defines the following objects:

  • The cluster peer management IP address is 10.10.99.6.
  • The administrative user name is admin.
  • The administrative user's password is admin.
  • The properties attribute "highAvailablityMode" is set to "active-active"; iWorkflow clusters are always configured as an Active/Active cluster and under normal circumstances should contain three members.

    Note: iWorkflow reports the cluster size as unsupported once the first peer is added, until there are three members defined.

Impact of procedure: F5 recommends that you use the cluster leader when you add more peer members to the cluster. The cluster leader is the node that you primarily use for administrative functions, and it should have the latest updates. When a peer joins the cluster, all existing data stored on that iWorkflow node is lost, as it is replaced with the data stored on the cluster leader.

  1. Log in to the iWorkflow command line.
  2. To change directories to the /var/tmp directory, type the following command:

    cd /var/tmp

  3. Use a text editor to create a text file called new_cluster_member.json.

    For example:

    vi new_cluster_member.json

  4. Add the previously provided syntax, using the iWorkflow management IP address, administrative username, and password values to reflect your environment.

    Note: Alternatively, you can create the JSON file externally, and use scp to copy the file to your iWorkflow host. 

  5. Use the cURL utility to add the new iWorkflow peer to the cluster by typing the following command syntax:

    curl -k -s -u <ADMIN_USER>:<ADMINS_PASSWORD> -X POST -d@<JSON_FILE>  https://<CLUSTER_LEADER>/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices

    For example:

    curl -k -s -u admin:admin -X POST -d@new_cluster_member.json https://localhost/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices

    Note: Because you are logged in to the iWorkflow instance, which should be the cluster leader, you can direct the cURL commands to localhost. You can run this command from another host, assuming you have network connectivity between both devices, by replacing the <CLUSTER_LEADER> syntax with the iWorkflow device leader's IP address or network resolvable name.

  6. The iWorkflow system should return details related to the newly added cluster peer. Review the response, and if there are issues with adding the peer, such as clock skew, the issues will also be returned in the REST call response, and the cluster join may fail.

    Note: The output indicates a state of PENDING during the discovery process, and the state changes to ACTIVE after the cluster update is complete.

    An example of the output may appear similar to the following:

    {"uuid":"9dba5ac3-ad27-4392-9456-e8a536bf771c","deviceUri":"https://10.10.99.6:443","machineId":"9dba5ac3-ad27-4392-9456-e8a536bf771c","state":"PENDING","address":"10.10.99.6","httpsPort":443,"groupName":"cm-f5-orchestration-peers","generation":6,"lastUpdateMicros":1474320708906529,"kind":"shared:resolver:device-groups:restdeviceresolverdevicestate","selfLink":"https://localhost/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices/9dba5ac3-ad27-4392-9456-e8a536bf771c"}

    Important: If the command in step 5 does not produce any output, then something did not go as expected. Ensure that the file referenced in your cURL command is valid and readable by the user who is running the command, and also confirm that the URL is valid.

    Take note of the UUID value in the output from the previous command, as we will use this information to confirm that the peer has been added, and that the state has changed to ACTIVE.

  7. Use the following cURL command to confirm the peer status. We will reference the uuid value found in the previous command.  The output can be piped through the json-format utility for improved reading, using the following command syntax:

    curl -k -s -u <ADMIN_USER>:<ADMINS_PASSWORD> https://<CLUSTER_LEADER>/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices/<UUID> | json-format

    For example:

    curl -k -s -u admin:admin https://localhost/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices/9dba5ac3-ad27-4392-9456-e8a536bf771c | json-format

    The output from the command may appear as follows:

    {"uuid": "9dba5ac3-ad27-4392-9456-e8a536bf771c",
      "deviceUri": "https://10.10.99.6:443",
      "machineId": "9dba5ac3-ad27-4392-9456-e8a536bf771c",
      "state": "ACTIVE",
      "address": "10.10.99.6",
      "httpsPort": 443,
      "hostname": "iwf-2.gnet.local",
      "version": "2.0.0",
      "product": "iWorkflow",
      "edition": "Final",
      "build": "0.0.9631",
      "restFrameworkVersion": "13.0.0-0.0.5136",
      "managementAddress": "10.10.99.6",
      "mcpDeviceName": "/Common/localhost",
      "properties": {
        "shared:resolver:device-groups:discoverer": "7345e107-d4f8-43a7-b3f6-22f44d11b2c8"
      },
      "isClustered": false,
      "isVirtual": true,
      "groupName": "cm-f5-orchestration-peers",
      "generation": 8,
      "lastUpdateMicros": 1474320712556808,
      "kind": "shared:resolver:device-groups:restdeviceresolverdevicestate",
      "selfLink": "https://localhost/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices/9dba5ac3-ad27-4392-9456-e8a536bf771c"
    }

  8. Inspect the following output entries so you know if the iWorkflow peer device has been successfully added to the cluster:
     
    • groupName : cm-f5-orchestration-peers

      The example output shows that the iWorkflow peer device 10.10.99.6 has been successfully added to the cluster. 

  9. To add the other iWorkflow device to the cluster, repeat steps 3 to 7.

Breaking an iWorkflow cluster

When you break the iWorkflow cluster, peers that are removed will be returned to a default state, and all configuration, with the exception of management IP details and licensing, will be removed.  To break the iWorkflow cluster, complete one of the following processes.

Using iWorkflow administrative user interface

Impact of procedure: The system will lose data stored on the peer that is evicted from the cluster.

  1. Log in to the iWorkflow administrative user interface with your administrator username and password.

    For example:

    https://192.168.5.21/ui/login

  2. From the top navigation menu, select the System module.
  3. Under the iWorkflow cluster panel, double click the peer you wish to remove.

    Note: localhost is the iWorkflow instance that you are directly logged in to.

  4. For the peer you wish to evict from the cluster, click remove in the properties panel.
  5. Repeat step 2 through 4 for each peer that you want to evict.

    Note: Once the first peer is removed, iWorkflow will report the cluster size as unsupported, until the leader is a standalone instance.

Using iControl REST

When you remove iWorkflow cluster members, it is important to consider the background processes that are always ongoing. You can remove an iWorkflow cluster member using the DELETE HTTP method, but this may not take into account the cluster communication, and could lead to inconsistencies. F5 recommends that you use the ha-peer-remover API to break the cluster or remove individual cluster members. When you send a request to remove a member from the cluster, you make the cluster member that is receiving the request the lead peer. The local copy of the peer that is to be removed is marked as PENDING_DELETE, and the system terminates communication to the peer. This prevents you from assigning ownership of any objects to the peer that the system is removing.

The following is a sample JSON text file:

{
    "command": DELETE_PEER,
    "peerReference": {
        "link": "https://localhost/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices/9dba5ac3-ad27-4392-9456-e8a536bf771c"
        }
}

The text file defines the command to delete the peer, and includes the self link for the peer that the system will remove. The self link value is provided in the output from a REST call to the device's collection. Alternatively, you can define an explicit uuid to restrict the output to just the peer in question.  

The following command example returns all peers in the iWorkflow cluster leader, and uses json-format to clean up the output, making it easier to read:

curl -k -s -u <ADMIN-USER>:<ADMIN-PASSWORD> https://<CLUSTER_LEADER>/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices | json-format

For example:

curl -k -s -u admin:admin https://localhost/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices | json-format

Note: Because you are logged in to the iWorkflow instance, you can direct the cURL commands to localhost. However, you can run this command from another host, assuming there is network connectivity between both devices. To do this, you would replace <CLUSTER_LEADER> with the iWorkflow system's IP address or network resolvable name.

Impact of procedure: Data stored on the peer that is evicted from the cluster will be lost.

  1. Log in to the iWorkflow command line.
  2. To change directories to the /var/tmp directory, type the following command:

    cd /var/tmp

  3. Use a text editor such as vi to create a text file called remove_cluster_member.json.

    For example:

    vi remove_cluster_member.json

  4. Add the previously provided syntax, but update the link value to reflect the peer you want to remove.

    Note: Alternatively you can create the JSON file externally and then use the scp utility to copy the file to your iWorkflow host. 

  5. To remove, from the cluster, the iWorkflow peer that is defined in the JSON file, use the following command syntax using the cURL utility:

    curl -k -s -u <ADMIN-USER>:<ADMINS-PASSWORD> -X POST -d@<JSON_FILE> https://<CLUSTER_LEADER>/mgmt/cm/shared/ha-peer-remover

    For example:

    curl -k -s -u admin:admin -X POST -d@remove_iwf_cluster_member.json https://localhost/mgmt/cm/shared/ha-peer-remover

  6. The iWorkflow system should return details related to the command in step 5.

    For example:

    {    "command": DELETE_PEER,    "peerReference": {        "link": "https://localhost/mgmt/shared/resolver/device-groups/cm-f5-orchestration-peers/devices/9dba5ac3-ad27-4392-9456-e8a536bf771c"        }}

    Important: If the command in step 5 does not produce any output, then something did not go as expected. Ensure that the file referenced in your cURL command is valid and readable by the user who is running the command.

  7. You can repeat steps 4 through 6 for each peer that you want to evict from the cluster. If you are upgrading iWorkflow or restoring iWorkflow from a UCS archive, return to those procedures now.

    Note: Once the first peer is removed, iWorkflow will report the cluster size as unsupported, until the leader is a standalone instance.
