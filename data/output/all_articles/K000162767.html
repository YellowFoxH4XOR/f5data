K000162767: SNMP GETNEXT requests  may cause SNMP to be unresponsive  for 2 minutes.

Description

SNMP GETNEXT requests  may cause SNMP to be unresponsive  for 2 minutes.

Environment

  • F5OS-A
  • rSeries appliance
  • SNMP

Cause

ID 2397765

Answer/Recommended Actions

The issue is associated with the GETNEXT processing path for the platform statistics callpoint.

When an SNMP  GETNEXT is sent to F5OS-A device, it can cause SNMP to be completely unresponsive for 2 minutes for all SNMP requests. 

When an SNMP request requires MIB traversal, F5OS-A dispatches the request to the platform statistics handler named 'SnmpCpuStatsHandler'.

If the handler or its internal data path does not respond correctly, the request can remain blocked until the ConfD worker socket timeout of 2 minutes expires.

After  two minutes is passed then , SNMP will log below error - 

"Error in packet. Reason: (genErr) A general failure occurred"

And after this 2 minute timeout and error logs, everything will come to normal but same state can re-appear if  another packet of SNMP GET NEXT is received.

Workaround:

Configure the monitoring system to issue direct SNMP GET requests for known, supported F5OS-A OIDs.

Do not begin an SNMP walk from an unsupported OID. GETNEXT and GETBULK traverse to the next lexicographically ordered OID, which can cause a request beginning in an unrelated or unsupported MIB subtree to enter the platform-statistics tables.

If the issue occurs, avoid repeatedly sending additional GETNEXT or GETBULK requests during the approximately two-minute stall. Allow the request timeout to complete and verify that SNMP processing has recovered and then stop further GETNEXT or GETBULK request.
