In this example showing a HTTP monitor probe, a GET request was issued from the BIG-IP using self IP 192.168.4.10.
The server at 172.16.23.55 began to return a large response. The BIG-IP acknowledged part of the response, then issued a reset with the cause RST from BIG-IP internal Linux host.
Subsequent ACKs from the server were reset with the cause No flow found for ACK.

Environment

  • TCP
  • Health monitors
  • Packet trace

Cause

This is expected behaviour. The reason is that bigd closes its socket for the connection once the expected receive string has been identified in the application data. This is done for performance reasons since there is little point in bigd waiting around for the remainder of a response that it will not use. A reset occurs in this scenario if the kernel still has data buffered that hasn't yet been delivered to the application layer when the socket is closed. This is more likely to occur if the HTTP response from the server is moderately large and the receive string appears early in the payload.
The data that arrives after the initial reset is correctly reset with No flow found for ACK, since there is no longer a connection for it to be matched with.

Note: There are other scenarios where RST from BIG-IP internal Linux host may be seen; this reset cause is not exclusively associated with health monitors.

Recommended Actions

This is safe to ignore if there is no issue with health monitors being marked down unexpectedly.

If health monitors have unexpected results, further troubleshooting may be required:

  • K12531: Troubleshooting health monitors

Additional Information

Be aware that bigd only reads 5120 bytes into HTTP response data when searching for a receive string:

  • K3451: Content length limits for HTTP and HTTPS health monitors
