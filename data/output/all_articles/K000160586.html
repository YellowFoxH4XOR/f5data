K000160586: Understanding "HTTP Protocol Compliance Failed: Bad Multipart Parameters Parsing" Blocking Behavior in BIG-IP ASM

Type
Support Solution
Published
2026-04-02
Updated
2026-04-02
Applies to
  • BIG-IP
  • BIG-IP ASM: 17.1.3
Source
https://my.f5.com/manage/s/article/K000160586

Description

HTTP requests are blocked by BIG-IP ASM with the violation "HTTP protocol compliance failed: Bad multipart parameters parsing," even though this specific subviolation is not enabled for blocking in the ASM policy. The event log shows "Block/Alarm/Learn" for this violation when the policy configuration is set to "Learn" only.

Error/Log Messages:

  • "HTTP protocol compliance failed: Bad multipart parameters parsing"
  • Event log "Applied Blocking Settings: Block Alarm Learn"

Environment

  • Product: BIG-IP ASM
  • Version: 17.1.3 (also observed in v17.5.1.3)
  • Violation: "HTTP protocol compliance failed: Bad multipart parameters parsing"
  • Policy settings: Subviolation set to "Learn" only, not "Block"
  • Other related violations (e.g., "Unparsable request content") may be enabled for blocking

Cause

The "Applied Blocking Settings" field in the event log reflects the effective enforcement mode for the entire request after evaluating all detected violations. If any violation within the request is configured to block and triggers enforcement, the final state (Block/Alarm/Learn) is applied at the request level and displayed across all subviolations of the "HTTP protocol compliance failed" category in the event details, even for those subviolations that are set to "Learn" only. This is by design.

Answer/Recommended Actions

  • Understand that the event log's "Applied Blocking Settings" reflects the overall enforcement action for the request, not the individual enforcement setting for each subviolation.
  • If a different violation (such as "Unparsable request content") is enabled for blocking and is triggered, the request will be blocked, and the event log will show "Block/Alarm/Learn" for all related subviolations, including those set to "Learn" only.
  • To avoid confusion in reporting, you can deselect "Learn" for subviolations that are not enabled, so they do not appear in the event log.
  • No action is required if the blocking behavior is as intended based on other enabled violations.
  • If you require more granular reporting, adjust the policy settings to match your monitoring and enforcement requirements.

Additional Information

  • This behavior is expected and by design in BIG-IP ASM. The event log aggregates the enforcement result at the request level, not per individual subviolation.
  • Disabling "Learn" for subviolations that are not enabled will prevent them from appearing in the event log, reducing confusion.
