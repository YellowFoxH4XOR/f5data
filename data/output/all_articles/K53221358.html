Description

X-Forwarded-Client-Cert (XFCC) is a proxy header that dynamically adds the certificate information of the client in a request that has flowed through on its way from the client to the server. This can be useful for authentication of clients in requests that are routed through, adding a layer of security. The sidecars are responsible for adding the headers while the request hops through them and the gateway deployed in the mesh has the ability to choose to either forward, modify or not to send the header at all based on the mode it is deployed in. Refer to the Configuring XFCC Headers section of the Aspen Mesh Operation Guide for the various modes.

Environment

  • Kubernetes: 1.17x,1.18.x,1.19.x,1.20.x 
  • Aspen Mesh: 1.6.x, 1.9.x 

Cause

None

Recommended Actions

Your XFCC configuration is applied once the connection is trusted. The default behavior for sidecar proxy is APPEND_FORWARD that is, adding the client certificate to the XFCC header before sending it to the next hop. There is no option to override or control this behavior. 

To change the default behavior of the XFCC header for the ingress gateway, you would need to add the following to your override file (overrides.yaml) and then upgrade istiod via helm.

meshConfig:
  defaultConfig:
    gatewayTopology:
      forwardClientCertDetails: <VALUE>

<VALUE>Description
UNDEFINEDField is not set.
SANITIZEDo not send the XFCC header to the next hop. This is the default value for a gateway.
FORWARD_ONLYWhen the client connection is mTLS (Mutual TLS), forward the XFCC header in the request.
APPEND_FORWARDWhen the client connection is mTLS, append the client certificate information to the request’s XFCC header and forward it.
SANITIZE_SETWhen the client connection is mTLS, reset the XFCC header with the client certificate information and send it to the next hop.
ALWAYS_FORWARD_ONLYAlways forward the XFCC header in the request, regardless of whether the client connection is mTLS.

After you have upgraded istiod via helm, you would need to restart the istio-ingressgateway in the istio-system namespace for it to load the new configuration. After the ingress gateways are restarted, you can check the configuration of the gateway using the istioctl command:

istioctl pc listeners <ingress-gateway>.istio-system -o json | grep forwardClientCertDetails

Use Curl to test your XFCC configuration

In the subsequent test, you run a curl command from your local machine to try to hit the httpbin pod which is inside the service mesh. This is an mTLS connection and you are required to add the certificate details in your request for the client for the connection to work, that is, it is a trusted connection. You add a custom XFCC header on the request itself and it goes through the ingress gateway which will then route it to the httpbin pod. The XFCC header value is a comma “,” separated string of XFCC elements. There are 2 hops that happens during the request.
  • First hop: Client to gateway
  • Second hop: Gateway to httpbin pod
Run the following curl request from your local machine, using the appropriate domain name:

curl -v -H "x-forwarded-client-cert:Hash=blablabla;CN=example.com" -H Host:httpbin.example.com --resolve "httpbin.example.com:$SECURE_INGRESS_PORT:$INGRESS_HOST" \
--cacert example.com.crt --cert client.example.com.crt --key client.example.com.key \
https://httpbin.example.com/get

INGRESS_HOST: External IP of the Ingress Gateway
SECURE_INGRESS_PORT: Port on which HTTPS connection is listening.

Additional Information

The following discusses the 3 modes of proxy operation:

Note: In some of the examples you may see the hash values are different for the same service account as this is due to the 24hr TTL of the certificates used.
  • SANITIZE_SET: When the client connection is mTLS, reset the XFCC header with the client certificate information and send it to the next hop.

In this case you can see the XFCC header that was on the curl request has been stripped and the client certificate is only passed through for the first hop. After the comma "," character, for the second hop, you can see the following:

  • the “By” key is filled with the SAN (Subject Alternative Name) of the proxy cert of the httpbin pod:
    spiffe://cluster.local/ns/default/sa/httpbin 
  • the “URI” key filled with client cert which is the ingress gateway in this case
    piffe://cluster.local/ns/istio-system/sa/istio-ingressgateway-service-account.
