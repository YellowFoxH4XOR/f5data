Topic

You can use role-based access control (RBAC) policies to grant the BIG-IP Controller granular and scoped permissions to Kubernetes resources. You do this by creating a Role or ClusterRole to define permissions and a RoleBinding or ClusterRoleBinding to grant permissions to a ServiceAccount. You then reference the BIG-IP Controller deployment with the ServiceAccount.

Description

RBAC is an authorization method enabled by default from Kubernetes 1.6.0. You can use RBAC to define the permissions and access to Kubernetes resources based on the roles of subjects (users). RBAC authorization policies are dynamically configured through the Kubernetes API.

Roles and ClusterRoles

You can use Roles or ClusterRoles to define actions, often called verbs, through which the BIG-IP Controller permits access to Kubernetes resources. Roles define access to a single namespace while ClusterRoles define access to any namespace in the Kubernetes cluster. The following table shows the supported permissions set.

Note: You can only define access or permission to cluster-scoped resources like nodes through a ClusterRole.

For example, you can define the following permissions for the BIG-IP Controller in the namespace my-namespace:

  • get, list, watch permissions to services and ingresses
  • get, list, watch, update, create, and patch permissions to configmaps
  • get, list, and watch permissions to a secret named secret-containing-bigip-login

To do so, you configure a Role similar to the following example:

kind: Role
apiVersion: rbac.authorization.k8s.io/v1
metadata: 
  namespace: my-namespace
  name: bigip-ctlr-role
rules: 
- apiGroups: ["", "extensions"] 
  resources: ["nodes", "services", "endpoints", "namespaces", "ingresses", "pods"] 
  verbs: ["get", "list", "watch"] 
- apiGroups: ["", "extensions"] 
  resources: ["configmaps"] 
  verbs: ["get", "list", "watch", "update", "create", "patch"] 
- apiGroups: ["", "extensions"] 
  resources: ["secrets"] 
  resourceNames: ["secret-containing-bigip-login"] 
  verbs: ["get", "list", "watch"] 

If you intend to define the same permissions across all namespaces, you can omit the namespace field and use a ClusterRole in as in the following example:

kind: ClusterRole
apiVersion: rbac.authorization.k8s.io/v1
metadata: 
  name: bigip-ctlr-clusterrole
rules: 
- apiGroups: ["", "extensions"] 
  resources: ["nodes", "services", "endpoints", "namespaces", "ingresses", "pods"] 
  verbs: ["get", "list", "watch"] 
- apiGroups: ["", "extensions"] 
  resources: ["configmaps"] 
  verbs: ["get", "list", "watch", "update", "create", "patch"] 
- apiGroups: ["", "extensions"] 
  resources: ["secrets"] 
  resourceNames: ["<secret-containing-bigip-login>"] 
  verbs: ["get", "list", "watch"] 

For more information on customizing RBAC rules, refer to Using RBAC Authorization

RoleBinding and ClusterRoleBinding

You can configure a RoleBinding and ClusterRoleBinding to map a Role or a ClusterRole to the ServiceAccount that the BIG-IP Controller references. When you grant permissions to the ServiceAccount, the BIG-IP Controller can effectively access the resources.

RoleBinding grants permissions within a namespace while ClusterRoleBinding grants permissions across all namespaces.

For example, to grant permissions defined in ClusterRole named bigip-ctlr-clusterrole to the a ServiceAccount named big-ctlr, which is referenced in the BIG-IP controller, you can configure a ClusterRoleBinding similar to the following:

kind: ClusterRoleBinding
apiVersion: rbac.authorization.k8s.io/v1
metadata: 
  name: bigip-ctlr-clusterrole-binding
  namespace: <controller_namespace> 
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: bigip-ctlr-clusterrole
subjects:  
- apiGroup: rbac.authorization.k8s.io   
  kind: ServiceAccount
  name: bigip-ctlr
  namespace: <controller_namespace>

For an example of RBAC configuration for BIG-IP Controller using the broader set of permissions, refer to Set up RBAC Authentication.

Recommendations

RBAC permissions are purely additive (there are no deny rules); therefore, F5 recommends that you restrict the permissions only to resources needed for your specific deployment.
