K000150387: Configuring serial console logging to a file for a BIG-IP tenant on F5OS-A rSeries platforms

Description

It can be beneficial to collect serial console output continuously from a BIG-IP system to troubleshoot intermittent issues where little diagnostic data is available, for example, a silent reboot.

This is accomplished with vCMP guests by following K68404255, writing the output to a file for later review.

While tenant serial console can be accessed on F5OS following K33373310, there is currently no feature similar to K68404255 for redirecting the output to a file.

A workaround is available that utilizes tmux.

Environment

  • F5OS-A
  • Tenant console logging

Cause

A requirement to collect serial console logging to a file for later review.

Recommended Actions

To configure serial console logging for a BIG-IP tenant on F5OS-A, follow these steps.

Note: The commands below assume a tenant name of tenant01 and a default, unmodified tmux configuration. Adjust accordingly for your environment.

  1. While logged in as root at the bash shell, create a tmux session:

    tmux new -s tenant01_console

  2. Within the first tmux window (0), run virtctl to console to the tenant and redirect the output to a file:

    tmux send-keys -t tenant01_console "virtctl console tenant01-1 &>/root/tenant01_console.log" C-m

    The bash prompt will not return.

  3. Detach from the tmux session and verify that the file is being written to:

    ctrl-b + d
    cat /root/tenant01_console.log

    Output will show a login prompt in most cases. Console output is now being collected.

Please note that the console logging will not survive reboots or upgrades. Similarly, if virtctl console is used separately, the console logging in the tmux session will be terminated.

In the event of a need to review the console output, kill the tmux session and gather the tenant01_console.log file:

tmux kill-session -t tenant01_console

Additional Information

Console output may be collected to assist in diagnosing unexpected or unexplainable events, for example silent reboot or suspected kernel panic.
