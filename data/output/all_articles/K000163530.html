K000163530: BIG-IP Management CAC/PIV Authentication: Full-Chain OCSP Validation Requires Responder Support for Intermediate CAs

Type
Support Solution
Published
2026-10-03
Updated
2026-10-03
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000163530

Description

BIG-IP management-plane HTTPD performs OCSP validation for the client certificate and each non-self-signed intermediate CA in the submitted CAC/PIV certificate chain. Authentication can fail when the OCSP responder validates the leaf certificate but cannot answer requests for one or more intermediate CAs.

Typical errors include:

AH01925: failed to verify the OCSP response OCSP_basic_verify:root ca not trusted

AH02039: Certificate Verification: Error (50): application verification failure

An OCSP response of unauthorized (6) can occur when the responder does not service the certificate identified in the request.

Environment

  • Product: BIG-IP management-plane HTTPD.
  • Authentication method: auth cert-ldap.
  • Authentication use case: CAC/PIV certificate authentication for the management GUI and CLI.
  • Client certificate chain:
    • Client leaf certificate.
    • One or more intermediate CA certificates.
    • Self-signed root CA.
  • OCSP validation enabled for the management client certificate.

Cause

BIG-IP management HTTPD performs full-chain OCSP validation by design. It checks the leaf certificate and each intermediate CA certificate in the submitted chain; the self-signed root CA is excluded.

A successful OCSP response for the leaf certificate does not prove that all intermediate CA certificates will pass validation. If the OCSP responder cannot provide status responses for the intermediate certificates, authentication fails even when the leaf certificate has a good revocation status.

An OCSP request containing an intermediate CA serial number is not necessarily evidence that BIG-IP selected the wrong client certificate. It may represent a separate OCSP check for that intermediate certificate.

Recommended Actions

  1. Review all OCSP requests in the transaction.
    • Use a packet capture to identify the OCSP CertID values, including the issuer name hash, issuer key hash, and serial number.
  2. Associate each CertID with the correct certificate.
    • Evaluate each request using the certificate’s direct issuer:
    • Client leaf certificate → immediate issuing CA.
    • Intermediate CA certificate → the CA that directly issued that intermediate.
    • Self-signed root CA → not checked through OCSP.
  3. Confirm responder coverage for the complete chain.
    • The OCSP infrastructure must answer for the client leaf certificate and every non-self-signed intermediate CA certificate in the submitted chain.
  4. Validate the BIG-IP trust configuration.
    • Confirm that the management HTTPD trust configuration contains the CA certificates required to validate both the client certificate chain and the OCSP response-signing chain. The management HTTPD trust configuration and the auth cert-ldap trust configuration are separate contexts and should not be assumed to serve the same purpose.
  5. Use a product fix for leaf-only OCSP checking when required.
    • The management-plane HTTPD implementation described here does not provide a supported configuration option equivalent to Apache’s leaf-only OCSP mode. No auth cert-ldap certificate parameter forces management HTTPD to check only the client leaf certificate.
  6. Evaluate the security implications.
    • Leaf-only checking prevents BIG-IP from checking the revocation status of intermediate CA certificates. This behavior should be evaluated against the organization’s certificate-policy requirements.
  7. Ensure the OCSP responder supports all required certificates.
    • If changing the certificate architecture is not feasible, a product fix that provides supported leaf-only OCSP checking is required.

Additional Information

  • The configured certificate verification depth does not change full-chain OCSP behavior to leaf-only validation.
  • An OCSP signing certificate embedded in the response still requires a trusted responder CA chain.
  • Multiple OCSP requests may be generated for a single client authentication attempt.
  • The serial number and issuer hashes in each OCSP CertID must be compared with the certificate and its direct issuer before determining whether the request is incorrect.
  • A fix is required to provide leaf-only OCSP validation where the responder cannot answer for intermediate CA certificates.
