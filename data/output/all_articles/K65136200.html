Topic

One of the key functions of a Public Key Infrastructure (PKI) is certificate lifecycle management. In a typical Certificate Authority (CA) setup, you can implement this function using one of the following methods:

  • A Certificate Revocation List (CRL): A CA periodically publishes a list of certificates that have been revoked.
  • Online Certificate Status Protocol (OCSP) service: A CA’s OCSP responder receives a request to check the status of a certificate and returns a digitally signed response containing the status (good, revoked or unknown) of the certificate.
  • OCSP stapling: A web server caches the OCSP response from the CA’s OCSP responder and sends it together with its certificate to a client web browser when the client initiates a TLS handshake.

Description

When F5 SSL Orchestrator acts as an SSL proxy between a client and a server, it uses the certificate from the server to forge a unique server certificate to send to the client. Since SSL Orchestrator signs the unique server certificate as a private CA, the client expects it to respond to OCSP requests.

SSL Orchestrator currently responds with OCSP stapled messages when it sends the forged server certificate to clients that include the Certificate Status Request extension in their SSL ClientHello handshake. Although OCSP stapling is the preferred approach adopted by most modern browsers, it is possible that some clients, for example clients with smart card certificate revocation checking, may need to verify the forged server certificate status through an out-of-band OCSP responder directly. 

Starting in SSL Orchestrator 16.1.0-9.0, you can include a local OCSP responder. When you configure a local OCSP responder, SSL Orchestrator sets up a new virtual server to process OCSP requests from the clients and associates an OCSP profile (located on the Local Traffic > Profiles > Services > OCSP page) to the virtual server. The OCSP profile performs the following functions:

  • Checks if the certificate serial number from the client’s OCSP request exists in the local forged certificate cache.
  • If it exists, extracts and returns it to the client with the Nonce extension, if enabled.

    Note: The Nonce setting is enabled by default. Enabling the Nonce setting allows the local OCSP responder virtual server to include the client’s nonce in its response so that the client can validate if the latest response is from the OCSP server or an old copy from a replay attack. Typically, an OCSP responder responds in clear text, however SSL Orchestrator associates an SSL profile to the local OCSP responder virtual server to resign its OCSP response with the client’s Nonce.

Additionally, SSL Orchestrator inserts the configured local OCSP responder URL into the Authority Information Access (AIA) extension of the unique server certificate that is send to the clients.

As part of the enhancements, SSL Orchestrator uses the following two settings from the Server SSL profile to provide certificate gateway response control for revoked and unknown certificate status:

  • Revoked Certificate Status Response Control (revoked-cert-status-response-control)
  • Unknown Certificate Status Response Control (unknown-cert-status-response-control)

These two settings are set to Ignore by default. Additional options are Drop or Mask. The following table describes the expected behavior for each option when SSL Orchestrator deployment is a forward proxy (for example, L3 outbound topology) or a reverse proxy (for example, L3 inbound topology):

Note: When SSL Orchestrator deployment is a reverse proxy, the system is no longer the CA. As a result, it does not forge a unique server certificate to send to the client or generate a OCSP response for the certificate sent to the client by the Client SSL profile.

Local OCSP responder profile statistics

You can view the following statistics for the local OCSP responder profile:

  • OCSP responder profile (name)
  • Associated virtual server (vs_name)
  • OCSP request received (req_rcvd)
  • OCSP cache miss (cache_miss)
  • OCSP response expired (resp_exp)
  • OCSP response re-sign failed (resp_sign_fail)
  • OCSP response successfully sent (resp_send_success)
To view these statistics, enter the following command from the SSL Orchestrator command line:

tmctl -w 150 profile_ocsp_responder_stat

The output appears similar to the following example:

Recommendations

You can configure the local OCSP responder feature using SSL Orchestrator Guided Configuration, located under the Authentication section in SSL Orchestrator Guided Configuration. When you configure the local OCSP responder feature, you should note the following:

  • Ensure the client must be able to resolve the hostname in the FQDN setting to the IP address in the Destination Address/Mask setting.
  • Ensure the client must be able to reach the IP address in the Destination Address/Mask setting as well as the listening port in the Port setting.

    Note: SSL Orchestrator combines the configuration from these settings to form the OCSP responder URL for the AIA extension when forging the unique server certificate.

Validation of the forged unique server certificate with the local OCSP responder

You can use the OpenSSL utility on a Linux client to manually validate the unique server certificate forged by SSL Orchestrator with the local OCSP responder. You should ensure the traffic from the Linux client goes through the SSL Orchestrator deployment. The following example uses an SSL Orchestrator L3 Outbound Transparent Proxy deployment with an intermediate CA intermediateca.askf5.local to forge the unique server certificate and http://ocsp.sslo.sea.askf5.local:80 as the local OCSP responder.

Using the OpenSSL utility on the Linux client, connect to an external site (for example, www.amazon.com) through the L3 Outbound Transparent Proxy, extract the unique server certificate sent by SSL Orchestrator, and save it to the certificate.pem file:

openssl s_client -connect www.amazon.com:443 < /dev/null 2>&1 | sed -n ‘/-----BEGIN/,/-----END/p’ > certificate.pem

You can inspect the unique server certificate and verify the AIA extension using the following OpenSSL command:

openssl x509 -in certificate.pem -text -noout

The output contains snippets similar to the following example:

…
        Issuer: C = US, ST = WA, O = F5Networks, OU = AskF5, CN = intermediateca.askf5.local
…
            Authority Information Access: 
                OCSP - URI:http://ocsp.sslo.sea.askf5.local:80
…

Next, extract the chain certificates that are associated with the external site and save them to the chain.pem file:

openssl s_client -showcerts -connect www.amazon.com:443 < /dev/null 2>&1 | sed -n ‘/-----BEGIN/,/-----END/p’ > chain.pem

With both the certificate.pem and chain.pem files, you can now validate the unique server certificate forged by SSL Orchestrator using the following OpenSSL command:

openssl ocsp -issuer chain.pem -cert certificate.pem -text -url http://ocsp.sslo.sea.askf5.local:80
