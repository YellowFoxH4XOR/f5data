Answer/Recommended Actions

Common types of attack

Cyber attacks range from amateur to expert levels of execution. F5® primarily protects against attacks that target systems for a prospectively greater yield of Personally Identifiable Information (PII).

Attack NameDefinition
Credential StuffingAttack where stolen username/password pairs are used in mass login attempts. Attackers test stolen credentials against the authentication mechanism to exploit credentials which have been reused across multiple platforms.
Denial of Service (DoS)An attack that overwhelms a system so that it cannot respond to service requests. This attack usually is intended to cause a system to shutdown to perform a separate attack.
Distributed Denial of Service (DDoS)Attack that targets a system using multiple host machines infected with malware.
Application DDoSThis attack targets a slow database search of a website, yielding vast resources from the website through a steady stream of GET requests that do not set off bandwidth trigger alarms.
Gift Card CrackingWhen attackers check millions of gift card number variations on a gift card application to identify card numbers that hold value. After the attacker identifies card numbers with positive balances, they use or sell the gift cards before the legitimate customer has a chance to use it.
ScrapingAttackers use automated tools to collect large amounts of data from a target application to reuse that data elsewhere.

 

Attacks and their causes

F5® works with enterprises to prevent unwanted automation—another term for cyber attacks. F5® protects against both web-based automation and mobile automation (or API-based). F5® monitors the activity on an enterprise's web service for indications of automation. The method and indicators inform F5® if the traffic is malicious or normal.

The following attacks are listed from the simplest to the most complex, which is the order in which F5® evaluates them.

AttackIndicatorsMethod
Token Missing

The required accompanying UUID token isn't present in the headers or body. That token is the first part of how the F5® client proves to the SSE that it's present when the request is created.

For example, if someone tries to hit the site with a curl from the command line it comes through with the Token Missing attack cause.

F5® uses this method to detect simple bots.

Token Invalid

The UUID token is present but isn't valid; that is, it wasn't created by F5® Client.

An attacker attempted to use a fake token.
Token Expired

The UUID token is present, but has exceeded its maximum age as defined in policy.

Every UUID encodes a timestamp of when it was generated. The duration (maximum age) the SSE lets a token exist is controlled by policy. Enforcing an age on tokens augments the next two checks, which deal with replay attacks. This prevents an adversary from harvesting numerous tokens over an extended period of time and then rotating through them at such a high velocity that the replay counters can't keep up.

A legitimate user loaded the login page but waited longer than 24 hours to log in, or an attacker attempted to reuse an old token.
Token Reuse

A UUID is used repeatedly across multiple instances of the JavaScript.

The exact limit for token reuse is controlled by policy, and may need to change, depending on site design for web properties.

Every transaction doesn't necessarily have a unique token; rather, every time F5® Client is served, it's accompanied by a unique token. If the site design lets a user generate multiple transactions without needing to fetch a new instance of the JavaScript (for example, with single-page apps or XHR-based transactions) the user continues using the same UUID. Not until the browser asks for a new instance of the JS does the UUID change.

A valid token is retrieved manually (in the browser) and copied into a script to be repeatedly reused.

This helps mitigate the second most naive type of attack.

It's possible for humans to use the same UUID for multiple transactions. For example, for some browsers, pressing the Back button loads the previous page from cache rather than fetching it anew, which can show up as token reuse.

Token DenylistedAn extension of token reuse. This relies on token expiration, since we physically can't keep track of every single token that gets denylisted because it would use too much memory. Even if, after a certain amount of time, the token falls out of the denylist, it will have expired.An attacker attempted to use a token that was previously reused more than ten times in five minutes.
Payload MissingPayload isn't present. If everything passes with the UUID, but the payload isn't there, this check fails. F5® clients attach decorations to the request all at once, not one by one.Something removed part of the payload after F5® Client added it, such as someone using a proxy to tamper with it.
Payload invalidPayload is present but could not be decoded.This almost always indicates tampering, similar to Payload Missing. The payload has several safeguards and checks to guarantee no changes occur after the F5® client attached it, and are validated at this step.
Payload ReplayRequest with a valid token and signal payload that is retrieved manually and re-submitted one or more times.

An exact payload is observed with a valid UUID more than once.

Threat Intelligence

The Threat intelligence flag is present, indicating that the TI rules detected that the request is automation.

The TI rules look for known markers of automation, check for inconsistencies and suspicious relationships in the data, and ultimately decide whether or not the transaction was generated by a human.

For certain older TI packages and behavior policies, Attack Inference may be raised instead of Threat Intelligence, to indicate automation detected based on signals.

An attacker used an automated tool such as Selenium, iMacros, or PhantomJS, or there were other indications of automation detected based on F5® signals.

Attack InferenceIllegitimate transaction where telemetry signals don't indicate automation (for example, otherwise legitimate traffic which is classified in Untrusted Allowlist on behavior policy).An attacker used an automated tool such as Selenium, iMacros, or PhantomJS, or there were other indications of automation such as a mismatch between the UA specified in the HTTP header and the DOM.
