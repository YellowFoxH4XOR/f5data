Topic

This article applies to BIG-IP 11.6.0 and later. For information about other versions, refer to the following article:

  • K5670: Overview of adaptive connection reaping (11.5.x and earlier)

The BIG-IP system allocates memory resources as connection flows are established. To prevent memory resource exhaustion, the system removes connection flows once the flows have been idle for longer than the configured idle timeout values. For each Traffic Management Microkernel (TMM) process, the adaptive connection reaping feature allows the BIG-IP system to dynamically adjust the criteria used to determine what connection flows to remove (reap) or prevent, and when to remove them.

Events or conditions that can substantially increase memory utilization or connection count on a virtual server or route domain, including but not limited to the following:

  • Denial-of-service (DoS) attacks: An attacker attempting to increase BIG-IP memory utilization by sending a large number of connections over a short period of time can cause the system to enter aggressive reaping mode.
  • RAM Cache memory allocation: Allocating too much system memory for the RAM Cache feature can potentially cause the system to enter aggressive reaping mode to free memory.
  • Memory leaks: If a memory leak persists for an extended period of time, the system may enter aggressive reaping mode to free memory.

Description

The sweeper is the component within the Traffic Management Microkernel (TMM) core that both watches for expired connection flows and responds to resource exhaustion by adaptively reaping connection flows. To help prevent resource exhaustion, connection flows are removed after they have been idle for longer than the configured idle timeout values. To help mitigate possible attacks or overflows on system flows, the adaptive connection reaping feature monitors connection flows and system resources to dynamically adjust how aggressively and what connection flows to remove (reap) or prevent. (This is the default behavior of sweeper before it hits the low-water value). After the low-water value is reached, the system logs aggressive sweeper mode start messages and starts reaping connections based on eviction policy algorithms. The connections are dropped based on the aggression level, which is determined by the distance traveled between high-water and low-water thresholds. At or above the high-water value, the aggression level reaches 100 percent; below the low-water threshold, the aggression level is 0 percent; and halfway between the high-water and low-water values, the aggression level is 50 percent. The adaptive connection reaping feature uses eviction policies to enact granular control over establishing new connections and purging stale or established connections, without sending reset packets (RST) to the client.

Within an eviction policy, the high-water and low-water values specify the resource quota percentage used to trigger when the adaptive connection reaping behavior starts and stops.

  • High-water: Specifies the target maximum load on the context. The adaptive reaper becomes more aggressive as this limit is approached. The allowable range is 50 to 100, and the high-water value must be higher than or equal to the low-water value.
  • Low-water: Specifies the aggressive sweeper activation threshold as a percentage of total capacity. The allowable range is 50 to 100, and the low-water value must be lower than or equal to the high-water value.

The context to which the eviction policy is associated determines which monitored resource quota triggers aggressive reaping behavior. The contexts to which an eviction policy can be applied and the associated monitored resources are detailed in the following table:

Eviction Policy ContextMonitored ResourceDescription
GlobalMemory UtilizationIn the global context, the percentage of memory (pagemem) utilization is used as the quota that triggers the start and stop of aggressive reaping behavior.
Virtual ServerConnection LimitsIn the context of a virtual server, the percentage of the maximum number of allowed connection flows (connection limits) for the virtual server is used as the quota that triggers the start and stop of aggressive reaping behavior.
Route DomainConnection LimitsIn the context of a route domain, the percentage of the maximum number of connection flows allowed (connection limits) for the route domain is used as the quota that triggers the start and stop of aggressive reaping behavior.

*Note when using Virtual Server or route domain the default connection limit of 0 will need to reflect the desired max connection to enforce.

Additionally, within an eviction policy, you can specify options to enable slow flow monitoring, and apply user-selectable algorithms that weight the decisions for what flows the system removes. The following algorithms are available to weight connection flow removal decisions:

  • Bias Idle
  • Bias Oldest
  • Bias Bytes
  • Low Priority Route Domains
  • Low Priority Virtual Servers
  • Low Priority Countries
  • Low Priority Ports and Protocols

For specific information about each of the configurable elements available in an eviction policy and how they affect what connection flows are reaped, refer to K15821: Overview of eviction policies.

Applicable strategies

The applicable strategies for a flow are only those with a policy configured on that flow's virtual server or route domain, and the global eviction policy. A policy in any other context cannot apply to the flow. When the sweeper evaluates connection flows, it determines if any of the flow's contexts are in aggressive mode. If no contexts are in an aggressive mode, then the only action taken is to remove flows that have exceeded their maximum idle time. If any contexts are in aggressive mode, then the indicated algorithms from each context in aggressive mode are used to determine whether the system should kill the flow.

Important: All selected algorithms are combined into a master strategy that determines how to discard flows. Each selected algorithm provides a bias that weights the overall strategy, but selecting an algorithm does not guarantee that only those flows are removed.

Additionally, specifying low priority virtual servers or low priority route domains in an eviction policy only has an effect if that policy is associated with that virtual server or route domain, and only if the strategy was triggered in the context of the specified virtual server or route domain.

For example, if you create policy Z that specifies virtual servers A and B as low-priority, and apply policy Z to virtual server B. Connection flows for virtual A is not pruned because policy Z is not applied to virtual A. Similarly, if virtual servers A and B are both in route domain N, and you apply policy Z to route domain M, nothing happens to flows for virtual servers A and B when route domain M is the context that triggers adaptive reaping. Similarly, if you create policy X that specifies route domain N as low-priority and apply policy X to virtual server A, the system prunes only connection flows for virtual server A. Even though virtual server B is in route domain N, connection flows for virtual server B are not affected because policy X is not applied to virtual server B.

Global context

Recommendations

The system comes with a default eviction policy named default-eviction-policy. The default eviction policy uses values of 85% for low-water and 95% for high-water, and has the Bias Idle and Bias Oldest algorithms selected. You should not modify the values of a default policy. If you want non-default values, you should create a custom eviction policy. For information about configuring an eviction policy with custom values, refer to K15822: Configuring custom eviction policies.

Calculating memory (pagemem) utilization
You can determine the percentage of memory (pagemem) that each TMM process uses on the BIG-IP system by typing one of the following commands, depending on your BIG-IP version:

BIG-IP 13.x and later

tmctl -d cluster page_stats

BIG-IP 11.6.0 - 12.x

tmctl -d blade tmm/pagemem

Depending on the BIG-IP platform, the command output may appear similar to the following examples, depending on your BIG-IP version:

BIG-IP 13.x and later

slot tmid pages_used pages_avail ...
---- ---- ---------- -----------
   1    0  936478624  1103101952
   1    1  936478658  1103102976
   2    ...

BIG-IP 11.6.0 - 12.x

name    used      avail
------- --------- ----------
pagemem 936478624 1103101952

When you have obtained the figures as described, use the following formula for calculation:

(used / avail) * 100 = percentage used

Using the previous example, the percentage of memory calculated would be as follows:

(936478624 / 1103101952) * 100 = 84.89%

 

Additional Information

Note: Eviction Policies/Reaping trigger percentages are based on Global Pagemem across all TMM instances.

If a single tmm instance uses all of the pagemem allocated to the instance, then future pagemem allocations for that instance will be taken from the next tmm instance that has available pagemem. This may result in  multiple tmm instances showing no free pagemem, but Eviction will not start if there is sufficient free pagemem globally to not trigger the threshold.

For example Eviction will not start in the following example because although tmm0 is at 100% pagemem utilization, global pagemem is only 46%, well below the threshold:

page_stats

row1      0      1       268293        394752        <== tmm1 pagemem utilization   68%
row2      0      2        35424        394752
row3      0      3        35375        394752
-------------------------------------
