K000133743: Nginx does not return response to the client during nginx reload

Type
Support Solution
Published
2023-04-29
Updated
2023-04-29
Applies to
  • NGINX Products
  • NGINX Plus: R27
Source
https://my.f5.com/manage/s/article/K000133743

Description

  • You configured and deployed Nginx to process HTTP/2 request with keepalive_timeout enabled
    • Keepalive_timeout allows Nginx to reuse existing and established connection to service new client request
  • With the above, for one reason or another if one instruct Nginx to reload configuration using command Nginx -s reload,
    • Nginx would first sends the client/application a protocol compliant GOAWAY frame to initiate graceful shutdown
    • However, if the a client initiate another request at the same time as the Nginx issuing HTTP/2 GOAWAY frame, it could result in a mid-air collusion
    • the resulting collusion could generate application error similar to the one shown below
2156: 2023-04-07 13:18:44.678086 Do request (rid: d1c030af59c71bbd05cce2304bce2d37) ... 
         Get "https://example.com/": http2: Transport: cannot retry 
              err [http2: Transport received Server's graceful shutdown GOAWAY] after Request.Body was written; define Request.GetBody to avoid this error

         panic: client.Do(req) failed.

Environment

  • Nginx Plus
  • HTTP/2
  • Keepalive_timeout Directive

Cause

  • Client initiating new request after Nginx issued HTTP/2 GOAWAY frame

Recommended Actions

  • None on the Nginx as it is Protocol RFC7540 compliant
  • The client mustn't send any additional request.

Additional Information

  • Based on the above error message
    • the client initiate a new request and it states "after Request.Body was written",
    • Nginx the proxy, at the same time, sends a graceful shutdown GOAWAY frame
      • http2: Transport received Server's graceful shutdown GOAWAY
    • here we have a midair collusion, which causes the request to end with " panic: client.Do(req) failed." message
  • Now let us review what the RFC states
    • as you can see from RFC7540 ,
      • The GOAWAY frame (type=0x7) is used to initiate shutdown
      • and more importantly, the RFC also identifies the possible presence of an inherent race condition between an endpoint starting new streams and the remote{Nginx} sending a GOAWAY frame
      • The GOAWAY frame with its stream identifier, indicates the last request that Nginx can process
      • if a GOAWAY frame is NOT sufficient for the client to stop the initiation of new request, this in turn results in unsuccessful request being initiated by the client.

In conclusion and with the above explanation, the observed outcome is in compliance to the mentioned RFC and Nginx is working within the bound of the protocol. Please consult RFC7540 for detailed reading and its application.
