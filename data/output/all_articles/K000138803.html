K000138803: HTTP connection reset is observed, F5RST Malformed HTTP error.

Type
Support Solution
Published
2024-03-04
Updated
2025-09-05
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.1, 15.1.10, 16.1.4
Source
https://my.f5.com/manage/s/article/K000138803

Description

After upgrading the device to BIG-IP 17.1.1.1, 16.1.4.2, or 15.1.10.3 you observe an HTTP connection reset from the BIG-IP device.

This behavior is observed when the device receives a Non-RFC complaint request or response from a client or server. This is known as a malformed HTTP request/response.

The issue is not observed when the software version is rolled back.

Environment

  • An iRule with an HTTP::redirect or an HTTP::respond command that redirects HTTP requests based on the content of the request.
  • An LTM policy that redirects HTTP requests based on the content of the request.
  • Upgrade to BIG-IP 17.1.1.1, 16.1.4.2, or 15.1.10.3.

Cause

  • The fix for Bug ID 1354253 causes the BIG-IP to send a RST when receiving or processing a malformed HTTP request instead of the previous undesirable behavior. For more information refer to K000137322: BIG-IP iRule or LTM policy may generate multiple HTTP redirect responses.

Recommended Actions

To understand the cause of HTTP connection reset from the device, you should perform the below given steps.

  1. Take a packet capture for one of the affected virtual server through bash, the file be stored in /var/tmp folder.
tcpdump -nnvi 0.0:nnnp -s0 host <VS IP address> -w /var/tmp/Malformed_Request_Response.pcap

Note: If the VS processes HTTPS (encrypted) traffic, please take a decrypted packet capture using the below given articles.

  1. Close any open browsers tabs on the system and generate traffic towards the affected VS to reproduce the issue.
  2. Download the capture file from the device and analysis the same using Wireshark.
  3. Look for resets or F5RST Malformed HTTP error packets

To narrow down the results - suggest to use the following filters:

tcp.flags.reset==1
f5ethtrailer.rstcausetxt == "Malformed HTTP header error"
  1. Examine the HTTP header for Malformed packet with respect to the RFC

Note: For more information, refer to the following document. The following link will take you to a resource outside of F5, and it is possible that the document may be removed without our knowledge:

  • RFC 7230
  1. Please refer the below given example, in which response received from the server is Non-RFC complaint.
HTTP/1.1 200 Strict-Transport-Security: max-age=0
X-Frame-Options: SAMEORIGIN
X-Content-Type-Options: nosniff
X-XSS-Protection: 1; mode=block
Cache-Control: no-cache
Expires: XXXXXXXXXXXXXX
Pragma: no-cache
Transfer-Encoding: chunked     <======
Content-Type: application/xxxx
Transfer-Encoding: chunked     <======
Date: XXXXXXXXXXXXXXXXXXXX
Keep-Alive: timeout=60
Connection: keep-alive

In this response the HTTP response has 2 Transfer-Encoding: chunked headers. Two Transfer-Encoding: chunked headers is equivalent to Transfer-Encoding: chunked,chunked.

This would indicate that the body was chunked 2 times which is not RFC compliant.
