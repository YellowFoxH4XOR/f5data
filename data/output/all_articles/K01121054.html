Description

The purpose of this article is to understand the different factors that limits ASM event logs.


Environment

  • BIG-IP ASM
  • Logs Rate limited
  • Local Logging
  • Guaranteed Logging Enabled


Cause

ASM local logging has limitations. This is by design.

For further information refer to K45320421: ASM event logs are deleted or rotated out very quickly


Recommended Actions

The following describes what logs to look for and how to determine log rate limitation behavior.
  1. BD has the variable PRX RateLimit which determines the initial rate limit for BD to pass requests either to pabnagd or asmlogd. The unit is configured with the default value (200); This is divided by the number of bd threads, e.g.

           200 / 16 (cores) = ~12 tps
           
    So each thread can send up to ~12 requests per second to the local logger.

    We need ECARD_POLICY in debug mode to fully confirm that PRX RateLimit thresholds are being exceeded.  Logs may look something like this (example):

    ```
    ECARD_POLICY|DEBUG |Sep 20 10:07:28.359|32519|proxy_log.c:1942|local filter: rate limit ok - req in cur sec: 9 time: 1568999248 limit: 10 (RPS)
    ECARD_POLICY|DEBUG |Sep 20 10:07:28.361|32519|proxy_log.c:1949|local filter: LRN/tightening RATE LIMITED: req in cur sec: 10 time: 1568999248 limit: 10 (RPS)
    ```
    NOTE: BD halts processing if guaranteed logging is enabled and pipes are full.

    BD also has a mechanism in place which reduces the amount of transactions that it relays to pabnagd for learning, based on the overall (aggregated per device) CPU utilization. The default setting of that "bd" mechanism is as follows:

     - CPU utilization  0% -  60%: bd offloads everything to pabnagd
     - CPU utilization 60% -  90%: bd offloads at most 10 requests and 10 responses, in a second, to pabnagd
     - CPU utilization 90% - 100%: bd offloads nothing to pabnagd
     
  2. pabnagd has an internal queue for requests to handle "policies_events_subscription_queue_limit"  (default is 10).
     
  3. asmlogd has a rate limit of 1500 requests per 5 seconds by default "local_insert_rate_limit_count". When the rate limit on asmlogd is reached, asmlogd skips requests and they are not written into db/protobuf. When this happens, you see "skipped" message in its log file as below.

    ```
    asmlogd|INFO|Sep 20 08:21:44.001|32610|F5::RequestLog::log_pulse_message,,270 requests handled since startup (last support id handled = 13315865692552583186, 229889 requests handled from PBRQL, skipped 229619 requests due to rate limit)
    ```
     
  4. About the storage of physical system [5GB]/virtual system [2GB], or 3M records in MySQL; this is for log rotation and not log throttling.
