Summary

The BIG-IP system includes a traffic acceleration feature called Clustered Multiprocessing (CMP). When CMP is enabled, the system creates separate Traffic Management Microkernel (TMM) instances for each CPU, sharing the workload among all CPUs.

Starting in BIG-IP 11.3.0, CMP architecture supports a multi-threaded TMM model for the following platforms.

Description

The CMP feature allows BIG-IP platforms that contain multiple CPUs to run multiple TMM instances. With multiple TMM instances simultaneously processing traffic, system performance is enhanced, and traffic management capacity is expanded. The CMP feature is automatically enabled on BIG-IP platforms, ensuring that all instances of TMM are available to process application traffic.

Certain BIG-IP platforms use a multi-threaded TMM model for CMP processing, while other platforms continue to use the single-threaded model. There is currently no performance difference between the two models; however, the multi-threaded architecture allows BIG-IP performance to more efficiently scale over time, as hardware and network performance continues to increase.

Multi-threaded TMM

Beginning in BIG-IP 11.3.0, TMM supports a multi-threaded architecture. The multi-threaded model is derived from the Symmetric Multi-Processing (SMP) infrastructure. SMP is employed by major operating system kernels and operates by allowing operating systems and software applications to effectively use the multiple processors that are available to the operating system. SMP performs this operation by spreading multiple threads across multiple processors. This model allows for faster processing and more efficient use of system resources, as multiple threads can be processed simultaneously instead of waiting in a queue to be processed.

Under the multi-threaded TMM model, the basic context of execution becomes a thread. The BIG-IP system allocates a fixed number of threads per processing core, which may include hyper-threaded cores. The threads reside in a shared virtual memory space and share a small subset of modules to reduce the greatest causes of overhead. The CMP feature allows platforms that contain multiple CPUs to run a single TMM process for every CPU and multiple TMM threads per processing core.

For example, starting in BIG-IP 11.3.0, the BIG-IP 8950 platform runs two TMM processes, one for each CPU. Each process creates four separate TMM threads. Load balancing behavior for CMP-enabled virtual servers

The BIG-IP system uses a Layer 4 (L4) hash to distribute connections for a CMP-enabled virtual server among the available TMM processes. The pool load balancing algorithm is then applied independently in each TMM instance. Because each TMM handles load balancing independently from the other TMMs, distribution across the pool members may appear to be incorrect when compared with a non-CMP enabled virtual server using the same load balancing algorithm.

Consider the following example configuration:

Virtual Server: 172.16.10.10:80

Pool with 4 members: 10.0.0.1:80
10.0.0.2:80
10.0.0.3:80
10.0.0.4:80

Pool Load Balancing Method: Round Robin

Scenario 1: Virtual server with CMP disabled

Four connections are made to the virtual server; all of which are processed by TMM. The BIG-IP system load balances the four individual connections to the four pool members, based on the Round Robin load-balancing algorithm:

--Connection 1--> |                           | --Connection 1--> TMM0 --> 10.0.0.1:80
--Connection 2--> |-> BIG-IP Virtual Server ->| --Connection 2--> TMM0 --> 10.0.0.2:80
--Connection 3--> |                           | --Connection 3--> TMM0 --> 10.0.0.3:80
--Connection 4--> |                           | --Connection 4--> TMM0 --> 10.0.0.4:80

Scenario 2: Virtual server with CMP enabled

Four connections are made to the virtual server. Unlike the first scenario where CMP was disabled, the BIG-IP system distributes the connections across the multiple TMM instances. For example, the BIG-IP 6900 platform uses four TMM instances. Because each TMM handles load balancing independently of the other TMM instances, it is possible that all four connections are directed to the same pool member.

--Connection 1--> |                           | --Connection 1--> TMM0 --> 10.0.0.1:80
--Connection 2--> |-> BIG-IP Virtual Server ->| --Connection 2--> TMM1 --> 10.0.0.1:80
--Connection 3--> |                           | --Connection 3--> TMM2 --> 10.0.0.1:80
--Connection 4--> |                           | --Connection 4--> TMM3 --> 10.0.0.1:80

The CMP feature is designed to speed up connection handling by distributing connections across multiple TMM instances. While initially this behavior may appear to favor one or several servers, over time, the load is distributed equally across all servers.

CMP Hash

Beginning in BIG-IP 11.3.0, the CMP Hash setting in the Advanced section of a VLAN Configuration allows you to disaggregate VLAN traffic based on source IP address, destination IP address, or TCP/UDP source and destination ports (default). For example, Service Provider (SP) clients can have large amounts of session data associated with their IP addresses. Gathering this session data from multiple (remote) TMMs can be costly in terms of CPU resources. Allowing all traffic from a client to use the same set of TMMs increases overall performance.

Note: This feature is supported in BIG-IP VE beginning in BIG-IP 11.4.0 and is not supported on Virtual Clustered Multiprocessing (vCMP) configurations.

CMP restrictions in the BIG-IP system

With the BIG-IP system, if a virtual server uses any of the following BIG-IP features, CMP is disabled for that virtual server and handled by TMM0 only:

  • An iRule using a non-static global variable
  • An iRule that refers to a Data Group List (class) using the $:: global variable prefix

Note: For more information, refer to K13033: Constructing CMP-compatible iRules.

Recommendations

Benchmarking throughput performance on CMP systems

CMP relies on an equitable hash distribution of traffic among a cluster of traffic processing cores and internal backplane connections. This architecture is optimized for real-world traffic, which generally includes a large variation of IP addresses and L4 port tuples.

When testing throughput performance on CMP systems, the benchmark test should be configured to match real-world traffic. For example, configuring the benchmark test to use multiple concurrent connections with many source IP addresses, several virtual servers, and multiple pool members, yield a better test result. This is because CMP spreads connections across processing cores, and traffic is also more evenly distributed among the internal backplane paths.

Disabling or enabling CMP for a virtual server

Note: Disabling CMP globally on the BIG-IP system is not supported or recommended. The supported way to disable CMP is to do so on a per-virtual basis. This can be done only by tmsh command on CLI, not GUI.

For performance reasons, F5 recommends that you leave the CMP feature enabled. However, you may occasionally need to disable CMP for a virtual server. To do so, perform the following procedure:

  1. Log in to the command line.
  2. Use the following command syntax:

    tmsh modify ltm virtual <virtual_server_name> cmp-enabled <yes/no>

    For example, to disable CMP mode for the virtual server named CMP_vip, enter the following command:

    tmsh modify ltm virtual CMP_vip cmp-enabled no

  3. To save the changes made to the virtual server, enter the following command:

    tmsh save sys config

Verifying whether CMP is enabled or disabled for a specific virtual server

To verify whether CMP is enabled or disabled for a virtual server, use the following command syntax:

tmsh show ltm virtual <virtual_server_name>

For example, the CMP line in the tmsh output indicates that CMP mode is enabled for the virtual server named CMP_vip:

---------------------------------------------------------
Ltm::Virtual Server: CMP_vip
---------------------------------------------------------
Status
Availability : available
State : enabled
Reason : The virtual server is available
CMP : enabled
CMP Mode : all-cpus
Destination : 10.11.10.212:80

Even if CMP is enabled on a virtual server, the BIG-IP system demotes a virtual server with incompatible features from CMP processing. If the virtual server has been demoted, the CMP Mode line reports none, disable, or single to indicate that CMP has been demoted for the virtual server. The command output appears similar to the following example:

---------------------------------------------------------
Ltm::Virtual Server: CMP_vip
---------------------------------------------------------
Status
Availability : available
State : enabled
Reason : The virtual server is available
CMP : enabled
CMP Mode : single
Destination : 10.11.10.212:80
