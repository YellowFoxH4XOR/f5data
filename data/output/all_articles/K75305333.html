K75305333: Configuring cluster domain in Aspen Mesh

Type
Support Solution
Published
2021-09-20
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K75305333

Description

Most Kubernetes clusters out of the box will assign a cluster domain using the default: cluster.local

The cluster domain is also heavily used in Aspen Mesh as it could define trust between workloads. That means if cluster domain is different from our installation, we would have issues in communication or denied all requests to workloads with a different trust domain.

Environment

  • Kuberntes: 1.17x,1.18.x,1.19.x,1.20.x
  • Aspen Mesh: 1.9.x 

Cause

If your Kubernetes installation uses a different domain than the default, use the following recommendations to upgrade/install Aspen Mesh with the same cluster domain.

Recommended Actions

  1. Update the clusterDomain and trustDomain on your override values file
  2. Verify components shows the new domain

Update the clusterDomain and trustDomain on your override values file

  1. On your override values file add the following to the global field to override the default cluster domain.

    global:
      proxy:
        # cluster domain. Default value is "cluster.local".
        clusterDomain: "my.domain"

      # The trust domain corresponds to the trust root of a system
      # Re-fer to https://github.com/spiffe/spiffe/blob/master/standards/SPIFFE-ID.md#21-trust-domain
      # Indicate the domain used in SPIFFE identity URL
      # The default depends on the environment.
      #   kubernetes: cluster.local
      #   else:  default dns domain
      trustDomain: "my.domain"

  2. Upgrade/Install Aspen Mesh.

    helm upgrade -i istiod manifests/charts/istio-control/istio-discovery -n istio-system --values aspenmesh-values.yaml

  3. If you have deployed an istio-ingress gateway you should use the same values and upgrade them as well.

    helm upgrade -i istio-ingress manifest/charts/gateways/istio-ingress -n istio-system – values aspenmesh-values.yaml

Verify components shows the new domain

After upgrading the trust domain, all the proxies running must be restarted so it will receive the new configuration from istiod controlplane.

Follow the next steps to ensure the proxy trust the new domain.

  1. From the logs, at the startup the proxy will log the configuration received, output the logs, and search the flag –trust-domain.

    For example:
    kubectl logs details-v1-6f94cb9ff6-nxp4k -c istio-proxy
    2021-09-01T15:52:32.188680Z     info    FLAG: --concurrency="2"
    2021-09-01T15:52:32.189015Z     info    FLAG: --disableInternalTelemetry="false"
    2021-09-01T15:52:32.189029Z     info    FLAG: --domain="default.svc.my.domain"

    [redacted]

    2021-09-01T15:52:32.190551Z     info    FLAG: --templateFile=""
    2021-09-01T15:52:32.190556Z     info    FLAG: --tokenManagerPlugin="GoogleTokenExchange"
    2021-09-01T15:52:32.190561Z     info    FLAG: --trust-domain="my.domain"

  2. You can also verify the new trust chain in the spiffe URI for the certificates on the proxy with the following command:

    Iistioctl proxy-config secret details-v1-6f94cb9ff6-nxp4k -o json | jq '[.dynamicActiveSecrets[] | select(.name == "default")][0].secret.tlsCertificate.certificateChain.inlineBytes' -r | base64 -d | openssl x509 -noout -text | grep UR

    URI:spiffe://my.domain/ns/default/sa/bookinfo-all

  3. If you are not able to see the new domain on the logs neither in the certificate, verify istiod pod has the new domain.

    You should be able to see the same flag –trust-domain in logs:

    kubectl logs istiod-c7cbd9469-x4mvb -n istio-system
    …
    2021-09-01T15:52:31.462501Z     info    FLAG: --trust-domain="my.domain"
