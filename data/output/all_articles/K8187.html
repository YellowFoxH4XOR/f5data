Topic

This article applies to BIG-IP 9.x through 10.x. For information about other versions, refer to the following article:

  • K15664: Overview of BIG-IP device certificates (11.x - 12.x)

Secure Socket Layer (SSL) certificates and keys are used on the BIG-IP system for a variety of purposes, such as administrative tasks, inter-device communication, and offloading SSL traffic. This article provides information about SSL certificates and keys used for administrative tasks and inter-device communication.

Note: The SSL certificates and keys used for BIG-IP SSL profiles are not covered in this article. For more information about the use of SSL certificates and keys in the Client SSL profile, refer to K10167: Overview of the Client SSL profile (9.x - 10.x)

BIG-IP devices use SSL certificates for inter-device authentication and communication. For authentication and communication between F5 devices to work properly, you should be aware of the following:

  • F5 device certificates need to be stored in the correct locations on each F5 system.
  • Management of F5 device certificates is critical in a BIG-IP GTM deployment.
  • Management of F5 device certificates is critical in a BIG-IP WebAccelerator symmetric deployment.
  • Device certificates must be valid, and must not be expired.
  • BIG-IP redundant pair members have unique device certificates that need to be maintained and renewed independently.
  • For BIG-IP GTM deployments and for BIG-IP WebAccelerator symmetric deployments, if you update or renew device certificates after they have expired, you must ensure that the new certificates are copied to the remote F5 devices. Device certificates are exchanged when running the following scripts on a BIG-IP system:
    • bigip_add (GTM and WebAccelerator)
    • big3d_install (GTM only)

Note: For more information about the bigip_add and big3d_install utilities, refer to K8195: Overview of the BIG-IP GTM big3d_install, bigip_add, and gtm_add utilities (9.x - 10.x).

OpenSSL overview

Device SSL certificates are stored in text files on the F5 systems, and the contents are BIG-IP PEM-encoded. If you look at the certificate file, you will see the BIG-IP PEM-encoded certificate between the BEGIN CERTIFICATE and END CERTIFICATE tags in the file. It may occasionally be useful to view the properties of a certificate; to do this, you would use the openssl x509 command.

Viewing and verifying SSL certificates

To view an SSL certificate in text form, you can use the openssl x509 -noout and -text options. For example, the following command displays the server.crt file in text form:

# openssl x509 -noout -text -in /config/httpd/conf/ssl.crt/server.crt

Note: If the certificate file contains more than one SSL certificate, the openssl x509 command will display only the properties of the first file.

To verify that an SSL certificate/key pair matches, refer to K6746: Verifying SSL certificates and keys from the command line (9.x - 10.x).

x509 Certificate properties

Some of the x509 certificate fields are described below:

  • Version:

    The version field notes the version of x509 standard for the certificate.

  • Serial Number:

    The CA that issued the certificate assigns a serial number to distinguish the certificate from other certificates that the CA issues.

  • Subject:

    The subject field identifies the owner of the private key.

  • Issuer:

    The issuer identifies the CA that issued the certificate.

    Note: If the Subject and the Issuer fields of the certificate match, the SSL certificate is a self-signed certificate. In most cases, F5 device certificates are self-signed certificates.

  • Validity:

    The period of validity identifies the starting and ending dates of the certificate validity. This field should be reviewed if the certificate is thought to be expired or expiring soon.

  • Public key:

    The public key field includes the public key and the encryption algorithm used to issue the key.

F5 device certificates and locations

The device certificate is used by the F5 system to identify itself to a requesting F5 client system.

The default device certificate name is server.crt. The device certificate is used by the Configuration utility for HTTPS communication as well as by the following device-to-device communication processes:

  • configsync
  • big3d
  • gtmd
  • iqdump

Viewing the device certificate properties using the Configuration utility

  1. Log in to the Configuration utility.
  2. Click System.
  3. Click Device Certificates.

    The system's device certificate is displayed.

Locating the device certificate and key from the command line

From the command line, the device certificate and key are found in the following locations:

  • Device certificate file:

    /config/httpd/conf/ssl.crt/server.crt

  • Device key file:

    /config/httpd/conf/ssl.key/server.key

Renewing or creating new device certificate and key pairs

On occasion, you may need to renew or create new device certificate and key pairs.

For information about renewing device certificate and key pairs, refer to the following two articles:

  • K6353: Updating an SSL device certificate on a BIG-IP system
  • K7754: Renewing self-signed device certificates

For information about creating new device certificate and key pairs, refer to the following article:

  • K9114: Creating a new SSL device certificate and key pair

Trusted device certificates

The trusted device certificates are used by the big3d agent of the local BIG-IP device to authenticate a connection from a remote BIG-IP device. For example, the big3d agent of the local BIG-IP GTM or BIG-IP LTM system uses the trusted device certificate obtained from a remote F5 device to authenticate the remote device's gtmd or iqdump requests. Additionally, BIG-IP WebAccelerator systems in a symmetric deployment use the trusted device certificate obtained from a remote F5 device to authenticate that device.

If a deployment includes many BIG-IP devices, all of which authenticate to one another, the list of trusted device certificates for a given device should include the signed certificates of each authenticating F5 device. In addition, the list of trusted device certificates must include the device's own certificate.

Starting in BIG-IP 9.3.0, the trusted device certificate can be signed by a third-party CA. If using third-party certificates, the trusted device certificate file only needs to contain the certificates of the certificate authorities that signed the device certificates. If a certificate chain is used, the trusted device certificate file must contain all of the certificates in the chain. In addition, it is recommended that the local device's certificates be included in the file.

Viewing the trusted device certificates using the Configuration utility

  1. Log in to the Configuration utility.
  2. Click System.
  3. Click Device Certificates.
  4. Click Trusted Device Certificates from the menu.

    The Trusted Device Certificates are displayed.

    Note: K6996: The trusted device certificate is imported to the incorrect file documents an issue where the trusted device certificates do not appear on the Trusted Device Certificates screen in the Configuration utility.

Locating the trusted device certificates from the command line

From the command line, you can find the trusted device certificates in the following file:

/config/big3d/client.crt

Note: The file is called client.crt because the trusted device certificates contained in the file are used to authenticate big3d and iquery client requests from remote F5 devices.

Trusted server certificates

The trusted server certificates are used when the local BIG-IP GTM system authenticates itself to a remote F5 device. For example, the local BIG-IP GTM uses the trusted server certificate when the BIG-IP GTM system's gtmd process or iqdump program attempts to connect to the big3d process on a remote F5 device.

The list of trusted server certificates must include the BIG-IP GTM system's own certificate as well as the self-signed certificates of any remote F5 device to which it will connect. The trusted server certificates list is synchronized to BIG-IP GTM devices in a synchronization group.

Starting in BIG-IP 9.3.0, the trusted server certificate can be signed by a third-party CA. If using third-party certificates, the trusted server certificate file needs to contain only the certificates of the certificate authorities that signed the device certificates. If a certificate chain is used, all of the certificates in the chain must be contained in the trusted server certificate file. In addition, it is recommended that the local device's certificates be included in the file.

Viewing the trusted server certificates using the Configuration utility

  1. Log in to the Configuration utility.
  2. Navigate to Global traffic > Servers > Trusted Server Certificates.
  3. Click Trusted Server Certificates from the menu.

    The Trusted Server Certificates are displayed.

Locating the trusted server certificates from the command line

From the command line, the trusted server certificates are contained in the following file:

/config/gtm/server.crt

Note: The file is called server.crt because the local BIG-IP GTM system (gtmd and iquery) uses the trusted server certificates contained in the file to authenticate itself to the remote F5 devices (big3d agents).

Summarizing F5 device certificate placement

For any local BIG-IP GTM device (device A) to communicate with the big3d agent on any other BIG-IP GTM (including itself) or BIG-IP device (device B), the following two statements must be true:

  • Device A's device certificate (and the CA chain) must exist in Device B's trusted device certificates list
  • Device B's device certificate (and the CA chain) must exist in Device A's trusted server certificates list

Managing device certificates is slightly more complicated when more devices exist in the BIG-IP GTM configuration. For example, if there are two BIG-IP GTM devices (GTM1 and GTM2) and two BIG-IP LTM devices (LTM3 and LTM4), you should ensure that the same certificate configuration exists for all of the following device pairings:

  • GTM1 to GTM1
  • GTM1 to GTM2
  • GTM1 to LTM3
  • GTM1 to LTM4
  • GTM2 to GTM1
  • GTM2 to GTM2
  • GTM2 to LTM3
  • GTM2 to LTM4

The following table indicates the certificates that each device in the group should maintain in order to establish inter-device communication.

Using certificates signed by a third party

Beginning in BIG-IP GTM and Link Controller 9.3.0 and 9.4.2, you can assign SSL certificates from a third-party CA. You must import each certificate to its respective system, and increase the certificate chain traversal depth (Certificate Depth setting) on all systems to an appropriate level.

For example, for the BIG-IP system to verify certificates that are directly signed by a root CA, the certificate depth value must be at least 1. For the BIG-IP to verify certificates signed by a CA whose certificate is signed by a root CA, the value must be at least 2. If you are unsure about the depth of your CA chain, set the value to 9.

In BIG-IP GTM and Link Controller 9.3.x and 9.4.2 through 10.2.4, two settings affect how far the BIG-IP system searches through a certificate chain when validating a certificate; one setting for the big3d process, and the other setting for the gtmd process and iqdump.

Configuring the certificate depth setting for big3d, gtmd, and iquery (9.3.x and 9.4.2 through 10.2.4)

  • big3d

    The BIG-IP LTM and BIG-IP GTM systems use the Big3d.CertificateDepth BigDB variable to determine how far the big3d process searches through a certificate chain when validating the certificate of a connecting BIG-IP GTM device. The default value is 0 (zero) to represent a self-signed certificate. The Big3d.CertificateDepth BigDB values can range from 0 (self-signed) to 9. A value of 1 would be used for a device certificate that is directly signed by the root CA.

    Note: If using certificates signed by a third party, the Big3d.CertificateDepth BigDB variable should be set to the appropriate value. There is no representation of the Big3d.CertificateDepth BigDB variable in the Configuration utility. For more information, refer to K7547: The Big3d.CertificateDepth Variable is not honored.

    Changing the Big3d.CertificateDepth BigDB variable

    To change the Big3d.CertificateDepth BigDB variable, type the following command from the command line, replacing <value> with a number between 0 and 9:

    bigpipe db Big3d.CertificateDepth <value>

  • gtmd and iquery

    On BIG-IP GTM systems, the gtmd process and iqdump use the Certificate Depth setting to determine how far through a certificate chain each process will search when validating the certificate of the remote big3d agent. The default value is 0 (zero).

    Changing the Certificate Depth value on the BIG-IP GTM system

    1. Log in to the Configuration utility.
    2. Click System.
    3. If running BIG-IP 9.x, click General Properties; if running BIG-IP 10.x, click Configuration.
    4. From the Global Traffic menu, select General.
    5. Set the desired value for the Certificate Depth setting.

      Note: Changing the Certificate Depth value will add a line to the Globals section of the wideip.conf file, similar to the following example:

      certificate_depth 3 // Default=0

Checking the third-party certificates

It is possible to generate certificates that will not work with the iQuery protocol. You can use OpenSSL to determine if there is a problem with the CA file. If there are no problems, the following commands should return OK.

  • openssl verify -purpose sslclient -CAfile <certificate chain file> <file.crt>
  • openssl verify -purpose sslserver -CAfile <certificate chain file> <file.crt>

Enterprise Manager SSL certificates

If the F5 device is remotely managed by an Enterprise Manager system, the /shared/em/ssl.crt directory on the F5 device contains SSL certificates from the remote Enterprise Manager system from which the F5 device is accepting connections. If there is not an Enterprise Manager system in the environment, the /shared/em/ directory may not exist. The certificates in the /shared/em/ directory should not be removed as they are necessary for Enterprise Manager communication.
