K000140726: Aspen Mesh Sidecar CRD conflict when multiple sidecar resources target the same workload

Type
Support Solution
Published
2025-06-22
Updated
2025-06-22
Applies to
  • Aspen Mesh: 1.14, 1.11
Source
https://my.f5.com/manage/s/article/K000140726

Description

When a global Sidecar resource (without a workloadSelector) is applied, typically to enforce namespace isolation. it is expected to affect all workloads within the mesh. However, if a workload-specific Sidecar is later applied with a workloadSelector targeting a particular workload, the global configuration stops to be applied to that workload.

For example, we have the following global Sidecar in the istio-system namespace to isolate all workloads, so they can only communicate within their own namespace and the istio-system namespace:

apiVersion: networking.istio.io/v1alpha3
kind: Sidecar
metadata:
  name: namespace-isolation
  namespace: istio-system
spec:
  egress:
  - hosts:
    - "./*"
    - "istio-system/*"

Later, we apply this workload-specific Sidecar in the default namespace to redirect traffic for a workload labeled "app: httpbin":

apiVersion: networking.istio.io/v1beta1
kind: Sidecar
metadata:
  name: server-redirect-8080
  namespace: default
spec:
  ingress:
  - defaultEndpoint: 0.0.0.0:8080
    port:
      name: server-http2-8080
      number: 8080
      protocol: HTTP
  workloadSelector:
    labels:
      app: httpbin

After this second resource is applied, the httpbin workload will no longer have the namespace isolation defined in the global Sidecar. The traffic restrictions from the global config will be overridden without any error, and httpbin will be able to access services in other namespaces.

Environment

  • Aspen Mesh 1.11.X 1.14.X 1.18.X 1.21.X
  • Istio Sidecar CRD

Cause

Aspen Mesh only allows one Sidecar resource to be applied per workload. When multiple Sidecar configurations exist:

  • If one or more Sidecar resources use a workloadSelector, Aspen Mesh gives priority to the most specific match, the Sidecar whose selector matches the workload’s labels.
  • A Sidecar resource without a workloadSelector (commonly used for namespace or mesh-wide configuration) will not be applied to any workload that is matched by a Sidecar with a selector.

Recommended Actions

To ensure the workload receives both Sidecar configuration (global sidecar and with workload selector):

  • Merge the desired configurations into a single Sidecar CRD that uses a workloadSelector matching the target workload and the global one. For example:
apiVersion: networking.istio.io/v1beta1
kind: Sidecar
metadata:
  name: httpbin-combined-sidecar
  namespace: default
spec:
  workloadSelector:
    labels:
      app: httpbin
  ingress:
  - defaultEndpoint: 0.0.0.0:8080
    port:
      name: server-http2-8080
      number: 8080
      protocol: HTTP
  egress:
  - hosts:
    - "./*"
    - "istio-system/*"

 

In this case, we combined both ingress and egress (global and per workload) Sidecar config into one so we can have both configurations.  

 

Additional Information

This behavior is consistent with other Istio resources like DestinationRule and VirtualService, where only one resource should be targeted per workload.
