K10628: The Kerberos proxy user generates Failure Audit log events on the Windows authentication server

Known Issue

This is the result of a known issue. Prior to ARX version 5.0.0, the ARX proxy user could only authenticate using NTLM authentication. Starting in ARX version 5.0.0, the ARX proxy user can also authenticate using Kerberos authentication. However, when authenticating using Kerberos, ARX does not include the Authentication Server Request (AS_REQ) with the initial authentication attempt. As a result, if failure auditing is enabled on the Windows authentication server, a log entry with an Event ID of 675 and a Failure Code of 0x19 is recorded each time authentication fails.

For example:

Event Type: Failure Audit
Event Source: Security
Event Category: Account Logon
Event ID: 675
Date: 7/6/2008
Time: 10:16:06 PM
User: NT AUTHORITY\SYSTEM
Computer: FILESERVER
Description:
Pre-authentication failed:
User Name: arx-proxy
User ID: DOMAIN\arx-proxy
Service Name: krbtgt/DOMAIN.LOCAL
Pre-Authentication Type: 0x0
Failure Code: 0x19.
 
Failure auditing is a Microsoft Windows feature, which can be useful for intrusion detection. However, enabling failure auditing may generate a high volume of logs that can quickly fill up disk space on a Windows server. If the ARX system frequently authenticates against the Windows server, the initial authentication failures may quickly consume disk space on the server.
 
Important: This issue does not not affect Kerberos authentication between the ARX system and the Windows authentication server. Although the initial authentication attempt fails, the subsequent authentication attempt will succeed if Kerberos authentication is correctly configured on the ARX system.
 
Note: For Windows auditing best practices, refer to the following location:

http://technet.microsoft.com/en-us/library/cc778162%28WS.10%29.aspx.
 
F5 Product Development tracked this issue as ARX ID 36111 and it was fixed in ARX version 5.0.5. For information about upgrading, refer to the ARX release notes.
 
Additionally, this issue has been fixed in a hotfix available for ARX version 5.0.1. Customers affected by this issue should request the hotfix from F5 Technical Support, referencing this Solution number and ARX ID 36111.
 
Workaround
 
You can work around this issue on the Active Directory server by assigning the DONT_REQ_PREAUTH flag to the ARX proxy user’s UserAccountControl attribute. To assign this flag, add the value 0x400000 (hexadecimal) or 4194304 (decimal) to the current value of the proxy user’s UserAccountControl attribute. For example, if the current value is 512, the new value would be 4194816 (4194304 + 512).
 
Modifying the UserAccountControl attribute requires the Ldp.exe tool or the Adsiedit.msc snap-in.

Note: For more information about modifying the UserAccountControl attribute, refer to the following location:

http://support.microsoft.com/kb/305144.
