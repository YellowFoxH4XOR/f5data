Description

Istio and Aspen Mesh support four different TLS connection modes for traffic originating from PODs being part of the mesh: 

  • DISABLE: Do not setup a TLS connection to the upstream endpoint.
  • SIMPLE: Originate a TLS connection to the upstream endpoint.
  • MUTUAL: Secure connections to the upstream using mutual TLS by presenting client certificates for authentication.
  • ISTIO_MUTUAL: Secure connections to the upstream using mutual TLS by presenting client certificates for authentication. Compared to Mutual mode, this mode uses certificates generated automatically by Istio for mTLS authentication. When this mode is used, all other fields in Client TLS Settings should be empty.

We control originating connection settings using DestinationRule custom resource definitions. Aspen Mesh, and latest releases of Istio, enforces mutual TLS local communication between PODs inside service mesh using a default PeerAuthentication and DestinationRule objects:

? kubectl get PeerAuthentication default -n istio-system  -o yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT

? kubectl get DestinationRule default -n istio-system  -o yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
  name: default
  namespace: istio-system
spec:
  host: '*.local'
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL

Destination rules by default are using ISTIO_MUTUAL mode so TLS certificates used by istio proxies created and managed by Istiod CA authority and provisioned using SDS API.

If applications need to communicate with any external service (not being part of the mesh) using mutual TLS protocol, then usually we do not want use ISTIO_MUTUAL mode. External services may have certificates signed by different CA authority or certificates may not be compatible with Istio CA certificate chain. In this scenario we can configure DestinationRule with MUTUAL mode and manually provisioned certificates or we can route traffic through egress gateway and use Gateway definitions. In this article we will document how to configure DestinationRule with local TLS certificates. For information how to configure egress gateway with mutual TLS, refer to Egress Gateway with mTLS Origination.

Environment

  • Kuberntes: 1.17x,1.18.x,1.19.x,1.20.x
  • Aspen Mesh: 1.6.x, 1.9.x 

Cause

None

Recommended Actions

TLS certificates are configured in Destination Rules using clientCertificate, privateKeyand caCertificates fields. In MUTUAL mode all these fields are required and should be empty for ISTIO_MUTUAL mode. For information about DestinationRule setting, refer to Istio DestinationRule configuration reference. 

Below is an example for configuring DestinationRule with MUTUAL TLS mode:

apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: dr-mtls
  namespace: ns1
spec:
  host: myservice.ns2.svc.cluster.local
  exportTo:
  - ‘.’
  trafficPolicy:
    tls:
      mode: MUTUAL
      clientCertificate: /etc/certs/myclientcert.pem
      privateKey: /etc/certs/client_private_key.pem
      caCertificates: /etc/certs/rootcacerts.pem

By applying dr-mtls rule all connections from applications running in ns1 namespace to myservice.ns2.svc.cluster.local service will be secured with mutual TLS connection. Envoy proxies in ns1 namespace will be configured to use certificates stored under /etc/certs/ local directory. It is important to note that the directory is a local directory for istio-proxy container and users are responsible for ensuring that the directory and certificates are available for Envoy  proxy process running inside istio-proxy container. 

Mounting certificates to istio-proxy container can be done in a few ways:

  • Using “istioctl kube-inject” tool to manually generate POD spec with injected sidecar proxy and modify the spec to mount certificate. For more information, refer to the example Manual sidecar injection.
  • By modifying injection template or using injectConfigFile option in istioctl command. For more information, refer to the example Manual sidecar injection.
  • Store certificates in a Kubernetes secret object and mount secret to istio-proxy container using POD annotations:

      annotations:
        sidecar.istio.io/userVolumeMount: '[{"name":"your-secret-name", "mountPath":"path-in-istio-proxy", "readonly":true}]'
        sidecar.istio.io/userVolume: '[{"name":"your-secret-name", "secret":{"secretName":"your-secret-name"}}]'

Here is an example for sleep a POD with certificates mounted to “/etc/certs/” directory inside istio-proxy container. Certificates are stored on “secret1” Kubernetes secret object.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: sleep
spec:
  replicas: 1
  selector:
    matchLabels:
      app: sleep
  template:
    metadata:
      labels:
        app: sleep
      annotations:
        sidecar.istio.io/userVolumeMount: '[{"name":"secret1", "mountPath":"/etc/certs/", "readonly":true}]'
        sidecar.istio.io/userVolume: '[{"name":"secret1", "secret":{"secretName":"secret1"}}]'
    spec:
      containers:
      - name: sleep
        image: curlimages/curl
        command: ["/bin/sleep", "3650d"]
        imagePullPolicy: IfNotPresent

Users must remember to use exportTo field in DestinationRules with MUTUAL mode configured. By Default, if exportTo field is missing or no namespaces are specified then the destination rule is exported to all namespaces (regardless of the namespace where DestinationRule is deployed). The value . in exportTo field is reserved and defines an export to the same namespace that the destination rule is declared in. Similarly, the value * is reserved and defines an export to all namespaces. 

Secret objects are namespaced in Kubernetes and usually PODs cannot mount secrets residing on a different namespace than the POD. If a DestinationRule with MUTUAL mode enabled is provisioned to the POD where certificates are not provisioned to istio-proxy container then the sidecar proxy may not start or may log logs like the below messages:

2021-12-08T23:23:38.741113Z          error    cache   resource:file-cert:/etc/certs/myclientcert.pem~/etc/certs/client_private_key.pem failed to generate secret for proxy from file: open /etc/certs/myclientcert.pem: no such file or directory
2021-12-08T23:23:38.741126Z          error    cache   resource:file-root:/etc/certs/rootcacerts.pem failed to generate secret for proxy from file: open /etc/certs/rootcacerts.pem: no such file or directory
