Issue

Description

If the verbose logging is enabled on a multi-bladed VIPRION, the monitor logs are distributed across the blades depending on the number of pool members.

The log file has the following file naming format:

<MonitorPartition>_<MonitorName>-<NodePartition>_<NodeName>-<port>.log

Environment

  • You have enabled the verbose (debug) monitor logging for one or more pool members on a multi-bladed VIPRION.
  • You have command line access to the BIG-IP system.

Cause

None

Recommended Actions

If the verbose monitor logging is enabled for two members in a pool, the pool member updates the logs on only one blade for each pool member. The rest of the blades do not contain the verbose log messages for these pool members; however, the log marker Logging enabled appears in their respective log files. To view these verbose log messages, you can perform the following procedure:

Impact of procedure: The /var/log directory may become full if you leave monitor logging enabled for a long period of time. Be sure to disable monitor logging after troubleshooting.
  1. Enable the monitor verbose logging from the Configuration utility or CLI. For information about enabling monitor verbose logging, refer to K12531: Troubleshooting health monitors.
     
  2. Verify the monitor log files on all the blades by entering the following command:

    clsh ls -al /var/log/monitors/

    Output appears similar to the following:

    === slot 1 addr 127.3.0.1 color green ===
    total 152
    -rw-r--r--. 1 root root 138160 2017-08-09 02:35 Common_tcp-Common_10.10.20.10-80.log
    -rw-r--r--. 1 root root    736 2017-08-09 02:35 Common_tcp-Common_10.10.20.16-80.log
    === slot 2 addr 127.3.0.2 color green ===
    total 16
    -rw-r--r--. 1 root root 256 2017-08-09 02:32 Common_tcp-Common_10.10.20.10-80.log
    -rw-r--r--. 1 root root 256 2017-08-09 02:32 Common_tcp-Common_10.10.20.16-80.log
    === slot 3 addr 127.3.0.3 color green ===
    total 140
    -rw-r--r--. 1 root root    256 2017-08-09 02:32 Common_tcp-Common_10.10.20.10-80.log
    -rw-r--r--. 1 root root 110572 2017-08-09 02:35 Common_tcp-Common_10.10.20.16-80.log
     

  3. From the previous example, the verbose monitor logging for pool member 10.10.20.16:80 is logged in the monitor logging file on blade3:
    -rw-r--r--. 1 root root    256 2017-08-09 02:32 Common_tcp-Common_10.10.20.10-80.log
    -rw-r--r--. 1 root root 110572 2017-08-09 02:35 Common_tcp-Common_10.10.20.16-80.log

     

  4.  If you view the monitor log file on blade2, you notice that it does not contain the verbose logging; however, you would observe the verbose monitor logging marker is included in that log file:

    [0][24447] 2017-08-09 02:32:41.388600: ID 5     :(inst_to_service) Logging enabled. [ addr=::ffff:10.10.20.10:80 srcaddr=none ]
    [1][24448] 2017-08-09 02:32:41.388600: ID 5     :(inst_to_service) Logging enabled. [ addr=::ffff:10.10.20.10:80 srcaddr=none ]

    Note: Debug logging is not enabled on one specific blade. If you delete the /var/log/monitors directory on a blade, the log files may not exist if the system decides to locate the log file on that blade. Restarting the bigd process restores that directory and log file.

Additional Information

In BIG-IP 11.5.0 and later, the Monitor Logging option is available to allow the system to log more verbose messages for each pool member and node level. To access the option from the Configuration utility, navigate to Local Traffic > Pools > Pool List and select the pool and member that you want, or navigate to Local Traffic > Nodes > Node List and select the node that you want.

The BIG-IP system stores the log of the respective pool member or node in the /var/log/monitors/ directory. The system does not save the Monitor Logging option setting into the system configuration but rather disables the option when the configuration loads. Additionally, the BIG-IP system does not include the Monitor Logging option in syncing operations.
