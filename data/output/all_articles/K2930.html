Topic

Beginning in BIG-IP 4.5, you can use universal persistence to achieve an effect similar to HTTP cookie persistence, but without requiring BIG-IP to record which pool member is selected in the persistence table.

Universal persistence allows you to persist on any string within a packet, or persist directly to a specific pool member. You can enable universal persistence by including rules-syntax expressions within a pool definition. In this way, a pool can perform load balancing operations, such as sending traffic to a specific node within the pool, or load balancing traffic based on any string or node that you define. Furthermore, the rules syntax has been expanded to allow rules to intelligently persist requests to cache servers based on more granular information in a request.

Universal persistence is particularly useful for persisting HTTP or TCP content that is unique to your application. Universal persistence is valuable when employed in i-mode phone usage and when working with BEA Weblogic servers, by creating persistence maps on BEA Weblogic identifiers, for example.

Note: For more information about the Universal Inspection Engine and iRules, refer to the iRules chapter of the BIG-IP Reference Guide.

Universal persistence should be used only in the following situations:

  • When it is not required that the client stay persisted to the same server that initially set the cookie.

  • When the client comes to the site with the cookie already present.

Universal persistence sequence

The sequence of events for universal persistence is:

  • HTTP request comes in without a cookie; the BIG-IP load balances the request normally.

  • HTTP server sets the cookie.

  • The next request contains the cookie and the BIG-IP hashes the cookie value (using a different hashing algorithm than the one used for cookie hash persistence), and inserts the hash as an index into the persistence table. Since an entry does not yet exist in the persistence table, the BIG-IP load balances the request normally, and adds an entry to the persistence table mapping the hash value to the selected pool member. As with cookie hash persistence, this is likely to be a different pool member than the one to which the first request was directed.

  • Subsequent requests contain the cookie and BIG-IP hashes the cookie value, inserts it as an index into the persistence table, and uses the entry in the persistence table to select the pool member.

It is much safer to use universal persistence, rather than cookie persistence, for cookies with values that vary from session to session, because BIG-IP uses load balancing to select the pool member the first time it sees each cookie value; however, since BIG-IP determines the node based on the cookie's hash value (and it may not see the cookie for the first time until after it is set by the server), it is likely that the node to which the client is persisted will differ from the node that sets the cookie.

Configuring BIG-IP to use universal persistence

To configure BIG-IP to use universal persistence, type the following command:

substr (http_cookie ("cookie_name"), byte offset, length of string to persist on)

Or, to use the entire cookie value, type the following command:

http_cookie ("cookie_name")

Note: The persist statement can use other arguments, such as http_uri, client_addr, and so forth. Refer to the BIG-IP Reference Guide for more information.
