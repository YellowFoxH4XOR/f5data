Description

  • You want to perform the TCP health check on your origin pool.

Environment

  • F5® Distributed Cloud (XC)
  • Load Balancers

Cause

None

Recommended Actions

Assigning the health check to the origin pool

  1. Under the appropriate namespace, go to Manage > Load Balancers > Origin Pools.

  2. Under Actions select Manage Configuration.
  3. In the top right corner, select Edit Configuration.
  4. Look for List of Health Check(s) and select Add item.
  5. In the dropdown menu, select an already existing health check or select Create new Health Checks for a new health check.

Create a health check

Note: You can start this process by editing the origin pool (following the previous steps) or by going to Manage > Load Balancers > Health Checks > Add Health Check.

  1. In the Metadata section, choose a valid Name and optionally add Labels and Description as required.
  2. In the Health Check Parameters section, for the Health Check parameter, select TCP HealthCheck from the drop-down menu.
  3. Optionally, for the Send Payload parameter, add raw bytes of payload (in hexadecimal form) which are sent in the request. This parameter can be left empty for a connect-only health check.
  4. Optionally, for the Response Payload parameter, add raw bytes of payload (in hexadecimal form) expected in the response.
  5. You can keep the default values for the rest of the health check parameters if you are positive your origin web server can handle them, but relaxing them a bit in the first place is recommended:
    ParameterValueDescription
    Timeout(s)Default: 3
    Minimum: 1
    Maximum: 600    		Time to wait for a health check response. A TCP handshake should take less than 2-3 seconds.
    Interval(s)Default: 15
    Minimum: 1
    Maximum: 600    		Time, in seconds, between two health check requests. A value of 20 seconds would test your server 3 times per minute.
    Unhealthy ThresholdDefault: 1
    Minimum: 1
    Maximum: 16    		Number of failed responses required before a host is marked unhealthy. You can probably tolerate an occassional network or server health check failure without taking the server out of the pool.
    Health ThresholdDefault: 3
    Minimum: 1
    Maximum: 16    		Number of healthy checks required before a host is marked healthy. This value should be higher than the value set for Unhealthy Threshold.
  6. Select Add Health Check.

Example parameter configuration screen

Note: The amount of time before a server is taken out of the origin pool is calculated using UT x I + T, where UT is the Unhealthy Threshold, I is the interval, and T is the timeout. With the values in the above screenshot, this will be 2 x 20 + 10 = 50 seconds. With the default values, it would be 18 seconds. Of course setting these values really low will end up with less traffic loss, but you risk emptying your pool of available origin servers by setting parameters to too demanding values.

Additional Information

  • TCP health checks are used to verify the availability of origin servers by attempting to establish a TCP connection (optionally sending/receiving payloads).
  • Bear in mind that, by nature, TCP healthchecks may not mark a server as down upon application-layer failure such as HTTP errors (4xx/5xx).  If application servers remain network-reachable during failure, a HTTP healthcheck may be more suitable.
  • You can configure TCP health checks either by editing the origin pool or by creating a new health check under "Manage > Load Balancers > Health Checks".
  • Key parameters for TCP health checks:
    • Timeout: Time to wait for a health check response, typically 3-way handshake establishment.  This should take no more than 2-3 seconds. It is recommended to align this value with Connection Timeout on the Origin Pool.
    • Interval: Time in seconds between health check attempts (e.g., 20 seconds tests the server 3 times per minute).
    • Unhealthy Threshold: Number of failed checks before marking a host as unhealthy.
    • Healthy Threshold: Number of successful checks before marking a host as healthy (should be higher than the unhealthy threshold).
  • The time before a server is taken out of the pool is calculated as: (Unhealthy Threshold x Interval) + Timeout.
  • Setting thresholds too low may result in unnecessary removal of healthy servers; setting them too high may delay detection of real failures.
  • You can optionally specify send/response payloads in hexadecimal for more advanced TCP health checks, but for basic connectivity, these can be left empty.
