Topic

Beginning in BIG-IP 10.1.0, the BIG-IP system implements SELinux in place of Subdomain. SELinux enforces mandatory access control policies that confine user programs and system services to the minimum amount of privilege they require to do their jobs. Implementing SELinux adds an extra layer of security to the BIG-IP system.

Note: For more information about SELinux, refer to the following web site. The following link will take you to a resource outside of AskF5, and it is possible that the document may be removed without our knowledge: 

http://www.nsa.gov/research/selinux/index.shtml

Because of SELinux, extra care must be exercised when manually handling files on the BIG-IP system. Operations that were legitimate in previous BIG-IP versions may cause issues in 10.1.0 or later.

Consider the following example scenarios:

The Configuration utility does not display an SSL certificate and key pair that was manually uploaded to the BIG-IP system
  • You are required to create a new SSL virtual server.
  • Using the SCP utility, you upload the SSL certificate and key for the new virtual server to the /root/ directory of the BIG-IP system. For the purpose of this example, we will assume that the files are named askf5.crt and askf5.key.
  • You run the following commands to move the aforementioned files to the appropriate directories:

    mv /root/askf5.crt /config/ssl/ssl.crt/
    mv /root/askf5.key /config/ssl/ssl.key/
  • You log on to the BIG-IP system Configuration utility to create a new Client SSL profile; however, the system does not display the new SSL certificate and key pair under Local Traffic >> SSL Certificates. Additionally, if you attempt to create the new Client SSL profile, the certificate and key are not displayed in the Certificate and Key drop-down menus.
An SSL virtual server stops working after a renewed certificate is installed
  • Your BIG-IP system is configured with the following Client SSL profile:

    profile clientssl AskF5 {
       defaults from clientssl
       key "askf5.key"
       cert "askf5.crt"
    }
  • The profile is associated to a virtual server that is working as intended.
  • The SSL certificate is about to expire and you are required to install a renewed certificate.
  • Using the SCP utility, you upload the renewed certificate to the /root/ directory of the BIG-IP system.
  • You run the following command to move the renewed certificate to the appropriate directory, thus overwriting the old certificate:

    mv /root/askf5.crt /config/ssl/ssl.crt/
  • You issue the bigpipe load command to reload the configuration.
  • Although the bigpipe load command returns no errors, the virtual server stops working and the following error message is logged to the /var/log/ltm file:

    local/tmm crit tmm[7279]: 01260000:2: Profile AskF5: could load neither certificate nor chain file

These issues occur because the files were originally uploaded to the /root/ directory and then moved to the /config/ directory. The SELinux security context (also known as security label) for files in the /root/ directory is different from that for files in the /config/ directory. SELinux will prevent TMOS processes from accessing a file whose security context is incorrect for the directory in which the file resides. Because the mv utility retains a file’s security context when the file is moved, SELinux denies access to the /config/ssl/ssl.crt/askf5.crt and /config/ssl/ssl.key/askf5.key files.

The SELinux security context is made up of 3 or 4 components separated by a colon character ( : ). You can display a file's security context by passing the -Z option to the ls utility. In the case of the above examples, SELinux denies access to the files because the Type component (the third component from the left) is incorrect for files residing in the /config/ directory:

  • The following is the security context for a file created in the /root/ directory:

    # ls -Z /root/askf5.crt
    -rw-r--r--  root root root:object_r:user_home_t        /root/askf5.crt
  • The following is the security context for the same file after the file is moved to the /config/ssl/ssl.crt/ directory:

    # ls -Z /config/ssl/ssl.crt/askf5.crt
    -rw-r--r--  root root root:object_r:user_home_t        /config/ssl/ssl.crt/askf5.crt
  • The following is the security context for a file created in the /config/ directory:

    # ls -Z /config/ssl/ssl.crt/askf5.crt
    -rw-r--r--  root root root:object_r:f5config_t         /config/ssl/ssl.crt/askf5.crt

When these issues occur, the BIG-IP system also logs messages similar to the following example to the /var/log/auditd/audit.log file:

type=AVC msg=audit(1272377796.039:115): avc:  denied  { getattr } for  pid=4122 comm="iControlPortal." path="/config/ssl/ssl.crt/askf5.crt" dev=md3 ino=118799 scontext=system_u:system_r:icontrol_t:s0 tcontext=root:object_r:user_home_t:s0 tclass=file

type=AVC msg=audit(1272377796.051:116): avc:  denied  { read } for  pid=4122 comm="iControlPortal." name="askf5.key" dev=md3 ino=118800 scontext=system_u:system_r:icontrol_t:s0 tcontext=root:object_r:user_home_t:s0 tclass=file

Workaround

In order to avoid these and similar issues, you should adhere to the following best practices:

  • When possible, use the Configuration utility to upload a file to the BIG-IP system.
  • If using the SCP utility to upload a file to the BIG-IP system, have the utility upload the file directly to the appropriate directory.
  • If a file has already been uploaded to a temporary directory using the SCP utility, you can copy the file to the appropriate directory. The cp utility does not retain a file’s security context when the file is copied.

If you are already experiencing an issue similar to those described in this Solution, you can use the restorecon utility to restore a file's default security context. For example:

restorecon /config/ssl/ssl.crt/askf5.crt

After you have restored the file’s default security context, reload the configuration by running the bigpipe load command.
