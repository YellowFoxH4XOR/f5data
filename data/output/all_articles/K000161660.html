Description

On BIG-IP LTM, connection-mirrored virtual servers can reset client traffic when the next-active peer evaluates mirrored flow state with different iRule or data-group content. The active unit may pass similar traffic, while the peer that receives mirrored state reaches a different allow or reject decision for the same virtual server logic.

Environment

  • BIG-IP LTM

Cause

Connection mirroring shares connection and persistence state with the HA device that can become active for the traffic group. If an attached iRule makes an early decision in FLOW_INIT, a peer-side difference in referenced objects can change the outcome before the expected server-side flow is created.

  • An iRule that calls reject during early flow handling causes BIG-IP to send a TCP reset.
  • Data-group, iRule, or sync-status differences between HA peers can make mirrored traffic follow a different decision path than traffic handled only by the active unit.
  • HA::status should be validated in the specific traffic-group and iRule-event context where it is used, rather than assumed to represent a global device role.

Recommended Actions

  1. Identify mirrored virtual servers:
    tmsh list ltm virtual <VIRTUAL-SERVER> mirror rules
    tmsh show sys ha-mirror
    Confirm whether mirroring is enabled and record the iRules attached to the affected virtual server.
  2. Compare peer-side iRule dependencies:
    tmsh show cm sync-status
    tmsh list ltm rule <IRULE-NAME>
    tmsh list ltm data-group internal <DATA-GROUP-NAME>
    Run the same checks on both HA peers and compare every object used by the mirrored virtual server.
  3. Correct configuration drift before deeper analysis:
    If the peers do not match, restore the intended iRule and data-group content, synchronize the device group, and retest before treating the reset as a backend or network issue.
  4. Review the early reject point:
    Where application behavior permits, evaluate whether the allow or reject decision can move from FLOW_INIT to a later event such as CLIENT_ACCEPTED. Validate the enforcement point carefully before production use.
  5. Confirm whether BIG-IP generated the reset:
    During testing, check whether a matching server-side connection is created. An immediate client-side reset with no server-side flow points the investigation toward mirroring, iRules, and local BIG-IP policy decisions.

Additional Information

Connection mirroring is most valuable for long-lived flows that must survive failover. For short-lived traffic, review whether mirroring is needed, because it adds HA-state dependencies and can expose peer-side object differences that would otherwise remain hidden.
