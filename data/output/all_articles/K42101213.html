Description

If you use an iRule to reselect a new pool member using the LB_FAILED event after the connection attempt to the originally selected pool member fails, the BIG-IP system does not trigger the LB_FAILED event when subsequent connection attempts to the reselected pool members also fail.

The LB_FAILED event is triggered when the BIG-IP system is ready to send the request to a pool member and one of the following occurs:

  • The system failed to select a pool or a pool member OR
  • The selected pool member is unreachable (when no route to the selected pool member exists) OR
  • The selected pool member is non-responsive (fails to respond to a connection request).

Environment

  • iRule with LB::reselect inside LB_FAILED event

Cause
Change in behavior due to ID 656898

Recommended Actions

If you want the system to continue to attempt reselection of remaining active pool members after previous failures, you can use the reselect-tries setting on the desired pool. This setting can replace the example iRule discussed in the Additional Information section and you have to disassociate the iRule from the virtual server. To do so, perform the either of the following procedures:

Impact of procedure: Performing this procedure should not have a negative impact on your system. F5 recommends testing all changes in an appropriate environment prior to implementing it in a production environment.

Configuration utility

  1. Login to the Configuration Utility
  2. Navigate to Local Traffic > Virtual Servers > Virtual Server List
  3. Click on the name of the virtual server associated with the example iRule
  4. Click Resources
  5. Click Manage under the iRules section
  6. Select the iRule and click >> to move it out of the Enabled box
  7. Click Finished to save the change
  8. Navigate to Local Traffic > Pools > Pool List
  9. Click on the name of the pool that you want the system to perform reselection
  10. Select Advanced from the Configuration setting
  11. Enter a value equal to the number of members in the pool minus one (n - 1) in the Reselect Tries setting. For example, enter 3 if you have four members in the pool.
  12. Click Update to save the change.

tmsh utility

  1. Login to the tmsh utility
  2. Disassociate the example iRule from the virtual server by entering the following command syntax:

    modify /ltm virtual <virtual server name> rules none

    For example, you would enter the following command for the myvirtual virtual server:

    modify /ltm virtual myvirtual rules none

  3. Configure the Reselect Tries value equal to the number of members in the pool by entering the following command syntax:

    modify /ltm pool <pool name> reselect-tries <number_of_pool_members>

    For example, you would enter the following command for the mypool pool that has four pool members:

    modify /ltm pool mypool reselect-tries 3

  4. Save the changes by entering the following command:

    save /sys config

Additional Information
You may consider using an alternative configuration if you require the system to perform subsequent reselection of pool members.

Starting in BIG-IP 13.1.0 and 12.1.3.6, the LB_FAILED event can only be triggered once when you use it to reselect a new pool member after the initial load balancing decision did not result in a successful connection to the selected server. Subsequent failures do not trigger the LB_FAILED event.

For example, you use an iRule similar to the following:

when CLIENT_ACCEPTED {
  set retries 0
}
when LB_FAILED {
  if { $retries < [active_members [LB::server pool]] } {
    LB::mode rr
    LB::reselect
    incr retries
  }
}

If you use this iRule with a pool of four active pool members and the connection attempt to the originally selected pool member failed, LB_FAILED event is triggered and the system attempts to select another pool member. However, if the connection attempt to the subsequently selected pool member also failed, the system does not trigger the LB_FAILED event. As a result, the system does not attempt to reselect from the remaining active pool members.

In versions prior to BIG-IP 13.1.0, the system triggers the LB_FAILED event each time the connection attempt to a selected pool member fails. This process repeats until all pool members have been tried once.
