Description

Third party switches report mac-address flapping errors when BIG-IP using in inline mode with virtual-wire. For example:

<date>: %L2FM-4-L2FM_MAC_MOVE2: Mac 0000.5e00.5310 in vlan 100 has moved from Po1 to Eth1/1
<date>: %L2FM-4-L2FM_MAC_MOVE2: Mac 0000.5e00.5310 in vlan 100 has moved from Eth1/1 to Po1

Scenario is with two third party devices in active/standby mode each connecting through BIG-IP setup inline using virtual-wire. When the third party devices perform a failover, it is followed by one or more adjacent switches complaining of mac-address movement between interfaces. This message can be informational only or may be accompanied by protective action (eg: interface shutdown, mac-address blocking, learning disabled) depending on the configuration of the switches.

                                                    +========+

           ---<network>---FW1 (active)----BIG-IP1---|        | 
clients---|                                         | switch |---servers
           ---<network>---FW2 (standby)---BIG-IP2---|        |

                                                    +========+

Environment

  • BIG-IP configured for virtual-wire or transparent vlan-group
  • BIG-IP configured for high availability (HA) and failover has occurred
  • BIG-IP traffic-group configured with mac masquerade
  • Third party switch (error above is from a Cisco)

Cause

The switch uses mac-address learning to identify egress ports for ingress traffic. If the switch learns a mac-address on one interface and then on another it might issue a log message indicating that mac-address flapping (or "mac move") has occurred.

In this instance, failover of the 3rd party firewalls has occurred

Recommended Actions

The solutions to this are any of the following:

  • Disable reset on timeout on all tcp profiles (standard TCP VS)
  • Disable reset on timeout on all fastl4 profiles (fastl4 TCP VS)
  • Set sys db tm.rejectunmatched to false (UDP and other protocols)

Additional Information


The scenario is that FW1 is active and passing traffic through BIG-IP1 to the servers and creating connflow entries (tmsh show sys conn). When failover occurs between FW1 and FW2 and FW2 is now active, all traffic is now flowing through FW2 and BIG-IP2 to the servers. The transparent nature of virtual-wire means that the same mac-addresses will be used between BIG-IP and servers independent of whether BIG-IP1 or BIG-IP2 is passing traffic.

The errors occur when the connflows on BIG-IP expire. If BIG-IP sends tcp reset or icmp unreachable notifying the client/server of the connflow expiration, then the mac-address flapping will be seen. ie: ongoing active connflows from BIG-IP2 (on active path from FW2) and reset/icmp from BIG-IP1 (as connflows expire).
