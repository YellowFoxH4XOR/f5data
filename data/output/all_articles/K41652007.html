Known Issue

The BIG-IQ system may fail to remove AlertsIgnoredCollectionWorker records from the database, which can consume /var disk partition space.

This issue occurs when the following condition is met:

  • The BIG-IQ system is configured with one or more data collection devices (DCD).

The records in the AlertsIgnoredCollectionWorker category do not expire, which causes the database to continue to grow. The database resides in the /var directory and the disk partition will fill up over a period of time.

Impact

The /var directory becomes full over time and causes unexpected behavior on the BIG-IQ system, which may include disruption of services provided by the system. System tools or services that require you to create a file in the /var disk partition will fail or abort with an error message.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The /var disk partition fills up over a period time. To check the percentage of disk usage on the /var directory, type the following command:

    df -h /var

  • When you access the BIG-IQ Advanced Shell (bash) or TMOS Shell (tmsh), you may observe a system broadcast message that appears similar to the following example:

    011d0004:3: Disk partition /var has only 0% free

  • After generating a QKView snapshot, the resulting file is too large and you are not able to upload it to BIG-IP iHealth.
  • When you attempt to save the active configuration to a UCS file in bash, it will fail and you may observe a series of error messages that appear similar to the following example:

    msgbusd_storage_save_pre: REST storage backup failed; ensure restjavad is running and healthy (see /var/log/restjavad.0.log)
    restjavad    run (pid 12421) 44 days, 1 start
    Failed starting local-only instance of TokuMX: 0
    Error executing 'pre-save' configsync script /var/tmp/cs_save_pre_script.
    /var/tmp/toku_storage_temp: Directory does not exist
    WARNING:There are error(s) during saving.
            Not everything was saved.
            Be very careful when using this saved file!
    Error creating package
    Error during config save.
    Unexpected Error: UCS saving process failed.

Workaround

There is no workaround for this issue. To prevent this issue, you must upgrade to a fixed release. To recover from this issue, you must perform all of the following three procedures:

  • Procedure 1: Slowing down the rate of these alerts
  • Procedure 2: Removing the AlertsIgnoredCollectionWorker records
  • Procedure 3: Re-indexing the database to reclaim space in the /var directory

Procedure 1: Slowing down the rate of these alerts

To recover from this issue, you can slow down the generation rate for the affected alerts. To do so, perform the following procedure:

Impact of workaround: F5 recommends performing this procedure during a scheduled maintenance period as it involves restarting BIG-IQ services that cause service disruptions.

  1. Back up a copy of the existing /var/config/rest/config/restjavad.properties.json file by typing the following command:
    cp -a /var/config/rest/config/restjavad.properties.json /var/config/rest/config/restjavad.properties.json.K41652007
     
  2. Using an editor of your choice, modify the /var/config/rest/config/restjavad.properties.json file.

  3. Inspect the Platform section in the file, and locate for fileObjectGroomer and policymgmt sections. The BIG-IQ systems that have been upgraded from 5.x may not have the policymgmt properties defined in the file. In this case, insert the policymgmt properties stanza (refer to the next step) right after the fileObjectGroomer properties and add a comma (if needed) to preserve the JSON structure.

  4. In the Platform section, locate the fileObjectGroomer section. Add a comma ( , ) after the second brace ( } ) for the fileObjectGroomer configuration file.

    For BIG-IQ systems that are directly installed with 6.0.x, the unmodified configuration file may appear similar to the following example:

            "fileObjectGroomer":
            {
                "pollingIntervalMillis": 600000
            }
                "policymgmt":
            {
                "groomingIntervalSec": 259200,
                "alertsQueryFrequencyMS": 3600000,
                "alertsQueryTimeFilterMS": 172800000,
                "alertsRequestLimit": 1
            }
      
    After adding the comma, the configuration appears similar to the following example:

            "fileObjectGroomer":
            {
                "pollingIntervalMillis": 600000
            }, 
                "policymgmt":
            {
                "groomingIntervalSec": 259200,
                "alertsQueryFrequencyMS": 3600000,
                "alertsQueryTimeFilterMS": 172800000,
                "alertsRequestLimit": 1
            }
      

  5. Save the modification and exit the editor.
  6. To verify that the modified file loaded properly, type the following command:

    jq .platform /var/config/rest/config/restjavad.properties.json

    Note: If you receive errors with this command, repeat steps 2 through 6 to review and correct the errors prior to proceeding.

  7. Restart the restjavad service by typing the following command:

    tmsh restart /sys service restjavad

    Completing these steps slows the alert-generation rate and ensures that /var disk partition usage does not increase rapidly. To remove unnecessary objects, perform Procedure 2.

Procedure 2: Removing the AlertsIgnoredCollectionWorker records

To remove the unnecessary records and objects that occupy disk space on the /var directory, perform the following procedure:

Impact of workaround: F5 recommends performing this procedure during a scheduled maintenance period as it involves restarting BIG-IQ services that cause service disruptions.

  1. Log in to bash on the BIG-IQ system.
  2. Using an editor of your choice, create a batch file that contains the following commands:

    for(var i = db.bigiqLiveObjects.find({'_value.kind':'cm:shared:policymgmt:alerts-ignored:alertsignoredstate'}).count(); i >=0; ) { print(i); var removeIdsArray=db.bigiqLiveObjects.find({'_value.kind':'cm:shared:policymgmt:alerts-ignored:alertsignoredstate'}, {_id : 1}).limit(100000).toArray().map(function(doc) { return doc._id; });  db.bigiqLiveObjects.remove({_id: {$in: removeIdsArray}}); i-=100000;}

  3. To initiate the batch file, use the following mongo command syntax:

    mongo bigiqDb <Filename_From_Step2>

    For example, if you saved the file to /shared/tmp/remove_alerts in step 2, you would type the following command:

    mongo bigiqDb /shared/tmp/remove_alerts

    A sample command output with the zero value may appear similar to the following example:

    TokuMX mongo shell v2.0.3-mongodb-2.4.10
    connecting to: bigiqDB
    0

  4. Before proceeding to Procedure 3, rerun this script as needed to ensure that the count is at or near zero. A large number of records (more than 10 KB) remaining in the directory may indicate that Procedure 1 did not complete correctly. Therefore, the number of records is still growing rapidly. In this case, repeat Procedure 1 and this procedure before continuing to Procedure 3.

Procedure 3: Re-indexing the database to reclaim space in the /var directory

F5 recommends re-indexing the database to reclaim excess space in the /var directory. To do so, perform the following procedure:

Impact of workaround: F5 recommends performing this procedure during a scheduled maintenance period as it involves restarting BIG-IQ services that cause service disruptions.

  1. Create a backup of the current BIG-IQ database by typing the following commands:

    mkdir /var/tmp/toku_backup 

    dump-rest-storage /var/tmp/toku_backup

  2. Stop the tokumond and restjavad services by typing the following command:

    tmsh stop /sys service tokumond restjavad

  3. Use the mongo shell to create a copy of the bigiqLiveObjects collection. To invoke the mongo shell, type the following command:

    mongo

  4. In the mongo shell, type the following commands:

    use bigiqDb

    db.bigiqLiveObjects.copyTo('bigiqLiveObjectsBackup')

    A sample of the command and output appears similar to the following example:

    bigiq0:PRIMARY> use bigiqDb
    switched to db bigiqDb
    bigiq0:PRIMARY> db.bigiqLiveObjects.copyTo('bigiqLiveObjectsBackup')
    204098

  5. Re-index the database collection by typing the following command:

    db.bigiqLiveObjects.reIndex()

    The re-indexing process is successful if the command output contains the following entry: 

    "ok" : 1

    While executing this step, you can access bash and invoke the mongo shell. To check the re-indexing progress, type the following command:

    db.currentOp()

    The message line shows a progress percentage for each of the 12 indices, one index at a time. Once it completes all of the indices, the system posts the "ok" : 1 entry.

  6. Once the re-indexing is process is successful, you can delete the backup by typing the following command:

    db.bigiqLiveObjectsBackup.drop()

    The command output appears similar to the following example:

    true

  7. To exit the mongo shell, type the following command:

    quit()

  8. Wait 5 minutes before starting up the tokumond and restjavad services. To wait and restart the services, type the following command:

    sleep 300; tmsh start /sys service tokumond restjavad;
