K94561586: Exposing a service over SIMPLE TLS using Istio ingress gateway in Aspen Mesh

Type
Support Solution
Published
2021-06-25
Updated
2023-02-07
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K94561586

Description

Istio Ingress Gateway is the Kubernetes Ingress Proxy that you can configure to expose a service to clients outside of the Aspen Mesh service cluster. You configure the Istio Ingress Gateway object using manifests but if you want to expose the service over secure HTTPS protocol, you have to provide SSL certificates the Ingress Gateway can fetch from a specified location. In this article we are going to describe how we can expose the service over the HTTPS protocol.
 

Environment

  • Aspen Mesh: 1.14.5  
     

Cause

HTTPS traffic is encrypted and therefore is recommended to avoid data in clear text over the internet.
 

Recommended Actions

Before you begin, you need to install Aspen Mesh and the Istio Ingress Gateway on your cluster. You will subsequently use the httpbin application deployed inside the Aspen Mesh mesh cluster. And finally to test the connection, you will reach the service from outside the cluster using the curl command.

  • Install Aspen Mesh and Istio Ingress Gateway

  • Create SSL certificates for the Ingress Gateway

  • Configure Istio Ingress Gateway to use the certificates

  • Expose httpbin with SIMPLE HTTPS protocol

Install Aspen Mesh and Istio Ingress Gateway

  1. Install Aspen Mesh and Istio Ingress Gateway using the steps in the Install section in the Aspen Mesh Getting Started guide.

    For more information about installing and configuring Istio Ingress Gateway, refer to K50557252: Install Istio Ingress Gateway using the Aspen Mesh Ingress Helm Chart.

  2. To install the httpbin application in the namespace app1, enter the following commands:

kubectl create namespace app1
kubectl label --overwrite namespace app1 istio-injection=enabled
kubectl apply -f samples/httpbin/httpbin.yaml -n app1 

Create SSL certificates for the Ingress Gateway

In the next step you’d need to create SSL certificates used by Ingress Gateway to secure the channel between the external client and the Ingress Gateway. If you enabled mTLS in the Service Mesh (which is enabled by default in Aspen Mesh), then the connection between the Ingress Gateway pod and the httpbin application will be secured using certificates maintained by Istio. To create SSL certificates using openssl, perform the following procedure:

  1. Create a self-signed root CA certificate and a key to sign the certificates used by the Ingress Gateway for the httpbin application.

    openssl req -x509 -sha256 -nodes -days 30 -newkey rsa:2048 -subj '/O=rootca Inc./CN=example.com' -keyout rootca.key -out rootca.crt

  2. Create a certificate and a private key for the httpbin application using the following commands:

    openssl req -out httpbin.csr -newkey rsa:2048 -nodes -keyout httpbin.key -subj "/CN=httpbin.example.com/O=httpbin app"
    openssl x509 -req -days 30 -CA rootca.crt -CAkey rootca.key -set_serial 0 -in httpbin.csr -out httpbin.crt

  3. You should have 2 SSL certificates pairs as output when you enter the ls following command:
    > ls
    httpbin.crt httpbin.csr httpbin.key rootca.crt  rootca.key

Configure Istio Ingress Gateway to use the certificates

After creating the certificates for your application you need to tell Istio Ingress Gateway where to find the certificates. From the Gateway object specification in the Istio documentation, you can do this in two ways:

  • By specifying credentialName field

  • By specifying serverCertificate and privateKey fields.

The credentialName field is the name of the secret object located in the same namespace where the Istio Ingress Gateway is installed. The secret object holds the TLS certificate, key and the CA certificates for mTLS, mutual TLS. The following describes the specifications:

  • The secret in generic type have to contain the files in the following format: key: <privateKey>, cert: <serverCert>.

  • For mTLS , specify in the format: cacert: <CACertificate>

  • For the Secret type TLS, specify the following fields: --key=<KEY_FILE> and --cert=<CERT_FILE>

The serverCertificate and privateKey fields are the paths to the files holding the certificates and keys. The paths are the absolute path to the files stored inside the Istio Ingress Gateway container. Usually, the files are mounted on the container as volumes and fetched from the Secret object.

If you do not want to modify the Istio Ingress Gateway deployment and configuration to mount additional volumes with TLS certificates for the Gateway you should use the credentialName object or you can create pre-mounted Secrets called ingressgateway-certs and ingressgateway-ca-certs. These 2 Secrets are mounted on the Ingress Gateway pod by default during the installation but usually they do not exist in the cluster. This is done intentionally and because the Secret volumes are mounted as Optional, this will not block the Ingress Gateway from the start. You need to name your secrets holding certificates ingressgateway-certs and ingressgateway-ca-certs. Secrets will be mounted inside the Ingress pod in the following locations:

  secretVolumes:
    - mountPath: /etc/istio/ingressgateway-certs
      secretName: istio-ingressgateway-certs
      name: ingressgateway-certs
    - mountPath: /etc/istio/ingressgateway-ca-certs
      secretName: istio-ingressgateway-ca-certs
      name: ingressgateway-ca-certs

Expose httpbin with SIMPLE HTTPS protocol

Perform the following procedure:

  1. Create the secret holding SSL certificates. The namespace should be the same as the Istio Ingress Gateway namespace.

    kubectl create -n istio-system secret tls httpbin-secret --key=httpbin.key --cert=httpbin.crt

  2. Configure the Gateway object using the kubectl command to apply the following yaml file to allow HTTPS traffic destined for the httpbin.example.com host:

    cat <<EOF | kubectl apply -n app1 -f -
apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: httpbin-gateway
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 443
      name: https
      protocol: HTTPS
    tls:
      mode: SIMPLE
      credentialName: httpbin-secret
    hosts:
    - httpbin.example.com
EOF

  3. Configure the VirtualService object to route all requests for the /get URI to the httpbin service listening on port 8000 using the kubectl command to apply the following yaml file:

    cat <<EOF | kubectl apply -n app1 -f -
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: httpbin-vs
spec:
  hosts:
  - "httpbin.example.com"
  gateways:
  - httpbin-gateway
  http:
  - match:
    - uri:
        exact: /get
    route:
    - destination:
        host: httpbin
        port:
          number: 8000
EOF

  4. Test your application using the following example curl command: 

    Note: Replace ISTIO_INGRESS_GATEWAY_IP from the command with the IP address of your Ingress gateway. 

    curl -H "Host: httpbin.example.com" --cacert rootca.crt --resolve "httpbin.example.com:443:<ISTIO_INGRESS_GATEWAY_IP>"  https://httpbin.example.com:443/get
{
  "args": {},
  "headers": {
    "Accept": "*/*",
    "Content-Length": "0",
    "Host": "httpbin.example.com",
    "User-Agent": "curl/7.64.1",
    "X-B3-Parentspanid": "6c9122a722a847bc",
    "X-B3-Sampled": "1",
    "X-B3-Spanid": "881483a270cf3fba",
    "X-B3-Traceid": "ab2bc8946d8a468e6c9122a722a847bc",
    "X-Envoy-Attempt-Count": "1",
    "X-Envoy-Internal": "true",
    "X-Forwarded-Client-Cert": "By=spiffe://cluster.local/ns/app1/sa/httpbin;Hash=61dba3d3d36ea6f5dc7d7454d7b58d97165c82a7919eb858638de375fe79241c;Subject=\"\";URI=spiffe://cluster.local/ns/istio-system/sa/istio-ingressgateway-service-account"
  },
  "origin": "10.131.2.2",
  "url": "https://httpbin.example.com/get"


    The Gateway configuration we used has the host field configured which means that the Istio Ingress Gateway will perform a TLS SNI match for all requests before decrypting the traffic and passing to the HTTP router. This means that any HTTPS request with the SNI field different from the host specified in the Gateway will be rejected.

    The curl command will include the host name into the SNI field only when we specify the --resolve "httpbin.example.com:443:<ISTIO_INGRESS_GATEWAY_IP" option. Without the –resolve option, if you use the Gateway IP in the URL (https://<IP>:443/get) then the SNI will contain the IP address instead of the hostname httpbin.example.com.

    Once the request is accepted by the Gateway it is processed later by the HTTP router. The HTTP router (configured by the VirtualService object) is using the Host header to choose the service and cluster where the traffic should be forwarded. If we remove the Host header from the curl command then the proxy will respond with a 404 error message because the proxy will not be able to select the correct route.
