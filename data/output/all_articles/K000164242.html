Description


  Some maintenance and workarounds require rebooting both VELOS system controllers. The two controllers share the chassis management and cluster control plane (OpenShift and etcd). A controller can take over from its peer only when its cluster services are running and the cluster is ready.
  A controller that has booted is not necessarily ready. If you fail over to a controller that is not ready, or reboot the only controller that is ready, the chassis loses its working control plane. That has the same effect as 
  rebooting both controllers at the same time, even when the reboots do not overlap. The result can be an extended outage that needs manual recovery.
  This article describes a rolling reboot that keeps one ready controller at every step.

  Environment


  - VELOS chassis with two system controllers
  - Chassis partitions and BIG-IP tenants, optionally in HA pairs with a peer chassis

  Cause
 

Not applicable (procedure guidance).

  Recommended Actions

  Rules for the whole procedure


  1. At every moment, at least one controller must be active and cluster-ready. Never reboot, reseat, or run go-standby on the only ready controller.
  2. Reboot only the standby controller. Fail over only to a standby controller that passes the readiness check.
  3. Run the readiness check before every step and again after it. Wait for the check to pass, not for a fixed time.
  4. One controller at a time. Do not power off a controller with the OBM and leave it in the chassis; keep it powered or remove it.
  5. Do not reboot to see whether it helps. If a check fails, stop, collect data, and contact F5 Support.

  Readiness check (see K000160334)


  Log in to each controller using its own management IP address and run:
    show system redundancy state
      Both controllers report the same current-active controller.
    show cluster
      cluster orchestration-manager cluster-initialized true
      cluster orchestration-manager cluster-ready true
      cluster orchestration-manager etcd-ha-running true
      All stages show Done.
      Both controllers show "In Cluster".
      summary-status "Openshift cluster is healthy, and all controllers and blades are ready."
    show system redundancy-details state hardware
      LOCAL HEALTHY is true for both controllers.
  If any item fails, or a command returns an error, the check fails. Read each field, not only the summary line.

  Procedure

  1. Prepare.
     a. Move tenant traffic to the peer chassis, using your HA-group and traffic-group procedure.
     b. Run the readiness check. It must pass on both controllers.
     c. Save the output from both controllers, and collect a qkview.
  2. Reboot the standby controller. From the floating management IP address:
       system reboot controllers controller standby
     The command takes the role ("active" or "standby"), not a controller number.
  3. Wait until the readiness check passes again: the rebooted controller is back "In Cluster", with cluster-ready true and etcd-ha-running true. Do not continue on a timer.
  4. Fail over to the controller you rebooted. From the floating management IP address:
       config
       system redundancy go-standby
     Your session to the floating IP address drops. Log in again after about 30 seconds.
  5. Run the readiness check. The rebooted controller must now be the current-active controller and pass every item. If it does not, stop and contact F5 Support. Do not reboot the other controller.
  6. Reboot the new standby controller (the original active controller). From the floating management IP address:
       system reboot controllers controller standby
     After step 4 the roles are swapped, so "standby" now refers to the other controller. Check which controller is standby (show system redundancy state) before you press Enter.
  7. Wait until the readiness check passes on both controllers.
  8. Return tenant traffic using your HA procedure, and confirm tenant HA state (tmsh show cm failover-status).

  What not to do


  - Do not run go-standby (step 4) because the rebooted controller has finished booting; wait for the readiness check.
  - Do not reboot the second controller (step 6) while the first is still not ready. Taking the only ready controller down has the same effect as rebooting both together.
  - Do not reboot both controllers at once unless F5 Support directs it.
  - Do not repeat a step "to try again" after a failed check.

  Additional Information


  - Controller role change messages in /var/log_controller/velos.log: "role change detected", "ConfD is now Active", "ConfD is now Standby".
  - Every CLI command, with the user and source address, is recorded in the controller audit log (/var/log_controller/audit.log). This is useful when reconstructing what happened during maintenance.
  - If a controller does not return to the cluster, see K000160334 and contact F5 Support before taking any further action on either controller.
