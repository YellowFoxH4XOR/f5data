Description

Site functionality is broken for Chrome browsers when a bot defense profile in use.

Observing a 307 redirect loop in developer tools.

Other browsers work fine.

Environment

  • Bot defense applied
  • Google Chrome
  • Cross-domain resource request

Cause

Bug ID 1036969: Chrome sometimes ignores cross-site bot-defense cookies

 

The issue happens because bot defense returns a 307 redirection to the client for the same URL with a TSPD_101_R0 cookie set. For example, when site-A requests a resource from site-B which uses bot defense protection, and this resource challenge is done by a 307 redirect, Chrome blocks site-B TSPD cookies due to the cookie SameSite setting; Chrome does not return this cookie in the follow-up request, resulting in further 307 redirections, and eventually a connection reset.

Chrome does not return the cookie because there is no SameSite attribute set. Recent versions of Chrome are defaulting to a SameSite value of Lax in this situation, which means the cookie can only be sent in top-level navigation, and not when following the 307 redirection.

Recommended Actions

There is no permanent fix for bug ID 1036969 at the time of this article's publication.

A workaround is to use an iRule to set the SameSite attribute on the cookie to none.

An example iRule is available here.

Following the instructions, this can be configured to set SameSite=none on the TSPD_101_R0 cookie at the HTTP_RESPONSE_RELEASE event.

An alternative workaround is to disable the redirection in bot defense:

tmsh modify sys db dosl7.proactive_defense_simple_redirect { value "disable" }
tmsh modify sys db dosl7.proactive_defense_simple_redirect_on_grace { value "disable" }

This is a system-wide change, and does reduce the effectiveness of bot defense.
