Description

Monitor traffic that is sourced from a tunnel interface might use an internal/local source IP of 127.1.1.x (depending on tmm). This can lead to monitor failing continually due to the node being monitored having no route back to the source IP used for the probe. In the case of the udp monitor, the monitor always succeeds. 

Environment

Originally seen scenario with IPsec interface configuration where tunnel had been configured with a floating self-ip but without a local self-ip (ie: traffic-group traffic-group-local-only). A monitor has been configured that will egress BIG-IP via the tunnel interface.

Cause

Due to the fact that there is no fixed self-ip, the monitor traffic is sourced by a tmm address 127.1.1.x (eg: 127.1.1.1).

This might be particularly damaging if a udp monitor is used. The udp monitor, will only mark the pool member down if it receives am icmp unreachable (indicating that the destination udp port is not available). If the traffic is sourced by a 127.1.1.x address then the icmp unreachable will never get returned and the monitor marks the pool member as a permanently up. See article K6143 for more details on the udp monitor.

In the instance of other monitor types (eg: tcp or icmp), the monitor will simply remain DOWN.

Recommended Actions

Configure the tunnel with a fixed self-ip. If a floating self-ip is used, then you might need to change from a /30 to a /29 subnet.

Additional Information

Confirmation that you hitting this issue can be made by making a suitable tcpdump. For example, filtering on the IP address of the pool member associated with the monitor.
