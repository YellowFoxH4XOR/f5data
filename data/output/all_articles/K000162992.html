K000162992: VELOS: Graceful Shutdown and Restart Using SSH When Console/AOM Access Is Unavailable

Type
Support Solution
Published
2026-08-20
Updated
2026-08-20
Applies to
  • VELOS Platforms
Source
https://my.f5.com/manage/s/article/K000162992

Description

This article documents an SSH-based graceful shutdown procedure. The procedure shuts down the VELOS nodes in the following order:

  1. All blades
  2. The standby system controller
  3. The active system controller
  4. After all nodes are shut down, remove and restore chassis power to restart the system.

Environment

  • Product: F5OS-C
  • Platform: VELOS chassis
  • Validated version: F5OS-C 1.8.2
  • Configuration: VELOS chassis with multiple blades and dual system controllers
  • Access requirement: SSH access to the controller floating IP or the active system controller IP


Cause

None


Answer/Recommended Actions

1. Set each tenant's running-state to Provisioned

From the partition CLI:

 config

 tenants tenant <tenant_name> config running-state provisioned

 commit

 exit

Wait for the tenant to fully shut down. Confirm with:

 show tenants tenant <tenant_name> state status

Expected result: status shows "Provisioned" (not "Running").

Repeat for all tenants in the partition, and for all partitions in the chassis if there is more than one.


2. Disable the chassis partition

From the system controller CLI (active controller, logged in as admin, or logged in as root and then use #(active-controller-bash)su admin):

 config

 partitions partition <partition_name> config disabled

 commit

 exit

Confirm with:

show partitions

Expected result: STATUS column shows "disabled" for both controllers under that partition name.

Repeat for all partitions if there is more than one.


3. Connect to the active system controller

From the management workstation, connect to the controller floating IP or the active system controller IP:

#(bash)ssh root@<controller-floating-IP-or-active-controller-IP>

Use the active system controller as the jump host for the remaining steps.


4. Shut down each blade

From the active system controller, shut down each blade individually. For example:

#(active-controller-bash)ssh blade-1

#(balde-1-bash)halt -p

Replace blade-1 with the actual blade name and repeat the operation for every blade.

Note: After halt -p is issued, the SSH session may stop responding and may not return to a prompt or disconnect automatically. This behavior was observed during the validation of this procedure and is expected.

When this occurs:

Close the unresponsive SSH session, or terminate it using the SSH escape sequence ~..

Reconnect to the active system controller.

Continue with the next blade.


5. Shut down the standby system controller

After all blades have been processed, connect to the standby system controller from the active system controller and issue:

#(active-controller-bash)ssh controller-2

#(standby-controller-bash)halt -p

Replace controller-2 with the actual standby system controller name.

The SSH session may become unresponsive after the command is issued. Close the session and reconnect to the active system controller.


6. Confirm that all other nodes are NotReady

On the active system controller, monitor the node states:

#(active-controller-bash)watch oc get nodes

Wait until all blades and the standby system controller show NotReady.

This is the critical safety checkpoint.

Do not shut down the active system controller until all other nodes show NotReady.

If a node does not transition to NotReady within a reasonable period, stop the procedure.

Investigate whether halt -p was executed on that node and contact F5 Support if necessary.


7. Shut down the active system controller

Only after all blades and the standby system controller show NotReady, run the following command on the active system controller:

#(active-controller-bash)halt -p

Because this command shuts down the system controller hosting the current SSH session, the session will disconnect or become unresponsive. This is expected.


8. Remove and restore chassis power

After all nodes have been shut down:

  1. Remove power from the entire VELOS chassis using the PDU or by disconnecting the chassis power cables.
  2. Wait approximately 30 seconds or longer to allow the system to fully discharge.
  3. Restore power to the entire chassis.
  4. Wait for the system controllers and blades to complete their startup sequence.

During laboratory validation on F5OS-C 1.8.2, the chassis automatically booted after power was restored without requiring manual AOM intervention.


9. Verify the system after startup

After the system has restarted, reconnect to a system controller and verify node status:

#(active-controller-bash)oc get nodes

Confirm that:

All system controllers and blades progressively return to Ready.

The expected nodes are present.

#(active-controller-bash)su admin

#(active-controller-confd)show cluster

#(active-controller-confd)show system health


10. Re-enable the chassis partition

From the system controller CLI:

 config

 partitions partition <partition_name> config enabled

 commit

 exit

Confirm with:

 show partitions

Expected result: STATUS column returns to "running-active" on the active controller and "running-standby" on the standby controller for that partition. Wait for this before proceeding to Step 11.

Repeat for all partitions if there is more than one.


11. Set each tenant's running-state back to Deployed

From the partition CLI:

 config

 tenants tenant <tenant_name> config running-state deployed

 commit

 exit

Confirm with:

 show tenants tenant <tenant_name> state status

Expected result: status transitions through "Starting" to "Running".

Repeat for all tenants in the partition, and for all partitions if there is more than one.
