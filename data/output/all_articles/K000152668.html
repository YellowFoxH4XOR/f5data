Description

If a security scanning tool (such as Tenable Nessus) sends unexpected HTTP CONNECT requests through an AWS Application Load Balancer to a BIG-IP LTM Virtual Server with an HTTP profile, subsequent legitimate HTTP traffic arriving at the virtual server may be pinned to a single pool member. This occurs because, after processing a CONNECT request, the BIG-IP treats all further data on that TCP connection as tunnelled binary data and forwards it to the same backend server, regardless of any load-balancing rules or URI-based iRule logic that may have been configured on the virtual server. No explicit error messages are generated, but application logs or backend server logs may show requests being handled by unexpected pool members.

Environment

  • BIG-IP LTM VE
  • Virtual Server with HTTP profile and iRule for URI-based pool selection
  • AWS Application Load Balancer (ALB) in front of BIG-IP
  • Security scanning tools or other clients sending HTTP CONNECT requests

Cause

The AWS ALB multiplexes client requests on a single TCP connection to the BIG-IP but does not properly support the HTTP CONNECT method. When a CONNECT request is received on a multiplexed TCP connection, the BIG-IP’s HTTP profile transitions that connection into a pass-through tunnel and the expectation is that only raw binary data will be received on the TCP connection henceforth . However, the ALB incorrectly continues to send multiplexed HTTP requests from additional clients over the same TCP connection. The BIG-IP forwards all subsequent data - which includes subsequent client HTTP multiplexed onto the same TCP connection by the AWS ALB - to the backend server selected for the original CONNECT request, bypassing BIG-IP load-balancing or iRule-based routing.

Recommended Actions

Since the CONNECT method is not handled properly by the AWS Load Balancer, you can add an iRule to your Virtual Server that blocks any incoming HTTP request using the CONNECT method:

when HTTP_REQUEST {
    if {[HTTP::method] eq "CONNECT"} {
        HTTP::respond 403 noserver Connection "close"
        event disable all
        return
   }
}
