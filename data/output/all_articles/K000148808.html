K000148808: Enforcing AES encryption when kerberos SSO delegation account is a computer account

Description

The recommended type of Active Directory account for an F5 kerberos delegation account is a user account.

However, for historical reasons, you may have a delegation account which is a computer account type.

Such account works without much trouble while RC4 encryption is still allowed on Active Directory.

Enforcing AES128/256 on the machine account will cause such error under /var/log/apm:

Oct 10 11:55:23 bigip1 err websso.3[16544]: 014d0056:3: /Common/AP_EXAMPLE:Common:ce4e67fe:Kerberos: can't decrypt S4U2Self ticket for user test@EXAMPLE.COM - Decrypt integrity check failed (-1765328353)

The cause is the same as what is described in K58414402 and bug ID 564482.

However there is an extra caveat to watch for as you cannot define the userPrincipalName attribute for a computer account the same way you do it for a user account.

Environment

  • kerberos SSO
  • delegation account is a computer account
  • AES encryption is enforced on the delegation account

Cause

AES is using userPrincipalName value and host (instead of http for a user account type) in the salt so it must match on both sides.

Recommended Actions

  • on the BIG-IP, modify kerberos SSO profile and use the following:
    • Account Name: host/delegation.example.com
    • REALM: EXAMPLE.COM
  • On Active Directory, using PowerShell, set a userPrincipalName attribute value for the Computer account (such attribute is empty by default):

Set-ADComputer delegation -add @{"userPrincipalName"="host/delegation.example.com@example.com"}

  • On Active Directory, using PowerShell, make sure SPN is is set properly for the Computer account:

setspn -s host/delegation.example.com delegation

Note: In this example, delegation is the name of the computer account
