Abstract

The BIG-IP ASM system provides many options for building security policies to safeguard your web applications. An essential feature for improving security in BIG-IP ASM policies is "entities." Presuming you use the Policy Builder feature to automatically build your policy, the decisions you make about configuring “learning” for “explicit” entities are particularly important. If you are new to these concepts or want to ensure you’re making the best decisions about using entities in your security policies, use this article to get an overview of entities, how they work, and how to add them to policies.

Description

Making the right choice: using and configuring entities

BIG-IP ASM is an advanced web application firewall (WAF) with deep capabilities. If you find the extensive selection of options available from WAFs complicated, you are in good company. With so many features, how can you be sure you're making the right choices for your security policies?

Among your selections, entities are important because they supply data to the BIG-IP ASM automatic policy building feature. When you use, configure, and properly "tune" entities, you help BIG-IP ASM build policies with the right level of security and maintenance responsibilities to match your needs. On the other hand, when you inaccurately configure entities, and particularly explicit entity learning settings for Policy Builder, you risk runaway policy complexity.

Entities work in conjunction with other BIG-IP ASM security checks, such as attack signatures, which look for patterns that match malicious traffic, and meta character checks. They facilitate rigorous examination and control of HTTP requests being made to your application.

When the BIG-IP ASM system receives an HTTP request, it examines and identifies its attributes, such as URLs, parameters, and file types. An entity specifies constraints and requirements for one type of HTTP request attribute. To determine whether a request is legal and can pass through to your application, the system compares the values of request attributes to entities that correspond to their type, such as a specific URL being compared to a URL entity.

For an HTTP request to be legal, it must be Request for Comment (RFC) compliant, and its attribute values must:

  1. Not match any "disallowed" entities of their type. These entities describe characteristics you want to block from your application.
  2. Match at least one "allowed" entity of their type. These entities describe characteristics that can pass through to your application.
  3. Match any properties defined for an allowed entity. These properties are additional checks on attribute values that provide further requirements for requests to access your application. For example, you can stipulate that the allowed parameter accountnumber must have an integer value with a maximum length of 16 digits.

You don't have to create and configure entities yourself. There are default entities, which allow all legal attribute values in HTTP requests. You can configure them to provide security, but when you want to spend less time maintaining your security policy, keeping the default entities is a valid approach.

When you have the BIG-IP ASM system build your security policy automatically using Policy Builder, including adding entities, you configure the level of security—and therefore, the amount of entities—you want: the maximum, minimum, or somewhere in between. While your selection determines how strict your security policy is, it also determines the level of maintenance your policy requires: the more entities, the more maintenance.

Therefore, when you’re deciding on your policy-building approach, you must weigh the level of security your application needs against the maintenance that level of security requires. When you need more security, expect to expend more effort maintaining many entities to ensure your security policy is functioning properly.

HTTP request and response attributes

The BIG-IP ASM system can validate the following HTTP request and response attributes using entities:

  • File types
  • URLs
  • Parameters
  • Cookies
  • Redirection domains

An introduction to each one follows.

File types

Though file types, such as GIF and PDF, are not defined as a URL component in the HTTP standard (not to be confused with Content-Types, which are), file name extensions contained in URLs have significant meaning, and the BIG-IP ASM system can use them for application security.

For most web applications, file names on the file system commonly include file name extensions that correspond directly to URLs. That is, the file system namespace typically corresponds to the URL namespace for the components of a web application.

For many web servers, you supply a filename expression that the configuration uses to pick a handler and adjust behavior for a file type, such as the Apache directives AddType, Files, and FilesMatch. For example, you can configure the server to respond to requests for URLs ending in .php using the PHP module instead of returning the .php file source code to browsers.

Because the BIG-IP ASM system recognizes file extensions in a URL, it can use this information to verify a request by ensuring that the extension matches a file type entity in the security policy before allowing requests to reach your application. Similarly, you can configure the system to identify and disallow problematic or unexpected file types from proceeding to your application.

URLs

The BIG-IP ASM system validates URLs that appear in the first line of an HTTP request. The system views URLs differently than standard URLs that appear in browser address boxes and HTML links. When matching URLs to URL entities, the system does not consider the following portions of a traditional URL:

  • Scheme, such as HTTP or HTTPS
  • Hostname
  • Query data

For example, given a request for a webpage, the BIG-IP ASM system renders it as shown below and then evaluates it against URL entities, which use the same format, for a match.

Parameters

Parameters are the primary means by which browsers pass user input into a web application, enabling users to perform actions like writing to a database. Consequently, parameters are one of the most common targets for application attacks by hackers.

In HTTP requests, parameters are name and value pairs, such as param1=value1. You can send parameters in two types of requests: GET and POST.

GET requests

In GET requests, parameters are in the request line, as demonstrated in the following URL:

  • /processTransaction?account=8675309&amount=12.99

In POST requests, parameters are in the request body. In this case, the system uses the appropriate parsers to examine the structured data types, such as JSON and XML, and validates the parameter values the data contains.

Cookies

Cookies have made their way into everyday conversation and most users are familiar with them. They are used for several purposes, including tracking users. Applications use persistent cookies to track users for longer periods of time, while they use session cookies to track typically brief, individual user interactions. For example, a session cookie can be a random string that uniquely identifies all HTTP requests associated with a user's requests.

Generally, there are numerous cookies set and sent in HTTP responses and requests. Cookies are commonly set by Set-Cookie headers in HTTP responses generated by server applications and sent by browsers to applications in the Cookie header of HTTP requests.

Redirection domains

Applications often send browsers to other URLs using the HTTP redirect mechanism, also known as 301 and 302 redirects. A redirection domain occurs when a server application generates an HTTP redirect response that includes a URL with a fully-qualified domain name (FQDN) or IP address in the Location header.

However, redirecting users to URLs outside the current application domain introduces security risks. The BIG-IP ASM system can examine and track domains used in application redirects.

For more information, refer to the Mitigating Open Redirects chapter in BIG-IP Application Security Manager: Implementations

Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

Entities

In many ways, entities are the backbone of your security policy. There are five types of entities, which correspond to each type of HTTP request attribute above. You can have multiple entities of every type. The system compares the value of each attribute passing through to your application against the entities of the corresponding type. Then it determines whether those attributes that exactly match an entity or entity pattern (wildcard) can access your application, based on the entity’s rules.

When the BIG-IP ASM system automatically builds your security policy, you can configure how, and to what extent, the system adds entities. This decision has significant consequences because, in the end, you want a policy that has the appropriate balance of security and maintainability. That is, you want:

  • The appropriate amount of entities to protect a specific application.
  • To avoid the unnecessary proliferation of entities.
  • To augment generic protection mechanisms, like attack signatures, when you need the highest levels of protection.

With that in mind, it's essential you are familiar with the following concepts, because they govern how entities are automatically added and enforced in your policy:

  • Explicit entities
  • Wildcards
  • Allowed and disallowed entities
  • Positive security
  • Policy learning

Explicit entities

An explicit entity defines a specific instance of a type of entity. The system compares that instance against the values of attributes of the corresponding type that are passing through in traffic. You can either allow or disallow the attribute values that match the explicit entity instance. Examples of explicit entities are in the following table.

Wildcards

A wildcard is a pattern, or expression, used in entities to identify multiple HTTP attributes that you want to allow or disallow in requests to your application. HTTP request attributes with values that match a wildcard are verified against that entity.

The BIG-IP ASM system uses an asterisk (*) to indicate a wildcard expression that matches all characters in a request or response attribute. The system also uses other shell-style wildcard characters, such as the question mark (?), which you use to match any single character in an attribute. However, this article only discusses wildcards that use the asterisk. For more information about wildcard syntax, refer to the Adding File Types to a Security Policy chapter of the BIG-IP Application Security Manager: Implementations manual.

Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

When you or the system uses an asterisk by itself, without providing an accompanying expression, it indicates all HTTP attributes of that type. This is sometimes called the pure wildcard. All entities are initially set to the pure wildcard by default.

Examples of wildcard entities using the asterisk are in the following table.

Entity properties

Entities also have properties, or additional checks, that you can enable and that attribute values must meet to be allowed by your security policy. These checks are on a variety of characteristics, such as URL or query string length and whether an attribute's value uses alphanumeric or integer formatting. For more information about the properties available for each entity type, refer to the Appendix.

Verifying request attribute values against entity properties (in addition to the entities themselves) is one way you can “tune" a security policy. When you want to "tighten" a policy, or make it more secure, you enable entity properties. When you want to "loosen" a policy, or reduce how strict it is, you disable or do not use entity properties.

The tighter the policy, the more false-positive violations it is likely to encounter, and the more time you spend reviewing them and maintaining your policy. The looser your policy, the fewer violations your policy is likely to encounter, and the less time you spend maintaining it. Your goal when refining your policy is to find the right balance to meet your security needs and maintenance capabilities.

Verifying HTTP request attributes using entities and wildcards

The BIG-IP ASM system uses order and specificity to verify attribute values. The system identifies the appropriate attributes for evaluation within an HTTP request and then determines the entity that most closely matches each attribute.

The process of verifying entities and entity properties is part of the verification process, described below.

  1. Identify the URL in the request.
    • Match it to the most specific allowed or disallowed URL entity.
    • Check for and enforce any entity properties, such as limits on URL length.
  2. Identify the file type (or that there is no file extension) in the request.
    • Match it to the most specific allowed or disallowed file type entity.
    • Check for and enforce any entity properties, such as exceeding the maximum file size.
  3. Identify the parameters in the request and parse them into a list.
    • Match each to the most specific parameter entity.
    • Check for and enforce any entity properties, such as requiring that the parameter be a particular data type, like alphanumeric, integer, or decimal.
  4. Identify the cookies in the request and parse them into a list.
    • Match each to the most specific allowed cookie entity.
    • Check for and enforce any entity properties, such as identifying a default attack signature that has been overridden.
  5. Identify the redirect domain in the response.
    • Match it to an allowed, explicit redirection domain entity, unless the default wildcard is still present.

      Note: Redirection domain entities do not have properties.

When an attribute value matches multiple entities, the system does not enforce them all; it matches the most specific entity first and enforces it. Therefore, the system only verifies requests against wildcard entities when it doesn’t find a more specific entity first.

Security models: positive vs. negative security

Positive and negative security models are opposite ends of the security spectrum. Positive security uses whitelists to define what is allowed and rejects everything else. This approach results in large, granular configurations that provide strict security. Conversely, negative security uses deny lists to define what is prohibited and allows everything else. This approach results in simplified configurations that provide looser security.

Positive security

In the BIG-IP ASM system, positive security is tightest when you use comprehensive whitelists of well-defined explicit entities. The system only allows requests that conform to your explicit entities and disallows those that don't.

When you define an explicit entity, configure all its available properties so that you carefully specify the attribute values allowed by your security policy. This makes security checks as precise as possible, because the system can use these details to tighten or relax the policy for each attribute, when necessary. On the other hand, if you simply use a generic wildcard that most attribute values match, your security is much looser.

The primary disadvantage to positive security is its high cost in maintenance. Complex security policies are sensitive to application changes. When you change or update an application, you must also update the security policy; otherwise, it will trigger false-positive security violations.

Negative security

A common approach to negative security combines entities with other available BIG-IP ASM protection mechanisms, namely attack signatures and meta character checks. You can block malicious URLs and file types by adding them as disallowed, explicit entities in your policies. For example, you can add the PL, PY, and SH file types as disallowed entities to ensure that requests are unable to execute any Perl, Python, or Unix shell scripts that you or others may have inadvertently left on the file system. Similarly, you can disallow problematic meta characters in URLs, parameter names, headers, and other request attributes.

You can also enable attack signatures, which use pattern matching to identify attacks on your application and then trigger violations. They cover a broad range of threats, provide fundamental protection, and are regularly updated by the F5 threat research and intelligence team.

Better together

In practice, the most efficient and precise methods for building security policies use a mix of both positive and negative security simultaneously. A mature security policy with a positive security approach is likely to detect malicious requests using multiple techniques, including:

  • Wildcard entities in combination with explicit entities for attributes like URLs.
  • Allowed explicit URL entities in combination with attack signatures.

Policy Builder, Automatic learning mode, and positive security

Policy Builder

Policy Builder is a BIG-IP ASM feature that can build security policies automatically using “learning.” When you set Policy Builder to Automatic learning mode, the system identifies legitimate application usage and builds your policy—including adding explicit entities—based on a statistical analysis of your traffic and the intended behavior of your application.

Automatic learning mode

Building security policies automatically using learning requires an initial policy development period of several days, during which the system prevents the policy from blocking genuine requests while it is still incomplete and inaccurate. You use Transparent enforcement mode or the Staged status for this period to prevent false-positive violations.

As part of the learning process, when Policy Builder observes that it no longer needs to adjust entities or your security policy, the system determines that it is ready to be enforced and changes the mode or status to Blocking or Enforced, respectively.

Positive security and Automatic learning mode

Automatic learning mode is very handy for incorporating positive security into your policy, because the system adds comprehensive lists of explicit entities to your policy during Transparent enforcement mode or staging.

By default, the system initially uses the pure wildcard (*) for each entity. Depending on your learning settings, you have the option to manually remove wildcards, or the system automatically removes them after the learning period, when it enforces the policy. In either case, removing wildcards is a significant step that you must consider carefully.

Automatically adding explicit entities with learning settings

A security policy with many explicit entities is difficult to maintain, so you may want to control their number. In versions of BIG-IP ASM 13.0.0 and later, when you use Policy Builder in Automatic learning mode, you have more options for controlling the logic the system uses to add explicit entities to your policy. These options, available on the Learning and Blocking page of the Configuration utility, are called learning settings, and the setting you choose impacts both the strength of your policy and your maintenance responsibilities.

Using learning settings to add explicit file type entities

When you want the BIG-IP ASM system to automatically add explicit file type entities to your policy using Policy Builder in Automatic learning mode, use the following insights to help you select the right learning setting for your needs.

Learning settingConsiderations
Always
  • Intended for a whitelist of allowed file types.
  • In a short period of time, the system generates a comprehensive whitelist of no more than 30 file types for a typical PHP application, such as .php, .jpg, .gif, .js, .xss, .html, and no_ext.
  • When there are minor updates—but no major updates, such as a new content management platform—the file types list does not change.
  • Policy Builder ultimately removes the default wildcard for allowed file types, resulting in a whitelist approach.
Selective
  • Keeps policy maintenance as simple as possible, but explicit file type entities aren't typically high maintenance.
  • Because this setting retains the default wildcard, the only value in using this setting is in the tightened security that comes from the system enforcing entity properties for the wildcard, such as limits on URL and request length.
Compact
  • Used to reduce policy complexity and simplify maintenance, this setting specifies the maximum number of explicit file type entities that Policy Builder can learn and add to the policy.
  • Because you cannot remove the default wildcard, the value of adding explicit entities is questionable.
Never
  • Minimizes policy complexity by exclusively using the default wildcard entity.
  • When a request triggers a false-positive violation against the wildcard entity, it’s typically related to entity properties, such as the length of a URL, request, query string, or POST data. Keep in mind that modifying the wildcard properties for a false-positive violation relaxes those security checks for all requests.

Using learning settings to add explicit parameter entities

When you want the BIG-IP ASM system to automatically add explicit parameter entities to your policy using Policy Builder in Automatic learning mode, use the following insights to help you select the right learning setting for your needs.

Learning settingConsiderations
Always*
  • Intended for a comprehensive whitelist of parameters.
  • F5 discourages removing the default wildcard because doing so makes the policy very sensitive to application updates. For example, a new form field on an existing page causes a violation when you don’t add it to the policy first.
  • It's acceptable to keep the wildcard because the system protects against known exploits using attack signatures for parameters and meta character checks on parameter values.
  • The system also reduces the risk of unexpected exploits, such as parameter values that don't trigger attack signatures, using policy tightening. During the policy building process, the system learns to recognize and enforce constraints on parameter values, including type, content value, and size.
Selective*
  • Minimizes policy complexity.
  • Enables the default wildcard entity to enforce as many of its settings as possible, such as selected attack signatures for parameters.
  • When false-positive violations occur—typically triggered by the wildcard entity’s properties—the system adds explicit entities to disable them. Using explicit entities, the system can learn length characteristics for the parameter value, thereby tightening the policy.
  • Parameters that match the default wildcard don’t benefit from tightening, leaving potentially critical parameters exposed.
  • Compact mode is a better choice when you want to add tightening for critical parameters, but they are unlikely to trigger false-positive violations against the default wildcard and result in the addition of an explicit entity.
Compact
  • Retains the default wildcard, so new parameters don't cause false-positive violations (though it’s still possible to encounter attack signature violations on legitimate values).
  • Of all the entity types, the best use of this setting is with parameters. The number of parameter entities is limited, reducing maintenance overhead.
  • You can still tighten explicit parameter entities.
Never
  • Uses only the default wildcard entity.
  • False-positive violations against a parameter the application uses—caused by, for example, attack signatures or meta characters that are not allowed in its value—require the system to loosen the default wildcard.
  • When you loosen your policy for false-positive violations in one parameter, it is loosened for all parameters. Because parameters are a favorite target for hackers, F5 does not recommend this approach.

* You can only use the Policy Builder Learn Dynamic Parameters setting in these modes.

Using learning settings to add explicit cookie entities

When you want the BIG-IP ASM system to automatically add explicit cookie entities to your policy using Policy Builder in Automatic learning mode, use the following insights to help you select the right learning setting for your needs.

Learning settingConsiderations
Selective (default setting)
  • You cannot remove the default wildcard, because new cookies often appear in application requests, even though the application has not changed. Consequently, the system validates all cookies in requests using attack signatures for cookies.
  • When a cookie triggers a false-positive violation against a cookie attack signature, the system adds an explicit entity for the cookie, thereby disabling the attack signature. Meanwhile, the default cookie entity continues to handle all cookies, (except those that match explicit entities) using all the selected cookie attack signatures.
Never
  • Uses only the default wildcard entity.
  • Any false-positive violations against an attack signature requires the system to loosen the default wildcard entity by disabling the signature. In so doing you lose the benefit of protecting all other cookies with that signature.

Using learning settings to add explicit redirect domain entities

When you want the BIG-IP ASM system to automatically add explicit redirect domain entities to your policy using Policy Builder in Automatic learning mode, use the following insights to help you select the right learning setting for your needs.

Learning settingConsiderations
Always (default setting)
  • This setting is valuable because, after the learning period, you can see the domains to which your application is redirecting users.
  • Redirects are typically to a small number of sites within your company's namespace, in which case you can accept the learning suggestions or manually add your domain name and use the option to include sub-domains.
Never
  • Some applications regularly redirect users to arbitrary or numerous external domains. Use this setting when you don't want to maintain a comprehensive whitelist of those domains.

Collapsing

You use the Always learning setting when you want a positive security approach and explicit entities automatically added to your policy. However, Policy Builder can quickly add hundreds or thousands of entities to your policy, which are difficult to maintain. One solution is the “collapsing” feature.

When you have numerous explicit entities that share the same data type settings, you can use an allowed wildcard in their place and then remove the explicit entities, thereby collapsing them. You can use collapsing with URL, parameter, and cookie entities.

For example, consider a case in which you have a mapping application with a checklist of global cities. After the user selects their cities, the application draws a map illustrating the locations of the cities. The selected cities are sent in a request as parameters: city1, city2, and city3. If you add each of these to your policy as an explicit parameter entity, the entities have the same data type settings. When you use collapsing, in place of the entities, you add one wildcard, city*, that includes the data type settings.

Strategies

Below are insights and best practices to help you make the best decisions about using entities in your security policies.

Using file type entities

Allowed, “no extension” (no_ext) file type entity

URLs that lack a filename extension are common in modern web applications. Some examples include /LoginServlet and paths to directories, like /products/. The BIG-IP ASM system often maps filename extensions in URLs to a file on the file system, but in these cases, there is no match. When the system validates requests like these, it uses the no_ext file type entity to prevent security policy violations.

Tip

  • While it is not required to have an allowed, no_ext file type entity, in practice, you need one for nearly all applications, because a request for the URL that contains only the forward slash (/) maps to the no_ext file type entity.

Allowed file type entities

You increase application protection when you use the properties available with file type entities. For example, consider a case in which you only allow requests for .gif files. When you also configure the Allowed Method property, you can further specify that requests use the GET method.

Entity properties also provide multiple layers of protection. For example, suppose you or Policy Builder sets the URL Length property for .gif files to a limit of 40 bytes, and you store image files at the top of your directory, such as /images/. At the same time, there are some images not currently intended for public consumption that reside in a more deeply nested location, such as /pendingcorporatemergersiteassets/images/ournewcompanylogo.gif. In this situation, the URL Length property protects against accidental access to the nested files, because the length of their URLs is more than 60 bytes.

Tip

  • Because of the no_ext entity, a positive security approach for file types doesn't offer significant protection from attacks. The system can’t identify the file type of each request, nor can it precisely check a request that is matched against the no_ext entity. For example, hackers may anticipate unpublished URLs, and whitelists are ineffective.

Disallowed file type entities

In older versions of the BIG-IP ASM system, you manually add disallowed file types, requiring you to know which ones are problematic. However, in more recent releases, Policy Builder in Automatic learning mode automatically adds candidates to the disallowed file types list based on observation of application traffic.

Tip

  • Using a disallowed file type list, or a deny list, is easy and provides maximum value with minimal effort.

Using URL entities

Allowed URL entities

You can use allowed URL entities to institute a positive security approach. After adding entities and removing the default wildcard, when a request URL does not match either an explicit or wildcard URL entity, it triggers a policy violation.

An approach that uses only whitelisting and Policy Builder in Always learning mode is attractive, because it has the potential to:

  • Significantly reduce the attack surface.
  • Protect against misconfiguration.
  • Protect against accidental unintended availability of URLs.

However, you must also consider the maintenance requirements of this approach. Updates to an application introduce new pages and URLs.

For example, an online banking service may be an appropriate use of a whitelisting approach: it requires very tight security, rarely changes, and has few URLs. Presumably, content like style sheets and images are served from a different hostname or content delivery network (CDN).

On the other hand, a mid- to large-size corporate home page that has frequent content updates from a content management system (CMS) used by active editors and no significant sensitive transactional elements is a poor candidate for URL whitelisting. First, the added security of a strictly whitelisting approach is not warranted by the sensitivity of the application.

Additionally, by the end of the staging period, the policy has numerous explicit URL entities added by Policy Builder, while the CMS continues to steadily introduce new URLs and, likely, trigger false-positive violations. Avoiding the false positives is a maintenance challenge, requiring very careful coordination of content and security policy updates.

Another use for allowed URL entities is fine-tuning the enforcement of requests, such as:

  • Tightening or overriding attack signature checking for a URL.
  • Tightening or overriding meta character checks for a URL.
  • Specifying request body content types, such as whether a URL expects form or JSON data.

Tips

  • A positive security approach that uses whitelisting is attractive because it is very strict; however, carefully weigh these advantages against the cost of addressing false-positive violations that arise with application changes and resulting new URLs.
  • You may be able to use the system’s negative security capabilities, including attack signatures and meta character checks, in place of a whitelisting approach. They are very effective in detecting requests for content you don’t want accessed, such as administrative URLs.

Disallowed URL entities

There are situations, like the ones below, when you need to prevent users from accessing specific pages. You or the system can do so by adding them to the disallowed URLs list.

  • There are site assets you want accessible to internal testers but not users, such as /newProductUrl/.
  • You have a CMS login and associated pages that you want accessible only to administrators, such as /cms/login.php. Though administrative URLs are typically detected by BIG-IP ASM validation signatures, you may want the certainty of a disallowed URL.

Tip

  • Consider that disallowed URLs entities cannot contain wildcards, so you must individually add all URLs that you want to explicitly block.

Using allowed parameter entities

Because manipulation of parameter values represents a significant portion of known web application attacks, the BIG-IP ASM system includes robust positive and negative security capabilities for validating parameter values, including the following:

  • Positive security—allowed parameter entities, added by you or Policy Builder, with properties that control value length and type, such as integer or alphanumeric.
  • Negative security—attack signatures, which examine parameter values, and meta character checks.

The system does not use disallowed parameter entities, because parameters often correspond to HTML form field names or hidden fields that developers often change in application updates. It is possible, but uncommon and not recommended, to add a comprehensive list of explicit parameter entities with no wildcards, thereby having the system trigger a violation when a request parameter doesn't match one of the explicit entities. You should only use this approach with applications that rarely change.

Tips

  • The introduction of a new parameter in an HTTP request is unlikely to compromise your application in an unexpected way. On the contrary, your application is apt to ignore an extra parameter for which it isn't specifically looking, such as input from a form.

  • Because the most likely attack scenario is one that targets a legitimate parameter allowed by your policy, removing the default wildcard from parameter entities provides little benefit. You get the most value from adjusting entity properties, such as tightening Maximum Length and Parameter Value Type, and loosening properties when needed to avoid false-positive violations.

    For example, consider a security policy that has two allowed parameter entities: the default wildcard and accountnumber. When you configure accountnumber entity properties to restrict the value type, data type, and length of the parameters that match it, you're using a positive security approach for a specific parameter but not enforcing a whitelisting approach for all parameters in HTTP requests.

    Therefore, the parameter values that appear in application traffic are consistent with the constraints defined in the policy during the policy learning process, but new parameters can still pass through in traffic. This approach minimizes the risk of false-positive violations, while significantly protecting against parameter attacks. For more information about parameter entity properties, see the Appendix.

  • The possibility does exist, though contrary to secure application coding best practices, that a developer uses parameters to access unreleased application behavior or a back door that they create. When there is the possibility of this scenario, a comprehensive parameter entity whitelist is valuable.

Note: There are many special scenarios for parameters, including URL-specific, flow, sensitive, navigation, dynamic content value (DCV), and dynamic parameter name parameters. However, the focus of this article is simply allowed parameter entities, which do or do not include a wildcard, and security policies that enforce them on parameter values. For more information about parameters, refer to the Adding Entities to a Security Policy chapter of the BIG-IP Application Security Manager: Implementations manual.

Using allowed cookie entities

You want to add cookie entities to your security policy that match the cookies your application uses. You can configure your policy to ignore certain recognized cookie headers in requests, such as those that can legally change on the client side, by adding them as allowed cookie entities. You can also prevent changes to certain cookies, such as session-related cookies set by the application, by adding them as "enforced" cookie entities.

Because you cannot delete the default wildcard entity, explicit cookie entities have two important roles:

  • Overriding and disabling false-positive violations triggered by attack signatures for cookies.
  • Validating that cookie values set by the server aren't manipulated by the user, using enforced cookies.

The system doesn't use whitelists of explicit cookie entities, because cookies are easily and frequently introduced by applications within a domain. For example, cookies can be set with a domain, such as F5.com. All applications within that domain, such as F5.com, devcentral.F5.com, and support.F5.com, can set cookies with that domain and browsers send them within the application.

Using allowed redirect domain entities

Because retaining the default wildcard entity leaves your application open to a redirect vulnerability, and there are no redirect domain entity properties that provide additional security checks, it's generally recommended to have the system learn all redirection domains, and then remove the default wildcard entity to further minimize risk.

One exception is certain, specialized applications that commonly redirect users to many external domains. These applications are poor candidates for a whitelisting approach to redirection protection.

Conclusion

 

When you are new to WAFs, application security, or the BIG-IP ASM system, and you are faced with the challenge of building and maintaining a security policy, you may be tempted to enable the maximum level of security, such as having your policy learn all explicit entities for your application. While this is the right approach for some applications, F5 does not recommend it for the majority, because it can lead to a policy that is unwieldy or must be abandoned.

Alternatively, when you learn the core entity types and how the BIG-IP ASM system uses them to enforce application security, you can correctly configure Policy Builder and entity learning for your application, taking into consideration your threat profile, risk, rate of change, and resources available for policy maintenance.

When you start using the BIG-IP ASM system, learn to walk before you run. Unless you simply must use maximum security, start slowly by creating minimal policies.
