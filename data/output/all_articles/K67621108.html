Description

The following is an overview of all the configuration references you can modify in your override values file for an Aspen Mesh installation.

Environment

  • Kuberntes: 1.17x,1.18.x,1.19.x,1.20.x
  • Aspen Mesh: 1.6.x, 1.9.x 

Cause

None

Recommended Actions

If you want to customize your Aspen Mesh installation, it is recommended to create your own override values file. The customization could change:

  • Set the name of your cluster for reporting via Aspen Mesh dashboard.
  • Configure the authentication mode for users within your organization to access the Aspen Mesh dashboard.
  • Enable, disable components.
  • Adjust resource request and limits and scaling.
  • Configure global settings for the mesh etc.

It is highly recommended to store your override values file in a source control repository like Git where your configuration resources are kept for your cluster.

The global values file is located under the aspen-mesh-<version.tag> directory following this path:

+-- manifests
¦   +-- charts
¦       +-- istio-control
¦       ¦   +-- istio-discovery
¦       ¦       +-- values.yaml

Important: Do not modify the default values.yaml file, take it only as a reference on which values can be modified but these changes will be always in your override values file.

If you want to know more about Helm charts and subcharts, please check the Helm official documentation.

In this article we will explore what components and fields you could change to override your Aspen Mesh configuration, since the default values file is extensive, we would only cover the basics, if you need additional information, please reach the Aspen Mesh Support team.

  1. Pilot

    All the settings for pilot discovery (istiod controlplane) values. You can adjust the resources consumption, image usage, registry, etc.

    Its not common modify these values, but as an example you could override the autoscale min and max in case you need a basic installation:

    # Default install 
    pilot:
      autoscaleEnabled: true
      autoscaleMin: 2
      autoscaleMax: 5
      replicaCount: 1
      rollingMaxSurge: 100%
      rollingMaxUnavailable: 25%    		# Override values
    pilot:
      autoscaleEnabled: true
      autoscaleMin: 1
      autoscaleMax: 2
      replicaCount: 1
      rollingMaxSurge: 100%
      rollingMaxUnavailable: 25%

  2. Aspen-mesh-controlplane

    The Aspen Mesh controlplane runs in your Kubernetes cluster and evaluates your metrics and cluster configuration to provide insights about the mesh to your Aspen-mesh-dashboard

    On the control plane settings, you can override the cluster name of your installation as well resources, image, and user authentication.

    # Default install 
    aspen-mesh-controlplane:
      enabled: true
      image: controlplane-1.9.1-am3
      modelruntimeImage: modelruntime-1.9.1-am3

      replicaCount: 2

      clusterId: demo

      userAuth:
        # "type" can be none, jwt or oauthOpenshift.  Configure details for your chosen type below, others are ignored.
        type: jwt    		# Override values
    aspen-mesh-controlplane:
      enabled: true
      image: controlplane-1.9.1-am3
      modelruntimeImage: modelruntime-1.9.1-am3

      replicaCount: 2

      clusterId: demo

      userAuth:
        # "type" can be none, jwt or oauthOpenshift.  Configure details for your chosen type below, others are ignored.
        type: none

  3. Aspen-mesh-secure-ingress

    Aspen Mesh Secure Ingress configures ingress into your cluster securely and takes the complexity out of Istio configuration. Designed from the ground up with two personae, the platform operator and the application developer, Secure Ingress allows finer-grained control on your ingress.

    Using the secure ingress depends of your use case but is always installed as part of your Aspen Mesh install, if you want to know more about secure ingress follow this guide.

    When secure ingress is enabled you need to provide an email if you want to use let’s encrypt certificates otherwise you can leave in blank if you will provide your own certificates.

    # Default install 
    aspen-mesh-secure-ingress:
      enabled: true
      image: secure-ingress-1.9.1-am1
      # Email to use for Let's Encrypt registra-tion (used for certificate expiry notices)
      # Leave blank ("") if you wish to manage your own TLS certificates.
      lets-encrypt-email: ""
      resources: {}
      externalDnsAnnota-tion: "policy.aspenmesh.io/externaldns"
      externalDnsEnabled: false    		# Override values
    aspen-mesh-secure-ingress:
      enabled: false

  4. Aspen-mesh-metrics-collector

    Aspen-mesh-metrics-collector will collect any available metrics in Istio and the sidecars and store them in a persistent volume.

    These metrics will be used later for our aspen-mesh-dashboard to provide insights about the health of the workloads and the status of your mesh.

    The default configuration includes just resources limits and request, and alertmanager image to use in conjunction with the metrics-collector, if you found that default resources are not enough, you can increase them through the override values file:

    # Default install 
    aspen-mesh-metrics-collector:
      serviceImage: metrics-collector-service-1.9.1-am3
      server:
        serviceResources:
          requests:
            memory: "512Mi"
            cpu: "500m"
          limits:
            memory: "512Mi"
            cpu: "500m"
      alertmanagerImage: alertmanager-1.9.1-am3
      configmapReloadImage: configmap-reloader-1.9.1-am3    		# Override values
    aspen-mesh-metrics-collector:
      serviceImage: metrics-collector-service-1.9.1-am3
      server:
        serviceResources:
          requests:
            memory: "512Mi"
            cpu: "500m"
          limits:
            memory: "2048Mi"
            cpu: "1000m"
      alertmanagerImage: alertmanager-1.9.1-am3
      configmapReloadImage: configmap-reloader-1.9.1-am3

  5. Citadel

    Aspen Mesh ships with the secure Secret Discovery Service (SDS) mode enabled in release 1.6 and higher as the primary means for provisioning TLS credentials (keys and certificates) for workloads within the mesh. This SDS provisioning system works well in cases where the sidecar proxies can be injected into the workload pods but can be challenging for legacy and non-Kubernetes native workloads

    For those non-kubernetes and legacy workloads, Citadel generates Kubernetes secrets with TLS credentials and automatically manages the lifecycle and rotation of these credentials.

    By default, this feature is off as SDS is a better option, but if your use case includes this case where your mesh needs to communicate with legacy or non-kubernetes workloads, enabling Citadel might be the solution.

    Important: Citadel need a root CA to sign new workloads certificates, ensure you have this installed in your Aspen Mesh install following this guide.

    # Default install 
    citadel:
      # to enable this feature you must setup a root CA in the istio-system namespace
      enabled: false    		# Override values
    citadel:
      # to enable this feature you must setup a root CA in the istio-system namespace
      enabled: true

  6. Jaeger

    Jaeger or tracing will capture all the traces generated by envoy sidecars automatically, this includes: HTTP1.1, HTTP/2 and GRPC network requests.

    By default, tracing is not enabled so you need to specify in your override files that you will be enabling tracing and provide the configuration.

    Additionally, you need to specify under the global field the address where sidecars will report all the traces (the address is the Kubernetes service name of the jaeger collector)

    Common changes to the configuration include the persistent volume size, traceTtl and the samplingConfig.

    Important: Do not enable this feature unless advised by Aspen Mesh support.

    # Default install # Override values
    global:
      tracer:
        zipkin:
          address: aspen-mesh-jaeger-collector.istio-system:9411

  7. meshConfig

    MeshConfig defines mesh-wide settings for the Istio service mesh. Values that can be changed are listed here. 

    Before any change in the meshConfig, please reach Aspen Mesh support.

    # Default install 
    meshConfig:
      # Config for the default ProxyConfig.
      # Initially using directly the proxy metadata - can also be activated using annotations
      # on the pod. This is an unsupported low-level API, pending review and decisions on
      # enabling the feature. Enabling the DNS listener is safe - and allows further testing
      # and gradual adoption by setting capture only on specific workloads. It also allows
      # VMs to use other DNS options, like dnsmasq or unbound.
      defaultConfig:
        proxyMetadata:
          # If empty, agent will not start :15013 DNS listener and will not attempt
          # to connect to Istiod DNS-TLS. This will also disable the core dns sidecar in
          # istiod and the dns-over-tls listener.
          # DNS_AGENT: DNS-TLS
          DNS_AGENT: ""
      accessLogFile: "/dev/stdout"

      # Set the default behavior of the sidecar for handling outbound traffic from the application:
      # ALLOW_ANY - out-bound traffic to unknown destinations will be allowed, in case there are no
      #   services or ServiceEntries for the destination port
      # REGISTRY_ONLY - re-strict outbound traffic to services defined in the service registry as well
      #   as those defined through ServiceEntries
      # AL-LOW_ANY is the default in 1.1 and later.  This means each pod will be able to make outbound requests
      # to services outside of the mesh without any ServiceEntry.
      # REGIS-TRY_ONLY was the default in 1.0.  If this behavior is desired, set the value below to REGISTRY_ONLY.
      outboundTrafficPolicy:
        mode: REGISTRY_ONLY

    Other scenarios when you want to change the meshConfig will include:

    • Change sampling rate (the % of spans generated by the mesh)
    • Turn features like DNS capture
    • Change trust domain
    • Adjust DNS refresh rate
    • Among others

  8. Global

    Global configuration can change most of the behavior in your Aspen Mesh install.

    In the example above when configuring Jaeger, we use the global config to instruct our sidecars where to connect.

    Other examples will be listed below and the effect that will produce:

    # Default install
    global:
      certificatesTTL:
        # the time from now for when a workload certificate is set to expire;
        # the certificate will be rotated before that time
        # format is done by duration (e.g. 36h30m15s)
        workloadCertTtl: 24h

        # the maximum TTL of issued workload certificates
        # the default is 90 days (90 * 24 hours / day)
        maxWorkloadCertTtl: 2160h

        # The TTL of self-signed CA root certificate.
        # the default is 10 years
        selfSignedCACertTtl: 87600h

      # generate certificates with SAN DNS extensions for workloads based
      # on annotations with the associated service account
      # you can find more information about this feature here: https://my.aspenmesh.io/client/docs/1.9/operations/mesh-workload-certs-san-entries/
      certificateCustomFields: false

      # generate elliptical curve certificates for workloads when the root
      # CA certificate also uses elliptical curve cryptography 
      # you can find more information here: https://my.aspenmesh.io/client/docs/1.9/operations/security/configure_ecc_certificates/
      enableEccCertificates: false

      # To output all istio components logs in json format by adding --log_as_json argument to each container argument
      logAsJson: false

      # Comma-separated minimum per-scope logging level of messages to output, in the form of <scope>:<level>,<scope>:<level>
      # The control plane has different scopes depending on component, but can configure default log level across all components
      # If empty, default scope and level will be used as configured in code
      logging:
        level: "default:info"
