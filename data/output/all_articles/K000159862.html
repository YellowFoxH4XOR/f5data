K000159862: SDC FEP Components Show "Not Synced" Status After Audit Restore and Web-UI Crash

Type
Support Solution
Published
2026-02-03
Updated
2026-05-19
Applies to
  • Traffix SDC: 5.X.X, 5.2.X, 5.2.0, 5.1.X, 5.1.0, 5.0.X, 5.0.0
Source
https://my.f5.com/manage/s/article/K000159862

Description

FEP (Front-End Processor) components display "not synced" status in the Configuration Sync Status after performing an Audit restore operation during which the Web-UI crashes and requires manual restart. The synchronization failure persists even after the Web-UI is restarted via monit, preventing proper configuration synchronization between the Configuration Manager (CM) and FEP components.

Symptoms:

  • FEP components show "not synced" in Configuration Sync Status (Topology > Site > SDC Components)
  • Issue occurs following an Audit restore operation
  • Web-UI crash during the restore process requiring manual restart
  • Configuration synchronization does not automatically recover after Web-UI restart

Environment

  • Product: SDC (Service Delivery Controller)
  • Version: 5.2.0 or later
  • Configuration: Multiple FEP components in high-availability (HA) configuration

Cause

The configuration synchronization failure is caused by process interruption during the Audit restore operation. When the Web-UI crashes during the restore and requires manual restart via monit, the Configuration Manager and FEP components lose synchronization state. The incomplete configuration propagation during the forced Web-UI restart leaves the FEP components unable to synchronize with the Configuration Manager.

Answer/Recommended Actions

Initial Verification:

  1. Check the status of all SDC components:

monit summary

  1. Attempt to restart the Configuration Manager (CM):

monit restart <site_name>_CM

  1. Verify the CM is running:

monit status <site_name>_CM

  1. Check Configuration Sync Status in Web-UI:

    • Navigate to: Topology > Site > SDC Components
    • Verify if FEPs show "Synced" status

If CM restart does not resolve the issue, proceed with FEP restart procedure:

For HA/Redundant FEP Configurations:

  1. Identify which FEP is currently active and which is standby

  2. Restart the STANDBY FEP first to minimize service impact:

monit restart <standby_fep_name>

  1. Wait for the standby FEP to come back online and verify:

monit status <standby_fep_name>

  1. Check if the standby FEP shows "Synced" status in the Web-UI (Topology > Site > SDC Components)

  2. Restart the ACTIVE FEP (this will cause failover to the standby FEP):

monit restart <active_fep_name>

  1. Wait for the previously active FEP to come back online and verify:

monit status <active_fep_name>

  1. Verify all processes are running:

monit summary
jps -m

  1. Check Configuration Sync Status in Web-UI:

    • Navigate to: Topology > Site > SDC Components
    • Confirm both FEPs now show "Synced" status with health "good" and operational status "up"

  2. Monitor peer connections to ensure all external peer connections have re-established successfully.

Important Considerations:

  • Schedule FEP restarts during maintenance windows when possible to control impact to peer connections
  • If HA/redundant FEPs are not functioning properly due to lack of synchronization, any FEP restart may cause brief loss of service for connected peers
  • Confirm the secondary FEP is healthy and can take over traffic before restarting the active FEP
  • Restart one FEP at a time, monitoring peer reconnections and service status
  • Wait for all connections to re-establish before restarting the next FEP

If the issue persists after FEP restarts:

  • Generate TTA logs from the affected SDC node
  • Collect relevant CM, FEP, and Web-UI logs for further analysis
  • Ensure network connectivity between CM and FEPs is stable
  • Review CM logs for successful configuration sync events

Additional Information

This is a known scenario in SDC environments where configuration data between the Configuration Manager and FEP components can become out of sync due to:

  • Process interruption during critical configuration operations
  • Resource constraints during restore operations
  • Incomplete configuration propagation when services are forcefully restarted

The systematic restart of FEP processes re-establishes the configuration synchronization channels between the Configuration Manager and FEPs, restoring proper high-availability functionality.
