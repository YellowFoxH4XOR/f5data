K000160756: Cookie hash persistence does not guarantee the same pool member selection across independent BIG-IP devices

Description

When using cookie hash persistence, customers may observe that different pool members are selected on two independent BIG-IP devices even when the same static cookie value is presented. This article explains why this behavior is expected and recommends alternatives for achieving consistent, stateless server selection across independent systems.

 

Symptoms

 

  • The same cookie value results in different pool member selection on two separate BIG-IP devices.
  • After persistence records expire or are manually deleted on a single BIG-IP, the same cookie value is forwarded to a different pool member.
  • Traffic distribution appears inconsistent across active/active or geographically distributed BIG-IP deployments using cookie hash persistence.

 

Environment

  • BIG-IP LTM
  • Persistence cookie hash
  • Geographically distributed BIG-IP deployments using cookie-hash persistence.

Cause

Cookie hash persistence operates by storing a persistence record (mapping the cookie value to a pool member) in the BIG-IP's persistence table. The forwarding decision is made based on whether a record exists in that table — not based on computing a consistent hash of the cookie value itself.

 

This means:

 

  • There is no shared state between two independent BIG-IP devices. Each device maintains its own persistence table, and a cookie record on one device has no effect on another.
  • Even on a single BIG-IP, if the persistence record expires or is deleted, the same cookie value will result in a new load-balancing decision, potentially selecting a different pool member.

The cookie hash value is used only as a lookup key in the persistence table — not as a deterministic selector.

 

Answer/Recommended Actions

Cookie hash persistence is not designed to provide consistent server selection across independent BIG-IP systems. This is expected behavior and not a defect.

If you require stateless, cross-device consistent server selection based on a cookie or other request attribute, consider using:

Hash CARP persistence — provides deterministic, stateless load balancing using the CARP (Cache Array Routing Protocol) hash algorithm. This does not rely on a persistence table, meaning the same input will always produce the same server selection on any device.

 See: K11362: Overview of the CARP hash algorithm
