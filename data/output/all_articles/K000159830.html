Description

This article provides a comprehensive guide to all available methods for establishing communication between the BIG-IP system and pool members. It covers configuration steps, use cases, best practices, and relevant KB article references for each method.

Environment

  • BIG-IP LTM (All versions)
  • Classic BIG-IP (versions 9.x - 17.x, 21.x)
  • F5OS-based systems (rSeries, VELOS)
  • All deployment scenarios (on-premises, cloud, hybrid)

Cause

The BIG-IP system requires network connectivity to pool members for load balancing and health monitoring. While the most common method is configuring a self IP on the same subnet as pool members, there are multiple alternative approaches depending on network architecture, security requirements, and deployment scenarios.

This article covers 11 different methods for BIG-IP to communicate with pool members:

  1. Self IP on the Same Subnet (Most Common)
  2. Default Gateway / Static Routes
  3. Route Domains
  4. SNAT (Source Network Address Translation)
  5. Tunnels (GRE, VXLAN, IPsec)
  6. VLANs with Tagged Interfaces (802.1Q)
  7. Forwarding Virtual Servers
  8. Proxy ARP
  9. Multiple Self IPs on the Same VLAN
  10. Direct Server Return (DSR) / nPath
  11. Service Discovery and Dynamic Pool Members

Method 1: Self IP on the Same Subnet (Most Common)

Description

The most straightforward method where the BIG-IP has a self IP address configured on the same subnet as the pool members, allowing direct Layer 2 communication.

How It Works

  • BIG-IP has a self IP (e.g., 10.1.10.245/24) on the internal VLAN
  • Pool members are on the same subnet (e.g., 10.1.10.10, 10.1.10.11, 10.1.10.12)
  • Communication happens via ARP at Layer 2
  • No routing required

Configuration Steps

# Create VLAN 
tmsh create net vlan internal interfaces add { 1.2 { untagged } }
# Create self IP on the VLAN
tmsh create net self 10.1.10.245/24 vlan internal allow-service default
# Create pool with members on same subnet
tmsh create ltm pool web_pool members add { 10.1.10.10:80 10.1.10.11:80 10.1.10.12:80 }
# Create virtual server
tmsh create ltm virtual vs_web destination 10.1.10.100:80 pool web_pool

Self IP Configuration Options

Allow-Service Settings:

  • default - Allows typical management services (SSH, HTTPS, etc.)
  • all - Allows all services
  • none - Blocks all services
  • Custom list - e.g., { tcp:443 tcp:22 udp:161 }

# Example: Self IP with custom allow-service
tmsh create net self 10.1.10.245/24 vlan internal allow-service { tcp:443 tcp:22 }

Method 2: Default Gateway / Static Routes

Description

The BIG-IP can reach pool members on different subnets via Layer 3 routing using a default gateway or static routes.

How It Works

  • BIG-IP has a self IP on one subnet
  • Pool members are on a different subnet
  • BIG-IP uses routing to reach pool members
  • Typically requires SNAT for return traffic

Configuration Steps

# Create self IP on local VLAN
tmsh create net vlan internal interfaces add { 1.2 { untagged } } tmsh create net self 10.1.10.245/24 vlan internal allow-service default
# Add default gateway
tmsh create net route default gw 10.1.10.1
# OR add specific static route to pool member subnet
tmsh create net route pool_member_route network 192.168.100.0/24 gw 10.1.10.1
# Create pool with members on different subnet
tmsh create ltm pool remote_pool members add { 192.168.100.10:80 192.168.100.11:80 }
# Create virtual server with SNAT (typically required)
tmsh create ltm virtual vs_remote destination 10.1.10.100:80 pool remote_pool source-address-translation { type automap }

Verification Commands

# View routing table
tmsh show net route
# Test connectivity to pool member
ping 192.168.100.10
# Verify route is being used
tmsh show net route 192.168.100.10

Method 3: Route Domains

Description

Route domains allow the BIG-IP to segment routing tables and communicate with pool members in different routing contexts, enabling multi-tenancy and overlapping IP address spaces.

How It Works

  • Each route domain has its own routing table
  • Route domain 0 is the default
  • Pool members can be in different route domains
  • Useful for overlapping IP addresses

Configuration Steps

# Create route domain
tmsh create net route-domain 10 id 10
# Create VLAN in route domain
tmsh create net vlan vlan_rd10 interfaces add { 1.3 { untagged } }
tmsh modify net route-domain 10 vlans add { vlan_rd10 }
# Create self IP in route domain (note the %10 suffix)
tmsh create net self 10.2.10.245%10/24 vlan vlan_rd10 allow-service default
# Add route in route domain
tmsh create net route route_rd10 network 192.168.200.0%10/24 gw 10.2.10.1%10
# Create pool with members in route domain
tmsh create ltm pool rd10_pool members add { 192.168.200.10%10:80 192.168.200.11%10:80 }
# Create virtual server in route domain
tmsh create ltm virtual vs_rd10 destination 10.2.10.100%10:80 pool rd10_pool

Method 4: SNAT (Source Network Address Translation)

Description

SNAT changes the source IP address of traffic from the BIG-IP to pool members, simplifying return traffic routing.

How It Works

  • BIG-IP changes source IP to one of its self IPs
  • Pool member sees traffic from BIG-IP, not original client
  • Return traffic goes directly to BIG-IP
  • Pool members only need a route to the BIG-IP's SNAT address

Configuration Steps

Option 1: SNAT AutoMap

tmsh create ltm virtual vs_web destination 10.1.10.100:80 pool web_pool source-address-translation { type automap }

Option 2: SNAT Pool

# Create SNAT pool
tmsh create ltm snatpool snat_pool members add { 10.1.10.50 10.1.10.51 10.1.10.52 }
# Create virtual server with SNAT pool
tmsh create ltm virtual vs_web destination 10.1.10.100:80 pool web_pool source-address-translation { type snat pool snat_pool }

Method 5: Tunnels (GRE, VXLAN, IPsec)

Description

The BIG-IP can communicate with pool members over various tunnel types, useful for remote data centers, cloud environments, or overlay networks.

Configuration Steps - GRE Tunnel

# Create GRE tunnel profile
tmsh create net tunnels gre gre_tunnel local-address 203.0.113.10 remote-address 198.51.100.10
# Create tunnel interface
tmsh create net tunnels tunnel gre_to_remote key 100 local-address 203.0.113.10 profile gre_tunnel
# Create self IP on tunnel
tmsh create net self 172.16.1.1/30 vlan gre_to_remote allow-service default
# Add route through tunnel
tmsh create net route remote_pool_route network 192.168.50.0/24 gw 172.16.1.2
# Create pool with remote members
tmsh create ltm pool tunnel_pool members add { 192.168.50.10:80 192.168.50.11:80 }

Method 6: VLANs with Tagged Interfaces (802.1Q)

Description

The BIG-IP can have multiple VLANs configured on the same physical interface using VLAN tagging.

Configuration Steps

# Create tagged VLANs on same interface
tmsh create net vlan vlan100 interfaces add { 1.1 { tagged } } tag 100 tmsh create net vlan vlan200 interfaces add { 1.1 { tagged } } tag 200
# Create self IPs for each VLAN
tmsh create net self 10.1.100.245/24 vlan vlan100 allow-service default tmsh create net self 10.1.200.245/24 vlan vlan200 allow-service default
# Create pools with members on different VLANs
tmsh create ltm pool pool_vlan100 members add { 10.1.100.10:80 10.1.100.11:80 } tmsh create ltm pool pool_vlan200 members add { 10.1.200.10:80 10.1.200.11:80 }

Method 7: Forwarding Virtual Servers

Description

Using forwarding (performance Layer 4) or performance Layer 2 virtual servers, the BIG-IP acts more like a router/switch with less processing overhead.

Configuration Steps

IP Forwarding (Layer 3):

# Create forwarding virtual server
tmsh create ltm virtual vs_forward destination 0.0.0.0:0 mask 0.0.0.0 ip-forward vlans add { internal } vlans-enabled

Performance Layer 4:

# Create performance L4 virtual server
tmsh create ltm virtual vs_perf_l4 destination 10.1.10.100:80 pool web_pool profiles add { fastL4 }

Method 8: Proxy ARP

Description

The BIG-IP can respond to ARP requests on behalf of pool members, making it appear as the Layer 2 gateway.

Configuration Steps

# Enable proxy ARP on VLAN
tmsh modify net vlan internal proxy-arp enabled
# Create self IP on VLAN
tmsh create net self 10.1.10.245/24 vlan internal allow-service default
# Add route for pool member subnet
tmsh create net route pool_subnet network 192.168.100.0/24 interface internal
# Create pool with members on different subnet
tmsh create ltm pool proxy_pool members add { 192.168.100.10:80 192.168.100.11:80 }

Method 9: Multiple Self IPs on the Same VLAN

Description

Configure multiple self IPs on the same VLAN but different subnets.

Configuration Steps

# Create VLAN
tmsh create net vlan internal interfaces add { 1.2 { untagged } }
# Create multiple self IPs on same VLAN
tmsh create net self 10.1.10.245/24 vlan internal allow-service default
tmsh create net self 10.1.20.245/24 vlan internal allow-service default
tmsh create net self 10.1.30.245/24 vlan internal allow-service default
# Create pools with members on different subnets
tmsh create ltm pool pool_subnet1 members add { 10.1.10.10:80 10.1.10.11:80 }
tmsh create ltm pool pool_subnet2 members add { 10.1.20.10:80 10.1.20.11:80 }

Method 10: Direct Server Return (DSR) / nPath

Description

In DSR mode, the BIG-IP only handles inbound traffic and health checks. Pool members respond directly to clients.

Configuration Steps

On BIG-IP:

# Create pool with gateway ICMP monitor
tmsh create ltm monitor gateway-icmp gw_icmp defaults-from gateway_icmp tmsh create ltm pool dsr_pool members add { 10.1.10.10:80 10.1.10.11:80 } monitor gw_icmp
# Create virtual server with fastL4 profile
tmsh create ltm virtual vs_dsr destination 10.1.10.100:80 pool dsr_pool profiles add { fastL4 } translate-address disabled translate-port disabled
# Ensure self IP exists for health check connectivity
tmsh create net self 10.1.10.245/24 vlan internal allow-service default

On Pool Members (Linux):

# Add VIP to loopback interface
ip addr add 10.1.10.100/32 dev lo
# Disable ARP for VIP
echo 1 > /proc/sys/net/ipv4/conf/lo/arp_ignore echo 2 > /proc/sys/net/ipv4/conf/lo/arp_announce

Method 11: Service Discovery and Dynamic Pool Members

Description

For cloud and container environments, the BIG-IP can dynamically discover pool members using cloud provider APIs or service registries.

Configuration Steps - AWS Example

# Create AWS cloud provider
tmsh create ltm cloud-provider aws-provider type aws region us-east-1 access-key-id AKIAIOSFODNN7EXAMPLE secret-access-key wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
# Create service discovery pool
tmsh create ltm pool aws_pool service-discovery aws { provider aws-provider tag-key Environment tag-value Production port 80 }

Best Practices

1. Health Monitoring

Ensure the BIG-IP can reach pool members for health checks:

# Test connectivity
ping <pool_member_ip>
# Verify monitor status
tmsh show ltm pool <pool_name> members

2. Return Traffic Path

Consider how return traffic reaches the BIG-IP or clients:

  • With SNAT: Return traffic always goes to BIG-IP
  • Without SNAT: Pool members must route back through BIG-IP
  • With DSR: Return traffic bypasses BIG-IP entirely

3. Security Considerations

  • Configure appropriate port lockdown on self IPs
  • Use firewalls between BIG-IP and pool members
  • Implement proper VLAN segmentation
  • Use route domains for tenant isolation

4. Troubleshooting Commands

# Verify connectivity
ping <pool_member_ip>
# Check routing
tmsh show net route <pool_member_ip>
# View ARP table
tmsh show net arp
# Check connection table
tmsh show sys connection cs-server-addr <pool_member_ip>
# Packet capture
tcpdump -nni <vlan_name> host <pool_member_ip>
# View pool member status tmsh show ltm pool <pool_name> members

Common Deployment Scenarios

Scenario 1: Simple Internal Load Balancing

  • Method: Self IP on same subnet
  • Why: Simplest, most straightforward
  • Configuration: Single VLAN, self IP, pool members on same subnet

Scenario 2: Multi-Tier Application

  • Method: Multiple VLANs with tagged interfaces + SNAT
  • Why: Separate web, app, and database tiers
  • Configuration: Tagged VLANs, self IP per tier, SNAT for tier-to-tier communication

Scenario 3: Data Center with Routed Network

  • Method: Static routes + SNAT AutoMap
  • Why: Pool members on different subnets, routed infrastructure
  • Configuration: Self IP on local subnet, static routes, SNAT for return traffic

Scenario 4: Multi-Tenant Environment

  • Method: Route domains
  • Why: Isolated routing tables, overlapping IP addresses
  • Configuration: Route domain per tenant, separate VLANs, isolated routing

Scenario 5: Hybrid Cloud

  • Method: Tunnels (GRE/IPsec) + Service Discovery
  • Why: Pool members in cloud and on-premises
  • Configuration: Tunnels to cloud, service discovery for dynamic members

Scenario 6: High-Performance Content Delivery

  • Method: DSR (Direct Server Return)
  • Why: Minimize BIG-IP bandwidth, high throughput
  • Configuration: FastL4 profile, loopback on pool members, gateway ICMP monitoring
