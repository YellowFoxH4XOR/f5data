Known Issue

Multiple B4450 blades in the same chassis may experience packet drops due to inconsistent DAG state.

This issue occurs when all of the following conditions are met:

  • You have more than one B4450 blades in the same VIPRION chassis.

Impact

The inconsistency of DAG state may introduce packet drops and cause traffic disruption.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The B4450 blades may experience packet drops and possible traffic disruption.
  • You may observe inconsistent DAG in one of the following tmctl tables:
    • daglib_dagv2_hsbs
    • daglib_dagv2_mirror_hsbs
    • daglib_dagv2_pgs
    • daglib_dagv2_mirror_pgs
You can check the DAG table output across the blades using the following command syntax:

ssh <slot#> tmctl -Sd blade tmm/<DAG_table>

For example, the following daglib_dagv2_pgs outputs show the inconsistent DAG table between slot1 (00:01:00:01) and slot2 (00:00:01:01):

ssh slot1 tmctl -Sd blade tmm/daglib_dagv2_pgs
pg pu source_pg  timestamp table_size table      
-- -- --------- ---------- ---------- -----------
 0  0         0 1522255013          4 00:01:00:01
 0  1         1 1522255013          4 00:01:00:01
...
ssh slot2 tmctl -Sd blade tmm/daglib_dagv2_pgs
pg pu source_pg  timestamp table_size table      
-- -- --------- ---------- ---------- -----------
 1  0         0 1537265723          4 00:00:01:01
 1  1         1 1537265723          4 00:00:01:01
...

  • If the VIPRION system is part of device group setup, the standby unit may repeatedly log a message in the /var/log/tmm file that appears similar to the following example:

    notice CDP: Selected DAG state from primary PG 0 for CMP state 03 with clock 6765

Workaround

To temporarily work around this issue, you can restart the Traffic Management Microkernel (TMM) on one of the blades in the chassis and force the blades to reform the cluster in data plane. To do so, perform the following procedure:

Impact of workaround: Performing the following procedure causes a temporary traffic disruption while the TMM process restarts. You should perform this procedure only during a scheduled maintenance period.

  1. Log in to tmsh by typing the following command:

    tmsh

  2. Restart the TMM process by typing the following command:

    restart /sys service tmm
