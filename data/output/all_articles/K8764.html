Topic

The BIG-IP system monitors the availability and performance of multiple WAN links and load balances inbound and outbound traffic flows to and from a site. When configuring a BIG-IP system to load balance outbound traffic, you may need the BIG-IP system to support outbound Point-to-Point Tunneling Protocol (PPTP) connections.

Note: For information about configuring inbound PPTP load balancing, refer to K7170: Configuring PPTP load balancing.

Challenges of passing outbound PPTP through the BIG-IP system

Normally, passing outbound traffic through the BIG-IP system is achieved by using a Secure Network Address Translation (SNAT) or SNAT pools. However, additional configuration steps are required in order to pass outbound PPTP traffic through the BIG-IP system, as a standard SNAT or SNAT pool cannot be used to process concurrent outbound PPTP sessions. The Traffic Management Microkernel (TMM) recognizes PPTP traffic as two distinct connections; one connection is TCP port 1723, and the other connection is an enhanced GRE tunnel, through IP protocol 47. If two or more concurrent PPTP clients share the same SNAT address, TMM will correctly apply the SNAT to the TCP port 1723 connections, but TMM will not be able to map subsequent GRE sessions to their proper internal addresses. This behavior causes multiple PPTP connections through a SNAT to fail.

Note: IP protocol 47 is described in RFC2637.

Options for passing outbound PPTP traffic through the BIG-IP system

The following options are available for passing outbound PPTP traffic through the BIG-IP system:

  • Using the BIG-IP CGNAT module for PPTP (BIG-IP 11.5.0 and later versions)
  • Defining a one-to-one SNAT mapping for each PPTP client
  • Forwarding the virtual server for PPTP+GRE traffic
  • Forwarding the PPTP traffic to external NAT devices
Using the BIG-IP CGNAT module for PPTP (BIG-IP 11.5.0 and later versions)

Starting in BIG-IP 11.5.0, the ALG PPTP profile for the CGNAT module is available. The ALG PPTP CGNAT profile provides a PPTP profile that enables you to configure the BIG-IP system to support a secure virtual private network (VPN) tunnel that forwards PPTP control and data connections. You can create a secure VPN tunnel by configuring a PPTP profile, and then assigning the PPTP profile to a virtual server. For more information about configuring CGNAT for PPTP, refer to the Creating a Secure VPN Tunnel with PPTP chapter of the BIG-IP CGNAT: Implementations guide.

Note: Only systems that run BIG-IP 11.5.0 and later versions, that are licensed and provisioned for the CGNAT module, can utilize this feature.

Defining a one-to-one SNAT mapping for each PPTP client

You can pass outbound PPTP traffic through the BIG-IP system by defining a one-to-one SNAT mapping for each PPTP client. For example, this option requires each internal PPTP client IP address to be mapped to a unique public IP address on the BIG-IP system for each Internet service provider (ISP).

Note: In some BIG-IP versions, forwarding virtual servers configured for non-TCP/UDP traffic may discard return traffic when a SNAT is enabled. For more information, refer to K11551: Forwarding virtual servers configured for non-TCP/UDP traffic discard return traffic when SNAT is enabled.

The one-to-one SNAT mapping option meets the following criteria:

  • ISP load balancing of PPTP sessions
  • Failover of PPTP sessions
  • Internal PPTP clients need to concurrently access the same external PPTP server

Using the Traffic Management Shell (tmsh) to define a one-to-one SNAT mapping configuration for each PPTP client, perform the following five procedures:

  • Configuring the one-to-one SNAT mapping option
  • Defining the SNAT pools
  • Defining the SNATs
  • Defining the PPTP control channel virtual server
  • Defining the GRE virtual server

Configuring the one-to-one SNAT mapping option

Demonstrating creation of the one-to-one SNAT mapping configurations, using the following sample ISP and internal network IP addresses:

  • ISP1:
    1.1.1.50
    1.1.1.51
  • ISP2:
    2.2.2.50
    2.2.2.51
  • Internal network:
    client1 - 192.168.0.50
    client2 - 192.168.0.51

Defining the SNAT pools

Each PPTP client IP address maps to a SNAT pool with IP addresses from each ISP.

For example using tmsh to create the SNAT pool configuration for client1 and client2 are defined as follows:

tmsh create /ltm snatpool client1_snatpool members add { 1.1.1.50 2.2.2.50 }

tmsh create /ltm snatpool client2_snatpool members add { 1.1.1.51 2.2.2.51 }

Defining the SNATs

A SNAT is defined for each PPTP client with a SNAT pool defined as the translation object for the SNAT.

For example using tmsh to define the SNAT for client1 and client2 as follows:

tmsh create /ltm snat client1_snat origins add { 192.168.0.50 } snatpool client1_snatpool

tmsh create /ltm snat client2_snat origins add { 192.168.0.51 } snatpool client2_snatpool

Defining the PPTP control channel virtual server

You must define the PPTP control channel virtual server as a network wildcard virtual server with a netmask of 0.0.0.0.

For example using tmsh to create the PPTP control channel virtual server as follows:

tmsh create /ltm virtual pptp_control destination 0.0.0.0:1723 mask 0.0.0.0 profiles add { fastL4 } ip-protocol tcp translate-port disabled persist replace-all-with { source_addr }

Defining the GRE virtual server

You must define the GRE virtual server as a network wildcard virtual server with a netmask of 0.0.0.0, using IP protocol 47.

For example using tmsh to create the GRE virtual server as follows:

tmsh create /ltm virtual pptp_gre destination 0.0.0.0:0 mask 0.0.0.0 profiles add { fastL4 } ip-protocol gre translate-port disabled persist replace-all-with { source_addr }

Forwarding the virtual server for PPTP+GRE traffic

You can pass outbound PPTP traffic through the BIG-IP system by defining a forwarding virtual server that is configured to pass All Ports and All Protocols.

The forwarding virtual server option requires the following:

  • PPTP client IP addresses are routable (non-RFC1918), and belong to one of the ISPs.

The forwarding virtual server option has the following limitations:

  • No ISP load balancing
  • No failover of PPTP sessions

Defining the forwarding virtual server

The virtual server must be configured to pass All Ports and All Protocols to or from one of the ISPs.

Using tmsh to create the forwarding virtual server configuration as follows:

tmsh create /ltm virtual pptp_forward destination 0.0.0.0:0 mask 0.0.0.0 ip-forward profiles add { fastL4 } ip-protocol any

Forwarding the PPTP traffic to external NAT devices

It is also possible to forward PPTP traffic and perform NAT overload on external routers, while maintaining outbound load balancing on the BIG-IP system for other types of traffic. In this case, you can configure the BIG-IP system to pass the PPTP traffic directly to the external router, which applies NAT functionality to the PPTP traffic.

Defining the PPTP control channel forwarding virtual server

Using tmsh to create the PPTP control channel forwarding virtual server as follows:

tmsh create /ltm virtual pptp_control_forward destination 0.0.0.0:1723 mask 0.0.0.0 ip-forward profiles add { fastL4 } ip-protocol tcp translate-port disabled persist replace-all-with { source_addr }

Defining the GRE forwarding virtual server

Using tmsh to create the GRE forwarding virtual server as follows:

tmsh create /ltm virtual pptp_gre_forward destination 0.0.0.0:0 mask 0.0.0.0 ip-forward profiles add { fastL4 } ip-protocol 47 translate-port disabled persist replace-all-with { source_addr }
