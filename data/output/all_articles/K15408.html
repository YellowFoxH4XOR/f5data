Issue

Prerequisites

Before attempting to troubleshoot a BIG-IP DNS monitor (formerly known as BIG-IP GTM), if you are running multiple BIG-IP devices, you must ensure that the iQuery mesh is complete between all devices. For more information, refer to the following articles:

  • K9837: An incomplete iQuery mesh across a sync group may result in inconsistent responses or configuration loss
  • K13690: Troubleshooting BIG-IP DNS synchronization and iQuery connections (11.x - 14.x)

Overview

The BIG-IP DNS health monitors verify connectivity to virtual server objects that reside on BIG-IP devices and non-BIG-IP devices. When a BIG-IP DNS monitor marks a virtual server down, and that virtual server is a member of a wide BIG-IP pool, the BIG-IP DNS no longer includes that virtual server's address in answers to DNS queries for a wide IP.

The BIG-IP DNS system receives the status of virtual servers that reside on non-BIG-IP devices directly from BIG-IP devices using the iQuery protocol. For example, if you have BIG-IP DNS devices and BIG-IP LTM devices in a data center, along with generic host servers, the BIG-IP DNS system will dynamically assign a BIG-IP device to probe the generic host server for status. You can also assign a specific BIG-IP device or group of devices to monitor a server object by using prober pools. For more information about prober pools, refer to the Configuring Device-Specific Probing and Statistics Collection section of the BIG-IP DNS Implementations manual.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Note: If you are using the BIG-IP LTM system to provide local load balancing for names resolved by the BIG-IP DNS system, F5 recommends that you configure only the BIG-IP LTM system to monitor the LTM pool members, allowing the BIG-IP DNS to collect object status information from the BIG-IP LTM system without configuring additional DNS monitors for the same objects. This behavior ensures the desired conservation of shared WAN bandwidth, and eliminates cross-data center latency.

Note: While the BIG-IP LTM and BIG-IP DNS monitors appear to provide similar functionality, they differ significantly in certain regards. For more information about the similarities and differences between BIG-IP LTM and DNS monitors, refer to K8170: Understanding differences between BIG-IP LTM and BIG-IP DNS monitors.

A failing or misconfigured health monitor may cause traffic management issues similar to, but not limited to, the following:

  • Responses for wide IP requests are unreliable or fail.
  • Wide IP statistics show a number of wide IP requests falling back to the last resort pool.
  • Wide IP pool statistics reveal a higher than expected number of requests using the alternate and fallback load balancing method.

The previously mentioned symptoms may indicate that a health monitor is marking a wide IP pool member down indefinitely, or that a monitor is repeatedly marking the pool member down and then back up (often referred to as a bouncing pool member). For example, if a misconfigured health monitor constantly marks wide IP pool members down and then back up, the virtual server may, or may not, be returned for wide IP requests. You will then need to determine whether the monitor is misconfigured, the device or application is failing, or some other factor is occurring that is causing the monitor to fail (such as network-related issue). The troubleshooting steps you take will depend on the monitor type and the observed symptoms.

When experiencing health monitor issues, you can use the following troubleshooting steps:

  • Confirming logical consistency of iQuery configuration
  • Identifying a failing health monitor
  • Verifying monitor settings
  • Troubleshooting monitor types

Confirming logical consistency of iQuery configuration

Apart from failures to communicate with big3d discussed at K52381445: DNS monitor state showing "no reply from big3d: timed out" health monitoring may also fail if iQuery members are using for their membership floating self IP addresses.

Logs

The BIG-IP DNS system logs messages related to the health monitor to the /var/log/gtm file. Reviewing the log files is one way to determine the frequency with which the system is marking down a pool, pool member, server, or virtual server. Logging related to monitor state changes are as follows:

  • Pools

    When a health monitor marks all members of a pool down or up, the system logs messages to the /var/log/gtm file that appear similar to the following example:

    alert gtmd[4679]: 011a1005:1: SNMP_TRAP: Pool /Common/<Pool_name> state change green --> red (No enabled pool members available)
    alert gtmd[4679]: 011a1004:1: SNMP_TRAP: Pool /Common/<Pool_name> state change red --> green

  • Pool members

    When a health monitor marks a member of a pool down or up, the system logs messages to the /var/log/gtm file that appear similar to the following example:

    alert gtmd[4679]: 011a4003:1: SNMP_TRAP: Pool /Common/<Pool_name> member <Pool_member> (ip:port=10.1.1.1:80) state change green --> red (Monitor /Common/tcp from 10.1.1.2 : no route)
    alert gtmd[4679]: 011a4002:1: SNMP_TRAP: Pool /Common/<Pool_name> member <Pool_member> (ip:port=10.1.1.1:80) state change red --> green

  • Servers

    When a health monitor marks a server down or up, the system logs messages to the /var/log/gtm file that appear similar to the following example:

    alert gtmd[4679]: 011a5004:1: SNMP_TRAP: Server /Common/<Server_name> (ip=10.1.1.1) state change green --> red (No enabled VS available)
    alert gtmd[4679]: 011a5003:1: SNMP_TRAP: Server /Common/<Server_name> (ip=10.1.1.1) state change red --> green

  • Virtual servers

    When a health monitor marks a virtual server down or up, the system logs messages to the /var/log/gtm file that appear similar to the following example:

    alert gtmd[4679]: 011a6006:1: SNMP_TRAP: VS <Virtual_server_name> (ip:port=10.1.1.1:80) (Server /Common/<Server_name>) state change green --> red (Monitor /Common/tcp from 10.1.1.2 : no route)
    alert gtmd[4679]: 011a6005:1: SNMP_TRAP: VS <Virtual_server_name> (ip:port=10.1.1.1:80) (Server /Common/<Server_name>) state change red --> green

Verifying monitor settings

It is important to verify that monitor settings are properly defined for your environment. For example, F5 recommends that you configure most BIG-IP DNS monitors with either a 4:1 or a 3:1 timeout:interval ratio, and a five-second timeout for the probes themselves.

The BIG-IP DNS system includes many different types of monitors, each designed to perform a specific type of monitoring. The monitors belong to one of three categories:

  • Simple
  • Extended content verification (ECV)
  • Extended application verification (EAV)

Simple monitors

You can use a simple monitor to verify the status of a server or virtual server (or the path to the node through a transparent device). The BIG-IP DNS system provides the following pre-configured simple monitor types: gateway_icmp, tcp_echo, tcp_half_open. If you determine that a simple monitor is marking a node down, you can verify the following settings:

You can define other monitor settings for simple monitors. For more information, refer to the Health and Performance Monitors section of the BIG-IP DNS: Concepts manual.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

  • Interval/timeout ratio

    Configuring an appropriate interval/timeout ratio is important for simple monitors. In most cases, the interval/timeout should have a timeout value of three to four times the interval. For example, the default ratio for the gateway_icmp monitor is 30/120. Verify that the ratio is properly defined.

  • Transparent

    A transparent monitor uses a path through the associated node to monitor the aliased destination. Verify that the destination target device is reachable and configured properly for the monitor.

Extended content verification (ECV)

ECV monitors use Send and Receive string settings to retrieve content from servers or virtual servers. The BIG-IP DNS system provides the following preconfigured monitor types: tcp, http, http_head_f5, https, and, https_head_f5. If you determine that an ECV monitor is marking a node down, you can verify the following settings:

You can define other monitor settings for simple monitors. For more information, refer to the Health and Performance Monitors section of the BIG-IP DNS: Concepts manual. For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

  • Interval/timeout ratio

    As with simple monitors, configuring the interval/timeout ratio is important for ECV monitors. In most cases, the interval/timeout should have a timeout value of three to four times the interval. For example, the default ratio for the HTTP monitor is 30/120. Verify that the ratio is properly defined.

  • Send string

    The Send string is a text string that the monitor sends to the pool member. The default setting is GET /, which retrieves a default HTML file for a website. If the Send string is not properly constructed, the server may send an unexpected response and be subsequently marked down by the monitor. For example, if the server requires the monitor request to be HTTP/1.1 compliant, you will need to adjust the monitor Send string.

    For information about modifying HTTP requests for use with HTTP or HTTPS application health monitors, refer to K13397: Overview of HTTP health monitor request formatting for the BIG-IP DNS system and K13622: BIG-IP DNS HTTP health monitor behavior when processing a server response.

  • Receive string

    The Receive string is the regular expression representing the text string that the monitor looks for in the returned resource. Extended Content Verification (ECV) monitor requests may fail and mark the server object down if the Receive string is not configured properly. For example, if the Receive string appears too late in the server response, or the server responds with a redirect, the monitor marks the pool member down.

    For information about modifying the monitor to issue a request to a redirection target, refer to K3224: HTTP health checks may fail even though the node is responding correctly.

  • Username and password

    ECV monitors have Username and Password settings for resources that require authentication. Verify whether the pool member requires authentication and ensure that the fields contain valid credentials.

Extended application verification (EAV)

EAV monitors check the health of a resource by accessing the specified application. If the monitor receives the correct response, then the health check is successful and the resource is considered up. Verification of EAV monitors varies, depending on the specific monitor used. For general considerations, refer to the following articles:

  • K8154: The BIG-IP GTM EAV monitor considerations
  • K11373: The external monitor location is /config/monitors (10.1.x - 10.2.x)

Troubleshooting monitor types

If you determine that a monitor is marking down a pool, pool member, server, or virtual server (or the object is bouncing), you can use the following steps to troubleshoot the issue:

Impact of procedure: Performing the following procedure may have a negative impact on your system. Enabling debug logging or running a packet capture on a busy system, for an extended period of time, may result in disk space exhaustion and a possible failover event.

  1. Determine which objects the monitor is marking down. Also, if a server defined in a BIG-IP GTM configuration is a BIG-IP system, such as a BIG-IP LTM system, the BIG-IP DNS system can assign certain probe tasks (executing a monitor) to that system, rather than conducting the probes itself; therefore, you should also determine which BIG-IP system the BIG-IP DNS system has assigned to probe the object.

    You can determine the IP address of the virtual servers that the monitor is marking down and the BIG-IP system assigned to perform the probes by reviewing log files. You can quickly search the /var/log/gtm file for status messages using the following command:

    # grep '> red' /var/log/gtm

    The command output appears similar to the following example:

    Note: The BIG-IP system assigned to probe the virtual server appears at the end of the log string and, in this example, it is 10.1.1.2.

    alert gtmd[4679]: 011a4003:1: SNMP_TRAP: Pool /Common/testpool member vm199vs (ip:port=10.1.1.1:80) state change green --> red ( Monitor /Common/tcp from 10.1.1.2 : no route)

    alert gtmd[4679]: 011a1005:1: SNMP_TRAP: Pool /Common/testpool state change green --> red (No enabled pool members available)

  2. (Optional) If you cannot determine which BIG-IP system the BIG-IP DNS system has assigned to conduct the probe by using the logs in the previous step, perform the following steps:
    1. Log in to tmsh by typing the following command:

      tmsh

    2. Enable DNS debug logging and DNS debug probe logging by typing the following command string, using the semicolon (;) to combine commands:

      modify /sys db log.gtm.level value debug; modify /sys db gtm.debugprobelogging value enable

    3. Allow debug logging for long enough to capture a monitor failure and then disable it by typing the following command string:

      modify /sys db log.gtm.level value notice; modify /sys db gtm.debugprobelogging value disable

    4. To determine which BIG-IP system is performing the probe, locate the following sub-string in the debug probe log string about the failing monitor:

      Probe from 10.1.1.2

      The system logs messages to the /var/log/gtm file that appear similar to the following full log example:

      notice gtmd[31373]: 011ae03d:5: Probe from 10.1.1.2: buffer = <monitor>    <name>/Common/http</name>    <addr>::ffff:10.1.1.1</addr>    <port>80</port>    <trans_addr>::ffff:10.1.1.1</trans_addr>    <trans_port>80</trans_port>    <server_name><![CDATA[/Common/ubuntu]]></server_name>    <vs_name><![CDATA[web_server]]></vs_name>    <monitor_state>6</monitor_state>    <node_type>4</node_type>    <monitor_type>4</monitor_type>    <vs_score>0</vs_score>    <why>state: no route</why>    <probe_time>39206</probe_time> </monitor>

  3. Check connectivity to the virtual server from the BIG-IP device that is marking the object down.

    If there are occurrences of a BIG-IP DNS object being marked down and not back up, or bouncing, check the connectivity to the object from the BIG-IP system that is responsible for probing the object, using commands, such as ping or traceroute. For example, if you have determined that BIG-IP LTM 10.1.1.2 is marking the node address 10.1.1.1 down, you can attempt to ping the resource from the BIG-IP system by using the following command:

    # ping -c 4 10.1.1.1

    The command output appears similar to the following example:

    PING 10.1.1.1 (10.1.1.1) 56(84) bytes of data.
    64 bytes from 10.1.1.1: icmp_seq=1 ttl=64 time=11.32 ms
    64 bytes from 10.1.1.1: icmp_seq=2 ttl=64 time=8.989 ms
    64 bytes from 10.1.1.1: icmp_seq=3 ttl=64 time=10.981 ms
    64 bytes from 10.1.1.1: icmp_seq=4 ttl=64 time=9.985 ms

    Note: The previous ping output shows high Round Trip Times (RTTs), which may indicate a network issue or a slow responding node.

    In addition, make sure that the virtual server is configured to respond to the simple monitor. For example, tcp_echo is a simple monitor type that requires that the TCP echo service is enabled on the monitored nodes. The BIG-IP device sends a SYN segment with information echoed by the receiving device.

  4. Check the monitor settings.

    Use the Configuration utility or command line to verify that the monitor settings (interval/timeout ratio) are appropriate for the object.

    To list the configuration for a monitor, use the following command syntax:

    tmsh list /gtm monitor <monitor type> <monitor name>

    For example, to check a monitor named http-test, you would type the following command:

    tmsh list /gtm monitor http http-test

  5. Create a custom monitor (if needed).

    If you are using a default monitor and have determined that the settings are not appropriate for your environment, consider creating and testing a new monitor with custom settings.

  6. Test the application response from the BIG-IP device that is responsible for probing the virtual server object, if you are monitoring using an ECV/EAV monitor.

    Use the BIG-IP command line to test the response from the web application. For example, the following command uses the curl (and time) command and attempts to transfer data from the web server while timing the response:

    # time curl http://10.1.1.1
    <html>
    <head>
    ---
    </body>
    </html>
    real 0m18.032s
    user 0m0.030s
    sys 0m0.060s

    Note: If you want to test a specific HTTP request, including HTTP headers, you can use the telnet command to connect to the pool member.

    For example:

    telnet <serverIP> <serverPort>

    Next, at the prompt, enter an appropriate HTTP request line and HTTP headers, pressing Enter once after each line.

    For example:

    GET / HTTP/1.1 <enter>
    Host: www.yoursite.com <enter>
    Connection: close <enter>
    <enter>

  7. Use the tcpdump command to capture monitor traffic.

    If you are unable to determine the cause of a failing health monitor, you may need to perform packet captures on the BIG-IP system that is responsible for probing the server or virtual server object. For more information about running tcpdump, refer to K411: Overview of packet tracing with the tcpdump utility.
