Description

Client-ssl profile "Cache Size" and "Cache Timeout" parameters are used to control TLS session resumption.

Given the protocol specification change in TLS 1.3 (RFC8446 section 2.2), now client-ssl profile "Cache Size" parameter has no effect on TLS 1.3 PSK resumption, as BIG-IP does not cache and use "Session ID" for TLS 1.3 resumption.

  > 2.2. Resumption and Pre-Shared Key (PSK)
  > ...
  > In TLS 1.2 and below, this functionality was provided by "session IDs" and "session tickets" [RFC5077]. Both mechanisms are obsoleted in TLS 1.3.

Meanwhile, client-ssl profile "Cache Timeout" parameter is still indirectly used in conjunction with "Session Ticket Timeout" parameter. When "Session Ticket Timeout" parameter is 0 (default), BIG-IP uses "Cache Timeout" parameter value (default 3600) as ticket_lifetime value in "New Session Ticket" message to the client. Clouddocs explains "Session Ticket Timeout" as follows.

  > session-ticket-timeout
  >      Specifies the session ticket timeout. The default value is 0 which means cache timeout is used.

In lieu of "Cache Size" and "Cache Timeout" parameters, "Session Ticket" parameter and "Session Ticket Timeout" parameters are used to control TLS 1.3 PSK resumption.

Note: In order to use TLS 1.3 PSK resumption, "Session Ticket" parameter needs to be enabled on client-ssl profile (default disabled). Refer to K000138324.

 

 

Here is demonstration of how TLS 1.3 PSK resumption works. Following example configuration is used to confirm TLS 1.3 PSK resumption.

ltm virtual /Common/clientssl_tls13_vs {
    destination /Common/10.1.1.202:443
    ip-protocol tcp
    mask 255.255.255.255
    pool /Common/http_pool
    profiles {
        /Common/my_clientssl_tls13 {
            context clientside
        }
        /Common/tcp { }
    }
    serverssl-use-sni disabled
    source 0.0.0.0/0
    source-address-translation {
        pool /Common/my_snatpool
        type snat
    }
    translate-address enabled
    translate-port enabled
}
ltm profile client-ssl /Common/my_clientssl_tls13 {
    app-service none
    cert-key-chain {
        web001.f5ss_ubuntu2204server1ca.f5ss_0 {
            cert /Common/web001.f5ss.local
            chain /Common/ubuntu2204server1ca.f5ss.local
            key /Common/web001.f5ss.local
        }
    }
    cipher-group /Common/my_cipher_group
    ciphers none
    defaults-from /Common/clientssl
    inherit-ca-certkeychain true
    inherit-certkeychain false
    options { dont-insert-empty-fragments no-dtlsv1.2 }
    session-ticket enabled
    session-ticket-timeout 123
}
ltm cipher group /Common/my_cipher_group {
    allow {
        /Common/my_cipher_rule { }
    }
}
ltm cipher rule /Common/my_cipher_rule {
    cipher DEFAULT
}

 

Here is packet capture of 2 client side TLS connections. On the first TLS connection, virtual server sends "Certificate" TLS message to the client and full TLS handshake is performed. On the second TLS connection, PSK resumption is performed.

Figure: TLS 1.3 resumption overview

 

Note: Packet capture is taken on BIG-IP with "--f5 ssl" tcpdump option and packet capture is decrypted by pre-master secret log file. Without decryption, you may not see whole TLS handshake messages. Refer to K31793632 for more in detail.

 

On the first TLS connection, after TLS handshake completed, BIG-IP sends frame-17 "New Session Ticket" TLS message to the client. On this "New Session Ticket" TLS message, you will see "session-ticket-timeout 123" is used. If "Session Ticket Timeout" is left as default "0", ticket_lifetime here will be 3600 seconds (default "Cache Timeout" value is used).

Figure: "New Session Ticket" TLS message to the client

 

Next, on the second TLS connection, the client set "key_share" extension and "pre_shared_key" extension in "Client Hello" TLS message. The client also set previously received "Session Ticket" value as "PSK Identity" on "pre_shared_key" extension.

Figure: "Client Hello" TLS message on second connection

 

BIG-IP virtual server received this "Client Hello" message, accepted it, and resumed connection without performing full TLS handshake.
