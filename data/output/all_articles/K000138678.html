K000138678: ASM/AdvWAF add a parameter to a URL to block or allow certain aspects of it.

Description

In order to properly set up a WAF you have to deal with many things. For instance a false/positive for an attack signature. When this happens you have a couple decisions to make…

  • What level do I deal with this at? It is for a parameter on a URL, but maybe it is best to deal with it on the actual URL based on network needs.
  • What other settings do I need to look at?

Environment

  • false/positive, Traffic Learning
  • URL, Parameter, Security Policy
  • ASM/AdvWAF

Cause

By the very nature of any type of firewall it has to fit your network to be the most effective. To do so each policy has to fit the traffic that it handles. This means adjustments need to be made. The BIG-IP by default is a “Deny All” device. Since that is not practical where and how do you make those necessary adjustments?

Recommended Actions

Let’s use the case of a false/positive. You get a block for an attack signature on a parameter used in a URL, but you know in your network this is a false/positive.

In most cases, you will create an allow for that attack signature, and you want that to be as small as possible. You could allow it for the entire URL in the event that it could be seen in different scopes in that URL/URI. But in most instances it needs to be targeted much tighter. To do so there are 2 ways:

IMPORTANT: In most cases, this should be as granular as possible. Applying this as Explicit, using the proper Positional (HTTP or HTTPS), and Method is likely the best option. All of that can be found in an Event Log entry in the case of a false/positive or in the Learning Suggestions.

If the URL already exists and just needs the parameter added to it:

  1. Go to Security ›› Application Security : URLs : Allowed URLs : Allowed HTTP URLs and at the top click on “URL Parameters”. Make sure at the top the correct policy is being displayed.
  2. Click Create.
  3. In the Event Log entry for the block will be a section titled “Parameter Name” that name goes into the section titled “Parameter Name”. In most cases leave it at the default of Explicit.
  4. In the section titled “Parameter Level” the URL Path and Method should already be there as will be the URL. These can be adjusted but should likely be left as is.
  5. There are several options. If the issue is something you need to deal with now then uncheck “Perform Staging”. For the other options you can read the information in the “Help” section found by clicking on that tab just below the F5 red ball.
  6. The most common other adjustment will be Parameter Value Type.
  7. To deal with the false/positive attack signature click on Attack Signature in just about the middle of the webpage. Wait for the attack signatures to load. Then using the attack signature ID found in the Event Log search on it in the Global Security Policy Settings section.
  8. Once it shows up move it to the Overridden Security Policy Settings section. It will show up as ‘Disabled’.
  9. Click Create.
  10. Go to the policy and ensure you click Apply Policy.

Note: This can also be done from the Parameter section by going to Security ›› Application Security : Parameters : Parameters List, clicking Create and at the Parameter Level choosing URL.

If the URL does not exist:

  1. Follow the steps here to create the URL:  K29418033: Configuring allowed or disallowed URL lists
  2. Once that is done then follow the steps above.

Note: This can again be done from Security ›› Application Security : Parameters : Parameters List, and by using an existing URL path or create a new one.

Additional Information

The most common issue is to set the allow. When needed a block can be created. To block a URL or Parameter you would create one that is not allowed. The above article will cover URLs. For Parameters the articles in the Related Content section will help.
