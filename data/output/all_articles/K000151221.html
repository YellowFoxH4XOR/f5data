Description

HTTP profile "Known Methods" parameter does not work when HTTP2 profile is attached to virtual server and client request comes in with HTTP/2 protocol.
If only HTTP(1.x) profile is attached to virtual server or client request comes in with HTTP/1.1 protocol, "Known Methods" parameter works and specific HTTP method can be allowed by "Known Methods" HTTP profile parameter.

Here is example configuration.

ltm virtual /Common/http2_vs {
    destination /Common/10.1.1.202:443
    ip-protocol tcp
    mask 255.255.255.255
    pool /Common/http_pool
    profiles {
        /Common/custom-http-profile { }
        /Common/http2 {
            context clientside
        }
        /Common/my_clientssl_http2 {
            context clientside
        }
        /Common/tcp { }
    }
    serverssl-use-sni disabled
    source 0.0.0.0/0
    source-address-translation {
        pool /Common/my_snatpool
        type snat
    }
    translate-address enabled
    translate-port enabled
}
ltm virtual /Common/http1.1_vs {
    ip-protocol tcp
    mask 255.255.255.255
    pool /Common/http_pool
    profiles {
        /Common/custom-http-profile { }
        /Common/my_clientssl_http2 {
            context clientside
        }
        /Common/tcp { }
    }
    serverssl-use-sni disabled
    source 0.0.0.0/0
    source-address-translation {
        pool /Common/my_snatpool
        type snat
    }
    translate-address enabled
    translate-port enabled
}
ltm profile client-ssl /Common/my_clientssl_http2 {
    app-service none
    cert-key-chain {
        web001.f5ss_ubuntu2204server1ca.f5ss_0 {
            cert /Common/web001.f5ss.local
            chain /Common/ubuntu2204server1ca.f5ss.local
            key /Common/web001.f5ss.local
        }
    }
    defaults-from /Common/clientssl
    inherit-ca-certkeychain true
    inherit-certkeychain false
    renegotiation disabled
}
ltm profile http /Common/custom-http-profile {
    app-service none
    defaults-from /Common/http
    enforcement {
        known-methods { PATCH CONNECT DELETE GET HEAD LOCK OPTIONS POST PROPFIND PUT TRACE UNLOCK }
        unknown-method reject
    }
    proxy-type reverse
}

 

On HTTP profile, "PATCH" method is specifically added to "known-methods" list and "unknown-method" parameter is set to "reject".
With this configuration, expected behavior is that client request with "PATCH" method is allowed to pass through virtual server and request should be load-balanced to pool member. However, when HTTP2 profile is attached and client request uses HTTP/2 protocol, request with "PATCH" method is blocked. Client will receive HTTP2 GOAWAY / RST_STREAM response.

 

Here is example packet capture. Client comes in with "PATCH" method on both HTTP/2 and HTTP/1.1 request. With same custom HTTP profile, HTTP/2 request is blocked although HTTP/1.1 request is allowed to pass through.

Environment

  • HTTP2 profile and HTTP profile are attached to virtual server.
  • On HTTP profile, "Unknown Method" property is set to "Reject".
  • On HTTP profile, to allow specific method (i.e., PATCH), "Known Methods" list is customized with specific method.
  • Client request comes in with HTTP/2 protocol.
