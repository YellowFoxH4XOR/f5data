K000137531: VELOS system controller may become stuck in an "in-progress" state during rolling software upgrade

Type
Known Issue
Published
2023-11-10
Updated
2025-01-07
Applies to
  • F5OS
  • F5OS-C: 1.5.0, 1.5.1, 1.6.0, 1.6.1
Source
https://my.f5.com/manage/s/article/K000137531

VELOS system controller may become inoperative during rolling software upgrade, indicate an "in progress" state, and log a 'No such file or directory' error.

This issue occurs when the following condition is met:

  • You attempt a rolling software upgrade on your F5 VELOS system controllers

Rolling software upgrades allow you to install F5OS-C 1.2.0 or later on one F5 VELOS system controller at time in order to limit downtime. Out-of-service upgrades install the new software on both system controllers at the same time resulting in a service outage. This issue occurs during a rolling upgrade from F5OS-C 1.5.0 or later. During the upgrade process, one of the system controllers successfully completes the software installation; however, the other system controller fails to complete the upgrade process and becomes inoperable. When this occurs, the affected system controller is no longer reachable using the management address.

Impact

The F5OS upgrade process fails and one of the F5 VELOS system controllers becomes inoperable.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The F5 VELOS system controller install status shows in-progress and the upgrade never completes. For example:

    syscon-1-active# show system image
                                            SERVICE  ISO          INSTALL
    NUMBER OS VERSION VERSION VERSION STATUS
    -------------------------------------------------------------------------
    1                1.6.1-19136 1.6.1-19136 -              success
    2                1.5.1-14085 1.5.1-14085 -              in-progress

  • The management address on the affected system controller is unreachable.
  • You are unable to connect to the system controller as root from the active system controller (for example, ssh controller-#).  The controller should be accessible over the ccpeer link.
  • Platform services are not running.
  • When you access the affected system controller, either by using the console or by connecting over the ccpeer link, you notice the following:
    • Some of the files in /var/docker/config/ are broken symlinks (env_var, env_var.patch, platform.yml, platform.patch.yml)
    • A log message similar to the following example is in the /var/log/sw-mgmt.debug file with the error No such file or directory:

      ERROR: sw-mgmt: priority=error msgid=0x3501000000000153 msg=Unexpected error importing controller services 1.6.1-19136: ('Connection aborted.', FileNotFoundError(2, 'No such file or directory'))

Workaround

If your system has encountered this issue, you can work around the issue by performing the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the active system controller as root using SSH.
  2. Log in to the standby system controller with SSH as root using the internal ccpeer link. By default, if a chassis uses RFC6598 IP addressing, the IP addresses of the system controllers on this network are the following:
    • controller-1: 100.65.7.51
    • controller-1: 100.65.7.52

    You can find the IP address of the peer controller on the ccpeer link by entering the following command:

    echo "peer controller: $(ifconfig ccpeer | grep -Po '(?<=inet )([^.]+\.){3}')$(( 53 - $(grep Slot /etc/PLATFORM | cut -d':' -f2 | tr -d ' ')))"

  3. Verify that both system controllers have the same set of software images present by comparing the output of the ls /var/import/staging/*.iso command on both system controllers.
  4. On the offline system controller, stop the sw-mgmt service by entering the following command:

    systemctl stop sw-mgmt

  5. On the offline system controller, make a backup copy of the import.json file by entering the following command:

    cp /var/import/import.json ~/import.json.bak

  6. On the offline system controller, enter the following command to copy import.json from the working system controller over the ccpeer link:
    • If controller-1 is working, and controller-2 is offline, enter the following command: scp 100.65.7.51:/var/import/import.json /var/import/import.json
    • If controller-1 is offline, and controller-2 is working, enter the following command: scp 100.65.7.52:/var/import/import.json /var/import/import.json
  7. On the offline system controller, start the sw-mgmt service by entering the following command:

    systemctl start sw-mgmt

  8. Wait about 5 to 10 minutes for the start up process to complete (you can monitor progress by running the tail -f /var/log/sw-mgmt.debug command), and then run the following command to list the system controller services versions that the sw-mgmt service has imported:

    echo list cc_iso | nc -U /var/sw-mgmt.unix

  9. After confirming the imported system controller services versions, restart the offline system controller by entering the following command:

    reboot

    After the system controller restarts, it should continue the installation process.

If your system has not yet encountered this issue, you can avoid this issue either by performing an out-of-service software upgrade on the F5 VELOS system controllers, rather than a rolling software upgrade, or by manually adding a systemd drop-in file for the sw-mgmt service on each F5 VELOS system controller. For more information about performing an out-of-service software upgrade, refer to the Install or Upgrade Software chapter in the VELOS Systems: Software Installation and Upgrade manual. To manually add a systemd drop-in file for the sw-mgmt service on the system controllers, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

Note: Ensure you add the systemd drop-in file to each F5 VELOS system controller on the affected VELOS system.

  1. Log in to one of the F5 VELOS system controllers as root using SSH.
  2. Enter the following command to create a new directory:

    mkdir /etc/systemd/system/sw-mgmt.service.d/

  3. Enter the following command to create a systemd drop-in file:

    echo -e '[Unit]\nWants=docker.service\nAfter=docker.service' > /etc/systemd/system/sw-mgmt.service.d/deps.conf

  4. View the contents of the file by entering the following command:

    cat /etc/systemd/system/sw-mgmt.service.d/deps.conf

    The output from the command should appear as follows:

    [root@controller-2 ~]# cat /etc/systemd/system/sw-mgmt.service.d/deps.conf
    [Unit]
    Wants=docker.service
    After=docker.service

  5. Enter the following command to reload systemd:

    systemctl daemon-reload

  6. Verify the service is functioning properly by entering the following command:

    systemctl status -l sw-mgmt

  7. Enter the following command to verify the sw-mgmt service now has an explicit dependency on docker:

    systemctl list-dependencies sw-mgmt | grep docker

  8. Log in to the other system controller as root.
  9. Perform steps 2 - 7 on the other system controller.

If needed, you can remove the workaround by renaming the drop-in file and reloading systemd on each system controller individually. To do so, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to one of the F5 VELOS system controllers as root using SSH.
  2. Enter the following command to rename the systemd drop-in file adding a .disabled extension:

    mv /etc/systemd/system/sw-mgmt.service.d/deps.conf /etc/systemd/system/sw-mgmt.service.d/deps.conf.disabled

  3. Reload systemd by entering the following command:

    systemctl daemon-reload

  4. Log in to the other system controller as root.
  5. Perform steps 2 - 3 on the other system controller.
