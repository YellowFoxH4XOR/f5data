Topic

The switch-over daemon (sod) causes the BIG-IP system to change to active or standby and provides failover capability. Enabling debug logging is useful when you want to troubleshoot failover issues.

Description

sod debug logging is controlled through the following database variables:

  • failover.debug enables debug logging to the /var/log/sodlog file. Prior to BIG-IP 13.0, enabling this results in continuous heartbeat logging that occur approximately once every 100ms. Beginning in BIG-IP 13.0, when you enable this database variable, the system logs only when there are failover transitions.
  • failover.debugsteadystate is available beginning in BIG-IP 13.0. Enabling this database variable results in the same logging behavior in versions prior to BIG-IP 13.0, in which there is continuous heartbeat logging approximately once every 100ms.
  • failover.printpeerstate logs peer state information and is not enabled by default. Enable this database variable to include peer information.

Important: Enabling sod steady state debug logging is extremely verbose and quickly increases the log file size. You should closely monitor the size of /var/log/sodlog and immediately disable logging as soon as logging is no longer necessary.

Procedure

You can enable sod debug logging by performing the following procedure:

  • To enable any of the database variables, use the following command syntax:

    tmsh modify sys db <DB variable> value enable

    For example, to enable sod debug logging, enter the following command:

    tmsh modify sys db failover.debug value enable

    sod debug messages are now logged to the /var/log/sodlog file.

You should disable this database variable as soon as debugging is no longer necessary. To do so, enter the following command:

tmsh modify sys db failover.debug value disable

Understanding the log messages

Whenever failover transitions occur, the system logs to /var/log/sodlog. You may observe an output similar to the following:

leaving standby @1002 peer dead fo_cond 0 15:02:34
Leaving as_standby state
Entering as_active state
compat_active : unit_m = 3 peer_m = 0 event = 0 15:02:34

  • fo_cond: The fo_cond value is 1 if there is any failover action configured. For example, VLAN failsafe.
  • The following table includes explanations of the log messages.
    MessageDescription
    event_cycleA heartbeat message was received from the unit.
    compat_activeThe unit goes active.
    compat_standbyThe unit goes to standby.
    sync_sigtermsod received a sigterm signal and is exiting.
    compat_sigu1sod wants to failover, either due to an internal event or due to a failover command initiated by an administrator.

  • The unit_m information indicates the high-availability (HA) status of the host.

    unit_munit_status
    0standby
    1unit 1 in active/active
    2unit 2 in active/active
    3active

  • The peer_m information is only available when network failover is activated. peer_m can be -1 when network failover is not configured or when network traffic is interrupted. If both HA systems become active, both host systems report unit_m = 3 and peer_m = -1.

    peer_mpeer status
    -1unable to reach
    0standby
    1unit 1 in active/active
    2unit 2 in active/active
    3active

  • The system logs a state parameter when you configure hardware failover. If the cable is not in place, this value is always 0x0. With a failover cable in place, the value for status represents the peer status with the following interpretations.

    statuspeer status
    0x0standby
    0x1active

Recommendations

When enabling sod debug logging, you should consider the following factors:

  • Steady state debug logging is verbose. You should monitor the size of /var/log/sodlog when enabling this feature.
  • To remove the /var/log/sodlog file, you should disable the failover.debug database variable first.
  • Along with enabling sod debug logging, you should perform a TCP capture, listening to the IP addresses used by both HA systems.
