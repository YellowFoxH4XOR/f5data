Prober functionality

Question:
The 3-DNS Controller's online help indicates that the function of the probers is to determine the availability and path of LDNS. The 3-DNS Controller's manual indicates that probers are used to check the availability of virtual servers. Do probers do both?

Answer:
Probers perform two functions: In the context of LDNS, probers perform path probing/metrics. In the context of servers (such as BIG-IP, 3-DNS, and hosts), probers are used to determine the availability of virtual servers.

Number of probes per virtual server

Question:
How many virtual servers can one 3-DNS Controller probe and what are the timing considerations (TTLs, probing intervals, expirations, and so forth) that are involved?

Answer:
As of version 3.0, there are no official stress-testing probing statistics available on the 3-DNS Controller. The short answer is that one 3-DNS Controller probe can probe "a lot" of servers; generally, far more than most customers would use.

The number of virtual servers that one 3-DNS Controller can probe is highly dependent on the network configuration and traffic load, and is limited by the following factors:

  • Number of prober factories
  • Amount of RAM
  • Bandwidth

big3d can easily send 50 probes per second for host-based virtual servers (these take more power than BIG-IP probes). Each prober factory takes up some physical memory, but the biggest limitation is the availability of bandwidth.

The formula for the bandwidth used is as follows, and includes a 5 second delay between each round of probing, which would give us 480 virtual servers (less 20% to be conservative):

((Host data refresh/2)/2)*50) = 600 probes
((Host data refresh/2)/2)*50) - ((Host data refresh*20)/100) = 480 virtual servers /p>

F5 Networks is aware of existing configurations that can poll 300 host-based virtual servers while the system is idle. There are also configurations that poll 1,100 BIG-IP-based virtual servers, successfully probing all of them.

As for the timing aspects of probing, the 3-DNS Controller Product Development team recommends using the defaults (90-second polling intervals for host servers, a 120- second TTL;, BIG-IP is 20 and 60, respectively).

As for the timing aspects of probing, the F5 Networks Product Development recommends that you use the defaults. For the 3-DNS Controller, the defaults are 90 second polling intervals for host servers with a 120 second TTL; for BIG-IP, the defaults are 90 second polling intervals for host servers with a 60 second TTL.

If you attempt to lower these values, do so while carefully monitoring the amount of probing resources available (either by checking big3d traffic or by using tcpdump to view the connections initiating from a particular 3-DNS Controller) and verify that the changes are not negatively impacting name resolution service or LDNS statistics gathering.

Check the resources by viewing the statistics in the 3-DNS Controller Configuration utility. The default settings are configured with breaks of at least 5 seconds between rounds of probing. It is important to verify that there isn't too much overlap. You do not want a constant stream of full-sized packets sent.

How many virtual servers can I define for one 3-DNS Controller?

Question:
Can we have 300, 500, or 1000 virtual servers defined to one 3-DNS?

Answer:
A 3-DNS Controller can probe well over 1,000 virtual servers on a BIG-IP, depending on the volume of all other network traffic and system load. However, the same considerations and limitations that apply to the number of probes also apply to the number of defined virtual servers. Those considerations and limitations are:

  • Number of prober factories
  • Amount of RAM
  • Bandwidth

Probing unavailable data centers

Question:
How does 3-DNS behave when a data center is marked unavailable?

Answer:
If data center load balancing is being used and a data center is marked unavailable, the 3-DNS Controller will not direct requests to that data center.

If data center load balancing is being used and all data centers are marked as unavailable, the 3-DNS Controller will use its fallback mechanism for that wideip.

Note: F5 Networks recommends that you configure the fallback mechanism as return to DNS.

If data center load balancing is not being used and a data center is marked unavailable, the 3-DNS Controller will not send requests to the unavailable host or virtual server unless the fallback mechanism is configured. In that case, a host/virtual server/data center may be returned even though it is considered down.

If topology load balancing is being used and one pool completely fails (for example, the 3-DNS Controller checked the source, destination, and weight of all matching entries and none of them worked because they were down) the 3-DNS Controller will randomly choose the next pool.

Probing data centers marked unavailable by the administrator

Question:
Will the 3-DNS Controller continue probing virtual servers defined as members of data centers if they have been marked unavailable/down by the administrator?

Answer:
If an administrator marks a virtual server down it will not be probed. If an administrator marks a data center that contains virtual servers as down, the virtual server will not be probed.

Unresponsive host of a virtual server

Question:
How does the 3-DNS Controller behave if a host of a virtual server is unresponsive?

Answer:
The 3-DNS Controller will not send requests to an unresponsive (down) host of a virtual server unless the fallback mechanism is in use, in which case a host may be returned even if it is considered down.

Probing and failure discovery

Question:
Can I fine-tune the 3-DNS Controller to speed up probing and failure discovery performance?

Answer:
Although, in general, F5 Networks recommends that you use the default settings for the various components of the 3-DNS Controller, you can speed up probing by making the following adjustments:

  • Use more prober factories (maximum of 56).
  • Lower the TTLs and the get_data intervals.
  • Increase the various Data Refresh Interval by a factor of two (to start).

Note:Note: You must test all changes when adjusting settings to something other than the default.

Optimizing LDNS probing

Question:
If I have a fast network, can I do anything to increase the speed of probing, such as change the TCP Retransmission intervals or add more CPUs?

Answer:
LDNS probing is self-optimizing. On every cycle, it will attempt to increase the number of probes it completed in the previous cycle. You can view these statistics in the Path Regulation Increment section Configuration utility under StatisticsProbers.

Adding more CPUs will not make increase speed because the 3-DNS Controller is not dependent on the processor; it is dependent on network speed.

Multithreading probes

Question:
Is the 3-DNS Controller capable of multithreading its probes, or are they all sequential?

Answer:
Probers are multithreaded in that they are not non-blocking. Probers are sequential in the order that they are started; however, one prober will not block another prober. This means that an additional probe can be sent without waiting for the first probe to complete.
