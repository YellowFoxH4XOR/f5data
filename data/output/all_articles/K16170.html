Known Issue

GET requests sent to the iControl REST API, for a non-existent pool member, fail to indicate that the pool member was not found.

This issue occurs when the following condition is met:

  • A GET request is sent for a specific pool member that does not exist.

The GET request response for a non-existent pool member should return an error message similar to the following example, to clearly indicate the resource was not found:

{
    "code": 404,
    "errorStack": [],
    "message": "01020036:3: The requested Pool Member (/foo/bar /foo/10.10.10.15 80) was not found."
}

However, when this issue occurs, the system returns a response that lacks detailed information about the pool member.

Impact

Returned responses for GET requests may fail to identify that the requested resource was not found.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • When using the iControl REST API, the response to a member-level GET request for a non-existent pool member fails to clearly identify that the requested resource was not found. Instead, the returned response for a non-existent pool member will resemble a valid response that lacks detailed information about the pool member. The response may appear similar to the following example:

    {
        "fullPath": "/foo/10.10.10.15:80",
        "generation": 787,
        "kind": "tm:ltm:pool:members:membersstate",
        "name": "10.10.10.15:80",
        "partition": "foo",
        "selfLink": "https://localhost/mgmt/tm/ltm/pool/~foo~bar/members/~foo~10.10.10.15:80?ver=11.6.0"
    }

    Whereas the response for an existent pool member provides additional details, similar to the following example:

    {
        "address": "10.10.10.10",
        "connectionLimit": 0,
        "dynamicRatio": 1,
        "ephemeral": "false",
        "fqdn": {
            "autopopulate": "disabled"
        },
        "fullPath": "/foo/10.10.10.10:80",
        "generation": 790,
        "inheritProfile": "enabled",
        "kind": "tm:ltm:pool:members:membersstate",
        "logging": "disabled",
        "monitor": "default",
        "name": "10.10.10.10:80",
        "partition": "foo",
        "priorityGroup": 0,
        "rateLimit": "disabled",
        "ratio": 1,
        "selfLink": "https://localhost/mgmt/tm/ltm/pool/~foo~bar/members/~foo~10.10.10.10:80?ver=11.6.0",
        "session": "user-disabled",
        "state": "user-down"
    }

Workaround

To work around this issue, you can perform a pool-level request for all members and then iterate through the items returned to determine if a pool member exists.
