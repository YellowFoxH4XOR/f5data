K000162782: BIG-IP LTM HTTP Proxy CONNECT and Redirect Errors Caused by Absolute-Form URI Handling

Type
Support Solution
Published
2026-08-05
Updated
2026-08-05
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000162782

Description

BIG-IP LTM proxy traffic can generate malformed HTTP CONNECT requests and HTTP redirects when an HTTP redirect iRule concatenates [HTTP::host] with an absolute-form [HTTP::uri]. The upstream proxy may interpret the resulting hostname incorrectly and return 504 Unknown Host.

 

Example:

CONNECT Web_1.example.comhttp:443 HTTP/1.1

 

Expected format:

CONNECT Web_1.example.com:443 HTTP/1.1

 

Proxy response:

HTTP/1.1 504 Unknown Host

 

A malformed redirect may also contain a duplicated host and scheme:

Location: https://Web_1.example.comhttp://Web_1.example.com/path/bookmark.jsp...

 

Environment

BIG-IP

 

Cause

The redirect iRule assumes that [HTTP::uri] contains only a path, such as /path/bookmark.jsp.

Proxy traffic can instead contain an absolute-form URI that includes the scheme and hostname:

http://Web_1.example.com/path/bookmark.jsp

 

The iRule concatenates the host and complete URI:

https://[HTTP::host][HTTP::uri]

 

When [HTTP::uri] already contains an absolute-form URI, this produces an invalid redirect similar to:

https://Web_1.example.comhttp://Web_1.example.com/path/bookmark.jsp

 

The malformed redirect can subsequently generate an invalid CONNECT request. The upstream proxy interprets Web_1.example.comhttp as the destination hostname and returns 504 Unknown Host.

 

Answer/Recommended Actions

  • Review the iRule applied to the HTTP redirector virtual server.
  • Confirm whether the iRule concatenates [HTTP::host] and [HTTP::uri] without accounting for absolute-form URIs.
  • Update the iRule to remove the applicable absolute-form prefix before constructing the redirect. Adapt the prefix to the application and proxy traffic.

The logic should:

    • Detect whether [HTTP::uri] begins with the expected absolute-form prefix.
    • Remove only that prefix. You may need to modify the redirector iRule as shown below:
when HTTP_REQUEST { 
   if {[HTTP::uri] starts_with "Web_1.example.com/"} {
     HTTP::uri [string map {"Web_1.example.com/" ""} [HTTP::uri]]
   }
     HTTP::redirect https://[HTTP::host][HTTP::uri] 
 }
}
    • Preserve the remaining path, query string, and encoded characters.
    • Construct the HTTPS redirect using the normalized URI.
  • Test the change with:
    • Standard origin-form requests:
       GET /path HTTP/1.1
    • Absolute-form requests:
       GET http://host/path HTTP/1.1
    • HTTPS CONNECT requests:
       CONNECT host:443 HTTP/1.1
    • Requests containing query parameters.
    • Requests containing encoded characters.
    • Requests traversing both the forward-proxy and application virtual servers.

 

  • If the issue recurs, capture traffic on both sides of the BIG-IP virtual server and compare:
    • The request received from the client or downstream proxy.
    • The request sent by BIG-IP to the upstream proxy.
    • Any HTTP redirect returned by the application server.
  • Determine whether the malformed request was:
    • Received from the client.
    • Modified by BIG-IP processing or an iRule.
    • Introduced by another proxy in the chain.

 

  • Review the BIG-IP configuration for additional HTTP profiles, traffic policies, iRules, proxy-chaining settings, or access policies that may modify the request or response.
  • Removing and re-adding the HTTP and HTTP Proxy Connect profiles may reinitialize proxy-processing state or existing connections, but this should be treated as a recovery action rather than the root-cause correction.
