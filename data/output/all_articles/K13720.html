Topic

This article discusses the behavior of the BIG-IP system upon receiving diameter messages from the client side when all members of a pool for a diameter virtual server are disabled, forced offline, or marked down. This article assumes that you have configured a diameter virtual server to perform message-based load balancing (MBLB) by assigning it with the diameter and mblb profiles.

Description

Upon establishing a TCP connection to the BIG-IP system, a diameter client sends its messages over the TCP connection to the BIG-IP system to be load balanced across the pool of diameter servers assigned to the diameter virtual server.

When one or more pool members are down (disabled, forced offline, or marked down by health monitor) and the diameter virtual server receives a new diameter message, the BIG-IP system load balances the message to the remaining available pool member(s).

When all the pool members are down (forced offline or marked down by health monitor) and the diameter virtual server receives a new diameter message, the BIG-IP system is unable to load balance the message. As a result, the BIG-IP responds back to the diameter client with a TCP RST and shuts down the TCP connection. This behavior prevents the diameter client from sending any further diameter messages to the BIG-IP system until it re-establishes a new TCP connection.

Note: If the pool members are manually disabled, the BIG-IP system does not respond to the diameter client with a TCP RST.

Recommendations

If you have a recurring issue with the availability of diameter pool members, you may be able to mitigate the issue using the iRule LB_FAILED event.

For example, the following iRule attempts to recheck the assigned pool for available pool members after 100 milliseconds:

Note: The following iRule may not apply to all environments. F5 recommends you author an iRule that may work best for your application environment. Additionally, adding an iRule will increase the resources used by the associated virtual server. Depending on the type and volume of the connections, this processing may introduce noticeable latency. F5 recommends testing any such changes in an appropriate environment.

when LB_FAILED {
after 100
if { [active_members [LB::server pool]] > 0 } {
LB::reselect pool [LB::server pool]]
}
}

For information about using the iRule LB_FAILED event, refer to DevCentral.
