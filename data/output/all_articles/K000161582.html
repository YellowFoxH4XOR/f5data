Description

This article describes three recommended methods to block untrusted bots, such as Amazonbot, using BIG-IP ASM and LTM. These approaches are applicable when default Bot Defense or ASM policies do not block specific bots.

Environment

  • AdvWAF/ASM, LTM
  • L7 Security for Bot Defense.

Cause

The request may include an unwanted or unknown bot. If that happens it may be necessary to add protection against it.
Example:GET /index.html HTTP/1.1
Connection: keep-alive
Pragma: no-cache
Cache-Control: no-cache
X-Requested-With: XMLHttpRequest
User-Agent: Mozilla/5.0 AppleWebKit/537.36 (KHTML, like Gecko; compatible; Amazonbot/0.1; +https://example.com/bot-info) Chrome/100.0 Safari/537.36
Accept: application/json, text/javascript, */*; q=0.01
sec-ch-ua: "Not:A-Brand";v="99", "HeadlessChrome";v="145", "Chromium";v="145"
sec-ch-ua-mobile: ?0
sec-ch-ua-platform: "Windows"
Sec-Fetch-Site: same-origin
Sec-Fetch-Mode: cors
Sec-Fetch-Dest: empty

In the above example Amazonbot has been added to the User-Agent and would be considered an unknown bot. 

Answer/Recommended Actions

There are 3 ways to possibly deal with this using a BIG-IP...

  1. Using AdvWAF/ASM create a custom bot signature and add it to the policy. For example... 
    1.  To add that to the policy follow these steps...Writing Custom Bot Signatures
      1. To get the proper Bot Category may require some research, but it is mostly informative so as to provide a category to fit it in.
  2. Using an iRule* that focuses on the User-Agent. There are a couple of ways to do this...
    1. Create an iRule the simply drops/discards the connection (No RST is sent to the client). Example:when HTTP_REQUEST {
          # Block requests containing "Amazonbot" in the User-Agent (case-insensitive)
          if { [string tolower [HTTP::header value "User-Agent"]] contains "Amazonbot" } {
              # Drop the connection immediately
              drop
          }
      }
      1. Use reject instead of drop if you want a TCP RST returned.
      2. The contains operator performs a substring match, so Amazonbot will match Amazonbot/0.1, Amazonbot/1.0, etc. Use the full string Amazonbot/0.1 if you want to restrict to that specific version only.
      3. The virtual server must have an HTTP profile attached 
    2. Another way is to use an iRule using HTTP::respond to return a 403 Forbidden instead of silently dropping the connection...when HTTP_REQUEST {
          if { [HTTP::header "User-Agent"] contains "Amazonbot" } {
              log local0. "Blocked User-Agent: [HTTP::header "User-Agent"] from [IP::client_addr]"
              HTTP::respond 403 content "Access Denied" "Content-Type" "text/plain"
          }
      }
      1. HTTP::respond sends an HTTP response directly from the BIG-IP to the client and terminates the request — the connection is not forwarded to the pool member.
      2. The virtual server must have an HTTP profile attached for HTTP::respond to work (same prerequisite as before).
      3. No drop or reject is needed after HTTP::respond — the command handles connection termination implicitly for that request.
    3. The third way is to use a LTM Local Traffic Policy. However, while is is simpler to manage than iRules for straightforward header matching it is less flexible for complex logic.

Additional Information

These three methods should work for a Malicious Bot that identify themselves via a recognizable User-Agent string, also. However, there are some important caveats...

  1. Malicious bots may spoof their User-Agent: Unlike Amazonbot, which identifies itself openly, a truly malicious bot may disguise itself as a legitimate browser (e.g., Chrome, Firefox). In that case, User-Agent matching alone would be insufficient.

  2. Bot Defense is better suited for malicious bots: Bot Defense uses JavaScript challenges, device fingerprinting, and behavioral analysis — making it much harder for malicious bots to bypass compared to simple header matching.

  3. ASM Attack Signatures: For malicious bots carrying attack payloads (e.g., SQL injection, XSS), ASM policy inspection would be the most appropriate layer of defense, as it inspects the actual request content rather than just the headers.

For malicious bots, a layered approach is strongly recommended:

  • Bot Defense as the first line of defense
  • DoS Protection to mitigate volumetric attacks
  • ASM to catch any attack payloads that bypass the first two layers
