Known Issue

Always-On Management (AOM) unexpectedly resets itself.

This issue occurs when the following condition is met:

  • You are running one of the following BIG-IP platforms:
    • BIG-IP 2000/4000
    • BIG-IP 5000/7000
    • BIG-IP 10000/12000

Impact

The AOM watchdog feature does the following:

  • Initializes AOM again
  • Recovers AOM from unexpected fault conditions back to proper operating state

However, this recovery mechanism interrupts existing secure shell (SSH) sessions opened with AOM. When you use best practices to properly configure the network high availability (HA) failover feature, application traffic should not be affected. For more information about best practices for configuring HA failover, refer to the Workaround section of this article.

For BIG-IP 10000 and 12000 series, an AOM reset does not affect HA failover.

For BIG-IP 2000, 4000, 5000, and 7000 systems, when you use best practices to configure the HA failover feature, an AOM reset does not result in a failover or disruption to application traffic. However, when you do not use best practices to configure the HA failover feature, the BIG-IP system can fail over to a peer device when AOM resets. When you configure the HA failover feature using only the management interface, an AOM reset can result in an unacceptable, transient active-active state in a single traffic group for the HA devices.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The LED alarm light turns red and the LCD panel displays a message similar to the following example:

    Lop connection is restored

    Note:  Versions of BIG-IP prior to 11.4.0 do not display this message on the LCD screen

  • You observe messages in the /var/log/ltm file that appear similar to the following examples:

    warning chmand[6246]: 012a0004:4: getLopReg Dev error: LopDev: sendLopCmd: Lopd status: 2 packet: action=1  obj_id=67  sub_obj=0  slot_id=ff  result=0  len=3  crc=0  payload=24 98 4    (error code:0x0)
    err chmand[7436]: 012a0003:3: GET_MEDIA failure (status=0x2) page=0x1 reg=0x0 : File mgmtif/BourneMgmtIfSvc.cpp Line 376
    err chmand[6246]: 012a0003:3: GET_STAT failure (status=0xffffffff) page=0x%24 reg=0x98  : File mgmtif/BourneMgmtIfSvc.cpp Line 250

  • You observe additional log messages in the /var/log/ltm file that appear similar to the following examples:

    err lopd[5622]: 013d0004:3: Not connected to LOP (retrying) : LopDev: Assuming LOP is in bootloader mode
    notice lopd[5622]: 013d0006:5: Connected to LOP
    notice lopd[5622]: 016d0001:5: Lop connection is restored
    notice chmand[6246]: 012a0005:5: Interface: 8.0 is UP
    notice chmand[6246]: 012a0005:5: Interface: mgmt is DOWN
    notice chmand[6246]: 012a0005:5: AOM total reset count: 1
    notice chmand[6246]: 012a0005:5: AOM watchdog reset count: 1
    notice chmand[6246]: 012a0005:5: AOM pin reset count: 1

  • BIG-IP systems in an HA configuration fail over or erroneously shift to an active-active state with a single traffic group while AOM resets.

Resolution

Status

F5 Product Development has assigned ID 562296 to this issue. F5 has confirmed that this issue exists in the products listed in the Applies to (see versions) box, located in the upper-right corner of this article. For information about releases, point releases, or hotfixes that resolve this issue, refer to the following table.

Type of fixFixes introduced inRelated articles
ReleaseNoneNone
Point release/hotfixNoneNone

Workaround

There is no workaround. To ensure resiliency, as a best practice, F5 recommends that you include both the management interface and a Traffic Management Microkernel (TMM) interface in HA failover configurations. For more information, refer to K16049: Limiting network failover disruptions.
