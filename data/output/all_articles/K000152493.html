Description

HTTPS health monitors with SSL profiles on BIG-IP LTM, pool members may be incorrectly marked down or experience monitor flapping after updating the SSL certificate. This issue comes with log errors like:

LTM logs: var/log/ltm

Jun 12 03:29:31 <hostname> notice mcpd[<pid>]: Pool <pool_name> member <member_name> monitor status up. [ <monitor_name> up ]  [ was down for 0hr:2mins:16sec ]
Jun 12 03:29:50 <hostname> notice mcpd[<pid>]: Pool <pool_name> member <member_name> monitor status down. [ <monitor_name> down; last error: <monitor_name> Response matched regex @<timestamp>. ]  [ was up for 0hr:0min:19sec ]
Jun 12 03:31:02 <hostname> notice mcpd[<pid>]: Pool <pool_name> member <member_name> monitor status up. [ <monitor_name> up ]  [ was down for 0hr:1min:12sec ]
Jun 12 03:31:20 <hostname> notice mcpd[<pid>]: Pool <pool_name> member <member_name> monitor status down. [ <monitor_name> down; last error: <monitor_name> Response matched regex @<timestamp>. ]  [ was up for 0hr:0min:18sec ]

When you enable Monitor logging on the node, you will observe log entries similar to the following:

var/log/monitors/<monitor_name_IP_address>.log

:Cannot load private key from file /config/filestore/files_d/Common_d/certificate_key_d/Common:<...>
:Open SSL error - error:...:digital envelope routines:EVP_DecryptFinal_ex:bad decrypt.
:Open SSL error - error:23077074:PKCS12 routines:PKCS12_pbe_crypt:pkcs12 cipherfinal error.
:Open SSL error - error:2306A075:PKCS12 routines:PKCS12_item_decrypt_d2i:pkcs12 pbe crypt error.
:Open SSL error - error:0907B00D:PEM routines:PEM_READ_BIO_PRIVATEKEY:ASN1 lib.

Environment

  • BIG-IP LTM
  • HTTPS Health Monitor
    • SSL Profiles
    • SSL key is encrypted with a passphrase

Cause

The external monitoring process (bigd) does not support loading or using encrypted (passphrase-protected) private keys for HTTPS monitors. bigd relies on OpenSSL, which cannot access an encrypted key without manual passphrase entry at runtime. In contrast, in-TMM monitoring can use encrypted keys because it leverages TMM, which has access to decrypted key material in memory.

Recommended Actions

To resolve this issue, choose one of the following solutions:

Option 1: Enable in-TMM monitoring for HTTPS monitors that use SSL profiles with encrypted private keys. In-TMM monitoring natively supports server-SSL profiles and can handle encrypted keys. 

Note: If you have a large number of HTTPS monitors with custom cipher strings, review compatibility before enabling in-TMM monitoring, as cipher string syntax differs between OpenSSL (bigd) and TMM.

To enable in-TMM monitoring:

tmsh modify sys db bigd.tmm value enable

Option 2: Remove the passphrase from the private key before importing it into BIG-IP. This allows the bigd process to load the key successfully. Perform the following procedure:

Impact of procedure: If you add a passphrase to a key that a virtual server is currently using, SSL connections to the virtual server may fail until the system updates the related SSL profile configuration with the newly added passphrase and loads the changes into memory. To avoid service disruption, perform this procedure during a scheduled outage.

1. Log in to the command line.

2. Change directories to 

cd /config/filestore/files_d/Common_d/certificate_key_d/

3. Locate the private SSL key that you want to remove a passphrase from, and then use the following command syntax:

openssl rsa -in <encrypted name>.key -out <unencrypted name>.key

4. Install the unencrypted SSL private key into the BIG-IP filestore by using the following command syntax:

tmsh install /sys crypto key <key_name> from-local-file <key_path_and_name>

5. Save your changes by entering the following command:

tmsh save sys config

6. Update the corresponding SSL profiles and remove the passphrase for the SSL keys that are no longer encrypted.
