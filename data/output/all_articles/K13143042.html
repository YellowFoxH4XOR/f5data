Description

Procedure to follow when upgrading any SSLO v4.x or below box to a newer version
If the HA pair is not broken before upgrading a pre-5.x release of SSLO, the following symptoms might be seen:
  • Deployment of SSLO iApp fails after upgrade
  • iAppsLX objects from old SSLO seen on iAppsLX admin GUI page blocking deployment of SSLO 5.x+

Environment

  • SSLO HA pair
  • running older version of SSLO (pre-5.x)
  • performing upgrade to 5.x+
Cause

Gossip protocol communication between HA pair could result in stale SSLO RESTDB config copied between boxes even after SSLO has been uninstalled from one box before admin uninstalls SSLO on 2nd box.

Recommended Actions

Important: When upgrading SSLO from pre-5.x to 5.x+, ensure that HA pair is broken before uninstalling SSLO.
Full procedure for upgrade:
  1. Break HA pair.
  2. Undeploy current pre-5.x SSLO deployment from both the boxes.
  3. Uninstall the SSLO RPM from both the boxes.
  4. Verify that all SSLO-related MCP objects were deleted, using the CLI command "tmsh list sys application service" (or check the iAppsLX page in admin GUI, if it's enabled). If any SSLO-related MCP objects remain for some reason even after the SSLO uninstall, manually delete them. The SSLO uninstall should generally delete all SSLO-related MCP objects automatically.
  5. Install new software build into the new partition. Make sure not to navigate to the SSLO menu page in admin GUI (as that would save some SSLO configuration in RESTDB, and the HA pair needs to be set up before that happens).
  6. Rejoin HA.
  7. On the active box, navigate to the SSLO menu page to automatically trigger the SSLO config process on both boxes.
  8. Configure and deploy SSLO on the active box (it should auto-propagate to standby box via gossip).
 

Additional Information

Possible pitfalls/important points to note:

Even when an admin opts to move to a newer TMM version without enabling config carry-forward – that setting only results in the big-ip not moving/carrying over the MCP objects. The REST database is still carried forward to the new partition, therefore the REST DB must be cleaned either by an SSLO uninstall, or by a 'clear-rest-storage -d' before the software build is installed into the new partition.
The first 4 steps above (undeploy, uninstall and clearing rest storage) should be completed before even installing a newer build. Whenever installation of a new build starts, the current state of MCP objects and rest storage is replicated in the newer partition.
