Topic

The default behavior of the BIG-IP ASM system is to block and report all Request For Comment (RFC) compliance violations in order to prevent requests with improper formatting or header content from being sent to the server. There are, however, some situations in which an administrator would want to send such requests to the server, such as in the case where a line feed (LF) is to be used as a line separator. RFC compliance is controlled through the use of an enforcement mask. The enforcement mask is set using the internal parameter non_rfc_bitmask.

Note: For information about accessing the internal parameters page, refer to K3853: Accessing the System Variables page.

Each bit in the bitmask represents a non_rfc_compliance case. For each bit, a value of 0 means that the case is RFC compliant; a value of 1 means that the case is not RFC compliant. The bit count determines whether to issue a NO_RFC_COMPLIANCE parse status or not, when the case occurs in the request parsing. Each case of non RFC compliance will be checked against the bitmask to determine whether to issue non RFC compliant violation message.

Supported cases, HEX values, and case definition

The following table displays supported cases, HEX values, and case definitions:

CaseHEX valueDefinition
POST request with Content-Length: 00x0001A post with a Content-Length header value of 0 (zero) is non-RFC compliant.

Note: POST request with a Content-Length header value of zero does not violate RFC 2616, but is considered a violation to the BIG-IP ASM system.

Header name with no header value0x0002Cases of a header name without a header value, without a colon (header-name\r\n, not header-name:\r\n) are considered non-RFC compliant
LF line separator0x0004The RFC line separator is only CRLF, not LF. However, some servers may know how to parse LF as a line separator as well. Therefore, the LF line separator can be configured as RFC compliant.
Several Content-Length headers0x0008More than one Content-Length header is considered non-RFC compliant.

Note: RFC 2616 does not state that a request with more than one Content-Length header is a non-RFC request. However, this behavior is common in header injection attacks.

Chunked request with Content-Length header0x0010Each chunk length within a chunked request is specified separately. The whole request does not have a content length and is considered non-RFC compliant.
Bad unescaping or incorrect unescaping0x0020The percentage sign ( % ), as stated in RFC 2616, must be followed by two hexadecimal characters, otherwise it is non-RFC compliant.
Body in GET or HEAD requests0x0040GET or HEAD requests should not be followed by a request body; only POST requests should.
DEFAULT_non_rfc_bitmask setting value: 590x003Is blocked except for bit 0x04 (LF line separator).

The DEFAULT_non_rfc_bitmask setting represents checks for:

  • POST request with Content-Length: 0 (0x01)
  • Header name with no header value (0x0002)
  • Several Content-Length headers (0x08)
  • Chunked request with Content-Length header (0x0010)
  • Bad escaping (0x20)
Enabling cases

You can enable different cases by adding the HEX values together and then converting the resulting value to a decimal to assign to the non_rfc_bitmask.

For example, you can configure the non_rfc_bitmask internal parameter to send a message to the forensics log on the following cases for non-RFC violations:

  • POST request with Content-Length: 0 (bit representation: 0x01)
  • LF line separator (0x04)
  • Several Content-Length headers (0x08)
  • Bad unescaping (0x20)

The non_rfc_bitmask value for the above cases is 45. This value is determined by adding the HEX values of each case together, then converting sum from HEX to a decimal value that is used for the non_rfc_bitmask value, as follows:

Hex(0x01 + 0x04 + 0x08 + 0x20) = Hex(0x2d) = Dec(45)

Note: If you update any of the internal parameters on the /dms/internal/ screen, the system generates the following warning message when you save the updates:

Please enter a valid <<UseAdvancedVerifier>>, the value must be Integer, the range 0 - 2147483647.

To avoid this issue, set the UseAdvancedVerifier field to 0 (zero), and then save the updates. For more information, refer to K6582: Known Issue: A default value for ASM internal parameter UseAdvancedVerifier is not defined.
