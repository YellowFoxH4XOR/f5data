Known Issue

In this example, you deploy an SSL Orchestrator in a horizontally scaled architecture in which there is a pre-load balancer balancing traffic across multiple SSL Orchestrator systems. By default, SSL Orchestrator does not support this approach to scaling if the systems shares Layer 3 (L3) or HTTP services. You can modify the SSL Orchestrator so that it does support this scaling.

Impact

If multiple SSL Orchestrator devices send traffic to an L3 or HTTP service device, the service devices have no way of knowing how to route the traffic back to the correct SSL Orchestrator system. The workaround involves enabling SNAT on the service virtual servers to determine from which system the traffic originates and then configuring the service device to route traffic back to the correct SSL Orchestrator using policy-based routing.

Workaround

Note: In this approach, the source address for the traffic becomes the SSL Orchestrator SNAT address, not the original address. This may impact how the service device handles and reports on the intercepted traffic.

Impact of workaround: When you change configuration of certain objects, the system re-deploys the various BIG-IP objects to match your new configuration. This re-deployment overwrites any existing BIG-IP objects without warning about existing changes. Before performing this procedure, you must first refer to the warnings and directions in the Disabling Strict Updates section of K00805840: SSL Orchestrator known issues and workarounds .

Deploying horizontally scaled architecture:

  1. Deploy and configure an SSL Orchestrator system including a high-availability (HA) pair/standby system.
  2. Deploy and configure a second SSL Orchestrator system on which you disable auto-manage on any L3 or HTTP services and set up unique manual addressing for them.

    Note: Make sure that you use addresses that are not in use elsewhere in the system. Check the network / self IP addresses to understand see which addresses are in use.

  3. On both SSL Orchestrator systems, disable strict update and enable SNAT on the L3 and HTTP services.
  4. Configure the service devices to correctly route traffic to the correct SSL Orchestrator using policy-based routing.
Note: To enable policy-based routing, see the documentation for that specific service device. You want to route traffic out of the same interface on which it arrives.

Enabling SNAT for service virtual server

  1. Navigate to SSL Orchestrator > Services.
  2. For each of the L3 and HTTP services, perform the following steps:
    1. Click the service to edit.
    2. Under General Properties, clear the Strict Update check box.
    3. Add the text FC:ADD SNAT to the Description.
    4. Note the IP network(s) that is(are) configured for the To Service.
    5. Click Finished.
  3. Navigate to Local Traffic > Address Translation > SNAT Pool List.
  4. Click Create.
  5. Name the SNAT pool, based on the service.
  6. Under Configuration, for Member List, for IP Address, enter an IP address range within the network for the service.

    Note: The address must start with the third or later available address in the network range.

  7. Verify that the addresses are not presently in use.
  8. Verify that any addresses selected are not used by service devices or other systems in that network.
  9. Click Finished.
  10. Repeat these steps for each service.
  11. Navigate to Local Traffic > Virtual Servers.
  12. Locate the sending virtual servers for L3 and HTTP services.

    Note: The virtual servers are named: ssloS_<service name>-t and ssloS_<service name>-u.

  13. For each of these, do the following:
    1. Click the virtual server.
    2. Under Configuration, for Source Address Translation, click SNAT and for SNAT Pool, click the appropriate SNAT pool.
    3. Click Update.
