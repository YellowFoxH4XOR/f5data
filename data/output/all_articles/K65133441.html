K65133441: Mounting vCMP guest vmdisk as loop device using kpartx utility

Type
Support Solution
Published
2020-12-28
Updated
2025-02-06
Applies to
  • BIG-IQ
Source
https://my.f5.com/manage/s/article/K65133441

Description

This solution describe how to access data on vCMP guest vmdisk when the vCMP guest is inaccessible or decommissioned and only the virtual disk image is available.
Following the procedure you will be able to access to the data contained in the vmdisk such as configuration files (bigip.conf) or files in the /var/log/ directory or UCS files can be extracted

The kpartx utility on the BIG-IP can be used. (please refer further detail for kpartx manual).
 

Environment

  • vCMP host with kpartx
  • vCMP Guest vmdisk


Cause

None

- Assuming the goal is to extract the following ltm log file from the guest vmdisk

# head /var/log/ltm
Feb 12 08:31:17 localhost info mprov:1534:: Invoked as: /usr/bin/mprov.pl (pid=1534) --logicaldisk --boot --quiet
Feb 12 08:31:17 localhost info mprov:1534:: \'Checking for and completing any logical disk transactions:\'

3. first ensure the guest is set to configured state on the host (The procedure below is to be performed on the vCMP host)

Example
vcmp guest G1 {
    state configured
}

The kpartx command creates device maps from partition tables. Each guest storage image has a partition table embedded in the file.

- Run the kpartx utility to list partition device mappings attached to a file-based storage image.
- In the example below G1.img is the vmdisk image

# kpartx -l G1.img
loop0p1 : 0 587663 /dev/loop0 1
loop0p2 : 0 2096640 /dev/loop0 587664
loop0p3 : 0 311888304 /dev/loop0 2684304
loop deleted : /dev/loop0

- Add the partition mappings to the recognized devices in /dev/mapper/.

# kpartx -a /shared/vmdisks/G1.img

- Test that the partition mapping worked. There should be new devices in the /dev/mapper/ directory

vmdisks # ll /dev/mapper | grep loop
lrwxrwxrwx. 1 root root       8 2019-02-12 15:18 loop0p1 -> ../dm-18
lrwxrwxrwx. 1 root root       8 2019-02-12 15:18 loop0p2 -> ../dm-19
lrwxrwxrwx. 1 root root       8 2019-02-12 15:18 loop0p3 -> ../dm-20

- Run vgscan to find the new volume groups

# vgscan
  Reading all physical volumes.  This may take a while...
  Found volume group "vg-db-vda" using metadata type lvm2
  Found volume group "vg-db-sda" using metadata type lvm1

- Activate the volume group on the partition (called vg-db-vda for the guest) with the vgchange -ay command.

# vgchange -ay vg-db-vda
  16 logical volume(s) in volume group "vg-db-vda" now active

- Use the lvs command to display information about the new volumes. The volume names (the LV column) are required to mount the volumes.

- The files are now available for reading in the /mnt/guestboot directory. Read or copy the files. In this case, the ltm log was of interest

# head ltm
Feb 12 08:31:21 localhost info mprov:1533:: Invoked as: /usr/bin/mprov.pl (pid=1533) --logicaldisk --boot --quiet
Feb 12 08:31:21 localhost info mprov:1533:: \'Checking for and completing any logical disk transactions:\'

- Unmount the device so the guest image can be reused by the guest. If the device is mounted the guest cannot access the image and therefore cannot start.

# umount /mnt/guestboot/

- Disconnect the volume group vg-db-vda

# vgchange -an vg-db-vda
  0 logical volume(s) in volume group "vg-db-vda" now active

- Disconnect the image file from the partition mappings.

# kpartx -d /shared/vmdisks/G1.img
loop deleted : /dev/loop0
 

Additional Information

For kpartx man page, run the below command in bash
# man kpartx
