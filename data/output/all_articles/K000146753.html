Description

  • There are a range of different timeout settings available in HTTP load balancer configuration in Distributed Cloud Console. What does each one of them do?

Environment

  • F5® Distributed Cloud (XC)
  • F5 Distributed Cloud HTTP Load Balancer

Answer/Recommended Actions

Key points:

  • Timeouts may operate at the HTTP layer, the TCP layer, or in one case, both.
  • TCP Timeouts track TCP activity over a connection, i.e. exchange of packets.
  • HTTP Timeouts track activity over a HTTP stream, i.e. request/response transaction.  Underlying TCP activity may not reset a HTTP timeout. 
  • Timeout Value: All timeout values are specified in milliseconds (ms) in the XC console. You can adjust these values depending on the needs of the application.

4Connection Timeout

Origin Pool

TCP

Upstream TCP connection establishment

Maximum time to establish an upstream TCP connection.  That is, the origin endpoint must return a TCP SYN+ACK within this period or a failure is declared.

This is not an idle timeout.  It becomes irrelevant once the TCP connection is established.

It is extremely rare to have a rational justification to increase this timeout above 5-10 seconds.  If the remote endpoint hasn't responded to TCP SYN within a few seconds, it's not going to.

5HTTP Idle TimeoutOrigin PoolTCP + HTTPHTTP/1.1 activity over upstream pooled TCP connections

Idle timeout for upstream connection pool connections.  This is the max time interval for which an upstream pooled connection will be kept open without any further HTTP activity.

This may be thought of as a keepalive timeout.  It applies to pooled upstream connections that have been kept open by a HTTP/1.1 Connection: keep-alive in a prior request.  It applies to HTTP/1.1 traffic only; HTTP/2 operates over a single TCP connection with multiplexing handled within the protocol itself.

The origin pool's HTTP Idle Timeout should be set lower than the effective timeout on the origin endpoint itself.

 

Under "Other Settings":

300,000

When the origin pool timeout is set to a higher value than the actual HTTP/keepalive timeout on the origin endpoint, a race condition can occur when the origin closes a connection the moment XC is writing data to it.  The data packet arrives at the origin on a half-closed connection and is returned a TCP RST, upon which XC returns a 503 to the client: 

upstream_reset_before_response_started{connection_termination}

6Per Try Timeout

HTTP LB Route - Retry Policy

HTTP

Retried upstream HTTP requests

The amount of time that can elapse without a response before a retried request is considered failed.

When creating a custom Retry Policy, ensure that

(per_try_timeout * num_of_retries) <= timeout  (of the route or LB)

 

NOTE: a retry policy is inapt for remediation of other timeouts (there will be a "timeout loop").
