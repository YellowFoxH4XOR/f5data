Description

Observing a failure message similar to the following in /var/log/openshift.log when attempting to add a VELOS blade to a chassis:

- Executing Ansible Command:
      - /usr/bin/ansible-playbook -vv --flush-cache -i /tmp/omd/etc_ansible_add /usr/share/ansible/openshift-ansible/playbooks/openshift-node/scaleup.yml
...
fatal: [blade-2.chassis.local -> controller-1.chassis.local]: FAILED! => {"msg": "The task includes an option with an undefined variable. The error was: {{ hostvars[groups.oo_first_master.0].openshift.master.api_url }}: 'dict object' has no attribute 'master'\n\nThe error appears to be in '/usr/share/ansible/openshift-ansible/roles/openshift_manage_node/tasks/main.yml': line 5, column 3, but may\nbe elsewhere in the file depending on the exact syntax problem.\n\nThe offending line appears to be:\n\n# systemd to start the master again\n- name: Wait for master API to become available before proceeding\n  ^ here\n"}

Note in particular, the error:

{{ hostvars[groups.oo_first_master.0].openshift.master.api_url }}: 'dict object' has no attribute 'master'

Environment

  • VELOS chassis
  • Adding blades

Cause

The /etc/ansible/facts.d/openshift.fact file on one or both controllers is not present, or is missing some of the expected content.

For example, it may only contain the following content:

[root@controller-1(VELOS.broken.lab) ~]# </etc/ansible/facts.d/openshift.fact jq .
{
  "node": {},
  "common": {
    "public_ip": "100.65.3.50",
    "ip": "100.65.3.51",
    "public_hostname": "controller-1.chassis.local",
    "generate_no_proxy_hosts": true,
    "portal_net": "100.75.0.0/16"
  }
}

On a working system, the file should typically contain around 96 lines if the JSON content is passed through jq:

[root@controller-1(VELOS.fixed.lab) ~]# </etc/ansible/facts.d/openshift.fact jq . | wc -l
96

ID1590425 tracks this issue. The fix for this bug will verify the openshift.fact file and re-build it, if needed.

Recommended Actions

You can re-populate the openshift.fact file on each controller by running an ansible playbook inside the orchestration_manager container with the following command:

docker exec orchestration_manager /usr/bin/ansible-playbook -vv --flush-cache -i /tmp/omd/etc_ansible_hosts /usr/share/ansible/openshift-ansible/playbooks/openshift-master/config.yml

This process takes approximately 7 minutes, and should not cause any negative impact to the chassis. The ansible-playbook output will be printed directly to the terminal.

Additional Information

When ansible runs it connects to the target host to gather details (facts) about it. The /etc/ansible/facts.d directory can be used to store additional local facts on the target host itself. The openshift.fact file specifically is used by openshift-ansible, which allows VELOS to provision openshift cluster nodes via ansible.
