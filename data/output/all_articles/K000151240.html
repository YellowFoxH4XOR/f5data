Description

A Virtual Server configured for the same subnet as a directly connected interface on the BIG-IP will not show up in the routing table as a Kernel Route.

Environment

  • BIG-IP
  • Zebos

Cause

  When a forwarding virtual server is configured on the same subnet as a locally assigned IP subnet (configured on a VLAN or self IP), the system already considers that subnet as directly connected to the BIG-IP system. In the BIG-IP's kernel routing table, the locally configured subnet is already marked as a "connected" route. Therefore, the forwarding virtual server does not create a new or distinct kernel route. Instead, it relies on the existing connected route associated with the self IP or the VLAN.

  The "redistribute connected" option in BIG-IP (via BGP in ZebOS) announces directly connected routes from the kernel routing table into the BGP routing table. However, this redistribution only applies to routes explicitly marked as "connected" in the kernel routing table. Since the forwarding virtual server does not introduce a new route and simply overlaps with the existing locally configured subnet, it does not generate an additional connected route. As a result, there is no new kernel route to redistribute.

 The "redistribute kernel" command in BGP does not redistribute directly connected routes; it only redistributes non-connected routes present in the kernel routing table. As such, unless a network statement is manually added or "redistribute connected" is used, the desired subnet will not be advertised via BGP.  As such, using "redistribute connected" may result in all connected subnets being advertised, which may be undesirable.

Recommended Actions

To have this forwarding virtual server to be added into the route table, you must configure 'redistribute connected'.

If it is necessary to only advertise some directly connected routes the creation of route-maps and ip prefix-lists can be used to filter route advertisements. 

For example to prevent Advertising the '192.168.21.0/24' subnet, this must be added to a prefix-list which is applied to a route-map.   This route-map then is applied to the neighbor.   Note that the DENY_NETS route-map must include the allowed prefixes to ensure that the subnets that are necessary are included to be advertised.  In this case '10.120.6.0/24' subnet.   

router bgp 65502
 max-paths ebgp 4
 bgp log-neighbor-changes
 bgp graceful-restart restart-time 120
 redistribute kernel
 redistribute connected
 neighbor 10.77.0.30 remote-as 65505
 neighbor 10.77.0.30 soft-reconfiguration inbound 
 neighbor 10.77.0.30 route-map DENY_NETS out      
!
ip prefix-list ALLOW seq 5 permit 10.120.6.0/24
ip prefix-list LOCAL_NETWORKS seq 10 permit 192.168.21.0/24
!
route-map DENY_NETS deny 10
 match ip address prefix-list LOCAL_NETWORKS
!
route-map DENY_NETS permit 20
 match ip address prefix-list ALLOW
