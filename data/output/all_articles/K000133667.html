Description

After upgrading your system, you may observe that ASM incorrectly blocks legitimate traffic. Specific violations include: 

  • 'Illegal HTTP Method' for valid 'GET' requests, even though 'GET' is explicitly allowed in the policy. 
  • 'Illegal URL' violations for URLs that match wildcard patterns defined in the policy. 

Environment

  • BIG-IP ASM

Cause

The issue may be due to one of the following: 

  1. The policy restoration process being interrupted during the upgrade, leading to incomplete policy application. 
  2. A lack of disk space in /var partition after the upgrade.  

If you see logs in /var/log/ts/asm_config_server.log similar to the message below, the ASM config upgrade was complete after device upgrade.  

asm_config_server.pl|INFO|Jun 13 11:58:27.969|21594|F5::ASMConfig::Handler::LoadComplete::load_complete,,populating completed successfully 

If you do not see these logs, please proceed with the mitigations in the Recommended Actions section to complete the upgrade.  DCC tables may have been corrupted during the upgrade process. This may be because another reboot was initiated by users after booting into new disk location, before the process was complete. 

Otherwise, the most likely cause of ASM incorrectly blocking legitimate traffic after an upgrade is that the system is short on disk space in the /var partition.  If so, you should see messages like the following:  

In /var/log/ltm:

 Recommended Actions

 

If policy restoration was interrupted:

If it appears that the process was not complete, please boot back to the original boot location, delete the new boot location, and reinstall the new software image, and then upgrade again. 

An ASM config upgrade can take a long time, so it's recommended to wait until you see the 'populating completed successfully' log before doing anything else. 
 
Re-applying the policies can fix the issue as well. 

If you are short on disk space in the /var partition:  

You can work around the problem with the process below.   

Note: Restarting ASM will interrupt traffic processing. Pease make these changes in a maintenance window. 

Run this perl one-liner to re-populate DCC.HSL_PROFILES 

perl -MF5::DbUtils -MF5::Hsl::Populate -MF5::PrepareConf::Hsl -MF5::LWP::UserAgent -e 'my $dbh = F5::DbUtils::get_dbh(database_username => "root"); die "error:: dbh undefined\n" unless $dbh; F5::Hsl::Populate::populate_defaults(dbh => $dbh, plc_dbname => "PLC", dcc_dbname => "DCC", logger => $logger,); my $prepare_hsl = F5::PrepareConf::Hsl->new(dbh => $dbh); die "error:: prepare_hsl undefined\n" unless $prepare_hsl; $prepare_hsl->prepare(hsl_profile_id => 1); $prepare_hsl->prepare(hsl_profile_id => 2);' 

Then restart asm to trigger generating DCC.HSL_DATA_PROFILES

bigstart restart asm
