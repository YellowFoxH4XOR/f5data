Description

When deploying F5 Distributed Cloud Customer Edge (CE) software within an enterprise environment, there are multiple ways to attach the CE to the existing network infrastructure. The choice of deployment and routing model impacts traffic flow, high availability, performance, and operational complexity. Understanding the available attachment options is essential for selecting the model that best fits the enterprise's network architecture, cloud environment, and team expertise.

  • What are the available network attachment options for an F5 Distributed Cloud Customer Edge site?
  • What environments can an F5 Distributed Cloud Customer Edge be deployed in?
  • How does traffic reach the Customer Edge nodes for each attachment model?
  • What are the differences between Layer 3, Layer 2, and external attachment models for Customer Edge deployments?
  • How does high availability work across multiple Customer Edge nodes?
  • How do custom VIPs behave differently across the Layer 2, Layer 3, and external attachment models?

Environment

  • F5 Distributed Cloud (SaaS)
  • Customer Edge (CE) software — Mesh persona (not AppStack)
  • One or more of the following CE deployment platforms:
    • Hypervisor (VMware or KVM)
    • Hyperscaler (AWS, Azure, or GCP)
    • Baremetal
  • Single-node or three-node CE cluster (three nodes required for High Availability)
  • One or more of the following network attachment types:
    • Layer 3 — Static Routing
    • Layer 3 — BGP Routing
    • Layer 2 — VRRP
    • External — Inline Load Balancer
    • External — Out-of-Path DNS Load Balancer
  • Custom VIPs configured on CE nodes (applicable to Layer 2 and Layer 3 attachment models)

Answer/Recommended Actions

F5 Distributed Cloud Customer Edge (CE) software can be deployed across four platform types and attached to the network using five deployment models, grouped into three attachment types. The appropriate model depends on the enterprise's network capabilities, routing expertise, high availability requirements, and cloud architecture.

CE Deployment Platforms

  • Hypervisor: VMware or KVM
  • Hyperscaler: AWS, Azure, or GCP
  • Baremetal: Baremetal Site
  • Kubernetes: K8s Site (Kubernetes attachment has unique considerations not covered in this article)

High Availability Requirements

  • A single-node CE deployment is supported but provides no redundancy.
  • To achieve High Availability, F5 Distributed Cloud requires exactly three nodes to form a cluster, due to the underlying software stack requirements.
  • Worker nodes can be added to any three-node cluster across all attachment models to provide horizontal scale and performance.

Attachment Type 1: Layer 3 Attached

Layer 3 attachment uses IP routing to direct traffic to CE nodes. Custom VIPs are configured on CE nodes and act as loopback addresses — locally significant to the CE software. Traffic from the network is routed to these VIPs, after which the CE software matches the application based on port, SNI, or host header information.

Two Layer 3 models are available:

  • Static Routing:
    • Static routes are configured on the network, each targeting the SLO or SLI interface of a CE node as the next hop to reach a custom VIP.
    • Simple and quick to configure, requiring less routing expertise.
    • Limitations may apply depending on the route/switch fabric's support for Equal Cost Multi-Path (ECMP) routing, or if static routes persist when the next hop is unreachable (no ARP response).
  • BGP Routing:
    • Each custom VIP is dynamically injected as a /32 route into the network's route/switch fabric via BGP.
    • If a CE node becomes unavailable, its /32 route is automatically withdrawn from the routing fabric, providing dynamic failover.
    • Supports ECMP for active/active/active traffic distribution across all three CE nodes.
    • Requires BGP capability on the existing network and routing expertise to configure.

Attachment Type 2: Layer 2 Attached (VRRP)

Layer 2 attachment uses VRRP (Virtual Router Redundancy Protocol) to share a custom VIP across the three CE nodes. This model is familiar to engineers experienced with network appliances such as firewalls, load balancers, or BIG-IP (analogous to traffic groups and floating IPs).

  • The VIP is active on only one node at a time, creating an Active/Standby/Standby topology per VIP.
  • The active node's physical MAC address is returned during ARP resolution for the VIP. When a new node becomes active, a Gratuitous ARP (GARP) is sent to update the MAC-to-VIP association across the broadcast domain.
  • In F5 Distributed Cloud, VRRP active node selection is random. Priority settings are not exposed.
  • When multiple custom VIPs are configured with VRRP, each VIP may become active on a different node, allowing all three nodes to actively process traffic — each handling a specific VIP and its associated applications.
  • Worker nodes participate in VRRP and can be used to scale the cluster horizontally.

Attachment Type 3: External Attachment

External attachment uses a load balancer or DNS to distribute traffic to CE node interfaces, without relying on custom VIPs or VRRP. This model is common in cloud environments where Layer 2 technologies such as ARP/GARP are not available.

Two external attachment models are available:

  • Inline (In-Path) Load Balancer:
    • An external L4 or L7 load balancer is placed in the traffic path to distribute requests across CE nodes.
    • The SLO or SLI interface of each CE node is used as the load balancer pool target (custom VIPs are less necessary in this model).
    • Worker nodes can be added to the external LB pool to scale the cluster horizontally.
    • L4 LB consideration: Source IP preservation depends on the LB technology used; source IP may be lost.
    • L7 LB consideration: Source IP can be preserved via headers, but TLS certificates must be managed at the L7 LB, which may introduce operational overhead.
  • Out-of-Path DNS Load Balancer:
    • DNS is used to distribute traffic across CE nodes. This can range from simple round-robin DNS A-records to advanced Global Server Load Balancing (GSLB) with health checking and intelligent response logic.
    • The CE node's SLO or SLI interface IP is used as the DNS LB target.
    • Worker nodes can be added as additional DNS targets to scale the cluster.
    • Consideration: Even with health checking enabled, traffic failover is subject to DNS cache and TTL expiration, which may result in delayed failover compared to other attachment models.

Additional Information

The F5 Distributed Cloud Customer Edge (CE) software is the same software stack deployed in F5's Regional Edges (RE). The key distinction is that Regional Edges are F5-managed SaaS data planes, while Customer Edges are deployed and operated within the enterprise's own environment. This gives enterprises the ability to extend F5 Distributed Cloud's application delivery and security capabilities into their own data centers, co-location facilities, and cloud environments.

The CE software supports two operational personas:

  • Mesh: Provides Multi-Cloud Networking, Application Delivery, and Application Security capabilities as a proxy data plane. This is the persona covered in this article.
  • AppStack: Transforms the CE into a managed Kubernetes cluster, enabling workloads to be deployed directly onto the CE. AppStack is not covered in this article.

Custom VIPs on CE nodes are locally significant addresses that behave similarly to loopback interfaces on a traditional router. They are not advertised externally by default and are used by the CE software as the listener addresses for application traffic. The CE software then matches incoming connections to the appropriate application configuration based on Layer 4–7 criteria (port, SNI, host header).

The five deployment models can be mixed and matched within an enterprise environment. Different CE sites, or even different applications within the same CE site, may use different attachment models depending on the specific network and application service requirements of each environment.

When evaluating which attachment model to use, consider the following factors:

  • Routing capability: Does the existing network support BGP or ECMP? If not, static routing or Layer 2 attachment may be more practical.
  • High availability model: Active/active/active (Layer 3 BGP with ECMP) vs. active/standby/standby per VIP (VRRP) vs. load balancer-managed distribution (external attachment).
  • Source IP preservation: Required for accurate logging, security policy enforcement, and geolocation. Layer 3 and Layer 2 models preserve source IP natively; external attachment may require additional configuration depending on LB type.
  • Cloud vs. on-premises: Layer 2 technologies are often unavailable in public cloud environments, making Layer 3 or external attachment the preferred models for hyperscaler deployments.
  • Operational expertise: BGP routing provides the most dynamic and resilient model but requires routing knowledge. Static routing and VRRP are more accessible for teams without deep networking backgrounds.
