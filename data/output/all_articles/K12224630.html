Description

BIG-IP and other routers configured with OSPF stub are not advertising routes.

Environment

  • BIG-IP
  • ZebOS
  • OSPF Stub

Cause

Stub areas (example "area 3.3.3.3 stub") only allow LSA types 1,2 and 3.  Routes pulled in to OSPF via redistribute are external routes, and can not be used in a stub area. 

Recommended Actions

The resolution to this issue is to use an NSSA area. This changes the stub rules slightly and also allows LSA type 7. The command to this are:
no area <ospf.id> stub
area <ospf.id> nssa

For an example, if the OSPF area is 3.3.3.3, the command would be as below.
no area 3.3.3.3 stub
area 3.3.3.3 nssa

This change needs to be done to all of the BIG-IP OSPF routes and also other OSPF routers.

Additional Information

Here are the possible LSA types for OSPF:

   LSA Type 1: Router LSA.
   LSA Type 2: Network LSA.
   LSA Type 3: Summary LSA.
   LSA Type 4: Summary ASBR LSA.
   LSA Type 5: Autonomous system external LSA.
   LSA Type 6: Multicast OSPF LSA.
   LSA Type 7: Not-so-stubby area LSA.
   LSA Type 8: External attribute LSA for BGP.

Stub areas (example "area 3.3.3.3 stub") only allow LSA types 1,2 and 3. Routes pulled in to OSPF via redistribute are external routes, and can not be used in a stub area. However, there is a workaround for this exact scenario, which is to use an NSSA area ("no area 3.3.3.3 stub / area 3.3.3.3 nssa").   This changes the stub rules slightly and also allows LSA type 7.

Once changing the area to NSSA, the virtual server's prefix will show up in the output of show ip ospf database, because it's now allowed. Just having it in the database means that other OSPF neighbours will see that data (it will show up in show ip ospf database on other routers in the same area), but only the ABR will do anything with that information (it will re-advertise it into OSPF as a type-5 LSA)

With area 3.3.3.3 set to NSSA, we see the prefix this on the ABR (next-hop IP addresses are NSSA routers inside area 3.3.3.3)

An example extract from show ip route

O N2    10.110.110.110/32 [110/20] via 172.16.116.111, clients, 00:01:56
                          [110/20] via 172.16.117.111, clients, 00:01:56

ltm-example.local[0]#show ip route 10.110.110.110/32
Routing entry for 10.110.110.110/32
  Known via "ospf", distance 110, metric 20,  External Route Tag: 0, best
  Last update 00:03:02 ago
  * 172.16.116.111, via clients
  * 172.16.117.111, via clients

Note that other routers (or zebos's) sitting entirely inside area 3.3.3.3 will NOT show the prefix in the routing table, because they are not ABRs (it will show up as a type 7 in the ospf database on those routers, but not in the route table). If one of those routers wanted to send a packet to 10.110.110.110, it would follow the default route towards area 0, which would then turn the packet around and send it back to what it knows as the next hop inside area 3.3.3.3.
