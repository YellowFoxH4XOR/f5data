K30425010: Understanding X-ENVOY-UPSTREAM-SERVICE-TIME in Envoy Access Logs

Description

Access Logs are standard outputs for istio-proxy container running beside application workload that outputs access information. By default, access log is enabled in Aspen Mesh. For information about configuring access logs, refer to K19302224: Configure Access Logs in Aspen Mesh.

The default format string of access log is shown as below:

[%START_TIME%] "%REQ(:METHOD)% %REQ(X-ENVOY-ORIGINAL-PATH?:PATH)% %PROTOCOL%"%RESPONSE_CODE% %RESPONSE_FLAGS% %BYTES_RECEIVED% %BYTES_SENT% %DURATION%%RESP(X-ENVOY-UPSTREAM-SERVICE-TIME)% "%REQ(X-FORWARDED-FOR)%" "%REQ(USER-AGENT)%""%REQ(X-REQUEST-ID)%" "%REQ(:AUTHORITY)%" "%UPSTREAM_HOST%"\n

In this article we discuss the X-ENVOY-UPSTREAM-SERVICE-TIME log entry, which is time in milliseconds spent by the upstream host processing the request and the network latency between Envoy and upstream host. For more information, refer to Envoy Access Logs and GitHub documentation. 

The access log collected from istio-proxy appears similar to the following example:

[2021-12-30T16:45:07.874Z] "GET /Redacted HTTP/2" 503 URX via_upstream - "-" 0 76 288 287 "-" "-" "807c075d-9469-465b-98dc-8579fba6fcf3" "nscp-w1-001:8081" "203.0.113.109:8081" outbound|8081||nscp-w1-001 192.168.28.26:41406 203.0.113.109:8081 192.168.28.26:64885 - default

Below shows a GET request with "807c075d-9469-465b-98dc-8579fba6fcf3" as REQ(X-REQUEST-ID), which is what Envoy uses to find the specific request. You can query for this string in your packet capture to follow the exact request. This packet capture was done on the pod level (closest to the Envoy proxy) and you can see that the time taken for the request to get a response of 503 in this case is 168 milliseconds which is different than 287 milliseconds shown in above access logs. 

10315   *REF*   192.168.28.26   203.0.113.109   HTTP2   243 HEADERS[99]: GET /Redacted/ 143
10323   0.168   203.0.113.109   192.168.28.26   HTTP2   215 HEADERS[99]: 503 Service Unavailable, DATA[99] (text/plain) 143
10325   0.168   192.168.28.26   203.0.113.109   HTTP2   79  RST_STREAM[99]  143

The following output is the first request in our capture with REQ “807c075d-9469-465b-98dc-8579fba6fcf3" but we got 2 more request with the same REQ ID:

10326   *REF*   192.168.28.26   203.0.113.109   HTTP2   175 HEADERS[101]: GET /Redacted 143
10335   0.032   203.0.113.109   192.168.28.26   HTTP2   172 HEADERS[101]: 503 Service Unavailable, DATA[101] (text/plain)   143
10336   0.032   192.168.28.26   203.0.113.109   HTTP2   79  RST_STREAM[101] 143
10337   *REF*   192.168.28.26   203.0.113.109   HTTP2   175 HEADERS[103]: GET /Redacted 143
10371   0.060   203.0.113.109   192.168.28.26   HTTP2   172 HEADERS[103]: 503 Service Unavailable, DATA[103] (text/plain)   143

These multiple requests with same REQ ID are because of the Envoy retries set by default in Aspen Mesh. After adding the time of all three requests (168+60+60) with time in between the reset stream, we get 287 shown in access logs. Therefore, X-ENVOY-UPSTREAM-SERVICE-TIME in access logs is sum of time taken by all the retries to server a request:

10315   *REF*   192.168.28.26   203.0.113.109   HTTP2   243 HEADERS[99]: GET /Redacted  143
10337   0.227   192.168.28.26   203.0.113.109   HTTP2   175 HEADERS[103]: GET /Redacted 143
10371   0.287   203.0.113.109   192.168.28.26   HTTP2   172 HEADERS[103]: 503 Service Unavailable, DATA[103] (text/plain)   143

Environment

  • Aspen Mesh: 1.9.x and higher

Cause

None 

Recommended Actions

None

Additional Information

You can check for the REQ ID in Hypertext Transfer Protocol 2 section for streams in Wireshark.
