Description

This documents describes the considerations that should be made with respect to idle timeout thresholds on F5 XC Origin Pools when connection reuse is enabled (as it is by default).

 

Environment

  • F5® Distributed Cloud (XC) HTTP Load Balancer
  • Origin Pools
  • HTTP/1.1
  • Connection Reuse
  • 503 Errors with connection_termination

Connection Reuse

Also referred to as HTTP persistent connection, HTTP keep-alive, or connection multiplexing, HTTP connection reuse is the concept of using a single TCP connection to send and receive multiple HTTP requests and responses, as opposed to opening a new connection for each request.

In a reverse proxy architecture like F5 XC, Connection Reuse is effectuated by the proxy adding the Connection: keep-alive header to requests forwarded upstream, then transmitting subsequent HTTP requests over that same persistent connection.  HTTP traffic from multiple distinct clients is therefore transmitted upstream over shared, reusable TCP connections that are held open until an idle timeout expires.

 

 

Connection Reuse mproves performance by allowing for HTTP request concurrency and reducing TCP connection overheads.  It is enabled by default on XC Origin Pools.

 

 

Note: HTTP/2 implements connection multiplexing within the protocol specification, making this topic moot.

 

 

The Idle Timeout Race

When Connection Reuse is in operation for upstream traffic from a reverse proxy, it becomes important to ensure the proxy, and not the upstream (origin) endpoint is the party responsible for idle connection closure.  If the origin endpoint initiates connection closure first, a race condition arises as follows:

  1. A connection has been idle for some time and its closure is initiated by the origin endpoint.
  2. At exactly the same moment (or within half the network RTT) the proxy sends a HTTP request on the same connection, which from its perspective remains established. 
  3. The data packet containing the HTTP request is received by the origin on a half-closed TCP connection.
  4. As an invalid TCP state transition, the origin endpoint rejects the data packet with FIN or RST..
  5. The proxy receives the FIN/RST and declares request failure.

 

 

In XC, this condition results in a 503 error returned to the client with rsp_code_details of upstream_reset_before_response_started{connection_termination}. 

In real world scenarios the condition typically manifests as intermittent occurrences of this 503 error.  Conversely, a problem presenting as intermittent connection_termination 503s is most commonly attributed to this condition.

 

 

Prevention

The condition is avoided by ensuring the TCP client (in this case, the XC Origin Pool) is the party responsible for closing idle pooled connections.  Therefore, the HTTP Idlle Timeout on the XC Origin Pool should be set to a value lower than that of the origin endpoint itself.

 

 

To determine the idle timeout enforced by the origin endpoint:

  1. Inspect its configuration.  The setting may be called Socket Timeout, Keepalive Timeout, Keepalive Interval, Idle Timeout, etc.
  2. Measure it from a packet capture:
    1. Start a tcpdump with appropriate parameters
    2. Send an HTTP/1.1 request with Connection: keep-alive and ensure the connection is held open.
    3. Wait for the endpoint to close the connection with FIN (or RST).
    4. Measure the time interval between the last data packet and the FIN.

This shows a keepalive timeout of 8 seconds.  The XC Origin Pool should thereto be set with HTTP Idle TImeout of under 8 seconds.
