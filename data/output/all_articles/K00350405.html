Description

The Same-Origin Policy is a fundamental security mechanism which restricts how a document (including scripts) that a web browser loads from one origin is able to interact with resources from another origin. The origin being defined by the scheme (e.g. HTTPS), hostname (e.g. www.example.com) and port (e.g. 443) being used to access the resource.

This helps isolate potentially malicious scripts, reducing attack vectors; for example, it prevents a malicious website (e.g. evil.example.com) from being able to read data, such as access tokens, from another site the victim is browsing (e.g. www.example.com).

Environment
A web application being delivered to a web browser on a client device (e.g., Chrome, Edge, Firefox etc)

Cause

  • None

Recommended Actions

Since the Same-Origin Policy is fundamental to security, it cannot be disabled and does not need to be enabled by the user – it is always-on*. Behaviour can be further restricted by setting headers relating to the Cross-Origin Resource Policy (CORP) or loosened by setting headers relating to Cross-Origin Resource Sharing (CORS).

*Note that Internet Explorer has some deviations from the standard in this regard which are not discussed here.

Additional Information
Two URLs have the same origin only if the protocol (e.g. HTTPS), port (e.g. 443) and host (e.g. www.example.com) are the same for both – for example, if a browser is rendering the page https://www.example.com/directory/page.jsp, the following is true:
 

URLOutcomeReason
https://www.example.com/otherdir/newpage.jspSame originPath differs
https://www.example.com/directory/subdirectory/page2.jspSame originPath differs
http://www.example.com/directory/page.jspDifferent originProtocol differs
https://www.example.com:8443/directory/page.jspDifferent originPort differs
https://host.example.com/directory/page.jspDifferent originHost differs

 
Cross-origin requests
 
The same-origin policy controls interactions between different origins (for example with XMLHttpRequest or JavaScript) and applies controls differently to different kinds of interactions. Broadly speaking:

  • Cross-origin reads are generally not allowed, however note that some embedding actions may leak cross-origin information (such as the dimensions of an embedded image)
  • Cross-origin embedding is generally allowed (such as including images within a web page from a third-party service)
  • Cross-origin writes are generally allowed (such as form submissions to a cross-origin destination)

Altering the behavior of Cross-origin requests
 
You can use the Cross-Origin Resource Sharing headers to allow cross-origin access for specific resources by specifying from which other hosts a browser is allowed to load content for a given URL.

To prevent cross-origin writes you can consider the use of a Cross-Site Request Forgery token for any resources that are not an entry point. For more information, refer to K80291425: What is a Cross-site Request Forgery (CSRF) attack?
