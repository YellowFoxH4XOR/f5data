Topic

In BIG-IP 15.0.0, F5 introduces the support for 0-RTT (Zero Round Trip Time) or early-data feature for resumed connections, which allows the TLS client to send data in the same packet as the ClientHello.

Description

The 0-RTT (early data) feature is introduced in TLS 1.3, which allows the TLS clients to send encrypted data in the same packet as the ClientHello during the handshake for resumed sessions. The client uses the PSK (Pre-shared key) to authenticate the server, encrypt the early data, and send it along with the ClientHello. This allows the server to respond immediately by including the requested data in the ServerHello/Finished message. This can significantly improve application performance by reducing the number of RTT (Round Trip Time) per TLS connection. For example, TLS 1.2 allows client resumed TCP connection to be established in a 1-RTT either using a session IDs or session tickets. In contrast, TLS 1.3 0-RTT eliminates an entire round trip time from the resumed TCP connections and enables the TCP connections to be established in 0-RTT (Zero Round Trip Time). This allows the client to include the actual application data on the first flight (early data).

The 0-RTT feature is disabled by default for BIG-IP systems and can be enable with or without anti-replay options in the ClientSSL profile.

The setting to configure 0-RTT is called Data 0-RTT in the advanced mode and the following three options are available for this setting:

  • Disabled: The 0-RTT (early data) is disabled by default, and any requests that are received that contain early-data will be rejected and the client should automatically resend without early-data.
  • Enabled With Anti-Replay: This enables early-data with anti-replay functionality. This is the recommended setting and specifies that applications can send data in the first TCP session after the TCP handshake completes rather than the ClientSSL holding early data until the handshake completes (client finished, handshake complete) and then delivered upwards to proxy/serverside. The BIG-IP provides optional protection against replay of early data through anti-replay protection. This allows the use of early data without additional requirements imposed on the back-end server.
  • Enabled Without Anti-Replay: This enables early-data without anti-replay protection. This setting is not recommended and specifies that early data without anti-replay protection can leave a TLS server exposed to a replay of data by a malicious TLS client.

You can use following procedure to configure 0-RTT feature in the ClientSSL profile:

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have access to the Configuration utility.
  • You have working knowledge of the TLS 1.3 protocol.
  • You have enabled TLS 1.3 on your BIG-IP system.

Procedure

Enabling the 0-RTT (early data) feature on a BIG-IP system

Impact of procedure: The impact of the procedure depends on the specific environment. In some cases, You may notice performance improvement of your applications when you enable the 0-RTT (early data) feature. F5 recommends that you test any such changes during a maintenance window and consider the possible impact on your specific environment.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Profiles > SSL > Client.
  3. Click Create.
  4. For Parent Profile, click clientssl.
  5. Select the Custom check box.
  6. For Configuration list, click Advanced.
  7. For Options List, enable TLS 1.3 by removing No TLS1.3 from the Enabled Options list.
  8. Now, Navigate to Data 0-RTT setting, specify the desired option from the list.
  9. Click Finished.

Recommendations

When configuring 0-RTT (early data) feature, you should consider the following factors:

  • F5 recommends that you enable 0-RTT (early data) with anti-replay functionality on your BIG-IP system. This protects your TLS server against replay of early data.
  • Depending on your application environment, your applications may benefit from faster connection establishment for existing sessions which are resumed, because no handshake messages have to go back and forth between client and server for the resumed session. However, you should perform thorough testing in your environment to secure your applications against security threats before you enable the feature in a production environment.
