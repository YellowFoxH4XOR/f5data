Introduction

F5 Networks includes SIP transaction persistence in its suite BIG-IP application layer functionality and we currently support load balancing and persistence to SIP proxy servers. The initial implementation (before BIG-IP version 4.5) supported SIP messages sent over UDP. As of version 4.5, BIG-IP supports SIP over TCP using the Universal Inspection Engine (UIE) and persisting on the Call-ID header.

Following is an overview of SIP as well as specific information about how to configure BIG-IP to add UDP SIP Call-ID persistence to a server pool.

The Session Initiation Protocol (SIP), as described in RFC 2543 (http://www.ietf.org/rfc/rfc2543.txt), is an application-layer control (signaling) protocol for creating, modifying and terminating sessions with one or more participants. These sessions include Internet multimedia conferences, Internet telephone calls, and multimedia distribution. Members in a session can communicate through multicast or through a mesh of unicast relations, or a combination of the two.

SIP invitations are used to create and carry session descriptions that allow participants to agree on a set of compatible media types.

SIP does not provide streaming media capability, but it does provide a means whereby participants can agree upon mutually acceptable streaming media parameters. SIP-enabled applications communicate by sending messages to each other using either UDP or TCP.

SIP supports user mobility by proxy and redirection requests to the current location of the user, which is registered by the user. SIP is not tied to any particular conference control protocol. A SIP message can be sent directly to its recipient, or it can pass through one or more proxy servers on the way. A proxy server is typically located at the edge of the recipient's network, and provides forwarding of messages for a group of individuals at the recipient's site.

SIP is designed to be independent of the lower-layer transport protocol and can be extended with additional capabilities.

SIP Calls

A SIP call consists of two transactions, the initial call setup and call termination. Call setup begins when the call originator sends an INVITE message to one or more participants. Following the INVITE, several messages are exchanged between client and server. Messages may pass through one or more SIP proxy servers between the client and server. SIP call termination begins with either the client or server sending a BYE message.

SIP Messages

SIP messages are text based, using ISO 10646 in UTF-8 encoding, and have a header field format that is very similar to HTML. The following example shows the header syntax:

CRLF
[ message-body ]
message-header = ( general-header
| request-header
| response-header
| entity-header )

All SIP messages within the context of a call contain a common identifier, the Call-ID, which is part of the general-header and has the following format:

Call-ID = ( 'Call-ID' | 'i' ) ':' local-id
local-id = 1*uricA Call-ID will not be reused for another call.

A Call-ID will not be reused for another call.

SIP Call-ID Persistence

SIP Call-ID persistence is included to all available persistence types for BIG-IP server pools. In the future, BIG-IP will be modified to provide persistence to a SIP proxy server based upon the SIP Call-ID general header field.

Inbound SIP Messages

For each UDP packet BIG-IP receives that is destined to a virtual server using a SIP Call-ID persistence pool, BIG-IP extracts the Call-ID field from the SIP header and attempts to match a persistence record. If BIG-IP does not find a matching persistence record, it chooses a proxy server based on the load balancing method for the pool. It then creates a persistence record referencing the selected member server for that Call-ID and forwards the packet to the proxy server stated in the persistence record.

Outbound SIP Messages

For BIG-IP to forward packets from a proxy server to an array of downstream hosts, you must configure a SNAT with a translated IP address that is the same as the virtual server handling inbound SIP messages.

For each outbound packet that is routed through the SNAT, the source IP address will be translated to the IP address of the SNAT, and the source port will be translated to a unique value for the flow consisting of the IP address and port of both the proxy server and the downstream host.

In order to allow BIG-IP to free resources associated with old SIP persistence entries without having to test each inbound packet for one of the variety of SIP final messages, a configurable timeout mechanism for SIP persistence records has been implemented on BIG-IP. This timer has a default value of 32 seconds when the SIP persistence attribute is assigned to a pool. When no messages are received for a specific Call-ID for the timer period, BIG-IP will remove the persistence record for that Call-ID. The timer will apply to all SIP persistence records pertaining to the particular server pool. The timeout value may be modified by a user at any time, but should be set to a value of no less than the SIP message timeout period.

SIP Proxy Server Health Monitoring

To provide high availability for SIP proxy servers, a new type of SIP monitor will be added to the existing health monitoring system on BIG-IP. This is currently being discussed and will be added at a later time.

Forwarding ICMP Messages

Although the implementation will include a health monitoring mechanism, there is the likelihood that a UDP SIP message may be forwarded by BIG-IP to a down proxy server between service check intervals. This may cause an ICMP message to be sent from the proxy server. Forwarding an internally generated ICMP error would cause an outside SIP host to consider the entire proxy server array to be down, so BIG-IP will not forward any ICMP messages generated by members of the SIP proxy server pool.

SIP applications using UDP employ a built-in mechanism for message retransmission and expiration. Since SIP relies on ICMP messages for timely notification of host-related errors, BIG-IP must pass ICMP messages destined for the virtual server IP address on to the proxy server that originated the request. ICMP messages are not likely to contain the SIP Call-ID field, so BIG-IP will find the correct proxy server to forward an ICMP message to by looking up the SNAT flow that matches the source address and port in the ICMP message data. BIG-IP will change the source IP address and port in the ICMP message data to that of the proxy server.

Packet Flow - Client to Downstream SIP Host

SIP applications that use UDP are likely to send messages from one port and receive them on another. Furthermore, a SIP application may use the same source port to send messages for more than one transaction. To determine which proxy server should handle a SIP message, BIG-IP examines the Call-ID field of all UDP datagrams that are destined to a virtual server that uses a SIP pool.

BIG-IP Configuration

To add SIP Call-ID persistence to a server pool, use the following command:

bigpipe pool <pool name> { persist_mode sip [sip_timeout ] }

Note:The default timeout value is 32 seconds.

To display the contents of the SIP persistence hash table, use the following command:

bigpipe sip dump

Note: New commands will be provided in future releases of BIG-IP to add support for SIP health monitoring.
