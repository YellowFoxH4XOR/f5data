Known Issue

 Description

The BIG-IP APM system may cache multiple entries for local user database authentication.

This issue occurs when all of the following conditions are met:

  • The BIG-IP APM access policy uses a local database for authentication.
  • The user attempting to log in already exists in the local user database or is added dynamically. 
  • The user attempts to log in multiple times using a case variation that does not match the case of their local user database username. For example, the user bob attempts to log in as Bob or BOB.

    When the user of a local user database or a dynamic user attempts to log in to a BIG-IP APM access profile, the system stores the authenticated case-sensitive username and password in cache. When authenticating with a variation of a local user database username (Bob, BOb, BOB), the APM system stores individual entries for each variation of the username in the cache instead of storing a single entry as defined in the local user database username (bob). However, when deleting or unlocking the local user through the Configuration utility (Access Policy > Local User DB > Manage Users), the system modifies only one entry in the cache, while entries with other username variations remain in the cache.

Impact

Since the BIG-IP APM system first uses the cache when authenticating, this behavior may lead to a scenario in which the BIG-IP APM system uses stale and erroneous information from the cache.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • Users attempting to log in to the BIG-IP APM access profile are denied access.
  • Authenticating with a username that was previously deleted from the Configuration utility does not dynamically add the user.
  • After unlocking a user from the Configuration utility, the user is still not able to authenticate.
