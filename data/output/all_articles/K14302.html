Topic

You should consider using this procedure under the following condition:

  • You need to replace an existing VIPRION chassis that has one or more blades installed.

Description

When you replace an existing VIPRION chassis that has one or more blades installed, by moving the blades with their original configuration to a new chassis, you will need to perform the tasks described in the Procedures section to prevent the following issues:

  • Missing license

    When a blade is started up on a VIPRION chassis, the blade compares the serial number of the chassis on which it is currently running with the serial number recorded in its license file. If the serial numbers are different, the blade runs with no license, instead of using its existing license file.

  • Missing cluster configuration

    When a blade is started up on a VIPRION chassis, the blade compares the serial number of the chassis on which it is currently running with the serial number recorded in its cluster configuration file. If the serial numbers are different, the blade runs with a factory-default cluster configuration.

    Since the cluster configuration information is unique to the chassis, the cluster configuration files are not included in the user configuration set (UCS) archive file. For more information, refer to K4423: Overview of UCS archives.

  • Failure to load a configuration with SSL profiles that use the SSL key passphrase encryption

    If the VIPRION system or a Virtual Clustered Multiprocessing (vCMP) guest that runs on the VIPRION system is configured with Secure Sockets Layer (SSL) profiles that use the SSL key passphrase encryption, moving the blades to a new chassis during a configuration load may result in SSL key passphrase errors that appear similar to the following examples:

    • The vCMP host may log errors to the /var/log/ltm file that appear similar to the following example:

      vcmpd[4898]: 01510004:3: master decrypt: decrypt failure - final
      vcmpd[4898]: 01510004:3: Guest (guest1): Guest unit key decryption failed.
      vcmpd[4898]: 01510004:3: master decrypt: decrypt failure - final
      vcmpd[4898]: 01510004:3: Guest (guest2): Guest unit key decryption failed.

    • The VIPRION system or a vCMP guest may log errors to the /var/log/ltm file that appear similar to the following example:

      mcpd[4532]: 012a0004:4: halStorageRead: unable to read storage on this platform.
      mcpd[4532]: 01071038:5: Loading keys from the file.
      mcpd[4532]: 012a0004:4: halStorageRead: unable to read storage on this platform.
      mcpd[4532]: 01071029:5: Cannot open unit key store
      mcpd[4532]: 012a0004:4: halStorageRead: unable to read storage on this platform.
      mcpd[4532]: 01071038:5: Loading keys from the file.

    If a UCS archive file is originally taken from a vCMP guest running on a blade and is reinstalled to the same vCMP guest running on the same blade, but inserted into a different chassis, the vCMP guest fails to load its configuration and reports an error message to the /var/log/ltm file that appears similar to the following example:

    mcpd[19819]: 01071027:5: Master key OpenSSL error: 19819:error:06065064:digital envelope routines:EVP_DecryptFinal_ex:bad decrypt:evp_enc.c:330: Â¦

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You must have physical access to the VIPRION system.
  • You must have serial console access to the VIPRION system.

Procedures

  • Before removing any blades from the original chassis
  • Removing blades from the original chassis and installing one blade to the new chassis
  • After installing one blade to the new chassis

Before removing any blades from the original chassis

Before you remove any blades from the original chassis, you must perform the following tasks, applicable for your environment:

  • Removing SSL key passphrase encryption
    and/or
    Copying master key from original device or active peer
  • Backing up an UCS archive file
  • Shutting down the vCMP guest
  • Shutting down the VIPRION system

Removing SSL key passphrase encryption

The BIG-IP system uses a hardware key encrypted master key to encrypt and decrypt SSL key passphrases in the configuration file. Due to a change in chassis, the hardware key needed to unencrypt the master key that protects the SSL key passphrases is not available. As a result, the encrypted passphrase cannot be decrypted. This behavior applies to both vCMP guests as well as a VIPRION system running modules other than vCMP.

Before you remove any blades from the original chassis, you must ensure that you have a record of each passphrase in a secure location on a system other than the system that uses the passphrase. Alternatively, you can replace the encrypted passphrase with the plain text passphrase for each SSL profile. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the command line.
  2. To back up the /config/bigip.conf file, type the following command:

    cp -p /config/bigip.conf /var/tmp/bigip.conf.sol14302

  3. Edit the /config/bigip.conf file using a text editor of your choice.
  4. Locate the SSL profile stanza similar to the following example:

    ltm profile client-ssl /Common/myexamplessl {
        app-service none
        cert /Common/myexamplessl.crt
        defaults-from /Common/clientssl
        key /Common/myexamplessl.key
        passphrase $M$Pq$6EYvH/L9oG0LFo7L/SYjAg==
    }

  5. Replace the encrypted passphrase with the plain text passphrase. Using the previous example, replace the line passphrase $M$Pq$6EYvH/L9oG0LFo7L/SYjAg== with passphrase <plain text passphrase>. After the edit, the example stanza should appear similar to the following example:

    ltm profile client-ssl /Common/myexamplessl {
        app-service none
        cert /Common/myexamplessl.crt
        defaults-from /Common/clientssl
        key /Common/myexamplessl.key
        passphrase <plain text passphrase>
    }

  6. Repeat steps 4 to 5 for any remaining SSL profiles
  7. Save the changes and exit the text editor

    Note: Do not load the modified configuration into memory and save it back to file. Doing so will overwrite the SSL profiles with their respective encrypted passphrases in the configuration file.

Copying the Master Key from the original device or peer system

Before powering off any blades from the original chassis, copy the master key from each host and vCMP guest.

  1. From the active peer BIG-IP system, obtain the master key by typing the following command:
    f5mku -K
  • K9420: Installing UCS files containing encrypted passwords or passphrases
Backing up a UCS archive file

Before removing any blades from the original chassis, you should create a UCS archive file and ensure that the UCS archive file is copied to a secure location on a system other than the system from which the UCS archive file was originally created. This is recommended in the following cases:

  • The VIPRION system is provisioned for vCMP; the UCS archive file must contain all vCMP guest instances.

    Note: For vCMP systems, the UCS archive will be restored in the Restoring the vCMP guest below.

  • The VIPRION system is provisioned to run multiple modules such as LTM and ASM.

    Note: For systems running multiple modules, you may need to install the UCS file if you run into issues after moving the blade to the new chassis.

To create a UCS archive file, refer to the following articles:

  • K13132: Backing up and restoring BIG-IP configuration files (11.x - 12.x)
  • K11318: Backing up and restoring BIG-IP configuration files (10.x)

To copy the UCS archive file to another location, refer to K175: Transferring files to or from an F5 system.

Shutting down the vCMP guest

Before shutting down a VIPRION system provisioned for vCMP, you must shutdown all vCMP guests running on the vCMP host. To do so, change the status for all vCMP guests from Deployed to Provisioned by performing the following procedure on the vCMP host:

Impact of procedure: The vCMP guests are unable to process traffic after the shutdown.

  1. Log in to the Traffic Management Shell (tmsh) on the vCMP host by typing the following command:

    tmsh

  2. To shut down all vCMP guests running on the host, type the following command:

    modify vcmp guest all state provisioned

Shutting down the VIPRION system

For a VIPRION system provisioned for vCMP, you must ensure that all vCMP guests are completely shut down before proceeding to shut down the VIPRION vCMP host system. After all vCMP guests are completely shut down, to shut down the host system, perform the following procedure:

Impact of procedure: The VIPRION system is unable to process traffic after the shutdown.

  1. Log in to the command line of the VIPRION vCMP host system.
  2. To shut down the vCMP host system, type the following command:

    clsh shutdown now

Removing blades from the original chassis and installing one blade to the new chassis

When the VIPRION system is shut down, remove the blades from the original chassis and install only one blade to the new chassis. For information about removing and installing blades to/from a chassis, refer to the About installing blades section of the Platform Guides for your VIPRION platform.

Note: It is less complicated to install only one blade to the new chassis and restore the blade to a working condition before adding the remaining blades to the cluster.

After installing one blade to the new chassis

When you have installed one blade to the new chassis, you must perform the following tasks:

  • Setting up a serial console to the blade
  • Configuring the networking options for the management interface
  • Activating the license for the new chassis
  • Configuring a cluster-specific configuration
  • Configuring data network configuration for the cluster
  • Provisioning modules
  • Applying master key
  • Restoring the vCMP guest
  • Adding the remaining blades to the cluster
  • Monitoring replication status of blades

Setting up a serial console to the blade

When a blade is started up on a new or RMA VIPRION chassis, the blade compares the serial number of the chassis with the serial number recorded in its cluster configuration file. The blade then runs with the factory-default cluster configuration, which contains no cluster information, including no management addresses. The only way to connect to the blade is through the serial console. The default serial console baud rate on VIPRION platforms is 19200. For information about setting up a serial console for VIPRION platforms, refer to the following articles:

  • K7683: Connecting a serial terminal to a BIG-IP system
  • K9156: Setting the baud rate of the serial console port (9.x - 10.x)
  • K587: Pinouts for serial terminal cables used to connect the 9-pin serial port on F5 products

Configuring the networking options for the management interface

When the installed blade is booted up, you need to configure the networking options for the management interface. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Using the serial port, connect a terminal emulator to the BIG-IP system.
  2. From the BIG-IP command line, start the F5 Management Port Setup tool by typing the following command:

    config

  3. Enter the appropriate data to assign an IP address, netmask, and default management route to the management interface.
  4. Reboot the blade by typing the following command:

    reboot

  5. When the blade is back up, connect the management port into your network, as appropriate.

    Note: If you do not have serial access to the device, you can set the management network settings by using the LCD display and keypad on the front panel of the device. For more information about this process, refer to the appropriate Platform Guide for your hardware platform.

Activating the license for the new chassis

After you have configured the networking options for the management interface, you can connect the management port by way of the network and access the Configuration utility to reactivate the license for the new chassis. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to System > License.
  3. Click Re-activate.
  4. Follow the on-screen instructions to complete the license activation.

    Note: For further assistance with license activation, refer to K7752: Licensing the BIG-IP system. For BIG-IP 10.1.0 and later, refer to K10245: BIG-IP UCS installation and licensing behavior.

Configuring a cluster-specific configuration

Since the blade is running with factory-default cluster configuration, you have to configure the cluster management addresses for each blade in the cluster as well as the Network Time Protocol (NTP) settings. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to System > Clusters > Management IP Address.
  3. Enter the Slot X IP Address, as appropriate, where X is the blade number in the chassis.
  4. To save the changes, click Update.
  5. Navigate to System > Configuration > Device > NTP.
  6. In the Address box, type the NTP Server address, and click Add.
  7. To save the changes, click Update.
  8. Optional: The following steps (9 through 12) are optional for creating a UCS archive file after you re-license and reconfigure the cluster.
  9. Navigate to System > Archives.
  10. Click Create.
  11. In the File Name box, type a name for the UCS archive file.
  12. To start the backup, click Finished.

Configuring data network configuration for the cluster

Once you have configured the cluster-specific configuration, configure the data network configuration, such as VLANs, self IP addresses, for the cluster. For information about configuring the network configuration, refer to the relevant chapters of the BIG-IP TMOS: Concepts guide.

Note: For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.

Impact of procedure: Performing the suggested procedure should not have a negative impact on your system.

Provisioning Modules

Prior to applying the ucs, reference the peer system to provision the necessary modules.

  • System > Resource Provisioning > Submit

Note: A reboot may be required after selecting or deselecting modules.

Applying the Master Key

Prior to applying the ucs, apply the master key to this appliance, host, or vCMP guest. The key will be different for each pair or standalone systems.

  1. To apply the Master key from the original device or peer system:
  • f5mku -r <key_value>
  • K9420: Installing UCS files containing encrypted passwords or passphrases

Restoring the vCMP guest

For a VIPRION system provisioned for vCMP, proceed to deploy the vCMP guests. When the vCMP guest is up and running with basic config and the same version as the old guest, transfer the UCS archive file that was created in an earlier task to the vCMP guest. You can transfer the UCS archive file using SCP, HTTPS, or FTP through the management interface. For assistance transferring the UCS archive from another BIG-IP device using SCP, from a remote FTP server using FTP, or from an attached workstation using HTTPS, refer to K175: Transferring files to or from an F5 system.

Once the UCS archives have been transferred to the respective vCMP guests, you can restore the configuration by installing the UCS archives to the respective vCMP guests. To do so, perform the following procedure for each vCMP guest:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the tmsh utility by typing the following command:

    tmsh

  2. Restore the UCS archive file by using the following command syntax, replacing <path/to/UCS> with the full path of the UCS archive file you want to restore:

    BIG-IP 11.x:

    load /sys ucs <path/to/UCS> no-license

    BIG-IP 10.x:

    load /sys ucs <path/to/UCS> rma

    If you do not specify the path, the BIG-IP system performs as if the UCS archive file is located in the default /var/local/ucs directory.

  3. If the UCS archive file was encrypted with a passphrase during the backup, you are prompted to enter the passphrase for the archive file.
  4. If the UCS archive file contains SSL key encrypted passphrases, you must replace each encrypted passphrase with the plain text passphrase by editing the /config/bigip.conf file with a text editor in the bash shell. You can access the bash shell by typing the following command:

    run /util bash

    Then edit the /config/bigip.conf file with a text editor, for example vi. Once you complete the changes, save the changes and exit the text editor.

  5. To stop the BIG-IP processes, type the following command:

    bigstart stop

  6. To remove the previous master key, type the following command:

    rm /config/bigip/kstore/master

  7. To remove the previous mcpd binary database, type the following command:

    rm /var/db/mcpdb.*

  8. To start the BIG-IP processes, type the following command:

    bigstart start

  9. To exit the bash shell, type the following command:

    exit

  10. To reload the configuration, type the following command:

    load /sys config

    The system automatically encrypts the plaintext passphrase.

  11. To save the configuration with the encrypted passphrase, type the following command:

    save /sys config partitions all

Adding the remaining blades to the cluster

Once you have verified that the configuration is properly restored on the installed blade in the new chassis, install the remaining blades to the cluster one at a time. For information about installing blades to a chassis, refer to the About installing blades section of the Platform Guides for your VIPRION platform.

Monitoring the replication status of the blades

To monitor the status of the blade replication, run the following command:

  • To observe the imaging of the new blade:

    watch tmsh show sys software

To monitor the status of the vCMP guests, run the following commands:

  • To monitor the virtual disk build, on each blade, for each guest:

    watch tmsh show vcmp virtual-disk

  • To show the guests coming up:

    watch tmsh show vcmp guest
