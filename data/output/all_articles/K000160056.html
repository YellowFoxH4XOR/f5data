K000160056: NGINX App Protect Policy Fails to Load Due to "PCRE compilation failed at offset 27: regular expression is too large"

Type
Support Solution
Published
2026-02-18
Updated
2026-02-18
Applies to
  • NGINX Products
  • NGINX App Protect WAF: 4.4.0
Source
https://my.f5.com/manage/s/article/K000160056

Description

When loading a security policy in NGINX App Protect, the policy fails to load and the following error messages are observed in the logs:

/var/log/app_protect/bd-socket-plugin.log
...
ECARD_POLICY|NOTICE|Feb 13 13:44:48.665|6297|/builds/uF6rUNwK/0/waf/waf-general/secore/common/bd_tbls/table_funcs.cpp:1606|handle_table_dynamic CONFIG_TYPE_WILDCARD_GLOBAL_PARAMETERS res:[0]
ECARD|ERR |Feb 13 13:44:48.665|6297|/builds/uF6rUNwK/0/waf/waf-general/secore/common/bd_tbls/regexp_table_management.cpp:0057|key crc 278b018e PCRE compilation failed at offset 27: regular expression is too large
ECARD|ERR |Feb 13 13:44:48.665|6297|/builds/uF6rUNwK/0/waf/waf-general/secore/common/bd_tbls/regexp_table_management.cpp:0166|Failed to PUT table
BD_MISC|ERR |Feb 13 13:44:48.665|6297|/builds/uF6rUNwK/0/waf/waf-general/secore/bd/bd/temp_func.c:2274|CONFIG_TYPE_PROTOBUF_FILENAMES message had parsing error: could not parse protobuf message
BD_MISC|ERR |Feb 13 13:44:48.665|6297|/builds/uF6rUNwK/0/waf/waf-general/secore/common/bd_tbls/table_funcs.cpp:2834|CONFIG_TYPE_PROTOBUF_FILENAMES message had errors in block_index: 38. status=-1

This issue prevents the policy from being loaded and enforced by NGINX App Protect.

Environment

  • Product: NGINX App Protect WAF
  • Version: 4.4.0 (WAF Engine version 10.310.0, wafNginxVersion 4.402.0)
  • Configuration: Policy contains custom regular expressions with large quantifiers and OR conditions
  • Directive used: app_protect_policy_file in NGINX configuration
  • Error location: Observed during policy load or NGINX startup/reload

Cause

The PCRE (Perl Compatible Regular Expressions) engine used by NGINX App Protect has a compiled size limit for regular expressions. Patterns with large quantifiers combined with OR conditions cause the regex engine to generate a decision tree that exceeds this limit.

Answer/Recommended Actions

To identify the offending regex, enable the ECARD bd debug and reload the nginx configuration . In the logs the problematic regex should be visible. Once identified edit the regex accordingly.

1.Create a backup copy of the /etc/app_protect/bd/logger.cfg file:

# cp /etc/app_protect/bd/logger.cfg /etc/app_protect/bd/logger.cfg.backup

2.Edit the Logger Configuration File /etc/app_protect/bd/logger.cfg and add the following debug modules:

MODULE=ECARD;
LOG_LEVEL=TS_ERR | TS_CRIT | TS_WARNING | TS_NOTICE | TS_DEBUG;
FILE = 2;

MODULE = ALL;
LOG_LEVEL = TS_ERR | TS_CRIT | TS_WARNING | TS_NOTICE;
FILE=2;

3.Restart the BD process to enable debug logging (according to Internal KB K000138088):

# pkill -SIGUSR1 bd

Note: Simply reloading NGINX is not sufficient; the BD process must be restarted for debug settings to take effect.

4.Reproduce the issue by reloading the policy:

# nginx -s reload

5.Check the debug logs in /var/log/app_protect/bd-socket-plugin.log for detailed ECARD error messages showing which regex patterns are failing.

6.Disable Debug Logging (when troubleshooting is complete):

# cp /etc/app_protect/bd/logger.cfg.backup /etc/app_protect/bd/logger.cfg
# pkill -SIGUSR1 bd

Additional Information

  • The issue is related to PCRE engine limitations, not a system or environmental problem
  • Loading multiple policies where at least one does not contain the problematic regex may allow NGINX to start, but the problematic policy will still fail to load
  • The error is reproducible with similar regex patterns and quantifier values
  • The syntax of the regular expression is the root cause; changing the pattern structure is necessary rather than adjusting system settings
