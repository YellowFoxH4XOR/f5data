Topic

The purpose of this article is to clarify the scope of Internet Key Exchange (IKE) and IPsec RFC support for interoperation with other vendors.

Note: This article is a reference for the IKE and IPsec related RFCs that are fully supported by the BIG-IP system. The BIG-IP system may partially support other IKE and IPsec related RFCs not included in this article, but the article is not a reference for those partially supported RFCs. Additionally, this article does not discuss the specific encryption and authentication ciphers supported in the different versions of IKE or IPsec.

Description

IPsec is a vendor independent standard for encrypting communication between two IP endpoints. These two endpoints (also known as IPsec peers) can encrypt the communication of entire computer networks. As a result, private networks separated by any number of bridges, routing hops, or the Internet, can communicate securely by way of one or several encrypted IPsec Security Associations (SAs) (also known as tunnels).

The IKEv1, IKEv2, and IPsec standards are considered separately because the correct implementation of one standard does not guarantee vendor interoperability for a complete tunnel.

Supported IKEv1 RFCs

The BIG-IP system interoperates with any IKEv1 peer that implements the following IKEv1 RFCs:

  • RFC4109: Algorithms for Internet Key Exchange version 1 (IKEv1)
  • RFC3947: Negotiation of NAT-Traversal in the IKE

Note: Support for IKEv1 was introduced in BIG-IP 11.0.0.

Supported IKEv2 RFCs

The BIG-IP system interoperates with any IKEv2 peer that implements the following IKEv2 RFCs:

  • RFC4478: Repeated Authentication in Internet Key Exchange (IKEv2) Protocol
  • RFC5996: Internet Key Exchange Protocol Version 2 (IKEv2)
  • RFC5723: Internet Key Exchange Protocol Version 2 (IKEv2) Session Resumption

Note: Support for IKEv2 was introduced in BIG-IP 11.6.0.

Supported IPsec RFCs

The BIG-IP system interoperates with any IPsec peer that implements the following IPsec related RFCs:

  • RFC3173: IP Payload Compression Protocol (IPComp)
  • RFC3948: UDP Encapsulation of IPsec ESP Packets
  • RFC4301: Security Architecture for the Internet Protocol
  • RFC4302: IP Authentication Header
  • RFC4303: IP Encapsulating Security Payload (ESP)
  • RFC4304: Extended Sequence Number (ESN) Addendum to IPsec Domain of Interpretation (DOI) for Internet Security Association and Key Management Protocol (ISAKMP)
  • RFC4891: Using IPsec to Secure IPv6-in-IPv4 Tunnels

Note: Support for IPsec was introduced in BIG-IP 11.0.0.

Recommendations

When planning an IPsec deployment between a BIG-IP system and another vendor, you should consider the following factors:

  • Does the vendor implement one or more proprietary Vendor IDs?

    Vendor IDs in IKE can be declared during negotiation by one peer but not the other. In which case, IKE should negotiate successfully, but the specific Vendor ID is not functional.

  • Does the vendor rely on proprietary features as mandatory to tunnel negotiation?

    A vendor's proprietary features are often protected by patents and cannot legally be implemented by other vendors.

  • Does the solution require a special IKE, IKEv2 or IPsec feature defined by an RFC not in the previous list?

    If you have a specific question regarding support for an RFC not in the previous list, contact an F5 Sales or Solution Engineer to verify compatibility.
