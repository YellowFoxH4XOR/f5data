Topic

The BIG-IP system has the following two routing tables:

  • The kernel table for routing BIG-IP system management traffic
  • The Traffic Management Microkernel (TMM) table for routing load-balanced traffic

You can add routes to the BIG-IP system by entering the routes statically using the Configuration utility or the command line, or dynamically if the system is licensed for the BIG-IP Advanced Routing Module (BIG-IP ARM). This feature is included for Better and Best licenses.

Note: You can determine if your system is licensed for BIG-IP ARM by checking for Routing Bundle under Active Modules on the License page in the Configuration Utility or show sys license in the TMOS Shell (tmsh).

The BIG-IP system supports BGP4 and BGP4+. Border Gateway Protocol (BGP) is a dynamic routing protocol primarily used on the Internet to exchange routing and reachability information among autonomous systems.

The following elements must be in place prior to configuring BGP on the BIG-IP system:

  • The BIG-IP system is licensed for BIG-IP ARM.
  • The tmrouted process starts and manages the ZebOS daemons.

    Important: The tmrouted process must only be managed using the bigstart command. Attempting to manipulate tmrouted using a Linux command or with invalid parameters may cause the daemon to crash.

    The tmrouted process must be running on the BIG-IP system in order for dynamic routing to function. To verify whether the tmrouted process is running, enter the following command at the command line:

    bigstart status tmrouted

    To start the tmrouted daemon, enter the following command:

    bigstart start tmrouted

  • BGP must be enabled in ZebOS. To verify whether BGP is enabled in ZebOS, enter the following command at the command line:

    zebos check

    If BGP is enabled in ZebOS, the zebos check command returns output similar to the following:

    nsm is running [22319]
    imi is running [22317]
    bgpd is running [22320]

    If BGP is not enabled in ZebOS, refer to the following articles for information about starting BIG-IP ARM:

    • K13802: Enabling dynamic routing protocols for a route domain
    • K8261: Enabling a dynamic routing protocol (9.x - 11.1.0)
  • Port lockdown must be configured to allow TCP/179 on all self IP addresses with which the routers will communicate. For information about port lockdown, refer to the following articles:
    • K13250: Overview of port lockdown behavior (10.x - 11.x)
  • If you want your BIG-IP system to advertise IPv6 network routes, you must configure a IPv6 link-local self IP address. For more information, refer to the following article:
    • K15203: Configuring IPv6 link-local self IP addresses (10.x - 13.x)

Advanced routing daemons

The tmrouted process is the routing table management daemon that updates the TMM routing table based on the kernel routing table. The tmrouted process depends on the mcpd and tmm daemons and if either of these daemons restart, tmrouted also restarts.

The tmrouted process starts and supervises the ZebOS daemons. ZebOS daemons are divided into the following two categories:

  • Core daemons:
    • nsm

      The nsm daemon is the ZebOS Network Services Module daemon.

    • imi

      The imi management daemon allows the system administrator to configure and monitor ZebOS daemons through a centralized connection.

  • Protocol daemons:
    • bgpd
    • isisd
    • ospfd
    • ospf6d
    • ripd
    • ripngd

ZebOS daemon startup is controlled by the presence of BIG-IP ARM license keys. Protocol daemons are started if they are licensed and enabled. Core daemons are started if at least one protocol daemon is licensed and enabled.

The tmrouted daemon handles SIGCHLD signals and restarts ZebOS daemons as necessary. The tmrouted daemon performs the following actions when a ZebOS daemon restarts:

  • Core daemon exits
    • Removes all dynamic routes
    • Stops all remaining ZebOS daemons
    • Exits and restarts
  • Protocol daemon exits
    • Restarts the protocol daemon

Advanced routing daemon logging

The ZebOS logs to the /var/log/zebos.log file. Additional messages are logged to the /var/log/daemon.log and /var/log/ltm files. The bgpd daemon information is logged for BGP daemon-specific issues, and nsm and imi daemon information is logged for core ZebOS daemon-related issues.

If a core ZebOS daemon exits, an error message that appears similar to the following example is logged to the /var/log/daemon.log file:

Mar 5 22:43:01 mybigip LOGIN: Re-starting tmrouted

In addition, error messages that appear similar to the following example are logged to the /var/log/ltm file:

mcpd[5157]: 01070410:5: Removed subscription with subscriber id bgpd
mcpd[5157]: 01070533:3: evWrite finished with no byte sent to connection 0xa56f9d0 (user Unknown) - connection deleted

Debug logging

When you are troubleshooting an issue with a ZebOS daemon, it may be necessary to create a debug log file and enable debug logging. To create a debug log file and enable debug logging, perform the following procedure:

Important: In order for the debug data to log properly, you must create the /var/log/zebos.log file prior to enabling debug logging.

  1. Log in to the BIG-IP command line.
  2. To access the IMI Shell (imish), type the following command.

    imish

  3. To enter enable mode, type the following command:

    enable

  4. To enter configuration mode, type the following command:

    config terminal

  5. To create the debug log file, type the following command:

    log file /var/log/zebos.log

  6. Exit configuration mode by typing the following command:

    end

  7. To write the configuration, type the following command:

    write

  8. After the debug log file is defined, enable debug logging by typing the following command:

    debug bgp all

  9. To verify that BGP debug logging is enabled, type the following command:

    show debug bgp

    or

    show debugging bgp

    For example, the following output indicates that BGP debug logging is enabled:

    BGP debugging status:
    BGP debugging is on
    BGP nsm debugging is on
    BGP events debugging is on
    BGP keepalives debugging is on
    BGP updates debugging is on
    BGP fsm debugging is on
    BGP filter debugging is on
    BGP Route Flap Dampening debugging is on

Note: To disable BGP debugging, type the undebug bgp all command.

Verifying routes

You should verify that the routes are being advertised from the vtysh shell. To do so, perform the following procedure:

  1. Log in to the BIG-IP command line.
  2. To access the imish utility, type the following command:

    imish

  3. To show the IP route information, type the following command:

    show ip route

    For example, the following command output displays the show the IP route information:

    Codes: K - kernel, C - connected, S - static, R - RIP, B - BGP
    O - OSPF, IA - OSPF inter area
    N1 - OSPF NSSA external type 1, N2 - OSPF NSSA external type 2
    E1 - OSPF external type 1, E2 - OSPF external type 2
    i - IS-IS, L1 - IS-IS level-1, L2 - IS-IS level-2, ia - IS-IS inter area
    * - candidate default

    Gateway of last resort is 10.1.99.254 to network 0.0.0.0

    K* 0.0.0.0/0 via 10.1.99.254, external
    B 10.0.0.0/8 [20/0] via 10.1.99.254, external, 00:13:08
    C 10.1.0.0/16 is directly connected, external
    K 10.1.51.80/32 is directly connected, tmm0
    K 10.1.51.81/32 is directly connected, tmm0
    C 10.10.0.0/16 is directly connected, internal
    C 127.0.0.1/32 is directly connected, lo
    C 127.1.1.0/24 is directly connected, tmm0
    B 172.24.0.0/16 [20/0] via 10.1.99.254, external, 00:13:08

    The following routes indicate the advertised virtual server addresses. The tmm routes are routes learned from TMM, and the /32 netmask indicates that ZebOS is advertising a single IP address:

    Note: The advertised virtual server addresses appear as kernel routes (K) because of the way TMM injects the routes into tmrouted. Therefore, you must have redistribute kernel configured in the BGP router definition in ZebOS.

    K 10.1.51.80/32 is directly connected, tmm0
    K 10.1.51.81/32 is directly connected, tmm0

    The following routes are learned from other BGP routers:

    B 172.24.0.0/16 [20/0] via 10.1.99.254, external, 00:13:08

    If you look at the routing table from the bash shell, it may not be obvious which routes have been learned from other routers. Dynamically learned routes will appear as follows:

    #route -n
    Kernel IP routing table
    Destination Gateway Genmask Flags Metric Ref Use Iface
    172.24.0.0 10.1.99.254 255.255.0.0 UG 0 0 0 external
    10.0.0.0 10.1.99.254 255.0.0.0 UG 0 0 0 external
