Description

Frequent failovers between Azure BIGIP VEs can result in total loss of Azure-configured secondary IPs (VIPs/floating IPs/SNATs) causing full traffic outage.

In ltm log we will see indications of connectivity loss between the peers on failover channel and we will see the Standby VE going Active, while its peer stays in Active state as well:

Mar 1 01:39:59 <VE2> warning sod[6089]: 010c0083:4: No failover status messages received for 3.100 seconds

Mar 1 01:40:04 <VE1> notice sod[6654]: 010c006d:5: Leaving Standby for Active: Next Active, peers agree on config.

Mar 1 01:40:04 <VE1> notice sod[6654]: 010c0053:5: Active for traffic group traffic-group-1.

Mar 1 01:40:04 <VE1> notice sod[6654]: 010c0019:5: Active

 

Here VE1 claims itself as Active, while VE2 is also Active.

Mar 1 01:40:04 <VE2> notice sod[6089]: 010c002a:5: Requesting tmm to resend gratuitous arps for traffic group traffic-group-1.

After a few seconds the connectivity is back and the pair is Active/Standby again, but traffic will be broken and VSs and pools will not be functional.

Environment

  • BIG-IP VE in Azure running 16.1.5, CFE 2.1.0.

Cause

When Azure BIGIP VEs in HA pair lose connectivity with one another causing Active-Active (split-brain) situation, CFE begins to remove Azure resources from the current Standby device (previously Active). This process takes about 30 seconds.

After 4 seconds VEs re-established connectivity and HA immediately failed back, so CFE running on the active device began removing the Azure resources from the standby device, which was still in the process of removing them from the first device (which is now active again).

At this point one or more of the Azure resources go into a "Failed" state.

Azure most likely considered the subsequent update request as invalid because the affected network interfaces were already updating.

As a result, we end up without resources on any of the VE, essentially causing traffic outage until the IPs are re-configured in Azure.

The 30 seconds timing benchmark for resources removal (and 30 seconds more for addition is essentially Azure-imposed , as we are subject to Azure's control plane latency when updating the network interfaces directly. This latency can be minimized and even eliminated if Azure LoadBalancer is deployed in front of BIG-IPs and CFE deleted. Here are the latency estimates for CFE failovers for reference:

https://clouddocs.f5.com/products/extensions/f5-cloud-failover/latest/userguide/performance-sizing.html?highlight=performance#azure

Recommended Actions

To recover from this situation, we need to perform the following steps:

1. Manually restore the Azure resources (network interfaces and route tables) for deployment.

2. Reinstall CFE and reapply the correct declaration using the /declare endpoint.

3. Then run a dry run failover on the standby device to make sure the output is correct.

 

Detailed steps explanation

For step 1,  check current IP configuration on the NIC's.

It is also possible to use the following commands for that:

az network nic ip-config list --resource-group <resource-group-name> --nic-name <NIC name>

 

If any of the virtual addresses are missing from the list of secondary IP's , they must be added manually and associated with the currently active unit.

For step 2, to remove current CFE installation and install it again run follow the below steps:

-On the BIG-IP user interface, click iApps > Package Management LX > f5-cloud-failover > Uninstall

-Download and install CFE as per https://clouddocs.f5.com/products/extensions/f5-cloud-failover/latest/userguide/installation.html#installation

-Configure CFE by posting a declaration as per https://clouddocs.f5.com/products/extensions/f5-cloud-failover/latest/userguide/configuration.html

 

For step 3,  log in to the standby VE and issue the following curl command:

curl -su admin: -X POST -d '{"action":"dry-run"}' http://localhost:8100/mgmt/shared/cloud-failover/trigger | jq .

The result will be logged into /var/log/restnoded/restnoded.log.
