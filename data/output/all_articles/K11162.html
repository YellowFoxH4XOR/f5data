K11162: The standby unit in a high availability pair may incorrectly mark a node or pool member as down when a VLAN group is in use

Known Issue

This is the result of a known issue. When a BIG-IP high availability pair is configured to use a VLAN group, the standby unit may intermittently mark a node or pool member as down even when the active unit sees the node or pool member as up and the node or pool member is up.

When a node sends a broadcast ARP request for another host, the active BIG-IP system may rebroadcast this ARP request on the other side of the VLAN group. When the standby BIG-IP system sees the broadcast ARP request, it will use the information contained in it to update its ARP cache with the VLAN and MAC address of the requester. Since the standby BIG-IP system will most likely see the broadcast ARP request on the wrong side of the VLAN group last, that will be the update that is retained. As a consequence, future health checks sent to the node will egress the standby BIG-IP system from the wrong VLAN of the VLAN group.

For example:

  • A BIG-IP high availability pair is configured with the vgroup1 VLAN group.
  • The vgroup1 VLAN group consists of the internal and external VLANs.
  • The test_pool pool, whose definition is included below, resides on the internal VLAN:

    pool test_pool {
       monitor all http
       members 10.0.0.10:http {}
    }

  • The active and standby units will have ARP entries for the 10.0.0.10 node on the internal VLAN.
  • If the 10.0.0.10 node sends a broadcast ARP request for an address which is not in the active unit’s ARP cache, the active unit will rebroadcast the request on the external VLAN.
  • The standby unit will receive the ARP request which was rebroadcasted on the external VLAN by the active unit. Since the standby unit has an ARP entry for the node, it will use the requester information contained in the broadcast ARP request to update its ARP cache, effectively moving the node to the external VLAN and possibly changing the node’s MAC address (in the case of translucent or opaque VLAN groups).
  • Future monitor traffic from the standby unit will be sent on the external VLAN and forwarded by the active unit to the internal VLAN. If the node responds directly to the standby unit on the internal VLAN, the connection will be reset by the standby BIG-IP system if the VLAN-Keyed Connections option is enabled (the default setting). This will result in the health checks timing out and the pool member being marked as down.

Note: This issue only affects the standby BIG-IP system.

Note: A similar behavior to that described in this Solution may also occur due to a different issue. For more information, refer to K10601: VLAN group proxy excludes are not properly converted upon upgrade.
