K000164366: iControl SOAP and iControl REST API requests return HTTP 403 responses after upgrade

Description

On BIG-IP 17.5.1.4 and later, iControl SOAP and iControl REST API requests from source IP addresses that are not in the httpd allow list return HTTP 403 responses. This behavior is caused by httpd access control enforcement for REST and SOAP requests, tracked as Bug ID 944817 and documented in K000156604: BIG-IP httpd access control vulnerability CVE-2026-40435.

Symptoms and messages:

  • A REST authentication request to https://<BIG-IP>/mgmt/shared/authn/login returns an HTML page titled "Access forbidden!" with the body "You don't have permission to access the requested object." and "Error 403."
  • SOAP clients fail with an httpd error like the following in /var/log/httpd/error_log:

    [authz_core:error] [pid <pid>] [client <client_ip>:<port>] AH01630: client denied by server configuration: /usr/local/www/iControl/iControlPortal.cgi

  • HA device trust can fail to establish if the peer IP address is not in the httpd and SOAP allow lists. The error is:

    [xmlHelpers.cpp:90 getXPathValue] expected 1 node for //faultstring, got 0

Environment

  • Behavior change applies on BIG-IP 17.5.1.4 and later, and on 17.1.3.1 and later within the 17.1.x branch.
  • Affected interfaces: REST API (/mgmt/shared/authn/login and other REST endpoints) and SOAP API (iControl, /usr/local/www/iControl/iControlPortal.cgi).
  • Access is controlled by the httpd allow list (tmsh sys httpd allow). The SOAP API is reached through httpd, so SOAP clients must also be permitted by the SOAP (icontrol-soap) allow list.

Cause

  • Bug ID 944817: Improper IP based access restrictions via httpd.
  • K000156604: BIG-IP httpd access control vulnerability CVE-2026-40435

Starting with 17.5.1.4, httpd enforces the allow list for REST and SOAP requests. Clients that are not explicitly listed are denied.

Answer/Recommended Actions

  1. Identify the source IP addresses or subnets of all REST and SOAP clients, including automation, monitoring, and orchestration hosts.
  2. Review the current allow lists:

    tmsh list sys httpd allow

    tmsh list sys icontrol-soap allow

  3. Add the required source addresses to the httpd allow list:

    tmsh modify sys httpd allow add { <subnet_or_ip> }

  4. Add the same SOAP/iControl clients to the icontrol-soap allow list. Clients that use SOAP must be in both lists, because the SOAP API is accessed externally through httpd.
  5. Save the configuration:

    tmsh save sys config

  6. Retry the REST and SOAP calls from each client and confirm they return a successful response instead of 403.
  7. For HA deployments, add each HA peer's self IP to the httpd and icontrol-soap allow lists before establishing device trust. See K000160309: Peer Device IP Needs to Be in HTTPD Allow List to Establish Device Trust.

Additional Information

Source addresses permitted by the SSH allow list are not automatically permitted by the httpd allow list.
