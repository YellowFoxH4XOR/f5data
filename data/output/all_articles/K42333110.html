Topic

Open Authorization (OAuth) 2.0 is a framework that allows an application to obtain limited access on a user's behalf to an HTTP service. OAuth 2.0 obtains access by way of different use cases. This article uses the following OAuth terminology:

  • Resource server (RS): A server hosting the protected resource. For example, an BIG-IP LTM+APM virtual server.
  • Resource owner (RO): An entity capable of granting access to a protected resource. This can be, or is usually, a user on a client device.
  • Client application: An entity making protected resource requests on behalf of the resource owner and with its authorization. Examples include email and office productivity applications.
  • Authorization server (AS): Issues access tokens to the client application after successfully authenticating the resource owner and obtaining authorization. This can be connected to a user database like OpenLdap or Active Directory.
  • Authorization grant: An authorization grant is a credential used by the client to obtain an access token. The credential represents the resource owner's authorization to access its protected resources. It is useful to analyze each use case in this article by the different grant types they use to obtain the access token:
    • Authorization code: This authorization is optimized for server side applications that can maintain client confidentiality (client ID/client secret). The client redirects the RO to an AS, which in turn directs the RO back to the client with the authorization code. The RO credentials are never exposed to the client application.
    • Implicit grant: This authorization is used for mobile and web applications that cannot guarantee client confidentiality (client ID/client secret). Instead of issuing the client an authorization code, the application issues the client an access token directly. The redirection URI used to deliver the access token to the client verifies the client identity. The AS does not authenticate the client.
    • Resource owner password credentials grant: Users provide their credentials directly to the client application which uses the credentials to obtain an access token from the service. You should only use this authorization when the user trusts the application, such as when the service owns the client application or it's the user’s desktop operating system.
    • Client credentials grant: The client submits its own credentials to the AS for an access token. The client typically uses this authorization grant when it acts on its own behalf (the client is also the resource owner), or it requests access to protected resources based on an authorization previously arranged with the authorization server.
    • Extension grant type: This is an extension mechanism for defining new extension grant types to support additional clients or to provide a bridge between OAuth and other trust frameworks.

OAuth protocol flow
The following diagram describes the general OAuth 2.0 protocol flow.

Figure: OAuth 2.0 protocol flow

  1. The user accesses client application.
  2. The application redirects the user to the AS for authentication. Upon authentication, the user is redirected back to the client application with an authorization grant.
  3. The client application retrieves access token from the AS by providing client id/secret and the authorization grant.
  4. The client application accesses the user data on the resource server by providing the access token.

Description

The following sections describe different use cases in OAuth 2.0 using the BIG-IP APM system. It is useful to differentiate each use case by the role the BIG-IP APM system plays, either as client/RS, AS, or both. In addition, each use case also uses different grant types to obtain an access token.

  • The BIG-IP APM system as client/RS

    Note: For information about how to configure this use case, refer to K25101870: Configuring BIG-IP APM as OAuth client with Google OAuth authorization server and K53313351: Configure BIG-IP APM as OAuth client with Azure AD OAuth authorization server. 

  • The BIG-IP APM system as client/RS using RO password credential grant
  • The BIG-IP APM system as AS—protecting enterprise resources

    Note: For information about how to configure this use case, refer to K14391041: Configuring an OAuth setup using one BIG-IP APM system as an OAuth authorization server and another as the OAuth client.

  • The BIG-IP APM system as AS—protecting SaaS applications
  • The BIG-IP APM system as AS—as a cloud service
  • The BIG-IP APM system as AS—allowing partner application to access enterprise resource with client credential grant type
  • The BIG-IP APM system as AS—native mobile applications

The BIG-IP APM system as client/RS

Figure: The BIG-IP system as client and RS

  1. The user accesses a resource protected by the BIG-IP APM system.
  2. The BIG-IP APM system redirects the user to OAuth 2.0 provider, such as Facebook, Twitter, Google, or Enterprise AS.
  3. The OAuth 2.0 provider authenticates the user.
  4. The OAuth 2.0 provider redirects the user back to the BIG-IP APM system with an authorization code.
  5. The BIG-IP APM system exchanges the authorization code for an access token with the OAuth provider.
  6. The BIG-IP APM system retrieves the user settings from the OAuth provider using the access token.
  7. The access control decision is performed based on the retrieved user settings.

The BIG-IP APM system as client/RS using RO password credential grant

Figure: The BIG-IP system as client and RS—using resource owner password credential grant

In this use case, users provide their credentials directly to the application, which uses the credentials to obtain an access token from the service. You should only use this method when the user trusts the application, such as when the service owns the application or it's the user's desktop operating system.

  1. The user accesses a resource protected by the BIG-IP APM system.
  2. The BIG-IP APM system collects user credentials.
  3. The BIG-IP APM system uses the collected credentials to retrieve an access token from the OAuth provider.
  4. The BIG-IP APM system retrieves the user settings from the OAuth provider using the access token.
  5. The access control decision is performed based on the retrieved user settings.

The BIG-IP APM system as AS—protecting enterprise resources

Figure: The BIG-IP APM system as AS—protecting enterprise resources

  1. The user accesses an enterprise resource.
  2. The OAuth client redirects the user to the BIG-IP APM AS for user authentication and authorization.

    Note: You can configure a second BIG-IP APM system to perform the function of the OAuth client/RS.

  3. The BIG-IP APM system collects user credentials.
  4. The BIG-IP APM system authenticates the user with their back-end Active Directory (AD) or authentication, authorization, and accounting (AAA).
  5. The BIG-IP APM system redirects the user back to the client with an authorization code.
  6. The OAuth client retrieves an access token using the authorization code from the BIG-IP APM system.
  7. The RS enforces access control checks based on the access token or by retrieving additional user attributes from the BIG-IP APM system using the access token.
  8. User request to access protected resources is allowed.

The BIG-IP APM system as AS—protecting SaaS applications

Figure: The BIG-IP APM system as AS—protecting SaaS applications

  1. The user accesses a SaaS application in the cloud.
  2. The OAuth client component of the SaaS app redirects the user to the BIG-IP APM AS for user authentication.
  3. The BIG-IP APM system collects user credentials.
  4. The BIG-IP APM system authenticates the user with its back-end AD or AAA server.
  5. The BIG-IP APM system redirects the user back to the client with an authorization code.
  6. The OAuth client retrieves an access token using the authorization code.
  7. The RS enforces access control checks based on the access token or by retrieving additional user attributes from the BIG-IP APM system using the access token.

The BIG-IP APM system as AS—as a cloud service

Figure: The BIG-IP APM system as AS—as a cloud service

  1. The user accesses a SaaS application in the cloud.
  2. The OAuth client component of the SaaS application redirects the user to the BIG-IP APM AS for user authentication.
  3. The BIG-IP APM system collects user credentials.
  4. The BIG-IP APM system authenticates the user with its back-end AD or AAA server.
  5. The BIG-IP APM system redirects the user back to the client with an authorization code.
  6. The OAuth client retrieves an access token using the authorization code.
  7. The RS enforces access control checks based on the access token or by retrieving additional user attributes from the BIG-IP APM system using the access token.

BIG-IP APM system as AS—allowing partner app to access enterprise resource with client credential grant type

Figure: The BIG-IP APM system as AS—allowing partner application to access enterprise resource with client credential grant type

This use case uses the client credential grant type. You use this use case when the client application is also the resource owner.

  1. A partner user accesses an application on the partner network.
  2. The partner authenticates with AD in the partner network.
  3. The partner starts using the partner application.
  4. Now the partner application needs to update information on the enterprise resource on behalf of the partner user, such as updating the inventory and pricing information of the items supplied by the partner. The partner application authenticates the application with the BIG-IP APM AS hosted in the enterprise network using the client credential grant. Upon successful authentication, the BIG-IP AS returns an access token to the partner application.
  5. The partner application invokes an API call on the enterprise network using the access token.
  6. The RS component validates the access token and allows the API call.

BIG-IP APM system as AS—native mobile applications

Figure: The BIG-IP APM system as AS—native mobile applications

Instead of an authorization code, this use case uses implicit grants in which the client directly receives an access token. You use implicit grants for mobile and web applications when you cannot guarantee client confidentiality (client ID/client secret). This use case does not support refresh tokens.

  1. The BIG-IP APM system supports OAuth 2.0 APIs. You configure the native mobile application to use the BIG-IP APM-supported API URIs for OAuth client and RS functionality (or client functionality alone, if the BIG-IP APM system on the enterprise side supports both AS and RS functionality).
  2. The mobile application authenticates the user using the APIs and retrieves an access token using implicit grant.
  3. The access token is used for resource access.
