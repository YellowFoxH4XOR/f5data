Topic

You should consider using these procedures under the following conditions:

  • You are running BIG-IP 11.x - 13.x.
  • You have a redundant BIG-IP system that recently failed over, and the Address Resolution Protocol (ARP) entries on the upstream router or other directly connected hosts have not updated and still point to the MAC address on the previously active BIG-IP device.

Description

When a redundant BIG-IP system moves to an active status for a traffic group, the system broadcasts a series of gratuitous ARP (GARP) packets to the network to update ARP tables on directly connected network devices or hosts.

Devices limiting the rate of ARP packets or network loss can cause some devices to miss the GARP packets, resulting in a situation in which a virtual server or floating self IP address on an active BIG-IP system becomes unreachable due to network devices or hosts sending packets to the wrong device or to the standby BIG-IP system.

If this is a recurring issue due to ARP rate-limiting on a receiving upstream network device or host, consider modifying the BIG-IP system to send GARPs at a slower rate. For more information, refer to K11985: Overview of the arp.gratuitousrate and arp.gratuitousburst database variables. Slowing the GARP rate increases the amount of time it takes the system to complete the full GARP.

If you want to minimize ARP communication during failover events, consider configuring MAC masquerade on the traffic group which allows a MAC address to be shared between BIG-IP systems. For more information, refer to K13502: Configuring MAC masquerade (11.x - 17.x).

Prerequisites

You must meet the following prerequisites to use these procedures:

  • You have administrative access to the upstream devices in your network.
  • You have access to the BIG-IP Advanced Shell (bash).

Procedures

  • Clearing the ARP tables in upstream devices and hosts that hold stale ARP information
  • Forcing the BIG-IP system to resend GARPs

Clearing the ARP tables in upstream devices and hosts that hold stale ARP information

Impact of procedure: Clearing the ARP cache on upstream devices causes the devices to send ARP requests increasing traffic on the network.

Clearing the ARP table on an upstream device or host causes that device or host to broadcast ARP requests for subnet relevant IP addresses to update its ARP table. If multiple routers, virtual routing forwarding tables (VRFs), or numerous directly connected hosts are involved, this process can be time-consuming and prone to error. Refer to vendor specific documentation for clearing ARP tables from network devices or hosts.

Forcing the BIG-IP system to resend GARPs

You can force the BIG-IP system to resend GARP packets by creating and deleting a temporary new VLAN and self IP address. The creation and deletion of a single new self IP address is sufficient to cause all self IP and active virtual addresses to resend GARP packets.

Impact of procedure: As long as you choose a VLAN name and self IP address that are not already in use, performing this procedure should not negatively impact traffic.

  1. Log in to bash.
  2. Create a temporary VLAN using the following command:

    tmsh create /net vlan vlan_temp

  3. Create a corresponding self IP address by entering the following command:

    tmsh create /net self self_temp address 198.51.100.1/32 vlan vlan_temp

  4. Delete the temporary self IP address by entering the following command:

    tmsh delete /net self self_temp

  5. Delete the temporary VLAN by entering the following command:

    tmsh delete /net vlan vlan_temp
