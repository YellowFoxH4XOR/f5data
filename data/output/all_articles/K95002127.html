Issue

You should consider using these procedures under the following conditions:

  • Your BIG-IP system experiences one or more unexpected failover events.
  • You want to determine the root cause of the failover events.

Symptoms

As a result of unexpected failover events, you may encounter the following symptoms:

  • The expected active device group member fails over to the standby state. For example, the preferred device configured in the failover order list fails over to the standby state.
  • Your BIG-IP system logs error messages related to failovers.

Recommended Actions

Failover is a process that occurs when an active BIG-IP system in a device group becomes unavailable, causing a peer device to become active and begin processing traffic originally targeted for the unavailable unit. A failover event can be the result of routine maintenance performed by an administrator or an unexpected issue that triggers the failover, such as resource or network-related problems.

This article includes information about failover components, steps for troubleshooting failover issues, and finding the root cause of unexpected failover events. Failover includes the following elements.

Failover components

When troubleshooting BIG-IP failover issues, you should be familiar with the following components:

  • Failover communication
  • Failover features
  • DSC features related to failover
  • HA table
  • sod process
  • overdog process

Failover communication

The BIG-IP system supports hardwired and network options for failover communication. If failover communication is disrupted or improperly configured for your environment, failover from one device to another may be delayed or may not occur seamlessly as expected. Device group deployments containing three or more BIG-IP, VIPRION, and Virtual Edition (VE) high availability (HA) systems require the network failover option.

  • Hardwired failover

    When BIG-IP systems are configured to use hardwired failover, a failover cable monitors the voltage levels of the systems and assures that the peer unit is available. If the standby BIG-IP system detects a voltage level drop in the active system, the standby system initiates the failover process and becomes the active device. No data is sent or received over a failover cable.

  • Network failover

    When BIG-IP systems are configured to use network failover, systems send heartbeat packets over the network to peer devices using User Datagram Protocol (UDP) port 1026 by default. In contrast to hardwired failover, where no data is sent or received over a failover cable, network failover heartbeat packets contain data used to communicate a device's availability and failover status. Network failover is required for Sync-Failover device groups containing three or more devices and certain deployments such as BIG-IP, VIPRION, and VE HA systems.

    Note: When configuring network failover for VIPRION platforms, refer to K13915: Configuring network failover for redundant VIPRION systems (11.x - 12.x).

Failover features

Over time, the BIG-IP system may experience issues such as resource or network-related problems. Depending on the system configuration, the issues encountered may or may not result in a failover. For example, if you configure the gateway fail-safe feature to monitor traffic between BIG-IP systems in a device group and a pool containing gateway routers, the system fails over when a router becomes unavailable. The BIG-IP system includes the following features that can initiate failover according to events that you define.

  • System fail-safe

    The system fail-safe feature enables the BIG-IP system to monitor system components, such as the heartbeat signal of various system daemons. When a component fails, the BIG-IP system initiates a specific failover action.

  • Gateway fail-safe

    The gateway fail-safe feature enables the BIG-IP system to monitor traffic between an active BIG-IP system in a device group and a pool containing a gateway router. You can configure the system to initiate failover whenever a specific number of gateway routers in a pool of routers becomes unreachable.

  • VLAN fail-safe

    The VLAN fail-safe feature enables the BIG-IP system to monitor network traffic going through a specified Virtual Local Area Network (VLAN). You can configure the system to initiate failover whenever the system detects a loss of traffic on the VLAN and the fail-safe timeout period has elapsed.

  • HA group

    The HA group feature enables the BIG-IP system to monitor the availability of resources for a specific traffic group. For example, you can configure the system to monitor trunk links, pool members, and VIPRION cluster members. If resource levels fall below a user-defined level, the system triggers failover.

  • HA ordered list and auto-failback

    You can configure a traffic group to use a static, ordered list of devices; the list specifies the order in which you want the devices to become active for the traffic group if the traffic group fails over. When you enable auto-failback, a traffic group that has failed over to another device fails back to a preferred device from the ordered list when that device is available. If auto-failback is disabled for a traffic group, and the traffic group fails over to another device, the traffic group remains active on that device until that device becomes unavailable.

DSC features related to failover

Device Service Clustering (DSC) provides the framework for high-availability features, such as failover and configuration synchronization (ConfigSync) for BIG-IP device groups. The following DSC components are relevant to understanding failover:

  • Device trust and trust domains

    A device trust creates a trust relationship between BIG-IP devices through certificate-based authentication. BIG-IP systems must join and maintain the same trust domain so that the devices can properly synchronize and transfer their configuration data.

  • Device groups

    A device group is a group of BIG-IP devices that belong to the same trust domain and are configured to synchronize their configurations and fail over when the active device becomes unavailable. A Sync-Failover device group uses traffic groups for failover purposes.

  • Traffic groups

    A traffic group is the "unit of failover" between devices in a Sync-Failover device group. A traffic group is a collection of related configuration objects, such as self IP addresses and virtual addresses, that are configured on a BIG-IP device. The traffic group ensures that when a device becomes unavailable, the failover objects in the traffic group fail over to any one of the devices in the device group. For example, if you create three traffic groups on a BIG-IP system, the traffic groups remain active on the device until one or more traffic groups fail over to another device.

HA table

The HA table is a utility that displays components monitored by the system, the status of the component, and the action that the system will take when the component fails. You can display the HA table using the TMOS Shell (tmsh). Some HA features are specific to certain hardware platforms, while other features only appear in the table when the related component is configured on the system. For example, the pool-mbr-down HA feature appears in the table when you configure gateway fail-safe on the BIG-IP system.

sod process

The switch over (failover) daemon detects fail-safe conditions on the BIG-IP system by monitoring the HA table and initiating the fail-safe action based on the condition it finds. The sod process works with the tmm, lacpd, and bcm56xxd processes to enable and disable external interfaces and manage HA functionality (on platforms without a Broadcom switch chip, the pfmand process manages the links). The BIG-IP system uses the following sequence to enable and disable the external interfaces, monitor the HA table, and facilitate failover:

  1. During startup, the system forces the external interfaces down until the required connections to the sod process are established.
    • The sod process monitors the HA table to verify the status of TMM instances (indicated by the ready-for-world HA status).
    • The bcm56xxd and lacpd processes attempt to connect to the sod process over TCP port 1030.
    • Assuming the TMM instances are available, the sod process allows the connections from the bcm56xxd and lacpd processes.

      Note: If TMM instances are unavailable, the sod process denies the connections and initiates a failover.

    • After the connection to the sod process is established, the bcm56xxd and lacpd processes enable external interfaces.
    • The sod process reports to the mcpd process that the interfaces are up.
    • The system sets its failover status as appropriate.
  2. During normal operation, the sod process monitors the HA table.
  3. If an HA table feature requires an action, such as go-offline-downlinks, the sod process closes the TCP connections and the bcm56xxd and lacpd processes disable the external interfaces which triggers a failover.

overdog process

The overdog process initiates the hardware watchdog feature and implements the daemon_heartbeat and proc_run HA features for the sod process.

Verifying the failover status of a device

When troubleshooting failover occurrences, you should verify the current failover status of devices in the Sync-Failover device group and determine whether the expected device is the active system. An Active failover state indicates that at least one traffic group is currently active on the device. A Standby failover state indicates that all traffic groups on the device are in a standby state. To verify the failover status for a device, perform one of the following procedures:

Impact of procedure: Performing the following procedures should not have a negative impact on your system.

Configuration utility

  1. Log in to the Configuration utility.
  2. In the upper-left corner, click Current Redundancy State.

    Note: Alternatively, navigate to Device Management > Devices and click the local device.

  3. In General Properties > Status, locate the failover status.
  4. Verify whether the current redundancy state is expected for the system.

tmsh

  1. Log in to tmsh by typing the following command:

    tmsh

  2. To view dynamic information about the failover status of the device in a device group, type the following command:

    run /cm watch-sys-device

Verifying the failover cable status

When using hardwired failover, you can verify the peer status that the sod process detects on the failover cable. You can also verify what the failover peer detects on the serial cable. To determine the status that the sod process detects on the failover cable, perform the following procedure:

Note: Hardwired failover only pertains to devices configured in an active-standby pair; hardwired failover does not pertain to VIPRION, BIG-IP VE, and device group deployments containing three or more devices.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to tmsh by typing the following command:

    tmsh

  2. To determine whether the system is configured to use hardwired failover, type the following command:

    show /sys failover cable

  3. Verify the output is correct for your environment.

    For example, if the output returns cable state unset, verify whether you are using the correct failover cable for your platform and that the cable connects securely to the failover port. You can interpret the command output as described in the following table.

    OutputDefinition
    cable state 0The active unit should detect zero (0) from its peer on the failover cable.
    cable state 1The standby unit should detect one (1) from its peer on the failover cable.
    cable state unsetThe system does not detect a failover cable connected between the devices; this can indicate that hardwired failover is not configured.

Verifying network failover traffic using tcpdump

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP command line.
  2. To verify unicast network failover traffic between device group members, use the following tcpdump syntax:

    tcpdump -ni <vlan> port <unicast_network_failover_port>

    For example:

    tcpdump -ni internal port 1026

  3. To verify multicast network failover traffic between device group members, use the following tcpdump syntax:

    tcpdump -ni <interface> port <multicast_network_failover_port>

    For example:

    tcpdump -ni eth0 port 62960

Note: For more information about using the tcpdump utility, refer to K411: Overview of packet tracing with the tcpdump utility.

Reviewing the HA table

 

The HA table is a tool that you can use for troubleshooting failover issues. The HA table displays the HA status of certain components, such as daemons or hardware components, for a BIG-IP device. The table is a shared memory segment that provides a way for the components to post information about the HA features they implement, and a way for other components to look up the status of a particular entity using the HA status feature name or key. For example, at system startup, the sod process determines whether all TMM instances are running. To do so, the sod process searches for the HA ready-for-world feature name and TMM key name, and confirms that TMM instances are not in a failed state.

The columns in the HA table are defined as follows:

  • Sys::HA Status Feature: Indicates the name of the HA feature, such as daemon-heartbeat. Features can trigger a defined action, such as failover.
  • Key: Indicates the name of the component that reports its status in the HA table. For example, a daemon.
  • Action: Indicates the action the system takes when the component fails.
  • Fail: Indicates the failure status of the specific component. The failure status can indicate something other than a fault condition. For example, the Ready for World feature reports a failed status for TMM during system initialization or when a chassis is disabled; the failed status is cleared when the TMM is ready to process traffic.

Understanding HA failsafe events

HA failsafe events can be loosely grouped into the following categories:

  • Hardware-related failsafe events
  • Daemon failsafe events
  • Feature-related failsafe events

Hardware-related failsafe events

The HA failsafe feature allows the BIG-IP system to monitor various hardware components and then take an appropriate action if the system detects a failure. The HA features in the following table may appear when the platform contains the relevant hardware device.

HA featureDescriptionFailsafe action
crypto-failsafeIndicates that the SSL card has locked up on BIG-IP systems with the Cavium Nitrox, Cave Creek, or Coleto Creek SSL cardgo-offline-downlinks
nic-failsafeUsed by TMM to detect a transmit/receive failure in an HSB attached interfacereboot
hardware-failoverUsed by the system to report voltage level drops over the failover cable for systems configured to use hardwired failovergo-active
switchboard-failsafeUsed to detect a transmit/receive failure in the data path between the Broadcom switch and TMMgo-offline-abort-tm

Daemon failsafe events

The daemon failsafe checks allow the BIG-IP system to monitor various daemons and then take some action if the system detects a failure. The following table describes the daemon-related HA features.

HA featureDescriptionFailsafe action
proc-runCertain daemons on the BIG-IP system must always be running, while other daemons are only required to be running if the related module is provisioned. The proc-run feature is used by the system to ensure that key daemons, such as TMM, are running; if the system detects that a required daemon is not running, then the specified action is taken.go-offline-downlinks
daemon-heartbeatSystem daemons increment their heartbeat values when they are in a running state, and the sod process monitors the heartbeat signals to ensure the daemons are running. If a daemon fails to increment its heartbeat timer, the system performs the failsafe action.various
ready-for-worldThe sod process monitors the HA table during system start up to verify the status of TMM instances and whether all TMM instances have started properly.none

Feature-related failsafe events

The feature-related failsafe checks allow the BIG-IP system to monitor aspects of the system, such as network traffic on a defined VLAN, and then take an action if the system detects a failure. The following table describes HA features that you configure the for corresponding BIG-IP feature.

HA featureDescriptionFailsafe action
pool-mbr-downWhen the gateway fail-safe feature is configured, the BIG-IP system monitors the gateway pool members and takes action when the available pool members are fewer than the number specified.Fail over to peer
vlan-failsafeWhen the VLAN fail-safe feature is configured, the BIG-IP system monitors network traffic going through a specified VLAN and takes action when a loss of network connectivity is detected.Restart
ha-group-scoreWhen an HA group is assigned to a traffic group, the system monitors objects such as trunks, pools, and/or VIPRION clusters. When you associate an HA group with a traffic group instance on a specific device, the BIG-IP system calculates a health score for that device for the associated traffic group, based on trunk, pool, or cluster availability.Failover

Troubleshooting hardware-related failsafe events

The BIG-IP system monitors various hardware components and takes an appropriate failsafe action if the system detects a failure. When the HA table reports a failure status for a hardware component, you may need to take additional action such as running the EUD utility to determine if the component has failed or locked up. To troubleshoot hardware-related failsafe events, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to tmsh by typing the following command:

    tmsh

  2. To display the HA table, type the following command:

    show /sys ha-status

    The following example output shows that the crypto-failsafe HA feature on blade 2 has indicated a failsafe event for a SSL card:

    ---------------------------------------------------------------------------

    2 crypto-failsafe         cn-crypto-2     failover                      no
    2 crypto-failsafe         cn-crypto-3     failover                      no
    ...

  3. Review the log files for error messages related to the hardware failsafe event.

    For example, the following command searches the ltm log file for failsafe messages and the resulting message indicates that the sod process initiated a failsafe action for the crypto_failsafe HA feature:

    show /sys log ltm | grep -E -i 'failover|failsafe'

    notice sod[9570]: 01140029:5: HA crypto_failsafe_t cn-crypto-0 fails action is failover.

    show /sys log ltm range <month-day>:<hr>:00:00--<month-day>:<hr>:59:59

    For example, type the following command:

    show /sys log tmm |grep -i 'device error'

  6. If you find additional indication of a hardware issue, you may need to run the EUD utility on the BIG-IP device.

    Note: For information about the EUD utility, refer to K7172: Overview of the End User Diagnostics software.
