Known Issue

The HTTP profile compression settings override the compression settings in the BIG-IP WebAccelerator acceleration policy. This issue occurs when the following condition is met:

  • Compression is enabled in the HTTP profile that is associated with the WAM-enabled virtual server

The expected behavior is for the compression configuration in the BIG-IP WebAccelerator acceleration policy to take precedence regardless of the compression configuration in the HTTP profile that is associated with the WAM-enabled virtual server.

Note: You can enable or disable the compression configuration of an object in the BIG-IP WebAccelerator system by selecting or clearing the Enable Content Compression check box under the Assembly tab of a leaf node in an acceleration policy.

Impact

Content may be compressed even if you disable compression for the specific object in the BIG-IP WebAccelerator acceleration policy.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • The HTTP response header of the object that has content compression disabled in the WebAccelerator acceleration policy contains a Content-Encoding: gzip entry.
  • The tmsh show ltm profile http <http profile name> command output displays increments for the object type in both the Pre-Compress and the Post-Compress columns under the Content Type Compression section.

    Consider the following example. The BIG-IP WebAccelerator acceleration policy has the Enable Content Compression option cleared for the Page leaf node while the myhttpacceleration profile associated with the BIG-IP WebAccelerator-enabled virtual server has compression enabled with text/html configured in the Content Include List:

    ltm profile http myhttpacceleration {  compress enabled
      compress-content-type-exclude none
      compress-content-type-include { text/html }
      defaults-from http-acceleration
    }

    When the BIG-IP WebAccelerator receives a request that has Accept-Encoding: gzip in the HTTP request header for HTML content, the BIG-IP WebAccelerator does not compress the response content, but the BIG-IP LTM performs the compression on the response content. The tmsh show ltm profile http myhttpacceleration command shows the HTML entry in the Content Type Compression section with 5.2K and 2.1K in both the Pre-Compress and Post-Compress columns, respectively, after the request, compared to the same display that has 0 in both columns before the request:

    Note: The command output is truncated for brevity.

    Before the request:

    Content Type Compression (bytes) Pre-Compress Post-Compress
    HTML                                      0               0

    After the request:

    Content Type Compression (bytes) Pre-Compress Post-Compress
    HTML                                   5.2K            2.1K

Workaround

To work around this issue, you can disable the compression configuration in the associated HTTP profile. To do so, perform the following procedure:

Impact of workaround: None.

  1. Log in to the Configuration utility.
  2. Click Local Traffic.
  3. Click Profiles.
  4. Click Services.
  5. Click HTTP.
  6. Click the name of the affected HTTP profile.
  7. From the Compression field, select Disabled.
  8. Click Update.
