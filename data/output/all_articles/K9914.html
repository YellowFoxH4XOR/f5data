Known Issue

This is the result of a known issue. When VLAN failsafe is triggered and the VLAN failsafe timeout value is less than 30 seconds, TMM may core.

When this issue occurs, information that appears similar to the following example is written to the /var/log/tmm file:

<Month> <Day> <Time> <Hostname> ** SIGABRT **
<Month> <Day> <Time> <Hostname> fault code: 0x0

In addition, a failover occurs in a redundant configuration, and the TMM process restarts.

This issue is more likely to occur when all of the following conditions are met:

  • TMM has been up for 49 days or longer.
  • VLAN failsafe timeout value is configured for less than the recommended 30 seconds.
  • Three-quarters of the VLAN failsafe timeout value is reached without receiving traffic.

A probe used by the VLAN failsafe is incorrectly updated, which causes the system to act as though the amount of time between probes has passed. As a result, the system issues another probe too soon and eventually results in a loop condition.

Another symptom that may indicate this issue is if TMM loops, which may prevent TMM from communicating to the watchdog process heartbeat. This may result in the watchdog process rebooting the system due to the failed communication, and no core file being created. This symptom is more likely to occur on a single processor system when the VLAN failsafe timeout value is less than 30 seconds.

F5 Product Development is tracking this issue as CR98735 for the BIG-IP 9.3.x code branch.

F5 Product Development tracked this issue as CR75407 for the 9.4.x code branch and it was fixed in BIG-IP version 9.4.2. For information about upgrading, refer to the BIG-IP LTM and Link Controller release notes.

Workaround

To prevent this behavior from occurring, do not set the VLAN failsafe timeout value lower than the default of 30 seconds.

Note: For more information, refer to K7066: Overview of VLAN failsafe.
