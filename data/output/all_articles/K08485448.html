Description

You want to replace an existing blade in a VELOS system that has multiple blades installed. The replacement blade could be a Return Materials Authorization (RMA) replacement blade or a spare blade that you may have.

  • To replace an existing blade in a VELOS system that has only a single blade installed, refer to K19494503: Replacing a blade in a VELOS system that has only a single blade installed.
  • To replace a VELOS system controller, refer to K000133249: Replacing VELOS system controller after a Return Materials Authorization.

BIG-IP tenants on a blade

The blade stores the BIG-IP tenant virtual disks. The following describes what results for single-slot and multi-slot tenants when you replace a blade:

  • Single-slot tenants: After replacing the blade, the new blade does not contain the original tenant virtual disks. The tenant boots with the software version of the BIG-IP image specified in the F5OS tenant configuration. If the BIG-IP image specified in the F5OS tenant configuration is not the same as the latest BIG-IP version of the tenant (meaning you have upgraded the tenant from within the tenan), after the new tenant instance deploys, you may need to upgrade it to a newer BIG-IP version or hotfix before restoring the UCS archive.

    If you do not have the UCS archive of a single-slot tenant, and the existing blade is no longer functional, you must manually rebuild the BIG-IP tenants’ configurations. F5 does not store customer’s configuration files.

  • Multi-slot tenants: When the new blade powers on, it should connect to the primary blade to install the required BIG-IP software automatically.

Environment

  • VELOS chassis with multiple blades installed.
  • You have physical access to the VELOS system.
  • You have serial console access to the VELOS system.
  • You have administrative access to the VELOS system.

Cause

None

Recommended Actions

Perform the procedures in this section to replace the blade in the same slot on your VELOS system:

  • Check the partition's root account status
  • Back up tenants with UCS archives and optionally other VELOS data 
  • Replace existing blade with the new one in the same slot
  • Power on the new blade and boot up the affected BIG-IP tenants
  • Restore BIG-IP configuration in single-slot tenants

Impact of Procedure

When replacing a blade, take the following impact into consideration:

  • Single-slot tenants on the blade to be replaced, will be shutdown. All services provided by the tenant will not be available as a result. However, if they are part of a high-availability (HA) pair with its peer on another separate VELOS system, you should fail over the tenant to its functional peer before attempting to perform the replacement and services can be maintained. For information about forcing an active BIG-IP tenant to standby mode, refer to K30371289: Forcing an active BIG-IP system to standby mode using the Configuration utility
  • For multi-slot tenants, they can remain running.
  • F5 recommends that you always perform blade replacement during a scheduled maintenance window to avoid any potential disruptions to your application environment.

Check the partition's root account status

Note: If replacing a blade that is not a member of a VELOS partition, the system will be unable to add the blade to the cluster until the root user's password on the blade is changed, or the blade is added to an enabled partition.  Refer to Bug ID 1575585 for more information.

Note: If replacing a blade that is a member of a VELOS partition, make sure that the root account is not disabled (expiry status of "locked" or a expiry date of "1"). Refer to Bug ID 1397145 for more information.

Impact of procedure: Ensure there is sufficient disk space on the system for the backup files. /var/log/ucs is the default directory for UCS archives. Otherwise, performing the following procedure should not have a negative impact on your system.

Replace existing blade with the new one in the same slot

Impact of procedure: The BIG-IP tenants on the affected blade will be shutdown. F5 recommends performing this during a scheduled maintenance.

  1. Shutdown affected single-slot BIG-IP tenants on the affected blade. 
    For every single-slot BIG-IP tenant on the affected blade, perform the following procedure to shutdown it down:
    Note: To identify the single-slot tenants, refer to Identify which blade a BIG-IP tenant resides procedure in the Additional Information section.
    Note: Multi-slot tenants can remain running. 
    1. Login to the webUI of the partition floating management IP address
    2. Select TENANT MANAGEMENT > Tenant Deployments
    3. Select the checkbox next to the affected tenant.
    4. Select Configured.
  2. Power off the affected blade via the AOM menu. If you have no further use for the blade, skip this step. 

    To enter AOM, enter Esc ( on the VELOS console. For more information, refer to K65442484: Overview of access to the F5 VELOS system.

  3. Physically replace the affected blade with the new one. For more information, refer to the Physically replace an affected blade with a new one procedure in the Additional Information section.

Power on the new blade and boot up the affected BIG-IP tenants

Impact of procedure: Performing the procedure should have no negative impact on the system.

  1. Power on the new blade if it is not already automatically powered on. For information about powering on a blade, refer to K19230226: Turn off or turn on a VELOS system using the AOM Command Menu.
  2. Verify the new blade's readiness and network connectivity. For more information, refer to the Verify a blade's readiness and network connectivity procedure in the Additional Information section.
  3. Boot up all BIG-IP affected BIG-IP tenants.
    1. Set the State of the BIG-IP tenant(s) to Deployed so that the VELOS system can start up the tenant(s). For information about starting up a tenant, refer to K21121803: Shut down and restart a tenant on the VELOS and F5 rSeries systems.
    2. Wait for the BIG-IP tenant to boot up completely. You can monitor the bootup of the tenant using the BIG-IP tenant console via the system controller console. For information about accessing the BIG-IP tenant console, refer to K65442484: Overview of access to the F5 VELOS system.

Restore BIG-IP configuration in single-slot tenants

For multi-slot tenants, when the new blade powers on, it should connect to the primary blade to install the required BIG-IP software automatically.

For single-slot tenants, after replacing the blade, the new blade does not contain the original tenant virtual disks. The tenant boots with the software version of the BIG-IP image specified in the F5OS tenant configuration. You may first need to upgrade this to a newer BIG-IP version or hotfix that it originally ran, before restoring the UCS archive. Perform the following procedure:

  1. Verify the BIG-IP version of the tenant is the same as the original version. Upgrade to a newer version or hotfix as required.
  2. Restore the UCS archive on the tenant. For more information, refer to the following:
    • K13132: Backing up and restoring BIG-IP configuration files with a UCS archive.
    • K9420: Installing UCS files containing encrypted passwords or passphrases (11.5.x and later)
  3. On the tenant, verify the configuration is loaded and the cluster is healthy by entering the following commands:

    tmsh show sys mcp-state
    tmsh show sys cluster

Additional Information

The following section contains the following procedures you may need to perform a blade replacement:

  • Identify which blade a BIG-IP tenant resides
  • Physically replace an affected blade with a new one
  • Verify a blade's readiness and network connectivity

Identify which blade a BIG-IP tenant resides
To identify which blade a BIG-IP tenant resides on the system, perform the following procedure:

Impact of procedure: Performing the procedure should have no negative impact on the system.

  1. Login to the webUI of the partition floating management IP address
  2. Select TENANT MANAGEMENT > Tenant Deployments
  3. Verify the blades in the Allowed Slots column.

Physically replace an affected blade with a new one

Impact of procedure: This procedure involves removing a blade from the chassis. Services provided by the blade will be disrupted. F5 recommends performing this during a scheduled maintenance.

  1. Note the network cables and optical modules configuration before you physically remove them from the blade. You need to restore them after inserting the new blade in a later step. Disconnect all cables and remove the optical modules.
  2. Note the network cables and optical modules configuration before you physically remove them from the blade. You need to restore them after inserting the new blade in a later step. Disconnect all cables and remove the optical modules.
  3. Remove the blade from the chassis. Press the blue latch release on the front of the blade to release the ejector handle. Grasp the ejector handle and pull towards you, ensure that you support the weight of the blade as you remove it from the chassis.
  4. Insert the new blade into the same slot as the previous blade. For example, if the blade removed in the previous step was in slot 1, ensure that you insert the new blade into slot 1. Press the blue latch release on the front of the blade to release the ejector handle. Slide the blade in until the ejector contacts the catch in the chassis. Press the ejector handle until the blade is locked in place.
  5. Restore the optical modules and cables back to the blade's interfaces as noted in step i.

Verify a blade's readiness and network connectivity

Perform the following procedure to verify a blade's readiness and network connectivity:

Impact of procedure: Performing the procedure should have no negative impact on the system.

  1. Log into the VELOS system controller CLI as the chassis admin user.
  2. Wait for the new blade to be ready. You can monitor the status of the new blade by entering the following command:

    show cluster | repeat

    When the blade is ready, the command will report the cluster-status summary-status as Openshift cluster is healthy, and all controllers and blades are ready.

  3. Additionally, you must wait for the new blade to be the replica in the partition that it is assigned. You can monitor this status by logging into the partition CLI as the partition admin user and enter the following command:

    show system redundancy

    When the blade is ready as the replica, the command should report the STATUS of the blade as replica.

  4. Verify that the portgroup modes are properly set and the optic-state is showing QUALIFIED. You can verify this by logging into the partition CLI as the partition admin user and enter the following command:

    show portgroups

  5. Ensure that the interface(s) is present and up. You can verify the interfaces' status by logging into the partition CLI as the partition admin user and enter the following command:

    show interfaces

    This will display all interfaces in the partition. Alternatively, if you want to verify only a specific interface, you can enter the following command syntax:

    show interfaces interface <interface number> state

  6. If you have configured LACP LAG for the partition, you should ensure that the LACP LAG is up. You can verify the status of the LACP LAG by logging into the partition CLI as the partition admin user and enter the following command syntax:

    show interfaces interface <LAG name>

    Alternatively, you can enter the command show lacp and verify that there are active members listed in the output.
