Known Issue

The Traffic Management Microkernel (TMM) daemon on the standby device may unexpectedly restart when it receives mirrored connections from the active device.

This issue occurs when all of the following conditions are met:

  • The BIG-IP LTM devices are configured as active and standby peers.
  • The BIG-IP LTM devices are configured to monitor nodes or pool members that reside on a routed network.
  • The BIG-IP LTM device configuration contains a mirroring-enabled object, similar to either of the following examples:
    • SNAT listener configured with mirroring enabled:

      ltm snat /Common/default_snat {
      mirror enabled
      origins {
      0.0.0.0/0 { }
      }
      snatpool /Common/default_snat_pool
      vlans {
      /Common/external
      }
      vlans-enabled
      }
    • Wildcard virtual server with a FastL4 profile, configured with mirroring:

      ltm virtual wildcard_vs_example {
      destination 0.0.0.0:any
      mask any
      mirror enabled
      profiles {
      fastL4 { }
      }
      source 0.0.0.0/0
      translate-address disabled
      translate-port disabled
      }
  • Connections are mirrored for the wildcard virtual server to the standby device.

This issue is most commonly triggered when the standby BIG-IP system sends a request, such as a monitor request, to a node on a different network. If the node erroneously sends the response packets back to the active BIG-IP LTM device, the active system processes the response connections and mirrors the connection state to the standby BIG-IP LTM device. This creates a scenario where the mirrored connection is a duplicate of an existing connection state on the standby BIG-IP LTM device.

Impact

The TMM daemon on the standby device produces a core file and restarts.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • BIG-IP iHealth lists Heuristic H432575 on the Diagnostics > Identified > Medium screen.
  • You notice log messages, similar to the following example, in the /var/log/tmm file:

    notice panic: ../modules/hudproxy/ha/ha_proxy.c:1477: Assertion "non-zero ha_unit required for mirrored flow" failed.
    notice ** SIGFPE **
  • A core file, similar to the following example, is produced in the /shared/core file:

    /var/share/tmm.0.bld2405.0.core.gz

Note: As shown in the previous example, the core file starts with tmm, followed by the TMM number (0, in this example), the TMM code-level build number (bld2405.0, in this example), and ends with core.gz.

Workaround

To work around this issue, you can eliminate routing issues on the network by disabling mirroring on the affected virtual server. To do so, perform the following procedure:

Impact of workaround: Connections will no longer be mirrored to the standby device, which can impact the state of existing connections in the event of a failover.

Using the Configuration utility to disable mirroring on a virtual server

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Virtual Servers.
  3. Select the affected virtual server's name.
  4. In the Configuration: menu, select Advanced.
  5. Clear the Connection Mirroring check box.
  6. Click Update.

Using the tmsh utility to disable mirroring on a virtual server

  1. On the active BIG-IP LTM device, using administrative access, log in to the command line.
  2. Type the following tmsh command, replacing <virtual_server_name> with the name of the affected virtual server:

    tmsh modify ltm virtual <virtual_server_name> mirror disabled
  3. Save the configuration change by typing the following command:

    tmsh save sys config
