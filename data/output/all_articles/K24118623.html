K24118623: istio-proxy logs indicate it does not reuse existing TCP connection in HTTP/2

Type
Support Solution
Published
2021-06-23
Updated
2023-07-19
Applies to
  • Aspen Mesh: 1.11
Source
https://my.f5.com/manage/s/article/K24118623

Description

The istio-proxy logs show that HTTP/2 request are always in different TCP connections from the outbound cluster but the same in inbound cluster why is this happening?

Environment

  • RedHat Openshift: 4.6x, 4.7.x
  • Kubernetes: 1.17x,1.18.x,1.19.x,1.20.x
  • Aspen Mesh: 1.6.x, 1.9.x

Cause

On the server-side, the server will keep the connections from various clients open until they are either closed by the client or until the server-side idle timeout fires. At that point, it's the server that initiates the close of the TCP connection.

When a request from the client is made to the server using HTTP/2, we need to consider that all the connections are not shared across worker threads in the istio-proxy. That means that when an application uses only one thread; we should only see 1 TCP connection. If the application uses four threads, all the requests will go on four different TCP connections. 

Recommended Actions

Test your application from client and server (if both are inside the mesh) in order to understand the HTTP/2 connection reuse behavior.
  1. Make a few requests from the client to the server.
  2. Ensure that you are only using 1 thread.
  3. Make a new request now using more than 1 thread.
  4. Compare the difference in the logs.

Gather the logs from your istio-proxy client and server and compare the data sent from the outbound clusters. To get the logs from your istio-proxy, refer to K67125033: Aspen Mesh: How to get isto-proxy logs.
