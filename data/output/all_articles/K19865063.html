Topic

Starting in BIG-IP 13.1.0, the Traffic Management Microkernel (TMM) can perform live debugging while it passes traffic. This feature may be useful if your TMM encounters serious problems that F5 cannot reproduce internally.

Note: Do not confuse TMM dynamic debugging, described in this article, with debugging using an instrumented TMM. An instrumented TMM is a special version delivered to specific customers in the form of an engineering hotfix, and you must install it as an engineering hotfix.

Important: If you have an instrumented TMM from F5 Support, you should follow the instructions provided to you by F5 Support for the instrumented TMM, not this instructions in this article.

Description

This article applies under the following conditions:

  • You are working with F5 to troubleshoot a problem that is occurring with your TMM in live traffic situations.
  • F5 cannot reproduce the problem internally.
  • F5 suggests that you perform dynamic debugging on your device to gather diagnostics to help fix the issue.

    Important: Do not perform the dynamic debugging procedures included in this article if you have an instrumented TMM from F5 Support.

This article explains:

  • Dynamic debugging
  • How to enable and disable dynamic bugging
  • The impact dynamic debugging may have on your live environment

For example, consider a case in which one of your TMMs is consuming large amounts of memory when specific traffic passes through it. The traffic looks like typical network traffic. F5 is unable to recreate the same behavior internally, which makes it challenging for F5 to identify the root cause. F5 may ask you to perform dynamic debugging in order to gather more diagnostic information than TMM typically provides.

Dynamic debugging

TMM is compiled with trace points that F5 can access using customized Lua debugging files. F5 does not make these files available to customers, because they are specific to troubleshooting. Also, the trace points that F5 needs to access depend on the problem you're investigating. When a TMM extension loads the Lua files, the system logs the trace points to /var/log/tmm when it encounters them. The system collects these logs when you run the qkview utility to produce a QKView file, and you can provide the logs to iHealth to help F5 in troubleshooting.

Recommendations

If F5 asks you to perform dynamic debugging, this article can help you understand the impact to your environment.

Dynamic debugging tools do not exist on the BIG-IP system. F5 must provide these tools in the form of an .rpm package. The package contains files that enable scripts that look for certain trace points specific to the problem you are encountering on your device. The files are encrypted using a key provided by your device, and you need to provide this key before you can start troubleshooting. The key is contained in the QKView file. If you are asked for it, you can generate the key using the following command:

tmsh list /sys dynad key blob

The RPM package produced from the key is specific to your device's master key and the version of software running on that device.

During this process, F5 explains what they are looking for and any possible performance impact your system may experience while the diagnostics are running. The goal is to have diagnostics running when the event that triggers the problem occurs, and then you can disable dynamic debugging, create a QKView file, and upload it to iHealth.

After you upload the diagnostics .rpm package to the BIG-IP /shared/rpms directory, you must install, enable, and disable it.

Use the following command syntax to install the package:

tmsh install /sys dynad rpm <rpm_name>

After you install the .rpm package, you can activate dynamic debugging using a command similar to the following example:

tmsh modify /sys dynad instrumentation debug.lua active true

Note: In this example, the debugging script is named debug.lua.

To view the dynamic debugging status, enter the following command:

tmsh list /sys dynad instrumentation

The amount of time required to run dynamic debugging with instrumentation enabled depends on the type of problem your system has and whether or not you can easily reproduce it. If you are able to trigger the issue, you can disable dynamic debugging by using command syntax like the following example:

tmsh modify /sys dynad instrumentation debug.lua active false

Note: In this example, the debugging script is named debug.lua.

The system logs trace points to the /var/log/tmm# file (# corresponds to the TMM number that encountered the trace point).

After you finish the dynamic debugging session, generate a QKView file and send it to iHealth for analysis.

Beginning BIG-IP 14.1.0, you can delete the instrumentation file after generating the debug output. To do so, you can delete it by using the following command syntax:

tmsh delete sys dynad instrumentation <output filename>

For example:

tmsh delete sys dynad instrumentation debug.lua
