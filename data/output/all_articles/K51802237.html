K51802237: Defining a Microservice within a Security Policy can cause potentially unexpected behavior

Description

Starting in BIG-IP 14.1 you can define Microservices. When a Microservice is defined with a security policy and the traffic passing through the policy matches the defined Microservice, the security policy will use the defined settings within the Microservice itself. 

  • Traffic not being handled how the general security policy is defined
  • Example would be if you see a illegal request and you believe the request should be blocked based on the general security policy settings
When you define a Microservice within your security policy it will have it own settings. The different areas that can be defined are the following: 
  • Evasion technique detected and the ability to Enable, Learn and Override within this
  • HTTP protocol compliance failed and the ability to Enable, Learn and Override within this
  • The overall enforcement setting for the Microservice itself
If you are seeing traffic that is flagged as illegal and you believe it should be blocked or vice versa please check to see if you have defined a Microservice that matches the traffic.

This can be found here on 14.1 by going to the following:

Security  ››  Application Security : Microservices


On 15.1 this can be viewed here: 

Security  ››  Application Security : Security Policies : Select the Policy in question and Microservices will be on the left


On 16.1 this can be viewed here: 

Security ›› Application Security : Security Policies : Select the Policy in question and click the drop down on the left for HTTP Message Protection

Environment

  • Have a Microservice defined within your security policy
  • Traffic in question matches the defined security policy

Cause

Overall if a Microservice is defined for the application traffic in question then the security settings for the Microservice will take precedence over the setting defined within the general policy.

Microservice example: 

If you have a defined Microservice within a security policy for the host: www.mysite.com and the URI /admin, the Microservice appears similar to the following: 

www.mysite.com/admin

This defined Microservice will allow you to have unique settings within the security policy for the specific host/URI. Once this is defined you need to keep in mind that if the traffic matches the Microservice (in this case, www.mysite.com/admin), then the system will use the security settings defined within the Microservice, including the policy Enforcement Mode. 

The Microservice configuration overrides other policy elements, such as the following disallowed URL:

/admin*

Without an overlapping Microservice, if a client browses to www.mysite.com/admin/ the policy will use the settings within the disallowed URL. If you have that set to block and it is not in staging the request should be blocked. 

However, if the client browses to www.mysite.com/admin and the request exactly matches both the disallowed URL and the defined Microservice, and the Microservice is set to Transparent, then the request to www.mysite.com/admin will be allowed because the matching Microservice is in Transparent mode.

Recommended Actions

If you have a defined Microservice within your security policy set to Transparent and we wanted this traffic to www.mysite.com/admin to be blocked we need to make a change to the security policy. The options at this point would be the following: 

  1.  You can change the Microservice from Transparent to Blocking within the Policy. You will need to manage this host/URI going forward with the Microservice in mind
     
  2. You can delete the defined Microservice that matches this traffic and it will then Block based on the Disallowed URL:

    /admin*
