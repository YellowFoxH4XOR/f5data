Topic

The BIG-IP system can generate core files for a variety of reasons. When the BIG-IP system encounters an issue, the system may deliver a signal to the affected process that terminates the process and writes a core file containing an image of the process's memory at the time of termination.

Core files may generate as a result of a variety of signals, the most common include SIGFPE, SIGSEGV, SIGABRT, and SIGTERM. When a BIG-IP process dumps a core file, the precipitating event is typically either a code defect in the target process or the result of a watchdog or failsafe process terminating the target process.

SIGFPE and SIGSEGV

Core files that generate as a result of the signals SIGFPE and SIGSEGV, almost always indicate the presence of a code defect, and typically include information useful in identifying the root cause of the defect. When the system sends a SIGSEGV to Traffic Management Microkernel (TMM), the Relative Instruction Pointer (RIP) for 64-bit systems can be a good indicator to what triggered the issue. The RIP is the CPU register containing the address of the code executed by the process at the time of the core. You can find the RIP in the stack trace logged to the /var/log/tmm* file, which appears similar to the following example:

<13> Aug 23 20:28:28 notice RIP=0x15cc743

The RIP is typically not a good indicator of the cause of a core when the SIGFPE signal is sent to TMM. The panic string indicating the assertion failure associated with the event should be located instead. If present, you can find the panic string logged prior to the associated stack trace the /var/log/tmm* file.

For example:

notice panic: ../modules/hudproxy/bigproto/bigproto.c:4041: Assertion "syncookie" failed
notice ** SIGFPE **

SIGABRT and SIGTERM

Core files that generate as a result of signals, such as SIGABRT and SIGTERM, typically indicate that a service was terminated by a watchdog mechanism, and may or may not be useful in identifying the root cause. The BIG-IP system has several watchdog mechanisms that may terminate other processes if they are deemed unresponsive, problematic, or if termination is otherwise necessary to continue normal system operation. These include failsafe mechanisms and daemon dependencies that have specifically been built into the BIG-IP system, and also the resource contention logic built into the Linux kernel itself. A core that results from one of these signals may reveal a code defect or abnormal operation, but in most cases the target process is terminated as an operational safeguard, and the core would only reveal that the process was operating as expected. For examples of this process in action, refer to K8519: The default switchboard failsafe action generates a TMM core file and K10095: Error Message: Clock advanced by <number> ticks.

Note: For more information about core files and signals, refer to the core(5) — Linux manual page and the signal(7) — Linux manual page on man7.org. These links take you to resources outside of MyF5. The third party could remove the documents without our knowledge.

BIG-IP core files

When your BIG-IP system generates a core file, you should contact F5 Support for assistance. You must follow the steps detailed in the following sections to correctly collect and submit the core files and other diagnostic data that the support representative will require in order to assist you.

For assistance creating a support case, refer to K2633: Submit a support case.

When a daemon produces a core file, the core file is written to the standard log file of the daemon and stored in a common location with a file name matching the daemon. For more information, refer to K42003030: BIG-IP daemons log core files to a common location.

Managing new core files

Important: Immediately following a core dump, you must generate an MD5 checksum for each core file, then move all core files with their corresponding checksum files out of the /var/core/ directory to another directory, such as the /var/tmp/ directory. This step ensures that the core files are not overwritten by new core files from a subsequent event. You may delete the core and checksum files once F5 Support determines that they are not needed, or when they have completed analyzing the issue.

You will have to submit the checksum file along with the core file to allow F5 Support to verify its integrity prior to examination. To do so, perform the following procedure:

  1. Log in to the Advanced Shell (bash) as the root user.
  2. Change to the /var/core/ directory, by enter the following command:

    cd /var/core

  3. Create an MD5 checksum file for the core file, by using the following command syntax:

    md5sum <name-of-core-file> > <name-of-core-file>.md5

  4. To move the core file and its MD5 checksum file to the /var/tmp/ directory, use the following command syntax:

    mv /var/core/<name-of-core-file>* /var/tmp/

Collecting initial diagnostic data

Before you submit core files to F5, you must gather diagnostic information from the F5 device and then open a case with F5 Support. For information about gathering the diagnostic data and submitting a support case to F5, refer to K2633: Submit a support case.

Forcing a core dump for analysis when asked by F5 Support

F5 Support may ask you to force a core dump on the BIG-IP system in order to establish the state of a process during an event. You can send signals, such as SIGABRT and SIGSEGV, to processes on the BIG-IP system using the kill command from the command line. Forcing the BIG-IP system to process a core dump interrupts service and you should perform this task only when asked to do so by F5 Support. For information about forcing a core dump on BIG-IP systems, refer to K13002225: Producing diagnostic core files to F5 Support (12.x and later).

Selecting core files for submission

If the system has generated only one core file, you should always submit this core for analysis along with the required initial diagnostic data listed. If the system has generated multiple core files, you may have to submit only some of them.

Due to the size and number of TMM core files that may generate on a multi-core system, it can be helpful to identify which TMM core files are of immediate interest to F5 Support, since you may not have to submit them all.

When multiple TMM core files are dumped together, those generated by SIGSEGV or SIGFPE signals will be of the most interest to F5 Support, and you should submit the files for analysis immediately. You should submit any associated stack traces containing RIPs as well. SIGABRT or SIGTERM signals will have generated the remaining cores, which were precipitated by the SIGSEGV or SIGSEGV event, and contain no useful troubleshooting information. You may submit TMM cores generated by SIGABRT or SIGTERM signals as time and bandwidth allow, or as requested by F5 Support.

Submitting diagnostic data and core files to F5 Support

To submit core files and the diagnostic data described in the previous section to F5 Support, refer to the steps detailed in K000090853: Exchange files with F5 Support.

Determining the signal responsible for a core file

You can determine the signal responsible for each TMM core file by performing the following procedure:

  1. To display the core files with their timestamps, enter the following command:

    ls -latr /var/core/

Downloading core files from a VIPRION system when the blades are not configured with individual management addresses

When the blades of a VIPRION system are not configured with individual management addresses and only the cluster management address is configured, you cannot download core files directly from the blade on which they were generated. You must first move the core files to the primary blade, which is accessible through the cluster management address. To download a core file from blade 4 when blade 1 is the cluster master, perform the following procedure:

  1. Log in to the BIG-IP command line.
  2. Access the Advanced Shell (bash) by entering the following command:

    bash

  3. Confirm the hosts file contains entries for the localhost blade IP addresses by entering the following command:

    cat /etc/hosts

    The output appears similar to the following example:

    127.3.0.1       slot1
    127.3.0.2       slot2
    127.3.0.3       slot3
    127.3.0.4       slot4
    127.3.0.5       slot5
    127.3.0.6       slot6
    127.3.0.7       slot7
    127.3.0.8       slot8
    127.3.0.1       primary

  4. Go to the slot with the core file by entering the following command:

    ssh root@slot<#>

    For example:

    ssh root@slot4

  5. Go to the core folder by entering the following command:

    cd /var/core/

  6. Confirm the core file is present by entering the following command:

    ls

  7. Create an MD5 checksum of the core file by entering the following command:

    md5sum <core_filename> > <core_filename>.md5

    For example:

    md5sum tmm.bld2.0.291.core.gz > tmm.bld2.0.291.core.gz.md5

  8. Copy the core and md5 checksum files to the primary blade by entering the following command:

    scp <core_filename> <primary_slot>:/var/tmp/<core_filename>
    scp <md5sum_filename> <primary_slot>:/var/tmp/<md5sum_filename>

    For example:

    scp tmm.bld2.0.291.core.gz slot1:/var/tmp/tmm.bld2.0.291.core.gz
    scp tmm.bld2.0.291.core.gz.md5 slot1:/var/tmp/tmm.bld2.0.291.core.gz.md5

  9. Return to the primary slot by entering the following command:

    exit

  10. Confirm the core md5 checksum files are present in the /var/tmp/ folder by entering the following command:

    ls /var/tmp/

  11. Confirm the core file copied successfully to the primary slot by entering the following command:

    md5sum /var/tmp/<core_filename> && cat /var/tmp/<md5sum_filename>

    For example:

    md5sum /var/tmp/tmm.bld2.0.291.core.gz && cat /var/tmp/tmm.bld2.0.291.core.gz.md5

  12. To confirm the two numbers are identical, compare the command output.
  13. Connect to the cluster management address with an SFTP application (WinSCP or similar).
  14. Download the core and md5 checksum files from the /var/tmp/ folder.
