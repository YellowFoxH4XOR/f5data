K000161074: VELOS BIG IP Tenant NTP Synchronization Fails on Non Primary Blades

Applies To

• Platform: F5 VELOS

• Product: BIG‑IP Tenant

• Deployment: Multi‑blade tenant deployments

• Modules: Any

• Software Version: All versions supporting VELOS multi‑blade tenants

 

Issue

In a multi‑blade VELOS BIG‑IP tenant deployment, system time may become skewed on non‑primary blades when slot‑specific (cluster member) management IP addresses are not configured.

In this condition, only the primary blade synchronizes successfully with the configured NTP servers. Secondary blades are unable to reach the NTP servers, resulting in time drift and potential blade‑to‑blade synchronization issues.

 

Symptoms

You may observe one or more of the following:

• Incorrect or inconsistent system time across tenant blades

• NTP synchronization succeeds on the primary blade only

• NTP queries from secondary blades fail

• HA instability or configuration synchronization issues

Example error from a secondary blade:

ntpdate: no servers can be used, exiting

 

 

Conditions

This issue occurs when all the following conditions are met:

• BIG‑IP tenant is deployed across multiple VELOS blades

• NTP is configured at the tenant level

• Only a floating (cluster) management IP is assigned

• No per‑blade (cluster member) management IPs are configured

• The management network gateway is reachable only from the primary blade

 

Cause

When per‑blade management (cluster member) IP addresses are not configured within the tenant, only the blade hosting the floating management IP has a routable path to the management gateway.

Secondary blades lack a management‑plane route and are therefore unable to reach the configured NTP servers. Because each tenant blade synchronizes time independently, this results in NTP failures and time drift on non‑primary blades.

 

Resolution

To restore proper NTP synchronization across all blades, configure a unique management IP address for each blade within the tenant.

Procedure

1. Log in to the BIG‑IP tenant.

2. Navigate to:

System ›› Clusters ›› Management IP Address

3. Configure:

    • One floating (cluster) management IP

    • One unique cluster member management IP per blade

4. Ensure each management IP:

    • Is routable

    • Can reach the management gateway

    • Can reach all configured NTP servers

 

Verification

Verify NTP Connectivity

From the tenant shell, test NTP reachability from each blade.

Primary blade example:

[root@labdev001:/S1-green-P::Active:Disconnected] config # ntpdate -q 192.168.1.20

server 192.168.1.20, stratum 2, offset 0.000718, delay 0.05432

 

Secondary blade example:

[root@labdev001:/S1-green-S::Active:Disconnected] config # ssh slot 2

[root@labdev001:/S2-green-S::Active:Disconnected] config # ntpdate -q 192.168.1.20

 

Verify System Time Across All Blades

Run the following command from within the tenant:

for (( x=1; x<=31; x=x+2 )); do ssh slot$x date; done

 

Confirm that all blades report consistent system time.

 

Additional Information

• Missing per‑blade management IP addresses is a common misconfiguration in multi‑blade VELOS tenant environments.

• In addition to NTP issues, this misconfiguration can cause:

    • HA instability

    • Configuration synchronization problems

• System Controller NTP sets time at the hardware level for controllers and blades.

• Tenant‑level NTP operates independently on each blade hosting the tenant and requires a functional cluster member management IP.

Best Practice

For VELOS BIG‑IP tenants deployed across multiple blades, always configure:

• One floating (cluster) management IP

• One unique cluster member management IP per blade

This ensures reliable NTP synchronization, improved resiliency, and stable management‑plane communication.
