K52091701: Handling Connections that have been matched to the wrong Virtual Server

Type
Support Solution
Published
2019-09-26
Updated
2023-02-14
Applies to
  • BIG-IP LTM: 15.X.X
Source
https://my.f5.com/manage/s/article/K52091701

Description
When adding a new virtual server or changing the configuration on a virtual server, traffic may not immediately reflect those changes or match to a new virtual server.

Environment

  • Virtual Server
  • Connection Table
  • Long-lived connections
  • Long TCP or UDP timeout
  • Configuration change
Cause

The Big-IP maintains an existing connection flow until the connection either times out or closes. As long as that connection flow record exists, the system will not re-evaluate which listener should handle this traffic or make new load balancing decisions. New connections that do not match an existing connection table entry should be processed by the current configuration as expected.

Recommended Actions

To force the Big-IP to create new connection table entry, identify the affected connection and delete the existing connections manually from the connection table. 

1. Login to tmsh utility 
2. Run the below command to list the connection table:
tmsh show /sys connection cs-client-addr <client IP address> cs-server-addr <virtual server address> cs-server-port <virtual server port> 
 
For example, the following command deletes all connections from client 10.1.1.20 to virtual server 10.1.1.2:80:
tmsh show /sys connection cs-client-addr 10.1.1.20 cs-server-addr 10.1.1.2 cs-server-port 80
 
3. Delete the connection from the connection table using the below command:
tmsh delete /sys connection cs-client-addr <client IP address> cs-server-addr <virtual server address> cs-server-port <virtual server port>
 
For example, the following command deletes all connections from client 10.1.1.20 to virtual server 10.1.1.2:80:
tmsh delete /sys connection cs-client-addr 10.1.1.20 cs-server-addr 10.1.1.2 cs-server-port 80

Additional Information
 
This behavior is most frequently but not always associated with one of the following circumstances:
  • The idle timeout in the TCP or UDP profile are configured with a long or indefinite timer
  • Traffic on the relevant connection is consistent, preventing the connection from timing out. For example, syslog traffic from a server that frequently generates new log messages
  • A new virtual server is added to handle traffic that already matches a wildcard virtual server

 Traffic using connectionless protocols like UDP can be more prone to this issue, as the connection doesn’t close naturally, and the Big-IP therefore maintains the existing connection table entry until the idle timeout is reached.
