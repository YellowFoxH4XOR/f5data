K000158823: BIG-IQ Autofailover Floating-IP is moving to secondary when Primary device gets rebooted or restarting services

Description

In BIG-IQ clusters configured with Autofailover and Floating-IP, it is observed that after a reboot of the primary node or restart of critical services/daemons, the floating IP may move to the secondary node. This behavior can disrupt access via the floating IP and requires manual intervention to restore expected operation.

 

Symptoms:

  • Using Floating Ip in Browser to access GUI redirects to Secondary read-only unit
  • Primary unit is accessible via mgmt IP GUI without problems

 

Environment

  • BIG-IQ Cluster configured for Autofailover with Floating-IP.
  • Two or more BIG-IQ Central Managers (CM), plus Quorum device.
  • No specific software version dependency.

Cause

The movement of the floating IP from primary to secondary can be triggered by:

  • Rebooting the primary node.
  • Restarting key daemons/services (such as restjavad, webd, pacemaker).
  • Network interruptions causing loss of cluster quorum or responsiveness. If the primary node becomes unavailable for longer than the failover timeout (typically 3 minutes), failover logic promotes the secondary node and moves ownership of resources including floating IP.

 

Recommended Actions

Monitoring & Diagnosis

  1. Monitor Service Uptime: Use system commands (pcs status) on each CM to check which node currently owns the floating IP and resource states.
  2. Review Logs: Check corosync/pacemaker logs for events indicating service restarts, network partitioning, or failover triggers.

Restoring Floating-IP Ownership

To manually move the floating IP back to your desired active CM:

  1. On any CM CLI, run:
    1. pcs resource move FLOATING_IP ha-primary
  1. Verify using:
    1. pcs status
    • Confirm that FLOATING_IP is now assigned to your chosen active CM.
