K000161447: On F5 rSeries appliances breakout interfaces may fail to come up after being enabled

Type
Support Solution
Published
2026-08-16
Updated
2026-08-16
Applies to
  • F5OS Products
  • F5OS-A: 1.8.3, 1.8.0
Source
https://my.f5.com/manage/s/article/K000161447

Description

On F5 rSeries appliances configured with OPT-0036 optics in 4x10G breakout mode, one or more breakout interfaces (e.g., 2.1, 2.2) may fail to come up after being enabled. The affected interface remains in a DOWN state with Tx and Rx disabled, while other interfaces sharing the same QSFP module may come up normally. Reseating the QSFP module temporarily resolves the issue, but it may recur when additional interfaces are enabled.

Relevant log messages observed:

fpgamgr: msg="Updating interface link state" ifname="2.1" state="DOWN"

fpgamgr: msg="Configured Interface MAC." INTERFACE="2.1" Tx="Disabled" Rx="Disabled"

ifMgrVanquish::cable_check(asw, eth25gq5) 2.2 DID:0x21 OK

DDM low alarm set PORTGROUP="2" rxPwr all lanes

Environment

  • Platform: F5 rSeries appliances (r5000/r10000 — Vanquish architecture)
  • F5OS Version: F5OS-A 1.8.0, 1.8.1, 1.8.2, 1.8.3
  • Optic: OPT-0036
  • Port mode: 4x10G breakout (e.g., interfaces 2.1, 2.2, 2.3, 2.4)
  • Condition: Issue occurs when enabling a breakout interface within a portgroup that uses OPT-0036 optics

Cause

Bug ID 2131429: OPT-0036 cable check fails and port stays down.

The cable check logic for OPT-0036 in 4x10G breakout mode uses an eye height threshold comparison. When the measured eye height falls below the threshold, the cable check fails and the port does not come up. Reseating the QSFP triggers a fresh optic insertion and re-initialization cycle, which may allow the eye height measurement to meet the threshold, temporarily resolving the issue.

Answer/Recommended Actions

Permanent Fix:

  • Upgrade F5OS-A to a version where Bug ID 2131429 is resolved.

Temporary Workaround (if upgrade is not immediately possible):

If an interface fails to come up after being enabled in 4x10G breakout mode with OPT-0036 optics, perform the following steps:

  1. Verify the interface is in a DOWN state and confirm Tx/Rx are disabled in the logs.
  2. Physically reseat the QSFP module in the affected portgroup.
  3. Wait for the optic insertion event to be logged:

    fpgamgr: msg="Optic inserted" Portgroup="X"

  4. Verify that the affected interfaces return to UP state:

    fpgamgr: msg="Updating interface link state" ifname="X.X" state="UP"

  5. Confirm all breakout interfaces in the portgroup have rejoined the LAG (if applicable).

Recommended Debug Data Collection (before reseating, if time permits):

  1. Enable fpgamgr debug logging from the F5OS management CLI:
    config
    system logging sw-components sw-component fpgamgr config severity DEBUG
    commit and-quit
  2. Note the exact timestamp of each activity performed.
  3. Collect a qkview and upload it to the support case.
  4. Debug logs will appear in /var/F5/system/log/platform.log.

Additional Information

  • Other interfaces sharing the same QSFP module (e.g., 2.3, 2.4) may come up normally even when 2.1 or 2.2 do not. This is expected behavior given the nature of the cable check failure, which can affect individual lanes differently.
  • Bug ID 1601253 (Few of the bifurcated ports not coming UP after inserting the optics, additional reboot required to make all ports UP) is a related issue involving similar breakout port initialization failures on rSeries platforms.
  • The issue is specific to the OPT-0036 optic in 4x10G breakout mode. Other optic types or port modes may not be affected.
