Description

SSLO service connections fail when return traffic from an in-line Layer 3 security service arrives on a different VLAN than expected in environments with asymmetric routing. The issue symptom as:

  • TCP handshake fail when SSLO receive the SYN from L3 inline service. SSLO receive the SYN from L3 inline service, did not reply the SYN ACK.
  • Check the F5 Ethernet trailer of the SYN (received from the L3 inline service), the VS name should be empty, but show the VS name is the client side Virtual Server name.

Environment

  • Product: BIG-IP SSLO
  • Version: 17.x (issue may affect other versions)
  • SSLO topology
  • L3 Inline Service
  • Asymmetric routing, sys db connection.vlankeyed is disable

Cause

When connection.vlankeyed is disabled to support asymmetric routing, the BIG-IP system relaxes VLAN-based connection matching. In this configuration, L3 Inline Service device send SYN packet, arriving on a different VLAN may incorrectly match an unintended virtual server instead of the SSLO from service virtual server.

Recommended Actions

To resolve SSLO service connection failures in asymmetric routing environments:

  • Primary Solution: If possible, follow K13558: Allowing asymmetrically routed connections across multiple VLANs (11.x - 17.x), enable the sys db connection.vlankeyed, and using a custom FastL4 profile with Loose Initiation and Loose Close to support asymmetrically routing.
  • Alternative Solution: Modify SSLO Service Virtual Server Source Port Setting

Identify the SSLO service virtual server (e.g., ssloS_<service_name>-t-4 and ssloS_<service_name>-u-4)

Change the source port setting from "preserve" to "change" via tmsh:

tmsh

modify ltm virtual /Common/ssloS_<L3 Service name>.app/ssloS_<L3 Service name>-t-4 source-port change

modify ltm virtual /Common/ssloS_<L3 Service name>.app/ssloS_<L3 Service name>-u-4 source-port change

save sys config

Important: This configuration change will be lost when you redeploy the SSLO topology or service, or when you upgrade BIG-IP SSLO. Document this workaround and reapply it after any SSLO redeployment or upgrade.

Additional Information

  • Impact of source port change: The in-line security service will see a different source port for connections. This typically does not affect security service operation, but should be verified in your specific environment. If concurrent connection count from same client IP is very high, it may cause connection fail.
  • Expected behavior: The behavior described is expected when connection.vlankeyed is disabled and asymmetric routing is present. The workaround addresses the specific interaction between SSLO service chaining and asymmetric routing.
