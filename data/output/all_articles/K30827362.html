Description

Connections experience packet loss when BIG-IP OneConnect is used in conjunction with an Azure Load Balancer.

Environment

  • BIG-IP virtual server is configured with OneConnect
  • The server-side/downstream connection goes through an Azure Load Balancer
  • The Azure Load Balancer has the idle timeout configured. (Default is 4 minutes -https://azure.microsoft.com/en-us/blog/new-configurable-idle-timeout-for-azure-load-balancer/)
  • The Azure Load Balancer does not have TCP RST configured.This is default. (https://docs.microsoft.com/en-us/azure/load-balancer/load-balancer-tcp-reset)

Cause

Azure Load Balancer can silently drop packets from the BIG-IP when OneConnect is used.

This can happen because by default Azure load balancer does not send TCP RST when it considers a TCP connection idle
The Big-IP therefore never receives a TCP RST so OneConnect thinks the TCP connection is still active and idle
OneConnect feature is designed to re-use idle TCP connections and the Big-IP tries to send packets through that TCP connection.
However for the Azure Load Balancer, that TCP connection is closed and it silently drops the packets.

Recommended Actions

You can mitigate this behavior using either of the following methods:
  • Remove OneConnect from the BIG-IP virtual server
    • When OneConnect is removed from the virtual server then there is no further packet loss.
  • Work with Microsoft to configure TCP RST on the Azure Load Balancer.
