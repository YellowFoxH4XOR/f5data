Description

  • When a server-side TCP connection enters a zero-window state, the connection stalls and never recovers despite data being received and acknowledged on the client-side
  • Packet captures taken on the BIG-IP, shows  that the BIG-IP sending zero window packets to the server
3520 102.397382 5.021169 4094 192.168.1.1 → 192.168.1.2  407 80 1234 TCP IN  s1/tmm6 : [TCP Window Full] 80 → 1234 [ACK] Seq=170334 Ack=13035 Win=2101248 Len=367 [TCP segment of a reassembled PDU]
3523 102.497323 0.099941 4094 192.168.1.2 → 192.168.1.1  40 1234 80 TCP OUT s1/tmm6 : [TCP ZeroWindow] 1234 → 80 [ACK] Seq=13035 Ack=170701 Win=0 Len=0
3524 102.753052 0.255729 4094 192.168.1.1 → 192.168.1.2  41 80 1234 TCP IN  s1/tmm6 : [TCP ZeroWindowProbe] 80 → 1234 [ACK] Seq=170701 Ack=13035 Win=2101248 Len=1 [TCP segment of a reassembled PDU]
3525 102.753079 0.000027 4094 192.168.1.2 → 192.168.1.1  40 1234 80 TCP OUT s1/tmm6 : [TCP ZeroWindowProbeAck] [TCP ZeroWindow] 1234 → 80 [ACK] Seq=13035 Ack=170701 Win=0 Len=0

Environment

  • BIG-IP TMOS 16.x
  • BIG-IP Virtual Server
  • One-connect profile

Cause

  • Bug ID 1020549
  • One-connect profile detaches server side connection for re-use
  • TCP flow control may be enabled by TCP proxy on the re-used server side flow causing the connection to remain in the zero-window state

Recommended Actions

  1. Avoid using one-connect profile on 16.0.x
  2. Upgrade to 16.1.2.2, which has a fix for ID1020549
