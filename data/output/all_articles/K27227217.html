Description

Monitor status 'down' messages log a "last error" reason that would actually mark the pool member "up", not "down".

The following Monitor:

ltm monitor http http_example {
    defaults-from http
    recv "HTTP/1.[01] ([23]0[0-8])"
    send "GET http://www.example.com/ HTTP/1.1\r\nPragma: no-cache\r\nConnection: Close\r\n\r\n"
}

May result in the following log message:

example.com notice mcpd[6338]: 01070638:5: Pool /Common/pool_example member /Common/192.0.2.10:80 monitor status down. [ /Common/http_example: down; last error: /Common/http_example: Response Code: 301 (Moved Permanently) @2020/08/26 10:21:05. ] [ was up for 0hr:2mins:2sec ]
Note: 301 response code is in fact valid with the above configuration.

Environment

  • BIG-IP LTM
  • http or https monitor

Cause
Bug ID 874877

Recommended Actions

None.

Additional Information

When monitor status changes (e.g., uncheck->up), the response code on that monitor response is stored to LAST_FAIL_REASON.
And then, assume that there is no more monitor status change happens for a while.
Without monitor status change, LAST_FAIL_REASON is never updated.
And then, assume that monitor server stops responding to monitor probes.
After predefined retries, bigd marks the pool member as down, and at that time, LAST_FAIL_REASON is populated on the log.

Further, here is an example of how this failure can be observed:

  1. Following monitor object is associated with pool. Monitor tries to get "/monitor_example.php" and expects string "myubuntuserver" (which could be seen in Host header, on my example).

    tmsh list ltm monitor http http_example_monitor send recv

    ltm monitor http http_example_monitor {
        adaptive disabled
        recv ubuntumyserver
        send "GET /monitor_example.php HTTP/1.0\r\n\r\n"
    }

    Note: What is monitor_example.php? It's here. No HTML content, just simply replies HTTP response code and Host header.

    cat monitor_example.php

    <?php
      header("HTTP/1.1 503 ERROR");
      header('Host: ubuntumyserver');
    ?>

  2. When I first time attach http_example_monitor to pool, monitor_instance table becomes as follows. Monitor status expectedly changes from "uncheck" to "up". And at that time, HTTP response code 503 is internally stored.
    Note: You may feel 503 is not right code, yes, but it's just a part of this example.

    ltm log

    example notice mcpd[6113]: 01070638:5: Pool /Common/monitor_pool member /Common/10.1.1.70:80 monitor status unchecked. [  ]  [ was up for 0hr:3mins:10sec ]
    example notice mcpd[6113]: 01070727:5: Pool /Common/monitor_pool member /Common/10.1.1.70:80 monitor status up. [ /Common/http_example_monitor: up ]  [ was unchecked for 0hr:0min:11sec ]

    guishell -c "select MON_NAME,LAST_FAIL_REASON,TIME_STAMP from monitor_instance where MON_NAME='/Common/http_example_monitor'"

    |----------------------------------------------------------------------------------|
    |            MON_NAME |            LAST_FAIL_REASON |          TIME_STAMP          |
    |----------------------------------------------------------------------------------|
    | /Common/http_example_monitor |  Response Code: 503 (ERROR) | 2018-01-22 10:22:08 |
    |----------------------------------------------------------------------------------|

  3. Next, change monitor response contents. Specifically, just changes "503 ERROR" to "200 OK". Please note at this time "Host: ubuntumyserver" part is still maintained (and therefore, monitor down never happens).

    sed -i -e 's/503 ERROR/200 OK/g' monitor_example.php
    cat monitor_example.php

    <?php
      header("HTTP/1.1 200 OK");
      header('Host: ubuntumyserver');
    ?>

  4. Wait for a while (until next time monitor fires), and you will see that pmbr changes response from "503" to "200 OK" expectedly. But please note that there is no "monitor down" happens.

    14 2018-01-22 10:26:08.647057    10.1.1.82 → 10.1.1.70    HTTP 95 GET /monitor_example.php HTTP/1.0
    15 2018-01-22 10:26:08.667808    10.1.1.70 → 10.1.1.82    TCP 66 80 → 1805 [ACK] Seq=1 Ack=30 Win=29056 Len=0 TSval=1357229951 TSecr=460913158
    16 2018-01-22 10:26:08.668444    10.1.1.70 → 10.1.1.82    TCP 234 [TCP segment of a reassembled PDU]
    17 2018-01-22 10:26:08.668451    10.1.1.70 → 10.1.1.82    HTTP 66 HTTP/1.1 200 OK
    Important: Even though bigd receives different monitor response code, mcpd does not change LAST_FAIL_REASON since no monitor status change happens.

    date ; guishell -c "select MON_NAME,LAST_FAIL_REASON,TIME_STAMP from monitor_instance where MON_NAME='/Common/http_example_monitor'"

    |----------------------------------------------------------------------------------|
    |            MON_NAME |            LAST_FAIL_REASON |          TIME_STAMP          |
    |----------------------------------------------------------------------------------|
    | /Common/http_example_monitor |  Response Code: 503 (ERROR) | 2018-01-22 10:22:08 |
    |----------------------------------------------------------------------------------|

  5. And then, stop httpd server. And BIG-IP correctly marks pmbr as montior down. Here is monitor down log. You can see that "Response Code: 503 (ERROR)" is there.

    example notice mcpd[6113]: 01070638:5: Pool /Common/monitor_pool member /Common/10.1.1.70:80 monitor status down. [ /Common/http_example_monitor: down; last error: /Common/http_example_monitor:  Response Code: 503 (ERROR) @2018/01/22 10:31:39.  ]  [ was up for 0hr:9mins:31sec ]

  6. Looking at LAST_FAIL_REASON, string changes from "Response Code: 503 (ERROR)" to "No successful responses received before deadline.".

    date ; guishell -c "select MON_NAME,LAST_FAIL_REASON,TIME_STAMP from monitor_instance where MON_NAME='/Common/http_example_monitor'"

    |--------------------------------------------------------------------------------------------------------|
    |                     MON_NAME |                                  LAST_FAIL_REASON |          TIME_STAMP |
    |--------------------------------------------------------------------------------------------------------|
    | /Common/http_example_monitor | No successful responses received before deadline. | 2018-01-22 10:31:39 |
    |--------------------------------------------------------------------------------------------------------|

  7. After httpd server gets back online, LAST_FAIL_REASON is updated with (latest) response code string "200 OK".

    date ; guishell -c "select MON_NAME,LAST_FAIL_REASON,TIME_STAMP from monitor_instance where MON_NAME='/Common/http_example_monitor'"

    |-------------------------------------------------------------------------------|
    |                     MON_NAME |         LAST_FAIL_REASON |          TIME_STAMP |
    |-------------------------------------------------------------------------------|
    | /Common/http_example_monitor |  Response Code: 200 (OK) | 2018-01-22 10:33:49 |
    |-------------------------------------------------------------------------------|
