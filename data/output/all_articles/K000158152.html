Description

This article addresses an issue on F5OS-Appliance platforms where the directory /var/export/chassis/IMAGES does not exist, resulting in tenant deployment failures. Symptoms include tenants remaining in a "pending" state with the message "insufficient memory on node, retrying tenant deployment." System logs may show repeated timeouts and dependency failures related to dev-partition_image-export_chassis.device and var-export-chassis.mount. The issue is associated with Bug ID 1388921.

Example error/log messages:

Job dev-partition_image-export_chassis.device/start timed out.

Timed out waiting for device dev-partition_image-export_chassis.device.

Job var-export-chassis.mount/start failed with result 'dependency'.

Tenant status: "pending" and "insufficient memory on node, retrying tenant deployment"

Environment

  • Product: F5OS - Appliance
  • Product Group: BIG-IP
  • Version: 1.8.0 (F5OS-A)
  • Platforms: F5-BIG-LTM-R2600, C130
  • Tenant image: BIG-IP 15.x (Note: v15.x is not supported on F5OS-Appliance; v17.x is recommended))
  • Symptoms observed after tenant deployment attempts
  • Systemctl and platform logs show device and mount failures for partition_image and VDO volumes

Cause

Bug ID 1388921

Recommended Actions

Important: Ensure you have backups of all important data (UCS, system backup files, etc.) before proceeding.
This workaround is intended for systems where:
- mount | grep partition_image returns no output
- vdo list returns no output

 

  1. Backup Data
    - Backup contents of relevant directories (such as ISO files and images) to a safe location.
    - Use rsync or cp to copy files from /var/export/chassis/IMAGES and related directories.
  2. Stop Services
    - Stop software management service:
    systemctl stop sw-mgmt
  3. Remove VDO and Create LVM Volume
    - Identify the device used for partition_image volume (e.g., /dev/sdX).)))
    - Wipe the device:

    wipefs -aq)

    - Create a new physical volume and volume group:

    pvcreate
    <sCRub_LINUXPATH_qsfyvdxuuV1>
    vgcreate partition_image
    <sCRub_LINUXPATH_qsfyvdxuuV1>

    - Determine total physical extents:

    TSZ=$(vgdisplay partition_image | awk '/Total PE/{print $NF}')

    - Create logical volume:

    lvcreate partition_image -n export_chassis -l $((TSZ))

    - Format new logical volume:

    mkfs -t ext4 -E nodiscard

  4. Restore Data
    - Mount new logical volume to appropriate mount point.
    - Restore previously backed-up files using rsync or cp.
  5. Finalise
    - Unmount the volume and remove any temporary directories used during restore.
    - Reboot system:
    reboot
    - Wait 10–20 minutes for system to become active.
  6. Post-Recovery
    - After recovery, ensure only supported tenant versions (e.g., BIG-IP v17.x) are deployed.

Additional Information

  • The workaround script does not destroy the entire disk; it specifically targets the partition_image volume.
  • The process replaces a VDO-based logical volume with a plain LVM volume to resolve mounting/dependency issues.
  • Always ensure backups are taken before performing disk operations.
  • Running unsupported tenant versions (such as BIG-IP v15.x) on F5OS-Appliance is not recommended.
