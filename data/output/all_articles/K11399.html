Known Issue

This is the result of a known issue. The BIG-IP LTM system does not consistently calculate persistence record ages between TMM instances on CMP-compatible systems.

Starting in BIG-IP version 9.6, persistence record timer behavior was changed to better accommodate CMP-based systems. As a result, when a corresponding connection and persistence record are owned by the same TMM instance, the persistence timer begins counting after the connection has closed. If no further connections are initiated for the session, the persistence record expires within the expected timeout value. However, when a corresponding connection and persistence record are owned by different TMM instances, the TMM that owns the connection sends a connection status update to the remote TMM instance only twice for every persistence timeout cycle. As a result, it is possible for the connection to close and for a delay of half the persistence timer value to occur before the persistence timer begins counting. This issue can effectively increase the persistence record timeout for a connection by one half of the timeout period.

For example, if the persistence timeout value is 90 seconds, and a persistent connection is distributed to TMM0 but TMM1 owns the persistence record, TMM0 will send a connection status update to the TMM1 instance every 45 seconds. This can potentially result in a 45 second delay between the time the connection closes and when TMM0 notifies TMM1 that the connection has closed.

Note: For more information about persistence record timers in BIG-IP versions 9.x and 10.x, refer to K11109: Changes to persistence record timers in BIG-IP versions 9.x and 10.x.

F5 Product Development tracked this issue as CR127318, and it was fixed in BIG-IP version 10.1.0. For information about upgrading, refer to the BIG-IP LTM release notes.

Additionally, this issue was fixed in Hotfix-BIGIP-10.0.1-402.7-HF4 issued for BIG-IP version 10.0.1. You may download this hotfix or later versions of the hotfix from the F5 Downloads site.
