Description

This article provides an overview of how to restore normal operation of BIG-IP HA cluster in MS Azure in case if one cluster member failed (VM failure).

Environment
  • BIG-IP VM(s) running in MS Azure
  • BIG-IP systems are members of a sync-failover device group
  • BIG-IP HA cluster in MS Azure was deployed from the following ARM template: https://github.com/F5Networks/f5-azure-arm-templates/tree/master/supported/failover/same-net/via-api/n-nic/existing-stack/byol
  • One BIG-IP VM which is a member of HA cluster failed (this can be VM failure for instance) and you need to restore failed VM and bring HA cluster back to working condition
Cause

VM failure due to hypervisor issues, hardware failures, etc.

Recommended Actions

 Two failure scenarios are reviewed in this article: 

  • Active BIG-IP VM fails (hostname f5010)
  • Standby BIG-IP VM fails (hostname f5011)

Use the following procedure to restore Standby BIG-IP VM (f5011) in HA cluster:

  1. Shut down failed BIG-IP VE (f5011) if it's still running.
  2. Remove Standby BIG-IP VE (f5011) and OS disk from Azure portal.
  3. Set remaining BIG-IP VM (f5010) to standalone. Remove failed device from “Sync” device group and reset device trust:
        - tmsh modify cm device-group Sync devices delete { f5011.uksouth.example.com }
        - tmsh delete cm trust-domain all
  4. If using via-api template version 7.4.0.0 and later. Remove any orphaned (Type: Unknown) role assignments from resource group IAM in Azure portal:
        - Click Resource Group > Access Control (IAM) > Role Assignments
        - Under “Scope”, select “This resource”
        - Select any Identity of Type: Unknown and click “Remove”
  5. Reset F5 license key for failed device (f5011) or use a new license key.
  6. Redeploy via-api template using same inputs as in original template but use different deployment name.

The result is two clustered devices with all requirements and configuration synchronized from the original device (f5010).

Use the following procedure to restore Active BIG-IP VM (f5010) in HA cluster:

  1. Shut down failed BIG-IP VE (f5010) if it's still running.
  2. Remove Active BIG-IP VE (f5010) and OS disk from Azure portal.
  3. Set remaining BIG-IP to standalone: Remove failed device from Sync device group and reset device trust:
        - tmsh modify cm device-group Sync devices delete { f5010.uksouth.example.com }
        - tmsh delete cm trust-domain all
  4. Remove any secondary IP configurations from the remaining BIG-IP NICs (f5011). Please note that this step will cause service outage until all the remaining steps are completed:
        - Go to https://resources.azure.com
        - Expand Subscriptions > <your_subscription_ID> > Resource Groups > <your_resource_group_name> > providers > Microsoft.Network > networkInterfaces.
        - Click on the external network interface for the original BIG-IP (it will end in "-ext1").
        - Click the “Read/Write” button.
        - Click the “Edit” button.
        - Under ipConfigurations, select all the secondary IP configuration(s); these will have the "primary: false" property.
        - Delete the selected configuration(s) and click the "PUT" button.
        - Wait until the network interface is finished updating.
  5. If using via-api template version 7.4.0.0 and later: Remove any orphaned (Type: Unknown) role assignments from resource group IAM
        - Click Resource Group > Access Control (IAM) > Role Assignments
        - Under "Scope", select "This resource"
        - Select any Identity of Type: Unknown and click "Remove"
  6. Reset F5 license key for failed device (f5010) or use a new license key.
  7. Redeploy via-api template using same inputs as in original template (before VM failure) but use different deployment name. Once template deployment is completed, both BIG-IP units end up in standalone mode. Secondary IP configuration(s) will be created on ext0 interface.
  8. Set up DSC:
        On existing BIG-IP (f5011):
        - tmsh create auth user <username> password <password> partition-access add {all-partitions { role admin } }    
  9.     On recovered BIG-IP (f5010). In the below tmsh commands use the device-ip, device-name, device-group-name from the non-failed instance (f5011):
        - tmsh modify cm trust-domain /Common/Root add-device { device-ip <config_sync_ip> device-name f5011.uksouth.example.com username <username> password <password> ca-device true }
        - tmsh modify cm device-group Sync devices add { f5011.uksouth.example.com }
        On existing BIG-IP (f5011):
        - tmsh run cm config-sync to-group Sync

The result is two clustered devices with all requirements and configuration synchronized from the original device (f5011).

In the above tmsh commands, note the following:

  • <username> is BIG-IP username
  • <password> is BIG-IP password
  • <config_sync_ip> is BIG-IP config-sync IP address
