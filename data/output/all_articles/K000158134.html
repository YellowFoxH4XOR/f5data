Description

Pool members configured with HTTP/HTTPS health monitors are unexpectedly marked down or are not being marked down when it should be.

Some issues and/ or questions you may encounter:

  • Manual connectivity tests (such as curl) to the same pool members may succeed and return HTTP 200 OK.
  • The pool members remain available when monitored via TCP.
  • Packet captures show that, during failed HTTP/HTTPS health checks, the pool member completes TCP and SSL/TLS (when the HTTPS monitor is used) handshakes.
  •  It may or may not respond with application data after the monitor's Send String is sent, resulting in the monitor marking the member as unavailable.

Environment

  • Default and custom HTTP/HTTPS monitors in use.

Cause

There are a number of situations that can bring about a monitor response, or lack thereof, due to improper or missing configuration of HTTP/HTTPS health monitors:

  • The absence of the Receive String. Without a valid Receive String, the monitor accepts any response. 
  • Configuration of the Send String does not elicit the proper response from the pool member
  • The Receive String presented by the pool member does not match what is configured in the monitor.
  • The pool member fails to respond to the Application Data Packet.
  • Using the default Http or Https monitors.

Note: There are often misconceptions about F5 monitors. A monitor is a very black and white thing. It sends out a packet (that packet type will be based upon the type of monitor) and if it does not receive the response it expects or maybe none at all it marks the pool member down. It does not mean the F5 is taking it offline it means the pool member is either offline, there is a network issue, or the pool member is not responding appropriately. By saying it is 'down' the BIG-IP is indicating the pool member is unavailable for traffic.

Recommended Actions

The purpose of an HTTP or HTTPS monitor is to check the status of an application to determine whether it is capable of receiving data. HTTP.HTTPS monitors are not a connectivity check. Connectivity would have to be already have been established via the TCP 3 Way Handshake (3WHS) and if required a SSL/TLS Handshake in order for data to be passed.

If you are having an issue where a pool member is being marked as unavailable or should be marked as unavailable:

1) The first check would be review and update HTTP or HTTPS monitor configurations to ensure both Send and Receive Strings are properly set to match expected application responses.

  1. In most cases the best way to determine what should be used for the Send and Receive String is to discuss this with whomever administers the application. They can usually provide you with what is needed to properly elicit the status of the application.
  2. The most common reason it is not marked as unavailable when it should be is due the Receive string being set as a 200. OK, or a 200 OK. This may not actually indicate the true status of the application.
  3. This may be simple syntax issue or you may need to configure a specific string to be used.
    • K2167: Constructing HTTP requests for use with the HTTP or HTTPS application health monitor
    • K5917: Using regular expressions in a health monitor receive string

2) Testing the Send and Receive Strings can be done to ensure the syntax is working as desired. The steps to do so can be found in the following articles:

    • K81239024: Testing HTTP/HTTPS Monitor Send String using openssl s_client and netcat (nc)
    • K16165: Testing an HTTPS monitor with user authentication from the command line (11.x - 15.x)

3) A very common issue is the use of the default http or https monitor. Neither of these have a Receive String.

  1. When either of the default monitors are used the only way the monitor would mark the application as 'unavailable' is if there was no response at all at some point in the monitor check.
    1. Without a Receive String the BIG-IP has no way to know what a proper Layer 7 response is and thus will assume that any Layer 7 response is valid and mark the pool member as available.
    2. The monitor must have both a proper Send and Receive string in order for it to determine the proper status of the application.
  2. To correct this creating a custom HTTP or HTTPS monitor with the proper Send and Receive String is needed. With that in place the BIG-IP can then properly ascertain if the application is available or not.

    • HTTPS monitor settings

4) If the configuration is correct then there are a couple of things that can be done to check the communication between the monitor and the pool member for the monitor flow:

  1. Monitor Logging
    1. Monitor traffic cannot be decrypted via a packet capture. So in order to see what the response is from the pool member, when using an HTTPS monitor, a look at what the BIG-IP sees once it has decrypted the packet may need to be done. To do that you would enable monitor logging. This is done for each pool member you want to investigate. This can be done at either the node or pool member level. To setup monitor logging...
      1. K000150659: Enable monitor logging for a pool member on the BIG-IP system
      2.  K000150661: Enable monitor logging for a node on the BIG-IP system
        1. This type of logging can be very verbose and should only be used during troubleshooting long enough to catch the response and then disabled.
    2. It is very important to note here that Monitor Logging will not work on FQDN pool members. The BIG-IP device does not allow modifications made to the individual FQDN ephemeral pool member, you can only make changes to the parent FQDN pool member. If you attempt to modify the individual FQDN ephemeral pool member, the BIG-IP device does not allow the modification and reports an error similar to the following example: 
      01071c39:3: Modify of ephemeral pool member (pool /Common/pool-test-autodns member /Common/192.168.40.131) is not permitted.

4) "But the pool member is available when a TCP monitor is used".

  1. This goes back to the issue of what the HTTP/HTTPS monitor is checking.
    1. A TCP monitor is a connectivity check that occurs before any data is exchanged. The HTTP/HTTPS monitor is a check for the ability to exchange data after the connectivity has been established. So it may very well pass the connectivity check while failing the data exchange check that occurs later in the stream.
