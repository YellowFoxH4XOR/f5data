Description

This article describes two custom AMI-generation methods for BIG-IP Virtual Edition (VE) outside the AWS Marketplace, selected by which release artifact is available:

Method A - VMDK Import (Engineering Hotfixes / EHF builds): EHFs are delivered as BIGIP-<version>-<build>.ALL-AWS.zip, which contains a -disk1.vmdk file. Import this VMDK as an EBS snapshot and register it as an AMI.

Method B - RAW Import (GA / Point Releases): GA and point releases are delivered as AWS-F5_Networks-<version>-<build>-<license>-<modules>-<bootloc>.tar.gz, which contains a single .raw disk image. Import this RAW disk image directly as an EBS snapshot and register it as an AMI.

Do not substitute a generic BIGIP-*.ALL-vmware.ova (VMware-platform) image for either method. The VMware OVA does not contain the AWS platform packages (amazon-ec2-api-tools, f5-cloud-lib) required for cloud-init/AWS first-boot setup to run. An AMI built from that artifact will boot, but the AWS platform marker will be recorded incorrectly, cloud-init will fall back to a ConfigDrive datasource that does not exist on EC2, and cloud-init will never run, resulting in no SSH key injection and no first-boot AWS onboarding.

Environment

  • BIG-IP VE image formatted as VMDK (EHF/custom builds) or as a single RAW disk image (GA/point release AWS artifact)
  • AWS (CLI, IAM, S3, EC2, and AMI)

Cause

VMDK path: Running aws ec2 import-image directly against a VMDK returns "Unsupported: Incomplete root disk: Missing kernel configuration file." The import-snapshot + register-image sequence below avoids this.

RAW path: GA/point-release artifacts are not delivered as VMDK; they contain a single .raw disk image that must be imported with Format=RAW, not Format=VMDK.

Wrong source artifact: If a generic VMware OVA is used as the import source (instead of the AWS-specific VMDK or RAW artifact), the resulting AMI will boot but cloud-init will not run: first-boot setup records the platform marker as HYPERVISOR=0 rather than HYPERVISOR=aws, and cloudinit-prepare then falls back to a ConfigDrive datasource that does not exist on EC2.

Answer/Recommended Actions

METHOD A - VMDK IMPORT (use for Engineering Hotfixes / EHF builds)

Use this when your artifact is BIGIP-<version>-<build>.ALL-AWS.zip (contains -disk1.vmdk).

1. On Bash CLI where you will be running AWS CLI commands (eg. AWS CloudShell), setup the environment variables.

REGION=<aws-region>
BUCKET_NAME=vmdk-import-bucket
VMDK_FILENAME=BIGIP-<version>-<build>-disk1.vmdk
IMAGE_PATH=/tmp/
BIGIP_AMI_NAME=BIGIP-<version>-<build>
EC2_KEY_NAME=your-ssh-key-name
INSTANCE_TYPE=m5.xlarge
SUBNET_ID=subnet-nnnnnnnnnnnnnnnnn
SECURITY_GROUP_ID=sg-mmmmmmmmmmmmmmmmm

2. Create an S3 bucket.

aws s3 mb s3://${BUCKET_NAME} --region ${REGION}

3. Configure IAM Role and Permissions.

3.1. Create a trust policy file.

cat > /tmp/trust-policy.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "vmie.amazonaws.com" },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:Externalid": "vmimport" } }
    }
  ]
}
EOF

3.2. Create required IAM role (vmimport) and attach the trust policy.

aws iam create-role --role-name vmimport --assume-role-policy-document file:///tmp/trust-policy.json

3.3. Create a role policy file to grant access to S3 bucket.

cat << EOF > /tmp/vmimport-s3-policy.json
{
  "Version": "2012-10-17",
  "Statement": [
      {
        "Effect": "Allow",
        "Action": [
            "s3:GetBucketLocation",
            "s3:GetObject",
            "s3:ListBucket"
        ],
        "Resource": [
            "arn:aws:s3:::${BUCKET_NAME}",
            "arn:aws:s3:::${BUCKET_NAME}/*"
        ]
      },
      {
        "Effect": "Allow",
        "Action": [
            "ec2:ModifySnapshotAttribute",
            "ec2:CopySnapshot",
            "ec2:RegisterImage",
            "ec2:Describe*"
        ],
        "Resource": "*"
      }
  ]
}
EOF

3.4. Attach the role policy to the role.

aws iam put-role-policy --role-name vmimport --policy-name vmimport-s3-access --policy-document file:///tmp/vmimport-s3-policy.json

4. Upload VMDK file into the S3 bucket.

aws s3 cp ${IMAGE_PATH}/${VMDK_FILENAME} s3://${BUCKET_NAME}/ --region ${REGION}

5. Import the VMDK image file as a snapshot. Note the ImportTaskId value.

IMPORT_TASK_ID=$(aws ec2 import-snapshot \
  --description "BIG snapshot import" \
  --disk-container "Format=VMDK,Description=BIGIP-17.5.1.6,UserBucket={S3Bucket=${BUCKET_NAME},S3Key=${VMDK_FILENAME}}" \
  --region ${REGION} \
  --query 'ImportTaskId' \
  --output text)

6. Monitor the progress of the snapshot import task.

aws ec2 describe-import-snapshot-tasks \
--import-task-ids ${IMPORT_TASK_ID} \
--region ${REGION} \
--query 'ImportSnapshotTasks[0].SnapshotTaskDetail.[Status,StatusMessage,Progress]' \
--output table

Once the task has been completed, get the Snapshot ID.

SNAPSHOT_ID=$(aws ec2 describe-import-snapshot-tasks \
--import-task-ids ${IMPORT_TASK_ID} \
--region ${REGION} \
--query 'ImportSnapshotTasks[0].SnapshotTaskDetail.SnapshotId' \
--output text)

7. Register the Snapshot as an AMI. F5 recommends using /dev/xvda as the root device name.

AMI_ID=$(aws ec2 register-image \
  --name ${BIGIP_AMI_NAME} \
  --description ${BIGIP_AMI_NAME} \
  --architecture x86_64 \
  --root-device-name "/dev/xvda" \
  --virtualization-type hvm \
  --ena-support \
  --sriov-net-support simple \
  --block-device-mappings "[{\"DeviceName\":\"/dev/xvda\",\"Ebs\":{\"SnapshotId\":\"${SNAPSHOT_ID}\",\"VolumeType\":\"gp3\",\"VolumeSize\":108,\"DeleteOnTermination\":true}}]" \
  --region ${REGION} \
  --query 'ImageId' \
  --output text)

8. You may then launch an EC2 instance using the AMI ID.

aws ec2 run-instances \
  --image-id ${AMI_ID} \
  --instance-type ${INSTANCE_TYPE} \
  --key-name ${EC2_KEY_NAME} \
  --subnet-id ${SUBNET_ID} \
  --security-group-ids ${SECURITY_GROUP_ID} \
  --region ${REGION} \
  --query 'Instances[0].InstanceId' \
  --output text

 

METHOD B - RAW IMPORT (use for GA / Point Releases)

Use this when your artifact is AWS-F5_Networks-<version>-<build>-<license>-<modules>-<bootloc>.tar.gz (contains a single .raw disk image). Download from my.f5.com/manage/s/downloads (container: AWS-Cloud).

1. On Bash CLI where you will be running AWS CLI commands (eg. AWS CloudShell), setup the environment variables.

REGION=<aws-region>
BUCKET_NAME=raw-import-bucket
TARBALL=AWS-F5_Networks-<version>-<build>-<license>-<modules>-<bootloc>.tar.gz
IMAGE_PATH=/tmp/
BIGIP_AMI_NAME=BIGIP-<version>-<build>
EC2_KEY_NAME=your-ssh-key-name
INSTANCE_TYPE=m5.xlarge
SUBNET_ID=subnet-nnnnnnnnnnnnnnnnn
SECURITY_GROUP_ID=sg-mmmmmmmmmmmmmmmmm

2. Inspect the archive to identify the RAW filename it contains, then extract it.

tar tzvf ${IMAGE_PATH}/${TARBALL}
-> F5_Networks-BIGIP-<version>-<build>-<license>-<modules>-<bootloc>-<buildid>-<timestamp>.raw

(exact filename varies by version/build/modules/boot-location selected at download; identify it from the tar listing output)

tar xzf ${IMAGE_PATH}/${TARBALL}

RAW_FILENAME=<raw filename identified above>

3. Create an S3 bucket and upload the RAW file.

aws s3 mb s3://${BUCKET_NAME} --region ${REGION}
aws s3 cp ${IMAGE_PATH}/${RAW_FILENAME} s3://${BUCKET_NAME}/ --region ${REGION}

Tip: For very large RAW files (eg. All-Modules/multi-boot-location images can be tens of GB), you can stream the extraction directly to S3 instead of extracting to local disk first. This avoids needing local disk space equal to the full uncompressed image size. Verify current AWS import-snapshot size limits in AWS's own documentation before relying on this for very large images.

tar -xzOf ${IMAGE_PATH}/${TARBALL} "${RAW_FILENAME}" \
| dd status=progress bs=64M \
| tee >(sha256sum > local-upload.sha256) \
| aws s3 cp - "s3://${BUCKET_NAME}/${RAW_FILENAME}"

4. Import the RAW disk image as a snapshot. Note: use Format=RAW, not Format=VMDK. Note the ImportTaskId value.

IMPORT_TASK_ID=$(aws ec2 import-snapshot \
  --description "BIG-IP RAW import" \
  --disk-container "Format=RAW,Description=${BIGIP_AMI_NAME},UserBucket={S3Bucket=${BUCKET_NAME},S3Key=${RAW_FILENAME}}" \
  --region ${REGION} \
  --query 'ImportTaskId' \
  --output text)

5. Monitor the progress of the snapshot import task.

aws ec2 describe-import-snapshot-tasks \
--import-task-ids ${IMPORT_TASK_ID} \
--region ${REGION} \
--query 'ImportSnapshotTasks[0].SnapshotTaskDetail.[Status,StatusMessage,Progress]' \
--output table

Once the task has been completed, get the Snapshot ID.

SNAPSHOT_ID=$(aws ec2 describe-import-snapshot-tasks \
--import-task-ids ${IMPORT_TASK_ID} \
--region ${REGION} \
--query 'ImportSnapshotTasks[0].SnapshotTaskDetail.SnapshotId' \
--output text)

6. Register the Snapshot as an AMI. F5 recommends using /dev/xvda as the root device name. Do not specify VolumeSize in the block-device mapping; let it inherit the snapshot's native size.

AMI_ID=$(aws ec2 register-image \
  --name ${BIGIP_AMI_NAME} \
  --description ${BIGIP_AMI_NAME} \
  --architecture x86_64 \
  --root-device-name "/dev/xvda" \
  --virtualization-type hvm \
  --ena-support \
  --sriov-net-support simple \
  --block-device-mappings "[{\"DeviceName\":\"/dev/xvda\",\"Ebs\":{\"SnapshotId\":\"${SNAPSHOT_ID}\",\"VolumeType\":\"gp3\",\"DeleteOnTermination\":true}}]" \
  --region ${REGION} \
  --query 'ImageId' \
  --output text)

Note: As with Method A, --sriov-net-support simple and --boot-mode legacy-bios may need adjustment depending on target instance family (Xen vs. Nitro) and boot device detection behavior. Test these adjustments in your own environment before relying on them in production.

7. You may then launch an EC2 instance using the AMI ID.

aws ec2 run-instances \
  --image-id ${AMI_ID} \
  --instance-type ${INSTANCE_TYPE} \
  --key-name ${EC2_KEY_NAME} \
  --subnet-id ${SUBNET_ID} \
  --security-group-ids ${SECURITY_GROUP_ID} \
  --region ${REGION} \
  --query 'Instances[0].InstanceId' \
  --output text

Additional Information

Do not use a generic VMware OVA (BIGIP-*.ALL-vmware.ova) as the import source for either method. It lacks AWS platform packages and will produce an AMI where cloud-init cannot detect the EC2 datasource (falls back to ConfigDrive), resulting in no SSH key injection and no AWS-specific first-boot setup, even though the instance otherwise boots.

EHF (Engineering Hotfix) artifacts are delivered as BIGIP-<version>-<build>.ALL-AWS.zip containing -disk1.vmdk (use Method A). GA and point-release artifacts are delivered as .tar.gz containing .raw (use Method B). Confirm current EHF delivery format with your F5 account team if this changes in future releases.
