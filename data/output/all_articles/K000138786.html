K000138786: Enabling FIPS mode and using SIP monitors can cause high CPU

Type
Support Solution
Published
2024-03-28
Updated
2024-03-28
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.1, 17.1.0, 15.1.10
Source
https://my.f5.com/manage/s/article/K000138786

Description

Big-IP with FIPS enabled and configured with SIP monitoring are having higher than normal CPU utilization. A standby device or device with minimal traffic is seen having utilization of between 45% to 50%. A standard F5 without FIPS enabled, but configured with SIP monitoring, is having utilization of between 15% to 20% which should be the expected value.

Environment

  • FIPS enabled
  • SIP monitoring

Cause

This is related to Bug ID 1395257: Processes that are using libcrypto during their startup are causing high CPU usage.
When FIPS mode is enabled and SIP monitors are used, initializing SIP monitors will also initialize the OpenSSL library, causing high CPU consumption. From the top command output:

Recommended Actions

Steps for the workaround:

1. In the local system (which can access BIGIP GUI), create a file with below content (workaround):

#!/bin/bash
 export SECURITY_FIPS140_COMPLIANCE=false
exec /usr/share/monitors/SIP_monitor "$@"
 
2. Save the file with any name of your choice, for example "eav_sip_mon.sh"
3. Access BIG-IP GUI.
4. Navigate to System  ››  File Management : External Monitor Program File List
5. Click on "Import" and upload the file you've created at step #1
Example screenshot:
 
6. Create a new External monitor object under Local Traffic  ››  Monitors  ››  New Monitor, and provide any name.
7. Chose the uploaded file with workaround at step #5 under "External program"
8. On the same External monitor page, under Arguments, define "MODE" under "Name" field, and "udp" under "Value" field.
9. Update the monitor settings.
Example screenshot:
 
10. Now, replace every Pool's SIP monitor with the External monitor that was created at step #6.
11. Monitor the CPU usage.

 

If a fix is required, please open a case with the support team and request an Engineering Hotfix (EHF) for this bug.

Additional Information

This symptom happened to devices enabled with FIPs regardless of version. Non-FIPS devices do not have this symptom.
