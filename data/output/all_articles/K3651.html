Topic

Although you cannot determine which clients are using a dial-up connection by examining a TCP connection, it is likely that connections from dial-up clients will have a higher TCP round trip time than users with higher bandwidth connections. It is unlikely all connections with a high round trip time are dial-up clients. However, all connections that have a high round trip time could benefit from compression.
Example rules

You can use the following rules to assist you in configuring compression based on TCP round trip time.

Important: You must set the HTTP profile Compression to Selective.

Determining round trip time for clients

To determine the round trip time for connecting clients, create the following iRule:

when HTTP_REQUEST {log "RTT:[TCP::rtt]"if {[TCP::rtt] < 150} {COMPRESS::disable}else {COMPRESS::enable}}

Note: This iRule will generate a log entry for each request received by the virtual server that is configured with the iRule. This logging can have a severe impact on performance for sites with a high volume of traffic.

Compressing data responses for clients with specified round trip times

To compress data for clients with specific round trip times, create an iRule similar to the following example, substituting an appropriate value for the <delay>. If you have not determined the round trip time for clients, F5 suggests that you start with a value of 150. You can refine this value based on the results.

when HTTP_REQUEST {if {[TCP::rtt] < <delay>} {COMPRESS::disable}else {COMPRESS::enable}}

This iRule is just one example. You can configure iRules to look for a variety of HTTP status codes and perform various actions based upon the status of those codes. Different environments may require variations on this iRule. For specific information about configuring iRules, refer to the Writing iRules chapter of the Configuration Guide for Local Traffic Management.
