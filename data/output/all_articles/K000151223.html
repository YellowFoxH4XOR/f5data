Description

After upgrading BIG-IP software, HTTP or HTTPS health monitors may change from UP to DOWN status, even though the backend application is healthy. This issue is commonly observed when custom monitor send strings are created or updated via API (iControl REST) with incorrect line ending formatting. Specifically, if the API payload uses single backslashes (e.g., \r\n ) instead of double backslashes (e.g., \\r\\n ), the resulting configuration will contain carriage return characters represented as ^M in some editors. These ^M characters allow the monitor to function before the upgrade, but after the upgrade, the configuration is re-parsed and the ^M characters are removed. As a result, the monitor sends malformed HTTP requests, causing health checks to fail.

For example:

  • Correct: "send": "GET /path HTTP/1.0\\r\\n Host:example.com\\r\\n \\r\\n "
  • Incorrect: "send": "GET /path HTTP/1.0\r\n Host:example.com\r\n \r\n "

The reason ^M appears is due to how JSON escaping works in API calls. When a single backslash is used in the JSON payload, the parser interprets it as a literal carriage return character (^M). This is visible in configuration files and some text editors. After a software upgrade, the configuration is re-parsed, and these carriages return characters may be lost, resulting in incorrect line endings in the monitor send string.

Environment

  • BIG-IP LTM
  • HTTP/HTTPS monitor
  • RestAPI

Cause

The issue is caused by incorrect construction of the monitor send string when using the API. If the JSON payload uses single backslashes (e.g., \r\n), the resulting configuration contains ^M characters. After a software upgrade, the configuration is re-parsed and these characters are removed, leading to malformed HTTP requests. This causes the health monitor to fail, as many backend servers require proper HTTP line endings.

Recommended Actions

  1. To avoid these issues and ensure your monitor works correctly after upgrades, always use double backslashes (\\r\\n) in your API JSON payload. This guarantees that the BIG-IP receives the correct line endings and your monitor remains compatible with future versions.

    • K2167: Constructing HTTP requests for use with the HTTP or HTTPS application health monitor
    • K13225405: Common iControl REST API command examples
    • Review and update all custom HTTP/HTTPS monitor configurations before performing a BIG-IP upgrade to ensure compliance.

    Additional Information

    What Happens When You Use the Incorrect API Expression

    If you use the incorrect API expression (with single backslashes, e.g., \r\n ), the system will display ^M at the end of each line in the configuration, for example (when viewing the configuration by command: vim /config/bigip.conf):

    send "GET / HTTP/1.0^M
Host:10.120.94.130^M
^M
"

    Despite this, the monitor will still work correctly before the upgrade, because the BIG-IP's bigd process can interpret these lines and automatically format them as standard HTTP requests, as shown below (when checking from pcap file):

    GET / HTTP/1.0\r\n
Host:10.120.94.130\r\n
\r\n

    However, after upgrading, the configuration is re-parsed and the ^M characters are removed.  For example, the configuration for the monitor becomes:

    send "GET / HTTP/1.0
Host:10.120.94.130

"

    As a result, the bigd process can no longer interpret the send string correctly. And the HTTP request is then sent in the following (incorrect) format (when checking from pcap file):

    GET / HTTP/1.0\n   --- (missing \r here)
Host:10.120.94.130\r\n
\r\n

    This means the first line uses only a line feed (\n) instead of the required carriage return and line feed (\r\n ). Many backend servers will not recognize this as a valid HTTP request and may respond with a 400 Bad Request error.
