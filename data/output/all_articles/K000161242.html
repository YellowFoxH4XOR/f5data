K000161242: Configuring iRule Logs to Write to a Custom Local File and Forward to a Remote Syslog Server

Description

When using iRules to generate log messages, the default behavior writes all local0 facility messages to /var/log/ltm. This article describes how to simultaneously write iRule log output to a custom local log file (e.g., /var/log/irule_custom) and forward those same messages to a remote syslog server, using a single syslog-ng include block configured via tmsh.

Environment

  • BIG-IP LTM (11.x – 17.x)
  • iRules using log local0. facility
  • Remote syslog server (UDP or TCP)
  • BIG-IP syslog-ng

Cause

By default, the BIG-IP syslog-ng configuration routes local0 facility messages only to /var/log/ltm. There is no built-in mechanism to simultaneously write iRule logs to a separate custom file and forward them remotely. However, syslog-ng supports multiple destinations within a single log {} block, which enables this behavior through a custom include statement.

Additionally, if a remote syslog server is configured via tmsh modify /sys syslog remote-servers, it forwards all syslog traffic without filtering. To apply filtering (e.g., only iRule messages), the remote-servers statement must be replaced with a custom include block.

 

Recommended Actions

Step 1 — Tag iRule log messages with a unique string

Modify your iRule to embed a unique tag string in the log message. This allows syslog-ng to distinguish iRule output from other local0 traffic (such as AUDIT entries).

Note: Use a tag string that includes a colon-space suffix (e.g., <IRULE_TAG>: ). Matching on the colon-space pattern avoids false matches on AUDIT log entries, which contain the tag string itself but not the :  suffix.

when HTTP_REQUEST {
  log local0.info "<IRULE_TAG>: [IP::remote_addr] accessed [HTTP::uri]"
}

The examples in this article use <IRULE_TAG>. You may use any unique string as your tag. For example: 

when HTTP_REQUEST {
  log local0.info "my_irule_tag: [IP::remote_addr] accessed [HTTP::uri]"
}

 

Step 2 — Remove any existing remote-servers configuration

If a remote syslog server was previously configured using the remote-servers statement, it must be removed before defining a custom include filter. Leaving it in place will cause unfiltered forwarding of all syslog traffic in parallel.

Impact: This step temporarily disables remote syslog forwarding until the new include block is applied in Step 3.

tmsh modify /sys syslog remote-servers none
tmsh save sys config

 

Step 3 — Define the combined syslog-ng include block

Open the syslog configuration in the vi editor:

tmsh edit /sys syslog all-properties

Locate the ' include none ' line and replace it with the following block. Substitute <remote_syslog_ip> and the port number with values appropriate for your environment:

include "
    filter f_local0 {
        facility(local0) and not match(\"<IRULE_TAG>: \");
    };
    filter f_irule_tag {
        facility(local0) and match(\"<IRULE_TAG>: \");
    };
    destination d_customlog {
        file(\"/var/log/irule_custom\" create_dirs(yes));
    };
    destination d_remote_loghost 
        udp(\"<remote_syslog_ip>\" port(514));
        tcp(\"<remote_syslog_ip>\" port(514));
    };
    log {
        source(s_syslog_pipe);
        filter(f_irule_tag);
        destination(d_customlog);
        destination(d_remote_loghost);
     };
"

Important: The system does not validate the syntax of the include parameter. An error in this block may cause syslog-ng to fail. Test in a non-production environment before deploying. See K13333: Filtering log messages sent to remote syslog servers (11.x – 17.x).

Exit the editor and save:

:wq!

At the prompt 

Save changes? (y/n/e), enter y.

If syslog filter syntax errors are present, tmsh will return:

There were errors. Continue editing (y) or discard changes (n) (y/n)

Correct any errors before proceeding.

 

Step 4 — Save the configuration and restart syslog-ng

tmsh save /sys config

Restart the syslog-ng service: 

bigstart restart syslog-ng

Note: Restarting syslog-ng does not affect traffic processing.

Step 5 — (Optional) Add log rotation for the custom log file

To include /var/log/irule_custom in the standard BIG-IP log rotation scheme:

tmsh modify /sys logrotate include "/var/log/irule_custom {compress missingok notifempty}"

Save the configuration: 

tmsh save /sys config

Step 6 — Verify

Test that messages are being written locally and forwarded remotely:

Trigger a test log entry:

logger -p local0.info "<IRULE_TAG>: test message"

 

Check the local custom log file:

tail -f /var/log/irule_custom

 

Capture remote syslog traffic (management interface):

tcpdump -i eth0 host <remote_syslog_ip> and port 514

 

Capture remote syslog traffic (TMM interfaces):

tcpdump -nni 0.0:nnn host <remote_syslog_ip> and port 514

 

Additional Information

iRules log at informational level by default. If your filter uses level(warning..emerg), informational messages will be silently dropped. Either use log local0.warning in the iRule, or include info in the filter level range. See K000139985.

Syslog-ng supports multiple destination() entries within a single log {} block. The message is delivered to all listed destinations simultaneously.

The tmsh modify /sys syslog remote-servers method and the include method are mutually exclusive for the same destination. The include approach must be used when filtering is required.

Always run tmsh save /sys config after modifying the syslog include. Changes are lost on configuration reload if not saved.

A syslog-ng issue with remote logging to an invalid remote syslog server may lead to an unexpected reboot. See K45824351.
