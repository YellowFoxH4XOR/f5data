Issue

In BIG-IP WebAccelerator 9.4.x, and also in version 10.0.x prior to 10.0.1-HF3, BIG-IP WebAccelerator policies use the Cache Content Received Over NTLM Connection setting to prevent user-specific content from being cached and served inappropriately. NTLM-authenticated objects are proxied with an S10201 code, which indicates that the objects were proxied because they are not in cache, following the disabled Cache Content Received Over NTLM Connection setting.

Note: The Cache Content Received Over NTLM Connection setting is configured on the policy node's Acceleration Rules >> Responses Cached tab.

Beginning in BIG-IP WebAccelerator 10.1.0 and in 10.0.1-HF3, F5 removed the Cache Content Received Over NTLM Connection setting. The Ignore no-cache HTTP headers in the response setting is used to control caching behavior. NTLM-authenticated objects that were served with the S10201 code in earlier versions may now be served with an S10201, S10202, or S10232 code, depending on how the object was cached and revalidated.

Note: The Ignore no-cache HTTP headers in the response setting is configured on the policy node's Acceleration Rules >> Lifetime tab.

This change was the result of ID 205388 (formerly CR114706-3).

The predefined policies that support NTLM were updated to accommodate this change; however, user-defined policies are not updated. In some cases, user-defined policies require manual modification. In other cases, caching behavior changes slightly.

The following sections detail each scenario:

  • IIS and SharePoint policy modifications are required after upgrading
  • SharePoint and OWA caching behavior changes

IIS and SharePoint policy modifications are required after upgrading

As a result of this change, user-defined policies based on the following predefined policies must be updated after upgrading:

  • Microsoft Internet Information Services (IIS)
  • Microsoft SharePoint Services 2003
  • Microsoft SharePoint Services 2007

To prevent user-specific NTLM-authenticated content from being inappropriately served to other users, the Ignore no-cache HTTP headers in the response setting must be disabled on each leaf node that represents NTLM-authenticated objects. For IIS and SharePoint, you must disable the Ignore no-cache HTTP headers in the response setting for the following leaf nodes:

  • Site >> Static >> Components >> Images
  • Site >> Static >> Components >> Includes

When the Ignore no-cache HTTP headers in the response setting is disabled, the BIG-IP WebAccelerator preserves any Cache-Control header directive set by the origin web server (OWS). If the OWS sets the Cache-Control header to private, the BIG-IP WebAccelerator preserves the Cache-Control header to inform downstream caches that they must not cache the object. The BIG-IP WebAccelerator caches the object, but serves it from cache only after revalidation by the OWS.

Note: Previous versions send a standard GET request to retrieve NTLM-authenticated objects from the OWS each time they are requested. With this change in behavior, the BIG-IP WebAccelerator revalidates the cached object by sending a conditional GET request that includes the If-None-Match header. The conditional GET method is intended to reduce unnecessary data transfer by allowing cached objects to be refreshed without requiring multiple requests or transferring data already held by the client. However, conditional GET request may provoke multiple 401 authentication challenges from some SharePoint servers. For more information, refer to Microsoft KB article 977023 (link following). The following link will take you to a resource outside of AskF5, and it is possible that the document may be removed without our knowledge:

http://support.microsoft.com/kb/977023

Note: The Standard Images and Standard Includes leaf nodes are configured appropriately with the Ignore no-cache HTTP headers in the response setting enabled. When the Ignore no-cache HTTP headers in the response setting is enabled, the BIG-IP WebAccelerator caches the object and sets the Cache-Control header to public, informing downstream caches that they can cache the object.

SharePoint and Microsoft Outlook Web Access caching behavior changes

In earlier versions, the cache content received over NTLM-authenticated connection is disabled for some predefined policy nodes, and objects matching these nodes are not cached. With this change in behavior, the Ignore no-cache HTTP headers in the response setting is now enabled for those nodes, and objects matching these nodes are cached. The following policy nodes are affected by this change:
