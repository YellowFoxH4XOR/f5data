Known Issue

Using the HTTP::proxy disable command may result in a mangled URI.

This issue occurs when all of the following conditions are met:

  • The BIG-IP APM access policy is configured for Kerberos authentication.
  • You have configured an iRule that invokes the HTTP::proxy disable command.

For example, the following iRule disables proxy processing for requests containing a Proxy-Authorization header.

when HTTP_PROXY_REQUEST {
   log local0. "[HTTP::method] [HTTP::uri]"
   if {[HTTP::header exists Proxy-Authorization]} {
      log local0. "Proxy-Authorization found"
   }
   HTTP::proxy disable
}

Impact

The back-end server rejects the mangled URI sent by the BIG-IP APM system.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • For every session, the first request with the Proxy-Authorization header is not proxied to to the back-end server.
  • The BIG-IP APM system generates an error message to the /var/log/ltm file every five minutes that appears similar to the following example:

    err tmm[<pid>]: 01230140:3: RST sent from <virtual_server_IP>:<port> to <client_ip>:<port>, Unknown reason

Workaround

To work around this issue, modify the iRule to ensure the URI is not mangled when using the HTTP::Proxy disable command.

Impact of workaround: Performing the suggested workaround should not have a negative impact on your system.

You can refer to the following iRule as a guidance:

when HTTP_PROXY_REQUEST {
   log local0. "[HTTP::method] [HTTP::uri]"
   if {[HTTP::header exists Proxy-Authorization]} {
      log local0. "Proxy-Authorization found"
      set loc [expr [string first [HTTP::host] [HTTP::uri]] + [string length [HTTP::host]]]
      set uri [string range [HTTP::uri] $loc [string length [HTTP::uri]]]
      HTTP::uri $uri
      log local0. "modified URI: [HTTP::uri]"
      unset loc
      unset uri
   }
   HTTP::proxy disable
}
