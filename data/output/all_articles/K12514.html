Beginning in BIG-IP WebAccelerator 10.0.0, the default size of the BIG-IP WebAccelerator disk cache has a limit of 6 GB. To keep the disk cache from growing too big, the BIG-IP WebAccelerator hds_prune process checks the size of the disk cache every 300 seconds and prunes it when the space available on the filesystem (/wam) decreases to 20 percent. The hds_prune process will prune the disk cache until the space available on the filesystem has increased to 40 percent. If the hds_prune process is overwhelmed by the rate of disk cache growth, the WebAccelerator system logs messages in the /var/log/wa/hds_prune.log file similar to the following example:

hds_prune[PID]: Disk cache /wam/hds/cache is 98% full. Tuning options in the config file /config/wa/pvsystem.conf should be adjusted.
hds_prune[PID]: Not sleeping between prune cycles as incoming files have already pushed available space below the pruning threshold of less than ~1 GiB (1258291 KiB) available (<20% available).
hds_prune[PID]: Sleeping for only 30 seconds as cache was over 95% full.

The amount of pruning performed by the hds_prune process is controlled by the hdsPruneStartLevel and hdsPruneStopLevel settings located in the /config/wa/pvsystem.conf file. You can modify the settings by following the procedure in the Modifying the hdsPruneStartLevel and hdsPruneStopLevel settings section in this Solution.

Note: For more information about the hds_prune process, refer to K9079: Overview of the BIG-IP WebAccelerator hds_prune process.

Beginning in BIG-IP WebAccelerator 10.1.0, when the hds_prune process is initiated, the WebAccelerator system determines whether pruning is required, and logs detailed messages indicating the current cache status in the /var/log/wa/hds_prune.log file. The messages are different depending on whether pruning is required.

If no pruning is required, a single message that appears similar to the following example is logged:

hds_prune[PID]: Disk cache /wam/hds/cache has ~1 GiB (1143720 KiB) used and ~5 GiB (5147736 KiB) available (18% used, 82% available).

If pruning is required, messages that appear similar to the following example are logged:

hds_prune[PID]: Disk cache /wam/hds/cache has ~5 GiB (5147736 KiB) used and ~1 GiB (1143720 KiB) available (82% used, 18% available). Pruning needed as below the pruning threshold of less than ~1 GiB (1258291 KiB) available (<20% available).
hds_prune[PID]: Target is ~2 GiB (2516582 KiB) free, so need to reduce disk usage by 27%. Starting pruning.
hds_prune[PID]: Pruning finished. Time taken: 192 wallclock secs ( 3.11 usr + 3.16 sys = 6.27 CPU) [Note: wallclock - CPU = I/O time]

You can determine if the hds_prune process is pruning the BIG-IP WebAccelerator disk cache excessively by monitoring the /var/log/wa/hds_prune.log file for the above log entries. If on average more than 1 in 10 of the Disk cache... available messages indicate pruning is required, the disk cache pruning activity is excessive.

Note: Prior to BIG-IP WebAccelerator 10.1.0, the hds_prune process does not log the above log entries during its disk cache pruning. However, the BIG-IP WebAccelerator system may log an error message to the /var/log/wa/pvac.log file when the disk cache grows excessively large. For more information, refer to K10507: Error Message: inHashLevel > 3.

Note: For BIG-IP WebAccelerator 10.1.0, F5 recommends you install hotfix BIG-IP-10.1.0-3372.0-HF1 in order to avoid the known issues described in K11083: The hds_prune process may start up before the disk cache is available and K11089: The hds_prune script incorrectly calculates the pruning thresholds.

Recommendations to reduce excessive disk cache

Note: Although it is possible to make changes to the <hdsPrune> settings in the /config/wa/pvsystem.conf file, this does not address the issue of overly aggressive BIG-IP WebAccelerator disk caching.

F5 recommends the following actions in order to reduce disk caching on the BIG-IP WebAccelerator system:

  • Configuring the Always proxy requests for this node option to reduce disk caching
  • Configuring a variation rule to reduce disk caching
  • Bypassing the BIG-IP WebAccelerator for certain objects

Configuring the 'Always proxy requests for this node' option to reduce disk caching

When a response matches a node that is configured with the Configure and use Proxy Rules for this node option enabled for its Acceleration Rules, the BIG-IP WebAccelerator system will attempt to cache the response in its disk cache. Comparatively, the BIG-IP WebAccelerator system will not cache a response matching a node that is configured with the Always proxy requests for this node option enabled.

The Application Generated >Pages leaf node is usually configured with the Configure and use Proxy Rules for this node option enabled in many of the pre-defined policies (for example, Level 2 Delivery) and policies derived from them. Dynamically generated HTML pages typically match this leaf node. By configuring this leaf node with the Always proxy requests for this node option enabled, the BIG-IP WebAccelerator system will no longer cache dynamically generated HTML pages in its disk cache. Many sites have response pages that are dynamically generated with every request, which means they are not good candidates for disk caching.

Note: By default, the Level 1 Delivery and Ecommerce pre-defined policies are configured with the Always proxy requests for this node option enabled.

You can configure this option by performing the following procedure:

  1. Log in to the BIG-IP Configuration utility using a privileged account, such as admin.
  2. Click WebAccelerator.
  3. Click Policies.
  4. Click on the name of the Acceleration Policy.
  5. Click on the plus (+) sign in front of the Site > Application Generated > Pages node.
  6. Click on the Matching Rules menu.
  7. Select Acceleration Rules > Proxying.
  8. Select the Always proxy requests for this node check box.
  9. Click Save.
  10. Click Publish.
  11. Click Publish Now.

Configuring a variation rule to reduce disk caching

If the BIG-IP WebAccelerator system receives multiple requests for the same static object but with different query parameters, it will treat the responses as different Unique Content Identifiers (UCI) for caching. As a result, multiple copies of the same static object are cached by the BIG-IP WebAccelerator system.

For example, the BIG-IP WebAccelerator system will cache the responses for /abc/foobar.htm and /abc/foobar.htm?sessionid=1234 as two different UCIs.

You can configure a variation rule for this object so that the BIG-IP WebAccelerator system will cache this object only once. For instructions on configuring a variation rule, refer to the Configuring Variation Rules chapter of the Policy Management Guide for the BIG-IP WebAccelerator System.

Bypassing the BIG-IP WebAccelerator system for certain objects

If the BIG-IP WebAccelerator system receives requests for objects, such as HTTP-based application Keep-Alive messages and search engine auto-complete requests, you can configure an iRule or HTTP classes to selectively bypass the BIG-IP WebAccelerator system for these requests so that they will not be disk cached. This is useful for objects where features such as Intelligent Browser Referencing (IBR) or MultiConnect are not required.

For instructions on bypassing the BIG-IP WebAccelerator, refer to the following Solutions:

K10127: Bypassing the BIG-IP WebAccelerator with an iRule in version 10.x
K9585: Using multiple HTTP classes to selectively bypass BIG-IP WebAccelerator

Modifying the hdsPruneStartLevel and hdsPruneStopLevel settings

Important: Prior to BIG-IP WebAccelerator version 10.0.0, the pruning process does not account for the actual size of the disk cache. The pruning process only uses the percentage of available space on the file system to determine if pruning is required. If files other than the disk cache are stored on the same file system, and the amount of available space on the file system drops below the configured amount, the BIG-IP WebAccelerator disk cache could be continuously and completely emptied by the pruning process. Therefore, it is important to account for disk usage by non-disk cache files when determining the desired settings for the hdsPruneStartLevel and hdsPruneStopLevel values. 

  1. Log in to the BIG-IP WebAccelerator command line.
  2. Verify the file system used for the BIG-IP WebAccelerator disk cache by typing the following command:

    grep hdsLocation /config/wa/pvsystem.conf
  3. To view the size of the file system used for the BIG-IP WebAccelerator disk cache, type the following command:

    df -h

    The output will appear similar to the following example:

    Note: The /var file system for this example system is 33GB, so the default hds_prune settings should be modified for BIG-IP WebAccelerator versions prior to version 10.0.0.

    Filesystem            Size  Used Avail Use% Mounted on
    /dev/sda5             5.5G  402M  4.8G   8% /
    /dev/sda7             5.5G   35M  5.2G   1% /config
    /dev/sda8              33G   21G   11G  67% /var
    /dev/sda9             5.5G  407M  4.8G   8% /usr
    /dev/sda1              28G  9.4G   17G  36% /shared
    none                  878M   60K  878M   1% /dev/shm
    /dev/loop0            6.6G  482M  5.8G   8% /var/log
    none                  878M  1.6M  877M   1% /var/tmpfs
  4. Change directories to the /config/wa directory by typing the following command:

    cd /config/wa
  5. Back up the original pvsystem.conf file by typing the following command:

    cp pvsystem.conf pvsystem.conf.sol9058
  6. Open the original pvsystem.conf file in a text editor.
  7. Locate the following entry:

    <hdsPruneStartLevel>20</hdsPruneStartLevel>
  8. Increase the hdsPruneStartLevel value to ensure the hds_prune process starts pruning when the BIG-IP WebAccelerator disk cache reaches approximately 4.6GB.

    For example, if the capacity of the file system used for the BIG-IP WebAccelerator disk cache is 33GB, the hdsPruneStartLevel value should be set to 86 (33GB capacity - 86 percent available = 4.62GB used).
  9. Increase the hdsPruneStopLevel value to ensure the hds_prune process stops pruning when the BIG-IP WebAccelerator disk cache reaches approximately 3.3GB.

    For example, if the capacity of the file system used for the BIG-IP WebAccelerator disk cache is 33GB, the hdsPruneStopLevel value should be set to 90 (33GB capacity - 90 percent available = 3.3GB used).
  10. Save the pvsystem.conf file.
  11. If the disk cache has grown extremely large, it is better to clear the cache manually rather than letting the hds_prune process clear it. Clear the cache manually by typing the following command:

    wa_clear_cache

    Important: This command stops and restarts the pvac process and will disrupt accelerated traffic for several seconds. 
     
  12. Restart or reinitialize the hds_prune process:

    For BIG-IP WebAccelerator versions 9.4.5 and later, you can reinitialize the hds_prune process and the configuration is reloaded without restarting the process. Reinitialize the hds_prune process by typing the following command: 

    bigstart reinit hds_prune

    For BIG-IP WebAccelerator versions prior to 9.4.5, you must restart the hds_prune process by typing the following command: 

    bigstart restart hds_prune
