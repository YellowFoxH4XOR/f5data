Description

Users configuring rate limiting on F5® Distributed Cloud HTTP Load Balancers may encounter the following technical issues:

  • Uncertainty about which users are counted toward the rate limit threshold
  • Inability to locate logs or telemetry identifying rate-limited clients (Client IP, User ID, timestamp)
  • Unexpected blocking behavior (HTTP 429 responses) even when Mitigation Action is set to Disabled
  • Difficulty distinguishing between rate-limit drops and standard WAF blocks in Security Analytics
  • Questions about how Mitigation Action: Disabled vs. Mitigation Action: Block settings affect enforcement behavior

Environment

  • Product: F5® Distributed Cloud — Web App & API Protection
  • Feature: Rate Limiting on HTTP Load Balancers
  • Configuration:
    • Custom Rate Limiting parameters configured
    • Rate limit threshold set (e.g., 20–40 requests/second)
    • Burst multiplier configured (e.g., 3x)
    • Mitigation Action set to Disabled
    • Rate Limiter Policies with Action: Bypass Rate Limiter

Cause

Mitigation Action: Disabled does not mean rate limiting enforcement is skipped. The leaky bucket algorithm still enforces the rate limit and returns HTTP 429 responses when the bucket overflows, regardless of the Mitigation Action setting.

Answer/Recommended Actions

Rate Limiting Behavior (Leaky Bucket Algorithm)

  • Incoming requests fill a virtual bucket
  • The bucket drains at the configured rate (requests per second)
  • When the bucket overflows (threshold exceeded), requests are dropped with an HTTP 429 response

Mitigation Action: Disabled (Default)

  • When the bucket overflows, HTTP 429 is returned
  • The bucket continues draining at the configured rate
  • As soon as capacity is available, the next request is allowed
  • Users are never permanently blocked; they must slow down

Mitigation Action: Block (with Duration)

  • When the bucket overflows, HTTP 429 is returned and the user is locked out for the configured duration (e.g., 30 seconds)
  • Even if the bucket drains during the lockout period, the user remains blocked until the timer expires
  • After the timer expires, the user can send requests again

Note: "Disable" in Mitigation Action does not mean rate limiting is bypassed. It means no additional lockout timer is applied beyond the standard leaky bucket 429 response.

Finding Rate-Limit Logs in the F5 Distributed Cloud Console

  1. Navigate to Web App & API Protection → Performance in the F5 Distributed Cloud Console
  2. Filter by your target Load Balancer
  3. Select Security Analytics → Security Monitoring
  4. Apply the filter: Result = rate_limiter_drop

Key Log Fields to Monitor

  • policy_hits.result = rate_limiter_drop
  • policy_hits.rate_limiter_user_id — identifies the unique user being rate-limited
  • rsp_code = 429 — HTTP response code for rate-limited requests
  • src_ip — the client's source IP address
  • @timestamp — the exact time of the event

Additional Information

  • Default LB Rate Limit Enforcement: If a Rate Limiter Policy is configured but contains no matching rules, the default LB rate limit is still enforced. The enforcement behavior (429 drop) follows the leaky bucket algorithm regardless of the Mitigation Action setting.
  • Mitigation Action: Block adds a configurable lockout duration on top of the standard leaky bucket behavior.
  • Mitigation Action: Disabled is appropriate when you want to throttle traffic without permanently blocking users.
