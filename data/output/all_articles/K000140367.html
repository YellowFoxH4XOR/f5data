Description

Security event logs are not sent per configurations in security log profile when multiple security log profiles are attached to a virtual server. When only a single log profile is attached to the virtual server, on the other hand, event logs are sent as expected. Even if re-configuration starts sending event logs, it stops after reboot.

Having two security log profiles: profile A has the affected sub-module enabled in the profile, and profile B has other sub-modules enabled, there are two scenarios to be affected:

  1. Profiles are attached in the order: B first, followed by A -- Profile config in A does not become effective, and event logs supposed to be sent by profile A are not sent
    Known to be affected sub-modules in log profile:
    1. Classification
    2. Network Address Translation
    3. Protocol Inspection
  2. Profiles are attached in the order: A first, followed by B -- Profile config in A is overwritten by profile B, and event logs supposed to be sent by profile A are not sent
    Known to be affected sub-modules in log profile:
    1. Auto Discovery
    2. Network Firewall - Port Misuse
    3. Protocol Security - SSH Proxy

For example, assume there are two security log profiles: One with protocol-inspection and the other with application security like below.

security log profile log_profile_01 {
    protocol-inspection {
        log-publisher my-publisher
    }
    application {
        log_profile_01 {
            logger-type remote
        }
    }
}
security log profile log_profile_02 {
    application {
        log_profile_02 {
            logger-type local
        }
    }
}

The following command attaches log_profile_02 and log_profile_01 in the specific order: log_profile_02 first, followed by log_profile_01. This matches the scenario 1 above, and the protocol-inspection event logs would not be sent through my-publisher.

tmsh modify ltm virtual vs_http security-log-profiles add { log_profile_02 log_profile_01 }

The following command attaches log_profile_01 and log_profile_02 in the specific order: log_profile_01 first, followed by log_profile_02. Both log profiles function properly in this case.

tmsh modify ltm virtual vs_http security-log-profiles add { log_profile_01 log_profile_02 }

Environment

  • BIG-IP AFM
  • More than one security log profiles are attached to a single virtual server
  • The affected sub-modules are enabled in security log profile

Cause

ID 1670445 tracks the issue.

Recommended Actions

There are two possible workarounds for this issue.

Workaround A

Consolidate multiple security log profiles into a single profile and attach it to a virtual server.

Workaround B

In case consolidating into a single security log profile is not an option for whatever reasons, and one of them has the affected sub-modules enabled, use CLI to explicitly attach security log profiles in specific order.

  1. Dissociate security log profiles from the virtual server
    tmsh modify ltm virtual <vs_name> security-log-profiles none
  2. Attach the necessary security log profiles to the virtual server in the correct order ( the left most profile inside curly braces { } will be attached first )
    Scenario 1: Specify the security log profile with the affected sub-module as the left most profile inside curly braces.
    tmsh modify ltm virtual <vs_name> security-log-profiles add { <log_profile_with_affected_sub_module> <other_profiles> }
    Scenario 2: Specify the security log profile with the affected sub-module as the right most profile inside curly braces.
    tmsh modify ltm virtual <vs_name> security-log-profiles add { <other_profiles> <log_profile_with_affected_sub_module> }

Important: The workaround B may not persist across reboots. Creating a custom script like below by following K11948 to run these commands will also be needed to apply the workaround automatically after reboots.

  1. Use a text editor like vim to create a startup script file

    vi /config/startup_script_K000140367.sh

    with contents like below:

    #!/bin/bash # Filename: /config/startup_script_K000140367.sh source /usr/lib/bigstart/bigip-ready-functions wait_bigip_ready # Here you could perform customized command(s) after MCPD is found running when the BIG-IP system starts up. # Customized startup command(s) can be added below this line. tmsh modify ltm virtual <vs_name> security-log-profiles none

    # Either one of them tmsh modify ltm virtual <vs_name> security-log-profiles add { <log_profile_with_affected_sub_module> <other_profiles> }
    # or
    tmsh modify ltm virtual <vs_name> security-log-profiles add { <other_profiles> <log_profile_with_affected_sub_module> } # Customized startup command(s) should end above this line. # End of file /config/startup_script_K000140367.sh

  2. Make the file executable
    chmod +x /config/startup_script_K000140367.sh

  3. Append the script command to the end of /config/startup file
    echo "/config/startup_script_K000140367.sh &" >> /config/startup

Additional Information

When using BIG-IP Configuration Utility (GUI) to attach more than one log profiles to a virtual server, the order to attach would be determined internally, and admins cannot control it. When using GUI, attach one log profile, click Update to save, and attach another log profile, and so on.
