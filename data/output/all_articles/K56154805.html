Environment

  • BIGIP virtual server 
  • hash persistence (default settings)

Cause

A hash persistence profile has two configurable settings that define the data to be used for persistence: These are  hash-offset, and hash-length, which both default to a value of zero.  Leaving them unconfigured means that every new connection will hash to the same value, which will match the existing hash persistence entry, and cause all new connections to end up being persisted to the same pool member.


Example in /var/log/bigip.conf

ltm virtual /Common/Web-Gui-VS-443 {
    description "Web GUI Servers"
    destination /Common/172.16.2.56:16311
    ip-protocol tcp
    last-modified-time 2022-06-23:10:56:07
    mask 255.255.255.255
    persist {
        /Common/hash {                              <====== default hash persistence
            default yes
        }
    }

The hash-offset and hash-length attributes are intended to be configured by a BIG-IP administrator to define the packet data intended for persistence decisions, for example '8 bytes located 14 bytes into the first packet'.

The specific data used for persistence is left for the BIG-IP administrator to identify and define, but should be configured to point to an offset and length of packet data that is consistently set to the same value for all connections that must persist to the same pool member.   Setting the offset and length to other values, or leaving them at the default values of zero may provide undesired load balancing results.

The 'hash' persistence method is a 'catch-all' feature for use cases where the built-in types of source-ip,  msrdp, sip, http host, or http cookie are not suitable.  It is similar to the 'universal' persistence method, in that the data being used for persistence can also be defined by the use of irule commands. The main difference between hash and universal persistence is that with universal persistence, the persistence record is the data itself, whereas with hash persistance, the persistence record is a hash of the data, which results a more efficient persistance lookup operation.

Recommended Actions

The "hash-offset" and "hash-length" properties of the hash persistence profile should be configured to values that are appropriate for the data being processed by the virtual server, and the specific persistence requiremnents of that virtual server. These values are protocol-specific, and use-case specific, often customer-specific, and must be determined by the BIG-IP administrator, based on their business's use-case and persistence requirements.  If more complex persistence requirements exist, then an irule may be required. Hash persistence records created in an irule supercede the hash-offset and hash-length properties of the hash profile.

Additional Information

In most cases, a client's IP address is the most appropriate data to persist connections on, in that subsequent connections arriving from the same source IP address should be sent to the same pool member.  In that situation, hash persistence is not an appropriate means of persistence - although it could be configured to hash a source IPv4 address by configuring it with a hash-offset of 14 and a length of 4, that offset and length is not guaranteed to always be the client's IP address, as fragmentation, encapsulation, and encryption may be present.  If the intent is to persist connections based simply on the client's source IP address, then 'source-addr' persistence should be used instead.

Note that creating and storing persistence records on the BIG-IP will consume tmm memory, and increase resource requirements.  BIG-IP administrators should be careful to configure the timeout property appropriately, so as not to exceed available BIG-IP memory capacity with millions of long-lived persistence records.   An alternative solution, for where the traffic is HTTP or HTTPS, is to make use of client HTTP cookies to store the persistence information on the client, which has the advantage of consuming no resources on the BIG-IP.
