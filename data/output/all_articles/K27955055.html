Topic

This article gives an overview of the supported algorithms in BIG-IP IPsec since BIG-IP 11.4.0 for both Internet Key Exchange (IKE) v1 and v2. The article helps inform a BIG-IP administrator in deciding which algorithms are appropriate for IPsec tunnels and is of particular use when deciding on the cipher sets when the BIG-IP system must interoperate with another vendor's device.

Description

In the following table, you should interpret the software version to mean the latest sustaining release. That means that some ciphers may not be available or may not work in the first release but are available in a later maintenance release or, in rare cases, through an engineering hotfix. For example, if an algorithm is listed as supported in BIG-IP 12.1.x, then that means any software version labelled BIG-IP 12.1, but the first release of BIG-IP 12.1.0 may not work correctly or may be missing the option in either the Configuration utility or in the TMOS shell (tmsh).

With IKEv2, the concept of phase 1 and phase 2 does not exist since the phase 2 negotiation overlaps the initial IKE SA negotiation. For the purpose of simplicity this document uses phase 1 to mean the IKE SA and phase 2 to mean the child SA created after an IKE SA.

The table is divided into two major sections:

  • IKE peer is "phase 1" configured in Network > IPsec > IKE peers using the Configuration utility or net ipsec ike-peer in tmsh.
  • IPsec policy is "phase 2" configured in Network > IPsec > IPsec Policies using the Configuration utility or net ipsec ipsec-policy in tmsh.

The subsection of the table names each element by the tmsh object name, which maps to the Configuration utility option as follows:

  • 2md5 is insecure and will be deprecated. From BIG-IP 13.1.0, the md5 option does not appear in the Configuration utility but you can configure it using tmsh. For more information, refer to K52833014: The BIG-IP system allows the MD5 algorithm to be specified for the IKE Phase 1 Authentication Algorithm but does not recognize the MD5 algorithm.
  • 3ECP is available for IKEv2 only.
  • 4When an AES-GCM or AES-GMAC is selected for authentication, that algorithm then handles both authentication and encryption.
  • 5When the IKE peer is configured to be IKEv2, the Perfect Forward Secrecy (PFS) option for the IPsec policy is inherited from the IKE peer configuration. Therefore, when using IKEv2, the PFS setting in IPsec policy is ignored.
