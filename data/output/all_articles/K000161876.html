K000161876: IP ACL (allow/deny) doesn't work in the location block with the return directive

Type
Support Solution
Published
2026-06-25
Updated
2026-06-25
Applies to
  • NGINX Products
  • NGINX Plus: 37.0.0, R33, R34, R35, R32, R36
Source
https://my.f5.com/manage/s/article/K000161876

Description

When using IP ACL ("allow"/"deny" directives) and the "return" directive in the same location, IP-based access limitation doesn't work in the NGINX Plus configuration.

Environment

  • NGINX Plus
  • The "allow"/"deny" directives and "return" directive configured in the same location.

Cause

The "return" directive is a part of the rewrite module. And the "allow"/"deny" directives are a part of the access module. The NGINX Plus architecture is designed so that the NGX_HTTP_SERVER_REWRITE_PHASE request phase occurs first and only then the NGX_HTTP_ACCESS_PHASE request phase. In other words, directives related to the access module cannot be executed if the request ended at the rewrite module.

Answer/Recommended Actions

Since the "allow"/"deny" directives cannot be used with the "return" directive in the same location, you can replace this limitation with the "geo" and "map" directives workaround.

For example:

http {
    geo $private_allow {
        10.0.0.0/8 1;
        172.16.0.0/12 1;
        192.168.0.1/16 1;
        default 0;
    }

    map $private_allow $location_return {
        1 200 text;
        0 403;
    }

    server {
        location / {
            return $location_return;
        }
    }
}

In this example, all clients with private IP addresses receive an HTTP 200 status code with the specified text, if required. The others receive an HTTP 403 (Forbidden) status code.

Additional Information

The "allow"/"deny" directives don't work in the case described in this article. This does not apply to other cases.
