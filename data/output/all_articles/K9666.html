Topic

FirePass offers several methods for configuring dynamic master group and resource group mapping, including LDAP. The following three types of LDAP group mapping methods exists:

  • User Object
  • Group Object
  • Filter

You can configure one or more of these LDAP mapping methods based on the the configuration of your LDAP directory schema.

LDAP Dynamic Group Mapping

The LDAP dynamic group mapping method is based on querying an LDAP server. A typical LDAP query consists of a Base DN and a search filter. Common for all three mapping methods, the FirePass first needs to define the value of the user DN, which corresponds to the user who will be logging in to FirePass. 

Note: DN is an acronym for Distinguished Name.

A user DN usually holds values that appear similar to the following example:

CN=joe,CN=users,dc=f5,dc=com

Defining the user DN

To define the user DN, perform the following procedure:

  1. Log in to the FirePass Administrative utility.
  2. Click on Users.
  3. Click on Groups.
  4. Click on Dynamic Group Mapping.
  5. Select the Group mapping methods tab.
  6. Click on Configure next to LDAP (user object).
  7. Populate the information in the Connect to LDAP server section with the information relevant to your environment. 
  8. Select Get user DN using template in the Query LDAP user object section.
  9. Populate the Template section with the appropriate information.

    For example:

    CN=%logon%,CN=Users,DC=f5,DC=com
  10. Click the Update button at the bottom of the screen. 

User DN

The user DN in the Connect to LDAP server section can be defined using the following two options:

  • The Get user DN using template option
  • The Get user DN using query option

Note: The session variables (such as %logon%) can be used in both of the methods that define the user DN. FirePass will replace it with the logon name when the mapping occurs.

The Get user DN using template option

FirePass uses this template-based user DN to retrieve the whole User object including all LDAP attributes.

For example:

CN=Administrator,CN=Users,dc=f5,dc=com

The Get user DN using query option

FirePass queries the LDAP server, with the Base DN defined in the Search Base DN box and a filter defined in the Query template.  If a record is found, the LDAP server will return the whole User Object including all LDAP attributes, which also includes the user DN.

LDAP (User Object)

The User Object mapping method should be used for LDAP schemas where the User object contains the Group Information of the user. For example,  the following user object has a memberOf group information attribute:

dn: CN=joe,CN=users,DC=f5,DC=com
objectClass: person
cn: joe
sn: smith
gender : male
l: Akasaka
st: Tokyo
title: Network Engineer
memberOf: CN=engineers,CN=users,DC=f5,DC=com
memberOf: CN=vpn-users,CN=users,DC=f5,DC=com
memberOf: CN=it-admins,CN=users,DC=f5,DC=com
mail: joe@f5.com

Note: The Administrator can define which attribute contains the group information on the Users: Groups: Dynamic Group Mapping: Group mapping methods tab under the Fetch group information from LDAP users object section. You can define the mapping table entries on the Users: Groups: Dynamic Group Mapping: Master group mapping table tab.

In the mapping table, any of the attributes previously defined can be selected. If no attributes are defined, the default attribute of Parent DN will be available, which is the one level parent of the user DN.  For example, if the user DN is CN=Joe,CN=users,dc=f5,dc=com, the Parent DN will be CN=users,dc=f5,dc=com.

FirePass will look into the user object to compare the value of the defined attribute with the value defined in each entry of the mapping table. If the match is found, that entry will be mapped. For master group mapping table, the first match will be used. For resource group mapping table, the first match is used if the Map user to first matched group only check box is selected; otherwise, all matches are used.

LDAP (Group Object)

On some LDAP schemas, group membership is defined within group objects instead of within user objects. In these instances, one or more attributes within the group object define group membership, either statically or dynamically. In this configuration, you can use the Group object mapping method.

For example, the following group object has members defined statically. In this case, the member attribute contains a list of group members:

dn: CN=engineers,CN=users,DC=f5,DC=com
objectClass: group
cn: engineers
member: CN=joe,CN=users,DC=f5,DC=com
member: CN=bob,CN=users,DC=f5,DC=com
member: CN=fred,CN=users,DC=f5,DC=com

Group objects may also have group membership defined dynamically defined through an LDAP URL. In these instances, one of the group object attributes must contain an LDAP URL with a search filter. The format for the LDAP URL must conform to the standard defined in RFC 2255. Specifically:

scheme://host:port/dn?attributes?scope?filter?extensions

In the following example, the attribute named memberURL contains the LDAP URL, part of which is a filter:

dn: CN=IT-engineers,CN=users,DC=f5,DC=com
objectClass: dynamicGroup
cn: IT-engineers
memberURL: ldap:///localhost:389/DC=f5,DC=com??sub?(&(objectClass=person)(title=*Engineer*)(dept=*IT*))

When group membership is defined statically, enter the attribute name which contains the member list in the Static members attribute field in the LDAP (group object) mapping method. When group membership is defined dynamically, enter the attribute name which contains the LDAP URL in the Dynamic members attribute field in the LDAP (group object) mapping method. Using our previous examples, you would enter member in the Static members attribute field and memberURL in the Dynamic members attribute field.

After configuring the LDAP (group object) mapping method, define an LDAP (group object) mapping table entry that maps the group object DN to a FirePass master group. Mapping table entries for master group mapping are configured under the Master group mapping table tab, and mapping table entries for resource group mapping are configured under the Resource group mapping table tab.

At user logon, FirePass queries the LDAP server for each group DN defined in the mapping tables to determine whether the group DN contains the user DN or username. Versions prior to FirePass version 6.0.3 only checked the user DN; starting in FirePass version 6.0.3, FirePass also checks the username. For master group mapping, only the first match will be used to map the user's master group since users cannot belong to multiple master groups. For resource group mapping, all matches will be mapped to the user unless the the Map user to first matched group only check box is selected. If the the Map user to first matched group only check box is selected, only the first match is mapped.

LDAP (Filter)

Some LDAP schemas do not have group objects. Their user object does not contain the group membership information. However, some attributes of the user object might be used with certain criteria to determine the group mapping. LDAP filter mapping method is used in this case. 

For example, the (&(st=WA)(title=*Engineer*)) filter will be matched if the user stays in WA state and the title includes Engineer. You can use this fiter to map to an Engineers from WA group.

Also, the (department=finance*) filter will be matched if the user's department name starts with finance. You can use this filter to map to a group called Finance.

Note: The filters are defined in the Mapping Table tab on the Users: Groups: Dynamic Group Mapping: Masters group mapping page.

The user object is queried with each defined filter to determine which filter results in a match.

LDAP filter mapping provides the ability to use any kind of LDAP filter. FirePass does not limit the types of filters that can be used. The configured filter will be passed to the LDAP server and if the LDAP server can respond to that filter request, the matching will be successful. The FirePass administrator must configure an LDAP filter that the LDAP server can support.

The first match will be used for master group mapping table. For the resource group mapping table, the first match is used if the Map user to first matched group only check box is selected; otherwise, all matches are used.

Filter-based mapping has the following limitations:

  • The session variables (like %logon% %username% %password%) do not work inside the LDAP filter mapping table.
  • Some LDAP servers do not support the use of wildcard (*) filters for Distinguished-name-syntax attributes.
