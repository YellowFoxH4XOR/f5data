Description

When testing a new ICAP implementation with ASM by following K70941653, you observe that files are not forwarded to the configured ICAP server.

The upload is Base64 encoded and part of a JSON payload parameter, similar to the following example:

Note: In this example, the file upload is the value of the Content parameter

POST /api/uploads/testing HTTP/1.1
<..>
Content-Type: application/json
<..>

{
  "Type": "CreateAttachmentJSONRequest",
  "Header": {
    "Type": "JSONHeaders",
    "Timezone": "British Summer Time"
  },
  "Body": {
    "Type": "JSONUpload",
    "Attachments": [
      {
        "Type": "FileAttachment",
        "Content": "SG93IGRvIHlvdSBwcm9ub3VuY2UgIkpTT04iIGFueXdheT8gSi1zYWhuPyBObywgSmFzb24uIEphc29uIGlzIGF3ZXNvbWUh",
        "ContentType": "text/plain",
        "Name": "memo.txt"
      }
    ],
    "Description": false
  }
}

Environment

  • ICAP
  • Virus scanning with ASM

Cause

The ASM implementation of ICAP performs content inspection on binary data only. The system checks content types for multipart file uploads in which no content profile is associated for that particular URL.

Requests similar to those described in the description of this article will not be sent to the ICAP server.

Recommended Actions

ASM will not send this type of request for inspection, but the LTM implementation of ICAP request or response adaptation will send this type of request. Consider using that instead, but some visibility will be lost in the ASM event logs.

For more information, refer to the Configuring Content Adaptation for HTTP Requests and Responses manual page for your BIG-IP version.

Additional Information

Many ICAP servers will decode Base64 encoded payloads for proper inspection, so sending this type of payload there can be desirable.
