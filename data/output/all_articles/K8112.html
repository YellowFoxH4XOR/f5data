Topic

When using the FirePass controller's Network Access feature to provide connectivity to remote clients, it is important to understand the implications on your organization's network infrastructure.

FirePass Network Access uses the  Point-to-Point Protocol (PPP), encrypted with SSL. Each remote client's PPP network adapter is assigned its own IP addresses through the PPP server running on the FirePass controller. Ranges of IP addresses available to the clients are configured using standard network address and netmask notation, and are called virtual subnets. While the actual network connection between client and FirePass is the standard point-to-point connection with an all-ones subnet mask (255.255.255.255, or /32 in CIDR notation), the aggregate of these connections appears to the organization's internal networks as a standard subnet, with the FirePass controller serving as the gateway for routing to the virtual subnets. Virtual subnets are configured on the Network Access: Global Settings page in the Add new IP Address Pool section.

Important: Do not configure a virtual subnet using a network range that includes an IP address assigned to the FirePass controller.

In order to route packets from the internal networks to the virtual subnets, the organization's routing infrastructure must include the routes to all virtual subnets. This configuration may be as simple as adding a single static route to one or more routers or hosts on the directly connected network to the FirePass controller. Or the configuration may require propagating the routes through a dynamic routing protocol such as OSPF, RIP or IGRP.

Alternatively, if you do not want to make routing changes in order to use Network Access, you may use a form of Network Address Translation (NAT) for the virtual subnet addresses of the clients. Using the FirePass Network Address Port Translation (NAPT) feature, you translate the client's virtual subnet IP address to the IP address of the FirePass controller. If the FirePass controller possesses multiple IP addresses, the IP address used in NAPT will be the address of the FirePass interface through which the client's packets exit (and translate in reverse for the return packets). The interface through which the client packets exit is determined by routing to the packet destination. Using NAPT, you can avoid any routing infrastructure additions or changes, because the routing infrastructure only needs to know how to route to the IP address of the FirePass controller, not the virtual subnets behind the FirePass controller. NAPT is enabled by selecting the Use NAPT to access LAN check box on the Network Access: Global Settings page.

Note: By default, NAPT is enabled in FirePass.

Important:  Applications that do not work with Network Address Translation will not work with the FirePass controller's NAPT feature. For example, any application that includes an IP address in the application data portion of the packet will not work. For such applications, you must make the aforementioned routing changes in your infrastructure instead of using NAPT.
