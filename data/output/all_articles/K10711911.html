  • K74767112: Overview of the TCP profile (15.x)
  • K29377715: Overview of the TCP profile (14.x)

  • K7559: Overview of the TCP profile (9.x - 10.x)

This article discusses the TCP profile settings. You can find the TCP profile in the Configuration utility by navigating to Local Traffic > Profiles > Protocol > TCP.

Description

The TCP profile allows you to specify how a BIG-IP virtual server processes TCP traffic. To manage traffic, you can use the TCP profile alone or in conjunction with other profiles. For example, you can use the HTTP profile to process Layer 7 (L7) traffic, or use the SSL profile to process SSL traffic.

Note: Starting in BIG-IP 13.0.0, the BIG-IP system does not allow you to modify the default TCP base profile. For more information, refer to K53830409: The default TCP base profile is read-only starting with BIG-IP 13.x. You can create a modified TCP profile using the default TCP base profile as the parent profile and associate the modified profile, which contains specific settings, with either individual virtual servers or groups of virtual servers.

Settings and definitions in the TCP profile

Timer Management

SettingDefault valueDescription
Close WaitSpecify : 5 secondsAvailable options:
  • Specify: User specified amount of time (in seconds) that a TCP connection remains in the LAST/ACK state before quitting.
  • Immediate: Specifies that the TCP connection closes immediately after entering the LAST/ACK state.
  • Indefinite: Specifies that TCP connections in the LAST/ACK state do not close until they meet the maximum retransmissions timeout.
Fin Wait 1Specify : 5 secondsAvailable options:
  • Specify: User-specified amount of time (in seconds) that a TCP connection is in the FIN/WAIT-1 or CLOSING state before closing.
  • Immediate: Specifies that the TCP connection closes immediately after entering the FIN/WAIT-1 or CLOSING state.
  • Indefinite: Specifies that TCP connections in the FIN/WAIT-1 or CLOSING state do not quit.
Fin Wait 2Specify : 300 secondsAvailable options:
  • Specify: User specified amount of time (in seconds) that a TCP connection is in the FIN/WAIT-2 state before quitting.
  • Immediate: Specifies that the TCP connection closes immediately after entering the FIN/WAIT-2 state.
  • Indefinite: Specifies that TCP connections in the FIN/WAIT-2 state do not quit.
Idle TimeoutSpecify : 300 secondsAvailable options:
  • Specify: User-specified amount of time (in seconds) that the connection can remain idle before the connection is eligible for deletion.
  • Indefinite: Specifies that the connection can remain idle indefinitely.

Note: Take caution when adjusting idle times, as each TCP connection requires resources to track and maintain the connection. Leaving TCP connections for long periods of time uses more resources that can be better used for new connections. For more information on changing a protocol profile idle timeout refer to K7166: Changing the idle timeout for a protocol profile.

Keep Alive IntervalSpecify : 1800 secondsAvailable options:
  • Specify: User-specified amount of time (in seconds) that determines the interval at which the system sends data over an idle connection, to determine whether the connection is still valid.
  • Indefinite: Specifies that the system does not send keep-alive communications.
Minimum RTO1000 millisecondsSpecifies the minimum length of time that the system waits for acknowledgements of data sent, before resending the data. The value must be equal to or less than 5000. The default is 1000 milliseconds, which means that the system uses the RFC-compliant value of 1 second. If the Packet Loss Ignore Rate and Packet Loss Ignore Burst settings contain values other than 0, this value drops to 203 ms. If MPTCP is enabled, the value drops to 200 ms.
Reset On TimeoutEnabledThe system sends a reset (RST) and deletes the TCP connection when the connection exceeds the idle timeout value. If disabled, the system deletes the TCP connection when the connection exceeds the idle timeout value, but does not send an RST to the client.

Note: This setting can cause the client (if Reset on Timeout is disabled) to assume that the connection is still valid long after it has been removed from the BIG-IP LTM system.

Time WaitSpecify : 2000 millisecondsAvailable options:
  • Specify: User-specified amount of time (in milliseconds) that a TCP connection remains in the TIME-WAIT state before the system closes it. The range is from 0 to 600000 milliseconds.
  • Immediate: Specifies that the system closes the connection immediately after the connection enters the TIME-WAIT state.
  • Indefinite: Specifies that TCP connections can remain in the TIME-WAIT state indefinitely.
Time Wait RecycleEnabledThe system recycles or reuses the connection when a SYN packet is received in a TIME-WAIT state. This option allows the system to better optimize system resources by reusing a connection in a TIME-WAIT state when a SYN packet is received, instead of creating a new connection.

Note: If disabled, the system establishes a new connection instead of reusing a connection that is in a TIME-WAIT state.

Zero Window TimeoutSpecify : 20000 millisecondsAvailable options:
  • Specify: User-specified amount of time (in milliseconds) that the TCP connection can receive zero-length window probes before the system closes the connection.

    Note: The timeout starts when the peer advertises a zero length TCP window or when enough data has been sent to fill the previously advertised window. The timer is cancelled when a non-zero length window is received.

    Note: The BIG-IP system honors timeout values in multiples of 5000 (for example: 5000 ms, 10000 ms, and 20000 ms). This behavior accounts for the minimal time required for CPU timers and round trip time (RTT) of packets to ensure that when a zero window size update is received, the system allows the counter to start and TCP window probes are sent to query whether there is a window size change on the receiver.

    If you enter a value that is not a multiple of 5000, the system rounds the value up to the next multiple of 5000. For example, if a 0 is entered, the system rounds up to 5000 ms. If 7000 is entered, the system rounds up to 10000 ms.

  • Indefinite: Specifies that the system does not delete TCP connections based on zero-length window.

Data Transfer

SettingDefault valueDescription
Acknowledge on PushEnabledImproves performance to Windows and Mac OS peers writing out on a small send buffer.
Delayed AcksEnabledAllows the system to send fewer than one ACK (acknowledgment) segment per data segment received. This is part of TCP congestion control that is defined in RFC 1122: Requirements for Internet Host and RFC 2581: TCP Congestion Control.

Note: F5 recommends that you keep this setting enabled as it allows the application to update the TCP window and send an immediate response if required. This setting also reduces the number of segments sent by the server.

Don't Fragment Flag (DF)PmtuSpecifies the Don't Fragment (DF) bit setting in the IP Header of the outgoing TCP packet. The default is Pmtu. The available settings are:
  • Pmtu: Sets the outgoing IP Header DF bit based on IP pmtu setting(tm.pathmtudiscovery).
  • Preserve: Sets the outgoing Packet's IP Header DF bit to be same as incoming IP Header DF bit.
  • Set: Sets the outgoing packet's IP Header DF bit.
  • Clear: Clears the outgoing packet's IP Header DF bit.
Initial Receive Window Size3 MSS unitsSpecifies the initial receive window size for connections to this destination. Actual window size is this value multiplied by the MSS (Maximum Segment Size) for the same connection. The default is 3. Valid values range from 0 to 64.
Max Segment Size (MSS)1460 bytesSpecifies the largest amount of data that the system can receive in a single TCP segment, not including the TCP and IP headers. If the value is 0 (zero), the system calculates the value from the MTU. The default value is 1460 bytes.
Nagle's AlgorithmDisabledDetailed in RFC 896: Congestion Control in IP/TCP Internetworks, the Nagle Algorithm is a TCP optimization that makes the stack wait until all data is acknowledged on a connection before sending more data. This process, called nagling, increases the efficiency of a network application system by decreasing the number of packets that must be sent.

Available options:

  • Disabled: Specifies that the system does not apply Nagle's algorithm.
  • Enabled: Specifies that the system applies Nagle's algorithm to reduce the number of short segments on the network. When the system receives packets that are less than the maximum segment size (MSS), the packets are coalesced until the peer has sent the ACK packet for the previous segment. This helps to reduce congestion by creating fewer packets on the network.
  • Auto: Specifies that the system determines whether to use Nagle's algorithm based on network conditions.

Note: In some highly interactive client/server environments, the use of Nagle's Algorithm may cause undesired behavior, and should be disabled.

PUSH Flag
(13.1.x and later)		DefaultSpecifies how the BIG-IP system receives ACKs. Frequent receipt of ACKs can affect BIG-IP system performance. To mitigate impacted performance, you can configure PUSH Flag to control the number of ACKs that the system receives because of setting the PSH bit in a TCP header. Available options:
  • Default: Specifies the system receives a TCP acknowledgement (ACK) whenever the system sends a segment with the PUSH (PSH) bit set in the Code bits field of the TCP header.
  • None: Specifies the system never sets the PSH flag when sending a TCP segment so that the system will not receive an ACK in response.
  • One: Specifies the system sets the PSH flag once per connection, when the FIN flag is set.
  • Auto: Specifies the system sets the PSH flag in these cases:
    • When the receiver’s Receive Window size is close to 0.
    • Once per Round Trip Time (RTT), that is, the length of time that the BIG-IP system sends a signal and receives an ACK.
    • At the end of the response from the server side. For example: a TCP FIN is received or the HTTP content-length is reached.
Note: This setting is introduced in BIG-IP 13.1.x. Prior to BIG-IP 13.1.x, the behavior in earlier versions is the same as Default.
Time To Live (TTL)ProxySpecifies the outgoing TCP packet's IP Header TTL mode. The default is Proxy. The available settings are:
  • Proxy: Sets the outgoing IP Header TTL value to 255/64 for IPv4/IPv6 respectively.
  • Preserve: Sets the outgoing IP Header TTL value to be same as the incoming IP Header TTL value.
  • Decrement: Sets the outgoing IP Header TTL value to be one less than the incoming TTL value.
  • Set: Sets the outgoing IP Header TTL value to a specific value (as specified by ip-ttl-v[4|6]).
Time To Live (TTL) v4255Specifies the outgoing packet's IP Header TTL value for IPv4 traffic. Maximum TTL value that can be specified is 255. The default is 255.

Congestion Control

SettingDefault valueDescription
Appropriate Byte Counting (RFC 3465)EnabledIncreases the congestion window by basing the increase amount on the number of previously unacknowledged bytes that each ACK covers.
Congestion Metrics CacheEnabledSpecifies that the system uses a cache for storing congestion metrics.
Congestion Metrics Cache Timeout0 secondsSpecifies the number of seconds for which entries in the congestion metrics cache are valid. The default value is 0, which defers to the route.metrics.timeout system database variable.
Congestion ControlHigh SpeedSpecifies the congestion control mechanism that the BIG-IP system uses.
Available options:
  • None: No congestion control algorithm implemented.
  • CAIA Delay-Gradient (CDG): Specifies that the system uses a delay based TCP that senses onset of congestion by variations in round trip time (RTT).
  • CAIA Hamilton Delay (CHD): Specifies that the system uses a TCP algorithm that aims to keep network queuing delays below a particular threshold (queue_threshold) and decides to reduce the congestion window (cwnd) probabilistically based on its estimate of the network queuing delay.
  • CUBIC: Specifies that the system uses a TCP algorithm that is optimized for high bandwidth, high delay networks.
  • High Speed: Specifies that the system uses a more aggressive, loss-based algorithm. RFC 3649: HighSpeed TCP for Large Congestion Windows.
  • Illinois: Specifies that the system uses a TCP algorithm that is especially targeted at high-speed, long-distance networks.
  • New Reno: Specifies that the system uses a modification to the Reno algorithm that responds to partial acknowledgements when SACKs are unavailable. RFC 2582: The NewReno Modification to TCP's Fast Recovery Algorithm.
  • Reno: Specifies that the system uses an implementation of the TCP Fast Recovery algorithm, which is based on the implementation in the BSD Reno release. RFC 2581: TCP Congestion Control.
  • Scalable: Specifies that the system uses a TCP algorithm modification that adds a scalable, delay-based and loss-based component into the Reno algorithm.
  • Vegas: Specifies that the system uses a TCP algorithm modification that adds a delay-based and loss-based component into the Reno algorithm.
  • Westwood+: Specifies that the system uses a TCP algorithm based on a bandwidth estimation metric.
  • Woodside: Specifies that the system uses a TCP algorithm that is especially targeted at high-speed, long-distance networks with enhanced congestion recovery.
Delay Window ControlDisabledSpecifies, when enabled, that the system uses an estimate of queuing delay as a measure of congestion to control the amount of data sent (in addition to the normal loss-based control).
Explicit Congestion NotificationDisabled (BIG-IP 13.0.x)
Enabled (BIG-IP 13.1.0 and later)		Specifies, when enabled, that the system uses the TCP flags CWR (Congestion Window Reduced) and ECE (ECN-Echo, used to indicate that the TCP peer is Explicit Congestion Notification capable during the three-way handshake) to notify its peer of congestion and congestion counter-measures.
In BIG-IP 13.0.x versions, this setting is Disabled by default. Beginning in BIG-IP 13.1.0 the default value is Enabled.

Note: When this option is enabled, it is used only when two hosts signal that they want to use it. It allows a host to set the ECN bit within the IP header to notify the transmitter that the link is congested.
Note: SYN re-transmissions sent by BIG-IP have ECN and CWR flags cleared. This is done to allow a handshake when a device in path drops traffic with ECN/CWR bits set.

Initial Congestion Window Size3 MSS unitsSpecifies the initial congestion window size for connections to this destination. Actual window size is this value multiplied by the MSS (Maximum Segment Size) for the same connection. The default is 3 MSS. Valid values range from 0 to 16.
Packet Loss Ignore Burst0 packet countSpecifies the probability of performing congestion control when multiple packets are lost, even if the Packet Loss Ignore Rate was not exceeded. Valid values range from 0 to 32. The default is 0, meaning that the system performs congestion control if any packets are lost. Higher values decrease the chance of performing congestion control.
Packet Loss Ignore Rate0 packets lost per millionSpecifies the threshold of packets lost per million at which the system performs congestion control. Valid values range from 0 to 1,000,000. The default is 0, meaning the system performs congestion control if any packet loss occurs. If you set the ignore rate to 10 and packet loss for a TCP connection is greater than 10 per million, congestion control occurs.
Rate PaceDisabledThe system paces the egress packets to avoid dropping packets, allowing for optimum goodput. This option mitigates bursty behavior in mobile networks.
Rate Pace Maximum Rate0 bytes/secondSpecifies the maximum rate in bytes per second to which the system paces TCP data transmission. If this value is 0, no maximum is enforced. The default value is 0.
Slow StartEnabledSpecifies that the system uses larger initial window sizes, as specified in RFC 3390: Increasing TCP's Initial Window, to help reduce round trip times. TCP slow-start congestion avoidance is a method of converging on the right amount of data to put on the link without overloading the link to prevent the system from dropping packets.
Timestamps Extension for High Performance (RFC 1323)EnabledSpecifies that the system uses the timestamp extensions for TCP, as specified in RFC 1323, to enhance high-speed network performance. The timestamp option allows for accurate Round Trip Time Measurement, in addition to simplifying window calculations for the sender.
Note: As explained in RFC 6691, TCP options are not included in the MSS value calculation. The BIG-IP system does not use timestamp extensions for TCP because doing so would result in traffic fragmentation.

Loss Detection and Recovery

SettingDefault ValueDescription
DSACK (RFC 2883)DisabledSpecifies the use of the Selective ACKs (SACK) option to acknowledge duplicate segments. RFC 2883 specifies an extension to Selective Acknowledgements, known as DSACK. Using DSACK, a receiver can notify its peer when it receives multiple copies of data, thus warning the sender of in-band network replication of segments, or causing the peer to scale back in its re-sending speed.
Early RetransmitDisabled (BIG-IP 13.0.x)
Enabled (BIG-IP 13.1.0 and later)		Specifies, when selected (enabled), that the system uses early retransmit (as specified in RFC 5827) to reduce the recovery time for connections that are receive- buffer or user-data limited. By default, this setting is disabled. Enabling this setting allows TCP to act as though a packet is lost, after fewer than the standard number of duplicate ACKs, if there is no way to send new data and generate more duplicate ACKs.
In BIG-IP 13.0.x versions, this setting is Disabled by default. Beginning in BIG-IP 13.1.0 the default value is Enabled.
Enhanced Loss RecoveryDisabledSpecifies that TCP uses SACK information to increase performance.
Initial Retransmission Timeout Base Multiplier for SYN Retransmission3000 millisecondsSpecifies the initial RTO (Retransmission TimeOut) base multiplier for SYN retransmissions. The default value is 0 (zero) which sets the initial base RTO for SYN retransmissions at three seconds. This value is modified by the exponential backoff table to select the interval for subsequent retransmissions.

For example, if the value of this setting is changed to 1000, then the initial base SYN RTO would be changed to one second, and the next RTO would be two seconds, and then subsequent RTO would be four seconds, etc., based on the exponential backoff table.

Note: For communication with pool members, the first 5 SYN retransmission interval is always the configured syn-rto-base value, and the 6th SYN retransmission and the subsequent SYN retransmissions will be modified based on the exponential backoff table.

Limited Transmit RecoveryEnabledSpecifies that the system uses limited transmit recovery revisions for fast retransmits, as specified in RFC 3042: Enhancing TCP's Loss Recovery Using Limited Transmit to reduce the recovery time for connections on a lossy network.
Maximum Segment Retransmissions8Specifies the maximum number of times the system resends data segments.
Maximum Syn Retransmissions3Specifies the maximum number of times the system resends a SYN or SYN/ACK when it does not receive a corresponding reply.
Retransmit Threshold3Specifies the number of duplicate ACKs (retransmit threshold) to start fast recovery. The default is 3. The range is from 3 to 255.
Selective ACKsEnabledSpecifies that the system processes data using selective ACKs to improve system performance.

Note: F5 recommends that you do not disable this option. Selective ACKs (SACK) improves performance by explicitly listing which packets, messages, or segments in a stream are acknowledged. This lets the sender know specifically what information is missing, so that it only retransmits the missing information. SACK is detailed in RFC 2018: TCP Selective Acknowledgment Options.

Selective NACKDisabledThe system processes data using a selective negative acknowledgment (SNACK) whenever possible, to improve system performance.
Tail Loss ProbeDisabledSpecifies, when selected (enabled), that the system uses Tail Loss Probe to reduce the number of retransmission timeouts. Retransmission timeouts occur when TCP segments are lost from the tail of a transaction, or a window of data/ACKs are lost. By default, this setting is disabled. Enabling this setting allows TCP to send a probe segment to trigger fast recovery instead of recovering a loss by way of a retransmission timeout.

Security and Quality of Service

Recommendations

None
