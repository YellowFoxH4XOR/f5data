Known Issue

The SSL::disable and SSL::enable iRules commands may cause connections to reset.

This issue occurs when the following condition is met:

  • An iRules configuration includes the SSL::enable command immediately after the SSL::disable command, similar to the following example:

    ltm rule /Common/test_ssl_rule {
        when HTTP_REQUEST {
            SSL::disable serverside
            if { [HTTP::uri] starts_with "/ssl" } {
                SSL::enable serverside
            }
        }
    }

Impact

Connections may be intermittently and unexpectedly reset or lost.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • When the tm.rstcause.log database variable is enabled, and the log.ssl.level database variable is set to debug, messages similar to the following log to the /var/log/ltm file:

    debug tmm[7613]: 01260009:7: Connection error: ssl_open:3081: Invalid timer state. (80)
    info tmm[7613]: 01260013:6: SSL Handshake failed for TCP 10.10.153.3:443 -> 10.10.153.95:38253
    err tmm[7613]: 01230140:3: RST sent from 10.10.161.95:80 to 10.10.161.3:55500, [0x1d75429:2003] {peer} SSL error (internal_error(80))

Workaround

None. To mitigate this issue, you can avoid re-enabling SSL processing immediately after disabling it. Instead, allow the logic of your iRule to determine the required state, and then use either the SSL::enable or SSL::disable command, as appropriate. For more information, refer to the SSL::enable and SSL::disable iRules command pages on F5 Cloud Docs.

Impact of workaround: Changing the design of an iRule may have additional effects on traffic processing. Ensure any modification is compatible with your environment.
