K000163529: Empty Timestamp in the CGNAT log

Type
Support Solution
Published
2026-10-03
Updated
2026-10-03
Applies to
  • BIG-IP
Source
https://my.f5.com/manage/s/article/K000163529

Description

CGNAT logs may show an empty 14th field(timestamp) when AFM is not licensed or provisioned. In the customer’s environment, this can cause compliance checks to fail.

 

CGNAT predefined field list:
"context_name","event_name","src_ip","dest_ip","src_port","dest_port","route_domain","protocol","translated_src_ip","translated_dest_ip","translated_src_port","translated_dest_port","translated_route_domain","timestamp","sub_id"

Example of empty timestamp:
"/Common/NAT","Session Start","1.1.1.1","2.2.2.10","56252","80","0","TCP","2.2.2.1","2.2.2.10","1084","80","0","","112233445566"

 

Environment

  • BIG-IP CGNAT(not using LSN legacy mode)
  • AFM not licensed or not provisioned
  • NAT logging via HSL

 

Cause

For CGNAT field-list logging (non-legacy mode), AFM must be licensed and provisioned to populate all fields; without AFM, the timestamp field remains empty.

 

Answer/Recommended Actions

  • License and provision AFM to populate the timestamp field. 
  • Alternatively, enable LSN legacy mode to use the legacy logging format, which includes its own timestamp.


Legacy mode example (timestamp present):
"LSN_ADD""1.1.1.1:42764""TCP""2.2.2.1:1036""2.2.2.10","80""1790086959707""112233445566"

 

With AFM provisioned (timestamp populated):
"/Common/NAT","Session Start","1.1.1.1","2.2.2.10","32870","8080","0","TCP","2.2.2.1","2.2.2.10","1062","8080","0","Sep 18 2026 05:43:07","112233445566"
