Description

After upgrading the BIG-IP VE or its Hyper-V host hypervisor, intermittent TCP connection failures may appear. This can manifest in symptoms ranging from large TCP data transfers connections stalling, taking much longer or large HA configsync operations being unable to complete. (For example, ASM and APM tend to be large)

 

Environment

This may happen when:

  • Making changes on the hypervisor on Azure or Hyper-V platforms
  • Installing BIG-IP VE versions between 17.5.0 to 17.5.1.5 or 21.0.0
  • Installing BIG-IP VE versions that include ID 1983145

Cause

As described in K000153024, BIG-IP VE version 17.5.0 and 21.0.0 on Hyper-V/Azure started using the dpdk driver to enable higher performance for network packet processing. However, some drivers did not handle IP fragments well. This resulted in TCP transfers stalling when packets become large enough to need fragmentation handling.

 

Symptoms

Without ID 1983145, the result is that when large packets that require TSO/LSO handling are observed, sometimes TCP transfers seem to stall. Also, tmm cores may occur when memory becomes corrupted.

Without ID 2224937, large TCP data transfers between tmms may fail intermittently. Large configsync operations may not be able to complete.

Without ID 2219929, multicast traffic may be dropped, causing symptoms ranging from BIG-IP VE may not be able to complete ipv6 neighbor discovery, resulting in loss of connectivity, to various failures related to protocols that require multicast.

 

Answer/Recommended Actions

Check that certain Hyper-V hypervisor parameters are set to appropriate values ( see K000137614 )

 

To make IP fragments work, it is recommended to install BIG-IP VE that have all of the following fixes:

- ID 1983145 allowed the forced processing of IP fragments for those drivers and avoided unexpected conditions that cause BIG-IP to crash

- ID 2224937 ensured the checksums are correct for IP fragments. ID 2224937 must also be applied to any EHF version that has ID 1983145, otherwise IP fragments may be dropped.

- ID 2219929 ensures the drivers are set to process multicast traffic even if promiscuous mode cannot be enabled. Without this fix, multicast and ipv6 ndp may fail, especially if the hypervisor blocks promiscuous mode or broadcasts.

 

Workarounds

  • Alternatively, users who do not need the fast packet processing or SR-IOV capability from the dpdk driver may revert back to the old Sock driver ( See K10142141 ).
    However, using the sock driver comes with the lack of GRO, lowering performance (see Bug ID 1106489 ).
  • Another workaround for failed configsync and HA operations, users may try configuring the configsync IP to the management port (which does not use the tmm to process packets).
