Description

URI-based pool selection can fail when multiple unrelated iRules use the same globally scoped static-variable name for different data-group references. The overwritten reference may cause the URI class match to use the wrong data group, leaving traffic on the default pool instead of routing WebSocket requests to the intended pool.

Environment

  • BIG-IP LTM virtual servers using application-routing iRules.
  • A data group that identifies URI paths requiring routing to a WebSocket backend.
  • Multiple iRules configured with the same globally scoped static-variable name.
  • Separate backend pools for standard HTTP traffic and WebSocket traffic.

Cause

A globally scoped static variable used to store a data-group reference is reassigned by another iRule using the same variable name for a different data group. This reassignment overwrites the reference used by the application-routing iRule. As a result, the URI class match can fail, and the intended pool-selection condition is not met.

Answer/Recommended Actions

  • Do not use the same globally scoped static-variable name for unrelated data-group references.
  • Replace shared static variables with appropriately scoped variables or uniquely named references for each iRule and service.
  • Audit iRules attached to affected virtual servers for duplicate static-variable names and conflicting assignments.
  • Validate that WebSocket URI requests match the intended data group and are routed to the required backend pool.
  • Confirm that successful WebSocket requests establish server-side connections to port 9090 and receive HTTP 101 Switching Protocols.

Additional Information

When the WebSocket URI condition fails, traffic is sent to the default port-8080 pool instead of the required port-9090 pool. The application then returns HTTP 403 responses.
