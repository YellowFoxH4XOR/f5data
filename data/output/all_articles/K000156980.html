Description

The management GUI on a BIG-IP LTM may become slow or unresponsive, showing high CPU usage in the mcpd process. This occurs when a GSLB BIG-IP DNS server object uses the 'bigip' monitor and manages a large number of virtual servers on that LTM, or when frequent and large iQuery requests (such as auto-discovery when hundreds or thousands of virtual servers are defined) towards the LTM device are configured. Excessive monitoring load from the 'bigip' monitor can overwhelm the LTM's mcpd process, resulting in degraded management plane performance and slow or incomplete GUI rendering.

The "bigip" monitor works by querying mcpd for the current status of virtual servers, and reports that back to the BIG-IP DNS via the iQuery protocol. 

Environment

  • BIG-IP LTM (including vCMP tenants) device(s)
  • BIG-IP DNS configured with server objects of type 'bigip'
  • DNS (GTM) 'bigip' monitor assigned to GSLB server objects that represent the LTM device(s)
  • Large configuration scale (many virtual servers under GSLB server object) on the LTM device(s)
  • Virtual server auto-discovery enabled, and/or frequent iQuery/statistics polling from BIG-IP DNS
  • High mcpd CPU usage observed on the LTM
  • Management GUI (TMUI) slow or unresponsive on the LTM

Cause

The 'bigip' monitor type attached to a GSLB server object with many virtual servers or frequent iQuery/statistics requests causes the big3d process to generate a large number of MCPD transactions querying the state of those virtual servers. This overwhelms mcpd, leading to high CPU utilization and degraded management plane performance.

Recommended Actions

  • Identify high mcpd CPU usage by checking the mcp_transaction_stat tmstat table for high transaction counts from the mcpd user named '%big3d'.
  • If the 'bigip' monitor type is assigned to a GSLB server object with many virtual hundreds or thousands of virtual servers, consider:
    • Changing the monitor type from 'bigip' to 'gateway_icmp' to reduce mcpd load on the LTM
    • Configuring the GSLB server as a 'generic host' and using a non-bigip monitor type.
    • Disabling virtual server auto-discovery on the GSLB server object if not required.
  • Monitor mcpd CPU usage and management GUI responsiveness after changes.
  • For large-scale GSLB deployments, follow best practices for monitor selection and avoid using the 'bigip' monitor on server objects with high configuration scale or frequent polling.
