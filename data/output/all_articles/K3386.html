Topic

Note: This article applies only to version 9.x iRules, and assumes that you are familiar with assigning an iRule to a virtual server. For detailed information about iRules and data groups for BIG-IP version 9.x, refer to the Writing iRules chapter of the Configuration Guide for Local Traffic Management. For detailed information about iRules and data groups for BIG-IP version 10.x, refer to the DevCentral iRules wiki.

Note: For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.

Beginning with version 9.0.0, data groups replace the class lists that are found in BIG-IP 4.x. Data groups are a collection of related elements, such as a set of IP addresses for AOL clients, and are useful with iRules. For example, you can use a data group to separate traffic based on URI components.

Data Group Types

Data groups can be one of the following types:

  • Address:

    An address data group consists of a collection of IP addresses.

  • String:

    A string address group consists of a group of strings, such as *.jpg.

  • Integer:

    An integer data group consists of a group of integers.

  • External File:

    You have the option to store data groups in an external file. The benefit of storing data groups in an external file is the data does not need to be sorted by the system when it is loaded, because it is stored outside of the bigip.conf file. The elements in the external data group file should be stored in comma-separated lists with a newline character after each entry. Refer to the BIG-IP Configuration Guide for more details about Data Groups.

    Note: Starting in BIG-IP 9.4.0, an empty external data group file containing an errant control character will prevent the data group from loading.

Data Group References by version

In versions 9.4.4 - 10.x, the matchclass and findclass commands reference the data group directly by name. For example, the following syntax is used in version 10.1.0:

[matchclass [HTTP::uri] contains example_class]

In versions 9.0.0 - 9.4.3, the matchclass and findclass commands reference the data group as a global variable: The class name is prefixed with the string $::. For example, the following syntax is used in version 9.4.2:

[matchclass [HTTP::uri] contains $::example_class]

iRules example

You can use an iRule to choose a pool based on the HTTP URI within the data group that is contained in the client request.

For example, you want an iRule that makes a decision based on whether the URI contains one of the following strings:

  • string1
  • string2
  • string3

After creating a data group of type String, the following configuration object is seen in the bigip.conf file:

class exampleClass  {  
    "string1"  
    "string2"  
    "string3"
}

The following version 10.0.1 iRule references the exampleClass listed above:

rule exampleRule {  
    when HTTP_REQUEST {    
        if {[matchclass [HTTP::uri] contains exampleClass]}{
            pool pool-uri-match  
            log local0. "Using uri-match pool - [HTTP::uri]"   
        } else {
            pool pool-no-uri-match      
            log local0. "No uri matched using no-uri-match pool - [HTTP::uri]"    
        }  
    }
}

Comparison order

In BIG-IP 4.x, the class operator one of always assumes the class is on the right side of the operator and checks to see if a variable for the class exists on the left side.

Note: In the above example, the operator is contains.

Beginning with version 9.0.0, you can switch the order of the class and operator in an iRule and use the class on either side of the operator.

There is a subtle difference in the way the following two example commands are written; however, the BIG-IP system processes each command differently:

  • [matchclass [HTTP::uri] contains $::example]

  • This command checks to see if the HTTP URI contains one of the URIs listed in the example class. The BIG-IP system first looks at the HTTP URI and compares that to what is listed in the example class list.

  • [matchclass $::example contains [HTTP::uri]]

  • This command checks to see if any of the contents in the example class list contain the HTTP URI. In other words, the BIG-IP system first looks at the example class list and compares that to what is presented in the HTTP URI.

If the client presents an HTTP URI of /foo/uri1, for which only uri1 is in the class list, the BIG-IP system would process the client according to the sample rules, as follows:

Using the first iRule, [matchclass [HTTP::uri] contains $::example], the BIG-IP system would see that the /foo/uri1 HTTP URI contains one of the URIs listed in the example class and successfully process the URI.

Using the second iRule, [matchclass $::example contains [HTTP::uri]], the BIG-IP system would see that the /foo/uri1 HTTP URI does not match any of the URIs in the example class and the iRule will fail.

Logging

F5 recommends that you use log statements when you write an iRule. Logging is important during the debug and testing phase. After you have tested the iRule, you can remove the log statement to simplify the rule and reduce logging. In the previous example rule, every connection parsed by the iRule will generate a log message. You also have the option to log only when the URI is not matched. This will decrease the amount of logging required.

Testing an iRule

You can use the cURL utility to test an iRule from the BIG-IP command line interface.

Following is an example curl command, where <virtual-server-address> is the IP address of the virtual server to which you have assigned the iRule:

curl <virtual-server-address>/test/uri1/test

This request will generate a log message similar to the following example in the /var/log/ltm file:

Sep 15 19:09:38 tmm tmm[14770]: Rule example <HTTP_REQUEST>: Using uri-match pool - /test/uri1/test

Following is another example curl command:

curl <virtual-server-address>/test/uri4/test

This request will generate a log message similar to the following example in the /var/log/ltm file:

Sep 15 19:09:46 tmm tmm[14770]: Rule example <HTTP_REQUEST>: No uri matched using no-uri-match pool - /test/uri4/test
