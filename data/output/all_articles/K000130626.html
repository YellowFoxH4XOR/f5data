Description

  • A couple of things may occur that bring into question how a BIG-IP processes TCP connections...
    • You may come across an issue where a security scan fails.
    • How the BIG-IP appears to handle certain TCP connections may seem odd.

Environment

  • CVE-2004-0230
  • Fastl4 profile, virtual server, Self-IP, Linux kernel
  • Qualys or other system security inspection apps, LTM, TCP

Cause

A BIG-IP, dependent upon configuration, does not handle the TCP connection or may appear to be vulnerable otherwise. There are basically 5 times this may be seen...

  • A Qualys security scan may come back saying the BIG-IP failed because it appears to be vulnerable to CVE-2004-0230
  • When a virtual server is configured with a fastl4 profile
  • When you connect to a BIG-IP via a self-ip
  • You have the BIG-IP TCP profile set to use a long Keep-Alive Interval settings in order to allow the server (pool member/destination) to maintain long-lived connections
  • If the db variable tm.tcpallowinsecurerst has been enabled

 Recommended Actions

In each case the BIG-IP is acting per design. 

  • The Qualys security scan will alert when one of the other 4 causes is seen during the scan. This is because of how both the BIG-IP and the TCP protocol function.
  • When a fastl4 virtual server, handled by tmm, is set up to use a fastl4 profile the TCP reset behavior is handled by the pool member/destination that is behind the virtual server.
  • When you connect to the BIG-IP via a self-ip (in some situations you can configure the BIG-IP to work similar to a switch and that is done via a self-ip) the BIG-IP uses a fastl4 to expose a service from the Linux host. Thus in this case the issue is with the Linux TCP stack supporting the service it has connected to.
  • As to the use of a long TCP Keep-Alive there are 2 possibilities as to how that could cause a scan to fail...
    • The first is due to simple CVE web-scraping based on version - because K3126 does not (and will not) explicitly list all versions as a non-vulnerable version, Qualys assumes all non-listed versions are vulnerable.
    • The second is that the scanner did actually probe the virtual servers and determined that large window sizes are supported - through the use of buffers that enable Window Scaling in the tcp profile. Allowing Window Scaling on a virtual server allows for better throughput, and so is a valid choice for you to make.
  • In regards to the db variable tm.tcpallowinsecurerst being enabled (it is disabled by default) that would make the BIG-IP vulnerable per K8894. By doing this the BIG-IP system will process TCP RST packets with sequence numbers in the receive window. However, that would be based on a manual configuration change and thus the BIG-IP is acting per configuration.

 

Additional Information

The BIG-IP is acting per RFC793 and by design.

By default the BIG-IP is not vulnerable. This issue is seen with long lived connections of hours or days. The Qualys scan is not a long-lived connection but simply a SYN sent and then the remote listener is not reachable so per rfc the BIG-IP ACKs the SYN and resets the connection. So the scan is not a valid test. Also, as is explained in K3126 "This vulnerability is found in the principle design of TCP/IP itself and cannot be completely corrected without changing to an alternate protocol." In other words - CVE-2004-0230 cannot fundamentally be fixed without changing from TCP to another protocol, and in the 19 years since CVE-2004-0230 was announced nothing has been developed that supplants TCP.
