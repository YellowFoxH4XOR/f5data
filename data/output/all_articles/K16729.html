Known Issue

The configuration for the secondary VIPRION blades may fail to load following a reboot.

This issue occurs when the following conditions are met:

  • The primary blade of a VIPRION chassis is rebooted and rejoins the cluster as a secondary blade.

Impact

The secondary blade moves to a disconnected state and is unavailable for traffic processing.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • In the /var/log/ltm file, you observe error messages that appear similar to the following example:

    01070088:3: The requested object name (/Common/default-eviction-policy) is invalid.
    01070935:3: Unexpected exception caught in MCPProcessor::rm_DBLowHighWide().
    01070734:3: Configuration error: MCPProcessor::check_initialization:
    01070734:3: Configuration error: URL category (/Common/Abortion) cannot be deleted. It is being used by a URL filter.

  • The secondary blade moves to a disconnected state, and is not available for traffic processing.

Workaround

To work around this issue, you can remove the binary database from the secondary blades, and then restart the services on the blade. To do so, perform the following procedure:

Impact of workaround: The services on the blade will be temporarily unavailable.

  1. Log in to the command line of the secondary blade.
  2. To remove the binary database, type the following command:

    /bin/rm -v /var/db/mcp*

  3. To restart the services on the blade, type the following command:

    bigstart restart

  4. Repeat the previous steps for each affected secondary blade.
