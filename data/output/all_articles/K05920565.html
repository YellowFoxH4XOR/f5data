Description

The image is not booting/upgrading after 'x' minutes.

During a BIG-IP software upgrade, installing a new software image in a new partition (both via webUI or TMSH) is failing with an error message similar to the one below:

failed (Could not access configuration source; <vda/sda>, 1 )

In /var/log/liveinstall.log, logs similar to the one below can be seen:

info: >++++ result:
info: mount: /dev/mapper/vg--db--vda-set.1._usr is already mounted or /mnt/tm_install/27210.OiQ1en/usr busy
info:        /dev/mapper/vg--db--vda-set.1._usr is already mounted on /usr            <<<----[!] 
info:        /dev/mapper/vg--db--vda-set.1._usr is already mounted on /opt/.sdm/usr   <<<----[!]
info:        /dev/mapper/vg--db--vda-set.1._usr is already mounted on /opt/.sdm/lib   <<<----[!]
info:        /dev/mapper/vg--db--vda-set.1._usr is already mounted on /opt/.sdm/lib64 <<<----[!]
info: >----
error: status 8192 returned by command: mount -oro  /dev/vg-db-vda/set.1._usr /mnt/tm_install/27210.OiQ1en/usr 2>/dev/null
info: >++++ result:
info: umount: /mnt/tm_install/27210.OiQ1en/shared: not mounted
info: >----
error: status 8192 returned by command: umount /mnt/tm_install/27210.OiQ1en/shared
Terminal error: Could not access configuration source; vda, 1
*** Live install end at 2020/07/08 20:49:21: failed (return code 2) ***

Environment

  • BIG-IP
  • Running on version 12.x through 16.0.0 (excluding version 15.1.2 which is not affected)
  • iRulesLX provisioned

Cause

This issue is caused by Bug ID 915605


Recommended Actions

  1. To determine if the /usr filesystem was mounted as read-write instead of read-only with the following command on CLI
    v12.x/v13.x:
       # grep usr /proc/mounts

    Incorrect output will be similar to:
    /dev/mapper/vg--db--vda-set.1._usr /usr ext3 ro,seclabel,noatime,errors=continue,barrier=0,data=ordered 0 0
    /dev/mapper/vg--db--vda-set.1._usr /opt/.sdm/usr ext3 rw,seclabel,nosuid,noatime,errors=continue,barrier=0,data=ordered 0 0

    v14.x and later:
       # mount | grep usr

    Incorrect output will be similar to:
    /dev/mapper/vg--db--vda-set.1._usr on /usr type ext4 (ro,noatime,seclabel,discard,data=ordered)
    /dev/mapper/vg--db--vda-set.1._usr on /opt/.sdm/usr type ext4 (rw,nosuid,noatime,seclabel,discard,data=ordered)
    /dev/mapper/vg--db--vda-set.1._usr on /opt/.sdm/lib type ext4 (rw,nosuid,noatime,seclabel,discard,data=ordered)
    /dev/mapper/vg--db--vda-set.1._usr on /opt/.sdm/lib64 type ext4 (rw,nosuid,noatime,seclabel,discard,data=ordered)

    NOTE: rw means read-write, this should be ro (read-only)

    If this applies to your system, you can work around this issue by remounting /usr filesystem as ro (read-only)
     
  2. To remount the /usr filesystem to Read-Only state, use the following command on the CLI (applicable to version 12.x/13.x or v14.x and later):
       # mount -o remount,ro /usr

      If unit is a mutiblade Viprion,  use command:
       # clsh mount -o remount,ro /usr  
     
  3. Validation/Verification that /usr filesystem is correctly mounted as ro (read-only) with the following command on CLI

    v12.x/v13.x:

       # grep usr /proc/mounts

    Correct output will be similar to:
       /dev/mapper/vg--db--vda-set.1._usr /usr ext3 ro,seclabel,noatime,errors=continue,barrier=0,data=ordered 0 0
       /dev/mapper/vg--db--vda-set.1._usr /opt/.sdm/usr ext3 ro,seclabel,nosuid,noatime,errors=continue,barrier=0,data=ordered 0 0

    v14.x and later:
        # mount | grep usr

    Correct output will be similar to:
       /dev/mapper/vg--db--vda-set.1._usr on /usr type ext4 (ro,noatime,seclabel,discard,data=ordered)
       /dev/mapper/vg--db--vda-set.1._usr on /opt/.sdm/usr type ext4 (ro,nosuid,noatime,seclabel,discard,data=ordered)
       /dev/mapper/vg--db--vda-set.1._usr on /opt/.sdm/lib type ext4 (ro,nosuid,noatime,seclabel,discard,data=ordered)
       /dev/mapper/vg--db--vda-set.1._usr on /opt/.sdm/lib64 type ext4 (ro,nosuid,noatime,seclabel,discard,data=ordered)
     
  4. Delete the failed HDX.X partition and reinstall the image again.

    IMPORTANT: After booting from the new boot location, if the version installed is the version affected by this Bug ID 915605, those partitions are mounted as rw, so it is good idea to run this workaround again after reboot, not to encounter the issue in the future when you upgrade.
