Topic

This article describes how to utilize the BIG-IP configuration synchronization (ConfigSync) feature to migrate a configuration from an old VIPRION blade hardware platform to a new one. If you have a standalone VIPRION device or prefer another migration method, refer to the VIPRION Systems: Blade Migration manual. If you want to attempt a migration without the aid of ConfigSync or the scripts described in the manual, refer to K82540512: Overview of the UCS archive 'platform-migrate' option.

Note: The platform-migrate TMOS shell option replaces the no-platform-check option described in K14906: Overview of the UCS 'no-platform-check' tmsh option.

Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

You should consider using these procedures under all of the following conditions:

  • You are replacing the VIPRION blades with a new hardware platform and not the chassis.

    Note: If you are replacing both the VIPRION chassis and blades, you should consider adding the replacement VIPRION system to the existing device group in order to migrate the BIG-IP configuration. For more information, refer to K15496: Migrating a device group member to a new BIG-IP hardware platform.

  • Your VIPRION systems are configured as a device group, and you want to use ConfigSync to migrate the current configuration to a new VIPRION blade hardware platform.

Description

When upgrading VIPRION blades to a newer hardware platform, you must migrate the existing BIG-IP configuration to the newly installed blades. To upgrade blades of VIPRION systems in a device group, you can replace the blades of one VIPRION system and then use the ConfigSync feature to migrate the existing configuration from the old blades of another VIPRION system in the device group to the VIPRION system with the new blades. After using ConfigSync to migrate the configuration, you can then replace the blades of the next VIPRION system and push the configuration to it from the device group. The following procedures describe how to perform the blade replacement and configuration migration in detail. This article is specific to replacing blades without replacing the chassis. For example, if you have B2100 blades that you want to upgrade to B2150 or B2250 blades, or B2150 blades that you want to upgrade to B2250 blades.

Prerequisites

You must meet the following prerequisites to use these procedures:

  • You have a user configuration set (UCS) backup of the VIPRION system or backups of the Virtual Clustered Multiprocessing (vCMP) hypervisor and guests stored in a secure location off the device. For more information, refer to K13132: Backing up and restoring BIG-IP configuration files with a UCS archive.
  • You have documented the base (non-synchronized) configuration objects, such as Virtual Local Area Networks (VLANs), non-floating self IP addresses, and route domains from the device or each vCMP guest you are replacing to have as a reference when you re-configure the VIPRION system or vCMP guests. For a list of non-synchronized items, refer to K21259300: BIG-IP items that are not synchronized between device group members during a ConfigSync operation. You can find the base configuration object stanzas in the bigip.conf and bigip_base.conf configuration files, located in the /config and /config/partitions/<partition_name> directories.

    Note: The device has unique base configuration objects that you do not need to re-configure on the new device, such as the interfaces, device certificates, device service clustering (DSC) device objects, and DSC device trust certificates.

  • If your VIPRION system is a vCMP hypervisor, you have documented the hypervisor configuration and the configuration defining the vCMP guest instances from the VIPRION system you are replacing to have as a reference when you re-configure the new VIPRION system. You can find the configuration object stanzas in the bigip.conf, bigip_base.conf, and bigip_user.conf configuration files, located in the /config and /config/partitions/<partition_name> directories of your VIPRION system.
  • You have administrative privileges and access to the Configuration utility.
  • You have administrative privileges and access to the command line on your VIPRION system.
  • You have serial console access to your VIPRION system.
  • You have physical access to your VIPRION system.

Procedures

  • Replacing existing VIPRION blades with new VIPRION blades
  • Re-configuring the base configuration of the new VIPRION system or vCMP hypervisor configuration
  • Deploying and re-configuring the base configuration of the new vCMP guests (vCMP systems only)
  • Setting Device Connectivity options for the new VIPRION system or new vCMP guests
  • Re-configuring the existing device trust and device group on an authority device and using ConfigSync to migrate the BIG-IP configuration
  • Performing failover to the new VIPRION system or new vCMP guests and verifying traffic

Note: Repeat the procedures for each VIPRION system with blades you plan to replace.

Note: The ConfigSync process does not synchronize the BIG-IP DNS (formerly known as BIG-IP GTM) global server load balancing (GSLB) configuration, such as data centers, wide IPs, and servers. If you configured the BIG-IP DNS system as a redundant server object, you must run the gtm_add utility to synchronize the GSLB configuration to the new VIPRION system and run the bigip_add utility to exchange certificates with all BIG-IP servers for iQuery communication. For more information, refer to K13312: Overview of the BIG-IP DNS big3d_install, bigip_add, and gtm_add utilities (11.x - 14.x).

Replacing existing VIPRION blades with new VIPRION blades

In this procedure, you physically remove old VIPRION blades from the existing VIPRION chassis and replace them with new VIPRION blades.

Impact of procedure: The VIPRION system with the blades you plan to replace becomes unavailable for traffic processing. You must shut down the device to remove the blades. The newly installed blades do not contain the full BIG-IP configuration until you perform the migration in a later procedure. F5 recommends that you schedule this procedure during a maintenance window to minimize impact in mission critical environments.

  1. Log in to the Configuration utility of one of the following:
    • The VIPRION system with the blades you are replacing
    • A vCMP guest on the VIPRION hypervisor with the blades you are replacing
  2. Navigate to Device Management > Devices and click the VIPRION system or vCMP guest designated with Self.
  3. Select Force to Standby. The selected VIPRION system or vCMP guest should change to standby mode.
  4. If applicable, repeat steps 1 through 3 for each vCMP guest.
  5. If applicable, disable each vCMP guest by performing the following actions:
    1. Log in to the Configuration utility of the vCMP hypervisor with the blades you are replacing.
    2. Navigate to vCMP > Guest List.
    3. Select the check box for all vCMP guests.
    4. From the Requested State list, select Provisioned and click Update (11.x through 12.x) or click Provision (13.x and later).
      The device group should report at least one other vCMP guest as active, and all guests should report that guests on the device with the blades you are replacing are offline and the ConfigSync status is disconnected.
  6. Use the serial port to connect a terminal emulator to the VIPRION system with the blades you are replacing. For more information, refer to K7683: Connecting a serial terminal to a BIG-IP system.
  7. Log in to the BIG-IP command line.
  8. Halt all blades by typing the following command:

    clsh halt

    After the blades are halted, at least one other VIPRION system in the device group should be active and all systems should report that the device with the blades you are replacing is offline and the sync status is disconnected. If the device is a vCMP hypervisor, it should be running in standalone mode.

  9. Detach the cables from the VIPRION blades you are replacing and remove the blades from the chassis. Keep the blades nearby, in case you need to roll back to the old configuration.
  10. Insert the new VIPRION blades into the empty chassis and attach the new cables.

Re-configuring the base configuration of the new VIPRION system or vCMP hypervisor configuration

To prepare the VIPRION system with the newly installed blades for ConfigSync, you must re-configure the hypervisor configuration or the base (non-synchronized) configuration. You can also use configuration information documented from the old device as a guide.

Impact of procedure: The VIPRION system with the newly installed blades becomes unavailable for traffic processing. The newly installed blades do not contain the full BIG-IP configuration until you perform the migration in a later procedure. F5 recommends that you schedule this procedure during a maintenance window to minimize impact in mission critical environments.

  1. Use the serial port to connect a terminal emulator to the new VIPRION system.
  2. After the blades have completed booting up, log in to the BIG-IP command line of the primary blade on the new VIPRION system.
  3. Start the F5 Management Port Setup tool by typing the following command:

    config

  4. Configure the IP address, netmask, and default management route.
  5. Log in to Configuration utility of the new VIPRION system and proceed through the Setup Utility steps, which include activating the new license and provisioning the new VIPRION system. Be sure to provision it the same as the old VIPRION system and click finished under Advanced Network Configuration when the Setup Utility presents this option, so you can re-configure the base or hypervisor configuration in a later step. For more information about licensing the new device, refer to K7752: Licensing the BIG-IP system.
  6. If necessary, upgrade the new VIPRION system at this point. For more information about upgrading, refer to the release notes for your BIG-IP version.

    Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

  7. On the new VIPRION system, re-configure the base configuration or hypervisor configuration that includes the vCMP guest definitions. To do so, you can create a file with the relevant configuration objects documented from the previous configuration and use the merge option with the tmsh load sys config command. For more information, refer to K81271448: Merging BIG-IP configuration objects into the running configuration using tmsh.

    Note: Even though Administrative partitions are synchronized, you must re-configure them to re-configure the partition-specific base configuration, if applicable.

    Note: The ConfigSync operation does not synchronize BIG-IP AFM firewall policies attached to non-floating self IPs addresses, so you must re-configure them on the new VIPRION system. If you re-configure the policies after the migration, you can add synchronized items, such as firewall address lists, firewall port lists, and firewall rule lists.

Deploying and re-configuring the base configuration of the new vCMP guests (vCMP systems only)

To prepare the new vCMP guests for ConfigSync, you must deploy and re-configure the base (non-synchronized) configuration of each. You can also use configuration information from the old guests as a guide.

Impact of procedure: The vCMP guests on the VIPRION system with newly installed blades become unavailable for traffic processing. The re-configured guests do not contain the full BIG-IP configuration until you perform the migration in a later procedure. F5 recommends that you schedule this procedure during a maintenance window to minimize impact in mission critical environments.

  1. Log in to the Configuration utility of the vCMP hypervisor with the new vCMP guests.
  2. Navigate to vCMP > Guest List.
  3. Deploy each vCMP guest, one at a time, by performing the following actions:
    1. Select the check box next to the vCMP guest name.
    2. From the Requested State list, select Deployed and click Update (11.x through 12.x) or click Deploy (13.x and later).
    3. Wait until the vCMP guest is deployed.
    4. If applicable, repeat these steps for each new vCMP guest.
  4. Log in to the Configuration utility of each guest and proceed through the Setup Utility. Provision the guests exactly the same as the guests that you replaced.
  5. Re-configure the base configuration on each new vCMP guest. You can use the configuration merge method described in K81271448: Merging BIG-IP configuration objects into the running configuration using tmsh.

    Note: Even though Administrative partitions are synchronized, you must re-configure them to re-configure the partition-specific base configuration, if applicable.

    Note: The ConfigSync operation does not synchronize BIG-IP AFM firewall policies attached to non-floating self IP addresses, so you must re-configure them on the new VIPRION system. If you re-configure the policies after the migration, you can add synchronized items, such as firewall address lists, firewall port lists, and firewall rule lists.

Setting Device Connectivity options for the new VIPRION system or new vCMP guests

Before you re-configure the existing device trust and device groups, you must configure the connectivity options on the VIPRION system with the newly installed blades or the vCMP guests running on it.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility of the new VIPRION system or new vCMP guest.
  2. Navigate to Device Management > Devices > Device List.
  3. Click the Self device.
  4. Click Device Connectivity (11.x - 12.x).
  5. Click ConfigSync.
  6. From the Local Address menu, select the self IP address for the ConfigSync IP address.
  7. Click Save Changes or Update.
  8. Click Device Connectivity (11.x - 12.x).
  9. Click Network Failover (11.5.x) or Failover Network (11.6.x and later).
  10. To re-configure the method used on the VIPRION system with the blades you replaced, configure Failover Unicast Configuration or Failover Multicast Configuration. For more information about configuring network failover for VIPRION systems, refer to K37361453: Configuring network failover for redundant VIPRION systems (13.x) or K13915: Configuring network failover for redundant VIPRION systems (11.x - 12.x).
  11. Click Device Connectivity (11.x - 12.x ).
  12. Click Mirroring.
  13. Configure the Primary and Secondary Local Mirror Address settings.
  14. Click Save Changes or Update.
  15. If applicable, repeat this procedure for each new vCMP guest.

Optional: Setting Minimum Blades Up on the new VIPRION system or new vCMP guests

You can configure the Minimum Blades Up setting to force a failsafe event. This setting prevents the VIPRION system with the newly installed blades, or vCMP guests on the hypervisor with the newly installed blades, from taking the active role when you add the device or guest to the existing device group.

Impact of procedure: Performing this procedure ensures that standby devices cannot become active due to insufficient available blades in the chassis. F5 recommends that you schedule this procedure during a maintenance window to minimize impact in mission critical environments.

  1. Log in to the TMOS Shell (tmsh) of the new VIPRION system or new vCMP guest by typing the following command:

    tmsh

  2. Set the Minimum Blades Up setting to a number that is greater than the total number of blades in the chassis or guest. For example, in a VIPRION chassis or vCMP guest with four blades, set the Minimum Blades Up setting to 5 by typing the following command:

    modify /sys cluster default min-up-members 5

  3. Enable the Minimum Blades Up setting by typing the following command:

    modify /sys cluster default min-up-members-enabled yes

  4. If applicable, repeat the procedure for each new vCMP guest.

Re-configuring the existing device trust and device group with the new VIPRION system or new vCMP guests

To correctly re-configure the existing device trust and device group, you must first remove the DSC device object that represented the old VIPRION system or old vCMP guests. Then, you can add the new VIPRION system or vCMP guests.

Impact of procedure: After you add the new VIPRION system to the device group, a failover to the new device can occur, unless you have forced the Minimum Blades Up failsafe event described in the previous procedure. Because the new VIPRION system does not contain the full configuration, F5 recommends that you schedule this procedure during a maintenance window to minimize impact in mission critical environments.

  1. Log in to the Configuration utility of an existing VIPRION system or existing vCMP guest that contains the full BIG-IP configuration you want to migrate.
  2. Navigate to Device Management > Device Groups > Device Group List.
  3. Select the device group that includes the device that is being replaced as a member.
  4. In the Include column, select the name of the device that you replaced.
  5. To remove the device and place it in the Available column, click the >> button.
  6. Click Update.
  7. Navigate to Device Management > Device Trust > Peer List (11.x - 12.x) or Device Trust Members (13.x and later).
  8. Select the check box for the device that represented the old instance of the VIPRION system or vCMP guest you replaced.
  9. To remove the selected device from the Local Trust Domain, click Delete.
  10. To confirm, click Delete again
  11. To add the new VIPRION system or new vCMP guest to the Local Trust Domain, click the appropriate Add button.
  12. Ensure Peer is selected for Device Type (13.x and later) then enter the Management IP address, Administrator Username, and Administrator Password of the new VIPRION system or new vCMP guest, and click Retrieve Device Information.
  13. Click Finished.
  14. Navigate to Device Management > Device Groups > Device Group List.
  15. Select the device group for the new VIPRION system to join.
  16. Under the Available column, select the new VIPRION system.
  17. To move the device to the Includes column, click the << button.
  18. Click Update.
  19. If applicable, repeat this procedure for each new vCMP guest.

Migrating the existing BIG-IP configuration to the new VIPRION system or new vCMP guests using ConfigSync

In this procedure, you use ConfigSync to migrate the existing BIG-IP configuration of the device group members to the VIPRION system with the newly installed blades or vCMP guests on the hypervisor with the newly installed blades.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility of an existing VIPRION system or existing vCMP guest that contains the full BIG-IP configuration you want to migrate.
  2. Ensure the system time of the new VIPRION system is synchronized with the existing device group members. For more information, refer to K3122: Using the BIG-IP Configuration utility to add an NTP server.
  3. Navigate to Device Management > Overview.
  4. From the Device Groups list, select the device group where you want to sync the configuration.
  5. In the Devices list, select an existing VIPRION system or existing vCMP guest that has the full BIG-IP configuration you want to migrate to the new VIPRION system or vCMP guest.
  6. In the Sync Options section, select Sync Device to Group (11.x - 12.x) or Push the selected device configuration to the group (13.x and later).
  7. Click Sync.
  8. If you have BIG-IP ASM provisioned, select the datasync-global-dg device group.
  9. In the Devices list, select the same VIPRION system or vCMP guest from step 5.
  10. In the Sync Options section, select Sync Device to Group (11.x - 12.x) or Push the selected device configuration to the group (13.x and later).
  11. If necessary, select the Overwrite Configuration check box.
  12. Click Sync.
  13. If you have BIG-IP AFM provisioned, you can now re-configure AFM policies that did not synchronize due to being attached to non-floating self IPs.
  14. If applicable, repeat the procedure for each new vCMP guest.

Optional: Reverting Minimum Blades Up from the new VIPRION system or new vCMP guests

If you modified the Minimum Blades Up setting in the Optional: Setting Minimum Blades Up on the new VIPRION system or new vCMP guests procedure, you must now revert the changes to release the failsafe condition on the new VIPRION system or new vCMP guests.

Performing failover to the new VIPRION system or new vCMP guests and verifying traffic

After you complete all migration procedures, you can perform failover to the VIPRION system with the newly installed blades or new vCMP guests on the hypervisor with the newly installed blades. This procedure verifies that traffic is flowing normally.

Impact of procedure: If the upstream switch or router cannot quickly update either the Content Addressable Memory (CAM) table or Address Resolution Protocol (ARP) for the new MAC address, service may be disrupted. The F5 MAC masquerade feature can help with this condition. For more information about MAC Masquerade, refer to K13502: Configuring MAC masquerade (11.x - 14.x).

  1. Log in to the Configuration utility of an existing VIPRION system or existing vCMP guest other than the device you most recently replaced.
  2. Verify the new device is the traffic group's Next Active Device by navigating to Device Management > Traffic Groups.
  3. Navigate to Device Management > Devices and select the local VIPRION system or vCMP guest designated with Self.
  4. Select Force to Standby. The new VIPRION system or new vCMP guest should change to active mode.
  5. Log in to the Configuration utility of the new VIPRION system or new vCMP guest you most recently replaced.
  6. Navigate to Statistics > Performance and verify that the connections and throughput statistics match the previous active device.
  7. Test connectivity using the appropriate client software for your applications.
  8. If there are connectivity issues through the new VIPRION system or new vCMP guest, and you need to fail back, navigate to Device Management > Devices and click the local VIPRION system or vCMP guest designated with Self.
  9. Select Force to Standby. The new VIPRION system or new vCMP guest you most recently replaced should change to standby mode.
  10. If applicable, repeat the procedure for each new vCMP guest.

Note: Repeat all procedures for each VIPRION system with blades you plan to replace.
