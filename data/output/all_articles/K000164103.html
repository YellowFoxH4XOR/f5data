K000164103: VELOS Controller Stuck at "Waiting for ConfD" After F5OS-C Upgrade

Type
Support Solution
Published
2026-11-04
Updated
2026-11-04
Applies to
  • F5OS Products
  • F5OS-C: 1.8.X, 1.8.2, 1.8.1, 1.8.0
Source
https://my.f5.com/manage/s/article/K000164103

Description

After an F5OS-C controller upgrade on a VELOS chassis, the standby controller may fail to complete startup and remain at the console prompt Waiting for ConfD. The Kubernetes API on that controller is unreachable, and the active controller cannot complete the upgrade.

Symptoms and log messages:

  • show system image shows the target image as in-progress on the standby controller and pending on the active controller.
  • docker ps -a shows the etcd and api_master containers repeatedly exiting, while the controller-services-registry containers remain running.
  • systemctl status platform-services-deployment.service reports active (exited), but the platform service containers are not running.
  • /var/log_controller/velos.log and /var/log/messages repeatedly show bootevent.sh: ... waiting for the alert service container.
  • Kubernetes reflector errors appear, such as Failed to list *v1.Service: ... dial tcp <controller-services-IP>:8443: i/o timeout.

Environment

  • Product: F5OS-C (VELOS controller)
  • Platform: VELOS chassis with redundant controllers
  • Conditions:
    • The standby controller imported a controller software image that the active controller did not import, because /var/export/chassis exceeded the 40% software-import utilization threshold.
    • A stale controller-services registry entry for the obsolete version remained in /var/import/import.json on the standby controller and was assigned port 2508.
    • The active controller later assigned port 2508 to the new controller-services registry. The standby controller accepted this assignment without detecting that port 2508 was already in use locally.
    • After reboot, port 2508 was backed by the obsolete registry, which did not contain the chassis-gui image required by the target version. Platform-services deployment failed.

Cause

  • Duplicate controller-services registry port assignment on the standby controller. The standby controller accepts a registry port from the active controller even when that port is already in use locally. Bug ID Bug ID 2014413 tracks this issue, and the fix is planned for a future F5OS-C release.
  • An image may still be imported on the standby controller even when the active controller import fails due to insufficient disk space. Bug ID Bug ID 2693653 tracks this issue, and the fix is planned for a future release.

Early Warning

Before starting an upgrade, check the image status on both controllers. A controller that failed to import an image displays a "Volume usage limit reached" message in both the GUI and show image output.

Recommended Actions

Workaround and recovery (perform on the affected standby controller only):

  1. Open an SSH session to the affected controller over the ccpeer link.
  2. Stop the software management service and back up import.json:

    systemctl stop sw-mgmt.service

    cp /var/import/import.json{,.bak}

  3. Remove the obsolete image from staging:

    chattr -i /var/import/staging/<obsolete-image>.iso

    rm -vf /var/import/staging/<obsolete-image>.iso

  4. Edit /var/import/import.json to remove all references to the obsolete version. Make sure the JSON remains valid after the edit, for example by removing the trailing comma from the preceding entry. Verify the affected lines on your system before editing.
  5. Set ccsync to standby mode:

    echo standby > /etc/ccsync/mode.conf

  6. Reboot the controller:

    reboot

  7. After the reboot, verify that the platform services started without image pull errors:

    journalctl -b -u sw-mgmt.service -u platform-services-deployment.service --no-pager

    Add -f to monitor in real time.

If the issue persists, collect a host-only qkview from the affected controller and contact F5 Support.

Preventive measures (until running a fixed release):

  • Verify that the software images in /var/import/staging are synchronized between both controllers.
  • Remove older, unused images as part of routine housekeeping.
  • Keep /var/export/chassis below the 40% software-import utilization threshold.
  • Check /var/import/import.json for duplicate port assignments before starting an upgrade, especially where the duplicate relates to the current or target software version.

Additional Information

  • The repeated waiting for the alert service container message in the boot logs is expected when platform services fail to start. It indicates a loop in bootevent.sh and does not identify the root cause by itself.
  • Restarting platform-services-deployment.service or rebooting the controller alone may not resolve the issue. Correcting the registry configuration in import.json and removing the stale image may be required.
