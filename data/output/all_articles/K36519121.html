K36519121: ElasticSearch shard in index ''.opendistro_security'' shows ''UNASSIGNED''

Type
Support Solution
Published
2022-05-13
Updated
2025-04-02
Applies to
  • BIG-IQ
Source
https://my.f5.com/manage/s/article/K36519121

Description
The only ElasticSearch shard in index ".opendistro_security" shows "UNASSIGNED" on one or more nodes in the cluster. For example, when querying for shards list using ElasticSearch REST API:

# curl -s -k https://localhost:9200/_cat/shards | grep opendistro_security
.opendistro_security    0     p    STARTED    5  27.7kb 192.168.3.12 e91fd2d2-d1dc-11ec-9d64-0242ac120002
.opendistro_security    0     r    STARTED    5  27.7kb 192.168.3.13 e91fd55c-d1dc-11ec-9d64-0242ac120002
.opendistro_security    0     r    STARTED    5  27.7kb 192.168.3.14 e91fd688-d1dc-11ec-9d64-0242ac120002
.opendistro_security    0     r    STARTED    5  24.9kb 192.168.3.15 e91fd7e6-d1dc-11ec-9d64-0242ac120002
.opendistro_security    0     r    STARTED    5  27.7kb 192.168.3.16 e91fda98-d1dc-11ec-9d64-0242ac120002
.opendistro_security    0     r    STARTED    5  27.7kb 192.168.3.17 e91fdbc4-d1dc-11ec-9d64-0242ac120002
.opendistro_security    0     r    UNASSIGNED

Environment

  • BIG-IQ with DCD
  • DCDs are assigned to two or more zones

Cause
The index ".opendistro_security" contains one shard only. The index setting "auto_expand_replicas" is configured to "0-all" by default on this index, which means all data nodes (DCDs) in the cluster should contain a copy (primary copy or replica copy) of the shard in the index.

When DCDs are assigned to two or more zones, and the numbers of DCDs in each zone are unbalanced, the replica may not be allocated on the DCD residing in a zone with more nodes than other zones. This behaviour is described in the following ElasticSearch document.

"The number of attribute values determines how many shard copies are allocated in each location. If the number of nodes in each location is unbalanced and there are a lot of replicas, replica shards might be left unassigned."

https://www.elastic.co/guide/en/elasticsearch/reference/current/modules-cluster.html

In this example, the DCD cluster contains 7 DCDs that reside in 2 zones in an unbalanced distribution. One zone contains 5 DCDs and the other zone contains 2 DCDs.

Zone1: 192.168.3.12; 192.168.3.13; 192.168.3.14; 192.168.3.17; 192.168.3.18
Zone2: 192.168.3.15; 192.168.3.16

The output of the shard allocation explain API tells us that the maximum number of shard copies for each zone can not exceed the ceiling value of number of "total shard copies" divided by the number of "total attribute value".

In this example, the number of "total shard copies" is 7 because there are 7 DCDs and the index setting "auto_expand_replicas" is configured to "0-all", the number of  "total attribute value" is 2 because all DCDs are split into 2 zones. The ceiling division result of these two values is 4. Therefore the allocated shard count per zone cannot be larger than 4. For zone1 which contains 5 DCDs, only 4 of them can have one allocated copy of shard, the other DCD in the same zone will be left and the status of the shard on it will be "UNASSIGNED".

Recommended Actions

  1. The "UNASSIGNED" shard of index ".opendistro_security" is an expected behaviour if the DCDs are assigned to two or more zones in an unbalanced way. It can be safely ignored if the number of shard copies in each zones is sufficient to recover the shard from loss of nodes in their residing zones respectively.
  2. The "UNASSIGNED" replica shard will be allocated to all DCDs if the DCD nodes distribution among zones becomes more balanced (for example, 4 DCDs in zone1 and 3 DCDs in zone2, instead of 5 DCDs in zone1 and 2 DCDs in zone2).
