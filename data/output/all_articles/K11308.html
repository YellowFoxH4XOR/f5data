Topic

The BIG-IP APM adtest tool can be used to test query and authentication to an Active Directory server. The basic syntax of the command can be viewed by typing adtest from the command line. Output appears similar to the following example:

[root@apm_01:Active] config # adtest

usage: adtest [options]
-t test type[auth|query|chgpswd]
-n test number[default: 1]
-c concurrency[default: 1]
-d debug [default: 0] *
-T timing *
-h hostname
-p port **
-r realm
-A adminName
-C credential cache file name
-W adminPassword
-N New Password
-u userName
-M machineName *
-O operatingSystemName *
-V operatingSystemVersion *
-E machineDescription *
-D userDomain *
-w userPassword
-a include pre-authentication data *
-s new password against domain password *
-g fetch group[true|false]
-G nested groups
-P password expiration time *
-U enableUPN[true|false]
-f filter[default: 'sAMAccountName=<userName>']
-F filename (required to dump all domain groups with test type 'groups')

* Added feature flags starting in BIG-IP 11.4.0.

** Starting with BIG-IP 11.5.0, the -p flag (alternate Active Directory server port) is no longer available. For example:

    adtest -t auth -r "siterequest.com" -u user1 -w 123456
    adtest -t auth -r "siterequest.com" -U true -u user1 -D user.domain.com -w 123456
    adtest -t auth -h "host.siterequest.com" -r "siterequest.com" -u user1 -w 123456
    adtest -t query -h "host.siterequest.com" -r "siterequest.com" -A Administrator -W password1\!a -u user1
    adtest -t query -h "host.siterequest.com" -r "siterequest.com" -A Administrator -W password1\!a -g -G -u user1
    adtest -t query -h "host.siterequest.com" -r "siterequest.com" -A Administrator -W password1\!a -u user1 -D user.domain.com
    adtest -t chgpswd -h "host.siterequest.com" -r "siterequest.com" -u user1 -w 123456 -N abcdef
    adtest -t join -h "host.siterequest.com" -r "siterequest.com" -A Administrator -W password1\!a -M myserver -O TMOS -V 11.3.0 -E BIG-IP
    adtest -t chgmpswd -h "host.siterequest.com" -r "siterequest.com" -M myserver -w machineAccountPassword

Note: Starting with BIG-IP 11.5.0, the -p flag (alternate Active Directory server port) is no longer available.

For example:

adtest -t auth -r "example.com" -u jones -w 123456
adtest -t auth -r "example.com" -U true -u jones -D user.domain.com -w 123456
adtest -t auth -h "host.example.com" -r "example.com" -u jones -w 123456
adtest -t query -h "host.example.com" -r "example.com" -A Administrator -W password1\!a -u jones
adtest -t query -h "host.example.com" -r "example.com" -A Administrator -W password1\!a -g -G -u jones
adtest -t query -h "host.example.com" -r "example.com" -A Administrator -W password1\!a -u jones -D user.domain.com
adtest -t chgpswd -h "host.example.com" -r "example.com" -u jones -w 123456 -N abcdef
adtest -t join -h "host.example.com" -r "example.com" -A Administrator -W password1\!a -M myserver -O TMOS -V 11.3.0 -E BIG-IP
adtest -t chgmpswd -h "host.example.com" -r "example.com" -M myserver -w machineAccountPassword

The auth test type tests authentication. Active Directory authentication does not require administrative credentials. For example:

adtest -t auth -h "adserver.example.com" -r "exampledomain.local" -A Administrator -W password123 -u jones -w letmein
Test done: total tests: 1, success=1, failure=0

The administrator credentials provided were unnecessary. If you run the same command with incorrect administrative credentials, the command still provides a successful result. For example:

adtest -t auth -h "adserver.example.com" -r "exampledomain.local" -u jones -w letmein
Test done: total tests: 1, success=1, failure=0

However, administrative credentials are required for a query to succeed. The following is an example of a query command sent with improper credentials:

adtest -t query -h "adserver.example.com" -r "exampledomain.local" -A Administrator -W invalidpassword -u jones -w letmein
ERROR: query with '(sAMAccountName=jones)' failed in krb5_get_init_creds_password(): Preauthentication failed, principal name: administrator@EXAMPLEDOMAIN.LOCAL (-1765328360)
Test done: total tests: 1, success=0, failure=1

The same command with proper credentials show the following results:

adtest -t query -h "adserver.example.com" -r "exampledomain.local" -A Administrator -W password123 -u jones -w letmein
Test done: total tests: 1, success=1, failure=0

If a query attempt yields the following error message, either the Active Directory domain controller is not resolving through DNS, or is not properly configured:

ERROR: query with '(sAMAccountName=student1)' failed in ldap_sasl_interactive_bind_s(): Local error, SASL(-1): generic failure: GSSAPI Error: Unspecified GSS failure. Minor code may provide more information (Cannot find KDC for requested realm) (-2)

Check the /etc/krb5.conf file for the domain controller for the domain. For example:

EXAMPLEDOMAIN.LOC = {
kdc = 172.16.20.20
admin_server = 172.16.20.20
}

The krb5.conf file should be automatically updated when an Active Directory server object is defined and used in an access policy.

Starting with BIG-IP 13.1.1, a groups option exists for the adtest command.

For example:

adtest -t groups -S /Common/ADResource -F testfile
Test done: total tests: 1, success=1, failure=0

Note: The example adtest command writes the  file  /shared/tmp/testfile containing the AD groups for ADResource.

The debug (d) option

Use of the debug setting ( -d 1 ) displays verbose information about authentication and the user account.

Depending on you Active Directory configuration, the following user account details may be supplied when using the debug option.

Note: The numeric value used for the debug option only toggles the debug option. Higher numeric values do not modify the debug verbosity.
