K000089435: Requests blocked due to attack signatures detected, when set to "block": false

Type
Support Solution
Published
2021-06-23
Updated
2021-06-23
Source
https://my.f5.com/manage/s/article/K000089435

Description

Requests blocked due to attack signature being detected, when the attack signature set block flag is set to false. 

For example:

{
  "name": "High Accuracy Signatures",
  "block": false,
  "alarm": true
}
Environment
  • NGINX App Protect
  • Attack signatures

Cause

This is the expected behaviour by default. Requests are blocked based on the Violation Rating of the request, all violations that are in alarm mode contribute to the evaluated risk of the request. So it may be sufficient for an an attack signature that is in alarm only to cause a blocked request, if the violation rating is high.

Recommended Actions

If a specific signature is causing a false positive, it is recommended to disable that particular signature, so the rest of the signatures in the set can still be retained.

Additional Information

App Protect may detect an attack signature even if that set is not explicitly configured in the policy. The default policy includes a number of signature sets:

  • Command Execution Signatures
  • Cross Site Scripting Signatures
  • Directory Indexing Signatures
  • Information Leakage Signatures
  • OS Command Injection Signatures
  • Path Traversal Signatures
  • Predictable Resource Location Signatures
  • Remote File Include Signatures
  • SQL Injection Signatures
  • Authentication/Authorization Attack Signatures
  • XML External Entity (XXE) Signatures
  • XPath Injection Signatures
  • Buffer Overflow Signatures
  • Denial of Service Signatures
  • Vulnerability Scanner Signatures
  • High Accuracy Signatures
  • All CVE Signatures

To remove a particular signature set, the following solution can be used:

{
   "$action" : "delete",
   "name" : "High Accuracy Signatures"
}

Alternatively, setting both alarm and block to false should be functionally equivalent. If a given set is removed with "$action" : "delete" in all policies, and the default policy is not in use (for example, by not specifying a policy with the app_protect_policy_file directive), then that signature set is not compiled, which is nominally more CPU efficient.
