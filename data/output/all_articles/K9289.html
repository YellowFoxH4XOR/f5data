K9289: Firewall connections may fail if asymmetrically routed by the ARX

Topic

The ARX supports a single default route, which may be an issue in a multi-VLAN network with certain firewall configurations. When clients connect to the ARX through firewalls sharing multiple VLANs with the ARX, the connections may fail. The ARX does not ensure that responses to clients will egress out the same VLAN on which it was received. The ARX will select the egress VLAN based on the response destination IP addresses using the route tables. Depending on the firewall configuration, the firewall may drop asymmetric routed traffic.

For example, a client connects to ARX through a firewall that is in VLAN_B. The firewall is expecting the response back to the same interface as the request was sent. However, per the route tables, the ARX returns the response to the default gateway, which is on VLAN_A. The firewall determines that the response does not match a request for VLAN_A, and blocks the traffic.

F5 Product Development tracked a request for enhancement (RFE) as ID 31240 to support a separate default route for each client VLAN. Beginning in ARX version 4.1.0 the per-vlan option for the ip route command was introduced to provide this functionality. For information about the per-vlan option for the ip route command, refer to the ARX CLI Reference Guide.

Workaround

You can work around this issue in ARX versions previous to version 4.1.0 by ensuring that all firewall connections are routed to ingress the ARX using a single VLAN, or by configuring the firewall to allow asymmetric routed traffic.
