Topic

F5 added the platform-migrate option to the tmsh load sys ucs command which enables you to migrate configurations from older platforms to newer platforms using an existing user configuration set (UCS) file. The new platform can be a newer generation hardware device, an F5OS tenant, a Virtual Clustered Multiprocessing (vCMP) guest, or BIG-IP Virtual Edition (VE).

In BIG-IP 21.1.0, the validate feature was introduced as an integral enhancement for the platform-migrate option. It ensures that the UCS is checked for platform compliance and logs any unsupported configurations or modifications that occur during the migration process.

Description

F5 introduced the platform-migrate option to better facilitate cross-platform configuration migrations. In previous versions, you can create a UCS on one platform type and install it on another using the no-platform-check option. However, the no-platform-check option installs the base configuration, so it may not be optimal when installing to different platforms.

You can enable the option using the following TMOS Shell (tmsh) command syntax:

tmsh load sys ucs <filename> platform-migrate

The platform-migrate option causes the UCS loader to ignore some platform dependent configuration objects when installing the UCS configuration. For example, when you install a UCS file using this option, configuration objects related to the following items may not be installed from the UCS file:

  • Interfaces
  • Interface bundles
  • Management IP and route
  • Assignments to trunks and VLANs
    For example, a trunk is loaded on the new platform but interfaces, interface bundles, and VLANs assigned to it previously are not loaded.

Note: When you install a UCS file using platform-migrate, the system saves a list of any configuration objects that it ignores or does not install to the /var/local/ucs/platform_migrate_ignored_objects file.

Validate option

The validate option, paired with the platform-migrate option, helps identify potential configuration incompatibilities when migrating UCS files from one platform to another. It performs validation of platform-specific settings and logs ignored or removed properties, ensuring the migration process does not carry unsupported configurations onto the new platform. This ensures the loaded UCS conforms to the hardware or system properties of the destination platform.

You can validate the UCS compatibility using the following command syntax:

tmsh load sys ucs platform-migrate validate

The validation option provides the following key features:

  • Validation Before Installation:
    • The command examines platform-specific configurations in the UCS file and detects unsupported objects or properties before final installation.
  • Detailed Warning Output:
    • During the UCS loading process, warnings are displayed indicating configurations that are removed for non-compliance.

      The following example warnings indicate incompatibilities with the network configuration:

      Network failover settings incompatible with the target platform removed
      Unsupported STP mode removed.
      Unsupported LACP configurations stripped during the migration.

  • JSON Log Summary:
    • A detailed log summary is stored in JSON format in the /var/log/platform_migrate_validate.log file. Among other details, this log file includes:
      • Properties ignored or removed during validation.
      • Objects skipped due to incompatibilities.
      • UCS file details and validation timestamps.

Limitations

When using platform-migrate, consider the following limitations:

  • The platform-migrate option does not work for migrating BIG-IP UCS files from BIG-IP 10.x. If you are migrating the BIG-IP system, you must start with a BIG-IP configuration from a BIG-IP 11.x installation.
  • After you load the UCS using platform-migrate, you may need to perform extra steps to get the device fully functional.

    For example:

    • You may need to reassign your new interfaces to VLANs.
    • In a high-availability (HA) environment, you may need to synchronize the configuration (enter configsync).
    • You may need to rebuild your device group if your new device's management IP address is changing as part of the migration. You can specify the keep-current-management-ip option to the load sys ucs command to keep the current management IP when you restore the UCS archive. For more information, refer to K000132494: Overview of the UCS archive 'keep-current-management-ip' option.
    • HA group configurations may fail to properly migrate as the objects being monitored, such as trunks and VIPRION clusters are not present on the destination system. As such, you may choose to remove any HA group configuration from the UCS prior to migration and rebuild it on the destination system.

      Note: Beginning in BIG-IP 21.1.0, HA Groups have their trunks removed from the configuration when migrating to tenants on VELOS and rSeries systems.

  • If you use platform-migrate to bring up a new F5OS tenant or vCMP guest, you configure the trunk (also known as LAG in F5OS) and VLANs from the host.
  • If the management IP address on the old platform used Dynamic Host Configuration Protocol (DHCP) relay, and you use platform-migrate, the management address of the new platform changes to use DHCP.

    Note: Beginning in BIG-IP 21.1.0, management interface DHCP settings on the old platform are ignored when you use the platform-migrate option.

Recommended Action

Consider using platform-migrate if you are migrating from old or obsolete BIG-IP appliances to a newer platform family. F5 recommends that you use the platform-migrate option for:

  • BIG-IP appliance-to-appliance migration
  • BIG-IP appliance to BIG-IP Virtual Edition (VE)
  • BIG-IP appliance-to-vCMP guest migration
  • BIG-IP appliance-to-F5OS tenant migration
  • F5OS tenant-to-tenant migration
  • vCMP guest-to-guest migration

Procedures

To complete a platform migration using the platform-migrate option, perform the following procedures:

  • Saving UCS files on the device to be replaced
  • Prepare UCS files that include trunk objects to be loaded on vCMP guest/F5OS Tenants
  • Validate UCS compatibility on the new device
  • Loading UCS configurations on the new device
  • Resolving issues

Saving UCS files on the device to be replaced

Important: If your configuration contains DNSSEC keys and you are running BIG-IP version prior to 16.0.0, do not use tmsh modify sys crypto master-key. Use the workaround provided in ID 639606.

  1. Log in to tmsh of the device you are replacing by entering the following command:

    tmsh

  2. Reset the master key based on a password you choose (remember this password because you'll need to use it on the destination device). This action will re-encrypt all passwords and passphrases in the BIG-IP configuration with the new master key.

    modify sys crypto master-key prompt-for-password

  3. Save the configuration change:

    save sys config

  4. (Optional) View the new master key using the following command:

    f5mku -K

  5. Create the UCS file using the following command syntax:

    save sys ucs <file name>

  6. Copy the UCS file to an offline location.
  7. On the device you are replacing, force it offline by entering the following command:

    run sys failover offline

    This ensures that the system moves the traffic to the other device before shutting it down.

  8. Shut down the old device.

Prepare UCS files that include trunk objects to be loaded on vCMP guest/F5OS Tenants

If the old device configuration includes trunk objects and the new device is either vCMP guest or F5OS tenant, perform the Recommended Actions section steps in K50152613 before proceeding to the next step.

Validate UCS compatibility on the new device

To identify potential configuration incompatibilities in the UCS before loading it to the new device, perform the following procedure:

  1. Copy the UCS file that you prepared on the old device, to the new device. You can do this using the Configuration utility by going to System > Archives > Upload or by manually uploading the configuration to the /var/local/ucs directory on the new device.
  2. Log in to tmsh by entering the following command:

    tmsh

  3. Validate the UCS file with tmsh using the following command were <filename> is the name of the UCS file:

    load /sys ucs <filename> no-license platform-migrate validate


    If the platform-migrate validate command completes successfully, the system displays a message with the UCS configuration incompatibilities similar to the following example:

    Warning: Removing trunk (trunk1) because it is not supported on platform Z101
    Warning: platform-dependent objects like interfaces, interface bundles, Management IP and route, assignments to trunks and VLANs are not reported with the validate option
    Validation complete. Details saved to: /var/log/platform_migrate_validate.log

Loading UCS configurations on the new device

Important: Before you load the configuration on the new device, you must first license, provision, and manually configure the low-level configuration on the new system. Before installing the UCS configuration, use tmsh or the Configuration utility to configure the management IP address (unless you are using DHCP) and configure the interface settings required for your environment.

To load the UCS configuration onto the new device, perform the following procedure:

  1. Copy the UCS file that you prepared on the old device, to the new device, if you haven't already done so.

    You can do this using the Configuration utility by going to System > Archives > Upload or by manually uploading the configuration to the /var/local/ucs directory on the new device.

  2. Log in to tmsh by entering the following command:

    tmsh

  3. Set the master key on the new device using the password you used in the previous procedure. The same password will generate the same master key. Use the following command:

    modify sys crypto master-key prompt-for-password

    Important: If you configured the management IP address of the new device to use a static IP address, and the old device used DHCP, the management IP address may change when you load the UCS using the platform-migrate option. Make sure you have appropriate console access available that does not require that you use the management IP address.

  4. Save the configuration change:

    save sys config

  5. (Optional) View the new master key. It should be the same as the master key you generated on the old device. Use the following command:

    f5mku -K

  6. Load the UCS file from tmsh by entering the following command:

    load /sys ucs <filename> no-license platform-migrate

    If the platform-migrate command completes successfully, the system displays the following message:

    Platform migrate loaded successfully. Saving configuration.

  7. Confirm that the system is in the running state by entering the following command:

    show sys mcp

    The system displays the following message:

    ---------------------------------------------------------
    Sys::mcpd State:
    ---------------------------------------------------------
    Running Phase running
    Last Configuration Load Status full-config-load-succeeded

  8. Confirm the new device joined the trust group and is in Standby mode. If your management IP address changes, you must reconfigure the Failover Unicast address so that it matches the management IP address.
  9. Bring the new device back online in the HA configuration by entering the following command:

    run sys failover online

Resolving issues

While installing a UCS with the platform-migrate option greatly reduces the time it takes to migrate from an old or obsolete platform to a new one, installing a UCS with the platform-migrate option does not guarantee that the configuration will successfully load on the new system. You may encounter errors if you do not create the low-level configuration in advance. If you encounter an error, review the error message, make the appropriate changes, and then run the command again.

Warning: The system is not in a running state after it produces an error, and the system will not save the configuration changes.

If the platform-migrate command fails, Master Control Program (MCP) is placed in a non-running state; enter the following command to check the MCP state:

tmsh show sys mcp

This command indicates that the running phase is called platform and the load status is high-config-load-failed.

Example output:

# tmsh show sys mcp
---------------------------------------------------------
Sys::mcpd State:
---------------------------------------------------------
Running Phase platform
Last Configuration Load Status high-config-load-failed

Therefore, the command tmsh save sys config fails to save the configuration and generates an error message. As you add the required low-level configuration objects, note that until the platform-migrate command succeeds, you can change the configuration, but you cannot save it.
