Description

Cross-site scripting (XSS) is a security vulnerability usually found in web applications. An application vulnerable to XSS is one that allows an attacker to inject malicious client-side scripts into the application that are then executed by the web browser of an unsuspecting, legitimate user.

Environment

  • A web application being delivered to a web browser on a client device.

    Examples: Google Chrome, Microsoft Edge, Firefox, and so on.

Cause

  • A web application that does not properly sanitize untrusted input.

Recommended Actions

You can mitigate XSS attacks against a web application using BIG-IP Advanced WAF, BIG-IP ASM, NGINX App Protect, Silverline WAF, and so on to block potentially malicious payloads from being ingested and interpreted by the web application to be protected. Specific instructions are outside of the scope of this document as any policy must be tailored to the web application in question.
 
If you are concerned about a known XSS vulnerability in the Configuration utility, the best mitigation is to ensure your administrators:

  • Access the Configuration utility from a dedicated management host, jump box, or another controlled environment.
  • Do not click links to access the Configuration utility but rather enter the address manually or use a bookmark.

Additional Information

XSS most commonly refers to attacks involving injected JavaScript code but can also extend to the injection of any potentially malicious code (ActiveX, Flash, HTML) which will be executed within the target user's browser. There are three main types of XSS attack, which we will briefly cover here. For more detailed information, see the links in the Related Content section of this article:

  • Reflected (non-persistent) XSS
  • Stored (persistent) XSS
  • DOM-based XSS

Reflected (or non-persistent) XSS

The most basic form of XSS vulnerability is reflected or non-persistent XSS. Here, malicious code is sent to a web application by the target browser and immediately reflected back to the user and executed on the client side; this is usually done using HTTP query parameters (for example: form submission) which are parsed on the server-side and then reflected back in the resulting page.

For example: Imagine there is a search page that accepts requests in the form http://example.com/search.php?search=foo, where “foo” is the string being searched for. The resulting page displays a banner that says, “Results for your search for foo.”

If the server does not properly sanitize inputs, it may be possible to pass JavaScript in the search parameter that is subsequently reflected back in the results page and executed on the client side.

For example:
http://example.com/search.php?search=<script>alert(“Hello!”)</script>

If this JavaScript were echoed back and parsed by the client browser, a pop-up window would appear.

Executing this attack requires an attacker to construct a malicious link and deliver it to the target user, perhaps via email, and the attack is unlikely to simply pop up a window but could be used to steal cookies, redirect the user to a malicious web application to execute a more realistic phishing attack, and so on.

Stored (or persistent) XSS

Stored XSS attacks can be much more effective than the simple reflected example above, though the basic principle is the same – the attacker provides script (for example: JavaScript) that is sent back to the target victim and executed within the context of their browser.

Unlike the reflected attack, however, the attacker does not necessarily need to trick their victim into clicking a malicious link. Instead, they are able to store their malicious code within the vulnerable web application and have it delivered to one or many target victims whenever they visit the application; imagine, for example, a guest book where visitors can leave anonymous messages for any subsequent visitors to read. If the web application does not properly sanitize input and allows an attacker to leave JavaScript in their guest book message, that script will be delivered to every subsequent visitor.

DOM-based XSS

First, the DOM is the Document Object Model, an object representation of the browser environment containing the currently rendered page.

DOM-based XSS is an attack in which the attack payload is executed as a result of modifying the DOM environment entirely within the browser on the client side, whereas reflected and stored XSS are attacks in which the attack payload is inserted on the server side.

This attack relies on the modern web's focus on using JavaScript to programmatically and dynamically construct pages on the client side (originally called “Web 2.0”) rather than relying on traditional static rendering, and here the attacker must find a place to insert their malicious code that will be subsequently consumed by legitimate application code and thereby alter the behavior of the application for the victim user.

Mitigations

The mitigation for all XSS attacks is to properly sanitize untrusted user inputs whenever they are consumed by the web application. For example:

  • Ensure all inputs are escaped (where special characters will be translated into HTML entities).
  • Ensure dynamic changes to the DOM HTML also JavaScript encode inputs prior to use.

You can also use a Web Application Firewall such as BIG-IP Advanced WAF, BIG-IP ASM, NGINX App Protect, and so on to:

  • Check inputs against signatures of known generic XSS methods.
  • Check inputs against signatures of known vulnerabilities in web frameworks and applications.
  • Block inputs that contain denylisted characters or allow only allowlisted characters.

A combination of both methods for a Defence-in-Depth posture is highly recommended.
