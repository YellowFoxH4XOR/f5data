Configuring BIG-IP nPath Routing (DSR) for UDP/DNS Load Balancing

Description

This article describes how to configure BIG-IP nPath routing (also known as Direct Server Return or DSR) for UDP/DNS load balancing. In this topology, BIG-IP receives client DNS requests, selects a pool member, and forwards the packet using Layer 2 MAC rewrite only — without modifying the Layer 3 destination IP address. The backend DNS server replies directly to the client, bypassing the BIG-IP on the return path.

This behavior is referred to as nPath routing in F5 documentation. It is also known as asymmetric routing or Direct Server Return (DSR).

Reference: For the official F5 nPath configuration guide, refer to K11116: Configuring nPath routing.

Environment

  • BIG-IP LTM (physical, virtual, or tenant)
  • BIG-IP version 13.1.x and later
  • FastL4 profile
  • UDP/DNS traffic (port 53)
  • Backend DNS servers (Linux-based) on the same L2 segment as the VIP
  • Virtual server with translate-address disabled and translate-port disabled

Prerequisites

  • BIG-IP must have a self-IP on the same subnet as the VIP and pool members
  • Backend DNS servers must be Linux-based (or equivalent OS supporting loopback IP configuration)
  • Client, BIG-IP VIP, and backend DNS server must be on the same L2 segment (for L2 nPath)
  • No SNAT configured on the virtual server

BIG-IP Configuration

Step 1: Create FastL4 Profile

Important: Per K42623065, loose-close enabled is strictly required for nPath deployments on BIG-IP 13.1.5 and later, including 17.x. Failure to enable this will cause connection issues for TCP-based DSR. For UDP/DNS it is still recommended for consistency.
tmsh create ltm profile fastl4 /Common/fastL4_nPath \
    defaults-from /Common/fastL4 \
    loose-close enabled \
    loose-initialization enabled \
    idle-timeout 120 \
    reset-on-timeout enabled \
    syn-cookie-enable enabled \
    tcp-close-timeout 5 \
    tcp-handshake-timeout 5

Step 2: Create Pool

tmsh create ltm pool /Common/DNS_pool \
    members add { 10.x.x.1:53 { address 10.x.x.1 } } \
    monitor gateway_icmp \
    min-active-members 1

Step 3: Create Virtual Server

tmsh create ltm virtual /Common/f5dns01-vip \
    destination 10.x.x.37:0 \
    mask 255.255.255.255 \
    pool /Common/DNS_pool \
    profiles add { /Common/fastL4_nPath { } } \
    persist replace-all-with { source_addr { default yes } } \
    translate-address disabled \
    translate-port disabled \
    source 0.0.0.0/0
Note: destination port 0 means the virtual server accepts all ports. translate-address disabled and translate-port disabled are the key settings that enable nPath/DSR behavior — BIG-IP will only rewrite the L2 MAC address, not the L3 destination IP.

Step 4: Save Configuration

tmsh save sys config

Verification

1. Confirm ARP and Pool Status on BIG-IP

# ARP must show resolved for pool member
tmsh show net arp | grep 10.x.x.1

# Pool member must be up
tmsh show ltm pool DNS_pool members

# Virtual server must show traffic incrementing
tmsh show ltm virtual hif5dns01-vip

2. Connection Table — Understanding nPath DSR Behavior

Important — Expected Behavior: In an nPath/DSR configuration, querying the connection table by pool member IP ss-server-addr <pool_member_ip> will NOT show client-originated connections. This is expected and correct. The only entries visible against the pool member IP are health monitor connections Type: self. Client traffic connections are only visible when querying by VIP IP.cs-server-addr <vip_ip>

Query by Pool Member IP — Shows Monitor Traffic Only (Expected)

tmsh show sys connection ss-server-addr 10.x.x.1

Example output — all entries show Type: self (monitor traffic only):

root@(localhost)(tmos)# show sys connection ss-server-addr 10.x.x.1 all-properties
Sys::Connections
10.x.x.3:60796 - 10.x.x.1:53 - 10.x.x.3:53195 - 10.x.x.1:53
----------------------------------------------------------------------
  TMM           1
  Type          self          <-- BIG-IP health monitor, NOT client traffic
  Acceleration  none
  Protocol      udp
  Idle Timeout  30
  Virtual Path  10.x.x.1:53
                      ClientSide        ServerSide
  Client Addr  10.x.x.3:60796    10.x.x.3:53195
  Server Addr     10.x.x.1:53       10.x.x.1:53
  Bits In                376               320
  Bits Out               320               376
  Packets In               1                 1
  Packets Out              1                 1

Total records returned: 6   <-- All 6 are monitor connections, zero client connections
Why no client connections appear here: With translate-address disabled, BIG-IP does not perform L3 NAT on the destination IP. The server-side of the connection table records the VIP IP as the destination, not the pool member IP. Therefore, filtering by pool member IP returns no client traffic entries.

Query by VIP IP — Shows Actual Client Traffic (Correct Method for nPath)

tmsh show sys connection cs-server-addr 10.x.x.37

Example output — client connections visible with VIP IP preserved on server-side:

root@(localhost)(tmos)# show sys connection cs-server-addr 10.x.x.37
Sys::Connections

End-to-End Verification Test

Run the following sequence to confirm DSR is working end-to-end:

# Step 1: Clear all connections (clean baseline)
tmsh delete sys connection all

# Step 2: From client, send DNS query to VIP
dig @10.x.x.37 www.example.local

# Expected client output:
# ;; Got answer:
# ;; ANSWER SECTION:
# www.example.local.  604800  IN  A  x.x.x.x
# ;; Query time: 4 msec
# ;; SERVER: 10.x.x.37#53

# Step 3: Immediately check connection table on BIG-IP
tmsh show sys connection cs-server-addr 10.x.x.37
# Expected: 1 entry with client IP and VIP IP on both sides

tmsh show sys connection ss-server-addr 10.x.x.1
# Expected: 0 client entries (monitor entries only)

Confirmed working output from lab validation:

# BIG-IP timestamp: Tue May 19 09:52:38 PDT 2026
# Client timestamp: Tue May 19 16:52:39 UTC 2026 (same time, different TZ)

# Client received valid DNS response in 4ms:
# www.example.local.  604800  IN  A  x.x.x.x

# BIG-IP connection table (cs-server-addr VIP):
10.x.x.34:50490  10.x.x.37:53  10.x.x.34:50490  10.x.x.37:53  udp  1  (tmm: 3)  none  none
Total records returned: 1   <-- Client connection visible via VIP

# BIG-IP connection table (ss-server-addr pool member):
Total records returned: 0   <-- No client entry -- EXPECTED for nPath/DSR

3. Packet Capture — Confirm L2 Rewrite and L3 Transparency

# On BIG-IP — capture with MAC addresses on TMM interface
tcpdump -i 0.0:nnnp -evnn -s0 host 10.x.x.37

# Expected output shows:
# Packet 1 (inbound):  ClientMAC > BIG-IP_MAC  SrcIP=Client  DstIP=VIP
# Packet 2 (outbound): BIG-IP_MAC > ServerMAC  SrcIP=Client  DstIP=VIP (unchanged)
Note on PVA hardware acceleration: On platforms with PVA (r-series, VELOS blades), flows are offloaded to hardware after the first packet. Subsequent packets in the same flow will not appear in tcpdump output. This is expected behavior — use the connection table for ongoing verification instead.

Key Configuration Parameters

ParameterRequired ValueReason
translate-addressdisabledPrevents BIG-IP from rewriting L3 destination IP — core DSR requirement
translate-portdisabledPrevents BIG-IP from rewriting L4 destination port
loose-close (FastL4)enabledRequired on 13.1.5+ / 17.x — BIG-IP never sees return traffic in DSR
loose-initialization (FastL4)enabledRequired for TCP DSR — BIG-IP never sees SYN-ACK. Not critical for UDP.
