K000092378: Missing client certificate during SSL handshake results in Nginx returning HTTP 400 response code - Bad Request page

Type
Support Solution
Published
2022-09-17
Updated
2022-09-17
Source
https://my.f5.com/manage/s/article/K000092378

Description

  • You configure Nginx to verify and validate client certificate before granting access to client request/s as shown below
  • As part of the overall setup, you would also have installed all of the certificates necessary in client keystore [system] 
        server {
            listen              443 ssl;
            server_name         www.example.com;
            ssl_certificate     www.example.com.crt;
            ssl_certificate_key www.example.com.key;
            ssl_protocols       TLSv1 TLSv1.1 TLSv1.2;
            ssl_ciphers         HIGH:!aNULL:!MD5;

            ssl_client_certificate /etc/ssl/clientcertificate.crt;
            ssl_verify_client on;
            ssl_verify_depth 3;
            ...
        }

 

 Environment

  • Nginx Plus
  • SSL Client certificate authentication

 Cause

  • None

 Recommended Actions

  • During SSL handshake, Nginx requirements for a client certificate is optional as per RFC 5246
  • Nginx verifies client certificates through the use of "ssl_verify_client" directives
  • "ssl_verify_client" directives by default is turned off but when turned 'on', it would require the client to present a valid client certificate
  • In the absence of a valid client certificate, Nginx completes SSL handshakes but results in Nginx returning HTTP 400 response code - Bad Request page in subsequent requests
  • Also, equivalent to request but no require for certificate is to have this directive with option "optional_no_ca", for more ssl_verify_client
  • If the user fails to present a valid client certificate intentionally or unintentionally, the workaround is to close and relaunch browser.

 Additional Information

 
The high overview of TCP and SSL handshakes can be described as follow
  • TCP three way handshake completes [ SYN, SYN/ACK, ACK]
  • and SSL handshake
  • [client Hello]
  • [Server Hello(server certificate)(server request client certificate along with a list of the accepted certificate authorities(CA)) ]
  • [client gets prompted for certificate]
  • [The client should select the appropriate certificates installed in client keystore which have been issued by any of these CA's listed above]
  • The above configuration instruct Nginx to authenticate users with a certificate prior to processing request

 

At this stage, if the client declines/cancels sending requested certificate

  • The rest of SSL handshake completes BUT without validating client
  • This in turn results in the generation of SSL session, which would then be used by the browser in subsequent request/s
  • Since, session key is generated without client validation and the browser persist with existing SSL session key, request for resources fails and Nginx returns HTTP 400 response code - Bad Request page
  • Refreshing browser page does not prompt the user for certificate from key-store as it persists in using existing SSL session key

Referring to RFC5246
  • The first message the client can send after receiving a ServerHelloDone message is "Client Certificate"
  • This message is only sent if the server, in our case Nginx, requests a certificate.
  • If no suitable certificate is available, the client MUST send a certificate message containing no certificates.
  • That is, the certificate_list structure has a length of zero.
  • If the client does not send any certificates, the server MAY at its discretion either continue the handshake without client authentication, or respond with a fatal handshake_failure alert.
  • With Nginx, it continues with the handshake, even if the certificate is not present and still make Nginx in compliant to RFC5246

 

Client certificates are sent using the Certificate structure defined in Section 7.4.2.
