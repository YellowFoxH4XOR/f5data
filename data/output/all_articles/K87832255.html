Known Issue

Compression enabled by the COMPRESS::enable iRule command in an HTTP_RESPONSE event may remain enabled for a subsequent HTTP request.

This issue occurs when all of the following conditions are met:

  • Your virtual server uses an iRule with the COMPRESS::enable iRule command within an HTTP_RESPONSE event.
  • The virtual servers processes multiple HTTP requests within the same TCP connection.
  • The initial HTTP response matches the COMPRESS::enable iRule command and contains an empty payload.

The response for the initial HTTP request enables compression, but because the response payload is empty, compression remains enabled for the subsequent request even if the request URI indicates that the response should not be compressed.

Impact

The system will experience unintended compression for subsequent HTTP responses.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • Some responses may be compressed even when the HTTP request indicates that the response should not be compressed.
  • Web applications may malfunction or fail to render properly.

Workaround

To work around this issue, you can ensure that affected iRules that enable compression with the COMPRESS::enable command will also disable compression in an else statement using the COMPRESS::disable command.

Impact of workaround: The impact of the suggested workaround depends on the specific environment. F5 recommends that you test any such changes during a maintenance window with consideration to the possible impact on your specific environment.
