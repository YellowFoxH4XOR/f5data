Description

DNS64 not working intermittently for AAAA when DNS64 in the DNS profile is set to secondary. The expectation is for domains with no ipv6 address, BIG-IP DNS should subsequently query for corresponding IPv4 address and prefix it with ipv6-prefix and pass it on the AAAA response to the client.

BIG-IP DNS is instead responding and caching the SOA received from the NS of the respective domain.

Environment

  • BIG-IP GTM
  • BIG-IP DNS 
  • DNS64 
  • Ipv4 and ipv6 listener 
  • DNS profile
  • AAAA Query

 

Cause

When a single cache profile is used, the underlying caching mechanism will cache the response received from the upstream NS and will respond to the client based on the cached entries.

So if an IPV4 listener received the AAAA request and the upstream NS is responding with SOA, the underlying caching mechanism will cache this as a valid response.

Next when the AAAA comes on the ipv6 listener, and if the SOA response is still present, BIG-IP DNS will respond to the client from the cache instead of performing DNS64 prefix.

This is the default working on the caching profile and F5 is tracking it via BugID1505689. This behavior wont be changed in the global releases and the recommendation is to separate the cache for ipv4 and ipv6 as mentioned in the recommended section.

 

Recommended Actions

  1. The caches for both ipv4 and ipv6 DNS profiles must be separate.
  2. The customer could choose to divide the amount of memory assignment to these caches based on the expected traffic volume on ipv4 and ipv6.
  3. The other alternative is to use a single DNS profile with single DNS cache. However, with this the ipv4 clients may start to receive prefixed DNS64 addresses. This set-up must be tested as ipv4 clients may not have NAT64 in some environments.
