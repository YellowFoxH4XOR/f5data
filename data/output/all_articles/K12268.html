Topic

This article applies to BIG-IP versions prior to 11.4.0. For information about other versions, refer to the following article:

  • K91382300: Successive HTTP requests that do not match the local traffic policy may bypass the BIG-IP ASM system

Description

The BIG-IP LTM load balancing component may bypass the BIG-IP ASM component and send subsequent HTTP requests to a pool when the requests do not match the requirements defined in the appropriate HTTP Class profile.

Under some circumstances, once the BIG-IP system has made a load balancing decision after the first successful request that matches an HTTP class, the BIG-IP system forwards all subsequent requests on the same connection to the same pool member, even if the requests do not meet the requirements of the assigned HTTP Class profile. Such requests bypass the BIG-IP ASM component and, without proper mitigation as described below, may potentially create a security concern by passing unchecked data to the origin web server (OWS) as long as a connection exists in the TMM connection table.

Important: This behavior has been confirmed by F5 Product Development as by design.

The BIG-IP LTM component is designed to achieve better performance by reusing the load balancing decision it makes for an initial request on all subsequent requests on the same connection. You can prevent subsequent requests from bypassing the BIG-IP ASM system by forcing the BIG-IP LTM system to make a new load balancing decision. To do so, you may use any of the following three methodologies:

  • Catch-all HTTP Class profile with a reject-all pool

    Important: F5 recommends this method as a best practice for deploying the BIG-IP ASM system in a way that mitigates the security concerns described in this article.

    With a selective HTTP Class profile in place, specified criteria is matched and those requests are sent to the BIG-IP ASM system. All other requests are matched by the catch-all HTTP Class profile, which does not forward the requests to the OWS. The second HTTP Class profile forces the new load balancing decision in this scenario.

  • OneConnect

    You can enable OneConnect to force a new load balancing decision. This option is only useful if more than one pool or HTTP class is configured. This can be a combination of two HTTP Class profiles, each with their own pool, assigned to the same virtual server, or one HTTP Class profile with a pool assigned, and a regular default pool assigned to the same virtual server.

  • iRules with LB-related commands (snat, pool, nexthop, snatpool, vlan, forward, virtual, use, etc.)

    You can use an iRule to force a new load balancing decision, which also requires two pools to be created. For more information about using iRules to load balance to multiple pools for virtual servers not using OneConnect, refer to K9800: Using an iRule to load balance HTTP requests to multiple pools.

    For more information about iRules, refer to DevCentral.

    Note: A DevCentral login is required to access this content.

Note: For more information about ordering HTTP Class profiles for sequential processing and configuring selective matching criteria, refer to K7280: Overview of the HTTP Class profile and K5422: Troubleshooting when connections are not passed to the BIG-IP ASM as expected.
