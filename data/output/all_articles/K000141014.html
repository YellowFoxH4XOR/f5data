Description

When client's connection is wireless the access to the virtual server works.

When client's connection is wired it does not work, there are tcp retransmissions on the server side from the BIG-IP to the backend servers.

There is no response from servers to the BIG-IP after the initial tcp handshake.

 

Environment

  • BIG-IP LTM
  • Clients not sending TSval Timestamps during the TCP three-way-handshake
  • Clients setting MSS during the TCP three-way-handshake but MSS is changed on the network path depending on their physical connection
  • TCP Profile Max Segment Size (MSS) is 1460 and Proxy Maximum Segment is enabled
  • Red hat servers

 

Cause

During the initial TCP three-way-handshake clients do not include TSval timestamp.

Wireless clients are setting an MSS equal to 1460 but network devices on the wireless network path are lowering down the MSS to 1250 bytes.

Wired clients are setting an MSS equal to 1460 with no change on the wired network path.

The BIG-IP did not add the TSval timestamp to the wired clients connections since it matches the MSS=1460 configured on the TCP profile and Proxy Maximum Segment is enabled, those causing the backend servers to not reply on the server side to the initial TCP syn sent from the BIG-IP when there is not TSval timestamp.

 

Recommended Actions

K15072130: Timestamps: TSval and TSecr are missing from SYN message sent from BIG-IP in case that the client is not sending TSval and TSecr

Apply one of the below actions

  1. Change behaviour on backend servers to allow the connection if the TSval timestamp is mandatory to establish tcp connections
  2. Change behaviour on clients to include the TSval timestamp when the connection is started regardless of the connection type
  3. Disable the Proxy Maximum Segment on the tcp profile

 

Additional Information

 

Packet Capture Examples:

For the clients using wireless connection you will see the behaviour shown below:

  • Client 172.19.10.10
  • Virtual server 10.11.11.11
  • Self-ip 10.10.10.10
  • Server 10.10.10.20

 

When taking a pcap on the client, there is not TSval Timestamp and MSS is set to 1460:

485  4.562782 0.000000 172.19.10.10 → 10.11.11.11 52 65038 80 TCP 55695 → 80 [SYN] Seq=0 Win=64240 Len=0 MSS=1460 WS=256 SACK_PERM=1

 

When taking a pcap on the big-ip (client side), there is not TSval Timestamp and MSS was changed on the wireless network path setting it to 1250:

 91  2.710087 0.000000 2322 172.19.10.10 → 10.11.11.11 52 65038 80 TCP IN s1/tmm2 : 65038 → 80 [SYN] Seq=0 Win=64240 Len=0 MSS=1250 WS=256 SACK_PERM=1

 

When taking a pcap on the big-ip (server side), the big-ip inserts the TSval Timestamp because the MSS is 1250 and then the MSS is 1262 which is lower than the MSS configured on the tcp profile: 

TCP_header + 1250 and TCP_header + 12 (TCP Timestamps Option is 12 bytes long in total) = 1262

 171  2.742652 0.000003 2322 10.10.10.10 → 10.10.10.20 60 65038 8002 TCP OUT s1/tmm2 : 65038 → 8002 [SYN] Seq=0 Win=12620 Len=0 MSS=1262 WS=1 SACK_PERM=1 TSval=3080606285 TSecr=0

For the clients using wired connection you will see the behaviour shown below:

  • Client 172.19.20.10
  • Virtual server 10.11.11.11
  • Self-ip 10.10.10.10
  • Server 10.10.10.20

 

When taking a pcap on the client, there is not TSval Timestamp and MSS is set to 1460:

307  3.037974 0.000000 172.19.20.19 → 10.11.11.11 52 55648 80 TCP 55648 → 80 [SYN] Seq=0 Win=64240 Len=0 MSS=1460 WS=256 SACK_PERM=1

 

When taking a pcap on the big-ip (client side), there is not TSval Timestamp and the MSS remains unchanged:

2  6.956979 0.000000 2322 172.19.20.19 → 10.11.11.11 52 55648 80 TCP IN s1/tmm2 : 55648 → 80 [SYN] Seq=0 Win=64240 Len=0 MSS=1460 WS=256 SACK_PERM=1

 

When taking a pcap on the big-ip (client side and server side), the big-ip does not insert the TSval Timestamp because the MSS is 1460 and it would need to fragment because it is greater than the MSS configured on the tcp profile, the big-ip tries on the server side with 3 TCP retransmissions because backend server is not answering until tcp times out and then it sends a tcp rst on client side with reason [F5RST: TCP retransmit timeout]: 

TCP_header + 1460 and TCP_header + 12 (TCP Timestamps Option is 12 bytes long in total) = 1472 (Greater than the MSS in tcp profile is 1460)
