Description

When F5's APM module acts as an OAuth Authorization Server, it's possible to see a jwt token that looks something similar to this:
"{\n  \"token_type\":\"Bearer\",\n  \"scope\":\"ScopeSeason openid\",\n  \"scope_data\":[\n    {\n        \"id\":\"ScopeSeason\",\n        \"value\":\"fall\"\n    },\n    {\n        \"id\":\"openid\",\n        \"value\":\"1\"\n    }\n  ],\n  \"iss\":\"https://oauth.lab\",\n  \"aud\":[\n    \"LabUsers\"\n  ],\n  \"claim1\":\"http://www.f5.com\",\n  \"email\":test2@oauth.lab,\n  \"userName\":\"test2\",\n  \"sub\":\"/Common/AccessProfile1_ap.test2\",\n  \"x-jti\":\"39a...dlPQ\",\n  \"jti\":\"0afe...9828\",\n  \"iat\":1633980890,\n  \"exp\":1633981190,\n  \"nbf\":1633980590\n}"

Environment

  • APM as OAuth Authorization server
  • Custom claim

Cause

This happens when the APM Admin is using a "custom" claim configured at Access -> Federation -> OAuth Authorization Server -> Claim:

Given a claim configured like this:
# tmsh list apm oauth oauth-claim E-Mail
apm oauth oauth-claim E-Mail {
    claim-name email
    claim-type custom
    claim-value "%{session.ad.last.attr.mail}"
}

and the OAuth Authorization object in the Visual Policy Editor is configured like this:
# tmsh list apm policy agent oauth-authz /Common/ExampleAS_ap_act_oauth_authz_ag
apm policy agent oauth-authz ExampleAS_ap_act_oauth_authz_ag {
    audience { You }
    customization-group ExampleAS_ap_act_oauth_authz_ag
    entries {
        0 {
            jwt-access-token-claim-entries {
                0 {
                    claim-name E-Mail
                    claim-value "%{session.ad.last.attr.mail}"
                }
            }
        }
    }
}

NOTE that in the BIG-IP WebUI, those values are not quoted. They are added in the configuration and therefore tmsh or bigip.conf shows the quotes around the dereferenced session variable

APM does not auto quote the value of the resulting string when the claim is set to custom as we are unsure what the value type will be.  Part of the process in generating the jwt is to base64 encode the values.  Base64 encoding standard will escape the results when the value is not quoted leaving the jwt as shown above when decoded. 

Using the above as an example, an AD query is made to populate session.ad.last.attr.mail session variable. The value returned from AD may be test2@oauth.lab (unquoted).  The value is dereferenced and stored as the claim-value before the jwt is base64 encoded. Base64 will then escape the jwt as shown above.

Recommended Actions

NOTE Starting in 15.1.x, you no longer need to perform the additional quoting of the session var as shown below.  The resulting tmsh command will show 

claim-value "%{session.ad.last.attr.mail}"

The fix for this issue is to either:

  1. Use a string type in the claim if possible
  2. Ensure you're using the proper type, a setting of Number and a value that is a string can produce this same, overly escaped jwt
  3. If a static string is set, ensure the string is quoted
  4. If a session variable is used as in the example above, Navigate to Access -> Profiles/Policies -> Access Profiles (Per-Session Policies) and edit the problematic policy to open the Visual Policy Editor.  Select the OAuth Authorization object. In the Scope/Claim Assign section, select Add/Delete.  Select the proper "claims" tab eg: Access Token Claims and add quotes around the session var for the claim who's type is set to custom.  If your app uses the other claims tab and those have claims that are custom, you'll need to quote those as well.  

    The result will look like this in tmsh and the jwt will be proper:

apm policy agent oauth-authz ExampleAS_ap_act_oauth_authz_ag {
    audience { You }
    customization-group ExampleAS_ap_act_oauth_authz_ag
    entries {
        0 {
            jwt-access-token-claim-entries {
                0 {
                    claim-name E-Mail
                    claim-value "\"%{session.ad.last.attr.mail}\""
                }
            }
        }
    }
}
