K000132518: Seeing issue with pod communications - block_all

Type
Support Solution
Published
2023-02-13
Updated
2023-02-13
Applies to
  • Aspen Mesh: 1.11, 1.14
Source
https://my.f5.com/manage/s/article/K000132518

Description

Two pods in the same namespace, one with sidecar injected and one without it, are unable to communicate between them. Istio-Proxy logs show block_all

[2023-01-23T17:44:14.899Z] "GET /path HTTP/2" 502 - direct_response - "-" 0 0 0 - "-" "user-agent" "example-a.com:50017" "-" - - 10.130.2.25:50017 10.130.3.150:8179 - block_all


Environment

  • Aspen Mesh 1.11.x
  • Openshift 4.7


Cause

HTTP request was made using a FQDN and existing ServiceEntry had a different host therefore Aspen Mesh couldn't find a match.

- apiVersion: networking.istio.io/v1beta1
  kind: ServiceEntry
  metadata:
    name: se-50017
    namespace: default
  spec:
    addresses:
    - 10.130.2.25
    endpoints:
    - address: 10.130.2.25
      ports:
        egress: 50017
    hosts:
    - 'example-b.com'
    location: MESH_EXTERNAL
    ports:
    - name: egress
      number: 50017
      protocol: HTTP2
    resolution: DNS


Recommended Actions

The ServiceEntry needs to list the correct host that matches the HTTP request.

- apiVersion: networking.istio.io/v1beta1
  kind: ServiceEntry
  metadata:
    name: se-50017
    namespace: default
  spec:
    addresses:
    - 10.130.2.25
    endpoints:
    - address: 10.130.2.25
      ports:
        egress: 50017
    hosts:
    - 'example-a.com'
    location: MESH_EXTERNAL
    ports:
    - name: egress
      number: 50017
      protocol: HTTP2
    resolution: DNS
