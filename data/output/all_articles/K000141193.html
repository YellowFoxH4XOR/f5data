Description

When the HTTP/2 profile is enabled on a Virtual Server in F5 BIG-IP, the application may fail to load correctly. In such cases, the browser displays an error message: ERR_HTTP2_PROTOCOL_ERROR. This issue can prevent users from accessing the application as expected.

Environment

  • BIG-IP LTM
  • HTTP/2 profile
  • Base HTTP profile

Cause

The HTTP/2 profile works in conjunction with the base HTTP profile..."In HTTP/1.x and prior you dealt with certain syntax. HTTP/2 is an "alternative to, but does not obsolete the HTTP/1.1 message syntax". As a matter of fact HTTP's current semantics remain unchanged. Basically what HTTP/2 does is add to it. Because of this you will see the afore mentioned items and more. " K95032535: Detecting the use of and troubleshooting HTTP/2 traffic on the BIG-IP Because of this  some of the fields overlap and what is set in the HTTP profile is used by the HTTP/2 profile.

Due to the "overlap" one potential cause of this error is that the default setting in the HTTP profile (64) effects the HTTP/2 traffic. For instance, if the maximum header count in the HTTP profile default setting is too low, it can prevent the processing of certain requests, such as GET requests that contain a large number of headers. When this threshold is exceeded, the server may terminate the connection, resulting in the ERR_HTTP2_PROTOCOL_ERROR in the browser.

Recommended Actions

1) To begin the analysis, it is helpful to have a decrypted packet capture of the traffic. The HTTP/2 protocol can only be seen when the traffic is decrypted. You can perform this capture as described here:  K31793632: Creating a decrypted tcpdump capture without using an iRule

Looking at the GET request in the gathered packet trace:

HyperText Transfer Protocol 2
    Stream: HEADERS, Stream ID: 419, Length 2469, GET <............>
        Length: 2469
        Type: HEADERS (1)
        Flags: 0x25, Priority, End Headers, End Stream
        [...]
        [Weight real: 256]
        Header Block Fragment: 824190f1e3c2d6a595d254257b6a3761af5d1f8704b463a8e8eb6d0349ec62d8cbeeb314…
        [Header Length: 5496]
        [Header Count: 75] <------------------------!!!!
        Header: :method: GET

Sometimes you can also notice the cause of the RST in the GOAWAY packet in the error section:

HyperText Transfer Protocol 2
    Stream: GOAWAY, Stream ID: 0, Length 8
        [...]
        Error: FRAME_SIZE_ERROR (6) <-----------!!!!!!!!!!

2) Verify the HTTP Profile Settings of the HTTP profile associated with the virtual server: This can be done via the GUI by going to Local Traffic  ››  Profiles : Services : HTTP  ››  <name of http profile> : Enforcement, and checking the setting for Maximum Header Count. It can also be checked via the CLI...

tmsh list /ltm profile http <name of http profile> 

Example output of the default profile:

root@(big-ip)(cfg-sync In Sync)(Standby)(/Common)(tmos)# list ltm profile http http
ltm profile http http {
    app-service none
    basic-auth-realm none
    enforcement {
        max-header-count 64
        max-header-size 32768
        pipeline allow
        unknown-method allow
    }
    lws-width 80
    oneconnect-status-reuse "200 206"
    oneconnect-transformations enabled
    proxy-type reverse
    request-chunking sustain
    response-chunking sustain
}

3) Adjust the max-header-count as needed.
