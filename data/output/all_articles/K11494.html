Known Issue

This is the result of a known issue. An NFS client renaming a file may result in a service outage to the source and destination directories of the renamed file. This issue may occur when all of the following conditions are met:

  • A multi-protocol namespace is configured with one volume and multiple shares.
  • The source and destination files are located on different shares.
  • The client attempting to rename the file is using NFS.
  • The destination filename already exists and is currently opened by a CIFS client, or if the destination filename is an NFS hard link that points to the same inode used for the destination file.

When the client attempts to rename the file to a destination filename that already exists and is currently open by a CIFS client, the rename will fail and cause the source and destination directories to lock. When this issue occurs, the ARX system will log error messages that appear similar to the following example to the syslog file:

:DNAS_PGRP-8-NOTE-MSG5:: DSTUB_ERROR: "Failed to remove file" [-213]: dnasstub.c:dstub_remove_file():[967]
:DNAS_PGRP-8-NOTE-TAKE_PERSIST_LOCK:: PEND: Taking persistent lock on directory /path1/ (did 0x8000000022b74) for pending operation.
:DNAS_PGRP-8-NOTE-TAKE_PERSIST_LOCK:: PEND: Taking persistent lock on directory /path2/ (did 0x80000000478fe) for pending operation.
:DNAS_PGRP-8-NOTE-PEND_KEEP:: RENAME (complete) vol=("/vol1") frdid=(0x8000000022b74) frshare=share1(88) frname=("source.txt") todid=(0x80000000478fe) toshare=share2(86) toname=("destination.txt") txid=(562949953781544) [15145 520236].
:DNAS_PGRP-8-NOTE-DIRLOCK_PERSIST:: Directory /path2/ (did 0x80000000478fe) is locked for pending operation recovery and cannot be modified.
:DNAS_PGRP-8-NOTE-MSG5:: DSTUB_ERROR: "Failed to remove file" [-213]: dnasstub.c:dstub_remove_file():[967]

F5 Product Development is tracking this issue as ID 38276 and it was fixed in ARX version 5.2.0. For information about upgrading, refer to the ARX release notes.

Workaround

You can resolve this issue by closing the open file or restarting the CIFS service for the volume.

Important: Restarting the CIFS service closes all open files on the VIP.

You can close the destination file using one of the following methods:

  • Have the user or application with the file open close the file.
  • Use Microsoft Management Console (MMC) to close the file on the ARX system.
  • Use the close cifs file command from the ARX command line. For information about the close cifs file command, refer to the ARX CLI Reference Guide.

Note: If the destination filename is not the actual open file, but rather an NFS hard link that links to the same inode used by the actual open file, it may not be possible for the user to determine all of the potential hard links to that same inode. Therefore, the only option may be to disable and re-enable the CIFS service that exports the affected volume.
