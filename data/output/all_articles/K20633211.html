Description

Aspen Mesh Dashboard contains sensitive data about the mesh like the architecture’s traffic metrics, services’ names, the state of the mesh and more. It is important not to expose the Dashboard to a wide audience or public internet without enforcing authentication. The Aspen Mesh Helm Chart allows you to secure the Dashboard with JWT tokens. This is documented in the Customizing your mesh section of the Aspen Mesh guide:

To configure JWT token authentication, you need to specify the JSON Web Keys, jwks URL where the Dashboard can retrieve keys to validate JWT Tokens sent by the client and redirectUrl where the client will be redirected in case the JWT token is missing or is not valid. Another solution to authenticate Aspen Mesh Dashboard is with OAuth2. Securing the Dashboard with oauth2 flow requires some additional steps to be performed as Aspen Mesh does not support oauth2 flow by default. You need to install the oauth2-proxy instance in front of the Aspen Mesh Dashboard to secure access with OAuth2.

All requests to the Dashboard passing through the proxy are checked for the proxy's session cookie. If the cookie is missing or not valid the user is asked to log in and redirected to the authentication provider. The user is asked for the username and password by the authentication provider. After returning from the authentication provider, the oauth tokens are stored in the configured session store and a cookie is set. The Client is next forwarded to the application upstream server (Aspen Mesh Dashboard).

In this article, we will discuss how to integrate the Aspen Mesh Dashboard with OKTA authentication provider using oauth2-proxy. For more information and the procedure in this article, refer to the official oauth2-proxy documentation.

Environment

  • Kubernetes: 1.18.x,1.19.x,1.20.x  
  • Aspen Mesh: 1.6.x, 1.9.x

Recommended Actions

To configure and integrate oauth2-proxy with the OKTA provider, perform the following procedures:
  • Configure and create the Authorization Server and Application Client on okta.com
  • Create an oauth2 Application with the Okta account
  • Configure oauth2-proxy credentials
  • Final deployment

Configure and create the Authorization Server and Application Client on okta.com

Create and configure a oauth2 Authorization Server:
  1. Login to the OKTA system using your administrative account. Development accounts may have URL https://dev-xxxxxxx-admin.okta.com/
  2. Navigate to Security then select API
  3. Every account should have a default Authorization Server created. This default server allows access to all users and can be referenced using a URL such as: https://dev-xxxxxxx.okta.com/oauth2/default. You can also create your own Authorization Server and Access Policy.
  4. To add a custom API Authorization server, click Add Authorization Server
  5. Fill out the Name with something to describe the application you are protecting. For example, Aspen Mesh Dashboard
  6. For Audience, pick the URL of the application you wish to protect. For example, https://dashboard.yourdomain.com (this DNS name should be routed to the IP you use to reach oauth2-proxy POD or kubernetes Service)
  7. Fill out a Description
  8. Add Access Policies to configure access to the Dashboard. To allow access to all users you can create allow all policy by selecting the Assign to: all clients check box.
  9. Leave all options with default values or consult the OKTA documentation for more details.

In the next steps you will use default API Server.

Create an oauth2 Application with OKTA the account
  1. Navigate to Applications then select Add Application
  2. Select Web Application for the Application type setting.
  3. Select OpenID – OpenID Connect and click Create
  4. Enter an Application Name such as Aspen Mesh Dashboard
  5. Set the Sign-in redirect URIs to https://dashboard.yourdomain.com (this DNS name should be routed to the IP you use to reach oauth2-proxy POD or Kubernetes Service)
  6. Under General set the Allowed grant types to Authorization Code and Refresh Token.
  7. Leave the rest as default, taking note of the Client ID and Client Secret.
  8. Under Assignments select the users or groups you wish to access your application. To allow access to all users choose Allow everyone in your organization to access
The oauth2-proxy POD you use is a proxy to your Aspen Mesh Dashboard (application to secure). The application you are going to secure in your deployment is this oauth2-proxy POD. Every URL and DNS name for the application you secure should point to the IP you use to reach the oauth2-proxy POD. If you use a Kubernetes cluster running in a public cloud (e.g. AWS) this can be the DNS name to your Kubernetes LoadBalancer service exposing the oauth2-proxy deployment which may be similar to https://xx7e7e794f6c9c8xxxxxyyy-xxxxxx.us-west-2.elb.amazonaws.com/oauth2/callback.
 

Configure oauth2-proxy credentials

In this section you configure credentials for the oauth2 proxy.
Note: If someone gets access to your shell’s scrollback buffer or history after you perform this procedure, they may be able to discover these secrets. You should close your shell once these steps are complete. Use the command set +o history to disable your shell history for this session (you need to run this each time you open a new shell for handling the secrets):
  1. Make a Cookie Secret. This is used to encrypt the cookies that are stored in your users’ browsers. It can be any long base64 value as long as it is confidential and used only for this application. Here is one way to generate one:

    export COOKIE_SECRET=`echo -n “<PASSWORD-IN-PLAINTEXT> | base64`

  2. Create a secret containing the Application details created in the previous steps, and a Cookie Secret. Replace this with the Client ID and Client Secret from the Application.

    kubectl create secret generic -n istio-system aspen-mesh-oauth2-proxy-secrets --from-literal=CLIENT_ID=<CLIENT_ID> --from-literal=CLIENT_SECRET=<CLIENT_SECRET> --from-literal=COOKIE_SECRET=$COOKIE_SECRET

  3. Create a secret containing the TLS certificate and key. Put the certificate chain and key in files called fullchain.pem and privkey.pem or replace those in the command below with a path to the files. Your platform may also have platform-specific techniques for securely creating Kubernetes TLS secrets - if so, create a TLS secret named aspen-mesh-oauth2-proxy-cert in the istio-system namespace.

    kubectl create secret tls -n istio-system aspen-mesh-oauth2-proxy-cert --key privkey.pem --cert fullchain.pem

At this point, you are finished handling credentials. You may want to remove local copies of the certificates and keys and close your terminal session and open a new one so that any credentials that appeared on screen while working through this section are not visible.

Final deployment

In the final deployment you are going to use oauth2-proxy secured with TLS and certificates created in the previous step. The oauth2-proxy application will redirect all requests to the oauth2-proxy POD without valid session cookie to this OKTA authorization server. In the following manifests, we also configure the LoadBalancer type Kubernetes Service to expose the oauth2-proxy deployment. The URL assigned to this LB Service has to be used in the previous steps to configure the Audience, Application URL and Sign-in redirect URIs in the OKTA administrative account. You can find the load balancer domain name or IP address in the EXTERNAL-IP as follows:

# kubectl get svc -n istio-system aspen-mesh-oauth2-proxy
NAME                      TYPE           CLUSTER-IP       EXTERNAL-IP
aspen-mesh-oauth2-proxy   LoadBalancer   10.20.113.3    a123w----------------------5a3e-150000001.us-west-2.elb.amazonaws.com

In the above example, the Sign-in redirect URIs should look like:

https://a123w----------------------5a3e-150000001.us-west-2.elb.amazonaws.com/oauth2/callback

In the following oauth2-proxy deployment, you used the default Okta API server with the URL: https://dev-xxxxx.okta.com/oauth2/default.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: aspen-mesh-oauth2-proxy
  namespace: istio-system
  labels:
    app: aspen-mesh-oauth2-proxy
spec:
  replicas: 1
  selector:
    matchLabels:
      app: aspen-mesh-oauth2-proxy
  template:
    metadata:
      labels:
        app: aspen-mesh-oauth2-proxy
      annotations:
        sidecar.istio.io/inject: "false"
    spec:
      containers:
        - name: oauth2-proxy
          image: quay.io/pusher/oauth2_proxy:v4.0.0
          imagePullPolicy: IfNotPresent
          args:
            - '--provider=oidc'
            - '--oidc-issuer-url=https://dev-xxxxx.okta.com/oauth2/default
            - '--upstream=http://aspen-mesh-controlplane.istio-system:19001'
            - '--tls-cert-file=/etc/oauth2-https-certs/tls.crt'
            - '--tls-key-file=/etc/oauth2-https-certs/tls.key'
            - '--cookie-secret=$(COOKIE_SECRET)'
            - '--client-secret=$(CLIENT_SECRET)'
            - '--client-id=$(CLIENT_ID)'
            - '--email-domain=*'
            - '--skip-provider-button=true'
            - '--https-address=0.0.0.0:8443'
          ports:
            - containerPort: 4180
              name: http
            - containerPort: 8443
              name: https
          env:
            - name: COOKIE_SECRET
              valueFrom:
                secretKeyRef:
                  name: aspen-mesh-oauth2-proxy-secrets
                  key: COOKIE_SECRET
            - name: CLIENT_SECRET
              valueFrom:
                secretKeyRef:
                  name: aspen-mesh-oauth2-proxy-secrets
                  key: CLIENT_SECRET
            - name: CLIENT_ID
              valueFrom:
                secretKeyRef:
                  name: aspen-mesh-oauth2-proxy-secrets
                  key: CLIENT_ID
          volumeMounts:
          - name: https-certs
            mountPath: /etc/oauth2-https-certs
            readOnly: true
      volumes:
        - name: https-certs
          secret:
            secretName: aspen-mesh-oauth2-proxy-cert
---
apiVersion: v1
kind: Service
metadata:
  name: aspen-mesh-oauth2-proxy
  namespace: istio-system
  labels:
    app: aspen-mesh-oauth2-proxy
spec:
  type: LoadBalancer
  selector:
    app: aspen-mesh-oauth2-proxy
  ports:
    - name: https
      port: 443
      protocol: TCP
      targetPort: 8443

The oauth2-proxy by default adds the Secure option to all session HTTP Cookies. The browser will not add Secure Cookies to the connection not secured by TLS (plain HTTP). To remove the Secret field, while setting cookies in the browser, you need to add the '--cookie-secure=false' flag to your oauth2-proxy deployment. More options available for oauth2proxy can be found in the OAuth documentation. If you want to use HTTP for your Cookie oauth2-proxy you have to modify the oauth2-proxy configuration on your deployment to the following:

      containers:

            - '--oidc-issuer-url=https://dev-xxxxx.okta.com/oauth2/default
            - '--upstream=http://aspen-mesh-controlplane.istio-system:19001'
            - '--cookie-secret=$(COOKIE_SECRET)'
            - '--client-secret=$(CLIENT_SECRET)'
            - '--client-id=$(CLIENT_ID)'
            - '--email-domain=*'
            - '--skip-provider-button=true'
            - '--http-address=0.0.0.0:4180'
            - '--cookie-secure=false'
