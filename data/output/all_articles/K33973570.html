Introduction

Upgrading BIG-IP VE instances in an AWS autoscaling group is different from other updates, because an AWS autoscaling group resource manages and scales up or down the BIG-IP instances on demand.

The method you use to update depends on how you initially created your BIG-IP instances and how you currently manage them.

This chapter primarily covers how to update BIG-IP VE instances that you created and manage using the F5 AWS CloudFormation Templates (CFT) 1.0 on GitHub.

Important: F5 deprecated the F5 AWS CloudFormation Templates 1.0 and replaced it with F5 AWS CloudFormation 2.0. The procedure in this article is also no longer supported and maintained.

The steps to update BIG-IP VE instances in an AWS autoscaling group using the CFT 1.0 include the following. You can use the written procedures below or watch the following videos

  1. Determine and note the Amazon Machine Image (AMI) ID you want the F5 AWS CloudFormation Templates 1.0 stack to use to create new BIG-IP instances. This image contains the BIG-IP version you want to update to.
  2. Create a user configuration set (UCS) archive of the existing primary BIG-IP instance and upload it to the /backup directory of the AWS Simple Storage Service (S3) bucket the template creates. 
  3. Change the AMI ID the stack currently uses to the AMI ID from step 1 and update the stack.
  4. When the F5 AWS CloudFormation Templates 1.0 stack detects the update, it terminates and launches new BIG-IP VE instances, one at a time, using the following method:
    • When the stack launches the first, or primary, BIG-IP VE instance of the autoscaling group, the template uses the UCS archive created in step 2 to perform a restore.
    • When the autoscaling group creates subsequent BIG-IP VE instances, it syncs to the primary BIG-IP instance to update its configurations.

Upgrade vs. update

This chapter may use the word upgrade to refer to either a software upgrade or update. For a definition that explains the difference between the two terms, refer to Upgrading vs. updating in the Introduction.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • The F5 AWS CloudFormation Templates 1.0 stack, deployed from the CFT, manages your BIG-IP VE instances and autoscaling group.
  • You have the required AWS credentials to log in to the AWS portal to manage the F5 AWS CloudFormation Templates 1.0 stack and the resources it manages. 
  • You have both SSH key pair and username/password credentials to log in into the primary BIG-IP VE instance.

Prepare

Impact of procedure: Performing the procedures in this section should not have a negative impact on your system.

Determine the AMI ID of the image you want to update or upgrade to

To watch a video demo of this procedure, go to  Update BIG-IP in an AWS auto-scaling group: Determine the AMI ID.

When you are updating, you must provide the F5 AWS CloudFormation Templates 1.0 stack with the AWS AMI ID you want to update to. To determine the AMI ID, perform the following procedure:

  1. Log in to the AWS Management Console.
  2. Go to AWS Console > EC2 > Images > AMIs.
  3. In the search filter, select Public images.
  4. Select the text field of the filter, and then select AMI Name.

    The console displays a list of suggestions.

  5. To filter further, enter the first part of the name of your BIG-IP version you want to update to, and then select Enter.

    For example, you enter the following name:

    F5 BIGIP-16.0.1

  6. From the search results, select the checkbox next to the AMI name you want to update to.

    Select the AMI name that has the BIG-IP version you want to update to and the same licensing and bandwidth type as your current BIG-IP VE instance. For example, you want to upgrade to BIG-IP 16.0.1.1 and you currently have a Pay As You Go license with 200 Mbps, so you select the following name:

    F5 BIGIP-16.0.1.1-0.0.6 PAYG-Good 200Mbps

  7. Note the AMI ID, because you need it in a future step.

    For example, you note the following AMI ID:

    ami-0c38e857afe4bdb88

Identify the primary BIG-IP VE instance in the autoscaling group

To watch a video demo of this procedure, go to  Update BIG-IP in an AWS auto-scaling group: Identify the primary BIG-IP.

You must know which of the BIG-IP VE instances in the autoscaling group is the primary instance. To identify it, perform the following procedure:

Note: For more information on the primary instance of the cluster, refer to the Detailed clustering information on GitHub.

  1. Log in to the AWS Management Console.
  2. Go to AWS Console > EC2 > Auto Scaling > Auto Scaling Groups.
  3. Select the name of your autoscaling group.
  4. Select Instance Management.
  5. In the Protected From column, the BIG-IP VE instance that has the value Scale in is the primary instance.

Generate a UCS archive of the primary BIG-IP VE instance

The following video uses steps that are not exactly the same as the ones in this procedure, but they are similar and you may find it helpful:

 Backing up BIG-IP config files with a UCS archive using the command line.

  1. To log in to the primary BIG-IP VE instance using your SSH key, enter the following command syntax:

    ssh -i <key pair name>.pem admin@<ip address>

  2. To generate a UCS archive and save it in the /var/tmp directory, enter the following command using the TMOS Shell (tmsh):

    save /sys ucs /var/tmp/original.ucs

  3. Download the UCS archive to your client device.

Upload the UCS archive to the S3 bucket in the F5 AWS CloudFormation Templates 1.0 stack

To watch a video demo of this procedure, go to  Update BIG-IP in an AWS auto-scaling group: Upload the UCS to the S3 bucket.

  1. In the AWS Management console, go to AWS Console > S3.
  2. Select the name of the S3 bucket.
  3. Select the backup/ directory.
  4. Select Upload.
  5. Select Add Files, and then select the UCS archive on your client device.
  6. Select Upload.

Update or upgrade

To watch a video demo of this procedure, go to   Update BIG-IP in an AWS auto-scaling group: Update the BIG-IP.

You update the BIG-IP VE instances in an autoscaling group by updating the AWS AMI ID in the F5 AWS CloudFormation Templates 1.0 stack. F5 recommends that you make only one change in the stack, as described in this procedure.

Impact of procedure: When the F5 AWS CloudFormation Templates 1.0 stack detects the update, it terminates and launches new BIG-IP VE instances, one at a time. If you have more than one BIG-IP VE instance, services may not be disrupted. However, the autoscaling group may have BIG-IP VE instances with different BIG-IP versions at one time. F5 recommends performing this procedure during a scheduled maintenance window.

  1. Log in to the AWS Management Console.
  2. Go to AWS Console > CloudFormation > Stacks.
  3. Select the name of the stack you want to modify.
  4. Select Update.
  5. Select Use current template, and then select Next.
  6. In Custom Image Id, enter the AMI ID you noted down in the Determine the AMI ID of the image you want to update or upgrade to section.
  7. Select Next until you are at the Review step.
  8. Review the changes.
  9. Select I acknowledge that AWS CloudFormation might create IAM resources.
  10. Select Update Stack.
  11. Follow the update progress by viewing the stack events as they happen.

Recommendations

  • Understand how the CFT updates the BIG-IP VE instances using the UCS archives and automatic sync. For more information, refer to Restoring or upgrading the solution on GitHub.
  • When you modify the AMI the F5 AWS CloudFormation Templates 1.0 stack uses, perform only one change at a time. Making multiple changes may result in issues whose root cause you are unable to determine.
  • The F5 AWS CloudFormation Templates 1.0 stack updates each BIG-IP instance one at a time, with a pause of around 30 minutes in between each update to initialize each instance. For example, when you have four instances running, the stack update takes two hours.

    Optional: Depending on your environment, before performing the update, you can set the maximum capacity of the autoscaling group to reduce the number of instances to update. For example, you can set the maximum capacity to two instances. After you successfully upgrade two instances, you can increase the capacity again.

Troubleshoot

After selecting Update to update the F5 AWS CloudFormation Templates 1.0 stack, follow the events to ensure there are no errors. As the stack launches BIG-IP VE instances, you can also log in to follow the initialization process in the /var/log/ltm file.

The following table lists common issues, possible causes, and resolutions.

Table 13.1 Common issues, possible causes, and resolutions
Common issuesPossible causesResolutions
After launching a new BIG-IP instance, the stack update remains in UPDATE_IN_PROGRESS status with Status reason: New instance(s) added to autoscaling group - Pausing for PT30M.When theF5 AWS CloudFormation Templates 1.0 stack detects the update, it terminates and launches new BIG-IP VE instances, one at a time. After launching an instance, it pauses for 30 minutes (PT30) to initialize the instance before proceeding to the next one.This is not an error. Time is required.

You can login to the new BIG-IP VE instance using its public IPv4 address to follow its progress by entering the following syntax:

tailf /var/log/ltm

The first BIG-IP instance to launch contains neither BIG-IP configurations not virtual servers and pools.When the new stack configuration launches the first BIG-IP VE instance, the stack takes time to initialize the instance before it uses the UCS archive from the S3 bucket to restore its configurations.
  • Ensure the S3 bucket contains the correct UCS archive. If more than one exists, the system selects the one with the latest timestamp. Note that the F5 AWS CloudFormation Templates 1.0 stack also generates a UCS archive daily at 12:00 AM.
  • Log in to the new BIG-IP VE instance using its public IPv4 address and follow its progress by entering the following syntax:

    tailf /var/log/ltm

  • If required, you can manually trigger the creation of a new primary BIG-IP instance by manually terminating the instance.
  • Use a different AMI image, one with a BIG-IP version that is tested. Refer to Tested BIG-IP versions on GitHub.
The subsequent BIG-IP instances that the stack creates contain neither BIG-IP configurations nor virtual servers and pools.When the new stack configuration launches subsequent BIG-IP instances, the stack initializes them before performing a sync with the primary instance to retrieve and update their configurations. They enter the Active and In Sync state when completed.Review the /var/log/ltm file in each BIG-IP instance to determine why automatic sync failed.
  • If required, you can manually trigger the creation of the BIG-IP instance by manually terminating the instance.
  • Use a different AMI image, one with a BIG-IP version that is tested. Refer to Tested BIG-IP versions on GitHub.
