K000161960: CRL Cache Stops Updating and keymgmtd Memory Leak with Dynamic CRL Validation on BIG-IP LTM

Type
Support Solution
Published
2026-06-29
Updated
2026-06-29
Source
https://my.f5.com/manage/s/article/K000161960

Description

When a Client SSL profile is configured with a dynamic CRL Validator on BIG-IP LTM, the CRL cache may stop being updated after working correctly for an extended period. Client SSL handshakes begin failing with the following error in /var/log/ltm:

Connection error: ssl_hs_do_crl_validation:7073: alert(46) unknown certificate error


The CRL is successfully downloaded from the CRL Distribution Point endpoint, but the downloaded file is not written to the CRL cache directory at /config/filestore/crl_file_cache_d/. The cached file retains its previous modification timestamp and the stale CRL continues to be used for validation. Removing the CRL Validator from the Client SSL profile immediately restores connectivity.

Restarting the keymgmtd service and deleting the stale cached CRL file resolves the issue temporarily. However, the problem recurs over time as keymgmtd memory grows again.

Symptoms


The following symptoms are observed when this issue is active.

SSL handshakes fail with the error message shown in the Description section above.

The CRL is downloaded successfully from the CRLDP endpoint, which can be confirmed via firewall logs or a tcpdump capture, but the cached file in /config/filestore/crl_file_cache_d/ is not updated. The modification timestamp on the cached CRL file does not change after a successful download.

The keymgmtd process memory, specifically VmRSS and VmSize, increases steadily over time without leveling off. Memory usage drops significantly after restarting the keymgmtd service.

Removing the CRL Validator from the Client SSL profile immediately restores SSL connectivity. Restarting keymgmtd and deleting the stale cached CRL file restores CRL validation temporarily.

Environment

  • BIG-IP LTM
  • Client SSL profile configured with a dynamic CRL cert-validator object (sys crypto cert-validator crl)
  • Internal proxy and DNS resolver configured for CRL downloads
  • CRL cache directory: /config/filestore/crl_file_cache_d/

Cause

This issue is caused by a known memory leak in the keymgmtd daemon when dynamic CRL validation is enabled, documented in Bug ID1256757.

When dynamic CRL validation is active, keymgmtd steadily accumulates memory in the emdeviced memory subsystem. Over time, as memory is exhausted, keymgmtd loses the ability to write the newly downloaded CRL file to the cache directory. The daemon continues to download the CRL from the CRLDP endpoint but cannot complete the cache update operation. As a result, the stale cached CRL file remains in place and is used for all subsequent certificate validation, causing handshake failures.

The memory leak is independent of traffic volume and occurs whenever CRL validation is enabled. The rate of memory growth may vary depending on the frequency of CRL downloads and the number of SSL handshakes processed.

Answer/Recommended Actions

Workaround

The following procedure temporarily resolves the issue by clearing the stale cache and resetting keymgmtd memory. This procedure must be repeated when the issue recurs as memory grows again.

Step 1. Re-enable the CRL Validator in the Client SSL profile if it was removed as a workaround.

Step 2. Delete the stale cached CRL file from the cache directory. The filename corresponds to the CRL URL with special characters replaced by underscores.

rm /config/filestore/crl_file_cache_d/<crl_cache_filename>

Step 3. Restart the keymgmtd service to reset memory and allow the daemon to download and cache a fresh CRL.

tmsh restart sys service keymgmtd

Step 4. Verify that a new CRL file is created in the cache directory with the current date after the restart.

ls -la /config/filestore/crl_file_cache_d/

Step 5. Confirm that the ssl_hs_do_crl_validation errors no longer appear in /var/log/ltm.

Monitoring keymgmtd Memory Growth

To confirm that keymgmtd memory is growing and to establish a trend, collect the following outputs periodically, for example every hour over a period of three days.

Check the keymgmtd process memory using ps:

date; ps aux | grep keymgmtd


Check the keymgmtd virtual memory details from the proc filesystem:

cat /proc/$(pgrep keymgmtd)/status | grep -i vm

Look for VmRSS and VmSize values that increase steadily over time without leveling off. This confirms the memory leak is active.

To check for evidence of prior keymgmtd crashes or out-of-memory events, run the following commands:

grep -i keymgmtd /var/log/ltm | grep -iE "crash|core|restart|killed|oom"
grep -i "out of memory" /var/log/messages
grep -i keymgmtd /var/log/daemon.log
ls -lh /var/core/ | grep keymgmtd

Inspecting the CRL Cache File

To check the Next Update timestamp in a cached CRL file and verify whether it is stale, run the following command:

openssl crl -inform der -in /config/filestore/crl_file_cache_d/<crl_cache_filename> -text | grep -E "Last Update|Next Update"

To check the file modification timestamp on the cached CRL file:

stat /config/filestore/crl_file_cache_d/<crl_cache_filename>

If the Modify timestamp on the cached file is older than the most recent CRL download confirmed in firewall or network logs, this confirms that keymgmtd downloaded the CRL but failed to update the cache file.
