Description
After a reboot or configsync you notice that the BIG-IP is showing INOPERATIVE on the CLI. In addition, you also notice one of more of the following:

  • The BIG-IP configuration utility shows the following message: Starting web server

  • You see output similar to the following in the /var/log/ltm file:

    Oct 19 07:58:10 bigip.local err mcpd[3937]: 01071684:3: Unable to encrypt application variable (/Common/myuser1 privacy_password usmuser /Common/snmpd)
    Oct 19 08:07:18 bigip.local err mcpd[26440]: 01071684:3: Unable to encrypt application variable (/Common/myuser2 privacy_password usmuser /Common/snmpd)


    Or:
    Nov 12 03:23:09 bigip.local     err mcpd[20771]: 0107102b:3: Master Key decrypt failure - decrypt failure - final
    Nov 12 03:23:09 bigip.local notice mcpd[20771]: 01071029:5: Master decrypt final
    Nov 12 03:23:09 bigip.local notice mcpd[20771]: 01071027:5: Master key OpenSSL error: 4007536372:error:0906D06C:PEM routines:PEM_read_bio:no start line:pem_lib.c:697:Expecting: CERTIFICATE
    Nov 12 03:23:09 bigip.local notice mcpd[20771]: 01b00001:5: Processed value is empty: class name (usmuser) field name ()
    Nov 12 03:23:09 bigip.local err mcpd[20771]: 01071684:3: Unable to encrypt application variable (/Common/snmpv3 auth_password usmuser /Common/snmpd).
    Nov 12 03:23:09 bigip.local err mcpd[20771]: 01070596:3: An unexpected failure has occurred, - framework/LtcfgInstance.cpp, line 3359, exiting... 

  • Output from the tmsh show sys service command shows numerous waiting for mcpd to release running semaphore messages:

    aced                  down, waiting for mcpd to release running semaphore
    adfs_proxy            down, waiting for mcpd to release running semaphore

    mdmsyncmgr            down, waiting for mcpd to release running semaphore
    merged                down, waiting for mcpd to release running semaphore
    ...

Environment

  • BIG-IP or BIG-IQ
  • SNMP v3 users configured

Cause
The BIG-IP configuration master key got out of sync with passwords saved in the /config/bigip_base.conf file.
For example, this can occur, if snmpv3 or other configuration containing encrypted passphrases is copied or merged into a system which uses a different Master Key. 

Recommended Actions

1. On both the Active and Standby (INOPERATIVE) unit, use the TMSH commands below to re-apply the passwords

Note: If the passwords are unknown use any password to bring the unit back online and then delete the user accounts via the configuration utility or TMSH:

tmsh modify sys snmp users modify { myuser1 { auth-password **** privacy-password **** } }
tmsh modify sys snmp users modify { myuser2 { auth-password **** privacy-password **** } }
tmsh save sys config

2. On the unit showing status INOPERATIVE additionally run the command below:
bigstart restart


3. [Optional] You may also have to do this if there is also an SNMP traps configuration:
tmsh modify sys snmp traps modify { trap1 { auth-password **** privacy-password **** } }
tmsh modify sys snmp traps modify { trap2 { auth-password **** privacy-password **** } }
tmsh save sys config


4. After performing step 3, on the unit showing status INOPERATIVE additionally run the command below:
bigstart restart
