Description

By default, the istio-proxy for clusters type STRICT_DNS and LOGICAL_DNS will constantly refresh the cache of each FQDN. The refresh will be based on the TTL of each record or using the config dnsRefresh which the default is 5 seconds.

This article covers the topic about what can trigger istio-proxy to perform those DNS queries or cache refresh over TCP instead of UDP.

Environment

  • Kubernetes: 1.19.x, 1.20.x, 1.21.x
  • Aspen Mesh: 1.11.x

Cause

The DNS server controls the switch to TCP. By default, all DNS queries are performed over UDP, when a client receives a response that is too large, the server sets a special bit TC in the response forcing the client to switch to TCP and perform a retry query.

In istio-proxy case DNS is asynchronous. We assume that istio-proxy uses the same mechanism when refreshing the cache as receives the same TC bit. On top of that, the asynchronous connection for DNS can query the upstream server without slowing down HTTP requests proxied by istio-proxy, this means the query is independent of the request and is not waiting for a response from the server. 

In some cases, the istio-proxy could switch to TCP over UDP and not come back to UDP knowing the responses will be too large. This can prevent DNS flood instead of performing a query over UDP and retrying over TCP, just leave the queries going over TCP.
