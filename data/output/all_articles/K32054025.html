K32054025: HTTP Host header rewrite with Aspen Mesh

Type
Support Solution
Published
2022-07-19
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K32054025

Description

HTTP requests are routed by sidecar proxies based on the Host or Authority headers sent by the Client applications. Istio sidecar proxy by default forwards requests to clusters and endpoints without modifying the Host header. Endpoints and backend servers can be discovered and identified in the configuration using DNS domains. The DNS domain might not be corresponding to the domain name sent in the Host or Authority headers.

Here is an example of the ServiceEntry where Endpoints are configured with different DNS domain names than the Listener:

apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: external-se
  namespace: ns4
spec:
  endpoints:
  - address: nginx1.pawelp.local.com
    ports:
      http2: 6644
    weight: 70
  - address: nginx2.pawelp.local.com
    ports:
      http2: 6655
    weight: 30
  exportTo:
  - .
  hosts:
  - nginx1.pawelp.local.com
  location: MESH_INTERNAL
  ports:
  - name: http2
    number: 6644
    protocol: HTTP2
  resolution: DNS

Environment

  • Aspen Mesh: 1.6.x - 1.11.x
  • Kubernetes: 1.17x - 1.22.x
  • Red Hat OpenShift: 4.6.x - 4.8.x

Cause

Application services may validate received Host headers and in case the header is not equal to the expected value than the requests may be rejected. In that scenario Envoy proxy sidecar should overwrite the Host header while forwarding requests to the Endpoints identified with the domain name different than the domain name specified in the ServiceEntry hosts field.

Envoy provides auto_host_rewrite option to configure that behavior. 

Recommended Actions

auto_host_rewrite setting is currently not available in any Istio API. To apply the host rewrite setting to the proxy EnvoyFilter has to be used.

Here is an example EnvoyFilter which can be used to apply auto host rewrite configuration:

apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: host-rewrite
spec:
  configPatches:
  - applyTo: HTTP_ROUTE
    match:
      routeConfiguration:
        vhost:
          name: nginx1.pawelp.local.com:6644
          route:
            action: ANY
    patch:
      operation: MERGE
      value:
        route:
          auto_host_rewrite: true
  workloadSelector:
    labels:
      app: <application label>

Vhost field has to correspond the host header and TCP port specified in the ServiceEntry and Envoy HTTP route where the configuration is applied. workloadSelector field is used to provision the configuration only to the PODs with the specified label. In our example the used vhost nginx1.pawelp.local.com:6644:

> istioctl pc listener sleep-557747455f-kzq5c.ns4 --port 6644
ADDRESS PORT MATCH DESTINATION
0.0.0.0 6644 ALL   Route: 6644
> istioctl pc route sleep-557747455f-kzq5c.ns4 --name 6644
NAME     DOMAINS                     MATCH     VIRTUAL SERVICE
6644     *                           /*
6644     nginx1.pawelp.local.com     /*

The configuration should be applied to the route:

> istioctl pc route sleep-557747455f-kzq5c.ns4 --name 6644 -o yaml
- name: "6644"
  validateClusters: false
  virtualHosts:
  - domains:
...
  - domains:
    - nginx1.pawelp.local.com
    - nginx1.pawelp.local.com:6644
    includeRequestAttemptCount: true
    name: nginx1.pawelp.local.com:6644
    routes:
    - decorator:
        operation: nginx1.pawelp.local.com:6644/*
      match:
        prefix: /
      name: default
      route:
        autoHostRewrite: true

Note: This option is applicable only when the destination cluster for a route is of type strict_dns or logical_dns. Setting this to true with other cluster types has no effect.
