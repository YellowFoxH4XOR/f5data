Description

When an NGINX Gateway Fabric (NGF) WAFPolicy uses spec.policySource.nimSource.policyName to pull a WAF policy from NGINX Instance Manager (NIM), NGF deploys the oldest compiled bundle of that policy instead of the most recent one. This occurs when one NIM policy has multiple compilations, for example with different appProtectWAFVersion or signature versions.

Symptoms:

  • Recompiling the policy, or compiling it with newer WAF or signature versions, does not change the bundle deployed to the data plane.
  • The data plane keeps the WAF engine version of the first compilation. For example, wafEngineVersion 11.665.2 (WAF 5.635.2) remains deployed while the newest compilation is WAF 5.635.3.
  • With polling enabled, NGF logs the following message on every poll cycle, but the deployed bundle hash never matches the new checksum:

    Bundle checksum changed, downloading full bundle

  • A new WAFPolicy that points to the same NIM policy also receives the oldest bundle.
  • A policy whose first compilation is the newest one deploys correctly, which indicates that the first-compiled bundle is always selected.

Reproduced on NGF 2.6.7 and 2.7.2 with NIM 2.22.2 and 2.23.0.

Environment

  • Product: NGINX Gateway Fabric 2.6.x and 2.7.x with F5 WAF for NGINX (NAP v5)
  • Management: NGINX Instance Manager (NIM) 2.22.x and 2.23.x
  • Configuration: WAFPolicy with spec.type: NIM and spec.policySource.nimSource.policyName set. Polling (policySource.polling.enabled: true) is optional and does not change the behavior.
  • Condition: The same NIM policy has more than one compiled bundle. NIM assigns all compilations of one policy the same metadata.policyUID, and each compilation has its own metadata.uid.

Cause

A defect in the NGF bundle fetch logic (fetchNIM flow in the WAF fetch package):

  1. resolveLatestNIMPolicyUID() selects the most recently created compilation, based on metadata.created, but returns its shared metadata.policyUID. The per-compilation metadata.uid is not used.
  2. fetchNIMByUID() then queries /api/platform/v1/security/policies/bundles?policyUID=<policyUID>. NIM returns every compilation of the policy in ascending creation order. NGF takes resp.Items[0], which is the oldest compilation.

The "latest" selection in step 1 is overridden in step 2. The checksum used for change detection and the content that is downloaded come from different compilations.

Answer/Recommended Actions

There is no configuration-only fix in the WAFPolicy CRD, because it has no field for selecting a specific bundle. F5 engineering has confirmed the defect, and a fix is planned for a future release. No release version has been committed.

Workaround (confirmed by F5 Support):

  1. In NIM, delete the WAF security policy that NGF uses.
  2. Recreate the policy in NIM with the same policy name.
  3. Compile the policy with the WAF version you want to deploy.
  4. Confirm that NGF has fetched the new bundle by checking the timestamp and wafEngineVersion in the bundle catalog on the NGINX data plane, and comparing them with the modified and appProtectWAFVersion values returned by the NIM bundles API.

Alternative used by customers (not an official F5 workaround):

  • Keep one compilation per NIM policy, and use a separate policy name for each WAF version you need.

Until the fix is released, avoid keeping multiple compilations of the same NIM policy if NGF must deploy the newest compilation.

Additional Information

  • Expected behavior: NGF deploys the most recently created compilation of the policy, which matches the intent of the latestNIMItem() selection.
  • Actual behavior: NGF deploys the oldest compilation and does not update when newer compilations are created.
  • The NIM list endpoint has no per-bundle selector. The single-bundle endpoint /api/platform/v1/security/policies/{POLICY_UID}/bundles/{POLICY_BUNDLE_UID} returns one compilation by its metadata.uid. F5 engineering identified this endpoint as the correct method for the fix.
  • Upgrading NGF to 2.7.2 does not resolve this issue.
