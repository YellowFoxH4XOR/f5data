Description

The Application DoS and Bot Defense (v14.1+) profiles do not use the policy setting configured in the ASM policy to "Trust XFF Header".  If not configured correctly this can result in the source IP of the upstream proxy device being used for TPS calculations and logging instead of the actual client IP.  False positives and improper reporting based on source IP may cause interruptions in service.  The equivalent setting to trust an HTTP header containing the client source IP is found in the HTTP profile configuration.

Environment

  • Trusted upstream proxy is inserting an X-Forwarded-For or equivalent source IP HTTP header.
  • Upstream SNAT is changing source IP.
  • Client IP logging or enforcement is required with Application DoS or Bot Profiles.

Cause
X-Forwarded-For (XFF), or equivalent client IP headers, must be configured to be trusted in the HTTP profile for use with Bot Defense and Application DoS profiles.  If the setting "Accept XFF" is not enabled in the HTTP profile associated with the virtual server using bot or DoS, then the source IP of the traffic as it arrives to the BIG-IP will be used instead.

Recommended Actions

  1. Determine the name of the trusted source IP header in your environment.  Common names are X-Forwarded-For (default), True-Client-IP, X-Client-IP, etc
    Note: Ensure this header name is inserted by a trusted source.  If you do not trust the header showing the original client IP it may be maliciously altered.
  2. Create a new HTTP profile or modify the existing HTTP profile for the virtual server. 
    Note: In general, F5 does not recommend altering the default HTTP profile.  Creating a custom profile is preferred. 
  3. Enable "Accept XFF" in the HTTP profile.
  4. If the name of the trusted header is NOT "X-Forwarded-For" you must configure the header name as the value for "XFF Alternative Names"
  5. Apply the HTTP profile to the virtual server which also uses the DoS or Bot profiles.
