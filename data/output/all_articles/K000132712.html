Description

When a Virtual Address is created, the system associates it with a Traffic Group. The following system configuration determines the Traffic Group to which the newly created object belongs by default:
 

  • GUI:
System > Users : Partition List > Common > Redundant Device Configuration > Traffic Group
  • CLI:
#tmsh list sys folder / 
sys folder / { 
    device-group /Common/device-group-1 
    hidden false 
    inherited-devicegroup false 
    inherited-traffic-group false 
    traffic-group /Common/traffic-group-1 
} 
#tmsh list sys folder /Common 
sys folder /Common { 
    device-group /Common/device-group-1 
    hidden false 
    inherited-devicegroup true 
    inherited-traffic-group true 
    traffic-group /Common/traffic-group-1 
}

 

Take the most common 2+0 architecture as an example:

 

Device A is the Active device of traffic-group-1, but for some reason, traffic-group-2 is set as the default traffic group of the Common Partition. Device B is the Active device in traffic-group-2.

A virtual address is first created on Device A, which is allocated to the default traffic-group-2, and then manually changes to traffic-group-1.

The IP address conflict was observed when these modifications are incrementally synced between the clusters.

 

Environment

  • BIG-IP System
  • LTM Provisioned
  • N+M DSC Architecture Configured


Cause

When a virtual address is first created on Device A, since it is not the active device of traffic-group-2, GARP won't be broadcasted on Device A.

When the virtual address is later changed to traffic-group-1, Device A broadcasts GARP immediately since it's the active device of traffic-group-1.

For Device B, the active device of traffic-group-2, it won't broadcast the GARP as the new configuration is not synced yet.

 

When the incremental configuration synchronization occurs, the same changing instructions will be executed on another device one by one.

That means Device B will also first create a virtual address belonging to traffic-group-2 and then change it to traffic-group-1.

 

In this process, when that virtual address is created on Device B, Device B will also broadcast GARP immediately since it's the active device of traffic-group-2.

IP address conflicts occur at this point because that site is available on both 2 devices from the inspection of the other devices on the same L2 network.

When Device B later changes the virtual address to traffic-group-1, since it's not the active device of traffic-group-1, it stops broadcasting GARP.

However Device a is the originator of the synchronization, nor does the extra GARP be sent out, only when new ARP Requests hit on the same L2 network.

 

Recommended Actions

  • The modification of the traffic group property of a virtual address should be done on the active device of the traffic group that the virtual address belongs.
  • Use full sync instead of incremental sync.
