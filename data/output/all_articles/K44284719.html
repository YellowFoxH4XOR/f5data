K44284719: How to use NGINX caching functionality to mitigate Denial of Service attacks

Description

During a Denial of Service attack, you may find that the devices in front of your application servers (for example, BIG-IP or NGINX) are not under undue stress, but your application servers are experiencing higher resource usage. In these instances you may wish to consider the possibility of caching responses in front of the application server to move the load, leaving application servers accessible to legitimate users and potentially frustrating your attackers.

Environment

  • You have a pool of application servers that are under excessive load
  • You have, or can put, NGINX instances in front of those servers
  • This is applicable to NGINX, NGINX Plus and NGINX App Protect

Cause

  • Denial of Service or Distributed Denial of Service attack

Recommended Actions

Consider using the NGINX proxy_cache_* directives to enable caching of content in such a manner as your attackers content will be served from cache while legitimate users content will be served from the target server.

Of particular interest may be:

proxy_cache_key

This controls the NGINX variables used to build the key for each page in the cache, by default it is $scheme$proxy_host$uri$is_args$args - meaning that the query string is included in the key and an attacker could bypass the cache by sending requests like 'http://example.com/test?arg=N' where N is a random number. Consider setting this to the most general key possible that will not cause legitimate users to receive cached responses for other users, for example build the client IP address into the key, e.g.; "proxy_cache_key $scheme$proxy_host$request_uri$remote_addr" This directive can be set at location level in the configuration so consider setting a more general key for static pages and a more specific key for pages that require login or a session to be established.

See the NGINX Variables manual pages in Related Content for more details on what artifacts of the request can be used to generate a cache key.

proxy_cache_methods

By default NGINX only caches responses to GET and HEAD requests. If your attacker is sending POST requests to submit data then you will need to set this to "GET HEAD POST"

proxy_cache_min_uses

If set, this controls the number of times NGINX must see the same request (based on proxy_cache_key) before caching the response. If you have an attacker sending many requests from each attacking IP address, consider setting this to the lowest number possible which will cause attacker requests to hit the cache and legitimate user requests to bypass, e.g., if a legitimate user only sends one request per key, you could set this to 2.

proxy_cache_lock

Setting this to 'on' and setting 'proxy_cache_lock_timeout' means that only one request per proxy_cache_key is allowed to be in-flight at any one time, other requests will be queued in NGINX until the server response is either cached or passed back to the first client in the queue.

proxy_ignore_headers

You may need to configure the cache to ignore headers set by your application server (e.g., Cache-Control)

Additional Information

While testing, consider instrumenting NGINX by adding the following to the relevant server or location configuration and inspecting the header in responses:

add_header X-Cache-Status $upstream_cache_status;
