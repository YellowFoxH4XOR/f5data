Description

You got an security advisory reporting that you need to encrypt HTTP persistence cookie. This is relating to the recent report by CISA - "Best Practices to Configure BIG-IP LTM Systems to Encrypt HTTP Persistence Cookies".

Will the change affect existing connection?

Environment

  • HTTP Persistence Cookie

Cause

  • Unencrypted cookie
  • CISA - "Best Practices to Configure BIG-IP LTM Systems to Encrypt HTTP Persistence Cookies"

Recommended Actions

Will the change affect existing connection?

The existing connection is not impacted. The new configuration only effects new connections made after the new configuration is implemented . For further information refer this article K13253: Configuration changes to local traffic objects do not affect existing connections (f5.com).

What is the impact of encrypting cookie in HTTP profile instead of Persistence profile?

Why follow or why is the iHealth Diagnostic tool and CISA advising you to follow this K14784: Configuring cookie encryption within the HTTP profile (f5.com) instead of K23254150: Configuring cookie encryption for BIG-IP persistence cookies from the cookie persistence profile (f5.com) article?

The reason why configuring cookie persistence encryption is done through the cookie persistence profile, instead of the HTTP profile, is because the cookie persistence profile is only responsible for encrypting cookies which are inserted by BIG-IP system. To encrypt the cookies coming from server, you need to configure that cookie name and enable cookie encryption under HTTP profile. By default cookies inserted by BIG-IP are not encrypted. 

Thus depending on the needs of the network you would apply encryption from either profile or both as needed.

How can you find virtual servers which require cookie encryption?

  1. Generate a qkview file. Upload it to iHealth.
  2. Go to the Diagnostics tool and in the search box, search for cookie.
  3. If you see "BIG-IP Cookie Persistence Encryption not enabled" then check which virtual servers may be affected and need cookie encryption. You can follow this article K14784: Configuring cookie encryption within the HTTP profile (f5.com) to configure cookie encryption for the affected virtual server.

How can you verify if the change has taken effect?

Browse your webpage using any browser and Inspect the page (Ctrl+Shift+I)

Go to Application tab and under Storage you should see Cookies.

Before cookie encryption, the cookie must have been something like this

Example:

Set-Cookie: BIGipServerhttp-pool=168430090.20480.0000

After cookie encryption, you should see an encrypted cookie value instead. Which will have random strings in it. This is something which cannot be reverse engineered easily.

Example:

Set-Cookie: BIGipServerhttp-pool=!LHmYFDA0qZyj4NoylBEaDn0/k2wesiGt0ANZhWaAohjULoWFXRc1b/yfibypy1qfBzD51kqvmwzfcy4=;

Additional Information

Why does a virtual server, which is on port 443, need additional cookie encryption via HTTP profile, when entire data is already encrypted which also includes the cookie? This is true, when MitM attack happens they do not see actual data or the cookie in it. What if it is not MitM, but just accessing the web application as a normal user. Once the 3 WHS and SSL handshake is completed, you are seeing the data, which includes the HTTP response headers, where you can see the unencrypted Set-Cookie header. This details can be used for malicious purpose. If the cookie is encrypted, then even a normal user will not able to decrypt the cookie information. This helps in preventing the method of reconnaissance or espionage by an attacker.

The default cookie persistence (HTTP Cookie Insert) contains server information which can be reverse engineered (as mentioned below encoding process) to gather the information. Encrypting makes it secure. Depending on the network setup, pool member information with an HTTP cookie may not pose a security risk. In an environment where the pool members are accessible without going through the BIG-IP system, the ability to map, profile, and directly access the servers may pose a security risk.

Note: For BIG-IP persistent cookies, the default cookie name is BIGipServer<pool-name>. If you have changed default cookie name then you will see the configured cookie name rather than the default BIGipServer<pool_name> format.

  • IPv4

    BIGipServer<pool_name>=<Encoded IP Address>.<Encoded Port>.0000

  • IPv6
