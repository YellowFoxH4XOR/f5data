Topic

When multiple monitors are applied to a pool member, the BIG-IP system may continuously log messages that appear similar to the following example, which indicate that the pool member is up, without logging the status of the monitor that produced the message:

Sep 23 16:03:01 bigip mcpd[1792]: 01070727:5: Pool member 10.5.0.140:22 monitor status up.
Sep 23 16:03:14 bigip mcpd[1792]: 01070727:5: Pool member 10.5.0.140:22 monitor status up.
Sep 23 16:03:22 bigip mcpd[1792]: 01070727:5: Pool member 10.5.0.140:22 monitor status up.
Sep 23 16:03:35 bigip mcpd[1792]: 01070727:5: Pool member 10.5.0.140:22 monitor status up.
Sep 23 16:03:43 bigip mcpd[1792]: 01070727:5: Pool member 10.5.0.140:22 monitor status up.
Sep 23 16:03:55 bigip mcpd[1792]: 01070727:5: Pool member 10.5.0.140:22 monitor status up.

This message pattern indicates that enough monitors are successful for the BIG-IP system to mark the pool member up, but one or more of the set of monitors applied to the pool member is failing intermittently.

The BIG-IP system logs pool member status messages only when the status of a monitor applied to the pool member changes. Each time any monitor applied to a pool member changes state, the status of the pool member is logged with a single message similar to the preceding example message. It is important to realize that while the overall status of the pool member itself is logged, the status of the monitor for which the state changed is not logged. This behavior results in the logging of this counter-intuitive message sequence when multiple monitors are applied to a pool member and some of them fail.

The example log messages above were generated by applying two service-specific monitors to a pool member running two services, and only requiring one of the monitors to succeed. One service was intermittently disabled, causing one of the monitors to transition repeatedly between the up and down states. Therefore, although a specific monitor has failed or succeeded, that status is not logged. Instead, the BIG-IP system logs the pool member's status as up, since the minimum monitor's threshold is still met. Only when the minimum number of successful monitors is not satisfied will the BIG-IP system log a status message indicating that the pool member has been marked down.

To determine the cause of this behavior, you may observe the status of the individual health monitors applied to the affected pool members to identify and correct any problems with the monitor configuration.

Note: For more information about configuring multiple monitors, refer to the BIG-IP Configuration Guide.
