Known Issue

This is the result of a known issue. The HTTP RFC 2616 specifies that line-endings with Carriage Return/Line Feed (CR\LF) that precede a new request should be ignored. The HTTP filter in the BIG-IP LTM does not currently ignore the preceding CR/LF, resulting in the failure of the header removal.

Note: A blank line in HTTP communication consists of two characters: a Carriage Return (CR) followed by a Line Feed (LF). This is typically represented in text as CRLF or CR/LF. This blank line, or termination, is required for effective HTTP communication.

The following example request has a CR/LF preceding the request:

<empty line>
GET / HTTP/1.1
Host: a
Accept-Encoding: gzip, deflate

If an HTTP filter is configured to remove the Accept-Encoding header, as would be the case if compression is being used, you would typically want the BIG-IP LTM to perform the compression and not the server. However, if the BIG-IP LTM were to perform the compression, the removal of the Accept-Encoding header would fail because the filter does not ignore the CR/LF, which is represented by the <empty line>. The following error would then be reported to the /var/log/ltm file:

Error removing clientside Accept-Encoding HTTP header: Not found

F5 Product Development tracked this issue as CR68832, CR69643, and CR69642 and it was fixed in BIG-IP LTM 9.1.3, 9.2.5, 9.3, and 9.4. For information about upgrading, refer to the BIG-IP LTM Release Notes.
