Topic

You should consider using this procedure under the following condition:

  • You need to replace a blade in a VIPRION system that has only one blade installed.

Description

When you replace an existing blade in a VIPRION system that has only one blade installed, depending on the state of the existing blade, you may be able to restore configuration to the new blade using the following methods:

  • If the existing blade is still functional, you can install the replacement blade in the VIPRION chassis while leaving the existing blade in the chassis and let the cluster replicate the configuration to the replacement blade.
  • If the existing blade is no longer functional and you have previous copies of the user configuration set (UCS) archive files taken from the existing blade, you can restore the configuration to the replacement blade using these UCS archive files.

    Note: For VIPRION systems with vCMP guests, the UCS archive file taken from the vCMP host does not contain the configuration of these vCMP guests. As such, you need to ensure that you have previous copies of the UCS archive files taken from both the vCMP host and the vCMP guests in order to restore configuration to these vCMP guests.

  • If the existing blade is no longer functional and you do not have any UCS archive files taken from the existing blade, you have to configure the replacement blade again.

If this single-bladed VIPRION system is the active member of a high-availability pair, you should fail over the system to its functional peer before attempting to perform the replacement. Additionally, F5 recommends that you should always perform blade replacement during a scheduled maintenance window to avoid any potential disruptions to your application environment.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have physical access to the VIPRION system.
  • You have serial console access to the VIPRION system.
  • You have administrative access to the VIPRION system.

Procedures

Depending on the state of the existing blade, you should perform only one of the following tasks:

  • Replacing a functional blade
  • Replacing a non-functional blade and restoring configuration using the UCS archive file
  • Replacing a non-functional blade without any UCS archive file

Replacing a functional blade

If the existing blade is still functional, you can install the replacement blade in the VIPRION chassis while leaving the existing blade in the chassis and allow the cluster to replicate the configuration to the replacement blade. To do so, perform the following procedures:

  • Backing up a UCS archive file
  • Installing the replacement blade
  • Provisioning the vCMP guests to use the newly inserted blade
  • Removing the existing blade

Backing up a UCS archive file

Before performing any blade replacement, you must create a UCS archive file of all vCMP guests if the VIPRION system is provisioned for vCMP and ensure that the UCS archive file is copied to a secure location on a system other than the one from which the UCS archive file was originally created. You must do the same for a VIPRION system that is provisioned to run modules other than vCMP.

  • To create a UCS archive file, refer to K13132: Backing up and restoring BIG-IP configuration files with a UCS archive.
  • To copy the UCS archive file to another location, refer to K175: Transferring files to or from an F5 system.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

Installing the replacement blade

When you have successfully backed up all copies of the UCS archive files, you can install the replacement blade to the VIPRION chassis by inserting the replacement blade into an empty slot on the VIPRION chassis. The VIPRION system automatically performs the following steps before replicating the configuration to the replacement blade:

Important: Before inserting a new or replacement blade in a VIPRION chassis, ensure that the primary member in the cluster is not disabled. For more information, refer to K16749: Inserting a blade into a VIPRION chassis may overwrite the configuration and cause a software upgrade/downgrade.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. The system boots the newly inserted blade.
  2. The system copies software images from the primary blade to the newly inserted blade.

    Note: If the necessary software images are not available on the primary blade, you must obtain these software images from F5 Downloads and import them to the VIPRION system.

  3. The system installs software images on the newly inserted blade to match the boot locations of the primary blade.
  4. The newly inserted blade restarts to complete the software installation.
  5. The system may restart the newly inserted blade an additional time to update the firmware.
  6. The system activates the newly inserted blade's license.
  7. The system places the newly inserted blade online and it becomes active.

For more information on these steps, refer to K13965: Overview of the automated process of joining a newly installed or RMA replacement VIPRION blade to the cluster.

Provisioning the vCMP guests to use the newly inserted blade

By default, if you provision the VIPRION system as a vCMP host, a vCMP guest can use all available slots on the vCMP host. If you have provisioned the vCMP guest to use specific slots, you must ensure that the vCMP guest is provisioned to use both the existing blade and the newly inserted blade. To do so, perform the following procedure:

Impact of procedure: Traffic processing may be disrupted.

  1. Log in to the Configuration utility.
  2. Select vCMP.
  3. Select Guest List.
  4. Select the name of the vCMP guest.
  5. For Properties, select Advanced.
  6. For Number of Slots, select 2.
  7. For Allowed Slots List, select the slot number of the newly inserted blade from the Available list and move it to the Selected list.
  8. Select Update.

The VIPRION system installs and replicates the vCMP guest to the newly inserted blade. Depending on the size and configuration of the vCMP guest, this process can take several hours to fully complete. You can monitor the status of the vCMP guest replication by using the tmsh show vcmp guest and tmsh show vcmp virtual-disk commands. After the VIPRION system completes the replication, the newly inserted blade joins the vCMP guest cluster so that the vCMP guest runs on both blades. You can confirm that the vCMP guest is running on both blades by entering the tmsh show sys cluster command in the vCMP guest command line.

Removing the existing blade

If you prefer, you can leave the newly inserted blade in its current slot and remove the existing blade. Alternatively, you can remove the existing blade from its current slot and move the newly inserted blade to the slot of the removed blade. To do so, perform either one of the following procedures:

  • Leaving the newly inserted blade in its current slot
  • Moving the newly inserted blade to the slot of the blade to be removed

Leaving the newly inserted blade in its current slot

If you decided to leave the newly inserted blade in its current slot, you must perform the following procedure before you remove the existing blade:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility of the VIPRION system (or vCMP host).
  2. Configure the Cluster Member IP Address for the slot of the newly inserted blade if you have not done so previously. You can do so by going to System > Clusters > Management IP Address. For Cluster Member IP Address, enter an IP address for the slot of the newly inserted blade.
  3. Configure the data network configuration to include the interfaces of the newly inserted blade to network elements such as trunks, VLANs, and so on. For information about configuring the network configuration, refer to the relevant chapters of the BIG-IP TMOS: Concepts manual.

    Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

  4. Install the necessary network cables to the interfaces on the newly inserted blade.
  5. For VIPRION systems with vCMP guests, you must perform the following additional procedure for each deployed vCMP guest:
    1. Disable the existing blade in the vCMP guest by going to System > Clusters > Properties. Select the check box for the slot for the existing blade and select Disable/Yield. This shuts down the blade for this vCMP guest only.
    2. Verify that data network connectivity for the vCMP guest remains operational by using methods such as a ping test on network peers.
    3. Repeat these steps for each deployed vCMP guest.
  6. Log in to the command line of the VIPRION system (or vCMP host).
  7. Remotely log in to the blade that you’re removing using the following command syntax:

    ssh slot<number>

    For example, if you are removing the blade in slot 1, enter the following command:

    ssh slot1

  8. Shut down the blade by entering the following command:

    shutdown -h now

  9. Wait for the blade to completely shut down before proceeding to remove the blade from the VIPRION system.

Moving the newly inserted blade to the slot of the blade to be removed

If you decide to move the newly inserted blade to the slot of the blade you are going to remove, you must perform the following procedures:

Impact of procedure: Traffic processing will be disrupted.

  1. Log in to the command line of the VIPRION system (or vCMP host).

    Note: F5 recommends that you use serial console access for this procedure.

  2. For VIPRION systems with vCMP guests, you must shut down all deployed vCMP guests by entering the following command:

    tmsh modify vcmp guest all state provisioned

    You can monitor the shutdown of all vCMP guests using the tmsh show vcmp guest command. Proceed to the next step when all vCMP guests have completely shut down.

  3. After the guests are moved to the provisioned state, save the configuration so that the state is preserved through a restart by entering the following command:.

    tmsh save sys config

  4. Shut down the VIPRION system (or vCMP host) by entering the following command:

    clsh shutdown -h now

  5. When the VIPRION system is completely shut down, remove both blades from the VIPRION system and install the replacement blade into the slot previously occupied by the blade that needs to be replaced.
  6. Wait for the replacement blade to boot up completely.

    Note: You can monitor the progress using serial console access.

  7. For VIPRION systems with vCMP guests, you must perform the following, additional procedure:
    1. Boot up one vCMP guest by using the following command syntax:

      tmsh modify vcmp guest <name> state deployed

      In the previous syntax, note the following:

      - <name> is the name of the vCMP guest.

    2. Wait for the vCMP guest to be completely booted up before accessing it.
    3. When the vCMP guest is up, log in to the vCMP guest and verify its network connectivity and configuration.
    4. Boot up the remaining vCMP guests one at a time by repeating the previous steps.

      Note: Before attempting to deploy your guests, make sure that you have uploaded the installed images to /shared/images, and that each guest's Initial Image and Initial Hotfix are set to the correct version so that it can create the new vDisk on the new blade.

Replacing a non-functional blade and restoring configuration using the UCS archive file

If the existing blade is no longer functional and you have previous copies of the UCS archive files taken from the existing blade, you can restore the configuration to the replacement blade using these UCS archive files after removing the existing blade and installing the replacement blade to the chassis. For information about removing and installing blades to/from a chassis, refer to the About installing blades section of the platform guides for your VIPRION platform. When you have removed the existing blade and installed the replacement blade to the chassis, you must perform the following tasks:

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

  • Setting up a serial console to the blade
  • Configuring the networking options for the management interface
  • Ensuring that the replacement blade is running the same software version as the UCS archive file
  • Restoring the VIPRION system configuration
  • Restoring the vCMP guest

Setting up a serial console to the blade

When a replacement blade is started up on a VIPRION chassis, the blade runs with the factory-default cluster configuration, which contains no cluster information, including no management addresses. The only way to connect to the blade is through the serial console. The default serial console baud rate on VIPRION platforms is 19200. For information about setting up a serial console for VIPRION platforms, refer to the following articles:

  • K7683: Connecting a serial terminal to a BIG-IP system
  • K9156: Setting the baud rate of the serial console port (9.x - 10.x)
  • K587: Pinouts for serial terminal cables used to connect the 9-pin serial port on F5 products

Configuring the networking options for the management interface

When the installed blade is booted up, you need to configure the networking options for the management interface by performing following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Using the serial port, connect a terminal emulator to the BIG-IP system.
  2. From the installed blade command line, start the F5 Management Port Setup tool by entering the following command:

    config

  3. Enter the appropriate data to assign an IP address, netmask, and default management route to the management interface.
  4. Restart the blade by entering the following command:

    reboot

  5. When the blade is back up, connect the management port into your network, as appropriate.

    Note: If you do not have serial access to the device, you can set the management network settings by using the LCD display and keypad on the front panel of the device. For more information about this process, refer to the appropriate platform guide for your hardware platform.

Ensuring that the replacement blade is running the same software version as the UCS archive file

Before you upload and restore the VIPRION system configuration using previous copies of the UCS archive files, you must ensure that the replacement blade is running the same software version as the UCS archive file taken previously from the non-functional blade. If the software on the replacement blade does not match that of the UCS archive file taken previously from the non-functional blade, the system may not load the UCS archive file to restore the configuration.

You can determine the software version which the UCS archive file is taken from by checking the contents of the config/ucs_version file in the UCS archive file. To view the contents of the config/ucs_version file in the UCS archive file, refer to K8465: Viewing and extracting the contents of an encrypted UCS archive file. To determine the software version of the replacement blade, refer to K8759: Displaying the BIG-IP software version.

If you have determined that the software version of the replacement blade matches the software version of the UCS archive file, you can proceed to the next procedure.

If the software version of the replacement blade does not match the UCS archive file, then you must first install the same software version as the UCS archive file from the non-functional blade to the replacement blade. Depending on whether you need to upgrade or downgrade the software version of the replacement blade, refer to the tasks listed in either of the following documents:

  • BIG-IP Systems: Upgrading 11.x software

    Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

  • K14568: Downgrading BIG-IP software (10.x - 15.x)

Restoring the VIPRION system configuration

After you have ensured that the replacement blade is running the same software version as the version the UCS archive file is taken from, you can upload the UCS archive file using SCP, HTTPS, or FTP through the management interface. For assistance transferring the UCS archive from another BIG-IP device using SCP, from a remote FTP server using FTP, or from an attached workstation using HTTPS, refer to K175: Transferring files to or from an F5 system.

Important: If the UCS archive file is previously taken from a vCMP host with deployed vCMP guests, you must ensure that you provision vCMP for the VIPRION system before proceeding to restore the configuration. For more information, refer to K15508: vCMP must be provisioned before loading UCS files containing deployed or provisioned vCMP guest instances.

After the UCS archives have been transferred to the VIPRION system, you can restore the configuration by installing the UCS archives to the VIPRION system. To do so, perform the following procedure on the VIPRION system:

Impact of procedure: The following procedure should not have a negative impact on your system.

  1. Log in to the TMOS Shell (tmsh) by entering the following command:

    tmsh

  2. Restore the UCS archive file by using the following command syntax, replacing <path/to/UCS> with the full path of the UCS archive file you want to restore:

    load /sys ucs <path/to/UCS> no-license

    If you do not specify the path, the BIG-IP system performs as if the UCS archive file is located in the default /var/local/ucs directory.

  3. If the UCS archive file was encrypted with a passphrase during the backup, the system prompts you to enter the passphrase for the archive file.
  4. If the UCS archive file contains SSL key encrypted passphrases, you must replace each encrypted passphrase with the plain text passphrase by editing the /config/bigip.conf file with a text editor in the bash shell. You can access the bash shell by typing the following command:

    run /util bash

    Then, edit the /config/bigip.conf file with a text editor, for example: vi. Once you complete the changes, save the changes and exit the text editor.
  5. Stop the BIG-IP system processes by entering the following command:

    bigstart stop

  6. Remove the previous master key by entering the following command:

    rm /config/bigip/kstore/master

  7. Remove the previous mcpd binary database by entering the following command:

    rm /var/db/mcpdb.*

  8. Start the BIG-IP system processes by entering the following command:

    bigstart start

  9. Exit the bash shell by entering the following command:

    exit

  10. Reload the configuration by entering the following command:

    load /sys config

    The system automatically encrypts the plaintext passphrase.

  11. Save the configuration with the encrypted passphrase by entering the following command:

    save /sys config partitions all

<Restoring the vCMP guest

For VIPRION systems with vCMP guests, the UCS archive file taken from the VIPRION system (vCMP host) contains the vCMP guests provisioning information but not their corresponding virtual disk images. As a result, you need to perform additional steps to restore the vCMP guests with their corresponding previous UCS archive files. To avoid potential resource exhaustion issue, F5 recommends that you restore one vCMP guest at any one time. To do so, perform the following steps:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility of the vCMP host.
  2. Go to vCMP > Guest List.
  3. Wait for the re-creation of the virtual disk image and software installation for the vCMP guest to complete. You can monitor the progress in the vCMP host using the tmsh show vcmp guest and tmsh show vcmp virtual-disk commands.
  4. When the status of the vCMP guest is running, upload its UCS archive file taken previously using SCP, HTTPS, or FTP through the management interface. For assistance transferring the UCS archive from another BIG-IP device using SCP, from a remote FTP server using FTP, or from an attached workstation using HTTPS, refer to K175: Transferring files to or from an F5 system.
  5. Log in to tmsh of this vCMP guest by entering the following command:

    tmsh

    Note: F5 recommends that you use the vconsole utility on the vCMP host to connect to the vCMP guest. For more information about the vconsole utility, refer to K15372: Overview of the vconsole utility.

  6. Restore the UCS archive file by using the following command syntax, replacing <path/to/UCS> with the full path of the UCS archive file you want to restore:

     

    load /sys ucs <path/to/UCS>

    If you do not specify the path, the BIG-IP system performs as if the UCS archive file is located in the default /var/local/ucs directory.

  7. If the UCS archive file was encrypted with a passphrase during the backup, the system prompts you to enter the passphrase for the archive file.
  8. If the UCS archive file contains SSL key encrypted passphrases, you must replace each encrypted passphrase with the plain text passphrase by editing the /config/bigip.conf file with a text editor in the bash shell. You can access the bash shell by typing the following command:

    run /util bash

    Then, edit the /config/bigip.conf file with a text editor, for example: vi. After you complete the changes, save the changes and exit the text editor.

  9. Stop the BIG-IP system processes by entering the following command:

    bigstart stop

    Important: If you are logging in remotely to the vCMP guest using SSH, running this command terminates your SSH access and you can regain access to the vCMP guest using only the vconsole utility.

  10. Remove the previous master key by entering the following command:

    rm /config/bigip/kstore/master

  11. Remove the previous mcpd binary database by entering the following command:

    rm /var/db/mcpdb.*

  12. Start the BIG-IP system processes by entering the following command:

    bigstart start

  13. Exit the bash shell by entering the following command:

    exit

  14. Reload the configuration by entering the following command:

    load /sys config

    The system automatically encrypts the plaintext passphrase.

  15. Save the configuration with the encrypted passphrase by entering the following command:

    save /sys config partitions all

  16. Force the vCMP guest to the offline state by entering the following commands:

    modify /sys cluster default min-up-members 5
    modify /sys cluster default min-up-members-enabled yes

    The vCMP guest enters an offline state; however, its self IP addresses is still reachable. This facilitates the next step on verifying the network connectivity with minimal impact on the application environment.

  17. Connect all the network cables to their corresponding network interfaces on the vCMP host and verify the vCMP guest connectivity.
  18. After you have verified the connectivity, you can bring the vCMP guest online by entering the following commands:

    modify /sys cluster default min-up-members 1
    modify /sys cluster default min-up-members-enabled no

    Note: The default value for min-up-members setting is 1 and min-up-members-enabled setting is no. You should change it to the value that you have previously configured if you used non-default values for these two settings.

  19. Repeat all previous steps to restore each of the remaining vCMP guests.

Replacing a non-functional blade without any UCS archive file

If the existing blade is no longer functional, and you have no UCS archive files taken from the existing blade, you have to manually rebuild the replacement blade configuration. Additionally, if the VIPRION system is configured with vCMP guests, and you do not have any UCS archive files taken from the vCMP guests, you have to rebuild each of the vCMP guests configurations manually. F5 does not store customer's configuration files and is unable to provide any information pertaining to the specific application environment in which the system is deployed. To rebuild the configuration, you may reference the manuals that are relevant to your application environment.
