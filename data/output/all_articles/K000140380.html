Configuring an external log consumer for a BIG-IP Next instance halts telemetry reception in BIG-IP Next Central Manager and previously configured log consumers.

This issue occurs when the following condition is met:

  • You configure an external log consumer for the BIG-IP Next instance using either the BIG-IP Next instance API or the Log Management tab for the instance in the BIG-IP Next Central Manager webUI.

Impact

The BIG-IP Central Manager stops receiving telemetry from managed BIG-IP Next instances where log consumers have been configured. Only the most recently configured external log consumer will continue to receive instance logs while previously configured log consumers will stop receiving instance logs. After 30 days, all external log consumers for an instance will stop receiving instance logs.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • If no metrics are received from a BIG-IP Next instance for over 3 minutes, an alert will be raised on the BIG-IP Next Central Manager with the following summary:

    Instance has not received stats for over 3 minutes

  • When you select the instance in BIG-IP Next Central Manager, you no longer see telemetry displayed in the Health, Traffic, or Network Interface tabs.
  • You stop receiving BIG-IP Next instance logs at the configured remote log consumers.
  • When you select an application in BIG-IP Next Central Manager, you will not see recent telemetry displayed in the Data Metrics tabs.
  • If using WAF, when you navigate to Security > Event Logs, you will not see recent event logs displayed.

Workaround

To work around this issue, you can use the provided scripts to determine if your systems are affected and correct the problem. You can download and run the find_broken_telemetry_instances.sh diagnostic script to check for any affected BIG-IP Next instances managed by the BIG-IP Next Central Manager. For affected BIG-IP Next instances, you can download and run the update_cm_logger.sh script to fix the problem and restore telemetry streaming between all instances to the BIG-IP Next Central Manager. To do so, perform the following procedure:

Impact of workaround: Performing the following procedure will delete all configured remote log consumers for all BIG-IP Next instances managed by the BIG-IP Next Central Manager. You will not be able to reconfigure remote log consumers again using the BIG-IP Next Central Manager webUI until you upgrade to a version containing the fix for this issue. Additionally, if you attempt to configure remote log consumers using the BIG-IP Next instance API after performing this procedure, this issue will be triggered again and the BIG-IP Next Central Manager will stop receiving telemetry until you perform this procedure again. 

  1. Log in to the BIG-IP Next Central Manager CLI as admin. If the BIG-IP Next Central Manager is running in HA mode, you should be able to perform this procedure on any node.

    Note: If you do not have SSH access to the BIG-IP Next Central Manager, log in to the BIG-IP Next Central Manager console using the hypervisor.

  2. Download the  find_broken_telemetry_instances.sh and update_cm_logger.sh scripts using the following commands:

    curl -s https://raw.githubusercontent.com/askf5/K000140380/main/find_broken_telemetry_instances.sh -O

    curl -s https://raw.githubusercontent.com/askf5/K000140380/main/update_cm_logger.sh -O

  3. Modify the file permissions for both scripts by entering the following command:

    chmod 744 ./find_broken_telemetry_instances.sh ./update_cm_logger.sh

  4. Enter the following command to run the diagnostic script. You will be prompted for the BIG-IP Next Central Manager admin password:

    ./find_broken_telemetry_instances.sh

    Output will appear similar to the following example if there are no affected BIG-IP Next instances:

    Retrieving device inventory...
    Processing device big-ip-next (10.10.10.100)...
    ---
    Total instances impacted: 0 out of 1

    If the script locates affected BIG-IP Next instances, the output will appear similar to the following example:

    Retrieving device inventory...
    Processing device big-ip-next (10.10.10.100)...
    Hostname 'server.ado.svc' not found in services for device 'big-ip-next' (10.10.10.100)
    ---
     Total instances impacted: 1 out of 1

  5. If the output of the script returns any affected BIG-IP Next instances, enter the following command to run the second script which will correct the issue. The script will fix all BIG-IP Next instances managed by the BIG-IP Next Central Manager in a single run:

    ./update_cm_logger.sh

    Output should appear similar to the following example:

    Initial Expiry Date: 2024-12-29T08:36:32Z
    Manually triggered issuance of Certificate default/mbiq-ado-vault-client-cert
    Renew command executed for mbiq-ado-vault-client-cert
    Waiting for expiry date to change...
    Expiry Date Updated: 2024-12-29T08:38:02Z
    Certificate renewal process completed.
    Restarting CM device service
    deployment.apps/mbiq-device-feature restarted
    Updating BIG-IP Next instances remote loggers
    Updated BIG-IP Next instance: 10.10.10.100 at 2024-08-03 08:38:27
    Done.

  6. After running the update_cm_logger.sh script, it may take a few minutes, depending on the number of BIG-IP Next instances deployed on BIG-IP Next Central Manager, before normal logging functionality returns. You can check to see that new data is logged for the previously affected instances, such as WAF event logs and app data metrics. You can also validate the script was successful by running the find_broken_telemetry_instances.sh script from step 4 again and checking that the output reflects Total instances impacted: 0 out of <#>.
