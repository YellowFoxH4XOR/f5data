Topic

If you use the HTTP TRACE method, the system may allow an attacker to access cookie data.

You should consider using these procedures under the following conditions:

  • You have configured your BIG-IP system to perform cookie encryption for either application cookies or the BIG-IP persistence cookie.
  • The origin web server (OWS) is configured to respond to HTTP TRACE requests per the Internet Engineering Task Force (RFC 7231).

    Note: This link takes you to a resource outside of AskF5. The third party could remove the document without our knowledge.

Description

If the BIG-IP system is configured to perform cookie encryption for application cookies or the BIG-IP persistence cookie, and the OWS is configured to respond to HTTP TRACE requests, then an incoming TRACE request with encrypted cookies will cause the following sequence of events to occur:

  • The BIG-IP system decrypts the cookies and forwards the request to the OWS.
  • Per the HTTP RFC, the OWS reflects the incoming request (including the decrypted cookies) back as a response.
  • The client receives the decrypted cookies.

As noted, this issue applies to user application cookies (for example, those encrypted by the HTTP profile) and persistence cookies (for example, those with BIG-IP cookie persistence with encryption enabled).

Recommendations

Where possible, F5 recommends that you disable the TRACE method as a good security practice, as the TRACE method can lead to the OWS reflecting any potentially sensitive information. You can accomplish this recommendation using one or more of the following options:

  • In BIG-IP 12.0.0 and later, configure the BIG-IP HTTP profile assigned to your virtual server to reject unknown methods, and then remove the TRACE method from the list of known methods.
  • Use an iRule to specifically block the TRACE method.
  • Use the BIG-IP ASM system to block the TRACE method.

    Note: BIG-IP ASM policies allow only the HTTP GET, POST, and HEAD methods, by default. For more information, refer to K12312: Overview of BIG-IP ASM Illegal Method violations.

  • Configure the OWS to reject requests using the TRACE method.

    Note: This is the default configuration for many Apache versions. Refer to your specific vendor documentation for configuration options and default settings.

The following section includes procedures for rejecting the TRACE method using either the BIG-IP HTTP profile or an iRule.

Prerequisites

You must meet the following prerequisite to use these procedures:

  • Have administrative access to the Configuration utility

Procedures

  • Using the HTTP profile to reject TRACE requests (BIG-IP 12.0.0 and later)
  • Using an iRule to reject TRACE requests

Using the HTTP profile to reject TRACE requests (BIG-IP 12.0.0 and later)

By default, the HTTP profile Known Methods contains a list of the most common HTTP request methods, including TRACE, and the Unknown Method option is set to Allow, which allows all methods regardless of whether they are known. This procedure causes the system to reject all unknown methods, and removes TRACE from the list of known methods, which effectively causes the system to reject TRACE requests.

Impact of procedure: When you set the Unknown Method to Reject, all unknown methods are rejected; this is not limited solely to TRACE requests.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Profiles > Services > HTTP.
  3. Click the Name of your HTTP profile.
  4. In the Enforcement section:
    1. Select the checkbox in the Unknown Method box, then select Reject from the menu.
    2. Select the checkbox in the Known Methods box.
    3. In the Enabled Methods list in the Known Methods box, locate and click TRACE, then click Delete.
  5. To save your changes, click Update.

Using an iRule to reject TRACE requests

Impact of procedure: The following example iRule may not apply to all environments. F5 recommends that you create an iRule that works best for your application environment. Adding an iRule increases the resources that the associated virtual server uses. Depending on the type and volume of the connections, this processing may introduce noticeable latency. F5 recommends that you test any such changes in an appropriate environment.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules.
  3. Click Create.
  4. In the Name box, type a name.
  5. In the Definition box, to reject connections for a particular HTTP request method, enter the following iRule syntax:

    when HTTP_REQUEST {
      if {[string tolower [HTTP::method]] contains "<x>"}{
        log local0. "Forbidden HTTP method ([HTTP::method]) attempted by [IP::client_addr]"
        reject
      }
    }

    Note: In the previous syntax, <x> indicates the name of the specific HTTP request method you want the iRule to filter.

    For example, to reject requests containing the TRACE method, enter the following text:

    when HTTP_REQUEST {
      if {[string tolower [HTTP::method]] contains "trace"}{
        log local0. "Forbidden HTTP method ([HTTP::method]) attempted by [IP::client_addr]"
        reject
      }
    }

    The previous iRule example filters all HTTP requests for the string trace in the request method. When the string is matched, the system rejects the connection, and in the /var/log/ltm file, logs a message similar to the following example:

    info tmm[12345]: Rule /Common/rule_reject_method <HTTP_REQUEST>: Forbidden HTTP method (TRACE) attempted by 10.11.12.1

    Note: The logging statement in this rule is optional.

  6. Click Finished.
  7. Assign the iRule to your virtual server.
