K33236043: SSL Orchestrator prompt ''One or more SSL Orchestrator configurations are still upgrading'' after upgade V16.0 to V16.1

Type
Support Solution
Published
2021-12-15
Updated
2023-02-21
Applies to
  • F5 App Protect
  • F5 SSL Orchestrator: 16.1.X, 16.1.2, 16.1.1, 16.1.3, 16.1.0
Source
https://my.f5.com/manage/s/article/K33236043

Description

Upgrade the SSLO HA pair from V16.0 to V16.1, maybe get the prompt below in the Configuration Utility:

SSL Orchestrator >> Configuration:

One or more SSL Orchestrator configurations are still upgrading. If the upgrade persist longer than 5 minutes, review /var/log/restnoded/restnoded.log for error and take corrective action to avoid additional errors....

Meanwhile, the SSL Orchestrator object is out of sync, some topology lost.
The LTM objects (created by SSL Orachstrator) lost. Perform the configuration sync cannot fix it too.

Environment

  • SSL Orchestrator HA pair
  • Upgrade V16.0 to V16.1

Cause

Under investigation.

Recommended Actions

Please perform the following steps.

  1. Reboot to the original version, like v16.0.

  2. Verify the HA pair is in a healthy state.

Sync the LTM configuration.
Check the SSLO HA status, make sure it is green.

  1. Create a UCS backup for both device.

  2. Remove any SSL Orchestrator created object dependency on non-SSL Orchestrator created objects.

If there is any SSLO object that is referring to an object created outside SSLO such as Virtuals, irules etc. These references have to be removed before starting the upgrade process. These references may have been made by the admins intentionally. Most of the times SSLO created objects have the prefix "sslo". If you do not see this prefix, it could be an outside reference.

  1. Remove circular dependencies between SSLO created objects.

BIG-IP config file could be looked at to find the app references to make sure there is no circular dependency. For example, if there is config A referring to config B, this in turn is referring to config C and config C needs config A. This is a circular dependency and could lead to upgrade failure.

  1. Remove bound, binding, or error state.

Please use the below command to verify there are no iapp blocks in BINDING, BOUND or ERROR state
restcurl -i -u admin:admin /mgmt/shared/iapp/blocks?\$filter=state%20eq%20%27BOUND%27%20and%20state%20eq%20%27BINDING%27%20and%20state%20eq%20%27ERROR%27
Output of this command should be something like this
{
  "selfLink": "https://localhost/mgmt/shared/iapp/blocks",
  "totalItems": 0,     --> Should be zero
  "items": [],
  "generation": XXXX,    -->Ignore this
  "kind": "shared:iapp:blocks:blockcollectionstate",
  "lastUpdateMicros": XXXXXXX     --> Ignore this
}

  1. Perform another UCS backup.

  2. Install 16.1.0 again on a new volume.

  3. Boot both devices in the new volume.

  4. Verify ISO upgrade is successful.

    Open the bash, confirm the restnoded, restjavad, and ltm logs are running to confirm the ISO installation was successful.

You can run the command below from both device, the the log should not grow (or grow very slow).
tailf /var/log/restnoded/restnoded.log

  1. Sync the LTM configuration, as it is "Change Pending" since boot up.

  2. Install RPM on active device (Check restnoded logs to be settled down).

Login to active device, Configuration Utility via admin or other administrator account.
Naviagte to iApps  ››  Package Management LX, import f5-iappslx-ssl-orchestrator-16.1.0-9.0.24.noarch.
We should see the restnoded log is printing, waiting until the log is not printing, like 1 minutes.

  1. Install RPM on the standby device

Login to standby device, Configuration Utility via admin or other administrator account.
Naviagte to iApps  ››  Package Management LX, import f5-iappslx-ssl-orchestrator-16.1.0-9.0.24.noarch.
Once both devices are on the same RPM version, the Configuration Upgrade is automatically triggered. It should take approximately xx minutes to complete (like more than 10 minutes).
At this step, please monitor the restnoded logs on both device, we should see the log is printing quickly, please wait until it is not printing log quickly.
Now, if we monitor the virtual server list, we can see, on the standby device, only see the virtual server which are not created by SSLO, on the active device, the virtual server list is changing, as SSLO will create more virtual servers.

  1. When the Configuration Upgrade is complete, the Configuration Synchronization (ConfigSync) needs to be triggered.

Before sync, the active device show normal virtual servers and SSLO virtual servers, but standby device only show the normal virtual servers, please sync the configuration from active device to standby device. Then both device show all virtual servers.
Caution: The configuration on the BIG-IP device that triggered the Configuration Upgrade should be pushed to the other device. If not, the deployed configuration will be lost.

  1. Restore all dependencies (in the step 4 5 6) and check to make sure system is running and healthy.

Note: Please schedule a maintanance window for this operation, as reboot / and upgrade operation maybe cause the business impact.
