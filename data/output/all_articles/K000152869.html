K000152869: Troubleshooting TLS Handshake Failures and PR_CONNECT_RESET_ERROR with SSL Bridging on F5 BIG-IP

Description

When implementing SSL bridging on F5 BIG-IP (LTM), clients connecting to a Virtual Server via HTTPS may encounter TLS handshake failures. The connection is reset by the client immediately after receiving the Server Hello message from the server, resulting in browser errors such as:

PR_CONNECT_RESET_ERROR

Packet captures typically reveal:

  • Successful TCP handshake.
  • Client sends a TLS 1.3 ClientHello (with SNI).
  • Server responds with ServerHello and additional handshake messages.
  • Client immediately issues a TCP RST (reset) following the ServerHello, terminating the session.
  • No TLS "Finished" message or application data is exchanged.

Environment

  • Product: F5 BIG-IP LTM
  • Version: 16.1.4
  • Configuration: SSL bridging using both client-side and server-side SSL profiles
    • Client SSL Profile: Custom certificate/chain, TLS 1.3 enabled, session resumption observed
    • Server SSL Profile: Custom certificate/key
  • Additional Network Element: Inline IPS (Intrusion Prevention System) with SSL certificate inspection enabled

Cause

TLS handshake failures and connection resets are caused by SSL certificate inspection being enabled on an inline IPS device. The IPS interferes with the TLS handshake process between the client and the F5 BIG-IP Virtual Server, prompting clients to terminate connections prematurely.

 

Recommended Actions

  • Disable SSL certificate inspection on the IPS for traffic between clients and the F5 BIG-IP Virtual Server.
  • Confirm that all certificates used in client-side SSL profiles are signed by trusted CAs present in client trust stores.
  • After changing certificates, ensure all intermediate/root certificates are correctly installed and trusted by clients.
  • If session resumption is configured, clear both client and server SSL session caches after any certificate changes.
  • For persistent issues, capture packet traces at both endpoints and across all intermediate network devices (including IPS) to pinpoint where resets occur.
