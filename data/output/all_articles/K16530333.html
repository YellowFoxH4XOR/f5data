Description

Mutual TLS enforces all workload pods, both client and server, to provide their identity while connecting to other services running inside the mesh cluster. Aspen Mesh enables mTLS by default in the whole mesh cluster. The identity is implemented with X.509 certificates. Each Envoy istio-proxy running alongside with the workload container is provisioned with the certificate managed the Istiod service. Beginning in Aspen Mesh 1.6, Envoy proxies use the SDS (Secret Discovery Service) interface to fetch the certificates from Istiod via the istio-agent service running in the istio-proxy container. The istio-agent forwards the request to Istiod where the certificate is created and signed by the CA certificate provisioned in the cluster. The istio-agent service monitors the expiration of the workload certificate and repeats the certificates creation process periodically before the certificates expire. For more information on the security concepts in Istio, refer to the Security section of the Istio documentation.

In this article we will focus on how to modify the workload TLS certificates’ validity period.

Environment

  • Kubernetes: 1.17x, 1.18.x, 1.19.x, 1.20.x  
  • Aspen Mesh: 1.6.x, 1.9.x  

Cause

None

Recommended Actions

None

Additional Information

  • Verify workload certificate validity

Verify workload certificate validity

The default validity period for every workload certificate is set to 24 hours. You can verify the workload certificate validity by inspecting the certificate offered by the service that has mTLS enabled. You can create a pod without an istio-proxy sidecar with the openssl tool installed and use the following command to inspect the server certificate.

openssl s_client -connect <pod-IP>:8000 2>/dev/null | openssl x509 -text | grep Validity -A2

The following example shows the certificate is valid for 24 hours:

Validity
            Not Before: Jun 21 11:27:59 2021 GMT
            Not After : Jun 22 11:27:59 2021 GMT

Modify the validity of certificates globally for all workloads

You can modify the validity of TLS certificates globally, for all workloads by modifying the Helm values yaml file that was used to install the istiod Helm chart. To modify the TTL globally, perform the following procedure:
  1. Add the workloadCertTtl field in the global.certificateTTL section and configure the TTL to 48h for example:

    global:
      certificatesTTL:
        workloadCertTtl: 48h

  2. Upgrade the Istiod chart configuration by using the following command syntax:

    helm upgrade istiod manifests/charts/istio-control/istio-discovery \
       --namespace istio-system \
       --value <YOUR_VALUES_YAML_FILE>

  3. Restart the service pod to recreate certificate or wait until the certificate expires and istio-agent will provision a new certificate.
  4. Verify the certificate is valid for the specified period with the following command syntax:

    openssl s_client -connect <pod-IP>:8000 2>/dev/null | openssl x509 -text | grep Validity -A2

    The following example shows the certificate is valid for 48 hours:

    Validity
                Not Before: Jun 21 20:33:52 2021 GMT
                Not After : Jun 23 20:33:52 2021 GMT

Modify the certificate validity for a pod overriding the global setting

To modify the TTL for a pod and override the global setting, perform the following procedure:

  1. Add the following annotation to your pod or deployment yaml file and configure the TTL to 72h for example:

    proxy.istio.io/config: |
      proxyMetadata:
        SECRET_TTL: 72h

  2. Restart the pod or wait until the certificate expires and istio-agent will provision a new certificate.
  3. Verify the certificate is valid for the specified period using the following command syntax:

    openssl s_client -connect <pod-IP>:8000 2>/dev/null | openssl x509 -text | grep Validity -A2

    The following example shows the certificate is valid for 72 hours:

    Validity
                Not Before: Jun 21 20:36:58 2021 GMT
                Not After : Jun 24 20:36:58 2021 GMT
