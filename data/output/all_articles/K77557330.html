Issue

Error Message

[WARN ][o.e.m.j.JvmGcMonitorService] [<UUID>] [gc][<sequence number>] overhead, spent [<seconds>] collecting in the last [<seconds>]

In this error message, note the following:

  • <UUID> is the universally unique identifier for this log message type.
  • <Sequence number> is the log sequence number.
  • <Seconds> is the time the system spends performing memory management.

For example, the system displays error messages similar to the following:

[2018-05-24T20:41:34,332][WARN ][o.e.m.j.JvmGcMonitorService] [00000000-0000-0000-0000-222222222222] [gc][20354] overhead, spent [1.4s] collecting in the last [1.6s]
[2018-05-24T20:41:35,949][WARN ][o.e.m.j.JvmGcMonitorService] [00000000-0000-0000-0000-222222222222] [gc][20355] overhead, spent [1.2s] collecting in the last [1.6s]
[2018-05-24T20:41:37,280][WARN ][o.e.m.j.JvmGcMonitorService] [00000000-0000-0000-0000-222222222222] [gc][20356] overhead, spent [1.3s] collecting in the last [1.3s]

Message Location

You may encounter this message in the following location:

  • /var/log/searchd/eslognode.log
Description

This message occurs when the following condition is met:

  • You perform a large operation, such as importing a device or creating an application.

Impact

The CPU usage for the BIG-IQ system may spike during a search, causing one or more of the following issues:

  • The system responds slowly.
  • The system becomes unresponsive.
  • Search results lag behind changes to data on the BIG-IQ system.

In the worst possible case, the situation does not resolve on its own.

You may also observe the following additional error messages in these locations:

  • /var/log/searchd/eslognode.log

    java.lang.OutOfMemoryError: Java heap space

  • /var/log/daemon.log

    emerg logger: Re-starting tokumond
    emerg logger: Re-starting tokumond
    emerg logger: Re-starting tokumond
    emerg logger: Re-starting tokumond

Recommended Actions

Workaround

To work around the issue, adjust the buffer allocation for the tokumond process by:

  • Backing up the file and adjusting the buffer allocation settings.
  • Clearing and re-indexing the data directory for search.

Additionally, if you have a secondary system in a BIG-IQ high availability (HA) pair, you must also do the following:

  • Updating buffer allocation settings on a secondary system (if you have one)

To do so, perform the following procedure(s):

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in the to the command line of the affected BIG-IQ system.
  2. Type the following command to determine the amount of memory, in gigabytes (GB), that is installed on the BIG-IQ system, and then record the number:

    physmem -g

  3. Type the following commands to back up the biq_daemon_provision.json file:

    cp /etc/biq_daemon_provision.json /etc/biq_daemon_provision.json.orig

  4. Open the /etc/biq_daemon_provision.json file using a text editor, such as vi, to lower the buffer allocation settings for tokumond.

  5. Within the file, find the tokumond section and look for the send_find_buffer_allocation settings. The settings appear similar to the following example:

    "send_find_buffer_allocation": {
            "SYS_4GB": {
                "batch_size":100,
                "queue_bounding_multiplier":3
            },
            "SYS_8GB": {
                "batch_size":180,
                "queue_bounding_multiplier":3
            },
            "SYS_16GB": {
                "batch_size":324,
                "queue_bounding_multiplier":3
            },
            "SYS_32GB": {
                "batch_size":583,
                "queue_bounding_multiplier":3
            },
            "SYS_64GB": {
                "batch_size":583,
                "queue_bounding_multiplier":3
            },
            "SYS_128GB": {
                "batch_size":583,
                "queue_bounding_multiplier":3
            }
          },
     

  6. Within the send_find_buffer_allocation block, find the setting that matches the amount of memory installed on your system; this is the number you found in step 2.

    For example, if your BIG-IQ system has 32 GB of memory, locate the SYS_32GB setting.

  7. Change the value for batch_size to approximately half of its current value.

    Using the example above, you change the batch_size setting under SYS_32GB from 583 to 290.

  8. Find the send_oplog_buffer_allocation settings. The settings appear similar to the following example:

     "send_oplog_buffer_allocation": {
            "SYS_4GB": {
                "batch_size":100,
                "queue_bounding_multiplier":3
            },
            "SYS_8GB": {
                "batch_size":180,
                "queue_bounding_multiplier":3
            },
            "SYS_16GB": {
                "batch_size":324,
                "queue_bounding_multiplier":3
            },
            "SYS_32GB": {
                "batch_size":583,
                "queue_bounding_multiplier":3
            },
            "SYS_64GB": {
                "batch_size":583,
                "queue_bounding_multiplier":3
            },
            "SYS_128GB": {
                "batch_size":583,
                "queue_bounding_multiplier":3
            }
          }

  9. Within the send_oplog_buffer_allocation block, find the setting that matches the memory installed on your system, as you did in step 6.
  10. Change the value for batch_size to approximately half of its current value, as you did in step 7.
  11. Save the file and exit the text editor.
  12. Type the following command to stop the restjavad, tokumond, and searchd services:

    bigstart stop restjavad tokumond searchd

  13. Type the following command to change the working directory to the data directory for searchd:

    cd /var/config/rest/searchd

  14. Type the following command to verify that the the working directory is /var/config/rest/searchd:

    pwd

  15. Type the following command to clear and then re-index the data directory on the next tokumond startup:

    rm -rf ./data/

  16. Type the following command to start tokumond and searchd services:

    bigstart start tokumond searchd

  17. Type the following command to monitor the tokumond log file:

    tail -f /var/log/tokumon/current

    Your new settings display in the log file.

    For example, when you set the batch_size for send_find_buffer_allocation and send_oplog_buffer_allocation to 290, the log appears similar to the following:

    2018-07-27_18:54:50.66791 tokumon:mode:PRODUCTION send_find_parallelize:false send_find_buffer_allocation:{"batch_size”:290,"queue_bounding_multiplier”:3} send_oplog_buffer_allocation:{"batch_size”:290,”queue_bounding_multiplier”:3} isSecondary:false

  18. Press Ctrl + C to stop monitoring the log.
  19. Monitor the following files while you wait for the system to re-index all data:
    • /var/log/tokumon/current—Look for the _indexOplog string to indicate when the system finishes re-indexing the data.
    • /var/log/searchd/eslognode.log—Ensure the error messages described earlier do not reoccur.

      Note: If you get an error message during re-indexing, you may need to reduce the batch_size settings further by repeating the procedure, starting at step 5.

    With large BIG-IQ configurations, a full re-index can take more than 10 minutes.

  20. If there are no errors, type the following command to start the restjavad process:

    bigstart start restjavad

  21. The CPU usage that the Java process requires for the Elasticsearch user can place it in the top results of the top command. You do not want this result.

    After the restjavad process starts, type the following command to verify that the CPU usage is no longer in the top results:

    top

    The Java process looks similar to the following example:

    Note: This example has a truncated command string.

    2414 root      20   0  6284 2380 1864 S  0.0  0.0   0:00.02 su elasticsearch -s /bin/bash -c export JAVA_HOME=/usr/lib/jvm/jre-1.8.0-openjdk.x86_64

    After the system re-indexes the data, it uses the new settings for future changes and is less likely to overwhelm searchd.

  22. Press Ctrl+C to stop monitoring top.

Updating buffer allocation settings on a secondary system (if you have one)

If you have a secondary system in a BIG-IQ high availability (HA) pair, you must update the settings on the secondary system to match the settings that you changed on the primary system. If you do not have a secondary system, you can stop here.

  1. Log in to the command line of the secondary BIG-IQ system.
  2. Back up the /etc/biq_daemon_provision.json file on the secondary BIG-IQ system.
  3. Change the send_find_buffer_allocation and send_oplog_buffer_allocation settings to the same values that are now working on the primary system.
  4. Type the following command to restart the tokumond process on the secondary BIG-IQ system:

    bigstart restart tokumond

  5. Type the following command to monitor the tokumond log file:

    tail -f /var/log/tokumon/current

    The new settings display in the log file.
