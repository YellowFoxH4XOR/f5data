Known Issue

The Database monitors may fail when the server resides in a non-default route domain.

This issue occurs when any of the following conditions are met:

  • The server is monitored with one of the following monitor types:
    • Oracle
    • MSSQL
    • MySQL
    • PostgreSQL

Impact

The BIG-IP system will mark the pool member as down.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • BIG-IP iHealth lists Heuristic H380428 on the Diagnostics > Identified > Medium screen.
  • If debugging is enabled for the monitor you may see error messages logged to the /var/log/DBDaemon.log file:

    For example, when MSSQL monitor attempts to connect to a Microsoft SQL server, you may observe following error message in /var/log/DBDaemon.log file with debugging enabled in the monitor configuration

    jdbc:sqlserver://2620:0:c10:f501:0:a:a00:14:1433;databaseName=master;(Thread-62): getConnection (The port number
    0:c10:f501:0:a:a00:14:1433 is not valid.)

    The above error message indicates that the MSSQL monitor failed to connect to the 10.0.0.20%10:1433 pool member. In reality, this pool member is a regular IPv4 host; however, because it was deployed in a non-default route domain (route domain ID 10), the BIG-IP system tracks the IPv4 address and the route domain information using the 2620:0:c10:f501:0:a:a00:14 IPv6 address. Since the Microsoft SQL Server JDBC driver is not IPv6 compatible, the health check fails.

    The MSSQL monitor verifies the availability of a Microsoft SQL Server by executing a userland program that relies on the Java Database Connectivity (JDBC) API. The BIG-IP system uses a version of the Microsoft SQL Server JDBC driver that is incompatible with IPv6; therefore, the MSSQL monitor will fail to connect to a Microsoft SQL Server through IPv6.
