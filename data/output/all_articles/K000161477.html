K000161477: BIG-IP LTM: HTTP/2 client requests intermittently delayed or reset

Type
Support Solution
Published
2026-08-25
Updated
2026-08-25
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.3
Source
https://my.f5.com/manage/s/article/K000161477

Description

Intermittent http2_protocol_error messages and HTTP/2 RST_STREAM frames occur when BIG-IP LTM uses HTTP/2 on the client side and HTTP/1.1 on the server side. Affected requests may be acknowledged by BIG-IP without application data being forwarded to the backend, while other streams complete normally with HTTP/1.1 200 OK responses.

Environment

  • BIG-IP LTM 17.1.3
  • Client-side HTTP/2 profile enabled
  • Server-side HTTP/1.1 connections to pool members
  • HTTP/2-to-HTTP/1.1 gateway 

The HTTP MRF Router (httprouter) profile is not generally required when the configuration uses HTTP/2 on the client side and HTTP/1.1 on the server side. It is required for specific full-proxy scenarios involving HTTP/2 on the backend or internal message routing.

Cause

The issue is associated with backend server-side TCP connection attempts being reset or delayed because of source-port reuse, port exhaustion, or TIME_WAIT collisions.

For affected streams, BIG-IP attempts to establish new TCP connections to the backend but receives TCP resets or no response. BIG-IP consequently cannot forward the HTTP/2 request to the backend or return an application response to the client.

In an HTTP/2-to-HTTP/1.1 gateway configuration, multiple client-side HTTP/2 streams can result in frequent server-side TCP connection creation. A backend server with a long TIME_WAIT interval or limited ephemeral-port range can contribute to connection collisions and resets.

Answer/Recommended Actions

  1. Check the backend server during the failure.
    • Review backend operating-system logs and TCP statistics.
    • Confirm whether SYN packets from BIG-IP are being reset, dropped, or left unanswered.
    • Check for ephemeral-port exhaustion and a large number of connections in TIME_WAIT.
    • Verify firewall, load balancer, and server-side connection limits.
  2. Review the BIG-IP HTTP profile.
    • Check the server-side connection timeout.
    • Increase the timeout if connections are being recycled prematurely.
    • Apply changes first to a test virtual server or during an approved maintenance window.
  3. Review backend TCP TIME_WAIT behavior.
    • Check the backend operating system’s TCP FIN/TIME_WAIT configuration.
    • If permitted by the backend platform and security policy, reduce an unnecessarily long FIN timeout so ports become available sooner.
    • Do not change operating-system TCP settings without validating the effect with the backend platform owner.
  4. Configure OneConnect where appropriate.
    • Attach and configure a OneConnect profile on the virtual server to promote server-side connection reuse.
    • Validate application behavior because OneConnect changes how server-side connections are selected and reused.
  5. Increase the available source-port space if required.
    • Enable SNAT for the virtual server if appropriate for the application and network design.
    • Use a SNAT pool with additional addresses when one source address does not provide sufficient concurrent source ports.
    • Confirm that backend servers allow the SNAT addresses and that application logging and access controls account for translated source addresses.
  6. Capture both sides of the BIG-IP connection if the issue persists.
    • Capture client-side and server-side traffic simultaneously.
    • Include the TLS handshake when decrypted analysis is required.
    • Correlate the HTTP/2 stream ID, backend TCP connection, SYN/RST packets, and response timing.
    • Clear existing connections to the test virtual server before a controlled reproduction to simplify traffic correlation.

Additional Information

  • HTTP/2 stream IDs on the client side do not necessarily match the corresponding server-side transaction identifiers because BIG-IP translates HTTP/2 requests into HTTP/1.1 requests.
  • A client-side HTTP/2 RST_STREAM is not by itself proof of an HTTP/2 header-format problem. It can be a downstream symptom of a missing or delayed backend response.
  • Some streams may receive backend responses normally while other streams have no corresponding backend request until the connection-establishment delay ends.
  • HTTP/2-to-HTTP/1.1 translation commonly requires frequent server-side connection establishment unless connection reuse is configured and effective.
  • The MRF Router profile should be enabled only when the deployment scenario requires it. It is not generally mandatory for client-side HTTP/2 to server-side HTTP/1.1 traffic.
