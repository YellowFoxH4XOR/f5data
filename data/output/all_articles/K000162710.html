Description

By default, when NGINX Instance Manager (NIM) performs a publish operation to a managed NGINX Plus instance, compiled F5 WAF for NGINX (NGINX App Protect) security policy bundles (.tgz) are written to the /etc/nms/ directory on the data plane instance.

NGINX Instance Manager documentation references this default location in all examples, for example:

app_protect_policy_file /etc/nms/NginxDefaultPolicy.tgz;

Customers who maintain their own filesystem layout standards may want published security policy bundles stored in a customer-defined directory instead, such as /etc/policy/ or /etc/nginx/policy/. 

This article describes how to publish an App Protect security policy bundle to a custom directory.

Scope: This article applies to App Protect security policy bundles referenced by the app_protect_policy_file directive only. It does not apply to security log profiles. See the Additional Information section.

Environment

  • NGINX Instance Manager (managing F5 WAF for NGINX configuration)
  • NGINX Plus with F5 WAF for NGINX (NGINX App Protect)
  • NGINX Agent installed on the managed data plane instance
  • Reported environment: NGINX Plus R37-p1 (nginx/1.29.8), F5 WAF for NGINX 5.13.4, Ubuntu 24.04

Cause

The destination path for a published security policy bundle is taken from the absolute path referenced in the published NGINX configuration, not from a fixed product setting.

The NGINX Agent resolves the write destination as follows:

  • If the file name in the published payload is an absolute path, the Agent writes the file to that path directly, and the default auxiliary payload root directory (etc/nms) is not applied.
  • If the file name is a relative path, the Agent joins it to the auxiliary payload root directory.

The Agent will only write to directory paths listed in its config_dirs parameter. When a custom directory is referenced but is absent from config_dirs, the publish operation is rejected. As a result, config_dirs acts as both the permission gate and the enabler for a custom location.

Recommended Actions

Perform steps 1 through 3 on each managed NGINX Plus instance that should receive the files.

1. Create the target directory on the managed instance

sudo mkdir -p /etc/policy

2. Add the directory to the NGINX Agent config_dirs allow-list

Back up the Agent configuration:

sudo cp /etc/nginx-agent/nginx-agent.conf /etc/nginx-agent/nginx-agent.conf_backup

Edit the Agent configuration:

sudo vi /etc/nginx-agent/nginx-agent.conf

Append the custom directory to the config_dirs parameter:

config_dirs: "/etc/nginx:/usr/local/etc/nginx:/usr/share/nginx/modules:/etc/nms:/etc/app_protect:/etc/policy/"

Save and exit.

3. Restart the NGINX Agent and confirm it is running

sudo systemctl restart nginx-agent.service
sudo systemctl status nginx-agent.service

4. In NGINX Instance Manager, create the security policy you intend to publish

Note: The policy being published must not already exist on the managed NGINX instance, and must not already be referenced in any existing NGINX configuration on that instance.

5. Reference the policy by its full absolute path in the custom directory

For example:

server {
    listen 8078 default_server;
    server_name localhost;

    app_protect_enable on;
    app_protect_security_log_enable on;
    app_protect_policy_file /etc/policy/test.tgz;

    location /nginx {
        root  /usr/share/nginx/html;
        index index.html index.htm;
    }

    location / {
        proxy_pass http://127.0.0.1:80;
    }

    error_page 500 502 503 504 /50x.html;
    location = /50x.html {
        root /usr/share/nginx/html;
    }
}

6. Publish the new configuration

The publish operation should complete successfully.

7. On the managed instance, verify the policy bundle exists in the intended directory

$ ls /etc/policy/
test.tgz

Additional Information

Security log profiles are not in scope

This procedure applies to App Protect security policy bundles only. Do not use it to relocate security log profiles.

Important: When Security Monitoring is in use, the Security Monitoring log profile bundle must remain at its default location and the following directive value must not be changed. The NGINX Instance Manager documentation ("Edit WAF configuration") states plainly: "Don't change this value."

app_protect_security_log "/etc/nms/secops_dashboard.tgz" syslog:server=127.0.0.1:514;

Support status

This procedure was reproduced in an F5 support lab for an App Protect security policy bundle. It is not the default configuration, and product documentation shows only the /etc/nms location. Validate the procedure in a non-production environment before deploying it.

Symptom when config_dirs is not updated

If the custom directory is not added to config_dirs, publishing fails with an error similar to the following:

the file /etc/policy/test.tgz is outside the allowed directory list

For this error condition, refer to:

  • K000091530: NGINX Instance Manager (NIM) unable to publish config file with error "<filename/directory> is outside the allowed directory list"
  • K000152962: NGINX Instance Manager 'Publish' configuration timeout

Directory ownership

When publishing to the default /etc/nms location, the directory is expected to be owned by root:nginx-agent. Incorrect ownership causes NGINX to fail to read the published bundle, with a configuration load failure reporting "permission denied". Verify with the following:

ls -ldh /etc/nms

If the ownership is anything other than root:nginx-agent, update it:

sudo chown root:nginx-agent /etc/nms

Equivalent ownership considerations are likely to apply to any custom directory used, although this was not specifically tested.

Reference: NGINX Agent write logic

The write behaviour described in the Cause section is implemented in the open source NGINX Agent, src/core/environment.go (reviewed at tag v2.41.1). The WriteFile function is documented in-code as: "WriteFile writes the provided file content to disk. If the file.GetName() returns an absolute path, it'll be written to the path. Otherwise, it'll be written to the path relative to the provided confPath."

Published auxiliary files, which include App Protect policy bundles, reach this logic through the WriteFile function in the same file, which iterates over the file list and calls WriteFile for each entry. The Agent creates the destination directory if it does not already exist, using os.MkdirAll with mode 0750.  For auxiliary files, the allow-list check against config_dirs is performed by the ensureFilesAllowed function in src/core/nginx.go, which produces the "outside the allowed directory list" error quoted above.
