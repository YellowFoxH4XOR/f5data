Known Issue

This is the result of a known issue. If a virtual server has a cookie persistence profile, and an iRule configured with the LB_Failed iRule event, and LB::reselect iRule command, requests to the virtual server can cause the TMM process to crash. This issue occurs when the LB::reselect operation fails because all of the members are marked down for the pool, and the BIG-IP LTM attempts to embed the persistence cookie into the response.

F5 Product Development tracked this issue as CR76991, and it was fixed in BIG-IP LTM 9.1.3 and 9.3.1. For information about upgrading, refer to the BIG-IP LTM Release Notes.

Workaround

You can work around this issue by modifying the existing iRule to check for available members.

For example, you can configure the iRule to check for available pool members, and issue the LB::reselect iRule command to reselect a pool member. For example:

when LB_FAILED {
    if {[active_members MyPool] > 0 }{
    LB::reselect
  }
}

Alternatively, you can configure the iRule to direct the request to a backup pool if no pool members are available. For example:

when LB_FAILED {
  if {[active_members MyPool] > 0 }{
    LB::reselect
  } else {
  persist none
  LB::reselect pool MyBackupPool
}
