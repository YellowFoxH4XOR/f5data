K31256034: Application Services Extension 3 (AS3) returns 502 after POST

Type
Support Solution
Published
2020-07-01
Updated
2025-02-06
Applies to
  • F5 Automation and Orchestration
  • BIG-IP
  • F5 Application Services 3 Extension
Source
https://my.f5.com/manage/s/article/K31256034

Description

When using curl or some other HTTP clients for an AS3 declaration, the BIG-IP may return a 502:

# curl -k -X POST -H "Content-Type: application/json" -u <user>:<password> -d @<declaration> https://<big-ip>/mgmt/shared/appsvcs/declare

<h2>Error 502</h2>

Log messages may also appear in the http_errors logfile:

err httpd[8434]: [error] [client <bgip-ip>] (20014)Internal error: proxy: error reading status line from remote server localhost
err httpd[8434]: [error] [client <bgip-ip>] proxy: Error reading from remote server returned by /mgmt/shared/appsvcs/declare

Where:

  • <declaration> is a json file with the complete tenant syntax.
  • <big-ip> is the IP or FQDN of the BIG-IP management address.
  • <user> is the BIG-IP administrator.
  • <password> is the BIG-IP administrator's password.

Environment

This message occurs when the following conditions are met:

  • When making an AS3 declaration to the BIG-IP.
  • The HTTP client sends an "Expect: 100 continue" or similar header.

You may encounter messages in the following locations:

  • A 502 will message will appear be returned to the HTTP client.
  • Internal and proxy errors will be observed in /var/log/httpd/httpd_errors

Cause

The problem is caused by the HTTP client (such as curl) sending an "Expect: 100 continue" in the HTTP headers.
It is incorrect to send an Expect: 100 header in a json POST.

For example:

# curl -k -X POST -H "Content-Type: application/json" -H "Expect:" -u admin:admin -d @my-application.json https://<big-ip>/mgmt/shared/appsvcs/declare

Recommended Actions

There is no user feedback to indicate the success or failure of the declaration. When the 502 and http_errors messages are observed, the declaration will complete successfully if the declaration itself is valid.

A workaround in curl is to specify "-H Expect:" on the curl command so that curl is forced to send no Expect header.
