K000140026: Filtering security event logs in the GUI may time out with large event volumes

Type
Support Solution
Published
2026-08-27
Updated
2026-10-23
Source
https://my.f5.com/manage/s/article/K000140026

Description

When filtering Web Application Security event logs through the GUI, the request may fail with an HTTP 400 error similar to:

400 Bad Request
Request timed out

This behavior is most likely when the system contains a very large number of event records. In the referenced investigation, the BIG-IQ system contained more than six million Web Application Security event records.

Environment

  • BIG-IQ Centralized Management
  • Web Application Security events collected from BIG-IP ASM/Advanced WAF devices
  • Large event database
  • GUI filtering or free-text searching

Cause

The free-text filter at the top of the event-list screen is not intended to search millions of records in the database.

Most GUI event-list screens initially retrieve only a limited page of records—typically a few hundred—and retrieve additional records as the user scrolls. The exact number is not a fixed documented limit.

As a result, the top-of-screen filter may operate only on the records currently loaded in the GUI rather than performing an efficient, database-wide search. When the event database contains tens of thousands or millions of records, attempting to use this filter can cause the request to run until it times out.

The timeout is therefore generally a limitation of the GUI search method and the volume of records being searched, rather than evidence of a WAF enforcement failure.

Recommended actions

Use the supported event-filter configuration

For BIG-IQ, create and use a log filter instead of relying on the free-text field at the top of the event list.

Navigate to:

Monitoring > Events > Web Application Security > Events > Filters and Tags

Create a filter using the available structured fields, such as:

  • Time range
  • Device
  • Policy
  • Virtual server
  • Source address
  • Violation or event type
  • Severity
  • Request status

The applicable BIG-IQ procedure is documented in Manage log filters.

Use restrictive criteria—especially a time range and policy or virtual-server value—to reduce the result set before viewing or exporting events.

Use supported query parameters

When using a BIG-IQ query or filter form, use only fields supported by the applicable BIG-IQ release. An otherwise valid query expression may still be rejected if it is not compatible with the query-parameter form. See K000150576: A query expression is valid but is not compatible with the Query Parameters form.

Reduce event generation at the BIG-IP source

For BIG-IP ASM/Advanced WAF systems, avoid generating unnecessarily large event volumes:

  • Prefer logging illegal requests rather than all requests unless all-request logging is required.
  • Remove duplicate or unnecessary logging profiles.
  • Use remote logging where long-term retention is required.
  • Limit Bot Defense and DoS logging to actionable classifications or mitigation actions.
  • Use local all-request logging only for temporary troubleshooting.

These recommendations are documented in K000152053: ASM Event Logging - Best Practices and General Recommendations.

Local ASM event storage is limited. When the database or storage limit is reached, older records may be purged. See K45320421: ASM event logs are deleted or rotated out very quickly.

Use a narrow filter before exporting

Export operations also have record limits. For example, K31743103: Unable to export large security logs from ASM via GUI documents a limitation of 100 records in a single ASM security-log export.

Before exporting, apply Basic or Advanced filters so that the result set is within the supported export size.

BIG-IP ASM GUI considerations

For BIG-IP ASM/Advanced WAF event logs, the Configuration utility displays locally stored events that meet the logging-profile criteria. The BIG-IP documentation describes structured filtering through the logging profile’s storage filter, including request type, protocols, response status codes, HTTP methods, and request content.

See:

  • BIG-IP 17.5: Logging Application Security Events
  • BIG-IP 17.0: Logging Application Security Events

If filtering by only one field produces no results, add an additional relevant criterion. For example, K81125632: “No records to display” when filtering ASM Event log by Signature ID documents a case where adding another filter, such as policy or virtual server, produces results.

Important distinction: missing records versus search timeout

A GUI timeout does not prove that the requested event does not exist.

Conversely, an event may exist in the underlying database but not be displayed in the GUI. ASM may mark records so that they are not displayed when they were created only for traffic learning, were accepted by the automatic policy builder, were generated while no logging profile was attached, or were affected by excessive logging or logging-service problems. See K70045451: Some request logs are missing on GUI but are found in the MySQL database.

Do not access or modify the internal database as a routine workaround. Database queries should be performed only by F5 Support or by following an applicable F5 procedure.
