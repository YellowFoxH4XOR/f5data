Description

How to monitor the memory utilization by the DNS cache resolver, and how much memory utilization is expected to be consumed by the DNS cache resolver.

Environment

  • BIG-IP DNS with DNS cache resolver profile configured
  • Monitor memory utilisation
  • Elevated TMM memory utilization observed, or DNS cache tuning required

Cause

1. The DNS cache resolver is a sub-system of the TMM memory and the underlying piece of code sub-divides the memory to various other chunks.
2. The memory is allocated to the caches, TCP and UDP flows. The more the traffic, higher is the "DNS cache resolver" memory utilization.
Lets take an example to understand the overall memory utilization briefly.

The DNS resolver cache profile consist of the following numbers:
tmsh list ltm dns cache resolver <cache_profile> all-properties | grep -E "max-concurrent|msg-cache-size|nameserver-cache-count|rrset-cache-size"
  max-concurrent-queries 1600 <<<---- The default value is 1024
  max-concurrent-tcp 2000 <<<---- The default value is 20
  max-concurrent-udp 32000 <<<---- The default value is 8192
  msg-cache-size 60mb <<<---- The default value is 1MB
  nameserver-cache-count 66000 <<<---- The default value is 16536
  rrset-cache-size 400mb <<<---- The default value is 10MB

Here in this case, the "DNS cache resolver" sub-system will include memory utilized by the caches as well as the tcp/udp/queries. For the tcp/udp flows and queries the memory utilization will heavily dependent on the traffic volume.

For the cache size, the memory utilization will be as per configured. And the system is not going to allocate any more memory to the caches.

3.. The memory utilized by these caches can be viewed using the tmctl command:
tmctl -d blade dns_cache_resolver_stat -s msg.bytes_allocated,rrset.bytes_allocated,nameserver.bytes_allocated

4.. Always note the CHR: cache hits ratio. Generally any value greater than 80% is good. The goal should be to have a better CHR and not high cache values. You could achieve high CHR with low cache values as well. It totally depends on the type of the traffic and customer must test this in their respective environment to be able to come to cache values which suits their respective environment. Thumb rule is to start from default values and monitor CHR.

CHR is the ratio of cache hits to queries. It is calculated as a percentage: (Synchronous/Queries)*100. Caches are generally considered to be performing well with a CHR above 80%.

A cache hit results from a DNS query that a BIG-IP® device can answer from information already contained within its sub-caches with no back end queries. This is tracked in the Synchronous and Queries fields. In order to find these fields, use the command tmsh show ltm dns cache resolver <cache_profile>.

Recommended Actions

  1. Always start with default values of the cache and monitor the CHR. This could be done during testing phase to get a good cache values for the prod environment.
  2. Tune the cache values unless CHR of greater than 80% is achieved.
  3. This tuning could be taken up regularly by monitoring the CHR ratio.
