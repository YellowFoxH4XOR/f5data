Topic

This article applies to BIG-IP 9.x through 10.x. For information about other versions, refer to the following article:

  • K14806: Overview of the Server SSL profile (11.x - 13.x)

The BIG-IP Server Secure Socket Layer (SSL) profile enables the BIG-IP system to initiate secure connections to your SSL servers using a fully SSL-encapsulated protocol. This article defines F5 recommended best practices to configure the Server SSL profile.

Server SSL profile settings

The Server SSL profile provides various settings to manage server-side SSL connections, as required by your site. Only some settings are required, and typically only a few of the available settings are configured. This article provides details for the most commonly used settings. In most cases, you should leave the remaining profile settings at their default values, unless advised by F5 Technical Support.

Note: The Name setting is the only setting that you must actively specify when you create an SSL profile; all other settings have default values.

Name

The Name setting is required. To create a Server SSL profile, you must specify a unique name for the profile.

Certificate

The Certificate setting is optional. Depending on the BIG-IP version, the certificate setting uses one of the following default values:

  • For BIG-IP 10.2.2 through 10.2.4, the default setting is None (no certificate is used).
  • For BIG-IP 10.0.0 through 10.2.1, the Server SSL profile uses the self-signed certificate named default.crt by default.
  • For BIG-IP 9.x, the default setting is None (no certificate is used).

When a Server SSL profile is applied to a virtual server, the BIG-IP system acts as an SSL client. If your servers do not expect the BIG-IP system to present its client certificate on behalf of clients traversing the virtual server, select None. If your servers expect the BIG-IP system to present a client certificate, then import the certificate and matching key to the BIG-IP system, and then choose the appropriate certificate from the menu.

Important: The BIG-IP system uses certificates and keys in the PEM format. In versions prior to BIG-IP 10.1.0, you can convert all certificates and keys before importing. For more information, refer to K6549: Converting PKCS certificates to PEM format for use with the BIG-IP system. Beginning in BIG-IP 10.1.0, you can import PKCS12 certificates without first converting them.

For information about verifying the certificate format, refer to K6746: Verifying SSL certificate and key pairs from the command line (9.x - 10.x)

Key

The system requires the Key setting only if a certificate is configured. If you configure a certificate, you must choose the key that matches the configured certificate.  The default value for the key setting is one of the following:

  • For BIG-IP 10.2.2 through 10.2.4 the default setting is None (no key is used because there is no default certificate).
  • For BIG-IP 10.0.0 through 10.2.1, the Server SSL profile uses the key named default.key by default, which matches the self-signed certificate named default.crt.
  • For BIG-IP 9.x, the default setting is None (no key is used because there is no default certificate).

The key must be in PEM format. For information about verifying the key format, refer to K6746: Verifying SSL certificate and key pairs from the command line (9.x - 10.x)

Passphrase

The Passphrase setting is optional. It is only required if the key is passphrase-protected. By default, no passphrase is configured. If a key is specified and the key is passphrase protected, enter the passphrase.

Note: When no passphrase is configured, the Passphrase field may display an eight asterisk mask (********), giving the appearance that an eight-character password has been configured.

Important: The passphrase is encrypted before it is saved in the bigip.conf file.

Chain

The Chain setting is optional. The system uses this setting to specify a certificate bundle or chain that the server can use to establish a trust relationship with a client that presents a certificate signed by an untrusted Certificate Authority (CA).

The default value for the Chain setting is None, indicating that the BIG-IP system will not present a chain certificate with its client SSL certificate.

The drop-down list also includes the names of all the SSL certificates installed in the BIG-IP system's SSL certificate store. For example, a newly installed system includes the following two certificates:

  • The default certificate:

    This setting represents the default.crt certificate. It is a self-signed certificate for use with testing SSL profiles. This certificate is not appropriate for use as a chain certificate.

  • The ca-bundle certificate:

    This setting represents the CA certificate bundle named ca-bundle.crt. It is a bundle of CA certificates from most of the well-known PKIs. This certificate is not appropriate for use as a chain certificate.

If the certificate configured in the Server SSL profile is signed by an intermediate CA, F5 recommends that you create and install a bundle that contains the certificates of all the CAs in the chain between the certificate configured in the Server SSL profile and a root CA whose certificate is trusted by your SSL servers. The new certificate bundle may then be selected in the Chain setting drop-down list.

When a BIG-IP virtual server initiates an SSL connection to a server using a Server SSL profile that has a chain certificate configured, the BIG-IP system presents the certificate bundle along with the SSL client certificate. If the SSL client certificate used in the Server SSL profiles is signed by an Intermediate CA whose certificate is not contained in the SSL server's Trusted Certificate store, the server will not explicitly trust the SSL client certificate. However, if the server trusts the certificate of another CA further up the same hierarchy, the BIG-IP system can present a chain of certificates that establish a chain of trust to a root CA whose certificate is trusted by the SSL server. Because the SSL server trusts the root CA, and the root CA in turn trusts the intermediate CA, the SSL server implicitly trusts the SSL client certificate.

For example, in a Public Key Infrastructure (PKI) that consists of a root CA and two Intermediate CAs, the bundle should consist of the three CA certificates (Root CA, Intermediate-1 CA, Intermediate-2 CA):

Root CA                                  -|
     -> Intermediate-1 CA                -|--> Chain Bundle  = These three CA certificates
          ->  Intermediate-2  CA         -|
               ->  client certificate  

When a connection is established to the SSL server using this profile, the BIG-IP system presents all four certificates to the server (the three CA certificates plus the configured client certificate). If the server already has the root CA certificate in its Trusted Certificate store, when the BIG-IP system presents the Intermediate CA certificates (1 and 2), the server can establish a chain of trust to the root CA. If the server already has both the root CA certificate and the Intermediate-1 CA certificate in its Trusted Certificate store, when the BIG-IP system presents the Intermediate CA-2 certificate, the server can establish a chain of trust to the Intermediate-1 CA.

Important: Including the root CA certificate in the certificate bundle is optional and never causes the server to trust the root CA. This would defeat the purpose of third-party validation, because trusted CAs should be predetermined and their certificates intentionally installed on the server. Presenting the Root CA in the chain serves no functional value in the context of server-side SSL connections, because the SSL servers cannot validate any certificate against a Root CA provided by the client, which is otherwise unknown to the server. However, including the Root CA in the certificate chain can simplify troubleshooting by making the client's PKI hierarchy more readily apparent. 

Note: You can verify whether the chain certificate bundle creates a chain of trust to the client certificate by using the following command syntax:

openssl verify -purpose sslserver -CAfile <path_to_chain_file> <path_to_server_cert_file>

If the system can establish the chain of trust for the client certificate using the specified chain certificate, the command returns the following output:

client.crt: OK

Trusted Certificate Authorities

The Trusted Certificate Authorities setting is optional. This setting is used to specify the CAs that the BIG-IP system trusts when verifying a server certificate. The default value is None, which means the BIG-IP system accepts a server certificate signed by any CA.

Important: If you select Require for the Server Certificate setting, you must specify a CA from the Trusted Certificate Authorities menu. This is the CA that the BIG-IP system trusts when verifying a server certificate. Additionally, make sure to specify a value in Authenticate Name as well. A blank Authenticate Name field means that everyone is authenticated, even though you have specified Require as the Server Certificate setting.

To limit which CAs the profile trusts, select a certificate bundle here. To trust only server certificates signed by a public CA, select the built-in ca-bundle.crt. To trust only a server certificate which has been signed by a private PKI or set of private PKIs, create and select a custom certificate bundle here.

When creating the bundle, it should at least include the CA that directly signed your servers' certificates. Ideally, the bundle should include all CAs in the servers' certificate chain.

For example, in a Public Key Infrastructure (PKI) that consists of a root CA and two Intermediate CAs, the bundle should consist of the three CA certificates (Root CA, Intermediate-1 CA, Intermediate-2 CA):

Root CA                                  -|
     -> Intermediate-1 CA                -|--> Chain Bundle  = These three CA certificates
          ->  Intermediate-2  CA         -|
               ->  client certificate  

Note: You can verify whether the Trusted CA bundle creates a chain of trust to the server certificate by importing the server certificate to the BIG-IP system's SSL certificate store, and using the following command syntax:

openssl verify -purpose sslserver -CAfile <path_to_chain_file> <path_to_server_cert_file>

If the chain of trust can be established for the server certificate using the specified certificate bundle, the command returns the following output:

server.crt: OK

Important: Configuring the Trusted Certificate Authorities setting has no effect on server validation of the SSL server certificate that the BIG-IP system presents upon connection to an SSL server. It is the SSL server's responsibility to verify the validity of the SSL client's certificate using its own Trusted Certificate store. If you need to specify a chain of trust to support the SSL server's verification of the BIG-IP system's client certificate, refer to your SSL server documentation for configuration details.

Ciphers

The Ciphers setting is optional. By default, the Server SSL profile uses the DEFAULT cipher set. In most cases, the DEFAULT setting is appropriate, but may be customized, as necessary, to meet the security and performance needs of your site.

For example, you may want the BIG-IP system to use only RC4-MD5 for performance reasons, but the server always selects AES256-SHA. If you know the server offers RC4-MD5, you can limit the Server SSL cipher suite to NATIVE RC4-MD5.

Note: The BIG-IP SSL profiles can use two different SSL stacks: the NATIVE stack, which is built into the Traffic Management Microkernel (TMM), and the COMPAT stack, which is built into OpenSSL. The NATIVE SSL stack is an optimized SSL stack used by the BIG-IP system that can leverage hardware acceleration. For best system performance, F5 recommends that you configure cipher suite strings that prefer the NATIVE stack.

Note: The cipher suite used in a particular connection is selected by the SSL server from among the cipher suites offered by the SSL client. When using Server SSL, the BIG-IP system is acting as an SSL client. Although the server decides which cipher to use, some control can be obtained by customizing what suites the client offers to the server (limiting the target server's choices).

Renegotiation

Starting in BIG-IP 10.1.0, the Renegotiation profile option was added to control whether the virtual server allows midstream session renegotiation. When Renegotiation is enabled, the BIG-IP system processes mid-stream SSL renegotiation requests. When Renegotiation is disabled, the system terminates the connection regardless of the configured serverssl cipher, and the server's HelloRequest to initiate renegotiation is ignored.

Secure Renegotiation

Beginning in BIG-IP 10.2.3, the BIG-IP SSL profiles support the TLS Renegotiation Indication Extension, which allows the user to specify the method of secure renegotiation for SSL connections. In BIG-IP 10.2.3 and 10.2.4, the default value for the Server SSL profile is Request.

The values for the Secure Renegotiation setting are as follows:

  • Request

    Specifies that the system requests secure renegotiation of SSL connections.

  • Require

    Specifies that the system requires secure renegotiation of SSL connections. In this mode, SSL connections initiated from the BIG-IP system to an unpatched server fail when renegotiation is enabled.

  • Require Strict

    Specifies that the system requires strict secure renegotiation of SSL connections. In this mode, SSL connections initiated from the BIG-IP system to an unpatched server fail when renegotiation is enabled.

Note: Within the context of the Server SSL profile, there is no behavioral difference between Require and Require Strict. In either mode, initial SSL connections from the BIG-IP system to unpatched servers fail.

Sample Server SSL profile

If a Server SSL profile supports SSL servers that do not require client certificates, and the Server SSL profile has been constructed according to the recommendations in this article, it appears similar to the following example:

profile serverssl my_serverssl {
   defaults from serverssl
}

A Server SSL profile supporting SSL servers that require client certificates signed by a private PKI appears similar to the following example:

profile serverssl my_serverssl {
   defaults from serverssl
   key "client.key"
   cert "client.crt"
   chain "client-PKI-bundle.crt"                         #Optional but highly recommended
   ca file "server-PKI-bundle.crt"                       #Required in order to trust target server's certificate
   ciphers "DEFAULT"                                     #Optional depending on security/performance requirements
   passphrase "$M$OK$X5wH6ggux9kHj5nYxZjmOw=="           #Optional depending on your key security
}

Note: It is common for the Chain and Trusted CA field to use the same bundle, because most implementations that require client certificates are private PKIs from which both the client's and server's certificate are generated.

F5 recommends that you retain the default values for all other settings as there is rarely a need to modify them.
