Description

  • LTM closes SSL session to backend server mid traffic after upgrade to 14.x
  • On packet capture you can see that the BIG-IP closes the SSL server side connection with the following Alert:

    Alert (Level: Warning, Description: Close Notify)

Environment

  • LTM
  • Virtual server that services both SSL and non-SSL traffic
  • iRule with "SSL::disable" and "SSL::enable" assigned to virtual server

Cause

According to https://clouddocs.f5.com/api/irules/SSL__disable.html it is by design that SSL::disable "Sends an SSL alert to the peer requesting termination of SSL processing". Thus, in 14.x and above when the 2nd request comes in, the iRule with "SSL::disable server side" runs, and terminates the server side connection.

Recommended Actions

To mitigate this issue, you can avoid re-enabling SSL processing immediately after disabling it. Instead, allow the logic of your iRule to determine the required state, and then use either the SSL::enable or SSL::disable command, as appropriate.

Note that the proper use of SSL::enable is highly protocol dependent and not recommended in the majority of cases. To selectively enable SSL processing, you should instead use an ssl profile and then use SSL::disable to selectively disable SSL processing.

Additional Information

Bug ID 513530 and K16520 are old bugs that describe the situation where F5 used to send resets (TCP RST, not Close Notify as it does now) when SSL::disable and SSL::enable were used and triggered "in quick succession" in the iRule. This was fixed - which in fact is why on version prior to 14.x you are able to use an iRule with "SSL::disable" and "SSL::enable" without any issues.

Later on, Bug ID 718881 was raised and fix for this issue changed how F5 handles SSL:disable command. Now, F5 is expected to send Close Notify when SSL::disable is invoked.
