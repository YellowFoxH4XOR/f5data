Topic

This article applies to BIG-IP 11.x. For information about other versions, refer to the following article:

  • K6911: Using iRules to rewrite HTTP redirects to match the port used by the virtual server (9.x - 10.x)

Purpose

You should consider using this procedure under the following conditions:

  • You want the BIG-IP system to send a redirect response with a trailing forward slash (/), rather than relying on a redirect response from the web server.
  • You want the BIG-IP system to send a redirect response with a different destination port than the original request contained.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You must have administrative privileges in the BIG-IP Configuration utility.

Description

When an HTTP client requests a directory without appending a trailing forward slash to the requested path, most web servers respond with a self-referencing HTTP redirect that includes the originally requested URL and a trailing forward slash. When the web server listens on a port other than 80, it includes the TCP port on which it is listening in the Location header when it sends the HTTP redirect response. If the virtual server is listening on a different port, the resulting redirect location is incorrect.

For example, consider a case in which a web server is listening on port 8080. The web server sends redirects that contain a Location header similar to the following:

Location: http://www.f5.com:8080/directory1/

When the client receives the port 8080 redirect response, the client issues a new HTTP request to the BIG-IP LTM system destined for a port that does not match the virtual server.

To solve this issue, you can do one of the following:

  • Create an iRule that appends a trailing forward slash to requests on your website that do not have a file extension.
  • Create an iRule that sends a redirect to the appropriate port when the system receives a request on the wrong port, following such a redirect.

Procedures

Using an iRule to append a trailing forward slash

F5 recommends that you configure the BIG-IP LTM system to append a trailing forward slash to the request, rather than depending on the web server to issue a redirect. To do so, perform the following two procedures:

Impact of procedure: Performing the following procedures should not have a negative impact on your system.

Creating a data group that contains a list of possible file extensions on your website

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules > Data Group List.
  3. Click Create.
  4. In the Name box, type a name for the data group.
  5. In the Type list, click String.

    For example, if your website contains the .html, .css, .doc, .pdf, .aspx, .jsp, .jpg, .gif, .jpeg, and .bmp file extensions, your data group appears as follows:

    ltm data-group internal /Common/extensions {
    records {
    .aspx { }
    .bmp { }
    .css { }
    .doc { }
    .gif { }
    .html { }
    .jpeg { }
    .jpg { }
    .jsp { }
    .pdf { }
    }
    type string
    }

Creating the iRule

You can create an iRule that looks at the incoming URI and appends a trailing forward slash to requests that do not contain a file extension that is in the data group, nor a trailing forward slash. To do so, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules.
  3. Click Create.
  4. In the Name box, type a name for the iRule.
  5. In the Definition box, type the following iRules syntax:

    when HTTP_REQUEST {
    set req [string tolower [HTTP::path]]
    if { !([class match $req ends_with extensions])
    and !($req ends_with "/") }
    { HTTP::path "[HTTP::path]/" }
    }

Using an iRule to redirect to a different port

You can redirect to a different port by doing the following:

  • Create a new virtual server on the BIG-IP system that listens on the same port as the web servers.
  • Associate an iRule with that virtual server that redirects requests back to the port 80 virtual server.

To do so, perform the following two procedures:

Impact of procedures: Performing the following procedures should not have a negative impact on your system.

Creating the redirect iRule

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules.
  3. Click Create.
  4. In the Name box, type a name for the iRule.
  5. In the Definition box, type the following iRules syntax, changing the Host portion of the URL to match the DNS name of your site:

    when HTTP_REQUEST {

    HTTP::redirect http://[getfield [HTTP::host] ":" 1][HTTP::uri]
    }

    This code redirects requests the system receives on an alternate port to port 80.

Creating the virtual server

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Virtual Servers.
  3. Click Create.
  4. Under General Properties, in the Name box, type a name for the virtual server.
  5. In the Destination Address box, type an address for the virtual server.
  6. In the Service Port box, type the service port number on which the web server listens.
  7. Associate the iRule.

    For example, the following virtual server listens on port 8080, the same port on which the web server listens:

    ltm virtual /Common/vs_http_8080 {
    destination /Common/192.168.1.1:8080
    ip-protocol tcp
    mask 255.255.255.255
    profiles {
    /Common/http { }
    /Common/tcp { }
    }
    rules {
    /Common/redirect_to_80
    }
    source 0.0.0.0/0
    translate-address enabled
    translate-port enabled
    vlans {
    /Common/vlan1
    }
    vlans-enabled
    }

With this virtual server and iRule in place, the following occurs:

  1. Clients that the system redirects from the web server to port 8080 reconnect to the BIG-IP virtual server on port 8080.
  2. The BIG-IP system redirects them to the correct port (port 80).

Note: When a browser receives a redirect response, POST transactions may fail because of browser security restrictions (the browser does not follow the redirect). An alternative approach is to configure the BIG-IP system to host the website on both port 80 and port 8080, pointing to the same pool of servers and eliminating the need for the redirect rule.
