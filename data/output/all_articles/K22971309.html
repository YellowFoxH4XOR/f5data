Known Issue

The add_del_internal script may fail to synchronize across blades on the VIPRION platform.

This issue occurs when the following conditions are met:

  • You use the add_del_internal command on the primary VIPRION blade to change an internal parameter.

    For example:

    /usr/share/ts/bin/add_del_internal add cookie_secure_attr 1

  • You then run the following command on the primary blade to initialize the internal parameter:

    bigstart restart asm

Impact

This situation results in an inconsistent configuration between the primary blade and the secondary VIPRION blades, which may cause the blades to respond differently to the same requests.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The internal parameters are not carried over to the secondary blades.
  • The bd.log indicates that the parameter was changed.

    For example:

    BD_MISC|NOTICE|Apr 04 00:54:28.139|18395|temp_func.c:1899|CHANGED INTERNAL PARAM: [cookie_secure_attr][1]

  • The VIPRION blades respond differently to the same requests.

Workaround

To work around this issue, you can use the clsh command with the internal parameter command. To do so, perform the following procedure:

Impact of workaround: Restarting the asm service will cause a brief traffic disruption.

  1. Log in to the command line of the primary VIPRION device.
  2. Use the clsh command before the internal parameter command.

    For example:

    clsh /usr/share/ts/bin/add_del_internal add cookie_secure_attr 1

  3. After you have modified the parameter, restart the BIG-IP ASM service by typing the following command:

    bigstart restart asm
