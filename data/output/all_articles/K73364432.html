Topic

This article provides a high-level overview of the VELOS system, its subsystems and the F5OS / F5OS-C software. For information about the F5 rSeries system and the F5OS-A software, refer to K49918625: Overview of the F5 rSeries system architecture.

Note: F5OS-A and F5OS-C are unified in F5OS 2.0.0. For information about F5OS 2.x software versions for F5 hardware platforms, refer to K000161884: F5OS-A and F5OS-C are unified in F5OS 2.0.0.

Description

The VELOS system is comprised of a VELOS chassis that houses system controllers, blades, power supplies, fans, and other components.

VELOS system controller

The system controller is a purpose-built blade that manages the entire chassis. The system controller includes a serial console and management port on its front panel, as well as both the control plane and the data plane switches to which every installed blade in the chassis connects. A functional VELOS system requires at least one controller. The system supports dual redundant controllers in an active-standby redundancy model to provide a single point of management and control. This redundancy model is controlled by a low-level hardware redundancy interface, which cross-connects to both controllers, and monitors the output for the following behaviors:

  • Presence of peer
  • Health of peer
  • Peer requesting to be active
  • Active peer indicator

Although the dual system controllers are in active-standby mode, the control plane and data plane on both controllers are fully operational in an active-active model. For high availability (HA) and full backplane performance, F5 recommends that you install the VELOS chassis with two system controllers.

The system uses a floating management IP address that is hosted on the active controller as an access point to the webUI, command-line interface (CLI), and representational state transfer (REST) API interfaces for configuring and managing the system. F5 recommends that you connect the management port on each of the system controllers to your management network.

Two confd processes manage the various configurations of the system at the chassis level in a highly available configuration running each instance on each controller. The configuration data is read/written in the configuration database of the active instance and replicated to the standby instance. The standby instance rejects received requests to modify the configuration, which ensures consistency and integrity of the configuration data in the event of a failover between the system controllers.

Note: F5OS / F5OS-C is not based on TMOS; the config and tmsh utilities are not available to configure the VELOS system. For information about performing the initial setup, refer to the VELOS system initial configuration chapter of the VELOS Systems: Getting Started guide.

VELOS blade

The VELOS blade is a compute blade with physical network ports and is the core component in the VELOS system that performs the data plane traffic processing. The VELOS blade has no physical management port and console port and is managed using only the chassis terminal service on the system controller.

F5OS 2.x

F5OS 2.x is the operating system software on the VELOS hardware. F5OS 2.x manages the various configurations of the VELOS system, such as network, partitions, tenants, and users. The F5OS 2.x software comprises the Base OS and Service components.

The Base OS component on the system controller includes the following software:

  • Rocky Linux
  • Docker
  • Ansible
  • KubeVirt-VELOS
  • K3s

The Service component on the system controller includes the following software:

  • F5-produced software, such as qkview, and platform-specific packages

F5OS-C 1.x

F5OS-C 1.x is the operating system software on the VELOS hardware. F5OS-C 1.x manages the various configurations of the VELOS system, such as network, partitions, tenants, and users. The F5OS-C 1.x software comprises the Base OS and Service components.

The Base OS component on the system controller includes the following software:

  • CentOS Linux
  • Docker
  • Ansible
  • KubeVirt-VELOS

The Service component on the system controller includes the following software:

  • KubeVirt
  • OpenShift
  • Multus
  • F5-produced software, such as qkview, and platform-specific packages

F5OS 2.x / F5OS-C 1.x partition

An F5OS 2.x / F5OS-C 1.x partition (also known as chassis partition) is a logical grouping of VELOS blades installed in a chassis. An F5OS 2.x / F5OS-C 1.x partition can have minimally one blade and up to the total number of blades installed in the chassis. By default, a blade installed in a chassis belongs to partition ID 1 until the blade is reassigned to another F5OS 2.x / F5OS-C 1.x partition. Partition 1 is the default partition of a VELOS system.

In terms of network security, an F5OS 2.x / F5OS-C 1.x partition functions like a standalone managed device where a blade belonging to a partition can only communicate with another blade in the same partition through the backplane. Therefore, both the control and data plane of a partition are logically separated from other partitions in a chassis.

A chassis administrator can create and manage an F5OS 2.x / F5OS-C 1.x partition through the system controller. When you configure an F5OS 2.x / F5OS-C 1.x partition, the F5OS 2.x / F5OS-C 1.x refers to an installed blade as a slot. For example, F5OS 2.x / F5OS-C 1.x refers slot 1 as the blade installed physically in the first slot.

Important: The F5OS 2.x / F5OS-C 1.x partition functions at the VELOS chassis level, which is different than the BIG-IP administrative partition. The BIG-IP administrative partition functions at the BIG-IP system objects. For more information about the BIG-IP administrative partition, refer to K7230: Overview of administrative partitions.

Similar to the system configuration at the chassis level, the configuration at the partition level is managed by partition-specific confd processes in a highly available configuration with each instance running on one of the two system controllers. Note that the partition-specific confd processes are separate instances from the confd processes running at the chassis level.

Also similar to the software at the chassis system controller, the F5OS 2.x / F5OS-C 1.x partition software comprises the Base OS and Service components.

The F5OS 2.x Base OS component on the partition includes the following software:

  • Rocky Linux
  • Docker
  • Ansible
  • K3s

The F5OS-C 1.x Base OS component on the partition includes the following software:

  • CentOS Linux
  • Docker
  • Ansible
  • Flannel

The F5OS 2.x / F5OS-C 1.x Service component on the partition includes the following software:

  • F5-produced blade-specific packages, such as qkview for the partition, license service, and Field-Programmable Gate Array (FPGA) manager
  • Partition webUI
  • tcpdump

F5OS 2.x / F5OS-C 1.x tenant

An F5OS 2.x / F5OS-C 1.x tenant is a guest system deployed in a VELOS partition. A partition can have zero or more tenants limited to the amount of computing resources (CPU/memory/network) of the partition.

When you create a tenant, the system leaves the tenant in the Configured state by default. In the Configured state, the tenant's configuration exists on the partition; however, the VELOS partition does not allocate any hardware resources to the tenant, and the tenant does not run in this state.

BIG-IP tenant

When you change the tenant from the Configured to the Provisioned state, the VELOS partition does the following:

  • Assigns the tenants to the blades
  • Creates virtual disks for the tenants on the assigned blades
  • Installs the image on the virtual disk

    Note: In the command line, F5OS 2.x / F5OS-C 1.x refers to a blade assigned to a partition as a node. However, in the webUI, it is referred to as a slot.

During this process, the system reports the status of the tenant as Provisioning. When this process completes, the system reports the status of the tenant as Provisioned.

When you change the tenant from the Provisioned to the Deployed state, the VELOS partition starts up the tenant, and the system reports the status of the tenant as Starting initially and subsequently Running when the tenant is up.

When you want to shut down a tenant, configure the state of the tenant to either Provisioned or Configured. For more information about shutting down and starting up a tenant on the VELOS system, refer to K21121803: Shutting down and restarting a tenant on the VELOS and rSeries systems.
