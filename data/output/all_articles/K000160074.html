Description

The F5 Observer on BIG-IP Next for Kubernetes supports the use of NFS (Network File System) as a StorageClass for its Persistent Volume Claims (PVCs) to facilitate long-term stats collection. While NFS provides a flexible storage solution, it requires specific permission and export configurations to work seamlessly with the Observer's containerized architecture.

If the NFS server or the Kubernetes StorageClass is not aligned with the pod's security context, the f5-observer-receiver may fail to initialize, typically resulting in a CrashLoopBackOff due to filesystem Permission Denied errors.

This article outlines some specific issues when using NFS-backed storage and provides four plausible solutions—ranging from manual ownership adjustments to Helm-based configuration changes—to restore full functionality to the stats collection pipeline.

Environment

  • BIG-IP Next for Kubrnetes
  • NFS as StorageClass for PVCs

Cause

The f5-observer-receiver pod fails to start and enters CrashLoopBackOff. The logs contain the following error:

metricsdb: failed to open pebble db: open /var/metrics/v1alpha2/LOCK: permission denied

This occurs when the Receiver pod (running as UID/GID 7053) cannot write to its NFS-backed persistent volume due to NFS server-side permission restrictions.

Recommended Actions

Use one of the following solutions to resolve the issue as appropriate for your environment:

  • Manually set ownership on NFS directory (root_squash)
  • Match the pod security context to NFS anonuid/anongid (all_squash)
  • Use emptyDir instead of persistent storage (helm only)
  • Create a new NFS storage class with UID/GID 7053

Manually set ownership on NFS directory (root_squash)

On the NFS server, create the required directory and set the ownership to 7053. For example:
Note: This solution is not scalable. Recommended only when deploying via F5 Lifecycle Operator (FLO), where the Receiver pod count remains fixed.

  1. Change directory:
    cd $NFS_ROOT/f5-utils-stats-pvc-f5-observer-receiver-0-pvc-*/f5-utils
  2. Create a new directory:
    mkdir -p v1alpha2
  3. Set the permissions with the cchown command:
    cchown -R 7053:7053 v1alpha2
  4. Repeat for each Receiver's PVC directory if multiple Receivers are deployed.

Match the pod security context to NFS anonuid/anongid (all_squash)

When the NFS server is configured with all_squash,anonuid=,anongid=, all client requests are mapped to the specified UID/GID regardless of the pod's actual user. To resolve this, update the Receiver's stateful-set security context and fsGroup to match the NFS squash UID/GID.

Use emptyDir instead of persistent storage (helm only):

Disable persistence in the Observer Helm values:
persistence:
   enabled: false
The above code replaces the PVC with an emptyDir ephemeral volume.
Note: If the Observer has already been installed via Helm, uninstall and reinstall with the updated values.
Impact:

  • Live TMM metrics are unaffected. Metrics are extracted from TMMs every 1-minute cycle regardless of persistence.
  • Dead-TMM metrics metrics from TMMs that were previously running but have since terminated may be lost if the Receiver pod restarts.

Mitigating factor:
Receivers synchronize dead-TMM metrics among themselves. If one Receiver restarts, other Receivers will re-sync the dead-TMM metrics to it upon recovery. Actual data loss only occurs if all Receivers go down simultaneously.

Create a new NFS storage class with UID/GID 7053

This solution requires changes on both the NFS server and Kubernetes cluster.

  1. Create a new NFS storage class that exports with all_squash,anonuid=7053,anongid=7053.
    This ensures all file operations are mapped to UID/GID 7053, matching the Receiver pod's security context.

  2. Configure a new export on the NFS server with the correct squash settings, then create a StorageClass pointing to it.
    The existing stats-pvc PVCs and StatefulSet must be deleted and recreated to use the new StorageClass, as PVC storage class configuration is immutable.
