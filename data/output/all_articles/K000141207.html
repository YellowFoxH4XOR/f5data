K000141207: Pool selection via iRule is not working properly

Type
Support Solution
Published
2024-09-27
Updated
2025-04-01
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000141207

Description

Pool selection using an iRule does not work reliably.

 

Environment

  • BIG-IP
  • Virtual Server has several iRules applied
  • At least one of the iRules has a HTTP::response command
  • Connections to the Virtual Server come via another proxy, such as Akamai, Cloudflare or similar

Cause

When using iRules with a HTTP::response command, care has to be taken to not do any further iRule processing that requires access to HTTP variables to avoid "ERR_NOT_SUPPORTED" TCL errors. A common approach is to either use "event disable all" after the HTTP response or "if { [HTTP::has_responded] } { return }" in all iRule events that access HTTP variables (K23237429).

If there is a proxy in front of the BIG-IP this becomes difficult since the proxy will most likely use TCP Connection Pooling (sending multiple HTTP request from different end-clients via the same TCP connection). In this case applying the above mentioned workarounds will result in iRules or iRule events being disabled for all HTTP requests that follow the request that produced the HTTP response. If these iRules or iRule events contain pool selections, these will not be executed and the requests may go to the wrong pool members.

 

Recommended Actions

Add the line "TCP::close" after the "HTTP::respond" line.
