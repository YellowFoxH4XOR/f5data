Description

When the BIG-IP starts loading its configuration, sometimes it will be unable to read the encrypted master key from the SEPROM module causing the device to be unable to load the configuration and forcing it to an INOPERATIVE state.
You may also observe log messages in /var/log/LTM similar to the following example: 

Feb 12 08:34:16 BIGIP-A notice mcpd[5595]: 01071029:5: SecureVault encountered issue with reading Unit key from SEEPROM. Try rebooting the system...
Feb 12 08:34:17 BIGIP-A notice mcpd[5595]: 01071029:5: SecureVault encountered issue with reading Unit key from SEEPROM. Try rebooting the system...

Environment

  • The affected unit is part of an HA configuration
  • The device is accessible through CLI/SSH
  • The Active device is accessible through CLI/SSH

Cause

The BIG-IP might encounter this error after the following actions were taken:

  • System reboot
  • Configuration reload (tmsh load sys config)
  • Failsafe service restart
  • Services restart (tmm, mcpd)

Recommended Actions

It is possible to recover the BIG-IP from an INOPERATIVE state caused by the SecureVault by following this procedure:

  1. Access the working device through SSH (Active in the HA).
  2. Make a UCS backup this working device.
    # tmsh save sys ucs f5-backup
     
  3. Print out the master key.
    # f5mku -K

Copy the base64 key output from the above command, and save it on your workstation also copy the UCS file to your workstation too.

The following steps need to be performed in the INOPERATIVE device of the HA.

  1. Clear the unit key.
    # f5mku -c

    Type Yes to confirm the command execution.
    The output should look similar to this:

    [root@BIGIP-B:INOPERATIVE:] # f5mku -c
    Clear unit key.  Checking for existing key.
    EXISTING KEY FOUND!  Removing this key may invalidate all
    encrypted passphrases!  Are you sure? yes
    Clearing unit key
    Removing unit key: /config/bigip/kstore/unit1.crt
    Removing master key: /config/bigip/kstore/master.1
    Removing new master key: /config/bigip/kstore/master
    [root@BIGIP-B:INOPERATIVE:] #
     
  2. Stop all BIG-IP services.
    # bigstart stop
     
  3. Set the flag for mcpd to perform a forceload.
    # touch /service/mcpd/forceload
     
  4. Start the BIG-IP services back up.
    # bigstart start
     
  5. Tail the logs and wait for the services to finish coming back up. This may take over 5 minutes since the device performs a hardware check and rebuilds the MCPD binary database out of the text configuration files. Eventually, you'll see some unit key / master key messages and errors, as it will fail to load the config. 
    # tailf /var/log/ltm
  6. Check to see that a new unit key was properly re-generated (look for SUCCESS printed out toward the bottom):
    # f5mku -f -v 

    The output should look similar to this:

    [root@BIGIP-B:INOPERATIVE:] # f5mku -f -v
    query unit: unit ID not found
    Query Platform: Secure Key NOT available
    loading unit key...
    load_unit_key() started
    Legacy Storage open: /config/bigip/kstore/.unitkey
    Unit Key Header successfully read.
    -- hdr.version = dad2
    -- hdr.hlen    = 32
    -- hdr.klen    = 32
    -- hdr.hash    = 91:ec:2e:aa:d0:31:3f:47:e9:fa:8f:be:3b:19:ad:b3:bd:ca:01:e7
    -- hdr.udate   = Fri Feb 12 12:55:02 2021

            SUCCESS
    Unit Key Hash:  kewuqtAxP0fp+o++Oxmts73KAec=    s
    [root@BIGIP-B:INOPERATIVE:] #
     
  7. Set the master key to the same value that was retrieved when running "f5mku -K" on the peer box:
    # f5mku -r PeerBase64Value
     
  8. Try to load the config, this step can take over 5 minutes.
# tmsh load sys config
  9. If the config did load, make sure you can save the config properly too
    # tmsh save sys config
