K000163891: Managing custom attack signature IDs and sequential naming in BIG-IP ASM

Description

BIG-IP ASM custom attack signature IDs continue to increase after signatures are deleted, leaving gaps in the allocated ID sequence. Custom signature IDs do not correspond sequentially to the signatures that currently exist.

Environment

BIG-IP ASM 17.5.1 with user-defined custom attack signatures.

Cause

Custom signature IDs are allocated from an auto-increment counter in the PLC.NEGSIG_SIGNATURES configuration database table. Deleting a custom signature removes its database row but does not decrement the counter. Deleted IDs are therefore not reused, and gaps are not backfilled.

Answer/Recommended Actions

Custom signature IDs are internal database keys and should be treated as opaque identifiers. Resetting the counter or reusing deleted signature IDs is not supported.

Do not edit sid_id values by exporting custom signatures to XML, modifying the XML, and importing it again. Although an unused sig_id may import and an existing ID may appear to be overwritten, this behavior is not fully verified and may affect database integrity. Reusing an ID may leave stale policy overrides in effect and may cause historical events that reference the reassigned ID to be mislabeled. Full downstream-reference validation during import has not been confirmed.

Do not use XML export and import to rename an existing signature. Instead, use the following replacement workflow:

  1. Create a new custom signature with the desired name and the same rule content.
  2. Add the new signature to the same signature sets and confirm its assignment to the intended policies.
  3. Re-create the old signature's per-policy enable or disable state, staging or quarantine state, URL-level and parameter-level overrides, and signature-set membership as applicable.
  4. Verify that the new signature has left staging and is enforcing.
  5. Delete the old signature only after verification.

Use the Attack Signature List, filtered to user-defined signatures, to determine the current number of custom signatures. The highest allocated signature ID represents the total number of signatures created, not the number of signatures currently present.

Additional Information

A new custom signature does not inherit per-policy state from the signature it replaces. Newly created or imported custom signatures are placed into staging for policies that include the signature in their assigned signature sets. Validate the replacement workflow with one signature in a non-production environment before applying it to additional signatures.
