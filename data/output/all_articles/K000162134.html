K000162134: Snat-translation object got orphaned while running "delete ltm snat all" TMSH command.

Type
Support Solution
Published
2026-07-08
Updated
2026-07-08
Applies to
  • BIG-IP
  • BIG-IP LTM: 21.1.0
Source
https://my.f5.com/manage/s/article/K000162134

Description

When "tmsh delete ltm snat all" command is executed, snat-translation object, which was automatically created while parent snat object was created, may not be deleted and got orphaned. 

Here is example case, snat-translation object "10.1.1.1" got orphaned after running "delete ltm snat all" command.

[root@bigipltm:Active:Standalone] config # tmsh create ltm snat my_snat origins add { 10.0.0.1 } translation 10.1.1.1
[root@bigipltm:Active:Standalone] config # tmsh list ltm snat
ltm snat my_snat {
    origins {
        10.0.0.1/32 { }
    }
    translation /Common/10.1.1.1
}
[root@bigipltm:Active:Standalone] config # tmsh list ltm snatpool
[root@bigipltm:Active:Standalone] config # tmsh list ltm snat-translation
ltm snat-translation 10.1.1.1 {
    address 10.1.1.1
    inherited-traffic-group true
    traffic-group traffic-group-1
}
[root@bigipltm:Active:Standalone] config # tmsh delete ltm snat all
[root@bigipltm:Active:Standalone] config #
[root@bigipltm:Active:Standalone] config #
[root@bigipltm:Active:Standalone] config # tmsh list ltm snat
[root@bigipltm:Active:Standalone] config #
[root@bigipltm:Active:Standalone] config #
[root@bigipltm:Active:Standalone] config # tmsh list ltm snat-translation
ltm snat-translation 10.1.1.1 {
    address 10.1.1.1
    inherited-traffic-group true
    traffic-group traffic-group-1
}
[root@bigipltm:Active:Standalone] config #

 

The remaining snat-translation object can not be manually deleted on TMSH or GUI. An error message "01070321:3: Snat translation address /Common/x.x.x.x is still referenced by a snat pool." is returned despite there is no snat pool object referring to the snat-translation object.

[root@bigipltm:Active:Standalone] config # tmsh delete ltm snat-translation all
01070321:3: Snat translation address /Common/10.1.1.1 is still referenced by a snat pool.
[root@bigipltm:Active:Standalone] config #

 

Once snat-translation object got orphaned, another error message "01070712:3: Invalid primary key on trans_addr object - path is empty." may be displayed and snat creation may fail while trying to create new snat-translation object.

[root@bigipltm:Active:Standalone] config # tmsh create ltm snat-translation 10.2.2.1 { address 10.2.2.1 traffic-group traffic-group-1 }
01070712:3: Invalid primary key on trans_addr object - path is empty.
[root@bigipltm:Active:Standalone] config #

 

Also, different error message "01070734:3: Configuration error: Invalid primary key on trans_addr object () - not a full path 2." may be displayed while trying to create another/new snat object.

[root@bigipltm:Active:Standalone] config # tmsh create ltm snat my_snat2 origins add { 10.4.4.1 } translation 10.5.5.1
01070734:3: Configuration error: Invalid primary key on trans_addr object () - not a full path 2.
[root@bigipltm:Active:Standalone] config #

 

Environment

  • Ran "tmsh delete ltm snat all" command.
  • Running BIG-IP v21.1.0. No other software versions are known to be affected, at the time of article publication.

 

Cause

Bug ID2365353.

 

Answer/Recommended Actions

Orphaned snat-translation object can be manually deleted after executing mcpd forceload reboot (ref: K13030). Once the problematic/orphaned snat-translation object is deleted, no more error should be generated while trying to create new snat or snat-translation object.

# touch /service/mcpd/forceload
# reboot
# tmsh delete ltm snat-translation 10.1.1.1 ; tmsh save sys config

 

The problem does not occur when "all" is not specified on "tmsh delete ltm snat" command. For instance, problem does not occur while deleting specific snat object only, as shown below.

# tmsh delete ltm snat my_snat2

 

Additional Information

None.
