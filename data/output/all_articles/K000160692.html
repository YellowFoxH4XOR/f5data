Description

The request for the manifest is made without any credentials (even if it's on the same domain), thus if the manifest requires credentials, you must include crossorigin="use-credentials" in the manifest tag.

https://developers.google.com/web/fundamentals/web-app-manifest/

This causes issues in APM because the request without a cookie is responded to with a 302 to /my.policy to start a session.  This will send new MRHSession cookies and confuse the browser and your currently authenticated session.  No sending cookies is the default behavior of the browser and nothing that APM has control over.

Request to https://<VIP DNS NAME>/f5-w-<hex string>$$/manifest.json recieves a 302 Redirect to https://<VIP DNS NAME>/my.policy

Environment

  • BIG-IP APM

Cause

Default browser behavior for web app manifest file request.

Recommended Actions

To accommodate for no cookies being sent we have two options.

  • If you don't have access to the application to make changes we can add an iRule to respond to the manifest file before it can alter the APM session.
when HTTP_REQUEST {
  if { [HTTP::has_responded] } { return }
  if { [HTTP::path] contains "/manifest.json" } {
    HTTP::respond 200 content {}
  }
}

*The path and name of the manifest file might be different than "/manifest.json" so you will need to adjust the iRule accordingly.

  • If you have control of the application you can include  crossorigin="use-credentails" to your manfiest tag.
Adding <link rel="manifest" href="/manifest.json" crossorigin="use-credentials"> for both cross domain as adding server cookies in the request for the manifest
