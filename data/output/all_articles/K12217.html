Known Issue

This is the result of a known issue. If an iRule applied to a virtual server uses the HTTP::respond command within an LB_FAILED event, and the pool applied to the same virtual server has the Action On Service Down setting configured to the reselect option, a condition may occur in which an HTTP response from the reselected pool member is sent to a client-side connection that has already been closed. This event causes TMM to dump core with a SIGSEGV fault.

This issue may occur if you apply an iRule that appears similar to the following example to a virtual server that sends traffic to a pool with the Action On Service Down setting configured to reselect:

rule Sorry_Page {
when LB_FAILED {
log local0. "<Host: [HTTP::host]><client: [IP::client_addr]> <server: [LB::server addr]>"
HTTP::respond 200 content "
<html>
<head>
<title> Sorry Page </title>
</head>
<body>
<center>
The site you are looking for is temporarily out of service<br>
</body>
</html>"
}

When this condition occurs, TMM will crash, as shown in log messages and core files that appear similar to the following examples:

  • /var/log/ltm

    notice sod[4166]: 01140045:5: HA reports tmm NOT ready.

  • /var/log/tmm

    notice cmp state: 0x0

    notice ** SIGSEGV **

  • /var/core/

    tmm.0.bld18.1.core.gz

F5 Product Development tracked this issue as ID 342346 and it was fixed in BIG-IP 11.0.0, and BIG-IP 10.2.4 HF12. For information about upgrading, refer to the BIG-IP LTM, ASM, GTM, PSM, Link Controller, WebAccelerator, or APM release notes.

Workaround

You can work around this issue by changing the Action on Service Down setting from reselect to none in the pool properties, or by ensuring that an iRule that meets the criteria featured in the above example is not assigned to a virtual server that has a pool set to reselect.
