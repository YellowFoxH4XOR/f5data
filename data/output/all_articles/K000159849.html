# F5 Access App for Android Certificate Verification Failure During SAML Authentication with Microsoft Azure IdP Due to Missing Intermediate CA Certificate

Description

Android users are unable to authenticate through F5 Access App when connecting to BIG-IP APM VPN configured with SAML authentication using Microsoft Azure as the Identity Provider (IdP). The following symptoms occur:

  • Error message: "Unable to verify SSL certificate presented by the server: aadcdn.msauthimages.net"
  • Error states: "This certificate is not from a trusted authority"
  • Certificate verification fails specifically for Microsoft authentication portal URLs during the SAML redirect process
  • Issue affects all Android users while other devices (laptops, Windows, iOS) authenticate successfully
  • No recent changes or upgrades to BIG-IP APM or F5 Access App

F5 Access App logs show:

java.security.cert.CertPathValidatorException: Trust anchor for certification path not found

handshake failed; returned -1, SSL error code 1, net_error -202

onReceivedSslError: primary error: 3 certificate: Issued to: CN=idnaakamaicdn.msftauth.net

The certificate validation error occurs when the F5 Access App attempts to load content from Microsoft authentication sites (aadcdn.msftauth.net, idnaakamaicdn.msftauth.net) during the SAML authentication flow, not during the initial connection to the BIG-IP APM virtual server.

Environment

  • Product: BIG-IP APM
  • Version: 17.1.3 (all versions with SAML authentication)
  • Platform: F5-BIG-APM-I5800-B, C119 (all platforms)
  • Client: F5 Access App version 3.2.1 on Android devices (Android 13 and later)
  • Configuration: APM virtual server configured as SAML Service Provider with Microsoft Azure as SAML Identity Provider
  • Affected URLs: aadcdn.msauthimages.net, aadcdn.msftauth.net, idnaakamaicdn.msftauth.net
  • Certificate Chain: Microsoft TLS G2 ECC CA OCSP 06 (intermediate), Microsoft TLS ECC Root G2 (root CA)
  • Authentication Flow: SAML-based authentication with redirect to Microsoft Azure IdP

Cause

The intermediate CA certificate (Microsoft TLS ECC Root G2) required to validate certificates presented by Microsoft authentication portals is missing from the Android device's trusted certificate store. This issue typically occurs due to certificate renewal on Microsoft's intermediate CA infrastructure.

Android devices do not automatically download missing CA certificates from the authorityInformationAccess field of certificates, which is an Android platform limitation. When the certificate chain is incomplete, the F5 Access App cannot validate the server certificates presented during the SAML authentication flow to Microsoft's authentication portals, resulting in authentication failures.

Important: This issue is not related to the BIG-IP APM's own SSL certificates. The certificate validation failure occurs during client-to-Microsoft communication after the SAML redirect, which does not traverse the BIG-IP APM.

Answer/Recommended Actions

Resolution Steps:

  1. Obtain the missing intermediate CA certificate (Microsoft TLS ECC Root G2) in .CER format:
    • Extract it from a packet capture taken on the Microsoft authentication server during a successful authentication from a non-Android device
    • Or obtain it directly from Microsoft
  2. Distribute the certificate file to affected Android users via email, file sharing, or mobile device management (MDM) system
  3. Instruct users to manually import the certificate on their Android devices:
    • Save the .CER file to the device's internal storage
    • Navigate to Settings → Security & Privacy → Other Security settings → Install from device storage → CA certificate
    • Select the saved .CER file and install it
    • The device may prompt for the device PIN or password
  4. Verify VPN connectivity through F5 Access App after certificate installation
  5. Test authentication with multiple Android users to confirm resolution

Preventive Measures:

  • Ensure Network Load Balancers and authentication infrastructure certificate stores include the entire certificate chain
  • When deploying SAML authentication with Microsoft Azure for Android devices, pre-distribute all required intermediate CA certificates to users via MDM
  • Monitor for certificate renewals on Microsoft authentication infrastructure that may impact Android clients
  • Consider implementing automated certificate distribution through MDM for enterprise deployments
  • Document the required certificate chain for your SAML authentication flow

Verification Steps:

To verify the certificate chain issue before resolution:

  1. Capture packets from the authentication server to the client during authentication
  2. Extract server certificates and intermediate certificates from the packet capture
  3. Compare against the Android device's trusted CA store to identify missing certificates
  4. Use OpenSSL to verify the certificate chain:
    openssl verify -CAfile <ca_bundle> <server_cert>

Additional Information

Android Certificate Handling Limitation:

Android does not support downloading additional certificates from the authorityInformationAccess field of certificates. This is true across all Android versions and devices, including the Chrome browser. Any server authentication certificate requiring additional certificate downloads will trigger validation errors if the entire certificate chain is not already present on the device.

Traffic Flow Context:

During SAML authentication with BIG-IP APM as Service Provider:

  1. F5 Access App connects to the APM virtual server
  2. APM generates a SAMLRequest and redirects to Microsoft Azure SAML IdP
  3. The client follows the redirect and submits the SAMLRequest to Microsoft's authentication portal
  4. Microsoft's authentication portal loads content from multiple Microsoft CDN sites (aadcdn.msftauth.net, idnaakamaicdn.msftauth.net, etc.)
  5. At this stage, the client communicates directly with Microsoft sites - this traffic does NOT traverse the BIG-IP APM
  6. Certificate validation failures occur during this direct client-to-Microsoft communication

Because the traffic does not traverse the BIG-IP APM, packet captures on the APM will not reveal this client-to-Microsoft communication. Troubleshooting requires client-side logs (F5 Access App logs) or packet captures from the client device.

Why Other Devices Work:

  • Windows, macOS, and iOS devices typically have more comprehensive trusted CA certificate stores
  • These platforms may already include the Microsoft TLS ECC Root G2 certificate
  • Some platforms automatically download missing intermediate certificates during TLS handshakes
  • Android's strict certificate validation and inability to auto-download certificates makes it more susceptible to this issue

Microsoft Documentation Reference:

Using ADAL to authenticate from Android devices fails if additional certificate downloads are required. This is a known limitation documented by Microsoft for Android authentication scenarios.

https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/mfa/adal-authenticate-android-devices-fail
