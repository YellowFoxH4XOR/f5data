Known Issue

Description

When an Origin Web Server sends back a 302 response through a BIG-IP WebAccelerator-enabled virtual server, the body of the response is not compressed, regardless of the BIG-IP WebAccelerator profile setting.

This issue occurs when the following condition is met:

  • Your BIG-IP WebAccelerator profile is configured to compress responses.

Impact

You may not benefit from bandwidth savings due to the data not being compressed.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • The body of a 302 redirect is not compressed, even if the client supports compression, as indicated by the client Accept-Encoding header.
  • 302 redirect responses sent to the client do not have the Content-Encoding: gzip header.

Due to architectural changes, this issue does not affect version 11.x of the BIG-IP WebAccelerator system.

Workaround

To work around this issue,  you can enable compression in the http profile to complement BIG-IP WebAccelerator compression.  When BIG-IP WebAccelerator and http profile compression are both enabled, BIG-IP WebAccelerator compression takes precedence over http profile compression, which then becomes the compressor of last resort. To enable http profile compression, perform the following procedure:

WebAccelerator 10.2.1 - 10.2.4

Impact of workaround: None

  1. Log in to the BIG-IP Configuration utility as an administrator.
  2. Click the Local Traffic tab on the left side of the screen.
  3. Choose the Profiles > Services > HTTP menu option.
  4. Select the http profile that is associated with your BIG-IP WebAccelerator-enabled virtual server.
  5. Under the Compression section, enable compression and any required user-configured compression options.
  6. Click Update to complete the change.

WebAccelerator 10.0.0 - 10.2.0

There is no workaround for these versions.
