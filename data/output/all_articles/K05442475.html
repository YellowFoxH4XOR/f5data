Description

The purpose of this article is to inform F5 BIG-IP customers about the hardware protection feature included in most modern CPUs such as the Intel CPUs used on current BIG-IP hardware platforms (or potentially Intel or AMD CPUs used by BIG-IP VE devices via a hypervisor) called "thermal throttling", and its effects. It also explains some limitations of software-based thermal throttling of CPU by lowering CPU frequency, which is a feature of some modern OSs such as Linux.

The hardware thermal throttling feature on current CPUs is not configurable in any way.

Environment

  • Any environment (VE or chassis in the case of BIG-IP) utilising a modern CPU, such as current Intel and AMD CPU offerings

Cause

None

Recommended Actions

None

Additional Information

Most modern CPUs (Intel or AMD) automatically instantaneously throttle their speed when their internal temperature goes too high, without giving any log messages that there is thermal throttling taking place. The only outward indication of this throttling taking place occurs when the hardware sensors are being monitored - there is a flag that says basically 'thermal throttling of CPU speed is currently taking place' which gets set to "true", but this is not monitored or logged anywhere by default in any common OS (eg. linux or windows), and it gets set back to "false" as soon as the temperature falls again and throttling is no longer taking place (ie. it is not a counter, it's a true/false flag which indicates only the current situation at the instant when the flag is read).

This means we (BIG-IP) can't really do a specific action (eg. graceful shutdown, or force failover) when hardware thermal throttling of CPU speed takes place, since we don't monitor that flag/sensor constantly.

There is confusion in some circles about this topic since the Linux OS does have an error message regarding thermal throttling taking place in its kernel, however this error message is referring to software-controlled thermal throttling, which is not CPU-specific and can be configured to trigger at any temperature specified in the OS (basically the CPU core temperature sensors are monitored at specific time intervals, and if the core temperature reaches above a certain number, Linux can be configured to throttle the CPU frequency, and logs a thermal throttling message).

Generally, when specific action by the OS is desired based on CPU core temperature, it's triggered by monitoring the CPU core temperature reported by the CPUs sensors at periodic intervals, and taking preventative action based on the current temperature reading and based on that the likelihood that the CPU will undergo instantaneous hardware thermal throttling in the near future (before the next poll).

Thus, setting up something like an SNMP alert that triggers a "shutdown" command which would trigger when the CPU core temperature goes above a set limit is possible - however it does not preclude the hardware thermal throttling from occurring, since SNMP usually updates only once per second or a similar time period, and it would be normal behaviour if the CPUs internal hardware thermal throttling kicked in automatically and silently before the CPU core temperature was detected as having been over the limit by the OS, if the temperature jumped suddenly due to a sudden workload.
This is why it's always advisable to set the OS check for the CPU core temperature to at least 5-10% below the actual core temperature limit on whatever CPU hardware is in your device.
