Topic

The bigpipe ms command provides a screen of statistical data that you can use to monitor and troubleshoot the BIG-IP system. The bigpipe ms command polls the BIG-IP kernel directly and, therefore, provides authoritative information. This article provides details about the information that is provided by the bigpipe ms command.

Note: The information provided in this article is for advanced users. If you have questions regarding this article, or if you need assistance interpreting the information from the bigpipe ms command, contact F5 Technical Support.

Important: Data presented by the bigpipe ms command is not stored after a reboot. If you want to retain the information, you must write the data to a file by using the bigpipe ms > <output.file> command before rebooting the BIG-IP system.

In normal operation, the BIG-IP kernel will attempt to request a gigabyte of memory for internal kernel use. If a full gigabyte is not available it will take a smaller portion of memory. The output of the bigpipe ms command shows how memory usage is distributed internally.

Note: Some versions of the BIG-IP system may not have all of the fields listed in the following example. The fields that are listed have the same meaning (as defined later in this article) in all versions of the BIG-IP system.

Each set of statistics is divided into the following three parts:

  • BIG-IP inuse
    The current number of instances for the listed object.
  • BIG-IP max
    The maximum number of instances for the object since the last reboot.
  • BIG-IP mem
    The number of kernel memory bytes used by all current instances.

Following are the details for the individual statistics:

snat tran, snat org
snat tran is the number of translated addresses used by all SNATs and snat org is the number of internal source addresses used by the SNATs. These statistics indicate the distribution for the source and destination addresses that are currently using SNATs.
nat
nat is the number of connections through all NATs on the BIG-IP system.
virtport, vipbox and virtaddr
The BIG-IP system stores virtual servers internally as a tree structure. The top of the tree is the IP address of the virtual server that is referred to as the virtual server head. Branches of the tree represent specific address:port combinations. Each branch is called a vip box. virtaddr is the number of different addresses for which virtual servers are defined on (virtual server heads). In the case of a network virtual server, virtaddr still represents only one entry. virtport is the total number of ports explicitly defined for all the virtual servers. A wildcard port is not counted in this list. FTP is only counted as one port in this structure even though it represents a port pair.
sslproxy, sslproxyaddr
sslproxy is the number of proxies that are defined on the BIG-IP system. sslproxyaddr is the number of unique IP addresses on which those proxies are defined.
pool
pool is the number of pools defined on the BIG-IP system. This statistic includes one entry for each forwarding pool as well as special pools, such as the default gateway pool.
nodebox, nodeaddr and nodeport
Node definitions are stored in a structure similar to virtual servers. The node IP address forms the head and the number of unique node IP addresses are stored in the nodeaddr structure. The nodeport is the total number of unique ports defined across all the nodes. The nodebox structure stores the number of unique address:port combinations. This contrasts with the member structure; if the same node address:port combination is defined in two separate pools, it would count as only one nodebox, but as two members.
member
member is the total number of nodes that are defined in all pools. It differs from a nodebox, because it does not account for the same node being defined in more than one pool. If the same node address:port combination is defined in two separate pools, it would count as two members, but only one nodebox.
vlanlist
vlanlist is tallied based on the number of disabled VLANs on the BIG-IP system; that number is calculated by checking each NAT, SNAT, virtual server, and proxy for a disabled VLAN. For example: if a NAT is disabled on a particular VLAN, an entry is created on the vlanlist. If the NAT is re-enabled on that VLAN, the entry is located and removed from the list and the count for this statistic decreases.
conn
conn is the total number of connections (TCP and UDP) in the connection table of the BIG-IP system (as seen in a b conn dump.)
snat conn
snat conn is the total number of TCP and UDP connections in the BIG-IP system's SNAT connection table. In BIG-IP version 4.5 and later, this statistic is rolled into the conn entry in the output of the bigpipe ms command.
persist
persist is the number of entries in the simple persistence table.
sticky
sticky is the number of entries in the sticky persistence table. In BIG-IP version 4.5 and later, this statistic is rolled into the persist entry.
ssl id
ssl id is the current number of SSL session IDs for use in session resumption by a proxy currently cached in memory (maximum value for this is defined by the global sslproxy serverssl cache size).
idle http
idle http reports the number of OneConnect streams (keep-alive connections) that are open and waiting for a request.
tcp proxy
There is one TCP proxy for each late binding/bound connection in the current connection table. Examples of connections requiring delayed binding are virtual servers that use a rule or a method of cookie persistence.
app proxy
app proxy defines the cumulative number of delayed binding sessions that are passed through the BIG-IP system. Examples of connections requiring delayed binding are virtual servers that use a rule or a method of cookie persistence.
app 2k, app 4k, app 8k and app 16k
In connections requiring delayed binding, the BIG-IP system must proxy the initial part of the connection before making a load balancing decision. For example, the BIG-IP system may need to proxy a connection long enough to scan the HTTP header for a cookie on pools using cookie persistence. The BIG-IP system initially places the received data into a 1K buffer (which is not shown in the bigpipe ms output). If the 1K buffer proves to be too small to hold the data, the data is promoted to the app 2K buffer. If more data is required before making a load balancing decision, the data is promoted to the app 4K buffer, then the app 8K buffer, and finally up to an app16K buffer for storage, while the BIG-IP system makes a load balancing decision. The number of buffers for different sizes provides a good indication of the size of the requests that the BIG-IP system is currently handling.
frags
frags is the number of IP fragments that the BIG-IP system receives on all interfaces.
ping tmplt
Each monitor creates one ping template. ping tmplt is the number of monitor templates that exist on the BIG-IP system.
ping instance
A single ping instance exists for each monitor that is associated with a node/service.

rule tmplt
The rule tmplt count is the sum of the user defined monitors. It is associated with at least one node and is added to the number of default port monitors.

For example:

- bigpipe node 10.10.10.1 10.10.10.2 monitor use http and http_443

You do not create a rule tmplt for each monitor, but for each unique linking between a monitor rule and a node. If a monitor type was previously associated with another node in the same manner, a new rule tmplt is not required.


rule inst
A rule inst is the grouping of a structure and pointer that is required for each instance of a monitor rule. You would generate one or more rule inst from each rule tmplt.
ping rule id
A ping rule id structure is required for each rule template you create.
sip persist
sip persist is the number of entries in the SIP persistence table.
service list
This entry is obsolete and will be removed from the output.
mem pool total, mem pool used and mem percent used
mem pool total is the total number of system memory owned by the kernel. mem pool is the sum total of the memory used for all the BIG-IP mem entries. mem percent is the ratio of the used kernel memory to total kernel memory and is expressed as a percentage.
