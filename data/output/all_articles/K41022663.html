Topic

You should consider using this procedure under the following conditions:

  • You attempt to deploy a Virtual Clustered Multiprocessing (vCMP) guest.
  • You receive a fragmentation error message that appears similar to the following example:

    0107131f:3: Could not allocate vCMP guest (example_guest) because fragmented resources

Description

When many vCMP guests are deployed and disabled over time, spaces between cores and hyperthreads are created in the vCMP host (hypervisor) allocation table. While the vCMP host allocation table shows a sufficient number of cores available for the deployed vCMP guest, fragmentation errors prevent deployment for the following reasons:

CPU socket allocation errors

vCMP hosts with multiple socket CPUs must be able to allocate the number of Cores Per Guest, or Cores Per Slot for VIPRION systems, within a single CPU socket. In the following example, deploying a vCMP guest with four cores produces a fragmentation error because the cores are not allocated within a single socket:

Core allocation table 
Socket01
Core01234567
vCMP guestGuest_oneGuest_twoAvailableAvailableGuest_threeAvailableGuest_fourAvailable


Hyperthread allocation errors

vCMP hosts using hyperthreading must be able to allocate the number of Cores Per Guest, or Cores Per Slot for VIPRION systems, using contiguous hyperthreads. In the following example, deploying a vCMP guest with four cores fails because the hyperthreads on physical core 0 and 1 are not contiguous:

Core allocation table 
Physical Core0123
Hyperthread01234567
vCMP guestGuest_oneAvailableGuest_twoAvailableAvailableAvailableGuest_three


PDE (0.x) allocation errors

vCMP hosts assign internal interfaces (called PDEs or 0.x interfaces) to vCMP guests. On certain platforms, you can assign these so that deployment of larger guests is not possible because no blocks with a sufficient number of contiguous PDEs are available. This is confirmed to impact the i11800 platform in particular, and ID1020789 tracks this issue. There is no workaround at this time and further updates will be provided in Bug Tracker as they become available.

Resolving fragmentation errors

Resolving fragmentation errors involves defragmenting the vCMP host core allocation table, thereby increasing the number of cores per socket or contiguous hyperthreads. You can defragment the core allocation table by redeploying a particular vCMP guest. When a vCMP guest redeploys, the vCMP host core allocator chooses the lowest number of contiguous core IDs. For example, if Guest_two from the Hyperthread allocation errors example in the previous section redeploy, the vCMP guest moves from physical core 1 to core 0, leaving the appropriate number of contiguous hyperthreads to deploy a four-core vCMP guest.

Prior to disabling and redeploying a vCMP guest, you should first determine the current vCMP host CPU socket and core information, and then the vCMP guest core allocation table by performing the following procedures:   

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You have access to the vCMP host (hypervisor) TMOS shell (tmsh).

Procedures

  • Determining the vCMP host CPU socket and core information
  • Resolving hyperthread allocation errors
  • Resolving socket allocation errors

Determining the vCMP host CPU socket and core information

To determine the vCMP host CPU socket and core information, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the vCMP host tmsh by typing the following command:

    tmsh

  2. Determine the vCMP host CPU socket and core information by typing the following command:

    show sys hardware | grep -E 'cores|sockets'

    • Single socket CPU

      In the following command output, the vCMP host has 8 physical cores, 16 hyperthreaded cores and 1 socket. The system has 16 available core allocations: 0 - 15:

      Note: Some single socket CPUs display only cores and have no cpu sockets entry.

      cores         16  (physical:8)
      cpu sockets   1

    • Multi-socket CPU

      In the following command output, the vCMP host has 24 physical cores, 48 hyperthreaded cores and 2 sockets. The system has 24 available core allocations per CPU socket: 0 to 23 and 24 to 47, for a total of 48:

      cores         48  (physical:24)
      cpu sockets   2

  3. Continue to the one of the following next procedures depending upon your vCMP host CPU socket design.

Resolving hyperthread allocation errors

Once you determine the core allocation for all vCMP guests, you can decide which currently deployed vCMP guest to redeploy. To determine the vCMP guest hyperthread mapping, perform the following procedure:

Impact of procedure: Performing the following procedure will stop all traffic processing for the deployed guest. You should perform this procedure only during a planned maintenance window, which should take approximately 20 minutes.

  1. Log in to the vCMP host tmsh by typing the following command:

    tmsh
     
  2. To determine the current vCMP guest hyperthread allocation, type the following command:

    show vcmp guest all-properties | grep -E 'deployed|Cores|Name'

    The following example command output shows the vCMP host has allocated hyperthreads 0, 1, 2, 4, 5, 6, leaving hyperthreads 3 and 7 unallocated. An attempt to deploy a vCMP guest with two cores will fail due to noncontiguous hyperthreads: 

    Note: For VIPRION systems, a slot identifier precedes the core ID number: 1/ indicates slot 1, 2/ indicates slot 2.

    guest_two                           running   deployed

  3. To deploy a two-core vCMP guest, redeploy guest_five to create two contiguous hyperthreads: 6, 7.
     
  4. To redeploy a vCMP guest, you must first set the vCMP guest to the configured state using the following command syntax:

    modify vcmp guest <name> state configured

    For example, to set the vCMP guest named guest_five to the configured state, type the following command:

    modify vcmp guest guest_five state configured
     
  5. To redeploy the vCMP guest, use the following command syntax:

    modify vcmp guest <name> state deployed

    For example, to redeploy the vCMP guest named guest_five, type the following command:

    modify vcmp guest guest_five state deployed
     
  6. Verify the contiguous hyperthreads by typing the following command:

    show vcmp guest all-properties | grep -E 'deployed|Cores|Name'

    In the following example, guest_five is reallocated to core 3, leaving contiguous hyperthreads 6 and 7 available:

Resolving socket allocation errors

Once you determine the CPU socket and core allocation mapping for all vCMP guests, you can decide which vCMP guest to redeploy. To determine the CPU socket and core mapping, perform the following procedure:

Impact of procedure: Performing the following procedure will stop all traffic processing for the redeployed guest. You should perform this procedure only during a planned maintenance window, which should take approximately 20 minutes.

  1. Log in to the vCMP host tmsh by typing the following command:

    tmsh
     
  2. To determine the current vCMP guest core allocation, type the following command:
