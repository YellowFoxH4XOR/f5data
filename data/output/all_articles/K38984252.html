Description

Following messages appear in the logs:

[GossipResourceUpdateSender] Failed to send update to peer https://x.x.x.x:443. Will try again later.

Environment

Messages appear when:

  • REST Framework has HA configured
  • And one or more of the following:
    • Self-ip has changed after HA was configured in the HA Framework
    • Blades added or removed

Cause

Gossip is the service that sends messages for the REST Framework HA, when changes are made it may need to be rebuilt.

Recommended Actions

Perform the following steps to rebuild the HA:

Note: Performing the steps should not affect the HA Device Group status (Active/Standby Status), HA settings, etc that were configured in LTM. It's always recommended to perform these steps in a maintenance window.

Assume, bigip1 and bigip2 are the active and standby devices, management-ip-1 and management-ip-2 are the management IP addresses. The following commands should be run from a host with management access to the device pair.

  1. Delete the devices from the device group using the following command on bigip1
    # curl -sku <username>:<password> -X DELETE https://<management-ip-1>/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices
  2. Delete the devices from the device group using the following command on bigip2
    # curl -sku <username>:<password> -X DELETE https://<management-ip-2>/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices
  3. Restart the java daemon on both units by running the following command:
    # bigstart restart restjavad
  4. Create the group again on bigip1 using the following command:
    # curl -sku <username>:<password> -X POST -d '{"address":"<management-ip-2>","userName":"<userName>","password":"<password>"}' https://<management-ip-1>/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices
  5. Create the group again on bigip2 using the following command:
    # curl -sku <username>:<password> -X POST -d '{"address":"<management-ip-1>","userName":"<userName>","password":"<password>"}' https://<management-ip-2>/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices

Avoiding credential exposure on the command line (optional)

In the commands above, the password is exposed in two parts of the command, which may be a concern in environments that record executed commands (for example, shell history or change-management/order logs):
# curl -sku <username>:<password> -X POST -d '{"address":"<management-ip-2>","userName":"<userName>","password":"<password>"}' https://<management-ip-1>/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices

- the credential passed with the -u flag (<username>:<password>), and
- the credential contained in the JSON request body of the POST commands (steps 4 and 5).

You can keep the password out of the recorded command line as follows.

Part 1 — the -u flag credential (all steps)
Drop the password after the -u flag and supply only the username. curl will then prompt for the password interactively at runtime, so it is not echoed to the terminal and does not appear in the command that is recorded: 

#curl -sku <username>: -X DELETE https://<management-ip-1>/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices

Enter host password for user '<username>':

Part 2 — the credential in the JSON body (steps 4 and 5)

For the POST commands, the credential is inside the JSON request body and cannot be prompted for interactively. Instead, place the JSON in a file and reference it with -d @<filename>, so the body is not part of the recorded command line.
1. Create the file with restrictive permissions before adding the credential:
# touch cred.json
# chmod 600 cred.json

2. Edit cred.json (for example with vi) so it contains the JSON body. On bigip1:
{"address":"<management-ip-2>","userName":"<userName>","password":"<password>"}
3. Run the POST command referencing the file with -d @cred.json, and supply only the username with -u so the password is prompted:
# curl -sku <username> -X POST -d @cred.json https://<management-ip-1>/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices
4. Repeat on bigip2 with a file containing the peer's address:
{"address":"<management-ip-1>","userName":"<userName>","password":"<password>"}
# curl -sku <username> -X POST -d @cred.json https://<management-ip-2>/mgmt/shared/resolver/device-groups/tm-shared-all-big-ips/devices
5. Delete the file when finished:
# rm -f cred.json

With this approach the recorded command line contains only the filename (cred.json) and the username, not the password. Note that the password is still transmitted inside the request body to establish device trust; this exchange is protected in transit by the management HTTPS/TLS connection.
