Topic

This article applies to BIG-IP 9.x and 10.x. For information about other versions, refer to the following article:

  • K13898: Determining which monitor triggered a change in the availability of a node or pool member (11.x)
  • K14407: The BIG-IP system now displays which monitor triggered a change in the availability of a node or pool member

On the BIG-IP system, you can apply one or more health monitors to pools, pool members, and nodes. When you apply more than one health monitor to one of these objects, the Availability requirement option controls how the BIG-IP system determines the state of the object. For example, the following table shows some valid monitor configurations:

Number of health monitorsAvailability requirementDescription
OneN/AThe health monitor must receive a successful response for the object to be considered available.
TwoAllAll health monitors must receive a successful response for the object to be considered available.
ThreeAt least two health monitorsAt least two health monitors must receive a successful response for the object to be considered available.

The mcpd process handles the operation of health monitors; however, the bigd process performs the actual health checks. The mcpd process periodically requests the bigd process to spawn a monitor instance to verify the availability of each object. Depending on the number of health monitors you applied to an object, a monitor instance may carry out multiple health checks. Regardless of the number of health checks required, the bigd process returns only the final result (the availability of the object) to the mcpd process.

For example, if you applied two health monitors to a pool member, and the system required that they were both available in order to define the pool member in an up state, the bigd process will:

  • Spawn a monitor instance that performs the two health checks
  • Determine the state of the object, based on the result of the two health checks and the availability requirement
  • Return the state of the object to the mcpd process

Once the bigd process returns the state of an object to the mcpd process, the mcpd process logs an entry to the /var/log/ltm file if the system detected a change in the availability of the object.

This implementation generally works well; however, the system never informs the mcpd process regarding which particular health monitor has caused a change in the availability of an object. As a direct result of this implementation, the log entry that the system writes to the /var/log/ltm file does not contain this information either. When you apply multiple health monitors to an object, lacking the information about what health monitor caused a change in the object availability may complicate troubleshooting to find out why the BIG-IP system marked the object as down.

Consider the following example:

  • On a BIG-IP system, the my_http pool is configured as follows:

    pool my_http {
       monitor all http and my_special_http
       members {
          10.1.2.9:80 {}
          10.1.2.10:80 {}
       }
    }

  • The 10.1.2.9:80 pool member fails to pass the health check defined by the my_special_http monitor.
  • Due to the availability requirements, the BIG-IP system marks the pool member as down.
  • The BIG-IP system logs the following entry to the /var/log/ltm file:

    Note: The following log entry does not specify which of the two health monitors triggered a change in the availability of the 10.1.2.9:80 pool member.

    local/bigip1 notice mcpd[3184]: 01070638:5: Pool member 10.1.2.9:80 monitor status down.

F5 Product Development tracked RFE ID 227271 (formerly CR82787), for an enhancement to allow the BIG-IP system to log which particular health monitor caused a change in the availability of an object. This functionality has been added in BIG-IP 11.4.0. For more information, refer to K14407: The BIG-IP system now displays which monitor triggered a change in the availability of a node or pool member.

Recommended Action

F5 recommends two actions for identifying which health monitor caused a change in the availability of an object. One consists of using the bigpipe command, and the other involves enabling a db key that triggers the bigd process to log which health monitor caused a change in the availability of an object. Both options are described in the following sections.

Using the bigpipe command to view which health monitor caused a change in the availability of an object

You may be able to determine which health monitor has caused a change in the availability of an object by executing the bigpipe monitor all instance command from the command line.

For example, the following command output displays a monitor instance performing three health checks, and reveals that the 10.1.2.9:80 pool member was marked down because it failed to pass the health check defined by the my_special_http monitor:

MONITOR  gateway_icmp and http and my_special_http   POOL my_http
+-> POOL MEMBER my_http/10.1.2.9:http   inactive,down
    +-> gateway_icmp
        |        10.1.2.9   up enable
    +-> http
        |        10.1.2.9:80   up enable
    +-> my_special_http
        |        10.1.2.9:80   down enable

Additionally, individual health check monitor availability may be viewed by executing the bigpipe monitor <monitor_name> instance command from the command line. 

For example:

bigpipe monitor my_special_http instance

MONITOR  my_special_http   - Instance:
my_special_http

|        10.1.2.9:80   up enable

Configuring the BIG-IP system to log which health monitor caused a change in the availability of an object

Additionally, you may be able to determine which health monitor has caused a change in the availability of an object by enabling the bigd.lognodestatuschange db key, which triggers the bigd process to log which particular health monitor has caused a change in the availability of an object. Refer to the following instructions for enabling the key, and also for reviewing the /var/log/ltm file.

Impact of procedure: Enabling the bigd.lognodestatuschange db key enables monitor-status logging globally. Depending on the configuration, this has the potential for more verbose logging.

  1. Log in to the BIG-IP command line.

    Verify the status of the bigd.lognodestatuschange db key by entering the following command:

    bigpipe db bigd.lognodestatuschange
  2. If the status is disabled, enable the bigd.lognodestatuschange db key by entering the following command:

    bigpipe db bigd.lognodestatuschange enable

    Note: To disable the bigd.lognodestatuschange db key, enter the following command:

    bigpipe db bigd.lognodestatuschange disable
  3. Monitor or review the /var/log/ltm file by entering one the following example commands:

    Monitor the log file:

    tail -f /var/log/ltm | egrep -i "detected.*mon|monitor.*status"

    Review the log file:

    cat /var/log/ltm | egrep -i "detected.*mon|monitor.*status" | more

    Note: Depending on the number of log messages, you may need to scroll through the output to locate the specific message.
  4. Press Ctrl+C to break out of either command.

In the following example, the pool member 10.1.2.9:80 is marked down because it fails to pass the my_special_http monitor test. The pool member then passes the my_special_http monitor test and is subsequently marked up. In the first example, there is no indication of which monitor marks the node down or up. However, after enabling the bigd.lognodestatuschange db key, the bigd process logs which monitor marks the node down and subsequently back up again.

Example output taken before enabling the db key:

local/bigip1 mcpd[1777]: 01070638:5: Pool member 10.1.2.9:80 monitor status down.
local/bigip1 mcpd[1777]: 01070727:5: Pool member 10.1.2.9:80 monitor status up.

Example output taken after enabling the key:

local/bigip1 bigd[1933]: 01060001:5: Service detected DOWN for ::ffff:10.1.2.9:80 monitor my_special_http.
local/bigip1 mcpd[1777]: 01070638:5: Pool member 10.1.2.9:80 monitor status down.
local/bigip1 bigd[1933]: 01060001:5: Service detected UP for ::ffff:10.1.2.9:80 monitor my_special_http.
local/bigip1 mcpd[1777]: 01070727:5: Pool member 10.1.2.9:80 monitor status up.

Note: Enabling the bigd.lognodestatuschange db key affects a behavior change in BIG-IP 10.x regarding the throttling of BIG-IP LTM log messages. When the key is enabled, log messages may be throttled, which is the opposite of the default behavior.
