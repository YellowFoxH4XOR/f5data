Description

There are 2 different ways for injecting the sidecar into the application pod. When you add a istio-injection=enabled label on a namespace, any pod created in that namespace get a sidecar through the injection webhook. 

kubectl label ns default istio-injection=enabled –overwrite

To manually add the sidecar, you can simply run:

istioctl kube-inject -f samples/sleep/sleep.yaml | kubectl apply -f -

This will use the config and values from the istio-sidecar-injector configmap that is in the istio-system namespace. By default, there are 6 volumes that gets created in pod and is mounted on to the pod.

  1. Istio-pod-info

    This volume is projected DownwardAPIVolume which is used to expose the information about itself to running container in the pod. In the following example, it exposes labels, annotations, limits and requests for the CPU resource. For more information, please check this.

    - downwardAPI:
          defaultMode: 420
          items:
          - fieldRef:
              apiVersion: v1
              fieldPath: metadata.labels
            path: labels
          - fieldRef:
              apiVersion: v1
              fieldPath: metadata.annotations
            path: annotations
          - path: cpu-limit
            resourceFieldRef:
              containerName: istio-proxy
              divisor: 1m
              resource: limits.cpu
          - path: cpu-request
            resourceFieldRef:
              containerName: istio-proxy
              divisor: 1m
              resource: requests.cpu
        name: istio-podinfo

  2. Istio-token

    This is a projected serviceAccountToken volume which has the token needed by the containers to access the istio CA. Path is where the token resides and has an expiration time. For more information please read this.

      - name: istio-token
        projected:
          defaultMode: 420
          sources:
          - serviceAccountToken:
              audience: istio-ca
              expirationSeconds: 43200
              path: istio-token

  3. istiod-ca-cert

    Data stored in configmap can be reference in volume of type configmap. Here, it is referencing “istio-ca-root-cert" which gets created every time a new namespace is created. It contains the root certificate in PEM format. For more information, read this.

      - configMap:
          defaultMode: 420
          name: istio-ca-root-cert

  4. <pod-name>-token

    This is a service account token secret which has token and the CA cert which is base64 encoded. The token is used to identify the service account and to access API server.

    - name: httpbin-token-qx2n2
        secret:
          defaultMode: 420
          secretName: httpbin-token-qx2n2

  5. Istio-Envoy

    This is an empty directory volume which is of type “memory”. This volume is used for storing certs in memory. These certs are created via exchange between istio-agent and envoy in various discovery service modes. Please read this for more information.

    volumes:
      - emptyDir:
          medium: Memory
          name: istio-envoy

  6. Istio-data

    This volume is used for all other activities beside above mentioned. One of the use cases is when you load a custom bootstrap file via configmap to your application deployment, it uses istio-data directory for that. Please read this for more details.

      - emptyDir: {}
        name: istio-data

Environment

  • Aspen Mesh:  1.6.x, 1.9.x

Cause

N/A

Recommended Actions

None

Additional Information

Here is the Volumes mounts for the all the above volumes:

volumeMounts:
    - mountPath: /var/run/secrets/istio
      name: istiod-ca-cert
    - mountPath: /var/lib/istio/data
      name: istio-data
    - mountPath: /etc/istio/proxy
      name: istio-envoy
    - mountPath: /var/run/secrets/tokens
      name: istio-token
    - mountPath: /etc/istio/pod
      name: istio-podinfo
    - mountPath: /var/run/secrets/kubernetes.io/serviceaccount
      name: <pod>token-qx2n2
      readOnly: true
