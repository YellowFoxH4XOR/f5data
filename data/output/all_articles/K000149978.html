Description

A DNSSEC-related issue was identified where the BIG-IP local BIND failed to respond to TCP-based DNS queries when there were two active Zone Signing Keys (ZSKs) for a zone. This failure occurred due to the local BIND process being unable to handle an increased number of concurrent TCP connections, resulting in connection failed.

The issue happens every time after the ZSK rollover and there are two active ZSKs for the zone. Logs may show errors as below in /var/log/ltm when the BIND unable to respond the query over TCP and the flow was closed by remote client. 

Jan  8 06:08:14 <hostname> warning tmm1[12509]: 01010264:4: DNSSEC: flow shutdown (11) for zone <zone name> during pkt completion

Environment

  • BIG-IP DNS
  • BIND
  • DNSSEC
  • ZSK rollover

Cause

The issue arises when the response size for a DNS query exceeds the default UDP payload size (512 bytes without EDNS or client-defined limits). This triggers the BIG-IP system to set the Truncated (TC) flag in its UDP response, prompting clients to retry their queries over TCP. When there are two active ZSKs, the response size increases further due to additional RRSIG records, leading to more frequent retries over TCP.

The local BIND process on BIG-IP has a default limit of 150 concurrent TCP connections (tcp-clients). When this limit is exceeded, subsequent TCP queries fail, causing connection resets and unresponsive behavior for affected zones.

The failure only happens on the queries responded by local BIND, the queries responded by GSLB, DNS express or DNS cache wouldn't be impact, as there is no limit for TCP connections on TMM.

Recommended Actions

Increase tcp-clients Limit in BIND:

  • Modify the tcp-clients value in BIND's configuration to accommodate a higher number of concurrent TCP connections.
  • Recommended initial value: start with 1024
    • Monitoring: Use rndc status after applying changes to monitor the current status.
    • Look for lines like tcp clients: X/Y, where the X is the current TCP connection over BIND, and the Y is your configured limit.
    • If necessary, increase further based on observed traffic patterns, the X value.

Long-Term Solutions (Since a high load BIND may cause the performance issue):

  1. Implement DNS Express:
    • Configure DNS Express on BIG-IP to pre-store zone data in TMM memory instead of relying solely on BIND for responses. This improves performance and reduces dependency on BIND's limitations.
  1. Implement DNS Cache (transparent mode):
    • Configure transparent mode caching so that frequently queried records are cached by TMM, reducing the load on BIND.

Additional Information

The maximum size over UPD for a DNS response is controlled by one of the EDNS options, UDP payload size. EDNS (Extension Mechanisms for DNS) is a specification that extends the original DNS protocol to overcome its limitations, particularly the size constraints of DNS messages. Traditional DNS over UDP has a maximum message size of 512 bytes. EDNS allows clients and servers to negotiate larger UDP packet sizes (commonly up to 4096 bytes), enabling the transmission of larger DNS responses without requiring TCP.
