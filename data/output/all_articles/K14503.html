Known Issue

The BIG-IP GTM system may erroneously change the unit_id of a generic server to two after loading a manually edited wideip.conf file. This issue occurs when all of the following conditions are met:

  • A user manually edits the name parameter of a generic server configuration stanza in the wideip.conf file
  • The gtmparse -l command is run on the BIG-IP GTM system

The erroneous change on the unit_id may not be visible in the wideip.conf file until a different configuration change is performed on the BIG-IP GTM system. Additionally, the erroneous configuration may be propagated to the remaining members in the same BIG-IP GTM synchronization group. The unit_id of value two is not a valid configuration for a generic server object and results in BIG-IP GTM configuration load failures.

For example:

  • The original wideip.conf file on GTM1 contains two generic servers located in two datacenters. A snippet of the configuration appears similar to the following example:

    // *** Data Center Definitions (2) ***

    datacenter { // 1 server(s)
    name "DC1"
    server "server1"
    }
    datacenter { // 1 server(s)
    name "DC2"
    server "server2"
    }

    // *** Server Definitions (2) ***

    server { // datacenter=DC1, #VS=0
    name "server1"
    type generic
    box {
    address 10.10.22.211
    unit_id 1
    }
    }
    server { // datacenter=DC2, #VS=0
    name "server2"
    type generic
    box {
    address 10.10.22.212
    unit_id 1
    }
    }
  • The wideip.conf file is manually edited to swap the names of the two generic servers, as well as their corresponding datacenters:

    // *** Data Center Definitions (2) ***

    datacenter { // 1 server(s)
    name "DC1"
    server "server2"
    }
    datacenter { // 1 server(s)
    name "DC2"
    server "server1"
    }

    // *** Server Definitions (2) ***

    server { // datacenter=DC1, #VS=0
    name "server2"
    type generic
    box {
    address 10.10.22.211
    unit_id 1
    }
    }
    server { // datacenter=DC2, #VS=0
    name "server1"
    type generic
    box {
    address 10.10.22.212
    unit_id 1
    }
    }
  • The wideip.conf file is loaded into the GTM1 memory by running the gtmparse -l command. The GTM1 system erroneously changes the unit_id of server2 to number two, but no configuration is written back to the wideip.conf file.
  • At a later time, a new wide IP is added to the GTM1 and this change is written into the wideip.conf file together with the erroneous configuration of server2.
  • Due to the update to the wideip.conf file, the BIG-IP GTM synchronization group synchronizes a copy of the wideip.conf file to the peer GTM2.
  • GTM2 attempts to load the wideip.conf file it receives from the BIG-IP GTM synchronization group but fails and reports an error message.
  • An attempt to reload the wideip.conf file on GTM1 fails and GTM1 reports an error similar to GTM2.

Note: This issue does not affect BIG-IP GTM 11.x, as it does not use the unit_id parameter.

Impact

The configuration load fails on the BIG-IP GTM system and its synchronization group peers. Additionally, the members of the BIG-IP GTM synchronization group may attempt to synchronize the configuration repeatedly due to previous failed attempts. As a result, the traffic volume may increase on the BIG-IP GTM synchronization group network.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • BIG-IP iHealth lists Heuristic H424107 on the Diagnostics > Identified > Medium screen.
  • The BIG-IP GTM synchronization group peer fails to load the configuration and reports an error message to the /var/log/gtm file. For example:

    ERROR, recvMCPreply: Got bad result: 0107018f:3: Server server2 has no IP addresses in unit 1
  • The wideip.conf file contains generic server configuration with unit_id two. For example:

    server { // datacenter=DC1, #VS=0
    name "server2"
    type generic
    box {
    address 10.10.22.211
    unit_id 2
    }
    }
  • When a manual configuration load is performed by running the gtmparse -l command, the BIG-IP GTM system fails to load the configuration and reports error messages. For example:

    gtmparse: Initializing ...
    /usr/share/monitors/gtm_base_monitors.conf: SUCCESS
    /usr/local/gtm/include/base_region.ISP: SUCCESS
    /config/gtm/wideip.conf: SUCCESS
    gtmparse: SUCCESS
    ERROR, recvMCPreply: Got bad result: 0107018f:3: Server server2 has no IP addresses in unit 1

Workaround

To prevent this issue, F5 recommends that you avoid manually editing the wideip.conf file, and instead use the Configuration utility or Traffic Management Shell (tmsh) utility to create a new generic server with the desired name and settings and delete the previous generic server. For information about creating a new generic server, refer to the Defining the Physical Network chapter of the Configuration Guide for BIG-IP Global Traffic Manager.

Note: For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.

To recover from this issue, you can replace unit_id 2 with unit_id 1 for the affected generic server configuration in the wideip.conf file. To do so, perform the following procedure:

Impact of workaround: Depending on the size of the wideip.conf file, the BIG-IP GTM system may be momentarily interrupted during the configuration reload.

  1. Log in to the command line.
  2. Backup a copy of the wideip.conf file by entering the following command:

    cp -p /config/gtm/wideip.conf /var/tmp/wideip.conf.sol14503
  3. Edit the wideip.conf file using a text editor of your choice.
  4. Locate the unit_id line in the affected generic server configuration stanza:

    server { // datacenter=DC1, #VS=0
    name "server2"
    type generic
    box {
    address 10.10.22.211
    unit_id 2
    }
    }
  5. Replace the unit_id 2 with unit_id 1. After the edit, the generic server configuration stanza should appear similar to the following example:

    server { // datacenter=DC1, #VS=0
    name "server2"
    type generic
    box {
    address 10.10.22.211
    unit_id 1
    }
    }
  6. Repeat steps 4 and 5 for the remaining affected generic servers if applicable.
  7. Save the changes and exit the text editor.
  8. Reload the configuration by typing the following command:

    gtmparse -l
  9. To propagate the changes to the remaining affected synchronization group peers, make a change using the Configuration utility. For example, you can add a dummy datacenter. For information about adding BIG-IP GTM objects, refer to the Defining the Physical Network chapter and the Defining the Logical Network chapter of the Configuration Guide for BIG-IP Global Traffic Manager.

Note: For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.
