Description

When OIDC is configured with NGINX Ingress Controller and NGINX App Protect WAF is enabled at the Virtual Server level, OIDC internal subrequests may intermittently fail. Symptoms include HTTP 444 responses, TCP resets in NGINX access logs, and unexpected termination of the associated client request.

The issue occurs when OIDC-generated internal locations inherit WAF directives from the server context.

Environment

  • NGINX Ingress Controller.
  • OIDC integration using NJS-generated internal locations.
  • NGINX App Protect WAF enabled through a policy attached to a Virtual Server.
  • WAF directives applied at server scope, such as app_protect_enable.
  • Internal subrequest-based processing.
  • Similar behavior may affect other features that use internal subrequests, including:
    • externalAuth or auth_request.
    • The NGINX mirror module.
    • External authentication configured through an Ingress policy attachment annotation.

Cause

Subrequest-based modules are not supported when NGINX App Protect WAF is enabled at the same scope as the subrequest locations.

When WAF directives are inherited by OIDC internal locations, WAF processing can occur during the internal subrequests. This may cause race conditions in the WAF module, terminating the main request and producing HTTP 444 responses or TCP resets.

Recommended Actions

  1. Avoid applying the WAF policy at the Virtual Server server scope through spec.policies when OIDC or another subrequest-based feature is used.
  2. Apply the WAF policy through spec.routes[].policies instead. This limits WAF processing to client-facing application locations and prevents the policy from being inherited by unrelated internal OIDC locations.
  3. If server-level WAF configuration is required, ensure that internal locations used for OIDC or other subrequests have WAF disabled. Generated internal locations must not inherit app_protect_enable from the applicable parent context.
  4. Upgrade to a NGINX Ingress Controller release that includes the fix for this behavior.
  5. After configuration or software changes, test OIDC authentication flows with WAF enabled and monitor NGINX access logs for:
    • HTTP 444 responses.
    • TCP resets.
    • Intermittent failures during authentication or callback processing.

Additional Information

  • The behavior may be intermittent and may not produce an obvious error-log message.
  • WAF protection for client-facing application locations is separate from WAF processing in internal locations used for subrequests.
  • The same limitation can apply to other subrequest-based NGINX features when their internal locations inherit WAF directives.
