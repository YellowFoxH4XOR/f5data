Issue

You should consider using this procedure under the following conditions:

  • You have configured Kerberos end-user logon authentication in your BIG-IP APM access policy.
  • You are using Windows Active Directory (AD) as your key distribution center (KDC).
  • You are accessing a service using a browser.
  • You want to troubleshoot Kerberos end-user logon issues.

Symptoms

As a result of Kerberos authentication issues, you may encounter the following symptom:

  • Users are unable to access configured internal resources after failing Kerberos authentication.

Recommended Actions

When troubleshooting, you need to have an understanding of the following sequence of events in the Kerberos end-user logon authentication process.

  1. The client connects to the BIG-IP virtual server and receives an HTTP 401 or HTTP 407 authentication response from the BIG-IP APM system.
  2. In an AS_REQ/AS_REP request, the client obtains the Kerberos ticket-granting ticket (TGT) from the KDC.
  3. In a TGS_REQ/TGS_REP request, the client presents the TGT to the KDC and obtains the Kerberos service ticket to the appropriate service in response.
  4. The client responds to the earlier response from the BIG-IP APM in step 1 by presenting the Kerberos service ticket in an AP_REQ request to the BIG-IP APM system.
  5. The BIG-IP APM system authenticates the client service ticket using the keytab file.
  6. When Kerberos authentication is successful, the BIG-IP APM system sends an AP_REP reply and the client is able to access the service.

Note: Connectivity between the BIG-IP APM system and the KDC is not required in Kerberos end-user logon authentication.

You should first identify the step at which authentication is failing before performing further troubleshooting. For example, at step 4, if the client is not sending the Kerberos service ticket in its AP-REQ request to the BIG-IP APM system, you should verify the configuration and exchanges between the client and the KDC.

Important: F5 supports BIG-IP APM system software. F5 does not support third-party software, such as the client operating system or KDC.

Procedures

When you experience Kerberos authentication failure issues, you can use the following troubleshooting steps to determine the root cause:

Note: When troubleshooting, as you make changes to the configuration and test each time, always first clear the cache on the client system with the klist purge command.

  • Enabling BIG-IP APM and Kerberos debug logging
  • Verifying that the client system is sending the Kerberos service ticket to the BIG-IP APM system
  • Verifying clock skew issues
  • Verifying DNS configurations
  • Verifying the client browser is configured for Kerberos authentication
  • Verifying the Kerberos tickets on the client device with klist
  • Verifying the service account name configuration on the KDC and the BIG-IP APM system
  • Verifying the Kerberos encryption configuration
  • Verifying the KVNO of the keytab file on BIG-IP APM system matches the KVNO of the service account on AD
  • Deleting and re-creating the service account at AD
  • Taking a packet capture on the client and the Kerberos request-reply protocol

Enabling BIG-IP APM and Kerberos debug logging

To enable BIG-IP APM debug logging, refer to K11124:Configuring the BIG-IP APM system logging level.

To enable Kerberos debug logging, perform the following procedure:

Impact of procedure: Enabling Kerberos debug logging may cause excessive logging in a system with a large number of user logins. You should only enable debug logging when troubleshooting. You should disable debug logging after you've finished troubleshooting.

  1. Log in to the TMOS Shell (tmsh) by typing the following command:

    tmsh

  2. To enable Kerberos debug logging, type the following command:

    tmsh modify sys db log.rba.level value debug

After you enable debug logging, examine the /var/log/apm logs.

Procedure back out: After you finish troubleshooting, disable Kerberos debug logging by typing the following command: tmsh modify sys db log.rba.level value Notice

Verifying that the client system is sending the Kerberos service ticket to the BIG-IP APM system

To isolate the root cause, you should first verify whether the client system is sending the Kerberos service ticket to the BIG-IP APM system. You can verify this on by setting BIG-IP APM logging to Informational or Debug and examining the session.logon.last.authparam value.

Note: Enabling debug logging on a busy system may increase CPU and other resource usage. You should only enable debug logging while actively troubleshooting and disable it after you have collected the information you need.

The value of session.logon.last.authparam should be set to a value beginning with YII. You should observe an output similar to the following in the /var/log/apm file:

info apmd[18913]: 01490007:6: /Common/example:Common:af26e8b5: Session variable 'session.logon.last.authparam' set to 'YII[...]

If the value of the session.log.last.authparam variable on BIG-IP APM system is set to a value similar to 'TlRM[...]', Kerberos authentication has failed and fallen back to using NT LAN Manager (NTLM).

Additionally, if the session.logon.last.authparam is not set, you also need to review the configuration and exchange between the client system and KDC. Alternatively, you can use a browser debugging tool to observe the client system's response to the BIG-IP APM HTTP 401/407 response. In the response from the client system to the BIG-IP APM system, the same value should be included in the Authorization header. For example, you may observe that the Authorization header has a value similar to the following example:

Authorization Negotiate YII[...]

Verifying clock skew issues

The time among the client system, KDC, and the BIG-IP APM system must be synced. Refer to your client documentation to sync your client system to the KDC. To verify that the BIG-IP system's time is synced, you can use the ntpstat command. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  • Type the following command:

    ntpstat

    You should observe an output similar to the following:

    # ntpstat
    synchronised to NTP server (ntpserver.example.com) at stratum 2
       time correct to within 126 ms
       polling server every 1024 s

    Note: Manually verifying that the times among the systems are within 5 minutes of one another is not sufficient. The systems' times must be synchronized to an NTP server as shown in the previous output.

Procedure back out: None

Verifying DNS configurations

Verify that the DNS configuration for the URL entered at the browser is configured so that the client browser is able to connect to the BIG-IP virtual server To do so, perform the following procedures:

Verifying the client browser is configured for Kerberos authentication

When the user enters the URL on a browser to access the service, the browser contacts the KDC to obtain the Kerberos tickets. For this to happen, the browsers must be configured to detect the specific URL to begin the authentication process with the KDC. To do that, refer to the Configuring the client browser for Kerberos procedure in Configuring Kerberos end-user logon authentication for multiple applications by merging keytab files.

Verifying the kerberos tickets on the client device using the klist command

To display the Kerberos tickets on the client device, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

This example displays a TGT ticket and a service ticket to app1.example.com for user1 at the realm EXAMPLE.COM. The highest-strength encryption type configured for the HTTP/app1.example.com AD service account is Kerberos AES 128 bit encryption.

Note: For security purposes, F5 recommends enabling AES 256 bit encryption by selecting the This account supports Kerberos AES 256 bit encryption check box on the Account tab in the user Properties after the account is created.

  1. Log in to the client device.
  2. Type the following command to delete existing tickets:

    klist purge

  3. Reproduce the issue.
  4. Type the following command to display the Kerberos tickets:

    klist

  5. You should observe at least two tickets, a TGT ticket and a service ticket to access the specific URL requested. For example:

    Cached Tickets: (2)

    #0>     Client: user1 @ EXAMPLE.COM
            Server: krbtgt/EXAMPLE.COM @ EXAMPLE.COM
            KerbTicket Encryption Type: AES-256-CTS-HMAC-SHA1-96
            Ticket Flags 0x40e00000 -> forwardable renewable initial pre_authent
            Start Time: 1/8/2019 14:41:59 (local)
            End Time:   1/9/2019 0:41:59 (local)
            Renew Time: 1/15/2019 14:41:59 (local)
            Session Key Type: AES-256-CTS-HMAC-SHA1-96

    #1>     Client: user1 @ EXAMPLE.COM
            Server: HTTP/app1.example.com @ EXAMPLE.COM
            KerbTicket Encryption Type: AES-128-CTS-HMAC-SHA1-96
            Ticket Flags 0x40a00000 -> forwardable renewable pre_authent
            Start Time: 1/8/2019 14:41:59 (local)
            End Time:   1/9/2019 0:41:59 (local)
            Renew Time: 1/15/2019 14:41:59 (local)
            Session Key Type: AES-128-CTS-HMAC-SHA1-96

Procedure back out: None

Verifying the service account name configuration on the KDC and the BIG-IP APM system

The AD service account configuration is essential and misconfiguration can lead to issues. Perform the following checks:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Verify the configuration of the Kerberos authentication object on the BIG-IP APM from the Configuration utility by navigating to Access > Authentication > Kerberos.

    Note: For BIG-IP 12.x and earlier, navigate to Access Policy > AAA Servers > Kerberos

    Verify that the Auth Realm and the Service Name are the Kerberos service. For example, HTTP. The principal in the keytab file should display the userPrincipalName of the AD service account. For example:

    HTTP/app1.example.com@EXAMPLE.COM

    Note: >app1.example.com is the HTTP URL that the user is attempting to access from the browser.

  2. Verify the service account name on Active directory. To display the configuration of the service account, you can perform the steps described in the Verifying the service account name configuration on the AD/KDC procedure in K01716018: Configuring Kerberos end-user logon authentication for multiple applications by merging keytab files .

    Note: If your BIG-IP APM system does not have connectivity to AD, you can also view the same configuration directly from the domain controller.

  3. On the domain controller, you can also use the setspn command to verify the service principal name (SPN) value of your HTTP service account.

    To check for duplicate SPNs, type the following command:

    setspn -X

    To list the SPNs associated to your HTTP service account, use the following command syntax:

    setspn -L <sAMAccountName>

    For example:

    setspn -L samaccountname1

  4. If your SPN is not listed in the output, you can add it by using the following command syntax:

    setspn -A <SPN> <sAMAccountName>

    For example:

    setspn -A HTTP/app1.example.com samaccountname1

Procedure back out:

  • To delete an SPN from your HTTP service account, use the following command syntax:

    setspn -D <SPN> <sAMAccountName>

    For example:

    setspn -D HTTP/app1.example.com samaccountname1

Verifying the Kerberos encryption configuration

The encrypted type in the keytab file must support the encryption used to encrypt the Kerberos service ticket on the client system.

  • To view the supported encryption types in the keytab file using the BIG-IP Configuration utility, refer to Verifying the service account name configuration on the KDC and the BIG-IP APM system procedure in this article.
  • To display the encryption used to encrypt the Kerberos service ticket, use the klist command described in the Verifying the Kerberos tickets on the client device with klist procedure in this article.

For more information on configuring Kerberos encryption on Windows, refer to Windows Configurations for Kerberos Supported Encryption Type.

Note: This link take you to resources outside of AskF5, and it is possible that the information may be removed without our knowledge.

F5 recommends using the AES 256 bit encryption type. To configure this, you need to enable the This account supports the Kerberos AES 256 bit encryption option on the Account tab in the AD Properties and also when generating the keytab file with the ktpass command.

Verifying the KVNO of the keytab file on the BIG-IP APM system matches the KVNO of the service account on AD

Password changes or other account activities can update the KVNO of the AD service account and cause it to become out-of-sync with the keytab file on the BIG-IP APM system. In such cases, a new keytab file has to be generated and updated on the BIG-IP APM system. You can verify the KVNO of the keytab file in the Kerberos Authentication configuration on the BIG-IP Configuration utility. To verify the KVNO of the service account on AD, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to Advanced shell (bash).
  2. To query AD for the KVNO of the AD service account, use the following command syntax:

    ldapsearch -xLLL -H ldap://<AD server IP address>:<ldap port number> -b '<searchbase>' -D '<username>' -w '<password>' '(sAMAccountName=<sAMAccountName>)' msDS-KeyVersionNumber

    For example:

    ldapsearch -xLLL -H ldap://192.0.2.2:389 -b 'dc=example,dc=com' -D 'user1' -w 'pass' '(sAMAccountName=samaccountname1)' msDS-KeyVersionNumber

    Note: You must include the single quotation marks around the password parameter.

    In this example, the service account name is app1 with sAMAccountName samaccountname1 and is using the read privileges of user1 to perform an LDAP search (ldapsearch). You should observe output similar to the following:

    dn: CN=app1,CN=Users,DC=example,DC=com
    msDS-KeyVersionNumber: 3

    In the previous output example, the KVNO of the service account named app1 is 3. Verify the keytab file has the same KVNO.

    If your BIG-IP APM does not have connectivity to AD, you can also verify the KVNO by using the following command syntax on AD:

    ldifde -d <RootDN>  -f <output filename> -p subtree -l *,msDS-KeyVersionNumber

    For example:

    ldifde -d CN=app1,CN=Users,DC=example,DC=com  -f c:\output.txt -p subtree -l *,msDS-KeyVersionNumber

    View the KVNO of the service account from the example output file c:\output.txt. Verify the keytab file has the same KVNO.

Procedure back out: None

Deleting and re-creating the service account at AD

If the issue persists after troubleshooting, it may be useful to delete and re-create the AD service account. After creating the AD service account, you must create a new keytab file and update it on the BIG-IP APM system. To do so, refer to the  Creating a new keytab file with the ktpass command procedure in K01716018: Configuring Kerberos end-user logon authentication for multiple applications by merging keytab files.

Taking a packet capture on the client and the Kerberos request-reply protocol

Finally, you can perform a packet capture on the client. You may filter your TCP capture for ports 443 for HTTPS, 88 for Kerberos and 53 for DNS. To determine the cause of the issue from your packet capture, perform the following checks:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  • The Kerberos protocol defines a series of requests and responses as described at the beginning of this article. Determine at which point of the Kerberos protocol that the request failed.
  • Examine the capture for useful error messages.
  • Verify the Kerberos configuration names from the capture.
