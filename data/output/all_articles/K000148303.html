Description

Clients getting connection resets when sending API calls through the BIG-IP, the virtual server uses an iRule to direct the traffic on the server side based on the HTTP Host value on the header, but when accessing the servers directly the connection is successful.

 

Environment

  • LTM
  • iRule
  • HTTP Headers
  • TCP Reset with reason "No server selected"

 

Cause

The client is sending a non matching 'Host' value on the HTTP header according to the iRule list of eligible hosts to direct the connection, the iRule will not take any action to direct the request to a specific pool since none of the conditions match the "Host" header causing the BIG-IP to send TCP reset to the client with the reason "No server selected".

For example this is the configured iRule assigned to the virtual server to direct incoming HTTP requests to different server pools based on the value of the HTTP "Host" header:

when HTTP_REQUEST {
  if { [HTTP::host] eq "server-1.com" } {
           pool Pool-1
         } elseif { [HTTP::host] eq "server-2.com" } {
           pool Pool-2
         } elseif { [HTTP::host] eq "server-3.com" } {
           pool Pool-3
         } 
}

 

When analysing the packet capture you can see that the BIG-IP is sending TCP resets to the client with the reason "No server selected":

tshark -r packet-capture.pcap 'f5ethtrailer.rstcausetxt == "No server selected"'
11376  50.931392 0.000000 227 10.10.10.10 → 10.10.10.100 40 443 52798 TCP OUT s1/tmm2 : 443 → 52798 [RST, ACK] Seq=4218 Ack=9625 Win=0 Len=0 [F5RST: No server selected]

 

When analysing the http headers coming from the client you see that it is including the host 'server-5.com' which is not included on the irule:

host: server-5.com
user-agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/130.0.0.0 Safari/537.36
sec-ch-ua-platform: "Windows"
cache-control: no-store, no-cache, must-revalidate
pragma: no-cache

......

 

Recommended Actions

  1. Ask the client to sent the correct http host header that matches the list of hosts defined in the iRule, so that the BIG-IP can have an eligible host to send the connection to the server.
  2. Include conditions to the irule to explicitly handle unmatched hosts, you might want to add an else clause at the end of the iRule, this else clause ensures that unmatched hosts are explicitly handled, either by rejecting the request, logging the event, or forwarding it to a default pool (uncomment the actions you want to use on the iRule): 
    when HTTP_REQUEST {
  if { [HTTP::host] eq "server-1.com" } {
           pool Pool-1
         } elseif { [HTTP::host] eq "server-2.com" } {
           pool Pool-2
         } elseif { [HTTP::host] eq "server-3.com" } {
           pool Pool-3
         } else {
            # Default action for unmatched hosts
            reject
            # Alternatively, log the event or send to a default pool
            # log local0. "Unmatched host: [HTTP::host]"
            # pool default_pool
        }
}

Additional Information

If the HTTP traffic is using TLS encryption (HTTPS) you will need to decrypt the packet capture using the SSL session secrets in order to analyse the HTTP headers, you can follow this article instructions K12783074: Decrypting SSL traffic using the SSL::sessionsecret iRules command (12.x and later)
