Known Issue

A memory leak may occur when capturing traffic with an Analytics profile.

This issue occurs when all of the following conditions are met:

  • An analytics profile and a pool containing at least two pool members are both associated with the same virtual server.
  • The analytics profile has the following configuration options:
    • The Traffic Capturing Logging Type setting has External enabled.
    • Capture Requests is set to All.
    • The Capture Filter is configured in such a way that some portion of traffic will not match the filter.

      The following are examples of filters that would meet this condition:
      • A Response Status Code filter configured as Only: 404, applied to a virtual that receives 200 OK response codes
      • A URL filter configured as Starts with: www.mydomain.com, applied to a virtual server that also receives requests for www2.mydomain.com
    • The Capture Filter is set to Only Selected Nodes.
    • The list of Selected Nodes includes a number of nodes between 1 and n - 1, where n is the total number of nodes in the Available Nodes list.

      For example, in the case of a list of three Available Nodes, if the Selected Nodes list contains any one node, or any combination of two nodes, the Capture Filter would be affected.

      If the Selected Nodes list contains all three available nodes, the Capture filter would not be affected.

Impact

A memory leak may eventually cause all analytics reporting to stop.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • Messages that appear similar to the following example may be written to the /var/log/ltm file:

    warning md[5510]: 01540004:4: AVR Alert, MD exceeded 80.7% of provisioned memory allocation!! Entering Collect Essential mode. Please raise AVR provisioning definitions

    warning md[5510]: 01540004:4: AVR Alert, MD exceeded 90.7% of provisioned memory allocation!! Entering Collect None mode. Please raise AVR provisioning definitions

  • Messages that appear similar to the following example may be written to the /var/log/avr/md.log file:

    MD_REPORT_STATS|ERR |<date and time>|7670|monitoring.c:0841|Memory exceeded 90.7% of MD Provisioned Allocation!! Entering Collect None Mode. Please raise AVR provisioning definitions

    MD_REPORT_STATS|NOTICE|<date and time>|7670|StatsCollector.cpp:1504|Performing hard-reset, collection mode 2

    MD_GENERAL|NOTICE|<date and time>|7670|monitoring.c:0203|Memory percentage 90.71% of MD Provisioned Allocation (667 MB consumed, out of 736 MB Provisioned). amm stat collection mode 2

    MD_GENERAL|NOTICE|<date and time>|7670|utils.c:1111|Memory usage. Cannot get TMSTAT info, treating only process VMSIZE: 700047360 (MB: 667).

  • The virtual and resident memory values for the md process continue to rise over time, as shown in the following iterated output excerpts from the top command:

    PID USER PR NI VIRT RES SHR S %CPU %MEM TIME+ COMMAND
    5702 root 20 0 99.7m 38m 8580 S 3.7 1.0 0:22.36    md

    PID USER PR NI VIRT RES SHR S %CPU %MEM TIME+ COMMAND
    5702 root 20 0 101m 40m 8580 S 3.3 1.0 0:23.72 md

Workaround

To work around this issue, you can switch from External to Internal logging. To do so, perform the following procedure:

Impact of workaround: Changing logging types requires the analytics service to be restarted, resulting in a brief disruption of any other analytics functionality that may be configured.

  1. Log in to the Configuration utility.
  2. Navigate to the Local Traffic > Profiles > Analytics screen.
  3. Click on the affected analytics profile.
  4. Change the Traffic Capturing Logging Type setting from External to Internal.
  5. Click Update.
  6. Log in to the command line.
  7. Restart the analytics service by entering the following command:

    bigstart restart md
