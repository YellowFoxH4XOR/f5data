Known Issue

This is the result of a known issue. When moving a blade from one chassis to another while maintaining the blade location (for example, from chassis 1, slot 1, to chassis 2, slot 1), the base MAC from the old chassis will be used to construct the interface and VLAN MAC addresses used by the new chassis. As a result, both units may use identical MAC addresses for the affected blades.

For example, the system reports the following MAC address information for a blade in one chassis:

UNIT 1:
VLAN external tag 4001 00:01:D7:56:16:21 MTU 1500
+-> INTERFACE 1/1.1 00:01:D7:56:16:35 ENABLED up MTU 1500
| media auto (10GbaseT full) aggregation: detached
VLAN internal tag 4002 00:01:D7:56:16:22 MTU 1500
+-> INTERFACE 1/1.1 00:01:D7:56:16:35 ENABLED up MTU 1500
| media auto (10GbaseT full) aggregation: detached
| base MAC: 00:01:D7:56:16:00

The VLAN and interface MAC addresses are derived from the base MAC address assigned to the chassis.

After the blade is moved to the same slot in a new chassis, the system reports the following MAC address information:

UNIT 2:
VLAN external tag 4001 00:01:D7:56:16:98 MTU 1500
+-> INTERFACE 1/1.1 00:01:D7:56:16:35 ENABLED uninitialized MTU 1500
| media auto (none) aggregation: detached
VLAN internal tag 4002 00:01:D7:56:16:99 MTU 1500
+-> INTERFACE 1/1.1 00:01:D7:56:16:35 ENABLED uninitialized MTU 1500
| media auto (none) aggregation: detached
| base MAC: 00:01:D7:56:A4:00

The VLAN and interface MAC addresses are derived from the base MAC address from the other chassis.

In rare cases, if the original slot is populated with a new blade, the VLAN and interface MAC address assignments may collide, disrupting communication with the affected interfaces or VLANs.

F5 Product Development tracked this issue as ID 326906 (formerly CR119247).

Note: This issue does not affect BIG-IP 11.x or later software branches.

Workaround

You can recover from this issue by removing the errant MAC address from the running configuration. To do so, refer to the procedures described in K13030: Forcing the mcpd process to reload configuration.

To prevent this issue, do not move a blade to the same slot in another chassis. If necessary, you can shift blades in the target chassis so that the incoming blade always goes into a different slot from which it came.
