Description

There are occasions when you look in the ASM Event Logs for an event and the expected entry is missing.

  • As an example a user contacts you with a Support ID but when you go to look for it the entry is not there.
  • A busy network, Security logging profile set to a Request Type value of  "All Requests", Bot Defense logging is being used.
  • Error messages similar to this:
In /var/log/ts/asmlogd.log you may see...
asmlogd|INFO|Mar 17 08:44:22.800|30241|F5::RequestLog::log_pulse_message,,373876 request records handled since startup (last support id handled = 6506145336664307418)
asmlogd|INFO|Mar 17 08:44:22.801|30241|F5::RequestLog::log_pulse_message,,114294046 Bot Defense records handled since startup (last Bot Defense support id handled = 4892444798353745048, skipped 1353946 Bot Defense requests due to rate limit)
asmlogd|INFO|Mar 17 08:44:22.801|30241|F5::RequestLog::log_pulse_message,,177 attack records handled since startup (last attack id handled = 44569468)

Environment

  • You review the Event Logs but the event you are looking for is missing.
  • Secuirty Logging Profiles in use.
  • ASM, Advanced WAF (AdvWAF)

Cause

This can be caused for a variety of reasons:

  • The most common reason is the use of a security logging profile(s)  assigned to virtual servers that are using a 'Request Type' value of "All requests".
  • You are local logging Bot Defense.
  • You have a busy network and are using ASM/AdvWAF with security logging

Recommended Actions

  1. If you are using a Request Type logging value of "All requests", which is only recommended to be used when troubleshooting, discontinue that. If you must use the "All Requests" value, most commonly due to local requirements, then it is best to set that up with remote logging and send it to a syslog/HSL server. There is an alternative to this but the use of it 'must be' done with the utmost discretion. There is an Advanced Variable that sets the rate limit to 200 per second by default. That is PRXRateLimit. In most cases we would not recommend changing this. The reason is simple... the more allowed the more resources needed to handle it and you risk overloading the mysql database that stores the data. If you choose to do this you will find it here... Security  ››  Options : Application Security : Advanced Configuration : System Variables.
  2. Bot Defense is specifically designed to protect against malicious (DDoS type) attacks. Since these events generate very high levels of logs, F5 recommends leveraging the abilities that HSL brings to the capacity and efficiency of logging services. Non-HSL logging uses the management interface to send logs, and is limited to a single server receiving logs. HSL leverages TMM to allow the full suite of LTM functions to send logs to more than 1 server, using load balancing, and other functions. The issue is that when you set up the Publisher to do HSL for Bot Defense it will not show up in the dropdown when you go to choose your "Remote Publisher". There is away around this and that can be found here...K09439152: HIgh Speed Logging (HSL) for Bot Defense
  3. In some cases even when "All requests" is not being used this can still happen. It usually involves a network that is very busy and uses a lot of ASM/AdvWAF with local logging. The answer here is also to use syslog or HSL.

Additional Information

The BIG-IP is not a logging device. Its purpose is to deliver your traffic safely and in a timely manner. In so doing there are times that some limited logging needs to be reviewed. This is most commonly done for troubleshooting of the BIG-IP itself or in the case of ASM to review Event Logs for recent occurrences.

The consequences of trying to make the BIG-IP into a logging device can range from not finding the data you need when there is an issue to filling up file systems and causing other serious issues.
