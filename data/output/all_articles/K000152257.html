Description

High CPU utilization can occur on the control and analysis plane CPUs of a BIG-IP LTM tenant, with the mcpd process consuming significant resources. This is typically observed when there are frequent or excessive messages from the dynconfd process to mcpd. The issue may be accompanied by a large number of FQDN nodes (some not resolving), a high number of monitor instances, and no production traffic required to trigger the problem. Restarting dynconfd temporarily reduces CPU usage, but it gradually increases again. System logs may show repeated dynconfd-to-mcpd messaging, and symptoms include:

  • High mcpd CPU usage (up to 80% or higher)
  • Gradual increase in CPU after restarting dynconfd
  • Large configuration scale (many FQDN nodes, pools, monitors)
  • No significant events in LTM or audit logs at time of spike

Environment

  • Product: BIG-IP
  • Configuration characteristics:
    • Using FQDN nodes and FQDN pool members.

Cause

This issue is caused by a known software defect (Bug ID 990173) where the dynconfd process repeatedly sends duplicate or excessive messages to mcpd, after a message validation failure, resulting in high control plane CPU usage. The problem may be exacerbated by large configurations with many FQDN nodes and monitor instances.

Recommended Actions

Upgrade to a version where ID990173 is fixed - 15.1.10.8, 16.1.6.1, 17.1.3, 17.5.1.3 and above.

Configuration Cleanup: Remove or correct any FQDN nodes that are not resolving.

Check statistics: You can use statistics from the mcp_transaction_stat table to see if dynconfd is one of the large users of mcpd. If it is it may well sort very near the top when sorted on total_transactions, but with a bit more processing with awk we can get a sense of the total transaction CPU use by multiplying that by the average time for a transaction. The units aren't very important, just the relative values. If you then sort on this use you can see if it's plausible dynconfd could be driving mcpd use.

Starting with the current values

The column titles will not show, but were added by hand for clarity. The fourth column below is created by awk and represents use, and this is also the sort key. There's nothing magical about showing only top three, but probably if dynconf isn't fairly close to top it may not be driving mcpd CPU.

On a BIG-IP use -d blade or use the full path to the relevant tmstat table -f /var/tmstat/blade/mcp_stat_segment.

# tmctl -q -d blade mcp_transaction_stat -s user,total_transactions,process_time_mean | awk '{use=$2*$3; print $0"   "use}' | sort -k 4 -rn | head -3
user                            total_transactions process_time_mean
------------------------------- ------------------ -----------------

%dynconf                                7585285874               159   1206060453966
%statsd                                     512773              5124   2627448852
%bigd.2                                    1975331               579   1143716649

 

In this case it's very clear that dynconfd is a big user of mcpd CPU. Usually the use falls of very quickly as you show more rows so typically the first few rows account for nearly all mcpd CPU use.

For completeness, the command below would give a similar output sorted on total_transactions, showing top three, and this does show column titles:

# tmctl -d blade mcp_transaction_stat -s user,total_transactions,process_time_mean -OK total_transactions -L 3

 

Looking at snapshot data

You can also look at the snapshot data, and this is advisable because you can see what happening recently. On a system with high uptime and a long mcpd process uptime conditions my change over time and total transactions over a long period may be misleading if they have. For instance new FQDN monitors may have been set up recently.

Change directory to /shared/tmstat/snapshots/blade0/public/3600 (or 86400) or use '-T public' argument to tmctl. On a multi-blade capable system replace blade0 with the primary blade number, often 1.

cd /shared/tmstat/snapshots/blade0/public/3600

Pick a snapshot file and put in place of placeholder below.

/shared/tmstat/snapshots/blade0/public/3600$ tmctl -q -f  <blade0-public-3600-20XX-XX-XXTXX:00:00> mcp_transaction_stat -s user,total_transactions,process_time_mean -OK total_transactions | awk '{use=$2*$3; print $0"   "use}' | sort -k 4 -rn | head -3
%dynconf                       9472078324    159   1506060453594
%statsd                           1048994   1752   1855357488
%cmi-mcpd-peer-/Common/ltm2        711704    816   580750464

Next we can see see how total_transactions for dynconf increases through the set of snapshot files.

/shared/tmstat/snapshots/blade0/public/3600$ tmctl -D . mcp_transaction_stat -s time,user,total_transactions,process_time_mean user=%dynconf | awk '/^2/{p3 ? delta=($3-p3)*$4 : delta=""; p3=$3; print $0"   "delta;next}{print $0}'
