Introduction

You should consider using this procedure under the following conditions:

  • You are experiencing unusually high VPN use and your BIG-IP APM systems do not have enough resources (CPU, memory) to handle the increased workloads.
  • You want to maximize your BIG-IP APM system resources by converting a high availability (HA) cluster into separate, active, standalone systems.

There may be times when you need to optimize your BIG-IP APM systems to handle unexpected increased workloads. You can scale out the HA clusters into active, standalone systems that all individually handle network access connections at the same time. You do so by using an existing BIG-IP LTM system to load balance inbound VPN traffic in front of the standalone BIG-IP APM systems.

There are multiple ways to approach this solution. This approach consists of two layers, with a FastL4 virtual server to spread the Network Access VPN workload across multiple BIG-IP APM systems.

The following diagram summarizes the setup.

 

Figure A.1 BIG-IP LTM load balancing VPN traffic in front of n BIG-IP APM systems

  1. User's VPN session encounters FAST L4 virtual server on BIG-IP LTMS system after being routed via NAT by perimeter router or firewall.
  2. The BIG-IP LTM system load balances VN sessions across pool of N x APM standalone VE instances with source address persistence.
  3. The BIG-IP APM VE instances process the VPM connection and provide external access into the network through next-hop router or firewall.
  4. The BIG-IP APM VE instances track the number of concurrent VPN sessions. When the session count reaches the defined threshold (for example, 90 percent), the BIG-IP APM VE instances change the response to an HTTPS monitor to offline, which results in the BIG-IP LTM system marking down the member as DISABLED. This allows existing sessions to continue but no new sessions to be established.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You have at least one pair of BIG-IP APM systems in an HA active-standby configuration.
  • You have a BIG-IP LTM system.

Implement the BIG-IP LTM system

Configure the BIG-IP LTM system using the following:

  • Two FastL4 virtual servers, one for Transport Layer Security (TLS) on port 443 and one for Datagram Transport Layer Security (DTLS) on port 4433.
  • Both virtual servers use the BIG-IP APM instances as pool members.
  • Both virtual servers use a source address persistence profile with Match Across Services enabled.
  • Because the virtual server load balances DTLS traffic, and Network Access VPN traffic may include Voice over Internet Protocol (VoIP) traffic, use the following settings, as described in K16680: VoIP through Network Access connections:
    • For Port Translation, select Disabled.
    • For Source Port, select Preserve Strict.
  • Use these settings:
    • No SNAT: Disable secure network address translation (SNAT) on the FastL4 virtual server.

      When you configured the BIG-IP APM instances on the same subnet as the internal VLAN of the BIG-IP LTM system, this setting allows the BIG-IP APM systems to see the actual client IP addresses.

    • SNAT: When you need SNAT on the BIG-IP virtual server so that the BIG-IP APM instances can see the actual client IP addresses, configure a standard virtual server with the following:
      • HTTP profile
      • Client and server SSL profiles
      • Automap/SNAT pool
      • iRule

      Note that the system must remove the HTTP profile after user authentication to establish the VPN tunnel. You can use the following iRule to insert the X-Forwarded-For header and disable the HTTP profile after authentication:

      when HTTP_REQUEST {
          HTTP::header insert X-Forwarded-For [IP::remote_addr]
          if {[HTTP::uri] starts_with "/myvpn" || [HTTP::uri] starts_with "/isession"} { HTTP::disable }
      }

    Implement the BIG-IP APM systems

    Configure each BIG-IP APM instance using the following:

    • Two BIG-IP APM Network Access virtual servers, one for TLS on port 443 and one for DTLS on port 4433.
    • A third, standard virtual server to monitor User Connectivity Licenses (CCUs) that are actively connected to the BIG-IP APM system. The virtual server responds to the monitor on the BIG-IP LTM system.
    • Follow the recommendations in K31143831: Optimizing BIG-IP APM Network Access VPN to configure:
      • The access policy and Network Access resource with DTLS.
      • Other settings.
    • To support VoIP traffic, follow the recommendations in K16680: VoIP through Network Access connections.
    • Use Auto Last Hop to return traffic back to the BIG-IP LTM system.
    • A default gateway for the BIG-IP APM instances that points to a firewall or router in the internal network leading to all corporate resources.
    • A unique pool of lease pool IP addresses.
    • An internal next hop firewall or router that routes traffic from the corporate servers back to the BIG-IP APM instances.
      • Specifically, configure it for routes to the BIG-IP APM lease pool ranges to point to the self IP address of the corresponding BIG-IP APM instance.

    Monitor the BIG-IP APM instances from the BIG-IP LTM virtual server

    To meet the design goal of spreading Network Access VPN connections evenly, you must monitor each BIG-IP APM instance for both availability and active connections (or license usage).

    To achieve this, configure the following:

    BIG-IP LTM system

    • Create the HTTPS monitor, vpn_https_monitor, with the following settings to monitor each BIG-IP APM Network Access VPN virtual server.

      Table A.3 Settings to monitor each BIG-IP APM Network Access VPN virtual server
      ParameterValue
      Send StringHEAD /my.logout.php3 HTTP/1.1\r\n
      Receive StringServer: BigIP

    • Create the HTTP monitor, vpn_ccu_monitor, to monitor Network Access VPN CCU usage on the BIG-IP APM instances.

      Table A.4 HTTP monitor parameters
      ParameterValue
      Send StringGET /monitor HTTP/1.1\r\n

    Each BIG-IP APM instance

    Create a standard HTTP virtual server (vpn_https_vs) on each BIG-IP APM instance to respond to the HTTP monitor (vpn_ccu_monitor) you created on the BIG-IP LTM system. An iRule (vpn_ccu_monitor_irule) generates the response from this HTTP virtual server. The iRule checks the status of a table that is updated by a Perl script (vpn_ccu_monitor_irule.pl) that runs every 10 seconds using an iCall. These components work together as summarized in the following figure.

     

    Figure A.2 Monitoring setup between BIG-IP LTM and BIG-IP APM instancesTo implement the setup, create the following resources:

    • A standard virtual server, vpn_monitor_vs, containing the vpn_ccu_monitor_irule iRule, which responds to the BIG-IP LTM system's monitor:

      #**
      #** Name : vpn_ccu_monitor_irule
      #** Description: Used in conjunction with vpn_ccu_monitor.pl #** Version: 1.0
      #**
      when HTTP_REQUEST {
         switch [string tolower [HTTP::path]] {
            "/offline" {
            table set monitor offline indef indef HTTP::respond 200 content "offline"
         }
         "/online" {
            table set monitor online indef indef
            HTTP::respond 200 content "online" }
         "/monitor" {
            set response [table lookup monitor] HTTP::respond 200 content $response
         }
         default { HTTP::close } }
      }

    • A Perl script, /shared/scripts/vpn_ccu_monitor.pl, with the following code:

      Note: Run chmod u+x /shared/scripts/vpn_ccu_monitor.pl to enable execute permissions for the script and also edit the $threshold and $vpn_monitor_vs variables in the script first.

      #!/usr/bin/perl -w
      #**
      #** Name : vpn_ccu_monitor.pl
      #** Description: Used in conjunction with vpn_ccu_monitor_irule #** Version: 1.0
      #**

      use strict;

      ## Edit these variables
      # User defined threshold. This is less than or equal to the total-connectivity-sessions (licensed)

      my $threshold=400;

      # Virtual Server hosting an iRule to update the APM status

      my $vpn_monitor_vs="10.5.2.53";

      ##
      # Subroutine that returns the current-connectivity-sessions (used)
      sub used_ccu {
         my $tmsh=`tmsh show apm license field-fmt raw | grep current-connectivity-sessions`;
         $tmsh=~ s/^\s+|\s+$//g;
         my @ccu=split(' ', $tmsh);
         return $ccu[1];
      }
      # Subroutine to change the monitor state to Offline
      sub offline {
         my ($vs) = @_;
         my $curl=`curl -s "http://$vs/offline"`;
      }

      # Subroutine to change the monitor state to Online
      sub online {
         my ($vs) = @_;
         my $curl=`curl -s "http://$vs/online"`;
      }

      # Return the current-connectivity-sessions (used)
      my $used=used_ccu();
      my $status;

      # If the current-connectivity-sessions is greater or equal to the defined threshold, mark the APM node as disabled
      if ($used >= $threshold) {
         # add error log message to /var/log/ltm
         # offline
         $status = offline($vpn_monitor_vs);
      } else {
         # online
         $status = online($vpn_monitor_vs);
      }

    • After you create the Perl script, use the Advanced Shell (bash) for each BIG-IP APM system and the following commands to create an iCall that runs the script every 10 seconds:
      • tmsh create sys icall script vpn_ccu_script definition { catch { exec perl /shared/scripts/vpn_ccu_monitor.pl } }
      • tmsh create sys icall handler periodic vpn_ccu_handler script vpn_ccu_script interval 10
