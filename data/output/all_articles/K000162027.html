K000162027: BIG-IP LTM may distribute client traffic unevenly across TMM CPU cores after reboot or core.

Description

After a reboot, upgrade, failover, blade replacement, or TMM restart, BIG-IP LTM may distribute client traffic unevenly across TMM CPU cores. A small number of cores can run persistently hot (for example, sustained utilization above 80%) while other cores remain lightly loaded, even though overall throughput and memory usage appear normal. The condition is most visible on multi-core or multi-blade platforms and often first appears immediately after a maintenance event.

Environment

  • BIG-IP LTM

Cause

Traffic is steered to TMM instances by the Disaggregation (DAG v2) hash table. The DAG v2 hash table is seeded with a value that is re-randomized on each reboot, failover, blade replacement, or TMM restart. Because the seed changes, the mapping of flows to TMM cores is non-deterministic and can shift after any such event, producing a different (and sometimes lopsided) distribution than before.

The imbalance is amplified when the source-address-translation pool (SNAT or CGNAT/LSN) contains too few translation addresses. With few translation IPs, the hashing input has low cardinality, so flows concentrate onto a small number of cores. This same condition also increases the likelihood of port exhaustion on individual translation addresses.

Recommended Actions

  1. Confirm the per-TMM CPU distribution:
    tmsh show sys tmm-info
    Compare CPU usage ratios across TMM instances to confirm that a subset of cores is carrying a disproportionate share of the load rather than a general capacity issue.
  2. Review the source-address-translation pool sizing:
    tmsh list ltm virtual source-address-translation
    Identify the SNAT or LSN pool in use, then confirm how many translation addresses it contains. A pool with few addresses reduces hashing granularity and concentrates flows on fewer cores.
  3. Expand the SNAT or LSN pool where feasible:
    Adding translation addresses increases hashing granularity and reduces both core concentration and per-address port exhaustion. Plan address additions in line with expected concurrent flow volume.
  4. Re-seed the distribution as a temporary workaround:
    Restarting TMM causes the DAG v2 table to be re-seeded, which may produce a more even distribution. This is disruptive to traffic and must be performed in a maintenance window. Note that the result is not deterministic and the imbalance can recur on any future reboot, failover, blade replacement, or TMM restart.
  5. Plan an upgrade if a stable mapping is required:
    A persistent DAG v2 mapping that survives restarts is only available through a fixed release. Where a stable distribution is a requirement, plan an upgrade to a version that includes the DAG v2 hash-table lock capability.

Additional Information

  • The re-seeding behavior is expected by design in affected releases; it is not a one-time upgrade artifact. The seed re-randomizes on every reboot, failover, blade replacement, or TMM restart, so the distribution can change after each such event.
  • A permanent remedy that allows the DAG v2 hash table to be locked or adjusted at runtime is delivered through a database-variable enhancement available only in later releases (17.1.3.2 and later, and 17.5.1.4 and later). This enhancement is not present in 15.1.x, where the change is not planned. Confirm the exact fixed versions against current F5 release notes before scheduling an upgrade.
  • Undersized CGNAT/LSN pools are a known trigger for both the uneven core loading and translation-port exhaustion. Increasing translation-address count typically addresses both symptoms together.
  • High utilization on a subset of cores does not by itself indicate user-visible impact. Correlate the hot cores with actual traffic behavior (drops, latency, or translation failures) before treating the imbalance as service-affecting.
