Topic

In order for a BIG-IP system pool to provide persistence based on a custom value, the BIG-IP system must first learn and store that value. If you attempt to use an iRule with a custom persistence method, it could result in the BIG-IP system choosing different nodes for initial load balancing and persistence.

To avoid this issue, create an iRule that will read both the persistence and the load balancing values from the packet and use them in combination to make load balancing decisions.

Refer to the following example scenario. In this example, there are two requirements for the BIG-IP system:

  • The BIG-IP system reads the value of the HTTP header, HTTPAuthenticated, and, based on that value, makes a load-balancing decision as follows:

    ValuePool
    "YES"Authed
    "NO"NotAuthed
    Other valueNotAuthed

  • The BIG-IP system reads the value of the HTTP header, HTTPAuthenticated (which should either contain a user name or be empty), and persists the session based on that value.

Therefore, the best way to construct an iRule is to use an and statement in the iRule. That way, the HTTP header values are included for both the load balancing and persistence decisions.

The new iRule for this example would appear as follows:

RULE AUTHEDNAME_RULE {
if (http_header("HTTPAuthenticated") == "YES" and exists http_header("HTTPUserName")) {
use pool Authed
}
else {
if (http_header("HTTPAuthenticated") == "NO" and exists http_header("HTTPUserName")) {
use pool NotAuthed
}
else {
log "client_addr ${client_addr} failed "
use pool NotAuthed
}
}
}
pool Authed {
persist http_header("HTTPUserName")
persist_timeout 180
member 10.90.100.50:80
member 10.90.100.51:80
}
pool NotAuthed {
persist http_header("HTTPUserName")
persist_timeout 180
member 10.90.100.52:80
member 10.90.100.53:80
}

For additional information about iRules, refer to the iRules chapter of the BIG-IP Reference Guide.
