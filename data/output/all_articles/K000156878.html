K000156878: What are TCP connections without message integrity protections? How can I implement safeguards to ensure data integrity?

Description

You are concerned about TCP connections that do not have message integrity protections, which could expose your systems to tampering or interception. This article outlines how to verify such connections and implement safeguards to ensure data integrity.

  • Plain TCP only checks for random bit-flips with a simple checksum. It does not cryptographically protect messages. An attacker on the path can change bytes and neither endpoint will know.
  • Message integrity is provided by cryptography (for example, TLS/SSL record MAC or AEAD like AES-GCM/ChaCha20-Poly1305), IPsec, or application-layer signing. With integrity, tampering is detected.

In practice, “TCP without message integrity” means any cleartext TCP protocol (HTTP on 80, LDAP 389, IMAP 143, POP3 110, SMTP 25 without enforced STARTTLS, custom TCP apps without TLS), or traffic that F5 passes at L4 without a protection layer. TLS gives both encryption and integrity.

Environment

  • TCP connections used by your application or service
  • No encryption or message validation mechanisms implemented
  • Configurations using plaintext communication or inadequate security controls

Cause

Not using cryptographic protocols such as TLS or additional message signing mechanisms results in unprotected communication, making it susceptible to attacks such as data interception or manipulation.

Recommended Actions

  1. Identify all TCP connections in your environment by reviewing logs and configurations.
  2. Check if the connections are secured using cryptographic protocols like TLS (Transport Layer Security). Non-secure connections often rely on plaintext communication.
  3. Enable TLS to provide encryption and ensure message integrity protection. Update configurations to enforce secure communication protocols.
  4. For applications requiring additional validation at the application layer, implement message signing using HMAC or other cryptographic methods.
  5. Run a security audit using tools like Wireshark or tcpdump to detect unencrypted TCP connections.
  6. Regularly monitor logs for suspicious activity and adjust security measures accordingly.
  7. Educate teams on secure coding practices to prevent insecure configurations.

Additional Information

Securing TCP connections is critical for protecting data integrity and privacy during transmission. F5 products such as BIG-IP SSL Orchestrator can help manage encrypted traffic and enhance communication security.

How to check on BIG-IP if traffic has integrity protection

  1. Check each Virtual Server (data plane)
  • In the GUI: Local Traffic > Virtual Servers > Virtual Server List > click a VS > Profiles.
    • If you see a Client SSL profile attached: client-to-BIG-IP traffic is protected.
    • If you also see a Server SSL profile: BIG-IP-to-server traffic is protected (end-to-end).
    • If neither profile is present: there is no TLS integrity on that side.
    • If only Client SSL is present: only the client side is protected; traffic to the pool is plaintext.
  • In tmsh (CLI):
    • tmsh list ltm virtual <vs_name> profiles
      • Look for clientssl and/or serverssl in the profiles block.
    • To review SSL profile details (versions, ciphers):
      • tmsh list ltm profile client-ssl <profile_name> all-properties
      • tmsh list ltm profile server-ssl <profile_name> all-properties
 
  1. Spot plaintext listeners by port
  • VS listening on ports like 80, 21, 25, 110, 143, 389, or a custom TCP port, with no Client SSL profile, are almost certainly plaintext.
  • In the GUI: check each VS’s Destination port and Profiles.
  • In tmsh: tmsh list ltm virtual one-line
    • Scan for VIPs on cleartext ports that lack clientssl.
 
  1. Verify with a quick packet capture (when in doubt)
  • On BIG-IP: tcpdump -nni 0.0:nnn -s0 host <client_or_server_ip> and port <port>
    • If you see TLS Client Hello/Encrypted Handshake, it’s protected.
    • If you see readable ASCII (HTTP/1.1 GET, LDAP binds, etc.), it’s plaintext.
 
  1. Management plane (admin access to BIG-IP)
  • Web UI should be HTTPS only; SSH should be used instead of Telnet.
  • tmsh list sys httpd
    • Check ssl-port (usually 443). Ensure no plain HTTP mgmt exposure.
  • tmsh list sys sshd
    • Ensure SSH is enabled and Telnet is not enabled.
  • SNMP: Prefer SNMPv3 (integrity and encryption) over v1/v2c.
    • tmsh list sys snmp | grep -i version

How to prevent TCP without message integrity on BIG-IP

  1. Terminate TLS on the VIP (Client SSL)
  • Create/attach a Client SSL profile to the Virtual Server.
  • Use modern TLS:
    • On newer TMOS, prefer TLS 1.2 and TLS 1.3 with AEAD ciphers (AES-GCM or ChaCha20-Poly1305).
    • Use built-in cipher groups like f5-secure (or your org’s approved group).
  • tmsh example:
    • tmsh create ltm profile client-ssl my_clientssl defaults-from clientssl
    • tmsh modify ltm profile client-ssl my_clientssl ciphers DEFAULT cipher-group f5-secure
    • tmsh modify ltm virtual <vs_name> profiles add { my_clientssl }
 
  1. Re-encrypt to servers (Server SSL)
  • If you need end-to-end protection, also attach a Server SSL profile so BIG-IP re-encrypts to the pool.
  • Optionally enable server certificate validation (set the proper CA, require SNI).
  • tmsh example:
    • tmsh create ltm profile server-ssl my_serverssl defaults-from serverssl
    • tmsh modify ltm virtual <vs_name> profiles add { my_serverssl }
 
  1. Eliminate or control plaintext protocols
  • For web apps:
    • Redirect HTTP to HTTPS at the VIP (LTM Policy or iRule).
    • Add HSTS to prevent SSL stripping (insert Strict-Transport-Security header).
  • For email, directory, and mail clients:
    • Enforce TLS/STARTTLS or move to implicit TLS ports (e.g., 465/993/995/636).
  • For custom TCP apps:
    • Wrap with TLS on BIG-IP (Client/Server SSL) or implement TLS in the app.
    • If you must run L4 only (FastL4), use IPsec tunnels between sites to protect traffic.
 
  1. Management plane hardening
  • Disable any plaintext management access.
  • Use SSH, HTTPS, and SNMPv3 only.
  • Restrict management access by source IPs and use firewall/AFM if licensed.
 
  1. Validate your posture
  • Scan VIPs externally with nmap or sslyze to confirm TLS is used and only strong suites are offered.
  • Capture briefly with tcpdump to confirm no sensitive flows remain in cleartext.
