Description

IMISH 'show ip bgp summary' output indicates some BGP peers are down and some are up.  In the following example, only one of the peers is showing as up.

 

#show ip bgp summary

BGP router identifier N.N.251.36, local AS number 65535

BGP table version is 55

29 BGP AS-PATH entries

13 BGP community entries

 

Neighbor   V    AS MsgRcvd MsgSent TblVer InQ OutQ Up/Down   State/PfxRcd

N.N.244.23 4 65534    6067    7721     55   0    0 2d01h30m           541

N.N.244.24 4 65534      59    3775      0   0    0 01:38:05        Active

N.N.255.26 4 65534       0    3676      0   0    0                 Active

N.N.251.33 4 65534       0    3587      0   0    0                 Active

 

However, when looking at the output of the command 'show ip route', there are preferred BGP routes from peers that are supposedly down indicating that bgpd may be receiving prefix updates from these peers.

 

#show ip route

Codes: K - kernel, C - connected, S - static, R - RIP, B - BGP

 O - OSPF, IA - OSPF inter area

 N1 - OSPF NSSA external type 1, N2 - OSPF NSSA external type 2

 E1 - OSPF external type 1, E2 - OSPF external type 2

 i - IS-IS, L1 - IS-IS level-1, L2 - IS-IS level-2, ia - IS-IS inter area

 * - candidate default

 

Gateway of last resort is N.N.251.33 to network 0.0.0.0

 

B* 0.0.0.0/0 [20/0] via N.N.251.33, vl251, 3d22h05m

B N.N.100.0/24 [20/0] via N.N.244.24, vl244, 01:15:23

B N.N.0.0/16 [20/0] via N.N.244.24, vl244, 01:15:23

B N.N.1.0/24 [20/0] via N.N.244.24, vl244, 01:15:23

 

Environment

  • BIG-IP
  • ZebOS

 

Cause

This is due to two bgpd processes simultaneously running for the same route domain. The underlying cause was an out of memory condition from processing large Telemetry Streaming data resulting in tmrouted incorrectly restarting bgpd where the original bgpd process did not get terminated.

 

Recommended Actions

Immediate workaround is to reboot the device to correct the BGP state. Longer term correction, as recommended by PD, is to set "enableGC" to true and "maxHeapSize" to 1600 in the controls section of the Telemetry Streaming declaration to mitigate out of memory conditions.

 

Additional Information

Additional verification checks can be done by inspecting outputs of 'ps' and 'netstat' for bgpd processes.

In this example, the 'ps' command output shows there are multiple process IDs for bgpd running on the same route domain. In this example, PIDs are 9189 and 19858, respectively, for route-domain 0.

$ ps aux | grep bgpd
root        9189   8482   0.0   0.0   10.9M    4.4M ?        S    Feb02   00:02:45.41 bgpd%0
root       19858      1   0.0   0.0   11.0M    4.4M ?        S    Jul09   01:21:07.46 bgpd%0 

Netstat output indicates that the peering that is up belongs to one PID, and those which are down belong to another bgpd PID.

$ netstat -pano | egrep "^tcp.*bgpd\%0"
tcp        0      0 0.0.0.0:179          0.0.0.0:*            LISTEN      9189/bgpd%0          off (0.00/0/0)
tcp        0      0 N.N.244.236:179      N.N.244.23:50058     ESTABLISHED 9189/bgpd%0          off (0.00/0/0)
tcp        0      0 N.N.244.236:179      N.N.244.24:50961     ESTABLISHED 19858/bgpd%0         off (0.00/0/0) <--
tcp        0      0 N.N.255.28:51984     N.N.255.26:179       ESTABLISHED 19858/bgpd%0         off (0.00/0/0) <--
tcp        0      0 N.N.251.36:35064     N.N.251.33:179       ESTABLISHED 19858/bgpd%0         off (0.00/0/0) <--

The expected normal working bgpd should only have a single process ID for the route domain.
