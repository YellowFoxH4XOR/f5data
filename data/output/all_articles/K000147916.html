Answer/Recommended Actions

About the Ingress Controller

The Ingress Controller manages external access to HTTP services in a Kubernetes cluster using the F5 Distributed Cloud Services Platform. The ingress controller is a K8s deployment that configures the HTTP Load Balancer using the K8s ingress manifest file. The Ingress Controller automates the creation of load balancer and other required objects such as VIP, Layer 7 routes (path-based routing), advertise policy, certificate creation(k8s secrets or automatic custom certificate), etc.

Note: The F5 Ingress Controller is supported only for the Sites running Managed Kubernetes, also known as Physical K8s (PK8s). Deployment of the ingress controller is supported only using Helm

 

Ingress Controller Operation

The ingress controller operates as summarized below:

  • It runs as pod on k8s Site.
  • It watches the kubernetes events for added, modified, and deleted actions performed on the networking.k8s.io/v1 Ingress objects.
  • When added or modified event is detected it programs the following F5 Distributed Cloud objects based on the ingress spec and annotations:
     
    • Origin pool is created based on the service referenced in backend.service or defaultBackend
    • The host is mapped to the load balancer domain
    • Load balancer routes are configured based on path and pathType to provide path-based routing. Having ImplementationSpecific in pathType indicates regex path match in the route configuration.
    • If TLS section is not present in the ingress spec, HTTP load balancer is created (no TLS termination)
    • If TLS section is present in the ingress spec, the secretName is mapped to the load balancer certificate and HTTPs load balancer is created.
    • Service policy used for allow listing.

Using the instructions provided in this article, you can perform the following:

  • Install Ingress Controller in your Sites using Helm
  • Create and advertise an HTTP/HTTPS load balancer with your TLS certificate or with the certificate minted by Distributed Cloud Services

Note: Distributed Cloud Services support automatic certificate generation and management. You can either delegate your domain to Distributed Cloud Services or add the CNAME record to your DNS records in case you do not delegate the domain to Distributed Cloud Services. See Automatic Certificate Generation for certificates managed by Distributed Cloud Services. See Delegate Domain for more information on how to delegate your domain to Distributed Cloud Services.

 

Prerequisites

The following prerequisites apply:

  • A Distributed Cloud Services Account.
  • A valid DNS domain delegated to Distributed Cloud Services in case you want Distributed Cloud Services to act as domain name server (DNS). For instructions on how to delegate your domain to Distributed Cloud Services, see Delegate Domain.
  • A Distributed Cloud Services Site with Managed K8s (PK8s). See Managed K8s and App Stack Site for more information.
  • The kubectl client version 1.19 or above.
  • Helm version 3.2.0 or above. See Helm Install Guide for more information. See Quick Start guide and Using Helm Guide for learning more about Helm.
  • Git must be installed on your local machine to pull the Ingress Controller Helm repository.

Install Ingress Controller

The F5 Distributed Cloud Ingress Controller can be installed using Helm package manager. Follow below steps to customize the helm template with the details of your tenant and cluster and install the ingress controller on your pk8s cluster.

Step 1: Obtain Ingress Controller helm templates. Clone the Ingress Controller Repo to your local file system.

git clone https://gitlab.com/volterra.io/f5xc-ingress-helm.git

The helm template can be updated with by updating parametes in the f5xc-ingress-helm-main/f5xc-ingress-controller/values.yaml. The following table provide reference to various parameters in values.yaml file

Step 2: Obtain tenant details

  • Log into F5 Distributed Cloud Console and select Cloud and Edge Services on the home page.
  • Go to Sites > Site List. Select a Site of your choice from the displayed list of Sites.
  • Use the > button against the Site to display its details in JSON format. Note down the tenant as the value for config.tenant parameter and name field as the value for config.siteName.

Note: The config.tenant field requires the full path, along with the suffix-id. This is different from other places that need tenant like the config.url where it is only the tenant name.

 

Step 3: Obtain API certificate and key.

  • Generate and download API certificate in the P12 format as per the instructions mentioned in Generate API Certificate. Save the file to your local folder. Ensure that the following roles are mapped to namespaces while generating the certificate:

 

Namespace Role
default ves-io-default-role
all app namespaces ves-io-admin-role
shared ves-io-admin-role

 

  • Extract the certificate and private key out of the P12 file. The following sample commands extract the certificate and key to vescred.cert and vesprivate.key files respectively.
$ openssl pkcs12 -in ~/[tenant].console.ves.volterra.io.api-creds.p12 -nodes -nokeys -out $HOME/vescred.cert

Enter Import Password:

MAC verified OK
$ openssl pkcs12 -in ~/[tenant].console.ves.volterra.io.api-creds.p12 -nodes -nocerts -out $HOME/vesprivate.key


Enter Import Password:

MAC verified OK

 

Step 4: Encode the certificate and key in base64 format.

Use the base64 command to encode the files. The following sample commands encode the files extracted in the previos step:

cat $HOME/vescred.cert | base64

cat $HOME/vesprivate.key | base64

Use this encoded values in config.apiCert and config.apiKey respectively in values.yaml.

Optionaly this can be set in the secret.yaml and can be applied directly or stored in Vault

E.g.:

apiVersion: v1 
kind: Secret 
metadata: 
  name: volt-ic-secret 
  namespace: volt-ic 
type: Opaque 
data: 
  ApiCert: QmFnIEF....0dHJpYn # base64 encoded apiCert 
  ApiKey: QmFnIEF0.....dHJpYn # base64 encoded apiKey 

Note: When the existingSecret parameter is set, the previous apiCert and apiKey are ignored. The existingSecret needs to be in the same namespace as deployment.

Step 5: Install the Ingress Controller.

You can install the controller by using the heml install command. You can either specify each parameter in the command itself or update the values.yaml with all parameters and use it to install. Make sure you are in the f5xc-ingress-helm directory while running the below commands.

Using Individual Parameters

Specify each parameter using the --set key=value[,key=value] argument. The following is a sample setting the deployment.tag to v1.4.

$ helm install my-release --set deployment.tag=v1.4 f5xc-ingress-controller

Using Manifest File

The following sample command uses the values.yaml manifest to install.

helm install my-release -f values.yaml f5xc-ingress-controller

Note: It is recommended to use immutable tags as it ensures your deployment does not change automatically if the same tag is updated with a different image.

Updating API Key and Certificate

Since the API certificates is valid only for a maximum of 12 months, it is required to update the secret with the new API certificates. After generating the new certificate as shown in steps 3 and 4, insert the new apiCert and apiKey into values.yaml file and execute the following command:

$ helm upgrade -f values.yaml my-release f5xc-ingress-controller

The above command will generate a new release with the updated API certificates.

Alternatively, if using the existingSecret, after updating the K8s secret in the pod, run the following command:

$ helm upgrade --set existingSecret=new-secret my-release f5xc-ingress-controller

This command will generate a new release with the updated existing secret.

 

Step 6: Create an ingress.

  • Create a service and expose it using an ingress

                            Or

  • Use below sample ingress manifest with a few F5XC annotations.
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend-ingress
  annotations:
    ingress.cloud.f5.com/https-auto-cert: "true"   #TLS termination with auto cert
    ingress.cloud.f5.com/http-redirect: "true"     #Enable HTTP to HTTPs redirect
    ingress.cloud.f5.com/ip-prefix-set: | 
                                 allow 209.177.156.77/32; 
                                 allow 163.114.225.0/24; 
                                 allow 209.58.164.15/32; 
                                 deny all;
spec:
  rules:
  - host: acme.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80

 

Step 7: Verify the created load balancers.

  • Log into Console and select Load Balancers service from home page, switch to the namespace into which your deployment is made.
  • Select Manage > Load Balancers > HTTP Load Balancers.
  • Confirm that the load balancers are created. Every ingress creates one to two HTTP load balancers for HTTP and/or HTTPs pointing to the same origin pool with K8s service discovery. The number of load balancers depends on the annotation set by users (users may need HTTPs, HTTP, or HTTP with redirect). The configuration of load balancers depends on the K8s ingress file. The populated IP address and CNAME can be found in both ingress status and load balancer configuration

Step 8: Verify the created origin pools.

  • Select Manage > Load Balancers > Origin Pools.
  • Confirm that the load origin pools are created. The origin pools are referenced by the Routes configuration of load balancer and origin pools point to the K8s services under the same name and namespaces. The configurations of origin pools depend on the K8s ingress file routes section and annotations.

Step 9: Verify the created IP prefix sets.

  • Select Security > Shared Objects > IP Prefix Sets. Confirm that the IP prefix sets are created.
  • The IP prefix sets are referenced by service policy and serve as allow or deny list of IPs. The configurations of IP prefix sets depend on the k8s ingress file annotations.

Step 10: Verify the created IP prefix sets.

  • Select Security > Service Policies > Service Policies. Confirm that the service policies are created.
  • The service policies are referenced by the Service Policies configuration of load balancers. The service policies use IP prefix sets for allowed and denied access. The configurations of service policies depend on the K8s ingress file annotations.

 

Additional Information

Troubleshooting Ingress Controller

You can use Console and also kubectl to find and troubleshoot potential issues with ingress controller. Perform the following:

Step 1: Inspect managed K8s events related to ingress controller.

  • Log into Console and select Cloud and Edge Sites service. Go to Managed K8s > Overview.
  • Select your K8s cluster from the displayed list to open its monitoring dashboard. Switch to Events tab.

     Figure: Managed K8s Ingress Controller Events

  • Check for events from ves-lb in the Source column. This shows the basic information for a given ingress. Expand the event using the > option to see the involved object, namespace, and site information.

Step 2: Inspect the pods of ingress controller using the Kube API.

  • Go to Managed K8s > Overview and select ... > Download Global Kuneconfig. Download the kubeconfig file to your local file system.

    Figure: Global Kubeconfig for Managed K8s

  • Use the kubectl command with the downloaded kubeconfig to view the ingress controller pod details. This example shows ingress controller pod information in the volt-ic namespace.
~ kubectl --kubeconfig=ves_system_qa1-inap-f5xcsse-sea1_kubeconfig_global.yml -n volt-ic get po -w

NAME READY STATUS RESTARTS AGE

volt-ic-777d7db88f-96vt2 2/2 Running 0 6d15h
