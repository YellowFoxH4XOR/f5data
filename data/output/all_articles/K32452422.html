Description

Istiod is the unified control plane responsible for configuring Envoy proxies (sidecar and gateways) in your cluster. It provides an abstraction layer for hiding the Envoy proxy APIs while allowing you to configure your mesh using the orchestration environment (in this case Kubernetes) APIs. It is also responsible for validating your mesh configuration as a Kubernetes validation webhook, automatically injecting the sidecar proxies into workloads and managing the lifecycle of keys and certificates used for securing workload-to-workload communication via mutual TLS.

If a pod was not able to get a sidecar injected or any of the Istio/Aspen Mesh resources are not configured properly, istiod is one of the essentials pods that we need to take care and starting to look if something wrong.

Environment

  • Kuberntes: 1.17x,1.18.x,1.19.x,1.20.x
  • Aspen Mesh: 1.6.x, 1.9.x 

Cause

There are a few things that you should consider doing first before deeply going into activating debug logging in your istiod controlplane:

  1. Ensure that the certificates are not expired if you use your own.
  2. Verify the validatingwebhooks and mutatingwebhooks works by deploying any resource like a Destination Rule, Virtual Service, Service Entry, or even a pod with a sidecar injected.
  3. Verify all the pods from your installation are up and running.
  4. Output the logs from istiod before trying to enable debugging.
  5. Contact Aspen Mesh Support team.
If none of the above gives you an insight into what’s going on with your service mesh, enabling debugging in istiod should be the last thing to do.

Recommended Actions

  • Enabling debugging manually
  • Enabling debugging via deploy template (less preferred)

Enabling debugging manually

Here are the steps you need for enabling debug on istiod:

  1. Run the following command:

    istioctl dashboard controlz istiod-76544f59-l6xms.istio-system

    If istioctl is not available or didn’t work, try port-forward an istiod pod:

    kubectl port-forward pod/istiod-76544f59-l6xms -n istio-system 9876:9876

  2. On the left side panel, click on Logging Scopes.
  3. In this screen you will see all the logger’s scopes by name, then change the output_level from info to debug.
If you don’t want to do it via web-ui, then use the following commands via CLI:
  1. We assume that port-forward is still running on another window run:

    curl http://localhost:9876/scopej/ | jq '.[].name' -r > loggers.txt

    This will extract all the loggers name.

  2. Change output level to debug:

    for i in $(cat loggers.txt); do curl -X PUT http://localhost:9876/scopej/$i -H 'Content-Type: application/json' -d '{"output_level":"debug"}' ;  done

  3. You can verify via web or curl the logger is now in debug mode:

    curl http://localhost:9876/scopej/ca {"name":"ca","description":"ca client","output_level":"debug","stack_trace_level":"none","log_callers":false}

Enabling debugging via deploy template (less preferred)

If for some reason you want the logs scope to run in debug log level for a long time, you can edit your deployment template and add the debug level to log scope in the arguments.

  1. Edit you istiod deployment:

    kubectl edit deployment istiod -n istio-system

  2. Under args you will see the field –log_output_level=default:info, we are going to change to debug:

    spec:
      containers:
      - args:
        - discovery
        - --monitoringAddr=:15014
        - --log_output_level=default:debug
        - --domain
        - cluster.local
        - --keepaliveMaxServerConnectionAge
        - 30m

  3. After edit the deployment your istiod pods will rollout with new ones with debug level.

The reason why we do not recommend this method is because after the edit on the deployment template your pod will be replaced, losing all the old data.

Note: You must not leave the istiod in debug mode for a long time, especially in big and complex clusters as will log a huge amount of data.
