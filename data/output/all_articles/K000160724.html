Description

A discrepancy occurs on BIG-IP SSL Orchestrator (SSLO) systems where the CLI shows the "strict-updates" setting as disabled for security policies, 

For example:

On CLI:

sys application service /Common/ssloP_example.app/ssloP_example {
  description hide
  device-group none
  inherited-devicegroup true
  inherited-traffic-group true
  lists none
  metadata none
  partition Common
  strict-updates disabled <-----
  tables none
  template none
  template-modified no
  template-prerequisite-errors none
  traffic-group /Common/traffic-group-1
  variables none
}

But the GUI ( SSLO > security Policies > Intercept...) continues to display the padlock icon, indicating the policy is still protected.

This issue is characterized by:

  • CLI output confirming "strict-updates disabled" for all relevant SSLO application services.
  • Audit logs showing successful execution of CLI commands to disable strict-updates.
  • GUI still showing the lock icon for affected security policies.
  • REST API inspection revealing that the iAppLX block data in REST storage retains "strictness": true, resulting in a mismatch between CLI (MCP) and GUI (REST/iAppLX) data.

Environment

  • Product: BIG-IP SSL Orchestrator (SSLO)
  • SSLO security policies configured
  • "strict-updates" disabled via CLI

Cause

The issue appears to be a synchronization problem between MCP (updated by CLI) and REST/iAppLX storage (used by the GUI), resulting in the GUI not reflecting the CLI state change for "strict-updates."

Answer/Recommended Actions

To resolve the discrepancy, redeploy the security policy to attempt to synchronise the REST storage with MCP configuration

  1. Navigate to SSLO GUI > Security Policies >  [affected policy]
  2. Click Edit
  3. Make a minor change (such as adding a description) 
  4. Click Deploy
