Known Issue

The BIG-IP system does not properly rewrite the destination IP address for fragmented User Datagram Protocol (UDP) packets.

This issue occurs when all of the following conditions are met:

  • A stateless virtual server is configured
  • The stateless virtual server handles large UDP packets that are fragmented

When using a stateless virtual server, the BIG-IP system correctly rewrites the destination IP address for the first UDP fragment, but does not rewrite subsequent fragment destination addresses. All fragments of a large fragmented UDP packet are load balanced correctly based on the Layer 2 (L2) destination MAC address. However, only the first fragment of the UDP datagram will have the Layer 3 (L3) destination address rewritten. All subsequent fragments of a given datagram will retain the virtual server L3 destination address.

For example:

  • The BIG-IP virtual server at 172.16.10.100 receives the packet fragments in packets #1 and #2 from the client at 172.16.10.10:

    #1 11.355756 172.16.10.10 172.16.10.100 Fragmented IP protocol (proto=UDP 17, off=0, ID=1dd6)
    #2 11.355765 172.16.10.10 172.16.10.100 Source port: 32876 Destination port: 90

  • On the server side, the BIG-IP sends the fragments to the pool member at 10.11.12.10 in packets #3 and #4. Notice that packet #3 has the appropriate destination IP address, but packet #4 reverts back to the virtual server IP address:

    #3 11.355798 172.16.10.10 10.11.12.10 Fragmented IP protocol (proto=UDP 17, off=0, ID=1dd6)
    #4 11.355802 172.16.10.10 172.16.10.100 Fragmented IP protocol (proto=UDP 17, off=1480, ID=1dd6)

  • The pool member eventually sends an Internet Control Message Protocol (ICMP) "Time-to-live exceeded" message in packet #5:

    #5 41.373868 10.11.12.10 172.16.10.10 Time-to-live exceeded (Fragment reassembly time exceeded)

Impact

The pool member does not correctly reassemble packet fragments, which causes the communication to time out.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • Communication fails, and you observe an ICMP message similar to the following example:

Workaround

To work around this issue, perform one of the following procedures:

Replacing the stateless virtual server with a Fast L4 virtual server with an immediate timeout

Impact of workaround: If you perform the following procedure, overhead may increase on high traffic systems.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Profiles > Protocol > Fast L4.
  3. Click Create.
  4. Enter a name for the new profile.
  5. Next to Idle Timeout, select the Custom check box.
  6. From the Idle Timeout menu, select Immediate.
  7. Click Finished.
  8. Navigate to Local Traffic > Virtual Servers.
  9. Click your Stateless virtual server.
  10. From the Type menu, select Performance (Layer 4).
  11. From the Configuration menu, select Advanced.
  12. From the Protocol Profile (Client) menu, select the custom Fast L4 profile you created.
  13. Click Update.

Replacing the stateless virtual server with a UDP virtual server with an immediate timeout

Impact of workaround: If you perform the following procedure, overhead may increase on high traffic systems.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Profiles > Protocol > UDP.
  3. Click Create.
  4. Enter a name for the new profile.
  5. Next to Idle Timeout, select the Custom check box.
  6. From the Idle Timeout menu, select Immediate.
  7. Click Finished.
  8. Navigate to Local Traffic > Virtual Servers.
  9. Click your Stateless virtual server.
  10. From the Type menu, select Standard.
  11. From the Configuration menu, select Advanced.
  12. From the Protocol Profile (Client) menu, select the custom UDP profile you created.
  13. Click Update.
