Topic

This article discusses the BIG-IP system split planes (HTSplit) feature.

Description

BIG-IP platforms with Hyper-Threading Technology (HT Technology) CPUs use separate logical cores for data plane and control plane tasks. The HTSplit feature improves performance by dedicating and prioritizing resources for the Traffic Management Microkernel (TMM) and allows for non-TMM control plane tasks to still be performed when TMM is fully utilized. The scheduler.splitplanes.ltm database key is enabled by default on all systems but only affects systems with HT Technology CPUs. When enabled, data plane tasks and control plane tasks are split and handled by separate logical cores (hyper-threads). Each HT Technology physical core has a single TMM running. The even-numbered hyper-threads (0, 2, 4, and so on) are dedicated to TMM as a high-priority process to service data plane tasks. The odd-numbered hyper-threads (1, 3, 5, and so on) process control plane tasks at a normal priority level.

There are two conditions in which idle enforcer becomes active

  1. TMM reaches 80 percent use, and the odd-numbered hyper-thread throttles the control plane tasks so that they can use only 20 percent, allowing TMM to use the remaining resources. 
  2. V1 plug-in state becomes inactive. If the plug-in is active, idle enforcer does not engage.

Note: Plug-ins refer to proprietary Linux processes outside of TMM so that the TMM process can work to accomplish additional traffic related options. For example, iLXplug-in, SSH plug-in, XML routing feature, NTLM, and also BIG-IP APM, BIG-IP ASM and BIG-IP PEM features.

In the /var/log/kern.log file, the BIG-IP system logs messages that appear similar to the following example:

info kernel: ltm driver: Idle enforcer starting - tid: <pid> cpu: 1/1
info kernel: ltm driver: Idle enforcer exiting - tid: <pid> cpu: 1

Note: tid denotes the thread ID of idle enforcer.

TMM performance is much more predictable due to the lack of context switching, causing latency to drop from 10-15 ms, in the worst case, to a few milliseconds. Additionally, this allows for management tasks to remain responsive when TMM is heavily utilized. For example, in cases where TMM is fully utilized, management tasks that previously took more than 10 minutes to complete (such as loading a very large configuration) are now complete in a few minutes. For more information on HTSplit, refer to K15003: Data plane and control plane tasks use separate logical cores when the BIG-IP system CPU uses Hyper-Threading Technology.

Most BIG-IP platforms support the HTSplit feature. However, you can use the following TMOS Shell (tmsh) command to determine if your platform supports the HTSplit feature:

tmsh show sys tmm-info | grep Sys::TMM

If your BIG-IP platform supports HTSplit and the feature is enabled, the output of the command appears similar to the following example, displaying even-numbered hyper-threads per TMM instance:

Sys::TMM: 0.0
Sys::TMM: 0.2
Sys::TMM: 0.4
Sys::TMM: 0.6

If your BIG-IP platform does not support HTSplit or the feature is disabled, the output of the command appears similar to the following example, displaying even- and odd-numbered hyper-threads per TMM instance:

Sys::TMM: 0.0
Sys::TMM: 0.1
Sys::TMM: 0.2
Sys::TMM: 0.3
Sys::TMM: 0.4
Sys::TMM: 0.5
Sys::TMM: 0.6
Sys::TMM: 0.7

Note: Virtual Clustered Multiprocessing (vCMP) guests support the HTSplit feature; however, the BIG-IP VE system does not support the feature running on generic hypervisors such as VMware ESX/i. BIG-IP Platforms such as the r2000 and r4000 by default do not support HTSplit. Fix for ID1574521/ID1575093 implements a software based HTSplit at the cost of throughput.

Recommendations

F5 recommends that you leave the HTSplit feature enabled, allowing the BIG-IP system to efficiently manage data and control plane tasks to improve performance.

Note: The HTSplit feature is enabled by default if your BIG-IP platform supports even-numbered hyper-threads.
