K14750: The BIG-IP GTM BIND does not accept non-secure transfer for a secondary zone configured with default key_id

Source

Issue

Old Behavior

In versions prior to BIG-IP GTM 10.2.4, the BIG-IP GTM BIND accepts a non-secure zone transfer for a secondary zone that is configured with either the default value key_id or an empty value for the Transaction Signature (TSIG) key parameter in the masters clause.

Note: When the BIG-IP GTM system receives a request for an unsecure zone transfer, the system accepts the zone transfer and reports an error message to the /var/log/daemon.log file. The error message appears similar to the following example:

general: error: zone <DNS zone name>/IN/external: unable to find key: key_id

By default, the BIG-IP GTM BIND automatically includes the default key value key_id in the masters clause whenever a secondary zone is created using the BIG-IP GTM ZoneRunner. The following example zone configuration stanza shows the masters clause that includes the key parameter with the default value of key_id:

masters {
<master IP address> port 53 key key_id;
};

New Behavior

Beginning in BIG-IP GTM 10.2.4, the BIG-IP GTM BIND no longer accepts a non-secure zone transfer for a secondary zone that is configured with either the default value key_id or an empty value for the TSIG key parameter.

Note: When the BIG-IP GTM system receives a request for an unsecure zone transfer, the system rejects the zone transfer and reports the above error message to the /var/log/daemon.log file.

This behavior is by design to prevent an improper usage involving the key parameter in the masters clause. If a secondary zone is configured to accept secure zone transfer using the TSIG protocol, then the correct TSIG key must be included. If a secondary zone is configured to accept non-secure zone transfer, then the key clause must be removed from the configuration.

Impact

  • For BIG-IP GTM systems upgraded from versions prior to 10.2.4 to BIG-IP GTM 10.2.4 and later, a secondary zone that has the key_id in its configuration will experience zone transfer failures after the upgrade.
  • For BIG-IP GTM 10.2.4 and later, a new secondary zone that is created using the BIG-IP GTM ZoneRunner will experience zone transfer failures by default.

Recommended Actions

  • If the secondary zone is supposed to accept a non-secure zone transfer, you must remove the key parameter from the masters clause for the affected secondary zone.
  • If the secondary zone is supposed to accept a secure zone transfer, you must replace the key value key_id with the appropriate TSIG key.
