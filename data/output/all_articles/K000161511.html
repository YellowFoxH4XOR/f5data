  • F5OS-C: 1.6.X, 1.8.X, 1.8.2, 1.8.1, 1.8.0, 1.6.4, 1.6.2, 1.6.1, 1.6.0

Description

A VELOS system partition may enter a failed state and is unable to recover across reboots due to XFS filesystem corruption on the partition configuration logical volume. The affected controller repeatedly fails to mount the partition LVs, causing a cascade of daemon failures and ultimately transitioning the partition to a failed state.

Symptoms include:

  • Partition shown in failed state via show partitions on the system controller CLI
  • ConfD fails to connect; multiple daemons are killed
  • XFS corruption errors repeating approximately every 60–65 seconds in /var/log/messages:
kernel: XFS (dm-X): Metadata corruption detected at xfs_inode_buf_verify
kernel: XFS (dm-X): Unmount and run xfs_repair
kernel: XFS (dm-X): metadata I/O error in "xlog_recover_do..(read#2)" at daddr 0x10be0c0 len 32 error 117
kernel: XFS (dm-X): log mount/recovery failed: error -117
kernel: XFS (dm-X): log mount failed

For example in messages log:

messages:May 29 03:19:57 controller-1 kernel: XFS (dm-2): Metadata corruption detected at xfs_inode_buf_verify+0x169/0x180 [xfs], xfs_inode block 0x10be0c0 xfs_inode_buf_verify
  • Mount failure on /var/F5/partition1:

mount /dev/mapper/partition_config-partition1 on /var/F5/partition1 failed: Structure needs cleaning

  • Docker/container errors in logs:
    • dockerd: No such container: part_1_part_vers_[version]_vers
    • dockerd: No such image: part_1_part_vers_[version]_vers
    • dockerd: get partition1-gui-volume: no such volume
    • dockerd: get tmstat1: no such volume
    • dockerd: network partition-net1 not found

For example in messages log:

messages.1:May 27 06:03:03 controller-1 dockerd-current: time="2026-05-27T06:03:03.273490233+01:00" level=error msg="Handler for GET /v1.26/containers/part_1_part_vers_1.6.4-44800_vers/json returned error: No such container: part_1_part_vers_1.6.4-44800_vers"

messages:May 29 03:10:59 controller-1 dockerd-current: time="2026-05-29T03:10:59.645360165+01:00" level=error msg="Handler for GET /v1.26/images/part_1_part_vers_1.6.4-44800_vers/json returned error: No such image: part_1_part_vers_1.6.4-44800_vers"

messages:May 29 03:10:18 controller-1 dockerd-current: time="2026-05-29T03:10:18.526183346+01:00" level=error msg="Handler for GET /v1.24/volumes/partition1-gui-volume returned error: get partition1-gui-volume: no such volume"

messages:May 29 03:10:40 controller-1 dockerd-current: time="2026-05-29T03:10:40.571771355+01:00" level=error msg="Handler for GET /v1.26/volumes/part_1_part_vers_1.6.4-44800_vers returned error: get part_1_part_vers_1.6.4-44800_vers: no such volume"

 

  • Partition LVs absent from df output - failed to mount
  • The same corrupted block address (eg, 0x10be0c0 above) appears consistently across all reboots (device node may change due to LVM re-enumeration). For example
May 24 03:06:15 controller-1 kernel: XFS (dm-8): Metadata corruption detected at xfs_inode_buf_verify
May 24 03:06:15 controller-1 kernel: XFS (dm-8): Unmount and run xfs_repair
May 24 03:06:15 controller-1 kernel: XFS (dm-8): metadata I/O error in "xlog_recover_do..(read#2)" at daddr 0x10be0c0 len 32 error 117
May 24 03:06:15 controller-1 kernel: XFS (dm-8): log mount/recovery failed: error -117
May 24 03:06:15 controller-1 kernel: XFS (dm-8): log mount failed

 

  • The redundant controller remains unaffected and holds the running-active role — no service impact, but redundancy is lost

Environment

  • Platform: F5 VELOS
  • Software: F5OS-C (Chassis)
  • Component: System controller (one affected, one unaffected)
  • Filesystem: XFS on LVM logical volume
  • Condition: XFS log corruption present on the partition configuration LV, triggered/exposed upon controller reboot when the volume is remounted from scratch
  • History: Corruption may be latent — present before the triggering reboot but not visible while the volume remained continuously mounted; exposed only when a remount is attempted after an unclean shutdown

Cause

XFS log corruption on the partition configuration logical volume, most likely caused by an unclean/unsafe shutdown of the system controller. Evidence includes:

  • wtmp records showing a reboot event with no preceding clean shutdown entry
  • NVMe SMART data reporting unsafe shutdowns
  • The corruption was latent while the volume stayed mounted; it became visible only after a controller reboot forced a fresh mount attempt, at which point XFS detected the corrupted log and refused to mount

Answer/Recommended Actions

First step is to attempt a recovery of the file system via xfs_repair.

If unsuccessful, then you may need to run xfs_repair -L, which forces the filesystem log (journal) to be zeroed and erased. It is used as a last resort when the journal is severely corrupted and prevents the filesystem from mounting, or when xfs_repair itself fails to proceed because it cannot replay a dirty log

This should allow the affected controller to mount successfully with a clean log and won't need to replay any journal entries, eliminating the 0x10be0c0 read during log recovery.  

Important: Using xfs_repair -L clears the filesystem log and may result in metadata loss; in some cases, files or directories that cannot be reconnected to their original location may be recovered as orphaned inodes and placed in the lost+found directory, potentially requiring manual inspection and restoration. If in doubt please contact F5 Support.

Important: This procedure requires a maintenance window (estimated 15–30 minutes of partition downtime). A partition configuration backup and ISO images should be taken beforehand if possible. xfs_repair recovers metadata and is non-destructive to data.

Pre-checks (no impact):

  • Take a partition configuration backup:

    syscon-2-active# config
    syscon-2-active(config)# system database config-backup name pre-xfs-repair-backup
    syscon-2-active(config)# exit

    Download the backup to a local computer.


Disable the partition (downtime begins):

  • Disable the affected partition:

    syscon-2-active(config)# partitions partition <partition-name> config disabled
    syscon-2-active(config)# commit

  • Wait until the partition is fully stopped on both controllers:

    syscon-2-active# show partitions

    The partition should show disabled on both controllers.

Unmount the partition LVs:

  • SSH to the affected controller bash shell and verify mount status:

    $ mount | grep partition1

  • If any mounts remain, unmount in this order:

    $ umount /var/F5/partition1/shared
    $ umount /var/F5/partition1/IMAGES
    $ umount /var/F5/partition1

  • Confirm no mounts remain:

    $ mount | grep partition1

    Expected: no output.

Run xfs_repair:

  • Execute the repair on the unmounted logical volume:

    $ xfs_repair /dev/partition_config/partition1

    • Capture and save the full output for records.
    • A successful run completes all 7 phases and ends with:

    Phase 7 - verify and correct link counts... done

    • If the tool reports the filesystem is still dirty or exits with errors, do not proceed. Escalate to F5 Support immediately.


Reboot the affected controller only:

  • Reboot the affected controller to force a fresh mount attempt on the repaired volume:

    # system reboot controllers controller standby

    (Verify standby status with show partitions before rebooting.)

Verify recovery:

  • Check partition state:

    # show partitions

    Expected:

    running-active
    running-standby

  • Verify no XFS errors in logs:

    $ egrep -i "xfs" /var/log/messages | tail -20

    Expected: clean mount messages with no corruption errors.

  • Collect a new qkview for verification once recovery is confirmed.

 

Re-enable partition if it is still disabled

syscon-2-active(config)# partitions partition <partition-name> config enabled
syscon-2-active(config)# commit

 

If recovery fails:

If XFS errors persist after repair and reboot, the logical volume may have unrecoverable corruption. Proceed with next steps of zeroing out the XFS log:

 

Next steps:

 

  • Follow through as above with ensuring the partition is disabled and unmounted. 

  • Run xfs_repair via the affected controller:

   $ xfs_repair -L /dev/mapper/partition_config/partition1

  • Reboot the affected controller only. 

Verify recovery:

 

  • Check partition state:

   syscon-2-active# show partitions

       Expected:

   running-active
   running-standby

  •  Verify no XFS errors in logs:

   $ egrep -i "xfs" /var/log/messages | tail -20
   
   Expected: clean mount messages with no corruption errors.

 

 

Additional Information

  • The XFS corruption is confined to the affected controller's logical volume. The redundant controller is unaffected, so there is no traffic/service impact — only redundancy is lost while the issue persists.
  • The corrupted block address remains consistent across all reboots; only the device node changes due to LVM re-enumeration after each reboot.
  • The corruption pattern — latent while the volume is continuously mounted, exposed only on remount — is characteristic of XFS log corruption caused by an unclean shutdown.
  • xfs_repair must be run while the target volume is unmounted and not actively attempting to remount. Running it against a mounted or actively-remounting volume will fail.
  • NVMe SMART data (unsafe_shutdowns counter) can be used as supporting evidence to identify whether unclean shutdowns have occurred during the device's lifetime.
