K36082029: Performing mTLS using istio ingress-gateway in Aspen Mesh

Type
Support Solution
Published
2022-02-07
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K36082029

Description

By default, mTLS is enabled when Aspen Mesh is installed. That means every workload will be secured between each of them. You could also have an ingress-gateway which is a standalone proxy that could be used as an ingress controller. There are other examples and use cases for the ingress-gateway explained in detail in the article K94561586: Exposing a service over SIMPLE TLS using Istio ingress gateway in Aspen Mesh. If you want to have also mTLS between the sidecar and the istio ingress-gateway this article will cover this specific use case.

Environment

  • Kubernetes: 1.17x, 1.18.x, 1.19.x, 1.20.x
  • Aspen Mesh: 1.6.x, 1.9.x

Cause

If you want to enforce communications between your workloads and even between namespaces we could have different options to achieve that like Calico Network Policies and Istio Authorization Policies.

On top of that, secure communications on workloads and only have one point of ingress and egress could be achieved with an istio ingress-gateway.

The use case can be illustrated as follow:

namespace foo                     namespace bar
Pod a    =====>   istio gw   =====>   Pod b  
     (istio gw can be in istio-system
      or Another namespace)
            [ mTLS protected ]

Recommended Actions

  • Prerequisites
  • Configure Destination Rule, Gateway and Virtual Service
  • Verify

Prerequisites

  • You must have an ingress-gateway installed either in root namespace for istio which is istio-system or your own namespace.
  • If you do not have an ingress-gateway follow the article K50557252: Install Istio Ingress Gateway using the Aspen Mesh Ingress Helm Chart.
  • If you plan to use a different port than the default, accommodate your values file before the installation.

Configure Destination Rule, Gateway and Virtual service

First, use a few istio objects that will help us to define what kind of TLS our client will initiate against our server. Then a gateway and a virtual service for routing the traffic.

  1. Destination Rule:

    Our host for the destination rule is our ingress-gateway service, we are using the local service in Kubernetes to reach the endpoint from the other container.

    The TLS mode as expected is ISTIO_MUTUAL which is mTLS but we do not have to provide the certificate and the key, the sidecar will do in our behalf.

    SNI here is required as the proxy will perform SNI matching before forwarding the request.

    apiVersion: networking.istio.io/v1beta1
    kind: DestinationRule
    metadata:
      name: httpbin-mtls-ext
      namespace: foo
    spec:
      host: istio-ingressgateway.istio-system.svc.cluster.local
      trafficPolicy:
        tls:
          mode: ISTIO_MUTUAL
          sni: httpbin.example.com 

  2. Gateway:

    Our gateway will create a specification on which istio ingress-gateway will use and tell which ports should be exposed. 

    In this example, we are using a different port from the default, but you could use 443 as well but the protocol must be HTTPS.

    As you can see, we are setting the same TLS mode as the Destination Rule this is how we enforce the TLS in the proxy. 

    apiVersion: networking.istio.io/v1beta1
    kind: Gateway
    metadata:
      name: httpbin-gw
      namespace: foo
    spec:
      selector:
        istio: ingressgateway
      servers:
      - hosts:
        - httpbin.example.com
        port:
          name: https-9896
          number: 9896
          protocol: HTTPS
        tls:
          mode: ISTIO_MUTUAL

  3. Virtual Service:

    Finally, we have a virtual service which will create a virtual destination in the routing of the ingress-gateway

    Once match on the URI in this case the path /headers is hit, then all the traffic will be redirected to the pod in namespace bar which is our httpbin server.

    apiVersion: networking.istio.io/v1beta1
    kind: VirtualService
    metadata:
      name: httpbin-vs
      namespace: foo
    spec:
      gateways:
      - httpbin-gw
      hosts:
      - httpbin.example.com
      http:
      - match:
        - uri:
            exact: /headers
        route:
        - destination:
            host: httpbin.bar.svc.cluster.local
            port:
              number: 8000
