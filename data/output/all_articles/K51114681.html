Known Issue

The HTTP or HTTPS monitor may erroneously send extra data strings after completing a TCP or SSL handshake.

This issue occurs when all of the following conditions are met:

  • You have a HTTP or HTTPS monitor with the send attribute set to none.

    For example, the output of the HTTP monitor may appear similar to the following example:

    ltm monitor http http_test {
    adaptive disabled
    defaults-from http
    destination *:*
    interval 5
    ip-dscp 0
    recv none
    recv-disable none
    send none
    time-until-up 0
    timeout 16
    }

  • You apply the monitor to a pool member or node.

With the send attribute set to none, the BIG-IP system should update the status of the pool member or node based on the result of the TCP or SSL handshake. It should then close the connection without sending any further data.

Impact

The health monitor may erroneously mark the monitored pool member or node down. As a result, client requests are not sent to the affected pool member or node.

Symptoms

As a result of this issue, you may encounter all of the following symptoms:

  • The network capture shows the BIG-IP system sending an extra 4-byte string (\r\n\r\n) after completing a TCP or SSL handshake. This unexpected data causes the system to reset the health monitor connection.
  • You notice that the health monitor incorrectly marks the pool member or node down.
