Description

You can find here techniques for troubleshooting iQuery connectivity more specific and advanced than section Troubleshooting iQuery connectivity of K13690: Troubleshooting BIG-IP DNS synchronization and iQuery connections.

Environment

  • BIG-IP DNS iQuery group 

Cause
iQuery handshakes seen failing. The most common causes include:

  • New deployment, device certificates not installed
  • Connectivity problems due to the network environment
  • Device certificates lost or expired

Recommended Actions

  • You must have the privilege to access bash CLI
  • You must be familiar with your network topology and know the addresses assigned to your iQuery member devices
  1. Confirming the underlying connectivity

    Run the below bash CLI command

    netstat -na | grep 4353

    The outputs are expected similar to:

    tcp        0      0 ::ffff:192.0.2.2:4353  ::ffff:192.0.2.4:58009 ESTABLISHED

    tcp        0      0 ::ffff:192.0.2.2:46002 ::ffff:192.0.2.4:4353  ESTABLISHED

  2. Making sure that the certificates are present

    During each iQuery handshake the peers exchange their device certificates/certificate chains. Depending on which side initiated the handshake the same device certificate/certificate chain will be used as the SSL/TLS client or the SSL/TLS server. The trusted certificates are stored in PEM format in files /config/big3d/client.crt and /config/gtm/server.crt
    Utility bigip_add usually does help to install copies of the certificates in these two files. Yet, while troubleshooting it needs to be confirmed.

    Illustrated below are two certificates from different devices. Their first lines are identical, cannot be used for confirming whether a certain certificate is present or absent from /config/big3d/client.crt and /config/gtm/server.crt

      • Ensure certificates do not produce conflicts or collisions

        Quoting here K6353: Updating a self-signed SSL device certificate on a BIG-IP system:

        Important: F5 recommends that you configure a unique Common Name for each BIG-IP DNS synchronization group member. If this is not possible, you must have at least one other field (typically Division) with a unique value for each BIG-IP DNS system in a synchronization group to prevent synchronization issues.

        The attributes of the certificates need to be unique so, that a lookup through /config/big3d/client.crt or /config/gtm/server.crt does not return a wrong certificate resulting in a mismatch failure
         
      • Inside the handshake
         
        1. The SSL server side must send its certificate to the SSL client for validation
          • A - If the TCP handshake completes successfully, but the SSL server does not send its certificate, then contact F5 Support to troubleshoot the condition further
          • B - If the SSL server does send its certificate, but the client responds with an SSL alert closing the SSL session, then check the alert diagnostic message
            • If the message reads "Unsupported Certificate", then verify the purpose of the certificate as explained at https://my.f5.com/manage/s/article/K7717
            • If the message reads "CA Unknown", then the client appears missing the certificate of the peer. Make sure that the certificate seen in the packet trace is included both in /config/gtm/server.crt and in /config/big3d/client.crt
               
        2. Then the SSL client side must send its certificate to the SSL server for validation
          • A - If the SSL client does not send its certificate, then contact F5 Support to troubleshoot the condition further
          • B - If the SSL client does send its certificate, but the server responds with an SSL alert closing the SSL session, then check the alert diagnostic message. If the message reads "Unsupported Certificate", then verify the purpose of the certificate as explained in K7717: BIG-IP DNS and Link Controller support for third-party SSL device certificates
          • C - If the message reads "CA Unknown", then the server appears missing the certificate of the peer. Make sure that the certificate seen in the packet trace is included both in /config/gtm/server.crt and in /config/big3d/client.crt
        3. Each member of DNS sync group must have one incoming iQuery session to its port 4353 from each member having DNS provisioned. Each member of DNS sync group having DNS provisioned must have one outgoing iQuery session to TCP port 4353 of each member of the sync group
