Description

Configured HA order can be ignored when adding/deleting device member from the Device Group causing any device member to be active in the cluster.

Environment

  • HA order
  • Device Group
  • Failover

Cause

Behaviour as per design

Answer/Recommended Actions

Whenever device gets added or deleted from the Device Group, CRC in that local device from where the change is done will be different from all other devices in the cluster. This CRC information is transferred to other devices in the cluster using failover unicast packets using UDP every 100ms. But this change in the config will be transferred to other devices in the cluster using prebuilt automatic sync enabled device-group 'device_trust_group' which uses TCP port 4343 config sync so now there is a race condition between UDP failover unicast packets and config sync TCP packets and config sync gets behind in this race to sync the config to other device which already knows that CRC has been changed.

Scenario 1:

bigip1 and bigip2 is in cluster with HA order configured with order of bigip1 and then bigip2.

If  'bigip3' is added without 'FORCED OFFLINE' to the sync failover cluster then, HA order list does not sync because of manual sync so CRC mismatch will happen in 'bigip3' and it might be active due to high TG score and CRC mismatch and HA order will be ignored.

Note: HA order list config has to be manually synced to newly added device. Always make new device FORCED OFFLINE when adding to the cluster.

Scenario 2:

bigip1, bigip2 and bigip3 is in cluster with HA order configured with order of bigip1 then bigip2 then bigip3.

If 'bigip3' is removed from the sync failover device group from the GUI/CLI console of 'bigip2' then this change is auto synced to both peers using DG 'device_trust_group' and CRC re-calculates in both devices 'bigip1' and 'bigip2' but still 'bigip2' TG score wins due to CRC mismatch because CRC agreement between peers 'bigip1' and 'bigip2' lags behind failover unicast packets exchange with 'bigip2' as high TG score and before CRC agreement happens, high TG score wins and 'bigip2' becomes Active.

Additional Information

F5 has raised RFE ID 2046581 for this feature enhancement.
