Topic

The FFP.UDP.PortOverrideList bigpipe db variable was introduced in BIG-IP version 10.1.0 to control how the BIG-IP system hashes and distributes UDP connections among TMM instances.

Note: Although the variable shows on all units running BIG-IP version 10.1.0 or later, only the BIG-IP 6900 and 8900 platforms currently utilize this variable.

In software versions prior to 10.1.0, the BIG-IP system only distributed connections (both TCP and UDP) among TMM instances based on a hash of the source and destinations ports (L4 information).

For example:

                Client           Virtual Server
Connection 1 -- 1.1.1.1:10366 -> 20.20.20.20:80 ---> TMM0
Connection 2 -- 2.2.2.2:31200 -> 20.20.20.20:80 ---> TMM1
Connection 3 -- 3.3.3.3:23881 -> 20.20.20.20:80 ---> TMM2
Connection 4 -- 4.4.4.4:42999 -> 20.20.20.20:80 ---> TMM3

This distribution mechanism generally works well and results in the connections divided equally between all TMM instances. However, it does not work well when a virtual server handles traffic that uses the same source and destination ports.

For example:

                Client          Virtual Server
Connection 1 -- 1.1.1.1:5000 -> 20.20.20.20:5000 ---> TMM0
Connection 2 -- 2.2.2.2:5000 -> 20.20.20.20:5000 ---> TMM0
Connection 3 -- 3.3.3.3:5000 -> 20.20.20.20:5000 ---> TMM0
Connection 4 -- 4.4.4.4:5000 -> 20.20.20.20:5000 ---> TMM0

This type of traffic causes the hash to degenerate and always choose the same TMM instance, thus not utilizing the resources of the system efficiently. For this reason, F5 Networks Product Development introduced an alternative distribution mechanism based on a hash of the source and destination IP addresses (L3 information).

Note: Currently only UDP connections may be distributed among TMM instances using L3 information.

F5 Networks Product Development is tracking this enhancement request as CR127636.

Modifying the FFP.UDP.PortOverrideList bigpipe db variable

Important: Situations that would benefit from distributing connections using L3 information are limited. Modify the value of this variable only if instructed to do so by F5 Networks Technical Support.

You can control whether UDP connections are distributed among TMM instances using L3 or L4 information by modifying the value of the FFP.UDP.PortOverrideList bigpipe db variable. Refer to the following table for a list of all possible values:

Important: Before setting the FFP.UDP.PortOverrideList bigpipe db variable to all, refer to K11844: Setting the FFP.UDP.PortOverrideList bigpipe variable to 'all' on a 6900 or 8900 platform may cause TMM to crash.
 

ValueExplanation
0The L4 hash is applied to all UDP connections (this is the default value).
allThe L3 hash is applied to all UDP connections.
A port number, for example 5000The L3 hash is applied only to those UDP connections whose source and destination ports match the specified port.
A list of port numbers delimited by a comma, for example 5000,5001,5002The L3 hash is applied only to those UDP connections whose source and destination ports match a port in the specified list.

To modify the value of the FFP.UDP.PortOverrideList bigpipe db variable, run the following command from the command line:

bigpipe db FFP.UDP.PortOverrideList ( 0 | all | <port> | <port1,port2,..portn> )

Limitations of connections distributed using L3 information

Distributing connections among TMM instances using L4 information is advisable in almost all cases. The BIG-IP system opens a server-side connection to a pool member, and attempts to use the same source port that was used by the client. This behavior ensures that the return traffic from the server hashes to the same TMM instance as the client-side.

For example:

        Client-side                                    Server-side
5.5.5.5:15189 -> 20.20.20.20:80 ---> TMM0 ---> 5.5.5.5:15189 -> 10.0.0.10:80
5.5.5.5:15189 <- 20.20.20.20:80 <--- TMM0 <--- 5.5.5.5:15189 <- 10.0.0.10:80

When the BIG-IP system opens a server-side connection to a pool member, at least one IP address will change: the destination IP address. Therefore, when hashing on L3 information, the hash from the client to the virtual server and the hash from the pool member to the client will likely result in a different TMM instance being selected for each direction.

For example:

        Client-side                                    Server-side
6.6.6.6:5000 -> 20.20.20.20:5000 ---> TMM0 ---> 6.6.6.6:5000 -> 10.0.0.10:5000
                                      TMM3 <--- 6.6.6.6:5000 <- 10.0.0.10:5000

Because the return traffic hits a different TMM instance, the traffic will not match an existing connection flow. As a result, the BIG-IP system will either drop the return traffic, or if the traffic is accepted due to the existence of a forwarding mechanism, the source IP address of the pool member will not be translated back to that of the virtual server. Therefore, when hashing using L3 information, in order for the connections not to fail, the return traffic needs to perform one of the following actions:

  • Bypass the BIG-IP system and have another device translate the source IP address back to that of the virtual server
  • Return to the BIG-IP system, but have an object such as a SNAT translate the source IP address back to that of the virtual server
