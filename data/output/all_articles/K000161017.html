Description

Application users report intermittent or consistent delays when accessing services through a BIG-IP LTM virtual server. The delay may occur during connection establishment, server response, data transfer, or application processing.

Environment

  • LTM
  • Client and server traffic passing through BIG-IP

Cause

Application latency can originate from multiple points in the traffic flow, including:

- Client-side network latency
- BIG-IP processing delays
- SSL processing on BIG-IP
- iRules or Local Traffic Policies introducing additional processing time
- Server-side application processing delays
- Network congestion or packet loss
- TCP retransmissions
- Delayed server responses
- Backend infrastructure performance issues

Answer/Recommended Actions

Packet captures performed on BIG-IP can help determine where the delay is introduced within the client-side, BIG-IP, or server-side traffic flow.

1. Review Interface and Drop Counters:

tmsh show net interface -hidden

Look for Drops, Errors, or hardware buffer exhaustion.

2. Capture traffic on BIG-IP during the issue occurrence for a few minutes.

Example: (If client-side IP is not available, use the VIP IP address instead)

tcpdump -s0 -ni 0.0:nnnp -w /var/tmp/delay.pcap "host <client_ip> or host <pool_member_ip>"

Press Ctrl + C to stop capture

Note: If you have a huge amount of traffic, add  -W 4 -C 100 to the tcpdump command to run it in a safe ring buffer 

3. Open the packet capture in Wireshark, and apply the following display filters one by one:

- Identify large packet gaps / possible connection or processing delays. Check the packet direction and Source/Destination IPs to determine where the delay occurred.

tcp.time_delta > 1 

- Identify TCP connections with an initial RTT greater than 200 ms.

tcp.flags.syn == 1 && tcp.analysis.initial_rtt > 0.2

- Identify TCP ACK RTTs greater than 200 ms, which can indicate network latency.

tcp.analysis.ack_rtt > 0.2   

- Identify delays greater than 200 ms during the TLS handshake. 

tls.handshake and tcp.time_delta > 0.2   

- Identify HTTP transactions taking more than 500 ms, which may indicate backend/application processing delay.

http.time > 0.5   

Note: For HTTP filtering, if the traffic is encrypted, you need to decrypt it; please follow the steps in the KB K31793632: Creating a decrypted tcpdump capture without using an iRule

4. Review packets with large time gaps to identify where the delay occurs between:

- Client and BIG-IP
- BIG-IP and server
- Server response back to BIG-IP
