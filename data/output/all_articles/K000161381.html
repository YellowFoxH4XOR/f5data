K000161381: Duplicate nginx_uid Persists on Cloned NGINX Plus Images Due to Shell Glob Expansion Failure When Deleting State File

Type
Support Solution
Published
2026-07-16
Updated
2026-07-22
Applies to
  • NGINX Products
  • NGINX One Console
Source
https://my.f5.com/manage/s/article/K000161381

Description

  • You have NGINX Plus instances that were deployed from a cloned image, such as an AWS AMI or VM template, resulting in all instances sharing the same nginx_uid.
  • You attempt to regenerate the nginx_uid by following these steps:
    1. Stop the NGINX service: sudo systemctl stop nginx
    2. Delete the state file: sudo rm -rf /var/lib/nginx/state/*
    3. Restart the NGINX service: sudo systemctl start nginx
  • However, after restarting, the nginx_uid remains unchanged — the same UID is still present in /var/lib/nginx/state/nginx-mgmt-state.

 

      Environment

      NGINX instances deployed on AWS from a shared AMI

      NGINX Plus with NGINX Agent installed.

       

      Cause

      The failure to regenerate nginx_uid was due to shell glob expansion failure caused by directory permissions. When the command "sudo rm -rf /var/lib/nginx/state/*" is used, glob expansion (the process where the shell converts wildcard patterns into a list of matching filenames) occurs before sudo elevation, using the logged-in user's permissions. If the user lacks read permission on /var/lib/nginx/state/, the wildcard is not expanded, and the file remains present, causing the UID to persist across restarts.

       

      Answer/Recommended Actions

      To reliably regenerate the nginx_uid and prevent duplication when using cloned images:

      1. Check the current UID: 

      sudo cat /var/lib/nginx/state/nginx-mgmt-state

      2. Check running processes: 

      ps aux | grep nginx

      3. Stop NIGNX service: 

      sudo systemctl stop nginx

      4. Verify no NGINX proces remain: 

      ps aux | grep nginx

      5. Confirm the state file exists: 

      sudo ls -l /var/lib/nginx/state/

      6. Explicitly delete the state file using the full path:

      sudo rm /var/lib/nginx/state/nginx-mgmt-state

      7. Confirm the directory is empty: 

      sudo ls -l /var/lib/nginx/state/

      8. Start NGINX service: 

      sudo systemctl start nginx

      9. Verify a new UID was generated: 

      sudo cat /var/lib/nginx/state/nginx-mgmt-state

       

      Additional Information

      • Note: Using a wildcard (*) in the deletion command may fail if the user does not have read permissions on the directory.  
        sudo rm -rf /var/lib/nginx/state/*

        Always use the explicit file path.

      • To prevent UID duplication when deploying NGINX Plus from a cloned image:
        • The only thing you need to take into account when creating cloned images is: If there is an existing /var/lib/nginx/state/nginx-mgmt-state file, you should remove it before capturing the image.
        • Alternatively, you can clone the image before starting the NGINX service, which prevents the nginx-mgmt-state file from being created. When you then start each instance for the first time, NGINX Plus will generate a unique nginx_uid for each system.
