You configure the Redundancy State Preference setting in a BIG-IP high availability pair to control which unit you want to be active when both units are online and capable of assuming the active role. You can specify a preference or let the BIG-IP units handle their status autonomously.

Available states

You can assign the Redundancy State Preference setting with one of the following values:

  • Active

    This setting specifies that the unit is the preferred active unit. If you choose this option, the unit can go standby due to a failover event. Failback to this unit is automatic when the unit becomes available again.
  • Standby

    This setting specifies that the unit is the preferred standby unit. If you choose this option, the unit can go active due to a failover condition. Failback to the peer unit is automatic when the peer unit becomes available again.
  • None

    This setting specifies that the unit does not have a preferred redundancy state. This is the default value on both units of a BIG-IP redundant pair. For example, if unit1 goes down and unit2 assumes control, when unit1 is back online and they are both able to serve traffic correctly, the units will not swap roles. Unit2 will remain active, and unit1 will remain standby.

    Note:  F5 recommends the None setting, as it gives you time to investigate why the primary unit failed over, and to assess whether this may happen again. If you select None, you can avoid further failovers if unit1 runs into the same issue multiple times.

Configuring the Redundancy State Preference setting from the Configuration utility

Important: When changing the Redundancy State Preference setting of one unit, you must also change the setting on the peer unit. It is important that you either specify None on both units, or Active on one unit and Standby on its peer.

To configure the members of a redundant pair so they default to an active or standby state, perform the following procedure:

  1. Log in to the Configuration utility of the standby system.
  2. Click System.
  3. Click High Availability.
  4. Select Standby from the Redundancy State Preference drop-down menu.
  5. Click Update.
  6. Log in to the Configuration utility of the active system.
  7. Click System.
  8. Click High Availability.
  9. Select Active from the Redundancy State Preference drop-down menu.
  10. Click Update.

Configuring the Redundancy State Preference setting from the command line interface

Important: When changing the Redundancy State Preference setting of one unit, you must also change the setting on the peer unit. It is important that you either specify None on both units, or Active on one unit and Standby on its peer.

The value of the Redundancy State Preference setting in the Configuration utility is directly linked to the value of the following two bigpipe database keys:

  • Failover.ForceActive = enable | disable
  • Failover.ForceStandby = enable | disable

If you change the Redundancy State Preference setting in the Configuration utility, the system automatically adjusts the database keys.

The following table describes how the Redundancy State Preference setting and the two database keys affect each other:

Value of the two bigpipe database keysValue of the Redundancy State Preference setting
Failover.ForceActive = enable
Failover.ForceStandby = disable		Active
Failover.ForceActive = disable
Failover.ForceStandby = enable		Standby
Failover.ForceActive = disable
Failover.ForceStandby = disable		None
Failover.ForceActive = enable
Failover.ForceStandby = enable		This configuration is not valid; the bigpipe utility will not allow you to enable both database keys on the same unit.

To configure the members of a redundant pair so they default to an active or standby state, perform the following procedure:

  1. Log in to the command line of the standby system.
  2. Enter the following commands:

    bigpipe db Failover.ForceActive disable
    bigpipe db Failover.ForceStandby enable
    bigpipe save all

  3. Log in to the command line of the active system.
  4. Enter the following commands:

    bigpipe db Failover.ForceStandby disable
    bigpipe db Failover.ForceActive enable
    bigpipe save all

VLAN failsafe considerations

Important: If you are using VLAN failsafe, use caution when configuring systems to be preferred active or standby. If the system you configured as the preferred active unit has an interface failure, or the switch it connects to has an interface failure, VLAN failsafe will reboot the system and the standby unit will take over. However, when the preferred active system comes back up, the preferred standby system will revert to standby, and VLAN failsafe will reboot the preferred active unit again since the interface will still be down. At this point, the preferred standby will take over again. This back and forth process will repeat indefinitely.

Recovering from an active-active situation

In a BIG-IP redundant pair (active/standby) where the Redundancy State Preference of its members is set to None, and network failover is used, if the high availability heartbeat communication is lost, both units will become active. As a result, an active-active situation occurs. When the units regain communication, the unit designated with an ID of 1 will become active, and the unit with an ID of 2 will become standby. This behavior is hardcoded and cannot be changed by a BIG-IP administrator.

During the transition from active-active to active/standby state, the unit with an ID of 1 will log one or more messages to the /var/log/ltm file that appear similar to the following example:

notice sod[1878]: 010c0025:5: Toggle from active to standby to active.

The unit with an ID of 2 will log a message that appears similar to the following example to the /var/log/ltm file, indicating that it is demoting its state to standby:

notice sod[14934]: 010c0018:5: Standby

This is the expected behavior when the members of a redundant pair do not have a preferred redundant state set.

Important: An active-active situation in an active/standby redundant pair is an undesired condition that will likely result in traffic disruption. F5 recommends that you have multiple network paths for the high-availability heartbeat.
