Description

BIG-IP DNS no longer responds to DNSSEC queries with a RRSIG record.

You can verify this by sending the query directly to the gtm listener IP address:

dig @<GTM_LISTENER_IP> +dnssec +multi example.com

Note that the following message is logged indicating that RRSIG was not added:

/var/log/ltm

warning tmm[23514]: 01010231:4: DNSSEC: Did not add RRSIGs to response RR set (owner: example.com).

Review the dnssec zsk key assigned to the DNSSEC zone to see if "generation" data is available. Lack of generation data means that the key has not been successfully generated/assigned. No "generation" data exists in the following example:

ltm dns dnssec key /Common/example.com_zsk {
    algorithm rsasha256
    bit-width 2048
    expiration-period 30:0:0:0
    rollover-period 20:0:0:0
    use-fips external
}

The failure to generate a new key on roll over is why BIG-IP is no longer responding with RRSIG record after the old key expires.

Environment

  • BIG-IP DNS
  • Thales netHSM
  • DNSSEC
  • 2000+ keys in /opt/nfast/kmdata/local/

Cause

ID807157

Recommended Actions

Key generation timeouts can occur if too many key generation requests happen at the same time.  For example if all the DNSSEC keys have the same roll-over period and are created at the same time.  Timeouts result in a failed key generation and redundant keys can accumulate in /opt/nfast/kmdata/local/ 

Having too many keys stored in /opt/nfast/kmdata/local/ can also increase the time it takes to generate a key so it is important to maintain the keys in /opt/nfast/kmdata/local/ by removing unused key files.

Use the following command to count the number of keys stored in /opt/nfast/kmdata/local/

ls /opt/nfast/kmdata/local/key_pkcs* | wc -l

For optimal performance, the number of keys should be maintained at less than 2000.

The following procedure can be used for a BIG-IP system which uses Thales netHSM solely to manage DNSSEC keys:
 

  1. Backup key files:
    mkdir /shared/tmp/kmdata_key_backup
    cp /opt/nfast/kmdata/local/key_pkcs* /shared/tmp/kmdata_key_backup
  2. List dnssec key handles to file:
    tmsh list ltm dns dnssec key| grep handle | awk '{print $2}' > /shared/tmp/key_handles
  3. List key file/key object to file:
    /opt/nfast/bin/nfkminfo -l > /shared/tmp/nfkminfol.txt
  4. Remove list of key_handles from nfkminfol.txt so you're left with a list of unused keys:
    for i in $(cat /shared/tmp/key_handles); do sed -i "/$i/d" /shared/tmp/nfkminfol.txt; done
  5. Check for any 'custom' keys you don't want to delete:
    Note: Custom keys refer to manually generated keys on BIG-IP for some purpose unknown to F5.  It is assumed the name of these keys do not contain _Common_
    grep -v "_Common_" /shared/tmp/nfkminfol.txt
    Manually remove these keys (if any) from /shared/tmp/nfkminfol.txt to avoid deletion
  6. Create unused key list:
    awk '{print $1}' /shared/tmp/nfkminfol.txt | grep key_pkcs > /shared/tmp/unused_keys
  7. Remove unused keys from /opt/nfast/kmdata/local/:
    Important: The following command will delete all the keys listed in /shared/tmp/unused_keys 
    for i in $(cat /shared/tmp/unused_keys); do rm -f /opt/nfast/kmdata/local/$i; done
  8. Regenerate new dnssec keys and apply to dnssec zones that are failing to respond with RRSIG
    Example:
    tmsh
    create ltm dns dnssec key example.com_zsk2 { algorithm rsasha256 bit-width 2048 expiration-period 30:0:0:0 rollover-period 20:0:0:0 use-fips external }
    modify ltm dns dnssec zone example.com keys replace-all-with { example.com_ksk1 example.com_zsk2 }



Additional Information

In order to avoid too many key generations to be simultaneously requested, consider staggering the rollover-period when creating multiple dnssec keys at the same time.

For Example:
