Topic

You should consider using this procedure under the following conditions:

  • You have a system with the BIG-APM module provisioned.
  • You have Oracle Access Manager resources configured.
  • Users are having difficulty connecting to Oracle Access Manager.

Description

The article provides the initial data-gathering steps that F5 Technical Support uses to identify potential causes of failure events when using Oracle Access Manager with the BIG-IP APM system. Connectivity problems may occur between the client and the BIG-IP APM system or between the BIG-IP APM system and Oracle Access Manager servers. To get a better understanding of the issue, you need to gather the appropriate data.

Note: To open support cases with F5 Technical Support, you must have an active support contract and be authorized to open cases. If you use an F5 product or client application, such as F5 Access for IOS or F5 Access for Android, and you require technical support, contact your system administrator or IT department for assistance.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have administrative access to the Configuration utility.
  • You have access to the BIG-IP Advanced shell (bash).
  • You have access to a test system experiencing issues connecting to Oracle Access Manager resources.

Procedures

Perform the following procedures to collect data required for troubleshooting Oracle Access Manager connectivity issues:

  • Enabling debug logging for an access policy
  • Increasing Oracle Access Manager logging on the BIG-IP APM system
  • Capturing BIG-IP APM logs while troubleshooting
  • Gathering an HTTPWatch capture

Enabling debug logging for an access policy

Enabling debug level logging on the BIG-IP APM system provides additional detail about failed authentication attempts. BIG-IP APM messages log to the /var/log/apm file.

Impact of procedure: Leaving debug logging enabled may generate excessive logging and cause poor performance. F5 recommends that you return the log level to the default value after you complete troubleshooting.

Enabling debug logging using the Configuration utility

  1. Log in to the BIG-IP Configuration utility.
  2. Navigate to System > Logs > Configuration > Options.
  3. Scroll down to the Access Policy Logging section and click Debug in the Access Policy list.
  4. Click Update.

Enabling Debug using the Traffic Management Shell (tmsh)

  1. Log in to tmsh by typing the following command:

    tmsh

  2. Set access policy logging level to debug by typing the following command:

    tmsh modify /sys db log.accesscontrol.level value debug

Disabling debug logging using the Configuration utility

  1. Log in to the BIG-IP Configuration utility.
  2. Navigate to System > Logs > Configuration > Options.
  3. Scroll down to the Access Policy Logging section and click Notice in the Access Policy list.
  4. Click Update.

Disabling debug logging using tmsh

  1. Log in to tmsh by typing the following command:

    tmsh

  2. Restore the access policy logging to the default level (notice) by typing the following command:

    tmsh modify /sys db log.accesscontrol.level reset-to-default

Increasing Oracle Access Management logging on the BIG-IP APM system

Impact of procedure: Leaving debug logging enabled may generate excessive logging and cause poor performance. F5 recommends that you return the log level to the default value after you complete troubleshooting.

  1. Log in to bash.
  2. Open the oblog_config.xml file for editing using a utility such as vi. Use the following path syntax to open the file:

    /config/aaa/oam/<partitionname>/<oamserver>/<accessgate>/oblix/config/oblog_config.xml

  3. In the file, locate the following stanza:

    <!-- Write all FATAL logs to the system logger. -->
    <ValNameList xmlns="http://www.oblix.com" ListName="LogFatal2Sys">
        <NameValPair ParamName="LOG_LEVEL" Value=" LOGLEVEL_FATAL" />
        <NameValPair ParamName="LOG_WRITER" Value="SysLogWriter" />
        <NameValPair ParamName="LOG_STATUS" Value="On" />
    </ValNameList>

  4. Change the value for LOG_LEVEL from LOGLEVEL_FATAL to LOGLEVEL_DEBUG3: so that the stanza appears as follows:

    <!-- Write all FATAL logs to the system logger. -->
    <ValNameList xmlns="http://www.oblix.com" ListName="LogFatal2Sys">
        <NameValPair ParamName="LOG_LEVEL" Value="LOGLEVEL_DEBUG3" />
        <NameValPair ParamName="LOG_WRITER" Value="SysLogWriter" />
        <NameValPair ParamName="LOG_STATUS" Value="On" />
    </ValNameList>

  5. Save the changes to the oblog_confg.xml file.

To reset the Oracle Access Management logging level to the default value (LOGLEVEL_FATAL), repeat steps 1 through 3 in the previous procedure. For step 4, change the LOG_LEVEL from LOGLEVEL_DEBUG3 back to LOGLEVEL_FATAL, then save the file.

Capturing BIG-IP APM logs while troubleshooting

Impact of procedure: Leaving debug logging enabled may generate excessive logging and cause poor performance. F5 recommends that you return the log level to the default value after you complete troubleshooting.

  1. Log in to bash.
  2. To tail the logs to the /var/log/<case_number>-apm.txt file, type the following command syntax:

    Note: Include the F5 support case number in the title if you know it.

    tail -f /var/log/apm > /var/tmp/<case_number>-apm.txt

After you have reproduced the issue, stop the tail command by typing Ctrl + C.

Gathering an HTTPWatch capture

Impact of procedure: Performing this procedure should not have any negative impact on your system.

Note: This procedure uses third-party software that may change without our knowledge. Check the manufacturer's website for compatibility details.

If you do not have HTTPWatch installed, you can download the free basic version to capture traffic. Use the following procedure to capture session traffic to the BIG-IP APM system:

  1. Open a browser and ensure that your Home page is not part of the application. If it is, you can temporarily change it.
  2. Open the HTTPWatch control panel and clear the cookies and cache by using the HTTPWatch toolbar to navigate to Tools and clicking Clear Cache and All Cookies.
  3. Close the browser to clear cached data, and then relaunch the browser.
  4. Start HTTPWatch and start recording.

    Note: Do not select the Automatically Record when IE or Chrome Starts option. This option creates a separate file for each browser window.

  5. To access the site through the BIG-IP APM system, type its name into the address bar.
  6. Perform the actions required to reproduce the issue in the application.
  7. Stop HTTPWatch and save the recording using the HTTPWatch Log File(*.hwl) file type option.

    Note: If you are using the free version of HTTPWatch, you may not be able to view all traffic details in the capture; however, F5 Technical Support uses a licensed version and is able to view the full traffic details.
