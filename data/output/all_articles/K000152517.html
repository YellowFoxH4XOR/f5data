K000152517: Virtual server remains UP even though the pool member is down

Type
Support Solution
Published
2025-07-10
Updated
2025-07-10
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.1
Source
https://my.f5.com/manage/s/article/K000152517

Description

When cascading virtual servers (VS) across different BIG-IP instances, using an ASM (Application Security Manager) policy in blocking mode on the backend VS can lead to unexpected outcomes in health monitoring. Specifically, the VS on the frontend BIG-IP may fail to reflect the correct status of the VS in the backend BIG-IP when the backend VS has no pool members, causing discrepancies in VS health status.

Environment

  • BIG-IP systems configured with cascading virtual servers: VS1 (frontend) --> VS2 (backend, acting as pool member)
  • ASM policy in blocking mode applied to VS2
  • Default HTTP monitor applied to the VS1 pool
  • VS2 pool is down with no pool members available

Cause

In a virtual server with an ASM policy attached, the ASM logic processes incoming connections before a load-balancing decision is performed. When the default http monitor traffic is received by VS2, the ASM policy blocks the request due to an RFC violation. As a response, VS2 will send a blocking response page (HTTP 200 OK). This http response causes the default http monitor to mark VS2 as up, even if there are no pool members available on VS2. In this scenario, a load balancing decision was never ran.

Recommended Actions

Use a Custom HTTP Monitor: Customize the HTTP monitor with a valid request format (e.g., GET /index.html HTTP/1.0) to bypass ASM formatting violations and ensure the monitor traffic is approved by the ASM policy. This way, the request will pass through ASM correctly and a load balancing decision will be made.
