Description

Security scanners may report the Content Security Policy (CSP) directives unsafe-inline and unsafe-eval in responses from BIG-IP Access Policy Manager (APM). These directives reduce the browser protections provided by CSP and may be reported as potential cross-site scripting (XSS) risks.

BIG-IP APM uses these directives for specific supported functionality:

  • unsafe-inline supports server-generated inline scripts used by APM-hosted pages, including logon pages, WebTop, and /my.policy.
  • unsafe-eval supports the Portal Access transparent-proxy rewriting architecture.

The presence of these directives does not, by itself, demonstrate an exploitable XSS vulnerability in default, unmodified APM-generated pages.

Environment

  • BIG-IP APM
  • BIG-IP APM Content-Security-Policy headers

Cause

None

Answer

unsafe-inline

BIG-IP APM uses server-generated inline scripts for functions such as:

  • Session-state handling
  • Session timeout handling
  • Page behavior
  • Event handlers
  • Logon-page functionality
  • WebTop functionality
  • /my.policy functionality

Consequently, unsafe-inline may be required for supported APM functionality. Removing this directive or replacing it with a CSP that blocks the required inline scripts may prevent supported APM features from operating correctly.

By default, shipped APM-generated pages have inline scripts constructed by the APM rendering engine on the BIG-IP system. These pages don't process arbitrary user-controlled data as executable script content, so the presence of unsafe-inline alone doesn't prove an exploitable XSS vulnerability in default, unmodified APM pages.

unsafe-eval

Portal Access uses script evaluation as part of its transparent-proxy rewriting model. In this context, unsafe-eval is associated with the Portal Access rewriting architecture and is not, by itself, evidence that APM is executing arbitrary attacker-supplied strings at the APM layer.

Portal Access is an access solution and is not a Web Application Firewall (WAF). If an application published through Portal Access contains an XSS vulnerability, unsafe-eval may prevent the browser from applying an additional CSP restriction against eval-based payloads on rewritten pages. The security of the proxied application must therefore be assessed separately.

Your (customer) customization

The statements above apply only to default, F5-supplied APM content. BIG-IP APM deployments support various forms of user-facing content customization. For customization guidance, see the BIG-IP Access Policy Manager Customization documentation.

Your (customer-generated or administrator-added) content—including customized logon content, HTML, JavaScript, Portal Access content, and iRules—must be securely developed and properly output-encoded.

Because unsafe-inline permits inline script content to execute in the browser:

  • CSP does not provide a browser-level backstop against unsafe administrator-added script content.
  • Customized content should be reviewed for injection and XSS risks.
  • Administrative access should be treated as highly privileged.
  • Administrative changes should be restricted, audited, and managed through an appropriate change-control process.
  • Applications published through Portal Access remain responsible for your own application-layer security.

F5 does not assess customer-created content or the security of applications published through Portal Access under this guidance.

Additional Information

Security scanner classification

A scanner finding that identifies unsafe-inline or unsafe-eval is technically accurate because these directives may be present by design.

For default, unmodified APM-generated pages, you may document the finding as a known product architectural limitation and an accepted operational risk, subject to your internal security governance and auditor approval.

The finding should not automatically be classified as a false positive solely because the directives are expected. The scanner has correctly identified the directives; however, their presence alone does not demonstrate an exploitable XSS vulnerability in default, unmodified APM pages.

Your customizations and applications accessed through Portal Access must be evaluated separately.

Security headers and stricter CSP policies

F5 provides guidance for adding HTTP security headers to a BIG-IP APM virtual server in K71130157: Adding HTTP security headers to an APM enabled Virtual Server.

A CSP that is too restrictive may block inline scripts required by BIG-IP APM and can cause supported functionalities - such as logon processing, endpoint checks, session handling, WebTop, or Portal Access features - to fail. Test any user-defined CSP policy thoroughly before deploying it to production.

For the current CSP limitation with BIG-IP APM, see K000133657: CSP / Content Security Policy Level-2 headers with BIG-IP APM.
