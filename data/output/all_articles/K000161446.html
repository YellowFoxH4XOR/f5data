Description

Users may observe a discrepancy in the number of illegal (blocked) requests when comparing the ASM Event Log (Security > Event Logs) and the Application Report (Security > Reporting > Application) over the same time period. For example, filtering both views for a single day (e.g., 00:00–23:59) may yield different counts — such as 80 in the Event Log versus 164 in the Application Report — for the same WAF policy.

Environment

  • Product: BIG-IP Advanced WAF / ASM
  • Feature: Security > Event Logs (ASM/PRX database) vs. Security > Reporting > Application (AVR database)
  • Condition: Device configured with a non-UTC timezone (e.g., Asia/Seoul, UTC+9)
  • Filter used: Custom Time Period in Application Report (e.g., 00:00 to 23:59 local time)

Cause

Two separate root causes contribute to this behavior:

  1. Different data sources: The ASM Event Log and the Application Report draw from entirely different backend databases:
    • ASM Event Log uses the PRX database — this is an accurate, per-event log.
    • Application Report uses the AVR database — this is an aggregated statistics database, not an event logger.
  2. Timezone misalignment in AVR Custom Time Period filter (RFE ID2301501): The Application Report's Custom Time Period filter operates in UTC, not in the device's configured local timezone. For devices in non-UTC timezones (e.g., KST/UTC+9), selecting a local day (00:00–23:59) causes the report to span across two UTC-aligned daily aggregation buckets, resulting in data from adjacent days being included. This is confirmed as by design behavior by the F5 Product Development team, with an RFE filed to improve it.

Answer/Recommended Actions

Understanding the difference:

  • The ASM Event Log (PRX database) is the accurate source for per-request data. Use this for precise counts of illegal/blocked requests.
  • The Application Report (AVR database) is designed for high-level trend analysis and aggregated statistics. It is not intended to provide exact per-event counts.

Workaround for accurate single-day reporting in Application Report (for non-UTC timezones):

To obtain Application Report data that matches a single local calendar day, manually adjust the Custom Time Period filter by your UTC offset:

  1. Determine your device's UTC offset (e.g., Asia/Seoul = UTC+9, so offset is +9 hours).
  2. In Security > Reporting > Application, set the Custom Time Period as follows:
    • Start: <local date> 09:00:01 (i.e., local midnight = UTC 09:00 for KST)
    • End: <local date + 1 day> 08:59:59
    • Example for 2026-01-11 KST: Set filter from 01/11/2026 09:00:01 to 01/12/2026 08:59:00
  3. This aligns the AVR aggregation boundaries with the local calendar day, yielding counts consistent with the ASM Event Log for that day.

Additional Information

  • AVR is not an event logger. The AVR (Application Visibility and Reporting) system aggregates statistics periodically and is designed to provide a high-level view of trends and analytics. It does not capture every individual event. Therefore, exact counts from AVR will not always match the ASM Event Log.
  • The ASM Event Log is the authoritative source for accurate per-request data, including illegal/blocked request counts.
  • The timezone mismatch behavior in the Application Report Custom Time Period filter is by design (as confirmed by F5 Product Development). Charts in Security > Reporting > Application are implemented in UTC. Users in non-UTC timezones must manually adjust the report period by their UTC offset to obtain accurate local-day data.
  • RFE ID2301501 ("Custom Reports in BIG-IP AVR Should Honor Device Timezones") has been filed to track and potentially improve this behavior in a future release. There is currently no ETA for implementation.
  • The discrepancy is not a defect in the ASM Event Log — the event log data is accurate.
