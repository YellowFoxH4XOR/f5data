Description

Some security proxy systems may use network stack fingerprinting libraries such as JA3 (https://github.com/salesforce/ja3) or JA4 (https://github.com/FoxIO-LLC/ja4) and may miscategorize valid requests from clients protected by SSL Orchestrator as Bot or Malicious traffic. 

You can potentially identify this in a decrypted capture. A common user of this is Cloudflare. If you suspect this may be an issue a decrypted capture will be needed to review a common HTTP response code seen when this happens...403 Forbidden. In the 403 is an identifier that will be different for each user...

The CF-Ray: 9ed6bb14cd6ef2e9-IAD header is a Cloudflare identifier. The -IAD suffix indicates the request was processed by Cloudflare's Washington D.C. (Dulles/IAD) data center. The 403 is being generated by Cloudflare's security layer on the origin side. The string proceeding the -IAD is the value of the fingerprint.

Environment

Traffic directed through an SSLO topology.

Cause

Ordinary web browsers simultaneously negotiate both SSL/TLS connections (OSI layer 5) and HTTP connections (OSI layer 7). In this situation, the "SSL client" and "HTTP client" are the same actor: A client browser.

In Internet networking, these two things may also operate on different devices. For example a TLS offloading proxy may handle the SSL/TLS connection and a client browser may handle the HTTP connection. Historically this is called "SSL Offloading" or "SSL Proxying" and it may be applied to either the *client* side or *server* side of an HTTPS connection. SSL Orchestrator applies such SSL Proxying to either the client side or server side of connections, depending on the topology type: Outbound or Inbound. From the server's perspective, the SSL is negotiated by SSL Orchestrator rather than the client's web browser directly. Because SSL and HTTP are independent layers, this works fine.

Some third party solutions such as "JA3" or "JA4" introduce a hybrid security mechanism where the SSL and HTTP are mixed together. In this system, the web hosting server has an SSL Proxy that interrogates the client's SSL connection and inserts an HTTP Request Header with a textual "SSL Fingerprint". The SSL Proxy then forwards this request to the HTTP Server. The HTTP Server then has access to both the SSL request data and HTTP request data for comparison.

Because the security solution expects the HTTP and SSL to occur on the same actor, but they were generated by different actors, the connection may be disallowed.

Answer/Recommended Actions

1- If possible disable the server-side security proxy. This allows the SSL and HTTP to be negotiated on different client devices.
2- Configure the SSL Orchestrator Security Policy to bypass the connections to the server. This moves the SSL negotiation from the BIG-IP to the client browser.
