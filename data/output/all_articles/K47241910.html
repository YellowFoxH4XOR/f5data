Issue

Description

In the case that a BIG-IP presents with oom-killer (out of memory) log messages, this article will assist in determining the triggering process.

Environment

  • BIG-IP with exhausted memory resources

Cause

The causes for memory pressure triggering oom-killer can be broad.  Here are several examples:

  • Over provisioning a device with modules (LTM, DNS, APM, ASM, AVR, etc).  Additional information can be found here:
    K13988: BIG-IP module provisioning exceptions
  • On vCMP guests and VE versions under provisioning resources (cores for vCMP, CPUs, and RAM for VE). Additional information can be found here:
    K14218: vCMP guest memory/CPU core allocation matrix
    K15796: Hardware requirements to host BIG-IP VE on private cloud platforms
  • Large configurations can also impact memory usage.  An F5 recommendation exists for configuration maintenance:
    K15335: F5 recommends removing orphaned configuration objects
  • Excessive load on a device can also cause legitimate memory usage to grow to a level which eclipses the capability of the device.  Review your hardware manual for capabilities:
    Hardware Knowledge Centers

Recommended Actions

OOM Killer information can be found in the /var/log/kern.log file.  There are several points of interest when reviewing OOM Killer messages

Determining available swap memory

When oom-killer is triggered it produces a large trace that includes the used and free swap.  The messages look similar to the following:

warning kernel: Total swap = 1048568kB
warning kernel: Free swap = 0kB

High swap use alone isn't much of a problem unless there is intensive paging due to true memory exhaustion. Usually there is a good correlation between very high swap use and low memory availability

Determining the process with the highest rss (resident memory)

The process which invoked the oom-killer is typically indicated in the oom-killer messages, it is also the process that required more memory at the time. In response, a possibly different process will be killed. The killed process is one that was calculated to have a greater impact on memory usage recently, based on a heuristic algorithm. However, none of these processes, even if both of them are the same, may necessarily be the culprit that ultimately causes the the memory pressure. To find the root cause, often more information is needed.

The oom-killer event logs also include a list showing the memory usage of the processes that were taken into account. There is also a header that helps determine which number is attributed to which value.  It looks similar to this:

info kernel: [ pid ] uid tgid total_vm rss cpu oom_adj oom_score_adj name

Using this key we can identify the process at the time of the process termination that had an unusually high rss.  In this example we have mcpd using a large amount of memory

info kernel: [ 5974] 0 5974 328442 >>109329<< 1 0 0 mcpd

Due to the fact RSS values are measured in 4KB pages, not bytes this example shows usage of 427MB (109329 x 4KB pages = 427MB)

Determining if there are many instances of unexpected processes

In other cases some external tools, external monitors, and tmsh/bash processes can cause memory pressure as a cumulative effect.  Here is an example of a multiple small processes which appear to be from multiple user logins or an external monitoring software:

info kernel: [10000]     0 21228     5442     1108   0       0             0 sshd
info kernel: [10001]     0 21243     5698      160   0       0             0 sshd
info kernel: [10002]     0 21244    28679     2980   0       0             0 tmsh
info kernel: [10003]     0 21270      559       99   0       0             0 less
info kernel: [10004]     0 15052     5442     1108   0       0             0 sshd
info kernel: [10005]     0 15067     5476      161   1       0             0 sshd
info kernel: [10006]     0 15068    28932     2946   0       0             0 tmsh
info kernel: [10007]     0 15085      559       99   1       0             0 less
info kernel: [10008]     0  9934     5442     1108   0       0             0 sshd

In this case we need to do an audit of our users, monitoring software, or external monitors to ensure sessions are appropriately closed

Determining how much slab memory is in use

In some cases large slab memory usage can indicate additional underlying issues.  This data is available via the oom-killer trace and looks similar to the following:

warning kernel: [3845526.752216]  free:20437 slab_reclaimable:6070 slab_unreclaimable:346915

Large unreclaimable slab use can indicate a possible memory leak.  In this case the usage was 1.3GB (346915 x 4KB pages = 1.3GB)

This information is also available in real time by using the command cat /proc/meminfo from the bash prompt.
