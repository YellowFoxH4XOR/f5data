Known Issue

Description

The AES::decrypt iRule command does not decrypt ciphertext that results from the AES::encrypt iRule command. This issue occurs when any of the following conditions is met:

  • The configuration is reloaded between the creation of the ciphertext using the AES::encrypt command and then attempts to decrypt it using the AES::decrypt command.
  • A TMM instance processes the connection when the ciphertext is created using the AES::encrypt command and by a different TMM instance when the AES::decrypt command attempts to decrypt it.
  • The BIG-IP system fails over or restarts between the creation of the ciphertext using the AES::encrypt command and then attempts to decrypt it using the AES::decrypt command.

This issue occurs because the AES::decrypt command uses the salt information from the current TMM instead of that provided in the ciphertext.

Impact

Decrypted data may not be available to make traffic decisions.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • F5 iHealth lists Heuristic H860958-1 on the Diagnostics > Identified > Low screen.
  • Data is not decrypted. If you attempt to log the result from the AES::decrypt command to a log file, the system logs a blank output. For example, you can use the following iRule crypto to log the result from the AES::decrypt on a ciphertext that represents the string XY:

    Note: The iRule has been truncated for brevity.

      when RULE_INIT {
        set cipehrtext [binary format H* "3c142fb05d95ee3ffca3ed0b64271b1578f9b1b070c42a1ce8cb04186f84a64343c03d13d8f1cf44"]
        set plaintext [AES::decrypt "keystring" $cipertext]
        log local0. "Plaintext: $plaintext"
      }
    The iRule logs the following line, which does not contain the expected decrypted data, to the /var/log/ltm file:

    Rule crypto <RULE_INIT>: Plaintext:

    The iRule should instead log the following line, which contains the decrypted string XY:

    Rule crypto <RULE_INIT>: Plaintext: XY

  • iRules using the AES::encrypt and AES::decrypt commands may not process traffic as expected.

Workaround

To work around this issue, you can specify the AES key as a hex string in the following format:

AES <length> <hex_key> 

For example, the following iRule sets a 256 bit AES key, uses it to encrypt a cookie seen in the request, then later decrypts it. The system uses the identical AES key each time, regardless of TMM instance or restart status:

when RULE_INIT {

     set static::key "AES 256 7618EAAF2D348D642C0DF02D8A4FD2A19AD70DA64B2BE83DD2CDD6139A65BBD1"
}

when HTTP_RESPONSE {
     # encrypt cookies in response
     ...
     set encrypted_secret [AES::encrypt $static::key [HTTP::cookie secret]]
     ...
}

when HTTP_REQUEST {
     # decrypt cookies in subsequent requests
     ...
     set decrypted_secret [AES::decrypt $static::key [$encrypted_secret]]
     ...
}
