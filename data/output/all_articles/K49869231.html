Chapter 5: Denial of Service

Table of contents | << Previous chapter | Next chapter >>

The BIG-IP AFM system provides mitigation techniques against DoS/DDoS attacks.

Denial of Service (DoS) attacks are attempts to render a machine or network resource unavailable to its intended users. Most network DoS attacks occur at OSI layers 3, 4, or 7.

The attacks work by overwhelming the server resources by directing traffic at a particular IP address and/or port with an inordinate amount of either legal traffic or malformed requests that exhaust available resources. For example, targeting of the number of concurrent L4 connections or available bandwidth are just a couple of common DoS attacks. The result is service denial to legitimate users.

Distributed denial-of-service attacks

Originally, a DoS attack might have been made by a lone attacker on a single computer targeting another computer. Now an attacker can command hundreds of compromised computers, or zombies, in an array, called a botnet, to launch a distributed denial-of-service (DDoS) attack. These DDoS attacks often simultaneously target the victim’s firewall, DNS and other resources as well. These blended attacks may not be conducted by an individual attacker. Online, loosely organized communities work together to multiply the scope and complexity of a DDoS attack.

Note: Distributed denial-of-service (DDoS) is referred to generically as denial-of-service (DoS) in the BIG-IP Configuration utility.

Symptoms of DoS/DDoS attacks

Symptoms of denial of service attacks may include:

  • unusually slow network performance (opening files or accessing websites).
  • inability to access a website or group of sites.
  • long-term denial of access to the web or any Internet services.

Types of DoS/DDoS attacks

While the DoS threat landscape is constantly evolving, attacks fall within four types:

  • Volumetric: Flood-based attacks against layer 2, 3, 4, 5, or 7.
  • Computational Asymmetric: Attacks designed to consume CPU cycles.
  • Stateful Asymmetric: Attacks designed to abuse memory by invoking timeouts of session-state changes.
  • Vulnerability-based: Attacks that exploit software vulnerabilities at any layer.

Attacks can be launched as a single attack or a combination of any of the listed typed.

BIG-IP AFM DoS mitigations

There are many possible strategies and architectures for mitigating DoS attacks. Some attacks are designed to overwhelm the on-premises network pipe to affect the availability of all services residing at the location. Since the volume of the attack is greater than the available network bandwidth to the location, these attacks are best defended using off-site, cloud-based solutions such as F5 Silverline: Cloud-delivered DDoS protection or large-scale globally distributed architectures.

On-premises equipment is the second tier of DoS mitigation. While the volume of an attack may not be enough to consume all available network resources, the attacker’s strategy is to consume enough resources to disrupt an application or group of applications. The mitigation strategy in such cases is to provide capacity to absorb the DoS while maintaining targeted service delivery goals.

Detecting and mitigating attacks

Using a combination of a robust, scalable operating system and the ability to offload many attack mitigations to dedicated hardware, the BIG-IP system with BIG-IP AFM is capable of detecting and mitigating a wide range of network-layer attacks to reduce the likelihood of downtime.

BIG-IP AFM detects attacks based on thresholds in events per second (EPS) or by percentage deviations from the previous hour’s baseline observed values. To mitigate attacks detected by these vectors, rate limiting can be applied to devices violating the thresholds.

In BIG-IP AFM 12.1 and later, auto-thresholds can estimate baseline levels for you if you do not have the time or ability to research them. For more information, refer to Threshold Mode in this article.

Attack vectors

The BIG-IP system classifies common types of DoS attacks into attack vectors. There are many different types of attack vectors which have been designed to exploit different system vulnerabilities. The specific number and type of attack vectors that BIG-IP AFM protects against depends on the BIG-IP TMOS version you’re using. F5 adds additional attack vectors and configuration options as attack types evolve.

Each DoS attack vector contains settings to customize when BIG-IP AFM detects an attack has started, and when BIG-IP AFM begins mitigating the attack by rate limiting attack packets.

Attack detection

Each BIG-IP AFM attack vector contains two configuration settings that can be used to recognize when a possible attack has started against the device: Detection Threshold events per second (EPS) and Detection Threshold Percentage.

Detection Threshold EPS

Note: In BIG-IP AFM versions prior to 13.x, Detection Threshold EPS is called Detection Threshold packets per second (PPS).

The BIG-IP system uses Detection Threshold events per second (EPS) as an early warning indicator that an attack may be occurring. When traffic exceeds the detection threshold, BIG-IP AFM generates a log message of this event to notify you of the condition. This setting is for attack detection only and you should not use it to mitigate attacks.

When you enable an attack vector, BIG-IP AFM tracks statistics on how many packets arrive at the device related to that vector. The system samples packets once every second. The system interprets this configured value differently depending on which context DoS Protection is applied. For more information, refer to Architecture in this article. Set this value based on your preference and the traffic-handling ability of the application.

Note: For more information about TMM, refer to: K14358: Overview of Clustered Multiprocessing (11.3.0 and later).

 

Figure 5.1 Detection Threshold events per second (EPS) detects when traffic exceeds the configured threshold

Detection Threshold Percentage

The BIG-IP system uses the Detection Threshold Percentage as an early warning indicator that an attack may be occurring. When the detection threshold is exceeded, BIG-IP AFM generates a log message of this event to notify you of the condition. This setting is for attack detection only and is not used to mitigate attacks.

When an attack vector is enabled, BIG-IP AFM compares the average rate of traffic related to that vector over the last hour to the average rate of traffic over the last minute.

When the quotient between the average rate of traffic over the last hour and the average rate of traffic over the last minute exceeds the threshold setting, BIG-IP AFM creates a log message and reports the EPS every second until the traffic recedes below the threshold.

Note: BIG-IP AFM must first collect three hours’ worth of traffic in order to create a value for the average rate of traffic over the last hour. In addition, the average rate must be above 100 EPS for this threshold to be triggered.

 

Figure 5.2 Detection Threshold Percentage compares the average rate of traffic related to that vector over the last hour to the average rate of traffic over the last minute

Attack mitigation

You can configure each BIG-IP AFM attack vector to rate-limit traffic automatically based on detected stress levels or manually based on a specified EPS value. After traffic reaches the limit, BIG-IP AFM begins dropping traffic that exceeds the limit. The system drops all packets exceeding the threshold and continues to drop until the EPS rate falls below the configured rate limit or the detected stress falls to an acceptable level.

Important: The system drops packets without regard to whether the traffic is legitimate or malicious. Rate-limiting applies to good and bad packets alike.

There are some features that attempt to discriminate between good and bad traffic. For more information, refer to the Single Endpoint Sweep and Flood, Dynamic Signatures, and Bad Actor Detection and Attacked Destination in this article.

Attack phases

There are four phases to a BIG-IP AFM DoS attack mitigation:

  1. DoS vector is enabled but no attack is present.
  2. Attack begins and BIG-IP AFM detects it.
  3. Attack is ongoing and BIG-IP AFM takes configured action.
  4. BIG-IP AFM stops attack and traffic returns to normal.

Architecture

DoS Protection is applied at one of three of the following levels: device protection (the BIG-IP system itself and everything on it), protected objects (generally only virtual servers), and protected zones (collections of VLANs).

Device Protection

Note: In BIG-IP AFM versions prior to 14.x, Device Protection is called Device Configuration.

DoS protection at the device level acts system-wide. You configure it using the Device Protection settings. Device Protection detects and mitigates network-layer DoS attacks across all services protected by BIG-IP AFM. The value of Device Protection is that it protects the BIG-IP system itself rather than any particular application managed by the system. The BIG-IP system sees all traffic passing to it, including traffic that may not have a legitimate listener as a destination. Detection and mitigation settings appropriate at the device level may be too high for individual applications. Additionally, mitigation at the device level is applied to all traffic crossing the BIG-IP system that matches the DoS vector, no matter the destination, service, or source. The system selects packets at random from among the good and bad traffic alike. For the exception, refer to Bad Actor Detection and Attacked Destination Detection in this article. This selection process may have the effect of spreading the DoS attack across the other services managed by the BIG-IP system since mitigation still affects legitimate traffic to unaffected services.

The system interprets Device Protection threshold setting values for almost all DoS vectors per-TMM instance, not cumulatively as a system. The system enforces the detection and mitigation values for the Single Endpoint vectors as you enter them for the system as a whole, not per-TMM. If you manually configure a detection limit of 1000 EPS, the system does not report an attack until at least one TMM receives more than 1000 EPS. If your BIG-IP system has four TMMs, the enforced value (assuming even hashing of traffic across the four TMMs) is 4000 EPS. Set this value based on your preference and the traffic handling ability of the application. For more information on threshold limits for each TMM refer to K15023: The BIG-IP AFM system enforces configured thresholds and limits for each TMM.

DoS profiles for virtual servers and protected objects

You usually configure and apply DoS profiles to the virtual-server level to detect and mitigate attacks to an application or group of application servers. You can carefully calibrate DoS Profiles to protect the resources associated with specific applications. While basic mitigation still results in dropped packets from good and bad traffic alike, the effect is limited to the service under attack and other services are not impacted.

DoS profiles designated apply at the virtual-server level offer a subset of the overall DoS attack vectors. You can only configure some DoS vectors at the device level. Counters can count against both when determining thresholds for detection and mitigation.

Note: L4/Network DoS attack vectors enabled on the virtual server DoS profile must also be enabled at the Device Protection level to trigger the vector at the virtual server level. This does not apply to L7 DoS attack vectors, such as DNS and SIP. Additionally, the threshold values configured in DoS profiles are internally divided by the number of TMMs and the threshold is enforced per TMM. For more information, refer to K15023: The BIG-IP AFM system enforces configured thresholds and limits for each TMM.

DoS profiles for SIP require that a SIP protocol profile be applied on the virtual server. Likewise, DoS profiles for DNS require a DNS protocol profile and a DNS protocol protection profile be applied on the virtual server.

Protected zones

Zones are lists of VLANs that are managed in Zones on the Security tab. You can use them as sources or destinations in Network Firewall rules. With BIG-IP 15.1.8, you can use zones in Protected Zones that use DoS Protection profiles.

Hardware acceleration

To reduce the requirements of the operating system (TMOS) processing attacks and maximize system resources, many DoS vectors are offloaded into programmable FPGA hardware.

For more information on which vectors are processed in hardware refer to Detecting and Preventing System DoS and DDoS Attacks in BIG-IP Systems: DoS Protection.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Whitelisting

Note: F5 is working to eliminate exclusionary language in our products and documentation. For more information, refer to K34150231: Exclusionary language in F5 products and documentation.

DoS whitelists provide a mechanism to configure trusted networks, protocols, and VLANs to bypass DoS checks and mitigations.

In BIG-IP 12.0 and later, the DoS whitelist is limited to eight (8) entries. You can base these on source or destination of hosts, networks, or VLANs. They include network protocols with or without specific ports, or combinations of these settings. Use of super-nets and larger masks to whitelist traffic or ingress VLANs is typically more efficient due to the limit on entries.

Configuring a whitelist entry using the Configuration utility (BIG-IP 14.x and later)

  2. Select Whitelists, then for Rich Whitelists select Add Whitelist.
  3. Fill in the white list entry as appropriate.
  4. Select Commit Changes to System.

Packet processing (SYN cookie protection)

The BIG-IP AFM SYN cookie feature protects the system against SYN flood attacks by allowing the BIG-IP system to continue to establish connections when the SYN queue begins to fill up during an attack.

When the SYN Check Activation Threshold value is reached, the BIG-IP system responds to SYN requests by sending back to the client the SYN+ACK response containing an encoded secret. The system then discards the SYN queue entry and waits for a correctly constructed ACK from the client before establishing an entry in the connection table.

The SYN cookie secret can be calculated in hardware or software depending on the platform. This behavior can be modified by adjusting the value for the SYN cookie algorithm database key.

For more information on connection SYN Cookies, refer to K16500: Overview of the connection.syncookies.algorithm database key.

When the SYN cookie authentication method is active for a virtual server or self IP address, established connection/packet handling and high-availability features such as mirroring should perform normally.

SYN cookie operation

 

Figure 5.6 SYN cookie packet flow

When SYN cookie protection is enabled for the protocol profile, the feature operates as follows:

  1. A client sends a TCP SYN request to the BIG-IP virtual server or self IP address.
  2. The receiving Traffic Management Microkernel (TMM) instance determines whether to enable hardware or software SYN cookie protection as follows:
    • If the platform contains the high-speed bus (HSBe2) chip and hardware SYN cookie protection is enabled in the profile, TMM notifies the HSB chip and other TMM instances in the cluster to enable hardware SYN cookie protection. The HSB chip and receiving TMM instance then programs HSB hardware for hardware SYN cookie generation and validation for the virtual server or self IP address, and synchronize the status to all TMM instances in the cluster.
    • For TCP and FastHTTP profiles, if the platform does not contain the HSB chip or hardware SYN cookie protection is disabled in the profile, the TMM notifies other TMM instances in the cluster to enable software SYN cookie protection.
    • For FastL4 profiles, if the platform does not contain the HSB chip or hardware SYN cookie protection is disabled, SYN cookie protection is not available for the virtual server unless the software SYN cookie protection option is specifically enabled.
  3. The BIG-IP system sends the SYN+ACK response back to the client but discards the SYN queue entry. The BIG-IP system does not maintain the SYN-RECEIVED state that is normally stored in the connection table for the initiated session. Because the system does not maintain the SYN-RECEIVED state for the connection, the SYN queue is not exhausted, and normal TCP communication continues.
  4. If the BIG-IP system then receives a subsequent ACK response from the client, the system reconstructs the SYN queue entry by decoding data in the TCP sequence number.
  5. After the BIG-IP system validates the client’s ACK, the system adds the session to the connection table and initiates a connection to the pool member.

For more information on SYN cookie protection refer to K74451051: Configuring SYN cookie protection (13.x - 16.x).

Threshold Mode

There are different ways to set thresholds to activate the detection and rate-limiting for a DoS vector, described in the following table.

ModeDescription
Fully AutomaticImplements automatic thresholds and mitigates DDoS attacks based on server stress. Simplifies the settings for DoS vectors by allowing the system to adjust typical DoS vector levels over time and adjusting the sensitivity of the detection and rate limiting for that vector automatically. Attack Floor EPS and Attack Ceiling EPS are configured for auto thresholds. If the server is not stressed, packets are not dropped.
Auto Detection / Multiplier Based MitigationImplements thresholds and mitigates DDoS attacks based on the specified Mitigation Multiplier. The system uses the value to calculate the rate limit thresholds and mitigates the attack vector if traffic reaches the threshold.
Manual Detection / Auto MitigationAllows you to set thresholds manually based on your experience with the network systems you are protecting or based on using simulated automatic thresholds. However, the system also automatically examines server stress, and mitigates the attack vector if the server is stressed.
Fully ManualAllows you to configure parameters for DoS vector detection and rate limiting manually. The system mitigates the attack vector based on the threshold values you set.

You can choose Fully Manual and then fine-tune the pre-configured values for the DoS vectors. This can be challenging for the following reasons:

  • There are many attack vectors to configure (over 200).
  • It is difficult to know the appropriate thresholds, which can vary by day and time of the week.

 

Figure 5.7 Example Fully Manual DoS vector configuration

Fully Automatic means the BIG-IP system learns from the history of observed traffic and knows how many packets it usually sees at that specific time for the specific vector. This is called the baselining and calculates the detection threshold.

Mitigation is stress-based. The measurement of stress depends on whether it is DoS Device Configuration or a DoS Protection Profile.

 

Figure 5.8 Example of Fully Automatic DoS vector configuration

Floors and Ceilings

Using automatic thresholds, you can still specify Floor and Ceiling values for EPS to provide limits. If the EPS value is lower than a configured Floor setting, no mitigation occurs no matter what stress the system detects. If the EPS value is greater than a configured Ceiling, mitigation occurs no matter what stress the system detects. As soon as a flood reaches the BIG-IP system and crosses the detection threshold for a vector, the system detects it as an attack for that vector, which means the BIG-IP system identifies it as an anomaly. However, system does not start to mitigate (drop traffic).

Auto Mitigation with Device Protection

For Device Protection, auto-mitigation only happens when a TMM load (CPU load) exceeds a certain utilization level.

Mitigation sensitivity is defined as follows:

  • Low: 78%
  • Medium 68%
  • High: 51%

If both conditions—packet rate is too high and TMM/CPU load is too high—are true, the mitigation starts and lowers (rate-limits) the number of packets for this vector going in to the BIG-IP system for the specific TMM. That means the DoS feature only drops packets if necessary to protect the BIG-IP CPU. This is a dynamic process which drops more packets when the attack becomes more aggressive and less when the attack becomes less aggressive.

Note: You can configure DoS vectors with Auto Mitigation with Floor and Ceiling thresholds. At EPS rates lower than the Floor, the system does not perform mitigation, no matter the CPU utilization. At EPS rates higher the Ceiling, the system performs mitigation no matter the CPU utilization.

Auto Mitigation with DoS Profiles

Fully Automatic mitigation, used in a DoS profile, discovers the health of the service. This works well if the traffic is TCP or DNS. The system does evaluates TCP behavior, such as window size, retransmission, congestions, and counting DNS outstanding requests versus responses, and so on.

Multiplier Based Mitigation is better than Auto Mitigation for ICMP and most UDP traffic. If the traffic is not DNS-UDP traffic or ICMP traffic, the stress measurement is not very accurate, so consider using the Multiplier Based Mitigation. In this case, the BIG-IP system performs the baselining (calculating the detection rate) similar to Fully Automatic mode, except it begins rate limiting if it experiences more than the defined multiplication for the specific vector, regardless of the CPU load. For example, when the calculated detection rate is 250k packets/sec and the multiplication is set to 500 (which means 5 times), the mitigation rate is 250k x 5 = 1,250,000 packets/sec. The multiplier feature provides the option to configure a threshold based on the multiplication of an expected rate.

Suggested settings for DoS vectors (Fully Manual configuration)

The system recognizes three categories of vectors, based on the confidence level with which the system regards packets as useless or malicious:

  • Invalid packets include bad header*, fragmentation, IP unknown protocol, land attack, and others.
  • Probably invalid packets include TCP RST, TCP SYN-ACK, and TCP Push.
  • Presumably valid packets include TCP SYN, TCP ACK, and UDP.

You can set the detection and rate-limit properties of these categories and vectors set with the following ranges:

  • Invalid packets: MINIMUM (1-100 EPS)
  • Probably invalid packets: LOW (100-500 EPS)
  • Presumably valid packets: HIGH (1000+EPS to the limit of the resource capacity)

The values vary depending on BIG-IP platform and environment, as well as whether you configure the vector type through DoS device configuration or a DoS profile.

You should set the DoS Device Protection settings at the level required to protect the stability of the BIG-IP system. You should have the system drop packets that it presumes are valid only in an emergency because this action affects every virtual server on the BIG-IP system.

Important: The BIG-IP system interprets the Device Protection threshold settings for detection and mitigation on a per-TMM basis for all DoS vectors except Single Endpoint Sweep and Flood. This means that the threshold values you enter do not trigger unless any one TMM experiences at least as many EPS as configured. Given an even distribution of traffic across TMMs, this makes the effective detection and mitigation thresholds equal to (value configured) * (number of TMMs). The BIG-IP system interprets threshold settings for the Single Endpoint vectors for the system as a whole.

Invalid packets

Invalid packets are those which violate protocol specifications. These includes bad header vectors.

While standard TMOS packet handling silently drops invalid packets, it can be more efficient to allow BIG-IP AFM DoS to handle them earlier to reduce TMOS workload.

DoS also allows you to configure alerts to your preference. You can configure DoS detection and rate limiting depending on whether you want to be alerted to all invalid packets or only at higher traffic levels.

Additionally, DoS reporting provides visibility into invalid packets.

Probably invalid packets

Legitimate TCP Push, TCP SYN-ACK, and TCP RST packets do match during the flow table lookup, so any of these packets received by DoS protection are probably invalid. However, since they are at least valid packets as far as protocol compliance, you can’t be sure they are invalid.

This traffic should be restricted.

Presumably valid packets

TCP SYN, TCP ACK, and UDP flood vectors all represent potentially legitimate traffic. You should not restrict these packets unless resource availability is threatened.

TCP ACKs are presumably valid because the system may experience them seen when SYN Cookies are active. If presumably valid packets fail a hardware SYN Cookie check, the system drops or rejects them before they reach DoS protection.

If SYN Cookies are not active, the system drops any unsolicited, bare ACKs.

BIG-IP AFM DoS vectors

This section lists examples of attack vectors and mitigations.

Bad header

The various bad header vectors all check for packets violating their respective protocol specifications.

Because the system drops packets matching a bad header vector later, there are no unwanted bad-header packets. There is no reason to keep them around. F5 recommends setting detection and rate-limiting thresholds to MINIMUM for these vectors.

To modify a specific Bad Header attack, refer to Device configuration in this article.

DNS

Domain Name System (DNS) attacks allow an attacker to attack use malformed packets and protocol errors to cause disruption of name resolution.

To modify a specific DNS attack, refer to Device configuration in this article.

Flood

Attackers use Flood attacks to overwhelm a resource. Flood vector packets are probably invalid; however, because they follow protocol specification, it is possible that they are valid. If the packets are valid, the system matches them on a flow lookup table and handles them without DoS protection experiencing them.

F5 recommends setting Detection and Rate Limiting to LOW for the following vectors:

  • TCP BadAck Flood
  • TCP RST Flood
  • TCP SYN-ACK
  • TCP SYN Oversize
  • TCP Window Size

Some of the flood vectors are presumably valid. These are valid packets, indistinguishable from legitimate connection requests. F5 recommends setting detection and rate-limiting thresholds to HIGH for the following vectors:

  • TCP SYN Flood
  • TCP ACK (when SYN Cookies are active the ACK does not match a Flow Table Lookup)
  • UDP

The recommended settings for the remaining flood vectors depend on the environment. F5 recommends setting detection and rate-limiting thresholds to HIGH for the remaining vectors in the flood group, pending an assessment of traffic patterns. This assessment may indicate LOW or MINIMUM settings are appropriate for specific vectors.

To modify a specific Flood attack refer to Device configuration in this article.

Fragmentation

Fragmentation is the process of breaking a single IP datagram into multiple smaller packets.

Attackers use fragmentation attacks to use this method as an attack vector. The vectors in the Fragmentation section represent invalid packets, which the system drops. They are not legitimate IP fragments, so there is no reason to keep them around.

The BIG-IP system tracks legitimate IP and IPv6 fragment traffic in the IP Flood and IPv6 Flood vectors. F5 recommends setting detection and rate-limiting thresholds to MINIMUM for these vectors.

To modify a specific Fragmentation attack, refer to Device configuration in this article.

Single Endpoint Sweep and Flood vectors

Single Endpoint vectors allow for detection and rate limit EPS involving a single device. This means that the system identifies only the attacker or target and only mitigates traffic from that attacker or to that target.

The Single Endpoint Sweep vector tracks the 100 source addresses sending the most of the selected packet types. The Single Endpoint Flood vector tracks the 100 destination addresses receiving the most of the selected packet types. These two vectors are especially useful because their mitigation efforts are directed only at the 100 involved hosts. The other vectors drop traffic without regard to its legitimacy.

Session Initiation Protocol

Session Initiation Protocol (SIP) is an IP telephony standard developed by the Internet Engineering Task Force (IETF) to manage the creation and destruction of voice-related IP networking sessions. One typically uses Session Initiation Protocol (SIP) for voice and video calls over IP. SIP protections within BIG-IP AFM allow for detection and mitigation of malformed packets containing errors intended to intentionally or unintentionally to disrupt this connectivity.

To modify a SIP vector refer to Device configuration in this article.

Other

The Other vector allows for detection and mitigation against other attack types.

The IP Unknown Protocol and Land Attack vectors are invalid packet types. There is no reason to keep them around. F5 recommends setting detection and rate-limiting thresholds to MINIMUM for these vectors.

To modify an Other protection, refer to Device configuration in this article.

Bad Actor Detection and Attacked Destination Detection

Bad Actor Detection is introduced with Single Endpoint Sweep in the Auto-Blacklist feature. Working with IP Intelligence, this feature classifies as malicious hosts that send too much traffic and drops traffic from them.

Many static vectors provide the opportunity to enable Bad Actor Detection or Attacked Destination Detection. If a Bad Actor or Attacked Destination is detected, the user has the option of adding the identified host to an IP Intelligence category. If an IP Intelligence policy is configured and applied in the relevant context, IP Intelligence will take the action specified in the policy for traffic belonging to that category. For more information, see the IP Intelligence section in K13723376: BIG-IP AFM operations guide | Chapter 9: Troubleshooting.

Dynamic Signatures (BIG-IP 13.x and later)

The Dynamic Signatures feature is an automated approach to identifying anomalous traffic patterns and restricting them when the BIG-IP experiences stress. Dynamic signatures reduce false positives by alerting and enforcing signatures only when an attack has a meaningful impact on the BIG-IP system and the applications it supports.

Dynamic signatures are ephemeral, which means the BIG-IP system creates them only when needed and discards them after an attack is over. During the time that dynamic signatures exist, you can review them, disable them, or modify their thresholds; however, after the system discards the signatures, it also permanently discards your modifications to them.

Beginning in BIG-IP 14.1, you can elect to retain (persist) Dynamic Signatures. For more information, refer to BIG-IP v14.1 AFM: DoS Dynamic Signatures Enhancements on LearnF5.

DoS profiles

DoS Profiles allow a BIG-IP provisioned with BIG-IP AFM the ability to detect and automatically mitigate DoS on an individual virtual server.

You can specify various detection and mitigation thresholds for DoS attack types to more accurately detect, track, and rate limit attacks.

For more information on each attack type, refer to Preventing Device DoS/DDoS Attacks in BIG-IP AFM: DoS/DDoS Protection Implementations.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

DoS profiles provide the ability to mitigate attacks at a granular level, contrary to global settings in Device DoS, while also giving the operator the ability to further tune many DoS attack vector thresholds on the virtual server level.

DoS Profiles contain three types of DoS vectors:

  • DNS
  • SIP
  • Network

Note: L4/Network DoS attack vectors enabled on the virtual server DoS profile must also be enabled at the Device Protection level to trigger the vector at the virtual server level. Additionally, the threshold values configured in DoS profiles are internally divided by the number of TMMs and the threshold is enforced per TMM. DoS policy development

A BIG-IP AFM DoS policy consists of multiple components working together to protect an infrastructure from DoS attacks. Some elements of a BIG-IP AFM policy protect the application from protocol-specific attacks, while others protect more broadly.

Depending on the use case, you may require a simple DoS policy or one requiring more extensive development and tuning. F5 recommends that you clearly identify your use case—what your policy must protect—before you create it. Having this information should make development and enforcement easier.

Policy life cycle

The DoS security policy life cycle has three phases:

  1. Create and deploy policy
  2. Tune policy
  3. Maintain policy

Create and deploy policy

Create a new policy using the network and protocol protections specific to the infrastructure that is being protected.

Tune policy

False positive violations are identified, and policy settings are adjusted to allow legitimate traffic to pass through to the protected applications and infrastructure. This is necessary as some legitimate traffic may not pass the configured policy rules and may wrongly be identified as an attack.

Maintain policy

The DoS policy allows for adaption to application and infrastructure changes, new security requirements, and activities, based on the review of logs, reports and statistics of attacks mitigated by the BIG-IP AFM system.

Policy tuning details

Depending on the policy’s initial settings, the BIG-IP AFM DoS policy may need to be disabled or thresholds may need to be adjusted if legitimate traffic is blocked. At the end of the tuning process, the policy should contain all the relevant protections and thresholds.

Tips and guidelines

F5 recommends the following tips and guidelines for policy development:

  • Consider a cloud-based solution such as F5 Silverline: Cloud Based DDoS Protection to augment on-premises DoS mitigation and especially for volumetric attacks that may exceed on-premises bandwidth.
  • Start with a policy that allows a higher percentage of traffic nonconformity to allow all legitimate behavior and disallow malicious requests.
  • Remember that Global DoS traffic settings are applied across the entire BIG-IP system, meaning all ingress traffic is counted.
  • Use DoS profiles associated with individual virtual servers for specific attack remediation on a more granular basis.
  • Set a lower detection and rate limiting thresholds for attack vectors where there is no level of wanted traffic.
  • Add critical infrastructure to the DoS White List.

Knowing the order in which the different DoS mechanisms operate may help you troubleshoot unexpected results.

DoS reporting and visibility

After a DoS protection is configured on the BIG-IP system, charts, reports, statistics, and event logs related to DoS attacks and mitigations are available on the system. For example, a DoS Overview page shows at-a-glance whether the system is under attack. It also indicates the impact of DoS attacks on the BIG-IP system performance.

Other reports show transaction outcomes and correlate the impact of system detection with the mitigation of DoS attacks. The reports and event logs can show whether DoS protection is functioning properly or whether tuning is necessary. They can also help identify and track DoS attacks. Analyzing attack and trend data can provide insight into DoS threats.

Note: To allow DoS data to populate DoS reports on a virtual server basis, you must associate a DoS profile with one or more virtual servers.

DoS Overview: The DoS Overview displays real-time information about all DoS attacks on the system. The system displays recent attacks.

Viewing the DoS Overview using the Configuration utility

  • Go to Security > Overview > DoS.

Logged Attacks shows a flag for an attack in progress. The log includes the 100 most recent events per protocol for application and network attacks. Up to 200 attacks may be shown in the charts. If the information you want is not shown, try increasing the time period selected in the filter.

You can filter your view by attack impact (High Impact, Medium Impact, or Low Impact). To focus in on the specific details in the charts, hover on the chart for the time period of interest. The system displays in a tooltip the details about what was happening at that time.

To learn more about attacks that have occurred, select the Attack ID number in the Historical & Recent Attacks Log.

The system displays events associated with the attack. If there are more than 100 events, there is a link to the event log, which you can select to see more events.

The Overview page includes information on throughput, RAM, and CPU usage. Because the statistics vary from system to system, it is a good idea to become familiar with typical memory and CPU usage and throughput on your system in association with recent attacks.

DoS profile logging

Requirements to log DoS Profile events include:

  • Enabled DoS logging within the log profile.
  • Assign the logging profile within the virtual server that the DoS Profile is being used.

Configuring DoS logging with a log profile using the Configuration utility

  1. Go to Security > Event Logs > Logging Profiles and select logging profile.
  2. For DoS Protection , select the check box to enable it.
  3. For DoS Protection, select the publisher.
  4. Select Update.

Enabling a logging profile on the virtual server using the Configuration utility

  1. Go to the virtual server properties Local Traffic > Virtual Servers > Virtual Server List.
  2. Select the virtual server.
  3. Select the Security tab and select Policies.
  4. For Log Profile, select Enabled.
  5. Select the logging profile from the Available list and move it to the Selected list.
  6. Select Update.

Signaling and intelligence

The BIG-IP AFM can block bad actors based on external sources of data or other processes within the BIG-IP platform. This allows the BIG-IP to dynamically react to DoS attacks based on numerous sources of intelligence.

Within BIG-IP AFM, the virtual server DoS profile sweep detection feature can provide intelligence to allow bad actors to be blocked automatically for a pre-defined period of time based on the detection threshold. This blocking configuration is mapped to an IP Intelligence category.

Additionally, blacklists can be created from external intelligence sources. F5 offers a subscription IP-intelligence service for categorization of discovered bad actors and allows the implementation of custom IP Intelligence policies.

To get a feed list for IP Intelligence, the configuration requires an external host to provide via either a website or FTP server a list of offending IP addresses.

The update interval is configured to specify the timeframe in which BIG-IP AFM regularly polls the server for updates. If an update poll fails, BIG-IP AFM continues to use the last known good list. The feed list is a simple CSV file.

Configuring the external feed list using tmsh

  • Enter the following command syntax:

    tmsh create /security ip-intelligence feed-list extBlacklist feeds add { <NAME> { default-blacklist-category <CATEGORY> default-list-type <BLACKLIST/WHITELIST> poll { url <URL> interval <INTERVAL> } } }
