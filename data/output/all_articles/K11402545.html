Issue

On a BIG-IP system that is licensed for F5 Full-Box FIPS, you can manually perform FIPS integrity checks. The system also automatically performs scheduled checks on a regular basis. Manual check results display on the console, and scheduled checks log to the /var/log/secure file. If an integrity check fails, the system fails to boot when restarted.

You should consider using this procedure under the following condition:

  • You have a BIG-IP system licensed with the Full-Box FIPS add-on license and an integrity check fails.

Symptoms

Symptoms include the following, when the system is operating and accessible:

  • You observe the error BIG-IP Integrity Check: [ FAIL ] -- Contact F5 Networks technical support in the /var/log/secure file.
  • A manual integrity check fails.

Note: If your system fails an integrity check when you turn it on and does not finish the boot procedure, see K42169041: Troubleshooting FIPS power-on self-test failures for troubleshooting and recovery information.

Important: If FIPS displays a fail status, the BIG-IP system does not boot to the current volume the next time it restarts. Therefore, it is important that you resolve any issues before you restart your system.

Recommended Actions

When troubleshooting FIPS self-test failures, review the following documents:

  • Your internal security policies
  • The release notes for your specific BIG-IP version
  • FIPS Platform Setup in F5 Platforms: FIPS Administration

    Note: For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.

Important: An integrity check failure indicates that some part of the BIG-IP software has unexpectedly changed. This may indicate that an attacker has gained access to your system and changed, installed, or removed something on the BIG-IP system. You should review your internal security policies prior to taking any further actions as they may require or prohibit specific troubleshooting procedures.

Procedures

Important: Do not restart your BIG-IP system during any of the steps in the following troubleshooting steps. When the BIG-IP system starts, it performs an integrity test again, and if this test fails, the system stops the boot process and disables that volume, restricting further troubleshooting. If this occurs, you need to use the procedures found in K42169041: Troubleshooting FIPS power-on self-test failures.

When your system experiences FIPS integrity check issues, you can use the following troubleshooting steps to determine the root cause:

  1. Backing up your system and upload a QKView file to F5 iHealth.
  2. Running sys-eicheck to find failed files.
  3. Determining the time window of the failure.
  4. Reviewing administrative actions during the failure time window.
  5. Backing out any changes made during the failure time window.
  6. Reloading your backup file on a new partition.
  7. Determining whether your system is compromised

Backing up your system and upload a QKView file to F5 iHealth

Back up your configuration to a user configuration set (UCS) file.

Note: Consider whether you may include the cause of the failure in your UCS file when you back up your system.

Run a QKView file using the qkview utility and upload it to F5 Technical Support using F5 iHealth.

Refer to the following articles:

  • K13132: Backing up and restoring BIG-IP configuration files (11.x - 13.x).
  • K12878: Generating diagnostic data using the qkview utility

Running sys-eicheck to find failed files

For information about running and analyzing sys-eicheck, refer to K00029945: Using the sys-eicheck (FIPS) utility

Determining the time window of the failure

BIG-IP systems licensed with the F5 FIPS (Full Box) run sys-eicheck on a daily basis. This check logs to the /var/log/secure file. View the time stamp on the first BIG-IP Integrity Check: [ FAIL ] -- Contact F5 Networks technical support message and the time stamp of the last successful check from the most recent BIG-IP Integrity Check: [ PASS ] message. The period between the two messages is the failure time window.

Reviewing administrative actions during the failure time window

  1. Review the list of changed files to narrow the potential actions that may impact them.

    For example, if system files were removed or changed, administrative actions are unlikely to impact them.

  2. Review any known administrative actions that occurred within the time window. To determine this, use information from the following sources:
    • Internal change control or trouble ticket documentation.
    • The BIG-IP audit log file: /var/log/audit.
    • Other BIG-IP logs, as appropriate.

Normal administrative actions performed using the Configuration utility or TMOS Shell (tmsh) commands should not cause integrity checks to fail. The most likely causes of failure are actions to troubleshoot problems or actions that impact the underlying Linux operating system, such as installing or modifying the Linux system software.

Backing out changes made during the failure time window

If any administrative actions occurred during the time window, consider backing these changes out and running the integrity check again. Depending on the actions, you may or may not be able to back them out. If you cannot back them out, you may need to reload the system configuration on a new partition using your UCS file.

After backing out changes, run sys-eicheck again to determine whether the problem is resolved.

Reloading your backup file on a new partition

Impact of procedure: If the problem is not resolved before booting into the new partition, you cannot access the current partition again. You should perform this action only as a last resort if you cannot otherwise resolve the issue.

  1. Create a new partition with the appropriate software version. For more information, refer to K34745165: Managing software images on the BIG-IP system using the tmsh utility.
  2. Restore your UCS backup to this partition. For more information, refer to K13132: Backing up and restoring BIG-IP configuration files (11.x - 13.x).

Note: Reloading your UCS file on a new partition may not solve the issue. If it does not, it is possible that the cause of the problem is included in your UCS file.
Important: Do not use your only remaining backup partition. Doing so may restore the problem along with the UCS on that partition, making it also unusable and potentially making it impossible to restart and boot the system. If this occurs, you need to re-image your system. .

Determining whether your system is compromised

You should base your final determination on whether your system is compromised based on your organization's security policy. If you are unable to determine any known administrative changes that occurred during the failure time window, you should review and follow your policies for devices that are suspected of being compromised.

In such cases, you can open a support ticket with F5 Technical Support. F5 may be unable to make a final determination whether a device is compromised if it requires deeper forensic analysis than F5 support procedures allow. In such cases, F5 recommends contacting a trusted forensic security firm for a final determination if it is necessary to determine whether the device is compromised.
