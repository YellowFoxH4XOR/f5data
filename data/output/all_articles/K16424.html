Known Issue

The iRule HTTP_DISABLED event may not be triggered.

This issue occurs when all of the following conditions are met:

  • You have configured a virtual server to process HTTP traffic.
  • The virtual server references an iRule that uses the HTTP_DISABLED event.
  • HTTP processing is switched into pass-through mode by one of the following:

    • The HTTP::disable command
    • CONNECT requests
    • Web-sockets traffic

Impact

The HTTP_DISABLED event is not triggered.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • The HTTP_DISABLED event is not triggered.

Workaround

To work around this issue, you can modify your iRule logic depending on which condition prevents the HTTP_DISABLED event from being triggering. To do so, perform one of the following procedures:

Impact of workaround: Performing the following procedures should not have a negative impact on your system.

The HTTP::disabled command

  • Add logging code within the HTTP_DISABLED event, after the iRule command.

CONNECT events

  1. Use an iRule to match the method in the HTTP_REQUEST event.
  2. Verify that 200 Connected is returned as the status in the HTTP_RESPONSE event.
  3. Invoke the logging code within the HTTP_DISABLED event.

Web-sockets protocol

  1. Use an iRule to match the 101 Switching Protocols status code in the HTTP_RESPONSE event.
  2. Invoke the logging code that is also within the HTTP_DISABLED event.
