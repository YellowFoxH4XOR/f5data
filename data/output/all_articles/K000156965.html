Description

  • When configuring BIG-IP Telemetry Streaming (TS) to forward LTM request logs to a Generic HTTP consumer, the expected logs may not appear at the remote HTTP endpoint.
  • The request-log profile is attached to a virtual server, and the telemetry declaration includes a properly defined Generic HTTP consumer. However, no log data is received by the destination. Trace logs do not show errors, and packet captures may lack evidence of HTTP POST requests being sent.

Environment

  • Product: BIG-IP LTM
  • Telemetry Streaming extension configured with:
    • Telemetry Listener (default port 6514)
    • Generic HTTP Consumer (custom port such as 8085 or 9570)
    • LTM request-log profile attached to a virtual server
    • Request-log pool forwarding logs to a pool member (e.g., syslog-tls port)

 

  • Example request-log template: 
    event_source="request_logging",hostname="$BIGIP_HOSTNAME",client_ip="$CLIENT_IP",server_ip="$SERVER_IP",http_method="$HTTP_METHOD",http_uri="$HTTP_URI",virtual_name="$VIRTUAL_NAME",event_timestamp="$DATE_HTTP"

Cause

  • Logs are not delivered because the configuration path between the LTM request-log profile and the Telemetry Streaming listener/consumer is incomplete or incorrect. If the request-log profile sends logs to a pool that does not route traffic correctly to the local TS listener (typically on loopback interface and port 6514), or if loopback addresses are not allowed for node selection in pools/iRules, then logs will not be processed or forwarded.

Recommended Actions

  1.  Configure Request-Log Profile Correctly:
    1. Ensure the request-log-pool in your LTM request-log profile points to a pool whose member is the loopback address (e.g., 127.0.0.1 or local self IP) and uses the port where TS listens (default: 6514)
    2. Example configuration:

 

ltm pool telemetry {
    members {
        <loopback_or_self_ip>:6514 { address <loopback_or_self_ip> }
    }
}

 

  1. Allow Loopback Node Selection:
    1. Enable use of loopback addresses for node selection by setting this database variable:

 

tmsh modify sys db tmm.tcl.rule.node.allow_loopback_addresses value true

 

  1. Verify Telemetry Streaming Declaration:
    1. Your declaration should include both a telemetry_listener on port 6514 and a generic HTTP consumer with accurate endpoint details
    2. Example Generic HTTP declaration

 

{
  "class": "Telemetry",
  "Event_Listener": {
    "class": "Telemetry_Listener",
    "port": 6514,
    "enable": true
  },
  "Generic_HTTP_Consumer": {
    "class": "Telemetry_Consumer",
    "type": "Generic_HTTP",
    "host": "<remote_http_endpoint>",
    "port": <port>,
    "path": "/",
    "protocol": "http",
    "method": "POST",
    "outputMode": "processed",
    "allowSelfSignedCert": false,
    "headers": [
      { "name": "Content-Type", "value": "application/json" }
    ]
  }
}

 

  1. Test End-to-End Connectivity:
    1. Use curl from BIG-IP shell to verify remote endpoint accessibility:
    2. Example command syntax:

 

curl -s -X POST http://<remote_http_endpoint>:<port>/ \
     -H 'Content-Type: application/json' \
     -d '{"metric":"cpu_usage","value":75.4}'

 

  1. Packet Capture & Troubleshooting:
    1. Use tcpdump/tshark on BIG-IP to confirm that log messages are sent from BIG-IP → TS listener → remote HTTP consumer.
    2. Look for outbound HTTP POST requests on your configured ports.
