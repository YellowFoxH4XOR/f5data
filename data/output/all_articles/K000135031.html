K000135031: How to handle high Client SSL throughput on the BIG-IP i4600 platform

Published

Description

Guidance and considerations when using software-accelerated ciphers on the BIG-IP i4600 platform.

Environment

  • BIG-IP i4600 platform
  • BIG-IP LTM and ASM provisioned
  • Client SSL profiles in use

Recommended Actions

TLS Cipher and DH Group selection
 
F5 recommends preferring hardware accelerated ciphers for best performance and greatest capacity, where this is acceptable to the business use-case. For example, the "f5-secure" default cipher group enables some ciphers and DH groups which are handled only in software such as ChaCha20-Poly1305 and the X25519 curve and the "f5-default" cipher group enables the X25519 curve. F5 recommends reviewing your cipher and DH group selection against the list of hardware accelerated ciphers in K13213 and using only hardware accelerated ciphers where possible, along with disabling any software-only ciphers on platforms such as the i4600 or where CPU capacity is restricted. The default configuration contains both hardware accelerated, and non-hardware accelerated ciphers to balance performance, security, and optimal compatibility.
This can be achieved by configuring a custom cipher rule with Cipher Suites set to “DEFAULT” (which does not enable ChaCha20-Poly1305), DH Groups set to “P256:P384:FFDHE2048:FFDHE3072:FFDHE4096” and Signature Algorithms to “DEFAULT”. The resulting combination of Cipher Suites and DH Groups should be reviewed against your business needs using the Rule Audit display of the Configuration Utility.

Enforce a limit on the maximum number of outstanding SSL handshakes
 
By default, the BIG-IP does not limit the number of concurrent active SSL handshakes unless the device has a limited license (e.g., the BIG-IP i4600 ships with a license limit of 10,000 TPS while the i4800 is limited only by hardware performance). F5 believes this to be the optimal default choice, given that it provides the highest likelihood of clients receiving a response under a variety of scenarios. However, during an attack, or when the device's capacity limit is exceeded, this could lead to the BIG-IP queuing an excessive number of handshakes. This could potentially lead to a depletion of the available memory resources and disrupt client connections. Furthermore, the excess load from queued handshakes might activate a fail-over procedure, where the system switches to a standby mode in an effort to preserve functionality and maintain service availability by passing traffic to an available HA group member where possible. Note: Continued traffic above the configuration capacity ceiling can cause rapid fail-overs between HA group members which will still result in an effective outage.

If there are no Denial-of-Service protections active earlier in the connection flow (e.g., BIG-IP AFM's L4DOS or IP Shunning, both of which may be performed in hardware ahead of the TLS handshake being handled), F5 recommends capping the number of active handshakes. On a BIG-IP i4600 provisioned with BIG-IP LTM and ASM the suggested number is 100,000 which can be configured by following the instructions in K83167850.

Apply a layered Denial of Service configuration using BIG-IP AFM
 
F5 recommends deploying BIG-IP AFM with Layer 4 Denial of Service protection (this can be on the same device) with appropriately configured limits to suit the expected traffic patterns and the throughput capability of the device given its unique configuration. Some attack vectors in the DOS protection profile provide the option to configure bad actor detection, this option allows deny-listing bad actor IP addresses with specific thresholds and time limits. Wherever possible, it is highly recommended to configure this option.   Professional Services can provide design assistance if necessary through a paid engagement.

License and configure the IP Intelligence feature

F5 recommends using the IP Intelligence feature to quickly block IP addresses known to be malicious. IP Intelligence can be used with any BIG-IP product (LTM, DNS, AFM, ASM, APM) but does require a separate subscription license. Depending on the BIG-IP product, IP Intelligence can be enabled using built-in product options or an iRule. The IP Intelligence database updates automatically as often as every five minutes, and no manual intervention is required.

For more information, see the following links:
  • https://www.f5.com/pdf/products/ip-intelligence-service-ds.pdf
  • https://techdocs.f5.com/en-us/bigip-14-1-0/big-ip-asm-implementations-14-1-0/setting-up-ip-address-intelligence-blocking.html
  • https://techdocs.f5.com/en-us/bigip-15-1-0/big-ip-network-firewall-policies-and-implementations/configuring-ip-address-intelligence-in-the-network-firewall.html

Make use of Virtual Server connection rate limit feature

To limit the number of connections per second as a stop-gap denial of service mitigation, F5 recommends using the Virtual Server connection rate limit feature built in to core BIG-IP functionality. Ideally, DoS mitigation features from AFM or ASM are recommended but there are instances that these modules are not licensed, and a Virtual Server connection rate limit can provide relief in times of unexpected traffic increase and drop connections exceeding the defined limit.  
See K45530602: Limiting the number of connections to a Virtual Server for more information.

Configure IP Shunning where BIG-IP ASM is available
 
F5 recommends utilizing the IP Shunning functionality of BIG-IP ASM where appropriate to ensure that malicious clients, once detected, have their IP addresses added to a hardware accelerated shun list. This ensures that any future TLS handshakes from shunned clients are dropped prior to being handled by the cryptographic functions within the BIG-IP.
  • This strategy is successful as long as a sufficient volume of traffic from these clients, which failed the configured tests (e.g., CAPTCHA, client-side integrity defense, proactive bot defense, etc.), has already been processed. This enables the IP addresses to be added to the shun list promptly, thereby preempting any detrimental impact on TLS throughput or system stability.
  • More information on how to configure Layer 7 DoS protection for your specific environment can be found in the ASM Implementation guide, e.g.: https://techdocs.f5.com/en-us/bigip-17-0-0/big-ip-asm-implementations/using-shun-with-layer-7-dos.html
