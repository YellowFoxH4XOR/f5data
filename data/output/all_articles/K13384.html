Topic

This article applies to BIG-IP 11.x through 16.x. For information about other versions, refer to the following article:

  • K11125: Performing a web applications trace (10.x)

You should consider using this procedure under the following conditions:

  • Users cannot access a web application through a BIG-IP APM Portal Access resource.
  • Web pages do not fully load when accessed through a BIG-IP APM Portal Access resource.
  • Web pages display error messages when accessed through a BIG-IP APM Portal Access resource.

Description

To troubleshoot issues with a particular web application, you can use the web application's engine trace feature offered in the BIG-IP APM system. This feature generates a trace file that contains the HTTP request and response exchanged between the client and the BIG-IP APM system, and also the HTTP request and response exchanged between the BIG-IP APM system and the back-end web server. You can determine whether the modifications made by the web application's engine are affecting the functionality of the web application by comparing the front-end request and response with the back-end request and response.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • Your BIG-IP APM system is configured with a web application.

Procedures

When experiencing web application issues, you can use the following procedure to collect a trace of the web application engine, and then analyze the trace file.

Configuring the BIG-IP APM system to capture a web application session to a trace file

  1. Instruct a user, who is assigned the affected web application, to log in to the BIG-IP APM system.
  2. Log in to the BIG-IP command line.
  3. To obtain the user's session ID, use the following command syntax, where <username> is the logon name of the user from step 1:

    sessiondump -allkeys | grep -i <username>

    For example:

    65a6b075.session.assigned.uuid 26 tmm.uuid.AD-Basic.jsmith
    65a6b075.session.logon.ad_auth_and_resources_act_logon_page_ag.username 8 jsmith
    65a6b075.session.logon.last.username 8 jsmith

    The session ID appears at the beginning of the line of output. In this example, the session ID for the user jsmith is 65a6b075.

  4. Enable a web applications trace for the session ID you recorded in the previous step, by using the following command syntax, where <session-id> is the session ID recorded in step 3.

    tmsh modify /sys db "log.webapplications.trace.sessionid" { value "<session-id>" }

    For example:

    tmsh modify /sys db "log.webapplications.trace.sessionid" { value "65a6b075" }

  5. Instruct the user to access the affected web application.
  6. After the user accesses the application, change directories to the directory of the webtrace by using the following command syntax:

    cd /var/tmp/WebAppTrace/<sessionid>

    In this command, note the following:

    • <sessionid> is the user's session ID

      For example:

      cd /var/tmp/WebAppTrace/65a6b075/

  7. To create the webtrace.tgz file and add the webtrace data, type the following command:

    /usr/bin/webtrace.finish

  8. Copy the webtrace.tgz file your local workstation.
  9. On the local workstation, extract the webtrace.tgz file, and open the index.html file to view the trace file.
  10. To disable the web applications trace, type the following command:

    tmsh modify /sys db "log.webapplications.trace.sessionid" { value " " }

Analyzing the trace file

To analyze the trace file you generated in the previous procedure, look at the following four sections of the trace file:

  • Requests
  • Request log
  • Front-end request/response
  • Back-end request/response

Requests

This section contains a list of HTTP requests sent from the client to the BIG-IP APM system. Click the request that you want to examine, which will populate the corresponding data in the other three sections of the index.html page.

The following example shows the requests made by the client:

16:54:21 6408 GET /
16:54:21 6408 GET /about.gif
16:54:21 6408 GET /pagerror.gif

Request log

This section contains a brief summary of the HTTP request and response.

For example:

New front-end request/response
# pid = 6408
# initializePatchInfo()
Front-end request: GET /
Parsing front-end request
URL: /
Context Hint: U
New back-end request/response
set Context Hint from content type: U
guess Content type returns HTML
final processContent egress release returns 151546456

Front-end request/response

This section contains the HTTP request sent from the client to the BIG-IP APM system, and the HTTP response from BIG-IP APM system to the client. The response is color coded with the changes that the web application engine made to the HTML code. For information about the color-coded sections, refer to the legend at the bottom of the front-end request/response window.

Note: The front-end response contains the web application content after it was rewritten by the web applications engine.

The following example shows the changed web link from the original URI to the address of the virtual server / the encoded URI of the original link. This redirects the href link to the virtual server:

<span class="submenu" id="sub3">
- <a href="https://10.1.1.64/f5-w-687474703a2f2f7777772e636f64696e67666f72756d732e636f6d$$/">Coding Forums</a><br>

Legend:

HTML REF

Note: The actual front-end request/response section has a background/text color highlight feature to indicate the changes.

Back-end request/response

This section contains the HTTP request sent from the BIG-IP APM system to the back-end web server, and the HTTP response from the back-end web server to the BIG-IP APM system. The response is color coded with the changes that the web application engine made to the HTML code. For information about the color-coded sections, refer to the legend at the bottom of the back-end request/response window.

Note: The back-end response contains the web application content before it was rewritten by the web applications engine.

The following example shows the back-end response from the server before the web application engine rewrites the href value:

<span class="submenu" id="sub3">
- <a href="http://www.example.com">Coding Forums</a><br>
</span>

Legend:

HTML REF

You can use the results of the trace to determine whether the rewriting performed by the web applications engine is impacting the functionality of the web application by comparing the data in the front-end request/response to the data in the back-end request/response.
