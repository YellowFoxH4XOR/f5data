K40453455: Portal Access to an internal HTTPS site fails when the server requires SNI

Type
Support Solution
Published
2022-03-08
Updated
2026-10-30
Applies to
  • BIG-IP
  • BIG-IP APM
Source
https://my.f5.com/manage/s/article/K40453455

Description

You access an HTTPS back-end application through a BIG-IP APM Portal Access resource, and the application does not load. When the BIG-IP system connects to the back-end server, the server closes the connection with a TCP reset after the BIG-IP system sends the TLS Client Hello.

Environment

  • BIG-IP APM 17.1.x, 17.5.x, or 21.1.x

  • One or more Portal Access resources that use HTTPS

  • A Server SSL profile on the Portal Access virtual server

  • A back-end server that requires the Server Name Indication (SNI) TLS extension

Cause

The back-end server requires SNI. One Portal Access virtual server can serve many Portal Access resources with different host names, and the Server SSL profile of the virtual server is not configured to send the SNI extension with the host name of each Portal Access resource.

The Portal Access section of the BIG-IP APM Client Compatibility Matrix states that Portal Access and web applications do not support TLS Server Name Indication (SNI), and that you can mitigate this issue with an iRule.

Answer/Recommended Actions

You can use one of the following options:

  • Option 1: Send the SNI extension for every Portal Access host. Use this option when the back-end servers require SNI with their own host name.

  • Option 2: Use a different Server SSL profile for one Portal Access host. Use this option when one back-end server needs a specific SNI configuration in its Server SSL profile.

Both iRules read the back-end host name in the REWRITE_REQUEST_DONE event, after Portal Access has rewritten the request. If the iRule logs a TCL error from HTTP::host in this event, refer to K000158986: iRule error ERR_ARG for HTTP::host or HTTP::path in the REWRITE_REQUEST_DONE event.

Impact of procedure: F5 recommends performing this procedure during a scheduled maintenance window. Test the iRule in a non-production environment first.

Note: F5 Support does not design or configure iRules. If you need help to adapt an iRule to your environment, contact F5 Professional Services.

Option 1: Send the SNI extension for every Portal Access host

  1. Log in to the Configuration utility.

  2. Go to Local Traffic > iRules > iRule List.

  3. Click Create.

  4. Enter a name for the iRule, for example apm_portal_sni.

  5. In Definition, enter the following iRule:

    when REWRITE_REQUEST_DONE {
    #log local0. "HOST: [HTTP::host]"
    set sni_value [getfield [HTTP::host] ":" 1]
    }
    when SERVERSSL_CLIENTHELLO_SEND {
    # SNI extension record as defined in RFC 3546/3.1
    #
    # - TLS Extension Type                = int16( 0 = SNI )
    # - TLS Extension Length             = int16( $sni_length + 5 byte )
    #    - SNI Record Length             = int16( $sni_length + 3 byte)
    #     - SNI Record Type             = int8( 0 = HOST )
    #         - SNI Record Value Length = int16( $sni_length )
    #         - SNI Record Value         =    str( $sni_value )
    #
    # Calculate the length of the SNI value, Compute the SNI Record / TLS extension fields and add the result to the SERVERSSL_CLIENTHELLO
    SSL::extensions insert [binary format SSScSa* 0 [expr { [set sni_length [string length $sni_value]] + 5 }] [expr { $sni_length + 3 }] 0 $sni_length $sni_value]
    }

  6. Click Finished.

  7. Go to Local Traffic > Virtual Servers > Virtual Server List, and click the name of the Portal Access virtual server.

  8. Click the Resources tab.

  9. In the iRules section, click Manage.

  10. Move the iRule from Available to Enabled, and click Finished.

  11. Start a new access session, and verify that the application loads.

To back out of this procedure, move the iRule from Enabled to Available.

Option 2: Use a different Server SSL profile for one Portal Access host

  1. Create a Server SSL profile with the settings that the back-end server needs, for example the SNI value of that server, configured in the Server SSL profile.

  2. Create an iRule with the following definition (use the same steps as in Option 1):

    when REWRITE_REQUEST_DONE {
        if { [HTTP::host] == "example" } {
            set changeSSLProfile 1
        }
    }
    when SERVER_CONNECTED {
        if { [info exists changeSSLProfile] && $changeSSLProfile } {
            SSL::profile your-specific-serverssl-profile
            unset changeSSLProfile
        }
    }

    Replace the following values:

    • example: the Host header value (FQDN) that the back-end server expects, for example application.example.com.

    • your-specific-serverssl-profile: the name of the Server SSL profile that you created in step 1.

  3. Add the iRule to the Portal Access virtual server, as in Option 1, steps 7 to 10.

  4. Start a new access session, and verify that the application loads.

To back out of this procedure, move the iRule from Enabled to Available.
