K000150375: Troubleshooting LTM Policy causing TCP Resets

Source

Description

A LTM Policy configured to switch traffic across LTM pools based on the host header of HTTP requests, can cause random TCP Resets for a specific HTTP Host Header. A TCP Reset can happen during or right after the TLS Handshake, which can be seen in logged RST reasons on the BIG-IP.

For such behavior, the below specific TCP Reset indication can be seen in the packet capture:

[F5RST: No server selected]

Environment

  • BIG-IP LTM
  • LTM Policy
  • Traffic distribution based on the HTTP Header

Cause

The TCP reset (RST) with the reason `[F5RST: No server selected]` indicates that the BIG-IP system was unable to select a Pool or backend server for the incoming request.

This typically happens when:

  • No Default Pool is Configured

The Virtual Server does not have a default Pool assigned, and traffic routing relies entirely on an LTM Policy or iRules to select a pool dynamically.

  • LTM Policy Conditions Not Met

The conditions in the LTM Policy did not match the incoming request attributes (e.g., HTTP Host Header).

As a result, no Pool was selected for load balancing.

  • Mismatch in Request Attributes

The Java applet may be sending an HTTP Host header that does not match any of the conditions defined in the LTM Policy.

Recommended Actions

1) Verify LTM Policy Configuration

- Check if all possible Host Headers sent by Clients (including those from Java applets) are accounted for in your LTM Policy

- Ensure there is a fallback/default action defined in the LTM Policy in case none of the conditions match.

 

2) Inspect Traffic from Java Applet

- Use packet captures to analyze what HTTP headers are being sent by the Java applet.

- Compare these headers with those sent by browsers where no issue occurs.

 

3) Review TLS Settings

- Ensure that TLS settings align with both browser and Java applet requirements.

- Verify whether any differences between browser and applet behavior during the TLS negotiation could contribute to this issue.

 

By addressing these points, you should be able to identify why `[F5RST: No server selected]` occurs specifically with requests from the Java applet and resolve it effectively.
