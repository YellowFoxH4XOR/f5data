Description

It may observe that iCall periodic handlers execute on both the Active and Standby units in a high availability (HA) configuration. This behavior may be unexpected when the intention is to have scripts run only on the Active unit.

Environment

  • BIG-IP LTM (all versions supporting iCall)
  • High Availability

Cause

The iCall framework does not inherently differentiate between Active and Standby units when executing periodic handlers.

Recommended Actions

This is working as designed. By default, iCall scripts run on both units in an HA pair regardless of the failover state (Active/Standby).

To ensure iCall scripts execute only on the Active unit, you must add logic within the script to check the device's failover status before proceeding with the main script logic.

Example Implementation (Recommended Approach):

Add the following code at the beginning of your iCall script definition to check if the device is in Standby state and exit early if true:

sys icall script <script_name> {
app-service none
definition {
# Skip iCall execution if this is the standby node
catch { tmsh::show /sys failover } failover_check
if { $failover_check contains "standby" } {
return
}

# Rest of your iCall logic goes here
# ...
}
description none
events none
}

Explanation:

  1. The tmsh::show /sys failover command retrieves the current failover status
  2. The script checks if the output contains "Standby"
  3. If the device is in Standby state, the script returns immediately without executing the remaining logic
  4. If the device is Active, the script continues with its intended operations

Additional Information

  • This behavior applies to all iCall periodic handlers
  • The same approach can be used for any custom iCall scripts where execution should be limited to the Active unit
  • For iCall event handlers triggered by specific events, consider whether the event itself only occurs on the Active unit before adding this check
