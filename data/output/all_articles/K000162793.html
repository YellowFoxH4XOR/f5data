K000162793: WebSocket traffic stalls after HTTP 101 handshake

Type
Support Solution
Published
2026-09-03
Updated
2026-09-03
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000162793

Description

A customer configured WebSocket traffic on a BIG-IP virtual server. After a successful WebSocket handshake (HTTP 101 Switching Protocols), subsequent WebSocket messages were not delivered to the backend server.

The client received no data, an N/A response, or the connection silently stalled. The backend application team confirmed that no WebSocket frames were arriving at the server, despite the handshake completing successfully from the client’s perspective.

The virtual server configuration was similar to the following:

ltm virtual /Common/test {
    destination /Common/<ip>
    ip-protocol tcp
    mask 255.255.255.255
    persist {
        /Common/test {
            default yes
        }
    }
    policies {
        /Common/asm_policy { }
    }
    profiles {
        /Common/ASM_Profile { }
        /Common/HTTP { }
        /Common/clientssl {
            context clientside
        }
        /Common/OPSWAT_ICAP/Metadefender_ICAP_Request {
            context clientside
        }
        /Common/serverssl {
            context serverside
        }
        /Common/tcp { }
        /Common/websecurity { }
        /Common/websocket { }
    }

An error similar to the following may be logged in /var/log/ts/bd.log:

IO_PLUGIN|ERR   |Jan 01 13:04:17.459|1599|websocket.c:0372|101 Switching Protocols HTTP status arrived, but the websocket handshake failed.
IO_PLUGIN|ERR   |Jan 01 13:04:17.460|1599|websocket.c:0373|Possible reasons are websocket profile isn't assigned on a virtual server or handshake is illegal.

Removing the ASM policy, ASM profile, and websecurity profile did not resolve the issue. The virtual server still had the OPSWAT ICAP Request Adapt profile attached.

Environment

  • BIG-IP LTM
  • Virtual Server configured with:
    • ASM profile and policy
    • Websecurity profile
    • OPSWAT_ICAP profile
    • Websocket profile
    • HTTP profile
    • Client SSL and/or Server SSL profile

Cause

In the reported configuration, the Request Adapt/ICAP profile is a suspected cause of the WebSocket stall. Request Adapt processing is HTTP-dependent. Confirm the cause by testing the WebSocket connection with the Request Adapt profile removed or bypassed.

F5 documentation states that a standard virtual server using a Request Adapt profile must also have an HTTP profile. The Request Adapt profile sends traffic to an internal virtual server for processing by an ICAP service. More here: K15819

  1. The reported failure sequence was:

    1. The client sent an HTTP GET request containing the WebSocket upgrade headers:

      Upgrade: websocket
Connection: Upgrade
      

    2. 

      The Request Adapt profile intercepted the request and forwarded it to the configured ICAP service.
      

    3. 

      The ICAP service inspected and returned the request, allowing the handshake to continue.
      

    4. 

      The backend server responded with:
      

      HTTP/1.1 101 Switching Protocols
      

      

    5. 

      The connection transitioned from HTTP processing to WebSocket traffic.
      

    6. 

      In the reported case, subsequent WebSocket frames were not delivered to the backend server.
      

    



Recommended Actions


Two resolution options are available depending on whether ICAP scanning must be retained for other traffic on the same virtual server.


Option 1: Remove the ICAP Request Adapt profile from the virtual server (Recommended)


Use removal of the Request Adapt profile as the primary isolation test.


If WebSocket traffic works after the profile is removed and fails when the profile is reattached, retain the profile removal as the resolution for that virtual server.


If ICAP scanning must remain enabled for regular HTTP traffic on the same application, use a separate virtual server for the WebSocket traffic or selectively bypass ICAP for WebSocket upgrade requests.


Via CLI:


The following command is the configuration example for removing the Request Adapt profile:


tmsh modify ltm virtual /Common/<virtual-server-name> profiles delete { <icap-request-adapt-profile-name> }
tmsh save sys config


Verify the exact profile name, partition, context, and command syntax on the target BIG-IP release before applying the change.


Via GUI:


  1. Navigate to Local Traffic › Virtual Servers › Virtual Server List.
  2. Click the name of the affected virtual server.
  3. From the Configuration drop-down, select Advanced.
  4. In the Profiles section, locate the Request Adapt profile (e.g., Metadefender_ICAP_Request).
  5. Click the Delete (×) button next to it.
  6. Click Update.
  7. Re-test the WebSocket connection.


Option 2: Selectively disable ICAP for WebSocket upgrade requests using an iRule
If ICAP scanning must remain on the virtual server for regular HTTP traffic (e.g., file uploads via HTTP POST), use an iRule to disable ICAP adaptation specifically for WebSocket upgrade requests. This allows ICAP to continue scanning normal HTTP traffic while bypassing it for WebSocket connections.


This approach is based on the ADAPT::enable command documented in K000159822. This documents selective ICAP control for HTTP requests; it does not specifically validate this WebSocket use case. Test the following iRule on the target BIG-IP release before production deployment.


when HTTP_REQUEST {
    if { [string tolower [HTTP::header "Upgrade"]] contains "websocket" } {
        ADAPT::enable false
    }
}


Steps to apply in GUI:


  1. Navigate to Local Traffic › iRules.
  2. Click Create.
  3. Enter a name (e.g., disable_icap_for_websocket).
  4. Paste the iRule definition above into the Definition field.
  5. Click Finished.
  6. Navigate to the affected virtual server.
  7. Assign the iRule to the Virtual Server.
  8. Re-test the WebSocket connection.


Note: This iRule disables ICAP adaptation for the WebSocket upgrade request. Once the connection upgrades to WebSocket (post-101), the HTTP filter enters passthrough mode and ICAP is no longer invoked for subsequent frames. This iRule ensures the upgrade request itself is not held by the ADAPT filter, allowing the protocol transition to complete cleanly.
