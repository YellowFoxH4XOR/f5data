Topic

This article applies to BIG-IP 11.4.0 and later. For information about other versions, refer to the following article:

  • K12268: Successive HTTP requests that do not match HTTP class may bypass the BIG-IP ASM

Description

The BIG-IP load balancing component may bypass the BIG-IP ASM security policy and send subsequent HTTP requests to a pool when the requests do not match the requirements defined in the appropriate local traffic policy.

The local traffic policy forms a logical link between the local traffic components and the BIG-IP ASM security policy. Under some circumstances, once the BIG-IP system has made a load balancing decision after the first successful request that matches the local traffic policy, the BIG-IP system forwards all subsequent requests on the same connection to the same pool member, even if the requests do not meet the requirements of the assigned local traffic policy. Such requests bypass the BIG-IP ASM security policy and, without proper mitigation as described below, may potentially create a security concern by passing unchecked data to the origin web server (OWS) as long as a connection exists in the Traffic Management Microkernel (TMM) connection table.

Important: This behavior has been confirmed by F5 Product Development as by design.

The BIG-IP LTM component is designed to achieve better performance by reusing the load balancing decision it makes for an initial request on all subsequent requests on the same connection. You can prevent subsequent requests from bypassing the BIG-IP ASM system by forcing the BIG-IP LTM system to make a new load balancing decision. To do so, you may use any of the following three methodologies:

  • Configure a catch-all rule for the local traffic policy

    You should already have a local traffic policy in place that directs HTTP traffic to the BIG-IP ASM security policy. You can add an additional rule to the local traffic policy, which disables the BIG-IP ASM system for those requests that do not match the policy. To do so, you can create the following two local traffic policy rule actions:

    • Target: ASM, Action: disable
    • Target: forward, Action: reset

      For example, the following rule called asm_disable has one rule action that uses a target of ASM and an Action of disable, and another rule action that uses a Target of forward and an Action of reset.

      -----------------------------------------------------
      | Rule Action Invoked Succeeded
      -----------------------------------------------------
      | asm_disable 0 [forward reset] 0 0
      | asm_disable 1 [asm disable] 0 0

  • OneConnect

    You can associate a OneConnect profile with the virtual server to facilitate a new load balancing decision for subsequent HTTP requests. This option is possible if more than one pool or local traffic policy is configured. This can be a combination of two local traffic policies, each with their own pool, assigned to the same virtual server, or one local traffic policy with a pool assigned, and a regular default pool assigned to the same virtual server.

  • iRules with LB-related commands (snat, pool, nexthop, snatpool, vlan, forward, virtual, use, etc.)

    You can use an iRule to force a new load balancing decision for subsequent HTTP requests. This option also requires two pools. For more information about using iRules to load balance to multiple pools for virtual servers not using OneConnect, refer to K9800: Using an iRule to load balance HTTP requests to multiple pools.
