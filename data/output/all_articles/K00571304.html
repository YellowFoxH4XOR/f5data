Known Issue

Azure Active Directory, AD will soon require strong encryption ciphers for all communications, causing JSON Web Keys (JWK) update requests from BIG-IP APM to Azure AD to fail. For more information on Azure AD cipher requirement changes, refer to Enable support for TLS 1.2 in your environment for Azure AD TLS 1.1 and 1.0 deprecation.

Note: This link takes you to a resource outside of AskF5, and it is possible that the document may be removed without our knowledge.

This issue occurs when all of the following conditions are met:

  • You configure an OAuth Client agent to authenticate users in an BIG-IP APM access policy.
  • The OAuth Client agent authenticates users against Azure AD tenants using JWT tokens.

Beginning from BIG-IP APM 13.1.0, F5 includes OpenID Connect Client and Resource Server features. These allow incoming users and clients to authenticate against per-session, per-request, and API Protection access profiles. The authentication is performed on an incoming transparent JSON Web Token, JWT token using an OAuth Client agent at some point during access policy execution. The OAuth Client agent behavior is driven from both its own configuration and that of its associated OAuth Provider object. This OAuth Provider in Internal Validation Mode has a JWT Provider List that is dynamically updated from Microsoft.

To provide authentication security, the incoming JWT is validated against a dynamically updated list of JWK keys, known as Internal Validation mode. Azure AD and BIG-IP APM interoperate on Internal Validation Mode only. Because the discovery process does not support strong encryption ciphers, the discovery process fail, eventually leading to failed authentications as the JWK expires.

To list the OAuth Client agents configured on your BIG-IP system, enter the following command in bash:

tmsh list apm policy agent aaa-oauth

When you observe an output for a OAuth Client agent that contains a jwt-provider-list configuration for an Azure provider in internal validation mode, similar to the following example, you may be affected:

apm policy agent aaa-oauth test-standard_act_oauth_scope_ag {
jwt-provider-list cloudExample_AzureB2C_provider_list
token-validation-mode internal
type scope
}

Impact

OpenID Connect Discovery and JWK updates fail.

This issue only impacts OpenID Connect Discovery and JWK updates; all other BIG-IP functions support strong encryption ciphers.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The discovery of JWT and key configurations from Azure AD fails. You observe the failure on the BIG-IP configuration utility when you go to Access > Federation > OAuth Client / Resource Server > Provider. For your Azure AD provider, under the Task Status column, you observe an error.
  • When you go to Access > Federation > OAuth Client / Resource Server > Provider , in the affected provider, for OpenID URI, you select Discover and the discovery process fails.
  • When the discovery process fails, you may observe an error in the /var/log/restjavad.0.log and /var/log/webui.log files similar to the following example:

    provider.ProviderFacade:processRequest - Exception:
    com.f5.openid.connect.ProviderMetadataException: Error in processing URL https://auth.example.name/auth/realms/... The message is - javax.net.ssl.SSLHandshakeException: Received fatal alert: handshake_failure

Workaround

To work around this issue, you can reconfigure your AzureAD Enterprise Application to use SAML rather than OpenID Connect.
