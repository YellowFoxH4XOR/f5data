K000162129: CPU Pinning and TMM Distribution Issues on BIG-IP VE in Oracle Cloud Infrastructure (OCI) with ve.scheduler.cputhreaded

Type
Support Solution
Published
2026-07-07
Updated
2026-07-07
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000162129

Description

When using BIG-IP LTM Virtual Edition (VE) in Oracle Cloud Infrastructure (OCI) with the database variable ve.scheduler.cputhreaded set to true, the DB key is introduced with the fix of ID1178225 , TMM processes may not be distributed as expected across CPU cores. After restarting TMM, the system may continue to use sequential logical CPUs, resulting in an uneven distribution of TMMs and suboptimal CPU utilization. This occurs when the system memory and CPU core count lead to a calculated TMM count that cannot be evenly distributed.

Environment

  • Product: BIG-IP LTM VE
  • Platform: Oracle Cloud Infrastructure (OCI)
  • Version: 17.5.1.6 (and other versions with the fix if ID1178225)
  • CPU: AMD EPYC (various models)

Cause

Example configuration:

  • CPU:4 physical cores with 2 threads per core (8 logical CPUs)

4 cores with 8 core. logical sibling cores are assigned with numerically adjacent numbers:

[root@bigip01:Active:Standalone] config # lscpu -e

  • Memory: ~9.9GB (issue observed),
  • Configuration:
    • ve.scheduler.cputhreaded set to true

[root@bigip01:Active:Standalone] config # tmsh list sys db ve.scheduler.cputhreaded

sys db ve.scheduler.cputhreaded {

value "true"

}


  • Observed behavior: 6 TMMs started, but not evenly distributed across 4 physical cores

6 TMMs only pinned on first 3 cores.

When the calculated number of TMMs (e.g., 6) cannot be evenly distributed across the available physical cores (e.g., 4), the CPU mask calculation aborts and falls back to sequential pinning. This results in all TMMs being pinned to a subset of the available cores, leaving some cores idle and causing uneven CPU utilization.


Answer/Recommended Actions

  • Increase the system memory to 16GB. This will allow the system to provision 8 TMMs, which can be evenly distributed (2 TMMs per core on a 4-core system), ensuring all cores are utilized.
  • After increasing memory, restart the BIG-IP VE instance to allow the new TMM distribution to take effect.
  • Verify TMM distribution using the following commands:

Additional Information

  • The current behavior is considered "working as intended" given the constraints of the bug. The workaround of increasing memory to 16GB is recommended for optimal TMM distribution in this scenario.
  • The issue is specific to situations where the calculated TMM count does not match the number of available physical cores or cannot be evenly distributed.
