Topic

This article applies to version 9.x.  For information about other versions, refer to the following article:

  • K14775: Configuring an HTTP profile to rewrite URLs so that redirects from an HTTP server specify the HTTPS protocol (10.x and 11.x)

Purpose

You should consider using this procedure under the following condition:

  • You want http:// URL responses from a pool member behind a Secure Sockets Layer  (SSL) Client profile enabled virtual server to present https:// responses to the client

Prerequisites

You must meet the following prerequisite to use this procedure:

  • Have the Client SSL profile configured on a virtual server.

Description

A virtual server with a client SSL profile applied accepts HTTPS connections from clients, decrypts the SSL sessions, and sends the HTTP requests to the web server. If the BIG-IP is not re-encrypting requests with a server SSL profile, the web server listens and responds to all requests using HTTP. As a result, self-referencing Location headers in redirect responses will specify the HTTP protocol, rather than the HTTPS protocol that the client originally requested. The BIG-IP client SSL profile encrypts the response and returns it to the client, but the Location header value is not modified by default. The client follows the HTTP redirect, and the request fails in one of the following ways:

  • If no HTTP virtual server was configured for the same virtual address on the BIG-IP system, the connection fails and the SSL session is no longer used.
  • If an HTTP virtual server is configured on the same virtual address and sends traffic to the same web servers, the request may unintentionally succeed, but not be encrypted because the system used the HTTP protocol rather than HTTPS. 
  • If an HTTP virtual server is configured on the same virtual address and uses an iRule or Fallback Host to redirect HTTP response to HTTPS, the request may be repeatedly redirected between the two locations until the browser reaches its maximum redirect limit and reports an error.

Many applications rely on the use of redirects. When these redirects fail, the SSL session is disrupted and in most cases the website is unusable.

Special case: Trailing slash re-directs

When a requested URI does not include a trailing forward slash ( / ) at the end of the URI, some web servers generate a courtesy redirect using the following algorithm:

  • When a request arrives specifying a resource name that does not end with a slash, the web server first searches for a file whose name matches the last section of the URI.
  • If the web server cannot find a matching file, it looks for a directory with a name that matches the last section of the URI.
  • If the web server finds a matching directory, it sends an HTTP 302 redirect response back to the client with the Location value, specifying the protocol over which the request was received, the originally-requested resource, and a trailing slash.

Following is an example of a trailing slash HTTP 302 redirect response scenario for a BIG-IP virtual server that has a client SSL profile configured, and does not have a server SSL profile configured:

  1. A user types https://www.f5.com/stuff without a trailing slash, intending to browse the stuff directory.
  2. The client browser sends an SSL request to the client SSL virtual server, which resides on the BIG-IP LTM system.
  3. The BIG-IP LTM system decrypts the request and sends a GET /stuff command to the web server using the HTTP protocol.
  4. Since a file named stuff does not exist in the root directory of the web server, but a directory named stuff exists, the web server sends an HTTP 302 redirect response for the same resource name over the same protocol, appending a trailing slash. Since the request was sent using the HTTP protocol, when the web server sends the HTTP 302 redirect response, it specifies HTTP (not HTTPS), and the resulting redirect header is Location: http://www.f5.com/stuff/.
  5. When the client receives the HTTP 302 redirect response, it sends a new request to the BIG-IP LTM virtual server requesting http://www.f5.com/stuff/.
  6. Since the request uses HTTP, rather than HTTPS, the SSL session fails in one of the ways previously described.

Trailing slash re-directs are matched by the Matching http-rewrite option, ignoring the trailing slash.

Important: The BIG-IP system does not rewrite redirects from web servers that use the HTTPS protocol. Typically, this is not an issue if the backend HTTPS server is running on the same port as the virtual server. The redirect works because the port the server is listening on is the same as the virtual server. However, if the backend HTTPS server is running on a different port than the virtual server, the redirect fails.

Procedures

Configuring HTTP re-writes using the BIG-IP Configuration utility

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP Configuration utility.
  2. Click Local Traffic.
  3. Click Profiles.
  4. Click Services.
  5. Click HTTP.
  6. To create a new HTTP profile, click Create. Alternatively, you can click on an existing profile that you want to modify.
  7. If you are creating a new profile, type a name for the profile, and from the Parent Profile menu, choose http.
  8. Under Settings, depending upon your configuration, set Redirect Rewrite to All, Matching, or Nodes.
    • Choose Matching to rewrite redirects when the path and query URI components of the request and the redirect are identical (except for the trailing slash). This option is useful if the redirect references the same object, changing only the protocol or hostname, while the path and name of the requested object remains the same. This setting is useful when addressing the trailing slash redirect special case issue previously discussed.
    • Choose Nodes to rewrite redirects when the redirect URI contains a node IP address instead of a host name, and you want the system to change it to the virtual server address.
    • Choose All to rewrite all HTTP 301, 302, 303, 305, or 307 redirects to HTTPS, whether or not they match the virtual server. 
    • Choose None to disable HTTP-rewrites.
  9. Click Finished.

    Note: If you created a new profile, you must now associate it with the virtual server. If you modified an existing profile, you can skip the remaining steps.

  10. Click Local Traffic.
  11. Click Virtual Servers.
  12. Select the virtual server for which redirect URLs should be rewritten.
  13. In the Configuration section, select the new HTTP profile from the HTTP profile box.
  14. Click Update.
