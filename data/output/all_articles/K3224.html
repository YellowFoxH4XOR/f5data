Topic

HTTP or HTTPS health monitor requests may fail even though the server appears to respond, as expected, to browser requests. Three common causes are as follows:

  • The receive string appears too late in the server response
  • There is an HTTP version mismatch
  • The server responds with a meta-refresh or a redirect

The receive string appears too late in the server response

If the receive string is not found within the first 5,120 bytes of the server response, the server is marked down. For more information, refer to K3451: Content length limits for HTTP and HTTPS health monitors.

There is an HTTP version mismatch

By default, the BIG-IP system uses HTTP 0.9 for HTTP monitor requests. When an HTTP 0.9 request is sent to an HTTP 1.1 or HTTP 2.0 server, the server may not respond as expected.

Confirming the issue

To confirm that an HTTP server is running HTTP 1.1 or HTTP 2.0 (BIG-IP 11.6.0 and later) and responds properly to a version specific formatted requests, perform the following procedure:

Note: When using HTTP 2.0, ensure that the HTTP or HTTPS server is specifically configured to process HTTP 2.0 request. 

  1. Log in to the BIG-IP command line.
  2. Telnet to the pool member using the following command syntax:

    telnet <ServerIP> <ServerPort>

    Note: ServerIP is the IP address of the server being monitored, and ServerPort is the port upon which the HTTP service is listening.

    If the connection is successful, the system displays output that appears similar to the following example:

    Trying 192.168.10.10...
    Connected to 192.168.10.10.
    Escape character is '^]'.

  3. Enter the following request, pressing Enter once after each line:

    GET / HTTP/1.1
    Host: www.yoursite.com
    Connection: close

    Note: For HTTP 2.0 on BIG-IP 11.6.0 and later, modify the HTTP/1.1 section of the request to HTTP/2.0.

  4. Press Enter again to send the request to the server.

    Output that appears similar to the following example confirms that the server is running HTTP 1.1, and that it responds, as expected, to properly formatted HTTP 1.1 requests:

    HTTP/1.1 200 OK
    Date: Mon, 14 Jun 2004 08:22:11 GMT
    Server: Apache/1.3.20 Sun Cobalt (Unix) mod_ssl/
    2.8.4 OpenSSL/0.9.6b PHP/4.1.2
    X-Powered-By: PHP/4.1.2
    Connection: close
    Transfer-Encoding: chunked
    Content-Type: text/html
    Connection closed by foreign host.

Using cURL

You can also use the Linux command-line cURL utility with the --http2 option.

A successful attempt returns the expected content from the destination HTTP/2.0 enabled server. For example:

curl --header 'Host: www.example.com' --http2 -k https://192.168.1.181

Note: When testing, replace www.example.com with the appropriate host name for your server. Replace 192.168.1.181 with the IP address or host name of your server.

Refer to the following example when authorization is required by the destination server:

curl -u Bart --header 'Host: www.example.com' --http2 -k https://192.168.1.181

Note: The cURL utility prompts for the user password.

Modifying the monitor Send String to send an HTTP 1.1 or HTTP 2.0 request

To prevent the monitor from incorrectly marking the server down, modify the health monitor Send String to send an HTTP 1.1 request by specifying the HTTP version, the required Host header, and the Connection: close header.

Note: Beginning in BIG-IP 15.1.0, the http2 and http2_head_f5 monitors are available. For more information refer to K29224049: Overview of the BIG-IP HTTP/2 monitor.

Note: HTTP/1.1 requires the Host header to be present in the request but does not require the header to contain a value. If you do not have a specific host name on your server, a value of Host: <space> suffices in most cases. A null value is valid unless the HTTP server requires them for virtual hosting.

For example:

Your existing monitor requests the default document in the root directory by sending the following send string:

GET /

To send an HTTP 1.1 compliant request, modify the existing send string to appear similar to the following example:

GET / HTTP/1.1\r\nHost: host.domain.com\r\nConnection: Close\r\n\r\n

The server responds with a meta-refresh or a redirect

A client browser transparently follows a meta-refresh or an HTTP redirect response, but the BIG-IP system does not.

Confirming the issue

When you load the page in the browser, monitor the address to see if the browser is redirected to a different location than the one that you specified.

If a URL other than the one you entered appears in the browser address, verify the server response by performing the following procedure:

  1. Log in to the BIG-IP command line.
  2. Telnet to the pool member using the following command syntax:

    telnet <ServerIP> <ServerPort>

    Note: ServerIP is the IP address of the server being monitored, and ServerPort is the port on which the HTTP service is listening.

    If the connection is successful, the system displays output that appears similar to the following:

    Trying 192.168.10.10...
    Connected to 192.168.10.10.
    Escape character is '^]'.

  3. Enter the following request, pressing Enter once after each line:

    GET / HTTP/1.1
    Host: www.yoursite.com
    Connection: close

  4. Press Enter again to send the request to the server.

    If you receive a response that contains HTTP headers that appear similar to the following example, then the server is redirecting the request:

    HTTP/1.1 302 Moved Temporarily
    Location: http://www.yoursite.com/new/location.html

    If you receive a response that contains HTML content that appears similar to the following example, then the server is sending a meta-refresh in response to the request:

    <meta http-equiv="refresh" content="1;url=http://www.yoursite.com/new/location.html">

Modifying the monitor send string to issue a request to the redirection target

To correct the redirection target issue, modify the health monitor send string to send a request for the redirection target instead of the page which generates the redirect or refresh.

Note: HTTP/1.1 requires the Host header to be present in the request but does not require the header to contain a value. If you do not have a specific host name on your server, a value of Host: <space> suffices in most cases. A null value is valid unless the HTTP server requires them for virtual hosting. Refer to the examples in the previous HTTP Version Mismatch section for examples.

For example:

Your existing monitor requests the default document in the root directory by sending the following send string:

GET /

However, this request results in a redirect to http://www.yoursite.com/new/location.html, which contains the content expected by the monitor definition receive string.

To send a request for the page that contains the expected content, modify the existing send string to appear similar to one of the following example:

GET /new/location.html HTTP/1.1\r\nHost: host.domain.com\r\nConnection: Close\r\n\r\n
