Description

When exposing applications through F5 Distributed Cloud Regional Edges (REs), health monitoring is performed by default from every Regional Edge globally. This can generate a large number of health check connections to origin servers and may cause operational confusion when firewall rules or network security groups restrict access from certain regions. Understanding how health monitoring works and how to control which Regional Edges perform health checks is essential for maintaining a clean and accurate application health view.

  • How does F5 Distributed Cloud perform health checks on origin servers from Regional Edges?
  • Why does the Origin Servers tab show the same origin IP address listed multiple times with different Regional Edge site names?
  • How can the list of Regional Edges performing health checks on an origin server be restricted?
  • What happens to traffic when an origin server is marked as DOWN at the ingress Regional Edge?
  • What is the difference between the "Local Endpoints Only," "Local Endpoints Preferred," and "All Endpoints" load balancing options?
  • How does F5 Distributed Cloud use the Global Network to reroute traffic when the local origin is unavailable?

Environment

  • F5 Distributed Cloud (SaaS)
  • Regional Edge (RE) data plane
  • HTTP or HTTPS Load Balancer with a public origin server
  • Origin Pool configured with a Public IP address
  • Health Check configured on the Origin Pool
  • Optional: Virtual Site configured to restrict health monitoring to specific Regional Edge locations
  • Optional: Firewall rules or Network Security Groups (NSGs) at origin that restrict inbound connections by source IP or geography

Cause

By default, when an Origin Pool is configured with a Public IP address, every Regional Edge independently performs health checks against that origin server using its own local internet breakout. With 23 Regional Edges (as of June 2023), this results in 23 separate health check sources per origin server. If firewall rules or NSGs at the origin restrict access from certain regions, health checks from non-allowed Regional Edges will fail, causing those origin server entries to show as DOWN in the F5 Distributed Cloud Console and lowering the application health score.

Answer/Recommended Actions

Understanding Default Health Check Behavior

By default, F5 Distributed Cloud health checks operate as follows:

  • Each Regional Edge independently health checks the origin server using its own local internet routing — not relying on the F5 Global Network.
  • When a Public IP is configured in the Origin Pool, all Regional Edges perform health checks against that IP and port.
  • The Origin Servers tab in the Load Balancer dashboard will display the same origin IP address listed once per Regional Edge (e.g., 23 entries for 23 REs), each with a different Site name.
  • Source IP ranges for F5 Distributed Cloud Regional Edge health checks are published at: https://docs.cloud.f5.com/docs/reference/network-cloud-ref

Restricting Health Checks to Specific Regional Edges

To limit which Regional Edges perform health checks against an origin server, change the Origin Server type from Public IP to IP Address of Origin Server on Given Sites and associate a Virtual Site scoped to the desired Regional Edge locations.

  1. Navigate to Multi-Cloud App Connect or Web App & API Protection → Manage → Load Balancers → Origin Pools.
  2. Edit the Origin Pool and select or edit the Origin Server entry.
  3. Change the Select Type of Origin Server dropdown from Public IP to IP Address of Origin Server on Given Sites.
  4. Enter the origin server IP address.
  5. Under Site or Virtual Site, select Virtual Site and choose (or create) a Virtual Site scoped to the desired Regional Edge locations:
    • Navigate to Shared Configuration → Manage → Virtual Sites → Add Virtual Site.
    • Set Site Type to RE.
    • Under Selector Expression, use a label such as ves.io/country In ves-io-fra to scope to French Regional Edges, or use site name or region labels for other scoping options.
  6. Set Select Network on the site to Outside Network.
  7. Save the configuration.

After applying this configuration, the Origin Servers tab will show only the Regional Edges included in the Virtual Site (e.g., 2 entries instead of 23 when scoped to France-only REs).

Understanding Endpoint Selection and Traffic Rerouting Behavior

When a Regional Edge receives client traffic but the origin server is marked as DOWN at that RE (or does not exist in the RE's origin server list), the behavior depends on the Endpoint Selection setting configured in the Origin Pool. This setting is found under Origin Pool → Other Settings → Load Balancer Algorithm → Endpoint Selection.

The default Endpoint Selection value is Local Endpoints Preferred. In this mode:

  • When the local RE has a healthy origin server entry, traffic egresses directly from that RE to the origin.
  • When the local RE's origin server entry is DOWN or does not exist (e.g., because a Virtual Site was used to restrict health checks to specific REs), the RE uses the F5 Global Network to forward traffic to the nearest RE that has a healthy origin server entry, and that RE egresses the traffic to origin.

Additional Information

Restricting health checks using Virtual Sites is particularly useful in the following scenarios:

  • Firewall or NSG restrictions at origin: When the origin server only accepts inbound connections from specific IP ranges or countries, restricting health checks to the permitted Regional Edges prevents false DOWN states and unnecessary firewall log noise.
  • Reducing health check volume: For origins with strict rate limiting or limited connection capacity, reducing the number of REs performing health checks reduces the total health check load.
  • Compliance and data residency: When regulatory requirements mandate that traffic to an origin must only originate from specific geographic regions, restricting both health checks and origin pool membership to a Virtual Site scoped to those regions ensures compliance.

This Virtual Site-based approach to restricting health checks is closely related to the broader Virtual Site traffic topology concepts covered in the F5 Distributed Cloud Virtual Sites - Regional Edge (RE) article. In that context, restricting the Origin Pool to a Virtual Site (server-side/upstream) without restricting the VIP Advertisement (client-side/downstream) corresponds to the "Solution 4: North America Only (Server-Side/Upstream)" topology — where traffic ingresses globally but egresses only through the REs included in the Origin Virtual Site, using the F5 SDN Fabric to bridge between the ingress and egress REs when needed.

The minimum required configuration elements for exposing an application through F5 Distributed Cloud are:

  • Health Check: Monitors application reachability by simulating client traffic (HTTP/HTTPS).
  • Origin Pool: Contains the public IP and port of the hosted application.
  • HTTP Load Balancer: The FQDN that end users resolve, with optional TLS termination certificate.
  • Optional: WAF Policy, API Protection, Bot Defense, and other security services can be layered on top.

For organizations that require tighter control over both traffic and health check routing, adding a Customer Edge (CE) closer to the origin application — whether on-premises or in cloud — provides the most granular control and allows the CE-to-origin path to be fully secured and isolated from the public internet.
