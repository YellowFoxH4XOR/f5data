K000161269: Intermittent Access to On-Premises Servers via BIG-IP APM VPN Caused by Missing Kerberos Ticket on Windows 11 Clients

Description

Users working from home and connected to VPN via BIG-IP APM report intermittent inability to access on-premises servers .The issue resolves temporarily after switching networks or restarting the client machine, but recurs upon reconnection using a Windows Hello PIN instead of a password.

  • Users can ping the affected server IP addresses successfully.
  • Traceroute confirms full network path reachability to the destination servers.
  • Packet captures on the BIG-IP confirm the TCP three-way handshake (3WHS) and TLS handshake complete successfully, indicating no connectivity issue at the BIG-IP level.
  • Accessing file shares prompts for credentials unexpectedly.
  • Error occurs when attempting to connect to the database server.

Environment

  • Product: BIG-IP APM
  • Client OS: Windows 11
  • VPN Configuration: Split tunneling enabled on the Network Access resource
  • No ACLs configured in the access policy
  • Authentication method in use: Windows Hello PIN (as opposed to password-based login)

Cause

The issue is caused by a missing Kerberos ticket on the Windows 11 client machine. When users authenticate using a Windows Hello PIN instead of their domain password, a Kerberos ticket is not generated. Without a valid Kerberos ticket, the client cannot authenticate to Kerberos-dependent on-premises resources (such as database servers), resulting in intermittent access failures.

This is NOT a BIG-IP APM issue.

Answer/Recommended Actions

To confirm and resolve the missing Kerberos ticket issue on Windows 11 clients:

  1. Verify Kerberos ticket presence on the affected client machine:
    - Open a Command Prompt and run:
    klist
    - If no tickets are listed, the Kerberos ticket is missing.
  2. Reproduce the behavior:
    - Log in using a Windows Hello PIN → confirm no Kerberos ticket is present → confirm loss of access to on-premises servers.
    - Log off and log back in using the domain password → confirm a Kerberos ticket is issued → confirm access to on-premises servers is restored.
  3. Workarounds (short-term):
    - Have the affected user log off and log back in using their domain password (not PIN) to obtain a Kerberos ticket.
    - Alternatively, switch to a different network and reconnect to VPN, or restart the machine and log in with the domain password.
  4. Long-term resolution:
    - Engage the Windows/Active Directory (Wintel) team to review and configure Windows Hello for Business to support Kerberos authentication (e.g., enabling Cloud Kerberos Trust or Hybrid Key Trust deployment).
    - Review Group Policy or Intune settings to ensure Kerberos ticket issuance is enforced upon PIN-based login where required.

Additional Information

  • The BIG-IP APM device and VPN configuration were confirmed to be functioning correctly. Packet captures showed successful TCP and TLS handshakes between the client and the database server, ruling out any VPN-layer connectivity issue.
  • This behavior is specific to Windows 11 and its handling of Kerberos authentication when Windows Hello PIN is used as the login method. PIN-based login in certain Windows 11 configurations does not trigger Kerberos ticket acquisition, unlike traditional password-based domain logon.
  • On-premises resources that rely on Kerberos authentication (such as SQL database servers and file shares) will be inaccessible when no valid Kerberos ticket exists on the client.
