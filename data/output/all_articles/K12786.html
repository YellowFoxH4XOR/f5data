K12786: The BIG-IP ASM CSRT token is not removed in requests to the origin web server

Known Issue
Published
2012-06-27

Status
Legacy Content
Applies to

  • BIG-IP ASM: 10.2.4, 10.2.2, 10.2.1, 10.2.3, 10.2.0
Source
https://my.f5.com/manage/s/article/K12786

Known Issue

This is the result of a known issue. When the BIG-IP ASM cross-site request forgery (CSRF) feature inserts the CSRT token on client side transactions, it does not remove the token when subsequently passing the request to the origin web server (OWS). As a result, HTTP requests will be sent to the OWS with a query string that will be unusable. Most web applications will ignore a query string they do not support, but it is possible that the inclusion of the CSRT token in the query string may cause some web applications to fail or otherwise behave unexpectedly.

F5 Product Development tracked this issue as ID 226657 (formerly CR141939) and it was fixed in BIG-IP version 11.0.0. For information about upgrading, refer to the BIG-IP ASM release notes.

Note: For more information about the CSRF feature and CSRT tokens, refer to K11930: Overview of the ASM CSRF protection feature.

Workaround

You can work around this issue by using a VIP-to-VIP configuration with an iRule to post-process the request. VIP-to-VIP is a configuration in which two virtual servers are used to process the request through the BIG-IP ASM policy and strip the CSRT token out before the data is sent to the OWS. The front virtual server hosts the HTTP Class Profile and ensures requests are processed by the BIG-IP ASM CSRF feature. The back virtual server contains the post processing iRule to remove the CSRT token before sending it on to the OWS.

Creating a VIP-to-VIP configuration to post-process the request and strip the CSRT token

Configuring the vip-to-vip iRule

Configure an iRule that sends traffic directly to the "back" VIP. For example, to define an iRule which sends traffic to a back VIP named ASM_back_vip, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Click Local Traffic.
  3. Click iRules.
  4. Click Create.
  5. Enter a name for the iRule.

    For example:

    asm_vip_to_vip

  6. Enter the following iRule in the Definition box:

    when RULE_INIT {
    set ::targetvip "ASM_back_vip"
    }
    when HTTP_REQUEST {
    virtual $::targetvip
    }

  7. Click Finished.

Configuring the CSRT post processing iRule

To define an iRule which strips the CSRT token from a response before sending the request to the OWS, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Click Local Traffic.
  3. Click iRules.
  4. Click Create.
  5. Enter a name for the iRule.

    For example:

    asm_CSRT_strip

  6. Enter the following iRule in the Definition box:

    when HTTP_REQUEST {
    if {[HTTP::method] equals "POST"}{
    HTTP::collect [HTTP::header Content-Length]
    }
    elseif { [HTTP::uri] contains "CSRT="}{
    regsub -all [findstr [HTTP::uri] ?CSRT= 1] [HTTP::uri] "" tmp_uri
    regsub -all [findstr $tmp_uri &CSRT= 0] $tmp_uri "" new_uri
    HTTP::uri $new_uri
    }
    }
    when HTTP_REQUEST_DATA {
    if { [string range [HTTP::payload] 0 4] equals "CSRT=" } {
    set ASM_CSRT [findstr [HTTP::payload] CSRT= 0 &]
    regsub -all [findstr [HTTP::payload] CSRT= 0 &] [HTTP::payload] "" new_payload
    }
    else {
    set ASM_CSRT [findstr [HTTP::payload] &CSRT= 1 &]
    regsub -all [findstr [HTTP::payload] &CSRT= 1 &] [HTTP::payload] "" new_payload
    }
    HTTP::payload replace 0 [HTTP::header Content-Length] $new_payload
    HTTP::release
    }

  7. Click Finished.

Configuring the "front" virtual server

Configure the virtual server which references the vip_to_vip iRule, enables the BIG-IP ASM system, and does not reference a default pool. For example, to define a "front" virtual server which processes connection requests from clients, perform the following procedure:

Note: This procedure assumes you have already created an HTTP Class Profile that enables BIG-IP ASM and has the CSRF feature enabled in the BIG-IP ASM security policy. For the purposes of this procedure, the example will refer to this HTTP Class Profile as My_ASM_Class. When creating the front virtual server you will need to use the name of your existing HTTP class profile in place of My_ASM_Class

  1. Log in to the Configuration utility.
  2. Click Local Traffic.
  3. Click Virtual Servers.
  4. Click Create.
  5. Enter a name for the virtual server.

    For example:

    front_vip

  6. Enter the virtual server address and port.

    For example:

    172.29.24.226:http

  7. From the Configuration drop-down menu, select Advanced.
  8. From the HTTP profile drop-down menu, select http.
  9. From the SNAT Pool drop-down menu, select automap.
  10. In the iRules section, click the asm_vip_to_vip iRule, and move it to the Enabled window.
  11. In the HTTP Class Profiles section, click the name of your ASM enabled HTTP Class Profile, and move it to the Enabled window.
  12. Click Finished.

>The virtual server should appear similar to the following example:

virtual front_vip {
snat automap
destination 172.29.24.226:http
ip protocol tcp
rules asm_vip_to_vip
httpclass My_ASM_Class
profiles
http
tcp
}

Configuring the "back" virtual server

To configure a virtual server which references the asm_CSRT_strip iRule, and then forwards the request to the OWS, perform the following procedure:

Note: This procedure assumes you have already defined a pool with an appropriate OWS pool member. For the purposes of this procedure, the example will refer to this pool as My_ASM_OWSPool. When creating the back virtual server you will need to use the name of your existing pool in place of My_ASM_OWSPool

  1. Log in to the Configuration utility.
  2. Click Local Traffic.
  3. Click Virtual Servers.
  4. Click Create.
  5. Enter a name for the virtual server.

    For example:

    ASM_back_vip

  6. Enter the virtual server address and port.

    For example:

    172.29.24.225:http

  7. From the Configuration drop-down menu, select Advanced.
  8. From the HTTP profile drop-down menu, select http.
  9. From the SNAT Pool drop-down menu, select automap.
  10. In the iRules section, click the asm_CSRT_strip iRule, and move it to the Enabled window.
  11. In the Default Pool drop-down menu, choose the correct pool for your OWS.
  12. Click Finished.

The virtual server should appear similar to the following example:

virtual ASM_back_vip {
pool My_ASM_OWSPool
snat automap
destination 172.29.24.225:http
ip protocol tcp
rules asm_CSRT_strip
profiles
http
tcp
}

The above configuration allows the front virtual server to accept HTTP requests and apply the BIG-IP ASM policy, including CSRF protection, to the traffic before forwarding it to the second virtual server. The second virtual server post-processes the traffic and strips the CSRT token before sending it on to the OWS.
