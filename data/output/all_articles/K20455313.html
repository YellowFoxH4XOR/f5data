Known Issue

TMM may restart and produce a core file when processing DNS requests on a UDP virtual server with a suspending iRules command.

Note: A virtual server processing DNS requests also appears as a Listener within the BIG-IP DNS configuration.

This issue occurs when all of the following conditions are met:

  • A virtual server is configured with a User Datagram Protocol (UDP) profile and an iRule with a suspending command.
  • The UDP profile has datagram load balancing enabled.
  • An iRule command suspends the iRule processing for a period longer than the idle timeout configured on the UDP profile.
  • The virtual server receives a DNS request.

Impact

If the BIG-IP system is a member in a redundant configuration, traffic fails over to the standby BIG-IP system. If the BIG-IP system is not part of a redundant pair, traffic is interrupted until the Traffic Management Microkernel (TMM) restarts.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • BIG-IP iHealth lists Heuristic H664173 on the Diagnostics > Identified > Low page.
  • Your BIG-IP system fails over to another device in the device group.
  • Your BIG-IP system generates a TMM core file to the /shared/core directory.
  • Your BIG-IP system temporarily fails to process traffic while TMM restarts.

Workaround

To work around this issue, you can ensure that the virtual server's iRule is not suspended for longer than the idle timeout of the virtual server's UDP profile. This may involve reworking the iRule to avoid lengthy suspension or removing the suspending command completely. For more information, refer to K12962: Some iRule commands temporarily suspend iRule processing. Alternatively, you can increase the idle timeout on the UDP profile until it is long enough for the iRule processing to complete while still maintaining a reasonably short timeout period. For more information refer to K7166: Changing the idle timeout for a protocol profile and K7606: Overview of BIG-IP idle session time-outs.

Impact of workaround: The impact of the suggested workaround depends on the specific environment. F5 recommends that you test any such changes during a maintenance window and consider the possible impact on your environment. Excessively long timeout periods can lead to resource exhaustion.

Important: Specifying an indefinite idle time-out for connectionless protocols, such as UDP, can lead to stalled connections and resource exhaustion. In most cases, F5 recommends that you set the idle time-out to a small as possible finite value to sustain the application.
