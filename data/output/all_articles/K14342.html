Topic

This article applies to BIG-IP ASM 11.x through 17.x. For information about other versions, refer to the following articles:

  • K10089: Preserving or modifying the Server HTTP response header for BIG-IP ASM (9.4.2 through 10.x)
  • K6752: Preserving or modifying the Server HTTP response header for BIG-IP ASM (9.2.0 through 9.4.1)

You should consider using this procedure under the following condition:

  • You want to preserve or modify the Server HTTP header or other HTTP response headers that are removed when processed by a BIG-IP ASM system.

Description

Certain HTTP headers allow an HTTP server to provide information about the software that the server uses to handle HTTP requests. These HTTP headers may contain product and version information, as well as comments identifying the server and any significant sub-products. While this information may be useful for some clients, it is considered unnecessary information leakage. As a result, the BIG-IP ASM system removes these HTTP headers from responses to increase application security.

The BIG-IP ASM system removes certain HTTP headers from responses to increase application security and prevent information leakage. The following table lists the HTTP headers that the system removes:

HTTP header removedBIG-IP ASM version
Server11.0.0 and later
X-Powered-By13.1.0 and later
X-AspNet-Version13.1.0 and later
X-AspNetMvc-Version13.1.0 and later
X-Generator13.1.0 and later
X-Powered-CMS13.1.0 and later

You can use the HTTP_RESPONSE_RELEASE iRule event to modify HTTP content before the system releases it on the client side of the connection. If you want to preserve or modify these header values, you can accomplish this by using a virtual server that is associated with an iRule that saves the header values in the HTTP_RESPONSE event and reinserts the values back in the HTTP_RESPONSE_RELEASE event.

The HTTP_RESPONSE event is triggered before the BIG-IP ASM processes the server response, and the HTTP_RESPONSE_RELEASE event is triggered after the BIG-IP ASM processing is complete.

For example, the following iRule snippet saves the Server header value before BIG-IP ASM processing takes place, and reinserts the value after BIG-IP ASM processing is complete:

Note: The following iRule may not apply to all environments. F5 recommends that you author an iRule that works best for your application environment. Adding an iRule increases the resources that the associated virtual server uses. Depending on the type and volume of the connections, this processing may introduce noticeable latency. F5 recommends that you test any such changes in an appropriate environment.

when HTTP_RESPONSE {
   if { [HTTP::header exists "Server"] } {
      HTTP::header insert Xerver [HTTP::header value "Server"]
   }
}
when HTTP_RESPONSE_RELEASE {
   if { [HTTP::header exists "Xerver"] } {
      HTTP::header insert Server [HTTP::header value "Xerver"]
      HTTP::header remove Xerver
   }
} 

In another example, the following iRule snippet detects the Server header and replaces the Server header value with a custom value using a variable before BIG-IP ASM processing takes place, and reinserts the custom value after BIG-IP ASM processing is complete:

Note: The following iRule may not apply to all environments. F5 recommends that you author an iRule that works best for your application environment. Adding an iRule increases the resources that the associated virtual server uses. Depending on the type and volume of the connections, this processing may introduce noticeable latency. F5 recommends that you test any such changes in an appropriate environment.

when HTTP_RESPONSE {
   set myserverheader "MyWebServervariable"

   if { [HTTP::header exists "Server"] } {
      HTTP::header insert Xerver $myserverheader
   }
}
when HTTP_RESPONSE_RELEASE {
   if { [HTTP::header exists "Xerver"] } {
      HTTP::header insert Server [HTTP::header value "Xerver"]
      HTTP::header remove Xerver
   }
}

If you prefer to have different custom values for different HTTP header, you can use a data group instead of a variable with the following iRule snippet:

Note: The following iRule may not apply to all environments. F5 recommends that you author an iRule that works best for your application environment. Adding an iRule increases the resources that the associated virtual server uses. Depending on the type and volume of the connections, this processing may introduce noticeable latency. F5 recommends that you test any such changes in an appropriate environment.

when HTTP_RESPONSE {
   if { [HTTP::header exists "Server"] } {
      HTTP::header insert Xerver [class match -value "Server" equals K14342-datagroup]
   }
}
when HTTP_RESPONSE_RELEASE {
   if { [HTTP::header exists "Xerver"] } {
      HTTP::header insert Server [HTTP::header value "Xerver"]
      HTTP::header remove Xerver
   }
} 

Where the data group is similar to the following example:

ltm data-group internal K14342-datagroup {
    records {
        Server {
            data MyWebServer
        }
    }
    type string
}

Prerequisites

You must meet the following prerequisites to use this procedure:

  • Have administrative access to the BIG-IP ASM system.
  • Have basic working knowledge of iRules.
  • Have an existing BIG-IP ASM virtual server that is masking information leaking HTTP headers required by an application.

Procedures

  • Configuring the iRule for the BIG-IP ASM virtual server
  • Associating the iRule to the BIG-IP ASM virtual server

Configuring the iRule for the BIG-IP ASM virtual server

The BIG-IP ASM virtual server uses the iRule to save the server and application technology header values to new headers. The new header values are unmodified by the BIG-IP ASM system and are available for reinsertion after the BIG-IP ASM system completes its processing. To create the iRule, perform the following procedure:

Impact of procedure: Depending on the type and volume of the connections, this processing may introduce noticeable latency. Additionally, these headers are masked to prevent information leakage so they should be preserved with caution. F5 recommends that you test any such changes in an appropriate environment.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules > iRule List.
  3. Click Create.
  4. In the Name field, type a name for the iRule.

    For example:

    K14342-ASMVS

  5. In the Definition field, copy and paste the iRule you want.

    For example, to preserve information leaking headers which are removed by the BIG-IP ASM system in 13.1.0 and later:

    when HTTP_RESPONSE {
       if { [HTTP::header exists "Server"] } {
          HTTP::header insert Xerver [HTTP::header value "Server"]
       }
       if { [HTTP::header exists "X-AspNetMvc-Version"] } {
          HTTP::header insert X-XspNetMvc-Version [HTTP::header value "X-AspNetMvc-Version"]
       }
       if { [HTTP::header exists "X-AspNet-Version"] } {
          HTTP::header insert X-XspNet-Version [HTTP::header value "X-AspNet-Version"]
       }
       if { [HTTP::header exists "X-Powered-By"] } {
          HTTP::header insert X-Xowered-By [HTTP::header value "X-Powered-By"]
       }
       if { [HTTP::header exists "X-Generator"] } {
          HTTP::header insert X-Xenerator [HTTP::header value "X-Generator"]
       }
       if { [HTTP::header exists "X-Powered-CMS"] } {
          HTTP::header insert X-Xowered-CMS [HTTP::header value "X-Powered-CMS"]
       }
    }
    when HTTP_RESPONSE_RELEASE {
       if { [HTTP::header exists "Xerver"] } {
          HTTP::header insert Server [HTTP::header value "Xerver"]
          HTTP::header remove Xerver
       }
       if { [HTTP::header exists "X-XspNetMvc-Version"] } {
          HTTP::header insert X-AspNetMvc-Version [HTTP::header value "X-XspNetMvc-Version"]
          HTTP::header remove X-XspNetMvc-Version
       }
       if { [HTTP::header exists "X-XspNet-Version"] } {
          HTTP::header insert X-AspNet-Version [HTTP::header value "X-XspNet-Version"]
          HTTP::header remove X-XspNet-Version
       }
       if { [HTTP::header exists "X-Xowered-By"] } {
          HTTP::header insert X-Powered-By [HTTP::header value "X-Xowered-By"]

          HTTP::header insert X-Powered-CMS [HTTP::header value "X-Xowered-CMS"]
          HTTP::header remove X-Xowered-CMS
       }
    }

Optional: Create a data group

You should only perform this procedure to create a data group if you are planning to replace the values of each of the information leaking headers which are removed by the BIG-IP ASM system in 13.1.0 and later with different custom values. To do so, perform the following procedure:

Impact of procedure: The following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP Configuration utility.
  2. Navigate to Local Traffic > iRules > Data Group List.
  3. Click Create.
  4. Enter a name for the data group.
  5. For Type, click String.
  6. For each String record, type the value for the HTTP header removed column in the table listed in the Description section. For the corresponding Value record, type the custom value you want for the HTTP header, then click Add.
    Using the example described in the Description section, type Server in the String record and MyWebServer in the Value record, and then click Add.
  7. Repeat the previous step for each of remaining HTTP headers listed in the table.
  8. Click Finished.

Associating the iRule to the BIG-IP ASM virtual server

After you have created the appropriate iRule for your application environment, you must associate the iRule with the appropriate BIG-IP ASM virtual server. To do so, perform the following procedure:

Impact of procedure: The following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Virtual Servers > Virtual Server List.
  3. In the Resource column for the appropriate BIG-IP ASM virtual server, click Edit.
  4. Under the iRules section, click Manage.
  5. From the Available box, select the iRule that you created in the previous procedure, and click << to move the iRule to the Enabled box.
  6. To save the change, click Finished.
