K000161655: How to log jti claim from OAuth Scope agent in API Protection flow

Type
Support Solution
Published
2026-06-09
Updated
2026-06-09
Applies to
  • BIG-IP
  • BIG-IP APM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000161655

Description

When configuring a Logging agent in a BIG-IP APM API Protection per-request policy to capture the jti claim from a JWT validated by an OAuth Scope agent, the log entry returns an empty string. Using the variable subsession.oauth.client.last.id_token.jti does not populate the expected value, resulting in output such as:

jti=

Example log entry showing the empty jti field:

01870023:5: /Common/TST-svc1-ApiProtection_ap:TST:6D610367: subsession

[OAuth Scope] -> [VarAssign from HTTP Authorization]

perflow.session.id=0000000000000000000000006D610367 ... jti=

Environment

  • Product: BIG-IP APM
  • Version: 17.5.1
  • Feature: API Protection per-request policy
  • Policy agents involved:
    • OAuth Scope agent (acting as resource server validating bearer tokens)
    • Logging agent
  • Configuration: Logging agent placed after the OAuth Scope agent in the per-request policy

Cause

The variable subsession.oauth.client.last.id_token.jti belongs to the OAuth Client agent namespace and is not populated by the OAuth Scope agent. In an API Protection flow, the OAuth Scope agent populates a separate set of subsession variables under a different namespace, requiring a different variable path to access JWT claims such as jti.

Answer/Recommended Actions

Use the correct variable for the OAuth Scope agent namespace:

In the Logging agent's Log Message field, use the following variable to log the jti claim:

jti=%{subsession.oauth.scope.last.jwt.jti}

Steps to configure:

  1. Navigate to your API Protection per-request policy in the BIG-IP APM Visual Policy Editor.
  2. Locate the OAuth Scope agent in the policy flow.
  3. Place the Logging agent immediately after the OAuth Scope agent on the Successful branch to ensure subsession variables are already populated when the Logging agent executes.
  4. In the Logging agent's Log Message field, enter:
    jti=%{subsession.oauth.scope.last.jwt.jti}
  5. Save and apply the policy.

If the variable still returns empty, confirm the exact variable name via debug logging:

  1. Go to Access > Overview > Event Logs > Settings.
  2. Edit the log setting for your access profile and set the Per-Request Policy log level to Debug.
  3. Trigger a test request and inspect /var/log/apm for all subsession.* variables populated by the OAuth Scope agent — look for any entry containing jti to confirm the exact variable path.
  4. Restore the log level to its original setting after testing, as debug logging generates significant log volume.

Alternatively, enable policy trace logging temporarily via tmsh:

tmsh modify sys db tmm.access.policytrace value enable

Note: Disable this after testing as it generates significant log volume:

tmsh modify sys db tmm.access.policytrace value disable

If the variable is still not populated, consider the following:

  • The incoming JWT may not contain a jti claim.
  • If the OAuth Scope agent is using external token introspection, the available claims depend on what the authorization server returns. In this case, use a Variable Assign agent after the OAuth Scope agent to map the value to a perflow variable, then log that instead:
    • Left side (Custom Variable): perflow.custom.jti
    • Right side (Session Variable): subsession.oauth.scope.last.jwt.jti
    • Then log %{perflow.custom.jti} in the Logging agent.

Additional Information

  • The OAuth Client agent namespace (subsession.oauth.client.last.*) and the OAuth Scope agent namespace (subsession.oauth.scope.last.*) are distinct. The OAuth Client agent is used in a different flow (e.g., when BIG-IP APM acts as an OAuth client), while the OAuth Scope agent is used when BIG-IP APM acts as a resource server validating bearer tokens in an API Protection flow.
  • The jti claim is a reserved/standard JWT claim. APM parses and stores it into the subsession variable namespace upon successful JWT validation by the OAuth Scope agent.
