K000134561: Aspen Mesh appends host header in request to authority header

Type
Support Solution
Published
2023-05-23
Updated
2023-05-23
Applies to
  • Aspen Mesh: 1.14, 1.11
Source
https://my.f5.com/manage/s/article/K000134561

Description

Aspen Mesh is appending host header received in the request to the :authority header. The following istio-proxy log example shows this behavior:

2023-05-02T14:21:41.258290Z    debug  envoy http     [C9021][S5093339925327115450] request headers complete (end_stream=false):
':method', 'POST'
':authority', 'service:9090,svcname.ns.svc.cluster.local:8080'.


Environment

Aspen Mesh: 1.14.x, 1.11.x
 

Cause

Istio is a versatile and powerful service mesh that provides a myriad of features including traffic management, service discovery, security, and observability. At the heart of Istio's traffic management capabilities are a few key components that allow users to define complex routing rules and policies. In this article, we will delve into how Istio routes application traffic to its destination service using three fundamental components: VirtualService, DestinationRule, and ServiceEntry.  Istio's objects typically configured to enable sidecar route the traffic to destination service.
 

Recommended Actions

VirtualService that removes the authority header could be created. Here's an example configuration: 
..
  http:
  - route:
    - destination:
        host: svc.example.com
        port:
          number: 80
    headers:              
      request:
        remove:
        - :authority

In this example, the :authority header will be removed from the request when sent to svc.example.com. This might not be suitable for all scenarios, as some servers require the :authority or Host header to function correctly.
 

Additional Information

Istio sidecar will route the traffic if the destination service for example is "svc.example.com". Based on the :authority header value svc.example.com, the Istio sidecar will attempt to route the traffic. The sidecar will look for a VirtualService that has a matching host field. In this case, it will search for a VirtualService with the host field set to svc.example.com. The sidecar will apply the routing rules defined in the matched VirtualService. In this case, the traffic will be directed to svc.example.com service on port 80.

After determining the destination, the sidecar will search for a DestinationRule that matches the destination host. In this case, it will look for a DestinationRule with the host field set to svc.example.com. If a matching DestinationRule is found, the sidecar will apply the traffic policies defined in the DestinationRule. As you can see the Istio sidecar will use the :authority header value svc.example.com to match the appropriate VirtualService and DestinationRule, and then route and manage the traffic according to the configurations defined in those objects.

When a request is made from an application in a pod, it is first intercepted by the Istio sidecar proxy (Envoy) co-located with the application. The sidecar proxy is responsible for routing the traffic according to the rules defined in Istio’s traffic management resources.

The primary resources we'll focus on are:

VirtualService: This is used to configure the routing rules to direct traffic to specific services within the Istio service mesh. It defines a set of traffic routing rules to apply when a host is addressed.
DestinationRule: This defines policies that apply to traffic intended for a service after routing has occurred. These rules specify load balancing policies, outlier detection, and TLS settings.
ServiceEntry: This is used to add additional entries to Istio's internal service registry, so that auto-discovered services in the mesh can route to these manually specified services.
 

HTTP 1.1 and HTTP 2.0 Traffic
In the context of HTTP 1.1 and HTTP 2.0 traffic, Istio uses the :authority or Host header of the HTTP request to match against the hosts field in the VirtualService configuration. The matched VirtualService then directs the traffic to the appropriate destination.

VirtualService Example:

apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
 name: vs-example
spec:
 hosts:
 - svc.example.com
 http:
 - route:
 - destination:
  host: svc.example.com
  port:
   number: 80

In this example, when the :authority or Host header of the HTTP request is svc.example.com, the traffic is routed to the service svc.example.com on port 80.
 

DestinationRule Example:

apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
 name: dr-example
spec:
 host: svc.example.com
 trafficPolicy:
 loadBalancer:
  simple: ROUND_ROBIN

After the VirtualService has routed the traffic to svc.example.com, the DestinationRule applies additional policies to the traffic. In this case, a round-robin load balancing policy is applied.
 

TCP Traffic
For TCP traffic, Istio uses the IP and Port of the request to direct traffic based on the ServiceEntry and VirtualService configurations. Unlike HTTP traffic, TCP traffic does not have a Host or :authority header. Therefore, the routing decisions are made based on the destination IP and port.
 

ServiceEntry Example:

apiVersion: networking.istio.io/v1alpha3
kind: ServiceEntry
metadata:
 name: external-svc-tcp
spec:
 hosts:
 - svc.example.com
 addresses:
 - 198.51.100.0
 ports:
 - number: 80
 name: tcp
 protocol: TCP
 location: MESH_EXTERNAL
 resolution: STATIC
 endpoints:
 - address: 198.51.100.1

In this example, a ServiceEntry is created for a service svc.example.com outside the mesh. The addresses field specifies the IP addresses associated with the host. The ports field specifies the port used by the service. The location field is set to MESH_EXTERNAL, indicating that the service is external to the mesh. The resolution field is set to STATIC, and the actual IP address of the service is provided in the endpoints field.
