Description

When BIG-IP Bot Defense is operating in blocking mode, cross-origin (CORS) requests to non-HTML endpoints may fail with a missing CORS headers error in the browser. This occurs because Bot Defense issues an HTTP 307 Temporary Redirect as part of its proactive defense challenge mechanism, and that redirect response does not include the Access-Control-Allow-Origin header or other required CORS headers.

As a result, browsers enforcing the CORS policy will reject the response, causing API calls or authentication requests from Single Page Applications (SPAs) or cross-origin clients to fail.


 

Environment

• BIG-IP LTM + ASM / Advanced WAF

• Bot Defense profile configured in blocking mode

• Applications using cross-origin requests (e.g. SPA, API clients)

• Non-HTML endpoints (e.g. JSON REST APIs, authentication endpoints)

• dosl7.proactive_defense_simple_redirect db variable enabled


 

Cause

The HTTP 307 redirect is triggered by Bot Defense under the following conditions:

• Bot Defense profile is in blocking mode

• The request does not include a valid TSPD_101 cookie

• The requested URL is not in the qualified URLs list, or the request is non-HTML (e.g. Content-Type: application/json)

• The db variable dosl7.proactive_defense_simple_redirect is enabled


 When these conditions are met, Bot Defense cannot inject a JavaScript challenge into the response (because the response is not HTML). It falls back to issuing a 307 redirect to the same URL. This redirect response is generated internally by Bot Defense and does not carry any CORS headers, causing cross-origin requests to fail at the browser level.

Separately, if a non-HTML endpoint (e.g. a JSON API) is incorrectly added to the dosl7.cs_qualified_urls list, Bot Defense will attempt to inject JavaScript into the JSON response body, resulting in malformed JSON and application errors.


Answer/Recommended Actions

Step 1: Disable the proactive defense simple redirect


Disable the db variable that triggers the 307 redirect fallback for non-HTML requests:


tmsh modify sys db dosl7.proactive_defense_simple_redirect value false

tmsh modify sys db dosl7.proactive_defense_simple_redirect_on_grace value false


With this setting disabled, Bot Defense will no longer issue a 307 redirect for requests that cannot be challenged via JavaScript injection. The JS challenge will instead be applied at the HTML entry point, which is the correct and supported flow.


Step 2: Ensure only HTML entry points are in the qualified URLs list


Review the dosl7.cs_qualified_urls db variable and confirm that only HTML entry points (e.g. /) are listed. Non-HTML endpoints such as API or authentication URLs must not be included. Adding a non-HTML endpoint to this list causes Bot Defense to attempt JavaScript injection into non-HTML responses, producing malformed output and further application errors.


 

Additional Information

Bot Defense applies JavaScript injection challenges at HTML entry points. For non-HTML traffic (JSON, XML, etc.), JS injection is not possible by design. The recommended architecture is to have Bot Defense challenge users at the HTML page load, after which the TSPD_101 cookie is set and subsequent API calls from the same browser session pass through without triggering a redirect or challenge.

The dosl7.proactive_defense_simple_redirect setting was intended as a fallback for environments where the HTML entry point is not always visited first. However, for cross-origin API requests from SPAs or other cross-origin clients, this fallback is not compatible with browser CORS enforcement and should be disabled.

This behavior affects all virtual servers and applications sharing the same Bot Defense profile and db variable configuration. If multiple applications exhibit the same CORS error, the same fix applies across all of them.
