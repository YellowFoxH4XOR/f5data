Description

When using AAA kerberos on BIG-IP APM, one of the tasks consists of creating a service account on Active Directory. You could configure such account so that it would handle multiple service principal name such as these for instance:

HTTP/app1.example.com@EXAMPLE.COM
HTTP/app2.example.com@EXAMPLE.COM
HTTP/app3.example.com@EXAMPLE.COM

If AES encryption is selected, you may end up seeing such errors under /var/log/apm when accessing https://app2.example.com:

Dec 18 05:35:03 bigip1 debug apmd[9126]: 01490266:7: /Common/AP_kerberos:Common:0d3b1f18: modules/Authentication/Kerberos/KerberosAuthModule.cpp: 'PrintGssErrorImpl()': 177: 0d3b1f18 : GSS-API error gss_accept_sec_context: d0000 : Unspecified GSS failure. Minor code may provide more information
Dec 18 05:35:03 bigip1 debug apmd[9126]: 01490266:7: /Common/AP_kerberos:Common:0d3b1f18: modules/Authentication/Kerberos/KerberosAuthModule.cpp: 'PrintGssErrorImpl()': 177: 0d3b1f18 : GSS-API error gss_accept_sec_context: 186a8 : Request ticket server HTTP/app2.example.com@EXAMPLE.COM kvno 4 enctype aes256-cts found in keytab but cannot decrypt ticket

You might even find out that same test against https://app1.example.com is successful.

Environment

  • BIG-IP APM with kerberos AAA
  • Multiple SPN are configured within a single service account
  • AES encryption is selected

Cause

In order to use multiple SPN within a given Active Directory service account, you must use several successive ktpass commands (each generated keytab will be re-injected into the next ktpass command using '-in' option).

ktpass will use automatic salt (it can be viewed using '+DumpSalt' option) when using AES encryption.

The salt value will be the complete principal name including the realm. So by default, from one ktpass command to another, the salt will change as the principal name will be different.

Each time a keytab will be generated for a given service account but a different SPN, it will invalidate the previous keytab entries as the default salt will be different.

Note: there is no such issue with RC4 as there is no salt involved.

Recommended Actions

  • A separate service account could be configured for each given SPN for simplicity

    or

  • If a single service account is mandatory, the same salt must be used for each ktpass command when generating the incremental keytab file.

Example:

Assume we have Active Directory service account 'service-account' handling these 3 different SPNs and using AES256:

HTTP/app1.example.com@EXAMPLE.COM
HTTP/app2.example.com@EXAMPLE.COM
HTTP/app3.example.com@EXAMPLE.COM

After running the 3 below commands, you will get a final keytab that will be valid for these 3 above SPNs:

  1. ktpass -princ HTTP/app1.example.com@EXAMPLE.COM -mapuser service-account@EXAMPLE.COM -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -pass F5Networks -out app1_aes256.keytab
  2. ktpass -princ HTTP/app2.example.com@EXAMPLE.COM -mapuser service-account@EXAMPLE.COM -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -pass F5Networks -in app1_aes256.keytab -rawsalt "EXAMPLE.COMHTTPapp1.example.com" -out app1_2_aes256.keytab -setupn
  3. ktpass -princ HTTP/app3.example.com@EXAMPLE.COM -mapuser service-account@EXAMPLE.COM -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -pass F5Networks -in app1_2_aes256.keytab -rawsalt "EXAMPLE.COMHTTPapp1.example.com" -out app1_2_3_aes256.keytab -setupn

The final keytab content will look like this:

PS C:\keytabs> ktpass /in app1_2_3_aes256.keytab

Existing keytab:
Keytab version: 0x502
keysize 84 HTTP/app1.example.com@EXAMPLE.COM ptype 1 (KRB5_NT_PRINCIPAL) vno 3 etype 0x12 (AES256-SHA1) keylength 32 (0x667e57c5e7c19dd274a2ef92698d4a9c043b9078de4b834a5a6c399b73cd947c)
keysize 84 HTTP/app2.example.com@EXAMPLE.COM ptype 1 (KRB5_NT_PRINCIPAL) vno 4 etype 0x12 (AES256-SHA1) keylength 32 (0x667e57c5e7c19dd274a2ef92698d4a9c043b9078de4b834a5a6c399b73cd947c)
keysize 84 HTTP/app3.example.com@EXAMPLE.COM ptype 1 (KRB5_NT_PRINCIPAL) vno 5 etype 0x12 (AES256-SHA1) keylength 32 (0x667e57c5e7c19dd274a2ef92698d4a9c043b9078de4b834a5a6c399b73cd947c)

The service account will look like this after running these 3 commands:

PS C:\keytabs> Get-ADUser -Identity service-account -property msDS-KeyVersionNumber,ServicePrincipalName,KerberosEncryptionType

DistinguishedName     : CN=service-account,CN=Users,DC=example,DC=com
Enabled               : True
GivenName             :
KerberosEncryptionType : {AES128, AES256}
msDS-KeyVersionNumber : 5
Name                  : service-account
ObjectClass           : user
ObjectGUID            : 342246b3-cd5b-494f-a988-cdc98c0bdeda
SamAccountName        : service-account
ServicePrincipalName  : {HTTP/app1.example.com, HTTP/app2.example.com, HTTP/app3.example.com}
SID                   : S-1-5-21-882427465-4011647165-2960366939-16634
Surname               :
UserPrincipalName     : HTTP/app1.example.com@EXAMPLE.COM

Notes:

  • the '-setupn' used in commands 2) and 3) will make sure the UserPrincipalName enforced in command 1) is kept, so resulting UserPrincipalName will be HTTP/app1.example.com in this example.
  • default salt from first command is "EXAMPLE.COMHTTPapp1.example.com", hence why this is what must be enforced as salt in commands 2) and 3) using '-rawsalt' option.
  • if you prefer having the same kvno number for every keytab entry, previous commands can be adjusted as below:

Assuming msDS-KeyVersionNumber attribute of Active Directory service account 'service-account' is 10 (as an example) before running the below commands:

  1. ktpass -princ HTTP/app1.example.com@EXAMPLE.COM -mapuser service-account@EXAMPLE.COM -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -pass F5Networks -kvno 13 -out app1_aes256.keytab
  2. ktpass -princ HTTP/app2.example.com@EXAMPLE.COM -mapuser service-account@EXAMPLE.COM -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -pass F5Networks -kvno 13 -in app1_aes256.keytab -rawsalt "EXAMPLE.COMHTTPapp1.example.com" -out app1_2_aes256.keytab -setupn
  3. ktpass -princ HTTP/app3.example.com@EXAMPLE.COM -mapuser service-account@EXAMPLE.COM -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -pass F5Networks -kvno 13 -in app1_2_aes256.keytab -rawsalt "EXAMPLE.COMHTTPapp1.example.com" -out app1_2_3_aes256.keytab -setupn

The final keytab content will look like this:

PS C:\keytabs> ktpass /in app1_2_3_aes256.keytab
Existing keytab:

Keytab version: 0x502
keysize 84 HTTP/app1.example.com@EXAMPLE.COM ptype 1 (KRB5_NT_PRINCIPAL) vno 13 etype 0x12 (AES256-SHA1) keylength 32 (0x667e57c5e7c19dd274a2ef92698d4a9c043b9078de4b834a5a6c399b73cd947c)
keysize 84 HTTP/app2.example.com@EXAMPLE.COM ptype 1 (KRB5_NT_PRINCIPAL) vno 13 etype 0x12 (AES256-SHA1) keylength 32 (0x667e57c5e7c19dd274a2ef92698d4a9c043b9078de4b834a5a6c399b73cd947c)
keysize 84 HTTP/app3.example.com@EXAMPLE.COM ptype 1 (KRB5_NT_PRINCIPAL) vno 13 etype 0x12 (AES256-SHA1) keylength 32 (0x667e57c5e7c19dd274a2ef92698d4a9c043b9078de4b834a5a6c399b73cd947c)

Note:

  • each ktpass will increment the msDS-KeyVersionNumber value, so the forecasted final kvno will be 13 (10+1+1+1) after running 3 ktpass commands.

Additional Information

In order to be able to use AES encryption, the Active Directory service account must be configured to allow it (cf K01716018 or K73872229 ).

Enforcing it the Powershell way:

PS> Set-ADUser -Identity service-account -KerberosEncryptionType "AES128,AES256"
