Description

How to determine if ASM has detected and prevented a slow transaction attack such as slow POST (body) or Slow Loris (headers)

The BIG-IP ASM system is capable of detecting and preventing Slow HTTP POST DDoS attacks by using the internal parameter slow_transaction_timeout in conjunction with the max_slow_transactions parameter to perform this enforcement.
The BIG-IP ASM system does not report the enforcement as a violation in the Configuration utility. When the BIG-IP ASM system has prevented Slow HTTP POST DDoS attacks, it logs indicative messages to the /var/log/ts/bd.log file and the /var/log/asm file.

Error Message:

01310001:3: event code D6983 Slow transactions attack detected - account id: (18), number of dropped slow transactions: (350)
ATTACK_ENGINE|NOTICE|Dec 14 08:47:00.962|8469|dos_engine.c:6982|Slow transactions attack detected - account id: (18), number of dropped slow transactions: (350)

Environment

  • ASM provisioned 
  • ASM policy is applied to a virtual server. Slow transaction protections are enabled by default with the ASM policy.

Cause

This is expected behavior.

Recommended Actions

Verifying Slow HTTP POST DDoS attack prevention
Impact of procedure: The following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP ASM command line.
  2. Review /var/log/ts/bd.log for log messages containing the string "Slow transactions attack detected"
    # grep "Slow transactions attack detected" /var/log/ts/bd.log
    Example Log: ATTACK_ENGINE|NOTICE|Dec 14 08:47:00.962|8469|dos_engine.c:6982|Slow transactions attack detected - account id: (18), number of dropped slow transactions: (350)
  3. Review /var/log/asm for log messages containing the string "Slow transactions attack detected"
    # grep "Slow transactions attack detected" /var/log/asm
    Example Log: 01310001:3: event code D6983 Slow transactions attack detected - account id: (18), number of dropped slow transactions: (350)

Depending on the attack and environment or application requirements, you may need to tune the parameters controlling this protection. For example your application may experience false-positive blocks due to the protections because your application requires a longer timeout due to specific network variables unique to your environment.
 

Note: Slow transactions dropped in this way receive no response from the server at all, and the connection is terminated without response. This is contrary to other BIG-IP ASM blocking mechanisms which serve the BIG-IP ASM blocking page in response.


Impact of procedure: If you change the values of the max_slow_transactions or slow_transaction_timeout parameters, you must restart BIG-IP ASM for the new values to take effect. For this reason, you should make these changes during a maintenance window, or you should perform the changes on a standby unit and fail over traffic after the restart has completed.

  1. Log in to the Configuration utility.
  2. Go to Security > Options > Application Security > Advanced Configuration > System Variables.
  3. For Search by Parameter Name, enter slow and select Go.
  4. Configure the values for the max_slow_transactions and slow_transaction_timeout parameters appropriately for the target environment.
  5. Restart the BIG-IP ASM service by entering the following command:
    # tmsh restart /sys service asm

Additional Information

slow_transaction_timeout (Default Value : 10 seconds) – Specifies the number of seconds after which a transaction is considered slow. A *transaction* is the amount of time that passes between the "request" event (once the Enforcer gets the transaction headers) and the "request done" event. 
max_slow_transactions (Default Value : 25 transactions) – Specifies the maximum number of slow transactions per CPU. If the Enforcer recognizes a slow connection, it checks whether the number of current slow connections is equal to the configured limit. If it is, the Enforcer disconnects the "slow connection".

Example: With a quad core CPU and max_slow_transactions set to a value of 2 in theory there could be 8 total slow transactions (2 per CPU) as determined by the value of slow_transaction_timeout and no connections would be silently dropped. Once one more slow transaction arrives we will begin enforcement on that connection silently dropping it.
