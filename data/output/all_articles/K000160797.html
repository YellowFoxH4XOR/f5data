Description

Loss of connectivity to virtual server IPs and floating self-IPs in Azure Stack Hub. Symptoms include inability to ping or access services via the virtual server or floating IPs from external devices. Packet captures show no ARP responses from BIG-IP for these IPs, and ARP requests are not observed arriving at BIG-IP.

Environment

  • Product: BIG-IP LTM
  • Version: 17.5.1
  • Deployment: Azure Stack Hub private cloud
  • Configuration: High Availability (HA) pair (Active/Standby)
  • Virtual server IPs and floating self-IPs configured

Cause

Virtual server and floating self-IPs were not registered as static secondary IPs on the Active BIG-IP VM’s NIC in Azure Stack Hub. Azure Stack Hub’s SDN fabric does not propagate ARP for unregistered IPs, causing ARP replies from BIG-IP to be dropped and resulting in loss of connectivity. This is by design in Azure/Azure Stack Hub environments.

Answer/Recommended Actions

  1. Register all virtual server and floating self-IPs as static secondary IPs on the Active BIG-IP VM’s NIC in Azure Stack Hub.
  2. Do NOT register these IPs on the Standby unit’s NIC; Azure Stack Hub does not support simultaneous assignment of the same secondary IP to multiple NICs.
  3. For automated failover in HA deployments:
    • Deploy and configure the F5 Cloud Failover Extension (CFE) to move secondary IPs between NICs during failover events.
    • Ensure both BIG-IP VMs have the required Azure permissions (Contributor role) and proper NIC tagging for CFE operation.
    • Confirm CFE compatibility with your Azure Stack Hub version before implementation.
  4. If CFE cannot be used due to Azure Stack Hub API limitations:
    • Manually reassign secondary IPs to the new Active unit’s NIC during failover.
    • Remove the IPs from the previously Active NIC before adding them to the new Active NIC.
  5. Improper IP management during failover can result in a complete traffic outage.

Additional Information

  • This behavior is expected in Azure and Azure Stack Hub environments due to SDN design.
  • Traditional GARP-based failover mechanisms are not supported; IPs must be moved at the Azure control plane level.
  • Manual failover is operationally intensive and not recommended for environments requiring high availability.
  • Frequent or improper failover handling can result in loss of all Azure-configured secondary IPs, causing a full traffic outage.
