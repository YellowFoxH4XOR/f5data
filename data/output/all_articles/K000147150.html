Answer/Recommended Actions

Insecure design is a broad category representing different weaknesses, expressed as “missing or ineffective control design.” Insecure design is not the source for all other Top 10 risk categories. There is a difference between insecure design and insecure implementation. We differentiate between design flaws and implementation defects for a reason, they have different root causes and remediation. For more information, please visit: A04:2021 – Insecure Design

Insecure design can include the absence of mechanisms like rate limiting, which can allow attackers to brute-force credentials without restriction. Your application might lack rate limiting on the login page, enabling attackers to attempt multiple password guesses rapidly. and we are going to focus on the following scenario below and how to mitigate it using a Rate Limiting policy in Distributed Cloud (XC).

To configure a Rate Limiting Policy:

  1. Make sure that you already have a LB configured. The following article should help you with this process: HTTP Load Balancer
  2. Now, let's configure our Rate Limiting policy in our LB. To do that, navigate in your XC console to your LB by going to: Home >> Web App & API Protection >> select the namespace in which you configure your LB >> Manage >> Load Balancers >> HTTP Load Balancers
     

  3. Locate your LB and click on the 3-dot figure at the right of your screen and select "Manage Configuration"
     

  4. Click on the "Edit Configuration" button at the upper-right corner of the console, select "Common Security Controls" from the "Edit" Menu, then locate the "Rate Limiting" option, select "Custom Rate Limiting Parameters" and then click on the "View Configuration" option below:
     

  5. Select an appropriate amount of request, you can configure it per second, minute or hour. You can also configure a burst multiplier if you expect to receive a burst of requests on your application:
     


  6. Click on the "Apply" button at the bottom-right of the console, and then click "Save and Exit" at the same location.

  7. To verify that the Rate Limiting policy is working as expected, we are running a test using the OWASP Juice Shop, which is a vulnerable application configured as backend. Check on the "Additional Information" for details on how we set this scenario.

    When executing the repeated curl request more than 10 times in less than a minute, our Rate Limiting Policy kicks in blocks the last request with a "429" HTTP response code and a support ID:
     

  8. To verify the Support ID that you just received, go back to the XC console and navigate to Home >> Web App & API Protection >> select the namespace in which you configure your LB >> Overview >> Security, then scroll to the bottom of the console and select your LB:

     

  9. Once in that page, click on the "Security Analytics" tab where you will see the latest security violations
     

  10. Click in the "Add Filter" option and then select: "req_id >> in >> insert the Support ID that you received in the juice shop". 
     
    Please be aware that, by default, the time range for the violations is 5 minutes, but you can adjust that time range as needed.

  11. The result will display the violation details in which you will be able to see detailed information about the source, the request that was made, and below that you will see the detection type, which is "svc_policy_sec_event" and the action that was taken, which was a "fail":

     

 

Additional Information

In this scenario, we are using OWASP Juice Shop, which is an insecure web application designed for security training and other related purposes. For more information about the Juice Shop please visit: OWASP Juice Shop

For this exercise we are executing a curl request that simulates a brute force attack trying different passwords for the admin account. As you can see from the script, it uses a different number in the password field for each run:

for i in {1..11}; do

curl -X POST "https://owasptest.test/rest/user/login" \
--header 'Content-Type: application/json' \
-d '{"email":"admin@juice-sh.op","password":"password12$i"}'

done
