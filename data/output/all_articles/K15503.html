Topic

The BIG-IP APM configuration for high availability (HA) does not use the same mirroring configuration settings that you typically use when configuring BIG-IP LTM devices for HA.

The important difference between a BIG-IP APM system and a BIG-IP LTM HA configuration is that the BIG-IP LTM system is set to mirror the TCP flow state of existing connections (connection mirroring), whereas the BIG-IP APM system is primarily an SSL-VPN application delivery platform which handles authentication and acts as a sophisticated conduit to pass HTTP and non-HTTP connections through an established BIG-IP APM HTTP session.

The BIG-IP APM system uses the Traffic Management Microkernel (TMM) sessionDB, which stores layer-7 (L7) data such as persistence, table, and sub-table state information. The system mirrors this information to BIG-IP APM peer HA devices to maintain state in the event of a failover. The BIG-IP APM system does not rely on TCP connection-level information mirrored between BIG-IP APM HA peer devices, but the BIG-IP APM system relies on the information mirrored from sessionDB.

Description

The following items describe expected BIG-IP APM failover behavior:

  • Authenticated client sessions are maintained.
  • Persistent protocol connections for the access sessions, such as TCP, SSL, and PPP, are reset based on the type of access and configured features, such as iSession, SSL VPN, forward error correction (FEC), and others.
  • Resetting protocols triggers clients to automatically renegotiate connections approximately two to five seconds after a failover event.
  • The system re-establishes user sessions by using mirrored sessionDB information.
  • Previous tunnel sessions should re-establish when the tunneled protocol supports TCP/User Datagram Protocol (UDP) reconnect, as with HTTP and Remote Desktop Protocol (RDP).

    Note: Tunneled connections that use protocols, such as FTP and secure shell (SSH), may not automatically re-establish, depending on the connection nature of these protocols.

  • Portal Access sessions and BIG-IP LTM+APM deployments do not maintain persistent protocol connections, so, following a failover, the system forwards the next HTTP request to the active unit and the session proceeds without interruption.

Recommendations

When configuring BIG-IP APM devices for failover:

  • You must configure the BIG-IP APM devices with mirroring IP addresses.

    For more information, refer to K14135: Defining network resources for BIG-IP high-availability features (11.x -16.x).

  • You should configure the BIG-IP APM virtual servers with connection mirroring disabled.

    For more information, refer to K17391: Configuring SSL connection mirroring for Client SSL virtual servers and the Managing Connection Mirroring chapter of the BIG-IP Device Service Clustering: Administration manual.

    Note: For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.

  • Prior to BIG-IP 13.1, you should use the single traffic group traffic-group-1 since BIG-IP APM HA is only supported in active-standby peer configurations. Starting in BIG-IP 13.1, you can use any traffic group, but all BIG-IP APM traffic objects must exist in the same traffic group. Additionally, in BIG-IP 13.1 and later BIG-IP APM systems can support up to eight member in a device service clustering (DSC) device group.

    For more information, refer to the Preconfigured traffic groups section of the Managing Failover chapter of the BIG-IP Device Service Clustering: Administration manual and K13983: BIG-IP APM HA Deployments.

    Note: For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.

  • You should run BIG-IP APM peer devices on identical hardware.

    For more information, refer to K7040: BIG-IP APM and FirePass do not support mixing hardware platforms within a high availability pair.

  • On applicable devices, the Turboflex profile or the FPGA firmware, or both, must be set to the same value on all devices in the device-group for mirroring to work correctly.

When configuring Virtual Clustered Microprocessing (vCMP) for failover:

  • All vCMP guest peers must run the same BIG-IP version.
  • All vCMP host peers must run the same BIG-IP version. vCMP guests inherit the disaggregation library (daglib) from their hypervisor, so each host must run the same BIG-IP version to ensure that traffic is hashed in the same manner on each guest.
  • All vCMP hosts must use the same platform type. Different platform types may use different daglib versions, so each host must run on the same platform type to ensure traffic is hashed in the same manner on each guest.
  • You must configure all vCMP guests with the same number of CPU cores to ensure the same number of the Traffic Management Microkernel (TMM) instances are present on each guest. This is also a requirement for mirroring to work.
  • You must provision all vCMP guests on a VIPRION platform for the same number of slots and the guests must use the same slot positions.
  • You must configure VLANs used for HA traffic with the default Clustered Microprocessing (CMP) hash.

Note: vCMP guests may run a different BIG-IP version than vCMP hosts so long as all previously listed requirements are met.

Note: BIG-IP APM systems running 13.1.0 and later that are deployed in active-standby-standby mode will only see access sessions mirrored to the device marked next active in the traffic group, not to all devices.

View the statemirror.mirrorsession system database variable

  1. Log in to the TMOS Shell (tmsh) by entering the following command:

    tmsh

  2. To see the current value of statemirror.mirrorsessions, enter the following command:

    list /sys db statemirror.mirrorsessions

    Output appears similar to the following example:

    sys db statemirror.mirrorsessions {
        value "enable"
    }

Enable the statemirror.mirrorsession system database variable

Impact of procedure: Enabling statemirror.mirrorsessions uses additional system resources.

  1. To re-enable statemirror.mirrorsessions if it has been disabled, enter the following command:

    modify /sys db statemirror.mirrorsessions value enable

  2. Save the change by entering the following command:

    save /sys config
