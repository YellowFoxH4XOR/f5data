K000152209: [F5OS] confd's RSS memory may grow rapidly after successful restore of confd backup on a new platform

Type
Support Solution
Published
2025-06-27
Updated
2025-06-27
Applies to
  • F5OS
  • F5OS-A: 1.5.X, 1.7.X, 1.8.X, 1.8.0, 1.7.0, 1.5.3, 1.5.2, 1.5.1, 1.5.0
  • F5OS-C: 1.6.X, 1.8.X, 1.8.1, 1.8.0, 1.6.2, 1.6.1, 1.6.0
Source
https://my.f5.com/manage/s/article/K000152209

Description

After successful restore of confd backup on a new platform, for example due to RMA, the system may become unusable due to excessive memory usage. 'top' output indicates confd.smp consuming a lot of resident memory.

SSH and GUI may not work at all or become very sluggish. Console is the only way to log in with local users credentials (remote users may time out). The instability comes back quickly after reboot.

In confd backup file, there are two entries for each SNMP user and ENGINE IDs in them are pointing to different MAC addresses.

Example (user=spectrum):

<usmUserEntry>
<usmUserEngineID>80:00:2f:f4:03:14:a9:d0:67:0b:02</usmUserEngineID> ------> EngineID with current device MAC address
<usmUserName>spectrum</usmUserName>
<usmUserSecurityName>spectrum</usmUserSecurityName>
<usmUserAuthProtocol>1.3.6.1.6.3.10.1.1.3</usmUserAuthProtocol>
<usmUserPrivProtocol>1.3.6.1.6.3.10.1.2.4</usmUserPrivProtocol>
</usmUserEntry>

<usmUserEngineID>80:00:2f:f4:03:14:a9:d0:38:fa:02</usmUserEngineID> ------> EngineID based on old device MAC address
<usmUserName>spectrum</usmUserName>
<usmUserSecurityName>spectrum</usmUserSecurityName>
<usmUserAuthProtocol>1.3.6.1.6.3.10.1.1.3</usmUserAuthProtocol>
<usmUserPrivProtocol>1.3.6.1.6.3.10.1.2.4</usmUserPrivProtocol>
<usmUserAuthKey>b2:e7:ec:c1:d9:ca:6d:b7:f5:20:95:5a:b9:d8:69:7f:3f:da:b4:d7</usmUserAuthKey>
<usmUserPrivKey>b2:e7:ec:c1:d9:ca:6d:b7:f5:20:95:5a:b9:d8:69:7f</usmUserPrivKey>
</usmUserEntry>

Environment

  • F5OS
  • Restoring confd backup from a different system, for example due to RMA
  • SNMP users stored in confd backup
  • SNMP targets configured
  • SNMP trap authentication enabled

Cause

The system was restored with another system's backup. For example, due to RMA.
Due to engine ID difference, you hit ID1812497, which caused SNMP users to be created with no passwords.
These users were associated with SNMP targets and SNMP trap authentication was enabled on the system.
Confd was trying to authenticate the SNMP users, and it was failing, continuously generating authentication failure traps. This caused a memory spike in the confd.smp.
New ID1968289 was created for confd.smp memory issue.

Recommended Actions

Reboot the device to recover from memory pressure. Once the device is back, quickly log in with admin user credentials, and disable SNMP trap authentication:

appliance-1# config
Entering configuration mode terminal
appliance-1(config)# SNMPv2-MIB snmp snmpEnableAuthenTraps disabled
appliance-1(config)# commit

The device should become stable at this point. Go to SNMP user settings, delete all users, and recreate them. Once this is committed, enable SNMP trap authentication again.

Additional Information

Although the workaround for ID1812497 (reenter SNMP user passwords) should suffice, recreating SNMP users is recommended.
This approach will remove stale SNMP users from the old device that are saved in confd backup. So taking and restoring backups in the future will be smooth.
