Topic

BIG-IP DNS and Link Controller systems can use SSL certificates signed by third-party Certificate Authorities (CA) to authenticate iQuery communications between BIG-IP systems.

Description

SSL device certificates signed by a third-party CA must include both the client authentication (clientAuth) and server authentication (serverAuth) extended key usage (EKU) extensions, to allow use by both server and client applications. For example, the big3d process operates as a server (serverAuth), while the gtmd process operates as a client (clientAuth).

Note: For information about the deprecation of clientAuth EKU for public certificates generated by Public Key Infrastructure (PKI) certificate authorities (CA) and what you can do to prepare, you may want to refer to the F5 DevCentral article: The End of ClientAuth EKU…Oh Mercy…What to do?.

If the EKU extensions are insufficient for the purposes of iQuery communications, then the following symptoms may be seen:

  • In the output of tmsh show gtm iquery the peer will not be showing connected
  • In the packet trace the handshake will be terminated with diagnostics Unsupported Certificate

    Frame #20 10.406194 10.2.2.2 -> 10.1.1.1 59 TLSv1.2 <F5TMM in> Alert (Level: Fatal, Description: Unsupported Certificate)

  • In the DNS log file /var/log/gtm, you may observe an error message similar to the following example:

    011ae114:3: iqmgmt_ssl_connect: SSL error: error:14094413:SSL routines:ssl3_read_bytes:sslv3 alert unsupported certificate (12345678) from connection 10.1.1.1

  • If you attempt to run iqdump, you may observe the iqdump fails with an error message similar to the following example:

    ssl3_read_bytes:sslv3 alert unsupported certificate:s3_pkt.c:1498:SSL alert number 43 SSL return code: SSL_ERROR_ZERO_RETURN

Verifying EKU extensions

To verify the EKU extensions on the BIG-IP DNS system, use the following procedure:

Impact of procedure: The following procedure should have no impact to your system.

  1. Secure copy (SCP) the SSL device certificate to the /var/tmp directory of the BIG-IP DNS system.
  2. Log in to the Advanced Shell (bash) of the BIG-IP DNS system.
  3. To verify your third-party certificate has the clientAuth and serverAuth extensions included, type the following command:

    openssl x509 -noout -purpose -in /var/tmp/<cert_name> | grep -iE 'client|server'

    For example, to verify the device certificate has the needed extensions, type the following command:

    openssl x509 -noout -purpose -in /config/httpd/conf/ssl.crt/server.crt | grep -iE 'client|server'

  4. The command output should show Yes for both SSL client and SSL server:

    SSL client : Yes
    SSL client CA : No
    SSL server : Yes
    SSL server CA : No

Note: Unless the Common Name of the certificate is a wildcard, the CN attribute should be unique within the DNS sync group.

Renewing or replacing a device certificate

Important: When installing a third-party CA signed certificate the full chain must be installed on the system. There are two ways to do this:

  • For versions prior to BIG-IP 14.1.x, you must import your device certificate as a single file that contains the CA signed device certificate, the root CA certificate, and all intermediate certificates. The maximum size of the combined certificate must be less that 8000 bytes. OR
  • Follow the steps under Update DNS sync group peers in K16951115: Changing the BIG-IP DNS system device certificate using the Configuration utility. Installing the Root CA and any needed Intermediate Certificates in both the Device Trusted Certificates and the GSLB Trusted Server Certificates is required.

Note: You must reinitialize the iQuery connection to use the new device certificate by restarting the gtmd and big3d processes.
