Description

  • FQDN pool members/Nodes are marked down or unavailable.
  • GUI showed node was unavailable (yellow triangle) icon. Mouse over the icon showed "FQDN does not exist. DNS query returns NXDOMAIN" or "No records returned."
  • Errors seen in the /var/log/dynconfd.log file

    Example log messages:
    2019-04-01 06:26:57.474834 (26092) [E]: [BIG-IP-01.local]: FQDN does not exist. DNS query returns NXDOMAIN
    2019-04-01 07:26:57.500746 (26092) [E]: [BIG-IP-01.local]: FQDN does not exist. DNS query returns NXDOMAIN

Environment

  • FQDN Pool members marked down
  • FQDN Node state: state fqdn-up-no-address
  • there may be more than one DNS server configured on the BIG-IP

Cause

The dynconfd daemon successfully queried the DNS server, and the DNS server responded that it has no knowledge of the indicated FQDN name ("DNS query returns NXDOMAIN") or the DNS server returns a valid DNS answer (RCODE 5 - REFUSED).

Recommended Actions

  • Restarting the dynconfig daemon will temporarily resolve the issue.
    You can use the following tmsh command to resolve the issue
    tmsh restart /sys service dynconfd
     
  • To troubleshoot the issue, you can turn on debug logging temporarily for the dynconfd daemon before restarting the daemon. Make sure that dynconfd makes a query for the FQDN node you are troubleshooting before restarting the daemon. You can use the following procedure to enable dynconfd logging:

    Impact of procedure: Verbose debug logging over time may result in an exhaustion of disk space. Debug level messages for the dynconfd process will now log to the /var/log/dynconfd.log file. You should only enable debug logging while actively troubleshooting DNS issues. You should disable debug logging after you have collected the desired information.
  1. Log in to the TMOS Shell (tmsh) by typing the following command:
    tmsh
  2. Set the logging level for the dynconfd process to debug by typing the following command:
     modify /sys db dynconfd.loglevel value debug_msg
  3. Restart the dynconfig daemon:
    restart /sys service dynconfd
  4. Collect the log file from /var/log/dynconfd.log file
  5. To restore the default logging level for the dynconfd daemon, issue the following command:
    modify /sys db dynconfd.loglevel reset-to-default
  6. You can forward the log file to F5 support for further debugging
  • With the information about the FQDN returning NXDOMAIN, and the DNS server returning that record, you should either fix the DNS server to have the appropriate FQDN record, or you should stop using the DNS server that does not have the record.
  • For RCODE 5 - REFUSED investigate and resolve why the DNS Server is refusing. Alternatively remove the DNS server responding with the RCODE 5.

Additional Information

  • The dynconfd process manages a list of DNS servers (resolvers) as part of the FQDNv2 implementation of the BIG-IP LTM monitors that permits users to configure 'node' and 'pool-member' instances using a Fully Qualified Domain Name (FQDN), where IP addresses are resolved through a lookup to a DNS server. FQDNv2 is released in BIG-IP 13.1.0.

Impact if not running: Communication with the DNS servers is lost, and FQDN monitoring fails.

Note: It is a common occurrence to use local caching or forwarding DNS servers that have internal only records that are used for FQDN nodes. Using a public DNS server without these internal records will eventually cause this issue to occur. Restarting dynconfd may temporarily fix this issue, but it will manifest again until the DNS server without the FQDN records is removed from the list of resolvers to use.

  • When the BIG-IP system receives an NXDOMAIN response, it will not immediately re-query the DNS server(s). Rather, the BIG-IP system will wait again for the interval or TTL to expire before another attempt is made.
