K000135767: Sensitive data being shown in istio-proxy sidecar logs

Type
Support Solution
Published
2023-08-08
Updated
2023-08-09
Applies to
  • Aspen Mesh: 1.14, 1.11
Source
https://my.f5.com/manage/s/article/K000135767

Description

istio-proxy sidecar logs contain sensitive information as part of the request, e.g. in the path portion, and the information needs to be removed from the logs.

[2022-03-25T06:05:12.372Z] "POST /example/?SSN=XXXXXXXX HTTP/1.1" 200 - via_upstream - "" 0 541 180 179 "10.10.10.10" "" "4684f627-ad47-43fe-8fa3-dc5666b587b5" "example.com" "10.214.1.128:443" outbound|443||example.com 10.11.11.11:43048 10.11.11.11:8443 10.10.10.10:56448 example.com


Environment

Aspen Mesh 1.11.x and Aspen Mesh 1.14.x
 

Cause

Application is sending sensitive data in clear text as part of the request and Istio/Aspen Mesh sidecar is logging it as part of the default access log format.
 

Recommended Actions

In this example, we can remove the %REQ(X-ENVOY-ORIGINAL-PATH?:PATH)% portion from the default access log format or modify it to %REQ(X-ENVOY-ORIGINAL-PATH?:PATH):8% to truncate the path to 8 characters (or any other amount) by defining an access log format in the Aspen Mesh Overrides file:

❯ cat aspen-mesh-override-values.yaml #in this example we are removing the path entirely
meshConfig:
  accessLogFormat: "[%START_TIME%] \"%REQ(:METHOD)% %PROTOCOL%\" %RESPONSE_CODE% %RESPONSE_FLAGS% %RESPONSE_CODE_DETAILS% %CONNECTION_TERMINATION_DETAILS% \"%UPSTREAM_TRANSPORT_FAILURE_REASON%\" %BYTES_RECEIVED% %BYTES_SENT% %DURATION% %RESP(X-ENVOY-UPSTREAM-SERVICE-TIME)% \"%REQ(X-FORWARDED-FOR)%\" \"%REQ(USER-AGENT)%\" \"%REQ(X-REQUEST-ID)%\" \"%REQ(:AUTHORITY)%\" \"%UPSTREAM_HOST%\" %UPSTREAM_CLUSTER% %UPSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_REMOTE_ADDRESS% %REQUESTED_SERVER_NAME% %ROUTE_NAME%\n"

❯ helm upgrade istiod manifests/charts/istio-control/istio-discovery \
    --namespace istio-system \
    --values aspen-mesh-override-values.yaml

Additional Information

The default access log format contains the following 
[%START_TIME%] \"%REQ(:METHOD)% %REQ(X-ENVOY-ORIGINAL-PATH?:PATH)% %PROTOCOL%\" %RESPONSE_CODE% %RESPONSE_FLAGS% %RESPONSE_CODE_DETAILS% %CONNECTION_TERMINATION_DETAILS% \"%UPSTREAM_TRANSPORT_FAILURE_REASON%\" %BYTES_RECEIVED% %BYTES_SENT% %DURATION% %RESP(X-ENVOY-UPSTREAM-SERVICE-TIME)% \"%REQ(X-FORWARDED-FOR)%\" \"%REQ(USER-AGENT)%\" \"%REQ(X-REQUEST-ID)%\" \"%REQ(:AUTHORITY)%\" \"%UPSTREAM_HOST%\" %UPSTREAM_CLUSTER% %UPSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_REMOTE_ADDRESS% %REQUESTED_SERVER_NAME% %ROUTE_NAME%\n

Starting with Aspen Mesh 1.14.x the access log format can be applied on an individual namespace, or to an individual workload, to control logging at a fine grained level using the Telemetry API.

The first step is to add extension providers in the override values file (at the mesh config level), here we can define the different log formats: 
meshConfig:
    extensionProviders:
      - name: file-log
        envoyFileAccessLog:
          path: /dev/stdout
          logFormat:
            text: "[%START_TIME%] \"%REQ(:METHOD)% %REQ(X-ENVOY-ORIGINAL-PATH?:PATH)% %PROTOCOL%\" %RESPONSE_CODE% %RESPONSE_FLAGS% \"%UPSTREAM_TRANSPORT_FAILURE_REASON%\" %BYTES_RECEIVED% %BYTES_SENT% %DURATION% %RESP(X-ENVOY-UPSTREAM-SERVICE-TIME)% \"%REQ(X-FORWARDED-FOR)%\" \"%REQ(USER-AGENT)%\" \"%REQ(X-REQUEST-ID)%\" \"%REQ(:AUTHORITY)%\" \"%UPSTREAM_HOST%\" %UPSTREAM_CLUSTER% %UPSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_REMOTE_ADDRESS% %REQUESTED_SERVER_NAME% %ROUTE_NAME%\n"
      - name: file-log2
        envoyFileAccessLog:
          path: /dev/stdout
          logFormat:
            text: "%RESPONSE_CODE% \"%REQ(:METHOD)% %REQ(X-ENVOY-ORIGINAL-PATH?:PATH)% %PROTOCOL%\"  %RESPONSE_FLAGS% \"%UPSTREAM_TRANSPORT_FAILURE_REASON%\" %BYTES_RECEIVED% %BYTES_SENT% %DURATION% %RESP(X-ENVOY-UPSTREAM-SERVICE-TIME)% \"%REQ(X-FORWARDED-FOR)%\" \"%REQ(USER-AGENT)%\" \"%REQ(X-REQUEST-ID)%\" \"%REQ(:AUTHORITY)%\" \"%UPSTREAM_HOST%\" %UPSTREAM_CLUSTER% %UPSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_LOCAL_ADDRESS% %DOWNSTREAM_REMOTE_ADDRESS% %REQUESTED_SERVER_NAME% %ROUTE_NAME% [%START_TIME%]\n"
In this case, we defined file-log and file-log2. For testing purposes, in file-log2 we placed [%START_TIME%] flag at the end and %RESPONSE_CODE% at the beginning.

The second step is to create a telemetry resource that will link to the extension providers as shown below: 
apiVersion: telemetry.istio.io/v1alpha1
kind: Telemetry
metadata:
  name: log-test1
  namespace: default
spec:
  accessLogging:
  - providers:
    - name: file-log2
  selector:
    matchLabels:
      service.istio.io/canonical-name: sleep
In this resource we can configure the workload specific behavior; this access logging configuration will only apply to the sleep application, while the rest will use the default one.
