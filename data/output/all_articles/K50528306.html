K50528306: HTTPS connections may fail with TCP reset when pool members require SNI

Type
Support Solution
Published
2019-05-15
Updated
2025-04-01
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K50528306

Description

  • Some pool members require Server Name Indication (SNI).
  • By default the Server SSL profile does not send a TLS server_name extension.
  • Pool member sends a TCP reset immediately after receiving Client Hello from BIG-IP LTM.

    For example, the following will be logged in the /var/log/ltm file:

    info tmm[<PID>]: 01260013:6: SSL Handshake failed for TCP <client_IP>:<client_port> -> <virtual_IP>:<virtual_port>

    In this error message, note the following:
    • <PID> is the process ID for the tmm process
    • <client_IP> is the IP address of the client.
    • <client_port> is the ephemeral port of the client.
    • <virtual_IP> is the destination IP address of the virtual server.
    • <virtual_port> is the destination port of the virtual server.

Environment

  • BIG-IP LTM
  • Server SSL profile
  • Pool members require SNI

Cause

By default, the Server SSL profile does not include TLS server_name extension.

Recommended Actions

  • Determining if the pool member requires SNI
  • Checking if the Server SSL profile is configured for SNI
  • Configuring the Server SSL profile to use SNI

Determining if the pool member requires SNI

The HTTPS servers in your pool may have been configured to require SNI.  If you are unable to verify the server configuration yourself of with the server administrator, perform the following procedures:

Using the openssl s_client command to test for SNI

  1. Log into the Advanced Shell (bash).

     

    Note: If you are at the (tmos) # prompt, type q to exit to the bash shell.

  2. Test the connection to the pool member without SNI by typing the following command:

    (echo -e "GET / HTTP/1.1\nHost: <server_name>\nConnection: Close\n\n";sleep 1) | openssl s_client -quiet -crlf -connect <pool_member_IP>:<pool_member_port>

    For example:

    (echo -e "GET / HTTP/1.1\nHost: example.com\nConnection: Close\n\n";sleep 1) | openssl s_client -quiet -crlf -connect 192.168.10.10:443

    Note: If the connection is reset or you receive an HTTP/1.1 403 Forbidden then your server likely requires SNI.

    Example output from an Apache web server when SNI is required:

    (echo -e "GET /test HTTP/1.1\nHost: example.com\nConnection: Close\n\n";sleep 1) | openssl s_client -quiet -crlf -connect 192.168.10.10:443
    depth=0 CN = pool-vm6958
    verify error:num=18:self signed certificate
    verify return:1
    depth=0 CN = pool-vm6958
    verify return:1
    HTTP/1.1 403 Forbidden
    Date: Fri, 15 Mar 2019 22:15:08 GMT
    Server: Apache/2.4.29 (Ubuntu)
    Content-Length: 429
    Connection: close
    Content-Type: text/html; charset=iso-8859-1

    <!DOCTYPE HTML PUBLIC "-//IETF//DTD HTML 2.0//EN">
    <html><head>
    <title>403 Forbidden</title>
    </head><body>
    <h1>Forbidden</h1>
    <p>You don't have permission to access /test

    </p>
    <hr>
    <address>Apache/2.4.29 (Ubuntu) Server at example.com Port 443</address>
    </body></html>
     

  3. Test the connection to the pool member with SNI by typing the following command:

    (echo -e "GET / HTTP/1.1\nHost: <server_name>\nConnection: Close\n\n";sleep 1) | openssl s_client -quiet -crlf -connect <pool_member_IP>:<pool_member_port> -servername <server_name>

    For example:

    (echo -e "GET / HTTP/1.1\nHost: example.com\nConnection: Close\n\n";sleep 1) | openssl s_client -quiet -crlf -connect 192.168.10.10:443 -servername www.example.com

    Note: If connection is successful, you have confirmed the server requires SNI.

    Example successful output:

    (echo -e "GET /test HTTP/1.1\nHost: example.com\nConnection: Close\n\n";sleep 1) | openssl s_client -quiet -crlf -connect 192.168.10.10:443 -servername www.example.com depth=0 CN = pool-vm6958

Checking if the Server SSL profile is configured for SNI

When using a Server SSL profile, the BIG-IP system acts as a client to the pool member, and the SSL properties of the connection is defined in the Server SSL profile. You can examine the properties of the Server SSL profile using the Configuration utility or the TMOS Shell (tmsh).

Verifying Server SSL profile settings using the Configuration utility

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Profiles > SSL > Server.
  3. Click the affected Server SSL profile.
  4. For Configuration, click Advanced.
  5. Review the Server Name property. If the field is blank, the BIG-IP system does not send a TLS SNI in the Client Hello.

Verifying Server SSL profile settings using tmsh

  1. Log into tmsh by typing the following command:

    tmsh
     
  2. Run the following command replacing <profile_name> with the name of the affected Server SSL profile:

    list /ltm profile server-ssl <profile_name> { server-name }

    The following output shows server-name is set to none, indicating SNI will not be sent in the Client Hello message:

    ltm profile server-ssl <profile_name> {
        server-name none
    }

Using tcpdump and tshark to confirm SNI is not in use

 

  1. Log in to the Advanced shell (bash)
  2. Start a fresh packet capture by typing the following command and replacing <pool_member_IP> and <pool_member_port> with the IP address and port of the pool member:

    tcpdump -s0 -i 0.0 host <pool_member_IP> and port <pool_member_port> -c 50 -w /var/tmp/K50528306_SNI.pcap -v

    Note: The above capture will write 50 packets to /var/tmp/K50528306_SNI.pcap and exit. To exit the capture early, type Ctrl-c.
     
  3. Send test traffic that includes the SNI server name to the pool member. You can use the command from step 3 of the Using the openssl s_client command to test for SNI procedure.
  4. Review the capture using tshark:

    tshark -r /var/tmp/K50528306_SNI.pcap -V -2 -R ssl | grep -A 7 'Extension: server_name'

    Note: If the output is empty, then SNI is not in use.

    Extension: server_name (len=20)
        Type: server_name (0)
        Length: 20
        Server Name Indication extension
            Server Name list length: 18
            Server Name Type: host_name (0)
            Server Name length: 15
            Server Name: www.example.com

Configuring the Server SSL profile to use SNI

Configuring the Server SSL profile to use SNI using the Configuration utility

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Profiles > SSL > Server.
  3. Click the affected Server SSL profile
  4. For Configuration click Advanced.
  5. For the Server Name option, enter the host name of the pool member.

Configuring the Server SSL profile to use SNI using tmsh

 

  1. Log in to tmsh by typing the following command:

    tmsh

  2. To view the current value for the server-name setting, type the following command replacing <profile_name> with the name of the Server SSL profile:

     

    list /ltm profile server-ssl <profile_name> { server-name }

  3. If the server-name setting is not configured with the correct host name, modify the Server SSL profile to use the desired host name by typing the following command. In the command, replace <profile_name> with the name of the Server SSL profile and <server_name> with the host name of the pool member:

    modify /ltm profile server-ssl <profile_name> { server-name <server_name> }

    For example:

    modify /ltm profile server-ssl serverssl_K50528306 { server-name example.com }

Additional Information

The SNI extension to the TLS protocol allows the client to include the host name it is connecting to in the client hello message.  Some HTTPS servers require SNI and may close a connection with a TCP reset if SNI is not provided in the Client Hello message.

In situations when HTTPS pool members consistently close connections from the BIG-IP system with a TCP reset immediately after receiving Client Hello, the lack of SNI in the Client Hello could be the reason, but it is not the only possible reason. You may need to troubleshoot to confirm if the lack of SNI is the cause.

Apache web servers will respond with an HTTP 4xx message when an invalid Server Name has been received and Microsoft IIS Servers (starting with IIS 8.0) will issue a TCP reset after receiving the Client Hello without a server_name TLS extension.
