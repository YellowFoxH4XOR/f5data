Description
This was exasperated by how Azure deals with HA failover of an ACTIVE/STANDBY setup. There is no mechanism within Azure to allow for failover. So to accomplish this a script has been written and is implemented when the heartbeat is exceeded. This script can take anywhere from 3 to 5 minutes to run and once started it cannot be stopped.

The script has to remove the IPs binded to the BIG-IP that is moving to STANDBY and then bind them to what will now be the ACTIVE BIG-IP.

The problem with this is if you have an issue where something such as memory pressure, or a service is having issues and constantly restarting, or anything that can cause an unexpected failover or failover loop then this time delay causes outages.

The default setting for a BIG-IP to begin failover, if it does not receive a reply from the peer is 3 seconds. So at 3.1 the failover process begins. This can be stopped in a more classic environment if say after 7.4 seconds they start to talk.

Environment

  • Azure
  • BIG-IP 

Cause
Azure has no way of moving the IPs so a script has been built to automatically move the IP Bindings if the heartbeat is exceeded.

Recommended Actions

The way to work with this is to modify the 3 second setting. Doing this provides the time for that momentary network glitch to be overcome without starting that script. If it is a real issue that would not matter either because it still takes 3 to 5 minutes for a real failover issue to happen anyway. So, what is 30 more seconds.

The setting to adjust is...
sys db failover.nettimeoutsec {
    default-value "3"
    scf-config "true"
    value "3"
    value-range "integer min:1 max:120"
}

As you can see it can be set from 3 to 120 seconds. We recommend you start at 30. In the cases where this has been an issue most all have worked well with that setting. A couple went to 40.

  1. To modify it you will need access to the CLI. 
tmsh modify sys db failover.nettimeoutsec value 30
