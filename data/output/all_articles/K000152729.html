Description

When installing or updating BIG-IP ASM Attack Signature files using LiveUpdate, the process may fail with Errors like below sample, under "/var/log/tomcat/live_update_upload.log":

live_update_upload 2025-02-08 00:05:36.060 +07:00  Error apply_asm_attack_signatures[10919] F5::LiveUpdate::PayloadHandler::clean_fail,,Fail load update files: TSocket: Could not read 1024 bytes from 127.0.0.1:9781

 

On WebUI, you may face the below Error Message while trying to Install the ASM Attack Signature Updates:

"Live Update file could not be loaded"

 

System status also shows very high SWAP Memory usage on WebUI (Statistics ›› Performance Reports ›› Memory Used), as well as using "free -h" command output: 

 

System kernel logs also Indicate 'OOM (Out-Of-Memory)' killer events under "/var/log/kern.log", including messages like:

kern     2025-07-21 15:52:44.000 +07:00      Warn     <Device-Name> kernel: postgres invoked oom-killer: gfp_mask=0x201da, order=0, oom_score_adj=0

...

kern     2025-07-23 14:20:06.000 +07:00      Warn     <Device-Name> kernel: mysqld invoked oom-killer: gfp_mask=0x201da, order=0, oom_score_adj=0

Environment

  • ASM/AWAF Module
  • ASM Attack Signatures Installation (LiveUpdate) Failed
  • High SWAP Memory Usage with some OOM-Killer Event Logs

Cause

This issue is caused by excessive Memory pressure resulting from:

  • Provisioning multiple Modules can Increase overall Memory demand
  • Insufficient allocation of Extra Memory via the 'provision' system DB variables
  • High SWAP Memory usage and OOM-Killer activity terminating critical processes needed for ASM and LiveUpdate operations

Recommended Actions

You can follow the below recommended actions one-by-one to check the results in your scenario. In most cases, only applying the first and/or second action can help to resolve the Issue.

Note: For all the below recommended actions, you need to consider performing the activity under a Maintenance Window to avoid any unexpected behavior of Traffic disruption.


1. De-provision Unused Modules:

Since in case of having multiple Modules as provisioned, you need more Memory allocated, as a workaround you can simply try to De-provision any unnecessary Module(s) to reduce overall Memory consumption.

 

2. Increase Provisioned Memory:

In case of having Default 'Provision' system variables or even low values for these parameters, as another workaround you can adjust the following system DB variables on each affected system to allocate more 'Provision' Memory for critical services.

For example, below we are going to Increase the value of "provision.extramb" from Its Default value "0" to "1024 MB", and the other one as "provision.tomcat.extramb" from Its Default value "0" to "128 MB", and the third one as "provision.restjavad.extramb" from Its Default value "384" to "512 MB":

# tmsh modify sys db provision.extramb value 1024
# tmsh modify sys db provision.tomcat.extramb value 128
# tmsh modify sys db provision.restjavad.extramb value 512
# bigstart restart tomcat httpd restjavad restnoded

 

3. Increase Total Memory:

In case of having vCMP Guests, F5OS Tenants, or Virtual Edition Instances, you may need to Increase the Memory assigned to the system to reduce the potential of Memory pressure risks.
