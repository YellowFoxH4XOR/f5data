K000150290: Vlan failsafe triggered when secondary blade is disabled and enabled in multi-blade VIPRION

Type
Support Solution
Published
2025-03-07
Updated
2025-03-07
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.2, 17.1.1, 17.1.0
Source
https://my.f5.com/manage/s/article/K000150290

Description

  • In a multi-blade Viprion system configured with VLAN failsafe, disabling and re-enabling a secondary blade triggers unnecessary failovers.

  • This occurs even when traffic continues to flow through other active blades, relevant logs may include:

Jan 22 09:20:18 slot2/viprion.local warning sod[27545]: 01140029:4: HA vlan_fs /Common/VLAN_Internal fails action is failover.
Jan 22 09:20:18 slot2/viprion.local warning sod[29969]: 01140029:4: HA cluster_member_disabled clusterd fails action is go offline and down links.

Environment

  • Multi-blades Viprion system.
  • VLAN configured with failsafe enabled and failsafe-action set to failover 
    net vlan /Common/VLAN_Internal {
    failsafe enabled    <<<<<-------- !!!
    failsafe-action failover    <<<<<-------- !!!
    interfaces { LACP_Internal { tag-mode service tagged } }
    tag 10
}

Cause

The issue is caused by a bug (ID1825153) in the software where disabling and re-enabling a secondary blade in a multi-blade Viprion system incorrectly triggers the VLAN failsafe mechanism, even though traffic continues to flow through other active blades.

Recommended Actions

  1. Use gateway-failsafe instead of VLAN-failsafe to avoid triggering unnecessary failovers until an official fix is available.
  2. Monitor the F5 Bug Tracker for updates on Bug ID1825153 for any fixes or patches that address this issue.
  3. Avoid disabling blades unnecessarily in environments where VLAN failsafe is critical.
