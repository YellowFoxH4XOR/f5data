Issue

Note: Starting in BIG-IP 11.4.0, the HTTP Class profile is replaced by the Local Traffic Policies feature. For more information, refer to K14409: The HTTP Class profile is no longer available in BIG-IP 11.4.0 and later.
An HTTP Class profile is the bridge between the BIG-IP LTM (Local Traffic Manager) and the BIG-IP ASM (Application Security Module). You use the HTTP Class profile to specify which incoming HTTP traffic should be either sent through the BIG-IP ASM or bypass the BIG-IP ASM before the traffic is load balanced by the BIG-IP LTM.

If traffic is not being passed to or bypassing the BIG-IP ASM system as expected, you should review the following common reasons:

  • Misconfiguration of the HTTP Class Profiles
  • The order in which the profiles are defined within the virtual server
  • Successive HTTP requests that do not match HTTP class may bypass the BIG-IP ASM

Misconfiguration of the HTTP Class Profiles

If traffic is not being passed to or bypassing the BIG-IP ASM system as expected, you should review the HTTP Class profile configuration.

Within the HTTP Class profile you specify the type of traffic that is passed to the BIG-IP ASM system. To do this, select Application Security Enabled when configuring the profile.

In addition, you can use an HTTP Class Profile to specify what traffic is not to be passed to the BIG-IP ASM system, as well as which pool the traffic should use. To do this, select Application Security Disabled when configuring the profile.

Note: Application Security Disabled is the default configuration.

The fields used in the HTTP Class profile to specify the types of traffic that are passed to the BIG-IP ASM system are as follows:

  • Hosts
  • URI Paths
  • Headers
  • Cookies

These fields are logically connected with an AND statement. All fields are used for evaluating traffic. For each field, you must specify whether the traffic is either Match all or Match only.

By specifying that the field should Match all, the field will be removed from the evaluation, placing none in the profile definition of the configuration file.

Note: Match all is the default configuration.

To classify specific HTTP traffic you select Match only and define the parameters of what you would like to be considered a match. These parameters are configured in the form of strings that match a list type. The string that you can match to one of these lists can be either a pattern string or a regular expression. The list types are case-sensitive for pattern strings. For example, the system treats the pattern string www.f5.com differently from the pattern string www.F5.com. You can override this case-sensitivity by using the Linux regexp command. The list types that you can use for string matching are listed in the following table:

List typeString exampleRegex example
Hostswww.f5.com - If the hostname in the request matches www.f5.com, route HTTP traffic according to the settings in the profilewww[1-10].f5.com - If the hostname matches www1.f5.com - www10.f5.com, route HTTP traffic according to the settings in the profile

Once the BIG-IP system matches the string to the corresponding list type, if you have selected Application Security Enabled the system will send the traffic to the BIG-IP ASM module.

Common misconfigurations within the HTTP Class profile that you should verify:

  • Ensure Application Security is Enabled or Disabled as expected.
  • Verify the information specified in the HTTP Class profile configuration actually matches the HTTP Request being received. For example:
    • Verify that any case sensitive strings specified in the HTTP Class profile will match the case of the HTTP Request. Remember the case specified in the HTTP Request may differ from the actual objects if the OWS is not case sensitive.
    • Verify any regex expressions specified in the HTTP Class profile will match all of the desired variations of the HTTP Request you may receive. For more information, refer to K6562: BIG-IP ASM support for regular expressions.


The order in which the profiles are defined within the virtual server

When your configuration requires multiple HTTP Class Profiles, you also need to specify the order in which these profiles are used. Once an object matches a profile definition it will not be passed to subsequent profiles. Depending on your specific configuration, the order in which these profiles are applied can affect how traffic is passed to, or bypasses, the BIG-IP ASM system.

For example, if you had two profiles configured where a profile named BypassASM with Application Security Disabled was configured to match a URI Path of /web/images, and a profile named SendtoASM with Application Security Enabled was configured match traffic for Host www.f5.com. A request for http://www.f5.com/web/images/image1.jpg would be affected by how the profiles were ordered within the virtual server configuration.

If the virtual server was configured with the BypassASM profile first and the SendtoASM profile second, the request would match the URI Path of /web/images and bypass the BIG-IP ASM system.

If the virtual server was configured with the SendtoASM profile first and the BypassASM profile second, the request would match the Host of www.f5.com and be sent to the BIG-IP ASM system.

Note: This example is intended to illustrate how the ordering of profiles can affect whether or not traffic is sent to the BIG-IP ASM. The example is not meant to be used in a production environment, as using the HTTP Class to bypass the BIG-IP ASM may not be secure for some web applications. For a secure method of bypassing the BIG-IP ASM for static content, refer to K7616: Configuring static web content to bypass the BIG-IP ASM in BIG-IP version 9.x.

Successive HTTP requests that do not match HTTP class may bypass the BIG-IP ASM

Under some circumstances, once the BIG-IP system has made a load balancing decision after the first successful request that matches an HTTP class, the BIG-IP system will forward all subsequent requests on the same connection to the same pool member even if the requests do not meet the requirements of the assigned HTTP class profile. Such requests bypass the BIG-IP ASM system component. For more information, refer to K12268: Successive HTTP requests that do not match HTTP class may bypass the BIG-IP ASM.
