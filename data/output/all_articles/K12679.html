K12679: The gtmparse utility now updates the timestamp of the wideip.conf file before reloading the configuration from disk or UCS archive

Issue

Beginning with BIG-IP 10.1.0, when you run the gtmparse -l or gtmload command, the utility updates the timestamp of the wideip.conf file before reloading the configuration from disk and sending it to the Master Control Program Daemon (mcpd) process. Essentially, the utility now touches the wideip.conf file before continuing.

In previous BIG-IP versions, the timestamp of the wideip.conf file is not updated when you run either command.

Note: The gtmparse utility is used from the command line of the BIG-IP system to perform certain actions that relate to the BIG-IP GTM configuration. For example, when the utility is invoked with no options, it only verifies the syntax of the BIG-IP GTM configuration files; when the utility is invoked with the -l option, it reloads the BIG-IP GTM configuration from disk and then sends it to the mcpd process. Running the gtmload command is the equivalent of running the gtmparse -l command. For more information about this utility, refer to the output of the gtmparse -? command.

This change in behavior simplifies the intentional rollback of the BIG-IP GTM configuration. To understand this concept, refer to the following example scenario:

BIG-IP versions prior to 10.1.0

  • A number of BIG-IP GTM systems belong to the same synchronization group.
  • The BIG-IP GTM configuration is currently synchronized between all members of the group.
  • You decide to restore a user configuration set (UCS) archive on one of the systems to intentionally roll back the BIG-IP GTM configuration.
  • As part of the UCS restore procedure, the system runs the gtmparse -l command to reload the BIG-IP GTM configuration from disk.
  • After installing the UCS archive, the restored BIG-IP GTM configuration does not propagate to the other systems; instead, the other systems push their configuration to the system where the UCS archive was just restored. As a result, you fail to roll back the BIG-IP GTM configuration. This behavior occurs because the timestamp of the wideip.conf file on the other BIG-IP GTM systems is newer than the one of the wideip.conf file that was restored from the UCS archive.

BIG-IP 10.1.0 - 10.2.x

  • A number of BIG-IP GTM systems belong to the same synchronization group.
  • The BIG-IP GTM configuration is currently synchronized between all members of the group.
  • You decide to restore a UCS archive on one of the systems to intentionally roll back the BIG-IP GTM configuration.
  • As part of the UCS restore procedure, the system runs the gtmparse -l command, which first updates the timestamp of the wideip.conf file and then reloads the BIG-IP GTM configuration from disk.
  • After installing the UCS archive, the restored BIG-IP GTM configuration propagates to all members of the synchronization group.

F5 Product Development tracked this change in behavior as ID 206787 and ID 249316 (formerly CR118656).

Additional information/Impacts

Important: The new behavior discussed in this article should be desirable in most cases; however, it should always be taken into consideration when restoring UCS archives. For example, if you replace a BIG-IP GTM system under the Return Materials Authorization (RMA) process, and the only available UCS archive for the system is an old archive, and you are unsure whether the BIG-IP GTM configuration contained in that archive is up-to-date, you probably do not want that configuration to be immediately and automatically propagated to all other members in the synchronization group.

If you need to restore a UCS archive and you are unsure whether the archive contains the latest BIG-IP GTM configuration, you can perform one of the following two procedures to ensure that the BIG-IP GTM configuration included in the archive does not overwrite that of other BIG-IP GTM systems in the same synchronization group:

Temporarily modifying the UCS installer script

  1. Log in to the command line of the BIG-IP GTM system that requires restoring a UCS archive.
  2. Remount the /usr file system in read-write mode by typing the following command:

    mount -o remount,rw /usr

    Note: For information about why this step is needed, refer to K11302: The /usr filesystem is mounted in read-only mode.
  3. Use a text editor to open the /usr/local/bin/install_ucs.pm file.
  4. Locate the following section:

    sub action_big3d_gtmd_named
    {
    # for gtmd
    if (&install_full_config == 1 && &isMcpdUp == 1) {
    if (-e "/usr/sbin/gtmparse") {
    `/usr/sbin/gtmparse -l`;
    }
    }
  5. Add the -k option to the gtmparse command, as shown below:

    sub action_big3d_gtmd_named
    {
    # for gtmd
    if (&install_full_config == 1 && &isMcpdUp == 1) {
    if (-e "/usr/sbin/gtmparse") {
    `/usr/sbin/gtmparse -k -l`;
    }
    }

    Note: The -k option, also introduced in BIG-IP 10.1.0, causes the gtmparse utility to not touch the wideip.conf file.
  6. Save the file and exit the text editor.
  7. Restore the UCS archive.

    Note: For more information, refer to K11318: Backing up and restoring BIG-IP configuration files (10.x).
  8. Repeat steps 3 through 6, only this time, remove the -k option from the gtmparse command.
  9. Remount the /usr file system in read-only mode by typing the following command:

    mount -o remount,ro /usr

Once the BIG-IP GTM system has joined the synchronization group again, the other members should push the latest BIG-IP GTM configuration to it.

Using the gtm_add utility

Important: The following procedure requires that you temporarily disconnect the BIG-IP GTM system's TMM switch port interfaces from the production network, while leaving the management interface connected. The goal is to isolate the BIG-IP GTM system from the production network and restore the UCS file. This prevents the system from potentially synchronizing an older configuration to the GTM sync group.

  1. Physically disconnect the BIG-IP GTM system's TMM switch port interfaces from the network.
  2. Log in to the Configuration utility using the management interface.
  3. Restore the UCS archive.

    Note: For more information, refer to K11318: Backing up and restoring BIG-IP configuration files (10.x).
  4. Once the UCS archive is installed, navigate to System > Configuration > Global Traffic > General.
  5. Clear the Synchronization check box.
  6. Click Update.
  7. Reconnect the BIG-IP GTM system's TMM switch port interfaces to the network.
  8. Log in to the BIG-IP GTM command line.
  9. Add the BIG-IP GTM system to the GTM synchronization group by typing the following command:

    Note: The gtm_add script is interactive, and replaces the GTM configuration on the system on which it is run with the configuration of the remote BIG-IP GTM system in the specified sync group.

    gtm_add <IP address of a member of the target GTM synchronization group>
