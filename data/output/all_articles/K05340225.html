Known Issue

An iRule that sends Large Scale NAT (LSN) traffic to a multicast address causes the Traffic Management Microkernel (TMM) to restart and produce a core file.

This issue occurs when all of the following conditions are met:

  • The BIG-IP carrier-grade network address translation (CGNAT) module is licensed on your system.
  • A CGNAT virtual server is associated with an LSN pool.
  • The CGNAT virtual server includes an iRule that changes the destination IP address to a multicast address in the 224.0.0.0/24 network.

When the iRule changes the destination IP address of a connection to use a multicast address, such as 224.0.0.1, the BIG-IP system attempts to use an internal route. The internal route used for multicast traffic does not have a local interface; however, LSN expects to find an interface. As a result, TMM will restart and produce a core file when attempting to use the non-existent interface for LSN traffic.

Impact

The BIG-IP system may temporarily fail to process traffic as it recovers from the TMM restart, and devices configured as a high-availability pair may fail over.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • When processing LSN traffic for a CGNAT virtual server, the BIG-IP system generates a TMM core file to the /shared/core directory.
  • The BIG-IP system fails over to another system in the device group.
  • The BIG-IP system temporarily fails to process traffic while TMM restarts.

Workaround

To work around this issue, you can remove or modify the iRule to prevent the iRule from using the affected destination.

Impact of workaround: The impact of the suggested workaround will depend on the specific environment. F5 recommends testing any such changes during a maintenance window with consideration to the possible impact on your specific environment.
