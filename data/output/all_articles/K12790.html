Known Issue

Description

The Configuration utility and the checkcert utility are not compatible with SSL certificates that use Generalized Time as their date format. If you use either utility to examine such a certificate, the utility incorrectly reports that the certificate expired on December 31, 1969.

X.509 certificates can encode validity dates using either UTC Time or Generalized Time. RFC3280 states that, due to key differences between the two formats, Certificate Authorities (CAs) must always encode certificate validity dates through the year 2049 as UTC Time, and certificate validity dates in the year 2050, or later, as Generalized Time.

The issue described in this Solution was discovered in a customer environment where a self-signed certificate expiring before 2050 was incorrectly created using Generalized Time as its date format.

For more information, refer to RFC3280, especially to the following sections:

4.1.2.5 Validity
4.1.2.5.1 UTC Time
4.1.2.5.2 Generalized Time

Note: This link takes you to a resource outside of AskF5, and it is possible that the documents may be removed without our knowledge.

Impact

You can safely ignore this issue; there is no impact. OpenSSL properly recognizes the certificate, and SSL transactions using the certificate and key pair are successful.

Workaround

To work around this issue, you can use the openssl utility from the command line to display the expiration date of the certificate in question. For example, to display the expiration date of the certificate that is stored in the example.crt file, you would type the following command:

openssl x509 -in /config/ssl/ssl.crt/example.crt -noout -dates

The command output contains the correct expiration date and appears similar to the following example:

notBefore=May 20 00:00:00 2009 GMT
notAfter=May 20 00:00:00 2024 GMT
