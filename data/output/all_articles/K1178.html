K1178: Configuring an SSL proxy to rewrite URLs so that redirects from an HTTP server specify the HTTPS protocol

Topic

An SSL proxy is typically configured to accept HTTPS connections from a client, decrypt the SSL session, and then send the unencrypted HTTP request to the web server.

When a requested URI does not include a trailing slash, some web servers generate a courtesy redirect. Without a trailing slash, the web server will first treat the resource specified in the URI as a file. If the file cannot be found, the web server may search for a directory with the same name and, if found, send a 302 redirect back to the client with a trailing slash. The redirect will be returned to the client in HTTP mode rather than HTTPS, causing the SSL session to fail.

Following is an example of how an HTTP 302 redirect causes the SSL session to fail:

  • To request an SSL session, a user types https://www.f5.com/stuff without a trailing slash.
  • The client browser sends an SSL request to the SSL proxy which resides on the BIG-IP LTM system.
  • The BIG-IP system then decrypts the request and sends a GET /stuff command to the web server.
  • Because a file named /stuff does not exist on the web server, but there is a virtual directory named /stuff/, the web server sends a 302 redirect for the directory, but appends a trailing slash to the resource. When the web server sends the 302 redirect, it specifies HTTP, not HTTPS.
  • When the client receives the 302 redirect, it sends a new request to the BIG-IP SSL proxy, specifying HTTP, not HTTPS which causes the SSL connection to fail.

Note: This redirect issue is a known problem with IIS and all proxy software, including Microsoft Proxy Server. The workaround suggested by Microsoft is to verify the accuracy of the URL before sending the request.

Beginning with BIG-IP version 4.0, you can use the rewrite redirect feature to modify URLs that contain the wrong protocol. Beginning in BIG-IP version 4.2, you can use an F5 Networks-supplied ISAPI filter to prevent your IIS servers from issuing incompatible redirects. For more information about the ISAPI filter, refer to K1871: Using an ISAPI filter on Microsoft IIS to rewrite URLs so that it creates redirects that match the protocol and port used by the BIG-IP virtual server or SSL proxy.

BIG-IP version 4.2 through 4.6.4

In BIG-IP version 4.2 and later, you can set the redirect feature from the Configuration utility. To do so, perform the following procedure:

  1. Log in to the BIG-IP Configuration utility.
  2. Click the Proxy Advanced Properties tab.
  3. From the Rewrite Redirects drop-down menu, choose all or matching.

BIG-IP version 4.1.1

To rewrite any HTTP 301, 302, 303, 305, or 307 redirects to HTTPS in BIG-IP version 4.1.1, type the following command:

bigpipe proxy x.x.x.x:443 clientssl redirect rewrite all

To rewrite redirects only if the path and query URI components of the request and the redirect are identical (except for the trailing slash), type the following command:

bigpipe proxy x.x.x.x:443 clientssl redirect rewrite matching

BIG-IP version 4.0

In BIG-IP 4.0, setting the Common.Bipip.Proxy.RewriteRedirects bigdb key to 2 (two) causes proxyd to rewrite any HTTP 301, 302, 303, 305, or 307 redirects to HTTPS.

Setting the Common.Bigip.Proxy.RewriteRedirects bigdb key to 1 (one), or any other non-zero integer, is a more sophisticated setting that will only rewrite redirects if the path and query URI components are identical in the request and the redirect (except for the trailing slash).

Setting the Common.Bigip.Proxy.RewriteRedirects bigdb key to 1 (one) causes the BIG-IP system to remember the URL of the client request, and to rewrite the redirection only if the URL matches. Setting the key to 2 (two) causes the BIG-IP to rewrite the URL regardless of where the client is redirected.

Note: These settings will not negatively affect SSL proxy performance.
