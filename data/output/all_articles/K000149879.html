Description

Intermittently replies with TCP-RST to new TCP-SYN packets at the <span style="background-color: rgb(255, 255, 255); color: rgb(68, 68, 68);">IGW level.</span>

 

Environment

Aspen Mesh 1.14.6-am9

 

Cause

Inital base memory for IGW was 35MB and after 4910 clusters configured, we could see the memory increased to ~550MB, so more number of clusters impact the memory.

 

Everytime we see an isito-proxy to crash with OOMKilled, we can see on the access logs the clusters/listeners updating.

 

On regular pods, we don't see this behavior because you have the Sidecar config to isolate namespaces. But on the official sidecar documentation there is this note: " A Sidecar is not applicable to gateways, even though gateways are istio-proxies."

 

Recommended Actions

The Sidecar resource in istio to isolate the namespace is not applicable to gateways, because gw are different than normal sidecars and it should be aware of mesh level and that is in line with opensource. And this is not a bug.

 

Tthere is only one way to to avoid to learn external clusters information at the ingress(IGW) or egress(EGW) level, the configuration is the "exportTo" at the service level. Please check this official information about it: Configuration Scoping ExportTo

 

You need to add an annotation at each service to control their own service’s visibility.

 

For example the following configuration makes the app Service only visible to its own namespace(default), and the test namespace:

 

apiVersion: v1

kind: Service

metadata:

name: app

namespace: default

annotations:

networking.istio.io/exportTo: ".,test"

spec: ...

After applying it, other Ingress or Egress gateway outside the default and test namespaces, won't be able to learn the cluster info and will reduce the processing of the istio-proxy.
