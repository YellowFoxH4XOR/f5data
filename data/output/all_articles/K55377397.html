Description

A pool/ pool member configured to use both inband and active health monitors may flap between available and not available, even if the pool/ pool members are actually unavailable. If the inband monitor fails but the active monitor is still successful then you will see the pool member status flap between down and up. Logs similar to the ones below can be observed from /var/log/ltm.

14:10:03 mybigip1 notice mcpd[6649]: 01070638:5: Pool /Common/my_http_pool member /Common/192.0.2.1:80 monitor status down. [ /Common/inband: down, /Common/my_http_monitor: up; last error: /Common/http: No successful responses received before deadline. @2021/05/05 14:12:46.  ]  [ was up for 0hr:0min:28sec ]
14:10:04 mybigip1 notice mcpd[6649]: 01070727:5: Pool /Common/my_http_pool member /Common/192.0.2.1:80 monitor status up. [ /Common/inband: up, /Common/my_http_monitor: up ]  [ was down for 0hr:0min:1sec ]

Environment

  • BIG-IP pool/ pool members with both inband and active health monitors attached

ltm pool my_http_pool {
  members {
    192.0.2.1:http {
      address 192.0.2.1 session monitor-enabled state up
    }
  } monitor inband and my_http_monitor 
}

Cause

This is expected behavior. If the inband monitor fails but the active monitor is still successful then you will see the pool member status flap between UP and DOWN. When an inband monitor fails, any active monitors also assigned to the pool member will be immediately scheduled. Any successful response from an active monitor will immediately transition the inband monitor to an 'up' state.

Recommended Actions

Review monitoring requirements to understand if both inband, also known as passive monitoring, should be used in conjunction with active monitoring
