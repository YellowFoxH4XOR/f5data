Description

This article aims to help guide SSLO administrators when trying to determine the maximum number of SSLO topologies their SSLO deployment can support.

Environment

SSL Orchestrator

Cause

Technically there is no "maximum" number of topologies you can create on an SSLO box at the moment (as of 9.x), in that the SSLO GUI doesn't actively stop administrators from creating new topologies.

However, it is planned in future versions to have a warning after a certain number of topologies (possibly 90) are present, to warn admins that the management subsystem on the box may not be able to cope with so many config objects (aka "LTM objects").

The difficulty lies in predicting what exact number of topologies a certain hardware/software platform can cope with - this is a constantly changing limit since there are many different hardware platforms, and Virtual Editions (VEs) as well, which might not have the same level of performance, as well as newer versions of software typically having a larger management footprint, which means that newer software versions running on the same old hardware typically can handle a slightly fewer number of LTM objects before overwhelming the mgmt plane.

Internal testing at F5 suggests that most current hardware platforms will be overwhelmed on a management subsystem level after approximately 90 basic topologies - this limit is expected to be lower on VEs, depending on the type and capability of the CPUs given to the VE by the host hypervisor.

However, the above testing was done with very "basic" topologies - although it is impossible to set a "hard limit" on how many topologies it is safe to use given any particular customer environment, it is advisable to use caution when creating anything more than 20-30 topologies in any given deployment on a hardware chassis, and perhaps 15-20 on a VE.

Recommended Actions

This article recommends that most administrators deploy no more than 20-30 topologies on a hardware system, and perhaps 15-20 on a VE, for typical SSLO deployments.

Wherever possible, the reason why so many topologies are being deployed on the same box should be looked at, and a "tiered" approach should be used to re-use the same topology/topologies, perhaps using an irule to switch between clientssl profiles based on client source IP, or similar, in order to minimise having to create new topologies just to have a different clientssl profile applied to each, for example. F5 Professional Services can be engaged on this task if required, in order to analyse a customer's use-case and determine the best way to deploy it (eg. using irules etc to minimise extra topology creation).

Additional Information

The internal testing was done with many sys db options set on the box to large values, such as provision.extramb, provision.tomcat.extramb, provision.restjavad.extramb, and restjavad.useextramb set to true. As such, any SSLO admin intending to deploy more than 1 topology should already be familiar with these db variables, and if deploying more than 10 topologies should already have set them to large values - example: provision.extramb 2000, provision.restjavad.extramb 1600, provision.tomcat.extramb 500.
