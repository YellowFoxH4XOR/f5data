Known Issue

The Traffic Management Microkernel (TMM) process on a standby BIG-IP system may restart with an Assertion "valid pcb" failed message. 

This issue occurs when all of the following conditions are met:

  • You have a virtual server configured with HTTP caching enabled in a Web Acceleration profile.
  • The virtual server also has mirroring enabled.
  • The BIG-IP systems are configured in a failover device group with at least one device in standby mode.
  • The active BIG-IP system is unable to fulfill an incoming HTTP request, due to an invalid RAM Cache entry or no available pool members, and begins closing the connection.
  • The standby BIG-IP system still has a valid RAM Cache entry for the mirrored request.

When the active unit is unable to fulfill an incoming HTTP request, due to an invalid RAM Cache entry or no available pool members, a rare race condition may allow the standby unit to still have a valid RAM Cache entry for the mirrored request. As a result, TMM on the standby system may panic with an Assertion "valid pcb" failed message.

Impact

A standby BIG-IP system in the device group becomes temporarily unavailable as it recovers from the TMM restart.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The standby BIG-IP system may temporarily become unavailable, as it recovers from the TMM restart.
  • The standby BIG-IP system generates a TMM core file to the /shared/core directory.
  • The standby BIG-IP system logs an error message in the /var/log/tmm file that appears similar to the following example:

    panic: ../modules/hudfilter/tcp4/tcp4.c:1057: Assertion "valid pcb" failed.

Workaround

This is the result of a rare race condition and normally a workaround should not be required. However, if your specific environment causes this issue to be exposed more frequently than you can tolerate, you can work around this issue by either disabling connection mirroring or caching for the affected virtual servers.
