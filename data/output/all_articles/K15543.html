Known Issue

The BIG-IP APM system may fail to rewrite HTML forms correctly.

This issue occurs when all of the following conditions are met:

  • The BIG-IP system is configured with an access policy.
  • The access policy rewrite processes HTML forms.
  • The HTML form uses the base tag reference.

Impact

The POST of the HTML form data may not be submitted properly.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • Web content that depends on the HTML form POST data may not render correctly.
  • When the BIG-IP APM system reads the HTTP transaction, the system incorrectly rewrites the form content that it sends to the user.

    For example:

    Original form sent by the destination resource:

    <form name="Contact" method="post" action="/general/searchContacts.do?method=search">

    Rewritten form presented to the user:

    <form name="Contact" method="post" action="javascript:location=((window.F5_WrapURL)?window:parent).F5_WrapURL("/general/searchContacts.do?method=search","");">

  • When the system analyzes the HTTP transaction between the BIG-IP APM system and the destination server, the system sends the user's HTTP POST as an HTTP GET request.

Workaround

To work around this issue, you may be able to create and apply an iRule for the affected BIG-IP APM virtual server. To do so, perform the following procedure:

Impact of workaround: F5 recommends that you perform this procedure during a scheduled maintenance window. If possible, test the iRule in a staging environment to ensure effectiveness.

Note: The following iRule may not apply to all environments. F5 recommends that you author an iRule that works best for your application environment. Additionally, adding an iRule increases the resources that the associated virtual server uses. Depending on the type and volume of the connections, this processing may introduce noticeable latency. F5 recommends that you test any such changes in an appropriate environment.

Create an iRule to check for the affected path and prefix the base tag value to the path

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules.
  3. Click Create.
  4. In the new iRule text Name box, type a name for the iRule.

    For example:

    prefix_form_base_value

  5. In the Definition box, enter the following text, replacing <affected rewrite path> with the URL path affected by this issue.

    when HTTP_REQUEST {
    # Correct form path by adding <base> tag value to URL.
    set URL_Match 0
    if { "[HTTP::path]" contains "<affected rewrite path>" } {
    set URL_Match 1
    if { [HTTP::version] eq "1.1" } {
    if { [HTTP::header is_keepalive] } {
    HTTP::header replace "Connection" "Keep-Alive"
    }
    HTTP::version "1.0"
    }
    }
    }
    when HTTP_RESPONSE {
    if { $URL_Match == 1 } {
    if { [HTTP::header exists "Content-Length"] and [HTTP::header "Content-Length"] <= 1000000 } {
    HTTP::collect [HTTP::header Content-Length]
    } else {
    HTTP::collect 1000000
    }
    }
    }
    when HTTP_RESPONSE_DATA {
    if { $URL_Match == 1 } {
    regexp {base\s+href="([^"]+?//[^"]+?)(/[^"]+/)[^"]*"} [HTTP::payload] base_tag base_host base_path
    if { [info exists base_host] } {
    # if form.action starts with '/' extend it to full url
    # with host value from <base> tag
    set loc [string first "action=\"/" [HTTP::payload]]
    if { $loc >= 0 }{
    HTTP::payload replace [expr $loc + 8] 0 "$base_host"
    }
    }
    set URL_Match 0
    HTTP::release
    }
    }

  6. Click Finished.
  7. Navigate to Local Traffic > Virtual Servers.
  8. Click the name of the virtual server that is affected by this issue.
  9. Click the Resources tab.
  10. In the iRules section, click Manage.
  11. From the Available column, select the iRule you previously created.
  12. Click the << button to move the iRule to the Enabled column.
  13. Click Finished.
