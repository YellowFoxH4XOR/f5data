K000141128: Creating an SSL Proxy to the BIG-IP Management IP

Description

The BIG-IP Management IP is the entry point for several control-plane features, including the BIG-IP TMUI (GUI), the BIG-IP REST endpoint, the BIG-IP SOAP endpoint, as well as for setting up BIG-IP iControl.

It is front-ended by httpd, with TLS encryption which uses the BIG-IP Device certificate/key pair.

It listens on the management port, which bypasses tmm, and on the self-IP, which is tcp-proxied by tmm.


At times, we need to debug traffic to and from the management IP. However, simply capturing a wireshark pcap of the management traffic does not help us determine what is going on.



Environment

BIG-IP system with a management IP either configured on the management port or as a self-IP on an existing VLAN.


Cause

The default TLS protocol and ciphers configured for httpd do not include the protocols that can be decrypted by the SSL key since these algorithms are now disabled by default.



Recommended Actions

In order to debug and diagnose issues when management traffic is encrypted, we will need to deploy a man-in-the-middle proxy to front-end the management IP.


One way that does not require a third party external MITM device involves creating an SSL proxy to communicate via TLS from the client, and rerouting that traffic to the management IP at 127.0.0.1.



Configure the production BIG-IP itself to act as a man-in-the-middle SSL proxy for the management IP

 

Create a virtual server that has clientssl+serverssl to front-end BIG-IP's httpd on 127.0.0.1, which allows us to save the premaster secrets for wireshark decoding.

 

Step 1. In order to allow access to 127.0.0.1 for debugging, we need to allow loopback in irules, and disable IP impersonation detection.

 


## K05413010

# tmsh modify sys db tmm.tcl.rule.node.allow_loopback_addresses value true

## K13048

# tmsh modify sys httpd auth-pam-validate-ip off



Step 2. Create an irule that accesses 127.0.0.1 and saves SSL premaster secrets in the log file.


ltm rule /Common/_debug_httpd {

when CLIENT_ACCEPTED {

node 127.0.0.1 443

}

when CLIENTSSL_HANDSHAKE {

if { [IP::addr [getfield [IP::client_addr] "%" 1] equals 10.201.141.131] } {

log local0. "[TCP::client_port] :: RSA Session-ID:[SSL::sessionid] Master-Key:[SSL::sessionsecret]"

}

}


Step 3. Create a virtual server that references that irule. The virtual IP should be a new IP address different from the self-IP or management IP. Example, if your management IP is 10.10.10.9, then create another IP address or port on the virtual server:

 


ltm virtual /Common/mgmt_vs {

destination /Common/10.10.10.10:443

ip-protocol tcp

mask 255.255.255.255

profiles {

/Common/clientssl {

context clientside

}

/Common/f5-tcp-lan { }

/Common/http { }

/Common/serverssl {

context serverside

}

}

rules {

/Common/_debug_httpd

}

serverssl-use-sni disabled

source 0.0.0.0/0

source-address-translation {

type automap

}

translate-address enabled

translate-port enabled

}

 


Step 4. To collect decryptable data, run two tcpdumps simultaneously while reproducing any problems.

 


tcpdump -nns 0 -i 0.0:nnn port 443 -w /var/tmp/mgmt_clientside.pcap # this tcpdumps the clientside towards the client

 

tcpdump -nns 0 -i 0.0:h port 443 -w /var/tmp/mgmt_serverside.pcap # this tcpdumps to the serverside towards the linux host



Describe the behavior during the test, and collect the client output, the tcpdumps, and the qkview after the test.
