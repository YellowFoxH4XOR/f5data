K000136987: Brute Force not detected for EWS

2026-08-26

2026-08-26
Applies to

  • BIG-IP ASM

Description

BIG-IP ASM Brute Force Protection does not count some failed NTLM authentication attempts for Exchange Web Services (EWS). The issue occurs when the authentication server does not return a response after receiving the NTLM type-3 authentication message.

Environment

  • Product: BIG-IP ASM
  • Feature: Brute Force Protection
  • Authentication protocol: NTLM
  • Protected application: Microsoft Exchange Web Services
  • Example URL: /ews/exchange.asmx
  • Login page configuration: EWS URL wildcard, such as ews*
  • Protection types:
    • Source-based protection by IP address
    • Username-based protection with Access Validation criteria
  • Possible actions: Alarm, Alarm and Drop, or blocking

Cause

For NTLM authentication, ASM Brute Force Protection requires both of the following:

  1. An NTLM type-3 authentication message from the client.
  2. A subsequent response from the authentication server.

ASM evaluates the server response against the configured Access Validation criteria. If the server closes the connection or does not respond after the type-3 message, ASM does not count the request as a failed login attempt.

An HTTP 401 Unauthorized response received before the type-3 message does not satisfy this processing sequence. The behavior is expected for this NTLM transaction and does not indicate an ASM processing failure.

Recommended Actions

  1. Verify the complete NTLM exchange in a decrypted packet capture:
    • Confirm that the request contains an NTLM type-3 message.
    • Confirm that the authentication server sends a response after the type-3 message.
    • Verify that the response satisfies the configured Access Validation criteria.
  2. Compare working and non-working requests. Check for differences in:
    • HTTP method, such as GET versus POST
    • Request URL and path
    • NTLM message sequence
    • Ordering of 401 Unauthorized responses
    • Connection termination or FIN packets
    • Presence or absence of a response after the type-3 message
  3. Review the authentication server behavior for POST requests. The server should return an appropriate response after receiving the NTLM type-3 message instead of closing the connection.
  4. To test source-based protection, use a lower threshold, such as three failed attempts, and configure the action as Alarm and Blocking Page.
  5. Monitor ASM brute-force statistics during testing:

watch tmctl asm_brute_force_stats -w 200

  1. If the EWS application does not require POST, configure method enforcement for the applicable URL to disallow POST. Verify application functionality before applying this restriction because EWS may depend on POST requests.
  2. If POST must remain allowed, consider creating a custom attack signature that identifies the specific unauthorized request characteristics.
  3. If the issue persists, collect:
    • Output of watch tmctl asm_brute_force_stats -w 200
    • Decrypted packet capture
    • HAR file
    • ASM QKView data
  4. Review authentication-directory account-lockout thresholds separately. The directory service may lock an account before or independently of ASM Brute Force Protection.

Additional Information

  • ASM Brute Force Protection does not count every HTTP 401 Unauthorized response as a failed login attempt. The response must be associated with the NTLM type-3 authentication exchange.
  • A request without an Authorization header, or without a Proxy-Authorization header when a proxy is used, is not treated as an NTLM type-3 login attempt.
  • The configured URL wildcard can match both /ews/ and /EWS/; URL capitalization is not necessarily the cause.
  • When the expected response after the type-3 message is present and the Access Validation criteria are met, ASM can increment the failed-login counter and generate events such as:
    • Brute Force: Maximum login attempts are exceeded
    • Detected Failed Logins / Threshold
