Description

When using BIG-IP LTM as a reverse proxy (Standard VS with HTTP profile) for HTTP/HTTPS traffic, HTTP requests from the client may not be forwarded to the backend server if the server-side TCP connection has already been half-closed (i.e., the backend server has sent a FIN, ACK). In this situation, if a client sends a new HTTP request on a connection that has received a FIN from the server, BIG-IP will not forward this request to the backend server.

Environment

  • BIG-IP LTM
  • HTTP profile
  • RFC2616

Cause

This behavior is expected. When a backend server sends a [FIN, ACK] on its TCP connection, it indicates that it will not transmit further HTTP request on that connection. Although TCP allows for additional data to be sent by the peer until both sides have closed the connection, HTTP/1.1 (RFC 2616) expects clients and servers to monitor for closure events and avoid sending further requests after receiving a FIN. As a full proxy, BIG-IP does not forward new HTTP requests to servers that have already signaled intent to close via FIN because no response can be expected from such connections.

Recommended Actions

This is a client issue, here are some useful experiences for your reference:

  1. Ensure client applications properly detect half-closed connections and do not send new HTTP requests after receiving a FIN from the backend.
  2. Increase the HTTP keep-alive timeout on backend servers if persistent connections are required or if clients may remain idle between requests.
  3. If multiple client requests per connection are needed, consider attaching a OneConnect profile to your BIG-IP virtual server. OneConnect enables multiplexing of client requests over available pool member connections; however, once a pool member sends FIN, that specific connection cannot be reused.
  4. Review application logic and client configuration for compliance with TCP/HTTP standards regarding handling of closed or closing connections.

Key information from: RFC 2616: Hypertext Transfer Protocol -- HTTP/1.1 

   When a client or server wishes to time-out it SHOULD issue a graceful
   close on the transport connection. Clients and servers SHOULD both
   constantly watch for the other side of the transport close, and
   respond to it as appropriate. If a client or server does not detect
   the other side's close promptly it could cause unnecessary resource
   drain on the network.

   A client, server, or proxy MAY close the transport connection at any
   time. For example, a client might have started to send a new request
   at the same time that the server has decided to close the "idle"
   connection. From the server's point of view, the connection is being
   closed while it was idle, but from the client's point of view, a
   request is in progress.

   This means that clients, servers, and proxies MUST be able to recover
   from asynchronous close events. Client software SHOULD reopen the
   transport connection and retransmit the aborted sequence of requests
   without user interaction so long as the request sequence is
   idempotent (see section 9.1.2). Non-idempotent methods or sequences
   MUST NOT be automatically retried, although user agents MAY offer a
   human operator the choice of retrying the request(s). Confirmation by
   user-agent software with semantic understanding of the application
   MAY substitute for user confirmation. The automatic retry SHOULD NOT
   be repeated if the second sequence of requests fails.

Additional Information

The above behavior over HTTP needs to be distinguished with TCP behavior. As we all learnt that the server could keep accepting the following data after it sent the First-FIN packet. Here is a detailed explanation contrasting the behavior between TCP and HTTP protocols in the context of this article:

TCP Protocol Behavior:

  • Half-Closed Connections:
    In TCP, when one side (e.g., the server) sends a FIN to the other side (e.g., the client), it is signaling that it will not send any more data, but it is still able to receive data from the peer. This is known as a "half-closed" connection. The client can continue to send data to the server until it also sends a FIN, at which point the connection is fully closed.
  • Data Transmission:
    The TCP protocol itself does not restrict the client from sending more data after receiving a FIN from the server. The server's TCP stack will accept the data and acknowledge it at the transport layer, even though the application layer (such as an HTTP server) may not process it.

HTTP Protocol Behavior:

  • Connection Semantics:
    HTTP (specifically HTTP/1.1 as described in RFC 2616) is an application-layer protocol that typically runs over TCP. HTTP defines its own semantics for connection management, including the use of persistent connections (keep-alive) and the proper handling of connection closure.
  • Server-Initiated FIN:
    When an HTTP server sends a FIN (usually after a keep-alive timeout or after sending a response with a "Connection: close" header), it is indicating that it will not process any further HTTP requests on that connection. Any subsequent HTTP request sent by the client after receiving the server's FIN will not be processed by the server application, even though the underlying TCP stack may accept the data.
  • BIG-IP Behavior:
    As a full proxy, BIG-IP is aware of the HTTP protocol semantics. When the backend server has sent a FIN, BIG-IP knows that the server will not process any more HTTP requests on that connection. Therefore, if the client sends a new HTTP request after the server's FIN, BIG-IP will not forward this request to the backend server, as it would be futile—the server application will not respond.

Key Point:

  • In TCP, the protocol allows continued data flow from client to server after the server's FIN, until the client also sends a FIN.
  • In HTTP, the application protocol expects that no further requests will be sent after a FIN from the server. Any such requests are not processed, and proxies like BIG-IP will not forward them.
