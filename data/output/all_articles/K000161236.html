Description

When deploying F5 Distributed Cloud Customer Edge (CE) nodes in private data centers or on-premises environments, traditional Active/Standby high availability models using VRRP leave standby nodes idle and create operational complexity during maintenance. BGP combined with Equal-Cost Multi-Path (ECMP) routing provides an Active/Active topology that maximizes resource utilization, enables automatic failover, and allows individual CE nodes to be gracefully isolated for maintenance without service disruption.

Answer/Recommended Actions

Understanding BGP and ECMP for CE High Availability

Traditional VRRP-based CE deployments create an Active/Standby/Standby topology where only one node actively processes traffic at a time. BGP with ECMP fundamentally changes this by enabling all CE nodes to actively process traffic simultaneously:

  • Each CE node advertises the same VIP prefix (/32) via BGP to the upstream firewall/router.
  • The upstream device learns multiple equal-cost paths to the VIP and distributes traffic across all CE nodes using ECMP.
  • If a CE node becomes unavailable and stops advertising its BGP route, the upstream device automatically removes it from ECMP paths and redistributes traffic to the remaining nodes — with no manual intervention.

Understanding CE VIP Architecture

F5 Distributed Cloud CE nodes support two VIP types that integrate with BGP:

  • Global VIP:
    • Configured at the CE site level in the F5 Distributed Cloud Console.
    • Acts as the default listener VIP for all Load Balancers on the CE that do not have a dedicated VIP.
    • Advertised as a /32 prefix via BGP.
    • Important: The Global VIP is NOT added to the CE routing table and NOT advertised via BGP until at least one Load Balancer is deployed on the CE. Configuring a Global VIP without deploying a Load Balancer will result in no BGP advertisement.
  • Dedicated VIP (per Load Balancer):
    • Individual Load Balancers can be configured with their own dedicated VIP, separate from the Global VIP.
    • The Load Balancer responds only to its dedicated VIP and does not respond to the Global VIP.
    • Also advertised as a /32 prefix via BGP.
    • Multiple Load Balancers can have different dedicated VIPs on the same CE, enabling per-application routing policies.

BGP Filtering Best Practices

Proper BGP filtering is essential for security and operational stability. The recommended filtering strategy follows the principle of explicit allow, implicit deny:

DeviceDirectionPolicyPrefix Match
Firewall/RouterInbound (from CE)Accept VIP range only192.168.100.0/24 le 32
Firewall/RouterOutbound (to CE)Deny allN/A
CEOutbound (to Router)Advertise VIPs only192.168.100.0/24 le 32
CEInbound (from Router)Deny allN/A

Note on prefix matching: Since VIPs are advertised as /32 prefixes, the prefix filter must use le 32 (less than or equal to 32) to match the actual /32 routes while keeping the filter manageable with a /24 range. For example, a filter matching 192.168.100.0/24 le 32 will match all /32 VIP prefixes within that range (e.g., 192.168.100.10/32, 192.168.100.20/32, 192.168.100.30/32).

Graceful CE Isolation for Maintenance

One of the most powerful advantages of BGP-based CE deployments is the ability to gracefully isolate a CE node for maintenance without impacting application availability.

Isolation Process:

  1. Isolate the CE: Configure a BGP outbound export policy on the CE to stop advertising VIP prefixes. In the F5 Distributed Cloud Console, edit the BGP Peer object for the CE and change the outbound BGP routing policy from the policy that allows VIP prefixes to the policy that denies VIP prefixes. Within seconds (based on BGP timers), the upstream firewall/router removes the CE from its ECMP paths and traffic shifts to the remaining nodes.
  2. Perform Maintenance: With the CE isolated, safely reboot, upgrade OS, apply software updates, or perform troubleshooting. Existing long-lived connections to the isolated CE will eventually timeout; new connections are automatically directed to the remaining CEs.
  3. Reintroduce the CE: Remove or modify the BGP export filter to allow VIP advertisement again. The CE will begin advertising its /32 VIP routes, the upstream device adds the CE back to ECMP paths, and traffic automatically begins flowing to the restored CE.

Rolling Upgrade Strategy:

Step 1: Isolate CE1 → Upgrade CE1 → Put back CE1 in the data path
Step 2: Isolate CE2 → Upgrade CE2 → Put back CE2 in the data path

Throughout this process, at least one CE is always handling traffic and no service interruption occurs.

Recommended approach: Configure isolation on the CE side (outbound export policy in F5 Distributed Cloud Console) rather than on the upstream firewall/router side (inbound filter). This approach gives the CE team full autonomy without requiring coordination with the network team, provides a consistent interface regardless of upstream device vendor, and maintains a centralized audit trail in the F5 XC Console.

Additional Information

BGP peering between CE nodes and upstream devices uses eBGP (External BGP), with the CE nodes and the upstream firewall/router assigned different AS numbers. In a multi-node CE deployment, all CE nodes share the same AS number (e.g., AS 65002), which is standard practice when multiple nodes advertise the same VIP prefixes. The upstream firewall/router uses a separate AS number (e.g., AS 65001).

The CE nodes should never accept prefixes from the upstream firewall/router (inbound deny-all policy on CE). This prevents unintended route injection into the CE routing table and maintains clean separation between the CE routing domain and the upstream network.
