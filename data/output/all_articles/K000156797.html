Description

In some packet captures, when decrypted, a Hello Request will be seen. Why is it there and how can it apply to an F5...

55 443 192.168.0.1 192.168.1.1 10002 OUT s1/tmm6 : Hello Request TLSv1.2

Digging into the Packet Panel a view of the Transport Layer Security will show:

Transport Layer Security
    TLSv1.2 Record Layer: Handshake Protocol: Hello Request
        Content Type: Handshake (22)
        Version: TLS 1.2 (0x0303)
        Length: 28
        Handshake Protocol: Hello Request
            Handshake Type: Hello Request (0)
            Length: 0

Environment

  • This will most likely be something you review when investigating TLS mAuth or some kind of unexpected behavior that could cause a server to send a client the HelloRequest to  begin the negotiation process anew. 
  • Clientssl and Serverssl profiles.
  • Secure Renegotiation, Client Authentication

Cause

Per RFC5246 7.4.1.1. Hello Request 

  • The HelloRequest message MAY be sent by the server at any time.

  • HelloRequest is a simple notification that the client should begin the negotiation process anew. In response, the client should send a ClientHello message when convenient.
  • Since handshake messages are intended to have transmission precedence over application data, it is expected that the negotiation will begin before no more than a few records are received from the client.
  • If the server sends a HelloRequest but does not receive a ClientHello in response, it may close the connection with a fatal alert.

A BIG-IP may send a Hello Request when something in the SSL/TLS Handshake is not as expected. For instance...

If a Client Hello is missing the renegotiation_info extension the BIG-IP will mark it as False in the Server Hello by showing the length as '0'...

Extension: renegotiation_info (len=1)
    Type: renegotiation_info (65281)
    Length: 1
    Renegotiation Info extension
        Renegotiation info extension length: 0

The client can refuse to respond or resend the Client Hello. If it resends it and it now includes the renegotiation_info:

Extension: renegotiation_info (len=13)
    Type: renegotiation_info (65281)
    Length: 13
    Renegotiation Info extension
        Renegotiation info extension length: 12
        Renegotiation info: 5c34a81e4cb04c57f02fc820

The BIG-IP will now show it as True and continue with the TLS handshake...

Extension: renegotiation_info (len=25)
    Type: renegotiation_info (65281)
    Length: 25
    Renegotiation Info extension
        Renegotiation info extension length: 24
        Renegotiation info: 5c34a81e4cb04c57f02fc8200b424fc3fe5ac3321bfbd9f6

If it is does not respond properly the connection attempt will be reset.

Note: Per RFC 5746 3.5:

  • This text applies if the connection's "secure_renegotiation" flag is set to TRUE (if it is set to FALSE, see Section 4.2).
  • The client MUST include the "renegotiation_info" extension in the ClientHello, containing the saved client_verify_data.

Recommended Actions

When a review of a decrypted capture has a reset, and a Hello Request is being seen, determine where and when the reset happens.

  • If the client does not respond to the Hello Request with a new Client Hello the BIG-IP will reset the connection. Review the Client Hello for something that is missing or in error.
  • If the Client Hello is sent and the connection is completed then this may be investigated because it should not happen.
  • If the Client Hello persists in being incorrect that will result in a reset and will need to be investigated.
