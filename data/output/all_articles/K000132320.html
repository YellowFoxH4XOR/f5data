Topic

WebSocket is a network protocol, standardized by the IETF as RFC 6455, that provides bidirectional communication between a client and server for real-time applications, such as multi-player browser-based games and real-time feeds. Websocket is compatible with HTTP and works over HTTP ports 443 and 80, but it has lower overhead than HTTP as messages are exchanged over a single TCP connection. To achieve compatibility, the WebSocket handshake uses the HTTP Upgrade header to change from the HTTP protocol to the WebSocket protocol.

Description

HTTP Upgrade handshake

The initial HTTP Upgrade handshake request sent by the client uses the following HTTP headers:

  • Host header: specifies the host name of the server to which the request is being sent, plus an optional port number (when not using the default port).
  • Upgrade header: contains the websocket keyword.
  • Connection header: contains the Upgrade keyword.
  • WebSocket key header: provides information used by the server to prove that it received a valid WebSocket opening handshake.
  • Sec-WebSocket-Version header: includes the Websocket version.

The client's initial HTTP Upgrade request appears similar to the following example:

GET /chat HTTP/1.1
Host: example.com:80
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: YlPRr67GgertSF1265LPrt==
Sec-WebSocket-Version: 13

If the server accepts the connection, it replies with the following HTTP headers:

  • Upgrade header: contains the value websocket.
  • Connection header: contains the value Upgrade.
  • Sec-WebSocket-Accept header: the value of this header field is constructed by using the key from the client to obtain a 20-byte and base64-encoded string.

The server's response to the HTTP Upgrade request appears similar to the following example:

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: 6BlPLMBiTxaQ3XhGzzhZRbk+xOo=

Websocket data flow

After the WebSocket handshake is complete and the connection is in the open state, the client or the server may transmit data at any time until an endpoint sends a Close frame. For security reasons and to accommodate intermediary devices, such as proxies and load-balancers, the client masks all frames that it sends to the server. By default the BIG-IP system preserves the mask of the received packets unless a BIG-IP Advanced WAF / ASM security policy or iRule is associated with the virtual server. In this case the system unmasks the packet, parses the data, and then remasks the packet before sending it to the server.

Websocket profile

The Websocket profile is configured in the Configuration utility by navigating to Local Traffic > Profiles > Services > WebSocket. You can use the Websocket profile with or without a HTTP profile, depending on the requirements of your application. The following table contains the settings and definitions for the Websocket profile:

SettingDefaultDescription
NameNoneSpecifies the name of the profile.
Parent ProfilewebsocketSpecifies the name of the parent profile.
MaskingSelectiveSpecifies how WebSocket frames will be operated on. The Masking setting allows the following options:
  • Preserve: Preserves the mask of the packet received, and makes no change. All modules receive masked frames. Application Security Policy (ASM) enforces unmasked copy of frame without influence on main masked frame.
  • Unmask: Removes the mask from the packet and remasks it using the same mask when sending the traffic to the server.
  • Remask: Removes the mask received from the client. The system generates a new, random mask when sending the traffic to the server.
  • Selective: Preserves the mask of the packet received, and makes no changes unless ASM is associated with the virtual server, or the system executes an iRule command (WS::masking remask). If it does, all modules get unmasked frames and the system remasks it on the server side.
Compress ModePreservedSpecifies the mode that controls what compression operations are performed. The compress mode setting allows the following options:
  • Preserved: No compression or decompression operations are performed in this mode.
  • Typed: The compression parameter controls whether compression is negotiated with the endpoint. Compressed data received from the endpoint is decompressed thereby enabling security policies to take actions on cleartext data. Data maybe recompressed before being masked and sent on the wire.
CompressionEnabledSpecifies whether compression will be negotiated with the endpoint.
Maximum Window Size10Indicates the maximum sliding window for compression negotiated with the endpoint.
No DelayEnabledIndicates whether data should be buffered for efficient compression, or compressed without delay.
Payload Processing ModeEnd-To-EndIn 17.x and later, the payload processing mode setting allows the following options:
  • End-To-End: Websocket is enabled on client as well as server side connection.
  • Termination: Websocket connection gets terminated on the client side.
Payload Protocol ProfileNoneIn 17.x and later you can specify the payload protocol profile.

 

Recommendations

When you configure the BIG-IP system to load balance WebSocket traffic, you should consider the following factors:

  • When the virtual server is configured with a BIG-IP Advanced WAF / ASM security policy, packets are unmasked by default to allow the BIG-IP system to examine the WebSocket payload. The packets are then remasked when sending the traffic to the destination server. You can change the default behavior by adjusting the masking setting.
  • If your application requires WebSocket traffic load balancing, consider using a virtual server with an applicable TCP profile.
  • If your application requires HTTP inspection and WebSocket traffic load balancing, you can use a single virtual server with an HTTP profile. The HTTP filter detects the handshake response from the server that signals upgrading the connection to the WebSocket protocol and automatically enables bidirectional communication between the client and server using a single TCP connection.
  • If the BIG-IP system terminates encryption for WebSocket traffic secured with Transport Layer Security (TLS), you must configure the virtual server with an appropriate Client SSL profile.
