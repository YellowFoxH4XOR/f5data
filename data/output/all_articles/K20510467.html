Topic

You should consider using this procedure under the following condition:

  • You want to implement policy-based routing with an IP forwarding virtual server based on the source address using iRules.

Description

Policy-based routing (PBR) is a technique used to overwrite the default routing behavior by adding an additional layer of control. The incoming packets are routed, conditionally, based on the pre-defined criteria, instead of solely depending on the destination of the traffic. On a BIG-IP system, IP forwarding virtual servers are used to route traffic without address translation and leave the destination address in the packet unchanged. You can alter the routing decision on an IP forwarding virtual server by implementing PBR using iRules. The source address, which is one of the most commonly practiced PBR criteria, is used to build the iRule example in this article. 

You can use the following key commands to build the iRule:

  • The nexthop command routes packets to the given VLAN and IP address, with the following command syntax:

    nexthop <VLAN> <IP_address>

  • The IP::client_addr command returns the source IP address of the client.
  • The class match command searches the entries in a data group.

For example, the following iRule code shows that the traffic is forwarded to 10.10.0.1 on internal VLAN, when the client IP address is in the internal_IP data group:

if { [class match [IP::client_addr] equals internal_IP] } {
  nexthop internal 10.10.0.1
}

Prerequisites

You must meet the following prerequisites to use this procedure:

  • Have administrative access to the BIG-IP Configuration utility.
  • Have an IP forwarding virtual server configured on the BIG-IP system.

Procedures

  • Creating a data group containing a list of IP addresses or subnets
  • Creating an iRule to route the traffic based on the source addresses
  • Applying the PBR iRule to an IP forwarding virtual server

Creating a data group containing a list of IP addresses or subnets

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > iRules > Data Group List.
  3. Select Create.
  4. For Name, type a name for the data group.
  5. For Type, select Address.
  6. Under Records, for Address, type an appropriate IP address with mask bits and leave Value blank.

    For example, to include the network 10.10.10.0 with subnet mask 255.255.255.0 for Address, use the following format:

    10.10.10.0/24

  7. Select Add.
  8. Repeat steps 6 and 7 as needed to add more addresses in the data group.
  9. Select Finished.

Creating an iRule to route the traffic based on the source addresses

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > iRules > iRule List.
  3. Select Create.
  4. For Name, type a name for the iRule.
  5. For Definition, enter the PBR iRule.

    For example, the following iRule directs requests to the nexthop IP 10.10.0.1 on internal VLAN, when the client IP address has a match in the internal_IP data group:

    when CLIENT_ACCEPTED {
      if { [class match [IP::client_addr] equals internal_IP] } {
        nexthop internal 10.10.0.1
      }
    }

  6. Select Finished.

Applying the PBR iRule to an IP forwarding virtual server

Impact of procedure: The impact of the suggested procedure depends on the specific environment. F5 recommends that you test any such changes during a maintenance window and consider the possible impact on your specific environment.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Virtual Servers > Virtual Server List.
  3. Select the name of the IP forwarding virtual server to which you want to apply the iRule.
  4. Select the Resources tab.
  5. For iRules, select Manage.
  6. In the Available list, select the PBR iRule you previously configured, and move it to the Selected list.
  7. Select Finished.

Additional Information

You may need to enable loose initiation and loose close in Fastl4 profile of the IP forwarding virtual server because if BIG-IP needs to accept and forward asymmetric routing traffic, loose initiation needs to be enabled to accept and forward packets even if there is no 3WHS packets seen in BIG-IP.
