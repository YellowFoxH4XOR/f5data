K000163703: Why an Origin-Pool Health Check Can Succeed While an Observability HTTP Monitor Reports TLS Failure

Published

Description

An F5 Distributed Cloud origin-pool health check reports an origin as Healthy, but an Observability HTTP Monitor for the same origin reports:

remote error: tls: handshake failure

A curl test from another client may also return HTTP 200.

Environment

  • F5 Distributed Cloud
  • Feature: Observability HTTP Monitor
  • Protocol: HTTPS
  • Origin server uses TLS termination.
  • The origin may support only legacy TLS cipher suites or key-exchange methods.

Cause

The origin-pool health check and the Observability HTTP Monitor are separate services. They do not necessarily use the same TLS client behavior, cipher preferences, or configurable security settings.

The origin-pool health check can be configured with TLS security options such as Low. The Observability HTTP Monitor uses a stronger TLS client configuration and does not provide the same option to accept legacy cipher suites.

Consequently:

  • A pool health check may complete successfully using a more permissive TLS configuration.
  • The Observability HTTP Monitor may fail before the HTTP request is sent because it cannot negotiate a compatible TLS cipher suite.
  • A curl client may succeed because its supported protocols and cipher suites differ from those used by the Observability HTTP Monitor.

Answer/Recommended Actions

Use the monitoring method appropriate for the origin’s TLS configuration:

Option 1: Update the origin

Update the origin to support modern TLS configurations, including:

  • TLS 1.2 and/or TLS 1.3.
  • Modern cipher suites.
  • Cipher suites providing Forward Secrecy.
  • Correct SNI handling.
  • A valid certificate with a complete certificate chain.

Then retest the Observability HTTP Monitor.

Option 2: Continue using the pool health check

If the origin must retain its legacy TLS configuration, continue using the origin-pool health check for availability monitoring.

This is a supported workaround when the pool health check reports the origin as Healthy but the Observability HTTP Monitor cannot establish a compatible TLS session.

Additional Information

  • A successful HTTP 200 response from curl does not prove compatibility with every TLS client.
  • An HTTP Host header is processed after TLS negotiation and cannot resolve a TLS handshake failure.
  • SNI may be required when multiple certificates or virtual hosts are configured on the origin.
  • Certificate validation, hostname matching, and the complete certificate chain should still be checked even when certificate verification is temporarily disabled for testing.
