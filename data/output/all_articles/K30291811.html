Description

This article applies to a scenario in which you are using other methods or tools to automatically create BIG-IP UCS backup files and want to restore the previously-created UCS archive file on your desired BIG-IP device or even restore the UCS archive file after resetting the device to factory default.

For example, you may have a cron job running regularly on your BIG-IP that creates UCS archive files from the latest configuration and you want to verify that the UCS archive files can be successfully restored. The main goal of this article is providing a simple step-by-step guide to restore these previously-created UCS files with the minimum risks.

This article expands on K13132: Backing up and restoring BIG-IP configuration files with a UCS archive by describing the UCS upload step. Refer to K13132 for more information about restoring UCS archives.

Note: Creating a cron job for automatically creating UCS archive files is covered in K13418: Archiving UCS files using the logrotate and crontab utilities.
 

Environment

You must meet the following prerequisite to use this procedure:

  • You have access to the Configuration Utility of BIG-IP.
  • You have Administrator privileges to make changes.
  • There is a cron job on your BIG-IP device or you use any other external tools such as Ansible which can create the UCS archive file automatically.
  • You may need to reset the BIG-IP to factory default state.

Cause

None

Recommended Actions

Restoring previously-created UCS archive files on BIG-IP devices without resetting to factory default:

Below are the steps for the UCS archive file restoration process, in devices which there is no need to reset to factory default state:

  1. Connect to the BIG-IP via console or via an SSH session. In case you have more than one BIG-IP in high-availability mode, make sure you are logged in to the standby device and there is NO traffic flow on this device.

    Note: If you are using Non-preemptive HA-mode like Load-aware with same Load Factor value, or HA-Order without Auto-failback option enabled, the standby device will remain in its standby-mode again after the UCS restoration is completed without affecting the active unit.
     
  2. Make sure all devices in the device-group are in sync with each other and there is NO configuration difference on them.
     
  3. Let the cron job or other external tool create the UCS archive file and copy it to your external storage.
     
  4. Before verifying your automatically created UCS archives, F5 recommends manually creating your own UCS from the GUI (System > Archives > Create...), and save a copy to your external storage with a different File Name.

     Note: The reason for this step is so you have another (redundant) UCS file created manually in case the UCS file you want verify fails to restore properly.

    Important: Also, make sure that the file size of both manually and automatically created UCS files are nearly the same. If the file size is NOT the same, it means that one of these UCS files was NOT created correctly, and you should not proceed further.
     
  5. Upload the automatically created UCS file by navigating to System > Archives > Upload...

    Note: Make sure that you are uploading the UCS file which has been created on the same device, with the same BIG-IP version, and with the same license, and same Resource Provisioning.

    Important: In case you are restoring the UCS Archive file on another device with a separate license, but with same BIG-IP version and Resource Provisioning state, you need to use the tmsh load /sys ucs <path/to/UCS> no-license command. Refer to the previously mentioned UCS restore article, K13132 for more information.
    Important: Do NOT use the UCS file of one device to restore the configuration on a different device.
     
  6. Select the File Name you just uploaded.
     
  7. If the UCS file is encrypted, enter the passphrase for the encrypted UCS file for restore Passphrase. Otherwise, you can skip this step.
     
  8. Select Restore and wait about a minute for the configuration to load completely on your device.

    Note: Choose (enable) the checkbox for Overwrite existing archive file, if the UCS file with the same name exists in the Archive List on your device; however; if you choose the previously-created UCS file on your Archive List and did NOT upload that UCS, you can skip this action.
     
  9. If after the restoration process, there are NO errors and all the expected objects have loaded, it means that the UCS restore was successful. For verification, you can change the HA role of this standby unit to active and then test your traffic flow.

    Note: The UCS archive file includes the device's license information. As a result, UCS file restoration also restores the license from the UCS.
     
  10. If you encounter any errors in step 8 or step 9, you can do the same process as mentioned on step 5, but instead choose the UCS file you created manually in step 4, and complete steps 6 through 9.



Restoring previously-created UCS archive files on BIG-IP devices after resetting to factory default:

Below is the complete step-by-step guide for another scenario in which you reset the device to the factory default state first, and then restore the UCS archive file you want to use:

  1. Connect to the Device via console or an SSH session. If you have more than one BIG-IP in High-availability mode, make sure you are logged in to the standby device and there is NO traffic flow on this device.
     
  2. To restore the configuration of the device to factory default, use the below command from K13127: Restoring the BIG-IP configuration to factory default settings. 
    Impact: This procedure removes all BIG-IP local traffic objects, network configuration, and BIG-IP module data (exceptions: device license, MGMT IP address, ALL files in /shared, manually-modified BigDB database variables).

    tmsh load /sys config default

    Note: After resetting device to factory default, you may not be able to access the device with the default admin/admin or root/default credentials. In case you encounter this issue, you can follow the procedures in the following articles otherwise you can continue with step 3:

    K18040601: Re-enable the root account from single user mode
    K35811337: Recover the root password on non-RAID BIG-IP platforms (BIG-IP 14.1.0 and later)
     
  3. Save the configuration change by typing the following command:
    tmsh save /sys config partitions all
     
  4. Complete the initial configurations (including Resource Provisioning, and other related configurations through the Wizard)

    Note: Before going to the next step make sure that the BIG-IP version, the Resource Provisioning configuration, and the device itself are as same as the device you created the UCS archive file on.
     
  5. Upload the automatically created UCS file or any manually created files by navigating to System > Archives > Upload...

    Important: In case you are restoring the UCS archive file on another device with a separate license, but with same BIG-IP version and Resource Provisioning state, you need to use the tmsh load /sys ucs <path/to/ucs> no-license command. Refer to the previously mentioned UCS restore article, K13132 for more information.
    Important: Do NOT use the UCS file of one device to restore the configuration on a different device.
     
  6. Select the file you just uploaded.
     
  7. If the UCS file is encrypted, enter the passphrase for the encrypted UCS file for restore Passphrase. Otherwise, you can skip this step.
     
  8. Select Restore, and wait about a minute for the configuration to completely load on your Device.

    Note: Choose (enable) the checkbox for Overwrite existing archive file, if the UCS file with the same name exists in the Archive List on your device; however, if you choose a previously-created UCS file in your Archive List and did not upload that UCS, you can skip this action.
     
  9. If after the restoration process, there are NO errors and all the expected objects have loaded, it means that the UCS restore was successful. For verification, you can change the HA role of this standby unit to active and then test your traffic flow.
     
  10. If you encounter any errors in step 8 or step 9, you can do the same process as mentioned on step 5, but instead choose a different UCS file you created, and complete steps 6 through 9.
