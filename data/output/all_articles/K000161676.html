K000161676: BIG-IP Upgrade Fails Silently: Configuration Objects Missing from GUI After Upgrade Due to Duplicate Client-SSL Profile SNI Conflict

Type
Support Solution
Published
2026-06-12
Updated
2026-06-12
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.3, 17.1.2
Source
https://my.f5.com/manage/s/article/K000161676

Description

After upgrading a BIG-IP system, the device may appear to upgrade successfully with no errors reported, yet configuration objects (virtual servers, profiles, etc.) are missing or not visible in the GUI. The device may also fail to pick up profiles as expected and may be placed into a "Forced Offline" state.

Notably, running "tmsh load sys config verify" before the upgrade returns only warnings (no errors), giving a false sense of configuration validity. The underlying configuration error is only exposed during a full configuration load (e.g., post-upgrade boot), resulting in the following error:

0107149e:3: Virtual server has more than one clientssl/serverssl profile with same server name

Environment

  • Product: BIG-IP LTM
  • Versions affected: 17.1.2.2 (pre-upgrade); 17.1.3.2 (post-upgrade)
  • Configuration condition: One or more virtual servers with two Client-SSL profiles attached, where both profiles have a blank/empty server-name field
  • Upgrade method: New software installed to a newly created boot location volume

Cause

The root cause is an invalid configuration where two Client-SSL profiles attached to the same virtual server both have a blank server-name field. This creates a duplicate/default SNI conflict that BIG-IP cannot resolve during a full configuration load. The reason this is not caught pre-upgrade could be related and similar to the Bug ID 1825241.

Answer/Recommended Actions

Pre-Upgrade Fix (Required — perform under a maintenance window before the upgrade):

1. Identify all virtual servers with multiple Client-SSL profiles where more than one profile has a blank or identical server-name field.

2. Back up the relevant partition configuration file before making changes:

# cd /config/partitions/<partition_name>/
# cp bigip.conf bigip.conf.backup

3. Edit the configuration file to add a unique server-name value to the conflicting SSL profile. For example:

ltm profile client-ssl /<partition_name>/<profile_name> {
    ...
    server-name *.example.com    <----------------- ADD THIS LINE
}

Then, use vi to edit the file:

# vi /config/partitions/<partition_name>/bigip.conf

4. Validate the configuration to confirm no errors:

# tmsh load sys config partitions all verify

5. Reload the configuration and confirm no errors:

# tmsh load sys config partitions all

6. Save the configuration and generate a fresh UCS backup:

# tmsh save sys config partitions all
# tmsh save sys ucs <filename>.ucs

 

Upgrade Best Practices (after the fix is applied):
1. Re-run tmsh load sys config verify on both units after the fix to confirm no errors remain.
2. Generate a fresh UCS backup from both devices immediately before the upgrade.
3. Disable Automatic ConfigSync — set ConfigSync to Manual on both units during the upgrade window.
4. Place the Standby device in "Force Offline" mode before booting into the new software volume to prevent unexpected active role takeover.
5. Upgrade the Standby device first; validate all objects are visible in the GUI before proceeding.
6. Once the Standby is confirmed healthy, perform a controlled failover and upgrade the Primary device.
7. After confirming the upgrade is successful, release the device from "Force Offline" mode.

If objects are missing post-upgrade (recovery):
Roll back to the previous working boot location to restore the configuration and HA relationship while the root cause is addressed.

Additional Information

  • "tmsh load sys config verify" does not fully replicate the commit/write path used during a real configuration load. Certain validators — including the SNI conflict check — are only invoked during a full load config or system boot. This is a known limitation documented in another similar Bug ID 1825241.
  • Although the conflicting SSL profiles may belong to a single partition, the config load failure can result in objects across all partitions being invisible in the GUI on the affected device.
  • When a client connects via HTTPS and sends an SNI hostname, BIG-IP selects the matching Client-SSL profile. If no SNI matches or the SNI is empty, BIG-IP falls back to the default SNI profile. When two profiles both claim the same (blank) server-name, BIG-IP cannot distinguish between them, causing the conflict.
  • Virtual servers with only one Client-SSL profile do not require a server-name to be set, as there is no ambiguity.
  • Virtual servers without any SSL profile (e.g., non-HTTPS services) are not affected by this issue.
