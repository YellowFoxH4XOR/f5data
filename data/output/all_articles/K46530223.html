Known Issue

In rare instances, a health monitor may remain in the checking status indefinitely.

This issue has been observed when all of the following conditions are met:

  • You are using a TCP, HTTP, or HTTPS health monitor.
  • The bigd process performs health monitoring on pool members that are unavailable.

A failed monitor health check, among other undetermined conditions, may trigger this issue. The bigd process inadvertently skips processing monitor timeouts. As a result, the monitors display the incorrect status.

Impact

The health monitor fails to mark an unavailable pool member down upon reaching the monitor timeout value.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The health monitor fails to mark an unavailable pool member down upon reaching the monitor timeout value.
  • The bigd process attempts to monitor the affected pool members, even after reaching the timeout value.
  • The status of the affected pool members appears similar to the following example:

    Status
      |   Availability   : unknown
      |   State          : enabled
      |   Reason         :
      |   Monitor Status : checking
      |   Session Status : enabled
      |   Pool Name      : test_pool
      |   IP Address     : 192.168.100.100

  • If you enable debug logging for the affected monitor, multiple log entries in the /var/log/bigdlog file appear similar to the following example:

    2016-09-13 00:15:12.205020: ID 3224  :(_do_ping): time to ping, now=[1473740112.204838][2016-09-13 00:15:12], status=UNKNOWN [ addr=<IP_Address> mon=/Common/tcp fd=-1 pend=0 #conn=0 up_intvl=5 dn_intvl=5 timeout=16 time_until_up=0 immed=0 next_ping=[1473740112.119613][2016-09-13 00:15:12] last_ping=[1473740107.133227][2016-09-13 00:15:07] deadline=[1473739960.942539][2016-09-13 00:12:40] on_service_list=True snd_cnt=34 rcv_cnt=0 ]

    In the previous example, the monitor process status is unknown, although the timestamp of the current activity represented by the now field (00:15:12) is past the monitor timeout represented by the deadline field (00:12:40). This message indicates that the bigd process failed to mark the pool member down when the monitor timeout was reached.
