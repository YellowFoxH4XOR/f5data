Topic

This article discusses the behavior of the diameter virtual server when it receives a Capabilities Exchange Answer (CEA) response with an unsuccessful Result-Code Attribute Value Pair (AVP).

Description

In a typical diameter session setup, after the system establishes the underlying transport layer, the diameter client sends a Capabilities Exchange Request (CER) message to the diameter server. The diameter server then responds with a CEA message that contains a 2001 (DIAMETER_SUCCESS) Result-Code AVP so that the system can establish a diameter session between the client and the server.

In some situations, the diameter server may respond with a CEA message that contains an unsuccessful Result-Code AVP to indicate a protocol error, a transient failure, or a permanent failure. For example, 3001 (DIAMETER_COMMAND_UNSUPPORTED) indicates a protocol error while 5001 (DIAMETER_AVP_UNSUPPORTED) indicates a permanent failure. Depending on the specific type of error or failure, the diameter client can retry at a later time, terminate the diameter session by the diameter server, or use an intermediate diameter agent to rectify the error described in RFC6733.

As a diameter agent, the diameter virtual server forwards the first CEA response from the server to the client regardless of the Result-Code AVP. This behavior allows the diameter client to decide its next course of action. For subsequent CEA responses with a Result-Code AVP that indicates permanent failure (5000 and above) from the server, the diameter virtual server resets the underlying transport layer connection. For subsequent CEA responses with all other Result-Code AVPs, the diameter virtual server forwards the CEA response to the client for the client to decide the next course of action.

Recommendations

When you configure the diameter virtual server, you should consider the following factor:

  • You may be able to use diameter iRules commands, such as DIAMETER::avp, and events, such as DIAMETER_INGRESS, to detect an unsuccessful Result-Code AVP in a CEA response and then perform a specific action.

    Note: Prior to BIG-IP 11.3.0 HF3, the diameter iRule events DIAMETER_INGRESS and DIAMETER_EGRESS can be triggered only after the CER/CEA messages are successfully completed; you may need to use other underlying protocol commands and events such as TCP::collect and SERVER_DATA instead. In BIG-IP 11.3.0 HF3 and later versions, these events can be triggered during the exchange of CER/CEA messages.
