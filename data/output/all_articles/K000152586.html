Description

Enabling the HTTP profile on a BIG-IP LTM virtual server that handles both HTTP and Citrix ICA (Independent Computing Architecture) traffic can cause Citrix VDI (Virtual Desktop Infrastructure) connections to fail. This is because Citrix ICA traffic is not HTTP-based, and the HTTP profile interferes with its processing. Users can access the Citrix portal and download ICA files with the HTTP profile enabled, but VDI connections initiated via ICA fail unless the HTTP profile is removed. The issue can be resolved by dynamically enabling or disabling the HTTP profile based on the detected protocol within the TLS session.

Environment

  • Virtual server
  • Client SSL profile
  • HTTP profile

Cause

Citrix ICA traffic is not HTTP over TLS. When the HTTP profile is always enabled, the BIG-IP system attempts to parse ICA traffic as HTTP, resulting in failed VDI connections. Disabling the HTTP profile for non-HTTP traffic (such as ICA) is necessary to allow proper Citrix VDI operation.

Recommended Actions

  1. Create the iRule to enable HTTP profile dynamically. The example iRule:
when CLIENTSSL_HANDSHAKE {
    SSL::collect 4
    HTTP::disable
}
when CLIENTSSL_DATA {
    if { ([SSL::payload 4] equals "GET ") or ([SSL::payload 4] equals "POST") or ([SSL::payload 4] equals "HEAD") or ([SSL::payload 4] equals "PUT ") or ([SSL::payload 4] equals "DELE") or ([SSL::payload 4] equals "PATC") or ([SSL::payload 4] equals "OPTI") or ([SSL::payload 4] equals "TRAC") or ([SSL::payload 4] equals "CONN") } {
        HTTP::enable
    } else {
        HTTP::disable
    }
    SSL::release
}
  1. Follow the article below, apply the iRule to the virtual server. 

K50565834: How to add an iRule to a virtual server

Additional Information

In the TCP connection for the VDI, the client will send 4 bytes to the server, then waiting for the response. The decrypted data is:

00000000 05 02 00 80 ....

So the workaround is, collect the TLS data, check the 4 bytes, and enable the HTTP profile if match the correct HTTP method.
