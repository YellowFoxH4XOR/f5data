K000160280: ATSE Datapath Lockup Due to HBM2 DRAM Calibration Failure on F5 rSeries Platforms (Bug ID 1783685)

Type
Support Solution
Published
2026-03-09
Updated
2026-06-29
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000160280

Description

F5 rSeries appliances running F5OS-A 1.8.3 may become unresponsive and stop processing all network traffic. The issue is characterized by LACP interfaces remaining down and repeated log messages such as:

  • dma-agent[13]: priority="Alert" ... msg="Health monitor detected DM Tx Action Completion ring hung."
  • dma-agent[13]: priority="Info" ... msg="Health monitor DM register dump complete." FILE="agent-dump-<...>.txt"

During the incident, Data Mover CPUs may show 100% utilization, and core dump files are generated. A device reboot temporarily restores service.

Environment

  • Software: F5OS-A 1.8.3
  • Hardware: ATSE FPGA with HBM2 DRAM
  • Features: LACP trunk interfaces, hardware datapath acceleration
  • Multiple tenants may be running on the affected appliance

Cause

Bug ID 1783685: ATSE Datapath lockup on HBM calibration issue

The root cause is a hardware datapath lockup caused by an HBM2 DRAM calibration failure within the ATSE FPGA. The internal FPGA HBM DRAM reset sequence did not meet the Altera specification, resulting in instability of the HBM DRAM interface at startup and during runtime.

Answer/Recommended Actions

  1. Apply Engineering Hotfix (EHF):
    • An EHF is available that resolves Bug ID 1783685.
    • This EHF is applicable to all r5000, r10000, and r12000 series platforms running F5OS-A 1.8.3.
  2. Immediate Workaround:
    • Reboot the appliance to clear the datapath lockup and restore service (temporary workaround).
  3. Monitor and Update:
    • Monitor for further ATSE datapath lockup events.
    • Plan to update to future F5OS releases (e.g., F5OS-A 1.8.4) that contain the permanent fix.
  4. Technical Validation:
    • Confirm the issue by reviewing logs for "DM Tx Action Completion ring hung" messages.
    • Analyze agent-dump files and FPGA debug logs (e.g., fpgatoolFpgaAtseSnapshot.sh, fpgatoolFpgaDataMoverSnapshot.sh) for evidence of RQM (FPGA receive queue) blocking and HBM DRAM interface errors.
    • Compare FPGA register values (e.g., 0x20880, 0x208A0, 0x208C8) against expected calibration values to confirm HBM calibration failure.

Additional Information

Technical Details:

The logs that confirm the datapath lockup are found in the FPGA debug logs within the qkview:

  • system_fpga - /etc/qkview-collect/fpgatoolFpgaAtseSnapshot.sh
  • system_fpga - /etc/qkview-collect/fpgatoolFpgaDataMoverSnapshot.sh

These logs show that RQM (the FPGA receive queue) is blocking traffic from the network, with DMA rings downstream of the RQM queues all empty.

HBM/DRAM Impact Evidence:

The FPGA receive queue is built from the HBM DRAM. The internal FPGA datapath debug shows a DRAM interface issue where the DRAM is not accepting writes on the input side and showing empty on the output side. This is a typical signature of HBM calibration failure.

DRAM Calibration Parameters:

The DRAM interface specification was provided by Intel. The issue was in the wmcrst_n_in logic, which was not controlled in a way that prevented it from asserting until after completion of calibration. There was a race condition between wmcrst_n_in and ninit_done signals.

Expected FPGA register values (healthy system):

0x00020880: 0x001111FF

0x000208A0: 0x000111FF

0x000208C8: 0x00000000

Failed calibration register values:

0x00020880: 0x00100000

0x000208A0: 0x00000000

0x000208C8: 0x00000001

The issue is resolved in ATSE bitfile v72.5.11.0 and will be included in F5OS-A 1.8.4 and later releases.
