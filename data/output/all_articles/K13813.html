Known Issue

Health monitors that you created using iApp may not work as expected after you disable the Strict Updates feature on the Application Service's Advanced properties page.

This issue occurs when all of the following conditions are met:

  • You used an iApp Application Service template that includes a health monitor to create the configuration.
  • The health monitor requires a query-response action between the BIG-IP system and the resource pool.

    Note: A query-response action is the data sent to the pool member and the expected response, and is defined in the Monitor Question section of the iApp template. An example of a query-response action would be an HTTP send-receive string, or a DNS query and IP address response.

  • You disabled Strict Updates on the Advanced Application Services Properties page.

The Strict Updates setting indicates whether the application service is tied to the template, so when the template is updated, the application service changes to reflect the updates.

Impact

This issue may cause the system to mark the pool resources with the incorrect state.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • The packet captures on the health monitor between the BIG-IP system and the pool member may show that the BIG-IP system improperly closed the network connection right after transmitting the SYN and SYN-ACK packets.
  • The resource pool may not receive a proper query string from the BIG-IP system's health monitor.
  • On version 11.0.0, the health monitor on the resource pool may incorrectly end up in a returned state and cause the iApp virtual server to be unavailable, because the iApp virtual server has no resources. The pool members will fail the health monitor evaluation because the BIG-IP system did not send the query string, and the pool members were unable to send a response to the BIG-IP system, hence the monitor gives a returned state indicating that the resource is unavailable.
  • On version 11.1.0, the health monitor may mark that same resource as available as long as the pool member's service port is valid. Hence, a pool member that is supposed to be unavailable will be falsely marked as available. You may also observe that the BIG-IP system did not send the query string to the pool member when you enabled debug mode on bigd.

Workaround

To work around this issue, you can replace the health monitor you created using iApp by creating a new health monitor using tmsh. To do so, perform the following procedure:

Impact of workaround: When you attempt to delete the iApp application service in the future, the system will not automatically delete the new monitor that you created as a workaround, which you placed in the iApp application services folder. Hence, you are required to manually unallocate the monitor from the iApp pool and delete the monitor manually, and then proceed to delete the iApp application service.

  1. Log in to the Traffic Management Shell (tmsh) by entering the following command:

    tmsh

    Note: If you are currently logged in to the tmsh shell, you can skip this step.

  2. Go to the iApp Application Services folder using the following command syntax:

    cd <iApp-Name>

    For example, to change the folder path to the iApp named eg_iapp, use the following command:

    cd eg_iapp

    Note: The health monitor created by iApp will be configured to reside in the partition path of the iApp name in the following format: /Common/<iApp-Name>.app

  3. Create a new health monitor with the required monitor type and parameters for the iApp, using the following command syntax:

    create /<Product-Module> monitor <Monitor-Type> <Monitor-Name> { defaults-from <Monitor-Name-To-Default-From> <Monitor-Parameters-Settings> }

    For example, to create an LTM health monitor, of HTTP type, with the name eg_http, using the send string "GET /\\r\\n", the receive string "Host", an interval of 30 seconds, and a timeout of 45 seconds, use the following command:

    create /ltm monitor http eg_http { defaults-from http recv "Host" interval 30 send "GET /\\r\\n" timeout 45 }

  4. Modify the iApp pool to use the new monitor eg_http that you created in Step 3, using the following command syntax:

    modify /ltm pool <iApp-Pool-Name> monitor eg_http

    For example, to modify the pool named eg_iapp_eg_pool to use the new monitor eg_http, use the following command:

    modify /ltm pool eg_iapp_eg_pool monitor eg_http

    Note: Resource pools created from iApp will have the pool name with the iApp name prefix.

  5. Save the change by typing the following command:

    save sys config

  6. To exit the tmsh utility, type the following command:

    quit
