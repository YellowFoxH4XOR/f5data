Description

  • How do I modify the domain flag missing in the cookie header?
  • What can I do to add cookie protection to a specific cookie?
  • The HTTP response from the web server contains one or more set-cookie HTTP headers

Environment

  • F5® Distributed Cloud Web Application Firewall 
  • F5 HTTP Load Balancer

Answer/Recommended Actions

  1. Select the namespace you wish to modify 
     
  2. Visit Manage and select Load Balancers
  3. In Actions, select Manage Configuration on the Load Balancer we will work with

     
  4. Select Edit Configuration
     
  5. Visit the Web Application Firewall and select Configure in the Cookie Protection Field
     
  6. Select Add Item to create a new Cookie Protection Rule
     

    **Note:** Wildcards and regular expressions (regex) are not supported. You must use the exact cookie name

  7. Click Apply
  8. Click Save and Exit 

Additional Information

Cookie Flags:

1. Path: The 'path' attribute signifies the URL or path for which the cookie is valid. The default path attribute is set as '/'.
2. SameSite: The SameSite attribute on a cookie allows sites to control the behavior and prevents browsers from appending the cookie to request if the request is generated from a third-party site page load.

  • Strict Attribute: This attribute ensures that cookies are not sent in any cross-site requests, including top-level navigation. This means that the cookie is restricted to the same site from where it originated, providing a high level of security for cross-origin transmission. This is useful for sensitive cookies, such as session identifiers, where cross-site requests should be completely restricted to mitigate various security threats like CSRF (Cross-Site Request Forgery) attacks.
  • Lax Attribute: Cookies can be sent in top-level navigations and cross-site requests initiated by safe methods, such as GET requests. This attribute is beneficial for maintaining the user experience and protecting against attacks. It offers more flexibility in terms of security than strict.
  • None Site Attribute: This attribute allows cookies to be sent in all scenarios, including cross-site requests. It is the least restrictive option and is usually used when cross-origin sharing is necessary for web applications to function properly, like when embedding content from multiple origins. In order to ensure that sensitive data is not exposed over unencrypted connections, using "non" requires adding the "secure" attribute in addition to the others.

3. Domain : The 'domain' attribute signifies the domain for which the cookie is valid and can be submitted with every request for this domain or its subdomains. If this attribute is not specified, then the hostname of the originating server is used as the default value.

4. Secure: When a secure flag is used, then the cookie will only be sent over HTTPS, which is HTTP over SSL/TLS.
5. HttpOnly: A cookie with the HttpOnly attribute is inaccessible to the JavaScript Document. cookie API; it's only sent to the server

Hashing all cookies without a defined domain guarantees the integrity of these cookies and acts as a security measure against manipulation. The principal ASM main cookie, which has a name like (TS01xxxx), is produced automatically. This cookie is by default domain-agnostic unless a host name within ASM is specified.

A separate "ASM main cookie" is created for each unique domain that is detected in the Set-Cookie headers of an HTTP response. These additional ASM main cookies are unique to each domain and are linked to the cookies for that particular domain. This is why we do not have a domain field in the options.

Generally, we can disregard vulnerability scans detecting this as a potential exploit vector if a vulnerability scan is run on their app/site as ASM/WAF cookie is only processed by the WAF, and is never seen by the server. The rest of the cookies that are not the main asm cookie can have the flags enforced by using the guided configuration.
