Description

Stack Overflows (CWE-121) are a sub-class of the Buffer Overflow vulnerability (see K69961311) that can affect applications written in many programming languages, and the name describes any situation in which the software attempts to move data from one location in memory into a fixed-length buffer allocated on the stack, which is too small to hold the data.

Environment

Any software application.

Cause

  • Insufficient bounds checking when working with user-supplied data.

Recommended Actions

Since buffer overflows can affect such a vast array of applications it is impossible to give one-size-fits-all advice beyond ensuring that your application applies good bounds-checking when working with any user-supplied input. If we talk about web applications, specifically, however, it may be possible to mitigate buffer overflow attacks against a web application or web server using BIG-IP Advanced WAF, Silverline WAF etc to enforce length checks against user-supplied input (in the form of HTTP parameters, URIs, and headers). Specific instructions are outside of the scope of this document since any policy must be tailored to the web application in question.
 
If you are concerned about a known buffer overflow vulnerability in the BIG-IP Configuration Utility the best mitigation is to ensure your administrators:
  • Access the Configuration Utility from a dedicated management host, jump box or another controlled environment

Additional Information

To explain the anatomy of a Stack Overflow, we must first explain (in brief) how common architectures handle memory management within processes and, specifically, how they manage the stack.

Imagine the memory space of a typical process looks something like this:

0xffff ffff +-------------+
            |    Stack    |
            +-------------+
            |      v      |
            |             |
            |     free    |
            |             |
            |      A      |
            +-------------+
            |    Heap     |
            +-------------+
            |    data     |
            +-------------+
            |             |
            |    Text     |
            |             |
0x0000 0000 +-------------+

At the bottom of this diagram, we have the lowest memory address associated with the process (and at the top, the highest). Reading top-down we have the stack space, which grows downward through unallocated space toward the heap, which grows upward toward the stack. Next comes data (which we can ignore for the purposes of this explanation) and finally text which, despite the name, contains the immutable application code.

Stack Overflows, as the name implies, deal entirely with variables allocated in the stack, so let’s zoom in on that part of the application’s address space and see how it looks:

0xffff ffff +-------------+
            |    ARG 2    |
            |    ARG 1    |
            +-------------+
            |    RETPTR   |
            +-------------+
            |     EBP     |
            +-------------+
            |     VAR     |
0xaaaa aaaa |     VAR     |
            |             |
            |             |
            |             |
...
0x0000 0000

Each time the application code calls a function, information about that function is pushed onto the stack in the format above – from the top down we have any arguments passed to the function followed by a pointer (RETPTR), the EBP (which we’ll ignore for now) and finally any variables created within the function. Earlier, we said that the stack grows downward (from 0xffffffff) and while that is true, variables within each stack entry are filled upward, so in the image above if we place data into the area reserved for ‘VAR’ it will begin at 0xaaaaaaaa and fill upward toward 0xffffffff.

You can probably already see here what would happen if we were to try to insert more data into VAR than it can hold – the data will overflow upward and overwrite EBP, RETPTR and so on.

We’re going to ignore EBP for now but consider RETPTR – that value is a pointer to the position in memory that the processor should jump to when this function has completed; it should be a pointer to a memory position containing an instruction to execute, but you can probably imagine that if we have overflowed VAR and overwritten RETPTR it will now be arbitrary data. At best, it will point to an area of memory that is not executable for some reason and the program will simply crash, but at worst it could be made to point to an area of memory that contained attacker supplied malicious code and if that is the case, the processor will simply start executing that code.

Even if we do not overflow far enough to overwrite the pointer area, if the variable being overflowed is not the uppermost variable in memory we might be able to overflow other variables and perhaps silently manipulate the logical flow of the program without ever causing a crash, or possibly causing a crash far away from the original source of the problem.

Affected Environments

As we have seen above, almost all applications, web servers, and environments are potentially susceptible to buffer overflows. The exception to this rule comes in the form of interpreted languages such as Python; here, it is not the application itself which may be susceptible but the underlying interpreter – i.e., Python code is considered safe, but this does not preclude the possibility of a buffer overflow vulnerability in the Python run-time itself as this was written in a lower-level programming language.

Examples

Consider the following simple stack overflow example C code:

#include <stdio.h>
#include <string.h>

void sass(char *colour)
{
    char buf[100];
    strcpy(buf, colour);
    printf("So your favourite colour is %s? How dull!\n", buf);
}

int main(int argc, char *argv[])
{
   sass(argv[1]);
   return 0;
}


The above snippet of C code takes whatever is passed as the first argument when it is run and uses that input to generate some output back to STDOUT. When we enter the function ‘sass’ and allocate 100 bytes of space for ‘buf’, our stack frame would look something like this: 

0xffff ffff +-------------+
            |    colour   |
            +-------------+
            | 0xAABBCCDD  |
            +-------------+
            |     EBP     |
            +-------------+
            |             |
0xaaaa aaaa |     buf     |
            +-------------+
            |             |
            |             |
            |             |
...
0x0000 0000

0xAABBCCDD is a pointer to the call to ‘return 0’ in the main function, as that is where we will return when the call to ‘sass’ is complete, and the 100 bytes of space reserved for ‘buf’ will be empty.
We will immediately copy the contents of the argument ‘colour’ into it through the call to strcpy. If we pass more than 100 bytes of data in the command line argument we will overflow the space allocated for ‘buf’ because the call to strcpy is unbounded in size, so imagine we pass 116 bytes of the character ‘A’ into buf:

0xffff ffff +-------------+
            |    colour   |
            +-------------+
            |  AAAAAAAA   |
            +-------------+
            |  AAAAAAAA   |
            +-------------+
            |  AAAAAAAA   |
0xaaaa aaaa |  AAAAAAAA   |
            +-------------+
            |             |
            |             |
            |             |
...
0x0000 0000

As you can see, we have overflowed ‘upward’ and overwritten both EBP and the return pointer with ‘AAAAAAAA’. Execution of the ‘sass’ function will continue until the processor attempts to return to what it believes to be the legitimate return pointer and, instead of this sending us to ‘return 0’ to end the program, it will attempt to read an arbitrary area of memory.

Note in the above diagram, though, that our allocated buffer for ‘var’ actually begins at 0xAAAAAAAA? Because of that, the processor will attempt to jump into what is variable space. Of course, in this example it will crash as that area of memory doesn’t contain valid instructions to execute – but if we were to pass instructions as the input to our program, rather than A’s, we could cause the processor to jump into our variable space and then begin executing our own malicious code. In this case the stack overflow has led to a code execution vulnerability.

There are many protection mechanisms built into current compilers and processors to try and prevent this attack from working as outlined above such as non-executable memory space, stack canaries and other compiler-based automatic bounds checking, and address space layout randomisation which makes predicting the address you need to jump to much more difficult.
 
Mitigations
 
If you wish to protect an application against buffer overflows attacks and cannot use Advanced WAF or a similar product to enforce bounds checking on input then you should build this functionality into the application itself:
  • Ensure that all input is subject to sufficient bounds checking
  • Ensure that any memory copy related code is subject to sufficient bounds checking, and do not rely on earlier checks on the original input length
  • Ensure that any application is compiled with all available compiler protections, e.g., stack canaries, NX-bit, ASLR/PIE etc
OWASP has additional advice for this in their Buffer Overflow cheat-sheet.
