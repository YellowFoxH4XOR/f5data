Known Issue

This is the result of a known issue. When RAM Cache generates a response with a status code other than 200, 206, or 304, if the cached document has a message-body, the message-body will not be included in the response served by RAM Cache. This issue will cause the connection to stall permanently.

Consider the following example:

  • A virtual server is configured with an HTTP profile with RAM Cache enabled.
  • In response to a request for a certain object, an OWS serves the following response, which is cached by the BIG-IP system:

    HTTP/1.1 301 Moved Permanently
    Location: http://www.example.com/
    Content-Type: text/html
    Content-Length: 174

    <html>
    <head>
    <title>Moved</title>
    </head>
    <body>
    <h1>Moved</h1>
    <p>This page has moved to <a href="http://www.example.com/">http://www.example.com/</a>.</p>
    </body>
    </html>
  • The BIG-IP system will reply to subsequent requests for the same object from RAM Cache; however, the responses will not include the message-body:

    HTTP/1.1 301 Moved Permanently
    Location: http://www.example.com/
    Content-Type: text/html
    Content-Length: 174
  • Because clients will receive the Content-Type and Content-Length headers, they will begin waiting for a message-body that will never arrive. This behavior causes the connection to stall permanently.

The expected behavior is for RAM Cache to serve the message-body of any document that has one, regardless of the response status code.

F5 Product Development tracked this issue as CR137184, and it was fixed in BIG-IP version 10.2.0. For more information about upgrading, refer to the BIG-IP LTM or WebAccelerator release notes.

Additionally, this issue has been fixed in Hotfix-BIGIP-10.1.0-3372.0-HF1 issued for BIG-IP version 10.1.0. You may download this hotfix or later versions of the hotfix from the F5 Downloads site.

Workaround

You can work around this issue by disabling RAM Cache for the affected responses. To do so, you may use an iRule similar to the following example:

when HTTP_RESPONSE {
if { ! ([HTTP::status] eq "200" or [HTTP::status] eq "206" or [HTTP::status] eq "304") } {
CACHE::disable
}
}
