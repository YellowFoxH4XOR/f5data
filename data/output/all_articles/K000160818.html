Description

Organizations expanding infrastructure across multiple cloud providers and on-premises locations need seamless, isolated network connectivity across heterogeneous environments. F5 Distributed Cloud provides a Global Layer 3 Virtual Network capability using Segments with Secure Mesh Sites v2 (SMSv2) Customer Edges. Understanding how to configure segments, assign them to CE interfaces, and establish BGP peering is essential for achieving dynamic routing and network isolation across distributed sites.

  • How can a Global Layer 3 Virtual Network be implemented using F5 Distributed Cloud Segments and SMSv2 Customer Edges?
  • How do Segments in F5 Distributed Cloud compare to Layer 3 VRFs in traditional networking?
  • How are Segments assigned to Customer Edge interfaces?
  • What route types are supported for advertisement through Segment interfaces?
  • How is BGP peering configured on a Customer Edge interface tied to a Segment?
  • How can route propagation across sites be verified after Segment and BGP configuration?

Environment

  • F5 Distributed Cloud (SaaS)
  • Secure Mesh Sites v2 (SMSv2) Customer Edges
  • Customer Edge deployed on one or more of the following platforms:
    • KVM hypervisor (private/on-premises data center)
    • AWS VPC
  • Dual-NIC (minimum) CE configuration — one SLO interface + one or more data plane/segment interfaces
  • F5 Distributed Cloud Segments configured under Multi-Cloud Network Connect
  • BGP peering configured between CE and local network infrastructure (optional, but required for advertising routes beyond connected subnets)
  • Multiple isolated sites with no direct VPC peering between cloud sites

Cause

None

Answer/Recommended Actions

Use F5 Distributed Cloud Segments as Layer 3 VRF-like constructs to connect isolated environments across private data centers and cloud VPCs through the F5 global network fabric. The following steps walk through the full configuration.

Prerequisites

  • F5 Distributed Cloud account with appropriate permissions.
  • Three deployed SMSv2 Customer Edge nodes, each with a minimum of two network interfaces (one SLO + one data plane interface).
  • Basic understanding of BGP configuration if implementing dynamic route advertisement.
  • For cloud-based CEs (e.g., AWS): source/destination checks must be disabled on all CE interfaces.
  • Ensure cloud instance types support the required number of network interfaces for the planned number of segments.

Understanding Segments

In F5 Distributed Cloud, Segments are the equivalent of Layer 3 VRFs in traditional networking. Each segment maintains its own isolated routing table, enabling traffic separation, overlapping IP address space support across segments, and explicit security boundaries between network domains. Key characteristics include:

  • Segments must be explicitly attached to CE data plane interfaces. The SLO interface cannot be used for segment assignment.
  • Each interface can belong to only one segment (one-to-one mapping).
  • Segments only advertise connected routes (interface subnets) and BGP-learned routes. Static route advertisement through segment interfaces is not currently supported.
  • Routes learned within one segment remain isolated from other segments unless explicitly shared via inter-segment policy.

Understanding CE Interface Types

Careful interface planning is required for SMSv2 CE deployments with segments:

  • Site Local Outside (SLO) Interface:
    • The management and control plane interface (typically eth0/ens3).
    • Used for zero-touch provisioning, VPN tunnel establishment to the F5 XC Global Controller, health monitoring, and telemetry.
    • Must have internet access to reach F5's global infrastructure.
    • Cannot be used for segment assignment.
  • Site Local Inside (SLI) and Segment Interfaces:
    • All remaining interfaces are available for data plane traffic.
    • SLI interfaces provide local network connectivity without segment assignment.
    • Segment interfaces are dedicated to a specific segment for VRF-like isolation, BGP peering, and segmented connectivity.

Interface planning rules:

  • Minimum two interfaces per CE: 1 SLO + 1 data plane/segment interface.
  • Maximum eight physical interfaces per CE, with VLAN sub-interfaces supported on top of physical interfaces.
  • Multi-segment deployments require one additional interface per segment (e.g., 4 segments require 5 interfaces: 1 SLO + 4 segment interfaces).

Step 1: Create the Network Segment

  1. Navigate to Multi-Cloud Network Connect → Manage → Networking → Segments.
  2. Click Add Segment.
  3. Configure the segment with an appropriate name and description.
  4. Define the segment scope based on your requirements.
  5. Save the configuration.

The segment acts as a logical network overlay spanning all participating sites, similar to extending a VRF across multiple locations in a traditional MPLS network.

Step 2: Assign Segments to CE Interfaces

  1. Navigate to Multi-Cloud Network Connect → Manage → Site Management → Secure Mesh Sites v2.
  2. Select the CE to configure and click Edit.
  3. Navigate to the node interface configuration section.
  4. Select the appropriate data plane interface (typically the second NIC — not the SLO interface).
  5. Assign the segment created in Step 1 to this interface.
  6. Configure the interface mode as required.
  7. Save and apply the changes.
  8. Repeat this process for all participating CE nodes.

Important:

  • The SLO interface (eth0/ens3) must not be used for segment assignment.
  • Each data plane interface can belong to only one segment.
  • Once all CEs have the segment assigned, all participating sites will be connected through the segment fabric.

Step 3: Configure BGP Peering (Optional but Recommended for Production)

BGP peering is required when advertising routes beyond the directly connected subnet of the segment interface. Because static routes cannot currently be advertised through segment interfaces, BGP is the only method available for multi-subnet route advertisement.

  1. Navigate to the BGP configuration section of the CE.
  2. Select the interface tied to the segment (e.g., ens4) as the BGP peering interface.
  3. Configure the following BGP parameters:
    • Local AS number
    • Peer AS number
    • Peer IP address
    • Network advertisements
  4. Apply the configuration.

Routes learned via BGP will be contained within the assigned segment's routing domain and propagated to other sites participating in the same segment.

Step 4: Verify Route Propagation

  1. Navigate to Multi-Cloud Network Connect → Overview → Infrastructure.
  2. Select the site name to inspect.
  3. Click on CE Routes.
  4. Apply filters as needed to scope the view.

Confirm the following in the route table:

  • Routes from remote sites appear with correct next-hop information pointing to remote CE IPs.
  • BGP-learned routes are present (if BGP is configured and Site Survivability is enabled).
  • Routes are properly isolated within their respective segments.
  • Only connected and BGP-learned routes are present — no static routes.

Additional Information

F5 Distributed Cloud Segments provide an architectural approach equivalent to traditional VRF implementations, extended globally across the F5 network fabric. This enables organizations to achieve:

  • Production/Development Separation: Different segments for prod and dev environments sharing the same CE infrastructure.
  • Multi-Tenant Deployments: Isolated segments per customer or business unit, with support for overlapping IP address spaces between segments.
  • Compliance Requirements: Segmented networks for regulated traffic domains such as PCI-DSS or HIPAA.

The current limitation of no static route advertisement through segment interfaces is an important architectural planning consideration. In environments where static routing would traditionally be used, BGP peering should be designed into the solution from the outset. A workaround is to use BGP to advertise routes that would otherwise be configured as static routes.

For cloud-based CE deployments (e.g., AWS VPCs), disabling source/destination checks on all CE network interfaces is a mandatory requirement, as the CE acts as a routing/proxy device and will forward packets that are neither sourced from nor destined to its own IP address.

The SMSv2 CE supports up to eight physical interfaces, with VLAN sub-interfaces available on top of physical interfaces for additional logical segmentation without requiring additional physical NICs. This provides flexibility for environments where the number of available physical interfaces on the host or cloud instance is limited.

As F5 Distributed Cloud continues to evolve, limitations such as static route support for segment interfaces may be addressed in future releases. Always refer to the latest F5 Distributed Cloud documentation and validate configurations in a non-production environment before deploying to production.
