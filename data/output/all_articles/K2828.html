Note: The information contained in this Solution is intended to serve as a guide for designing SSL solutions and is not an indication of the BIG-IP system's performance. Older BIG-IP hardware has TPS limits of less than 800.

Introduction

F5 Networks currently offers the following two solutions to manage SSL connection termination and load balancing. When designing an SSL solution based on the BIG-IP system, it is important to understand the capacity for each option in order to select between these two solutions and scale designs appropriately.

  • SSL operation

    A single BIG-IP system, optionally paired with a standby partner, handles all connections through an SSL Proxy for SSL traffic and virtual servers for non-SSL traffic.

  • Load balancing to eCommerce Controllers

    An alternative solution for large deployments is to load balance SSL connections to a number of eCommerce Controllers that are dedicated to the task of SSL termination. This increases SSL capacity in a linear manner with each additional eCommerce Controller.

Summary of SSL termination and load balancing operation

An SSL connection has two main phases, the handshake and data transfer. The handshake involves authenticating one or both parties and exchanging information to establish the keys required to encrypt and decrypt the subsequent data transfer. The handshake phase is computationally more expensive than the data transfer. Because of this, BIG-IP Server Appliances offload this process to a dedicated, optional SSL card, while Switch Appliances offload the process to a built-in chip on the Switch Appliance.

Critical boundaries

The following three parameters are of primary importance when sizing SSL solutions:

  • Transactions per Second (TPS)
  • Bulk encryption/decryption (bulk crypto)
  • Concurrent Connections

Transactions per Second (TPS)

Although the term transaction includes both the handshake and the transfer phases, TPS is often used to describe only the handshake performance. For the BIG-IP, TPS is limited according to the license, allowing up to 800 TPS, and 1,200 TPS on the BIG-IP 5000 series Switch Appliance.

Note: If the BIG-IP system's license limit is exceeded, additional connections are deferred to the next second and a syslog message is generated. This allows you to upgrade the license without adversely affecting general performance, as long as the excess is reasonably small and the upgrade is outstanding. CPU load increases linearly with TPS.

Bulk encryption/decryption (bulk crypto)

This describes the total amount of client data, typically displayed in Mbps, handled by the SSL proxy, which usually requires encryption or decryption. This function is not offloaded and the performance is ultimately limited by the speed of the processor. The BIG-IP 5000 series has a maximum bulk crypto of 150Mbps, and all other system types have a maximum bulk crypto of 100Mbps. CPU load increases linearly with bulk crypto. TPS decreases linearly as bulk crypto increases, and TPS increases linearly as bulk crypto decreases.

Note: You may not reach these TPS levels. If you have small page sizes or high concurrent connections, the TPS are limited before attaining these rates. However, if you have a few connections that generate high bulk crypto, refer to the recommendations contained in the Recommendations for Design section of this document.

Concurrent Connections

Concurrent Connections are the number of connections associated with SSL proxies. These connections reside in the BIG-IP connection table. Concurrent connections are not closely related to TPS or to the number of users, since multiple connections can exist for each user operation. For additional information, refer to Latency in the Additional Factors section. As the number of active SSL connections increase, the CPU load also increases because the BIG-IP has more sockets to manage. Therefore, as the number of active SSL connections increase, exceeding recommended practical limits, TPS and bulk crypto will decrease.

The relevance of these three parameters depends on the configuration. The parameters have a bearing on each other and with the factors listed in the following section.

SSL proxy daemon limits

The approximate limits for the SSL proxy daemon are as follows:

  • BIG-IP version 4.5 PTF-04 - 4.6.4: 5,500 TPS for single processor systems and those running the Auxiliary Network Interface Processor (ANIP) kernel; 11,000 TPS for dual processor systems running the Symmetric Multi-Processor (SMP) kernel.
  • BIG-IP version 4.2 through 4.5 PTF-03: 8,100 TPS

Note: For more information about choosing a kernel, refer to K1691: Selecting the proper BIG-IP kernel.

These SSL proxy daemon limits assume that the majority of connections are idle and are affected by latency. A practical limit, under light to medium load, is 3,000 concurrent connections. If the average HTTP response (page) size exceeds 50KB, or if the bulk crypto across all proxies exceeds 50MB, then the following limits apply irrespective of TPS:

  • Single processor systems: 1,200 TPS
  • Dual processor systems: 1,700 TPS

Note: At these limits, CPU utilization will likely be close to 100%.

Connection duration

SSL performance planning most often assumes a connection of short duration and, therefore, focuses on the handshake phase. However, some application designs are intended for a fixed user base where users perform an initial login and make intermittent requests on the same SSL session. In this case, TPS may be the less relevant factor compared to concurrent connection limits.

Note: Some browsers renegotiate an SSL session ID at regular intervals The resulting increase in TPS is normally irrelevant in fixed user base scenarios, but may become an issue when there is a mixture of long and short duration connections.

Session ID reuse

The ability to cache and reuse SSL Session IDs can increase the TPS considerably, depending on the duration of the connection. Although fresh keys are calculated, presentation of previously-used SSL Session IDs implies the authenticity of both parties and the possession of the correct keying material (Pre-Master Secret); thus the processor-intensive authentication and key exchange functions can be bypassed. Although reusing sessions is recommended, the accelerator card or chip only performs full handshake operations.

Note: For a small page size, such as 1KB, the BIG-IP 5000 series can achieve approximately 800 TPS; however, when Session IDs are reused, it is possible to reach up to 1,200 TPS. The F5 Networks SSL license only takes new sessions into account. Reused sessions are not factored into the calculation for license enforcement.

Bulk crypto and TPS

Bulk crypto has a direct impact on the completed TPS, which is a combination of SSL handshakes and data transfers. In the case of HTTP, bulk crypto is best described by the average page size of HTTP responses, unless other factors such as large client POST operations are significant. The handshake phase is relatively slow with small amounts of user data. As the data size increases, the time spent on encrypting or decrypting begins to outweigh the time taken for the initial handshake.

Certificate related considerations

Most of the computation involved in the handshake phase involves signing and verifying data using a public key algorithm such as RSA. BIG-IP authenticates itself to the client by supplying its certificate, then the client performs the verification workload. In the key exchange, the client uses the BIG-IP public key to encrypt the Pre-Master Secret, requiring that BIG-IP decrypt it using its private key. BIG-IP's handshake workload is further increased if BIG-IP is required to verify the certification presented by the client, and if ephemeral keys are used, rather than static.

For Switch and Server Appliances with accelerator cards or chips, performance is not affected by the key types and lengths for the key exchange algorithm. For Switch and Server Appliances without accelerator cards or chips, the handshake must be performed on the main CPU. In this case, assume 512 bit keys perform two to three times faster than 1,024 bit keys, and 1,024 bit keys perform two to three times faster than 2,048 bit keys.

Note: The use and authentication of client certificates has a negligible effect on performance.

system_check

The system_check script, which runs in the cron system utility on BIG-IP Switch Appliances, gathers information about the system's health, including CPU state, fan speed and temperature. This script can decrease TPS, for a 10 second duration every two minutes, by up to 30% when it is executed.

Latency

As concurrent connections increase, latency affects those connections. If latency is considered an issue, F5 Networks recommends that you limit concurrent connections to approximately 3,000. This limit maintains a reasonably short latency per connection. As the number of connections increase, the work of maintaining connections starts to impact the ability of the processor(s) to perform bulk encryption or decryption for existing connections, and the processor(s) ability to accept new connections. Because of this effect, concurrent connections are limited under load.

Note: As latency increases, concurrent connections also increase since each connection takes longer to process. Therefore, the number of users and the offered load may not represent the actual number of concurrent connections.

Mirroring

Mirroring affects SSL performance according to system type and configuration:

  • Dual processor with BIG-IP in SMP mode - moderate impact
  • Dual processor with BIG-IP in ANIP mode - severe impact
  • Single processor BIG-IP - severe impact

Important: Do not enable mirroring on virtual servers that handle proxy traffic. Such connections will not fail over because SSL session keys are not mirrored between BIG-IP active/standby pairs.

Non-SSL traffic

Non-SSL traffic affects SSL performance according to system type and configuration:

  • Dual processor BIG-IP in ANIP mode - moderate impact
  • Dual processor with BIG-IP in SMP mode - severe impact
  • Single processor BIG-IP - severe impact

The effect of non-SSL traffic can require an e-Commerce Controller solution when the SSL load could otherwise be handled by a BIG-IP solution; however, certain functions affect TPS in particular, such as layer 7 operations like cookie insertion, use of iRules, and so on.

Monitors

TPS is adversely affected by the use of advanced monitor types, such as SSL monitors, that consume larger amounts of CPU time. You should remove the SSL monitors from the configuration if the BIG-IP system is terminating SSL traffic, rather than load balancing SSL traffic to nodes.

Number of SSL proxies required

The BIG-IP Configuration utility (bigapi) has a memory restriction, which limits the number of proxies to approximately 150. If you must view all proxies though the Configuration utility, you will need to deploy an eCommerce Controller solution.

Recommendations for Design

Note: The following section does not account for performance gains that can be made by changing a BIG-IP dual processor from ANIP to SMP mode.

Important: The choice of SMP or ANIP mode has opposite effects on mirroring and layer 7 operations, referenced in the Additional Factors section. You may also be able to increase performance for traffic that is eligible for hardware acceleration on the BIG-IP 2400 Switch Appliance, particularly where layer 7 operations are required.

Perform the following design steps to account for the factors discussed in the Critical Boundaries section.

Note: These processes are based on scaling TPS per BIG-IP.

Important: For scenarios that involve long-lived connections (where bulk crypto may be high and TPS low), follow steps 3(a) through 3(d) using bulk crypto values reduced by the percentages shown.

  1. Profile your traffic (for example, if currently terminating SSL on servers, analyze server statistics) and obtain realistic estimates for the following:
    • Peak TPS
    • Decrease the peak TPS by the percentage of connections that will be using a cached Session ID. This requires knowledge of the application and how it is used. You will also need to set an appropriate cache timeout.
    • Average page size for HTTP or bulk data, utilized for longer lived connections.
    • Concurrent connections across all servers being load balanced.

    You will need to consider the expected increase of the number of concurrent connections. If you are planning a new installation, remember to account for session renegotiation and to decrease the target TPS accordingly.

  2. Check to see if any of the limits described in the Critical boundaries section would be exceeded on a single live BIG-IP. If so, implement an eCommerce Controller solution.

    Important: Due to the vulnerability of 512-bit certificate keys and the significant performance implications of handshaking in software, F5 Networks recommends that you use accelerator cards or chips. The remaining steps assume accelerator cards or chips are in use.

  3. Estimate the maximum completed TPS per BIG-IP, noting that the number will most likely be higher on an eCommerce Controller dedicated to handling SSL traffic. Allow a margin for error in terms of BIG-IP performance and estimated load.

    a) Reduce the maximum TPS per BIG-IP to account for the average page and data size of each connection by the following:

    Data sizeTPS
    1KB685
    8KB530
    32KB300
    64KB200
    256KB70
    512KB28

    Note: These numbers are based on BIG-IP version 4.5 PTF-07.

    b) Reduce the maximum TPS by 50% if all connections will be re-encrypted using the BIG-IP system's SSL to Server option. If only a certain percentage of proxy instances require re-encryption, you can reduce the maximum TPS by the appropriate percentage.

    c) Reduce the maximum TPS per BIG-IP as follows to account for the presence of non-SSL traffic and any Layer 7 operations, such as iRules and cookie insert:

    Processor typeTrafficReduction
    Dual Processorlight non-SSL load15%
    Dual processorheavy non-SSL load30%
    Single Processorlight non-SSL load20%
    Single Processorheavy non-SSL load40%

    d) Reduce the maximum TPS per BIG-IP by 40% if mirroring is used.

    e) Reduce the maximum TPS per BIG-IP by 10% if any SSL or intensive EAV monitors are used.

  4. Divide the peak TPS value from step 1 by the per-BIG-IP number from step 3. If this is 0.7 or less, a single BIG-IP or redundant pair should suffice. Otherwise, design for an appropriate number of eCommerce Controllers.
  5. Review the bulk crypto numbers using the percentages (shown in steps 3b and 3c) to check per-unit capacity.

Design scenarios

Scenario 1

  • The site currently handles 3,000 peak TPS.
  • The average page size is 8KB, and each connection terminates upon retrieval of this page.
  • About 40% of SSL Session IDs are being reused. This is expected to increase by 20% over the next two years. At this stage, iRules are not required, but may be in the future.

An eCommerce Controller solution is required for this scenario, because the TPS exceeds 1,200.

Each eCommerce Controller is limited as follows:

  • Total TPS to be designed for: 3,000 less 40% (SSL ID re-use) = 1,800
  • Bulk crypto is 3,000 x 8KB = 24MB

For each eCommerce Controller:

  • 530 TPS (due to 8KB object size)

Solution:

  • 1,800 / 530 = 4 eCommerce Controllers, each handling 6MB of bulk crypto.

A BIG-IP load balancer is used to balance the SSL traffic across the eCommerce Controllers and to balance the clear connections among servers. At this second stage, iRules are applied. Since iRules are configured on the BIG-IP, they do not affect the performance of the eCommerce Controllers. With total TPS scaling by 20% to 3,600. 2,160/530 = 4.07; therefore, one additional eCommerce Controller will be required within the next two years.

Scenario 2

  • A new site requires a total of 230 peak TPS.
  • The average data size per connection is 32KB, with most connections terminating after four seconds.
  • No SSL Session IDs are being reused.
  • About 100MB of non-SSL traffic is to be load balanced and cookie insertion is required. The total TPS will increase by 30% throughout the next year and by an unknown factor thereafter.

Concurrent connections will be 230 x 4 = 920. Bulk crypto will be 230 x 32KB = 7.36Mbps. A single BIG-IP 5100 Switch Appliance can manage 300 TPS (at 32KB data size) less 15% (due to layer 7 operations at light load) = 255 TPS.

This number indicates that the solution would be a single BIG-IP system; however, since it needs to scale by 30% to 300 TPS relatively quickly, a two-system eCommerce Controller solution is recommended.

Monitoring SSL variables

After you design and install a solution, you can monitor the following variables to measure SSL traffic load:

  • proxyd statistics
  • CPU utilization

proxyd statistics

To view the proxyd statistics, find the proxy daemon's Process ID and send it a SIGUSR1 signal by typing the following command:

kill -SIGUSR1 <PID>

This will send extended statistics to the /var/log/proxyd file.

Starting in BIG-IP version 4.5 PTF-04, you can capture many of these statistics at a specified delay using the proxydstats utility. For specific instructions about using this tool, type proxydstats -h from the command line.

Important: As well as generating statistics to standard output, proxydstats also logs to the syslog. This could quickly fill the /var directory on compact flash systems.

    Per-proxy
    • Current entries in the SSL session cache.
    • Client cipher usage.
    • Details about bulk crypto (including number of connections at various object sizes).
    Global You can view the following proxyd details from the Global Statistics screen:
    • Concurrent connections.
    • Peak successful crypto hardware operations per second (for example, handshakes performed by the accelerator chip or card).
    • Client-side/ Server-side data (used for bulk crypto).

    CPU utilization

    Prior to BIG-IP version 4.5 PTF-04, using the top utility to monitor CPU load on dual processor systems did not account for the second processor. Systems with dual processors can exhibit 70% CPU utilization at maximum load. Non-SSL traffic handled by the second processor can also cause the proxy daemon to report too high of a percentage for CPU usage, because proxyd reports this traffic running on the first processor. This means that the amount of CPU available for user daemons, such as the SSL proxy, appears to be less than the actual amount.

    Beginning with BIG-IP version 4.5 PTF-04, top correctly displays the CPU load for dual processor systems and provides an effective way to measure SSL proxy performance.

    Although proxyd is a user process, the work done by the kernel on behalf of proxyd also counts against proxyd. A high percentage of system usage can indicate a high number of idling concurrent connections. This situation would require little processing by proxyd, but a high workload for the kernel because it must perform connection state maintenance on behalf of proxyd.

    If connections are delayed due to rate-limiting based on the SSL Gateway Level (TPS), messages indicating this will appear in the /var/log/proxyd log (through the syslog local3 facility in BIG-IP 4.2 and later). If you receive these log messages, contact F5 Networks Technical Support.

    Notes/other considerations

    Performance gain in SSL processing

    In releases prior to BIG-IP version 4.5.10, two-processor appliances had one processor dedicated to network I/O and one processor dedicated to other system processes that perform functions such as handling SSL traffic. In certain cases, you can switch to SMP mode and have both processors dedicated to SSL traffic. You can achieve a performance gain in SSL processing by using SMP mode, but only if your configuration meets the following requirements:

    • The system is a dual CPU platform.
    • The system is for processing SSL only.
    • The system is not handling significant quantities of L2 or L4 traffic.
    • You want an increase in the SSL proxy performance.

    Important: F5 Networks recommends that you design configurations for the default mode and modify the kernel as a tuning option. For more information about the kernels and specific instructions about how to change the default kernel, refer to K1691: Selecting the proper BIG-IP kernel.

    You should not modify the current configuration if BIG-IP is managing mixed network traffic. For example, if virtual IP addresses that only perform L2 traffic and virtual IP addresses that perform SSL traffic are processing on the same system, they would be considered mixed network traffic. SMP mode only improves the performance of systems that exclusively use the BIG-IP for SSL traffic.
