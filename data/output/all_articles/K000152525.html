Topic

This article provides an overview of what you can monitor for high host (OS) or Linux memory usage on your BIG-IP system. This article focuses on host memory. For more information on:

  • BIG-IP memory allocation, refer to K16419: Overview of BIG-IP memory usage
  • monitoring for high TMM memory, refer to K000151903: Overview of monitoring high TMM memory usage
    Note: TMM does not contribute to host memory use

Description

Host (OS) or Linux memory utilization may increase due to a variety of reasons. BIG-IP provides the following facilities that you can use to monitor for symptoms of high Host (OS) memory usage and respond before services are disrupted.

Monitor host memory utilization graphs from the Configuration utility and iHealth

The diagram illustrates an example of a slow memory leak over 30 days with increasing host memory use, followed by increasing swap usage resulting in an OutOfMemory killer and service restart around the 28th day. 

  • On the Configuration utility, go to Statistics > Performance Reports.
  • On iHealth, go to Graphs > Standard, select Memory used.
The Understanding BIG-IP memory statistics section of K16419: Overview of BIG-IP memory usage
Monitor high host memory from command outputs

(A BIG-IP system under memory pressure displays downward trend in free and free-able RAM, and this is typically indicated by a persistent downward trend in MemAvailable (from /proc/meminfo) and increased resident memory, rss and swap use by a process.)

Monitor the following with top:

  • Memory:
    In interactive mode, enter M to sort by memory.
    In non-interactive mode, use -o to sort by entering: top -b -n 1 -o RES.
    RES:     The resident memory size. Resident memory is the amount of non-swapped physical memory a task is using. This represents the actual space a process occupies in physical memory.
    %MEM:     The percentage of available physical memory used by the process.
  • CPU: High memory usage is often accompanied by high CPU usage.
  • K16739: Understanding 'top' output on the BIG-IP system
  • CPU: K32264816: High CPU troubleshooting with the top command

Monitor MemAvailable with:

  • cat /proc/meminfo
    MemTotal:       16433396 kB
    MemFree:          150992 kB
    MemAvailable:     562016 kB <----

MemAvailable is a metric in the Linux kernel that indicates the amount of memory available for allocation. It includes:

  • Immediately available free memory
  • Memory used for Buffers and Cache to enhance performance.
You can also monitor MemAvailable using SNMP. For more information, refer to: 
K51343007: How to create a custom SNMP OID for monitoring MemAvailable

Monitor swap with:

  • cat /proc/meminfo | grep Swap

High swap use alone may not be a problem. However, when accompanied by any of the above indicators, or with intensive paging, an issue exists. Monitor for intensive paging using the vmstat command. For example:

  • vmstat 1 5

monitor the swap in (si) and swap out (so) values.
  • K40027012: Monitoring Swap Usage for Each Process With the top Command
  • K30279635: Swap memory appears to be leaking

Monitor host memory usage trends over time by using tmctl to query snapshots in the host_info_stat and proc_pid_stat tables. Refer to the following examples:

  • monitor free swap trend: 
    tmctl -w 10000 -D /shared/tmstat/snapshots -s time,slot_id,free_ram,shared_ram,buffer_ram,total_swap,free_swap -T performance -R 10800 host_info_stat
    The command displays the value of free_swap in bytes together with other memory statistics in the host_info_stat table containing snapshots every 3 hours.

  • monitor rss trend of a process using the following command syntax: 
    tmctl -w 10000 -D /shared/tmstat/snapshots -T public -R 86400 -s time,proc_name,pid,vsize,rss,command_line proc_pid_stat proc_name=<process name>
    For example:
    tmctl -w 10000 -D /shared/tmstat/snapshots -T public -R 86400 -s time,proc_name,pid,vsize,rss,command_line proc_pid_stat proc_name=java
    The command displays the statistics specified by the -s switch including rss in the proc_pid_stat table for the java process, containing snapshots taken once a day (86400).

Monitor individual daemon log files 

Monitor the health of each daemon and service through the log files they log to at the appropriate log levels (emerg, alert, crit, error) for early indications of an issue. For more information refer to the following:

  • Daemons services and their log files: K48615077: BIG-IP daemons (15.x - 17.x)
  • Log levels: K15521451: Log files and alerts | BIG-IP TMOS operations guide
  • Log filtering: K13333: Filtering log messages sent to remote syslog servers (11.x - 17.x)

F5 recommends monitoring at least the /var/log/ltm file, together with the log files of the modules and critical services that the system is running. For example:

  • System: /var/log/ltm
  • BIG-IP APM: /var/log/apm
  • BIG-IP ASM/Advanced WAF, bd: /var/log/asm, /var/log/ts/bd.log
  • Automation toolchain:(AS3, DO, TS): /var/log/restjavad.x.log
  • K61101414: BIG-IP APM daemons (14.x - 17.x)
  • K14020: BIG-IP ASM daemons (11.x - 17.x)
  • K14387: Overview of BIG-IP AFM daemons
Monitor log messages in /var/log/kern.log

err kernel: Out of memory: Kill process <process ID> (<process name>) score <score value> or sacrifice child

The process killed may not necessarily be the root cause of the memory pressure. In the case of a memory leak, the issue is likely to return as memory usage builds up again. Use the following resources to identify the root cause:

  • K47241910: Interpreting an OOM killer log (out of memory
  • K20204992: Identifying top memory consuming processes from an OOM (out of memory) killer log

K16786: Error Message: kernel: Out of memory: Kill process <process ID> (<process name>) score <score value> or sacrifice child

Other common failure symptoms

You may also observe other failure symptoms such as the following on your system as a result of memory exhaustion. Note that these symptoms may also be a result of other causes not related to memory usage:
Note: While services may have restarted and running again after these events, the root cause may not have been addressed, and the issue likely to return.

  • Application and traffic performance impact
  • Daemons and internal services restarts
  • Core files generated in /shared/core
  • Network interface goes down
  • High availability failover.
  • System reboot.

Recommended Actions

When understanding or investigating host (OS) memory usage, consider the following:

  1. exclude TMM in your analysis. For TMM refer to K000151903: Overview of monitoring high TMM memory usage.
  2. monitor and use a combination of at least 2 or more facilities to analyze host memory usage.
  3. Use iHealth:
    1. generate different graphs over different time periods including using the Custom option to focus on a specific time period.
    2. cross reference information from the different graphs with information from a combination of different commands described in this article.
    For more information, refer to K000150125: Generating and uploading a QKView file to F5 iHealth.
