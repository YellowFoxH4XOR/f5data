Issue

You should consider using this procedure under the following condition:

  • You are having issues with Lightweight Directory Access Protocol (LDAP) authentication.

Symptoms

As a result of an LDAP authentication failure, you may encounter the following symptom:

  • Users cannot log in to the BIG-IP APM system.

Recommended Actions

The BIG-IP APM system supports LDAP as an authentication method. If you experience issues logging in to the BIG-IP APM system and are using LDAP authentication, you may need to troubleshoot the communication between the LDAP server and the BIG-IP system to determine the cause of the failure.

The BIG-IP APM LDAP goes through the following steps to authenticate a user:

  • Establishes a TCP connection with the LDAP server.
  • Binds to the LDAP server with the configured administrator account.
  • Sends a search request to locate the user's Distinguished Name (DN).
  • Authenticates using the DN returned by the LDAP search and the password entered by the user.

A failure or misconfiguration in any of the steps can cause authentication to fail.

Procedures

When experiencing LDAP authentication issues, use the following troubleshooting steps to help determine the root cause:

  • Running the tcpdump utility
  • Analyzing LDAP connectivity
  • Analyzing LDAP admin authentication
  • Analyzing LDAP user search
  • Analyzing LDAP user authentication

The examples in this procedure use the following configuration:

  • BIG-IP 10.2.0.90
  • LDAP server 10.2.0.201
  • LDAP port 389
  • Administrator DN CN=Administrator,CN=users,DC=adw2k3,DC=lab
  • APM user TestUser

Running the tcpdump utility

The tcpdump utility captures the communication between network devices. This procedure sets up and filters the network traffic, so it captures only LDAP communication with an LDAP server.

Note: For more information about packet tracing with tcpdump, refer to K411: Overview of packet tracing with the tcpdump utility.

  1. Log in to the command line.
  2. Use the following command syntax:

    tcpdump -nn -vv -i <LDAP server vlan> -s0 -w /shared/tmp/ldap.cap host <LDAP server IP> and port <LDAP port>

    In the previous syntax, note the following:

    • <LDAP server vlan> is the interface Virtual Local Area Network (VLAN) on which the LDAP server resides.
    • <LDAP server IP> is the IP address of the LDAP server.
    • <LDAP port> is the port on which the LDAP service is listening, typically port 389.

    For example:

    [root@bip111:Active] config #tcpdump -nn -vv -i internal -s0 -w /shared/tmp/ldap.cap host 10.2.0.201 and port 389

  3. With tcpdump running, attempt to log in to a BIG-IP APM virtual server that is using LDAP authentication.
  4. Press Ctrl+C to stop tcpdump.
  5. Transfer ldap.cap to the system you are using to analyze the capture file. For more information, refer to K175: Transferring files to or from an F5 system.
  6. Review the packet trace with a tool such as Wireshark, which is capable of decoding the LDAP protocol.

Analyzing LDAP connectivity

Now you can analyze the tcpdump capture file to determine if the BIG-IP system is able to connect to the LDAP server.

This example shows a successful three-way handshake that establishes the TCP connection to the LDAP server.

In the following example, the BIG-IP system sends sends six SYN packets to the LDAP server, increasing the wait time while the system attempts to establish a connection with the LDAP server.

If you encounter this situation, verify that your LDAP server is up, the LDAP service is listening on the LDAP that you configured, and network devices (that is, firewalls, routers, switches, and so on) are allowing the network traffic to pass to the LDAP server.

Analyzing LDAP admin authentication

After the BIG-IP system establishes a connection, it attempts to bind to the LDAP server using the administrator account defined in the LDAP authentication, authorization, and accounting (AAA) server configuration.

The following example shows a bind request and a successful bind response from the LDAP server.

The system passes the administrator DN in the bindRequest. WireShark masks the password using the word simple. Reviewing the raw packet data that contains the password in clear text at that position.

When the LDAP server is able to successfully authenticate the administrator, the server returns the bindResponse success message.

4 0.000801 10.2.0.90 10.2.0.201 LDAP 152 bindRequest(1) "CN=Administrator,CN=users,DC=adw2k3,DC=lab" simple
5 0.004236 10.2.0.201 10.2.0.90 LDAP 110 bindResponse(1) success

The following example shows the LDAP error in bindResponse when the LDAP cannot locate the administrator DN. The standard LDAP response when the server cannot locate an object is data 525. If you encounter this error, verify that the DN for your administrator account in the LDAP AAA server configuration is correct.

Note: Depending on the vendor of your LDAP server, the system may not display the AcceptSecurityContext error data codes discussed in this article.

4 0.000689 10.2.0.90 10.2.0.201 LDAP 153 bindRequest(1) "CN=badAdministrator,CN=users,DC=adw2k3,DC=lab" simple
5 0.001264 10.2.0.201 10.2.0.90 LDAP 197 bindResponse(1) invalidCredentials (80090308: LdapErr: DSID-0C090334, comment: AcceptSecurityContext error, data 525,vece)

The following example shows the LDAP error in bindResponse when the administrator DN password is not valid. The standard LDAP response when the server cannot authenticate the account is data 52e. If you encounter this error, verify that the password for your administrator account in the LDAP AAA server configuration is correct.

4 0.001290 10.2.0.90 10.2.0.201 LDAP 152 bindRequest(1) "CN=Administrator,CN=users,DC=adw2k3,DC=lab" simple
5 0.003865 10.2.0.201 10.2.0.90 LDAP 197 bindResponse(1) invalidCredentials (80090308: LdapErr: DSID-0C090334, comment: AcceptSecurityContext error, data 52e,vece)

Analyzing LDAP user search

After the BIG-IP system authenticates to the LDAP server, the system performs a search to locate the user and obtain the user's DN. The search request is built from the information in the access policy LDAP Auth action.

The example below uses the following configuration in the LDAP Auth action:

SearchDN cn=users,dc=adw2k3,dc=lab SearchFilter (sAmAccountName=%{session.logon.last.username})

The example shows a successful search for a user. Note the following:

  • The searchRequest queries LDAP with the SearchFilter the system defined in the LDAP Auth action, starting at the DN defined in the SearchDN.
  • This example expands the searchRequest packet to show the detail search parameters.
  • Filter shows the SearchFilter that the BIG-IP APM system applies to the LDAP query.

The searchResEntry packet returns the queried user's DN, a success result, and one entry.

8 0.005353 10.2.0.201 10.2.0.90 LDAP 166 searchResEntry(2) "CN=TestUser,CN=Users,DC=adw2k3,DC=lab" | searchResDone(2) success [1 result]

The following example shows a search that did not match the applied filter.

The packet details for the searchRequest are the same as the successful previous example, except that it has a user that does not exist in LDAP. The LDAP returns a searchResDone packet that contains no searchResEntry and 0 results. When the system returns 0 results, verify that the user account exists in LDAP, the SearchDN is set to a container that contains the user accounts in the subtree below that level, and your SearchFilter is properly constructed.

8 0.005085 10.2.0.201 10.2.0.90 LDAP 110 searchResDone(2) success [0 results]

Analyzing LDAP user authentication

The following example shows a bind request and the successful bind response from the LDAP server.

The system passes the user DN acquired in the LDAP search in the bindRequest. WireShark masks the password using the word simple. Reviewing the raw packet data contains the password in clear text at that position.

When the LDAP server is able to successfully authenticate the user, the server returns the bindResponse success message.

9 0.006907 10.2.0.90 10.2.0.201 LDAP 143 bindRequest(3) "CN=TestUser,CN=Users,DC=adw2k3,DC=lab" simple
10 0.008026 10.2.0.201 10.2.0.90 LDAP 110 bindResponse(3) success

The following example shows the LDAP error in bindResponse when the LDAP cannot locate the user DN. The standard LDAP response when it cannot locate an object is data 525. If you encounter this error, verify that the DN returned by the LDAP search is correct.

Note: In some LDAP configuration environments, the data 52e value may be returned instead of the data 525 value.

4 0.000689 10.2.0.90 10.2.0.201 LDAP 153 bindRequest(1) "CN=TestUser,CN=users,DC=adw2k3,DC=lab" simple
5 0.001264 10.2.0.201 10.2.0.90 LDAP 197 bindResponse(1) invalidCredentials (80090308: LdapErr: DSID-0C090334, comment: AcceptSecurityContext error, data 525, vece)

The following example shows the LDAP error in bindResponse when the user password is not valid. The standard LDAP response when it cannot authenticate the account is data 52e. If you encounter this error, verify that the user password is valid.

4 0.001290 10.2.0.90 10.2.0.201 LDAP 152 bindRequest(1) "CN=Administrator,CN=users,DC=adw2k3,DC=lab" simple
5 0.003865 10.2.0.201 10.2.0.90 LDAP 197 bindResponse(1) invalidCredentials (80090308: LdapErr: DSID-0C090334, comment: AcceptSecurityContext error, data 52e, vece)
