K11479: If the session iRule command is used to add binary data to the session table, the data will be corrupted

Known Issue

This is the result of a known issue. If the session iRule command is used to add binary data to the session table, the data will be corrupted. The likely result is that the BIG-IP system will return a TCL error when operating on the corrupted binary data retrieved from the session table.

This issue occurs because the BIG-IP system incorrectly assumes that any data added to the session table is a string.

The expected behavior is for the session iRule command to be able to add and retrieve data to/from the session table regardless of whether the data is a string or a binary value.

In the following example, an iRule ceases to work after the BIG-IP system is upgraded to 10.1.0:

  • A BIG-IP system running a version prior to 10.1.0 is configured with the following iRule:

    rule SOL11479 {
    when CLIENTSSL_CLIENTCERT {
    set cert [SSL::cert 0]
    session add ssl [SSL::sessionid] $cert
    }
    when HTTP_REQUEST {
    set res [session lookup ssl [SSL::sessionid]]
    HTTP::header insert "X-SSL-CLIENT-CRT-SUBJECT" [X509::subject $res]
    }
    }

    Note: The SSL::cert iRule command returns an X.509 certificate in binary format.

    Note: When this iRule is applied to an SSL virtual server, which requests or requires the client to present a valid certificate, the iRule stores the subject of the client's certificate in an HTTP header that can then be read by the back-end servers. For more information about why this iRule caches the client's certificate in the session table, refer to the Additional information section.
  • The iRule is applied to an SSL virtual server which requires the client to present a valid certificate. The virtual server is working as expected; an HTTP header containing the client's certificate subject is appended to each request, for example:

    X-SSL-CLIENT-CRT-SUBJECT: CN=Workstation-01,OU=AskF5,O=F5,L=Seattle,ST=WA,C=US
  • The BIG-IP system is upgraded to BIG-IP 10.1.0.
  • After the upgrade, the virtual server no longer functions, and for each HTTP request it processes the BIG-IP system logs the following error message to the /var/log/ltm file:

    local/tmm err tmm[7058]: 01220001:3: TCL error: SOL11479 <HTTP_REQUEST> - while executing "X509::subject $res"

F5 Product Development tracked this issue as ID 226923, and it was fixed in BIG-IP LTM 11.2.0. For information about upgrading, refer to the BIG-IP LTM release notes.

Workaround

You can work around this issue by converting the binary data to a string before storing the data in the session table. Then, depending on how you intend to use the data after this has been retrieved from the session table, you can convert the string back to a binary value.

For example, you would need to modify the iRule discussed in this Solution as shown below:

rule SOL11479 {
when CLIENTSSL_CLIENTCERT {
set cert [SSL::cert 0]
session add ssl [SSL::sessionid] [b64encode $cert]
}
when HTTP_REQUEST {
set res [session lookup ssl [SSL::sessionid]]
HTTP::header insert "X-SSL-CLIENT-CRT-SUBJECT" [X509::subject [b64decode $res]]
}
}

Additional information

In BIG-IP versions prior to 10.1.0, it is necessary to store the client's certificate in the session table because the SSL::cert iRule command returns information about the client's certificate only during the TCP connection in which the certificate is actually presented. For example, if the client resumes an SSL session, the SSL::cert iRule command does not return any information.

Beginning in BIG-IP 10.1.0, the BIG-IP system automatically caches the client's certificate along with the SSL session ID. Therefore, as of BIG-IP 10.1.0, it is no longer needed to store the client's certificate in the session table.

For example, the iRule discussed in this Solution can be replaced by the following iRule:

rule SOL11479 {
when HTTP_REQUEST {
HTTP::header insert "X-SSL-CLIENT-CRT-SUBJECT" [X509::subject [SSL::cert 0]]
}
}

If it is possible to work around the issue described in this Solution by not storing any data in the session table, F5 recommends that you follow this approach.

For more information, refer to K11482: Change in Behavior: The BIG-IP system automatically caches SSL client certificates.
