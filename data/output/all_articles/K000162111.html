BIG-IP: ip route get command may display management interface when used within a non-default route domain context

Description

When you execute the Linux ip route get <destination_IP> command within a non-default route domain context (after entering the route domain shell via rdsh <RD_ID>), the output may display dev mgmt as the egress interface for certain destination IP addresses. This occurs even when the source IP is correctly selected from the route domain's self-IP pool, and tmsh show net route correctly shows the expected Traffic Management Microkernel (TMM) VLAN interface for that route domain.

For example:


[admin@bigip:Active:In Sync] ~ # rdsh 20
[admin@bigip:Active:In Sync] ~ # ip route get <destination_IP>
<destination_IP> dev mgmt  src <RD20_self_IP>
    cache

Environment

  • BIG-IP Local Traffic Manager (LTM), all versions with route domains configured
  • Multiple route domains configured for VLAN isolation
  • Non-default route domain with self-IPs and associated VLANs
  • rdsh <RD_ID> used to enter route domain shell context

Cause

The BIG-IP system maintains two separate routing subtables:

  • TMM routing subtable — managed by the Traffic Management Microkernel (TMM). This is the authoritative data-plane routing table, viewed with tmsh show net route. Routes are identified with a %<RD_ID> suffix (for example, %20).
  • Linux management routing subtable — managed by the Linux kernel, viewed with ip route, ip route get, or netstat -rn. This table is used for administrative traffic only.

The ip route get command performs a lookup in the Linux kernel routing table, which operates at the OS level and does not have full awareness of BIG-IP's TMM route domain architecture. When used within an rdsh shell context, the command enters the Linux network namespace for that route domain, but the kernel's route resolution for certain destinations may still resolve via the management interface — particularly when:

  • The destination subnet is not directly connected to a TMM VLAN in the kernel's view of that namespace.
  • The kernel falls back to the management default route for the lookup.

This is a cosmetic display artifact of the Linux kernel's routing view and does not represent the actual data-plane forwarding path used by TMM.

Note: If the src address shown in the ip route get output is the correct self-IP from the route domain (not the management IP), TMM's source IP selection logic is functioning correctly, confirming that actual traffic forwarding via TMM is unaffected.

Recommended Actions

  1. Use tmsh show net route as the authoritative source for verifying route domain routing behavior. Routes in the TMM table are identified with the %<RD_ID> suffix. Run the following command:

    tmsh show net route

    Look for entries with %20 (or your route domain ID) to confirm correct VLAN associations.

  2. Verify the route domain configuration:

    tmsh list net route-domain <RD_ID>

  3. To definitively confirm the actual traffic forwarding path, run simultaneous tcpdump captures on both the expected TMM VLAN interface and the management interface while generating traffic to the destination IP:

    tcpdump -nni <expected_tmm_vlan_interface> host <destination_IP> -w /var/tmp/tmm_capture.pcap

    tcpdump -nni mgmt host <destination_IP> -w /var/tmp/mgmt_capture.pcap

    Traffic appearing only on the TMM VLAN interface confirms correct data-plane forwarding.

  4. Do not rely on ip route get for route domain routing verification in multi-route-domain environments. This command reflects the Linux kernel's view, which may not accurately represent TMM's route domain routing logic.
  5. To confirm which route domain context you are in when using rdsh, run the following command:

    ip netns identify

    This returns the current network namespace (for example, rd20). For more information, see K37059707.

Additional Information

  • This behavior is more likely to be observed on the standby unit of a high availability (HA) pair, as the active unit may have floating self-IPs active that result in a different effective TMM routing table.
  • For running userland applications (such as ssh, ping, and curl) in a non-default route domain, use rdexec or rdsh as documented in K13472: Userland applications on a BIG-IP system can connect to hosts in non-default route domains.
  • This behavior is not a bug or configuration error. No corrective action is required if tmsh show net route shows the correct TMM routes and traffic is forwarding as expected.
