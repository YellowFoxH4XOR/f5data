K000157307: VELOS Partition configuration may be wiped after an upgrade to F5OS-C 1.6.4, 1.8.1 or 1.8.2

Type
Support Solution
Published
2025-11-06
Updated
2025-11-10
Applies to
  • F5OS
  • F5OS-C: 1.6.0, 1.6.X, 1.8.X, 1.8.2, 1.8.1, 1.8.0, 1.6.4, 1.6.2, 1.6.1
Source
https://my.f5.com/manage/s/article/K000157307

Description

After a controller upgrade to F5OS-C 1.6.4, 1.8.1 or 1.8.2, a partition's configuration and data can be completely wiped.

When this issue is observed, the partition will prompt for the admin password to be set on initial login after upgrade.

After setting the password and logging in to the partition, it will be observed to have a default configuration; all user-defined configuration has been lost, including tenants.

Environment

  • VELOS system controller upgrade to F5OS-C 1.6.4, 1.8.1 or 1.8.2
  • VELOS partition

Cause

Bug ID 2079113: Partitions created on VELOS v1.1.x will have configuration wiped during controller upgrade to VELOS v1.6.4 or v1.8.1 or later

The partition startup logic in F5OS-C 1.6.4, 1.8.1 or 1.8.2 checks that a partition's three logical volumes have an xfs filesystem on them. It does this using the blkid command.

In F5OS-C prior to 1.2.x, a partition's logical volumes were incorrectly created as thin provisioned pools with the lvcreate --thin option. These volumes will have been carried forward when upgrading.

There is an issue where the blkid command does not detect a filesystem on volumes that have been created in this way.

When the blkid command does not detect a filesystem for those volumes on F5OS-C 1.6.4, 1.8.1 or 1.8.2 during partition startup, the partition is completely wiped.

This problem does not affect partitions that were created on F5OS-C 1.2.x and later. Partition volumes created in F5OS-C 1.2.x onwards are not thin provisioned.

Recommended Actions

This issue will not affect the majority of VELOS installs, so no action will be required in most cases.

Bug ID 2079113 has no fix at the time of this article's publication, but workarounds are available for impacted systems.

Identifying the issue before an upgrade

To identify whether a partition is susceptible to this issue before an upgrade to F5OS-C 1.6.4, 1.8.1 or 1.8.2, examine the output of these commands on each system controller:

lvs
blkid -o value -s TYPE /dev/partition_config/partition<id> # replace with partition ID from 'show partitions'

Affected volumes that are thin-provisioned will have a t attribute and non-empty Data% and Meta% fields in the lvs output.

In this example, partition 1 is unaffected, partition 2 is affected:

[root@controller-1:Active ~]# lvs
LV                VG               Attr       LSize   Pool Origin Data%  Meta%  Move Log Cpy%Sync Convert
partition1        partition_config -wi-ao----  10.00g                                                    
partition2        partition_config twi-aotz--  10.00g             0.00   10.79             <---
export_chassis    partition_image  -wi-ao---- 256.12g                                                    
partition1        partition_image  -wi-ao----  15.00g                                                    
partition1_shared partition_image  -wi-ao----  10.00g                                                    
partition2        partition_image  twi-aotz--  15.00g             0.00   10.47             <---
partition2_shared partition_image  -wi-ao----  10.00g                                                    
root              velocity         -wi-ao---- 338.98g                                                    
swap              velocity         -wi-a-----   1.00g                                                    

The problem affects 2 out of 3 of the partition's volumes. The partition_shared volume is unaffected.

The blkid command will fail to find a filesystem on affected volumes.

For example:

# This is OK / expected

[root@controller-1:Active ~]# blkid -o value -s TYPE /dev/partition_config/partition2
xfs

# No output is returned - problem likely is present

[root@controller-1:Active ~]# blkid -o value -s TYPE /dev/partition_config/partition2
[root@controller-1:Active ~]#

You can also determine whether a partition's volumes were created as thin provisioned by examining the contents of /etc/lvm/archive, looking for the lvcreate invocation that was used to create the partition's volumes.

For example:

# Output similar to the following confirms the partition's config volume was created as thin-provisioned.

[root@controller-1:Active ~]# grep 'lvcreate.*config' /etc/lvm/archive/*
/etc/lvm/archive/partition_config_00002-632898560.vg:description = "Created *before* executing 'lvcreate -L 5120 --thin -n partition2 partition_config'"

Note: It is possible for the partition volumes on only one system controller to be affected, so it is important to check both when working through the above steps.

Workarounds before upgrade

To fix a partition on a system that has not yet been upgraded to F5OS-C 1.6.4, 1.8.1 or 1.8.2, the partition volumes must be deleted and re-created.

Methods for this are:

A) While the partition is running and in an enabled state, PXE boot the standby system controller off the current active one (K000152443), wait for it to clean install, sync the partition configuration and rejoin the openshift cluster. This part of the process should take around 1 hour, but may take longer in some cases.

Verify the partition volumes are 'normal' provisioned with the lvs command, and that the partition is running-standby on the newly PXE booted controller, using the show partitions command.

Fail over to the newly PXE booted controller at the chassis and partition levels and verify that there are no issues.

PXE boot the other controller off the freshly installed one and wait for it too to rejoin the cluster and transition to running-standby in the partition.

An openshift rebuild (K000152701) may be required in some cases if the second PXE-booted controller does not join the cluster successfully. This will add an additional 90 minutes (approximately) to the process.

Finally, when all controllers and blades are ready in the cluster, and the controllers are in a state of running-active|running-standby for the partition, disable and re-enable the partition.

This is a time consuming process overall but it should retain the partition configuration and fix the issue with the volumes. Both controllers have effectively been clean installed while maintaining the system configuration. Partition configuration and tenants will not need to be re-created. The system can now be safely upgraded.

B) Delete the partition and re-create it. A partition backup CANNOT be loaded onto the new partition. The partition configuration will need to be re-created from scratch. UCS can be loaded onto re-created tenants.

You can dump a copy of the partition's configuration for reference, with:

show running-config | nomore

C) Take controller, partition and tenant backups, perform a controller system database reset-to-default, followed by a controller config-restore, then partition config-restore, then restore tenants (load UCS).

Confirming the issue after an upgrade

The problem will occur when the partition starts up after a controller upgrade to F5OS-C 1.6.4, 1.8.1 or 1.8.2.

To confirm whether the issue has occurred after an upgrade, examine the /var/log/sw-util.log file on each system controller.

For example:

# The issue is present - the partition has been wiped

[root@controller-1:Active ~]# grep -A1 'blkid.*partition_config' /var/log/sw-util.log
2025-10-28T10:38:10.156139+01:00 ++ blkid -o value -s TYPE /dev/partition_config/partition2
2025-10-28T10:38:10.158427+01:00 + '[' '' '!=' xfs ']'

# The issue is not present - a filesystem is detected

[root@controller-1:Active ~]# grep -A1 'blkid.*partition_config' /var/log/sw-util.log
2025-10-28T12:05:47.413440+01:00 ++ blkid -o value -s TYPE /dev/partition_config/partition2
2025-10-28T12:05:47.415568+01:00 + '[' xfs '!=' xfs ']'

Recovering an impacted partition after upgrade

To recover an impacted partition after upgrade to F5OS-C 1.6.4, 1.8.1 or 1.8.2, delete and re-create the partition (option 'B' above).

In some cases it may be possible to load a partition backup onto the existing, wiped partition with thin provisioned volumes, restore tenants, then PXE boot the controllers (similar to option 'A' above). However, this would only be recommended if the partition itself was not upgraded. Otherwise, the configuration backup will be from a different version to the target partition and the config-restore operation may fail.

It is NOT sufficient to simply restore a partition backup to the impacted partition, without doing the PXE boots afterwards to re-create the volumes. The problem will occur again the next time the partition is started up (e.g., during a subsequent upgrade).

Open a case with F5 Support referencing this article if there are any questions or concerns about the recommended actions described above.

Additional Information

Once a partition has "normal" (non thin-provisioned) volumes, the "wiping" issue will no longer occur on subsequent partition startups / upgrades.

VELOS partition volumes created on F5OS-C 1.2.x or later will already have normal volumes and will be unaffected by this issue. The problem will typically affect older VELOS installs that have been upgraded up over the years, having been initially created under F5OS-C 1.1.x.
