Security Advisory Description

Vulnerability in the Oracle Java SE, Oracle GraalVM for JDK, Oracle GraalVM Enterprise Edition product of Oracle Java SE (component: Compiler). Supported versions that are affected are Oracle Java SE: 8u511b33-perf, 17.0.21.0.3, 21.0.13.0.3, 25.0.5.0.3, 27.0.1.0.3; Oracle GraalVM for JDK: 17.0.21.0.3 and 21.0.13.0.3; Oracle GraalVM Enterprise Edition: 21.3.20.0.3. Difficult to exploit vulnerability allows unauthenticated attacker with network access via multiple protocols to compromise Oracle Java SE, Oracle GraalVM for JDK, Oracle GraalVM Enterprise Edition. Successful attacks of this vulnerability can result in takeover of Oracle Java SE, Oracle GraalVM for JDK, Oracle GraalVM Enterprise Edition. Note: This vulnerability can only be exploited by supplying data to APIs in the specified Component without using Untrusted Java Web Start applications or Untrusted Java applets, such as through a web service. CVSS 3.1 Base Score 8.1 (Confidentiality, Integrity and Availability impacts). CVSS Vector: (CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H). (CVE-2026-114938)

Security Advisory Recommended Actions

Using BIG-IP Advanced WAF, BIG-IP ASM, F5 WAF for NGINX, and NGINX App Protect WAF signatures

F5 recommends the following actions to mitigate the vulnerability for your backend pool members:

  • Use attack signatures
  • Create an iRule to reject Java4Shell style requests

Use attack signatures

If you are using BIG-IP Advanced WAF, BIG-IP ASM, F5 WAF for NGINX, or NGINX App Protect WAF to protect your backend pool members, you can mitigate this vulnerability for your backend pool members by using the following attack signature enabled in Blocking mode:

Create an iRule to reject Java4Shell style requests

This iRule inspects incoming HTTP requests for malformed Base64 values matching the input shape described for the Java4Shell trigger, such as 64 "A" characters followed by =. It rejects any request that matches one of three conditions:

  • An Authorization: Basic header, where the credential is a block of 64, 128, or 256 Base64 (standard or URL-safe) characters followed by an odd-length tail (=, ==, ===, x=, x==, xx=).
  • An Authorization: Bearer header, where the token uses the same block and tail pattern. The block may be the whole token, or may sit within the first three dot-separated segments (for example header.payload.signature), and it must end at the end of the value or at a dot (.).
  • A SAMLRequest or SAMLResponse parameter in the query string, where the value is a block of 64, 128, or 256 Base64 characters (encoded %2B and %2F count as one character) followed by an odd-length tail using = or %3D. The value must end at "&" or the end of the query string.

Each condition uses its own regular expression and is matched independently. Matching requests are logged without the credential or parameter value. The log line records which condition fired (Authorization Basic, Authorization Bearer, or SAML query), the client IP, and the length of the matched value. The request is then rejected with either an HTTP 400 response or a TCP reset, depending on the option left uncommented in the iRule. The iRule runs at HTTP_REQUEST priority 100, so it executes ahead of other iRules on the virtual server.

This iRule does not inspect SAML values in a POST body or Base64 in other headers or cookies. The underlying OpenJDK bug on affected systems needs to be updated. To create the iRule and associate it with a virtual server, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > iRules > iRule List.
  3. Select Create.
  4. Enter a name for the iRule.
  5. For the Definition, enter the following code. You can disable logging as needed by commenting out the line with #:
    when RULE_INIT {
    # Tcl ARE max repeat count is 255, so the original {256} is written as (?:...{128}){2}.
    # Everything else follows the three original signatures, one regex each.
    # @B@ = [a-z0-9+/] @U@ = [\w\-] @S@ = (?:[a-z0-9+/]|%2B|%2F) (-nocase applied at match time)
    # re1: Authorization: Basic (header value only)
    set static::re_basic \
        [string map [list @B@ {[A-Za-z0-9+/]} @U@ {[A-Za-z0-9_-]}] \
        {^[ ]*Basic[ ]+(?:(?:@B@{64}|@B@{128}|(?:@B@{128}){2})(?:=|==|===|@B@=|@B@==|@B@{2}=)|(?:@U@{64}|@U@{128}|(?:@U@{128}){2})(?:=|==|===|@U@=|@U@==|@U@{2}=))$}]

    # re2: Authorization: Bearer (header value only)
    set static::re_bearer \
        [string map [list @B@ {[A-Za-z0-9+/]} @U@ {[A-Za-z0-9_-]}] \
        {^[ ]*Bearer[ ]+(?:(?:@B@+\.){0,2}(?:@B@{64}|@B@{128}|(?:@B@{128}){2})(?:=|==|===|@B@=|@B@==|@B@{2}=)|(?:@U@+\.){0,2}(?:@U@{64}|@U@{128}|(?:@U@{128}){2})(?:=|==|===|@U@=|@U@==|@U@{2}=))(?:$|\.)}]

    # re3: SAMLRequest / SAMLResponse parameter (query string)
    set static::re_saml \
        [string map [list @S@ {(?:[A-Za-z0-9+/]|%2B|%2F)} @T@ {(?:=|%3D)} @U@ {[A-Za-z0-9_-]}] \
        {(?:^|[?&])SAML(?:Request|Response)=(?:(?:@S@{64}|@S@{128}|(?:@S@{128}){2})(?:@T@{1,3}|@S@@T@{1,2}|@S@{2}@T@)|(?:@U@{64}|@U@{128}|(?:@U@{128}){2})(?:@T@{1,3}|@U@@T@{1,2}|@U@{2}@T@))(?:&|$)}]
}

when HTTP_REQUEST priority 100 {
    set hit ""
    set len 0

    # 1 + 2. Authorization header: Basic and Bearer, each with its own regex
    foreach auth [HTTP::header values Authorization] {
        if { [regexp -nocase $static::re_basic $auth] } {
            set hit "Authorization Basic"
            set len [string length $auth]
            break
        }
        if { [regexp -nocase $static::re_bearer $auth] } {
            set hit "Authorization Bearer"
            set len [string length $auth]
            break
        }
    }

    # 3. SAMLRequest / SAMLResponse in the query string
    if { $hit eq "" } {
        set q [HTTP::query]
        if { [string match -nocase {*SAMLRe*} $q] && [regexp -nocase $static::re_saml $q] } {
            set hit "SAML query"
            set len [string length $q]
        }
    }

    if { $hit ne "" } {
        log local0. "Rejected possible Java4Shell trigger ($hit) from [IP::client_addr] (len=$len)"

        # Option A: HTTP 400 then close
        HTTP::respond 400 content "Bad Request" Connection close

        # Option B: TCP reset (comment out Option A, uncomment these two)
        #reject
        #event disable all
        return
    }
}
  6. Select Finished.
  7. Go to Local Traffic > Virtual Servers > Virtual Server List, and select the virtual server.
  8. Under Resources > iRules, select Manage, then select the created iRule from the Available list and move it to the Enabled list.
  9. Select Finished.
  10. Monitor the /var/log/ltm file for log messages containing "Rejected possible Java4Shell trigger." For example:

    tmm[26733]: Rule /Common/java4shell : Rejected possible Java4Shell trigger (Authorization Basic) from 10.10.10.13 (len=71)
    tmm2[26733]: Rule /Common/java4shell : Rejected possible Java4Shell trigger (Authorization Bearer) from 10.10.10.13 (len=79)
    tmm2[26733]: Rule /Common/java4shell : Rejected possible Java4Shell trigger (SAML query) from 10.10.10.13 (len=79)
