Topic

The 'class' iRules command does not honor route domain specifications within an IP class.

Description

If you use an IP class to store a collection of IP addresses and these IP addresses are in a route domain other than 0 (the default route domain), the route domain information is ignored and the class iRules command fails to match the entries in the class.

For example:

  • A BIG-IP system is configured with the following IP class:

    class my_hosts {
       {
          host 10.0.0.20%10
          host 10.0.0.21%10
          host 10.0.0.22%10
          host 10.0.0.23%10
          host 10.0.0.24%10
       }
    }

  • The BIG-IP system is also configured with the following iRule, which compares the IP address of the client with the IP addresses in the my_hosts class:

    rule my_irule {
      when CLIENT_ACCEPTED {
        if {[class match [IP::client_addr] equals my_hosts]}{
          log local0. "[IP::client_addr] matched against the my_hosts class"
    }
    }
    }

  • If a match is found, the iRule logs a message. However, because of the issue described in this article, the class iRules command never returns a match, even if the IP address of the client is in the my_hosts class.

Note: This issue also affects the matchclass iRules command, which is the equivalent of the class match iRules command.

Note: The Configuration utility and the TMOS Shell tmsh refer to classes as data groups.

Workaround

You can work around this issue in the following ways:

Note: Both workarounds have a common limitation: you cannot match the IP address of the client against a network address (for example, 192.168.1.50%10 against 192.168.1.0%10 255.255.255.0).

Replacing the IP class with a string class

You can store all necessary IP addresses in a string class instead of an IP class. By doing so, the class iRules command correctly matches IP addresses in a route domain other than 0. For example, you can replace the my_hosts class mentioned in this article with the following string class:

class my_hosts_string_class {
   {
      "10.0.0.20%10"
      "10.0.0.21%10"
      "10.0.0.22%10"
      "10.0.0.23%10"
      "10.0.0.24%10"
   }
}

Replacing the IP class with a series of 'or' statements in the iRule

You can avoid using a class by implementing a series of or statements in your iRule. Because the class iRules command is not used, the iRule correctly matches IP addresses in a route domain other than 0. For example, instead of using the iRule and the class mentioned in this article, you can use the following iRule:

rule my_irule_workaround {
  when CLIENT_ACCEPTED {
    if { [IP::addr [IP::client_addr] equals 10.0.0.20%10] or
         [IP::addr [IP::client_addr] equals 10.0.0.21%10] or
         [IP::addr [IP::client_addr] equals 10.0.0.22%10] or
         [IP::addr [IP::client_addr] equals 10.0.0.23%10] or
         [IP::addr [IP::client_addr] equals 10.0.0.24%10] }{
      log local0. "[IP::client_addr] matched against the provided list of IP addresses"
}
}
