Description

A strange behavior observed when source-address persistence profile is associated with a virtual server which is configured using source/destination address list.

Traffic connection to the backend server is getting stalled and a wrong persistence record is created. This behavior is not observed when source/destination address list was removed from the VS.

ltm virtual /Common/Example_A {
    ip-protocol tcp
     persist {
        Example_source_addr { <====
            default yes
        }
    }
    <.......>
    traffic-matching-criteria /Common/Example_A_Address_List <==== 
    translate-address enabled
    translate-port enabled
}

Source/Destination shared address list attached to the VS

ltm traffic-matching-criteria Example_A_Address_List {
    destination-address-inline Example_A_Dest <==== 
    <......>
    source-address-list Example_A_Source      <==== 
}

 

Environment

  • Connection stalling
  • Source address affinity persistence profile
  • Traffic-Matching-Criteria using shared source/destination address list

Cause

  • Bug ID 912293: Persistence might not work properly on virtual servers that utilize address lists

Recommended Actions

Enable match-across-virtual-servers option in the source address persistence profile using the below given command, replace <Name of the persistence profile> with the actual name

tmsh modify ltm persistence source-addr <Name of the persistence profile > match-across-virtuals enabled

Note: Enabling match-across-virtual-server might might affect the behavior of other virtual servers in the configuration that utilize persistence, for more information refer K84104359: Source Address Persistence with match-across-virtuals not working expectedly

Additional Information

  • Match-Across-Virtual-Servers specifies that all persistent connections from the same client IP address, will go to the same node, the default setting is disabled.
  • When any Match-Across-Servers option is enabled, the BIG-IP system will search for a persistence record through the table, and the record selected might be created by a different virtual servers whose persistence profile doesn't have any Match-Across-Servers options enabled, refer K30369344: Match Across Options In Persistence Profiles May Match Any Persistence Entries In Persistence Table
