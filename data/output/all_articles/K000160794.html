Description

When multiple Client SSL profiles are attached to a single virtual server in BIG-IP LTM, and those profiles have certificates with overlapping Subject Alternative Names (SANs) and no explicit Server Name configured, the SSL certificate selected for a given hostname may change unpredictably. This can result in inconsistent certificate presentation for the same requested hostname, especially after adding, removing, or re-adding profiles. The selection order is not based on GUI-visible order, alphabetical order in the configuration, or most-recently-added profile, and there is no CLI or GUI method to view or control the internal order directly. 

Environment

  • Product: BIG-IP LTM
  • Multiple client SSL profiles attached to a single virtual server
  • At least two profiles with certificates containing the same SAN (e.g., *.example.com)
  • No explicit Server Name configured in the client SSL profiles
  • SNI (Server Name Indication) enabled on at least one profile
  • Profiles added, removed, or re-added to the virtual server during runtime
  • TMM restarts or configuration reloads

Cause

When multiple Client SSL profiles with overlapping SANs are attached to a virtual server and no explicit Server Name is set, BIG-IP LTM selects the first matching profile in TMM’s internal registration list. This internal order is determined by the sequence of profile attachment and TMM’s configuration load process:

  • After a full TMM restart or config reload, profiles are sorted alphabetically by name per virtual server.
  • When profiles are added or removed on a running system, newly added profiles are appended to the end of the list.
  • The selection is not based on GUI order, alphabetical order in the configuration, or most-recently-added profile, but strictly on TMM’s internal list, which is not user-visible or user-controllable.
  • This leads to non-deterministic and unsupported behavior when profiles with overlapping SANs are used without explicit SNI mapping.

Answer/Recommended Actions

To ensure deterministic and predictable SSL certificate selection:

  1. Configure an explicit Server Name in each client SSL profile for the intended hostname. This gives the profile the highest selection precedence.
  2. Alternatively, remove overlapping SAN entries from certificates so that only one profile matches a given hostname.
  3. Avoid relying on the order of profile attachment or removal for certificate selection.
  4. Do not use multiple Client SSL profiles with identical SANs/CNs without explicit SNI mapping.
  5. If a single SSL profile is used on multiple virtual servers, TMM maintains a separate entry for each virtual server.
  6. There is no supported method to control or view the internal profile order in TMM memory.

Additional Information

  • Each virtual server maintains its own independent list of SSL profiles in TMM memory.
  • After a full TMM restart/config reload, profiles are sorted alphabetically by name per virtual server.
  • On a running system, newly added profiles are appended to the end of the internal list for that virtual server.
  • Removing and re-adding a profile always resets it to the last position in that virtual server's list.
  • The same SSL profile can be at different positions in different virtual servers, depending on the add/remove history.
  • When a SAN-level tie occurs, TMM picks the profile at the lowest position (first) in the internal list.
  • There is no CLI or GUI to view or control these position numbers; it is an internal TMM detail.
