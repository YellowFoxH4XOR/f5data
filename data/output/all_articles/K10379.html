Topic

In BIG-IP 9.0.0 and later, you can create a pool member using a local virtual server IP address. However, the BIG-IP does not respond to its own Address Resolution Protocol (ARP) requests for locally-hosted virtual server addresses, and thus is unable to establish a network connection to a locally-hosted virtual server. As a result, if you add a locally-hosted virtual server to a BIG-IP load balancing pool, no traffic will ever be sent to that pool member, as it is not possible for the system to load balance traffic to that pool member.

Note: Since non-local virtual servers (virtual servers configured on another system) are indistinguishable from any other IP destination, the BIG-IP system is fully capable of monitoring and load balancing traffic to virtual servers that are hosted on other systems as if they were normal pool members. This configuration is commonly used in layered high-availability environments. For example, a BIG-IP WebAccelerator or BIG-IP ASM system may define a virtual server that references a pool containing a second virtual server that is hosted on the next hop redundant BIG-IP LTM system.

Beginning in BIG-IP 9.4.0, you can specify a local virtual server as a load balancing target for another virtual server by using the virtual iRules command. To direct traffic to the second virtual server, apply an iRule, which uses logic similar to the following example, to the first virtual server (the one that will accept client connections):

when HTTP_REQUEST {
  if { [HTTP::uri] contains "param=x" } {
    virtual VS_2
  }
}

Note: For more information about the virtual iRules global command and other iRules elements, refer to the iRules Home on F5 CloudDocs.
