Known Issue

This is the result of a known issue. If you specify an AES key in an iRule that has an invalid character length or contains an invalid hexadecimal value, TMM will crash.

You can specify AES keys in iRules by using the following syntax and requirements:

AES::key ["128" | "192" | "256"]

For example, the following syntax specified an AES key:

when RULE_INIT {
 set ::key [AES::key]
}

The AES key portion is composed of a number of characters specific to the bit value. The characters must be within the following hexadecimal range:

0123456789ABCDEF

The AES key must also contain the following number of characters to fulfill the bit requirement:

Note: One character is composed of 4 bits.

Bit StrengthNumber of Characters Required
12832
19248
25664

The following example sets an AES key of 128 bits, containing 32 characters in hexadecimal form:

set ::key "AES 128 0123456789abcdef0123456789abcdef"

The following example will fail as it contains the invalid character g in the key representation:

set ::key "AES 128 g0123456789abcdef0123456789abcdef"

This following example will fail as it does not contain 64 characters to fulfill the 128 bit strength requirement:

set ::key "AES 128 0123456789abcdef"

F5 Product Development tracked this issue as CR68290, CR68291, and CR65733, and it was fixed in BIG-IP LTM versions 9.1.3, 9.2.4, 9.3.0, and 9.4.0. For information about upgrading, refer to the BIG-IP LTM release notes.
