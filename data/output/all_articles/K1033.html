Topic

HTTP application health monitors are used to verify the content that is returned by an HTTP request. To configure an HTTP monitor to send a POST request, configure the health monitor Send string using one of the examples specific to your software version.

BIG-IP 10.2.0 and later

To send an HTTP 1.0 request, configure the Send string to appear similar to the following example:

POST /MyApp.cgi HTTP/1.0\r\nContent-Length:15\r\n\r\nD1=asdf&D2=jklm

To send an HTTP 1.1 request, configure the Send string to appear similar to the following example:

POST /MyApp.cgi HTTP/1.1\r\nHost: host.domain.com\r\nContent-Length:15\r\nConnection: Close\r\n\r\nD1=asdf&D2=jklm

BIG-IP 10.2.0 requests with Basic Authentication

Starting in BIG-IP 10.2.0, if Basic Authentication is enabled by adding a user name and password to the monitor configuration, the BIG-IP system appends the Authorization header and a double CR/LF sequence after the last character in the Send string.

Health checks that require a message body, such as POST data, with Basic Authentication can be configured by creating a custom external monitor that uses the cURL utility to process the POST request.

For more information about creating external monitors, refer to HTTP Monitor cURL Basic POST on DevCentral.

Alternatively, you may generate an encrypted auth string by performing the following procedure:

  1. Log in to the BIG-IP command line.
  2. Generate an encrypted auth string by using the following syntax:

    echo -n 'username:password' | base64

    For example, if you used the user name f5 and the password f5passwd, the output would appear as follows:

    ZjU6ZjVwYXNzd2Q=

  3. To create an HTTP 1.0 post, use the following syntax:

    POST /MyApp.cgi HTTP/1.0\r\nContent-Length:10\r\nAuthorization: Basic <string>\r\n\r\n0123456789

    In this syntax, note the following:

    • <string> is the output from step 2

    For example:

    POST /MyApp.cgi HTTP/1.0\r\nContent-Length:10\r\nAuthorization: Basic ZjU6ZjVwYXNzd2Q=\r\n\r\n0123456789

  4. To create an HTTP 1.1 post, use the following syntax:

    POST /MyApp.cgi HTTP/1.1\r\nHost: host.domain.com\r\nConnection: Close\r\nContent-Length: 10\r\nAuthorization: Basic <string>\r\n\r\n0123456789

    In this syntax, note the following:

    • <string> is the output from step 1

    For example:

    POST /MyApp.cgi HTTP/1.1\r\nHost: host.domain.com\r\nConnection: Close\r\nContent-Length: 10\r\nAuthorization: Basic ZjU6ZjVwYXNzd2Q=\r\n\r\n0123456789

In these examples, your content length of 10 would match the length of your message body, which in this example is 0123456789.

You do not need to specify a user name and password in the monitor configuration when performing this workaround.

BIG-IP 9.4.0 to 10.1.x

To send an HTTP 1.0 request, configure the Send string to appear similar to the following example:

POST /MyApp.cgi HTTP/1.0\r\n\r\nD1=asdf&D2=jklm

To send an HTTP 1.1 request, configure the Send string to appear similar to the following example:

POST /MyApp.cgi HTTP/1.1\r\nHost: host.domain.com\r\nConnection: Close\r\n\r\nD1=asdf&D2=jklm

BIG-IP 9.2.x and 9.3.x

To send an HTTP 1.0 request, configure the Send string to appear similar to the following example:

POST /MyApp.cgi HTTP/1.0\r\n\r\nD1=asdf&D2=jklm

To send an HTTP 1.1 request, configure the Send string to appear similar to the following example:

POST /MyApp.cgi HTTP/1.1\r\nHost: host.domain.com\r\nConnection: Close\r\n\r\nD1=asdf&D2=jklm

BIG-IP 9.0.x and 9.1.x

To send an HTTP 1.0 request, configure the Send string to appear similar to the following example:

POST /MyApp.cgi HTTP/1.0\n\nD1=asdf&D2=jklm

To send an HTTP 1.1 request, configure the Send string to appear similar to the following example:

POST /MyApp.cgi HTTP/1.1\nHost: host.domain.com\nConnection: Close\n\nD1=asdf&D2=jklm

Important: In BIG-IP versions prior to 10.2.0, the bigd process automatically appends one or two CR/LF sequences to the end of the monitor Send string. The HTTP 1.1 specification RFC2616 states in part: "an HTTP/1.1 client must not preface or follow a request with an extra CRLF." As a result, HTTP 1.1 POST requests sent by a BIG-IP system running software prior to version 10.2.0 are not RFC-compliant, and your servers may not respond as expected. If you are unable to upgrade to version 10.2.0 or higher, you can create a custom external monitor that is RFC-compliant.
