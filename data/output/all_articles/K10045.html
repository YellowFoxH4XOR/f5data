Issue

The Portal Access Web Applications feature provides remote access to a variety of web-based applications. To ensure that web application traffic routes through the FirePass controller, Portal Access utilizes a high performance reverse-proxy engine to rewrite HTML, Cascading Style Sheet (CSS), JavaScript, Java Applet, and Adobe Flash content. 

While the reverse-proxy engine rewrites content correctly in most cases, in some instances the rewritten code may cause the application to perform incorrectly through Portal Access. If an application does not load or perform correctly through a Portal Access Web Application favorite, perform the following steps to troubleshoot the issue:
 
  1. Access the application from different clients and browsers directly, bypassing the FirePass controller. If the application does not perform as expected from all clients and browsers, resolve any issues before proceeding to the next step.
  2. If you are running FirePass version 6.x or later, ensure that the Allow list field configured for the web application favorite contains all URLs required to access the application.

    Note: To view the Allow list for a web application favorite, navigate to the Portal Access: Web Applications: Resources page and select the appropriate resource group from the Resource Group menu at the top of the page. Select the name of the favorite, and then view the URLs configured in the Allow list field.

    For example, if the Allow list is set to http://www.example.com/*, but the page http://www.example.com refreshes to http://www1.example.com, http://www.example.com:8080, or https://www.example.com, access will be denied. Similarly, if you allow access to http://www.example.com/*, but the page http://www.example.com includes links or images on http://images.example.com, users cannot access those links or images.
     
  3. If the application is completely inaccessible through Portal Access, proceed to the next step. If the application partially loads, but one or more features do not function properly, skip to Step 6.
     
  4. If the application allows access by IP address, configure a new Portal Access favorite using the IP address of the application instead of the hostname. For example:

    http://192.168.16.100/training/tr1/day1.html

    If this step resolved the issue, you must ensure that the name servers configured for FirePass can resolve the application’s hostname if you want the favorite to reference the hostname instead of the IP address. Alternately, you can configure a static hostname in FirePass to statically map the hostname to the IP address (not recommended).

    Note: Name servers are configured on the Device Management: Configuration: Network Configuration page under the DNS tab. Static hostnames are configured on the Device Management: Configuration: Network Configuration page under the Hosts tab. If you change a setting under the DNS or Hosts tab, you must finalize the change under the Finalize tab before the change will take effect.

    If this step did not resolve the issue, or if the application does not allow access by IP address, proceed to the next step.
     
  5. Configure a Network Access connection for access to the application.

    Note: Network Access connections are configured on the Network Access: Resources page. For instructions about configuring a Network Access connection, refer to the FirePass Controller Administrator Guide.

    If you enabled split tunneling for the connection under the Client Settings tab, ensure that the IP address or subnet of the web application server is included in the LAN address space field. Additionally, ensure that the name servers configured under the DNS tab can resolve the hostname of the application.

    If the application is not accessible through the Network Access connection, resolve the connectivity issue between FirePass and the application server before proceeding to the next step. For example, ensure that traffic can route between the FirePass controller and the application server, and that there is no firewall blocking the traffic between the FirePass controller and the application server.
     
  6. Configure a new Portal Access favorite using the simplest URL and fully qualified domain name (FQDN) of the application.

    For example:

    http://www1.example.com/training/tr1/day1.html

    For troubleshooting purposes, do not enable any auto-logon features or configure session variables in the URL. Test this favorite from the actual FirePass webtop and not a customized webtop (also referred to as an Intranet Webtop). If the application works properly, enable additional features one by one so that you can isolate which feature is causing the issue.

    If the application still does not work properly, continue to use the simplest URL for testing in the following steps. Additionally, continue to test the favorite from the FirePass webtop and not from a customized webtop.
     
  7. If you are running a Portal Access certified application, refer to the FirePass Release Notes and the AskF5 Knowledge Base to determine if there are any known issues or configuration requirements for your application.

    Note: Starting in FirePass version 6.0.2, Portal Access certified applications are listed in the Certified applications for Portal Access Web Applications feature section of the FirePass Release Notes. For previous versions of FirePass software, this information can be found in the Configuring web applications on the FirePass controller section of the FirePass Administrator Guide.

    Additionally, refer to the F5 Deployment Guides page to determine if there is a deployment guide for your application.
     
  8. On the Portal Access: Web Applications: Caching and Compression page, note all settings currently configured. The following steps will modify these settings. You should note your current settings so that you can revert to back to them later.

    Important: Performing the following steps will affect all Portal Access web applications, and will cause a brief service disruption for all users each time you restart the FirePass services. Additionally, these steps may significantly increase the load on the FirePass controller. Perform these steps at your own discretion.

    On the Portal Access: Web Applications: Caching and Compression page, enable the following settings one at a time. After changing each setting, click the service restart link and then the Restart button to restart the FirePass services. Test the application from the webtop before enabling the next setting.
    • Clear the Enable Dynamic Cache on FirePass check box, if selected
    • Clear the Enable Compression check box, if selected
    • Select the Don't cache anything, except Style Sheets and Javascript includes option button, if not already selected

    If the application functionality does not improve after configuring the above settings, revert to your previously configured caching and compression settings. You’ll need to perform another service restart after configuring your previous settings.

    If you decide to keep any of the new settings, test all other Portal Access Web Application favorites configured on the FirePass controller to ensure that their functionality is not adversely affected by the change.
     
  9. On the Portal Access: Web Applications: Content Processing page under the Global Settings tab, note all settings currently configured. The following steps will modify these settings. You should note your current settings so that you can revert to back to them later.

    Important: Performing the following steps will affect all Portal Access web applications, and will cause a brief service disruption for all users each time you restart the FirePass services. Perform these steps at your own discretion.

    On the Portal Access: Web Applications: Content Processing page under the Global Settings tab, enable the following settings one at a time. After changing each setting, click the service restart link and then the Restart button to restart the FirePass services. Test the application from the webtop before enabling the next setting.

    Note: Not all of the following options are present on all versions of FirePass software. If you cannot locate a particular option for your version of FirePass software, disregard that option.
    • Clear the Compatibility Mode check box, if selected
    • Select the Automatically patch Java Applets check box, if not selected
    • Select the Process content of the FP_DO_NOT_TOUCH element check box, if not selected
    • Select the Do not block cookies at FirePass, pass them to the browser for specified URL patterns check box, if not selected, and enter an asterisk ( * ) character in the text field below this check box

      Note: If changing this setting resolves the issue, you should replace the asterisk character with a comma-separated list of URLs specific to the application.
    • Select the Automatically add websites that require client side cookie manipulation check box, if not selected
    • Select the Obfuscate cleartext cookies check box, if not selected
    • If the application uses Java, enter an asterisk ( * ) character in the text box in the Java Byte Code Rewriting section

      Note: If changing this setting resolves the issue, you should replace the asterisk character with a comma-separated list of URLs specific to the application.
       
    If the application functionality does not improve after configuring the above settings, revert to your previously configured content processing settings. You must perform another service restart after configuring your previous settings.

    If you decide to keep any of the new settings, test all other Portal Access Web Application favorites configured on the FirePass controller to ensure that their functionality is not adversely affected by the change.
     
  10. If the previous steps did not resolve the issue, enable the minimal content-rewriting bypass feature for the application.

    Note: For instructions, refer to K4746: Overview of the Minimal Content-Rewriting Bypass feature.
     
  11. If the application still has some minor features that are not functioning through Portal Access, proceed to the following steps.

    If the application still has significant issues when accessed through Portal Access, consider an alternate access method, such as a Network Access connection or an Application Tunnel for access to the application.
  12. Access the application directly from a client, bypassing the FirePass controller. On the client, perform an HTTP trace so that you can view each successful request and response exchanged between the client and server.

    Note: There are many tools available for performing HTTP traces, such as Live HTTP Headers and HTTPWatch.
     
  13. Perform a Web Applications engine trace while the client accesses the application through Portal Access. After collecting the trace data, compare the back-end response (the response sent from the application server to FirePass) with the front-end response (the response sent from FirePass to the client).

    Note: For instructions about performing a Web Applications engine trace, refer to K4879: Overview of the Web Applications engine trace feature.
     
  14. Perform two network packet captures on the FirePass controller. For the first packet capture, capture packets on the interface which faces the client while the client accesses the application through Portal Access. For the second packet capture, capture packets on the interface which faces the application server while the client accesses the application through Portal Access.

    Note: For information about performing a network packet capture, refer to K9704: Capturing and viewing packets. You can view the packet capture data using freely available tools such as WireShark or tcpdump.
     
  15. Review the data you collected in Steps 12 through 14 to determine which parts of the source code are modified by FirePass, and which modifications are causing the issues.

    If a search-and-replace function can resolve the issues caused by the modifications, create a Web Applications content processing script to rewrite the affected code. When configuring the script, you typically want to select Post-process response data (after content patching) from the Processing menu.

    Note: For instructions about configuring a content processing script, refer to K9688: Overview of Web Applications content processing scripts.
     
  16. If the previous steps did not resolve the issue, contact F5 Networks Technical Support and provide the data you collected in Steps 12 through 14. Additionally, provide any relevant screenshots.

    For example:

    • A screenshot displaying a Java or JavaScript error
    • A screenshot displaying the affected page when accessed through Portal Access, and another screenshot displaying the same page when accessed directly (bypassing FirePass)
    • Screenshots of the Portal Access favorite configuration page and the Portal Access global configuration pages
