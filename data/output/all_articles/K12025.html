Topic

When an HTTP profile with RAM Cache enabled is applied to a virtual server, the clientside connection count for that virtual server may increase. This occurs even though serverside traffic is significantly reduced, as expected. This behavior is intentional; it is a side-effect of the BIG-IP LTM RAM Cache's HTTP/1.0 stepdown for serverside requests.

Note: For more information about the HTTP version stepdown when RAM Cache is enabled, refer to K10480: Enabling the BIG-IP HTTP cache on a virtual server causes all server-side requests for that virtual server to use the HTTP/1.0 protocol.

When HTTP Keep-Alive connections are used, the Content-Length header is used to determine when a response is complete. However, if the content length is not known in advance, as for many dynamic pages, HTTP/1.1 supports a chunked transfer coding mechanism where a response is served in pieces. When chunked transfer encoding is used, the end of the response and availability of the connection for re-use is indicated when the server sends a 0-byte chunk sent after sending the last of the data.

When LTM RAM Cache is applied to a virtual server, the serverside request is stepped down to HTTP version 1.0. Since HTTP 1.0 does not support chunked transfer encoding, the end of any serverside response which lacks a Content-Length header is indicated by the server closing the connection. When this occurs, the clientside connection is also closed, forcing the client to open a new connection for subsequent requests.

Note: The BIG-IP WebAccelerator system closes the clientside connection even if the client requested a Keep-Alive connection using the Connection: Keep-Alive header. The BIG-IP WebAccelerator system closes the connection by including a Connection: close header in the response, followed by a FIN packet.
