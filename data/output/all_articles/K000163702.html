Description

An F5 Distributed Cloud Observability HTTP Monitor reports:

remote error: tls: handshake failure

The error occurs when the monitor cannot complete a compatible TLS negotiation with the monitored HTTPS endpoint.

A request from another client, such as curl, may still succeed because different clients can use different TLS protocol versions, cipher suites, extensions, SNI behavior, and certificate-validation settings.

Environment

 

  • Product: F5 Distributed Cloud
  • Feature: Observability HTTP Monitor
  • Protocol: HTTPS
  • The target may support only legacy TLS cipher suites or key-exchange methods.

Cause

TLS handshake can fail when the monitor and the HTTPS endpoint cannot agree on the parameters required to establish a secure session. Common causes include:

  1. No common TLS protocol version
    The endpoint may allow only an older or otherwise unsupported TLS version.
  2. No common cipher suite
    The endpoint may be restricted to legacy cipher suites that are not supported by the monitor.
  3. Legacy RSA key exchange
    The endpoint may offer only static-RSA key-exchange cipher suites or may not offer cipher suites that provide Forward Secrecy.
  4. Incorrect or missing SNI configuration
    The endpoint may host multiple HTTPS sites and require Server Name Indication to select the correct certificate and virtual host.
  5. Certificate or hostname mismatch
    The certificate presented by the endpoint may not match the hostname configured in the monitor.
  6. Invalid, expired, or incomplete certificate chain
    The endpoint may present an expired certificate, an untrusted certificate, or an incomplete certificate chain.
  7. Mutual TLS requirements
    The endpoint may require a client certificate that the Observability HTTP Monitor does not provide.
  8. TLS inspection or security-device interference
    A firewall, reverse proxy, WAF, or other TLS-intercepting device may reject the monitor’s TLS ClientHello or terminate the handshake.
  9. Origin-side TLS policy restrictions
    The endpoint may reject connections based on client capabilities, TLS extensions, security policy, or source-address restrictions.

The absence of ALPN by itself is not necessarily the cause of a TLS handshake failure. The TLS protocol, cipher-suite, certificate, SNI, and server-policy settings should be reviewed together.

Answer/Recommended Actions

1. Review the HTTPS endpoint’s TLS configuration.
2. Enable a supported TLS 1.2 and/or TLS 1.3 configuration.
3. Ensure that the endpoint supports modern cipher suites, preferably including cipher suites that provide Forward Secrecy.
4. Avoid restricting the endpoint to legacy static-RSA key-exchange cipher suites.
5. Verify that the certificate:
    * Matches the monitored hostname.
    * Is currently valid.
    * Includes the required intermediate certificates.
    * Is issued by a trusted certificate authority.
6. Confirm that the endpoint correctly supports SNI for the monitored hostname.
7. Confirm whether the endpoint requires mutual TLS or a client certificate.
8. Review firewall, WAF, reverse-proxy, and TLS-inspection policies that could reject connections from F5 Distributed Cloud monitoring locations.
9. Retest the endpoint using the exact hostname configured in the Observability HTTP Monitor.
10. If multiple virtual hosts or TLS configurations exist, verify that the hostname, SNI value, certificate, and application endpoint all correspond to the same service.

Validation

After the endpoint configuration is updated:
1. Confirm that the endpoint offers at least one TLS protocol and cipher-suite combination compatible with modern clients.
2. Confirm that the correct certificate is returned for the monitored hostname.
3. Confirm that the complete certificate chain is available.
4. Confirm that the endpoint accepts connections from the applicable F5 Distributed Cloud monitoring locations.
5. Verify that the Observability HTTP Monitor reports the endpoint as healthy.

Additional Information

The Observability HTTP Monitor establishes a TLS session before sending the HTTP request. Consequently, an HTTP Host header cannot correct a failure that occurs during TLS negotiation.

A curl request returning HTTP 200 confirms that the curl client can establish a session with the endpoint. It does not confirm that the endpoint is compatible with every TLS client configuration.

Observability HTTP Monitors are intended to monitor HTTPS endpoints from F5 Distributed Cloud monitoring locations. They should not be treated as a direct replacement for monitoring individual backend pool members.
