Known Issue

If you use the TMOS Shell (tmsh) batch mode to modify all members of a pool, the transaction may silently fail.

This issue occurs when the following condition is met:

  • Using tmsh batch mode, you create a BIG-IP LTM pool and modify all of the pool members in a single transaction.

    An example transaction:

    [root@example:Active:Standalone] config # tmsh
    root@(example)(cfg-sync Standalone)(Active)(/Common)(tmos)# list ltm pool
    root@(example)(cfg-sync Standalone)(Active)(/Common)(tmos)# create cli transaction
    [batch mode]root@(example)(cfg-sync Standalone)(Active)(/Common)(tmos)# create ltm pool example_pool
    Command added to the current transaction
    [batch mode]root@(example)(cfg-sync Standalone)(Active)(/Common)(tmos)# modify ltm pool example_pool { members replace-all-with { 4.4.4.1:80 4.4.4.2:8000 } }
    Command added to the current transaction
    [batch mode]root@(example)(cfg-sync Standalone)(Active)(/Common)(tmos)# modify ltm pool example_pool { members modify { all { connection-limit 1003 } } }
    Command added to the current transaction
    [batch mode]root@(example)(cfg-sync Standalone)(Active)(/Common)(tmos)# submit cli transaction
    root@(example)(cfg-sync Standalone)(Active)(/Common)(tmos)# list ltm pool
    ltm pool example_pool {
        members {
            4.4.4.1:http {
                address 4.4.4.1
            }
            4.4.4.2:irdmi {
                address 4.4.4.2
            }
        }
    }

    Note: The transaction does not apply the connection limit of 1003, which is specified for all pool members.

Impact

The system does not modify the pool members.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • When you view the pool configuration after running the transaction, commands that modify all members of the pool are not effective.
  • The system generates no error output due to the failed modification of the all pool members command.
  • If you run separate tmsh transactions, where the system creates the pool in one transaction, and then modifies the pool in a second transaction, you get the results you expect.

Resolution

Status

F5 Product Development has assigned ID 671372 to this issue. F5 has confirmed that this issue exists in the products listed in the Applies to (see versions) box, located in the upper-right corner of this article. For information about releases or hotfixes that resolve this issue, refer to the following table:

Type of FixFixes Introduced InRelated Articles
ReleaseNoneNone
HotfixNoneNone

Workaround

To work around this issue, you can use two transactions. One transaction to create the LTM pool and a second transaction to modify the pool. 

Impact of workaround: Performing the suggested workaround should not have a negative impact on your system.
