Description

  • IPSEC IKEv2 connections that are passing through a FastL4 virtual server can see re-connect attempts fail after establishing a tunnel through the BIG-IP.
     

Environment

  • BIG-IP FastL4 Virtual Server passing though IPSEC IKEv2 connections.
  • Connections are using two ports:
    • 500 for initial security connection.
    • 4500 for traffic after tunnel was established.
  • Persistence is in use.
  • TCP or UDP and Persistence Idle Timeouts are mismatched.
  • More than one back-end IPSEC IKEv2 server

Cause

The issue arises when the Persistence Timeout value is lower than the TCP or UDP connection timeout. 

When the initial security connection establishes through the BIG-IP on port 500, that connection is saved within both the persistence and connection table of the the BIG-IP.  After the tunnel is established, traffic flow switches to port 4500.

The initial security connection persistence record (port 500) times out, while the TCP/UDP connection table (port 4500) still has an entry so when the same client leaves their session and comes back to reconnect, there isn't a entry for the connection on Port 500.  Since there is no entry a new load balancing decision is made, while the port 4500 connection entry is still valid.  So even though the security connection is made, the client still tries to re-use the traffic flow connection on port 4500.  

Recommended Actions

It is recommended to set the Persistence and TCP or UDP idle timeouts to match to prevent this from occurring.
