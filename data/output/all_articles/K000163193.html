Description

Due to the layers involved when tracking down potential ARP issues capturing ARP traffic may need to be done at multiple points. What you would run into with the r2000/r4000 series devices is that a packet capture is limited to broadcast traffic only. This limitation is extended further with ARP. In short: the r2000/r4000 host can capture broadcast ARP requests, but it cannot reliably capture the unicast ARP replies. 

This distinction matters because a device may issue a unicast ARP refresh request to the MAC address it already expects. F5 documents this behavior in K91095002, which describes targeted ARP requests as unicast. Such a request would not be visible in the r2000/r4000 host capture even though it is ARP traffic.

Cause

These limitations are due to the use of the Single Root I/O Virtualization (SR-IOV). Port Profiles (r2000 and r4000 only)

Because the r2000/r4000 host capture is limited to broadcast traffic:

  • Normal broadcast ARP requests—Who has ...?—should be captured.
  • Gratuitous ARP requests should be captured.
  • A normal ARP reply is commonly sent unicast to the requester’s MAC and generally will not be captured by the F5OS host.
  • A targeted/unicast ARP request also will not be captured.

Therefore, the host-side command cannot provide a complete request/reply view of ordinary ARP exchange. This is a platform limitation, not a missing filter.

Note: The host interface counters may show unicast traffic even though the host tcpdump does not capture it

Answer/Recommended Actions

Before getting into the how-to it is important to understand the Port-Profile-dependent interface mapping. 

On these platforms, tcpdump is run from the F5OS-A host Linux Bash shell as root, not through the normal F5OS ConfD tcpdump command. Therefore, you do not select the F5OS interface name directly. You select its corresponding Linux interface name.

A review of  K000132908: [F5OS-A] running tcpdump in bash shell on rSeries r2000/4000 will cover this.

Note: A normal broadcast ARP “Who has” request should be captured on an r2000/r4000 host capture, because its Ethernet destination is normally the broadcast MAC ff:ff:ff:ff:ff:ff.

Getting an ARP capture on an r2000/r4000 host:

  1. Log in as root to F5OS host.
  2. The capture should be able to run one of two ways...tcpdump -ni sfp_x arpor depending on the configured port profile it would look something like this:tcpdump -ni <port mapping> arp
    example:
    tcpdump -ni x557_x arp    Note: Use the physical-interface mapping from KB K000132908: F5OS-A tcpdump on r2000/r4000.
  3. To get a complete ARP exchange you will need to use more than one capture point. For example:
    1. BIG-IP tenant, from the tenant’s TMOS shell, on the relevant VLAN/interface. For example:tcpdump -s0 -nni 0.0:nnn -w /var/tmp/tenant-arp.pcap arp
    2. Upstream switch, SPAN/mirror port, or network TAP, which can observe both broadcast requests and unicast replies.
    3. The ARP peer itself, such as the gateway or pool member.

Note: Since the tenant has direct access to the dataplane interfaces, due to the use of SR-IOV on the r2000/r4000, it can see a complete exchange. If it reaches the tenant then it reached the F5OS host.

Getting one on the tenant is pretty standard to what would be done on any BIG-IP.

  1. From an SSH session using the bash shell the syntax would look something like this...tcpdump -s0 -nni 0.0:nnn -w /var/tmp/r5600-tenant-arp.pcap arp

Note: For troubleshooting traffic between two tenants or two appliances, start captures concurrently on the relevant F5OS hosts and tenants, reproduce the issue—for example, ping the peer or affected gateway—and run the capture for at least one minute.

Additional Information

At this time F5OS unified release version 2.x has not changed the way this functions on the r2000/r4000 platforms.
