What Happened?

  • Why do all my HTTP LBs have the same IP assigned to them?
  • I am concerned with my service reliability/availability now that my LBs share the same IP 

 

Environment

  • F5 Distributed Cloud
  • F5 Distributed Cloud WAAP
  • HTTP Load Balancers
  • TCP Load Balancers

 

Resolution/Answer

F5 Distributed Cloud IP Allocation

  • F5 Distributed Cloud by default assigns one Virtual IP (VIP) to all Tenants. This VIP will be Anycast from all Regional Edges and used by all Internet Advertised Load Balancers you create.
  • Additional VIPs(Public IPs) can be purchased if you require them.
  • Customers accustomed to a one FQDN = one IP architectural model can rest assured that having Shared IPs will not affect service delivery.

Common Questions and Concerns

  • How are requests directed to the correct LB under a VIP?
    • Each HTTP LB has one or more mandatory Domain attribute(s).  Inbound connections to the VIP listener are required to present the SNI Servername TLS extension which is matched against the full set of domains assigned to LBs on the VIP.  When the client's SNI is matched, the request is directed to the appropriate LB.  When the client's SNI is not matched to any LB on the VIP, or SNI is absent, the connection is rejected with TCP RST.
      • An exception this behavior exists when the LB is configured as "Default LB" which ignores SNI.  This is a special configuration that does not apply in most environments.
    • The underlying HTTP request's Host: header must also match the SNI and LB domain.  Unmatched requests are rejected at the HTTP layer with 404 or 421 response code.
    • See also: https://community.f5.com/kb/technicalarticles/f5-distributed-cloud---listener-logic/326096
  • Having one IP assigned to all my Load Balancers will provide a single target to attackers, which will put my entire environment at an increased risk of attack.
    • Because the client must present valid SNI and Host to reach the application, it is not possible for the application to be targeted by IP address.
    • L7DDoS protection mechanisms apply per virtual host (LB), not per VIP.
  • I am unable to use a CNAME DNS entry and must use an A record for my FQDNs
    • The drawback to using an A record is that a DNS change is required should there ever be a need to change the VIP on a given LB.  If using a CNAME record, such a change is seamless.
    • Using an A record will still work perfectly fine subject to that caveat.
    • An ALIAS record can be used in place of CNAME for an apex domain.
  • Users of my applications are noticing that all my applications share the same IP and are forming negative perceptions about how my organization manages our infrastructure
    • While such objections may be conscientious, they are based on flawed assumptions of how the platform operates.  Virtual hosts under a VIP listener are no less logically segregated than /32 host addresses within a /24 prefix.
  • I am worried that using a single IP will lead to capacity and load issues
    • The platform's resource utilization within the Regional Edges is unchanged whether the same volume of traffic hits one IP shared by 10 Virtual Hosts or 10 Virtual Hosts with unique IPs.
  • Having one IP for all my LBs will prevent me from implementing ACLs to restrict/allow access on a per-application basis
    • Implementing ACLs on a per-application basis is fully available by taking advantage of Client Blocking Rules, Trusted Client Rules, or Service Policies that can be uniquely applied to each of your LBs.
  • Former/Current Silverline Customers may be used to having unique IPs assigned to all their proxies may be hesitant moving from a dedicated IP model to a shared IP model
    • Switching from dedicated proxy IPs to shared IPs does not affect service delivery at all.
