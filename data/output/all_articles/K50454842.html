Description

A virtual server may be configured to use an iRule to reference multiple pools. When there is a change in pools' status, SNMP trap for the virtual server may not be sent immediately. Instead, the virtual server's status is only updated, and hence SNMP trap is sent, when a user views the virtual server status via the configuration utility or TMSH.

Environment

An SNMP trap may not be sent immediately when all of the following conditions are met:

  • BIG-IP LTM
  • A virtual server is configured with no default pool
  • The virtual server uses iRule to select from one or more pools
  • A pool's status changes that will lead to a change in the virtual server's status

Cause

Bug ID 507487. Although the stated effect (Zebos Route not withdrawn) is different, the underlying cause is still the same, and will cause SNMP trap to be not sent.

Recommended Actions

Follow the workaround of Bug ID 507487.

Additional Information

SNMP trap for the virtual server will only be sent, and you may observe a similar entry as follows in /var/log/ltm, when you next view the status of VS via the configuration utility or TMSH.

Example:
01071681:5: SNMP_TRAP: Virtual /Common/vs_name has become available
