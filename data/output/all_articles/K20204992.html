Description

When the BIG-IP runs out of host memory, you may observe error messages in /var/log/kern.log.

For more information on the log messages, refer to:

  • K16786: Error Message: kernel: Out of memory: Kill process <process ID> (<process name>) score <score value> or sacrifice child
  • K47241910: Interpreting an OOM killer log (out of memory)


When OOM killer is triggered, it also logs the processes running at that moment.

Examining the process list may reveal if any process was consuming unreasonable amount of memory. However, this list is not sorted by RSS (resident memory) and the values displayed are in 4KB pages, it may not be easy to identify offending processes to the untrained eye.

This article explains how to sort this process list by RSS and display the value in MB for easy consumption. You can modify the example commands to fit your situation.

Example desired output (sorted by RSS):

36429*4KB = 142MB    mcpd
26685*4KB = 104MB    tmm.0

8053*4KB = 31MB    lacpd

Environment

  • BIG-IP
  • oom-killer triggered

Cause

Host runs out of memory.

Recommended Actions

When the host runs out of memory, it may trigger oom-killer a number of times. It is important that for each episode, you use the list at the start of the episode. This list contains all processes before any process is killed. If you do not use the first process list in an episode, there is a possibility that the offending process have been killed and may not show in the process list.

Crafting the command to generate the desired output

This walks you through crafting the command to generate the required output. The command is built part-by-part, and each part is connected with a pipe "|". Make sure the preceding part produces the correct output before adding the next part.

  1. Identify the first instance in (start of) an OOM killer episode.

    $ zgrep oom-killer /var/log/kern.log
    Jan 26 04:00:03 bigip1 warning kernel: sshd invoked oom-killer: gfp_mask=0x201da, order=0, oom_score_adj=0
    Jan 26 04:04:03 bigip1 warning kernel: sshd invoked oom-killer: gfp_mask=0x201da, order=0, oom_score_adj=0
    Jan 26 04:08:12 bigip1 warning kernel: sshd invoked oom-killer: gfp_mask=0x201da, order=0, oom_score_adj=0
    Jan 26 04:24:23 bigip1 warning kernel: sshd invoked oom-killer: gfp_mask=0x280da, order=0, oom_score_adj=0
    Jan 26 04:28:44 bigip1 warning kernel: tmsh invoked oom-killer: gfp_mask=0x201da, order=0, oom_score_adj=0
    Jan 26 04:28:46 bigip1 warning kernel: tmsh invoked oom-killer: gfp_mask=0x200da, order=0, oom_score_adj=0

    The above shows that OOM killer started at around Jan 26 04:00:03.
     
  2. Identify the timestamps of the first instance.

    $ less /var/log/kern.log

    Type "/ rss" (with a space after /) and press "Enter", which will bring you to the start of the process list. Press "Page Up" and "Page Down" keys to confirm the start and end timestamps, and "q" to exit.

    Jan 26 04:00:09 bigip1 info kernel: [ pid ]   uid  tgid total_vm      rss nr_ptes swapents oom_score_adj name
    Jan 26 04:00:09 bigip1 info kernel: [  534]     0   534    50862      237      34      371             0 lvmetad
    Jan 26 04:00:09 bigip1 info kernel: [  537]     0   537    11563      266      23      556         -1000 systemd-udevd
    Jan 26 04:00:09 bigip1 info kernel: [ 1140]     0  1140     1084      119       8       13             0 jitterentropy-r
    - snip -
    Jan 26 04:00:11 bigip1 info kernel: [27887]     0 27887     1898       45       8        0             0 sshd
    Jan 26 04:00:11 bigip1 info kernel: [27888]     0 27888      307        1       6        0             0 sshd

    The above shows that the timestamps are 04:00:09 - 04:00:11. A gap of up to a few seconds is normal.
     
  3. Extract the process list by searching based on the timestamps.

    $ grep -P 'Jan 26 04:00:.* bigip1 info kernel: \[' /var/log/kern.log | less

    Use the front part of the log message ("Jan 26 04:00:09 bigip1 info kernel: [") as the pattern in the grep command. However, modify the pattern so that it will match the period between the start and end timestamps. To match the timestamps 04:00:09 - 04:00:11 in our example, remove the second "09" and replace with ".*" (any number of any character). The "[" character also need to be escaped into "\[".

    The output should show the full process list (and nothing else).

    Jan 26 04:00:09 bigip1 info kernel: [ pid ]   uid  tgid total_vm      rss nr_ptes swapents oom_score_adj name
    Jan 26 04:00:09 bigip1 info kernel: [  534]     0   534    50862      237      34      371             0 lvmetad
    Jan 26 04:00:09 bigip1 info kernel: [  537]     0   537    11563      266      23      556         -1000 systemd-udevd
    Jan 26 04:00:09 bigip1 info kernel: [ 1140]     0  1140     1084      119       8       13             0 jitterentropy-r
    - snip -
    Jan 26 04:00:11 bigip1 info kernel: [27887]     0 27887     1898       45       8        0             0 sshd
    Jan 26 04:00:11 bigip1 info kernel: [27888]     0 27888      307        1       6        0             0 sshd
     
  4. Extract the columns (uid, tgid, total_vm, ..., name).

    $ grep -P 'Jan 26 04:00:.* bigip1 info kernel: \[' /var/log/kern.log | grep -P '\d+\s+\d+\s+\d+\s+\d+\s+\d+\s+\d+\s+.*' -o | less

    The output should contains the column values, starting from uid.

    0   534    50862      237      34      371             0 lvmetad
    0   537    11563      266      23      556         -1000 systemd-udevd
    0  1140     1084      119       8       13             0 jitterentropy-r
    - snip -
    0 27887     1898       45       8        0             0 sshd
    0 27888      307        1       6        0             0 sshd
     
  5. Extract RSS and command name, sort the list by RSS (descending order) and calculate RSS in MB.

    $ grep -P 'Jan 26 04:00:.* bigip1 info kernel: \[' /var/log/kern.log | grep -P '\d+\s+\d+\s+\d+\s+\d+\s+\d+\s+\d+\s+.*' -o | awk '{print $4 "    " $8}' | sort -rn | awk '{print $1 "*4KB = " int($1*4/1024) "MB    " $2}' | less

    This produces the final output.

    36429*4KB = 142MB    mcpd
    26685*4KB = 104MB    tmm.0
    21910*4KB = 85MB    overdog
    20074*4KB = 78MB    sod
    - snip -
    31*4KB = 0MB    sshd
    1*4KB = 0MB    sshd


Typical memory usage of processes

The process list can be quite long. Your focus should be on control-plane (non-TMM) processes consuming more than 50MB. Check if there is any process that uses an unreasonable amount of RSS memory, and if there is an abnormally large number of similar processes.

mcpdtens to low hundredsmcpd consumes more memory if you have a large configuration, for example, thousands of virtual servers, pools, monitors.
