K000151814: LTM URI-translation rewrite profile support for HTTP Host header optional port subcomponent

Type
Support Solution
Published
2025-06-12
Updated
2025-06-27
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.0, 17.1.2, 17.1.1, 17.1.X, 17.5.X, 17.5.0
Source
https://my.f5.com/manage/s/article/K000151814

Description

LTM URI-translation rewrite profile doesn't honor requests where the Host header includes the port subcomponent on the default scheme.

 

Environment

  • BIG-IP LTM
  • Rewrite profile

 

Cause

The BIG-IP LTM URI-translation rewrite profile expects a normalized URI when using default schemes for http and https. When the HTTP Host header request includes the optional port subcomponent for the default scheme, the rewrite will not be honored as this is not expected to occur. RFC 9110 and RFC 3986 state that the normal form for the default scheme is to omit the port subcomponent.

URI-translation doesn't permit the definition of duplicated entries, including the default ports in the definition would be normalized by the BIG-IP producing a failure because of duplicate entries. (E.g. https://example.com:443 will be normalized to https://example.com).

URI-translation does take into consideration nonstandard optional ports and permits its definition honoring the rewrite when there is a match.

 

Recommended Actions

This use case can be supported by many methods. Here are some suggestions.

1. Remove Default Port from Client Requests

Ensure clients do not include the default port number in their Host headers (Host: example.com instead of Host: example.com:443 for HTTPS) as RFC 9110 recommends.

2. Rewrite Host Header Using LTM Policy

Configure an LTM Policy to rewrite the Host header. LTM Policy lets the user differentiate between host and port subcomponents in the HTTP Host header as separate conditions.

3. Normalize Host Header Using iRule

Apply an iRule to strip out any occurrence of the default port from incoming requests before they reach other processing stages.

 

Note: it is important to take into consideration that the order of execution will be, LTM Policy > iRule > Rewrite Profile. If the iRule or the Policy modifies the Host header, the profile will not be able to process the original request.
