Answer/Recommended Actions

In our daily tasks, identifying and managing authentication while ensuring secure session management is essential to prevent authentication-related vulnerabilities. An application may inherently have authentication weaknesses if it allows automated attacks, such as credential stuffing, where attackers use wordlists to launch spray attacks. This can open the door to brute force and other automated attacks.

Additionally, the use of commonly weak passwords, such as "password," "123456," "admin," or even more personalized options like birthdates or simple patterns like "abcd1234," further compromises security. These passwords are often easily guessed or cracked by attackers, making systems vulnerable to unauthorized access.

 

To configure the Bot Protection Module (Bot Defense):

1. From the Distributed Cloud console homepage, WAAP service.
2. Select HTTP Load Balancer under Manage->Load Balancers.
3. Select your Load Balancer and go to Manage Configuration, and then click Edit Configuration.
4. Go to Bot Protection, select Bot Defense Standard. 

5. Select any Bot Defense Region you wish.
6. Select Configure within Bot Defense Policy. 

You will see the following interface for the configuration:  

7. You may leave the settings as default and select Configure within App Endpoint Type followed by (+) Add Item.
8. You may configure with the name you prefer, the HTTP Method for bruteforce attacks is generally POST method, and Path Prefix can be the entire site "/" or a specific path.

  

9. Select Bot Mitigation action to block & the response status you wish to set, 403 is a good option, the rest of the configurations can be left at default. 

10. Select Apply on all screens.
11. Select Save and Exit.

 

12. To validate the WAF is working as expected we have launched a POC on a Brute Force Attack, , go back to the XC console and navigate to Home >> Web App & API Protection >> select the namespace in which you configure your LB >> Overview >> Security, then scroll to the bottom of the console and select your LB.

Note: This trigger will not generate a request id that is visible in plain sight, but rather the body response you have previously configured in the Load Balancer.

Additional Information

Brute Force Attack - Proof-Of-Concept:

In order to execute this POC, we will need the following: 

  1. Download Burp-suite
  2. Set Up Damn Vulnerable Web App 

In this proof of concept, we will utilize Burp Suite's Intercept feature to conduct a Pitchfork spray attack. This attack method involves systematically attempting to authenticate using a combination of commonly found username and password lists available on the internet. By leveraging these lists, we can simulate how attackers exploit weak credentials to gain unauthorized access to systems. This exercise will help us demonstrate a comparison between a spray/bruteforce attack comparison without XC waf and with XC WAF. 

1. Go to the Proxy Tab.
2. Go to the Intercept subtab
3. Once you are on the vulnerable site login path you plan to brute force toggle on intercept.
4. Refresh your site and this will populate the HTTP History with the URI Path that is vulnerable, right click it and send it to the Intruder Tab. 

5. Navigate to the Intruder Tab & select Attack Type: Pitchfork .
6. Highlight the username variable and hit "Add $", to add a placeholder .
7. Highlight the password variable and hit "Add $", to add a placeholder.

8. Navigate to the Payloads subtab.
9. Select Payload set: 1.
10. Select Payload Type: Simple List.
11. Paste or Load your usernames to be utilized for the attack, these can be obtained from a common username list online or your own.

   

12. Select Payload Set: 2 and we will do the same process, however this time we will load the password list to be utilized.

13. Select "Start Attack" Orange button on the top right hand corner.

This initiates a sequential attack that tests every combination of Payload 1 and Payload 2. In this proof of concept (POC), we notice that an invalid username and/or password combination is returned, along with a 200 status code, confirming the request successfully reached the backend. The sequential responses suggest a series of attempts will continue until a different status code is detected, or until the response to an attempt indicates a successful breach.

If we replicate the same steps, but prior to this configure the XC WAF as indicated in this article we would be receiving the following response:

(403 generated & error message indicating the requested URL was rejected)

This indicates the WAF was successfully able to mitigate successfully the attack by generating the configured response code and the configured message set in the XC console.
