Description

Appdata is important for host upgrades and deploying guests. If there is insufficient appdata the following may be occur:

  • Getting an error in the GUI when setting the state of guest to Deployed. The state hangs on "Starting".
  • Insufficient appdata can also cause a host upgrade to fail.
  • On the host, log messages indicating that /appdata is near or at 100%

Environment

This issue occurs on platforms licensed and provisioned for vCMP.

  • The I5800 and i7800 and i10800 platforms store guest disk images under /appdata.
  • Appdata is used to create the virtual disc spade needed for a host upgrade

Other devices may store the images under /shared/images

Cause

On these particular appliances the appdata for the vCMP host is sparsely allocated. It is possible due to the number of guests and/or the size that they will consume enough of the appdata that the host  has insufficient space needed for host upgrades or deploying guests.

Recommended Actions

Depending on whether it is deploying  a guest or an upgrade the steps to correct the issue vary.

To simply free up space on the vCMP host for deploying a guest that is done by deleting the disk of the guest(s). Then redeploying it.

This requires that you have downloaded a UCS archive and know the masterkey. A ucs should always be kept for each BIG-IP guest, and it should always be downloaded and stored in a safe location. Keeping a record of the master key(s) for a guest is also a good idea if the ucs is encrypted, but not entirely necessary if there is a peer device or a record of passwords and passphrases is kept.

  • K13132: Backing up and restoring BIG-IP configuration files with a UCS archive
  • K9420: Installing UCS files containing encrypted passwords or passphrases

IMPORTANT: The host does not maintain a ucs archive for a guest.

This will create new Guest virtual disks ( .img files on the host) with minimal size. Guest disks cannot be shrunk directly.

  1. Go to vCMP ›› Guest List and change the state of the guest to Configured
  2. Go to vCMP ›› Virtual Disk List and delete the guest virtual disk. Do not delete the guest itself.
  3. Go to vCMP ›› Guest List click on its name. That will show its settings.
    1. Confirm that the Initial Image and Initial Hotfix are correct.  These settings are not visible unless it is Configured. When the guest is provisioned, it will be created with that version.
    2. You may need to download the correct image from F5's download site and upload to the host.
  4. Go to vCMP ›› Guest List and deploy the guest. This will provision a new Guest Disk image and start it.
  5. Log into the guest and perform the minimal setup. Enter the minimal values required to complete setup . What you enter will be overwritten when the UCS is restored.
  6. Once the guest has been setup , upload the UCS to the new guest.
  7. Use the cli (bash) on the Guest  to restore (re-key) the masterkey. See Solution 2: Copy a master key to a new system
    run   under bash    f5mku -r  masterkeystring
  8. On the guest restore the UCS archive. This will take longer than usual as its creating everything.
  9. Reboot the guest to give a clean start.

If the issue is occurring during an upgrade of the host then the above steps will likely also need to be used if you are seeing a error message similar to this /var/log/liveinstall.log...warning: tm_install::VolumeSet::choose_filesystem_plan -- Selected tiny plan (disk = 38797312, sz_standard = 14612880, sz_tiny = 8647152) error: tm_install::Process::Process_full_install -- predicted size for BIGIP16121 is 8647152 and vg has 7761920 remaining. Terminal error: Disk full (volume group). See SOL#10636

K10636: Issues related to a disk full error that has a recommendation to 'See SOL#10636'
K91895955: Unable to upgrade with error ''failed (Disk full (volume group). See SOL#10636)''

However, running the above steps will release appdata back to the host, but does not make it available to be used as virtual disk space for a host upgrade. That will require reallocating disk space. The steps to do that can be found here...K74200262: Reducing the size of the appdata volume with the lvreduce utility

Additional Information

The masterkey is the same on all members of a HA setup, so you can get it from a peer device.

To get the masterkey run this under bash and record the string printed as the masterkey. You should record this in your management records.

f5mku -K

to re-key a new device run

f5mku  -r  masterkey

If you do not re-key the new guest, the configuration in the UCS will not load as the passwords it contains cannot be decrypted.
