Description

BIG-IP DNS configuration synchronization may fail to propagate changes between devices, even though iQuery connections display as "connected." Common symptoms include GSLB sync not working, missing commit_id information in heartbeat messages, and log entries such as:

Skipped xml broadcast to: ::ffff:<IP_ADDRESS>:36302 reason: not connected to same local address

Additionally, virtual server auto-discovery may fail when this issue is present.

Environment

  • BIG-IP DNS
  • Synchronization failure

Cause

This issue is caused by misconfiguration of the GTM server objects. Both the Address (external) and Translation (internal) fields are set to self IP addresses of the BIG-IP device itself, rather than using the correct external NAT/firewall IP for Address and internal self IP for Translation. This leads to iQuery connections that appear healthy but do not function correctly for configuration synchronization because the system cannot properly map connections for sync operations or heartbeat messaging.

Configuration details:

  1. GSLB sync group with multiple BIG-IP devices
  2. GTM server objects configured with both Address and Translation fields using self IPs
  3. Devices may be deployed behind a firewall or NAT

Recommended Actions

Correct Server Object Configuration based on K14707: Configuring BIG-IP DNS server objects for BIG-IP devices that reside behind a firewall NAT

For devices NOT behind a firewall/NAT:

  • Configure only self IP addresses in the Address field of the GTM server object.
  • Do NOT use the Translation field.

For devices BEHIND a firewall/NAT:

  • Set the Address field to the external (NAT/firewall) IP.
  • Set the Translation field to the internal self IP.
  • Ensure there is a proper 1:1 mapping between external and internal addresses.
  • Never configure both Address and Translation fields with self IPs from the same device.
