Topic

This article applies to BIG-IP 10.x. For information about other versions, refer to the following articles:

  • K52245924: Bypassing the BIG-IP WebAccelerator or BIG-IP AAM or BIG-IP HTTP cache with an iRule in 11.x through 13.x
  • K6882: Bypassing BIG-IP WebAccelerator with an iRule in version 9.4.x

To bypass the BIG-IP WebAccelerator in 10.x, perform the following procedure as appropriate for your BIG-IP WebAccelerator version:

Bypassing BIG-IP WebAccelerator in 10.1.0 and later

In 10.1.0 and later, you can bypass BIG-IP WebAccelerator processing based on information in either the request or the response. To bypass BIG-IP WebAccelerator processing based on information in the request, use the HTTP::class disable iRules command in the HTTP_REQUEST iRules event. To bypass BIG-IP WebAccelerator processing based on information in the response, use the WAM::disable iRules command in the HTTP_RESPONSE iRules event. 

Note: In most cases, when bypassing BIG-IP WebAccelerator, you should also explicitly disable BIG-IP LTM RAM Cache using the CACHE::disable iRules command to prevent the bypassed content from being cached by the BIG-IP LTM system. However, there is no need to re-enable BIG-IP WebAccelerator processing or BIG-IP LTM RAM Cache after disabling for a single request. BIG-IP LTM RAM Cache is implicitly enabled at the start of the HTTP_REQUEST event, and BIG-IP WebAccelerator processing is implicitly enabled for each request matching the HTTP class filter.

For example, the following iRule disables the BIG-IP WebAccelerator module and the BIG-IP LTM RAM Cache for POST requests:

when HTTP_REQUEST {
   if { [HTTP::method] equals "POST" }{
      HTTP::class disable
      CACHE::disable
   }
}

The following iRule bypasses BIG-IP WebAccelerator processing and disables BIG-IP LTM RAM Cache based on the Content-Type set by the origin web server in the response:

when HTTP_RESPONSE {
    if { [HTTP::header exists "Content-Type"] } {
        switch -glob [HTTP::header "Content-Type"] {
            "application/octet-stream" -
            "video/*" -
            "audio/*" {
                WAM::disable
                CACHE::disable
                HTTP::close
            }
        }
    }
}

Note: The HTTP::close command prevents the issue described in K12271: Using the WAM::disable command in an HTTP_RESPONSE event may cause a pvac transaction leak.

When this iRule is applied to a BIG-IP WebAccelerator enabled virtual server, all audio and video file types, as well as those of the application/octet-string type, which is frequently used for generic downloads, will bypass BIG-IP WebAccelerator processing.

Bypassing BIG-IP WebAccelerator in 10.0.1

In 10.0.1, you can bypass BIG-IP WebAccelerator processing based on information in either the request or the response using the WAM::disable iRules command. To bypass BIG-IP WebAccelerator processing based on information in the request, use the WAM::disable iRules command in the HTTP_REQUEST iRules event. To bypass BIG-IP WebAccelerator processing based on information in the response, use the WAM::disable iRules command in the HTTP_RESPONSE iRules event.

Note: In most cases, when bypassing BIG-IP WebAccelerator, you should also explicitly disable BIG-IP LTM RAM Cache using the CACHE::disable iRules command to prevent the bypassed content from being cached by the BIG-IP LTM system. However, there is no need to re-enable BIG-IP WebAccelerator processing or BIG-IP LTM RAM Cache after disabling for a single request. BIG-IP LTM RAM Cache is implicitly enabled at the start of the HTTP_REQUEST event, and BIG-IP WebAccelerator processing is implicitly enabled for each request matching the HTTP class filter.

For example, the following iRule disables the BIG-IP WebAccelerator module and BIG-IP LTM RAM Cache only when a file with the .pdf extension is requested:

when HTTP_REQUEST {
   if { [HTTP::path] ends_with ".pdf" } {
      WAM::disable
      CACHE::disable
   }
}

The following iRule bypasses BIG-IP WebAccelerator processing and disables BIG-IP LTM RAM Cache based on the Content-Type set by the origin web server in the response:

when HTTP_RESPONSE {
    if { [HTTP::header exists "Content-Type"] } {
        switch -glob [HTTP::header "Content-Type"] {
            "application/octet-stream" -
            "video/*" -
            "audio/*" {
                WAM::disable
                CACHE::disable
                HTTP::close
            }
        }
    }
}

Note: The HTTP::close command prevents the issue described in K12271: Using the WAM::disable command in an HTTP_RESPONSE event may cause a pvac transaction leak.

When this iRule is applied to BIG-IP WebAccelerator enabled virtual server, all audio and video file types, as well as those of the application/octet-string type, which is frequently used for generic downloads, will bypass BIG-IP WebAccelerator processing.

Bypassing BIG-IP WebAccelerator in 10.0.0

In 10.0.0, you can use an iRule to conditionally send requests which should bypass BIG-IP WebAccelerator processing to a non-WebAccelerator-enabled virtual server. To do so, define the following virtual server and iRule configuration:

  • Create one virtual server with BIG-IP WebAccelerator enabled
  • Create one virtual server with BIG-IP WebAccelerator disabled
  • Create a third virtual server, and apply an iRule similar to the following that conditionally sends requests to a non-WebAccelerator-enabled virtual server:

    when HTTP_REQUEST {
        if { [HTTP::header User-Agent] contains "Firefox" } {
            virtual <WAM_disabled_vs>
        }
        else {
            virtual <WAM_enabled_vs>
        }
    }

Note: A known issue prevents the PLUGIN iRules commands from functioning as expected. For more information, refer to K10128: The PLUGIN iRule commands do not function in BIG-IP version 10.0.0.
