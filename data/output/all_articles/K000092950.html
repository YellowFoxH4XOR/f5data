K000092950: Aspen Mesh sidecar does not keep an existing TCP Connection Open when DNS TTL expires

Type
Support Solution
Published
2022-12-02
Updated
2022-12-02
Source
https://my.f5.com/manage/s/article/K000092950

Description

When using Service Entries with “Resolution Type” of Static or DNS, if the record is updated with a new IP address and after the TTL expires for an upstream connection, the client Envoy or sidecar will begin to drain the TCP connections to the remote service in favor of the new IP address.   Envoy will close these connections and force a new connection to the remote endpoint.

Environment

  • Kubernetes 1.17x,1.18.x,1.19.x,1.20.x ,1.21.x
  • Aspen Mesh 1.6.x, 1.9.x , 1.11.x 

Cause

This is due to the behavior described in the Strict DNS Section of the Service Discovery types within the  envoyproxy documentation.  

“When using strict DNS service discovery, Envoy will continuously and asynchronously resolve the specified DNS targets. Each returned IP address in the DNS result will be considered an explicit host in the upstream cluster. This means that if the query returns three IP addresses, Envoy will assume the cluster has three hosts, and all three should be load balanced to. If a host is removed from the result Envoy assumes it no longer exists and will drain traffic from any existing connection pools.”

For example:

apiVersion: networking.istio.io/v1alpha3 
kind: ServiceEntry 
metadata: 
  name: external-svc-https 
spec: 
  hosts: 
  - www.example.com 
  location: MESH_EXTERNAL 
  ports: 
  - number: 31191 
    name: http 
    protocol: http 
  resolution: DNS
k exec -it client -- netstat -tna | grep 31191 

tcp        0      0 10.244.1.196:45202      10.155.97.81:31191      ESTABLISHED 103627/telnet 
tcp        0      0 10.244.1.196:45418      10.155.97.81:31191      ESTABLISHED - 
 
# DNS Change from 10.155.97.81 to 10.155.97.83 for 'www.example.com' 
 
k exec -it client -- netstat -tna | grep 31191 
tcp        0      0 10.244.1.196:38566      10.155.97.83:31191      ESTABLISHED - 
tcp        0      0 10.244.1.196:45418      10.155.97.81:31191      TIME_WAIT   - 
tcp        0      0 10.244.1.196:45202      10.155.97.81:31191      ESTABLISHED 103627/telnet


Recommended Actions

This behavior can be mitigated in two ways:  

  1. Beginning in Istio 1.14.x and Aspen Mesh 1.14.x a new Resolution Type of DNS Round Robin will utilize the envoy service discovery type Logical DNS. Per the envoyproxy documentation for Logical DNS:  

“However, instead of strictly taking the results of the DNS query and assuming that they comprise the entire upstream cluster, a logical DNS cluster only uses the first IP address returned when a new connection needs to be initiated.”

  1. If you are unable to upgrade to the latest version of Aspen Mesh or Istio you can use an envoy filter.  

Note: Please use envoy filters with caution. Envoy Filters are not managed by Istio or Aspen Mesh and can have the potential to impact behavior.

apiVersion: networking.istio.io/v1alpha3 
kind: EnvoyFilter 
metadata: 
  name: logicaldns-envoyfilter 
  namespace: default 
spec: 
  configPatches: 
  - applyTo: CLUSTER 
    match: 
      cluster: 
        service: www.example.com 
    patch: 
      operation: MERGE 
      value: 
        type: LOGICAL_DNS
