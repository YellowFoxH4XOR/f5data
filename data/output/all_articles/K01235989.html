Topic

The following sections cover the Request length exceeds defined buffer size violation and using advanced configuration system variables to control how the BIG-IP ASM system determines when the violation is triggered, memory allocation for long request processing, and the related impact of processing multiple concurrent long requests and the effects of exceeding the configured limit.

Description

  • The "Request length exceeds defined buffer size" violation
  • The "ASM bad request: event code <XXXXX> Too many concurrent long request" informational log message
  • Calculate the total number of available long request buffers 

The "Request length exceeds defined buffer size" violation

When receiving a request, the BIG-IP ASM system allocates an appropriate buffer size to process the request in tiers up to 128KB. When a non-chunked request exceeds 128KB, or a chunked request exceeds 10KB, the BIG-IP ASM marks the request as a long request and transfers the request to one of the pre-allocated long request buffers. The long_request_buffer_size advanced configuration system variable represents the maximum size in bytes of the long request buffer. The default value is 10 MB or 10000000 bytes. When a request exceeds the long_request_buffer_size, the BIG-IP ASM triggers a Request length exceeds defined buffer size violation.

When increasing the allocated memory for the long_request_buffer_size advanced configuration system variable, you may also want to consider allocating a higher percentage of memory that the system uses for processing long requests, which depends on your traffic flow. The default setting for the long_request_mem_percentage variable is 10 percent of the allocated memory to the BIG-IP ASM bd process. For more information, refer to K11434152: Configuring BIG-IP ASM to process large requests.

Note: Depending on the total available system resources for your BIG-IP ASM system, you should consider increasing the allocated percentage of memory or the amount of device memory when increasing the values for long_request_buffer_size and the max_concurrent_long_request system variables.

Important: BIG-IP ASM does not send requests to ICAP servers that exceed the maximum request size. For more information, refer to K12984: BIG-IP ASM does not send requests to ICAP servers that exceed the maximum request size.

Important: When a request causes the Request length exceeds defined buffer size violation, the system stops validating the request.

Note: Beginning in BIG-IP ASM 11.5.0, when the request length exceeds the defined buffer size, and the violation is not set to block, the BIG-IP ASM system inspects the first 10 KB of large requests (larger than 10 MB by default) for slow post attacks. With this behavior, administrators can allow the large requests, and the BIG-IP ASM system can inspect and enforce the first part of the data instead of passing all the data without inspection. For more information, refer to K17573: The BIG-IP ASM system does not need to be disabled to allow large file uploads.

The "ASM bad request: event code <XXXXX> Too many concurrent long requests" informational log message

The maximum number of concurrent long requests is defined by the max_concurrent_long_request advanced configuration system variable. Starting in BIG-IP ASM 11.6.0, the value of max_concurrent_long_request is dynamically calculated, for BIG-IP ASM versions prior to 11.6.0, the default value is 100.

When an incoming request exceeds the long_request_buffer_size advanced configuration system variable value, and the max_concurrent_long_request limit is reached, the BIG-IP ASM system terminates the incoming request by sending a TCP reset, and logs the Too many concurrent long requests informational and warning messages to the /var/log/asm and /var/ts/log/bd.log files respectively.

Example informational message logged to the /var/log/asm file:

info perl[<pid>]: 01310012:6: ASM bad request: event code <XXXXX> Too many concurrent long requests

Example warning message logged to the /var/log/ts/bd.log file:

IO_PLUGIN|WARN  |<date/time>|plugin_common.c:3076|Too many concurrent long requests allowed <numeric value> ,current <numeric value> needed request length: <bytes>

For more information, refer to K8292: Error Message: 01310015:6: ASM bad request: event code XXXX Too many concurrent long requests.

Calculate the total number of available long request buffers

To calculate the maximum concurrent long request allowed by the configuration, use the following equation by substituting the configured value for each of the advanced configuration system variables. When stating the value of long_request_mem_percentage, use a decimal value where 1 = 100 percent.

For example, the default value for long_request_mem_percentage is 10 percent, which is stated as 0.10. The default value of the total_umu_max_size advanced configuration system variable is determined through a calculation based on the provision size of the BIG-IP ASM host and the device memory resources. To determine the amount of memory currently allotted to UMU, enter the following command:

tmctl asm_memory_util_stats -s total_max_mem
 

The command output appears similar to the following example:

total_max_mem
-------------
1087488

(total_umu_max_size *  long_request_mem_percentage ) / long_request_buffer_size = max concurrent long request)
 

Example long request memory use calculation:

total_umu_max_size 1087488 (KB)  * 1024 = 1113587712 (B)
long_request_buffer_size is 20000000 (B)
long_request_mem_percentage is 10

( 1113587712 * 0.1) / 20000000 = 5.56 

Note: total_umu_max_size is in KB but the formula is in bytes. Convert as directed.

Rounded down max concurrent long request =  5

Recommendations

  • Modify advanced configuration system variable values
  • Monitor the memory use impact of parameter variable value changes
  • Disable large file processing by the BIG-IP ASM
  • Configure bypassing of BIG-IP ASM processing for specific files

Modify advanced configuration system variables values

You can make changes to the advanced system variable values using the Configuration utility.

  1. Go to Security > Options > Application Security > Advanced Configuration > System Variables.
  2. To locate the advanced system variable, for Search By Parameter Name enter all or part of the variable name.

    Note: If you are unable to locate the advanced configuration system variable, refer to the command steps in the next section.

  3. Select the parameter name of the advanced configuration system variable.
  4. For parameter value, enter the new parameter value.
  5. Select Update.

To modify an advanced configuration system variable from the configured default value that is not available through the Configuration utility, perform the following procedure:

Note: The following example raises the size of the long request buffer from 10MB to 30MB. This outcome allows BIG-IP ASM to process requests up to 30MB but reduces the total number of buffers that are available. To increase the number of buffers available, you must either increase the long_request_mem_percentage variable or decrease the long_request_buffer_size variable. F5 recommends that you understand the relationship of these variables to the resulting total number of buffers by evaluating the formula in the Calculate the total number of available long request buffers section of this article. Your environmental needs may vary.

  1. Log in to the BIG-IP ASM command line.
  2. Configure the advanced system variable using following command syntax:

    /usr/share/ts/bin/add_del_internal add <system variable name> <value in bytes>

    For example, to configure the long request limit to the maximum value of 30 MB, enter the following command:

    /usr/share/ts/bin/add_del_internal add long_request_buffer_size 30000000

  3. Restart the BIG-IP ASM service by entering the following command:

    tmsh restart /sys service asm

    Important: You must use the tmsh restart /sys service asm command for the changes to take effect. When configured as part of a device group, you need to perform this step on all members of the device group.

Note: After you modify a system hidden advanced configuration system variable default value and restart the ASM service, the system variable is available for viewing and modification in the Configuration utility. Go to Security > Options > Application Security > Advanced Configuration > System Variables.

Monitor the memory use impact of parameter variable value changes

Prior to making modifications to advanced configuration system variable values, you should obtain an understanding of the current memory use of the BIG-IP ASM system.

To monitor memory use of the BIG-IP ASM, use the following command syntax from the BIG-IP ASM command line:

tmctl asm_memory_util_stats

The command output appears similar to the following example:

blade_num transactions vm_size rss_size swap_size total_mem_allocated
--------- ------------ ------- -------- --------- -------------------
        0            0 1449432    77492         0                   5

total_mem_used total_max_mem total_xml_mem_used total_xml_max_mem
-------------- ------------- ------------------ -----------------
             0        952320                408            300000

bypass_counter abort_counter
-------------- -------------
             0             0

Review the second line of the command output for total_mem_used and total_max_mem. In the example, total_mem_used is 0, and total_max_mem is 952320. After you gather enough data to determine the average and peak memory use, you can implement your intended changes to the advanced configuration system variables value(s). After implementing the system variable changes, repeat monitoring the memory utilization to determine the average and peak levels of memory utilization and compare these to your previous finding to determine the impact of the modification(s).

Disable large file processing by the BIG-IP ASM

In some circumstances you may want to disable full processing of large requests, especially if very large binary request bodies are being received and ICAP inspection is not required. To do so, you can modify the blocking setting mask so that BIG-IP ASM does not block for the Request length exceeds defined buffer size violation and instead processes the first 10KB before releasing the request to the server or blocking any other violation found in the initial 10KB. If you want to block all requests that exceed the long_request_buffer_size variable then ensure the Request length exceeds defined buffer size violation remains in blocking.

Note: If the long_request_buffer_size system variable is reduced in order to gain more available buffers, the Request length exceeds defined buffer size violation triggers on this reduced value instead of the default 10MB.

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Policy Building > Learning and Blocking Settings > Policy Building Settings.
  3. Set Current edited security policy to the affected security policy.
  4. Expand Policy Building Settings if needed.
  5. Expand the General Settings section.
  6. Locate Request length exceeds defined buffer size.
  7. Clear the Learn, Alarm, and Block check boxes as needed.
  8. Select Save.
  9. Select Apply Policy.

Note: Accepting a Request length exceeds defined buffer size violation recommendation in Security > Event Logs > Application > Requests also disables large file processing after applying the modified security policy.

Configure bypassing of BIG-IP ASM processing for specific files

You can enable the bypass feature by configuring a local traffic policy in conjunction with an iRule.

For more information, refer to K22021244: Bypassing the BIG-IP ASM system (12.1.0 and later) and K14709: Bypassing the BIG-IP ASM system (11.4.0 - 12.0.0).

Note: The value configured in long_request_buffer_size is applied across all the services with security policies configured on the BIG-IP device. If the design requirement is to allow larger sizes to only specific HTTP requests, then:

  • The device will have to be configured to accommodate the largest HTTP request allowed
  • Additional control over the maximum size allowed per request will have to be implemented via iRules applied to the individual services
