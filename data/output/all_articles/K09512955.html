Description

If you have previously enabled debug level log output for the mcpd process, for example for for troubleshooting reasons, and have subsequently turned it off, the log file remains held open and can occupy significant amounts of disk space on the /shared mount (/var/tmp is a symlink to /shared/tmp).  Deleting the /var/tmp/mcpd.out log file does not free up the disk space because the mcpd process still has an open file handle on it. This article explains how to recover that disk space, even if the log file has been deleted.

Environment

  •     mcpd debug level logging has been used.
  •     You want to free up the disk space used by /var/tmp/mcpd.out

Recommended Actions

The general issue with deleting open files on Unix-based systems is that directory entry gets removed, but the OS does not free up disk space until all file handles referencing the file have been closed.  Because mcpd keeps a file handle open to /var/tmp/mcpd.out, the deletion of that log file will not increase the amount of disk space available on /var/tmp.  

To address this. the first step is to ensure that mcpd is not still writing to the file, by making sure that the mcpd log level is set back to the default value of 'notice':

[root@bigip1:Active:Standalone]# tmsh modify sys db log.mcpd.level value notice


Secondly, although an open file can not be immediately deleted, it can be truncated, which causes the data in file to be lost, and the space to be freed up, without closing the file. This can be done simply by using the shell redirect operator:

[root@bigip1:Active:Standalone]# cat /dev/null > /var/tmp/mcpd.out


This can be shortened to just "redirect nothing", with the same result:

[root@bigip1:Active:Standalone]# > /var/tmp/mcpd.out


The situation is more complicated if the file has already been deleted or overwritten, as there's no longer a directory entry to manipulate. In such a scenario, lsof can be used to see the size of the deleted file.  The output below indicates that the mcpd process has two filehandles open to the same deleted file, and that the file is 37,810,589 bytes in size.

[root@ltm-12134-4-163:Active:Standalone]# lsof 2>/dev/null  | grep mcpd.out
mcpd      31053      root    1w      REG              253,1  37810589      16397 /shared/tmp/mcpd.out (deleted)
mcpd      31053      root    2w      REG              253,1  37810589      16397 /shared/tmp/mcpd.out (deleted)


Fortunately the /proc/ filesystem contains symlinks to all open files, even if the file has been deleted.

[root@ltm-12134-4-163:Active:Standalone]# ls -l /proc/$(pidof mcpd)/fd | grep mcpd.out
l-wx------. 1 root root 64 2019-09-04 13:49 1 -> /shared/tmp/mcpd.out (deleted)
l-wx------. 1 root root 64 2019-09-04 13:49 2 -> /shared/tmp/mcpd.out (deleted)


Those symlinks can be used for file truncation just as if they were the original directory entry:

[root@bigip1:Active:Standalone]# > /proc/$(pidof mcpd)/fd/1


After performing this command, lsof now shows the deleted file is 0 bytes in size, and the disk space it was using has now been released.

[root@ltm-12134-4-163:Active:Standalone]# lsof -w |  grep mcpd.out
mcpd      31053      root    1w   REG              253,1         0      16397 /shared/tmp/mcpd.out (deleted)
mcpd      31053      root    2w   REG              253,1         0      16397 /shared/tmp/mcpd.out (deleted)


Additional Information

Sparse Files
The ability to create sparse files is a feature of many modern file systems, and describes a file that has one or more areas where no data exists.  There is no impact to having sparse files in the file system - it's just a more efficient way to store the file. For example, if an application was to create a file, advance the file pointer by 1,000,000 bytes, write 1 byte and close the file, then only one byte of actual data would exist in the file, but it will show up as 1,000,001 bytes in size in the output of ls -l.  If you were to view the contents of the file, the file system would dynamically generate null data for any sparse areas of the file, but if you inspect at the amount of space actually used by the file, it will be much less. The du command, or the -s switch with ls can be used to report the amount of disk space used to store the file.

After truncating /var/tmp/mcpd.out, the data is lost, but the open file handle's position remains at the end of the file, and any further data that gets written to it will be written at that point, causing the file to become sparse. This can lead to confusion about the amount of disk space actually used to store the file on disk.


For example:

A 4MB file using 4008 1K blocks on disk:

[root@ltm-12134-4-163:Active:Standalone]# ls -ls /var/tmp/mcpd.out
4008 -rw-r--r--. 1 root root 4097303 2019-09-04 13:58 /var/tmp/mcpd.out


And the same thing reported using du:

[root@ltm-12134-4-163:Active:Standalone]# du /var/tmp/mcpd.out
4008    /var/tmp/mcpd.out


Now we truncate the file, and view the size again:

[root@ltm-12134-4-163:Active:Standalone]# > /var/tmp/mcpd.out
[root@ltm-12134-4-163:Active:Standalone]# ls -ls /var/tmp/mcpd.out
0 -rw-r--r--. 1 root root 0 2019-09-04 13:58 /var/tmp/mcpd.out


If we then turn mcpd logging back on and off (causing more data to be written to the end of the file), it will become sparse, and the reported file size (4,173,982 bytes) will no longer be the same as the amount of disk space (84 K) required to store the file.

[root@ltm-12134-4-163:Active:Standalone]# ls -ls /var/tmp/mcpd.out
84 -rw-r--r--. 1 root root 4173982 2019-09-04 13:58 /var/tmp/mcpd.out
