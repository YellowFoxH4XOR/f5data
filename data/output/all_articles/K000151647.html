K000151647: Troubleshooting WebSocket (WSS) Connection Issues with F5 Distributed Cloud HTTP Load Balancer and SSL Offload

Description

WebSocket (WSS) connections may fail when using an F5 Distributed Cloud HTTP Load Balancer (VIP) with SSL offload and a backend server listening on port 80 or a custom port. Browsers attempting to connect to wss://<hostname>/wss can encounter errors such as NS_ERROR_WEBSOCKET_CONNECTION_REFUSED or HTTP 403 Forbidden. These WebSocket requests do not reach the backend server, as indicated by missing entries in the origin server logs.

 

Environment

  • Product: F5 Distributed Cloud
  • Configuration:
    • HTTP Load Balancer with SSL offload enabled
    • VIP front-end using HTTPS (port 443)
    • Backend origin pool using HTTP (port 80) or a custom port (e.g., 44444)
    • WebSocket support enabled on the load balancer
    • Application code constructs WebSocket URIs dynamically based on protocol
    • WebSocket server may be running on a different port than the main web server

Cause

The application constructs WebSocket URIs that default to wss://<hostname>/wss when accessed over HTTPS. The load balancer forwards these upgrade requests to the backend on port 80 (or another specified port) with the /wss path. If the backend WebSocket service is not configured to accept connections at this path, is listening on a different port or is expecting WebSocket over HTTP (ws://), connection attempts will fail. The F5 Distributed Cloud proxy does not support rewriting either the path or protocol of incoming WebSocket requests at the proxy level, which limits adaptation to application-specific URI construction.

Recommended Actions

  • Verify that your backend WebSocket server is listening on both the expected port and path as constructed by your application's code.
  • If your application appends /wss to its WebSocket URI, configure your backend service to accept connections at this path, or modify your application logic so it builds URIs compatible with your backend listener.
  • When running the WebSocket service on a non-standard port (e.g., 44444), create an origin pool for that specific port and use route rules to direct only relevant traffic there.
  • Set the HTTP protocol version in your origin pool configuration explicitly to HTTP/1.1 for compatibility with WebSocket upgrade requests.
