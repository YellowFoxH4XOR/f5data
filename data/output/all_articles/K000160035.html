Description

This article describes the procedure to restore and delete individual Elasticsearch indices from a BIG-IQ data collection snapshot when you need to recover specific data without performing a full snapshot restoration. This is particularly useful when dealing with large snapshots where restoring all data would be time-consuming or when you only need to recover or delete specific indices.

Environment

  • BIG-IQ CM DCD Cluster
  • Snapshots
  • Restore huge index from snapshot

Cause

When restoring large Elasticsearch snapshots, the process can hang or take an extremely long time. The standard GUI-based restore operation attempts to restore all indices at once, which can lead to:

  • Process timeouts
  • Statistics collection failures
  • Extended restoration times (hours for large datasets)
  • Potential system performance issues

Answer/Recommended Actions

Follow Index restore process:

Step 1: Identify the Snapshot and Index

  1. Navigate to the BIG-IQ GUI: System → BIG-IQ DATA COLLECTION → BIG-IQ Data Collection Cluster → External Storage & Snapshots → View History
  2. Copy the snapshot name you want to restore from (e.g., scheduled_snapshot_version6.8.1_2026-01-18t22-46-39.471z)
  3. Log in to the BIG-IQ CM command line
  4. List available indices in the snapshot:
  5. curl -sk https://localhost:9200/_snapshot/backup/<snapshot_name> | jq .

Step 2: Check Current Cluster Status

Before restoring, verify the current indices in your cluster:

curl -sk -u admin:admin https://localhost:9200/_cat/indices?v | grep <index_prefix>

Example for ASM indices:

curl -sk -u admin:admin https://localhost:9200/_cat/indices?v | grep asmindex

Step 3: Delete Empty or Conflicting Indices (Optional)

If you have empty indices that conflict with the snapshot data, delete them first:

curl -sk -u admin:admin "https://localhost:9200/<index_pattern>*" -X DELETE

Example:

curl -sk -u admin:admin "https://localhost:9200/asmindex_2026-01-30*" -X DELETE

 

Expected response: {"acknowledged":true}

Step 4: Restore a Specific Index

Execute the restore command for a single index:

curl -sk https://localhost:9200/_snapshot/backup/<snapshot_name>/_restore \

-sX POST \

-H "Content-type: application/json" \

-d '{"indices":"<index_name>"}'

Example:

curl -sk https://localhost:9200/_snapshot/backup/scheduled_snapshot_version6.8.1_2026-01-18t22-46-39.471z/_restore \

-sX POST \

-H "Content-type: application/json" \

-d '{"indices":"asmindex_2026-01-16t00-00-00+0000"}'

Expected response: {"accepted":true}

Step 5: Monitor Restoration Progress

The restoration process runs asynchronously. Monitor progress by checking the index status:

curl -sk -u admin:admin https://localhost:9200/_cat/indices?v | grep <index_name>

Status indicators:

  • Yellow: Index is being restored, shards are being allocated
  • Green: Index restoration is complete, all shards are allocated

For large indices, this process can take considerable time (hours). The index will show as "yellow" until all shards are fully allocated.

Step 6: Verify Data Availability

Once the index status turns green:

  1. Check the index size and document count match expectations
  2. Verify data is visible in the BIG-IQ GUI (e.g., ASM event logs, statistics)
  3. Confirm the date range of restored data
