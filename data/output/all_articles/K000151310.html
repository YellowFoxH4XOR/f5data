K000151310: Why does BIG-IP DNS Return NXDOMAIN when wide IP and pool are healthy?

Type
Support Solution
Published
2025-05-30
Updated
2025-06-03
Applies to
  • BIG-IP
  • BIG-IP DNS: 17.1.1
Source
https://my.f5.com/manage/s/article/K000151310

Description

When performing DNS queries for a domain on BIG-IP DNS, the system may return an NXDOMAIN response even though a Wide IP and its associated pool are configured and healthy. 
Queries for NS records may also yield outdated or unexpected results, and public DNS resolvers can cache incorrect NS records longer than expected. 
Logs or packet captures may show that queries fall through to BIND/ZoneRunner or that responses are provided from local BIND data rather than authoritative external sources.

 

Environment

  • BIG-IP DNS (GTM) VE
  • Wide IPs with associated pools marked healthy
  • iRules disabling DNS cache for specific domains
  • BIND/ZoneRunner enabled for local zone management
  • Listeners using DNS profiles with “Use BIND Server on BIG-IP” enabled
  • Recursion/fallback to BIND allowed in the DNS profile

 

Cause

  • When a query matches a Wide IP but the system cannot provide a complete answer (for example, due to missing or unsynced records in BIND/ZoneRunner), and the DNS profile is set to use the local BIND server, the query is passed to BIND.
  • If BIND does not have the required A record, it responds with NXDOMAIN, even if the Wide IP and pool are up.
  • This behavior can result from race conditions, configuration sync issues, or internal state problems causing the Wide IP not to answer as expected.
  • Public DNS resolvers may cache outdated or incorrect NS records based on previously published data and TTL values; this caching is outside of F5 control.

 

 

Recommended Actions

 

1.) Validate Wide IP & Pool Status

Confirm that both the Wide IP and its pool members are up and correctly configured.

 

2.) Check ZoneRunner/BIND Records

Ensure all necessary A records exist in ZoneRunner/BIND for relevant domains.

If missing or out-of-date, remove/re-add affected Wide IPs/pools to force record regeneration.

 

3.) Review Listener & Profile Settings

Examine attached DNS profiles; disable “Use BIND Server on BIG-IP” if fallback is not desired.

Adjust “Unhandled Query Action” as needed to prevent unwanted fallback behavior.

 

4.) Audit iRule Logic

Review any iRules affecting caching or query handling to ensure they do not interfere with expected resolution flow.

 

5.) Synchronize Local & Public Zones

 

6.) Regularly update ZoneRunner/BIND data to match authoritative public zone content for consistency in responses.

 

7.) Understand Public Resolver Caching

Be aware that public resolver caches are outside F5 control; stale NS records will clear only after their TTL expires.
