K7308: AAAA DNS queries to a BIG-IP GTM or Link Controller wide IP can result in a delay resolving the name

Known Issue

This is the result of a known issue. When a Local Domain Name System (LDNS) server makes an AAAA DNS query to a BIG-IP GTM or BIG-IP Link Controller wide IP, there is a delay in resolving the name. This delay occurs because the BIG-IP GTM and BIG-IP Link Controller systems do not reply with the NOERROR DNS code in response to AAAA DNS requests. According to RFC 4074 (section 3), if a client requests an AAAA record, and the zone does not contain AAAA record types for that name, the DNS server should respond with a NOERROR response code (DNS response code of 0) and an empty answer section.

This behavior can occur in the following configurations:

  • BIG-IP GTM configurations where no AAAA pool members exist for the wide IP, and the zone entry has been removed from the BIND configuration
  • BIG-IP Link Controller systems

Behavior in BIG-IP GTM configurations where the zone entry has been removed from BIND, leaving only a wide IP

When an AAAA query is received by the BIG-IP GTM and no AAAA pool members exist in the wide IP, the gtmd process passes the request to BIND. If the corresponding zone file does not exist in the BIND configuration, the BIG-IP GTM sends a DNS response back to the client that includes a list of the root servers. This process causes a delay in resolving the name, as the client must query the root name servers before it is able to perform an A record query.

Note: The default BIG-IP GTM behavior creates a zone file BIND entry when a wide IP is created. This delay occurs on the BIG-IP GTM system only when the zone entry for the wide IP is removed manually by an administrator.

Behavior in BIG-IP Link Controller systems

The BIG-IP Link Controller does not create a zone file in BIND when a wide IP is created, by default. Therefore, the BIG-IP Link Controller always encounters this issue if an AAAA query is received. The result is the BIG-IP Link Controller system sends a response back to the client that includes a list of the root servers, causing the client or LDNS to send requests to the root servers. This process causes a delay before the client is able to perform an A record query.

F5 Product Development tracked this issue as CR73573, and it was fixed in BIG-IP GTM and BIG-IP Link Controller 9.3.0 and 9.4.2. For information about upgrading, refer to the BIG-IP GTM and BIG-IP Link Controller release notes.

Note: For information about configuring the BIG-IP Link Controller or BIG-IP GTM 9.3.0 to provide IPv6 NOERROR responses for wide IP queries, refer to K7851: Configuring the BIG-IP GTM or Link Controller systems to provide NOERROR responses for IPv6 queries.

Workaround

Note: The following workaround is for the BIG-IP GTM system. Currently, there is no workaround available for the BIG-IP Link Controller system, as it does not support iRules.

To work around this issue for the BIG-IP GTM system, create an iRule and associate it with the wide IP, by performing the following procedure:

  1. Log in to the Configuration utility.
  2. Click Global Traffic.
  3. Click iRules.
  4. Click Create.
  5. Type a name for the iRule.
  6. In the Definition field, enter the following iRule text:

    when DNS_REQUEST {
    if { [DNS::rrtype] equals "AAAA" } {
    noerror
    }
    }

  7. Click Finished.

You must now associate the iRule with the BIG-IP GTM wide IP.
