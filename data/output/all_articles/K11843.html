Known Issue

This is the result of a known issue. After installing an additional VIPRION blade in a fully functional chassis, the new blade may reboot continuously. If a serial terminal is connected to the blade, the following message may be observed before each reboot:

01140043:0: Ha feature software_update reboot requested

This issue occurs when a blade running a software version prior to 10.1.0 with BIOS revision 456 or 461 is installed in a VIPRION cluster, wherein the member blades are running version 10.1.0 or later with BIOS revision 470.

After inserting the blade, the cluster will reboot the blade in an attempt to install the newer software version. However, the installation will fail because a manual BIOS update is required.

Note: For more information, refer to K10633: BIOS update may be required before installing BIG-IP version 10.1.0 or later on the VIPRION platform.

Once the software installation has failed, the cluster does not become aware of the issue and reboots the blade in an effort to upgrade the other boot locations. In this way, the reboot process continues indefinitely.

F5 Product Development tracked this issue as ID 337055, and it was fixed in BIG-IP version 11.0.0.

Workaround

You can work around this issue by manually installing the BIOS from the functional blades to the new blade. To do so, perform the following procedure:

  1. Log on to the command line of the primary blade by opening an SSH connection to the floating management IP address.
  2. Connect to the console of the newly installed blade by entering the following command:

    bladectl -b <slot number> -c

    For example, if the blade affected by the issue was installed in slot 3, you would enter the following command:

    bladectl -b 3 -c

    Note: The bladectl option -c will function only on the PB100 blade; it will not function on any other hardware.

  3. If necessary, wait until the blade has booted. Then, quickly log on to the blade and proceed to Step 4.
  4. Stop all BIG-IP services by entering the following command:

    bigstart stop

    This command will stop all inter-chassis communication with the new blade and break the continuous reboot cycle.

  5. Exit the bladectl utility and return to the command line of the primary blade. To do so, press the Esc key and then press the Shift and 9 keys simultaneously.

    The system returns the following output:

    exiting...

  6. To determine the BIOS build number, enter the following command:

    tmsh show /sys hardware | grep BIOS

    Take note of the build number displayed at the end of the string.

    For example, the following output displays that the build number is 470:

    BIOS revision: LinuxBIOS 2.0.0 OBJ-0235-07 REV. A build 470

  7. Change directories to the /usr/firmware/ directory by entering the following command:

    cd /usr/firmware/

  8. List all files with the .rom file extension by entering the following command:

    ls *.rom

  9. Identify the BIOS file associated with the build number that you determined in Step 6. Using the above example, the correct BIOS file is puma-bios-470.rom.
  10. Copy the BIOS file to the newly installed blade by entering the following command:

    scp /usr/firmware/<file name> slot<slot number>:/shared/

    For example, if the name of the file is puma-bios-470.rom and the blade affected by the issue was installed in slot 3, you would enter the following command:

    scp /usr/firmware/puma-bios-470.rom slot3:/shared/

  11. Reconnect to the console of the newly installed blade as described in Step 2.
  12. Change directories to the /shared/ directory by entering the following command:

    cd /shared/

  13. Install the new BIOS by entering the following command:

    flashrom -w <file name>

    For example:

    flashrom -w puma-bios-470.rom

  14. After the previous command completes and the CLI prompt becomes available, enter the following command:

    reboot


    At this point, the blade will reboot and install the new BIOS. Installation of the new BIOS may incur another reboot. After the new BIOS is installed, the blade will join the cluster and begin installing software to match the other blades, eventually successfully establishing itself as a secondary blade in the cluster.

If necessary, repeat this procedure for any other affected blades.
