K74433702: Control plane sending a huge number of communications towards applications

Type
Support Solution
Published
2022-05-26
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K74433702

Description

When inspecting the traffic hitting the istio-proxy sidecar there may seem to be an excessive amount of traffic from the control plane.

Environment

  • Aspen Mesh: 1.6.x - 1.11.x
  • Kubernetes: 1.17x - 1.22.x
  • Red Hat OpenShift: 4.6.x - 4.8.x
  • Large cluster with Istio injection enabled on several namespaces

Cause

When there are changes or modifications to the Aspen Mesh cluster, the Istiod daemon by default updates all the sidecars or istio-proxies in the cluster where istio-injection has been labeled on the namespace. Additionally, each proxy generates metrics about all the ingress and egress traffic passing through.  Therefore, when there are a lot of changes within a larger cluster, more traffic is seen on the sidecars. The large amount of traffic will be encrypted over TCP port 15012 which is gRPC communicating the updates over the xDS (* discovery service) API.

Recommended Actions

You can minimize this communication by using the Sidecar custom resource. The sidecar describes the configuration of the sidecar proxy that mediates inbound and outbound communication of the workload instance to which it is attached. Setting this configuration restricts the data (and services) that is sent to pods in other namespaces. 

For example, to reduce traffic use the Sidecar custom resource to restrict the traffic to what namespaces the traffic is allowed to egress. In the example below the configuration allows egress traffic to its own namespace “default” and the “istio-system". 

cat <<EOF | kubectl apply -f -
apiVersion: networking.istio.io/v1alpha3
kind: Sidecar
metadata:
  name: sidecar-example
  namespace: default
spec:
  egress:
  - hosts:
    - "default/*"
    - "istio-system/*"
EOF

When performing the following command, we can see configuration related to another pod in a different istio labeled namespace named “dev.”:

# kubectl exec -it sleep-557747455f-4cvxt -- curl localhost:15000/clusters | grep dev | head –n 4 

outbound|80||sleep.dev.svc.cluster.local::observability_name::outbound|80||sleep.dev.svc.cluster.local
outbound|80||sleep.dev.svc.cluster.local::default_priority::max_connections::4294967295
outbound|80||sleep.dev.svc.cluster.local::default_priority::max_pending_requests::4294967295
outbound|80||sleep.dev.svc.cluster.local::default_priority::max_requests::4294967295

After applying the above sidecar configuration, the command should return no results.

Additional Information

To revert the changes, simply remove the configuration.
