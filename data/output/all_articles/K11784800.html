Description

After successfully installed Aspen Mesh with multicluster enabled in K14643443: Install multi-cluster Aspen Mesh on KOPS Cluster, the common question is what are the next steps?

It all depends on your use case. For example:

Imagine that you want the exact same copy of your environment so in case of a disaster in the remote site, automatically all the requests failover from site 1 it will be redirected to site 2 - A common practice for Disaster Recovery.

On the other hand, instead of performing a failover, you want a distributed weight in requests on multiple regions so the same copy of the application will be running across regions, but the amount of traffic for each workload will be different. 

Environment

  • Kuberntes: 1.17x,1.18.x,1.19.x,1.20.x
  • Aspen Mesh: 1.9.x 

Cause

N/A

Recommended Actions

To achieve the scenarios described above, you can use the following configurations:

  • Configure locality failover
  • Configure locality load balancing

Configure locality failover

Note: if your clusters live in different regions (i.e us-west and us-east), labeling might not be necessary.

  1. Introducing subzone labeling

    In our example, we have two clusters with Aspen Mesh 1.9.5-am1 deployed in the same region us-west-2, and in the same AZ us-west-2b. This would set our Envoy priority with the same value and failover would not be working as expected.

    To solve this, we would introduce a subzone label that Istio/AM provides to divide zones properly and set a difference between the endpoints.

    Label the nodes

    Run the following command to label all the nodes from your cluster.

    Cluster 1

    kubectl get nodes -o json | jq '.items[].metadata.name' | for i in $(xargs); do kubectl label node $i --overwrite topology.istio.io/subzone=cluster1; done

    Cluster 2

    kubectl get nodes -o json | jq '.items[].metadata.name' | for i in $(xargs); do kubectl label node $i --overwrite topology.istio.io/subzone=cluster2; done

  2. Enable locality failover

    After labeling the nodes, we should restart Pilot and the applications with sidecar in-jected to take over the new configuration.

    Restart istiod pods with the following command:

    kubectl rollout restart deploy istiod -n istio-system

    Restart the application pods with the following command:

    kubectl rollout restart deploy <deployment-name>

    After all the pods received the new configuration, you should see that cluster now have the subzone define for the local and the remote pod in cluster2, we could verify this in our client pod with the following command:

    kubectl exec sleep3-5cff6fbbf5-h2s46 -c sleep -- curl localhost:15000/clusters | grep hello

    You expect to see the subzone field with the nodes labels we set before:

    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::region::us-west-2
    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::zone::us-west-2b
    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::sub_zone::cluster1
    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::canary::false
    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::priority::0

    outbound|5000||helloworld.default.svc.cluster.local::44.240.xx.xx:15443::region::us-west-2
    outbound|5000||helloworld.default.svc.cluster.local::44.240.xx.xx:15443::zone::us-west-2b
    outbound|5000||helloworld.default.svc.cluster.local::44.240.xx.xx:15443::sub_zone::cluster2
    outbound|5000||helloworld.default.svc.cluster.local::44.240.xx.xx:15443::canary::false
    outbound|5000||helloworld.default.svc.cluster.local::44.240.xx.xx:15443::priority::0

    Note that the priority for both clusters at this point is still the same priority::0

    Internally, Envoy priorities are used to control failover. 

    These priorities will be assigned as follows for traffic originating from the client pod (in region1 zone1):

    PriorityLocalityDetails
    0region1.zone1Region, zone, and sub-zone all match.
    1NoneSince this task doesn’t use sub-zones, there are no matches for a different sub-zone.
    2region1.zone2Different zone within the same region.
    3region2.zone3No match, however failover is defined for region1->region2.
    4region3.zone4No match and no failover defined for region1->region3.

    In this example we will only work with priority 0 and 1.

    We would solve the priority by applying a Destination Rule that will enable the locali-ty failover for our host helloworld.default.svc.cluster.local.

    Apply this in the namespace your applications are deployed in both clusters:

    kubectl apply -n <namespace> -f - <<EOF
    apiVersion: networking.istio.io/v1beta1
    kind: DestinationRule
    metadata:
      name: helloworld-failover
    spec:
      host: helloworld.default.svc.cluster.local
      trafficPolicy:
        connectionPool:
          http:
            maxRequestsPerConnection: 1
        loadBalancer:
          simple: ROUND_ROBIN
          localityLbSetting:
            enabled: true
        outlierDetection:
          consecutive5xxErrors: 1
          interval: 1s
          baseEjectionTime: 1m
    EOF

    Note: you can adjust the consecutive5xx errors and the interval time as well baseE-jectionTime, this example would trigger the failover as soon the first request failed.

    You could verify with the same command above the cluster are now set up with a proper priority:

    kubectl exec sleep3-5cff6fbbf5-h2s46 -c sleep -- curl lo-calhost:15000/clusters | grep hello

    You expect to see the subzone field with the nodes labels we set before:

    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::region::us-west-2
    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::zone::us-west-2b
    out-bound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::sub_zone::cluster1
    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::canary::false
    outbound|5000||helloworld.default.svc.cluster.local::100.96.9.104:5000::priority::0

    outbound|5000||helloworld.default.svc.cluster.local::44.240.xx.xx:15443::region::us-west-2
    outbound|5000||helloworld.default.svc.cluster.local::44.240.xx.xx:15443::zone::us-west-2b
    out-bound|5000||helloworld.default.svc.cluster.local::44.240.xx.xx:15443::sub_zone::cluster2

Configure locality load balancing

Locality load balancing if fair simpler than the failover, from our example above, delete the destination rule helloworld-failover.

Instead, we will apply this new destination rule:

kubectl apply -n <namespace> -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: helloworld-loadbalancing
spec:
  host: helloworld.default.svc.cluster.local
  trafficPolicy:
    loadBalancer:
      localityLbSetting:
        enabled: true
        distribute:
        - from: us-west-2/us-west-2b/*
          to: "us-west-2/us-west-2b/cluster1": 10
              "us-west-2/us-west-2b/cluster2": 90
    outlierDetection:
      consecutive5xxErrors: 100
      interval: 1s
      baseEjectionTime: 1m
EOF

In this example, we are going to send traffic to helloworld service and 10% will go to cluster 1 and 90% to cluster 2.

If we send ten requests at least one request will go to cluster 1. For example:
