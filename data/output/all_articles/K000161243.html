K000161243: Troubleshooting Empty or Garbled HTTP::host and HTTP::path values in BIG-IP LTM iRule Logging

Type
Support Solution
Published
2026-05-13
Updated
2026-05-13
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000161243

Description

When using an iRule on BIG-IP LTM to log HTTP request details, log entries for HTTP::host and HTTP::path may sometimes be empty or contain unexpected (garbled) characters. This typically occurs when the device is acting as an explicit forward proxy, especially for HTTPS traffic. The client IP address is reliably logged, but the destination URL may not appear as expected. The objective is to consistently log the source client IP address and the requested destination URL for all HTTP requests.

Environment

  • Standard virtual server
  • HTTP profile
  • iRules

Cause

The HTTP_REQUEST event fires for CONNECT methods when BIG-IP is configured as an explicit forward proxy. In these cases, HTTP::host and HTTP::path may be empty or contain unexpected values because the destination is encoded in the request line (absolute URI form), not in a standard Host header. This is expected behavior as documented in F5 Knowledge Base article K000132975.

Answer/Recommended Actions

1.) On simplest form, to reliably log the client IP and the full requested URL, update your iRule as follows:

when HTTP_REQUEST {
  log local0. "Client IP [IP::client_addr] connecting to [HTTP::host][HTTP::uri]"
}
  • [IP::client_addr] reliably returns the connecting client's IP address.
  • [HTTP::uri] returns the full URI, including the path and query string.

2.) Test any iRule changes in a lab environment before deploying to production.

3.) If you require more advanced logging or encounter issues with specific request types, consider engaging F5 Professional Services for custom iRule development.

Additional Information

HTTP::host returns the value of the Host header from the client's HTTP request. If the Host header is missing or malformed (as in CONNECT requests), HTTP::host may be empty or unexpected.
HTTP::uri provides the full URI, which is more reliable for logging the destination in proxy scenarios.
This behavior is expected and documented; the application is not impacted, and the client IP is always logged correctly.
