Issue

You should consider using this procedure under the following conditions:

  • You have configured NT LAN Manager (NTLM) authentication in your BIG-IP APM access policy.
  • You want to troubleshoot NTLM logon issues.

Symptoms

As a result of Kerberos authentication issues, you may encounter the following symptom:

  • You are unable to access configured internal resources after failing NTLM authentication.

Recommended Actions

This article provides steps for troubleshooting common login issues related to NTLM authentication

Important: By default, NTLM authentication is enabled for every request, and the BIG-IP APM system connects (typically on TCP port 445) to the domain controller to authenticate a user. Network connectivity between the BIG-IP system and the domain controller is therefore required at all times.

The main configuration objects in NTLM authentication on the BIG-IP APM system are the following:

  • The NTLM machine account
  • The NTLM authentication configuration
  • An object that enables an ECA profile and selects the NTLM authentication configuration. For example, an iRule, an Exchange profile, or a Secure Web Gateway (SWG) access profile.
  • The NTLM Authentication result checker in the access policy
  • A virtual server with an ECA profile enabled

Note: Verify that you have configured these objects correctly.

Important: F5 supports BIG-IP APM system software. F5 does not support third-party software, such as the client operating system or Windows Server.

Procedures

When you experience NTLM authentication failure issues, you can use the following troubleshooting steps to determine the root cause:

  • Reviewing all configuration steps from K03010204
  • Verifying the DNS configuration
  • Verifying clock skew issues
  • Enabling BIG-IP APM and ECA debug logging
  • Enabling logging for NTLM on Windows server
  • Identifying and reviewing the NTLM machine account and authentication configuration
  • Verifying your iRule configuration
  • Creating new NTLM machine account and NTLM auth configuration and replace the existing ones
  • Conducting advanced troubleshooting with browser and TCP captures

Reviewing all configuration steps from K03010204

Review the steps in K03010204: Configuring BIG-IP APM NTLM authentication had been performed correctly, in particular, an ECA profile has been added to the virtual server and the virtual server FQDN has been added to the Local Intranet site on the client.

Verifying the DNS configuration

The BIG-IP APM system communicates with the Windows domain controller for every NTLM authentication requests from the client. To do this, DNS must be set up correctly. To verify DNS configuration, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to Advanced shell (bash).
  2. Use the following command syntax:

    dig <FQDN of domain controller>

    For example:

    dig dc.example.com

  3. Verify that the IP addresses and names from the command output are correct.

Verifying clock skew issues

If the BIG-IP APM system's clock is not synchronized to the Windows domain controller, you can't create an NTLM machine account. To verify that the BIG-IP system's time is synchronized, you can use the ntpstat command. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to bash.
  2. Type the following command:

    ntpstat

    Output appears similar to the following:

    # ntpstat
    synchronised to NTP server (ntpserver.example.com) at stratum 2
    time correct to within 126 ms
    polling server every 1024 s

    Note: Manually verifying that the times among the systems are within 5 minutes of one another is not sufficient. The system's times must be synchronized to an NTP server as shown in the previous output.

Enabling BIG-IP APM and ECA debug logging

Unlike BIG-IP APM debug logging, in which you can apply debug on a customized logging profile, to enable ECA debug logging, you must configure the default logging profile (default-log-settings). To set both BIG-IP APM and ECA logging to debug, perform the following procedure:

Impact of procedure: Enabling BIG-IP APM and ECA debug logging may cause excessive logging in a system with a large number of user logins. You should only enable debug logging when troubleshooting and disable debug logging after you've finished troubleshooting.

BIG-IP 12.x and later

  1. Log in to the Configuration utility.
  2. Navigate to Access > Overview > Event Logs > Settings.

    Note: For BIG-IP 12x, navigate to Access Policy > Event logs > Log Settings.

  3. Select the check box next to default-log-setting.
  4. Click Edit
  5. Click Access System Logs.
  6. For Access Policy and ECA, click Debug.
  7. Click Access Profiles.
  8. In the Selected list, verify that your access profile is there. If not, select it in the Available list and move it.
  9. Click OK.

Procedure back out

After you have finished troubleshooting, to revert the changes, repeat the steps in the procedure, but in step 6, for Access Policy and ECA, click Notice and then click Update.

BIG-IP 11.x

  1. Log in to the TMOS Shell (tmsh) by typing the following command:

    tmsh

  2. To enable BIG-IP APM debug logging, type the following command:

    modify /sys db log.accesscontrol.level value debug

  3. To enable NTLM ECA debug logging, type the following command:

    modify /sys db log.eca.level value debug

Procedure back out

After you have finished troubleshooting, to revert the changes, type the following tmsh commands:

modify /sys db log.accesscontrol.level reset-to-default
modify sys db log.eca.level value Notice

Enabling logging for NTLM on Windows server

NTLM event logs at the domain controller are logged in Windows Event Viewer under Application and Services Logs > Microsoft > Windows > NTLM > Operational.

Note: Refer to your Windows server documentation to enable NTLM auditing.

Identifying and reviewing the NTLM machine account and authentication configuration

After you have enabled BIG-IP APM and ECA debug logging, you can identify the NTLM Auth Configuration setting that is used in the authentication in the /var/log/apm logs. Review its configuration, along with the configuration of the NTLM machine account setting. To review the NTLM Machine Account and NTLM Auth Configuration settings, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Access > Authentication > NTLM > Machine Account and review its configuration.

    Note: For BIG-IP 12.x and earlier, navigate to Access Policy > Access Profiles > NTLM > Machine Account.

  3. Navigate to Access > Authentication > NTLM > NTLM Auth Configurationand review its configuration.

    Note: For BIG-IP 12.x and earlier, navigate to Access Policy > Access Profiles > NTLM > NTLM Auth Configuration.

Verifying your iRule configuration

For NTLM to work, you must first enable the ECA profile and then select the appropriate NTLM Auth Configuration object. On the BIG-IP APM system, there are three common methods to do this:

  • Using the ECA::enable and ECA::select commands in an iRule
  • Configuring an Exchange profile and associating it to the access profile
  • Associating the NTLM Auth Configuration setting for an SWG access profile in an SWG deployment.

Most deployments use an iRule to accomplish these methods. Some iRules can be complex and may lead to unexpected issues. To troubleshoot your iRule, perform both of the following procedures:

  • Review the /var/log/ltm file for iRules errors.
  • Replace your iRule with a minimal iRule that only enables the ECA profile and selects the appropriate NTLM Auth Configuration object.

To replace your existing iRule with a minimal one to troubleshoot the issue, perform the following procedure:

Important: The iRule in the following example may not apply to all environments, and you may have to modify your access policy for it to work.

Impact of procedure: Removing or replacing an existing iRule can potentially disrupt services of a virtual server. F5 recommends performing this during a scheduled maintenance window.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules.
  3. Click Create.
  4. Enter a name for the iRule.
  5. For Definition, enter the following iRules syntax:

    when HTTP_REQUEST {
    ECA::enable
    ECA::select select_ntlm:/Common/<example_NTLM_Auth_Config>
    }

    Note: Replace <example_NTLM_Auth_Config> with the name of your NTLM Auth Configuration object.

  6. Click Finished.
  7. Navigate to Local Traffic > Virtual Servers.
  8. Click the name of the virtual server that is affected by this issue.
  9. Click the Resources tab.
  10. For iRules, click Manage.
  11. In the Enabled list, click your existing iRule and move it to the Available list to disable it.
  12. In the Available list, click the new iRule and move it to the Enabled list to enable it.
  13. Click Finished.

Procedure back out

After you have finished troubleshooting, to revert the changes, disable the new iRule and reenable the original iRule.

Creating new NTLM machine account and NTLM authorization configurations and replace the existing ones

Due to possible changes to the Computer account on Active Directory, the NTLM machine account object on the BIG-IP APM system may become out of synchronization. It is useful to remove and recreate the configuration objects again on the BIG-IP APM system.

To remove the NTLM machine account and NTLM auth configuration objects, perform the following procedure:

Note: If the NTLM auth configuration you are removing is associated to an Exchange profile or an access profile, you first need to de-associate them from the profiles.

Impact of procedure: Replacing the existing NTLM machine account and NTLM authorization configuration may cause NTLM authentication to fail. F5 recommends performing this during a scheduled maintenance window.

  1. To create new NTLM objects, refer to the Creating an NTLM Machine Account and Creating the NTLM Authentication Configuration procedures in K03010204: Configuring BIG-IP APM NTLM authentication.
  2. To use the newly created NTLM Auth Configuration object, you must identify where the NTLM Authentication Configuration is called first. It may be called from an iRule, an Exchange profile, or an SWG access profile.
  3. Modify the appropriate object (an iRule, an Exchange profile, or an SWG access profile) to use the new NTLM Authentication Configuration object.

Note: You may remove the original NTLM Machine Account and NTLM Auth Configuration objects when you are done troubleshooting.

Procedure back out

Modify the same object (the iRule, the Exchange profile, or the SWG access profile) at step 3 to use the original NTLM Auth Configuration object.

Advanced troubleshooting with browser and TCP captures

When troubleshooting NTLM authentication issues, you need to have an understanding of the authentication protocol to analyze the communication between the BIG-IP APM client system and BIG-IP APM system domain controller. Use a browser capture or a TCP capture to analyze the following exchange:

BIG-IP APM client system NTLM HTTP authentication protocol

The NTLM HTTP authentication between the client and the BIG-IP APM system works as follows:

  1. The client requests a protected resource from the server.

    For example:

    GET /index.html HTTP/1.1

    The server responds with a 401 status, indicating that the client must authenticate. NTLM is presented as a supported authentication mechanism through the WWW-Authenticate header. Typically, the server then closes the connection:

    For example

    HTTP/1.1 401 Unauthorized
    WWW-Authenticate: NTLM
    Connection: close

    If the BIG-IP APM system does not respond with a 401 challenge, verify if you have configured an iRule (ECA::enable), Exchange profile, or access profile to enable an ECA profile.

  2. The client resubmits the request with an Authorization header containing a Type 1 message NTLMSSP_NEGOTIATE. The Type 1 message is base-64 encoded for transmission. From this point forward, the connection remains open. Closing the connection requires re-authentication of subsequent requests. The following example shows the relevant request headers:

    GET /index.html HTTP/1.1
    Authorization: NTLM TlRMTVNTUAABAAAABzIAAAYABgArAAAACwALACAAAABXT1JLU1RBVElPTkRPTUFJTg==

    If your client does not respond with an Authorization header, verify that you have added the URL to the Local Intranet sites on your browser.

  3. The server replies with a 401 status containing a Type 2 message NTLMSSP_CHALLENGE in the WWW-Authenticate header (again, base-64 encoded). For example:

    HTTP/1.1 401 Unauthorized.
    WWW-Authenticate: NTLM
    TlRMTVNTUAACAAAADAAMADAAAAABAoEAASNFZ4mrze8AAAAAAAAAAGIAYgA8AAAARABPAE0AQQBJAE4AAgAG8AbQADACIAcwBlAHIAdgBlAHIALgB

    Use the /var/log/apm log file to determine if the correct NTLM Auth Config has been called.

  4. The client responds to the Type 2 message by resubmitting the request with an Authorization header containing a base-64 encoded Type 3 message NTLMSSP_AUTH:

    GET /index.html HTTP/1.1
    Authorization: NTLM TlRMTVNTUAADy9RPyXgqZnr21CfG3mfCDC0+d8ViWpjBwx6BhHRmspst9GgPOZWPuMITqcxg==

  5. The server validates the responses in the client's Type 3 message and allows access to the resource.

    For example:

    HTTP/1.1 200 OK

BIG-IP APM system domain controller NTLM authentication protocol

Important: By default, NTLM authentication is enabled for every request, and the BIG-IP APM system connects (typically on TCP port 445) to the domain controller to authenticate a user. Network connectivity between the BIG-IP system and the domain controller is therefore required at all times.

Similar to the client side, the NTLM authentication between the BIG-IP APM system and the domain controller consists of the three messages, Type 1 (negotiation), Type 2 (challenge), and Type 3 (authentication).

  1. The BIG-IP system sends a NTLMSSP_NEGOTIATE Type 1 message containing its hostname to the domain controller.
  2. The domain controller replies with a NTLMSSP_CHALLENGE Type 2 message. This message contains important NetBIOS, domain, and DNS names that you should verify against your configuration on the BIG-IP system.
  3. The BIG-IP system replies to the challenge with a NTLMSSP_AUTH Type 3 message. Examine this message in detail as it also contains NetBIOS, domain, DNS, hostnames, and other configuration parameters that may be incorrectly configured.
  4. The domain controller replies with a STATUS_SUCCESS message. If authentication is not successful, examine this message for an error message for a root cause. For example, if you had configured an incorrect domain name or NETBIOS name, you may observe the following error message in the packet capture:

    NT Status: STATUS_LOGON_FAILURE (0xc000006d)

    You may also observe a message similar to the following in the /var/log/apm file:

    err nlad[<pid>]: 01620000:3: <0x55a5fb90> nlclnt[10104060a] init: Error [0xc000006d,NT_STATUS_LOGON_FAILURE] connecting to DC <DC IP address>
