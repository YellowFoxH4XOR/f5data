Description

File upload requests are blocked due to triggered violations based on the pattern matches within the binary content of the HTTP request body. Although the "File Upload" parameter is defined and attack signature checks are disabled (as outlined in K01385558: Attack Signatures triggered when files are uploaded in the requests, some violations are still triggered, resulting in the request being blocked.

Environment

  • BIG-IP
  • ASM
  • Security policy in blocking mode. 

Cause

The steps mentioned in K01385558: Attack Signatures triggered when files are uploaded in the requests apply only to attack signatures with a Signature Scope set to "Parameter". Other types of attack signatures, such as those with the Signature Scope set to "Request Content", will still be triggered even after applying this setting. This is expected behaviour because a signature with a "Request Content" scope ignores parameter extraction and instead performs a bitwise comparison of the signature across the entire request as a single flat hex blob.

Recommended Actions

You can either disable the triggered attack signatures at the URL level each time they occur or create an iRule to disable attack signatures with the "Request Content" scope specifically for the file upload URL.

  • Disable the signatures at the URL.
  • Configure an iRule.

Disable the signatures at the URL

  1. Log in to the BIG-IP system Configuration Utility.
  2. Navigate to Security  ››  Application Security : URLs : Allowed URLs : Allowed HTTP URLs.
  3. Make sure you select the correct Security Policy from the policy drop down.
  4. Click on the URL. 
  5. Choose Click here to load Signatures List from the Attack Signatures section below.
  6. Move the required signatures from the right Global Security Policy Settings listing to Overridden Security Policy Settings.
  7. Click on Update

Note: This approach adds extra work for the security administrator, as each time a false-positive violation is triggered, the configuration needs to be updated.

Configure an iRule

Important: It is essential to adjust the parameters according to your specific requirements and thoroughly test in a staging environment before implementing in production. The provided examples are for guidance only. If you need F5 to write an iRule for you, please contact Professional Services.

 

  1. Log in to the BIG-IP system Configuration Utility.
  2. Navigate to Local Traffic  ››  iRules : iRule List.
  3. Click on Create to create a new iRule.
    • When a user sends a POST request containing "multipart/form-data" in the Content-Type header and an attack signature with a "Request Content" scope is triggered, allow the request to process.  
      when ASM_REQUEST_VIOLATION {
  if {([HTTP::method] equals "POST") and ([string tolower [HTTP::path]] ends_with "/foo.cfm") and ([string tolower [HTTP::header "Content-Type"]] contains "multipart/form-data") } {
    if {([lindex [ASM::violation_data] 0] contains "VIOLATION_ATTACK_SIGNATURE_DETECTED") and ([ASM::violation details] contains "context request") } {
      ASM::unblock
    }
  }
}
  4. Attach the iRule the virtual server.
  5. Navigate to Security  ››  Application Security : Security Policies : Policies List  ››  <Policy_Name>
  6. Under the Policy Configuration ›› General Settings, set Trigger ASM iRule Events Mode to Compatibility
  7. Save and apply the policy.  

Note: The iRules consume more CPU cycles, keep an eye on the resource utilisation when using them.
