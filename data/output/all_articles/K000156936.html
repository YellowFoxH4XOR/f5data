K000156936: BIG-IP LTM gRPC Trailer-Only Error Handling Limitation

Type
Support Solution
Published
2025-10-08
Updated
2025-10-08
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.1
Source
https://my.f5.com/manage/s/article/K000156936

Description

When gRPC clients send requests through a BIG-IP LTM virtual server, error responses from the backend gRPC server (such as those triggered by missing authentication tokens) are not handled correctly. Instead of receiving the expected gRPC error message, clients experience protocol or internal errors (e.g., “server closed the stream without sending trailers”). This issue does not occur when clients connect directly to the backend server.

Environment

  • Product: BIG-IP LTM (versions 16.1.x, 17.1.x and likely others)
  • Configuration: HTTP/2 full proxy virtual server, SSL profiles (client and server), HTTP/2 profiles (client and server), HTTP MRF Router enabled, gRPC backend services
  • Network: BIG-IP LTM load balancing gRPC traffic between clients and backend servers
  • Recent Changes: None required; issue is inherent to the product’s HTTP/2/gRPC proxy implementation

Cause

BIG-IP LTM’s HTTP/2 proxy implementation does not fully support gRPC trailer-only error responses. When the backend server sends a HEADERS frame with the END_STREAM flag (and no DATA frame), BIG-IP appends a 0-byte DATA frame, which is not compliant with the gRPC specification. This causes gRPC clients to fail to process the error correctly.

This limitation is tracked as an enhancement request under Bug ID 1787457.

Recommended Actions

  • Application-Level Workaround: Embed Error Information in Protobuf Message Modify the backend gRPC service to always return a normal gRPC response with a message body, embedding error details in the Protobuf message rather than relying solely on gRPC trailers for error signaling. This ensures clients receive error information even if the trailers are malformed by BIG-IP.
  • Bypass BIG-IP for Critical gRPC Error Flows (if feasible): For critical gRPC error flows that must be handled per spec, consider routing those requests directly to the backend, bypassing BIG-IP (e.g., via DNS, routing, or client logic).
  • Monitor for F5 Product Updates: Track the progress of RFE Bug ID 1787457 with your F5 account team or support. Test new BIG-IP releases as they become available for improved gRPC support.

Note: Do not use request-log profiles or iRules for header manipulation as a workaround, as these can further disrupt gRPC trailer handling but do not resolve the core issue.
