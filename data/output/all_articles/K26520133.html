How to Identify SSL Orchestrator Objects

Before you can troubleshoot SSL Orchestrator an understanding of the configuration objects that are created when the topology is setup is helpful.

The naming of these objects is done in two parts

  1. The first part is created by the user and it does have some limitations due to the language being used.

    • The user created portion cannot exceed 11 characters.
    • Do not use a hyphen character in object names. K15572588: Do not use hyphen character in F5 SSL Orchestrator object names
    • They must begin with an alphabetic character.
    • There are certain words that should not be used. The following articles provide the details.
      K13209: BIG-IP configuration object names must begin with an alphabetic character
      K6869: Reserved words that should not be used in BIG-IP configurations (10.x - 14.x)    

  2.  Along with these individual naming conventions, when the topology is created, specific syntax will be added. This syntax identifies where the object is in the chain, and often its function in the chain. With that information a more targeted troubleshooting process can, in most cases, be used.

Service Objects and Naming

  • All object names are prefixed by the name of the Application Service (iApp instance name)
  • Objects that accept IPv4 traffic have -4 added.
  • Objects that accept IPv6 traffic have -6 added.
  • A TCP or UDP object will a -t or a -u.
  • A none TCP/UDP traffic object will have -ot.
  • Traffic arrives to the transparent proxy Ingress on virtual servers with -in in the name.
  • When an Explicit Proxy is configured the object name will include the letters xp
  • SSLFWD client and Server SSL profiles are named cssl and sssl.
  • The endings -vht and -vhf stand for Verified Handshake True and Verified Handshake False
    • This changed starting with version 9.1. You can read more about that here...Interception Rules
  • In-line services use these designations for virtual servers...
    • When sending traffic -t-
    • When receiving traffic -D-O-

Note: There can be different versions for TCP/UDP and IPv4/IPv6.

  • The ICAP flow makes use of.
    • an -ic virtual server for Adapt.
    • a separate -req and -rsp virtual servers for the ICAP profiles.

Note: SSL Orchestrator policies are per-flow (one-per-connection) verses per transactions, like other access per-request policies. The exceptions are HTTP and ICAP.

System objects

  • iRule: ssloGS_global-settings        (created by RPM install)
  • Access: ssloDefault_accessProfile    (created by RPM install)
  • Resolver: ssloGS-net-resolver        (created by explicit proxy)
  • Route: ssloGS_global-exit-4-A/B/C    (created with system route)
  • Pool: ssloGS_global-ex-pool-4    (created with system route)

Determining the SSL Orchestrator Version

With so many versions already out there and with the product growing at at phenomenal rate change is a constant. With that in mind one of the first things that needs to be determined is the version. There are 2 things to keep in mind when determining the version.

  1. SSL Orchestrator has its own versioning enumeration within TMOS.
    • In all OS versions 13.x and prior SSL Orchestrator was an iApp and was run by the iRules and configuration objects created using the iApp.
    • The SSL Orchestrator versions seen here are 3.x and prior.
    • There are also special versions called Field Contributed versions, such as 3.0FC.
      • These are versions where the iApp was modified in the field by the client or by F5 Security Engineers.
      • The most robust of these is still in use... 3.0FC. However, it is no longer supported. K30498134: F5 SSL Orchestrator software support policy (12.x - 13.x)
  2. With the inception of 4.0, that came with 14.0.0, there were some major changes.
    • The datagroups and other objects were removed and replaced with Access Policies.
    • In order to use SSL Orchestrator, an SSL Forward Proxy license had to be added to LTM for SSL Orchestrator to show up in the WebUI and to configure it.
    • Starting in 4.0 SSL Orchestrator became its own module. As its own module it can be a standalone SSL Orchestrator BIG-IP or used as an add-on license with other modules.
    • Virtual Wire (often referred to a VWire) was introduced as the successor to vlan groups. Careful attention needs to be paid here because STP and MAC flapping due to a potential looping in the network may occur.
      • One instance that can cause this is if the BIG-IPs are setup in an Active/Active state. They will forward any broadcast packets independently as they're both Active. For example, if SSLO1 receives a broadcast packet from interface 1.2 from a server it will then forward that packet out to interface 1.1. Given that 1.1 is connecting with the 1.1 on SSLO2 such a broadcast will arrive on SSLO2 on 1.1 and then be forwarded to 1.2 of SSLO2. This means the broadcast will come "back".

The version being used can be determined several ways...

  1. In the GUI go to iApps >> Package Management : f5-iappslx-ssl-orchestrator and the SSL Orchestrator version will be listed under "Build". It can also be seen in the SSL Orchestrator GUI in the upper right-hand corner of the SSL Orchestrator Configuration Panel.
  2. The version can also be found in a qkview.  
    1. Open the qkview to the Files tab and select the "all" navigation tab.
    2. In the search bar use this syntax to search with "var versionArr".
    3. The output will be similar to: var versionArr = '-15.0.0-6.2.22'.substring(1).split('-');
      1. 15.0.0 is the OS version
      2. 6.2.22 is the rpm version used by SSL Orchestrator

How to use the Qkview
SSL Orchestrator has some characteristics that differ from other BIG-IP modules. While it now works within TMOS it does so using REST Calls. When a topology is deployed a .json file is created. From that .json file REST Calls are used to create the configuration objects that SSL Orchestrator uses to run the traffic. Also, with the addition of Access Policies in place of iRules and Datagroups there are some specific logs that will need to be used.
Important: A qkview is limited to 5MB for each log entry. Often the verbosity that occurs in logs will cause the actual log on the BIG-IP to be larger than that. Due to this the logs, that appear in the qkview, will often be truncated and will be missing important information. To overcome this there are 2 approaches.

  1. Create a qkview using an "Unlimited Snaplen". This is done one of 2 ways.
    1. Navigate To: TMUI > System > Support :: Create New Snapshot
      1. In the Options section check Unlimited Snaplen
    2. Via the CLI using the comman: 
      qkview -s0
      Once it has been completed it will have to be retrieved from /var/tmp.
  2. While obtaining a qkview with an Unlimited Snaplen is simple enough it is not truly unlimited. When using that option it increases the log entry size to 100MB. To overcome the rare occasion when that is not sufficient a tarball of the logs will be needed. To create a tarball of the logs open an SSH session and run this command.  
    tar czvf /var/tmp/varlogs.tgz /var/log/*
    Note: When the tarball has completed it will need to be retrieved from the /var/tmp directory manually.

Once the qkview has been created and uploaded to iHealth the most common logs to review are.

  • /var/log/apm (SSL Orchestrator does not need APM to be licensed or provisioned in order to fully function)
  • /var/log/ltm
  • /var/log/restnoded
  • /var/log/restjavad

Testing SSL Orchestrator Functionality

  1. A browser can be used but cURL often reveals more information.
  2. Pick the TLS version or versions:
    Syntax: 
    curl -vk [--tlsv1 | tlsv1.0 | tlsv1.1 | tlsv1.2] [URL}
    Example:  
    curl -vk -tls1.2 https://www.example.com/
  3. Some basic curl commands: 
    curl -vk <URL>
curl -vk --proxy <PROXY IP:PORT> <URL>
curl -vk
curl -vk --proxy <PROXY IP:PORT> --proxy-ntlm --proxy-user 'user:pass' <URL>
curl --help

Check Traffic

  1. Checking pools and monitors is usually a good first step. The monitor that will normally be used is ICMP Gateway. The ICMP Gateway Monitor is an address check monitor. It provides a simple verification of an address on the network. Due to this it does not check an actual server/application for functionality. It is only ensuring the the IP address is available in the network, not an IP:port (websocket).
  2. SSLO did support HTTP/2 until 16.1.0. K32080520: F5 SSL Orchestrator and SSL Forward Proxy support for HTTP/2 traffic
  3. Ping both sides of the services.
  4. Reviewing the logs can often reveal clues as to what may be occurring within the traffic. To make the most of the information in the logs it is often helpful to enable SSL Orchestrator debug.
    1. To set SSL Orchestrator debug go to SSL Orchestrator >> Logs:Settings.       
    2. There are several settings here, each preset to Error by default. There are 2 that need to be checked while the others are only used in very specific cases.
      1. In the dropdown for both Per-request Policy and SSL Orchestrator Generic set them both to debug. You can look further in the F5 SSL Orchestrator Deployment Guides for the version in use to learn more about debug.
        1. For instructions on how to enable debug logging using the tmsh utility, refer to K81086420: Enable SSL Orchestrator topology debug logging using the tmsh utility.
          Important: Enabling debug creates a great deal of logging and must be returned to the default setting when the troubleshooting steps are complete. If left set to debug there are issues that can occur due to the logs filling up
    3. SSLO uses the Access Policy portion of APM (APM does not need to be provisioned). Enabling APM debug can also provide relevent information. To enable APM debug K45423041: Enabling APM Policy debug logging
    4. Enabling debug and then tailing the logs will provide realtime data quickly.
      1. These are the 2 most common tailing commands. 
        tail -F /var/log/ltm
tail -F /var/log/apm |grep <syntax you want to search on>
  5. tcpdumps
    1. Captures are done on 3 levels: 1) Targeted on one of the services 2) Wide-open on 0.0 or 3) Using a specific object.
      1. To capture on a service: 
        tcpdump -s0 -lnni ssloN_<service>.app/ssloN_<service>
      2. Wide open captures can fill very fast and become large quickly. Thus, they should only be used when a specific service or object cannot be determined. Also, when capturing with a wide-open capture it is often best to filter on Wireshark using VLAN display filters. Those VLANs can be seen in the capture.
        1. A basic syntax for a wide-open capture would resemble something like this. 
          tcpdump -s0 -lnni 0.0:nnn
          Note:  Help with VLAN display filters can be found here.
            Display Filter Reference: 802.1Q Virtual LAN on www.Wireshark.org
            Virtual Bridged LAN (VLAN, IEEE 802.1Q) on wiki.Wireshark.org
            K11954: Treatment of long VLAN names by the Linux host subsystem
      3. Capturing using a specific source IP, client-vlan, or outbound vlan will reduce the size of the capture making it easier to work with.
        1. By IP
          For Example: 
          tcpdump -s0 -nni 0.0:nnp <source IP>
        2. By vlan
          For Example: 
          tcpdump -s0 -nni outgoing_VLAN:nnn
          Note: All of the above examples will output to screen. Copy pasting those outputs and sending that to F5 Support is close to useless. There is a very large amount of data that will not be shown. If the capture is to be sent to F5 Support send it to a file and then retrieve that and upload it to F5 Support Files. An example of that syntax would look something like this.For Example: 
          tcpdump -s0 -nni outgoing_VLAN:nnn -vw /var/tmp/VLAN_capture.pcap
      4. When doing a capture, especially when using a source IP. There are a couple of things to consider.
        1. Which virtual server do I attach the capture to? In an SSL Orchestrator topology there are several virtual servers created (one that is even hidden and is not seen in the bigip.conf). In most cases you will want to attach it to the virtual server where the traffic enters the BIG-IP. That virtual server will have a couple of characteristics...
          1. There will be a clientssl and http profile attached to it.
          2. The name of the virtual server will end in either a -t or -u with a -4 or -6. For example it will look something like ssloS_EXCHANGE.app/ssloS_EXCHANGE-t-4 in the GUI and the bigip.conf.
        2. Ensure that the capture syntax has both "full" noise and the "p" flag. By using "full" noise the capture will contain the data for the F5 Ethernet Trailer Dissectors. This makes it much easier to track flows and several other things. The "p" flag will allow the data gathered to include the flow of traffic on both the clientside, serverside, and the flows in between. The capture will look something like this 
          tcpdump -s0 -nni 0.0:nnnp host 1.1.1.1 -vw /var/tmp/noise_flag.pcapng
          Note: For a deeper explanation of tcpdump and the BIG-IP refer to K00463541: A breakdown of the tcpdump utility, recommended actions, and information to help you use and apply it to the BIG-IP.
  6. Create a browser capture.
    1. This can be done using the development tools in Chrome, Firefox or Edge (Edge starting version 75). This will enable you to examine the actual traffic that the client is using.     
    2. This output can then be saved to a file for examination by F5 Support. To create a .har file and upload it to F5 Support Files...
      1. For Chrome, Firefox or Edge (Chrome or Firefox are preferred) use the F12 button to open the Development Tools. (For IE please refer to the HTTP Watch Support page)
      2. Click the Network tab
      3. Click the radio button Preserve Log (Does not exist in Edge).
      4. Navigate to the webpage in question
      5. Stop it by using the little Red Button in the upper left corner of the dev tool panel.
      6. For Chrome and Firefox right click on one of the lines and choose Save a HAR with content. For Edge click on the save symbol and "Export as HAR".
      7. The file can then be uploaded to F5 Support Files for examination.
  7. Isolating services can help to identify where the issue is happening.
    1. Remove the working chains.       
    2. Delete and rebuild. This can clear many misconfigurations or possible errors.
  8. If a decrypted capture is needed there are 2 appraoaches to use.
    1. Using this on the internal and external vlans:
      K16700: Decrypting SSL traffic using the SSL::sessionsecret iRules command
      K31793632: Creating a decrypted tcpdump capture without using an iRule
      1. When using the SSL::sessionsecret the iRule will need to be attached to the virtual server in the chain with the http and clientssl profile. That is usually a t-4 or t-6 virtual. Also, with this step be sure to remember to add the "p" flag to capture the traffic on both sides of the BIG-IP. For example 
        tcpdump -s0 -nni 0.0:nnnp host 1.1.1.1 and port 443 -vw /var/tmp/sessionsecret.pcapng
  9. Clear the certificate cache.
    1. Clearing the SSL Forward Proxy certs can be used to delete any certs that may be corrupted or otherwise at issue. Also, if the certs are suspected then running this command either before the tcpdump or as a second run with cleared certs (before and after tcpdump) can be used. 
      tmsh show ltm clientssl-proxy cached-certs clientssl-profile [profile] virtual [vip]
tmsh delete ltm  clientssl-proxy cached-certs clientssl-profile [profile] virtual [vip]
  10. One thing to consider when checking traffic is that the -D-0 vlans do not show up when the ifconfig command is run. This is because they exist in alternate route domains. To show these VLANs use rdexec <route domain ID> <command>
    Example: 
    rdexec 65000 ifconfig -a |grep ssl


Specific Settings

  1. There are some specific settings and things to check.
    1. An explicit proxy requires an SSL defined DNS forward. This is set in System >> Configuration : Device : DNS. 
    2. If DNS is changed, you must restart 'named'.       
    3. If URLF (URL Filtering) is not licensed (A seperate subscription is needed), and custom categories are in use then non-matching URLs break. This is because the Category Lookup agents are.
      1. Programmatically set to use default and custom categories
      2. Reset on Failure is 'enabled'
      3. Resetting Category Type in the UI does not change the setting.       
    4. The Category Type can be changed via: 
      tmsh modify apm policy agent category-lookup [object] lookup-type custom-only      
    5. Tail the logs for iAppLX issues when deploying. 
      tailf /var/log/restnoded/restnoded (grep for severe will sometimes help here)
tailf /var/log/restjava.0.log      
    6. Then attempt to manually clear any detected dependencies 
      tmsh modify sys application service sslGS_global.app/ssloGS_global strict-updates disabled
  2. There are times issues occur within the SSLO Guide Configuration GUI.
    1. If the GUI hangs restart restnoded and restjavad       
    2. Starting in version 9 you can use the SSLOFix script. This script is specifically for HA issues but SSLO Guided Configuration issues often intertwine with HA due to how REST is used. Steps to use the script can be found in the applicable Deployment Guide for your version.
    3. There are also a couple of known issues:

Upgrading and Platform Migrations
If the issue is one of upgrading in versions prior to 5.4 this can only be done via a "forklift" upgrade. This entails deleting the entire SSL Orchestrator config and then rebuilding it within the newer version. Also, a license for the new SSL Orchestrator module must be obtained. Any prior license for SSL Forward Proxy will not work.

Starting in version 9.1 SSLO moved away from use of REST Gossip for HA and now stores the information in iFiles. This corrected many issues that the use of Gossip created. When upgrading to 9.1 or higher the upgrade will take much longer as this will require the move from Gossip to iFiles as everything is re-indexed.

The upgrade for SSLO does not follow the same steps as a typical upgrade. Please review ALL of the following prior to the upgrade. It is not a hard process but is different.

Network
Always ensure the ports needed are not blocked. In particular attention needs to be paid to ports 443 and 8100. For example, if a firewall has a rule that says only traffic sourced from a specific vlan is allowed then HA and sync may not work.

High Availability (HA) and ConfigSync
Prior to SSLO version 9.1 HA and sync for SSL Orchestrator operated differently than other BIG-IP modules. SSL Orchestrator uses internal REST based calls to sync using the REST Gossip mechanism. This sync is only done when the topology is deployed. Using the normal sync function via Device management will push the TMM configuration items across but not the .json file that runs them.
Note: is that SSL Orchestrator does not support an Active/Active setup for HA.

When having HA/Configsync issues they can often be corrected using the SSLOfix tool mentioned previously.

Troubleshooting Steps for HA and ConfigSync

  1. Check for consistent application IDs
    1. Check the application ID on each device 
      restcurl shared/iapp/global-installed-packages | jq     
    2. Verify that the ID of the f5-iappslx-ssl-orchestrator application is the SAME on both devices.       
    3. If these are not the same then undeploy, uninstall the RPM, and then install the matching RPM.
  2. Be aware that BigipFailoverStateWorker detects device group and failover settings on the BIG-IP by polling. So, whenever you make changes to the device-group and failover/sync settings it might take some time before the change is reflected in the REST framework.
    1. To review the current polling period and failover settings: 
      restcurl tm/shared/bigip-failover-state
    2. To make immediate changes you can "poke" BigipFailoverStateWorker. 
      restcurl -X POST -d '{}' tm/shared/bigip-failover-state
  3. SSLO (9.0 and earlier ) uses REST framework "gossip" mechanisms to replicate configuration. REST framework gossip basically re-plays REST requests on the peer device(s) to keep configs in sync. It supports the "eventual consistency" model.
    • To make sure changes are "gossiping" from one device to another.
      restcurl shared/echo 
      restcurl -d '{"content":"foo45"}' shared/echo
    • To view the BIG-IP devices detected in the REST framework device-group 
      restcurl shared/resolver/device-groups/tm-shared-all-big-ips/devices
    • To ensure the gossip worker is in an active state with correct peer group set to "tm-shared-all-big-ips". 
      restcurl shared/gossip
    • To check the gossip status: 
      restcurl 'shared/gossip?$select=gossipPeerDevices' |grep -I "uuid\|\"state\|hostname"
    • Look for gossip related warnings in restjavad 
      grep WARNING /var/log/restjavad.*.log |grep Gossip
    • Delete old self-ips in the list of devices in the device-group 
      restcurl -X DELETE shared/resolver/device-groups/tm-shared-all-big-ips/devices/[ID]
    • When GossipWorker cannot apply an update to the local worker it adds a description of the problem in /shared/gossip-conflicts: 
      restcurl shared/gossip-conflicts
  4. If you get to this point and still have an issue the next step would to use the ha-sync script to correct HA issues. In versions prior to 16.0.0 this can only be obtained with the assistance of F5 Support. Starting in version 16.0.0/8.0 it is now built into the OS. The information needed to run this script can be found here for version 16.x/8.x Manual Chapter : Overview: SSL Orchestrator High Availability Diagnostics and Sync-Repair Tool. Subsequent versions should be titled much the same.
  5. In some rare cases the gossip will have to be reset. These steps should not have an adverse effect on traffic, but care should always be taken when performing these steps.
    1. Create a new UCS backup . Previous versions of this guide guided to stop restjavad/restnoded before grabbing UCS. This is no longer recommended. Please make sure restjavad/restnoded are running prior to taking UCS.
    2. Check gossip status on both Active and standby by running this command: 
      restcurl shared/gossip | grep "status" && restcurl shared/resolver/device-groups/tm-shared-all-big-ips/devices | grep "managementAddress"
      1. If the gossip state is Active on both peers and you see the management IP of both Active and Standby on each box, then it is good to go.
      2. If gossip status shows "UNPAIRED" then continue to step 5.3
      3. If any unit's gossip status shows "SYNCHRONIZING", wait one minute and run step '5.2' again. They need to show Active. This may need to be done a few times until the SYNCHRONIZING is complete.
    3. Delete existing device information: 
      restcurl -X DELETE shared/resolver/device-groups/tm-shared-all-big-ips/devices
    4. Run the following commands: 
      bigstart restart restjavad
restcurl -X POST -d '{}' tm/shared/bigip-failover-state
    5. Go to step 2 and run the command again. It is complete when it shows Active.
    6. Deploy config
  6. Configsync must always be set to manual and whatever VLAN sync happens on has to be open to the REST traffic. SSL Orchestrator changes should always be made on the Active device then deploy. This will sync the changes to the peers. When checking the HA configuration ensure it was built properly:
    1. Establish HA before any SSL Orchestrator config is built:
      1. Use a dedicated HA VLAN (TMM interface)
      2. Ensure the HA VLAN self-IP has Port Lockdown set to Allow Default in order to allow full REST conversation; if you need to set Port Lockdown to Allow Custom, ensure that TCP port 443 is included.
      3. Set Sync Type to Manual with Incremental Sync
    2. Perform an initial full manual sync
    3. Configure SSL Orchestrator – you should see REST traffic on 443 flowing on the HA VLAN between the peers.
      Note: Further, while modifying SSL Orchestrator settings on the Active peer you will see Sync status "Changes Pending" even though that setting is already synced to the peer SSL Orchestrator unit. You may perform manual Sync by clicking on "changes pending".
      Note: SSL Orchestrator changes should always be made on the Active device then deploy it to sync to the peers.

Important: In conjunction with maintaining a UCS always create one for all peers prior to making configuration changes. Under normal circumstances when you redeploy the sync is pushed with no issues. However, if a pair gets out of/or will not sync simply pushing a sync from one device to another may not sync the configs. If this happens the only way to restore it, short of a wiping and starting over, is to reload the ucs backups (made before the config changes) simultaneously on the peers then sync. For example, if changes are made and after a reasonable amount of time, say 5 minutes (sync for SSL Orchestrator is normally very quick), the sync does not happen then the gossip mechanism used for sync are likely broken. This can be seen in /var/restjavad.x.log
For Example:

[I][118198][11 Apr 2019 05:16:30 UTC][GossipResourceUpdateSender] Failed to send update to peer https://1.1.1.1:443. Will try again later.

  • Review the restnoded logs for any errors. If any unusual log entries are seen use the log entry text and search MyF5 fro any known issues. If an issue is found follow the steps provided in the article.
  • If a search of the logs does not provide resolution then using the Scripts built into SSLO will be best way to try and correct any HA/Configsync issues.
  • If that does not resolev the issue open a support case with F5 Support. Please folow the appropriate steps here when doing so K2633: Submit a support case


Rebuilding the Configuration
If the prior steps do not work, in 9.0 and earlier, to correct config issues or HA, then it is may be necessary to delete the SSL Orchestrator config and rebuild it. This is used only as a "last resort" method.

  1. Starting with SSL Orchestrator 4.0 there is a delete function in the SSL Orchestrator GUI.
  2. Once that is done then delete any remaining items under iApps > Application Services > Applications LX
  3. Delete the SSL Orchestrator objects under iApps > Templates > Templates LX
  4. Delete the SSL Orchestrator RPM under iApps > Package Management LX
  5. Re-install the RPM and rebuild. (This is a good time to upgrade to the newest SSL Orchestrator rpm version and a newer OS)
    Note: At times when using these steps an error message will popup saying the strict updates needs to be disabled.
    For Example:     
    010715bc:3: The application service (/Common/sslo_tango.app/sslo_tango) has strict updates enabled, the object (Virtual Server /Common/sslo_tango.app/sslo_tango-ot-4) must be updated using an application management interface.
    However, when you go to iApps > Application > iAppsLX the object to disable strict updates is not there. This most often occurs when the GUI delete does not work properly or when the "red" square is associated with the config object. To disable strict updates in cases like this it will need to be disabled via the CLI.
    For Example:     
    tmsh modify sys application service sslo_tango.app/sslo_tango strict-updates disable
  6. Optionally, you can also run this command and reboot instead of deleting all the config. It will, in essence, do much the same thing. 
    clear-rest-storage -l -d
Important: When using clear-rest-storage -l -d the entire BIG-IP configuration including SSL Orchestrator is deleted. The -d option resets the BIG-IP system configuration to default by running tmsh load sys config default. Refer to K13127: Restoring the BIG-IP configuration to factory default settings (11.x - 16.x) for more information.



Resource Considerations
When a single SSLO topology is created anywhere from 150 to 700 control plane objects are created. Comparing that to the average LTM virtual server deployment of around 15 Control Plane objects it is easy to see why SSLO is resource intensive. When you are experiencing issues of slowness in the BIG-IP GUI, the SSLO Guided Configuration GUI, or mybe even traffic latncy through the BIG-IP the issue is often due to resource issues. Often referred to as "over-subscribing". If you run into such issues here are some things to look for and to deal with the situation...

  1. If a Virtual Edition (VE) is in use add resources. As a "minmum" per  F5 SSL Orchestrator Release Notes (use the Release Notes for your version)
    1. 16 CPU
    2. 16 GB of RAM or greater
    3. Set Management (MGMT) to Large. If this is done after the intial provisioning this will cause a reload of the configuration and if done on the Active device will cause a failover. To do this do the Standby first, failover and test, if all is well then do the peer.
  2. On both VE and hardware platforms Setting MGMT to Large is recommended. In some cases that may not be sufficient. If that occurs then the you would have to use the CLI to increase this beyond the 500MB that setting it to Large will provide. There are also some other adjustments that may help.
    1. If needed then follow these steps to dedicate some memory to the GUI and REST functions...
      1. Run these 4 commands one at at time. 
        tmsh modify sys db provision.extramb value 1024
tmsh modify sys db provision.tomcat.extramb value 64
tmsh modify sys db restjavad.useextramb value true
tmsh modify sys db provision.restjavad.extramb value 128

If these are run in the TMOS shell then leave off the "tmsh".
        Note: These are suggestions of where to start and may need further adjustment. The first is used to expand beyond the Large setting for MGMT.
      2. Then restart the services. 
        tmsh modify sys service tomcat restnoded restjavad
      3. Verify the changes to these variables. 
        tmsh list sys db provision.tomcat.extramb restjavad.useextramb provision.restjavad.extramb
      4. Save. 
        tmsh save sys config
        Note: These tmsh commands will not sync so they will need to be run on each BIG-IP. They should not cause a disruption in traffic.
      5. Wait 5 minutes then test
  3. If there are modules that are not in use then deprovision them. This is otfen seen with AVR in particular.
  4. Deprovsion LTM. In many cases you will not lose any functionality. If this is something you can look into then pleaese review... K17173140: Setting LTM Provision NONE does not disable licensed LTM functionality.
    1. The caveats for this are gone over in this document...K48278733: Syncookie Protection Behavior since V13.x and LTM being provisioned or not provisioned.
  5. Reduce the number of Topologies in use by using a Layered Deployement. SSL Orchestrator Advanced Use Cases: Reducing Complexity with Internal Layered Architecture (sometimes referred to us "tiered" architecture). Security rules generally equate to macros in an access per-request policy, so the more complex the VPE, the more CPU it consumes. Many of these complex architectures can be optimized simply by stepping back and identifying the usually consistent patterns that most of the topologies perform. In many cases, having 50 or more topologies will be doing the same combination of things – allow or block, intercept or bypass, send to a service chain, and egress a defined path. If you can identify this pattern, you can move SSL Orchestrator into a “layered” architecture, treating a smaller, mostly static set of topologies as FUNCTIONS.
    1. Doing this is beyond the scope of what can be done in F5 Support. If assistance is needed please contact F5 Professional Services .
  6. Consider using fewer topologies. K000092739: Maximum number of topologies allowed on SSL Orchestrator
    1. Doing this is beyond the scope of what can be done in F5 Support. If assistance is needed please contact F5 Professional Services .
