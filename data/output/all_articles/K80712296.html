K80712296: BIG-IQ 7.1 Upgrade fails during database conversion of ASM policies

Type
Support Solution
Published
2021-02-17
Updated
2023-02-21
Applies to
  • Virtual Editions
  • BIG-IQ Platforms
  • BIG-IQ
Source
https://my.f5.com/manage/s/article/K80712296

Description
When there are a sufficient large number of ASM Policy instances in the BIG-IQ database, upgrading to version 7.1 and later will fail during the database migration from toku to postgres that occurs as part of the upgrade.

Environment

  • BIG-IQ upgrade to 7.1.0 or later
  • ASM Policies present in BIG-IQ
  • Deployment snapshots containing ASM Policy deployments

Cause
After the initial boot and the post-boot activities occur, the bootstrap log (/var/log/bootstrap/bootstrap[date and time].out) and the GUI will show something like below:

When the total number of ASM Policy instances in the database exceeds 2442, mongo will be unable to complete some of the migration actions needed to convert the database to postgres, resulting in the upgrade failing during the post-boot tasks.

Each ASM Policy present in the configuration will result in a single ASM Policy instance (1:1 ratio) while Deployment Snapshots containing changes to ASM Policies deployed to BIG-IPs may result in a number of ASM Policy instances each, depending on the nature of the deployment. Each Deployment Snapshot contains a version of objects (like ASM Policies), to allow rollback to the snapshot's earlier state if desired. ASM Policy instances will be created in the database for each ASM Policy modified across every BIG-IP selected in the deployment and captured in the Snapshot. Multiple changes across multiple BIG-IPs can result in a single Deployment snapshot containing a number of ASM Policy instances.

The bug ID994737 has been opened for this upgrade issue.

Recommended Actions

There are two workarounds to allow the database conversion to succeed. An index can be manually created in mongo for the ASM Policies prior to initiating upgrade, or ASM Policy Deployment Snapshots can be deleted prior to upgrading.
  1. Manually create an index for ASM Policies in mongo
    This will create an index used during upgrade which then becomes inactive along with mongo and toku in 7.1+ after the upgrade completes and they are disabled.
    1. SSH to the BIG-IQ
    2. Confirm no index for ASM Policies currently exists
      mongo bigiqDb --eval "printjson(db.bigiqWorkingConfig.getIndexes())" | grep '"_value.generation"' -A4 -B2
      Note: This should return no result, indicating no index is present.
    3. Create the index
      mongo bigiqDb --eval 'db.bigiqWorkingConfig.createIndex( { "_value.generation": 1 } )'
    4. Confirm the index is now present
      mongo bigiqDb --eval "printjson(db.bigiqWorkingConfig.getIndexes())" | grep '"_value.generation"' -A4 -B2
      Note: The output should look like:
              {
                      "key" : {
                              "_value.generation" : 1
                      },
                      "ns" : "bigiqDb.bigiqWorkingConfig",
                      "name" : "_value.generation_1"
              }
    5. Close SSH session and proceed with upgrade
  2. Delete Deployment Snapshots
    This will remove all the ASM Deployment Snapshots present on the BIG-IQ, resulting in an inability to revert ASM Policy changes which occurred prior to the upgrade. Ensure all ASM Policies are in a desired state prior to deleting Deployment Snapshots.
    1. Log into the BIG-IQ GUI
    2. Go to Deployments -> Snapshots -> Web Application Security
    3. Click the name of a Deployment Snapshot, opening the detail window
    4. Click Delete in the upper right hand corner and confirm Delete in the following pop-up window
    5. Repeat steps 3 and 4 until all ASM Policy Deployment Snapshots have been deleted
    6. Proceed with upgrade

Additional Information
The impact of adding an additional index to toku (the first workaround) is negligible as toku can process many more database records than would be generated for ASM Policy instances. Since toku and mongo are disabled in 7.1, there is no need to remove the index after the upgrade completes. Utilizing the index allows for retention of the Deployment Snapshots however the upgrade itself may take longer due to the number of records contains in the Snapshots. Deleting the Deployment Snapshots is a more time-consuming process and prevents the ability to revert to older Snapshots, however it will result in a potentially shorter upgrade as there will be less records to convert to postgres.

To view the number of ASM Policy instances, ASM Policy instances from Policies and Policy instances from Deployment Snapshots, SSH to the BIG-IQ and run the following read-only query:

instances=$(mongo bigiqDb -quiet --eval 'db.bigiqWorkingConfig.find({"_value.kind": "cm:asm:working-config:policies:policystate"}).count()'); policies=$(mongo bigiqDb -quiet --eval 'db.bigiqWorkingConfig.distinct("_value.name", {"_value.kind": "cm:asm:working-config:policies:policystate"}).length'); echo "$instances ASM Policies instances. $policies from ASM Policies and $(($instances-$policies)) from Deployment snapshots."; unset instances; unset policies

Example output:
2803 ASM Policies instances. 319 from ASM Policies and 2484 from Deployment snapshots.

In this case deleting all of the Deployment snapshots will result in 319 ASM Policy instances remaining due to 319 ASM Policies being present.
