Topic

BIG-IP maintains a binary (machine-readable) version of the device's configuration and, in order to boot up more quickly, loads from there rather than from the text-based configuration in /config/bigip*.conf. Under certain rare conditions, the binary-based configuration may become mismatched to the text-based configuration.

You should consider using this procedure when you want to force the mcpd process to reload the configuration for situations such as, but not limited to, the following:

  • The text-based configuration (such as /config/bigip.conf) and the running configuration loaded in the mcpd process from the binary configuration image are out of synchronization.
  • The bigpipe load (BIG-IP 9.4.x or 9.6.x) or tmsh load config (BIG-IP 10.0.x) or tmsh load sys config (BIG-IP 10.1.0 or later) commands do not load the text configuration files into the running configuration.
  • The MAC address assignments need to be reset due to an errant binary configuration image such as the issue described in K10129: VIPRION clusters in a redundant pair may improperly share MAC addresses.
  • Configuration objects or health monitors fail to maintain their expected status and other troubleshooting steps have been exhausted.
  • Config Sync operations fail or generate errors and other troubleshooting steps have been exhausted.
  • iHealth erroneously shows objects such as nodes, pools, or pool members as not in use, despite being assigned directly to a pool or virtual server.  (Note, pools selected by an iRule will register as orphaned in iHealth and restarting mcpd will have no effect.)

Description

This procedure forces the mcpd process to reload the configuration from the text configuration files instead of from the binary-based configuration image.

Starting in BIG-IP 9.4.0, the mcpd process loads the text-based configuration files into the running configuration during the first boot up and builds a binary configuration image into the following two files:

  • /var/db/mcpdb.bin
  • /var/db/mcpdb.info

When the mcpd process is subsequently started, it loads the binary-based configuration image files into the running configuration instead of parsing, validating, and loading the text-based configuration files. As a result, the BIG-IP system starts processing traffic more quickly

In cases where the system is unable to load the binary-based configuration, or where the binary image is no longer accurate, you can correct the situation by forcibly reloading the configuration from the text-based configuration files.

Prerequisites

You must meet the following prerequisite before using this procedure:

  • You have root access to the Advanced Shell (bash)

Procedures

Force the mcpd process to reload the configuration

Important: In some cases, configuration changes might not be properly written to the disk during Sync operations. For example, this may occur when using auto-sync with save on auto-sync disabled. Before you proceed with the below steps, you should review the text-based configuration files in /config and /config/partitions/*/ to verify that the configuration you want and intend to load is present. If the intended configuration is not present in the files, you should run tmsh save /sys config partitions all and then run the steps to rebuild the binary configuration image.

Impact of procedure: BIG-IP system traffic processing is interrupted while the system restarts.

  1. Log in to the Advanced Shell (bash).
  2. Verify your BIG-IP configuration using this command:

    tmsh load sys config verify

    Note: This command is non disruptive to traffic processing on the BIG-IP system.

    Important: Ensure there are no errors. If you see warnings, you may continue but they should be addressed later. If you see ANY errors when the command completes, you should STOP IMMEDIATELY and either open a new case or inform the engineer with whom you are working.

  3. Create a UCS file to ensure you have a backup:

    tmsh save sys ucs <filename>.ucs

  4. Create an empty file with the file name forceload in the /service/mcpd directory.  To do so, enter the following command:

    touch /service/mcpd/forceload

    On multi-blade VIPRION/vCMP systems and F5OS tenants deployed across multiple slots/blades, enter the following command to run this command on all blades. You should use this on both multi-slot hosts and multi-slot guests. You do not need to run this if your system is a single-slot host or single-slot guest, but doing so should not have any negative impact on your system:

    clsh touch /service/mcpd/forceload

  5. To restart the BIG-IP system, enter the following command:

    reboot

    On multi-blade VIPRION/vCMP systems and F5OS tenants deployed across multiple slots, enter the following command to run this command on all blades:

    clsh reboot

  6. When the equipment recovers, a manual sync will be required.  Click on the "Sync required" link in the upper left, and follow the recommendation provided in the GUI.

Determine whether the configuration is loaded from the binary- or text-based files

You can determine which source was used to load the configuration by inspecting the /var/log/ltm file. When the configuration is loaded, the message The configuration DB has been initialized ... is logged. If the configuration is loaded from the binary image file, an additional message saying Configuration restored from binary image is also logged:

[root@bigip1:Active:Standalone] config # grep -A1 "configuration DB" /var/log/ltm
Nov 19 10:38:44 bigip1 notice mcpd[20187]: 01390002:5: The configuration DB has been initialized with 26130560 bytes of memory
Nov 19 10:38:44 bigip1 notice mcpd[20187]: 01070730:5: Configuration restored from binary image.
