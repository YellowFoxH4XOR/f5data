 Applies to

  VELOS chassis with BX520 blades running F5OS-C.

  Affected blades are those running F5OS-C earlier than 1.8.1-26929, and also any blade on a later release that has not yet had the corrected firmware applied. See "Fix" -- the software version alone does not determine whether a blade is affected.


  Symptoms

  Following a period of very high-rate ingress traffic -- for example a DDoS event -- legitimate application traffic traversing the affected blade is no longer forwarded correctly. In observed cases this presented as HTTP sessions failing or performing poorly once the high-rate traffic began.

  The distinguishing characteristic is that the loss is silent. Traffic entering the blade's queues does not reach its destination, no drop counter anywhere in the platform accounts for the difference, and no alarm is raised. In the analyzed case  approximately 25% of host-destined traffic was lost with no corresponding drops recorded.

   Cause

  The issue is a defect in the programmable hardware logic that implements the 100G MAC on the blade's network processing component.

  Traffic passing through this path is held briefly in an internal FIFO buffer. Normally, when that buffer approaches capacity, a back-pressure mechanism signals the upstream stage to pause so the buffer can drain. F5 Engineering has determined that this back-pressure mechanism contains a logic defect: in a narrow and specific set of traffic conditions, the pause is not applied when it should be, and the buffer overflows.

  The overflow corrupts frames as they traverse the chassis backplane. The receiving switch detects the corruption as frame check sequence (FCS) errors and discards the affected frames. Because the loss occurs in this way, it is not recorded by the  platform's normal packet-drop counters -- which is why traffic disappears without any drop being reported and without an alarm being raised.

  The defect is not related to the type of traffic involved. The hardware logic does not inspect or distinguish packet types; only the rate, packet size and burst characteristics of the traffic determine whether the condition is reached. A DDoS  event reliably produces that combination, which is why the issue has been observed in association with DDoS activity -- but the defect is not specific to DoS handling or to any DoS configuration.

  The conditions required are unusual, which is why the issue is not seen under normal production load.


  Diagnosis

  Where this defect is active, FCS error counters on the affected backplane switch ports increment continuously while the platform's packet-drop counters remain clean. That combination -- rising FCS errors with no corresponding drops -- is the  signature of this issue, and distinguishes it from congestion, which does increment drop counters.

  A second indicator is a mismatch between the packet rate entering the blade's queues and the rate leaving toward its destination. These rates should match; under this defect the output rate is measurably lower, with the shortfall unaccounted for.

  Confirming these counters requires diagnostic access to the backplane switch. If you observe the symptoms above, contact F5 Support and reference this article.


  Impact

  Legitimate traffic traversing an affected blade is lost. Because the loss is not reflected in drop counters and raises no alarm, it may not be visible to standard monitoring, and is often reported first as an application problem rather than a platform one.


  Workaround

  None. The defect is in hardware logic rather than in configuration or software policy, so it cannot be avoided by adjusting DoS profiles, rate limits, or any other configuration on the system.


  Fix

  Corrected firmware for the affected component first shipped in F5OS-C 1.8.1-26929 and is included in later releases.

  Important: running F5OS-C 1.8.1-26929 or later does NOT mean the corrected firmware is in use. The firmware is delivered with the software but applied per blade, and blades may continue to run the previous firmware after the software is  installed. F5 has confirmed chassis running F5OS-C 1.8.2 -- several releases beyond the fix -- on which the corrected firmware was present on the blade but not in use, with the majority of blades still running pre-fix firmware.

  Do not treat the F5OS-C version as evidence of remediation. Verify every blade individually.

 


  Verifying that a blade is running the corrected firmware

  From the F5OS-C CLI:

      show components

  For each blade, check the reported value of fw-version-fpga-vqf0. Two hardware variants exist and are identified by the leading digits of the running version:

      Running version begins 74.1.x     -> corrected at 74.1.31.0 or later
      Running version begins 74.80.x    -> corrected at 74.80.9.0 or later

  A blade reporting a value below the threshold for its variant has not had the corrected firmware applied and remains affected.

  On the 74.80.x variant only, a companion component must also be updated: check fw-version-fpga-tam0, corrected at 73.80.17.66 or later. On the 74.1.x variant that component is not affected by this defect and requires no action.

  This is a per-blade check. A chassis may be partially remediated, and confirming one blade does not confirm the others.
