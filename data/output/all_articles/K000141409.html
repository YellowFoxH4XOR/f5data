K000141409: Detecting versions of software other than Antivirus or Firewall as a part of an APM policy

Type
Support Solution
Published
2024-10-10
Updated
2024-10-10
Applies to
  • BIG-IP
  • BIG-IP APM: 17.1.1
Source
https://my.f5.com/manage/s/article/K000141409

Description

You would like to know if, using APM, there is any way to check a version of some application installed on User PCs as a part of an APM policy, for example, so that if the user has a new version he can proceed, and if the user has an old version he should be blocked.

Environment

Custom Software version check

Cause

A need to detect versions of software other than AV or FW.

Recommended Actions

1. The only native way to check any app's state/version is our AV check/FW check, and if your product does not qualify as such, we won't be able to check it that way. If you wish to see a full list of products we can detect for your current EPSEC version, you can log in to GUI and navigate to https://MANAGEMENTIP/sam/admin/vpe2/public/php/supportTable.php .

Note: Steps 2, 3 and 4 will require some knowledge of your application, so please reach out to the vendor if you need some assistance if we can do it any of those ways. These are also not fault-proof - since some of them only check for existence of an "x" thing ( like a file or a registry value), so if a user knows what exactly is being checked, then they can simply create it on their own and have the policy pass. Please make sure you understand this idea and its implications before proceeding. This is not an official solution, but rather an idea on how this can be accomplished for those who are interested in it.

2. If the process name for one of the processes that the app uses (and has running as the app runs) includes the version of that app (for example a process named 'chrome-v122'), you can use the "Windows Process" policy block to determine this. This block will check if particular Windows process exists, and based on that, will branch out the policy (allow/deny).

3. In a similar fashion we can use the "Windows File" policy block - if you know where the app files of your app reside on the client devices, you can go through them and see if any of them includes the version of this application as a file name (for example - C:/Program Files/Google/chrome-v122.exe) and if so - add a "Windows File" policy block to see if a file of this name exists and based on that, branch out the policy (allow/deny).

For example - on Windows devices - the C:\Program Files\CrowdStrike folder includes a file, the name of which includes us which version of CrowdStrike is installed.

4. The same story applies to the "Windows Registry" policy block - if you can verify if your app stores their version as a Registry key, you can use this policy element to check if a particular Windows Registry value exists or fetch the Windows Registry value, and based on that, branch out the policy (allow/deny).

5. If you are unable to find any of these (Steps 2, 3 or 4) then we will likely need a custom script. The script could check the version of your app, and based on that, create, for example, a file under C:/ . A file named, for example, chrome-allow-access-new-version.txt. You would have to create this script. If it notices an old version - it does not create the file, and if it sees the new version - it does create this file. Then you can simply add a "Windows File" policy block which will check for that file's existence, and based on that, branch out the policy (allow/deny).

As mentioned in point #1, there's unfortunately no way to check non-AV and non-FW software's details, so this is what we can try to do if there is such a need. This may require you to either look around the system to see if we have a Reg key/ File/ process by which we can determine that version of your app, or reach out to the vendor's support to ask where all of these versions are stored, or, as mentioned in #5 - push a script that will check this and create something that we can check as a part of the APM policy (Reg key/ File).
