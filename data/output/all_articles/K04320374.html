Description

System reports lot of logs in /var/log/ltm after upgrade to 14.x and above
example:

Suppressed 99 messages from /system.slice/httpd.service

Environment

  • Upgrade to 14.x or above
  • Monitoring system  which uses iControl REST API

Cause

Change in behavior of logs in versions above 14

Recommended Actions

Remove CustomLog by using following procedure:

  1. Remount /usr as read/write:

    mount -o remount,rw /usr

  2. Comment out the CustomLog parameters:

    awk '/CustomLog/ {print "#" $0;getline; print "#" $0;next} {print}' /defaults/config/templates/ssl.tmpl > /defaults/config/templates/ssl.tmpl.new

  3. Keep a backup of the original template file:

    mv /defaults/config/templates/ssl.tmpl /defaults/config/templates/ssl.tmpl.orig

  4. Move the new template file into place

    mv /defaults/config/templates/ssl.tmpl.new /defaults/config/templates/ssl.tmpl

  5. Rebuild the apache configuration file

    confpp

  6. Remount /usr as read-only

    mount -o remount,ro /usr     

Additional Information

These messages mean the system is under pressure and generating lots of messages. They are generated by apache (httpd) each time the iControl REST API or the GUI are accessed.

In 11.x the decision was made to filter these logs OUT of syslog-ng logs based on their log levels.

The flow of these spammy logs was therefore:

apache --> syslog-ng -> suppress/drop

However F5 introduced systemd in 14.x, in which logs additionally go through journald.

The flow therefore became:

apache --> journald -> syslog-ng -> drop

journald is now exposing some of the spam caused by apache which was previously hidden by syslog-ng.

To review which logs were suppressed use following command in CLI (bash):

journalctl -ex -u httpd.service

Under certain conditions, a restart of the journald daemon might be necessary.

To restart journald daemon use the following command in CLI (bash):

systemctl restart systemd-journald
