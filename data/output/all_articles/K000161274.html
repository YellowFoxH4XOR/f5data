K000161274: Incompatibility of transparent/translucent vlan-groups and shared VLANs in F5OS

Type
Support Solution
Published
2026-05-27
Updated
2026-05-27
Source

Description

On a VELOS chassis running F5OS-C or appliance running F5OS-A, BIG-IP tenant configured with translucent or transparent vlan-group may experience intermittent packet loss, pool member monitor flapping, or unicast traffic being incorrectly replicated to other tenants, after one or more of the VLANs belonging to that vlan-group is also assigned to an additional tenant — making the VLAN shared.

Symptoms include:

  • Intermittent ICMP packet loss to self-IPs on VLANs that are part of a vlan-group, packets being dropped on ingress.
  • Pool member monitors (ICMP, TCP) flapping down and up after a VLAN is shared between tenants
  • Unicast traffic (for example, ICMP replies, TCP flows) being received by tenants that should not be receiving it
  • Symptoms may persist after removing the VLAN from the additional tenants until the L2 state ages out or the partition is reconfigured.

Environment

Platform: VELOS chassis, rSeries appliances

Affected versions: F5OS-C 1.6.x, 1.8.x, F5OS-A 1.5.x, 1.8.x, TMOS v15.1.x and further.

 

Cause

Combining a VLAN-group with a shared VLAN creates an architectural incompatibility in how the F5OS layer handles L2 forwarding listeners as per current design.

When a VLAN is assigned to more than one tenant, the F5OS creates a special rebroadcaster listener that is needed to forward broadcasts as well as DLFs (Destination Lookup Failure packets) to the tenants that share the VLAN. The rebroadcaster listener can be seen in the "show vlan-listeners" output on partition, as per example below:

show vlan-listeners
                                                                                             
INTERFACE   VLAN  ENTRY TYPE     OWNER     NDI ID SVC VTC SEP DMS  DID  CMDS  MIRRORING  SERVICE IDS
....
TRUNK1       1111  RBCAST-LISTENER rbcast    4095   5  56  15  3   -   -   disabled   [ svc_id1 svc_id2 ]
....

For vlan-groups in translucent mode, BIG-IP TMM bridges traffic between two VLANs while flipping the locally-administered (LA) bit of the source MAC address. For example:

Original source MAC address (entering VLAN A): 00:50:00:00:00:01  (LA bit = 0)

Bit-flipped bridged source MAC address (exiting VLAN B): 02:50:00:00:00:01  (LA bit = 1)

This "bit-flipped" MAC is considered a new source MAC address that FPGA needs to learn.  FPGA creates a dynamic listener and not a static per-tenant listener for this bit-flipped MAC address. However, this entry is learned without a tenant service ID, as currently only static entries (such as tenant MAC address or masquerade MAC) are learned with tenant service ID. Since there is no service ID for this bit-flipped MAC address listener, it is associated with rebroadcaster listener.

Incoming unicast traffic that matches these bit-flipped MAC addresses as destination MAC will be using rebroadcaster listener and as a result traffic will be sent to all the tenants that share VLAN, including unicast traffic. The rebroadcaster listener is not designed for line-rate unicast and under certain load can cause packet drops.

The following nse_l2 fpga table (fpga forwarding table) output illustrates the problematic FDB entry:

# Defective: bit-flipped MAC learned without service ID, DID=F → routes to rebroadcaster:
mac                nti  l2_tag  entry_type  ifh.did  ifh.did_en  ifh.svc  ifh.svc_en
02:50:00:00:00:01  4095  3610   dynamic      F          1          0          0
#                                                                  ↑ svc=0 → rebroadcaster path

# Correct: tenant MAC with proper service ID:
00:50:00:00:00:01      4095  3623   L2-LISTENER  D          1      9          1
#                                                                  ↑ svc=9 → correct tenant
For transparent VLAN-groups, although there is no bit-flipping for MAC address, the MAC addresses of the endpoints are preserved after passing through BIG-IP tenant. As a result of that F5OS FPGA will need to learn them dynamically leading to the same issue. Thus same incompatibility described for translucent vlan-groups applies to transparent vlan-groups as well.
 
This issue is tracked under bug ID2230257.

Recommended Actions

1. Do not share VLANs used in VLAN-groups (preferred)

The most reliable and fast workaround is to ensure that VLANs that are members of a VLAN-group are assigned to only one tenant. Remove the shared VLAN assignment from any additional tenants, so the reboradcaster is not used.

Verify the current listener state in partition/appliance CLI by running "show vlan-listeners". If there is an RBCAST-LISTENER, the VLAN is shared.

2. Switch to opaque VLAN-group mode

In opaque mode, BIG-IP uses its own static tenant MAC address instead of a bit-flipped external MAC. The static MAC is pre-registered in the FDB and is not subject to dynamic learning issues.

# On the BIG-IP tenant CLI — change VLAN-group mode to opaque:
tmsh modify net vlan-group <vlan-group-name> mode opaque
tmsh save sys config
Note: Switching to opaque mode changes the bridging behavior and must be validated based on specific deployment.
 

3. Migrate to virtual-wire (vWire) solution

Virtual-wire is hardware-based equivalent of VLAN-group for L2 inline deployments. The vWire solution needs to be evaluated on a per-deployment basis.
