Topic

This article provides an example to implement an API authorization mechanism using session variables in BIG-IP APM's per-request policy.  You should consider using this procedure under the following condition:

  • You want to secure your APIs with an authorization mechanism against attacks such as Broken Object Level Authorization in OWASP API Security Top 10.

Description

You can secure your APIs with BIG-IP APM API protection against attacks by configuring authorization checks using BIG-IP APM session variables. BIG-IP APM processes API requests through a per-request policy. Through the per-request policy flow, you can extract a range of information from the API request, assign them to subsession or perflow variables and validate the values to ensure each request is authorized. The following table lists the different information you can use in a per-request policy.

Note: To view the list of variables, refer to the Perflow and subsession variables chapter of the BIG-IP Access Policy Manager: Visual Policy Editor manual. You can also enable BIG-IP APM debug mode to log them in the /var/log/apm file.
For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

This article provides an example of an implementation that validates that an API request is authorized to make the following client request:

GET https://api.f5example.com/v2/6d2f7c68-d11e-4707-b36a-af67cfc90ec4/orders/findByStatus?status=pending
Header: Authorization, Value: Bearer eyJ0eX[...] MQ8Er-JA

In this request, a GET method is sent to get the status of orders that have status=pending and the user includes his/her azureoid value in the path of the URL. Depending on the application logic, there may be the following restrictions:

  • The client app always includes the azureoid value of the user in the API request path as follows:

    https://api.f5example.com/v2/<azureoid>/<path>

  • The client app must include the JWT in the header of the request for authorization.
  • Only users that have specific Scope parameters in their JWT access token can make this API request.

Note: You can decode JWTs from MS Azure AD to get a range of information with debugger tools. For example, JSON Web Tokens - jwt.io. This link takes you to a resource outside of AskF5, and it is possible that the document may be removed without our knowledge.

Exploit

In Broken Object Level Authorization, bad actors can exploit this by replacing their azureoid value in the request path with another user's OID. This may enable them to retrieve orders belonging to other customers if no authorization checks are performed. For example:

GET https://api.f5example.com/v2/83413080-062e-4a34-9e6b-0acfadb4d20/orders/findByStatus?status=pending
Header: Authorization, Value: Bearer eyJ0eX[...] MQ8Er-JA

Authorization validation mechanism

You can use BIG-IP APM session variables as appropriate to implement an authorization mechanism. In this example, you validate if the azureoid value in the URI path matches the value extracted from the JWT. To do so, configure the following three items after the OAuth Scope agent in the per-request policy of your BIG-IP APM system:

Important: The authorization mechanism in this example validates only the azureoid and scope information as a single layer of protection. Depending on the application logic, your solution should include other checks.

  • A gating criteria that takes into account both the JWT and API request URL before the system creates a distinct subsession.
  • A variable assign item named Extract oid and assign value that extracts the azureoid value from the URL's path and assigns it to a variable, for example perflow.username.
  • A branch rule item named Validate azureoid and scope that compares the value of perflow.username with the actual value of the azureoid extracted from the JWT in the API request. This branch rule also validates that the JWT has the right scope.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You already have a BIG-IP APM API protection virtual server deployed.
  • This virtual server has a API Authentication and OAuth Scope agent in the per-request policy that verifies JWTs issued internally by Microsoft Azure Active Directory (AD).

If you require assistance to set up a BIG-IP APM API protection virtual server first, refer to K12744365: Quick deployment: BIG-IP APM API protection virtual server with Postman as OAuth client using Azure AD.

Procedures

To implement an authorization mechanism for this virtual server, perform the following procedures:

  • Open the API profile per-request policy in VPE
  • Configure the subroutine gating criteria
  • Create a variable assign item to extract the Azure OID and assign it to a variable
  • Create a branch rule item to verify API requests parameters

Open the API profile per-request policy in VPE

Perform all the procedures in this article in Subroutine: OAuth Scope Check AuthZ in the per-request policy in the Visual Policy Editor (VPE) of your API profile. To enter the subroutine in VPE, perform the following:

  1. Go to Access > API Protection.
  2. Select Edit next to your API protection profile to open the per-request policy editor.
  3. In VPE, scroll to the bottom and select the add icon (+) to expand Subroutine: OAuth Scope Check AuthZ.

Configure the subroutine gating criteria

By default, the Subroutine: OAuth Scope Check AuthZ gating criteria is set to expr { [ mcget {request.header.authorization} ] }. This means that the subroutine runs only when a request submits a different JWT. To enhance security, configure the gating criteria to take the API request URL into account as well so that the subroutine runs as long as there are any changes in the JWT and URL. To do so, perform the following in Subroutine: OAuth Scope Check AuthZ in VPE:

  1. Select Subroutine Settings / Rename
  2. For Gating Criteria, enter the following criteria to concatenate the JWT value and the API request URI:

    expr { "[mcget {request.header.authorization}]\\[mcget {perflow.category_lookup.result.url}]" }

  3. Optionally, adjust the other timeout settings as appropriate.
  4. Select Save.

Create a variable assign item to extract the Azure OID and assign it to a variable

Perform this procedure in Subroutine: OAuth Scope Check AuthZ in VPE to add a new variable assign item to extract the Azure OID value from the request parameter of the API request and assign the value to a variable.

  1. Select the add icon (+) at the Successful branch after the OAuth Scope agent.
  2. Select Assignment
  3. Select Variable Assign
  4. Select Add Item
  5. For Name, enter an appropriate name. For example:

    Extract oid and assign value

  6. Select Add new entry.
  7. Select change.
  8. For Custom Variable, enter the variable name:

    perflow.username

  9. For Custom Expression, enter an expression to extract the Azure OID from the request parameter of the URL. For example:

    Note: This expression works only specifically for the API request in this example. Depending on your application logic, you should use your own expression. Bad actors may also manipulate URL requests, you should use BIG-IP Advanced WAF to validate URL requests.

    expr { [lindex [split [mcget {perflow.category_lookup.result.url}] /] 4] }

  10. Select Finished.
  11. Select Save.

Create a branch rule item to verify API requests parameters

Perform this procedure in Subroutine: OAuth Scope Check AuthZ in the VPE to use a branch rule item to verify the Azure OID value in the API request and the scope value in the JWT.

  1. Select the add icon (+)  after the variable assign item created in the previous procedure.
  2. Select General Purpose.
  3. Select Empty.
  4. Select Add Item.
  5. Enter an appropriate name for the item. For example:

    Validate azureoid and scope

  6. Select Branch Rules.
  7. Select Add Branch Rule
  8. Enter an appropriate name for the branch. For example:

    Correct oid and scope

  9. Select change.
  10. Select Advanced.
  11. Enter the following expression to validate the Azure OID and scope values.

    Note: This example validates the Azure OID in the API request matches the one in the JWT and the requestor has the member, premium and read scopes.

    expr { [mcget {perflow.username}]==[mcget {subsession.oauth.scope.last.jwt.oid}] && [mcget {subsession.oauth.scope.last.jwt.scp}] == "member premium read" }

  12. Select Finished.
  13. Select Save.
