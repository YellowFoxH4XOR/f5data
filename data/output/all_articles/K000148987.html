K000148987: Client certificate verification for 2 locations on the same hostname does not work

Description

When using NGINX Plus, there may be a need to implement different configurations for the same hostname based on client requirements. For example, one client might require client certificate verification, while another does not. A straightforward attempt to achieve this using ssl_client_certificate in location blocks will result in configuration errors, as this directive is not valid within location blocks.

Environment

  • NGINX Plus

Cause

The root cause lies in the placement of the ssl_client_certificate directive. This directive is specific to the SSL/TLS handshake and must be configured at the server block level. It cannot be used within location blocks because the SSL/TLS handshake occurs before the location block logic is applied. Thus, attempting to set ssl_client_certificate within a location block leads to a failure in the configuration.

Recommended Actions

To accommodate different client requirements under the same hostname, separate server blocks should be created. Each block can apply distinct configurations, such as enabling or disabling client certificate verification. This separation ensures that SSL/TLS settings are correctly handled during the handshake process, aligning with NGINX's requirements.

 

Server Block for Client 1 (No Client Certificate Verification)

server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate           /path/to/server.crt;
    ssl_certificate_key       /path/to/server.key;

    location /client1 {
        proxy_pass http://backend.example.com/api/routing-keys/hook-a;
        proxy_set_header Host $http_host;
    }
}

Server Block for Client 2 (With Client Certificate Verification)

server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate           /path/to/server.crt;
    ssl_certificate_key       /path/to/server.key;

    ssl_client_certificate    /path/to/client2.pem;
    ssl_verify_client         on;
    ssl_verify_depth          2;

    location /client2 {
        proxy_pass http://backend.example.com/api/routing-keys/hook-b;
        proxy_set_header Host $http_host;
    }
}

 

In this solution, separate server blocks are created for each client. Each server block specifies the appropriate client certificate verification settings or omits them as needed. This approach ensures that SSL/TLS requirements are properly applied during the handshake process.
