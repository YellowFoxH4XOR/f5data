When compression is enabled for the HTTP profile, the BIG-IP system reads the Accept-Encoding header of a client request, and determines which content encoding method is preferred by the client. The BIG-IP system then removes the Accept-Encoding header from the request and passes the request to the server. Upon receiving the server response, the BIG-IP system inserts the Content-Encoding header, specifying either gzip or deflate based on the compression method specified by the client in the Accept-Encoding header.

Compression Methods

The HTTP profile supports the deflate and gzip compression methods. The deflate method differs from gzip in that it does not use an internal header or trailer. Because it is not necessary to calculate the running checksum the way that gzip does, the deflate method is generally faster. Each of the following compression settings apply to the gzip and deflate methods of compression:

  • Compression Buffer Size
  • gzip Compression Level
  • gzip Memory Level
  • gzip Window Size

The header contains basic information (for example, the optional last-modification time of the original file, the OS type, and so on). The trailer contains a running checksum of the input file, as well as the original file length.

Compression Buffer Size

This value is the maximum amount of compressed data that the BIG-IP system will buffer in order to preserve the Content-Length header for a connection. The Content-Length header must be set to the size of the compressed content; therefore, the BIG-IP system must retain the headers and wait until the entire response is compressed before rewriting the headers and sending the content to the client.

In BIG-IP 9.0.0 - 9.3.x, if this compression buffer size is exceeded, the Content-Length header is deleted and the BIG-IP system forces a Connection: Close header into the stream. This parameter does not have an effect on streams that do not contain a Content-Length header due to chunking.

However, in BIG-IP 9.4.0 and later, if the compression buffer size is exceeded, the BIG-IP system preserves the Content-Length header and sends out the entire response.

You can configure response chunking by modifying the Response Chunking setting in the Settings section of the HTTP Profiles property page. The optimal setting for compression under most circumstances is Rechunk.

gzip Compression Level

This setting dictates the level of compression that is applied to the connection. The lowest value is 1 and the highest value is 9. A lower number provides a lower, but faster compression ratio. A higher number provides a higher compression ratio; however, it requires more processing, which makes it slower. The default setting is level 1.

You can increase the level (up to 9), for a higher compression ratio at a slower rate. However, the benefit of a marginally higher compression ratio is usually not a major advantage when weighed against the extra CPU cycles required to achieve the higher ratio.

gzip Memory Level

This value specifies the amount of memory that the compression library (zlib) uses for its internal compression buffers. The default (8 kilobytes) is the optimal setting for the most common cases. However, sites that primarily serve larger files may benefit from increasing this value. You must take into consideration the average size of the files that are being compressed when you change this setting.

Note: Increasing the gzip memory level value can increase the speed of the compression process, but at the expense of the use of more memory per connection.

gzip Window Size

This setting dictates the amount of memory that is used for the compression history buffer. This value is similar to gzip Memory Level, but zlib uses the value differently. Like the gzip Memory Level setting, sites that primarily serve larger files may benefit from increasing this value. You must take into consideration the average size of the files that are being compressed when you change this setting.
