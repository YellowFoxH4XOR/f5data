Description

By default, DNS Express stores the zone data in an efficient disk based database located under /shared/zxfrd, and uses that file to answer queries.  To improve performance further, F5 provides the ability to store the database entirely in memory blocks, called huge pages, though doing so decreases the total memory available to the tmm process.

To enable memory storage, set the DB key "DNSExpress.HugePages" to a non zero number, and restart the tmm process (this will be service impacting). The variable controls the number of 2MB pages that tmm will dedicate to DNS express usage.  

When huge pages are used, the database is primarily stored in a memory based filesystem mounted at /dev/mprov/zxfrd, but can be copied periodically to the files under /shared/zxfrd, in order to provide initial zone data after the BIG-IP device has been rebooted (restarting tmm without rebooting does not delete the database), using the db key "DNSExpress.PersistHugePages" to "True"

The timing of the writes to disk is controlled by a third db key - "DNSExpress.DBWriteDelay", which sets the amount of time, in seconds, where the zxfrd process commits any changes it has received through zone transfers to the tmm process. If huge pages are being used, this also causes the database to be copied to /shared/zxfrd.  

When using huge pages, tmm must reserve a block of memory for DNSX during startup, and can not resize this block dynamically, therefore it must be sufficiently large to accommodate all the data received, as well as the effects of memory fragmentation as records are deleted and created, and also uncommitted memory pages pending a write to disk.   If insufficient memory is available, symptoms can include the zxfrd process crashing with a SEGV signal and writing a core image to disk, and tmm responding to DNS queries with stale or incomplete data.

If Huge Pages are to be used, determine an appropriate value for DNSExpress.HugePages, using the following guidance.

Environment

  • DNSExpress
  • GTM/DNS

Cause

None

Recommended Actions

The actions or steps required to address the topic covered in the description.
Example:

  1. Start with huge pages set to 0, as this mode does not impose an upper limit on the size of the database. If huge pages are already set to 0, skip this step.
    tmsh modify sys db dnsexpress.hugepages value 0
    bigstart restart tmm zxfrd # This will restart tmm and be service impacting
  2. Check the size of the existing disk-based database:du -sh /shared/zxfrd
    3.9G    /shared/zxfrd
  3. Multiply the number displayed by 2.5, and round  up,  for a value that will provide room for growth:
    • 3.9 * 2.5 ==> 9.75 GB  
    • => 10 GB   
  4. Convert to MB, then divide by 2, as each huge page is 2MB in size: 
    • 10 * 1024 / 2
    • => 5120
  5. Make the changes
    (bigip)# tmsh modify sys db dnsexpress.hugepages value 5120
    (bigip)# tmsh modify sys db dnsexpress.persisthugepages value true
    (bigip)# bigstart restart tmm zxfrd # service impacting

Additional Information

Whenever the value of DNSExpress.HugePages is changed, particularly if it is changed from zero to a non-zero value, the tmm and zxfrd processes must both be restarted concurrently to effect that change, as they both access the same database files.   If they are not both restarted, a situation can occur where zxfrd is stuck in a restart loop, or is updating database files that tmm isn't using. To avoid these situations, make the changes to the db keys only during a maintenance window, when tmm and zxfrd can be restarted immediately afterwards.
