Overview

Note: For information about upgrading an active/standby high availability pair, refer to K11215: Upgrading an active/standby BIG-IP high availability pair (9.x - 10.x).

An active-active BIG-IP high availability pair consists of two systems, both operating in active mode and handling traffic simultaneously. The traffic is divided between the two systems by manually assigning some virtual servers to each unit. In the event that one of the systems fails, the surviving unit picks up the traffic of the failed unit (in addition to its own).

BIG-IP systems in an active-active configuration determine each other's availability based on heartbeat detection. However, active-active systems require exchanging more information than just the single bit used in an active/standby configuration. For this reason, as part of setting up an active-active BIG-IP high availability pair, an administrator must configure network failover. Serial cable failover alone is not sufficient.

Note: Beginning with BIG-IP version 10.0.0, this requirement is enforced. If network failover is not enabled for an active-active BIG-IP high availability pair, the systems remain in an offline state. In previous versions, the systems will generally work, but you may experience some issues during a failover or failback.

Note: Beginning with BIG-IP 9.3.0, you can configure network failover to use the management interface instead of a TMM interface.

BIG-IP systems in an active-active high availability pair also communicate with each other over the network to exchange information required by the following features:

  • Connection mirroring
  • Persistence mirroring

The standard upgrade procedure calls for upgrading one system in the high availability pair while the peer system temporarily runs the older version. However, because active-active systems use network failover, a BIG-IP system administrator must consider the following:

  • Will the new software version use the same transport protocol and port for network failover as the old software version?
  • Will the network failover payload of the new software version be compatible with that of the old software version?

If during the upgrade procedure the systems in the active-active high availability pair are running BIG-IP versions that do not meet these requirements, network failover will not function. This behavior usually results in an improper active-active situation and ultimately in traffic disruption.

The network failover payload of a BIG-IP system is likely to be incompatible with that of another BIG-IP system running a new major or minor release. This is because when a new software version introduces enhancements to the network failover feature, the network failover payload is also likely to change. For example, although BIG-IP 9.4.8 and BIG-IP 10.0.0 use the same network failover transport protocol and port (UDP port 1026), their network failover payloads are different and incompatible.

The aim of this article is to provide an upgrade procedure that will result in zero or minimum traffic disruption. To upgrade an active-active BIG-IP high availability pair, perform one of the following procedures:

  • Upgrading an active-active BIG-IP high availability pair configured with network failover (over a TMM interface)
  • Upgrading an active-active BIG-IP high availability pair configured with network failover (over the management interface)

Note: F5 strongly recommends that you have a serial console connection open to each unit for the duration of the upgrade. This action allows you to follow an installation through all its stages, making it possible to detect any errors or premature interruptions of the installation process.

Note: Customer configurations and environments vary. Therefore, F5 recommends that you test the upgrade procedure in a test environment first, and then upgrade the production units during a designated maintenance window.

Note: In the following procedures, F5 assumes that at the time of the upgrade, both units will be available and handling their respective traffic.

Upgrading an active-active BIG-IP high availability pair configured with network failover (over a TMM interface)

  1. Read the release notes and any known issue articles or the BIG-IP version to which you are upgrading.
  2. Reactivate the license of both units. You can use the Configuration utility to reactivate a system's license; to do so, navigate to System > License and click Re-activate.

    Note: For more information about why this step is required, refer to K7727: License activation may be required prior to software upgrade.

  3. Create a UCS backup of each unit by running the following command:

    bigpipe config save /config.ucs

    Note: For more information about UCS archives, refer to K4423: Overview of UCS archives and K10245: BIG-IP UCS installation and licensing behavior.

  4. Copy the UCS archives off the units to a safe location on the network.
  5. Copy the software image and its associated MD5 to both units, and verify the integrity of the image against its MD5.

    Note: If you are performing the upgrade using an Enterprise Manager, you may skip this step.

  6. If you are using serial cable failover in addition to network failover, disconnect the serial failover cable from the units. Serial cable failover is superfluous and may unnecessarily complicate the upgrade procedure.
  7. Failover the traffic of Unit ID 2 to Unit ID 1. To do so, type the following command on Unit ID 2:

    bigpipe failover standby

  8. Confirm that Unit ID 1 is now handling the traffic of both units. To do so, type the following command on each unit:

    bigpipe unit

    Unit ID 1 should return the following output:

    UNITS  1 2

    Unit ID 2 should return the following output:

    UNITS

  9. On Unit ID 2, disconnect all network cables except that of the management interface. Alternatively, you may shut down the interfaces on the upstream devices.

    Note: From this point forward, Unit ID 2 will effectively be isolated from the production network.

  10. Launch the install on Unit ID 2. For specific instructions, refer to the release notes of the software version you are installing.

    Note: Once the installation has completed and the BIG-IP system has rebooted, Unit ID 2 will set itself as active. However, because it is isolated from the network and the two units cannot talk, Unit ID 1 will continue to process the traffic of both units.

  11. Confirm that Unit ID 2 has successfully imported the old configuration and that no errors are returned when you issue the bigpipe load command from the command line.

    Note: Steps 12 through 14 will transition traffic to the newly-upgraded Unit ID 2. Complete these steps as quickly as possible to minimize the downtime.

  12. On Unit ID 1, disconnect all network cables except that of the management interface. Alternatively, you may shut down the interfaces on the upstream devices.

    Important: Upon execution of this step, both units will be isolated from the network and all traffic will be temporarily stopped until Step 14 is completed.

  13. Reconnect all network cables to Unit ID 2 (or re-enable the relative interfaces on the upstream devices).
  14. Flush the L2 databases of the upstream devices, so that they may now begin forwarding traffic to Unit ID 2 instead.

    Note: If for some reason you are unable to flush the L2 databases of the upstream devices, you may trigger Unit ID 2 to send another round of gratuitous ARPs by restarting its services. To do so, type the bigstart restart command.

  15. Confirm that Unit ID 2 is successfully passing the traffic of both units.

    Note: If any issues occur during this test, gather all appropriate data (for example, qkviews, full logs, traffic captures, and core files), and contact F5 Technical Support before rebooting the unit into the previous software version.

  16. Launch the install on Unit ID 1.

    Note: Once the installation has completed and the BIG-IP system has rebooted, Unit ID 1 will set itself as active. However, because it is isolated from the network and the two units cannot communicate with one another, Unit ID 2 will continue to process the traffic of both units.

  17. Confirm that Unit ID 1 has successfully imported the old configuration and that no errors are returned when you issue the bigpipe load command from the command line.

    Note: If you do not complete Steps 18 through 20 and you bring the interfaces of Unit ID 1 back up while both systems are active and attempting to serve the traffic of both units, you will experience an improper active-active situation and possibly some additional downtime. To avoid this, perform Steps 18 through 20.

  18. On Unit ID 1, stop all services by entering the following command from the command line:

    bigstart stop

    Note: If you are upgrading a VIPRION platform, enter the clsh bigstart stop command instead. This command is the equivalent of running bigstart stop on every blade.

  19. Reconnect all network cables to Unit ID 1 (or re-enable the relative interfaces on the upstream devices).
  20. On Unit ID 1, start all services by entering the following command from the command line:

    bigstart start

    Note: If you are upgrading a VIPRION platform, enter the clsh bigstart start command, instead. This command is the equivalent of running bigstart start on every blade.

  21. Allow approximately 60 seconds and then verify that each unit is processing only its own traffic. To do so, type the following command on each unit:

    bigpipe unit

    Unit ID 1 should return the following output:

    UNITS  1

    Unit ID 2 should return the following output:

    UNITS  2
