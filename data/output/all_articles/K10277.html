K10277: Idle NTLM-authenticated sessions are not reused when the NTLM profile is applied without a clientssl profile

Known Issue

This is the result of a known issue. When an NTLM profile is configured on a virtual server, the BIG-IP system always sets the secure attribute on the NTLM connection pool cookie, regardless of whether the virtual server is configured with a clientssl profile.

If no clientssl profile is enabled on the virtual server handling the request, the virtual server sends a secure cookie to the browser. However, since the browser is communicating with the virtual server using HTTP, it will not present the secure cookie for subsequent requests to that virtual server. As a result, idle NTLM-authenticated connections are never re-used.

Note: The NTLM connection pool cookie is named NTLMconnpool by default.

Note: A virtual server must be configured with a clientssl profile to be capable of accepting HTTPS connections.

Note: If an HTTPS virtual server is also configured for the same domain name, the browser submits the secure cookie for connections to the HTTPS virtual server, as expected.

F5 Product Development tracked this issue as CR122393, and it was fixed in BIG-IP version 10.1.0. For information about upgrading, refer to the BIG-IP LTM, ASM, or WebAccelerator release notes.

Additionally, this issue was fixed in cumulative hotfix Hotfix-BIGIP-10.0.1-342.0-HF1 issued for BIG-IP version 10.0.1. You may download this hotfix or later versions of the cumulative hotfix from the F5 Downloads site.

Additionally, F5 Product Development is tracking a request for enhancement as CR122396 to provide an informational warning regarding the credential theft exposure potential of configuring NTLM connection pooling without also configuring a clientssl profile.

Workaround

You can avoid this issue by applying a clientssl profile to the virtual server that is configured with the NTLM profile.

Note: A virtual server configured with a clientssl profile typically accepts only HTTPS connections. If your application is not compatible with SSL offloading, you may not be able to use this workaround.

When a virtual server is configured to use an NTLM profile, but is not configured to use a clientssl profile, you can work around this issue by using an iRule similar to the following example to remove the secure attribute from the cookie:

when HTTP_RESPONSE {
HTTP::cookie secure NTLMconnpool disable
}

Important: F5 does not recommend removing the secure attribute from the cookie. If the NTLM cookie is transmitted in cleartext, the virtual server is susceptible to man-in-the-middle attacks (exploits in which the attacker snoops the authentication messages, then accesses the server using previously authenticated flows). Using an HTTPS virtual server with a clientssl profile applied ensures that the authentication stream is always encrypted.
