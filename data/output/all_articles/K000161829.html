K000161829: HTTP/2 connections might get stalled on the BIG-IP

Published

Applies to

  • BIG-IP LTM: 17.1.0, 17.1.2, 17.1.1, 17.5.X, 17.1.X, 17.5.1, 17.5.0, 17.1.3
Source

Description

HTTP/2 traffic might stop mid-transfer until an idle-timeout is triggered.

The observed symptoms will be that an HTTP/2 client might be able to download contents on some streams, while others get stalled. On the stalled streams, HEADERS might be received, and the client presents a response code, but the DATA frames above the HTTP/2 profile's write size (default 16 KB) will not be delivered, and the connection goes idle until a timeout. In the server-side, it will be observed that the BIG-IP stops processing traffic, i.e. the reception buffer will eventually get full, but it will not be consumed by the BIG-IP; and the connection will be an exchange of TCP Zero Window and Zero Window Probe until a timeout happens.

Environment

Product: BIG-IP LTM

Feature: HTTP/2

Configuration:

  • Virtual server using an HTTP/2 profile.
  • HTTP/2 profile configured with a Frame Size that is equal or higher than Write Size. 

Cause

This is a consequence of Bug ID 2331445.

Answer/Recommended Actions

A possible workaround is decreasing the Frame Size below the Write Size value on the HTTP/2 profile.

Example showing a non-default Frame Size and Write Size:

ltm profile http2 custom_http2_profile {
    app-service none
    defaults-from http2
    frame-size 8191   # Lower the Frame Size below Write Size
    write-size 8192
}

Note: Consider carefully reviewing K04412053: Overview of the BIG-IP HTTP/2 profile. Frame Size modifications can impact performance and reduce/increase concurrency among different HTTP/2 streams.
