K000163297: NGINX One Metrics Missing When the NGINX Plus API Is Disabled or Misconfigured

2026-09-10
Updated
2026-09-10
Applies to

  • F5 Distributed Cloud
Source

Description

Detailed NGINX Plus traffic and network metrics are unavailable in NGINX One even though the NGINX Agent reports the instance as healthy.

Symptoms may include:

  • Missing instance, HTTP, TCP, or traffic telemetry.
  • No Found NGINX Plus API message in the NGINX Agent log.
  • Newly added NGINX configuration not appearing in the NGINX One configuration view.
  • NGINX rejecting the API configuration with:

    nginx: [emerg] "server" directive is not allowed here

The NGINX Agent can report healthy management-plane communication even when the local NGINX Plus API required for detailed metrics is unavailable.

Environment

  • NGINX Plus.
  • NGINX Agent.
  • NGINX One Console instance metrics and traffic telemetry.
  • NGINX Plus API configured on a dedicated listener.
  • NGINX configuration includes additional configuration within the http {} context.
  • Detailed metrics require:
    • An active NGINX Plus API.
    • status_zone directives on monitored application servers and, where applicable, location blocks.
    • An NGINX Agent API URL that matches the active API listener and protocol.
    • A valid NGINX Agent authentication token.

Cause

One or more of the following conditions can prevent detailed metrics from being collected:

  • The NGINX Plus API configuration is commented out or inactive.
  • No active status_zone directives are configured.
  • The NGINX Agent API URL uses HTTPS while the NGINX Plus API uses plain HTTP, or vice versa.
  • The NGINX Agent configuration does not contain the required authentication token.
  • Duplicate API server blocks use the same listener.
  • The API server block is placed outside the http {} context.

Successful messages such as INSTANCE_HEALTH_STATUS_HEALTHY and Successfully sent health status update confirm management-plane communication only. They do not confirm that the local NGINX Plus API has been discovered or that detailed traffic metrics are available.

Recommended Actions

  • Configure the NGINX Plus API in the correct context

    Place the API configuration in an included configuration section loaded from within the http {} block:

    server {
       listen 9000;

       location /api/ {
          api write=on;
       }

       location = /dashboard.html {
          root /usr/share/nginx/html;
       }
    }

    Do not place the server block at the top level of the main NGINX configuration outside the http {} context.

  • Remove duplicate API listeners

    Use only one API server block for the selected listener. Combine the API and dashboard locations into that block and remove duplicate definitions that listen on the same port.

  • Restrict API access

    Do not expose the NGINX Plus API publicly. Restrict access with appropriate allow and deny rules, firewall controls, or authentication.

    Example:

    server {
       listen 9000;

      allow 127.0.0.1;
       deny all;

       location /api/ {
          api write=on;
       }

       location = /dashboard.html {
          root /usr/share/nginx/html;
       }
    }

  • Configure status zones

    Add status_zone to each monitored application server and, where applicable, location block:

    server {
       listen <application-listener>;
       status_zone <server-zone-name>;

       location / {
          status_zone <location-zone-name>;
          proxy_pass <existing-upstream>;
       }
    }

    The listener, upstream, and zone names must match the existing application configuration.

  • Correct the NGINX Agent API settings

    In the NGINX Agent configuration:

    • Configure the required authentication token.
    • Set data_plane_config.nginx.api.url to the active NGINX Plus API listener.
    • If the API uses plain HTTP, use an HTTP URL and remove TLS and CA settings associated with HTTPS.
    • If TLS is enabled on the API listener, use the corresponding HTTPS URL and valid certificate settings.
  • Validate and reload NGINX

    Run:

    sudo nginx -t

    Resolve any syntax errors before applying the configuration. After the test succeeds, reload NGINX:

    sudo nginx -s reload
  • Restart the NGINX Agent and verify API discovery

    Run:

    sudo systemctl restart nginx-agent
    sudo journalctl -u nginx-agent --no-pager | grep "Found NGINX Plus API"

    The expected log message is:

    Found NGINX Plus API

  • Verify service connectivity

    Ensure the NGINX Agent can reach the NGINX One service endpoint over TCP port 443. Confirm that outbound firewall and network controls permit the required connection.

  • Review metrics

    After the API is discovered and NGINX has been reloaded, allow time for metric collection. Then review the instance metrics and traffic dashboard again.

  • Collect diagnostics if the issue persists

    Collect sanitized versions of the following:

    • NGINX Plus version.
    • NGINX Agent version.
    • NGINX Agent configuration.
    • Active NGINX configuration.
    • Output of sudo nginx -t.
    • Output of sudo systemctl status nginx-agent --no-pager.
    • Recent output of sudo journalctl -u nginx-agent --no-pager -n 100.
    • NGINX diagnostic package, if required.

    Remove all tokens, API keys, credentials, and other sensitive information before sharing diagnostic data.

Additional Information

  • INSTANCE_HEALTH_STATUS_HEALTHY and Successfully sent health status update indicate that the NGINX Agent is communicating with the management plane. They do not confirm NGINX Plus API discovery.
  • The configuration view may not immediately reflect newly added NGINX configuration. Verify the effective running configuration on the host and confirm API discovery in the NGINX Agent log.
  • If NGINX rejects a server directive, verify that the configuration is loaded inside the http {} context.
  • Confirm that duplicate API listeners have been removed.
  • Ensure that the NGINX Agent API protocol matches the protocol configured on the NGINX Plus API listener.
