Topic

Intermediate System to Intermediate System (IS-IS) is a link-state routing protocol which operates by flooding link state information through a network of routers. This allows IS-IS routers to converge route information faster and more efficiently. Each IS-IS router independently builds a database of the network's topology by aggregating the flooded network information.

Description

One of the advanced routing protocols that the BIG-IP system supports is the IS-IS protocol, a link-state routing protocol, which uses a graph traversal algorithm to compute the best path through the network.

Understanding the BIG-IP route tables

The BIG-IP system has two routing tables; the system uses the kernel table to route BIG-IP system management traffic, and the Traffic Management Microkernel (TMM) table to route load-balanced traffic. To add routes, you can enter the routes statically by using the Configuration utility or the command line, or dynamically if the system is licensed for the BIG-IP Advanced Routing Module (ARM).

The following elements must be in place before you configure IS-IS on the BIG-IP system:

  • The BIG-IP system must have the IS-IS ARM license.
  • The tmrouted process must run on the BIG-IP system in order for dynamic routing to function. To verify whether tmrouted is running, type the following command at the command line:

    bigstart status tmrouted

    To start the tmrouted process, type the following command:

    bigstart start tmrouted
  • IS-IS must be enabled. To verify whether IS-IS is enabled, type the following command at the command line:

    zebos check

    If IS-IS is enabled, the zebos check command returns output that appears similar to the following example:

    nsm     is running [22319]
    imi     is running [22317]
    isisd   is running [22320]

    If IS-IS is not enabled, refer to the following articles for information about starting BIG-IP ARM:
     
    • K13802: Enabling dynamic routing protocols for a route domain
    • K8261: Enabling a dynamic routing protocol (9.x - 11.1.0)
  • You must configure port lockdown to allow the IS-IS protocol on all self IP addresses for the routers to communicate with. For information about port lockdown, refer to K13250: Overview of port lockdown behavior (10.x - 11.x).

Advanced routing daemons

The tmrouted process is the routing table management daemon that updates the TMM routing table based on the kernel routing table. The tmrouted process depends on the mcpd and tmm daemons. If either of these daemons restart, the tmrouted process also restarts.

The tmrouted process starts and supervises the ZebOS daemons. ZebOS daemons are divided into the following two categories:

  • Core daemons:
     
    • nsm

      The nsm daemon is the ZebOS Net­work Services Module (NSM) daemon.
       
    • imi

      The imi management daemon allows the system administrator to configure and monitor ZebOS daemons through a centralized connection.
  • Protocol daemons:
     
    • bgpd
    • isisd
    • ospfd
    • ospf6d
    • ripd
    • ripngd

ZebOS process startup is controlled by the presence of BIG-IP ARM license keys. Protocol daemons are started if they are licensed and enabled. Core daemons are started if at least one protocol daemon is licensed and enabled.

The tmrouted process handles SIGCHLD signals and restarts ZebOS daemons as necessary. The tmrouted process performs the following actions when a ZebOS daemon restarts:

  • Core daemon exits
    • Removes all dynamic routes
    • Stops all remaining ZebOS daemons
    • Exits and restarts
  • Protocol daemon exits
    • Restarts the protocol daemon

Advanced routing daemon logging

The ZebOS logs to the /var/log/zebos.log file. Additional messages are logged to the /var/log/daemon.log and /var/log/ltm files. The isisd process information is logged for IS-IS daemon-specific issues, and nsm and imi daemon information is logged for core ZebOS daemon-related issues.

If a core ZebOS daemon exits, an error message that appears similar to the following example is logged to the /var/log/daemon.log file:

LOGIN: Re-starting tmrouted

In addition, error messages that appear similar to the following example are logged to the /var/log/ltm file:

mcpd[5157]: 01070410:5: Removed subscription with subscriber id isisd

Enabling debug logging

When you troubleshoot an issue with a ZebOS daemon, it may be necessary to create a debug log file and enable debug logging. To create a debug log file and enable debug logging, perform the following procedure:

Impact of procedure: Enabling debug logging for an advanced routing protocol may result in significant logging information being written to the system log files.

  1. Log in to the BIG-IP command line.
  2. To access the IMI command line shell, type the following command:

    imish
  3. To enter enable mode, type the following command:

    enable
  4. From the prompt, to enter configuration mode, type the following command:

    config terminal
  5. From the prompt, to create the debug log file, type the following command:

    log file /var/log/zebos.log
  6. Exit configuration mode by typing the following command:

    end
  7. To write the configuration, type the following command:

    write
  8. Once the debug log file is defined, enable debug logging by typing the following command:

    debug isis all
  9. To verify that IS-IS debug logging is enabled, type the following command:

    show debugging isis

    For example, the following output indicates that IS-IS debug logging is enabled:

    IS-IS debugging status:
      IS-IS Interface FSM debugging is on
      IS-IS Neighbor FSM debugging is on
      IS-IS events debugging is on
      IS-IS PDU debugging is on
      IS-IS lsp debugging is on
      IS-IS spf debugging is on
      IS-IS NSM debugging is on
  10. To enable debug logging for NSM, type the following command:

    debug nsm all
  11. To verify that NSM debug logging is enabled, type the following command:

    show debugging nsm

    For example, the following output indicates that NSM debug logging is enabled:

    NSM debugging status:
      NSM event debugging is on
      NSM packet detail debugging is on
      NSM kernel debugging is on
      NSM HA all debugging is on
  12. You can disable IS-IS/NSM debugging by typing the following commands:
    • IS-IS

      undebug isis
    • NSM

      undebug nsm

Verifying routes

You should verify that routes are advertised from the IMI command line shell. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP command line.
  2. To access the IMI command line shell, type the following command:

    imish
  3. To show the IP route information, type the following command:

    show ip route

    For example, the following command output displays the IP route information:

    Codes: K - kernel, C - connected, S - static, R - RIP, B - BGP

           O - OSPF, IA - OSPF inter area
           N1 - OSPF NSSA external type 1, N2 - OSPF NSSA external type 2
           E1 - OSPF external type 1, E2 - OSPF external type 2
           i - IS-IS, L1 - IS-IS level-1, L2 - IS-IS level-2, ia - IS-IS inter area

           * - candidate default

    Gateway of last resort is not set

    K*      0.0.0.0/0 via 10.20.90.1, internal
    K       1.1.1.1/32 is directly connected, tmm0
    i L2    2.2.2.2/32 [115/10] via 10.20.110.1, internal, 00:05:08
    i L2    3.3.3.3/32 [115/10] via 10.20.110.1, internal, 00:00:08
    C       10.0.0.0/8 is directly connected, internal
    C       127.0.0.1/32 is directly connected, lo
    C       127.1.1.0/24 is directly connected, tmm0
    i L2    172.29.20.0/24 [115/10] via 10.20.110.1, internal, 00:05:08
    i L2    172.29.23.0/24 [115/10] via 10.20.110.1, internal, 00:05:08

    The following routes indicate the advertised virtual server addresses. The tmm routes are routes learned from TMM, and the /32 netmask indicates that ZebOS is advertising a single IP address:

    Note: The advertised virtual server addresses appear as kernel routes (K) because of the way TMM injects the routes into tmrouted. Therefore, you must have redistribute kernel configured in the IS-IS router definition in ZebOS.

    K       1.1.1.1/32 is directly connected, tmm0

    The following routes are learned from other IS-IS  routers:

    i L2    2.2.2.2/32 [115/10] via 10.20.110.1, internal, 00:05:08
    i L2    3.3.3.3/32 [115/10] via 10.20.110.1, internal, 00:00:08

    If you look at the routing table from the advanced shell (bash), it may not be obvious which routes have been learned from other routers. Dynamically learned routes appear similar to the following:

Note: No method currently exists to monitor IS-IS using SNMP, either through polling or SNMP traps.

Capturing routing protocol traffic

In certain cases, when peering is not establishing or updates are not correct or not appearing to arrive at the peer, the tcpdump command may help to track the routing updates. To capture IS-IS traffic, use the following tcpdump commands concurrently, where <vlan> is the Virtual Local Area Network (VLAN) name where the IS-IS device exists:

tcpdump -ni 0.0:nnn -s0 -w /var/tmp/0.0_isis.pcap isis or icmp

tcpdump -ni <vlan>:hnnn -s0 -w /var/tmp/vlan_hostside_isis.pcap isis or icmp
