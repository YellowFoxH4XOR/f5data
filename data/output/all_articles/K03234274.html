K03234274: Aspen Mesh allows Prometheus to scrape metrics from pods with sidecar injected

Type
Support Solution
Published
2021-11-12
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K03234274

Description

Aspen Mesh is shipped with a Prometheus instance for collecting metrics about sidecars stats and control plane, which will be later used by Aspen Mesh Dashboard.

Your application could also expose a metrics endpoint that allows you to monitor different metrics. These metrics are not shared across the Prometheus instances, and it is probably a good idea to have an external Prometheus instance to collect these types of metrics.

Environment

  • Kubernetes: 1.17x, 1.18.x, 1.19.x, 1.20.x
  • Aspen Mesh: 1.6.x, 1.9.x

Cause

When you set a job in Prometheus for scrapping metrics from a pod with sidecar injected, you may encounter an error that says there was a connection refused by the pod when it is trying to pull the metrics.

The error comes from a connection to the pod where the istio-proxy sidecar is capturing all of the traffic. By default, in Aspen Mesh, mTLS is enabled to secure all the connections, and since the Prometheus instance cannot prove its identity, the connection is dropped.

Recommended Actions

Disabling mTLS on port where metrics are exposed

  1. Identify what port will be used in Prometheus to access the metrics, in the example below you can find a scrape configuration of the application infrabin:

    - bearer_token_file: /var/run/secrets/kubernetes.io/serviceaccount/token
          job_name: infrabin
          kubernetes_sd_configs:
          - role: pod
          relabel_configs:
          - action: keep
            regex: infrabin
            source_labels:
            - __meta_kubernetes_pod_label_app
          - source_labels: [__meta_kubernetes_namespace]
            regex: default
            action: keep
          - source_labels: [__meta_kubernetes_pod_container_port_number]
            regex: "8080"
            action: keep
          scheme: http
          scrape_interval: 15s
          scrape_timeout: 10s
          tls_config:
            ca_file: /var/run/secrets/kubernetes.io/serviceaccount/ca.crt

    The port where Prometheus is accessing the metrics is 8080.

  2. Create a PeerAuthentication rule to disable mTLS on port 8080 only. For exmaple:

    apiVersion: security.istio.io/v1beta1
    kind: PeerAuthentication
    metadata:
      name: infrabin
      namespace: default
    spec:
      selector:
        matchLabels:
          app: infrabin
      mtls:
        mode: STRICT
      portLevelMtls:
        8080:
          mode: DISABLE

    The PeerAuthentication above still maintains mTLS enabled as you see (STRICT) but disabled only in port 8080.

    Notice also, we are using a selector for a specific workload, if the selector is omitted, the PeerAuthentication rule will be applied to all the workloads in the namespace and is possible to some applications stop working as intended.

  3. Verify that the error about refused connection is gone on your Prometheus instance and the endpoint is healthy.
