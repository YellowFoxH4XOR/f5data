K24549196: AFM Protocol Inspection IPS ''sys_max_inspection_count''

Type
Support Solution
Published
2022-06-03
Updated
2025-02-06
Applies to
  • BIG-IP
  • BIG-IP AFM
Source
https://my.f5.com/manage/s/article/K24549196

Description
AFM IPS contains many signatures and parameters available to be enabled/disabled.
One example of a configuration parameter is "sys_max_inspection_count".  This system check is raised when a single flow produces more than the specified number of compliance matches (numeric value, default is 50).

Environment

  • AFM IPS

Cause
This specific parameter ("sys_max_inspection_count") allows the BIG-IP to perform an action (such as drop or reject) to a connection flow when a certain number of signatures is hit, independent of these specific signatures action.
So for example, let's say you configure "http_host_with_ip_address" parameter as "accept" and "http_response_with_no_content_len_and_transfer_encoding_header" also as accept.  A flow that hits both conditions would still be allowed to go through because both these actions individually are configured as "accept".  However, if you then set "sys_max_inspection_count" to a value of 1 and action "drop", this flow would be dropped when the second condition was hit.  Even though both conditions individually are set to "accept", the total of them (2 in this case) are higher than the number defined in "sys_max_inspection_count".

Recommended Actions

  1. Set a higher value to "sys_max_inspection_count" or set it to "accept" instead of drop.

Additional Information
A flow which hits the above conditions ('drop' in sys_max_inspection_count) will be silently dropped by the BIG-IP.  This makes troubleshooting difficult as there is no indication anywhere of this fact.  One way to spot the problem is via packet trace, where typically you see a connection flowing (3WHS completed, packets in/out) and suddenly one packet doesn't have a flow (seen on f5 ethernet trailer) when it should, as it should be part of the same connection.  This packet usually triggers a TCP RST from the BIG-IP with "No flow found for ACK" or "Policy Action", although it's posible other RST reasons may be seen.
Another way to check is via tmctl statistics ("tmctl protocol_inspection_stats").  This will output the VIP names, profile names, inspection names, hit count and last hit time.  Last hit time is in UNIX time.  If the counter for "sys_max_inspection_count" is not zero for the VIP you are having issues, and the "last hit time" is recent (increased when problem manifests), then it's a good indication this may be the problem at hand.
