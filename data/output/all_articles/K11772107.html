Security Advisory Description

There is an issue with regenerating certificates and keys when deploying BIG-IP and BIG-IQ cloud images in Amazon Web Services (AWS), Azure or Verizon cloud services environments. (CVE-2016-2084)

Note: CVE-2016-2084 impacts only BIG-IP or BIG-IQ AWS, Azure, or Verizon cloud deployments; it does not impact other cloud environments, BIG-IP or BIG-IQ hardware, hypervisor-based Virtual Edition (VE), or vCMP (host or guest) deployments.

Impact

BIG-IP and BIG-IQ AWS, Azure, or Verizon cloud instances do not properly regenerate certificates and keys when deployed, resulting in multiple instances sharing the same certificates and keys. To exploit this vulnerability, an attacker would first need to obtain a copy of the configuration of the target instance containing encrypted information, and requires an in-depth knowledge of TMOS internals. A successful attack could potentially result in disruption of services and/or an information leak. There are no known public exploits at this time.

Security Advisory Recommended Actions

F5 responds to vulnerabilities in accordance with the Severity values published in the previous table. The Severity values and other security vulnerability parameters are defined in K4602: Overview of the F5 security vulnerability response policy.

If you are running a version listed in the Versions known to be vulnerable column in the AWS, Azure, or Verizon clouds, you can eliminate this vulnerability with a fresh deployment of a version listed in the Versions known to be not vulnerable column. If the table lists only an older version than what you are currently running, or does not list a non-vulnerable version, then no upgrade candidate currently exists.

Important: Upgrading an existing instance to a non-vulnerable version will not eliminate the issue. The existing certificates and keys are not replaced during an upgrade. To fully eliminate this issue, you must follow the mitigation steps below.

Important: Do not restore an existing UCS file to a new deployment after you have followed the mitigation steps below. If you follow the steps to mitigate this vulnerability and then restore a UCS file from an affected instance, you will reintroduce the vulnerability as the affected certificates and keys will be reinstalled on the system.

In addition to performing the following mitigation steps, any existing UCS or SCF files that you have saved on a vulnerable system will continue to be vulnerable. F5 recommends deleting any existing backups to eliminate risk. If there is a possibility that backups have been accessed by untrusted parties, there is a risk that any information contained therein has been compromised. In this case, F5 recommends immediately replacing all certificates, keys, and credentials used on the system. If your UCS files are protected with a strong password, the risk is reduced because the password is required before the vulnerability can be exploited.

Mitigating the vulnerability

You can mitigate this issue by regenerating keys. Perform the following procedure appropriate for your product:

  • BIG-IQ mitigation
  • BIG-IP mitigation
BIG-IQ mitigation

You can mitigate this issue for affected BIG-IQ products by performing the following procedures:

  • Obtaining the current admin user's public key
  • Regenerating the admin user's SSH public/private key-pair
  • Removing the old public key from the remote system's authorized_keys file

Obtaining the current admin user's public key

You must log into the BIG-IQ system and obtain the admin user's public key as you will remove the key from remote system's authorized_keys file. To obtain the admin user's public key, perform the following steps:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log into the command line of the BIG-IQ system using the admin account.

    For example:

    ssh -i aws-test.pem admin@172.24.20.63

  2. Change directories to the .ssh directory by typing the following command:

    cd $HOME/.ssh

  3. Display the public key for the admin account by typing the following command:

    cat identity.pub

    The output will appear similar to the following example:

    ssh-rsa
    AAAAB3NzaC1yc2EAAAABIwAAAIEAwllp+y4uTv2daGXHEss2eEKys2TpzXcJe7GpspKE4W3TFZOvZfOQJ79g3AEeg/
    MyzNBsmTI6SQcbQk1oKxdw6IlAQ5MJlJYfK2Bc3kejYYuRsbFl9FUm9FMT0V82urP1whHMM9kUd4oF8et71CMQi0k1
    VbQVA/rHdQE3/OZW848= Host Processor Superuser
  4. Save the public key output as you will remove the key from remote system's authorized_keys file.

Regenerating admin user's SSH public/private key-pair

To regenerate the admin user's SSH public/private key pair, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.
  1. Remove the existing SSH public/private key pair by typing the following command:

    rm -f .ssh/identity .ssh/identity.pub

  2. Create a new secure SSH public/private key pair for the admin account by typing the following command:

    ssh-keygen -f $HOME/.ssh/identity -t rsa -b 3072

  3. Follow the prompts to enter the passphrase.
  4. Once the new SSH public/private key pair is generated, the system will display output that appears similar to the following example:

    Your identification has been saved in /home/admin/.ssh/identity.
    Your public key has been saved in /home/admin/.ssh/identity.pub.
    The key fingerprint is:
    uk:39:57:c6:eb:7c:3a:91:dd:ef:a1:e9:1f:25:4a:6f root@ip-10-0-3-137.ec2.internal

  5. Display the new public key by typing the following command:

    cat identity.pub

    The output will appear similar to the following example:

    ssh-rsa
    AAAAB3NzaC1yc2EAAAABIwAAAIEA6saiqwrALkXcK9Z+T1pxDhZJwsif8h5QRLemyW7ggfNXFBmLyGv7aBD59pGj1H
    skxjo1ZYh3TLEhVbIfKPGVNQYW6ahp5qrV6m9poD9CRx7xXMwxfM6o3yrPh/XZ9LjIOYZ692WTJs/pFNIrSYWKJ7W1
    98DdYwWdybejvH8lPXM= Host Processor Superuser

Removing old public key from remote system's authorized_keys file

Log in to remote systems that are configured to allow passwordless login to this BIG-IQ system and remove the public key that you recorded in the Obtaining the current admin user's public key procedure. You can then add the new public key that you created in the Regenerating admin user's SSH public/private key-pair procedure to configure passwordless login with the new key. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.
  1. Log in to the command line of the remote system that is configured to allow passwordless login to the current system.
  2. Change directories to the .ssh directory by typing the following command:

    cd $HOME/.ssh

  3. Use a text editor to edit the authorized_keys file.

    For example:

    vi authorized_keys

  4. Locate and delete the public key that you recorded in the Obtaining the current admin user's public key procedure.
  5. Copy and paste the new public key that you created in step 5 of the Regenerating admin user's SSH public/private key-pair procedure to the end of the authorized_keys file. This step will allow passwordless login operations to continue.
  6. Save the changes to the authorized_keys file and exit the text editor.
  7. Repeat this procedure for any other remote systems that are configured to allow passwordless login to the BIG-IQ system.

BIG-IP mitigation

For BIG-IP systems, the following options are available to partially or completely mitigate this vulnerability:

  • Partial mitigation steps
    • If you are unable to immediately perform the complete mitigation steps to resolve the issue completely, F5 recommends that you immediately perform the partial mitigation steps on all affected systems to lessen the impact of the vulnerability.

      Important: The partial mitigation steps can be taken to lessen the impact, however the partial mitigation steps are not sufficient to remove the vulnerability. To remove the vulnerability you must follow the complete mitigation steps as soon as possible, even if you follow the partial steps.

  • Complete mitigation steps
    • The only way to completely mitigate this issue is to create new BIG-IP instances and use the steps provided in the complete mitigation section to migrate the configuration.

Note: The following instructions apply to AWS and Azure cloud instances.

Downloading the necessary files from the F5 Downloads site and extracting the scripts to the BIG-IP system

Before beginning either of the mitigation steps, make sure to download the necessary files from the F5 Downloads site, upload the files to the BIG-IP system and extract the scripts. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.
  1. Go to the F5 Downloads site.

    Note: You will need to log in to access the F5 Downloads site. If you do not have an account, you may register using the Register for an F5 Support Account link. You will be able to log in and download the files when you receive the confirmation email and activate your account.

  2. From the Downloads Overview page, click Find a Download.

    The Select a Product Line page displays.

  3. Navigate to BIG-IP > CVE-2016-2084.
  4. Download the CVE-2016-2084.zip file containing the scripts, the MD5 and SHA-1 signature files to verify the download, and the README to your local system.
  5. Once you have downloaded and verified the CVE-2016-2084.zip file, upload the zip file to the /tmp directory on the BIG-IP system.

    For example:

    scp -p CVE-2016-2084.zip <username>@<server>:/tmp/

    Note: For information about uploading files to the BIG-IP system, refer to K175: Transferring files to or from an F5 system.

  6. Log in to the BIG-IP command line.
  7. Unzip the scripts using the following command:

    unzip /tmp/CVE-2016-2084.zip

Checking the vulnerability status

After you have uploaded the scripts to the BIG-IP system, you should run the check-vulnerability-status script to verify whether the system is vulnerable to CVE-2016-2084. To run the check-vulnerability-status script, perform the following procedure:

  1. Log in to the BIG-IP command line.
  2. Run the mitigation script by typing the following command:

    /tmp/check-vulnerability-status

  3. The script will examine system files for the vulnerability, and then report one of the following results:

  • This system is vulnerable to CVE-2016-2084. - Please follow the remediation instructions to correct the vulnerability.
  • This system is not vulnerable to CVE-2016-2084
If the script reports that the system is vulnerable to CVE-2016-2084, you must complete the mitigation steps in this section of the article.

Overview of the master keys to generate

While you follow the mitigation/remediation instructions, you will need to select three new master keys. These keys should each be different and strong, but you will use only the final key after the mitigation and remediation is complete:

Note: For each of the following keys, choose a strong master key and protect it like a password. F5 recommends that you use a strong master key with at least 128 bits of entropy; for example, a random string of letters (upper and lowercase), numbers, and symbols at least 20 characters long.

  • In Mitigation, Step 2: A new master key is required to temporarily enhance the security of the vulnerable instance. You may discard this key once the steps are complete and you have verified the new instance is functional.
  • In Remediation, Step 8: A new master key is required to secure the configuration that is transported from the vulnerable instance to the clean instance. You may discard this key once the steps are complete and you have verified the new instance is functional.
  • In Remediation, Step 10: A new master key is required to secure the configuration for the future. You must not discard this key. Since you will use this key going forward, it is important that the key is strong and you store it in a safe location.

Complete mitigation (BIG-IP)

Complete mitigation for this vulnerability includes creating a new BIG-IP instance and carefully migrating the configuration by performing the following procedure:

Important: Restoring a UCS backup from an affected instance to a new instance will reintroduce the vulnerability as it restores the affected certificates and keys. Do not restore an existing UCS to a new deployment.

  1. Log in to the command line of the affected BIG-IP system and create a UCS backup file using the following syntax:

    save /sys ucs <path/to/UCS> passphrase <password>

    For example:

    save /sys ucs /var/tmp/MyUCS.ucs passphrase $trongPassword!

    Note: F5 recommends that you create a password-protected UCS backup file on the affected systems. If the complete mitigation steps fail, you can restore the system using the UCS file (which will also restore the vulnerability) and try the mitigation steps again.

  2. Identify the versions of affected BIG-IP systems by typing the following command:

    tmsh show /sys version

    The output appears similar to the following example:

    Sys::Version
    Main Package
    Product BIG-IP
    Version 12.0.0
    Build 0.0.606
    Edition Final
    Date Fri Aug 21 13:29:22 PDT 2015

    For the migration path, you can identify the previous example version as Version 12.0.0, Build 0.0.606.

  3. To identify the correct version to deploy as the new BIG-IP instance, use the following table:
    ProductCloudOld versionNew version

    • F5 recommends that you deploy the new instance into the same environment (for example, region, availability zone, security group) as the old instance for simplicity. However, this recommendation it is not part of the security remediation. You should deploy a new instance of the same type and same version, except for the updated Hotfix version (for instance, if your affected instance is F5 BIG-IP Virtual Edition 200Mbps Best version 11.6.0.4.0.420-HF4, you should deploy a new F5 BIG-IP Virtual Edition 200 Mbps Best version 11.6.0.6.0.XXX-HF6).
  5. Move the license for BYOL instances.
    • The BIG-IP instances in the cloud can be licensed as either Bring-Your-Own-License (BYOL) or Utility. If you purchased a license from F5 and installed it on the affected instance, you are using a BYOL instance. If your instance starts with a license automatically, you are using a Utility instance. You chose which instance type to use in step 3. If you are unsure whether you chose BYOL or Utility, you can check the new instance type through the AWS EC2 console or Azure portal, or you can see if the instance has received a Utility license automatically.
      • To determine if the instance has received a Utility license, type the following command:

        tmsh show /sys license

        • If command output returns the following error message, you have a BYOL instance and must contact F5 Support to request an Allow Move procedure, which will move the license from your affected instance to the new BIG-IP instance:

          Can't load license, may not be operational

        • If the previous command returns a license and not an error message, you have a Utility instance and you can skip to the next section.
  6. Migrate the Configuration.
    • If you use an external orchestration or configuration management system to generate the BIG-IP configurations, make sure to direct that system to configure the new BIG-IP instances with the configuration in the external orchestration system. You may then proceed to the Reboot section.
    • If you configure BIG-IP, but do not generate that configuration in a separate orchestration or configuration management system, continue to the next section.
  7. Upload the scripts to the BIG-IP systems.
    • The cleaning and reloading procedure will be automated by two scripts. The script save-clean-ucs runs on the vulnerable instance to extract a non-vulnerable configuration. The restore-clean-ucs script runs on the new BIG-IP instance and installs the non-vulnerable configuration. The scripts are included in the zip file downloaded above. If you have not already done so, you can upload the script file to the BIG-IP system and extract the scripts. To do so, refer to the Downloading the necessary files from the F5 Downloads site and extracting the scripts to the BIG-IP system section.

You will use this same master key in a later step to restore the configuration, and then replace it once more with a final master key. Choose a strong master key and protect it like a password. F5 recommends that you use a strong master-key with at least 128 bits of entropy; for example, a random string of letters (upper and lowercase), numbers, and symbols at least 20 characters long.   11. Restoring the Device Trust in HA Configurations.
    • If the vulnerable BIG-IP systems are deployed in an HA configuration, you will need to reconfigure the trust group on the new instances. To restore the device trust for the systems, follow the steps in the Resetting device trust across all devices section of the following article:

      Note: You must advance all members of a trust group to this section before completing this step. You should only add clean instances to the new device group.
      • K13946: Troubleshooting ConfigSync and device service clustering issues (11.x - 12.x)
    • After you have reset the device trust, follow the steps to recreate the device group in the following article:
      • K13649: Creating a device group using the Configuration utility
  12. Reboot the BIG-IP system.
    • F5 recommends that you reboot the new BIG-IP instance before proceeding. To reboot the BIG-IP system, enter the following command at the command line:

      reboot
  13. Verify the new BIG-IP instance.
    • Verify that the new BIG-IP instance is properly configured and functioning, following the procedure you used when configuring the old BIG-IP instance.
  14. Backing up the BIG-IP system.
    • F5 recommends that once you have verified the BIG-IP instance is properly configured and functioning, you create a UCS backup file. To do so, use the following syntax:

      tmsh save sys ucs <backup-name> passphrase <password>
  15. Migrate services to the new BIG-IP instance.
    • Migrate the cloud provider's service endpoints from the vulnerable BIG-IP instance to the new BIG-IP instance. For example, in AWS you may migrate Elastic Network Interfaces or Elastic IPs to the new BIG-IP instance. For Azure, you may migrate a public IP address.
  16. Decommission the vulnerable BIG-IP instances.
    • Terminate the vulnerable cloud instances using the AWS or Azure control panel. It is important that you terminate this instance once you are confident in the capability of the new BIG-IP instance. If an attacker can gain access to the old vulnerable instance, they may be able to extract secrets that have been moved to the clean instance.
After completing the Complete mitigation procedure, the BIG-IP instances are not affected by CVE-2016-2084. You can use all existing BIG-IP functionality, including taking and restoring backups and upgrading to newer versions of BIG-IP software as it becomes available. You do not need to repeat this procedure when you upgrade a clean instance. However, please note the following:
  • You must take caution to never restore a backup from a BIG-IP instance that is vulnerable to CVE-2016-2084 to the new instances that are not vulnerable.
  • An attacker may be able to extract secrets from any previous UCS or SCF backups taken from the vulnerable BIG-IP system. If you are concerned that an attacker may have gained access to these UCS or SCF backups, you should replace the secrets contained therein.
