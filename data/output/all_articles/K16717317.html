Description

Managing resources, and troubleshooting issues, whether it is a hardware appliance or a virtual edition is both simple and complex. 

  • It is simple in that the BIG-IP needs enough resources to do what you ask of it. Much like your home computer what are you doing with it? Is it being used for some simple word-processing and streaming or are you pushing it hard with the most demanding games? Each will require a setup to meet the needs and that will effect cost, reliability, and ability.
  • It is complex in that there are so many variables. Those include what modules are in use, how many and which monitors are in use, how many objects will be configured, are there enough resources to run traffic and sustain a DDoS attack, and many more variables.
A simple search of MyF5 using either the word 'memory' or acronym 'CPU' will produce thousands of hits. Thus some kind of comprehensive article is not possible. What this article's intended purpose is to provide a very general overview, a starting point if you will, in regards to troubleshooting resource issues on a BIG-IP.

Common examples of what you may see:
  • You may see high swap occur that results in the Out-of-memory killer (oom-kiiler) being invoked.
  • There may be unexpected failovers.
  • Traffic latency.
  • Logins may be slow or timeout.
  • A slow GUI/WebGUI..
  • Error messages that may appear in the logs:

Environment

There are many environmental factors. Here are a few:

  • Multiple modules, high swap, based on BIG-IP resources high demand on the BIG-IP
  • Provisioning settings
  • The number of objects configured (pools, virtual serves, monitors, etc.).

Cause

The causes of possible resource issues can vary. The cause can range from the use of multiple modules, a DDoS attack, over-subscribing the BIG-IP, a lack of awareness about how a BIG-IP assigns memory on start-up, and others.

Where to start?

When there are indications of resource issues, either or both memory or CPU, the place to start is the BIG-IP logs. The logs you will most often find possible issues in are...

  • /var/log/ltm
  • /var/log/kern.log
  • /var/log/asm if ASM is provisioned and in use
  • /var/log/restjavad
  • /var/log/tomcat/catalina.out
Note: these logs rotate daily and after the eight day the oldest rotates out. Along with that as the log age progresses it will change the name slightly. For instance /var/log/ltm will become /var/log/ltm.1 and so on.

If you find a log entry that applies run the log entry as a search syntax at MYF5. You may need to break it down to find an issue that is already been identified.


Checking and setting Management to Large

Going to System  ››  Resource Provisioning you will see the list of licensed and provisioned modules. At the top is Management (MGMT). Options for MGMT include Small, Medium, and Large. If the issue is with "Other memory" or "swap" then setting this to Large may alleviate the issue altogether, or at the least minimize any memory issue with the Linux Kernel and/or BIG-IP functions running on the Control/Analysis Plane. This is the simplest place to start when dealing with memory issues. K26427018: Overview of Management provisioning

If setting MGMT to Large is not sufficient then a second option is to use the db variable provision.extramb that is mentioned in K26427018: Overview of Management provisioning. This db allows for up to an additional 8GBs of RAM to be allocated to the Linux kernel and the Control/Analysis Plane. The important thing to remember here is that you are taking memory away from TMM and "re-allocating" it to the Control/Analysis Plane and Linux processes.

In most cases TMM is using about 10% to 20% of what it is allocated so this can be a good way to alleviate a memory issue. 'But' before attempting this a look at what tmm is historically using is important. The easiest way to do so is to go to Dashboard...Statistics  ››  Analytics : Memory : TMM. Look at the 'Details' in the BIG-IP GUI. If the average used and average free of the total show that what TMM is using is low then this option can be used. For example if Avg TMM Total RAM (GB) is 10.63GB and Avg TMM Free RAM (GB) is 9.24GB (not being utilized) then historically tmm is not utilizing very much RAM and that will allow for the use of the db variable.


Important: Using the db variable should be done in small increments and stopped when the back channel processes are calmed down.

Note: Changing the Management (MGMT) size on the Active BIG-IP, after 'initial' provisioning, causes a reprovision operation which will bring about a failover (When High Availability is used) and may interrupt traffic as it recovers from a TMM restart. When HA is being used do the Standby first, failover, test, and if there are no issues adjust the MGMT setting on what is now the Standby BIG-IP.

The reason for doing this on all the BIG-IPs in the HA group separately is because this setting does not sync to the peer.

De-Provisioning Local Traffic Manager (LTM)

To deprovision LTM review:K17173140: Setting LTM Provision NONE does not disable licensed LTM functionality.
For each module provisioned a specific amount of resources are dedicated to it. By deprovisioning LTM those resources are released back to the system for the other modules in use to access.
Important: If Auto Sync is enabled disable it before performing these steps. Please test this either in a QA type environment first or do the steps on the Standby then failover and test. If all goes well then sync to the peer. If there are any issues you can then failback to the peer while further troubleshooting is done.

Important: There are some changes to the GUI when choosing this method to alleviate resource issues. Please review the following article for further information  K48278733: Syncookie Protection Behavior since V13.x and LTM being provisioned or not provisioned.
  1. If there is no iApp in play, that is LTM dependent, then we can work with the provisioning to create a better environment for the other modules. When LTM is licensed almost all LTM functionality is still available, via the other modules, even if LTM is not provisioned. So in most cases simply de-provisioning LTM will resolve the issue.
Review the command you used previously to identify any iApps in use. The simplest way to determine if an iApp in use is LTM dependent is review the iApps being used (if any). Depending on whether you are using standard Templates or Templates LX go to  iApps  ››  Templates : Templates or iApps  ››  Templates : Templates LX and click on the name of the iApp in use. In the section labelled Required BIG-IP Modules if LTM is listed then deprovisioning cannot be done.

Reduce Max Entities allowed For AVR Database Entries
In cases where there are iApps that are LTM dependent, or even if not and done in conjunction with the prior step concerning AVR, and the system is using less than 16 cores and AVR is in use, then a db variable can be adjusted. Bug ID 828937, K45725467: BIG-IP systems may experience long I/O wait times during AVR data aggregation, provides a workaround that may help here. You can decrease the amount of data collected during aggregation by lowering the value of the avr.stats.internal.maxentitiespertable database variable. The recommended value for systems with more than 16 CPU cores is 20000. For systems with 16 CPU cores or less, the recommended value is 2148. To do so, perform the following procedure:

  1. Log in to the Advanced Shell (bash)
    Note: You should already have the output of the number of cores.
    Note: Based on the number of CPU cores found, set the value for the avr.stats.internal.maxentitiespertable database variable using the following syntax
     
  2. Update avr.stats.internal.maxentitiespertable to a desired value: 
    tmsh modify /sys db avr.stats.internal.maxentitiespertable value <#>
    For example, to set the value to 2148, enter the following command: 
    tmsh modify /sys db avr.stats.internal.maxentitiespertable value 2148

Increase restjavad Memory Allocation
Something else that can be done, if there are restjavad out of memory errors in /var/log/restjavad.<log number>.log, is to add additional resources to provisioning. The db variables restjavad.useextramb and provision.restjavad.extramb can help here. 
sys db restjavad.useextramb {
    default-value "false"
    scf-config "true"
    value "false"
    value-range "false true"
}

sys db provision.restjavad.extramb {
    default-value "192"
    scf-config "true"
    value "192"
    value-range "integer min:192 max:8192"
}

192 is the default setting. Also, it is only available from versions 17.1.0, 16.1.3.1, 15.1.7, and 14.1.5.1 and beyond.

To use either or both of these db variables please review the following articles...
Bug ID 1025261: Restjavad uses more resident memory in control plane after software upgrade

Use High Speed Logging

High Speed Logging was designed to be a high volume, low overhead logging mechanism. HSL supports logging via TCP or UDP. Informal testing has shown CPU and memory utilization for HSL to be very low (<10% CPU, almost no additional memory utilization).
For example, you could use these commands to:
  • Log all HTTP requests and responses processed via the LTM by sending the data to a pool of remote servers.
  • Log the SSL cipher name, version, size for each SSL session before restricting ciphers
  • Log every load balancing failure (not just a member failing a monitor)
  • Supplement or replace tcpdump for troubleshooting layer 7 issues (it can be much easier to log the decrypted content rather than decrypting SSL with ssldump, etc)

Note that HSL requires the use of the TMM routes and a route must be in place to send HSL traffic via switch port interfaces. Routing via the management interface is not supported and will not work.

Java issues

Along with the above db variables is one for the tomcat process. When this process is having issues it often coincides with GUI issues.

When using provision.tomcat.extramb to resolve GUI issues it is recommended that it be done in conjunction with the provision.extramb variable. provision.tomcat.extramb should not exceed 1/4 of what has been added to provision.extramb

For example if you set provision.extarmb to 1024MB then provision.tomcat.extramb should not exceed 256MB.

To administer this variable K9719: Error Message: java.lang.OutOfMemoryError

Deprovision unused modules
Often seen is the provisioning of modules that are not being used. Deprovisioning them will return the dedicated resources back to the system.

BIG-IP Virtual Editions

There are basically 3 kinds of Virtual Editions...
  • BIG-IP tenant running on F5OS-C (VELOS) / F5OS-A (rSeries)
  • F5's vCMP
  • External hypervisors such VMWare ESXi
    • A sub category to this would be virtual cloud instances. But they are handled much the same way.

If you are running into resource issues using BIG-IP tenant on F5OS-C/A or vCMP there are a couple of options...

  • If there are cores available on the host add them to the guest that needs them.
  • Review the license. A VE license is set based on throughput. In conjunction with that a limit is placed on the number of CPUs allowed. You may need to obtain a license that has a higher throughput to enable you to use additional vCPUs. 
    • K99532652: Error Message: 01010045:5: Bandwidth utilization is &lt;rate&gt; Mbps, exceeded &lt;percent&gt;% of Licensed &lt;limit&gt; Mbps
    • K14810: Overview of BIG-IP VE license and throughput limits
  • If that is not possible then the above steps can be used to minimize the impact of limited resources.
  • Use an Active/Active configuration for HA instead of Active/Standby
    • Creating an Active-Active Configuration using the Configuration Utility
  • Review the following article appropriate for your BIG-IP type:
    • BIG-IP tenant on F5OS-C (VELOS): VELOS Performance and Sizing
    • BIG-IP tenant on F5OS-A (rSeries): rSeries Performance and Sizing
    • vCMP: K14218: vCMP guest memory/CPU core allocation matrix
