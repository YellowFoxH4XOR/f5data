K000092600: tcpdump on F5OS does not capture packets of certain sizes

Type
Support Solution
Published
2022-11-10
Updated
2022-11-20
Source
https://my.f5.com/manage/s/article/K000092600

Description


When using tcpdump on the F5OS host, packets of certain sizes may not be captured via tcpdump, when compared to the same captures done on the tenant.
 

Environment

  • F5OS

 

Cause


This is a known issue tracked under Bug ID 1116869.
 

Recommended Action

If possible, please take a tcpdump capture on the tenant. If a capture is required on the rSeries host, a workaround can by applied by disabling TCP Segmentation Offload (TSO) and Large Segment Offload (LRO)

# setdb tm.tcpsegmentationoffload disable
# setdb tm.tcplargereceiveoffload disable


F5 Support can be contacted to request an Engineering Hotfix for the bug ID. Please reference this knowledge article, or Bug ID 1116869.

 

Additional Info

Tcpdump packets less than 1501 bytes and greater than 1483 bytes as well as several other ranges are affected by this issue.

ACKs are not seen in the packet capture due to TMM dropping them. The reason TMM is dropping them is because of a combination of LRO, and a bare ACK.

When a client sends another packet with payload just after the ACK, we aggregate the packets and drop the ACK for less CPU/resource overhead purposes.

How we see the above is with the rx_bare_acks_dropped counter in the tcp_lro table on the tenant's tmctl output.
 

# tmctl tcp_lro
name   rx_pkts rx_actual_pkts rx_pkt_per_poll rx_actual_per_poll

tmm0.0       0              0               0                  0

rx_max_pkt_size rx_avg_pkt_size rx_max_chunks_per_pkt rx_avg_chunks_per_pkt
--------------- --------------- --------------------- ---------------------
              0               0                     0                     0

rx_collisions rx_ooseg rx_bare_acks_dropped rx_bare_acks_merged
