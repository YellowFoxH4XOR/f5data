Description

Aspen Mesh Sidecar proxies are configured by default to retry HTTP requests in case of any network or application failures.
This article is an overview of HTTP retries policies in Istio and Aspen Mesh

 

Environment

Aspen Mesh 1.11.x, 1.14.x

 

Cause

Envoy sidecar proxy is trying to keep persistent TCP connections for HTTP services and workloads deployed within the service mesh. Every POD and workload being a part of the service mesh has the Sidecar proxy injected and the communication is done in a pod-to-pod basis. HTTP requests sent by the client application are proxied by 2 Envoy sidecars, 1st on Client POD and 2nd on Server POD

In case the service application responds with a HTTP error, Envoy Sidecar can retry the request using the same TCP connection. Envoy Access Logs on client POD do not log the number of retries so it is important to understand how to configure and interpret logging and behaviour on workload/server PODs.

 

 Recommended Actions

  1. Default Istio retry policy
    1. Istio uses Envoy as a proxy inside sidecar container. Retry policy for HTTP Services is configured on Envoy Route section. A route is an http filter attached to http_connection_manager network filter on Envoy. Istio adds default retry policy by default to every http service. To see the policy we can use "istioctl proxy-config route" command. An example below shows the default Envoy retry policy set by Istiod: 
      • istioctl pc route client-pod.namespace --name 8000 -o yaml
...
    retryPolicy:
     hostSelectionRetryMaxAttempts: "5"
     numRetries: 2
     retriableStatusCodes:
     - 503
     retryHostPredicate:
     - name: envoy.retry_host_predicates.previous_hosts
      typedConfig:
       '@type': type.googleapis.com/envoy.extensions.retry.host.previous_hosts.v3.PreviousHostsPredicate
     retryOn: connect-failure,refused-stream,unavailable,cancelled,retriable-status-codes

         
    2. Envoy Retry Policy API is documented on official doc pages 5., 6., 7.
    3. By default Istio Sidecar tries to send the request to the upstream service and in case of failure it will retry 2 times.
    4. Sidecar will retry only in case of the following failure reasons:
      1. connect-failure
        1. Envoy will attempt a retry if a request is failed because of a connection failure to the upstream server (connect timeout, etc.). (Included in 5xx).
        2. NOTE: A connection failure/timeout is a the TCP level, not the request level. This does not include upstream request timeouts specified via x-envoy-upstream-rq-timeout-ms or via route configuration or via virtual host retry policy.
      2. refused-stream
        1. Envoy will attempt a retry if the upstream server resets the stream with a REFUSED_STREAM error code. This reset type indicates that a request is safe to retry. (Included in 5xx)
      3. unavailable
        1. Envoy will attempt a retry if the gRPC status code in the response headers is “unavailable” (14)
      4. cancelled
        1. Envoy will attempt a retry if the gRPC status code in the response headers is “cancelled” (1)
      5. retriable-status-codes
        1. Envoy will attempt a retry if the upstream server responds with any response code matching one defined in either the retry policy or in the x-envoy-retriable-status-codes header.
        2. Default retriable status code is only 503
    5. In addition to the retry policy Istio also sets Retry Host Predicate plugin. During retries host selection for HTTP request follows the same process as the original request. Retry plugins can be used to change this behavior. By default Istio configures Envoy to use PreviousHostPredicate plugin on every route. Thanks to this plugin Envoy will keep track of previously attempted hosts, and rejects hosts that have already been attempted. Having multiple workloads or PODs attached to the same service we do not have to worry that the Sidecar will retry and resend the request to the same instance.   2. Changing default retry policy globally within the mesh
    1. ​​​​​Beginning from Istio 1.12 you can configure the global Retry Policy for HTTP services and override the default policy. This feature is available in Aspen Mesh 1.14.x or later releases. In Istio and Aspen Mesh 1.11.x or earlier releases you have to use VirtualService object to specify retry policy per Service (using fully qualified domain name) or per set of Services (using wildcard "*" domain names). Beginning 1.14.x releases VirtualService CRD allows the use of 'exportTo" field to specify retry policy limited to a specific namespace.
    2. In Aspen Mesh, to configure global HTTP retry policy you have to add meshConfig.defaultHttpRetryPolicy option in global override-values.yaml file and upgrade/install istio-discovery Helm chart.
      1. defaultHttpRetryPolicy field is documented as an HTTPRetry object in Istio documentation:
        1. https://istio.io/latest/docs/reference/config/networking/virtual-service/#HTTPRetry
        2. The syntax is the same as VirtualService retry field API
          1. NOTE: On Envoy API the naming convention of fields is different than Istio. In Istio fields are in camelCase while Envoy uses snake_case convention.
      2. Example below presents an example of the default HTTP policy specified in a values.yaml file
        • override-value.yaml:
        • meshConfig:
  defaultHttpRetryPolicy:
    attempts: 3
    perTryTimeout: 2s
    retryOn: "connect-failure,refused-stream,503,500,501"
      3. To apply the configuration we have to execute Helm upgrade like below: 
        • helm upgrade istiod manifests/charts/istio-control/istio-discovery -n istio-system --values override-values-policy.yaml
      4. The above meshConfig will result with the following RetryPolicy: 
        • ➜  ~ istioctl pc route <pod>.<namespace> --name 8000 -o yaml
...
        retryPolicy:
          hostSelectionRetryMaxAttempts: "5"
          numRetries: 3
          perTryTimeout: 2s
          retriableStatusCodes:
          - 503
          - 500
          - 501
          retryHostPredicate:
          - name: envoy.retry_host_predicates.previous_hosts
            typedConfig:
              '@type': type.googleapis.com/envoy.extensions.retry.host.previous_hosts.v3.PreviousHostsPredicate
          retryOn: connect-failure,refused-stream,retriable-status-codes
          retryPriority:
            name: envoy.retry_priorities.previous_priorities
            typedConfig:
              '@type': type.googleapis.com/envoy.extensions.retry.priority.previous_priorities.v3.PreviousPrioritiesConfig
              updateFrequency: 2
        • NOTE: Status codes specified in "defaultHttpRetryPolicy.retryOn" field were appended to retriableStatusCodes list. For the more detailed description please refer to Istio docs 5.
      5. To disable HTTP retries globally please use the following policy 
        • meshConfig:
  defaultHttpRetryPolicy:
    attempts: 0
        • Only "attempts" field has to be specified, otherwise Istio will throw an error.
           
  3. Changing retry policies for specific services
    1. To change HTTP retry policy for specific services we can use VirtualService CRD.
    2. Example of the policy  
      • kubectl apply -n default -f - <<EOF
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: httpbin-retries
spec:
  hosts:
  - httpbin.default.svc.cluster.local
  http:
  - route:
    - destination:
        host: httpbin.default.svc.cluster.local
    retries:
      attempts: 7
      perTryTimeout: 5s
      retryOn: connect-failure,refused-stream,503,504
EOF
    3. Result: 
      • ➜  ~ istioctl pc route nettools-netadmin-bf8886597-ddwgp.ns1 --name 8000 -o yaml
- name: "8000"
...
      route:
        cluster: outbound|8000||httpbin.default.svc.cluster.local
        maxGrpcTimeout: 0s
        retryPolicy:
          hostSelectionRetryMaxAttempts: "5"
          numRetries: 7
          perTryTimeout: 5s
          retriableStatusCodes:
          - 503
          - 504
          retryHostPredicate:
          - name: envoy.retry_host_predicates.previous_hosts
            typedConfig:
              '@type': type.googleapis.com/envoy.extensions.retry.host.previous_hosts.v3.PreviousHostsPredicate
          retryOn: connect-failure,refused-stream,retriable-status-codes
        timeout: 0s
  4. Changing retries per HTTP request
    1. You can modify the HTTP retry policy configured on Envoy Sidecar by including special HTTP Headers in the request. Those headers are consumed and understood by Envoy route filter. This feature is disabled by default on Istio and Aspen Mesh. For the full list of supported headers please go to:
      1. https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/router_filter#http-headers-consumed-from-downstreams
    2. Envoy will accept "x-envoy-*" headers only sent by trusted applications. Depending on your IP CIDR in the cluster you might need to enable useRemoteAddress feature on Sidecars to allow applications to override retry policy.
    3. To allow changing retry strategy via HTTP request headers we can use the following EnvoyFilter:
      1. NOTE: this is an example and by applying this filter we will change useRemoteAddress field for all services and listeners. Use this only for testing
      2. Example: 
        • kubectl apply -n ns1 -f - <<EOF
apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: internal-network2
spec:
  configPatches:
  - applyTo: NETWORK_FILTER # http connection manager is a filter in Envoy
    match:
      context: SIDECAR_OUTBOUND
      listener:
        filterChain:
          filter:
            name: "envoy.filters.network.http_connection_manager"
    patch:
      operation: MERGE
      value:
        name: "envoy.filters.network.http_connection_manager"
        typed_config:
          "@type": "type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager"
          useRemoteAddress: true
EOF
      3. For more information please contact Aspen Mesh support or read Envoy documentation
    4. By adding "X-envoy-* headers you can instruct Envoy about the retry strategy for a specific request: 
      • curl -H "X-envoy-retriable-status-codes: 501" -H "x-envoy-max-retries: 2"  httpbin.default:8000/status/501 -v
  5. Envoy retry policy API and Advanced retry policies
    1. Istio RetryPolicy API does not expose all features available on Envoy RetryPolicy API. EnvoyFilter CRD has to be used to directly manipulate Envoy Sidecar configuration and to enable those features.
    2. The list of available retry features looks like below: 
      • {
  "retry_on": ...,
  "num_retries": {...},
  "per_try_timeout": {...},
  "per_try_idle_timeout": {...},
  "retry_priority": {...},
  "retry_host_predicate": [],
  "retry_options_predicates": [],
  "host_selection_retry_max_attempts": ...,
  "retriable_status_codes": [],
  "retry_back_off": {...},
  "rate_limited_retry_back_off": {...},
  "retriable_headers": [],
  "retriable_request_headers": []
}
    3. For details please refer to Envoy RetryPolicy API documentation available  here:
      1. https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto#config-route-v3-retrypolicy
    4. Example of Envoy filter to manipulate Envoy route HTTP retry policy: 
      • apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: httpbin.default.svc.cluster.local
spec:
  workloadSelector:
    labels:
      app: httpbin
  configPatches:
  - applyTo: VIRTUAL_HOST
    match:
      context: SIDECAR_OUTBOUND
      routeConfiguration:
        vhost:
          name: "httpbin.default.svc.cluster.local:8000"
    patch:
      operation: MERGE
      value:
        retry_policy:
          retriable_headers:
            name: "HEADER-NAME"
            string_match:
              exact: "retry-required"
  6. Troubleshooting retry policies
    1. To demonstrate how HTTP retries work on we will use httpbin as a server (deployed in default namespace) and netshoot as a client (deployed in ns1 namespace) applications.
      1. Both application PODs have sidecar injected.
      2. The retry policy for httpbin.default.svc.cluster.local is set as the following: 
        • ...
      route:
        cluster: outbound|8000||httpbin.default.svc.cluster.local
        maxGrpcTimeout: 0s
        retryPolicy:
          hostSelectionRetryMaxAttempts: "5"
          numRetries: 2
          perTryTimeout: 5s
          retriableStatusCodes:
          - 503
          - 504
          retryHostPredicate:
          - name: envoy.retry_host_predicates.previous_hosts
            typedConfig:
              '@type': type.googleapis.com/envoy.extensions.retry.host.previous_hosts.v3.PreviousHostsPredicate
          retryOn: connect-failure,refused-stream,retriable-status-codes
    2. The number of retries is not specified in Access Logs by Envoy Sidecar however "URX" flag set on the client sidecar proxy may indicate that the request has been retried by Envoy.
      1. URX flag is documented by Envoy as:

        1. URX: The request was rejected because the upstream retry limit (HTTP) or maximum connect attempts (TCP) was reached.
