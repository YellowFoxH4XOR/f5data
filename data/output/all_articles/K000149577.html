Topic

This article applies to the TLS stack used by the F5 BIG-IP Traffic Management Microkernel (TMM) to enable Post-Quantum Cryptography (PQC) algorithms. 

Description

The US National Institute of Standards and Technology (NIST), along with other academic and scientific agencies, have recognized that by 2030, based on current trajectory of quantum computing, our commonly used cryptographic algorithms may become insecure. This includes the widely used RSA and ECC cipher schemes (though AES-256 and above encryption algorithms will likely remain safe). In preparation for this event, NIST initiated a competition to create the next generation of “quantum-resistant cryptography” (QRC). This event has produced several viable proposals, and some of those have recently reached standardization.

  • The FIPS 203 document describes ML-KEM (Module Lattice Key Encapsulation Mechanism) and is the evolution of the "Kyber" algorithm submission. It is a general-purpose algorithm used for establishing shared secret keys. As of this publication there are three ML-KEM parameter sets, including ML-KEM-512, ML-KEM-768, and ML-KEM-1024, each with increasing security but decreasing performance generally based on key size.
  • The FIPS 204 document describes ML-DSA (Module Lattice Digital Signature Algorithm) and is the evolution of the "Dilithium" algorithm submission. It is a general-purpose digital signature algorithm. As of this publication there are three ML-DSA parameter sets, including ML-DSA-44, ML-DSA-65, and ML-DSA-87, each with increasing security but decreasing performance generally based on key size.
  • The FIPS 205 document describes SLH-DSA (StateLess Hash-based Digital Signature Algorithm) and is the evolution of the "SPHINCS+" algorithm submission. It is a hash-based cryptographic algorithm. As of this publication SLH-DSA provides twelve parameter sets, six using SHA2 and six using SHAKE, each with differing security category and signature sizes.

As of this publication, neither of the digital signature algorithms are in widespread use and the technical implementations are still being considered by the industry. As for key agreement, three groups have emerged:

  • X25519Kyber768Draft00 (0x6399) - defined prior to the FIPS 203 publication, many browser and server vendors have already implemented this cipher and is in widespread use.
  • X25519MLKEM768 (0x11EC) - one of the two official ML-KEM cipher groups and an update to X25519Kyber768Draft00.
  • SecP256r1MLKEM768 (0x11EB) - one of the two official ML-KEM cipher groups, not yet widely supported.
  • SecP384r1MLKEM1024 (0x11ED) - NIST hybrid ML-KEM cipher group

Implementation

In the pursuit of the highest cryptographic standards and capabilities, F5 maintains a lock step with industry requirements and is implementing Post-Quantum Cryptography support in a phased approach following guidance from NIST. As of F5 BIG-IP 17.5.1, the BIG-IP now supports the widely implemented X25519MLKEM768 hybrid MLKEM cipher for client-side (Decrypt, BIG-IP as a TLS server) and server-side (Re-encrypt, BIG-IP as a TLS client) TLS negotiations. Other ciphers and capabilities will become available in subsequent releases.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • BIG-IP TMOS version 17.5.1 or later for X25519MLKEM768.
  • BIG-IP TMOS version 21.1 or later for SecP256r1MLKEM768 and SecP384r1MLKEM1024.
  • You have administrative access to the BIG-IP system.

Procedure

  • Configure PQC cipher group using the BIG-IP Configuration Utility
  • Configure PQC cipher group using the BIG-IP command line

Configure PQC cipher group using the BIG-IP Configuration utility

To watch a video dem of this procedure, go to  K000157923: Enable post-quantum cryptography on the BIG-IP system using the Configuration utility.

To configure PQC cipher group using the Configuration utility, perform the following procedures:
Impact of procedure: PQC ciphers will minimally require TLS1.3. F5 recommends testing the changes in a staging environment before applying the changes in a scheduled maintenance windows.

Create a new cipher rule

  1. To create a new cipher rule, log in to the Configuration utility, and go to Local Traffic > Ciphers > Rules.
  2. Select Create.
  3. Provide a name for the cipher rule.
  4. For Cipher Suites, enter the name of a cipher suites. Use DEFAULT to use the recommended list of suites.
  5. For DH Groups
    1. X25519MLKEM768 support (17.5.1): Enter X25519MLKEM768
    2. SecP256r1MLKEM768 support (21.1): Enter P256MLKEM768
    3. SecP384r1MLKEM1024 support (21.1): Enter P384MLKEM1024
    4. Optionally enter the following to support all forms: X25519MLKEM768:P256MLKEM768:P384MLKEM1024:DEFAULT
      Note: this sets the preference for MLKEM over the remaining DEFAULT ciphers.
      Important: For BIG-IP versions prior to 21.0.0, when configuring dh-groups in a cipher rule that supports both TLS 1.2 and TLS 1.3, classic DH-group algorithms (e.g., X25519, P256, P384) must be listed before hybrid KEM algorithms (e.g., X25519MLKEM768). Listing hybrid KEM algorithms first may cause TLS 1.2 handshake failures. For more information, refer to K000160037: Virtual server not working after applying Hybrid KEM Cipher Group.
  6. For Signature Algorithms, enter DEFAULT to use the recommended list of signature algorithms..
  7. Select Finished.

Create a new cipher group

  1. Go to Local Traffic > Ciphers > Groups
  2. Select Create.
  3. Provide a name for the cipher group.
  4. In Group Details, add the newly created Cipher Rule to Allow the following or Restrict the Allowed list to the following. .
  5. All of the other details, including DH Group, Signature Algorithms, and Cipher Suites are reflected under Group Audit in Cryptographic Parameters.
  6. Select Finished.

Configure a Client SSL profile

  1. Go to Local Traffic > Profiles > SSL > Client.
  2. Create a new client SSL profile or edit an existing.
  3. For Configuration, select Advanced.
  4. For Certificate Key Chain, select the custom check box and make sure that appropriate site certificate and key are selected.
  5. For Ciphers ,select the custom check box, select Cipher Group, and then select the previously created cipher group.
  6. For Options, select No TLSv1.3 and select Disable to remove it from Enabled Options.
  7. Select Finished.

Configure PQC cipher group using the BIG-IP command line

To configure PQC cipher group via BIG-IP command line:

Impact of procedure: PQC ciphers will minimally require TLS1.3. F5 recommends testing the changes in a staging environment before applying the changes in a scheduled maintenance windows.

  1. Log in to the BIG-IP command line.
  2. Log in to tmsh by entering the following command:
    tmsh
  3. Create the ltm cipher rule using the following command:
    create ltm cipher rule PQC cipher DEFAULT dh-groups X25519MLKEM768:P256MLKEM768:P384MLKEM1024:DEFAULT signature-algorithms DEFAULT
  4. Create the ltm cipher group using the following command:
    create ltm cipher group PQC allow add { PQC }
  5. Configure X25519KYBER768 through a client SSL profile. To do so, use the following command:
    create ltm profile client-ssl PQC cipher-group PQC options { dont-insert-empty-fragments } ciphers none

Additional Information

    To test PQC cipher support, perform one of the following procedures with your preferred browser:

    Note: On June 24, 2025, Google released Chrome 138.7204.49 that no longer includes Kyber support. The chrome://flags options for PQC algorithms was also removed, and MLKEM is enabled by default.

    • Chrome (124 and later)
      1. To enable PQC cipher:
        • go to chrome://flags/
        • For KYBER support: Use the search to find two entries related to kyber. Set the TLS 1.3 post-quantum key agreement option to Enabled enable PQC key agreement, and set the Use ML-KEM in TLS1.3 option to Disabled to force the browser to use Kyber instead of ML-KEM, and then relaunch the browser.
        • For MLKEM support: Use the search to find two entries related to kyber. Set the TLS 1.3 post-quantum key agreement option to Enabled enable PQC key agreement, and set the Use ML-KEM in TLS1.3 option to Enabled to prefer MLKEM over Kyber, and then relaunch the browser.
      2. To verify PQC is being used, go to More Tools > Developer Tools > Security. If using Kyber you should see something similar to the following:
        Connection - secure connection settings
        The connection to this site is encrypted and authenticated using TLS 1.3 X25519MLKEM768        , and AES_128_GCM
    • Firefox (Nightly 2024-01-18 and later)
      1. To enable PQC cipher, go to about:config,
      2. Enable security.tls.enable_kyber, then re-launch the browser.
      3. Access your BIG-IP configured service.
      4. To verify PQC is being used, go to More Tools -> Web Developer Tools. Click on the Network tab.
      5. Select a request, then in the right-side panel select the Security tab. If using Kyber you should see something similar to the following:
        Connection
        Protocol Version: "TLSv1.3"
        Cipher suite: "TLS_AES_128_GCM_SHA256"
        Key Exchange Groups: "X25519MLKEM768"
        Signature Scheme: "RSA-PSS-SHA256"
