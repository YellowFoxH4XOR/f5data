Description

As F5 Distributed Cloud continues to expand capacity within its Regional Edge (RE) infrastructure, a new architectural concept called Resiliency Zones has been introduced. Resiliency Zones add additional Regional Edge clusters within the same metropolitan area, creating new RE instances that may appear in the F5 Distributed Cloud Console and impact existing Virtual Site configurations. Understanding how Resiliency Zones work and how they interact with Virtual Sites is important for maintaining expected traffic routing behavior and avoiding misconfiguration.

  • What is a Regional Edge Resiliency Zone in F5 Distributed Cloud?
  • How do Resiliency Zones differ from new Regional Edge POPs?
  • How will Resiliency Zone Regional Edges appear in the F5 Distributed Cloud Console?
  • How do existing Virtual Site configurations interact with newly added Resiliency Zone Regional Edges?
  • What are the best practices for configuring Virtual Sites in light of Resiliency Zones?
  • Can Customer Edge tunnel terminations be configured on Resiliency Zone Regional Edges?

Environment

  • F5 Distributed Cloud (SaaS)
  • Regional Edge (RE) data plane
  • Regional Edge POPs with Resiliency Zones configured (e.g., Ashburn, Virginia — dc12-ash, b-dc12-ash)
  • Virtual Sites configured for Regional Edge grouping using SiteName, Country, or Region label selectors
  • HTTP, HTTPS, or TCP Load Balancer objects with VIP Advertisement and/or Origin Pool Virtual Site assignments
  • Customer Edge (CE) sites with tunnel terminations to Regional Edges (CE tunnel behavior on Resiliency Zones is subject to change in a future release)

Cause

F5 Distributed Cloud has experienced continuous growth and increased platform utilization, requiring infrastructure capacity expansion beyond adding new POPs in new geographic locations. In high-density connectivity regions such as Ashburn, Virginia, F5 has introduced Resiliency Zones — additional Regional Edge clusters within the same metropolitan area — as a strategic capacity expansion mechanism. These new RE instances introduce new site names and labels that may not be automatically included in existing Virtual Site configurations depending on the label selector used.

Answer/Recommended Actions

Understanding Resiliency Zones

A Resiliency Zone is an additional Regional Edge cluster deployed within the same metropolitan (metro) area as an existing Regional Edge POP. Resiliency Zones may be within the same physical facility (split across racks) or within a common campus of POPs (separate buildings). Key characteristics include:

  • Each Resiliency Zone consists of dedicated compute structures and network hardware, forming isolated fault and operational domains.
  • During maintenance on one Resiliency Zone, other Resiliency Zones within the same POP can handle traffic locally, keeping traffic within the same region or country rather than rerouting to a different POP.
  • Resiliency Zones are not equivalent to AWS Availability Zones, as the level of physical separation may vary and F5 Distributed Cloud services are globally significant rather than locally scoped to a region.

Identifying Resiliency Zone Regional Edges in the Console

Resiliency Zone Regional Edges are identifiable by a letter prefix appended to the existing RE site name. For example:

  • Original RE: dc12-ash
  • First Resiliency Zone: b-dc12-ash
  • Additional zones will follow the same pattern (e.g., c-dc12-ash)

The original Regional Edge will not have an "a" suffix appended. To observe Resiliency Zone REs currently visible in the platform, navigate to a Load Balancer's Performance Dashboard → Origin Servers tab and filter or sort by the original RE site name (e.g., dc12-ash). Both the original and Resiliency Zone entries will appear.

Impact on Virtual Site Configurations

The impact of Resiliency Zones on existing Virtual Sites depends on the label selector used when the Virtual Site was built. Review the following scenarios and take action where applicable:

  • SiteName label selector (e.g., SiteName in dc12-ash): Resiliency Zone REs (e.g., b-dc12-ash) will not be automatically included. Manual updates to the Virtual Site selector are required to include the new Resiliency Zone site names as they come online.
  • Country label selector (e.g., country in USA): Resiliency Zone REs will be automatically included as they come online, requiring no manual Virtual Site updates.
  • Region label selector (e.g., region in Ashburn): Resiliency Zone REs will be automatically included as they come online, requiring no manual Virtual Site updates.

Site Selection Restrictions for Resiliency Zones

Resiliency Zone RE sites cannot be configured as the sole site or Virtual Site for an origin. The F5 Distributed Cloud Console enforces a safeguard that prevents assigning a Resiliency Zone RE (e.g., b-dc12-ash) to an origin configuration without also including the original RE (e.g., dc12-ash) in the same association. Attempting to do so will result in an error similar to the following:

Origin servers cannot currently be configured on the following sites:
b-dc12-ash, c-dc12-ash, ves-io-b-dc12-ash, ves-io-c-dc12-ash.
Please choose a different site or virtual site.

Customer Edge Tunnel Terminations

  • Customer Edge (CE) sites will not terminate their tunnels onto Resiliency Zone Regional Edges at this time.
  • F5 is developing the logic and capabilities to support CE tunnel terminations on Resiliency Zone REs, including the option for customers to choose whether tunnels remain within the same POP across Resiliency Zones.
  • No action is required at this time. Updates will be communicated when this capability becomes available.

Best Practices for Virtual Site Configuration

The recommended approach is to use less granular label selectors (Country or Region) rather than SiteName when configuring Regional Edge Virtual Sites. This approach:

  • Automatically includes new Resiliency Zone REs and new POPs as F5 expands capacity, without requiring manual Virtual Site updates.
  • Maximizes available compute capacity closest to clients for application delivery.
  • Maximizes globally distributed security enforcement points for WAF, L7 DDoS mitigation, bot protection, and API security.

If granular SiteName-based control is required (e.g., for compliance, firewall allowlisting, or geo-IP database management), be prepared for the following operational overhead:

  1. Monitor F5 maintenance and capacity notices. F5 will provide advance notice before new IP prefixes associated with new RE capacity become active. Ensure notification channels with your F5 account team are established.
  2. Update firewall rules and security groups to allow traffic from new RE IP prefixes before they become active.
  3. Verify with your geo-IP database provider that new prefixes are correctly classified for your region and access policies.
  4. Review your VIP Advertisement and Origin Pool Virtual Site strategy to understand the impact of new RE capacity on client-side and server-side traffic flows before changes take effect.
  5. Engage your F5 account team or open a support ticket if you have questions about how Resiliency Zones will impact your specific configuration.
