Description

Controllers and blades in a VELOS chassis may become unreachable, partitions and tenants may disappear, and management access (SSH/GUI) may fail. Error messages and logs can include "no route to host," controller-manager pod restarts, unhealthy multus-status, and OpenShift cluster failures. Attempts to run commands such as show cluster or access the partition may result in communication errors or missing configuration.

Environment

  • Product: F5OS - Chassis (VELOS)
  • Version: 1.8.1 or later
  • Platform: F5-VEL-LTM-CX410-AC, F101
  • Configuration: Internal chassis network prefix changed (e.g., from RFC6598 to RFC1918) without a full chassis powercycle.
  • Symptoms may appear after network configuration changes, controller or blade reboots, or OpenShift cluster reinstallation attempts.

Cause

Changing the internal chassis network prefix (e.g., from RFC6598 to RFC1918 or vice versa) without performing a full chassis powercycle causes controllers and blades to use mismatched internal IP ranges. This results in loss of communication between controllers and blades, loss of configuration, and OpenShift cluster failures.

Recommended Actions

  1. Verify Internal Network Configuration:
    On each controller, check the contents of the following files:
    cat /etc/sysconfig/chassis_network_config.txt
    cat /etc/sysconfig/chassis_network_active.txt
    Ensure both files end with:

    network_range_type=RFC6598

    chassis_network_selection=0

    chassis_id=1

    network_prefix=100.65

    If a different network_range_type or prefix is present, update the configuration using:

    config

    system network config network-range-type RFC6598

    commit and-quit

  2. Powercycle the Chassis:
    After confirming the correct network configuration on both controllers, perform a full chassis powercycle. This ensures all controllers and blades reboot and synchronize to the correct internal network settings.
  3. Verify Controller and Blade Communication:
    After powercycling, confirm both controllers are reachable.
    From the active controller, verify blade connectivity:

    ping blade-1.chassis.local

    ping blade-2.chassis.local

    ping blade-3.chassis.local

    ping blade-4.chassis.local

    If blades are not reachable, collect a fresh Qkview for analysis.
  4. Restore Partition and Tenant Configuration:
    Assign blades to the default partition if necessary:

    config

    slots slot range 1-8 partition default

    commit and-quit

    Enable the default partition:

    config

    partitions partition default config enabled

    commit and-quit

    Wait for OpenShift cluster to rebuild and verify cluster health:

    show cluster

    If required, disable and re-enable the partition to ensure proper blade initialization.
  5. Configure Management IPs:
    If management IPs (controller-1, controller-2, floating) are missing from the running-config, set them using:
    config
    system mgmt-ip config ipv4 controller-1 address <controller-1-IP>
    system mgmt-ip config ipv4 controller-2 address <controller-2-IP>
    system mgmt-ip config ipv4 floating address <floating-IP>
    system mgmt-ip config ipv4 prefix-length <prefix>
    system mgmt-ip config ipv4 gateway <gateway-IP>
    commit and-quit
  6. Additional Configuration:
    Set partition management IP , hostname , DNS server , NTP server as needed .
    If restoring from a ConfD backup file : Always verify 'system network' settings before / after restore ; immediately revert any unintended changes to prevent recurrence of mismatched networking .
