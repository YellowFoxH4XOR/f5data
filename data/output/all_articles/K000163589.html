    VELOS architecture: system controller, partition, blade, and tenant

    • Blades with front-panel dataplane ports.
    • Chassis partitions that own groups of blades.
    • Tenants within those partitions.
    • Separate controller-management and partition-management paths.

    • 0/0.0 for all interfaces in the partition.

    • For tenant management, identify the primary blade and use the relevant management interface.

    Answer/Recommended Actions

    VELOS uses different capture procedures depending on whether you are troubleshooting dataplane traffic in a chassis partition or out-of-band management traffic through the system controller. Do not apply the rSeries/F5OS-A interface syntax directly to VELOS/F5OS-C.

    1. VELOS chassis partition — dataplane ARP

    Run this from the VELOS chassis partition CLI as an administrator:system diagnostics tcpdump outfile velos-partition-arp.pcap bpf "arp"

    This captures ARP traffic for the current chassis partition, including traffic traversing front-panel ports assigned to the partition and relevant backplane traffic. The capture operation runs across the member blades and combines the results.

    The file is stored in the partition’s shared tcpdump directory:/var/F5/partition<partition-ID>/shared/tcpdump/

    It is exposed through the F5OS CLI as:diags/shared/tcpdump/

    In the GUI it can be located by going to 

    SYSTEM SETTINGS > File Utilities :: dias/shared/ :: tcpdump

    Stop the capture with Ctrl+C.

    Capture a specific blade interface

    The VELOS interface format is:<blade>/<port>.<subport>

    For example:system diagnostics tcpdump interface "2/1.0" outfile blade2-port1-arp.pcap bpf "arp"

    This captures interface 1.0 on blade 2.

    To capture all interfaces in the partition, omit the interface option or use:system diagnostics tcpdump interface "0/0.0" outfile partition-all-arp.pcap bpf "arp"

    To capture traffic entering or leaving the host side of blade 2, the VELOS documentation specifies:system diagnostics tcpdump interface "2/0.0" outfile blade2-host-arp.pcap bpf "arp"

    Use an appropriate interface or LAG filter where possible. VELOS interfaces can operate at high rates, and an overly broad capture can result in dropped packets. Also place outfile before bpf; the documented syntax warns that reversing those options can cause a BPF syntax error.

    Source: KB K12313135: Overview of the tcpdump utility on the VELOS system.

    2. VELOS system controller — controller management ARP

    For ARP related to the system controller management addresses, use the Linux host interface, not the partition system diagnostics tcpdump command.

    First identify the active system controller:show system redundancy

    Then access the active controller’s root bash shell and capture on team0:tcpdump -s0 -enni team0 -w ~/velos-controller-arp.pcap "arp"

    For ARP and ICMP together:tcpdump -s0 -enni team0 -w ~/velos-controller-arp-icmp.pcap "(arp or icmp)"

    team0 is the management-side interface used by the system controller. The capture should normally be taken on the active controller because VELOS management traffic is handled through the active controller’s management path.

    Source: KB K000139433: INTERNAL — Capturing VELOS management traffic.

    3. VELOS partition management ARP

    If the issue concerns the partition management IP, first identify which system controller is active for that partition:show system redundancy

    Run the capture from the active system controller’s root bash shell, also on team0:tcpdump -s0 -enni team0 -w ~/velos-partition-management-arp.pcap "arp"

    For a focused test involving a particular partition management IP:tcpdump -s0 -enni team0 -w ~/partition-management-arp.pcap \"(host <partition-management-IP> or arp)"

    The partition CLI’s system diagnostics tcpdump is intended for that partition’s dataplane capture. It is not the appropriate method for selecting the controller management interface team0.

    4. If the problem involves a tenant management IP

    For tenant out-of-band management traffic, identify the tenant’s primary blade from the partition CLI:show tenants tenant <tenant-name>

    Then access the primary blade’s root bash shell and capture on the tenant management subinterface documented by F5:tcpdump -s0 -enni team0.4 -w ~/tenant-management-arp.pcap "arp"

    The exact subinterface should be confirmed for the VELOS/F5OS-C release and tenant placement. The F5 procedure identifies team0.4 for tenant management traffic.

    5. View or export a partition capture

    From the partition CLI, the documented file location is exposed as diags/shared/tcpdump. For example:file show diags/shared/tcpdump/velos-partition-arp.pcap

    To export it:file export local-file diags/shared/tcpdump/velos-partition-arp.pcap \
    remote-host <server> \
    remote-file <remote-path>/velos-partition-arp.pcap \
    username <user>

    Check the transfer with:file transfer-status

    You can also use the partition GUI under System Settings → File Utilities, selecting the diags/shared/ base directory and then tcpdump.

    Source: KB K12313135: Overview of the tcpdump utility on the VELOS system.

    Practical capture plan for an ARP issue

    For a tenant-to-network or tenant-to-tenant ARP problem, collect concurrently:

    1. Partition dataplane capture using system diagnostics tcpdump.
    2. Tenant TMOS capture using the tenant’s tcpdump.
    3. System-controller management capture only if the affected traffic uses management IPs.
    4. A QKView from the relevant system controller, partition, and tenant.

    The partition capture shows how VELOS handled the traffic within that partition; the tenant capture confirms what the BIG-IP tenant generated or received; and the controller capture is relevant only to the management path.

    Additional Information

    Effect of F5OS 2.0

    F5OS 2.x is a unified software release family. Packet-capture behavior remains dependent on the platform’s hardware forwarding architecture and the management layer where the capture is initiated.
