Known Issue

This is most likely the result of a known issue. If you have configured SSL proxy target virtual servers that do not match a self IP address, they are bound to BIG-IP's loopback interface. If those proxy addresses are not included in the loopback network (127.0.0.0/8), they are still bound to the loopback interface with an 8-bit netmask (255.0.0.0). For example, if you create a virtual server with the address 10.10.1.1 and there is no matching self IP network, the virtual server 10.10.1.1 is bound to the loopback interface with a netmask of 255.0.0.0.

If ZebOS is restarted on an active unit when this type of target virtual server exists, ZebOS creates a route for the network represented by the target virtual server and netmask to the loopback interface. As a result, any addresses within the internal network fall within the new route, traffic destined for those addresses will be routed to BIG-IP's loopback interface, and will never reach the intended destination.

F5 Networks Product Development tracked this issue as CR41694 and CR42150.

Workaround

To work around this issue, specify a 32-bit netmask (255.255.255.255) for all target virtual servers that do not match a self IP address. To change the netmask of an existing virtual server, perform the following steps:

  1. Log in to the command line.
  2. Redefine the virtual server, using the following command syntax:

    bigpipe virtual <address>:<port> netmask <netmask> use <object> <name>

    Replace the command variables as listed below:
    • <address> with the virtual server address
    • <port> with the virtual server service port
    • <netmask> with the new netmask
    • <object> with pool or rule
    • <name> with the name of the pool or rule the virtual server will use.

    For example:

    bigpipe virtual 10.10.1.1:80 netmask 255.255.255.255 use pool testpool
