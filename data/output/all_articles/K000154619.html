Description

In BIG-IP SSL Orchestrator environments, there may be a requirement to support both SSL offloaded (decrypted) HTTPS traffic and direct TCP passthrough (such as telnet) to the same backend server. The challenge is to allow SSL offload for protocols that require decryption (e.g., HTTPS) while also permitting non-SSL protocols (e.g., telnet) to bypass SSL processing and reach the backend server unmodified. This scenario requires careful configuration to distinguish between SSL and non-SSL traffic and to direct each to the appropriate processing path.

Environment

  • SSL Orchestrator
  • Topology
  • Virtual server

Cause

When a single virtual server is configured for SSL offload (Standard mode), all traffic is expected to be SSL/TLS and is processed accordingly. Non-SSL protocols such as telnet cannot be decrypted and will fail if directed to a virtual server expecting SSL handshakes. Conversely, switching to a Performance L4 (PL4) virtual server allows passthrough of all TCP traffic but disables SSL offload, making it impossible to decrypt HTTPS traffic. The need to support both types of traffic to the same backend server is not natively handled by a single virtual server configuration.

Recommended Actions

There are 2 ideas for this issue, please review and try to work out the proper configuration to match the network environment and your requirement.

  1. Separate Virtual Servers for SSL and Non-SSL Traffic:

The existed Standard virtual server with SSL and HTTP profiles for HTTPS (SSL offload and decryption).

Create a new virtual servers: A Performance L4 (PL4) or Standard virtual server without SSL profiles for direct TCP passthrough (e.g., telnet).

Use distinct destination ports or IP addresses if possible to separate traffic types.

  1. Protocol Detection and Traffic Steering:

If both traffic types must arrive on the same IP/port, cannot distinguish the traffic via IP address and port, use an initial PL4 virtual server with an iRule to inspect the first few bytes of each connection.

The iRule should detect SSL handshake initiation (for HTTPS) and use the virtual command to hand off the connection to the Standard virtual server for SSL offload. Non-SSL traffic (e.g., telnet) should be allowed to pass through or be directed to a separate pool or virtual server.

Example iRule logic:

On CLIENT_ACCEPTED, collect initial payload.

If payload matches SSL handshake, use virtual command to switch to the SSL offload virtual server.

Otherwise, allow passthrough.

Caveats and Limitations:

SSL offload and protocol detection require careful iRule implementation; improper handling can result in resets or protocol errors. Test thoroughly to ensure correct separation and handling of both SSL and non-SSL traffic.
