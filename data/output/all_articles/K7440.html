Topic

A passive health monitor uses an iRule to parse the server response and change the pool member status when a pre-defined server response is seen in response to load balanced traffic.

When a BIG-IP LTM virtual server is configured with a passive health monitor iRule, the BIG-IP LTM parses the pool member's response for a defined value. When the pool member returns the defined HTTP value, the BIG-IP LTM system can do one of the following:

  • Send the connection to a different server
  • Mark the pool member as down

Benefits of passive health monitoring

One of the benefits of using a passive health monitor iRule is that the BIG-IP LTM system does not have to wait for an ECV or an EAV health monitor to time out before marking the pool member as down and redistributing the request. When the defined value is returned from the pool member, the BIG-IP LTM system can immediately mark that pool member as down and manage the request appropriately.

Configuring a passive health monitor

To configure a passive health monitor, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > iRules.
  3. Click Create.
  4. Type a name for the iRule.
  5. Enter the required iRule syntax in the Definition field.

    Note: For an example iRule, refer to the Best practices recommendations section of this article.

  6. Click Finished.

You must now associate the iRule with the virtual servers for which passive monitoring is desired.

Best practices recommendations

F5 recommends the following best practices when configuring passive monitors:

Passive monitor must be applied in conjunction with a pool or pool member application health monitor

Passive health monitor iRules should always be used in combination with a pool or pool member application health monitor. If you use a passive health monitor iRule without also applying any application health monitors, pool members will never be marked up after they have been marked down by a passive health monitor iRule. The BIG-IP LTM health monitors continuously manage the status of the pool member depending on the server response to the monitor, even if no traffic is load balanced to the pool. The pool member will continue to be marked down as long as it does not respond as expected to the health monitor. However, as soon as the pool member responds as expected to the health monitor, it will be marked up again.

Note: If you use a passive health monitor iRule in combination with only a node monitor, such as the ICMP monitor, the node monitor can mark the IP address of the downed pool member and the pool member itself as up immediately, although the application service may not be responding. You must apply a monitor to the pool or the pool member itself to properly manage service availability for pool members.

Parsing the server response

The simplest form of a passive health monitor iRule parses the server response for HTTP status codes. For example, an HTTP 5xx status code indicates that the server has encountered an error or is incapable of performing the request, and the following iRule parses the server response for an HTTP status code equal to or greater than 500, and marks the node as down when the server response contains any HTTP 5xx status code:

when HTTP_RESPONSE { 
    if { [HTTP::status] >= 500 } {    
        LB::down
    }
}

However, F5 does not recommend parsing exclusively for HTTP 404 or 50x status codes in the passive health monitor iRule, as they may result in a possible DoS attack on the site if an attacker requests request nonexistent objects on the web page, or submits malformed requests to an application without proper error management.

You can instead use the HTTP::collect and HTTP::payload commands to collect and parse server responses for specific error codes or messages which are known to occur when your servers are unable to process requests, such as when the backend database is not available, or when the server is overloaded. For example, the following iRule looks for status code 50x, but only marks the pool member down when a specific error is seen in the HTTP error data returned by the server:

when HTTP_REQUEST {  
# Don't allow data to be chunked  
    if { [HTTP::version] eq "1.1" } {
        if { [HTTP::header is_keepalive] } {
            HTTP::header replace "Connection" "Keep-Alive"    
        }    
        HTTP::version "1.0"  
    }
}

when HTTP_RESPONSE {  
# Get the content length so we can request the data to be  
# processed in the HTTP_RESPONSE_DATA event.  
    if { [HTTP::header exists "Content-Length"] && [HTTP::header "Content-Length"] < 1048577 } {
        set content_length [HTTP::header "Content-Length"]  
    } else {    
        set content_length 1048576  
    }
# comment out the log command below when using the iRule in a production environment
    log local0.info "Content Length: $content_length"  
    if { $content_length > 0 } {
        HTTP::collect $content_length  
    }
}

when HTTP_RESPONSE_DATA {
    if {[HTTP::payload] contains "this specific string"} {
        LB::down
    }  
    HTTP::release
}

Note: For more information about HTTP data collection and the previous iRules example, refer to the following DevCentral codeshare entry: HTTP Payload Collection.
