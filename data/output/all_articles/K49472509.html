Description

Aspen Mesh Packet Inspector 1 is a component available in Aspen Mesh Carrier Grade distribution. It provides advanced HTTP traffic inspection and capture capabilities for applications running in a Kubernetes mesh environment. Packet Inspector allows capturing application network traffic in plain text before it is encrypted by sidecar proxies. The captures add contextual metadata about pods and services to match captures with workloads running in the Kubernetes cluster. Data are stored in a well-known pcap format so they can be analyzed by tools like Wireshark. This article presents a technical overview about Packet Inspector architecture and components.

Additional Information

Aspen Mesh Packet Inspector 1 consists of several components that work together:

  • Envoy filter used by every istio-sidecar proxy and gateway capturing and forwarding packets to Packet Inspector daemon set.
  • Packet Inspector Daemon Set deployed on every Kubernetes node receiving data from Envoy filters, transforming packets into pcap format, and forwarding files to network analysis tool or emulator.
  • Network analysis tool or analysis emulator receiving pcap files from Daemon set and storing them on a filesystem.

To use Packet Inspector, we need to install Aspen Mesh Carrier Grade release which is distributed as a separate installation package. At the moment of writing this article Packet Inspector is not available a separate package installed at the top of standard Aspen Mesh system. Packet Inspector filters are compiled as all other Envoy filters and Aspen Mesh is building dedicated carrier grade istio-proxy container with all required software to run packet inspector.

For Packet Inspector Installation, refer to Aspen Mesh Packet Inspector Installation Guide .

Installation process is a few steps procedure:

  1. Create and provision custom CA certificate for Istio and Aspen Mesh.
    1. Refer to Provisioning custom CA certificate for Aspen Mesh .
    2. Custom CA certificate is necessary to generate TLS certificates used by Packet Inspector Daemonset and optionally Analysis Emulator.
  2. Label istio-system and optionally analysis-emulator namespaces for Citadel to generate SDS certificate secrets.
    1. Follow the steps described in Installation Guide and Analysis Emulator Install Guide .
  3. Installing Aspen Mesh Carrier Grade release with enabled: Citadel, PacketInspector, and certificateCustomFields.

We can customise installation settings for Packet Inspector in override Helm values yaml file as we always do for Aspen Mesh. For all available fields, refer to Packet Inspector Config Reference Guide .

Analysis Emulator tools included into Aspen Mesh Carrier Grade release can be used as a replacement for other production ready Network Analysis solutions like Gigamon or Netscout. Analysis Emulator should not be used in production and it is intended for test purposes only. Customers wanting to use Analysis Emulator can follow Analysis Emulator Installation Guide to install the tools. Helm chart is used to create all emulator resources.

Packet Inspector 1 Envoy filters are using gRPC protocol to stream packets from PODs to the Daemonset using NodePort 31672 exposed by the Kubernetes Service. Topology Aware routing was not available in later releases of Kubernetes and Packet Inspector cannot guarantee that Envoy filters will connect to local Daemon set POD using Node Port. 

Daemon set PODs are implemented as circular buffers. The size of the buffer can be controlled by daemonSetBufferMemoryPercent field in the override values.yaml file. This value is a percentage of the total amount of memory allocated to the Packet Inspector daemon set. When this buffer limit is exceeded, packet captures will be dropped starting with the oldest capture and proceeding in capture order. The total memory allocated defaults to 128MB. If the daemon set does not have a memory limit assigned, this value will be based on the total node memory available. It is strongly recommended to set the memory limits depending on your environment to ensure all packets can be captured.

Packet Inspector daemon set PODs are forwarding packets stored in pcap files to network analysis emulator tool using HTTP2 protocol on port 2100 (can be customized).

Beginning Aspenmesh 1.11.8-am4 we introduced Packet Inspector 2 component to our Istio distribution.
Packet Inspector 2 has simplified architecture. Sidecars are streaming application traffic directly to analysis service (either the network analysis tool or the analysis emulator). The Aggregator Daemonset PODs were removed and are not installed with Packet Inspector 2.
The Solution redesign allowed us to give a user the control of what kind of application traffic is being captured.
By setting labels on PODs and namespaces we can configure which Sidecar should capture application traffic:

  1. All pods with sidecars, regardless of namespace    
  2. All pods with sidecars in a namespace    
  3. A set of labeled pods with sidecars, regardless of namespace
  4. A set of labeled pods with sidecars in a namespace
