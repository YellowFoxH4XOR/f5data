Known Issue

The Traffic Management Microkernel (TMM) may produce a core file with the 'Assertion "domain != RT_DOMAIN_NONE" failed' error message.

This issue occurs when all of the following conditions are met:

  • The TMM processes Session Initiation Protocol (SIP) requests that include via headers with a missing rport attribute.
  • The SIP profile attached to the virtual server has the Dialog Aware setting enabled.

Impact

The BIG-IP system may temporarily fail to process traffic and fail over if configured as part of a high-availability system.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The TMM process restarts and produces a core file in the /var/core directory.
  • The BIG-IP system logs a message similar to the following example in the /var/log/tmm* files:

    notice panic: ../netinet/route.c:722: Assertion "domain != RT_DOMAIN_NONE" failed.

Workaround

To work around this issue, you can either disable the Dialog Aware setting in the associated SIP profile, or configure SIP OneConnect in scenarios where the BIG-IP system is the intermediary between more than two parties. To do so, perform one of the following procedures:

Disabling the Dialog Aware setting for the associated SIP profile

Impact of workaround: The TMM will no longer be able to snoop SIP dialog information. The Dialog Aware setting is disabled by default.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Profiles > Services > SIP.
  3. Click the name of the affected SIP profile.
  4. Clear the Dialog Aware check box.
  5. To save the change, click Update.

Configuring SIP OneConnect

If your configuration requires separate inbound and outbound SIP virtual servers and profiles (for example, in scenarios where an internal client initiates an outbound call using a wildcard virtual server to an external client that already has an existing flow on the inbound virtual server), you can enable SIP OneConnect by configuring the Community strings for both SIP profiles. This creates a proxy functional group which associates the SIP profiles.

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Profiles > Services > SIP.
  3. Click the name of the SIP profile associated to your first SIP virtual server.
  4. In the box next to the Community setting, enter a unique name which will identify this SIP profile as part of your proxy functional group.

    For example:

    myProxyGroup
  5. To save the change, click Update.
  6. Repeat steps 3 through 5 for each SIP profile that you wish include in your proxy functional group.
