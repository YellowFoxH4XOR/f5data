Description

The ntpq command provides us with useful information about the NTP servers that are currently configured on the device, however there are quite a few details that need to be understood in order to properly read the provided output.

Important: In order for NTP to function properly and to be considered accurate, it is advised, according to RedHat, to have at least 4 distinct NTP servers configured. (In some cases 3 may be acceptable, but best to avoid using only 3 NTP servers). Anything below that number cannot be considered accurate enough.

See the links in the Related Content section below for ways to force sync the NTP clock where/when necessary.

Environment

  • NTP
  • The ntpq command

Cause

None

Recommended Actions

Below is a sample ntpq -pn output (the IPs used below are for illustration purposes, therefore not realistic, and should not be used as NTP servers):

     remote           refid      st t when poll reach   delay   offset  jitter
==============================================================================
 127.127.1.0     .LOCL.          10 l  23d   64    0    0.000    0.000   0.000
o127.127.22.0    .PPS.            0 l   11   16  377    0.000    0.003   0.001
*10.0.0.23       .MRS.            1 u 1004 1024  377    2.859    0.051   0.100
*192.0.2.251     192.0.2.252      2 u   28   64  357    9.257   -0.738   0.117
-198.51.100.133  203.0.113.102    2 u   64   64  373   16.422    1.668   0.343
+203.0.113.30    172.16.0.145     2 u    1   64  377   11.194   -1.658   0.116
+172.16.0.1      198.51.2.174     2 u   21   64  317   11.198   -0.816   0.068

Explanation by column:

  1. remote: This is the list of NTP servers that are configured on the device. 
    • Accepted peers:
      • * (System Peer): Identifies the current time synchronization source. This is the single peer selected by the NTP algorithm as the best candidate to discipline the local system clock.
      • + (Candidate): Indicates a peer that is considered acceptable and is included in the final selection set (the set used to calculate the time).
      • # (Failsafe Candidate): Signifies a peer that has been selected for synchronization, but the estimated distance (e.g., dispersion or jitter) to the host exceeds a predefined maximum threshold. It remains available as a high-stratum failsafe.
      • o (PPS Signal Used): Identifies a peer that is selected and is utilizing a high-precision Pulse Per Second (PPS) signal to improve its accuracy. This typically results in higher precision than standard NTP alone.
    • Discarded Peers:
      • x (False Ticker): Marks a peer that has been discarded because it fails the intersection algorithm and is deemed a false ticker (its time is inconsistent with the majority of other good time sources).
      • - (Clustered Out): Indicates a peer that was discarded by the clustering algorithm. This algorithm removes redundant peers when multiple peers have similar measurements to optimize the selection process.
      • . (Excessive Jitter): Signifies a peer that was discarded because it was selected from the end of the candidate list, typically due to excessive jitter, delay, or being out of specification.
      • Blank (Discarded): A blank prefix means the host was discarded early in the process due to factors like having an unacceptably high Stratum number or failing initial sanity checks (e.g., unreachable, massive offset).
  2. refid: The refid is the immediate next hop in the synchronization chain (not necessarily the ultimate Stratum 1 source). The minimum suggested number of different NTP servers according to RedHat is 4 servers, with a minimum of 3. Anything less than that will not be considered accurate enough. 

    REFID for Stratum 1 Servers

    When the synchronized server is at Stratum 1, the REFID displays a four-character ASCII code identifying the physical, high-precision time source it is directly connected to. This code indicates the type of hardware being used to generate the time signal. The list of codes is quite extensive, so the codes shown below are some of the most common.

    Common and Official Code Examples

    • .GPS.: Identifies the use of a Global Positioning System receiver as the time source. This is the most prevalent high-accuracy source today.
    • .PPS.: Denotes the server is utilizing a Pulse Per Second signal, usually derived from a GPS receiver or atomic clock, to achieve microsecond-level accuracy.
    • .ATOM.: Indicates the use of a dedicated Atomic Clock (e.g., Cesium or Rubidium standard) physically connected to the server.
    • .WWVB.: Identifies synchronization via the WWVB Radio Time Signal broadcast from the U.S. National Institute of Standards and Technology (NIST).
    • .MSF.: Identifies synchronization via the MSF Radio Time Signal broadcast from Anthorn, UK.
    • .DCF.: Identifies synchronization via the DCF77 Radio Clock signal broadcast from Mainflingen, Germany.
    • .IRIG.: Indicates the use of a time code following the Inter-Range Instrumentation Group standards, commonly used in military or aerospace applications.
    • .GOES.: Denotes synchronization via the time signals derived from the GOES Satellites.
    • .CHU.: Identifies synchronization via the CHU Radio Time Signal broadcast from Ottawa, Canada.
    • .STEP.: A server displaying .STEP. derives its time from its own internal hardware clock (the local system oscillator or Real-Time Clock - RTC). It also indicates that the server's local clock is managed by the Step Clock Synchronizer (SCS), which is designed to handle time synchronization errors using two distinct methods: for errors exceeding the panic threshold (typically ±128 ms), the clock is instantly stepped (reset to the correct time); for smaller errors, the clock's frequency is slewed (gradually adjusted) to maintain continuity.
    • .XFAC.: This is a "kiss-o'-death" or status code that appears in the refid column. It indicates an interface or association change. Essentially, it means the connection to that specific NTP server was reset because the local network interface used to reach it changed, went down, or was reassigned. .XFAC. can occur when the NTP daemon (ntpd) detects that the local IP address or network interface associated with a peer has changed or disappeared, it resets the "association" (the logical connection) to that server. During this reset:
      • The reach register is cleared to 0.
      • The stratum is usually set to 16 (unsynchronized).
      • The refid is temporarily set to .XFAC. to explain why the history for that peer was wiped.
      While not officially documented in every manual, it is widely accepted in the NTP community to stand for: X (Inter)Face Association Change.
      Common causes of .XFAC. are (but not limited to):
      1. Network Flapping: If your Ethernet or Wi-Fi drops and reconnects, ntpd may reset associations.
      2. DHCP Lease Renewal: If your local machine receives a new IP address, the old routing path is no longer valid, triggering a reset.
      3. VPN Connectivity: Starting or stopping a VPN often changes the default routing table, causing ntpd to re-evaluate which interface to use for its peers.
    • .INIT.: Indicates that the NTP client has not yet established a connection with that specific server. It is a transient state signifying Initialization. The client has sent a request (or is about to), but a valid response from the remote peer has not been received, processed, and validated. Until the server responds with its own stratum and reference ID, the client populates the field with this placeholder.
      • Transition States
        • Packet Exchange: The client must successfully exchange a minimum of one packet (and usually several for filter dispersion) before .INIT. is replaced by a real IP address or a four-letter Kiss-o'-Death (KoD) code.
        • Reachability: Under the reach column, a server in .INIT. will typically show 0, indicating that no successful communication has occurred in the last eight polling intervals.
      • Possible root causes: If a server remains in the .INIT. state indefinitely, the following barriers are present:
        1. Network Connectivity: The host cannot reach the remote IP.
        2. Firewall Obstruction: UDP port 123 is blocked inbound or outbound.
        3. Server Refusal: The remote server is down or intentionally ignoring requests from the client's IP.
        4. DNS Failure: If using a hostname, the client may be failing to resolve the address, though ntpq usually shows the IP or hostname if resolution succeeded.
    • .LOCL.: A specific, officially recognized code that signifies the server is using an Unsynchronized Local Clock. This usually means there is no external source, and the local clock is being used as a fallback, which carries a very low accuracy rating. This is possibly the only exception where a code will show up at a stratum 10 server. There is only one scenario where using .LOCL. is considered good practice:
      • Isolated Networks: If you are running a completely private network with no internet access and no GPS/Atomic clock, you pick one server to be the "Master." You configure that server to use its own .LOCL. at a high stratum (like Stratum 10) so that all other machines at least agree on the same time, even if that time is slightly off from the real world.  Common IPs seen that generate the .LOCL. refid:
      • 127.0.0.1: This is your own computer (localhost).
      • 127.127.1.0: You may also see this specific "pseudo-IP." It is a special internal address used by the NTP daemon to talk to the local hardware clock.

    Vendor-Specific and Aggregate Code Examples

    Some codes are specific to hardware vendors or represent a combination of sources:
    • .MRS.: A widely adopted code (often used by vendors like Meinberg) indicating a Multi-Reference Source. This means the clock hardware utilizes multiple signal types (e.g., GPS, Galileo, and radio time) simultaneously for better redundancy and stability.
    • .CDMA.: Indicates the use of a time signal derived from the Code Division Multiple Access wireless network infrastructure.

    REFID for Stratum 2 and Higher Servers

    When the synchronized server is at Stratum 2 or any higher stratum, the REFID does not display a code. Instead, it displays the IP address of the immediate upstream time server it is currently synchronized with. This is essential for tracing the path of the time signal back toward the Stratum 1 source. Example: If your Stratum 3 server is getting time from the server at 192.168.1.1, the REFID field will simply show 192.168.1.1.
  3. st: The stratum level of the remote host - In practical, real-world networks, you will rarely see a synchronization chain extend beyond Stratum 4 or 5, as the accuracy loss and increased dispersion (error) at higher strata become functionally meaningless. 
    • Stratum 0 (Reference Source): This level represents the highest-precision reference clock. These sources are highly stable and typically include atomic clocks (Cesium, Rubidium) or high-accuracy external time signals (e.g., GPS or radio time signals). Stratum 0 devices are not subject to network jitter.
    • Stratum 1 (Primary Servers): These are time servers directly synchronized to a Stratum 0 source. They act as the highly accurate primary time providers on the network. They maintain precise time without referencing any other network server.
    • Stratum 2 (Secondary Servers): These servers obtain their synchronization by actively querying and peering with Stratum 1 servers (or other Stratum 2 servers). Stratum 2 servers distribute time to client devices and can often handle load balancing for larger network segments.
    • Stratum 3, Stratum 4, etc.: The hierarchy continues with each successive Stratum level. A server at Stratum N synchronizes to a server at Stratum N−1. Each step away from Stratum 1 introduces minor, cumulative deviations in time accuracy due to network latency and server processing time.
    • Stratum 15 (Lowest Usable Level): This is the highest stratum number that can be actively synchronized and distributed across the network.
    • Stratum 16 (Unsynchronized/Unreachable): A stratum value of 16 is reserved by the protocol to indicate that the clock is unsynchronized or that the remote peer is unreachable. Any server reporting a stratum of 16 cannot be used as a time source
  4. t: Type of association with the server 
    • l (Local): Indicates the server is syncing to a local reference clock attached directly to the machine, such as a high-precision GPS receiver or a radio clock. This often represents a Stratum 0 source.
    • u (Unicast): The most common synchronization type, signifying a standard client-server relationship where the server polls a specific, known remote NTP server address.
    • m (Multicast): The server is listening for and synchronizing with a group of remote servers over a defined multicast address (a one-to-many communication).
    • b (Broadcast): The server is receiving time updates from a source that is broadcasting the time to the entire local network segment (a one-to-all communication).
    • – (Netaddr): This usually indicates a non-synchronizing peer or a reserved internal entry where the network address (Netaddr) field is not applicable (often seen as 0.0.0.0).
  5. when: Specifies the time elapsed (in seconds) since the most recent successful message exchange (probe or response) was received from the remote peer or server.
  6. poll: Represents the current polling interval (in seconds) being used to query the remote host. This value is dynamically adjusted by the NTP algorithm, constrained by the minpoll and maxpoll settings defined in the configuration file.
  7. reach: An octal-encoded 8-bit shift register that tracks the success or failure of the last eight NTP probes sent to the remote host.
    • A full register of successful responses is indicated by the value 377 (binary 11111111).
    • A value of 001 (binary 00000001) means only the most recent probe was successful.
    • A value like 357 (binary 11101111) indicates that the fourth-to-last probe failed, while the others succeeded.
  8. delay: The total round-trip time (in milliseconds) required for an NTP message to travel from the local host to the remote peer and for the reply to return. It is a fundamental measurement of network latency and path distance. The NTP algorithm minimizes this delay, which is critical for determining the synchronization path's symmetry (the assumption that travel time is equal in both directions) and assessing the true distance to the time source.
  9. offset: The estimated time difference (in milliseconds) between the local system's clock and the clock of the remote peer. This metric represents the magnitude of the error in the local time and is the primary value that the NTP daemon seeks to drive toward zero through continuous clock adjustments. A consistently high offset value (e.g., exceeding 128 ms) is a key indicator of severe synchronization difficulty and will typically trigger alert messages in system logs. Do note that the offset tends to be shown in milliseconds, although some older versions may display it in seconds.
  10. jitter: The estimated error bound of the offset measurement, calculated as the Root Mean Square (RMS) of the differences in successive offset values across the most recent samples. Measured in milliseconds (ms), this metric is a primary indicator of network service quality. Low jitter is crucial for achieving stable and predictable synchronization; conversely, excessively high jitter often results in the peer being discarded by the NTP selection algorithms (e.g., marked with a '.' or 'x').

Do note that the offset tends to be shown in milliseconds, although some older versions may display it in seconds.
jitterThe estimated error bound of the offset measurement, calculated as the Root Mean Square (RMS) of the differences in successive offset values across the most recent samples. Measured in milliseconds (ms), this metric is a primary indicator of network service quality. Low jitter is crucial for achieving stable and predictable synchronization; conversely, excessively high jitter often results in the peer being discarded by the NTP selection algorithms (e.g., marked with a '.' or 'x').
