Known Issue

The performance graphs on a VIPRION system may report more blades than are installed in the chassis. This issue occurs when the following conditions are met:

  • The VIPRION system is booted after a software upgrade or installation.

This issue occurs because the mcpd process incorrectly identifies the VIPRION system as an appliance rather than a chassis. The statsd process then creates a performance data file that is meant for an appliance. When the mcpd process subsequently identifies the VIPRION system as a multi-blade chassis, the statsd process creates the correct performance data files appropriate for a cluster, but does not remove the incorrect performance data file.

Impact

The performance graphs may show incorrect data.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • BIG-IP iHealth lists Heuristic H380445 on the Diagnostics > Identified > Low screen.
  • The statsd process incorrectly creates a /var/tmstat/cluster/blade0 performance data file on the affected VIPRION system (the blade0 file should exist on only a standalone appliance system). The names of the performance data file must correspond to the blades installed on the VIPRION system. For example, if there are two blades installed in slot 1 and 2, there must be only two performance data files with corresponding filenames /var/tmstat/cluster/blade1 and /var/tmstat/cluster/blade2.
  • The Memory Used graph reports the Total Phys Memory incorrectly on the VIPRION system. For example, if the VIPRION 4400 system has three B4100 blades installed, the Total Phys Memory is reported to have 32.0 G instead of 24.0 G.
  • The tmsh show /sys tmm-info command incorrectly reports a table for TMM0.0
  • The tmsh show /sys tmm-info global command reports an incorrect TMM Count. For example, if the VIPRION 4400 system has three B4100 blades installed, the TMM Count is reported as 16 instead of 12.

Workaround

Impact of workaround: There may be gaps in the performance graphs indicating the restart of the statsd process.

To work around this issue, you can remove the /var/tmstat/cluster/blade0 file and restart the statsd process. To do so, perform the following procedure:

  1. Log in to the BIG-IP command line.
  2. Remove the /var/tmstat/cluster/blade0 files from all blades by typing the following command:

    clsh rm /var/tmstat/cluster/blade0

  3. Restart the statsd processes on all blades by typing the following command:

    clsh bigstart restart statsd
