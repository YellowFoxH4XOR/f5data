Description

Web server is not accessible when connecting via newly configured virtual server.

Packet capture shows a reset from the BIG-IP due to No route to host, similar to the following example:

10.10.10.1 → 10.10.10.80  TCP IN  s1/tmm3 : 55619 → 443 [SYN]
10.10.10.80 → 10.10.10.1  TCP OUT s1/tmm3 : 443 → 55619 [SYN, ACK]
10.10.10.1 → 10.10.10.80  TCP IN  s1/tmm3 : 55619 → 443 [ACK]
10.10.10.1 → 10.10.10.80  TLSv1 IN  s1/tmm3 : Client Hello
10.10.10.80 → 10.10.10.1  TCP OUT s1/tmm3 : 443 → 55619 [ACK]
10.10.10.80 → 10.10.10.1  TLSv1.2 OUT s1/tmm3 : Server Hello, Change Cipher Spec, Encrypted Handshake Message
10.10.10.1 → 10.10.10.80  TLSv1.2 IN  s1/tmm3 : Change Cipher Spec, Encrypted Handshake Message
10.10.10.80 → 10.10.10.1  TCP OUT s1/tmm3 : 443 → 55619 [ACK]
10.10.10.80 → 10.10.10.1  TCP OUT s1/tmm3 : 443 → 55619 [ACK]
10.10.10.1 → 10.10.10.80  TLSv1.2 IN  s1/tmm3 : Application Data
10.10.10.80 → 10.10.10.1  TCP OUT s1/tmm3 : 443 → 55619 [ACK]
10.10.10.80 → 10.10.10.1  TCP OUT s1/tmm3 : 443 → 55619 [RST, ACK] [F5RST: No route to host]

Environment

  • Virtual Server
  • Pool
  • Establishing connections

Cause

BIG-IP has no self IP in pool member's subnet, and no TMM routes configured. TMM is therefore unable to open a server-side connection.

Recommended Actions

Verify how the BIG-IP is supposed to reach the pool member, and configure self IPs and TMM routes as appropriate.

Additional Information

Monitors may succeed if pool members are reachable via a management route, but TMM traffic can never use management routes.
