Description

When using BIG-IP with FastL4 virtual servers to handle SIP traffic, you may encounter the following issues:

  • Inconsistent Source Port Preservation:
    SIP packets (such as INVITE or OPTIONS) sent from a SIP client to the BIG-IP may have their original source port preserved in some cases, but in other cases, the LC translates the source port to a random high port when forwarding the packet to the backend SIP server.
    • Example of source port mismatch:
      Client-side: IP_A:7592 → VIP:5060
      Server-side: IP_A:34007 → Pool_Member:5060

    • Example of source port preserved:
      Client-side: IP_A:7596 → VIP:5060
      Server-side: IP_A:7596 → Pool_Member:5060

  • One-Way Audio on RTP Streams:
    After SIP signaling is established, RTP (audio) streams may experience one-way audio. This typically occurs when RTP packets are routed through the wrong virtual server or SNAT pool, causing return RTP traffic to be sourced from an unexpected IP address or port. This is often due to overlapping or misconfigured virtual server destination addresses, or the lack of SIP-aware processing.

Cause

  • Source Port Translation:
    With FastL4 virtual servers, if the source port is set to preserve (default), the BIG-IP may not always preserve the original client source port, especially if there are port conflicts or existing connection table entries. This can result in the source port being translated to a random high port.
  • Lack of SIP Profile:
    FastL4 does not provide SIP-aware processing. Without a SIP profile, the BIG-IP cannot inspect SIP messages, manage dynamic pinholing for RTP streams, or handle SIP-specific behaviors such as Via header processing and media negotiation.
  • One-Way Audio:
    One-way audio is often caused by RTP traffic being routed through an incorrect virtual server or SNAT pool, resulting in return RTP packets being sourced from an unexpected IP address or port.

Recommended Actions

Please apply either:

  • Source Port Preservation on FastL4 Virtual Server type
    • Set the virtual server’s source port to preserve-strict to improve the likelihood of preserving the original client source port:
      ltm virtual <VS_NAME> {
  ...
  source-port preserve-strict
  ...
}

       

    • After changing this setting, clear existing connections:
      tmsh delete /sys connection all

  • Use SIP Profile for SIP Traffic for Standard Virtual Server type
    • For SIP deployments, configure a SIP profile on the relevant virtual servers:
      Note: Applying a SIP profile requires the virtual server to be of the "Standard" type. If your current virtual server is set to "Performance (Layer 4)" (FastL4), you must change it to "Standard" before you can attach a SIP profile.
      • Go to Local Traffic > Profiles > Message Routing > SIP.
      • Create a new SIP profile based on the parent profile sipsession.
      • Enable "Honor Via", disable "Do Not Connect Back", and disable "Insert Via Header".
      • Apply this profile to the virtual server handling SIP signaling.
    • This ensures the BIG-IP system can properly parse and manage SIP traffic, preserving protocol-specific behaviors and supporting advanced SIP features.

  • Configure Virtual Servers for RTP
    • Ensure RTP traffic is routed through the correct virtual server by restricting destination addresses/IPs so that each virtual server matches only its intended endpoint(s).
    • Use address lists if multiple destinations are required, but avoid overlap between virtual server definitions.

  • Review SNAT Pool Configuration
    • Assign SNAT pools carefully so that return traffic uses the expected IP addresses. Misconfiguration can cause one-way audio due to unexpected NAT behavior.

  • General Best Practices
    • Avoid using FastL4 alone for complex SIP deployments; use SIP profiles where possible.
    • After any configuration change, test end-to-end call flow and verify via packet capture on BIG-IP that ports and IPs behave as expected.
