K000161599: SFP serial numbers displayed even no SFP inserted

Published
2026-06-05
Updated
2026-06-05
Applies to

  • F5OS-A: 1.8.X, 1.8.4, 1.8.3, 1.8.0
Source
https://my.f5.com/manage/s/article/K000161599

Description

On an F5OS-A system, one or more portgroups continue to display SFP serial numbers and optic state information in CLI output even after the SFP modules have been physically removed from the cage. 
This results in a mismatch between the system-reported hardware status and the actual physical condition of the ports.

Symptoms include:

  • show portgroups CLI output still displays vendor-serialnum and optic-state for portgroups where no SFP module is physically installed
  • Affected portgroups show stale EEPROM data (serial number, optic state) from the last installed module
  • The issue may affect only a subset of portgroups or devices in the same environment, while others behave normally

Environment

  • Platform: rSeries appliance
  • Software: F5OS-A version 1.8.3
  • Affected portgroups: Any portgroup from which an SFP module was physically removed
  • SFP modules involved: OPT-0016 (or similar) SFP modules previously installed and removed
  • Condition: The optics-mgr daemon was killed and restarted multiple times during or immediately after SFP removal events

Cause

A race condition between the timing of the SFP physical removal and the operational state of the optics-mgr daemon.

The normal SFP removal flow on F5OS-A is:

  1. fpgamgr detects the physical removal and fires an "Optic REMOVED" event
  2. optics-mgr receives the event and clears the cached EEPROM/serial data from the ConfD configuration database (CDB)
  3. show portgroups returns no data for that portgroup (empty cage = no output)

When optics-mgr is killed or restarted during or immediately after an SFP removal event, the "Optic REMOVED" notification from fpgamgr is lost in transit — optics-mgr is not running to receive it. As a result, the stale vendor serial number and optic state data from the last insertion is never cleared from the system database.

Devices where the optics-mgr daemon remained stable during SFP removal are not affected.

Answer/Recommended Actions

To clear the stale SFP serial number and optic state data, perform the following steps on each affected portgroup:

  1. Re-insert the SFP module (e.g., OPT-0016) into the affected portgroup.
  2. Monitor platform.log and wait for the system to log the "Optic inserted" event for that portgroup:

Optic inserted Portgroup="<X>" PartNum="..." Serial="..."

  1. Fully remove the SFP module from the portgroup.
  2. Confirm that "Optic REMOVED" is logged in platform.log for that portgroup:

Optic REMOVED Portgroup="<X>"

  1. Verify that show portgroups no longer displays the SFP serial number or optic state for the affected portgroup (empty cage = no output).
  2. Repeat steps 1–5 for each remaining affected portgroup.

Important: Ensure the optics-mgr daemon is running and stable before and during the SFP removal to prevent the "Optic REMOVED" event from being lost again.

Additional Information

  • The optics-mgr daemon caches the last-known EEPROM data for each portgroup. It relies on receiving "Optic REMOVED" events from fpgamgr to clear this cached state. If the daemon is not running at the moment of removal, the event is lost and stale data persists.
  • This issue may affect only specific devices in an environment where multiple rSeries appliances are deployed. Devices on which optics-mgr was stable during SFP removal will not exhibit the stale data behavior.
  • A partially-withdrawn SFP module (latch released but not fully pulled out) can still maintain I2C/EEPROM contact and appear "present" to the system. Always fully extract the module until the "Optic REMOVED" event is confirmed in platform.log.
  • Live DDM reads on affected portgroups will return sentinel/floor values (e.g., RX power = -40.0 dBm, no temperature, no TX power) indicating no physical module is present, even though stale cached data remains visible in show portgroups.
