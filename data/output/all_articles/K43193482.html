Topic

You should consider using this procedure under the following condition:

  • You want to configure Kerberos SSO on the BIG-IP APM system so that the system can use multiple key distribution centers (KDCs) at the same time to provide scalability and better overall performances.

Description

By default, there are several ways to define which KDC servers a Kerberos SSO profile is going to use. The following lists all the current available options:

  • If a KDC entry (IP or FQDN) is provided in the Kerberos SSO profile then the profile uses this server.
  • If no KDC entry is provided in the Kerberos SSO profile, then there are few possibilities:
    • if there is a KDC entry in the appropriate realm defined in the /etc/krb5.conf file, then the profile uses that KDC server.
    • if there are multiple KDC entries in the appropriate realm defined in the /etc/krb5.conf file, then the profile only uses the first entry. It uses the second entry only when the first one becomes unavailable. The profile uses the third one (if any exists) only when the first two KDC servers become unavailable, and so on. This is similar to a high availability (HA) mode.
    • if there is no KDC entry in the appropriate realm defined in the /etc/krb5.conf file and dns_lookup_kdc is set to false, then no KDC servers is usable
    • if there is no KDC entry in the appropriate realm defined in the /etc/krb5.conf file and dns_lookup_kdc is set to true, then the BIG-IP system sends DNS SRV queries (_kerberos._udp/tcp.<DOMAIN>) to fetch the responsible KDCs for a given realm. The profile uses only the first KDC of the retrieved list. The profile uses the second entry (if any exists) only when the first one becomes unavailable. The profile uses the third one (if any exists) only when the first two KDC servers become unavailable, and so on. This is similar to HA mode.

With all these options, only a single KDC at a time is involved, which can be limiting in large environments with high-authentication rate.

In order to use multiple KDC servers at the same time, you can leverage intermediate Kerberos virtual servers that balance the load between selected servers from a pool.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You have administrative access to the Configuration utility.
  • You have a Kerberos realm that contains multiple KDCs.
  • You are running a BIG-IP APM system that is configured to delegate to a Kerberos realm.
  • You have Advanced Shell (bash) access to the BIG-IP system.
  • You understand how to use a vi text editor.

Procedures

The following procedures show you how to configure BIG-IP APM to get the best performances when using Kerberos SSO and you want to load balance to multiple KDC servers.

Perform one of the following procedures depending on whether you have a single domain or multi domain in your environment:

  • Single-domain scenario
    • Create a Kerberos SSO profile
    • Create a node for each and every participating KDC
    • Create a pool to include the relevant KDC servers
    • Create a TCP virtual server listening on port 88
    • Create a UDP virtual server listening on port 88
  • Multiple-domain scenario
    • Create a Kerberos SSO profile
    • Configure /etc/krb5.conf
    • Create a node for each and every participating KDC
    • Create a pool per domain to include the relevant KDC servers
    • Create a TCP virtual server listening on port 88 for each domain
    • Create a UDP virtual server listening on port 88 for each domain

Single-domain scenario

In this scenario, authenticated users are located within a single domain, domain.com which is handled by 2 domain controllers:
  • dc1.domain.com: 10.0.0.1
  • dc2.domain.com: 10.0.0.2
Create a Kerberos SSO profile

In this procedure, you create a Kerberos SSO profile using the following example configuration:

apm sso kerberos /Common/SSO_KERBEROS {
    account-name host/account.domain.com
    account-password $M$dh$ijqYgSKdtZAuvsGQZwCVKdwxb/5DmFDAjiYxCHVWi1Y=
    kdc 192.168.1.1
    realm DOMAIN.COM
}

For this profile, the only difference from the usual configuration is that a fictitious IP address is used in the KDC field. That IP address is a virtual server IP address that will be created later in this procedure. 

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Access > Single Sign-On > Kerberos.
  3. Select Create.
  4. For Name, enter the name of the SSO profile. For example:

    SSO_KERBEROS

  5. For Kerberos Realm, enter the name of the Kerberos realm. For example:

    DOMAIN.COM

  6. For KDC, enter an IP address that will be a virtual server IP address. This is only known to the BIG-IP system so think of it as a fictitious IP. For example:

    192.168.1.1

  7. For Account Name, enter the name of the delegation account created on your Active Directory. For example:

    host/account.domain.com

  8. For Account Password and Confirm Account Password, enter the password of that delegation account.
  9. Select Finished.
Create a node for each and every participating KDC

In this procedure you create a node for each and every KDC that you want to use in the Kerberos SSO setup as follows:

ltm node /Common/10.0.0.1 {
    address 10.0.0.1
}
ltm node /Common/10.0.0.2 {
    address 10.0.0.2
}

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Nodes > Node List.
  3. Select Create.
  4. For Name, enter the name of the KDC you want to add. For example:

    10.0.0.1

  5. For Address, enter the IP address of the KDC you want to add. For example:

    10.0.0.1

  6. Select Finished.
  7. To add more KDC servers, repeat steps 3-6. In this example, add 10.0.0.2.

Create a pool to include the relevant KDC servers

In this procedure you create a pool in which you add each and every node representing the KDC servers to use in the Kerberos SSO setup as follows:

ltm pool /Common/P_kdc_servers_domain_com {
    members {
        /Common/10.0.0.1:0 {
            address 10.0.0.1
        }
        /Common/10.0.0.2:0 {
            address 10.0.0.2
        }
    }
}

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Pools > Pool List.
  3. Select Create.
  4. For Name, enter the name of the pool you want to add. For example:

    P_kdc_servers_domain_com

  5. Select an appropriate health monitor.
  6. For New Members, select Node List.
  7. For Address, select one of the nodes created in the previous procedure. For example:

    10.0.0.1

  8. For Service Port, select Select and select * All Services.
  9. Select Add.
  10. Add every node that needs to be added to the pool. In this example, repeat steps 7-9 for 10.0.0.2.
  11. Select Finished.

Create a TCP virtual server listening on port 88

In this procedure you create a Performance (Layer 4) TCP virtual server listening on the IP address used in the Kerberos SSO profile with the following example configuration:

ltm virtual /Common/vs_kerberos_sso_tcp_domain_com {
    destination /Common/192.168.1.1:88
    ip-protocol tcp
    mask 255.255.255.255
    pool /Common/P_kdc_servers_domain_com
    profiles {
        /Common/fastL4 { }
    }
    source 0.0.0.0/0
    source-address-translation {
        type automap
    }
    translate-address enabled
    translate-port enabled
}

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Virtual Servers.
  3. Select Create.
  4. For Name, enter the name of the virtual server you want to add. For example:

    vs_kerberos_sso_tcp_domain_com

  5. For Type, select Performance (Layer 4).
  6. For Destination Address/Mask, enter the IP address of the fictitious KDC IP used in the Kerberos SSO profile for domain domain.com. For example:

    192.168.1.1

  7. For Service Port, enter 88.
  8. For Source Address Translation, select Auto Map.
  9. For Default Pool, select the pool that you created previously. For example:

    P_kdc_servers_domain_com

  10. Select Finished.

  4. For Name, enter the name of the virtual server you want to add. For example:

    vs_kerberos_sso_udp_domain_com

  5. For Type, select Performance (Layer 4).
  6. For Destination Address/Mask, enter the IP address of the fictitious KDC IP used in the Kerberos SSO profile for domain DOMAIN.COM For example:

Multiple-domain scenario

In a multiple-domain scenario, unauthenticated users are coming from two different domains, domain.com and otherdomain.com, which are handled by the same realm. Each of these domains are handled by different domain controllers:

  • domain.com
    • dc1.domain.com: 10.0.0.1
    • dc2.domain.com: 10.0.0.2
  • otherdomain.com
    • dc1.otherdomain.com: 10.10.10.1
    • dc2.otherdomain.com: 10.10.10.2

This scenario is similar to the previous one in terms of configuration. The main difference is that there is one fictitious IP per referenced domain. Also these fictitious IPs are referenced under /etc/krb5.conf instead of the Kerberos SSO profile.

Create a Kerberos SSO profile

In this procedure, you create the following Kerberos SSO profile:

apm sso kerberos /Common/SSO_KERBEROS {
    account-name host/account.domain.com
    account-password xxxxxxxxxxKdtZAuvsGQZwCVKdwxb/5DmFDAjiyyyyyyy
    realm DOMAIN.COM
}

For this profile, the only difference from the usual configuration is that no KDCs is mentioned. This makes BIG-IP APM system look at the /etc/krb5.conf file to search for KDCs.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Access > Single Sign-On > Kerberos.
  3. Select Create.
  4. For Name, enter the name of the SSO profile. For example:

    SSO_KERBEROS

  5. For Kerberos Realm, enter the name of the Kerberos realm. For example:

    DOMAIN.COM

  6. For Account Name, enter the name of the delegation account created on your Active Directory. For example:

    host/account.domain.com

  7. For Account Password and Confirm Account Password, enter the password of that delegation account.
  8. Select Finished.

Configure /etc/krb5.conf

For this procedure, the goal is to reference a fictitious IP address for each and every domain participating in the Kerberos SSO environment. You configure the /etc/krb5.conf file as follows:

[libdefaults]
 
 default_realm = EXAMPLE.COM
#F5mod
 dns_lookup_realm = true
 dns_lookup_kdc = true
 udp_preference_limit = 1
 ticket_lifetime = 24h
 renew_lifetime = 7d
 forwardable = true
 
[realms]
 DOMAIN.COM = {
   kdc = 192.168.1.1
 }
 OTHERDOMAIN.COM = {
   kdc = 192.168.1.2
 }
 
[domain_realm]
[...]

Impact of procedure: Incorrectly editing the krb5.conf file may prevent the Kerberos daemon from loading and cause the Kerberos authentication to fail. This change does not synchronize across clusters.

  1. Log in to the BIG-IP command line interface.
  2. Create a backup of the /etc/krb5.conf file by entering the following command:

    cp /etc/krb5.conf /etc/krb5.conf.multi

  3. Using the vi text editor, open the /etc/krb5.conf file by entering the following command:

    vi /etc/krb5.conf

  4. Under the [realms] section, all participating domains must be defined. For each domain, the kdc entry must point to a virtual server IP address that are responsible for load-balancing the Kerberos requests to the KDC servers serving a given domain. The following example shows a working configuration to use both domain.com and otherdomain.com. In your example, you add 192.168.1.1 in the kdc entry for domain.com and 192.168.1.2 in the kdc entry for otherdomain.com. These two IP addresses represent the virtual server IP addresses for each domain that are created in the subsequent procedures:

    [realms]
     DOMAIN.COM= {
      kdc = 192.168.1.1
     }

     OTHERDOMAIN.COM= {
      kdc = 192.168.1.2
     }
  5. Save the file and exit vi

Additional configuration considerations

Using the mentioned configuration with load-balancing mechanism will help deal with Kerberos SSO deployed in a large environment.

In addition, consider the following additional configuration changes that will help achieve better performances:

  • Use a shared SPN instead of a different SPN per web server (that keeps the size of the Kerberos cache smaller).
  • Define the SPN value in the Kerberos SSO profile to prevent DNS lookups (which happen when SPN is empty), or configure the BIG-IP system hosts file to provide the SPN value for each and every web server IP address.
  • Consider that Kerberos UDP traffic can be totally removed by disabling the Kerberos UDP virtual servers (vs_kerberos_sso_udp_domain_com and _kerberos_sso_udp_anotherdomain_com).
