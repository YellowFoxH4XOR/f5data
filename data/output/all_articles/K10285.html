Known Issue

This is the result of a known issue. When a BIG-IP virtual server is configured with an NTLM profile, the BIG-IP system sets the NTLM connection pool cookie (NTLMconnpool) without specifying a domain attribute for the cookie.

Different browsers may respond differently when managing a cookie that does not include a domain attribute. As a result, cookie-dependent BIG-IP WebAccelerator features, such as MultiConnect, may not function as expected with some browsers.

For example, Microsoft Internet Explorer will send a domainless cookie in future requests for the originally requested host and any of its subdomains. Requests for multiconnected URLs will include the cookie. However, Firefox will send a domainless cookie only in future requests for the originally requested host, not for its subdomains. As a result, Firefox requests for multiconnected URLs will not include the expected cookie, and the MultiConnect feature will fail.

F5 Product Development tracked this issue as CR122236 and it was fixed in BIG-IP version 10.1.0. For information about upgrading, refer to the BIG-IP LTM or WebAccelerator Release Notes.

Additionally, this issue was fixed in BIGIP-10.0.1-378.0-HF3 issued for BIG-IP version 10.0.1. You may download this hotfix or later versions of the cumulative hotfix from the F5 Networks Downloads site.

Workaround

You can work around this issue by using an iRule that appears similar to the following example to add a domain to the NTLMconnpool cookie:

when HTTP_RESPONSE {
if { [HTTP::cookie exists NTLMconnpool] } {
HTTP::cookie domain NTLMconnpool "www.domain.com"
}
}

Note: For more information about HTTP cookies, refer to RFC2965 - HTTP State Management Mechanism.

Note: For information about a related issue regarding the pv_ntlm_auth cookie used in BIG-IP WebAccelerator version 9.4.x, refer to K10316: The pv_ntlm_auth cookie does not include a domain attribute.
