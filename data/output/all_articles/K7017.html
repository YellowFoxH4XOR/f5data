Known Issue

The BIG-IP ntpd process is unable to communicate with the network time protocol (NTP) server.

This issue occurs when all of the following conditions are met:

  • The BIG-IP system is configured to use an NTP server.
  • The ntpd process restarts, or if the system starts the ntpd process before initializing, the interface through which the system reaches the NTP server.

Depending on the BIG-IP system's network and routing configuration, the system may reach the NTP server through the management interface or through a Traffic Management Microkernel (TMM) Virtual Local Area Network (VLAN). Since the system starts the ntpd process before initializing the TMM interfaces and routing, the ntpd process may fail to communicate with the NTP server in the following two situations:

  • The ntpd process fails to communicate with the NTP server on system startup
  • The ntpd process communicates with the NTP server on system startup, but communications fail if the ntpd process restarts
Note: You can use the ntpq utility to query the NTP server and print a summary of the NTP server's state. For more information, refer to K10240: Verifying NTP peer server communications.
Note: This issue may also adversely affect other management traffic. For more information, refer to K10239: Traffic originating from management processes may not use the intended management address or management routes.

Impact

The BIG-IP system clock will drift and may become out of sync with an HA peer (10.x) or device group peers (11.x). Time critical features may encounter issues.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • BIG-IP iHealth lists Heuristic H380440 on the Diagnostics > Identified > Medium screen.
  • The BIG-IP system reports an incorrect system time.
  • When this issue occurs, the ntpd process logs an error message to the /var/log/daemon.log file.

    For example:

    err ntpd[<pid>]: sendto(<NTP server IP address>) (fd=16): Network is unreachable

The ntpd process fails to communicate with the NTP server on system startup

The ntpd process fails to reach the NTP server on system startup in network configurations where you have configured the management network with a default gateway, and the NTP server is reachable only through a TMM network (either directly or using a TMM route or default gateway). When the BIG-IP system starts, the ntpd process starts before the system loads the TMM network configuration, and the ntpd process attempts to use the management network to reach the NTP server. However, the attempt fails because the NTP server is on the TMM network.

Workaround

You can work around this issue by manually restarting the ntpd process. To do so, type the following command:

Impact of workaround: System clock synchronization will be unavailable while the ntpd process restarts.

  1. Log in to the BIG-IP command line.
  2. Manually restart the ntpd process by typing the following command:

    bigstart restart ntpd

Alternatively, you can automate the restart of the ntpd process by performing the following procedure:

Impact of workaround: System clock synchronization will be unavailable while the ntpd process restarts.

  1. Log in to the BIG-IP command line.
  2. Back up the /config/user_alert.conf file by typing the following command:

    cp /config/user_alert.conf /config/user_alert.conf.SOL7017

  3. Using a text editor, open the /config/user_alert.conf file for editing.
  4. Add the following lines to the end of the file:

    alert ntpd_startup_delay "Initialization complete.  The MCP is up and running" {
    exec command="sleep 15";
    exec command="/usr/bin/bigstart restart ntpd";
    }

  5. Save the file and close the editor.

The ntpd process communicates with the NTP server on system startup, but communications fail if the ntpd process restarts

The ntpd process can reach the NTP server on system startup in network configurations where the NTP server is reachable through only a route or default gateway on the management interface. The ntpd process uses the management route or default gateway before TMM starts. However, if the system subsequently restarts the ntpd process after starting the TMM process, the operation fails because the ntpd process attempts to use the available TMM network default gateway and is unable to reach the NTP server.

Workaround

The ntpd process can communicate with the NTP server by way of the management interface at startup and upon subsequent restarts of the ntpd process under either of the following circumstances:

  • The NTP server is located directly on the management subnet, and the system does not require routing for communications.
  • The NTP server is routable by way of the management subnet, and you have configured a non-default static route toward the NTP server.

The ntpd process can communicate with the NTP server by way of a TMM interface at startup and upon subsequent restarts of the ntpd process under either of the following circumstances:

  • The management interface has not been assigned an address, and the system can reach the NTP server through a TMM network, either directly or using a TMM route.
  • The management network has not been assigned a default gateway, no static management routes exist that match the NTP server's address, and the NTP server is reachable through a TMM network, either directly or using a TMM route.

Important: Non-default static routes created on the management network will create a GATEWAY entry in the /etc/sysconfig/network file. If you must remove a GATEWAY entry on BIG-IP 9.0.0 through 9.2.5, and 9.4.0 through 9.4.1, you must remove it manually. For information, refer to K7814: Non-default static routes on the management network create a GATEWAY entry.

Note: For more information about configuring and troubleshooting routing entries for use by management traffic, refer to K13284: Overview of management interface routing (11.x - 12.x) or K3669: Overview of management interface routing (9.x - 10.x).
