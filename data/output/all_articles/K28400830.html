K28400830: BIG-IQ - HA Alert - Scheduled sync of files failed: ssh: connect to host x.x.x.x port 22: Connection timed out rsync: connection unexpectedly closed

Type
Support Solution
Published
2019-12-17
Updated
2025-02-06
Applies to
  • BIG-IQ
Source
https://my.f5.com/manage/s/article/K28400830
Description

BIG-IQ ALERTS & NOTIFICATIONS page displays an HA Alert similar to the one below: 

Scheduled sync of files failed: ssh: connect to host X.X.X.X port 22: Connection timed out rsync: connection unexpectedly closed (0 bytes received so far) [sender] rsync error: unexplained error (code 255) at io.c(600) [sender=3.0.6]
  1. Log in to the primary BIG-IQ system, using administrator credentials.
  2. From the BIG-IQ main list, select Monitoring.
  3. On the BIG-IQ Systems panel, select ALERTS & NOTIFICATIONS.
Environment
  • Two BIG-IQ systems in a high availability (HA) configuration
  • BIG-IQ 5.4.0

Cause

A communication issue over TCP port 22 between the primary BIG-IQ and secondary peer due to some network firewall restriction, peer being unavailable (down), etc..

Recommended Actions

On the primary BIG-IQ, make note of the timestamp for the last HA Alert generated and select to delete the alert if deemed an old alert.
  1. Log in to the primary BIG-IQ system, using administrator credentials.
  2. From the BIG-IQ main list, select Monitoring.
  3. On the BIG-IQ Systems panel, select ALERTS & MONITORING.
  4. Select the alert and force deletion.
On the primary BIG-IQ, force a manual file sync in order to verify current file sync status.
  1. Log in to the primary BIG-IQ system, using administrator credentials.
  2. From the BIG-IQ main list, select System.
  3. On the BIG-IQ Systems panel, select BIG-IQ HA.
  4. Select BIG-IQ HA Settings.
  5. Select Sync Files
Note: If an error similar to the one below is displayed then proceed with troubleshooting connectivity issues over TCP port 22 (ssh) between the BIG-IQ peer devices.
File synchronization already in progress is encountered when manually syncing files.

Verify TCP port 22 (ssh) connectivity between the peer BIG-IQ devices

You can use the ssh utility to verify TCP port 22 availability. To do so, perform the following procedure:
  1. Log in to the command line of the BIG-IQ systems.
  2. Use the following ssh command syntax, replacing <x.x.x.x> with the remote BIG-IQ system's Management IP address or internal self IP address:
    ssh <x.x.x.x>
    Optional: If a warning message appears, asking if you want to continue, select yes.
    For example:
    Are you sure you want to continue connecting (yes/no)? yes
  3. When you receive the Password prompt, provide the root user credentials.
  4. To verify the remote BIG-IQ system by host name, view the command prompt or run the following command:
    [root@remote1:Active:Standalone] config # tmsh list sys global <hostname>
    sys global-settings {
        <hostname> remote1.f5.com
    }

Test failures

If either TCP port tests fail, the following diagnostic data provided by the error message can help you understand the cause:
Connection refused error messages usually indicate a TCP port is being blocked, either in the network or on the remote BIG-IQ system.
No route to host error messages usually indicate a misconfigured route or a missing or mistyped IP address.

  • There are three categories of data for BIG-IQ: shared, copied, and device-specific.
    • The majority, by a large margin, is shared. Shared data is always replicated between the devices with very low latency (<100ms on average)
    • The copied data set is local users/user groups and more importantly UCS backups. The default schedule for copying these is 30 seconds (user configurable). We use rsync to perform the copy over TCP port 22 (ssh), which performs a delta-only copy.
    1. Log in to the primary BIG-IQ system, using administrator credentials.
    2. From the BIG-IQ main list, select System.
    3. On the BIG-IQ Systems panel, select BIG-IQ HA.
    4. Select BIG-IQ HA Settings.
    5. Adjust HA Sync Interval as seen fit.
    • The device-specific data are not copied. This includes any settings configured via TMSH (ie, MCP data), SNMP and SMTP configurations, IP configuration, etc.
