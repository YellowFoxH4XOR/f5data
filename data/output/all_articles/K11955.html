Known Issue

This is the result of a known issue. Each execution of a suspending iRule command erroneously increments the event count for the event in which the command is executed. As a result, invocation statistics for events and iRules containing suspending commands are inflated, and the Cycles calculation for each affected event is under-reported.

Note: For information about iRules commands that temporarily suspend iRule execution, refer to K12962: Some iRules commands may temporarily suspend iRule processing.

For example, the following iRule contains two after commands in the HTTP_REQUEST event:

when HTTP_REQUEST {
after 1 ...
...
after 1 ...
...
}
}

After two requests have traversed the iRule, the bigpipe rule show all command displays the following statistics:

+-> HTTP_REQUEST 6 total 0 fail 0 abort
| Cycles (min, avg, max) = (113, 4245, 4567898)

Although the iRule event was only invoked twice, the event counter for HTTP_REQUEST was erroneously incremented by 6: 2 for the actual event invocation, and 4 for the invocations of the after command. Since the Cycles value is derived by dividing the total cycles by the number of event invocations, the Cycles value is under-reported by a factor of 3.

F5 Product Development tracked this issue as ID 222913 (formerly CR125800) and it was fixed in BIG-IP version 11.0.0. For information about upgrading, refer to the BIG-IP LTM, ASM, GTM, PSM, Link Controller, WebAccelerator, APM, WOM, or Edge Gateway release notes.

Workaround

The statistics for events containing any suspending command should be ignored. However, you may be able to estimate statistics for an affected event by dividing the event counter by the number of times a suspending command is called within that event, plus 1. When event timing is enabled, the Cycles calculation which reports timing for each invocation of the event may be similarly estimated by multiplying the reported Cycles value by the number of times a suspending command is called within that event, plus 1.
