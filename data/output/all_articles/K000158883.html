K000158883: ASM Security Policy Stuck Buffering for Single User

Type
Support Solution
Published
2026-03-31
Updated
2026-03-31
Applies to
  • BIG-IP
  • BIG-IP ASM: 17.1.3
Source
https://my.f5.com/manage/s/article/K000158883

Description

A single LDAP-authenticated user may experience the BIG-IP ASM (Application Security Manager) GUI stuck indefinitely on "Applying policy" (buffering) when attempting to modify or update ASM security policies. Other users with similar permissions and group memberships are able to apply policies without issue. The problem persists across browsers, devices, and after clearing browser cache or restarting BIG-IP services. No relevant error messages appear in standard logs, but HAR captures may show failed requests related to policy tasks.

Environment

  • BIG-IP ASM (Application Security Manager), version 17.1.3
  • User authentication via external LDAP
  • Multiple users with similar group memberships and roles
  • Issue isolated to a single LDAP user account
  • No recent changes to affected user's LDAP profile, group membership, or password
  • Attempts to resolve by restarting restjavad, tomcat, httpd, and clearing /run/pamcache tokens were unsuccessful

Cause

Stale or orphaned ASM policy task objects associated with the affected LDAP user account cause the system to incorrectly consider the policy "locked" by that user. This results in the GUI being stuck on "Applying policy" and prevents further modifications.

Recommended Actions

  1. Backup device configuration:
    tmsh save sys ucs "$HOSTNAME"_$(date +%y%m%d-%H%M%S)
  2. Delete stale ASM task objects for the affected user:
    Run the following commands (replace <username>, <password>, and <task_object_url> as appropriate):
    curl -k -S -u '<username>:<password>' -XDELETE <task_object_url>
    Repeat for each relevant task object URL.
  3. Restart httpd process:
    bigstart restart httpd
  4. Verify resolution:
    Have the affected user attempt to modify/apply ASM policies again.
  5. If issue persists:
    Collect a new asmqkview and relevant database dumps for further analysis:
    nice -n 19 asmqkview -s0 -f "$HOSTNAME"_$(date +%y%m%d-%H%M%S).qkview
    Use mysqldump commands for relevant ASM databases if requested by support.

Additional Information

  • Creating a new LDAP user for the affected individual allows normal policy modification, confirming the issue is tied specifically to the original LDAP user object.
  • The issue is not resolved by changing group membership, role assignment, or restarting BIG-IP services.
  • The problem is specific to ASM policy operations; other modules such as LTM or DoS/BOT remain unaffected for this user.
