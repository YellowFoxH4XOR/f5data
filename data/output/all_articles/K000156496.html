K000156496: Unable to see cause of Server Side Code Injection, SQL-Injection, Cross Site Scripting (XSS) or other Security Event Log

Published
2025-09-17

Applies to
  • BIG-IP
  • BIG-IP ASM: 17.0.0, 17.1.0, 17.0.X, 17.X.X, 17.5.X, 17.5.1, 17.5.0, 17.1.X, 17.1.2, 17.1.1
Source

Description

Access to application URLs is denied by BIG-IP Application Security Manager (ASM) due to detection of attack signatures for Server Side Code Injection, SQL Injection (e.g., "if(Expression,value,value)", "' and 1 --"), and Cross Site Scripting (XSS). Event logs indicate violations, but actual triggering parameter values are masked when data masking is enabled in the ASM security policy.

Environment

  • Product: BIG-IP Application Security Manager (ASM)
  • Configuration:
    • ASM security policy with attack signature detection enabled
    • Blocking and alarm settings active for detected threats
    • Data masking enabled in the security policy, which obscures actual triggering values in event logs

Cause

Attack signatures such as SQL Injection, Server Side Code Injection, or XSS (among others) are triggered by patterns found in HTTP POST parameters. When data masking is enabled, the specific parameter values causing the violation are hidden in logs, making root cause analysis difficult.

Recommended Actions

  • Disable data masking within the ASM policy to reveal actual parameter values that trigger attack signatures.
  • Reproduce violations in a lower environment (QA/Dev) where it is safe to analyze triggering data.
  • If lower environment testing is not feasible, consider targeted testing in production using a restrictive virtual server and a separate ASM policy with data masking disabled.
  • Review and tune attack signature settings to minimize false positives for known safe parameters.
  • Use learning mode or create exceptions for legitimate traffic that matches certain attack patterns.

Additional Information

  • By default, ASM blocking pages return HTTP 200 OK responses; if necessary to use a different response code (e.g., 403 Forbidden), configure a custom blocking page (for instance to alert monitoring tools that the application is getting blocks) under Security → Application Security : Security Policies : Policy Enforcement → Response and Blocking Pages.
  • Use asmqkview --add-request-log to collect detailed event logs for troubleshooting.
  • If necessary, open a case with F5 Support and provide the relevant event logs and qkview files to F5 support or iHealth for further analysis.
