Description

This is intended to clarify a commonly misunderstood mechanism: it may appear that the forced password-change conversation ("You are required to change your password immediately," followed by current/new/confirm prompts) requires a special SSH protocol extension unique to password authentication

How F5OS-A communicates a forced password change (for example, triggered by last-change being reset to 0, or first login after an administrator uses set-password) to an SSH client when the device is configured to allow plaintext password authentication (PasswordAuthentication yes).

Environment

F5OS-A (rSeries)
SSH access as root or any local user
PasswordAuthentication 'yes' configured in '/etc/ssh/sshd_config'
Password change forced via GUI-initiated password change, CLI set-password, or last-change field reset to 0

Cause

    • This is expected/by-design SSH and PAM behavior. 

      Forced password-change prompts appearing after a shell session is already established (PAM-driven, occurs when password auth is enabled).
      Forced password-change prompts appearing during SSH authentication itself, before any shell exists (SSH-protocol-driven via keyboard-interactive, occurs when password auth is disabled).

    • When troubleshooting a forced password-change scenario, check whether the prompts appear before or after the SSH session establishes a shell/PTY (visible in ssh -vvv output via the presence of pty-req and shell request accepted messages) to determine which mechanism is in play.

    Answer/Recommended Actions

      ​​Behavior When Only 'PasswordAuthentication' Is Available:

     

    • The client authenticates using the password method. Authentication completes successfully at the SSH protocol layer — the server issues SSH_MSG_USERAUTH_SUCCESS even though the account has a forced password change pending. The SSH authentication layer has no visibility into account-aging state; it only validates the submitted password.
    • The client then requests a pseudo-terminal (PTY) and shell, which the server confirms.
    • Once the interactive shell session is open, the PAM (Pluggable Authentication Modules) account-management phase takes over — this is a Linux-level mechanism, separate from SSH itself. PAM detects that the account's last-change value forces an immediate password change and invokes the standard Linux password-change conversation:
      You are required to change your password immediately (root enforced)
      Changing password for root.
      (current) UNIX password:
         New 
         Retype new 
    • Because this conversation happens inside an already-open interactive terminal session (not during SSH authentication), it behaves exactly like manually running the passwd command at a shell prompt. Each character typed is transmitted immediately to F5OS-A and echoed back individually — this is standard interactive PTY behavior, not a special protocol feature tied to password authentication.
    • Key clarification: No special SSH authentication protocol extension is involved in this flow on F5OS-A. The forced password change is entirely a post-authentication, shell-level PAM interaction — it happens after SSH login succeeds, not as part of the SSH login exchange itself.

    Behavior When Only keyboard-interactive Is Available:

     

    • On F5OS-A versions/configurations where PasswordAuthentication no is set (see K000149804 for when this applies), password is not offered by the server at all. In that case, the forced password-change conversation must occur during SSH authentication itself, using keyboard-interactive's native SSH_MSG_USERAUTH_INFO_REQUEST / SSH_MSG_USERAUTH_INFO_RESPONSE exchange — because no shell/PTY session can exist yet at that stage, and keyboard-interactive is the only method capable of carrying a multi-step, server-driven conversation before authentication completes.

    Depending on the sshd_config state of a given F5OS-A system:

    With password enabled: the forced password change is a post-authentication, PAM-driven shell interaction.
    With only keyboard-interactive available: the forced password change is a pre-authentication, SSH-protocol-driven interaction.

    Both methods accomplish the same end result — the user is required to set a new password before proceeding — but the underlying mechanism and protocol layer involved are fundamentally different.
