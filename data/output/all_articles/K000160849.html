Description

F5 Distributed Cloud Services (F5 XC) can both integrate with existing Kubernetes (K8s) clusters and host K8s workloads directly. Multiple architecture options exist within these capabilities, and selecting the appropriate architecture depends on whether the goal is to integrate with an existing K8s platform, run CE software inside a K8s cluster, consume a managed Namespace, or deploy a fully managed K8s cluster at a customer site.

  • What Kubernetes architecture options are available with F5 Distributed Cloud Services?
  • What is the difference between F5 XC integrating with an existing K8s cluster versus hosting K8s workloads itself?
  • When should the Secure K8s Gateway (External Load Balancer) architecture be used?
  • When should the K8s Site (CE as a pod) architecture be used?
  • What is vK8s (virtual Kubernetes) and when is it appropriate?
  • What is mK8s (managed Kubernetes) and how does it differ from vK8s?
  • What are the restrictions and traffic management capabilities for each architecture?

Environment

  • F5 Distributed Cloud Services (F5 XC)
  • One or more of the following deployment scenarios:
    • Existing Kubernetes cluster (any distribution) — Architectures 1 and 2
    • F5 Distributed Cloud Regional Edge (RE) PoPs — Architectures 3 and 4
    • Customer Edge (CE) nodes on hypervisor, hyperscaler, or baremetal — Architectures 1, 2, 3, and 4
    • CE deployed as a Kubernetes pod within an existing cluster — Architecture 2
  • F5 XC Mesh functionality (required for all four architectures)
  • F5 XC AppStack functionality (required for Architectures 3 and 4)

Answer/Recommended Actions

F5 Distributed Cloud supports four Kubernetes architecture options, presented below in ascending order of sophistication. The first two architectures integrate with existing K8s platforms and require only Mesh functionality. The last two require AppStack functionality and position F5 XC as the K8s platform itself.

Architecture 1: External Load Balancer (Secure K8s Gateway)

In a Secure Kubernetes Gateway architecture, F5 XC integrates with an existing K8s cluster by acting as the external load balancer. The XC node performs service discovery against the K8s API server using a ServiceAccount and kubeconfig file.

  • When to use: When you have an existing K8s platform and want to expose its services to your local network, remote sites, or the internet without modifying the cluster itself.
  • Supported service types: NodePort and ClusterIP services.
  • Key characteristics:
    • F5 XC is not hosting any workloads — it is acting purely as a load balancer and security proxy in front of the existing cluster.
    • Origin pools can reference NodePort services discovered via K8s service discovery.
    • Provides application delivery and security services (WAF, bot defense, etc.) in front of K8s services.
  • F5 XC functionality required: Mesh only.

Architecture 2: CE as a Pod (K8s Site Type)

A K8s site is created by deploying a single manifest into an existing K8s cluster. This manifest deploys a group of pods and related resources that together provide CE functionality and register as a customer site in F5 XC.

  • When to use: When you want F5 XC to run inside your existing K8s cluster to expose services by DNS name (including ClusterIP services), or when you want F5 XC to act as an ingress controller with built-in application security for the cluster.
  • Deployment: Apply the manifest available at https://gitlab.com/volterra.io/volterra-ce/-/blob/master/k8s/ce_k8s.yml to the target cluster.
  • Supported service types: NodePort and ClusterIP services. Because the site runs inside the cluster, services can be resolved by DNS name from within the cluster.
  • Key characteristics:
    • Supports Mesh functionality only. AppStack functionality is not supported (a cluster cannot run within a cluster).
    • Enables Mesh features such as publishing this site's discovered services to other sites, and consuming other sites' published services on this site.
  • F5 XC functionality required: Mesh only.

Architecture 3: vK8s (Virtual Kubernetes — Namespace-as-a-Service)

In a virtual Kubernetes (vK8s) architecture, F5 XC is the K8s platform. Creating a vK8s object in F5 XC provides a single managed Namespace within a virtual cluster. This is not integration with an existing K8s platform — XC hosts and manages the K8s workload.

  • When to use: When you want to deploy workloads to remote regions where you have no infrastructure and prefer to run in F5 RE PoPs, or when you want to manage disparate workloads across multiple sites via a single centralized virtual cluster interface.
  • Deployment options: The managed Namespace can run on F5 RE PoPs, on customer CE nodes, or a combination of both.
  • Access: A kubeconfig file is provided for access to the Namespace via a hosted API server. Standard kubectl CLI or the F5 XC web console can be used to create, delete, and manage K8s resources (Deployments, Services, Secrets, ServiceAccounts, etc.) and view resource metrics.
  • Restrictions: Because vK8s provides a managed Namespace (not a full cluster), the following restrictions apply:
    • Containers cannot run as root or bind to privileged ports or the host network.
    • CRDs, ClusterRoles, PodSecurityPolicies, and Namespaces cannot be created.
    • Kubernetes Operators are not supported.
  • F5 XC functionality required: AppStack + Mesh.

Architecture 4: mK8s (Managed Kubernetes)

In a managed Kubernetes (mK8s) architecture (also referred to as physical K8s or pK8s), F5 XC deploys, manages, and upgrades a full enterprise-grade K8s cluster at the customer's site. The customer manages K8s resources; F5 XC manages the K8s infrastructure.

  • When to use: When you need a full K8s cluster (not just a Namespace) at your site, with enterprise-level traffic controls, native security policy enforcement, and centralized multi-cluster management across a large number of sites.
  • Key capabilities:
    • Multi-cloud automation support for AWS, Azure, and GCP environments.
    • Consumed as SaaS — no discrete installation managed by the customer.
    • A large and arbitrary number of managed clusters can be logically grouped into a Virtual Site with a single K8s management interface.
    • kubectl access can be enabled against the local cluster with the option to disable the hosted API server, allowing the kubeconfig to point to a local on-premises endpoint.
  • Differences from vK8s: mK8s provides a full K8s cluster at the customer site, not just a managed Namespace. The restrictions that apply to vK8s do not apply to mK8s — privileged pods, Operators with ClusterRoles and CRDs, and other cluster-wide operations are supported.
  • Native traffic management controls available with mK8s:
    • Service isolation: Pods in a given namespace cannot communicate with services outside that namespace by default.
    • Service-to-service controls: Granular policies can define which services are permitted to communicate with each other.
    • Egress control: Outbound traffic from the cluster can be natively enforced by namespace, labels, IP ranges, or other methods (e.g., Service A can reach myapi.example.com but no other internet service).
    • Inline security policies: WAF, bot defense, L3/L4 policies, and other security services can be applied natively within the platform.
  • F5 XC functionality required: AppStack + Mesh.

Additional Information

F5 Distributed Cloud's global platform consists of Regional Edges (REs) — globally distributed PoPs that form the backbone of the platform — and Customer Edges (CEs) — compute nodes deployed in the customer's network that register to the F5 XC global control plane and are managed as SaaS. CEs can run on hypervisors (VMware, KVM), hyperscalers (AWS, Azure, GCP), baremetal, or as K8s pods.

Two core F5 XC service capabilities are relevant to K8s architecture selection:

  • Mesh: Provides connectivity between sites, security services, and observability. Required for all four architectures.
  • AppStack: Provides managed K8s compute capabilities, allowing a large and arbitrary number of clusters to be logically grouped into a Virtual Site with a single K8s management interface. Required for Architectures 3 and 4 only.

Service-to-service communication between K8s clusters and other F5 XC sites is supported across all four architectures. Each site can publish K8s services to other sites, making any K8s service reachable from other sites as configured. More granular service-to-service controls are available in the more sophisticated architectures (particularly mK8s).

As K8s adoption continues to grow and deployment patterns evolve, the flexibility of F5 XC's architecture options allows organizations to choose an integration model that matches their current environment while providing a path toward more sophisticated managed K8s capabilities as needs mature.
