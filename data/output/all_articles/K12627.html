Known Issue

This is the result of a known issue. If the VLAN or netmask of a self IP is modified, TMM will no longer use any routes that depend on that self IP. However, the routes will still appear in the routing table (displayed by the bigpipe route show command).

For example:

  • A BIG-IP system is configured with four VLANs: vlan1, vlan2, vlan3, and vlan4.
  • A self IP is assigned to vlan1, vlan2, and vlan3.
  • A default route is added that will go out vlan1.
  • A more specific route is added that will go out vlan2.
  • A wildcard forwarding virtual server is created.
  • If at this stage traffic ingresses the BIG-IP system through vlan3, and the traffic is meant to be forwarded by the virtual server via the more specific route, the traffic will egress the BIG-IP system the right way. However, if the self IP of vlan2 is now moved to vlan4, or if the netmask of the self IP is modified, the traffic described in the previous step will begin egressing the BIG-IP system the wrong way (via the default route). Effectively, the BIG-IP system will now behave as if the more specific route did not exist.

F5 Product Development tracked this issue as ID 249179 and ID 214277 (formerly CR101765), and it was fixed in BIG-IP version 10.0.0. For information about upgrading, refer to the BIG-IP LTM, ASM, PSM, GTM, Link Controller, or WebAccelerator release notes.

Workaround

You can work around this issue by restarting TMM, after which the affected route(s) will resume working as intended. To do so, run the bigstart restart tmm command from the command line.

Important: Restarting TMM will temporarily interrupt traffic processing. Additionally, if the BIG-IP system is the active member of a redundant pair, the system will failover.
