K36107562: Unable to generate a TTA due to an illegal peer name

Type
Support Solution
Published
2022-05-09
Updated
2024-10-01
Applies to
  • Traffix SDC: 5.2.X, 5.2.0, 5.1.X, 5.1.0
Source
https://my.f5.com/manage/s/article/K36107562

Description

  • The debug logs shows "No space left on device" as the reason why TTA was not completed.
  • Multiple lines in the last parts of the TTA debug shows "No space left on device".
mkdir: cannot create directory `tta-ng_5.1_<date>_<node>/os': No space left on device
gzip: stdout: No space left on device

Environment

  • SDC 5.x 
  • TTA

Cause

While the TTA script was working and collecting data on a folder where the peer configs are, using find_latest_version function of the script, it is not able to handle specific patterns used by a peer name and it resulting in the find path change as shown below. The repercussion is the effect of find command returning an unexpected large and long list of extra files to tar.

Note : This is an example and can be found in the TTA debug logs, the sample peer name here starts with "z." and it cannot be handled by the TTA.

290820-+ for file in '$(find "$DATA_BACKUP_DIR" -name "latestVersion.xml")'
290821-++ grep fileName z. <--- #Looking for the peer that starts with "z."
290822-++ awk '-F>' '{print $2}'
290823-++ awk '-F<' '{print $1}'
290824:grep: z.: No such file or directory <--- #Cannot find the peer
290825-+ local version=
290826-++ dirname b.
290827-+ local directory=./ <--- #Path change
290828-++ find ./ -type f <--- #Script is now finding in the wrong path
290829-+ for file2 in '$(find $directory -type f)'

Since the find_latest_versions function of the script cannot handle the peer name "z." it reverts to "./" instead of the recent peerconfig file, it will find and add a bunch of unexpected and unrequired files from "./" to the TTA directory by the use of the add_file function. The effect is a very large TTA file, with files that is actually not required or part of the TTA. This TTA file will then be TAR-ed which also requires at least an additional 50% (of the current TTA size) extra space for it to complete. This means /var/log/rsyslog should have an available space that is at least 150%-200% the size of the TTA file when its being collected. Hence, if the available space of /var/log/rsyslog is still considerably large compared to the size of the collected TTA (with the illegal peer name causing the TTA to bloat) the TTA collection would still work. However, if the available space of /var/log/rsyslog is low compared to the size of the collected TTA then the TTA will fail with debug logs showing "No space left on device".

Recommended Actions

The illegal peer name should be deleted or updated to a valid one. 

If peer (with illegal name) is IN USE :

  1. Login to GUI of the SDC site and check if a peer (with illegal name) is present. If there is one, proceed to create another peer with the same configuration as the peer (with illegal name) but with a different name and then add it to the same pool as the peer (with illegal name).
  2. After the new peer is added and available, you can DELETE peer (with illegal name) from the POOL and then from the PEER list.
  3. Log in to the SDC nodes and backup the folder (illegal peer name) by copying it to another directory or system.
  4. After peer (with illegal name) is deleted from the /data/backup/sitename/node_configmgr/peerConfigurations directory, perform another TTA collection.

If peer (with illegal name) is NOT IN USE :

  1. Login to GUI of the SDC site and check if a peer (with illegal name) is present.
  2. If the peer is present in the SDC system GUI, you can DELETE the peer (with illegal name) from the POOL and then from the PEER list.
  3. Log in to the SDC nodes and DELETE the peerConfigurations folder for the peer (with illegal name). No need to backup the folder (illegal peer name) if its not in use.
  4. After peer (with illegal name) is deleted from the /data/backup/sitename/node_configmgr/peerConfigurations directory, perform another TTA collection.
