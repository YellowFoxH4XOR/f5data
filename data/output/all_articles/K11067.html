Known Issue

This is the result of a known issue. The BIG-IP WebAccelerator generates incorrect 304 responses when multiple servers within a pool do not synchronize their Etags.

This issue occurs when the BIG-IP WebAccelerator is configured to load balance to multiple pool members that contain the same content or object, but each pool member generates different Etags. When the content with the LTM RAM Cache expires, the LTM sends an internal conditional request to the WebAccelerator module. If the WebAccelerator's cached copy is also expired, the WebAccelerator sends the request to one of the pool members in its configured pool. If the pool member returns the requested content with a different Etag, the WebAccelerator incorrectly changes the 200 OK response into a 304 Not Modified and disables the LTM RAM Cache for the requested object. The BIG-IP WebAccelerator then incorrectly delivers the 304 response directly to the client, regardless of whether the client previously cached the content. If the client has no local copy then no content is displayed.

This behavior can result in reduced performance for the LTM RAM Cache; this behavior may allow content to bypass the cache.

F5 Product Development tracked this issue as CR129513 and it was fixed in BIG-IP WebAccelerator version 10.1.0. For information about upgrading, refer to the BIG-IP WebAccelerator release notes.

In addition, this issue was fixed in BIGIP-10.0.1-378.0-HF3, which has been issued for BIG-IP WebAccelerator version 10.0.1. You may download this hotfix or later versions of the cumulative hotfix from the F5 Downloads site.
