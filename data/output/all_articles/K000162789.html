K000162789: NGINX App Protect WAF Resource Threshold Semantics on High-RAM and High-Core Linux Hosts

Type
Support Solution
Published
2026-08-05
Updated
2026-08-05
Applies to
  • NGINX Products
  • F5 WAF for NGINX
Source
https://my.f5.com/manage/s/article/K000162789

Description

In standalone NGINX App Protect WAF deployments, physical_memory_utilization can report a high value on an idle Linux host with low actual memory usage. A waf_resource_exception event may then place the enforcer into failure mode:

APP_PROTECT {

"event": "waf_resource_exception",

"mode": "failure",

"mode_changed": true,

"resource": "physical_memory_utilization",

"value": 94,

"threshold": 90

}

The physical-memory and CPU metrics have different semantics.

Environment

  • Standalone NGINX App Protect WAF deployment
  • NGINX Plus on a high-core, high-memory Linux host
  • RHEL 9-family operating system
  • Example configuration:

    app_protect_cpu_thresholds high=90 low=80;

    app_protect_physical_memory_util_thresholds high=90 low=80;

    app_protect_failure_mode_action drop;

    app_protect_request_buffer_overflow_action drop;

  • Actual host memory consumption may remain low while physical_memory_utilization reports a value above 90.
  • The CPU metric is calculated across all host CPUs rather than per core or per worker.

Cause

The physical_memory_utilization metric has inverted practical semantics in the affected implementation. The NGINX module obtains system memory information and reports free RAM. Therefore:

  • A high value indicates a large amount of free RAM.
  • A low value indicates less free RAM.
  • The metric does not represent enforcer RSS, the total_umu_max_size pool, or actual memory pressure.
  • The calculation does not use CPU core count or enforcer thread count.
  • Changing total_umu_max_size does not materially change this reading.

An idle host with substantial free memory can therefore exceed the configured high threshold and enter failure mode. The apparent correlation with core count is not part of the metric calculation.

The CPU metric has normal polarity: a higher value indicates higher aggregate CPU busy time.

Recommended Actions

  • Configure the physical-memory threshold
    1. Measure the steady-state physical_memory_utilization value under representative operating conditions.
    2. If the check is retained, set the high threshold above the normal steady-state value and the low threshold below the high threshold. For example:

      app_protect_physical_memory_util_thresholds high=98 low=95;

    3. If free-RAM monitoring is not useful, disable the check by setting both thresholds to 100:

      app_protect_physical_memory_util_thresholds high=100 low=100;

    4. Do not increase total_umu_max_size to change physical_memory_utilization. This parameter controls the enforcer’s UMU allocation budget, not this metric.
  • Configure the CPU threshold

    Use the aggregate CPU threshold as a coarse protection mechanism for sustained host-wide CPU saturation:

    app_protect_cpu_thresholds high=90 low=80;

    The CPU value is calculated from aggregate /proc/stat deltas:

    in_use = delta_user + delta_nice + delta_sys + delta_iowait

    total = in_use + delta_idle

    sample = 100 * in_use / total

    The reported value is averaged over the 10 most recent samples. Short CPU spikes may not trigger a waf_resource_exception.

    A single busy core contributes only a small percentage of aggregate CPU on a high-core host. Validate CPU threshold behavior with sustained load distributed across all cores when required.

  • Use operating-system resource controls

    For actual resource protection, supplement the NGINX App Protect WAF thresholds with:

    • MemoryMax= or MemoryHigh= on the NGINX systemd unit, or an equivalent container cgroup limit.
    • CPUQuota= on the NGINX systemd unit, or an equivalent container CPU limit.
    • Monitoring for kernel out-of-memory and OOM-kill events.
    • Monitoring of memory and CPU Pressure Stall Information (PSI).
    • NGINX request and connection limiting.
    • Appropriate worker sizing and CPU affinity.
    • Per-worker capacity planning, because aggregate CPU measurement may not detect single-core hotspots.

Additional Information

  • The resource state machine enters failure mode when the reported value exceeds high and returns to normal mode when it falls below low.
  • Because the physical-memory value represents free RAM, an idle high-memory host may remain above the high threshold and stay in failure mode until the value falls below the low threshold.
  • A high physical_memory_utilization value does not by itself indicate memory exhaustion.
  • The NGINX App Protect WAF CPU metric reports aggregate busy CPU time and is intended as a broad safety net for sustained saturation.
  • tmm_count and total_umu_max_size should not be tuned to correct the physical-memory metric. total_umu_max_size remains relevant for limiting enforcer UMU allocations.
