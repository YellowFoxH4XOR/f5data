Description

iControl REST Fine-Grained Role Based Access Control (RBAC) is covered in the following devcentral article. However, that devcentral article does not cover the case for remotely authenticated users on BIG-IP. This article describes the procedure how to configure the iControl REST RBAC for remotely authenticated users. In this article remotely authenticated users on BIG-IP are using Active Directory as a backend. However, the same procedure can be used for other remote authentication backends such as Radius.

Environment

Remote authentication for administrative users is configured on BIG-IP (such as Active Directory, Radius, etc.).

Cause

None

Recommended actions

You need to have an administrative privilege on BIG-IP to perform the following configuration steps.

  1. Remote authentication for administrative users is configured in the following way on BIG-IP: 

    For LDAP/AD users 

    # cat /config/bigip.conf

    auth ldap system-auth {
        bind-dn cn=administrator,cn=Users,dc=eslab,dc=local
        bind-pw $M$jj$5i5zQKaRaA8sE
        login-attribute sAMAccountName
        search-base-dn cn=Users,dc=eslab,dc=local
        servers { 192.168.10.1 }
    }
    auth remote-role {
        role-info {
            F5Guest {
                attribute memberOF=CN=F5Guest,OU=f5guest,DC=eslab,DC=local
                console tmsh
                line-order 10
                role guest
                user-partition All
            }
        }
    }
    auth source {
        type active-directory
    }
Make sure that remote authentication for administrative users works on BIG-IP before proceeding to the next step. For details how to configure remote authentication for administrative users using LDAP, please read K11072.

For Radius Users

       auth radius /Common/system-auth {
               servers {
               /Common/system_auth_name1
             }
        }
     auth radius-server /Common/system_auth_name1 {
             secret $M$g7$g3Pm25/tg0tjUEb92L+81A==
             server 10.10.10.10
       }
     auth remote-user {
             default-role guest
             remote-console-access tmsh
      }
     auth source {
             type radius
      }
  1. Create remote user "test2" with password "test123" (memberOF=CN=F5Guest,OU=f5guest,DC=eslab,DC=local) in Active Directory, or radius server. This user, once authenticated on BIG-IP will be assigned to 'guest' role (see BIG-IP authentication config in step 1 for details).

    Note: Make sure to assign the right role for your user account:
    This steps in this article assigns role ‘guest’ to user 'test2' . To demonstrate fine grained RBAC we use a custom role for the user but the user inherits permissions from the 'guest' role. Here we use GET API to query virtual server resources and role type 'guest' has builtin permission for GET operations. You will need to use the appropriate role per your needs, For example write-access to Pool resources will require a role of type ‘operator’. For more details on permissions allocated to roles please see User Roles chapter in the BIG-IP Systems: User Account Administration manual.

  2. Create two virtual servers 'vs-1'/'vs-2' using the user interface for testing purposes.
  3. SSH to BIG-IP either with local or remote account that has BIG-IP administrator privilege.
  4. Get a token for the remote user "test2". Without the token, the remote user will not be able to access configuration objects on BIG-IP (such as virtual servers or pools). 
     
    # curl -sk -XPOST https://localhost/mgmt/shared/authn/login --data-binary '{"username":"test2", "password":"test123", "loginProviderName":"tmos"}' -H "Content-Type: application/json" | jq . | grep token

      "token": {
        "token": "EQIPKLNLHWEKNPVKYMQN4UZ4GX",
        "kind": "shared:authz:tokens:authtokenitemstate",
        "selfLink": "https://localhost/mgmt/shared/authz/tokens/EQIPKLNLHWEKNPVKYMQN4UZ4GX"

    Note: token validity time is 1200 seconds by default, after this time it expires and new token needs to be created.

    Note: Make sure to use the right authentication method:
    Below example lists two methods to authenticate users via REST . This article uses the second method and is the recommended method to authenticate remote users.

    • Method 1: Specify credential during every REST operation. Here the generated token has a URL in the format '.../mgmt/shared/authz/users/<username>' 

      # curl -ks -u 'myusername:mypassword' -X PATCH ‘https://x.x.x.x/mgmt/tm/ltm/…

    • Method 2: Create an authentication token to reuse for multiple REST operations. Here we specify username/password in JSON format and the generated token has a URL in the format '.../mgmt/cm/system/authn/providers/tmos/<provider-GUID>/users/<user-GUID>' 

      # curl -sk -XPOST https://x.x.x.x/mgmt/shared/authn/login --data-binary '{"username":"myusername", "password":"mypassword", "loginProviderName":"tmos"}' -H "Content-Type: application/json" | jq .

  5. Use the token from previous step to validate that remote user "test2" has access to all the resources granted by "guest" role on BIG-IP. For instance, "test2" user can get a list of all virtual servers on BIG-IP:
     
    # curl -sk -H 'X-F5-Auth-Token: EQIPKLNLHWEKNPVKYMQN4UZ4GX' -H 'Content-Type':'application/json' https://localhost/mgmt/tm/ltm/virtual | jq . | grep name
     
          "name": "vs-1",
          "name": "vs-2",

     From the above output one can see that there are two virtual servers configured on BIG-IP: "vs-1" and "vs-2".

  6. Create a custom resource-group on BIG-IP in order to restrict access to virtual server list . In this case we are creating resource-group with name "ResourceGroup-test2" and restrict access to virtual server with the name "vs-1".
     
    # curl -sku admin https://localhost/mgmt/shared/authz/resource-groups -X POST -H "Content-Type: application/json" -d '{"name":"ResourceGroup-test2", "resources":[ {"restMethod":"GET", "resourceMask":"/mgmt/tm/ltm/virtual/vs-1" } ]}' | jq .
    Enter host password for user 'admin':
    {
      "id": "c3f3f712-8995-3608-8e18-1734c63e06ae",
      "name": "ResourceGroup-test2",
      "resources": [
        {
          "resourceMask": "/mgmt/tm/ltm/virtual/vs-1",
          "restMethod": "GET"
        }
      ],
      "generation": 1,
      "lastUpdateMicros": 1562399051558623,
      "kind": "shared:authz:resource-groups:roleresourcegroupstate",
      "selfLink": "https://localhost/mgmt/shared/authz/resource-groups/c3f3f712-8995-3608-8e18-1734c63e06ae"
    }

    To view all resource-groups you can use ‘restcurl -u admin:admin /mgmt/shared/authz/resource-groups’ to confirm that it shows in the output

  7. We will now identify the full URL of the newly created user and remove from iControl_REST_API_User. 

    • a. Run below command to list all local user accounts:

      # restcurl -u admin:admin /mgmt/shared/authz/users

    • b. Run below commands to list users in the iControl_REST_API_User group. 

      Note: this output will only display user-GUIDs of remote users in the format …/tmos/<provider-GUID>/users/<user-GUID> and not list their corresponding usernames.

      # restcurl -u admin:admin /mgmt/shared/authz/roles/iControl_REST_API_User

    • c. To find the list of remote users along with their usernames use the following command. Replace <provider-GUID> with the value seen in the output of iControl_REST_API_User. This output will show the usernames of remote users along with their corresponding user GUIDs:

      # restcurl -u admin:admin /mgmt/cm/system/authn/providers/tmos/<provider-GUID>/users/

      Here is a sample output:

      # restcurl -u admin:admin /mgmt/cm/system/authn/providers/tmos/1f44a60e-11a7-3c51-a49f-82983026b41b/users/
      {
      "items": [
      ...
      {
      "id": "c6d50d31-b985-3268-ba24-1678b6460e13",
      "name": "test2",
      "generation": 1,
      "lastUpdateMicros": 1651759092719995,
      "kind": "cm:system:authn:providers:tmos:1f44a60e-11a7-3c51-a49f-82983026b41b:users:usersstate",
      "selfLink": https://localhost/mgmt/cm/system/authn/providers/tmos/1f44a60e-11a7-3c51-a49f-82983026b41b/users/c6d50d31-b985-3268-ba24-1678b6460e13
      }
      ...
      }

    • d. Identify the GUID of the newly created user "test2" in above output. Below is the URL of the user "test2" that we created here:

      https://localhost/mgmt/cm/system/authn/providers/tmos/1f44a60e-11a7-3c51-a49f-82983026b41b/users/c6d50d31-b985-3268-ba24-1678b6460e13

    • e. Now that we have the URL, we need to make sure to remove this user from the iControl_REST_API_User group . Note that this part applies to BIG-IP 13.1.0 and above (If your BIG-IP is a version prior to 13.1.0 then you can ignore this removal step). To remove, use step 2 in the Devcentral article iControl REST Fine-Grained Role Based Access Control. If you do not remove the user from this REST group then RBAC may misbehave arbitrarily (for example, you may see ‘MCP session terminated’ errors for certain users).

  8. Create a custom role with name "Role-test2" and attach "test2" user to the role. Make sure to use the full user URL in the format ‘.../mgmt/cm/system/authn/providers/tmos/<provider-GUID>/users/<user-GUID>'. 

    Also attach the resource group "ResourceGroup-test2" (using its resource id, here c3f3f712-8995-3608-8e18-1734c63e06ae) to the role so that user "test2" has access to  resource  "ResourceGroup-test2" via role "Role-test2". Ensure that the "link" values point to localhost and not to the BIG-IP management IP.

    This makes the user to become a member of the role "Role-test2", hence restricts "test2" user to get information only about "vs-1" and prohibits access to all other virtual servers on BIG-IP. 

    # curl -sku admin https://localhost/mgmt/shared/authz/roles -X POST -H "Content-Type: application/json" -d '{"name":"Role-test2", "userReferences":[ {"link":"https://localhost/mgmt/cm/system/authn/providers/tmos/1f44a60e-11a7-3c51-a49f-82983026b41b/users/c6d50d31-b985-3268-ba24-1678b6460e13"} ], "resourceGroupReferences":[{"link":"https://localhost/mgmt/shared/authz/resource-groups/c3f3f712-8995-3608-8e18-1734c63e06ae"}]}' | jq .

    To view all roles you can use ‘restcurl -u admin:admin /mgmt/shared/authz/roles’ to confirm that it shows in the output

  9.  Finally, we will verify that remote user "test2" has access only to "vs-1" on BIG-IP and not other virtual servers.
     
    # curl -sk -H 'X-F5-Auth-Token: EQIPKLNLHWEKNPVKYMQN4UZ4GX' -H 'Content-Type':'application/json' https://localhost/mgmt/tm/ltm/virtual | jq .
    {"code":401,"message":"Authorization failed:" ..}

    # curl -sk -H 'X-F5-Auth-Token: EQIPKLNLHWEKNPVKYMQN4UZ4GX' -H 'Content-Type':'application/json' https://localhost/mgmt/tm/ltm/virtual/vs-2 | jq .
    {"code":401,"message":"Authorization failed:" ..}

    # curl -sk -H 'X-F5-Auth-Token: EQIPKLNLHWEKNPVKYMQN4UZ4GX' -H 'Content-Type':'application/json' https://localhost/mgmt/tm/ltm/virtual/vs-1 | jq .
    HTTP/1.1 200 OK ...

    From the above output one can see that "test2" user can only access "vs-1" virtual server properties and is not allowed to access "vs-2" virtual server properties because of RBAC rules configured on BIG-IP.
