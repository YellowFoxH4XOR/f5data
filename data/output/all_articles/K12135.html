Known Issue

This is the result of a known issue. When the BIG-IP ZebOS module is configured to run two or more Open Shortest Path First (OSPF) router processes, changes on one router process deletes dynamic routes that still exist on the other.

In the following example, the BIG-IP system participates in two different OSPF areas, and the ZebOS is configured with the two OSPF areas in separate OSPF route processes:

router ospf 20
ospf router-id 20.20.20.152
network 20.20.0.0/16 area 20
!
router ospf 30
ospf router-id 30.30.30.152
network 30.30.0.0/16 area 30
!

The following output shows the peering with two routers on separate OSPF areas:

OSPF process 20:
Neighbor ID Pri State Dead Time Address Interface
10.10.10.153 1 Full/DR 00:00:31 20.20.20.153 vlan1010

OSPF process 30:
Neighbor ID Pri State Dead Time Address Interface
10.10.10.155 1 Full/DR 00:00:30 30.30.30.155 vlan1010

The following output shows OSPF E2 and IA routes in the ZebOS route table received from the two peer routers:

O*E2 0.0.0.0/0 [110/1] via 30.30.30.155, vlan1010, 00:00:34
O IA 10.10.0.0/16 [110/20] via 20.20.20.153, vlan1010, 00:00:35
C 20.20.0.0/16 is directly connected, vlan1010
C 30.30.0.0/16 is directly connected, vlan1010
C 127.0.0.1/32 is directly connected, lo
C 127.1.1.0/24 is directly connected, tmm0
O E2 192.168.204.0/24 [110/20] via 30.30.30.155, vlan1010, 00:00:34

ZebOS will remove all OSPF routes from its route table including those from the other peer router 20.20.20.153 when ZebOS no longer receives multicast LSAs from peer router 30.30.30.155, possibly due to network issues (for example, router interface or link down) and considers peer router 30.30.30.155 dead. When this issue occurs, output appears similar to the following example:

C 20.20.0.0/16 is directly connected, vlan1010
C 30.30.0.0/16 is directly connected, vlan1010
C 127.0.0.1/32 is directly connected, lo
C 127.1.1.0/24 is directly connected, tmm0

F5 Product Development tracked this issue as ID 224585 (formerly CR136848) and ID 247878 (formerly CR136848-1) and it was fixed in BIG-IP version 11.0.0. For information about upgrading, refer to the BIG-IP LTM, GTM, PSM, Link Controller, WebAccelerator, APM, WOM, or Edge Gateway release notes.

Workaround

You can work around this issue by configuring only one instance of OSPF route process with multiple OSPF areas in ZebOS. To do so, perform the following procedure:

  1. Log in to the BIG-IP command line with administrator privileges.
  2. To stop the ospfd process, type the following command:

    Important: Disabling OSPF will stop the BIG-IP system from using OSPF routes until OSPF is re-enabled.

    zebos disable ospf

  3. Back up a copy of /config/ZebOS.conf by typing the following command:

    cp –p /config/ZebOS.conf /var/tmp/ZebOS.conf.backup

  4. Use a text editor to modify the OSPF configuration stanza to appear similar to the following example:

    router ospf 20
    ospf router-id 20.20.20.152
    network 20.20.0.0/16 area 20
    network 30.30.0.0/16 area 30
    !

  5. Save the changes.
  6. To start the ospfd process, type the following command:

    zebos enable ospf
