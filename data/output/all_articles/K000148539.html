Description

The GTM synchronization issue occurred when attempting to add the "secondary" GTM into an existing sync group with the "primary" GTM using the gtm_add command. The configuration from the "primary" GTM was not fetched, resulting in the GTMs not being in sync, and no error message was prompted.

Environment

  • BIG-IP DNS
  • CLI Bash Command
  • gtm_add <gtm.ip>
  • tmsh load sys config gtm-only verify
  • Wide A config entries conflict

Cause

There's a Wide IP records configuration crash/conflict between the primary and secondary GTMs. 

Recommended Actions

To confirm the error message, follow these steps: 

  1. On secondary GTM, rename the configuration "bigip_gtm.conf" to "bigip_gtm.conf.bak_dates":
    mv bigip_gtm.conf bigip_gtm.conf.bak_dates

  2. Copy the GTM configuration file "bigip_gtm.conf" from primary GTM to secondary GTM "/conf" folder.
    Notes: May use either SFTP or SCP

  3. On secondary GTM, run TMOS command to verify copied "bigip_gtm.conf" GTM configuration with current running config and you should see similar error messages as example listed below.
    tmsh load sys config gtm-only verify

    Example error messages: 
    01070734:3: Configuration error: DB validation exception, unique constraint violation on table (gtm_wideip_alias) object ID (1 <partition_name/wide_IP_name alias_name>). A duplicate value was received for a non-primary key unique index field. DB exception text (Cannot update_indexes/checkpoint DB object, class:gtm_wideip_alias status:13)

    01070734:3: Configuration error: DB validation exception, unique constraint violation on table (gtm_wideip_alias) object ID (1 <partition_name/wide_IP_name alias_name>)    . A duplicate value was received for a non-primary key unique index field. DB exception text (Cannot update_indexes/checkpoint DB object, class:gtm_wideip_alias status:13)

    0107022e:3: Wide IP Alias wide_IP_name of type A can not be added as a Wide IP <partition_name/wide_IP_name> of type A already exists with the same name(case insensitive)

  4. Once confirmed, you may either resolve all the conflicts manually, or follow an easier as steps listed below on the secondary GTM.
    1. Restore the BIG-IP GTM configuration to default and then perform the gtm_add command again.
      1. Backup the bigip_gtm configuration (may skip this steps if not required)
        cd /config
        mv bigip_gtm.conf bigip_gtm.conf.bak$(date +%H%M-%m%d%Y)

      2. Create a new bigip_gtm.conf file and edit it
        vim bigip_gtm.conf OR nano bigip_gtm.conf 
        Notes: You may use which ever method you are familiar with to edit the bigip_gtm.conf file

      3. Enter content below to the new bigip_gtm.conf
        #TMSH-VERSION: 15.1.8.2
gtm global-settings metrics {
    metrics-collection-protocols { icmp }
}
gtm global-settings metrics-exclusions {
    addresses none
}

      4. After that, perform a force mcpd reload with below command.
        touch /service/mcpd/forceload
        reboot now

    2. Once booted up, the "secondary" GTM configuration would have restored to default, you may confirm by checking either via "GUI ›› Statistics  ››  Module Statistics : DNS : GSLB  ››  Status Summary" or "DNS  ››  GSLB : Wide IPs : Wide IP List"

  5. Finally, on the secondary GTM, run the GTM command gtm_add to add the "secondary" GTM to the "primary" GTM sync group.

If further assistance is needed, please raise a case with technical support to troubleshoot and resolve the issue.
