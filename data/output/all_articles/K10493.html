Known Issue

This is the result of a known issue. When URL Normalization is disabled, the BIG-IP WebAccelerator adds an Accept-Ranges HTTP header to the response when the origin web server (OWS) does not set the header. As a result, the BIG-IP WebAccelerator may inappropriately proxy requests to the OWS for certain objects.

This issue can result in the OWS returning an error page in response to a request for a linearized PDF document, as illustrated in the following sequence example:

  • A client connects to the virtual server and sends a POST request for a dynamically generated PDF document
  • The OWS responds with a Linearized PDF document, and does not include an Accept-Ranges HTTP header in the response
  • The BIG-IP WebAccelerator incorrectly inserts an Accept-Ranges header in the response to the client, activating the PDF reader's plugin linearization feature
  • The client sends multiple GET requests (with Range headers) for chunks of the PDF document
  • These GET requests do not have the POST data included in their query string, so they are treated as new requests
  • The BIG-IP WebAccelerator proxies the requests to the server, resulting in the OWS returning an error page

F5 Product Development tracked this issue as CR124967 and it was fixed in BIG-IP WebAccelerator 10.1.0. For information about upgrading, refer to the BIG-IP WebAccelerator release notes.

Workaround

You can work around this issue using one of the following methods:

Bypass the BIG-IP WebAccelerator for affected pages

To bypass the BIG-IP WebAccelerator for affected pages using an iRule, refer to K6882: Bypassing BIG-IP WebAccelerator with an iRule in version 9.4.x. To bypass the WebAccelerator for affected pages using the HTTP Class profile, refer to K9585: Using an additional HTTP class to selectively bypass BIG-IP WebAccelerator.

Use an iRule to remove the Accept-Ranges header

Note: Due to architecture changes made in BIG-IP version 10.0.0, this workaround does not apply to version 10.x.

In BIG-IP WebAccelerator 9.4.x, you can use an iRule to remove the Accept-Ranges header in responses for affected pages. For example:

when HTTP_RESPONSE {
if { [HTTP::header exists "Accept-Ranges"] } { HTTP::header remove "Accept-Ranges" }
}
