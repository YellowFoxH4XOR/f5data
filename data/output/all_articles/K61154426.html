Description

You should consider using this article under any of the following conditions:

  • You attempt to create a QKView diagnostic file from the GUI (Configuration utility) and nothing happens.
  • You are unable to create a QKView diagnostic file from the command line and receive a message similar to the following indicating the qkview utility is already running:

    Another qkview is running.
    You can't run multiple instances of qkview at once.

  • You attempt to generate a QKView diagnostic file using the Configuration utility and it fails or generates a 0 byte-size file.
  • The qkview process is unresponsive, stuck, stalled, or runs indefinitely.

Environment

  • You attempt to create a QKView diagnostic file using the Configuration utility.
  • You attempt to create a QKView diagnostic file from the command line using the qkview command.

Cause

  • Under certain conditions, the qkview process may stop responding and become orphaned.
  • Insufficient disk space available on the system for the QKView diagnostic file. 
  • If the BIG-IP system is experiencing high CPU or memory utilization, the qkview process may not complete successfully.

Recommended Actions

You can perform the following procedures to troubleshoot issues generating QKView diagnostic files:

  • Stopping unresponsive qkview generation
  • Verifying /var disk usage
  • Verifying CPU/memory utilization
  • Running the qkview verbosely
  • Running the qkview utility only on a specific blade

Stopping unresponsive qkview generation

A previous qkview process may have stopped responding and become orphaned. You can perform the following procedure to identify and stop (kill) an unresponsive qkview process:

  1. Log in to the BIG-IP command line.
  2. Use the ps command to find the qkview process by typing the following command:

    ps -ef | grep -i [qk]view

    The output of the command appears similar to the following:

    root     11112 11053 34 12:30 pts/0    R+     0:01 qkview

  3. To stop the orphaned qkview process, use the following command syntax:

    kill -9 <PID>

    Note: <PID> is the process ID of the orphaned qkview process.

    For example, with the output previously listed, use the following command:

    kill -9 11112

    Note: If there are multiple instances of the qkview process running, you need to stop (kill) all instances.

  4. After all instances of the qkview process is stopped, you should verify that a /shared/tmp/.qkview_lock file is removed (if present) by typing the following command:

    rm /shared/tmp/.qkview_lock

  5. You should be able to create a new QKView diagnostic file using the Configuration utility or from the command line using the qkview command.

Verifying /var disk usage

QKView files are saved to the /var partition by default. Verify usage of this partition and ensure that adequate disk space is available by performing the procedures in the following article:

  • K14403: Maintaining disk space on the BIG-IP system

For BIG-IP Virtual Edition (VE), you may also consider increasing available disk space by extending the /var partition. For information refer to the following article:

  • K14952: Extending disk space on BIG-IP VE

Verifying CPU/memory utilization

If you suspect the qkview process is not completing as a result of the BIG-IP system experiencing high CPU or memory utilization, you can verify the CPU and memory usage by using either (both) of the following methods:

  • In the Configuration utility, navigate to the Statistics > Dashboard page.
  • From the command line, use the top utility.

    Note: For information about using the top utility to determine if the output of the top command indicates high memory or CPU usage, refer to K16739: Understanding 'top' output on the BIG-IP system.

Running the qkview utility verbosely

The qkview process executes a series of commands to collect configuration and diagnostic information. Running the qkview process verbosely will allow you to identify if the qkview generation gets stuck on a particular process. If the qkview process gets stuck running a particular command, it is likely that this is the reason the QKView generation is failing, and you should focus on execution of that command when troubleshooting.

Use the following command to run the qkview process verbosely:

qkview -v

If the qkview process gets stuck on a command, you may see an output similar to the following example:

/usr/bin/tmsh -a show analytics report view-by virtual include-total measures { average-page-load-time } range now-1h

Executing Module: [qkavr.so]
            Executing /usr/bin/du -h /var/lib/mysql/AVR/
            Result: [0] Elapsed: 0.031813
            Executing /usr/bin/tmsh -a show analytics report view-by virtual include-total measures { average-page-load-time } range now-1h ...

Running the qkview utility only on a specific blade

In case the standard qkview generation does not complete on a multi-blade system, it may be useful to run the qkview verbosely on a specific blade.

A good indication that this is necessary is when the verbose qkview, as previously described, appears to stop or hang after a message mentioning "chassis.so".

For example:

Executing Module: [chassis.so]

Log in to the affected blade (or all blades in order) by using the -r option in addition to the -v option, and use SSH to log in the the specific blade number by using the following command syntax:

Note: Replace the N with the blade number).  It may be necessary to locally run the qkview utility in this manner on all blades, one after the other to find which one is experiencing a problem.

ssh slotN

qkview -v -r

The output appears similar to the verbose invocation previously described, but the procedure only uses the local blade to collect data.
