Description

Connections to Virtual Server using Websockets are reset.

Environment

  • BIG-IP LTM
  • Virtual Server
  • TCP, HTTP, and Websockets Profiles

Cause

Websocket handshake requests are being rejected with "Error 403" by the pool members
 

Recommended Actions

Take a packet capture of the connection attempt and investigate whether the client is able to complete a websockets

If your pool members are providing a 403 or other 400 series response code, they may need to be reconfigured to accept websockets requests

"Error 403" means the origin server is not authorized to access websocket application.

Solution options:
  
The options here are:


The most efficient one involves the modification of the "WebSocket" application residing on the back-end server to accept the "origin" header:

Origin: https://mysite.com\r\n


Or try an iRule to modify the host header:

when HTTP_REQUEST {
        if { [HTTP::host] contains "0non_authorized_site.com" } {
            log local0. "Original Request:  [HTTP::host][HTTP::uri]"
            HTTP::header replace Host [string map -nocase {"non_authorized_site.com" "correct_site.com"} [HTTP::header Host]]
            log local0. "Modified Request:  [HTTP::host][HTTP::uri]"
        }
    }




Additional Information 
 

The WebSocket Protocol

https://tools.ietf.org/html/rfc6455 
1.2 _This section is non-normative._

   The protocol has two parts: a handshake and the data transfer.

   The handshake from the client looks as follows:

        GET /chat HTTP/1.1
        Host: server.example.com
        Upgrade: websocket
        Connection: Upgrade
        Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
        Origin: http://example.com                      <------------------------------
        Sec-WebSocket-Protocol: chat, superchat
        Sec-WebSocket-Version: 13

   The handshake from the server looks as follows:

        HTTP/1.1 101 Switching Protocols
        Upgrade: websocket
        Connection: Upgrade
        Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
        Sec-WebSocket-Protocol: chat

10.2.  Origin Considerations

   Servers that are not intended to process input from any web page but
   only for certain sites SHOULD verify the |Origin| field is an origin
   they expect.  If the origin indicated is unacceptable to the server,
   then it SHOULD respond to the WebSocket handshake with a reply
   containing HTTP 403 Forbidden status code.                                   <------------------------------ !!!

   The |Origin| header field protects from the attack cases when the
   untrusted party is typically the author of a JavaScript application
   that is executing in the context of the trusted client.  The client
   itself can contact the server and, via the mechanism of the |Origin|
   header field, determine whether to extend those communication
   privileges to the JavaScript application.  The intent is not to
   prevent non-browsers from establishing connections but rather to
   ensure that trusted browsers under the control of potentially
   malicious JavaScript cannot fake a WebSocket handshake.
