Topic

This article applies to BIG-IP 10.x. For information about other versions, refer to the following article:

  • K13384: Performing a web applications trace (11.x - 13.x)

Purpose

You should consider using this procedure under the following conditions:

  • Users cannot access a web application through the BIG-IP APM system.
  • Web pages do not fully load when accessed through the BIG-IP APM system.
  • Web pages display errors when accessed through the BIG-IP APM system.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • Your BIG-IP APM system is configured with a web application.

Description

Description

To troubleshoot issues with a particular web application, you can use the BIG-IP APM system's web applications engine trace feature. This feature generates a trace file that contains the HTTP request and response exchanged between the client and the BIG-IP APM system, and also the HTTP request and response exchanged between the BIG-IP APM system and the back-end web server. You can determine whether the modifications made by the web applications engine are affecting the functionality of the web application by comparing the front-end request and response with the back-end request and response.

Procedures

When experiencing web application issues, you can perform the following procedures to collect and analyze a trace of the web application engine:

  • Generating a web applications trace file
  • Analyzing the trace file

Generating a web applications trace file

  1. Have a user who is assigned the affected web application log in to the BIG-IP APM system.
  2. Log in to the BIG-IP command line.
  3. To obtain the user's session ID, use the following command syntax, and replace <username> with the user's user name:

    sessiondump -allkeys | grep <username>

    The session ID appears at the beginning of each line of output. In the following example, the session ID for the user jsmith is 65a6b075:

    [root@3400a:Active] config # sessiondump -allkeys | grep jsmith
    65a6b075.session.assigned.uuid 26 tmm.uuid.AD-Basic.jsmith
    65a6b075.session.logon.ad_auth_and_resources_act_logon_page_ag.username 8 jsmith
    65a6b075.session.logon.last.username 8 jsmith
    [root@3400a:Active] config #

  4. To enable a web application's trace for the session ID, use the following command syntax, and replace <session-id> with the user's session ID:

    bigpipe db Log.WebApplications.Trace.SessionId <session-id>

    For example:

    bigpipe db Log.WebApplications.Trace.SessionId 65a6b075

  5. Have the user access the affected web application.
  6. After the user has accessed the application, change directories to the directory of the webtrace by using the following command syntax:

    cd /var/tmp/WebAppTrace/<sessionid>

    In this command, <sessionid> is the user's session ID.

    For example:

    cd /var/tmp/WebAppTrace/65a6b075/

  7. To create the webtrace.tgz file and add the webtrace data, use the following command syntax:

    /usr/bin/tar -czf webtrace.tgz *

    For example:

    /usr/bin/tar -czf webtrace.tgz *

  8. Copy the webtrace.tgz file your local workstation.
  9. On the local workstation, extract the webtrace.tgz file and open the index.html file view the trace file.

Analyzing the trace file

The trace file you generated in the previous procedure contains the following four sections. You can use the results of the trace to determine whether the rewriting performed by the web applications engine is impacting the functionality of the web application, by comparing the data in the Front-end request/response to the data in the Back-end request/response.

  • Requests

    This section contains a list of HTTP requests sent from the client to the BIG-IP APM system. Click the request that you want to examine, which will populate the corresponding data in the other three sections of the index.html page.

    The following example shows the requests that the client made:

    16:54:216408GET /
    16:54:216408GET /about.gif
    16:54:216408GET /pagerror.gif
  • Request log

    This section contains a brief summary of the HTTP request and response.

    For example:

    New front-end request/response
    # pid = 6408
    # initializePatchInfo()
    Front-end request: GET /
    Parsing front-end request
    URL: /
    Context Hint: U
    New back-end request/response
    set Context Hint from content type: U
    guess Content type returns HTML
    final processContent egress release returns 151546456

  • Front-end request/response

    This section contains the HTTP request sent from the client to the BIG-IP APM system, and the HTTP response from BIG-IP APM system to the client. The response is color coded with the changes that the web application engine made to the html code. For information on the color-coded sections, refer to the legend at the bottom of the Front-end request/response window.

    Note: The front-end response contains the web application content after it was rewritten by the web applications engine.

    The example below shows the changed web link from the original URI to the address of the virtual server / encoded URI of the original link. This redirects the href link to the virtual server.

    For example:

    <span class="submenu" id="sub3">
    - <a href=" https://10.1.1.64/f5-w-687474703a2f2f7777772e636f64696e67666f72756d732e636f6d$$/ ">Coding Forums</a><br>

    Legend:

    HTML REF

    Note: The actual Front-end request/response section has a background/text color highlight to indicate the changes.

  • Back-end request/response

    This section contains the HTTP request sent from the BIG-IP APM system to the back-end web server, and the HTTP response from the back-end web server to the BIG-IP APM system. The response is color coded with the changes that the web application engine made to the html code. For information on the color-coded sections, refer to the legend at the bottom of the Back-end request/response window.

    Note: The back-end response contains the web application content before it was rewritten by the web applications engine.

    The example below shows the backend response from the server before the web application engine had rewritten the href value.

    For example:

    <span class="submenu" id="sub3">
    - <a href="http://www.example.com">Coding Forums</a><br>
    </span>

    Legend:

    HTML REF

You can use the results of the trace to determine whether the rewriting performed by the web applications engine is impacting the functionality of the web application, by comparing the data in the Front-end request/response to the data in the Back-end request/response.
