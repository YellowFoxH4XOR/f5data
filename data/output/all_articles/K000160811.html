K000160811: F5 Distributed Cloud - How to restrict TLS decryption and traffic proxying to specific Regional Edge locations using Virtual Sites

Description

When deploying application delivery and security services on F5 Distributed Cloud, TLS termination and traffic proxying occur by default across all Regional Edges (RE) globally. Organizations with regulatory or compliance requirements around encryption key storage and inspection points may need to restrict which Regional Edge locations are permitted to decrypt traffic and proxy application flows.

  • How can TLS decryption be restricted to specific Regional Edge locations in F5 Distributed Cloud?
  • How can Virtual Sites be used to control which Regional Edges process traffic for a specific application?
  • How does F5 Distributed Cloud route traffic to a specific Regional Edge when a custom Virtual Site is configured?
  • What are the prerequisites for configuring a custom Regional Edge decryption topology using Virtual Sites?
  • How can I verify that traffic is being decrypted only at the intended Regional Edge locations?

Environment

  • F5 Distributed Cloud (SaaS)
  • Regional Edge (RE) data plane
  • HTTP or HTTPS Load Balancer objects
  • VIP Advertisement configured on Load Balancer objects
  • Organization has compliance or regulatory requirements restricting where TLS decryption and key storage may occur (e.g., specific countries or continents)
  • Additional Tenant IP or BYO-IP (/24 or larger) available in the tenant as a prerequisite
  • Virtual Sites configured for Regional Edge grouping
  • F5 Global Backbone (Application Delivery Network - ADN) used for inter-RE traffic routing

Cause

By default, F5 Distributed Cloud advertises a shared public IP address across all Regional Edges globally using Anycast routing. This means any Regional Edge can terminate TLS and proxy traffic for services attached to the tenant's default IP. When regulatory or compliance requirements mandate that encryption key storage and TLS inspection occur only within specific geographic boundaries, the default global topology does not satisfy those constraints.

Answer/Recommended Actions

Use Virtual Sites combined with additional public IP addresses to build a custom Regional Edge topology that restricts TLS decryption and proxying to specific Regional Edge locations. The following steps walk through the full configuration.

Prerequisites

  • One additional public IP address per custom topology must be available within the tenant. Additional IPs can be sourced from F5 Distributed Cloud IP blocks or by bringing your own IP space (BYO-IP). BYO-IP requires a minimum prefix size of /24 due to internet advertisement standards.

Step 1: Create a Virtual Site

  1. From the home screen, navigate to Select Service → Shared Configuration → Manage → Virtual Sites.
  2. Click Add Virtual Site and provide a name and description.
  3. Set Site Type to RE (Regional Edge).
  4. Under Site Selector Expression, use the pre-defined RE labels to select the desired Regional Edge locations (e.g., London and Paris for an EU Virtual Site).
    • To find RE labels, navigate to Multi-Cloud Network Connect → Overview → Sites, filter by Site Type: REGIONAL_EDGE, and expand the site JSON to locate the labels section.
  5. Important: Always include more than one Regional Edge in a Virtual Site. A single-location Virtual Site will cause an outage during F5's regular maintenance windows (every 4–8 weeks).

Step 2: Associate the Additional Public IP Address with the Virtual Site

  1. Navigate to Select Service → Shared Configuration → Manage → Public IP Addresses.
  2. Locate the additional IP address to be used for this topology. Click the three dots under Actions and select Manage Configuration.
  3. In the top right corner, click Edit Configuration.
  4. Under the Virtual Site field, select the Virtual Site created in Step 1.
  5. Save the configuration.

Once the Virtual Site is attached to the IP address, that IP will be advertised into the F5 Global Backbone as a /32. Internet traffic will still route to the nearest Regional Edge via the /24 Anycast advertisement, but once it enters the F5 Global Backbone, the more specific /32 route directs traffic to the Regional Edges defined in the Virtual Site.

Step 3: Update VIP Advertisement on the Load Balancer

  1. Navigate to Select Service → Load Balancers → Manage → Load Balancers → HTTP Load Balancers.
  2. Create a new HTTP Load Balancer or edit an existing one.
  3. Navigate to Other Settings and change the VIP Advertisement setting to Internet (Specified VIP).
  4. Select the public IP address updated in Step 2.
  5. Save the Load Balancer configuration.

Note: Because the Virtual Site and public IP address are configured within the shared namespace, this configuration can be applied to Load Balancers in any namespace within the tenant.

Verification

  1. Confirm that DNS has been updated so the FQDN(s) associated with the Load Balancer resolve to the new public IP address. Verify using nslookup or dig from a local machine.
  2. Navigate to Select Service → Load Balancers → Virtual Host → Load Balancer → Performance Monitoring → Requests.
  3. Locate a request and confirm that the Regional Edge listed for L5–L7 services (TLS termination, proxying, load balancing) corresponds to one of the locations defined in the Virtual Site, regardless of where the client is geographically located.
  4. Click on the JSON tab of the request for detailed attributes, including the Regional Edge that processed the traffic.

Additional Information

F5 Distributed Cloud's Regional Edges are connected to two networks by default: the public internet and the F5 Global Backbone (also referred to as the Application Delivery Network, or ADN). The ADN is a multi-terabit, low-latency physical network with a software-defined distributed overlay. It provides interconnectivity between Regional Edges, Customer Edges, customer data centers, and cloud environments.

F5 is one of the most peered global networks in the world, with nearly 5,000 IPv4 and 4,000 IPv6 BGP adjacencies. This extensive peering underpins the Anycast route advertisement that routes clients to the nearest Regional Edge. Internet standards require organizations advertising network prefixes to use a /24 or larger, which is why BYO-IP requires a minimum of /24.

When a custom Virtual Site is applied to an additional public IP:

  • The /24 prefix continues to be advertised globally from all Regional Edges, so clients always reach the nearest RE via standard internet routing.
  • The specific IP associated with the Virtual Site is advertised as a /32 within the F5 Global Backbone only.
  • Once client traffic enters the F5 Global Backbone at the nearest RE, the more specific /32 route directs that traffic internally to the nearest RE included in the Virtual Site, where TLS termination and proxying occur.

This architecture allows F5 Distributed Cloud to ingest traffic globally while ensuring that sensitive operations such as TLS decryption and key usage are confined to approved Regional Edge locations — satisfying regulatory requirements around data sovereignty, encryption inspection points, and key storage geography.

Multiple custom Virtual Site topologies can coexist within a single tenant. Different applications can be assigned to different Virtual Sites based on their individual compliance requirements. Some applications may continue to use the default global topology while others are restricted to specific regions.
