Topic

If a BIG-IP DNS (formerly BIG-IP GTM) sync group has an incomplete iQuery mesh, it is possible for configuration changes to be lost or for systems in the same sync group to provide different answers to the same query.

The gtmd process on each BIG-IP DNS system in a sync group attempts to establish an iQuery connection to a remote system's big3d process. By default, the big3d process listens on each self IP address defined on each BIG-IP server object listed in the BIG-IP DNS configuration. If Link Discovery is enabled and a default gateway pool is assigned as the default route on that server, the BIG-IP DNS system also attempts to connect to the self IP addresses assigned to the VLANs on which each default gateway pool member resides.

If the gtmd process fails to connect to a remote systems big3d process, it subsequently fails to learn of any configuration objects newly defined or modified on the remote BIG-IP system.

Note: An iQuery connection is defined as an SSL connection on port 4353 from a local gtmd process to the big3d process on a remote or local BIG-IP server. When big3d starts, it listens for port 4353 on all configured self IP addresses and the management interface IP address.

Sync group communication

BIG-IP 11.x and later sync group communication

In 11.x and later, the BIG-IP system uses a commit_id structure, which is linked to an MCP transaction, as a timestamp when updating the configuration for a given device group. When a change is made to the BIG-IP DNS/GTM configuration, the local mcpd process forwards the new configuration to the local gtmd process. The gtmd process updates the commit_id value and instructs the local big3d process to begin advertising the updated commit_id value to all remote gtmd processes.

BIG-IP 10.x sync group communication

In 10.x, each BIG-IP system broadcasts the timestamps of its configuration files to all other systems in the sync group every 10 seconds, by default, as part of the heartbeat message. After gtmd receives this message, it compares its own wideip timestamp with the wideip timestamp received from the peer system. When the timestamps differ, the system with the older timestamp for the wideip.conf configuration files initiates a sync operation, pulling the newer configuration from the peer and loading it into memory.

Common failures

If a BIG-IP system does not have a proper iQuery connection with its peer BIG-IP systems, changes between the systems are not reconciled, and the affected sync group member is no longer synchronized with the group.

Sync group communication failure

The following example includes three BIG-IP systems in a sync group. BIG-IP1 and BIG-IP2 have full bi-directional connectivity (gtmd to big3d); however, both devices are unable to connect to the big3d process on BIG-IP3. The gtmd process on BIG-IP3 is able to connect to big3d on both BIG-IP1 and BIG-IP2. As a result, BIG-IP1 and BIG-IP2 are able to receive big3d messages from each other, but neither can receive messages from BIG-IP3. BIG-IP3 can receive messages from BIG-IP1 and BIG-IP2. The iQuery mesh is incomplete, as demonstrated in the following table.
gtmd hostConnection statusbig3d host
BIG-IP1OKBIG-IP2
BIG-IP1FAILBIG-IP3
BIG-IP2OKBIG-IP1
BIG-IP2FAILBIG-IP3
BIG-IP3OKBIG-IP1
BIG-IP3OKBIG-IP2

Any configuration changes that are made on BIG-IP3 may not be synchronized to BIG-IP1, and BIG-IP2. Under these conditions, BIG-IP3  has a newer configuration and may potentially return different responses than BIG-IP1 and BIG-IP2.

If subsequent configuration changes are made on BIG-IP1, those changes are synchronized by BIG-IP2 and BIG-IP3 since both have established iQuery connections to the BIG-IP1 big3d process. Both BIG-IP2 and BIG-IP3 would recognize that BIG-IP1 has a newer configuration than their own, and each would download the BIG-IP1 configuration and load it into memory. This behavior results in a loss of all changes that originated on BIG-IP3 but were never synchronized by BIG-IP1 or BIG-IP2.

To troubleshoot iQuery communication issues, refer to the following solutions:

  • K13690: Troubleshooting BIG-IP DNS synchronization and iQuery connections (11.x - 15.x)
  • K14227: Troubleshooting BIG-IP GTM synchronization and iQuery connections (10.x)

Sync group member type mismatch

After the underlying connectivity is established and working correctly, it is also important to confirm that the server type values of each member are in agreement across the group. Starting in BIG-IP 13.x,  the server type value is displayed in the output of the tmsh show gtm iquery command:

  • For BIG-IP devices with the BIG-IP DNS module provisioned - as BIGIP-DNS
  • For BIG-IP devices without the BIG-IP DNS module provisioned - as BIGIP

If the same group member is reported with different values for the Server Type attribute across the different members of the sync group, for example (the following outputs have been truncated for brevity):
