Known Issue

Log messages concerning SSL handshake failures may not include enough detail.

This issue occurs when all of the following conditions are met:

  • A BIG-IP virtual server is configured with a server-side SSL profile.
  • The server-side SSL profile Expire Certificate Response Control option is set to drop (this is the default setting).

In this configuration, connections to a server with an expired certificate will be dropped, but the default log level (Warning) produces a log message indicating only a handshake failure. Information indicating that the certificate was the cause of the handshake failure can only be seen when the SSL logging level is set to Debug.

Important: Increasing the amount of system information logged can lead to significant increase in resource utilization. Debug logging should only be used briefly, while troubleshooting a specific problem. Once the troubleshooting procedures are complete, the logging level should be immediately restored to the default state.

Impact

When handshake failures occur, it may be more difficult to determine the root cause.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • BIG-IP iHealth lists Heuristic H515855 on the Diagnostics > Identified > Medium page.
  • When using the BIG-IP system with a server-side SSL profile with the Expire Certificate Response Control option set to drop, the message logged to the /var/log/ltm file shows only that there was a handshake failure.

    For example:

    info tmm[14628]: 01260013:6: SSL Handshake failed for TCP 10.11.12.10:443 -> 10.11.12.20:41608

  • If debug logging is enabled, the following message is also logged to the /var/log/ltm file:

    debug tmm[14628]: 01260006:7: Peer cert verify error: ok (depth 0; cert /C=NO/CN=103.example.com)

Workaround

To work around this issue, you can temporarily enable debug logging for SSL. To do so, perform the following procedure:

Impact of workaround: Debug logging should be used temporarily, while performing troubleshooting procedures, and then turned off immediately when the procedures are complete. Failure to return logging levels to normal can lead to system performance degradation.

  1. Log in to the Traffic Management Shell (tmsh) by typing the following command:

    tmsh

  2. To determine the current logging level value for the log.ssl.level database key, type the following command:

    list /sys db log.ssl.level

    The output should appear similar to the following example:

    sys db log.ssl.level {
        value "Warning"
    }

  3. To change the value to Debug, type the following command:

    modify /sys db log.ssl.level value debug

  4. Repeat the command in step 2 to confirm the change. The output should look similar to the following example:

    sys db log.ssl.level {
        value "Debug"
    }

  5. Once the troubleshooting procedures are complete, return the logging level to the default level (Warning) by typing the following command:

    modify /sys db log.ssl.level value warning

  6. Repeat the command in step 2 to confirm that the logging level has returned to the default level.
