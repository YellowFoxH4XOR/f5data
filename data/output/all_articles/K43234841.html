Description

Since switched to VELOS OS platform, log's format, missing Slot ID and Hostname, which were included before:

Mar  9 13:03:26 LTM1 notice clusterd[]: 013a0006:5: mcpd tells us that config is being saved;  incrementing this blade's revision and saving cluster config
Mar  9 13:03:26 slot2 notice mcpd[]: 01071d15:5: adjust_admin_ips: old_mbrAddrs of slot: 2: 10.10.10.152/255.255.0.0

As an example - logs on VIPRION platform format looks like this:

Mar  9 11:00:13 slot2/LTM1 notice clusterd[]:013a0006:5: mcpd tells us that config is being saved; incrementing this blade's revision and saving cluster config
Mar  9 11:00:14 slot1/LTM1 notice mcpd[]:01071d15:5: adjust_admin_ips: old_mbrAddrs of slot: 1: 10.10.10.121/255.255.0.0


Environment

  • F5OS
  • BIG-IP tenants

Cause

The issue is tracked under ID992097.

Recommended Actions

Overall, this is related to syslog formatting. This is the same for VIPRION (both native and vCMP) and BIG-IP tenants on VELOS.

From version 12, indeed the default message format is supposed to be "slotX/hostname level process", for example:

slot1/viprion1.local err tmsh[29839]

Moreover, there are 2 db keys to control the behavior: 
  1. This controls whether the slot identifier is prepended to the hostname - that is enabled by default and is seen in example above
    # tmsh modify sys syslog clustered-host-slot enabled|disabled
  2. This controls whether the slot identifier is included as a column on its own in the message body - that is disabled by default. When it's enabled the log line format will look like: "slotX/hostname level slotX process".
    # tmsh modify sys syslog clustered-message-slot enabled|disabled
 As an example:
slot1/viprion1.local err slot1 tmsh[29839]

Additional Information

The log format got broken starting version 14.1.3.1 and version 15.1.2 because of regression of another bug. And now, in Viprions (both native and vCMP) it behaves like this:

- Primary blade: slotX is missing from LTM logs, but the hostname is logged.
- Secondary blades: the hostname replaced by slotX.

So, as VELOS tenants inherited the same BIG-IP code, it applies to them as well. So, what you see in the log examples, is the behavior (first line is from Primary slot showing just hostname and second line from Secondary showing Slot number only)

Mar  9 13:03:26 lb009.i.etech.sk notice clusterd[5838]: 013a0006:5: mcpd tells us that config is being saved;  incrementing this blade's revision and saving cluster config
Mar  9 13:03:26 slot2 notice mcpd[8359]: 01071d15:5: adjust_admin_ips: old_mbrAddrs of slot: 2: 10.1.0.152/255.255.0.0

We can add the slot number to the line using the clustered-message-slot db key (done on tenant side):
# tmsh modify sys syslog clustered-message-slot enabled

And it will look like this on primary slot ("hostname level slotX"):

Mar 24 03:02:20 VIP2400-R38-S15.sea.pslab.local info slot2 bigstart[4464]: Start 2 bigd processes
Mar 24 03:02:20 VIP2400-R38-S15.sea.pslab.local info slot2 bigd.start[4468]: Execing bigd: /usr/bin/bigd bigd.1 -P 2 -I 1
Mar 24 03:02:20 VIP2400-R38-S15.sea.pslab.local info slot2 bigd.start[4467]: Execing bigd: /usr/bin/bigd bigd.0 -P 2 -I 0

And on secondary we have twice the slotX:
Mar 24 03:02:22 slot4 info slot4 bigd.0[23917]: 0114002b:6: HA daemon_heartbeat bigd enabled.
Mar 24 03:02:22 slot4 info slot4 bigd.1[23918]: 0114002b:6: HA daemon_heartbeat bigd enabled.
