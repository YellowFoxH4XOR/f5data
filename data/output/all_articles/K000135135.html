Description

One of the requests triggers violation "Bad multipart parameters parsing".

 

Environment

  • HTTP Compliance Sub Violations Enabled
  • Request is Blocked

 

Cause

The payload is:

 

----------1111111111\r\nContent-Disposition: form-data; name="x"\r\n\r\nx\r\n----------1111111111--

 

which with the CR, LF, would look like:

 

----------1111111111

 

Content-Disposition: form-data; name="x"

 

 

x

 

----------1111111111--

 

The issue here is that the CRLF characters are not actually present.

 

The string contains the printable characters"\" "r" "\" "n" 0x5c 0x72 0x5c 0x6e and it *not* the actual CRLF sequence of 0x0d 0x0a.

 

Therefore, ASM sees this as a violation.

 

Recommended Actions

Many systems will display payload with CRLF characters replaced by \r\n in order to avoid line breaks on display and some systems can perform the replacement in the other direction as well such as BIG-IP monitor send strings.

 

However, when replaying these through HTTP ( such as Splunk or Postman ) these must reverted back to actual CRLF characters to represent what was actually originally sent.

 

Additional Information

Note from RFC 9110: 8.3.3. Multipart Types

 

MIME provides for a number of "multipart" types -- encapsulations of one or more representations within a single message body. All multipart types share a common syntax, as defined in Section 5.1.1 of [RFC2046], and include a boundary parameter as part of the media type value. The message body is itself a protocol element; a sender MUST generate only CRLF to represent line breaks between body parts.

 

For more details from RFC2046: https://www.rfc-editor.org/rfc/rfc2046#section-5.1.1 [Page 19]
