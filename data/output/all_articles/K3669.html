Topic

This article applies to BIG-IP 9.x through 10.x. For information about other versions, refer to the following article:

  • K13284: Overview of management interface routing (11.x - 14.x)

The Traffic Management Microkernel (TMM) controls all of the BIG-IP switch ports (TMM interfaces), and the underlying Linux operating system controls the management interface. The BIG-IP management interface processes administrative traffic only. The TMM interfaces process both load balanced traffic and administrative traffic.

Traffic types

The BIG-IP system processes the following types of traffic:

  • Load balanced traffic

    Inbound connections to a BIG-IP self IP address or a virtual server address that arrive on a TMM interface are processed by TMM.

  • Inbound administrative connections

    Inbound connections sent to the BIG-IP management IP address that arrive on the management interface are processed by the Linux operating system. Inbound connections sent to the BIG-IP self IP addresses that arrive on a TMM interface are processed by TMM. If the self IP address is configured to allow a connection to the destination service port, TMM hands the connection off to the Linux operating system, which then processes the connection request.

  • Outbound administrative connections

    Outbound connections sent from the BIG-IP system by administrative applications (SNMP, SMTP, SSH, NTP, etc.) are processed by the Linux operating system. These connections may use either the management address or a self-IP address as the source address. The BIG-IP system compares the destination address to the routing table to determine the interface through which the BIG-IP system routes the traffic.

    Note: This behavior applies to only unsolicited outbound traffic--traffic that is not in response to a request originated by a remote host. A response to a request originated by a remote host is returned to the last MAC address traversed by the inbound request.

    Note: You can configure a health monitor to send probes by way of the management network, but F5 strongly discourages this configuration, because the management network is not intended for production traffic. F5 strongly recommends that you have the pool members/nodes reside on a network that is reachable by way of TMM interfaces so that health monitor probes are sent by way of TMM interfaces.

BIG-IP routing tables

The BIG-IP routing table actually consists of two routing subtables: the TMM routing subtable and the management routing subtable. Routes in the TMM subtable are defined with a lower metric than routes in the management subtable.

For traffic sourced from the management address, management routes are preferred over TMM routes, and the most specific matching management route is used. If no management routes match, the most specific matching TMM route is used.

Traffic sourced from a TMM (self IP) address always uses the most specific matching TMM route. Traffic sourced from a TMM address never uses a management route.

Note: When TMM is not running, the TMM addresses are not available, and all TMM routes are removed. As a result, when TMM is not running, all outbound administrative traffic uses the most specific matching management route.

Some anomalies have been noted for some BIG-IP versions in the implementation of the combined routing table, as noted in the following articles:

  • K10239: Unsolicited management traffic may not use the intended management address or management routes
  • K7017: The BIG-IP ntpd process is unable to communicate with the NTP server
  • K8571: The route to the local management subnet is not configured in the WANJet management route table
  • K9143: The Linux IP routing policy rule for route lookups on the management port is missing
  • K9188: SNMP startup traps may not always be sent
  • K10710: BIND responses may use management interface with a 127.0.0.1 source address

Managing routing functions

Use the following commands to manage routing information.

Viewing, deleting, and adding management IP addresses

  • To view the management IP address and netmask, type the following command:

    bigpipe mgmt show

  • To delete an existing management IP address, use the following command syntax, replacing <address> with the management IP address:

    bigpipe mgmt <address> delete

  • To add a new management IP address, use the following command syntax, replacing <address> with the management IP address and replacing <netmask> with the network mask:

    bigpipe mgmt <address> netmask <mask>

Viewing routing tables

  • To view existing management routes, type the following command:

    bigpipe mgmt route show

  • To view all existing routes, type the following command:

    bigpipe route show

  • To view all existing routes in the Linux kernel routing table, type the following command:

    netstat -rn

    Note: The management interface MGMT is represented by the netstat command as eth0 in the command output.

  • To view routes in the routing table, main, type the following command:

    ip route show table main

  • To view the management routing table (table 245) routes, type the following command:

    ip route show table 245

Adding and deleting management routes

F5 recommends that you add static routes for management traffic whose destination does not match the directly-connected management network. This configuration is useful when handling SNMP traffic that is directed to an SNMP Manager that resides on another network, which is accessible only through the management network or other network services hosted on networks that are not accessible by way of the TMM interfaces.

Note: If a destination address does not match that of the network of the management interface, and no static route is specified, the system uses the default gateway that is specified for use by TMM.

  • To add a static route for traffic to use the management network, type the following command:

    bigpipe mgmt route <destination network> netmask <netmask> gateway <management gateway>

  • To delete an existing static route, type the following command:

    bigpipe mgmt route <destination network> delete

    Note: Any configuration changes must be saved to the file in the event of a reboot. To do so, type the bigpipe base save command.

Viewing, deleting, and adding IP rules

  • To view existing IP rules, type the following command:

    ip rule show

  • To delete an existing IP rule, use the following command syntax, replacing <address> with the management address:

    ip rule del from <address>

  • To add an IP rule to the management routing table, use the following command syntax, replacing <address> with the management address:

    ip rule add from <address> pref 245 table 245

    Note: This command adds the management address to the management routing table with a route metric of 245.

Troubleshooting management interface routing

If the BIG-IP system does not route traffic through the management interface as described in this article, and you have ruled out the anomalies previously listed, troubleshoot the issue as follows:

Note: The following troubleshooting steps include running the bigstart restart command. Running bigstart restart disrupts load-balanced traffic, and you should run it only during a maintenance window.

  • View the existing IP rules. Verify that the IP rules match the management address. If they do not match, delete and re-create the rule.
  • View the management routing table. Verify that the IP address and netmask match the management address. If they do not match, type the following command:

    bigstart restart

    The BIG-IP system should use the correct management address after the system daemons restart.
  • View the Linux kernel routing table and verify that the route for the management address exists. If the management address is not listed, type the following command:

    bigstart restart

    After the system daemons have restarted, the BIG-IP system should use the correct management address.
  • View the table of cached routes by typing the following command:

    netstat -C -nr

  • Verify that the cached route for the management address is correct. If it is not correct, type the following command:

    bigstart restart

    After the system daemons have restarted, the BIG-IP system should use the correct management address.
