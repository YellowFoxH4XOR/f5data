Known Issue

iRules that use the CACHE::enable command may mistakenly cache objects, and may return the cached objects in response to subsequent requests.

This issue occurs when all of the following conditions are met:

  • An iRule associated with the affected virtual server uses the CACHE::enable command in an HTTP_REQUEST event.
  • Either of the following iRule commands occurs in the HTTP_REQUEST event of the same iRule as the CACHE::enable command or in the HTTP_REQUEST event of a different rule that is associated with the affected virtual server.
    • HTTP::respond
    • HTTP::redirect
  • A single HTTP request triggers both CACHE::enable and either HTTP::respond or HTTP::redirect.
  • Multiple HTTP requests are processed by the affected virtual server on the same TCP connection.

When an HTTP request triggers CACHE::enable and either HTTP::respond or HTTP::redirect, a second HTTP request on the same TCP connection causes the CACHE::enable command to erroneously force the server response to the HTTP cache. Subsequent requests on new TCP connections for the same object will receive the cached data.

The following iRule contains an example of the CACHE::enable and HTTP::respond commands occurring during the HTTP_REQUEST event, which would cause this issue:

ltm rule Rule_ID382373 {
when HTTP_REQUEST {
if {[HTTP::request_num] == 1} {
CACHE::enable
HTTP::respond 200 content <HTML>MyRule</HTML> "Content-Type" text/html
}
}
}

Impact

Data may be incorrectly cached, and subsequent requests may receive previously-cached response data.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • Data that should not be cached according to the HTTP profile is present in the HTTP Cache.

    You can inspect the contents of the cache using the following command syntax, appropriate to your version:
    • 10.x and 11.x

      tmsh show ltm profile ramcache <profile name>

    • 9.x

      bigpipe profile http <profile name> ramcache entry show all

    Note: By default, the tmsh command displays only a limited number of entries per TMM instance. You can use the exact, host, max-response, or uri qualifiers to display additional entries or search the cache for specific objects. For more information, refer to the Traffic Management Shell (tmsh) Reference Guide. For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

  • Data cached from previous connections is served to subsequent connections.

    Note: You may need tools such as HTTP Watch and tcpdump to inspect and verify the data in the TCP connections. For more information on capturing TCP packets, refer to the Supplemental Information section, following.

Workaround

To work around this issue, you can modify your iRules in one of the following ways:

Impact of workaround: None.

  • F5 recommends that you modify any affected iRule or group of iRules so that no iRule (or group of iRules) can invoke both CACHE::enable and either HTTP::respond or HTTP::redirect for the same HTTP request.
  • You can modify an affected iRule to include the TCP::close command after calling the HTTP::respond or HTTP::redirect commands. This modification closes the TCP connection, ensuring that subsequent HTTP requests are processed on a new TCP connection.

For more information, refer to HTTP_REQUEST and TCP::close on F5 Cloud Docs.
