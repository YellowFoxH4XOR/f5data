Description

NGINX converts authentication subrequest responses other than 2xx, 401, and 403 into HTTP 500 responses. The original upstream status, such as 429 or 502, must be captured and handled separately.

Environment

  • NGINX Plus
  • auth_request authentication subrequests

Cause

This behavior is by design. The auth_request module translates authentication subrequest responses other than 2xx, 401, and 403 into an HTTP 500 response.

Answer/Recommended Actions

Use auth_request_set to save the original upstream status, then use an error_page directive to redirect the generated 500 response to an internal named location.

 

  1. Configure the authentication subrequest and capture its upstream status: 
    location /login/ {
    error_page 500 = @my_error_page;
    auth_request /auth;
    auth_request_set $actual_status $upstream_status;
    ...
}
  2. Create an internal error location that returns selected status codes: 
    location @my_error_page {
    default_type text/plain;
    if ($actual_status = 429) {
        return 429;
    }

    if ($actual_status = 502) {
        return 502;
    }
    return 500 "Unsuccessful Response(s) From The Upstream Server(s): $actual_status ";
}
  3. Add conditional handling for any additional single status codes that should be returned to the client.

Additional Information

  • A successful upstream response such as 200 does not trigger error_page handling because the authentication request succeeds.
  • When $actual_status contains one matching unsuccessful status, such as 429 or 502, the corresponding status can be returned to the client.
  • When $actual_status contains multiple status codes, such as 502, 429, or contains an unsuccessful status without a corresponding condition, the configuration returns 500 and includes the upstream status value in the response body.
  • The conditional comparisons shown above are intended for exact single-status matches.
