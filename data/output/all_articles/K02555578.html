Description

When a program is stuck/uncharacteristically slow, or shows an error previously not seen previously, strace can reveal what sequence of operations lead to the incorrect behaviour.

Environment

  • BIG-IP

Cause

None

Recommended Actions

You should only perform the following troubleshooting under guidance/instruction from F5 support.

Using strace is the most convenient when we want to find out what files affect a program, for example, when its error reporting is too brief, or to discover which part of it is taking too long.

However, it's typically less useful when the program functionality we want to inspect is depending on encrypted operations - for example if the error is about the TLS protocol, using a strace may not be sufficient to completely understand what the program is doing.

The strace output file will contain a sequence of operations, sometime intermixed from different processes prefixed by their PIDs, of the most elementary operations on Unix, called syscalls.

The syscalls are the lowest level about how a program or the operating system can talk to the kernel, and it sometimes needs significant effort to parse. For example, the handling of memory allocation is typically quite opaque. Most program's memory management is actually built on even more arcane operations, such as brk() or mmap() to mark memory areas as used in a specific way.

Sometimes kernel version specific internals will be revealed, such as a suffixed number or version appended to the syscall name.

The reason for this that a system call, once implemented, cannot change its behaviour, as old programs will still depend on how it worked. They are part of the ABI - the Application Binary Interface.

Some extensions will be implemented by implementing a new system call with a similar name. This has happened with the mmap() system call, later versions can be seen as mmap2(), sometimes both in the same program, or a 64-bit version of a system call might be used from a 32-bit program. This is the case when the program is created to run on an earlier, 32-bit Intel architecture, but is prepared to fully handle files larger than 2^32 bytes, which originally the architecture was not capable of - but really, files larger than 4 Gigabytes are quite common these days.

Commonly Required strace Flags

We often need a basic set of flags to make sure the appropriate level of detail is collected about an incorrectly behaving program.

These are all important to make sure we're not missing most of the details handled by other programs executed from inside the traced one,
allowing to discover how long an operation took, and what it's parameters were.

The two basic ways of invoking strace are different whether the program is already running, or if we want to start a new program, and inspect it from the first moment.

The output file in /var/tmp will need to be reviewed or submitted to us to research further.

strace -f -Tttv -o /var/tmp/mcpdstrc.out -s 200 -p $(pgrep -f '/usr/bin/mcpd')

strace -f -Tttv -o /var/tmp/lsstrace.out -s 200 bash -c ls /tmp

-f - will follow child processes (across fork/clone)
-T - will show the time taken for the system call itself
-tt - will prefix each line by the starting time (in microsecond precision)
-v - do not shorten some structures displayed (which should be generally helpful, but will obscure details with older strace running under newer kernels)
-s 200 - show at least 200 bytes of strings (path names, error messages), the default is too short
-o FILENAME - the filename to log the trace output, without interfering with standard output and standard error used by the program
-p PID - when the program we are interested in is already running, we typically use another way to find the PID we want to use, here, by pgrep

A Simple Program

For example, this is how the bash shell executes an ls command:

# strace -f -Tttv -o /var/tmp/lsstrace.out -s 200 bash -c ls
[ Process PID=8252 runs in 32 bit mode. ]

What we cannot see is how the PATH contents are split - that's a basic string operation, the programs do not need to involve the kernel with that.

This is everything ls does indeed! the getdents64() system call is used to fetch the contents of the "." directory opened as file descriptor 3 above.

The second getdents64() returns zero - no further entries. The directory descriptor is now closed, some memory is reserved via mmap2()/mmap() and this area is used to build the listing (in this case, a single filename), it's written to the standard output and that's it.

Everything done before this is setting up the system environment to locate the shared libraries to set up networking or multi-threading which is not very relevant for such a simple program.

Multiple Processes

It gets more and more complicated when several processes communicate. When one program is executed, it can simply be loaded into the current process, but when there are more processes that depend on each other's operation, a single parent process will typically stay in memory, supervising the child processes. The setting up of those might look like this:

8949  08:27:59.991160 execve("/bin/bash", ["bash", "-c", "ls|grep /"], ...) = 0 <0.000097>
8949  08:27:59.994142 clone(child_stack=0, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, child_tidptr=0) = 8950 <0.000031>
8949  08:27:59.994329 clone( <unfinished ...>
8949  08:27:59.994371 <... clone resumed> child_stack=0, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, child_tidptr=0) = 8951 <0.000039>

Here, we can see two clone() being run, both ending up with a new PID, 8950 and 8951, both of them will be executing a different process in a pipeline. bash itself will stay in memory as PID 8949.

We can also observe, that sometimes the operation is split into two, when a task is switched during a system call, it will be reported as unfinished. Depending on the operation, the arguments might be reported at the initial attempt, or the second (last) attempt, with the result of the completion.

8950  08:27:59.995360 execve("/bin/ls", ["ls"], ...
8951  08:27:59.995512 execve("/bin/grep", ["grep", "/"], ...
8950  08:27:59.995596 <... execve resumed> ) = 0 <0.000160>
8951  08:27:59.995683 <... execve resumed> ) = 0 <0.000091>

Another important part is how the parent process can find if the child processes completed. This is done by the wait()/waitpid() system call:

8951  08:27:59.998287 read(0,  <unfinished ...>
8951  08:27:59.998296 <... read resumed> "", 32768) = 0 <0.000006>
8951  08:27:59.998350 exit_group(1)     = ?
8950  08:27:59.998355 exit_group(0)     = ?
8949  08:27:59.998389 <... waitpid resumed> [{WIFEXITED(s) && WEXITSTATUS(s) == 1}], 0) = 8951 <0.003726>
8949  08:27:59.998399 waitpid(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0) = 8950 <0.000003>
8949  08:27:59.998475 --- SIGCHLD (Child exited) @ 0 (0) ---
8949  08:27:59.998519 exit_group(1)     = ?

Here, grep saw no further inputs from read() (zero means EOF - end of file), and exited with the return code of 1 (which is the way for grep to report that no match was found).

bash, in PID 8949 will keep track of the child processes run, and will continue to run waitpid() until it finds all the children have completed. In this example grep returned earlier, with the exit status/return code of 1, then ls, with zero, and as no processes left, it reported the most serious exit code as it's on exit status.
