Topic

You should consider using this procedure under the following conditions:

  • You are configuring an IPsec Internet Key Exchange (IKE)v1 tunnel between a BIG-IP system and an Amazon Web Services (AWS) virtual private cloud (VPC).

    Note: This article does not apply to scenarios in which the IPsec peer is within the AWS cloud.

    Note: The my-id-value and peers-id-value settings are mandatory configuration elements for IKEv2 tunnels. The symptoms described in this article do not apply to IKEv2 tunnels.

  • You experience intermittent IPsec IKEv1 tunneling problems between the BIG-IP system and an AWS VPC peer.
  • You experience similar tunneling problems when configuring an IPsec IKEv1 tunnel between the BIG-IP system and non-AWS VPC peers.

Description

To maintain reliable IPsec connectivity between a BIG-IP system and an AWS VPC gateway peer, you must configure the Presented ID Value (my-id-value) and the Verified ID Value (peers-id-value) options. These options are configuration elements of the IKE peer (ike-peer) configuration object. If you do not configure these elements, the tunnel may fail to establish or re-establish when the BIG-IP system is the responder.

IPsec tunnel failures may exhibit the following symptoms:

  • The BIG-IP system establishes an Internet Security Association and Key Management Protocol Security Association (ISAKMP-SA) but not an IPSec Security Association (IPsec-SA). If this occurs, the system logs a message to the /var/log/racoon.log file which appears similar to the following:

    INFO: ISAKMP-SA established 127.0.0.1[500]-10.14.1.1[500] spi:1b190a4b52377457:d0feefec8ead6cca

    Note: The 127.0.0.1 address in the previous example indicates that the BIG-IP system is the responder.

  • If Dead Peer Detection (DPD) is enabled, as F5 recommends, the system quickly determines that the AWS peer is dead. When this occurs, the system logs a message to the /var/log/racoon.log file which appears similar to the following:

    INFO: DPD: remote (ISAKMP-SA spi=1b190a4b52377457:d0feefec8ead6cca) seems to be dead. (fail count:10)

  • The system deletes the ISAKMP-SA. If this occurs, the system logs a message to the /var/log/racoon.log file which appears similar to the following:

    INFO: ISAKMP-SA deleted 127.0.0.1[500]-10.14.1.1[500] spi:1b790a4b52377457:d0feefec8ead6cca

  • During a period of failure, the AWS peer may send the BIG-IP system an ISAKMP PAYLOAD-MALFORMED notification. This message may not appear in the /var/log/racoon.log file because the racoon daemon acts as though the daemon is in the process of establishing an IPSec-SA with the peer and does not expect an unencrypted packet from the peer. As a result, the system may log an ambiguous message to the /var/log/racoon.log file which appears similar to the following:

    ERROR: none message must be encrypted

    If this occurs, a packet capture with a UDP port 500 filter may reveal an unencrypted ISAKMP packet with a PAYLOAD-MALFORMED notification message which appears similar to the following:

    Internet Protocol Version 4, Src: 10.14.1.1, Dst: x.x.x.x
    User Datagram Protocol, Src Port: 500 (500), Dst Port: 500 (500)
    Internet Security Association and Key Management Protocol
        Initiator SPI: 1b190a4b52377457
        Responder SPI: d0feefec8ead6cca
        Next payload: Notification (11)
        Version: 1.0
        Exchange type: Informational (5)
        Flags: 0x00
            .... ...0 = Encryption: Not encrypted
            .... ..0. = Commit: No commit
            .... .0.. = Authentication: No authentication
        Message ID: 0x3df54941
        Length: 40
        Type Payload: Notification (11)
            Next payload: NONE / No Next Payload  (0)
            Payload length: 12
            Domain of interpretation: ISAKMP (0)
            Protocol ID: ISAKMP (1)
            SPI Size: 0
            Notify Message Type: PAYLOAD-MALFORMED (16)
            Notification DATA: <MISSING>

Prerequisites

You must meet one of the following prerequisites to use these procedures:

  • You have administrative access to the TMOS Shell (tmsh).
  • You have administrative access to the Configuration utility.
  • Configuring the Presented ID Value (my-id-value) and Verified ID Value (peers-id-value) settings using tmsh
  • Configuring the Presented ID Value (my-id-value) and Verified ID Value (peers-id-value) settings using the Configuration utility

Configuring the Presented ID Value (my-id-value) and Verified ID Value (peers-id-value) settings using tmsh

To specify the my-id-value and peers-id-value for an existing ike-peer configuration object, perform the following procedure:

Note: The my-id-value and peers-id-value values do not establish IP connectivity; however, the system presents and verifies them during the ISAKMP (phase1) negotiation.

Impact of procedure: Performing the following procedure should not have a negative impact on your system. However, F5 recommends testing any such changes during a maintenance window with consideration to the possible impact on your specific environment.

  1. Log in to tmsh by typing the following command:

    tmsh

  2. Modify the ike-peer object configuration with the desired my-id-value and peers-id-value values using the following command syntax:

    modify net ipsec ike-peer <ike peer profile> my-id-type address my-id-value <x.x.x.x> peers-id-type address peers-id-value <y.y.y.y>

    In the previous command syntax example:

    • <ike peer profile> is the name of the ike-peer configuration object you want to modify.
    • <x.x.x.x> is the IP address to present as the identity for the BIG-IP system.
    • <y.y.y.y> is the IP address that the BIG-IP system receives and verifies for the remote peer.

    For example, to modify an ike-peer object named aws-peer with a my-id value of 1.1.1.1 and a peers-id-value of 2.2.2.2, type the following command:

    modify net ipsec ike-peer aws-peer my-id-type address my-id-value 1.1.1.1 peers-id-type address peers-id-value 2.2.2.2

    Important: As long as the configuration is the same on both peers, the ID values are arbitrary. F5 recommends that you configure the x.x.x.x address shown in the previous example so that it represents the IP address that the AWS peer uses as the remote address to BIG-IP system. If the BIG-IP system uses network address translation (NAT), use the IP address that the AWS peer uses as the source IP of the ISAKMP packets, not the IP address local to the BIG-IP system.

  3. Save the configuration by typing the following command:

    save /sys config

Configuring the Presented ID Value (my-id-value) and Verified ID Value (peers-id-value) settings using the Configuration utility

To specify the Presented ID Value and Verified ID Value for an existing ike-peer configuration object, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system. However, F5 recommends testing any such changes during a maintenance window with consideration to the possible impact on your specific environment.

  1. Log in to the Configuration utility.
  2. Navigate to Network > IPsec > IKE Peers.
  3. Click the name of the desired IPsec IKE peer.
  4. Locate the Common Settings section.
  5. Select Address from the Presented ID Type menu.
  6. Select Override from the Presented ID menu.
  7. In the Presented ID Value field, enter the IP address to present as the BIG-IP system identity. For example, 1.1.1.1.
  8. Select Address from the Verified ID Type menu.
  9. Select Override from the Verified ID menu.
  10. In the Verified ID Value field, enter the IP address for the remote peer that the BIG-IP system should expect to receive and verify. For example, 2.2.2.2.
  11. Click Update to save the configuration.

    Important: As long as the configuration is the same on both peers, the ID values are arbitrary. F5 recommends that you configure the x.x.x.x address shown in the previous example so that it represents the IP address that the AWS peer uses as the remote address to BIG-IP system. If the BIG-IP system uses NAT, use the IP address that the AWS peer uses as the source IP of the ISAKMP packets, not the IP address local to the BIG-IP system.
