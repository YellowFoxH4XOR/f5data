K000157362: WebUI unexpectedly requires client certificate for login

Description

When attempting to access the BIG-IP LTM WebUI, users may encounter the error message: "Access to <hostname> was denied. <hostname> didn’t accept your login certificate, or one may not have been provided. Try contacting the system admin. ERR_BAD_SSL_CLIENT_AUTH_CERT." This issue results in the WebUI unexpectedly requiring a client certificate for login, even though no known configuration changes were made to require client certificate authentication. The problem persists across reboots, configuration reloads, and license reactivations, preventing administrative access to the BIG-IP management interface.

Environment

  • Product: BIG-IP LTM
  • Version: 17.1.1
  • Affected Component: WebUI (Management Interface)
  • Configuration:
    • sys httpd ssl-verify-client set to "no" (default)
    • auth cert-ldap system-auth sso set to "on"
  • No recent explicit changes to client certificate authentication settings
  • Issue persists after reboot, config reload, and license reactivation

Cause

The underlying cause is the sso (Single Sign On) setting being enabled in the system-auth configuration. When SSO is enabled (auth cert-ldap system-auth sso on), the BIG-IP device automatically sets SSLVerifyClient require in the Apache configuration (/run/config/httpd.conf.d/ssl.conf`)) causing the WebUI to require a client certificate for login).

Recommended Actions

To resolve the issue and disable the requirement for a client certificate when accessing the WebUI:

 

  1. Log in to the BIG-IP device using an alternative method (such as SSH or console access).
  2. Run the following commands to disable SSO for system-auth:
    tmsh modify auth cert-ldap system-auth sso off

tmsh save sys config
    Verify that you can now access the WebUI without being prompted for a client certificate.
  3. Confirm that the change persists after a reboot or configuration reload.

Additional Information

The ssl-verify-client db variable for sys httpd may still show "no", but enabling SSO at the system-auth level overrides this by modifying the Apache configuration directly.

This behavior is expected when SSO is enabled; disabling SSO restores standard WebUI authentication.

The issue is not caused by a bug, but by the interaction between SSO and client certificate requirements in the management interface.
