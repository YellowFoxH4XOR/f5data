Description

This article outlines the general process for fixing some common SSLO block corruption issues, which can show up as an error message in the SSLO admin GUI mentioning that the mcpd config does not matching the SSLO config, or a similar message. 
Please note that the presence of such a message in itself does not necessarily indicate that the SSLO config blocks are corrupted.

Please also note that in general, it is much easier to restore the SSLO box from a "known good" UCS (or simultaneously restore a HA pair from "known good" UCSs) than to manually try to fix the dg-data, if that is an option.

If you are in doubt about any of the steps in this article, please open a case with F5 Support who can guide you through the processes discussed in the article if applicable. 

 

Environment

BIG-IP SSLO


Cause

SSLO iApp block corruption

 

Recommended Actions

Please keep in mind that dg-data is meant to be a JSON object so proper JSON syntax must be followed. 

When fixing the dg-data we will be working with the value array. This is an array of objects with the following properties:
    - type: What type the object is
    - name: The name of the object
    - data: another json object that just contains the selflink to the object in the block data
    - parent: All other objects that contain a reference to this object
    - references: All other objects that this object contains a reference to
    - inactiveReferences: Same as references but for objects that are inactive

The parent, references, and inactiveReferences all have the same format. They are arrays of objects that contain 
    - name: the name of the referenced object
    - type: the type of the referenced object

In this example the service chain is a part of the ssloP_example security policy so there is an entry for the ssloP_example security policy in the parents array. 
The service chain also uses two different services ssloS_example_OLD and ssloS_example_NEW and so they have entries in the references array.

When dg-data gets corrupted, it is usually one of the following three problems: 
1. The selfLink is missing, or
2. There are references to objects that have since been deleted, or
3. New objects have not been added properly.


If the selfLink is missing, we can search through the block data for the appropriate block and copy the "working" selfLink from there. 
- Missing selfLinks can be found by simply searching for `selfLink: ""`.

On the other hand, for the other two data corruption types there isn't an easy way to automatically find them. 
Instead someone with knowledge of how the configuration is set up, who knows what things should reference what, needs to look through the dg-data to see what looks incorrect. 
When multiple dg-data are involved, it is helpful to compare each of them to find discrepancies and where the data corruption is.

If there are references to deleted objects, the referenced deleted objects need to be deleted from all the appropriate arrays
- The main value entry
- Any parent or references array

The most common instances of dg-data corruption occur when additional dg-data items are being created, and so the correct information is usually spread out between all of them.
When this is the case, we need to grab the dg-data that seems the most correct to work as a base, and than use the above steps to correct the three common issues for that dg-data.
Finally PATCH the dg-data that was fixed up and DELETE the other dg-data so that only the fixed up dg-data remains.

To delete:
restcurl -u <username>:<password> -X DELETE /shared/iapp/blocks/<dg-data block id>

to patch:
restcurl -u <username>:<password> -X PATCH /shared/iapp/blocks/<dg-data block id> -d "$(cat dgdata.json)"

or if the dgdata.json is too long:
curl -ku <username>:<password> -X PATCH https://localhost/mgmt/shared/iapp/blocks/<dg-data block id> -d @dgdata.json
