Topic

The Fast HTTP profile is a scaled down version of the HTTP profile that is optimized for speed under ideal traffic conditions. The Performance HTTP virtual server combined with the Fast HTTP profile is designed to speed up certain types of HTTP connections and reduce the number of connections opened to the back-end HTTP servers. However, Fast HTTP may not be an appropriate profile to use when network conditions are less than optimal. In most cases, when load balancing Internet-based traffic, F5 recommends the HTTP profile.

Note: For more information about choosing a profile for HTTP traffic, refer to K4707: Choosing a profile for HTTP traffic.

Note: The Performance (HTTP) type virtual server and companion Fast HTTP protocol profile are not configurable using the F5 Application Services 3 Extension (AS3).

Fast HTTP is an appropriate profile to use under ideal traffic conditions. For example, the Fast HTTP profile is optimized for the following traffic conditions:

  • Traffic with few network problems, such as dropped or out-of-order packets
  • Traffic generated by clients and servers that conform to the various HTTP RFCs
  • Traffic with protocol headers contained within a single packet
  • Traffic produced by load generators

Fast HTTP advantages

Using the Fast HTTP profile has the following advantages:

  • Performance enhancements for certain traffic
  • Common features implementations:
    • Fast HTTP combines some of the most commonly used features from the TCP, HTTP, and OneConnect profiles into a single profile that is optimized for network performance.
  • Low latency, CPU usage:
    • The Fast HTTP profile is designed to reduce network latency and system CPU usage.

Fast HTTP limitations

Using the Fast HTTP profile has the following limitations:

  • The Fast HTTP profile requires client source address translation:
    • SNAT is enabled for all Fast HTTP connections. This places a 65,536 connection limit on the number of concurrent TCP connections that can be open between each BIG-IP self IP address configured on the VLAN and the node.
  • The Fast HTTP profile is not compatible with the following advanced features:
    • No IPv6 support
    • No SSL offload
    • No compression
    • No caching
    • No PVA acceleration
    • No virtual server authentication
    • No state mirroring
    • No HTTP pipelining
    • No TCP optimizations
  • HTTP Header Insert of the Fast HTTP profile only supports insertion of a static text HTTP header. The Fast HTTP profile does not perform iRules variable expansion for HTTP Header Insert; this is considered an unnecessary performance hit for the Fast HTTP profile.

    Note: The HTTP profile perform iRules variable expansion for HTTP Header Insert of the HTTP profile.

    If you must use the Fast HTTP profile and an HTTP header insertion requires iRules variable expansion, you can use an iRule in conjunction with the Fast HTTP profile for the virtual server. The iRule uses the HTTP::header insert iRules command and the HTTP_REQUEST event.

  • Limited iRules support:
    • iRules are limited to L4 and a subset of HTTP header operations and pool/pool member selection

      For information about iRules creation and iRules compatibility with the Fast HTTP profile, refer to the BIG-IP Configuration Guide for Local Traffic Management for your specific version. Additionally, for information about iRules functionality and assistance, refer to DevCentral. 

  • Out of order packets are dropped:
    • When the Fast HTTP profile is used for a virtual server, the BIG-IP system drops TCP packets that are received out of order and that contain HTTP headers, forcing the client to retransmit the packets. To process packets received by a Fast HTTP virtual server, the BIG-IP system must be able to read the headers in the proper order.

Fast HTTP operation

Fast HTTP achieves its performance by operating on a packet-by-packet level, and by combining SNAT and OneConnect functionality to all connections.

Packet-by-packet operation

Fast HTTP operates on a packet-by-packet level with the goal of making decisions and forwarding the packet as soon as possible upon receipt of the packet. When a Fast HTTP profile is enabled for a virtual server, the system only buffers enough data to parse packet headers.

SNAT functionality

Fast HTTP automatically applies a SNAT to all client traffic. The SNAT can be either a SNAT pool or the BIG-IP self IP addresses configured for the VLAN that are the closest to the subnet on which the node resides. From the node's perspective, all Fast HTTP-processed connections appear to come directly from the BIG-IP itself, and the source client IP information is not retained.

Note: Performance HTTP virtual server connections may incorrectly use a non-floating self IP address as the source address when connecting to pool members. For more information, refer to K13843: Performance HTTP virtual connections may use the incorrect source IP address when connecting to pool members.

OneConnect functionality

Fast HTTP incorporates basic OneConnect functionality to minimize the latency imparted by TCP three-way handshakes between the BIG-IP system and the node.  Whenever possible, Fast HTTP chooses to re-use an existing connection to a node rather than create a new one.

For example, when a Fast HTTP profile is enabled for the virtual server, the BIG-IP system establishes server-side flows by opening TCP connections to the pool members. When a client makes a connection to the virtual server, if an existing server-side flow to the pool member is idle, the BIG-IP LTM system marks the connection as non-idle and sends client requests over the connection.

If an idle server-side flow is not found, the BIG-IP creates a new server-side TCP connection and sends client requests over the connection.

Note: A Fast HTTP virtual server should never attempt to re-use a connection that is not in the IDLE state.

Note: A Fast HTTP virtual server closes a connection after an HTTP POST response. Refer to K14003: Fast HTTP virtual server connections may be closed after a POST response, for more information.

HTTP/1.0 Requests

By default, Keep-Alive connections are not enabled in HTTP/1.0. With HTTP/1.0 requests, the client sends a Connection: close header to close the TCP connection after sending the request. Both the server and client-side connections that contain the Connection: close header closes after the response is sent.

The Fast HTTP profile uses OneConnect transformations to transform Connection: close headers in client-side requests to Xonnection: close headers on the server side, causing the server to ignore the header. This allows the BIG-IP LTM system to make client requests containing the Connection: close header, such as HTTP/1.0 requests, eligible for connection reuse.

Fast HTTP / HTTP profile comparison

The Fast HTTP profile is optimized for performance under ideal traffic conditions. However, the HTTP profile is recommended when load-balancing Internet-based traffic. The Fast HTTP profile is compared to the HTTP profile in the following table.
