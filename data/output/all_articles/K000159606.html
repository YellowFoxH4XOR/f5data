K000159606: BIG-IP LTM Sends Packets Using Both Physical MAC and MAC Masquerade Address After Adding to GTM Prober Pool

Description

When BIG-IP LTM devices are added to a GTM prober pool and non-bigip monitors are configured at the GTM pool level, the LTM may send health monitor traffic using both the physical MAC address and the MAC masquerade address from the same source IP address. This behavior can cause network issues when:

  • The GTM big3d process initiates health probes to virtual servers local to the same LTM device
  • The virtual server does not have SNAT configured
  • The source IP is a non-floating self-IP address
  • MAC masquerade is configured on the traffic group

Symptoms include:

  • Network devices detecting MAC address changes for the same IP address
  • Sporadic connectivity issues for applications using VIPs on the affected LTM pair
  • Health monitor failures
  • Pool members being marked down intermittently

Environment

  • BIG-IP LTM version 17.1.x
  • GTM configuration with prober pool containing LTM devices as members
  • non-bigip monitors configured at the GTM pool level
  • Virtual servers local to the LTM device without SNAT configuration
  • Traffic group configured with MAC masquerade address

Cause

When an LTM device is added to a GTM prober pool, the big3d process becomes eligible to perform health monitoring of GTM pool members. When non-bigip monitors such as TCP are configured at the GTM pool level, big3d initiates probes using the local non-floating self-IP address as the source.

When these probes connect to a virtual server that is local to the same LTM device, the connection transitions from control-plane to data-plane traffic. Without SNAT configured on the virtual server, packets forwarded to pool members retain the self-IP as the source address. In the data-plane context, these packets use the MAC masquerade address associated with the traffic group rather than the physical MAC address of the interface.

This results in the same source IP address appearing with two different MAC addresses on the network, causing network infrastructure to detect MAC address changes and potentially triggering network instability.

Recommended Actions

  1. Remove monitors from the GTM pool level configuration
  2. Configure health monitoring at the BIG-IP LTM level instead, allowing the local LTM monitors to track virtual server and pool member status
  3. Allow GTM to rely on the LTM's local monitoring results by using bigip monitors at the GTM server level
  4. Verify that health monitoring continues to function correctly after the configuration change
  5. Monitor for any recurrence of MAC address conflicts or connectivity issues

Alternative solutions (if GTM-level monitoring is required):

  • Use SNAT pools or SNAT automap to translate the source address for connections to pool members
  • Remove MAC masquerade

Additional Information

This issue specifically occurs when all of the following conditions are met:

  • LTM devices are members of a GTM prober pool
  • Monitors are applied at the GTM pool level
  • The monitored virtual servers are local to the probing LTM device
  • No SNAT is configured on the virtual servers
  • MAC masquerade is enabled on the traffic group

The behavior is expected from a BIG-IP perspective, as data-plane traffic through a traffic group uses the MAC masquerade address by design. However, this can conflict with network infrastructure expectations when the same IP address appears with multiple MAC addresses.

LTM pairs that were already in the prober pool before monitor configuration changes may not exhibit this behavior immediately, as the issue is triggered by the specific combination of configuration and timing of when devices join the prober pool.

When all members of a BIG-IP DNS pool are BIG-IP LTM virtual servers, you do not need to associate a monitor with the DNS pool. The health monitors on the BIG-IP LTM system provide the status for those virtual servers, and the BIG-IP LTM system's big3d agent uses iQuery to report the BIG-IP LTM virtual server status to the BIG-IP DNS system.
