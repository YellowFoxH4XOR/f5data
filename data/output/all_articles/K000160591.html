Description

OpenShift reinstall or rebuild is failing repeatedly, with messages similar to the following observed in /var/log/openshift.log on the active controller:

PLAYBOOK: uninstall.yml ********************************************************
...
fatal: [controller-1.chassis.local]: FAILED! => {"changed": false, "cmd": "systemctl reset-failed", "delta": "0:00:25.032506", "end": "2026-03-19 18:06:13.276833", "msg": "non-zero return code", "rc": 1, "start": "2026-03-19 18:05:48.244327", "stderr": "Failed to execute operation: Connection timed out", "stderr_lines": ["Failed to execute operation: Connection timed out"], "stdout": "", "stdout_lines": []}
fatal: [controller-2.chassis.local]: FAILED! => {"changed": false, "cmd": "systemctl reset-failed", "delta": "0:00:25.034935", "end": "2026-03-19 18:06:14.067173", "msg": "non-zero return code", "rc": 1, "start": "2026-03-19 18:05:49.032238", "stderr": "Failed to execute operation: Connection timed out", "stderr_lines": ["Failed to execute operation: Connection timed out"], "stdout": "", "stdout_lines": []}
Ansible Failed /usr/bin/ansible-playbook -vv --flush-cache -i /tmp/omd/etc_ansible_cluster_delete /usr/share/ansible/openshift-ansible/playbooks/adhoc/uninstall.yml

These messages indicate that a systemctl reset-failed command returned a failure (non-zero) exit status on both controllers, due a timeout after 25 seconds.

Executing a systemctl status --all | head -5 command shows a large number of units in a failed state, similar to the following example:

● controller-2.chassis.local
    State: degraded
     Jobs: 0 queued
   Failed: 64979 units                                                          <--
    Since: Tue 2024-06-04 16:50:53 PST; 1 years 9 months ago

Environment

  • VELOS cluster
  • OpenShift rebuild
  • F5OS-C version prior to 1.8.0

Cause

The systemctl reset-failed command times out after 25 seconds due to the accumulation of a large number of failed systemd ccsync service units. The large number of failed service units is a known issue that can occur on versions prior to F5OS-C 1.8.0. This problem will typically be observed on VELOS controllers with high uptime (hundreds of days).

Recommended Actions

Reboot each VELOS system controller in turn - standby first, then fail over to it, then reboot formerly active.

Trigger another OpenShift rebuild after the reboots and monitor the progress in the openshift.log on the active controller:

tail -F /var/log/openshift.log

Additional Information

The design of ccsync has been changed from F5OS-C 1.8.0 onwards so the accumulation of failed ccsync service units should no longer occur.
