Description

Connections remain visible in the connection table after forcing a DNS pool member offline and deleting connections on a BIG-IP LTM DNS virtual server (VIP) in an L2 nPath (Direct Server Return/DSR) deployment. This leads to confusion about whether real client traffic is still reaching the backend server during maintenance, even after running connection deletion commands.

Common symptoms:

  • Connections remain after tmsh delete sys connection commands
  • tmsh show sys connection ss-server-addr <backend_IP> continues to show entries
  • GUI and CLI show inconsistent connection counts
  • tcpdump filtering by backend IP does not show expected traffic

Environment

  • BIG-IP LTM 17.5.1
  • L2 nPath (DSR) deployment
  • Virtual server with translate-address disabled and translate-port disabled
  • Backend servers configured with loopback address
  • FastL4 profile with PVA acceleration enabled
  • UDP/DNS traffic (port 53)
  • DNS health monitors assigned to pool members
  • Source address persistence configured

Cause

In L2 nPath (DSR) deployments, BIG-IP forwards traffic to backend servers by rewriting only the Layer 2 (MAC) address, leaving the IP header unchanged. As a result:

  • Real client-to-backend connections are not tracked on the server-side connection table, because the destination IP remains the VIP address.
  • Connections visible via tmsh show sys connection ss-server-addr <backend_IP> after force offline are health monitor traffic and control-plane/system DNS traffic (connection type: self), not real client data-plane connections.

Answer/Recommended Actions

To verify real client connections in an L2 nPath deployment:

  1. Use the client-side connection table command:
    tmsh show sys connection cs-server-addr <VIP_IP>
    Real client connections will show connection type any with the backend server's MAC address as the Server Nexthop.
  2. To confirm no new traffic is sent to the offline pool member, use MAC address-based tcpdump filtering (required because PVA acceleration prevents IP-based filtering):
    tcpdump -venni 0.0:nnnp ether host "<backend_MAC_address>" and not host <self_IP> -c 100
    • Obtain the backend server's MAC address from: tmsh show net arp
    • If packets appear with the destination MAC of the offline backend and direction OUT, traffic is still being forwarded to that server.
  3. To delete persistence records for the offline pool member:
    tmsh delete ltm persistence all-records mode source-address node-addr <backend_IP>
  4. To delete client-side connections (note: this affects all connections to the VIP, not just those going to the offline member):
    tmsh delete sys connection cs-server-addr <VIP_IP>

Additional Information

  • In L2 nPath (DSR) deployments, BIG-IP only modifies the Layer 2 MAC address when forwarding traffic to the backend. The destination IP remains the VIP address. Backend servers accept the traffic because the VIP IP is configured as a loopback address.
  • Because the IP header is not modified, the BIG-IP connection table does not record a separate server-side entry with the backend's IP address for real client traffic. Only health monitor connections (which originate from the BIG-IP self-IP) appear in the server-side connection table.
  • The show sys connection ss-server-addr <backend_IP> command will only show health monitor traffic (type: self) in this deployment model — this is expected behavior.
