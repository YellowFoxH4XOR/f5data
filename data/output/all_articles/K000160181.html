K000160181: BIG-IP VE licensing error 51133 on Nutanix AHV/KVM with UEFI or newer SMBIOS; workaround: Legacy boot or pc-i440fx-8.0

Type
Support Solution
Published
2026-02-27
Updated
2026-09-27
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1, 17.5.0
Source
https://my.f5.com/manage/s/article/K000160181

Description

Licensing BIG-IP VE can fail with registration error 51133 and messages indicating the platform cannot be detected or recognized. This has been observed on Nutanix AHV (Acropolis), where UEFI is the default VM boot mode, and on KVM/libvirt hosts (including Ubuntu 24.04 and Proxmox) that expose newer SMBIOS/machine-type versions to the guest. The issue is related to UEFI boot and newer SMBIOS versions not being fully supported by the current licensing platform identification process.

Environment

  • BIG-IP VE versions observed: 17.1.3.1 and 17.5.1.4

  • Hypervisors:

    • Nutanix AHV (example versions reported: AHV 20230302.103003, AOS 6.10.1)

    • KVM/libvirt on Ubuntu 24.04 (default i440fx machine type version is 8.2)

    • Proxmox (similar SMBIOS exposure behavior)

  • VM firmware: UEFI (default on Nutanix AHV), Legacy BIOS

  • Error: Registration error from license server 51133

  • Licensing keys provisioned from MyF5

Cause

On certain hypervisors, the BIG-IP VE licensing process relies on platform identification data that is affected by the VM’s firmware and SMBIOS. When the VM boots with UEFI or when newer SMBIOS/machine-type versions are presented (for example, the default pc-i440fx-8.2 on newer KVM/libvirt stacks), the licensing service may misidentify the guest platform and fail to activate the license, resulting in error 51133.

Answer/Recommended Actions

For Nutanix AHV

  • Use Legacy BIOS boot for the BIG-IP VE VM instead of UEFI.

  • In Nutanix Prism, set the VM Boot Type to Legacy (SeaBIOS) rather than UEFI (OVMF), reboot the VM, and retry online license activation.

For KVM/libvirt (Ubuntu 24.04, Proxmox, and similar)

  • Downgrade the machine type version presented to the guest. The default is pc-i440fx-8.2; the workaround is to drop it down to pc-i440fx-8.0.

  • Example libvirt XML:

    <os>
<type arch='x86_64' machine='pc-i440fx-8.0'>hvm</type>
<boot dev='hd'/>
</os>

  • If UEFI is enabled, switch to Legacy BIOS (SeaBIOS) while this issue persists.

If UEFI is required

  • Coordinate with F5 Support for guidance. Engineering is actively working to add support for UEFI and newer SMBIOS versions in upcoming releases. Until a generally available fix is published, use Legacy BIOS and older machine-type versions as above.

If licensing still fails

  • Open an F5 support case and include:

    • BIG-IP VE version

    • Hypervisor and host OS version

    • VM boot firmware type (UEFI vs Legacy)

    • Machine type string and version (e.g., pc-i440fx-8.2 vs pc-i440fx-8.0)

    • SMBIOS information (if available)

    • Exact license registration error (51133) and any console/log output

    • License registration key(s) and whether activation was online or offline

Additional Information

This behavior has also been commonly observed on Proxmox due to newer SMBIOS exposure. Internal testing indicated the issue persisted on 17.5.1.4 or later in some environments; engineering is tracking fixes for UEFI and newer SMBIOS support in future releases. Consult release notes for updates when available.

    • Use Legacy BIOS on Nutanix AHV.

    • Use an older machine type version (pc-i440fx-8.0) on KVM/libvirt/Proxmox.

If the detected platform is blank (""), verify the VM firmware, machine type/chipset, SMBIOS presentation, and QEMU/KVM, libvirt, oVirt, and RHEL versions.

  • Use pc-i440fx-8.0 for KVM/libvirt/Proxmox where applicable.
  • If UEFI continues to fail, use Legacy BIOS and retry activation.
  • If UEFI is required, provide F5 Support with a current QKView and the complete virtualization configuration.
