K000163607: ClickHouse Memory Exhaustion During TTL Processing in NGINX Instance Manager

Type
Support Solution
Published
2026-10-08
Updated
2026-10-08
Applies to
  • NGINX Products
  • NGINX Instance Manager
Source
https://my.f5.com/manage/s/article/K000163607

Description

NGINX Instance Manager may fail to configure the nms.events table TTL when ClickHouse exhausts its available memory. The failure can cause ClickHouse connection errors, NGINX Instance Manager publish timeouts, unavailable runtime sockets, NATS connectivity errors, and NGINX App Protect WAF policy compilations that remain in progress.

Representative errors include:

MEMORY_LIMIT_EXCEEDED

would use 6.69 GiB

current RSS: 5.90 GiB

maximum: 6.69 GiB

could not set TTL for nms.events table

Environment

  • NGINX Instance Manager 2.22.0.
  • NGINX App Protect WAF policy compilation.
  • NGINX Open Source 1.30.3.
  • RHEL 9.
  • A host with 4 vCPUs and 8 GiB of RAM.
  • High metrics and event ingestion volume.
  • ClickHouse configured with a memory limit close to the host’s usable memory.
  • TTL mutations, background merges, or other ClickHouse operations running concurrently.

An 8 GiB host may report less usable memory because the operating system, kernel, drivers, and system firmware reserve part of the allocated memory.

The NGINX Instance Manager retention settings are configured in:

/etc/nms/nms.conf

Example:

ttl_configs:

- feature: metrics

ttl: 7

- feature: events

ttl: 7

- feature: securityevents

ttl: 32

Cause

The issue is caused by ClickHouse resource exhaustion while processing a TTL mutation for the nms.events table or while performing background data operations.

A minimum-sized host has limited memory available for the operating system, NGINX Instance Manager services, ClickHouse, metrics and event ingestion, TTL processing, and background merges. When ClickHouse reaches its configured memory limit, the TTL mutation may fail. ClickHouse can then become temporarily unavailable, causing dependent NGINX Instance Manager operations to fail.

The exact trigger for ClickHouse connection loss and related NGINX Instance Manager service interruptions may require additional ClickHouse server logs for confirmation.

Recommended Actions

Reduce ClickHouse resource pressure

  1. Configure ClickHouse with a memory limit that leaves sufficient headroom for the operating system and NGINX Instance Manager services.
  2. Do not configure ClickHouse to consume nearly all usable host memory.
  3. Monitor memory usage during high-volume ingestion, TTL processing, background merges, and maintenance operations.
  4. Increase host memory or processing resources if the workload regularly approaches the available limits.
  5. Use retention periods appropriate for the metrics and event volume. A shorter retention period can reduce ClickHouse storage and processing requirements.

Verify incomplete mutations

Use the supported ClickHouse metadata procedure for the deployed NGINX Instance Manager version to identify incomplete mutations for the nms.events table.

The following read-only query can be used when approved for the environment:

SELECT mutation_id, command, create_time, is_done, latest_fail_reason

FROM system.mutations

WHERE database = 'nms'

AND table = 'events'

AND is_done = 0;

No rows should be returned after all mutations have completed. Review any mutation with:

  • is_done = 0
  • A populated latest_fail_reason
  • A memory-limit or resource-related failure

Reapply a failed TTL

If the nms.events TTL mutation failed:

  1. Reduce ClickHouse memory pressure before retrying the operation.
  2. Confirm the intended event-retention period in /etc/nms/nms.conf.
  3. Ensure the NGINX Instance Manager retention value and the ClickHouse table TTL use the same interval.
  4. Reapply the TTL using the supported NGINX Instance Manager procedure for the deployed version.
  5. Materialize the TTL for existing data only when required by the approved procedure.
  6. Verify that the mutation completes successfully and that no stalled mutations remain.

Do not use an example retention interval unless it matches the required retention policy.

Review the ClickHouse memory setting

The ClickHouse configuration is located at:

/etc/clickhouse-server/config.xml

The relevant setting is:

<max_server_memory_usage>...</max_server_memory_usage>

After changing the setting through an approved change procedure, restart ClickHouse during an appropriate maintenance window. The effective setting can be reviewed with:

SELECT name, value, changed

FROM system.server_settings

WHERE name = 'max_server_memory_usage';

Post-remediation monitoring

Monitor the following after remediation:

  • ClickHouse memory consumption.
  • ClickHouse availability on port 9000.
  • Pending, failed, or stalled mutations.
  • NGINX Instance Manager service and runtime socket availability.
  • Configuration publish operations.
  • NGINX App Protect WAF policy compilation status.
  • NATS connectivity.
  • Disk usage and growth of the NGINX Instance Manager event tables.
  • /var/log/nms/nms.log for memory-limit, connection, and mutation errors.

A failed or inactive TTL may delay automatic cleanup of event data. Continue monitoring disk usage until TTL processing completes and the retention policy is confirmed.

Additional Information

  • NGINX Instance Manager requires 8 GB of system memory as a minimum, but the usable memory reported by the operating system is normally lower.
  • ClickHouse memory configuration must leave sufficient headroom for NGINX Instance Manager services and operating-system functions.
  • The NGINX Instance Manager TTL settings and ClickHouse table TTL definitions must remain consistent. Mismatched values may cause the retention policy to be changed or overridden by subsequent NGINX Instance Manager operations.
  • Successful publishing or policy compilation after a temporary recovery does not confirm that a failed TTL mutation or resource condition has been resolved.
  • Attack-signature download warnings are separate from ClickHouse TTL and configuration-publishing failures unless additional evidence directly correlates them.
