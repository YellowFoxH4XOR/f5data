Description

Understanding the Static Persist load balancing method for GSLB pools.

Environment

GTM (DNS) Pool members are configured to use the Static Persist load balancing method.

Cause

The Static Persist load balancing method for GSLB pools is designed to consistently return the same pool member (virtual server) in replies to DNS queries from the same LDNS address or range (using CIDR masking) of source addresses.

There are two global settings that control which part of the LDNS address the tmm should regard as important. By default, these are 32 for IPv4 and 128 for IPv6. For example, the setting can be adjusted so that all clients in the same /16, /24, or /28 would be treated the same way. Any value in the range of 1-32 can be entered for IPv4 and 1-128 for IPv6.

In the GUI, these settings are available as:​​​
  • DNS  ››  Settings  ››  GSLB  ››  Load Balancing
    • Load Balancing Defaults
      • Static Persist CIDR (IPv4): 32
      • Static Persist CIDR (IPv6): 128
In tmsh, they are available as: 
gtm global-settings general {
    static-persist-cidr-ipv4 32
    static-persist-cidr-ipv6 128
}
A GSLB pool can be configured to use "Static Persist" as the load balancing method:
 

GUI

  • DNS  ››  GSLB  ››  Pools  ››  <Pool>  ››  "Members" tab
    • Load Balancing
      • Load Balancing Method: Preferred: Static Persist

TMSH

gtm pool a example_pool {
    load-balancing-mode static-persistence
}

Recommended Actions

Configure the "Static Persist" load balancing method for GSLB pools as advised in the article.

Additional Information

When a GSLB pool is configured to use the Static Persist load balancing method, the selection behavior is as follows.

IPv4 LDNS addresses

  1. Take the source IP address of the DNS request (the LDNS IP) and shift it right to leave the configured number of bits from the CIDR length.  By default, this is 32 for IPv4, which leaves the IP address unchanged. If CIDR length is set to 24, the address would be shifted right by 8 bits, effectively throwing away the last byte. In other words, for the purpose of LB selection, an LDNS IP of 10.1.2.3 with a CIDR length of 24 would be treated as 0.10.1.2.
  2. Divide the IP address (32-bit integer) by the total number of pool members (regardless of whether they're up or down), take the remainder, and add 1. This gives a number 'n' between 1 and the number of pool members.
  3. If the nth pool member is up and available, select it. Otherwise, increment to the next pool member and try again. If no pool members are available, return LB failure.

Note that if a new member is added to an existing pool, or an existing member is removed, the result of the calculation will change. Customers may wish to consider using Wide IP persistence if it is important that a client continues to receive the same DNS reply in that situation.

Assuming an LDNS IPv4 address of 10.0.0.128, with a 32-bit IPv4 CIDR length, and the 5 pool members like below:

gtm pool a gtm_pool {
    load-balancing-mode static-persistence
    members {
        generic:10.0.0.1:80 {
            member-order 0
        }
        generic:10.0.0.2:80 {
            member-order 1
        }
        generic:10.0.0.3:80 {
            member-order 2
        }
        generic:10.0.0.4:80 {
            member-order 3
        }
        generic:10.0.0.5:80 {
            member-order 4
        }
    }
}


The 32-bit IPv4 address 10.0.0.128 is equivalent to a 32-bit integer:

  167772288

Then, apply the following calculation to these values:

  1. No shift-right is needed, as the mask is 32 bits
  2. Divide 167772288 by 5 and take the remainder (3)
  3. Add one to the result (4)
  4. Return the 4th pool-member (10.0.0.4)

IPv6 LDNS addresses

For IPv6 addresses, the calculation is slightly different to avoid dividing a 128-bit number, which is computationally expensive.
  1. Take the source IP address of the DNS request (the LDNS IP) and shift it right to leave the configured number of bits from the CIDR length. By default, this is 128 for IPv6, which leaves the IP address unchanged. If CIDR length is set to 112, the address would be shifted right by 16 bits. For example, for the purpose of LB selection, an LDNS IP of 2001:DB8::f5:1 with a CIDR length of 112 would be treated as 0:2001:DB8::f5.
  2. Split the 128-bit into four 32-bit values, and XOR these values together.
  3. Divide the resulted 32-bit value by the total number of pool members (regardless of whether they're up or down), take the remainder, and add 1. This gives a number 'n' between 1 and the number of pool members.
  4. If the nth pool member is up and available, select it. Otherwise, increment to the next pool member and try again. If no pool members are available, return LB failure.

For example, if static-persist-cidr-ipv6 is 48, then the mask will be applied to the 2nd 32-bit word (the one containing bits 32-63), and an XOR is then performed between that value and the first 32-bit word (bits 0-31). Similarly, if the cidr length was 120 bits, the mask would be applied to the 4th 32-bit value, and the result would be xor'd against the 3rd 32-bit word, and then again against the 2nd, then the 1st. This ensures that the entropy of the full 128-bit IPv6 address is retained, without the performance hit of performing 128-bit division.

Assuming an LDNS IPv6 address of 2001:0db8::1:80, with a 128-bit IPv6 CIDR length, and the same 5 pool members as above:

The 128-bit IPv6 address 2001:0db8::1:80 is equivalent to four 32-bit integers:

  0x20010db8 0x00000000 0x00000000 0x00010080

Then, apply the following calculation to these values:

  1. No shift-right is needed, as the mask is 128 bits
  2. XOR the right-most 32-bits with the 32-bits immediately before it (0x00010080 xor 0x00000000 = 0x00010080)
  3. XOR the result with the 32-bits immediately before it (0x00010080 xor 0x00000000 = 0x00010080)
  4. XOR the result with the 32-bits immediately before it (0x00010080 xor 0x20010db8 = 0x20000D38)
  5. Divide 0x20000D38 by 5 and take the remainder (1)
  6. Add one to the result (2)
  7. Return the 2nd pool-member (10.0.0.2)
