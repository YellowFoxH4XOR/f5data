Protocol Inspection

Protocol Inspection provides an intrusion detection system (IDS) and intrusion prevention system (IPS) to the BIG-IP system. Protocol Inspection enforces policies against entire flows, unlike the network firewall, which the system bypasses for established flows. For more information, refer to Chapter 2: Packet flow.

Protocol Inspection consists of two main features: protocol compliance and signature-based inspection.

Protocol compliance

  • Models the protocols and applications and alerts and blocks violations.
  • Mostly uses a positive security model: unless the protocol matches, the protocol is bad.

    For example: http-bad-version alerts and blocks if the HTTP version is not 0.9, 1.0, or 1.1

  • Allows you to modify some elements of some compliance checks, but you cannot add checks.

Signature-based inspection

  • Includes deep-packet inspection of traffic and pattern matching.
  • Uses a subset of Snort® rules syntax.
  • Uses a negative security model: if the protocol matches, the protocol is bad.
  • Allows you to author custom signatures, enabling faster response to threats, which may be easier than using an equivalent iRule.

There is some overlap with the BIG-IP Protocol Security Manager (PSM), which Protocol Inspection replaces. The differences include the following:

  • Protocol Inspection is more extensible. The parsing infrastructure you to add allows you to more easily add compliance checks. You and third parties can author signatures.
  • Signatures and the matching engines can be updated outside of the BIG-IP release cycle.
  • In BIG-IP PSM, every protocol is implemented separately. It takes at least one release development cycle to add a single protocol.
  • There is no signature matching in BIG-IP PSM .

Enabling protocol inspection

Protocol Inspection requires specific licensing to enable the Signature Matching and Compliance engines, and there is an optional signature subscription available. BIG-IP AFM is often licensed as a bundle with other modules. BIG-IP AFM must be the base module to which other modules (BIG-IP LTM, BIG-IP BIG-IP APM, BIG-IP ASM, BIG-IP GTM, and so on) are added. If BIG-IP AFM is the add-on, you must add a separate license specifically for Protocol Inspection.

Inspection engines

Compliance checks

The Compliance Engine is functionally similar to existing BIG-IP PSM features. It employs compliance checks, which are application-aware and provide a positive security model. They define what is acceptable traffic and can drop traffic that does not meet the standard. This ability can stop unknown attacks that don't follow the approved protocol specifications. Additionally, compliance checks are generally less prone to false positives than signatures are.

With compliance checks, it is easier to update and enhance security outside of the BIG-IP release cycle. You cannot add to compliance checks, but you can modify default parameters in some compliance checks

Signature checks

Signature checks employ a negative security model in which you define what constitutes bad traffic. You can author your own rules and import those authored by others.

F5 ships a default set of Protocol Inspection signatures, which are modified Snort rules. Metadata and rules syntax are separated into separate files. Updates for F5 Protocol Inspection signatures are available using a subscription.

Using the negative security model, signatures enumerate badness, which is infinite and therefore impossible to completely cover. This approach may be useful for specific remediation. The signatures are similar in concept to antivirus definitions and subject to the same limitations, such as polymorphism, obfuscation, and so on.

Signatures compared to iRules

iRules mitigate known attacks but have some drawbacks in comparison to signatures:

  • iRules do not scale well. You have to check for multiple attack patterns in a single iRules event, which can make development and testing difficult. In contrast, each signature stands on its own, and you can enable hundreds of signatures in a single Protocol Inspection policy.
  • Signatures are generally more efficient for the system to process than iRules.
  • Signatures are typically easier to write and maintain. They are also potentially easier to troubleshoot since Protocol Inspection is in the set of obvious enforcement mechanisms.
  • Visibility is better with signatures. Neither iRules nor inspection signatures force you to log, but Protocol Inspection statistics counters increment even without logging.

Protocol Inspection suggestions and confidence level

Beginning in BIG-IP 14.0.0, Protocol Inspection includes automatic signature updates and usability features, such as staging and automated learning. Automated learning allows the BIG-IP system to train itself based on observed traffic and to provide suggestions. This enhancement makes it possible to identify signatures and compliance checks that are useful to your environment without the user having to sift through false positives. The BIG-IP system presents the results of the automated learning as suggestions with a confidence level for the suggestion.

Suggestions and confidence levels

The primary task of intrusion prevention is managing false positives. If you cannot review the alerts because there are too many of them, intrusion prevention loses its value. The problem is even worse if you block legitimate traffic. The system performs statistical analysis on traffic to provide guidance about which inspections may generate false positives. This guidance is provided in the form of suggestions with a confidence level value associated with the suggestions. Beginning in BIG-IP 14.1.0, the learning process to gather these statistics and generate the guidance is continuously updated. The guidance is also heavily weighted against the completeness of the historical record: by default, a one-week period is considered an adequate sample on which to base guidance.

Important: The guidance provided by suggestions and confidence levels does not make judgement on the efficacy or accuracy of an inspection. It only informs you about the likelihood of false positives from an inspection. It has no information about the likelihood of false negatives from missing an attack. For example, a signature that never matches due to an error in coding may be recommended because it never generates a false positive.

Suggestions

To help the implement Protocol Inspection, the BIG-IP system offers suggested settings for each signature and compliance check. These suggestions are based solely on traffic statistics and do not address the inherent accuracy of an inspection. The suggestion has no information about how good an inspection is at finding malicious traffic but only informs you about how statistically likely an inspection is to generate a false positive. An extremely detailed, sophisticated signature that never generates a false positive actually looks suspicious to the system if it generates a lot of hits relative to the normal traffic load.

To make suggestions, the BIG-IP system determines whether an inspection has a match in the rolling 7-day baseline period. If it has never had a match, that means it has never generated a false positive. The BIG-IP system suggests enabling the inspection on that basis. This is the single most significant factor in the analysis.

Other factors the system weighs when formulating suggestions include the following:

  • Who is involved? 1-1, 1-many, or many-many?
  • What proportion of traffic do the signature matches represent? The assumption is that attacks are not a major portion of overall traffic. This may not be a valid assumption for some attacks.

Confidence level

Confidence level is primarily an indication of how much of the baseline period has transpired. For example, if there is an entire week of data to refer to, the confidence level is 100%.

Deployment of individual protocol inspections

You should set a Protocol Inspection action as Accept+Log until acceptance because of the risk of dropped traffic from a false positive. Note that, by default, many signatures and compliance checks are configured to drop traffic. If you enable these, you may drop valid traffic, so be sure to bulk edit the inspections to set the action to Allow. Only after you set them to Allow can you enable them by bulk edit.

Applying specialized Protocol Inspection profiles to specific applications

Protocol Inspection is inherently computationally expensive. It absolutely cannot scale with lower level mechanisms like Network Firewall, DoS Protection, and IP Intelligence, which operate at or near wire speed.

You can reduce the load on Protocol Inspection through specialization. Protocol Inspection applies every enabled inspection to every packet of every flow that the Protocol Inspection profile encounters. So, it makes sense to enable only relevant inspections. F5 recommends that you not enable SIP inspections in front of a web server farm. You could break it down even further if necessary. For example, you could employ NGINX-relevant inspections in front of pools of NGINX servers, Apache-relevant inspections in front of pools of Apache servers, and so on.

Managing false positives

If an inspection generates false positives (signature or compliance check matches that are not caused by malicious traffic) in spite of passing the statistical tests of the suggestion and confidence, you have to intervene. Disabling inspections that generate false positives improves performance and enhances the signal-to-noise ratio of logging and reporting.

Optionally, you can replace signature inspections with more accurately targeted custom signatures. You cannot review signatures obtained through subscription, so you have to search the web by CVE for alternative Snort signatures and add these as a custom signature with the Allow action until they are proven.

Be sure to reference the replaced signature in your metadata. Refer to the original in the Signature Description or Documentation settings, along with what is different and better about the custom signature. If the default signatures provide the signature in question, you can find the signature definition in the /defaults/ips_snort_signatures.txt file. Search for the signature_id that you are interested in. You can copy and enhance these signatures for your custom signatures.

You can deploy protocol inspections more restrictively: only using them where they are relevant.

Some compliance checks have parameters you can configure which you can tune to reduce false positives.

Multiple policy layers

The F5 DDoS Reference Architecture is a useful guide to help with deploying application and network security tools. This reference architecture recommends multiple tiers of protection.

Whether deploying different defenses in layers across the network topology or collapsing them into a single BIG-IP system, use the features that operate lower in the stack to accomplish inexpensive, bulk filtering to spare the more complex features extra work.

Use the most efficient mechanism that accomplishes the result you want. Mitigate using DoS Protection when you can or use the Network Firewall when you can't, and use the Protocol Inspection when you need to go deeper than L4.

For web applications, place BIG-IP AFM close to the servers it protects where it won't have to waste effort looking at irrelevant traffic. Placing the L7 defenses closer to the resources they protect and tuning them to specialize in the needs of those resources can conserve their cycles for exactly what they are most needed for: the tasks only they can handle.

If the BIG-IP system can handle the load, you can collapse the multiple tiers of protective features into a single device group. This has a lot of appeal as far as conserving rack space, reducing complexity, and so on. It is still worth approaching the deployment of these protective features as separate tiers, with each doing what it does best.

Be aware that a Protocol Inspection policy applied to a virtual server takes precedence over a policy invoked through a firewall rule applied in the global context. You can think of the global context policy as a default, subject to override.

Real-world experience with Network Firewall policies shows that customers overwhelmingly prefer to use a single, global policy rather than maintaining multiple customized policies at the virtual server or route domain level. There is no significant performance penalty for doing so. With Protocol Inspection, there are significant benefits to using multiple policies for the protected objects.

For example:

  • Tailored policies reduce the workload by applying only relevant signatures.
  • Policies applied to a virtual server to inspect traffic after the Client SSL profile decrypts it. Unencrypted web traffic is becoming the exception, not the rule.

Logging

F5 recommends that you log remotely. A BIG-IP system is not optimized for heavy disk read/write operations. Local logging is more demanding for Protocol Inspection than other features. The following paragraphs compare the logging burden imposed by the different BIG-IP AFM mechanisms:

You can configure DoS to log locally when the volume is low (Attack started, Attack sample 1/sec with stats collected over the interval, Attack stopped). The BIG-IP system can handle low volume logging; however, remote logging is still useful to consolidate security events in a single console.

Network Firewall and IP Intelligence use one-log-message-per-rule or host match (if the rule enables logging). Aggregate Log Throttling in the Security Log profile can save the system at the cost of discarded log messages. Remote logging is useful for event consolidation and you do not lose information as you do rate-limited local logging.

With logging enabled, Protocol Inspection logs any signature or compliance check match, up to 10 messages per flow by default, with no aggregate throttling implemented. You can reduce the number to 1 message per flow using a database key, but, with potentially millions of flows, doing this still can threaten the stability of the BIG-IP system if you are using local logging. Thus, F5 strongly recommends remote logging.

When logging to a remote system, consider enabling the Log Packet Payload setting in the Security Logging profile. The analysis of the packet payload extracted from the logs can be very important in determining whether an event is a false positive or a real attack.

Protocol Inspection signatures management

BIG-IP AFM protocol inspection signatures are an evolving set of protections that must be kept up-to-date to provide the best available protection against new and emerging threats and to ensure minimal false positives. F5 publishes signature update files on a regular basis. You must establish a process to keep protocol inspection signatures updated and manage the update process. The easiest way to update protocol inspection signatures is using the automatic delivery mode through scheduled or manual updates. However, for air-gapped systems with no access to the Internet (either direct or via a proxy), use the manual delivery mode. Manual delivery mode allows you to download the update file manually from MyF5 Downloads to your local workstation and then upload that file using the BIG-IP AFM Configuration utility.
