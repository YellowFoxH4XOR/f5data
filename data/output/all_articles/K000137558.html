Description

One or more blades in a VELOS cluster are not joining the cluster:

                                                          ABLE  ABLE
                                        IN       READY    TO    TO                       PARTITION
INDEX  NAME                   INSERTED  CLUSTER  CLUSTER  PING  SSH   STATE              LABEL
----------------------------------------------------------------------------------------------------
1      blade-1.chassis.local  true      false    false    true  true  Adding to Cluster
2      blade-2.chassis.local  true      false    false    true  true  Adding to Cluster
3      blade-3.chassis.local  true      false    false    true  true  Adding to Cluster
4      blade-4.chassis.local  true      false    false    true  true  Adding to Cluster
5      blade-5.chassis.local  true      false    false    true  true  Adding to Cluster
6      blade-6.chassis.local  true      false    false    true  true  Adding to Cluster
7      blade-7.chassis.local  true      false    false    true  true  Adding to Cluster
8      blade-8.chassis.local  true      false    false    true  true  Not In Cluster

The /var/log/openshift.log file on the active controller and /var/log/messages file on the blades show issues pulling docker images from the controller registries:

Error initializing source docker-daemon:controller-ha.chassis.local:2000/openshift-3.11/ci-cd/496e03f/openshift/origin-node:3.11.0.496e03f: Error loading image from docker engine: Error response from daemon: reference does not exist

When attempting to pull the image(s) manually from a blade, the image does exist in the registry, but docker returns server gave HTTP response to HTTPS client:

[root@blade-1 ~]# curl -s 'http://controller-ha.chassis.local:2000/v2/openshift-3.11/ci-cd/496e03f/openshift/origin-node/tags/list'
{"name":"openshift-3.11/ci-cd/496e03f/openshift/origin-node","tags":["3.11.0.496e03f","v3.11.0"]}

[root@blade-1 ~]# docker image pull controller-ha.chassis.local:2000/openshift-3.11/ci-cd/496e03f/openshift/origin-node:3.11.0.496e03f
Trying to pull repository controller-ha.chassis.local:2000/openshift-3.11/ci-cd/496e03f/openshift/origin-node ...
Get https://controller-ha.chassis.local:2000/v1/_ping: http: server gave HTTP response to HTTPS client

Environment

  • VELOS
  • Docker

Cause

Docker's insecure registry configuration is missing from /etc/sysconfig/docker on one or more blades.

There is no --insecure-registry configuration at all in that file:

[root@blade-1 ~]# cat /etc/sysconfig/docker
OPTIONS=' --selinux-enabled        --log-driver=journald --selinux-enabled --signature-verification=false --bip 100.64.10.0/16 --host tcp://0.0.0.0:4243 --host unix:///var/run/docker.sock --signature-verification=False'
(no other contents)

[root@blade-1 ~]# docker info
...
Insecure Registries:
 127.0.0.0/8                <--- Note

Proper configuration example:

[root@blade-1 ~]# cat /etc/sysconfig/docker
...
INSECURE_REGISTRY='--insecure-registry controller-1.chassis.local --insecure-registry controller-2.chassis.local --insecure-registry controller-ha.chassis.local --insecure-registry 100.64.0.0/12 --insecure-registry 10.0.0.0/8'

[root@blade-1 ~]# docker info
...
Insecure Registries:
 controller-ha.chassis.local
 controller-1.chassis.local
 controller-2.chassis.local
 100.64.0.0/12
 10.0.0.0/8
 127.0.0.0/8

The exact root cause of this problem is not known at the time of publication. ID1391589 tracks this issue.

Recommended Actions

To recover from this issue, confirm which blades are missing INSECURE_REGISTRY in /etc/sysconfig/docker, manually insert that config, then reboot the blades.

  1. Confirm which blades have the missing INSECURE_REGISTRY line:

    # from controller
    for i in {1..8}; do echo "blade-${i}:"; ssh blade-${i} "grep -c INSECURE /etc/sysconfig/docker"; done
    # 0 = missing

  2. SSH to the affected blades and edit /etc/sysconfig/docker, adding the missing line:

    INSECURE_REGISTRY='--insecure-registry controller-1.chassis.local --insecure-registry controller-2.chassis.local --insecure-registry controller-ha.chassis.local --insecure-registry 100.64.0.0/12 --insecure-registry 10.0.0.0/8'
    # Above is one line

  3. Reboot the blades
  4. Confirm if the docker pull attempts are now successful. This may take some time.

Note: These steps have been tested one time and resolved the issue on the chassis in question. If these steps do not work in your environment, consider a clean install.

Additional Information

Blades may be out of cluster for numerous reasons. Further troubleshooting is required if the observed symptoms do not match this article's description.
