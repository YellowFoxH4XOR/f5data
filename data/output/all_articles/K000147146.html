K000147146: WAF Exclusions on Unparseable Data Types

Description

In some cases, HTTP request parameters (or other entities) may contain data types that cannot be reliably parsed by a HTTP-speaking Web Application Firewall (WAF).  Patterns within such data can inadvertently trigger False Positives (FPs) on various WAF signatures in ways that are not always predictable or deterministic.  Common scenarios include:

  1. File Uploads such as images, video, PDFs

  2. Unconstrained user input that accepts code blocks
  3. Encrypted data such as authentication tokens, hashes and other cryptographic objects.
  4. Mixed data with binary elements, such as the __VIEWSTATE parameter in ASP.NET applications
  5. Uncommon encoding methods and character sets

 

FP remediation on such data types is rarely accomplished by excluding a single signature.  Sometimes it is necessary to exclude all signature checks on the entity.  

 

Environment

  • F5® Distributed Cloud HTTP Load Balancer
  • Distributed Cloud Web Application and API Protection (WAAP)

Cause

Certain HTTP request parameters may contain data types or patterns that are not plain text. These patterns can inadvertently match Web Application Firewall (WAF) signatures, resulting in false positives and blocking legitimate requests.

Recommended Actions

Note: While this process can be done through either a WAF Exclusion Rule or a Service Policy (SP), it's generally preferred to enact by SP to avail of advanced match criteria options, particularly for matching on the Content-Type header.

 

To disable WAF signature checks for a specific parameter (or other contexts like cookies):

1. Create a WAF Exclusion Rule or Service Policy in the appropriate namespace or load balancer.

2. Set Match Conditions: Specify the HTTP path and method.

As this is to be a wide exclusion rule, it's wise to define match conditions as tightly as possible to avoid creating an overly broad security bypass.  Ideally, match conditions should consist of exact HTTP path (avoid prefix match), method and header regex for the request content-type (e.g. multipart/form-data, image/jpeg, application/octet-stream...

3. Configure the App Firewall Detection Control: Add a new signature override item.

4. Enter the Parameter Details:

  • In the Context field, input the name of the parameter containing the triggering data (e.g., a file upload parameter).
  • Select Context Type as Parameter.

5. Disable Signature Checks:

  • In the Signature ID field, enter 0. This acts as a wildcard (*), disabling signature checks for the specified parameter.

6. Save and Apply the changes.

 

Example: 

For example, to disable signature checking for the parameter filename in POST requests to /submissions/upload.php, the configuration would look like this:

  • HTTP Path: /submissions/upload.php
  • HTTP Method: POST
  • Parameter Name: filename
  • Signature ID: 0 (wildcard to disable signature checks)

This will disable signature checking on the parameter named 'filename' for POST requests to /submissions/upload.php.

  • Note: a 'parameter' exclusion context can refer to a URL query parameter, a POST/form-data parameter, or a JSON key.

 

If the file upload is performed by multipart POST, a SP will be needed matching method, exact path, and .*multipart/form-data.*  regex on Content-Type header.  Exclude all signatures on body context for matched traffic.

 

 

Additional Information

You can apply similar steps for other context types, such as cookies or headers, by adjusting the Context Type in step 4.

HTTP-literate WAF is ineffective for scanning binary content.  Leverage the Malware Scanning feature for inspection of binary content.

Apply blanket exclusion of all signatures only on data types that the WAF cannot parse.  Ensure this is properly understood before proceeding.
