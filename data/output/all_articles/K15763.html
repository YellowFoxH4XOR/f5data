Issue

You should consider using this procedure under the following conditions:

  • The BIG-IP system is configured to use the RADIUS protocol for authenticating BIG-IP administrative users.
  • Administrative user accounts defined on the remote RADIUS server are unable to log in to the BIG-IP system.

Note: If the remote user accounts are unable to log in to the BIG-IP system, the locally defined user accounts, such as the default administrator account and the root command line account, are able to log in to the system.

Symptoms

As a result of RADIUS authentication failures, you may encounter the following symptoms:

  • The login process fails for BIG-IP administrative users.
  • The BIG-IP system logs error messages related to RADIUS login failures for administrative users.

Recommended Actions

The RADIUS protocol provides access control for network devices using one or more centralized servers. RADIUS operates over UDP and provides Authentication, Authorization, and Accounting (AAA) management for users connecting to a network service. You can change the authentication source for BIG-IP administrative users from using the local database to using an external authentication source, such as RADIUS. Configuring the remote RADIUS authentication source specifies that the BIG-IP system uses a remote RADIUS server to authenticate administrative users.

RADIUS operation

RADIUS is a client/server application layer protocol, using UDP as the transport. The officially assigned port number for RADIUS is 1812 (older versions use port 1645). When you configure RADIUS authentication for BIG-IP administrative users, the BIG-IP system operates as the RADIUS client and passes user information to the designated RADIUS server. The RADIUS server then responds to the BIG-IP system. The authentication process occurs as follows:

  • An administrative user attempts to log into the BIG-IP system using an appropriate username and password.
  • The BIG-IP system compiles the user information and sends an 'Access-Request' message to the RADIUS server containing the user attributes.
  • The RADIUS server receives the request and validates the user information.
  • If the request is valid, the RADIUS server consults the user database to verify the user attributes.
  • If any condition is not met, the RADIUS server sends an 'Access-Reject' response to the BIG-IP system indicating that the request is invalid.
  • If all conditions are met, the RADIUS server sends an 'Access-Accept' response to the BIG-IP system containing a list of configuration values for the user.

There may be times when you need to troubleshoot RADIUS authentication or connections to the remote RADIUS server.

Procedures

When experiencing RADIUS authentication issues, you can use the following troubleshooting steps to determine the root cause:

  • Verify the BIG-IP RADIUS configuration
  • Verify RADIUS server availability
  • Review RADIUS log messages
  • Enable debug logging for RADIUS authentication
  • Packet tracing RADIUS traffic

Verify the BIG-IP RADIUS configuration

To verify the BIG-IP RADIUS configuration, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility using the administrator account.
  2. Go to System > Users > Authentication.
  3. Verify the BIG-IP RADIUS server configuration settings, including the Port and shared Secret settings:
    • Host: Specifies the name of the primary RADIUS server.
    • Port: Specifies the port for primary RADIUS server communications. The default is 1812.
    • Secret: The secret is a shared secret text string used between the BIG-IP system and the RADIUS server.
  4. Confirm that the above setting match those on the RADIUS servers.

Verify the RADIUS server availability

When experiencing RADIUS authentication issues, you should verify that the BIG-IP system can access the RADIUS servers on the network. In most environments the RADIUS servers are configured to be reachable over the BIG-IP system's management network. However, it is possible that the servers are reachable over a TMM network. To verify the RADIUS server availability, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the TMOS Shell (tmsh) by entering the following command:

    tmsh

  2. To determine the IP addresses of the defined RADIUS servers, enter the following command:

    list /auth radius-server

    For example:

    auth radius-server system_auth_name1 {
    secret $M$It$v+bMvmHjXhjQ8YIXm8jOoQ==
    server 172.24.171.1
    }

  3. Use a utility, such as Ping or Traceroute, to verify network availability of the remote RADIUS server.

    For example:

    ping <RADIUS_server_ip>

Review RADIUS log messages

If the RADIUS servers are available on the network, but fail to authenticate users, you may need to review the BIG-IP log files for relevant RADIUS messages. To review the log messages related to RADIUS authentication, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP command line using the root account.
  2. Use a Linux text utility, such as less or tail, to review the /var/log/secure file.

    For example:

    less /var/log/secure

  3. Review the log entries for error messages related to RADIUS login failures.

When reviewing the log entries for RADIUS login failures, you may view messages related to the following categories:

  • Bad username or password: When an administrative user attempts to log in using a bad username or password, the system logs messages similar to the following example:

    alert httpd[11037]: pam_unix(httpd:auth): check pass; user unknown
    notice httpd[11037]: pam_unix(httpd:auth): authentication failure; logname= uid=48 euid=48 tty= ruser= rhost=192.168.8.58
    err httpd[11037]: [error] [client 192.168.58.58] AUTHCACHE PAM: user 'testuser' - not authenticated: Authentication failure, referer: https://172.24.171.235/tmui/login.jsp
    info httpd(pam_audit)[11037]: User=testuser tty=(unknown) host=192.168.8.58 failed to login after 1 attempts (start="Thu Oct 30 10:20:01 2014" end="Thu Oct 30 10:20:04 2014").

  • Invalid or incorrect secret key: When the BIG-IP system or RADUS server is configured to use an invalid or incorrect secret key, the system logs error messages similar to the following example:

    err httpd[11072]: pam_radius_auth: packet from RADIUS server 172.24.171.1 fails verification: The shared secret is probably incorrect.
    err httpd[11072]: pam_radius_auth: All RADIUS servers failed to respond.

  • The RADIUS server fails to respond or refuses the connection: When the specified service port or IP address for the RADIUS server is incorrect, or the RADIUS server is configured to allow requests from only a certain address range, the system logs error messages similar to the following example:

    err httpd[27674]: pam_radius_auth: RADIUS server 172.24.171.1 failed to respond
    err httpd[27674]: pam_radius_auth: All RADIUS servers failed to respond.

Enable debug logging for RADIUS authentication

You can enable debug logging for RADIUS authentication, attempt to log in using remote user accounts, and then review the debug log files. To do so, perform the following procedure:

Impact of procedure: F5 recommends that you return the log level to the default value after you complete the troubleshooting steps. Leaving debug logging enabled when the system is in normal production mode may generate excessive logging and cause poor performance.

  1. Log in to tmsh by entering the following command:

    tmsh

  2. To enable debug logging, enter the following command:

    modify /auth radius all debug enabled

  3. Test RADIUS authentication by attempting to log in using remote user accounts.
  4. After testing RADIUS authentication, disable debug logging by entering the following command:

    modify /auth radius all debug disabled

  5. Review the /var/log/secure file for debug log messages.

Packet tracing RADIUS traffic

You may need to run tcpdump packet captures to troubleshoot RADIUS sessions. When reviewing RADIUS tcpdump output, it is helpful to understand the RADIUS packet format.

RADIUS packets contains the following fields:

  • Code: The code field indicates the RADIUS packet type. For example, code type 1, indicates an 'Access-Request' message.
  • Identifier: The identifier field matches a RADIUS request to a corresponding RADIUS response. For example, a RADIUS request message with an identifier value of 200, can be matched to a response message with an identifier value of 200.
  • Length: The length field indicates the length of the RADIUS packet.
  • Authenticator: The authenticator field is used to authenticate the reply from the RADIUS server. The two types of authenticator fields are; Request Authenticator (sent in RADIUS request packets), and Response Authenticator (sent in RADIUS response packets).
  • Attributes: The RADIUS attributes field contains information such as authentication, authorization, and configuration details for the request and reply messages.

To packet trace RADIUS traffic, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the command line.
  2. You can capture RADIUS traffic by running one of the following tcpdump captures:

    Note: Older versions of RADIUS servers may use port 1645. Use the appropriate port numbers for your environment in the following commands.

    • If the RADIUS server is reachable on the management network, use the following syntax:

      tcpdump -s0 -ni eth0 port 1812 -vw /shared/tmp/rad.pcap

    • If the RADIUS server is reachable on a TMM network, use the following syntax:

      tcpdump -s0 -ni <vlan> port 1812 -vw /shared/tmp/rad.pcap

      Note: The -vw switches write the output to /shared/tmp/rad.pcap and it also starts a packet counter to show if any packets are being written to the file.

  3. You can view the capture file in a packet analysis program for further debugging.
