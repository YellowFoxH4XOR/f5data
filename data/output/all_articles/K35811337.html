Description

How to recover the root password on non RAID-capable BIG-IP platforms.

Environment

  • BIG-IP 14.1.0 and later
  • Root password

Cause

Forgotten root password

Recommended Actions

Beginning in BIG-IP 14.1.0, the system uses CentOS 7 as the base operating system (OS). To reset the root password, you must use rd.break to apply a break at an early stage of the boot process rather than appending single to the kernel entry in GRUB to enter single-user mode. This new behavior is a result of Red Hat Enterprise Linux (RHEL) 7 adopting systemd software.

Note: In BIG-IP 14.0.0, you can still reset the root password by appending single to the kernel entry and using mount -a.

Procedures

Reset a lost or forgotten root password

Impact of procedure: This procedure requires that you restart the BIG-IP system in single-user mode. While in this mode, the device is unable to process traffic.

Note: Once in Single mode, you have limited time to complete the procedure, if a timer expires the device will reboot automatically outside the single-user mode, so you'd need to execute fast or be prepared to execute multiple times the first steps of the procedure. A good piece of advice is to write down the result of the command in step 2 and prepare the commands in step 4, so you can send them faster.
 

  1. Start the system in single-user mode. This procedure applies to both GRUB 0.97 and 2. Depending on the platform for your system, you must decide where to append rd.break in the kernel entry line (replacing single with rd.break), in addition to initiating a system boot (b or Ctrl-X). For more information, refer to K4178: Restarting the BIG-IP system in single-user mode (GRUB 0.97) or K14662: Restarting the BIG-IP system in single-user mode (GRUB2).

    Note: Some attempts at booting to single-user mode result in a forced FSCK and asking for the password. K14662 states that you can skip the file system check by appending the words single fastboot instead of single. Keep in mind that this does not work to put fastboot after rd.break, which is the current method.

    After the system boots into single-user mode, the command prompt appears similar to the following example:

    switch_root:/#

    In some BIG-IP platforms, you may instead be prompted to login with: localhost login: In this case enter the username "root" and press ENTER, then you should be at the switch_root prompt.

  2. Verify the current mounting path for later reference by entering the following command:

    mount | grep /dev/mapper/vg--db

    Output appears similar to the following example:

    /dev/mapper/vg--db--sda-set.2.root on /sysroot type ext3 (ro,relatime,errors=continue,barrier=0,data=ordered)
    /dev/mapper/vg--db--sda-set.2._usr on /sysroot/usr type ext3 (ro,noatime,errors=continue,barrier=0,data=ordered)
     

    Important: On some BIG-IP platforms, you may observe vda instead of sda in the output. For example, /dev/mapper/vg--db--vda-set.2.root.On such platforms, you must replace sda with vda for the commands in the rest of the procedure. In other platforms instead of vda or sda you may observe cpmirror, you must replace sda with cpmirror. Also, be careful with the number after the set. For example, /dev/mapper/vg--db--cpmirror-set.3.root 

  3. Remount both the /sysroot and /sysroot/usr directories to read-write mode by entering the following commands:

    mount -o remount,rw /sysroot
    mount -o remount,rw /sysroot/usr

  4. Mount the appropriate /sysroot/config and /sysroot/var directories using the mounting path and volume set references retrieved from step 2, taking careful note of which set you need to mount. For example, if step 2 shows that you have set 2 (which means you booted into HD1.2) already mounted, then in this step you need to mount the set.2._config and set.2._var volumes. Similarly, if you boot to HD1.3, you mount set.3._config and set.3._var volumes in this case. Ensure that you mount both config and var volumes.

    For example, to mount the HD1.2 config and var volumes, enter the following commands:

    mount /dev/mapper/vg--db--sda-set.2._config /sysroot/config
    mount /dev/mapper/vg--db--sda-set.2._var /sysroot/var

    For example, to mount the HD1.3 config and var volumes, enter the following commands:

    mount /dev/mapper/vg--db--sda-set.3._config /sysroot/config
    mount /dev/mapper/vg--db--sda-set.3._var /sysroot/var

    Use ls -1 /dev/mapper/vg* to view available volumes. For example:

    [root@i7800:Active:Standalone] config # ls -1 /dev/mapper/vg*
    ...
    /dev/mapper/vg--db--sda-set.1.root          <-- HD1.1
    /dev/mapper/vg--db--sda-set.1._config       <-- HD1.1
    /dev/mapper/vg--db--sda-set.1._usr          <-- HD1.1
    /dev/mapper/vg--db--sda-set.1._var          <-- HD1.1
    /dev/mapper/vg--db--sda-set.2._config       <-- HD1.2
    /dev/mapper/vg--db--sda-set.2.root          <-- HD1.2
    /dev/mapper/vg--db--sda-set.2._usr          <-- HD1.2
    /dev/mapper/vg--db--sda-set.2._var          <-- HD1.2

    On some platforms (such as iSeries FIPS platforms), the entries will appear similar to the following:

    [root@i5820F:Active:Standalone] config # ls -1 /dev/mapper/vg*
    ...
    /dev/mapper/vg--db--cpmirror-set.2._config
    /dev/mapper/vg--db--cpmirror-set.2.root
    /dev/mapper/vg--db--cpmirror-set.2._usr
    /dev/mapper/vg--db--cpmirror-set.2._var

    Mount these as normal, ensuring that the path to the volumes are modified as appropriate in the mount command.

  5. Verify the current mounting path and ensure the directories are in read-write mode by entering the following command:

    mount | grep /dev/mapper/vg--db

    Output appears similar to the following example:

    /dev/mapper/vg--db--sda-set.2.root on /sysroot type ext3 (rw,relatime,errors=continue,barrier=0,data=ordered)
    /dev/mapper/vg--db--sda-set.2._usr on /sysroot/usr type ext3 (rw,noatime,errors=continue,barrier=0,data=ordered)
    /dev/mapper/vg--db--sda-set.2._config on /sysroot/config type ext3 (rw,relatime,errors=continue,barrier=0,data=ordered)
    /dev/mapper/vg--db--sda-set.2._var on /sysroot/var type ext3 (rw,relatime,errors=continue,barrier=0,data=ordered)

  6. Change to the root file system by entering the following command:

    chroot /sysroot

    A new command prompt appears similar to the following example:

    sh-4.2#

  7. Change the root password by entering the following command:

    passwd root

  8. When prompted, enter a new password.

    The output should appear similar to the following example:

    sh-4.2# passwd root
    Changing password for user root.
    New BIG-IP password: 
    Retype new BIG-IP password: 
    Changing password for user root.
    passwd.bin: all authentication tokens updated successfully.

    Note: If the following error message is returned, make the root password more complicated.
    "passwd.bin: Have exhausted maximum number of retries for service"

  9. Force Security-Enhanced Linux (SELinux) to re-label the file system on the next boot by entering the following command:

    touch /.autorelabel

  10. Exit and restart the system using the exit command for chroot and single-user mode command prompts. To do so, refer to the following examples:

    sh-4.2# exit
    switch_root:/# exit

Note: If you perform this operation on a VIPRION system with more than one blade installed, you must ensure the password is changed on the primary blade. You can do this by logging in to the secondary blade after rebooting and resetting the password there. After you are logged in, use ssh primary (which is key-authenticated and doesn't prompt for a password), and then use the passwd root command again to change the password.

Additional Information

  • K000148340: Cannot reset root password - "The user root is currently authenticated from a remote source. Please change the password at the remote authentication server."
