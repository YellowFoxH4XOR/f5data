Description

When connecting from the F5 Edge Client (Windows) to a BIG-IP APM virtual server configured with an Access IPsec VPN tunnel using certificate-based (RSA-signature) IKEv2 authentication, the connection fails during authentication. The Windows Edge Client log shows:

CURDialer::OnRasCallback(), RAS error (state=RASCS_AuthNotify, error=13801: IKE authentication credentials are unacceptable )

The client immediately issues RasHangUp() and disconnects following this error.

The client reaches RASCS_AuthNotify during IKE authentication, then immediately fails with RAS error 13801 ("IKE authentication credentials are unacceptable"). The Host component fires an OnError event and the client tears down the session via RasHangUp().

Environment

  • BIG-IP APM with Access IPsec (native net ipsec access-ipsec feature)
  • IKEv2, phase1-auth-method rsa-signature
  • Windows F5 Edge Client (RAS/IKEv2 initiator)

Cause

This is a certificate configuration issue on the BIG-IP APM side. Two contributing misconfigurations can produce this symptom:

  1. The my-cert-file and my-cert-key-file values in the net ipsec access-ipsec object do not correctly reference a valid, installed IKE identity certificate and matching private key.
  2. The IKE identity certificate used for the tunnel does not include the BIG-IP virtual server's IP address (or the public NAT IP, if the client connects through a NAT boundary) in the Subject Alternative Name (SAN). For IKEv2 certificate authentication against a Windows Edge Client, the SAN must include this IP address, not just a DNS name.

Additionally, because the Edge Client first establishes the outer HTTPS/TLS session to the virtual server before negotiating the native IKEv2/IPsec tunnel, an incomplete certificate chain on the client-ssl profile (missing intermediate/issuing CA in the chain option of the cert-key-chain) can also contribute to client-side trust/authentication failures.

Recommended Actions

  1. Confirm the certificate and key referenced by my-cert-file / my-cert-key-file in the access-ipsec object are valid and currently installed:

tmsh list sys crypto cert <name>

tmsh list sys crypto key <name>

  1. Regenerate or reissue the IKE identity certificate so that subject-alternative-name includes the virtual server's IP address (or the public NAT IP, if applicable), for example:

subject-alternative-name DNS:vpn.example.com, IP Address:<virtual-server-IP_or_NAT-IP>

  1. On the client-ssl profile bound to the IPsec-enabled virtual server, verify the cert-key-chain includes the correct chain (issuing/intermediate CA bundle), for example:

ltm profile client-ssl profile_vpn.example.com {
    ca-file myCA.crt
    cert-key-chain {
        vpn_myCA_0 {
            cert vpn.example.com
            chain myCA.crt
            key vpn.example.com
        }
    }
    inherit-ca-certkeychain true
    inherit-certkeychain false
}

  1. Re-test the connection from the Edge Client.
  2. Confirm successful negotiation in /var/log/ltm and /var/log/ipsec.log:

tmm IPsec: Tunnel up <virtual-server-IP> - <client-IP>

\[IKE\] ... state RES_IKE_AUTH_RCVD -> ESTABLISHED

Verification

  • Edge Client no longer reports RAS error 13801.
  • ipsec.log shows the IKEv2 state machine reaching ESTABLISHED.
