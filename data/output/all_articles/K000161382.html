K000161382: Clearing Persistent Peer Alarms in F5 SDC After Network Disturbance

Type
Support Solution
Published
2026-05-22
Updated
2026-05-22
Applies to
  • Traffix SDC: 5.2.X, 5.2.0
Source
https://my.f5.com/manage/s/article/K000161382

Description

False peer alarms may remain visible in the WebUI after a network disturbance affecting Diameter peers on an F5 SDC node. These alarms persist even though the peers are operationally up. Standard procedures such as NMS restarts and Cassandra alarm table truncation may not clear these alarms. Symptoms include:

  • Alarms remain active for specific interfaces
  • Peer status confirmed as OPEN/UP in WebUI and via SCTP HEARTBEAT/ACK packet captures
  • Cassandra logs may show memory exhaustion errors
  • Alarm-clearing procedures do not resolve the issue

Environment

  • F5 SDC (Signaling Delivery Controller)
  • Two-node SDC deployment
  • Cassandra database for alarm state persistence (stateful_alarms table)
  • Recent event: Network disturbance causing mass peer disconnections

Cause

  • Cassandra memory exhaustion prevented alarm state updates, resulting in stale alarms.
  • Stale state persisted in FEP interfaces after SCTP ADDR_UNREACHABLE/LINK_DOWN events.
  • Restarting peers or NMS did not clear FEP-level alarm state.

Answer/Recommended Actions

  1. Verify Peer Status
    • Use system tools to confirm affected peer IPs are connected and all components are running.
    • Check WebUI for OPEN/UP status.
    • Use packet capture to confirm SCTP HEARTBEAT/ACK exchanges for affected peers
    • Check Cassandra Memory Health

      Review Cassandra logs for memory errors:

      cd /var/logs/cassandra

      grep "Maximum memory usage" system.log

      grep "Maximum memory usage" debug.log

    • If memory exhaustion is found, restart Cassandra and verify normal operation.
  2. Clear Alarms via Cassandra Procedure (K93439385)
    • Stop NMSAgent on all nodes.
    • Connect to Cassandra.
    • Truncate stateful_alarms table in the site keyspace:

       

      truncate table nms_<site>_ems.stateful_alarms;

      select count(*) from nms_<site>_ems.stateful_alarms;

    • Restart NMSAgent.
    • Allow several minutes for components to respond and alarms to clear.
  3. Restart FEP Interfaces
    • Restart the affected FEP interfaces on the node where alarms persist.
    • This step clears any stale FEP-level alarm state not resolved by previous actions.
  4. If Alarms Persist
    • Collect and upload TTA logs from both affected and healthy nodes for further analysis.

Additional Information

  • After FEP interface restart, all false alarms should clear.
  • Memory exhaustion in Cassandra can prevent alarm state changes; ensure JVM heap is properly sized.
  • Stale alarms may be interface-specific and not system-wide.
