K000137348: APM: F5RST "Session killed by session DB"

Type
Support Solution
Published
2023-10-25
Updated
2023-10-25
Applies to
  • BIG-IP
  • BIG-IP APM: 16.1.3
Source
https://my.f5.com/manage/s/article/K000137348

Description

The BIGIP Administrators may notice that some APM sessions are reset as per tcpdump capture with reason "F5RST(peer): Session killed by session DB" or "F5RST: Session killed by session DB" and wonder what can be the explanation of such reset. There can be different triggers to TCP RST from APM, but here is one example. From decrypted packet capture during attempt to get the service behind APM Virtual Server (VS), the Administrator may observe the similar flow which results to TCP RST:


client -> 1.1.1.1

vs -> 1.1.1.2

snat -> 2.2.2.1

server -> 2.2.2.2

 

1) the client sends the HTTP query, it's handled by APM logic (the session id is assigned, the query is processed and etc.). The connection is seen on client-side from APM perspective. TCP handshake related packets under stream 148 are omitted for brevity: 


1457 2023-09-28 13:31:38.423899 1.1.1.1 1.1.1.2 HTTP/JSON 40482 443 148 IN s1/tmm9 : POST /api/some-data HTTP/1.1 , JavaScript Object Notation (application/json)

 

2) then the connection is initiated on server-side from APM perspective in tcp stream 151: 


1481 2023-09-28 13:31:38.437719 2.2.2.1 2.2.2.2 TCP 40482 443 151 OUT s1/tmm9 : 40482 → 443 [SYN] Seq=0 Win=14600 Len=0 MSS=1460 WS=1 SACK_PERM TSval=3690783812 TSecr=0


3) the same HTTP request (as in frame 1457) is sent to server, but now on server-side from APM perspective:

 

1498 2023-09-28 13:31:38.471921 2.2.2.1 2.2.2.2 HTTP/JSON 40482 443 151 OUT s1/tmm9 : POST /api/some-data HTTP/1.1 , JavaScript Object Notation (application/json)

 

4) the server acknowledges that it receives the above POST via TCP ACK:

 

1499 2023-09-28 13:31:38.481616 2.2.2.2 2.2.2.1 TCP 443 40482 151 IN s1/tmm9 : 443 → 40482 [ACK] Seq=5952 Ack=1736 Win=16335 Len=0 TSval=2829392054 TSecr=3690783847 


5) but nothing happens after that: the server doesn't reply with 2XX or 4XX or with 5XX http response. So, APM resets the connection ~12 sec later on server-side first from APM perspective: 


1513 2023-09-28 13:31:49.733025 2.2.2.1 2.2.2.2 TCP 40482 443 151 OUT s1/tmm9 : 40482 → 443 [RST, ACK] Seq=1736 Ack=5952 Win=0 Len=0 [F5RST(peer): Session killed by session DB]

 

6) then on client-side from APM perspective:

 

1514 2023-09-28 13:31:49.733086 1.1.1.2 1.1.1.1 TCP 443 40482 148 OUT s1/tmm9 : 443 → 40482 [RST, ACK] Seq=4401 Ack=2066 Win=0 Len=0 [F5RST: Session killed by session DB]

Environment

  • APM
  • F5RST: Session killed by session DB

Cause

Non-F5. The end server is not responding to HTTP request on server-side. As result of that, ~ 12sec later APM resets the connection on server-side, then on client-side

Recommended Actions

To verify with server administrator why HTTP request is not responded.
