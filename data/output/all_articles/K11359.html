Topic

When you configure an HTTP monitor to monitor a pool member, the BIG-IP HTTP monitor uses the timeout setting to determine when a pool member will be marked down.

Description

The BIG-IP HTTP monitor sends a FIN packet (and may also send RST packets) to initiate the close sequence as soon as the health check Receive String is matched, even if the BIG-IP system has not yet received the entire object that was requested in the HTTP monitor Send String. The early FIN from the BIG-IP system effectively reduces the consumption of BIG-IP resources, and is fully RFC-compliant; however, it may also result in orphaned sessions or log messages regarding improper session closure on the webservers responding to the monitor requests.

If the BIG-IP system does not receive any response before the next monitor Interval, the BIG-IP system sends subsequent monitor requests over the same open socket, expecting a response, for the duration of the configured Timeout period. For more information, refer to K13820: Configuring BIG-IP monitor socket reuse behavior.

The HTTP monitor's default Interval is five seconds and the Timeout period is 16 seconds. If the pool member does not provide an expected response, for example, the pool member's response does not match any of the configured Receive String, or there is no response at all within the configured Timeout period, the system considers the member to be down. The pool member will remain down until a valid HTTP response is received. In some BIG-IP versions, the HTTP may reuse the same TCP session and send multiple HTTP requests before closing the TCP connection. However, the HTTP monitor continues to use the timeout setting to mark the member down. The following example illustrates how the BIG-IP system uses the timeout interval to mark down pool members:

Time interval (seconds)HTTP requestHTTP server replyNode Status
0GET /index.html HTTP/1.1Unexpected or no replyUp
5GET /index.html HTTP/1.1Unexpected or no replyUP
10GET /index.html HTTP/1.1Unexpected or no replyUP
15GET /index.html HTTP/1.1Unexpected or no replyUP
16 (timeout reached)----Down
0--200 OK (reply to a previous HTTP request)*Down
5GET /index.html HTTP/1.1200 OKUP

*Once the monitor's timeout value is reached, the node status will remain down until the next request receives a successful reply.

Recommendations

F5 recommends that you set timeout values for HTTP monitors to be three times the interval plus 1 second to ensure that the base monitor has three full requests before declaring a node down.

Note: You can create custom Extended Application Verification (EAV) monitors to match your application requirements. For information about writing EAV monitors, refer to the DevCentral Advanced Design & Config wiki page. A DevCentral login is required to access this content.
