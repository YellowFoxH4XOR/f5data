K000162880: HTTP 502 Responses Caused by Broken Prefix Set References in an F5 Distributed Cloud Service Policy

Type
Support Solution
Published
2026-08-12
Updated
2026-08-12
Applies to
  • F5 Distributed Cloud Services
  • F5 Distributed Cloud WAF
Source
https://my.f5.com/manage/s/article/K000162880

Description

An F5 Distributed Cloud HTTP Load Balancer may return HTTP 502 responses for all requests to Load Balancer when an attached Service Policy contains a broken reference to an IP Prefix Set. The issue can occur when the referenced Prefix Set does not exist in the namespace specified by the Service Policy or is missing from XC Console.

The customer may observe the following symptoms:

  • Application requests consistently return HTTP 502 Bad Gateway.
  • F5 Distributed Cloud request logs show rsp_code: 502.
  • The request diagnostic detail may show rsp_code_details: ext_authz_denied.
  • The Service Policy result may be reported as unresolved.
  • The request may include the following response flag:
{"UnauthorizedDetails":"&ResponseFlags_Unauthorized{Reason:EXTERNAL_SERVICE,}"}

The Service Policy configuration may also display warnings such as:

Broken References Detected
Field Rules contains configurations with broken or disabled references
Does not exist

The 502 response is generated because the Service Policy cannot be resolved during request processing. It will affect all requests on given Load Balancer. This is a policy-resolution failure and should not be interpreted as an explicit application or WAF deny decision.

Environment

  • F5 Distributed Cloud
  • HTTP Load Balancer
  • One or more Service Policies attached to the HTTP Load Balancer
  • Service Policy field rules that reference IP Prefix Sets
  • Missing IP Prefix Sets including namespace and name reference.

Cause

The Service Policy contains a reference to an IP Prefix Set using an incorrect or invalid namespace/name. For example, the Service Policy may reference a Prefix Set in the /shared namespace even though the object is defined in another namespace. The resulting reference cannot be resolved, and the Service Policy remains in a broken state.

A Service Policy can contain multiple field rules that reference the same Prefix Set. Therefore, a single invalid object reference may appear repeatedly across several rules. All references must be reviewed, not only the first warning displayed by the console.

Recommended Actions

  1. Identify the affected HTTP Load Balancer and record a sample request ID associated with the HTTP 502 response.
  2. In the F5 Distributed Cloud Console, open the affected HTTP Load Balancer and review the Service Policies attached to it.
  3. Record the Service Policy order before making any changes. This is important when several policies are attached to the same Load Balancer.
  4. Open the first attached Service Policy and select Manage Configuration.
  5. Review the Service Policy rules individually. Expand each field rule and inspect every condition that references an external object, including IP Prefix Sets.
  6. For each referenced IP Prefix Set, verify all of the following:
    • The Prefix Set exists.
    • The Prefix Set name is correct.
    • The Prefix Set is enabled.
    • The namespace in the Service Policy reference matches the namespace where the Prefix Set is defined.
  7. Pay particular attention to warnings such as Does not exist, disabled references, or references that cannot be opened from the UI/object selector.
  8. If a broken reference is found, edit the affected field rule and replace the invalid reference with the existing Prefix Set from the correct namespace or recreate object first. For example, use the namespace where the object is actually defined rather than assuming that the object is located in /shared.
  9. Review all remaining rules in the Service Policy, including repeated references to the same Prefix Set. Confirm that no additional broken references remain.
  10. Save the Service Policy and reapply it to the HTTP Load Balancer.
  11. Confirm that the Broken References Detected warning is no longer displayed.
  12. Retest the affected application request and verify that the HTTP 502 response no longer occurs.
  13. Review the request logs and confirm that:
    • The response code is no longer 502.
    • The Service Policy result is no longer unresolved.
    • The EXTERNAL_SERVICE unauthorized response flag is no longer present for the affected request.

Procedure to Identify the Culprit Service Policy

If multiple Service Policies are attached to the HTTP Load Balancer and the affected policy is not immediately apparent, use the following controlled isolation procedure. Perform these steps during an approved maintenance window or in a non-production environment whenever possible.

  1. Capture a failing request ID and confirm that the request returns HTTP 502 with an unresolved Service Policy result.
  2. List all Service Policies attached to the HTTP Load Balancer in their current evaluation order.
  3. Start with the first policy that was recently added or modified. If no recent change is known, inspect each policy systematically from top to bottom.
  4. Open the Service Policy and select Manage Configuration.
  5. Review the field rules one at a time. For every rule, record:
    • Rule name or position
    • Match conditions
    • Action
    • Referenced IP Prefix Sets
    • Namespace of each referenced Prefix Set
    • Any broken-reference or disabled-reference warning
  6. If no broken reference is found, continue with the next Service Policy.
  7. If operationally safe, temporarily remove or disable only the policy being tested, then save and reapply the HTTP Load Balancer configuration.
  8. Retest the same application request using the same route and, where possible, the same test conditions.
  9. Interpret the result as follows:
    • If the HTTP 502 response stops after one Service Policy is removed, that policy is the likely source of the resolution failure.
    • If the HTTP 502 response continues, restore the policy and continue testing the next Service Policy.
  10. After identifying the affected Service Policy, inspect every field rule in that policy and correct all invalid Prefix Set references.
  11. Restore the intended Service Policy order, save the configuration, and reapply the policy to the HTTP Load Balancer.
  12. Confirm that all broken-reference warnings have cleared and validate successful application requests from more than one test location when appropriate.

Validation Checklist

  • The referenced IP Prefix Set exists.
  • The Prefix Set is enabled.
  • The Prefix Set name is spelled correctly.
  • The Prefix Set is located in the expected namespace.
  • The Service Policy references the correct namespace.
  • All repeated references across all field rules have been reviewed.
  • No Broken References Detected warning remains.
  • Application requests no longer return HTTP 502.
  • Request logs no longer show an unresolved Service Policy result.

Additional Information

An unresolved Service Policy result indicates that the policy or the policy-processing path could not be resolved successfully. When the unresolved result is associated with HTTP 502 and Service Policy authorization details, inspect the Service Policy and its referenced objects before investigating the origin server.
