Topic

The auto-lasthop module on a BIG-IP management interface provides the same functionality as the Auto Last Hop feature on the Traffic Mangement Microkernel (TMM) interfaces, where reply traffic is automatically addressed to the MAC address of the sender, without performing a route lookup or ARP resolution.

Description

When the auto-lasthop module is enabled, the BIG-IP management interface may not require a specific or default route back to the BIG-IP administrator's host machine and the BIG-IP system uses the lasthop MAC address to send the response back to the initial client. The auto-lasthop module is automatically loaded at boot time and enabled on the management interface by default.

Depending on the BIG-IP software version, you can either disable this feature by configuring a system db key, or using the tmsh command:

  • For BIG-IP versions below 14.0.0, you can manually prevent the kernel module from loading (see below for details)
  • For BIG-IP versions 14.0.0 or later, the feature can be disabled by using tmsh to modify the "ltm global-settings general mgmt-auto-last-hop" setting, or the system db key "mgmt.autolasthop".

In both cases, the change will not take effect until the config is saved, and the BIG-IP device is rebooted.

Support for the auto-lasthop module on a BIG-IP management interface

  • BIG-IP hardware platforms support the auto-lasthop module on a BIG-IP management interface
  • BIG-IP Virtual Edition (VE) supports the auto-lasthop module on the management interface only in BIG-IP versions prior to 14.1.0; BIG-IP VE 14.1.0 and later does not support the Auto Last Hop feature for the management interface.

Recommendations

In most situations, the default behaviour of the management lasthop kernel module is desired, as it reduces the management configuration overhead, ensuring that even without a management routes configured on the device, the BIG-IP management IP address is still reachable from outside of the directly connected subnet.

However, there are situations where the bahaviour of the module can produce undesirable results. In these cases, the module can be disabled, and the necessary management route(s) must be configured.

  • Where a device is reachable by tmm (for example, a pool member), and also communicates with the same BIG-IP's management address.  In this case, it may not be possible to reliably monitor the device
  • Where there is a section of reduced MTU present in the network path (for example, a network tunnel), and the BIG-IP management interface needs to respond to ICMP 'unreachable / Fragmentation needed' messages. to reduce the size of the payload. 

Note: From BIG-IP Virtual Edition ((VE) v14.1.0 and later, the kernel lasthop module is not installed on the device, and can not be activated.   For more information, refer to K55225090: BIG-IP VE no longer supports Auto Last Hop for management connections.  This limitation does not apply to physical BIG-IP devices.

Understanding the BIG-IP mangagement interface route lookup process

When the lasthop kernel module is enabled, routing exceptions will automatically be created for packets that arrive on the management interface.  The exceptions will bypass the normal linux routing lookup process, and force response packets to be addressed to the MAC address of the original sender, and the egress interface set to the management interface.    The effect of this behaviour is that management routes will not need to be configured to return such traffic back to the sender.  

When the lasthop kernel module is disabled (or not installed, as with BIG-IP Virtual Edition), a normal linux routing lookup will occur to find the next hop, and then ARP will be used to resolve the MAC address of that next hop.  On the BIG-IP platform, traffic sourced from the management-ip address is directed to special route table which only contains management routes. This means that traffic sourced from the management address (such as reply traffic to an incoming ssh connection) can not egress the box through a tmm interface, regardless of the configured tmm routes. If lasthop is disabled, and no management routes exist for the destination, then the routing lookup will fail, and the packet will be dropped.  In technical terms, an IP rule directs the kernel to use route table 245 for any traffic originating from the management IP address (this can be inspected with the linux commands 'ip rule show'  and  'ip route show table 245') 

The route that the linux kernel would select for a given destination can be inspected with the "ip route get x.x.x.x" command, for example, the following output shows a routing exception (cache) entry that forces traffic to the destination to egress to address 10.0.0.1 via the mgmt interface, using the BIG-IP's management address (192.168.1.1) as the source IP, with no nexthop  (via) attribute, even though the route table may return a different route.  The layer-2 MAC address that the packet would be sent to is not shown in the command output.

[root@bigip1:Active:Standalone] ~ # ip route get 10.0.0.1
10.0.0.1 dev mgmt  src 192.168.1.1
    cache  mtu 1500 advmss 1460 hoplimit 64

Without a routing exception installed by the lasthop module, the output would be different  - there is no cache entry, and a "via x.x.x.x" attribute will be shown to indicate the next layer-3 router (gateway)

[root@bigip1:Active:Standalone] ~ # ip route get 10.0.0.1
10.0.0.1 via 192.168.1.254 dev mgmt  src 192.168.1.1
    cache 

 

Disabling the Auto Last Hop feature

Impact of procedure: Performing the following procedure restarts all the services on BIG-IP system and all production traffic is affected. 

Note: The lasthop kernel module will still appear as loaded in the output of 'lsmod' after rebooting, but will be inactive.

BIG-IP 14.1.0 and later 

    1. Set the value of the mgmt-auto-last-hop parameter disabled, by entering the following command:
      tmsh modify ltm global-settings general mgmt-auto-last-hop disabled

    2. Restart the BIG-IP system by entering the following command:

      Standalone appliances:   full_box_reboot

      VIPRION or multiblade vCMP guests: clsh full_box_reboot

BIG-IP 14.0.x and earlier

    1. Log in to the Advanced Shell (bash).
    2. Rename the lasthop.modules file extension to lasthop.modules.bak:

      Standalone appliances: 
      mv -v /etc/sysconfig/modules/lasthop.modules{,.bak}

      VIPRION or vCMP guests: 
      clsh mv -v /etc/sysconfig/modules/lasthop.modules{,.bak}

    3. Restart the BIG-IP system by entering the following command:

      Standalone appliances:   full_box_reboot

      VIPRION or multiblade vCMP guests;  clsh full_box_reboot

Note: On BIG-IP 14.0.x and earlier, the changes will not survive a software upgrade, and will need to be re-applied to each new boot location

 

Re-enabling the Auto Last Hop feature

Impact of procedure: Performing the following procedure restarts all the services on BIG-IP system and all production traffic is affected. 
Note: The BIG-IP Virtual Edition (VE) platform from v14.1.0 and later does not support the kernel lasthop feature, and it can not be enabled.

BIG-IP 14.1.0 and later

      tmsh modify ltm global-settings general mgmt-auto-last-hop enabled

    2. Restart the BIG-IP system by entering the following command:

      Standalone appliances:   full_box_reboot

      VIPRION or multiblade vCMP guests: clsh full_box_reboot
