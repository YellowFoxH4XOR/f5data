Known Issue

The VIPRION system may falsely report the cluster status as offline. This issue occurs when all of the following conditions are met:

  • There are two or more blades installed in the VIPRION system
  • The min up members option is set to 1, and is also disabled
  • The primary blade is set to offline

By default, a one-cluster VIPRION system has its min up members option set to 1 and is disabled, which cannot be changed.

You can use the bigpipe cluster list all command to display the cluster configuration. For example, the following cluster configuration defines a default cluster that is affected by this issue:

cluster default {
enable
addr 172.28.72.34/24
min up members 1
min up members disable
members {
1 {
enable
priming disable
addr 172.28.72.134
}
2 {
enable
priming disable
addr 172.28.72.135
}
3 {
enable
priming disable
addr 172.28.72.136
}
4 {
enable
priming disable
addr 172.28.72.137
}
}
}

Impact

This is a cosmetic issue and does not affect the traffic processing capability of the affected VIPRION system.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The VIPRION system reports the cluster status under the System > Clusters > Cluster > Properties page in the Configuration utility with the following message:

    Offline (Enabled) - Too many cluster members HA offline

  • The VIPRION system reports the following message for the current redundancy state in the Configuration utility:

    Unit: Too many cluster members HA offline

Workaround

For a VIPRION system that has already encountered this issue, you can recover the system by restarting the clusterd processes on all the blades in the system. To do so, restart the clusterd processes on all blades by typing the following command from the command line:

Impact of workaround: Restarting the clusterd processes will interrupt traffic processing. F5 recommends that you perform this procedure during a maintenance window.

clsh bigstart restart clusterd
