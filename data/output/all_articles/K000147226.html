Description

  • You found that the value of duration_with_data_tx_delay is large in the requests log
  • You are investigating the Duration longer than expected.
  • You want to know the difference between duration_with_data_tx_delay and duration_with_no_data_tx_delay
  • You want to know the difference between duration_with_data_tx_delay and time_to_first_upstream_rx_byte
  • Interpreting F5 Distributed Cloud performance

Environment

  • F5® Distributed Cloud (XC)
  • HTTP Load Balancer (LB)

Cause

The F5 Distributed Cloud (XC) HTTP Load Balancer logs provide multiple timing metrics to help users analyze and troubleshoot request/response performance. Metrics such as duration_with_data_tx_delay and total_duration_seconds are included to distinguish between time spent on data transmission, processing within the load balancer, and upstream (origin) server response times. Large values in these metrics may indicate network latency, slow origin server response, or processing delays within the load balancer.

Recommended Actions

The typical flow is Client <=> F5XC Load Balancer <=> Origin Server (endpoint)

  • time_to_first_upstream_tx_byte => Interval between the first downstream byte received (from client) and the first upstream byte sent ( to origin server)
  • time_to_last_upstream_tx_byte - Interval between the first downstream byte received and the last upstream byte sent.

  • time_to_first_upstream_rx_byte - Interval between the first downstream byte received and the first upstream byte received

  • time_to_last_upstream_rx_byte - Interval between the first downstream byte received and the last upstream byte received

  • time_to_first_downstream_tx_byte - Interval between the first downstream byte received and the first downstream byte sent.

  • time_to_last_downstream_tx_byte - Interval between the first downstream byte received and the last downstream byte sent

  • duration_with_data_tx_delay = time_to_last_downstream_tx_byte - time_to_first_upstream_tx_byte

    • Basically indicates how much "time" its inside XC LB to do processing of the request/response (eg WAF , API detection , service policy , Bot detection etc. if enabled ) + time upstream spent to process

  • duration_with_no_data_tx_delay = time_to_first_downstream_tx_byte - time_to_first_upstream_tx_byte

    • Similar to duration_with_data_tx_delay, except that reference is taken from the moment first byte is sent to client

Additional Information

  • duration_with_no_data_tx_delay is a metric that measures the time it takes for a request to be processed by F5 Load Balancer / App stack(Customer Edge) without any data transmission delay
  • duration_with_data_tx_delay is a metric that measures the time it takes for a request to be processed by F5 LB / App stack(Customer Edge) including the time it takes to transmit data to upstream server
  • time_to_first_upstream_rx_byte is a metric that measures the time it takes for F5 LB / App stack(Customer Edge) to receive the first bytes of data from the upstream server.

As you can see, the End to end Latency section shows an specific metric. Let's understand what are those measurement

Client Latency ( <10ms) :

  • Measurement of RTT (round trip time) between client and to our F5XC HTTP LB proxy.

  • RTT – is the duration in milliseconds (ms) it takes for a network request to go from a starting point to a destination and back again to the starting point – obtained from TCP stats.

  • F5XC does not have visibility on routing or equipment in between. The metric obtains from how long it takes to establish a network/tcp/udp connection.

Server Latency ( 49.8ms) :

  • Server refers to L3/4 device (e.g., AWS EC2 server, Azure Server, VM, barametal, among others)

  • Measurement of RTT between F5XC to the origin pool – how long it takes when F5XC HTTP Load Balancer establishes a TCP connection and receive first byte back – from connection RTT perspective.

  • Metric obtains from TCP stats given from packets.

App Latency ( <1ms) :

  • App latency refers to the origin pool. F5XC doesn't have visibility beyond the origin pool. “App” to us is an endpoint.

  • Time taken for App to process the request and response back to F5XC.

  • The delay involved between sending a request (e.g., F5XC LB HTTP HEAD/GET to origin pool) and receiving a response on the upstream (note: upstream same meaning of origin pool) – This value minus the value in Server Latency to get “App Latency”.

Total Upstream Latency ( 49.8ms) :

  • The total latency is computed through - 
    time_to_first_upstream_rx_byte - (time_to_first_upstream_tx_byte + rtt_upstream_seconds)
