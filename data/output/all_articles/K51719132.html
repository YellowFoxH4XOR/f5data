K51719132: 502 bad gateway response returned from a pod within the same cluster

Type
Support Solution
Published
2022-05-26
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source
https://my.f5.com/manage/s/article/K51719132

Description

A 502 Bad gateway response may be received when attempting to connect from pod to pod within the OpenShift or Kubernetes cluster. The server, while acting as a gateway or proxy, received an invalid response from the upstream server it accessed in attempting to fulfill the request.

Environment

  • Aspen Mesh: 1.6.x - 1.11.x
  • Kubernetes: 1.17x - 1.22.x
  • Red Hat OpenShift: 4.6.x - 4.8.x
  • The pod you are attempting to connect to has an istio-proxy sidecar
  • May have traffic routing rules applied such as a virtual service or gateway
  • Attempting to connect to the service incorrectly

Cause

A 502 error occurs when there is no route available for the domain that is intended:

# kubectl exec sleep-557747455f-pldwd -- curl -Is httpbin.default.svc.cluster.local

HTTP/1.1 502 Bad Gateway
date: Fri, 15 Apr 2022 15:01:08 GMT
server: envoy
transfer-encoding: chunked

Log message received in the client log: 

# kubectl logs sleep-557747455f-pldwd -c istio-proxy

[2022-04-15T15:01:08.778Z] "HEAD / HTTP/1.1" 502 - direct_response - "-" 0 0 0 - "-" "curl/7.82.0-DEV" "f93f9b42-6fdb-4f7c-90fc-20e883eff839" "httpbin.default.svc.cluster.local" "-" - - 100.71.26.17:80 100.96.2.5:60730 - block_all

Recommended Actions

Look for the ports the service is listening on: 

# kubectl get svc httpbin
NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE
httpbin ClusterIP 100.71.26.17 <none> 8000/TCP 43h

Verify that the istio-proxy sidecar is listening on the service:

# istioctl proxy-config listener httpbin-74fb669cc6-bdx6n --port 8000
ADDRESS PORT MATCH DESTINATION
0.0.0.0 8000 ALL Route: 8000

Run the following curl command with the correct listener and path results in a 200 OK:

# kubectl exec sleep-557747455f-pldwd -- curl -Is httpbin.default.svc.cluster.local:8000
HTTP/1.1 200 OK
server: envoy
date: Fri, 15 Apr 2022 15:16:12 GMT
content-type: text/html; charset=utf-8
content-length: 9593
access-control-allow-origin: *
access-control-allow-credentials: true
x-envoy-upstream-service-time: 3

Verify the response in the istio-proxy container logs: 

# kubectl logs sleep-557747455f-pldwd -c istio-proxy --tail=1

[2022-04-15T15:16:12.981Z] "HEAD / HTTP/1.1" 200 - via_upstream - "-" 0 0 3 3 "-" "curl/7.82.0-DEV" "8a135d48-5975-4311-b1cf-1e2f9450cb86" "httpbin.default.svc.cluster.local:8000" "100.96.1.8:80" outbound|8000||httpbin.default.svc.cluster.local 100.96.2.5:52556 100.71.26.17:8000 100.96.2.5:53822 - default
