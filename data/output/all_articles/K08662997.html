Topic

Monitoring login attempts is an important part of network security. Successful and failed login attempts are recorded in the BIG-IQ system log files.

Description

You can view BIG-IQ system login attempts using the Configuration utility or from the Advanced Shell (bash).

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have administrator credentials to access the audit logs through the Configuration utility.
  • You have bash administrator credentials to access the system log files through the command line.

For BIG-IQ systems running the BIG-IQ Centralized Management identity, you can use either the Configuration utility or the command line method to review audit logs. While BIG-IQ systems running the DCD or License Manager identify, you are required to use the command line method to review audit logs.

The following three important log files track BIG-IQ login attempts:

  • /var/log/audit
    • Tracks successful login attempts and the start-to-end session details that are initiated through SSH using bash and tmsh.
    • Tracks successful and failed login attempts through HTTP using REST API or the Configuration utility.
  • /var/log/restjavad.0.log
    • Tracks details of the login attempts that are initiated through HTTP using REST API or the Configuration utility, including the source IP address and the authentication used by the provider.
  • /var/log/secure
    • Tracks the details of the successful and failed login attempts that are initiated through SSH using bash and tmsh, including the source IP address.

Procedures

  • Review login attempts using the Configuration utility (BIG-IQ Centralized Management only)
  • Review login attempts using the command line
  • View archived log files
  • Interpret the log files using scenarios

Review login attempts using the Configuration utility (BIG-IQ Centralized Management only)

To review login attempts from the System Audit Log using the Configuration utility, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Monitoring > AUDIT LOGS > System. The right screen will display the lines of system audit log.

    For example, the following set of field values displays when an admin account reaches its login failures limit:

    Client Address: 10.10.10.1
    Time: Apr 13, 2021 16:45:09(+08)    
    User: admin     
    Action: Login failures limit reached. Account locked.   
    Object Type: Login

    While an account is locked and the user attempts to log in, the log shows a line entry with another set of field values:

    Client Address: 10.10.10.1
    Time: Apr 13, 2021 16:45:18(+08)
    User: admin
    Action: Account is locked out.
    Object Type: Login

    For more information about enforcing the password policy on the BIG-IQ system, refer to K49507549: Configuring a secure password policy for the BIG-IQ system.

Review login attempts using the command line

To review login attempts from the command line in the /var/log/audit file, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IQ command line.
  2. The following three file destinations track login attempts on the BIG-IQ system:
    • /var/log/audit
    • /var/log/secure
    • /var/log/restjavad.0.log

    To view the contents of the log files, you can use either the less or cat command.

    For example, to view the /var/log/audit log file, enter the following command:

    cat /var/log/audit

    To review a username from the most recent /var/log/audit and /var/log/restjavad.0.log files that may have authentication failure attempts, use the following command syntax:

    grep -i "user <USERID>" /var/log/audit /var/log/restjavad.0.log | grep -i "fail"

    In this command, note the following:

    <USERID> is the username of a valid user in the BIG-IQ system

    For example, to review the log entries reported for user admin, enter the following command:

    grep -i "user admin" /var/log/audit /var/log/restjavad.0.log | grep -i "fail"

    The command output displays similar to the following example:

    /var/log/audit:Apr 26 02:11:51 bigiq.lab.local info rest(pam_audit)[19754]: 01070417:6: AUDIT - user admin - RAW: rest(pam_audit): User=admin tty=(unknown) host=(unknown) failed to login after 1 attempts (start="Mon Apr 26 02:11:49 2021" end="Mon Apr 26 02:11:51 2021").
    /var/log/audit:Apr 26 02:15:48 bigiq.lab.local info rest(pam_audit)[16235]: 01070417:6: AUDIT - user admin - RAW: rest(pam_audit): User=admin tty=(unknown) host=(unknown) failed to login after 1 attempts (start="Mon Apr 26 02:15:46 2021" end="Mon Apr 26 02:15:48 2021").
    /var/log/restjavad.0.log:[INFO][26 Apr 2021 10:11:51 UTC][/shared/authn/login AuthnWorker] User admin failed to login from 10.10.10.1 using the local authentication provider

    For more examples of reviewing the BIG-IQ system log files, refer to the Interpret the log files using scenarios section.

View archived log files

  • The /var/log/audit files are log-rotated daily, and renamed incrementally with a trailing .1, .2, and higher. In addition, the aged files are archived with gzip compression and renamed with the .gz suffix.

    For example:

    /var/log/audit.2.gz
    /var/log/audit.3.gz

    To view the /var/log/audit files with .gz in compressed form, you can use the zcat command.

    For example:

    zcat /var/log/audit.3.gz

    Similarly, to search a particular pattern from the .gz file, you can use the zgrep command.

    For example:

    zgrep 'user admin' /var/log/audit.3.gz

    Note: zgrep works on both zip-compressed and non-compressed files.

  • The var/log/restjavad.0.log files are rotated based on size limit, and renamed incrementally on the numeric number part of the file name.

    For example:

    /var/log/restjavad.0.log
    /var/log/restjavad.1.log
    /var/log/restjavad.2.log

    The restjavad log files are not compressed.

  • The /var/log/secure files are log-rotated daily, and renamed incrementally with trailing a .1, .2, and higher. In addition, the aged files are archived with gzip compression and renamed with the .gz suffix.

    For example:

    /var/log/secure.2.gz
    /var/log/secure.3.gz

    To view the /var/log/secure files with .gz in compressed form, you can use the zcat command.

    For example:

    zcat /var/log/secure.3.gz

    Similarly, to search a particular pattern from the .gz file, you can use the zgrep command.

    For example:

    zgrep 'user admin' /var/log/secure.3.gz

    Note: zgrep works on both zip-compressed and non-compressed files.

Interpret the log files using scenarios

  • Scenario 1: Locate all user accounts that have login failure attempts through HTTP using REST API or the Configuration utility

    To locate the login failures on /var/log/audit* files, the matching log entry will include failed to login. The zgrep command will locate the log entries that match the search pattern.

    Example command:

    zgrep "failed to login" /var/log/audit*

    Example output:

    /var/log/audit:Apr 23 08:02:43 bigiq.lab.local info rest(pam_audit)[23872]: 01070417:6: AUDIT - user admin - RAW: rest(pam_audit): User=admin tty=(unknown) host=(unknown) failed to login after 1 attempts (start="Fri Apr 23 08:02:41 2021" end="Fri Apr 23 08:02:43 2021").
    /var/log/audit:Apr 23 14:06:38 bigiq.lab.local info rest(pam_audit)[7616]: 01070417:6: AUDIT - user app20mgr - RAW: rest(pam_audit): User=app20mgr tty=(unknown) host=(unknown) failed to login after 1 attempts (start="Fri Apr 23 14:06:35 2021" end="Fri Apr 23 14:06:38 2021").

    The command output displays that the access is from rest(pam_audit), which means it was accessed through HTTP using REST API or the Configuration utility. To locate the source IP address and the authentication provider used for the login failures, you can use the date and time stamp on the events, and cross-reference them to the restjavad log files.

    Using the previous example output with the two lines of login failure dates and time stamps, you locate the details from the restjavad.*log files using the following commands:

    For the first event on Apr 23 08:02:43, rearrange the day, month, and time values to form the following command:

    grep "23 Apr .* 08:02:43" /var/log/restjavad.*.log

    The output from the restjavad log file appears similar to the following example:

    /var/log/restjavad.0.log:[INFO][23 Apr 2021 08:02:43 UTC][/shared/authn/login AuthnWorker] User admin failed to login from 10.10.10.1 using the local authentication provider

    For the second event on Apr 23 14:06:38, rearrange the day, month, and time values to form the following command:

    grep "23 Apr .* 14:06:38" /var/log/restjavad.*.log

    The output from the restjavad log file appears similar to the following example:

    /var/log/restjavad.0.log:[INFO][23 Apr 2021 14:06:38 UTC][/shared/authn/login AuthnWorker] User app20mgr failed to login from 10.10.20.15 using the local authentication provider

    The output shows that two login failures were attempted from the IP addresses 10.10.10.1 with username admin, and 10.10.20.15 with username app20mgr using the local authentication provider, which refers to the local password database on the BIG-IQ system.

  • Scenario 2: Locate the user accounts that have login failures initiated through SSH

    bash or tmsh access through SSH that uses local authentication provider will use the pam module. Therefore, the matching log entry will contain pam_unix(sshd:auth) and the matching string to look for authentication failure, the zgrep command will locate the log entries that matches the search pattern.

    Example command:

    zgrep "pam_unix(sshd:auth): authentication failure" /var/log/secure*

    Example output:

    /var/log/secure:Apr 23 16:49:04 bigiq.lab.local notice sshd[26295]: pam_unix(sshd:auth): authentication failure; logname= uid=0 euid=0 tty=ssh ruser= rhost=10.10.20.1  user=root
    /var/log/secure:Apr 23 16:49:15 bigiq.lab.local notice sshd[27531]: pam_unix(sshd:auth): authentication failure; logname= uid=0 euid=0 tty=ssh ruser= rhost=10.10.10.15  user=app10mgr

    The output shows that two SSH login failures were attempted from the IP addresses 10.10.20.1 with username root, and 10.10.10.15 with username app10mgr using the local authentication provider, which refers to the local password database on the BIG-IQ system.

  • Scenario 3: Locate the root user access through SSH with the start and end session details on the /var/log/audit* files, and the start session date is April 19

    Example command:

    zgrep "user root" /var/log/audit* | grep "start=\".*Apr 19.*\".*end="

    Example logs:

    /var/log/audit.7.gz:Apr 19 07:00:45 bigiq.lab.local info sshd(pam_audit)[9619]: 01070417:6: AUDIT - user root - RAW: sshd(pam_audit): user=root(root) partition=[All] level=Administrator tty=ssh host=10.10.10.2 attempts=1 start="Mon Apr 19 07:00:44 2021" end="Mon Apr 19 07:00:45 2021".
    /var/log/audit.7.gz:Apr 19 07:00:46 bigiq.lab.local info sshd(pam_audit)[9724]: 01070417:6: AUDIT - user root - RAW: sshd(pam_audit): user=root(root) partition=[All] level=Administrator tty=ssh host=10.10.10.2 attempts=1 start="Mon Apr 19 07:00:45 2021" end="Mon Apr 19 07:00:46 2021".
    /var/log/audit.7.gz:Apr 19 07:00:48 bigiq.lab.local info sshd(pam_audit)[9825]: 01070417:6: AUDIT - user root - RAW: sshd(pam_audit): user=root(root) partition=[All] level=Administrator tty=ssh host=10.10.10.2 attempts=1 start="Mon Apr 19 07:00:47 2021" end="Mon Apr 19 07:00:48 2021".

    The log entries show that there are three access records with start and end session details.

  • Scenario 4: Locate authentication failures through REST API on the /var/log/restjavad.*.log files

    Example command:

    grep "failed to login from" /var/log/restjavad.*.log

    Example logs:

    /var/log/restjavad.1.log:[INFO][19 Apr 2021 00:03:22 UTC][/shared/authn/login AuthnWorker] User admin failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][19 Apr 2021 08:03:18 UTC][/shared/authn/login AuthnWorker] User app11mgr failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][19 Apr 2021 16:03:40 UTC][/shared/authn/login AuthnWorker] User app12mgr failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][20 Apr 2021 00:04:17 UTC][/shared/authn/login AuthnWorker] User admin failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][20 Apr 2021 08:03:42 UTC][/shared/authn/login AuthnWorker] User app11mgr failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][20 Apr 2021 16:03:50 UTC][/shared/authn/login AuthnWorker] User app12mgr failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][21 Apr 2021 00:04:08 UTC][/shared/authn/login AuthnWorker] User admin failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][21 Apr 2021 08:03:42 UTC][/shared/authn/login AuthnWorker] User app11mgr failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][21 Apr 2021 16:02:46 UTC][/shared/authn/login AuthnWorker] User app12mgr failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][22 Apr 2021 00:03:21 UTC][/shared/authn/login AuthnWorker] User admin failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][22 Apr 2021 08:02:34 UTC][/shared/authn/login AuthnWorker] User app11mgr failed to login from 10.1.1.1 using the local authentication provider
    /var/log/restjavad.1.log:[INFO][22 Apr 2021 16:03:02 UTC][/shared/authn/login AuthnWorker] User app12mgr failed to login from 10.1.1.1 using the local authentication provider

    The log entries show a regular pattern on the time of 0003hrs, 0803hrs, and 1603hrs where the authentication failures on three different users occurred, and they were initiated from the same source IP address 10.1.1.1. In this situation, F5 recommends implementing a quick firewall rule on the BIG-IQ system to block the reported IP address. In addition, F5 recommends performing a security review on the system assigned with the reported IP address.

    In this example, the access from 10.1.1.1 originates from the management IP of the BIG-IQ system. You can use the built-in firewall on the BIG-IQ system to add a rule to block 10.1.1.1 access to all ports and all protocols of the BIG-IQ system.

    Example command:

    tmsh modify /security firewall management-ip-rules rules add { drop-login { source { addresses add { 10.1.1.1 } } action drop place-before first } }

    For more information about using the built-in firewall rules for the management interface, refer to F5 TMSH Reference on CloudDocs. To learn more about the configuration syntax for the management IP firewall rules, select Modules > Security > security firewall management-ip-rules.

Recommendations

In addition to maintaining strong authentication and password standards, monitoring login attempts can help with tracking both authorized and unauthorized attempts to access a BIG-IQ system. This information will provide administrators vital information for formulating a security policy to reacting against threats.

For more information about managing the audit logs, such as filtering and customizing the log display, refer to the Managing Audit Logs chapter of the BIG-IQ: Monitoring and Reports manual. For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.
