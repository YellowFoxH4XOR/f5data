Description

IPv6 Self-IP addresses may not be reachable between BIG-IP VE instances configured on KVM, while IPv4 connectivity between the same devices and outbound IPv6 connectivity to external destinations may function normally.

The issue manifests as persistent ICMPv6 "Destination unreachable: Address unreachable" errors when attempting to ping the peer's IPv6 Self-IP, despite successful reachability from other network locations

[root@F5.Active:In Sync] config # ping6 XXXX:XXXX:XXXX:XXXX::3 -I XXXX:XXXX:XXXX:XXXX::2
PING XXXX:XXXX:XXXX:XXXX::3(XXXX:XXXX:XXXX:XXXX::3) from XXXX:XXXX:XXXX:XXXX::2 : 56 data bytes
From XXXX:XXXX:XXXX:XXXX::2 icmp_seq=1 Destination unreachable: Address unreachable
From XXXX:XXXX:XXXX:XXXX::2 icmp_seq=2 Destination unreachable: Address unreachable

Environment

  • BIG-IP LTM
  • KVM platform
  • Interfaces configured as macvtap using <interface type='direct'>
  • IPv6 neighbour discovery and multicast traffic 

Cause

The root cause is the absence of the trustGuestRxFilters='yes' parameter in the KVM/libvirt XML interface definition for the BIG-IP VE instances.

Without this parameter, the macvtap interface on the KVM host does not set the ALLMULTI flag. As a result, the macvtap interface filters out IPv6 multicast frames — specifically, Neighbor Solicitation (NS) messages sent to the solicited-node multicast address of the peer's Self-IP. These frames are received on the underlying physical/VLAN interface but are silently dropped by macvtap before being passed into the guest VM.

This prevents NDP resolution between the two HA peers, breaking IPv6 Self-IP communication.

This behaviour is expected on a KVM hypervisor host and is not a BIG‑IP software bug or version‑specific defect.

Recommended Actions

 1. On the KVM host, identify the libvirt domain XML for the affected BIG-IP VE instance: virsh dumpxml <domain-name>

 2. Edit the domain XML (using virsh edit <domain-name>) and locate each <interface type='direct'> definition used for BIG-IP networking.

 3. Add trustGuestRxFilters='yes' to the opening <interface> tag. Example:

Before:

<interface type='direct'>
<mac address='52:54:00:7c:b7:e8'/>
<source dev='ens2f0.1030' mode='bridge'/>
<target dev='macvtap0'/>
<model type='virtio'/>
<alias name='net2'/>
<address type='pci' domain='0x0000' bus='0x08' slot='0x00' function='0x0'/>
</interface>

After:

<interface type='direct' trustGuestRxFilters='yes'>
<mac address='52:54:00:7c:b7:e8'/>
<source dev='ens2f0.1030' mode='bridge'/>
<target dev='macvtap0'/>
<model type='virtio'/>
<alias name='net2'/>
<address type='pci' domain='0x0000' bus='0x08' slot='0x00' function='0x0'/>
</interface>

 4. Apply the same change to all relevant network interfaces on both HA peer VMs.

 5. Restart the affected BIG-IP VE instances to apply the configuration change.

 6. After restart, verify that the ALLMULTI flag is now set on the macvtap interface on the host: ip link show dev macvtap0

3: macvtap0: <BROADCAST,MULTICAST,UP,LOWER_UP,ALLMULTI> mtu 1500 qdisc pfifo_fast state UP mode DEFAULT group default qlen 500

7. Verify IPv6 Self-IP reachability between BIG-IP units: ping6 <peer-self-ip>

Additional Information

When the BIG-IP initiates traffic to a destination first, the destination device automatically learns and caches the BIG-IP’s link-layer address. This can eliminate the need for NDP resolution.

This explains why in certain situations the issue is only seen on the self-IP/ HA VLAN, where communication occurs only between the two BIG-IP devices, both configured without the required trustGuestRxFilters setting on the hypervisors. Other destinations remain reachable because they can still rely on normal NDP discovery.
