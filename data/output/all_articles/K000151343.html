Description


When using an iRule(K4794539) to perform SNAT based on a data group lookup, connections to a BIG-IP LTM virtual server may be reset unexpectedly. The following error can appear in the LTM log:


TCL error: ... - bad IP address format (line 4)TCL error (line 4) invoked from within "snat $mapped_snat"


Additionally, TCPDUMP traces may show TCP RST packets with the cause:


rst_cause="[0x308e6a6:1860] iRule execution error"




Environment

Using the irule in K47945399


when CLIENT_ACCEPTED {

  set sourceip [IP::client_addr]

  set mapped_snat [class lookup $sourceip SNAT-Map]

  snat $mapped_snat

  }



Cause


If the client IP address is not present in the data group, the class lookup command returns an empty string. The iRule then attempts to execute snat with an invalid or empty value, resulting in a TCL error. This causes the BIG-IP system to reset the connection.



Recommended Actions


Update your iRule logic to ensure that SNAT is only applied when a valid mapping exists. For example:


when CLIENT_ACCEPTED {

  set sourceip [IP::client_addr]

  set mapped_snat [class lookup $sourceip SNAT-Map]

  if { $mapped_snat ne "" } {

    snat $mapped_snat

  }

  # Optionally, add logging or other actions for unmatched IPs

}


This prevents TCL errors and unwanted connection resets by ensuring that SNAT is only performed when a valid result is returned from the data group.
