K000157877: Downloading a file from AWS fails occasionally via BIG-IP

Type
Support Solution
Published
2025-11-23
Updated
2026-01-27
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1, 17.1.2
  • BIG-IP AFM: 17.1.2, 17.5.1
Source
https://my.f5.com/manage/s/article/K000157877

Description

  • You observe that client device sometimes fails to download files (out of order and delayed packets) from internet or AWS via BIG-IP. When the same file is being downloaded which are out-of-order packets or delayed, works fine when bypassing BIG-IP. Files gets downloaded normally.
  • In client and BIG-IP packet capture, you are able to see BIG-IP is forwarding packets immediately and all packets reach the client device.
  • TCP protocol has mechanism to deal with out of order and delayed packets but for some reason client device fails to process out of ordered and delayed packets which comes via BIG-IP. The same out of order and delayed packets is accepted by client device when bypassing BIG-IP.

Environment

  • LTM/AFM
  • 17.1.2, 17.5.1.2, 17.5.1.3
  • IP forwarding virtual server; fastL4 profile

Cause

Bug ID 2015973: BIG-IP is generating non-RFC-compliant TSval values that exceed the PAWS threshold defined in RFCs 1323/7323, causing client device to discard segments. Additionally BIG-IP is failing to preserve the same TSval on client and server side even when the TCP Timestamp Mode in fastL4 profile is Preserve (default setting).

Recommended Actions

To resolve this issue:

  1. Log in to the BIG-IP command line.
  2. Disable Timestamp Cookie in AFM DoS vector configuration:
    tmsh modify security dos device-config dos-device-config dos-device-vector { tcp-ack-ts { tscookie disabled }}
  3. Save the configuration:
    tmsh save sys config

Or disable TCP timestamp on the client device (Linux):

sysctl -w net.ipv4.tcp_timestamps=0

Additional Information

As per the PAWS mechanism, the next TSval should not cross beyond this calculation "s < t if 0 < (t - s) < 2^31". For example, BIG-IP TSval is 150. The next packet BIG-IP is sending the TSval is 2,250,325,700.

s = 150
t = 2,250,325,700
2^31 = 2,147,483,648

t - s = 2,250,325,700 - 150 = 2,250,325,550

t - s = 2,250,325,550 value is way greater than 2^31 = 2,147,483,648.

The value of t - s should be less than 2^31. If not, then it is not RFCs 1323/7323 compliant. In the example clearly BIG-IP TSval incrementing way beyond the compliant value, hence the client device is discarding the segments.
