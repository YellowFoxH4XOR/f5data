Description

Using an iRule to select a pool based on request URI may fail in some instances, when the pools and pool members are configured using the same IP and port combination, as well as same names, in different partitions.

Analyzing a packet capture will show the reset cause to be:

F5RST: Route domain not reachable (strict mode)

Environment

  • Virtual server without a default pool
  • iRule that performs lookup and routing to the appropriate pool based on URI attached to mentioned Virtual server
  • same pool members configured under multiple pools, under different partitions
  • strict isolation enabled on partitions

Cause

When the configuration on the BIG-IP uses the same pool members on multiple partitions that have strict isolation enabled, there is tendency that MCP might try to send the serverside traffic to the pool in a different route domain/ partition which causes a reset because the traffic will not be able to pass.

The configuration looks similar to this:

Recommended Actions

There are two recommended ways to avoid this issue.

  1. Use different pool names, or use the same pool if the services reside on the same pool anyway
  2. Use the full path to the pool in the iRules
}
ltm rule /Partition01/iRule.poolselect {
when HTTP_REQUEST {
    switch -glob -- [string tolower [HTTP::path]] {
        "/uri_string_1*" {
            pool /Partition01/pool.partition1.service1.com
            return
        }
        "/uri_string_2*" {
            pool /Partition01/pool.partition1.service2.com
            return
        }
        default {
            pool pool.default.service
            return
        }
    }
}
