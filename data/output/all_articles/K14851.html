Known Issue

The BIG-IP system may incorrectly handle responses for EDNS0 queries. The BIG-IP system may fail to truncate a response over the User Datagram Protocol (UDP), or unexpectedly truncate a response over TCP.

This issue occurs when the following condition is met:

  • The BIG-IP system provides the Domain Name System (DNS) response from DNS Express or DNS Cache.

When the BIG-IP system receives a UDP EDNS0 query with a max UDP size specified, and the response is larger than the specified value, the response is truncated (TC flag set) so the client can send the request over TCP again. For UDP queries without a max UDP size specified, responses larger than 512 bytes should be truncated. However, if the response is provided by DNS Express or DNS Cache, the response is not truncated.

When the BIG-IP system receives a TCP EDNS0 query, the response should never be truncated. However, EDNS0 responses that exceed 512 bytes provided over TCP by DNS Express or DNS Cache are unexpectedly truncated.

Impact

Requested resource records response may be too large over UDP, or the response may be truncated over TCP.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • BIG-IP iHealth lists Heuristic H438068 on the Diagnostics > Identified > Medium screen.
  • Affected DNS resolutions provided by DNS Express or DNS Cache fail.

Workaround

Impact of workaround: F5 recommends that you create an iRule that works best for your application environment. Additionally, adding an iRule increases the resources that the associated virtual server uses. Depending on the type and volume of the connections, this processing may introduce noticeable latency. F5 recommends that you test any such changes in an appropriate environment.

To work around this issue, you can use an iRule to track the query ID and conditionally truncate the response.
