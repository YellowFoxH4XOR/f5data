Topic

OneConnect? automatically activates when the following two circumstances occur simultaneously:

  • Delayed binding
  • Where the client and server have negotiated HTTP Keep-Alives

Note: Keep-Alives are negotiated when there is a Connection: Keep-Alive header present, or when HTTP version 1.1 is specified with the header Connection: close is not present. For a detailed explanation about how HTTP keep-alives are negotiated, refer to http://www.rfc.net/rfc2616.txt (HTTP/1.1 specification)

If both of these circumstances are not met, OneConnect? will not activate.

Important: You can disable OneConnect? using the no_http_one_connect command, but F5 recommends that you only do so when you are troubleshooting an issue and have exhausted all other possible setting changes.

BIG-IP version 4.5 introduced several changes to the OneConnect? feature. These changes are outlined as follows:

Web Aggregation and Web Parse

The functionality of OneConnect? is now split in to the following two parts:

  • Web Aggregation
  • Web Parse

These functions provide the following global variables:

  • web aggregate [all, port, ip, none]
  • web aggregate timeout [1-4294967295 seconds]
  • web parse [all, first]

These global variables allow you to control the behavior of OneConnect? with greater granularity than previous versions of BIG-IP. You can set these through the command line or in the Configuration utility under System, Advanced properties.

Web aggregation

The web aggregate variable manages the aggregation of multiple client-side TCP connections into fewer server-side TCP connections that are using the HTTP protocol with keep-alives enabled. Although it's called OneConnect?, this doesn't mean that there will only be a single TCP connection to the backend; rather, there is one TCP connection to a backend server for each simultaneously active client connection.

The web aggregate timeout variable controls the idle timeout of the TCP streams to the backend server and sends an RST packet if the stream is idle for longer than the timeout value, which is set at a default of 5 seconds. This process only closes the server-side connection, not the client-side connection. If the client sends another request after the server-side connection is closed, BIG-IP will open another connection to the webserver. This is why, in BIG-IP version 4.0 and later, you will see the BIG-IP sending RST packets to the servers after 5 seconds have elapsed with no new traffic on the internal connection.

To disable aggregation without turning off the HTTP parser, set the web aggregate variable to none and set the web aggregate timeout variable to the same value as the service timeout value. This configuration is essential if you want to run BIG-IP with delayed binding, but you do not want client aggregation to the servers. This also guarantees the identity of the person accessing the data behind the BIG-IP, avoiding a potential security issue since, when it is enabled, you may not be able to guarantee that only certain clients will be connected to specific nodes.

Note: For instructions about how to change web aggregate timeout, refer to K2351: Configuring the web aggregation (OneConnect) timeout.

Web parse

The web parse variable manages how the BIG-IP parses the HTTP requests. By setting the web parse variable to first, all HTTP traffic on the first TCP stream is inspected (on the first HTTP Request). Subsequent requests in the same TCP connection are ignored (this is the same behavior as BIG-IP version 3.3.1). The streams are then load balanced and persisted and treated as any other TCP connection for the duration of that TCP session. This setting can be useful in specific applications where the HTTP header is encoded, but not browser-based, such as the new Oracle thin clients; however, in most cases you want to set the web parse variable to all (the default) so that every HTTP request in the keep-alive stream is inspected.

Setting the internal variable in BIG-IP version 4.2, no_http_one_connect, to 1 is the equivalent to setting the web aggregate variable to none and the web parse variable to first in BIG-IP version 4.5. This, however, is not the best setting for persistence performance. In most cases you will want the web parse variable set to all, otherwise rules/cookie persistence will not behave as expected when your clients and servers use HTTP keep-alives.

Note: If you have to disable OneConnect? to troubleshoot (after all other avenues are exhausted), change this setting to first.
