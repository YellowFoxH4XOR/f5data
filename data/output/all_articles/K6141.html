Topic

Important: When using an iRule to collect traffic payload, you must limit the data collection to less than 32 megabytes (MB) for BIG-IP 11.x or less than 4 MB for versions prior to BIG-IP 11.x. For more information, refer to K6578: TMM will crash if an iRule collects too much data.

BIG-IP 11.x

In BIG-IP 11.x, the BIG-IP system allows iRules to initiate outbound TCP connections with the use of the iRule command sideband. For more information about the usage of the iRules sideband command, refer to the SIDEBAND page on DevCentral.

BIG-IP 9.x and 10.x

In BIG-IP 9.x and 10.x, the BIG-IP system does not allow iRules to initiate outbound TCP connections because the TCL socket command has been disabled. However, you may use the HTTP::retry command to initiate a new outbound HTTP connection to the same destination server, or a new destination server, when an HTTP request is received from a client.

The HTTP::retry command is primarily intended to mitigate issues associated with slow or failing back-end servers, allowing the same request to be replayed to a new or different server or pool upon failure. However, since the request submitted by the HTTP::retry command is configurable, and a new destination may be specified using the node or pool iRule commands, it is possible to send a completely different request to a different server. Data collected from the initial request/response may be used to construct the secondary request.

When the secondary request is sent and the server responds, the HTTP_RESPONSE event is again raised for the original client connection, making it possible to use information received from the secondary request to condition the action taken on the original request, or to pass along the secondary response data as part of the original request.

For example:

when CLIENT_ACCEPTED { set retrying 0 } when HTTP_REQUEST { set request [HTTP::request] if {$retrying == 0} { pool pool1 } else { pool pool2 set retrying 0 } } when HTTP_RESPONSE { HTTP::collect [HTTP::header Content-Length] } when HTTP_RESPONSE_DATA { set original_response [HTTP::payload] if { [IP::addr [IP::server_addr] equals 10.0.0.46] } { set retrying 1 HTTP::retry $original_response } elseif { [IP::addr [IP::server_addr] equals 10.0.0.47] } { set retrying 0 } }

In the previous example, the first server is a web server, the response from which is passed as the body of a request to a transcoding server. The response from the transcoding server is returned to the client.

Note: For additional information, refer to iRules and disabled TCL commands on F5 Cloud Docs.
