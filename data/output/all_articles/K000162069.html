K000162069: [CIS]IPAM ip-range extending issue

Source

Description

Using F5 BIG-IP Container Ingress Services (CIS) with the F5 IPAM Controller (FIC) default provider, modifying the FIC deployment --ip-range for an existing label can restart the IPAM pod and cause previously allocated IPs to be reallocated to existing Kubernetes Service type LoadBalancer objects. This can result in changed/lost service-to-IP mappings, duplicate BIG-IP virtual servers (old VS remains and a new VS is created with a different IP), and inability to restore prior mappings by editing IPAM CR instances.

Environment

  • Product: F5 BIG-IP Container Ingress Services (CIS) with F5 IPAM Controller (FIC)

  • Kubernetes/OpenShift environment; Service type LoadBalancer using annotation cis.f5.com/ipamLabel: <app-label>

  • FIC default provider using SQLite DB on persistent storage

  • FIC configured with --ip-range JSON label map

Cause

A design deficiency in F5 IPAM Controller where changing the --ip-range value for an existing label triggers a cleanup routine (CleanUpLabel()) that deletes existing allocation records for that IPAM label from the SQLite database. Subsequent reconciliation allocates new IPs and breaks existing mappings.

Recommended Actions

Avoid updating the --ip-range field unless you are running a version v0.1.13 or above.

Additional Information

  • This behavior is noted as a known limitation in release notes (“Updating the --ip-range in FIC deployment is an issue”).

  • When the allocation DB state is deleted, editing/restoring only the IPAM CR instance content may not persist because the controller reconciles based on the current DB and configuration state.
