Description

Procedure to create an external HTTP monitor using Curl command to monitor the status of the pool member. 

Note: You should use an EAV external monitor only when the specific logic needed to determine the health of a pool member is not found in the built-in BIG-IP monitors; a poorly written monitor script may use high amounts of BIG-IP cpu/memory resources.

Environment

  • External monitor
  • Curl 

Cause
None

Recommended Actions

Follow the below procedures to configure custom external monitor using Curl. 

Configuring the External monitor program and import to the BIG-IP system 

  1. Create an external monitor script or copy the sample script in the Additional Information section or from the command line of your BIG-IP device located in /config/monitors/sample_monitor to create an external monitor.
  2. Modify the sample script according to your monitoring requirements. 
  3. Save the script to a text editor.
  4. Import the script from BIG-IP Configuration Utility
    System > File Management > External Monitor Program File List
  5. A file is automatically generated after the script is imported under
    /config/filestore/files_d/Common_d/external_monitor_d.

    For example: If the name of the created file is curl_monitor_ex_68725_1
    /config/filestore/files_d/Common_d/external_monitor_d/curl_monitor_ex_68725_1

  6. Run the following command to make sure that the script syntax is accepted by the BigIP. If the syntax has issues, then logs mentioned under "Additional information" section can be noticed.
    sed -i 's/\r$//' /config/filestore/files_d/Common_d/external_monitor_d/\:Common\:curl_monitor_ex_68725_1

Configure the monitor and assign the External monitor script to the configured monitor 

  1. Configure the monitor from Configuration Utility > Local Traffic > Monitor
  2. Click Create
  3. Select the monitor type External
  4. Select the external program which you created in the previous step.
  5. Click Finish
  6. Assign the newly configured monitor to the pool.

Sample script
#!/bin/sh
# (c) Copyright 1996-2007 F5 Networks, Inc.
#
# @(#) $Id: http_monitor_cURL+GET,v 1.0 2007/06/28 16:10:15 deb Exp $
# (based on sample_monitor,v 1.3 2005/02/04 18:47:17 saxon)
#
# these arguments supplied automatically for all external monitors:
# $1 = IP (IPv6 notation. IPv4 addresses are passed in the form 
#                         ::ffff:w.x.y.z
#                         where "w.x.y.z" is the IPv4 address)
# $2 = port (decimal, host byte order)
#
# Additional command line arguments ($3 and higher) may be specified in the monitor template
# This example does not expect any additional command line arguments
#
# Name/Value pairs may also be specified in the monitor template
# This example expects the following Name/Vaule pairs:
#  URI  = the URI to request from the server
#  RECV = the expected response (not case sensitive)
#
# remove IPv6/IPv4 compatibility prefix (LTM passes addresses in IPv6 format)
IP=`echo ${1} | sed 's/::ffff://'`
PORT=${2}

PIDFILE="/var/run/`basename ${0}`.${IP}_${PORT}.pid"
# kill of the last instance of this monitor if hung and log current pid
if [ -f $PIDFILE ]
then
   echo "EAV exceeded runtime needed to kill ${IP}:${PORT}" | logger -p local0.error
   kill -9 `cat $PIDFILE` > /dev/null 2>&1
fi
echo "$$" > $PIDFILE

# send request & check for expected response
curl -fNs http://${IP}:${PORT}${URI} | grep -i "${RECV}" 2>&1 > /dev/null

# mark node UP if expected response was received
if [ $? -eq 0 ]
then
    rm -f $PIDFILE
    echo "UP"
else
    rm -f $PIDFILE
fi
exit
# End sample script


Note: If you want to match based on a header or response code you will need to use verbose output from curl using the -v option and then redirect the standard error (which is where verbose output is) to standard in so that your grep applies properly.

For example your curl should look like this:
curl -v http://${IP}:${PORT}${URI} 2>&1 | grep -i "${RECV}"  > /dev/null

Otherwise you will be unable to use the response codes and can only match on data within the body.  You can manually test your curl with something like this:
# curl -v http://10.12.15.16/index.html 2>&1 | grep -i "HTTP/1.1 404"
# echo $?

If the grep matched and got something back it returns a 0 which marks the member up. Otherwise it returns something else in which case the pool member would be marked down.  The 2>&1 before the grep is redirecting stderr to stdout so that the grep can match against it.
