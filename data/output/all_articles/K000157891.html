Description

I am unable to rerun an Ansible playbook to create and apply a new apm profiles using the bigip_apm_policy_import module, 

I do not have any issues running a playbook to create a new Access Policy as long as the virtual server and its Access Policy does not already exist.

I'm trying to re-deploy without deleting the current virtual server and update the active Access Policy. The option to force overwrite does not work.

 

Environment

  • using the Ansible Imperative Module in a playbook
  • BIG-IP APM Access Policy 
  • Automation using bigip_apm_policy_import Ansible module (or similar like REST API's or Terraform) 

Cause

Ansible Re-deploy (or even any direct REST API modification) is not supported when updating Access Policies. Only creation of new named policies is supported.

In the F5 BIG-IP Ansible Collections https://clouddocs.f5.com/products/orchestration/ansible/devel/ there is a clear distinction between Imperative APIs and Tasks and Declarative Tasks and they are published as seperate modules. 

This issue was originaly raised as https://github.com/F5Networks/f5-ansible/issues/1130 and there is no Declarative solution available.

 

Answer/Recommended Actions

When using Ansible for creating APM Access Policies be aware that the Imperative Module not idempotent and this means that re-running of create policy tasks is not supported.

A variety of APM features can be configured with the APM Wizard, or by using the APM Visual Policy Editor (VPE) and they do not have any API equivalents. When making any changes with VPE, the incremental changes cannot be cancelled, and cannot be easily reversed. A common strategy is to only make changes in (a time stamped) copy of the current working Access Policy.

At publication the most recent version of the Ansible Modules can be found at
https://galaxy.ansible.com/ui/repo/published/f5networks/f5_modules/
F5 BIG-IP Imperative Collection for Ansible, Version 1.39 released Sept 2025

This documentation is incorrect when referencing the "force" feature  and should be clarified with the next version to list this as not supported.

Additional Information

When using the APM Web interface to manipulate a specific Access Policy there are 3 available TMUI options under the menu

  • Access > Profiles / Policies : Access Profiles (Per-Session Policies)
    • Export... to create a named Access Profile export named profile_Common_{{YourAPname}}.conf.tar.gz (substitute your value in double brackets)
    • Copy... to use a Copied Profile Name (enter YourAPname, trying to copy an existing name will create a new profile with the sequential name YourAPname_1 )
    • and also Edit... to open a new window with the Visual Policy Editor to edit the policy flow and then subsequently save the changed version

From the command line TMUI interface, you can use the commands ng_export and ng_import to export and then create a new Access Policies (copy) K30575107
There are a number of other caveats to be aware of, and import/export across versions (especially backwards) is not generally supported. 
The Ansible bigip_apm_policy_import is the same as the ng_import command, and needs a policy to be ng_export to use as the source of the import.

The recommended workaround here is to use ng_export or the copy menu to export a date-stamped new Access Policies (e.g. use naming like MyVPN-YYMMDDx using date and sequence labels, for multiple archived versions) and if necessary to restore to that previous copy by resetting the Virtual Server to use a different Access Policy (note this change is service affecting). Once the changes are fully tested, older archived versions should be deleted to minimise the resource usage of unnecessary archive revisions.
