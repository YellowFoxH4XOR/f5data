Description

When using or managing your BIG-IP, you can notice really bad performance. Access to the GUI is not possible or performance is so bad that causes user sessions to be disconnected. You may notice that the performance of your applications gets impacted. You notice the same problem happening in other vCMP guests or blades in a VIPRION Chassis. You can also notice excessive memory consumption and sometimes high CPU on the control plane. Another symptom that you might observe is that the restjavad process is constantly restarting:

When you check /var/run/pamcache directory, you can notice that it is full of entries in several blades:

Environment

  • Users or APIs that make use of REST tokens are not deleted from cache /var/run/pamcache when expired or deleted.
  • Multi-slot VIPRION Chassis
  • vCMP Guest

Cause

Bug ID 1103369: DELETE of REST Auth token does not result in deletion of the pamcache token file on a multi-slot VIPRION chassis, vCMP guest, or VELOS tenant

 

A large number of REST tokens are not deleted from cache /var/run/pamcache when they are expired causing excessive memory consumption (cache is stored in an in-memory filesystem). csyncd syncs these tokens between blades causing the problem to propagate This can also contribute to pushing the control-plane CPU load up higher than it needs to be.

 

Recommended Actions

You can resolve this issue by upgrading to a version in which this is fixed: 17.1.0, 17.0.0.2, 16.1.3.3, 15.1.8.1, 14.1.5.3.

If the upgrade is not possible, restarting httpd and configuring csyncd not to monitor the /var/run/pamcache directory solves the issue. After this, a reboot needs to be done in order to clear the entries contained in /var/run/pamcache (you need to do this blade by blade). Here are the steps you can follow. The steps taken depend if you run a VIPRION or non-VIPRION host.


Important: Traffic processing is briefly interrupted while the BIG-IP system reboots. To avoid such scenarios, perform the activity in a maintenance window. It should be advisable to create a UCS backup prior to performing this procedure.

 

Steps for VIPRION (with or without vCMP Guest)

1. Log in to a blade.

2. Verify the tokens to be deleted:
          clsh "find /run/pamcache -regextype posix-extended -type f  -regex '/run/pamcache/[A-Z0-9]{26}' -print"
3. Delete the tokens you have previously verified:
          clsh "find /run/pamcache -regextype posix-extended -type f -regex '/run/pamcache/[A-Z0-9]{26}' -delete"
4. Restart httpd service:

tmsh restart sys service httpd

5. If you see that restjavad is constantly restarting, manually restart it also:

tmsh restart sys service restjavad

6. Configure csyncd not to monitor /var/run/pamcache directory and then reboot to clear pamcache entries:

clsh "cp /etc/csyncd.conf /etc/csyncd.conf.$(date +%Y%m%d_%H%M%S)"

clsh "sed -i '/run\/pamcache/,+2s/^/#/' /etc/csyncd.conf"

clsh "bigstart restart csyncd"

reboot


7. Wait for the blade to come back online and repeat the same steps on each blade:
 

Steps for non-VIPRION vCMP Guest:
 

1. Log in to a vCMP guest.

2. Restart httpd service:

tmsh restart sys service httpd

3. If you see that restjavad is constantly restarting, manually restart it also:

tmsh restart sys service restjavad

4. Configure csyncd not to monitor /var/run/pamcache directory and then reboot to clear pamcache entries:

reboot
