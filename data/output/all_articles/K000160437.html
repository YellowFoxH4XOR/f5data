Description

TLS handshakes with the KYBER768 cipher Post-Quantum Key Agreement (MLKEM768) offered may have segmented ClientHello requests.

This may cause issues for iRules that expect the ClientHello to be within a single packet, or for legacy intervening devices that examine TLS handshakes.

Environment

  • BIG-IP LTM
  • Client-SSL Profile
  • iRules
  • X25519MLKEM768 key exchange

 

Cause

A typical ClientHello from prior to the introduction of X25519MLKEM768 (Kyber768) was around 500 bytes. This typically allows the ClientHello to fit into a single TCP segment.

The Key Agreement data present in the ClientHello handshake when X25519MLKEM768 is offered by the client is 1212 bytes. This makes the typical ClientHello more than 1700 bytes. On many networks this exceeds the TCP Maximum Segment Size (MSS).

 

The BIG-IP Client-SSL profiles do not have an issue with segmented ClientHello requests.

However, some iRules used to examine an incoming ClientHello at the TCP level (i.e in the CLIENT_DATA event) may assume that the ClientHello will only fit into a single TCP segment, and so may not correctly assemble and examine segmented ClientHello requests. The most common use of this type of iRule is when examining the ClientHello for a Server Name Indication extension to allow a Client-SSL profile to be selected.

 

In addition, some legacy network devices that examine TLS ClientHello handshakes (for IPS or other tracking) may also not be capable of correctly examining/handling segmented ClientHello requests. This may prevent the TLS Handshake from completing if such a device corrupts the TCP data stream.

 

Answer/Recommended Actions

iRules that rely on examining the entire ClientHello should be modified to collect multiple TCP segments until all the ClientHello has been received. An example of such an iRule is provided below in the Additional Information (from DevCentral).

 

Identifying legacy devices in the network that interfere with segmented ClientHello requests is more difficult. Very often the presence of such a device has to be determined by ongoing connection failures from modern Web Browsers (which all support Kyber768) and examination of traffic captures from the client and the BIG-IP.
