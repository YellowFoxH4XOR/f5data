Topic

This article discusses the support for large DNS zones in DNS Express.

Description

DNS Express is a feature that allows the BIG-IP system to perform the function of a high-speed authoritative DNS server and answer DNS queries for a DNS zone as well as respond to zone transfer requests from specified DNS clients on behalf of an authoritative DNS server.

Beginning in BIG-IP 14.0.0, 13.1.0.2, and 12.1.3.1, the DNS Express supports large DNS zones comprising several hundred thousand to several million records (depending on the underlying hardware). The support for large DNS zones is not enabled, by default, and requires tuning a number of related database variables. The following table provides a list of the database variables related to the support for large DNS zones.

Database variable name and parameterDefault valueDescription
dnsexpress.hugepages <value>0When the <value> is non-zero, DNS Express stores the zone data in huge memory pages of 2MB each instead of regular memory page sizes. The BIG-IP system attempts to reserve the configured amount of memory (<value> x 2MB) for the DNS Express zone data. The memory specified here is excluded from the memory allocated for the Traffic Management Microkernel (TMM).

Note: You must restart the BIG-IP system for changes to this database variable to take effect. F5 recommends performing the change during a scheduled maintenance window appropriate for your environment.

When the <value> is set to zero, DNS Express reverts back to the default state and stores the zone data in regular memory pages (typically 4KB).
dnsexpress.persisthugepages <true | false>falseWhen this database variable is set to true, the BIG-IP system saves the zone data in memory to /shared/zxfrd directory to persist the data across restarts. This allows DNS Express to load the data from the saved files into memory whenever a restart occurs. The save is scheduled for the time in seconds set in the database variable dnsexpress.dbwritedelay after any successful Authoritative Transfer (AXFR) or Incremental Zone Transfer (IXFR) that results in a change to the zone data. The dnsexpress.dbwritedelay database variable controls the delay in seconds between the time zxfrd updates its internal database and the time zxfrd creates an updated zone database for TMM to serve.

When this database variable is set to false, the DNS Express does not save the zone data in memory to the filesystem and needs to request a zone transfer from the authoritative DNS server whenever a restart occurs.

dnsexpress.notifyport <value>0When the <value> is set to non-zero, the zxfrd process listens directly on the configured database (UDP) port on all self IPs and management address. This eliminates the need to wait for TMM to forward the DNS Notify message from the authoritative DNS server to DNS Express and may help to avoid potential non-delivery of the DNS Notify message (due to it being a UDP packet) on a heavily loaded system. However, configuring this database variable means that several checks performed by TMM will be bypassed. This includes but not limited to the following:
  • The zxfrd process does not verify the TSIG entry in the DNS Notify message nor does it use the TSIG entry in its response.
  • Any rate limiting configured for the DNS Notify messages is not enforced.
  • The zxfrd process does not verify the originating IP address of the DNS Notify message against the configured allow list for certain versions. For more information on this, refer to K45435121: DNS Express vulnerability CVE-2018-5538.

Note: You should always ensure that the configured UDP port is not in use by any other processes. 

When the <value> is set to zero, the DNS Notify messages is processed by the configured DNS listener and TMM then forwards the messages to the zxfrd process using the mcpd process to perform the AXFR/IXFR.
dnsexpress.xfrnotifydelay <value>5This DB variable controls the delay in seconds between the time the zxfrd process receives a DNS Notify message from the authoritative DNS server and the time it schedules an AXFR/IXFR.

Note: This does not mean the zone transfer occurs immediately after this delay as the start of the zone transfer also depends on the load on the BIG-IP system, the authoritative DNS server and the network between them; as well as the size of the zone transfer.

dnsexpress.rrperzonestats <true | false>trueWhen this database variable is set to false, the BIG-IP system does not update the RR per zone statistics. This may help to improve performance on a loaded system.

Recommendations

When you configure support for a large DNS zone in DNS Express, F5 recommends that you start with about two and a half times the memory that the authoritative DNS server uses that loads the large DNS zones and adjust, as necessary, for your application environment. For example, if your authoritative DNS server uses about 10GB of memory to load the large DNS zone data, you may want to start by configuring 25GB for the dnsexpress.hugepages database variable. This means setting the value of dnsexpress.hugepages database variable to 12800 (2 MB of pages gives about 25 GB).

Depending on the type of authoritative DNS server, you should be able to locate the memory usage of the DNS process from the operating system’s tasks/activity report. For example, you can find the memory usage of BIND on a Linux server by locating the VIRT column from the output of the top utility. For detailed instructions about locating the memory usage of your authoritative DNS server, refer to the documentation from your DNS server vendor.

Modifying a database variable

Impact of procedure: F5 recommends that you test changes in an appropriate environment before scheduling a maintenance window to effect the changes in your production environment.

  1. Log in to the TMOS Shell (tmsh).
  2. To modify a database variable, use the following command syntax:

    modify sys db <DB variable name> value <value>

    For example, if you want to modify the dnsexpress.hugepages database variable to the value of 12800, type the following command:

    modify sys db dnsexpress.hugepages value 12800

  3. Save the changes by typing the following command:

    save sys config
