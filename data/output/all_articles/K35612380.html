Description

When you use Wireshark to analyze a packet capture, it performs analysis on TCP connections and is able to flag certain behaviors that can help understand TCP performance. Some of these correspond to specific TCP messages, while others are Wireshark highlighting a connection state. These flags include:

  • TCP Window Full
  • TCP ZeroWindow
  • TCP Retransmission (including variants)
  • TCP Dup Ack

This article discusses how to use this analysis feature to help understand and optimize TCP performance with BIG-IP. The following applies primarily when using a Standard virtual server, since BIG-IP does not participate in TCP when using a FastL4 virtual server (it only edits the header as needed).

Note: when using certain settings with FastL4 (particularly Forwarding virtual servers), Wireshark may interpret normal traffic as duplicate ACKs or retransmissions since captures may show packets twice (once for ingress to BIG-IP, once for egress).

Important: These behaviors are part of normal TCP operation and can occur during normal conditions because networks are complex systems, so should not be taken as evidence of a problem.

Environment

None

Cause

This article uses the following terminology specific to TCP:

  • Receive Window - also simply called the TCP window, this is advertised by a TCP receiver to its peer. It is the window that is visible in the capture, and may be different in either direction in a connection. The receive window is usually the size of the available receive buffer. TCP receivers can adjust the size of the receive window by changing the window value in ACKs they transmit. On BIG-IP the maximum size is controlled by the Receive Window TCP profile option.
  • Send Window - technically the congestion window, this is an internal value in a TCP sender which indicates the maximum amount of data it can send without receiving an acknowledgement. This is constantly adjusted by the TCP Congestion Control algorithm, and on BIG-IP the maximum size is controlled by the Send Buffer TCP profile option. This value cannot be observed in a capture; it can be inferred, if a sender stops sending data even though the recipient's receive window is not full, but the actual value is never sent on the network.
  • Bytes In Flight - this is the term Wireshark uses to indicate the amount of unacknowledged data a TCP sender has transmitted. It is always less than or equal to the recipient's receive window.

TCP Window Full: if a TCP sender transmits a packet which results in the number of unacknowledged bytes - or bytes in flight - being the same as the recipient's receive window, this is called filling the window, and Wireshark reports TCP Window Full.
Example: Client is configured on WAN and server on LAN

When you see TCP Window Full flags, it usually means that the sender is using the full capacity of the TCP flow, limited by the recipient's receive window. The network may have higher capacity. See below for more detail on this.

TCP Zero Window: When a TCP receiver's buffer begins to fill, it can reduce its receive window. If it fills, it can reduce the window to zero, which tells the TCP sender to stop sending. This is called "closing the window". Typically this indicates that the network is delivering traffic faster than the receiver can process it.

When BIG-IP closes its receive window, it usually means that BIG-IP is receiving data faster than it can send it on the peer flow. This is normal in situations where, for example, the server-side network is faster than the client-side network, and there is a large transfer from the server to the client. BIG-IP buffers a certain amount of data then closes its receive window when the proxy buffer reaches the configured high-water mark.

TCP Retransmission: When TCP sends a packet, it waits for an acknowledgment to confirm if the packets sent by the sender are received by the receiving party. If the acknowledgment is not received within the timeout interval (known as the retransmission timeout or RTO), the sender retransmits the packet.


Retransmissions can also be forced when a TCP sender receives duplicate ACKs.

Wireshark differentiates several categories of TCP retransmission; see the Wireshark TCP Analysis documentation for more information.

TCP Duplicate ACK: When a TCP receiver receives packets out of order, which it interprets as data loss, it sends an ACK indicating the expected sequence number. After two duplicate ACKs, a TCP sender begins retransmission.

Recommended Actions

Use the following guidelines when you observe the above behaviors while troubleshooting TCP performance.

TCP Window Full

  • Check BIG-IP configuration. The default TCP profile on most versions of BIG-IP has Send Buffer and Receive Window settings of 65535, which also limits the receive window of remote endpoints (that is, clients and servers) to 65535 since it disables Window Scaling. If you believe the BIG-IP window settings are limiting throughput, it is usually safe to experiment by doubling them until you stop seeing a performance improvement. The Receive Window setting should be increased if bandwidth is limited transmitting to BIG-IP, and the Send Window setting should be increased if bandwidth is limited transmitting from BIG-IP to another device.

    Note: Increasing Send Buffer and Receive Window increase the maximum memory consumed per connection, so F5 recommends monitoring TMM memory use when adjusting these settings on busy virtual servers. However, this memory is only used when needed and connections only max out the buffer limit during maximum throughput.
     
  • Check remote configuration. Certain TCP devices, particularly older OSes or less powerful devices, may use smaller TCP buffers to limit memory use. This may not be configurable.


TCP Zero Window

If BIG-IP advertises Zero Window:

  • Check the peer flow - for example, if you see Zero Window on the server-side, check the client-side flow. Zero Window usually indicates that throughput is limited by the peer flow.
  • Check BIG-IP system performance and features. If BIG-IP is taking a long time to process data, which can happen if it is heavily loaded and performing heavy processing, BIG-IP itself can introduce delay.
  • If it takes a long time (relatively) for the remote system to begin transmitting again after BIG-IP opens its receive window, you may see performance improvements from increasing the Proxy Buffer settings which allow BIG-IP to buffer data in between client-side and server-side TCP flows. There is no set guideline for these; higher settings may improve performance with high reception delays, but oversized proxy buffers can introduce delays in delivering data on high-performance networks. For more details on the Proxy Buffer settings and their operation, see K3422: Overview of content spooling.

    Note: Increasing Proxy Buffer settings increase the maximum memory consumed per connection, so F5 recommends monitoring TMM memory use when adjusting these settings on busy virtual servers. However, this memory is only used when needed and connections only max out the buffer limit during maximum throughput.

TCP Dup Ack and TCP Retransmissions

These behaviors are typically related. These usually indicate network loss. Loss may or may not be an issue; TCP is designed to increase throughput until loss is observed to estimate network capacity, so if you see occasional duplicate ACKs and retransmissions with stable throughput, you may be observing normal TCP behavior.

Additional Information

If you know the characteristics of the end-to-end network, the required Send Window and Receive Buffer settings (that is, the required TCP window) may be estimated using the bandwidth-delay product (BDP). This is the product of the bandwidth (usually measured in bits per second) and round-trip-time (RTT, or delay) to the client, expressed in bytes. Note that RTT is usually expressed in milliseconds and bandwidth is usually expressed in kilo-, mega-, or gigabits per second, so it's necessary to adjust the units accordingly.

For example, for a network that can carry 40 megabits per second (Mbit/s) and an RTT of 50 milliseconds, the BDP is:

40,000,000 bit/s * 0.05 s = 2,000,000 bit 8 bit/byte = 250,000 bytes

In order to fill this link, that is in order to fully saturate the bandwidth under ideal conditions, the TCP window must be at least 250000 bytes.
