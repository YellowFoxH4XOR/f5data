Topic

The BIG-IP LTM Extended Application Verification (EAV) monitors run a service checker program to verify the status of pool member applications by starting the application remotely on the server. When running an EAV monitor, the BIG-IP system calls an external program located in the /usr/bin/monitors directory. The application status is reported to the bigd process, which manages health checking for the BIG-IP LTM system.

For example, the FTP EAV monitor calls the FTP_monitor script on the BIG-IP LTM system, which connects to the pool member and attempts to download a specified file to the /var/tmp directory. If the file is not retrieved or the FTP connection fails, the bigd process determines that the check is not successful.

Since EAV monitors run as external programs and are managed by the Linux host, they are not part of the Traffic Management Microkernel (TMM). As a result, EAV monitors generally require more system overhead and have more of a performance impact on the BIG-IP LTM system than Extended Content Verification (ECV) monitors. In some cases, running a large number of EAV monitors can cause performance issues on the BIG-IP LTM system.

For example, the resident memory footprint of an EAV monitor is at least 2 megabytes while it is running. When the nodes are responsive and the monitor finishes the check in less than 10 ms, little impact affects the BIG-IP LTM system resources. However, if the network is busy and the nodes are down, or slow to respond, the EAV monitor can fail to report its status to the bigd process in a timely fashion.

When the EAV monitors used in a configuration are causing higher than average memory usage on the BIG-IP LTM system, you may decrease the load on the system by replacing the EAV monitor with an ECV monitor. For example, if you are using the TCP Half Open EAV monitor, consider replacing it with a TCP ECV monitor.

Note: For more information about EAV monitors and ECV monitors, refer to the Configuration Guide for BIG-IP Local Traffic Management.
