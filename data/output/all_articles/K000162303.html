K000162303: BIG-IP LTM Pool Members Remain Offline When an HTTPS Monitor Checks HTTP Services

Type
Support Solution
Published
2026-08-02
Updated
2026-08-02
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.0
Source
https://my.f5.com/manage/s/article/K000162303

Description

Newly added BIG-IP LTM pool members remain offline even though they are enabled and their service ports are reachable. The monitor status reports "No successful responses received before deadline" and "Monitor Status: down." When an HTTPS monitor is assigned to a backend service that uses plain HTTP, TLS testing fails with "SSL23_GET_SERVER_HELLO:unknown protocol."

 

Environment

BIG-IP LTM version 17.5.0

Load-balancing pool with newly added members

Backend services listening on ports such as 3001 and 3002

Pool assigned an HTTPS monitor

Backend application protocol confirmed as HTTP

TCP connectivity to service ports is available

Node-level monitoring not enabled; member availability determined by pool monitorCause

 

Cause

The pool was using an HTTPS health monitor against backend services that served plain HTTP. The monitor initiated a TLS handshake, but the backend returned non-TLS HTTP data, producing the SSL23_GET_SERVER_HELLO:unknown protocol error.

 

Consequently, the monitor marked the members offline even though TCP connectivity was available. Assigning an HTTP monitor resolved the issue.

 

Answer/Recommended Actions

  1. Confirm the protocol used by the backend service on each affected port.
  2. Test TCP connectivity from the BIG-IP system to the backend service port:  
    nc -v <node_ip> <port>
  3. If the service uses plain HTTP, create an HTTP monitor with request and response values appropriate for the application:  
    tmsh create ltm monitor http /alg-nonprod/http-monitor 
  defaults-from http 
  interval 5 
  timeout 16 
  send "GET / HTTP/1.1\r Host: <hostname_or_IP>\r Connection: close\r \r " 
  recv "200"
    Confirm the correct request path, Host value, and expected response with the application team.
  4. Assign the HTTP monitor to the pool:  
    tmsh modify ltm pool /alg-nonprod/https-pool monitor /alg-nonprod/http-monitor
  5. Save the BIG-IP configuration: tmsh save /sys config partitions all
  6. Verify the pool-member status:  
     tmsh show ltm pool /alg-nonprod/https-pool members
     Members should transition to Available after the HTTP monitor receives the expected response.
  7. If the pool contains both HTTP and HTTPS services, use one of the following designs:
    1. Assign protocol-appropriate monitors at the individual member level.
    2. Separate HTTP and HTTPS services into different pools.
  8. For member-specific monitoring, assign the HTTP monitor only to the applicable HTTP member:  
    msh modify ltm pool /alg-nonprod/https-pool members modify {
  /alg-nonprod/<http_member>:<port> {
    monitor /alg-nonprod/http-monitor
  }
}

 

Additional Information

  • A member can be enabled while its availability is offline. These are separate states.
  • A node may show "Availability: unknown" and "Node address does not have service checking enabled" when no node-level monitor is assigned. In that configuration, pool-member availability is controlled by the pool-level monitor.
  • Use HTTPS monitors only when the monitored backend service supports HTTPS/TLS on the specified port.
  • Use an application-appropriate receive string, such as "200", to validate the expected health response rather than checking only TCP connectivity.
