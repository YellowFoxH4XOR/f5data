Known Issue

This is the result of a known issue. The iRule parser may fail to correctly parse and load an iRule when the configuration is reloaded using the bigpipe load command, even though the iRule loads correctly using the Configuration utility. This issue occurs when one of the following two conditions are met:

  • An opening brace is followed by data or a command
  • An iRule with an unquoted string contains the // or the /* patterns

Note: The BIG-IP system uses the bigpipe load command to reload the configuration in the following cirumstances:

  • Upon invocation of the bipipe load command
  • When the system reboots
  • Upon invocation of the bigstart restart command
  • After synchronizing the configuration from the peer

In BIG-IP LTM version 9.4.1, the configuration file will load without reporting an error. However, when the bigpipe list command is used to display the running configuration, the failed iRule and all objects defined after it in the bigip.conf file are missing from the configuration. The bigip.conf file still contains all the configured objects.

In BIG-IP LTM version 9.4.2 through 9.4.6, and 9.6 through 9.6.1, the following error message will report at the command line when the configuration file load fails:

BIGpipe parsing error (Line 45):   012e0021:3: The requested attribute () for 'rule' is invalid.

When the bigpipe list command is used to display the running configuration, the failed iRule and all objects defined after it in the bigip.conf file are missing from the configuration. The bigip.conf file still contains all the configured objects.

An opening brace followed by data or a command

This issue occurs when the parser encounters an opening brace followed by data or a command. This issue does not affect loading the iRule from the Configuration utility for the first time. However, subsequent loads will fail when the iRule is read, as the iRule is copied verbatim to the configuration file. This issue also applies to a system reboot, or when a bigpipe load command is issued from the command line.

For example, the following iRule will fail to load from the command line as there is data following the open braces. The server_pool statement is immediately followed by the action to occur when selected. The syntax correctly loads when it is entered from within the Configuration utility and written to the configuration file maintaining the same layout. However, when the configuration file is loaded after a reboot or when the bigpipe load command is used, the iRule parser fails to load the iRule due to the action body immediately following the server_pool statement:

rule redirect_rule {  when LB_FAILED {    switch [LB::server pool] {      server_pool { log local0. "LB_FAILED, server_pool" }      default { log local0. "LB_FAILED, default" }    }  }}

An iRule with an unquoted string contains the // or the /* patterns

This issue also affects the // and /* patterns as displayed in the below iRule example. The double forward slash ( // ) and the forward slash and asterisk ( /* ) patterns, in addition to the text following them, are considered to be comments by the iRule interpreter:

rule switch_rule {
when HTTP_REQUEST {
switch -glob [string tolower [HTTP::uri]] {
/static/* -
//shared* {
pool http_pool
}
}
}
}

F5 Product Development tracked this issue as CR85806, and it was fixed in BIG-IP 9.4.7 and 10.0.0. For information about upgrading, refer to the BIG-IP LTM, ASM, GTM, Link Controller, PSM, or WebAccelerator Release Notes.

Workaround

You can work around this issue by modifying your iRule. Refer to one of the following two workarounds, depending on which condition caused the known issue.

An opening brace followed by data or a command

You can work around this issue by modifying the iRule to add carriage returns after each opening brace.

The following iRule example will load and parse correctly because no additional data exists after the opening braces. The iRule parser correctly reads and loads this statement when the configuration file is loaded on reboot, or when the bigpipe load command is used:

rule redirect_rule2 {  when LB_FAILED {    switch [LB::server pool] {      server_pool {         log local0. "LB_FAILED, server_pool"         }      default {         log local0. "LB_FAILED, default"      }    }  }}

An iRule with an unquoted string contains the // or the /* patterns

You can work around this issue by escaping the offending characters with a backslash character ( \ ), or enclosing any affected pattern with double quote characters ( " ), as displayed in the following corrected iRule:

rule switch_rule2 {
when HTTP_REQUEST {
switch -glob [string tolower [HTTP::uri]] {
"/static/*" -
"//shared*" {
pool http_pool
}
}
}
