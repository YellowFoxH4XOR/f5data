K000162419: Goodput may report values near 1TB

Type
Support Solution
Published
2026-07-23
Updated
2026-07-23
Applies to
  • BIG-IP
  • BIG-IP APM
Source
https://my.f5.com/manage/s/article/K000162419

Description

BIG-IP VE deployments on VMware ESXi may experience packet loss, VPN latency, application monitor failures, and unusually high TCP Analytics Goodput values that do not match the actual interface throughput. Goodput may report values near 1 Tbps while BIG-IP CPU, memory, interface, and packet-drop statistics appear normal. VMware monitoring may show a NetWorld thread saturating a single physical CPU core.

Environment

  • BIG-IP Virtual Edition deployed on VMware ESXi.
  • VMXNET3 virtual network interfaces.
  • BIG-IP APM and BIG-IP LTM modules.
  • APM VPN and LTM virtual servers.
  • TCP Analytics enabled for traffic monitoring.
  • BIG-IP VE configured as an active/standby pair.
  • Physical interface throughput substantially lower than the Goodput value displayed by TCP Analytics.

Cause

The root cause was a VMware ESXi VMXNET3 network-processing configuration issue.

The default VMXNET3 settings did not provide adequate Receive Side Scaling (RSS) and multiqueue processing for BIG-IP VE. Network interrupts and processing were therefore concentrated on a single physical CPU core. The associated NetWorld thread became saturated during traffic increases, causing:

  • Increased network latency.
  • Packet loss affecting traffic traversing the BIG-IP system.
  • Failed application and LTM health monitors.
  • VPN performance degradation.
  • Inflated or misleading Goodput values in BIG-IP TCP Analytics.

The BIG-IP CPU statistics did not reflect the physical host-core saturation.

Recommended Actions

Apply the following VMXNET3 advanced parameters to all virtual network interfaces assigned to the BIG-IP VE:

  • ctxPerDev=3
  • pnicFeatures=5
  • udpRSS=1

After applying the settings:

  1. Verify that the parameters are configured on every VMXNET3 vNIC used by BIG-IP VE.
  2. Reboot BIG-IP VE so the VMXNET3 changes take effect.
  3. Monitor the ESXi host during representative traffic.
  4. Confirm that network-processing load is distributed across multiple physical CPU cores.
  5. Monitor:
    • ESXi NetWorld CPU utilization.
    • BIG-IP TCP Analytics Goodput.
    • BIG-IP interface throughput.
    • Packet loss and latency.
    • APM VPN performance.
    • LTM monitor status.
  6. Compare Goodput with physical interface throughput. Goodput should not be treated as a direct measurement of physical interface capacity.
  7. If the issue persists, collect diagnostic data while the event is active, including QKviews, packet captures, Goodput and packet-loss screenshots, ESXi per-core CPU data, and Analytics diagnostic data as requested by F5 Support.

Additional Information

  • TCP Analytics Goodput is an application-level metric and may not match interface throughput, CPU utilization, or memory utilization.
  • A Goodput value exceeding the BIG-IP VE licensed throughput does not by itself prove that the physical interface transmitted that amount of traffic.
  • Packet loss may affect traffic passing through the BIG-IP even when pings to BIG-IP self IP addresses do not reproduce the loss.
  • A rate-limit message for a specific virtual server indicates that the configured limit was reached on that virtual server. It does not by itself prove that all BIG-IP traffic is being rate-limited.
  • VMXNET3 configuration should be evaluated together with ESXi host CPU telemetry because BIG-IP CPU statistics may not reflect saturation of a physical host core handling virtual network processing.
