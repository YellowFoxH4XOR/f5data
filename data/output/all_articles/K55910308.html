Known Issue

Multiple changes to file configuration objects may cause the Master Control Program Daemon (MCPD) to restart and produce a core file on VIPRION systems.

This issue occurs when all of the following conditions are met:

  • Two or more VIPRION chassis are configured in a device synchronization group.
  • You perform the following steps, in the indicated order:

    • On one of the chassis, you add, modify, or delete file objects such as Secure Sockets Layer (SSL) certificates.
    • You synchronize changes to other members of the device synchronization group.
    • While the previous changes are synchronizing to all blades in all chassis of the device synchronization group, an overlapping set of file objects is added, modified, or deleted on a chassis in the group; the subsequent changes typically occur on the same chassis from which the first changes were performed.
    • While the previous synchronization operation is still in progress, these subsequent changes are synchronized to other members of the device synchronization group.

When a configuration synchronization (ConfigSync) is performed from one VIPRION chassis to another, secondary blades within the chassis synchronize with the primary blade. At this point, a second modification can be performed and synchronized between VIPRION systems, before changes from the initial ConfigSync are synchronized between all blades in the chassis.

Impact

One or more VIPRION chassis that are receiving the ConfigSync may temporarily fail to function, and traffic may be interrupted on one or more secondary blades.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • On the secondary blades of the VIPRION chassis that is receiving the ConfigSync, the mcpd process restarts and produces a core file.
  • In the /var/log/ltm file, you observe messages similar to the following example:

    err mcpd[1234]: 0107134b:3: (rsync: link_stat "/config/filestore/.snapshots_d/<_additional_path_to/_affected_file_object_>" (in csync) failed: No such file or directory (2) ) errno(0) errstr().
    err mcpd[1234]: 0107134b:3: (rsync error: some files could not be transferred (code 23) at main.c(1298) [receiver=2.6.8] syncer /usr/bin/rsync failed! (5888) () Couldn't rsync files for mcpd. ) errno(0) errstr().
    err mcpd[1234]: 0107134b:3: (rsync process failed.) errno(255) errstr().
    err mcpd[1234]: 01070712:3: Caught configuration exception (0), Failed to sync files.

Workaround

To mitigate this issue, F5 recommends that after performing one set of file object modifications and synchronizing those changes to the high availability (HA) group members, you should wait at least one minute before making and synchronizing additional file object changes. Waiting for the synchronization to complete allows all changes to be synchronized to all blades in the member chassis.
