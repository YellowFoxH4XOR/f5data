Description

If you are using a Last Resort Pool(LRP) on a Wide IP Pool with persistence and the LRP is selected due to the primary pools being down the persistence record that is created will remain on the LRP regardless of the primary pool(s) status(es).  This persistence record will remain on the LRP for as long as there are queries being received from clients that match this record.  This record will only be removed if there are zero queries from clients for the duration of the persistence record TTL.

  • Last Resort Pool configured on Wide IP
  • Persistence is used with Wide IP Pools
  • Last Resort Pool records pinned 

Environment

  • Primary Wide IP Pools go down and query falls through to LRP
  • Persistence record created for LRP
  • Client or LDNS system continues to query and match a persistence record to a LRP

Cause

Bug ID 1066397: GTM persists to last resort pool members even when primary pool members become available.

Recommended Actions

None, see possible workarounds in additional information below.

Additional Information

Option 1:
On the Wide IP load balancing pool load balancing method you can set the Fallback Method to "Fallback IP" and set a static Fallback IP Address to be returned when the Pool is down.

Option 2:
Don't use persistence when using Last Resort Pools

Option 3:
The following iRule has been known to work for this and prevent a persistence record from being created for the LRP.
gtm rule /Common/no-persist-last-resort {
when DNS_REQUEST {
   if { [active_members <WIDEIP_POOL> ] < 1 } {
             persist disable
     }
   }
}

Option 4:
Once Primary pools come back up you can clear the DNS Persistence Records  for the Wide IP per K12139717: How to delete DNS/GTM wideip persistence records
