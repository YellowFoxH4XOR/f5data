For some customers auditing of all activities from privileged accounts is a requirement. This article explains how to effectively setup additional non-standard audit logging, for privileged accounts including admin, root, and role groups beyond what is configured by default.

there are several documents that explain how to audit users in TMSH and Linux existing today:

  • K53108777 - Hardening your F5 system
  • K13426 - Monitoring login attempts on BIG-IP system
  • K56602501 - Configuring syslog to send only audit logs to a remote logging destination

This article will assume the reader has already reviewed and/or implemented the above articles, and are looking for additional logging of the "root" user environment. This requires modifying configuration settings in the Linux kernel for the audit.d process.

IMPORTANT:  F5 does not make any recommendations on what audit values to add or modify to enact more stringent audit logging.   Doing research on how to use audit.d and auditctl is up to the administrator of the device.

Make sure you have completed the steps to send the kernel audit logs to remote logging, then add the specific rules you need to record  the desired 'root' activities: 

Here are some example options: 

# Watch bash and tmsh shell history
auditctl -w /root/.bash_history -p wa -k history-watch-bash
auditctl -w /root/.tmsh-history-root -p wa -k history-watch-tmsh

# Audit execution of su and sudo
auditctl -w /bin/su -p x -k priv-esc
auditctl -w /usr/bin/sudo -p x -k priv-esc

# Watch all root execution events for base 32/64 root users (****)

auditctl -a always,exit -F arch=b64 -S execve -F euid=0
auditctl -a always,exit -F arch=b32 -S execve -F euid=0 

**** These 2 commands will watch ALL root level executions to include pre-configured cron, Logrotate, and other activites that are not part of users from console or SSH.   There is no way to differentiate "user logged in as root" and "system controls using root".  This will result in additional logs and logging that you may not expect in the /var/log/auditd/audit.log.   Please watch the log file carefully for size/retention.

You can list the rules added by reviewing "auditctl -l" (*list auditctl rules) 

These rules are not persistent and will not survive a reboot. 

To make the rules persistent,   please append the rules to the end of  /etc/audit/rules.d/audit.rules.   Do not remove the default rules already in that file. 

Example using the above command options, along with the 'default' values in /etc/audit/rules.d/audit.rules : 

## This file is automatically generated from /etc/audit/rules.d
-D
-b 8192
-f 1
-w /etc/selinux/ -p wa -k MAC-policy
-w /root/.bash_history -p wa -k history-watch-bash
-w /root/.tmsh-history-root -p wa -k history-watch-tmsh
-w /bin/su -p x -k priv-esc
-w /usr/bin/sudo -p x -k priv-esc
-a always,exit -F arch=b64 -S execve -F euid=0
-a always,exit -F arch=b32 -S execve -F euid=0

Please remember to test these rules carefully and ensure any security of the audit log contents is taken into consideration.

Note:   Changes to /etc/audit/rules.d/audit.rules will not persist across an upgrade.    Any time you upgrade these audit.rules will need to be re-submitted and saved.

There are several online references on how to audit root users in a Linux environment.  Search terms like "Linux audit root user activity" will provide additional references on how to manage and modify the auditctl and auditd configuration files.   These settings are not unique to BIG-IP, but are common to many Linux environments.   You will need to look for and include auditctl details required for your environment.

Limitations to this activity: 

 A 'root' user has the ability to modify, delete or otherwise stop logging if they're bound and determined to modify the system without observation, therefore alternate methods to enforce ROOT auditing is strongly recommended.

Alternate methods like restricting 'root' access to a known audited and separately controlled computer; where the user accessing a system as "root" does not have the rights or permissions to modify logging of the computer. This ensures you are auditing the users accessing devices with privileged accounts in a way they cannot hide, modify or delete their user activity.
