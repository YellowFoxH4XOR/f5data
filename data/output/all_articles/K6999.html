A number of security advisories including US-CERT VU#261869 4 have been published that discuss potential vulnerabilities related to web browser domain-based security in clientless SSL VPN products. Two of these articles can be found at the following locations:

  • November 2009: http://www.kb.cert.org/vuls/id/261869
  • January 2007: http://www.mnin.org/advisories/2007_firepass.pdf

This potential vulnerability is discussed in the Web browser domain-based security section of this advisory.

Additionally, the January 2007 security advisory 1 discusses a potential FirePass cross-site scripting vulnerability related to the double eval() Javascript and FP_DO_NOT_TOUCH tags. This potential vulnerability is discussed in the Cross-site scripting (XSS) with the double eval() Javascript and FP_DO_NOT_TOUCH tags section of this advisory.

Web browser domain-based security

If FirePass users are accessing a web server with malicious code, two possible explanations include overly permissive access control lists, and a compromised web server within the trusted domain (as defined by access control lists).

Overly permissive access control lists

Overly permissive access control lists allow FirePass users to access untrusted resources, such as arbitrary Internet web sites. The core security model for FirePass (and any other SSL VPN product) is an access control model, in which your access control lists (ACLs) provide access only to resources that are needed and known to be trusted, denying access to all other resources that your organization does not control.

F5 strongly recommends the use of a default deny policy when deploying (ACLs) for Portal Access Web Applications. A default allow policy (with specific deny list patterns) could result in unintended access due to misconfiguration or use of alternate encoding for URLs by authenticated attackers. In general, good security practices dictate the use of default deny policies for ACLs, just as when firewall rules are configured.

To enable a default deny policy for version 6.0 of FirePass and later releases, you would configure a Default action of Deny under Portal Access : Web Applications : Master Group Settings : Access Control Lists. To enable a default deny policy on earlier releases of FirePass, you would enter URLs in the Allow box under Portal Access: Web Applications: Master Group Settings: Accessibility Scope, leaving the Deny box empty.If a trusted web server to which users have been granted access is compromised, then the access control model does not offer protection. A content-inspection model would be required, where the content of web server responses would be inspected at the application layer. However, this is an extremely difficult, resource-intensive model to implement when the content is as complex and varied as in a web application environment. No SSL VPN product implements this model to any significant degree (FirePass does employ some response content-inspection, such as blocking of attachment downloads, or blocking whole web pages based on the appearance of URLs not explicitly trusted).

Compromised trusted web server

Without such a model, the issue of malicious code on a trusted web server is largely irrelevant. Any kind of attack, not just a cross-site scripting attack, is made possible. Any code, not just the type mentioned by the advisory, can perform a wide array of malicious actions.

Cross-site scripting (XSS) with the double eval() Javascript and FP_DO_NOT_TOUCH tags

One section in the January 2007 security advisory 1 , titled XSS with double eval() Javascript and FP_DO_NOT_TOUCH tags, states that two constructs—double eval() JavaScript constructs, and FP_DO_NOT_TOUCH tags (a markup tag interpreted by the FirePass controller) 2—represent vulnerabilities in FirePass because these two constructs, if used in web page source code, allow additional JavaScript or other web page source code to bypass the FirePass controller's mechanism for preventing cross-site scripting (XSS) attacks.

While these methods can be employed as part of a cross-site scripting attack, F5 believes that these issues do not represent vulnerabilities in the FirePass controller.

The assertion made in this section of the document is that certain types of content within a web page sent from a web server through the FirePass reverse proxy are not handled—or in this case, rewritten—securely. FirePass reverse proxy rewriting on JavaScript functions, such as eval(), is performed by wrapping them inside FirePass functions that are defined in a JavaScript header file sent with the rewritten web page to the client's browser.

Other types of rewriting are performed on other elements of web page source code. For example, links within web page content are rewritten so that the URLs point to the FirePass, rather than the web server that will provide the content 3.

The following points must be made in order to understand the issues involved in the advisory's claim:

  1. The anti-cross site scripting mechanism in the FirePass controller does not operate on web page source code sent from a web server through the FirePass, to the client's browser. Inspection for malicious application content, such as code to perform a cross-site scripting attack, is performed on the HTTP requests sent from a client to the web server, not on the response sent from the web server to the client. The advisory does not state explicitly what anti-XSS mechanism is being bypassed; however, in the FirePass Administrative Console, the XSS scripting tab on the Portal Access: Content Inspection page states that the anti-XSS mechanism "will scan user input data—for example, the HTTP requests. Thus, this mechanism is not being directly bypassed by content in an HTTP response.

  2. While the advisory may be claiming that the rewriting performed by the reverse proxy constitutes an anti-XSS mechanism, this view does not accurately represent the purpose of rewriting. As indicated earlier, the purpose of rewriting is to modify web page source code so that references to origin web servers are replaced with references to the FirePass controller. Hostnames in URL links and cookie domains are changed; digitally signed mobile code such as Java applets are resigned, and other similar changes are made in the web page content. Rewriting causes web requests made by this code to go through the FirePass for reverse-proxying, rather than being sent to the origin web server. Rewriting in itself is not a mechanism against cross-site scripting or any other form of attack. Therefore, bypassing rewriting does not constitute bypassing an anti-XSS mechanism.

  3. The advisory is implicitly raising a more general (not XSS-specific) question of malicious code in web server responses. The advisory is correct in stating that its two examples of web page source code, double eval() constructs and FP_DO_NOT_TOUCH tags, will allow other web source code contained within these constructs to avoid rewriting. When executed in the browser, code that has not been rewritten will not traverse the FirePass and will thereby avoid any of the security mechanisms that FirePass provides, including but not limited to the aforementioned anti-XSS mechanism. While true, this raises the question of whether it is the responsibility of FirePass to defend against a web server that serves malicious code.

    The scenario implied in the advisory's claim is one where FirePass users have been granted access to a web server which contains malicious code containing statements of the type the advisory describes. Double eval() constructs would almost certainly not be used in legitimate production web pages in the way the advisory intends; FP_DO_NOT_TOUCH tags, if used properly in production code, do not typically allow access to arbitrary and wide-ranging sets of web sites. Unless a web application developer has misused these statements, the expectation is that this type of code is being inserted into web pages by an attacker.

Beginning with FirePass version 6.0.1, you can configure the processing of the FP_DO_NOT_TOUCH tags in the FirePass Administrative Console. Under the Global Settings tab of the Portal Access : Web Applications : Content Processing page, you may clear the Process content of the FP_DO_NOT_TOUCH element check box if you want the reverse proxy to rewrite all content, regardless of any FP_DO_NOT_TOUCH tags. The default setting is to process the tags.

Conclusions

After careful assessment of the issues raised in this advisory, F5 believes that the current behavior of the FirePass controller is correct, and no vulnerability to these issues exists. Rather, the types of attacks described in this advisory can be performed on any SSL VPN product, given the security model employed and the precondition of an attacker having already compromised a trusted resource.

F5 encourages anyone with questions about the advisory's claim or this response to contact F5 Technical Support.
