K000148560: How to preserve the client IP address when going through a TCP Load Balancer (Proxy Protocol)

Applies to

Description

I have a TCP Load Balancer configured and I want to preserve the client IP address (source IP) when reaching the back-end server. 

Environment

  • TCP Load Balancer | F5 Distributed Cloud Technical Knowledge

Cause

Protocol extensions such as “X-Forwarded-For” header for HTTP require knowledge of the underlying protocol (such as HTTP) which is why it only works for HTTP Load Balancers. For layer 4 applications, F5 Distributed Cloud Load Balancers now supports the PROXY protocol (PROXY protocol spec), which conveys the original connection parameters, such as the client IP address, to the back-end servers.

Answer / Recommended Actions

As of May 28, 2024 support for Proxy Protocol was added on the TCP Load Balancers.

The TCP Proxy Protocol conveys the original connection parameters, such as the client IP address, to the back-end servers for L4 Load Balancers (TCP).

Configuration in XC TCP Load Balancer

  • This  Proxy Protocol Configuration is available on the setting for the origin pool under Other Settings > Proxy Protocol Configuration
  • You will find two versions of the PROXY protocol , V1 (human-readable format) and V2 (binary encoding).

Configuration in the Back-end Server

The Proxy Protocol needs to also be configured on the back-end server. Few things worth pointing out:

  • The back-end server needs to be configured to only receive the defined Proxy Protocol instead of having to guess whether the Proxy Protocol is present or not.
  • It should not start processing the connection until a complete valid Proxy Protocol header is received.
  • Client information is forwarded to the back-end server only at the beginning of the connection before any other data is sent (even before TLS handshake, as this one lives on TCP protocol - "The Proxy Protocol adds a header to a TCP connection to preserve the client's IP address.").
  • The back-end server should also process the header at once. The back-end server must not start to parse an address before the whole address block is received. The back-end server must also reject incoming connections containing partial protocol headers.
  • There can be a performance impact as there will be no upstream connection re-use for downstream clients

 

Additional Information

The information carried by the protocol is the following:

  • address family (AF_INET for IPv4, AF_INET6 for IPv6, AF_UNIX)
  • socket protocol (SOCK_STREAM for TCP, SOCK_DGRAM for UDP)
  • layer 3 source and destination addresses
  • layer 4 source and destination ports if any

Compatibility between versions

  • Version 1 senders MAY only produce the human-readable header format.
  • Version 2 senders MAY only produce the binary header format.
  • Version 1 receivers MUST at least implement the human-readable header format.
  • Version 2 receivers MUST at least implement the binary header format, and it is recommended that they also implement the human-readable header format for better interoperability and ease
    of upgrade when facing version 1 senders.
