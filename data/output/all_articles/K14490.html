Topic

The BIG-IP system has the following two routing tables:

  • The kernel table for routing BIG-IP system management traffic
  • The Traffic Management Microkernel (TMM) table for routing load-balanced traffic

You can use the Configuration utility or command line to statically enter new routes into the BIG-IP system. Alternatively, when you have a license for BIG-IP Advanced Routing Module (ARM), you can add new routes dynamically. The F5 Better and Best licenses include this feature. For more information about the Good, Better, and Best licenses, refer to K14826: Good, Better, Best license options and provisioning.

Note: You can determine whether you have a license for ARM by going to System > License in the Configuration utility and looking for Routing Bundle in the Active Modules section. You can also check for Routing Bundle using the TMOS Shell (tmsh) and the show sys license command.

One of the advanced routing protocols supported by the BIG-IP system is the Open Shortest Path First (OSPF/OSPFv3) protocol, which is a link-state dynamic routing protocol for external networks.

The following elements must be in place before you can configure OSPF/OSPFv3 on the BIG-IP system:

  • You have a license for ARM on your BIG-IP system.
  • The tmrouted process starts and manages the BIG-IP ARM daemons.

    Important: You must manage the tmrouted process using the bigstart command or tmsh.

    The BIG-IP system must be running the tmrouted process for dynamic routing to function. To verify whether the tmrouted process is running, enter the following command at the command line:

    bigstart status tmrouted

    To start the tmrouted process, enter the following command:

    bigstart start tmrouted

  • You must enable the OSPF/OSPFv3 protocol. To verify whether OSPF or OSPFv3 is enabled, enter the following command:

    zebos check

    If OSPF is enabled, the system displays output similar to the following example:

    nsm is running [22319]
    imi is running [22317]
    ospfd is running [22320]

    If OSPFv3 is enabled, the system displays output similar to the following example:

    nsm is running [2296]
    imi is running [2295]
    ospf6d is running [2298]

    If neither OSPF orOSPFv3 is enabled, refer to the following articles for information about starting the BIG-IP ARM system:

    • K13802: Enabling dynamic routing protocols for a route domain
    • K8261: Enabling a dynamic routing protocol (9.x - 11.1.0)
  • You must configure port lockdown to allow protocol 89 on all self IP addresses that the routers communicate with. For information about port lockdown, refer to the following articles:
    • K13250: Overview of port lockdown behavior (10.x - 11.x)
    • K7317: Overview of port lockdown behavior (9.x)
Note: When you do not configure port lockdown to allow protocol 89 on self IP addresses that the routers communicate with, the BIG-IP system still processes multicast packets, including OSPF multicast packets, such as Hello and LS Update. This may cause OSPF adjacency to remain in the ExStart state and/or experience other unexpected behavior.

Advanced routing daemons

The tmrouted process is the routing table management daemon that updates the TMM routing table, based on the kernel routing table. The tmrouted process depends on the mcpd and tmm processes. If either of these processes restarts, tmrouted also restarts.

The tmrouted process starts and supervises the BIG-IP ARM daemons. BIG-IP ARM daemons are divided into the following two categories:

  • Core daemons:
    • nsm

      The BIG-IP Network Services Module (nsm) daemon.

    • imi

      The Integrated Management Interface (imi ) management daemon allows you to configure and monitor BIG-IP ARM daemons through a centralized connection.

  • Protocol daemons:
    • bgpd
    • isisd
    • ospfd
    • ospf6d
    • ripd
    • ripngd

The presence of BIG-IP ARM license keys controls BIG-IP ARM daemon startup. The system starts protocol daemons if you licensed and enabled them. The system starts core daemons if you licensed and enabled at least one protocol daemon.

The tmrouted process handles SIGCHLD signals and restarts BIG-IP ARM daemons as necessary. The tmrouted process performs the following actions when a BIG-IP ARM daemon restarts:

  • Core daemon exits
    • Removes all dynamic routes
    • Stops all remaining BIG-IP ARM daemons
    • Exits and restarts
  • Protocol daemon exits
    • Restarts the protocol daemon

Advanced routing daemon logging

The BIG-IP ARM system logs to the /var/log/zebos.log file. The system logs additional messages to the /var/log/daemon.log and /var/log/ltm files.

The system logs:

  • ospfd and ospf6d processes information for OSPF/OSPFv3 daemon-specific issues.
  • nsm and imi daemon information for core BIG-IP ARM daemon-related issues.

If a core BIG-IP ARM daemon exits, the system logs an error message to the /var/log/daemon.log file, which appears similar to the following example:

LOGIN: Re-starting tmrouted

In addition, the system logs error messages to the /var/log/ltm file, which appear similar to the following example:

mcpd[5157]: 01070410:5: Removed subscription with subscriber id ospfd

Debug logging

When you troubleshoot an issue with a BIG-IP ARM daemon, you may need to create a debug log file and enable debug logging. To create a debug log file and enable debug logging, perform the following procedure:

  1. Log in to the BIG-IP command line.
  2. To access the IMI command line shell, enter the following command.

    imish

  3. To enter enable mode, enter the following command:

    enable

  4. At the prompt, to enter configuration mode, enter the following command:

    config terminal

  5. At the prompt, to create the debug log file, enter the following command:

    log file /var/log/zebos.log

  6. Exit configuration mode by entering the following command:

    end

  7. To write the configuration, enter the following command:

    write

  8. After you define the debug log file, enable debug logging by entering one of the following commands:
    • OSPF

      debug ospf all

    • OSPFv3

      debug ipv6 ospf

  9. To verify that OSPF/OSPFv3 debug logging is enabled, enter one of the following commands:
    • OSPF

      show debug ospf

    • OSPFv3

      show debug ipv6 ospf

      For example, the following output indicates that OSPF debug logging is enabled:

      OSPF debugging status:
      OSPF all IFSM debugging is on
      OSPF all NFSM debugging is on
      OSPF packet Hello detail debugging is on
      OSPF packet Database Description detail debugging is on
      OSPF packet Link State Request detail debugging is on
      OSPF packet Link State Update detail debugging is on
      OSPF packet Link State Acknowledgment detail debugging is on
      OSPF all LSA debugging is on
      OSPF all NSM debugging is on
      OSPF all events debugging is on
      OSPF all route calculation debugging is on

      For example, the following output indicates that OSPFv3 debug logging is enabled:

      OSPFv3 debugging status:
      OSPFv3 all packet detail debugging is on
      OSPFv3 all IFSM debugging is on
      OSPFv3 all NFSM debugging is on
      OSPFv3 all LSA debugging is on
      OSPFv3 all NSM debugging is on
      OSPFv3 all route calculation debugging is on
      OSPFv3 all event debugging is on

  10. To enable debug logging for the NSM, enter the following command:

    debug nsm all

  11. To verify that NSM debug logging is enabled, enter the following command:

    show debug nsm

    For example, the following output indicates that NSM debug logging is enabled:

    NSM debugging status:
    NSM event debugging is on
    NSM packet detail debugging is on
    NSM kernel debugging is on
    NSM HA all debugging is on

  12. You can disable OSPF/OSPFv3/NSM debugging by entering the following commands:
    • OSPF

      undebug ospf

    • OSPFv3

      undebug ipv6 ospf

    • NSM

      undebug nsm

Verifying routes

You should verify that routes are advertised from the vtysh shell. To do so, perform the following procedure:

  1. Log in to the BIG-IP command line.
  2. To access the IMI command line shell, enter the following command:

    imish

  3. To show the IP route information, enter the following command:

    show ip route

    For example, the following command output displays the IP route information:

    Codes: K - kernel, C - connected, S - static, R - RIP, B - BGP
    O - OSPF, IA - OSPF inter area
    N1 - OSPF NSSA external type 1, N2 - OSPF NSSA external type 2
    E1 - OSPF external type 1, E2 - OSPF external type 2
    i - IS-IS, L1 - IS-IS level-1, L2 - IS-IS level-2, ia - IS-IS inter area
    * - candidate default

    Gateway of last resort is 10.1.99.254 to network 0.0.0.0

    K* 0.0.0.0/0 via 10.1.99.254, external
    O IA 10.0.0.0/8 [20/0] via 10.1.99.254, external, 00:13:08
    C 10.1.0.0/16 is directly connected, external
    K 10.1.51.80/32 is directly connected, tmm0
    K 10.1.51.81/32 is directly connected, tmm0
    C 10.10.0.0/16 is directly connected, internal
    C 127.0.0.1/32 is directly connected, lo
    C 127.1.1.0/24 is directly connected, tmm0
    O IA 172.24.0.0/16 [20/0] via 10.1.99.254, external, 00:13:08

    The following routes indicate the advertised virtual server addresses. The system learns the tmm routes from TMM, and the /32 netmask indicates that the BIG-IP system is advertising a single IP address:

    Note: The advertised virtual server addresses appear as kernel routes (K) because of the way TMM injects the routes into tmrouted. Therefore, you must configure redistribute kernel in the OSPF router definition.

    K 10.1.51.80/32 is directly connected, tmm0
    K 10.1.51.81/32 is directly connected, tmm0

    The system learns the following routes from other OSPF routers:

    O IA 172.24.0.0/16 [20/0] via 10.1.99.254, external, 00:13:08

    When you look at the routing table from the Advanced Shell (bash), the routes that the system learns from other routers may not be obvious. Dynamically learned routes appear similar to the following example:

    #route -n
    Kernel IP routing table
    Destination Gateway Genmask Flags Metric Ref Use Iface
    172.24.0.0 10.1.99.254 255.255.0.0 UG 0 0 0 external

Capturing routing protocol traffic

In certain cases, when peering is not establishing, or updates are not correct or not appearing to arrive at the peer, you can use the tcpdump command to help track routing updates. To capture OSPF traffic, use the following tcpdump commands concurrently:

IPv4

tcpdump -ni 0.0:nnn -s0 -w /var/tmp/0.0_ospf.pcap ip proto ospf

tcpdump -ni <vlan>:hnnn -s0 -w /var/tmp/vlan_hostside_ospf.pcap ip proto ospf

IPv6

tcpdump -ni 0.0:nnn -s0 -w /var/tmp/0.0_ospfv3.pcap ip6 proto ospf

tcpdump -ni <vlan>:hnnn -s0 -w /var/tmp/vlan_hostside_ospfv3.pcap ip6 proto ospf

Note: <vlan> is the name of the VLAN on which the unit is using OSPF.
