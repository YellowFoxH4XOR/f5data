Description

This article presents details on some aspects of implementation of DPDK drivers with BIG-IP Virtual Edition (VE).

Environment

  • BIG-IP VE
  • SR-IOV
  • KVM/OpenStack
  • DPDK

Cause

DPDK driver may not be selected by default even if SR-IOV capable NIC supports DPDK

Recommended Actions

Definitions and nomenclature of BIG-IP VE network drivers

Traditional “compatibility” drivers rely on what host’s kernel is providing to user space application like BIG-IP – they come in two flavors unic and sock. Both drivers  are generally interrupt driven and would not scale/perform to the highest levels .
Currently, F5 prefers the use of NICs for KVM in a form of synthetic devices . The flavors are virtio and xnet. We need to keep in mind that xnet is not a NIC but an abstraction that allows to tap into DPDK and SR-IOV, and serves as an insulator between TMM and other memory abstractions.

DPDK was conceived to enable application to bypass kernel resources for fast packet processing. This is achieved with:

  • User-space packet processing (kernel bypass).
    • Avoid context switching overhead.
  • Poll Mode Driver (PMD).
    • Avoid interrupt processing overhead.
    • Keeps a core busy.
  • Memory usage optimizations.
    • Light-weight mbufs.
    • Memory pools that use hugepages, cache alignment, etc.
    • Lockless ring buffers

Since F5 is already bypassing kernel and providing memory management within TMM, all memory allocation magic for DPDK is done by TMM with facilitation of xnet driver.
The data-pass is: TMM -> NDAL -> XNET -> (native driver OR DPDK).

F5 implements the DPDK driver on the guest side. DPDK driver is a part of xnet and xnet is baked into TMM. Therefore, there is no separate process for DPDK activities outside TMM process.

Since we are running Poll Mode Driver (PMD) to constantly poll the NIC for new packets this means that a CPU core must be dedicated and assigned to running PMD (see discussion in "Additional information" regarding "pinning").

Let's take an example where BIG-IP VE is deployed to use Mellanox NIC.

View discovered network devices on the Linux side:

lspci
...
00:03.0 Ethernet controller: Red Hat, Inc Virtio network device
00:05.0 Ethernet controller: Mellanox Technologies MT28800 Family [ConnectX-5 Virtual Function]
00:08.0 Ethernet controller: Mellanox Technologies MT28800 Family [ConnectX-5 Virtual Function]
00:09.0 Ethernet controller: Mellanox Technologies MT28800 Family [ConnectX-5 Virtual Function]
00:0a.0 Ethernet controller: Mellanox Technologies MT28800 Family [ConnectX-5 Virtual Function]


Depending what the default driver is selected we may need to switch to xnet.
From higher level of TMM  “/config/tmm_init.tcl” should contain PCI ID (pci_bdf) and driver that we want to bind. This file does not exist by default and will likely be need to be created.
Use the ‘pci_bdf’ values and create a line-entry for each.

/config/tmm_init.tcl

device driver pci 00:05.0 xnet
device driver pci 00:08.0 xnet
device driver pci 00:09.0 xnet
device driver pci 00:0a.0 xnet
ndal mtu 1500 1137:0043

Use  tmctl -d blade tmm/device_probed to view discovered network drivers from TMM viewpoint.
You may observe output similar to the following:

[root@BIG-IP_VE: Active: Standalone] config # tmctl -d blade tmm/device_probed

pci_bdf         pseudo_name     type      available_drivers   driver_in_use
--------------- --------------- --------- ------------------  ---------------
0000:01:00.0                    F5DEV_PCI xnet, sock,
0000:05:00.0    1.3             F5DEV_PCI mlxvf5, xnet,       xnet
0000:08:00.0    1.4             F5DEV_PCI mlxvf5, xnet,       xnet
0000:09:00.0    1.1             F5DEV_PCI mlxvf5, xnet, sock, xnet
0000:0a:00.0    1.2             F5DEV_PCI mlxvf5, xnet, sock, xnet


Now since TMM is instructed to use xnet abstraction we can fine tune xnet behavior between DPDK driver and native driver (Native driver is default)

You may observe output similar to the following:

[root@BIG-IP_VE: Active: Standalone] config # tmctl -d blade tmm/xnet/device_probed
id              available_drivers driver_selected   driver_in_use
--------------- ------------------- --------------- --------------
0000:08:00.0    mlxvf5, dpdk,       mlxvf5          Yes
0000:0a:00.0    mlxvf5, sock, dpdk, mlxvf5          Yes
0000:09:00.0    mlxvf5, sock, dpdk, mlxvf5          Yes
0000:05:00.0    mlxvf5, dpdk,       mlxvf5          Yes

File “/config/xnet_init.tcl” controls xnet behavior, this file does not exist by default, and similarly should use the values from ‘device_probed’

[root@localhost:Active:Standalone] config # cat /config/xnet_init.tcl
device driver pci 00:08.0 dpdk
device driver pci 00:0a.0 dpdk


After TMM restart we are ready to use DPDK:

[root@BIG-IP_VE: Active: Standalone] config # tmctl -d blade tmm/xnet/device_probed
id              available_drivers   driver_selected driver_in_use
--------------- ------------------- --------------- --------------
0000:08:00.0    mlxvf5, dpdk,       dpdk            Yes
0000:0a:00.0    mlxvf5, sock, dpdk, dpdk            Yes
0000:09:00.0    mlxvf5, sock, dpdk, mlxvf5          Yes
0000:05:00.0    mlxvf5, dpdk,       mlxvf5          Yes


Note: When we select DPDK driver under xnet and the NIC that we are driving is Mellanox, we are just going to use DPDK API to drive SR-IOV- so for now if pure performance is the key and there is control of host environment we need to use native driver. Refer to (https://clouddocs.f5.com/cloud/public/v1/kvm/kvm_mellanox.html) for more detail.

On the Host, use 'lscpu' to get a count of how many CPUs and hyper-threads there are.
Node, Socket, and Core form a tuple representing a physical core, and if more than two CPUs share the same tuple then those CPUs are hyper-threads on the same physical core.
Ex: CPU 1 has tuple (0,0,1); because CPU 25 shares this same tuple, CPU 1 and CPU 25 are hyper-threads on the same physical core.
