Topic

An HTTP class provides a method for matching HTTP requests to specific patterns and defining the action that should be applied to that traffic.

An HTTP class may be configured to match HTTP requests based on the following attributes:

  • Hosts
  • URI Paths
  • Headers
  • Cookies

The HTTP class must then define the actions to be applied to matching requests. An HTTP class may be configured to define the following actions:

  • Send matching requests to the pool specified by the HTTP class.
  • Send matching requests to the virtual server default pool.

    Note: If the virtual server does not have a default pool configured, matching requests are dropped.

  • Redirect matching requests to a specified URL.
  • Rewrite the request URI for matching requests to a specified URI without sending an HTTP redirect to the client.

Ensuring that all traffic is accounted for

The ability to configure various filter and pool configuration combinations allows for several options to control traffic flow and provides flexibility in designing solutions. Evaluate the HTTP class configurations carefully to ensure that all traffic is accounted for.

Important: The design flexibility and multiple traffic flow options may complicate your configuration; you must ensure that your configuration is valid. For example, if you define an HTTP class with a host filter of www.f5.com, all requests that arrive to www.f5.com will be sent to the pool configured in the HTTP class. However, any requests that arrive at the virtual server using other hosts, such as www.f5networks.com or www.bigip.com, would not be matched by the HTTP class. As a result, these requests would be dropped because the virtual server does not have a default pool configured.

Possible methods to ensure that all requests are matched:

  • Create an HTTP class, with no filters, that redirects requests to the site homepage; apply the HTTP class as the virtual server’s last HTTP class.
  • Create an HTTP class with no filter that rewrites the request to a specific page on the server; apply the HTTP class as the virtual server's last HTTP class.

Ordering HTTP classes for the virtual server

You can configure a virtual server to use multiple HTTP classes. The order of the HTTP classes determines how the request is evaluated. When a request matches an HTTP class, the request is processed and is not evaluated against any subsequent HTTP classes. If a request does not match any of the HTTP classes, the virtual server's default pool will be used; if the virtual server does not have a default pool configured, the request will be dropped.

Logging unmatched requests

When the configuration results in a dropped request, the drop will not be logged, which is the desired behavior in most situations. However, you might want to ensure that all traffic is accounted for.

You can have the system log an entry for any requests that fail to match the HTTP class by using an iRule that appears similar to the following example:

when HTTP_CLASS_FAILED {
log local0. "Request didn't match class"
}

Note: For information about other logging options using iRules, refer to log command on F5 Cloud Docs.

When using the BIG-IP ASM system, you can have the system log an entry for any unmatched requests for a virtual server by doing the following: create an additional HTTP class with no filters; configure a BIG-IP ASM security policy to block everything and to log illegal requests; and configure the HTTP class as the final class in the virtual server's list of assigned classes. This configuration allows the BIG-IP ASM system to provide logs for any unmatched requests that make it through to the HTTP class.

Configuration scenarios

The following three scenarios explore a variety of options that you may use to define traffic flow using HTTP classes:

Scenario 1 : Multiple virtual servers configured without a default pool, which are using the same HTTP class that has been configured to send traffic to a pool

You can use this configuration in the following situations:

  • You want to send specific file types to a common pool. Multiple virtual servers use a common HTTP class that matches requests for multimedia files and sends the requests to a dedicated pool of multimedia servers.
  • You want to maintain a common BIG-IP ASM policy for HTTP and HTTPS traffic. A configuration that allows you to maintain one BIG-IP ASM policy for both HTTP and HTTPS traffic is, when you have two virtual servers--one virtual server for HTTP and one virtual server for HTTPS that is configured to terminate SSL, and both virtual servers use a common HTTP class that sends requests to a pool of servers that are listening to only HTTP traffic.

Scenario 2: A single virtual server with no default pool, configured to use multiple HTTP classes

You can use this configuration in the following situations:

  • If you want to deny or allow specific requests, you would configure your system as follows:
    • Configure a virtual server to use two HTTP classes; the first HTTP class does not have a pool configured.
    • Configure a pool for the second HTTP class.
    • Configure the first HTTP class to match requests for which access is denied.
    • Configure the second HTTP class to match all other requests or all requests for which access is allowed.

    As a result of the previous configuration, because the HTTP class does not have a pool configured, the requests matching the first HTTP class will be handled according to the virtual server configuration. Because the virtual server does not have a default pool configured, the requests matching the first HTTP class will be dropped. The requests that do not match the first HTTP class will be passed to the second HTTP class. The requests that match the second HTTP class will be sent to the pool configured in the HTTP class.

  • If you want to map different sites based on the URL, you would configure your system as follows:
    • Configure a virtual server to use multiple HTTP classes.
    • Configure each HTTP class to send requests to different pools of servers.
    • Configure each HTTP class to match requests for different sites, for example, where the differentiation between sites is done by the URL, such as /site1/, /site2/, etc. Requests with a URL beginning with /site1 will match the first HTTP class and will be sent to the pool configured for that HTTP class. If the request did not match the first HTTP class, the request is passed to the next HTTP class in the list, and will continue down the list until it matches a class. If the different sites are hosted on different servers, you can redirect the traffic to different pools at the class level.

Scenario 3: Multiple virtual servers are configured with a default pool and are using the same HTTP class, which has not been configured, to send traffic to a pool

You can use this configuration in the following situation:

  • Multiple applications need to share a common HTTP class and maintain the ability to send the request to different server pools. For example, when using the BIG-IP ASM system, you would configure your system as follows:
    • Configure two virtual servers, an HTTP virtual server and an HTTPS virtual server, to use different pools.
    • Do not configure the HTTP class to send traffic to a pool.
    • Configure the system so that requests for the HTTP virtual server that match the HTTP class are sent to the default pool for the HTTP virtual server.
    • Configure the system so that requests for the HTTPS virtual server that match the HTTP class are sent to the default pool for the HTTPS virtual server.
