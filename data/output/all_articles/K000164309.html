Description

NGINX Plus load balancers must block the HTTP methods TRACE, TRACK, and CONNECT for security hardening. NGINX core rejects TRACE with HTTP 405 and has rejected CONNECT since nginx 1.21.1. NGINX core has no built-in rejection for TRACK, so TRACK requests can be passed to upstream servers through proxy_pass. Where the block configuration is missing, TRACK returns 404 instead of 405. From NGINX Plus R36, CONNECT forward proxying can be enabled with tunnel_pass, so CONNECT must remain in the block map.

Environment

  • NGINX Plus R32 (nginx 1.25.5) and NGINX Plus R37 (nginx 1.29.8)
  • Multiple NGINX Plus instances managed through centralized configuration management
  • Shared configuration files in /etc/nginx/global/, including fileandnetwork.conf, which is included at server level in HTTP and HTTPS server blocks
  • Port 80 server blocks that contain return 301 https://$host$request_uri; before the global includes
  • stream {} blocks that proxy plain TCP on several ports, including 80 and 8080

Cause

  • NGINX core does not handle TRACK and requires explicit configuration to reject it.
  • TRACK returned 404 instead of 405 on instances where the map and the block-methods include were absent from the running configuration.

Answer/Recommended Actions

  1. In the http {} context, create /etc/nginx/global/block-methods-map.conf with the following content:

    map $request_method $blocked_method {
    default 0;
    TRACE 1;
    TRACK 1;
    CONNECT 1;
    }

    Include the file in the http {} block of /etc/nginx/nginx.conf, before the conf.d include lines. Alternatively, place the map directly inside http {}.
  2. Create /etc/nginx/global/block-methods.conf with the following content:

    if ($blocked_method) {
    return 405;
    }

  3. Include block-methods.conf in every HTTP (port 80) and HTTPS (port 443) server block, directly after the listen and server_name lines and before any return or rewrite redirect:

    server {
    listen :80;
    server_name app.example.com;
    include global/block-methods.conf;
    return 301 https://$host$request_uri;
    }

    If your server blocks already include global/fileandnetwork.conf, you can add include global/block-methods.conf; as the last line of that file. This works only if the fileandnetwork.conf include line appears before any return or rewrite redirect in the server block. If a block has a redirect above that include line (for example, return 301 https://$host$request_uri; on port 80), move include global/fileandnetwork.conf; above the redirect, or add include global/block-methods.conf; directly above the redirect. Include fileandnetwork.conf only inside server blocks, never in http {}. For server blocks that do not include fileandnetwork.conf, add include global/block-methods.conf; directly. Do not add fileandnetwork.conf to those blocks, because it may duplicate directives defined inline.
  4. Deploy the map and the updated shared file together to every NGINX Plus instance. The $blocked_method variable is undefined without the map, so deploy both before reloading.
  5. Validate and reload on each instance:

    nginx -t && nginx -s reload

  6. Verify the running configuration:
    • Compare the count of include global/fileandnetwork.conf lines with the count of server_name lines in nginx -T output. A small difference is expected for management servers.
    • Confirm the map is present with:

      nginx -T 2>/dev/null | grep -n -A6 "map \$request_method"

  7. Re-test TRACK, TRACE, and CONNECT with curl over both HTTP/1.1 and HTTP/2 on each virtual server. Use the real hostname so the correct server block is selected:

    curl -i --http1.1 -X TRACK https://<hostname>/

    curl -i --http2 -X TRACK https://<hostname>/

    curl -i --http1.1 -X TRACE https://<hostname>/

    curl -i --http1.1 -X CONNECT --request-target <hostname>:443 https://<hostname>/

    Expected results:
    • TRACK and TRACE return 405.
    • CONNECT is rejected with an error status (405 or 400), and no tunnel is established.

Notes:

  • Keep CONNECT in the map on R36 and later. NGINX Plus R36 introduced HTTP CONNECT forward-proxy support (tunnel_pass), so relying only on the built-in rejection is not sufficient on those releases.
  • The same configuration is supported on NGINX Plus R32 and R37. No changes to the snippets are required.
  • Do not include the HTTP snippet in stream {} configuration. HTTP applications published through stream {} must enforce method restrictions on the backend or be moved to an HTTP server block.
  • Server blocks for the NGINX Plus API/dashboard on port 8080 and the stub_status server on port 80 do not need the include, as they are management endpoints restricted by allow/deny rules or authentication.

Additional Information

  • Expected behavior: Blocking TRACK, TRACE, and CONNECT affects only these three methods. GET, HEAD, POST, PUT, PATCH, DELETE, and OPTIONS are not affected. Confirm with application owners that no published application relies on these methods.
  • Port 80 redirects: If the include is placed after return 301, TRACK requests on port 80 receive a 301 redirect instead of 405. The request still does not reach the upstream server, but the 405 response is not returned. Placing the include before the redirect provides a consistent 405.
  • Change window: Apply the change first on a non-production instance or during a maintenance window.
  • Verification status: The fix was accepted by the customer and the case was resolved, but the case does not contain post-change test output for eaaorigin-knocker.timesinternet.in, etm.spog.ai, or auth.gaana.com. These hostnames returned 404 for TRACK before the change. Confirm the results in a lab before relying on this article.
