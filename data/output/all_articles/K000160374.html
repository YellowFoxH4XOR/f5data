Description

When BIG-IP APM is configured to access Citrix environment in Citrix integration mode (Citrix web interface is used), users may intermittently fail to launch Citrix applications or desktops with an "Unable to start" error.

The failure occurs because the BIG-IP APM vdi plugin resolves the Citrix VDA backend FQDN to 127.0.0.1 (localhost) instead of the correct VDA IP address, causing the CGP (Common Gateway Protocol) connection on port 2598 to be attempted against the loopback address, which immediately returns a TCP RST.

Relevant log messages observed in /var/log/apm with vdi log level in debug:

RD: [C] <client_ip>.<port> i <vip>.443: SessVar[Address]: 'vda-hostname.example.com:1494;vda-hostname.example.com:2598;'
RD: [C] <client_ip>.<port> i <vip>.443: Setup connection for CITRIX_CGP to 127.0.0.1:2598
RD: [S] 127.0.0.1.2598 i <tmm_ip>.<port>: server-side connection was reset, reason: TCP RST from remote system

Packet capture confirms the BIG-IP initiates a TCP SYN to 127.0.0.1:2598, which is immediately rejected with a TCP RST:

OUT s1/tmmX : <tmm_ip>:<port> → 127.0.0.1:2598 [SYN]
IN  s1/tmmX : 127.0.0.1:2598 → <tmm_ip>:<port> [RST, ACK]

Environment

  • Citrix deployed in integration mode on BIG-IP APM
  • Citrix VDA backend servers are published using FQDNs (not IP addresses)
  • BIG-IP DNS Lookup Server List configured with multiple DNS servers, including at least one public/external DNS server that cannot resolve internal FQDNs
  • DNS Search Domain List configured with "localhost" (BIG-IP default)

Cause

The BIG-IP APM vdi plugin (and virtually all APM processes) uses an internal process called dnscached (a local BIND instance) for DNS resolution.

This is true regardless of whether the BIG-IP DNS Cache feature is enabled or not.

The dnscached process is responsible for selecting which DNS server from the BIG-IP DNS lookup server List to query. It uses the SRTT (Smoothed Round Trip Time) algorithm (the default BIND upstream nameserver selection algorithm) to prefer the server that has historically responded fastest.

This means the configured order of DNS servers in the BIG-IP DNS lookup server list is not strictly honored by dnscached.

Any server in the list may be selected at any given time based on its cached SRTT value.

The failure chain is as follows:

  1. dnscached selects a public/external DNS server (due to its SRTT, it responded faster than others).
  2. The public DNS server cannot resolve the internal Citrix VDA FQDN (e.g., vda-hostname.example.com) and returns NXDOMAIN.
  3. The BIG-IP system DNS resolver module has a final retry mechanism that appends the configured DNS Search Domain to the failed query and retries. On BIG-IP, the default DNS Search Domain is localhost (stored in sys db DNS.DomainName).
  4. The retry query becomes: vda-hostname.example.com.localhost
  5. Per RFC 6761, any DNS query ending in .localhost is resolved to the loopback address 127.0.0.1 by most DNS servers and resolvers. The response is:
    • A record: 127.0.0.1
    • Rcode: NOERROR (successful response — not NXDOMAIN)
  6. The vdi plugin receives 127.0.0.1 as the resolved address for the VDA and attempts to establish the CGP connection to 127.0.0.1:2598.
  7. The connection is immediately rejected with a TCP RST, and the Citrix application launch fails.

Recommended Actions

Primary fix (required):

Remove all DNS servers from the BIG-IP DNS Lookup Server List that cannot resolve internal FQDNs. This includes public/external DNS servers (e.g., internet-facing resolvers) that are not authoritative for internal domain names. Only DNS servers capable of resolving all required internal FQDNs should remain in the list.

To verify which DNS servers can resolve the required FQDNs, run the following commands from the BIG-IP bash shell (replace the server IPs and FQDN as appropriate):

dig @<dns_server_1> <vda-fqdn>
dig @<dns_server_2> <vda-fqdn>
dig @<dns_server_3> <vda-fqdn>

Any server returning NXDOMAIN, SERVFAIL, or no answer section should be removed from the BIG-IP DNS configuration:

tmsh modify sys dns name-servers replace-all-with { <working_dns_1> <working_dns_2> }
tmsh save sys config

Secondary consideration (optional, not sufficient alone):

You could remove the localhost entry from the DNS Search Domain List.

However, this alone does not resolve the issue: if public DNS servers remain in the list and return NXDOMAIN, the vdi plugin will still fail to resolve the VDA FQDN — just without the 127.0.0.1 fallback. The end-user experience would still be a launch failure.

    Additional Information

    • dnscached is always active when APM is provisioned, regardless of whether the BIG-IP DNS Cache feature (sys db dns.cache) is enabled. It runs as a local BIND instance and handles DNS resolution for all APM processes including the vdi plugin.
    • There is no configuration option to force dnscached to query DNS servers in strict list order. The SRTT algorithm is inherent to BIND's upstream nameserver selection behavior. The only way to ensure correct resolution is to ensure all configured DNS servers can answer all required queries.
    • Bug ID 422201 (Delayed name resolution might stall VDI traffic processing): Unreachable DNS servers in the list cause vdi processing to block while waiting for DNS timeouts. Removing unreachable servers improves overall Citrix launch performance for all users.
