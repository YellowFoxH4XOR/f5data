K000148451: TCP DNS query failed when sidecar/istio enabled

Type
Support Solution
Published
2025-06-22
Updated
2025-06-22
Applies to
  • Aspen Mesh: 1.14, 1.11
Source
https://my.f5.com/manage/s/article/K000148451

Description

When attempting to perform DNS queries using the dig command to resolve a domain managed by an external CoreDNS instance, the queries fail with a connection reset. This occurs even though a ServiceEntry is defined to route TCP traffic on port 53. The intention is to allow services within the mesh to reach an external DNS service via TCP. 

The Service Entry used to reach the TCP DNS was applied at the istio-system namespace so it will be applied globally to all workloads:

apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: tcp-dns-default-se
  namespace: istio-system
spec:
  exportTo:
  - .
  hosts:
  - '*.coredns.cluster.dns'
  location: MESH_EXTERNAL
  ports:
  - name: tcp-53
    number: 53
    protocol: TCP
  resolution: NONE

When using this Service Entry, we get the following error when using the dig command to resolve a domain managed:

#dig test.httpbin.com NAPTR +tcp

;; communications error to 198.223.98.49#53: connection reset

 

Environment

  • Aspen Mesh 1.11.X 1.14.X 1.18.X 1.21.X
  • Istio Service Entry
  • Core DNS

Cause

The root cause is the usage of exportTo: ["." ] in the ServiceEntry. This configuration limits the visibility of the service entry to the istio-system namespace only. As a result, workloads in other namespaces are unable to route traffic through the service entry to reach the external DNS service, which leads to the failed TCP resolution attempt.

Recommended Actions

To ensure the ServiceEntry is accessible by workloads in all namespaces:

  1. Edit the existing ServiceEntry and remove the exportTo field entirely or set it to ["*"]:
    apiVersion: networking.istio.io/v1beta1
    kind: ServiceEntry
    metadata:
      name: tcp-dns-default-se
      namespace: istio-system
    spec:
      hosts:
      - '*.coredns.cluster.dns'
      location: MESH_EXTERNAL
      ports:
      - name: tcp-53
        number: 53
        protocol: TCP
      resolution: NONE

  2. Validate with the dig command from a workload in a different namespace:

    # dig test.httpbin.com NAPTR +tcp
     <<>> DiG 9.16.1-Ubuntu <<>> test.httpbin.com NAPTR +tcp
     global options: +cmd
     Got answer:
    ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
    flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1

    QUESTION SECTION:
    test.httpbin.com.          IN      NAPTR

    Query time: 20 msec
     SERVER: 198.223.98.49#53(TCP)
     WHEN: Thu Jun 20 13:30:42 UTC 2025
     MSG SIZE  rcvd: 45

     

Additional Information

dig, nslookup, and kdig can be used to validate DNS resolution modes. Make sure the query protocol (UDP/TCP) matches the expected routing behavior (e.g., dig +tcp vs default UDP).
