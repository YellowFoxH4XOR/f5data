Description

Configsync failes and received error on GUI:

Sync error on <hostname>: Load failed from /Common/<peer_name> 01070734:3: Configuration error: Modify of node attribute is not permitted.

and /var/log/ltm shows:

err mcpd[<pid>]: 01070734:3: Configuration error: Modify of node attribute is not permitted.
err mcpd[<pid>]: 01071488:3: Remote transaction for device group /Common/<device_group_name> to commit id <commit ID> /Common/<hostname> 0 failed with error 01070734:3: Configuration error: Modify of node attribute is not permitted..

Environment

  • BIG-IP
  • ConfigSync

Cause

The cause of the error message is due to a discrepancy in the autopopulate setting between BIG-IP peer devices. For example, this may occur when you delete a FQDN node and re-create the same node with different autopopulate setting in one of the devices.

For example,

LTM1

ltm node /Common/node.com {
    fqdn {
        address-family all
        autopopulate enabled
        name node.com
    }
}

LTM2

ltm node /Common/node.com {
    address 198.51.100.42
}

Recommended Actions

Remove the conflicting node from one of the devices and synchronize again.

For example, if you want to delete the non-FQDN node, perform the following tasks:

  • Log into the Configuration utility of the device with the non-FQDN node.
  • Navigate to Local Traffic > Pools, select the pool object that contains the conflicting node and remove the node from the pool.
  • Navigate to Local Traffic > Nodes and delete the conflicting node.
  • Initiate a config sync and push the configuration from the device with the FQDN node to the device with the deleted node.

Additional Information

Once an FQDN node is created, its autopopulate settings cannot be modified via the Configuration Utility or tmsh. When the BIG-IP HA devices are synced, the node will have the same setting on both devices. An FQDN node should not have different autopopulate setting, unless it had been deleted and re-created with different setting. It is by-design that configsync fails in this case.

If unable to identify the node, it is possible to do the following:

  1. Take a backup of the LTM with the known good configuration
  2. Delete all the iApps on the LTM that is not receiving the sync
  3. Delete all the virtual servers on the LTM that is not receiving the sync
  4. Delete all the iRules on the LTM that is not receiving the sync
  5. Delete all the pools on the LTM that is not receiving the sync
  6. Delete all the nodes on the LTM that is not receiving the sync
  7. Re-run the config sync from the known good configuration unit.
  8. Accept the "overwrite" warning box because the "newer" configuration will be the deleted config.  You want to sync the "older" configuration from the known good LTM

Alternatively, it is possible to use diff command to find the discrepancy of the nodes in a case that there are numbers of nodes. 

  1. Save all of the nodes configuration from the bigip.conf file to a separate file. Do that in the other device. E.g(file1 for bigip1, file2 for bigip2). You might need to copy both files into a linux machine. The diff command is available in F5 BIG-IP too, you can put them into the same BIG-IP, and compare. 
  2. use diff to check the discrepancy
    1. Run this command in a BIG-IP or any Linux device: # diff -u file1 file2 
    2. similar output will show: 
      --- file1     2025-04-07 09:32:05
+++ file2     2025-04-07 09:33:32
@@ -356,6 +356,11 @@

 ltm node /Common/node1 {
     fqdn {
-        address-family all
-        autopopulate enabled
         name node1
     }
 }

+ltm node /Common/node2{
+    fqdn {
+        address-family all
+        autopopulate enabled
+        name node2
+    }
+}

                   The above output means node2 exist with autopopulate enabled in file2, but not in file1.

                    For node1. the follow two lines exist in file1, but not in file 2. This means that file2 configuration has the same node, but it is missing the following two lines. 

-        address-family all
-        autopopulate enabled

        This is a strong evidence that nodes are configured differently across this two BIG-IPs. 

3. Locate the node in both BIG-IP GUI, and check the configuration. Delete the one that aren't in service. Perform configsync by pushing the desired device into the Failover group, the sync should be successful.
