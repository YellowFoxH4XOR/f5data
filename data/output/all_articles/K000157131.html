K000157131: TLSv1.3 negotiation fails after upgrade to BIG-IP 17.1.3 when using cipher groups with FFDHE4096 and 'Strength' ordering

Type
Support Solution
Published
2025-10-24
Updated
2025-12-19
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.3
Source
https://my.f5.com/manage/s/article/K000157131

Description

After upgrading to BIG-IP TMOS 17.1.3 TLSv1.3 may not be available or negotiable for client connections, even when the configuration includes TLSv1.3 ciphers. This issue can manifest as TLSv1.3 not appearing in third-party SSL testing tools (such as SSL Labs or Qualys), or as handshake failures with errors such as javax.crypto.AEADBadTagException: Tag mismatch in Java/OpenJDK clients. Packet captures may show the handshake failing after the Server Hello, with fatal alerts and connection resets.

Environment

  • Product: BIG-IP LTM
  • Version: 17.1.3
  • Configuration:
    • Custom cipher groups including TLSv1.3 ciphers
    • Cipher group ordering set to "strength"
    • DH groups including FFDHE4096
    • Client SSL profiles using custom cipher groups
  • Affected clients:
    • Java/OpenJDK-based clients
    • Third-party SSL testing tools (SSL Labs, Qualys)

Cause

A compatibility issue exists between the FFDHE4096 Diffie-Hellman group and certain clients (notably OpenJDK and SSL Labs). When the cipher group ordering is set to "strength," BIG-IP prefers the highest strength cipher and DH group (FFDHE4096). Some clients claim to support FFDHE4096 but fail to complete the handshake, resulting in TLSv1.3 negotiation failures. This behavior may not have been observed in earlier versions due to a previous bug in cipher selection logic, which was corrected in version 17.1.3.

Recommended Actions

To resolve or work around this issue, use one or more of the following approaches:

 

  1. Exclude FFDHE4096 from Cipher Groups:
    Create a cipher rule that specifies DH groups to exclude FFDHE4096.
    Apply this rule as an exclusion in your cipher group.

    ltm cipher rule <rule_name> {
        dh-groups FFDHE4096
    }
    ltm cipher group <group_name> {
       allow { <existing_rule> { } }
        exclude { <rule_name> { } }
        ordering strength
    }

     

  2. Change Cipher Group Ordering to "default":
    Create a new cipher group with ordering default instead of ordering strength. Apply this cipher group to the affected virtual server.

    ltm cipher group <group_name> {
        allow { <cipher_rule> { } }
        ordering default
    }
