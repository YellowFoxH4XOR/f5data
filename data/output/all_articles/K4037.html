Topic

The BIG-IP system's state mirroring mechanism was redesigned in version 4.6.3. This new version provides significant performance and stability improvements.

As in previous versions of BIG-IP, state mirroring is controlled by the sfd process. This daemon sends and receives messages between the peer units in a redundant configuration. These messages are used to create or delete connections and persistence entries so that the connection and persistence tables on each unit are synchronized.

Important: State mirroring will not function during a software upgrade.

Network Behavior

Each unit in a redundant pair listens on TCP port 1028 for connections from its peer. Each unit sends data to its peer using TCP source port 1027 or 1029. An HTTP Keep-Alive packet is no longer sent between the units in a failover pair.

Configuration Files

Stateful failover configuration is contained within the bigdb variables. You set these variables during the initial configuration and generally do not need to change them.

The following bigdb variables are used with stateful failover:

bigdb variableDescription
Local.Bigip.StateMirror.IPAddrThe IP address used for stateful failover.
Local.Bigip.StateMirror.PeerIpAddrThe IP address of the peer unit.
Common.Bigip.MaxQLengthThe maximum size of the queue used for scheduled mirroring messages.

Limits

The maximum size for normal persistence entries is 63 characters.
The maximum size for SIP persistence entries is 2048 characters.

Functionality that relies on sfd

The bigpipe time sync command relies on the sfd process to send time synchronization messages between the two units.

The bigpipe unit peer show command relies on the sfd process to query the peer unit for its unit number.

Log messages

When the sfd process starts and opens a socket to receive a connection from the peer unit, it logs the following message to the /var/log/bigip file:

sfd: Waiting on accept

When the sfd process starts and opens a socket to send a connection to the peer unit, it logs the following message the /var/log/bigip file:

sfd: starting connect

Startup, shutdown, and other processes

When the sfd process is started, it verifies that the BIG-IP variables that contain its configuration data are present. If the required variables do not exist, the sfd process will exit.

Note: The sfd process also checks to see if it is running on a 3-DNS stand-alone system. If it is running on a 3-DNS stand-alone system, the sfd process will exit.

The sfd process will also detect and attempt to kill any other instances of the sfd process when it starts. As a result, multiple sfd parent processes should not exist.

The process ID for the current sfd process is written to the /var/run/sfd.pid file.

Command changes

The bigpipe sfstats command is no longer available.
