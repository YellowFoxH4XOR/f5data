Description

BIG-IP supports vMotion migrations on VMware ESXi hypervisors. VMware vMotion allows you to migrate BIG-IP VE guests from one physical host to another while maintaining continuous service.

When vMotioning BIG-IP VE guests, there can be a transitory pause in response from BIG-IP. The delay in response can be something on the order of several seconds, possibly a bit longer or even shorter, depending on your environment. F5 Support has recommendations to minimize impact for production traffic served on BIG-IP LTM and DNS VEs.

Environment

  • BIG-IP VEs running on ESXi hypervisors

Cause

BIG-IP VEs will be vMotioned (virtual resources migrated from one server to another server) as part of ESXi hypervisor maintenance activities.

Recommended Actions

A BIG-IP administrator can be logged into the CLI, and the CLI will not immediately take your input during the vMotion migration. BIG-IP will process any input you provided after the vMotion process is complete, which shouldn't take long, but there could be a noticeable delay.

While logged into the CLI, press "Enter" repeatedly to determine if and when the vMotion unresponsiveness happens during the vMotion process.

For BIG-IP LTM VEs, as most virtual servers will be processing connections over TCP, the best plan is to perform the vMotion on the Standby guest to account for any unexpected delays due to the vMotion migration. Once complete, failover traffic, then perform the vMotion migration on the peer guest.

In the case of BIG-IP DNS, it is connectionless and most implementations have all BIG-IP DNS guests in the Active state. As long as there are other BIG-IP DNS guests available to answer DNS queries while a DNS guest is being migrated, you can vMotion one DNS guest at a time. 

F5 Support recommends verifying all BIG-IP DNS guests are up, CPU and memory resources healthy, and answering DNS queries prior to the maintenance window.

If you plan to vMotion several BIG-IP DNS guests during the same maintenance window, F5 Support recommends waiting several minutes prior to performing the next vMotion to verify the vMotion migration is complete. There could be a short delay in BIG-IP response when the vMotion migration is complete, yet BIG-IP could take a bit longer past that time to be as responsive as is normal.

Run dig queries against the BIG-IP DNS guest being vMotioned to test for its availability to answer queries.

dig a [DNS WideIP name] @[DNS listener address] +short

You could run this as a loop. Edit the values as needed for testing.

for i in `seq 1 [number of times to run the synchronous commands in this for loop]`; do echo "query ${i}"; dig a [WideIP name] @[DNS listener address] +short; sleep [interval in seconds]; done

If there is no answer for a DNS query, then that means the BIG-IP DNS VE was not responsive during the query, and you would have an estimate for how long a given DNS VE is unreachable during the vMotion migration.

[root@localhost:Active:In Sync] config # for i in `seq 1 100`; do echo "query ${i}"; dig a wip1.example.com @10.2.115.170 +short; sleep .5; done
