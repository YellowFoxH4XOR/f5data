Description

  • You have a CDN (F5 XC CDN or an external CDN such as Akamai, Cloudflare, AWS CloudFront, etc.) in front of your F5® Distributed Cloud HTTP Load Balancer.
  • You want to ensure the XC Load Balancer correctly identifies the real client IP address for logging, security controls, and policy enforcement.
  • You are unsure whether to enable the Trusted Client IP Headers setting and how to do so safely.

Environment

  • F5® Distributed Cloud (XC) HTTP Load Balancer
  • Content Delivery Network (CDN): F5 XC CDN or any external CDN/reverse proxy in the data path

Client IP Preservation

By default, the F5 XC HTTP Load Balancer uses the Layer 3 source IP address as the client IP. When a CDN sits in front of the XC LB, the L3 source IP will be the CDN's egress IP, not the original client's IP address.

 

To preserve true client IP information in the upstream request, CDNs typically embed the original client IP in an HTTP request header before forwarding traffic to the origin.  The archetypal header for this purpose is X-Forwarded-For (XFF), but depending on the CDN it may be called True-Client-IP, X-Client-IP, X-Connecting-IP, or a custom name.  We will use the archetypal XFF descriptively in the below, but when referenced it denotes any such header containing client IP information.

 

Trusted Client IP Headers

Configure the Trusted Client IP Header on the XC Load Balancer

Navigate to your HTTP Load Balancer configuration and set the Trusted Client IP Headers field:

HTTP Load Balancer → Other Settings → Trusted Client IP Headers

Enter the header name that your CDN injects (such as: True-Client-IP, X-Forwarded-For).

 

 

Result of this configuration: The rightmost IP value found in the named header will be treated as the true client source IP by the XC LB, for the purposes of:

  • Logging
  • IP-based security controls (Service Policies)
  • User Identification Policy and dependent functions (Rate Limiting)
  • Malicious Users
  • IP Reputation checks
  • L7DDoS Automitigation

Important Note: It is recommended that the Trusted Client IP Headers setting should only be enabled when a trusted proxy or CDN is confirmed to be in the data path between the client and the XC LB. Enabling this setting without a CDN in the path allows clients to spoof their source IP by injecting arbitrary header values.

 

Network Access Controls

A decision to trust a client IP header like XFF is predicated on it having been inserted by a trusted proxy.  We assume the downstream CDN is trusted, but how can we be sure the header was inserted by the CDN?  HTTP headers are entirely within the client's control, and a client connecting directly to an XC LB with Trusted Client IP Headers enabled could abuse the implicit trust of the header to obfuscate their source and potentially evade security controls.

Therefore, it's strongly recommended to restrict network access to the XC LB allowing only the CDN's IP ranges to reach it (customers may choose to selectively add additional IPs to the whitelist for testers, operations staff, and others who may have a legitimate need to bypass the CDN).

The first step toward implementing such a control is to obtain the IP ranges definition from the CDN provider.  All CDN providers will provide a reference document for this.  Consult with your provider if you cannot find it.

In F5 XC, the control can be implemented in either of two ways:

  1. A Fast ACL applied to the LB's public VIP.  Add the CDN IP ranges to the Fast ACL with the Allow action, and append a default deny to the end.  More information can be found here.
  2. A Service Policy applied to the LB (it should be first in the order).  For ease of administration, it's recommended to enter the CDN IP ranges in an IP Prefix Set and reference the prefix-set in a Service Policy Rule to permit the CDN range and deny access to other sources.
    1. Note: if there are additional Service Policies on the LB, the NEXT_POLICY action should be used on the whitelist rule.  Using the ALLOW action will result in matched traffic skipping all subsequent Service Policy rule evaluation, which is typically not intended. 

 

Validation Checklist

To ensure proper configuration of the XC LB for a downstream CDN data path, perform the following checks:

  1. Access the application through its normal public data path, i.e. through the CDN.  Ensure that:
    1. The application operates as expected
    2. Your test traffic is identifiable in XC request logs with a source IP of your client, not the CDN.
    3. True client IP information is logged at the origin servers as expected.
  1. Attempt to access the XC LB directly from an external source not in the CDN whitelist.
    1. Ensure the XC LB is not reachable, or returns an error response.
    2. Add the relevant HTTP header with a trusted client IP to your request (for instance, append to a curl command -H 'X-Forwarded-For: 1.2.3.4' where 1.2.3.4 is within the CDN's trusted range).  This spoofing attempt should not permit access to the LB.

 

 

Additional Information

The Trusted Client IP Headers setting affects all IP-based security functions on the XC LB. Validate your Service Policies, and rate limiting rules after enabling this setting to ensure they behave as expected with real client IPs.
