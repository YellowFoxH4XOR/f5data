Description

Upgrade attempts on BIG-IP Virtual Edition (VE) systems may fail with errors like below sample trail, in the log file "/var/log/liveinstall.log":

info:  WARNING: Device for PV DSbBKH-oc0S-SGDe-notX-LF6Q-D7IM-FK49Bz not found or rejected by a filter.
info:  Cannot change VG vg-db-vda while PVs are missing.
info:  Consider vgreduce --removemissing.
info:  Cannot process volume group vg-db-vda
info: >----
error: Disk full (volume group). See SOL#10636
Terminal error: tm_install::VolumeSet::VolumeSet_add_planned -- error adding /:83 volume to set sda.22
Live install end at 2025/07/25 18:44:57: failed (return code 5)

 

You may see continuous Warning logs on the Console, like below sample:

WARNING: Device for PV DSbBKH-oc0S-SGDe-notX-LF6Q-D7IM-FK49Bz not found or rejected by a filter.

 

When running the command "tmsh show /sys software", you can see that the last upgrade attempt was failed, like the below sample output:

--------------------------------------------------------
Sys::Software Status
Volume Product Version Build Active Status
--------------------------------------------------------
HD1.22 BIG-IP 17.1.2.2 0.0.12 no failed (tm_install::VolumeSet::VolumeSet_add_planned -- error adding /:83 volume to set sda.22)
HD1.2 BIG-IP 15.1.10.2 0.0.2 yes complete

 

When running the command "vgdisplay -vA", you can see more than one PV (Physical Volume), like the below sample output. One of the PVs is normally detected, but the other one is marked as 'unknown', and actually caused the problem:

...

--- Physical volumes ---

 PV Name        /dev/sda3
 PV UUID        4Iljxc-EVnk-vsYf-ghV5-rdIk-dFmF-uMaa9n
 PV Status       allocatable
 Total PE / Free PE  63945 / 56721

 PV Name        [unknown]     
 PV UUID        DSbBKH-oc0S-SGDe-notX-LF6Q-D7IM-FK49Bz
 PV Status       allocatable
 Total PE / Free PE  63999 / 63999

 

When running the command "vgreduce --removemissing --test vg-db-vda", you may see something like below output which confirms that there is some problem with Disk Volume consistency:

TEST MODE: Metadata will NOT be updated and volumes will not be (de)activated.
  WARNING: Device for PV DSbBKH-oc0S-SGDe-notX-LF6Q-D7IM-FK49Bz not found or rejected by a filter.
  Wrote out consistent volume group vg-db-vda

Environment

  • BIG-IP VE (Virtual Edition)
  • Upgrade Attempt Failed
  • LVM with multiple Physical Volumes (PVs) in a Volume Group (vg-db-vda)
  • Wrong / Missed PV reference in the Volume Group

Cause

The upgrade attempt fails because the Logical Volume Manager (LVM) volume group contains references to missing or inaccessible physical volumes. This situation can occur if virtual disks were removed or reconfigured at the Hypervisor-level without updating LVM metadata, causing the volume group to be considered "full" or "unusable" even when free space is reported.

 

Recommended Actions

 

1. Create a UCS Archive file and download on your local system, before going for next steps.

 

2. Run the below command to remove the wrong / missed PV reference:
# vgreduce --removemissing vg-db-vda

 

3. Run the below command to confirm that the volume group is consistent with the expected output as 'Volume group "vg-db-vda" is already consistent':
# vgreduce --removemissing --test vg-db-vda

 

4. Delete the previously-failed (Inactive) Boot Location from WebUI (System  ››  Disk Management  ››  HD1)

 

5-1. Run the below command to make sure that there is at least 15GB of free disk space for the new Boot Location [K13636984], before starting the new round of upgrade:
# vgs

5-2. If you still do not have enough disk space, increase the size of the virtual disk in your Hypervisor-level.

 

6. Once the volume group is consistent and sufficient space is available, you can start the upgrade procedure [K84205182], and check for the result.
