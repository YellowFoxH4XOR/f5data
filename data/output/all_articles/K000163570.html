K000163570: BIG-IP APM OAuth Client Password-Grant Requests Return HTTP 503 Due to Username Validation

Type
Support Solution
Published
2026-10-06
Updated
2026-10-06
Applies to
  • BIG-IP
  • BIG-IP APM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000163570

Description

A BIG-IP APM OAuth Client using the password grant can return HTTP 503 when the username submitted to the OAuth Authorization Server contains characters rejected by Logon Page input validation.

The following messages may appear:

Failed to validate logon page input field username.

OAuth Client: failed for server '<OAuth-Authorization-Server>'

using 'password' grant type, error: HTTP error 503

The OAuth Client may then follow the configured fallback branch.

Environment

  • BIG-IP APM configured as an OAuth Client.
  • The OAuth Client uses the password grant.
  • A local OAuth Authorization Server is hosted on BIG-IP.
  • The Authorization Server uses an APM access policy containing a Logon Page agent.
  • The username contains one or more characters rejected by Logon Page validation.
  • The OAuth Client and Authorization Server may use different virtual servers.
  • A software fix is available for this behavior.

Cause

A Logon Page input-validation change tracked by Bug ID 2259313 rejects the following characters in the username field:

" / [ ] : ; | = , + * ? < >

When the OAuth Client submits a username containing one or more of these characters, the OAuth Authorization Server Logon Page rejects the username. The OAuth Client reports the resulting authorization failure as HTTP 503.

Answer/Recommended Actions

Apply a BIG-IP software release containing the fix for this issue, where available.

If the fix cannot be applied, use one of the following workarounds.

Workaround 1: Change the Logon Page username field type

  1. Open the access policy used by the OAuth Authorization Server.
  2. Open the Logon Page agent.
  3. Change the username field type from text to password.
  4. Enable username splitting if required by the access policy.
  5. Use equivalent settings for the applicable Logon Page agent:

    customization-group /Common/<logon-page-agent>

    fieldtype1 password

    split-username true

  6. Save and apply the access policy.
  7. Test the OAuth password-grant request with the original username.
  8. Confirm that the Authorization Server access policy reaches the expected Allow branch.
  9. Validate all relevant claims in the issued token.

Impact of workaround: Testing showed that the JWT sub claim retained the original username, while the JWT username claim was empty. Confirm that downstream applications do not depend on the username claim before using this workaround.

Workaround 2: Encode and decode the username

If changing the Logon Page field type is not suitable, encode the username before the OAuth request and decode it in the OAuth Authorization Server access policy.

  1. In the action that prepares the username for the OAuth request, encode the value as hexadecimal and add the f5hx prefix:

    binary scan [mcget {perflow.custom}] H* h
    return "f5hx$h"

  2. In the OAuth Authorization Server access policy, add a Variable Assign action after the Logon Page action and before the OAuth Authorization action.
  3. Decode the value and assign it to session.logon.last.username:

    set u [mcget {session.logon.last.username}]
    if { [string match "f5hx*" $u] } {
        return [binary format H* [string range $u 4 end]]
    }
    return $u

  4. Configure the OAuth Authorization subject to use:

    %{session.logon.last.username}

  5. Test usernames containing special characters and usernames containing only ordinary characters.
  6. Confirm that the Authorization Server access policy reaches the expected Allow branch.
  7. Validate the resulting JWT claims.

Impact of workaround: Testing showed that the JWT sub claim contained the original decoded username, while the JWT username claim retained the encoded f5hx value. Validate the token claims in the target environment before deploying this workaround.

Additional Information

  • An HTTP 503 from the OAuth Client does not necessarily indicate that the OAuth Authorization Server virtual server was unreachable.
  • The Authorization Server may receive the request and reject it during Logon Page input validation.
  • The absence of a TCP/443 flow to the Authorization Server virtual server in a packet capture does not rule out an alternate internal connection path.
  • Validate downstream dependencies on the JWT sub and username claims after applying either workaround.
