Description

When using an iRule with DECOMPRESS::enable on a gzip compressed request, the HTTP request appears to be truncated when uncompressed and sent to the server.

Environment

  • iRule
  • HTTP Compression
  • Large request such as a POST with a payload

Cause

Content-Length header is not updated to reflect uncompressed payload size after decompression. The server then responds after receiving data equal to the Content-Length size. However the uncompressed payload is larger and this may therefore appear that the request is being truncated.

This behaviour is controlled by the HTTP Compression profile's Compression Buffer Size setting, which is 4096 bytes by default.

Recommended Actions

There are two solutions to this issue.

The first solution is to increase the Compression Buffer Size to a value that is equal or greater than the expected HTTP payload size.

Alternatively, enable Selective request chunking in the HTTP profile, which removes the Content-Length header and instead chunks the request sent to the server, with the Transfer-Encoding: Chunked header.

Additional Information

Decompressing a compressed request from a client is typically done to allow content manipulation or inspection, for example by ASM.
