K000162464: SNMPv3 polling not working on BIG-IP device

Type
Support Solution
Published
2026-07-29
Updated
2026-08-05
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000162464

Description

The remote SNMP manager reports a timeout, while local queries return valid data.

[itrsprod@snmp ~|$ snmpwalk -v3 -1 authPriv -u SNMPv3User -a SHA -A ""********" -x AES -X ""********" 172.24.208.205

snmpwalk: Timeout

A packet capture on the BIG-IP management interface shows incoming SNMP requests but no response packets:

15:13:04.748248 IP .<SOURCE_PORT> > <BIG-IP_MGMT_IP>.161: SNMPv3 GetRequest

15:13:04.748248 IP .<SOURCE_PORT> > <BIG-IP_MGMT_IP>.161: SNMPv3 GetRequest

15:13:04.748248 IP .<SOURCE_PORT> > <BIG-IP_MGMT_IP>.161: SNMPv3 GetRequest

 

The absence of return traffic confirms that no SNMP response was observed leaving the BIG-IP at the capture point.

Environment

  • SNMP v2 and V3 version
  • The remote SNMP manager reports a timeout
  • Local SNMP queries succeed
  • BIG-IP Mangament security firewall

 

Cause

The issue occurs because an external security policy blocks the SNMP manager’s source IP, preventing successful SNMPv3 communication even though requests reach BIG-IP. Whitelisting the source IP resolves the issue.

 

Recommended Actions

  1. Capture the SNMP traffic

Start a packet capture on the BIG-IP management interface, then initiate a query from the remote SNMP manager.

#tcpdump -nni mgmt -s0 -w /var/tmp/snmp_host.pcap 'host <NMS_IP> and (port 161 or port 162)'

 

you see only IN copies with no OUT copies:

2 2026-07-13 02:52:19.204848 192.0.2.10 → 198.51.100.20 92 47407 161 SNMP get-request

4 2026-07-13 02:52:20.205923 1.001075 192.0.2.10 → 198.51.100.20 92 47407 161 SNMP get-request

6 2026-07-13 02:52:21.207000 1.001077 192.0.2.10 → 198.51.100.20 92 47407 161 SNMP get-request

8 2026-07-13 02:52:22.207065 1.000065 192.0.2.10 → 198.51.100.20 92 47407 161 SNMP get-request

 

  1. Test SNMP locally on the BIG-IP

Run a local SNMPv2 query,

#snmpget -v2c -c public 127.0.0.1 sysDescr.0

 

Expected output:

SNMPv2-MIB::sysDescr.0 = STRING: BIG-IP Tenant : Linux 3.10.0-862.14.4.el7.x86_64 : BIG-IP software release 17.5.1.3, build 0.0.19

 

Run a local SNMPv3 query,

 #snmpget -v3 -l authPriv -u SNMPv3User -a SHA -A "********" -x AES -X "********" 127.0.0.1 sysDescr.0nfig

 

Expected output:

SNMPv2-MIB::sysDescr.0 = STRING: BIG-IP Tenant : Linux 3.10.0-862.14.4.el7.x86_64 : BIG-IP software release 17.5.1.3, build 0.0.19

 

A successful local query confirms that:

    • The SNMP daemon is responding locally.
    • The specified SNMP credentials are valid for the local test.
    • The requested OID is accessible to the test account.

It does not confirm that:

    • The SNMP daemon can process the remote request under the current configuration.

 

  1. Verify the route to the remote SNMP manager

From the BIG-IP tenant, verify the route to the SNMP source address:

#ip route get <SNMP_Server_IP>

 

Example output:

[root@bigip:Standby:In Sync] config # ip route get 192.0.2.10
192.0.2.10 via 198.51.100.3 dev mgmt src 198.51.100.20
cache

 

Confirm that:

    • The route uses the expected management interface.
    • The next hop information.
    • The SNMP is not reached through an unintended data-plane route.

If the route uses an unexpected interface or source address, correct the routing configuration before continuing.

 

  1. Verify the BIG-IP SNMP configuration

Verify allowed-addresses in the configured SNMP source allow list:

#tmsh list sys snmp allowed-addresses

 

Example output:

sys snmp {
    allowed-addresses {
        127.0.0.1/8
        192.0.2.13/32
    }
}     

The source address observed in the packet capture must be present. For a single SNMP server host, the entry should normally use a /32prefix.

 

If the SNMP address is missing, add it:

#tmsh modify sys snmp allowed-addresses add { SNMP_server_IP/32 }
#tmsh save sys config

 

Verify the SNMPv3 User Configuration

Confirm the user exists and the auth/priv settings match what you're passing on the command line:

#tmsh list sys snmp users

 

Example sample output:

sys snmp {

    users {

      lab_user {

            auth-protocol none

            oid-subset .1

            privacy-protocol none

            security-level no-auth-no-privacy

            username snmp_lab_user

        }

    }

}

Check that:

    • Username matches (SNMPv3User)
    • Auth protocol 
    • Privacy protocol 

F5 documents the remote SNMP configuration in K52219241: Configure SNMP access to the BIG-IP system. 

 

  1. Verify that snmpd is running correctly

Check for the SNMP process is running on the device

#tmsh show /sys proc-info | grep -A 3 -i snmpd

 

Example output:

[root@bigip1] config # tmsh show /sys proc-info | grep -A 3 -i snmpd

Process: snmpd      

----------------------------

Process ID              6686

Blade Id                   0

 

You can also check the listening sockets from the advanced shell:

#netstat -anup | grep snmp

 

           Example output:

[root@bigip1] config # netstat -anup | grep snmp

udp        0      0 127.1.1.254:55819       127.1.1.253:3792        ESTABLISHED 6686/snmpd          

udp        0      0 0.0.0.0:161             0.0.0.0:*                           6686/snmpd          

udp6       0      0 :::161                  :::*                                6686/snmpd    

 

The output should show an active snmpd process and a listener for UDP/161.

  1.  Check the SNMP logs

Review recent SNMP-related log messages: #tail -100 /var/log/daemon.log | grep -i snmp

Also review the SNMP daemon logs: #tail -100 /var/log/snmpd.log

Look for messages such as: can't verify hostname or: Connection from UDP/IPv6: [::ffff:<SNMP_Server_IP>]:<SOURCE_PORT> REFUSED

 

    • A REFUSED message generally indicates that the source address is not present in the authorized SNMP management-station list. 
    • If an FQDN is configured in the SNMP allow list, verify that the BIG-IP can resolve it. An unresolved FQDN may cause messages similar to can't verify hostname or gethostbyname(...) failed
    • Replacing FQDN entries in the SNMP allowed-address list with IP addresses when DNS resolution is unreliable. 

  1. Check the BIG-IP management interface firewall

The management interface firewall rule can block UDP/161 even when the SNMP configuration is correct.

GUI procedure

    1. Log in to the BIG-IP Configuration utility.
    2. Go to System > Platform.
    3. Select the Security tab.
    4. Review the management interface firewall rules.
    5. Confirm that an rule are created
    6. Confirm that the allow rule is placed before any deny-all rule.
    7.  Whitelisting the SNMP IP from the configuration.

CLI procedure:

To review the management IP firewall rules specifically:

#tmsh list /security firewall management-ip-rules

 

          After updating the Management Firewall rules, initiate SNMP polling and verify whether the issue is resolved.

 

  1. Verify if the issue aligns with the known behavior documented in K35622341

If the issue still occurs after applying all the recommended changes, generate a new QKView and PCAP and open a support case for further investigation.
