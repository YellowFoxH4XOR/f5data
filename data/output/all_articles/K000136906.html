Description

When running "/usr/lib/jvm/jre/bin/java -version" to find details about the version of java insalled on bigip VE, it appears that the "qcow2.zip.bundle" file for deploying a tenant Big-IP on a F5OS host installs a different type of the OpenJDK software compared to the usual ".iso" file.

The qcow2 file seems to contain a version beginning with "OpenJDK Client VM", while the iso file's version begins with "OpenJDK Server VM".


Sample output on iso install:

java version "1.7.0_181"

OpenJDK Runtime Environment (rhel-2.6.14.8.el7_5-i386 u181-b00)

OpenJDK Server VM (build 24.181-b00, mixed mode)


Sample output on qcow2 tenant install:

java version "1.7.0_181"

OpenJDK Runtime Environment (rhel-2.6.14.8.el7_5-i386 u181-b00)

OpenJDK Client VM (build 24.181-b00, mixed mode)

 

Environment

BIG-IP tenant on F5OS host

 

Cause

This is by design - the above does not actually signify that a different version of java is installed, it is rather the result of different configuration parameters being passed to the same java binary upon startup.

Basically the difference between client vm and server vm is:

"

On platforms typically used for client applications, the JDK comes with a VM implementation called the Java HotSpot Client VM (client VM). The client VM is tuned for reducing start-up time and memory footprint. It can be invoked by using the -client command-line option when launching an application.

On all platforms, the JDK comes with an implementation of the Java virtual machine called the Java HotSpot Server VM (server VM). The server VM is designed for maximum program execution speed. It can be invoked by using the -server command-line option when launching an application.

"

(from https://docs.oracle.com/javase/8/docs/technotes/guides/vm/index.html )

Thus, the qcow2 is optimised for reducing start-up time and memory footprint, while the iso is optimised for execution speed. The exact same application is launched, but with different command line options.
