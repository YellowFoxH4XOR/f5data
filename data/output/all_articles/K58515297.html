Topic

You should consider using this procedure under any of the following conditions:

  • You want to view different information related to the high availability (HA) status of the VELOS partition.
  • You want to configure redundancy mode of a partition.
  • You want to manually trigger a failover of the partition controllers.

Description

The VELOS partition coordinates the creation of tenants and assignment of compute resources to these tenants. HA of the VELOS partition typically requires no setup other than the floating management IP address when you install the VELOS chassis with two system controllers. For more information about how HA functions at the partition level, refer to K19204400: Overview of the VELOS system architecture: High availability.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You must have a partition administrator-privileged account.
  • You must have access to the command-line interface (CLI) of the floating management IP address of the desired partition.

Procedures

You can view the different aspect of the HA status, configure the partition redundancy mode, trigger a manual failover of the partition controllers, and check the log file for failover event(s). To do so, perform the following procedures:

  • View the redundancy state of a partition
  • View the operational state of all configured nodes of a partition
  • Configure the redundancy mode of a partition
  • Enable auto failback to the preferred controller of a partition
  • Manually trigger a failover of the controllers for a partition
  • Determine if a failover occurred on the partition controllers
  • Determine if the partition configuration and files are replicated

View the redundancy state of a partition

To view the redundancy state of a partition in the CLI, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the CLI of the partition’s floating management IP address as the partition administrator.
  2. View the system redundancy state setting by entering the following command:

    show system redundancy state

    The following example output displays that the redundancy mode is set to auto with auto-failback disabled, and the current active controller is controller 1:

    system redundancy state mode auto
    system redundancy state auto-failback disabled
    system redundancy state auto-failback failback-delay 30
    system redundancy state current-active controller-1
    system redundancy state status redundant

View the operational state of all configured nodes of a partition

To view the operational state of all configured nodes (both controller and compute) of a partition in the CLI, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the CLI of the partition’s floating management IP address as the partition administrator.
  2. View the system redundancy state setting by entering the following command:

    show system redundancy nodes

    The following example output displays that the currently active controller is controller-2, while the configuration read-only replica resides on blade-1:

                                                        STARTUP  STATUS               SERVICES     
    NAME          STATUS   STATUS REASON         FAULT  AGE      AGE     OS VERSION   VERSION      
    -----------------------------------------------------------------------------------------------
    blade-1       replica  services running      false  9d       9d      2.0.0-22925  2.0.0-22925  
    controller-1  standby  peer active           false  9d       9d      2.0.0-22925  2.0.0-22925  
    controller-2  active   peer was not present  false  9d       9d      2.0.0-22925  2.0.0-22925 

    The definition of each field is noted as follows:

    • NAME: Name of the node (both controller and compute)
    • STATUS: The replication state of the configuration database for each node of a partition, which includes the following statuses:
      • replica: The configuration database instance is a read-only replica of the instance on the active controller.
      • active: The configuration database instance on the active controller.
      • standby: The configuration database instance on the standby controller.
      • offline: The configuration database instance is disconnected or starting.
      • failed: An error occurred on the configuration database instance.
      • - : The state of the configuration database instance is unknown.
    • STATUS REASON: The reason why it is in the current status.
    • FAULT: Indicates that the system has detected a fault on the node.
    • STARTUP AGE: Indicates the last restart time of the node.
    • STATUS AGE: Indicates the time that a change in the reported status was detected.
    • OS VERSION / SERVICES VERSION: Indicates the currently running software versions on the node. Typically all nodes should have the same version. During an upgrade, certain nodes may temporarily report different versions. In general, if a node is running a different services version than the active controller, it will be offline until the software update completes.

Configure the redundancy mode of a partition

To configure the redundancy mode of a partition, perform the following procedure:

Impact of procedure: Depending on the health of your system controllers, changing the setting may trigger a failover of the partition controllers.

  1. Log in to the CLI of the floating management IP address as the partition administrator.
  2. Enter the configuration mode terminal by entering the following command:

    config

  3. Change the partition redundancy mode using the following command syntax:

    system redundancy config mode <auto/prefer-1/prefer-2/active-controller>

    For example, to set the system redundancy state setting to prefer-1, enter the following command:

    system redundancy config mode prefer-1

    Note: By default, this setting is set to auto. For optimal performance, F5 recommends leaving this setting in its default value of auto.

  4. Save the change by entering the following command:

    commit

  5. Exit the configuration mode terminal by entering the following command:

    exit

Enable auto failback to the preferred controller of a partition

If the partition redundancy mode remains as auto, you do not have to enable the auto failback. If you configured the partition redundancy mode to a value other than auto and you want to enable auto failback to the preferred controller of a partition, perform the following procedure:

Impact of procedure: Depending on the health of your system controllers, changing the setting may trigger a failover of the partition controllers.

  1. Log in to the CLI of the floating management IP address as the partition administrator.
  2. Enter the configuration mode terminal by entering the following command:

    config

  3. Change the partition redundancy mode using the following command syntax:

    system redundancy config auto-failback <enabled/disabled>

    For example, to enable auto failback, enter the following command:

    system redundancy config auto-failback enabled

    Note: By default, this setting is set to disabled. If the partition redundancy mode remains as auto, there is no requirement to change this setting.

  4. If you have enabled the auto failback, you should also review the failback delay setting as appropriate. By default, the delay is set to 30 seconds. To change the delay, use the following command syntax:

    system redundancy config auto-failback failback-delay <value in seconds>

    For example, to change the delay to 40 seconds, enter the following command:

    system redundancy config auto-failback failback-delay 40

  5. Save the change by entering the following command:

    commit

  6. Exit the configuration mode terminal by entering the following command:

    exit

Manually trigger a failover of the controllers for a partition

To manually trigger a failover of the controllers for a partition in the CLI, perform the following procedure:

Impact of procedure: All SSH connections to the floating management IP address are terminated during failover. If you logged in to the active controller using SSH prior to triggering the failover, you will need to reestablish your SSH connection to the newly promoted active controller.

  1. Log in to the CLI of the floating management IP address as the partition administrator.
  2. Enter the configuration mode terminal by entering the following command:

    config

  3. Trigger the manual failover of the controllers by entering the following command:

    system redundancy go-standby

    Important: You can only use this command when the standby controller is available and healthy.

Determine if a failover occurred on the partition controllers

The system logs the HA event logs for the partition controllers in the /var/F5/partition<ID>/log/velos.log file. To determine if a failover occurred, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the CLI of the chassis floating management IP address as the chassis root user.
  2. To look for log messages related to role change logged by the partition-ha process, use the following command syntax:

    grep partition-ha /var/F5/partition<ID>/log/velos.log

    grep partition-ha /var/F5/partition2/log/velos.log

Determine if the partition configuration and files are replicated

The system logs the partition configuration and files replication event logs in the /var/F5/partition<ID>/log/partition_sync.log file. To determine if the replication for a specific file has occurred, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the CLI of the chassis floating management IP address as the chassis root user.
  2. Look for log messages related to configuration or file replication in the /var/F5/partition<ID>/log/partition_sync.log file using the following command syntax:

    cat /var/F5/partition<ID>/log/partition_sync.log

    For example, to look for these messages on partition2, enter the following command:

    cat /var/F5/partition2/log/partition_sync.log
