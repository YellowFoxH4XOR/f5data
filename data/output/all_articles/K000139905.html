Description

In BIG-IP versions later than v17.1.1, v16.1.4 and v15.1.10, the following message may appear in /var/log/tmm* under rare conditions:

notice HSB loopback corruption at offset <value>. tx: <value>, rx: <value>, len: <value>

This indicates that the HSB is experiencing data corruption (bit flip). For more information, refer to Bug ID 1211513 .

Environment

BIG-IP platforms with HSB chips. Refer to K70264409: BIG-IP platforms that contain HSB chips.

Cause

HSB bit flip

Recommended Actions

A reboot of the BIG-IP appliance is needed to resolve the issue.  After a reboot, the issue will be fixed and is unlikely to return.

You may also set the DB key tmm.hsb.loopbackvalidationErrthreshold to a non-zero value, so that the system reboots automatically in future when it detects HSB corruption.   

With vCMP considerations: 

  • HSB corruption can occur on either the vCMP host or the guest
  • The HSB is shared at the platform level
  • If HSB corruption occurs on a vCMP guest and triggers a reboot, only the guest will reboot
  • The underlying HSB issue persists on the host, and the problem will recur
  • The entire vCMP host needs to be rebooted to fully clear the HSB corruption

When the DB key tmm.hsb.loopbackvalidationErrthreshold is set to a value greater than 0 and the number of corrupt HSB loopback packets reaches this threshold, the system will:

  • Log the message: "Reached threshold count for corrupted HSB loopback packets"
  • Trigger a nic_failsafe event
  • Automatically reboot the system 

This automatic reboot mechanism helps ensure rapid recovery without manual intervention when HSB corruption is detected.

For vCMP systems, there is a db variable vcmp.guest.failsafe introduced in v15.0 (disabled, by default) can be used to reboot the host on HSB failure. The biggest downside that comes with enabling the vcmp.guest.failsafe db variable on the host is that upon detection of a guest's HSB failure, a reboot will bring down ALL of the host's guests along with it. It is important to keep this in mind before enabling the failsafe DB variable.

Note: The vcmp.guest.failsafe feature is disabled by default for good reason. When enabled, upon detection of any guest's HSB failure, the host reboot will bring down ALL of the host's guests simultaneously and non-gracefully whether they are affected or not.

Configuration:

Set the database variable to a non-zero value (recommended value depends on your tolerance for false positives, but typically 50-100):

tmsh modify sys db tmm.hsb.loopbackvalidationErrthreshold value <number>
tmsh save sys config

Configuration on the vCMP Host:

tmsh modify sys db vcmp.guest.failsafe value enable
tmsh modify sys db tmm.hsb.loopbackvalidationErrthreshold value <number>
tmsh save sys config

Configuration on the vCMP Guest:

tmsh modify sys db tmm.hsb.loopbackvalidationErrthreshold value <number>
tmsh save sys config

Additional Information

The bit flip is addressed with updated HSB firmware introduced in versions 21.0.0, 17.5.1, 17.1.3.1 (see ID891333).  The occurrence of HSB bit flip does not indicate a hardware defect, unless it happens on the same BIG-IP appliance repeatedly despite a reboot of the appliance.
