K000163689: TCP TIME_WAIT Accumulation When an Upstream Returns Connection: close

Type
Support Solution
Published
2026-10-13
Updated
2026-10-13
Applies to
  • NGINX Products
  • NGINX Plus
Source
https://my.f5.com/manage/s/article/K000163689

Description

NGINX Plus R37 can accumulate TCP TIME_WAIT connections when an HTTP/1.0 upstream consistently returns Connection: close. With Version R37 and above, NGINX is the active TCP closer when when an HTTP/1.0 upstream consistently returns Connection: close, which can exhaust source ports and disrupt traffic.

Environment

  • NGINX Plus R37.
  • HTTP/1.1 communication between NGINX and an upstream application.
  • Upstream keepalive disabled.
    • Upstream responses include:
      Connection: close
  • Linux-based system.

Cause

  • When an HTTP/1.1 client receives Connection: close, it must stop using the connection and close it after reading the response. NGINX therefore sends the first TCP FIN and becomes the active closer.
  • The resulting connections enter TIME_WAIT on the NGINX host. When the upstream repeatedly disables connection reuse, TIME_WAIT sockets can accumulate and consume available source ports. This can lead to connection failures and traffic disruption.
  • This behavior differs from earlier NGINX Plus releases in which the upstream could initiate the connection close.

Resolution

  1. Enable upstream keepalive if the application can reliably support persistent connections.
  2. If keepalive cannot be enabled, evaluate HTTP/1.0 for the NGINX-to-upstream connection, provided the application supports the required HTTP/1.0 behavior.
  3. Monitor the NGINX host for:
    • Growth in TCP TIME_WAIT connections.
    • Available source ports.
    • Connection failures.
    • Traffic disruption.
  4. Use packet captures, when necessary, to verify which endpoint sends the first TCP FIN.
  5. Confirm that the selected protocol and keepalive configuration are compatible with the upstream application.

Additional Information

  • The connection tear-down behavior is consistent with the HTTP/1.1 requirements described in RFC 9112. The endpoint that actively closes a TCP connection typically owns the resulting TIME_WAIT state.
  • HTTP/1.0 can prevent this specific accumulation pattern, but it should be treated as an application-dependent workaround rather than a universal replacement for HTTP/1.1.
