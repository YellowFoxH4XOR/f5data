Known Issue

Disabling a virtual server may not prevent a lower precedence virtual server from processing traffic.

This issue occurs when all of the following conditions are met:

  • You disable a port-specific host virtual server.
  • A lower precedence virtual server is configured to use the same virtual address.

In BIG-IP 9.4.0 and later versions, default settings do not allow a lower precedence virtual server to handle a request when a higher precedence virtual server is administratively disabled. This behavior is by design, and is controlled by the tm.continuematching db variable.

However, as a result of this issue, if you configure two virtual servers to use the same virtual address, disabling the higher precedence virtual server may not prevent traffic from matching the lower precedence virtual server. For example, consider the following configuration:

ltm virtual vs_http {
destination 10.10.10.10:http
disabled
ip-protocol tcp
mask 255.255.255.255
pool pool_http
profiles {
http { }
tcp { }
}
source 0.0.0.0/0
source-address-translation {
type automap
}
vs-index 2
}
ltm virtual vs_http_any {
destination 10.10.10.10:any
ip-protocol tcp
mask 255.255.255.255
pool pool_http_any
profiles {
tcp { }
}
source 0.0.0.0/0
source-address-translation {
type automap
}
translate-address disabled
translate-port disabled
vs-index 3
}

In this example, the more specific virtual server, vs_http, is administratively disabled. However, traffic destined to 10.10.10.10:80 may match the vs_http_any virtual server even though the tm.continuematching db variable is set to false.

Impact

The less specific virtual server processes traffic that should be rejected by the disabled virtual server.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • BIG-IP iHealth lists Heuristic H438559 on the Diagnostics > Identified > Medium screen.
  • The system sends requests to the wrong pool.
  • Application traffic fails or produces unexpected results.
