K000162272: How to use smbclient on APM

Type
Support Solution
Published
2026-07-16
Updated
2026-07-16
Applies to
  • BIG-IP
  • BIG-IP APM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000162272

Description

Remote users can not access network resources via encrypted SMB3 shares once a VPN tunnel is established.

In the tcpdump you can see back-end server sending a TCP/RST after receiving an encrypted SMB3 message from the client.

You can use 'smbclient' tool on APM to verify if the problem is on server side, from APM to back-end server.

Environment

  • BIG-IP deployed with APM
  • Computers using Edge Client to establish a VPN tunnel with APM
  • Users accessing network resources via encrypted SMB3 shares
  • Users authenticating to SMB shares via Kerberos

Cause

If your back-end server issues a TCP/RST immediately following an encrypted SMB3 request, maybe is caused by an intermediate network device that modifies or proxies SMB requests ("Negotiate Protocol" and "Session Setup" messages).

The client and server will generate mismatched cryptographic context that will make the server’s derived key to fail decrypting the SMB3 message sent by the client.

Recommended Actions

'smbclient' on BIG-IP is running v4.4.4 and negotiates AES_128_GCM. So you need to confirm that the server sharing the encrypted folder over SMB supports AES_128_GCM encryption cipher.

On Windows Servers you can use this command

Get-SmbServerConfiguration | Select-Object -Property EncryptionCiphers

create a 'smb.conf' file (ie. "/var/tmp/test-smb.conf") with this content

[global]
    client min protocol = SMB3
    client max protocol = SMB3
    client ipc max protocol = SMB3

    # Try client-side negotiation
    smb encrypt = desired

    # Enforce Kerberos globally for client connections in Samba 4.4
    kerberos method = secrets and keytab

    # Force SPNEGO to handle the Kerberos ticket negotiation
    client use spnego = yes

    # Disable older, less secure NTLM protocols entirely
    client ntlmv2 auth = no
    client lanman auth = no
    client plaintext auth = no

You can run a tcpdump before running Kerberos and 'smbclient' to match logs and traces

tcpdump -nni 0.0:nnnp -s0 -w /var/tmp/test.pcap port 445 or port 88 or icmp

On a different CLI, clear Kerberos cache with 'kdestroy' and obtain a kerberos TGT (Ticket-Granting Ticket) with 'kinit' for the user accessing the shared resource (ie. user1 in realm LAB.LAN)

kdestroy

kinit user1@LAB.LAN

Check with 'klist' which is the ticket cache and there is a Kerberos TGT for that user

klist

Ticket cache: KEYRING:persistent:0:0
Default principal: user1@LAB.LAN

Valid starting       Expires              Service principal
x                    x                    krbtgt/LAB.LAN@LAB.LAN

Use 'smbclient' to access the encrypted shared resource (ie. //dc.lab.lan/ShareEncrypted) with debug log level 10, the 'smb.conf' file you created and the kerberos cache.

The following 'smbclient' command will list the files inside that encrypted shared resource.

smbclient "//dc.lab.lan/ShareEncrypted" -s /var/tmp/test-smb.conf --port 445 -d 10 -k --use-krb5-ccache=KEYRING:persistent:0:0 -c 'ls'

Response should include 'encrypt SMB2 message' and 'decrypt SMB2 message' lines, along with the files stored in the shared resource (in this case only one file "abc.txt")

<...>
encrypt SMB2 message
decrypt SMB2 message
encrypt SMB2 message
decrypt SMB2 message
  .                                   D        0  
  ..                                DHS        0  
  abc.txt                             A        7  
encrypt SMB2 message
decrypt SMB2 message
encrypt SMB2 message
decrypt SMB2 message
encrypt SMB2 message
decrypt SMB2 message
encrypt SMB2 message
decrypt SMB2 message
encrypt SMB2 message
decrypt SMB2 message
<...>

Running 'klist' again will include now a service ticket to CIFS (Common Internet File System)

klist

Ticket cache: KEYRING:persistent:0:0
Default principal: user1@LAB.LAN

Valid starting       Expires              Service principal
x                    x                    cifs/dc.lab.lan@LAB.LAN
x                    x                    krbtgt/LAB.LAN@LAB.LAN
