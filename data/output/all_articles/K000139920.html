K000139920: Traffic disrupted on Active vCMP guest, after reboot secondary vCMP host

Type
Support Solution
Published
2024-06-05
Updated
2024-06-05
Applies to
  • BIG-IP
  • BIG-IP LTM: 15.1.6
Source
https://my.f5.com/manage/s/article/K000139920

Description

Traffic disrupted on vCMP guest environment when there is a reboot on a vCMP host configured with same MAC masquerade as a vCMP guest HA pair.

 

Environment

  • Pair of vCMP host units in standalone mode. 
  • Pair of vCMP guests in HA mode.
  • vCMP host tagging interfaces over a link aggregation.
  • Multiple VLANs associated with affected vCMP guest.
  • Same MAC Masquerade configured on vCMP guests pair and vCMP host. 

 

Cause

After a vCMP host resumes from a reboot there are specific ether type 0x23f5 packets sent by the tmm to the internal switch in order relearn the BIG-IP's VLAN MAC address, such packets can be forwarded to the upstream switches. So if the rebooted vCMP host is using same MAC masquerade as a vCMP guest pair this will cause MAC address being duplicated on the upstream switches and eventually in the non-rebooted vCMP host and where active vCMP guest reside.

 

Recommended Actions

The recommendation is not configure vCMP host with a MAC masquerade as its traffic group is not going to process any packet. The failover tasks are completed at the vCMP guests level.

  • As this configuration item is not available at the vCMP host GUI, next command can be executed to confirm if MAC masquerade is configured or not at the vCMP host, 
# tmsh list cm traffic-group
cm traffic-group traffic-group-1 {
    mac <MAC-masquerade>  # Same MAC as vCMP guest traffic-group
}
  • Use next command to remove the MAC masquerade from vCMP host configuration,
# tmsh modify cm traffic-group traffic-group-1 mac none
  • If vCMP host is a multi-blade platform the affectation could be persistent due asymmetric FDB entries caused by the VIPRION cluster distribution Optimized (default). In this case you can force the vCMP host to send GARP packets for a floating IP which will return FDB table to a consistent state, use next command to create a new floating IP address on the affected VLAN,
# tmsh create /net self <self IP name> address <IP address> vlan <vlan name> traffic-group traffic-group-1

Once service is restored you can remove the created floating IP using next command 

# tmsh delete /net self <self IP name>
