Description

This is by no means a 'comprehensive' article about HTTP/2. That would take a good size volume. The purpose here is to give an overview about what you will see in HTTP/2, some 'gotchas' with the BIG-IP, and ways to work with it.

HTTP/2 is not always easy to identify in traffic. It only shows up as a protocol in Wireshark when the capture is decrypted. It also functions differently having different "Frame Definitions" .

There are certain BIG-IP features that are not supported for a HTTP/2 full proxy deployment and its not compatible with NTLM protocols.

These characteristics, and others, bring about some differences you need to be aware of when capturing/troubleshooting HTTP/2 traffic on a BIG-IP.

Environment   
There are some considerations on the BIG-IP when a virtual server is configured to use HTTP/2 and/or when HTTP/2 traffic traverses the BIG-IP...

  • OneConnect, Hash and SSL session persistence types, and Connection mirroring in High Availability (HA) configurations are not compatible with HTTP/2 in a full-proxy deployment.
  • The tcpdump :p option (commonly referred to as the 'p' flag) will not capture serverside traffic when used.
  • To use HTTP/2 you must also enable the HTTP MRF Router setting for the virtual server for full proxy support.
  • ASM is not compatible with HTTP/2 + HTTP MRF Router prior to version 15.1.x.
  • SSL Orchestrator (SSLO) and SSL Forward Proxy added support for HTTP/2 with the TLS Application-Layer Protocol Negotiation (ALPN) extension in version 16.1.0
  • Full Proxy ability was not available prior to 14.1.x
  • The HTTP/2 protocol is not compatible with NTLM protocols
  • Chunked transfer encoding is not supported in HTTP/2, which provides its own mechanism for data streaming.
Along with the above points when dealing with HTTP/2 there are significant differences in what will be seen in the traffic of a decrypted capture.

HTTP/1.0 allowed only 1 current request at a time for a TCP connection. HTTP/1.1 added pipelining but it was only partially successful and had to deal with head-of-line blocking. Thus HTTP/1.0 and 1.1, many times, had to make many requests using multiple connections in order to achieve concurrency and effectively reduce latency.

Along with that HTTP header fields can often be repetitive and verbose. This can bring about needless network traffic and can cause the initial TCP congestion window to quickly fill.

HTTP/2 allows interleaving of request and response messages on the same connection and uses a more capable coding for HTTP header fields. HTTP/2 has a more effective means of prioritization of requests, letting more important requests complete more quickly.

All of this, and more, needs to be taken in to account when troubleshooting HTTP/2 traffic.


When reviewing traffic that is using HTTP/2 there are some indications it is in play. 


1) The first indication you may have run into HTTP/2 is when a capture is run and there is no serverside peer flows. For example you write a capture similar to this...

tcpdump -s0 -nni 0.0:nnnp host 192.168.1.1 -vw /var/tmp/capture.pcapng
 
In that capture is the 'p' flag. When the 'p' flag is used, and HTTP/2 is in play, there will be no peer flow on the serverside. To make it even odder when the packet data is reviewed and you look at the F5 Ethernet Trailer Protocol there is no serverside Peer ID:...

To add to this oddity, if the capture is not decrypted, you will have no indication when the capture is viewed in WIreshark that HTTP/2 is in play. This is because it is a Layer 7 protocol and when it is encrypted the protocol will show as whatever TLS version is being used.

2) On the other hand when you do have a decrypted capture you wiil see packet information with syntax like "GOAWAY", "PING", "RST_STREAM", and others. So you ask yourself "Now what and where is the stuff I am used too?".
 
In HTTP/1.x and prior you dealt with certain syntax. HTTP/2 is an "alternative to, but does not obsolete the HTTP/1.1 message syntax". As a matter of fact HTTP's current semantics remain unchanged. Basically what HTTP/2 does is add to it. Because of this you will see the afore mentioned items and more.

One of the first things you will come across are the 'Frames'. Some of what you see and a brief definition can be seen in the following table...
 
OVERVIEW of FRAME DEFINITIONS
DATADATA frames (type=0x0) convey arbitrary, variable-length sequences of octets associated with a stream. (Section 6.1)
HEADERSThe HEADERS frame (type=0x1) is used to open a stream (Section 5.1), and additionally carries a header block fragment. (Section 6.2)

Recommended Actions
1) First thing needed is to understand that HTTP/2 inherits the scheme design of it predecessors. There is no http2 or http2s.

While keeping the semantics as is, HTTP/2 introduces new “syntax”, featuring:
  • connection preface,
  • header compression,
  • binary-encoded frames, and
  • streams.
2) The Connection Preface is a simple 24-byte plain text ASCII code introduced after the TLS handshake. In Wireshark it is referred to as "Magic".
 
HyperText Transfer Protocol 2
    Stream: Magic
        Magic: PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n

At this point after the server receives the "Magic" it will expect to receive and send messages using the HTTP/2 protocol.

3) Next is the Header Compression. There is a fundamental change here between HTTP/2 and earlier versions. In the earlier versions we saw:accept-encoding: gzip, deflate, br.
 
With HTTP/2 a new compression algorithm is introduced...HPACK, which is designed for header compression. HPACK is a stateful algorithm. It asks the browser and the server to maintain a read-only table.
  • There are 3 key features here:
    • The pseudo-header fields start with a : .
    • HTTP/2 pseudo-headers are required to be lower cases.
    • All data in headers are now in key-value pairs.
For example in HTTP/1.1 a typical status line would look like HTTP/1.1 200 OK. However with HTTP/2 it will look like :status: 200 using the pseudo header :status. It removes the version and the status text.

4) You will also encounter the Binary-Encoded Frames. HTTP/2 uses the binary format for its messages instead of ASCII codes, making messages computer friendly. HTTP/2 thus handles a message differently.
  • The message is broken up into pieces. Each of them is a frame.
    • HEADERS Frame is for header data
    • DATA Frame is for body data
 

 
  • The structure breaks down as such;
    • A Length indicates the length of the frame. A frame is usually less than 2^14 bits but can be up to 2^24 bits. Therefore, its size usually is less than 16K.
    • A Type shows the frame's type, such as data frames (HEADERS frame, DATA frame) and flow-control frames (SETTINGS frame, PRIORITY frame, etc.). HTTP/2 defines 10 types, but it can be up to 2^8 types. You can define custom types when needed.
    • A Flag is for simple flow control, such as END_HEADERS indicating the end of the headers data.
    • The Data is the frame payload.
Example:
Stream: HEADERS, Stream ID: 1, Length 196, 200 OK
    Length: 196
    Type: HEADERS (1)
		Flags: 0x04, End Headers
		    00.0 ..0. = Unused: 0x00
		    ..0. .... = Priority: False
		    .... 0... = Padded: False
		    .... .1.. = End Headers: True
		    .... ...0 = End Stream: False
    0... .... .... .... .... .... .... .... = Reserved: 0x0
    .000 0000 0000 0000 0000 0000 0000 0001 = Stream Identifier: 1    .....
    .....
  • The length shows that the frame's size is 196 bytes.
  • The type is 1, meaning is a HEADERS frame.
  • The flags are 0x04 (End Headers), meaning this is the last frame of all headers frames.
  • The stream Identifier is 1, meaning this response is in the stream[1].
 
  • Streams are how HTTP/2 handles delivering frames. After breaking messages into pieces, a browser sends all frames to the server.  With HTTP/2 frames can arrive, on the receiving end, at different times. A data frame can arrive earlier than its corresponding headers frame. So the question is how are the frames reassembled?
When breaking up the message, the browser marks corresponding frames with a stream ID (the Stream Identifier) and the order. This allows for the frames on the receiving end to be reassembled in the proper order. Something to consider is that the corresponding request and response are sharing the same stream ID. With that the browser can match requests and responses.

HTTP/2 allows for multiple HTTP conversations simultaneously. Thus achieving multiplexing. In this way, each stream is decoupled, and has almost no head-of-the-line blocking issues.
  • Part of this is the Stream State. In the frame is a  Flag and for changing the stream state.
    • These 5 states are:
      • Idle: the stream has not yet been created.
      • Open: the stream is created and running.
      • Half-Close: The browser has completed sending requests and waiting for responses.
      • Closed: The stream ended.
      • Reserved: the stream is reversed for server-push messages.
When the browser send the HEADERS frame, a stream is created and a stream ID is assigned.
 
The stream then starts its Open state. Once that has happened both ends can send and receive data.
Once there are no more requests waiting the browser sends an frame with the END_STREAM flag. This informs the server that the stream is about to close.
 
The server then responds with its last message, an END-STREAM of it own and the stream is closed.
 
HTTP/2 does not reuse a stream ID. Making the lifecycle of a stream equivalent to a response-request message in HTTP/1.x.
 
However, something to be aware of is that a new id is assigned until it reaches 2³¹. When that last id is consumed the browser will send a GOAWAY frame to initialize a new TCP connection. When the happens the stream ID is reset.
 
Of note here are a couple of other things..
      • The browser and the server can both initialize a stream independently.
      • The stream ID increments in an increasing order. Odd numbers for the browser and even numbers for the server. The norm here would often be that you will see the odd numbers more often.
      • Streams can be prioritized.
      • HTTP/2 does not use Connection: keep-alive as it assumes the connection is persistent.
5) When doing a capture that will involve HTTP/2 the capture will need to include the clientside and serverside IPs.
For example if you have a virtual server with the websocket of 192.168.1.1:443 and there are 3 pool members using 10.1.1.1, 10.1.1.2, 10.1.1.3 all on port 80 it could look something like this...
tcpdump -s0 -nni 0.0:nnn '(host 192.168.1.1 and port 443)' or '((host 10.1.1.1 or host 10.1.1.2 or host 10.1.1.3) and port 80)' -vw /var/tmp/send_to_file.pcapng

If there are a large number of pool members you can also set to capture on a network or target a set of specific pool members.
