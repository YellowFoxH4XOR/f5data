Known Issue

This is the result of a known issue. When a pool member configured with a connection limit reaches that limit, it is no longer available to receive new connections, which reduces the number of available pool members. The active_member iRule command is intended to return the number of members available to accept new connections. However, the value returned by the active_members command includes all pool members whose status is up, even those that have become ineligible for load balancing after reaching the configured connection limit.

The active_members command is typically intended to condition an alternate response or a redirect when some or all of the servers are unavailable, as in the following example:

rule AltResponseWhenNoActiveMembers {
when HTTP_REQUEST {
if { [active_members testpool] < 1 } {
HTTP::respond 200 content "<html>…</html>"
} else {
...
}
}
}

If the servers are unavailable because they have reached their connection limits, the intended logic will fail, and the BIG-IP may continue to send traffic to servers that have reached their configured connection limits, but are still responding timely to application health monitor traffic.

F5 Product Development tracked this issue as CR85057 and CR111235 and it was fixed in BIG-IP versions 9.3.1, 9.4.7, and 10.0.1. For information about upgrading, refer to the BIG-IP LTM or ASM Release Notes.

Workaround

To avoid timed out or otherwise failed requests sent to overloaded servers, you may work around this issue by using the LB_FAILED iRule event to execute the alternate response if the BIG-IP is unable to establish a new connection with a pool member.

For example:

rule AltResponseWhenLBFails {
when HTTP_REQUEST {
...
}
when LB_FAILED {
HTTP::respond 200 content "<html>…</html>"
}
}
