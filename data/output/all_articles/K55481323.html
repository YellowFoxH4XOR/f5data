Description

BIG-IP VEs may behave as if CPU limited even though utilisation is not high. Strange performance problems may occur. For example, less than expected TCP throughput.

The VE may also log the following messages in /var/log/ltm:
01010029:5: Clock advanced by <ticks> ticks

Environment

  • BIG-IP VE
  • VMWare ESX
Cause

VMWare ESX has a per-guest setting called "Minimum CPU MHz" which can be reserved for that guest, which is understandably causing confusion among some admins running BIG-IP VE on ESX.

BIG-IP VE requires real-time access to the CPU since so many of its functions are very sensitive to latency - eg. even an extra 100ms of latency added to client requests would be unacceptable to most admins, and if the box operations are 'paused' for over 3 seconds it will cause a failover in most HA deployments.

Due to this, BIG-IP VE does not support being "paused" for any length of time - this is also why BIG-IP VE doesn't currently support the taking of live "snapshots" from the hypervisor, because the VM's operations are paused by the hypervisor while a snapshot is being generated.

The CPU MHz reservation setting on any hypervisor (eg. VMware ESX) should be set to 'maximum' for BIG-IP VEs, effectively dedicating a core to each BIG-IP virtual core, as "sharing" a CPU always has a performance hit and it could affect the box's performance badly. The exact MHz you require per BIG-IP core depends on your traffic, but even for a less utilised box at least a 2GHz dedicated physical core per BIG-IP virtual core should be used, since virtualisation generally results in at least a small performance hit compared to having direct access to a physical CPU.

Even if a much faster CPU (eg. 4GHz for the above example where only 2GHz is required) is in use, since it is never clear how a hypervisor's CPU manager is going to allocates the MHz in the "CPU MHz reservation" setting, we recommend setting the MHz value to "maximum" for every CPU core allocated to a BIG-IP VE. This is because a hypervisor's CPU manager is certainly not going to perform a CPU context switch at every cycle, so if you have a 4GHz physical core with 2 VMs running at 2GHz virtual each, it is certainly not going to give every second CPU cycle to a different VM since that would not get any work done due to the huge overhead of attempting a context switch every clock cycle. Alternatively, If it split it on a per-second basis, and gave half a second of processing time to one VM, and then blocked the VM for the second half of the second, every second - that would not be supported for BIP-IP VE either, because it would mean 500ms delay for half the traffic sent to the BIG-IP, and would wreak havoc with our TCP flow control, among other things.

Based on all the above, the reason we don't recommend setting the specific MHz reservation to anything other than "Maximum" (even if you had a 4GHz CPU and only needed 2GHz for your traffic) is so that we don't fall foul of whatever way the hypervisor decides to perform context switching on the physical CPUs. Any context switching could result in strange performance problems that could be hard to detect or troubleshoot.

Recommended Actions

Set CPU MHz reservation setting on any hypervisor (eg. VMware ESX) to  Number of Cores * Per Physical CPU capacity.
For example:
2 Cores for this VM and Per  Processor Frequency is 2300 MHz

Reservation :4600Mhz (2*2300)
