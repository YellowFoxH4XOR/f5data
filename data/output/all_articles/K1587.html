Note: This solution does not describe how to configure a client-to-network or a network-to-network SSL-based VPN. That functionality is included in the F5 Networks FirePass products.

To allow non-SSL clients to access SSL-enabled application on a well-known port <server_port> for a predefined server IP address <server_ip>:

  • Configure the SSL Proxy for the specified virtual server's IP address <proxy_address> and port <proxy_port>
  • Enable encryption on the server side
  • Disable encryption on the client side

To do this, perform the following steps:

  1. Create a pool with a single member <server_ip>:<server_port>.
  2. Create a loopback virtual server using the newly created pool.
  3. Create a "server SSL" type SSL proxy on the IP address of the <proxy_ip> and TCP port <proxy_port> using the newly created loopback virtual server as its destination.

This configuration allows non-SSL clients to connect to address <proxy_ip> and TCP port <proxy_port> and have their communication SSL encrypted and transparently proxied to the target server.

Note: Refer to the BIG-IP Reference Guide for details about how to configure pools, virtual servers, and proxies.

Following is an example of the relevant portion of the BIG-IP /config/bigip.conf file for this configuration.

In this example, non-SSL clients are allowed access to the SSL server with IP address 169.254.254.17 and port 443 (HTTPS), through the proxy address 10.66.66.169 and port 80. The proxy would encrypt their communication and send it to server 169.254.254.17 on port 443.

pool server-https {
member 169.254.254.17:https
}
virtual 127.1.1.17:443 unit 1 {
use pool server-https
}
proxy 10.66.66.169:80 unit 1 {
target virtual 127.1.1.17:443
serverssl enable
serverssl server cert ignore
}

Other considerations:

  • If you are running BIG-IP version 4.6 or later, verify that the Enable ServerSSL checkbox in the Pool Properties page is unchecked.
  • The virtual server used in the proxy configuration cannot be a forwarding or wildcard virtual server.
  • You can use a SNAT to hide the client addresses in the encrypted connection.
  • You can use this procedure to allow access to any service using any fully encapsulated application protocol that uses a common fixed (rather than dynamically negotiated) TCP port and IP address of a fixed target server (each proxy can provide a connection to only one target server).
