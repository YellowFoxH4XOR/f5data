What Happened?

  • Why do src_site (source site) and dst_site (destination site) not match for some HTTP requests?
  • This inefficient scenario could be introducing latency in your application flow.

Environment

  • XC Console
  • Load Balancer
  • Origin Pool
  • XC network
  • Regional Edge (RE)
  • Customer Edge (RE)

Resolution/Answer

Let's first define src_site (source site) and dst_site (destination site) as found in HTTP request logs (a.k.a API Access logs) and security event logs:

  • src_site: This is the F5 XC site (RE or CE) which receives the request from the client.
  • dst_site: XC site (RE or CE) which is used to send the traffic to the endpoint / origin server.

Typically, src_site and dst_site will match for a given request. For example, if a client located in Washington, USA makes an HTTP request to a domain hosted in XC and ingresses to XC network in Seattle, RE (src_site: wes-sea), then that request will usually be sent to the origin server from XC Seattle RE (dst_site: wes-sea). This is most efficient. However, there are at least two possible reasons why src_site and dst_site won't match for a given request:

  1. If health checks are failing from the pertinent XC RE (wes-sea in our previous example) to the pertinent origin server, then XC will not send traffic to the origin server from that regional edge. 
  2. If Origin Pool setting Endpoint Selection is set to All Endpoints, then XC will not have a preference to use the src_site as the dst_site. Instead, the default setting Endpoint Selection: Local Endpoints Preferred should be used. With this setting, XC will try to match src_site and dst_site. If they don't match in that scenario, it's typically because of reason number 1 above.
