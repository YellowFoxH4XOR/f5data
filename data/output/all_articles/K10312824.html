Description

The Content-Security-Policy header is an HTTP response header set by a web server and is an instruction to the requesting browser about what resources it should trust to be executed or rendered.

Environment

  • Any modern standards-compliant web browser (e.g., Chrome, Edge, Firefox etc)

Cause

None

Recommended Actions

None

Additional Information

The Content-Security-Policy header (moving forward, CSP or CSP header) is commonly used by a web application to dictate what resources content the client browser should allow to be executed or rendered in the context of the current page, for example:

  • To restrict URLs in the HTML <base> element
  • To restrict URLs for workers or embedded frame contents
  • To limit the origins for WebSockets/XHR/EventSource connections
  • To limit what fonts may be downloaded to render the page
  • To limit where form content may be submitted to
  • To restrict what sources can embed the current page
  • To define what servers may be contacted to download images, video, audio, plugin content
  • To limit what kinds of plugins the page may launch
  • To force the browser to switch to HTTPS rather than HTTP using upgrade-insecure-requests

You will most commonly see questions relating to using the CSP header to restrict the execution of Javascript components of webpages, e.g., the CSP script-src policy:

Content-Security-Policy: script-src 'self' https://js.example.com

The above policy informs the browser that it should only execute Javascript that is downloaded from either self (that is, the same server as the current page was requested from, respecting the same-origin policy) or https://js.example.com. Setting a restrictive policy like this limits the opportunity for Cross Site Scripting (XSS) attacks by preventing the browser from executing untrusted Javascript injected into the page and/or from a malicious third-party website.
Note: For additional information regarding the HTTP Content Security Policy response header refer to: Content Security Policy Reference.

Webpages commonly contained in-line Javascript (that is, Javascript contained in the HTML of the page itself, rather than requested from a separate source). A mechanism was be provided to control this as well. Apart from the self directive, shown above, there are three additional supported keywords:

  • none which, as the name suggests, bans the policy content type entirely
  • unsafe-inline which allows inline JavaScript
  • unsafe-eval which allows functions like eval to programmatically construct JavaScript

It should be noted that inline JavaScript on a publicly available web application is considered harmful and dangerous. If you allow inline scripts then the browser has no way to determine if the script it is executing was provided by the server, or maliciously injected into the page by a Cross Site Scripting attack, Man-in-the-Middle or Man-in-the-Browser attack and it will execute innocent and malicious code alike.

It is possible to tag each portion of legitimate inline code with a cryptographic number used once or a hash, and then list these numbers and/or hashes in the CSP header however this is strongly discouraged in most environments as ongoing maintenance can be extremely problematic, especially with hashes since the hash must be recalculated and updated in both the page and header if the page content changes.
