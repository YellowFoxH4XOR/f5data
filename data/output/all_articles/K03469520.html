Known Issue

Using a transaction to update pool members resets the monitor status.

TMOS Shell

For this issue to occur when you're using TMOS Shell (tmsh), you do one of the following:

  • Use the cli transaction command to execute a series of tmsh commands that delete and recreate pool members
  • Use the replace-all-with command to modify pool members

iControl REST

For this issue to occur when you're using iControl representational state transfer (REST), you use the PUT method to update pool members, and the monitor status resets. When you do so, iControl does not modify the members. Instead, it removes and recreates them with the specified attributes, and uses system defaults for unspecified attributes.

Both approaches cause the monitor status to reset to unchecked for the newly created pool members. When you apply health monitors to pool members, the status eventually transitions, based on health checks to up or down.

This issue occurs when one or more of the following conditions is met:

  • You use cli transaction or replace-all-with to modify pool members with tmsh.
  • You use the PUT method for an iControl REST call to update pool members.

Impact

The system loses the current status of pool members, which must be determined again through subsequent health monitor checks.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • The system logs messages to the /var/log/ltm file similar to the follow examples:

    notice mcpd[5195]: 01070638:5: Pool /Common/example_http_pool member /Common/example_node:80 monitor status unchecked. [  ]  [ was up for 0hr:4mins:36sec ]
    notice mcpd[5195]: 010719e8:5: Virtual Address /Common/172.16.1.1 monitor status changed from UP to UNCHECKED.
    notice mcpd[5195]: 01070727:5: Pool /Common/example_http_pool member /Common/example_node:80 monitor status up. [ /Common/http: up ]  [ was unchecked for 0hr:0mins:5sec ]
    notice mcpd[5195]: 010719e8:5: Virtual Address /Common/172.16.1.1 monitor status changed from UNCHECKED to UP.

Workaround

To work around this issue, you can individually modify members of a pool and do the following:

  • When using tmsh, avoid using cli transaction or replace-all-with.
  • When using iControl REST, use the PATCH method.

To do so, perform one of the following procedures:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  • Modify only a specific member, and the monitor status persists based on its previous state. The following tmsh syntax changes the status of an individual member:

    tmsh modify ltm pool <pool name> members modify { <node name>:<node port> { session user-disabled state user-down }}

    For example, the following command disables pool member example_node:80:

    tmsh modify ltm pool example_http_pool members modify { example_node:80 { session user-disabled state user-down }}

  • When you use the PATCH method on individual pool members, it modifies only that specific member, and the monitor status persists based on its previous state. The following iControl REST command syntax changes the status of an individual member:

    curl -sk --user <user:password> -X PATCH -H "Content-type: application/json" -d '{"session":"<session status>", "state":"<health status>"}' https://<BIG-IP system IP Address>/mgmt/tm/ltm/pool/~Common~<pool name>/members/~Common~<node name>:<node port>

    For example, the following command disables pool member example_node:80:

    curl -sk --user admin:admin -X PATCH -H "Content-type: application/json" -d '{"session":"user-disabled", "state":"user-down"}' https://192.168.1.1/mgmt/tm/ltm/pool/~Common~example_http_pool/members/~Common~example_node:80
