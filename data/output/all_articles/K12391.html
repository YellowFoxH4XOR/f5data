Known Issue

This is the result of a known issue. When a client negotiates a Secure Sockets Layer (SSL) connection with a virtual server on the BIG-IP system, the Traffic Management Microkernel (TMM) reorders the cipher suite contained in the Client Hello message based on the Ciphers option in the Client SSL profile; the resulting list is sorted from the strongest cipher to the weakest cipher. If the top cipher in the reordered list is a COMPAT cipher, and if the Client SSL profile also allows the use of COMPAT ciphers, TMM chooses the cipher for the SSL connection based on the client's cipher preference. This behavior is incorrect, because the BIG-IP system should always operate in server cipher preference mode, which chooses the cipher based on the preference expressed in the Client SSL profile.

Note: For more information about the expected behavior, refer to K12390: The 'Cipher server preference' option in a Client SSL profile has no effect.

For example:

  • A virtual server on the BIG-IP system is configured with a Client SSL profile that uses the following Ciphers option:

    AES256-SHA:AES+HIGH+EDH:AES+HIGH:AES+EDH:AES+MEDIUM:RC4+SHA:EDH+SHA:DH+SHA:3DES:RC4-MD5:DES+SHA:+LOW:EXPORT:+EXPORT56:+EXPORT40:!ADH:!SSLv2

  • An attempt to connect to the aforementioned virtual server is made from a client system using the openssl utility. The following command, which specifies the ciphers that the client is willing to use, is run on the client system:

    openssl s_client -connect 10.0.0.100:443 -cipher 'EXP-RC2-CBC-MD5:DHE-RSA-AES128-SHA:EXP-EDH-RSA-DES-CBC-SHA'

  • Based on the above settings, the BIG-IP system incorrectly chooses the EXP-RC2-CBC-MD5 cipher for the SSL connection. The correct behavior is for the BIG-IP system to choose the DHE-RSA-AES128-SHA cipher.

F5 Product Development tracked this issue as ID 340274 and it was fixed in BIG-IP 10.2.2.
