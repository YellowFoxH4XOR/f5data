K000160451: Intermittent 503 Errors and Health Check Failures Due to SNAT/ARP Issues on F5 Distributed Cloud Customer Edge (CE) Clusters

Applies to

Source

Description

Intermittent 503 errors with the log message upstream_reset_before_response_started{connection_failure} were observed on an F5 Distributed Cloud HTTP Load Balancer. The errors occurred specifically when health checks were performed from one Customer Edge (CE) cluster, while another cluster functioned normally. The issue resulted in health check failures, causing the application to be marked as unhealthy. The problem was isolated to a single SNAT IP within the SNAT pool, which was found to resolve to an unexpected MAC address, causing Layer 4 connection failures.

Environment

  • Product: F5 Distributed Cloud
  • Features: HTTP Load Balancer, Origin Pools, Health Checks, SNAT Pools
  • Topology:
    • Two CE clusters for redundancy pointing to the same Origin
    • SNAT pool with multiple IPs per CE cluster
  • Health check configuration (example):
    • Timeout: 3 seconds
    • Interval: 15 seconds
    • Unhealthy Threshold: 3
    • Healthy Threshold: 3
    • Jitter Percent: 30
  • Recent actions:
    • SNAT pool IPs were modified (removal and re-addition)
    • CE nodes were rebooted and upgraded to the latest OS and software versions

Cause

The root cause was an incorrect ARP entry for a SNAT IP on one CE node, causing it to resolve to the MAC address of a different CE node. This resulted in failed Layer 4 (TCP/TLS) connections to the origin server, leading to intermittent 503 errors and health check failures. The issue was traced to a stuck or desynchronized dataplane state on the CE, not a configuration or network problem. Using the same SNAT pool across multiple endpoints can also lead to object convergence issues.

Answer/Recommended Actions

  1. Validate SNAT Pool and ARP Entries:
    • After adding or modifying SNAT IPs, verify ARP resolution for each SNAT IP from the upstream switch or firewall.
    • Ensure the MAC address matches the intended CE node.
  2. Troubleshooting Steps:
    • Remove the affected SNAT IP from the origin pool configuration if it is associated with an incorrect MAC address.
    • Monitor for recurrence of 503 errors and health check failures.
    • If the issue persists, collect debug files and packet captures (PCAPs) from the CE and origin.
  3. Node Maintenance:
    • Reboot CE nodes one by one, starting with the node showing no traffic or abnormal behavior.
    • Upgrade CE nodes to the latest OS and software versions to benefit from recent ARP/VIP advertisement fixes.
  4. Health Check Configuration:
    • Avoid overly aggressive health check settings. Recommended values:
      • Interval: 20 seconds (range: 15–60 seconds)
      • Timeout: 5 seconds (range: 3–10 seconds)
      • Unhealthy Threshold: 2 or higher
      • Healthy Threshold: 4 or higher (should be greater than unhealthy threshold)
    • Use HTTP health checks for application-level validation and TCP checks for basic liveness.
    • Choose a stable endpoint that returns 200 OK for health checks.
  5. Best Practices:
    • Do not share the same SNAT pool across multiple endpoints or origin pools.
    • After changes, monitor backend load and health check behavior.
    • Regularly test failover and recovery scenarios.
  6. If Issue Recurs:
    • Collect and review ARP tables, debug logs, and PCAPs.
    • Engage F5 Support for further analysis and root cause investigation.

Additional Information

  • The issue may reoccur if a new SNAT IP is added back without addressing the underlying dataplane condition.
  • Keeping CE software up to date is critical, as several ARP/VIP advertisement bugs have been fixed in recent releases.
  • Using the same SNAT pool for multiple endpoints is not supported and can cause object convergence issues.
  • Monitoring ARP table consistency and CE dataplane health is recommended after any SNAT pool changes.
