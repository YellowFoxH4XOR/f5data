Description

Intermittent packet loss and latency may occur on BIG-IP LTM systems running as F5OS tenants, when peer device has a MAC address which is just for receiving traffic but not used for sending traffic to F5. This is particularly common in environments where VRRP, HSRP, Arista IP Anycast, or other virtual-MAC redundancy protocols are enabled.

How it works:

  • BIG-IP learns the gateway MAC address via ARP — the virtual VRRP MAC is returned
  • BIG-IP uses this virtual MAC as the destination MAC for all egress traffic
  • The peer device uses its physical/system MAC as the source MAC for all traffic it sends back to F5
  • The virtual VRRP MAC is never used as a source MAC by the peer (except for ARP responses). As a result, the F5OS FDB (Forwarding Database) entry for the virtual VRRP MAC is never refreshed by regular business traffic. When the entry expires, packet loss occurs until the MAC is re-learned via ARP.

When you run into this issue, the following symptoms may be observed:

  • Intermittent TCP retransmissions and delayed application traffic
  • Periodic packet loss burst approximately every 5 minutes, correlating with the FDB aging interval
  • Intermittently missing ICMP replies in ping tests
  • Application connection accumulation or timeouts around gateway ARP refresh time
  • Slow file transfers (for example, SCP) on specific VLANs while other VLANs on the same LAG work normally
  • No physical interface errors/drops or physical link issues observed

Environment

  • Platform:
    • rSeries: R5000 (r5600/r5800/r5900), R10000 (r10600 / r10800 / r10900, R12000)
    • VELOS platform (all blade types)
  • Protocol: VRRP, HSRP, Arista IP Anycast, or any virtual MAC redundancy technology, where the virtual MAC is used only for receiving but not for sending
  • F5OS Version: F5OS-A 1.5.x, 1.7.x, 1.8.x; F5OS-C 1.6.x, 1.8.x
  • BIG-IP Tenant Version: 17.1.x, 17.5.x, and other tenant versions

Cause

F5OS does not dynamically learn the VRRP virtual MAC address from regular business traffic when the peer device uses its physical MAC as source for egress. As a result:

  • The business traffic does not update or refresh the dynamic FDB entry for the virtual VRRP virtual MAC.
  • When this entry expires (default timeout: 5 minutes), new packets destined for that MAC are sent to the DLF queue.
  • If no ARP request/response occurs to trigger relearning before DLF queue fills, packet loss occurs at FPGA level.

The detailed issue procedure is as follows:

  1. FDB entry created: BIG-IP issues an ARP request; the VRRP device responds with the virtual MAC, creating a dynamic FDB entry in F5OS.
  2. FDB entry not regularly refreshed: All inbound business traffic from the peer uses the physical MAC as source — the virtual MAC FDB entry is never refreshed by production traffic.
  3. FDB entry expires: After the default 5-minute (300-second) timeout, the virtual VRRP MAC entry is removed from the FDB table.
  4. Packet loss occurs: Egress traffic destined to the expired virtual MAC cannot be forwarded normally, causing packet drops until the MAC is re-learned.

Recommended Actions

  1. Confirm this is an FDB aging issue

    Check for elevated DLF packet counts. A high and increasing rx_dlf counter in the output indicates the FDB aging issue is active.

    F5OS-A (rSeries):

    docker exec -it system_fpga tmctl -d blade -w 200 rbcast_pkt_stat

    F5OS-C (VELOS) — run on each affected partition blade:

    ssh blade-1
docker exec -it partition_fpga tmctl -d blade -w 200 rbcast_pkt_stat

    Example output:

    name         connected rx_pkts   rx_bytes  rx_bytes_copied  ...  rx_dlf   rx_bcast
    ------------ --------- -------   --------  ---------------  ...  ------   --------
    SwRbcaster-1         1 1142650   ...                            1142189      461
  2. Confirm the affected MAC is aging out

    Regularly check using the commands below.

    F5OS-A (rSeries):

    docker exec -it system_fpga tmctl -d blade -w 200 nse_l2

    F5OS-C (VELOS):

    docker exec -it partition_fpga tmctl -d blade -w 200 nse_l2

    Via F5OS admin CLI:

    show fdb | tab

    Look for the virtual gateway MAC entry. If it is absent from the table, or if its age value is low and keeps decreasing, the entry is aging out. Only dynamic FDB entries are subject to aging; static entries are not.

  3. Verify via packet capture

    Confirm that the virtual MAC never appears as a source MAC in regular inbound traffic — only in ARP replies:

    tcpdump -s0 -nni 0.0:nnn 'ether src '

Workaround/Solution:

You can use any one of the following solutions to fix this issue.

Impact of workaround: Adding or removing static FDB entries does not disrupt ongoing business traffic. Changes to ARP timeout or health monitors apply only to the BIG-IP tenant and do not require maintenance windows.

Option 1: Add a static FDB entry for the virtual VRRP MAC (Recommended)

Prevent expiration by configuring a static entry for the relevant virtual VRRP virtual MAC address on F5OS:

appliance-1(config)# fdb mac-table entries entry tag_type_vid interface interface-ref config interface 
appliance-1(config)# commit

For LAG interfaces, specify the LAG name.

Remove static entry if needed:

appliance-1(config)# no fdb mac-table entries entry  
appliance-1(config)# commit

Option 2: Lower ARP timeout on the tenant

Configure the BIG-IP tenant to send ARP requests before the F5OS FDB entry expires (default: 300 seconds).

tmsh modify sys db arp.timeout value 250
tmsh save sys config

Option 3: Configure upstream router to use virtual VRRP MAC as source

Configure your upstream router's VRRP implementation to use its virtual VRRP MAC as both source and destination in outgoing frames. This allows dynamic learning by normal traffic. This is the most permanent solution but requires changes on the peer network device.

Option 4: Reduce GARP interval on upstream device

If the peer device sends periodic GARP or VRRP advertisements, reduce the advertisement interval to well below the F5OS FDB aging timer (300 seconds). This ensures the FDB entry is refreshed before it expires.

Additional Information

Additional scenarios where this can occur:

  • Selective VLAN impact: On the same LAG, only VLANs where the gateway virtual MAC is never refreshed by inbound traffic are affected. VLANs where the peer sends traffic using the virtual MAC as source are not affected.
  • rSeries R10000/R12000 (Dual-FPGA platforms): These platforms have 2 FPGAs handling different port ranges. When a LACP trunk spans both FPGAs, FDB aging may occur even with inbound traffic, because aging events are only processed by the FPGA that originally learned the entry.
  • VELOS Multi-Blade: On multi-blade VELOS, FDB aging is managed by the "owner" blade (the blade that first learned the MAC). Traffic arriving on a non-owner blade does not refresh the aging timer on the owner blade. This can compound the issue in LACP configurations spanning multiple blades.
  • Static ARP entries: A static ARP entry configured on the BIG-IP tenant does not automatically create or refresh an FDB entry on F5OS. This affects clone pool and SSLO service chain scenarios where traffic is sent to a MAC address that never generates inbound traffic.
