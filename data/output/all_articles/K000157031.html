K000157031: UDP Virtual server is not distributing correctly traffic across pool members when datagram-load-balancing is enabled in the UDP profile

Type
Support Solution
Published

Updated

Applies to

  • BIG-IP LTM: 17.0.0, 17.1.0, 17.0.X, 21.X.X, 17.X.X, 21.0.X, 21.0.0, 17.5.X, 17.5.1, 17.5.0, 17.1.X, 17.1.3, 17.1.2, 17.1.1
Source

Description

A BIG-IP LTM UDP Virtual Server (VIP) configured for syslog traffic may fail to distribute traffic evenly across pool members. Even when the Round Robin load balancing method is selected and datagram-load-balancing is enabled in the UDP profile, most or all syslog traffic can be sent to a single pool member. Packet captures may show that syslog messages are not forwarded to all pool members as expected, and sometimes only non-syslog traffic (such as ICMP/ping) is observed. Enabling datagram-load-balancing can also result in log outages or instability in logging services.

Environment

  • Load Balancing Method: Round Robin
  • UDP Profile with datagram-load-balancing enabled

Cause

The issue arises from how BIG-IP manages UDP connection flows when datagram-load-balancing is enabled. If existing connections are not cleared after enabling this feature, traffic may remain sticky to one pool member due to connection persistence. Additionally, configuring the same IP address for both local syslog server destination (for BIG-IP's own logs) and remote logging VIP can cause routing confusion, resulting in logs not reaching all intended pool members or causing outages when datagram-load-balancing is active.

Recommended Actions

1- Enable Datagram Load Balancing Correctly

In the relevant UDP profile, enable datagram-load-balancing and set idle-timeout "immediate" per-packet load balancing.

2-Clear Existing Connections

After making changes, clear all existing connections so new UDP packets are distributed individually:

# tmsh delete sys connection all

Or for a specific virtual server:

# tmsh delete sys connection cs-server-addr <vip ip>

Note: If there are multiple virtual server with same IP but different service ports, ensure to include cs-server-port as an addition filter.

For example:

#tmsh delete sys connection cs-server-addr <vip ip> cs-server-port <port number>

3- Reset Statistics Before Testing

Reset statistics on both the virtual server and its associated pool before testing distribution:

# tmsh reset-stats ltm virtual <virtual_server_name>

# tmsh reset-stats ltm pool <pool_name>

4- Avoid Overlapping VIP/Syslog Server IPs

Do not configure the same IP address as both a local syslog destination on BIG-IP itself and as a remote logging VIP; this can cause routing confusion.

5- Monitor Selection

Use ICMP (gateway_icmp) as your default pool monitor unless you require a specific UDP health check.

6- If Issues Persist

If enabling datagram-load-balancing causes outages or instability in logging services, consider alternative designs such as layered/intermediate virtual servers for distributing syslog traffic.
