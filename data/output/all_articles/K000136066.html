Description

Leaked Credential Check is a new feature added to BIG-IP versions 16.1.x and 17.1.x that provides protection against leaked or stolen credentials being used to access personal or business applications. It incorporates both F5 AdvWAF and F5 Shape.

The purpose of this article is to augment the Implementation Guide to help get the most out of the Leaked Credential Check. F5 Leaked Credential Check Implementation Guide

Environment

  • In order to use the Leaked Credential Check you must first purchase a subscription and enter the Blackfish ID and Key. When you enter it there is no notification that it was done successfully. The blue sphere will not change color nor will anything else change in the GUI.
    • In most other cases when you add a subscription to a BIG-IP you will use an add-on license, but not in this case. Simply entering the ID/key activates it by contacting the Shape servers. Because of this there is no change on the BIG-IP license that will verify the subscription.
    • Once you have entered the ID/Key the 2 notes in RED that can be seen when you create a new policy or add Leaked Credential Detection to Security >> Application Security:Brute Force Attack Prevention to an existing policy will not disappear.
    • If you do not see the Blackfish ID it is likely due to this db being disabled. 
      asm.credential_stuffing_service
    • There is no need to create a new Cloud Security Application Profile. You can simply enter the ID/Key into the default one…f5-credential-stuffing-cloud-app
  • In order for the BIG-IP to verify the subscription it must have access to the Shape servers at bf.shpapi.com.
    • Ensure that access to bf.shpapi.com is not blocked.
    • The BIG-IP has to have a DNS Lookup Server configured.
    • By default the BIG-IP will use the f5-aws-dns resolver.
  • Once the Blackfish ID/Key has been entered and DNS is setup you will then need to manually configure the login pages. The login pages can also be created Automatically. More information about that can be found here… Configuring Leaked Credential Check.
    • Ensure you check the box for Leaked Credential Detection.
  • The blue sphere that is seen where you enter your credentials only changes colors when actual traffic has been detected that has been identified as possibly having an issue or does have an issue.
    • The sphere color only changes when a real LCC attempt is made, so if the key/id are configured properly, and there's internet connectivity, it still will not go green until there is an ASM policy enabled with a Brute Force Protection Configuration AND a failed login is received to check the credentials on. The response from the real check is what updates that color. Not having added the credentials.
    • If there is an issue found it logs in /var/log/asm.

Cause

The only way to know if you have successfully added Leaked Credential Check is to fully configure it and test it with a known bad login.
 

Recommended Actions

If a connection issue arises it is most commonly due to an issue with DNS. To troubleshoot it these steps should help...

Note: If there is more than one DNS name server configured on the BIG-IP you may have to run these steps to test each one. The BIG-IP only uses one at at time and will only use another one if the one in use fails to respond.


1) Verify which BIG-IP interface the local/internal DNS servers are using:
 

ip route get <LocalDNS>

Example:
ip route get 192.168.1.1

Example output:
[root@big-ip:Active:Standalone] config # ip route get 192.167.1.1
192168.1.1 via 10.1.1.254 dev mgmt src 10.1.1.1
cache mtu 1500


2) Then to verify bf.shpapi.com domain invoke the following command:

nslookup bf.shpapi.com <LocalDNS>

Example:
[root@big-ip:Active:Standalone] config # nslookup bf.shpapi.com 192.168.1.1
Server: 192.168.1.1
Address: 192.168.1.1#53
Non-authoritative answer:
Name: bf.shpapi.com
Address: 35.241.35.24


3) The resolved IP will be the one currently in use. As of the writing of this article it is 35.241.35.24. Then to know which BIG-IP interface is used to reach bf.shpapi.com:

ip route get 35.241.35.24

Example:
[root@big-ip:Active:Standalone] config # ip route get 35.241.35.24
35.241.35.24 via 10.1.1.254 dev mgmt src 10.1.1.1
cache mtu 1500


4) Other commands that can be used are 'dig' and 'curl' for testing.

5) By default the BIG-IP uses 8.8.8.8:53 for the DNS resolver. If you are using internal ones ensure they are accessible and the BGI-IP configuration has been updated to reflect hose IPs.

If the Blackfish ID/key does not show up in the GUI:


1) Check the db variable to ensure it is enabled...

tmsh list sys db asm.credential_stuffing_service

2) If it is not enabled run this command to do so:

tmsh modify sys db asm.credential_stuffing_service value enable

 

Additional Information

To see how this sets up and works you can visit the F5 Simulator that will walk you through the "why you want to use LCC" and the basic configuration. F5 Leaked Credential Check Simulator

An easy summary is that the only things that are required to ensure that the BIG-IP can use LCC are..

1) A subscription

2) Entering the Blackfish ID/Key that are provided by email when that subscription is purchased.

3) Internet connectivity

4) That the BIG-IP has DNS setup and it is able to access the DNS .

5) Once that is done then enabling/configuring it in the Brute Force Protection section of the applicable ASM policy
