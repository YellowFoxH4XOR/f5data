Description

When troubleshooting BIG-IP HTTPS health monitors, the BIG-IP HTTPS monitor may show the pool member as Up when recv none is configured, but show Down after adding recv "200", even though a standard curl test against the backend returns HTTP/1.1 200 OK. The following error may be observed in the logs:

No successful responses received before deadline

This behavior occurs when the backend server strictly enforces a valid Host: header per the HTTP/1.1 specification, and the monitor send string contains an empty Host: header. This article describes how to identify the backend server type from the Server: response header using curl, and how to use this information to correctly configure the BIG-IP HTTPS health monitor send string.

Environment

  • BIG-IP LTM
  • HTTPS health monitors
  • Backend servers with strict HTTP/1.1 compliance requirements (e.g., Oracle HTTP Server, Apache, Nginx, IIS)

Cause

The BIG-IP HTTPS monitor default send string includes an empty Host: header:

GET / HTTP/1.1\r\nHost:\r\nConnection: close\r\n\r\n

Some backend web servers (such as Oracle HTTP Server) strictly enforce the HTTP/1.1 specification. As stated in RFC 2616 Section 14.23:

"A client MUST send a Host header field in all HTTP/1.1 request messages. If the requested URI does not include an Internet host name for the service being requested, then the Host header field MUST be given with an empty value."

However, many strict server implementations reject requests where the Host: header is present but empty, returning HTTP/1.1 400 Bad Request instead of the expected 200 OK.

When recv none is configured, BIG-IP accepts any response including 400 Bad Request and marks the member Up. When recv "200" is added, the monitor correctly fails because the actual response is 400, not 200, causing the member to be marked Down.

Answer/Recommended Actions

Step 1: Identify the backend server type

Run the following curl command from the BIG-IP CLI, using an empty Host: header to simulate the exact request the monitor sends:

curl -vk --header "Host:" https://<pool_member_IP>:<port>/<path>

Examine the Server: response header in the output. For example:

< HTTP/1.1 400 Bad Request
< Date: Thu, 01 Jan 2026 00:00:00 GMT
< Server: <backend_server_type>

The Server: header identifies the backend web server software (e.g., Oracle-HTTP-Server, Apache, nginx, Microsoft-IIS).

If the server returns HTTP/1.1 400 Bad Request with an empty Host: header, this confirms that the server requires a valid Host: header value in the monitor send string.

Step 2: Identify the correct Host header value from the SSL certificate

Run a standard curl command (without the empty Host: override) to view the SSL certificate details:

curl -vk https://<pool_member_IP>:<port>/<path>

Locate the CN= field in the server certificate section of the output. For example:

* Server certificate:
*    subject: C=XX; ST=State; O=Company Name; CN=<application.example.com>

The CN= value is the hostname to use as the Host: header value in the monitor send string.

Note: If the backend server hosts multiple applications, the correct hostname may be a Subject Alternative Name (SAN) rather than the CN. Confirm the appropriate hostname with the application or server team if unsure.

Step 3: Update the monitor send string

Update the HTTPS monitor send string to include the correct Host: header value identified in Step 2.

Via GUI:

    1. Navigate to Local Traffic > Monitors > select the affected monitor
    2. In the Send String field, update the value to include the correct hostname: GET / HTTP/1.1\r\nHost: <application.example.com>\r\nConnection: close\r\n\r\n
    3. Click Update

Via tmsh:
tmsh modify ltm monitor https /<partition_name>/<monitor_name> send "GET / HTTP/1.1\r\nHost: <application.example.com>\r\nConnection: close\r\n\r\n"
tmsh save /sys config partitions all

Step 4: Verify the fix

Run the curl command again with the correct Host: header to confirm the server now returns HTTP/1.1 200 OK:

curl -vk --header "Host: <application.example.com>" https://<pool_member_IP>:<port>/<path>

Expected output:

< HTTP/1.1 200 OK

Once confirmed, the BIG-IP monitor should also reflect the pool member as Up.

Additional Information

  • Not all web servers disclose their type via the Server: response header. Some servers are configured to suppress or obfuscate this header for security reasons. In such cases, the 400 Bad Request response itself is still a strong indicator that the server requires a valid Host: header.
  • When using recv "200" as the monitor receive string, be aware that BIG-IP matches the receive string against the entire HTTP response including headers and body, not just the status line. Refer to K3618 for details on receive string matching behavior.
  • If the backend always returns HTTP 200 OK regardless of application health state (healthy or error), recv "200" alone is insufficient. Consider configuring a recv string matching a unique string from the healthy response body, and a recv-disable string matching the error page body to enable graceful session draining.
