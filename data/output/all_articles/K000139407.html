Description

If CM's Management Network is configured via DHCP or or by using cloud-init and DNS IPs are NOT included, the CM's coredns pod will not start resulting in a CM startup failure and the GUI will be inaccessible.

Environment

Relevant environmental factors specific to the topic

  • BIG-IP Next Central Manager
  • DHCP or Cloud-Init is used to configure the Management Network
  • DHCP or Cloud-Init does not provide DNS IPs 

Cause

For CM deployments, there are 3 approaches available for configuring the Management Network:

1. Run the 'setup' script

  • DNS configuration is enforced

2. Configure cloud-init within vSphere/VIO/KVM

  • DNS configuration is not enforced

3. Use DHCP

  • DNS configuration is not enforced

When using DHCP or cloud-init to provide the IP address to CM instances, if the DHCP server or cloud-init config does not include the optional DNS IPs, CM will fail to startup correctly due to an unrecoverable coredns CrashLoopBackoff.

This condition is related to Ubuntu's use of systemd-resolved by default. This is known to causes issues for coredns, which is a core component of k8/k3s. The issue is discussed here: https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/#known-issues.

On Ubuntu, Systemd-resolved moves and replaces system file /etc/resolv.conf with a stub file that contains:

 nameserver 127.0.0.53

Systemd-resolved's actual resolv.conf file is located here: /run/systemd/resolve/resolv.conf

When using DHCP or cloud-init to configure the IPs for CM, if the DHCP or cloud-init config does include DNS IPs, systemd-resolved will update its /run/systemd/resolve/resolv.conf file and include the desired 'nameserver' entries:

 nameserver 10.154.1.224
 nameserver 10.154.1.225
 search .

When this occurs, coredns will start without issues.

When using DHCP or cloud-init to configure the IPs for CM, if the DHCP server or cloud-init config does not supply DNS IPs, systemd-resolved will be unable to update its /run/systemd/resolve/resolv.conf file. Instead you'll end up with a default configuration:

# No DNS servers known.
search .

When this occurs, coredns will enter a DNS lookup loop, which coredns detects and triggers an unrecoverable CrashLoopBackOff.

The coredns pod log will report:

[Fatal] plugin/loop: Loop (127.0.0.1:55605 -> :53) detected for zone ".", see https://coredns.io/plugins/loop#troubleshooting.

Recommended Actions

The actions or steps required to address the topic covered in the description.

  1.  Configure DHCP to provide DNS IPs if using DHCP to configure the Central Manager
  2. Configure cloud-init configuration to include DNS IPs if using cloud-init to configure Central Manager
  3. Redeploy Central Manager
