Description

When using BIG-IP APM (Access Policy Manager), certain HTTP headers are reserved for APM internal state management and are automatically stripped from requests before being forwarded to pool members. This can cause application communication failures when backend applications require these specific headers.

Symptoms:

  • Backend applications report missing required HTTP headers
  • Application communication breaks after APM authentication
  • Users unable to connect to applications that were previously working
  • Specific headers like "Session-ID" not reaching pool servers despite being present in client requests

Reserved APM Headers:

The following headers are blocked by APM and will not be forwarded to pool members:

  • partition-id
  • profile-id
  • traffic-id
  • session-key
  • session-id
  • client-session-id
  • snapshot-id
  • cmp-pu

Environment

  • Product: BIG-IP APM
  • Version: 17.1.3 (applicable to other versions)
  • Configuration:
    • Virtual server with APM access profile applied
    • Backend pool members requiring specific HTTP headers
    • Client requests containing APM-reserved header names

Cause

APM reserves specific HTTP header names for maintaining internal state and session management. These headers are intentionally stripped from requests before forwarding to pool members to prevent conflicts with APM's session handling mechanisms. This is by design.

Answer/Recommended Actions

To forward APM-reserved headers to pool members, use an iRule that captures the header value on the client side and re-inserts it on the server side after APM processing:

Step 1: Create the following iRule (adjust the header name as needed):

#F5 iRule to forward APM-reserved headers
# Manually copy a client request header to the pool member
# These headers are reserved for APM and are normally blocked

when RULE_INIT {
set static::check "session-id"
}

when HTTP_REQUEST {
if [ HTTP::header exists ${static::check} ] {
set myheader [ HTTP::header value $static::check ]
# log local0. "Header $static::check found: $myheader"
}
}

when HTTP_REQUEST_RELEASE {
if [ info exists myheader ] {
# log local0. "ServerSide myheader variable exists, $myheader, inserting as $static::check header."
HTTP::header insert $static::check $myheader
}
}

Step 2: Modify the static::check variable to match your required header name (e.g., "session-id", "partition-id", etc.)

Step 3: Apply the iRule to the virtual server with the APM profile

Step 4: Test the configuration:

  • Authenticate through APM
  • Verify the header is received by the backend application
  • Monitor for any APM functionality issues

Step 5: (Optional) Enable logging by uncommenting the log statements for troubleshooting

Validation:

Use packet captures to confirm the header is present in server-side traffic:

tcpdump -nni <interface> -s0 host <pool_member_IP> -w /var/tmp/header_validation.pcap

Additional Information

Important Considerations:

  • This workaround may potentially interfere with APM functionality since these headers are reserved for APM state management
  • Thoroughly test in a non-production environment before implementing
  • Monitor APM session behavior after implementation
  • This approach differs from inserting APM session variables as custom headers, which is the standard method for passing APM session data to backend servers

Alternative for APM Session Data:

If you need to pass APM session information (not client-provided headers), use the standard approach of inserting APM session variables as custom headers:

when ACCESS_ACL_ALLOWED {
HTTP::header insert "X-APM-Session-ID" [ACCESS::session data get "session.user.sessionid"]
}

Troubleshooting:

  • Use sessiondump -allkeys | grep session to identify available APM session variables
  • Apply a logging iRule to verify all headers being sent/received
  • Coordinate with application teams to confirm exact header requirements
