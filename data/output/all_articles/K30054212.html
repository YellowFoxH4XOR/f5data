LDAPS Auth

LDAPS TCP/636

LDAPS Auth and LDAPS Query works.

  • LDAPS Auth and LDAP Query use a simple bind over SSL/TLS. 

  • LDAP Signing (LDAPServerIntegrity=2)

    The LDAPServerIntegrity requirement is satisfied as the transport layer (SSL) provides channel signing. BIG-IP APM provides secure connections to the SSL-protected DC by using a fully SSL-encapsulated protocol via the server-ssl profile.The profile can also be configured with additional security settings to control ciphers, server certificate validation / chaining and certificate revocation via OCSP or CRL in order to provide additional security. 

  • LDAP Channel Binding (LdapEnforceChannelBinding=2)

    The LDAP Channel Binding options does not apply here as it does not have bearing for these types of sessions - LDAP sessions using TLS/SSL, binding by using certificate for user authentication.

    For more information on LDAP session options, refer to LDAP session security settings and requirements.
 
LDAPS Query
AD AuthLDAP TCP/389

AD Auth and AD Query works.

  • AD Auth and AD Query use a simple LDAP bind over a signed and encrypted SASL channel. 

  • LDAP Signing (LDAPServerIntegrity=2)

    The LDAPServerIntegrity requirement is satisfied at the SASL layer. When using signing with a SASL the sessions are secure from Man-In-The-Middle attacks as the signing keys are derived from the user password. BIG-IP APM AD Auth can also seal (encrypt) via the Kerberos Pre-authentication feature in order to add an extra layer of protection. 

  • LDAP Channel Binding (LdapEnforceChannelBinding=2)

    The LDAP Channel Binding options does not apply here as it does not have bearing for these types of sessions - LDAP sessions not using TLS/SSL, binding by using  SASL. 

    For more information on the different LDAP session options, refer to LDAP session security settings and requirements.

The Microsoft Windows Server event logs may display the following message when using AD Auth or AD Query: 

Event ID: 2889  
Description: The following client performed a SASL (Negotiate/Kerberos/NTLM/Digest) LDAP bind without requesting signing (integrity verification), or performed a simple bind over a clear text (non-SSL/TLS-encrypted) LDAP connection.

Logging anomaly of Event ID 2889

Applications that use third-party LDAP clients may cause Windows to generate incorrect Event ID 2889 entries. This occurs when you log LDAP interface events and if LDAPServerIntegrity is equal to 2 . The use of sealing (encryption) satisfies the protection against the MIM attack, but Windows logs Event ID 2889 anyway.

This happens when LDAP clients use only sealing together with SASL. We have seen this in the field in association with third-party LDAP clients."

AD Query

Environment

  • BIG-IP APM AD or LDAP(s) authentication and query
  • Windows Active Directory Servers 

Cause

There is a security requirement to enable LDAP channel binding and signing on AD Domain Controllers.

Recommended Actions

You can perform the following actions to secure your LDAP communication and also prevent service disruption:

  • Keep up to date with the latest Microsoft's updates on ADV190023. In the latest updates, Microsoft announced that the March 10, 2020 and updates in the foreseeable future will not make changes to LDAP signing or LDAP channel binding policies or their registry equivalent on new or existing domain controllers.
  • Continue to use or implement AD Authentication and AD Query for authentication and access control with your AD servers.
  • Configure LDAP AAA server resources to use LDAPS and port 636
    1. In the AAA server configuration (Access > Authentication > LDAP), check the box for LDAPS under Mode
    2. Ensure that the port (which defaults to 636) matches the port your AD server is listening on for LDAPS.
    3. Specify a ServerSSL profile to customize the SSL settings for that connection.
    4. Ensure that your AD servers are configured to listen for and handle LDAPS connections.
