Known Issue

Note: Hardware SYN Cookie Protection is only available for virtual servers using the FastL4 profile on BIG-IP systems equipped with a Packet Velocity ASIC version 10 (PVA10). For this reason, this Solution applies to only the BIG-IP 8400 and 8800 platforms. For more information about PVA10 and SYN cookie protection, refer to K4832: Overview of Packet Velocity ASIC (PVA) Acceleration features and sub features and K7847: Overview of BIG-IP SYN cookie protection.

This is the result of a known issue. If Hardware SYN Cookie Protection is enabled for a virtual server, the BIG-IP system may fail to honor the Maximum Segment Size (MSS) requested by a client connecting to that virtual server. When this issue occurs, the BIG-IP system may reply to the client with TCP segments larger than the MSS it had requested. As a result, the connection fails.

Note: The MSS announced by a host is usually calculated automatically; it is directly linked to the Maximum Transmission Unit (MTU) of a given network interface. For example, with an MTU of 1500 bytes, a host would set its MSS to 1460 bytes (1500 bytes minus 20 bytes used by the TCP header and minus 20 bytes used by the IP header).

For example:

  • A BIG-IP 8800 platform is configured with the HTTP_VS virtual server.
  • The HTTP_VS virtual server uses a FastL4 profile where PVA Acceleration is set to Full and Hardware SYN Cookie Protection is enabled.
  • The ingress VLAN for the HTTP_VS virtual server is configured with an MTU of 1472 bytes.
  • A client required to access the HTTP_VS virtual server is configured with an MTU of 1472 bytes.
  • The current connection count in the PVA10 has reached the threshold specified by the Pva.SynCookies.ConnectionThreshold bigpipe database variable, and Hardware SYN Cookie Protection is being enforced.
  • When the client initiates a TCP connection to the HTTP_VS virtual server, it announces its MSS to be 1432 bytes. When the BIG-IP system begins transmitting data to the client, the system will create TCP segments with 1460 bytes of data in each, therefore failing to honor the MSS requested by the client and the MTU of the ingress VLAN.

This issue occurs because the BIG-IP system does not encode the correct MSS in the secret cookie, which is sent to the client in the SYN-ACK reply. When a new TCP connection proves to be legitimate by successfully completing the three-way handshake, the BIG-IP system decodes the secret cookie and obtains an MSS, which may not reflect what was requested by the client.

Important: The maximum value that the BIG-IP system can encode in a secret cookie to represent the MSS is 1460 bytes. For this reason, this issue occurs only when the client requests an MSS lower than 1460 bytes.

F5 Product Development tracked this issue as ID 223023 and ID 323698 (formerly CR126842).

Support for the affected BIG-IP8400 and 8800 platforms ended in BIG-IP 11.1.0. For more information about software support for the BIG-IP 8400 and 8800 platforms, refer to K13520: Updated End of New Software Support announcement for the 6400 FIPS/NEBS, 6800 FIPS, 8400/8400 FIPS/NEBS, and 8800 platforms

Workaround

You can work around this issue by switching from Hardware SYN Cookie Protection to Software SYN Cookie Protection. To do so, perform the following procedure:

  1. Log in to the BIG-IP Configuration utility.
  2. Navigate to Local Traffic > Profiles.
  3. Under the Protocol tab, click FastL4.
  4. Click the FastL4 profile which is in use by the virtual server presenting the issue.
  5. Clear the Hardware SYN Cookie Protection check box.
  6. Select the Software SYN Cookie Protection check box.
  7. Click Update.

Note: As an alternative workaround, you could configure your network to allow path-MTU-discovery. In this configuration, the PVA10 would continue to behave incorrectly; however, the network would correct the behavior. This may require configuration changes in other network devices, but would allow you to continue using Hardware SYN Cookie Protection on the BIG-IP system.
