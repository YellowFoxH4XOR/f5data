Broken object level authorization

This is a security risk that occurs when authorization rules dictating user object accessibility do not exist or are not applied properly. This allows users to manipulate API request parameters to access objects to which they are not authorized. Note that this is not related to authentication. You may authenticate API requests correctly but still be vulnerable to broken object level authorization. The most common cause for this is that server components do not track the client state and instead rely on object IDs in API requests, which can be easily manipulated.

This vulnerability can lead to data exfiltration enabling attackers to destroy or modify application data. In worst-case scenarios, depending on the application, sensitive information such as account information, IDs, and passwords may be leaked, enabling attackers to take over accounts.

Broken object level authorization attack scenario

In the following attack scenario, the attacker manipulates the userid value in the URI path to retrieve user information from other users' account.

  1. The attacker uses a legitimate account and sends the following API request to retrieve their user information.

    GET https://api.example.com/v2/userid-1a-1234/userinfo
    Cookie: _userId=userid-1a-1234

  2. The attacker creates a second legitimate account, and using the userid, the attacker guesses and enumerates different userid values. They use a script or tool to send API requests, testing a range of userids, and receive sensitive information of other users.

    GET https://api.example.com/v2/userid-1a-1111/userinfo
    Cookie: _userId=userid-1a-1111
    GET https://api.example.com/v2/userid-zz-9999/userinfo
    Cookie: _userId=userid-zz-9999

  3. They expand the scope of the attack by manipulating the API request to delete users.

    DELETE https://api.example.com/v2/userid-1a-1111
    Cookie: _userId=userid-zz-9999

Secure your APIs against broken object level authorization attacks with F5 products

To protect your APIs, best practices recommend the following:

  • implement authorization mechanisms to check if the logged-in user has access to perform the requested action on the record in every function that uses an input from the client to access a record in the database.
  • Be extremely methodical and precise when testing the authorization mechanisms to ensure every API endpoint is secured against attacks on every object possible according to business requirements.
  • Securing against broken object level authorization attacks is about more than just rolling out fixes at the source code level. It involves implementing a series of defenses at each layer in the authentication and authorization process.

Use BIG-IP APM to mitigate broken object level authorization attacks

Responsibility of preventing broken object level authorization tends to fall on the application server because it is closely related to the application code and logic. However, there are a lot of reasons to share, if not delegate, this responsibility to the API Gateway as well. BIG-IP APM, as the API Gateway and single central IdP solution, sees all the parameters in the API request, can correlate object ID relationships, and, most importantly, can manage user sessions.

To protect your APIs against broken object level authorization attacks, you need to implement different layers of defence against attackers such as the following:

  • Authorization mechanisms to validate the API calls are authorized to perform what they are requesting

    The system processes API requests through per-request policies. Through the per-request policy flow, you can extract a range of information from the API request, assign them to subsession or perflow variables, and validate the values to ensure each request is authorized. To design and implement the authorization mechanism you want, use a combination of the following in per-request policies based on your application logic:

    • Per-request policy branches
    • Subsession and per-flow variables
    • Subroutine gating criteria

For example, you can enforce the following application logic to validate API calls:

An API request to read or modify an object, includes the azureID value in its path and this value must match the value in the JWT token included in the authorization header of the request. For a specific example on how to configure the per-request policy for this, refer to K11764434: Configure BIG-IP APM API protection session variables for secure API authorization.

  • Leverage BIG-IP APM as an identity provder (IdP). BIG-IP APM supports different authentication and authorization technologies and federation services like OAuth, OpenID connect, JWT, and so on, and you can use BIG-IP APM as a central IdP solution. In addition, you can also configure it to integrate with other IdPs in your existing environment to provide single sign-on for all your users and API requests, allowing you to manage the resources, scopes, roles, and policies needed to perform object-level authorization decisions.

  • Implement and enforce the zero trust security model. Zero trust refers to not only continuously authenticating and authorizing every user but also every API requests made eliminating any implicit trust. A BIG-IP APM per-request policy can examine the details (URL path, parameters, cookies, HTTP headers, JWT token, and so on) of each API requests, giving you the granular control to handle and route each requests according to the specific business logic of your application.

  • User session tracking

    One of the main reasons for broken object level authorization attacks is the lack of user session tracking. On the same note, you can resolve many attacks by tracking user sessions. Use a combination of the following in Per-request policies based on your application logic to design and implement user session tracking:

    • BIG-IP APM subsession: This is a distinct ID created for each subsession for each distinct gating criteria value that you can use.
    • HTTP connector agent: This is used to communicate with external servers to make API calls or retrieve information.
    • iRules: These are used to manipulate data, headers, and so on.

For example, you can enforce the following application logic through tracking user sessions to secure against broken object level authorization:

In order to read or modify attributes of a purchase item, the user must have created the item in a previous API call. The API request must include a unique, non-guessable ID in the HTTP cookie or header that is made up of IDs such as the apm subsession ID combined with the ID of the object.

Use F5 Distributed Cloud Services to mitigate broken object level authorization attacks

You can use F5 Distributed Cloud Services to augment your API gateway's functionality to mitigate broken object level authorization attacks by using the following features:

  • API discovery

    Granular testing of every API endpoint is essential to protect against broken object level authorization attacks. This becomes a challenge as the development team continuously rolls out new API endpoints and schema to meet the evolving application requirements, creating a drift between your organization's documented APIs and operational ones. F5 Distributed Cloud Service's API discovery allows your SecOps team to keep up with constant changes in APIs and easily identify all API endpoints mapped to your applications and monitor anomalous activities or shadow APIs including blocking of suspicious requests and endpoints.

  • Malicious user detection and mitigation

    The main strategy broken object level authorization attacks use to exploit the vulnerability is to enumerate  a series of repeated requests through object and user IDs. F5 Distributed Cloud Services uses artificial intelligence and machine learning (AI/ML) to analyze API requests to an organization’s applications over time, and outliers are identified. It learns client behavior through forbidden activity through configured layer-7 protection policies (including HTTP methods, paths, query parameters, headers, and more), failed login attempts, WAF and threat campaigns signatures, IP reputation database triggers, and invalid or nonexistent URL/request activity (404 not found response codes).
    Use the WAAP security incident feature which continuously pushes application events to internal AI/ML engines, grouping thousands of events into few incidents based on context and common characteristics. This allows you to more quickly examine issues by aggregating many events into a few incidents based on context.
