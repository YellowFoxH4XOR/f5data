Known Issue

This is the result of a known issue. Route domains allow you to segment network traffic, and define separate routing paths for different network objects on the BIG-IP system. NAT objects configured within a route domain fail to forward traffic. NAT objects that are not configured within a route domain forward traffic as expected.

For example, the following NAT object is configured within a route domain, and host 192.168.33.1%1 is unable to successfully contact a host on the 172.16.15/24 subnet through the floating self IP:

nat 192.168.33.1%1 to 172.16.15.146 {
}

The following NAT object is not configured within a route domain, and host 192.168.31.33 is successfully able to contact a host on the 172.16.15/24 subnet through the floating self IP:

nat 192.168.31.33 to 172.16.15.145 {
}

F5 Product Development tracked this issue as CR116062 and it was fixed in BIG-IP version 10.1.0. For information about upgrading, refer to the BIG-IP LTM, ASM, PSM, or WOM release notes.

Workaround

You may configure similar functionality to a NAT by defining a virtual server and pool to allow ingress traffic to a node, and defining a virtual server and iRule to allow egress traffic from a node to an external resource.

To allow ingress traffic to an internal node, define a virtual server and pool object.

For example, the following virtual server and pool allows hosts on the external vlan (the outside network) in route domain 10 to connect to the origin host on the internal vlan (the inside network) in route domain 20 via the IP address 10.1.161.122:

virtual outbound-SNAT {
   destination any%20:any
   mask 0.0.0.0
   rules iSNAT
   vlans internal enable
}
rule iSNAT {
   when CLIENT_ACCEPTED {
  switch [IP::client_addr] {
       10.2.161.21%20 {
          snat 10.1.161.122%10
          set ipaddr_rd [ split [IP::local_addr] "%" ]
          node [lindex $ipaddr_rd 0]%10
       }
       default { log local0. "didn't match" }
 }
}
}
