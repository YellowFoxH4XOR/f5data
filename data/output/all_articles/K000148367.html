K000148367: Missing logs on F5OS-A when modifying 'system logging remote-servers' configuration

Published
2024-11-01
Updated
2024-11-01
Applies to
  • F5OS
  • F5OS-A: 1.8.X, 1.7.X, 1.5.X, 1.8.0, 1.7.0, 1.5.2, 1.5.1, 1.5.0
Source

Description

When making multiple changes in short succession, for example:

system logging remote-servers remote-server 10.10.1.1 config proto udp remote-port 514
commit
portgroups portgroup 4 config ddm ddm-poll-frequency 29
commit

Log messages relating to the second commit are missing from the audit.log and platform.log.

Why are these logs going missing? Is this expected? Can it be avoided?

Environment

  • F5OS-A
  • Logging
  • Updating system logging remote-servers configuration

Cause

When modifying the system logging remote-servers configuration, the rsyslogd process inside the system_rsyslogd container is restarted. This restart typically takes 3-4 seconds, and any log messages in flight will be lost. This is expected behaviour, and is a limitation of rsylog.

Recommended Actions

On F5OS-A versions prior to v1.8.0, the rsyslog restart is immediate when committing a system logging remote-servers configuration change.

With the fix for ID1411137 in v1.8.0, the rsyslog restart is delayed by 3 seconds. The lost logs can mostly be avoided in versions with that fix, by making multiple changes inside a single commit.

For example:

system logging remote-servers remote-server 10.10.1.1 config proto udp remote-port 514
portgroups portgroup 4 config ddm ddm-poll-frequency 29
commit

Additional Information

It is still possible for some logs to be lost, even with the fix for ID1411137. If changes are made 3-4 seconds after the commit containing the system logging remote-servers change, rsyslog may already be in the process of restarting.

For example:

system logging remote-servers remote-server 10.10.1.1 config proto udp remote-port 514
commit
# Wait 3-4 seconds
portgroups portgroup 4 config ddm ddm-poll-frequency 29
commit      # Log messages from this commit will be lost

Bug ID1710413 tracks this issue.
