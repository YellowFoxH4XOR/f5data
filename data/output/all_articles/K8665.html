Topic

Beginning in BIG-IP 11.x, redundant BIG-IP configurations may consist of two or more BIG-IP systems that form a redundant failover group. A redundant BIG-IP configuration allows traffic processing to continue in the event that one of the redundant BIG-IP units becomes unavailable. In most cases, the units in a redundant configuration should be identically licensed, provisioned, and configured, and should also run on the same hardware platform. These requirements are explained in detail in the following sections.

BIG-IP hardware/virtual platform requirements

Beginning in BIG-IP 11.4.0, F5 supports redundant devices in a device group on different hardware or virtual platforms through the load-aware failover feature. If you are configuring devices with different capabilities/capacities, for example a BIG-IP iSeries and a BIG-IP Virtual Edition (VE) tenant running on a F5 rSeries, you must configure the ha-capacity setting on both devices. This setting specifies a number that represents the relative capacity of the device to be active for a number of traffic groups; the higher the number the greater the capacity to take on connections. The value for this setting is zero (0) by default which means the device may run any number of traffic groups; the valid range must be between zero (0) and 100000 inclusive. Additionally, you should configure the HA Load Factor setting for the traffic group common to both devices. The HA Load Factor setting specifies a number that represents the load the traffic group presents to the system relative to other traffic groups; the higher the number the greater the amount of resources the traffic group needs to use relative to other traffic groups. The value is set to one (1) by default and must be within a valid range of 1 and 1000 inclusive. For more information about configuring the load-aware failover feature as well as the limitations for a device group consisting of heterogeneous hardware or virtual platforms, refer to the About using traffic load to pick the next-active device section under the Managing Failover chapter of the BIG-IP Device Service Clustering: Administration manual.

Note: For information about how to locate F5 product manual, refer to K12453464: Finding product documentation on AskF5.

Important: Features that rely on similar resources, such as connection and persistence mirroring, may not be supported for device groups consisting of heterogeneous hardware, virtual platforms or BIG-IP software versions.

For VIPRION systems in a redundant configuration, each VIPRION system should have the same number of blades in each chassis. Additionally, the blades should be seated in the same slots, or some features may not function correctly (for example, connection mirroring). For example, if a VIPRION system has a blade in slot 1 and a blade in slot 3, the peer VIPRION system should also have a blade in slot 1 and a blade in slot 3.

BIG-IP software requirements

The BIG-IP units in a device group must run the same major, minor, and maintenance software version numbers. By default, the BIG-IP system does support running device group members with different point release or hotfix versions.

For example, if one BIG-IP system in a redundant configuration runs BIG-IP 16.0.1, the peer system must also run BIG-IP 16.0.1. However, if one BIG-IP system in a redundant configuration runs BIG-IP 16.0.1, the peer system can run a different point release, such as BIG-IP 16.0.1.1.

If the existing BIG-IP system runs a later major, minor, or maintenance software version, you must upgrade the peer system. For information about upgrading, refer to the following article: K84205182: BIG-IP update and upgrade guide | Chapter 1: Guide contents.

Important: F5 strongly recommends performing software upgrades during a scheduled maintenance window. When you upgrade the units in a redundant system, they temporarily run different software. In most cases, failing over to upgrade the second system is no different from a normal failover. However, depending on the versions involved in the upgrade, some traffic may be disrupted due to changes in profile functionality and any mirroring options that may be configured. Two specific examples of mirroring features that may be impacted are detailed in K7225: Transport protocol used for BIG-IP connection and persistence mirroring and K9057: Service port and protocol used for BIG-IP network failover.

BIG-IP licensing and provisioning requirements

The BIG-IP units in a redundant system must match with respect to product licensing and module provisioning. There are two occasions when licensing and provisioning can differ:

  • Redundant BIG-IP systems can be licensed for BIG-IP LTM on both units and for the BIG-IP GTM module on only one unit. For more information about proper provisioning for this scenario in BIG-IP 10.0.0 and later, refer to K12322: Provisioning requirements for BIG-IP redundant pairs in which the BIG-IP GTM module is licensed on only one of the units.
  • Redundant BIG-IP Virtual Edition (VE) systems can be licensed for different throughput rates and function properly. However, if for example, an active member licensed for 200 Mbps is currently processing 100 Mbps of traffic fails over to a standby member licensed for only 25 Mbps, traffic processing will be impacted. For more information about determining the maximum allowed throughput rate on the BIG-IP VE system, refer to K14356: Determining the maximum allowed throughput rate on the BIG-IP VE system.

BIG-IP hotfix requirements

BIG-IP device group members must run the same major, minor, and maintenance software version numbers. However, the hotfix version numbers are not required to match among device group members; failover and ConfigSync operations function as expected.

SCCP firmware requirements

The Switch Card Control Processor (SCCP) is a separate subsystem that controls the F5 switch hardware.

BIG-IP systems in a redundant configuration are not required to run the same version of SCCP firmware. However, F5 recommends running the latest version of SCCP firmware on redundant systems.

AOM firmware requirements

The Always-On Management (AOM) subsystem enables you to manage the BIG-IP system remotely by using secure shell (SSH) or the serial console, even if the host is turned off. The AOM Command Menu operates independently of Traffic Management Operating System (TMOS).

BIG-IP systems in a redundant configuration are not required to run the same version of AOM firmware.

Turboflex profile and FPGA firmware requirements
 
On applicable devices, the Turboflex profile or the FPGA firmware, or both, must be set to the same value on all devices in the device-group for mirroring to work correctly.
