K000159854: Resolving /var Storage Size Discrepancy on Data Collection Device During Rolling Upgrade

Description

During a BIG-IQ rolling upgrade, the upgrade process may pause at certain % on a Data Collection Device (DCD) with the following alert message:

The /var storage for DCD was previously increased. To avoid data loss, increase the storage for the new active volume before you upgrade. See AskF5 article K16103 for more information.

This alert appears when:

  • The DCD has a previously extended /var partition
  • The new boot volume's /var partition is smaller than the old boot volume's /var partition
  • The upgrade process detects a size mismatch that could result in data loss

The upgrade will pause and wait for user intervention before continuing.

Environment

  • Product: BIG-IQ Centralized Management with Data Collection Devices (DCD)
  • Upgrade scenario: Rolling upgrade to version 8.3 or later
  • Configuration: DCD with previously extended /var storage (e.g., 266 GB or larger)
  • Symptom: Upgrade pauses at (e.g., 65%) completion with storage alert
  • System state: DCD has already booted into the new boot volume

Cause

During the BIG-IQ upgrade process, the system creates a new boot volume with default /var partition sizes. When a DCD has a previously extended /var partition, the upgrade process will not automatically replicate the extended size to the new boot volume.

The upgrade safety mechanism detects that the /var storage on the new boot volume is smaller than the /var storage on the old boot volume, triggering an alert to prevent potential data loss. This discrepancy occurs because the previously extended /var storage was not automatically expanded to match the old boot volume size during the upgrade process.

Answer/Recommended Actions

To resolve the /var storage size discrepancy and continue the upgrade:

Step 1: Verify which boot volume is currently active

Before making any changes, confirm which boot volume the system is currently running on:

  • Run: tmsh show sys software status
  • Look for the boot location marked as "yes" in the "Active" column
  • Example output:

    Sys::Software Status

    Volume Product Version Build Active Status

    ---------------------------------------------------------------

    HD1.1 BIG-IQ 8.3.0 0.0.2 yes complete

    HD1.2 BIG-IQ 7.1.0 2.0.3 no complete

  • In this example, HD1.1 is the active (new) boot volume
  • The system should be booted into the new boot volume after the upgrade process has started

Important: If the system is not on the new boot volume, do not proceed with these steps. Contact F5 Support for assistance.

Step 2: Verify the current /var storage allocation

  • Run: tmsh show sys disk directory
    • This shows the current disk usage and available space

Step 3: Compare the /var volume sizes between old and new boot volumes

  • Run: lvs --unit=k | grep var
  • Identify the active boot location (new boot volume) and the previous boot location (old boot volume)
  • The output shows logical volumes with "o" flag indicating the active volume
  • Example output:

    set.1._var vg-db-vda -wi-ao---- 283115520k (269.9GB) ← New boot volume (active - note the "o")

    set.2._var vg-db-vda -wi-a----- 304861184k (290.7GB) ← Old boot volume

  • The volume with -wi-ao---- (note the "o") is the active/open volume (currently mounted)
  • The volume with -wi-a----- (no "o") is the inactive volume
  • Calculate the size difference that needs to be added to the new boot volume

Note: Cross-reference the active boot location from Step 1 with the logical volume naming:

  • HD1.1 typically corresponds to set.1._var
  • HD1.2 typically corresponds to set.2._var

Step 4: Check available free space in the volume group

Before attempting to resize, verify that sufficient free space is available:

  • Run: vgs --unit=k
  • Look for the VFree column to see available free space in the volume group (typically vg-db-vda)
  • Example output:

    VG #PV #LV #SN Attr VSize VFree

    vg-db-vda 1 10 0 wz--n- 524288000k 50000000k

  • Calculate if the free space is sufficient:
    • Required space = (Old boot volume size) - (New boot volume size)
    • Example: 304861184k - 283115520k = 21745664k (~20.7 GB required)
    • Ensure VFree is greater than the required space

Important: If insufficient free space is available, you must expand the underlying virtual disk before proceeding. Refer to K16103 for instructions on expanding disk space on BIG-IQ Virtual Edition.

Step 5: Check current disk usage on /var

  • Run: df -h /var
  • Verify that the current usage is well below the target size to ensure the resize operation will succeed
  • Example output:

    Filesystem Size Used Avail Use% Mounted on

    /dev/mapper/vg--db--vda-set.1._var 270G 180G 90G 67% /var

  • Confirm the filesystem path matches the active boot volume identified in Step 1 and Step 3

Step 6: Resize the /var volume on the new boot volume

Below steps are referrencing KB K30902515:

  • Run: resizevol /var <size_in_kilobytes>
  • Example: resizevol /var 304861184
  • Important:
    • Use the exact size in kilobytes from the old boot volume
    • Do not specify a size smaller than the currently used space
    • Ensure the size does not exceed available free space in the volume group
    • The resizevol command will resize /var on the currently active boot volume

Step 7: Save the system configuration

  • Run: tmsh save sys config

Step 8: Reboot the DCD

  • Run: reboot now

Step 9: Wait for the system to stabilize

  • Allow 3–5 minutes after reboot for the system to fully initialize

Step 10: Verify the resize operation

After reboot, confirm the /var partition has been resized correctly:

  • Run: tmsh show sys software status
    • Verify the system is still booted into the same boot volume
  • Run: df -h /var
    • Verify the new size is reflected
  • Run: lvs --unit=k | grep var
    • Verify that the active boot volume now matches or exceeds the old boot volume size
  • Example verification output:

    set.1._var vg-db-vda -wi-ao---- 304861184k (290.7GB) ← Now matches old boot volume

    set.2._var vg-db-vda -wi-a----- 304861184k (290.7GB) ← Old boot volume

Step 11: Continue the upgrade process

  • In the BIG-IQ rolling upgrade interface, click the "Continue" button

Step 12: Monitor the remaining upgrade process

  • Verify that all remaining DCDs and the Central Manager complete the upgrade successfully

Additional Information

  • The alert and upgrade pause are expected safety behaviors designed to prevent data loss when /var storage has been previously extended.
  • On DCDs without previously extended /var partitions, the upgrade process typically completes without this alert.
  • The resizevol command affects /var on the currently active boot volume. Always verify which boot volume is active before proceeding.
  • Do not specify a size smaller than the currently used space in /var to avoid data loss.
  • If the volume group does not have sufficient free space, you must expand the underlying virtual disk at the hypervisor level before attempting to resize /var.
  • Important: The BIG-IQ upgrade process does NOT preserve custom /var partition sizes. During upgrade to BIG-IQ v8.x, the new boot volume is created with the default /var size of 75 GB, regardless of the size configured on the old boot volume. If the /var partition was previously extended beyond 75 GB, you must follow the procedure in K86200286 to set the desired /var size on the new boot volume before starting the upgrade.
  • This procedure should be performed on each DCD that encounters this alert during the rolling upgrade.
  • Always verify available free space and the active boot volume before attempting any disk resize operation to prevent system instability or data loss.
  • The logical volume naming convention typically follows: set.1._var corresponds to HD1.1, set.2._var corresponds to HD1.2, etc.
