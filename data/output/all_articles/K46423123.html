Topic

An invalid option in an iRule will cause a bad option Tool Command Language (Tcl) error. This article describes a common cause for this error and a best practice for preventing it.

Description

If an argument with a leading dash is passed to an iRules command in a position where options are placed, the command will interpret the argument as an option. This often occurs when a variable is placed in a command immediately following the options section. This scenario results in a Tcl error indicating that a bad option was used and the BIG-IP system resets the connection. The BIG-IP system logs an error message to the /var/log/ltm file similar to the following example:

err tmm[11491]: 01220001:3: TCL error: /Common/TableMissingDoubleDash <HTTP_REQUEST> - bad option "-leadingdash": must be -notouch, -subtable, -excl, -mustexist, -remaining, -count, or -all while executing "table incr -subtable MyTable -mustexist [HTTP::header "X-Custom"]"

To avoid this incorrect interpretation of an argument, you can mark the end of options in an iRules command by including two dash characters ( -- ) at the end of the options section. This prevents the command from treating the arguments that follow as options even if they begin with a single dash character ( - ).

Example iRule without marking the end of options

In the following iRule applied to a virtual server, the HTTP:header "X-Custom" command looks for the header named X-Custom in an HTTP request and passes the value as an argument to the table command. The data is also stored and referenced with the variable $key.

when HTTP_REQUEST {
    if {[table incr -subtable MyTable -mustexist [HTTP::header "X-Custom"]] eq ""} {
        table set -subtable MyTable [HTTP::header "X-Custom"] 1 7200
    }
    if {[string tolower [HTTP::uri]] eq "/logthetable"} {
        foreach key [table keys -subtable MyTable] {
        log local0. "$key: [table lookup -subtable MyTable $key]"
        }
        HTTP::redirect "http://[HTTP::host]/"   
    }
}

If the virtual server receives an HTTP request that contains the X-Custom: -leadingdash header and value, the table command interprets the argument as an option. The three table commands in the iRule appears as shown in the following example after a variable substitution occurs:

table incr -subtable MyTable -mustexist -leadingdash
table set -subtable MyTable -leadingdash 1 7200
table lookup -subtable MyTable -leadingdash

Since -leadingdash is not a valid option, the iRule execution results in a Tcl error and the connection is reset.

Example iRule marking the end of options with two dash characters ( -- )

You can prevent this error by including two dash characters ( -- ) at the end of the options in each command that you use in an iRule.

Important: Apply the workaround to all affected stanzas. In the following example, the second and third lines require the workaround prior to the [HTTP::header "X-Custom"] evaluation.

Continuing with the iRule from the previous example, when the BIG-IP system administrator marks the end of options, it appears similar to the following:

when HTTP_REQUEST {
    if {[table incr -subtable MyTable -mustexist -- [HTTP::header "X-Custom"]] eq ""} {
        table set -subtable MyTable -- [HTTP::header "X-Custom"] 1 7200
    }
    if {[string tolower [HTTP::uri]] eq "/logthetable"} {
        foreach key [table keys -subtable MyTable] {
        log local0. "$key: [table lookup -subtable MyTable -- $key]"
        }
        HTTP::redirect "http://[HTTP::host]/"   
    }
}

If the virtual server receives an HTTP request that contains an X-Custom: -leadingdash header and value, the table command will stop parsing options after the double dashes ( -- ) and correctly interpret the argument. The three table commands in the iRule appears as shown in the following example after variable substitution occurs:

table incr -subtable MyTable -mustexist -- -leadingdash
table set -subtable MyTable -- -leadingdash 1 7200
table lookup -subtable MyTable -- -leadingdash

With this configuration the iRule now runs successfully.
