Source

Description

  • DNS requests are not responded to via the BIG-IP GTM / DNS for persistent Wide IPs
  • tcpdump on the listener may see DNS requests for the persistent Wide IP come in, but no response is sent.  Other DNS requests are working properly
  • Error messages

    After enabling the logging you can see a following for our DNS drops due to persistence table updates.:

      011ae03f:7: resolve3D: current value of reqInitState = Waiting for LDNS sync
      011ae025:5: UNRESOLVED rrtype = A, wip = help.f5.com, LDNS(x.x.x.x), Drop packet

    The reason behind packet drops is due to the persistent record updates among GTMs. When one system is receiving updates from the peers system it goes into "wait for sync" state (NOT ready) and will not be resolving the incoming queries for the duration on update period and this is the default behavior.

  • This can be problematic if all devices in the GTM/DNS sync group are unable to communicate via iQuery with each other.

Environment

  • GTM / DNS has Wide IPs configured with persistence
  • GTM / DNS iQuery mesh isn't fully "connected"
  • gtm.maxpersistsyncspersecond value may be too low

Cause

  1. Issues can be observed due to the iQuery mesh not fully connected, working state.  When one system is receiving updates from the peers system it goes into "wait for sync" state (NOT ready) and will not be resolving the incoming queries for the duration on update period and this is the default behavior.  This can be problematic if any of the devices in the GTM/DNS sync group are unable to communicate via iQuery with each other.

  2. This also could be because the gtm.maxpersistsyncspersecond value is too low.

    BIG-IP DNS persistence information is synchronized to each member of the BIG-IP DNS synchronization group by the gtmd process using the iQuery protocol. A BIG-IP DNS system's gtmd process sends persistence updates to the remote big3d process of another sync group member. When the remote big3d receives persistence information, it forwards the persistence update to its local gtmd process. The receiving gtmd then creates the appropriate persistence entry in memory and eventually the ldns.gz file.  The default is 800 per second.

    Another way you may experience this issue could be the gtm.maxpersistsyncspersecond database variable value is to low.

Recommended Actions

  1. Fix BIG-IP GTM/DNS iQuery mesh if they are not all connected and working properly.

  2.  Modify the "gtm.maxpersistsyncspersecond database variable"

    A BIG-IP DNS synchronization group is a collection of multiple BIG-IP DNS systems that share and synchronize configuration settings, including persistence information.

    BIG-IP DNS persistence information is synchronized to each member of the BIG-IP DNS synchronization group by the gtmd process using the iQuery protocol. A BIG-IP DNS system's gtmd process sends persistence updates to the remote big3d process of another sync group member. When the remote big3d receives persistence information, it forwards the persistence update to its local gtmd process. The receiving gtmd then creates the appropriate persistence entry in memory and eventually the ldns.gz file.

    You can use the gtm.maxpersistsyncspersecond database variable to control the rate at which gtmd sends BIG-IP DNS persistence updates to big3d. The default is 800 per second.

    # tmsh modify sys db gtm.maxpersistsyncspersecond value <value>

    This setting is based on two BIG-IP DNS systems in a sync group. An additional factor to the gtm.maxpersistsyncspersecond value is the number of BIG-IP DNS systems in the sync group. If there are more than two gtmd processes, the bandwidth allocated is automatically divided by N-1 (number of BIG-IP DNS systems in the sync group, minus one). For example, with three gtmd processes in a sync group, any one gtmd is allowed to send 400 persist updates per second (800 per second divided by 2 (3 members - 1) = 400 per second).

  3. Disable persistence on the WIPS.
    # tmsh modify /gtm wideip <record type> <wideip name> persistence disabled
    # tmsh save sys config

Additional Information

Data Gathering

Follow the steps below for each GTM/DNS devices within the GTM/DNS sync group

Enable HSL via GUI

  1. Enable HSL DNS logging to local-syslog (i.e. /var/log/ltm)
    1. There’s checkboxes in the Wide IP configuration in the gui to enable various decision logging levels
    2. Create a log publisher that delivers messages to local syslog
      System >> LOGS >> Log Publisher
    3. Create a DNS logging profile that sends to the Log Publisher created in step 2.
      Local Traffic >> Profiles>> Other >> DNS Logging
    4. Create a custom DNS profile that uses the DNS Logging profile created in step 3.
      Local Traffic >> Profiles >> Services >> DNS
    5. Modify the Listener(s) to use the new DNS Profile created in step 4.
  2. Proceed to Enabling Debug
Enable HSL via Merge
  1. Modify WIP(s) to enable LB Decision Logging
    1. Click into WIP
    2. Set 'General Properties" to "Advanced"
    3. Select the 'Load-Balancing Decision Log' items you want to see in the log
    4. Click Update
  2. Merge the following config snippet into your bigip.conf config using TMSH load sys config merge file /config/dnslogging.inc

    1. Using VI or Pico, copy-and-paste the following lines to file /config/dnslogging.inc on the BIG-IP.

      ltm profile dns /Common/DNS-Logging-LocalSyslog {
        app-service none
        defaults-from /Common/dns
        enable-logging yes
        log-profile /Common/Prof-HSL-DNS-LSYSLOG
      }
      ltm profile dns-logging /Common/Prof-HSL-DNS-LSYSLOG {
        enable-response-logging yes
        include-query-id yes
        log-publisher /Common/Publ-HSL-DNS-LSYSLOG
      }
      sys log-config publisher /Common/Publ-HSL-DNS-LSYSLOG {
        destinations {
         /Common/local-syslog
        }
      }

    2. Merge config into your bigip.conf config using TMSH load sys config merge file:

      # tmsh load sys config merge file /config/dnslogging.inc

    3. Modify the Listener(s) to use the new DNS Profile "DNS-Logging-LocalSyslog"
    3. Proceed to Enabling Debug
    Enabling Debug
    1. Enable debug GTM logging

      # tmsh modify sys db gtm.debugprobelogging value enable

    2. Enable gtm debug logging

      # tmsh modify sys db log.gtm.level value debug

    3. Enable big3d debug logging

      # tmsh modify sys db log.big3d.level value debug

    4. Enable gtm query logging

        # tmsh modify sys db gtm.querylogging value enable
    Reproduce

    1. Get tcpdump

      # tcpdump -nni 0.0:nnn -s0 -w /var/tmp/$HOSTNAME-DNS.pcap host <listener.ip.address> and port 53 -v

    2. Reproduce the issue

      # dig @<listener.anycast.ip.address> <wideip>

    3. Run script on GTM/DNS

      # while true; do date >> /var/tmp/$HOSTNAME-tmctl.txt;  tmctl -ai -c -d blade >> /var/tmp/$HOSTNAME-tmctl.txt; tmsh list sys db gtm.reqinitstate >> /var/tmp/$HOSTNAME-tmctl.txt; echo "Collecting tmctl stats. Press ^c to stop"; sleep 5; done

      Note: Above script collects tmctl stats every 5s. We need to run it to observe how different gtm relevant counters change.

      Keep the script and debug logging running for a few minutes whilst sending multiple queries to ALL GTMs' WideIP with persistence enabled and no persistence records so we trigger the problem. After a few minutes, please stop the script and the debug logging.
    Disable Debugging and Collect Data

    1. Run the following commands to disable debugging

      # tmsh modify sys db log.gtm.level value notice
      # tmsh modify sys db log.big3d.level value notice
      # tmsh modify sys db gtm.debugprobelogging value disable
      # tmsh modify sys db gtm.querylogging value disable

    2. Stop scripts and tcpdumps

    3. (Optional) Core gtmd

      # ps ax | grep gtmd
      # kill -6 <pid of gtmd process>

    4. Gather all qkviews (and core file if gtmd is killed)
