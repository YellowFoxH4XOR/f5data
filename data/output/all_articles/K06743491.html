Topic

You can configure the BIG-IP APM system as a Security Assertion Markup Language (SAML) Identity Provider (IdP) to provide inline single sign-on (SSO) for service providers (SP) not directly reachable by the client. The SP represents an application that you have that requires authentication. This may be content management systems (CMS) such as Microsoft SharePoint, learning management systems (LMS), accounting applications, and so on.

Description

With SAML Inline SSO, users authenticated through the BIG-IP APM system as SAML IdP can access resources outside of the APM webtop. BIG-IP APM also supports SP-initiated multi-domain SAML inline SSO.

Requirements for configuring APM as a SAML IdP for inline SSO

  1. The external DNS should point the apps/SP's hostname to the APM. For example, if the internal SP is named app.domain.com, it should resolve to the APM virtual server externally.
  2. After configuring the SP connector (preferably with metadata), edit and set its SP Location Settings to 
    1. 'Internal' - when Configuring BIG-IP as SAML IdP for inline SSO 
    2. 'Internal Multi-domain' - when Configuring BIG-IP as SAML IdP for multi-domain inline SSO
      1. Multi-domain Location - the scheme, hostname, and (optionally) port of the virtual server behind which this Service Provider is located, e.g. "https://app1.domain.com".
  3.  SSO is configured on Access Profile SSO/Auth Domains configuration page.
  4.  If using a webtop link, create a webtop link configured with the full URI with the app. For example, using simplesamlphp's default app, the full URI is https://app.domain.com/<default path>/module.php/core/authenticate.php?as=ssPHPSP2. The URL points back to the IdP (https).

SP-initiated inline SAML SSO

In this scenario, the BIG-IP system is configured in BIG-IP LTM+APM mode. Internal SP is located behind IdP's Virtual Server. The SP is referenced by the BIG-IP LTM pool members, whereas the BIG-IP system can be configured as SAML IdP or as both SAML IdP and SP.

BIG-IP as SAML IdP

When the BIG-IP system is configured as SAML IdP, the user is locally authenticated on the BIG-IP system. The following chart shows the flow for SP-initiated inline SSO with BIG-IP configured as SAML IdP.

Sequence

  1. The user attempts to access a resource protected by BIG-IP APM. BIG-IP redirects the user to /my.policy and starts access policy evaluation.
  2. BIG-IP APM authenticates the user.
  3. After successful authentication, the user resends the original request for the resource.
  4. The BIG-IP system load balances the user's request to one of the pool members associated with the accessed virtual server.
  5. If the user does not have a valid session, the internal SP (or the SAML-enabled application) initiates SAML SSO by generating an authentication request (AuthRequest) and redirects the user to the IdP.
  6. The redirect request forwards to the user.
  7. The user submits a request with the AuthRequest to the IdP.
  8. The IdP consumes the AuthRequest, and upon successful validation generates an assertion or artifact.
  9. The client's HTTP request (7) is modified as follows, and is released to the internal SP:
    • The authentication request is received through a GET request:
      • Request method is changed to POST for assertion and to POST/GET for artifact based on the matched assertion consuming service present in the configuration of service provider connector.
      • Host header is replaced with the host value extracted from the matched ACS URI of the internal SP.
      • Request URI is replaced with assertion consuming service URI path.
      • Content-length header is included, indicating the size of the POST body (assertion).
    • The authentication request is received through a POST request:
      • Host header is replaced with the host value extracted from the matched ACS URI of the internal SP.
      • Request URI is replaced with the ACS URI path.
      • Content-length header is adjusted to indicate the size of the POST body (assertion).
  10. The internal SP receives and validates the assertion from the IdP.
  11. Upon successful assertion validation (or artifact resolution), the SP provides access to the application. Alternatively, if the assertion validation fails, the application is expected to provide error(s) to the user.

BIG-IP as SAML IdP and SAML SP

When the BIG-IP system is configured as both SAML IdP and SAML SP, the BIG-IP system could user consume an assertion from an external IdP through the SAML Auth agent in the access policy. The following chart shows the flow for SP-initiated inline SSO with BIG-IP configured as both SAML IdP and SAML SP.

Sequence

  1. A user attempts to access a resource protected by APM. BIG-IP redirects the user to /my.policy and starts access policy evaluation.
  2. BIG-IP generates an authentication request (AuthRequest) and redirects the user to the external IdP for authentication.
  3. The user submits an authentication request to an external IdP.
  4. The external IdP authenticates the user.
  5. After successful authentication, the IdP generate an assertion and redirect the user to the BIG-IP system.
  6. The user posts the assertion to the BIG-IP system.
  7. The BIG-IP system validates and consumes the assertion.
  8. The BIG-P system redirects the user to the landing URI.
  9. The user resend the original request.
  10. The BIG-IP system forwards the the request to the internal SP.
  11. The internal SP generates another authentication request (AuthRequest) and redirects the user to the BIG-IP system.
  12. The redirect request is forwarded to the user.
  13. The user submits a request with the AuthRequest to the BIG-IP system.
  14. The BIG-IP system consumes the AuthRequest, and upon successful validation generates an assertion or artifact.
  15. The client's HTTP request (7) is modified as follows, and is released to the internal SP:

    • The authentication request is received through a GET request:

      • Request method is changed to POST for assertion and to POST/GET for artifact based on the matched assertion consuming service present in the configuration of service provider connector.

      • Host header is replaced with the host value extracted from the matched ACS URI of the internal SP.

      • Request URI is replaced with assertion consuming service URI path.

      • Content-length header is included, indicating the size of the POST body (assertion).

    • The authentication request is received through a POST request:

      • Host header is replaced with the host value extracted from the matched ACS URI of the internal SP.
      • Request URI is replaced with ACS URI path.
      • Content-length header is adjusted to indicate the size of the POST body (assertion).
  16. The Internal SP receives and validates the assertion from the BIG-IP.
  17. Upon successful assertion validation (or artifact resolution), the SP provides access to application and serves content to BIG-IP system.
  18. The BIG-IP system forwards the application content to the user.

Configuring BIG-IP as SAML IdP for inline SSO

To configure the BIG-IP system as SAML IdP for inline SSO, perform the following procedures:

Configure an access profile for SAML inline SSO

To configure an access profile to support the LTM-APM profile type and with single domain SSO for SAML inline SSO, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Access > Profiles / Policies .

    The Access Profiles (Per-Session Policies) page opens.

  3. Select Create.

    The New Profile page opens.

  4. For Name, enter a name for the access profile.
  5. For Profile Type, select LTM-APM.
  6. In SSO Across Authentication Domains (Single Domain mode), perform the following actions:
    • For SSO Configuration, select your SSO configuration.
    • Retain default settings for Domain Cookie (blank) and Cookie Options (with only the Secure check box selected).
  7. In Language Settings, add and remove accepted languages, and set the default language.

    A browser uses the highest priority accepted language. If no browser language matches the accepted languages list, the browser uses the default language.

  8. Select Finished.

Create a virtual server for SAML inline SSO

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Virtual Servers.

    The Virtual Server List page opens.

  3. Select Create.

    The New Virtual Server page opens.

  4. For Name, enter a unique name for the virtual server.
  5. For Destination Address, enter the IP address for a host virtual server.
  6. For Service Port, enter 443 or select HTTPS from the list.
  7. For HTTP Profile, verify that the default HTTP profile, http, is selected.
  8. For SSL Profile (Client) , in the Available list, select the name of the Client SSL profile you previously created and move the name to the Selected list.
  9. For SSL Profile (Server) , in the Available list, select the name of the Server SSL profile you previously created and move the name to the Selected list.
  10. Under Access Policy, in the Access Profile list, select the access profile that you configured earlier.
  11. Under Resources, for Default Pool, select the pool containing the SP IP address.
  12. Select Finished.

SP-initiated multi-domain inline SAML SSO

You can configure multi-domain inline SAML SSO when multiple SPs are located behind different virtual servers. All SPs share a single access profile with SAML assertions generated on request by the IdP which is the primary authentication virtual. A user should be able to connect to any one of SPs protected by the virtual servers that participate in the domain group, and be authenticated by the IdP. Subsequent connections to other SPs within the domain group should not require the users to authenticate.

Sequence

1. The user attempts to access the resource app1.domain.com located on virtual server 1 (VIP1) protected by the BIG-IP APM system.
2. VIP1 is configured for multi-domain SSO and redirects the user to the Primary Authentication URI "https://idp.domain.com" (VIP0) for authentication.
3. The IdP authenticates the user.
4. After successful authentication, the user is redirected back to VIP1.
5 - 6. VIP1 load balances the user request and directs it to one of the pool members.
7. Because the user does not have a valid session, the internal SP (or SAML enabled application) initiates SAML SSO by generating an AuthRequest and redirects the user to IdP.
8 - 9. The authentication request is forwarded through the user-agent to IdP (idp.domain.com).
10. The IdP consumes and validates the authentication request. Upon successful validation, a new SAML assertion and token are generated. The assertion is stored in session database, and the token SAMLtoken is sent back to the client through the HTTP-Redirect binding. The location of the original virtual is derived from the Referer header of request 8.
11 - 12. The user is redirected back to the application virtual server together with the SAMLtoken.
13 - 14. VIP1 consumes the SAMLtoken request and modifies the client request to inject a SAML assertion inline.
15. app1.domain.com validates and consumes the assertion.
16 - 17. Upon successful validation of the assertion, the application content is served to the user.
18 - 19. Because the user-agent already has a valid cookie for domain.com, the user request (18) is allowed to reach the pool member SP2 app2.domain.com.
20. However, since app2.domain.com does not have a valid session with the client, an authentication request is generated by the SP2 app2.domain.com.
21 - 22. The authentication request reaches IdP through the user-agent.
23 - 30. This sequence is similar to 10 through 17.
 

Configure BIG-IP as SAML IdP for multi-domain inline SSO

Configure an access policy for SAML multi-domain inline SSO

You configure an access profile to support the LTM-APM profile type and with single domain SSO for SAML inline SSO.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

Note: IdP objects assigned in multi-domain access policy (either in resource assign agent or in advanced resource assign agent) are applied to requests from all authentication domains.

Note: When Cookie Scope for application virtual in multi-domain SSO is set to Domain, the BIG-IP system also uses the SSO configuration (IdP object) configured for that domain in SSO Config attribute, provided Primary Authentication URI is in the same domain.

Note: When Cookie Scope for application virtual in multi-domain SSO is set to Host, the BIG-IP system ignores SSO config (IdP object) configured for that host when processing authentication request from the internal SP because SAML authentication requests are processed by the primary authentication virtual server hosting the IdP. Instead, IdP object(s) assigned in the access policy and access profile for Primary Authentication URI is applied when processing authentication requests from the internal SP.

Create a virtual server for SAML multi-domain inline SSO

For every domain, you should configure a virtual server. To create a virtual server for SAML multi-domain inline SSO, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

Configure BIG-IP APM as SAML IdP for SAML multi-domain inline SSO

  1. Log in to the Configuration utility.
  2. Go to Access > Profiles / Policies.
  3. Select an access profile to which you want to add SSO capability.
  4. The properties page for that access profile opens.
  5. Select SSO/Auth Domains.
  6. For Domain Mode, select Multiple Domains.
  7. For Primary Authentication URI, enter the URI to the IdP, for example, http://idp.domain.com.
  8. Each domain that you configure indicates the domain the Access Policy Manager session (established by the primary authentication URI) is bound to.
  9. In Authentication Domain Configuration, configure the Cookie setting by selecting Host or Domain, and entering the IP address for the host or, for domain, entering the fully qualified domain name.
  10. Select Cookie Options. By default, Secure is selected.
  11. For SSO Configuration, select the configuration that you want to associate to each host or domain. The default is None.
  12. Select Update.
  13. Log in to the Configuration utility.
  14. Go to Local Traffic > Virtual Servers.
  15. The Virtual Server List page opens.
  16. Select Create.
  17. The New Virtual Server page opens.
  18. For Name, enter a unique name for the virtual server.
  19. For Destination Address, enter the IP address for a host virtual server.
  20. For Service Port, enter 443 or select HTTPS.
  21. For HTTP Profile, verify that the default HTTP profile, http, is selected.
  22. For SSL Profile (Client) , in the Available list, select the name of the Client SSL profile you previously created and move the name to the Selected list.
  23. For SSL Profile (Server) , in the Available list, select the name of the Server SSL profile you previously created and move the name to the Selected list.
  24. Under Access Policy, in the Access Profile list, select the access profile that you configured earlier.
  25. Select Finished.

To configure the following tasks, refer to the Using APM as a SAML IdP (SSO portal) chapter of the BIG-IP Access Policy Manager: Authentication and Single Sign-On manual.
