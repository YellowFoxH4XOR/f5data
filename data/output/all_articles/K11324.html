Topic

An origin web server (OWS) can specify the secure flag when setting a cookie in the response to the client. The secure attribute specifies that the client should use secure means, such as Secure Sockets Layer (SSL), to contact the OWS when making a subsequent request and sending the cookie back to the server. Use the secure cookie attribute to prevent session hijacking.

RFC2109 states the following, regarding how the client may respond when receiving a cookie containing the secure attribute:

The user-agent may determine what level of security it considers appropriate for "secure" cookies. You should consider the secure attribute as security advice from the server to the user agent, indicating that it is in the session's interest to protect the cookie contents.

Some industry security practices require that cookies passed over an encrypted connection should have the secure attribute set. Modern browsers send a cookie with the Secure attribute to the server only in an encrypted request over the HTTPS protocol, not over unsecured HTTP (except on localhost).

Beginning in BIG-IP 12.0.0, cookie persistence profiles have a feature that allows an administrator to use the HTTP Cookie Insert method to set the secure cookie attribute for BIG-IP persistence cookies.

  • Configure the secure attribute for a cookie persistence profile
  • Use an iRule to set the secure attribute for one or multiple HTTP cookies

Configure the secure attribute for a cookie persistence profile

Note: In the cookie persistence profile, the Secure attribute is only applied to persistence cookies sent over SSL/TLS connection.

You can configure your BIG-IP cookie persistence profile to utilize the secure attribute using the Configuration utility or through the TMOS shell (tmsh)

To modify the secure attribute for an existing cookie persistence profile follow the following steps:

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Profiles > Persistence.
  3. Select the name of the cookie persistence profile.
  4. For Configuration select the Custom check box.
  5. Select the Custom check box for Secure Attribute.
  6. For Secure Attribute, select Enabled (default) or Disabled.
  7. Select Update.

To modify the secure attribute for an existing cookie persistence profile using tmsh use the following steps.

  1. Log in to tmsh.
  2. Use the following command syntax to disable the secure attribute:

    modify /ltm persistence cookie <profile name> secure disabled

    Note: Replace <profile name> with the cookie persistence profile name you want to modify. For profiles located in a partition other than the default (Common) prefix step 2 by changing directories to the specific partition, cd ../<partition name>. For example: cd ../Sales.  

    For example:

    modify /ltm persistence cookie Choclate_Chip secure disabled

  3. Use the following command syntax to enable the secure attribute:

    modify /ltm persistence cookie <profile name> secure enabled

    Note: Replace <profile name> with the cookie persistence profile name you want to modify. For profiles located in a partition other than the default (Common) prefix step 2 by changing directories to the specific partition, cd ../<partition name>. For example: cd ../Sales.

    For example:

    modify /ltm persistence cookie Choclate_Chip secure enabled

  4. Save the configuration modifications by entering the following command:

    save /sys config partitions all

Use an iRule to set the secure attribute for one or multiple HTTP cookies

You can use the HTTP::cookie secure iRules command to set the secure attribute for one or multiple HTTP cookies that the BIG-IP system returns to the client. In addition, your virtual server may reference a BIG-IP cookie persistence profile, which creates an additional BIG-IP cookie in the response to the client.

The following iRule uses the HTTP_RESPONSE event to add the secure attribute for all cookies returned in the server side response on the BIG-IP:

when HTTP_RESPONSE {
    foreach mycookie [HTTP::cookie names] {
    HTTP::cookie secure $mycookie enable
   }
}

Note: An iRule using the HTTP_RESPONSE event does not add the secure attribute to cookies generated from a client-side BIG-IP response, such as a 302 redirect or response issued directly from the BIG-IP system. 

To add the secure attribute for all cookies returned in all BIG-IP responses, including client side BIG-IP responses, use the HTTP_RESPONSE_RELEASE event similar to the following iRule:

when HTTP_RESPONSE_RELEASE {
    foreach mycookie [HTTP::cookie names] {
    HTTP::cookie secure $mycookie enable
   }
}

A typical HTTP response from the OWS may contain multiple Set-Cookie headers, as shown in the following example:

HTTP/1.1 200 OK
Connection: Keep-Alive
Date: Fri, 02 Nov 2009 21:32:30 GMT
Cache-Control: private
Content-Type: text/html; charset=utf-8
Set-Cookie: cookie-1; Path=/
Set-Cookie: cookie-2; Path=/

If you use an iRule similar to the previous examples, the resulting HTTP response header returned from the BIG-IP system to the client contains the secure attribute, and appears similar to the following example:

HTTP/1.1 200 OK
Connection: Keep-Alive
Date: Fri, 02 Nov 2009 21:32:30 GMT
Cache-Control: private
Content-Type: text/html; charset=utf-8
Set-Cookie: cookie-1;Secure; Path=/
Set-Cookie: cookie-2;Secure; Path=/
Set-Cookie: BIGipServercookie_test=20974090.36895.0000;secure; path=/

Note: The HTTP::cookie secure iRules command does not change a cookie that already has the secure flag set by the web server.
