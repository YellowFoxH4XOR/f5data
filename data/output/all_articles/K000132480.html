K000132480: Incorrect ASM policy enforcement on multi-blade system

Type
Support Solution
Published
2023-02-09
Updated
2026-07-17
Status
Legacy Content
Applies to
  • BIG-IP
  • BIG-IP ASM: 15.1.5
Source
https://my.f5.com/manage/s/article/K000132480

Description

  • After modifying an ASM policy you notice that some traffic is not enforced according to the new policy configuration
  • Some traffic follows the enforcement for the new configuration while other traffic appears to be enforced using the previous configuration

Environment

  • Multi-blade system
  • ASM policy configured and applied to a virtual server
  • ASM policy is changed (adding or removing signatures for example)

Cause

This issue is due to the csyncd process failing to sync the configuration across multi-blade systems. Different blades may service each inbound request so if the policy is consistent on blade 1 but was never synced to blade 2 and a unique requests is serviced by each blade then the enforcement applied to the request may be different.


 Recommended Actions

  • Test if files are syncing between blades:

# touch /ts/var/cluster/send/syncTestFile

- This will create a file with no content titled syncTestFile in the /ts/var/cluster/send/ directory. This is the directory that is synced across blades.

# clsh 'ls -l /ts/var/cluster/send | grep syncTestFile'

- This should be ran 1 minute after creating the test file.

- This will list all files titled syncTestFile in the /ts/var/cluster/send directory on each blade.

- If the file is present on all blades no further action is needed.


  • Follow the workaround noted in support solution "Csyncd can consume excessive CPU time (https://cdn.f5.com/product/bugtracker/ID1002969.html)"

Impact: The impact of disabling replication for the pamcache folder is that in the event of a primary blade failover, the new primary blade would not be aware of the existing valid auth tokens, so the user (eg, a GUI user, or a REST script already in progress at the time of the failover) would need to authenticate again.

# clsh "cp /etc/csyncd.conf /etc/csyncd.conf.$(date +%Y%m%d_%H%M%S)"

# clsh "sed -i '/run\/pamcache/,+2s/^/#/' /etc/csyncd.conf"

# clsh "bigstart restart csyncd"


Additional Information

Csyncd can consume excessive CPU time
