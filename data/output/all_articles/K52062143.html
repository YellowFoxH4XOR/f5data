Lack of resources and rate limiting

API requests consume resources such as network, CPU, memory, and storage. When there are no restrictions on the number, content, and type of requests made by users, an attacker can exploit this vulnerability. The following describe some of the techniques attackers can use:

  • Send a high volume of API requests to overload server resources.
  • Send specially crafted requests with large payloads or large file uploads or downloads that can hog server resources.
  • Make specific requests (such as uploading archived zip files that require significant resources to process) to overload server resources.

The lack of resources and rate limiting restriction can result in two kinds of impact:

  • The application server resources are insufficient to process the requests, resulting in slow application performance, and in some cases, becoming unresponsive, leading to a denial-of-service (DoS).
  • The high volume of API requests are crafted to quickly enumerate through large datasets. In the case where these datasets are credentials, a brute force authentication attack occurs and can lead to data leakage or even compromised accounts.

Lack of resources and rate limiting common weakness enumeration (CWE)

The following common weaknesses may increase the likelihood of attacks against your APIs:

  • CWE-307: Improper Restriction of Excessive Authentication Attempts
  • CWE-770: Allocation of Resources Without Limits or Throttling
  • CWE-1059: Insufficient Technical Documentation

Lack of resources and rate limiting attack scenario

In the following scenario an attacker manipulates the content of the API request, leading to a server response with an excessively large payload, resulting in slow application performance.

  1. An attacker sends a legitimate API request for a single page with 200 items.
  2. The attacker modifies the page size, increasing it from 200 to 200,000. 

This increase causes the application to return an excessive number of items in response to the query, consuming excessive server resources.

Secure your APIs against lack of resources and rate limiting attacks with F5 products

To protect your APIs, best practices recommend that you implement limits (CPU, memory, processes, and so on) on how clients can call your APIs and examine and validate client queries to ensure query strings and request that body parameters conform to your application schema, maximum size, and other requirements.

Use BIG-IP APM to mitigate lack of resources and rate limiting attacks

BIG-IP APM lets you implement resource and rate limiting security for your APIs in the following ways:

  • Configure limits based on entities such as Client ID, User Group, Client IP address, User Name, multiple values (like User Group and User Name), or a perflow variable name. This allows you to group API requests granularly by user, type of request, or any identifiable characteristics.
  • For your selected group of users or API requests, enforce rate limiting restrictions by setting Request Quotas, Spike Arrest values, or direct such requests to a different set of server resources.
  • Create allow/deny lists to allow or reject requests identified by key and key values.
  • Apply different weights to API requests based on key and key values.
  • For the quota, spike, or allow/deny lists you created, generate unique and appropriate responses.

Use NGINX products to mitigate lack of resources and rate limiting attacks

There are a variety of NGINX products that provide rate limiting security for your APIs in the following ways:

  • Configure the request rate limit based on NGINX parameters, such as client IP address ($binary_remote_addr), requested URI ($request_uri), and so on.
  • Define the size of the shared memory zone that buffers the excess requests beyond the configured request rate limit.

The following NGINX products provide the rate limiting controls to protect your API against lack of resources and rate limiting attacks.
