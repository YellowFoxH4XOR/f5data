Description

A tenant on rSeries (r5k or above) did not receive unicast traffic destined to its MAC address, but the traffic is observed in an F5OS capture.

Examination of show services and show service-instances output reveals that the tenant's service ID overlaps or conflicts with another tenant, and problems are still seen after stopping one of the tenants.

The FDB entry for the tenant also shows a different service ID.

The below example illustrates a possible manifestation of the issue, where the problem is experienced in VLAN 100 for tenant01.
The problem is observed because traffic for tenant01 matches the FDB entry pointing to service ID 12, but this is in use by tenant02, and tenant01 has a different service ID.

Environment

  • BIG-IP tenants on r5k or above
  • After config-restore

Cause

This problem can happen when a system database config-restore operation is performed with existing tenants in place, without first performing a system database reset-to-default.

Messages similar to the following will be observed in the output of docker logs system_network_manager, for one or more tenants:

Failed to find default service

The problem will persist across upgrades and tenant re-deployments. The system database config-restore that triggered the issue does not necessarily need to be recent; it may have been done some time in the past.

Recommended Actions

Do not perform a system database config-restore, without first performing a system database reset-to-default.

To recover from the problem state, delete and re-create affected tenants. Newly created tenants will be assigned a new service ID.

Review the FDB entries and service table to confirm that there are no conflicting service IDs and that the FDB entry points to the correct/expected service ID.
