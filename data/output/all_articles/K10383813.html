Description

This article explains the needed features and steps to enhance security policy IP Address Exception configuration by accepting FQDN. Security policy IP Address Exception feature allows the system to treat an IP address in a specific way for a security policy. For example, you can specify IP addresses from which the system should always trust traffic, IP addresses for which you do not want the system to generate learning suggestions for the traffic, and IP addresses for which you want to exclude information from the logs. You can use the IP address exception feature to create exceptions for IP addresses of your company's internal tools, such as penetration tools, manual or automatic scanners, or web scraping tools.

The workflow to achieve this enhancement is as the chart below describes:

Figure: Workflow to accept FQDN in Security Policy's IP Address Exception Feature.

Environment

  • Security Policy.
  • Bot Profile.
  • Custom bot signature.

Cause

Using security policy IP Address Exception feature alone doesn't support FQDN as an entry.

Recommended Actions

Perform the following procedure:

  • Create Custom Bot Signature
  • Create Bot Profile
  • Define Fictive Address In Security Policy's IP Address Exception feature
  • Enable Trust XFF Header In Security Policy
  • Create iRule to Handle Workflow

Create Custom Bot Signature

  1. Log in to the Configuration utility.
  2. Navigate to Security  ››  Bot Defense : Bot Signatures : Bot Signatures List page.
  3. Click Create.
    The Bot Signature Properties screen opens.
  4. In the Bot Name field, type a unique name for the bot signature.
    Note. If you attempt to create a custom bot signature with the same name as a system-supplied signature, you will receive an error and the signature will not be created.
  5. In Bot Category field, select Seach Engine in order for the system to perform identity validation using reverse DNS lookup.
    Note. You must configure a DNS server and a DNS resolver before configuring a Bot Defense profile, as the profile requires these two items to work.
  6. In Rule setting, for User-agent, select either contains or regexp match, and then type the pattern in the text box.
    Note. If there are multiple possible user agents, a signature can be created for each or one signature for all.
  7. In the Domains field, type the name of one or more domains from which the bot can send its requests, and click Add.

Create Bot Profile

Note. If using an existing bot profile is preferable, ensure the search engine bot signatures are enabled and Trusted Bot Mitigation isn't set to block, then skip this step.

  1. Navigate to Security  ››  Bot Defense : Bot Defense Profiles.
  2. Click Create.
    The Bot Profile Configuration screen opens on the General Settings tab.
  3. Enter Profile Name.
  4. In Profile Template, select Relaxed.
  5. Click Save.

Define Fictive Address In Security Policy's IP Address Exception feature

  1. Within Security Policy's centralized IP Address Exceptions list, Click Create. 
  2. In the IP Address field, type a fictive IP address that you want the system to trust, e.g 10.200.200.200.
  3. Select desired IP Address Exception Properties. 
  4. Click Add.
  5. Click Apply.

Enable Trust XFF Header In Security Policy

  1. Within Security Policy's General Settings/Properties, Navigate to Advanced Settings. 
  2. Enable Trust XFF Header Setting.
  3. In the Custom XFF Headers setting, type the XFF header that the system should trust, e.g  X-Fake-Scanner-IP.
  4. Click Add.
  5. Click Save Changes.
  6. Click Apply.

Create iRule to Handle Workflow

  1. Navigate to Local Traffic  ››  iRules : iRule List.
  2. Click Create.
  3. Add the following iRule code and adjust it as needed:
    when BOTDEFENSE_ACTION {
        # XXX is the name of Custom Bot Signature where FQDN is defined.
        if { [BOTDEFENSE::bot_name] eq "XXX" } {
              # X-Fake-Scanner-IP is Trusted XFF Header In Security Policy.
              # 10.200.200.200 is Fictive Address In Security Policy IP Address Exception setting.
              HTTP::header insert X-Fake-Scanner-IP "10.200.200.200"
           }
        }
    when ASM_REQUEST_DONE {
        if { [HTTP::header exists "X-Fake-Scanner-IP"]} {
            HTTP::header remove "X-Fake-Scanner-IP"
           }
        }

    Note. If the true scanner address is important, you can preserve it in another header, e.g X-True-Original-IP which you can also populate in the same iRules event.
