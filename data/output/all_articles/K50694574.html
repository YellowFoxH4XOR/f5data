Description

Pool member up/down can't be predicted. It is difficult to capture problematic monitor traffic because the problem occurs rarely  and randomly. 

  • Pool members or nodes were up/down.
  • Concern about disk limitation during running tcpdump
  • The logs maybe rotated when collecting QKView

Environment

  • BIG-IP
  • Pool members or nodes
  • Monitor

Cause

Pool members were marked down  rarely  and randomly. It is difficult to capture problem by only running tcpdump.

Recommended Actions

Stop running tcpdump and collect log files when the problematic pool member is marked down.

  1. Login and go to bash

  2. Run tcpdump to capture monitor traffic. The command will produce 5 tcpdump file, each one is around 100M bytes. 

    nohup tcpdump -ni 0.0 -s 0 host <self-ip> and host <pool-member-ip> -w /var/tmp/<file-name>.pcap -C 100 -W 5 &

  3. Run a script to stop tcpdump and collect log file when seeing a log with "pool_server_01: down".

    Refer to K14397: Running a command or custom script based on a syslog message
    1. Add the following to /config/user_alert.conf:

      alert oracle_monitor_down "pool_server_01: down" {
      exec command="sleep 10";
      exec command="/bin/bash /var/tmp/capture_monitor.sh > /dev/null 2>&1 &";
      }

    2. Create a /var/tmp/capture_monitor.sh script with the following syntax:

      #!/bin/bash
      if [ -f /var/tmp/monitor.flag ]
      then
        rm -f /var/tmp/monitor.flag
        killall tcpdump
        tar -czPf /var/tmp/logFiles.tar.gz /var/log/*
      fi

  4. Create flag to check if this scrip has been run ever.

    touch /var/tmp/monitor.flag

Additional Information

We are able to collect QKView after the problem if we need.
The pool member or node may be flapping, but we only capture problem at the first time.
