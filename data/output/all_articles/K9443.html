Known Issue

This is the result of a known issue. When you create a packet filter rule on the VIPRION primary blade, the rule is not propagated to secondary blades. This behavior can result in packet filter rules not enforcing an access policy on traffic being processed by secondary blades.

For example, a packet filter defined on the VIPRION system can be displayed by running the following command:

bigpipe packet filter

The command output appears similar to the following example:

PACKET FILTER
+-> ALLOW TRUSTED
    |     VLANs: none
    |     IP addresses: none
    |     MAC addresses: none
+-> PACKET FILTER AllowTest   ORDER 25   accept   0 hits
|   |     { ( proto TCP ) and ( dst host 10.10.10.1 ) and ( dst port 80 ) }

When running the same bigpipe packet filter command from the secondary blade, the command output does not display a packet filter.

For example:

PACKET FILTER
+-> ALLOW TRUSTED
    |     VLANs: none
    |     IP addresses: none
    |     MAC addresses: none
No packet filter rules were found.

Note: It is not possible to define the packet filter separately on the VIPRION secondary blade.

F5 Product Development is tracking this issue as CR110881 and it was fixed in BIG-IP 10.0.0. For information about upgrading, refer to the BIG-IP LTM release notes.

This issue still exists in the BIG-IP LTM 9.6.x software branch.
