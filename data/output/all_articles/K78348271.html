Description

When observing the persistence table on a multi-bladed vcmp guest, mirrored persistence entries show up on secondary blades but are identified as owner entries.

The Persist table will show the same persist record entries existing on multiple slots. There should be one Owner entry, and the rest are Mirrored entries. These entries are not identified as mirrored entries (ID 767329).
Additionally, you will see the Mirrored persist record disappear and re-appear while the Owner entry remains. This exhibits as a flapping behavior (ID 767397).

When the Mirrored entry re-appears it will have the same timeout as the owner entry.  This can cause confusion when troubleshooting persistence issues.
The entry that is honored is the record on the primary blade, or the record with the Owner entry identified in the table, and not a Mirror entry.

Environment

  • LTM
    • UIE persistence
      • Mirroring enabled in the persistence profile
  • VCMP
    • ????Multi-blade guest

Cause

  • Bug ID 767397: tmsh does not consistently display persistence records present on non-primary blades
  • Bug ID 767329: Mirrored persistence records are not identified in tmsh output


Recommended Actions

  1. To verify ID 767329 , you can run the following script to review the persistence entries. Note the second persist record with the same key, client, and node. It should be identified as a mirrored entry.

    # while true; do echo "############### `date` ##############"; clsh --slot=1,2 tmsh show ltm persistence persist-records mode universal key 00-50-B6-CC-6A-12 all-properties; sleep 1; done

Additional Information
The Secondary entry (identified as blade 2) should be identified as a Mirrored entry instead of an Owner entry.  ID 767329 Should resolve this issue.  ID 767397 is identified as an inconsistency with tmsh and should always show the secondary entries.
