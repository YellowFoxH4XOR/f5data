Description

  • What is the purpose of the idle time out that is under domains name
  • and also the HTTP Load Balancer idle timeout, the one from the origin and routes.
  • how each idle timeout inside of the Load Balancer?
  • explanation for each idle timeout

Environment

  • F5® Distributed Cloud Load Balancer

Cause

Different idle timeout settings exist within the F5 Distributed Cloud Load Balancer to control how long connections or requests are kept open when there is no activity. These timeouts are necessary to efficiently manage resources, prevent resource exhaustion, and ensure proper connection handling for both downstream (client to proxy) and upstream (proxy to origin) traffic.

Recommended Actions

  • https.connection_idle_timeout (default: 120s): specifies the maximum duration the downstream TCP connection can remain inactive before it is closed.
  • more_option.idle_timeout (default: 30s): specifies the maximum duration of a HTTP transaction between downstream client and upstream server.  An HTTP request not receiving a response within this timeout period will receive a 504 error with no_healthy_upstream.
  • routes.advanced_options.timeout (default: 30s): specifies the maximum duration of a HTTP transaction, including any retries.  It is effectively the same timeout as more_option.idle_timeout but applied at the Route level and effective on requests hitting that Route.  The lower timeout value between LB and Route takes precedence in case of conflict.  When Retry Policy is used, the Route-level timeout should be greater than (no_of_retries * (retry_timeout + retry_interval))
  • origin_pool http_idle_timeout:  idle timeout for the upstream connection pool, where in the same upstream connection would be interleaved for multiple HTTP requests. Make sure this timeout is lesser than the http-keepalive timeout configured on your Origin Server.

Additional Information

Downstream vs. Upstream

Assuming a typical reverse proxy data path:

  • Downstream: flows between clients and the proxy
  • Upstream: flows between the proxy and origin servers
