Description

All ASM Event Logs no longer exist in the GUI. If you fail over to the peer F5 device, you can find the new Active device can show the event logs.
No matter if you force load mcpd and reboot per K13030: Forcing the mcpd process to reload the BIG-IP configuration, or restart these services (asm_config_server, asmlogd, pabnagd) per K48313113: Troubleshooting ASM logging issues, the BIG-IP ASM is still not able to display any event logs.

You can in fact see many log entries from the database by running the following command in the CLI:
$mysql -uasm -p`perl -MF5::Cfg -e 'print F5::Cfg::get_mysql_password()'` -e "select COUNT(*) from PRX.REQUEST_LOG"
or
$mysql -uasm -p`perl -MF5::Cfg -e 'print F5::Cfg::get_mysql_password()'` -e "select * from PRX.REQUEST_LOG"

 

Environment

  • ASM logging profiles are attached to Virtual Servers
  • Be able to verify traffic would trigger ASM security policy and generate log entries

Cause

The log entries indeed exist in the device's database. It is most likely running into this issue: 
Bug ID 746682: ASM unable to display *any* event logs, unless they are searched for by support ID

Recommended Actions

Reset the tables REQUEST_LOG_PROPERTIES and REQUEST_LOG_CLEARED by running the following commands:

# mysql -t -u root -p$(perl -MPassCrypt -nle 'print PassCrypt::decrypt_password($_)' /var/db/mysqlpw) -e "truncate PRX.REQUEST_LOG_PROPERTIES"
# mysql -t -u root -p$(perl -MPassCrypt -nle 'print PassCrypt::decrypt_password($_)' /var/db/mysqlpw) -e "truncate PRX.REQUEST_LOG_CLEARED"

 This is not a service-affecting procedure. It can be deployed during regular hours.
