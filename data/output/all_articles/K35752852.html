Description

Associating an address list to the virtual server on UI makes it appear wildcard in CLI.

Before source address list association:
ltm virtual /Common/Traffic_match_VS {
    creation-time 2022-07-04:02:31:06
    destination /Common/192.168.1.100:80 <<<
    ip-protocol tcp
    last-modified-time 2022-07-04:02:31:06
    <truncated for brevity>
    serverssl-use-sni disabled
    source 0.0.0.0/0 <<<
    translate-address enabled
    translate-port enabled
}

After source address list association:
ltm virtual /Common/Traffic_match_VS {
    creation-time 2022-07-04:02:31:06
    destination :any <<<
    ip-protocol tcp
    last-modified-time 2022-07-04:02:35:26
    <truncated for brevity>
    serverssl-use-sni disabled
    source 0.0.0.0/0 <<<
    traffic-matching-criteria my_traffic_match  <<<
    translate-address enabled
    translate-port enabled
}

Traffic Matching Criteria:
ltm traffic-matching-criteria my_traffic_match {
    destination-address-inline 192.168.1.100
    destination-address-list none
    destination-port-inline http
    destination-port-list none
    <truncated for brevity>
    source-address-inline 0.0.0.0
    source-address-list test_add_list <<<
}

Environment

  • Address list
  • Traffic-matching-criteria

Cause

Associating an address list in UI attaches the traffic matching criteria in question to the virtual server, which causes the CLI/Config to appear as if the virtual is a wildcard one when it is not. If you look closely, you should see traffic matching criteria associated to the virtual, which in turn has the address list configured under it.

Recommended Actions

This is expected behavior, and you shouldn't see any functional issues.
However, the virtual servers involved wouldn't appear if you filter the virtual server listing using an IP address.
