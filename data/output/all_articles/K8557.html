Known Issue

This is the result of a known issue. A RAM Cache entity for an existing cached resource can be updated with an incorrect vary value.

When a response for an entity with a different vary value in the RAM Cache is received, the resource owning the entity is invalidated. If the response is determined to be un-cacheable, the resource is left in the RAM Cache with an updated vary value, but no entities. If another request is made, but the response is compressed, the response will be placed into the cache with no vary value. As a result, client requests for uncompressed responses will receive compressed responses.

For example:

  • Client A issues an HTTP 1.0 request for an uncompressed document. The document is currently in the RAM Cache as a compressed document. Due to this issue, the compressed document is removed.
  • Client B issues an HTTP 1.1 request for the compressed version of the document client A requested. The server responds with the request, but the RAM Cache inserts the compressed version of the document into the cache with an empty vary value header.
  • Client C issues an HTTP 1.0 request for the uncompressed version of the document. However, due to the incorrect behavior of the RAM Cache, requests from client C and subsequent requests for the uncompressed version will receive the compressed version until the document expires.

If another client requests the compressed version of the document, the RAM Cache will update the cache with a new copy of the compressed document. Additionally, the RAM Cache will insert the correct vary header value.

F5 Product Development tracked this issue as CR95133 and it was fixed in BIG-IP LTM 9.4.5. For information about upgrading, refer to the BIG-IP LTM Release Notes.

Additionally, this issue was fixed in Hotfix-BIG-IP-9.4.4-HF1 issued for BIG-IP 9.4.4, in Hotfix BIG-IP-9.4.3-HF4 for BIG-IP 9.4.3, and in Hotfix-BIG-IP-9.3.1-HF3 issued for BIG-IP 9.3.1. You may download these hotfixes or later versions of these hotfixes from the F5 Downloads site.
