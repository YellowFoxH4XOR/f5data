Description

Insecure deserialization describes the act of taking untrusted serialized data and consuming that data without ensuring that it is valid, which may allow for attacks such as remote code execution, privilege escalation etc.

Environment

A web application being delivered to a web browser on a client device (e.g., Chrome, Edge, Firefox etc), though many other applications also use serialization, we are only discussing web applications.

Cause

  • A web application which does not properly validate, filter or sanitize user input

Recommended Actions

It is possible to mitigate many deserialization attacks against web applications using BIG-IP Advanced WAF, NGINX App Protect, Silverline WAF etc to block potentially malicious user input from being ingested and deserialized by the web application. Specific instructions are outside of the scope of this document as any policy must be tailored to the web application in question.
 
If you are concerned about a known deserialization vulnerability in the BIG-IP Configuration the best mitigation is to ensure your administrators:
  • Access the Configuration Utility from a dedicated management host, jump box or another controlled environment
  • Do not click on links to access the Configuration Utility but rather enter the address manually or use a bookmark

Additional Information

Serialization is the act of converting native object data held within an application into a format that can be restored later and is easier to transmit across a network link or save out to a storage system not native to the application (e.g., to store in a database).

Deserialization, therefore, is the act of converting that serialized data back to the native object format used by the programming language or application framework.

In modern applications data is often serialized into JSON format, though XML is also a common format used by older frameworks. Many programming languages also offer native functionality for serializing and deserializing structures (e.g., “pickle” in Python). Use of native functionality is not a mitigation for insecure deserialization as most languages operate on the basis that any validation of input will have been done prior to the call to deserialize the input.

Since serialization deals with entire objects, it may be possible to serialize malicious code and inject that serialized data into a vulnerable application. Constructed correctly, the malicious code will then be called without any further interaction being required, when the target application deserializes the data and instantiates the resulting object in memory.

In recent years this attack has been common against Java based server-side applications.
 
Mitigations
 
Application-side mitigations for injection attacks are:
  • Sign & seal any serialized data to ensure the data is not modified in transit (e.g., using HMAC)
    • Note that this assumes the sender has not been compromised and that modification takes place in transit (e.g., a person-in-the-middle attack)
  • Use a safe mechanism to reconstruct the data, e.g., populate a new object with data retrieved from the serialized representation rather than re-instantiating the serialized object.

You can also use a Web Application Firewall such as Advanced WAF, ASM, NGINX App Protect etc to:
  • Check user inputs against signatures of known vulnerabilities in web frameworks & applications
  • Validate JSON and XML
 
A combination of both methods for a Defence-in-Depth posture is highly recommended.
