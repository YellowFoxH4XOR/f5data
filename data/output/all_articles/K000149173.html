Security Advisory Description

When name-based virtual hosts are configured to share the same IP address and port combination, with TLS 1.3 and OpenSSL, a previously authenticated attacker can use session resumption to bypass client certificate authentication requirements on these servers. This vulnerability arises when TLS session tickets are used and/or the SSL session cache is used in the default virtual server and the default virtual server is performing client certificate authentication. This issue affects both the NGINX http and NGINX stream modules. (CVE-2025-23419)

Impact

This vulnerability can lead to the exposure of resources or functionality to unintended actors, possibly providing attackers with limited access to sensitive information. There is no control plane exposure; this is a data plane issue only.

Note: This issue only impacts NGINX OSS compiled with OpenSSL as the crypto library and NGINX Plus. NGINX OSS compiled with LibreSSL or BoringSSL is not vulnerable to this issue. NGINX Plus is only compiled with OpenSSL.

If the Fixes introduced in column does not list a version for your branch, then no update candidate currently exists for that branch and F5 recommends that you upgrade to a version with the fix (refer to the tables).

If the Fixes introduced in column lists a version prior to the one you are running, in the same branch, then your version should have the fix.

Mitigation

To mitigate this vulnerability, F5 recommends that you ensure that each server block in the NGINX configuration is configured with a unique IP address and port combination, using the listen directive. This avoids the system sharing SSL session state when the configuration lacks an explicitly defined default virtual server. For more information about the listen directive, refer to https://nginx.org/en/docs/http/ngx_http_core_module.html#listen. Alternatively, if you cannot configure separate server blocks with unique IP address and port combinations, F5 recommends that you configure a default stub server that does not perform client authentication. Additionally, F5 recommends that the server blocks that are used for client authentication perform authorization checks for the correct client certificate values of the embedded variables $ssl_client_s_dn and $ssl_client_i_dn. If you cannot  perform any of these changes, you can, optionally, disable TLS 1.3 in your server configuration. To perform these procedures, refer to the following examples:

Note: The stub server and authorization check mitigations apply only to use cases with the NGINX http module. These mitigations do not work for use cases where the NGINX stream module is used.

  • Create a default stub server
  • Perform authorization checks for client certificate values
  • Disable TLS 1.3 in each server block

Create a default stub server

Create an explicit default stub server that does not perform client authentication.

Note: For customers using client authentication in multiple name-based virtual servers that use the same IP address and port combination, F5 recommends that you use the following configuration in addition to applying the fixed version.

Impact of actions: Performing the following procedure should not have a negative impact on your system.

Example stub server with SSL handshake and client authorization disabled:

server {
  listen 443 ssl default_server;
  ssl_reject_handshake on;
  ssl_verify_client off;
  ssl_protocols TLSv1.2 TLSv1.3;
}

For more information about how NGINX processes a request with the default_server parameter of the listen directive, refer to https://nginx.org/en/docs/http/request_processing.html.

For more information about the ssl_reject_handshake and ssl_verify_client directives and their default states, refer to:

  • https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_reject_handshake
  • https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_verify_client

Perform authorization checks for client certificate values

Perform authorization checks for the correct client certificate values of the embedded variables $ssl_client_s_dn and $ssl_client_i_dn.

Note: For customers using client authentication in multiple name-based virtual servers that use the same IP address and port combination, F5 recommends that you use the following configuration in addition to applying the fixed version.

Impact of actions: Adding the additional authorization check may result in a slight decrease in performance. F5 recommends that you test any changes during a maintenance window and consider the possible impact on your specific environment.

Example server configuration block that performs authorization checks against the expected subject DN ($ssl_client_s_dn) of the client certificate for the established SSL connection:

server {
  listen 443 ssl;
  server_name example.org;

  ssl_client_certificate org.crt;
  ssl_verify_client on;

  if ($ssl_client_s_dn != "CN=clientA,O=siteA,L=City,C=DE") {
    return 403;
  }
}

For more information about the $ssl_client_s_dn and $ssl_client_i_dn embedded variables, refer to https://nginx.org/en/docs/http/ngx_http_ssl_module.html#variables.

Disable TLS 1.3 in each server block

If you cannot make the recommended changes listed previously, you can disable TLS 1.3 in your server configuration. TLS 1.3 is enabled, by default, beginning in NGINX Plus R29 and NGINX OSS 1.23.4.

Impact of actions: Removing TLS 1.3 from your configuration may prevent certain clients from connecting. F5 recommends that you test any changes during a maintenance window and consider the possible impact on your specific environment.

To disable TLS 1.3, use the ssl_protocols directive to specifically add the protocol versions that your app supports, and remove protocol version 1.3.

For example:

server {
  listen 443 ssl;
  ssl_protocols TLSv1.2 TLSv1.3;

  ...
}

Would become:

server {
  listen 443 ssl;
  ssl_protocols TLSv1.2;

  ...
}
