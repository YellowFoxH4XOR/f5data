Description

External monitors can significantly increase CPU usage and impact ability of the device to function properly.
Warning: Changes in monitors CPU utilization may be multiplied to have a significant effect depending on your configuration, especially when a monitor configuration may be used by hundreds or thousands of nodes and pool members in the configuration.

Environment

  • BIG-IP
  • External monitor - not implemented within the bigd monitoring process. Examples include type external, LDAP, SMTP, POP3. 
  • CPU

Cause

External monitors can cause high CPU impacting performance of device.

Recommended Actions

Note: F5 Support does not design or configure external monitors.  If you are in need of any assistance configuring an external monitor to best work for your environment, F5 Professional Services and/or DevCentral can assist.
  1. Where possible use an built in monitor instead of an external monitor
  2. Test external monitors on a test system before deploying in production
  3. Have techniques to measure CPU impact when deployed

Additional Information

One technique for measuring the collective CPU Impact of all external monitors spawned by the monitoring process bigd (those not internally implemented within it) is below.

Note: While top can be used to monitor CPU of long lasting processes, external monitors are usually ephemeral and top is unlikely to be useful. Since the external monitors are not running within bigd there is no need to monitor the CPU use of bigd itself which will only increase slightly with overhead to spawn external monitors.

Standby systems should have same monitor use as active systems so may be most suitable for tests.
Cut and paste the following small script into a good text editor, including the line starting with END.
Remove any extraneous formatting, and then from there to a bash shell session on the BIG-IP.

perl <<"END"
  $n=6; $d=10; 
  $n++; 
  while($i<$n) {
    ($ut,$st)=split(/\s+/,`tmctl proc_pid_stat -qs cutime,cstime proc_name=bigd`); 
    if($i) {
      printf "%d%%\n",($ut+$st-$last)/$d;
    }
    else{
      $fi=$ut+$st; $ft=time;
    }
    $last=$ut+$st; $i++; 
    if($i<$n) {
      sleep($d);
    }
     else {
      printf "Average over %d seconds: %d%%\n",time-$ft,($last-$fi)/(time-$ft);
    } 
  }
END

This runs six times at intervals of 10s, and those values can be modified. A longer run time will give a slightly more accurate result.
Output will look like this:

39%
33%
40%
39%
33%
38%
Average over 60 seconds: 37%

Note: 100% would be equivalent to one CPU core fully utilised. Small vCMP guests may have one control plane CPU core, but most systems will have more. It's perfectly possible the CPU use could be above 100% on larger systems.

Note: This script has some limitations. It will only show the CPU use of external monitors spawned by the first bigd process. Larger systems may have multiple bigd processes on a blade or appliance, and multi-bladed systems will have bigd  processes on each blade. Since external monitor instances will be distributed among the bigd instances  it should be possible to scale up the result to the number of bigd processes with reasonable accuracy. The source of the CPU use data is a statistics table that is only updated every 10s normally. If you set a delay less than 10s then most values will shows as 0% even though external monitors may be using CPU at that time. The overall average should be fine though if enough samples are taken. Running for a minute or more, or at least for several iterations of the monitor (interval) of interest is recommended.

If the CPU use is high then suspect monitors can be tested using the time technique below or modified to run less frequently by increasing interval (and timeout) or maybe replaced by a simpler monitor (TCP will often be suitable), and the CPU use retested.

It should also be possible to time the execution of a monitor script in a similar way to below.
The monitor script file will usually be found in the appropriate partition of the filestore. The example beneath is in the Common partition. Use quotes to deal with the embedded colons within the file name.
bigd will supply some arguments to the script when executing it. In the simplest case this will be an IPv6 encoded pool member IP address and port number. 

 time "/config/filestore/files_d/Common_d/external_monitor_d/:Common:badmonfile_44113_1" ::ffff:10.2.2.2 80
UP

real    0m0.496s
user    0m0.475s
sys     0m0.004s

In this example a single execution of the external monitor used 0.5s of CPU time - a very expensive monitor. Only a few instances of these would overload a typical small system. Monitors should use low milliseconds or less to be scalable.
