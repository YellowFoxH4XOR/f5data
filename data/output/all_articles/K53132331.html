Description

Environment

  • BIG-IQ 7.0.0

Recommended Actions

  1. Check if the license have been reactivated, running on each device
    restcurl /tm/shared/licensing/registration | jq .serviceCheckDateTime
     
  2. Alternatively you can also run on the CM:
    for i in `restcurl /shared/resolver/device-groups/cm-esmgmt-logging-group/devices/ | jq -r '.items[]|select(.properties.isLoggingNode == true)| .uuid'`; do echo -n "${i} : "; restcurl /shared/resolver/device-groups/cm-esmgmt-logging-group/devices/${i}/rest-proxy/mgmt/tm/shared/licensing/registration | jq .serviceCheckDateTime; done
     
  3. Look specifically at this portion of the output, they should be different.
    restcurl cm/shared/esmgmt/cluster

    Example:
    "primaryMachineId"      : "8c2d3fc3-e935-4b32-9f1d-6b40a8104555",
    "secondaryMachineId" : "8c2d3fc3-e935-4b32-9f1d-6b40a8104555",
To resolve this issue, you need to failover to the secondary BIG-IQ (failback if desired) and then rerun the preUpgradeCheck script. Once the failover is complete, please run the above restcurl command from bash to ensure that both of the machine IDs listed above are present and correct.

To complete the failover using the Big-IQ CM UI
  1. Log on to the Configuration utility.
  2. Go to System > BIQ-IQ HA.
  3. Click BIG-IQ HA Settings.
  4. Promote next to the name of the standby BIG-IQ.
  5. Repeat these steps as needed to failback to the original primary.

Note: At this point the original script should run to completion without additional errors. If so, you can proceed with the upgrade process. It is important to note that breaking HA is required prior to starting the upgrade. Unfortunately, simply breaking HA does not resolve the problem with the above record.
