Description

  • Would like to clarify the licensing model for Nginx Ingress Controller [KIC] subscription.
  • Currently, the subscription shows " NGINX Plus Ingress Controller (per instance)"
  • Does per instance mean the allowed number of Nginx Ingress master processes?


  • For example


 Environment

  • Licensing
  • Nginx Ingress Controller

 Cause

  • Ingress controller works to marry/bridge Kubernetes environment with that of a load-balancer
  • The ingress controller is a deployment, usually with a replica set of one for a given cluster
  • If we modify the number of replicas say from one to three
    • Then, there would be ONE ingress controller out of the many replicas we created that would be elected as a leader and responsible for updating the load balancer
    • The process of electing a leader helps eliminate conflict between the many ingress controller replicas at a time of updating the load balancer
    • https://github.com/nginxinc/kubernetes-ingress/blob/master/deployments/helm-chart/values.yaml#L269
  • The presence of multiple ingress controller instances does however increase the availability of the ingress as it is already up and running in multiple nodes, if a node where the leader elect resides becomes unstable
  • Also, by default, Nginx Ingress controller works in any namespace of a given cluster [ cluster wide]

 Recommended Actions

  • None

 Additional Information

As said above, irrespective of how many ingress controllers instances created in a cluster, we would only have one controller responsible for managing and reflecting K8S deployment onto the load-balancer. This means the function of updating the load-balancer falls onto a single instances of the ingress controller. This, however, DOES NOT mean the use of a SINGLE instance of the license. If the license indicates PER INSTANCE as shown in the figure, then this means we would count the instances of the pod created irrespective of the status of the ingress, that is, leader elect or passive Ingress. In other words, each of the instances NGINX IC (NIC) POD in which the deployment creates is counted against available/subscribed quantity.


apiVersion: apps/v1

kind: Deployment

metadata:

annotations:

deployment.kubernetes.io/revision: "3"

name: nginx-ingress-controller

namespace: ingress-space

spec:

replicas: 8 < --- desired number of ingress pods/instances in a cluster

selector:

matchLabels:

name: nginx-ingress


So, from the above figure with a quantity of 48, if a deployment/daemonset creates 8 pods of the NIC in a given cluster, then we would have 40 remaining. So the elected leader concept does not factor into the licensing equation. In short, it would be pointless to create multiple instances of the ingress in a cluster, since only one of them would be active while at the same time reducing/consuming the number of available instances that can be created in another cluster. Also the controller is created as part of deployment, if a node where the primary ingress controller resides experiences an issue, then a new instance of the ingress would be created on another node and in this way we minimize license utilization. Please note the discussion above applies for PER INSTANCR type of license. Finally and while on the topic, we have a new type of license called " Microservices ". Microservices is designed to account/work with NODES rather than focus on the number of POD instances in a cluster. Microservices removes the need to track number of pods in a cluster altogether
