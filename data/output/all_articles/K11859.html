K11859: External data groups configured as read-only do not load correctly on secondary VIPRION blades after a reboot or service restart

Known Issue

This is the result of a known issue. External data groups configured as read-only do not load correctly on secondary VIPRION blades after a reboot or service restart.

Consider the following example:

  • The following data group is created on the primary blade:

    class my_acl {
    type ip
    filename "/config/acl"
    mode read
    }
  • The configuration is automatically synchronized to all secondary blades in the chassis.
  • At this point, if one of the secondary blades is rebooted or its services are restarted, the blade will fail to load the configuration and will remain in an inoperative state.

    When this issue occurs, messages that appear similar to the following example are logged to the /var/log/ltm file:

    err mcpd[17358]: 01070631:3: The class (my_acl) is read-only.
    err mcpd[17358]: 01070969:3: File cache: (Rolling back on error 17237553) (FileCache.cpp:1671)
    err mcpd[17358]: 01070734:3: Configuration error: Configuration from primary failed validation: 01070631:3: The class (my_acl) is read-only.

    Additionally, some BIG-IP daemons will restart continuously.

F5 Product Development is tracking this issue as ID 337404.

This issue does not affect BIG-IP versions 10.1.0 and later.

Workaround

You can work around this issue by setting the access mode of the affected data group to Read/Write. To do so, perform the following procedure:

  1. Log on to the Configuration utility of the VIPRION system.
  2. Navigate to Local Traffic > iRules > Data Group List.
  3. Click on the affected data group.
  4. Set the Access Mode option to Read/Write.
  5. Click Update.

    Upon completion of this step, all secondary blades will retrieve the new configuration from the primary blade. After loading the new configuration, the secondary blades will resume normal operation.
