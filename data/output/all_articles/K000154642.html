Description

In order to analyse disk latency related issues, the disk_latency.log file needs to be interpreted. Each line in the disk_latency log captures a snapshot of disk I/O latency statistics at a given time. The values are recorded in seconds, unless otherwise noted. The disk latency log files are populated by the chmand daemon. It periodically issues a single read to a random location on disk to measure latency.

 

Example output:

-------time--------,s,rdlat_us,minlatus,avglatus,maxlatus,avg_1min,avg_5min,avg_1hr ,read_errs
2025/09/05 04:15:47,0,0.000224,0.000182,0.000285,0.001146,0.000224,0.000264,0.000261,0
2025/09/05 04:16:47,0,0.000284,0.000182,0.000285,0.001146,0.000284,0.000278,0.000261,0
2025/09/05 04:17:47,0,0.000227,0.000182,0.000285,0.001146,0.000227,0.000276,0.000259,0
2025/09/05 04:18:47,0,0.000204,0.000182,0.000285,0.001146,0.000204,0.000260,0.000259,0

Disk Latency Log - Column Reference

 

ColumnDescriptionTypical Healthy RangeNotes / How to Interpret
timeTimestamp of the sample-Format: YYYY/MM/DD HH:MM:SS
sStatus code / sample ID0Usually 0 in healthy logs.
rdlat_usRead latency of the most recent operation< 0.005s (5ms)Key column for spotting anomalies. Spikes indicate storage slowness.
minlatusMinimum latency observed in the sample~0.00004s (40 µs)Normally very small (near zero).
avglatusAverage latency of all the operations in the sample< 0.001s (1ms)Good for detecting general slowdowns.
maxlatusMaximum latency observed in the sample~constant unless real stalls occur.Often fixed at the maximum observed sample.
avg_1minRolling average latency of the last 1 minute< 0.002sDetects short bursts of issues
avg_5minRolling average latency of the last 5 hour< 0.002sDetects sustained problems
avg_1hjrRolling average latency of the last 1 minute< 0.001sLong-term health check
read_errsNumber of read errors0Should always be 0. Non-zero indicates signs of disk failure.

 

Note: rdlat_us column generally is considered a key column to start inspections on.

Example High Latency Row

 

time,s,rdlat_us,minlatus,avglatus,maxlatus,avg_1min,avg_5min,avg_1hr,read_errs
2025/08/29 16:53:56,0,0.127418,0.000039,0.000243,1.702960,0.002243,0.000542,0.000330,0
2025/08/30 01:02:48,0,0.117983,0.000039,0.000244,1.702960,0.010310,0.005194,0.000600,0
2025/08/27 01:01:18,0,0.106178,0.000039,0.000243,1.702960,0.010676,0.002224,0.000341,0

Interpretation: first row's `rdlat_us` shows an unusually high spike (~127 ms) at this moment, and short term average (1 min) is elevated. However, 5 min and 1hr averages remain close to normal. Likely a short burst of activity. Read errors is 0, which means no disk failure observed. Maxlatus, while high, is more historical, and remains unchanged.

 

Environment

  • BIG-IP
  • Disk latency log files in /var/log/disk_latency.log*

Cause

None.

 

Recommended Actions

  • Occasional spikes can be expected on a busy box. However, repeated ones matter.
  • Causes of high latency can include
    • Heavy I/O workload
    • Disk contention (multiple apps competing)
    • Underlying hardware problems
    • Virtualisation overhead (if running in a VM).
  • If high latency anomalies are observed,
    • Correlate with system metrics (CPU, memory, I/O wait, etc).
    • Check for any read_errs (disk failure vs latency)
    • Track whether it's transient or persistent
    • Consider scheduling alerts if thresholds are breached repeatedly.
  • For reference,
    • 1 ms = 0.001s
    • 100 µs = 0.0001s
