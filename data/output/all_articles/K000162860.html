K000162860: Microsoft Entra ID unauthorized_client / AADSTS700016 Causes Azure VNet CE Cloud-Controller-Manager CrashLoopBackOff

Type
Support Solution
Published
2026-08-10
Updated
2026-08-10
Applies to

  • F5 Distributed Cloud
Source
https://my.f5.com/manage/s/article/K000162860

Description

The Azure VNet Customer Edge (CE) cloud-controller-manager repeatedly restarts and enters CrashLoopBackOff because the Azure application or service principal configured for the CE cannot be authenticated in the configured Microsoft Entra ID tenant.

Observed symptoms may include:

  • Repeated cloud-controller-manager restarts.
  • CrashLoopBackOff.
  • Container exit code 255.
  • Azure authentication failure after the component starts.
  • Failure while retrieving Azure regional or zone information.

Relevant error messages include:

unauthorized_client
AADSTS700016

The error indicates that the application or client ID used by the CE was not found in, or cannot be authenticated against, the configured Microsoft Entra ID tenant.

Environment

  • F5 Distributed Cloud Azure VNet Customer Edge.
  • Kubernetes cloud-controller-manager.
  • An Azure application, service principal, managed identity, client secret, or certificate used by the CE.
  • An F5 Distributed Cloud cloud credential referenced by the Azure VNet CE site configuration.
  • A recent deletion, replacement, renaming, expiration, or modification of the Azure service principal or F5 Distributed Cloud cloud credential.

Cause

The Azure identity referenced by the CE is unavailable or does not match the configured Microsoft Entra ID tenant. Common causes include:

  • The Azure application or service principal was deleted.
  • The application or client ID belongs to a different Microsoft Entra ID tenant.
  • The CE site references an incorrect or outdated client ID.
  • The client secret or certificate is invalid or expired.
  • The service principal is missing the required Azure permissions.
  • The F5 Distributed Cloud cloud credential object was deleted, renamed, or replaced.
  • The CE site still references a cloud credential that is no longer available.

Answer/Recommended Actions

1. Validate the Microsoft Entra ID application and service principal

An Azure administrator should verify the following using the client ID and tenant information associated with the CE:

  1. Confirm that the Azure application identified by the client ID exists.
  2. Confirm that the application is registered in the Microsoft Entra ID tenant configured for the CE.
  3. Confirm that a corresponding service principal exists in that tenant.
  4. Verify that the client secret or certificate is present, valid, and not expired.
  5. Verify that the service principal has the Azure permissions required by the CE deployment.
  6. Confirm that the tenant ID used by the CE matches the tenant containing the application and service principal.

Use the client ID, tenant ID, timestamp, trace ID, and correlation ID from the Azure authentication error when validating the failure.

2. Restore or recreate the required Azure identity

  1. Restore the original Azure application or service principal if it was removed and is still valid.
  2. If the original identity cannot be restored, create a replacement application or service principal using the customer's approved Azure process.
  3. Create or update the required client secret or certificate.
  4. Apply the required Azure permissions to the replacement identity.
  5. Record the replacement client ID and tenant ID for use when updating the F5 Distributed Cloud configuration.

3. Validate and restore the F5 Distributed Cloud cloud credential

  1. Confirm that the corresponding F5 Distributed Cloud cloud credential exists in the correct tenant.
  2. Restore the cloud credential if it was deleted, or create a new cloud credential for the replacement Azure identity.
  3. Update each affected Azure VNet CE site to reference the correct cloud credential.
  4. Apply the updated site configuration through the supported F5 Distributed Cloud site-management workflow.
  5. Confirm that all affected sites reference the intended credential.

Recreating the Azure service principal alone is not sufficient when the F5 Distributed Cloud cloud credential or CE site reference still points to a deleted, renamed, or incorrect credential.

4. Verify recovery

  1. Allow the CE component time to restart after the identity and site configuration are corrected.
  2. Review fresh logs from the affected CE.
  3. Confirm that the following authentication or credential-retrieval errors no longer occur:
unauthorized_client
AADSTS700016
FetchAzureSecrets
NotFound
unable to retrieve cloud credentials
  1. Confirm that cloud-controller-manager remains running without repeated restarts.
  2. Confirm that the related pod-crashing alert clears.
  3. Continue monitoring the CE after remediation.

If the authentication errors are no longer present but the component continues to restart, collect a new support bundle and investigate the new event independently.

Additional Information

  • The CE may remain online and carry traffic while cloud-controller-manager is repeatedly restarting.
  • The unauthorized_client / AADSTS700016 condition is an Azure identity or tenant-alignment problem; upgrading CE software or the operating system is not, by itself, a remediation for this authentication error.
  • A missing F5 Distributed Cloud cloud credential can produce a separate credential-retrieval error such as FetchAzureSecrets with NotFound. The Azure identity and the F5 Distributed Cloud cloud credential must both be valid and correctly referenced.
  • Do not assume that later pod restarts have the same cause after the Azure authentication error has been corrected. Validate each subsequent event using current logs and timestamps.
