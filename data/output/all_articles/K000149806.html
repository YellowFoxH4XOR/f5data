Description

Observed a message similar to the following in VELOS partition's velos.log:

dagd-service[1]: priority="Err" version=1.0 msgid=0x1901000000000019 msg="Couldn't bulk write DagState for tenant" tenant_name="tenant01" confd_errno=45 confd_errstr="Lost connection to ConfD".

What is the meaning of this message?

Environment

  • VELOS partition
  • dagd

Cause

This message means that a BIG-IP tenant sent out a DAG state update to the dagd service on a blade, but the dagd service on the blade could not write the updated DAG state to confd.

The message will typically be preceded by another dagd message such as the following:

dagd-service[1]: priority="Info" version=1.0 msgid=0x1901000000000033 msg="Dagd published DAG state: ." tenant_name="tenant01" table_type="slot hash table" sdag_table_hash=22279.

BIG-IP will retry a failed DAG state update in 17.1.1 onwards, due to the fix for bug ID 1305897.

You may see a further Dagd published DAG state message, about 5 seconds after the initial failure. If there are no further Couldn't bulk write DagState for tenant messages, the DAG state has now been committed successfully.

Recommended Actions

In the event of a failed DAG state update, the tenant TMM logs will contain a sequence of messages similar to the following:

notice SDAG CDP INFO: Sent DAG context commit request, status 0
notice SDAG CDP INFO: Received error in DAG context commit reply, err 0x1

A successful DAG state update consists of a sequence of messages similar to the following:

notice SDAG CDP INFO: Sent DAG context commit request, status 0
notice SDAG CDP INFO: Receive DAG context commit reply, event 0x0

A one-time occurrence of this issue is not cause for concern if the next DAG state update was successful.

If DAG state constantly or regularly fails to commit to confd, open a case with F5 Support for further investigation.

Additional Information

A DAG state update will happen in response to a change in CMP state in the tenant - a blade going offline due to a TMM crash, for example. Troubleshooting should typically focus on that.
