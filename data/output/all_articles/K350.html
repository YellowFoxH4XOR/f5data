Topic

The recommended interval and timeout values for a service check by a BIG-IP health monitor vary, depending on the type of service being checked.

An interval is measured in seconds. As a rule, the timeout should be 3 times the interval, plus one second.

For example:

Interval: 5
Timeout: 16

This timeout allows BIG-IP to send four checks and provide a reasonable amount of time to receive the reply. For example when you have the 5 second interval with a 16 second timeout this gives the service four tries to respond: 0 sec, 5 sec, 10 sec, 15 seconds. If no response is received or the receive string doesn’t match, then at 16 seconds the service is marked down. So if it fails to respond to the first two checks but responds at 10 seconds, then the service will stay marked up since it responded within the timeout window.

For any given service, set the health check to a time that reflects the maximum delay in response that is acceptable for customer access.

In an ideal environment, BIG-IP should mark a server as down if it fails to respond to a single service check, but in a normal networking environment, it is expected that traffic spikes will occasionally cause servers to fail a service check. The most important function of a health check is to determine if a server is completely down, or if the server has been down for an unacceptable amount of time.

A 3:1 service check ratio is an effective setting because it provides a good balance between an acceptable amount of downtime and enough queries per timeout. This ensures that the node is actually down before it is marked down, because even if the node is down and has not responded to the client requests (because of delays or dropped packets), TCP clients continue to resend the unacknowledged packets at regular intervals until a response is received. However, if this ratio or resulting behavior is undesirable, you can configure a health monitor to use another ratio, such as 1:1 or 2:1. F5 Support recommends a 3:1 ratio.

Note: A 1:1 service check ratio will increase the amount of log messages and, in turn, could mark down the service unnecessarily if the node is too busy handling client requests to respond to the health check.
