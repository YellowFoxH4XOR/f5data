Known Issue

Under some circumstances, one or more BIG-IP GTM synchronization group members may create extraneous generations of DNSSEC keys. This issue may occur when you bring one of the sync group members offline for maintenance, or the iQuery connection between the BIG-IP GTM sync group members is temporarily disrupted.

The BIG-IP GTM system implements an automatic key rollover feature that uses overlapping key generations so that the system can always respond to requests with a valid key signature. Generally, a DNSSEC key should not have more than two key generations; the currently active key, and possibly a rollover key. When BIG-IP GTM systems are defined in a sync group configuration, the sync group member with the GTM.PeerInfoLocalId BigDB variable designation of 0 is responsible for creating new generations of each DNSSEC key and distributing the keys to each sync group member.

The BIG-IP GTM systems determine the GTM.PeerInfoLocalId BigDB designation as follows:

  • Each BIG-IP GTM sync group member dynamically determines its own GTM.PeerInfoLocalId value in relation to the other sync group members
  • The system with the lowest self IP address assigns itself a GTM.PeerInfoLocalId value of 0, and assumes the responsibility of generating rollover keys
  • If one of the sync group members drops offline, the system with the next-lowest self IP address assigns itself a GTM.PeerInfoLocalId value of 0

The above designation process can cause a problem if the BIG-IP GTM system that is responsible for generating rollover keys (GTM.PeerInfoLocalId = 0) becomes unavailable on the network at the same time that a DNSSEC key rollover is scheduled to occur. When this occurs, more than one sync group member may have a GTM.PeerInfoLocalId value of 0, causing both units to create and distribute new rollover keys to the other sync group members.

Note: Allowing extraneous DNSSEC keys to reach their expiration period will not resolve this issue.

When the BIG-IP GTM sync group members generate enough extraneous generations of DNSSEC keys, a BIG-IP GTM system may issue a DNSSEC response that exceeds the 4096 UDP packet size limit. The BIG-IP GTM system truncates any DNS response that exceeds 4096 bytes and then sets the TC bit, informing the LDNS to perform the query again using TCP rather than UDP. If a TCP GTM listener has not been created, the subsequent DNS query will fail.

Impact

This issue may cause some DNSSEC DNS queries to fail.

Symptoms

As a result of this issue, the BIG-IP GTM system may experience the following symptoms:

  • The BIG-IP GTM sync group member's configuration may contain more than two DNSSEC key generations for a specific key.
  • This issue may cause some DNSSEC DNS queries to fail.

Workaround

To work around this issue you can create a new DNSSEC key and delete the extraneous keys. To do so, perform the following procedure:

Note: The following procedure should not disrupt GTM DNSSEC responses; however, as a precaution, F5 recommends that you perform the procedure during a maintenance window.

Note: You must perform this procedure on the BIG-IP GTM with the GTM.PeerInfoLocalId = 0 designation.

  1. Log in to the command line on each BIG-IP GTM sync group member.
  2. Issue the following command on each system:

    bigpipe db GTM.PeerInfoLocalId

  3. Determine which sync group member has the GTM.PeerInfoLocalId = 0 designation.
  4. Log in to the Configuration utility of the BIG-IP GTM sync group member with the GTM.PeerInfoLocalId = 0 designation.
  5. Navigate to Global Traffic > DNSSEC Key List > Create.
  6. Enter a new name for the DNSSEC key, and define the remaining values for the new DNSSEC key.

    Note: The new key should have a different name than the existing DNSSEC key that is currently in use.

  7. Navigate to Global Traffic > DNSSEC Zone List.
  8. Associate the new DNSSEC key with the appropriate zone(s).

    Note: Each zone should now have two enabled and one disabled keys assigned for the key type created in Step 5.

  9. Verify that the changes were synchronized to all BIG-IP GTM sync group members.
  10. Navigate to Global Traffic > DNSSEC Key List.
  11. Select the check box next to the old DNSSEC key that has extraneous branches.
  12. Click Delete.

    Note: Deleting the old DNSSEC key also removes the old key from its association with the DNSSEC Zones involved.

  13. Verify that the zones are still green on all BIG-IP GTM sync group members and that the change synchronized.
  14. Navigate to Global Traffic > DNSSEC Key List, and verify that the extraneous DNSSEC keys no longer appear on the DNSSEC Key List screen.

    Note: The new keys should have only one generation; other keys could have up to two generations.

  15. Navigate to Global Traffic > DNSSEC Zone List and verify that there is only one enabled ZSK and KSK assigned to the zone, and that the old keys are gone.
  16. Verify that the DNS zones return a single RRSig resource record.
    For example, to verify that the DNS zone returns a single RRSig record, use the following dig command syntax:

    dig @<gtm_listener_ip> +dnssec <domain_name> -tA

You should now have only a single RRSig return for each A record in the response.
