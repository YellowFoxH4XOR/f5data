Known Issue

When using the bigip monitor, the BIG-IP GTM system is unable to obtain status of the virtual server when the virtual server's relative traffic group is set to None.

This issue occurs when all of the following conditions are met:

  • The BIG-IP GTM system is configured to have one or more BIG-IP LTM servers with virtual server discovery enabled, and it uses bigip as the health monitor.
  • The BIG-IP LTM system has one or more virtual servers and has one of the following settings:

    • The virtual server belongs to an administrative partition where its traffic group was set to None.
    • The virtual address was configured with its traffic group set to None.

Impact

The BIG-IP GTM monitor incorrectly marks down the affected BIG-IP LTM virtual servers.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • From the BIG-IP GTM system, the affected BIG-IP LTM virtual server is marked down, while the BIG-IP LTM virtual server designated monitor marked it as up and available.
  • In the /var/log/gtm log file of the BIG-IP GTM system, you may see a log entry where the monitor has marked the virtual server down; the entry may appear similar to the following example:

    gtmd[24674]: 011ae0f2:1: Monitor instance /Common/bigip 10.10.10.100:80 UP --> DOWN from /Common/MyServer (no reply from big3d: timed out)

  • When using tmsh to verify the virtual-servers from the BIG-IP GTM system, you may observe the reason for the virtual server's down status as no reply from big3d: timed out.

    For example, using tmsh, you would type the following command from the BIG-IP GTM system to verify the current monitor status of a virtual server named MyServer:

    tmsh show /gtm server MyServer { virtual-servers } | grep 'Destination\|Reason'

    The output appears similar to the following example:

    Reason : Monitor /Common/bigip from /Common/MyServer : no reply from big3d: timed out
    Destination : 10.10.10.100:80

    Using tmsh from the BIG-IP LTM system, to verify the current monitor status of the affected virtual server named MyServerVS1, you would type the following command:

    tmsh show /ltm virtual MyServerVS1 | grep 'Destination\|Reason'

    The output appears similar to the following example:

    Reason : The virtual server is available
    Destination : 10.10.10.100:80

Workaround

To work around this issue, you can modify the traffic group of the affected virtual server from None to traffic-group-local-only. You can modify the traffic group setting of the affected virtual server from the Administrative Partition configuration or from the Virtual Address configuration.

Using the Administrative Partition configuration

To modify the traffic group setting on the affected administrative partition, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to System > Users > Partition List.
  3. Click the name of the affected administrative partition.
  4. Modify the value for Traffic Group from None to traffic-group-local-only.
  5. Click Update.

Using the Virtual Address configuration

To modify the traffic group setting on the affected virtual address, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Virtual Servers > Virtual Address List.
  3. Click the affected virtual address.
  4. Modify the value for Traffic Group from None to traffic-group-local-only.
  5. Click Update.
