Topic

An internal virtual server provides a method for sending a request or a response to an external service, such as an Internet Content Adaptation Protocol (ICAP) server for content adaptation.

Description

Starting in BIG-IP 11.3.0, you can configure an internal virtual server to load balance requests and/or responses to a pool of ICAP servers for content adaptation before returning the modified content to their intended destinations. You can use the internal virtual server to send requests or responses to external ICAP services, such as (but not limited to) the following:

  • Antivirus scanning
  • Advertisement insertion or content transformation
  • Video adaptation and optimization
  • Web content filtering

By design, the internal virtual server is accessible only by a locally configured standard virtual server. The standard virtual server sends traffic that requires content adaptation to the internal virtual server, which then load balances these traffic to a pool of ICAP servers. Once the internal virtual server receives the modified content from the ICAP server, it returns the traffic back to the standard virtual server for further traffic processing; for example, load balances the ICAP-modified client request to its pool members or returns the ICAP-modified server response back to a client. Due to the way the internal virtual is accessed, it does not require configuration of an IP address.

To configure the standard virtual server to send traffic to the internal virtual server, you must associate the Request Adapt profile to the standard virtual server if you are forwarding client requests to the internal virtual server, and/or associate the Response Adapt profile to the standard virtual server if you are forwarding server responses to the internal virtual server. You must also associate an HTTP profile to the standard virtual server to properly enable the Request/Response Adapt profile(s).

To configure the internal virtual server to send traffic to its pool of ICAP servers, you must associate the ICAP profile to the internal virtual server for the system to wrap the request/response in an ICAP message before sending to the selected pool member. If required, you can enable persistence on the internal virtual server to ensure that subsequent requests/responses go back to the same selected pool member.

The following example configuration stanzas describe the HTTP_ICAP_request_response standard virtual server configured with two content adaptation profiles, the ICAP_Request_Adapt request adaptation profile that sends client requests to the ICAP_request_Internal internal virtual server, and the ICAP_Response_Adapt response adaptation profile that sends server responses to the separate ICAP_response_internal internal virtual server. Although both internal virtual servers are associated with the same ICAP_pool pool, their ICAP profiles are configured to send to different ICAP services. The client_side_icap ICAP profile sends client requests to the virusScan ICAP service, while the server_side_icap ICAP profile sends server responses to the videoOptimization ICAP service:

ICAP profiles for the internal virtual servers

ltm profile icap client_side_icap {
app-service none
defaults-from icap
uri "icap://${SERVER_IP}:${SERVER_PORT}/virusScan"
}
ltm profile icap server_side_icap {
app-service none
defaults-from icap
uri "icap://${SERVER_IP}:${SERVER_PORT}/videoOptimization"
}

Internal virtual servers

ltm virtual ICAP_request_Internal {
description "This virtual server ensures HTTP request modification through the use of the service_name ICAP service.."
destination 0.0.0.0:any
internal
ip-protocol tcp
mask 255.255.255.255
pool ICAP_pool
profiles {
client_side_icap { }
tcp { }
}
source 0.0.0.0/0
translate-address disabled
translate-port disabled
vlans-enabled
vs-index 2
}
ltm virtual ICAP_response_internal {
description "This virtual server ensures HTTP response modification through the use of the service_name ICAP service."
destination 0.0.0.0:any
internal
ip-protocol tcp
mask any
pool ICAP_pool
profiles {
server_side_icap { }
tcp { }
}
source 0.0.0.0/0
translate-address disabled
translate-port disabled
vlans-enabled
vs-index 3
}

Request and Response Adapt profiles

ltm profile request-adapt ICAP_Request_Adapt {
app-service none
defaults-from requestadapt
internal-virtual ICAP_request_Internal
}
ltm profile response-adapt ICAP_Response_Adapt {
app-service none
defaults-from responseadapt
internal-virtual ICAP_response_internal
}

Standard virtual server

ltm virtual HTTP_ICAP_request_response {
destination 192.168.15.20:http
ip-protocol tcp
mask 255.255.255.255
pool HTTP_pool
profiles {
ICAP_Request_Adapt {
context clientside
}
ICAP_Response_Adapt {
context serverside
}
http { }
tcp { }
}
source 0.0.0.0/0
source-address-translation {
type automap
}
vs-index 4
}
