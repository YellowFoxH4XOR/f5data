Known Issue

This is the result of a known issue. When a FastL4 virtual server or SNAT object process a SYN request followed by an RST from the pool member, the connection entry should be deleted from the connection table after the default TCP handshake timeout of 5 seconds. However, the BIG-IP system incorrectly retains the connection for the duration of the idle connection timeout configured for the object.

For example, in the following configuration, when the fastl4_vip virtual server processes a SYN request followed by an RST from the pool member, the connection entry remains in the connection table for 900 seconds instead of the TCP handshake timeout of 5 seconds:

virtual fastl4_vip {
pool linux64.askf5.net
destination 172.1.1.1:81
ip protocol tcp
profiles fastl4_profile
}
profile fastL4 fastl4_profile {
defaults from fastL4
idle timeout 900
tcp handshake timeout 5
}

Important: If the connection traverses a SNAT and a FastL4 virtual server, the lower of the two idle timeout values is used. If both of the idle timeout values are set to a high number, this behavior may cause ephemeral port exhaustion for the SNAT. You should ensure that one or both of the idle timeout values are set as low as possible for the application.

F5 Networks Product Development tracked this issue as CR118554 and it was fixed in BIG-IP versions 9.4.8 and 10.1. For information about upgrading, refer to the BIG-IP LTM, ASM, or WebAccelerator Release Notes.
