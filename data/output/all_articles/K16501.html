Known Issue

Failing Active Directory (AD) or Lightweight Directory Access Protocol (LDAP) server connections may cause the apd process to stop processing requests when service is restored.

This issue occurs when all of the following conditions are met:

  • The BIG-IP APM system is configured with either an AD or LDAP type AAA server.
  • The AAA server is configured to use direct or a pool of servers.
  • The back-end authentication server becomes temporarily unavailable when communicating with the BIG-IP APM system.

Impact

The BIG-IP APM apd process can hang and stop processing user requests. In rare circumstances, the apd process may exit and produce a core file.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • Failed user login attempts and client browser resets coincide with backend server connectivity issues.
  • Users experience stalled browser sessions.
  • CPU utilization by the apd process is abnormally high.
  • The system generates an apd core file to the /shared/core directory.
  • Output from the netstat -pano command shows output similar to the following:

    Proto Recv-Q Send-Q Local Address Foreign Address State PID/Program name Timer
    tcp 270 0 127.0.0.1:10001 10.10.225.85:53212 ESTABLISHED 12191/apd off (0.00/0/0)
    tcp 269 0 127.0.0.1:10001 10.10.225.4:56305 ESTABLISHED 12191/apd off (0.00/0/0)
    tcp 272 0 127.0.0.1:10001 10.10.57.10:57508 CLOSE_WAIT 12191/apd off (0.00/0/0)
    tcp 0 0 127.1.1.1:56230 127.7.0.1:389 ESTABLISHED 12191/apd keepalive (1909.72/0/0)

    The Timer keepalive (1909.72/0/0) value in the last line indicates that apd has been waiting excessively for a response, has no retries, yet has not timed out. The large Recv-Q 272 values seen in other lines indicate that apd is not reading incoming requests as expected (specifically, that the internal worker queue is overloaded because all threads are waiting for the one hanging thread to be processed).
