Issue

Description

When configuring Remote Desktop Protocol (RDP) services, you may want to dynamically specify a RDP resource by IP or host name. This article outlines how to create a user-defined RDP resource. The user-defined RDP resource presents the user with a pop-up window to allow manual entry of a host name or an IP address. The main components of Windows remote desktop in the BIG-IP APM system are the following:

  • A virtual server.
  • A remote desktop gateway, RDG-RAP access profile with an access policy to authorize access to the resources.

    Note: Instead of an ACL, remote desktop (RD) executes an additional access policy called RDG-RAP. If the RDG-RAP access policy ends in Allow, the RD connection is allowed. This special access policy does not have access to the user’s main session variables. This special access policy also can not execute iRules and does not have access to the name of the RemoteApp that the client is trying to execute. It allows access to any host name listed in the Active Directory (AD) domain, regardless of the assigned ACLs, resources, or filters.

  • An access profile with an access policy to authenticate and authorize users.
  • A remote desktop object.

Important: OneConnect Profile is not supported. Do not assign OneConnect Profile to this virtual server.

Environment

  • Windows remote desktop client and server devices must be supported. For the full list, refer to the Remote Desktop Compatibility matrix section of the BIG-IP APM Client Compatibility Matrix manual.

    Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

  • The BIG-IP APM is a gateway for users to access Windows remote desktop resources.
  • The BIG-IP APM is used to authenticate and authorize users to Windows remote desktop resources.

Cause

There is a requirement for users to access Windows remote desktop using the BIG-IP APM using the Windows native client.

Note: F5 recommends using the native client to access Windows remote desktop resources. From BIG-IP APM 15.0, ActiveX and Java clients are deprecated.

Recommended Actions

Perform the following procedures to configure Windows native user define remote desktop:

  • Creating a user-defined RDP resource
  • Creating a RDG-RAP access profile
  • Creating an Access profile with Full Webtop with Advanced Resources Assign
  • Creating a virtual server

Creating a user-defined RDP resource

  1. Log in to the Configuration utility.
  2. Navigate to: Access > Connectivity > VPN > VDI / RDP > Remote Desktops.
  3. Click Create.
  4. Configure the following settings:
    • Name: Provide an appropriate name.
    • Type: Click RDP.
    • Client Type: Click Native.
    • Destination: Click User defined.
  5. Click Finished.

Creating a RDG-RAP access policy

  1. Log in to the Configuration utility.
  2. Navigate to Access > Profiles / Policies > Access Profiles (Per-Session Policies).
  3. Click Create..
  4. Configure the following:
    • Name: Provide an appropriate name.
    • Profile Type: Click RDG-RAP.
    • Profile Scope: Click Profile.
  5. Click Finished.
  6. For the RDG-RAP profile you just created, click Edit.
  7. Change the ending from Deny to Allow by clicking Deny.
  8. Click Allow and click Save.

Creating an Access profile with Full Webtop with Advanced Resource Assign

  1. Log in to the Configuration utility.
  2. Navigate to Access > Profiles / Policies > Access Profiles (Per-Session Policies).
  3. Click Create.
  4. Configure the following:
    • Name: Provide an appropriate name.
    • Profile Type: Click All.
    • Profile Scope: Click Profile.
    • Languages: Click the languages you want to use.
  5. For the access profile you just created, click Edit to open the Visual Policy Editor.
  6. To add a Logon page:
    • Click the Add icon (+).
    • Click Logon Page.
    • click Add Item.
  7. Add the Authentication you want to use. For example, to add the AD Auth policy item:
    • Click the Add icon ( +)to on the right of the Logon Page policy item.
    • Click the Authentication tab.
    • Click AD Auth and click Add Item.
  8. Add an RDG Policy Assign policy item:
    • Click the Add icon (+ ) on the Successful branch of the authentication policy item (AD Auth in this example).
    • Click the Assignment tab.
    • Click RDG Policy Assign .
    • Click Add Item.
    • Click Add/Delete.
    • Click the RDG policy created in Creating a RDG-RAP access policy.
    • Click Save.
  9. If you do not have a full webtop, create one first by navigating to Access > Webtops > Webtop Lists and clicking Create.
  10. Add a Advanced Resource Assign policy item for users to access the RD resources.
    • Click the the Add icon (+ ) on the right of the RDG Policy Assign policy item.
    • Click the Assignment tab.
    • Click Advanced Resource Assign.
    • Click Add new entry.
    • Click Add/Delete.
    • Click the WebTop tab and click a Full Webtop.
    • Click the Remote Desktop tab and click the remote desktop object created in Creating a user defined RDP resource.
    • Click Update and click Save.
  11. On the successful branch of the AD Auth policy item, change the ending from Deny to Allow by clicking Deny.
  12. Click Allow and click Save.
  13. Click Apply Access Policy to apply all the changes.

Creating a virtual server

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Virtual Servers > Virtual Server List.
  3. Click Create, and enter a name for the profile.
  4. For Destination Address/Mask, type the virtual server IP address.
  5. For Service Port, type 443 or click https.
  6. For the SSL Profile (Client) and SSL Profile (Server), click the appropriate profiles.

    Note: You cannot use the default Client SSL profile as the certificate. It does not specify the keyUsage and enhancedKeyUsage properties. For more information, refer to the section, Additional Information.

  7. For HTTP Profile, click an appropriate HTTP profile. For example, http.
  8. For Source Address Translation, click Auto Map if your environment requires it.
  9. Under Access Policy , for Access Profile, click the access profile you created in the Creating an access profile with an access policy with SSO credential mapping procedure.
  10. For Connectivity Profile, click an appropriate profile. If you do not have one, click the Add icon (+) to create a new one.
  11. For VDI Profile, click an appropriate VDI profile.
  12. Click Finished.

Important: When the Source Port on the Virtual server settings is set to Change, the RDP connection may fail. Please apply workaround described in K29453454: Remote desktop access fails due to the virtual server configuration

Additional Information

Note that the Client SSL profile of the virtual server must be configured with a certificate that specifies the keyUsage and enhancedKeyUsage properties. The Windows native client generates an error when a certificate without these two properties specified is used in the Client SSL profile of the virtual server. For example, if you use the default.crt and default.key provided in the BIG-IP system, the Windows native client displays an error generates similar to the following:

The digital signature of this RDP File cannot be verified. The remote connection cannot be started.

For more information on certificate requirements for Terminal Server Gateway, refer to Obtain a Certificate for the TS Gateway.

For steps to create a certificate specifying the keyUsage and enhancedKeyUsage properties, refer to New-SelfSignedCertificate.

Note: The previous links take you to resources outside of AskF5. The third party could remove the documents without our knowledge.

In addition, the certificate must also be trusted on the client device. When the certificate is not trusted, the Windows native client generates an error similar to the following:

This computer can't verify the identity of the RD Gateway "apm.example.com". It's not safe to connect to servers that can't be identified Contact your network administrator for assistance.

You can import the certificate on the client device to the Trusted Root Certification Authorities store on the client computer to resolve this issue.
