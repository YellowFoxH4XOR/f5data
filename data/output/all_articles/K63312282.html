Security Advisory Description

Multiple desync attacks have been discovered. For more information refer to the following related articles:

  • K27144609: Overview of HTTP/2 desync attacks
  • K30341203: BIG-IP LTM and NGINX are not exposed to certain desync attacks
  • K97045220: BIG-IP LTM HTTP/2 desync attacks: malicious CRLF placement

An attacker can manipulate an HTTP/2 request to inject a malicious element into the HTTP/1 request line on the server-side. If the affected BIG-IP system translates requests from HTTP/2 to HTTP/1 without adequate sanitization, this may lead to unexpected HTTP requests reaching the target server-side pool member.

This issue occurs when all of the following conditions are met:

  • The BIG-IP LTM has one or more virtual servers configured to proxy HTTP/2 requests from the client-side to HTTP/1 requests on the server-side.
  • An HTTP/2 client sends a request with one of the following issues and the BIG-IP passes it to the server-side pool members:
    • H2.TE request line injection
      • An HTTP/1 request embedded within an HTTP/2 pseudo-header value
      • Individual carriage return (CR) or line feed (LF) allowed within an HTTP/2 pseudo-header
    • Request line injection (folder traps)
    • Request line injection (rule bypass)
Important: This security exposure does not affect NGINX.

Impact

Malicious HTTP/2 requests may be translated to HTTP/1 requests and sent to the pool member web server. Depending on the behavior of the pool member web server, this may lead to an HTTP request smuggling attack. When the affected virtual server is configured with the OneConnect profile, an attacker may be able to impact the responses sent to a different client.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • The BIG-IP system may pass malicious requests to server-side pool members.

Security Advisory Recommended Actions

Workaround

Blocking malformed HTTP requests using the BIG-IP ASM system / Advanced WAF

You can configure the BIG-IP ASM system or Advanced WAF to block an HTTP/1 request that is embedded within an HTTP/2 pseudo header value from being sent to the backend server.

To do so, perform one of the following actions on the Blocking Settings page of the BIG-IP ASM policy:

  • Set the HTTP protocol compliance failed violation to Block and enable the Unparsable request content subviolation.

    For more information about viewing and enabling these subviolations, refer to K10280: Overview of BIG-IP ASM HTTP protocol compliance.

  • Set the illegal method violation in the Headers category to Block.

Note: After you configure these blocking settings, no further mitigation is necessary.

Modifying or disabling the OneConnect profile

Note: Performing these actions on the OneConnect profile prevents the aggregation of HTTP requests and thus mitigates the risk of an attacker interacting with a legitimate client. However, the changes to the OneConnect profile do not prevent the target pool member web server from being subjected to potential HTTP request smuggling attacks.

Impact of workaround: Depending on your application environment, adjusting the value of the Source Prefix Length or Source Mask setting in the OneConnect profile may impact optimal connection re-use, while disabling OneConnect may impact performance. For additional information, refer to K7208: Overview of the OneConnect profile.

If the BIG-IP ASM system is not available and the affected virtual server is configured with the OneConnect profile, consider adjusting the Source Prefix Length or Source Mask (BIG-IP 11.x) setting of the OneConnect profile to prevent aggregation of HTTP requests from separate client-side TCP streams into the same server-side connection. Alternatively, you may consider using an iRule to disable OneConnect for specific connections or removing it entirely on the affected virtual server if your application environment permits. For information about modifying an iRule to disable OneConnect reuse, refer to the ONECONNECT::reuse iRule command
