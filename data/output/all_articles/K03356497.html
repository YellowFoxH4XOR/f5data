Description

After pool member down event request are still send to "down" pool member when persistence is configured.


In the persistence table  we see persistence :

show ltm persistence persist-records node-addr <IP of DOWN backend server> node-port <port of pool member>

Example:
Sys::Persistent Connections
source-address  192.168.1.201  10.10.10.10:443  10.10.1.53:8443  (tmm: 1)
source-address  192.168.1.76     10.10.10.10:443  10.10.1.53:8443  (tmm: 0)
source-address  192.168.1.73    10.10.10.10:443  10.10.1.53:8443  (tmm: 0)
source-address  192.168.1.201  10.10.10.10:443  10.10.1.53:8443  (tmm: 0)

And status of pool member is seen as down:

 --------------------------------------------------------------
  | Ltm::Pool Member: 10.10.10.10:8443
  --------------------------------------------------------------
  | Status
  |   Availability   : offline
  |   State          : enabled
  |   Reason         : https_monitor server: No successful responses received before deadline. @2020/04/23 10:41:33.
  |   Monitor        : min 1 of /Common/https_monitor (pool monitor)
  |   Monitor Status : down
  |   Session Status : enabled
  |   Pool Name      : POOL_test
  |   IP Address     : 10.10.10.10

Possible 400 Error seen in the browser

Environment

  • BIG-IP LTM - all versions
  • Persistence configured
  • HTTP/HTTPS virtual server
  • Action on service down configured as None
  • HTTP monitor
Cause

When a pool member fails to respond to a health monitor, the system marks that pool member down.
Persistence entries associated with the pool member are removed when a new connection matches the entry or when the timeout period is reached.
If a new connection matches a persistence record that has not timed out, the BIG-IP system removes the old persistence record and creates a new entry.

Recommended Actions

Set Action on service down according to K15095: Overview of the Action On Service Down feature
