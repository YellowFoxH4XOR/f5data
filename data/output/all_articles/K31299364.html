K31299364: You Find the BIG-IP Does not Send Probing Traffic When the Monitor Is Marked as DOWN

Type
Support Solution
Published
2022-06-13
Updated
2025-02-06
Applies to
  • BIG-IP
Source
https://my.f5.com/manage/s/article/K31299364

Description

On some rare occasions, when you are troubleshooting monitors following the K12531: Troubleshooting health monitors, you find there is no probing traffic sent out by the BIG-IP as expected. For example, if you use the tcpdump command to take traffic capture on tmm(0.0:nnn flag) like the below, you find there is no traffic while the monitor is showing down around 09:14:38 to 09:16:13.
// tcpdump -s0 -ni 0.0:nnn -vw /shared/tmp/capture.pcap host 192.168.1.2 and host 192.168.10.8
1    2022-02-07 09:14:38.363859    192.168.1.2    192.168.10.8    8080    31657    TCP        IN  s1/tmm1 : 8080 → 51657 [FIN, ACK] Seq=1 Ack=2 Win=29056 Len=0 
2    2022-02-07 09:14:38.364019    192.168.10.8    192.168.1.2    51657    8080    TCP        OUT s1/tmm1 : 51657 → 8080 [ACK] Seq=2 Ack=2 Win=29312 Len=0
3    2022-02-07 09:16:13.387499    192.168.10.8    192.168.1.2    31037    8080    TCP        OUT s1/tmm3 : 31037 → 8080 [SYN] Seq=0 Win=29200 Len=0 MSS=1460 
4    2022-02-07 09:16:13.388153    192.168.1.2    192.168.10.8    8080    31037    TCP        IN  s1/tmm3 : 8080 → 31037 [SYN, ACK] Seq=0 Ack=1 Win=28960 Len=0 MSS=1460 

Environment

  • BIG-IP LTM
  • Monitor Down or Flapping
  • No Monitor Traffic

Cause

The cause can vary and depends, most likely it could be related to the communication between the host and the tmm. Please follow the Recommended Actions below for the next action.

Recommended Actions

To quickly get through the potential issue, you may consider using the below methods. Please note a reboot might clear the improper state between the host and the tmm, so RCA might be impossible if you choose to do so.
  1. Restart the tmm by:
bigstart restart tmm
  1. Or restart the system:
reboot

To get a Root Cause Analysis, please collect the below data and open a case to F5 support.

  1. Generate a qkview, you may further refer to K12878: Generating diagnostic data using the qkview utility

  2. Start traffic capture on the host and tmm by both of the commands below, it is recommended to run them in two separate SSH sessions:
tcpdump -s0 -ni <VLAN>:nnnh -vw <location_store_the_file_host.pcap> host <your_self_IP> and  host <your_member_IP> 

AND:

tcpdump -s0 -ni 0.0:nnn -vw <location_store_the_file_tmm.pcap> host <your_self_IP> and  host <your_member_IP>

  1. Collect arp and routing table by:

while true; do OUTPUT_LOG="/shared/tmp/arp_route_table.txt"; (echo "========= $(date) =========" ; tmsh show net arp; echo "---" ;ip -s neighbor list; echo "-- route --"; tmsh show net route; echo "---"; ip -f inet route show;  echo "") >> ${OUTPUT_LOG}; sleep 1; done

  1. Wait for the issue to recur, you may also tail the ltm log for verification on this:

tailf /var/log/ltm

  1. Stop the commands by CTRL + C for steps 2 and 3

  2. Generate a new qkview

  3. Collect a logs tarball by

tar -zcvf /shared/tmp/$(/bin/hostname)_varlog_$(date +"%Y%m%d-%H%M%S").tar.gz /var/log/

  1. Following the instructions by K2633: Instructions for submitting a support case to F5 to open a support case for RCA with the collected data.
