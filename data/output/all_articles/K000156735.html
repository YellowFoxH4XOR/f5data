Description

After running full config-sync, FQDN template node status may change to "Unknown (Enabled)" from "Available (Enabled)" even though FQDN template node name is resolvable via DNS name resolution. "Unknown" status will be seen on sync receiver BIG-IP only. Sync initiator BIG-IP will report proper FQDN template node status.

Here are example of GUI screenshots. On one of HA unit, FQDN template node "www.test1.local" is shown as "Unknown" with reason "Node address service checking is enabled, but result is not available yet".

 

Figure: correct FQDN template node status on sync initiator BIG-IP.

 

Figure: invalid FQDN template node status on sync receiver BIG-IP.

 

Here is status of affected FQDN template node on TMSH. Monitor status is reported as "fqdn-checking" and availability is reported as "unknown".

 

[root@VELTM1b:Standby:In Sync] config # tmsh show ltm node | grep -B 1 -A 9 'Ltm::Node: www.test1.local'
------------------------------------------
Ltm::Node: www.test1.local (::)
------------------------------------------
Status
  Availability   : unknown
  State          : enabled
  Reason         : Node address service checking is enabled, but result is not available yet
  Monitor        : none
  Monitor Status : fqdn-checking
  Session Status : enabled

[root@VELTM1b:Standby:In Sync] config #

 

Environment

  • FQDN node is used.
  • Run full config-sync on BIG-IP HA. Incremental sync (default) does not cause this problem.

 

Cause

Bug ID 2038309.

 

Recommended Actions

Restarting dynconfd will be able to rescue FQDN nodes with 'unknown' status immediately, as DNS query for the FQDN template node will immediately fires after restarting dynconfd.
Alternatively, using shorter TTL value on FQDN template node will help to quickly update affected FQDN node objects automatically although DNS query for FQDN template node will more frequently happens.
