Issue

You should consider using this procedure under the following conditions:

  • You have configured Kerberos single sign-on(SSO) constrained delegation in your BIG-IP APM access policy.
  • You want to troubleshoot Kerberos SSO constrained delegation issues.

Symptoms

As a result of Kerberos SSO issues, you may encounter the following symptoms:

  • The system prompts users to enter their credentials more than once when accessing internal resources.
  • Kerberos SSO fails.

Recommended Actions

This article provides steps for troubleshooting common SSO issues related to Kerberos.

The main configuration objects to check in Kerberos SSO are the following:

  • The Active Directory (AD) service account with constrained delegation in Windows domain controller.
  • The IIS server configured with Windows Authentication, with Kerberos as provider.
  • The Kerberos SSO object in BIG-IP APM.
  • An object that selects the Kerberos SSO object, such as an iRule, a portal access resource, an access profile, or an Exchange profile.
  • The SSO credential mapping in an access policy.
  • Optionally, the /etc/krb5.conf may be configured manually.
  • A virtual server.

Verify that you have configured these objects correctly. Note also that, unlike Kerberos end-user login authentication, in Kerberos SSO, the client device does not require connectivity to the domain controller and web server.

Important: F5 supports BIG-IP APM system software. F5 does not support third-party software, such as the client operating system or Windows Server.

Procedures

When you experience Kerberos SSO failure issues, you can use the following troubleshooting steps to determine the root cause:

Note: If possible, before each test, clear the Kerberos ticket cache by running the bigstart restart websso command as you make changes to the configuration. F5 recommends running this command during a scheduled maintenance window.

  • Reviewing configuration steps
  • Verifying the DNS configuration
  • Verifying clock skew issues
  • Verifying Kerberos authentication is enabled on the Windows IIS web application
  • Enabling BIG-IP APM and WEBSSO debug logging
  • Enabling Kerberos event logging on Windows server
  • Reviewing the AD service account configuration
  • Advanced troubleshooting with WebSSO debug logs

Reviewing configuration steps

Review the steps described in the procedures for K43063049: Configuring BIG-IP APM Kerberos SSO Constrained Delegation for portal access. Ensure that the steps have been performed correctly. In particular, ensure that the Kerberos SSO object on the BIG-IP APM system and the AD service account on the domain controller are configured correctly. The following table shows sample values that should be present:

Configuration objectParameters
Kerberos SSO object on the BIG-IP APM systemAdmin Name: host/apm.example.com

Kerberos Realm: EXAMPLE.COM

AD service account on domain controllerservicePrincipalName: host/apm.example.com

userPrincipalName: host/apm.example.com@example.com

msDS-AllowedToDelegateTo: | http/webserver.example.com/example.com | http/webserver.example.com | http/webserver.example.com/EXAMPLE |

Verifying the DNS configuration

Use dig to verify the DNS configuration. The tool forwards and reverses the DNS resolution of the domain controller and web server. Hostnames and IP addresses are configured with using following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to Advanced shell (bash).
  2. Use the following command syntax for forward and reverse DNS for both the domain controllers and web servers:

    dig <FQDN of domain controller>
    dig -x <IP address of  domain controller>

    For example:

    dig dc.example.com
    dig -x 192.0.2.2

  3. Run the same commands for your web servers.
  4. Verify that the IP addresses and names from the command output are correct.

Verifying clock skew issues

If the BIG-IP APM system's clock is not synchronized to the Windows domain controller, Kerberos fails and an error message is logged in the /var/log/apm file. To verify that the BIG-IP system's time is synchronized, you can use the ntpstat command. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to bash.
  2. Type the following command:

    ntpstat

    Output appears similar to the following:

    # ntpstat
    synchronised to NTP server (ntpserver.example.com) at stratum 2
    time correct to within 126 ms
    polling server every 1024 s

    Note: Manually verifying that the times among the systems are within 5 minutes of one another is not sufficient. The system's times must be synchronized to an NTP server as shown in the previous output.

Verifying Kerberos authentication is enabled on the Windows IIS web application.

Only IIS servers are supported for pool members or web application resources on the BIG-IP APM. To verify that Kerberos authentication is enabled on the IIS application, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Follow the procedure detailed in Enabling integrated authentication on your IIS web application.
  2. Access the web application from a client device without the BIG-IP APM using Kerberos authentication. Verify that the client is authenticating using Kerberos instead of NTLM. You can do this by observing the value of the Authorization header the client device is sending the IIS server. The Authorization header can be viewed from the in built developer tools in browsers or third-party software, such as HTTPwatch or fiddler.  For example, you may observe that the Authorization header has a value similar to the following:

    Authorization Negotiate YII[...]

    If the value of the Authorization header instead has a value similar to 'TlRM[...]', Kerberos authentication has failed and may have fallen back to using NTLM.

However, even if Kerberos is enabled on the IIS web application, there may be other reasons Kerberos SSO fails with the BIG-IP APM. For example, if you have a load-balanced environment with multiple web servers, where users access < strong>app.example.com instead of server1.example.com or server2.example.com, in IIS you should configure the application pool to run using the AD service account. For more information, refer to Kerberos and Load Balancing.

Reviewing the AD service account configuration

You can attempt to delete and re-create the AD service account if the issue persists. Refer to the Creating an AD service account in with Kerberos constrained delegation procedure in K43063049: Configuring BIG-IP APM Kerberos SSO Constrained Delegation for portal access. However, you should review its configuration first before that. To do that, you can review its configuration by logging into AD Domain Services on your Windows domain controller. Alternatively, you can verify its configuration by using the adtest command on the BIG-IP APM system, which also provides a network connectivity test between the BIG-IP APM system and the key distribution center (KDC). To verify the names for the account you created, you can run the adtest command on the command line of your BIG-IP APM. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

Use the following adtest command syntax:

adtest -t query  -r "<REALM>" -A <user> -W <password> -u <kerberos_delegation_account> -d 1 -g true -G true | grep 'domain name\|Delegate'

Note: <user> refers to any user in AD with read permissions and <password> refers to the user password.

For example, for the previous account, run the following command:

adtest -t query  -r "EXAMPLE.COM" -A user1 -W 'pass' -u samaccountname -d 1 -g true -G true | grep -i 'name\|Delegate'

Output appears similar to the following example:

Test done: total tests: 1, success=1, failure=0
domain name = 'EXAMPLE.COM'
locateKDC:Domain Controller is not specified for domain 'EXAMPLE.COM', KDCs will be discovered using DNS
locateKDC:Adding 'dc.example.com' to KDC list
[...]
msDS-AllowedToDelegateTo: | http/webserver.example.com/example.com | http/webserver.example.com | http/WEBSERVER | http/webserver.example.com/EXAMPLE | http/WEBSERVER/EXAMPLE |
[...]
servicePrincipalName: host/apm.example.com
userPrincipalName: host/apm.example.com@example.com

Using the output, verify the following:

  • The domain name is correct.
  • The locateKDC messages, which provides an indication to how the BIG-IP APM system locates the KDC, are present. If BIG-IP APM is unable to locate the KDC, adtest and Kerberos also fail.
  • The msDS-AllowedToDelegateTo value is set to the HTTP service your web server is providing. This is configured at the Delegation tab of the AD service account.
  • The servicePrincipalName value follows the host/<name>.<domain> format, as shown previously, and matches the Account Name value in the Kerberos SSO object in the BIG-IP APM system. If not, use the following command syntax to add the SPN:

    setspn -A host/<name>.<domain> <samaccount_nameK

    For example:

    setspn -A host/apm.example.com samaccountname

  • The userPrincipalName value matches the servicePrincipalName and has the same realm as the Kerberos SSO object configured in the BIG-IP APM system. However, the realm in the Kerberos SSO object configured in BIG-IP APM should appear in uppercase letters.

Advanced troubleshooting with WebSSO debug logs

The exchange between the BIG-IP APM system and the KDC and web server is the most important part of troubleshooting. The BIG-IP APM system communication with the KDC consists of DNS queries and responses on port 53 and Kerberos on port 88. The communication with the web server is usually encrypted, but you can enable WebSSO debug logging on the BIG-IP APM system to log the details of the exchange for troubleshooting. Enabling apm and websso debug logging should provide a clear understanding of the sequence of exchange with the BIG-IP APM system to resolve the issue. The following information describes this sequence:

  • At the end of the BIG-IP APM access policy evaluation, the system logs the username and password used for Kerberos SSO in session variables. You can verify this by using the following command syntax:

    grep <apm sessionID> /var/log/apm | grep "Session variable"

    Output appears similar to the following example, in which both session variables are set.

    ae78de16: Session variable 'session.sso.token.last.password' set to '**********'
    ae78de16: Session variable 'session.sso.token.last.username' set to 'user1'

    If the session variables are not set, verify that you have SSO Credential Mapping configured in your access policy.

  • The websso daemon raises the Kerberos SSO object that you configured for SSO. You can verify this by using the following command syntax:

    grep <apm sessionID> /var/log/apm | grep <kerberos SSO object name>

    Output appears similar to the following:

    ae78de16: Websso Kerberos authentication for user 'user1' using config '/Common/example_kerberos_sso'

    Verify the name of the Kerberos SSO configuration used for SSO. If you do not see an output, WebSSO is not raised or another incorrect SSO object was used. Kerberos SSO objects can be called from an iRule, a portal access resource, an access profile, or an Exchange profile.

  • The BIG-IP APM system next identifies the web server and the service for which it requests access. To list this, use the following command syntax:

    grep <apm sessionID> /var/log/apm | grep "<webserver IP address>\|SPN"

    Output appears similar to the following:

    [...]
    ae78de16: ctx:0x96414d0 server address = ::ffff:192.0.2.2
    ae78de16: ctx:0x96414d0 SPN = HTTP/webapp.example.com@EXAMPLE.COM

    This is the first step of the Kerberos process in which a reverse DNS resolution of the IP address of your web server is performed to obtain the SPN in the following format: HTTP/<name>.<domain>@REALM.

    This SPN value is the name:

    • that you must configure for constrained delegation in the AD service account.
    • of the Kerberos service that the BIG-IP APM system requests to access when later obtaining the S4U2Proxy ticket.
    • of the SPN Pattern value (if configured) in the Kerberos SSO object on the BIG-IP APM system.
  • The BIG-IP APM system next obtains the Kerberos ticket-granting ticket (TGT) issued to the service account host/<name>.<domain>. The TGT allows the service account to request access to other services in the Kerberos environment. To verify that this is successful, use the following command syntax:

    grep <apm sessionID> /var/log/apm | grep TGT

    Output appears similar to the following:

    ae78de16: fetched new TGT, total active TGTs:1
    ae78de16: TGT: client=host/apm.example.com@EXAMPLE.COM server=krbtgt/EXAMPLE.COM@EXAMPLE.COM expiration=Mon Apr  8 21:10:37 2019  flags=40e00000

    If the TGT request is unsuccessful, you should examine the service account configuration in AD and also the Account Name configured in the Kerberos SSO object in the BIG-IP APM system.

  • With the TGT, the BIG-IP APM system requests S4U2Self and S4U2Proxy tickets. S4U2Self and S4U2Proxy are Microsoft extension of Kerberos. You can verify the tickets are fetched successfully by using the following command syntax:

    grep <apm sessionID> /var/log/apm | grep S4U

    Output appears similar to the following:

    ae78de16: S4U ======> - fetched S4U2Self ticket for user: user1@EXAMPLE.COM
    ae78de16: S4U ======> trying to fetch S4U2Proxy ticket for user: user1@EXAMPLE.COM server: HTTP/example.com@EXAMPLE.COM
    ae78de16: S4U ======> fetched S4U2Proxy ticket for user: user1@EXAMPLE.COM: HTTP/example.com@EXAMPLE.COM
    ae78de16: S4U ======> OK!

    The S4U2Self is a ticket the BIG-IP APM system requests on behalf of the user to itself. If the request fails, perform the following verifications:

    • Ensure that the host/apm.example.com configuration on the BIG-IP APM Kerberos SSO object is correct and matches the value of the userPrincipalName of the service account in AD.
    • Verify that you have added the SPN to the service account with the following command syntax on the domain controller:

      setspn -A host/<name>.<domain> <samaccount_name>

      For example:

      setspn -A host/apm.example.com samaccountname

    • Verify there are no duplicate SPNs on the domain controller. To do so, use the following command:

      setspn -X

    • The S4U2Proxy is a ticket to access the service provided by the web servers the BIG-IP APM system requests on behalf of the user. If this request fails, verify that Kerberos constrained delegation is configured for the HTTP service, HTTP/example.com@EXAMPLE.COM your web server is providing. This is configured at the Delegation tab of the AD service account. Refer to the Creating an AD service account with Kerberos constrained delegation procedure in K43063049: Configuring BIG-IP APM Kerberos SSO Constrained Delegation for portal access.
