K000162066: Performance Layer 4 virtual server does not forward IKE_SA_INIT traffic to pool member

Type
Support Solution
Published
2026-07-10
Updated

Applies to

  • BIG-IP LTM: 17.0.0, 17.1.0, 17.0.X, 21.X.X, 17.X.X, 21.1.X, 21.1.0, 21.0.X, 21.0.0, 17.5.X, 17.5.1, 17.5.0, 17.1.X, 17.1.3, 17.1.2, 17.1.1
Source
https://my.f5.com/manage/s/article/K000162066

Description

When a BIG-IP is configured as Performance (Layer 4) virtual server with a FastL4 profile to forward IKE_SA_INIT (IKEv2) VPN traffic on UDP port to a next hop through the pool member. The pool member is configured to act as the gateway for forwarding traffic to the next hop.

The virtual server receives the traffic but does not forward it to the pool member. The VPN tunnel fails to establish because the IKEv2 negotiation does not complete.

[root@F5.Active:In Sync](/Common)(tmos)# tcpdump -nni 0.0 host <Virtual_server_IP> and port 500
13:14:26.201463 IP <SOURCE_IP>.500 > <Virtual_server_IP>.500: isakmp: parent_sa ikev2_init[I] in slot1/tmm1 lis= port=0.40 trunk=
13:14:29.203974 IP <SOURCE_IP>.500 > <Virtual_server_IP>.500: isakmp: parent_sa ikev2_init[I] in slot1/tmm1 lis= port=0.40 trunk=
13:14:35.207078 IP <SOURCE_IP>.500 > <Virtual_server_IP>.500: isakmp: parent_sa ikev2_init[I] in slot1/tmm1 lis= port=0.40 trunk=

The condition is its VPN tunnel traffic passing through the BIG-IP, not the VPN tunnel between the BIG-IP to the peer device.

 

Environment

  • Performance (Layer 4) virtual server with FastL4 profile
  • Internet Protocol Security (IPsec) VPN traffic
  • VPN traffic forwarding through BIG-IP

Cause

The virtual server has translate-address set to disabled. This setting has two different effects depending on where the pool member is located:

  • When the pool member is on the same network as the VIP: The BIG-IP system forwards the packet with the original destination IP address preserved. This is the correct behavior for pass-through topologies and works as expected.

  • When the pool member is on a different network than the VIP: The BIG-IP system still forwards the packet with the original destination IP address (the VIP). It then tries to find the VIP on the external network using ARP. Because the VIP is the BIG-IP system's own address, no device ever responds to the ARP request. The packet waits for a reply that never arrives and is dropped. The internal network path to the pool member is never used.

Recommended Actions

The fix is to set translate-address to enabled. This causes the BIG-IP system to rewrite the destination IP address to the pool member's IP address before forwarding, so the packet is routed correctly through the internal network.

  1. Confirm traffic is arriving but not being forwarded

    Run the following command, replacing <vip_ip> with the Virtual server IP address of the IKE peer:

    #tcpdump -nni 0.0 host <client_ip> and udp port 500

    You see only IN copies with no OUT copies:

    IP <client_ip>.500 > <vip_ip>.500: isakmp: parent_sa ikev2_init[I] in slot1/tmm1 lis= port=0.40 trunk=
IP <client_ip>.500 > <vip_ip>.500: isakmp: parent_sa ikev2_init[I] in slot1/tmm1 lis= port=0.40 trunk=

    A working configuration produces both IN and OUT copies:

    IP <client_ip>.500 > <vip_ip>.500: isakmp: parent_sa ikev2_init[I] in slot1/tmm1 lis= port=0.40 trunk=
IP <client_ip>.500 > <pool_member_ip>.500: isakmp: parent_sa ikev2_init[I] out slot1/tmm1 lis= port=0.40 trunk=
  2. Confirm pool member server-side egress traffic

    Run the following command, replacing <pool_name> with the name of your pool:

    #tmsh show ltm pool <pool_name> detail

    The output shows Bits In greater than zero but Bits Out equal to zero:

      Traffic                   ServerSide
  Bits In                       1.4G
  Bits Out                         0    ← packets not leaving server-side
  Packets In                     2.1M
  Packets Out                      0
  3. Confirm the virtual server has translate-address disabled

    Run the following command, replacing <vs_name> with the name of your virtual server:

    #tmsh list ltm virtual <vs_name> translate-address translate-port

    The output shows:

    ltm virtual <vs_name> {
    translate-address disabled  → Note the setting is disabled
    translate-port    disabled
}
  4. Confirm the ARP failure

    Run the following command, replacing <vip_ip> with your VIP address:

    #tcpdump -nni 0.0 host <vip_ip>

    You can see repeated unanswered ARP requests for the VIP sourced from the external self-IP address, immediately following each IKE_SA_INIT arrival:

    IP <client_ip>.500 > <vip_ip>.500: isakmp: parent_sa ikev2_init[I] in slot1/tmm1 lis= port=0.40 trunk=
ARP, Request who-has <vip_ip> tell <external_self_ip>  out slot1/tmm0
ARP, Request who-has <vip_ip> tell <external_self_ip>  out slot1/tmm0
ARP, Request who-has <vip_ip> tell <external_self_ip>  out slot1/tmm0
ARP, Request who-has <vip_ip> tell <external_self_ip>  out slot1/tmm0
  5. Confirm the pool member routes via the internal VLAN

    Run the following commands, replacing <pool_member_ip> with the pool member IP address:

    #tmsh show net arp | grep <pool_member_ip>
#ip route get <pool_member_ip>

    If the pool member ARP is resolved via the internal VLAN and the route exits via the internal interface, the pool member is on a different subnet than the VIP which confirms that translate-address enabled is required.

    Example output:

    <pool_member_ip>  resolved  /Common/<internal_vlan>
<pool_member_ip> dev <internal_vlan>  src <internal_self_ip>
  6. Confirm the connection table entry shows the wrong server-side destination

    Run the following command, replacing <vip_ip> with your VIP address:

    #tmsh show sys connection ss-server-addr <vip_ip> ss-server-port 500

    The server-side destination IP matches the VIP address instead of the pool member IP address:

    <client_ip>:500  <vip_ip>:500  <client_ip>:500  <vip_ip>:500  udp
  7. Enable translate-address on the virtual server

    Replace <vs_name> with the name of your virtual server:

    #tmsh modify ltm virtual <vs_name> translate-address enabled
#tmsh save sys config

    Verify the change is applied:

    #tmsh list ltm virtual <vs_name> translate-address translate-port

    The output should show:

    ltm virtual <vs_name> {
    translate-address  enabled
    translate-port     disabled
}
  8. Clear existing stale connections

    Replace <vip_ip> with your VIP address:

    #tmsh delete sys connection ss-server-addr <vip_ip> ss-server-port 500

    Existing connections use the flow state in place when established. Clearing stale connections ensures new flows use the updated setting.

  9. Trigger a new IKE_SA_INIT from the remote peer

    Confirm that both IN and OUT copies now appear:

    #tcpdump -nni 0.0 host <client_ip> and udp port 500

    Expected output after the fix:

    IP <client_ip>.500 > <vip_ip>.500: isakmp: parent_sa ikev2_init[I] in slot1/tmm1 lis= port=0.40 trunk=
IP <client_ip>.500 > <pool_member_ip>.500: isakmp: parent_sa ikev2_init[I] out slot1/tmm1 lis= port=0.40 trunk=
  10. Confirm connection table and traffic counters 
    #tmsh show sys connection ss-server-addr <pool_member_ip> ss-server-port 500
#tmsh show ltm pool <pool_name> members detail
