Description
While attempting to add a Standby BIG-IQ, it fails with an error similar to the following in the GUI:

An error occurred while adding the BIG-IQ: ERROR: Failure executing pg_basebackup. status: 1 ERROR: Failure establishing streaming replication on the standby. Error code: 1 /usr/bin/ha_streaming_replication: line 25: 27623 Terminated ( sleep "$sleep_time" & local sleep_pid="$!"; trap "kill $sleep_pid 2>/dev/null" EXIT; wait "$sleep_pid"; kill "$cmd_pid" 2> /dev/null ) ERROR: Failure establishing streaming replication with standby. Restored the standby database to its previous state

An error will be logged in restjavad logs with a message:
ERROR: Failure executing pg_basebackup. status: 1
ERROR: Failure establishing streaming replication on the standby. Error code: 1

Additionally, a similar error will be logged in /var/log/ha.log

Interface packet captures show a TCP connection from the Standby to the Active on port 5432, which is torn down after the TLS Encrypted Handshake Message. The connection ends before any application data is sent over the connection. The failed connection is the Postgres utility pg_basebackup attempting to establish a streaming connection to Postgres on the Active and copy the Active BIG-IQ database.

Environment

  • BIG-IQ CMs forming an HA pair
  • Hostname and IP not matching  in postgresql certificate
  • or expired postgresql certificate

Cause
This TLS failure is caused by host name values in the certificate used by Postgres on the Active BIG-IQ that do not match the IP address on the Active BIG-IQ that is being connected to or expired certificate of Active BIG-IQ device

For example, if the /var/lib/pgsql/config/server.crt certificate on the Active BIG-IP has a CN that matches the IP address of the management-ip but the self-ips are specified during the HA setup, the pairing would fail the TLS handshake when the Standby attempted to establish a streaming connection. 

Example:
If the Active BIG-IQ had the following IP addresses:
192.0.2.180        Management-IP
203.0.113.180    Self-IP

And the Postgres certificate on The Active contained these CN values:
issuer= /CN=192.0.2.180/O=F5 BIG-IQ System
subject= /CN=192.0.2.180/O=F5 BIG-IQ System

If the Standby BIG-IQ attempts to connect to 203.0.113.180, the TLS handshake will fail for the streaming replication because "203.0.113.180" does not match the certificate CN "192.0.2.180"
 

Or expired certificate example

openssl x509 -in /var/lib/pgsql/config/server.crt -startdate -enddate -noout

notBefore=Jan 26 13:24:42 2022 GMT

notAfter=Jan 25 13:24:42 2023 GMT. <<  date before current date

Recommended Actions

  1. Use to following openssl command on the Active BIG-IQ to verify that the certificate has the proper CN host name values:
    openssl x509 -in /var/lib/pgsql/config/server.crt -issuer -subject -startdate -enddate -noout

  2. If the CN values in the output from step #1 do not equal the IP address on the Active used for HA generate a new Postgres certificate with the correct CN values:
    ha_generate_certs  -f <BIG-IQ Local Discovery Address>

    Note: Each HA certificate must contain the Discovery IP configured on the same BIG-IQ device it is generated on. The Discovery address can be identified in the BIG-IQ GUI: System > This Device > General Properties

Additional Information

All files must be owned by postgres to allow replication of the db to take place.
The ERROR message can also be caused by incorrect file permissions on the Primary CM in /var/lib/pgsql/data
cd /var/lib/pgsql/data

Verify that all files are owned by postgres:
ls -l

Modify any files that are not owned by postgres:
chown postgres:postgres <filename>
