Description

A BIG-IP Access Policy Manager (APM) virtual server does not allow Application Security Manager (ASM) and/or Fraud Protection Services (FPS) features during access policy (AP) evaluation. You can move your ASM and/or FPS profiles to a layered virtual server in front of the APM to protect it while establishing an APM session. 

Environment

  • BIG-IP APM
  • BIG-IP ASM 
  • BIG-IP FPS

Cause

The APM module is first in the Hud Chain, preventing ASM features from firing during AP evaluation.

Recommended Actions

Create an ASM/FPS layered virtual server in front of the APM virtual server, so that it will fire before AP evaluation on each request.

What you will need:

  • An additional private IP address as the new destination IP address on the APM virtual server.
  • New ASM virtual server that has the original destination IP and port that DNS resolves and/or is NAT'd to, as well as all the ASM and profiles.
  • New iRule on the new ASM virtual server to make it a layered virtual server. For more information refer to K03113285: Overview of BIG-IP APM layered virtual servers

Steps to fix existing APM/ASM/FPS virtual server:

  1. Select a private IP address to use as the new destination for the APM virtual server which will handle all traffic that comes through the layered ASM virtual server.
    This IP will also make it possible to complete step #3, as the destination IP is unique on each virtual server.
  2. Create the following iRule that will be applied to the new layered ASM virtual server, making sure to change <nameOf_apmVs> to the actual name of your APM virtual server:
when CLIENT_ACCEPTED { 
virtual <nameOf_apmVs>
} 
  1. Create a new layered ASM virtual server and move all necessary ASM profiles/policies from the APM virtual server to the new layered ASM virtual server and set the destination IP to the original IP address that DNS resolved to on the APM virtual server.
