Description

After attempting to update the NGINX App Protect attack signatures, the App-Protect service fails to start.

Environment

The log entry that identified the probable cause:BD_MISC|CRIT  |Mar 27 21:04:17.428|3640329|/builds/t1_j2fGn9/7/waf/waf-general/secore/bd/bd/manifest_listener.cpp:0125|read_manifest failed, about to exit. info:

"jobCreateDatetime":"2026-03-27T21:04:17Z",
"messages":["CONFIG_TYPE_PROTOBUF_FILENAMES message had parsing error: could not parse protobuf message","CONFIG_TYPE_PROTOBUF_FILENAMES message had errors in block_index: 0. status=-1","CONFIG_TYPE_MANIFEST message had parsing error: could not parse protobuf message","failed to read dynamic data from file"],

Breakdown on the 2 components that point to an issue...

  • CONFIG_TYPE_PROTOBUF_FILENAMES message had parsing error: Corrupted/mismatched/missing file, version mismatch, or permissions
  • CONFIG_TYPE_MANIFEST message had parsing error: Same as above

Cause

The logs indicated parsing errors and failures related to signature files, resulting in the service remaining down until the corrupted or mismatched signature package is purged and reinstalled.

In the bd logs it is indicating that the signature file used was either...

  • Corrupted
  • Incomplete
  • Mismatched with the running engine version 
  • or has incorrect permissions.

Answer/Recommended Actions

In many cases purging the signatures will correct the issue and allow the update to work.

1) Purge the signatures.sudo apt purge app-protect-attack-signatures

2. then install a non-corrupted and version matching set of signatures.sudo apt install app-protect-attack-signatures

3) Then restart the service;sudo systemctl restart nginx-app-protect.service

These steps will often allow the update to take place and correct the issue. If updating the signatures continues to be a problem or the log messages persist run the following Plan of Action (PoA). 

Enable F5 WAF for Nginx debug logging, reproduce the issue, tar logs and share the tar log files.

Enabling debug mode for the bd process without restarting the bd process

1. Log in to the command line.

2. Create a backup copy of the /etc/ts/bd/logger.cfg file using the following command:cp /etc/app_protect/bd/logger.cfg /etc/app_protect/bd/logger.cfg.bak

3. Add the following lines:  MODULE=ECARD_POLICY;
  LOG_LEVEL=TS_INFO | TS_DEBUG;
  FILE = 2;
  
  MODULE=BD_MISC;
  LOG_LEVEL=TS_INFO | TS_DEBUG;
  FILE = 2;
  
  MODULE = ALL;
  LOG_LEVEL = TS_ERR | TS_CRIT | TS_WARNING | TS_NOTICE;
  FILE=2;

4. Save and exit the logger.cfg file.

  Note: If the logger.cfg format is not correct, the system uses the last good configuration of the logger.cfg file.

5. Reproduce the issue.

After completing F5 WAF for NGINX debug testing, return the logging levels to the default configuration to avoid excessive logging by performing the following procedure:

1. Copy the /etc/ts/bd/logger.cfg_sol9955 to /etc/ts/bd/logger.cfg backup file.cp /etc/app_protect/bd/logger.cfg.bak /etc/app_protect/bd/logger.cfg

2. Generate and upload tar logs.tar -czpf /var/tmp/$HOSTNAME-logs.`date "+%F"`.tar.gz /var/log/*

3. Run the steps here F5 WAF for NGINX Support to include the additional information needed for the case.

4. Then open a case with f5 Support and upload the files to it.  K000090853: Exchange files with F5 Support
