Disabling Strict Updates

iApps deploys much of the SSL Orchestrator's configuration, and that configuration is largely controlled by the Strict Updates feature. Strict Updates locks the BIG-IP configuration objects deployed by SSL Orchestrator, and you can only edit them using the SSL Orchestrator user interface. You cannot edit them using BIG-IP system interfaces.

To modify SSL Orchestrator configurations in ways that are not supported by the SSL Orchestrator interface, you must first disable Strict Updates. This allows you to change the configuration of the objects that are deployed by iAppLX template. However, if you later need to modify those SSL Orchestrator objects, you first have to re-enable Strict Updates to correctly deploy those changes. Re-enabling Strict Updates overwrites without warning any earlier changes made that required you to disable it.

If you need to disable Strict Updates, make sure to document the change in case you need to change the configuration later. After you make a change to the SSL Orchestrator, you should go back and verify that your earlier modifications to the underlying objects still exist and, if they don't, you should re-implement the removed or modified objects.

The Strict Updates control exists in most SSL Orchestrator objects. Disabling it on one object does not disable it on another. Make sure that you disable the Strict Updates control for each object that requires it.

Important: You should always make sure to back up your system before making modifications to it.

Changing rules and rule objects

The objects created when you add and modify rules, especially the BIG-IP APM per-request policies, are more stable and are not protected by Strict Updates. However, the system can overwrite these objects when you modify the default rules or the SSL Orchestrator per-request policy item in the Visual Policy Editor (VPE); therefore, you should check them after you make any modifications.

The examples in this document describe how to change the default BIG-IP APM per-request policy called ssloP_<chain name>_prpTcp.(<chain name> is the name of the policy item chain.) In most implementations, there are two BIG-IP APM per-request policies: one for TCP and one for User Datagram Protocol (UDP). In many cases, you only have to modify the TCP per-request policy when the modification only affects TCP, for example when the policy is for HTTP or HTTPS traffic. However, if the modification can impact UDP traffic, you may also need to implement the change in the ssloP_<chain name>_prpUdp per-request policy.

In addition, you can create additional SSL Orchestrator per-request policies, which result in additional BIG-IP APM per-request policies. In these cases, you may also have to modify these additional policies if iRules uses them. For more information, refer to the SSL Orchestrator Architecture Guide Version 14.0.0-4.0.

Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

Flagging objects with official F5 workarounds

Making changes to any objects marked for Strict Updates is not supported, and F5 Technical Support may ask you to re-enable Strict Updates before troubleshooting SSL Orchestrator.

Note: Re-enabling Strict Updates overwrites changes and resets SSL Orchestrator to the factory-default configuration.

However, F5 Technical Support supports official workarounds published and approved by F5. You can indicate these workarounds on a BIG-IP system by appending the object description with the following syntax. Doing so can help you and F5 Technical Support identify objects that are modified with approved F5 workarounds.

MOD:<modification name>.

For example, if you are instructed to add SNAT to a service, after you disable Strict Updates, append the description with the following text:

MOD:ADDED-SNAT

Determining where to modify a policy

Before modifying your policy, you need to determine the location of the information in the policy chain that you'll need to make changes. For example, in the default TCP per-request policy, decryption happens after the SSL Intercept Policy macro, so you cannot determine how to modify the TCP per-request policy based on any encrypted information, such as HTML or HTTP.

The following figure shows information available at various points in the policy. This information may change as it moves through each macro, so it is important to pay careful attention to what each policy item does. Considering this information important when you're designing changes to the policy. For more information, refer to the SSL Orchestrator Architecture Guide Version 14.0.0-4.0.

Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.
 

  1. The policy receives traffic. At this point you can determine the IP address, the TCP and UDP port information, and whether the traffic is encrypted. You can also look at the content for things like URIs and HTTP headers.
  2. Following the Categorization macro, the URL category is available, but unencrypted information, such as HTTP headers, is not yet available.
  3. Following the SSL Intercept Policy macro, decrypted content is available due to the SSL Intercept Set policy item within the SSL Intercept Policy macro.
  4. Following the Service Chain macro, content may have been modified by individual policy items. You can see the final content before it's re-encrypted and sent to its destination.

For example, you can't determine a branch or block based on the URL category of some HTTPS traffic until after it's categorized, which happens in the Categorization macro. Therefore, you need to add the Categorization macro in front of the SSL Intercept Policy macro.

Note: Keep in mind that your policy may need to handle failures. For example, in the default IP Policy macro, if the IP Reputation lookup policy item fails, the system continues to process traffic. Be sure to take such possibilities into account for your implementation to avoid unexpected behavior.

Blocking HTTP and HTTPS traffic based on URL

To block traffic when the system encounters a particular URL, you can use URL categories. If you have URL Filter or Secure Web Gateway (SWG) licensed and set up, you can make policy design decisions based on pre-defined categories; however, even if you don't have these features available, you can create custom categories with URLs you define and use those to help make your decisions.

Note: Before you implement the following use case, refer to the Modifying the policy section of this article.

The URI that the system matches is based on the Category Lookup policy item in the Categorization macro. For more information, refer to the SSL Orchestrator Architecture Guide Version 14.0.0-4.0.

Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

Creating a custom category

Note: You need to perform this procedure only if you are not filtering based on URL Filtering or SWG categories.

  1. Navigate to SSL Orchestrator > Policies > URL Categories.
  2. Click Create.
  3. Type the name of the URL category.
  4. For Associated URLs, enter a URL you want to block in the URL box, and click Add. Repeat this step until you've added all of the URLs you want to block.
  5. Click Save.

Creating an additional intercept chain and choosing the appropriate intercept chain based on IP Intelligence or IP Geolocation

The following workaround example describes how to select a different intercept chain. The example intercept chain provides enhanced scanning for traffic from North Korea or other traffic with a suspicious reputation.

Note: To use IP Intelligence information and IP Geolocation, you need to have them licensed and configured on your BIG-IP system.

By default, the IP Policy macro blocks specified traffic. In the following procedure, you modify the macro to instead set a flag to use a different chain, build a new chain macro, and link the macro to the SSL Intercept Policy by looking for the set variable.

Note: Before you implement the following use case, refer to the Modifying the policy section of this article. Also, make sure that you have the required services set up that will be providing the enhanced scanning.

Opening the per-request policy

  1. Navigate to SSL Orchestrator > Policies > Access Per-Request Policies.
  2. Find ssloP_<chain name>_prpTcp.

    Note: <chain name> is the name of your policy chain.

    Note: You can filter by typing the policy name in the box and clicking Search.

  3. Under Per-Request Policy, click the + icon next to Show All.

Modifying the IP Policy macro

  1. Click ssloP_<chain name>_prpTcp.

    The Visual Policy Editor opens.

  2. Click the + icon next to Macro: IP Policy to expand the macro.
  3. Click Macro Settings / Rename.
  4. For One-Shot Macro, click Yes and click Save.
  5. Click the Server IP Geolocation Match policy item.
  6. Click the Branch Rules tab.
  7. Change the name of the branch to IP Geolocation Country code is KP.
  8. Click Change and modify the Country code to KP.

    Note: KP is the ISO 3166-1 alpha-2 country code for North Korea.

  9. Click Finished and then click Save.
  10. Click the Server IP Reputation policy item.
  11. Click the Branch Rules tab.
  12. Change the branch name Good to Questionable.

    By default, if there is no information for address, the branch flags the address as good. Updating it to Questionable requires the policy item to perform enhanced scanning.

  13. Click Save.
  14. In the IP Policy macro, click the Failed terminal to edit it.
  15. For Select Terminal, click Passed and then click Save.

    Note: In your deployment you may want to keep the Failed terminal in some circumstances, but in this example the macro does not block anything but instead performs more scanning.

  16. On the fallback branch for the Server IP Reputation policy item, click the + icon to add a new policy item.
  17. On the Assignment tab, click Variable Assign and then click Add Item.

  19. Click Add new entry and in the new entry, click change.
  20. In the Custom Variable box, type session.custom.scan_level.
  21. In the Custom Expression list, click Text, and in the Text box, type normal.
  22. Click Finished and then click Save.
  23. Edit the remaining three macro terminal branches by repeating steps 16-20 for each branch.

    Note: Because the Failed branch is not used, this step should have no impact for this use case; however, setting it to Reject ensures future traffic it is correctly handled.

  6. Click Save.

Selecting the Non-Intercept chain based on IP information

You can configure BIG-IP systems in a specific IP network to use the Non-Intercept policy chain so that their traffic is not decrypted. You may need to do this, for example, if you want to scan some payment processing servers for attacks but do not want to decrypt the traffic.

To do this, you can build a new macro to filter IP addresses. It's also possible to use the IP Services macro and replace items in it, this example describes how to build a new macro.

For performance reasons, it's important that you configure IP branching in its own macro. You don't need to do this in the IP Services macro, but the macro needs to have the One-Shot macro option set to Yes. This allows the IP Services to run once per TCP connection instead of running every request. This saves a significant amount of time.

Also, in this example, you bypass the Categorization steps for any matching traffic since you already know what type of traffic it is. In a live configuration, this may not be true.

Note: Before you implement the following use case, refer to the Modifying the policy section of this article and make sure that you have the required services set up for enhanced scanning.

Opening the per-request policy

  1. Navigate to SSL Orchestrator > Policies > Access Per-Request Policies.
  2. Find ssloP_<chain name>_prpTcp.

    Note: <chain name> is the name of your policy chain.

    Note: You can filter by typing the policy name in the box and clicking Search.

  3. Under Per-Request Policy, click the + icon next to Show All.
  4. Click ssloP_<chain name>_prpTcp.

    The Visual Policy Editor opens.

  5. In the main per-request policy, click Add New Macro.
  6. Using the Empty macro template, in the Name type Handle Payments, and click Save.
  7. Click the + icon next to Macro: Handle Payments to expand the macro.
  8. On the fallback branch, click the + icon to add a new policy item.
  9. Click the General Purpose tab, click Empty, and then click Add Item.
  10. On the Properties tab, name the policy item Check Source Address.
  11. Click the Branch Rules tab, click Add Branch Rule, and name the branch rule Payment Processor.
  12. For Expression, click change and then click Add Expression.
  13. For Agent Sel, click IP Subnet Match.

    Note: If you want to match a TCP or UDP port, click Port match.

  14. For Condition, click Client IP Subnet Match because you want the system to detect traffic from payment processors.
  15. For Client IP Subnet is type the address of the network containing the payment processors.

    Note: This use case example uses 192.0.2.0/24 , but your network should be a single system with an IPv4 mask of /32 or a smaller network range.

  16. Click Finished and then click Save.
  17. Click Edit Terminals.
  18. Rename the Out terminal to Other.
  19. Click Add Terminal, name the new terminal Payment, then click Save.
  20. Click the terminal on the Payment Processor branch, click Payment, and click Save .

Integrating macros into the base policy

  1. In the base policy, click the + icon on the Categorization fallback branch.
  2. Click the SSLO Macros tab, click Handle Payments, and then click Add Item.
  3. (Optional): If the Handle Payment terminal goes to the Categorization macro, click the swap icon (>>) on the branch next to the Categorization macro and then click the arrow next to Other.
  4. Next, add in the non-intercept chain again for the payment branch.

    Note: Before traffic passes to an intercept chain or a non-intercept chain, it must go through an SSL Orchestrator Intercept Set or SSL Orchestrator Bypass Set policy item.

    On the Handle Payments branch, click the + icon, click the General Purpose tab, click SSL Bypass Set, click Add Item, and then click Save.

  5. Save the policy item.
  6. Click the + icon to add the Service Chain Not Intercepted macro after the bypass set you just added.

Note: Because the Categorization macro gets bypassed, the policy cannot perform any Categorization activities based on URL or protocols.

Configuring HTTP to bypass chains, based on user group

You can configure a policy so that user traffic that belongs to the no_intercept group bypasses the SSL Orchestrator. In this use case, the BIG-IP APM system is licensed and is set up for authentication.

Note: Before you implement the following use case, refer to the Modifying the policy section of this article and make sure that you have the required services set up for the enhanced scanning.

  1. Navigate to SSL Orchestrator > Policies > Access Per-Request Policies.
  2. Find ssloP_<chain name>_prpTcp.

    Note: Replace <chain name> with your policy chain name.

    Note: You can filter by typing the policy name in the box and clicking Search.

  3. Under Per-Request Policy, click the + icon next to Show All.
  4. Click ssloP_<chain name>_prpTcp.

    The Visual Policy Editor opens.

  5. Click the + icon immediately before the Categorization macro.
  6. Click the General Purpose tab, click Empty, and click Add Item.
  7. For Name, type Check Bypass Group.
  8. Click the Branch Rules tab and click Add Branch Rule.
  9. For Name, type bypass.
  10. For Expression, click change to edit.
  11. Click the Advanced tab and enter the following expression in the box:

    expr { [mcget {session.ad.last.attr.memberOf}] contains "CN=no_intercept, CN=Users, DC=domain.com" }

  12. Click Finished.
  13. Click Save.

Remapping ports for inbound traffic

To use the Port Remap option for inbound traffic, you need to add an iRule to the interception rule to allow the system.

Updating the interception rule

Note: This procedure assumes that you chose the Advanced configuration when creating the inbound rule. If you did not, you do not see the iRules and have to recreate the interception rule.

  1. Install the SSL Orchestrator Extras library.

    Note: Refer to Using the SSL Orchestrator Extras Library.

  2. Navigate to Local Traffic> iRules.
  3. Click Create.
  4. For Name, type allow_remap_ports.
  5. In the Definition box, enter the following:

    When CLIENT_ACCEPTED { call /Common/sslo_extras/set_ctx_to_https null }

  6. Click Finished.
  7. Navigate to SSL Orchestrator > Deployment> Interception Rules.
  8. From the list, click the inbound interception rule that contains the service in question.
  9. Under Resources, for iRules add the new allow_remap_ports iRule to the interception rule.

Configuring SSL Orchestrator to use an upstream explicit proxy

To configure explicit proxy chaining, which is the BIG-IP system sending data to an upstream explicit proxy device, you need to add proxy chaining macros to the BIG-IIP ASM default policy.

To have the BIG-IP system correctly send traffic to an upstream explicit proxy, you need to add the HTTP Connect header to the traffic since the system cannot re-encrypt the traffic before sending it.

To add the HTTP Connect header, you can add the Proxy Chaining(Connect) and Proxy Chaining(URI Rewrite) macros into the default policy. Proxy Chaining(Connect) initiates the connection with the upstream proxy to verify and forge the end certificate, and the Proxy Chaining(URI Rewrite) macro rewrites the headers for the connection.

Note: Before you implement the following use case, refer to refer to the Modifying the policy section of this article.

Creating the Pool

  1. Navigate to Local Traffic > Pools.
  2. Click Create.
  3. For Name, type sslo_xp_pool.
  4. For Health Monitors, click gateway_icmp in the Available list and move it to the Active list.
  5. Under Resources, for New Members add the upstream explicit proxy addresses to the members list.
  6. Click Finished.

Modifying the policy

  1. Navigate to SSL Orchestrator > Policies > Access Per-Request Policies.
  2. Find ssloP_<chain name>_prpTcp.

    Note: Replace <chain name> with your policy chain name.

    Note: You can filter by typing the policy name in the box and clicking Search.

  3. Under Per-Request Policy, click the + icon next to Show All.
  4. Click ssloP_<chain name>_prpTcp.

    The Visual Policy Editor opens.

  5. Click Macro: Proxy Chaining(Connect).
  6. Click the Proxy Connect policy item.
  7. For Pool, click /Common/sslo_xp_pool.
  8. For Upstream Proxy Mode, click Explicit, No URI Rewrite.

    Note: If you omit this step, only HTTPS traffic passes through the proxy.

  9. Click Save.
  10. Click Macro: Proxy Chaining(URI Rewrite) macro.
  11. Click the Proxy URI Rewrite policy item.
  12. For Pool, click /Common/sslo_xp_pool.

    Note: You do not need to add any custom headers to the configuration. SSL Orchestrator automatically handles this.

  13. Click Save.
  14. In the base policy, click the + icon immediately before the Categorization, click the SSLO Macros, click Proxy Chaining(Connect), and then click Add Item.
  15. Choose a branch that terminates in Allow, and click the + icon on the branch between the last policy item and the terminal.
  16. Click the SSLO Macros tab, click Proxy Chaining(URI Rewrite) macro, and then click Add Item.
  17. Repeat steps 15 and 16 on each branch that terminates in Allow.

Managing Forward Proxy Authentication

The BIG-IP system can provide user authentication to SSL Orchestrator before traffic passes through the services. The system can then use gathered authentication information for policy branching decisions. For more information, refer to the Configuring HTTP to bypass chains, based on user group section of this article.

Note: Your BIG-IP system must be licensed and configured for it to support authentication.

Note: SSL Orchestrator only supports authentication on explicit proxy connections. It does not transparent proxy connections.

For more information, refer to the Managing Forward Proxy Authentication  chapter of the F5 SSL Orchestrator Deployment Guide on F5 Cloud Docs.

Updating the interception rule

This procedure assumes that you have set up the default rules for the policy, including an explicit proxy rule.

  1. Navigate to SSL Orchestrator > Deployment > Interception Rules.
  2. Click the outbound explicit proxy rule <sslo system name>-xp-[4/6].
  3. In the Access Policy box, click the /Common/sslo_xp_session policy you created.
  4. Under Resources, for iRules, in the Available list, click the Common/<sslo_system name>.app/<sslo system name>-xp-auth iRule and move it to the Selected list.
  5. Click Finished.

Setting policy to bypass ICAP services

Internet Content Adaptation Protocol (ICAP) services can use BIG-IP LTM policies to choose which traffic is sent to the services. ICAP services are enabled by default, but if you want specific types of HTTP traffic, such as empty non-POST requests, to bypass ICAP services .you configure the BIG-IP LTM policy to select the traffic that you do not want to be processed and disable ICAP.

For more information on setting up ICAP policies, see the SSL Orchestrator Architecture Guide Version 14.0.0-4.0.

In this procedure, you disable all ICAP processing for traffic that is destined for our credit card processor so that sensitive traffic is not decrypted or stored in the logs of the ICAP server.

Note: In this example, you disable both request and response processing; however, you can disable only one of the two if it better fits your situation.

Creating the BIG-IP LTM policy

  1. Navigate to Local Traffic > Policies.
  2. Click Create.
  3. For Policy Name, type sslo_skip_cc.
  4. Click Create Policy.
  5. Create a new iRule by clicking Create.
  6. For Name, type sslo_skip_cc_rule.
  7. Add a match condition by clicking the + icon.
  8. Set Match all of the following conditions, to HTTP URI host is any of api.cc_example.com at request time.
  9. Click Save.
  10. For Do the following when the traffic is matched, click the + icon, and set to Disable request adapt at request time.
  11. Repeat the previous steps 8 and 9 and set to the item to Disable response adapt at request time.
  12. Click Save.
  13. Hover on Save Draft and click Save and Publish Policy.

Attaching the policy to the service

  1. Navigate to SSL Orchestrator > Services > ICAP Services.
  2. Click the ICAP service you want to attach the policy to.
  3. Under ICAP Services, for ICAP Policy, click the policy you created.

Configuring VLANs for L2 wire Interfaces

Before you choose a Layer2 (L2) network, you need to configure the BIG-IP system. In this example, you configure interfaces 1.1 and 1.2 as part of the virtual wire and add VLAN 100 to the virtual wire interface.

  1. Connect to the SSL Orchestrator CLI and login as root.
  2. Create networks using the following commands:
    • (tmsh)# modify net interface 1.1 port-fwd-mode virtual-wire.

Configuring SNI for inbound listeners

If you have multiple HTTPS servers inside the network to which you want to provide access, you can have SSL Orchestrator choose the certificate to send to the client, based on Server Name Indication (SNI).

By default, an inbound rule can only support one SSL Settings group, which in turn can only support one host, although it can support multiple certificate types per host. If you want to configure an inbound interception rule with a network destination address instead of a single host, you may need to configure SNI to handle selecting certificates.

In this example, you create the inbound interception rule, then create an additional Client SSL profile to attach to it. In a production environment, you may need multiple additional Client SSL profiles, depending on how many certificates you need to offer.

Important: Before making this change, refer to the warnings and information in the Disabling Strict Updates section of this article.

This example assumes that you have the certificates and keys needed uploaded already on the BIG-IP system.

Creating an interception rule

  1. Navigate to SSL Orchestrator > Deployment > Interception Rules.
  2. Click Create Inbound Rule.
  3. For Name, type sslo_inbound.
  4. For Description, add MOD:ADDED_CSSL_PRO to the end of the description.

    Note: This description tells F5 Technical Support that you are using the official modification for this workaround..

  5. Under Ingress Network, in the Available list, click the outside VLAN you want to use and move it to the Selected list.
  6. On the SSL Management tab, for Name, type ssloT_sslo_inbound.
  7. Under Client-side SSL, add certificates and keys.
  8. Click Finished.
  9. On the Inceptions Rules tab, under Security Policy, for SSL settings, click Create New.
  10. Under Security Policy, for L7 Profile Type, click HTTP.
  11. For L7 Profile, click /Common/sslo_<system name>-http.
  12. For Access Profile, click /Common/ssloP_<SSL Orchestrator per-req-policy>.app/ssloP_<sslo per-req-policy>_accessProfile.
  13. For Per-request Policy, click /Common/ssloP_<SSL Orchestrator per-req-policy>.app/ssloP_<sslo per-req-policy>_prpTcp.
  14. Click Finished.

Unlocking the application

  1. Navigate to SSL Orchestrator > Deployment > Deployment Settings.
  2. For Strict Update, clear the check box.
  3. For Description, add MOD: INBOUND_SNI to the end of the description.

    Note: This description tells F5 Technical Support that you are using the official modification for this workaround..

  4. Click Finished.

Creating Client SSL profiles

  1. Navigate to Local Traffic > Virtual Servers.
  2. Click the virtual server for the inbound traffic. It should be named sslo_<system name>-<inbound rule name>.
  3. Find and note the name of the SSL Profile (Client). It should be named ssloT_<rule name>-cssl-vhf.

    Note: Make sure to distinguish between the f and the t at the end of the server names.

  4. Navigate to Local Traffic > Profiles > SSL > Client.
  5. Click Create.
  6. Name the profile.
  7. For Parent Profile, click the name of the SSL Orchestrator.
  8. For Configuration, click Advanced and select the Custom check box.
  9. For Certificate Key Chain click Add and for the Add SSL Certificate Key Chain click the appropriate Certificate, Key, and Chain, optionally add a Passphrase, then click Add.
  10. For SSL Forward Proxy, select the Custom check box.
  11. For Certificate Extensions List, if Subject Alternative Name does not appear in the Enabled Extensions box, click it in the Available extensions box and click Enable.
  12. For Default SSL Profile for SNI, select the check box if it is not already selected.
  13. Click Finished.
  14. Repeat steps 5 through 13 for additional required certificates .

    Note: When you create these SSL profiles and link them to the existing one, you need to manually delete or set a different parent profile before you delete the SSL Orchestrator application or clean up the SSL Orchestrator SSL applications. If you don't, the SSL Orchestrator displays an error when you try to delete the existing SSL profile.

Attaching Client SSL profiles to virtual server

  1. Navigate to Local Traffic > Virtual Servers.
  2. Click the inbound traffic virtual server.
  3. Under Configuration, for SSL Profile (Server), click the profile in the Selected list and move it to the Available list.
  4. Click the new Client SSL profiles you created.
  5. Click Update

Adding a monitor to a TAP service

By default, Terminal Access Point (TAP) services are not attached to monitors because TAP services are not inline. That is, if TAP services devices go down, traffic does not fail. However, in some cases, you may want to block traffic if TAP services fail.

Note: TAP services has a policy item on service down option; however, since there is no monitor attached, the BIG-IP system ignores this option.

In this workaround, you add an Internet Control Message Protocol (ICMP) monitor and use an alias to define the address for the BIG-IP system to ping.

Since most monitoring devices using TAP services do not have an address assigned to the interface on which they are monitoring, you have to use a different address for the alias. This may be the management address, or it may be another address on the BIG-IP system.

Note: Because traffic may take a different route to get to the monitored device, the BIG-IP system does not monitor the network or the receiving device. It only monitors access to the interface the BIG-IP system is pinging. This may miss critical outages if they involve the network path between SSL Orchestrator and the monitoring interface.

When you create a TAP device in SSL Orchestrator, no monitor is added to the pool. The TAP device configuration includes an option for action device down but it does not work as expected. Consequently, monitoring information for the pool is inaccurate.

When you change the configuration of certain objects, the BIG-IP system re-deploys the various BIG-IP objects to match your new configuration. This re-deployment overwrites any existing BIG-IP objects without warning about existing changes. Before performing this procedure, you must first refer to the warnings and directions in the the Disabling Strict Updates section of this article.

Creating the monitor

  1. Navigate to Local Traffic > Monitors.
  2. Click Create, and for Name, use a name based on the service to which you want to attach it.
  3. For Type, click Gateway ICMP.
  4. For Transparent, click Yes.
  5. For Alias Address, enter the service device address.
  6. Click Finished.

Updating the service

  1. Navigate to SSL Orchestrator > Services > TAP Services.
  2. Click the service you want to add the monitor to.
  3. Under General Properties, clear the Strict Update check box.
  4. For Description, add MOD:ADD_MONITOR to the end of the description.

    Note: This description tells F5 Technical Support that you are using the official modification for this workaround..

  5. Set Service Down Action, as needed.
  6. Click Finished.

Assigning the monitor to the virtual server

  1. Navigate to Local Traffic > Pools.
  2. Click the pool with the name matching the service.
  3. Under Configuration, click the health monitor you created from the Available list and move it to the Active list.

Configuring external communications for services

In designing a secure SSL Orchestrator system, F5 recommends you not allow service devices to access traffic outside the protected networks. For more information, refer to the SSL Orchestrator Architecture Guide Version 14.0.0-4.0.

Note: For information about how to locate F5 product manuals, refer to K12453464: Finding product documentation on AskF5.

However, service devices may require access to outside traffic for validation, software updates, or other reasons. In these cases, rather than providing a route out of the protected network, F5 recommends creating another outbound rule for that service device that is configured only to access the specific address with which the service must communicate. To do so, perform the following procedure:

  1. Navigate to SSL Orchestrator > Deployment > Interception Rules.
  2. Click Create Outbound Rule.
  3. Name the rule.

    Note: A recommended name syntax is: <service name>_to_<destination>.

  4. For Protocol, click the appropriate protocol for the service connection.
  5. For Source Address, enter the IP address of the service device.
  6. For Destination Address and Service Port, enter the IP address and port of the expected destination.
  7. For VLAN, in the Available list, click the service the VLAN uses and move it to the Selected list.
  8. Leave the remaining settings at the default None value and leave Explicit Proxy disabled (check box cleared).

proc fc_log {level msg} {
if { ${msg} eq "" } { return }
if { ${level} == 0 } {
ACCESS::log ssl-orchestrator.error "${msg}"
} elseif { ${level} == 1 } {
ACCESS::log ssl-orchestrator.notice "${msg}"
} elseif { ${level} == 2 } {
ACCESS::log ssl-orchestrator.debug "${msg}"
}
}

}

}

call /Common/sslo_extras::fc_log 2 ${msg}
}

proc get_urlcat args {
switch [ACCESS::perflow get perflow.irule_agent_id] {
"sslo_get_category" {
call /Common/sslo_extras::fc_log_debug "FC_get_urlcat: Looking up HTTP category ID"
set urlcat_dg "urlcat"
call /Common/sslo_extras::fc_log_debug "FC_get_urlcat: Setting datagroup to ${urlcat_dg}"
if { [class exists ${urlcat_dg}] } {
if { [ACCESS::perflow get perflow.scratchpad] ne "" } {
set URL "http://[ACCESS::perflow get perflow.scratchpad]"
call /Common/sslo_extras::fc_log_debug "FC_get_urlcat: checking urlcat for url: ${URL}"
set res [CATEGORY::lookup ${URL} request_default_and_custom]
set found 0
set cat_id ""
foreach x ${res} {
set y [string map {"/Common/" ""} ${x}]
set srch [class lookup ${y} urlcat]
if { ${srch} ne "" } {
if { !${found} } {
set cat_id "| ${srch} |"
set found 1
} else {
append cat_id " ${srch} |"
}
}
}
if { ${found} } {
ACCESS::perflow set perflow.scratchpad ${cat_id}
call /Common/sslo_extras::fc_log_debug "FC_get_urlcat: returning cat_id: ${cat_id}"
} else {
call /Common/sslo_extras::fc_log_debug "FC_get_urlcat: no matching cat_id"
}
}
} else {
call /Common/sslo_extras::fc_log_error "FC_get_urlcat: Datagroup ${urlcat} does not exist"
}
}
}
}

proc store_host_header said {
if { [regexp {^([A-Z]+) (?:/|https?://|[A-Za-z\d-]{1,63}[.]|\[[a-fA-F\d:]+\]|(?:[*]\x20))} ${said} junk method] && ([lsearch -exact -sorted {CONNECT DELETE GET HEAD LOCK OPTIONS PATCH POST PROPFIND PUT TRACE UNLOCK} ${method}] >= 0) } {
set host_hdr [findstr ${said} "Host: " 6 "\r\n"]
if { ${host_hdr} ne "" } {
ACCESS::perflow set perflow.scratchpad ${host_hdr}
call /Common/sslo_extras::fc_log_debug "FC_Store_host_header: Setting host header to $host_hdr"
} else {
call /Common/sslo_extras::fc_log_debug "FC_Store_host_header: Empty host header found"
}
} else {
call /Common/sslo_extras::fc_log_debug "FC_Store_host_header: Not HTTP or HTTPS, or unable to parse header"
}
}

proc snat_pool_perc_init {pool_name} {
set static::snatpool_name ${pool_name}
set static::members_cmd "members -list $static::snatpool_name"
unset -nocomplain static::snat_ips
set static::i 0
foreach static::snat_ip [eval $static::members_cmd] {
set static::snat_ips($static::i) [lindex $static::snat_ip 0]
incr static::i
}
set static::array_size [array size static::snat_ips]
call /Common/sslo_extras::fc_log_notice "Loaded $static::array_size SNAT IPs from $static::snatpool_name: [array get static::snat_ips]"
unset static::snatpool_name static::members_cmd static::i static::snat_ip
}

proc snat_perc_client_addr args {
snat $static::snat_ips([expr {[crc32 [IP::client_addr]] % $static::array_size}])
}

proc snat_perc_client_addr_source_port args {
snat $static::snat_ips([expr {[crc32 [IP::client_addr][TCP::remote_port]] % $static::array_size}])
}
