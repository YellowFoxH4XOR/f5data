K000163256: Why a TCP Connection Is Opened from a Nonallowed IP to the Upstream Server

Type
Support Solution
Published
2026-09-08
Updated
2026-09-08
Applies to
  • F5 Distributed Cloud Services
  • F5 Distributed Cloud
Source
https://my.f5.com/manage/s/article/K000163256

Description

A TCP Load Balancer has a Service Policy that allow certean traffic and blocks all other traffic. However, the upstream server may still show TCP connections from nonallowed sources.

This is expected behavior for a raw TCP proxy. The connection can be opened before the Service Policy evaluates application data.

Environment

  • F5 Distributed Cloud TCP Load Balancer
  • Source-IP-based Service Policy
  • TCP client
  • Upstream or origin server

A raw TCP Load Balancer is protocol-agnostic. It does not understand application requests or know which side will send data first.

Cause

The TCP Load Balancer operates as a full proxy with two separate connections:

  1. Client to the TCP Load Balancer
  2. TCP Load Balancer to the upstream server

The Service Policy is applied when the proxy receives data from the client. It is not applied during the initial TCP connection establishment.

The connection sequence can be:

  1. The client opens a TCP connection to the Load Balancer.
  2. The Load Balancer opens or attempts a connection to the upstream server.
  3. The client sends data.
  4. The Service Policy evaluates the data.
  5. Data from an allowed IP is forwarded.
  6. Data from a nonallowed IP is blocked.

Therefore, the upstream server may see a TCP connection from a nonallowed IP even though the Service Policy later blocks the application data. Seeing a TCP connection or handshake does not prove that application data reached the upstream server.

This behavior is native to a raw TCP Load Balancer and is not an indication that the Service Policy failed.

Recommended Actions

  • Use Fast ACLs, where supported, to block traffic at Layer 3 or Layer 4 before the TCP connection is processed by the TCP Load Balancer.
  • Adjust the origin pool circuit breaker settings, where applicable, to help limit the number of upstream connections.
  • Continue using Service Policies when access control based on received application data is sufficient.
  • Use security events to confirm whether the data was allowed or blocked.
  • Correlate Distributed Cloud logs with upstream logs to distinguish a TCP connection from actual application-data delivery.
