Known Issue

This is the result of a known issue. If you assign an SNMP health monitor to a virtual server object on the BIG-IP GTM system, the monitor will incorrectly mark the virtual server down.

The BIG-IP GTM SNMP health monitor was designed to operate at the server object level. When defined for a server object, the monitor uses the server type to determine what SNMP queries to send and how to interpret the results returned from the server.

The following configuration contains an SNMP monitor server object with associated virtual servers. If the user assigns the snmp_test monitor to the server object, the monitor will function as expected. If the user associates the monitor with the virtual server object directly, the virtual server will be marked down even if the object responds properly to the SNMP queries.

monitor "snmp_test" {
defaults from "snmp_gtm"
interval 90
timeout 180
probe_interval 1
probe_timeout 5
probe_num_probes 3
probe_num_successes 1
dest *:*
snmp port "161"
community "public"
snmp version "v1"
partition "Common"
}

server { // datacenter=dc, #VS=4
name "generic_host"
type generic
box {
address 10.10.10.100
unit_id 1
}
prober 10.10.1.251
monitor "gateway_icmp" <------------- if the snmp_test monitor is applied here, it will mark the server green.
vs {
name "vs_10.10.10.100"
address 10.10.10.100:80 // http
}
vs {
name "vs_10.10.10.100_snmp"
address 10.10.10.100:161 // snmp
monitor "snmp_test" <------------- if the snmp_test monitor is applied here, it will mark the VS red.
}
vs {
name "vs_10.10.20.100"
address 10.10.20.100:80 // http

}
vs {
name "vs_10.10.30.100"
address 10.10.30.100:80 // http
}
}

F5 Product Development is tracking this issue as ID 340369.

Workaround

You can work around this issue by removing the SNMP monitor association from the virtual server definition, and associating the monitor with the server object.
