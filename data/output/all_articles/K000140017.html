Description

When a primary nameserver (may also be referred to as a master server) undergoes an update, regardless of the method employed, it becomes imperative to synchronize the altered zone data with other authoritative servers for that zone, commonly referred to as secondary servers (may also be referred to as a slave servers). This synchronization process is commonly known as a 'zone transfer.'

Zone transfers are classified into two categories: full (Authoritative Transfer - AXFR) and incremental (Incremental Zone Transfer - IXFR). A full zone transfer entails transmitting the entire dataset of the zone, while an incremental zone transfer involves solely the transmission of the changes necessary to update the secondary zone. To facilitate incremental zone transfers, both the provider and the recipient are required to maintain individual journal files for each zone. By default, secondary servers will opt for IXFR, resorting to AXFR only in the absence of an IXFR option.

The key determinant of whether the zone requires updating is the serial number housed within the zone's SOA record. Additionally, upon reloading, the primary server verifies the timestamp on the zone data file prior to scrutinizing the SOA. It is a fundamental assumption within BIND that if the serial number remains unaltered, the zone remains unchanged.

Additionally, if the NOTIFY option is configured on the primary server, when the primary server updates the zone file (increments the serial number) the primary server will send a packet to all secondary servers configured under NOTIFY to inform them that the zone may have been modified. This then triggers the AXFR/IXFR zone transfer. If no NOTIFY is configured, then the secondary servers will use the TTL from the SOA records. When the TTL expires, a DNS SOA request is sent to check the serial number of the primary server and, if it is found to be different, the zone transfer is initiated. Please see the BIND Modifications section below for more information on this.

Zone transfers are always initiated by the secondary server, characterized as 'requested' or 'pulled.' Despite the existence of mechanisms to prompt secondaries to verify the necessity for a zone transfer, the transfer process itself is invariably initiated by the secondary server.

Recommended Actions

If it's required to modify the AXFR/IXFR behaviour, then editing the BIND configuration file will be needed.

Note that F5 does not support BIND configuration changes directly. These changes fall outside the scope of F5 Support. More details on this can be found in article K7176: F5 support for ZoneRunner, BIND, and the named process.
This article is here to help you if you're planning to make these modifications on your own providing the necessary information and resources for you to do so.

There are 2 ways to modify a BIND configuration file. More details on this can be found in article K6963: Managing the BIG-IP BIND configuration file.

From the GUI/Configuration utility
    1. Log in to the Configuration utility.
    2. Navigate to DNS > Zones > ZoneRunner > named Configuration.
    3. In the named Options box, make the appropriate changes.
    4. Click Update.

From the CLI
Important: You can manually edit the DNS configuration file on a BIG-IP DNS system; however, F5 recommends that you use the ZoneRunner utility. Incorrectly editing the DNS configuration files on a BIG-IP DNS system can cause issues, such as the ZoneRunner utility or BIND failing to start properly.

  1. Log in to the BIG-IP command line.
  2. To stop the ZoneRunner utility on the BIG-IP system, type the following command:

    # bigstart stop zrd

  3. Use a text editor to edit the /var/named/config/named.conf DNS configuration file.
  4. Save the changes and exit the text editor.
  5. When you have completed the necessary changes to the DNS configuration files, type the following command to verify that the syntax is correct:

    # named-checkconf -t /var/named -z -j /config/named.conf

    If there is a syntax error in the DNS configuration file, the output from the named-checkconf command reports the error.
    For example, the following error was generated by a syntax error in the named.conf file:

    /config/named.conf:33: boolean expected near 'yessd'

  6. If no syntax errors were found, restart the named process by typing the following command:

    # bigstart restart named

  7. To restart the ZoneRunner utility, type the following command:

    # bigstart start zrd

BIND Modifications

From the BIG-IP's perspective, control over AXFR and IXFR is quite limited. Which one is to be chosen at any given time for the zone transfer is dynamically chosen at the discretion of the primary server depending on the circumstances. However, there are a couple of options that would allow us to choose if the servers would always use AXFR or both AXFR/IXFR.

These options can be applied either globally under the 'option' clause or individually on a specific 'server' or 'view' clauses. (In case of DNS Express this option is solely limited on the primary server)

OptionConfigurationDefault ValueApplicable onDescription
provide-ixfrprovide-ixfr yes|no ;yesPrimary serverDefines whether a primary server will respond to an incremental zone transfer request(IXFR) (option = yes) or will only respond with a full zone transfer (AXFR) (option = no)
request-ixfrrequest-ixfr yes|no ;yesSecondary Server

Defines whether a secondary server will request an incremental zone transfer (IXFR) (option = yes) or will only request full zone transfers (AXFR) (option = no)

Other AXFR/IXFR related configuration options:

OptionConfigurationDefault ValueApplicable onDescription
notifynotify yes | no | explicit;yesBoth Primary and Secondary server

When "notify" is set to 'yes' (the default) then, when a zone is loaded or changed, for example, after a zone transfer, NOTIFY messages are sent to the name servers defined in the NS records for the zone (except itself and the 'Primary Master' name server defined in the SOA record) and to any IPs listed in any also-notify statement.

If set to 'no' NOTIFY messages are not sent.

If set to 'explicit' NOTIFY is only sent to those IP(s) listed in an also-notify statement.

If a global notify statement is set to 'no' an also-notify statement may be used to override it for a specific zone, and conversely if the global options contain an also-notify list, setting notify 'no' in the zone will override the global option. This statement may be specified in zone, view clauses or in a global options clause.

Configuration example:

options {
....
    also-notify {10.1.0.15; 172.28.32.7;}; // all zones
....
};
....
zone "example.com in{
....
    // NS RRs and global also-notify
    notify yes;
....
};
zone "example.net in{
....
    // no NOTIFY to NS RRs
    // NOTIFY to also-notify IPs above
    notify explicit;
....
};

 

allow-notifyallow-notify { address_match_list };N/ASecondary Server

Defines a match list, for example, IP address(es) that are allowed to NOTIFY this server and implicitly update the zone in addition to those hosts defined in the masters option for the zone. The default behaviour is to allow zone updates only from the masters IP(s). This statement may be used in a zone, view or global options clause.

Configuration example:

// allows notify from the defined IPs 
allow-notify {192.168.0.15; 192.168.0.16; 10.0.0.1;};
// allows no notifies 
allow-notify {none;};
