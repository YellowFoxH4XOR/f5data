Topic

The BIG-IP system uses SSL certificates and keys for administrative tasks, inter-device communication, and offloading SSL traffic. This article provides information about SSL certificates and keys used for administrative tasks and inter-device communication. For information about SSL certificates used to offload SSL traffic, refer to K14783: Overview of the Client SSL profile (11.x - 21.x).

Description

The BIG-IP system uses SSL certificates to secure connections when using the Configuration utility to perform administrative tasks and to secure inter-device communication between BIG-IP systems such as BIG-IP LTM device groups and BIG-IP DNS synchronization groups. For successful authentication and secure communication, you should be aware of the following factors:

  • Device certificate Common Name (CN) should reflect the hostname of the BIG-IP.
  • Device certificates must be valid and must not be expired.
  • Device certificates must be maintained and renewed on each BIG-IP system.
  • Redundant BIG-IP systems must exchange renewed certificates.
  • SSL certificates signed by a third-party CA must include both the client authentication (clientAuth) and server authentication (serverAuth) extended key usage (EKU) extensions to allow use by both server and client applications. For more information, refer to K7717: BIG-IP DNS and Link Controller support for third-party SSL certificates.

BIG-IP systems use device certificates for a variety of tasks. The following sections list F5 device certificate types and their locations.

  • Device Service Clustering (DSC): Device trust certificates
  • Configuration utility: Device certificates
  • Trusted device certificates
  • Trusted server certificates

Device Service Clustering (DSC): Device trust certificates

The BIG-IP system uses SSL certificates to establish a trust relationship between devices. In a device trust, a BIG-IP device can act as a certificate signing authority or a subordinate non-authority. Each device also has peer authorities. When acting as a certificate signing authority, the BIG-IP device signs x.509 certificates for another BIG-IP device that is in the local trust domain. The BIG-IP device for which a certificate signing authority device signs its certificate is known as a subordinate non-authority device.

BIG-IP systems use the trust architecture to provide a secure framework for configuration synchronization (ConfigSync) and other high availability (HA) features, such as failover for BIG-IP device groups. When the device group components are properly defined, the device group members establish a secure communication channel using SSL certificates to accommodate device group communication and synchronization. For more information about ConfigSync and device cluster issues, refer to K13946: Troubleshooting ConfigSync and device service clustering issues.

You can view the DSC device trust certificates in the location shown in the following table.

File nameConfiguration utility locationDescription
dtdi.crtDevice Management > Device Trust > IdentityThe dtdi.crt is the identity certificate that is used by a device to validate its identity with another device.
dtdi.keyN/AThe dtdi.key is the corresponding key file used by a device to validate its identity with another device.
dtca.crtDevice Management > Device Trust > Local DomainThe dtca.crt is the CA root certificate for the trust network.

Trusted device certificates

The local BIG-IP device uses trusted device certificates to authenticate certain connections from a remote BIG-IP device. For example, the big3d agent of the local BIG-IP DNS or BIG-IP LTM system uses the trusted device certificate obtained from a remote F5 device to authenticate the remote device's gtmd or iqdump requests. For more information, refer to K13312: Overview of the BIG-IP DNS big3d_install, bigip_add, and gtm_add utilities (11.x - 17.x).

If a deployment includes many BIG-IP devices, all of which authenticate to one another, the list of trusted device certificates for a given device should include the signed certificates of each authenticating F5 device. In addition, the list of trusted device certificates must include the device's own certificate.

The trusted device certificate must be an RSA certificate and can be signed by a third-party CA. If using third-party certificates, the trusted device certificate file only needs to contain the certificates of the certificate authorities that signed the device certificates. If a certificate chain is used, the trusted device certificate file must contain all of the certificates in the chain. In addition, F5 recommends that the file includes the local device's certificates.

Trusted server certificates

The BIG-IP DNS system uses trusted server certificates when the local BIG-IP DNS system authenticates itself to a remote F5 device. For example, the local BIG-IP DNS system uses the trusted server certificate when the BIG-IP DNS system's gtmd process or iqdump program attempts to connect to the big3d process on a remote F5 device.

The list of trusted server certificates must include the BIG-IP DNS system's own certificate, as well as the self-signed certificates of any remote F5 device to which it will connect. The trusted server certificates list is synchronized to BIG-IP DNS devices in a synchronization group.

The trusted server certificate must be an RSA certificate and can be signed by a third-party CA. If using third-party certificates, the trusted server certificate file needs to contain only the certificates of the certificate authorities that signed the device certificates. If a certificate chain is used, all of the certificates in the chain must be contained in the trusted server certificate file. In addition, F5 recommends that the file includes the local device's certificates.

Global Traffic > Servers		The trusted server certificates are used when the local DNS system authenticates itself to a remote F5 device.
