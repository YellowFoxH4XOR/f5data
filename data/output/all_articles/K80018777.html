Description

Istio and the istio-proxy components have exposed a variety of metrics that the user can take advantage of. In this article, we will explore how to scrape this metrics and what are the most useful.
 

Environment

  • Kubernetes: 1.17x,1.18.x,1.19.x,1.20.x

  • Aspen Mesh:  1.6.x, 1.9.x, 1.11.x, Metrics Collector deprecated in 1.14.x
     

Cause

Metrics provide a way of monitoring and understanding behavior in aggregate. These metrics provide information on behaviors such as the overall volume of traffic, the error rates within the traffic, and the response times for requests.
 

Recommended Actions

Below you can find different ways to scrape the metrics and what are the recommended ways to do it:

  • Use federation for Prometheus (recommended)

  • Consume metrics over Grafana dashboards

  • Bring your own metrics (BYOM) (less preferred)

Use federation for Prometheus

Prometheus can be configured to achieve a Prometheus instance to consume scraped metrics selected from another Prometheus instance.

This can have better benefits than consuming metrics directly from sidecars:

Pros:

  • Simple configuration with a scraping job.

  • Avoid managing complex job configurations.

  • Avoid missing time-series labels changes, automatically Aspen Mesh will update label metrics if they change over time, you don't need to perform any changes in your configuration.

  • Good choice if you consume metrics via Prometheus API.

Cons:

  • If the Prometheus (aspen-mesh-metrics-collector) instance is not available, metrics would not be available also.

How to configure the federation

Using the simple job, you could consume metrics for specific job labels:

- job_name: federate
  honor_labels: true
  honor_timestamps: true
  params:
    match[]:
    - '{job="prometheus"}'
    - '{job="envoy-stats", namespace=~"testing"}' #You can delete namespace to scrape all the metrics over your cluster
  scrape_interval: 15s
  scrape_timeout: 10s
  metrics_path: /federate
  scheme: http
  basic_auth:
    username: aspenmesh
    password: <secret>
  static_configs:
  - targets:
    - aspen-mesh-metrics-collector.istio-system.svc.cluster.local:19090

You can still configure alerts based on Istio metrics with the federate job.

Consume metrics over Grafana Dashboard

You can integrate Grafana with our metrics-collector we have an insightful guide here: K11884926: Integrating Grafana with Aspen Mesh Metrics Collector for monitoring mesh metrics.

Pros:

  • You don't have to maintain any configuration over another Prometheus instance.

  • Easy integration.

  • Good choice if you don't need to consume metrics over API but over digested and great visualization graphs.

BYOM

You can continue scraping metrics from the sidecar directly. You will need to develop your own job configuration to retrieve those metrics.

We cannot ensure that future metrics labels will not change in Istio and Prometheus projects; they are constantly changing with new releases.

Pros:

  • You have control of what metrics you want to see.

Cons:

  • This method is not supported as we don't guarantee stability or changes over time in metrics labels.

  • You will need to accommodate and maintain scraping jobs.

 


Additional Questions
Which metrics should we monitor?

The default metrics exposed by every istio-proxy sidecar should be used to monitor every POD.

Default metrics allow monitoring:

  • Total connections handled by the POD

  • Response times for HTTP requests

  • Response/request sizes for HTTP requests

  • Number of TCP connections handled by the proxy

  • Istio-proxy sidecar status like memory, healthy, xDS requests

General information with examples

Default useful metrics to monitor HTTP services:

Name

Description

istio_requests_total

Number of HTTP requests received by an Envoy proxy.

istio_request_duration_milliseconds_bucket

How long it takes an Envoy proxy to process an HTTP request.

istio_request_bytes_bucket

The size of the HTTP response bodies that an Envoy proxy has processed.

istio_response_bytes_bucket

The size of the HTTP request bodies that an Envoy proxy has processed.

Default useful metrics to monitor TCP services:

Name

Description

istio_tcp_sent_bytes_total

This is a COUNTER which measures the size of total bytes sent during response in case of a TCP connection.

istio_tcp_received_bytes_total

This is a COUNTER which measures the size of total bytes received during request in case of a TCP connection.

istio_tcp_connections_opened_total

This is a COUNTER incremented for every opened connection.

istio_tcp_connections_closed_total

This is a COUNTER incremented for every closed connection.

Examples of metrics to monitor istio-proxy sidecar status:

  • envoy_server_memory_allocated

  • envoy_server_memory_physical_size

  • envoy_server_state

  • envoy_cluster_manager_active_clusters

  • envoy_cluster_upstream_rq* - this include all pending, active, cancel, completed, reset and retry

More information about querying metrics can be found on official Prometheus documentation.
