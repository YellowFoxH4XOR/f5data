Topic

You should consider using this procedure under the following condition:

  • You want to use F5 Modules for Ansible to force a node offline, but only if it does not take a pool offline.

Description

Before forcing a node offline for maintenance, you often need to determine to which pools it is a member of and the active member count in each so that you aren't taking out the only active pool member. You can automate the steps to complete this on a single BIG-IP system or numerous BIG-IP systems using Ansible, which is a tool that automates and manages multi-machine configuration and deployment.

Example playbook

The following is an example of a playbook that gathers the ltm-pools fact subset from bigip_device_facts, finds all the pools that a given node belongs to, collects all the active member counts of those pools and finds the smallest one, and, if the smallest number is greater than 1, offlines the node. Use the procedures in this article to create a similar playbook:

---
- name: Conditionally force a node offline
  hosts: bigip15-0.askf5team.local:bigip14-1.askf5team.local
  gather_facts: False
  vars:
    provider:
      password: "{{ bigip_password }}"
      server: "{{ ansible_host }}"
      user: "{{ bigip_username }}"
      validate_certs: False
    active_list: []

  vars_prompt:
    - name: node
      prompt: "What is the node address? "
      private: no

  tasks:
    - name: Collect bigip facts
      bigip_device_facts:
        gather_subset:
          - ltm-pools
        provider: "{{ provider }}"
      register: pools

    - name: Determine pools the node is in and record their active member counts
      set_fact:
        active_list: "{{ active_list + [ item[1] ] }}"
      when: node in item[2]
      loop: "{{ pools | json_query('ltm_pools[].[name, active_member_count, members[*].address]') }}"

    - name: Display active member count list
      debug: var=active_list

    - name: Display count with the least amount of active members
      debug: msg="Minimum active member count from all pools {{ active_list | min }}"

    - name: Force node offline
      bigip_node:
        state: offline
        name: "{{ node }}"
        provider: "{{ provider }}"
      delegate_to: localhost
      when:  active_list | min | int > 1

Prerequisites

You must meet the following prerequisites to use these procedures:

  • You are familiar with using Ansible.
  • You read the User's Guide section of F5 Modules for Ansible Documentation.
  • You have Ansible 2.8 or later installed on the control machine.
  • You have BIG-IP 12.x or later installed on the devices in the environment.
  • The Python packages required for each module or filter you want to use on the control machine are installed. For example, the F5 Modules require the f5-sdk package and the JSON Query filter requires the jmespath package. For more information, refer to Module Index in the Ansible User Guide.

Defining initial play settings

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to your control machine.
  2. Create a playbook file called conditional_node_offline.yml.
  3. Start composing your playbook YML file and set the hosts to the BIG-IP or group of BIG-IP devices you want to force a node offline on. Gathering system facts is not necessary for this playbook.
  4. In the vars parameter, create a playbook variable called provider. Add the BIG-IP connection details as the values to the provider variable. In the example, group variables from the group the hosts belong to are used. You can reference the provider variable in the provider parameter of the F5 Module for Ansible. You can encrypt BIG-IP passwords for the playbook by placing them in the vault. For more information, refer to K64450989: Using the 'ansible-vault' command to encrypt BIG-IP passwords used in a playbook.
  5. Also in vars, create an empty list called active_list.

The following is the initial play settings section from the example playbook showing all the elements described in this procedure:
---
- name: Conditionally force a node offline
  hosts: bigip15-0.askf5team.local:bigip14-1.askf5team.local
  gather_facts: False
  vars:
    provider:
      password: "{{ bigip_password }}"
      server: "{{ ansible_host }}"
      user: "{{ bigip_username }}"
      validate_certs: False
    active_list: []


Including variables in the playbook

There are a variety of methods for including a variable in the playbook for the node you want. The following procedure describes how to use a prompt to define the variable. When the playbook is executed, it prompts the user for input on the command line.
You can follow the procedure to use prompts or you can use another method to include variables. For more information, refer to the Using Variables page of the Ansible User Guide.

Important: The playbook gathers the node address from the user and uses it to find pool membership in the ltm_pools fact subset and uses it in the bigip_node module which requires the node name. The playbook assumes that you use the common practice of using the node IP address as the node name.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Create a vars_prompt section.
  2. Create a variable for the node IP address and the prompt that appears to the user. Include private: no so that the input is echoed to the screen. 

The following var_prompts section from the example playbook shows the elements described in this procedure:

  vars_prompt:

    - name: node
      prompt: "What is the node address? "
      private: no

Creating a task that collects the pool facts

An Ansible fact is a characteristic about a remote machine, such as its IP address or operating system. The bigip_device_facts module collects facts about your BIG-IP devices. The ltm_pools subset facts of the bigip_device_facts module collects the pool configuration on the BIG-IP. This includes, among other properties, the name, the members, and how many members are active, the active_member_count.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Start your list of tasks with the tasks statement.
  2. Create a task that uses the bigip_device_facts module to gather the ltm_pools subset from the hosts defined in the playbook. Register the gathered facts in a variable called pools.
  3. Configure the provider parameter.

The following task from the example playbook shows the elements described in this procedure:

  tasks:
    - name: Collect bigip facts
      bigip_device_facts:
        gather_subset:
          - ltm-pools
        provider: "{{ provider }}"
      register: pools

Creating a task that determines the pools the node belongs to and records the active member count of each pool

The set_fact module allows you to set a variable for a host in a task. In this procedure you collect the active_member_count data using the json_query filter and place it in a list variable. The task appends contents to the list only when the node variable matches an address in the list of pool members for each pool so you're only getting active_member_count data from the pools the node belongs to.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Create a task that uses the set_fact module. You'll use the json_query filter to gather specific data about the pool configuration.
  2. Create a fact called active_list that appends the active_member_count which you reference as item[1] to the empty list you created previously.
  3. Add a when statement that appends contents to the list only when the node variable matches an address in the list of pool members, item[2].
  4. Add a loop statement where the value is a list created with the json_query filter. Search in the ltm_pools fact subset for the pool name, active_member_count, and the member addresses.

The following task from the example playbook shows the elements described in this procedure:

    - name: Determine pools the node is in and record their active member counts
      set_fact:
        active_list: "{{ active_list + [ item[1] ] }}"
      when: node in item[2]
      loop: "{{ pools | json_query('ltm_pools[].[name, active_member_count, members[*].address]') }}"
 

(Optional) Creating debug tasks that display variable values

Using the debug module, you can display the contents of the active_list and the ltm_pools fact subset data that is collected by the json_query filter.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Create a task that uses the debug module.
  2. Display the contents of active_list with the var parameter.
  3. Create a second task that uses the debug module
  4. Display the minimum active member count with the min filter in the msg parameter. This number uses the when statement for the bigip_node task.

The following tasks from the example playbook show the elements described in this procedure:

    - name: Display active member count list
      debug: var=active_list

    - name: Display count with the least amount of active members
      debug: msg="Minimum active member count from all pools {{ active_list | min }}"
 

Creating a task that conditionally forces a given node offline

After you have obtained the list of active members from each pool the node is a member of you can then combine the bigip_node module with the when statement to conditionally force the node offline.
Important: The playbook gathers the node address from the user and uses it to find pool membership in the ltm_pools fact subset and uses it in the bigip_node module which requires the node name. The playbook assumes that you use the common practice of using the node IP address as the node name.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Create a task with the bigip_node module.
  2. Configure the task to update the node status by including state: offline.
  3. Include the node variable as the value for the name parameter.
  4. Configure the provider parameter.
  5. Add delegate_to: localhost so the task is performed on the control machine itself which is required for all F5 Modules for Ansible.
  6. Add a when statement so that the task is performed when the lowest number in the active list obtained with the min filter (the number that represents the pool with the least amount of active members) is greater than 1. This ensures you force the node offline only if it is not taking a pool offline.

The following tasks from the example playbook show the elements described in this procedure:

    - name: Force node offline
      bigip_node:
        state: offline
        name: "{{ node }}"
        provider: "{{ provider }}"
      delegate_to: localhost
      when:  active_list | min | int > 1


Running the playbook

You can now run the playbook from your control machine to make configuration changes to the BIG-IP devices in the play.

Impact of procedure: Performing the following procedure forces a node offline on the BIG-IP system; therefore, only active connections are allowed.

  1. Log in to your control machine.
  2. Change the working directory to the one with your playbooks.
  3. To run the playbook from the command line of your control machine, type the following command:

    ansible-playbook conditional_node_offline.yml

    The output from the command appears similar to the Example playbook output section of this article.
