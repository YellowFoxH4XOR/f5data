K000158099: CDN returns WAF Support ID instead of proper page

Type
Support Solution
Published
2025-12-07
Updated
2026-07-12
Applies to
  • F5 Distributed Cloud Services
  • F5 Distributed Cloud WAF
Source
https://my.f5.com/manage/s/article/K000158099

Description

Sometimes our CDN intermittently serves cached WAF support ID block messages to users instead of the expected website content. 

Environment

  • CDN
  • CDN Origin pool has WAF
  • Cached Support IDs

Cause

Often CDN acts as front-end and it's origin pool points to Load balancer (LB) with WAF policy applied. Traffic flow looks similar to presented flow: 

User → CDN (on cache miss) → LB (WAF) → Origin Pool

By default, CDN doesn't have WAF policy and if response for current customer requests will not be in cache, CDN forwards request to CDN origin pool (LB with WAF) with unchanged content.

When request with malicious content will be forwarded from CDN to LB with WAF, request will be blocked and LB will return WAF Support ID which is 200 HTTP response by default. CDN treats threat that as successful response from server and will cache it. Subsequent users for the same path will receive the same support ID from cache, even if their request is not malicious.   

Summary of events: 

  • Malicious requests are forwarded from CDN to LB and blocked by WAF, which responds with HTTP 200 and a support ID.
  • CDN caches this HTTP 200 response containing the support ID.
  • Subsequent users may receive cached support IDs instead of correct website content.

Recommended Actions

  1. Switch to CDN integrated with Load Balancer
    One click CDN is now available. You can configure CDN on HTTP LB directly in settings. 
  2. Change Response Code for Blocked Requests (Support IDs):
    Configure your WAF policy to return support ID with HTTP status code of 4xx or 5xx.
    The CDN will not cache responses with these status codes.

  3. Apply Same WAF Policy on Both Layers - early access:
    Currently, this option is Early Access. 
    You can add your existing WAF policy to both the CDN and LB.
    Malicious traffic will be blocked at the edge (CDN), preventing it from reaching LB and avoiding caching of block messages.

Note: Once you change configuration, CDN hard purge is required to remove all currently cached support IDs.
