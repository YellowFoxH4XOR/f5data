Environment

Aspen Mesh 1.14.x, 1.11.x

Cause

MTLS conflicting configuration.
By default, mTLS is enabled when Aspen Mesh is installed, this behavior is enforced with the following objects: 
➜  aspenmesh-carrier-grade kubectl get pa default -n istio-system -o yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT
➜  aspenmesh-carrier-grade kubectl get dr default  -n istio-system -o yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
  name: default
  namespace: istio-system
spec:
  host: '*.local'
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL
Looking at the envoy listeners of any pod on port 15006 (the port used by envoy for inbound connections), there are no non-tls listeners:

Adding the following object will cause a mtls conflict since we are disabling it but there are no non-tls listeners present in the destination pod(no filter chain that matches). 
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: httpbin-istio-mtls-disable
spec:
  host: httpbin.default.svc.cluster.local
  trafficPolicy:
    tls:
      mode: DISABLE

Recommended Actions

Make sure proper peerauthentication and/or destination rule objects are in place.
We can use the following object to enable permissive mode (mtls/non-mtls communication) within a particular namespace

apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default-ns-permissive
  namespace: default
spec:
  mtls:
    mode: PERMISSIVE
