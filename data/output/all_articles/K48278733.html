Description

Before v13 F5 tried to calculate a good default threshold that could fit most users. To do this we made use of the db variable pvasyncookies.virtual.maxsyncache with a setting of 2999. With version v13 F5 decided that with your knowledge of your network and its applications you are better qualified to determine the proper threshold for the per Virtual Server setting. This is because so much depends on several factors that we cannot control. For instance the platform itself, the type of application, and/or the expected traffic for your application(s). Since the inception of V13 we instituted the configuration object "Default Per Virtual Server SYN Check™ Threshold" with a default setting of zero for per virtual protection. This is usually found at System  ››  Configuration : Local Traffic : General. Taking that all into account F5 enabled SYNCookie on the global level, with a default setting of 64000, to protect the BIG-IP. The per virtual setting for SYNCookie Protection, using "Default Per Virtual Server SYN Check™ Threshold", is configured by you to protect your applications using that knowledge you have.

Environment

Relevant environmental factors specific to the topic

  • SynCookie is seen activating at the virtual server level.
  • Default Per Virtual Server SYN Check™ Threshold, Virtual Servers
  • AFM, APM, ASM, DNS/GTM, FPS, LTM, SSLO, DDoS Defender

Cause

There is an issue that has been identified as ID1015453 that under certain circumstances may come into play. In order for the config object Default Per Virtual Server SYN Check™ Threshold to be available in the GUI LTM must be provisioned. Under certain circumstances LTM may not be provisioned or it may be suggested that it be deprovisioned.

  • In some cases you may have a memory condition on your BIG-IP. In order to relieve the memory pressure it may be recommended you deprovision LTM, if there are other modules provisioned. As long as LTM is licensed you will still have full LTM functionality. The only caveat to that is if you have an iApp that is LTM dependent. In that case you cannot deprovision LTM.
  • In many cases a BIG-IP is not built to even use LTM. For example it may only be licensed for ASM and AVR and both are provisioned.

Recommended Actions

  1. In cases where LTM is not provisioned/deprovisioned you can still make use of the Default Per Virtual Server SYN Check™ Threshold via the CLI.
  2. To check the current setting you would run this command... 
    tmsh list ltm global-settings connection
    1. The output will resemble... 
      ltm global-settings connection {
default-vs-syn-challenge-threshold 0
}
Note: '0' is the default setting.
  3. To modify the setting run this command... tmsh modify ltm global-setting connection value <value>
    1. Example: 
      tmsh modify ltm global-setting connection value 2999  

Additional Information

There are other effects also due to this bug. When LTM is not provisioned it removes all System  >> Configuration : Local Traffic access from the GUI. This would entail...

  • System  >> Configuration : Local Traffic : General
  • System  >> Configuration : Local Traffic : Persistence
  • System  >> Configuration : Local Traffic : Eviction Policy
Also, when LTM is not provisioned when you open the "Shared Objects" section  of the GUI there will not be a section there for Port Lists.

Because of this there are may other configuration objects that will no longer be accessible from the GUI, but only via the CLI. These would include...
  • Auto Last Hop
  • VLAN-Keyed Connections
  • Hardware VLAN SYN Cookie Protection
  • SNAT Packet Forwarding
  • Management of Destination Address Entries
  • Eviction Policy List
  • and many others.
If you run into any issues with this please contact F5 Support and open a case. When doing so please reference this article and the bug ID.
