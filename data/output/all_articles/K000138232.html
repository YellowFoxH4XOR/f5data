K000138232: Replaced VELOS System Controller does not join cluster when Internal Chassis Networking configured to RFC1918

Type
Support Solution
Published
2024-01-15
Updated
2026-02-12
Applies to
  • F5OS
  • VELOS Platforms
  • F5OS-C
Source
https://my.f5.com/manage/s/article/K000138232

Description

If a VELOS system is configured to use RFC1918 address space for the Internal Chassis Networking, a new system controller will fail to automatically join the cluster.  This can occur if a clean install is performed on a VELOS system controller, or if the controller is replaced via a Return Materials Authorization (RMA).

Note: For information on replacing a system controller in a VELOS chassis, refer to K000133249: Replacing VELOS system controller after a Return Materials Authorization.

The active system controller will report in the "show cluster" output that a controller is present in the cluster, but it is not able to ping it:

syscon-1-active# show cluster
                                                               ABLE   ABLE
                                             IN       READY    TO     TO
INDEX  NAME                        INSERTED  CLUSTER  CLUSTER  PING   SSH    STATE
-----------------------------------------------------------------------------------------
1      controller-1.chassis.local  true      true     false    false  false  In Cluster
2      controller-2.chassis.local  true      true     true     true   true   In Cluster

The two system controllers will have IP addresses in different subnets assigned on the "ccpeer" network interface, which can be examined by logging into each system controller as root and running "ip -4 addr show dev ccpeer":

[root@controller-1(VELOS):Active ~]# ip -4 addr show dev ccpeer
3: ccpeer: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc mq state UP group default qlen 1000
    inet 10.225.7.51/24 brd 10.225.7.255 scope global noprefixroute ccpeer
       valid_lft forever preferred_lft forever
    inet 10.225.7.50/24 brd 10.225.7.255 scope global secondary noprefixroute ccpeer
       valid_lft forever preferred_lft forever

[root@controller-2 ~]# ip -4 addr show dev ccpeer
3: ccpeer: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc mq state UP group default qlen 1000
    inet 100.65.7.52/24 brd 100.65.7.255 scope global noprefixroute ccpeer
       valid_lft forever preferred_lft forever

On the replaced system controller, there will be logs similar to the following repeating:

/var/log/messages
journal: DEBUG Failed to connect to ConfD: No route to host

/var/log_controller/cc-confd
<err> Mmm DD HH:MM:SS maintain_confd: confd --start-phase1: failed (exited code 1)
<emerg> Mmm DD HH:MM:SS clear_config: failed to upgrade, will try restore last version

 

Environment

  • Velos
  • F5OS-C
  • System Controller
  • Configured with RFC1918 Internal IP range
  • RMA or clean install

 

Cause

  • Bug ID 1067757

 

Recommended Actions


To fix this issue, perform the following steps:

  1. Log into the active (healthy) system controller as root, and run the following command:
    grep -vE '^(#|$)' /etc/sysconfig/chassis_network_config.txt

    The output should look similar to this:

    [root@controller-1(VEL410) ~]# grep -vE '^(#|$)' /etc/sysconfig/chassis_network_config.txt
    network_range_type=RFC1918
    chassis_network_selection=14
    chassis_id=4
    network_prefix=10.228
    [root@controller-1(VEL410) ~]#
  2. Log into the newly-installed (unhealthy) system controller as root, and run the following command:
    grep -vE '^(#|$)' /etc/sysconfig/chassis_network_active.txt

    On a functioning system, the output should match the output from the active system controller, but it is likely it will be different, e.g.:
    [root@controller-2(VEL410) ~]# grep -vE '^(#|$)' /etc/sysconfig/chassis_network_config.txt
    network_range_type=RFC6598
    chassis_network_selection=0
    chassis_id=1
    network_prefix=100.65
    [root@controller-2(VEL410) ~]#
  3. If the output from the two commands do not match, edit the command does not match the healthy system controller, then on the unhealthy system controller, create the file /etc/sysconfig/chassis_network_override.txt and copy the contents from the healthy system controller.
  4. On the unhealthy system controller, wait for platform-services-deployment to finish starting up before proceeding by monitoring one of the following commands:
    systemctl status -l platform-services-deployment
    journalctl -f -u platform-services-deployment
    When it's finished (which should take about 15 minutes), the output should look similar to this:
    [root@controller-2 ~]# systemctl status -l platform-services-deployment
    ● platform-services-deployment.service - Launch platform service containers through Docker Compose Loaded: loaded (/usr/lib/systemd/system/platform-services-deployment.service; static; vendor preset: disabled) Active: active (exited) since Thu 2025-11-13 15:27:37 PST; 1min 30s ago <----- Main PID: 21758 (code=exited, status=0/SUCCESS) Tasks: 0 Memory: 0B CGroup: /system.slice/platform-services-deployment.service [...] Nov 13 15:27:37 controller-2.chassis.local platform-deployment[21758]: Platform services done Nov 13 15:27:37 controller-2.chassis.local systemd[1]: Started Launch platform service containers through Docker Compose. [root@controller-2 ~]#
  5. After the file has been created and platform-services-deployment has started, reboot the unhealthy system controller:
    reboot

Note: Once this workaround has been applied, it may take up to 1.5 hours for the system controllers to cluster.  Monitor /var/log/openshift.log on the active system controller to see the progress.
