Understanding a Slowloris attack

The Slowloris attack is a type of denial-of-service (DoS) attack which targets threaded web servers. It attempts to monopolize all of the available request handling threads on the web server by sending HTTP requests which never complete. Since each request consumes a thread, the Slowloris attack eventually consumes all of the web server's connection capacity, effectively denying access to legitimate users.

The HTTP protocol specification (RFC 2616) states that a blank line must be used to indicate the end of the request headers and the beginning of the payload, if any. Once the entire request is received, the web server may then respond.

Note: A blank line is created by sending two consecutive newlines:

<CR><LF><CR><LF>

The Slowloris attack operates by establishing multiple connections to the webserver. On each connection, the attack sends an incomplete request which does not include the terminating newline sequence. The attacker sends additional header lines periodically to keep the connection alive, but never sends the terminating newline sequence. The webserver keeps the connection open, expecting more information to complete the request. As the attack continues, the volume of long-standing Slowloris connections increases, eventually consuming all available webserver connections, thus rendering the webserver unavailable to respond to legitimate requests.

Effects of a Slowloris attack on a BIG-IP virtual server configured with an HTTP profile

A virtual server which uses an HTTP profile will only open connections and proxy requests to pool members once a complete and valid HTTP request has been received. Since the principle of the Slowloris attack is to never complete any request, no connections are ever opened nor any data sent to the pool members.

The attack consumes connections on the BIG-IP system, rather than the web servers in the pool. When the total size of the headers sent by the Slowloris attack exceeds the maximum header size configured in the HTTP profile, the BIG-IP system resets the connection, recovering the TCP socket and removing the connection from the connection table. As the Slowloris attack continues to open new connections, the BIG-IP virtual server continues to reap them in this manner. This renders the Slowloris attack ineffective against web servers which are load balanced by a BIG-IP virtual server configured with an HTTP profile.

Effects of a Slowloris attack on a BIG-IP virtual server configured without an HTTP profile

Since the Slowloris attack exploits behavior in the HTTP protocol to deny access to a web server, if the BIG-IP system does not parse the traffic as HTTP (that is, has no HTTP profile configured), it will process the traffic as regular L4 traffic and pass the requests unchanged to the web servers.

Identifying a Slowloris attack on the BIG-IP system

Slowloris attacks can be identified on the BIG-IP system by the following characteristics:

  • Long-standing active connections to the client side of the HTTP virtual server
  • Incomplete HTTP requests on the client side (missing terminating CR-LF CR-LF sequence)
  • No corresponding HTTP traffic on the server side

Further mitigation using iRules (version 10.x and later)

In BIG-IP 10.0.0 and later, it is possible to use an iRule to further mitigate the effects of a Slowloris attack on BIG-IP virtual servers. The following iRule will silently discard the connection if the complete HTTP request has not been received one second after the connection was established:

when CLIENT_ACCEPTED {
set rtimer 0
after 1000 {
if { not $rtimer} {
drop
}
}
}

when HTTP_REQUEST {
set rtimer 1
}

Note: This iRule may cause issues for legitimate users connecting over very slow links.
