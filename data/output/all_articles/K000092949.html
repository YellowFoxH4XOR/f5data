Description

503 errors are one of the most common errors seen in the Aspen Mesh logs.  Typically, this error is a result of service connectivity issues.   Here are some common reasons for istio-proxy logs to report 503 errors.  

Environment

  • Redhat Openshift: 4.6x, 4.7.x, 4.8.x, 4.9.x and 4.10.x 
  • Kubernetes: 1.17x,1.18.x,1.19.x,1.20.x, 1.21.x, 1.22.x, 1.23.x 
  • Aspen Mesh: 1.6.x,1.9.x,1.11.x,1.14.x 

Cause

In this example we receive a 503 error code when trying to connect to a service that is in a namespace external to the cluster:  

kubectl exec -it clientpod -- curl -Is nginx-svc.external.svc.cluster.local:8080 
HTTP/1.1 503 Service Unavailable 
content-length: 190 
content-type: text/plain 
date: Wed, 19 Oct 2022 18:02:48 GMT 
server: envoy


The log message received in the client’s istio-proxy log shows that 503 was a result of the wrong version number.  

[2022-10-19T18:02:48.496Z] "HEAD / HTTP/1.1" 503 UF,URX upstream_reset_before_response_started{connection_failure,TLS_error:_268435703:SSL_routines:OPENSSL_internal:WRONG_VERSION_NUMBER} - "TLS error: 268435703:SSL routines:OPENSSL_internal:WRONG_VERSION_NUMBER" 0 0 41 - "-" "curl/7.83.1" "de424048-5020-4182-86a0-a01f6e28cace" "nginx-svc.external.svc.cluster.local:8080" "10.244.1.218:80" outbound|8080||nginx-svc.external.svc.cluster.local - 10.107.255.32:8080 10.244.1.212:40982 - default


By default, the workloads that exist within Aspen Mesh use mTLS. Because the nginx service is not using TLS, we need to create a destination rule to disable the TLS for traffic destined to that service.

apiVersion: networking.istio.io/v1beta1 
kind: DestinationRule 
metadata: 
     name: disable-mtls 
     namespace: default 
spec: 
     host: nginx-svc.external.svc.cluster.local
     trafficPolicy:
       tls:
          mode: DISABLE


After applying the destination rule the istio-proxy logs now report a 200 HTTP Response code:

[2022-10-19T18:38:23.787Z] "HEAD /index.html HTTP/1.1" 200 - via_upstream - "-" 0 0 12 12 "-" "curl/7.83.1" "9b6c57a7-1fc7-455f-893f-48840a561ee2" "nginx-svc.external.svc.cluster.local:8080" "10.244.1.218:80" outbound|8080||nginx-svc.external.svc.cluster.local 10.244.1.212:49764 10.107.255.32:8080 10.244.1.212:47606 - default


TCP and HTTP Codes related to 503 errors produced by the istio-proxy (Envoy):

UH: No healthy upstream hosts in upstream cluster in addition to 503 response code. 
UF: Upstream connection failure in addition to 503 response code. 
UO: Upstream overflow (circuit breaking) in addition to 503 response code. 
NR: No route configured for a given request in addition to 404 response code, or no matching filter chain for a downstream connection. 
URX: The request was rejected because the upstream retry limit (HTTP) or maximum connect attempts (TCP) was reached. 
NC: Upstream cluster not found. 
DT: When a request or connection exceeded max_connection_duration or max_downstream_connection_duration.


Recommended Actions

Here are a couple of actions on how to resolve the 503 codes:

  • NR: No route configured, check your DestinationRule or VirtualService.
  • UO: Upstream overflow with circuit breaking, check your circuit breaker configuration in DestinationRule.
  • UF: Failed to connect to upstream, if you are using Istio authentication, check for a mutual TLS configuration conflict.
  • UH: No healthy upstream hosts in upstream cluster in addition to 503 response code, check if the application or sidecar is responding; review the Service Entries and make sure they are created correctly; check for network latency.
  • via_upstream: Check the application.
