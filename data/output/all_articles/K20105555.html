K20105555: F5 SSL Orchestrator may fail to stop an attacker from exfiltrating data on a compromised client system (SNIcat)

Type
Security Advisory
Published

Updated

Applies to

Security Advisory Description

An attacker may be able to exfiltrate data from a target system sitting behind F5 SSL Orchestrator by inserting data into the TLS SNI field. This approach assumes that the attacker has already compromised, and is in full control of, the target system to be able to create outbound connections to arbitrary destinations with specifically crafted TLS handshake details. Note that the data insertion into the TLS SNI field is performed on the compromised system itself and is done outside of the F5 SSL Orchestrator's traffic management.

This issue occurs when all of the following conditions are met:

  • You deployed an Outbound topology configuration on the F5 SSL Orchestrator.
  • The target system behind the F5 SSL Orchestrator is compromised by the attacker.

Impact

The attacker can extract sensitive data from the target system that is sitting behind the F5 SSL Orchestrator. Note that this issue is not a vulnerability or defect in the F5 SSL Orchestrator; however, you can use the F5 SSL Orchestrator to mitigate this issue as described in the Workaround section.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • The compromised target system connects to the attacker's system using specifically crafted TLS handshake details.

Recommended Actions

Workaround

If the affected F5 SSL Orchestrator is licensed for Secure Web Gateway (SWG) or URL Filtering, the first iRule (following) compares the presented TLS SNI information against known malicious patterns within the URL Filtering database, as well as a custom URL category. You need to add entries to the custom URL category with new exploit domains which have been detected by your other passive tools. For more information about this iRule, refer to iRule to compare TLS SNI information against known malicious patterns within the URL Filtering database and custom URL category.

If the affected SSL Orchestrator does not have SWG or URL Filtering licensed, you can only use the iRule to compare the presented TLS SNI information against your custom URL category. You need to ensure your custom URL category is populated with exploit domains that your passive tools have detected. For more information about this iRule, refer to iRule to compare TLS SNI information against your custom URL category only. Alternatively, you may consider a different iRule that allows the SSL Orchestrator to send the TLS SNI information to a Security Information and Event Management (SIEM) device/log aggregator using high-speed logging (HSL) for offline analysis. For more information about this iRule, refer to iRule to send TLS SNI information to a SIEM device by way of HSL. If you prefer not to use this iRule, you can alternatively configure your SSL Orchestrator to send all traffic to a clone pool comprised of a TAP device in your environment that can potentially flag SNIcat SNI signatures. For more information about this alternative, refer to Configuring SSL Orchestrator to send traffic to a TAP device.

iRule to compare TLS SNI information against known malicious patterns within the URL Filtering database and custom URL category

To use this iRule, ensure that your SSL Orchestrator is licensed and provisioned with SWG or the URL Filtering feature. Ensure that you have created a custom URL category by performing Creating a custom URL category and adding entries. Then copy the following iRule, replace the custom URL category MyDetectedExploitURLCat in the iRule with the name of the custom URL category you created, and  perform Implementing the iRule.

when CLIENT_ACCEPTED {
    set cat ""
    set lookup_url ""
}
when CATEGORY_MATCHED {
    set cat [CATEGORY::result category]
}
when CLIENTSSL_CLIENTHELLO priority 50 {
    if { $cat eq "" } {
       set lookup_url [ACCESS::perflow get perflow.category_lookup.result.url]

        if { ${lookup_url} eq "" } {
            # extract SNI from TLS ClientHello
            if {[SSL::extensions exists -type 0]} {
                binary scan [SSL::extensions -type 0] @9a* SNI
                if {[regexp {(?i)[^a-z0-9.-]} $SNI]} {
                    log local0. "client offered bogus SNI"
                    reject
                } else {
                    set ctx(SNI) [string tolower $SNI]
                    set lookup_url "https://$ctx(SNI)/"
                }
            }
        }

        if { ${lookup_url} ne "" } {
            set cat [CATEGORY::lookup ${lookup_url} request_default_and_custom]
        }
    }

    if { $cat ne "" } {
        switch $cat {
            /Common/Advanced_Malware_Command_and_Control -
            /Common/Advanced_Malware_Payloads {
                reject
            }
            /Common/MyDetectedExploitURLCat {
                reject
            }
            default {
            }
        }
    }
} ; #CLIENTSSL_CLIENTHELLO

iRule to send TLS SNI information to a SIEM device by way of HSL

To use this iRule, ensure that you have configured a pool with the appropriate SIEM device or log aggregator. Copy the following iRule, replace the pool syslog_pool in the iRule with the name of your SIEM device pool, and perform Implementing the iRule.

when RULE_INIT {
    set static::debug 0
}
when CLIENTSSL_CLIENTHELLO priority 25 {
    if {[SSL::extensions exists -type 0]} {
        set hslpool syslog_pool
        set hsl [HSL::open -proto UDP -pool $hslpool]
        binary scan [SSL::extensions -type 0] @9a* SNI
        if {$static::debug eq 1} {log local0. "[IP::client_addr]:[TCP::client_port]->[IP::local_addr]:[TCP::local_port]; SNI:$SNI"}
        # Modify the formatting between quotes to suit whatever SIEM/log aggregation system you are sending to
        # Note syslog expects an RFC3164 compliant facility & severity indicator, e.g. local7.info = <190>
        HSL::send $hsl "<190> [IP::client_addr]:[TCP::client_port]->[IP::local_addr]:[TCP::local_port]; SNI:$SNI"
    }
}

Create a custom URL category and add entries

To create a custom URL category and adding entries, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the SSL Orchestrator Configuration utility.
  2. Go to SSL Orchestrator > Policies > URL Categories.
  3. Select Create.
  4. For Name, enter a name for your custom URL category. For example, MyDetectedExploitURLCat.
  5. For URL, enter a URL you want to block and select Add.
  6. Repeat the previous step for adding more URLs that you want to block.
  7. Select Finished.

Implement the iRule

After you select the iRule most appropriate for your application environment, implement the iRule by performing the following procedure:

Impact of workaround: The example iRule may not apply to all environments. F5 recommends you create an iRule that works best for your application environment. Additionally, adding an iRule increases the resources that the associated virtual server uses. Depending on the type and volume of the connections, this may introduce noticeable latency. F5 recommends testing any such changes in an appropriate environment.

  1. Log in to the SSL Orchestrator Configuration utility.
  2. Go to Local Traffic > iRules > iRule List.
  3. Select Create.
  4. For Name, enter a name for the iRule. For example, K20105555-workaround.
  5. For Definition, paste the iRule you selected.
  6. Select Finished.
  7. Go to SSL Orchestrator > Configuration.
  8. Select Interception Rules.
  9. Select the name of the relevant transparent forward proxy interception rule. For SSL Orchestrator 16.0.0-8.x and later, you need to select the pencil icon to display the Interception Rule settings page.
  10. Under Resources, for iRules, in the Available list, select the iRule you configured earlier and move it to the Selected list.
  11. For SSL Orchestrator 16.0.0-8.x and later, select Save & Next, then select Deploy. For SSL Orchestrator versions prior to 16.0.0-8.x, select Deploy.

Configure SSL Orchestrator to send traffic to a TAP device

If you have a TAP device that can potentially flag SNIcat SNI signatures, you can configure your SSL Orchestrator to send all traffic to this TAP device by performing the following procedure:

Impact of procedure: The workaround requires that you remove protection for the affected SSL Orchestrator deployment configuration by disabling Strict Update; this allows you to manually change your deployment configuration but does not prevent any potential misconfiguration that can result in an unusable application. If re-enable Strict Update for the affected deployment configuration after performing this workaround, the change you made to the virtual server in this workaround are removed.

  1. Log in to the SSL Orchestrator Configuration utility.
  2. Go to Network > VLANs > VLAN List.
  3. Select Create.
  4. Enter a name for the TAP device’s VLAN in the Name setting, for example, tap-vlan.
  5. Select the appropriate interface and tagging, and for Interfaces, select Add.
  6. Select Finished.
  7. Go to Network > Self IPs.
  8. Select Create.
  9. For Name, enter a name for the self IP address. For example, tap-self.
  10. For IP Address and Netmask, enter the self IP address and its netmask, respectively, for example, 198.18.0.100 and 255.255.255.0.
  11. For VLAN / Tunnel, select the appropriate VLAN.
  12. Select Finished.
  13. Configure a static ARP for the TAP device by performing the following steps:
    1. Go to Network > ARP > Static List.
    2. Select Create.
    3. For Name, enter a name for the TAP device’s ARP. For example, tap-arp.
    4. For IP Address, enter the IP address of the TAP device. For example, 198.18.0.50.
    5. For MAC Address, enter the TAP device’s MAC address. If the TAP device does not have a MAC address, ensure that the TAP device is directly connected to the SSL Orchestrator and enter a unique, arbitrary MAC address. For example, 12:12:12:12:12:12.

      Note: When the BIG-IP system clones traffic to the TAP device, the source MAC is the SSL Orchestrator interface and the destination MAC is the MAC address specified in this setting.

    6. Select Finished.
  14. Go to Local Traffic > Pools > Pool List.
  15. Select Create.
  16. For Name, enter a name for the TAP device’s pool. For example, tap-pool.
  17. For Address and Service Port, enter the IP address and listening port of the TAP device, respectively. For example, 198.18.0.50 and 0.
  18. Select Add.
  19. Select Finished.
  20. Go to SSL Orchestrator > Configuration.
  21. Under Topologies, to remove protection for the configuration, select the lock icon for the affected deployment configuration.
  22. Select OK to confirm that you want to remove protection for the configuration.
  23. Go to Local Traffic > Virtual Servers > Virtual Server List.
  24. Select the name of the appropriate virtual server.
  25. For Configuration, select Advanced.
  26. For Clone Pool (Client), select the name of the TAP device pool which you created in previous steps.
  27. Select Update.
