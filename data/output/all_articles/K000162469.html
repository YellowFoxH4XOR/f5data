K000162469: Troubleshooting BIG-IP LTM HA Failover After Lost Heartbeats and Post-Failover Traffic Loss

Type

Published
2026-07-27
Updated
2026-07-27
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000162469

Description

A BIG-IP LTM HA pair can fail over when the standby device stops receiving failover status messages for longer than the configured failover.nettimeoutsec value. Logs may show 010c0083, 010c007e, 010c006d, 010c0053, and 010c0084. After failover, some virtual servers may appear online while their traffic is inaccessible.

Environment

  • BIG-IP LTM HA pair.
  • Active/standby traffic-group configuration.
  • Network failover using unicast communication.
  • Floating virtual server addresses.
  • MAC masquerading configured for the traffic group.
  • Upstream switches and routers responsible for MAC-table and ARP-table updates.
  • The failover.nettimeoutsec system database variable controls the interval before a peer is considered disconnected.
  • Automated REST API or Ansible log extraction may increase management-plane utilization.

Cause

The immediate failover condition is a gap in failover status messages that exceeds the configured failover.nettimeoutsec value. Typical messages include:

010c0083: No failover status messages received for <duration> seconds

010c007e: Not receiving status updates from peer device (Disconnected)

010c006d: Leaving Standby for Active

010c0053: Active for traffic group traffic-group-1

010c0084: Failover status message received after <duration> second gap

The available BIG-IP evidence may confirm the heartbeat interruption without identifying the device or event that caused it. Possible external causes include a transient interruption involving a switch, trunk, link, router, or other network device. Switch-side or router-side captures are required to identify the specific failure mechanism.

If only some virtual servers fail to pass traffic after failover, investigate the upstream network handling of the corresponding floating addresses. Potential causes include:

  • MAC-table learning or forwarding issues.
  • ARP-table update failures.
  • VLAN configuration differences.
  • Port-channel or trunk behavior.
  • ARP inspection or other network policies.
  • Different routing paths for affected and unaffected virtual servers.

A management-plane CPU or memory condition caused by restjavad, REST API, or Ansible activity is a separate issue. It should not be identified as the cause of an HA heartbeat gap without supporting evidence such as TMM termination, SIGABRT, a core dump, or SOD messages indicating that TMM was killed.

Recommended Actions

  • Validate the HA failover
    1. Review /var/log/ltm on both BIG-IP devices.
    2. Search for missing-heartbeat, peer-disconnected, active, standby, and heartbeat-recovery messages.
    3. Compare the heartbeat gap with the configured failover.nettimeoutsec value:
      tmsh list sys db failover.nettimeoutsec
    4. Check for evidence of TMM termination, SIGABRT, core files, or SOD messages indicating that TMM was killed.
    5. Confirm whether the peer completed the expected active-to-standby or standby-to-active state transition.
    6. Review interface, VLAN, failover-network, and system resource logs for evidence of a BIG-IP-side interruption.
    7. Do not attribute the event to management-plane starvation unless the corresponding diagnostic evidence is present.
  • Review the failover timeout

    The failover.nettimeoutsec value determines how long the standby device waits for a failover status update before attempting to become active.

    To modify the value:

    tmsh
    modify /sys db failover.nettimeoutsec value <new_value>

    After changing the value, verify that the configuration is synchronized to the peer device. A value that is too low can cause unnecessary failovers, while a value that is too high can delay legitimate failover detection. Changing the timeout does not correct the underlying network interruption.

  • Validate post-failover traffic
    1. Identify affected and unaffected virtual servers.
    2. Compare their floating IP addresses, VLANs, routes, upstream devices, and network paths.
    3. Confirm that the newly active BIG-IP sent GARPs for the required floating addresses.
    4. Verify that the upstream switches learned the correct MAC-to-port mapping.
    5. Verify that upstream routers refreshed their ARP entries.
    6. Check VLAN configuration, MAC learning, ARP inspection, port-channel behavior, and network policies.
    7. Ask the network team whether any GARP traffic received back on another BIG-IP interface is expected for the physical topology.
    8. Compare the network behavior of affected and unaffected virtual servers to identify configuration or path differences.
  • Perform a controlled GARP or failover test
    1. Use a DR or maintenance environment with a test virtual server.
    2. Use a planned force failover when validating normal failover and GARP behavior.
    3. Avoid restarting the SOD service unless the test specifically requires that behavior.
    4. Capture traffic simultaneously:
      • On both BIG-IP devices.
      • On the switchports connected to the BIG-IP devices.
      • On relevant upstream switches or directly connected network devices.
    5. Confirm that the newly active BIG-IP sends GARPs for every required floating address.
    6. Confirm that the upstream network receives the GARPs and updates its MAC and ARP information.
    7. Compare BIG-IP captures with switch-side captures to identify where traffic is lost, reflected, or ignored.
    8. Verify application access for each test virtual server after the state transition.
    9. Restore the preferred active device after testing.
  • Investigate management-plane utilization
    1. Correlate REST API or Ansible activity with restjavad CPU and memory utilization.
    2. Avoid high-volume automated REST API collection during critical production activity.
    3. Use QKView or other supported diagnostic collection methods where possible.
    4. Review management-plane memory, disk utilization, process restarts, and system resource data before changing provisioning values.
    5. If memory provisioning or service restarts are required, perform the changes during a maintenance window with the device in standby.
    6. Review the guidance for provision.extramb, provision.restjavad.extramb, and Tomcat memory settings before making changes.
    7. Treat extramb values as additional memory above a nonzero baseline. The baseline can vary by BIG-IP version and provisioning configuration.
  • Collect evidence if the issue recurs
    1. Use continuous or rotating packet captures at strategic points in the HA and application traffic paths.
    2. Preserve BIG-IP captures covering the heartbeat interruption and traffic-group transition.
    3. Collect switch and router information for:
      • Link-state changes.
      • Interface errors and discards.
      • MAC-table changes.
      • ARP-table changes.
      • Spanning Tree events.
      • Port-channel events.
      • CPU and I/O utilization.
    4. Ensure that BIG-IP and network-device clocks are synchronized.
    5. Compare the heartbeat interruption with GARP transmission and upstream MAC or ARP updates.
    6. Preserve diagnostic data immediately after the event because a short network interruption cannot generally be reconstructed without captures taken during the interruption.

Additional Information

  • A Clock advanced by <number> ticks message should be correlated with a failover only when its timestamp overlaps the heartbeat interruption. A message recorded outside that interval does not establish the cause of the failover.
  • A GARP capture on BIG-IP confirms that BIG-IP transmitted the GARP. It does not confirm that every upstream switch or router accepted the GARP or updated its forwarding and ARP state.
  • Increasing failover.nettimeoutsec may reduce failovers caused by shorter transient interruptions, but it does not resolve the underlying network condition.
  • Management-plane utilization and TMM traffic-plane processing must be analyzed separately.
  • High restjavad utilization alone does not prove that TMM failed or that HA heartbeat communication was interrupted.
  • A specific external network root cause cannot be confirmed without packet captures or network-device diagnostics from the time of the interruption.
