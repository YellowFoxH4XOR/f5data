K000140936: IPv6 OSPF peering fails after upgrade from 15.1.x to 17.1.x

Type
Support Solution
Published
2024-09-03
Updated
2024-09-03
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.0.0, 17.1.0, 17.0.X, 17.X.X, 17.1.X, 17.1.1
Source
https://my.f5.com/manage/s/article/K000140936

Description

After upgrading from 15.x to 17.x , OSPFv3 neighbor adjacency cannot be established.
Affected Interfaces remain in either EXCHANGE or ExStart state.

Environment

OSPFv3
Software Upgrade from 15.x to 17.x
IPv6 link-local addresses in use

Cause

Unicast OSPF frames are getting dropped between TMM and ZebOS due to a behavior change introduced in version 17.0.0 where the default value of the system variable tm.linklocal.allowservice is now set to none to protect against CVE-2020-5923.
This behavior change is documented in K05975972: BIG-IP self IP vulnerability CVE-2020-5923

Recommended Actions

Follow the steps below to allow OSPF traffic from ipv6 link local addresses while protecting against CVE-2020-5923.

a) Change the 'Allow Default' port lock-down settings to only allow 'ospf:any'
    tmsh modify /net self-allow defaults replace-all-with {ospf:any}

b) Then change the sys db tm.linklocal.allowservice to default
   tmsh modify sys db tm.linklocal.allowservice value default

Note:
This will restrict any self-ip configured with port-lockdown set to default to only accept OSPF, therefore for any such self-IPs if other services such as (ssh, iquery, etc...) are needed, you'll need to modify them and set a custom port-lockdown setting instead of Allow Default.

Additional Information

The sys db tm.linklocal.allowservice only has two possible values - default or none.
The value none means traffic from IPv6 link local addresses is not accepted and the value default relies on the Allow Default port lock-down settings.
