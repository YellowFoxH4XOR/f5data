Description

After upgrading BIG-IP APM to certain recent versions:

  • Some devices cannot connect to the VPN any longer
  • Devices now taking wrong paths though the Policy (different than previous version)
  • Session variables being populated incorrectly

Environment

  • Only affects connections from Windows or MacOS Edge Client applications
  • Browser initiated Access connections (Helper applications) and F5 Access on the various platforms work as expected.
  • Only affects the specific BIG-IP Versions 14.1.4.3, 14.1.4.4, 14.1.4.5, 15.1.2, 15.1.2.1, 15.1.3, 15.1.3.1 and 16.1.0 
  • APM Access Policies deployed on BIG-IP Versions that use "OS Check" or "Client type" Agents, or that make decisions based on session variables

Cause

Changes to the code in the versions above, as a result of fixing ID 660913 have caused some session variable to not be populated correctly.
The variable "session.user.agent" will be blank. Other variables may be incorrect, and tests using these variable may now take inappropriate paths through the Access Policy

Recommended Actions

There are possible workarounds depending on the specific access policy.
There are EHF fixes available for some versions.
Open a case with F5 support for further analysis and recommendations.
The resolution of the issue caused by ID 660913 is being tracked as ID 1042505.

Additional Information

To follow the path being taken by a given session, thru the Access Policy, run the cli command (replacing <sessionID> with the actual session). See the articles below to find the session variable.

  grep 'Following rule' /var/log/apm | grep <sessionID> 

The result will be a series of messages like Following rule 'fallback' from item 'Message Box' to ending 'Allow'
that will allow you to trace the path taken through the specific VPE and find if the session is taking an unexpected path.

As a possible workaround, an iRule can be used to generate a replacement session variable. This could be amended to extract information from the User-Agent.

For example:

# This event fires once per session
when ACCESS_SESSION_STARTED {
  log local0. "Setting User-Agent based on HTTP data - [HTTP::header User-Agent]"
  ACCESS::session data set session.custom.client.useragent [HTTP::header User-Agent]
  #Use this variable in the VPE later to make some decision
}

Note that many browsers are now removing specific information and becoming more general in the name of security. They also may not be accurate, for example Windows 11 has a UA that represents itself as Win 10. MacOS Monterey Beta releases, identified themselves as Big Sur.
