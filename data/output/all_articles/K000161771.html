K000161771: Rebuilding VCMP Guest on Viprion on single blade while other blade is working fine

Source

Description

During some unexpected behavior, config on one of the blades for specific VCMP Guest might be damaged, but working fine on other slot. In such cases, rebuilding from working slot might be easier than troubleshooting the issue on faulty blade.

Environment

  • BIG-IP

  • Viprion
  • VCMP Guest

Cause

There might be multiple reasons for rebuilding VCMP Guest on single slot, compared to rebuilding VCMP Guest from UCS, this procedure does not require deleting config for healthy blade.

Answer/Recommended Actions

Before You Start

  • Save a UCS backup from the working guest slots (not the broken one): tmsh save sys ucs /var/local/ucs/backup_before_repair.ucs
  • Make sure that initial image is matching version running on healthy slot: tmsh list vcmp guest <guest_name> initial-image
  • Note the master key (in case it's needed): f5mku -K

Step 1 — Set Guest to Configured (Shuts it down)

GUI (vCMP Host):

  1. Navigate to vCMP > Guest List
  2. Click the name of the affected guest
  3. In the State field, select Configured
  4. Click Update

The guest will shut down on all slots. Monitor until it disappears from the running list:

watch -n1 tmsh show vcmp guest

Press Ctrl+C when the guest no longer appears.

Step 2 — Delete the Virtual Disk on the Affected Slot Only

GUI (vCMP Host):

  1. Navigate to vCMP > Virtual Disk List
  2. Wait ~1 minute for the vdisk status to change from in-use to ready
  3. Locate the entry for your guest on the affected slot (e.g., guestname.img with Slot ID = affected slot)
  4. Check the checkbox to the left of that entry
  5. Click Delete → confirm Delete

Important: Only delete the vdisk for the affected slot. Do not delete vdisks for the healthy slots.

You can verify via CLI:

tmsh show vcmp virtual-disk

Step 3 — Remove the Affected Slot from "Allowed Slots"

GUI (vCMP Host):

  1. Navigate to vCMP > Guest List
  2. Click the name of the guest (must be in Configured state to edit)
  3. Find the Allowed Slots section
  4. Move the affected slot from the Selected list back to the Available list
  5. Adjust Minimum Number of Slots if needed (must be ≤ number of remaining allowed slots)
  6. Click Update

Step 4 — Deploy the Guest (Without the Affected Slot)

GUI (vCMP Host):

  1. Navigate to vCMP > Guest List
  2. Click the name of the guest
  3. Change State to Deployed
  4. Click Update

Monitor until all remaining slots show running:

watch -n1 tmsh show vcmp guest

Step 5 — Add the Affected Slot Back (Without Shutting Down)

Once the guest is fully running on the other slots, add the affected slot back while the guest remains deployed — this can be done without shutting it down:

GUI (vCMP Host):

  1. Navigate to vCMP > Guest List
  2. Click the name of the guest (while it is still Deployed/Running)
  3. In the Allowed Slots section, move the affected slot back from Available to Selected
  4. Click Update

The host will provision a fresh vdisk on the affected slot and replicate the configuration from the primary slot. Monitor the affected slot coming back up:

tmsh show vcmp guest tmsh show vcmp virtual-disk

The affected slot should transition from starting → running

Additional Information

If this procedure would fail, you can try rebuilding VCMP Guest from UCS.
