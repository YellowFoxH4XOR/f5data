Issue

You should consider using this procedure under the following conditions:

  • Your BIG-IP system experienced network failover occurrences.
  • You want to learn more about troubleshooting network failover communication.

Symptoms

As a result of network failover issues, you may encounter the following symptoms:

  • The active device group member fails over to the standby state.
  • Device group members repeatedly fail over, back and forth.
  • Your BIG-IP system logs error messages related to network failover.

Recommended Actions

Failover is a high availability (HA) process that occurs when an active BIG-IP system in a device group goes offline. When this happens, it causes another device in the device group to become active and begin processing traffic originally targeted for the unavailable unit. The BIG-IP system supports hardwired and network failover options for failover communication. The network failover option is required for the following Sync-Failover device group deployments:

  • Device group configurations containing three or more BIG-IP systems
  • VIPRION HA systems
  • BIG-IP Virtual Edition (VE) HA systems

Network failover communication

When you configure BIG-IP systems to use network failover, each device group member sends network failover heartbeat packets over the network to peer systems. The failover heartbeat packets are transported using User Datagram Protocol (UDP) (default port 1026) for unicast configurations and UDP (default port 62960) for multicast configurations. The packets contain data used to communicate a device's availability and failover status. BIG-IP device group members process network failover traffic as follows:

  • Each device group member advertises a set of IP addresses on which the device is listening for network failover traffic from other device group members.
  • The network failover IP addresses may be one or more of the following types:
    • Multicast IP address (management network only).
    • Unicast IP address (self IP or management network).
  • Each device begins sending its failover status updates to all listening addresses in the device group.
  • The local sod process on each device gathers the failover state information from the failover messages and the HA table, and then it determines if the active traffic group should change.
  • The sod process broadcasts the failover state information to remote sod processes in the device group.
    • For chassis-based systems, each blade runs a sod instance. One blade receives the inbound network failover packets and communicates the failover status to the other blades over the management backplane.
  • Each device independently evaluates the current state of the traffic group on every device group member and determines which should host the traffic group and become the active device.

Network failover IP addresses and ports

Before you troubleshoot a network failover issue, review and ensure that the following network failover requirements are in place:

  • You must allow UDP traffic between all BIG-IP systems in the HA configuration for the network failover service ports used in your environment.
  • You configured the following IP addresses for failover communication, depending on your BIG-IP platform:

Procedures

When experiencing network failover issues, you can use the following troubleshooting steps to determine the root cause:

  • Verifying network failover status
  • Verifying the devices in the device group
  • Verifying network failover IP addresses
  • Reviewing the log files for network failover messages
  • Verifying the failover.nettimeoutsec database value
  • Troubleshooting network failover traffic using the tcpdump utility

Verifying network failover status

When you configure the BIG-IP system to use network failover, it communicates failover status with peer systems by sending failover packets over the network to remote device group members. The network failover heartbeat packets contain data that communicates a device's availability and failover status. You can use the TMOS Shell (tmsh) (BIG-IP 13.x and later) or the tmctl command (BIG-IP 12.x) to display information about the failover status of the local BIG-IP device and the remote device group members, including the number of failover packets exchanged, the date and time of the last received packet, and any network failover warning conditions. To verify the network failover status, perform one of the following procedures:

    tmsh

Verifying the devices in the device group

Depending on the size of the device group configuration, you may want to verify the devices in a device group when troubleshooting network failover communication. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to tmsh by typing the following command:

    tmsh

  2. To verify the devices in the affected device group, use the following command syntax:

    list /cm device-group <device_group_name> network-failover devices

    For example, the following command lists devices in the DG-failover device group. The output indicates that you enabled network failover and three devices reside in the group:

    list /cm device-group DG-failover network-failover devices

    cm device-group DG-failover {
        devices {
            bigip_1.local { }
            bigip_2.local { }
            bigip_3.local { }
        }
        network-failover enabled
    }

Verifying network failover IP addresses and ports

When you configure BIG-IP device group members using network failover, they communicate with each other over the network using addresses and ports that you define. When troubleshooting network failover issues, verify that the systems are configured to communicate using compatible IP addresses and ports. To verify the network failover IP addresses and ports, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to tmsh by typing the following command:

    tmsh

  2. To verify network failover IP addresses and ports, use the following command syntax:

    list /cm device <bigip_hostname> <bigip_hostname> unicast-address multicast-ip multicast-port

    list /cm device bigip_1.local bigip_2.local bigip_3.local unicast-address multicast-ip multicast-port

    • bigip_2.local is not configured to send/receive network failover traffic.

Reviewing the log files for network failover messages

The BIG-IP system logs error messages related to failover, and specifically to network failover, to the /var/log/ltm file. After you locate a log message that indicates a network failover occurrence, you can review the log files surrounding the failover event to help determine the cause of the failover. To review log files related to network failover issues, refer to the following commands:

Impact of procedure: Performing the suggested actions should not have a negative impact on your system.

To display the /var/log/ltm file, use a Linux command similar to the following example:

cat /var/log/ltm

To display log messages related to network failover, use the grep or egrep commands to search for certain patterns in the /var/log/ltm file. For example:

grep -i 'failover packet' /var/log/ltm

You may observe messages similar to the following:

Network failover messageDescription
010c0059: Dropping a failover packet that is too largeThe sod process received a message on one of its failover interfaces that is too large to be a valid failover packet.
010c005a: Dropping a failover packet that is too smallThe sod process received a message on one of its failover interfaces that is not big enough to be a valid failover packet.
010c005b: Dropping a packet that is not a failover packetThe sod process received a message on one of its failover interfaces that is an unknown packet type.
010c0078: Not listening for unicast failover packets on address <IP_address> port <port>The specified IP address / port was removed from or is not defined in the network failover unicast configuration. 

Verifying the failover.nettimeoutsec database value

The BIG-IP system uses a timer to track how many seconds have passed since receiving the last failover heartbeat packet. The failover.nettimeoutsec database key specifies the number of seconds that the system waits after the last update from the peer unit and before attempting to initiate a failover event. For most environments, F5 recommends using the default failover.nettimeoutsec value of three seconds. If you previously changed the failover.nettimeoutsec database key to a value less than the default of three seconds, the systems may experience unnecessary failover events.

To verify the failover.nettimeoutsec database value, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to tmsh by typing the following command:

    tmsh

  2. To verify the failover.nettimeoutsec database value, type the following command:

    list /sys db failover.nettimeoutsec

  3. If the failover.nettimeoutsec database value is less than the default of three seconds, and the BIG-IP systems are experiencing unnecessary failover events, you may need to change the setting back to the default value.

Troubleshooting network failover traffic using the tcpdump utility

In some cases, you may need to manually inspect network failover packets using the tcpdump utility and verify that the devices are receiving packets as expected. To verify network failover traffic using the tcpdump utility, perform the following steps:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the BIG-IP command line.
  2. To verify unicast network failover traffic between device group members, use the following tcpdump command syntax:

    tcpdump -ni <vlan> port <unicast_network_failover_port>

    For example:

    tcpdump -ni internal port 1026

    To verify multicast network failover traffic between device group members, use the following tcpdump command syntax:

    tcpdump -ni <interface> port <multicast_network_failover_port>

    For example:

    tcpdump -ni eth0 port 62960

  3. Verify that the devices are sending and receiving packets as expected and traffic is not blocked by a third-party device, such as a firewall.

Note: For more information about using the tcpdump utility, refer to K411: Overview of packet tracing with the tcpdump utility.
