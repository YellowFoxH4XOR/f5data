Topic

You should consider using this procedure under the following conditions:

  • You want to run tasks in an Ansible playbook on the active member of a device group, and then push the configuration changes to the rest of the device group.
  • Your device group has only one active member.

Description

When you use an Ansible playbook to create objects that are eligible for synchronization on all devices in a device group, you encounter a change conflict between the members. However, you can use the failover state as a condition for performing a task to ensure you are making changes to only the active device in the device group. More specifically, you create a playbook with tasks that use a when statement to ensure they only run when the failover state of a device is active. Then, the tasks run on the active device and not the standby device.

After you create objects on the active device, handlers save the configuration and push a synchronization from the device to the group.

The following is an example of a playbook that uses the preceding elements. The procedures in this article guide you through creating a similar playbook:

---
- name: Create objects only on the active DG member
  hosts: my_dg
  gather_facts: False
  vars:
    provider:
      password: "{{ bigip_password }}"
      server: "{{ ansible_host }}"
      user: "{{ bigip_username }}"
      validate_certs: False

  tasks:
    - name: Get failover state
      shell: tmsh show sys failover | awk '{print $2}'
      register: failover_state

    - block:
      - name: Create node1
        bigip_node:
          provider: "{{ provider }}"
          host: "10.10.10.10"
          name: "10.10.10.10"

      - name: Create node2
        bigip_node:
          provider: "{{ provider }}"
          host: "10.10.10.11"
          name: "10.10.10.11"

      - name: Create pool
        bigip_pool:
          provider: "{{ provider }}"
          lb_method: "round-robin"
          monitors: http
          name: "pool1"

      - name: Add nodes to pool
        bigip_pool_member:
          provider: "{{ provider }}"
          host: "{{ item.host }}"
          name: "{{ item.host }}"
          pool: "pool1"
          port: "80"
        loop:
          - host: "10.10.10.10"
          - host: "10.10.10.11"

      - name: Create a virtual server
        bigip_virtual_server:
          provider: "{{ provider }}"
          name: "vip1"
          destination: "172.31.10.10"
          port: 80
          snat: "Automap"
          all_profiles:
            - http
          pool: "pool1"
        notify:
          - Save the running configuration to disk
          - Sync configuration from device to group

      when: failover_state.stdout == 'active'
      delegate_to: localhost

  handlers:
    - name: Save the running configuration to disk
      bigip_config:
        provider: "{{ provider }}"
        save: yes

    - name: Sync configuration from device to group
      bigip_configsync_action:
        provider: "{{ provider }}"
        device_group: "{{ dg_name }}"
        sync_device_to_group: yes

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have a device group that contains a single active member and any number of standby members.
  • You read the User's Guide section of F5 Modules for Ansible Documentation.
  • You installed ansible-base 2.7 or later or ansible-core 2.11 or later on the control machine.
  • You installed BIG-IP 15.x or later on the devices in your device group.
  • You installed the Python packages required for each module you want to use on the control machine. For more information, refer to Module Index in the Ansible User Guide.

Procedures

  • Creating a group in your inventory that represents the device group
  • Creating the playbook
  • Running the playbook

Creating a group in your inventory that represents the device group

Create a group in your inventory with your device group members.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to your control machine.
  2. Determine whether the control machine has a way to resolve the BIG-IP fully-qualified domain names (FQDNs).

    If it does not, you must use the ansible_host behavioral inventory parameter with device group members.

  3. Create a group in your inventory that represents the device group.

    The following example shows the device group with the ansible_host parameter:

    [my_dg]
    bigip1.askf5team.local ansible_host=172.24.1.1
    bigip2.askf5team.local ansible_host=172.24.1.2

  4. Add group variables that contain the name of the device group and the BIG-IP username and password.

    In this example, you create a group_vars/my_dg/vars.yml file and define the variables there, similar to the following example. Note that the BIG-IP systems use the same password. There are, however, multiple ways to complete this step.

    Important: To avoid exposing the BIG-IP password in plain text, you can define the sensitive variable within a separate group variable file named vault.yml, located in group_vars. Then, you encrypt the file using the ansible-vault command. For more information about how to perform this procedure, refer to K64450989: Using the 'ansible-vault' command to encrypt BIG-IP passwords used in a playbook.

    ---
    bigip_username: "admin"
    bigip_password: "secret"
    dg_name: "my_group"

Creating the playbook

Create a playbook that does the following:

  • Learns the failover status
  • Uses a block of tasks with a conditional that each task inherits
  • Runs the handlers

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to your control machine.
  2. Create a playbook file called failover_state_conditional.yml.
  3. Start your playbook .yml file and set the hosts to the device group you created, such as my_dg in the previous example. Create a playbook variable called provider using the var parameter. Add the BIG-IP connection details with your group variables you defined in step 4 of the Creating a group in your inventory that represents the device group procedure as the values to the provider variable. You can then reference the provider variable in the provider parameter in each BIG-IP module. Refer to the example playbook while creating your playbook. The beginning of your playbook should look similar to the example.

    Note: In the example playbook, F5 assumes that the server parameter value is ansible_host, as described in step 2 of the Creating a group in your inventory that represents the device group procedure. You can also use inventory_hostname for this parameter if it is an FQDN and the control machine can resolve it.

  4. Start your list of tasks with the tasks statement. In the first task, determine the failover state of the devices. Register the state in a variable called failover_state. Your first task should appear similar to the example playbook Get failover state task.
  5. In most scenarios, you want to create more than one object on the active device group member. To avoid having to add when statements to multiple tasks, you can simply add a when statement once to a block statement. Tasks enclosed within the block inherit the directives you apply to it. Create the block statement with your tasks and add when: failover_state.stdout  == 'active' at the block level. When the task runs on the host and the host's failover state matches active, the system runs the task. Otherwise the system skips it. Also add delegate_to: localhost at the block level if all tasks are F5 Modules for Ansible, as shown in the example playbook. For more information, refer to the Connection or delegation chapter of the F5 Modules for Ansible User Guide.

    Since the final task of creating a virtual server requires that the previous tasks completed successfully, you can include a notify statement in this final task to signal the handlers to run. The example playbook shows tasks in a block that creates two nodes and a pool, applies the nodes to the pool, creates a virtual server, and attaches the pool.

  6. Create handlers that run the bigip_config and bigip_configsync_action modules. Your syntax should appear similar to the handlers section in the example playbook.
  7. Save the playbook .yml file

Running the playbook

By this point, you've created each of the following:

  • A group in your inventory that represents the device group.
  • The playbook with the tasks you want to perform on the active device.

You can now run the playbook from your control machine to make configuration changes to the active BIG-IP device in your device group.

Impact of procedure: The following procedure makes configuration changes to the active BIG-IP device group member, saves them, and synchronizes the changes to the group. F5 recommends that you perform this procedure during a scheduled maintenance window.

  1. Log in to your control machine
  2. To run the playbook from the command line of your control machine, type the following command:

    ansible-playbook failover_state_conditional.yml

    The output from the command appears similar to the following example. Note that bigip2 is the standby device, so the configuration change tasks skip this host.

    PLAY [Create objects only on the active DG member] ********************************************************************************

    TASK [Get failover state] ********************************************************************************
    changed: [bigip1.askf5team.local]
    changed: [bigip2.askf5team.local]

    TASK [Create node1] ********************************************************************************
    skipping: [bigip2.askf5team.local]
    changed: [bigip1.askf5team.local]

    TASK [Create node2] ********************************************************************************
    skipping: [bigip2.askf5team.local]
    changed: [bigip1.askf5team.local]

    TASK [Create pool] ********************************************************************************
    skipping: [bigip2.askf5team.local]
    changed: [bigip1.askf5team.local]

    TASK [Add nodes to pool] ********************************************************************************
    skipping: [bigip2.askf5team.local] => (item={u'host': u'10.10.10.10'})
    skipping: [bigip2.askf5team.local] => (item={u'host': u'10.10.10.11'})
    changed: [bigip1.askf5team.local] => (item={u'host': u'10.10.10.10'})
    changed: [bigip1.askf5team.local] => (item={u'host': u'10.10.10.11'})

    TASK [Create a virtual server] ********************************************************************************
    skipping: [bigip2.askf5team.local]
    changed: [bigip1.askf5team.local]

    RUNNING HANDLER [Save the running configuration to disk] ********************************************************************************
    changed: [bigip1.askf5team.local]

    RUNNING HANDLER [Sync configuration from device to group] ********************************************************************************
    changed: [bigip1.askf5team.local]

    PLAY RECAP ********************************************************************************
    bigip1.askf5team.local     : ok=8    changed=8    unreachable=0    failed=0
    bigip2.askf5team.local        : ok=1    changed=1    unreachable=0    failed=0
