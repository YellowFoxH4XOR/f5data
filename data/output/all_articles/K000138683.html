Description

BIG-IP Edge Client connections will fail after an upgrade to APMClients 7.2.4.6, 7.2.4.7, 7.2.4.8 or 7.2.5.x which included the fix for Tunnel Crack vulnerability.

You may see a message on Edge Client similar to:

The VPN connection has failed because it attempted to connect to an insecure network. Please switch to a secure network.

Additionally, in logterminal.txt (which is a part of the Client Troubleshooting Utility report generated per K12444: Overview of the Client Troubleshooting Utility for Windows or located under %TEMP% as explained in K00819308: Gathering F5 VPN client logs ) we can see logs similar to:

YYYY-MM-DD,HH:MM:SS:mmm, 10868,10876,HOST, 48,,,, HostCtrlStatusCallback:CONNECTING_TO_SERVER - [<IPv6/IPv4>].
YYYY-MM-DD,HH:MM:SS:mmm, 10868,10876,HOST, 48,,,, HostCtrlStatusCallback:CONNECTED_TO_SERVER - [<IPv6/IPv4>]. Abort operation.

NOTE: This IP address <IPv6/IPv4> is client DNS server resolved for the Access Virtual server used to connect to the VPN.

...

YYYY-MM-DD,HH:MM:SS:mmm, 10848,11448,HOST, 1, \m_VerifyPreConfigInfo.cpp, 545, verifyPreConfigLocalAndServerIpInformation, ALERT: Provided Resolved IP is NOT a Valid APM Server IP, seems the VS IP is spoofed
...
YYYY-MM-DD,HH:MM:SS:mmm, 10848,11448,APPCTRL, 1, , 53, CAppTunnelEx::OpenByParam, VPN connection is failed due to possible server IP attack, please change your network

Environment

  • BIG-IP APM 15.1.10.3 and later, 16.1.4.3 and later, 17.1.1.x or later
  • APM client/BIG-IP Edge Client  7246, 7247, 7248 or 7250
  • SSL VPN configured

Cause

  • Bug ID 1505789 

Recommended Actions

Perform the following procedures:

  1. Upgrade to BIG-IP 17.5.0, 17.1.2 or 16.1.5 (or later versions of each branch) that contain the fix (which is an ability to account for a scenario where the resolved VPN IP is different than the VS IP, in which cases the connection is considered Insecure before these fixes are applied).
  2. Mitigate the Tunnelcrack vulnerability

Mitigate the Tunnelcrack vulnerability

Prerequisite: This procedure configures the vpn.serveriplist DB variable which was introduced in the Engineering hotfix versions previously provided by F5 product development to fix the issue, as well as the newest releases, BIG-IP 17.5.0, 17.1.2 or 16.1.5 (or later versions of each branch). To perform this procedure, your BIG-IP version needs to be running a version listed in Engineering hotfix (in the Additional Information section) or BIG-IP 17.1.2 or 16.1.5 (or later versions of each branch).

To mitigate the Tunnelcrack vulnerability, perform the following procedure:

1. Determine the FQDN(s) that your users use to access the VPN. It is recommended to do this by performing an nslookup on the fqdn that your client device is using to connect to VPN.

For example:

Client <--- internet ---> [global-ip 159.60.134.0 2001:DB8:0:0:8:800:200C:417A ] NAT/Firewall Device <----> [x.x.x.1] APM VS

Here, client is trying to establish VPN tunnel with vpn1.example.com which resolves to 159.60.134.0. The NAT/Firewall device NAT this traffic to internal APM virtual server (10.10.10.6).

vpn1.example.com resolves to 159.60.134.0 2001:DB8:0:0:8:800:200C:417A (on APM vs handled by vs1 (x.x.x.1))
vpn2.example.com resolves to 159.60.134.1 (on APM vs handled by vs2 (x.x.x.2))
vpn3.example.com resolves to 159.60.134.2 (on APM vs handled by vs3 (x.x.x.3))

2. Configure the DB variable vpn.serveriplist. If you have multiple IP addresses resolved, then separate by "space". Their order does not matter.

tmsh modify sys db vpn.serveriplist value "<ipv4_1> <ipv6_1> ..."
tmsh save sys config

For example, with the data above it would be:

tmsh modify sys db vpn.serveriplist value "159.60.134.0 2001:DB8:0:0:8:800:200C:417A 159.60.134.1 159.60.134.2"
tmsh save sys config

Important: If you've followed these actions, but are still faced with the Insecure prompt, please see K000140218: Insecure Network Prompt even after populating the vpn.serveriplist DB Variable per K000138683

Note:  We recommend to use Apmclients v7248 or later due to below bugs in the Apmclients in v7246 and v7247:

  • Bug ID 1586657, using the vpn.serveriplist DB variable when the BIG-IP APM VPN enabled virtual server is using an IPv6 address may fail with a network is vulnerable error.
  • Bug ID 1580505, the maximum number of IPs that can be processed by v7246 and 7247 of Edge Client is limited (approximately max 18 of ipv4). 

Please refer this solution for how to upgrde Apmclients: K52547540: Updating BIG-IP Edge Client for the BIG-IP APM system

Note: GUI for vpn.serveriplist is not available, and the value would not sync to peer units, so you will need to run this command on all unit in sync and sync-failover group.

 

Additional Information

Important: This section is only for informational purposes and actions described here are no longer the recommended way to fix this problem.

F5 product development previously provided the following actions and workarounds. 

  • Engineering hotfix
  • iRule workaround

Engineering hotfix

Upgrade your BIG-IP APM to one of the following Engineering Hotfix (EHF) versions and also configure the vpn.serveriplist DB variable via tmsh command as described below, By not setting the vpn.serveriplist DB appropriately, you are restoring the previous behavior that is vulnerable to the Tunnelcrack. vulnerability

  • BIGIP-17.1.1.4.0.100.9-ENG
  • BIGIP-17.1.1.3.0.12.5-ENG
  • BIGIP-16.1.4.3.0.11.3-ENG
  • For BIG-IP version v15, which is no longer in support, we no longer have public EHFs available - please open a support case so that we can provide some options.

NOTE: v15.x is in End of Software support on the end of 2024, Please consider upgrading to v16 or later. For the FIPS licensed and supported platforms, we support till end of 2025. Please request EngHF if it is not available in the download site. Please refer further detail of support status: K5903: BIG-IP software support policy

IMPORTANT: The listed BIG-IP EHFs disable the Tunnelcrack fixes by default, setting the vpn.serveriplist DB variable to null.

After installing the BIG-IP updates, perform the procedure to mitigate the Tunnelcrack vulnerability

iRule workaround

There was also an interim iRule workaround to force the serveriplist setting, This is no longer recommended. 

Before applying this iRule, first upgrade BIG-IP APM and Edge Client and any client components like epsec to the recommended versions above. If additional upgrades are installed in the future, you must remove the iRule first, perform the upgrade and then complete steps a.-c. 
This iRule is needed if the https://<Virtual server ip>/pre/config.php?version=2.0 response has ServerIPCheckEnabled flag true. If this tag is not present this is not applicable.

    1. Navigate to https://apm-vs-fqdn.com/pre/config.php?version=2.0 (e.g. using a browser, or the curl command - for that please see the Additional Information section) => You will get the XML payload. (use your VPN fqdn in place of the placeholder "apm-vs-fqdn.com")
    2. Inside the XML payload, in a text editor of your choice, replace the <IP_ServerIP>populate-resolved-global-ip-for-apm-vs-fqdn.com</IP_ServerIP>. (This can be done using a DNS resolution tool like nslookup or dig). 

    3. Use the modified payload in the following iRule in place of XML_Modified_Payload. See the Additional Information section for an example.

      when HTTP_REQUEST {
    if { [HTTP::uri] contains "pre/config" } {
        set xmlPayload1 {XML_Modified_Payload}

        set xmlPayload $xmlPayload1
        HTTP::respond 200 content \
        $xmlPayload \
        "Content-Type" "application/xml"
    }
}
when CLIENT_ACCEPTED {
    ACCESS::restrict_irule_events disable
}

For example:

  1. Use a client, for example the curl command to get the XML payload from the SSL VPN setup at apm-vs-fqdn.com
    curl -k https://<apm-vs-fqdn>/pre/config.php?version=2.0
    Note: that your APM server address should be a secure https port 443 for best security.
    <PROFILE VERSION="2.0"> [... unique XML payload details...] </PROFILE>

    Note: The following iRule uses the pair of curly braces to enclose your XML payload. set xmlPayload1 { <XML payload>.. }
