Topic

This article applies to BIG-IP Link Controller 9.x - 10.x. For information about other versions, refer to the following article:

  • K13761: BIG-IP GTM and Link Controller require a unique VLAN and IP subnet for each configured link (11.x - 13.x).

Note: For detailed information about deploying the BIG-IP Link Controller system, refer to the BIG-IP Link Controller: Implementations guide (this resource was previously known as the BIG-IP Global Traffic Manager and Link Controller: Implementations guide). For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.

As part of the procedure to configure a BIG-IP Link Controller system, you must define the physical connections to the Internet. To do this, you can create link objects using the IP addresses of routers on the network that provide a path to the Internet. To monitor the availability and status of the links, you must use the bigip_link health monitor.

A requirement exists for each link to be associated with a unique Virtual Local Area Network (VLAN) and IP subnet. If multiple links are defined in the same IP subnet, only one link will be marked as up by the bigip_link health monitor (which link will be marked as up depends on the order of the links in the wideip.conf file). This behavior is by design.

You may be able to use the following techniques to ensure that each link resides on a unique VLAN with a unique IP subnet:

  • VLAN tagging

    If the BIG-IP platform does not have sufficient interfaces to accommodate all links and internal networks, you can use the IEEE 802.1Q standard (also known as VLAN tagging) to host multiple VLANs on the same interface. For example, the internal, isp1, isp2 and isp3 VLANs can all reside on the same physical interface as long as VLAN tagging is used.

  • IP subnetting

    If you cannot dedicate an entire IP network to each link, you may be able to more efficiently use the address space that is available to you by performing subnetting. For example, you do not need to dedicate an entire class C network to each link; depending on your specific requirements, the following subnets could suffice: 192.168.1.0/30 for isp1, 192.168.1.4/30 for isp2, and 192.168.1.8/30 for isp3.

F5 Product Development is tracking a Request For Enhancement (RFE) to eliminate the need for the requirement discussed in this article as ID 227251 (formerly CR74470).

Note: The architectural constraint that is discussed in this article may also cause a virtual server to be associated with the wrong link. For more information, refer to K7741: Associating virtual servers with link objects (9.x - 10.x).

Workaround

F5 strongly recommends configuring the BIG-IP Link Controller so that each link resides in a different VLAN and IP subnet. However, if this configuration is not possible, for example because your company does not own or manage the upstream routers, performing the following procedures will allow the bigip_link monitor to correctly verify the availability and status of all links:

Configuring additional self IP addresses so that one self IP address exists for each upstream router

When multiple links reside in the same VLAN and IP subnet, you must create a self IP address for each link. For example, if the BIG-IP Link Controller uses the external VLAN to communicate with three upstream routers and you have already configured the 192.168.1.1/24 self IP address on this VLAN, you need to create two additional self IP addresses. These could be, for example, 192.168.1.2/24 and 192.168.1.3/24. To create the required additional self IP addresses, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Navigate to Network > Self IPs.
  3. Click Create.
  4. Enter an appropriate IP address.

    For example:

    192.168.1.2

  5. Enter an appropriate subnet mask.

    For example:

    255.255.255.0

  6. Select the VLAN that the BIG-IP Link Controller uses to communicate to the upstream routers.

    For example:

    external

  7. Click Finished.

Repeat this procedure until one self IP address exists for each upstream router.

Ensuring that the big3d agent is listening on all configured self IP addresses (prior to version 10.1.0)

The previous procedure had you configure additional self IP addresses on the VLAN that the BIG-IP Link Controller uses to communicate with the upstream routers. Each self IP address configured on this VLAN must listen for incoming iQuery connections. However, on BIG-IP versions prior to 10.1.0, the big3d agent only listens for incoming iQuery connections on the first self IP address configured on each VLAN. For more information, refer to K10331: Configuring the big3d agent to listen on all self IP addresses on a VLAN. If this applies to your BIG-IP Link Controller, perform the procedure outlined in K10331 before continuing.

Manually editing the wideip.conf file and defining a one-to-one mapping between links and self IP addresses

By performing this last procedure, you define a one-to-one association between links and self IP addresses. This manual association will ensure that the availability and status of all links is retrieved correctly.

  1. Log in to the BIG-IP system command line.
  2. Using a text editor of your choice, open the /config/gtm/wideip.conf file.
  3. Inspect the wideip.conf file.

    The file should include a Link Definitions section similar to the following example:

    // *** Link Definitions (3) ***

    link { // datacenter=Default DC
       name        "isp1"
       address     192.168.1.251
       monitor     "bigip_link"
    }

    link { // datacenter=Default DC
       name        "isp2"
       address     192.168.1.252
       monitor     "bigip_link"
    }

    link { // datacenter=Default DC
       name        "isp3"
       address     192.168.1.253
       monitor     "bigip_link"
    }

    The file should include a Server Definitions section similar to the following example:

    // *** Server Definitions (1) ***

    server { // datacenter=Default DC, #VS=0
       name            "LinkController.example.com"
       type            bigip
       box { // gtm
          address 192.168.1.1
          address 192.168.1.2
          address 192.168.1.3
          unit_id 1
       }
       autoconf        enable
       monitor "bigip"
    }

  4. Modify the Server Definitions section by appending a link name after each self IP address. For example

    // *** Server Definitions (1) ***

    server { // datacenter=Default DC, #VS=0
       name            "LinkController.example.com"
       type            bigip
       box { // gtm
          address 192.168.1.1 link "isp1"
          address 192.168.1.2     link "isp2"
          address 192.168.1.3 link "isp3"
          unit_id 1
       }
       autoconf        enable
       monitor "bigip"
    }

  5. Reload the GTM configuration by typing the following command:

    gtmload -l

    Note: One or more instances of the following error may be logged to the /var/log/gtm file:

    011ae0f6:3: Encountered error while processing mcp message at db_gtm_ip.c:164 : GTM IP objects not found

    These errors are benign and should be ignored.

  6. Restart the gtmd daemon by typing the following command:

    bigstart restart gtmd

All links should now be reported as up by the bigip_link monitor.
