Description

The sod process is the core HA failover engine on BIG-IP. It monitors heartbeat communication between HA peers, evaluates HA health scores, and drives traffic group state transitions (Active / Standby / Offline). When sod detects a problem or simply changes state, it logs messages to /var/log/ltm with a structured error code.

This article provides a reference for the most commonly encountered sod log messages, their meaning, impact, and recommended actions.

Environment

  • BIG-IP LTM All
  • Switch-Over Daemon

Cause

  1.  010c0083 — No Failover Status Messages Received (Heartbeat Timeout)

 

Log Example:

warning sod[PID]: 010c0083:4: No failover status messages received for 3.100 seconds, from device /Common/bigip01 (<mgmt_IP>) (unicast: -> <IP>)

 

Description: The sod process has not received a failover heartbeat packet from the peer on this specific unicast path for the duration of the configured network failover timeout (default: 3 seconds, controlled by sys db failover.nettimeoutsec).

 

Impact: If heartbeats are lost on all configured failover addresses simultaneously, a failover will occur. Loss on a single path alone does not trigger failover if other paths are still healthy.

 

Common Causes:

  • Network connectivity issue between HA peers on the failover VLAN/path

  • Peer device is busy (high CPU, resource starvation on VE/hypervisor)

  • Peer device is offline or rebooting

  • Firewall blocking UDP port 1026

 

Recommended Actions:

  • Check if the peer device is reachable on the failover unicast address.

  • Verify UDP port 1026 is not blocked between peers.

  • If on VE/hypervisor, check for CPU overcommitment or VM descheduling.

  • Confirm multiple unicast failover addresses are configured (management IP + TMM self IP) for redundancy.

 

Ref: K95002127: Troubleshooting BIG-IP failover events.

Ref: K17362757: Error Message: 010c0083:4: No failover status messages received for <timeout> seconds

 

2. 010c007e — Not Receiving Status Updates from Peer (Disconnected)

 

Log Example:

notice sod[PID]: 010c007e:5: Not receiving status updates from peer device /Common/bigip01 (Disconnected)

 

Description: The local device has not received failover packets from the peer for the full duration of the network failover timer. The local device marks the peer as Disconnected/Offline. This message typically follows one or more 010c0083 messages and represents the final determination that the peer is unreachable.

 

Impact: The disconnected peer is no longer eligible to become the next active device until failover communication is restored.

 

Common Causes:

  • Sustained network connectivity failure on all failover paths

  • Peer device hardware failure, crash, or reboot

  • Only one unicast failover address configured (single point of failure)

 

Recommended Actions:

  • Verify the physical/logical state of the peer device.

  • Ensure more than one failover unicast address is configured per device (management IP + TMM self IP). See K29518125: HA Active/Active with log message 'Not receiving status updates from peer device'.

  • Check network connectivity between HA peers.

 

Ref: K24005222: Error Message: 010c007e:5: Not receiving status updates from peer device <device> (Disconnected)

 

3. 010c008b — Unable to Send to Unreachable Unicast Address

 

Log Example:

notice sod[PID]: 010c008b:5: Unable to send to unreachable unicast address <IP> port 1026

 

Description: The sod process cannot find a route to send heartbeat packets to the peer's unicast failover address. This is an outbound send failure — the local device has no path to reach the peer's IP.

 

Impact: Peers in the Device Service Cluster (DSC) may not receive heartbeats from this device, potentially causing them to mark this device as disconnected and trigger a failover.

 

Common Causes:

  • Routing issue — no route to the peer's failover IP

  • Interface or VLAN down on the local device

  • Misconfigured failover unicast address (wrong IP/subnet)

 

Recommended Actions:

  • Verify routing to the peer's failover unicast IP address.

  • Check the status of the interface/VLAN used for HA communication.

  • Review network failover configuration: Device Management > Devices > [Device] > Failover Network.

 

Ref: K75975904: Troubleshooting network failover.

Ref: K29449945: Error Message: 010c008b:5: Unable to send to unreachable unicast address <IP_address> port <port_number>

 

4. 010c0078 — Not Listening for Unicast Failover Packets

 

Log Example:

notice sod[PID]: 010c0078: Not listening for unicast failover packets on address <IP> port 1026

 

Description: The sod process has stopped listening for heartbeat packets on the specified unicast address. This occurs when an IP address is removed from the network failover unicast configuration while sod is running.

 

Impact: The sod process no longer listens for heartbeat packets on this address. This is an informational message about a configuration change — it is not an error condition by itself.

 

Common Causes:

  • Administrator removed a unicast failover address from the device configuration

  • Configuration sync pushed a change that removed a failover address

  • Recommended Actions: None required if the address removal was intentional. If unexpected, verify the failover unicast configuration on both devices under Device Management > Devices > [Device] > Failover Network.

 

Ref: K16057220: Error Message: notice sod[<PID>]: 010c0078: Not listening for unicast failover packets on address <IP_address> port <port>

 

5. 010c0084 — Failover Status Message Received After Gap

 

Log Example:

warning sod[PID]: 010c0084:4: Failover status message received after 2073.100 second gap, from device BIG-IP-01 (<mgmt_IP>) (unicast: -> <IP>)

 

Description: A heartbeat message was received from the peer, but only after a very long gap in communication. This indicates that HA communication was interrupted for an extended period and has now resumed. The gap duration shown in the message reflects how long the communication was broken.

 

Impact: During the gap, both devices may have considered themselves active (Active/Active split-brain condition). This is associated with Bug ID1347825, which can occur after upgrades or maintenance on HA pairs with long uptime.

 

Common Causes:

  • Maintenance activity (upgrade, reboot) that disrupted HA communication for an extended period

  • Long uptime of BIG-IP devices combined with a sod counter overflow (Bug ID1347825)

  • Network disruption that lasted longer than the failover timeout

 

Recommended Actions:

  • Before any maintenance that could disrupt HA communication, restart the sod daemon on both devices (during a maintenance window):

    bigstart restart sod

  • Important: Restarting sod on an Active device will cause a momentary offline state and trigger failover.

  • After the gap resolves, verify both devices are in the correct Active/Standby state:

    tmsh show /cm failover-status

 

Ref: K000137340: After the upgrade devices unexpectedly in Active/Active state

Ref: K000140373: [VELOS] Tenants lose HA network failover connection to each other from time to time (F5OS-C Bug ID 1556173)

 

6. 01140029 — HA Feature Fails Action 

 

Log Example:

notice sod[PID]: 01140029:5: HA config_not_received sod fails action is go offline.

warning sod[PID]: 01140029:4: HA daemon_heartbeat tmm fails action is failover and restart
warning sod[PID]: 01140029:4: HA vlan_fs <VLAN_NAME> fails action is failover and abort tm
warning sod[PID]: 01140029:4: HA proc_running bd fails action is go offline and down links

Note: The severity level varies by variant :5: (notice) for config_not_received; :4: (warning) for daemon_heartbeat, proc_running, vlan_fs, and pool_memb_down variants.

Description: The 01140029 message ID is a generic HA failure action message broadly used by sod to report that an HA feature has failed and a configured action is being taken. The specific feature name (e.g., config_not_received, daemon_heartbeat, proc_running, vlan_fs) and the action (e.g., go offline, failover, restart) vary depending on what triggered it.
For the config_not_received variant specifically: In an active-active configuration, network failover must be enabled. If it is not enabled, the BIG-IP systems remain in the offline state and log this message.

 

Impact: The device takes the action specified in the log message (go offline, failover, restart, etc.). For the config_not_received variant, the device goes offline and traffic will not be processed until the underlying condition is resolved.

 

Common Causes (config_not_received variant):

  • Network failover is not enabled on an active-active HA pair

  • Configuration has not been synchronized between peers

 

Recommended Actions:
First, identify the specific feature name in the log message (e.g., config_not_received, daemon_heartbeat, vlan_fs, proc_running) to determine the appropriate response. The actions below apply to the config_not_received variant specifically.

  • For config_not_received:

    • Verify network failover is enabled: Device Management > Device Groups > [Group] > Network Failover.

    • Ensure configuration sync is complete between HA peers. 

  • For other variants, refer to the following resources:

    • daemon_heartbeat / proc_running: Review /var/log/ltm for the daemon   that failed its heartbeat. Check system resources (CPU, memory). Ref: K95002127: Troubleshooting BIG-IP failover events

    • vlan_fs: Review VLAN failsafe configuration. Ensure failsafe is not   enabled on HA-only VLANs. Ref: K000152325: Unexpected Failover of   Active Unit to Standby During Upgrade.
    • pool_memb_down: Check the health of pool members in the HA-monitored pool. Ref: K95002127.

Ref:  K2397: Comparison of serial failover and network failover features.

Ref: Legacy Content K11343: Error Message: HA config_not_received sod fails action is go offline

Ref: K95002127: Troubleshooting BIG-IP failover events
Ref: K000152325: Unexpected Failover of Active Unit to Standby During Upgrade

 

7. 010c0052 — Standby for Traffic Group

 

Log Example:

notice sod[PID]: 010c0052:5: Standby for traffic group traffic-group-1

Note:  K23721299 is marked Legacy Content.

 

Description: A traffic group on this device has transitioned to the Standby state. This is a state notification message, not an error. It is generated when a traffic group is forced to standby, released from forced offline, or transitions to standby as part of a failover event.

 

Impact: No direct impact from this message alone. The floating IPs associated with the traffic group are no longer owned by this device.

 

Recommended Actions: This message by itself requires no action. Always examine the log entries immediately preceding this message to determine what caused the state transition (e.g., 010c0083, 010c0045, 01140029, or an administrative command).

 

Ref: Legacy Content K23721299: Error Message: 010c0052:5: Standby for traffic group /<partition>/<name>

 

8. 010c0053 — Active for Traffic Group

 

Log Example:

notice sod[PID]: 010c0053:5: Active for traffic group traffic-group-1

 

Description: A traffic group on this device has transitioned to the Active state. This is a state notification message. It appears during normal boot-up, after a failover event, or when a device takes over the active role.

 

Impact: No direct impact from this message alone. The device now owns the floating IPs for the traffic group and is processing traffic.

 

Recommended Actions: This message by itself requires no action. If this appears unexpectedly (e.g., on a device that should be standby), examine the preceding log entries to determine the cause of the unexpected state change.

 

Ref: Confirmed in multiple KBs including K27337165, K62511312, and K95002127.

 

9. 010c0045 — Leaving Active (HA Group Score-Based Failover)

 

Log Example:

notice sod[PID]: 010c0045:5: Leaving active, group score 0 peer group score 30

 

Description: The active device is relinquishing the active role because its HA group score has dropped below the peer's score. The HA group feature monitors trunks, pools, or cluster health to calculate a health score. When the local score falls below the peer's score (accounting for the active bonus), a failover is triggered.

 

Impact: The device transitions to Standby. The peer with the higher score takes over as Active. This is by design when the HA group feature is configured.

 

Common Causes:

  • Pool members in an HA-monitored pool went down, dropping the local score to 0

  • A trunk or interface monitored by the HA group went down.

  • The minimum-threshold on an HA group object was breached, zeroing the entire score (applies to BIG-IP 13.1.0 and later).

     

Recommended Actions:

  • Identify what caused the score drop:

    tmsh show sys ha-group detail

  • Check for pool member or trunk failures that preceded the failover.

  • Investigate and resolve the underlying resource failure.

  • If HA group is not required, consider removing it: System > High Availability > HA Group List.

 

Review K16947: F5 recommended practices for the HA group feature.

Ref: K62511312: Cause of Failover - HA Group

Recommended Actions

When you encounter sod log messages related to HA failover, use the following general approach:

  1. Identify the specific error code in /var/log/ltm and locate the corresponding section in this article.
  2. Review the log entries immediately before the sod message to determine the triggering condition.
  3. Check the current HA state of both devices: 
    tmsh show /cm failover-status
tmsh show sys ha-status
  4. For sustained or recurring failover events, collect a QKView and /var/log/ltm from both devices covering the time of the event, and open a case with F5 Support.
  5. Refer to K95002127: Troubleshooting BIG-IP failover events for a comprehensive troubleshooting workflow.
