Description

Retry policy can resend failed requests on upstream side of connection. 
Retries are a mechanism to address transient errors, such as service unavailability, network delays, or temporary backend failures.
Retry policy gives you control over how many times a failed request will be retried, under what conditions this retry should happen and which errors are eligible for retry.
This process is transparent for the user, retry is done fully by load balancer.

Environment

  • F5® Distributed Cloud HTTP Load Balancer
  • Retry policy
  • Simple Route

Answer/Recommended Actions

Retry policy you will find in load balancer routes options:

  1. Open load balancer details.
  2. In the top-right corner click on Edit Configuration.
  3. Scroll down to the Routes section and click Edit Configuration.
  4. In the Routes list that appears, click on Add an item if the list is empty, or click on the existing route Edit option.
  5. Go to Advanced Options and Edit Configuration.
  6. Then find Miscellaneous Options and Select Retry Policy.
  7. You can choose from 3 options:

    All options are described below.  

Do not retry: Retry mechanism on route will be disabled. 

Default retry policy 

Default retry policy use below settings:

  • Retry condition: 5xx
  • Number of retries: 1

Custom retry policy option

In custom retry policy, we have available below options.

Retry conditions - specifies condition when retry take place (we can choose multiple conditions):

  • "5xx" : Retry will be done if the upstream server responds with any 5xx response code, or does not respond at all (disconnect/reset/read timeout). 
  • "gateway-error" : Retry will be done only if the upstream server responds with 502, 503 or 504 responses (Included in 5xx) 
  • "connect-failure" : Retry will be done if the request fails because of a connection failure to the upstream server (connect timeout, etc.). (Included in 5xx) 
  • "refused-stream" : Retry is done if the upstream server resets the stream with a REFUSED_STREAM error code (Included in 5xx)
  • "retriable-4xx" : Retry is done if the upstream server responds with a retriable 4xx response code. The only response code in this category is HTTP CONFLICT (409) 
  • "retriable-status-codes" : Retry is done if the upstream server responds with any response code matching one defined in retriable_status_codes field  
  • "reset" : Retry is done if the upstream server does not respond at all (disconnect/reset/read timeout.)"

Number of Retries - specify the allowed number of retries.

Per Try Timeout - specifies timeout of the retry in milliseconds.

Status code to retry - HTTP status codes that should trigger a retry in addition to those specified by Retry conditions.

Base Retry Interval - Specifies the base interval between retries. 

Maximum Retry Interval - Specifies the maximum interval between retries in milliseconds. This parameter is optional, but must be greater than or equal to the base_interval if set. The default is 10 times the base_interval.

Be aware that per try timeout has to be greater than or equal to the max response time for a HTTP request (you might set this to what's currently configured in the Route -> Miscellaneous Options -> Timeout (ms)). As well as, the Routes Timeout should be greater than or equal to No of Retries * (PerTryTimeout + MaxRetryInterval). If Route timeout is lower, we will not perform all of the retries. As soon as request will reach route timeout, LB will stop request processing/retries and will return timeout error.

Example: if the PerTryTimeout is 30000ms and with 3 retries and 100ms max interval then the Routes timeout should be at least 91000ms.

Additional Information

LB without routes use "Default retry policy". 

Modification of retry policy is possible only via route configuration.
