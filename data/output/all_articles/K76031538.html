Known Issue

The BIG-IP system may fail to provide BIG-IP control plane processes (such as sod and bigd) with adequate CPU processing time.

This issue occurs when all of the following conditions are met:

  • The BIG-IP system is provisioned with one or more modules that uses MySQL, for example BIG-IP ASM and BIG-IP Analytics.

    Note: The following also implicitly provision BIG-IP Analytics: BIG-IP ASM, BIG-IP AFM, BIG-IP DNS, BIG-IP APM, BIG-IP PEM, and Virtual Clustered Multiprocessing (vCMP).

  • The BIG-IP system is running on a vCMP guest that is provisioned with two CPU cores, or with two cores per blade for multi-blade vCMP guests.
  • The vCMP host is running on platforms with Intel Hyper-Threading Technology (HT Technology) physical CPUs.

On systems such as BIG-IP ASM, the control plane processes are pinned to the highest-numbered logical CPU core. This may cause contention with BIG-IP control plane processes in systems that are only provisioned with two CPU cores where one core is dedicated to the Traffic Management Microkernel (TMM) while the other core is shared among the remaining BIG-IP and BIG-IP ASM control plane processes. This may result in BIG-IP control plane processes deprived of CPU processing time.

Impact

This is a rarely occurring issue. The impact depends on the BIG-IP control plane process affected. If the sod process is affected, then the BIG-IP system in a high availability (HA) configuration may fail over to its peer. If the bigd process is affected, then the BIG-IP system may erroneously mark down the pool members.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The BIG-IP system fails over to a peer system when the sod process experiences CPU processing time deprivation.
  • The BIG-IP system erroneously marks down pool members when the bigd process experiences CPU processing time deprivation.

Workaround

To prevent this issue from occurring, you may consider provisioning additional CPU cores to the affected vCMP guest. If you are not able to do so, you may consider the following workaround:

To work around this issue, you can set the scheduler.splitplanes.asmopt database key to false. You should not modify the default value (true) of this database key unless requested by F5 Technical Support as this action reverts the BIG-IP ASM behavior to that of versions before BIG-IP 11.5.1 HF4. For more information, refer to K16469: Certain BIG-IP ASM control plane processes are now pinned to the highest-numbered logical CPU core. However, if required, you can set the database key to false by performing the following procedure:

Impact of workaround: This procedure may cause loss of performance and management response improvements and requires a system restart. Restarting services causes a brief traffic disruption.

  1. Log in to the TMOS Shell (tmsh) by typing the following command:

    tmsh

  2. To set the scheduler.splitplanes.asmopt database key to false, type the following command:

    modify sys db scheduler.splitplanes.asmopt value false

  3. To restart the system, type the following command:

    reboot
