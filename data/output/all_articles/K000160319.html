Description

Users experience intermittent failures (often under increased load) when attempting to launch new Citrix VDI sessions through BIG-IP APM. Users can authenticate and access the Citrix StoreFront portal, but are unable to launch new applications or desktops. Error messages such as "unable to load resource" may appear in the browser. Packet captures and logs show TCP RST packets during failed connection attempts, with the destination IP resolved as 127.0.0.1 (localhost) instead of the correct VDA IP.

Environment

  • F5 BIG-IP APM
  • Citrix VDI integration using iApp template (f5.citrix_vdi.v2.4.6)
  • Multiple DNS servers configured on BIG-IP, including both internal and public DNS servers
  • Citrix StoreFront and VDA servers accessed via FQDNs requiring internal DNS resolution

Cause

The root cause is the presence of public DNS servers in the BIG-IP DNS resolver list that cannot resolve internal Citrix VDI FQDNs. When these servers are selected, they return NXDOMAIN or no answer, triggering a final retry with ".localhost" appended. This results in a DNS response of (localhost127.0.0.1, causing the VDI plugin to attempt backend connections to localhost, which fail.

Answer/Recommended Actions

When DNS resolution fails, BIG-IP may append ".localhost" to the query, resulting in a ,127.0.0.1 response per RFC 6761. Removing non-functional or external DNS servers from the resolver list prevents the fallback to ".localhost" and ensures correct VDI backend resolution. Please perfrom the following tasks to avoid this problem:

 

  1. Review the DNS server list configured on BIG-IP (System ›› Configuration ›› Device ›› DNS).
  2. Remove any DNS servers that cannot resolve internal Citrix VDI FQDNs (such as public DNS servers).
  3. Ensure only internal DNS servers capable of resolving all required internal hostnames are configured.
  4. Optionally, review and update the DNS Search Domain List to avoid unintended ".localhost" resolution behavior.
  5. After making changes, monitor for further connection failures and verify that all VDI-related FQDNs resolve correctly from the BIG-IP CLI using the dig or nslookup commands.
  6. If the issue persists, consider capturing DNS traffic on BIG-IP to confirm which DNS server is being queried and what response is received.
