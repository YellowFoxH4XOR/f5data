Description

On a VELOS chassis with BX520 blades running F5OS-C, BIG-IP tenants configured with translucent or transparent VLAN-groups may experience intermittent packet loss and pool member monitor flapping (monitors going down and recovering repeatedly). The issue occurs even when the VLANs involved are not shared with other tenants.

Symptoms include:

  • Pool member ICMP or TCP monitors flapping, typically going down for 24–30 seconds before recovering
  • Intermittent packet loss when pinging self-IPs on VLANs that are members of a VLAN-group
  • The issue affects both Active and Standby tenants; on Standby tenants only monitor traffic is dropped, while on Active tenants user traffic is also impacted
  • Symptoms are not observed on BX110 blades, on VCMP guests on the same upstream switch, or on Viprion platforms with equivalent VLAN-group configuration
  • FPGA DLF (Destination Lookup Failure) drop counters incrementing at a high and sustained rate

Similar log messages may appear repeatedly in /var/log/ltm on the affected BIG-IP tenant:

notice mcpd[7822]: 01070638:5: Pool /partition/pool member /partition/node:0 monitor status down. [ /partition/monitor: down; last error: Connection reset @2026/02/17 14:30:38. ] [ was up for 115hrs:57mins:13sec ]
Important: This issue is specific ONLY to the BX520 blade due to its dual-ATSE architecture. BX110 blades, rSeries appliances, and Viprion platforms are not affected by this particular failure mechanism.

See the companion article F5OS VELOS: Packet loss or unicast traffic replication when a VLAN used in a tenant VLAN-group is shared with other tenants.

Cause

The root cause is a cascade of events unique to the BX520 blade's dual-ATSE architecture (ATSE being one of the internal FPGA components).

The egress tenant traffic sent from different TMMs that are physically dispersed between different traffic processing units inside FPGA. This is leading to a situation in which same source MAC address is being learned from different internal host ports. This is happening very quickly due to constant egress traffic and causing FPGA to consider the entry as unstable and putting into Pending state, effectively not inserting into L2 forwarding table. This is similar to "MAC address flapping" between 2 L2 switch ports in switching environments.

Since these MAC addresses are not part of the table, all return traffic destined to these MACs is therefore treated as a Destination Lookup Failure (DLF) and is intermittently dropped by the FPGA's built-in DLF rate-limiter.

The issue affects both transparent and translucent VLAN-groups, in which the source MAC address can be either bit-flipped tenant MAC address or actual client/server MAC addresses (that are preserved in vlan-group implementation).

Recommended Actions

There are a few possible workarounds/approaches.

1. Configure a static FDB entry for the bit-flipped MAC (in translucent VLAN-groups)

This will make sure the entry won't be flapping during learning process.

In the VELOS partition CLI, list all L2-LISTENER entries to find the bit-flipped MAC associated with the affected tenant. The bit-flipped MAC has the locally-administered (LA) bit set — the second hex digit of the first octet will be 2, 6, A, or E (for example, 16:xx:xx:xx:xx:xx is bit-flipped from 12:xx:xx:xx:xx:xx).

Then in VELOS partition CLI, show all the fdb entries and find the L2-LISTENER entry for the tenant.

show fdb

# Look for rows where ENTRY TYPE = L2-LISTENER and OWNER = <affected-tenant-name>
# The bit-flipped MAC will have the second hex nibble as 2, 6, A, or E

Then in partition CLI add a static fdb entry that points towards the tenant. For example:

# Replace <bit-flipped-MAC>, <vlan-id>, <tenant-name> and svc with actual values. Note that for ingress static MAC (i.e. tenant is the forwarding destination), we configure L2-LISTENER with svc ID as destination.

conf t
fdb mac-table entries entry <bit-flipped-MAC> <vlan-id> tag_type_vid config entry-type L2-LISTENER owner <tenant-name> config ifh-fields svc 15 ifh-fields cmds 1
commit

# To remove the static entry when no longer needed:
no fdb mac-table entries entry <bit-flipped-MAC> <vlan-id>
commit
Limitation: This workaround must be applied for each VLAN in the VLAN-group in case of translucent one.
For transparent vlan-group, this workaround might not be practical as there are too many MAC Addresses involved.

2.  Switch to opaque VLAN-group mode

In opaque mode, BIG-IP uses its own static tenant MAC address as the source MAC for all bridged traffic. The static MAC is already part of the FDB and does not experience dynamic learning or flapping.

# On the BIG-IP tenant CLI:
tmsh modify net vlan-group <vlan-group-name> mode opaque
tmsh save sys config
Note: Opaque mode changes bridging behavior. Validate this change for your specific deployment before applying it in production.

3. Consider migrating to virtual-wire (vWire) solution instead of VLAN-groups

Virtual-wire is the F5OS-native, hardware-based equivalent of VLAN-group for L2 inline deployments. vWire was designed for F5OS and uses MAC-learning-avoiding mechanisms that are fully compatible with the VELOS FPGA forwarding architecture. Migration to vWire is the recommended long-term solution. This solution needs dedicated planning and it is always recommended to have F5 Professional Services involved in such a deployment change.
