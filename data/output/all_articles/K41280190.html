Topic

A certificate chain acts to establish trusts between Certificate Authorities (CAs) of a Public Key Infrastructure (PKI). The trust sets the hierarchical roles and relationships between the root CA, the intermediate CA, and the issued SSL certificates.

Description

Differentiating root and intermediate CAs

The root CA is the absolute base of the certificate chain. Certificates issued by the root CA carry the same level of trust as the root CA certificate. The root CA typically signs the certificate for the intermediate CA. The role of the intermediate CA is to sign end-entity certificates for the root CA. The goal in having the intermediate CA perform this task is to limit exposure to the root CA.

SSL certificate

The SSL certificate is signed by an intermediate CA for use as a domain specific certificate. The SSL certificate is installed on a SSL enabled server (end-entity) and the certificate is presented to the browser when initiating an SSL connection with the server. The browser will attempt to confirm the authenticity of the end-entity certificate by checking the signing authority of the certificate.

Intermediate CA

The intermediate CA is a subordinate to a specific root CA and uses a certificate signed by the root CA. The intermediate CA is typically the signer of SSL certificates. The intermediate CAs derive their CA directly from the signing root CA.

Root CA

The root CA utilizes a X.509-based public key certificate that specifically identifies the root CA. The root CA is the absolute signing authority for the SSL certificate chain. Browser vendors include a list of known, trusted root CAs that will ultimately determine the validity of a SSL certificate.

In order for a browser to accept an SSL certificate, the certificate must be issued by a CA that has a signed certificate from a root CA that is included in the browser's store of known, trusted root CAs. The browser will check each intermediate CA's certificate to establish if it was issued by a known, trusted root CA. If the certificate of the intermediate CA was signed by another intermediate CA, the web browser will then check that intermediate CA's certificate to see if the issuer of the certificate is a known, trusted root CA. This chain of checking one level deeper will continue until the root CA certificate is located and checked against the browser's trusted store of root CAs.

When the root CA matches a known, trusted root CA in the browser's store, the SSL certificate is accepted as valid. When there is no match for the root CA, the SSL certificate is considered untrusted. Untrusted SSL connections are handled in various ways by different browser vendors, most will warn that the connection is untrusted, requiring the user to acknowledge the discrepancy or outright fail to allow the connection to establish.

Mapping SSL certificates from the SSL certificates through the intermediate CA that signed the SSL certificate, and ultimately to the root CA that signed the intermediate CA certificate, is what is called the SSL certificate chain. The chain may contain several intermediate CAs between the SSL and the root CA.

Figure: SSL chain example

  1. A browser initiates an SSL connection to a domain (end entity) that has an SSL certificate signed by an intermediate CA.
  2. A root CA signs the intermediate CA.
  3. The browser follows signing signatures in the end entity through the intermediate CA and the root CA.
  4. The browser compares the root CA signature against that of the root CA it contains within its security store.
  5. If the root CA signatures match, the intermediate certificate and the end entity certificate are validated as authentic and the connection is secured.

Note: This chain of events occurs in the same manner regardless of whether you have one intermediate CA certificate or multiple intermediate CA certificates.

Note: To have this chain of events function correctly for the end-entity certificate given to the browser SSL request, all the intermediate certificates need to be present along with the end-entity (server) certificate when receiving the SSL connection request. The grouping of certificates for all the intermediate CAs is called a certificate bundle. You can configure the BIG-IP Client SSL profile to include a certificate bundle along with the end-entity certificate and key.

View the chain from the command line

You can use openssl to view all of the certificates and their subject and issuers to trace the chain of trust by entering the following syntax:

# openssl crl2pkcs7 -nocrl -certfile <FILENAME GOES HERE> | openssl pkcs7 -print_certs -noout -text | grep "Issuer:\|Subject:\|Not Before:\|Not
