K000162645: Prevent Kerberos WebSSO from Processing OAuth Bearer-Authenticated API Traffic

Type
Support Solution
Published
2026-07-29
Updated
2026-07-29
Applies to
  • BIG-IP
  • BIG-IP APM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000162645

Description

BIG-IP APM can disable Kerberos WebSSO for a session when an API returns an HTTP 401 response with a WWW-Authenticate: Bearer challenge. The following messages may appear in /var/log/apm:

  • Disabled the SSO for this session: no supported WWW-Authenticate header is found
  • Server Response won't be processed further as SSO disabled
  • sso_disable: 1

This occurs when OAuth Bearer-authenticated API traffic and Kerberos WebSSO application traffic use the same APM access profile.

Environment

  • BIG-IP APM
  • APM access profile with an associated Kerberos WebSSO configuration
  • API endpoints accessed through the same APM tunnel or session as an application that requires Kerberos WebSSO
  • API endpoints authenticated with OAuth Bearer tokens
  • Kerberos WebSSO required only for selected application traffic

Cause

When WebSSO is associated with an APM access profile, the WebSSO agent can process HTTP responses traversing sessions that use the profile. WebSSO is not automatically restricted to a specific destination host unless the access policy explicitly scopes the processing.

When an API returns an HTTP 401 response containing WWW-Authenticate: Bearer, the Kerberos WebSSO configuration does not support that authentication scheme. APM then disables WebSSO for the session.

A WebSSO-disabled message does not necessarily terminate the APM session or block all subsequent traffic. However, later requests that depend on Kerberos WebSSO may fail.

Recommended Actions

  1. Identify the application traffic that requires Kerberos WebSSO and the API hosts or paths that use OAuth Bearer authentication.
  2. Configure access-policy branching or host- and path-based conditions so that Kerberos WebSSO is applied only to the intended application traffic.
  3. Prevent OAuth Bearer-authenticated API requests and responses from being processed by the Kerberos WebSSO configuration while keeping the requests within the existing APM tunnel or session.
  4. If WebSSO is not required by any traffic using the access profile, remove the WebSSO association from the profile. Do not use this approach when other application traffic on the same profile requires Kerberos WebSSO.
  5. If access-policy scoping cannot be implemented, evaluate a host- or path-based iRule approach. Test the configuration in a non-production environment and verify that it does not interfere with access-session processing.
  6. Test with a new APM session and verify the following:
  • Kerberos WebSSO continues to work for the intended application.
  • API requests retain their OAuth Bearer tokens.
  • API responses do not cause WebSSO to be disabled.
  • Application SSO and related API functions operate normally.
  1. Return APM logging to its normal level after troubleshooting.
  2. Rotate or revoke any OAuth tokens, credentials, API keys, or other authentication material exposed in debug logs.

Additional Information

  • KRB5KRB_ERR_RESPONSE_TOO_BIG in a Kerberos packet capture does not by itself indicate a failure. Kerberos can retry the exchange over TCP when the response exceeds the UDP limit.
  • Successful Kerberos ticket acquisition and S4U2Proxy processing do not prevent a separate OAuth Bearer authentication conflict from disabling WebSSO.
  • A new APM session is required to validate configuration changes because an existing session may already have WebSSO disabled.
  • If an API returns HTTP 401 with WWW-Authenticate: Bearer, verify that OAuth Bearer authentication is the expected authentication method for that endpoint.
