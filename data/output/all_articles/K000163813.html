K000163813: Troubleshooting iRuleLX Streaming Mode Request Processing Stalls on BIG-IP

Type
Support Solution
Published
2026-10-21
Updated
2026-10-21
Applies to
  • BIG-IP
  • BIG-IP LTM: 21.1.0
Source
https://my.f5.com/manage/s/article/K000163813

Description

iRuleLX in Streaming mode stops processing requests. The iRule continues to run in TMM, but most requests remain unprocessed, and no iRuleLX logs are generated, including logs from the business logic within the iRuleLX extension. Requests resume processing after the iRuleLX workspace is reloaded.

Key characteristics:

  • Most requests remain in an unprocessed state, and only a small number are occasionally handled.
  • TMM and overall host performance show no degradation, and no TMM crashes or iRule errors are reported.
  • No iRuleLX business logic log output is produced during the stall.

Because iRuleLX sends data from the iRule to a control plane Node.js component, a stall with a healthy TMM typically indicates a failure in the control plane component, not in the iRule itself. Control plane failures can be caused by:

  • restjavad failures or restarts
  • High control plane CPU or memory contention from other processes
  • High TMM traffic load that starves control plane CPU, including activation of Idle Enforcer on the management/control plane CPUs

Environment

  • BIG-IP LTM with iRuleLX (Streaming mode) using the llm-router extension
  • Reported affected version: BIG-IP 21.1.0
  • Lab validation performed on BIG-IP v17.1.3 and v21.x without reproducing the issue
  • Lab configuration tested: 4-core, 8 GB VE with LTM, iRuleLX, and Large MGMT provisioning, with stable iRuleLX extension CPU and memory

Cause

Control plane resource starvation (CPU or memory) affecting the Node.js component of iRuleLX, possibly related to restjavad memory pressure or Idle Enforcer activation during peak traffic load.

Answer/Recommended Actions

  1. Verify control plane health before enabling iRuleLX. Upload a qkview of the affected device to iHealth and confirm the following:
    • No crashing or restarting processes
    • Low control plane CPU usage
    • Sufficient free memory after TMM allocation
  2. Check restjavad health. If iHealth shows restjavad failures due to lack of memory, increase its memory provisioning. Confirm sufficient free memory first, and apply these changes during a maintenance window on a standby device, because they restart TMM and can cause an HA failover if run on an active device. Example of high provisioning settings:

    tmsh modify sys db provision.extramb value 4000

    tmsh modify sys db provision.restjavad.extramb value 2227

    tmsh modify sys db provision.tomcat.extramb value 300

    tmsh modify sys db restnoded.timeout value 600

    tmsh modify sys db restjavad.timeout value 600

    tmsh modify sys db icrd.timeout value 600

    tmsh modify sys httpd max-clients 25

    bigstart restart tomcat && sleep 20 && bigstart restart httpd && sleep 20 && bigstart restart restjavad && sleep 20 && bigstart restart restnoded

    tmsh save sys config

  3. Check for Idle Enforcer activation. Review qkview graphs to determine whether Idle Enforcer activates on the management/control plane CPUs during peak TMM load. If it does, add licensed traffic cores so that Idle Enforcer does not activate, or defer iRuleLX deployment until it no longer activates.
  4. On a VE, allocate more CPU cores to the management/control plane if control plane CPU is constrained.
  5. Monitor the iRuleLX extension during operation with the following command:

    tmsh show ilx plugin /Common/<plugin_name> extensions { <name> }

  6. Collect diagnostic data immediately after a failure:
    • Generate a full qkview with logs using qkview -s0. Ideally, generate it within 3 hours of the failure, because the first 3 hours of qkview graphs provide the highest granularity.
    • Collect a tarball of /var/log/ in case the qkview omits data.
    • Check /var/log/ltm for TCL errors, which would indicate an iRule-side failure.

Additional Information

  • A TMM-side failure (iRule errors in /var/log/ltm, TMM crashes, or traffic impact) points to the iRule itself. A stall with a healthy TMM and no logs points to the control plane Node.js component.
  • Lab testing that does not reproduce the issue does not rule out the problem, because the failure is likely tied to production control plane load and conditions (such as monitoring load or high traffic) that are not present in a lab environment.
  • Redeploying iRuleLX on a device with unresolved control plane issues is likely to reproduce the failure.
