Description

Big-IP uses OpenSSL for certification validation. Big-IP versions prior to 14.1.x use OpenSSL-1.0.1. In Big-IP versions starting with 14.1.x, OpenSSL is upgraded to use OpenSSL-1.0.2. 

In versions prior to 14.1.x, the Big-IP device used to create a certificate chain and send the same to OpenSSL at the time. The OpenSSL version used in these releases used to only validate a certificate chain supplied to it. It allowed any externally created certificate chain.

In versions starting with 14.1.x, the OpenSSL version used in these releases creates a certificate chain as part of its validation. It does not accept any externally created certificate chain. An error message is raised if any such externally created chain were supplied to it.

Environment

  • Virtual server with Client SSL profile associated to perform client authentication
  • Expired certificates present within Certificate Authority chain

Cause

Originally the constructed certificate chain contains only one trusted certificate (may not be the root certificate). The chain verification succeeded if all certificates below this certificate was verified successfully. This was the case in all BIG-IP versions prior to 14.1.x. In the Big-IP versions starting with 14.1.x, if even one invalid (i.e., expired) trusted root or intermediate certificate is present in the chain, the verification fails. This is tracked as a known bug by Product Development at ID1070789.

Recommended Actions

The short-term recommendation is to remove all invalid trusted (i.e., expired) certificates from the certificate chain and, if it hasn't already been done, replace them with a valid trusted certificate.

The long-term recommendation is to upgrade to 16.1.3.1+ or 17.1.0+ releases in order to obtain the fix for ID1070789. As part of the fix, BIG-IP evaluates all intermediate/root certificates with the same Subject name in the bundle, not just the first one. The selection process considers the validity of the certificates and here are examples of some scenarios:

  1. If the bundle contains two issuer certificates with the same Subject name, where the first certificate is expired and the second one is valid, the fix will include the second (valid) certificate in the chain and ignore the first (expired) one.
  2. If the bundle has two issuer certificates with the same Subject name and both are expired, the fix will include the second (expired) certificate in the chain to complete it, leading to a TLS handshake failure.
  3. If the bundle has two issuer certificates with the same Subject name and both are valid, the fix will include the first valid certificate in the chain.

In summary, as part of the fix, BIG-IP evaluates all certificates in the bundle until it finds a valid one with the same Subject name. If none are valid, it will choose the last expired certificate.

Additional InformationA bug in OpenSSL 1.0.2 (and possibly earlier versions) went undetected until recently, leading to a solution being implemented in BIG-IP software code. The OpenSSL team didn't resolve the issue in version 1.0.2 due to its end-of-life status, though it was fixed in later versions. 

The fix still doesn't allow for OpenSSL to accept any externally created certificate chains. Instead, it simply results in changes made to TMM which uses OpenSSL's x509_verify_cert() function to perform certificate validation.
