Description
Some customers are introducing the implementation of Cross-Origin Resource Sharing or "CORS"  functionality within HTML in order to execute calls between domains in an HTTP website.   This is commonly used as a request for resources in another domain as part of an HTML Page load.    CORS has restrictive rules about what is allowed, and not allowed in packets specific to a CORS request, which may interfere with the normal operation of a website or web page being protected by an APM policy. 

Environment

  • BIG-IP APM
  • A Website that contains CORS Specification related functionality. 
  • Attempting to access the website thru an APM Protected resource

Cause
CORS functionality is not supported by BIG-IP APM.

Recommended Actions

  1.   Do not attempt to access websites containing CORS functions that, in the process of creating the sending packet, strip APM Headers, APM Session cookies, or other information critical to APM function from the packets. 

Additional Information

CORS Pre-flight requests come with a requirement that no Cookies or headers are allowed in the request.   Unfortunately,  this CORS request breaks APM functionality by stripping the APM Session cookies from the packet payload.    This results in a 302 redirect to https://<APM protected Virtual>/my.policy 

This results in APM asking the user to authenticate, and/or to create a new APM session.   While this is normal behavior for an APM protected resource (all requests must contain APM related Session Cookies), it does not work with some functions in the CORS Standard located at https://www.w3.org/TR/cors/

iRules might be used to manage or mitigate these requests, but F5 does not have specific guidance, as each specific use case is quite unique.  F5 Professional services may be able to assist with this type of customization.
