Description

The pool member is marked down by HTTPS monitor failure since the monitor uses Client Hello with TLSv1 which is not a supported version on the server.

Symptoms

  • HTTPS monitors to mark a TLS v1.2-configured pool member down and never mark it back up again, even if the pool member is up.
  • After the handshake fails for some reason, the monitor falls back to TLS v1.1 or TLS v1 by triggering the legacy mode.
  • The server sends a Reset packet after the client hello instead of the SSL alert error packet regarding the "protocol_version" alert.

Environment

  • HTTPS monitor configured.
  • The server only supports TLSv1.2.
  • The legacy mode of the HTTPS monitor is enabled for fallback.
Monitor logging enabled, you can see the "legacy: true" when monitor is in fallback mode. 
[0][25276] 2020-05-14 17:10:07.346789: ID 20    :(initialize_ssl) legacy: true, compat: true, options: 0x80000bff [ tmm?=false td=true tr=false addr=....]

Cause

  • If the server supports only versions greater than client_version, it MUST send a "protocol_version" alert message and close the connection based on RFC5426.
  • However, the server does not send an SSL alert message, the server just sent a Reset packet instead after the client hello. 
  • By design, the system expects a TLS layer response to versions with the wrong request. But there is no SSL alert from the server, so it just can stay in fallback mode using TLS1.0.

Recommended Actions

  1. Please determine why the server does not send an SSL alert for an "unsupported protocol version". 
  2. As a workaround to restore the state of the member, remove it, and add it back to the pool.

Additional Information

This issue is a different behavior, compared with BugID739963.

Due to BugID1987309 monitor may stuck in legacy mode.
