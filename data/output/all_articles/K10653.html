Known Issue

This is the result of a known issue. Server-side iRule events associated with the virtual server that created the OneConnect connection may be executed instead of the events that are associated with the current virtual server, when a OneConnect connection is reused for a different virtual server. This issue occurs when all of the following conditions are true:

  • The same OneConnect profile is assigned to multiple virtual servers
  • The virtual servers have different iRules applied
  • The virtual servers use the same pool
  • A server-side connection is reused for a client connection made to a different virtual server

When a server-side connection becomes idle in the OneConnect connection pool, it retains a pointer to the virtual server that initiated the server-side connection. If the connection is then used to serve another request from a different virtual server, the BIG-IP system does not update the pointer to reference the new virtual server. As a result, server side events from the iRule that is applied to the first virtual server are executed on traffic on the second virtual server.

F5 Product Development tracked this issue as CR127411 and it was fixed in BIG-IP version 10.1.0. For information about upgrading, refer to the BIG-IP LTM, ASM, Link Controller, WebAccelerator, or WOM release notes.

Affected iRule events include the following:

  •  HTTP_REQUEST_SEND
  •  HTTP_RESPONSE
  •  HTTP_RESPONSE_DATA
  •  HTTP_RESPONSE_CONTINUE
  •  SERVERSSL_DATA
  •  SERVERSSL_HANDSHAKE
  •  STREAM_MATCHED
  •  SERVER_CONNECTED
  •  SERVER_DATA
  •  SERVER_CLOSED
  •  RTSP_RESPONSE
  •  RTSP_RESPONSE_DATA
  •  SIP_REQUEST_SEND
  •  SIP_RESPONSE

Note: For a complete list of iRule events, refer to the DevCentral iRules wiki Master List of iRules Events. A separate DevCentral login is required to access this content; you will be redirected to authenticate or register (if necessary).

For example, this issue would occur under the following conditions:

  • Virtual1 uses Rule1
  • Virtual2 uses Rule2
  • Both Virtual1 and Virtual2 utilize the pool named mypool
  • Both Virtual1 and Virtual2 utilize the OneConnect profile named myoneconnect
  • Both Rule1 and Rule2 have code for the HTTP_RESPONSE event, but the code is different

Under these conditions, the following sequence of events may be observed:

  • A request arrives on Virtual1
  • A OneConnect connection is made to a pool member in mypool
  • The HTTP_RESPONSE from Rule1 is executed when the initial server reponse is returned to the client
  • A request arrives on Virtual2
  • The BIG-IP selects the mypool pool 
  • A OneConnect connection established by the first request is reused
  • The HTTP_RESPONSE from Rule1 is executed when the server responds
  • The HTTP_RESPONSE from Rule2 is not executed when the server responds

Note: iRule variables and connection data are not shared; only the incorrect code is executed.

Note: Client side events are not affected by this issue.

Workaround

You can work around this issue by creating and applying unique OneConnect profiles to virtual servers that share a common pool, but have different iRules applied. To do so, perform the following procedure:

Note: Using multiple OneConnect profiles to serve the same pool may increase the number of connections to your pool members.

  1. Log in to the Configuration utility.
  2. Browse to Local Traffic > Profiles > Other OneConnect.
  3. Click the Create button.
  4. Enter a unique name for the profile.
  5. Enter OneConnect profile details matching those of the originally applied OneConnect profile.
  6. Browse to Local Traffic > Virtual Servers.
  7. Select an affected virtual server from the list.
  8. Change the OneConnect Profile setting to use the new profile.
  9. Repeat this procedure for each affected virtual server.
