Topic

When a BIG-IP system fails over, the newly active unit sends out gratuitous Address Resolution Protocols (ARP) for all floating self IP addresses and virtual server IP addresses to update the ARP cache of devices on the network. This practice ensures that all established traffic is transitioned to the newly active unit as quickly as possible. For more information on the gratuitous ARP rate, refer to K91071055: The BIG-IP system now sends gratuitous ARPs as quickly as possible.

Description

Under a few conditions, network devices may not fully update their ARP cache when a failover event occurs. For example, if the configuration of the BIG-IP system is very large, the number of gratuitous ARP packets may be of such a volume that the receiving network devices are able to accept only a limited number of the gratuitous ARP packets.

Conversely, some network devices may require more gratuitous ARP packets in a shorter period. In either case, when the ARP cache of a network device is not updated in a timely fashion and with the complete set of information, established connections may fail. If you think it's necessary, you can modify the BIG-IP system's gratuitous ARP behavior using the arp.gratuitousrate and arp.gratuitousburst database variables or keys.

Note: Prior to BIG-IP 12.0.0, the Traffic Management Microkernel (TMM) 0 is responsible for proxying all ARP requests. Beginning in BIG-IP 12.0.0, gratuitous ARP requests are handled across all TMMs on a system, based on the BIG-IP distributed hash. For more information, refer to K62135790: ARP handling on CMP-enabled BIG-IP systems.

The arp.gratuitousrate database key

In BIG-IP 10.2.0 introduces the arp.gratuitousrate database key to control the number of gratuitous ARPs per second that the BIG-IP system sends out. Additionally, the gratuitous ARPs that the BIG-IP system is allowed to send out each second is spread out evenly.

By default, the arp.gratuitousrate database variable is set to 0, which means that there is no limit to the number of gratuitous ARPs that the BIG-IP system can send out per second. If the arp.gratuitousrate database variable is set to values in the order of several thousands, the behavior is similar to 0 (unlimited).

Modifying the arp.gratuitousrate database variable using tmsh

  1. Log in to the TMOS Shell (tmsh) by entering the following command:

    tmsh

  2. Modify the value of the arp.gratuitousrate database variable by using the following command syntax:

    modify sys db arp.gratuitousrate value <new value>

    For example, to configure the BIG-IP system to send a maximum of 50 gratuitous ARPs per second, enter the following command:

    modify sys db arp.gratuitousrate value 50

  3. Save the change by entering the following command:

    save /sys config

The arp.gratuitousburst database key

The arp.gratuitousburst database key is introduced in BIG-IP 11.5.3 HF2 to control the initial number, or burst, of gratuitous ARPs that the BIG-IP system sends out. This database key also works in conjunction with the arp.gratuitousrate database key.

When the arp.gratuitousrate database key is not the default setting of 0, the BIG-IP system immediately sends, or bursts, the number of gratuitous ARPs configured using the arp.gratuitousburst database key. The default setting is 1. After the initial burst, the gratuitous ARP send rate goes back to the value set by arp.gratuitousrate. If the arp.gratuitousburst database variable is set to 0, the initial burst number of the gratuitous ARP request is set to 25% of arp.gratuitousrate.

Modifying the ARP.GratuitousRate database variable value using tmsh

  1. Log in to tmsh by entering the following command:

    tmsh

  2. Modify the value of the arp.gratuitousburst database variable by using the following command syntax:

    modify sys db arp.gratuitousburst value <new value>

    For example, to configure the BIG-IP system to send three gratuitous ARPs in a single burst, enter the following command:

    modify sys db arp.gratuitousburst value 3

  3. Save the change by entering the following command:

    save /sys config

The following table shows several example configurations of the arp.gratuitousrate and arp.gratuitousburst database keys and the resulting BIG-IP system's gratuitous ARPs behavior. For more information, refer to K62135790: ARP handling on CMP-enabled BIG-IP systems.
 

SettingsResult
(Default)
arp.gratuitousrate = 0
arp.gratuitousburst = 1		The BIG-IP system sends gratuitous ARPs out as fast as possible to minimize failover time until all gratuitous ARPs are sent.
arp.gratuitousrate = 10
arp.gratuitousburst = 10		The BIG-IP system sends 10 gratuitous ARPs in the first second, followed by 10 more every second until all gratuitous ARPs are sent.
arp.gratuitousrate = 10

arp.gratuitousrate = 10

Note: The gratuitous ARP is sent up to five times for each floating self IP, SNAT translation IP, and virtual server IP address.

Recommendations

When you modify either the arp.gratuitousrate or arp.gratuitousburst database keys, you should consider the following factors:

  • You can adjust the value of the variable so that the BIG-IP system is consistent with the configuration of your other network devices. For example:
    • In versions prior to BIG-IP 12.0.0, if the arp.gratuitousrate database variable is set to 5, TMM0 acts as a proxy to all ARP traffic and sends out only five gratuitous ARPs per second, approximately 200 milliseconds apart. If, upon failover, the BIG-IP system sends out 20 gratuitous ARPs, sending all the ARPs takes four seconds.
    • Beginning in BIG-IP 12.0.0, ARP traffic is handled across all TMMs and the setting of the arp.gratuitousrate database variable sets the value for each TMM. If the arp.gratuitousrate database variable is set to 5 for a system with two TMMs (TMM0, TMM1), each TMM sends out only five gratuitous ARPs per second, approximately 200 milliseconds apart. If, upon failover, the BIG-IP system sends out 20 gratuitous ARPs, sending all the ARPs takes two seconds.
  • If the arp.gratuitousrate database variable is modified from its default value, the newly active unit may take longer to advertise all of the floating and virtual addresses when a failover occurs. Ensure that the arp.gratuitousrate database variable is set to a value that allows all floating and virtual address advertising in a matter of a few seconds.
  • To limit the number of gratuitous ARPs sent during failover, consider configuring MAC masquerade.
