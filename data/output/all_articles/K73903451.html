Description

Occasionally, you notice an infinite loop when accessing a page, for example, www.example.com, then you are redirected to example.com (by an iRule on the Virtual Server, see example below), and then back to www.example.com and so on, until you receive ERR_TOO_MANY_REDIRECTS from an client's side perspective.

You can notice on a packet capture, that after a HTTP request from the client, the BIG-IP responds with a HTTP status code 302 Found and then closes the connection right away, without attempting to connect to server side first.

In this example, the irule configured on the Virtual Server to redirect to the same page, removing "www" looks similar to:

when HTTP_REQUEST {
    if { [HTTP::host] equals "www.example.com" }{
        HTTP::respond 301 Location "https://example.com[HTTP::uri]"
    }
}

Environment

  • HTTP profile with fallback-host option configured

Cause

The HTTP request with status code 302 Found seen, is sent by the BIG-IP when triggering the fallback-host option configured on the HTTP profile. In this case, the fallback-host option is wrongly configured to use the same host that is used to access the Virtulal Server, causing a loop if the backend servers are flapping. When the BIG-IP detects the backend server is flapping or unreachable, the fallback-host activates, redirecting to https://www.example.com again, instead of https://example.com as the iRule intended.

ltm profile http /Common/http_profile {
    defaults-from /Common/http
    enforcement {
        known-methods { CONNECT DELETE GET HEAD LOCK OPTIONS POST PROPFIND PUT TRACE UNLOCK }
        max-header-count 64
        max-header-size 32768
        max-requests 0
        pipeline allow
        truncated-redirects disabled
        unknown-method allow
    }
    fallback-host https://www.example.com → Note: this is the same link used to access the VS, causing the infinite loop
    fallback-status-codes none
    header-erase none
    header-insert none

The fallback-host should be another host that works as back up when the original servers are down, not the same Virtual Server link.

Recommended Actions

The real solution is checking why the backend servers and monitors are going down intermittently. However, to avoid the loop you can simply configure the fallback-host on the HTTP profile to use another backup link different to the original link used to access the Virtual Server.
