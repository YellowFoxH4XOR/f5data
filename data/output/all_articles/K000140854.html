K000140854: After upgrading AFM to 17.1.0 or later, sometimes client RST packet is not forwarded to server through fastL4 virtual server.

Type
Support Solution
Published
2024-08-27
Updated
2025-04-10
Applies to
  • BIG-IP
  • BIG-IP AFM: 17.1.2, 17.1.X, 17.1.1, 17.1.0
Source
https://my.f5.com/manage/s/article/K000140854

Description

Under specific condition, when client sends RST packet to server through fastL4 virtual server, the RST packet does not reach to backend (pool member) server.

While running tcpdump on BIG-IP 0.0 interface (TMM), outgoing RST packet is certainly captured. However, while running tcpdump on (egress) physical interface, no outgoing RST packet is captured. This indicates outgoing RST packet is internally dropped somewhere between TMM/CPU and physical interface.

Here are example of packet captures which were simultaneously taken on 0.0 interface and physical interface (1.1). Packet capture taken on physical interface 1.1 lacks of outgoing RST packet to pool member 192.168.10.71.

 

Figure: packet capture taken on 0.0 interface

 

Figure: packet capture taken on physical interface 1.1

 

Here is test configuration used to demonstrate the issue.

ltm virtual fastl4_vs {
    destination 10.1.1.141:http
    ip-protocol tcp
    mask 255.255.255.255
    pool http_pool
    profiles {
        fastL4 { }
    }
    serverssl-use-sni disabled
    source 0.0.0.0/0
    translate-address enabled
    translate-port enabled
}
ltm pool http_pool {
    members {
        192.168.10.71:http {
            address 192.168.10.71
            session monitor-enabled
            state up
        }
    }
    monitor gateway_icmp
}

 

When client's RST does not reach to backend server, backend server may hold the TCP connection open and stale connections may accumulate on backend server. As a result, backend server performance may be affected (due to too many open connections).

 

Environment

All of the following conditions are required for this problem to occur.

  • AFM is provisioned.
  • Version 17.1.0 or later ("TCP ACK Flood" attack vector was newly added in 17.1.0. Refer to K41305885).
  • FastL4 ePVA accelerated connection. Either "Forwarding (IP)" type virtual server or "Performance (Layer 4)" type virtual server.
  • Client sends TCP RST packet to backend server (pool member) through BIG-IP virtual server.
  • TCP timestamp option is disabled on client. That means, client's initial SYN does not have TCP timestamp option.
  • Under "Security"=>"DoS Protection"=>"Device DoS Protection", "TCP ACK Flood" attack vector state is NOT set to "Disabled" state. That means, state is either "Learn Only" or "Detect Only" or "Mitigate" (default).

 

Figure: AFM "TCP ACK Flood" attack vector configuration screen under Device DoS Protection

 

Cause

Bug ID1623277.

 

Recommended Actions

It is possible to mitigate the issue by any one of these two workarounds.

  • Disable ePVA acceleration on fastL4 profile.
  • Set "TCP ACK Flood" state to "Disabled" on "Device DoS Protection".
