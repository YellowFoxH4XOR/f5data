Description

This issue can manifest in a few ways:

  • Virtual-address route-advertisement setting changes to disabled after config load, or after re-license
  • Virtual-address route-advertisement setting changes from enabled to selective in the tmsh running config
  • Virtual-address route-advertisement setting is different in the bigip.conf -vs- tmsh running config
Note: Command to check the tmsh running config virtual-address route-advertisement:
tmsh list ltm virtual-address route-advertisement

Environment

  • Virtual-address route-advertisement configured
  • System was upgraded from 11.x/12.x and is now on 13.x or higher

Cause

This is a result of F5 Bug ID 858701 but the symptoms and impact can occur even on versions where it is marked fixed.

Recommended Actions

  • Procedure to identify systems at risk
  • Procedure to clean the legacy ROUTE_ADVERTISEMENT setting mitigating the risk of unintentional changes to the virtual-address route-advertisement setting

Systems running 13.x or higher can be identified at risk if ROUTE_ADVERTISEMENT=true in mcpd. 

Note: legacy 11.x/12.x mcpd virtual-address route-advertisement value ROUTE_ADVERTISEMENT { true, false }
Note: 13+ mcpd virtual-address route-advertisement value RA_OPTION {  0, 1, 2, 3, 4, 5 } where 0=DISABLED, 1=ENABLED, 2=SELECTIVE, 3=ALWAYS, 4=ANY, 5=ALL

Procedure to identify systems at risk

Virtual-addresses may be at risk of unintended changes to virtual-address route-advertisement on versions 13.0.0 and up if ROUTE_ADVERTISEMENT=true in mcpd.

This value can be checked with the guishell command:

guishell -c "select NAME,ROUTE_ADVERTISEMENT,RA_OPTION from virtual_address";

Example:

guishell -c "select NAME,ROUTE_ADVERTISEMENT,RA_OPTION from virtual_address";

-----------------------------------------------------------
|                  NAME | ROUTE_ADVERTISEMENT | RA_OPTION |
-----------------------------------------------------------
|  /Common/10.32.101.41 |               false |         0 |  <<<  no risk, virtual-address created in 13.1.3.2 with route-advertisement disabled
|  /Common/10.32.101.42 |               false |         2 |  <<<  no risk, virtual-address created in 13.1.3.2 with route-advertisement selective
|  /Common/10.32.101.43 |               false |         1 |  <<<  no risk, virtual-address created in 13.1.3.2 with route-advertisement enabled
|  /Common/10.32.101.47 |                true |         0 |  <<< MEDIUM RISK virtual-address from a 12.1.3 upgrade or 12.1.3 ucs with route-advertisement not in use
|  /Common/10.32.101.49 |                true |         1 |  <<< HIGH RISK virtual-address from a 12.1.3 upgrade or 12.1.3 ucs with route-advertisement enabled

Any virtual address that shows ROUTE_ADVERTISEMENT=true is as risk.  If true but route-advertisement not in use then no risk unless later it is enabled.

Procedure to clean the legacy ROUTE_ADVERTISEMENT setting mitigating the risk of unintentional changes to the virtual-address route-advertisement setting
  1. Fail over the system to a standby status:
    tmsh run sys failover standby
     
  2. Save the config to disk:
    tmsh save sys config
     
  3. Load the config from disk. This may temporarily cause route-advertisement to revert to disabled on at risk virtual-addresses:
    tmsh load sys config
     
  4. Load the config a 2nd time.  This will remove the legacy artifact, re-enable route-advertisement as per the configuration, and will leave the system in a no longer at risk state:
    tmsh load sys config

  5. Verify it worked:

    guishell -c "select NAME,ROUTE_ADVERTISEMENT,RA_OPTION from virtual_address";

    Example of a fixed config:

    guishell -c "select NAME,ROUTE_ADVERTISEMENT,RA_OPTION from virtual_address";
    -----------------------------------------------------------
    |                  NAME | ROUTE_ADVERTISEMENT | RA_OPTION |
    -----------------------------------------------------------
    |  /Common/10.32.101.41 |               false |         0 |  <<<  no risk, virtual-address created in 13.1.3.2 with route-advertisement disabled
    |  /Common/10.32.101.42 |               false |         2 |  <<<  no risk, virtual-address created in 13.1.3.2 with route-advertisement selective
    |  /Common/10.32.101.43 |               false |         1 |  <<<  no risk, virtual-address created in 13.1.3.2 with route-advertisement enabled
    |  /Common/10.32.101.47 |               false |         0 |  <<<  no risk, virtual-address from a 12.1.3 upgrade or 12.1.3 ucs with route-advertisement not in use
    |  /Common/10.32.101.49 |               false |         1 |  <<<  no risk, virtual-address from a 12.1.3 upgrade or 12.1.3 ucs with route-advertisement enabled

Additional Information

BIG-IP upgraded from 11.x/12.x can carry forward a legacy artifact in the mcpd config that can cause unintended changes to the virtual-address route-advertisement setting. 

In 11.x/12.x config the virtual-address route-advertisement allowed only 2 settings: enabled, disabled

Starting in 13.0.0 the config for virtual-address route-advertisement now allows 6 settings: disabled, enabled, selective, always, any, all

The core issue is this legacy setting in mcpd can cause unintentional virtual-address route-advertisement settings when mcpd re-parses running config (happens at config load but also happens when re-license).
