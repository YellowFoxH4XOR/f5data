Injection

Injection attacks are very common in web applications and APIs. They occur when attackers send malicious data to an app or API that has an interpreter/parser processing the data and passing the malicious data on to the backend integrated service such as a database management system (DBMS). The attack assumption is that the interpreter/parser does not filter, validate, or sanitize, or perhaps lacks these capabilities and seeks to exploit the backend systems leading to unintended information disclosures, data loss, denial-of-service (DoS), remote code execution (RCE), or potentially complete host takeover. Though structured query language (SQL) is a common injection vector, other interpreters/parsers such as lightweight directory access protocol (LDAP), NoSQL, extensible markup language (XML), and object-relational mapping (ORM) are also known to be susceptible to injection attacks.

Injection common weakness enumeration (CWE)

The following common weaknesses may increase the likelihood of attacks against your APIs:

  • CWE-77: Improper Neutralization of Special Elements used in a Command (Command Injection)
  • CWE-89: Improper Neutralization of Special Elements used in an SQL Command (SQL Injection)

Injection attack scenario

Common injection attack scenarios usually involve an attacker appending additional syntax to a parameter in a GET or POST request which the interpreter/parser does not filter, validate, or sanitize. For example, a typical SQL injection attack appends the ‘ OR 1=1 syntax to an existing account ID parameter in a GET or POST request to the API. The additional syntax, when passed on unfiltered to the DBMS, causes the DBMS to evaluate the query as true regardless of whether the preceding ID matches any existing records. As a result, the DBMS returns all rows in the table, instead of just the row that matches the ID, and the data is returned through the API back to the attacker.

Secure your API against injection attacks

Best practices recommend that you perform data validation, sanitization, and filtering on all client-provided data, where special characters should be escaped using the specific syntax for the target interpreter/parser. In addition, you should always limit the number of returned records to minimize the information disclosure risk should this situation ever occur. Most traditional web application firewalls (WAFs) and API gateways may be able to identify common injection attacks and protect from these attacks using signatures.

Use NGINX Plus, NGINX OSS, or NGINX Ingress Controller to mitigate injection attacks

You can use NGINX Plus, NGINX OSS or NGINX Ingress Controller to mitigate injection attacks, such as SQL injection attacks, for a Kubernetes cluster.

Table 8.3 NGINX Plus, NGINX OSS, and NGINX Ingress Controller controls that mitigate injection attacks

NGINX productRecommendationsResource
NGINX Plus, NGINX OSSYou can deploy an NGINX Plus or NGINX OSS instance as a sidecar proxy in a Kubernetes cluster for an existing app using a configuration stanza in nginx.conf, similar to the following example, to block off potential SQL directives:

location ~* "(\'|\")(.*)(drop|insert|md5|select|union)" {
  deny all;
}

location / {
  proxy_pass http://localhost:80/;
}

NGINX Ingress ControllerYou can define an Ingress manifest to include the configuration similar to the following example to block off potential SQL directives:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: entry
  annotations:
    nginx.org/server-snippets: |
      location ~* "(\'|\")(.*)(drop|insert|md5|select|union)" {
          deny all;
      }
spec:
  ingressClassName: nginx
  rules:
    - host: "example.com"
      http:
        paths:
          - backend:
              service:
                name: app-without-sidecar
                port:
                  number: 80
            path: /
            pathType: Prefix
