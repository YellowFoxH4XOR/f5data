Secure against the OWASP Top 10 for 2017

About the OWASP Top 10 2017

The Open Web Application Security Project (OWASP) Top 10 defines the most serious web application security risks, and it is a baseline standard for application security. For more information refer to OWASP Top Ten Project.

This guide provides information that enables you to secure your applications against the OWASP Top 10 2017 risks.

  • Injection attacks (A1)
  • Broken authentication (A2)
  • Sensitive data exposure (A3)
  • XML external entity attacks (A4)
  • Broken access control (A5)
  • Security misconfiguration attacks (A6)
  • Cross-site scripting (A7)
  • Insecure deserialization (A8)
  • Using components with known vulnerabilities (A9)
  • Insufficient logging and monitoring (A10)

Injection attacks

The OWASP Top 10 Project describes the top 10 security risks against web applications. Because they are so prevalent, injection flaws are listed as the number one security risk.

An injection attack occurs when the following occurs:

  1. An attacker injects a command, query, or code into a vulnerable element of the application.
  2. The web application server executes the injection.
  3. The attacker gains unauthorized access, causes a denial of service, steals sensitive data, or causes a similarly nefarious outcome.

Common application technologies that are victims of an injection attack are: SQL, NoSQL, Lightweight Directory Access Protocol (LDAP), XPath, operating system commands, XML parsers, and SMTP headers.

Attackers typically exploit injection flaws by injecting an operating system command, SQL query, or even a full script into a parameter, header, URL, other form of data that an application receives.

SQL injection is a very common method of injection attack. To perform SQL injection, an attacker modifies part of a query string sent to a SQL database to perform a malicious action, such as listing all usernames and passwords. For an example of a SQL injection attack, refer to SQL Injection.

While it is the role of application developers to validate and sanitize data coming into their systems, the BIG-IP ASM system can help protect your web application from injection attacks.

Secure against injection attacks with the BIG-IP system

The BIG-IP ASM system provides the following controls to mitigate and protect your application against injection attacks.

Attack signatures

The BIG-IP ASM system provides attack signatures sets that detect client requests or server responses that contain patterns of command execution and code injection attacks. Additionally, you can create custom signatures, if needed, that are specific to your application. If a request or response contains an attack, it triggers a specific attack signature set violation. The following are examples of signatures that defend against injection attacks:

  • The attack signature, SQL-INJ "*_user()" sql functions, from the Generic Detection Signatures set
  • The attack signature, "nc" execution attempt, from the OS Command Injection Signature set

Meta character restrictions

With the BIG-IP ASM system, you can configure the character sets you want to allow in XML and JSON parameters, URLs, headers, and content profiles. The BIG-IP ASM system ensures that these entities and the content within requests only contain characters allowed in your security policy. When a disallowed character appears in a request, it triggers the Illegal meta character violation. For example, if an attacker inserts <script> (malicious JavaScript)</script> within a parameter value, and, in your security policy, you include angle brackets (< >) as disallowed characters in a value, the BIG-IP ASM system blocks the request.

Enforce meta characters in parameters

To enable meta character checking on parameters or to override an illegal meta character, perform the following procedure:

Impact of procedures: Performing the following procedures should not have a negative impact on your system.

  1. Go to Security > Application Security > Parameters > Parameters List.
  2. Verify that the policy you want to edit displays in the list below the tabs. If not, select the correct policy in the list.
  3. Select the parameter name.
  4. To check meta characters on parameter values, do the following:
    1. Under Edit Parameter, select the Value Meta Characters tab.
    2. Select Check characters on this parameter value.
    3. (Optional) In the Global Security Policy Settings list, select the characters you want to allow for this parameter value and move them to the left.
    4. Select Update.
  5. For wildcard parameters, to check meta characters on the parameter name, do the following:
    1. Under Edit Parameter, select the Name Meta Characters tab.
    2. Select Check characters on this parameter value.
    3. (Optional) In the Global Security Policy Settings list, select the characters you want to allow for this parameter value and move them to the left.
    4. Select Update.

Parameter restrictions

When you add a parameter to your BIG-IP ASM security policy, you can enable multiple checks that defend it against injection attacks. For example, when you enable known acceptable parameters, any unknown parameter triggers the Illegal parameter violation and is not allowed.

Additionally, you can block other injection attacks by enabling the following checks:

  • Not allow repeated occurrences triggers the Illegal repeated parameter name violation.
  • Enforce a maximum length (a minimum length in BIG-IP 15.0.0 and later) triggers the Illegal parameter value length violation.
  • Enforce a specific data type triggers the Illegal parameter data type violation.

Broken authentication

The OWASP defines broken authentication as incorrect implementation of application functions related to authentication and session management. Using broken authentication, attackers can compromise passwords, keys, or session tokens, or exploit other implementation flaws to assume other users' identities, either temporarily or permanently.

The BIG-IP ASM and BIG-IP APM systems provide control mechanisms to mitigate and protect against attacks that attempt to exploit broken authentication.

Attackers use a range of techniques to exploit broken authentication, including the following:

  • Brute force/credential stuffing
  • Session hijacking
  • Session fixation
  • Cross Site Request Forgery (CSRF)
  • Execution After Redirect (EAR)
  • One-select attack

Secure against broken authentication with the BIG-IP system

The BIG-IP ASM and APM systems help defend against broken authentication attacks. You can configure the following:

  • The BIG-IP APM system to enforce or enhance access to your application and resources.
  • The BIG-IP ASM system to secure your application against malicious traffic.

Sensitive data exposure attacks

Attackers often target sensitive data, such as passwords, credit card numbers, and personal information, when you do not properly protect them. According to the OWASP, sensitive data exposure is the most common attack and has the most impact.

A sensitive data exposure flaw can occur when you do the following:

  • Store or transit data in clear text (most common).
  • Protect data with an old or weak encryption.
  • Fail to properly filter or mask data in transit.

Secure sensitive data with the BIG-IP system

The BIG-IP LTM and BIG-IP ASM systems provide security mechanisms to protect against sensitive data exposure attacks.

Attackers commonly target unencrypted or poorly protected data. They attack sensitive data that is at rest or in transit. The BIG-IP system and modules provide the following features and mechanisms to help protect against this type of attack.

BIG-IP system (all supported modules and versions)

Secure Vault

The BIG-IP system applies an additional layer of protection by encrypting passwords and passphrases that it stores in the configuration. The BIG-IP system Secure Vault feature uses the following two cryptographic keys to protect data while it is at rest:

  • The master key is a symmetric AES128CBC key that performs password and passphrase encryption and decryption.
  • The unit key is a is a symmetric AES256CBC key that performs master key encryption and decryption.

For more information about BIG-IP Secure Vault, refer to K73034260: Overview of the BIG-IP system Secure Vault feature.

BIG-IP LTM system

SSL profiles

The BIG-IP LTM system encrypts data in transit by applying SSL profiles on client- and server-side streams.

When you have a BIG-IP LTM full-proxy architecture and you want a high level of security, you can implement SSL bridging. With SSL bridging, you configure both client and server SSL profiles in the virtual server settings, so the system re-encrypts data before it leaves the BIG-IP system.

Furthermore, you can enhance SSL transactions by fine-tuning cipher strings in your SSL profiles to ensure the system uses an encryption algorithm supported by perfect forward secrecy (PFS) during SSL/TLS negotiation, such as Elliptic Curve Diffie-Hellman Exchange (ECDHE).

HTTP Strict Transport Security (HSTS)

HSTS is an HTTP security enhancement defined in Request for Comments (RFC) 6797. When you implement HSTS, it forces all communications through HTTPS to ensure all web browsing is secure. HSTS is one of the directives that OWASP suggests to prevent sensitive data exposure.

You can enable HSTS on your BIG-IP system by modifying the HTTP profile. To do so, perform the following procedure (BIG-IP 12.0.0 and later):

Impact of procedures: Performing the following procedures changes the HTTP traffic flow by inserting additional HTTP headers and enforcing HTTPS redirection. The procedure may break the traffic flow if HSTS/HTTPS is not fully supported in any traffic path.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Profiles > Services > HTTP.
  3. Select the name of the HTTP profile you want.
  4. Under HTTP Strict Transport Security, select the Mode check box.
  5. Select Update.

Important: F5 recommends that you consult with your security team before implementing HSTS to ensure that it aligns with your information security policy guidelines.

XXE attacks

According to the OWASP, an XXE attack is an attack against an application that parses XML input. The attack occurs when a weakly configured XML parser processes XML input containing a reference to an external entity. XXE attacks exploit Document Type Definitions (DTDs), which are considered obsolete; however, they are still enabled in many XML parsers.

The BIG-IP ASM system provides control mechanisms to mitigate and protect against XXE attacks.

Successful XXE exploits can result in the following:

  • Data disclosure and services access
  • Denial-of-service (DoS)
  • Port scanning
  • Remote code execution

Secure against XXE attacks with the BIG-IP system

The best protection against XXE attacks is to disallow DTDs. However, if your application requires DTDs, you can do the following to mitigate and protect against XXE attacks:

Disallow DTDs

On the BIG-IP ASM system, you can configure the XML profile to disallow references to DTDs in the XML document part of a request. To do so perform the following procedure:

Impact of procedures: Performing the following procedures should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Content Profiles > XML Profiles.
  3. For Current edited policy list (upper left), select the name of the policy you want.
  4. Select the name of the XML profile you want.
  5. Under Profile Properties, select the XML Firewall Configuration tab.
  6. For Defense Configuration, select Advanced.
  7. Clear the Allow DTDs check box.
  8. Select Update.
  9. Select Apply Policy.

Note: If you upload a .Web Services Description Language (WSDL) file and there are valid Simple Object Access Protocol (SOAP) methods, this setting is inactive and disabled. The system does not validate DTDs.

Access control, also called authorization, allows or denies access to your application's features and resources. Misuse of access control enables the following:

Security misconfiguration attacks

Security misconfiguration vulnerabilities occur when a web application component is susceptible to attack due to a misconfiguration or insecure configuration option. The BIG-IP ASM system provides security mechanisms to mitigate and protect against attacks that attempt to exploit misconfiguration vulnerabilities.

Misconfiguration vulnerabilities are configuration weaknesses that may exist in software components or subsystems. For example, web server software may ship with default user accounts that an attacker can use to access the system, or the software may contain sample files, such as configuration files, and scripts that an attacker can exploit. In addition, software may have unneeded services enabled, such as remote administration functionality.

Misconfiguration vulnerabilities make your application susceptible to attacks that target any part of the application stack. For example, the following attack types may target misconfiguration vulnerabilities:

  • Brute force/credential stuffing
  • Code injection
  • Buffer overflow
  • Command injection
  • Cross-site scripting (XSS)
  • Forceful browsing

XSS

Cross-site scripting (XSS or CSS) occurs when a web application receives untrusted data and then sends that data, without validation, to an end user's web browser. This transaction enables an attacker to send executable code to the victim’s browser and, ultimately, manipulate the end user's session by doing one of the following:

  • Session hijacking
  • Defacing the website
  • Redirecting the user to a site with malicious intent (most common)

Secure against XSS with the BIG-IP ASM system

You can manually configure the BIG-IP ASM system to include XSS protection as part of a security policy.

Important: You can use Policy Builder to automatically build security policies based on its analysis of traffic. To do so, you set the Learning mode to Automatic when you create the policy. However, you cannot perform the following procedures using a security policy with the Learning mode set to Automatic; you must set the Learning mode to Manual (except for modifying the system variable for HTTPOnly cookie attribute).

The system protects against XSS by doing the following:

  • Validating cookies
  • Validating user input
  • Examining input for evasion techniques, such as multiple encoded strings
  • Verifying that parameter characters are used properly
  • Processing input against known and custom attack patterns (attack signatures) that you configure for your specific environment
  • Logging and blocking requests that trigger violations

Important: Use the Fundamental or Comprehensive template to create a security policy that protects against XSS because those templates cover the required configuration objects.

Configure an existing security policy with XSS attack signature detection

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

When you set the Enforcement mode for the security policy and Cross Site Scripting Signatures to Block, the system blocks requests containing XSS.

  1. Log in to the Configuration utility.

  3. For Enforcement Mode select View Learning and Blocking Settings.
  4. Under Policy Building Settings, expand Attack Signatures.

    • The items refer to the objects you use in your environment, such as the operating system, application code, and web server types.
    • Cross Site Scripting Signatures displays in a row. If it doesn't, do the following:

Insecure deserialization

Serialization occurs when an application converts data structures and objects into a different format, such as binary or structured text like XML and JSON, so that it is suitable for other purposes, including the following:

  • Data storage
  • Messaging
  • Remote procedure call (RPC)/inter-process communication (IPC)
  • Caching
  • HTTP cookies
  • HTML form parameters
  • API authentication tokens

Deserialization is when an application reverts the serialized output into its original form.

To exploit insecure deserialization, attackers typically tamper with the data in data structures or objects that modify an object's content or change an application's logic. When attackers are successful, their exploits can lead to denial-of-service (DoS) attacks, authentication bypasses, and remote code execution attacks.

Secure against insecure deserialization with the BIG-IP ASM system

The BIG-IP ASM system provides the following controls to mitigate and protect your application against insecure deserialization attacks.

JSON validation

The BIG-IP ASM JSON profile allows you to define what is considered legitimate JSON data. With the JSON profile, you can detect malformed JSON data, parse parameters in a JSON payload as parameters, or manually override Attack Signatures and Meta Characters security settings. You can associate a JSON profile with a URL or with a parameter.

For information on how to configure a JSON profile, refer to Adding JSON Support to an Existing Security Policy chapter of the Application Security Manager: Implementations manual.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

XML validation

The BIG-IP ASM XML profile provides formatting and attack pattern checks for XML data. With the XML profile, you can configure XML validation and protection, manually override Attack Signatures and Meta Characters security settings and manage Simple Object Access Protocol (SOAP) messages. You can associate a JSON profile with a URL or parameter.

For more information on the XML profile, refer to K44151603: Overview of the BIG-IP ASM XML profile.

For information on how to enhance XML security, refer to the Fine-tuning Advanced XML Security Policy Settings chapter of the Application Security Manager: Implementations manual.

The BIG-IP ASM system allows you to customize and enforce the format and configuration of HTTP headers, including the following:

Components with known vulnerabilities

Component-based vulnerabilities occur when a web application component is unsupported, out of date, or vulnerable to a known exploit. The BIG-IP ASM system provides security features, such as attack signatures, that protect your web application against component-based vulnerability attacks.

A software component is part of a system or application that extends the functionality of the application, such as a module, software package, or API. Often, you inadvertently use vulnerable software components in production environments, posing a threat to the web application. For example, an organization may download and use a software component, such as OpenSSL, and fail to regularly update or patch the component as flaws are discovered. Since many software components run with the same privileges as the application itself, any vulnerabilities or flaws in the component can result in a threat to the web application.

Using components with known vulnerabilities makes your application susceptible to attacks that target any part of the application stack. For example, the following attack types are a few that may target known component vulnerabilities:

  • Code injection
  • Buffer overflow
  • Command injection
  • Cross-site scripting (XSS)

Insufficient logging and monitoring

Insufficient logging and monitoring is frequently a factor in major security incidents. The BIG-IP ASM system includes advanced logging and monitoring functionality and provides security features to protect against attacks that can result from insufficient application logging and monitoring.

Failure to sufficiently log, monitor, and report security events, such as login attempts, makes suspicious behavior difficult to detect and significantly raises the likelihood that an attacker can successfully exploit your application. For example, an attacker may probe your application or software components for known vulnerabilities over a period. Allowing such probes to continue undetected increases the likelihood that the attacker ultimately finds a vulnerability and successful exploits the flaw.

Insufficient logging, monitoring, and reporting make your application susceptible to attacks that target any part of the application stack. For example, the following attack types may result from a failure to log, monitor, or report security events:

  • Code injection
  • Buffer overflow
  • Command injection
  • Cross-site scripting (XSS)
  • Forceful browsing

Recommendations for mitigating insufficient logging vulnerabilities

Use the following procedures to mitigate risks related to insufficient logging and monitoring.

Configure BIG-IP ASM logging profiles

You can use BIG-IP ASM logging profiles to log requests that your application receives. The logging profile determines the type of requests the system logs—illegal or all requests—and whether the system logs the requests locally or to a remote logging server.

You can also configure multiple logging profiles and assign the profiles to a single virtual server. For example, if your company uses multiple security information and event management (SIEM) systems to collect logs, such as Splunk and ArcSight, you can set up three logging profiles as follows:

  • Local storage with illegal requests
  • Remote logging filter in Splunk format
  • Remote logging filter in Arcsight format

To configure one or more BIG-IP ASM logging profiles, perform the following steps:

  1. Log in to the Configuration utility.
  2. Go to Security > Event Logs > Logging Profiles.
  3. Select Create.
  4. For Profile Name, enter a name for the profile.
  5. For Application Security, select Enabled.
  6. On the Application Security tab, for Configuration, select Advanced.
  7. For Storage Destination, select the storage destination you want.
  8. For Response Logging, select the type of request you want.
  9. Select Create.

Associate the logging profile with a security policy

After you create the logging profiles, you can associate the profiles with the virtual server. To do so, perform the following steps:

  1. Go to Local Traffic > Virtual Servers.
  2. Select the name of the virtual server the security policy uses.
  3. Go to Security > Policies.
  4. For Application Security Policy, do the following:
    1. Select Enabled.
    2. For Policy, select the security policy you want.
  5. For Log Profile, select Enabled.
  6. In the Available list, select the profiles you want to use for the security policy, and move them left.
  7. Select Update.

Filter logging information

You can use the storage filter option of the logging profile to specify the type of requests that are included in the event logs. For example, you can configure a filter that only logs failed login attempts. To configure a logging filter, perform the following steps:

  1. Go to Security > Event Logs > Logging Profiles.
  2. Select the name of the logging profile you want.
  3. On the Application Security tab, for Storage Filter, select Advanced.
  4. Define the logging filter options as required.
  5. Select Update.

Set attack alarm and blocking logging

For some violations you may want to adjust the alarm and blocking settings so that, when a request triggers a violation, the system records the request, depending on the settings of the logging profile. To adjust the alarm and blocking settings, perform the following procedure:

  1. Go to Security > Application Security > Policy Building > Learning and Blocking Settings.
  2. For General Settings, select Advanced.
  3. Under Policy Building Settings, select the objects for which you want to log requests, and then select Alarm or Block, or both.
  4. Select Save.
  5. Select Apply Policy.

View event correlation

The Event Correlation page displays a list of incidents that are likely to be part of a suspected attack on a web application. Incidents are triggered based on single or multiple correlation heuristics applied to illegal requests. To view the Event Correlation page, perform the following steps:

  • Go to Security > Event Logs > Application > Event Correlation.

    The Event Correlation page displays. The page categorizes incidents type and subtype. Incident Type is a category of Malicious Activity, and Incident Subtype is the name of the specific attack.
