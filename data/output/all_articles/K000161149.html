K000161149: Managing Deletion and In-Place Updates of Virtual Sites (Vsites) Referenced by Load Balancers in F5 Distributed Cloud

Type
Support Solution
Published
2026-05-06
Updated
2026-06-12
Applies to
  • F5 Distributed Cloud Services
  • F5 Distributed Cloud WAF
Source
https://my.f5.com/manage/s/article/K000161149

Description

Virtual site (vsite) objects in F5 Distributed Cloud cannot be deleted or updated in place if they are referenced by other objects, such as HTTP load balancers. Attempts to delete these vsites via API or Terraform result in a 409 Conflict error, with messages indicating the vsite is still being referred to by a load balancer.

Example error message:

Error: Deleting object from api gateway: Unsuccessful DELETE at URL https://example.console.ves.volterra.io/api/public/namespaces/foo/virtual_sites/bar, status code 409, body {"code":6,"details":[{"code":"UNKNOWN","details":"DeleteResource: ves.io.schema.virtual_site.Object ... is still being referred by 1 objects - [ves.io.schema.views.http_loadbalancer.Object .../internal-load-balancer]","timestamp":"2026-04-16T14:10:46Z"}],"message":"ves.io.schema.virtual_site.Object ... is still being referred by 1 objects - [ves.io.schema.views.http_loadbalancer.Object .../internal-load-balancer]"}
,

Environment

  • F5 Distributed Cloud platform
  • Multiple vsite objects referenced by HTTP load balancer objects
  • API gateway used for object management
  • Terraform Volterra provider (version 0.11.48 and earlier affected; resolved in 0.11.49)

Cause

A change in object dependency logic enforced validation to prevent deletion of vsite objects while they are referenced by other objects (e.g., HTTP load balancers). This validation is enforced at the API level and is designed to prevent accidental deletion of resources that are still in use, ensuring proper dependency cleanup order.

Recommended Actions

  1. Upgrade the Terraform Volterra provider to version 0.11.49 or later:
    This version introduces the ability to control dependency validation during vsite deletion.
  2. Review and update dependencies:
    • Before deleting a vsite, ensure it is not referenced by any load balancer or other objects.
    • Remove the vsite from all referencing load balancers before attempting deletion, or use the new provider option below.
  3. Use the fail_if_referred parameter (API/Terraform):
    • The vsite delete API and Terraform Volterra provider (v0.11.49+) support a fail_if_referred boolean parameter.
    • Setting fail_if_referred to false allows deletion to proceed even if references exist.
    • Example (Terraform):
    resource "volterra_virtual_site" "example" {
  # ... other config ...
  lifecycle {
    prevent_destroy = false
  }
  delete_request {
    fail_if_referred = false
  }
}
    • Refer to the API documentation for details.
  4. Monitor for workflow regressions:
    If you encounter further issues with vsite deletion or updates, report them to F5 support.

Additional Information

  • The validation logic applies globally across all resources via code generation, not just vsites.
  • The default behavior is to block deletion if references exist, but this can now be overridden with the fail_if_referred parameter in provider v0.11.49+.
