Description

When connectivity through a Performance Layer4 (FastL4) virtual server appears to be failing, analyzing a TCPdump can determine if the BIG-IP is correctly forwarding traffic between the Clients and Servers.

Environment

  • A Performance Layer4 virtual server relaying traffic between Clients and Servers
    K01155812: Overview of the Performance (Layer 4) virtual server

Recommended Actions

By default, the FastL4 profile used with a Performance Layer4 virtual server uses the PVA/ePVA to accelerate traffic processing through the BIG-IP.  For all packets to be captured by tcpdump, the PVA/ePVA must be disabled using the following steps

1.A. Using the Configuration Utility

  1. Navigate to Local Traffic >> Profiles : Protocol : Fast L4 in the BIG-IP configuration utility
  2. Create a new Fast L4 profile
  3. Set the Parent Profile to the FastL4 profile applied to the virtual server
  4. Set PVA Acceleration = None
  5. Finish the new FastL4 profile

1.B. Using tmsh CLI

Use below command to create custom FastL4 profile named F5TAC-FastL4

tmsh create /ltm profile fastl4 F5TAC-FastL4 pva-acceleration none
 

2. Modify the Performance Layer4 virtual server to use the new FastL4 profile

3. Collect a tcpdump recording the communication through the Performance Layer4 virtual server:

Note:  For more information on using tcpdump, please refer to the articles in the supplemental information section below

3.1. Log into the advanced shell (bash) as the root user

3.2. Start a tcpdump similar to the following example

tcpdump -vi 0.0:nnn -s0 -w /var/tmp/<outputfile.pcap> -c <maximum packets> host <virtual_server_IP> or host <pool_member_IP>

where:

  • <outputfile.pcap> is the filename for the TCPdump
  • <maximum packets> is an optional safeguard to limit the maximum size of the packet trace file
  • <virtual_server_IP> is the virtual server's IP address
  • <pool_member_IP> is the pool member's IP address

3.3. Generate the traffic of interest through the Performance Layer4 virtual server

3.4. Stop the tcpdump with Ctrl+c

3.5. Download the tcpdump output from the /var/tmp/ folder of the BIG-IP. See K175: Transferring files to or from an F5 system

4. Analyse the tcpdump in Wireshark to look for two copies of each packet sent to the BIG-IP, the Ingress copy and the Egress copy:

  • If Source Address Translation is set to None in the Performance Layer4 virtual server, filter the packet capture in Wireshark to show only the packets for a particular Client IP:
      ip.addr == <client_IP>
      replacing <client_IP> with the Client's IP address
     
  • If Source Address Translation is not set to None in the Performance Layer4 virtual server
      1. Examine the packets from a particular Client to identify something unique to the Client that will remain unchanged when passing through the BIG-IP
      2. Instruct Wireshark to filter the capture on this unique item.

Additional Information

It is common for the egress copy to have its timestamp value a tiny fraction of a second later than the value of the ingress copy.

Note: If the traffic volume is too high for manual identification based on their timestamps alone, then additional information ("noise") appended by TMM to its frames can be also used for identifying the corresponding ingress and egress packets. Specifically:
  • Ingress
  • VIP
  • Flow ID
  • Peer ID
More details are available at K13637: Capturing internal TMM information with tcpdump


Each packet has a number of attributes with reasonably unique values, which may be preserved by the virtual server (depending on its actual configuration settings) allowing to correlate the ingress copy to its egress copy. Below is a summary of the protocol fields.

IPv4

  • ip.id
  • ip.src
  • ip.dst
  • ip.frag_offset
  • ip.checksum - requires caution as its value changes when the virtual server uses address translation

ESP

  • esp.spi - see also K79345554: Reasons why an established IPsec tunnel fails to forward packets

TCP

  • tcp.srcport
  • tcp.dstport
  • tcp.seq
  • tcp.ack
  • tcp.checksum - requires caution as its value changes when the virtual server uses address translation
  • tcp.payload

UDP

  • udp.srcport
  • udp.dstport
  • udp.checksum - requires caution as its value changes when the virtual server uses address translation

Selecting the packet protocol fields for correlation:
 

  • Source MAC xx:xx:xx:xx:xx:xx and destination MAC yy:yy:yy:yy:yy:yy:

    0000  yy:yy:yy:yy:yy:yy xx:xx:xx:xx:xx:xx .. .. .. ..

    will probably change
  • IP id 0xii'ii will probably remain unchanged
  • IP source address xx.xx.xx.xx will remain unchanged unless Source Address Translation is configured in the virtual server
  • IP destination address yy.yy.yy.yy will change unless Address Translation is disabled in the virtual server
  • TCP source port xx'xx and destination port yy'yy will likely remain unchanged unless Source Port translation is enabled in the virtual server or pool
  • TCP sequence number ss'ss'ss'ss and acknowledgment number aa'aa'aa'aa:

    0010  .. .. ii'ii .. .. .. .. .. .. xx.xx.xx.xx yy.yy
    0020 .yy.yy xx'xx yy'yy ss'ss'ss'ss aa'aa'aa'aa .. ..

    will likely remain unchanged
