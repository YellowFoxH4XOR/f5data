Topic

When a connection is placed into the BIG-IP connection table, TMM is responsible for counting how many seconds the connection has been idle. If the number of seconds the connection has been idle exceeds the idle timeout value specified in the profile handling that connection, then the connection is eligible for deletion.

TMM periodically updates its internal clock with the time reported by the Linux host. If TMM updates its internal clock with a time that is in the past, then the difference between the new present time and the last idle timestamp for a connection in the connection table becomes a negative number. An issue arises when the BIG-IP system has to compare this negative value to the idle timeout. For this reason, if the time on the Linux host is set back (for example by the NTP daemon), connections already in the connection table may either age prematurely or be removed.

Note: Leap second adjustments may also cause the system to either age connections prematurely or remove connections in the connection table.

F5 Product Development tracked a request for enhancement (RFE) as ID 221972 (formerly CR105632) to allow TMM to track time in a way that prevents this issue from occurring, and it was fixed in BIG-IP 10.2.3 and 11.0.0. For information about upgrading, refer to the BIG-IP LTM, ASM, PSM, Link Controller, WebAccelerator, WOM, or Edge Gateway release notes.

Additionally, this issue has been fixed in cumulative hotfix BIGIP-10.1.0-3402.0-HF2, which has been issued for BIG-IP 10.1.0 and Hotfix-BIGIP-10.2.2-852.0-HF1, which has been issued for BIG-IP 10.2.2. You may download these hotfixes or later versions of the hotfix from the F5 Downloads site.

Note: This issue will also affect connections that have been mirrored to a standby system in a BIG-IP redundant pair. If the time is set back on the standby system, the connections that were already mirrored may age prematurely, or even be removed completely from the connection table of the standby system. Any connections removed from the connection table of the standby system would be terminated if a failover event were to occur before the connection ended on the active system. It is possible to rebuild mirrored FastL4 and SNAT connections on the standby system by temporarily bringing down the high-availability link used for connection mirroring between the two systems, and then bringing the link back up. However, for mirrored layer 7 connections, it is not possible to rebuild the connection flow information lost when the connection was removed from the connection table on the standby system. Layer 7 connections will require a new connection to be established and mirrored from the active system to the standby system. For information about connection mirroring, refer to K7222: Overview of connection and persistence mirroring (9.x - 10.x).

Note: In some BIG-IP versions, the Linux default security level prevents administrators from setting the time or date back from what the system currently displays. For more information about changing the time or date on a BIG-IP system, refer to K3381: Setting the time and date on the BIG-IP system.

Note: As a best practice, F5 recommends that you configure a reliable NTP server before deploying a BIG-IP system into production. For more information, refer to K3122: Configuring BIG-IP to use an NTP server.
