Description

When configuring a Forwarding IP virtual server with a network address for Destination Address/Mask and a Port List, traffic stops working. It's not processed correctly by the BIG-IP.

On a packet capture you can only see SYNs from the client with no response from the BIG-IP. In the following example, the virtual server is configured with destination address: 10.10.10.0/24 and Port List including ports 80 and 81, and the client IP is 192.168.1.1:

192.168.1.1 → 10.10.10.2  TCP  52000 → 80 [SYN]
192.168.1.1 → 10.10.10.2  TCP  [TCP Retransmission] 52000 → 80 [SYN]
192.168.1.1 → 10.10.10.2  TCP  [TCP Retransmission] 52000 → 80 [SYN]

When viewing the virtual server properties on the Local Traffic > Virtual Servers > Virtual Server List page, it shows the destination address with a missing mask, as if it was a host address and not a network address.

When listing the virtual server properties with tmsh list ltm traffic-matching-criteria, or on the bigip.conf file, you can also see the network mask does not show as configured, for example:

ltm traffic-matching-criteria /Common/VS_Forwarding_TMC_OBJ {
    destination-address-inline 10.10.10.0 =======>>> Note: missing /24 mask
    destination-port-list /Common/Web_Ports
    protocol tcp
    source-address-inline 0.0.0.0

Environment

  • Forwarding IP virtual server
  • Using Port List
  • Using destination network address

Cause

Bug ID 779137: Using a source address list for a virtual server does not preserve the destination address prefix

Recommended Actions

If you are using a relatively short Port List, to avoid the issue you should consider creating separate virtual servers for each port instead. For example:

  • VS_Forwarding_80 with destination address 10.10.10.0/24 and destination port 80
  • VS_Forwarding_81 with destination address 10.10.10.0/24 and destination port 81

To workaround the issue on affected versions, and continue to use a Port List, follow these steps:

  1. List the virtual server properties to identify the traffic-matching-criteria related to the affected virtual server:

    tmsh list ltm virtual

    Example Output:

    ltm virtual VS_Forwarding {
        description VS_Forwarding
        ip-forward ip-protocol
        tcp profiles { fastL4 { } }
        source-port preserve-strict
        traffic-matching-criteria VS_Forwarding_TMC_OBJ =======>>> Related TMC
        translate-address disabled         
        translate-port disabled
        vs-index 2
        }

  2. Modify the traffic-matching-criteria identified in step 1, to include the desired network mask:

    tmsh modify ltm traffic-matching-criteria <traffic-matching-criteria-name> destination-address-inline <network address / network mask>

    For example:

    tmsh modify ltm traffic-matching-criteria VS_Forwarding_TMC_OBJ destination-address-inline 10.10.10.0/24

Now the virtual server should work as expected allowing traffic to be processed correctly. You should also see the correct network mask when viewing the virtual server properties on the Local Traffic > Virtual Servers > Virtual Server List page and when listing them with tmsh list ltm traffic-matching-criteria.

Note: Once the destination-address-inline is manually modified with the mask on step 2, if you navigate to Local Traffic > Virtual Servers > Virtual Server List, and click on the relevant virtual server, the Destination Address/Mask shows a double mask, for example: 10.10.10.0/24/24. If you modify the virtual server configuration on the GUI and try to save,  you will get another error, Invalid IP Address.
