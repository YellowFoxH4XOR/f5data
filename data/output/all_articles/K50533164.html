Description

  • Notice connectivity issues on a Virtual Server with Fast L4 profile attached, after an upgrade
  • This can happen with various protocols, such as ICMP, TCP and UDP traffic passing through the BIG-IP
  • When booting into the previous software version, behaviour corrects itself
  • When the issue happens with ICMP traffic you can notice the following:

    • ICMP packets from client to server passing through a Performance Layer 4 Virtual Server, are not successful

    • Traffic captures might show that BIG-IP is changing the ICMP ID before re-transmitting traffic. Similar to this example:

      Note: id=0x5a01 and id=0xe617

      10.10.10.1   192.168.10.1  IN  s1/tmm1 : Echo (ping) request  id=0x5a01, seq=1/256, ttl=64
      10.10.10.1   192.168.10.1  OUT s1/tmm1 : Echo (ping) request  id=0xe617, seq=1/256, ttl=63

Environment

  • Platforms VE, 2000, 4000
  • After upgrade to versions where ID726176 has been fixed:
    Bug ID 726176: Platforms using RSS hash reuse source port too rapidly when the FastL4 virtual server is set to source-port preserve
  • Source Port Preservation set to Preserve (default)

Cause

Bug ID 890229: Source port preserve setting is not honored

Recommended Actions

To confirm if your system is affected, open a case with F5 Support and reference this Support Solution.

To workaround the immediate issue, set Source Port Preservation on the Virtual Server to Preserve Strict.

Additional Information

  • This behaviour can affect other type of traffic, not only ICMP
  • With ICMP traffic, the ICMP ID shown on a traffic capture referes to the source port for this traffic. For example: id=0x5a01
