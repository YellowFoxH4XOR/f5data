Topic

This article applies to BIG-IP 11.x and later. For information about other versions, refer to the following articles:

  • K10966: Determining which monitor triggered a change in the availability of a node or pool member (9.x - 10.x)
  • K14407: The BIG-IP system now displays which monitor triggered a change in the availability of a node or pool member

You should consider using this procedure under the following conditions:

  • You have multiple monitors assigned to a pool, pool member, or node.
  • You want to know which health monitor caused a change in the availability of an object.

Description

When a health monitor is in use, the mcpd process logs a message when a pool, pool member, or node changes state, although the mcpd process does not identify which health monitor caused a change in the availability of an object. Typically, this behavior is not an issue when only one health monitor is assigned to a pool, pool member, or node. However, this behavior may be an issue in configurations in which multiple health monitors are in use, and you want to know which health monitor caused a change in the availability of an object.

The functionality to allow the BIG-IP system to log which particular health monitor caused a change in the availability of an object is added in BIG-IP 11.4.0. For more information, refer to K14407: The BIG-IP system now displays which monitor triggered a change in the availability of a node or pool member.

To work around this limitation, you can use the tmsh utility to view the current state of monitors associated with an object or you can configure a database key that enables the bigd process to log which particular health monitor has caused a change in the availability of an object. Refer to the following section for instructions.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You have multiple monitors assigned to a pool, pool member, or node.
  • You have command line access to the BIG-IP system.

Procedures

Viewing the monitor state using the tmsh utility

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

You may be able to determine which monitor caused the change in availability of an object by viewing the state of the associated monitors. The monitor state can be seen by viewing the details of the object using the tmsh utility. To do so, perform the following procedure:

  1. Log in to the Traffic Management Shell (tmsh) by entering the following command:

    tmsh

  2. Show the details of the object using the following command syntax. Specify either pool or node as the object_type.

    Note: Details for pool members are included in the output of the show /ltm pool <pool_name> detail command. You do not need to specify members as an argument.

    show /ltm <object_type> <object_name> detail

    For example, to view the details of the pool_http pool, enter the following command:

    show /ltm pool pool_http detail

  3. Locate the Monitors section in the output for the affected pool member to view the current status of the associated monitors. The output appears similar to the following example:

    --------------------------------------------------------------
    | Ltm::Pool Member: 10.10.10.11:80
    --------------------------------------------------------------
    | Monitors
    | http 10.10.10.11:80 enabled up
    | https_443 10.10.10.11:443 enabled down
    | tcp 10.10.10.11:80 enabled up

    Note: In the previous example, the status of the https_443 monitor is down, indicating the pool member is marked down by the monitor.

Enabling the bigd.lognodestatuschange database key and reviewing the /var/log/ltm file

Impact of procedure: Enabling the bigd.lognodestatuschange database key enables monitor-status logging globally. Depending on the configuration, this has the potential for more verbose logging.

You may be able to determine which health monitor has caused a change in the availability of an object by enabling the bigd.lognodestatuschange database key, which triggers the bigd process to log which particular health monitor has caused a change in the availability of an object. To enable the key and review the /var/log/ltm file, perform the following procedure:

  1. Log in to the Traffic Management Shell (tmsh) by entering the following command:

    tmsh

  2. Verify the status of the bigd.lognodestatuschange database key by entering the following command:

    list /sys db bigd.lognodestatuschange

  3. If the status is disabled, enable the bigd.lognodestatuschange database key by entering the following command:

    modify /sys db bigd.lognodestatuschange value enable

    Note: To disable the bigd.lognodestatuschange database key, enter the following command: tmsh modify /sys db bigd.lognodestatuschange value disable.

  4. To exit the tmsh utility, enter quit and press Enter.
  5. Monitor or review the /var/log/ltm file by entering one the following example commands:

    Monitor the log file: tail -f /var/log/ltm | egrep -i "detected.*mon|monitor.*status"

    Review the log file: cat /var/log/ltm | egrep -i "detected.*mon|monitor.*status" | more

  6. To break out of either command, press Ctrl+C.

    Note: Depending on the number of log messages, you may need to scroll through the output to locate the specific message.

In the following example, the pool member 10.1.2.9:80 is marked down because it fails to pass the http monitor test. The pool member then passes the http monitor test and is subsequently marked up. In the first example there is no indication of which monitor marks the node down or up. However, after enabling the bigd.lognodestatuschange database key, the bigd process logs which monitor marks the node down and subsequently back up again.

Example output taken before enabling the database key

local/bigip-1 notice mcpd[3741]: 01070638:5: Pool member 10.1.2.9:80 monitor status down.
local/bigip-1 notice mcpd[3741]: 01070727:5: Pool member 10.1.2.9:80 monitor status up.

Example output taken after enabling the key

local/bigip-1 notice bigd[3747]: 01060001:5: Service detected DOWN for ::ffff:10.1.2.9:80 monitor http.
local/bigip-1 notice mcpd[3741]: 01070638:5: Pool member 10.1.2.9:80 monitor status down.
local/bigip-1 notice bigd[3747]: 01060001:5: Service detected UP for ::ffff:10.1.2.9:80 monitor http.
local/bigip-1 notice mcpd[3741]: 01070727:5: Pool member 10.1.2.9:80 monitor status up.

Note: Enabling the bigd.lognodestatuschange database key affects a behavior change in BIG-IP 10.x and 11.x regarding the throttling of BIG-IP LTM log messages. When the key is enabled, log messages may be throttled, which is the opposite of the default behavior.
