Description

A virtual service defines routing rules to be applied when a host is addressed. There is a matching criterion for traffic which routes it further down to host via destination service defined in the registry. In this article, we investigate an example of virtual service:

  1. Below shows a configuration example of virtual service:

    apiVersion: networking.istio.io/v1alpha3 
    kind: VirtualService 
    metadata: 
      name: dummy-one 
    spec: 
      gateways: 
        - common-gateway 
        - common-gateway-nlb 
      hosts: 
        - '*' 
      http: 
        - match: 
            - uri: 
                prefix: /endpoint-update 
          route: 
            - destination: 
                host: endpointupdatesvc 
                port: 
                  number: 8080 
                subset: v1 
        - route: 
            - destination: 
                host: endpointupdatesvc 
                port: 
                  number: 8080 
                subset: v2

    The above configuration creates route in your cluster configuration. If there is a match on prefix: /endpoint-update, route it to service endpointupdatesvc with destination pods with label v1. If there is no match, route all the traffic from the host * to destination pods with label v2. 

  2. The configuration below creates routes in your cluster for host reviews.com. The traffic is split between 2 different destination services with weights attached to it:

    apiVersion: networking.istio.io/v1alpha3
    kind: VirtualService
    metadata:
      name: reviews-route-two-domains
    spec:
      hosts:
      - reviews.com
      http:
      - route:
        - destination:
            host: dev.reviews.com
          weight: 25
        - destination:
            host: reviews.com
          weight: 75

  3. If you want to verify the routes created after applying your virtual service configuration, you can use istioctl to view them. This one below shows it matches just httpbin.example.com host for /headers endpoint but for other two categories, it matches all the host, i.e., *:

    > istioctl pc route <pod-name>.<pod-namespace>.

    NAME                                                                      DOMAINS                 MATCH                  VIRTUAL SERVICE
    https.443.https-443.httpbin-gw.default     httpbin.example.com     /headers               httpbin-vs.default
                                               *                       /healthz/ready*
                                               *                       /stats/prometheus*

Environment

Aspen Mesh 1.9.x and higher.

Cause

In need of Virtual Services config verification.

Recommended Actions

This article is intended to show how routes are created for subtle changes in indentation values in virtual services. Make sure to check your routes when you set up virtual services via istioctl command line tool if the routing is not happening as expected.
