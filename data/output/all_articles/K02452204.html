Description

You added a syslog server to the BIG-IP configuration. The syslog destination is a virtual server on the BIG-IP system which load balances to a pool of remote syslog servers. You're not able to see logs leaving the system and traffic is not seen at the syslog servers either.

You tested with tcpdump using commands similar to the following:

tcpdump -s0 -ni 0.0:nnnp -v -w /var/tmp/syslog_issue.pcap host 10.1.1.1
tcpdump -i eth0 -v -w /var/tmp/syslog_issue_mgmt.pcap host 10.1.1.1

Both pcap files are empty after running for some time and you generated sample logs using a logger command similar to the following:

logger -n 10.1.1.1 -p local0.error -P 514 "Test message from the BIG-IP system"

Note: The logger utility -n option is not available in BIG-IP 13.x and earlier.

Environment

  • BIG-IP
  • Syslog destination is a virtual server on the BIG-IP system which load balances to a pool of syslog servers

  • Multiple default routes, learnt via dynamic routing (or a gateway pool):

    ----------------------------------------------------------
    Net::Routes
    Name         Destination  Type  NextHop       Origin
    ----------------------------------------------------------
    default      default      gw    10.1.2.253  dynamic ecmp
    default      default      gw    10.1.2.254  dynamic ecmp
  • No log filters in use

Cause

With multiple equal-cost multipath routes, the following route will be injected into the kernel routing table:

default via 127.1.1.253 dev tmm

This exists to ensure that traffic from the Linux host (e.g. syslog) is load balanced correctly between the two default routes, using a hidden pool.

You may see output similar to the following when using the ip route get command:

[root@ltm-1:Active:In Sync] ~ # ip route get 10.1.1.1
10.1.1.1 via 127.1.1.253 dev tmm  src 127.1.1.254
    cache

In this situation, the syslog traffic will be sourced from IP address 127.1.1.254, accessing the virtual server via the tmm device. This means traffic will egress the system towards the syslog pool using this source IP, as well (assuming no source address translation is in use).

Without special modifiers, traffic between TMM and the virtual server will not be visible in a tcpdump that is filtered on the virtual server IP address, for example when using the tcpdump command in the description of this article.

Recommended Actions

A tcpdump taken on the TMM interface using the h modifier (tmm:h) will allow you see to see traffic generated from the Linux host towards the virtual server. Similarly, capturing on 0.0 (or the egress VLAN) using the IP address or port (e.g. 514) of the pool member should capture the syslog traffic egressing the system towards the gateways.

An example of an appropriate tcpdump command:

tcpdump -s0 -ni tmm:h host 10.1.1.1 and port 514 -w /var/tmp/tmm_h_syslog.pcap

Investigate what happens to this traffic once it reaches the gateway devices. It is possible the source 127.1.1.254 causes a problem for an intermediate device between the BIG-IP and syslog server. In this situation, configuring the virtual server with source address translation will help.

Additional Information

It is also possible to see a connection established between syslog-ng and the virtual server using the netstat or ss commands, for example:

Netid  State      Recv-Q Send-Q Local Address:Port             Peer Address:Port
udp    ESTAB      0      0      127.1.1.254:55142              10.1.1.1:514                 users:(("syslog-ng",pid=6452,fd=52))
