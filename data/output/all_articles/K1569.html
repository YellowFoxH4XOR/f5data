Topic

Rule failure messages are usually benign. These messages are created when BIG-IP receives a header that it cannot parse or one that does not follow the HTTP/1.1 or HTTP/1.0 specification. This is most commonly caused by the following two reasons:

Note: If your rule contains numerous decode_uri statements, refer to K4596: Known Issue: iRules that contain a large number of decode_uri functions can fail, for more information.

  • Someone has mistakenly connected to a HTTP virtual server using encrypted HTTPS, causing content to appear completely unreadable and therefore unable to match to any rule.
  • A rule does not contain an else statement.

    For example:

    rule myrule2 {
    if (http_uri contains 'xxx')) {
    use ( web1 )
    }
    else if (http_uri contains 'yyy') {
    use ( web2 )
    }
    }

    In the preceding rule, if the http_uri does not contain 'xxx' or 'yyy', it will generate a rule failure. For this reason, it is necessary to have an absolute else (without any conditions) statement.

    For example:

    rule myrule2 {
    if (not (http_uri ends_with 'xxx')) {
    use ( web1 )
    }
    else if (http_uri ends_with 'yyy') {
    use ( ssl1 )
    }
    else {
    discard
    }
    }

    The else statement in the preceding rule could just as easily reference a pool. The important thing is that the else statement matches if nothing else does. If it doesn't, BIG-IP will generate the Rule Failure message.

    Starting in BIG-IP version 4.2, if an else statement is defined without a condition, BIG-IP discards it in order to prevent this Rule Failure message.
