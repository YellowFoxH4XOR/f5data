Description
Attack signatures are rules or patterns that identify attacks on a web application. When Application Security Manager™ (ASM) receives a client request (or a server response), the system compares the request or response against the attack signatures associated with your security policy. If a matching pattern is detected, ASM™ triggers an Attack signature detected violation, and either alarms or blocks based on the enforcement mode of your security policy.

There are instances that a custom pattern is needed to block or alarm on traffic that is considered malicious. ASM allows creation of user-defined/custom attack signatures to address this requirement. 

Environment

  • Application Security Manager™ (ASM) is provisioned
  • An ASM Security Policy is applied to a Virtual Server

Cause

Suspected malicious traffic with a custom pattern is hitting an ASM protected Virtual Server normally encountered during an HTTP based attack
 

Recommended Actions

Review Malicious Traffic


During an HTTP based attack or when suspicious traffic is hitting an ASM protected Virtual Server, malicious traffic can be observed by gathering data thru the BIGIP.  Taking a packet capture (using tcpdump) and reviewing the decrypted HTTP traffic will provide insight on what HTTP headers, parameters, cookies, payload the request contain and decide what is considered malicious. 

HTTP request information can also be reviewed by using iRules or LTM Policy to log HTTP headers and payload locally or remotely. Similarly, as an ASM policy is expected to be applied on the Virtual Server,  a Log Profile can be applied to the Virtual Server and log illegal or all requests which can be reviewed for traffic pattern that is considered malicious. 

example: 

Here is a curl command sending a HTTP POST request using as a valid user agent. 

curl -lv https[:]//site[.]biz[.]loc/ -H "Host: site[.]biz[.]loc" -H "User-Agent:Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/75.0.3770.100 Safari/537.36" -H "Referer: https[:]//site[.]biz[.]loc/" -H "Origin: https[:]//site[.]biz[.]loc/" -H "Upgrade-Insecure-Requests: 1" -X POST

Using an iRule, LTM Policy or ASM Event logs or packet capture, this request can be observed and if has seen to be sending an anomalous amount of request, an administrator can decide to block this certain pattern.


Create a User-Defined / Custom Attack Signature 

Based on the defined malicious traffic qualities/pattern from the observed traffic during an HTTP based attack, a User-Defined / Custom Attack Signature can be created.

Note: Developing custom attack signatures is an advanced feature only needed in specific cases. Remove the square brackets [] when adding a FQDN or URL to the configuration.

Create a Custom Attack Signature in Simple Edit Mode (v13.1.x and later)

1. In the Configuration Utility, Security  ››  Options : Application Security : Attack Signatures : Attack Signature List  ››  Create
2. Provide a unique Name
3. For the Signature Type setting, select Request or Response to determine whether the new signature applies to client requests or server responses.
4. For the Systems setting, select from the Available Systems list any systems to which the new signature applies, and move them to the Assigned Systems list.
5. For the Attack Type setting, select the type of threat that the new signature protects against.
6. On the Rule section, select Simple Edit Mode
Click Add
On the Matched Element, select an appropriate option. Example Header
On the Matched Criteria, select an appropriate option. Example contains string
For the Keyword, provide the strings that should be matched by this attack signature. example, use the HTTP header values in the sample malicious HTTP request

Example:
Header contains string site[.]biz[.]loc
Header contains string Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/75.0.3770.100 Safari/537.36
Header contains string https[:]//site[.]biz[.]loc/
Header contains string 1

7. For the Accuracy setting, select an accuracy level.
The accuracy level indicates the ability of the attack signature to identify the attack, including susceptibility to false-positive alarms.
8. For the Risk setting, select a risk level.
The risk level indicates the level of potential damage this attack may cause, if it were successful.
9. Click Create to create the new attack signature.

Resulting Attack Signature:

headercontent:"site[.]biz[.]loc"; nocase; headercontent:"Mozilla/5.0 (Windows NT 10.0|3b| Win64|3b| x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/75.0.3770.100 Safari/537.36"; nocase; headercontent:"https[:]//site[.]biz[.]loc/"; nocase; headercontent:"1"; nocase;

Create a Custom Attack Signature in Advanced Edit Mode

1. In the Configuration Utility, Security ›› Options : Application Security : Attack Signatures : Attack Signature List ›› Create
2. Provide a unique Name
3. For the Signature Type setting, select Request or Response to determine whether the new signature applies to client requests or server responses.
4. For the Systems setting, select from the Available Systems list any systems to which the new signature applies, and move them to the Assigned Systems list.
5. For the Attack Type setting, select the type of threat that the new signature protects against.
6. On the Rule section, select Advanced Edit Mode
Click Add

Here is an example of an Attack Signature syntax that can be used in the Rule. 

headercontent:"site[.]biz[.]loc"; nocase; headercontent:"Mozilla/5.0 (Windows NT 10.0|3b| Win64|3b| x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/75.0.3770.100 Safari/537.36"; nocase; headercontent:"https[:]//site[.]biz[.]loc/"; nocase; headercontent:"1"; nocase;

Note: Writing the Attack Signature follows Signature Syntax listed in Manual Chapter : Signature Syntax of BIG-IP Application Security Manager: Attack and Bot Signatures and is not covered on this Article. 

7. For the Accuracy setting, select an accuracy level.
The accuracy level indicates the ability of the attack signature to identify the attack, including susceptibility to false-positive alarms.
8. For the Risk setting, select a risk level.
The risk level indicates the level of potential damage this attack may cause, if it were successful.
9. Click Create to create the new attack signature.

Expected Result:

Sample traffic will be blocked if ASM policy and User-Defined/Custom Attack Signature sample is in blocking mode and not in staging mode respectively.

Sample Attack Signature:
headercontent:"site[.]biz[.]loc"; nocase; headercontent:"Mozilla/5.0 (Windows NT 10.0|3b| Win64|3b| x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/75.0.3770.100 Safari/537.36"; nocase; headercontent:"https[:]//site[.]biz[.]loc/"; nocase; headercontent:"1"; nocase; 

Sample traffic:
curl -lv https[:]//site[.]biz[.]loc/ -H "Host: site[.]biz[.]loc" -H "User-Agent:Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/75.0.3770.100 Safari/537.36" -H "Referer: https[:]//site[.]biz[.]loc/" -H "Origin: https[:]//site[.]biz[.]loc/" -H "Upgrade-Insecure-Requests: 1" -X POST
