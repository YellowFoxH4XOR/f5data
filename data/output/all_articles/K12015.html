Topic

The BIG-IP system offers key features that allow you to manage SSL traffic. Properly configuring these features and traffic-management components, such as SSL virtual servers, profiles, pools, and monitors, is critical to managing SSL traffic. For example, mixing both SSL and non-SSL pool members in the same load-balancing pool will result in intermittent traffic disruptions and dropped connections. This behavior occurs because in nearly all circumstances, a host that is configured to process SSL connections will drop non-SSL connections and vice versa. This article covers common requirements for configuring SSL virtual servers, profiles, pools, and monitors.

Pool configuration

In general, an application that is configured to process SSL connections is unable to process non-SSL connections, and conversely, an application that is configured to process non-SSL connections is unable to process SSL connections. To avoid intermittent traffic disruptions and dropped connections, F5 recommends that you avoid mixing both SSL and non-SSL pool members in the same pool.

Monitors

The BIG-IP LTM system includes a wide variety of health monitors. When selecting a monitor to associate with a pool, pool member, or node, it is important to note that some health monitors generate SSL traffic and some generate non-SSL traffic. Associating the wrong monitor type with a pool member or node results in the BIG-IP system marking a pool member or node down. The following sections group BIG-IP health monitors according to whether the monitor generates SSL traffic or non-SSL traffic:

  • BIG-IP health monitors that generate SSL traffic
  • BIG-IP health monitors that generate non-SSL traffic

BIG-IP health monitors that generate SSL traffic

The following BIG-IP health monitor types generate only SSL traffic. Assigning these health monitor types to non-SSL pool members or nodes may result in the BIG-IP system marking the pool members down (even if the pool member or node is configured to use the same Layer 7 protocol).

  • HTTPS
  • LDAP (with the Security option set to SSL)
  • SOAP (with the Protocol option set to HTTPS)

BIG-IP health monitors that generate non-SSL traffic

The following BIG-IP health monitor types generate only non-SSL traffic. Assigning these health monitor types to SSL pool members or nodes (even if the pool member or node is configured to use the same Layer 7 protocol) may result in the BIG-IP system marking the pool members down.

  • FTP
  • HTTP
  • IMAP
  • LDAP (with the Security option set to None or TLS)
  • NNTP
  • POP3
  • SIP
  • SMTP
  • SOAP (with the Protocol option set to HTTP)
  • TCP
  • UDP
  • WAP

Note: For more information about troubleshooting BIG-IP health monitors, refer to K12531: Troubleshooting health monitors.

Virtual server types

You can configure the BIG-IP system to process SSL traffic by performing SSL decryption and/or encryption, or by passing SSL traffic directly to SSL pool members. It is important to select the correct virtual server type when configuring the BIG-IP system to process SSL traffic. The following sections list the virtual server type and whether it is compatible with SSL traffic:

  • Virtual servers capable of performing SSL decryption/encryption
  • Virtual servers capable of performing SSL passthrough
  • Virtual server types not compatible with SSL traffic

Virtual servers capable of performing SSL decryption/encryption

If you want the BIG-IP system to decrypt and/or encrypt SSL traffic, you must define the following virtual server type:

  • Standard

    The standard virtual server is the only virtual server type that can be associated with Client SSL and Server SSL profiles, and perform SSL decryption and/or encryption. If you want the BIG-IP system to decrypt and/or encrypt SSL traffic, you must import the SSL certificates to the BIG-IP system and configure a standard virtual server and appropriate SSL profile.

    Note: For more information about configuring the BIG-IP to manage SSL traffic, refer to the Managing SSL Traffic chapter of the Configuration Guide for BIG-IP Local Traffic Manager.

    Note: You can configure a Client SSL virtual server to accept non-SSL connections by using the Non-SSL Connections profile setting. When you enable the Non-SSL Connections setting in the profile, non-SSL connections pass through the BIG-IP system in clear-text. For more information, refer to the Managing SSL Traffic chapter of the Configuration Guide for BIG-IP Local Traffic Manager.

    Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation.

Virtual servers capable of performing SSL passthrough

If the virtual server is not required to decrypt and/or encrypt the SSL traffic, the SSL profiles are not required and you can use the following virtual server types to pass the SSL traffic to the pool members:

Note: If Layer 7 processing, such as iRules or cookie persistence, is required for the virtual server, you must configure a standard virtual server with the appropriate profiles (SSL, HTTP, and so on.)

  • Performance (Layer 4)
  • Forwarding (Layer 2)
  • Forwarding (IP)
  • Standard

Note: SSL traffic can pass through these types of virtual servers unmodified if the virtual server and pool both use SSL. Additionally, if a Standard virtual server type is used, an HTTP profile should not be configured as there will be no way to parse the encrypted content.

Virtual server types not compatible with SSL traffic

  • Performance (HTTP)
  • Stateless

The performance (HTTP) and Stateless virtual server types are not compatible with SSL traffic. To use a virtual server port, pool, or both, that passes SSL traffic, the standard virtual server type is recommended.

Virtual server and SSL profile configuration requirements

The following section discusses various SSL configuration scenarios and whether SSL profiles are necessary:

Note: For more information about configuring SSL profiles, refer to the Managing SSL Traffic chapter of the Configuration Guide for BIG-IP Local Traffic Manager. For information about how to locate F5 product documentation, refer to K98133564: Tips for searching AskF5 and finding product documentation.

  • Neither the virtual server nor the pool members are required to process SSL connections.

    In this scenario, no SSL profiles are necessary. Associating an SSL profile with the virtual server may cause traffic disruption.

  • The virtual server is required to process SSL traffic, but the pool members do not process SSL connections.

    In this scenario, the BIG-IP system must be configured to perform SSL decryption. Configure a standard virtual server, and associate a Client SSL profile with the virtual server.

  • The virtual server is required to use a non-SSL port, and the pool members process SSL connections.

    In this scenario, the virtual server must be configured to perform SSL encryption. Configure a standard virtual server, and associate a Server SSL profile with the virtual server.

  • Both the virtual server and pool members are required to process SSL connections, but the BIG-IP system is not required to perform Layer 7 processing, such as iRule or cookie persistence.

    In this scenario, SSL decryption and re-encryption is not strictly required. However, if you want the BIG-IP system to present a common SSL certificate on behalf of the pool members, configure a standard virtual server and associate the appropriate SSL profiles with the virtual server.

  • Both the virtual server and pool members are required to process SSL connections, and the BIG-IP system is required to perform Layer 7 processing, such as iRule or cookie persistence.

    In this scenario, the virtual server must be configured to perform SSL decryption and re-encryption. Configure a standard virtual server and associate Client SSL and Server SSL profiles with the virtual server.
