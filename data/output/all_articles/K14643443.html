Description

In this article, you install multi-cluster Aspen Mesh on two KOPS clusters. First, ensure that you have two Kubernetes clusters with the same version of Aspen Mesh installed on each of them. Enter the following command:

kops get cluster

You should see an output similar to the following:

ssah-test1.dev.k8s.local        aws    us-west-2a
ssah-test2.dev.k8s.local        aws    us-west-2a

There are multiple ways to configure Aspen Mesh on a multi-cluster environment. You install Aspen Mesh Istio distribution on both of your clusters in the following example, and the installation type is "Multi-Primary on different networks"

Environment

  • Kubernetes: 1.18.x - 1.23.x  
  • Aspen Mesh:  1.9.x, 1.11.x, 1.14.x
The details below are applicable for Aspen Mesh 1.14.x and earlier version. For the procedure about 1.9.5 and future versions, refer to K44817186: Installing multi-cluster Aspen Mesh version 1.9.5-x.

Cause

N/A

Recommended Actions

  • Configure trust
  • Enable multi-cluster
    • Cluster 1: sample_overrides-aspenmesh.yaml
    • Cluster 2: sample_overrides-aspenmesh_2.yaml
    Upgrade/Install istiod manifest
  • Create ingress gateway
    • Cluster 1: cluster1_gateway_config.yaml
    • Cluster 2: cluster2_gateway_config.yaml
  • Configure API communications
  • Edit the ingress east-west gateway
Pre-requisites for the Setup:
  • API: The servers of each cluster must be able to access the API server of the other cluster.
  • Trust: Trust must be established between all clusters in the mesh. This is achieved by having a common Root CA to generate intermediate certs for each cluster.
Configure trust:
  1. Create an RSA type certificate for your root cert.
  2. Download the Aspen Mesh installer from Aspen Mesh.
  3. Extract the installer. It contains a tools directory to create your certificate.

    cd tools

  4. Create a cert folder and add the folder to the directory stack by entering the following commands:

    mkdir -p certs; pushd certs

  5. Run the make command to create a root-ca folder, which will consist of four files: root-ca.conf, root-cert.csr, root-cert.pem and root-key.pem.

    Note: For more information on the make command, refer to the README.md file in the tools/certs directory.

    make -f ../tools/certs/Makefile.selfsigned.mk root-ca
    make -f ../tools/certs/Makefile.selfsigned.mk cluster1-cacerts
    make -f ../tools/certs/Makefile.selfsigned.mk cluster2-cacerts

    The following lists the example output when you enter the following commands:

    > cd certs
    > ls
    # root CA certificates
    cluster1    cluster2    root-ca.conf    root-cert.csr    root-cert.pem    root-cert.srl    root-key.pem
    > ls -l cluster1
    # Intermediate CA certificates signed by the common root CA certificate
    total 32
    [...] 1895 May 10 20:04 ca-cert.pem
    [...] 3243 May 10 20:04 ca-key.pem
    [...] 3700 May 10 20:04 cert-chain.pem
    [...] 1805 May 10 20:04 root-cert.pem
    > ls -l cluster2
    total 32
    [...] 1895 May 10 20:08 ca-cert.pem
    [...] 3243 May 10 20:08 ca-key.pem
    [...] 3700 May 10 20:08 cert-chain.pem
    [...] 1805 May 10 20:08 root-cert.pem

    For each of your clusters, you will need to generate an intermediate cert and key for the Istio CA.

  6. Create secrets for each of your clusters in the istio-system namespace with all the input files that you generated from the last step using the following commands:

    Note: These secrets at each of the clusters is what configures trust between them as the same root-cert.pem is used to create the intermediate cert.

    kubectl  create secret generic cacerts -n istio-system  --from-file=ca-cert.pem  --from-file=ca-key.pem  --from-file=root-cert.pem  --from-file=cert-chain.pem --context="${CTX_CLUSTER1}"
    kubectl create secret generic cacerts -n istio-system --from-file=ca-cert.pem  --from-file=ca-key.pem  --from-file=root-cert.pem --from-file=cert-chain.pem --context="${CTX_CLUSTER2}"

Enable multi-cluster

Move on to the Aspen Mesh configuration. You will enable multi-cluster for istiod and give names to the network and cluster. Create a separate file for each cluster, adding the fields to your override files as shown below for each cluster. The files will be used during the Helm installation/upgrade. You will also need to label the istio-system namespace in both of your clusters with the appropriate label. Use the following command syntaxes:

kubectl --context="${CTX_CLUSTER1}" label namespace istio-system topology.istio.io/network=network1
kubectl --context="${CTX_CLUSTER2}" label namespace istio-system topology.istio.io/network=network2

Cluster 1: sample_overrides-aspenmesh.yaml

# Global DNS Proxy configuration is optional, can be also enabled per POD with POD annotations.
# In order to make the application service callable from any cluster, the DNS lookup must succeed in each cluster
#This provides DNS interception for all workloads with a sidecar, allowing Istio to perform DNS lookup on behalf of the application.
#meshConfig:
# defaultConfig:
#   proxyMetadata:
    # Enable Istio agent to handle DNS requests for known hosts
    # Unknown hosts will automatically be resolved using upstream dns servers in resolv.conf
    #  ISTIO_META_DNS_CAPTURE: "true"

global:
  meshID: mesh1
  multiCluster:
    # Set to true to connect two kubernetes clusters via their respective
    # ingressgateway services when pods in each cluster cannot directly
    # talk to one another. All clusters should be using Istio mTLS and must
    # have a shared root CA for this model to work.
    enabled: true
    # Should be set to the name of the cluster this installation will run in. This is required for sidecar injection
    # to properly label proxies
    clusterName: "cluster1"
    globalDomainSuffix: "local"
    # Enable envoy filter to translate `globalDomainSuffix` to cluster local suffix for cross cluster communication
    includeEnvoyFilter: false
  network: network1

Upgrade/Install istiod manifest

Now, you will upgrade/install the istiod manifest with the newly added configuration from the override file. You have separate override files for each cluster.

helm upgrade istiod manifests/charts/istio-control/istio-discovery -n istio-system --values sample_overrides-aspenmesh_2.yaml
helm upgrade istiod manifests/charts/istio-control/istio-discovery -n istio-system --values sample_overrides-aspenmesh.yaml

Check the pods in the istio-system namespace to see if all are in a running state. Be sure to delete all your application pods in your default namespace for the new configuration to kick in when the new pods will be spun. You can also check to see if the root cert used for pods in each cluster is the same. You are using pods from the bookinfo sample application.

istioctl pc secrets details-v1-79f774bdb9-pqpjw -o json | jq '[.dynamicActiveSecrets[] | select(.name == "ROOTCA")][0].secret.validationContext.trustedCa.inlineBytes' -r | base64 -d | openssl x509 -noout -text | md5istioctl pc secrets details-v1-79c697d759-tw2l7 -o json | jq '[.dynamicActiveSecrets[] | select(.name == "ROOTCA")][0].secret.validationContext.trustedCa.inlineBytes' -r | base64 -d | openssl x509 -noout -text |md5

Create ingress gateway

Once istiod is upgraded, create an ingress gateway used for communication between the two clusters by installing an east-west gateway. Use the following configuration to create yaml files which will be used with Helm to install in each of the clusters.
 
Create two yaml files: cluster1_gateway_config.yaml and cluster2_gateway_config.yaml that will be used with the respective clusters:

Cluster 1: cluster1_gateway_config.yaml

#This can be on separate override file as we will install a custom IGW
gateways:
  istio-ingressgateway:
    name: istio-eastwestgateway
    labels:
      app: istio-eastwestgateway
      istio: eastwestgateway
      topology.istio.io/network: network1
    ports:
    ## You can add custom gateway ports in user values overrides, but it must include those ports since helm replaces.
    # Note that AWS ELB will by default perform health checks on the first port
    # on this list. Setting this to the health check port will ensure that health
    # checks always work. https://github.com/istio/istio/issues/12503
    - port: 15021
      targetPort: 15021
      name: status-port
      protocol: TCP
    - port: 15012
      targetPort: 15012
      name: tcp-istiod
      protocol: TCP
    # This is the port where sni routing happens
    - port: 15443
      targetPort: 15443
      name: tls
      protocol: TCP
    - name: tls-webhook
      port: 15017
      targetPort: 15017
    env:
      # A gateway with this mode ensures that pilot generates an additional
      # set of clusters for internal services but without Istio mTLS, to
      # enable cross cluster routing.
      ISTIO_META_ROUTER_MODE: "sni-dnat"
      ISTIO_META_REQUESTED_NETWORK_VIEW: "network1"
    serviceAnnotations:
      service.beta.kubernetes.io/aws-load-balancer-type: nlb
 
global:
  meshID: mesh1
  multiCluster:
    # Set to true to connect two kubernetes clusters via their respective
    # ingressgateway services when pods in each cluster cannot directly
    # talk to one another. All clusters should be using Istio mTLS and must
    # have a shared root CA for this model to work.
    enabled: true
    # Should be set to the name of the cluster this installation will run in. This is required for sidecar injection
    # to properly label proxies
    clusterName: "cluster1"
    globalDomainSuffix: "local"
    # Enable envoy filter to translate `globalDomainSuffix` to cluster local suffix for cross cluster communication
    includeEnvoyFilter: false
  network: network1

Use Helm to install eastwest gateways on each cluster to open data plane communication between clusters.
helm install egressgw  manifests/charts/gateways/istio-ingress --namespace istio-system --kube-context  "${CTX_CLUSTER1}"   --values cluster1_gateway_config.yaml
helm install egressgw  manifests/charts/gateways/istio-ingress --namespace istio-system --kube-context  "${CTX_CLUSTER2}"   --values cluster2_gateway_config.yaml
 

Configure API communications

Now that the gateway is configured to communicate, enable the API of each cluster to talk to the other cluster. You can do this in AWS by making sure API instances are accessible to each other by creating specific rules for their security group. You will then need to create a secret in cluster 1 that provides access to cluster 2’s API server and vice versa for endpoint discovery.

Enable endpoint discovery Cluster 2:
istioctl x create-remote-secret --context="${CTX_CLUSTER1}" --name=cluster1 | kubectl apply -f - --context="${CTX_CLUSTER2}"

Enable endpoint discovery Cluster 1:
istioctl x create-remote-secret --context="${CTX_CLUSTER2}" --name=cluster2 |kubectl apply -f - --context="${CTX_CLUSTER1}"

Edit the ingress east-west gateway

At this stage, the pilot (which is bundled in the istiod binary) should have the new configuration. When you tail the logs for the pod, you should be able see the log’s message

Number of remote cluster: 1

With this version, you would also need to edit the ingress east-west gateway in the istio-system namespace that you created earlier as the selector label and the annotation added via Helm chart is different from expected. It shows istio: ingressgateway but should be istio: eastwestgateway.

You can now create pods in each cluster and verify it is working as expected. For more information on the verification steps, refer to Verify the installation in the Istio documentation.

The following is an example of an east-west gateway you can use to route traffic to remote cluster.
The Gateway has to be applied on both clusters

# Cluster1
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  labels:
    app: istio-eastwestgateway
    istio: eastwestgateway
    release: istio-eastwestgateway
    topology.istio.io/network: network1
  name: istio-multicluster-ingressgateway
  namespace: istio-system
spec:
  selector:
    istio: eastwestgateway
  servers:
  - hosts:
    - '*.local'
    port:
      name: tls
      number: 15443
      protocol: TLS
    tls:
      mode: AUTO_PASSTHROUGH

# Cluster2
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  labels:
    app: istio-eastwestgateway
    istio: eastwestgateway
    release: istio-eastwestgateway
