K000160923: ConfigSync Failure When Changing Monitor Type via AS3 Using the Same Monitor Name on BIG-IP LTM

Type
Support Solution
Published
2026-04-23
Updated
2026-04-23
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000160923

Description

ConfigSync fails when changing a pool member’s health monitor type (e.g., from HTTP to ICMP) via AS3 using the same monitor name. The update succeeds on the Active device but fails to synchronize to the Standby device in a BIG-IP LTM HA pair. Error messages include:

 

  • 01b40045:3: Cannot modify the port of monitor
  • Monitor ... contains an argument that is not allowed.

The issue is resolved only by detaching and deleting the monitor before re-creating it, which can be disruptive.

 

Environment

  • Product: BIG-IP LTM
  • BIG-IP Versions: 17.1.1.1, 17.5.1.3
  • AS3 Versions: 3.53.0-7, 3.54.x, 3.55.x, 3.57.0-6
  • High Availability (HA) pair: Active/Standby
  • Pool members with health monitors managed via AS3 declarations
  • Monitor type changes (e.g., HTTP → ICMP) performed using the same monitor name

 

Cause

A defect (ID423304)  in AS3’s handling of monitor type changes when the monitor name remains the same. When AS3 changes a monitor’s type but reuses the same name, the Active device deletes and recreates the monitor, but ConfigSync on the Standby device interprets this as a parameter modification. This leads to an invalid configuration state, as certain monitor properties (such as port) cannot be modified for an in-use monitor, resulting in sync errors.

A fix is available to resolve this issue.

 

Answer/Recommended Actions

  • Upgrade AS3 to a version including the fix for this issue.
  • If upgrading is not possible, request a backported fix for the specific AS3 version in use (e.g., 3.53.0-7).
  • As a workaround, when changing a monitor type, use a unique monitor name for each type, or detach and delete the monitor from all pools before re-creating it with the new type.
  • Test the fix in a non-production environment before deploying globally.

 

 

Additional Information

  • This issue is triggered when the monitor name remains the same while the monitor type changes (e.g., HTTP to ICMP).
  • The workaround (detaching and deleting the monitor before re-creating it) may not be feasible in automated or production environments.
  • The fix is available for backport to earlier versions upon request.
