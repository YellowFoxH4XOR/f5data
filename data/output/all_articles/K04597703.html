Topic

This article applies to BIG-IP 12.1.x. For information about other versions, refer to the following article:

  • K15085: Overview of the Local Traffic Policies feature (11.4.0 - 12.0.0)

This article covers the settings and usage of the Local Traffic Policies feature for BIG-IP 12.1.0 and later.

Description

The Local Traffic Policies feature allows you to classify traffic based on a list of matching rules and then run specific actions, such as directing all HTTP traffic to the BIG-IP ASM system for security checks based on the configured security policy, redirecting traffic received on an HTTP virtual server to an HTTPS virtual server, sending traffic to a load balancing pool based on header data, or refining the types of traffic collected for statistical analysis in BIG-IP Analytics.

In BIG-IP 12.1.0 and later, you can create and implement a local traffic policy using the following steps:

  • Create the local traffic policy draft
  • Create the rules you will associate with the policy
  • Publish the policy
  • Associate the local traffic policy with a virtual server

The local traffic policy settings are organized into the following sections and are described in the following tables:

General Properties

Local traffic policies require a matching strategy to determine which rules apply to the traffic destined for the virtual server. When you create the policy you define the matching strategy.

SettingDescription
Policy NameThe policy name setting is required and specifies the name of the local traffic policy.
DescriptionThe Description is not a required setting, and can be used to identify the local traffic policy.
StrategyThe Strategy setting specifies which actions get executed in the case where there are multiple rules that match. The following options are available:
  • all: When you define the 'all' strategy, the system starts the actions belonging to all rules in the Rules list that match. In the event of a conflict, the system uses the best matching rule strategy to resolve the conflict.
  • first: When you define the 'first' strategy, the system orders the rules either implicitly or explicitly using an ordinal/priority. When multiple matches apply, the system applies the actions of only the first rule, that is, the rule with the lowest ordinal, highest priority, or first rule that matches in the Rules list.
  • best: When you define the 'best' strategy, the system does not order the rules. Instead, the system selects and starts the actions of the rule in the Rules list with the best match. When multiple rules match and specify an action, conflicting or otherwise, only the action of the best matching rule is implemented. A best matching rule can be the lowest ordinal (determined by the precedence of the operand), the highest priority, or the first rule that matches in the Rules list.

Rules

You can configure the local traffic policy rules to match conditions and take specific actions based on the traffic. The rule settings are defined as follows:

ConditionDescription
Client SSLThe rule can be configured to inspect the Secure Sockets Layer (SSL) connection on the client side of the device and match any of the following elements:
  • cipher. Specifies the cipher name.
  • cipher bits. Specifies the cipher strength by means of the number of bits.
  • protocol. Specifies the SSL protocol name.
CPU UsageYou can configure a rule condition that is based on CPU usage during 15-second, 1-minute, or 5-minute intervals.
Geo. IPYou can configure a rule condition that uses properties of the geographical location of the IP address.
  • continent. Matches a two-character continent code, for example, AF (Africa), AN (Antarctica), AS (Asia), OC (Oceania), NA (North America), or SA (South America).
  • country code. Matches a two-character country code, as defined in ISO-3166-2.
  • country name. Matches the full name of a country.
  • isp. Matches the Internet Service Provider associated with the address.
  • organization. Matches the organization associated with the address.
  • region code. Matches the abbreviation of a state, province, or country-specific region.
  • region name. Matches the full name of a state, province, or country-specific region.
HTTP Basic AuthThe rule can be configured to inspect the username and password for basic authentication HTTP requests.
  • password. Matches the basic authentication password.
  • username. Matches the basic authentication username.
HTTP CookieYou can configure a rule that inspects the Cookie header of an HTTP request.
HTTP HeaderYou can configure a rule to match any HTTP header.
HTTP HostThe rule can be configured to match the following host properties of an HTTP request.
  • host. Matches the host name.
  • port. Matches the port number.
  • full string. Matches the full host header string.
HTTP MethodThe rule can inspect the HTTP method for the request (for example, GET, POST, or HEAD)
HTTP RefererYou can configure the rule to inspect the HTTP Referer header or parts of the URI.
  • extension. Matches the document extension, for example, cgi.
  • host. Matches the DNS host name or IP address.
  • path. Matches the URI path, for example, /path.
  • path segment. Matches the path segment by numerical index (1 - 2147483647).
  • port. Matches the numeric port number, for example, 80.
  • query parameter. Matches the value of the query parameter by name.
  • query string. Matches the full query string, for example, a=b&c=d.
  • scheme. Matches the scheme, for example, http, https, or ftp.
  • unnamed query parameter. Matches the value of the query parameter by numerical index.
  • full string. Matches the full URI
HTTP Set CookieThe rule can inspect the Set-Cookie header of an HTTP response.
  • domain. Matches the value of the domain specified by the named cookie.
  • expiry. Matches the time when the validity of the named cookie expires in RFC 6265 format (Wdy, DD Mon YYYY HH:MM:SS GMT).
  • path. Matches the path of the named cookie.
  • value. Matches the value of the named cookie specified by the parameter.
  • version. Matches the version of the named cookie.
HTTP StatusThe rule can inspect the status of the HTTP response.
  • code. Matches the numeric HTTP response status code.
  • text. Matches the HTTP response status string, for example, Authentication Required.
  • full string. Matches the full HTTP status response, including the code and text.
HTTP URIYou can configure the rule to inspect the URI on a request and matches parts of or the entire URI.
  • extension. Matches the file extension in the URI, for example, html or cgi.
  • host. Matches the host name in the URI.
  • path. Matches the URI path.
  • path segment. Matches a part of the URI path by a numeric index (1 - 2147483647).
  • port. Matches the port number in the URI.
  • query parameter. Matches the value of the named query parameter from the query string.
  • query string. Matches the text specified in the query string.
  • scheme. Matches the scheme, for example, http, https, ftp, or file.
  • unnamed query parameter. Matches the value of a query parameter by a numeric index instead of by a name index.
  • full string. Matches a specified full text string.
HTTP User AgentThe rule can inspect the User Agent header.
  • browser type. Matches the browser name or type.
  • browser version. Matches the browser version string.
  • device make. Matches the make of the device.
  • device model. Matches the model of the device.
  • token. Matches a string associated with a specified parameter.
HTTP VersionThe rule can inspect the version of an HTTP request or response.
  • major. Matches the numeric major part of the HTTP version.
  • minor. Matches the numeric minor part of the HTTP version.
  • protocol. Matches the HTTP protocol.
  • full string. Matches the full version string.
IPThe rule can inspect the IP protocol or version.
IP ReputationThe rule can inspect the IP Reputation category.
  • BotNets
  • Cloud Storage Provide
  • Denial of Service
  • Illegal
  • Infected Sources
  • Networks
  • Phishing
  • Proxy
  • Scanners
  • Spam Sources
  • Web Attacks
  • Windows Exploits
SSL CertificateThe rule can inspect the properties of an SSL certificate
SSL ExtensionYou can configure the rule to inspect the SSL extensions that are negotiated during the SSL handshake.
  • alpn. Matches the application layer protocol negotiation.
  • npn. Matches the next protocol negotiation.
  • server name. Matches the server name indication.
TCPConfigure the rule to inspect and the parameters associated with TCP connections.
  • address. Matches the specified IP address. The IP address is the address associated with the external interface remote end of the connection.
  • mss. Compares the TCP maximum segment size on the external network interface.
  • port. Matches the port number. The specified port is associated with the external interface, remote end of the connection.
  • route domain. Compares traffic with the specified route domain number on the external network interface.
  • rtt. Inspects the round-trip time on the external network interface.
  • vlan. Compares traffic with the specified Virtual Local Area Network (VLAN) on the external network interface.
  • vlan id. Compares traffic with the specified VLAN ID number on the external interface.

  • extension. Matches the value of the Sec-WebSocket-Extensions header.
  • key. Matches the value of the masking-key.
  • protocol. Matches the value of the Sec-WebSocket-Protocol header.
  • version. Matches the value of the Sec-WebSocket-Version header.

Logical operators

Local traffic policy rules provide you with different types of logical operators for matching conditions, which are determined by the order and configuration of the conditions within and between the rules. The different types of logical operators that you can configure are AND logical operators for conditions within a rule, and OR logical operators for values within a condition and for conditions between rules.

Policy rule actions

The actions for a local traffic policy rule determine how traffic is handled. Some actions apply only to certain condition types:

  • Enable: Enables certain actions.
  • Disable: Disables certain actions.
  • Forward traffic: Controls where a connection is forwarded.
  • Insert: Inserts an HTTP header into the request or response.
  • Remove: Removes an HTTP header from the request or response.
  • Replace: Replaces an HTTP header
  • Redirect: Redirects traffic to a different URL.
  • Reset traffic: Resets the connection.
  • Log: Writes messages to the local or remote system log.
  • Persist session: Controls how a connection is persisted.
  • Set variable: Sets a Tcl variable in the runtime environment.

Recommendations

When working with local traffic policies, you should consider the following factors:

  • If you want to reorder rules in a published local traffic policy, you must first create a draft of the policy, reorder the rules in the draft, and then save and publish the changes.
  • To create a different draft policy with the same settings as an original policy, you can clone a draft or published local traffic policy. After you clone the policy, you can modify and publish it.
