Topic

You should consider using this procedure under the following conditions:

  • You have a BIG-IP cloud instance deployed on Microsoft Azure Cloud.
  • You want to migrate the instance to a newer version of the BIG-IP system, retaining the configuration of the instance.
  • You want to migrate the instance within the same Azure subscription. This procedure does not apply to migration across different subscriptions.

Description

Migrating a BIG-IP instance (within the same Azure subscription) requires destroying the existing Azure BIG-IP instance and launching a new one. To retain the exact configuration of the original BIG-IP instance, it is essential to understand what the configuration of a BIG-IP instance on Azure cloud consists of. This includes the following:

  • BIG-IP configuration refers to virtual servers, pool members, network IP addresses on the BIG-IP system, and so on. To retain the BIG-IP configuration, you generate a UCS archive on your original BIG-IP instance and restore it on the new one. It is important to take note of your BIG-IP license (BYOL or payg) and whether the license supports the change you plan to make to the new instance. Use the following no-license command syntax when restoring the UCS archive if a new license is required: tmsh load sys example.ucs no-license.

  • Azure instance configuration refers to the instance image, operating system type, OS disk, connected network interfaces, and so on. To retain the Azure instance configuration, you can export the instance configuration to an Azure Resource Manager (ARM) template and launch the new instance from the Azure portal or using Ansible. Alternatively, you can also import the instance as a Terraform resource and use Terraform to launch the new instance.

  • Customizations refers to any script or Azure customizations you configured with your BIG-IP instance that are not captured in the ARM template.

The following summarizes the required steps to migrate your Azure instance:

  1. Generate a user configuration set (UCS) archive on the original BIG-IP system and store it on your client machine.
  2. Export the Azure instance configuration of your BIG-IP instance and its associated disk to an Azure ARM template.
  3. Make the necessary changes to the template.
  4. Delete the BIG-IP instance and its associated disk (downtime required).
  5. Deploy the template to the same resource group.
  6. Restore the UCS file on the new BIG-IP VM on Azure.
  7. Restore any customizations not captured in the Azure ARM template.
  8. Test your applications.

The procedure uses the Azure ARM template feature. Microsoft may update or revise Azure portal and the template features, and specific steps in this article may change as a result. F5 support for this procedure does not include issues related to the Azure portal or ARM template. For more information on ARM templates, refer to Azure ARM templates.

In addition to modifying the BIG-IP version of the Azure image in the ARM template, you can also modify or configure other parameters of the Azure BIG-IP image. To obtain the different available configurations of the image, perform the following procedure using Azure cloud shell:

Note: If you set up the Azure command-line interface, you can also enter the command using the command-line interface of your local machine. For more information, refer to Get started with Azure CLI and Azure VM Image.   1. Log in to the Azure portal.
  2. In the top navigation, next to the bell icon, select and launch Cloud Shell.

    Note: If this is your first time using Azure Cloud Shell, you must select a subscription account and then select Create Storage to persist your work.

  3. Use the following command syntax to display the different available Azure BIG-IP images:

    az vm image list --offer big-ip --all --output table | grep <version> | grep <license>

    For example, you enter the following command:

    az vm image list --offer big-ip --all --output table | grep 16.0.1 | grep 25m-best

    From the output, you can obtain the values of the BIG-IP image to launch. For example, in the following resources stanza in the ARM template, you can modify the name and sku values from "f5-bigip-virtual-edition-25m-best-hourly" to "f5-bigip-virtual-edition-200m-best-hourly" depending on your requirements.

     "resources": [
                [...]
                
                "plan": {
                    "name": "f5-bigip-virtual-edition-25m-best-hourly", <------
                    "product": "f5-big-ip-best",
                    "publisher": "f5-networks"
                },
                "properties": {
                    "hardwareProfile": {
                        "vmSize": "Standard_DS3_v2"
                    },
                    "storageProfile": {
                        "imageReference": {
                            "publisher": "f5-networks",
                            "offer": "f5-big-ip-best",
                            "sku": "f5-bigip-virtual-edition-25m-best-hourly", <------
                            "version": "16.0.101000"
                        },
      [...]

Consider the following when modifying the configurations of your Azure BIG-IP image on the ARM template:

  • Configuring incorrect or incompatible values in the ARM template can result in Azure errors when launching the instance or errors on the BIG-IP system when booting up. To troubleshoot such issues, destroy the instance, revert the changes, and re-launch.
  • Ensure the BIG-IP license of the new instance (BYOL or PAYG) supports the services you plan to run. For example, if you plan to run BIG-IP ASM and BIG-IP APM, configure either the Better or Best license type. For more information on license type, refer to K49243459: BIG-IP VE BYOL product listings on public cloud marketplaces.

  • Depending on the changes you make (for example when modifying the name and sku as in the previous case), when restoring the UCS archive on the newly launched BIG-IP instance, you need to use the no-license switch:

    tmsh load sys ucs <filename.ucs> no-license
