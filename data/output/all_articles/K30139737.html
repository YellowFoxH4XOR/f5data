Description

How BIG-IP implements DPD/Liveness

Environment

  • BIG-IP configured as IPsec end-point
  • IKEv1 (DPD) or IKEv2 (Liveness)

Cause

Unexpected termination of Ipsec communication due to DPD/Liveness detection of network failure.

Recommended Actions

None

Additional Information

Details refer to DPD, equally you can use Liveness (IKEv2, rfc 5996 ).

If an IPsec peer declares support for DPD (and all remotely recent implementations should support DPD, rfc 3706 ) then it is only obliged to respond to incoming DPD requests. A peer can (if it wants) support DPD but not send DPD requests itself. Apart from responding to DPD requests, an IPsec installation can decide how it wants to implement DPD for checking liveliness of the remote peer.

BIG-IP supports DPD and it is not possible to disable that support.

The only configuration option is to configure dpd-delay under the ike-peer configuration. The default value is 30 (seconds).

If you configure dpd-delay of 0, then BIG-IP will not send any DPD requests and will only send DPD responses to incoming DPD requests from the remote peer. In this case, BIG-IP will not detect the loss of a remote peer and will not take any action based on DPD loss.

If you configure any other value (range 1 to 2147483647), then BIG-IP will send DPD at that configured interval. It will do this so long as it does not see a DPD request from the peer during that interval. ie: if the peer has a lower DPD interval, then BIG-IP will respond to the incoming DPDs and not send DPD itself.

The sending of DPDs by BIG-IP is not influenced by ingress ESP packets from the remote peer. ie: BIG-IP does not consider ingress ESP (data) packets to be proof of liveness of the remote peer.

For IKEv1: If a single DPD request from BIG-IP does not get a response from the remote peer, then it will retransmit the same request (with the same message_id (MID) number) every 4 seconds for 9 repeats: ie: after 4s, 8s, 12s, 16s, 20s, 24s, 28s, 32s & 36s. If at the end of the sequence (ie: after 40s from sending the first DPD request with the MID) then the remote peer is considered as dead and all SAs (phase 2 and phase 1) are deleted for that peer.

For IKEv2: If a single DPD request from BIG-IP does not get a response from the remote peer, then it will retransmit the same request (with the same message_id (MID) number) using incremental backoff, ie: after 1s, 2s, 4s, 8s, 16s & 32s. If at the end of the sequence (ie: after 63s from sending the first DPD request with the MID) then the remote peer is considered as dead and all SAs (phase 2 and phase 1) are deleted for that peer.

If you configure dpd-delay to be default (30s) then BIG-IP will detect a failure (and take action) 93 seconds after the last valid isakmp message seen from remote peer. Lowering the dpd-delay to 10s would reduce the total time to 73s.
