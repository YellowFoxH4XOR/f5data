K37190316: Bring Your Own NGINX App Protect WAF policy with NGINX Controller

Type
Knowledge
Published
2021-09-15
Updated
2023-02-21
Applies to
  • NGINX Products
  • NGINX Controller: 3.20.0
Source
https://my.f5.com/manage/s/article/K37190316

Topic

You should consider using this procedure under the following condition:

  • You have an existing NGINX App Protect WAF declarative JSON security policy that you want to use to configure the NGINX App Protect WAF instances to protect your Application Delivery Controller, ADC app components.

Description

Beginning with NGINX Controller 3.20.0, you can use the App Security Add-on for NGINX Controller ADC to Bring Your Own NGINX App Protect WAF policies into NGINX Controller. This lets you use your existing declarative JSON policies to protect your ADC app components.

Your existing security policies can be from NGINX App Protect WAF instances from another infrastructure, a custom security policy provided by the security team, or one exported and converted from BIG-IP Advanced WAF. For more information about converting security policies exported from BIG-IP Advanced WAF in XML format to JSON format, refer to The BIG-IP Advanced WAF security policies conversion tool section in K69732105: Create NGINX App Protect WAF security policies.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • Have NGINX Controller 3.20.0 or later licensed with the App Security Add-on, with one or more NGINX App Protect WAF instances already added to the NGINX Controller.
  • Have created the following resources in your NGINX Controller: Environment, Gateway, Certificates, App, and Components.
  • Have an existing NAP declarative JSON security policy. 
  • Have admin privileges to the NGINX Controller.

Procedures

  • Enable WAF for a component using your own NGINX App Protect WAF policy
  • Verify that WAF is enabled

Enable WAF for a component using your own NGINX App Protect WAF policy

To enable WAF functionality using the default security strategy, send a PUT request to the Components endpoint using a REST API client. To do so, perform the following procedure:

Impact of procedure: Enabling WAF security for a component protects the component. Production traffic is blocked based on the specifications in the WAF policy. F5 recommends that you perform this procedure during a scheduled maintenance window.

  1. Log in to a client system with a REST API client (for example, curl) installed.
  2. Use the following command syntax to authenticate to NGINX Controller to create the cookies file, cookie.txt:

    curl -k -c cookie.txt -X POST --url 'https://<Controller IP address or FQDN>/api/v1/platform/login' --header 'Content-Type: application/json' --data '{"credentials": {"type": "BASIC","username": "<username>","password": "<password>"}}'

    For example:

    curl -k -c cookie.txt -X POST --url 'https://controller.example.com/api/v1/platform/login' --header 'Content-Type: application/json' --data '{"credentials": {"type": "BASIC","username": "john@example.com","password": "C0mpl1catedPassw0rd"}}'

  3. To upload your NGINX App Protect WAF policy to the NGINX Controller, perform the following steps:
    1. Create and save your WAF security policy in a file, for example, exampleByoPolicy.json. You can find a sample WAF security policy in the NGINX documentation. Ensure that the name attribute in the metadata object is lower case.
    2. Upload your WAF security policy using the following command syntax:

      curl -k -b cookie.txt -d "@exampleByoPolicy.json" -X PUT --header 'Content-Type: application/json' https://<Controller IP address or FQDN>/api/v1/security/policies/<policyURI>

      For example, enter the following command:

      Note: <policyURI> must match the name attribute in the metadata object in exampleByoPolicy.json and both must have lower case characters.

      curl -k -b cookie.txt -d "@exampleByoPolicy.json" -X PUT --header 'Content-Type: application/json' https://controller.example.com/api/v1/security/policies/examplepolicy

  4. To create or update a security strategy with your WAF policy, perform the following steps:
    1. Create and save your security strategy API Spec in a file, for example, exampleStrategy.json, using the following syntax:

      Note: examplepolicy name must match the name in the previous procedure.
      {
          "metadata": {
              "name": "examplestrategy",
              "displayName": "Security Strategy",
              "description": "my special security strategy",
              "tags": [
                  "tag1",
                  "tag2"
              ]
          },
          "desiredState": {
              "content": {
                  "securityPolicyRef": "/security/policies/examplepolicy"
              }
          }
      }

    2. Apply the strategy API specification on the NGINX Controller using the following command syntax:

      curl -k -b cookie.txt -d "@exampleStrategy.json" -X PUT --header 'Content-Type: application/json' https://<Controller IP address or FQDN>/api/v1/security/strategies/<strategyURI>

      For example, enter the following command:

      Note: <strategyURI> must match the name attribute in the metadata object in exampleStrategy.json and both must have lower case characters.

      curl -k -b cookie.txt -d "@exampleStrategy.json" -X PUT --header 'Content-Type: application/json' https://controller.example.com/api/v1/security/strategies/examplestrategy

  5. To enable WAF and add your WAF security policy to an App Component, perform the following steps:
    1. Create a JSON file, component.json, that consists of the API Spec of the component you want to protect. You can get the JSON API Spec from the Component API endpoint of the NGINX Controller user interface or with an API call. For more information on creating this file, refer to the Additional Information section.
    2. Edit the component.json file to modify the security object, as follows, to enable WAF and to use the default security strategy:

      Note: examplestrategy must match the name you used in the previous procedure.

      "security": {
        "waf": {
          "isEnabled": true
        },u
        "strategyRef": {
          "ref": "/security/strategies/examplestrategy"
        }
      }

    3. To apply the changes, use the following command syntax:

      curl -k -b cookie.txt -d "@component.json" -X PUT --header 'Content-Type: application/json' https://<Controller IP address or FQDN>/api/v1/services/environments/<env_name>/apps/<<app_name>/components/<component_name>

      For example, enter the following command:

      curl -k -b cookie.txt -d "@component.json" -X PUT --header 'Content-Type: application/json' https://controller.example.com/api/v1/services/environments/exampleenv/apps/exampleapp/components/examplecomponent

Verify that WAF is enabled

To verify that the changes you made were applied successfully, perform the following procedure:

  1. Log in to your NGINX App Protect WAF instance.
  2. Enter the following command to search for app_protect in the nginx.conf file, for example, /etc/nginx/nginx.conf:

    grep app_protect /etc/nginx/nginx.conf

    You may observe output similar to the following example, indicating that the NGINX App Protect WAF is loaded and showing the name of the WAF policy file protecting your App Component:

    load_module modules/ngx_http_app_protect_module.so;
                            app_protect_enable on;
                            app_protect_security_log_enable on;
                            app_protect_security_log /etc/controller-agent/configurator/auxfiles/log-default.json syslog:server=127.0.0.1:514;
                            app_protect_policy_file /etc/controller-agent/configurator/auxfiles/examplepolicy.json;
                            app_protect_logging_str 'e:myenv;g:examplegw;a:exampleapp;c:examplecomp;r:$request_id;';

To verify that your bring your own (BYO) WAF policy is blocking traffic according to its specifications, make a simulated malicious request. To do so, perform the following procedure:

  1. From a client, access the app component URI with the following request, or a custom request, depending on your BYO WAF policy:

    Note: In this example, ensure that your BYO WAF policy is blocking scripts first.

    https://[gateway FQDN]<app component path>/?a=<script>

  2. Perform the following steps to review the WAF Security Events that correspond to the simulated malicious request:
    1. Log in to the NGINX Controller user interface.
    2. Select the NGINX Controller menu icon, then select Services.
    3. On the Services menu, select Apps.
    4. On the Analytics sub-menu, select Security Events.
    5. If you see a list of security violations and the outcome, this confirms that NGINX App Protect WAF are running.

Additional Information

You can retrieve the JSON API Spec of objects from either the user interface or command line interface of the NGINX Controller. For example, to retrieve the API Spec of an App Component object, perform one of the following procedures:

  • Retrieve the API Spec of an App Component from the NGINX Controller user interface
  • Retrieve the API Spec of an App Component from the command line interface

Retrieve the API Spec of an App Component from the NGINX Controller user interface

  1. Log in to the NGINX Controller user interface.
  2. Select the NGINX Controller menu icon, then select Services.
  3. On the Services menu, select Apps.
  4. Select the name of your App.
  5. Select Components.
  6. Select the name of your Component.
  7. Select Edit Config.
  8. Select API Spec.
  9. Copy the API Spec for your component.
  10. Select Cancel without making any changes.

Retrieve the API Spec of an App Component from the command line interface

  1. Log in to a client system with a REST API client (for example, curl) installed.
  2. Use the following command syntax to authenticate to the NGINX Controller and create the cookies file, cookie.txt:

    curl -k -c cookie.txt -X POST --url 'https://<Controller IP address or FQDN>/api/v1/platform/login' --header 'Content-Type: application/json' --data '{"credentials": {"type": "BASIC","username": "<username>","password": "<password>"}}'

    For example:

    curl -k -c cookie.txt -X POST --url 'https://controller.example.com/api/v1/platform/login' --header 'Content-Type: application/json' --data '{"credentials": {"type": "BASIC","username": "johnAdmin","password": "C0mpl1catedPassw0rd"}}'

  3. To retrieve the API Spec of your App Component, use the following command syntax:

    Note: The command pipes the output to jq. Install jq on your client system.

    curl -k -b cookie.txt --header 'content-type:application/json' https://<Controller IP address or FQDN>/api/v1/services/environments/<env_name>/apps/<<app_name>/components/<component_name> | jq

    For example, enter the following command:

    curl -k -b cookie.txt --header 'content-type:application/json' https://controller.example.com/api/v1/services/environments/exampleenv/apps/exampleapp/components/examplecomponent | jq

    You should see similar output to the following, containing the following three objects:

    {
       "metadata": {
          ...
       },
       "desiredState": {
          ...
       },
       "currentStatus": {
          ...
       },
    }

    If you need to use the API Spec in a subsequent PUT or POST command, remove the currentStatus object and save only the metadata and desiredState contents in a file:

    {
       "metadata": {
          ...
       },
       "desiredState": {
          ...
       },
    }
