Known Issue

The chassis manager daemon (chmand) leaks memory on BIG-IP systems containing the Always-On Management (AOM) subsystem. The memory leak occurs when the chmand process makes an RPC call to the AOM to collect media settings for internal interfaces. The memory leak occurs on all systems containing the AOM, regardless of whether the system is passing traffic or is idle.

The chmand process is responsible for tasks such as platform identification, device discovery, chassis sensor monitoring, and chassis configuration (management and serial interfaces).

This issue occurs when the following condition is met:

  • You are using the BIG-IP 1600, 3600, 3900, 6900, 8900, 8950, or 11050 platforms.

Impact

Performance may degrade over time and the system may eventually become unresponsive due to memory exhaustion.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • The memory allocation for the chmand process grows over time. Typically, the chmand process is allocated approximately 50 MB of memory after a restart or reboot. If you use the top utility, you can monitor the memory usage for the chmand process. To determine increases in memory usage over time, you should monitor the VIRT and RES field for BIG-IP version 10.x. For BIG-IP version 9.x, you should monitor the SIZE and the RES fields.

    For example, the following top command was run on a BIG-IP 1600 platform with an uptime of 56 days, and shows that the chmand process has consumed 115 MB of physical memory:

    top -p `pidof chmand` -b -n 1

    top - 10:36:57 up 56 days, 21:43, 1 user, load average: 0.57, 0.46, 0.45
    Tasks: 1 total, 0 running, 1 sleeping, 0 stopped, 0 zombie
    Cpu(s): 4.6%us, 5.7%sy, 0.0%ni, 89.6%id, 0.0%wa, 0.0%hi, 0.0%si, 0.0%st
    Mem: 4056352k total, 4028668k used, 27684k free, 24056k buffers
    Swap: 1048568k total, 7504k used, 1041064k free, 255664k cached

    PID USER PR NI VIRT RES SHR S %CPU %MEM TIME+ COMMAND
    3453 root 15 0 160m 115m 4556 S 0.0 2.9 4:52.83 chmand

  • Due to excessive memory allocation that may lead to swap pressure, TMM may miss answering watchdog polls and cause a reboot. The system may register log files that appear similar to the following example to the /var/log/ltm log file, indicating a TMM process heartbeat timeout:

    01140029:5: HA daemon_heartbeat tmm fails action is failover and restart

  • The system may reboot or fail over due to either a watchdog timeout or a memory leak, impacting other system daemons.

Resolution

Status

F5 Product Development has assigned ID 355152 to this issue, and has confirmed that this issue exists in the products listed in the Applies To box. For information about releases or hotfixes that resolve this issue, refer to the following table:

Type of FixFixes Introduced InRelated Articles
Release10.2.2K2200: Most recent versions of F5 software
Hotfix9.4.8 HF5K9502: BIG-IP hotfix matrix

Important: The AOM firmware version 10.1.8 or later provides part of the fix for the issue described in this article. Simply upgrading the AOM subsystem of the affected BIG-IP system to AOM version 10.1.8 or later does not resolve this issue. You must upgrade the affected BIG-IP system to BIG-IP 10.2.2 to completely fix the issue.

Workaround

To work around this issue, you can restart the chmand process. To do so, perform the following procedure:

Impact of workaround: Restarting the chmand process also restarts core BIG-IP system daemons such as TMM. Running this procedure interrupts traffic processing.

  1. Log in to the BIG-IP command line.
  2. To restart the chmand process, type the following command:

    bigstart restart chmand
