Topic

This article applies to BIG-IP 15.x and later versions. For information about other versions, refer to the following article:

  • K7301: Protecting the BIG-IP system against denial of service attacks (9.x - 11.3.x)

You should consider using this procedure under the following condition:

  • You want to detect and mitigate denial-of-service (DoS) and distributed denial-of-service (DDoS) attacks against the BIG-IP system.

Description

The BIG-IP system default configuration is secure; the system denies all traffic except for traffic types that you specifically configure the system to accept. Although the deny-by-default approach protects the resources managed by the BIG-IP system against attacks, remote attackers can initiate DoS or DDoS attacks. DoS and DDoS attacks attempt to make a machine or network resource unavailable to its intended users. The following procedures can help to detect and mitigate the effects of such attacks:

Types of DoS and DDoS attacks

The following table defines common DoS/DDoS attacks.

AttackDescriptionMitigation
SYN floodA SYN flood attack can exhaust system resources on the target device. The attacker attempts to exhaust all available resources used to establish TCP connections by flooding the target device with SYN packets that contain incorrect IP addresses.SYN cookie protection
ICMP floodThe ICMP flood (Smurf attack) attack directs ICMP echo request packets from remote locations to the IP broadcast address of an intermediary network device. If the intermediary device does not filter ICMP packets directed to IP broadcast addresses, all computer hosts on the network may receive the ICMP packet and send an ICMP echo response back.Maximum reject rate and virtual server IP rate class (Connection Rate Limiting).
Peer-to-peer attacksThe attacker instructs clients of large peer-to-peer file sharing networks to connect to the victim's website.The BIG-IP system is a port-deny device, and prevents many common exploits by not passing the attack through to the server.
IP fragmentation
attacks		Numerous IP fragmentation attacks can cause denial of service to networks.The BIG-IP system drops IP fragments that fail to meet a certain threshold, unless the fragment is the last in a communication.
SlowlorisThe Slowloris attack can monopolize all of the available request handling threads on the web server by sending HTTP requests that never complete. The Slowloris attack eventually consumes all of the web server's connection capacity.iRules can filter out well-known attacks.
UDP floodThe UDP flood attack is a common DDoS attack where multiple remote systems send a large flood of UDP packets to the target.UDP idle session timeout and virtual server IP rate class (Connection Rate Limiting).
Ping of deathThe Ping of death attack uses ICMP echo packets that are larger than 65,535 bytes. Because this is the maximum ICMP packet size that the system allows, systems that attempt to reassemble the packet can stop responding.The BIG-IP system is hardened to resist this attack. If the attack is against a virtual server with the Any IP feature enabled, then these packets are sent on to the server.
LandA Land attack is a SYN packet sent in which the source IP address is the same as the destination IP address.The BIG-IP system is hardened to resist this attack, and does not send this type of packet to the server.
TeardropThe Teardrop attack exploits an overlapping IP fragment problem present in some common operating systems. The problem causes the TCP/IP fragmentation re-assembly code to improperly handle overlapping IP fragments.The BIG-IP system correctly checks frame alignment and discards improperly aligned fragments to process these attacks.
Data attackA data attack is one or more attacks on a web server's content. The BIG-IP system acts as a port-deny device, and prevents many common exploits by not passing the attack through to the server.The BIG-IP system is a port-deny device, and prevents many common exploits by not passing the attack through to the server.
NukeA Nuke attack uses a modified ping utility to repeatedly send invalid ICMP packets to target systems, slowing down the affected computers in the process. For example, the WinNuke attack exploits the way certain common operating systems handle data sent to the NetBIOS ports.The BIG-IP system denies ports unless they are specifically enabled.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You can access the Configuration utility or the Traffic Management Shell (tmsh).

Procedures

You can perform the following tasks to detect and mitigate DoS and DDoS attacks on the BIG-IP system.

Detecting DoS and DDoS attacks

The BIG-IP system provides methods to detect ongoing or previous DoS and DDoS attacks on the system. To detect these attacks, perform the following procedures:

Verifying the SYN cookie status for a virtual server

The BIG-IP SYN cookie feature protects the system against SYN flood attacks and allows the BIG-IP system to maintain connections when the SYN queue begins to fill up during an attack. You can monitor the SYN cookie status for a virtual server, and determine whether the system has active hardware or software SYN cookies by checking the SYN cookie status for the virtual server. The possible values are listed in the following table.

SYN cookie statusDescription
OffThe SYN cookie feature is not currently engaged for the virtual server.
Full HardwareThe SYN cookie feature is currently engaged for the virtual server, and the system uses the HSB chip for SYN cookie processing.
Software Syncookie OnlyThe SYN cookie feature is currently engaged for the virtual server, and the system uses software for SYN cookie processing.

To verify the SYN cookie status for the virtual server, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Virtual Servers.
  3. Select the virtual server name.
  4. Select the Statistics tab.
  5. For statistics about hardware and software SYN cookies, and to find out whether SYN cookie protection is currently active, view the Syncookie Details section.

Reviewing SYN cookie threshold log messages

The BIG-IP system may log one or more error messages that relate to SYN cookie protection to the /var/log/ltm file. Messages that relate to SYN cookie protection appear similar to the following examples:

  • When the virtual server exceeds the SYN Check Activation Threshold, the system logs an error message similar to the following example:

    warning tmm5[18388]: 01010038:4: Syncookie threshold 0 exceeded, virtual = 10.11.16.238:80

  • When hardware SYN cookie mode is active for a virtual server, the system logs an error message similar to the following example:

    notice tmm5[18388]: 01010240:5: Syncookie HW mode activated, server = 10.11.16.238:80, HSB modId = 1

  • When hardware SYN cookie mode is not active for a virtual server, the system logs an error message similar to the following example:

    notice tmm5[18388]: 01010241:5: Syncookie HW mode exited, server = 10.11.16.238:80, HSB modId = 1 from HSB

Reviewing maximum reject rate log messages

The tm.maxrejectrate db key allows you to adjust the number of TCP RSTs or ICMP unreachable packets that the BIG-IP system sends in response to incoming client-side or server-side packets that cannot be matched with existing connections to BIG-IP virtual servers, self IP addresses, or Secure Network Address Translations (SNATs). A high number of maximum reject rate messages may indicate that the BIG-IP system is experiencing a DoS/DDoS attack.

The BIG-IP system may log error messages that relate to SYN cookie protection to the /var/log/ltm file. Messages that relate to SYN cookie protection appear similar to the following examples:

  • When the number of packets that match a virtual IP address or a self IP address exceeds the tm.maxrejectrate threshold, but the packets specify an invalid port, the system stops sending RST packets in response to the unmatched packets and logs an error message to the /var/log/ltm file that appears similar to the following example:

    011e0001:4: Limiting closed port RST response from 299 to 250 packets/sec

  • When the number of packets that match a virtual address and port, or a self IP address and port, exceeds the tm.maxrejectrate threshold, but the packet is not a TCP SYN packet and does not match an established connection, the system stops sending RST packets in response to the unmatched packets. The system also logs an error message to the /var/log/ltm file that appears similar to the following example:

    011e0001:4: Limiting open port RST response from 251 to 250 packets/sec

Mitigating DoS and DDoS attacks

The BIG-IP system provides features that allow you to mitigate DoS and DDoS attacks on the system. To do so, perform the following procedures:

Configuring adaptive reaping

The BIG-IP system allocates memory resources as connection flows are established. To prevent memory resource exhaustion, the system removes connection flows once the flows have been idle for longer than the configured idle timeout values. The adaptive connection reaping feature allows the BIG-IP system to dynamically adjust the criteria used to determine what connection flows to remove (reap) or prevent, and when to remove them.

Adaptive reaping (BIG-IP 11.6.0 and later)

Starting in BIG-IP 11.6.0, you can configure the adaptive connection reaping feature in an eviction policy. For information about the feature in BIG-IP 11.6.0 and later, refer to K15740: Overview of adaptive connection reaping (11.6.0 and later). To configure adaptive connection reaping on the BIG-IP system, perform the following procedure:

Note: You must license and provision the BIG-IP system with the BIG-IP LTM or the BIG-IP AFM module in order for the eviction policy list page to show up in the Configuration utility.

Impact of procedure: Improper threshold setting for high-water and low-water mark thresholds can result in system instability.

  1. Log in to the Configuration utility.
  2. Go to System > Configuration.
  3. For Local Traffic, select Eviction Policy List.
  4. Create a new eviction policy and enter the policy name you want.
  5. Configure the Trigger High-water Mark and Trigger Low-water Mark settings.

    Note: To disable adaptive connection reaping, set both the high-water and low-water values to 100.

  6. Select Finished.
  7. To associate the newly created eviction policy as the system-wide global eviction policy, go to System > Configuration > Local Traffic > General.
  8. From the Eviction Policy list, select the eviction policy you created.
  9. Select Update.

Adaptive reaping (BIG-IP 11.4.0 through 11.5.x)

Adaptive reaping allows the BIG-IP system to remove connections from its connection table when the connection load surpasses a defined percentage of memory usage. To mitigate DoS attacks, you can configure low-water mark and high-water mark thresholds, as follows:

  • The Reaper Low-water mark threshold determines the percentage of memory usage at which the system silently purges stale connections from the connection table. When the memory usage remains above the low-water mark, adaptive reaping becomes more aggressive and the BIG-IP system begins to purge active connections that are closest to their service timeout. The default low-water mark threshold value is 85%.
  • The Reaper High-water mark threshold determines the percentage of memory usage at which the system prevents new connections from being established. When the memory usage exceeds the high-water mark, the BIG-IP system does not accept new connections until the memory usage drops below the low-water mark threshold. The default high-water mark threshold value is 95%.

To configure adaptive connection reaping on the BIG-IP system, perform the following procedure:

Note: You must license and provision the BIG-IP system with the BIG-IP LTM module in order for the adaptive connection reaping feature to show up in the Configuration utility.

Impact of procedure: Modify the high-water/low-water mark threshold settings carefully; improperly configured threshold settings can result in system instability.

  1. Log in to the Configuration utility.
  2. Go to System > Configuration.
  3. For Local Traffic, select General.
  4. In the Properties section, configure the Reaper High-water Mark and Reaper Low-water Mark settings.

    Note: To disable adaptive connection reaping, set both values to 100.

  5. Select Update.

Configuring the SYN check activation threshold

SYN check threshold (BIG-IP 13.x and later)

The BIG-IP system includes Global SYN Check Threshold setting, which helps protects the system against SYN flood attacks. The Global SYN Check Threshold setting indicates the maximum number of allowed connections in the SYN queue. If that limit is reached, the BIG-IP system responds to SYN requests by sending the SYN-ACK response that contains an encoded secret back to the client. The system then discards the SYN queue entry and waits for the ACK from the client. The default value for the Global SYN Check Threshold setting is 64,000 connections. Additionally, you can configure the BIG-IP system to protect only certain virtual servers or VLANs against SYN flood attacks. For information about the different SYN check threshold features in BIG-IP 13.x and later, refer to K74451051: Configuring SYN cookie protection (13.x and later).

Note: You must license and provision the BIG-IP system with the BIG-IP LTM or the BIG-IP AFM module to access the Global SYN Check Threshold setting using the Configuration utility.

To adjust the Global SYN Check Threshold setting, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to System > Configuration.
  3. For Local Traffic, select General.
  4. For Global SYN Check Threshold, enter a value.
  5. Select Update.

SYN check threshold (BIG-IP 11.4.0 through 12.x)

The BIG-IP system includes the SYN Check Activation Threshold setting, which helps prevent the BIG-IP SYN queue from becoming full during a SYN flood attack. The SYN Check Activation Threshold setting indicates the number of new TCP connections that can be established before the BIG-IP system activates SYN cookie protection for subsequent TCP connections. When the BIG-IP system activates SYN cookie protection, the system does not need to maintain the SYN-RECEIVED state that is normally stored in the connection table for the initiated session. Because the system does not maintain the SYN-RECEIVED state, the SYN queue is not exhausted, and normal TCP communication can continue. The default value for the SYN Check Activation Threshold setting is 16,384 connections.

Note: You must license and provision the BIG-IP system with the LTM module to access the SYN Check Activation Threshold setting using the Configuration utility.

To adjust the SYN Check Activation Threshold, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to System > Configuration.
  3. For Local Traffic, select General.
  4. For SYN Check Activation Threshold, enter a value.
  5. Select Update.

Configuring the maximum reject rate

The tm.maxrejectrate database key allows you to adjust the number of TCP RST packets or ICMP unreachable packets that the BIG-IP system sends in response to incoming client-side or server-side packets that cannot be matched with existing connections to BIG-IP virtual servers, self IP addresses, or SNATs. The default value for the tm.maxrejectrate key is 250 TCP RSTs or 250 ICMP unreachable packets per second. The minimum value allowed is 1 and the maximum value is 1000.

To adjust the rate at which the BIG-IP system issues TCP RSTs or ICMP unreachable packets, perform the following procedure:

Impact of procedure: Increasing the tm.maxrejectrate threshold may cause the BIG-IP system to use more system resources during a DoS attack.

  1. Log in to tmsh by entering the following command:

    tmsh

  2. Adjust the tm.maxrejectrate database key by using the following command syntax:

    modify sys db tm.maxrejectrate value <value>

    For example, to change the tm.maxrejectrate to 200, enter the following command:

    modify sys db tm.maxrejectrate value 200

  3. Save the change by entering the following command:

    save sys config

Configuring the ICMP error rate

The tm.maxicmprate BigDB key can reduce the effects of a DoS attack by allowing you to limit the number of responses the BIG-IP LTM system sends for ICMP errors. The default value for the tm.maxicmprate BigDB key is 100.

To adjust the number of ICMP error responses from a BIG-IP system, perform the following procedure:

Impact of procedure: You use the tm.maxicmprate database key to protect BIG-IP system against DDoS attacks, so you use caution when increasing the limit on your BIG-IP system.

  1. Log in to tmsh by entering the following command:

    tmsh

  2. Adjust the tm.maxicmprate database key by using the following command syntax:

    modify /sys db tm.maxicmprate value <value>

    For example, to change the tm.maxicmprate to 200, enter the following command:

    modify sys db tm.maxicmprate value 200

  3. Save the change by entering the following command:

    save /sys config

Configuring protocol profile Idle Timeouts

Stale connection table entries can cause the BIG-IP system's memory utilization to increase, and leave fewer system resources available for legitimate connections. Lowering the Idle Timeout in the protocol profiles that are assigned to active virtual servers allows the BIG-IP system to remove stale connections from the connection table earlier and frees up system resources.

To adjust the Idle Timeout in a protocol profile, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Profiles.
  3. For Protocol, select the type of profile to modify (such as TCP).
  4. Select the name of the profile to modify.
  5. In the Settings section, select Specify from the Idle Timeout list.
  6. Enter the new timeout value.

    For example, to lower the TCP Idle Timeout from the default value of 300 seconds to a new value of 60 seconds, enter 60.

  7. Select Update.

Configuring TCP profile settings

TCP profile settings, including Maximum Segment Retransmissions and Deferred Accept, can mitigate DOS/DDOS attacks.

Maximum Segment Retransmissions

The Maximum Segment Retransmissions setting specifies the maximum number of data segment retransmissions that the BIG-IP system allows. The default is eight retransmissions. When the system exceeds the default number of retransmissions, the Traffic Management Microkernel (TMM) resets the TCP connection to avoid resource starvation during a potential DoS attack.

The Maximum Syn Retransmissions setting specifies the maximum number of times that the BIG-IP system retransmits a SYN packet when it does not receive a corresponding SYN-ACK. The default is four retransmissions.

To change either the Maximum Segment Retransmission setting or the Maximum Syn Retransmissions setting, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility
  2. Go to Local Traffic > Profiles.
  3. For Protocols, select TCP.
  4. Select the TCP profile to modify.
  5. Change the Maximum Segment Retransmission setting or the Maximum Syn Retransmissions setting.
  6. Select Update.

Deferred Accept

The Deferred Accept setting specifies that the BIG-IP system does not dedicate resources to the connection until the system receives the data packet from the client. This setting is useful when the system negotiates three-way handshake DoS attacks.

By default, the Deferred Accept setting is disabled on the BIG-IP LTM.

To enable the Deferred Accept setting, perform the following procedure:

Impact of procedure: The Deferred Accept setting is not compatible with some applications, such as FTP, POP3, or SMTP. For more information, refer to K4654: The Deferred Accept TCP Profile option may not be compatible with some applications.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Profiles.
  3. For Protocols, select TCP.
  4. Select the TCP profile to modify.
  5. Select the Deferred Accept check box.
  6. Select Update.

Configuring a virtual server IP rate class

A rate class is a rate-shaping policy that allows you to enforce a throughput restriction on incoming traffic. To implement a rate-shaping policy, you must create a rate class, and then apply the rate class to the virtual server. For example, you can create an IP rate class of 30 Mbps, with a maximum queue size of 2 Mbps.

To create a rate class, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Acceleration > Rate Shaping.
  3. Select Create.
  4. Enter a name for the Rate Class.
  5. For Base Rate, enter 2000000 (2 Mbps).
  6. For Ceiling Rate, enter 30000000 (30 Mbps).
  7. For Burst Size, enter 500 and then select Megabytes.
  8. For Direction, select Any.
  9. For Queue Discipline, select Stochastic Fair Queue.
  10. Select Finished.

You must now associate the rate class with the virtual server.

Configuring virtual server connection limits

Connection limits determine the maximum number of concurrent connections the system allows for a virtual server.

Note: The BIG-IP system sends a TCP reset in response to connection attempts to a virtual server for which the connection limit is reached.

To configure connection limits for the virtual server, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Virtual Servers.
  3. Select the virtual server to configure.
  4. For Configuration, select Advanced.
  5. Enter a connection limit.
  6. Select Update.

Understanding iRule mitigation

You can create an iRule that blocks or limits the number of requests that match a specific profile to filter out a specific connection-based DoS attack. If you can profile the requests that result from a particular DoS attack, then you can write an iRule that discards requests based on those specific criteria, such as source IP address or request pattern.

For example, using an iRule, the BIG-IP system can mitigate the effects of the Slowloris denial of service attack as detailed in K10260: Mitigating Slowloris DoS attacks with the BIG-IP system.

You can use the following example iRule definition syntax to rate limit the number of SIP request per IP address for a SIP configured virtual server.

when RULE_INIT {
    set static::maxQuery <max_query>
    set static::holdTime <hold_time>
}

when SIP_REQUEST {
    set SRCip "[IP::remote_addr]:sipdos"
    if { [table lookup $SRCip] != "" } {
        SIP::discard
        return
    }
    set currentTime [clock second]
    set sipKey "count:$SRCip:$currentTime"
    set connectionCount [ table incr $sipKey ]
    table lifetime $sipKey 2
    #log local0. "Count = $connectionCount source = $SRCip"
    # Uncomment the previous line to log request count by the iRule for the source ip address.
    if { $connectioCount > $static::maxQuery } {
        table add $SRCip "blocked" indef $static::holdTime
        log local0. "At $connectionCount $SRCip added to Table"
        #table delete $sipKey
        SIP::discard
        return
    }
}

Note: Replace <max_query> with the maximum number of queries allowed per IP address. Replace <hold_time> with the maximum amount of hold time to hold an offending request.

Note: After creating an iRule with the stanza, the affected SIP virtual server is configured with the iRule.
