Known Issue

The BIG-IP system may migrate an HTTP Class profile to a local traffic policy that matches more patterns than expected. This issue occurs when all of the following conditions are met:

  • The HTTP Class profile glob command does not contain the asterisk (*) operator.
  • The BIG-IP system migrates the configuration containing this HTTP Class profile during either an upgrade or a user configuration set (UCS) archive restoration.
  • The configuration is migrated to a BIG-IP version listed in the Applies To box.

When the BIG-IP system migrates the configuration containing the affected HTTP Class profile, the system generates a local traffic policy rule that uses the contain Condition operand instead of the equals Condition operand. For example, the following HTTP Class profile glob command should only match traffic with the exact URI path /test_test_test:

ltm profile httpclass /Common/test_rewrite_1 {
app-service none
asm disabled
cookies none
defaults-from /Common/httpclass
headers none
hosts none
paths { glob:/test_test_test }
pool none
redirect /test_rewritten
}

After the migration, the local traffic policy generated by the system based on this HTTP Class profile has the following rule, which matches traffic with any URI path that includes /test_test_test:

ltm policy /Common/test_rewrite_1 {
controls { forwarding }
requires { http }
rules {
test_rewrite_1_policy_rule {
actions {
1 {
http-reply
redirect
location /test_rewritten
}
}
conditions {
1 {
http-uri
path
contains
values { /test_test_test }
}
}
ordinal 1
}
}
strategy /Common/first-match
}

As a result, the policy erroneously matches traffic with URI paths, such as /test_test_test1 or /test_test_test_abc.

Impact

The BIG-IP system matches more traffic than expected.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • The BIG-IP system matches traffic with unexpected URI paths.
  • The local traffic policy rule generated by the system contains a condition that uses the contain Condition operand instead of the equals Condition operand.

Workaround

There is no workaround for this issue. However you can recover from this issue by modifying the affected local traffic policy to use the equals Condition operand instead of the contains Condition operand. To do so, perform the following procedure:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Policies > Policy List.
  3. Click the name of the affected local traffic policy.
  4. In the Rules section, click the name of the affected rule.
  5. Click the incorrectly generated condition in the Conditions list.
  6. Click Edit.

    The condition will clear from the Conditions list and the respective operands will populate with the previously configured condition values in the Conditions section.
  7. From the Condition menu, select equals.
  8. Click the URI path in the Values list.
  9. Click Delete.
  10. In the Values box, enter the URI path.
  11. To re-add the URI path back to the Values list, click Add next to the Values box.
  12. To re-add the modified condition back to the Conditions list, click Add above the Conditions list.
  13. To save the changes, click Update Rule.
