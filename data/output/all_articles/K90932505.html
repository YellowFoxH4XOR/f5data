Description

TLS version shown in wireshark could not indicate the TLS version the client actually supports, this can confuse the user and lead to thinking the client-side is sending an incorrect version of TLS and that's the reason the TLS handshake is not successful. For example:

BIG-IP: 1.1.1.1
POOL MEMBER: 2.2.2.2

11:10:30.972128    0    0.000012    3040    1.1.1.1    55467    2.2.2.2    443    TLSv1    379    OUT s1/tmm1 : Client Hello
11:10:30.972627    0    0.000499    3040    2.2.2.2    443    1.1.1.1    55467    TCP    157    443 → 55467 [RST, ACK] Seq=983821354 Ack=3528904392 Win=0 Len=0

The first packet shows "TLSv1" in wireshark, which is not accurate. The user may think Bigip doesn't use TLS 1.2 to start the TLS negotiation as it's configured in serverssl profile.


Here is an example of serverssl profile in this case. As you can see, the tls 1.0 and tls 1.1 is disabled and ciphers is set to tls 1.2 only.

ltm profile server-ssl /Common/serverssl_test {
    app-service none
    cipher-group none
    ciphers TLSv1_2
    defaults-from /Common/serverssl
    options { dont-insert-empty-fragments no-tlsv1.1 no-tlsv1 }
}

In fact, the BIG-IP does use TLS 1.2 to start the ssl. Here is a more expanded version of the client hello (sending by BIG-IP on server-side ssl)

TLSv1.2 Record Layer: Handshake Protocol: Client Hello
  Content Type: Handshake (22)
  Version: TLS 1.0 (0x0301)                       <-- envelop version
  Length: 512
  Handshake Protocol: Client Hello
    Handshake Type: Client Hello (1)
    Length: 508
    Version: TLS 1.2 (0x0303)                     <-- highest supported client version, for negotiation

+ The envelop version is just stating that the version of the envelope delivering the protocol negotiations is TLS 1.0.
+ The version in the Client Hello record layer stats the highest supported TLS version.

As BIG-IP is using TLS 1.2, why does wireshark show the client hello as TLSv1?

Here is the explanation found on wireshark website:

https://www.wireshark.org/lists/wireshark-users/201701/msg00004.html

Note: These links takes you to a resource outside of AskF5, and it is possible that the document may be removed or modified without our knowledge.

"
Browsing the SSL dissector's code it appears that the SSL session version is based on not just the client hello but also the server hello.  So it would seem that in file-c.pcap the server has responded that TLS v1.2 is used while in file-u.pcap either the server's response was not seen or responded that TLS 1.0 will be used.
"

So BIG-IP does use TLS 1.2 in this case. This is not the root cause for server reset the ssl handshake. The user should check other possible causes on the backend server.

Environment

  • TLS handshake is needed between two devices and multiple TLS versions are supported by the client-side.
  • No answer is received from the server-side.
  • Probably an RST is received or just a FIN. 
Cause

To initiate the TLS handshake the client  sends a Client Hello.

Wireshark application tags the TLS version based not only on the Client Hello but on the Server hello message, if only the Client hello is received wireshark could tag incorrectly the Client hello message causing the user may think the problem is on the client-side, but not necessarily, additional investigation should be performed to find out the actual reason the server-side is not accepting the Client hello message.

Recommended Actions

If you find out only client hello and no server hello, and the client hello is tagged in wireshark as TLSv1. Don't simply conclude the TLSv1 is the cause because the TLS handshake is not being successful.


Look at the client hello in detail, reviewing in the envelop level and the handshake level. Those different versions could be considered the minimum version (in the envelope) and the maximum version (in the handshake) that are supported by the client-side.  This concept of minimum and maximum version apply for TLSv1.0, TLSv1.1, and TLSv1.2, for TLSv1.3 is slightly different, you would see a maximum version of TLSv1.2 but a different set of ciphers.
