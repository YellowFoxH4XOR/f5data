Description

When using BIG-IP Local Traffic Manager (LTM), a virtual server is configured with a cookie persistence profile but no default pool. Instead, an iRule sends traffic directly to specific nodes. In this setup, the BIG-IP cookie is not inserted into HTTP responses because the HTTP Cookie Insert persistence method requires a pool to generate the cookie. When traffic bypasses the pool, the profile cannot insert the cookie, causing fallback to source-address persistence (if configured) or loss of session stickiness.

Environment

  • BIG-IP LTM
  • iRule
  • Cookie persistence (Insert persistence method)

Cause

The HTTP Cookie Insert persistence method is designed to work with pool members. If an iRule uses the node command to send traffic directly to a node, bypassing any pool, the persistence profile cannot encode pool member information into the cookie. As a result, no BIG-IP persistence cookie is inserted into HTTP responses, causing fallback on source-address persistence (if configured) or loss of session stickiness.

Recommended Actions

If you capture the traffic, you will notice that the following Set-Cookie is missing in the HTTP response header:

Set-Cookie: BIGipServer<pool_name>=<encoding>

To resolve this:

Modify the iRule to use the pool command instead of the node command, so that the HTTP Cookie Insert persistence method can function as intended.

For example, in iRule:

# Do NOT use:
node <ip_address> <port>

# Use this instead:
pool <pool_name>
