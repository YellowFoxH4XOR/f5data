Topic

This article applies to BIG-IP ASM 14.1.x and later. For information about other versions, refer to the following article:

  • K10550850: Mitigating credential stuffing attacks (13.x - 14.0.x)

You should consider using this procedure under the following condition:

  • You want to protect your login page from credential stuffing attacks.

Description

Credential stuffing is an attack in which the attacker uses compromised credentials (usually obtained through a data breach) and attempts to gain access to user accounts by injecting the credentials into web application login pages. The degree to which credential stuffing attacks are successful depends on the following factors:

  • Usernames and passwords are reused across multiple online accounts.
  • Poor/insecure passwords are frequently used.
  • Data breaches and credential spills increase in frequency.

Due to the previous factors, attackers can often use one piece of stolen credential information to unlock multiple online accounts. Once the accounts are unlocked, the attacker is able to steal information, such as credit card numbers, gift card balances, and other valuable information. The attacker can then repeat the process using the same sets of credentials on numerous different services.

For example, an attacker obtains a list of usernames and passwords obtained from a social media data breach. The attacker uses an automated credential stuffing tool to inject login requests across multiple sites. If credentials obtained in the data breach are reused on another site, such as a banking site, the attacker gains access to the user's bank account and drains funds from the account.

Users can mitigate many credential stuffing attacks by observing the following guidelines:

  • Close or delete unused online accounts
  • Do not reuse credentials across multiple online accounts
  • Use a secure password and regularly change passwords
  • Enable two-factor authentication for online accounts

If you suspect one of your login pages is under a credential stuffing attack, you can protect your login pages against internet bot traffic by configuring a Bot Defense profile and enabling the Proactive Bot Defense and Bot Signature Checking features.

Prerequisites

You must meet the following prerequisites to use these procedures:

  • You can access the Configuration utility.
  • You have configured a DNS resolver on the BIG-IP system to resolve DNS host names.
  • Client browsers accessing your web application are configured to accept JavaScript.
  • You suspect a login page is under credential stuffing attack and the malicious IPs are sourced from bots.

Procedures

  • Configuring Proactive Bot Defense
  • Configuring traffic policy to limit the DoS profile to login pages only
  • Assigning the created DoS profile and the traffic policy to the impacted virtual server

Configuring Proactive Bot Defense

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Security >  Bot Defense > Bot Defense Profiles.
  3. Click Create.
  4. Type a name for the Bot Defense profile.
  5. Click Advanced (14.1.x only).
  6. Click Blocking next to Enforcement mode.
  7. Select Balanced from the Profile Template list.
  8. Click Enabled next to Signature Staging upon Update.
  9. Define the settings for the Response and Blocking Pages section, as required.
  10. Click Bot Mitigation Settings and change the following mitigation settings, as needed:
    • Trusted Bot     
    • Untrusted Bot     
    • Suspicious Browser     
    • Malicious Bot     
    • Unknown
  11. Click Browsers (Browser Verification in 14.1.x) to change the following settings from their default values as needed:
    • Browser Access: For bot defense to work, monitoring of browser access and/or mobile applications must be enabled. The default is Allow.
    • Browser Verification: Determines whether JavaScript and header-based browser verification is performed. The default is Verify after Access.
    • Device ID Mode: Determines whether Device ID is collected by injecting JavaScript in the request or response. The default is Generate After Access.
    • Verification and Device-ID Challenges in Transparent Mode: Enable to allow challenges and JavaScript injection, even though Transparent Enforcement Mode is configured. The default is Disabled.  
    • Single Page Application: Enable if your website is a single page application. The default is Disabled.
    • Cross Domain Requests: Defines how the policy responds to cross domain requests. The default is Allow All Requests.
  12. Click Signature Enforcement. Use the filter to filter the list of signatures. Select one or more signature from the list and click Enforce or Stage and Save to change the enforcement setting.
  13. Click Save to save the Bot Defense profile.

Configuring traffic policy to limit the Bot Defense profile to login pages only

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Policies > Policy List.
  3. Click Create.
  4. Type a policy name.

    For example: LoginPBD

  5. For Strategy, click the appropriate option for your application environment.

    If you perform this procedure to only limit bot actions on login pages, you can use the default setting, Execute first matching rule.

  6. Click Create Policy.
  7. Under Rules, click Create.
  8. Type a name for the rule.

    For example: EnablePBD

  9. For Match all of the following conditions, click the Add icon (+).
  10. Choose the following controls:
    • HTTP URI
    • path
    • contains
    • any of
    • Add the application login URLs in the any of control.
    • at request time
  11. For Do the following when the traffic is matched, click the Add icon (+).
  12. Choose the following controls:
    • Enable
    • bot defense
    • Choose the Bot Defense profile that you created in the previous procedure.
    • at request time
  13. Click Save.
  14. Under Rules, click Create to a second rule.
  15. Type a name for the rule.
  16. For Match all of the following conditions, leave the default setting, All traffic.
  17. For Do the following when the traffic is matched, click the Add icon (+).
  18. Choose the following controls:
    • Disable
    • bot defense
    • at request time
  19. Click Save.

Assigning the created Bot Defense profile and the traffic policy to the impacted virtual server

Impact of procedure: Performing the following procedure activates PBD on the defined URLs in the traffic policy.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic > Virtual Servers > Virtual Server List.
  3. Click the name of the virtual server to which you want to associate the Bot Defense profile.
  4. Click the Security tab and click Policies.
  5. In the Bot Defense Profile list, click Enabled.
  6. In the Profile list, click the name of the profile you want to associate with the virtual server.
  7. Click Update.
  8. In the Resources column for the virtual server in question, click Edit.
  9. Under Policies, click Manage.
  10. In Available, click the local traffic policy you created in previous steps and move it to Enabled.
  11. Click Finished
