Security Advisory Description

Bypass/Injection vulnerability in Apache Camel. This issue affects Apache Camel: from 4.10.0 through <= 4.10.1, from 4.8.0 through <= 4.8.4, from 3.10.0 through <= 3.22.3. Users are recommended to upgrade to version 4.10.2 for 4.10.x LTS, 4.8.5 for 4.8.x LTS and 3.22.4 for 3.x releases. The vulnerability arises due to a bug in the default filtering mechanism that only blocks headers starting with "Camel", "camel", or "org.apache.camel.". Attackers can bypass this filter by altering the casing of letters. This allows attackers to inject headers which can be exploited to invoke arbitrary methods from the Bean registry and also supports using Simple Expression Language (or OGNL in some cases) as part of the method parameters passed to the bean. It's important to note that only methods in the same bean declared in the bean URI could be invoked. Mitigation: You can easily work around this in your Camel applications by removing the headers in your Camel routes. There are many ways of doing this, also globally or per route. This means you could use the removeHeaders EIP, to filter out anything like "cAmel, cAMEL" etc, or in general everything not starting with "Camel", "camel" or "org.apache.camel.". (CVE-2025-27636)

Impact

There is no impact; F5 products are not affected by this vulnerability.

F5 Product Development has evaluated the currently supported releases for potential vulnerability, and no F5 products were found to be vulnerable.

Security Advisory Recommended Actions

F5 recommends either of the following actions to mitigate the vulnerability for your backend pool members:

  • iRule
  • BIG-IP Next WAF / BIG-IP Advanced WAF/ASM / NGINX App Protect WAF signature

iRule

You can use the following iRule to mitigate the vulnerability for your backend pool members:

when HTTP_REQUEST {
   foreach header_name [HTTP::header names] {
       if {[regexp {^(?!camel|Camel|org\.apache\.camel\.)(?:[cC][aA][mM][eE][lL]|[oO][rR][gG]\.[aA][pP][aA][cC][hH][eE]\.[cC][aA][mM][eE][lL]\.)[\w.]*} $header_name]} {
           #log local0. "Blocked request - Header: $header_name"
           drop
           return
       }
   }
}

Note: To enable logging in the iRule, you can remove the pound sign (#) from the iRule logging command #log local0. "Blocked request - Header: $header_name" ; the iRule logging command should look like log local0. "Blocked request - Header: $header_name" after removing the #.

Note: This iRule may be updated based on the latest available information.

To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact to your system. However F5 recommends that you always test the iRule for your staging application environment before deploying it to your production application environment.

  1. Login to the BIG-IP Configuration utility.
  2. Navigate to Local Traffic > iRules > iRule List.
  3. Select Create.
  4. Enter a name for the iRule, for example, k000150304_irule.
  5. Copy the iRule provided prior to this procedure and paste it in the Definition setting.
  6. Select Finished to save the iRule.
  7. Navigate to Local Traffic > Virtual Servers > Virtual Server List.
  8. Select Edit... next to the name of the virtual server which you want to protect your backend pool members.
  9. Select Manage... for the iRules section.
  10. Locate the iRule which you have saved in step 6 in the Available box and select it. Then select << to move it to the Enabled box.
  11. Select Finished to save the change.

BIG-IP Next WAF / BIG-IP Advanced WAF/ASM / NGINX App Protect WAF signature

If you are using the BIG-IP Next WAF or BIG-IP Advanced Web Application Firewall (WAF) or BIG-IP ASM module or the NGINX App Protect WAF to protect your backend pool members, you can mitigate this vulnerability for your backend pool members by using the following attack signature enabled in blocking mode:

  • Apache Camel HeaderFilter bypass attempt, ID 200016013

This attack signature is part of the newly released attack signature update ASM-AttackSignatures_20250309_023422.im; you must perform a signature file update to ASM-AttackSignatures_20250309_023422.im or later for this signature to be available on your system.

For information about updating and managing attack signatures on the BIG-IP Next WAF system using the BIG-IP Next Central Manager, refer to the Attack Signatures for the BIG-IP Next guide.

For information about updating attack signatures on the BIG-IP system, refer to K82512024: Managing BIG-IP ASM Live Updates. For information about assigning attack signatures to security policies on the BIG-IP system, refer to the Assigning Attack Signatures to Security Policies chapter of the BIG-IP Application Security Manager: Attack and Bot Signatures guide.

Note: After you configure this attack signature, no further mitigation is necessary.
