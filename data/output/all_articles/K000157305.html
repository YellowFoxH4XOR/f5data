K000157305: Upon failover, newly active device fails to send out all required GARPs and does not process all traffic

Type
Support Solution
Published
2025-11-06
Updated
2025-11-26
Applies to
  • BIG-IP
Source
https://my.f5.com/manage/s/article/K000157305

Description

When a standby unit takes over as the active unit, the affected unit may fail to process all traffic, including some GARPs (Gratituous ARPs) for all Virtual Addresses and SNAT IPs.

This leads in a failed fail-over as traffic to/from virtual servers and SNATs become unreachable and some traffic will still be sent to the now standby unit.

 

Environment

VCMP guest

 

Cause

This could be an HSB issue.

In this observed case the standby guest unit started up successfully, but some tmms may fail to attach itself to all HSB PDEs (the HSB PDEs are essentially network interfaces for the tmms).

Therefore, when the standby takes over as active, it can only send out GARPS that is associated with healthy tmms, while tmms that do not have HSB PDEs attached cannot receive or send out any traffic.

Ideally this would be a cause for the system to remain offline instead of standby because ideally it should not be fit to receive traffic when some of the available tmms cannot attach itself to an HSB PDE. However, since the device continues to run after failing to attach to HSB PDEs, users may not be able to realize that the device is not operating optimally.

 

Symptoms

This log may appear in startup messages:

notice hsb2: F5 High Speed Bridge PDE device attach failed.

 

However, sometimes logs are logrotated out, so another way to determine if all tmms are healthy is to check if the HSB PDE is alive for all tmms on a vcmp guest. So another way is to look at the internal tmstat table by using the internal tmctl command.

Here's an example of the failure that shows some of the HSB PDEs are marked as zero (not alive):

 

$ clsh tmctl -d blade tmm/hsb_internal_pde_info -s name,hw_id,alive,tmm_id -K hw_id
  
  name   hw_id  alive
2/0.21  1      1
2/0.25  2      1
2/0.22  8      1
2/0.26  9      1
2/0.23  16     0
2/0.27  17     0
2/0.24  24     1
2/0.28  25     1

 

Recommended Actions

Verify if your unit is affected using the methods above.

Options to try:

  • It might be possible to clear a bad HSB condition by performing a hard reboot ( a blade reset ).
  • Upgrade to a version with the latest HSB bitfile.
  • If none of the above clears the issue, try moving the VCMP guest to a different blade that is not affected, and/or run an EUD to verify the hardware is operating normally.

While a future enhancement is planned to ensure that devices that startup with the errors aren't able to remain available as standby, we encourage current users to verify that the bootup logs do not contain the error PDE device attach failed (see above)
