When you configure a secure network address translation (SNAT) on a BIG-IP virtual server, the source address of each connection is translated to a configured SNAT address, and the source port is mapped to a port currently available for that address. If you only use one SNAT address, the system can handle a maximum of 65,535 concurrent connections.

Note: The port limit is not an IP limitation but a restriction of User Datagram Protocol (UDP) and TCP, since the port information is contained within a defined UDP and TCP header that limits the number of ports to 65,535. The source and destination port represented in UDP and TCP have 16 bits (2 ^ 16 = 65536), which is represented as 0 - 65535 available ports. However, when the Traffic Management Microkernel (TMM) is forced to perform a port lookup to find an unused ephemeral port, port numbers 0 to 1023 are not used.

The BIG-IP system is not restricted to this port limit because the limit applies separately to each SNAT address, and you can configure the BIG-IP system to use multiple SNAT addresses for a single virtual server.

Each TCP connection tuple must be unique and is defined by the following four parameters:

  • Source IP Address
  • Source Port
  • Destination IP Address
  • Destination Port

Because the uniqueness requirement includes more than source address and source port, the same source port may be used for two different connections with different destination addresses, as follows:

10.1.1.1:1234 ----> 10.1.1.10:80
10.1.1.1:1234 ----> 10.1.1.20:80

This behavior allows the BIG-IP system to potentially handle more than 65,535 concurrent connections per SNAT address when translating traffic bound for multiple service ports.

The TMM makes a limited number of attempts to locate a free port before closing the client-side connection. The tm.portfind.linear and tm.portfind.random system database variables affect this behavior. When an ephemeral port is already in use and port reuse is not set to use the preserve strict option, the BIG-IP system first attempts to find an available port by performing a linear search for X number of ports (based on the value of tm.portfind.linear). The system then attempts to find an available port by searching Y number of random ports (based on the value of tm.portfind.random).

For example, consider a connection on port 25000, with tm.portfind.linear and tm.portfind.random set to their default values of 16. The system would first sequentially check ports 25001, 25002, and so on, up to port 25016. If the system fails to find an open port, it then tries up to an additional 16 random ports. For the vast majority of cases and scenarios, this is an adequate number of ports to check. However, if both of these methods fail to locate an open port, the connection is reset and an the system logs an inet port exhaustion message. For more information about the error message, refer to K33355231: Error Message: 01010201:2: Inet port exhaustion on <ip_address> to <ipaddress:port> (proto <protocol>).

Note: Use caution when modifying these values. Increasing these variables may increase latency for connections and increase memory utilization. F5 recommends that you test any such changes during a maintenance window with consideration to the possible impact on your specific environment.

However, if the virtual server is set to preserve strict, then the system stops attempting to use any other ports and resets the connection.

Note: Servers that do not close connections gracefully, and other conditions outside of the BIG-IP system's control, may cause free ports to appear busy. F5 recommends that you configure multiple SNAT addresses or larger SNAT pools to prevent destination port exhaustion.
