K000156615: Preventing Idle connection race conditions between F5 XC and upstream endpoints

Description

I want to understand which party endpoint, origin server, downstream, or upstream closes the connection in idle scenarios.

Environment

  • F5® Distributed Cloud HTTP Load Balancer
  • F5 Distributed Cloud (XC)

Answer/Recommended Actions

The HTTP idle timeout configured on the XC Origin Pool should be shorter than the idle timeout configured on the upstream endpoint. This ensures that XC, not the origin, is responsible for closing idle connections.

If the origin closes an idle pooled connection at the same time XC attempts to reuse it for a new request, a race condition may occur.

Result:
A failure due to an illegal TCP state transition, typically logged as:

  • upstream_reset_before_response_started{connection_termination} OR
  • connection_failure

This manifests as an HTTP 503 error to the client.

Cause

In the diagram, the client sits downstream of the reverse proxy, which in turn sits downstream of the application server. For simplicity, the illustration mixes concepts from Layer 4 and Layer 7 of the OSI model.

The race condition occurs when the XC proxy attempts to reuse a keep-alive connection for Request 2 at the exact moment the application server’s idle timeout expires. The server closes the connection, sending a TCP segment with the RST flag.

The core issue is that the proxy is unaware the upstream has already closed the connection. If the proxy’s idle timeout were configured shorter than the server’s, the proxy would proactively terminate idle connections first, preventing the race and avoiding attempts to reuse a stale connection.

While conceptually simple with a diagram, this condition is notoriously hard to detect and troubleshoot, especially in environments where you don’t own or control all layers of the stack.

Additional Information

Example Scenario:

  • XC proxy idle timeout: 100 seconds
  • Upstream server idle timeout: 10 seconds
  1. The XC proxy selects a pooled connection that has been idle for 9.99 seconds.
  2. It begins writing a request to that connection.
  3. Simultaneously, the upstream server closes the connection due to its 10 second idle timeout.
  4. Instead of receiving an ACK, the reverse proxy receives a FIN while writing the request.
  5. The XC proxy aborts and returns an HTTP 502 to the client.
