Topic

You can use the LB::reselect iRules command in the LB_FAILED event to select a new load balancing target when the initial load balancing decision did not result in a successful connection to the chosen server. However, in BIG-IP versions prior to 13.1.0, using the LB::reselect command without some logic to limit the number of times a reselection is attempted can result in a SYN flood when no pool members are available to service the request. BIG-IP versions starting from 13.1.0 no longer present this issue, due to changes made in Bug ID 656898. See K42101213 for more details on this change in behavior.

Note: The LB_FAILED event is triggered when the BIG-IP LTM system is ready to send the request to a pool member and one has not been chosen (the system failed to select a pool or a pool member), is unreachable (when no route to the chosen pool member exists), or the selected pool member is non-responsive (fails to respond to a connection request).

Problematic logic

If the connection attempt to the originally selected pool member fails, and the iRule invokes the LB::reselect command in the LB_FAILED event with no limiting logic, the following sequence of events occurs:

  • The BIG-IP system will make a new load balancing selection based on the node or pool defined in the iRule
  • If a target is apparently available, it will be selected, and the BIG-IP system will attempt to make a new connection
  • If this connection also fails, the LB_FAILED event is triggered again
  • In the absence of some limiting mechanism, the BIG-IP system will attempt to make connections to the apparently available load balancing target as fast as it is able, up to the limitations of CPU and bandwidth

The following examples may result in a SYN flood if the reselected pool or node is not available:

  • Reselecting from the same pool upon each failure
  • Reselecting from a backup pool upon each failure
  • Reselecting a specific node upon each failure

Reselecting from the same pool upon each failure may result in SYN flood

Using the following iRule, a SYN flood can occur if all but one member of the default pool is marked down, and the last is still marked up or unknown but is not accepting connections:

when LB_FAILED {
  LB::reselect
}

Reselecting from a backup pool upon each failure may result in SYN flood

Using the following iRule, a SYN flood can occur if all but one member of the backup_pool pool is marked down, and the last is still marked up or unknown but is not accepting connections:

when LB_FAILED {
  LB::reselect backup_pool
}

Reselecting a specific node upon each failure may result in SYN flood

Using the following iRule, a SYN flood can occur if all but one member of the default pool is marked down, and the reselected node is not accepting connections:

when LB_FAILED {
  LB::reselect node 10.0.1.10
}

Recommended logic

When using the LB::reselect command in the LB_FAILED event, you should always include some logic that limits the number of times or the conditions under which the BIG-IP will attempt to connect to a new load balancing target when the initial load balancing decision fails.The following iRules are corrected versions of the examples in the Problematic logic section, which include the recommended logic:

  • Reselecting from the same pool upon failure, reselection attempts limited to the number of available pool members
  • Reselecting from a backup pool upon failure, reselection attempts limited to the number of available pool members
  • Reselecting a specific node upon each failure, reselection attempts limited to one attempt

In all cases, the client side connection will be reset after the last reselection fails.

Note: Use of the LB::mode rr command prevents reselection of the same member when reselection is required within the same pool.

Reselecting from the same pool upon failure, reselection attempts limited to the number of available pool members

Using the following iRule, a SYN flood is prevented by logic which limits the number of reselection attempts to the number of pool members currently available in the selected pool:

when CLIENT_ACCEPTED {
  set retries 0
}
when LB_FAILED {
  if { $retries < [active_members [LB::server pool]] } {
    LB::mode rr
    LB::reselect
    incr retries
  }
}

Reselecting from a backup pool upon failure, reselection attempts limited to the number of available pool members

Using the following iRule, a SYN flood is prevented by logic which limits the number of reselection attempts to the number of pool members currently available in the selected pool:

when CLIENT_ACCEPTED {
  set retries 0
}
when LB_FAILED {
  if { $retries < [active_members backup_pool] } {
    LB::mode rr
    LB::reselect backup_pool
    incr retries
  }
}

Reselecting a specific node upon each failure, reselection attempts limited to one attempt

Using the following iRule, a SYN flood is prevented if all but one member of the default pool is marked down, and the reselected node is not accepting connections:

when CLIENT_ACCEPTED {
  set retries 0
}
when LB_FAILED {
  # set number of desired retries to selected node below
  if { $retries < 1 } {
    LB::reselect node 10.0.1.10
    incr retries
  }
}

Note: Persistence may affect the ability of the system to reselect a new pool member from a pool for which persistence has been established for the connection. If persistence should be ignored on reselection, insert the persist none command before the LB commands, as in the following example:

when CLIENT_ACCEPTED {
  set retries 0
}
when LB_FAILED {
  if { $retries < [active_members [LB::server pool]] } {
    persist none
    LB::mode rr
    LB::reselect
    incr retries
  }
}
