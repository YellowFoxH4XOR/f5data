Description

Cross-Origin Resource Sharing (CORS) is a mechanism by which a web server can instruct a browser from which origins, other than its own, that the browser should permit the loading of resources. For more information, refer to K00350405: What is the Same-Origin Policy?

This can be useful if, for example, JavaScript code served from https://www.example.com wishes to use XMLHttpRequest to make a request for data from https://www.example.net/. Most browsers would disallow this for security reasons, by default, and this restriction can be overridden using the CORS headers.

Environment
A web application being delivered to a web browser on a client device (e.g., Chrome, Edge, Firefox etc)

Cause

  • None

Recommended Actions

Setting or modifying existing CORS headers should be undertaken only if there is a specific need (e.g., to alter security restrictions or allow specific functionality). For more information on specific F5 scenarios in which this may be necessary, please see the Related Content section.

Additional Information

CORS is useful in any situation where the browser, by default, will disallow a cross-origin request and you have a specific need to enable them, for example:

  • JavaScript use of XMLHttpRequest or the Fetch API to make requests for additional resources (e.g., data, page elements)
  • Font resources referenced within Cascading Style Sheets (CSS)
  • Drawing elements using the JavaScript drawImage() call

The CORS mechanism

The CORS standard defines additional HTTP headers which allow web servers to describe which origins are permitted to read and operate on the returned information within the browser. For requests that may cause server-side modification of data (e.g., methods other than GET), CORS requires that browsers conduct a “preflight” check, requesting supported methods from the server using the OPTIONS method prior to sending the actual request, and that the browser must abandon the request if the preflight check does not return approval. CORS also allows servers to specify which credentials (e.g., Cookies or HTTP Authentication) should be sent with cross-origin requests.
 
A CORS failure will result in an error condition, however client-side scripts are unable to retrieve specific details about the error – debugging CORS failures requires manual inspection of the browsers console or developer tools logs.

CORS headers

The CORS specification defines several HTTP headers. Headers you may see set in client requests are:
 
Origin: <origin>
 
This indicates the server from which the request is initiated, it should include only the server name and no path, e.g.: Origin: https://www.example.com
 
Access-Control-Request-Method: <method>
 
When issuing a preflight request, this header informs the server which HTTP method the client wishes to use for the actual request, e.g.: Access-Control-Request-Method: POST
 
Access-Control-Request-Headers: <field-name>[, <field-name]*
 
When issuing a preflight request, this header informs the server which HTTP header(s) will be used in the actual request, e.g.: Access-Control-Request-Headers: Content-Type, X-ForwardedFor
 
Headers you may see set in responses are:

Access-Control-Allow-Origin: <origin> | *
 
This header specifies either a single origin permitted to access this resource or, if the wildcard is specified (for requests without credentials) that all origins may access this resource, e.g.: Access-Control-Allow-Origin: https://www.example.com allows code from www.example.com to access this resource.
 
Access-Control-Allow-Expose-Headers: <header-name>[, <header-name>]*
 
This header grants JavaScript access to the contents of the specified header(s) in the returned response, e.g.: Access-Control-Allow-Expose-Headers: X-Custom-Header would allow JavaScript to access the contents of X-Custom-Header.
 
Access-Control-Allow-Methods: <method>[, <method>]*
 
In response to a preflight request, this header indicates which method(s) are permitted when accessing the resource, e.g.: Access-Control-Allow-Methods: POST, PUT
 
Access-Control-Allow-Headers: <header-name>[, <header-name>]*
 
In response to a preflight request, this header indicates which headers can be used when making the actual request – this is the server side response to the client side Access-Control-Request-Headers header.
 
Access-Control-Max-Age: <delta-seconds>
 
This header controls how long the results of a preflight request are considered valid and may be cached for, in seconds.
 
Access-Control-Allow-Credentials: true
 
This header controls whether or not the response to the request may be exposed to the browser when the credentials flag is true. For example, if a GET request is made for a resource with credentials and this header is not returned, then the response will not be exposed to the browser.
