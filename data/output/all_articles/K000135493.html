Description

This article provides the possible solutions when the Aspen Mesh Ingress gateway upgrades the connection to HTTP2 when you are using HTTP1.

 

Environment

Aspen Mesh 1.11.x 1.14.x

 

Cause

When you don't specify the name of the protocol on the service port, it can use a protocol that you don't want.

For example, this is the error seen when the Ingress Gateway upgrades the traffic to HTTP2 when it is not allowed on the application:

[2023-07-03T19:05:52.086Z] "GET  /path/path HTTP/2" 503 UC upstream_reset_before_response_started{connection_termination}

 

Also, on the Destination Rule, it can be specified to upgrade the connetion by setting the H2upgradepolicy to "UPGRADE"
 

Recommended Actions

To avoid the connection to upgrade the HTTP traffic, it is recommended to specify the protocol on the Service Ports names, by default, they should be in the format  <protocol>[-<suffix>]. 

This is the sevice when the error "503 UC upstream_reset_before_response_started" was seen because the application can't handle http2 connections:
 

kind: Service
metadata:
  name: myservice
spec:
  ports:
  - port: 80
    name: http2-80

This is the example of the service, specifying the proper protocol and port(http):
  
kind: Service
metadata:
  name: myservice
spec:
  ports:
  - port: 80
    name: http-80

As you can see, under "port > name", it was specified the protocol and port using the following http name formats:
 
Protocol   Sidecar PurposeGateway Purpose
httpPlaintext HTTP/1.1 traffic   Plaintext HTTP (1.1 or 2) traffic  
http2Plaintext HTTP/2 trafficPlaintext HTTP (1.1 or 2) traffic



Another recommended action to avoid connections http1 upgrading to http2, is to include the policy H2upgradepolicy to "DO_NOT_UPGRADE" on your destination rule yaml. For example:
 

kind: DestinationRule
metadata:
  name: example
spec:
  host: example-host
  subsets:
  - name: v1
    labels:
      version: v1
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL
    connectionPool:
      http:
        h2UpgradePolicy: DO_NOT_UPGRADE

 

     

    Additional Information

     

    To be a part of the service mesh, ports on pods and services in a Kubernetes cluster must satisfy the following requirements:
     

    • Named ports: Service ports must be named. The port names must be of the form <protocol>[-<suffix>] with http, http2, grpc, mongo, or redis as the <protocol> in order to take advantage of Istio's routing features. For example, name: http2-foo or name: http are valid port names, but name: http2foo is not. If the port name does not begin with a recognized prefix or if the port is unnamed, traffic on the port will be treated as plain TCP traffic (unless the port explicitly uses Protocol: UDP to signify a UDP port).
     
    • Service association: If a pod belongs to multiple Kubernetes services, the services cannot use the same port number for different protocols, for instance HTTP and TCP.


    For more detailed information about services requirements inside the istio mesh, please see the oficial istio and Aspen Mesh documentation listed under "Related Content"
