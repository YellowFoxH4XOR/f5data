Topic

You should consider using this procedure under the following condition:

  • You want to reduce the number false positive violations generated by the security policy.

Description

A false positive violation occurs when the BIG-IP ASM security policy detects a security violation for a valid request to the web application. The BIG-IP ASM system may report a false positive violation for a variety of reasons. For example, the system may report a false positive when a client sends a request for a web application entity, such as a file type, that is not defined in the security policy. The system may also report a false positive when a client sends a request for an entity that is included in the policy but the request attribute properties do not align with the entity properties as they are defined in the security policy.

Managing a small number of false positive violations is a normal part of building and maintaining a security policy, especially in the early stages of building the policy during the traffic learning period. However, an excessive number of false positives may indicate an issue with how the policy was deployed or configured.

Excessive false positive violations can be detrimental in the following ways:

  • The policy flags and blocks legitimate traffic.
  • The system consumes additional resources processing the false positive violations.
  • The administrator spends time investigating false positive violations.

False positive scenarios

One of the goals of an administrator is to accurately identify a false positive violation and decide whether to accept the learning suggestions and add the request to the security policy. For examples of possible false positive violations that you may encounter, refer to the following scenarios:

  • The entity is not included in the policy.

    Requests for entities that are not defined in the policy may cause false positive violations. For example, the following GET request contains the file type (jsonp) that is not defined in policy. As a result, the system may generate the Illegal file type violation.

    GET /path/file.jsonp?mod=profiles&id=1234 HTTP.1.1

  • The request does not match the defined entity.

    In some cases, false positive violations are caused by requests for an entity that is included in the policy, but the request attribute properties do not match the configured entity. For example, the policy includes a parameter named id with a defined maximum length of 10 bytes, and the request includes the same parameter with a length of 12 bytes. The following request may generate an Illegal parameter value length violation, although the request may not be malicious.

    GET /processTransaction?id=867530923454

  • An attack signature causes a false positive.

    Attack signatures are rules that identify attacks or classes of attacks. In some cases, a legitimate request to your web application causes the system to report a false positive for an attack signature. For example, you may have an internal script that triggers false positive violations using a non-browser client, such as cURL, to connect to your application. As a result, the system may generate the Attack signature detected (automated client access) violation.

  • A missing content profile causes a false positive.

    Content profiles allow you to define what elements the security policy enforces and considers legal when it detects traffic that contains specific types of data. In some cases, a request to your web application causes the system to report a false positive for specific types of data, such as XML content. For example, if your XML application has special requirements and you have not configured an XML profile for the policy, some XML requests may generate false positive violations.

Considerations for reducing false positives prior to building the policy

When you are preparing to build a security policy, the more you plan the policy building process in advance, the smoother the process and the fewer false positive violations you can expect to experience over time. For example, refer to the following considerations to prior to building the policy:

  • Have an understanding of the application(s) you want to protect.
  • Choose the appropriate security policy type and template for your application.
  • Make a list of the parameters, URLs, and other entities that are associated with the application.
  • Define your security requirements and how strict you want the policy to be. For example, fundamental or comprehensive.
  • Determine your ability to maintain the policy against your security requirements.

Note: For more information about planning and building a security policy, refer to the Supplemental Information section of this article.

Prerequisites

You must meet the following prerequisite to use this procedure:

  • You have access to the Configuration utility.

Procedures

Reducing false positives during the policy building period

During the policy building process, you can take proactive steps to minimize the number of false positive violations that occur in your environment. In general, the more you refine and tighten the security policy, the more false positive violations you are likely to encounter and the more time you spend reviewing them and maintaining your policy. The less you refine your policy, the fewer violations you are likely to encounter and the less time you spend maintaining it. To reduce false positives during the policy building period, perform to the following procedures:

Impact of procedure: Performing the following procedures should not have a negative impact on your system.

Choosing the appropriate Policy Builder learning speed

Choosing the appropriate Policy Builder learning speed for your environment creates a more accurate security policy and less false positives. For example, if your applications have a high number of unique visitors per day, using the Slow learning speed option builds a policy using higher thresholds for the rules and may prevent fewer false positives violations over time. To view or change the Policy Builder Learning Speed setting, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Security Policies > Policy List > Policy Name.

    Note: For BIG-IP 12.x through 14.x, go to Security > Application Security > Policy Building > Learning and Blocking Settings.

  3. Under General Settings, select the appropriate setting for Learning Speed.
  4. Select Save.
  5. Select Apply Policy.

Adding IP address exceptions

When you build the security policy, you should add IP address exceptions for IP addresses that you want the system to treat in a specific way. For example, you can create exceptions for IP addresses of internal tools, such as penetration tools, scanners, and web scraping tools. In general, you should add exceptions for all IP addresses from which the system should trust connections and for which you do not want the system to generate learning suggestions. Doing so decreases the number of false positive violations that the system generates over time. To add IP address exceptions, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Security Policies > Policies List > <policy_name> > Policy Configuration > IP Address Exceptions.
  3. Select Create.
  4. On the IP Address Exception Properties page, configure the IP address for which you want the system to treat in a specific way. For example, IP addresses for which you want to exclude information from the logs.
  5. Select Save.
  6. Select Apply Policy.

Adding and fine-tuning content profiles

If you create a security policy with the Learning Mode set to Automatic, the Policy Builder examines application content and adds content profiles, such as XML or JSON, as needed. For example, if the application uses HTTP as a transport layer for XML data, the policy builder should add a XML content profile to the policy. During the policy building process, you should verify that the system added the appropriate content profiles to the policy and make sure that the profiles are configured properly. Doing so can limit the number of false positive violations that the system generates. To add or fine-tune content profiles, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Content Profiles.
  3. Select the appropriate content profile type. For example, XML Profiles.
  4. Select the name of the content profile or add a new profile by selecting Create.
  5. Ensure that the profile is configured properly for your environment.
  6. Select Save.
  7. Select Apply Policy.

Adding and fine-tuning entities

If you create a security policy with Automatic Learning Mode, the Policy Builder automatically adds entities, such as URLs, file types, and parameters to the policy. During the policy maintenance period you may need to fine-tune the entities added by the Policy Builder and add additional entities that the Policy Builder did not add to the policy. Doing so helps the system build the policy with the right level of security and maintenance. For more information about building security policies with entities, refer to K74535942: Building web application security policies with entities.

Enabling Signature Staging

By default, the system puts new and updated attack signatures into staging. Staging means that the system applies the attack signatures to the traffic but does not block the requests that trigger those attack signatures. The default staging period is seven days. F5 recommends using attack signature staging to help reduce the number of false positives. When signatures match attack patterns during the staging period, the system generates learning suggestions. You can then view the learning suggestions, and, if you see that an attack signature violation has occurred, you can select the violation to see details about it and decide what to do about it. To verify that the attack signature staging setting is enabled, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Go to Security > Application Security > Policy Building > Learning and Blocking Settings.
  3. For Policy Building Settings, select Attack Signatures.
  4. Select the Enable Signature Staging check box.
  5. Select Save.
  6. Select Apply Policy.

Reducing false positives during the policy maintenance period

Periodically review the learning suggestions on the Requests page and Traffic Learning page to determine whether the violations are legitimate and caused by an attack or if they are false positives that indicate a need to update the security policy. Typically, a wide recurrence of violations at some place in the policy (with a low violation rating and a high learning score) indicates that they may be false positives, and you should change the policy to reduce them. If the violations indicate attacks (they have a high violation rating), the policy can remain as-is, and you can review the violations that it triggered.

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

Listing potential false positive violations

You can investigate potential false positives by reviewing violation ratings of illegal requests. Requests with a low violation rating (1 to 2) are more likely to be false positives that you may want to investigate and add to the policy if appropriate. The violation ratings are defined in the following table.

Violation ratingAction
5The request is most likely a threat so consider clearing any learning suggestions associated with it.
4The request looks like a threat but requires examination before clearing the suggestion.
3The request needs further examination before accepting learning suggestions to add the request to the policy.
2The request looks like a false positive but requires examination before accepting learning suggestions to add the request to the policy.
1The request is most likely a false positive. Review the request details and consider accepting learning suggestions to add this to the security policy.

To list potential false positive violations, perform the following procedure:

  1. Log in to the Configuration utility.
  2. Go to Security > Event Logs > Application > Requests.
  3. Select Open Filter (magnifying glass icon).
  4. From Requests List, adjust the Violation Rating slider to 1 to 2, and select Apply Filter.
  5. For Requests List, select a request to view information about the request and any violations associated with it.
  6. For Request Details, review violations associated with the request and other details, such as the violation rating, and potential attack types.
  7. For Request, review the request syntax and select the highlighted text to view the decoded request fields.
  8. Review the request details and determine whether the request is a false positive. To do so, refer to the guidelines in the following table.
Request detailsAction
The request matches an internal IP address.Consider adding IP address exceptions to the policy.
The request matches a web application entity that is not defined in the policy.Determine whether you need to add the entity to the policy.
The request matches a web application entity that is defined in the policy.Determine whether you need to reconfigure the entity.
The request matches specific types of data, such as XML or JSON content.Determine whether a content profile is required for your policy.
The request was triggered by an attack signature.Verify signature staging is enabled or whether you need to disable the signature for the specific entity.
The request was triggered by the CSRF protection feature.Ensure that the request is legitimate and originated from the web application itself and not from a selected link or embedded malicious HTML or JavaScript that resides on other web applications. Verify that the CSRF token is present in the request.
