Known Issue

The BIG-IP ASM system may erroneously block traffic when it fails to properly handle policies with the same name.

This issue occurs when all of the conditions are met for each of the following types of high availability (HA) configurations:

  • The BIG-IP ASM system is part of an HA configuration:
    • The affected system is part of a device group that is not enabled with Automatic Sync.
    • The devices in the device group are in sync.
    • You delete and recreate active security policies with identical names in different orders on a device.
    • You manually sync all changes to the other devices in the device group.
  • The BIG-IP ASM system is standalone:
    • You associate active security policies with their respective virtual servers.
    • A user configuration set (UCS) file is generated.
    • You delete the active security policies from the system.
    • You recreate new active security policies with the same names and associate them with the same virtual servers, but in a different order.
    • You load the previous UCS file on the system.
The following example provides the sequence of events that triggers this issue:
  • You create security policy A and associate it with virtual server 1.
  • You then create security policy B and associate it with virtual server 2.
  • A UCS file is generated.
  • Subsequently, you delete security policies A and B from the system.
  • You create security policy B and associate it with virtual server 2.
  • You create security policy A and associate it with virtual server 1.
  • You load the UCS file that was generated previously.

Impact

The BIG-IP ASM system blocks traffic and resets the affected TCP connections.

Symptoms

As a result of this issue, you may encounter one or more of the following symptoms:

  • Traffic is blocked, and TCP connections are reset unexpectedly with the following TCP RST cause:

    Internal error (ASM requested abort (plugin abort error))

  • You observe multiple instances of the following error logs in the /var/log/ts/bd.log file:

    bd_agent|ERR|...|F5::BdAgent::handle_bd_pipe_message,,Some records sent to enforcer were not handled
    ECARD|ERR   |...|account_id_table_management.cpp:0222|Failed to PUT table

Workaround

To work around this issue, you can deactivate and reactivate the affected security policy. Alternatively, you can restart the BIG-IP ASM service on the affected device. To do so, perform either of the following procedures:

  • Deactivating and reactivating the affected security policy
  • Restarting the BIG-IP ASM service
Deactivating and reactivating the affected security policy

Impact of workaround: Traffic may be briefly interrupted during the time the security policy is deactivated and reactivated.

  1. Log in to the Configuration utility of the affected device.
  2. Navigate to Security > Application Security > Security Policies.
  3. Select the affected security policy you want to deactivate.
  4. Click Deactivate.
  5. When prompted to confirm, click OK.
  6. Navigate to Local Traffic > Virtual Servers > Virtual Server List.
  7. Click the name of the virtual server that you want to reactivate the deactivated security policy.
  8. Click the Security tab, and then click Policies.
  9. For the Application Security Policy setting, select Enabled.
  10. For the Policy setting, select the desired deactivated security policy.
  11. To save the changes, click Update.

Restarting the BIG-IP ASM service

Impact of workaround: Traffic processing will be briefly interrupted during the restart.

  1. Log in to the TMOS Shell (tmsh) by typing the following command:

    tmsh

  2. Restart the BIG-IP ASM service by typing the following command:

    restart sys service asm
