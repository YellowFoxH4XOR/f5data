Description

Buffer overflows (CWE-120) are a class of vulnerabilities that can affect applications written in many programming languages, and the name describes any situation in which the software attempts to move data from one location in memory into a fixed-length buffer (in another location in memory) which is too small to hold the data.

Environment

Any software application.

Cause

  • Insufficient bounds checking when working with user-supplied data.

Recommended Actions

Since buffer overflows can affect such a vast array of applications it is impossible to give one-size-fits-all advice beyond ensuring that your application applies good bounds-checking when working with any user-supplied input. If we talk about web applications, specifically, however, it may be possible to mitigate buffer overflow attacks against a web application or web server using BIG-IP Advanced WAF, Silverline WAF etc to enforce length checks against user-supplied input (in the form of HTTP parameters, URIs, and headers). Specific instructions are outside of the scope of this document since any policy must be tailored to the web application in question.

If you are concerned about a known buffer overflow vulnerability in the BIG-IP Configuration Utility the best mitigation is to ensure your administrators:

  • Access the Configuration Utility from a dedicated management host, jump box or another controlled environment

Additional Information

Buffer overflow attacks can impact virtually any software application, so we cannot be exhaustive in our explanations here, but we can briefly cover a few of the most common scenarios.

Buffer overflows in Web Applications
It is entirely possible for a web application to be vulnerable to buffer overflow attacks, and the outcome will vary depending on what component is vulnerable and what language was used to create the vulnerable component.

It may be possible to cause a buffer overflow in the web application code, in which case the outcome might be to crash or influence the business logic of the application itself (usually only within the context of the user sending the request), but a more likely attack is against either the web server code or third-party libraries used by the web application (for example to generate images). In this scenario the impact may be to crash the web server and deny access to other users or use the buffer overflow to effect remote code execution against the target server and execute malicious code within the context of the web server application or third-party component (“Remote Code Execution”).
 
Buffer overflows in applications
You will probably more commonly find Buffer Overflows discussed in the context of software rather than web applications, and in this instance the impact is as we discussed above in the contest of web servers. If an attacker is able to cause a buffer overflow in an application, then they will be able to crash the application (either immediately or in a delayed fashion depending on the result of the overflow at a memory level) and, potentially, insert arbitrary code to be executed within the context of the application itself.

In the context of software running on a workstation that may lead to the attacker being able to execute code with the same rights as the user running the software, while in the context of a service running on a server (e.g., a daemon, in Unix or Linux) an attacker may be able to execute arbitrary code in the context of the user the service is running as. This is, in part, why it is not best practice to run daemons operating on untrusted input (for example, a web server) with root privileges. By limiting the privileges available to the process (by running as a less privileged user or by implementing security features such as selinux) you immediately limit the impact of any as-yet unknown or unpatched buffer overflow being exploited.

Affected Environments

As we have seen above, almost all applications, web servers, and environments are potentially susceptible to buffer overflows. The exception to this rule comes in the form of interpreted languages such as Python; here, it is not the application itself which may be susceptible but the underlying interpreter – i.e., Python code is considered safe, but this does not preclude the possibility of a buffer overflow vulnerability in the Python run-time itself as this was written in a lower-level programming language.

Examples
The simplest example of a buffer overflow is as follows:

char buf[100];
gets(buf);
The above snippet of C code shows the programmer allocating a fixed-size buffer of 100 bytes before copying an arbitrary amount of data from STDIN (provided by ‘gets()’) into that buffer. The only control on the amount of data inserted into the buffer is trust in the user or process providing the data, and attempting to copy more than 100 bytes into ‘buf’ will lead to an immediate buffer overflow – as written here, this would be a Stack Overflow (CWE-121, see also K40055166).

Buffer overflows do not only affect buffers allocated from the stack (as above) but affect fixed-size buffers allocated in any area of memory where there is insufficient bounds checking during a copy or move of data into that buffer. For example:

#define BUFSIZE 512
…
char *buf;
buf = (char *)malloc(sizeof(char)*BUFSIZE);
gets(buf);
Here we are defining a 512-byte (assuming a character to be a single byte) buffer and, again, reading from STDIN into that buffer without any bounds checking. This time, however, the buffer has been dynamically allocated in the heap using the ‘malloc’ call and so an overflow is unlikely to lead to an immediate crash unless the amount of data read is so large that the heap space is exhausted. Instead, the most likely outcome is unpredictable operation following the overflow unless the attacker applies additional techniques to achieve code execution via a crafted Heap Overflow (CWE-122, see also K53293427)
 
Mitigations
If you wish to protect an application against buffer overflows attacks and cannot use Advanced WAF or a similar product to enforce bounds checking on input then you should build this functionality into the application itself:

  • Ensure that all input is subject to sufficient bounds checking
  • Ensure that any memory copy related code is subject to sufficient bounds checking, and do not rely on earlier checks on the original input length
  • Ensure that any application is compiled with all available compiler protections, e.g., stack canaries, NX-bit, ASLR/PIE etc

OWASP has additional advice for this in their Buffer Overflow cheat-sheet.
