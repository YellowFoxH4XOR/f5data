K000161961: VLAN Tag Corruption on Ingress After Expanding vCMP Guest to Two Blades on VIPRION Chassis

Type
Support Solution
Published
2026-06-29
Updated
2026-06-29
Source
https://my.f5.com/manage/s/article/K000161961

Description

After expanding a vCMP guest from one blade to two blades on a VIPRION chassis running BIG-IP 17.1.3, approximately 33% of ingress traffic arriving on the newly added blade arrives at the guest TMMs with an incorrect VLAN tag. In the case analyzed, traffic that should be tagged VLAN 1024 arrives tagged VLAN 1026. VLAN 1026 is not configured anywhere on the F5 system or the upstream switch.

Because no egress path exists for the unexpected VLAN, the BIG-IP correctly drops all traffic carrying that tag. In the case analyzed, this resulted in approximately 17.7% of total DNS queries going unanswered.

The issue begins 2 to 3 weeks after the blade expansion and is not resolved by restarting the vCMP guest. A full chassis reboot resolves the issue. This behavior matches Bug ID891333: The HSB on BIG-IP platforms can get into a bad state resulting in packet corruption.

Environment

  • BIG-IP LTM
  • VIPRION chassis with B4450N blades
  • Issue isolated to the newly added blade only; the original blade operates normally

Cause

The root cause is a hardware-level bit corruption in the High-Speed Bridge (HSB) FPGA on the affected VIPRION blade, as documented in Bug ID891333.

Answer/Recommended Actions

Rebooting the affected blade clears the HSB state and resolves the VLAN tag corruption. In the case analyzed, rebooting the entire chassis resolved the issue on the affected blade.

Note that rebooting only the vCMP guest has no effect. The vCMP host on the affected blade, or the entire chassis, must be rebooted to clear the HSB state.

After the reboot, monitor the system for recurrence. If the issue returns after a reboot, the blade hardware may need to be replaced via RMA, as documented in the Bug ID891333 guidance.
