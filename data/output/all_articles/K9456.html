Known Issue

Using the HTTP::respond iRules command in the LB_FAILED event may result in truncated responses.

This issue occurs when all of the following conditions are met:

  • The HTTP::respond command is used within the LB_FAILED event to return a large response.
  • No other TCP data has been sent to the client.

Impact

The response sent by the BIG-IP system will be truncated.

Symptoms

As a result of this issue, you may encounter the following symptom:

  • The correct Content-Length header value is always inserted, but the response itself is truncated at twice the Maximum Segment Size (2 * MSS, or two full packets).

Workaround

To work around this issue, you can disable the TCP Slow Start option in the TCP profile that is associated with the virtual server.

If disabling the TCP Slow Start option is not a viable option for your environment, you may be able to modify your iRule.

Impact of workaround: Changing the design of an iRule may have additional effects on traffic processing. Ensure any modification is compatible with your environment.

For example, instead of directly using the HTTP::Respond command to send a large response inside of an LB_FAILED event, you can instead perform a 302 Redirect to another URI, which can then be handled by an event that is unaffected by this issue.

Refer to the following iRule example:

when LB_FAILED {
   HTTP::respond 302 Location "http://www.example.com/sorry.html"
}

when HTTP_REQUEST {
   if {[HTTP::uri] equals "/sorry.html"} {
      HTTP::respond 200 content "START  [string repeat "X" 10000] END"
   }
}
