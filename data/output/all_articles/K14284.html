This article applies to BIG-IP DNS (formerly BIG-IP GTM) 11.x through 17.x . For information about other versions, refer to the following article:

  • K10721: Overview of the Longest Match algorithm (9.x - 10.x)

When you enable topology load balancing, the BIG-IP DNS system sorts topology records using the longest match algorithm. The longest match algorithm requires the system to evaluate all records in the topology statement and use the record that most completely matches the source IP address of the name resolution request. In the event that a name resolution request matches more than one topology record, the BIG-IP DNS system uses the destination object with the highest weight (score) to determine which statement to use to load balance the request.

When the Longest Match option is enabled, the BIG-IP DNS system automatically sorts the topology records in the following manner:

Note: The score values in the following topology statements are for example purposes only.

  • The system sorts wildcard records to the bottom of the list.

    For example, any records containing a 0.0.0.0/0 address statement appear at the bottom of the list as follows:

    ldns: subnet 0.0.0.0/0 server: subnet 10.0.0.0/8 { order 14 score 100 }

  • The system sorts entries containing a negation in the Local Domain Name System (LDNS) section of the record above any wildcard entries, but below other entries.

    For example, the following record includes a negation in the LDNS section of the record:

    ldns: not country BR server: pool /Common/Pool-C { order 12 score 100 }

  • The system sorts entries containing a negation in the server section of the record above any LDNS negation records.

    For example, the following record includes a negation in the server section of the record:

    ldns: continent SA server: not pool /Common/Pool-B { order 11 score 100 }

Note: You can view topology records by running the following tmsh command:

tmsh list /gtm topology all

After the BIG-IP DNS system sorts the records containing the above criteria, it compares the LDNS section of the topology statement. If the priority is the same for entries in the LDNS section, the BIG-IP DNS system compares the server section of the topology statement for the entries. The sorting for both the LDNS and server sections of the statement is as follows from highest priority to lowest:

  • An IP subnet is highest priority. If both records are IP subnets, the longest netmask has the higher priority. The system sorts wildcard IP subnets below other IP subnets but above other LDNS and server types.

    For example, given the following records, the record containing the 10.10.10.10/32 subnet is given a higher priority due to the /32 bit netmask:

    ldns                 server           score
    country."AU"              10.10.10.10/32    100
    country."AU"              10.10.0.0/16      100

  • By type from highest to lowest priority:
    • Datacenter
    • Pool
    • Region
    • ISP
    • Geolocation ISP (BIG-IP DNS 12.1.x and later only)
    • State
    • Country
    • Continent

  • If multiple server statements match, the BIG-IP DNS system uses the LDNS criteria to sort the records, which appear similar to the following example:

    ldns                   server              score
    pool."gtm_pool"                  10.10.10.10/32      100
    user."userregion"              10.10.10.0/24      100
    ISP."Comcast"                           10.10.20.10/24      100
    country."US"                              10.10.0.0/16     100
    c    ontinent."Europe"             10.10.30.10/16      100

  • If multiple LDNS statements match, the BIG-IP DNS system uses the server criteria to sort the records, which appear similar to the following example:

    ldns                server              score
    10.10.10.10/32                  10.10.10.0/24        100
    10.10.10.10/32                  10.10.0.0/16         100
    10.10.10.10/32                  dc."mydc"            100
    10.10.10.10/32                  continent."Africa"   100
    10.10.0.0/16                      user."userregion"    100
    10.10.10.0/24                    country."AD"         100
