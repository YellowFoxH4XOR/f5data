Description

When a pool member in a BIG-IP LTM high availability (HA) cluster is set to "Force Offline" and then re-enabled, the standby cluster member may log an incorrect downtime period for the pool member's monitor status. The standby device can display a downtime duration that is significantly longer than the actual period, while the active device logs the correct downtime. For example, after approximately 6 minutes of downtime, the standby device may log:

monitor status up. [ ... up ] [ was down for 0hr:13mins:4sec ]

while the active device correctly logs:

monitor status up. [ ... up ] [ was down for 0hr:5mins:49sec ]

The affected standby device shows downtime in brackets as a change between the last and current active/enabled/UP state, as shown in another example below:

Jun  5 13:28:47 Hostname notice mcpd[6499]: 01070639:5: Pool Pool_name member Some_member_name session status enabled.
Jun  5 13:28:47 Hostname notice mcpd[6499]: 01070727:5: Pool Pool_name member Some_member_name monitor status up. [ /Common/gateway_icmp: up ]  [ was down for 0hr:2mins:50sec ]

in the meantime, this node was again forced offline:
Jun  5 13:36:57 Hostname notice mcpd[6499]: 01070639:5: Pool Pool_name member Some_member_name session status forced disabled.

Enabled again:
Jun  5 13:37:01 Hostname notice mcpd[6499]: 01070639:5: Pool Pool_name member Some_member_name session status enabled.
Jun  5 13:37:01 Hostname notice mcpd[6499]: 01070727:5: Pool Pool_name member Some_member_name monitor status up. [ /Common/gateway_icmp: up ]  [ was down for 0hr:8mins:14sec ]

If we take 13:37:01 - 13:28:47 = it is exactly the time  "was down for 0hr:8mins:14sec". The real downtime was about 4 seconds and should be counted from the last offline/down/forced offline state. This can also be confirmed on the active device:

Jun  5 13:37:01 Hostname notice mcpd[6718]: 01070727:5: Pool Pool_name member Some_member_nam monitor status up. [ /Common/gateway_icmp: up ]  [ was down for 0hr:0min:5sec ]

Environment

  • BIG-IP LTM
  • HA Cluster

Cause

This issue is caused by a synchronization or state-tracking problem between the active and standby cluster members in an HA pair. The standby device may not correctly reset or update its internal timer for pool member state changes after actions such as "Force Offline" and "Enable." As a result, it accumulates or miscalculates the downtime period, leading to inaccurate log entries. The issue is most probably associated with the following Bug ID 906449.

Recommended Actions

Basically, if you hit this issue, the downtime in brackets is wrong, because it shows time between enabled/UP statuses and not real downtime. The real downtime is between the last down/offline state and the current enabled/UP state. 

As a temporary workaround, rely on the active device’s logs for accurate downtime information until an official fix or update becomes available. If you need to follow logs on the standby device, check timestamps of the events instead of downtime logged in brackets as "[ was down for 0hr:13mins:4sec ]".
