Topic

You should consider using these procedures under the following condition:

  • You need to collect HTTP traffic data from a BIG-IP system for self-analysis or as requested by F5 Technical Support.

    Important: These tasks require access to the Advanced Shell (bash).

Description

Before you can collect HTTP captures, you must determine if the HTTP client's original IP address arrives at the BIG-IP virtual server unaltered or translated.

If the HTTP client's original source IP address arrives unaltered at the virtual server, use the following command syntax to capture traffic at the BIG-IP system:

tcpdump -vvv -ni 0.0:nnn -s0 host <Client_IP_Address> or host <P1_ADDRESS> or host <P2_ADDRESS> -w /var/tmp/capture.cap

If the HTTP client’s original source IP address arrives translated at the virtual server, then all inbound traffic to that virtual server appears to come from the network address translation (NAT) address and it is impossible to distinguish a single client's connection. In this scenario, use the following command syntax to capture traffic at the BIG-IP system:

tcpdump -vvv -ni 0.0:nnn -s0 host <VS_ADDRESS> or host <P1_ADDRESS> or host <P2_ADDRESS> -w /var/tmp/capture.cap

In these syntaxes, <Client_IP_Address> is the original client source address, <VS_ADDRESS> is the IP address of the virtual server, and <P1_ADDRESS> and <P2_ADDRESS> are the pool members used by this virtual server. If there are more than two pool members, you must add more "or host" entries with the relevant IP address for the host.

Determining the expected connection flow

There are three common methods for an HTTP client to reach a pool member via the BIG-IP system.

  • Unencrypted: Plain, unencrypted traffic is sent to and from clients and servers.
  • SSL terminated: Encrypted SSL traffic arrives from the client, is processed by the client_ssl profile, and then is sent to the pool member as decrypted traffic.
  • SSL bridged: Encrypted SSL traffic arrives from the client, is decrypted and processed by the client_ssl profile, is re-encrypted by the server_ssl profile, and then is sent to the pool member as encrypted traffic.

Procedures

Depending on the type of expected HTTP connection flow, use one of the following procedures:

  • Capturing plaintext HTTP communications
  • Capturing SSL-terminated HTTPS communications
  • Capturing SSL-bridged HTTPS communications (terminate SSL from clients and re-encrypt to servers)

After you capture the HTTP traffic, perform the following procedure:

  • Using Wireshark to view ssldump captured data

Capturing plaintext HTTP communications

Perform this procedure when the virtual server receives plain, unencrypted traffic and sends it to pool members as unencrypted traffic.

Impact of procedure: You should enable debug logging temporarily, while performing troubleshooting procedures, and then disable debug logging after the procedure is complete. Failure to revert logging levels can lead to system performance degradation. For more information, refer to K15530: Debug logging and BIG-IP system resource utilization.

  1. Clear your client browser cache.
  2. Log in to the command line.
  3. Enable the reset cause logging feature on the BIG-IP system by typing following commands:  

    tmsh modify /sys db tm.rstcause.log value enable
    tmsh modify /sys db tm.rstcause.pkt value enable

  4. Start a tcpdump capture on the BIG-IP system using the following command syntax:

    tcpdump -vvv -ni 0.0:nnnp -s0 host <client_ip> -w /var/tmp/<vs_name>_outage.pcap   

    In this syntax, <client_ip> is the IP address of the HTTP client you are testing from, and <vs_name> is the name of the virtual server you are connecting to.

  5. While the capture runs, reproduce the issue you want to capture and press CTRL+C to stop the capture.
  6. Disable the reset cause logging feature on the BIG-IP system by typing the following commands:   

    tmsh modify /sys db tm.rstcause.log value disable
    tmsh modify /sys db tm.rstcause.pkt value disable

For more information about using tcpdump, refer to K411: Overview of packet tracing with the tcpdump utility.

Capturing SSL-terminated HTTPS communications

Perform this procedure when encrypted SSL traffic arrives from the client, is decrypted by the client_ssl profile, and then is sent to the pool member as decrypted traffic.

Impact of procedure: You should enable debug logging temporarily, while performing troubleshooting procedures, and then disable debug logging after the procedure is complete. Failure to revert logging levels can lead to system performance degradation. For more information, refer to K15530: Debug logging and BIG-IP system resource utilization.

  1. Clear the browser cache in the HTTP client you are testing from.
  2. Log in to bash as the root user.
  3. Enable the SSL debug feature on the BIG-IP system by typing the following command:

    tmsh modify /sys db log.ssl.level value debug

  4. Enable the reset cause logging feature on the BIG-IP system by typing the following commands:

    tmsh modify /sys db tm.rstcause.log value enable
    tmsh modify /sys db tm.rstcause.pkt value enable

  5. To decrypt SSL traffic captures from the client side using the ssldump utility, you must temporarily modify the SSL profile to specify a custom cipher-string: NONE:AES128-SHA.

    For more information about this change, refer to one of the following articles for your BIG-IP version:

    Important: Configuring the profile to use only a specific protocol causes connection failures for clients that do not support that protocol.

    K01770517: Configuring the cipher strength for SSL profiles (14.x)
    K17370: Configuring the cipher strength for SSL profiles (12.x - 13.x)
    K13171: Configuring the cipher strength for SSL profiles (11.x)

  6. If the traffic is not NAT'd, start the tcpdump capture on the BIG-IP system using the following command syntax:

    tcpdump -vvv -ni 0.0:nnnp -s0 host <Client_IP_Address> -w /var/tmp/<VS_ADDRESS>_outage.pcap

    In this syntax, <Client_IP_Address> is the IP address of the computer you are testing from, and <VS_ADDRESS> is the name of the virtual server you are connecting to.

  7. While the capture runs, reproduce the issue you want to capture and press CTRL+C to stop the capture.
  8. Run the ssldump command to decrypt the SSL tcpdump. To do so, use the following command syntax with the -M option to create a pre-master secret key log file:

    ssldump -r <path_to_capture_file>.cap -k <path_to_private_key> -M <path_to_pre-master-key-log-file>

    For example, the following ssldump command reads the www-ssl-client1.cap capture file using the test.org key file to decrypt the session and creates the PMS log file named client1.pms:  

    ssldump -r /var/tmp/www-ssl-client1.cap -k /config/filestore/files_d/Common_d/certificate_key_d/\:Common\:test.org.key_1 -M /var/tmp/client1.pms

    For more information about using tcpdump, refer to K411: Overview of packet tracing with the tcpdump utility. For more information about the ssldump utility, refer to K10209: Overview of packet tracing with the ssldump utility.

  9. Download the *.pcap and *.pms files from the /var/tmp/ folder of the BIG-IP file system.
  10. Restore the BIG-IP debug feature values to default settings by typing the following commands:

    tmsh modify /sys db tm.rstcause.log value disable
    tmsh modify /sys db tm.rstcause.pkt value disable
    tmsh modify /sys db log.ssl.level value Warning

Capturing SSL-bridged HTTPS communications

Perform this procedure when encrypted SSL traffic arrives from the client, is decrypted and processed by the client_ssl profile, is re-encrypted by the server_ssl profile, and then is sent to the pool member as encrypted traffic.

Impact of procedure: You should enable debug logging temporarily, while performing troubleshooting procedures, and then disable debug logging after the procedure is complete. Failure to revert logging levels can lead to system performance degradation. For more information, refer to K15530: Debug logging and BIG-IP system resource utilization.

  1. Clear the browser cache in the HTTP client you are testing from.
  2. Log in to bash as the root user.
  3. Enable the SSL debug feature on the BIG-IP system by typing the following command:

    tmsh modify /sys db log.ssl.level value debug

  4. Enable the reset cause feature on the BIG-IP system by typing the following commands:

    tmsh modify /sys db tm.rstcause.log value enable
    tmsh modify /sys db tm.rstcause.pkt value enable

  5. If the BIG-IP system can access the client IP address, add the following iRule to the affected virtual server. The system retrieves the session keys for the client and server to decrypt TLS packets.

    when CLIENTSSL_HANDSHAKE {
         if {[IP::addr [IP::client_addr] equals x.x.x.x] } 
         { 
           log local0. "TCP source port: [TCP::remote_port]"
           log local0. "RSA Session-ID:[SSL::sessionid] Master-Key:[SSL::sessionsecret]"
         }
      }
     when SERVERSSL_HANDSHAKE      {
         log local0. "TCP Source port: [TCP::local_port]"
         log local0. "RSA-Session-ID: [SSL::sessionid] Master-Key: [SSL::sessionsecret]"
         }

    Note: Change x.x.x.x to the client IP address for the Client SSL handshake.

  6. Start a capture from the BIG-IP system by using the following command syntax:

    tcpdump -vvv -ni 0.0:nnnp -s0 host <client_ip> -w /var/tmp/<vs_name>_outage.pcap

    In this syntax, <client_ip> is the IP address of the computer you are testing from, and <vs_name> is the name of the virtual server you are connecting to.

  7. Note the time that this capture starts and then reproduce the issue. As soon as you notice the issue, press CTRL+C to stop the capture and note the date and time.
  8. Generate a new QKView file.
  9. Restore the BIG-IP debug feature values to default settings by typing the following bash commands:

    tmsh modify /sys db tm.rstcause.log value disable
    tmsh modify /sys db tm.rstcause.pkt value disable
    tmsh modify /sys db log.ssl.level value Warning

  10. Produce a master secret log file by typing the following command:  

    sed -e 's/^.*\(RSA Session-ID\)/\1/;tx;d;:x' /var/log/ltm > /var/tmp/sessionsecrets.pms

  11. Download the /var/tmp/sessionsecrets.pms file to your local drive.

Using Wireshark to view ssldump captured data

  1. Launch Wireshark on your computer.
  2. Navigate to Edit > Preferences > Protocols > SSL.
  3. In the Secure Sockets Layer options, click Browse for the (Pre)-Master-Secret log file name, locate the session key file (pms) you downloaded from the BIG-IP system, click Open, and then click OK.
  4. Open the packet capture to examine the HTTP application data.

The selected SSL sessions are now decrypted, and the HTTP application data is available for analysis.
