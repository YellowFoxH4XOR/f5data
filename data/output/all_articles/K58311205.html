Beginning in BIG-IP 14.1.0, F5 includes Remote Attestation, which builds on the previously released Local Attestation feature, to provide an option to remotely perform attestation with a trusted source in F5 iHealth. Using the Phone Home feature functionality, you can automatically and securely perform attestation on the authenticity and validity of the firmware and boot software of your device to make sure that it has not changed in any way from the firmware and boot software supplied by F5.

Description

Trusted Platform Module (TPM) (ISO/IEC 11889) is an international standard for a secure crypto-processor, a dedicated microcontroller designed to secure hardware through integrated cryptographic keys. F5 implements the TPM chain of custody and attestation using the TPM 2.0 chipset, Linux Trusted Boot (tboot), and Intel TXT technology. The TPM chip performs certain measurements each time the system starts. These measurements include taking hashes of most of the BIOS code, BIOS settings, TPM settings, tboot, Linux Initrd, and Linux kernel so that alternative versions of the measured modules cannot be easily produced and so that the hashes lead to identical measurements. You can use these measurements to validate against known good values. The following document provides an explanation about the terminologies used in TPM attestation and the local and remote TPM features available beginning in BIG-IP 14.1.0.

  • Terminology
  • Local Attestation
    • Automatic Local Attestation at boot time
    • Manual Local Attestation
  • Remote Attestation with F5 iHealth

Terminology

The terms in the following table may be useful when discussing chain-of-custody implementation and attestation.

Note: Attestation does not currently include other software components such as tmm or mcpd.

TermDescription
AttestationValidating the TPM PCR values against known good values to confirm that they have not changed
Chain of custodyMaintaining a consistent and unmodified state in which tampering has not occurred, even during a change of ownership
Platform Configuration Register (PCR)A TPM-volatile memory register where the hashed value of a firmware or software component is stored for later validation
System integrity measurement (SIM)The computed hashes of the BIOS and TMOS components being measured
System Integrity Reference Repository (SIRR)Two local databases (BIOS SIRR and TMOS SIRR) of known, good TPM PCR values published by F5 Product Development

The following table lists the two logs introduced in BIG-IP 14.1.0 for Local Attestation and Remote Attestation.

LogPurpose
/var/log/pcrContains PCR values and attestation status from the TPM status when it is run during the boot sequence
/var/log/txt-statContains tboot logs from the usual boot sequence

Local Attestation

Local Attestation measures and validates the BIOS, OpROMs, tboot, the Linux kernel, and initrd, and checks the certificates on the Infineon TPM chipset. It uses two local databases (BIOS SIRR and TMOS SIRR) that contain known, good TPM PCR values published by F5 Product Development. Each BIG-IP device contains a different set of known SIM values, released by F5 Product Development.

The BIOS SIRR database

  • The BIOS SIRR database is located in the /shared/lib/sirr/directory.
  • The database contains firmware measurements relating to the BIOS (ACM, BIOS, OpROMs, and so on).
  • The database is persistent across BIG-IP versions.
  • The /var/lib/sirr/ directory is a temporary location for updated BIOS SIRR from installer package.

The TMOS SIRR database

  • The TMOS SIRR database is located in the  /usr/lib/sirr/ directory.
  • The database contains values for tboot, the kernel, and initrd.
  • The database is specific to each version of BIG-IP software and does not contain firmware measurements.

Automatic Local Attestation at boot time

Automatic Local Attestation provides the ability to automatically validate the authenticity of the firmware that is being checked on the BIG-IP system. The feature runs at every boot and logs its results. When Local Attestation is run at boot time, the system logs entries in the /var/log/ltm file. Output appears similar to the following example:

info tpm-status[1179]: TPM Status Version 14.1.0.0.0.76
info tpm-status[1179]: TMOS BIG-IP 14.1.0-0.0.76.0
info tpm-status[1179]: BIOS 0645 v5.02.022.0
info tpm-status[1179]: BIOS SIRR 2018-09-18_15-36-59
info tpm-status[1179]: Remote Attestation
info tpm-status[1179]: System Integrity Status: Valid

In addition, when a BIOS TPM update is required, this increases the time required for the system to start by approximately 30 seconds. After the TPM firmware update process, the system may need to restart again. You may observe the an output similar to the following example:

Manual Local Attestation 

While Local Attestation runs automatically on every boot, you can also run it manually. You should manually perform Local Attestation when you first receive the BIG-IP device or when you perform any hardware replacement to confirm that the hardware is authentic and unmodified. You can use either the tpm-status utility or the tmsh run sys integrity status-check utility. To do so, perform either of the following procedures:

Impact of workaround: Performing the following procedure should not have a negative impact on your system.

Using the tpm-status utility to perform manual Local Attestation

  1. Log in to the BIG-IP system command line.
  2. Enter the following command syntax:

    tpm-status -a <output filename> <verbosity>

    For example, to log the output to /var/log/pcr with verbosity 2, type the following command:

    tpm-status -a /var/log/pcr -v2

Using the tmsh run sys integrity status-check utility to perform manual Local Attestation

  1. Log in to the BIG-IP system.
  2. Type the following command:

    tmsh run sys integrity status-check

    Output appears similar to the following example:

    System Integrity Status: Valid

The following table shows the possible output states from the commands, depending on the result of the attestation attempt.

StateMeaning
Not SupportedThe system is unable to perform a SIM (that is, no TPM available).
PendingThe system is not ready to perform a SIM.
ValidThe solicited SIM matches the SIRR.
InvalidThe solicited SIM does not match the SIRR.
UnavailableAn error has occurred, and a more detailed status message is reported on the console.

When the System Integrity Status status is Unavailable or Invalid, you should validate the platform integrity by manually comparing each PCR value. Refer to K93302141: Performing manual attestation with TPM on BIG-IP systems.

Remote Attestation with F5 iHealth

Remote Attestation builds on Local Attestation by collecting the SIM values and packaging them in JSON format during the qkview collection process. In addition to the SIM values, the TPM Infineon certificates are collected and packaged. When the QKView file is uploaded to F5 iHealth, F5 iHealth automatically performs attestation with the given data. The QKView may be created manually, or you can enable the Phone Home feature, which automatically generates the QKView and uploads it to F5 iHealth.

The following data, which is stored in the /var/spool/sirr/pcrs.json directory, is sent to F5 in the QKView file for Remote Attestation:

  • The JSON version to use
  • The F5 product (for example, the BIG-IP system)
  • Product version
  • Installed BIOS version
  • Installed BIOS part number
  • Device serial number
  • Local Attestation status
  • Kernel init string
  • TPM version
  • TPM status
  • TPM manufacturer
  • TPM vendor string (for identifying the correct certificate to use)
  • TPM firmware version installed
  • TPM attestation key
  • TPM endorsement key
  • TPM public keys
  • SIMs for PCRs 0, 1, 2, 17, and 18

PCR #Components measured
PCR_00ACM, BIOS, MBR
PCR_01CPU uCode

Viewing Remote Attestation status from F5 iHealth

To view the Remote Attestation status in F5 iHealth from the data in a QKView file, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to F5 iHealth.
  2. Click the QKView file you uploaded.
  3. Validation results display on the Status page, under Integrity Check. A green circle indicates that the system integrity status is valid.
  4. Click the circle next to Status to view the steps to resolve any identified issues.

The following table displays the possible Integrity Check statuses and what they mean.

F5 iHealth system Integrity Check statuses

StatusMeaning
ValidSIMs taken on the device match PD provided SIMs. Status color: Green.
InvalidSIMs taken on the device do not match PD provided SIMs and you should work with your security team and follow your internal security protocols for a breach. Status color: Red.
UnavailableThe version installed on your device does not match a version F5 iHealth has listed. Status color: Red.

Note: Updates to F5 iHealth may be delayed one to two weeks after a new software release for the SIRR databases that may cause this status to appear. Otherwise, this status may indicate a breach, and you should manually confirm the findings.

If the Integrity Check status is Unavailable or Invalid, you can use the tpm-status utility to perform manual local attestation. Alternatively, you can verify by manually comparing each PCR value. Refer to K93302141: Performing manual attestation with TPM on BIG-IP systems.
