Topic

You should consider using this procedure under the following condition:

  • You want to load balance HTTP requests to multiple pools using the Local Traffic Policies feature.

Description

You can configure a local traffic policy with multiple rules for a virtual server to load balance HTTP requests to different pools depending on the attributes of the traffic. For example, the system can load balance individual HTTP requests to different pools based on the URI path, HTTP headers, cookies, or other request attributes.

However, the system must first detach the existing server-side connection to support proper pool reselection mid-connection, such as supporting multiple HTTP requests arriving on the same Keep-Alive connection. When no conditions resulting in pool selection match the request, the system fails to detach from the existing server-side connection, which may result in an unexpected choice for the default pool. You can ensure that the system detaches the existing server-side connection by using one of the following recommendations:

  • Apply a OneConnect profile to the virtual server.
  • Create a catch-all local traffic policy rule using the default pool of the virtual server.

With a selective local traffic policy in place, when a request matches specified criteria, the system sends that request to the pool specified by local traffic policy rules. All other requests match the catch-all local traffic policy rule, which forwards the requests to the virtual server default pool and forces the new load-balancing decision.

For more information, refer to the Profiles Reference Introduction to Local Traffic Profiles chapter of the BIG-IP Local Traffic Management manual.

Note: For information about how to locate F5 product manuals, refer to K98133564: Tips for searching AskF5 and finding product documentation

Default pool selection for virtual servers using OneConnect

Important: It's important to cover all possibilities, including default pool selection within the policy, even if using OneConnect. OneConnect will not cause a new load-balancing decision if there is no server-side connection. For example, this behavior can occur if a request is satisfied from cache on the BIG-IP system, and if a subsequent request is not matched in the policy. In this case, pool selection may not update to the default pool, but will remain on a pool picked for the request before.

When you apply a OneConnect profile, the system always detaches the server-side connection upon completion of the server response and resets the default pool selection for each request to match the default pool configured on the virtual server. As a result, the system performs pool reselection using a local traffic policy applied to a OneConnect virtual server as expected:

  • The system always sends requests matching the pool selection conditions coded in the local traffic policy rules to the indicated pool.
  • The system always sends requests not matching any pool selection condition in the local traffic policy rules to the default pool configured on the virtual server, regardless of whether the system already selected a pool for a previous request on the same connection.

Note: If your application relies on the actual client IP address to provide functionality, you may need to configure a custom OneConnect profile using a Source Mask of 255.255.255.255.  For more information, refer to K7208: Overview of the OneConnect profile.

When a client connects to a OneConnect virtual server that uses a local traffic policy for pool selection, the system selects a pool based on the attributes of each request and the conditions configured in the local traffic policy rules. When a condition resulting in pool selection matches the request, the system sends the request to the selected pool. When multiple conditions resulting in pool selections match the request, the system sends the request to the pool selected in the first matching condition, if the local traffic policy uses the first-match strategy. When no local traffic policy rule condition resulting in a pool selection matches the request, the system sends the request to the default pool that is configured on the virtual server.

For example, using the following local traffic policy foo, the system always sends requests for /foo/bar/index.html to the pool foo_pool, while it always sends requests for /login to the default pool configured on the virtual server:

ltm policy foo {
    controls { forwarding }
    requires { http }
    rules {
        forward_on_foo {
            actions {
                0 {
                    forward
                    select
                    pool foo_pool
                }
            }
            conditions {
                0 {
                    http-uri
                    path
                    starts-with
                    values { /foo }
                }
            }
            ordinal 1
        }
    }
    strategy first-match
}

Default pool selection for virtual servers not using OneConnect

When you do not apply a OneConnect profile, the system only detaches the server-side connection when a new pool is explicitly selected. The system does not reset the default pool selection to match the default pool configured on the virtual server for subsequent requests on the same connection. Therefore, the system only uses the default pool defined on the virtual server as the default selection for initial requests that do not match any of the pool selection conditions (never for subsequent requests).

As a result, when the system reselects a pool using a local traffic policy applied to a non-OneConnect virtual server, the reselection does not always operate as expected:

  • The system always sends initial and subsequent requests matching the pool selection conditions coded in a local traffic policy rule to the indicated pool.
  • The system always sends initial requests not matching any pool selection condition in a local traffic policy rule to the default pool configured on the virtual server.
  • The system always sends subsequent requests not matching any pool selection condition in a local traffic policy rule to the last pool selected for this connection.

Initial pool selection

The system uses the same initial pool selection for new connections to both a non-OneConnect virtual server and a OneConnect virtual server. When a client connects to a non-OneConnect virtual server that uses a local traffic policy for pool selection, the system selects a pool based on the attributes of the first request and the coded conditions in the local traffic policy rules. When a condition resulting in pool selection matches the request, the system sends the request to the selected pool. When multiple conditions resulting in pool selections match the request, the system sends the request to the pool selected in the first matching condition, if the local traffic policy is configured to use the first-match strategy. When no condition resulting in a pool selection matches the request, the system sends the request to the default pool configured on the virtual server.

For example, using the previous local traffic policy configuration example, the system always sends a new connection containing a request for /foo/bar/index.html to the pool foo_pool, while sending a new connection containing a request for /login to the default pool configured on the virtual server.

Subsequent pool selection

The system selects pools for subsequent requests on a Keep-Alive connection to a non-OneConnect virtual server differently than it does for a OneConnect virtual server. When a subsequent request arrives on a client connection for which the system has already chosen a pool, the system may select a new pool based on the attributes of the subsequent request and the conditions in the local traffic policy rules. As with the initial request, when a condition resulting in pool selection matches the request, the system sends the request to the newly selected pool. When multiple conditions resulting in pool selections match the request, the system sends the connection to the pool selected in the first matching condition, if the local traffic policy is configured to use the first-match strategy.

However, when no condition resulting in a pool selection matches the request, the system does not send the request to the default pool configured on the virtual server. Instead, the system sends the request to the pool selected for the previous request on the same connection.

For example, using the previous local traffic policy configuration example, the system sends a new connection containing a request for /foo/bar/index.html on a Keep-Alive connection to the pool foo_pool, and it sends a subsequent request for /profile.php on the same connection to the pool foo_pool, even though the attributes of the requests do not match the condition choosing the pool foo_pool.

Note: When you have iRules and Local Traffic Policies on the same virtual server, and there is a server-side connection, the iRule command LB::detach can cancel a pool selection made by the local traffic policy. For example, on the first request on a Keep-Alive connection, there is no server side connection; therefore, the selection made by the policy is left in place. However, on a subsequent request, there is a server-side connection; therefore, when the LB::detach command runs, it cancels the policy's selection and the request goes to the default pool. The behavior is inconsequential if LB::detach appears in an iRules event after the request is sent on the server-side.

To ensure the system sends subsequent requests to the expected pool on a non-OneConnect virtual server, you must configure a catch-all local traffic policy rule. When requests do not match a prior local traffic policy rule, they do match the catch-all local traffic policy rule, which forwards the requests to the virtual server default pool.

For example, in the following local traffic policy configuration example, requests that do not match the forward_on_foo local traffic policy rule do match the catch_all rule and are sent to the default_pool, as expected for the virtual server. As a result, when pool reselection uses the local traffic policy with a catch-all rule applied to a non-OneConnect virtual server, it operates as expected:

ltm policy foo {
    controls { forwarding }
    requires { http }
    rules {
        catch_all {
            actions {
                0 {
                    forward
                    select
                    pool default_pool
                }
            }
            ordinal 2
        }
        forward_on_foo {
            actions {
                0 {
                    forward
                    select
                    pool foo_pool
                }
            }
            conditions {
                0 {
                    http-uri
                    path
                    starts-with
                    values { /foo }
                }
            }
            ordinal 1
        }
    }
    strategy first-match
}

When you apply the local traffic policy with the catch-all rule to a non-OneConnect virtual server, the system sends a new connection that contains a request for /foo/bar/index.html on a Keep-Alive connection to the pool foo_pool, and a subsequent request for /profile.php on the same connection to the pool default_pool.

Prerequisites

You must meet the following prerequisites to use this procedure:

  • You must have an existing HTTP virtual server configured with a default pool on your BIG-IP system.
  • You must have one or more pools configured on your BIG-IP system.
  • You must have administrative access to the Configuration utility.

Procedures

To configure a local traffic policy to load balance HTTP requests to multiple pools for a HTTP server, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Local Traffic > Policies > Policy List.
  3. Select Create.
  4. In the Policy Name setting, enter a policy name.

    For example:

    myMultiPoolpolicy

  5. Select the appropriate Strategy setting for your application environment, unless you require very complex conditions for matching traffic in your application environment. Otherwise, you can leave the Strategy setting as first, which is the default setting.
  6. Select Create Policy. The system saves a draft of the policy.
  7. In the Rules section, select Create.
  8. In the Name setting, enter a name for the rule.

    For example:

    myMultiPoolrule

  9. Under the Match all of the following conditions section, select the plus (+) and then select the values you want for the condition operands you require to build the conditions. In the Do the following when the traffic is matched section, select the plus (+) and click the action operands you require for the local traffic policy to perform the action you want on the matching traffic. For information about each operand, refer to the Local Traffic Policies chapter of the BIG-IP Local Traffic Manager: Concepts guide and K15085: Overview of the Local Traffic Policies feature.

    Note: For information about how to locate F5 product guides, refer to K12453464: Finding product documentation on AskF5.

    Using the first configuration in this article as an example, you add the following values:

    • For the Match all of the following conditions section:

      HTTP URI
      path
      begins with
      /foo

      Next to the the box where you entered /foo, select Add to add your input to the list.

    • For the Do the following when the traffic is matched section:

      Forward traffic
      pool
      foo_pool

  10. Select Save to save the rule.
  11. In the Rules section, select Create to create a catch-all rule for the default pool configured on the virtual server.
  12. In the Name setting, enter a name for the rule.
  13. For the Match all of the following conditions section, leave the default setting of All Traffic. This will match all traffic that did not match any other rules in the policy.
  14. For the Do the following when the traffic is matched section, select the plus (+) and add the following selecting the default pool from the drop down list:

    Forward traffic
    pool
    default_pool

  15. Select Save.
  16. Under General Properties, select Save Draft to save the changes.
  17. To publish the policy, under Draft Policies, select the checkbox next to the policy then select Publish.
  18. To associate the local traffic policy with the virtual server you want, go to Local Traffic > Virtual Servers > Virtual Server List.
  19. Under the Resources column for the HTTP virtual server that you want to load balance to multiple pools, select Edit.
  20. Under the Policies section, select Manage.
  21. In the Available list, select the local traffic policy you created in previous steps and move it to the Enabled list.
  22. To save the changes, select Finished.
