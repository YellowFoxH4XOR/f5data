Description
BIG-IP is not routing traffic through a VXLAN tunnel. This occurs when trying to connect through a virtual server. 

You may observe the following:

  • when monitor traffic and other administrative traffic is transmitted on the tunnel, the tunnel traffic is sent from the local address instead of the secondary address
  • depending on remote VTEP behavior, monitor and other administrative traffic may fail from the secondary device
  • when traffic transmitted through a virtual server is lost, you observe log messages similar to the following:
    Nov 20 17:10:29 bigip1 err tmm1[14358]: 01830003:3: Unable to find a flow for remote vtep 198.51.100.5%1, tunnel name = /Common/VXLAN_Tunnel
  • you may observe IP address conflicts for the tunnel local address

Environment

  • BIG-IP in HA configuration
  • VXLAN tunnel with the following options:
    • Floating traffic group
    • Secondary address configured
  • sys db variable iptunnel.configsync set to disable

Cause
Bug ID 858245

Recommended Actions
F5 recommends the use of secondary addresses for network virtualization tunnels instead of disabling iptunnel.configsync.

Impact of procedure: Tunnels configured with a non-floating local address may cause issues. These should be deleted first and recreated with floating local addresses and non-floating secondary addresses after following this procedure.
To enable iptunnel.configsync:

  1. In tmsh, run the following command:
    modify /sys db iptunnel.configsync value enable 

Additional Information
iptunnel.configsync was introduced to allow standby devices to use VXLAN tunnels. Starting in v13.0.0, the secondary address feature was added which allows a more robust configuration where the local address acts as a VTEP which is shared among all device group members and each device's secondary address (a non-floating self IP) is used for local-only traffic such as monitors.
