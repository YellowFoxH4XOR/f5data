K65743455: Istio proxy SPIFFE validation for inbound connection

Published
2021-09-08
Updated
2023-02-21
Applies to
  • Aspen Mesh
Source

Description

Istio is using SPIFFE standards to identify applications within the Mesh. Each application (POD) is provided with an identity encoded in SPIFFE format, and this identity is used when connecting to other services and applications running in the Mesh. The identity is part of the TLS certificate assigned to every istio-proxy (on both Client-side and Server-side) by the mesh CA (e.g., Citadel being a part of Istiod). The proxy on a receiving POD is validating the identity included in the client's TLS certificate. The client must present a TLS certificate to the server when mTLS (mutual-TLS) is enabled in the Mesh. When the Client application cannot present the certificate (trusted by the Mesh) with the SPIFFE identity, the TLS Handshake will be dropped by the server application (a part of the Mesh). SPIFFE validation is enabled by default on Istio and Aspen Mesh and cannot be disabled without modifying the istio-proxy Envoy proxy configuration.

The identity in Istio is formatted according to SPIFFE standard:

spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>

The identity uniquely identifies a specific service within trust domain.

In this article we are going to show examples about how to workload create certificates trusted by Istio mesh and how Envoy istio-proxy is validating the certificates on a service POD.

Environment

  • Kubernetes: 1.17x,1.18.x,1.19.x,1.20.x 
  • Aspen Mesh: 1.9.x 

Cause

None

Recommended Actions

Istio provides an easy way to securely manage and provision identities and X.509 TLS certificates to mesh workloads. The Istiod component is a heart of certificate management in Istio. In a typical installation, Istiod is a CA Authority inside the mesh and it offers a gRPC API service to receive and sign TLS Certificate Signing Requests sent from Clients (PODs). 
When a mesh workload (POD) starts istio-agent component running in istio-proxy container creates CSR request for the workload and sends it to Istiod via gRPC Api. Istiod signs the CSR request and sends back the signet certificate to istio-agent. Envoy proxy (running in the same istio-proxy container as istio-agent) then requests the certificate from istio-agent via SDS API.
More details about identity and certificate management can be found on official Istio documentation.

Istiod is a Certificate Authority (CA) for key and certificate management in Istio and Aspen Mesh on a typical installation. The default behavior in Aspen Mesh is to generate self-signed root CA certificate which in-turn is used by Istiod to sign CSR requests for workload certificates within the cluster. We can also provision our own external certificate (e.g. signed by trusted public CA) to Istiod which is a recommended way due to security reasons.
The procedure for provisioning external CA certificate to Istiod is documented by Aspen Mesh and Istio.

For the purpose of this article, we will provision Istiod with our own CA certificate chain created according to our multi-cluster documentation:

Aspen Mesh install tarball contains a script to create a TLS certificate chain which can be used by Istiod to sign workload certificates.

To create the CA certificate chain:

  1. Extract Aspen Mesh install tarball and enter to the directory:

    cd aspenmesh-1.9.5-am1

  2. Enter to tools/certs directory:

    cd tools/certs

  3. Run the make command to create a root-ca folder, which will consist of four files: root-ca.conf, root-cert.csr, root-cert.pem, and root-key.pem:

    make -f Makefile.selfsigned.mk root-ca

  4. Run the make command to create Intermediate CA certificate signed by root-ca certificate created in the previous step:

    make -f Makefile.selfsigned.mk cluster1-cacerts

After this procedure we should have Root CA and Intermediate CA certificates inside cluster1 directory:

ls cluster1
ca-cert.pem ca-key.pem cert-chain.pem root-cert.pem

To provision this CA certificate chain to Istiod we need to create a secret inside istio-system namespace:

kubectl create secret generic cacerts -n istio-system --from-file=ca-cert.pem --from-file=ca-key.pem --from-file=root-cert.pem --from-file=cert-chain.pem

If your Istiod was already running before creating the secret we need to restart all Istiod PODs to pull new certificates to Citadel.

Having Istiod provisioned with custom CA certificates we can look at workload certificates.
As we already said, every workload (POD) in the mesh is provisioned with TLS certificate with SPIFFE identity. The SPIFFE ID is encoded into x.509 “Subject Alternative Name” certificate extension. The format for SPIFFE is as follow:

spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>

To extract SPIFFE ID from the workload certificate we will provision httpbin application to Aspenmesh and a client application with openssl tool installed which will not be a part of the mesh. The application will be deployed in the same namespace as httpbin app.
To apply httpbin application you can use the configuration included into Aspenmesh tarball file. 

kubectl apply -f samples/httpbin/httpbin.yaml -n ns1

We will use netshoot container as a client. Netshoot is a container with a lot of useful tools installed by default. The container is documented here.
Below config needs to be applied to same namespace where we deployed httpbin (ns1 namespace in our case)

apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: nettools
  name: nettools-deploy
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nettools
  template:
    metadata:
      creationTimestamp: null
      labels:
        app: nettools
        sidecar.istio.io/inject: "false"
    spec:
      containers:
      - command:
        - sleep
        - 20d
        image: nicolaka/netshoot
        name: netshoot

Netshot POD does not have istio-proxy container injected which means that the application is not part of the mesh and does not have TLS certificate provisioned by Istiod.
Let’s open a shell into netshot POD and verify connectivity to httpbin.

As we can see below, we can resolve httpbin DNS name which means that the application should be available from netshoot (assuming httpbin POD is healthy and our mesh configuration does not block any traffic from netshoot). 

bash-5.1# nslookup httpbin
Server:     100.64.0.10
Address:    100.64.0.10#53

Name:   httpbin.ns1.svc.cluster.local
Address: 100.71.239.13

bash-5.1#

In our example mTLS is enabled in the mesh globally.

If we try to connect to httpbin application from the netshoot application (with no istio-proxy sidecar) the connection will be dropped. The error “certificate required” tells that httpbin POD is requested a TLS Certificate from the client but we did not provide any certificate to curl command.

bash-5.1# curl https://httpbin:8000/get -k
curl: (56) OpenSSL SSL_read: error:1409445C:SSL routines:ssl3_read_bytes:tlsv13 alert certificate required, errno 0

Because we have keys and CA certificates provisioned to Istiod we can try to generate a new Client certificate we will use in Netshoot application to connect to httpbin. The Client certificate used by curl will be signed by the same certificate chain so httpbin and istio-proxy should accept this certificate.

Let’s create a new certificate for the curl and netshoot application signed by the same CA certificate we provisioned to Istiod.

openssl req -out curl.csr -newkey rsa:2048 -nodes -keyout curl.key -subj "/CN=curl.example.com/O=test" 
openssl x509 -req -in curl.csr  -CA cluster1/ca-cert.pem  -CAkey cluster1/ca-key.pem  -CAcreateserial -out curl-nospiffe.crt -days 365 -sha256

We should see the following set of files and directories:

ls -ltrh
common.mk
Makefile.selfsigned.mk
README.md
Makefile.k8s.mk
certs
root-key.pem
root-ca.conf
root-cert.csr
root-cert.pem
root-cert.srl
curl.key
curl.csr
cluster1
curl-nospiffe.crt

curl-nospiffe.crt file is a certificate we will use with curl.

bash-5.1# curl --cacert ca.cert  --cert curl-nospiffe.crt --key curl.key https://httpbin:8000/get -k
curl: (56) OpenSSL SSL_read: error:14094416:SSL routines:ssl3_read_bytes:sslv3 alert certificate unknown, errno 0

Next try to create a same certificate with 1 additional SAN extension.
Note: -addext option is available on openssl version 1.1.1 and later.

openssl req -new -out curl-spiffe.csr -newkey rsa:2048 -nodes -keyout curl-spiffe.key -subj "/CN=curl.example.com/O=test" -addext "subjectAltName = URI:spiffe://cluster.local/test"

We need to create openssl configuration to add SAN extension to the certificate:

bash-5.1# cat san.cfg
[ v3_ca ]
subjectAltName = URI:spiffe://cluster.local/testing-cert

Having the above config file and CSR we can sign the certificate using the same ca-cert.pem CA certificate we provisioned to Istiod.

openssl x509 -req -in curl-spiffe.csr -CA ca-cert.pem -CAkey ca-key.pem -CAcreateserial -out curl-spiffe.crt -days 365 -sha256 -extensions v3_ca -extfile san.cfg

Let’s now check whether we have SPIFFE ID encoded into SAN extension:

bash-5.1# openssl x509 -text -in curl-spiffe.crt 
Certificate:
    Data:
        Version: 3 (0x2)
        Signature Algorithm: sha256WithRSAEncryption
        Issuer: O = Istio, CN = Intermediate CA, L = cluster1
...
        X509v3 extensions:
            X509v3 Subject Alternative Name:
                URI:spiffe://cluster.local/testing-cert

Now let’s look at the Envoy configuration from httpbin service POD responsible for validating TLS certificates received from clients.

All inbound traffic is redirected in the POD by ipdatbles rules to the Envoy proxy virtualInbound Listener on port 15006 and then connections are routed to the Listener configured with original TCP port (before redirection). Httpbin application is listening on port 80 inside the POD and our service Listener is configured with the same port.

Connection validation is configured on 15006 Listener:

As we can see above, Envoy istio-proxy is using CombinedValidationContext API from tls.v3 network folter to configure SAN validation. Details about the API can be found on official Envoy documentation here.

Envoy istio-proxy for inbout connections will accept all certificates with SAN extension starting with spiffe://cluster.local/. 
SPIFFE identifies in Istio have the following format: 

spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>

For inbound connections istio-proxy is validating only trust-domain. 

Default trust domain on Istio is cluster-local.
We can customize trust-domain during installation by specifying the domain name in global values.yaml file in the meshConfig sections:

meshConfig
    TrustDomain: <trust-odmain>

The trust domain name is added to every POD for  istio-proxy container as an environmental variable:

  - name: TRUST_DOMAIN
      value: cluster.local
