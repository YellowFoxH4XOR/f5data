K000163495: FQDN pool member remains forced down even though associated FQDN template node object is re-enabled.

Type
Support Solution
Published
2026-10-01
Updated
2026-10-01
Applies to
  • BIG-IP
  • BIG-IP LTM: 17.1.3, 21.1.0, 17.5.1
Source
https://my.f5.com/manage/s/article/K000163495

Description

When FQDN node object is once forced down and then re-enabled, a pool member with the FQDN node object should also become available. However, FQDN pool member object may stuck with "Forced down" status. Here is example of how issue happens.

 

First, when FQDN template node object is forced down, FQDN template/ephemeral node status becomes as follows. This is expected behavior.

root@(bigip2)(cfg-sync In Sync)(Active)(/Common)(tmos)# show ltm node | grep -B 1 -A 9 "Ltm::Node:"
------------------------------------------
Ltm::Node: _auto_10.2.2.10 (10.2.2.10)
------------------------------------------
Status

  State          : disabled
  Reason         : Forced down
  Monitor        : none
  Monitor Status : user-down
  Session Status : user-disabled

--
------------------------------------------
Ltm::Node: www.test1.local (::)
------------------------------------------
Status
  Availability   : available
  State          : disabled
  Reason         : The DNS server(s) are available
  Monitor        : none
  Monitor Status : fqdn-up
  Session Status : user-disabled

root@(bigip2)(cfg-sync In Sync)(Active)(/Common)(tmos)#

 

And once parent FQDN template node object is forced down, FQDN pool member status also becomes forced down with reason "Parent down". This is also expected behavior.

root@(bigip2)(cfg-sync In Sync)(Active)(/Common)(tmos)# show ltm pool members | grep -B 1 -A 11 "Ltm::Pool Member:"

When the associated FQDN template node object is re-enabled, node object status get back to proper status "available && enabled". This is also expected behavior.

root@(bigip2)(cfg-sync In Sync)(Active)(/Common)(tmos)# show ltm node | grep -B 1 -A 9 "Ltm::Node:"

On GUI, FQDN pool member availability is shown as "Offline (Enabled) - Forced down".

Figure: Pool member status after FQDN node is re-enabled

 

 

Environment

  • FQDN node object is used in a pool.
  • FQDN node object is once forced down and then re-enabled.
  • Software version with Bug ID1571817 fix (17.1.3.3 or later, 17.5.1.7 or later, or 21.1.0.1 or later, at the time of article publication).

 

 

Cause

Bug ID2488345.

 

 

Answer/Recommended Actions

To recover FQDN pool member with "forced down" status, manually enable FQDN pool member.

On GUI, navigate to "Local Traffic >> Pools : Pool List >> [pool name]", check FQDN template pool member checkbox, and press "Enable" button.

Figure: re-enable FQDN template pool member

 

On CLI, run "modify ltm pool [pool name] members modify { [fqdn-pool-member] { state user-up } }".

root@(bigip2)(cfg-sync In Sync)(Active)(/Common)(tmos)# list ltm pool fqdn_pool members { www.test1.local:http { session state } }
ltm pool fqdn_pool {
    members {
        www.test1.local:http {
            session user-enabled
            state user-down
        }
    }
}
root@(bigip2)(cfg-sync In Sync)(Active)(/Common)(tmos)# modify ltm pool fqdn_pool members modify { www.test1.local:http { state user-up } }
root@(bigip2)(cfg-sync In Sync)(Active)(/Common)(tmos)#
