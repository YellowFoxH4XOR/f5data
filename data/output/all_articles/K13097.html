Known Issue

Connections to a virtual server will fail when the BIG-IP system is unable to complete the three-way TCP handshake. This issue occurs when all of the following conditions are met:

  • The affected virtual server is associated with a TCP profile that has the Verified Accept feature enabled.
  • The affected virtual server is associated with a OneConnect profile.

The Verified Accept feature allows the BIG-IP system to verify that a pool member is available to accept the connection by sending the server a SYN packet prior to responding to the client with a SYN-ACK packet. However, when the virtual server is associated with a OneConnect profile, a sequence of events similar to the following may prevent the BIG-IP system from accepting some new connections:

  • The BIG-IP system receives the initial SYN packet from the client
  • The BIG-IP system attempts to reuse an existing server-side connection
  • The BIG-IP system fails to respond to the client's SYN packet with the expected SYN-ACK packet
  • The server-side connection eventually times out due to inactivity
  • When the server-side connection closes, the BIG-IP system sends the SYN-ACK packet to the client
  • The client sends back the ACK packet followed by the initial data packet
  • The BIG-IP system never processes the final ACK packet and retransmits the SYN-ACK packet to the client
  • The client sends an RST packet on receiving the retransmitted SYN-ACK packet since the client has already completed the three-way handshake
  • When the BIG-IP system receives the RST packet from the client, it retransmits the SYN-ACK packet to the client again
  • This retransmission cycle of the client's RST and the BIG-IP system's SYN-ACK continues until the BIG-IP system reaps the connection

Impact

Some connections to the virtual server will fail.

Symptoms

As a result of this issue, you may encounter the following symptoms:

  • BIG-IP iHealth lists Heuristic H923068 on the Diagnostics > Identified > Medium screen.
  • Client connections appear to stall and eventually time out.
  • The BIG-IP system retransmits the SYN-ACK packet repeatedly regardless of the client's response to each retransmission. For example, if you capture a tcpdump on the client-side, the tcpdump capture will show that the BIG-IP system responds to the client’s SYN packet with a SYN-ACK packet, followed by the client responding back with an RST packet, both in a continuous fashion.

Workaround

To work around this issue, you can either disable one of the conflicting features, or you can replicate their functionality with a VIP-to-VIP connection. To do so, perform one of the following procedures:

  • Disabling Verified Accept
  • Disabling OneConnect
  • Replicating Verified Accept behavior with a VIP-to-VIP connection

Disabling Verified Accept

Impact of workaround: The BIG-IP system may complete the three-way TCP handshake when there is no server available to take the connection.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic >> Virtual Servers >> Virtual Server List.
  3. Click the name of the affected virtual server.
  4. Select None for the OneConnect Profile dropdown box.
  5. Click the Update button to save the modification.

Disabling OneConnect

Impact of workaround: Performance may be significantly impacted by disabling connection re-use.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic >> Profiles >> Protocol >> TCP.
  3. Click the name of the TCP profile associated with the affected virtual server.
  4. Clear the Enabled box for the Verified Accept option.
  5. Click the Update button to save the modification.

Replicating Verified Accept behavior with a VIP-to-VIP connection

If you would like to replicate the functionality of OneConnect with Verified Accept, you need to modify your BIG-IP configuration to use a PerformanceL4 virtual server to target a standard virtual server that is configured with only OneConnect. To do so, perform the following procedure:

Impact of workaround: The BIG-IP system may experience a slight performance degradation.

  1. Log in to the Configuration utility.
  2. Navigate to Local Traffic >> iRules >> iRule List.
  3. Click the Create button.
  4. Type a name for the iRule in the Name box.

    For example:

    sol13097-rule

  5. Type the following in the Definition box, replacing <VIP> with the name of the affected virtual server

    when CLIENT_ACCEPTED {
         virtual <VIP>
    }

    For example, if the name of the affected virtual server is http-vs-all, you would type the following in the Definition box:

    when CLIENT_ACCEPTED {
         virtual http-vs-all
    }

  6. Click the Finished button to save the changes.
  7. Navigate to Local Traffic >> Virtual Servers >> Virtual Server List.
  8. Click the Create button.
  9. Type the name of the PerformanceL4 virtual server in the Name box.

    For example:

    sol13097-vs

  10. Type the IP address for the PerformanceL4 virtual server in the Destination Address box.

    For example:

    172.28.21.204

  11. Type the port for the PerformanceL4 virtual server in the Service Port box.

    For example:

    80

  12. Select Performance (Layer 4) for the Type dropdown box.
  13. Select the iRule created in Steps 3 – 6 in the Available box, and click the << button to enable it for the iRules.
  14. Select the pool name of the affected virtual server in the Default Pool dropdown box.
  15. Click the Finished button.
