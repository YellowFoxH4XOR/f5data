K000160065: Understanding and Resolving ASM XML/JSON Memory Exhaustion and Capacity Planning

Description

BIG-IP ASM may experience recurring XML/JSON memory exhaustion during XML or JSON processing, resulting in event code X264 ("Exceeded maximum memory assigned for XML/JSON processing"). This issue causes connection resets and prevents XML/JSON traffic from being processed properly.

Symptoms include:

  • Connection resets during XML/JSON processing
  • Error messages in /var/log/ts/bd.log*:
    • BD_XML|ERR: Cannot allocate [bytes] more bytes for XML parser. current memory size [bytes]
    • BD_XML|ERR: JSON parser is out of memory - resetting the connection
  • Error messages in :
    • IO_PLUGIN|ERR: TMEVT_REQUEST_DONE: handling http request failed
    • ASM out of memory error: event code X264 Exceeded maximum memory assigned for XML/JSON processing

Environment

  • Product: BIG-IP ASM (Application Security Manager)
  • Configuration:
    • Multiple ASM policies with XML/JSON profiles enabled
    • XML memory utilization approaching or exceeding 99%
    • Multiple bd threads (CPU cores)
    • ASM policies in Blocking or Transparent enforcement mode

Cause

XML/JSON memory exhaustion occurs when the ASM bd (security daemon) process runs out of allocated memory for XML/JSON parsing. This is a capacity-related issue, not a memory leak or platform defect.

Key characteristics of XML/JSON memory behavior:

  • XML memory is allocated per XML profile per bd thread
  • Memory grows to accommodate peak traffic and plateaus
  • Memory is not released after processing requests; it remains allocated to handle future traffic
  • Memory is only released when ASM processes are restarted
  • Multiple bd threads multiply the total memory requirement (e.g., 8 threads = 8 parsers per profile)

Answer/Recommended Actions

Step 1: Assess Current XML/JSON Memory Utilization

Check current memory usage:

tmctl asm_memory_util_stats -s total_xml_mem_used,total_xml_max_mem

Calculate utilization percentage:

tmctl asm_memory_util_stats -s total_xml_mem_used,total_xml_max_mem | awk '(c!=0&&c!=1&&$2) {print $1"KB "$2"KB " $1*100/$2"%"} {c++}'

Step 2: Determine Required Memory Allocation

Analyze the largest XML/JSON requests that failed:

zgrep -i 'XML parser' /var/log/ts/bd.log* | awk '{print $7,$9}' | sort -nr | head

This output shows the largest allocation requests that exceeded available memory.

Step 3: Increase XML Memory Allocation

  1. Navigate to Security > Options > Application Security > Advanced Configuration > System Variables
  2. Modify total_xml_memory to a value above observed peak usage (e.g., 800MB or higher)
    • Maximum for total_xml_memory: 1GB (1,073,741,824 bytes)
    • For requirements exceeding 1GB, use additional_xml_memory_in_mb (up to 64GB)
  3. Click Update
  4. Restart ASM service during a maintenance window:
    tmsh restart /sys service asm

Note: Restarting ASM will interrupt traffic processing and may trigger failover in HA configurations.

Step 4: Implement Proactive Monitoring

Set up custom monitoring for XML/JSON memory usage:

Real-time monitoring command:

tmctl asm_memory_util_stats -s total_xml_mem_used,total_xml_max_mem | awk '(c!=0&&c!=1&&$2) {print $1"KB "$2"KB " $1*100/$2"%"} {c++}'

Alerting options:

  • Configure syslog, SNMP traps, or email alerts when memory usage exceeds threshold (e.g., 80%)
  • Integrate monitoring with existing infrastructure using iControl REST API
  • Review iHealth snapshots for historical memory usage trends

Note: No standard SNMP OIDs exist for XML memory usage; custom monitoring scripts are required.

Step 5: Optimize Configuration and Application

ASM Policy Optimization:

  • Review and consolidate XML/JSON profiles where possible
  • Disable XML/JSON inspection for applications where it is not required
  • Consider splitting ASM policies across multiple virtual servers to distribute memory load

Application-Side Optimization:

  • Work with development teams to optimize XML/JSON payload sizes
  • Reduce unnecessary data in XML/JSON requests
  • Implement payload compression where applicable

Platform Considerations:

  • Evaluate upgrading to newer BIG-IP versions for improved memory management
  • Consider hardware upgrades or larger VE instances for high-volume XML/JSON processing

Additional Information

Default XML Memory Allocation by Platform:

  • Platforms with < 16 GB RAM: 300 MB
  • Platforms with 16-32 GB RAM: 450 MB
  • Platforms with > 32 GB RAM: 1 GB

Important Behavioral Notes:

  • XML memory allocation is per XML profile per bd thread; multiple threads significantly increase total memory consumption
  • Memory is not released after processing; it plateaus at peak usage levels
  • After ASM restart, memory usage resets and gradually increases again with traffic
  • Modifying XML/JSON profiles causes memory reallocation as old parsers are purged and new ones created
  • Multiple identical XML/JSON profiles across policies may share a single internal object, reducing memory overhead

Historical Memory Trend Analysis:

To check historical memory usage from snapshots:

find /shared/tmstat/snapshots/blade0/public/86400/ -type f | sort | xargs -I {} sh -c 'echo " {} "; tmctl asm_memory_util_stats -s total_max_mem,total_xml_ -type f | sortmem_used 2>/dev/null | head -7'
