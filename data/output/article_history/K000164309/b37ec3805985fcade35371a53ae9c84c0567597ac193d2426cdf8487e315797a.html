Description

You want to block the HTTP methods TRACE, TRACK, and CONNECT on NGINX Plus for security hardening, and apply the restriction consistently to all HTTP and HTTPS virtual servers.

  • NGINX rejects TRACE with HTTP 405 by default.
  • NGINX rejects CONNECT by default (since nginx 1.21.1). Starting with NGINX Plus R36, CONNECT can be enabled for a server or location with the tunnel_pass directive.
  • NGINX has no built-in rejection for TRACK. Without explicit configuration, NGINX processes a TRACK request like any other request and may pass it to the upstream server. The response status then depends on the location or upstream.

Environment

  • NGINX Plus R32 and later
  • HTTP and HTTPS server blocks, for example in a reverse proxy (proxy_pass) deployment

Cause

NGINX does not recognize TRACK as a known method, so TRACK must be blocked with explicit configuration. The restriction cannot be implemented in the http {} context alone: the map directive is valid in http {}, but the if and return directives that reject a request are valid only in server and location context.

Recommended Actions

  1. Create the file /etc/nginx/global/block-methods-map.conf with the following content:

    map $request_method $blocked_method {
    default   0;
    TRACE     1;
    TRACK     1;
    CONNECT   1;
}

    Include the file in the http {} block of /etc/nginx/nginx.conf:

    http {
    ...
    include /etc/nginx/global/block-methods-map.conf;
    ...
}

    Alternatively, place the map block directly inside http {}.

  2. Create the file /etc/nginx/global/block-methods.conf with the following content:

    if ($blocked_method) {
    return 405;
}

  3. Include block-methods.conf in every HTTP and HTTPS server block, directly after the listen and server_name lines and before any return or rewrite directive. For example:

    server {
    listen 80;
    server_name app.example.com;
    include /etc/nginx/global/block-methods.conf;
    return 301 https://$host$request_uri;
}

    Alternative – shared file: If all your server blocks already include a common file at server level, you can add include /etc/nginx/global/block-methods.conf; as the last line of that shared file instead of editing every server block. In this case:

    • The include line of the shared file must appear before any return or rewrite directive in each server block. If a server block has a redirect above that include line, move the include above the redirect, or add include /etc/nginx/global/block-methods.conf; directly above the redirect.
    • Include the shared file only inside server blocks, never in http {}, because the if directive is not allowed in the http {} context.
    • For server blocks that do not include the shared file, add include /etc/nginx/global/block-methods.conf; directly. Do not add the shared file to those blocks if they already define some of the same directives inline, because this may duplicate the directives.

  4. Deploy the map and block-methods.conf together to every NGINX Plus instance. block-methods.conf uses the $blocked_method variable, which is defined by the map.

  5. Validate the configuration and reload NGINX on each instance:

    nginx -t && nginx -s reload

  6. Verify the running configuration:

    • Confirm that the map is present:

      nginx -T 2>/dev/null | grep -n -A6 "map \$request_method"

    • If you include block-methods.conf directly in each server block, compare the following two counts. The first (include lines) should equal the second (server_name lines), apart from server blocks that you intentionally exclude. The server_name count is an approximation: server blocks without server_name are not counted.

      nginx -T 2>/dev/null | grep -c "include /etc/nginx/global/block-methods.conf"
nginx -T 2>/dev/null | grep -cE "^\s*server_name"

      If you use a relative include path (for example, include global/block-methods.conf;), adjust the first command accordingly.

    • If you use the shared-file approach, the block-methods.conf count returns 1, because nginx -T prints each included file only once. Instead, compare the number of include lines for the shared file with the number of server_name lines. A small difference is expected for server blocks that you intentionally exclude.

  7. Test TRACK, TRACE, and CONNECT on each virtual server, using the real hostname so that the correct server block is selected:

    curl -i --http1.1 -X TRACK https://<hostname>/
curl -i --http2 -X TRACK https://<hostname>/
curl -i --http1.1 -X TRACE https://<hostname>/
curl -i --http1.1 -X CONNECT --request-target <hostname>:443 https://<hostname>/

    Expected results:

    • TRACK and TRACE return 405.
    • CONNECT is rejected with an error status (405 or 400), and no tunnel is established.

Notes:

  • Keep CONNECT in the map. Starting with NGINX Plus R36, CONNECT can be enabled with tunnel_pass. Keeping CONNECT in the map ensures that it stays blocked in server blocks that include block-methods.conf, even if tunnel_pass is added to them later. Do not include block-methods.conf in server blocks that are intended to work as an HTTP CONNECT forward proxy.
  • The same configuration works on NGINX Plus R32 and later. No changes to the snippets are required between releases.
  • Do not include block-methods.conf in stream {} configuration. The stream module proxies TCP/UDP and does not process HTTP methods. HTTP applications published through stream {} must enforce method restrictions on the backend, or be moved to an HTTP server block.
  • Management-only server blocks, such as the NGINX Plus API or stub_status, can be excluded if access to them is already restricted, for example with allow and deny directives.

Additional Information

  • Expected behavior: The configuration affects only TRACE, TRACK, and CONNECT. Other methods, such as GET, HEAD, POST, PUT, PATCH, DELETE, and OPTIONS, are not affected. Confirm with application owners that no published application relies on the blocked methods.
  • Port 80 redirects: If the include is placed after a return 301 directive, TRACK requests on port 80 receive the 301 redirect instead of 405. The request is still not passed to the upstream server. Placing the include before the redirect returns a consistent 405.
  • Change window: Apply the change first on a non-production instance or during a maintenance window.
  • Reference documentation:

    • Module ngx_http_rewrite_module (if and return directives)
