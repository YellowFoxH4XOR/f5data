Description


  A PXE clean install rebuilds a VELOS system controller (K000152443) or a compute blade (K000130388) from the PXE server running on the other, healthy system controller. The rebuilt controller comes back at the active 
  controller's software version and takes the active controller's configuration. Nothing on the rebuilt node's own disk is preserved: configuration, logs and, for a blade, tenant virtual disks.
  Use this article to decide whether a clean install is the right step, and what to do before you start.

  Environment


  - VELOS chassis with two system controllers
  - Blades assigned to chassis partitions; BIG-IP tenants on those blades

  Cause


  Not applicable (procedure guidance).

  Recommended Actions

  1. When a PXE clean install is the right step
     - A system controller is stuck on the wrong software version or does not rejoin the cluster after an upgrade, and the standard recovery steps (set-version, OpenShift cluster reinstall) did not resolve it.
     - A system controller's disk or operating system is damaged, and the other system controller is healthy and holds the current configuration.
     - A chassis partition create or upgrade fails because of stale disk-volume state left by an earlier upgrade (see K000152443).
     - A single blade's operating system is damaged, or the blade does not boot correctly (see K000130388).

  2. When not to use a PXE clean install
     - You do not know which system controller holds the current configuration. The rebuilt controller takes the active controller's configuration. If the controller you rebuild held the only current copy, that configuration is 
  lost. After a failed upgrade, the active controller can be the one that fell back to an older saved configuration.
     - The other system controller is down, still booting, or not cluster-ready. PXE requires a working peer. If both controllers are down, the only clean install option is from USB media. After a failover, wait at least 10 
  minutes before you rebuild the new standby controller.
     - The problem is in a chassis partition or a tenant. A controller rebuild does not fix those and adds risk.
     - Logs are needed to determine the root cause. A clean install removes the controller's logs. Collect a qkview first, and contact F5 Support: in some failed-upgrade situations, F5 Support can return a controller to its 
  previous software version without a clean install.

  3. Before a system controller clean install
     a. Identify which controller holds the current configuration.
     b. Set the primary key to a known value, record it, and back up the configuration (K50135154). From the floating management IP address:
          config
          system aaa primary-key set
          (enter the passphrase and salt when prompted, and record both)
          end
          show system aaa primary-key state hash     (record the hash)
          config
          system database config-backup name <file-name>.xml
        Export the backup file off the system. A configuration backup can only be restored with the primary key that was in place when it was taken. "show system aaa primary-key state status" returns NONE when the key was never 
  set.
     c. Confirm the other controller is healthy and cluster-ready:
          show cluster
            cluster orchestration-manager cluster-initialized true
            cluster orchestration-manager cluster-ready true
            cluster orchestration-manager etcd-ha-running true
            both controllers "In Cluster"
     d. On F5OS-C 1.7.x, confirm that both controllers run matching OS and services versions. A mismatch can cause the rebuilt controller to loop. Contact F5 Support to correct a mismatch first.
     e. Check the boot order on both controllers (efibootmgr -v from the root shell). A controller whose next boot is already set to PXE reinstalls itself on its next reboot.

  4. Before a blade clean install
     Assume that a blade clean install erases every tenant virtual disk on that blade. A tenant's BIG-IP configuration is stored only on those disks; the chassis partition stores the tenant definition, not its configuration.
     - Save a UCS archive from every tenant with a slot on the blade, and save each tenant's master key (K9420). Copy both off the system.
     - Multi-slot tenant: confirm its other slots are healthy. They continue to pass traffic while the rebuilt slot returns.
     - Single-slot tenant whose only slot is on the blade: plan an outage for that tenant. It returns with no BIG-IP configuration, and you must restore the UCS archive.
     - Keep the tenant images on the chassis partition; the relaunch needs them.
     - After the rebuild, confirm which software volume the tenant slot booted. A new tenant disk can boot the base tenant image instead of the installed version.

  5. During the work
     - Rebuild one system controller at a time. Never reboot or rebuild one controller while the other is down or still booting.
     - Do not power off a controller with the OBM and leave it in the chassis. A controller that is present but not powered prevents blade detection on the other controller. Keep it powered, or remove it.
     - A controller rebuild takes about an hour. Monitor it from the other controller with show cluster.
