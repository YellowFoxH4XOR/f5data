Description

BIG-IP VE 13.1.3 becomes unresponsive and TMM aborts after a bulk configuration load. The virtio driver fails to add MAC filters, which leads to a TMM SIGABRT.

Observed symptoms:

  • TMM stops responding and the device cannot be brought up.
  • Logs cannot be collected and qkview generation hangs.
  • Packets from backend servers are not parsed, and the BIG-IP cannot ping its gateways.

The issue is triggered when many virtual server objects, along with associated profiles, policies, and rules, are created in quick succession with tmsh load sys config merge file.

Key log messages:

virtio[0:5.0]: Error: Transaction [01,00] timed out

virtio[0:5.0]: Error: Failed to add MAC filter <...>

errdefs: errdefs: config load failed

** SIGABRT **

TMM aborted @ ...

Environment

  • BIG-IP VE, version 13.1.3 (TMM Version 13.1.3.4.0.0.5)
  • Deployed in a public cloud on a KVM hypervisor with virtio network drivers
  • Configuration with a large number of virtual servers (more than 1,000 in affected deployments)
  • Bulk configuration load via tmsh (load sys config merge file) that creates multiple virtual servers, persistence profiles, policies, and SNAT pools in a short time span

Cause

The virtio driver cannot handle rapid bulk configuration changes in the hypervisor/KVM environment. The flood of configuration changes makes the virtio driver unresponsive, and TMM subsequently crashes.

This is a hypervisor/virtio issue, not an F5 software defect. An internal tracking reference (ID803245) was created for this analysis.

Answer/Recommended Actions

  1. Slow down configuration changes. Apply configuration changes in smaller batches with pauses between actions, rather than creating many objects in a short span.
  2. Avoid bulk config merges during active traffic on virtualized deployments that use virtio, particularly when creating large numbers of virtual servers.
  3. Monitor for virtio errors in /var/log/tmm* (for example, Transaction timed out and Failed to add MAC filter) during configuration changes.
  4. Recover from a TMM crash. If TMM has crashed, collect a qkview and the TMM core file, then open a support case for analysis.
  5. Engage F5 Support if the issue recurs, providing the qkview, core file, and /var/log/audit and /var/log/tmm entries from the time of the event.

Additional Information

  • TMM crashes were observed in deployments with more than 1,000 virtual servers and not in setups with fewer than 100 virtual servers.
  • The virtio timeout errors and the subsequent TMM SIGABRT are the expected failure pattern when the hypervisor cannot keep up with configuration-driven MAC filter updates. This is not normal operational behavior.
  • Review the hypervisor and virtio driver versions with the cloud or hypervisor vendor when this symptom appears.
