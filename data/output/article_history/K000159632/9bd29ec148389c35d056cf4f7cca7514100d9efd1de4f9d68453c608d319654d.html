K000159632: Why do TCP port scanners report more open ports than those configured on my load balancer?

Description:

 

  • During a security scan performed by the customer using a TCP-based port scanning tool, the load balancer IP address was reported as having more open ports than those defined in the load balancer configuration, leading to concerns about unexpected port exposure.

 

 

Environment:

 

  • F5® Distributed Cloud HTTP Load Balancer
  • F5® Distributed Cloud TCP Load Balancer

 

Answer/Recommended Actions

 

  • Conventional network scanners typically validate whether a port is open by attempting to establish a TCP connection. This validation is performed strictly at the TCP layer, based on the combination of destination IP address and port.

 

  • In our environment, multiple TCP/HTTP load balancers across different namespaces may share the same public IP address. As a result, when a conventional scanner probes a given IP and port, the scan may report the port as open because at least one load balancer bound to that IP is listening on that port, even if it does not belong to the specific application or namespace being tested.

 

  • It is important to note that this result represents only an initial, low-level TCP validation. Once traffic is received by our platform, it is subsequently evaluated at the application routing layer, where the request is matched against the destination domain (Host header / SNI) and port. This routing logic ensures that the request is mapped to the correct load balancer configuration.

 

  • If the resolved load balancer does not have the destination port explicitly exposed or configured, the traffic is dropped at the platform level and is not forwarded to the backend server, even if a generic TCP scan reports the port as open on the shared IP.

 

 

  • The most reliable way to validate the actual application-level behavior of the load balancer is by issuing explicit HTTP/HTTPS requests using a tool such as curl, rather than relying solely on TCP-level port scans.

 

  • The following example iterates over multiple ports while explicitly binding the domain name to a specific IP address, ensuring that both SNI (for TLS) and the HTTP Host header are evaluated during request processing:

 

for i in 80 443 4443 8011 8443 9000; do

echo "==== Testing port $i ===="

curl -vk https://payments.hdfc.bank.in:$i \

--resolve payments.hdfc.bank.in:$i:159.60.128.212

done

 

  • This approach allows you to observe the real response generated by the load balancer once a connection attempt is made on each port. Specifically, it helps identify whether the load balancer accepts, rejects, or actively resets (RST) the connection after evaluating the request at higher layers, rather than merely confirming that the port is reachable at the TCP handshake level.
