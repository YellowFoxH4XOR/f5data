Description

When copying a file between one pod and the other(same namespace, AspenMesh enabled), connection gets reset intermittently, istio-proxy log shows the following:

20260828T14:45:44.403632319Z{"x_b3_spanid":null,"bytes_sent":0,"requested_server_name":null,"route_name":null,"3gpp_sbi_target_apiroot":null,"connection_termination_details":null,"upstream_cluster":"outbound|443||kubernetes.default.svc.cluster.local","x_forwarded_for":null,"duration":0,"request_id":null,"3gpp_sbi_correlation_info":null,"x_b3_traceid":null,"start_time":"2026-08-28T14:45:44.146Z","method":null,"RespDetails":null,"protocol":null,"path":null,"authority":null,"upstream_transport_failure_reason":null,"response_code":0,"response_code_details":null,"downstream_local_address":"198.223.20.10:443","upstream_service_time":null,"response_flags":"URX","downstream_remote_address":"192.168.26.145:44554","upstream_local_address":null,"upstream_host":"198.223.20.10:443","bytes_received":0,"user_agent":null,"server":null}

Environment

-AspenMesh 1.14.x
-Istio 1.22

Cause

This issue is caused by open source bug: https://github.com/envoyproxy/envoy/issues/37679

Answer/Recommended Actions

a) Upgrade to am1.21
b) EnvoyFilter with retry mechanism on TCP level:

apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: apiserver-tcp-connect-retries
  namespace: <your_app_namespace>
spec:
  workloadSelector:
    labels:
      app: <your_app_label>
  configPatches:
    - applyTo: NETWORK_FILTER
      match:
        context: SIDECAR_OUTBOUND
        listener:
          #name: 192.168.0.1_443 #use name for a specific ip address
          portNumber: 443
          filterChain:
            filter:
              name: envoy.filters.network.tcp_proxy
      patch:
        operation: MERGE
        value:
          typed_config:
            "@type": type.googleapis.com/envoy.extensions.filters.network.tcp_proxy.v3.TcpProxy
            max_connect_attempts: 5
            idle_timeout: 3600s


c) different retry mechanism on client side depending on client type. For example for a client running kubectl cp you need to add retry parameter: kubectl cp --retries=-1

Additional Information

An Envoy connection-pool cleanup race in the Envoy version bundled with Aspen Mesh 1.14.x can cause intermittent termination of new TCP connections to the Kubernetes API server.

When an existing upstream connection closed, Envoy invoked its idle-connection cleanup callback twice. A new connection to the same upstream cluster and pool key was created between the two callbacks. The stale second callback then deleted the newly created pool and closed the new connection before data was transmitted. This produced the TCP reset observed by kubectl and the corresponding URX flag in the Istio sidecar.

The case evidence matched Envoy issue #37679 / PR #30807. 

The customer confirmed that applying EnvoyFilter with tcp retry prevented further failures.
