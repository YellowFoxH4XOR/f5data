Security Advisory Description

A buffer overflow vulnerability in the Brotli decoder (c/dec/decode.c) in Google Brotli versions 1.0.3 through 1.2.0 on all platforms allows a remote unauthenticated attacker to corrupt adjacent decoder state memory, disclose sensitive memory contents, cause a denial of service, or potentially execute arbitrary code using a crafted Brotli-compressed stream. Users need to update any Brotli libraries or binaries between 1.0.3 through 1.2.0 to the latest available version: 1.0.10 or 1.1.1 or 1.2.1. (CVE-2026-111497) (also known as HTTP2shell)

This CVE was previously included in K000163874: Multiple Node.js vulnerabilities. The remaining nine CVEs from the Node.js October 21, 2026 Security Releases can be found in that article. For more information about these vulnerabilities, refer to the following Node.js web page: Wednesday, October 21, 2026 Security Releases.

Create a custom attack signature for CVE-2026-111497

  1. As an administrator role user, navigate to Security ›› Options : Application Security : Attack Signatures > Attack Signatures List.
  2. Click Create.
  3. Provide an Attack Signature Name, example temp_CVE-2026-111497
  4. Assign a Tag, example temp_CVE-2026-111497:
    For Signature Type, use Request
    For Attack Type, use Command Execution
    For Assigned Systems, use Node.js
    For Rule, use Advanced Mode. Paste the custom rule:
    headercontent:"Content-Encoding:"; nocase; re2:"/^Content-Encoding:[^\n]+\bbr\b/Hmi"; re2:"/^(?:POST|PUT|PATCH)/i";
    Note: This signature blocks all requests with an "Content-Encoding" header that indicates the Brotli compression method, while limiting to POST/PUT/PATCH method to reduce false positives.
    Set Accuracy, example Low
    Set Risk, example Low
  5. Click Add.

Create a custom attack signature set and configure to match the custom attack signature

  1. Navigate to Security ›› Options : Application Security : Attack Signatures > Attack Signatures Sets.
  2. Click Create.
  3. Provide an Attack Signature Set Name, example temp_CVE-2026-111497
    Set Default Blocking Actions, example Learn, Alarm, Block.
    Set 'Assign Set to Newly Created Policies', example Always.
    Set 'Signature Set Type' , example Manual, then use one of the available filters, example Tag, and use the custom attack signatures Tag, example temp_CVE-2026-111497. The matched attack signature will appear in the Available Signatures list. Click on the plus sign to assign the Attack Signature.
  4. Click Add.
    The newly created Attack Signature set will appear in the list.

Assign the Custom Attack Signature Set to the specific Adv WAF Security Policy

  1. Navigate to Security ›› Application Security : Policy Building : Learning and Blocking Settings.
  2. In the dropdown list, select the specific Adv WAF Security Policy.
  3. Under Attack Signatures, click Change.
  4. Click the checkbox next to the newly created Custom Attack Signature Set, then click Change.
  5. Enable the Attack Signature Set's violation settings, example enable Learn, Alarm, Block checkboxes.
  6. Click on Save.

Ensure that the newly created custom attack signature is Enforced

  1. Navigate to Security ›› Application Security : Security Policies : Policies List > select the specific Adv WAF Security Policy.
  2. Under Policy Configuration, Attack Signatures, select the custom attack signature, click Enforce.
  3. Click Apply Policy.

This procedure is relevant for Next.js apps hosted on vulnerable Node.js servers. F5 recommends to restrict the list of domains in the`url`parameter under the allowed URL `/_next/image` to include only trusted websites.

  1. As an Administrator role user, navigate to Security ›› Application Security : URLs : Allowed URLs : Allowed HTTP URLs.
  2. Select the specific Adv WAF security policy.
  3. Click Create.
  4. Under Create New Allowed URL, set Explicit, HTTPS, '/_next/image'.
  5. Remove Perform Staging to immediately enforce the URL.
  6. Click Create.
    The created HTTPS /_next/image URL is now listed in the Allowed URL list.

Configure a URL parameter named "url"

  1. Click on the HTTPS /_next/image URL in the Allowed URL list, it will open the page.
  2. Security ›› Application Security : URLs : Allowed URLs : Allowed HTTP URLs ›› Allowed HTTP URL Properties.
  3. Click on URL Parameters, it will open the page.
  4. Security ›› Application Security : URLs : Allowed URLs : Allowed HTTP URLs ›› URL Parameters.
  5. Click Create, it will open the page.
  6. Security ›› Application Security : URLs : Allowed URLs : Add URL Parameter…Allowed HTTP URLs ››
  7. Set Parameter Name as Explicit 'url'.
  8. Set Parameter Level as URL, Path HTTPS '/_next/image'.
  9. Uncheck Perform Staging to immediately enforce the URL parameter.

CVE-2026-111497 and the NGINX Plus Brotli module

The NGINX Plus Brotli module does not use the Brotli decoder functionality directly and is therefore not directly affected by the decoder-only vulnerability CVE-2026-111497. The module links using dynamic linking to the Google open source Brotli library. The module compresses responses using the Brotli encoder or serves existing Brotli-compressed files; it does not decompress Brotli content.

The nginx-plus-module-brotli package does not bundle the Brotli shared library. It depends on the library supplied by the operating system vendor’s repositories. Other applications on the same system may use the affected decoder functionality.

Recommended actions

No NGINX Plus Brotli module update is required for this decoder-only vulnerability. However, consult your OS vendor to determine whether the installed Brotli library requires an update for other applications. Use the vendor advisory to identify the fixed package release. Vendors may backport security fixes without changing the upstream version number.

F5 WAF for NGINX mitigation

This NGINX map configuration will reject requests whose Content-Encoding header contains the Brotli token 'br'. This should be configured to check the header, and if it exists, reject the request before the F5 WAF for NGINX/App Protect pre-access inspection phase runs. For more information on updating configuration files for F5 WAF for NGINX, refer to F5 WAF for NGINX > Virtual machine or bare metal > Update configuration files section documentation.

  1. To reject requests whose Content-Encoding header contains the Brotli token br, add the following configuration:
    http {
    map $http_content_encoding $reject_brotli_request {
    default 0;
    ~*(^|,)[[:space:]]*br[[:space:]]*(,|$) 1;
    }

    server {
    listen 443 ssl;

    # Runs before the App Protect pre-access inspection phase.
    if ($reject_brotli_request) {
    return 415;
    }

    app_protect_enable on;

    # Existing configuration...
    }
    }

    Note: You can use return 444 instead of 415 if the requirement is to close the connection without a response:
    if ($reject_brotli_request) {
    return 444;
    }
    The case-insensitive expression covers:
    • Content-Encoding: br
    • Content-Encoding: BR
    • Content-Encoding: gzip, br
    • Additional whitespace around the encoding
  2. Once you have updated your configuration files, reload NGINX with the following command:
    nginx -s reload

Create an iRule to Reject HTTP requests with Content-Encoding: br HTTP header and value

This iRule will reject HTTP requests with "Content-Encoding: br" as the HTTP header and value. The iRule will not reject HTTP responses from the pool member/upstream server that sends the "Content-Encoding: br" HTTP header and value. As a general mitigation, disable Brotli compression until the Brotli package is updated on affected upstream servers/systems.

  1. Navigate to Local Traffic > iRules > iRule List.
  2. Select Create.
  3. Enter a Name for the iRule.
  4. For the Definition, use the following:
    when HTTP_REQUEST {
    foreach encoding [HTTP::header values "Content-Encoding"] {
    if { [regexp -nocase {(^|,)[ \t]*br[ \t]*(,|$)} $encoding] } {
    log local0. "Rejected Brotli request: client=[IP::client_addr]:[TCP::client_port]"
    reject
    return
    }
    }
    }
    Note: Disable logging as needed by commenting the line with #.
  5. Select Finished.
  6. Navigate to Local Traffic > Virtual Servers > Virtual Server List, and select the Virtual Server.
  7. Under Resources > iRules > Click Manage, select the created iRule from the Available list and move it to the Enabled list.
  8. Select Finished.
  9. Monitor /var/log/ltm for 'Rejected Brotli request' logs.

Configure Header-Based Content Profile to Disallow "Content-Encoding: br" HTTP header and value in Allowed URLs in Adv WAF Security Policy

This configuration will disallow HTTP requests to an allowed URL that includes the "Content-Encoding: br" HTTP header and value.

  1. As admin role user, navigate to Security > Application Security > URLs > Allowed URLs > Allowed HTTP URLs. Select the specific Adv WAF Security Policy and URL. Allowed HTTP URL Properties opens.
  2. Use the Advanced view. Under Header-Based Content Profiles, use:
    Request Header Name: Content-Encoding
    Request Header Value: *br*
    Request Body Handling: Disallow
    Select Update.
  3. Ensure Illegal request content type violation Alarm and Block are enabled in the Adv WAF Security Policy.
  4. Navigate to Security > Application Security > Policy Building > Learning and Blocking Settings, and enable Alarm and Block for Illegal request content type violation.
  5. Select Save.
  6. Select Apply Policy.

Create LTM Policy to Reject HTTP Requests with "Content-Encoding: br"

This LTM Policy will reject HTTP requests with the "Content-Encoding: br" HTTP header and value.

  1. As an admin role user, navigate to:
    Local Traffic > Policies > Policy List
  2. Select Create.
  3. Provide a Policy Name and select Create policy. The Draft Policy page opens.
  4. Under Rules, select Create and provide a name.
  5. Under Match all of the following conditions:, select the plus (+) sign.
  6. Configure the rule with:
    HTTP Header full string named Content-Encoding is any of br at request time
  7. Under Do the following when the traffic is matched:, select the plus (+) sign.
  8. Configure the policy action with:
    Reset traffic connection at request time
  9. Add the following log message at request time:
    tcl:IP [IP::client_addr] brotli requests blocked by LTM Policy
  10. Select Save. This saves the LTM Policy as a Draft Policy.
  11. Select Save and Publish Policy.

  3. Navigate to Resources > Policies.
  4. Select Manage.
  5. Select the created LTM Policy from the Available list and move it to the Enabled list.
  6. Select Finished.

    brotli requests blocked by LTM Policy

F5 Distributed Cloud mitigation

Background and Current Status

  • A dedicated WAF signature for CVE-2026-111497 mitigation does not currently exist in the F5 Distributed Cloud WAF catalog. At this time, it is not expected a signature will be released.

  • There are two known vector classes for exploitation of CVE-2026-111497:

    1. Send an HTTP request with crafted/malformed Brotli-encoded request body.

    2. Induce the application to fetch crafted/malformed Brotli-encoded data from an external source.

  • Neither vector can be completely and reliably mitigated with HTTP-based detective controls (WAF and WAF-adjacent components):

    1. Detection of the specific malformed Brotli-encoded payload would require Brotli-aware parsing.

    2. Paths to induce a remote fetch are application-dependent and theoretically unbounded.

  • Mitigation options can reduce exposure to known CVE-2026-111497 exploit vectors, but do not represent a complete remediation, and carry inherent false positive risk depending on legitimate application behavior.

  • Specific mitigation guidance is logically constructed for each vector as follows:

    1. Block POST/PUT/PATCH requests with declared Broti encoding in body. Note that this control cannot distinguish malicious from legitimate Brotli-encoded content. It is uncommon for HTTP clients to submit Brotli-encoded request content (it is more commonly used on the response side), but application owners should review their endpoint surface and verify suitability before deploying the rule in production.

    2. Enforce a domain allow list in url query parameter values submitted at the /_next/image path. This requires application owner awareness of allowable domains for external fetch, and does not cover application-specific vectors that induce the same behavior (including those that may not be seen by the Distributed Cloud load balancer).

  • The above mitigation rules can be implemented in Distributed Cloud Service Policies. Once again, they can reduce exposure to the aforementioned vectors, but do not provide complete remediation and must be assessed for potential impact to legitimate application traffic. 

Pseudologic for Service Policy Mitigation

(1) Block requests with declared Brotli-encoded body.

Create and apply to relevant LB(s) a Service Policy with the following rule:

  • Rule name: brotli-encoding

  • Match Conditions:

    • Methods: POST, PUT, PATCH

    • Header: Content-Encoding 

      • Regex match: \bbr\b

  • Action: DENY

This rule matches POST, PUT, or PATCH requests that contain Content-Encoding: br, with 'br' as a standalone word pattern. The word boundary avoids partial matches on strings like 'brief' or 'abrupt'. 

Application owners should review their endpoint surface and verify suitability before deploying the rule in production.

(2) Restrict the Next.js Image Optimizer url parameter to a domain whitelist (if you run Next.js). 

Create a Service Policy with two rules:

  • Rule 1:  permits legitimate requests with no 'url' parameter

    • Name: allow-no-url-param

    • Match Conditions:

      • Path Prefix: /_next/image

      • HTTP Query Parameter: url  Not Present

    • Action: NEXT_POLICY

  • Rule 2: if the 'url' parameter exists at this URL, which we know it does since it didn't match rule 1, restrict its value to URLs for domains on the allow list.

    • Name: next-image-url-allowlist

    • Match Conditions:

      • Path Prefix: /_next/image

      • HTTP Query Parameter: url   

        • Regex line 1:  ^$

        • Regex line 2:  ^https?:/{1,2}([^/?#@]*\.)?xc\.com([:/?#].*)?$

    • Action: DENY
