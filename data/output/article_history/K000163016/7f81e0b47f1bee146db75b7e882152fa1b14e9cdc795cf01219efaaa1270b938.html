IKEv2 IKE_AUTH Failure When Server and Client Machine Certificates Share Identical Subject/CN, Issuer, and SAN (BIG-IP APM Access IPsec VPN)

Applies to: BIG-IP APM 21.1.0+ (Access IPsec VPN / IKEv2 with machine certificate authentication)

Symptom

After the APM Access Policy completes successfully (machine certificate authentication passes, connectivity resource/webtop assigned), the Edge Client remains stuck in "Connecting." IPsec communication is attempted, but BIG-IP does not respond to the client's IKE_AUTH request. No IKE SAs or IPsec SAs are established.

Environment

  • BIG-IP APM with an IPsec connectivity profile assigned to the virtual server
  • Access Policy using the Machine Cert Auth agent, followed by resource assignment
  • Separate certificate objects configured for the server (sys crypto cert) and the client machine cert, but both certs share identical identity attributes

Observed Cause

In this case, the server certificate and the client machine certificate had identical Subject/CN, Issuer, and SAN — differing only in serial number and validity period:

Server cert (/Common/server-cert):
  subject = C=US, ST=State, L=City, O=Example Corp, CN=vpn.example.com
  issuer  = DC=internal, DC=example, C=US, O=Example Corp, OU=CA, CN=example-ca
  SAN     = DNS:vpn.example.com

Client cert (/Common/client-machine-cert):
  subject = C=US, ST=State, L=City, O=Example Corp, CN=vpn.example.com   <- identical
  issuer  = DC=internal, DC=example, C=US, O=Example Corp, OU=CA, CN=example-ca  <- identical
  SAN     = DNS:vpn.example.com                                          <- identical
  (only serial number and validity dates differ)

Note: The precise internal certificate-validation mechanism that causes IKE_AUTH to fail under this condition was not identified during troubleshooting. This is an observed correlation from case resolution, not a documented root-cause mechanism.

Resolution

Changing the Subject/CN of the client machine certificate to a distinct value (different from the server certificate) resolved the connection failure. IPsec connectivity was successfully established after this change.

Recommended Action

  • Ensure the BIG-IP server certificate and the client machine certificate used for IKEv2 authentication have distinct Subject/CN values. Do not reuse identical subject identities across server and client certificates.
  • If IKE_AUTH fails after Access Policy/machine cert authentication succeeds and IPsec traffic is attempted, compare openssl x509 output of both certificates for identity overlap as part of triage.
