K000163734: F5 ASM and APM Integration - login page (/my.policy)

Published

2026-10-15
Applies to

Source

Description

When BIG-IP ASM is placed in front of a BIG-IP APM virtual server, requests to the APM /my.policy endpoint may be blocked after the client is redirected to that endpoint.

The issue is related to ASM processing the APM /my.policy redirect and session-establishment flow.

The initial application request may pass through ASM successfully. APM then returns a redirect to /my.policy and generates APM session related data (compression, encryption etc). When the client follows the redirect, the /my.policy request is processed by ASM. ASM may identify the APM-generated request, cookie, or HTTP content as a policy violation and block it before the request reaches APM.

The issue is resolvedf by an iRule that disables ASM for /my.policy.

Environment

  • BIG-IP APM
  • BIG-IP ASM or Advanced WAF
  • APM virtual server protected by a layered ASM virtual server
  • APM access policy using /my.policy
  • SAML authentication may or may not be configured
  • BIG-IP 14.x or later supported releases

Cause

APM generates and processes the /my.policy request as part of the access-policy and session-establishment flow. ASM may inspect this request on the layered virtual server and block it based on the configured security policy.

Transparent mode does not bypass ASM processing. Requests continue to be inspected and may still be blocked when a violation is detected.

The supported architecture is to place ASM on a layered virtual server in front of the APM virtual server. This allows ASM to process traffic before APM access-policy evaluation. However, APM authentication-related requests such as /my.policy require an ASM bypass.

See K54217479: How to protect an APM virtual server with ASM.

Resolution

1. Use a layered ASM virtual server

Configure ASM on a separate client-facing virtual server and keep the APM access profile on the dedicated APM virtual server.

The procedure and example layered virtual-server configuration are documented in K54217479.

2. Confirm the affected request

Before changing the ASM policy, review the ASM event logs and request details for the failed transaction.

Check whether the blocked request:

  • Uses the /my.policy path.
  • Occurs after an APM redirect.
  • Contains APM session cookies such as MRHSession or LastMRH_Session.
  • Generates an HTTP protocol compliance violation.
  • Is blocked before reaching the APM virtual server.

Analyze the redirect response and the subsequent /my.policy request separately. In the reported behavior, the subsequent request to /my.policy is the request that must be allowed to reach APM.

3. Bypass ASM only for /my.policy

If the ASM event confirms that /my.policy is the affected request, create a narrowly scoped ASM bypass for that path.

F5 documents Local Traffic Policy and iRule methods for disabling ASM for selected requests in K22021244: Bypassing the BIG-IP ASM system (12.1.0 and later).

Example iRule:

when HTTP_REQUEST {
    set path [string tolower [HTTP::path]]

    if { $path starts_with "/my.policy" } {
        ASM::disable
    }
}

Apply the iRule to the layered ASM virtual server. Test the rule in a controlled environment and ensure that the match is limited to the required APM endpoint.

A Local Traffic Policy can also be used. Place the specific /my.policy rule before the general ASM-processing rule and configure the action to disable ASM at request time.

Do not bypass ASM for all traffic on the virtual server unless the security requirements and application design explicitly allow it.

Alternative policy adjustment

If the ASM event identifies a specific violation involving APM-generated cookies or HTTP protocol compliance, review and adjust the policy instead of bypassing the entire /my.policy request.

K13401: BIG-IP APM client traffic may be blocked by the BIG-IP ASM security policy describes related APM/ASM interactions involving:

  • MRHSession
  • LastMRH_Session
  • Modified domain cookies
  • Header names without values
  • Missing Host headers
  • Host headers containing an IP address

K13401 is marked Legacy Content and applies to older BIG-IP versions and configurations. Use it as related diagnostic information, not as confirmation that the same historical defect applies to the current release.

Any policy relaxation should be limited to the confirmed violation and evaluated against the security requirements of the application.
