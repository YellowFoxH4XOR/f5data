K000157372: Failure to boot into new software volume after upgrading UEFI-enabled BIG-IP VE system in GCP

Type
Support Solution
Published
2026-11-10
Updated
2026-11-10
Applies to

  • BIG-IP LTM
Source

Description

Upgrading pre-17.5.0 GCP BIG-IP VE instance with the UEFI_COMPATIBLE guest OS feature enabled on the GCP image can result in the following symptoms:

  • Remaining on the old software version after the upgrade reboot
  • mcpd and devmgmt fail to start and enter a restart loop

Environment

  • GCP
  • UEFI_COMPATIBLE image
  • 17.1.x upgrade to 17.5.x

Cause

The UEFI_COMPATIBLE guest OS feature causes GCP to boot the instance through UEFI. This bypasses the MBR-based GRUB configuration that BIG-IP updates when a new volume is installed, so the device keeps loading the first volume. UEFI boot support for BIG-IP was added in 17.5.0 (RFE 1270525). Images at 17.1.x do not include it.

ID2149173 and ID2141373 have been raised for this issue.

Recommended Actions

The recommended, but more involved method of recovering from this situation is to deploy a new VE instance from scratch and restore configuration from UCS. The new image must be 17.5.0 or higher if the UEFI_COMPATIBLE flag is needed for the instance.

A second workaround also exists if the second volume being installed is 17.5.0. The new volumeset can be mounted temporarily within the old software installation to make use of its UEFI-compatible tools:

VOLUME="HD1.2"   # Set this to the volume that contains the failed 17.5.x (or higher) installation
volumeset -f mount "$VOLUME"
mount --bind /proc "/mnt/${VOLUME}/proc"
mount --bind /dev "/mnt/${VOLUME}/dev"
GRUB_FILE="$(chroot /mnt/${VOLUME} grub_open)"
chroot "/mnt/$VOLUME" sed -i 's/default=0/default=1/' "$GRUB_FILE"
chroot "/mnt/$VOLUME" grub_close
umount "/mnt/${VOLUME}/proc" "/mnt/${VOLUME}/dev"
volumeset -f umount "$VOLUME"
reboot
