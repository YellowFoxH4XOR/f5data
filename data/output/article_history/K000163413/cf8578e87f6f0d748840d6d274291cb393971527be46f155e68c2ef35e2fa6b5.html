K000163413: Configuration deployment using automation via NIM API call is not reloading nginx to make the configuration active

Type
Support Solution
Published
2026-09-24
Updated
2026-09-24
Applies to
  • NGINX Products
  • NGINX Instance Manager
Source
https://my.f5.com/manage/s/article/K000163413

Description

NGINX Instance Manager API deployments may report success and update the NGINX configuration, while the active NGINX worker processes continue using the previous configuration. The NGINX Agent may log a successful reload even though the reload signal was sent to a third-party monitoring companion process instead of the actual NGINX master process.

Environment

  • NGINX Instance Manager.
  • NGINX Agent.
  • NGINX instances managed through NGINX Instance Manager.
  • Configuration deployments submitted through the NGINX Instance Manager API, such as through Ansible.
  • A third-party monitoring agent with NGINX deep monitoring enabled.
  • The monitoring agent creates a helper process with a command line similar to:

    nginx: OneAgent companion process

  • The actual NGINX master process has a command line similar to:

    nginx: master process /usr/sbin/nginx -c /etc/nginx/nginx.conf

  • Both processes can have parent PID 1.

Cause

The NGINX Agent process-discovery filter is too permissive and identifies processes whose command line begins with nginx: as NGINX processes.

The third-party monitoring companion process therefore can be incorrectly classified as an NGINX master process. The companion process and the actual NGINX master process can resolve to the same NGINX identifier, causing a collision in the Agent process map.

The Agent may then select the companion process and send the reload signal to it. The Agent logs the reload as successful, but the actual NGINX master and worker processes are not reloaded.

Recommended Actions

Apply the NGINX Agent process-discovery fix that restricts matching to actual NGINX master and worker process patterns.

After applying the fix:

  1. Deploy a configuration through the NGINX Instance Manager API.
  2. Confirm that the deployment reports success.
  3. Confirm that the Agent reload message references the actual NGINX master process.
  4. Verify that NGINX worker process start times change after deployment.
  5. Confirm that the new configuration is active without requiring a manual reload.

Additional Information

Use one of the following workarounds until the NGINX Agent fix is available:

  1. Disable NGINX deep monitoring in the third-party monitoring agent.
  2. Determine whether the third-party monitoring agent can rename its companion process so that its command line does not begin with nginx:.
  3. Manually reload NGINX when immediate configuration activation is required:
    systemctl reload nginx

Use the following command to compare the NGINX processes:

ps -eo pid,ppid,lstart,cmd | grep -i nginx | grep -v grep

The reload must target the process identified as the actual NGINX master, for example:

nginx: master process /usr/sbin/nginx -c /etc/nginx/nginx.conf

A reload message that references the third-party monitoring companion process does not confirm that NGINX was reloaded.

A successful API response, NGINX Instance Manager deployment status, or Agent success message alone does not confirm that the active NGINX workers were refreshed. Compare worker process start times before and after deployment to verify the reload.

The nginx -T command can show the updated configuration even when the running worker processes have not been reloaded. Verify both the configuration output and worker process start times.
