K000163615: F5OS RESTCONF returns limited data before a local user changes the initial password

Type
Support Solution
Published
2026-10-08
Updated
2026-10-08
Applies to
  • F5OS Products
  • F5OS
  • F5OS-A
  • F5OS-C
Source
https://my.f5.com/manage/s/article/K000163615

Description

Newly created local user accounts on F5OS may return only minimal RESTCONF/API data instead of full configuration data until the account completes the mandatory first-login password change. Affected sessions can appear authenticated, but API responses may contain only limited user information such as authorized-keys, blank or minimal username, last-change: "0", tally-count, role, and expiry-status, rather than the expected full openconfig-system:system configuration.

Environment

  • RESTCONF/API queries to endpoints such as restconf/data/openconfig-system:system
  • Local user accounts intended for scripted or service-account API access
  • Systems using local authentication, including deployments where TACACS+ may also be configured as fallback
  • Newly created local accounts where the initial password was set but the user has not yet logged in and changed that password

Cause

F5OS policy requiring a password change on first login for newly created local user accounts. Until that password change is completed, the account can be internally treated as limited, resulting in restricted REST API visibility.

Answer/Recommended Actions

  • After creating a local user account and setting its initial password, log in as that user and complete the required password change.
  • For service accounts intended for RESTCONF/API automation, create the account with a temporary password, then immediately log in as that account and change the password to the desired final value before using it in scripts.
  • If RESTCONF output is unexpectedly minimal, verify the account state by checking whether the user shows last-change as 0.
  • Compare RESTCONF output before and after completing the first-login password change to confirm the account is no longer restricted.
  • If testing via CLI, review the local user details with:
    show system aaa authentication users user <username>
  • If testing via API, retry the same query after the password change using the updated credentials.
  • If the behavior is not obvious from CLI or API output, test login through the WebUI, where the forced password-change prompt is exposed.

Additional Information

  • This behavior can be misleading because authentication may appear to succeed while authorization remains effectively restricted for RESTCONF/API access.
  • The issue may resemble a role-mapping, permissions, or configuration-difference problem across otherwise similar devices.
  • In observed cases, devices returning minimal output showed last-change as 0, while devices returning full output showed a valid date for last-change.
  • The restriction is not clearly indicated through normal API or CLI behavior and may only become obvious when logging in through the WebUI.
