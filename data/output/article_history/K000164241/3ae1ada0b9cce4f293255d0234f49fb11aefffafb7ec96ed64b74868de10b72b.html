 Description

 A VELOS system has two system controllers. They run active/standby for management and the cluster control plane, and active/active for backplane traffic. Each chassis partition also runs active/standby across the two  controllers. A split brain is when both controllers, or both partition instances, claim the same role: both active, or both standby.

 

 Symptoms can show up at any layer:

 - Both controllers' prompts show active, and each controller reports itself as current-active.

 - The floating management IP address (VIP) is unreachable, because both controllers are standby.

 - Partition configuration or API calls fail or fail back.

 - BIG-IP tenants in an HA pair go active/active.

 

 Rebooting a controller while the other controller is not cluster-ready has the same effect as rebooting both at once, and can lead to an extended outage.

 

 Environment

 - VELOS chassis with two system controllers

 - One or more chassis partitions; BIG-IP tenants, optionally in HA pairs

 

 Cause

 The two controllers, or the two partition instances, lose contact with each other. Usually this is the internal network between the controllers: the control-plane link, the controller switch fabric, or a hung controller. When

 the link is restored, the partition HA pair returns to the preferred controller (see Bug ID 2187625 for a known issue after that recovery).

 

 Recommended Actions

 

 1. Understand the layers. Look top-down, fix bottom-up.

   Layer 3 Tenants (BIG-IP): traffic groups, failover, mirroring

   Layer 2 Chassis partitions (F5OS-P): partition HA, blades, VLANs, LAGs

   Layer 1 Controller software (F5OS-C): controller redundancy, ConfD, OpenShift/etcd, switch fabric

   Layer 0 Host OS: hardware, kernel, kubelet, Docker, DRBD

   A symptom at a higher layer is often caused by a lower one. Find the lowest layer that is broken, and fix that first.

 

 2. Rules before rebooting, reseating, or failing over a controller

   At every moment, at least one controller must be active and cluster-ready. Never reboot, reseat, or run go-standby on the only ready controller.

Do not reboot "to try": first know which layer is broken and why the reboot fixes it. For the full rolling-reboot procedure, see the companion article "Reboot both VELOS system controllers safely (rolling reboot)" (link once published).

 

 3. Readiness check before manual failover (see K000160334)

   On the controller that is, or will become, active:

    show cluster

     cluster orchestration-manager cluster-initialized true

     cluster orchestration-manager cluster-ready true

     cluster orchestration-manager etcd-ha-running true

     all stages Done; both controllers "In Cluster"

     summary-status "Openshift cluster is healthy, and all controllers and blades are ready."

    show system redundancy-details state hardware

     LOCAL HEALTHY true for both controllers

   If any item fails, stop. Do not fail over to that controller, and do not reboot the other one.

   Read the individual fields, not only the summary line: the summary can report all controllers ready while the node table shows a controller NotReady.

 

 4. Detect split brain

   Log in to each controller using its own management IP address, not the floating IP address.

   Controller layer:

    

show system redundancy state   (both controllers must report the same current-active)

    show cluster           (same active-node on both; etcd-ha-running true)

    show system redundancy-details state hardware  (exactly one controller with LOCAL ACTIVE GRANTED true)

  

 Split brain looks like this:

    - each controller reports itself as current-active and active-node;

    - both prompts show active;

    - etcd-ha-running is false;

    - redundancy-details returns "Error: application error".

   Both controllers can still show "In Cluster" during a split brain. An error from these commands is a failed check, not missing data.

  

 Partition layer (partition CLI):

    show system redundancy  (one controller node active and one standby, fault false, status redundant)

  

 Tenant layer (BIG-IP):

    tmsh show cm failover-status  (a traffic group must not be active on both devices)

 

 5. Recover

   First restore the connection between the two sides. Save qkviews from both controllers before you make changes.

   - Both controllers active: keep the controller that passes step 3. On the other controller, using its own IP address:

     config

     system redundancy go-standby

    

If it does not change role, or if both or neither controller pass step 3, contact F5 Support. Do not reboot either controller until the good controller is known.

   - Both controllers standby (no floating IP address): contact F5 Support. Setting system redundancy config mode prefer-1 or prefer-2 on the controller that passes step 3 makes it the preferred active controller. Return the 

 mode to auto afterwards.

   - Chassis partition active on both controllers: this resolves to the preferred controller when the internal connection is restored. If go-standby then fails back immediately, see Bug ID 2187625. The workaround is to restart  the partition HA service on the non-preferred controller:

     system diagnostics os-utils docker restart node controller-2 service partition<ID>_ha

    This affects configuration and the data path. Perform it during a maintenance window.

   - Tenants active on both devices: restore the HA path first (HA VLAN and LAG in both partitions, controllers healthy). Then, on the tenant that should be standby:

     

tmsh run sys failover standby

    

Do not reboot tenants to resolve active/active.

   - Controller failed but still inserted, and blocking recovery: contact F5 Support (see Bug ID 1752821, /var/omd/FORCE_PEER_CC_MISSING).

 

 Additional Information

 - Log messages that mark a controller role change (/var/log_controller/velos.log): "role change detected", "ConfD is now Active", "ConfD is now Standby", "standby confd lost contact with active confd".

 - Controller redundancy modes: auto (default), prefer-1, prefer-2. Partition redundancy modes add active-controller (see Bug ID 1696269).
