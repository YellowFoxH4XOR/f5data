K000163643: ICANN DNS trust anchor rollover impact

Type
Support Solution
Published
2026-10-10
Updated
2026-10-23
Applies to
  • BIG-IP
  • BIG-IP DNS
Source
https://my.f5.com/manage/s/article/K000163643

Description

BIG-IP DNS validating resolvers with manually configured DNSSEC trust anchors may fail DNSSEC validation and return SERVFAIL for queries after the ICANN root KSK rollover on 11 October 2026 if only the KSK-2017 (key tag 20326) trust anchor is present. This occurs when trust anchors are managed under ltm dns cache validating-resolver ... trust-anchors and are not automatically updated to include the new KSK-2024 (key tag 38696).

Environment

  • BIG-IP DNS

  • Validating resolver DNS caches with DNSSEC validation enabled

  • Trust anchors manually configured under ltm dns cache validating-resolver ... trust-anchors

  • Only KSK-2017 (key tag 20326) present as trust anchor

Cause

Manually maintained trust anchors do not include the new root KSK-2024 (key tag 38696), resulting in DNSSEC validation failures after the root KSK rollover.

Answer/Recommended Actions

  • Check the current trust anchors using:
    tmsh list ltm dns cache validating-resolver <resolver_name> trust-anchors

  • If only key tag 20326 is present, obtain the KSK-2024 DS record (key tag 38696) from the IANA root anchors publication.

  • Add the new KSK-2024 DS trust anchor using the add command, not replace-all-with, to ensure both KSK-2017 and KSK-2024 are present until January 2027. The GUI equivalent is DNS > Caches > Cache List, select the validating resolver, open the Trust Anchors tab, and select Add. See Related Content for the full procedure.

  • Save the configuration and verify both trust anchors are present.

  • If the validating resolver is part of an HA pair or other BIG-IP DNS systems, sync the configuration to the HA peer and apply the same change to the other systems.

  • Test DNSSEC query handling with a DNSSEC-enabled query.

  • After January 2027, remove the KSK-2017 (key tag 20326) trust anchor.

  • Only the DS record is required as a trust anchor; do not upload a certificate file or add a DNSKEY record.

    Additional Information

    • Only the SHA-256 DS digest is required for the new KSK-2024 trust anchor.

    • Forward zones using upstream nameservers are not directly affected, but upstream resolvers should also be checked for rollover readiness.

    • After the KSK-2024 anchor is added, SERVFAIL responses can persist for names already held in the cache. Negative cache entries tied to the expired DS record remain until they expire, so the failure rate declines gradually rather than dropping to zero immediately. In the reported case, the SERVFAIL rate fell from about 100 percent to about 25 percent after the change and continued to decline. Track the decline with DNS cache statistics (Statistics > Module Statistics > DNS > Caches) and do not treat residual SERVFAIL for previously cached names as a failed fix.
    • No dedicated BIG-IP syslog message, SNMP trap, or email alert was identified for expiration of a manually configured validating-resolver trust anchor. To detect recurrence, a DNS logging profile with response logging enabled can be attached to the listener and forwarded to a syslog or SIEM destination. Filter the response events for SERVFAIL. Logging both queries and responses affects BIG-IP performance.
