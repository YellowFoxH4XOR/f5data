K000164039: WideIP flapping after migration

Type
Support Solution
Published
2026-10-28
Updated
2026-11-01
Applies to
  • BIG-IP
  • BIG-IP DNS
Source
https://my.f5.com/manage/s/article/K000164039

Description

BIG-IP DNS (GTM) virtual servers may flap between UP and DOWN states when LTM virtual servers with the same name exist on several LTM systems monitored by the same BIG-IP DNS.

Symptoms:

  • DNS Virtual servers alternate between available and unavailable states.
  • The GTM log shows a monitor state change for the VIP on the old LTM. Example log entry:

Monitor instance /Common/bigip 192.168.2.0:1528 UP --> DOWN from 10.0.0.1 (DOWN)

 

  • The SNMP trap shows the parent server being marked unavailable. Example: VS /Common/vs_member1.example.com-1528 ... state change green --> red (Parent server /Common/gtm_server_1 marked VS unavailable.)

Environment

  • You have more then one BIG-IP LTM which has a virtual server configured with the same name (vs_member1.example.com-1528) but with different IP addresses
  • The virtual server on one of the BIG-IP LTMs is in down or disabled state
  • Virtual Server Discovery is enabled on the DNS system

 

Cause

  • The cause is a duplicate virtual server name across different LTM systems that are monitored by the same BIG-IP DNS
  • iQuery monitors virtual servers' status using the cached LTM VIP names, not the IP address and port.
  • One LTM has virtual server in down or disabled state. When iQuery queries the LTM, it returns DOWN.
  • BIG-IP DNS then probes another LTM, which returns UP for the same virtual server name.
  • The alternating DOWN and UP results causes the GTM virtual server, pool, and Wide IP to flap.

 

Answer/Recommended Actions

  • Apply "ltm-name" to one of the affected virtual servers following the article K53557413
  • As alternative, rename the affected LTM virtual server by deleting it on one of the LTMs and create a new one using a different name.
  • Use static method for adding DNS virtual server
