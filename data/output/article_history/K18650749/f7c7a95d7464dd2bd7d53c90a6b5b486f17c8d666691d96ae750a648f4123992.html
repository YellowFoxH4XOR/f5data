Topic

This article applies to BIG-IP 13.1.0 and later. For information about earlier versions, refer to the following article:

  • K54335130: Configuring brute force attack protection (12.1.2 - 13.0.x)

You should consider using these procedures under the following condition:

  • You want to configure the security policy to mitigate brute force attacks.

Description

In a brute force attack, the attacker attempts to gain unauthorized access to a secured area of the web application by making multiple username/password guesses with the hope of eventually guessing correctly; the attack involves systematically checking all possible passwords and passphrases until the correct combination is found.

The BIG-IP Advanced WAF/ASM system can detect brute force attacks from a single source (source-based brute force protection) or from multiple sources (distributed brute force protection) and mitigate the attacks by tracking the number of failed login attempts for a URL that is defined in the security policy and taking an action when an attack is detected.

For source-based brute force protection, the system tracks the number of failed login attempts per source (username, device ID and IP address) over a detection period. When the configured threshold for a source is exceeded, the system performs the configured enforcement action. If the threshold for one or more sources is exceeded, the system applies the strictest configured enforcement action among the triggered sources. Note that successful logins do not reset the failed login attempts over the detection period. The following table lists the configurable enforcement action sorted from the least strict to the most strict.

Note: Depending on the setting, some of these enforcement actions may not be applicable and may not be available for that setting.

Enforcement actionDescription
AlarmThe system only logs the login attempt.
Alarm and Client Side IntegrityThe system logs the login attempt and sends a page containing JavaScript code to determine whether the client is a legal browser or a bot. Note that legal browsers can execute the JavaScript code and return a valid response while a bot is not able to.
Alarm and CAPTCHAThe system logs the login attempt and sends a CAPTCHA challenge to determine whether the client is operated by a human user.
Alarm and Blocking PageThe system logs the login attempt, blocks the request and sends the blocking page.
Alarm and Honeypot PageThe system logs the login attempt, blocks the request and sends the default Honeypot page. The purpose of the Honeypot page is for attacker deception and should look like an application failed login page. You can customize the Honeypot page by selecting Custom Response for the Response Type setting under the Failed Login Honeypot option located on the following page:

BIG-IP 15.x and later:

Security > Application Security > Security Policies > Policies List > <policy name> > Policy Configuration > Response and Blocking Pages

BIG-IP 14.x and earlier:

Security > Application Security > Policy > Response Pages

Alarm and DropThe system logs the login attempt and resets the TCP connection.

For distributed brute force protection, the system tracks the number of failed login attempts for the configured login page over a detection period. If credential stuffing attack detection is enabled, the system tracks the number of login attempts that match known leaked credentials dictionary. When the configured threshold for either or both is exceeded, the system applies the configured enforcement action until either attack stops or the maximum prevention duration has passed. The following table lists the configurable actions.

Enforcement actionDescription
AlarmThe system only logs the login attempt.
Alarm and Client Side IntegrityThe system logs the login attempt and sends a page containing JavaScript code to determine whether the client is a legal browser or a bot. Note that legal browsers can execute the JavaScript code and return a valid response while a bot is not able to.
Alarm and CAPTCHAThe system logs the login attempt and sends a CAPTCHA challenge to determine whether the client is operated by a human user.
Alarm and Client Side Integrity followed by CAPTCHAThe system logs the login attempt and sends a page containing JavaScript code to determine whether the client is a legal browser or a bot upon the first failed login attempt from a source, it then sends a CAPTCHA challenge upon the second and subsequent failed login attempts.

Starting in BIG-IP 16.1.x, you can configure the BIG-IP Advanced WAF/ASM system to match presented credentials to the known leaked credentials dictionary provided by Cloud Security Services such as Blackfish Credential Stuffing Service. To do so, you must first configure the Cloud Security Service Application with the subscribed service credentials and API endpoint on the Security > Cloud Services > Cloud Security Services Applications page. For more information about configuring the Cloud Security Service Application, refer to the Registering Leaked Credential Check with BIG-IP Cloud Services chapter of the F5 Leaked Credentials Check Implementation Guide. When you have configured the cloud security service on the BIG-IP Advanced WAF/ASM system, proceed to enable the Detection setting under the Leaked Credentials Detection section and select the action you want the system to perform:

Alarm and Blocking PageThe system only logs the login attempt which includes the matched username from the known leaked credentials dictionary, blocks the request and sends the blocking page.
Alarm and Honeypot PageThe system only logs the login attempt which includes the matched username from the known leaked credentials dictionary, blocks the request and sends the default Honeypot page. The purpose of the Honeypot page is for attacker deception and should look like an application failed login page. Security > Application Security > Security Policies > Policies List > <policy name> > Policy Configuration > Response and Blocking Pages

Alarm and Leaked Credentials PageThe system only logs the login attempt which includes the matched username from the known leaked credentials dictionary, blocks the request and sends the default Leaked Credentials response page. The default Leaked Credentials response page warns the user that the username and password have been leaked and the password should be changed. You can customize the Leaked Credentials response page by selecting Custom Response for the Response Type setting under the Leaked Credentials option located on Security > Application Security > Security Policies > Policies List > <policy name> > Policy Configuration > Response and Blocking Pages.

Prerequisites

You must meet the following prerequisites to use these procedures:

  • You have access to the Configuration utility.
  • You have defined one or more login URLs and specified the appropriate authentication type for the URL.

Configure brute force attack protection

To configure the security policy to mitigate brute force attacks, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to the Brute Force Attack Prevention page:
    • 17.x and later: Security > Application Security > Security Policies > Policies List > <policy name> > Advanced Protection > Brute Force Prevention
    • 14.x - 16.x: Security > Application Security > Brute Force Attack Prevention
    • 13.1.x: Security > Application Security > Anomaly Detection > Brute Force Attack Prevention
  3. Select a login page from the Login Page menu, or select Create to create a login page.
  4. If you have subscribed to credential stuffing cloud security services and configured the Cloud Security Services Application on the BIG-IP Advanced WAF/ASM system, you should enable the Detection setting under the Leaked Credentials Detection section and select the appropriate action from the Mitigation Action setting.
  5. In the Source-based Brute Force Protection section, define the following settings:
    • Detection Period

      The time period in minutes in which the system tracks the number of failed login attempts. This period works as a sliding window for each enabled source. The default is 60 minutes.

    • Maximum Prevention Duration

      The time period in minutes in which the system applies the enforcement action on the source when the configured threshold is exceeded. The default is 60 minutes.

    • Username

      When enabled, the system tracks the number of failed login attempts based on username for the login page. The default threshold is three failed login attempts and the default action is Alarm and CAPTCHA.

    • Device ID

      When enabled, the system tracks the number of failed login attempts based on device ID. Typically, device ID is not known for non-browser clients. This setting is disabled by default.

    • IP Address

      When enabled, the system tracks the number of failed login attempts based on the source IP address. Note that it is possible a single IP address may represent more than one user, especially when the IP address is a NAT address. As a result, the default threshold is higher than the other two sources at 20 failed login attempts. The default action is Alarm and CAPTCHA.

    • Client Side Integrity Bypass Mitigation

      This setting is only relevant when one or more sources has selected Alarm and Client Side Integrity as their enforcement actions. When enabled, the system attempts to identify cases where the Client Side Integrity challenge has passed, but the login attempt still fails. The default threshold is three successful challenges with failed logins and the default action is Alarm and CAPTCHA.

    • CAPTCHA Bypass Mitigation

      This setting is only relevant when one or more sources has selected Alarm and CAPTCHA as their enforcement actions. When enabled, the system attempts to identify cases where the CAPTCHA challenge has passed, but the login attempt still fails. The default threshold is five successful challenges with failed logins and the default action is Alarm and Drop.

  6. In the Distributed Brute Force Protection section, define the following settings:
    • Detection Period

      The time period in minutes in which the system tracks the number of failed login attempts. The default is 15 minutes.

    • Maximum Prevention Duration

      The time period in minutes in which the system applies the enforcement action when configured threshold(s) is/are exceeded. The default is 60 minutes.

    • Detect Distributed Attack

      When enabled, the system tracks the number of failed login attempts and applies mitigation when the threshold is exceeded. The default threshold is 100 failed login attempts.

    • Detect Credential Stuffing

      When enabled, the system tracks the number of login attempts with credentials matching the credentials stuffing dictionary. The default threshold is 100 login attempts matching the credentials stuffing dictionary.

    • Mitigation

      The system applies the configured mitigation action. The default mitigation action is Alarm and CAPTCHA.

  7. If you are editing an already existing login page, select Update. If you are adding a new login page, select Add.
  8. Select Apply Policy.

    Note: For the brute force attack protection to work, the security policy's Enforcement Mode setting must be set to Blocking and both the Alarm and Block flags are enabled for Brute Force: Maximum login attempts are exceeded violation (under Sessions and Logins section). You can find these settings in Security > Application Security > Policy Building > Learning and Blocking Settings page.

View brute force logging data

You can view the event logs to see whether brute force attacks have occurred, and review information about the attacks. To do so, perform the following procedure:

Impact of procedure: Performing the following procedure should not have a negative impact on your system.

  1. Log in to the Configuration utility.
  2. Go to Security > Event Logs > Application > Brute Force Attacks.
  3. By default, the page displays brute force attack event logs based on Attack Start Time. You can switch to display event logs based on Number of Login Attempts or select the funnel and filter events by Login Page, Attack Type, or Mitigated Entity.
  4. Review the list of brute force attacks to see which URLs were attacked, and the start and end times of the attack.
