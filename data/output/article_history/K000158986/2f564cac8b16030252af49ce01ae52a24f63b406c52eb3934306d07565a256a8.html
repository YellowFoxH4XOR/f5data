Description

TCL errors such as "<REWRITE_REQUEST_DONE> - ERR_ARG (line 1) invoked from within 'HTTP::host'" or "<REWRITE_REQUEST_DONE> - No HTTP header is cached - ERR_NOT_SUPPORTED (line 1) invoked from within 'HTTP::header exists \"Host\"'" may occur when iRules for BIG-IP APM Portal Access attempt to access HTTP headers in the REWRITE_REQUEST_DONE event. This is especially likely with large POST requests and when iRules are used to switch SSL profiles based on request hostnames.

Environment

  • BIG-IP APM Portal Access
  • iRules using REWRITE_REQUEST_DONE and SERVER_CONNECTED events
  • iRule logic accessing HTTP headers (e.g., HTTP::host, HTTP::header exists "Host")
  • SSL profile switching based on request hostname
  • Large POST requests to portal access resources

Cause

HTTP headers are not reliably cached or accessible in the REWRITE_REQUEST_DONE event, particularly for large POST requests. The system may have already forwarded headers or transitioned to chunked payload handling, resulting in TCL errors when iRule commands attempt to access header data at this stage.

Recommended Actions

  • Avoid using HTTP::host or HTTP::header commands in the REWRITE_REQUEST_DONE event for iRules in BIG-IP APM Portal Access.
  • Use the HTTP_REQUEST event instead, where HTTP headers are available.
  • Adapt iRule logic to perform hostname or header checks in HTTP_REQUEST, and set flags or variables for use in subsequent events (such as SERVER_CONNECTED).
  • If issues persist, collect QKView and traffic traces for further analysis.

Additional Information

  • The ACCESS_ACL_ALLOWED event occurs earlier in the flow and can be used if header access is required before rewriting.
  • This behavior is expected due to internal memory optimization and event sequencing in BIG-IP APM Portal Access.
  • The issue is more prevalent with large POST requests, where payload and headers are processed separately.
