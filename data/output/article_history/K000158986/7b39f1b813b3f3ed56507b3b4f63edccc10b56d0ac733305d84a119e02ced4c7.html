K000158986: iRule error ERR_ARG for HTTP::host or HTTP::path in the REWRITE_REQUEST_DONE event

Description

You use an iRule on a BIG-IP APM Portal Access virtual server, and the iRule reads HTTP request data, for example with HTTP::host, HTTP::header, HTTP::path, or HTTP::uri, in the REWRITE_REQUEST_DONE event. Some requests fail, and the iRule logs TCL errors.

When you troubleshoot this issue, you may observe the following symptoms:

  • The /var/log/ltm file contains TCL errors similar to the following examples (the iRule name, line number, and process ID vary):

    err tmm2[<pid>]: 01220001:3: TCL error: /Common/<irule_name> <REWRITE_REQUEST_DONE> - ERR_ARG (line 1) invoked from within "HTTP::host"

    tmm[<pid>]: 01220001:3: TCL error: /Common/<irule_name> <REWRITE_REQUEST_DONE> - No HTTP header is cached - ERR_NOT_SUPPORTED (line 15) invoked from within "HTTP::host"

  • A packet capture shows a reset with the reset cause iRule execution error.

  • The errors occur for some requests only, more often for large POST requests, for example file uploads.

Environment

  • BIG-IP APM 17.1.x, 17.5.x or 21.1..x

  • Portal Access resource and rewrite profile

  • An iRule that reads HTTP request data in the REWRITE_REQUEST_DONE event, for example to select a Server SSL profile or an SNI value by host name

Cause

The REWRITE_REQUEST_DONE event runs after Portal Access has processed and rewritten the request. Depending on the state of the request flow at that point, the HTTP request headers may no longer be available to the iRule. For example, Portal Access may have already forwarded the headers, or, for a large POST request, it may already be processing the request payload. In this state, HTTP commands that read the request, such as HTTP::host or HTTP::header, fail with a TCL error.

Note: Many iRules read HTTP::host in the REWRITE_REQUEST_DONE event and work as expected for most requests, for example the iRules in K40453455: Portal Access to an internal HTTPS site fails when the server requires SNI. The issue in this article occurs only for some requests, depending on the flow state.

Answer/Recommended Actions

Read the HTTP request data in an event in which the headers are available, store the result in a variable, and use the variable in the later events (for example REWRITE_REQUEST_DONE, SERVER_CONNECTED, or SERVERSSL_CLIENTHELLO_SEND).

Impact of procedure: Test iRule changes in a non-production environment before you apply them to production.

  1. Identify the iRule and the line from the TCL error in /var/log/ltm.

  2. Move the HTTP commands from REWRITE_REQUEST_DONE to an earlier event:

    • ACCESS_ACL_ALLOWED: runs earlier in the flow, when the request headers are available.

    • HTTP_REQUEST: runs before Portal Access rewrites the request. In this event, the request path still contains the Portal Access prefix (/f5-w-<hex>$$), and the back-end host is encoded in hexadecimal in the prefix. Make sure that your iRule logic matches the request before it is rewritten.

  3. In the earlier event, set a variable (for example a flag or a host name). In the later events, check that the variable exists with info exists before you use it, and unset it after use.

  4. Start a new access session, repeat the requests that failed (including large POST requests), and verify that /var/log/ltm has no new TCL errors from the iRule.

If the issue persists, open a support case. Provide the iRule, the TCL error messages, and the data listed in the Collect HTTPWatch or HAR files for support section of K14184: Troubleshooting BIG-IP APM Portal Access applications.

Note: F5 Support does not design or configure iRules. If you need help to adapt an iRule to your environment, contact F5 Professional Services.
