Description

After upgrading BIG-IP VE tenants on rSeries appliances from version 17.5.1.5 to 17.5.1.6, multiple issues were observed: GUI failures, truncated TMM core files, and-most critically - TMM failing to start on one or more tenants. The TMM startup failure was accompanied by repeated log messages such as "Waiting for tmm1 to reach state 1...".

Environment

BIG-IP LTM tenants running version 17.5.1.6

Platform: F5-BIG-R4800 (rSeries), C131

F5OS-A platform version 1.8.4

High Availability (HA) pair configuration

Cause

The root cause of TMM failing to start after upgrade is a race condition affecting TMM and MCPD communication, particularly on rSeries platforms. When TMM0 is stalled waiting for other TMMs (which are themselves stalled pending MCPD, which is stalled waiting for ARP replies that never arrive because TMM0 is stalled), the system enters a deadlock. The fix for Bug ID1697041 (which addressed similar symptoms on other platforms) does not apply to rSeries due to differences in packet polling and disaggregation mechanisms. The issue was tracked under Bug ID2298633.

Answer/Recommended Actions

Apply Engineering Hotfix Hotfix-BIGIP-17.5.1.6.0.250.25-ENG.iso to affected tenants.

If TMM fails to start, attempt manual restart of TMM as a temporary workaround, issuing the command:

restart /sys service tmm

Before performing initial upgrade, enable sys db tmm.mcp.disconnect.core to force TMM to restart automatically when MCPD <-> TMM connection is disrupted (may help avoid indefinite stalls, but not always effective). You can do it by issuing the command:

modify /sys db tmm.mcp.disconnect.core value true

save /sys config

Monitor for recurrence and provide QKview and logs to F5 Support if issues persist.

For hardware faults (CPU IERR), perform RMA of the affected appliance.
