Description

When you create an HTTP Load Balancer in F5 Distributed Cloud and choose HTTPS with Automatic Certificate, XC automatically requests and provisions a TLS certificate for your domain from Let's Encrypt. Before that certificate can be issued, you must prove that you control the domain. This proof is done through DNS.

This article explains:

  • What the ACME challenge is and why a DNS record is required
  • The two supported ways to complete domain validation and obtain an AutoCert
  • How to verify that your certificate has been issued
  • How to troubleshoot the most common error: PreDomainChallengePending

Environment

  • HTTP Load Balancer
  • DNS Zones

What is the ACME challenge?

ACME (Automated Certificate Management Environment) is the standard protocol used by Certificate Authorities (CAs) such as Let's Encrypt to issue certificates automatically. To make sure a certificate is only issued to the rightful domain owner, the CA issues a challenge that the requestor must satisfy.

The flow works like this:

  1. Request – After registering with the ACME CA, the client (in this case, F5 XC on your behalf) requests a certificate for your domain.
  2. Challenge – The CA returns a one-time random token and asks for it to be published in DNS, under the reserved record _acme-challenge.<your-domain>.
  3. Validation – Once the token is published, the CA performs a DNS lookup against the authoritative servers for the domain. If it finds the correct token, ownership is confirmed.
  4. Issuance – The certificate is signed and delivered, and XC applies it to your Load Balancer.

For renewals this whole process repeats automatically so you only configure DNS once.

Method 1 — Primary DNS Zone with "Allow HTTP Load Balancer Managed Records"

With this method, XC hosts the DNS zone and creates/removes every required record (including the ACME challenge) for you.

What you need

  • A domain you own at a registrar. (F5 is not a domain registrar, so the parent domain must be registered elsewhere like Cloudflare, GoDaddy, Route 53...)

Steps

  1. In the XC Console, create a Primary DNS Zone for the domain or subdomain you want XC to manage. Location: Home > DNS Management > Manage > DNS Zone Management
  2. In your DNS Zone configuration, enable Allow HTTP Load Balancer Managed Records. This grants XC permission to create and maintain the records needed by the Load Balancer.
  3. At your registrar (or in the parent zone), point the NS records for that zone to F5's name servers
    1. ns1.f5clouddns.com
    2. ns2.f5clouddns.com
  4. Create the HTTP Load Balancer with HTTPS with Automatic Certificate enabled, using a hostname inside that zone.
 






What happens behind the scenes


  • XC automatically creates the required records (visible under Additional Resource Record Sets in the Primary DNS Zone).
  • A temporary _acme-challenge.<host> record is created for validation and is automatically removed once the certificate is issued — this is expected behavior.
  • After issuance, XC creates the A record pointing the domain to the Load Balancer's VIP.


Provisioning typically completes in about 5–10 minutes, though backend synchronization can occasionally take longer (allow up to 24 hours).




Example: A Primary DNS Zone "delegated.example.com" is created in XC, its NS records are pointed at ns1/ns2.f5clouddns.com, and a Load Balancer is created for test.delegated.example.com. No manual record creation is needed.




Method 2 — Self-Managed DNS (non-delegated)


Use this method when the zone must remain on your own DNS provider. You will create two CNAME records by hand.


Important: You do not need to change any NS records with your DNS provider for this method. Only the two CNAME records below are required.


Steps


  1. Create the HTTP Load Balancer with HTTPS with Automatic Certificate enabled and enter your application domain.
    Path in Console: WAAP > your-namespace > Manage > Load Balancers > (⋯) > Manage Configuration > Edit Configuration
  2. Open the Load Balancer configuration and click DNS Information to obtain the two values XC generated for you (the ACME challenge target and the Load Balancer host name). If the LB hosts multiple domains, an ACME record is shown per domain.
  3. In your own DNS provider, create the ACME challenge record:

    _acme-challenge.<your-domain>   CNAME   <UID>.autocerts.ves.volterra.io
    

  4. Create the application domain record, pointing it at the Load Balancer host name:

    <your-domain>   CNAME   ves-io-<UID>.ac.vh.ves.io
    

  5. Wait for Let's Encrypt to query the domain (up to 24 hours, usually much less).


Example (domain demo.example.com):


_acme-challenge.demo   CNAME   XXXXXXXXXXXX.autocerts.ves.volterra.io
demo                   CNAME   ves-io-XXXXXXXXXXXX.ac.vh.ves.io


The ACME challenge CNAME is what allows the certificate to be issued; the application domain CNAME is what allows traffic to actually reach the Load Balancer. After the initial setup, certificates auto-renew with no further DNS changes.


Why CNAME instead of TXT?


A standard DNS-01 challenge is satisfied with a TXT record. F5 XC instead request you to publish a CNAME that delegates _acme-challenge.<your-domain> to F5's autocerts.ves.volterra.io.


This lets F5 create, rotate, and update the underlying challenge value automatically on its side, so a renewal happen with minimal manual intervention on your side.


Verifying that the certificate was issued


  • In the XC Console, the Load Balancer shows Auto Cert State: Certificate Valid once issuance succeeds.
  • You can also click View Status on the HTTP Load Balancer to see the current certificate state and any error description.
  • To confirm your DNS record resolves correctly, use dig:

    dig CNAME _acme-challenge.<your-domain>
    
The answer should return the *.autocerts.ves.volterra.io target you configured.


Notes on the certificate


  • Only the first domain on the Load Balancer is shown under auto_cert_subject.
  • One automatic certificate is provisioned per Load Balancer. Additional domains on the same LB are included as SAN (Subject Alternative Name) entries on that single certificate.


Troubleshooting: PreDomainChallengePending


PreDomainChallengePending means the certificate request has started but Let's Encrypt has not yet been able to validate domain ownership — the DNS challenge has not completed. In almost all cases this is a DNS configuration or DNS propagation issue.


Check these first


  1. Confirm you used a supported method. Either a Primary DNS Zone with Allow HTTP Load Balancer Managed Records (Method 1) or the two self-managed CNAME records (Method 2). Delegated Domains are deprecated and will not work.
  2. Verify the ACME challenge record exists and resolves. Run:

    dig CNAME _acme-challenge.<your-domain>
    
If nothing is returned, or the value does not match the <UID>.autocerts.ves.volterra.io target shown in the Console, the record is missing or incorrect — re-create it.
  3. Allow time for propagation. DNS changes and the backend sync can take up to 24 hours, though it is usually 5–10 minutes. Wait and re-check before assuming a failure.
  4. Avoid duplicate or conflicting records. In an XC-managed (Primary DNS) zone, do not create the same records manually with another provider, and do not manage subdomains of a zone XC already manages. Duplicates cause inconsistent behavior and can block issuance.
  5. Use View Status. On the Load Balancer, click View Status, then open the object to read the Error Description. A "missing or invalid record" message confirms a DNS-side problem you can correct with the steps above.


If it still does not resolve


If you have confirmed the correct method, verified the record with dig, removed any duplicates, and waited for propagation but the certificate remains stuck in PreDomainChallengePending, open a support case with F5 so the platform side can be investigated.


Delegated Domains are deprecated


The legacy Delegated Domain feature was deprecated (October 2023). New domains can no longer be onboarded with Domain Delegation.


The supported replacement is to use an F5 XC Primary DNS Zone together with the Allow HTTP Load Balancer Managed Records option (Method 1 below), or to manage the records yourself (Method 2 below).




Note: XC does not support switching an existing Load Balancer between managed (delegated) and self-managed (non-delegated) DNS, and does not support mixing both in the same Load Balancer. If you need to change approach, create a new Load Balancer.
