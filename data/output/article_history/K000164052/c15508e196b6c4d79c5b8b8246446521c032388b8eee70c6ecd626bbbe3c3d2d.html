K000164052: ACME Providers stuck in Updating state

Type
Support Solution
Published
2026-10-29
Updated
2026-10-29
Applies to
  • BIG-IP
  • BIG-IP LTM: 21.1.0
Source
https://my.f5.com/manage/s/article/K000164052

Description

BIG-IP ACME providers that previously issued certificates can stop working. Certificate requests fail with the following error:
Code: [], Details: [Internal error: newOrder URL not available in directory listing]

The ACME provider objects may then remain in an Updating state for an extended period, even after a restart of restjavad, restnoded, and tomcat, or a system reboot.
Clearing the stale Updating state can leave the provider in an Error state, with account-status error shown in the configuration.

Relevant log messages observed in this scenario:

err tmsh[...]: 01420006:3: 01020036:3: The requested Virtual Server (/Common/proxy-acme) was not found.
err mcpd[...]: 01070734:3: Configuration error: Deleting ACME provider '/Common/<provider>' not allowed: account-action ('update') is in progress.
err keymgmtd[...]: 01a40000:3: Failed to create ACME account. curl_code=0, response_code=403, error=
err mcpd[...]: 01070712:3: Caught configuration exception (0), Values (<vs>) specified for ACME Provider (/Common/<provider>): foreign key index (acme_internal_proxy_FK) do not point at an item that exists in the database.
err mcpd[...]: 01070734:3: Configuration error: ACME provider (/Common/<provider>) missing required field: internal proxy

Environment

  • BIG-IP VE, version 21.1.0.x (Standalone configuration)
  • Native ACMEv2 integration with Let's Encrypt, using two ACME providers (production and staging)
  • ACME providers using challenge-type http-01
  • ACME providers referencing an internal proxy (sys internal-proxy) with a dedicated DNS resolver (net dns-resolver)
  • A virtual server on port 80 with acmev2-challenge enabled and an iRule that redirects HTTP to HTTPS while allowing /.well-known/acme-challenge/ requests through
  • Configuration changes made to an existing ACME provider, or a provider that was previously in use

Cause

Unknown at time of publication.

  • Bug ID 2471597 describes After an ACME account update, the account-action value may remain set to update even though the account status is valid.
  • This leaves the provider in an Updating or Pending state and may prevent additional account changes, certificate operations, or provider deletion. 
  • Clearing the stale Updating state can leave the provider in an Error state, with account-status error shown in the configuration.

Recommended Actions

Perform the following steps from the BIG-IP command line.
Replace <acme-provider> with the provider name.

  1. Clear a stuck Updating state by resetting the account action:
    tmsh modify sys crypto acme-provider <acme-provider> account-action none
    tmsh save sys config
    tmsh list sys crypto acme-provider <acme-provider>

  2. Delete the ACME provider:

    tmsh delete sys crypto acme-provider <acme-provider>

    If the delete fails with the following error, repeat step 1 and then delete the provider again:

    account-action ('update') is in progress

  3. Create a dedicated account key before recreating the provider:

    • Navigate to System > Certificate Management > Traffic Certificate Management > SSL Certificate List and create a self-signed certificate and key that is used only for the ACME account.
    • Do not use default.key as the account key.
  4. Recreate the ACME provider and select the dedicated key as the account key. Confirm that the internal proxy and DNS resolver are correctly configured, and that the provider is linked to the internal proxy.

  5. Confirm that the HTTP-01 challenge path is reachable:

    • Ensure the virtual server on port 80 has acmev2-challenge enabled.
    • Ensure any iRule that redirects HTTP to HTTPS does not redirect /.well-known/acme-challenge/ requests.
    • Follow the ACME provider setup steps in the SSL certificate management documentation to verify the configuration.
  6. Verify that the provider shows account-status valid, then retry certificate issuance.

Note: Applying K000163249 to clear the Updating state may leave the provider in an Error state. If this occurs, use steps 2 through 6 above.

Additional Information

  • In one reported scenario, deleting and recreating the ACME providers with a dedicated account key resolved the issue, and certificates were issued successfully for two domains. Renewal behavior after this change was not verified at time of publication.
  • The default.key account key is generated per device. In an HA pair, the active and standby units would use different keys, which can cause ACME account validation problems.
  • Log entries showing Values (...) specified for ACME Provider ... foreign key index (acme_internal_proxy_FK) do not point at an item that exists in the database indicate that the provider's internal proxy reference is missing or invalid. Verify that sys internal-proxy exists and is referenced by the provider.
