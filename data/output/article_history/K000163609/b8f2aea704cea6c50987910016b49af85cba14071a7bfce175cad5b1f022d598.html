K000163609: ASM Violations Logged as “Unblocked from iRule” When Session Tracking Delay Blocking Is Enabled

Type
Support Solution
Published
2026-10-08
Updated
2026-10-08
Applies to
  • BIG-IP
  • BIG-IP ASM
Source
https://my.f5.com/manage/s/article/K000163609

Description

ASM may log a security violation with the following values:

  • Enforcement Action: None
  • Request Status: Unblocked
  • Blocking Exception Reason: Unblocked from iRule

This message can appear even when there are attached iRules that do not contain ASM functions such as ASM::unblock or ASM::noblock. It can also appear when no iRules are attached to the virtual server configuration.

The behavior occurs when the violation is included in the Session Tracking Delay Blocking configuration under Associated Violations. That can be found per the link provided Security  ››  Application Security : Session Tracking :: Delay Blocking:: Associated Violations.

The Blocking Exception Reason: Unblocked from iRule can occur when any violation is selected in the Associated Violations list. For example, Evasion Technique Detected may exhibit this behavior.

Environment

  • BIG-IP ASM
  • Security policy in Blocking mode
  • One or more violations configured to block
  • The affected violation included in the Session Tracking Delay Blocking Associated Violations list
  • A Session Tracking threshold and delay-blocking period configured

Cause

Session Tracking Delay Blocking intentionally delays enforcement for violations selected in the Associated Violations list.

Before the applicable Session Tracking threshold is reached, the system does not immediately block requests that trigger one of the selected violations. The AdvWAF Event Log may represent this result with the blocking exception reason:

Unblocked from iRule

This reason does not necessarily indicate that an iRule unblocked the request. In this scenario, the message describes the internal handling of the delayed request and can be misleading.

Violations that are not included in the Associated Violations Selected list continue to follow the normal blocking settings of the security policy.

Using IP Address Threshold as an example it states..."Note: For IP addresses which caused 5 violations in the last 60 seconds, the system will block illegal requests for 600 seconds. Before reaching this threshold: For the selected violations, the system will not block users; for the rest of the violations, the system immediately blocks the users, according to the blocking settings configuration of the security policy."

1.    So the first 4 are not blocked if they happen within 60 seconds.
2.    If a fifth one arrives within that 60 seconds that violation will be blocked for the following 600 seconds per the policy configuration.

When it does not block the system uses a function similar to the iRule event ASM::unblock. Then to provide a "reason" it uses "Blocking Exception Reason: Unblocked from iRule".

Resolution

1) Before deciding that what is occurring is due to how ASM/AdvWAF handle these you should review:

  1. Confirm that the affected violation is configured to block in the ASM policy.
  2. Confirm whether the violation is present in the Session Tracking Delay Blocking > Associated Violations list.
  3. Review the configured Session Tracking threshold, tracking dimension, threshold window, and delay-blocking period.
  4. Verify that the attached iRules do not contain ASM unblock commands.
  5. Generate a request that triggers the affected violation.
  6. Confirm that removing the violation from the Associated Violations list causes the request to follow the policy’s immediate blocking configuration.

2) If a violation must be blocked on its first occurrence:

  1. Open the affected ASM security policy.
  2. Navigate to Security > Application Security > Session Tracking.
  3. Open the Delay Blocking configuration.
  4. Review the Associated Violations list.
  5. Remove the violation that must be blocked immediately.
  6. Save the configuration.
  7. Apply the updated security policy.

Review all entries in the Associated Violations list and remove any violation that should not use delayed enforcement.

If delayed enforcement is intentional, no configuration change is required. The request status and “Unblocked from iRule” reason are expected for applicable requests before the configured Session Tracking threshold is reached.

Additional Information

  • The Associated Violations list can contain multiple violation types.
  • This behavior is controlled by Session Tracking Delay Blocking, not by the name of the violation.
