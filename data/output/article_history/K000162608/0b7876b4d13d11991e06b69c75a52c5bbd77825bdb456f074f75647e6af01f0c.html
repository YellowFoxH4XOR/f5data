Security Advisory Description

NGINX Plus and NGINX Open Source have a vulnerability in the ngx_http_core_module module. When asynchronous file I/O (AIO) is enabled in certain configurations, processing a Server Side Includes (SSI) page containing include virtual commands may trigger a Use-After-Free (UAF) in the NGINX worker process. This may cause memory corruption or cause a worker process to terminate unexpectedly. Additionally, attackers can execute code on systems with Address Space Layout Randomization (ASLR) disabled or when the attacker can bypass ASLR. (CVE-2026-97205)

Impact

This vulnerability may allow remote attackers to cause a denial-of-service (DoS) on the NGINX system, corrupt its memory, or possibly trigger code execution. There is no control plane exposure; this is a data plane issue only.

If the Fixes introduced in column does not list a version for your branch, then no update candidate currently exists for that branch and F5 recommends that you upgrade to a version with the fix (refer to the tables).

If the Fixes introduced in column lists a version prior to the one you are running, in the same branch, then your version should have the fix.

Mitigation

To mitigate this vulnerability, you can either disable AIO or SSI. To do so, perform one of the following procedures, based on your environment requirements:

  • Disable asynchronous file I/O (AIO)
  • Disable Server Side Includes (SSI)

Disable asynchronous file I/O (AIO)

Disabling AIO removes the asynchronous processing path that triggers the memory corruption while leaving SSI functionality intact.

Impact of action: Disabling AIO may impact performance on systems serving large static files or media streaming under high concurrency, as worker processes may block on disk I/O. For standard reverse proxy, API gateway, or typical web workloads, the performance impact should be negligible. F5 recommends testing all configuration changes in an appropriate test environment before implementing them in production.

  1. Locate any instances of aio on; or aio threads; in the HTTP, server, or location contexts of your configuration files.
  2. Set the directive to off or remove the directive entirely, since off is the default behavior. For example:

    # --- Before (Vulnerable) ---
    http {
      ...
      aio on; # or aio threads;
      ...
    }
    # --- After (Mitigated) ---
    http {
      ...
      aio off;
      ...
    }

  3. To test the configuration syntax, use the following command:

    sudo nginx -t

    The output should appear similar to the following example:

    nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
    nginx: configuration file /etc/nginx/nginx.conf test is successful

    Note: If you chose to remove the directive entirely rather than setting it to off, F5 recommends that you use the nginx -T command to confirm that included files in your configuration do not unintentionally re-enable the directive. The nginx -t option tests the configuration and exits while the nginx -T option will also dump the effective configuration to the terminal.

  4. To reload the NGINX configuration, use the following command:

    sudo nginx -s reload

Disable Server Side Includes (SSI)

If your environment heavily relies on AIO for high-throughput disk I/O and does not rely on NGINX-rendered SSI tags, disable SSI processing.

Impact of action: If your application uses SSI directives like <!--# include file="includes/header.html" -->, disabling SSI will cause those tags to be served in the HTML source rather than being processed by NGINX. F5 recommends testing all configuration changes in an appropriate test environment before implementing them in production.

  1. Locate any instances of ssi on; in the HTTP, server, or location contexts of your configuration files.
  2. Set the directive to off or remove the directive entirely, since off is the default behavior. For example:

    # --- Before (Vulnerable) ---
    server {
      listen 80;
      server_name example.com;

      location / {
        ssi on;
        ...
      }
    }
    # --- After (Mitigated) ---
    server {
      listen 80;
      server_name example.com;

      location / {
        ssi off;
        ...
      }
    }

  3. To test the configuration syntax, use the following command:

    sudo nginx -t

    The output should appear similar to the following example:

    nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
    nginx: configuration file /etc/nginx/nginx.conf test is successful

    Note: If you chose to remove the directive entirely rather than setting it to off, F5 recommends that you use the nginx -T command to confirm that included files in your configuration do not unintentionally re-enable the directive. The nginx -t option tests the configuration and exits while the nginx -T option will also dump the effective configuration to the terminal.

  4. To reload the NGINX configuration, use the following command:

    sudo nginx -s reload
