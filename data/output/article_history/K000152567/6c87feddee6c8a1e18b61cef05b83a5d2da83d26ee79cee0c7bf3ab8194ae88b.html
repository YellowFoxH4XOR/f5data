Description

There are 4 parameter value violations:

  • VIOL_PARAMETER_VALUE_BASE64
    • The system checks that the value is a valid Base64 string. If the value is indeed Base64, the system decodes this value and continues with its security checks.
  • VIOL_PARAMETER_VALUE_LENGTH
    • The system checks that the request contains a parameter whose value length (in bytes) matches the value length defined in the security policy.
  • VIOL_PARAMETER_VALUE_METACHAR
    • The system checks that all parameter values, XML element/attribute values, or JSON values within the request only contain meta characters defined as allowed in the security policy. Enforces proper input values. In case of a violation, the reported value represents the decimal ASCII value (metachar_index), or, in case of using “json_log” the hexadecimal ASCII value (metachar) of the violating character.
  • VIOL_PARAMETER_VALUE_REGEXP
    • The system checks that the request contains an alphanumeric parameter value that matches the expected pattern specified by the regular-expression field for that parameter. Prevents HTTP requests which do not comply with a defined pattern. NGINX App Protect WAF lets you set up a regular expression to block requests where a parameter value does not match the regular expression.

Environment

When the violation is seen in the logs in will normally show as a violation_rating="1". A violation of 1 indicates it is most likely a false positive. However, depending upon the situation being seen it may not be.

With the Default Policy these violations are set to Alarm only by default. Since it is a rating of 1 the same would be true of the Strict Policy.

As each request comes in it is inspected based on how the policy is setup. When a request matches a rule or signature, it's considered a violation. The security policy determines the action (alert or block) for each violation based on its severity and configuration.

  • The severity is different based on whether the policy started as a default or strict policy (that can be reviewed here NGINX App Protect WAF Configuration Guide).
  • For parameters support is only auto-detect parameter value type and acts according to the result: plain alphanumeric string, XML or JSON.
  • It examines the request looking for patterns. If one is recognized then based on that severity and configuration the appropriate action, if any, is taken.

Cause

There are a couple of reasons why you may need to deal with this log entry...

  1. You have determined it is not a false positive.
  2. The shear number of these log entries is filling up the logs.
  3. You decide the constant alarms need to be dealt with.

Recommended Actions

Whitelist: That is manual based on violations. However the severity for a violation can vary based on the Adaptive Violation Rating.  NGINX App Protect WAF's Adaptive Violation Rating feature uses machine learning (ML) to analyze traffic patterns and automatically adjust the violation rating of requests, helping to reduce false positives and improve user experience. By continually assessing behavior, it can identify when a service's typical behavior changes and lower the violation rating for requests that would have been blocked, making the WAF more effective and less disruptive.

Block: If it becomes necessary to block then a manual change in the configuration is necessary.

In this example you will see where one metacharacter is blocked and one is whitelisted to pass through without a block or alarm.

{
    "policy": {
        "name": "parameters_allowed_metachars",
        "template": { "name": "POLICY_TEMPLATE_NGINX_BASE" },
        "applicationLanguage": "utf-8",
        "enforcementMode": "blocking",
        "blocking-settings": {
            "violations": [
                {
                    "name": "VIOL_PARAMETER_VALUE_METACHAR",
                    "alarm": true,
                    "block": true
                }
            ]
        },
        "parameters": [
            {
                "checkMetachars": true,
                "sensitiveParameter": false,
                "parameterLocation": "any",
                "valueType": "auto-detect",
                "nameMetacharOverrides": [
                    {
                        "isAllowed": false,
                        "metachar": "0x0a"
                    },
                    {
                        "isAllowed": true,
                        "metachar": "0x24"
                    }
                ],
                "metacharsOnParameterValueCheck": true,
                "allowEmptyValue": true,
                "checkMaxValueLength": false,
                "valueMetacharOverrides": [
                    {
                        "isAllowed": false,
                        "metachar": "0x0a"
                    },
                    {
                        "isAllowed": true,
                        "metachar": "0x24"
                    }
                ],
                "name": "*",
                "level": "global",
                "allowRepeatedParameterName": true,
                "attackSignaturesCheck": true,
                "signatureOverrides": [],
                "type": "wildcard"
            }
        ]
    }
}

Override Rules: If there are any special request attributes that they can use as conditions,  Override rules could help.  
"The Override Rules feature allows overriding of the default policy settings. Each override rule consists of a condition followed by changes to the original policy applied to requests that meet the respective condition. This feature provides the ability to include the override rules within a declarative policy such that all incoming requests are verified against those rules. "

For example:

{
    "name": "VIOL_PARAMETER_VALUE_METACHAR",
    "alarm": true,
    "block": false
}

as base, and

{
    "name": "VIOL_PARAMETER_VALUE_METACHAR",
    "alarm": true,
    "block": true 
}

in the override.
