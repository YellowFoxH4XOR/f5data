Description

When F5 Container Ingress Services (CIS) connects to a BIG-IP high-availability (HA) pair through a Floating Self IP with insecure: false Each BIG-IP can present its own device certificate. CIS must trust the certificate presented by whichever device is Active. This article explains how to provide more than one BIG-IP device certificate to CIS 2.20.4.

Environment

  • Product: F5 Container Ingress Services (CIS) 2.20.4
  • Platform: Red Hat OpenShift Container Platform (OCP)
  • BIG-IP: Active-Standby HA pair
  • CIS connection: Floating Self IP configured as bigip-url: <Floating_IP>
  • TLS verification: insecure: false
  • Certificates: One self-signed device certificate on each BIG-IP

Cause

None. This is a configuration task, not a defect.

Answer/Recommended Actions

CIS 2.20.4 trusts multiple BIG-IP device certificates through a single trusted-certs-cfgmap A multi-certificate PEM bundle was accepted by CIS with tag insecure: false (means enforced certificate check)insecure: false

Option 1: One PEM bundle in one ConfigMap key (tested)

  1. Collect the device certificate from each BIG-IP. Include certificates only. CIS does not need the private keys.
  2. Combine the certificates into one PEM file:
    cat bigip1.crt bigip2.crt > bundle.pem
  3. Confirm the bundle.pem contains all certificate 
    cat bundle.pem
     Output should be-----BEGIN CERTIFICATE----- and -----END CERTIFICATE-----
  4. Create the ConfigMap in the namespace where CIS runs:
    kubectl create configmap trusted-certs --from-file=./bundle.pem -n kube-system
  5. Confirm that the ConfigMap contains every certificate. 
     block should appear under 
    kubectl -n kube-system get cm trusted-certs -o yaml
kubectl -n kube-system describe configmap trusted-certs
kubectl -n kube-system get cm trusted-certs -o jsonpath='{.data.server_cert\.pem}' | \
openssl x509 -noout -subject -issuer -dates -fingerprint -sha256 -text | \
grep -E 'Subject:|Issuer:|Not |Fingerprint|Subject Alternative|IP Address|DNS'
  6. Set the following CIS arguments in the deployment: 
    --insecure=false
--trusted-certs-cfgmap=kube-system/trusted-certs
  7. Confirm that CIS starts without certificate errors: 
    kubectl -n kube-system logs deploy/cis-k8s-f5-bigip-ctlr --since=3m | grep -Ei 'x509|certificate|tls|\[ERROR\]'

Certificate requirements for HA with a Floating Self IP

Each device certificate SAN should include:

  • The Floating Self IP address
  • Each BIG-IP hostname (DNS name)
  • The self IP address of each device

With these entries, the certificate name matches the address CIS connects to, regardless of which device is Active.

Certificate changes

When a BIG-IP or CA certificate is renewed, update the ConfigMap with the new certificate and restart CIS, as described in the CIS Installation guide. Test this in a non-production environment first.

Additional Information

  • Failover does not require a CIS restart for certificate validation. CIS validated the certificate presented by the newly Active device without a restart.
  • CIS accepts the insecure parameter with a default of false. Setting insecure: true disables SSL verification and is not recommended.
  • If the insucure is false insecure: false and the ConfigMap is missing in CRD mode, CIS may fail with x509: certificate signed by unknown authority
