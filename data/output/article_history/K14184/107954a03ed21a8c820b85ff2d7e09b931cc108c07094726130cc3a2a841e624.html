Issue

You should consider using this procedure under the following condition:

  • Clients are having issues accessing Portal Access applications.

Symptoms

As a result of the reverse-proxy rewrite engine not correctly identifying information that needs to be redirected, you may encounter the following symptoms:

  • The webpage does not render.
  • Items on the web page may not render.
  • Links may not redirect properly.
  • Forms may not post properly.
  • There may be additional symptoms not listed here.

While the reverse-proxy engine rewrites content correctly in most cases, in some instances the rewritten code may cause the application to perform incorrectly through portal access. If an application does not load or perform correctly through a portal access web application, the following actions can assist in troubleshooting the issue.

Recommended Actions

The Portal Access Web Applications feature provides remote access to a variety of web-based applications. To ensure that web application traffic routes through the BIG-IP system, Portal Access utilizes a high-performance reverse-proxy engine to rewrite HTML, CSS, and JavaScript content.

Procedures

When experiencing web application issues, you can use the following troubleshooting actions to determine the root cause:

  • Accessing the web application directly
  • Accessing the web application with through BIG-IP APM with a different web browser
  • Accessing the web application with a different client system
  • Verifying client DNS resolution
  • Pinging the BIG-IP APM system to determine basic network connectivity
  • Conducting a network packet capture
  • Troubleshooting the BIG-IP APM web portal
  • Collect HTTPWatch or HAR files for support

Accessing the web application directly

To determine if an issue exists with the target web application, attempt to access the web application directly from the client system. If the symptoms are the same, an issue may exist in the target web application or web browser compatibility with the web application. Troubleshoot your back-end server and client system.

Accessing the web application through the BIG-IP APM system with a different web browser

To determine if an issue with browser compatibility exists, access the web application through the web portal using an alternate web browser such as Firefox or Chrome. If the issue is resolved, there may be a compatibility issue with the particular web browser or web browser version. To ensure you are using a compatible web browser, refer to K14047: Supported operating systems and web browsers for the BIG-IP APM system.

Accessing the web application with a different client system

To determine if the issue is isolated to a particular client system, access the web portal from a different client system. If the issue is resolved, the client system may be misconfigured. To troubleshoot your client system, use the Client Troubleshooting Utility (CTU) to assist in verifying the BIG-IP Edge Client configuration. For more information, refer to K12444: Overview of the Client Troubleshooting Utility for Windows.

Verifying client DNS resolution

To determine that the client system is able to correctly resolve the DNS name of the BIG-IP virtual server, you can use a tool such as nslookup to verify that the client can correctly resolve the DNS name of the BIG-IP virtual server. If DNS fails, you need to troubleshoot your DNS configuration.

For example:

Note: The following example uses the Microsoft Windows operating system.

Correct DNS result
C:\>nslookup webapp1.example.com
Server: dns.example.com
Address: 10.1.1.240
Non-authoritative answer: Name: webapp1.example.com
Addresses: 10.1.1.12

Unable to resolve DNS request
C:\>nslookup webapp1.example.com
Server: dns1.example.com
Address: 10.1.1.240
*** dns.example.com can't find webapp1.example.com: Non-existent domain

Pinging the BIG-IP APM system to determine basic network connectivity

You can ping the BIG-IP network interface to determine that it is responding to the client.

Note: Ping uses the Internet Control Message Protocol (ICMP) protocol, which may be blocked by network devices in the path.

For example:

Conducting a network packet capture

You can use a network sniffing tool such as WireShark to capture the client side traffic sent and received by the client. For more information about analyzing packet traces, refer to K1893: Packet trace analysis.

Troubleshooting the BIG-IP APM web portal

  1. Verify the configuration of your virtual server, access policy, portal access resource object, connectivity profile, and rewrite profile. For example, if the Portal Access resource is HTTPS, you should configure a Server SSL profile on the virtual server. 

    Note: Configuring a Server SSL profile on the virtual server should not affect other HTTP Portal Access resources. However, if you have other resources on your webtop, you should perform this change during a scheduled maintenance window.

  2. If you configured the Portal Access resource using a fully qualified domain name (FQDN), make sure that the BIG-IP system is able to resolve it using the DNS server configured in System > Configuration > Device > DNS.

    Note: Portal Access does not use static host entries in the /etc/hosts file. For more information, refer to K12257: BIG-IP APM resources that do not have DNS records may fail to load.

  3. If the virtual server that is hosting the Portal Access resource in question has a Compression profile, a Web Acceleration profile, or both attached to it, consider removing them from the virtual server to reduce complexity and unexpected results.

Collect HTTPWatch or HAR files for support

Before opening a case with support to help troubleshoot an issue with an application configured in Portal Access please gather the following items.

  1. An HTTPWatch/HAR file going directly to the application bypassing APM.
  2. An HTTPWatch/HAR file going through APM Portal Access
  3. Output from the browsers developers console (F12).
  4. Screenshots/Videos of the issue
  5. Qkview

NOTE: When collecting HTTPWatch/HAR files make sure the following.

  • When using HTTPWatch save in HWL format, you can use the free basic version to record and send it into support where we can read the full file.  This is the preferred method to capture data.
  • When recording data, make sure that you open the browser, start the capture then access the application, if the application opens a new tab, make sure that tab is recording and refresh the page to make sure the data is captured. 

After those items have been collected please open a support case and provide the details, if any additional information is needed it will be requested.
