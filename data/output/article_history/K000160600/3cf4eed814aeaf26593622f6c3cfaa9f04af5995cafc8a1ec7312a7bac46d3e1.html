K000160600: Site not loading through reverse proxy

Type
Support Solution
Published
2026-05-14
Updated
2026-05-14
Applies to
  • BIG-IP
  • BIG-IP APM: 17.5.1
Source
https://my.f5.com/manage/s/article/K000160600

Description

When a web application is accessed through BIG-IP APM Portal Access (webtop/reverse proxy), the application displays a blank or non-functional page. Direct access to the backend application works correctly. Packet capture and HAR analysis reveal that the backend server returns HTTP 404 responses on certain resources (such as static assets or JavaScript files). Further investigation shows that BIG-IP APM Portal Access removes the Accept-Encoding header from requests before forwarding them to the backend server. The backend application requires this header to serve content correctly, and its absence results in failed resource loads and a broken portal page.

Environment

BIG-IP APM

APM Portal Access resource (webtop) configured with a rewrite profile

Backend application that requires the Accept-Encoding header to serve content correctly (for example, iDRAC web interface or similar web applications)

BIG-IP version 17.x (may affect other versions)

Cause

BIG-IP APM Portal Access, by design, removes the Accept-Encoding header from requests forwarded to backend servers. This occurs because the APM rewrite engine processes and potentially re-encodes content. For certain backend applications, the absence of this header causes the server to return HTTP 404 responses for required resources (such as JavaScript files or static assets), resulting in a blank or broken page through the portal. Configuring the Accept-Encoding header via the Advanced headers section within the Portal Access resource item settings does not reliably re-insert this header.

Answer/Recommended Actions

Workaround: Apply an iRule to re-insert the Accept-Encoding header

Use the HTTP_REQUEST_RELEASE event to insert or replace the Accept-Encoding header after the APM rewrite engine has processed the request, immediately before it is forwarded to the backend server.

  1. Log in to the BIG-IP Configuration utility.
  2. Navigate to Local Traffic > iRules > iRule List.
  3. Click Create.
  4. Enter a name for the iRule (for example, apm_portal_insert_accept_encoding).
  5. In the Definition field, enter the following iRule:

    when HTTP_REQUEST_RELEASE {
        if { [HTTP::header exists "Accept-Encoding"] } {
            HTTP::header replace "Accept-Encoding" "gzip, deflate"
        } else {
            HTTP::header insert "Accept-Encoding" "gzip, deflate"
        }
    }

  6. Click Finished.
  7. Navigate to Local Traffic > Virtual Servers and click the name of the APM portal access virtual server.
  8. Click the Resources tab.
  9. In the iRules section, click Manage.
  10. Move the newly created iRule to the Enabled column.
  11. Click Finished.
  12. Start a new APM session and verify the application loads correctly through the portal.

Troubleshooting steps to confirm the root cause before applying the workaround:

  1. Collect HAR traces for both direct access and portal access to the backend application and compare request headers. Confirm that Accept-Encoding is present in the direct access trace but absent in the portal access trace.
  2. Enable SSL decryption on the BIG-IP for packet capture:

    tmsh modify sys db tcpdump.sslprovider value enable

  3. Collect a packet capture from the BIG-IP (not from the client workstation):

    tcpdump -nni 0.0:nnn --f5 ssl -vw /var/tmp/capture.pcap host <client_ip> or <backend_server_ip>

  4. Disable SSL decryption after capture:

    tmsh modify sys db tcpdump.sslprovider value disable

  5. Analyze the decrypted capture. If the Accept-Encoding header is missing in requests from BIG-IP to the backend server and the backend returns HTTP 404 on resources, apply the iRule workaround above.

Additional Information

  • The HTTP_REQUEST_RELEASE event is the correct iRule event to use in the context of BIG-IP APM Portal Access. Portal Access involves two separate traffic flows (client-to-BIG-IP and BIG-IP-to-backend), and using HTTP_REQUEST_SEND or HTTP_REQUEST may not behave as expected for the server-side flow.
  • This behavior (removal of Accept-Encoding) is by design in the APM rewrite engine and is not classified as a defect. However, for applications that depend on this header, the iRule workaround above is effective.
  • Note: Adding Accept-Encoding headers via the Advanced header configuration within the Portal Access resource item settings (under the Portal Access resource configuration) has been observed to be unreliable for re-inserting this header.
  • If a Web Acceleration or Compression profile is also assigned to the virtual server, consider removing it temporarily during troubleshooting to reduce complexity.
