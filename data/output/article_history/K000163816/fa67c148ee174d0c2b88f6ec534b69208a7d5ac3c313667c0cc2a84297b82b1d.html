Description

IPv6 HTTPS and ICMP probe traffic can stop when the TMM deployment is scaled to multiple pods. Virtual servers created from F5BigContextSecure resources may fail proxy initialization and enter the EDENY state with Defaulting to DENY.

Environment

  • BIG-IP Next CGNAT CNF deployed on OpenShift
  • TMM deployment scaled from one to multiple pods
  • F5BigContextSecure resources reference F5BigFastl4Setting profiles whose names differ from the existing resource names by letter case

Cause

The F5BigContextSecure resources referenced FastL4 profile names containing uppercase characters, while the corresponding F5BigFastl4Setting resource names were lowercase. TMM pods received the lowercase profile resource but could not initialize virtual servers that referenced the uppercase profile name. The virtual servers consequently defaulted to DENY (EDENY).

Answer/Recommended Actions

  1. Review each affected F5BigContextSecure resource and ensure that spec.fastL4Settings.profileName exactly matches the corresponding F5BigFastl4Setting resource name, including letter case.
  2. If the resources are managed through Git or Argo CD, update the authoritative source manifests and apply the configuration change.
  3. Scale the TMM deployment to the required production pod count.
  4. Verify the virtual-server status on every TMM pod. All virtual servers should report OK, not EDENY:
    oc exec -n f5-cnf <tmm-pod> -c debug -- tmctl -d blade virtual_server_stat -s name,conf_status
  5. Verify IPv6 HTTPS and ICMP probe operation across all TMM pods.

Additional Information

Restarting the ingress controller can temporarily restore service for TMM pods that exist when the controller restarts. TMM pods added after the restart can enter EDENY until the FastL4 profile references are corrected. The Warning, ICMP error limit reached message was observed only on pods with denied virtual servers and is a consequence of denied traffic rather than the cause.
