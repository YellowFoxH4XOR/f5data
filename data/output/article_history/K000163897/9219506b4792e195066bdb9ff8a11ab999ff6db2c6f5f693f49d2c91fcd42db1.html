K000163897: F5OS-C: Address Resolution Protocol requests intermittently fail to reach BIG-IP tenants during excessive broadcast or unknown unicast traffic

Published

Description

You have intermittent connectivity loss between upstream devices, such as firewalls, and virtual servers or self IP addresses on BIG-IP tenants that run on a VELOS system. When this occurs, you observe some or all of the following symptoms:

  • The upstream device sends broadcast Address Resolution Protocol requests for the BIG-IP virtual server or self IP address, but some requests never reach the tenant interface.
  • Packet captures show the ARP requests arriving at the partition, but the same requests are missing from captures taken on the tenant. ARP resolution may succeed only after later requests
  • The rx_dlf counter, the rx_bcast counter, or both increase sharply in the rbcast_pkt_stat table on one or more partition blades.
  • The system does not log a message or send an alert when it drops these packets.

Environment

  • VLANs shared by multiple tenants
  • A high rate of broadcast or Destination Lookup Failure (DLF) traffic (unknown unicast traffic flooded by upstream switches) on those VLANs
  • Upstream devices with short ARP cache timeouts that send repeated broadcast ARP requests 

Cause

When F5OS receives a broadcast ARP request, it cannot tell which tenant owns the requested IP address. The software rebroadcaster therefore sends a copy to every tenant configured on that VLAN. If the combined rate of broadcast and DLF traffic is more than the software rebroadcaster can process, its buffers fill and it silently drops packets, including ARP requests, before they reach the tenant. F5 Engineering classifies this as expected behavior under excessive broadcast or DLF flooding, not a software defect. The software rebroadcaster has no rate limit that you can view or configure.

Answer/Recommended Actions

  • On upstream devices that send frequent broadcast ARP requests, increase the ARP cache timeout to at least 240 seconds, unless you have a specific operational reason to keep a lower value.
  • Configure upstream devices to use unicast ARP requests after the first resolution, where supported. F5OS forwards a unicast ARP request only to its destination, but must copy a broadcast ARP request to every tenant on the VLAN.
  • If you lowered the BIG-IP tenant ARP timeout, restore it to the default of 300 seconds unless you have a documented reason to use a lower value.
  • Make sure the content-addressable memory (CAM) or MAC address table timeout on upstream switches is longer than the ARP cache timeout on upstream devices. This reduces unknown unicast flooding.
  • Consider reducing the number of VLANs shared between tenants. Tighter VLAN separation per tenant may tolerate higher broadcast rates. Validate any design change before you put it into production.

Additional Information

F5 is tracking the following enhancement requests. They are not currently available features:

  • ID2202129: Generate a Simple Network Management Protocol (SNMP) trap when the rate of dropped DLF or direct memory access (DMA) packets rises significantly.
  • ID2200245: Generate a syslog message when the rate of dropped DLF or DMA packets rises significantly.
  • ID2238549: Provide a configurable DLF rate limit.
