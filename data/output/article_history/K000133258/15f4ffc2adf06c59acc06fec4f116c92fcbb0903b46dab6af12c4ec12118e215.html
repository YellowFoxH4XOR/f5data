Description

Beginning in BIG-IP 15.1.9, 16.1.4 and 17.1.0, db restjavad.useextramb is removed and you can use provision.restjavad.extramb to provision memory for restjavad.

When you try to modify or list the value of sys db restjavad.useextramb you see an unexpected response:

      01020036:3: The requested database variable (restjavad.useextramb) was not found.
      
The sys DB key restjavad.useextramb has been removed as provision.restjavad.extramb was introduced in recent versions, and in this further change restjavad.usextramb is now not needed. While restjavad.useextramb is removed in an update, keep in mind it may not have been the most recent update, as you may not notice until you choose to change its value.

Changes to restjavad memory should now be made by altering the value of provision.restjavad.extramb and restarting restjavad. Increases above the default size do require sys db provision.extramb to be at least the size of the increment. An alternative way of looking at that is you can have the value of provision.extramb you need and size restjavad memory size so as not to use all that extra host memory.
      
There are also some tweaks to the defaults and how the memory settings are applied. This includes better logging to ltm logging when restjavad starts, so do look at the log after making memory changes along with the restjavad restart.

Environment

All BIG-IP versions that have fix for ID 1153865. At the time this article was written this is TMOS versions 15.1.9, 16.1.4 and 17.1.0 and releases after these.

Cause

This is a behavior change to simplify restjavad memory size setting, but still allow precise control of restjavad heap size with some independence from value of provision.extramb. It also fixes issues introduced by the introduction of provision.restjavad.extramb by ID 1025261 where it initially sized the value to the minimum. 

Recommended Actions

In general the new default settings should suit most uses, but it is possible to precisely set heap size within certain limits (see additional information).
Here are some examples of how to make the restjavad heap larger, smaller or return it to the default size - remember to restart restjavad after making changes.

  • Set restjavad memory to default settings
  • Increase restjavad memory
  • Reduce restjavad memory

Set restjavad memory to default settings

If you wish to set restjavad back to default settings, which previously would have been done by setting restjavad.usextramb to false:

        tmsh modify sys db provision.restjavad.extramb reset-to-default

or functionally equivalent:

        tmsh modify sys db provision.restjavad.extramb value 384

Note: Set values take precedence over default values. If a default value changes any set value will override that. In this recent change the default was updated from 192 to 384 but if there was a value set - even at 192 - that will be honoured. So the difference between the two examples above is that by setting a value of 384 you indicate that you wish to use that value even if the default value changes in the future.

When you restart restjavad after making either of those changes you should see something like this log in /var/log/ltm:

        notice restjavad[xxxxx]: Heap size is default: starting 96 MB and maximum 384 MB

The settings database has both default and possibly user set values with the latter overriding the former if present. So the difference is if you set the value 384 then you should retain that even if we change the default in the future. It's preferable to use reset-to-default though, it's certainly more resistant to typos.

Should you wish to see default value for a DB variable then the following command is useful, shown here for sys db restjavad.useextramb:

        printdb -n restjavad.useextramb

Increase restjavad memory

If you want to increase the heap size, this will need sys db provision.extramb to be at least as big as the increment above default size of 384 MB for provision.restjavad.extramb.  Then you just increase provision.restjavad.extramb to the value you want.

Here it has been increased to 600 MB, and provision.extramb is larger than the 216 MB increment above default amount of 384 MB:

        tmsh modify sys db provision.restjavad.extramb value 600

Resulting in this ltm log when restjavad is restarted:

        notice restjavad[xxxxx]: Maximum JVM heap size is  600 MB and Minimum heap size is 600 MB

In the example below provision.extramb wasn't quite big enough, just 200 MB, so the value of heap was capped to 584 MB - that doesn't change the value stored in provision.restjavad.extramb though, which remained at 600 MB. While this is usually harmless It may be worth adjusting provision.restjavad.extramb downwards to match what is in use if that works sufficiently well. Then if the capping threshold is changed in the future the restjavad heap size won't mysteriously change. So that would be a value of 584 MB here. Sorry for the fussy numbers, we should have rounded off restjavad size to 400 MB to make for easier arithmetic!

        notice restjavad[10373]: Warning - consider increasing provision.extramb  if insufficient: value of provision.restjavad.extramb, 600 MB, is larger than [provision.extramb + default heap size -> 584 MB]

Modifying provision.extramb restarts most F5 services, takes at least several minutes to settle afterwards, and is traffic impacting on an active unit. You'll probably want  to avoid doing it multiple times. You may want to consider setting provision.extramb slightly bigger if you're not sure exactly what restjavad heap size you need, or just if you know you need the extra host memory for reasons other than restjavad. With a bigger free memory space you can trial different values of provision.restjavad.extramb quite quickly as only the REST API should be affected when restjavad is restarted, and this should take only seconds typically.

Reduce restjavad memory heap size

For the final example we reduce the size of restjavad. This might possibly be of use for very small systems with very limited host memory where even 192 MB reclaimed is significant. Note though that the default value of 384 MB doesn't imply that much will be used, so it may not be necessary to lower the heap because the starting heap size will be 96 MB, and it may not grow to be bigger than 192 MB. Sometimes Java memory use does creep up as it depends on garbage collection to free memory. Setting a lower limit may help if it is still big enough to meet the needs of restjavad. The values below were default values for a few versions, they may well still work, but it's not guaranteed.

        tmsh modify sys db provision.restjavad.extramb value 192

The lower than normal size is logged in /var/log/ltm on restjavad start:

        notice restjavad[15206]: Heap size is smaller than default: starting 96 MB and maximum 192 MB


One more reminder: restjavad needs to be restarted after making changes to provision.restjavad.extramb:

        tmsh restart sys service restjavad    (or  bigstart restart restjavad )

If you don't do this it means the running restjavad will have different heap values and these will change unexpectedly at next reboot.

On the BIG-IP you can check the values of starting heap size (-Xms) and maximum heap size (-Xmx) in the command line arguments with this command (default values shown):

        # /bin/ps -p $(pidof java) | grep Rest | grep --color '\-Xms\|\-Xmx'
        ............ -Xms96m -Xmx384m ..............

In a qkview on ihealth it may be possible to look at restjavad -Xms, -Xmx arguments in the pstree command output.
The restjavad garbage collection logs (restjavad-gc.log) also show heap size when restarted and when GC operates.
 

Additional Information

       Upon install of software of a version with ID 1153865 fix the value of provision.restjavad.extramb in the new version will be set automatically with the aim of preserving the current restjavad heap size as far as is sensible. The version in use at time of software install and the value of restjavad.useextramb are inputs to this calculation. If you start on version A, install version B as a 'stepping stone' and then version C with this new behaviour (so  A  to B to C) the value of provision.restjavad.extramb will be based upon the value it would have had in version B, and not version A. 

       provision.restjavad.extramb now has a default value of 384 MB to match the default restjavad heap size from versions 15.1.3 and 14.1.4 and above. This replaces the default value of 192 MB from when it was introduced by ID 1025261. The minimum value remains 192 MB. 
       
       For values of provision.restjavad.extramb of 384 (the default) and lower the starting heap size is set at 96MB. This matches default behaviour for versions before 15.1.3 and 14.1.4 and will hopefully keep restjavad smaller where the REST API is only lightly or not used, though the heap is allowed to increase to 384 MB if necessary. For values of provision.restjavad.extramb above 384MB the starting heap size is set to the same value as maximum heap size. This matches behaviour in 14.1.4, 15.1.3 and above.

Going back to our earlier example:

        notice restjavad[xxxxx]: Maximum JVM heap size is  600 MB and Minimum heap size is 600 MB

You'll notice that the starting heap size has been set the same as maximum heap size when the value is above default. Setting starting heap size (-Xms)  to be the same as maximum heap size (-Xmx) helps preserve restjavad performance when it needs a lot of memory. It also will try to acquire all that memory when it starts and thus usually appear bigger in utilities such as top. On systems with not much host memory Linux may not allocate it all at once, and allocate some only when restjavad tries to use it. 

       If the previous version allowed restjavad heap to be  a range of possible values (so -Xms < -Xmx) then the update script will choose the higher of the two (-Xmx). If this would have resulted in a value less than the default of 384MB then the default will be used. Possibly the heap size actually in use was less so it might be that the value needs to be decreased, particularly on very memory constrained devices.

       Where provision.restjavad.extramb already existed but with a default value of 192MB the default value is updated to 384MB. If a value of provision.restjavad.extramb had previously been set by administrator action it will be honoured and preserved.

As well as a possible cap caused by the value of provision.extramb, the restjavad heap will possibly be capped to a sensible maximum chosen by F5. This will be similar on 64 bit and 32 bit versions of Java and for the latter chosen to keep it within 32 bit process limits. From 16.1 restjavad is 64 bit and the sensible maximum is 4000MB. Note also that provision.extramb in 17.1 can have a maximum value of 4096 MB (dropped from 8192 MB on previous versions). It will be very, very rare to need a restjavad heap size near that limit. Even 1000 MB is a very big restjavad.

The first row has a range of values because the starting value of heap is smaller than the maximum value. In upgrades to the new system the maximum value will be used but a smaller value may work, particularly for the larger values shown.
The row with mostly the value 192 MB is due to ID 1025261 where provision.restjavad.extramb was introduced, but is only used when restjavad.useextramb is true. It defaults to 192 MB though can be raised to the amount in one of the two rows above depending on version.

In the new system there is flexibility to set the maximum heap size within the ranges indicated, decoupling it from the value of provision.extramb for the lower value.

The starting heap value will be set to maximum value, aside from when provision.restjavad.extramb is at default 384 MB or lower, when starting value will be set to 96 MB.
