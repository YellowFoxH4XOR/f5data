Description

High Speed Logging (HSL) and syslog-ng are separate BIG-IP logging mechanisms. They can coexist, but they do not automatically send every message through both logging paths.

A BIG-IP log filter can redirect matching messages to the log publisher configured in that filter. The message is then sent to the log destinations configured in that log publisher. Therefore, a message captured by an HSL log filter may no longer be sent through the normal syslog-ng path unless the log publishers also contains the local-syslog destination.

This behavior can affect audit messages, including audit messages generated by mcpd.

Environment

  • BIG-IP LTM
  • High Speed Logging (HSL)
  • syslog-ng
  • Log filters
  • Log publishers
  • Local or remote logging destinations

Cause

When High Speed Logging (HSL) is configured in Log filters as Log publishers to remote logging destinations. The log may not log to local anymore but it is expected behaviour as the log is filtered and send to remote logging destination only. This is not related the log type and which daemon for the logging, the log filter may override and forward the log by its configuration.

For example, if you configured Log filter that forward the audit log to a remote logging destination with HSL, you will see the audit arriving remote logging destination.

However, the audit log will be missing in original local log files (/var/log/audit) which managed by syslogd. This is expected behaviour if you configure single log destination for HSL only in the log filter.

Recommended Actions

For logs forward by either HSL and local-syslog, follow K35284961: Filtering BIG-IP log messages to configure single log destination.

Sending Audit Messages Through Both HSL and syslog-ng

To send a matching audit message through both HSL and the local syslog-ng path, configure both destinations in the same publisher:

  • The HSL destination, such as HSL_destination_Splunk
  • The local-syslog destination

The HSL destination does not need to be removed. The publisher can contain multiple destinations, allowing the message to be delivered through both paths.

The resulting behavior is:

  1. The log filter evaluates the message.
  2. If the message matches the filter, BIG-IP sends it to the assigned publisher.
  3. The HSL destination sends the message through HSL and the errdefsd path.
  4. The local-syslog destination sends a copy through the local logging path.
  5. The message can be forwarded by syslog-ng and remain available in the applicable local BIG-IP log list.

Audit Message Handling

Audit messages require a specific clarification.

Under the normal behavior documented in K000133677:Audit logs not being sent to HSL, audit messages sent directly through the standard syslog() function are processed by syslog-ng and are not directly collected by HSL.

However, a BIG-IP log filter can capture and redirect a matching audit message before it follows the normal syslog-ng path. If the filter publisher contains an HSL destination, the matching audit message is sent to that publisher.

Consequently:

  • An audit message that does not match an applicable HSL log filter normally follows the syslog-ng path.
  • An audit message that matches a log filter whose publisher contains only an HSL destination is sent through HSL and is not automatically sent through syslog-ng.
  • An audit message that matches a log filter whose publisher contains both an HSL destination and local-syslog can be sent through both logging paths.
  • When the message is sent only to HSL, it may no longer appear under System ›› Logs : Audit : List.
  • When local-syslog is also configured in the publisher, the message can continue through the local logging path and remain visible in the applicable BIG-IP Audit log list.

Log-Filter Routing

A log filter does not automatically duplicate a message to all available logging mechanisms. It routes a matching message to the publisher assigned to the filter.

For example, if a filter matches an audit message generated by mcpd:

Publisher configurationResult for the matching audit message
HSL destination onlyThe message is sent through HSL. It is not automatically sent through the local syslog-ng path.
local-syslog onlyThe message is sent through the local logging path.
HSL destination and local-syslogThe message is sent through both HSL and the local logging path.

When a publisher contains only an HSL destination, the matching message may no longer be visible under System ›› Logs : Audit : List. This is expected because the message has been redirected away from the local logging destination.

The related routing behavior is documented in ID562242:Configuring log filters will redirect certain syslog messages. The bug states that configuring log filters can redirect certain syslog messages, including mcpd messages, to the destinations associated with the configured publisher.

Clarification of HSL and syslog-ng Coexistence

Important: Both logging methods, syslog-ng and HSL, can coexist, as log messages generated by the BIG-IP system that do not match HSL filtering criteria are passed from TMOS to syslog-ng for processing.

This should be interpreted as a description of the normal routing relationship for messages that are eligible for the standard syslog path and do not match an applicable HSL log filter. It should not be interpreted as a guarantee that all messages from all processes or daemons are sent through syslog-ng.

The actual path depends on:

  • The message source or daemon
  • The message type
  • The message severity
  • Whether the message matches a log filter
  • The publisher assigned to the filter
  • The destinations configured in that publisher
  • Whether the message is generated through the standard syslog() path
  • The normal local logging configuration

In summary:

  • Not every message generated by every process is handled by both mechanisms.
  • Native Linux system messages, such as messages from operating-system services, are generally handled by syslog-ng and are not directly collected by HSL.
  • BIG-IP module and data-plane messages are generally handled through HSL/errdefsd when configured for HSL.
  • Audit messages normally use syslog-ng, but a matching BIG-IP log filter can redirect them to an HSL publisher.
  • A message can use both paths only when the applicable publisher contains both the HSL destination and local-syslog.
  • A message captured by a log filter is sent according to that filter's publisher destinations; it is not automatically duplicated to a separately configured syslog destination.

Troubleshooting Missing Messages

When a message is missing from the remote syslog server or the BIG-IP GUI log list:

  1. Review all configured log filters.
  2. Identify the source, daemon, severity, and other criteria for each filter.
  3. Determine whether the message matches an HSL log filter.
  4. Identify the publisher assigned to the matching filter.
  5. Review every destination configured in that publisher.
  6. Determine whether the publisher contains:
    1. Only an HSL destination
    2. Only local-syslog
    3. Both an HSL destination and local-syslog
  7. Generate a test event that matches the filter.
  8. Verify the event at:
    1. The HSL destination
    2. The remote server receiving syslog-ng messages
    3. System ›› Logs : Audit : List, for audit events

Additional Information

For HSL configurations using the management interface, verify the management-port destination and publisher configuration. See K50040950:Configuring the BIG-IP system to send high-speed logs through the management interface.
