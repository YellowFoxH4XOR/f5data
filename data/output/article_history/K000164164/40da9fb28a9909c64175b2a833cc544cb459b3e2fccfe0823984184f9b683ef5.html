K000164164: BIG-IQ WAF Events Free-Text Search Times Out with Large Event Volumes

Published
2026-11-10
Updated
2026-11-10
Applies to

Source

Description

On BIG-IQ, the free-text filter on Monitoring > WAF > Events (Web Application Security events) can fail with the following error when the event database is large:

Error on server request 1. The system returned an unexpected error (400 Bad Request). Request timed out.

The free-text filter searches only the records already loaded in the GUI, not the full event database. When the database holds tens of millions of events, a search that uses leading and trailing wildcards (for example, *Mozilla*) can run until it times out. 

Environment

  • BIG-IQ deployed as a BIG-IQ Centralized Management (CM) and BIG-IQ Data Collection Device (DCD) cluster
  • Event storage: Elasticsearch with multiple event indices, millions of documents, and hundreds of shards
  • Connected BIG-IP systems generating millions of ASM events every couple of hours
  • ASM event logging configured to log all requests on the virtual servers
  • Search method: free-text wildcard search in the Events filter box with a 1-minute time range

Cause

The timeout results from two factors that combine:

  • Leading-wildcard free-text searches: Elasticsearch cannot use the sorted term index for a term that begins with * or ?. It must scan every term in the index. Elasticsearch documentation states: "In order to prevent extremely slow wildcard queries, a wildcard term should not start with one of the wildcards * or ?."
  • High event volume and shard count: Aggressive logging creates a very large document count and shard count. The GUI filter operates on loaded records and does not provide an efficient database-wide search, so large volumes lead to request timeouts.

Answer/Recommended Actions

  1. Use structured filters instead of the free-text box. Go to Monitoring > Events > Web Application Security > Events > Filters and Tags. Set a short time range and select a specific policy or virtual server.
  2. Avoid leading wildcards in search terms. Do not begin a search term with * or ?. If a search is required, use a trailing wildcard only.
  3. Reduce event logging on the BIG-IP systems:
    • Log illegal requests only, unless your environment requires logging all requests.
    • Remove duplicate logging profiles.
    • Limit Bot Defense logging to actionable events.
  4. Reduce shard count and stored data on the DCD:
    • Review the security-auditlog indices. These indices are not managed by the retention policy and can accumulate over time.
    • Remove old asmindex indices if they are not required (for example, keep only the last 3–4 days).
    • Remove stale empty indices from  past years (for example, bruteforceprimindex_2021*, bruteforcesecindex_2021*, botindex_2021*, asm-correlation_2021*).
    • Warning: Index deletion is destructive and cannot be undone. Confirm that the data is not required before you delete any index.
  5. Verify the results. Run the following commands on the DCD and CM, and confirm the shard count and cluster status have improved:
    curl -s localhost:9200/_cluster/health?pretty
    curl -s localhost:9200/_cat/allocation?v
  6. Use remote syslog for long-term retention. Forward events to a remote syslog server instead of storing them on the BIG-IQ Data Collection Device. Shorter raw retention also reduces the number of indices and shards.

Additional Information

  • Expected behavior: The free-text filter is limited to records already loaded in the GUI and is not intended for searching millions of records. This limitation also exists in the latest BIG-IQ release, so the steps above are the recommended path rather than a product fix.
