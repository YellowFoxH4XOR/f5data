Description

In a BIG-IP High Availability (HA) environment, you have configured the HA order within a traffic-group. During testing, you observe the following scenario:

  • BIG-IP01 is currently active, and BIG-IP02 is standby.
  • On BIG-IP01, the option 'Always failback to first device if it is available' has been enabled.
  • Subsequently, BIG-IP02 is moved to the top of the preferred order list within the traffic-group.

After saving these changes and syncing the device group, BIG-IP02 does not become active as expected.

Environment

This issue occurs in a BIG-IP HA environment involving two devices, for example, BIG-IP01 and BIG-IP02. The 'Always failback to first device if it is available' setting is enabled, typically configured with a specific timeout (e.g., within X seconds).

Cause

The auto-failback mechanism does not trigger in this scenario because the current active unit, BIG-IP01, became active as a result of a user action (manual configuration change) rather than a genuine failover event. Auto-failback is specifically designed to restore the preferred active unit's status only after it has previously failed over due to an operational issue.

Recommended Actions

Auto-failback is designed to automatically return the traffic-group to the preferred primary device when that device recovers from a genuine failover event. This functionality is intended for scenarios such as a Traffic Management Microkernel (TMM) process being killed or a loss of connectivity.

To verify that auto-failback works as expected, you should simulate a genuine failover:

  1. Ensure the preferred active unit (e.g., BIG-IP01) is currently active.
  2. Induce a genuine failover event on the active unit (BIG-IP01), such as restarting the TMM process or simulating a loss of connectivity.
  3. The peer device (BIG-IP02) will then become active.
  4. Once the original active (preferred) unit (BIG-IP01) recovers, the auto-failback feature should take over, causing BIG-IP01 to become active again.

Additional Information

To properly test the auto-failback feature, initiate the test with the preferred active unit already in an active state. Then, intentionally trigger a failover event, like restarting TMM on that unit. If configured correctly, a failback to the preferred active unit should occur upon its recovery.

Note: testing the auto-failback option might cause traffic impact, hence it is strongly recommended to have a maintenance window to perform this activity.
