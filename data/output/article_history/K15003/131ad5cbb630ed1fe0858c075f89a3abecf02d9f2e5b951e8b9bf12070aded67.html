Issue

Old Behavior

In versions prior to BIG-IP 11.5.0, on systems with Intel Hyper-Threading Technology (HT Technology) physical CPUs, each logical core (hyper-thread) has a separate Traffic Management Microkernel (TMM) running. Each HT Technology logical core processes tasks in both the data plane (TMM tasks) and control plane (non-TMM tasks). Having TMM share a logical core with control plane tasks requires the Traffic Management Operating System (TMOS) to perform context switching between TMM and control plane tasks. This context switching introduces latency that can impact performance. Additionally, control plane and TMM tasks may block each other. For example, a long-lived control plane task may block TMM and prevent it from servicing data plane or packet processing tasks. Similarly, a busy TMM may impede or prevent completion of control plane tasks, such as management tasks.

Note: The data plane relates to traffic processing (TMM tasks) while the control plane relates to computing, storing, and processing information (non-TMM tasks).

New Behavior

Beginning in BIG-IP 11.5.0, data and control plane tasks use separate logical cores on systems with HT Technology CPUs. The new split planes (HTSplit) behavior improves performance by dedicating and prioritizing resources for TMM. Meanwhile, all other processes can still perform control plane tasks (that is, non-TMM tasks), even while TMM is fully utilized.

The scheduler.splitplanes.ltm database key is enabled by default on all systems but affects only systems with HT Technology CPUs. When enabled, data and control plane tasks are split and handled by separate logical cores (hyper-threads).

Each HT Technology physical core has a single TMM running. The even-numbered hyper-threads (0, 2, 4, etc.) are dedicated to TMM as a high-priority process to service data plane tasks. The odd-numbered hyper-threads (1, 3, 5, etc.) process control plane tasks at a normal priority level. However, if TMM reaches 80% utilization, the odd-numbered hyper-thread throttles control plane tasks so they can use only 20%, allowing TMM to use the remaining resources. When this happens, the BIG-IP system logs a message to the /var/log/kern.log file that appears similar to the following example:

info kernel: ltm driver: Idle enforcer starting - tid: <pid> cpu: 1/1
info kernel: ltm driver: Idle enforcer exiting - tid: <pid> cpu: 1

Due to the absence of context switching, TMM performance is much more predictable, reducing latency from 10-15 milliseconds, in the worst case, to a few milliseconds. Additionally, management tasks remain responsive when TMM is heavily utilized. For example, management tasks that took more than 10 minutes to complete when TMM is fully utilized (such as loading a very large configuration) now complete in a few minutes.

Note: This change in behavior does not detrimentally affect license limits, and overall license limits that the platform applies do not change if you upgrade to BIG-IP 11.5.0 or later. For example, consider a VIPRION B2100 blade that you license for 500 Secure Sockets Layer (SSL) TPS per core. Before BIG-IP 11.5.0, this blade runs eight TMMs, and the overall SSL TPS limit is 500*8=4000. Beginning in BIG-IP 11.5.0, when you enable HTSplit, a B2100 blade runs only four TMMs. However, the BIG-IP system is aware of this change and correctly adjusts all license limits. The SSL TPS limit previously mentioned becomes 2*500*4=4000 and remains unchanged before and after BIG-IP 11.5.0.

For a list of BIG-IP platforms that include HT Technology, refer to K14358: Overview of Clustered Multiprocessing (11.3.0 and later).

Impact

  • TMM data plane performance improves.
  • When systems are heavily utilized, responsiveness for control planes improves, allowing for better manageability.
  • Fewer TMMs (one per physical core instead of one per thread) affects configuration settings and iRules that are configured based on the number of TMMs running on a system. For example, BIG-IP AFM denial-of-service (DOS) detection thresholds may be configured for a system with 12 TMMs. However, after you upgrade to BIG-IP 11.5.0, the system has only six TMMs running, which may result in false positive DOS detection alerts.
  • For Virtual Clustered Multiprocessing (vCMP) guests to use HTSplit, a vCMP hypervisor must be running 11.5.0 or later.
  • The tenant on VELOS and rSeries (r5000, r10000, and r12000 platforms) supports the HTSplit feature.

Recommended Actions

Review your configuration for any custom settings or iRules that may be affected by the number of TMMs running on the system.

Ensure that your vCMP hypervisor is running BIG-IP 11.5.0 or later, if you intend to have vCMP guests use the HTSplit feature.

Reverting to previous behavior

Do not revert to behavior from before BIG-IP 11.5.0, unless it is requested by F5 Technical Support. However, if it is required, you can disable the new split planes behavior and revert to behavior from before BIG-IP 11.5.0 by performing the following procedure:

Important: VELOS and rSeries platforms do not support disabling the HTSplit feature.

Impact of procedure: Performing this procedure may cause loss of performance and management response improvements. The following procedure requires a reboot of the system. Restarting services causes a brief traffic disruption.

  1. Log in to the Traffic Management Shell (tmsh) by typing the following command:

    tmsh

  2. Set the scheduler.splitplanes.ltm database key to false by typing the following command:

    modify sys db scheduler.splitplanes.ltm value false

  3. Restart the system by typing the following command:

    reboot
