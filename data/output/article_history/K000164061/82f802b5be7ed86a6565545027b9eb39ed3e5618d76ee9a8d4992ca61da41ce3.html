K000164061: Source IP Stickiness Does Not Maintain Client Affinity Across Multiple CE Sites in a Virtual Site

Type
Support Solution
Published
2026-10-30
Updated
2026-10-30
Applies to
  • F5 Distributed Cloud Services
  • F5 Distributed Cloud
Source
https://my.f5.com/manage/s/article/K000164061

Description

Source IP Stickiness does not keep a client on the same origin server when an HTTP Load Balancer is advertised from multiple Customer Edge (CE) sites grouped in a Virtual Site. Requests from the same client IP are forwarded to different origin servers in the same origin pool.

Symptoms:

  • Requests from the same client IP are sent to different origin servers.
  • Requests from the same client may be processed by different CE sites or different CE nodes.

Environment

  • F5 Distributed Cloud Services (SaaS)
  • HTTP Load Balancer advertised from two or more CE sites
  • Sites grouped in a Virtual Site
  • Origin pool with multiple origin servers
  • Load Balancing Algorithm set to Source IP Stickiness
  • Upstream router, firewall, or proxy that performs NAT or distributes connections across CE sites

Cause

  • Persistence is evaluated per CE site. Each CE site makes its own load-balancing and persistence decision. Persistence is not shared between CE sites.
  • A Virtual Site does not share persistence. A Virtual Site provides logical grouping and centralized configuration. It does not create a shared persistence domain across its sites.
  • Upstream distribution across sites. If an upstream router distributes one client's connections across different CE sites (for example, with a four-tuple ECMP hash), the client is not consistently associated with one site and, therefore, not with one origin server.

Answer/Recommended Actions

  1. Send each client's traffic to one CE site. Configure the upstream path so that requests from a given client consistently reach the same CE site. Persistence cannot follow a session between separate CE sites.
  2. Make upstream distribution consistent. If an upstream router or firewall load-balances across CE sites, configure a sticky hash, such as a two-tuple of source IP and destination IP, instead of a four-tuple hash. The exact configuration depends on the upstream device.
  3. Hash on a client-specific header when clients share a source IP. If the upstream device performs NAT or proxying, configure the HTTP Load Balancer hash policy to use a header that identifies the client:
    1. In the HTTP Load Balancer configuration, open the Load Balancing Algorithm settings.
    2. Select Ring Hash Policy and select Configure.
    3. Select Add, then set Hash Policy Specifier to Header Name.
    4. Enter the header name that has a unique, consistent value for a client. Confirm that the header is present on requests that reach the load balancer before you use it.
  4. Confirm the load balancing algorithm. Source IP Stickiness and header-based hashing are set through the Load Balancing Algorithm setting. The Trusted Client Headers setting is a separate feature and does not change the hash key.

Additional Information

  • Expected behavior: Source IP Stickiness has no session timeout. Requests from one client IP stay on the same origin server only when the origin pool members and their order remain the same, and all members remain healthy. Persistence is hash-based.
  • Expected behavior: Cookie-based persistence and header-based hashing have the same cross-site limitation. They do not keep a session on one origin server when consecutive requests are processed by different CE sites.
  • Expected behavior: Sites in the same Virtual Site can select different origin servers, because each site computes its own hash.
  • Validation: To test, send requests from one client through a single advertised path and confirm whether the same origin server responds. If the same client still reaches different origin servers on one CE site, collect request IDs, timestamps, source site, destination site, source IP, and destination IP for review.
