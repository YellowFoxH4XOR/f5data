K000163381: BIG-IP SSL Profiles: OCSP and CRL Validator Interaction and Precedence

Type
Support Solution
Published
2026-10-07
Updated
2026-10-07
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000163381

Description

When both OCSP and Dynamic CRL validators are configured on the same BIG-IP LTM Server SSL profile, OCSP takes precedence and the CRL validator is not used as a fallback. A certificate containing a CRL Distribution Point (CRLDP) but no OCSP responder URL can therefore be accepted even when it is listed as revoked in the CRL.

Observed results with a test certificate for example.com:

  • CRL validation only detected the revoked certificate and blocked the connection.
  • OCSP validation only made no OCSP request because the certificate had no OCSP responder URL.
  • OCSP and CRL validation together allowed the connection to proceed.

Environment

  • Product: BIG-IP LTM
  • Topology: F5 SSL Orchestrator explicit proxy
  • Profile type: Server SSL
  • Configured validators:
    • Dynamic CRL
    • OCSP
  • Certificate extensions:
    • AIA containing a CA Issuers URI only
    • No OCSP responder URI
    • CRLDP URI
  • The certificate was revoked and listed in the cached CRL.
  • The Server SSL profile required peer certificate validation.

The revoked-certificate response can be configured to either terminate the TLS connection or allow F5 SSL Orchestrator to display its policy block page, depending on the deployment design.

Cause

The validation implementation prioritizes OCSP when an OCSP validator is configured on the profile. Other configured validation methods, including Dynamic CRL validation, are bypassed instead of being used as fallback mechanisms.

The presence of an AIA extension does not necessarily indicate that a certificate contains an OCSP responder URI. In this scenario, the AIA extension contained only a CA Issuers URI.

Configuring both validators can therefore create a misleading configuration in which the Dynamic CRL validator is effectively inactive.

Recommended Actions

  1. Do not configure OCSP and Dynamic CRL together when CRL validation is required for certificates without an OCSP responder URI. The current implementation does not provide CRL fallback when OCSP is configured.
  2. For CRL-based validation, remove the OCSP validator and configure only the Dynamic CRL validator:
    tmsh modify ltm profile server-ssl <server_ssl_profile> ocsp none
    tmsh modify ltm profile server-ssl <server_ssl_profile> crl <crl_validator>
  3. For OCSP-only validation, remove the Dynamic CRL validator and configure only the OCSP validator:
    tmsh modify ltm profile server-ssl <server_ssl_profile> crl none
    tmsh modify ltm profile server-ssl <server_ssl_profile> ocsp <ocsp_validator>
  4. Inspect certificate extensions before selecting the validation method. Confirm separately whether the certificate contains:
    • An AIA OCSP responder URI
    • A CRLDP URI
    Do not treat the presence of any AIA extension as proof that OCSP is available.
  5. Verify CRL operation using validator statistics and logs. A successful CRL revocation check can produce output similar to:

    Total Certificate Status Queries 1

    Certificate Status Good 0

    Revoked 1

    Unknown 0

     

    Relevant log messages include:

    Cert status: revoked

    Certificate with subject name (...) and serial number (...) is revoked

  6. Select the revoked-certificate response behavior according to the deployment design:
    • Use a drop or reject response to terminate the TLS connection.
    • Use the appropriate F5 SSL Orchestrator response-control setting when the intended result is an SSL Orchestrator block page.
  7. Do not assume that configuring both validators provides defense in depth. A true OCSP-preferred and CRL-fallback mechanism requires product support for validator coexistence and fallback behavior.

Additional Information

  • The behavior is not caused by the absence of a CRLDP URI. The certificate contained a CRLDP URI, and CRL-only testing identified it as revoked.
  • OCSP-only validation recorded zero OCSP requests because the certificate did not contain an OCSP responder URI.
  • With both validators configured, the CRL validator did not receive the revocation query even though the cached CRL contained a matching revoked certificate.
  • The current implementation treats OCSP and Dynamic CRL as alternative validation methods rather than independent checks.
  • The configuration interface may allow both validators to be attached to a profile, but this does not mean both will be evaluated.
  • A fix is required to support true OCSP and Dynamic CRL coexistence with fallback behavior.
