K000164284: Pool Member status shows "enabled" instead of "disabled-by-parent" after reboot or upgrade when health check fails

Type
Support Solution
Published
2026-11-17
Updated
2026-11-17
Applies to
  • BIG-IP
  • BIG-IP LTM
Source
https://my.f5.com/manage/s/article/K000164284

Description

After rebooting or upgrading BIG-IP device, a pool's State changed from "disabled-by-parent" to "enabled" (Availability: offline, shown as a red diamond in the GUI). All pool members remained user-disabled, and their monitors were failing. The pool member configuration persisted through the upgrade.

Pre-upgrade or pre-reboot output:

Ltm::Pool: /Common/example_pool
Status
  Availability : offline
  State : disabled-by-parent
  Reason : The children pool member(s) are down
  Monitor : tcp

 

Post-upgrade or post-reboot output:

Ltm::Pool: /Common/example_pool
Status
  Availability : offline
  State : enabled
  Reason : The children pool member(s) are down
  Monitor : tcp

This behavior is expected. The pool state depends on the result of the first health check after a reboot or upgrade, not on the upgrade itself.

Environment

  • BIG-IP version: All TMOS versions
  • Pool with one or more user-disabled pool members
  • Pool member server is down or the monitored service is not responding
  • Event that triggers the change: reboot or upgrade

Cause

Expected behavior. The reported pool State is determined by the initial health-check result after a reboot or upgrade:

  • Health check fails from the start: The pool State is "enabled," even though the member is user-disabled and the pool Availability is "offline."
  • Health check passes initially, then fails: The pool State is "disabled-by-parent." After the server goes down, the pool continues to report "disabled-by-parent." After a reboot, if the first health check fails, the pool State changes to "enabled."

The key distinction is the initial health-check result—not whether the reboot follows an upgrade. Also, enabled describes the pool’s state; it does not mean the pool is available or its members are enabled.

Answer/Recommended Actions

(1) Verify the pool member's health status:

# tmsh show ltm pool <pool_name> members

 

(2) Restore the backend server or service so that the monitor passes.

(3) Do not use the pool "enabled" state as an indicator of availability. Instead, check the pool Availability and the member session status and monitor status.

(4) Re-enable the pool member only after the backend service is confirmed healthy.

(5) Review the health monitor configuration for the affected pool to confirm it reflects the expected service health.
