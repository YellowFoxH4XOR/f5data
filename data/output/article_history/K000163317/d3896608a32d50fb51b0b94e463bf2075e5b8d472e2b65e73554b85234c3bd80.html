1. Description

ACME account creation on BIG-IP LTM may fail and leave the ACME provider status as Error instead of Valid when the DNS resolver or internal proxy used by the ACME provider cannot reach its next-hop or destination through the configured TMM route domain.

The following messages may appear in the BIG-IP /var/log/ltm:

debug keymgmtd[6558]: 01a40000:7: curl_code: 56
debug keymgmtd[6558]: 01a40000:7: response_code: 0
debug keymgmtd[6558]: 01a40000:7: curl_err_str: Failure when receiving data from the peer
debug keymgmtd[6558]: 01a40000:7: content_type:
err keymgmtd[6558]: 01a40000:3: Failed to get ACME directory listing from https://<ACME_DIRECTORY_ENDPOINT>. curl_code=56,response_code=0, error=Failure when receiving data from the peer
err keymgmtd[6558]: 01a40000:3: Cannot take account action as directory listing is invalid

When an internal proxy is configured, it may return: 

HTTP/1.0 503 Service Unavailable
Connection: close
DNS lookup failed


These messages indicate that BIG-IP did not obtain a usable response from the ACME directory. They do not, by themselves, prove that the ACME directory is unavailable, that DNS resolution failed, or that the cause is a missing route. Interpret them together with the DNS resolver logs, TMM route information, packet captures, and firewall evidence collected during the same reproduction.


In the documented failure scenario, the DNS resolver assigned to the ACME internal proxy could not reach its configured nameserver through the resolver's TMM route domain. The resulting DNS failure prevented the internal proxy from establishing the outbound ACME connection.


The DNS resolver and internal proxy use BIG-IP networking objects and route-domain settings. A successful shell-based DNS or HTTPS test does not necessarily validate the exact resolver and proxy path used by the ACME operation. Validate the configured DNS resolver route domain, the internal-proxy route domain, the selected TMM source address, and the corresponding packet flow.


2. Environment


  • BIG-IP LTM
  • ACME provider configured with an ACME directory endpoint such as https://<ACME_DIRECTORY_ENDPOINT>
  • ACME provider configured with an Internal proxy

    • Internal proxy: /Common/acme_internal_proxy
    

  • DNS resolver associated with the internal proxy

    • DNS resolver: /Common/f5-aws-dns
    

  • TMM route domain configured for the internal proxy and DNS resolver

    • Proxy route domain: /Common/0
    



3. Cause


In the investigated failure scenario, the DNS resolver associated with the ACME internal proxy used a TMM route domain that had no usable path to its configured DNS nameserver.


As a result:


  • The TMM DNS resolver cannot send DNS queries to the configured resolver.
  • DNS resolution for the ACME hostname fails with resolver-generated SERVFAIL for A and AAAA queries.
  • When the TMM DNS resolver cannot reach the configured DNS server, it cannot resolve the ACME hostname. The internal proxy consequently cannot establish the outbound ACME connection and may return HTTP/1.0 503 Service Unavailable. keymgmtd reports curl_code=56, response_code=0, and an invalid ACME directory listing.
  • The ACME provider reports an invalid directory listing and remains in an error state.
  • Successful shell-based DNS or HTTPS tests do not necessarily validate the TMM path used by the ACME transaction. The shell test and the ACME transaction may use different routing contexts, source addresses, or interfaces. Verify the route and DNS activity for the TMM route domain used by the internal proxy and DNS resolver.


To determine whether missing or unusable TMM routing is the cause, identify the route domain configured on both the DNS resolver and the internal proxy. Then collect DNS resolver logs, a DNS packet capture, an internal-proxy capture, and the relevant TMM route information during the same reproduction.


  1. Enable temporary DNS resolver logging only if the setting is supported on the installed BIG-IP release (Debug logging can be noisy. Enable it only for the shortest period needed to reproduce the issue and monitor available local storage):

    tmsh modify sys db dnscacheresolver.loglevel value debug3
    

    1. Start the captures before reproducing the issue.
    

  2. Capture TMM DNS traffic:

    tcpdump -s0 -nni 0.0:nnnp -w /var/tmp/acme-dns.pcap 'port 53'

    

  3. Capture the internal-proxy connection:

    tcpdump -s0 -nni 0.0:nnnhp -w /var/tmp/acme-proxy.pcap host <INTERNAL_PROXY_IP> and port <INTERNAL_PROXY_PORT>

    

    1. Replace <INTERNAL_PROXY_IP> and <INTERNAL_PROXY_PORT> with the proxy address and port  shown in the keymgmtd log.
    

  4. Collect comparison tests from the BIG-IP shell::

    nslookup <ACME_ENDPOINT_FQDN>
zebos -r 0 cmd "show ip route"
zebos -r 0 cmd "show ip route database"
date -u

    

  5. Reproduce the issue

    1. Click Update for the ACME provider once.
    

  6. Stop both captures  with Ctrl+C.
  7. Restore normal DNS resolver logging:

    tmsh modify sys db dnscacheresolver.loglevel value notice

    

  8. Review the evidence

    1. Check /var/log/ltm for entries similar to:

      DNScache: resolving <ACME_ENDPOINT_FQDN>. A IN
DNScache: sending query
DNScache: error sending query to auth server
DNScache: configured stub or forward servers failed -- returning SERVFAIL
DNScache: return error response SERVFAIL

      

      • Correlate these entries with the packet capture and timestamp. The log messages support a DNS-resolution failure, but they do not alone identify whether the failure was caused by a missing route, an unreachable nameserver, a firewall policy, a return-path problem, or a DNS-server failure.
      

    2. Confirm the associated keymgmtd error:

      Failed to get ACME directory listing
curl_code=56
response_code=0
Failure when receiving data from the peer
Cannot take account action as directory listing is invalid
      

      • These messages show that keymgmtd did not obtain a usable ACME directory response. They are secondary evidence and must be interpreted together with the DNS, proxy, route, and firewall evidence.
      

    3. Review the route output:

      === route domain: 0 ===
      

      • 

        Do not conclude that a route domain has no installed routes from a heading-only ZebOS response alone. First confirm that the command executed successfully and that the output represents the TMM route table for the intended route domain.
        

        The missing-route diagnosis is supported when the authoritative TMM route output shows no usable route to the configured DNS nameserver, or when the route lookup selects an egress path that is not reachable from the relevant TMM self IP.
        

      • A shell-based nslookup test does not necessarily validate the TMM DNS resolver path. The shell command and the ACME transaction may use different routing contexts. Therefore, successful shell DNS or HTTPS tests do not, by themselves, prove that the TMM path used by the ACME internal proxy is functional. Verify the TMM route to the configured DNS resolver and correlate the result with TMM DNS logs.
      

    4. In the proxy capture, the expected failure pattern is:

      HTTP/1.0 503 Service Unavailable
Connection: close
DNS lookup failed

      

    

  9. 

    When the failure is caused by DNS or outbound-connectivity failure in the internal proxy, a capture may show some or all of the following:
    

    • The BIG-IP internal proxy listener is reachable from keymgmtd.
    • The TCP three-way handshake to port 39443 completed successfully for this transaction.
    • The CONNECT request for the ACME endpoint reached /Common/acme_internal_proxy.
    • The proxy returned HTTP/1.0 503 Service Unavailable.
    • The proxy closed the connection before a successful CONNECT tunnel was established.
    • No TLS ClientHello to the ACME endpoint was visible in this proxy-leg capture.
    



This capture confirms that the failure occurred after the CONNECT request reached the internal proxy and before a successful proxy tunnel was established. The proxy-leg capture alone does not determine whether the proxy attempted an outbound connection, whether DNS resolution failed, or whether an external firewall or other network device blocked the connection. Additional DNS, route, and firewall evidence is required.


Conclusion: If, during the same reproduction, the TMM DNS log shows repeated failures sending queries to the configured resolver or shows resolver-generated SERVFAIL, the proxy-leg capture shows the CONNECT request reaching the internal proxy and receiving HTTP/1.0 503 Service Unavailable, and the relevant route domain has no usable route to the configured resolver, the evidence supports missing or unusable TMM routing as the cause of the ACME failure.


The HTTP 503, curl_code=56, response_code=0, and invalid-directory messages are secondary symptoms in this evidence pattern. They do not, by themselves, indicate a problem with the ACME directory.


If the TMM DNS and route evidence is absent, investigate the DNS resolver and forward-zone configuration, the proxy or firewall path, TLS inspection or resets, and the ACME directory response before concluding that routing is the cause.


4. Recommended Actions


A valid TMM default route in the route domain used by the ACME internal proxy and its associated DNS resolver is generally preferred because ACME hostnames may resolve to multiple or changing IP addresses over time.


Route domain 0 is not automatically correct for every deployment. Configure the route in the route domain selected by the internal proxy and DNS resolver. Use route domain 0 only when it is the intended egress context for the deployment.


The route must use:


  • The appropriate TMM egress interface or self IP
  • A TMM gateway
  • A gateway directly reachable through a BIG-IP interface
  • A firewall policy that allows the resulting TMM source address
  • For Classic BIG-IP TMOS, K13833 documents the static-route syntax:

    tmsh
create /net route <route-destination/mask> gw <TMM-gateway>
list /net route
save /sys config
    



Please note: These routing commands apply to Classic BIG-IP TMOS. They do not apply to F5OS management-layer routing.


For a default route in the applicable Classic BIG-IP TMOS route domain, the destination would normally be represented as:


0.0.0.0/0


Do not add the route only to the management routing context or to an unrelated route domain. Verify that the route is installed in the route domain selected by /Common/acme_internal_proxy and that the DNS resolver used by that proxy is associated with the intended route domain.


5. Additional Information


1. Alternative Fix: Specific TMM Routes


If a TMM default route cannot be used, configure specific Classic BIG-IP TMOS routes in the applicable route domain for:


  • Every DNS server configured in the DNS resolver used by the ACME internal proxy.
  • The currently resolved ACME destination addresses or networks.


In the investigated deployment, adding TMM routes for the DNS resolver and the ACME endpoint allowed the internal proxy to complete the ACME transaction. Treat this as case-derived evidence rather than a universal result; validate the route, source address, gateway, and return path in each deployment.


However, this is less reliable for ACME because the hostname can resolve to multiple or changing IP addresses. A route to only one resolved address may stop working when DNS returns a different address.


Therefore:


  • Specific DNS routes are appropriate when the DNS server location is stable.
  • Specific ACME host routes should be treated as a workaround or controlled design choice.
  • A valid TMM default route is preferred because newly resolved ACME addresses can use it automatically without manual route updates.


The static route must use a TMM-reachable gateway and must not create an asymmetric path.


 


2. Firewall Requirements


The firewall must permit traffic from the actual TMM source or egress address selected for the applicable route domain to:


  • The configured DNS resolver over DNS, normally UDP/TCP port 53.
  • The resolved ACME endpoint over HTTPS, normally TCP port 443.
  • Any external proxy or other egress device required by the network design.


In the investigated deployment, TCP port 39443 was the local BIG-IP internal-proxy listener. Do not treat this port as universal; verify the listener port and topology on the affected system. It normally does not need to be allowed through the external firewall unless the network topology places that connection across a firewall.


If the TMM route and DNS checks are correct but the ACME operation still fails, ask the firewall team to correlate the exact reproduction timestamp and verify:


  • Whether the TMM connection reached the firewall.
  • Whether DNS traffic was permitted and whether the response returned.
  • Whether the HTTPS connection to the resolved ACME address was permitted.
  • Whether the CONNECT-related traffic was allowed.
  • Whether TLS inspection was applied.
  • Which device sent the FIN or TCP reset:
    CONNECT <ACME_ENDPOINT_FQDN>:443 HTTP/1.1
HTTP/1.0 503 Service Unavailable
FIN, ACK
    

  • Whether the firewall used the expected TMM source or egress address.


A successful management-plane DNS or HTTPS test does not prove that the firewall permits the TMM path used by the ACME internal proxy. Correlate the exact reproduction timestamp with the TMM source address, DNS request and response, resolved ACME destination, and outbound HTTPS connection.
