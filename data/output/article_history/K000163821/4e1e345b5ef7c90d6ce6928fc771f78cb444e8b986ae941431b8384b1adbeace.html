Security Advisory Description

  • CVE-2026-109618 (also known as php2shell)

    PHP uses longjmp() for out-of-memory (OOM) errors to exit the current context and abort handling of the request. Some contexts may not properly account for this scenario and leave request memory in an uninitialized state before performing an allocation. The subsequent request cleanup procedure may read or branch on this memory. Multiple OOM strategies can consistently trigger this condition and lead to remote code execution (RCE).

  • CVE-2026-109619 (also known as php2shell)

    PHP has various global state that temporarily points into request memory. In some scenarios, global state may not be correctly reset, or may be repopulated after being reset. The global state may then refer to request memory even after it has been freed. Subsequent requests may read or branch on this stale state before it is fully initialized. Multiple strategies can trigger this condition and produce remote code execution (RCE).

Impact

  • APM Data Plane
    This vulnerability may allow a remote unauthenticated attacker to execute arbitrary system commands, create or delete files, or disable services.
  • Control Plane
    This vulnerability may allow a remote authenticated attacker to execute arbitrary system commands, create or delete files, or disable services.

Security Advisory Recommended Actions

The following section provides information on mitigations for BIG-IP on both control and data plane, along with mitigations that can be applied to protect backend applications.

Mitigation

  • BIG-IP mitigation
  • BIG-IP Configuration utility mitigation
  • Protection for your backend pool members

BIG-IP mitigation

The following mitigates BIG-IP control plane configuration utility exposure as well as BIG-IP APM data plane exposure.

At a high level, the admin needs to login on BIG-IP with advanced shell, create a new file with the content below, and restart apache.

Important: F5 recommends that you verify the following php.ini configuration in your testing/staging environment before deploying to your production environment.

Note: If you have a multi bladed system these steps must be done on each individual blade.

  1. Create a new file - /etc/php.ini.d/K000163821.ini and include the content below.

    ; The configuration mitigations recommended by PHP for CVE-2026-109618 and CVE-2026-109619
    ; These will NOT survive an upgrade of BIG-IP TMOS.
    memory_limit = -1
    post_max_size = 8M
    upload_max_filesize = 7M
    session.upload_progress.enabled = 0

  2. Restart apache using bigstart restart httpd.

    On multi-bladed systems, restart apache using clsh bigstart restart httpd.

  3. Only for BIG-IP APM systems, restart apache using bigstart restart httpd_sam.

    On multi-bladed BIG-IP APM systems, restart apache using clsh bigstart restart httpd_sam.

    Note: Restarting the httpd_sam process may disrupt webtop connections, requiring users to reconnect.

  4. If you have configured a device group, repeat on each high availability (HA) peer in the group.

BIG-IP Configuration utility mitigation

In addition to the above mitigation, you can also restrict access to the Configuration utility (the control plane) using the following procedures:

  • Block Configuration utility access through self IP addresses
  • Block Configuration utility access through the management interface

Block Configuration utility access through self IP addresses

You can block all access to the Configuration utility of your BIG-IP system using self IP addresses. To do so, you can change the Port Lockdown setting to Allow None for each self IP address on the system. If you must open any ports, you should use the Allow Custom option, taking care to block access to the Configuration utility. By default, the Configuration utility listens on TCP port 443. If you modified the default port, ensure that you block access to the alternate port you configured.

Note: Performing this action prevents all access to the Configuration utility and iControl REST using the self IP address. These changes may also impact other services, including breaking high availability (HA) configurations. For more information, refer to K46122561: Restrict access to the BIG-IP management interface using network firewall rules.

Before you make changes to the configuration of your self IP addresses, F5 strongly recommends that you refer to the following articles:

  • K17333: Overview of port lockdown behavior (12.x - 17.x)
  • K13092: Overview of securing access to the BIG-IP system
  • K31003634: The Configuration utility of the Single-NIC BIG-IP Virtual Edition now defaults to TCP port 8443
  • K51358480: The single-NIC BIG-IP VE may erroneously revert to the default management httpd port after a configuration reload

If you must expose port 443 on your self IP addresses and want to restrict access to specific IP ranges, you may consider using the packet filtering functionality built into the BIG-IP system. For more information, refer to the following article:

  • K13383: Configure CIDR Network Addresses for the BIG-IP packet filter

Block Configuration utility access through the management interface

To mitigate this vulnerability for affected F5 products, you should restrict management access to F5 products to only trusted users and devices over a secure network. For more information about securing access to BIG-IP systems, refer to the following articles:

  • K13309: Restricting access to the Configuration utility by source IP address (11.x - 17.x)
  • K13092: Overview of securing access to the BIG-IP system
  • K46122561: Restrict access to the BIG-IP management interface using network firewall rules

Protection for your backend pool members

Important: The following BIG-IP controls reduce exposure to specific attack paths but do not replace patching.

PHP RCE from out-of-memory (OOM) corruption - CVE-2026-109618

Before configuring the BIG-IP system

  • Identify all ASM policies protecting the affected PHP applications.
  • Save backups of all identified policies.
  • Review legitimate upload, form, and API requirements before introducing restrictions.

Recommended BIG-IP Advanced WAF/ASM configuration

Block unnecessary multipart requests

For applications that do not require multipart submissions:

  1. Open the relevant security policy’s Allowed URLs configuration.
  2. In Header-Based Content Profiles, add or modify an entry matching the Content-Type header for *multipart*.
  3. Set the action to Disallow.
  4. Enable Alarm and Block for Illegal request content type.
  5. Apply the restriction to all relevant URL entries (explicit and wildcards).

This prevents blocked requests from reaching PHP’s multipart parser. It will also prevent legitimate multipart uploads and forms.

Limit request size

In the policy’s File Types configuration:

  • Enable POST Data Length checking and set the smallest maximum body size the application requires.
  • Enable Request Length checking and set an appropriate total-request limit, allowing for headers and the URL.
  • Review explicit file types, the wildcard entry, and the no-extension entry.
  • Enable Alarm and Block for Illegal POST data length and Illegal request length.

PHP recommends a conservative backend post_max_size: 8M where uploads are unnecessary or 32M where uploads are required. These are exposure-reduction guidelines, not guaranteed safe WAF thresholds. The WAF max request buffer size is by default 10M so the recommendation is to limit to 8M.

Limit input complexity and enforce protocol checks

Under HTTP Protocol Compliance, enable:

  • Check maximum number of parameters — reduce the maximum to the application’s required count.
  • Check maximum number of headers — set an application-appropriate maximum.
  • Bad multipart/form-data request parsing.
  • Bad multipart parameters parsing.
  • Unparsable request content.
  • Several Content-Length headers.
  • Chunked request with Content-Length header.

Enable Alarm and Block for HTTP protocol compliance failed. Also configure an appropriate HTTP header-length limit and block Illegal header length. Where practical, allow only expected form parameters. If array-style parameter names are unnecessary, restrict, and in parameter names and block Illegal meta character in parameter name.

Important: Small, valid multipart requests can still cause excessive PHP memory allocation. Ordinary HTTP header limits do not establish a limit on headers inside multipart parts, and parameter-count checks must not be assumed to count every empty file control. These controls do not fully address all documented OOM techniques.

Require a declared length for POST requests

Where application compatibility permits, reject POST requests without a valid Content-Length header. This reduces exposure to the documented attack path in which PHP processes multipart data without a usable declared length.

  • Under HTTP Protocol Compliance, enable POST request with Content-Length: 0.
  • Enable Alarm and Block for HTTP protocol compliance failed, then apply the policy.
  • Separately enforce the presence of Content-Length on POST requests using a method-scoped BIG-IP local traffic policy or iRule. The POST request with Content-Length: 0 check should not be treated as a general missing-header check.
  • Continue enforcing actual request-body size limits and rejecting ambiguous framing, including requests containing both Transfer-Encoding and Content-Length.

Compatibility impact: Requiring Content-Length rejects otherwise valid chunked POST requests and HTTP/2 POST requests that omit it. Blocking zero-length POST requests can also disrupt legitimate application workflows.

Limitation: A valid Content-Length does not prevent memory amplification or other OOM triggers. These restrictions reduce exposure but do not replace updating PHP.

Apply the policy and validate
  1. Set the policy to Blocking, resolve relevant staging or bypass exceptions, and Apply Policy.
  2. Confirm prohibited and over-limit requests are blocked before reaching PHP.
  3. Test legitimate uploads, forms and APIs, and monitor WAF events and application availability.
  4. Prevent direct-origin access that bypasses the BIG-IP system.
  5. Complete the PHP update promptly, then review temporary restrictions.

Mitigation Configuration on BIG-IP Advanced WAF/ASM for CVE-2026-109619

Block the PHP session upload-progress parameter (Where PHP session upload progress is not required)

Under Security --> Application Security --> Parameters --> Parameter List:

  1. Create an Explicit parameter named PHP_SESSION_UPLOAD_PROGRESS, or the name configured in PHP’s session.upload_progress.name.
  2. Set its value type to User Input and data type to Alpha-Numeric.
  3. Enable regular-expression validation with an expression that rejects every value. (?!) is a candidate deny-all PCRE expression; confirm that the deployed BIG-IP version accepts and enforces it.
  4. Disable Allow Empty Value so an empty value cannot bypass validation.
  5. Leave Mandatory disabled—requests without this parameter should remain allowed.
  6. Disable staging for this parameter.

Under Security --> Application Security --> Policy Building --> Learning and Blocking Settings:

Enable Alarm and Block in the Parameters section for:

  • Parameter value does not comply with regular expression
  • Illegal empty parameter value

Ensure the policy is in Blocking mode and Apply Policy.

Review URL-specific definitions that could override a global parameter definition. Ensure multipart bodies are parsed as Form Data.

Validate: Requests containing the parameter, with either empty or non-empty values, must be blocked. Requests without it should continue working, including those permitted by existing wildcards.
