Description

The ASM internal DCC database corruption during an upgrade may cause issues such as transparent security policies unexpectedly switched to blocking mode after the upgrade.

Environment

  • AWAF/ASM upgrade

Cause

The ASM DCC database may become corrupted during an upgrade for various reasons, such as an interrupted upgrade process or insufficient free space in the /var partition.

Answer/Recommended Actions

Follow these steps to manually run the upgrade script:

1. Create a new UCS archive on the upgraded BIG-IP system.

tmsh save sys ucs K67645520.ucs

2. Extract the UCS archive to a temporary directory.

rm -rf /var/tmp/UCS 
mkdir -p /var/tmp/UCS
cd /var/tmp/UCS
tar -xzf /var/local/ucs/K67645520.ucs

3. Set the required permissions.

chmod a+xw /var/tmp/UCS
chmod a+xw /var/tmp/UCS/var/tmp

4. Run the upgrade script using with a slight spoof of the UCS version .This forces all security policies in the UCS archive to reactivate, effectively repopulating the DCC database.

/usr/share/ts/bin/ts_configsync.pl -a load --ucs_version <source_version> --bigip_version <target_version> --dir /var/tmp/UCS/var/tmp

For example, if the system is running ASM 15.1.5.1 and the UCS archive was created on the same version, specify 15.1.5.0 as the UCS source version. This slight version mismatch causes the script to rerun the upgrade process while still allowing it to complete successfully.

/usr/share/ts/bin/ts_configsync.pl -a load --ucs_version 15.1.5.0 --bigip_version 15.1.5.1 --dir /var/tmp/UCS/var/tmp

This process may take more than 30 minutes based on the size of the ASM configuration. You can monitor its progress in /var/log/asm.

5. Delete the temporary files after the process is complete.

rm -rf /var/tmp/UCS
