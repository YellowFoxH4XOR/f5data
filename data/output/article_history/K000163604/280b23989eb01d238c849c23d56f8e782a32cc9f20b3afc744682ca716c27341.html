K000163604: NGINX Ingress Controller: Unix Socket Path Length Limit for TransportServer and VirtualServer Resources

Type
Support Solution
Published
2026-10-08
Updated
2026-10-08
Applies to
  • NGINX Products
  • NGINX Ingress Controller
Source
https://my.f5.com/manage/s/article/K000163604

Description

NGINX Ingress Controller derives Unix domain socket paths for TransportServer passthrough listeners from the Kubernetes namespace and resource name. When the generated path exceeds the operating system limit, NGINX rejects the listen directive during configuration reload:

too long path in the unix domain socket in

"unix:/var/lib/nginx/passthrough-<namespace>_<metadata.name>.sock"

of the "listen" directive

The affected resource may enter the following state:

state: Invalid

reason: AddedOrUpdatedWithError

Environment

  • NGINX Ingress Controller with NGINX Plus
  • Kubernetes TransportServer resources using passthrough listeners, such as TLS_PASSTHROUGH
  • VirtualServer or TransportServer resources with long combined namespace and metadata.name values
  • Generated socket path template:

    /var/lib/nginx/passthrough-<namespace>_<name>.sock

Cause

Unix domain sockets use a fixed-size sun_path field. On Linux-based systems, the field is 108 bytes, with filesystem socket paths supporting up to approximately 107 characters.

The static portion of the NGINX Ingress Controller socket path is 33 characters:

/var/lib/nginx/passthrough-_.sock

The combined namespace and CRD metadata.name values should therefore remain within approximately:

  • 74 characters on Linux-based systems
  • 70 characters on BSD-based systems, including macOS

When the combined values exceed the available length, NGINX rejects the generated configuration and the resource cannot be applied successfully.

Recommended Actions

  1. Use shorter namespace and resource names.

    Keep the combined namespace and metadata.name length within the applicable operating system limit. On Linux-based systems, use a combined length of no more than approximately 74 characters.

  2. Inspect generated socket paths.

    Run the following command from the NGINX Ingress Controller pod:

    kubectl -n nginx-ingress exec "$POD" -- sh -c \ "grep -rho 'unix:/var/lib/nginx/passthrough-[^ ;]*' /etc/nginx/stream-conf.d/ \ | sed 's|^unix:||' | awk '{print length(\$0), \$0}' | sort -rn"

    Review paths that approach or exceed 107 characters.

  3. Validate resource names before deployment.

    Use an admission policy, such as Kyverno, to prevent TransportServer and VirtualServer resources from being created or updated when their namespace and metadata.name values would generate an overlong socket path.

    The validation must account for the complete socket path template and the namespace length, rather than validating only the resource name.

  4. Enable configuration safety where supported.

    NGINX Ingress Controller 5.4.x introduced the experimental -enable-config-safety option. Enable it in the controller deployment:

    kubectl -n nginx-ingress edit deploy/nginx-ingress-controller

    Set the option to:

    -enable-config-safety=true

    This feature rejects invalid configurations and helps preserve the last known good configuration. It does not increase the operating system’s Unix domain socket path limit.

  5. Use a product fix when available.

    A product fix can prevent this condition by validating the combined namespace and resource name before rendering the NGINX configuration or by shortening or hashing the generated socket path.

Additional Information

  • Kubernetes can accept a resource even when NGINX later rejects the generated configuration.
  • The failure is caused by the generated Unix domain socket path, not by the functional TransportServer or VirtualServer configuration.
  • Increasing the Kubernetes CRD name limit does not resolve the operating system socket-path restriction.
  • Reducing the namespace or resource name is the current workaround.
  • Configuration safety can limit the impact of an invalid resource on other managed resources, but it does not remove the Unix domain socket path restriction.
