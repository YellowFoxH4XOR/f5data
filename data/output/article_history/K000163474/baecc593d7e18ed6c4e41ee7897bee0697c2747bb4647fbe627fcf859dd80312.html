Description

When reviewing changes to BIG-IP iRules, a match on a logging or connection command is a reason to inspect the rule, not evidence of malicious activity. Review whether the changed code can read sensitive traffic data and pass it to a destination that is not approved for that data.

Environment

  • BIG-IP LTM

Cause

A potential exposure path exists when an applicable iRule event reads request or response data and a reachable code path logs or sends that data to a recipient not approved for it. Output may be a locally retained or forwarded log, a directly remote log call, high-speed logging, or a sideband send. The path depends on the data selected, conditions and transformations in the rule, the virtual server and profiles in use, and the actual destination. This is a review mechanism, not a claim of a product vulnerability or a confirmed disclosure.

Recommended Actions

  1. Identify the changed rule and its traffic scope:
    Compare the current definition with an approved prior version and review the virtual servers that reference it.
    Run:
    tmsh list ltm rule <IRULE-NAME>
    Run:
    tmsh list ltm virtual <VIRTUAL-SERVER>
    Check the attached rules, profiles, event blocks, conditional branches, and referenced objects. A command in an unattached rule, unreachable branch, or inapplicable event is not by itself evidence that traffic was sent.
  2. Trace the data selected by the rule:
    Inspect whether the changed code accesses sensitive HTTP headers with HTTP::header or collected body content with HTTP::payload after HTTP::collect. Identify the specific field or portion selected, any filtering or masking, and the event and conditions under which it is available. Reading or modifying data alone does not establish that it was disclosed.
  3. Trace each output and its recipient:
    Inspect the arguments of each reachable log call to determine whether it includes the selected data. Check where local logs are retained or forwarded; a directly remote log call can instead send to a specified IP address via UDP. For high-speed logging, follow HSL::open to the referenced pool or publisher and check what data is supplied to HSL::send. For sideband traffic, review the destination supplied to connect and the data supplied to send. Validate each recipient and the data it is authorized to receive; opening a handle or connection alone is not proof of disclosure.
  4. Resolve unexpected paths through change control:
    Ask the rule owner to confirm the intended purpose and authorized destinations. If the code or recipient is unexpected, preserve the relevant change and destination evidence for the security response team. Limit access to exported configurations and logs because they may contain sensitive data; avoid copying raw payloads into review notes.

Additional Information

  • Logging, HTTP payload inspection, and sideband connections also have legitimate application and diagnostic uses. Assess the combination of data source, executable event, conditional path, and recipient rather than treating a keyword match as a verdict.
  • This is a focused review checklist, not an exhaustive iRules command inventory or a method for proving that data left the system. The presence or absence of these particular commands alone cannot establish historical disclosure.
