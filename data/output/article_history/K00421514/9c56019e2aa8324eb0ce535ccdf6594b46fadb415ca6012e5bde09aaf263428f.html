Description

While taking a snapshot of the BIG-IP VE, a failover or active/active period occurs.

Messages similar to the following may appear in /var/log/ltm:

notice tmm[16072]: 01010029:5: Clock advanced by 10893 ticks

sod[6009]: 010c0083:4: No failover status messages received for 3.800 seconds, from device BIGIP-A.example.com (192.168.1.2) (unicast: -> 10.10.20.1).

Environment

  • BIG-IP VE
  • Failover
  • Snapshots

Cause

The snapshot process freezes the whole BIG-IP VE at points, including TMM, so no traffic is passing at that time. When TMM starts running again, it sees that it essentially jumped to some point in the future, hence the clock advances.

From the peer system's perspective, the active system is unresponsive during this time, so if it does not receive a failover packet by the configured failover.nettimeoutsec value (default 3 seconds), it will go active.

sys db failover.nettimeoutsec {
    default-value "3"
    scf-config "true"
    value "3"      <---------
    value-range "integer min:1 max:120"
}

Recommended Actions

Taking snapshots in this way is not recommended. The recommended way to back up the system is to use UCS archives.

If you still want to make snapshots, you can disable the memory option of the snapshot, the backup will still be valid, but the BIG-IP VE will need to be rebooted after the backup is restored, but in most cases, when you have a failure of the BIG-IP VE, this will need to be done anyway, so it does not affect the validity of the backup. Alternatively, shut down the BIG-IP VE before taking a snapshot.

Additional Information

These symptoms can also appear as a result of other issues on the hypervisor host, such as storage latency or over-commitment of resources.
